# sources/sync-backup/syncthing/lib/relay/protocol/packets_xdr.go

## Purpose
Generated XDR serialization/deserialization code for relay protocol packets defined in `packets.go`.

## Important APIs, Types, and Functions
For each packet type, the file provides `XDRSize`, `MarshalXDR`, `MustMarshalXDR`, `MarshalXDRInto`, `UnmarshalXDR`, and `UnmarshalXDRFrom` where relevant. It enforces maximum lengths for `JoinSessionRequest.Key`, `ConnectRequest.ID`, and `SessionInvitation` fields `From`, `Key`, and `Address`.

## Control Flow
Marshal methods allocate a buffer of computed size, create an `xdr.Marshaller`, write fields in protocol order, and return any marshaller error. Unmarshal methods create an `xdr.Unmarshaller`, read fields in order, and return the unmarshaller error. Empty packets marshal/unmarshal to no payload.

## State and Persistence Behavior
No state is stored. The code transforms in-memory packet structs to/from byte slices used by relay connections.

## Dependencies and Integration Points
Depends on `github.com/calmh/xdr` and is generated by `go tool genxdr`. `relay/protocol/protocol.go` calls these methods when reading and writing relay messages.

## Risks and Edge Cases
Manual edits would be overwritten and risk wire incompatibility. XDR max-length checks are critical because `ReadMessage` permits up to 1024-byte payloads while individual fields have tighter limits. `MustMarshalXDR` panics on marshal errors, so it should only be used where inputs are guaranteed valid.

## Test Signals
Compile coverage ensures generated APIs match packet definitions. Interoperability tests should round-trip all packet types, reject overlong fields, and validate compatibility with existing relay servers.
