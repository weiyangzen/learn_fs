# sources/object-store/rustfs/crates/ecstore/src/bucket/replication/replication_pool.rs

Purpose: Implements the RustFS replication worker pool and its global scheduling facade. It accepts object and delete replication work, fans it out to regular, large-object, and MRF retry workers, persists overflowed failures for restart recovery, initializes global replication stats, and bridges bucket resync lifecycle calls to `ReplicationResyncer`.

Important APIs and types: `ReplicationPool<S>` owns worker channels, active counters, `ReplicationStats`, storage, worker limits, MRF persistence channels, task handles, and an embedded `ReplicationResyncer`. `ReplicationPoolOpts` selects `ReplicationPriority::{Fast, Slow, Auto}` and maximum worker caps. `ReplicationQueueAdmission::{Skipped, Queued, Missed}` reports queue outcomes, with `merge()` making `Missed` dominate `Queued`, and `Queued` dominate `Skipped`. `ReplicationOperation` wraps either `ReplicateObjectInfo` or `DeletedObjectReplicationInfo` and implements `ReplicationWorkerOperation`, including conversion to `MrfReplicateEntry`. `ReplicationPoolTrait` exposes object-safe async operations through `DynReplicationPool` and the `GLOBAL_REPLICATION_POOL`/`GLOBAL_REPLICATION_STATS` once cells.

Control flow: `ReplicationPool::new()` derives regular/MRF worker counts from priority, applies max caps, creates bounded Tokio MPSC channels, spawns large, regular, and failed/MRF workers, then starts MRF replay and MRF persistence background tasks. Regular and large workers consume `ReplicationOperation` values and call `replicate_object()` or `replicate_delete()`; regular and MRF object workers also increment and decrement per-bucket queue stats. Object queueing hashes bucket plus object name to a stable worker channel, while large objects of at least `MIN_LARGE_OBJ_SIZE` are hashed onto the large-worker pool. Heal and existing-object operations are routed directly to MRF retry workers. Delete queueing follows the same regular-or-MRF routing but always records zero-size delete queue stats.

State and persistence behavior: Live state is held in Tokio `RwLock`/`Mutex` structures and atomic active-worker counters. Overflowed normal queue work is converted to `MrfReplicateEntry` and sent to `mrf_save_tx`; the persister flushes pending entries to `config/replication/mrf.bin` every 10 seconds or after 1000 entries. Startup MRF replay reads that file, decodes entries, re-queues object entries through `queue_replication_heal()` after fresh `get_object_info()`, re-queues delete entries through `schedule_replication_delete()`, then clears the file only after processing the entries. Resync state is loaded from `${BUCKET_META_PREFIX}/{bucket}/.replication/resync.bin`, cached in the resyncer map, and auto-resumed only for `ResyncPending` and `ResyncStarted`; failed resync targets are deliberately skipped until manually restarted.

Dependencies and integration points: The pool depends on `StorageAPI + NamespaceLocking` for object IO and locks, `ObjectIO` for config persistence, `ReplicationStats` for queue/proxy metrics, `BucketTargetSys` and `metadata_sys` for heal decision setup, `save_config`/`read_config` for metadata files, `rustfs_filemeta` replication structs and status maps, Tokio channels/tasks, and `CancellationToken` for resync startup/cancel. Public entry points `schedule_replication()`, `schedule_replication_delete()`, `queue_replication_heal()`, and `queue_replication_heal_internal()` are the integration layer used by object mutation paths, MRF replay, and healing/resync scans.

Resync integration: `start_bucket_resync()` creates or updates a target status as `ResyncPending`, persists it, registers a cancellation token keyed by bucket and ARN, then spawns `ReplicationResyncer::resync_bucket()`. `cancel_bucket_resync()` cancels the token and marks the target `ResyncCanceled`. `init_resync_internal()` launches `start_resync_routine()`, which repeatedly calls `load_resync()` until it succeeds or the supplied token is cancelled. `load_resync()` reads persisted metadata for each bucket, repopulates the in-memory map, and starts a new resync task for any target still pending or started.

Scheduling details: `schedule_replication()` converts an `ObjectInfo` and `ReplicateDecision` into `ReplicateObjectInfo`, preserving target status maps, purge status maps, replication state, actual size, tags, timestamps, and operation type. Synchronous decisions call `replicate_object()` immediately; asynchronous decisions use the global pool. `schedule_replication_delete()` queues delete work and updates stats for pending delete targets. `queue_replication_heal_internal()` builds a heal `ReplicateObjectInfo`, skips zero mod-time objects and missing configs, routes failed/pending normal objects to object heal work, routes delete markers and version-purge failures to delete heal work, and fans existing-object delete resync across selected targets using `queue_replicate_deletes_wrapper()`.

Risks: Backpressure fallback to MRF is lossy when the MRF save channel is full; warnings state that dropped entries will not be retried. The MRF persister overwrites the file with only its current in-memory pending buffer, so if the file already contains unreplayed entries while the process is running, callers must ensure startup replay has cleared or requeued them before new flushes become authoritative. `resize_failed_workers()` sends kill notifications but the spawned shared-receiver MRF workers do not read `mrf_worker_kill_tx`, so decreasing `mrf_worker_size` changes the counter but may not actually stop workers until channels close. `ReplicationPoolTrait::resize()` calls `self.resize(...)`, but no inherent `resize` method is present in this file; this may rely on another method not shown by this file or be a recursion/compile risk. MRF replay for object entries skips objects that are no longer found, while delete entries avoid source lookups; that asymmetry is intentional but important for recovery semantics. The global once cells make reconfiguration difficult after initialization. Worker task handles are stored but no shutdown/join lifecycle is implemented here.

Test signals: Unit tests cover queue-admission merge ordering, auto-resume status selection, MRF encode/decode round trips for object/delete/versioned-delete/mixed entries, routing defaults for legacy MRF entries without an `op` field, and legacy MRF binary compatibility. Additional valuable tests would exercise worker resize down behavior, queue full admission for regular and large queues, MRF persister append/overwrite semantics across multiple flushes, restart replay idempotence, global pool initialization idempotence, `schedule_replication()` synchronous versus asynchronous paths, and stale or failed resync recovery behavior.
