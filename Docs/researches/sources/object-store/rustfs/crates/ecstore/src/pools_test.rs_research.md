# sources/object-store/rustfs/crates/ecstore/src/pools_test.rs

Purpose: This file provides focused unit tests for pool usable-capacity accounting, especially deduplication of duplicate disk entries. It protects against inflated total/free capacity when `StorageInfo.disks` contains repeated `rustfs_madmin::Disk` records, and verifies erasure-coding data-disk filtering.

Important APIs/types/functions: The tests import `get_total_usable_capacity`, `get_total_usable_capacity_free`, `fallback_total_capacity_dedup`, and `fallback_free_capacity_dedup` from `crate::pools`. Test fixtures use `rustfs_madmin::Disk`, `rustfs_madmin::StorageInfo`, and `rustfs_madmin::BackendInfo`, setting disk identity fields (`endpoint`, `drive_path`, `pool_index`, `set_index`, `disk_index`), capacity fields (`total_space`, `available_space`, `used_space`), `state`, and backend erasure coding fields such as `standard_sc_data` and `standard_sc_parity`.

Control flow: `test_single_disk_no_duplication` builds one online 2 TB disk with 500 GB free and backend data count `1`, then asserts total/free usable capacity exactly match the disk. `test_duplicate_disk_entries_deduped` pushes the same disk record 232 times and asserts both total and free capacity are counted once. `test_four_disk_erasure_coding` creates four 1 TB disks in one set with two data disks and two parity disks, then asserts usable total capacity includes only disk indexes below the configured data-disk count. `test_fallback_dedup` creates 100 duplicate disk records without erasure-index fields and verifies fallback total/free deduplication counts one physical disk.

State and persistence behavior: The file has no persistent state and no filesystem or object-store side effects. All state is in-memory fixture data passed directly to capacity helper functions. The important modeled state is the disk identity tuple and backend erasure coding layout; assertions check the derived reported capacity.

Dependencies and integration points: These tests exercise the public capacity helpers in `pools.rs`, which are used by `ECStore::get_decommission_pool_space_info` and therefore affect `ECStore::status` and decommission progress reporting. They also indirectly document the contract with `rustfs_madmin::StorageInfo`: `standard_sc_data` determines usable disk indexes when available, while fallback logic deduplicates by endpoint and drive path when backend layout cannot drive the calculation.

Risks: The tests cover duplicate entries, a single erasure-coded set, and fallback deduplication, but they do not cover offline disk states, negative `pool_index`, multiple pools, multiple sets, inconsistent `standard_sc_data`, zero data-disk counts, or fallback behavior with distinct disks sharing endpoint/path but different indexes. The duplicate-entry scenario assumes duplicate records have identical endpoint, drive path, pool, set, and disk indexes; partial identity duplication is left to the implementation. Free-capacity erasure coding is not explicitly checked in the four-disk parity test.

Test signals: Strong signals are exact capacities: one disk reports `2_000_000_000_000` total and `500_000_000_000` free, 232 duplicate records still report the same single-disk values, four disks with `standard_sc_data = vec![2]` report `2_000_000_000_000` total usable capacity, and 100 fallback duplicate records report one disk's total/free capacity.
