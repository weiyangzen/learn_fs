## Purpose

The module is RustFS's generated RPC boundary for node-to-node or control-plane operations against an object-store node. It exposes a broad service surface that combines bucket metadata operations, low-level disk and volume operations, object metadata/version manipulation, distributed lock operations, node diagnostics, profiling, bucket statistics, IAM/policy reload/delete hooks, site replication reloads, service signaling, background healing, metacache operations, rebalancing, transition-tier config reloads, and live events.

The generated code translates protobuf schema into:

- `prost::Message` structs used as serialized request and response payloads.
- `node_service_client::NodeServiceClient<T>`, a strongly typed async Tonic client.
- `node_service_server::NodeService`, an async trait implementers must provide to serve the RPCs.
- `node_service_server::NodeServiceServer<T>`, a Tower/Tonic `Service` wrapper that dispatches HTTP/2 gRPC paths to trait methods.

## Message Surface

Common envelope patterns:

- Most mutating or lookup responses use `success: bool` plus an optional `Error { code, error_info }`.

## Client API

The generated client module begins at line 1134. `NodeServiceClient<T>` wraps `tonic::client::Grpc<T>`. For the normal transport case, `NodeServiceClient<tonic::transport::Channel>::connect` constructs an endpoint and connects asynchronously. The generic client implementation supports:

- `new(inner)` and `with_origin(inner, origin)` constructors.
- `with_interceptor(inner, interceptor)` for request interception.
- `send_compressed` and `accept_compressed` for compression negotiation.
- `max_decoding_message_size` and `max_encoding_message_size` for per-client message size limits.

Each RPC method follows the same generated control flow:

1. Await `self.inner.ready()` and convert readiness failures into `tonic::Status::unknown("Service was not ready: ...")`.
2. Create a `tonic_prost::ProstCodec`.
3. Build a static `http::uri::PathAndQuery` such as `/node_service.NodeService/ReadAll`.
4. Convert the input into a Tonic request.
5. Insert `GrpcMethod::new("node_service.NodeService", "<RpcName>")` into request extensions.
6. Call `self.inner.unary`, `self.inner.streaming`, or `self.inner.server_streaming` depending on the RPC shape.

Most client calls are unary. The chunk also includes streaming calls:

- `write_stream` accepts a client stream of `WriteRequest` and returns a stream of `WriteResponse`.
- `read_at` accepts a client stream of `ReadAtRequest` and returns a stream of `ReadAtResponse`.
- `walk_dir` sends one `WalkDirRequest` and receives a server stream of `WalkDirResponse`.

The full client method set is present in this chunk, including the later administrative calls through `get_live_events`.

## Server API and Dispatch

`NodeServiceServer<T>` stores:

The arm then constructs `tonic::server::Grpc::new(ProstCodec::default())`, applies compression and message size configuration, and invokes `grpc.unary`, `grpc.streaming`, or `grpc.server_streaming`.

## Control Flow

There is no handwritten algorithmic branching in the protobuf message definitions. Runtime control flow exists only in generated client and server glue:

- Client call flow is readiness check -> codec/path setup -> request extension metadata -> Tonic invocation.
- Server call flow is path match -> generated adapter construction -> trait method forwarding -> codec/compression/size application -> Tonic response.
- Streaming shape is encoded at the Tonic service trait level rather than inside custom loops in this file.
- Error propagation at this layer is transport-oriented: client readiness failures become `tonic::Status`, and server implementations return `tonic::Status` directly. Domain-level errors are represented inside response messages with `success`, `Error`, or `error_info`.

This means the generated layer does not decide whether a disk operation should succeed, how to heal a bucket, how to enforce locks, or how to persist metadata. It only preserves the wire contract and dispatch shape required by the `.proto` schema.

## Risks and Edge Cases

- Generated file drift: manual patches to this file are fragile because prost/tonic regeneration will overwrite them. Contract changes should start in `node.proto`.
- Dual error representation: older APIs use optional structured `Error`, while newer APIs use optional `error_info`. Callers must handle both patterns consistently.
- Opaque payloads: many fields are strings or raw bytes with domain-specific encodings. Schema compatibility is weaker than for fully typed protobuf messages, and bad payloads will fail later in implementation code.
- Message size defaults: both client and server document a default 4 MB decode limit and `usize::MAX` encode limit unless callers/server builders override them. Large object parts, profile data, metadata batches, metrics, and bucket stats may require explicit size configuration.
- Path casing is contract-sensitive: `ReadXL`, `GetSELinuxInfo`, and `GetSRMetrics` are easy to mistype when debugging raw gRPC paths.
- Streaming backpressure and cancellation behavior is delegated to Tonic and the service implementation. This generated file only wires the stream types.
- The chunk boundary stops mid-route arm. Any review of the complete server router must include the continuation after line 4771 to cover metacache/rebalance/tier/live-event route arms, unknown path handling, clone, and named-service declarations.
- Domain success can be `false` while the gRPC status is `OK`. Consumers must not treat transport success as operation success.
- Empty marker request structs such as `GetCpusRequest {}` and `DownloadProfileDataRequest {}` carry no authorization or selection fields at the message level; policy enforcement must happen in interceptors or implementation code.

## Control Flow

For each recognized path, the flow is mechanically identical:

1. Match the gRPC path string, for example `"/node_service.NodeService/GetLiveEvents"`.
2. Declare a private adapter struct for the specific method.
3. Implement `UnaryService<SpecificRequest>` for that adapter, setting `type Response` to the matching response type and `type Future` to a boxed tonic response future.
4. In the adapter `call`, clone the shared `Arc<T>` and await the corresponding `NodeService` trait method on the implementor.
5. Copy compression and message-size settings from `self`.
6. Clone `self.inner` for the async block.
7. Build a `tonic::server::Grpc` with `ProstCodec`, apply the copied settings, and call `grpc.unary(method, req).await`.
8. Return `Ok(res)` in a boxed future because the outer service error type is `Infallible`.

The fallback `_` arm constructs an empty `http::Response<tonic::body::Body>`, inserts `grpc-status: Unimplemented` and the standard gRPC content type, and returns it. This means unknown path handling is transport-level gRPC unimplemented rather than application-specific `NodeService` logic.

After dispatch, `Clone` duplicates the `Arc<T>` and copies the compression/message-size fields. This lets tonic clone server services cheaply while preserving runtime configuration. `NamedService` then binds the server type to the constant service name.
