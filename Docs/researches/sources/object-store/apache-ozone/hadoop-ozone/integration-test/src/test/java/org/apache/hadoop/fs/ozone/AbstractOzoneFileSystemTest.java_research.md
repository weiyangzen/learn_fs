# sources/object-store/apache-ozone/hadoop-ozone/integration-test/src/test/java/org/apache/hadoop/fs/ozone/AbstractOzoneFileSystemTest.java

Purpose: This abstract JUnit suite exercises `OzoneFileSystem` (`o3fs`) behavior that is not fully covered by generic contract tests. It mounts a single bucket as the filesystem root and validates file, directory, listing, rename, delete, trash, replication, metrics, block-location, snapshot, link-bucket, and OM metadata behavior across configurable bucket layouts.

Important APIs and types: The suite extends `OzoneFileSystemTestBase` and uses `MiniOzoneCluster`, `OzoneClient`, `ObjectStore`, `OzoneBucket`, `OzoneVolume`, `OzoneManagerProtocol`, `OzoneFileSystem`, `OzoneFSStorageStatistics`, `Trash`, `OMMetrics`, `OMMetadataManager`, `OmKeyArgs`, `OpenKeySession`, `OzonePrefixPathImpl`, `OzoneFileStatus`, `OzoneKeyDetails`, `BucketLayout`, `ECReplicationConfig`, `RatisReplicationConfig`, `StandaloneReplicationConfig`, `LocatedFileStatus`, and `BlockLocation`. It delegates common checks to base-class helpers such as `createDoesNotAddParentDirKeys`, `fileDelete`, `verifyListStatus`, `listStatusIterator*`, `renameFile`, `renameFileToDir`, `renameToParentDir`, `setTimes`, and `fileSystemDeclaresCapability`.

Control flow: `init` configures a five-datanode `MiniOzoneCluster`, enables ACLs, trash, hsync, HBase enhancements, batch iteration size, and bucket layout, creates one volume/bucket, sets `fs.defaultFS` to `o3fs://bucket.volume/`, opens the filesystem, captures storage statistics, and creates a non-default user filesystem. `cleanup` deletes all root children after each test. Individual tests create files and directories through public `FileSystem` APIs or directly through OM/client APIs, then check `FileStatus`, metadata tables, metrics, and object-store state.

State and persistence behavior: Persistent state lives in the test Ozone cluster: volumes, buckets, keys, directory marker keys, open keys, snapshots, trash paths, and bucket replication defaults. Runtime state includes filesystem statistics snapshots, OM metrics, user identity via `UserGroupInformation`, and a cached adapter view of bucket defaults. Tests intentionally verify fake directory behavior for non-FSO layouts, explicit directory key behavior, refreshed bucket replication after adapter clock advancement, trash checkpoint purging, snapshot read isolation, and block allocations for multi-block files.

Dependencies and integration points: The suite integrates the Hadoop `FileSystem` API with Ozone Manager, object-store client APIs, OM metadata tables, native ACL behavior, trash policies, key manager prefix listing, link buckets, and datanode-backed block locations. It also checks compatibility boundaries such as rejecting `OBJECT_STORE` buckets for filesystem semantics and handling invalid checksum combine mode by returning no checksum.

Risks: Many tests are layout-dependent and use `assumeFalse(FILE_SYSTEM_OPTIMIZED...)` where legacy fake-directory semantics differ from FSO object-ID semantics. Timing-sensitive tests wait for list status, trash emptier cleanup, and refreshed bucket replication. User switching through `UserGroupInformation.setLoginUser` must restore the original user. Root cleanup must avoid trash artifacts through filters. Tests involving link-bucket loops, snapshots, and multi-block files depend on cluster services and OM metrics being stable.

Test signals: Key signals include expected `FileAlreadyExistsException` and `FileNotFoundException` paths, exact root and subdirectory listing sizes, owner/group attribution for real and proxy users, EC flags on intermediate and leaf statuses, large-directory pagination correctness, delete and rename return values for edge cases, stable modification time semantics, trash root discovery and purge, OM metric deltas, storage-statistic deltas, block-location host/name/offset/length values, `pathToKey` conversion, snapshot listing counts, and explicit failure on incompatible bucket layout.
