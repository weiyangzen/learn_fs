# sources/object-store/apache-ozone/hadoop-ozone/integration-test/src/test/java/org/apache/hadoop/fs/ozone/AbstractOzoneFileSystemTestWithFSO.java

Purpose: This subclass specializes the `o3fs` test suite for `FILE_SYSTEM_OPTIMIZED` buckets. It focuses on FSO-specific semantics: object-ID directory tables, non-recursive listing, recursive file iteration, rename validation, parent and bucket modification time updates, open-key commit layout, lease recovery, logging for missing deletes, and a regression where deleted children in the double-buffer cache should not keep a parent directory from being deleted.

Important APIs and types: The class extends `AbstractOzoneFileSystemTest` with `super(true, BucketLayout.FILE_SYSTEM_OPTIMIZED)`. It uses `OMMetadataManager`, `OmBucketInfo`, `OmDirectoryInfo`, `OmKeyInfo`, `OzoneManagerDoubleBuffer`, `LeaseRecoverable`, `LocatedFileStatus`, `RemoteIterator`, `LogCapturer`, and inherited `OzoneFileSystem` accessors. Helpers `verifyDirKey`, `verifyOMFileInfoFormat`, and `renameAndAssert` inspect FSO database key formats and metadata timestamps directly.

Control flow: Tests create nested files and directories with the mounted `o3fs` URI and assert that `listStatus` returns only immediate children while `listFiles(..., true)` returns all files recursively. Rename overrides assert failures for moving a directory into its own child or into a missing/file parent. Modification-time tests capture source parent, destination parent, bucket, and file mtimes before and after rename, expecting parent/bucket changes only when affected and preserving renamed object mtimes. `testCreateFile` opens a file, verifies parent directory-table entries, closes the stream to commit the key, then waits until the open-key table is empty. `testDeleteParentAfterChildDeleted` pauses the OM double buffer, deletes child directory and file, and verifies the parent can still be deleted.

State and persistence behavior: FSO persistence is explicitly object-ID based. Directory rows are expected under `/volumeId/bucketId/parentObjectId/name`, file key rows are expected under `/volumeId/bucketId/parentObjectId/fileName`, and `OmKeyInfo.path` stores `parentID/fileName`. The suite verifies OM `numKeys` metrics for created directories, object IDs for sibling dirs, open-key cleanup after commit, TableCache/double-buffer behavior, and log output when deleting a missing path.

Dependencies and integration points: These tests connect public `FileSystem` operations to FSO-specific OM tables and the Ratis double-buffer pipeline. Lease tests integrate `LeaseRecoverable.isFileClosed` and `recoverLease` with hsync-visible open files. Listing tests exercise Ozone's FSO path resolution rather than legacy prefix-only key scanning.

Risks: The class is tightly coupled to internal OM DB key formats, object ID allocation, and double-buffer behavior. `@TestMethodOrder` plus `@Order(1)` on file creation hints at sensitivity around shared class-level cluster state. Pausing the double buffer must always be undone. Log-message assertions can be brittle if wording changes. Some comments still refer to "prefix layout", but the constructor unambiguously selects FSO.

Test signals: Strong signals include exact qualified paths in `listStatus` and `listFiles`, expected false return values for invalid renames, increasing parent/bucket mtimes where required, unchanged file mtime after rename, valid directory-table and key-table DB rows, OM `numKeys` counts, empty open-key table after commit, `isFileClosed` state transitions around hsync and lease recovery, warning logs for missing delete, and successful parent deletion while deleted children are still buffered.
