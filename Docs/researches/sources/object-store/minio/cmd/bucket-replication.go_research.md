# sources/object-store/minio/cmd/bucket-replication.go

## Purpose
This file is MinIO server-side bucket replication's central runtime implementation. It decides whether object writes, deletes, metadata updates, heal scans, existing-object resyncs, and active-active proxy reads should be replicated; performs the replication to remote bucket targets; tracks per-target status; and persists retry/resync state. It sits between bucket metadata (`globalBucketMetadataSys`), target clients (`globalBucketTargetSys`), the object layer, replication config/rule evaluation from `internal/bucket/replication`, MinIO admin structures, and replication metrics.

## Important APIs, types, and functions
Key entry points include `getReplicationConfig`, `validateReplicationDestination`, `mustReplicate`, `checkReplicateDelete`, `scheduleReplication`, `scheduleReplicationDelete`, `QueueReplicationHeal`, `getReplicationDiff`, proxy helpers for active-active setups, and `initBackgroundReplication`. `replicateObject` and `replicateDelete` are the high-level worker operations; `ReplicateObjectInfo.replicateObject`, `ReplicateObjectInfo.replicateAll`, `replicateDeleteToTarget`, and `replicateObjectWithMultipart` do target-specific data movement. `ReplicationPool` owns normal workers, large-object workers, MRF workers, resync state, and retry persistence channels. `replicationConfig`, `ResyncDecision`, and `resyncTarget` bridge bucket rule evaluation with reset/existing-object replication decisions.

## Control flow
Normal PUT/metadata paths call `mustReplicate`, which rejects uninitialized object layers, versioning-excluded prefixes, incoming replication requests, and already-replica objects except metadata replication. It loads bucket replication config, builds `replication.ObjectOpts`, filters target ARNs, asks the replication config whether each target should receive the object, and records synchronous mode from the `TargetClient`. Delete paths use `checkReplicateDelete`, then `scheduleReplicationDelete` queues a `DeletedObjectReplicationInfo`.

`scheduleReplication` converts `ObjectInfo` into `ReplicateObjectInfo`, then either calls `replicateObject` inline for synchronous targets or queues it through `ReplicationPool`. `replicateObject` namespace-locks the object, fans out target work concurrently, merges target results, updates source object metadata with per-target status and timestamps, updates metrics, emits events, and saves failures into MRF. The target fast path sends data; the heal/resync path first stats the target and chooses none, metadata-only, or full replication. Deletes follow the same fan-out/update pattern and use remote `RemoveObject` with internal replication options.

The resync path uses reset IDs and reset-before timestamps to decide whether existing objects need re-replication. `resyncBucket` walks object versions, filters with `getHealReplicateObjectInfo`, feeds hashed workers, replicates objects or deletes, probes target state, emits trace events, and increments per-target resync stats. Active-active proxy helpers read HEAD/GET/tagging from replication targets while avoiding loops with proxy headers and `disableProxy`.

## State and persistence behavior
The file mutates object metadata with reserved replication status, timestamp, reset, delete replication, object-lock, and tagging timestamp fields. Remote writes preserve source version IDs, ETags, modtimes, replication status, and replication request markers. `ReplicationPool` stores bounded in-memory queues for normal, large-object, MRF, and MRF-save work. MRF state is persisted as msgp with a 4-byte format/version header under `.minio.sys/buckets/.replication/mrf/<node>.bin`. Resync metadata is persisted as msgp with a header under the bucket metadata replication directory as `resync.bin` and is reloaded/resumed by the leader.

## Dependencies and integration points
Major dependencies include `globalBucketTargetSys`, `globalBucketVersioningSys`, `globalBucketObjectLockSys`, `globalBucketMonitor`, `globalReplicationStats`, `globalSiteResyncMetrics`, `globalTrace`, `globalLeaderLock`, object-layer namespace locks and object APIs, minio-go client/core APIs, `madmin`, replication config/rules, crypto/checksum helpers, event notification, and msgp-generated persisted types.

## Risks and test signals
Correctness depends on preserving metadata, encryption mode, checksums, part sizes, version IDs, and object-lock timestamps. Queue overflow falls back to MRF, but retry limits, full channels, or local-drive write failures can drop/delay retries. Multipart replication must abort failed uploads and handle SSE-C sizes correctly. Active-active proxying must avoid loops and stale reads. `bucket-replication_test.go` directly covers resync decisions; most network, MRF, delete, proxy, checksum, and multipart behavior relies on broader integration coverage.
