# File Research: sources/virtualization/spdk/module/bdev/crypto/vbdev_crypto.c

This file implements SPDK's `crypto` virtual bdev. It claims a base bdev and exposes a same-sized virtual bdev whose reads are decrypted and writes are encrypted through the SPDK accel framework. It supports deferred creation: requested `(base_bdev, crypto_bdev, key)` associations are stored until the base bdev appears during examine.

The persistent configuration list is `g_bdev_names`, each entry holding `vbdev_crypto_opts` with virtual name, base bdev name, crypto key pointer, and key ownership. Active devices live in `g_vbdev_crypto`; each `vbdev_crypto` stores the base bdev/descriptor, embedded virtual bdev, opts pointer, and the thread that opened the base descriptor. Per-channel state stores the base bdev channel, an accel channel, and the crypto key. Per-IO state stores the accel sequence, optional write auxiliary buffer and memory-domain metadata, resubmit wait entry, and state needed to retry after base-bdev `-ENOMEM`.

Write IO is encrypted out-of-place. `vbdev_crypto_submit_request()` obtains an accel buffer sized to the write, `crypto_encrypt()` aligns it to the crypto bdev buffer requirement, appends an encrypt operation to the IO's accel sequence, and then `crypto_write()` submits the encrypted auxiliary iov to the base bdev using `spdk_bdev_writev_blocks_ext()`. The auxiliary buffer is returned in `_complete_internal_io()`.

Read IO decrypts in-place after the base bdev transfer by using the accel sequence option on the base read. `crypto_read_get_buf_cb()` appends decrypt from the destination iovs to the same destination iovs, then `crypto_read()` submits `spdk_bdev_readv_blocks_ext()` with the sequence and caller memory domain. The base IO completion sets the original IO status from the base IO, frees the base IO, and returns any auxiliary buffer.

Pass-through operations include UNMAP, FLUSH, and RESET. WRITE_ZEROES is deliberately not supported so the bdev layer supplies real zero writes that can be encrypted as normal writes. IO type support is otherwise delegated to the base bdev. If base submission returns `-ENOMEM`, reads/writes can queue an IO wait and resubmit in the correct post-accel state; some accel-buffer or append failures complete as NOMEM or fail/abort the sequence.

Registration copies base geometry and capabilities, sets `max_rw_size` to the smaller of base max and SPDK iobuf large buffer capacity, computes required alignment from base alignment and accel encrypt/decrypt buffer alignment for the block size, mirrors block length/count/write cache/optimal boundary/NUMA, generates a SHA1 UUID from a crypto namespace UUID and the base UUID, claims the base bdev, registers an IO device, and registers the virtual bdev.

The module handles base bdev remove by unregistering dependent crypto vbdevs and base resize by notifying block count change. It reports memory domains as the generic accel domain plus domains that support encrypt, reports memory-domain types from encrypt-capable accel domains, and marks READ/WRITE as accel-sequence-supported. Teardown releases the base claim, closes the base descriptor on the opening thread if needed, unregisters the IO device, and frees virtual bdev storage. Module finish removes all saved associations and destroys owned keys.
