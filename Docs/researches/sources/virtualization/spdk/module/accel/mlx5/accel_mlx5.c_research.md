# File Research: sources/virtualization/spdk/module/accel/mlx5/accel_mlx5.c

This file implements SPDK's `mlx5` acceleration module and optional accel platform driver. It offloads copy, AES-XTS encrypt/decrypt, CRC32C/copy-CRC32C, and RDMA memory-key registration onto Mellanox/NVIDIA mlx5 hardware through SPDK internal mlx5, RDMA utility, memory-domain, accel-module, and verbs APIs.

The core state model is split between global module state, device context, per-channel device instances, QPs, and tasks. `g_accel_mlx5` holds module attributes, stats, allowed device names, initialization/enabled flags, and feature support. `accel_mlx5_dev_ctx` owns one verbs context, PD, memory domain, PSV pool, PSV array, and mkey pool capability flags. Each SPDK IO channel allocates `accel_mlx5_io_channel`, which owns one `accel_mlx5_dev` per selected device, including CQ, QP, memory map, mkey pool refs, pending no-resource task queue, and per-device stats. `accel_mlx5_task` embeds `spdk_accel_task` and tracks source/destination iov traversal, request and completion counts, mkey objects, PSV state for CRC, crypto block splitting, task flags, and the internal mlx5 opcode.

Address translation is centralized in `accel_mlx5_translate_addr()`. If the task supplies a source or destination memory domain, it calls `spdk_memory_domain_translate_data()` into the mlx5 device domain and requires a single translated iov. Otherwise it consults the channel RDMA memory map for local DMA lkeys. `accel_mlx5_fill_block_sge()` uses that translation while walking an internal iov cursor, filling at most 16 SGEs per work request. The helper code includes explicit advance/unwind logic so crypto and CRC paths can back up to block-aligned boundaries when fragmented buffers exceed hardware SGE limits.

Copy offload maps to RDMA WRITE. `accel_mlx5_copy_task_init()` counts how many RDMA writes are required from source and destination iov layouts, initializes iov cursors, and checks available QP/CQ slots. `accel_mlx5_copy_task_process_one()` builds source SGEs and a single destination SGE, then posts `spdk_mlx5_qp_rdma_write()`. `accel_mlx5_copy_task_process()` batches unsignaled writes and makes the final write signaled with the task pointer as `wr_id`.

Crypto offload uses UMR-configured crypto mkeys followed by RDMA READ. `accel_mlx5_crypto_task_init()` validates block-size alignment and that the crypto key belongs to this module, determines in-place versus out-of-place mode, computes request splitting based on hardware multi-block support and `crypto_split_blocks`, allocates crypto mkeys, and checks QP depth. `accel_mlx5_configure_crypto_umr()` fills source and optional destination SGEs, handles fragmentation by reducing processed block count to a valid block boundary, sets AES-XTS IV/key/tweak/order attributes, and posts `spdk_mlx5_umr_configure_crypto()`. `accel_mlx5_crypto_task_process()` then posts RDMA READs from each crypto mkey to the destination or source buffer and signals the last request.

CRC32C offload uses mlx5 signature UMRs and PSV objects. Single-request CRC configures one signature UMR, appends a DMAable CRC output word to the RDMA SGE list, optionally resets an error-marked PSV with SET_PSV, and posts a signaled RDMA READ. Multi-request CRC splits according to both source and destination SGE alignment, carries a signature across UMRs, handles the final CRC-only request case by reusing the last mkey, and copies the final inverted CRC from the PSV wrapper into `base.crc_dst`. PSV wrappers live in a mempool and include a DMA-translated `crc_lkey`.

The file also implements two special mkey-producing task types used by the mlx5 accel driver path. `ACCEL_MLX5_OPC_MKEY` registers a plain UMR mkey over an external RDMA memory domain. `ACCEL_MLX5_OPC_CRYPTO_MKEY` registers a crypto UMR mkey. Both reject multi-task sequences and the generic accel memory domain, require low fragmentation, and can initiate `spdk_memory_domain_transfer_data()` after hardware completion to hand a generated mkey-backed domain transfer to the destination memory domain.

Task submission and completion are resource-aware. `_accel_mlx5_submit_tasks()` increments opcode stats, initializes the task, queues it on `dev->nomem` if mkeys or QP slots are unavailable, registers a post-poller handler to ring QP doorbells, and posts the initial batch. CQ polling via `accel_mlx5_poll_cq()` consumes completions, updates `num_completed_reqs`, frees QP/CQ accounting slots, completes tasks when all requests finish, or continues partially complete tasks. `accel_mlx5_resubmit_nomem_tasks()` retries queued tasks after polling. Error completions mark the QP recovering, fail tasks only after submitted requests are accounted for, and recreate the QP immediately or via a retry poller.

Initialization discovers RDMA devices with `spdk_rdma_cm_get_devices()`, filters to Mellanox vendor devices and optional allowed names, queries mlx5 capabilities, and either selects the single best device automatically or uses all allowed devices. Feature support is conservative: with explicit device selection, crypto and CRC32C are enabled only if every selected device supports them; with auto-selection, the best device's capabilities determine support. Device context setup allocates PD/memory domain, base mkey pool, optional crypto/signature pools, and optional PSV pool. Per-channel setup creates CQs/QPs and per-device memory maps.

Configuration is exposed through `accel_mlx5_enable()`, default attributes, config JSON emission, crypto-key init/deinit, cipher support, memory-domain reporting, and stats dumping. Stats can be dumped at total, channel, or device level and include UMR counts, RDMA reads/writes, polling/completion counts, no-memory counters, and task opcode counts. The module registers as `spdk_accel_module_if` named `mlx5`; if `enable_driver` is set, it also registers an accel driver named `mlx5` that can merge copy/encrypt/decrypt sequences involving RDMA memory domains into mkey or crypto-mkey operations.

Important constraints and failure paths: `num_requests / core_count` must be at least 16 and `qp_size` at least 8; block sizes for crypto are limited to mlx5 selectors 512, 520, 4096, and 4160; many paths return `-ENOMEM` to queue and retry instead of failing; unsupported sequence or domain shapes return `-ENOTSUP`/`-EINVAL`; teardown unregisters the IO device before freeing global resources and destroys mkey pools, PSV pools, PD refs, memory-domain refs, and allowed-device copies.
