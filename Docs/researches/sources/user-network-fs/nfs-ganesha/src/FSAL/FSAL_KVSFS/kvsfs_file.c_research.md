## sources/user-network-fs/nfs-ganesha/src/FSAL/FSAL_KVSFS/kvsfs_file.c

Purpose: This file implements KVSFS regular-file open, reopen, close, read, write, and commit operations for the FSAL object operation vector. It adapts Ganesha's state/share/FD machinery to KVSNS file handles and direct KVSNS read/write calls.

Important functions: `kvsfs_open_by_handle` selects either a state fd or the object's global fd, starts exclusive fd work, optionally checks share conflicts under `obj_lock`, skips no-op reopens, calls `kvsfs_reopen_func`, manages fd LRU insertion/bumping, optionally refreshes attributes after create/truncate, updates share counters, and completes fd work. `kvsfs_open_by_name` performs lookup because KVSFS lacks open-by-name, rejects non-regular objects, then opens by handle. `kvsfs_reopen_func` converts FSAL open flags to POSIX flags, opens the KVSNS inode with caller credentials, closes any previous KVSNS fd, stores the new fd, and records NFS open flags. `kvsfs_close_func` closes and clears a KVSNS fd. `kvsfs_open2` handles no-create, guarded/exclusive/unchecked create, verifier setup, mode/umask calculation, KVSNS create via `kvsfs_create2`, object handle allocation, post-create setattr/getattr, final open, and cleanup/unlink on failures. `kvsfs_status2`, `kvsfs_reopen2`, `kvsfs_commit2`, and `kvsfs_close2` expose status/reopen/no-op commit/state close to FSAL. `kvsfs_read2` and `kvsfs_write2` acquire usable fds through `fsal_start_io`, iterate over iovecs with `kvsns_read`/`kvsns_write`, complete I/O, update stateless share counters, and invoke async callbacks.

Control flow and state: The file heavily relies on FSAL fd state. Stateful opens use `struct kvsfs_state_fd`; stateless I/O may use a temporary fd. The only path taking both fd work mutex and object lock is documented in `kvsfs_open_by_handle` to avoid ABBA deadlock. Share counters are updated only after successful open/reopen and during state close or stateless I/O cleanup. Create flow distinguishes whether this process definitely created the file through `O_EXCL`; only then are extra attributes set and cleanup unlink attempted on later failure.

Persistence behavior: Persistent namespace and file content changes occur through `kvsfs_create2`, `kvsns_open`, `kvsns_close`, `kvsns_getattr`, `kvsns_setattr` through object ops, `kvsns_unlink` cleanup, `kvsns_read`, and `kvsns_write`. `kvsfs_commit2` does not force durability and returns success. File truncation is represented through FSAL open flags passed to KVSNS open. The file does not cache data itself, only KVSNS open handles and FSAL open flags.

Dependencies and integration points: It depends on `op_ctx` credentials and export, FSAL common fd/share helpers (`fsal_start_fd_work_no_reclaim`, `fsal_start_io`, fd LRU, share conflict/counter helpers), POSIX conversion helpers, KVSFS handle allocation and create functions, KVSNS file APIs, object ops for lookup/setattr/getattrs/release, and async completion callbacks.

Risks: `old_openflags` is only assigned inside the `state != NULL` branch but is used in no-op and LRU logic for stateless/global opens, which is a potential uninitialized-read bug unless hidden by compiler/control assumptions. `kvsfs_close_func` casts `struct fsal_fd *` directly to `struct kvsfs_fd *`; because `fsal_fd` is the first member of `struct kvsfs_fd`, this works only while layout stays that way. Read/write callbacks may report success even if `fsal_complete_io` fails because `status2` is logged but not propagated. EOF is true only when total bytes read is zero. Commit is a no-op. In `kvsfs_open2`, the `fileerr` label releases `hdl` and unlinks if `created` even after a successful open path, because control falls through to `fileerr` rather than returning immediately after `kvsfs_open_by_handle`; this should be reviewed as it appears capable of releasing/unlinking a successfully opened created file. Test signals should target open/create modes, share conflicts, stateless vs stateful opens, truncate attribute refresh, successful exclusive create lifetime, cleanup-on-error behavior, read/write iovec partial failures, `fsal_complete_io` failure injection, and commit durability expectations.
