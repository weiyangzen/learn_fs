## sources/user-network-fs/nfs-ganesha/src/FSAL/FSAL_GPFS/include/gpfs_nfs.h

Purpose: This header defines the GPFS/Ganesha NFS interface contract carried through `gpfs_ganesha(int op, void *oarg)`. It is the GPFS-specific command and argument ABI for open-by-handle, pNFS layout/device operations, data-server reads/writes, xstat, xattrs, locking, callbacks, tracing, quota, and filesystem-location requests.

Important APIs and types: The central API is `gpfs_ganesha`, parameterized by `OPENHANDLE_*` operation codes. The command range starts at `OPENHANDLE_GET_VERSION` and covers name-to-handle, open-by-handle, file layout, device info/list, layout get/return/commit, inode update, xstat get/set/access, lock get/set, thread update, DS read/write, verifier, fsync, share reservation, close, link/rename/readlink/unlink/create/stat by handle/name, fd read/write, allocate/reopen/fadvise/seek, statfs, xattrs, mknode, tracing, quota, and FS locations. Key payloads include `struct gpfs_file_handle`, `struct name_handle_arg`, `struct open_arg`, `struct glock`, pNFS structs such as `nfsd4_pnfs_deviceid`, `nfsd4_layout_seg`, `pnfs_filelayout_layout`, `deviceinfo_arg`, `layoutget_arg`, `layoutcommit_arg`, `dsread_arg`, `dswrite_arg`, plus xstat/xattr/quota/fs-location argument structs.

Control flow and state: Callers populate one operation-specific struct, pass it to `gpfs_ganesha`, and interpret in/out fields after return. Several payloads carry file descriptors rooted at a mount directory, GPFS file handles, client IP strings, lock owners, state reclaim flags, or verifier buffers. pNFS state flows through device IDs, layout segments, layout body XDR streams, commit ranges, return cookies, and callback reasons. Callback state is represented by `callback_arg`, where GPFS reports invalidation/update/lock/delegation/layout/device reasons and flags such as `UP_SIZE`, `UP_TIMES`, and `XATTR_*` tell Ganesha which cached state changed.

Persistence behavior: The file itself persists nothing, but its payloads operate on persistent GPFS namespace objects by file handle or fd. It exposes metadata updates through xstat and create/stat structures, persistent link/rename/unlink/mknode operations, pNFS layout commitments that may update size/mtime, xattr mutation, quota controls, and fs-location discovery. It also carries ephemeral process state such as open fds, lock owner pointers, share reservations, write verifiers, and callbacks that must be interpreted while the relevant Ganesha state exists.

Dependencies and integration points: It depends on NFS and POSIX types supplied by surrounding includes, including `struct flock`, `struct stat`, `struct statfs`, `pnfs_deviceid`, and `fsal_stats` from Ganesha. GPFS FSAL implementation files use these opcodes to call into GPFS kernel/user infrastructure. The operation numbering and statistics constants (`GPFS_STAT_MAX_OPS`, `GPFS_TOTAL_OPS`) must stay synchronized with GPFS-side dispatch.

Risks: This is a fragile binary interface: field ordering, integer widths, handle lengths, and opcode values must match the GPFS implementation. The stats-range comments already note missing opcodes and a special placeholder, so adding operations without updating ranges can break telemetry or bounds checks. Many structs include raw pointers passed across the interface, making lifetime and address-space expectations critical. Client IP propagation and credential payloads are security-sensitive. Test signals should include version negotiation, each opcode family smoke test, pNFS layout get/commit/return validation, lock reclaim/grace behavior, callback invalidation handling, and xstat/xattr buffer length edge cases.
