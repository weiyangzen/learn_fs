# sources/user-network-fs/rclone/backend/b2/b2.go

## Purpose
Main rclone backend implementation for Backblaze B2. It registers `b2`, parses config, authorizes accounts, maps rclone paths to buckets/object names, implements `fs.Fs` and `fs.Object`, and provides listing, metadata, direct uploads, copy, deletion/hiding, public links, lifecycle commands, and cleanup commands. Large-file mechanics are delegated to `upload.go`.

## Important APIs, types, and functions
`Options` covers account/key, endpoint, version modes, hard delete, upload/copy cutoffs, chunk size/concurrency, checksum disabling, download URL/auth duration, lifecycle, encoding, and SSE-C settings. `Fs` stores the REST client, B2 authorization info, bucket existence cache, bucket ID/type maps, upload URL cache, pacer, and upload token dispenser. `Object` stores remote path, file ID, modtime, SHA1, size, and MIME type.

`NewFs` validates and normalizes config, decodes SSE-C keys, creates the REST client/pacer, calls `authorizeAccount`, handles bucket-restricted keys, detects root paths that are files, and fills features. `list`, `ListP`, and `ListR` adapt B2 name/version listings into rclone directory entries. `Update` chooses direct upload, unknown-size streaming large upload, or multipart upload. `copy` chooses single B2 copy or multipart copy. `Remove`, `Purge`, `CleanUp`, `lifecycleCommand`, and backend `Command` implement B2-specific mutation and maintenance behavior.

## Control flow
Startup flows from config parsing to account authorization, then optional bucket restriction and file-root checks. Listing splits remotes into bucket and prefix, uses `/b2_list_file_names` or `/b2_list_file_versions`, filters prefix/root, and handles version-at semantics. Uploads ensure bucket existence, then use direct `/b2_upload_file` for small files and large upload paths for larger or streaming data. Deletion hides files by default, hard-deletes when configured, and blocks writes in version-at mode.

## State and persistence
Remote state is stored in B2 buckets, file versions, B2 file info metadata, lifecycle rules, and large-file markers. Local runtime state includes in-memory bucket caches, reusable upload URLs, auth data, pacer state, and upload tokens. Modtime is persisted under `src_last_modified_millis`; large-file SHA1 may be stored under `large_file_sha1`.

## Dependencies and integration points
Uses rclone `fs`, `accounting`, `operations`, `list`, `multipart`, `bucket.Cache`, `encoder`, `pacer`, `pool`, `rest`, and B2 API types. Integrates with B2 Native API endpoints for authorization, bucket operations, listings, upload/download, copy, delete/hide, download authorization, lifecycle, and cleanup. Advertises purger, copier, streamer, clean-upper, recursive/partial lister, public linker, chunk writer, commander, MIME typer, and IDer.

## Risks
Version and point-in-time modes are subtle and write paths must stay blocked. Upload URL reuse must clear bad tokens after retryable errors. `hex_digits_at_end` direct uploads depend on exact content-length adjustment. Custom download URLs may omit native B2 headers, requiring fallback metadata. SSE-C headers must be consistent across upload, copy, and download. Cleanup is destructive and relies on dry-run/interactive guards.

## Test signals
Covered by generic B2 integration in `b2_test.go` and internal tests for URL encoding, metadata, large upload metadata, versions, version-at, cleanup, unfinished uploads, and lifecycle rules.
