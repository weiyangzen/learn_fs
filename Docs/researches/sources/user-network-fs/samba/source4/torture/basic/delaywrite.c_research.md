# sources/user-network-fs/samba/source4/torture/basic/delaywrite.c

Purpose: implements the `delaywrite` Samba torture suite for SMB1 last-write-time behavior. It exercises when servers should update file or directory write timestamps immediately, when an explicit `SET_FILE_BASIC_INFO` write time becomes sticky, how path info and handle info should agree, and how close, flush, truncation, allocation changes, two-handle access, and two-connection access affect timestamps.

Important APIs and types: the exported suite factory is `torture_delay_write(TALLOC_CTX *ctx)`. It registers `test_finfo_after_write`, `test_delayed_write_update`, `test_delayed_write_update1`, `1a`, `1b`, `1c`, `2`, `3`, `3a`, `3b`, `3c`, `4`, `5`, `5b`, `6`, `7`, `test_directory_update8`, and `test_modern_write_time1`. The tests use `struct torture_context`, `struct smbcli_state`, `union smb_fileinfo`, `union smb_setfileinfo`, `union smb_open`, `union smb_flush`, `NTSTATUS`, `NTTIME`, and talloc contexts. Important SMB client calls include `torture_setup_dir`, `smbcli_open`, `smbcli_write`, `smbcli_smbwrite`, `smbcli_ftruncate`, `smb_raw_fileinfo`, `smb_raw_pathinfo`, `smb_raw_setfileinfo`, `smb_raw_open`, `smb_raw_flush`, `smbcli_close`, `smbcli_unlink`, and `smbcli_deltree`.

Local helper macros define the recurring assertions and state transitions. `COMPARE_WRITE_TIME_CMP` compares write times with optional strict mode and a one-second-rounded fallback for filesystems with coarse timestamp resolution. `GET_INFO_*` macros combine raw queries with failure handling and log comments. `SET_INFO_FILE_EX`, `SET_INFO_FILE`, and `SET_INFO_FILE_NS` issue `RAW_SFILEINFO_BASIC_INFO` updates and model explicit sticky write times, including a nanosecond offset for timestamp-resolution checks.

Control flow: every test creates or reuses `BASEDIR` (`\\delaywrite`), opens one or two SMB handles, captures initial `RAW_FILEINFO_BASIC_INFO` or `RAW_FILEINFO_ALL_INFO`, performs writes or metadata changes, then repeatedly compares returned handle/path timestamps. Sleep calls via `smb_msleep` step around filesystem timestamp granularity and the configurable `writetimeupdatedelay` torture setting. Normal completion closes handles and removes test files and `BASEDIR`; most failure paths jump to cleanup or return through torture assertion failure.

The early tests focus on immediate update semantics. `test_delayed_write_update` verifies a simple one-byte write changes `write_time`. `test_delayed_write_update1` verifies zero-length `SMBwrite` truncation updates immediately, subsequent non-zero `SMBwrite` updates within the expected window, and close does not change the final write time. `1a`, `1b`, and `1c` cover expansion/truncation through zero-length `SMBwrite`, `SET_END_OF_FILE_INFO`, and `SET_ALLOCATION_INFO`. `test_finfo_after_write` catches stale path-info cache behavior after writes across two connections.

The two-handle and explicit timestamp tests model Samba/Windows compatibility behavior. `test_delayed_write_update2` sets a write time with `smb_raw_setfileinfo`, verifies writes through the same handle and flush do not disturb the explicit time, then checks how another handle and later reopen lose or bypass that stickiness. `test_delayed_write_update3`, `3a`, `3b`, `3c`, and `4` stress repeated normal writes and truncate writes, asserting immediate timestamp progression during writes and no extra timestamp update on close. `test_delayed_write_update5`, `5b`, and `6` show that explicit write times suppress later normal/truncate write updates and close-time updates, including across two connections.

The later tests cover precision and modern semantics. `test_delayed_write_update7` requires a non-zero millisecond write time to be preserved through qfileinfo, qpathinfo, close, and reopen. `test_directory_update8` opens a directory handle, creates a file inside it, and requires the directory write time to increase while the directory handle remains open. `test_modern_write_time1` is a two-handle timeline where sticky time is globally visible until a write from the non-sticky handle restores normal current write-time behavior.

State and persistence behavior: all persistent side effects are remote SMB filesystem state under `\\delaywrite`. File contents are incidental; the suite observes file size, access time, write time, change time, attributes, and handle/path consistency. Explicit write-time state is expected to behave like server-side open-handle state rather than a local variable. The code uses talloc only for test memory and open-request memory; outputs are not retained beyond each test.

Dependencies and integration points: this file sits in `source4/torture/basic` and is exposed through `torture/basic/proto.h`. It depends on Samba raw SMB1 client plumbing from `libcli/raw`, higher-level `smbcli_*` helpers, `torture/util.h`, `system/time.h`, and `system/filesys.h`. The suite registration uses one- and two-SMB torture test adapters, so execution depends on the torture framework provisioning connected SMB clients.

Risks: the suite is timing-sensitive and can be flaky on filesystems with low timestamp resolution, slow servers, or unusual write-back policies; the macros mitigate this by rounding timestamps unless `strict mode` is enabled. Several tests use loops bounded by scaled seconds and can be expensive. Because the code intentionally probes Windows-compatible edge cases, changing server timestamp caching, open-handle metadata propagation, or explicit write-time semantics can break many tests at once.

Test signals: failures identify concrete protocol regressions: unchanged write time after write/truncate, write time changed by close, path info diverging from file info, sticky write time ignored, sticky write time not cleared by another handle write, timestamp precision loss after close/reopen, directory write time not updated on child creation, or delayed update happening after an explicit set.
