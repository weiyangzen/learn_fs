# sources/user-network-fs/samba/source4/torture/basic/delete.c

Purpose: implements the `delete` Samba torture suite for SMB delete-on-close semantics. It verifies file and directory deletion behavior across initial `NTCREATEX_OPTIONS_DELETE_ON_CLOSE`, later `smbcli_nt_delete_on_close` calls, delete access rights, share-delete compatibility, readonly attributes, multiple open handles, connection death, rename, non-empty directories, and expected NTSTATUS values.

Important APIs and types: the exported suite factory is `torture_test_delete(TALLOC_CTX *ctx)`. It registers `deltest1` through `deltest25a`, with `deltest21`, `deltest22`, and `deltest24` as simple tests that open their own connections. Key helpers are `check_delete_on_close`, `del_clean_area`, and `CHECK_STATUS`. The file uses `struct torture_context`, `struct smbcli_state`, `union smb_search_data`, `union smb_fileinfo`, `union smb_setfileinfo`, security masks, create dispositions, share flags including `NTCREATEX_SHARE_ACCESS_DELETE`, and create options including `NTCREATEX_OPTIONS_DELETE_ON_CLOSE` and `NTCREATEX_OPTIONS_DIRECTORY`.

The core operations are `smbcli_nt_create_full`, `smbcli_nt_delete_on_close`, `smbcli_close`, `smbcli_open`, `smbcli_unlink`, `smbcli_deltree`, `smbcli_setatr`, `smbcli_getatr`, `smbcli_mkdir`, `smbcli_rename`, `smb_raw_setfileinfo`, `smb_raw_fileinfo`, `smb_raw_exit`, `smbcli_transport_dead`, `torture_single_search`, and `torture_open_connection`. `check_delete_on_close` is the main verifier: it searches the path, optionally queries all/standard info by handle, checks `delete_pending` and `nlink`, then expects `smbcli_qpathinfo` to succeed normally or fail with `NT_STATUS_DELETE_PENDING`.

Control flow: most tests start with `del_clean_area(cli1, cli2)`, which sends raw exit on both sessions and removes `\\delete.dir`, `\\delete.file`, and `\\delete.new` after clearing file attributes. Each `deltest*` then constructs a specific open/delete/close scenario, checks return handles or NTSTATUS values, and confirms final path existence or deletion. The suite uses two connected SMB clients for most scenarios to distinguish same-session and cross-session behavior.

Basic file cases cover direct deletion and access validation. `deltest1`, `2`, `3`, `4`, `7`, `8`, `10`, and `13` cover delete-on-close at open time or set after open, including share-delete requirements, multiple handles, clearing the flag, and global visibility of `delete_pending`. `deltest5` ensures `smbcli_nt_delete_on_close` cannot be applied to a legacy `OpenX` handle. `deltest6`, `9`, and `9a` verify DELETE access is required and missing access fails with `NT_STATUS_INVALID_PARAMETER` without creating or deleting the target. `deltest11` and `12` verify readonly files reject delete-on-close with `NT_STATUS_CANNOT_DELETE`.

Multi-handle propagation is the largest risk area. `deltest16`, `16a`, and `17` through `17f` encode subtle Windows-observed rules around initial delete-on-close, later opens, which close causes pending-delete state to become visible, whether subsequent opens clear or inherit the state, and whether clearing delete-on-close on one handle affects remaining handles. These tests assert when `delete_pending` should be false while the initial delete-on-close handle is still open, when closing that handle should make other handles report pending delete, and when final close should produce `NT_STATUS_OBJECT_NAME_NOT_FOUND`.

Rename, connection, and directory behavior broaden the coverage. `deltest15` and `20b` verify delete-on-close across rename, including handle-based `RAW_SFILEINFO_RENAME_INFORMATION`. `deltest21` simulates a dropped transport and expects delete-on-close cleanup. `deltest24` verifies unsetting an initial delete-on-close request before close does not prevent deletion. `deltest14`, `18`, `19`, `20`, `20c`, `22`, `23`, `25`, and `25a` cover empty directories, non-empty directories, pending-delete directory opens, invalid access, and `NT_STATUS_DIRECTORY_NOT_EMPTY`.

State and persistence behavior: persistent remote state is limited to `\\delete.file`, `\\delete.new`, and `\\delete.dir`. The suite intentionally manipulates server-side open-handle state, delete-pending state, link counts, attributes, and namespace entries. It uses `nlink` expectations of `0` when delete is pending and `1` otherwise in `check_delete_on_close`. Local state is just integer fnums, booleans, and status values. Cleanup is defensive because many scenarios leave paths pending or readonly.

Dependencies and integration points: this file depends on `libcli/libcli.h`, `libcli/raw/raw_proto.h`, `torture/util.h`, `torture/raw/proto.h`, and `torture/basic/proto.h`. It integrates with the Samba torture suite registry through `torture_suite_add_2smb_test` and `torture_suite_add_simple_test`. It also depends on raw search and qfileinfo behavior accurately exposing `delete_pending`, `nlink`, and path-status transitions.

Risks: delete-on-close rules are highly compatibility-sensitive and vary by object type, create disposition, and server version; several comments document Windows version differences. Tests can leave files pending delete if a failure aborts before final close, so `del_clean_area` is important. Some tests check transport error state using `CHECK_STATUS`, which reads the last transport NTSTATUS and can be affected by an unexpected intervening call.

Test signals: expected failures include `NT_STATUS_DELETE_PENDING`, `NT_STATUS_OBJECT_NAME_NOT_FOUND`, `NT_STATUS_INVALID_PARAMETER`, `NT_STATUS_CANNOT_DELETE`, and `NT_STATUS_DIRECTORY_NOT_EMPTY` in specific scenarios. Behavioral regressions show up as successful opens while delete is pending, missing deletion after final close or socket death, deletion despite clearing a permitted flag, invalid create attempts leaving objects behind, or directory delete-on-close ignoring non-empty protection.
