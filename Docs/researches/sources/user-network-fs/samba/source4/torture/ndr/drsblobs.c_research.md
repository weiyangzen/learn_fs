# sources/user-network-fs/samba/source4/torture/ndr/drsblobs.c

Purpose: this file defines the Samba torture NDR suite for DRS-related directory service blobs: forest trust information, trust-domain password/authentication blobs, and supplemental credentials captured from several Samba and Windows releases. It is primarily compatibility regression coverage for complex, historically fragile AD replication/security blob layouts.

Important APIs, types, and functions: the exported entry point is `ndr_drsblobs_suite(TALLOC_CTX *ctx)`. It uses generated `ndr_drsblobs.h`, base64 decoding, and the NDR torture helpers for raw byte arrays and decoded `DATA_BLOB`s. `forest_trust_info_check_out()` validates a two-record `ForestTrustInfo`: version `1`, count `2`, a top-level name `f2.test`, and a domain-info record with SID `S-1-5-21-677661288-1956808876-2402106903`, DNS name `f2.test`, and NetBIOS name `F2`. `forest_trust_info_check_out2()` validates a five-record forest trust fixture, including normal top-level/domain records, disabled TLN records (`LSA_TLN_DISABLED_NEW`), and `FOREST_TRUST_SCANNER_INFO`.

`trust_domain_passwords_check_in()` validates a `trustDomainPasswords` fixture. It asserts outgoing and incoming counts, current/previous offsets, current array metadata, `TRUST_AUTH_TYPE_CLEAR`, clear password sizes, password byte equality against offsets inside the original fixture, zero previous counts, and final outgoing/incoming sizes. Supplemental credential checkers cover empty forms and real package sets: `supplementalCredentials_empty1_check()`, `supplementalCredentials_empty2_check()`, `alpha13_supplementalCredentials_check()`, `release_4_1_0rc3_supplementalCredentials_check()`, `release_4_5_0pre_GPG_supplementalCredentials_check()`, and `win2012R2_supplementalCredentials_check()`.

Control flow: `ndr_drsblobs_suite()` creates a parent suite named `drsblobs` and child suites for empty, alpha13, release 4.1.0rc3, release 4.5.0pre-GPG, and Windows 2012 R2 supplemental credential cases. It registers forest trust fixtures, trust-domain password fixtures, incoming/outgoing trust auth blobs, and supplemental credential fixtures. Most real-world supplemental credentials are stored as base64 strings, decoded with `base64_decode_data_blob_talloc()`, then registered with `torture_suite_add_ndr_pull_validate_test_blob()`. For the Windows 2012 R2 fixture, the suite explicitly forces the final byte to zero before registering it because that byte is typically uninitialized and Samba requires stable pull/push behavior.

State and persistence behavior: there is no external persistence. The only mutation is local normalization of the decoded Windows 2012 R2 supplemental credential blob's final byte. Suite-local `DATA_BLOB`s and decoded structures are allocated under talloc contexts and discarded after test execution. No directory, network, key database, or filesystem state is modified.

Dependencies and integration points: this file sits at the boundary between DRS IDL definitions and authentication/trust consumers that depend on those blobs. It tests SID decoding (`dom_sid_parse_talloc()` comparisons), forest trust record union arms, timestamp and size fields, trust-auth array offsets, supplemental credential prefixes/signatures (`SUPPLEMENTAL_CREDENTIALS_PREFIX`, `SUPPLEMENTAL_CREDENTIALS_SIGNATURE`), and package-name extraction for Kerberos, WDigest, Packages, and SambaGPG. It also exercises pull/push validation, not only loose pull parsing, for many fixtures.

Risks: the fixtures deliberately encode old Samba and Windows layouts, including uninitialized bytes and release-specific package ordering. Normalizing or sanitizing decoded structures may break these tests even when higher-level consumers ignore those fields. The trust-domain password checker uses hard-coded offsets into the original fixture for password comparison, so layout changes in the IDL must be intentional and accompanied by fixture updates. Some trust auth blob tests have no callback, so they mainly prove parser/pusher acceptance rather than semantic correctness.

Test signals: failures indicate regressions in forest trust record sizing, timestamp endianness, SID parsing, TLN-disabled flags, scanner-info union selection, trust-password offset interpretation, clear-password extraction, supplemental credential prefix/signature parsing, package counting/order, or handling of historically uninitialized trailing data. The strongest safety signal is that captured credentials from multiple eras still parse and push consistently.
