# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/audit_log.c

Purpose: `audit_log.c` is the DSDB ldb module that observes write-side database operations, transaction boundaries, and selected replication extended operations so Samba can emit human-readable audit lines, JSON audit records, and optional messaging-bus events. It converts adds, modifies, deletes, transaction lifecycle events, password/authentication-info changes, and replicated-update metadata into structured audit payloads. It depends on `audit_util.c` for SID/session/DN/value rendering and redaction decisions.

Important APIs, types, and functions: the module-private `struct audit_private` stores event-notification booleans, an `imessaging_context`, the current transaction GUID, and transaction start time. `has_password_changed()` and `has_authentication_information_changed()` classify messages using audit utility attribute sets. `operation_json()`, `replicated_update_json()`, `password_change_json()`, `transaction_json()`, and `commit_failure_json()` build versioned JSON wrappers. Human-readable counterparts are `operation_human_readable()`, `password_change_human_readable()`, `replicated_update_human_readable()`, `transaction_human_readable()`, and `commit_failure_human_readable()`. `audit_callback()` is the ldb asynchronous completion hook. `log_add()`, `log_modify()`, `log_delete()`, and `log_extended()` rebuild requests with this callback and add `DSDB_CONTROL_TRANSACTION_IDENTIFIER_OID`. Transaction hooks are `log_start_transaction()`, `log_prepare_commit()`, `log_end_transaction()`, and `log_del_transaction()`. `ldb_audit_log_module_init()` registers `ldb_audit_log_module_ops`.

Control flow: init allocates `audit_private`, reads `loadparm`, enables DSDB/password event notification, and optionally initializes messaging. Each write operation creates a new downstream ldb request, preserving original controls and adding the current transaction identifier. The callback forwards entries/referrals immediately and logs only when it receives `LDB_REPLY_DONE`, so audit status reflects the final ldb result. Standard operations log DSDB change payloads and, when the input message contains password or authentication attributes, emit additional password-audit events. Transaction start creates a fresh GUID and timestamp; prepare/end failures are logged at failure level; successful end logs a commit at completion level and clears the GUID; rollback logs and clears the GUID.

State and persistence: no database state is persisted by this module. Its only retained state is per-module transaction metadata and the optional messaging client. Audit artifacts leave the process through Samba debug classes, JSON audit logging, and `audit_message_send()` on `DSDB_EVENT_NAME` or `DSDB_PWD_EVENT_NAME`. Attribute values in audit records are redacted or truncated, not stored by the module.

Dependencies and integration points: this file integrates with ldb module callbacks, `lib/audit_logging`, `auth_session_info`, `imessaging`, loadparm flags `lpcfg_dsdb_event_notification()` and `lpcfg_dsdb_password_event_notification()`, password ACL validation control `DSDB_CONTROL_PASSWORD_ACL_VALIDATION_OID`, transaction identifier control `DSDB_CONTROL_TRANSACTION_IDENTIFIER_OID`, and replicated-object extended data `struct dsdb_extended_replicated_objects`. It relies on `audit_util.c` for remote address, user SID/session, request DN/name mapping, and attribute JSON generation.

Risks and edge cases: logging correctness depends on callback completion; operations that bypass these hooks or fail before a downstream request is built may not be audited. Secret redaction is delegated to attribute-name lists, so incomplete lists would leak values. Transaction GUID is module-private and reset on end/rollback; nested or missing transaction callbacks would confuse correlation. `log_operation()` appears to call `log_replicated_operation()` only when the extended OID is not `DSDB_EXTENDED_REPLICATED_OBJECTS_OID`, while `log_extended()` only wraps that OID; this inverted condition is a notable audit-coverage risk for replicated updates. Messaging send is best-effort and does not fail the ldb operation. JSON construction failures produce invalid/empty objects and a debug error rather than blocking the original DB change.

Test signals: Samba selftest registration includes `samba4.dsdb.samdb.ldb_modules.audit_log`, `samba4.dsdb.samdb.ldb_modules.audit_log.errors`, Python audit-log password-change and DSDB suites, and shared `lib.audit_logging` tests. Useful coverage should exercise successful and failed add/modify/delete, password reset versus change controls, authentication attribute changes, transaction rollback/commit failure, JSON error paths, event notification enabled/disabled, and replicated extended-operation logging.
