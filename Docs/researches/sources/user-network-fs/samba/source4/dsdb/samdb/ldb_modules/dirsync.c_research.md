# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/dirsync.c

Purpose: `dirsync.c` implements Samba's LDAP DirSync control handling for DSDB searches. It validates DirSync controls, upgrades/adjusts the underlying search, filters returned attributes and entries based on USNs, replication metadata, linked-value metadata, and up-to-dateness vectors, and returns a refreshed DirSync cookie.

Important APIs, types, and functions: `struct dirsync_context` holds request/module, default attribute count, highest/from-request USN, cursor vector, extended-DN mode, incremental linked-value mode, local-only/partial flags, functional level, invocation ID, schema, and NC root. `dirsync_ldb_search()` is the search hook. `dirsync_filter_entry()` is the large per-entry filtering engine. `dirsync_create_vector()` builds the cookie up-to-dateness vector. `dirsync_search_callback()` handles entries, referrals, and final cookie/control creation. `dirsync_ldb_init()` registers `LDB_CONTROL_DIRSYNC_OID`.

Control flow: searches without DirSync pass through. DirSync requests must be critical and rooted at an NC head. If object-security mode is absent, the module checks `GUID_DRS_GET_CHANGES` against the NC root security descriptor, preserving Windows-like error behavior while not using the result for detailed attribute filtering. Requested attrs are copied and augmented with needed internal attrs such as `uSNChanged`, `replPropertyMetaData`, `instanceType`, `objectGUID`, and `parentGUID`; `*` or null attrs also request full SD flags. Extended-DN, reveal-internals, show-recycled, and show-deleted controls are added as needed. Cookies are unmarshalled to determine `fromreqUSN`, local-only behavior, and cursor suppression. The downstream search is forced to subtree scope and optionally filters `uSNChanged >= fromreqUSN + 1`.

State and persistence: the module persists no server-side state. Client progress is encoded in the returned `ldapControlDirSyncCookie`, which stores time, high-watermark USNs, current invocation ID, and optionally an up-to-dateness vector derived from `replUpToDateVector` on the NC root. Per-request `highestUSN` advances while entries are emitted.

Dependencies and integration points: DirSync depends on ldb LDAP controls, DSDB schema/attribute metadata, replication metadata NDR blobs (`replPropertyMetaDataBlob`, `replUpToDateVectorBlob`, `ldapControlDirSyncCookie`), linked-attribute extended DN components (`RMD_LOCAL_USN`, `RMD_INVOCID`, `RMD_FLAGS`, `RMD_ORIGINATING_USN`), ACL extended rights (`GUID_DRS_GET_CHANGES`), sequence numbers, invocation IDs, and ranged-results behavior that observes the control's critical bit.

Risks and edge cases: filtering is complex and security-sensitive because it decides what changed data is disclosed. Backlinks, constructed/non-replicated attrs, deleted links, referrals, NC roots, RDN attributes, and incremental linked values all have special paths. Cookie parsing failure maps to unsupported critical extension. The module ignores some advertised flags (`ANCESTORS_FIRST_ORDER`, `PUBLIC_DATA_ONLY`) and marks partial false unconditionally, so paging/size-limit behavior should be reviewed with surrounding modules. Attribute filtering relies on replicated metadata being present and parseable; missing metadata on inaccessible deleted objects is treated specially. Timing/commentary around filtered attribute sets notes a known limitation.

Test signals: selftest registers `samba4.ldap.dirsync.python(ad_dc_ntvfs)` via `dsdb/tests/python/dirsync.py`. Strong tests should cover first sync, cookie resume, cross-invocation vectors, object-security flag behavior, insufficient rights error selection, null/`*`/specific attrs, incremental linked-value add/delete ranges, deleted/recycled objects, referrals to other naming contexts, malformed cookies, and interaction with ranged results.
