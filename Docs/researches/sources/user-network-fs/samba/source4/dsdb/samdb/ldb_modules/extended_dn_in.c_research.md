# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/extended_dn_in.c

Purpose: `extended_dn_in.c` is an input-side ldb module that resolves extended DN syntax such as `<GUID=...>`, `<SID=...>`, and `<WKGUID=...>` into normal database DNs before search/modify/delete/rename processing. It also rewrites DN-valued search filter terms so filters against linked DN attributes use canonical extended-linearized DNs.

Important APIs, types, and functions: `struct extended_search_context` carries original request, rewritten parse tree, candidate base DN, input DN, and WKGUID prefix. `extended_base_callback()` resolves the base extended DN and builds the real downstream operation. `extended_final_callback()` forwards downstream replies. `ldb_dn_match_allowed()` enforces stricter LDAP-facing syntax for untrusted requests. Filter rewriting is handled by `struct extended_dn_filter_ctx`, `set_parse_tree_false()`, `extended_dn_filter_callback()`, and `extended_dn_fix_filter()`. `extended_dn_in_fix()` orchestrates base-DN and filter rewriting for search/modify/delete/rename hooks. Module init registers both `extended_dn_in_openldap` and `extended_dn_in`.

Control flow: each operation calls `extended_dn_in_fix()` with the operation DN. Search requests first walk the filter in test mode; if a DN-valued equality/transitive term needs resolution, the parse tree is shallow-copied and rewritten. If the operation DN has no extended component, the original or filter-rewritten request is passed down. Otherwise, the module validates extended-DN shape for untrusted requests, prioritizes GUID lookup over SID lookup, handles WKGUID by searching `wellKnownObjects`/`otherWellKnownObjects` under the specified base, and performs an internal system search with extended-DN display. The base callback rejects duplicate matches, maps no match to `NO_SUCH_OBJECT`, and then builds the original operation with the resolved DN.

State and persistence: no persistent state is kept. All resolution state is request-scoped talloc data. The module reads schema metadata and database objects to canonicalize DNs but does not modify DB contents directly.

Dependencies and integration points: it uses ldb extended DN APIs, DSDB schema attributes with `dn_format == DSDB_NORMAL_DN`, matching rule `SAMBA_LDAP_MATCH_RULE_TRANSITIVE_EVAL`, always-false matching rule `SAMBA_LDAP_MATCH_ALWAYS_FALSE`, DSDB search flags for system/extended-DN/deleted/recycled/DBCHECK behavior, all-partition searches for GUID/SID, and WKGUID attributes `wellKnownObjects` and `otherWellKnownObjects`. The OpenLDAP variant avoids certain one-way-link transformations.

Risks and edge cases: resolving by SID can be ambiguous, so GUID is prioritized; duplicate matches intentionally return `NO_SUCH_OBJECT`. Untrusted LDAP requests with multiple extended components are rejected or rewritten to always false. Treating confidential indexed DN attributes as unindexed avoids timing side channels, but changes search behavior. Filter parse-tree shallow copies and in-place value replacement require careful ownership. WKGUID parsing depends on a comma separator and `B:32:<guid>:` prefix matching. Failed internal lookups often return success without rewriting filter terms, which can make malformed DN filters behave as no-match instead of hard failure.

Test signals: useful coverage is typically LDAP behavior tests around extended DN searches and link filters. Cases should include GUID/SID/WKGUID base resolution, duplicate SID matches, untrusted invalid multi-component extended DNs, deleted/recycled controls, DBCHECK behavior, DN-valued equality filters, transitive-eval filters, confidential indexed DN attributes, OpenLDAP module variant behavior, and modify/delete/rename using extended old DNs.
