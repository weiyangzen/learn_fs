# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/dns_notify.c

Purpose: `dns_notify.c` is an ldb transaction module that detects changes to DNS zone objects under Samba's MicrosoftDNS containers and notifies the internal DNS server to reload zones after a successful transaction. It covers direct database changes and replicated inbound changes that create, modify, or delete `dnsZone` objects.

Important APIs, types, and functions: `struct dns_notify_private` stores a linked list of watched base DNs and a transaction-scoped `reload_zones` flag. `struct dns_notify_watched_dn` stores each watched container. `dns_notify_add()`, `dns_notify_modify()`, and `dns_notify_delete()` detect relevant changes. `dns_notify_start_trans()`, `dns_notify_end_trans()`, and `dns_notify_del_trans()` manage transaction state. `dns_notify_dnssrv_send()` creates an `imessaging` client, binds to IRPC service `dnssrv`, and sends `dcerpc_dnssrv_reload_dns_zones_r_send()`. `dns_notify_dnssrv_done()` receives completion and cleans up.

Control flow: init builds watched DNs for `CN=MicrosoftDNS,CN=System,<domain>`, `CN=MicrosoftDNS,DC=DomainDnsZones,<forest>`, and `CN=MicrosoftDNS,DC=ForestDnsZones,<forest>`. Add checks whether the new DN is below a watched container and whether the structural object class is `dnsZone`; modify/delete first search the existing object class, then set `reload_zones` if it is a zone. Relax-control and special-DN requests pass through. At transaction start/rollback the reload flag is cleared. At successful transaction end, if the flag is set, the module asynchronously sends an IRPC reload request to the DNS server.

State and persistence: watched DNs are module-private state. `reload_zones` is transient transaction state. No ldb data is changed by this module; the only side effect is an asynchronous reload notification after commit. Failed notification logs debug output but does not roll back the committed database transaction.

Dependencies and integration points: the module uses DSDB schema lookup, structural object-class resolution, DSDB module search helpers with recycled/internal/storage-format flags, ldb transaction hooks, `imessaging_client_init()`, `irpc_binding_handle_by_name()`, generated DNSSRV IRPC client stubs, loadparm, and Samba event context. It is tightly coupled to Samba AD DNS partition layout.

Risks and edge cases: notification is best-effort, so DNS may be stale if messaging setup, IRPC binding, send, or async completion fails. The code skips requests with `LDB_CONTROL_RELAX_OID`. In `dns_notify_modify()` and `dns_notify_delete()`, the watched-base comparison references `req->op.add.message->dn` even though the active operation is modify/delete; this union-field access is a serious correctness/crash risk and could prevent reloads. The module notifies once per transaction regardless of how many zones changed. Watched DNs are constructed unconditionally; absent DNS partitions are not validated at init.

Test signals: coverage is likely integration-level through DNS server/database tests rather than direct unit tests. Useful tests include add/modify/delete of `dnsZone` in all three watched containers, non-zone DNS child changes that should not reload, relaxed operations, transaction rollback, multiple changes in one transaction, missing/unreachable `dnssrv`, and the modify/delete watched-DN access path.
