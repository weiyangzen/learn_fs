# sources/user-network-fs/samba/source3/librpc/crypto/gse.c

## Purpose
`gse.c` implements Samba source3's GENSEC backend for Kerberos GSSAPI security extensions. It provides the `gse_krb5` mechanism used by SPNEGO/DCERPC/SMB client and server paths to acquire credentials, run GSS context establishment, expose negotiated features, derive session keys and session information, and sign, seal, wrap, and unwrap application packets.

## Important APIs, types, and functions
- `struct gse_context` is the private mechanism state: GSS context, imported server/client names, desired and negotiated GSS flags, wrap and signature sizing cache, delegated creds, expiry time, Kerberos context/ccache/keytab, selected mechanism OID, imported creds, returned mechanism OID, and optional channel bindings.
- `gensec_gse_security_by_oid()` is the exported selector. It currently returns the static Kerberos ops only for `GENSEC_OID_KERBEROS5`.
- Client setup flows through `gensec_gse_client_start()`, `gensec_gse_client_prepare_ccache()`, and `gse_init_client()`.
- Server setup flows through `gensec_gse_server_start()` and `gse_init_server()`, which imports an acceptor credential from `gse_krb5_get_server_keytab()`.
- Token exchange is handled by `gensec_gse_update_send/recv()` and `gensec_gse_update_internal()`, dispatching to `gse_get_client_auth_token()` or `gse_get_server_auth_token()`.
- Packet services are `gensec_gse_wrap/unwrap()`, `gensec_gse_sign_packet/check_packet()`, and `gensec_gse_seal_packet/unseal_packet()`.
- Introspection helpers include `gensec_gse_have_feature()`, `gensec_gse_expire_time()`, `gensec_gse_session_key()`, `gensec_gse_session_info()`, `gensec_gse_max_input_size()`, `gensec_gse_max_wrapped_size()`, `gensec_gse_sig_size()`, and `gensec_gse_final_auth_type()`.

## Control flow
Startup allocates `struct gse_context`, installs a destructor, initializes Kerberos, copies channel binding pointers from `gensec_security`, and sets GSS desired flags from requested GENSEC features. Client startup first checks that Kerberos is possible, reuses or creates a credential cache, optionally performs password-based `kinit`, imports the ccache as a GSS credential, and starts the Kerberos mechanism. Server startup builds an in-memory keytab and imports it as acceptor credentials.

During client token generation, the code constructs or reuses a server principal, then calls `gss_init_sec_context()`. Non-Heimdal builds first try the client realm and can fall back to a realm derived from the hostname for external trust scenarios. Major/minor GSS and Kerberos errors are mapped to NTSTATUS values that higher SPNEGO layers can interpret, including server-principal-not-found, expired ticket, clock skew, KDC unreachable, unsupported enctype, and generic logon failure. Server token generation calls `gss_accept_sec_context()`, enforces required channel binding evidence when supported, maps continue/complete/bad-binding/failure status, and returns output tokens when present.

After authentication, wrapping and packet signing/sealing delegate to Samba GSS helper functions. Feature detection consults negotiated GSS flags and, for `GENSEC_FEATURE_NEW_SPNEGO`, rejects legacy key types that should keep old SPNEGO behavior.

## State and persistence behavior
The file owns volatile security-context state, not durable on-disk state. Kerberos ccaches may be created in memory and attached to `cli_credentials`; imported acceptor credentials are based on a keytab generated by `gse_krb5.c`. The destructor closes ccaches and keytabs, frees Kerberos context, releases GSS names/contexts/credentials, and asserts that mechanism OIDs remain static Kerberos OIDs. Expiry is tracked as `NTTIME` after GSS completion. `sig_size` caches the computed signature length for later packet sizing.

## Dependencies and integration points
This file is compiled only with `HAVE_KRB5`. It depends on GSSAPI, Samba Kerberos helpers, GENSEC, cli credentials, PAC/session-info generation, loadparm settings, `gse_krb5_get_server_keytab()`, and DCERPC auth type constants. It is consumed by auth setup (`auth_generic.c`), DCERPC helpers through GENSEC packet callbacks, SMB session setup, and SPNEGO negotiation.

## Risks and edge cases
Security-sensitive behavior includes channel binding enforcement, credential cache ownership, fallback realm selection, delegated credential cleanup, negotiated signing/sealing flags, and correct NTSTATUS mapping for SPNEGO fallback. A mismatch between requested and negotiated seal/sign flags can silently weaken behavior if callers do not check `have_feature()`. The MIT/Heimdal differences around DNS canonicalization, realm fallback, `gss_store_cred_into()`, and OID ownership are important portability risks. Packet-size logic relies on stable `gssapi_get_sig_size()` behavior after negotiation.

## Test signals
Useful validation includes Kerberos client/server authentication against MIT and Heimdal, external trust referral/fallback cases, required and optional channel-binding cases, sign-only and seal modes, DCE-style auth, ticket-expired/clock-skew/KDC-down error mapping, SPNEGO mechListMIC behavior with old RC4/DES/3DES keys, and leak/destructor tests for failed handshakes.
