## Scope

This chunk covers the first 5,068 lines of Rook's generated `deploy/examples/csi-operator.yaml` manifest. The range contains four complete `apiextensions.k8s.io/v1` CRDs in the `csi.ceph.io` API group: `CephConnection`, `ClientProfileMapping`, `ClientProfile`, and `Driver`. It then begins the `OperatorConfig` CRD and continues through the early `spec.driverSpecDefaults.controllerPlugin.volumes.volume.rbd.monitors[]` schema before the chunk boundary cuts the CRD mid-field.

The file is declarative Kubernetes YAML generated by `controller-gen.kubebuilder.io/version: v0.17.2`. There are no executable functions in this range. The important interfaces are the CRD names, namespaced API resources, OpenAPI v3 schemas, CEL validations, Kubernetes structural schema extensions, and `/status` subresources.

## Purpose

These CRDs define the Kubernetes API surface consumed by the Ceph CSI operator. They let cluster administrators describe external Ceph connection details, map local and remote client profiles, define per-client Ceph CSI profile settings, create CSI `Driver` instances, and establish operator-wide driver defaults through `OperatorConfig`.

`CephConnection` captures the Ceph monitor endpoints required to connect to a Ceph cluster. It also models optional RBD mirror daemon count and CRUSH-location read affinity labels.

`ClientProfileMapping` maps remote client profiles to local client profiles and can map block pool IDs in fixed two-element string pairs. This is a cross-cluster or replication-oriented association layer rather than a workload deployment spec.

`ClientProfile` binds a profile to a `CephConnection` and carries protocol-specific settings for CephFS, RBD, NVMe-oF, and NFS. It is the place where CSI secret references, RADOS namespace settings, CephFS mount options, and CephFS subvolume group configuration are persisted.

`Driver` is the main desired-state API for deploying one Ceph CSI driver instance. Its schema covers driver identity, driver type naming, controller plugin deployment settings, node plugin daemonset settings, sidecar resources, log and liveness settings, encryption configuration, CSI-Addons integration, fencing and metadata toggles, leader election timing, mount options, and snapshot policy.

The visible part of `OperatorConfig` begins an operator-level defaulting API. In this chunk it defines the start of `spec.driverSpecDefaults`, which mirrors the `Driver` spec shape so defaults can be applied consistently to driver resources.

## Important APIs And Schema Surfaces

`CephConnection` exposes the namespaced resource `cephconnections.csi.ceph.io/v1`. `spec.monitors` is required and must contain at least one string. `spec.rbdMirrorDaemonCount` must be at least 1 when set. `spec.readAffinity.crushLocationLabels` is required inside `readAffinity` and must also contain at least one label. The CRD enables a status subresource, but `status` is only typed as a generic object in this generated schema.

`ClientProfileMapping` exposes `clientprofilemappings.csi.ceph.io/v1`. `spec.mappings` is required. Each mapping requires `localClientProfile` and `remoteClientProfile`, with optional `blockPoolIdMapping` entries represented as arrays of exactly two strings. The fixed pair shape is the main validation signal for pool ID translation.

`ClientProfile` exposes `clientprofiles.csi.ceph.io/v1`. `spec.cephConnectionRef` is required, and `cephConnectionRef.name` defaults to an empty string but is validated as non-empty. `spec.cephFs`, `spec.rbd`, and `spec.nvmeof` can each carry `cephCsiSecrets.controllerPublishSecret` references with `name` and `namespace`. CephFS also supports `fuseMountOptions`, `kernelMountOptions`, `radosNamespace`, and `subVolumeGroup`. RBD and NVMe-oF support `radosNamespace`. All protocol-specific `radosNamespace` fields are immutable by CEL validation. `spec.nfs` is currently an unstructured empty object placeholder.

`Driver` exposes `drivers.csi.ceph.io/v1`. Its metadata name is validated by CEL against `[<prefix>.](rbd|cephfs|nfs|nvmeof).csi.ceph.com`, which ties driver resources to CSI driver names. Top-level fields include `attachRequired`, `cephFsClientType` enum `autodetect|kernel`, `clusterName`, `deployCsiAddons`, `enableFencing`, `enableMetadata`, `fsGroupPolicy`, `generateOMapInfo`, `grpcTimeout`, `fuseMountOptions`, `kernelMountOptions`, `snapshotPolicy`, and references to `imageSet` and encryption config maps.

`Driver.spec.encryption.configMapName.name` and `Driver.spec.imageSet.name` use the same pattern as `ClientProfile`: default empty string plus a non-empty CEL validation. `grpcTimeout`, leader election durations, and retry periods must be non-negative. `liveness.metricsPort` is required when `liveness` is set and must be between 1024 and 65535. `snapshotPolicy` is constrained to `none`, `volumeGroupSnapshot`, or `volumeSnapshot`.

`Driver.spec.controllerPlugin` embeds Kubernetes workload customization for controller deployments. It includes affinity, pod annotations and labels, extra container args, deployment strategy with `maxSurge` and `maxUnavailable` as int-or-string values, `hostNetwork`, image pull policy, priority class, privileged mode, `replicas` with minimum 1, service account name, tolerations, resources, and additional volumes.

`controllerPlugin.resources` is split by CSI sidecar/container role: `addons`, `attacher`, `liveness`, `logRotator`, `omapGenerator`, `plugin`, `provisioner`, `resizer`, and `snapshotter`. Each resource section follows Kubernetes `ResourceRequirements` structure with `claims`, `limits`, and `requests`. Quantity values use Kubernetes int-or-string quantity regex validation.

`Driver.spec.nodePlugin` is the node-side equivalent for daemonset-style deployment. It includes affinity, annotations, extra args, `enableSeLinuxHostMount`, image pull policy, `kubeletDirPath`, labels, priority class, sidecar resources, service account, tolerations, topology domain labels, update strategy, and additional volumes. Node resources are split across `addons`, `liveness`, `logRotator`, `plugin`, and `registrar`.

Both plugin sections embed Kubernetes `VolumeMount` plus `VolumeSource` schemas for extra volumes. The volume source schema is broad and includes in-tree and projected volume types such as AWS EBS, Azure Disk/File, CephFS, Cinder, config maps, CSI, downward API, emptyDir, ephemeral PVC templates, Fibre Channel, flexVolume, Flocker, GCE PD, gitRepo, GlusterFS, hostPath, image, iSCSI, NFS, PVC, Photon, Portworx, projected sources, Quobyte, RBD, secrets, StorageOS, and vSphere. The chunk repeats this volume schema for controller and node plugins and starts repeating it again under `OperatorConfig.driverSpecDefaults.controllerPlugin`.

`Driver.spec.log` contains `rotation` and `verbosity`. `rotation.periodicity` is limited to `hourly`, `daily`, `weekly`, or `monthly`, and CEL requires either `maxLogSize` or `periodicity` whenever `rotation` is present. `verbosity` is constrained from 0 to 5.

The visible `OperatorConfig` API exposes `operatorconfigs.csi.ceph.io/v1` and begins `spec.driverSpecDefaults`. The shown fields mirror early `Driver` fields: `attachRequired`, `cephFsClientType`, `clusterName`, and `controllerPlugin` workload customization. This chunk ends before the `OperatorConfig` CRD schema is complete.

## Control Flow

There is no imperative control flow in the YAML itself. Runtime behavior is driven by Kubernetes API registration and the Ceph CSI operator:

1. A user applies `csi-operator.yaml` to the cluster.
2. The Kubernetes API server registers the namespaced `csi.ceph.io/v1` resources and uses these OpenAPI schemas for create/update validation, pruning, merge semantics, and status subresource separation.
3. Users or higher-level automation create `CephConnection`, `ClientProfileMapping`, `ClientProfile`, `Driver`, and `OperatorConfig` custom resources.
4. The Ceph CSI operator watches those resources and reconciles CSI controller deployments, node daemonsets, sidecar containers, config maps, secret references, CSI-Addons behavior, liveness endpoints, leader election settings, and per-driver snapshot behavior.
5. Controllers write status through the `/status` subresource where enabled. In this chunk every complete CRD exposes `subresources.status`, but status schemas are generic objects.

The `Driver` control path is the most operationally significant: metadata name validation selects the CSI driver identity, `controllerPlugin` configures controller workloads, `nodePlugin` configures node workloads, and top-level toggles enable or disable auxiliary features such as metadata, fencing, OMAP generation, encryption, and CSI-Addons deployment.

## State And Persistence Behavior

The CRDs persist API definitions in Kubernetes. Custom resources created from them persist desired state in etcd, while their generic `status` objects persist operator-observed state.

Long-lived desired state includes Ceph monitor endpoints, profile mappings, Ceph connection references, secret references, RADOS namespace names, mount options, sidecar resource requests and limits, scheduling constraints, leader election timing, liveness ports, log rotation policy, and extra Kubernetes volumes. These settings affect reconciled Kubernetes workloads and, through the CSI drivers, storage behavior.

Several schema rules influence update behavior. `ClientProfile` protocol-specific `radosNamespace` fields are immutable, so changing a namespace requires replacing the custom resource or using a new profile. `x-kubernetes-map-type: atomic` appears on object references and many embedded Kubernetes objects, causing server-side apply and merge behavior to replace those subtrees atomically. Many embedded Kubernetes lists use `x-kubernetes-list-type: atomic`; resource claim lists use `x-kubernetes-list-type: map` keyed by `name`.

Default-empty object references combined with non-empty CEL validations are important persistence semantics. If fields such as `cephConnectionRef.name`, `encryption.configMapName.name`, or `imageSet.name` are omitted in a context where their containing object exists, defaulting can produce an empty string that validation then rejects.

The extra-volume schemas can persist references to many Kubernetes resources and host paths. These do not create storage directly inside the CRD, but they become part of the operator's rendered controller and node pod templates.

## Dependencies And Integration Points

The primary dependency is Kubernetes CRD support from `apiextensions.k8s.io/v1`, including structural schemas, CEL validation, status subresources, int-or-string handling, and server-side apply merge hints.

The main runtime consumer is the Ceph CSI operator. Its Go API types and reconcilers must match this generated schema. It integrates these resources with Ceph CSI drivers for RBD, CephFS, NFS, and NVMe-oF, and with CSI sidecars such as the external attacher, provisioner, resizer, snapshotter, node-driver registrar, liveness probe, OMAP generator, log rotator, and CSI-Addons components.

`CephConnection` and `ClientProfile` integrate with Ceph cluster connection data and Kubernetes secrets. `ClientProfileMapping` integrates profile names and block pool IDs across local and remote contexts. `Driver` integrates with Kubernetes workload APIs through embedded affinity, deployment strategy, daemonset update strategy, resources, tolerations, service accounts, and volume definitions.

The generated manifest is also an integration boundary between Rook release artifacts and cluster operators. Because this file lives under `deploy/examples`, it is meant to be directly applied or used as a reference manifest rather than rendered from a Helm chart in this path.

## Risks And Edge Cases

The `OperatorConfig` CRD is incomplete in this chunk. Any research or merge step must combine this note with later chunks before describing the full `OperatorConfig` API.

The generated schemas embed large Kubernetes workload and volume schemas. Manual edits are risky because list/map merge hints, int-or-string quantity patterns, required fields, and atomic object annotations must stay structurally valid for the API server.

`Driver` metadata name validation can reject resources before reconciliation. Tests and examples must use names such as `rbd.csi.ceph.com`, `cephfs.csi.ceph.com`, `nfs.csi.ceph.com`, `nvmeof.csi.ceph.com`, or the allowed prefixed variants.

Several fields have validation only at the API layer, not controller logic in this file. Invalid `snapshotPolicy`, `cephFsClientType`, liveness ports, negative timeouts, missing required monitor lists, and bad resource quantities should fail at admission. Secret references, mount option keys, and many workload customization values are only typed as strings or maps and may fail later during reconciliation.

Immutability of `radosNamespace` is a migration hazard. A typo or namespace change in `ClientProfile` cannot be patched in place once stored.

The extra-volume schema permits powerful pod customizations including host paths, projected credentials, PVCs, and legacy in-tree volume types. That flexibility is useful for deployments but broadens the security and compatibility surface of driver pods.

Status is intentionally weakly typed as a generic object for the CRDs in this chunk. Consumers should avoid relying on detailed status structure from this schema alone and should verify operator-specific status contracts in controller code or later documentation.

## Purpose

The schema section preserves Kubernetes-native pod and volume shapes so users can declaratively customize generated CSI controller/node pods without bypassing API-server validation. ## Important Kubernetes APIs And Manifest Objects

The first part of the chunk remains inside a large CRD `openAPIV3Schema`. The visible schema fields include CSI deployment options such as `deployCsiAddons`, `enableFencing`, `enableMetadata`, `encryption.configMapName`, `fsGroupPolicy`, `fuseMountOptions`, `generateOMapInfo`, `grpcTimeout`, `imageSet`, `kernelMountOptions`, `leaderElection`, `liveness`, `log.rotation`, `log.verbosity`, `nodePlugin`, and `snapshotPolicy`.

`nodePlugin` is a major schema surface. It allows pod-level customization for node plugin pods: `affinity`, `annotations`, `containerExtraArgs`, `enableSeLinuxHostMount`, `imagePullPolicy`, `kubeletDirPath`, `labels`, `priorityClassName`, `resources`, `serviceAccountName`, `tolerations`, `topology`, `updateStrategy`, and `volumes`. The embedded affinity schema mirrors Kubernetes `NodeAffinity`, `PodAffinity`, and `PodAntiAffinity`, including `preferredDuringSchedulingIgnoredDuringExecution`, `requiredDuringSchedulingIgnoredDuringExecution`, selectors, namespace selectors, match label keys, mismatch label keys, and topology keys.

The `resources` schema is split by CSI sidecar/container role: `addons`, `liveness`, `logRotator`, `plugin`, and `registrar`. Each role accepts Kubernetes-style resource `claims`, `limits`, and `requests`. Quantity fields use `x-kubernetes-int-or-string` and the Kubernetes quantity regex, which lets users express values such as integer CPU-like values or strings like `500m`, `128Mi`, and similar resource quantities.

The `volumes` array defines pairs of `mount` and `volume`. `mount` resembles Kubernetes `VolumeMount`, requiring `mountPath` and `name` and allowing `mountPropagation`, `readOnly`, `recursiveReadOnly`, `subPath`, and `subPathExpr`. `volume` embeds many Kubernetes volume sources, including `awsElasticBlockStore`, `azureDisk`, `azureFile`, `cephfs`, `csi`, `downwardAPI`, `emptyDir`, `ephemeral`, `fc`, `flexVolume`, `flocker`, `gcePersistentDisk`, `gitRepo`, `glusterfs`, `hostPath`, `image`, `iscsi`, `nfs`, `persistentVolumeClaim`, `photonPersistentDisk`, `portworxVolume`, `projected`, `quobyte`, `rbd`, `scaleIO`, `secret`, `storageos`, and `vsphereVolume`. Required fields are preserved for many source types, such as `volumeID` for AWS EBS, `diskName`/`diskURI` for Azure Disk, `secretName`/`shareName` for Azure File, `driver` for CSI, `spec` for ephemeral PVC templates, `pdName` for GCE PD, `iqn`/`lun`/`targetPortal` for iSCSI, `path`/`server` for NFS, `claimName` for PVCs, and `image`/`monitors` for RBD.

`projected` volume sources include current Kubernetes projection types: `clusterTrustBundle`, `configMap`, `downwardAPI`, `podCertificate`, `secret`, and `serviceAccountToken`. These schemas retain required path-like fields and mark config map/secret references as atomic maps. This is important for server-side apply and CRD merge behavior.

The end of the CRD schema sets `snapshotPolicy` to one of `none`, `volumeGroupSnapshot`, or `volumeSnapshot`, provides a top-level `log.verbosity` constrained from 0 to 3, leaves `status` as an object, marks the CRD version `served: true` and `storage: true`, and enables the `status` subresource.

After the CRD, the chunk defines ServiceAccounts in `rook-ceph`: controller and node plugin identities for CephFS, NFS, NVMe-oF, and RBD, plus the `ceph-csi-controller-manager` service account for the operator itself.

Namespace-scoped `Role` objects provide plugin-local permissions. Controller plugin roles for CephFS, NVMe-oF, and RBD can manage `coordination.k8s.io` leases, manipulate `csiaddons.openshift.io/csiaddonsnodes`, read pods/replicasets, and update Deployment/DaemonSet finalizers. Node plugin roles can manage CSI addons nodes, read pods/replicasets, and update workload finalizers. `ceph-csi-leader-election-role` grants the manager access to ConfigMaps, Leases, and Events for controller-runtime leader election.

ClusterRole objects are the broad control-plane permissions. Viewer/editor roles are generated for `cephconnections`, `clientprofiles`, `clientprofilemappings`, `drivers`, and `operatorconfigs` under `csi.ceph.io`, with status reads included. `ceph-csi-manager-role` lets the operator manage ConfigMaps, Services, DaemonSets, Deployments, custom CSI objects, their finalizers/status, `operatorconfigs`, and `storage.k8s.io/csidrivers`. The metrics roles provide `/metrics` read access plus TokenReview and SubjectAccessReview permissions for authenticated metrics serving.

CSI plugin ClusterRoles differ by storage backend. CephFS, NFS, NVMe-oF, and RBD controller roles can read or manage PVs/PVCs, StorageClasses, CSINodes, Nodes, VolumeAttachments, Events, Secrets/ConfigMaps, snapshot resources, service account tokens, and token reviews. CephFS and RBD include group snapshot and OpenShift replication/group-snapshot APIs; RBD also reads `cbt.storage.k8s.io/snapshotmetadataservices`. Node plugin ClusterRoles are narrower, centered on reading nodes, secrets, PVs, volume attachments, config maps, service accounts/tokens, token reviews, events, and PVCs as needed by node-side CSI operations.

RoleBindings and ClusterRoleBindings connect each role to the matching ServiceAccount. The manager service account is bound to manager and metrics-auth ClusterRoles and to the namespace leader-election Role. Each plugin service account is bound to both its namespace Role and backend-specific ClusterRole.

The final Deployment installs `ceph-csi-controller-manager` in `rook-ceph` with one replica, the `ceph-csi-controller-manager` service account, `/manager --leader-elect`, and image `quay.io/cephcsi/ceph-csi-operator:v1.0.1`. It sets `OPERATOR_NAMESPACE` from the pod namespace, `CSI_SERVICE_ACCOUNT_PREFIX` to `ceph-csi-`, and `WATCH_NAMESPACE` to an empty string, implying cluster-wide watching. Health endpoints are `/healthz` and `/readyz` on port 8081. The container has small CPU/memory requests and limits, drops all Linux capabilities, disallows privilege escalation, uses a read-only root filesystem, and the pod runs as non-root.

## Control Flow

The runtime flow is Kubernetes-driven:

1. Applying this manifest registers or updates CRD schema validation and status-subresource behavior for the CSI operator CRDs.
2. Kubernetes creates the service accounts, roles, cluster roles, bindings, and controller-manager Deployment.
3. The Deployment starts one manager pod running `/manager --leader-elect`.
4. Controller-runtime leader election uses the namespace Role over ConfigMaps/Leases/Events so only the active manager reconciles.
5. The manager watches `csi.ceph.io` resources and storage APIs according to `ceph-csi-manager-role`.
6. When reconciling CSI driver CRs/config, the manager creates/updates Deployments, DaemonSets, Services, ConfigMaps, CSIDrivers, and status/finalizer fields.
7. Managed CSI controller and node pods run under backend-specific service accounts. Their Role and ClusterRole permissions let sidecars perform provisioning, attaching, snapshotting, token review, event emission, lease handling, and CSI addons node registration as applicable.

The schema portion affects control flow before reconciliation starts: invalid CR specs are rejected by the API server, defaults may be applied for fields such as several secret names and legacy volume defaults, and structural schema hints such as atomic maps/lists affect how apply/patch operations merge user intent.

## State And Persistence Behavior

Persistent state is stored in Kubernetes, not in local files:

- CRD definitions persist accepted schemas, version storage flags, and the `status` subresource.
- Custom resources created later under `csi.ceph.io` persist desired CSI operator state and status.
- RBAC objects persist the authorization model for operator and plugin identities.
- Leader election persists transient coordination state in ConfigMaps or Leases in the `rook-ceph` namespace.
- Generated Deployments, DaemonSets, Services, ConfigMaps, CSIDrivers, PV/PVC updates, snapshots, group snapshots, and finalizers are reconciled through Kubernetes resources.

The schema uses `x-kubernetes-list-type: atomic` for many embedded Kubernetes arrays and `x-kubernetes-map-type: atomic` for selected references/selectors. This affects persistence during server-side apply: callers replace whole atomic lists/maps rather than merging individual nested items. The `status` subresource separates controller-written status from user-written spec, which is required for safe reconciliation.

The Deployment sets `WATCH_NAMESPACE` to an empty value, so persisted operator behavior is cluster-scoped unless downstream tooling patches this value. `CSI_SERVICE_ACCOUNT_PREFIX` is also persisted as pod environment and must align with the service account names declared in this same chunk.

## Dependencies And Integration Points

This manifest integrates with standard Kubernetes APIs: `v1` ServiceAccounts, RBAC `Role`, `ClusterRole`, `RoleBinding`, `ClusterRoleBinding`, `apps/v1` Deployments/DaemonSets, `coordination.k8s.io` Leases, storage resources under `storage.k8s.io`, snapshots under `snapshot.storage.k8s.io`, and core PV/PVC/Node/Secret/ConfigMap/Event APIs.

It also integrates with non-core or optional APIs:

- `csiaddons.openshift.io/csiaddonsnodes` for CSI addons integration.
- `groupsnapshot.storage.k8s.io` and `groupsnapshot.storage.openshift.io` for volume group snapshot flows.

The schema embeds Kubernetes pod customization APIs rather than inventing a separate scheduling model. This makes it integrate naturally with cluster-level schedulers, topology labels, tolerations, priority classes, update strategies, resource quotas, secret/configmap projection, and volume mounting policies.

## Risks And Edge Cases

The manifest grants broad cluster permissions to CSI controller service accounts. PV/PVC create/update/delete, VolumeAttachment patch/status, snapshot content update/status, service account token creation, and TokenReview permissions are powerful. These are typical for CSI sidecars, but any namespace compromise of a plugin service account has cluster-level blast radius.

Optional API groups can be absent. Clusters without snapshot, group snapshot, OpenShift replication, CBT, or CSI addons CRDs may reject RBAC rules for unknown resources depending on API-server behavior and installation order, or the operator may reconcile features that remain unavailable. Install sequencing should account for optional CRDs.

The CRD embeds a very large subset of Kubernetes volume source schema, including legacy and cloud-provider-specific volume types. This is convenient but increases drift risk when Kubernetes removes, deprecates, or changes embedded fields. The schema already includes newer fields such as `podCertificate`, `clusterTrustBundle`, `volumeAttributesClassName`, and `recursiveReadOnly`, so compatibility with older Kubernetes API servers should be checked.

Atomic list/map annotations reduce merge ambiguity but can surprise users applying partial patches. For example, updating one projected source or affinity term can replace an entire atomic list rather than merging a single item.

Validation is uneven by design because the schema mirrors Kubernetes object shapes. Many string fields, object maps, tolerations, update strategy types, and mount options are only typed, not semantically constrained. The API server can accept values that later fail in the operator, scheduler, kubelet, or CSI sidecar.

`WATCH_NAMESPACE` is empty in the Deployment. That is appropriate for a cluster-scoped operator but is risky in multi-tenant clusters if the intended deployment should be namespace-scoped. It also requires the broad ClusterRoles defined here.

The operator image is pinned to `quay.io/cephcsi/ceph-csi-operator:v1.0.1`. Upgrading the image without updating CRDs/RBAC can create version skew; updating CRDs/RBAC without the image can expose fields the running controller does not understand.

The Deployment selector and pod template labels use `control-plane: ceph-csi-op-controller-manager`, while Deployment metadata also uses `control-plane: controller-manager`. That is valid because the selector matches the pod template, but tooling that expects the metadata label value to match the selector could be confused.

Security posture is good for the manager container, but this chunk only shows the operator Deployment. The generated CSI node plugins are likely privileged elsewhere because CSI node plugins commonly need host mounts and kubelet integration. The CRD also exposes `hostPath`, mount propagation, and `enableSeLinuxHostMount`, so downstream CRs can request sensitive host integration.
