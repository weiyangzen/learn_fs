# sources/control-plane/rook/pkg/operator/ceph/cluster/osd/osd_test.go

## Purpose
`osd_test.go` is the broad behavioral test suite for the Ceph OSD cluster reconciler. It validates OSD property helpers, `Cluster.Start()` orchestration, node add/remove flows, post-reconcile OSD property updates, cleanup of dangling prepare artifacts, deployment-to-`OSDInfo` round trips, CRUSH location derivation, CephCluster storage status updates, CephX status aggregation, storage spec validation, and device-class resolution.

## Important APIs, Types, and Functions
The file exercises `New()`, `Start()`, `postReconcileUpdateOSDProperties()`, `getPVCHostName()`, `makeDeployment()`, `getOSDInfo()`, `updateLocationWithNodeLabels()`, `updateCephOsdStorageStatus()`, `getOSDLocationFromArgs()`, `validateOSDSettings()`, `perDeviceClassForOSD()`, and `resolveDeviceClass()`. Local helpers create fake discover ConfigMaps and Kubernetes Nodes, while `mockNodeOrchestrationCompletion()` and `waitForOrchestrationCompletion()` are shared with status tests to drive the ConfigMap watch loop.

## Control Flow, State, and Persistence
Most tests build fake Kubernetes clients, fake controller-runtime clients, fake Rook clients, and mock Ceph executors. `TestAddRemoveNode` starts reconciliation in a goroutine, waits for an OSD prepare status ConfigMap to reach `starting`, modifies it to `completed`, and verifies a deployment appears. It then removes the node from storage spec and confirms the health monitor, not the basic reconcile, removes the OSD deployment when safe-to-destroy conditions are mocked. Cleanup tests seed status ConfigMaps and Jobs and verify reconcile deletes orphaned resources while preserving jobs tied to existing nodes. Storage status tests persist results into the fake `CephCluster.Status`.

## Dependencies and Integration Points
The tests integrate the OSD package with Kubernetes batch/core/apps APIs, `k8sutil` labels and owner refs, Rook Ceph CRDs, fake Ceph command execution, the OSD health monitor, discover daemon ConfigMaps, and deployment labels/env vars generated by `spec.go`. They also depend on Ceph command contracts for `osd df`, `osd crush class ls`, `osd dump`, `safe-to-destroy`, `ok-to-stop`, and auth deletion.

## Risks
The suite depends heavily on exact fake Ceph command argument positions, which can make refactors noisy. Several tests are integration-style and asynchronous, so timing changes in status watching can introduce flakes. Device-class behavior is nuanced: node labels, CR config, per-device config, and `AllowDeviceClassUpdate` interact differently. The CephX status aggregation intentionally reports the minimum/common safe generation across OSD deployments; changing annotations or deployment labels can silently affect cluster status.

## Test Signals
Strong signals include add/remove reconciliation success, failed job creation propagation, orphaned prepare cleanup, `OSDInfo` recovery from deployments, encrypted-label upgrade compatibility, custom CRUSH roots, storage status store-type counts, CephX status convergence, duplicate device-set validation, per-device class matching, and node-label device-class conflict detection.
