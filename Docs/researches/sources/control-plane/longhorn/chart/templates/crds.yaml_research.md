# sources/control-plane/longhorn/chart/templates/crds.yaml

Purpose: Installs the Longhorn `longhorn.io` CustomResourceDefinitions used by the manager and controllers. The header notes it is generated from `github.com/longhorn/longhorn-manager/k8s/pkg/apis` and copied into the chart, so it is not intended as a hand-authored standalone manifest. It defines the persistent Kubernetes API surface for Longhorn storage, backup, engine, node, snapshot, support, and system recovery objects.

Important APIs/types/functions: Every object is an `apiextensions.k8s.io/v1` `CustomResourceDefinition` with Helm-rendered `longhorn.labels` and `longhorn-manager: ""` labels. All CRDs are in group `longhorn.io`, scope `Namespaced`, version `v1beta2`, `served: true`, `storage: true`, and expose `status` subresources. Defined resources are `BackingImageDataSource`, `BackingImageManager`, `BackingImage`, `BackupBackingImage`, `Backup`, `BackupTarget`, `BackupVolume`, `EngineFrontend`, `EngineImage`, `Engine`, `InstanceManager`, `Node`, `Orphan`, `RecurringJob`, `Replica`, `Setting`, `ShareManager`, `Snapshot`, `SupportBundle`, `SystemBackup`, `SystemRestore`, `VolumeAttachment`, and `Volume`. Each schema includes OpenAPI `spec` and `status` fields plus `additionalPrinterColumns` for kubectl output.

Control flow: Helm applies CRDs before or with the rest of the release, making the Longhorn API types available to controllers and users. Longhorn manager then creates and reconciles namespaced CRs through Kubernetes watches and status updates. The custom resources represent desired state in `spec` and observed state in `status`: volumes and engines track attachment, frontend, replicas, backup/restore, snapshots, migration, and robustness; replicas and instance managers track per-node process state; backup resources track target, snapshot, upload, sync, progress, error, and URL fields; nodes track disks, scheduling, conditions, region/zone, and disk health; settings store configured values and applied state.

State and persistence behavior: These CRDs define durable cluster state. Kubernetes stores CR instances and status in etcd, while Longhorn controllers use them as the source of truth for storage lifecycle. `status` subresources separate controller-observed state from user spec writes. Enumerations constrain important values such as data engines `v1`/`v2`, backing image source types, backup modes, frontend types, recurring job tasks, volume access modes, data locality, replica balancing policies, snapshot integrity modes, and trim/offline rebuild flags. Some fields include immutability validation messages, for example volume backing image and encryption.

Dependencies and integration points: Depends on Kubernetes CRD v1 support and Helm label templating. It must be consistent with Longhorn manager Go API structs, generated clients/informers, RBAC in `clusterrole.yaml`, admission webhooks, UI/API clients, backup infrastructure, CSI controller behavior, snapshot integration, and upgrade/migration logic. The CRD inventory also drives RBAC resource names and informs cleanup/uninstall behavior.

Risks: Generated CRDs are large and easy to drift from controller code if the generation/copy process is skipped. Because every CRD stores `v1beta2`, schema mistakes can affect persisted production state and upgrade compatibility. CRD upgrades can be disruptive if fields, enum values, validations, or status shapes change without conversion planning. The chart labels CRDs through Helm templating, so this template cannot be applied directly with plain `kubectl apply` as the header warns. Broad schemas with nullable maps and nested status objects should be validated against server-side OpenAPI limits and Kubernetes version compatibility.

Test signals: Generation tests should diff this file against the manager API source output. `helm template` and `helm install --dry-run` should ensure all CRDs render valid YAML with labels. Cluster tests should create representative CRs for each kind and verify status subresource updates, kubectl printer columns, enum validation, and manager reconciliation. Static checks should compare the CRD resource list with `clusterrole.yaml` and generated client code.
