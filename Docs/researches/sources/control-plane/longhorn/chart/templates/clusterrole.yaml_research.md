# sources/control-plane/longhorn/chart/templates/clusterrole.yaml

Purpose: Renders cluster-scoped RBAC for Longhorn. The primary `ClusterRole` named `longhorn-role` grants the Longhorn manager broad access to Kubernetes core resources, storage APIs, snapshot APIs, Longhorn CRDs, admission webhooks, RBAC objects, leases, metrics, and discovery resources. When OpenShift support is enabled, it also renders `longhorn-ocp-privileged-role` for use of privileged and anyuid security context constraints.

Important APIs/types/functions: Kubernetes API types are `rbac.authorization.k8s.io/v1` `ClusterRole` objects. Helm helpers include `include "longhorn.labels" . | nindent 4` and the conditional `.Values.openshift.enabled`. Rule groups cover `apiextensions.k8s.io/customresourcedefinitions`, core pods/secrets/services/events/PVs/PVCs/nodes/namespaces, `apps` controllers, `batch` jobs, `policy` PDBs, `scheduling.k8s.io` priority classes, `storage.k8s.io` storage classes and CSI attachment resources, `snapshot.storage.k8s.io` snapshot resources, all listed `longhorn.io` resources and statuses, `coordination.k8s.io/leases`, `metrics.k8s.io` pods/nodes, `apiregistration.k8s.io/apiservices`, admission webhook configurations, RBAC roles/bindings and cluster roles/bindings, and `discovery.k8s.io/endpointslices`.

Control flow: Helm emits `longhorn-role` unconditionally. The Longhorn manager service account is bound to it by `clusterrolebinding.yaml`, and runtime controllers then use those permissions to install/manage CRDs, reconcile Longhorn custom resources, coordinate storage and CSI objects, inspect pods/nodes, publish events, register webhooks, and manage selected RBAC objects. If `.Values.openshift.enabled` is true, Helm appends a second ClusterRole for SCC `use` permissions; matching subjects are bound in the OpenShift branch of `clusterrolebinding.yaml`.

State and persistence behavior: The rendered ClusterRoles are persistent cluster-level RBAC resources. They do not store application state, but they authorize controllers that mutate persistent Kubernetes and Longhorn resources. RBAC changes during chart upgrade can immediately affect reconciliation, webhook lifecycle, CRD management, snapshot integration, and CSI attachment behavior.

Dependencies and integration points: Depends on `_helpers.tpl` for labels and on `values.yaml` for `openshift.enabled`. It must stay synchronized with `crds.yaml`, manager code, CSI deployment behavior, snapshot controller APIs, Kubernetes storage API versions, and OpenShift SCC requirements. The long list of `longhorn.io` resources includes volumes, engines, replicas, engine images/frontends, nodes, instance managers, share managers, backing images, backups, recurring jobs, orphans, snapshots, support bundles, system backups/restores, volume attachments, and backup backing images.

Risks: The role is intentionally broad, including wildcards on CRDs, storage resources, snapshot resources, Longhorn resources, and cluster roles/bindings. That increases blast radius if the manager service account is compromised. Missing new Longhorn CRDs or new Kubernetes resources will break reconciliation after upgrades. The OpenShift finalizer entries are conditional, so OpenShift-specific delete/finalizer flows depend on enabling the chart flag. Admission webhook create/patch/delete permissions are sensitive and should be reviewed whenever webhook names or lifecycle changes.

Test signals: `helm template` should verify both normal and OpenShift output. RBAC can be validated with `kubectl auth can-i --as system:serviceaccount:<ns>:longhorn-service-account` for manager operations and with end-to-end upgrade tests that exercise CRD creation, webhook registration, snapshot/CSI flows, and Longhorn CR status updates. Static review should compare the `longhorn.io` resource list with CRDs in `crds.yaml`.
