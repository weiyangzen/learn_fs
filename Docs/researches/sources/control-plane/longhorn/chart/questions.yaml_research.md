# sources/control-plane/longhorn/chart/questions.yaml

Purpose: Defines Rancher catalog questions for installing the Longhorn Helm chart. It is UI-facing metadata rather than a Kubernetes manifest: the file groups chart values into form controls for image selection, private registry credentials, default Longhorn settings, default StorageClass settings, ingress/HTTPRoute exposure, default backup resources, PSP/Windows/network-policy options, and related validation hints.

Important APIs/types/functions: The main schema is the Rancher `questions` list. Each item maps a `variable` to a Helm value key, sets a `type` such as `boolean`, `string`, `password`, `int`, `enum`, or `hostname`, and may define `default`, `label`, `description`, `group`, `required`, `min`, `max`, `options`, `show_if`, `show_subquestion_if`, and nested `subquestions`. Top-level `categories: [storage]` and `namespace: longhorn-system` classify the chart. Important value namespaces include `image.longhorn.*`, `image.csi.*`, `privateRegistry.*`, `defaultSettings.*`, `persistence.*`, `ingress.*`, `httproute.*`, `service.ui.*`, `defaultBackupStore.*`, `enablePSP`, `global.cattle.windowsCluster.enabled`, and `networkPolicies.*`.

Control flow: There is no executable flow. Rancher evaluates visibility and validation metadata, then writes selected answers into Helm values. `image.defaultImage`, `privateRegistry.createSecret`, `longhorn.default_setting`, `persistence.*.enable`, `ingress.enabled`, `httproute.enabled`, `service.ui.type`, and `longhorn.default_resource` gate subquestions. Once Helm values are produced, other chart templates consume them: image fields feed manager and CSI workloads, default settings feed the `longhorn-default-setting` ConfigMap, persistence fields feed the StorageClass, service and ingress fields feed UI exposure templates, and backup store fields should feed `default-resource.yaml`.

State and persistence behavior: This file persists no cluster state directly. Its answers become Helm release values and may indirectly create durable Longhorn cluster defaults, StorageClasses, secrets, ConfigMaps, routes, and services. Several settings are explicitly first-install or detached-volume sensitive, especially `longhorn.default_setting`, `longhorn.default_resource`, data-engine options, replica and node scheduling policies, storage network, taint toleration, node selector, and CPU/memory/resource knobs.

Dependencies and integration points: The file must remain aligned with `values.yaml`, `README.md`, and templates under `sources/control-plane/longhorn/chart/templates`. It also encodes Longhorn manager and CSI sidecar image names/tags, Rancher private-registry behavior, OpenShift PSP/SCC and route behavior, Kubernetes Ingress/Gateway API fields, Longhorn default-setting names, StorageClass parameters, and backup target defaults.

Risks: The largest risk is drift from real chart values. One concrete mismatch is present: the question variable `defaultBackupStore.backupstorePollInterval` does not match `values.yaml` and `templates/default-resource.yaml`, which use `defaultBackupStore.pollInterval`; users setting this question may not affect the rendered ConfigMap. Type drift is also likely because many Longhorn settings use JSON-like string defaults such as `{"v1":"3","v2":"3"}` while others use booleans or ints. Several warnings describe unsafe live changes, but Rancher questions cannot enforce operational preconditions like all volumes being detached. Image tag defaults and sidecar versions must be kept current with the release.

Test signals: Useful checks are `helm lint`, `helm template` with representative Rancher answer sets, schema/value-name diffing against `values.yaml`, and UI smoke tests for gated subquestions. Specific regression tests should assert that every `questions.yaml` variable path exists in `values.yaml` or is an intentional Rancher-only flag, and should cover the private-registry, default-setting, default-resource, ingress, HTTPRoute, StorageClass, OpenShift, and Windows branches.
