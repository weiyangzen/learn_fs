## Purpose

`init_vusb_ids.go` stores USB device match-table records that syzkaller can inject into generated virtual USB descriptors. The values are compact binary strings rather than Go structs. Each USB ID record is 17 bytes, matching `BytesPerUsbID` in `init_vusb.go`, and is later decoded into `UsbDeviceID` with little-endian `binary.Read`.

The file is generated by `tools/syz-usbgen` from kernel logs emitted after applying the USB ID extraction patch described by `docs/linux/external_fuzzing_usb.md`. The generator emits a deterministic Go map from driver name to concatenated binary records. This lets syzkaller bias generated USB descriptors toward IDs that Linux USB drivers actually match.

## Control Flow and Consumers

This chunk has no local control flow. Its behavior comes from consumers in `sys/linux/init_vusb.go`:

- `generateUsbDeviceDescriptor` calls `patchUsbDeviceID(..., usbIdsAll, true)` to patch a generic generated USB descriptor with one random ID from the full concatenated ID pool. `usbIdsAll` is generated later in this same file from every `usbIds[...]` value.
- `generateUsbPrinterDeviceDescriptor` looks up `usbIds["usblp"]` for printer-class matching. That key is outside this chunk, but this chunk uses the same per-driver storage contract.
- `generateAudioDeviceDescriptor` builds a pool from sound-driver keys such as `snd-usb-audio`; those keys are outside this chunk, but again rely on the same map shape.
- `patchUsbDeviceID` decodes one selected 17-byte record with `randUsbDeviceID`, then patches `idVendor`, `idProduct`, `bcdDevice`, device class fields, and per-interface class/protocol/number fields in the generated descriptor according to the record's match flags.

The generator-side flow in `tools/syz-usbgen/usbgen.go` is:

1. Read a syslog file.
2. Extract `USBID: <34 hex chars> (<driver>)` matches into a driver-to-ID map.
3. Sort driver names and per-driver IDs.
4. Emit the `usbIds` map and then an all-IDs concatenation variable.

## Risks

- Generated-data drift: editing this file by hand can conflict with the generator and with `usbIdsAll`, which is emitted later from sorted map keys.
- Binary layout coupling: the strings are tightly coupled to `UsbDeviceID` field order and little-endian decoding. Any struct layout or `BytesPerUsbID` change requires regenerating or migrating every record.
- Silent descriptor quality loss: malformed match flags or swapped bytes may still compile but cause syzkaller to generate descriptors that no longer bind to the intended Linux driver.
- Key-name sensitivity: driver lookups are plain map key strings. Renaming an entry without matching generator and consumer expectations removes it from targeted pools.
- Partial chunk boundary: line 3658 stops during the `mt76x2u` entry, so this chunk alone cannot validate the full map literal or the later all-ID concatenation.
- Large static initializer cost: the file is a large package-level map of binary strings. It is acceptable for generated syzkaller target data, but it increases source size and package initialization data.

## Purpose

Each `usbIds` map key is a Linux USB driver name, and each value is a concatenated binary string of fixed-width `UsbDeviceID` records. These records mirror kernel `struct usb_device_id` matching rules extracted by syz-usbgen, including vendor/product IDs, bcdDevice ranges, device class/subclass/protocol, interface class/subclass/protocol, and interface number.

## Important APIs, Types, And Fields

The chunk itself declares data inside:

The consumer schema is in `init_vusb.go`:

- `USB_DEVICE_ID_MATCH_*` constants define which fields are meaningful. The first two bytes of each record are `MatchFlags` in little-endian order.
- `patchUsbDeviceID` copies matched fields into generated USB device and interface descriptors.
- `randUsbDeviceID` chooses one record from a concatenated string and decodes it with `binary.Read(..., binary.LittleEndian, &id)`.

The visible record prefixes show common match classes. Many values begin with `\x03\x00`, meaning vendor and product matching. ## Control Flow

There is no local branching or function execution in this chunk. The runtime flow is data-driven:

1. Go initializes the `usbIds` map when package `sys/linux` is loaded.
2. Later in the same file, generated `usbIdsAll` concatenates every `usbIds["driver"]` value in sorted driver order.
3. `generateUsbDeviceDescriptor` creates or mutates a syzkaller USB descriptor argument.
4. If the descriptor does not contain `ANY`, it calls `patchUsbDeviceID(g, &arg, calls, usbIdsAll, true)` to choose a random packed record from the whole generated corpus.
5. `patchUsbDeviceID` decodes the selected 17-byte record and patches descriptor fields. With `patchNonMatching=true`, it also fills fields not explicitly guarded by the match flags.
6. Specialized paths use subsets. `generateAudioDeviceDescriptor` builds a concatenated string from audio driver names, including `snd-bcd2000`, `snd-ua101`, `snd-usb-6fire`, and `snd-usb-audio` from this range, then patches only matched fields with `patchNonMatching=false`.

The data in this chunk can therefore be reached either through the all-driver USB descriptor generator or through specialized generator paths that select named driver subsets.

## State And Persistence Behavior

The durable state is the checked-in generated Go source. Runtime state is in-memory only:

## Risks And Maintenance Notes

The highest-risk invariant is record width. `randUsbDeviceID` computes `len(ids) / BytesPerUsbID` and slices exactly 17 bytes. If a generated string is truncated, has an extra byte, or is concatenated across a bad boundary, the last partial record can be silently ignored or a selected record can decode incorrectly.

Match flags must stay aligned with `UsbDeviceID` field order and little-endian decoding. A generator/schema mismatch can patch vendor/product/class fields into the wrong descriptor positions and either miss the intended driver or accidentally bind another driver.

Large entries increase skew. Drivers with many records, such as `option`, `qmi_wwan`, `rt2800usb`, `rtl8xxxu`, `sierra`, and `snd-usb-audio`, have higher selection probability in `usbIdsAll` because selection is uniform by record, not by driver. That is useful for common hardware families but can reduce coverage of sparse drivers.

Targeted generators depend on exact driver-name strings. For example, `generateAudioDeviceDescriptor` names `snd-bcd2000`, `snd-ua101`, `snd-usb-6fire`, and `snd-usb-audio`; if generation changes a key spelling or omits a key, that specialized path silently loses those IDs.

Chunk boundaries are a review hazard. This range starts inside `mt76x2u` and ends inside `snd-usb-audio`, so byte-count or completeness analysis cannot treat the requested lines as a standalone valid Go fragment. Adjacent chunks are needed to validate those two boundary values.

Because the file is generated, fixes should target extraction inputs or `tools/syz-usbgen` rather than hand-editing individual string literals.
