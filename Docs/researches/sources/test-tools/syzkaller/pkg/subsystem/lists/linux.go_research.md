## Risks And Maintenance Notes

The largest risk is generated-data drift. The file encodes Linux tree layout, MAINTAINERS-derived lists, maintainers, and generated parent inference. If Linux paths move or subsystem ownership changes, old rules misroute reports until the file is regenerated.

Regex breadth is another major risk. Many rules include broad alternatives such as bare keywords (`meson`, `mtk`, `tdx`) or wide directory prefixes. These improve recall but can create false positives. Exclude-bearing positional literals are especially sensitive because field order is `IncludeRegexp, ExcludeRegexp`.

Parent graph correctness matters because `ReachableParents()` panics on cycles and `Extractor` removes parents when children are present. A bad parent pointer can either panic service creation/use or hide a broader subsystem unexpectedly.

The chunk boundary itself is a review hazard: the `net` subsystem is incomplete in this range, and the final `return []*Subsystem{...}` is outside the chunk. Merge/reconciliation should treat this document as a partial view of the generated function.

Regeneration can produce very large diffs because this is a monolithic generated file. Manual edits are inappropriate; fixes should go through the generator inputs or generation logic.

## Notable Matching Semantics

The list deliberately allows overlapping matches. A source path may map to a narrow subsystem and one or more broader parents because `PathMatcher.Match` collects all matching subsystem objects. Parent relationships then help downstream code collapse or enrich results depending on the consumer.

Some rules are broad text matches rather than pure path prefixes, for example `riscv`, `rockchip`, `sophgo`, `spacemit`, or `[^a-z]tegra`. These catch device-tree, driver, and symbol naming conventions but increase false-positive risk if unrelated paths contain those tokens.

Some positional `PathRule` literals use include/exclude pairs. Examples include the `rcu` rule that excludes SRCU from the broader RCU include, and the `wireless` rule that excludes many vendor subtrees from a broad wireless prefix. These exclusions depend on field order in `PathRule`; reordering fields would break generated code that does not use named fields.

The `usb` subsystem has many granular rules under one parent domain, including gadget, host-controller, storage, Type-C, serial, thunderbolt, and syzkaller USB connect pseudo-syscalls. `usb-storage` is a child that matches `drivers/usb/storage/`, so storage paths can resolve to both `usb` and `usb-storage`.

## Risks

- Generated regex drift: Linux tree movement or renamed headers can make routing stale until the list is regenerated.
- Overbroad token regexes can match unrelated paths and attach incorrect maintainers or lists.
- Underbroad anchored rules can miss new files if a subsystem adds new directories outside the generated patterns.
- Parent graph mistakes affect email fan-out and extractor parent removal logic. Cycles would panic in `ReachableParents`.
- Duplicate or omitted subsystem names in the final return list can break service construction or make a declared subsystem unreachable.
- Positional `PathRule` literals depend on `PathRule` field order. This is a structural coupling between generated list code and `entities.go`.
- `regexp.MustCompile` means a bad generated regex causes a runtime panic during matcher creation, not a recoverable error.
- `Emails()` includes parent mailing lists transitively, so an incorrect parent can over-CC broad lists such as `linux-kernel`, `netdev`, `linux-fsdevel`, or architecture lists.
