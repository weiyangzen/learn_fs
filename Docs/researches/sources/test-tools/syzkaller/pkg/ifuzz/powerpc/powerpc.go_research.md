# sources/test-tools/syzkaller/pkg/ifuzz/powerpc/powerpc.go

## Purpose

`powerpc.go` implements the syzkaller ifuzz backend for PPC64/PowerISA instruction generation and decoding. It defines the instruction model used by generated PowerPC tables, registers the architecture with the shared `iset` package, emits randomized machine code, recognizes instruction byte streams, and provides helper macros for pseudo-instruction generators that need to materialize integer values in registers or memory.

## Important APIs, Types, and Functions

Core data types are `InsnBits`, `InsnField`, `Insn`, `insnSetMap`, and `InsnSet`. `Insn` carries name, privilege and pseudo flags, primary and suffix opcode/mask data, field metadata, a back-pointer to the instruction map, and an optional pseudo generator. `InsnSet` exposes `GetInsns`, `Decode`, and `DecodeExt` to satisfy the ifuzz architecture interface. Encoding APIs are `Insn.Encode`, `encodeOpcode`, `encodeBits`, `enc`, and `encOpcode`. Registration and metadata APIs are `Register`, `Info`, `mode`, and `uint32toBytes`. Instruction-map helpers `ld64`, `ld32`, `ldgpr32`, and `sc` build common PowerPC sequences used by pseudo instructions.

## Control Flow

`Register` is called by generated instruction-table packages. It builds a name-to-instruction map, stores that map back into every instruction, appends pseudo instructions through `initPseudo`, adds all instructions to `modeInsns`, and installs the set into `iset.Arches[iset.ArchPowerPC]`. `Decode` first requires at least four bytes, reads little-endian instruction words, detects PowerISA prefixed instructions via the six-bit prefix opcode, and then compares masks/opcodes against known instructions. Prefixed decode requires eight bytes and validates both prefix and suffix words; non-prefixed decode returns four bytes on the first opcode/mask match.

Encoding starts at `Insn.Encode`. Pseudo instructions delegate to their generator. Normal instructions encode the primary word and, for prefixed opcodes, a suffix word. `encodeOpcode` starts with fixed opcode bits, optionally randomizes unknown bits when memory regions exist, fills each declared field with random values, forces register-pair fields even, and may prepend register materialization sequences for memory-related register fields. `enc` and `encOpcode` provide deterministic field-value encoding for pseudo helpers.

## State and Persistence Behavior

The backend keeps runtime state in `InsnSet.Insns`, `InsnSet.modeInsns`, `InsnSet.insnMap`, and each instruction's `insnMap` pointer. There is no filesystem persistence. Generated byte slices are transient. The global integration state is `iset.Arches`, which receives the PowerPC backend during registration. Randomness comes from the caller-provided `rand.Rand`, while memory-aware immediate/register values come from `iset.Config` and `iset.GenerateInt`.

## Dependencies and Integration Points

The file depends on `encoding/binary`, `errors`, `fmt`, `math/rand`, and `github.com/google/syzkaller/pkg/ifuzz/iset`. It integrates with generated PowerISA instruction data, with `pseudo.go` through `initPseudo` and instruction-map helper methods, and with syzkaller's architecture-agnostic ifuzz scheduling through `iset.Arches`, `iset.ModeInsns`, `iset.Config`, and `iset.Insn`. The helper methods assume base instructions such as `addis`, `ori`, `rldicr`, `stw`, and `sc` exist in the generated map.

## Risks and Edge Cases

Decode performs a linear scan over the instruction list, so ordering matters when masks overlap. Prefixed decode validates the suffix against any prefixed instruction rather than the matched prefix instruction's own suffix metadata, which could admit mismatched prefix/suffix pairs if encodings overlap. `encOpcode` accepts a field parameter but loops over `insn.Fields`, so suffix field encoding may be wrong for prefixed suffixes. Unknown-bit randomization is gated on `MemRegions`, which makes encoding behavior differ between memory-aware and plain configurations. Several helper methods index the instruction map by string and will panic if generated tables omit expected mnemonics.

## Test Signals

Strong tests should register a small instruction set and verify `Decode` length/error behavior for short, valid, invalid, and prefixed byte streams. Encoding tests should assert little-endian output, fixed mask preservation, register-pair evenness, deterministic `enc` output, and correct `ld64`/`ld32` sequences. Integration tests should ensure `Register` adds pseudo instructions, populates `modeInsns`, and publishes `iset.Arches[iset.ArchPowerPC]`.
