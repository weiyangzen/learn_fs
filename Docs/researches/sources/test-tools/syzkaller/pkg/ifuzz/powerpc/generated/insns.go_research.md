## Control Flow

Package initialization is the primary control flow:

1. Go loads package `generated`.
2. `init` invokes `powerpc.Register(insns)`.
3. `Register` creates an `InsnSet`, indexes every descriptor by mnemonic, back-links each instruction to the map, appends pseudo-instructions, adds all instructions to `modeInsns`, and installs the set for `ArchPowerPC`.
4. Later ifuzz users call `Encode`, `Decode`, `Info`, or `GetInsns` through the `iset` architecture registry.

Encoding and decoding are data-driven from this generated table. For a normal 32-bit instruction, `Insn.Encode` starts from `Opcode`, randomizes unmasked bits when memory regions are configured, encodes each named field with `encodeBits`, and returns one little-endian word. For a prefixed instruction, `isPrefixed` sees the primary opcode prefix and appends a second encoded word from the suffix descriptor. `InsnSet.Decode` mirrors this by checking `(Mask & word) == Opcode`; prefixed instructions require an 8-byte input and also verify the suffix word against `MaskSuffix`/`OpcodeSuffix`.

The generated table itself has no loops or branches beyond the registration hook. Its behavior is entirely indirect through the `powerpc` package consumers.

## State And Persistence Behavior

The persistent state is the generated instruction catalog itself. At runtime, `Register` mutates only in-memory package-level state:

- it stores every descriptor in a new `InsnSet`;
- it populates `insnMap` for mnemonic lookup and helper expansion;
- it writes the `insnMap` pointer into each generated `Insn`;
- it installs the completed set in the global `iset.Arches` registry.

There is no file I/O, database state, cache persistence, or external process state in this generated file. The generated descriptors are static Go literals. State changes only happen during package initialization and during later encode/decode calls that allocate byte slices or choose random field values.

Memory-aware encoding has one indirect state effect worth noting: when `iset.Config.MemRegions` is non-empty, `encodeOpcode` may prepend register materialization sequences for fields named `RA`, `RB`, or `RS` by calling `insn.insnMap.ld64`. That means table entries with those field names are not just bit-layout data; they can cause extra setup instructions to be emitted by the generic encoder.

## Risks And Maintenance Notes

The largest risk is descriptor accuracy. A wrong `Opcode`, `Mask`, field name, or bit range can silently generate invalid instructions, reject valid instructions in `Decode`, or encode operands into the wrong positions. Generated table changes should be reviewed against the generator and ISA source rather than patched locally.

Field names are semantic, not cosmetic. Pair-register names ending in `p` for known forms (`Ap`, `FRAp`, `FRBp`, `FRTp`, `FRSp`) are forced even by the encoder. Memory setup behavior is triggered by exact `RA`, `RB`, and `RS` names. Renaming fields would therefore change generated code behavior even if bit positions stayed identical.

Prefixed instructions have two independent masks and field sets. A primary/suffix mismatch can make `Encode` emit an instruction that `Decode` rejects, or can make `Decode` accept the wrong suffix for a prefix. This chunk has many prefixed entries around lines 533-650, so regression tests should include two-word encodings.

The `Priv` flag affects instruction metadata exposed through `Info` and instruction filtering/classification outside this generated file. Missing `Priv: true` on system/TLB/MSR/SLB/message instructions can make privileged instructions available in contexts that expect user-safe fuzzing.

The `//go:build !codeanalysis` tag means static-analysis-only builds may not see this package data. Any code that assumes the generated package always registers PowerPC instructions must account for builds where the file is excluded.

The generated file is very large. Broad formatting changes, generator churn, or source-ISA PDF parsing differences can produce huge diffs with subtle behavioral changes. Stable counts and round-trip tests are useful signals when regenerating.
