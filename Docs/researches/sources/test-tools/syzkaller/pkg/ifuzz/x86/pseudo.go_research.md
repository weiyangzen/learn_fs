## sources/test-tools/syzkaller/pkg/ifuzz/x86/pseudo.go

Purpose: adds x86 pseudo-instructions to ifuzz so generated byte streams can exercise privileged and multi-instruction architectural behavior that cannot be represented as a single generated opcode row. The file defines the `pseudo` instruction list and private `generator` byte-emission helpers.

Important APIs/types/functions: `pseudo` contains `*Insn` values named `PSEUDO_RDMSR`, `PSEUDO_WRMSR`, PCI port read/write, generic port read/write, control-register/EFER toggles, debug-register breakpoints, segment loads, far jump/call, LTR/LLDT, LGDT/LIDT, and KVM hypercalls. `makeGen`, `byte`, `imm16/32/64`, `operand16`, `operand32`, `addr32`, register move helpers, `readCR/writeCR`, `readDR/writeDR`, `in/out` helpers, `randSelector`, and `pciAddrPort` build concrete instruction bytes. Static data includes control register bit lists, `eferMSR`, I/O ports, and a large MSR corpus shared conceptually with `sys/kvm.txt`.

Control flow: each pseudo instruction creates a `generator`, chooses operands using `math/rand` and `iset.GenerateInt`, emits setup instructions, then emits the privileged instruction. The helper methods encode mode-dependent prefixes and panic on impossible register/mode/size combinations, relying on pseudo instruction `Mode` masks and call sites to keep inputs valid.

State and persistence: no persisted state. The only mutable state is the per-generation `generator.text` buffer. Package-level slices/maps are immutable lookup tables after init.

Dependencies and integration: integrated by `x86.go` through `Register`, which appends `pseudo` to generated x86 instructions. It depends on `pkg/ifuzz/iset` for modes and random integer generation. The emitted instructions target CPU, KVM, PCI config, and legacy I/O behavior, so they are privileged and intentionally high-risk for VM fuzzing.

Risks: byte encodings are hand-authored and easy to desynchronize from architectural rules. Mode-prefix mistakes can create undecodable or semantically different instructions. Many pseudo ops mutate CPU control state; bad values may reboot or wedge test VMs. The large MSR list is duplicated knowledge and can drift.

Test signals: covered indirectly by x86 decode/generation tests; `x86_test.go` includes decode regressions involving pseudo-generated privileged sequences. No direct table-driven tests assert each pseudo generator.
