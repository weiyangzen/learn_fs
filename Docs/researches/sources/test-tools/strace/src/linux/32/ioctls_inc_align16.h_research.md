# sources/test-tools/strace/src/linux/32/ioctls_inc_align16.h

## Purpose

`sources/test-tools/strace/src/linux/32/ioctls_inc_align16.h` is a generated strace ioctl-definition input table for 32-bit Linux personalities whose ioctl size field follows 16-bit alignment rules. In the current tree it contains 3,383 initializer entries generated by `maint/ioctls_gen.sh` from Linux UAPI include trees. Each entry records:

- the Linux header where an ioctl macro was discovered,
- the ioctl symbol name,
- the `_IOC_*` direction bits or literal `0` for legacy commands,
- the command type/number field as a resolved integer,
- the encoded ioctl argument size for this ABI variant.

The file is not a standalone C header with declarations or guards. It is intended to be included inside a `struct ioctlent`-like initializer array during strace build-time generation of `ioctlent*.h`.

## Important APIs, Types, And Data Shape

The direct records have the shape consumed by `src/ioctlsort.c`:

```c
struct ioctlent {
	const char *info;
	const char *name;
	unsigned int dir;
	unsigned int type_nr;
	unsigned int size;
};
```

Representative entries include terminal ioctls from `asm-generic/ioctls.h`, DRM ioctls from `drm/*.h`, block filesystem ioctls from `linux/fs.h`, network socket ioctls from `linux/sockios.h`, audio ioctls from `sound/*.h`, and device-specific command sets for v4l2, btrfs, vfio, vhost, binder, kfd, gpib, USB, Xen, and others. A quick table scan shows 276 distinct source headers and this direction distribution:

- `_IOC_READ|_IOC_WRITE`: 932 entries
- `_IOC_WRITE`: 913 entries
- `_IOC_READ`: 579 entries
- `_IOC_NONE`: 558 entries
- literal `0`: 401 legacy entries

The largest direct providers in this file are `drm/drm.h`, `linux/soundcard.h`, `sound/asound.h`, `linux/videodev2.h`, `linux/sockios.h`, `asm-generic/ioctls.h`, `drm/i915_drm.h`, `linux/btrfs.h`, `linux/android/binder.h`, `linux/vhost.h`, `linux/wireless.h`, and `linux/fs.h`.

The runtime ioctl lookup table uses the smaller public strace type declared in `src/defs.h`:

```c
typedef struct ioctlent {
	const char *symbol;
	unsigned int code;
} struct_ioctlent;
```

This generated align16 include is therefore an intermediate source for build-time code computation, not the final runtime lookup table itself.

## Control Flow And Build Integration

`src/linux/32/ioctls_inc.h` selects this file only when `M68K` is defined:

```c
#if defined M68K
# include "../32/ioctls_inc_align16.h"
#elif defined X86_64 || defined X32 \
 || SIZEOF_STRUCT_I64_I32 < SIZEOF_LONG_LONG * 2
# include "../32/ioctls_inc_align32.h"
#else
# include "../32/ioctls_inc_align64.h"
#endif
```

Most 32-bit architectures include `../32/ioctls_inc.h` from their `linux/<arch>/ioctls_inc0.h`, so this file becomes active through that wrapper for the ABI family that needs 16-bit size alignment.

The build path is:

1. `maint/ioctls_gen.sh` crawls Linux include directories and writes generated `ioctls_inc*.h` and architecture-specific `ioctls_arch*.h` initializer lists.
2. `src/Makefile.am` builds `ioctls_all%.h` by concatenating the selected common `ioctls_inc%.h` and the architecture `ioctls_arch%.h`.
3. `ioctlsort%.o` compiles `src/ioctlsort.c` with `-DIOCTLSORT_INC="<ioctls_all%.h>"`.
4. `ioctlsort` expands each five-field initializer into an ioctl numeric command with:

```c
type_nr | (size << _IOC_SIZESHIFT) | (dir << _IOC_DIRSHIFT)
```

5. `ioctlsort` de-duplicates by symbol name, sorts by numeric code and name, emits `ioctlent*.h`, and `src/syscall.c` includes those files into `const struct_ioctlent ioctlent0[]`, `ioctlent1[]`, or `ioctlent2[]`.
6. At runtime, `src/ioctl.c` uses `bsearch` over the sorted `ioctlent` array to translate an ioctl command number into symbolic names for `ioctl(2)` decoding.

## State And Persistence Behavior

This header has no mutable state, no functions, no storage duration of its own, no I/O, and no persistence side effects. Its persistence role is source-control and build artifact provenance: checked-in generated data is used to regenerate deterministic `ioctlent*.h` tables during the strace build.

The lasting runtime state derived from it is the compiled `ioctlent` array selected by strace personality. In multi-personality builds, `src/syscall.c` switches the global `ioctlent` pointer and `nioctlents` count when the traced task personality changes. The entries from this file are therefore indirectly persistent for the lifetime of the strace process as part of read-only program data.

## Dependencies

Primary dependencies are:

- Linux UAPI header content used by `maint/ioctls_gen.sh`.
- The ABI-specific `_IOC_*` encoding constants from `ioctl_iocdef.h`, generated via `src/ioctl_iocdef.c` so build-host compilation still uses the target-relevant ioctl layout.
- `src/linux/32/ioctls_inc.h`, which chooses this align16 variant.
- Per-architecture `ioctls_arch*.h` files, concatenated with this common include before sorting.
- `src/ioctlsort.c`, which defines the five-field input structure, encodes final numeric command values, removes duplicate names, and emits the two-field runtime table.
- `src/ioctl.c`, which assumes final `ioctlent*.h` output is sorted by code for binary search.

The file also depends on generated-data conventions: every line must remain a valid C initializer fragment for `struct ioctlent ioctls[]`, including trailing commas and resolvable `_IOC_*` tokens.

## Integration Points

This file integrates with the strace tree at three levels:

- Build system: listed in `src/Makefile.am` `EXTRA_DIST`, selected through `linux/32/ioctls_inc.h`, concatenated into `ioctls_all%.h`, and compiled into `ioctlsort%`.
- Runtime decode: contributes symbol-to-code mappings that `SYS_FUNC(ioctl)` uses to print readable ioctl operation names instead of only raw hex values.
- Maintenance tooling: tied to `doc/HACKING-scripts`, which documents that generated ioctl tables may require manual merge work because regenerating from one kernel version can drop older or newer definitions that strace still wants to recognize.

## Risks And Edge Cases

The main risk is ABI drift. The same ioctl symbol can encode to different numeric values when structure size or alignment changes, so using the wrong align variant would make strace print wrong symbols or miss symbols on affected 32-bit personalities. The align16 file is especially sensitive because it exists solely to capture one layout family.

Generated data can also age relative to Linux headers. New kernel ioctls may be missing, removed or renamed ioctls may linger intentionally for compatibility, and regenerated output can accidentally drop entries if it is copied without the manual merge step described in the strace hacking notes.

Duplicate numeric command values are normal. `ioctlsort` keeps distinct symbols when their codes match unless the later name is only a prefixed variant of the previous one, and `src/ioctl.c` walks backward from the binary-search hit to the first matching code so all aliases can be considered. Bad sort order or malformed generated rows would break this assumption.

Legacy literal-`0` direction entries do not carry encoded `_IOC` direction or size. They are valid for old command definitions but provide less semantic information for diagnostics and can collide with newer encoded commands.

Because this file is a raw initializer fragment, syntax breakage is easy: an omitted comma, unknown `_IOC_*` token, or accidental include guard/text outside initializer syntax would fail the `ioctlsort` build rather than a normal compile unit.

## Test Signals

Useful validation signals for changes touching this file are:

- Build target generation succeeds for the affected architecture/personality, especially the `ioctlsort%`, `ioctlent%.h`, and `ioctl_redefs%.h` rules.
- The generated `ioctlent*.h` remains sorted by numeric command and contains expected aliases for known overlapping commands.
- `ioctl` decoder tests continue to pass, including broad tests under `sources/test-tools/strace/tests/ioctl*.c` and `ioctl.test`.
- Architecture coverage includes the align16 selector path, primarily the `M68K` branch of `linux/32/ioctls_inc.h`.
- Spot checks of known symbols from this table, such as terminal, DRM, filesystem, socket, sound, and Xen commands, print the expected symbolic ioctl names under strace verbosity modes.
