# sources/test-tools/strace/src/linux/32/ioctls_inc_align32.h

## Purpose

`sources/test-tools/strace/src/linux/32/ioctls_inc_align32.h` is a generated strace build-time ioctl table fragment for 32-bit Linux personalities whose ioctl structure-size encoding follows 32-bit alignment rules. It is generated by `ioctls_gen.sh` from definitions found under a Linux `$linux/include` tree and records common Linux UAPI ioctl symbols after resolving the command number and ABI-specific argument size.

The file is not a standalone header with declarations, include guards, or callable code. It is a raw C initializer fragment included inside `src/ioctlsort.c`'s temporary `struct ioctlent ioctls[]` table. In the current source it has one generator comment and 3,384 initializer rows spanning 276 UAPI header names.

Each row captures:

- the discovered UAPI header path, such as `asm-generic/ioctls.h`, `drm/drm.h`, `linux/fs.h`, or `sound/asound.h`;
- the ioctl macro name, such as `TCGETS2`, `DRM_IOCTL_MODE_GETRESOURCES`, `BINDER_WRITE_READ`, or `VIDIOC_QUERYCAP`;
- direction bits as `_IOC_READ`, `_IOC_WRITE`, `_IOC_READ|_IOC_WRITE`, `_IOC_NONE`, or literal `0` for legacy commands;
- the resolved type/number portion of the ioctl code;
- the ABI-specific encoded argument size for the align32 layout.

## Important APIs, Types, And Data Shape

The direct consumer shape is the private build-time type in `src/ioctlsort.c`:

```c
struct ioctlent {
	const char *info;
	const char *name;
	unsigned int dir;
	unsigned int type_nr;
	unsigned int size;
};
```

Rows in this file initialize those fields in order:

```c
{ "header/path.h", "IOCTL_SYMBOL", _IOC_DIRECTION, 0xTYPE_NR, 0xSIZE },
```

`info` is provenance metadata used for deterministic duplicate-name ordering; it is not emitted to the final runtime table. `name` is the symbol strace may print for an ioctl command. `dir`, `type_nr`, and `size` are combined by `ioctlsort.c` into the final numeric command code with:

```c
type_nr | (size << _IOC_SIZESHIFT) | (dir << _IOC_DIRSHIFT)
```

The final runtime type is smaller and is declared in `src/defs.h`:

```c
typedef struct ioctlent {
	const char *symbol;
	unsigned int code;
} struct_ioctlent;
```

The current align32 table contains this direction distribution:

- `_IOC_READ|_IOC_WRITE`: 932 entries
- `_IOC_WRITE`: 913 entries
- `_IOC_READ`: 580 entries
- `_IOC_NONE`: 558 entries
- literal `0`: 401 legacy entries

2,442 rows carry non-zero encoded sizes. The largest direct header contributors are `drm/drm.h`, `linux/soundcard.h`, `sound/asound.h`, `linux/videodev2.h`, `asm-generic/ioctls.h`, `linux/sockios.h`, `drm/i915_drm.h`, `linux/btrfs.h`, `linux/android/binder.h`, `linux/vhost.h`, `linux/wireless.h`, and `linux/fs.h`.

## Control Flow And Build Integration

`src/linux/32/ioctls_inc.h` selects this align32 fragment for 32-bit ioctl layouts when:

```c
defined X86_64 || defined X32 || SIZEOF_STRUCT_I64_I32 < SIZEOF_LONG_LONG * 2
```

The surrounding 32-bit selector uses three generated variants:

- `ioctls_inc_align16.h` for `M68K`;
- `ioctls_inc_align32.h` for the align32 branch;
- `ioctls_inc_align64.h` for the remaining 32-bit layouts with larger alignment.

The build flow is:

1. Linux UAPI headers are scanned by the ioctl generation tooling to produce `ioctls_inc_align*.h` fragments.
2. `src/Makefile.am` discovers `$(OS)/$(ARCH)/ioctls_inc*.h` and maps them to generated `ioctlent*.h` targets.
3. The chosen common include and any architecture-specific ioctl fragments are compiled into an `ioctlsort%` helper through `ioctls_all%.h` or `IOCTLSORT_INC`.
4. `ioctlsort.c` sorts first by symbol and header provenance, drops duplicate symbol names after preserving the preferred definition, computes the final numeric ioctl code, sorts by code and name, and emits two-field `ioctlent*.h` rows.
5. `src/syscall.c` includes `ioctlent0.h`, `ioctlent1.h`, and `ioctlent2.h` into `const struct_ioctlent` arrays.
6. `src/ioctl.c` uses `bsearch` over the selected sorted `ioctlent` array and walks adjacent equal-code aliases so `SYS_FUNC(ioctl)` can print symbolic ioctl operation names.

There is no runtime control flow inside this source file. Its only control-flow effect is through C preprocessor inclusion and build-time generation.

## State And Persistence Behavior

This file has no mutable state, functions, static storage, I/O, locks, or persistence side effects. It persists as checked-in generated source data.

State derived from it appears later in the compiled strace binary. `src/syscall.c` owns read-only `ioctlent*` arrays and, in multi-personality builds, updates the global `ioctlent` pointer and `nioctlents` count when switching traced task personality. The align32 rows therefore become part of long-lived process data only after build-time sorting and compilation.

## Dependencies

Key dependencies are:

- Linux UAPI include content used by `ioctls_gen.sh`.
- ABI-specific ioctl encoding constants from `ioctl_iocdef.h`, generated via preprocessing of `src/ioctl_iocdef.c`.
- The selector wrapper `src/linux/32/ioctls_inc.h`.
- Architecture-specific `ioctls_arch*.h` fragments that can be concatenated with this common table.
- `src/ioctlsort.c`, which defines the five-field input contract and emits the final two-field lookup table.
- `src/Makefile.am` rules for `ioctlsort%`, `ioctlent%.h`, and `ioctl_redefs%.h`.
- `src/syscall.c` and `src/ioctl.c`, which rely on sorted `ioctlent` output for runtime decoding.

The source also depends on strict initializer syntax: every non-comment line must remain a valid element for the build-time `struct ioctlent` array.

## Integration Points

The primary integration point is strace ioctl name decoding. When a traced process calls `ioctl(fd, op, arg)`, `src/ioctl.c` first gives specialized decoders a chance to interpret known ioctl families, then falls back to the generated `ioctlent` table to print names for the numeric command. Entries from this align32 file determine which symbols are available for affected 32-bit personalities.

The file also integrates with maintenance workflows. Regenerating the ioctl tables from a newer or different kernel include tree can add, remove, resize, or rename rows. Because strace wants stable decoding across many kernel versions, generated changes need review rather than blind replacement.

The table contains many naturally overlapping code spaces, including terminal/sound overlaps, DRM driver families, filesystem ioctls, socket and wireless legacy commands, v4l2/media commands, USB commands, Xen commands, and architecture-sensitive time or pointer-size variants such as `*_TIME32`, `*_32`, and `*_64` suffixed symbols.

## Risks And Edge Cases

The main risk is ABI mismatch. The same source-level ioctl macro can encode a different numeric command when structure size or alignment changes. Selecting `ioctls_inc_align32.h` for an ABI that needs align16 or align64 would make strace miss valid names or print the wrong symbolic alias.

Generated-table drift is another risk. A kernel header update can introduce new ioctls, alter structure sizes, or expose definitions that collide with existing names. Conversely, regenerating from a narrower header set can accidentally drop old commands that strace still should recognize.

Duplicate numeric codes are expected. `ioctlsort.c` keeps multiple symbols for the same final code when they are not removed by duplicate-name or prefix filtering, and `ioctl.c` walks adjacent equal-code entries after binary search. If sorting or code computation changes, alias printing can silently regress.

Literal `0` direction entries are valid legacy ioctl definitions, but they do not encode `_IOC` direction or size. They are more collision-prone and give less semantic information than modern `_IOC_*` rows.

Because the file is a generated initializer fragment, small textual mistakes are high impact: a missing comma, unknown `_IOC_*` token, wrong field order, or stray declaration would break `ioctlsort` compilation or generate incorrect runtime lookup data.

## Test Signals

Useful validation signals after touching this file are:

- the strace build regenerates the relevant `ioctlsort%` helper and `ioctlent%.h` without syntax or preprocessing errors;
- generated `ioctlent*.h` remains sorted by numeric command code, as required by `src/ioctl.c` binary search;
- known align32-sensitive entries still encode to expected values, especially `*_TIME32`, `*_32`, and structure-size-heavy DRM, v4l2, ALSA, btrfs, vfio, vhost, and USB commands;
- ioctl decoder tests under the strace test suite continue to print expected symbolic names and aliases;
- multi-personality tests exercise the personality that selects the align32 table through `src/linux/32/ioctls_inc.h`;
- spot checks of overlapping command ranges, especially `0x5401` through `0x5408`, still show appropriate alternative names where strace expects overlap handling.
