# sources/test-tools/kdevops/workflows/pynfs/baseline/6.3.0-rc3+-v4.0.json

## Purpose
Checked-in pynfs NFSv4.0 baseline result for kernel `6.3.0-rc3+`. It is a stable historical comparison fixture for the kdevops pynfs workflow, result display, visualization, and regression triage against later NFSv4.0 server test runs.

## Important APIs, Types, and Data Shape
The file is a JSON object with aggregate keys `errors`, `failures`, `name`, `skipped`, `testcase`, `tests`, `time`, and `timestamp`. `name` is `all`; `tests` is the numeric testcase count `679`; `errors` is `0`; `failures` is `1`; `skipped` is `98`; `time` is the numeric suite runtime `1782.7480309009552`; and `timestamp` is `2023-03-20 16:13:01.857565`.

`testcase` is an array of 679 JUnit-like testcase objects. Each testcase has `classname`, `code`, `name`, and string-valued `time`; skipped cases carry `skipped: 1`; failing cases carry a `failure` object with traceback text in `err` and a concise `message`. The only failure is `st_lock` code `LOCK24`, `testOpenUpgradeLock`, with message `OP_LOCK should return NFS4_OK, instead got NFS4ERR_BAD_SEQID`.

## Control Flow
The file is data, not executable code. Consumers should parse the top-level suite object, iterate `testcase`, derive pass/skip/failure counts from item fields, and compare case codes/messages/timing with current result JSON. For this baseline, the derived counts are 679 total cases, 98 skipped, 1 failed, and 580 passed. Coverage spans 42 pynfs v4.0 server test classes, including access, ACL, close, commit, compound, create, delegation, fslocations, getattr, getfh, gss, link, lock, lookup, open, read, readdir, remove, rename, replay, renew, setattr, setclientid, verify, and write suites.

The local workflow integration explains the expected result shape: `workflows/pynfs/scripts/run_pynfs.sh` runs `./testserver.py --json=... --maketree --uid=0 --gid=0 ... all` from the NFSv4.0 pynfs tree, while `workflows/pynfs/Makefile` exposes `pynfs-show-results` for JSON display and `pynfs-visualize` for HTML generation from result directories.

## State and Persistence Behavior
This is persisted fixture state in the source tree. It should remain stable unless maintainers intentionally refresh the `6.3.0-rc3+` baseline. Per-test `time` values are strings while top-level `time` is numeric, so tools should convert testcase times before summing or sorting. The failure traceback embeds historical absolute paths under `/data/pynfs/nfs4.0/...`; those paths document the original test environment and are not repository-local dependencies.

Skipped state is also part of the baseline contract. Entire optional or environment-dependent areas are skipped, notably all 32 `st_delegation` cases, all 13 `st_fslocations` cases, all 9 `st_reboot` cases, all 8 `st_gss` cases, plus smaller skip groups in lock, read, write, spoof, setattr, secinfo, rename, lookupp, ACL, and other classes.

## Dependencies and Integration Points
The fixture depends on the pynfs JSON schema emitted by `testserver.py`, not on in-repository code execution. It integrates with kdevops workflow collection under `workflows/pynfs/results`, with checked-in baseline files under `workflows/pynfs/baseline`, and with report/visualization tooling that expects one JSON suite object per protocol version.

The NFSv4.0 baseline is complementary to the v4.1 baseline in the same directory, but it is not directly comparable case-for-case. The runner uses different pynfs directories and flags for the two protocol versions: v4.0 uses `all`, while v4.1 uses `all deleg xattr`.

## Risks
The known failure in `LOCK24` may reflect a real NFSv4.0 lock sequencing issue or an environment-specific accepted failure. Regression tooling should report the exact failure code/message delta rather than treating any single failure as equivalent. The reduced skipped count compared with older baselines can indicate improved environment coverage, but skip changes in optional suites require context about export capabilities, special-file support, GSS, delegation, fslocations, and reboot tests.

Runtime comparisons are sensitive to timeout-heavy tests. The largest recorded durations are `WRT15` `testSizes` at about 309.84 seconds, `CLOSE8` and `CLOSE9` around 182 seconds each, `RENEW3` around 182 seconds, replay wait tests around 180 seconds, lock timeout tests around 135 to 137 seconds, `RDDR8b` around 88.72 seconds, and `CID5` around 54.31 seconds. Small policy or lease-time changes can dominate the total runtime without indicating broad regressions.

## Test Signals
Validation should assert aggregate consistency: 679 `testcase` entries, 98 entries with `skipped: 1`, 1 entry with `failure`, 580 entries with neither skip nor failure, 0 top-level errors, and a top-level failure count matching the derived failure count. Regression reports should highlight the known failing `st_lock/LOCK24` message, skipped-count changes by `classname`, missing or newly added case codes, and large timing movement in the timeout-heavy close, renew, replay, lock, write-size, readdir, and setclientid tests.
