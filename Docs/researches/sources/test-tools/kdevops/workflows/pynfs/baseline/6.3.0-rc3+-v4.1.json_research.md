# sources/test-tools/kdevops/workflows/pynfs/baseline/6.3.0-rc3+-v4.1.json

## Purpose
Checked-in pynfs NFSv4.1 baseline result for kernel `6.3.0-rc3+`. It provides the expected historical result set for kdevops NFSv4.1 comparison, visualization, and regression analysis.

## Important APIs, Types, and Data Shape
The file is a JSON object with aggregate keys `errors`, `failures`, `name`, `skipped`, `testcase`, `tests`, `time`, and `timestamp`. `name` is `all`; `tests` is the numeric testcase count `262`; `errors` and `failures` are both `0`; `skipped` is `91`; `time` is the numeric suite runtime `546.1761648654938`; and `timestamp` is `2023-03-20 16:22:10.506308`.

`testcase` is an array of 262 JUnit-like testcase objects. Each entry has `classname`, `code`, `name`, and string-valued `time`; skipped cases add `skipped: 1`. This particular baseline has no `failure` objects, so all non-skipped cases are passes. The derived counts are 262 total, 91 skipped, 0 failed, and 171 passed.

## Control Flow
The file has no executable control flow. Consumers should parse the suite object, iterate `testcase`, normalize string times to numbers for timing analysis, and compare class/code/name/status tuples against current v4.1 result JSON. The 25 classes cover v4.1-specific and shared protocol areas: courtesy locks, xattrs, flex files, sparse/block/pNFS-related cases, current stateid, reboot, putfh, rename, lookupp, open, trunking, sequence, secinfo, reclaim complete, destroy client/session, create session, exchange ID, copy, compound, and delegation.

The local kdevops runner invokes the v4.1 pynfs tree with `./testserver.py --json=... --maketree --uid=0 --gid=0 ... all deleg xattr`, so this baseline intentionally has a different suite mix from the v4.0 file. The Makefile targets `pynfs-show-results` and `pynfs-visualize` consume JSON results from the workflow result directories using the same suite shape.

## State and Persistence Behavior
This is durable baseline data checked into the source tree. It captures a single historical NFSv4.1 run and should not mutate except during an intentional baseline refresh. Per-test `time` values are strings while aggregate `time` is numeric; parsers should handle that mixed typing explicitly.

Skipped status captures unavailable or disabled feature coverage. The largest skipped groups are 27 `st_flex` cases, 11 `st_xattr` cases, 11 `st_reboot` cases, 10 `st_delegation` cases, 8 `st_getdevicelist` cases, 6 `st_destroy_session` cases, 4 `st_block` cases, and 3 `st_sparse` cases, with single or paired skips in copy, compound, courtesy, create-session, current-stateid, exchange-id, lookupp, and rename.

## Dependencies and Integration Points
The fixture depends on the pynfs v4.1 JSON schema emitted by `testserver.py` and on the kdevops collection layout. It integrates with baseline comparisons beside the v4.0 JSON for the same kernel release and with visualization scripts that treat each protocol version as a separate result suite.

Only nine class names overlap with the v4.0 baseline: `st_compound`, `st_delegation`, `st_lookupp`, `st_open`, `st_putfh`, `st_reboot`, `st_rename`, `st_secinfo`, and `st_verify`. Many v4.1-only classes are session, trunking, exchange-id, reclaim, xattr, flex, and pNFS oriented. Consumers should compare this file against other v4.1 baselines, not against v4.0 totals.

## Risks
Because this baseline has zero failures, any new failure is a strong regression signal, but skip-to-pass or pass-to-skip transitions still need environment interpretation. Optional feature families such as flex files, xattrs, pNFS getdevicelist/layout operations, block layouts, sparse allocation, delegation, and reboot/reclaim can legitimately depend on server configuration.

Runtime is dominated by long lease/courtesy/session tests. The largest cases are `COUR3`, `COUR6`, `COUR5`, `EID9`, and `COUR2`, each around 100 to 101 seconds, plus `CSESS29` around 32.8 seconds. Total runtime changes should be decomposed by testcase before concluding that the whole suite became slower or faster.

## Test Signals
Validation should assert 262 testcase entries, 91 skipped entries, 0 failure entries, 171 passing entries, 0 top-level errors, and consistency between top-level aggregate counts and derived testcase counts. Regression tooling should flag any introduced `failure` object, skipped-count changes by class, disappearance of core session or exchange-id cases, and timing movement in courtesy-lock, lease-period, and create-session stress tests.
