# sources/test-tools/kdevops/playbooks/roles/bootlinux/templates/config-linux-5.10.y

Purpose: this file is a generated Linux/x86 kernel `.config` snapshot for Linux 5.10.105, kept as a bootlinux role template in kdevops. It is used as a monolithic kernel configuration when `target_linux_ref` resolves to `linux-5.10.y`, giving test nodes a repeatable x86_64 kernel feature set instead of relying on a host distro config or fragment merge. The header records GCC 11.2.0, binutils ld 2.38, `CONFIG_KERNEL_XZ=y`, and `CONFIG_BUILD_SALT="4.19.0-1-amd64"`, so the file appears to have been generated from a Debian-derived baseline and then stored as static input for automation.

Important APIs/types/functions: there are no source-level functions or classes. The important interface is the Linux Kconfig `.config` grammar: enabled built-ins as `CONFIG_FOO=y`, modules as `CONFIG_FOO=m`, disabled options as `# CONFIG_FOO is not set`, strings, and numeric constants. In this file that produces 1,441 built-in options, 184 modules, 2,623 explicit disabled options, 25 string assignments, and 75 numeric assignments. The consuming APIs are Ansible tasks in the bootlinux role: `target_linux_config` defaults to `config-{{ target_linux_ref }}`, `tasks/config.yml` searches `role_path/templates/config-kdevops`, `role_path/templates/{{ target_linux_config }}`, and the newest `config-next-*`, then stores the selected basename as `linux_config`. Build tasks use `ansible.builtin.template` to copy `linux_config` into the Linux source tree as `.config`, then run `make olddefconfig` or `yes "" | make oldconfig` before building.

Configuration profile: the kernel targets x86_64 SMP virtualization-heavy testing. Core architectural features include `CONFIG_X86_64=y`, `CONFIG_SMP=y`, `CONFIG_NR_CPUS=512`, NUMA and memory hotplug support, EFI boot support, kexec/crash dump, KASLR, ACPI, PCI hotplug, and paravirtual guest support. It enables both Xen guest/domain functionality (`CONFIG_XEN=y`, `CONFIG_XEN_DOM0=y`, PV/PVHVM/PVH support) and KVM guest support (`CONFIG_KVM_GUEST=y`) while leaving the in-kernel KVM host hypervisor disabled (`# CONFIG_KVM is not set`). This is a guest/test-kernel profile, not a virtualization host profile.

Subsystem coverage: storage and filesystem support are tuned for kdevops and filesystem/block testing. Block, SCSI, NVMe, virtio-blk, loop, device-mapper, dm-thin, dm-delay, dm-flakey, dm-log-writes, and SCSI debug are present, mostly as modules where appropriate. Filesystems include ext4, XFS, Btrfs, FAT/VFAT/exFAT/NTFS modules, overlayfs built in, and 9P filesystem support as a module. Network support is broad enough for IPv4/IPv6, bridges, tc infrastructure, BPF JIT, and 9P transports, but many container/network appliance features are deliberately absent, including nftables, conntrack, XDP sockets, TUN, veth, VXLAN, NFS, CIFS, and FUSE.

Debug and test surface: the file enables a large diagnostics surface useful for kernel development: `CONFIG_DEBUG_INFO=y`, `CONFIG_DEBUG_FS=y`, dynamic debug, SysRq, stack traces, lockup/hung-task detectors, scheduler stats, ftrace/function graph tracing, kprobes/uprobes events, BPF events, block I/O tracing, fault injection, `FAIL_MAKE_REQUEST`, and `MEMTEST`. It does not enable KUnit or KCOV. That means runtime and integration failures are easier to observe through debugfs/ftrace/blktrace/fault injection, but unit-test and coverage workflows are not available from this config alone.

Control flow: in a normal bootlinux run, `tasks/main.yml` first includes `tasks/config.yml` unless a packaged kernel workflow is selected. The config task constructs a search list with `config-kdevops` first and `config-{{ target_linux_ref }}` second; for `target_linux_ref=linux-5.10.y`, this file is the version-specific fallback. The selected file name becomes `linux_config`. Builder, target-node, and 9P build paths then copy that template to `.config` in the chosen Linux tree. Non-9P builder builds call `make olddefconfig`; target-node and 9P paths use `yes "" | make oldconfig` for monolithic configs. Only after Kconfig reconciliation does the role build the kernel, optional CXL test module, packages, and install artifacts.

State and persistence behavior: this template is static repository state, but its contents are persisted into several downstream artifacts. The immediate persisted state is `.config` in `target_linux_dir_path` or `bootlinux_9p_host_path`; Kconfig may then rewrite it during `olddefconfig` or `oldconfig` if upstream 5.10 Kconfig defaults or dependencies differ from the stored snapshot. The build persists module signing material under `certs/`, kernel packages under `bootlinux_artifacts_dir`, and a `kernel.release` file. Runtime state exposed by this configuration includes debugfs, securityfs, sysfs/procfs, AppArmor/SELinux/TOMOYO/Yama LSM availability, pstore, tracing buffers, and many module-loadable test drivers.

Dependencies: the file assumes an x86 Linux 5.10 Kconfig tree and a toolchain capable of the recorded GCC/binutils feature set. It depends on the bootlinux role variables `target_linux_ref`, `target_linux_config`, `linux_config`, `target_linux_dir_path`, `bootlinux_9p_host_path`, `bootlinux_use_config_fragments`, compiler selection variables, and artifact paths. It also depends on Linux Kconfig preserving symbol names and dependencies close enough that `olddefconfig` does not silently drop required test capabilities. Runtime dependencies include initramfs support, module loading, virtio/Xen/9P transports for virtualized deployments, and userspace able to mount or use debugfs/securityfs/tracing when tests require them.

Integration points: the direct integration point is `sources/test-tools/kdevops/playbooks/roles/bootlinux/templates/`, where sibling `config-*` files provide other kernel-version baselines. The role integrates this template with `playbooks/bootlinux.yml`, `playbooks/build_linux.yml`, `roles/bootlinux/tasks/config.yml`, `roles/bootlinux/tasks/build/builder.yml`, `roles/bootlinux/tasks/build/targets.yml`, and `roles/bootlinux/tasks/build/9p.yml`. It also intersects with optional config-fragment mode, but fragment mode bypasses this monolithic template. Test integrations are indirect: fstests, blktests, CXL testing, filesystem debugging, block fault injection, and 9P-hosted builds rely on the resulting kernel exposing drivers and debug facilities selected here.

Risks: the largest risk is drift between this generated 5.10.105 snapshot and the actual `linux-5.10.y` tree checked out by automation. New, removed, or dependency-changed symbols may be accepted by `olddefconfig` with warnings or silently changed, causing test environments to differ from the intended baseline. A second risk is boot viability: several common root/device drivers are modules, SATA AHCI and USB storage are disabled, and virtio/Xen support is split between built-in and modular options, so initramfs content and deployment transport matter. Security and debug tradeoffs are also explicit: module signatures are enabled but not forced, debugfs is unrestricted, SELinux/AppArmor/TOMOYO are built, and extensive tracing/fault injection can alter performance and attack surface. Finally, `CONFIG_BUILD_SALT`, compiler metadata, and old generated defaults reduce reproducibility unless the bootlinux reproducible-build variables override the environment consistently.

Test signals: the first signal is Ansible selecting this file as `linux_config` when `target_linux_ref=linux-5.10.y` and no higher-priority `config-kdevops` override is present. The next signal is a clean `make olddefconfig` or `yes "" | make oldconfig` with no unexpected Kconfig warnings. Build success for `make all`, package targets, and optional `M=tools/testing/cxl` confirms compiler/toolchain compatibility. Runtime smoke signals should include booting the built kernel in the target virtual environment, loading expected modules such as `virtio_blk`, `virtio_net`, `9p`, `9pnet_virtio`, `ext4`, `xfs`, `btrfs`, `scsi_debug`, and `dm_flakey`, mounting debugfs/tracing when needed, and verifying that fstests or blktests can see the expected block and filesystem capabilities. Negative signals include oldconfig prompts that change defaults unexpectedly, missing root/storage/network modules in initramfs, inability to use 9P transport, and tests skipped because KUnit, KCOV, FUSE, NFS, TUN, nftables, or KVM-host features are unavailable.
