# sources/test-tools/kdevops/playbooks/roles/bootlinux/templates/config-xfs-5.4.y

Purpose: this file is a generated Linux/x86 kernel `.config` snapshot for Linux 5.4.225, stored as a kdevops `bootlinux` role template. It provides a reproducible, monolithic kernel configuration for the 5.4.y XFS test profile rather than deriving behavior from the host distribution or from many smaller fragments. The header records GCC 8.5.0 from Red Hat Enterprise Linux 8 era tooling, and the body shows a virtualization-heavy x86_64 kernel with a narrow filesystem focus around XFS.

Important APIs/types/functions: this is configuration data, not executable code, so it has no functions, classes, or in-source types. The primary interface is the Linux Kconfig `.config` language: `CONFIG_FOO=y` for built-in features, `CONFIG_FOO=m` for modules, `# CONFIG_FOO is not set` for disabled symbols, plus numeric and string assignments. This file contains 1,675 built-in symbols, 102 module symbols, 2,586 explicit disabled symbols, 25 string assignments, and 74 numeric assignments. The operational API is the kernel build system consuming the file as `.config`, then reconciling it with the selected Linux 5.4.y Kconfig tree through `oldconfig` or `olddefconfig`.

Configuration profile: the target is x86_64 SMP testing with extensive CPU, memory, ACPI, EFI, PCI, NUMA, hotplug, cgroup, namespace, tracing, and security surfaces enabled. It uses `CONFIG_X86_64=y`, `CONFIG_SMP=y`, `CONFIG_NR_CPUS=8192`, 5-level page tables, NUMA balancing, memory hotplug/remove, kexec/crash dump, KASLR, EFI stub support, and a 1000 Hz timer. Virtualization support is broad: Xen PV/PVHVM/PVH and dom0 symbols are enabled, KVM guest support is enabled, KVM host support is modular for AMD only (`CONFIG_KVM=m`, `CONFIG_KVM_AMD=m`, `# CONFIG_KVM_INTEL is not set`), and virtio core exists with modular PCI transport.

Filesystem and storage behavior: XFS is the central filesystem target. `CONFIG_XFS_FS=m` builds XFS as a module, while `CONFIG_XFS_QUOTA=y`, `CONFIG_XFS_POSIX_ACL=y`, `CONFIG_XFS_RT=y`, and `CONFIG_XFS_DEBUG=y` enable quota, ACL, realtime-device, and debug code paths. `CONFIG_XFS_ONLINE_SCRUB` and `CONFIG_XFS_ASSERT_FATAL` are disabled, so this profile exposes debug assertions and checks without enabling online scrub tests or panic-on-assert behavior. Ext2 and ext4 are modules, Btrfs and F2FS are disabled, overlayfs is built in, FUSE is disabled, NFS client support is modular but all NFS protocol versions are disabled, and pseudo filesystems such as procfs, sysfs, tmpfs, configfs, hugetlbfs, efivarfs, and pstore are enabled.

Block and device-mapper coverage: the block layer includes blk-mq, cgroup writeback, zoned block-device framework, writeback throttling, debugfs block diagnostics, and multiple I/O schedulers. Loop devices, SCSI disks, virtio SCSI, NVMe core/block/fabrics/TCP, ATA PIIX, and many iSCSI adapters are modules. Device mapper is modular with debug support plus dm-snapshot, dm-thin, dm-delay, dm-dust, dm-flakey, dm-log-writes, and dm-integrity, which are useful for filesystem failure and replay tests. Important absences are also part of the profile: `CONFIG_VIRTIO_BLK`, `CONFIG_XEN_BLKDEV_FRONTEND`, `CONFIG_SCSI_DEBUG`, `CONFIG_BLK_DEV_NULL_BLK`, `CONFIG_SATA_AHCI`, and `CONFIG_USB_STORAGE` are disabled.

Control flow: during a kdevops bootlinux run, role logic selects a template based on the configured kernel reference or explicit `target_linux_config`. Once selected, this file is copied into the Linux source tree as `.config`. The kernel build then invokes Kconfig reconciliation, so the effective final configuration is this file plus any dependency repairs or default answers from the checked-out Linux 5.4.y tree. After reconciliation, normal kernel build, module build, package, install, or target-node deployment steps consume the resulting `.config`.

State and persistence behavior: the repository persists this file as static input. The build persists a derived `.config` in the Linux build tree, and Kconfig may rewrite that derived file when symbol dependencies differ from the generated 5.4.225 snapshot. Module signing is enabled with generated signing material under `certs/signing_key.pem`; signatures are generated for modules, but `CONFIG_MODULE_SIG_FORCE` is off. Runtime state from this profile is substantial: debugfs, tracing buffers, sysfs/procfs, pstore, SELinux/IMA/EVM policy state, module state, device-mapper tables, XFS module parameters, and fault-injection debugfs controls all become observable or mutable surfaces in test machines.

Dependencies: this template assumes an x86 Linux 5.4 Kconfig tree and a toolchain compatible with the recorded GCC feature probes. It depends on the bootlinux role copying it to the correct Linux source directory and on userspace/initramfs carrying required modules for storage, network, and filesystem access because many relevant drivers are modular. Runtime filesystem testing depends on `xfs.ko`, quota tooling, device-mapper modules, loop or NVMe/SCSI storage availability, debugfs/tracing mounts, and an environment that does not require disabled features such as FUSE, Btrfs, F2FS, SATA AHCI, USB mass storage, virtio-blk, or SCSI debug.

Integration points: the direct integration point is the `sources/test-tools/kdevops/playbooks/roles/bootlinux/templates/` directory, where sibling `config-*` files represent other kernel baselines. The downstream integration is the bootlinux Ansible role and any kdevops workflow that asks for the XFS 5.4.y config. Test integrations are mostly indirect: xfstests can exercise XFS quota, ACL, realtime, debug, DAX, overlayfs interactions, dm-flakey/dm-log-writes failure paths, fault injection, block tracing, ftrace, kprobes, uprobes, BPF events, and panic/hung-task behavior exposed by the resulting kernel.

Risks: the main risk is config drift. Although the header says Linux 5.4.225, automation may build a different 5.4.y revision, and `oldconfig` can silently change defaults or drop stale symbols. Boot risk is also high if the deployment expects built-in root-device drivers: common virtual and physical storage paths such as virtio-blk, Xen block frontend, SATA AHCI, USB storage, and SCSI debug are disabled, while loop, NVMe, SCSI disk, virtio SCSI, and XFS are modules. The profile intentionally enlarges the debug and security surface with debugfs, tracing, KGDB/KDB, fault injection, SELinux, IMA, EVM, module signing, and BPF JIT; this is useful for tests but can affect performance, boot policy, module loading, and reproducibility. XFS online scrub tests will be skipped or fail because online scrub is not enabled.

Test signals: selection succeeds when kdevops resolves this exact template for the 5.4.y XFS kernel profile and copies it to `.config`. Build-time signals include clean `oldconfig`/`olddefconfig` output, successful module signing, and successful compilation of `xfs.ko`, device-mapper modules, NVMe/SCSI modules, and tracing/debug infrastructure. Runtime smoke signals include booting the kernel, loading `xfs`, `loop`, `dm_flakey`, `dm_log_writes`, `dm_delay`, `dm_thin_pool`, `nvme`, `virtio_scsi`, or the actual storage driver required by the test host, mounting XFS with quota/ACL scenarios, mounting debugfs/tracing, and observing fault-injection controls. Negative signals include unexpected Kconfig prompts, missing initramfs modules, inability to mount XFS because it is modular, xfstests skips for online scrub/FUSE/Btrfs/SCSI debug, or boot failure on environments that depend on disabled virtio-blk, Xen block, AHCI, or USB storage support.
