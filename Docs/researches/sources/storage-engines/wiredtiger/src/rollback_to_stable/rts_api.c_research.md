# sources/storage-engines/wiredtiger/src/rollback_to_stable/rts_api.c

Purpose: implements the rollback-to-stable API entry layer and connection initialization/reconfiguration hooks. It validates that the operation is safe to run, establishes the rollback timestamp from the stable timestamp, updates global transaction visibility state, opens an internal no-logging session, coordinates schema/checkpoint locks, optionally performs a forced checkpoint after rollback, and exposes single-object rollback for schema-worker style callers.

Important APIs and functions: `__wt_rollback_to_stable_init` installs function pointers into `conn->rts` and reads `rollback_to_stable.threads`. `__wt_rollback_to_stable_reconfig` updates the configured worker count. `__rollback_to_stable` parses per-call `dryrun` and `threads`, opens an internal session, sets RTS runtime config, records runtime stats, runs `__rollback_to_stable_int` under checkpoint and schema locks, logs a summary, finalizes RTS state, and closes the internal session. `__rollback_to_stable_int` performs active-session checks, updates oldest/pinned transaction state, chooses the rollback timestamp, invokes `__wti_rts_btree_apply_all`, updates the global durable timestamp when not dry-run, asserts pinned/stable timestamps did not move in diagnostic builds, and checkpoints when required. `__rollback_to_stable_one` rolls back one btree URI and sets the schema-worker skip flag for file objects. `__rts_check` and `__rts_check_callback` reject active transactions or open file cursors.

Control flow: API calls enter through the function pointer initialized on the connection. Runtime configuration is parsed defensively because internal callers can pass `NULL` config arrays. The operation then switches to an internal session to avoid handle caching and user-session concurrency surprises. `__rollback_to_stable_int` marks the session as RTS, checks for active user work, forces oldest transaction state forward with strict/wait flags, snapshots stable and pinned timestamps, logs the initial state, maps an unset stable timestamp to `WT_TS_MAX`, runs the all-btree RTS orchestrator, optionally rolls back the global durable timestamp to stable, and forces a checkpoint unless disabled, dry-run, or in-memory.

State and persistence behavior: mutates `conn->rts` runtime fields (`dryrun`, `threads_num`, progress), connection statistics (`txn_rollback_to_stable_running`), session flags (`WT_SESSION_ROLLBACK_TO_STABLE`, quiet corrupt file during single-btree apply), and global durable timestamp state. The rollback itself changes btree and history-store content through `__wti_rts_btree_apply_all`; a post-RTS forced checkpoint makes on-disk state match in-memory rollback results. Dry-run suppresses durable timestamp update and the final checkpoint while still exercising the traversal/reporting path configured by lower layers.

Dependencies and integration points: depends on session-array walking and `api_lock` for safety checks, checkpoint/schema locks for global exclusion, transaction global timestamp helpers, metadata search for single-object rollback, btree apply orchestration in `rts.c`, connection configuration parsing, verbose recovery logging, stats, internal session lifecycle, and the public WiredTiger checkpoint API.

Risks and sharp edges: `__rts_check` is best-effort; new cursors or transactions can appear after it returns unless higher-level locking and usage discipline prevent it. The function assumes callers hold checkpoint and schema locks in `__rollback_to_stable_int` and asserts that. Stable and pinned timestamps are read once and expected not to change; diagnostic assertions catch violations but production relies on external exclusion. Error handling must close the internal session and reset RTS runtime fields, but `txn_rollback_to_stable_running` is set back to zero only after the locked call returns, so panic/error paths should be reviewed carefully. Single-object rollback frees metadata config only on the normal path shown here; any added early return after metadata search must preserve cleanup.

Test signals: API tests should verify rejection with active transactions and active file cursors, behavior with stable timestamp unset, dry-run behavior, worker thread configuration parsing, forced-checkpoint suppression via `no_ckpt`/dry-run/in-memory modes, single-URI skip semantics, durable timestamp rollback to stable, reconfiguration of `rollback_to_stable.threads`, and diagnostic timestamp-stability assertions.
