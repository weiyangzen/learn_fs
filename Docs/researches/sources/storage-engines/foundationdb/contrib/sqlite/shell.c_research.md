# sources/storage-engines/foundationdb/contrib/sqlite/shell.c

Purpose: This file implements the standalone `sqlite` command-line shell for the bundled SQLite library. It handles interactive and batch input, command history, SQL statement accumulation and execution, output formatting, dot commands such as `.dump`, `.schema`, `.import`, `.backup`, and `.restore`, SQLite status reporting, optional extension loading, logging, timers, VFS selection, and process-level signal interruption.

Important APIs and types: Runtime state is carried by `struct callback_data`, which stores the open `sqlite3 *db`, output stream, display mode, separator, null rendering, column widths, destination table for insert mode, current statement, log stream, database filename, VFS name, echo/stats flags, and previous `.explain` state. Output modes are `MODE_Line`, `MODE_Column`, `MODE_List`, `MODE_Semi`, `MODE_Html`, `MODE_Insert`, `MODE_Tcl`, `MODE_Csv`, and `MODE_Explain`. Key functions include `main_init`, `main`, `open_db`, `process_sqliterc`, `process_input`, `do_meta_command`, `shell_exec`, `shell_callback`, `dump_callback`, `run_schema_dump_query`, `run_table_dump_query`, `display_stats`, `local_getline`, `one_input_line`, `set_table_name`, `appendText`, `output_quoted_string`, `output_c_string`, `output_html_string`, `output_csv`, `find_home_dir`, and the SIGINT `interrupt_handler`.

Control flow: `main` initializes callback state, configures SQLite logging and single-thread mode, installs the SIGINT handler, performs an early argument scan for database/init/VFS/heap settings, opens an existing database lazily, processes `~/.sqliterc` or `-init`, applies command-line display options on a second pass, then either executes one command or enters `process_input`. `process_input` reads lines, dispatches leading-dot meta commands only when no SQL is buffered, accumulates SQL until semicolon or recognized `go`/`/` terminators, checks completeness with `sqlite3_complete`, opens the database if needed, times execution when enabled, and passes SQL to `shell_exec`. `shell_exec` prepares one statement at a time, echoes SQL if requested, steps rows, constructs column/value/type arrays for `shell_callback`, prints stats, finalizes, and advances to leftover SQL. Dot commands are parsed in-place by `do_meta_command` and handled through a long prefix-matching dispatch chain.

State and persistence behavior: Persistent effects mostly occur through SQLite APIs invoked by SQL or dot commands. `.backup` and `.restore` use `sqlite3_backup_init`, repeated `sqlite3_backup_step(100)`, and `sqlite3_backup_finish` to copy database pages between files, with restore retrying short busy periods. `.dump` emits a transactional SQL script, toggles writable schema for virtual tables, queries `sqlite_master`, prints table contents as `INSERT` statements, and disables foreign key enforcement for replay. `.import` opens an input file, starts a transaction, splits lines by the configured separator, binds fields into an `INSERT`, and commits or rolls back on format/error conditions. Runtime state includes global `db` for interrupt handling, `seenInterrupt`, `bail_on_error`, `stdin_is_interactive`, prompts, output/log file handles, command history path, and per-session display settings.

Dependencies and integration points: The shell integrates with `sqlite3.h`, the SQLite C API, readline/editline when available, platform timing APIs (`getrusage` or `GetProcessTimes`), signal handling, home-directory discovery, stdio file I/O, optional loadable extensions, optional I/O tracing, optional VFS tracing, and SQLite test controls. The `shellstatic` SQL function is registered to safely pass shell pattern strings into `.dump`, `.schema`, `.tables`, and `.indices` queries without formatting them directly into SQL. The shell is a consumer of the SQLite library in this subtree, so it indirectly exercises pager, b-tree, parser, VDBE, backup, virtual table, status, and VFS layers.

Risks: Several command parsers mutate argument buffers in place, so quoted/backslash parsing bugs can affect subsequent dispatch. `.import` is separator-based rather than a full CSV parser and does not handle quoted separators or multiline fields. Some fixed buffers (`separator`, `nullvalue`, prompts, column arrays of size 100, `azArg[50]`) impose silent truncation or command limits. Error handling is uneven in places: backup/restore loops step fixed page chunks without progress callbacks, `.dump` has corruption fallback behavior that can emit reordered data, and dynamically built SQL requires careful quoting. `run_schema_dump_query` allocates `len + 100` but calls `sqlite3_snprintf(sizeof(zQ2), ...)`, which uses pointer size rather than allocation size and is a likely truncation bug. The `.log` branch accepts `nArg >= 1` but immediately reads `azArg[1]`, so a bare `.log` can dereference an uninitialized argument. The `.testctrl` prefix checks include suspicious comparisons such as `strncmp(..., "bitvec_test", 6) == 3`, which likely makes some options unreachable. The shell configures `SQLITE_CONFIG_SINGLETHREAD`, so embedding assumptions differ from multithreaded clients.

Test signals: High-value tests include batch and interactive-style input completion, dot-command prefix matching, `.bail` behavior, Ctrl-C interruption against a long query, every output mode including BLOB and NULL rendering, `.mode insert` identifier quoting, `.dump` and restore replay for tables/indexes/triggers/views/virtual tables, `.schema`, `.tables`, and `.indices` pattern filtering through `shellstatic`, `.import` commit and rollback on column-count mismatch, `.backup` and `.restore` page-copy behavior under busy and normal conditions, `.output` and `.log` file handling, `.stats` and `.timer` output under supported platforms, `-init` and `.sqliterc` precedence, command-line option parsing, extension loading gates, and sanitizer/fuzzer coverage for meta-command tokenization and SQL accumulation.
