# sources/storage-engines/foundationdb/contrib/pkg_tester/test_fdb_pkgs.py

Purpose: implements pytest-based package validation for FoundationDB Linux packages by installing built `.deb` and `.rpm` artifacts into disposable Docker images and running functional, packaging, backup/restore, client-build, ownership, and executable-stack checks.

Important APIs/types/functions: `run(args)` streams subprocess output and asserts success. `Image` wraps a Docker image ID with `dispose()`. `Container` wraps Docker container lifecycle (`docker run`, `exec`, `cp`, `commit`, `rm -f`) and supports optional systemd-style init arguments. `ubuntu_image_with_fdb_helper(versioned)` and `centos_image_with_fdb_helper(versioned)` locate packages under `$BUILDDIR/packages`, install prerequisites and FDB packages, then commit reusable images. Pytest fixtures expose unversioned/versioned Ubuntu and CentOS images and parametrized `linux_container` values. Tests include `test_db_available`, `test_client_app`, `test_write`, `test_execstack_permissions_libfdb_c`, `test_etc_owner`, and `test_backup_restore`.

Control flow: session fixtures build base images once per package type/platform, yielding `None` if no matching artifacts exist. Each test invocation receives a fresh container derived from the committed image; Ubuntu containers manually start `/etc/init.d/foundationdb`, while CentOS uses `initd=True`. Test bodies execute commands inside containers, compare selected command output to syrupy-style snapshots, and dispose containers/images in `finally` blocks.

State and persistence: the test creates Docker containers and intermediate committed images, writes temporary files inside containers, and uses `/tmp/fdb_backup` for backup/restore. Cleanup removes containers and committed images, but package installation state persists in the committed image for the duration of the test session. It requires external state in `$BUILDDIR/packages` and a working Docker daemon.

Dependencies and integration: depends on pytest, snapshot fixture support, Docker, Ubuntu and `centos:7` images, package manager network access, FoundationDB package artifacts, `fdbcli`, `fdbbackup`, `fdbrestore`, `execstack`, `ldconfig`, `gcc`, `pkg-config`, `cmake`, and the installed FoundationDB C client package config/CMake config. It integrates with FoundationDB build outputs rather than source code directly.

Risks: `run()` reads line-by-line while the process is alive and asserts after the loop; unusual buffering or large output could delay visibility. Docker image/container cleanup is best-effort after successful object creation but failed Docker commands before assignment can leave external resources. Versioned fixture checks in `linux_container` test `ubuntu_image_with_fdb is None` and `centos_image_with_fdb is None` instead of their versioned counterparts, which can skip or mis-handle versioned-only package sets. CentOS 7 and package-manager network dependencies are aging and can make tests flaky. The tests run privileged-ish system services in containers and mount `/sys/fs/cgroup:ro`, so host Docker configuration matters. Snapshot assertions are sensitive to CLI text changes.

Test signals: the file is itself a test suite. Passing signals include all four parametrized container modes either run or skip only when their package type is absent, `fdbcli get/set` succeeds, the sample C client compiles with both pkg-config and CMake, `execstack` output matches the expected non-executable stack snapshot, `/etc/foundationdb` ownership matches the package contract, and backup/restore round-trips key `x`.
