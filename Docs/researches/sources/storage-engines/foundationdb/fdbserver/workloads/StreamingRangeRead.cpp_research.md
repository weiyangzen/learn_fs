# sources/storage-engines/foundationdb/fdbserver/workloads/StreamingRangeRead.cpp

## Purpose
`StreamingRangeReadWorkload` compares FoundationDB's range streaming API with repeated snapshot `getRange()` calls over the same keyspace. It is a correctness workload for `Transaction::getRangeStream()` ordering and completeness.

## Important APIs, Types, and Functions
The file defines free actors `streamUsingGetRange()` and `convertStream()`, plus `StreamingRangeReadWorkload : KVWorkload`. It uses `PromiseStream<RangeResult>`, `PromiseStream<KeyValue>`, `RangeResult::more`, `nextBeginKeySelector()`, `Transaction::getRange()`, `Transaction::getRangeStream()`, `GetRangeLimits`, and `bulkSetup()`.

## Control Flow
`setup()` bulk-loads random values for `nodeCount` normal keys. `start()` runs `streamingClient()` under `timeout()` for `testDuration`. The client starts at `next`, creates two raw streams, converts both to per-key streams, and compares values one by one: one side is generated by repeated `getRange()` with a byte limit, the other by `getRangeStream()`. At end-of-stream it resets `next` to the beginning; otherwise it advances to `keyAfter()` each matched key. Errors call `tr.onError()` and the loop is rate-limited by a short delay.

## State and Persistence Behavior
Database state is the bulk-loaded normal keyspace inherited from `KVWorkload`; this source does not write after setup. Client state is transient stream futures and the `next` key used to resume across passes through the range.

## Dependencies and Integration Points
It integrates with `KVWorkload` key generation, bulk setup, Native API streaming range reads, Flow promise streams, and tester factories. It also exercises snapshot reads by using `Snapshot::True` in the comparison implementation.

## Risks and Edge Cases
The comparison can be sensitive to concurrent writers in the same keyspace because it reuses one transaction and compares streaming outputs within that transaction. `RangeStreamMismatch` asserts false, ending the simulation. There are no performance metrics, so it is primarily pass/fail. The helper propagates non-cancellation errors through streams, which is useful but can make the first error surface in either stream consumer.

## Test Signals
The principal signal is absence of `RangeStreamMismatch` and assertions during the timeout window. `check()` cancels the client future by assigning `Void()` and returns true.
