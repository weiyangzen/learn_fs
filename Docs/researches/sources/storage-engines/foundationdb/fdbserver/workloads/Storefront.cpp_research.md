# sources/storage-engines/foundationdb/fdbserver/workloads/Storefront.cpp

## Purpose
`StorefrontWorkload` models a simple transactional order system with item inventory counters and order records. It stresses concurrent read-modify-write transactions, serialization of order payloads, retry handling, and post-run durability checks for orders generated by the workload.

## Important APIs, Types, and Functions
The workload derives from `TestWorkload` and is registered as `Storefront`. It uses `bulkSetup()` with the workload functor `operator()`, `Transaction`, `BinaryWriter`, `PerfIntCounter`, and `PerfDoubleCounter`. Internal helpers include `itemKey()`, `orderKey()`, `itemValue()`, `valueToInt()`, `itemUpdater()`, `orderingClient()`, `orderChecker()`, and `inventoryCheck()`.

## Control Flow
`setup()` initializes `/items/%016d` keys with value `0`. `start()` launches `actorCount` ordering clients at a Poisson rate derived from `transactionsPerSecond`. Each client chooses a unique order ID, checks whether the order key already exists to tolerate commit-unknown replays, selects random item quantities, runs `itemUpdater()` futures to read and increment item counts inside the transaction, serializes the ordered item list, commits, and stores the order map in process memory. `check()` detects failed clients, clears the future list, and runs `inventoryCheck()`, which batches local order IDs through `orderChecker()` transactions.

## State and Persistence Behavior
Database state lives under `/items/` and `/orders/`. The in-memory `orders` map is the oracle for committed order records; it is not persistent across client restarts. Item counters are modified transactionally, but the final checker only verifies the orders table against in-memory records. A file comment and `FIXME` note state that inventory totals are not yet reconciled against orders.

## Dependencies and Integration Points
The workload integrates with FoundationDB tester options, bulk setup helpers, Native API transactions, Flow counters, and binary serialization using the current protocol version. It uses deterministic random IDs and item selection for reproducible simulation behavior.

## Risks and Edge Cases
`orders` is updated only after successful commit, so commit-unknown cases where the order was committed but the client did not record it can be counted as spurious commit failures and skipped. `itemUpdater()` asserts if a setup item is missing. `getMetrics()` divides by `transactions.getValue()` for average latency; if no transactions complete, that metric can be invalid. The checker can miss inventory counter corruption because order-to-inventory reconciliation is not implemented.

## Test Signals
Metrics include transactions, retries, spurious commit failures, and average latency. Error traces include `StorefrontItemMissing`, `OrderingClient`, and `TestFailure` reasons for client errors, missing orders, and order content mismatches. The return value of `inventoryCheck()` is the final correctness signal.
