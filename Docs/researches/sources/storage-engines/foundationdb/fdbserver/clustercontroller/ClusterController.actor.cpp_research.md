# sources/storage-engines/foundationdb/fdbserver/clustercontroller/ClusterController.actor.cpp

## Purpose
`ClusterController.actor.cpp` implements FoundationDB's cluster-controller role: leader election entry point, worker registry, database recovery supervisor, role recruitment coordinator, status server, DBInfo broadcaster, health monitor, and several system-keyspace watchers. It is the control-plane actor that publishes `ServerDBInfo`/`ClientDBInfo`, recruits or replaces the master, storage workers, transaction-system roles, data distributor, ratekeeper, consistency scan, and log routers, and reacts to failures, process-class changes, region health, and operator requests.

The file sits between coordinator leadership and the rest of `fdbserver`. Once elected, the controller owns a `ClusterControllerData` instance and an actor collection; all long-running monitors feed into that shared state and into `AsyncVar` publications used by workers and clients.

## Important APIs, Types, And Functions
`ClusterControllerData` is the central mutable state holder. The constructor seeds an initial `ServerDBInfo`, opens a lock-aware internal database connection, records controller identity/locality, initializes health-monitor inputs, and installs metrics such as client count and request counters. Methods used here include worker selection/recruitment helpers, DBInfo setters, degraded-server analysis, failover predicates, and health update processing defined in the companion headers/implementation.

Recovery supervision is centered on `clusterWatchDatabase()`. It repeatedly recruits a new master with `recruitNewMaster()`, builds fresh `ServerDBInfo` and `ClusterRecoveryData`, starts `clusterRecoveryCore()`, watches master failure or forced recovery, drains recovery child actors on exit, and retries normal recovery errors. `clusterRegisterMaster()` accepts `RegisterMasterRequest` updates from the active master and publishes recovery state, log system config, resolvers, client proxies, cluster configuration, and exclusion state.

Worker registry paths include `registerWorker()`, `workerAvailabilityWatch()`, `clusterRecruitStorage()`, `checkOutstandingStorageRequests()`, `checkOutstandingRecruitmentRequests()`, and `checkOutstandingRemoteRecruitmentRequests()`. Worker registration validates cluster ID, resolves process class and priority info, records `WorkerInfo`, tracks DBInfo update endpoints, starts per-worker failure watching, and handles registering singletons.

Singleton and role supervision is handled by `startDataDistributor()`/`monitorDataDistributor()`, `startRatekeeper()`/`monitorRatekeeper()`, and `startConsistencyScan()`/`monitorConsistencyScan()`. Shared helpers such as `findNewProcessForSingleton()`, `findBestFitnessForSingleton()`, `isHealthySingleton()`, `haltRegisteringOrCurrentSingleton()`, and `checkBetterSingletons()` choose better placements, avoid unwanted colocation, account for exclusions, and halt stale or conflicting singleton instances.

Log-router replacement is implemented by `monitorAndRecruitLogRouters()`, `monitorLogRouters()`, `recruitFailedLogRouters()`, and the generic `monitorAndRecruitWorkerSet()`. After full recovery, the controller monitors remote/satellite log routers and, when enabled by knobs, recruits replacements in parallel on suitable workers, updates the live `LogSystem`, and triggers registration propagation.

Client and status APIs include `clusterOpenDatabase()`, `clusterGetServerInfo()`, `statusServer()`, `handleForcedRecoveries()`, `handleTriggerAuditStorage()`, `triggerAuditStorage()`, `cancelAuditStorage()`, and `handleGetEncryptionAtRestMode()`. These serve open-database and status requests, forward audit requests to the data distributor, support forced recovery/failover behavior, and answer legacy encryption-at-rest mode requests.

Persistent metadata watchers include `timeKeeperSetVersion()`/`timeKeeper()`, `monitorProcessClasses()`, `monitorServerInfoConfig()`, `monitorStorageMetadata()`, `monitorGlobalConfig()`, and `updateClusterId()`. They read and write system keys for timestamp-to-version mapping, process classes, latency-band config, storage metadata, global configuration history, and cluster ID publication.

Leadership and top-level orchestration are in `clusterControllerCore()`, `replaceInterface()`, and the two overloads of `clusterController()`. The core actor starts all background monitors, serves cluster-controller interfaces, broadcasts coordination pings, exits on actor-collection failure or leadership loss, and lets the outer loop reconnect/restart when coordinators change.

## Control Flow
The outer `clusterController(connRecord, ...)` loop constructs `ServerCoordinators` and calls the coordinator-based overload. That overload initializes a fresh `ClusterControllerFullInterface`, attempts leadership via `tryBecomeLeader()`, waits until it appears in `currentCC`, and then enters `clusterControllerCore()`. If pending messages arrive before election, `replaceInterface()` forces a new interface to avoid stale endpoints.

`clusterControllerCore()` creates `ClusterControllerData`, starts an actor collection, and submits the major control loops: database recovery, process metadata watchers, status serving, timekeeper, global config propagation, region-change handling, role monitors, cluster-health monitor, DBInfo updater, cluster ID update, audit/forced-recovery handlers, optional worker-health/failover monitors, and optional log-router rerecruitment. Its main `choose` loop handles request streams for opening databases, storage recruitment, worker registration, worker enumeration, DBInfo fetches, worker-health reports, pings, coordination pings, actor errors, and leader failure.

Recovery proceeds as a repeated master lifetime. `clusterWatchDatabase()` recruits a master, publishes new `ServerDBInfo`, constructs `ClusterRecoveryData`, starts `clusterRecoveryCore()`, and waits for either recovery completion, master failure, forced failure, backup-worker completion notices, DBInfo changes, or child-actor failure. Normal transaction-system failures become recovery retries; controller restart/coordinator changes propagate out.

Worker availability is event driven. Registration inserts or refreshes `id_worker`, starts `workerAvailabilityWatch()`, updates health-monitor inputs, and queues DBInfo broadcast. The watcher removes failed workers, replies to outstanding registration long-polls, clears master process identity if needed, erases address-to-locality entries used by intra-DC latency filtering, and triggers recruitment checks when storage availability returns.

Outstanding requests are not busy-polled directly. `checkOutstandingRequests()` schedules delayed check actors, gates local requests on both recent recruitment backoff and `goodRecruitmentTime`, then retries transaction-role, storage, singleton placement, stalled recovery, and better-master checks. Remote recruitment has a separate `goodRemoteRecruitmentTime` gate.

Health control flow aggregates worker reports through `workerHealthMonitor()`. It waits for initial recruitment stability, computes degradation info, removes recovered excluded servers, logs degraded/disconnected sets, and either triggers master failure for recovery, suggests recovery, triggers/suggests failover, or checks pending recruitment when a server recovers. `updateRemoteDCHealth()`, `updateDatacenterVersionDifference()`, and `monitorRatekeeperTpsLimit()` provide additional safety gates for multi-region failover.

## State And Persistence Behavior
The main in-memory state is `ClusterControllerData`: maps of process ID to `WorkerInfo`, process classes, address locality, pending recruitment/storage requests, worker-health complaints, excluded degraded servers, DBInfo endpoint queues, cluster-health inputs, desired/changing/changed datacenter IDs, singleton recruitment IDs, and counters. Most state is process-local and rebuilt when a new cluster controller is elected.

Published cluster state lives in `AsyncVar<ServerDBInfo>` and `AsyncVar<ClientDBInfo>`. Every meaningful mutation generates a new random ID and often increments `infoGeneration`; `dbInfoUpdater()` serializes `ServerDBInfo` and broadcasts it to registered workers, with retry of endpoints that did not update. `clusterOpenDatabase()` long-polls `ClientDBInfo` for clients and records recent client status by endpoint.

Durable state is accessed through lock-aware, system-key transactions. `timeKeeper()` writes `timeKeeperVersionKey` and a bounded `timeKeeperPrefixRange` timestamp-to-version map. `monitorProcessClasses()` performs an old-key upgrade, watches `processClassChangeKey`, and reflects process-class records into workers. `monitorServerInfoConfig()` watches `latencyBandConfigKey`. `monitorStorageMetadata()` reads server list and metadata ranges and watches `serverMetadataChangeKey`. `monitorGlobalConfig()` reads versionstamped global-config history and republishes it through DBInfo. `updateClusterId()` reads or initializes `clusterIdKey` and publishes it to both server and client info.

Recovery state itself is mostly owned by `ClusterRecoveryData` and `clusterRecoveryCore()`, but this file controls lifetime, registration propagation, and forced restarts. Log-router rerecruitment mutates the in-memory `LogSystem` configuration and triggers recovery registration rather than directly writing durable state.

## Dependencies And Integration Points
The file depends heavily on Flow actors (`ACTOR`, `Future`, `choose`, `PromiseStream`, `actorCollection`), RPC request streams and failure monitoring, and FoundationDB system-key transaction APIs. It includes client and server interfaces for `WorkerInterface`, `MasterInterface`, `DataDistributorInterface`, `RatekeeperInterface`, `BackupInterface`, `LogSystem`, `ServerDBInfo`, `ClusterRecoveryData`, `CoordinatedState`, and status generation.

Integration points include coordinator leader election (`tryBecomeLeader()`), the recovery subsystem (`ClusterRecovery.h`, `clusterRecoveryCore()`), worker processes registering through `RegisterWorkerRequest`, storage recruitment from data distribution, transaction-role recruitment from recovery, singleton initialization endpoints on workers, data distributor audit RPCs, ratekeeper health metrics, tlog queuing metrics, cluster health monitor event providers, and clients polling `openDatabase`/`getServerDBInfo`/status interfaces.

Knobs under `SERVER_KNOBS` and `CLIENT_KNOBS` are central to behavior: failure reaction times, recruitment delays, status rate limits, DBInfo batching, process-class delays, health-monitor intervals, failover thresholds, remote log-router monitoring switches, and log-router rerecruitment timeouts all alter control flow.

## Risks And Edge Cases
This file has many concurrent actors mutating shared controller state cooperatively. Races are explicitly managed in several places, such as delaying after worker insertion before failure watching, replacing old worker watchers on re-registration, batching DBInfo endpoint updates, and cleaning recovery actor collections before retry. Changes that add awaits near shared-state mutations can reorder recruitment, DBInfo publication, or failure handling.

Master and recovery loops are intentionally sensitive. Too-fast failure detection can restart long recoveries; too-slow detection can leave clients on stale recovery state. The code uses different failure slopes before and after master registration and enforces `MASTER_SPIN_DELAY` to avoid tight recovery loops.

Worker and singleton placement balances process class, exclusion status, master colocation, used process IDs, and datacenter fitness. Mistakes can repeatedly halt healthy data distributor/ratekeeper/consistency-scan instances, strand a singleton in the wrong DC, or keep excluded processes in important roles.

Multi-region health behavior is knob-dependent and safety-sensitive. The controller distinguishes local, satellite, remote TLog, and log-router degradation; failover also depends on remote health, version difference, recent recovery count, and TPS-limit observations. Incorrect address locality, stale worker-health complaints, or bad threshold tuning can cause unnecessary recovery/failover or suppress a needed one.

Long-poll request handling must tolerate gone clients/workers. `clusterOpenDatabase()` and `clusterGetServerInfo()` use jittered timeouts to eventually reply even if no info changes. Worker registration replies may be used to ask workers to re-register with updated class/priority; sending the wrong reply or leaving promises unset can delay class/exclusion changes.

Durable system-key watchers run at system-immediate priority and mostly retry through `onError()`. They assume bounded ranges below `TOO_MANY`, correct serialization versions, and valid system-key access flags. Bugs here can break cluster ID consistency, process-class propagation, global config updates, latency-band config publication, or backup timestamp lookup.

## Test Signals
The file embeds unit tests for health-state logic: `/fdbserver/clustercontroller/updateWorkerHealth`, `/updateRecoveredWorkers`, `/getDegradationInfo`, `/recentRecoveryCountDueToHealth`, `/shouldTriggerRecoveryDueToDegradedServers`, `/shouldTriggerFailoverDueToDegradedServers`, and `/invalidateExcludedProcessComplaints`. These cover complaint refresh/removal, expired-link cleanup, degraded/disconnected server selection, recent health-triggered recovery counting, transaction-system role sensitivity, remote-region failover blocking, satellite behavior, and invalidation of complaints from excluded processes.

Runtime trace signals are extensive and are important validation hooks: `CCWDB`, `MasterRegistrationReceived`, `PublishNewClientInfo`, `ClusterControllerWorkerFailed`, `ClusterControllerActualWorkers`, `DBInfoStartBroadcast`/`DBInfoFinishBroadcast`, singleton recruitment/halt events, `ClusterControllerHealthMonitor`, `DegradedServerDetectedAndTriggerRecovery`, failover suggestion/trigger events, log-router rerecruitment events, `DatacenterVersionDifference`, and status overload warnings.

Simulation probes exercise recovery and recruitment edge cases, including master/transaction-role failures, old worker registration, log-router recruitment drops, log-router/backup rerecruitment failure, forced health recovery, and ratekeeper zero-TPS failover. Useful regression tests should include simulation workloads that churn workers, alter process classes, exclude processes, force coordinator changes, run multi-region configurations, and validate DBInfo/client-info propagation after recovery and singleton replacement.
