# sources/storage-engines/foundationdb/fdbserver/logsystem/LogSet.cpp

Purpose: Implements `LogSet` helper behavior for describing log servers/routers, identifying routers and backup workers, selecting best and quorum-compatible TLog locations for tags, maintaining locality maps, and building satellite tag placement tables.

Important APIs/types/functions: `logRouterString` and `logServerString` render configured interface IDs for tracing. `hasLogRouter` and `hasBackupWorker` test membership by UID. `populateSatelliteTagLocations` creates per-tag satellite TLog replica teams. `checkSatelliteTagLocations` validates distribution balance and traces abnormalities. `bestLocationFor` returns the preferred log index for a tag. `updateLocalitySet`, `satisfiesPolicy`, and `getPushLocations` wrap `LocalityMap`/`LocalitySet` selection logic.

Control flow: Normal primary log sets select `tag.id % logServers.size()` as the best location, add it to the push set when the tag locality matches, and then ask the locality policy for extra replicas. `allLocations` bypasses tag matching and writes to every local log server. Restricted locality sets narrow replica selection during version-vector unicast recovery. Satellite log sets use precomputed `satelliteTagLocations` and return all team members for TLog or log-router tags, then uniquify the location list. Satellite placement walks possible tag teams, repeatedly selects policy-satisfying replicas from the least-used server ordering, rotates best-server usage, and asserts each team can be built.

State and persistence behavior: `LogSet` is in-memory state derived from `TLogSet`/`CoreTLogSet` configuration and recruitment replies. It stores vectors of log servers, log routers, backup workers, localities, policy, replication/anti-quorum parameters, and `satelliteTagLocations`. Persistence occurs indirectly when `LogSystem` serializes `LogSet` back into log-system config or core state.

Dependencies and integration points: Depends on `LocalityMap`, `LocalitySet`, replication policies, `Tag` locality conventions, `TLogInterface`, `BackupInterface`, and `LogSystem` serialization/recruitment code. `LogPushData`, recovery initialization, log consumers, and commit push paths all rely on `getPushLocations` and `bestLocationFor` to choose the correct TLogs.

Risks: Placement correctness is policy-sensitive. A bad satellite `satelliteTagLocations` table can overload a subset of logs or fail anti-affinity. `satisfiesPolicy` asserts policy selection succeeds and interprets an empty result set as already satisfying the policy. `getPushLocations` must keep `locations` offsets aligned with the flattened TLog location numbering used by `LogSystem::push` and unicast recovery. Tag locality matching is central: special, satellite, transaction, log-router, and negative pseudo localities have different behavior.

Test signals: Tests should cover primary best-location modulo routing, all-location pushes, restricted locality sets, locality-policy replica expansion, satellite team generation balance, duplicate zone/multiple DC trace paths, special-locality matching, and stable flattened offsets across multi-log-set configurations.
