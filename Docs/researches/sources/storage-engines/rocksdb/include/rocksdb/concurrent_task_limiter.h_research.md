# Research: sources/storage-engines/rocksdb/include/rocksdb/concurrent_task_limiter.h

- **Purpose:** Declares a small public handle for limiting the number of concurrent internal tasks shared across column families and RocksDB instances. It exposes the result of `NewConcurrentTaskLimiter()` while making clear that third-party derived classes are not supported.
- **Important APIs/types/functions:** `class ConcurrentTaskLimiter` has `GetName()`, `SetMaxOutstandingTask(int32_t limit)`, `ResetMaxOutstandingTask()`, and `GetOutstandingTask()`. `NewConcurrentTaskLimiter(const std::string& name, int32_t limit)` creates the internal implementation. Limits use `0` for "block new tasks" and negative values for "unlimited".
- **Control flow:** Callers create one limiter and pass/share it through options that accept concurrent task limiters. RocksDB internals consult the limiter before starting background work and update outstanding counts around task execution. Public methods let operators change the cap at runtime.
- **State and persistence behavior:** The limiter is an in-memory coordination object. It does not persist into SST, WAL, MANIFEST, or OPTIONS files except through whatever option owns a pointer to it. `GetOutstandingTask()` is live process state and should be treated as approximate under concurrency unless the implementation documents stronger guarantees.
- **Dependencies:** Includes `<stdint.h>`, `<string>`, and the RocksDB namespace header. Actual synchronization and scheduling are in RocksDB internals, not in this header.
- **Integration points:** Intended for options controlling background tasks such as compaction or subcompaction throttling across column families/DB instances. It also integrates with operational controls that adjust resource budgets while a DB is open.
- **Risks:** Ownership is raw-pointer based from the factory, so callers need to follow RocksDB's expected lifetime pattern and avoid deleting while DBs still reference it. Derived external implementations are unsupported, so tests or applications that subclass this interface risk breakage. Setting limit to zero can stall new work and amplify write stalls if used accidentally.
- **Test signals:** Unit and stress tests should check limit transitions (`0`, positive, negative), outstanding counts returning to zero after task completion, sharing across multiple column families/DBs, runtime cap changes under concurrency, and safe destruction only after DB/task users are gone.
