# sources/storage-engines/rocksdb/utilities/transactions/transaction_test.h

## Purpose
This header provides shared GoogleTest fixtures and parameter helpers for RocksDB transaction tests. It centralizes construction of `TransactionDB` instances across normal and stackable DB modes, ordered and unordered writes, one or two write queues, write-committed/write-prepared/write-unprepared policies, and both legacy and per-key point lock managers. It also contains reusable transaction scenarios for sequence-number accounting and cross-policy compatibility checks.

## Important APIs, Types, and Functions
`IsInCombination()` is a bit-test helper used by parameterized tests. `WriteOrdering` maps test parameters onto `Options::unordered_write`.

`TransactionTestBase` owns the database under test (`TransactionDB* db`), `SpecialEnv`, `FaultInjectionTestFS`, `CompositeEnvWrapper`, DB path, `Options`, `TransactionDBOptions`, stackable-mode choice, and deadlock timeout. Its constructor configures a small-buffer, low-fsync, fault-injectable transaction DB with merge support, WAL recycling, optional two write queues, selected write policy, optional per-key lock manager, reduced write-prepared commit cache bits for TSAN, write-unprepared batch-flush stress settings, and autogenerated transaction names. It opens either through `TransactionDB::Open()` or through the local stackable wrapping path.

`ReOpenNoDelete()`, `ReOpenNoDelete(cfs, handles)`, and `ReOpen()` close and reopen the test DB with or without destroying data. The no-delete paths assert no leaked open files, drop unsynced fault-injection data, reset fault state, and then reopen with the same stackable/non-stackable branch. `OpenWithStackableDB()` has overloads for default and explicit column-family descriptors; both call `TransactionDB::PrepareWrap()`, open `DBImpl` with policy-dependent `use_seq_per_batch` and `use_batch_per_txn`, then wrap a `StackableDB` with transaction behavior.

`TestTxn0()` through `TestTxn4()` are reusable transaction patterns that update atomic counters for expected sequence consumption: direct `Put`, direct `WriteBatch`, transaction commit without prepare, prepared commit, and prepared rollback. `CrossCompatibilityTest()` writes a randomized mix of direct DB writes, write batches, and transactions under one write policy, optionally flushes WAL state, switches policy, reopens, and verifies either successful data preservation or fast `NotSupported` rejection for incompatible non-empty WALs.

The derived fixtures are `TransactionTest`, `TransactionDBTest`, `TransactionStressTest`, `MySQLStyleTransactionTest`, `WriteCommittedTxnWithTsTest`, and `TimestampedSnapshotWithTsSanityCheck`. The timestamped write-committed fixture adds `GetFromDb()` for `TxnTimestamp` reads and `NewTxn()` that toggles transaction write-batch indexing according to the parameter set. The template helpers `WrapParamWithPerKeyPointLockManagerParams*` expand existing parameter tuples with lock-manager and deadlock-timeout variants; the macros at the end make that expansion concise in test instantiations.

## Control Flow
Fixture construction is the main control path: set options, destroy any old DB path, fill `TransactionDBOptions`, open, and assert success. Destruction deletes the DB and destroys the path unless `KEEP_DB` is set. Reopen helpers always close first and then select the same direct-open or stackable-open path. Stackable opening prepares transaction wrapping metadata, opens a root `DBImpl`, creates `StackableDB`, wraps it, and cleans column-family handles or stackable DB ownership on failure.

The transaction scenario helpers execute real writes and then adjust counters based on write policy and write-queue topology. Write-committed generally consumes one sequence per key. Write-prepared generally consumes one sequence per batch plus commit/rollback markers where applicable. Write-unprepared can consume one sequence per flushed key batch plus prepare or marker sequences. `CrossCompatibilityTest()` loops over 1024 deterministic randomized operations, records the last committed value per key, then tests reopen behavior after policy migration.

## State and Persistence Behavior
The fixture persists a per-thread DB path and uses a fault-injection filesystem to model lost unsynced data on reopen. Small memtables, WAL recycling, two-write-queue toggles, commit-cache sizing, write-batch flush thresholds, and merge operators deliberately stress transaction persistence and recovery behavior. Atomic counters (`linked`, `exp_seq`, `commit_writes`, `expected_commits`, `with_empty_commits`) are shared test bookkeeping for concurrent or sequence-sensitive tests. Column-family handles in derived timestamp fixtures are owned in `handles_` and destroyed in fixture destructors.

## Dependencies and Integration Points
The header integrates `DBImpl`, transaction DB public APIs, stackable DB wrapping, pessimistic and write-unprepared transaction internals, lock-manager parameterization, fault-injection filesystems, sync points, merge operators, RocksDB test utilities, and GoogleTest parameter interfaces. It is included by many transaction tests, including the timestamped write-committed tests in this work item.

## Risks and Edge Cases
Because this file opens real DBs in a constructor, any option interaction or environment failure fails fixture setup before individual tests run. Stackable wrapping has delicate ownership rules: failed `WrapStackableDB()` may delete the stackable DB while handle cleanup remains local. Sequence accounting in `TestTxn*()` is tightly coupled to write-policy implementation details and two-write-queue marker behavior, so transaction internals changes require updating expectations. `CrossCompatibilityTest()` assumes policy migration is safe only with an empty WAL; the non-empty WAL path intentionally expects rejection. The GCC 14 diagnostic suppression around tuple wrappers indicates compiler-sensitive template code.

## Test Signals
This header is not a standalone test binary, but it supplies the setup and assertions for transaction suites. A passing dependent suite signals that transaction opening, stackable wrapping, fault-injection reopen behavior, lock-manager parameter expansion, sequence accounting, and cross-policy compatibility still match RocksDB expectations.
