# Research: sources/storage-engines/rocksdb/db/db_write_test.cc

- **Purpose:** Broad write-path regression suite for RocksDB `DBImpl::WriteImpl`, write-thread batching, WAL flushing/syncing/locking, error propagation, WAL recycling/recovery, and `IngestWriteBatchWithIndex`.
- **Important APIs/types/functions:** Defines parameterized `DBWriteTest : DBTestBase, testing::WithParamInterface<int>` and unparameterized `DBWriteTestUnparameterized`. Key tests include `SyncAndDisableWAL`, `WriteStallRemoveNoSlowdownWrite`, `WriteThreadHangOnWriteStall`, `WriteThreadWaitNanosCounter`, `IOErrorOnWALWritePropagateToWriteThreadFollower`, `PipelinedWriteRace`, `ManualWalFlushInEffect`, `UnflushedPutRaceWithTrackedWalSync`, `InactiveWalFullySyncedBeforeUntracked`, `IOErrorOnWALWriteTriggersReadOnlyMode`, `IOErrorOnSwitchMemtable`, `LockWALInEffect`, `LockWALConcurrentRecursive`, `ConcurrentlyDisabledWAL`, WAL recycle tests, and `IngestWriteBatchWithIndex`. Helper `CorruptLogFile()` rewrites a WAL record header byte range to simulate recovery corruption.
- **Control flow:** The file instantiates write-mode variants (`kDefault`, `kConcurrentWALWrites`, `kPipelinedWrite`). It creates deterministic write-stall and write-group interleavings with `SyncPoint`, spawns `port::Thread`/`std::thread` writers, injects filesystem failures through fault-injection env/fs wrappers, and reopens DBs to validate durable WAL behavior. WAL-lock tests hold recursive locks while parallel Put, Flush, and external-file ingestion block until the final unlock.
- **State and persistence behavior:** Exercises WAL buffers, synced WAL size tracking in MANIFEST, alive/recycled WAL metadata, read-only/background-error state after WAL failures, sequence numbers frozen by `LockWAL`, write-thread linked-list state, and persisted key/value state after crash-style `DropUnsyncedFileData()` or corrupted WAL recovery. It also validates that disabled-WAL writes do not inflate `WAL_FILE_BYTES`.
- **Dependencies:** Uses DB test utilities, `WriteBatchInternal`, `WriteThread`, `FaultInjectionTestEnv`, `FaultInjectionTestFS`, log reader/writer classes, `SstFileWriter`, `WriteBatchWithIndex`, merge operators, perf context, and RocksDB public APIs such as `FlushWAL`, `SyncWAL`, `LockWAL`, `UnlockWAL`, `Resume`, `IngestExternalFile`, and `IngestWriteBatchWithIndex`.
- **Integration points:** Directly targets `DBImplWrite`, `WriteThread` group formation/completion, WAL tracking and manual flush semantics, background error handling after write path I/O failures, external SST ingestion blocking on WAL locks, and write-batch-with-index ingestion constraints.
- **Risks:** Many scenarios are concurrency regressions with busy waits and sync points, so internal ordering changes can make tests flaky or stale. Fault-injection expectations vary with `manual_wal_flush`; tests deliberately branch on option behavior. WAL corruption tests assume current log record layout and point-in-time recovery semantics.
- **Test signals:** Signals include InvalidArgument for sync+disableWAL, OK/Incomplete/NOK results under stalls, perf counter `write_thread_wait_nanos`, leader/follower counts, persisted key visibility after reopen, `WALBufferIsEmpty()`, current log numbers, read-only mode after failure, recursive WAL lock completion flags, WAL byte statistics, and expected corruption during reopen.
