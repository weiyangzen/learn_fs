# Research: sources/storage-engines/rocksdb/db/error_handler.h

- **Purpose:** Declares the `ErrorHandler` class and `DBRecoverContext`, which encapsulate RocksDB background-error state, severity policy entry points, recovery lifecycle, DB-stop queries, and quarantined file tracking.
- **Important APIs/types/functions:** `DBRecoverContext` stores `FlushReason flush_reason` and `bool flush_after_recovery`, defaulting to `kErrorRecovery` and false. `ErrorHandler` exposes constructor, `EnableAutoRecovery`, `GetErrorSeverity`, `SetBGError`, `GetBGError`, `GetRecoveryError`, `ClearBGError`, `IsDBStopped`, `IsBGWorkStopped`, `IsSoftErrorNoBGWork`, `IsRecoveryInProgress`, `ReadyForShutdown`, `RecoverFromBGError`, `CancelErrorRecoveryForShutDown`, `EndAutoRecovery`, `AddFilesToQuarantine`, `GetFilesToQuarantine`, and `ClearFilesToQuarantine`.
- **Control flow:** Public methods are called under DB mutex for error setting, recovery, shutdown, and quarantine access. `IsBGWorkStopped` stops background work when an active error is hard-or-worse, auto recovery is disabled, or a soft error requires exclusive recovery work. `ReadyForShutdown` only returns true when recovery is not in progress and listener notification has not temporarily blocked DB close.
- **State and persistence behavior:** Holds references to `DBImpl`, immutable DB options, DB mutex/condition variable, background and recovery status objects, recovery thread, flags for auto recovery/recovery progress/no-bg-work/shutdown, atomic stopped state, statistics pointer, and file numbers quarantined during uncertain MANIFEST recovery. State is in-memory but directly affects durable recovery, flush behavior, and obsolete file deletion safety.
- **Dependencies:** Includes instrumented synchronization, DB options, `IOStatus`, listener/status APIs, and `autovector`. Forward-declares `DBImpl`; private methods integrate with SstFileManager, DB resume, listener notifications, logging, and statistics in the `.cc` implementation.
- **Integration points:** Owned by `DBImpl` to mediate background errors from flush, compaction, writes, MANIFEST writes, memtable operations, and async file opens. It is consulted by write/background scheduling paths to determine stopped state and by close/destructor logic to avoid shutdown while recovery callbacks are active.
- **Risks:** Most public methods assume DB mutex discipline; using them without the lock can race recovery state, quarantine vectors, or close readiness. Severity escalation is monotonic except explicit recovery clearing, so callers must pass accurate reasons/status metadata. The class owns a recovery thread and must join it during shutdown to avoid use-after-free of DBImpl or mutex state.
- **Test signals:** Behavior is observed by tests that inject I/O errors, call `Resume`, check read-only/stopped modes, wait for auto recovery, verify listener callbacks, and ensure quarantined or obsolete files are not deleted prematurely.
