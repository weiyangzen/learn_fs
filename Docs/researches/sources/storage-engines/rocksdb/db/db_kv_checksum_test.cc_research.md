# Research: sources/storage-engines/rocksdb/db/db_kv_checksum_test.cc

- **Purpose:** Regression and fault-injection coverage for key/value checksum protection across write batches, WAL handoff, memtable insertion, reads, iterators, column families, and flush. The file verifies that protected write batches and `memtable_protection_bytes_per_key` detect byte-level corruption and return `Status::Corruption` before corrupted state is accepted as durable data.
- **Important APIs/types/functions:** Defines `WriteBatchOpType` for `Put`, `Delete`, `SingleDelete`, `Merge`, `PutEntity`, and `DeleteRange`; `WriteMode` for protected-batch and write-option protection paths; `GetWriteBatch()` for constructing one-operation batches; `DbKvChecksumTestBase::GetCFHandleToUse()` for default-CF fallback on `PutEntity`; `DbKvChecksumTest::ExecuteWrite()` and `CorruptNextByteCallBack()` for parameterized corruption loops; `DbKvChecksumTestMergedBatch` and `CorruptWriteBatch()` for write-group merge coverage; `DbKVChecksumWALToWriteBatchTest`; and `DbMemtableKVChecksumTest` for read-side memtable checksum validation. It relies on `WriteBatch::VerifyChecksum()`, `WriteBatchInternal::Append()`, `WriteBatchInternal::Contents()`, `WriteOptions::protection_bytes_per_key`, `Options::memtable_protection_bytes_per_key`, `DBImpl` test hooks, and `XXH3_64bits`.
- **Control flow:** Parameterized tests iterate through operation types, corruption addends, write modes, and protection-byte sizes. WAL tests set `SyncPoint` callbacks at `DBImpl::WriteToWAL:log_entry`, skip the unprotected sequence-number prefix, reopen after each corruption-induced read-only transition, and assert WAL size and background error state do not advance. Memtable-add tests corrupt the encoded memtable entry through `MemTable::Add:Encoded` and expect the write to fail. Merged-batch tests force a two-writer write group via `WriteThread::JoinBatchGroup` sync points, corrupt either leader or follower pre-merged batch bytes, and verify both writers see corruption. Read-side tests first write valid entries, then corrupt saved memtable bytes through `Memtable::SaveValue:Found:entry` or `MemTable::Add:BeforeReturn:Encoded`, then exercise `Get`, `MultiGet`, iterators, and flush.
- **State and persistence behavior:** The tests repeatedly destroy, reopen, and create column families because checksum failures move the DB into read-only/background-error state. WAL state is observed through `TEST_wals_total_size()` and `TEST_GetBGError()`. Column-family tests write through non-default handles named `pikachu` or `ramen`. Memtable corruption tests deliberately avoid corrupting selected length bytes to prevent invalid memory access while still checking checksum detection.
- **Dependencies:** Includes `db/blob/blob_index.h`, `db/db_test_util.h`, and `rocksdb/rocksdb_namespace.h`. It depends on RocksDB's gtest harness, `SyncPoint`, `DBTestBase`, write-thread internals, merge operators, wide-column `PutEntity`, XXH3 checksum implementation, and DBImpl test-only inspection methods.
- **Integration points:** Covers the write path between public `DB::Write`, `WriteBatch`, write group leader/follower merging, WAL serialization, recovery log replay, memtable add/save, point reads, multi-get, iterator creation, and flush. It also validates that column-family-aware encodings and default-column-family fallbacks are protected consistently.
- **Risks:** The tests are tightly coupled to internal sync-point names and encoded entry layouts, including hard-coded sequence-number and value-length offsets. Corrupting too early or too broadly can produce crashes instead of corruption statuses. The merged-batch tests use busy waiting and thread coordination, so scheduler timing changes can affect reliability. One-byte checksum cases are explicitly skipped as flaky.
- **Test signals:** Success is indicated by `ASSERT_TRUE(status.IsCorruption())`, unchanged WAL sizes, corruption background errors, successful `VerifyChecksum()` in non-corruption cases, expected XXH3 handoff checksum during recovery, iterator invalidity with corruption status, and `Flush()` returning corruption after reading corrupted protected memtable data.
