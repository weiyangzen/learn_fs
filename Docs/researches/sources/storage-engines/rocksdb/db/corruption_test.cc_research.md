# sources/storage-engines/rocksdb/db/corruption_test.cc research

Purpose: `corruption_test.cc` is RocksDB's broad corruption and recovery regression suite. It validates WAL recovery modes, SST corruption detection, manifest/descriptor repair, paranoid file checks, range-deletion metadata corruption, file checksum verification, write failure propagation, key-order guards, and crash-during-recovery consistency across regular DB and TransactionDB.

Important APIs, types, and fixtures: `ErrorFS` wraps `FileSystemWrapper` and can inject `NewWritableFile` errors. `CorruptionTest` builds an isolated DB with `kTolerateCorruptedTailRecords`, an `ErrorFS` composite env, tiny block cache, and block-based table options. Helpers include `Build()` for deterministic key/value writes, `Check()` for approximate surviving-key verification without checksum reads, `Corrupt()` for latest-file byte corruption, `CorruptTableFileAtLevel()`, `RepairDB()`, decimal `Key()`/random `Value()`, `GetSortedWalFiles()`, and WAL truncation through `CorruptFileWithTruncation()`. `CrashDuringRecoveryWithCorruptionTest` parameterizes `avoid_flush_during_recovery` and `track_and_verify_wals_in_manifest`.

Control flow: early tests corrupt WAL bytes or truncate WALs, reopen under tolerant or point-in-time modes, and assert expected data loss and open behavior. SST tests build and compact files, corrupt data/index/footer/magic/size, then compare behavior with `paranoid_checks` enabled or disabled. Other tests repair missing or corrupted descriptors, validate recovered sequence numbers, and ensure unrelated keys remain writable despite existing corrupted SSTs. Paranoid file checks use `mock::MockTableFactory` corruption modes to force bad keys, values, and reordered keys during flush or compaction. Recovery-crash tests simulate multi-column-family WAL state, inject sync/open errors through `SyncPoint`, reopen again, and verify RocksDB does not persist a MANIFEST that makes SSTs appear ahead of recoverable WAL state.

State and persistence behavior: the suite mutates actual DB directory contents: WALs are truncated, SST bytes are overwritten or extended, files are deleted, descriptors are corrupted, and `RepairDB` rebuilds metadata. Persistent state spans MANIFEST log numbers, WAL retention, column-family handles, table properties, file sizes recorded in metadata, and transaction prepare records. Several tests intentionally close and reopen DBs to force recovery code paths and validate whether corruption is caught at open time or deferred to reads/checksums.

Dependencies and integration points: the file uses `DBImpl` test hooks, `TransactionDB`, `WriteBatch`, `VersionSet`, file naming/parsing helpers, `RandomAccessFileReader`, block-based table metadata (`FindMetaBlockInFile`, `kRangeDelBlockName`), `VerifyChecksum`, `VerifyFileChecksums`, `GetFileChecksumGenCrc32cFactory`, `mock::MockTableFactory`, `SpecialEnv`, and `SyncPoint`. It also validates public convenience checksum behavior indirectly through DB-level checksum APIs.

Risks and edge cases covered: corruption may be tolerated, rejected, repaired, or deferred depending on recovery mode and paranoid flags. These tests cover corrupted WAL tails, WAL retention after point-in-time recovery, filesystem write failures, table index/footer damage, file-size mismatches, missing/deleted SSTs, corrupted range-deletion blocks, compaction input corruption with and without paranoid mode, bad key ordering from memtable or table factory, full-file checksum mismatch callbacks, and crash windows before WAL sync during recovery. TransactionDB tests add prepared transaction WAL-retention constraints.

Test signals: expected statuses are precise: `OK`, `NotFound`, `IsCorruption`, `IsIOError`, or non-OK depending on mode. Data checks assert surviving-key counts or exact values. Other signals include random-read counters for checksum readahead, error-message substrings such as `magic number`, `format_version`, and `file size mismatch`, callback hit counts for checksum mismatch, and successful second reopen after injected crash windows. The suite is intentionally white-box and sensitive to DB file layout, but it gives strong coverage of recovery invariants.
