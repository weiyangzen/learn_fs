# Research: sources/storage-engines/rocksdb/db/error_handler.cc

- **Purpose:** Implements RocksDB background error classification, severity escalation, automatic recovery from no-space and retryable I/O errors, recovery shutdown coordination, quarantine handling for ambiguous MANIFEST edits, and error-handler statistics.
- **Important APIs/types/functions:** Defines severity maps `ErrorSeverityMap`, `DefaultErrorSeverityMap`, and `DefaultReasonMap`. Implements `ErrorHandler::CancelErrorRecoveryForShutDown`, `HandleKnownErrors`, `SetBGError`, `AddFilesToQuarantine`, `ClearFilesToQuarantine`, `OverrideNoSpaceError`, `RecoverFromNoSpace`, `ClearBGError`, `RecoverFromBGError`, `StartRecoverFromRetryableBGIOError`, `RecoverFromRetryableBGIOError`, `CheckAndSetRecoveryAndBGError`, `EndAutoRecovery`, and `RecordStats`.
- **Control flow:** `SetBGError` converts incoming status to `IOStatus`, records counters, handles data-loss and manual-WAL fatal cases, routes retryable/file-scope I/O errors to auto-resume logic, and falls back to `HandleKnownErrors`. `HandleKnownErrors` classifies by reason/code/subcode/paranoid checks, applies no-space overrides, notifies listeners, records the most severe background error, sets recovery context, invokes SstFileManager no-space recovery, and stops DB work for hard errors. Auto-resume starts a recovery thread that loops `ResumeImpl()` with timed waits until success, fatal/shutdown, nonretryable failure, or retry-count exhaustion.
- **State and persistence behavior:** Maintains `bg_error_`, `recovery_error_`, `recovery_in_prog_`, `soft_error_no_bg_work_`, `allow_db_shutdown_`, `end_recovery_`, `is_db_stopped_`, `recover_context_`, `recovery_thread_`, and unsorted `files_to_quarantine_`. It does not write persistent files directly, but controls whether DB writes/background work stop and whether quarantined SST file numbers may be deleted during MANIFEST recovery.
- **Dependencies:** Depends on `DBImpl::ResumeImpl`, DB options/listeners/statistics, `SstFileManagerImpl::StartErrorRecovery/CancelErrorRecovery`, event helper notifications, logging, `InstrumentedMutex`/condvar, `port::Thread`, `IOStatus` metadata such as scope/retryable/data-loss, and background error reason enums.
- **Integration points:** Central path for compaction/flush/write callback/MANIFEST/memtable/async-open errors. It gates write availability, background work scheduling, DB close readiness, SstFileManager no-space recovery, listener callbacks (`OnBackgroundError`, `OnErrorRecoveryEnd`), statistics tickers/histograms, and recovery flush reasons.
- **Risks:** Severity maps are policy-critical; missing reason/code/subcode combinations fall through to broader defaults. Incorrect auto-recovery decisions can either leave a recoverable DB stopped or resume unsafely after WAL/data-loss errors. Recovery thread coordination releases and reacquires DB mutex; shutdown, listener callbacks, and close readiness require careful ordering. Quarantine must be cleared only after successful recovery to avoid deleting files needed for MANIFEST consistency.
- **Test signals:** Directly and indirectly tested by DB write/background-error suites through fatal/read-only transitions, `Resume()`, auto-resume counters, listener notifications, recovery success/failure, no-space handling, retryable I/O behavior, and file-quarantine deletion blocking.
