# Research: sources/storage-engines/rocksdb/db/db_write_buffer_manager_test.cc

- **Purpose:** Parameterized RocksDB test coverage for `WriteBufferManager` behavior across column families, independent DB instances sharing one manager, runtime `allow_stall` changes, and WAL recovery enforcement. It exercises both cache-costed and non-cache-costed WBM construction through `testing::Bool()`.
- **Important APIs/types/functions:** Defines `DBWriteBufferManagerTest : DBTestBase, testing::WithParamInterface<bool>` with `cost_cache_`. Test cases cover `SharedBufferAcrossCFs1`, `SharedWriteBufferAcrossCFs2`, `SharedWriteBufferLimitAcrossDB`, `SharedWriteBufferLimitAcrossDB1`, `MixedSlowDownOptionsSingleDB`, `MixedSlowDownOptionsMultipleDB`, `StopSwitchingMemTablesOnceFlushing`, `RuntimeChangeableAllowStall`, `WriteBufferManagerLimitDuringWALRecoverySingleDB`, `WriteBufferManagerLimitDuringWALRecoveryMultipleDBs`, `DoubleSchedulingBugDuringWALRecovery`, and `ReadOnlyRecoveryWithEnforceWBMDoesNotAssert`.
- **Control flow:** Most tests configure small global WBM limits with large per-CF `write_buffer_size`, write enough data to exceed the shared limit, then use `SyncPoint` callbacks such as `WBMStallInterface::BlockDB`, `WriteThread::WriteStall::Wait`, and `DBImpl::BackgroundCallFlush:start` to hold flushes while asserting which DBs or writers block. Recovery tests write WAL-only data, close, reopen with different WBM limits/options, and check whether flushes bound memory during replay.
- **State and persistence behavior:** State under test is mutable memtable memory charged to `WriteBufferManager`, write-stall state, immutable memtable/flush-pending properties, shared WBM accounting across multiple `DB::Open()` instances, and WAL contents replayed during recovery. Persistent artifacts are test DB directories, WAL files, and generated SSTs; cleanup closes and destroys auxiliary DBs where created.
- **Dependencies:** Uses `db/db_test_util.h`, `db/write_thread.h`, `NewLRUCache`, `WriteBufferManager`, `InstrumentedMutex`, `InstrumentedCondVar`, `SyncPoint`, `SleepingBackgroundTask`, and DB test helpers (`CreateAndReopenWithCF`, `Put`, `Flush`, `ReadOnlyReopen`, `TotalTableFiles`). It depends on RocksDB internals exposing test sync points and test-only properties.
- **Integration points:** Validates DB write admission and memtable switching paths that consult WBM, the WBM-to-cache charging mode, `WriteOptions::no_slowdown`, background flush scheduling, and `Options::enforce_write_buffer_manager_during_recovery`. It also protects `FlushScheduler` interactions during WAL recovery and read-only recovery.
- **Risks:** The tests depend on exact memory thresholds and allocator/accounting behavior; changes to arena charging or mutable limit calculations can require updating expected counts. SyncPoint dependencies are race-sensitive and can hang if internal sync-point names or ordering drift. Multi-DB tests share one WBM, so cleanup failures can leak state into later assertions.
- **Test signals:** Assertions check OK/Incomplete statuses, block counts, writer-set sizes, WBM `ShouldFlush()`, mutable memtable memory before/after recovery, L0 table counts, DB properties, and absence of debug assertions in duplicate scheduling regressions.
