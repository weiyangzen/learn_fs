# Research: sources/storage-engines/rocksdb/db/wide/blob_column_resolver_util.h

- **Purpose:** Header-only shared helpers for resolving wide-column blob values in read and compaction paths.
- **Important APIs/types/functions:** Namespace `blob_resolver_util` provides `FindBlobColumn`, `FindInCache`, `CacheInlinedBlob`, and `IsBlobColumnIndex`. It operates on vectors of `(column_index, BlobIndex)` and `(column_index, unique_ptr<PinnableSlice>)`.
- **Control flow:** Each lookup helper performs a linear scan because the expected number of blob columns per entity is small. `FindBlobColumn` returns the matching `BlobIndex` or null, handling a null blob-columns pointer. `FindInCache` returns a cached `PinnableSlice*` or null. `CacheInlinedBlob` appends a new `PinnableSlice`, pins the inline blob value from `BlobIndex::value()`, and returns a `Slice` over the cached value. `IsBlobColumnIndex` delegates to `FindBlobColumn`.
- **State and persistence behavior:** No persistent state. The only mutation is appending to the caller-owned per-resolution cache so returned `Slice`s remain valid after the helper returns.
- **Dependencies and integration points:** Depends on `db/blob/blob_index.h`, `rocksdb/slice.h`, and `PinnableSlice`. Shared by `ReadPathBlobResolver` and `CompactionBlobResolver` to keep blob-column lookup/cache logic consistent across foreground reads and compaction.
- **Risks:** Returned pointers and slices are valid only while the caller-owned vectors and `PinnableSlice` instances remain alive and un-invalidated. Duplicate column indices would return/cache the first match for lookup but `CacheInlinedBlob` does not deduplicate, so callers should check cache before appending. Linear scan is appropriate for the documented few-column case but would scale poorly if wide entities contain many blob columns.
- **Test signals:** No direct test in this file. Expected signals come from wide-column blob read/compaction tests that compare resolved values, cache reuse, and behavior for non-blob columns.
