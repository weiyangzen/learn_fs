# Research: sources/storage-engines/pebble/read_state.go

- **Purpose:** Provides lock-light snapshots of the current LSM `Version` and memtable queue for readers, avoiding `DB.mu` on normal read-state loads while preserving lifetime safety.
- **Important APIs/types/functions:** `readState` contains `db`, atomic `refcnt`, `current *manifest.Version`, and `memtables flushableList`. `ref`, `unref`, and `unrefLocked` manage version and memtable reader references. `DB.loadReadState` grabs `DB.readState.RLock`, references the current state, and returns it. `DB.updateReadStateLocked` builds a fresh snapshot under `DB.mu`, references its version/memtables, installs it under `DB.readState.Lock`, optionally runs a checker, and unreferences the old snapshot.
- **Control flow:** Readers load and later unref snapshots. Writers or version/memtable transitions publish a new immutable snapshot for future readers. Last unref releases the manifest version and each memtable reader reference; the non-locked path also schedules obsolete object deletion.
- **State and persistence behavior:** State is in-memory but protects persistent objects from deletion while readers can still see them. Version references retain sstable metadata and object lifetimes; memtable reader refs retain mutable/immutable memtable storage. `updateReadStateLocked` reflects durable and in-memory state transitions into the read path.
- **Dependencies:** Depends on `sync/atomic`, `internal/manifest`, `DB.mu`, `DB.readState`, `flushableList`, version reference APIs, memtable reader ref APIs, and obsolete object deletion scheduling.
- **Integration points:** Central to iterator/get creation and any read path that needs a consistent view. It bridges write-side version/memtable changes to read-side snapshot isolation.
- **Risks:** Reference-count imbalance can leak versions/memtables or allow premature deletion. Calling `unref` while holding `DB.mu` would violate lock ordering, which is why `unrefLocked` exists. The checker callback runs after publishing the new state and fatal-exits on error, so it must remain diagnostic rather than recoverable control flow.
- **Test signals:** `read_state_test.go` provides a benchmark stressing `loadReadState`, `unref`, and update publication under parallel access with several update ratios. Functional coverage is mostly indirect through all DB read/write tests.
