# sources/storage-engines/sqlite/src/btree.h

## Purpose

`btree.h` is the public interface for SQLite's B-tree storage subsystem. It exposes the opaque `Btree`, `BtCursor`, `BtShared`, and `BtreePayload` types used by higher layers, and declares the entry points used by the pager/VDBE/schema layers to open database files, manage transactions, create and destroy tables, open cursors, move through table/index b-trees, read/write payloads, maintain database-header metadata, and run integrity checks. The header is deliberately interface-heavy and implementation-light; detailed page layout, cursor state, shared-cache internals, and pointer-map details live in `btreeInt.h`.

## Important APIs, Types, and Flags

The central lifecycle APIs are `sqlite3BtreeOpen()`, `sqlite3BtreeClose()`, `sqlite3BtreeSetPageSize()`, `sqlite3BtreeGetPageSize()`, `sqlite3BtreeSetCacheSize()`, `sqlite3BtreeSetSpillSize()`, `sqlite3BtreeSetPagerFlags()`, `sqlite3BtreeMaxPageCount()`, `sqlite3BtreeLastPage()`, `sqlite3BtreeSecureDelete()`, `sqlite3BtreeSetAutoVacuum()`, and `sqlite3BtreeGetAutoVacuum()`. `sqlite3BtreeOpen()` accepts both btree-layer flags (`BTREE_OMIT_JOURNAL`, `BTREE_MEMORY`, `BTREE_SINGLE`, `BTREE_UNORDERED`) and VFS open flags, making it the bridge between SQLite connection setup and the pager/VFS stack.

Transaction APIs are `sqlite3BtreeBeginTrans()`, `sqlite3BtreeCommitPhaseOne()`, `sqlite3BtreeCommitPhaseTwo()`, `sqlite3BtreeCommit()`, `sqlite3BtreeRollback()`, `sqlite3BtreeBeginStmt()`, `sqlite3BtreeSavepoint()`, `sqlite3BtreeTxnState()`, and, when WAL is enabled, `sqlite3BtreeCheckpoint()`. The commit API is explicitly split into two phases for multi-database commit coordination and rollback-journal/WAL interactions.

Schema and metadata APIs include `sqlite3BtreeSchema()`, `sqlite3BtreeSchemaLocked()`, `sqlite3BtreeGetMeta()`, `sqlite3BtreeUpdateMeta()`, `sqlite3BtreeNewDb()`, `sqlite3BtreeSetVersion()`, and the metadata indexes `BTREE_FREE_PAGE_COUNT`, `BTREE_SCHEMA_VERSION`, `BTREE_FILE_FORMAT`, `BTREE_DEFAULT_CACHE_SIZE`, `BTREE_LARGEST_ROOT_PAGE`, `BTREE_TEXT_ENCODING`, `BTREE_USER_VERSION`, `BTREE_INCR_VACUUM`, `BTREE_APPLICATION_ID`, and virtual `BTREE_DATA_VERSION`. The comment maps these indexes to database-header offsets by `36 + idx*4`, so callers in `build.c` and other schema code can manipulate file-format, text-encoding, and schema-cookie fields through the btree abstraction.

Structural mutation APIs are `sqlite3BtreeCreateTable()`, `sqlite3BtreeDropTable()`, `sqlite3BtreeClearTable()`, `sqlite3BtreeClearTableOfCursor()`, `sqlite3BtreeTripAllCursors()`, `sqlite3BtreeIncrVacuum()`, `sqlite3BtreeTransferRow()`, and `sqlite3BtreeClearCache()`. Table creation flags distinguish rowid-table b-trees (`BTREE_INTKEY`) from index/WITHOUT ROWID b-trees (`BTREE_BLOBKEY`).

Cursor APIs form the data-access contract used by the VDBE: `sqlite3BtreeCursor()`, `sqlite3BtreeCloseCursor()`, `sqlite3BtreeTableMoveto()`, `sqlite3BtreeIndexMoveto()`, `sqlite3BtreeCursorHasMoved()`, `sqlite3BtreeCursorRestore()`, `sqlite3BtreeFirst()`, `sqlite3BtreeLast()`, `sqlite3BtreeNext()`, `sqlite3BtreePrevious()`, `sqlite3BtreeEof()`, `sqlite3BtreeIntegerKey()`, `sqlite3BtreePayload()`, `sqlite3BtreePayloadFetch()`, `sqlite3BtreePayloadSize()`, `sqlite3BtreeMaxRecordSize()`, `sqlite3BtreeInsert()`, `sqlite3BtreeDelete()`, `sqlite3BtreeCount()`, and incremental-blob helpers under `SQLITE_OMIT_INCRBLOB`. Cursor flags include write cursors (`BTREE_WRCSR`), delete-only optimization hints (`BTREE_FORDELETE`), insert/delete hints (`BTREE_SAVEPOSITION`, `BTREE_AUXDELETE`, `BTREE_APPEND`, `BTREE_PREFORMAT`), and hint flags (`BTREE_BULKLOAD`, `BTREE_SEEK_EQ`).

`BtreePayload` is the key insert payload contract. For rowid tables, `pKey` is `NULL`, `nKey` is the integer rowid, and `pData`/`nData`/`nZero` describe the table record. For indexes and WITHOUT ROWID tables, `pKey`/`nKey` contain the encoded key, and `aMem`/`nMem` may expose decomposed values. This split lets the btree layer operate on both table and index b-trees without exposing page-format internals to the VDBE.

## Control Flow and State

At runtime, higher layers open a `Btree`, configure pager/cache/page-size settings, begin a transaction, create/open cursors, move cursors to entries, read or mutate cells, and commit or roll back. `sqlite3FinishCoding()` and DDL code in `build.c` rely on the metadata constants and btree transaction opcodes generated by the VDBE; the actual btree methods implement the storage-side work. Cursor movement follows a seek/restore pattern: external callers can ask whether a cursor moved, restore a saved position, or pin/unpin it while reading payload. This is critical because writes may rebalance pages and invalidate raw page pointers.

Shared-cache builds add mutex and table-lock APIs: `sqlite3BtreeLockTable()`, `sqlite3BtreeEnter()`, `sqlite3BtreeLeave()`, `sqlite3BtreeEnterAll()`, `sqlite3BtreeLeaveAll()`, `sqlite3BtreeEnterCursor()`, `sqlite3BtreeLeaveCursor()`, `sqlite3BtreeSharable()`, and debug mutex assertions. Non-shared-cache builds macro many of these to no-ops, preserving call-site simplicity while avoiding unnecessary locking.

## Persistence Behavior

The header defines the stable interface for persistent database state: page size, reserved bytes, secure-delete behavior, auto-vacuum mode, header metadata, schema cookies, file-format version, largest root page, and text encoding. `BTREE_AUTOVACUUM_NONE`, `BTREE_AUTOVACUUM_FULL`, and `BTREE_AUTOVACUUM_INCR` are persisted through header metadata and interpreted by the implementation to decide whether pointer-map pages and truncation work are required. `BTREE_DATA_VERSION` is explicitly virtual: it is read like metadata but computed by the pager rather than stored directly in the database header.

Table/index b-tree type flags determine on-disk cell semantics. `BTREE_INTKEY` is used for SQL rowid tables and stores a 64-bit integer key with separate payload. `BTREE_BLOBKEY` is used for indexes and WITHOUT ROWID tables, where the key itself encodes the record identity and content. Insert/delete flags provide persistence hints but must not weaken correctness; for example, `BTREE_APPEND` may optimize append paths but cannot assume the caller's prediction is true.

## Dependencies and Integration Points

`btree.h` depends on core SQLite types such as `sqlite3`, `sqlite3_vfs`, `Pgno`, `Pager`, `KeyInfo`, `UnpackedRecord`, `Mem`, `sqlite3_value`, `Schema`, and `BtCursor`, most of which are declared through `sqliteInt.h` and related internal headers. It is consumed broadly by the VDBE, schema builder, pager-facing code, integrity-check code, backup API, incremental blob API, WAL checkpoint paths, and shared-cache locking logic.

The file connects directly to `build.c`: schema-building code uses `BTREE_FILE_FORMAT`, `BTREE_TEXT_ENCODING`, and `BTREE_SCHEMA_VERSION` in generated `OP_ReadCookie`/`OP_SetCookie` opcodes; table/index creation emits `OP_CreateBtree` with `BTREE_INTKEY` or `BTREE_BLOBKEY`; temporary databases are opened with `sqlite3BtreeOpen()` and configured with `sqlite3BtreeSetPageSize()`; read-only checks use `sqlite3BtreeIsReadonly()`.

## Risks and Edge Cases

The API is sensitive to transaction state and mutex discipline. Cursor operations against moved or invalidated pages must use restore and movement checks correctly or risk reading wrong data after rebalance or concurrent shared-cache changes. The `BTREE_FORDELETE` flag is only a hint for alternative storage engines; SQLite's native engine ignores it, so callers must not depend on it for semantic behavior.

Metadata index constants are part of the database file contract. Changing them would corrupt interpretation of the database header and break compatibility. `BTREE_DATA_VERSION` is a special virtual meta-value in the same API space, so implementation and callers must avoid treating every meta index as a writable header field.

Compile-time feature gates can remove WAL, shared-cache mutex calls, incremental blob support, cursor hints, mmap limit support, and test/debug APIs. New code using this interface must honor the same guards or it will break reduced builds.

## Test Signals

Good test coverage should exercise DDL paths that create rowid tables, indexes, WITHOUT ROWID tables, temp tables, and auto-vacuum databases because those paths use different btree flags and metadata. Transaction tests should cover begin/commit phase split, rollback, savepoints, statement rollback, WAL checkpointing, and backup interactions. Cursor tests should include payload fetch across overflow pages, cursor movement after inserts/deletes, `BTREE_APPEND`, `BTREE_SAVEPOSITION`, incremental blob reads/writes, and shared-cache table locks. Integrity-check tests should call through `sqlite3BtreeIntegrityCheck()` and verify corruption detection for duplicate pages, orphaned pages, malformed overflow chains, and bad root-page metadata.
