# sources/storage-engines/sqlite/test/fuzzcheck.c

## Purpose
`fuzzcheck.c` is SQLite's broad fuzz-regression harness. It stores and runs fuzz cases from source databases with `db`, `xsql`, and `readme` tables; imports new SQL, database, and dbsqlfuzz cases; exports cases; runs database-image fuzzing through an in-memory VFS; runs combined database-plus-SQL dbsqlfuzz inputs; checks crashes, assertion failures, timeouts, memory leaks, and optional query invariants.

## Important APIs, Types, and Functions
- Data models: `VFile`/`VHandle` implement the in-memory VFS, `Blob` stores loaded database images or SQL scripts, and global `g` tracks source database name, VFS files, loaded blob lists, PRNG seed, invariant count, and current test name.
- Utility functions: `fatalError()`, `signalHandler()`, `setAlarm()`, `safe_realloc()`, `readFile()`, SQL scalar helpers `readfileFunc()`, `readtextfileFunc()`, `writefileFunc()`, `pathTail()`, `integerValue()`, and `numberOfVChar()`.
- Corpus management: `blobListLoadFromDb()`, `blobListFree()`, `rebuild_database()`, `isDbSql()`, and `isDbSqlFunc()`.
- dbsqlfuzz path: `FuzzCtx`, `decodeDatabase()`, `isOffset()`, `runCombinedDbSqlInput()`, `block_troublesome_sql()`, `runDbSql()`, `bindDebugParameters()`, `toggleDbConfig()`, `recoverDatabase()`, and `recoverSqlCb()`.
- In-memory VFS path: `formatVfs()`, `reformatVfs()`, `createVFile()`, `inmem*` VFS methods, `inmemRandomness()`, and `inmemVfsRegister()`.
- External extension hooks include `sqlite3recover`, `fuzz_invariant`, `sqlite3_dbdata_init`, `sqlite3_vt02_init`, and many extension init functions (`series`, `regexp`, `sha`, `decimal`, etc.).

## Control Flow
Startup enables URI and memory-status support, registers an OOM simulator, initializes SQLite, installs Unix signal handlers, registers the in-memory VFS as default, and parses many CLI options. For each source database, it opens or creates the corpus database, optionally handles metadata/info/import/export/rebuild operations, loads SQL scripts and database blobs into linked lists, closes the source database, resets SQLite memory configuration, formats the in-memory VFS, and runs tests.

For ordinary SQL/database pairs, it creates `main.db` in the VFS from each database blob, opens it, applies limits and optional pragmas, enables test/internal functions, installs progress handlers for SQL fuzz or VDBE limits, seeds PRNG deterministically, runs the SQL script with `runSql()`, closes the connection, checks memory use, and reformats the VFS.

For dbsqlfuzz inputs, `runCombinedDbSqlInput()` decodes a hex database recipe up to the `\n--\n` separator, optionally renders a CLI reproduction script, opens an anonymous database, applies optimization and dbconfig bits encoded in database bytes 72..79, sets limits and hard heap caps, deserializes the decoded database, installs an authorizer that blocks dangerous/debug SQL, activates extension modules, runs recovery, splits SQL at complete statement boundaries, executes statements with `runDbSql()`, and checks memory cleanup.

## State and Persistence Behavior
The source corpus database persists imported `db`, `xsql`, and `readme` rows. Test execution state is transient: loaded `Blob` lists, in-memory VFS files, deserialized databases, hard/soft heap limits, alarm timers, PRNG seed, OOM counters, and progress context. Import and rebuild modes write to the source database inside transactions and vacuum it. Export modes write selected blobs to filesystem paths through the `writefile()` SQL function.

The custom VFS stores up to `MX_FILE` files, enforces `MX_FILE_SZ`, reference-counts open handles, deletes anonymous files on close, and uses deterministic randomness from `g.uRandom`. After each test it verifies all VFS files are closed and all SQLite memory is released.

## Dependencies and Integration Points
This file depends on public SQLite APIs, internal test controls, SQLite recovery APIs, dbdata/dbptr virtual tables, optional carray binding, many extension initialization functions, the in-memory VFS contract, Unix signals, and SQLite's memory allocator configuration. It is a central integration point for fuzz corpora generated by dbsqlfuzz, OSS-Fuzz, SQL fuzzers, and external database mutators.

## Risks and Edge Cases
The harness intentionally executes malformed SQL and corrupted database images, so containment is critical. Authorizer rules block debug pragmas, high busy timeouts, and unsafe `ATTACH`, but allow in-memory and memdb attaches. Progress handlers and alarms mitigate infinite loops; heap, length, depth, VDBE-op, LIKE-pattern, and database-size limits bound resource usage. OOM simulation replaces SQLite's allocator globally and must be registered before allocation. Memory accounting failures are fatal, so every extension and test path must clean up.

Potential pitfalls include fixed-size VFS limits, unsigned/offset handling in dbsqlfuzz decode recipes, dbconfig/optimization bits encoded in fuzz input bytes, noisy timeout behavior, and query invariant checks that are skipped when statements use non-deterministic or aggregate/window functions. The source database may be opened read-write for import/rebuild/message operations, so option parsing directly affects persistence.

## Test Signals
Primary pass criteria are zero crashes, zero fatal signals, zero timeouts beyond configured limits, zero memory leaks, successful close of every SQLite connection, and summary output reporting zero errors. Additional signals include invariant-check counts, brief/slice summaries, spinner progress, exported reproducer scripts, simulated `TEST_FAILURE` behavior for automation validation, and verbose SQL/result traces.
