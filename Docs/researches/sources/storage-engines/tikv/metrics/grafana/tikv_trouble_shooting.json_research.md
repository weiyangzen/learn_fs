# sources/storage-engines/tikv/metrics/grafana/tikv_trouble_shooting.json

## Purpose
Generated Grafana dashboard `Test-Cluster-TiKV-Trouble-Shooting` (`uid` `Lg4wiEkZz`) for symptom-oriented TiKV operations. It organizes Prometheus views for hot read/write, leader drops, channel full events, busy server signals, slow reads, slow writes, RocksDB write stalls, OOM, and huge region diagnosis.

## Important Structures
The dashboard has standard Grafana metadata (`__inputs`, `__requires`, `annotations`, `templating`, `panels`, `time`, `refresh`, `timezone`, `schemaVersion`, `version`) and 80 panels: 10 row panels and 70 graph panels. It uses the `${DS_TEST-CLUSTER}` Prometheus datasource and a default `Annotations & Alerts` entry.

## Control Flow and State
Grafana resolves templating variables, then evaluates panel PromQL targets on refresh. Variables scope charts by `k8s_cluster`, `tidb_cluster`, `db`, `command`, and `instance`; several variables allow multi/all selection. Persistent state is the dashboard definition itself: UID, layout, panel queries, variable definitions, and schema metadata.

## Dependencies and Integration Points
Panels depend on TiKV, RocksDB, raftstore, scheduler, gRPC, coprocessor, process, and node-exporter metrics such as `tikv_thread_cpu_seconds_total`, `tikv_grpc_msg_duration_seconds_*`, `tikv_raftstore_*`, `tikv_engine_*`, `tikv_channel_full_total`, `process_resident_memory_bytes`, and `node_disk_*`. The file is regenerated by `scripts/gen-tikv-details-dashboard` and protected from manual drift by `scripts/check-dashboards` checksum validation.

## Risks and Test Signals
Metric or label drift can leave panels blank while JSON parsing still succeeds. Very high quantiles such as `0.999999` can be noisy on sparse histograms, and disk metrics rely on correct label alignment with TiKV scopes. Validation should include JSON parsing, Grafana import, representative PromQL execution, populated dropdowns, visible row panels, and a passing `./scripts/check-dashboards`.
