# sources/storage-engines/tikv/tests/integrations/raftstore/test_snap.rs

## Purpose
This integration test file validates raftstore snapshot generation, transport, application, garbage collection, and compatibility behavior. It exercises both classic raftstore and raftstore v2 where supported, with special emphasis on large/multi-file snapshots, stale snapshots, overlapping snapshots after split, column-family snapshots, tablet snapshots, snapshot precheck cancellation, snapshot I/O accounting, and snapshot-backed raft log cleanup.

## Important APIs, Types, and Functions
The file is built around `test_raftstore::*` cluster helpers, `PdClient` peer operations, raft `MessageType::MsgSnapshot`, `RaftMessage`, `RaftSnapshotData`, `SnapManager`, and the server snapshot senders `tikv::server::snap::send_snap` and `tikv::server::tablet_snap::send_snap`. Local test filters include `StaleSnap`, `SnapshotAppendFilter`, and helper routines `send_a_large_snapshot`, `generate_snap`, and `check_observer`. `MockApplySnapshotObserver` implements `Coprocessor` and `ApplySnapshotObserver` to validate pre/post apply hooks and tablet snapshot paths.

## Control Flow
The tests typically configure aggressive raft log GC or snapshot size limits, start a cluster, write enough data to force log compaction or snapshots, add or remove peers through PD, and then use filters to delay, drop, duplicate, or mutate snapshot messages. `test_huge_snapshot` writes multi-megabyte data, adds followers, and confirms stale duplicate snapshot handling. `test_server_snap_gc_internal` drops snapshots to accumulate snap files, clears filters, waits for catch-up, then asserts snapshot directories are eventually empty. `test_concurrent_snap` and `test_concurrent_snap_v2` hold parent-region snapshots while splits create overlapping range snapshots. Precheck tests drop `MsgSnapGenPrecheckRequest`, remove peers, stop nodes, or step down leaders to ensure later snapshots are not blocked.

## State and Persistence Behavior
The tests inspect persisted raft log entries, snapshot directories, tablet snapshot filesystem paths, CF data after snapshot apply, and the raft/apply state used to construct manual snapshots. They verify stale snapshot application does not corrupt newly added peers, CF deletions survive snapshot catch-up and restart, snapshot application cleans old raft logs, tablet snapshots generated by v2 can be applied by v1 and later garbage-collected, and `ExtraRegionOverride` snapshots enforce region epoch, leader, and term checks.

## Dependencies and Integration Points
This file integrates raftstore, raftstore v2, PD mock scheduling, grpc snapshot streaming, server security managers, file-system snapshot directories, RocksDB/Titan options, I/O limiter statistics, coprocessor snapshot observer hooks, and `tikv_kv::Engine` snapshot APIs. It uses network filters from the test harness as the primary fault-injection mechanism.

## Risks
The tests are timing sensitive: many rely on sleeps, short GC intervals, receiving a particular filtered message, or waiting for snapshot directories to drain. The scenarios cover high-risk code paths where stale snapshot metadata, wrong snapshot term, pending snapshot precheck state, or tablet snapshot compatibility can cause data loss, stuck peer addition, or panics. Multi-file snapshot behavior is version-gated by simulated PD version, so regressions may be hidden if the compatibility matrix changes.

## Test Signals
Strong signals include `must_get_equal` / `must_get_none` on follower engines, explicit snapshot directory counts, raft log emptiness after apply/destroy, nonzero I/O limiter replication/load-balance stats, observer path matches, grpc send completion, and request errors for stale term/epoch/not-leader cases. The file also exercises both node and server clusters and v1/v2 variants for many snapshot paths.
