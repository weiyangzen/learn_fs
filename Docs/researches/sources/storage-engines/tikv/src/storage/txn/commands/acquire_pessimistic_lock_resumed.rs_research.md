# sources/storage-engines/tikv/src/storage/txn/commands/acquire_pessimistic_lock_resumed.rs

## Purpose
Handles pessimistic-lock requests that were previously blocked in the lock manager and later resumed. It reconstructs command input from `LockWaitEntry` records and retries lock acquisition for each queued key while preserving wait tokens and request cancellation state.

## Important APIs, Types, and Functions
`ResumedPessimisticLockItem` carries the key, existence assertion, `PessimisticLockParameters`, `LockWaitToken`, and shared request state. `AcquirePessimisticLockResumed` is generated by `command!` and returns `StorageResult<PessimisticLockResults>`. `from_lock_wait_entries` converts lock-manager queue entries into a typed command. `process_write` calls the shared `acquire_pessimistic_lock` action and reuses `acquire_pessimistic_lock::make_write_data` to package MVCC writes and optional old values.

## Control Flow
The write path groups work by transaction start timestamp: when an item has a different `params.start_ts`, it flushes the previous `MvccTxn` modifies and reader statistics, then builds a new `MvccTxn` and `SnapshotReader`. Each key is retried. Success appends a `PessimisticLockKeyResult` and records old values when `ExtraOp::ReadOldValue` is active. `KeyIsLocked` or shared-lock shrink-mode failures are converted back into `WriteResultLockInfo` so the scheduler can wait again using the original token. Other MVCC errors become per-key failed results.

## State and Persistence
Successful locks produce lock-CF modifies and `new_acquired_locks`; encountered locks are not persisted but are returned to lock-wait handling. The response policy is `OnProposed`, matching pessimistic lock pipelining semantics. The command is latch-protected over all item keys and reports write bytes as encoded key sizes.

## Dependencies and Integration Points
Integrates with `lock_manager::lock_waiting_queue`, `LockWaitContextSharedState`, MVCC pessimistic lock action code, old-value collection, and scheduler `WriteResult` wait handling. It depends on the first resumed item context for the command context.

## Risks and Test Signals
The main risks are rebuilding txn/reader state across mixed start timestamps, retaining the correct wait token when a resumed key blocks again, and starvation around shared locks not in shrink mode. Tests cover successful resumed locking, mixed transaction timestamps, value/conflict returns, repeated waiting, and token/lock-info consistency.
