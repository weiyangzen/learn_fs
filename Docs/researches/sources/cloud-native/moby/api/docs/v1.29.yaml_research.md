## Control Flow And API Behavior

The YAML is declarative, but it encodes user-visible daemon flows:

- Container lifecycle: list containers, create with `Config` plus `HostConfig` and `NetworkingConfig`, inspect, top/logs/changes/export/stats, resize, start/stop/restart/kill/update/rename, pause/unpause, attach, websocket attach, wait, delete, archive stat/download/upload, and prune. Create and inspect share many nested schemas, while update narrows to mutable `Resources` plus `RestartPolicy`.
- Container streaming: logs may return plain body data or a `101` hijacked stream when following; attach documents raw TCP connection hijacking, optional upgrade headers, and the 8-byte multiplexing frame format used when TTY is disabled. TTY mode switches to unframed raw PTY data.
- Filesystem transfer: export returns a container tarball; archive `HEAD` returns `X-Docker-Container-Path-Stat`; archive `GET` returns a tar stream; archive `PUT` uploads tar/gzip/bzip2/xz content into a container path and exposes read-only or directory/non-directory conflict errors.
- Image lifecycle: list, build from tar or remote context, pull/import, inspect, history, push, tag, delete, search, prune, commit, save one or many images, and load image tarballs. Build is cancellable by client disconnect and accepts Dockerfile location, tags, remote contexts, cache options, resource limits, labels, network mode, content type, and registry auth config.
- System endpoints: auth, info, version, ping, event stream, and disk-usage reporting expose daemon identity, platform/driver/cgroup/security options, registry config, API version bounds, experimental state, real-time event filtering, and aggregate image/container/volume disk usage.
- Exec flow: `POST /containers/{id}/exec` creates an exec instance, `POST /exec/{id}/start` starts it using raw-stream output unless detached, `POST /exec/{id}/resize` changes TTY dimensions, and `GET /exec/{id}/json` inspects running state, exit code, process config, open streams, container ID, and PID.
- Volume and network flows: volumes can be listed, created, inspected, removed, and pruned; networks can be listed, inspected, created, removed, connected, disconnected, and pruned. Filters are JSON-encoded maps; connect/disconnect operations bind containers to endpoint settings and reject unsupported swarm-scoped operations where applicable.
- Plugin flow: list, fetch privileges, pull/install with accepted privileges and registry auth, inspect, remove, enable, disable, upgrade, create from tar, push, and set mutable settings. Plugin endpoints mix local state transitions with remote registry access.
- Swarm flow: nodes can be listed, inspected, deleted, and updated with required version indexes; swarm can be inspected, initialized, joined, left, updated, unlocked, and queried for unlock keys; services can be listed, created, inspected, deleted, and updated. Update endpoints require object versions to prevent stale writes.

## State And Persistence Behavior

The API contract exposes multiple daemon-managed state domains:

- Containers persist runtime state, process state, restart count, log paths, hostname/hosts/resolv files, graph-driver data, network endpoint state, mounts, anonymous volumes, resource limits, and changed filesystem contents. Delete and prune endpoints reclaim container state and optionally volumes.
- Images persist layers, tags, digests, history, graph-driver/rootfs metadata, build outputs, imported archives, committed container filesystems, and registry push/pull results. Image prune and delete reclaim image data; save/load move persistent image state through tar streams.
- Volumes persist independent storage under a driver and may outlive containers. `UsageData` records disk size and reference count where supported, while remove/prune conflict responses protect in-use volumes.
- Networks persist driver/IPAM/options/labels and endpoint attachment state. Network inspect includes attached containers and IP addresses; connect/disconnect mutate endpoint membership.
- Plugins persist installed plugin packages, rootfs/config metadata, enabled/running state, mutable settings, registry references, and accepted privileges. Enable/disable/upgrade/remove operations transition this local plugin state.
- Swarm state is strongly versioned. `ObjectVersion.Index` appears on nodes, swarm/cluster info, tasks, and services, and update endpoints require a `version` query parameter to protect concurrent writes. Swarm manager autolock introduces an unlock key; join tokens and manager unlock keys can be rotated on swarm update.
- Service and task state are orchestrator-managed. Service specs include task templates, replicated/global mode, update and rollback strategies, endpoint exposure, and networks; task status tracks desired/current state, timestamps, error messages, container status, node/service placement, and desired state.

## Risks And Edge Cases

- The file is both documentation and a generation source; an apparently small schema edit can break generated Go types, API clients, ReDoc rendering, or compatibility tests.
- Open-schema compatibility is intentional. Tightening request/response validation in generated clients would violate the documented expectation that extra response fields are ignored and extra request properties/query parameters are tolerated.
- Several schemas contain platform-specific or daemon-specific fields with subtle precedence, including Windows CPU control precedence, Linux mount propagation, restart backoff, healthcheck timing minimums, cgroup parent semantics, and namespace modes.
- Streaming endpoints are easy to misimplement because HTTP status may be `101` or `200`, attach/log/exec data can use raw hijacked TCP, and non-TTY streams require Docker's 8-byte frame header while TTY streams do not.
- Archive and image endpoints transfer tar streams whose formats are security-sensitive. Path handling, read-only roots, volume permissions, compression formats, whiteout files, and tar extraction directory conflicts are all part of the contract.
- Registry auth is passed in headers as base64 JSON and may contain credentials or identity tokens. Build and service creation also use registry auth for pulls; clients must avoid logging these headers.
- Swarm object updates depend on `ObjectVersion.Index`; missing or stale version values should fail rather than silently overwrite another writer's changes.
- YAML/schema correctness matters. In this chunk there are historical doc quirks such as TODO descriptions, mixed integer/string query encodings, generated extension fields, and examples with fields not fully represented by nearby schemas; tools consuming this file need to preserve documented compatibility behavior rather than treating examples as strict schemas.

## Purpose

The endpoints in this chunk expose swarm runtime observability and secret-management operations:

- service and task log endpoints let clients fetch stdout/stderr for swarm workloads, either as a bounded response body or as a hijacked raw stream;

## Important APIs And Types

- `ServiceUpdate` fragment: requires a `version` query integer to avoid conflicting writes, accepts `registryAuthFrom` with `spec` or `previous-spec`, accepts a `rollback` query value of `previous`, and can receive `X-Registry-Auth` as a base64-encoded registry auth header.
- `GET /services/{id}/logs` with operation ID `ServiceLogs`: returns service `stdout`/`stderr` logs. It produces `application/vnd.docker.raw-stream` for upgraded streaming and `application/json` for non-upgraded response handling.
- `GET /tasks` with operation ID `TaskList`: returns an array of `#/definitions/Task`. The example task shape includes `ID`, `Version.Index`, timestamps, `Spec`, `ServiceID`, `Slot`, `NodeID`, `Status`, `DesiredState`, and `NetworksAttachments`.
- `GET /tasks/{id}` with operation ID `TaskInspect`: returns a single `Task` by ID.
- `GET /tasks/{id}/logs` with operation ID `TaskLogs`: mirrors service log behavior for one task.
- `GET /secrets` with operation ID `SecretList`: returns an array of `#/definitions/Secret`.
- `POST /secrets/create` with operation ID `SecretCreate`: consumes a `SecretSpec` body and returns a `201` object containing the created secret `ID`. The example body includes `Name`, `Labels`, and base64 `Data`.
- `GET /secrets/{id}` with operation ID `SecretInspect`: returns a `Secret`.
- `DELETE /secrets/{id}` with operation ID `SecretDelete`: deletes a secret and returns `204` on success.
- `POST /secrets/{id}/update` with operation ID `SecretUpdate`: accepts a `SecretSpec` body and a required `version` query value. The description says only `Labels` can currently be updated; all other fields must remain unchanged from `SecretInspect`.

Referenced schema definitions in this range are `Task`, `Secret`, `SecretSpec`, and `ErrorResponse`.

## Control Flow

The service and task log endpoints use the same request flow. The client identifies the service or task with a path `id`, selects log streams with `stdout` and/or `stderr`, optionally includes contextual `details`, filters by `since`, controls timestamp decoration with `timestamps`, and limits output with `tail`. If `follow=true`, the server returns `101 Switching Protocols` with a connection upgrade and then hijacks the HTTP connection to stream Docker's raw multiplexed output. Without follow, successful output is represented as a `200` string response body.

Task listing accepts an optional `filters` query parameter encoded as JSON `map[string][]string`. The documented filters narrow scheduler objects by desired state, task ID, label, task name, node, or service. Task inspection is a direct path lookup by task ID.

Secret creation consumes a JSON `SecretSpec` and produces a newly allocated secret ID. Secret inspection and deletion are path-ID operations. Secret update is a versioned write: clients are expected to inspect the current secret, preserve immutable fields, change only labels, and submit the current object version so the daemon can reject stale writes.

Error flow is consistent across the swarm endpoints: `404` identifies missing resources, `500` covers daemon/server errors, and `503` signals that the target node is not part of a swarm. `SecretCreate` adds `409` for name conflicts.

## State And Persistence Behavior

The YAML itself has no runtime state. It describes daemon operations that read or mutate swarm state:

- task and service log endpoints read log data from task containers through supported logging drivers and may keep a connection open when following;
- task list/inspect endpoints read swarm manager task state, including task versions, desired state, runtime status, container status, and network attachments;
- secret list/inspect read swarm secret metadata and specs;
- secret create persists a new swarm secret object, including secret data supplied in `SecretSpec.Data`;
- secret delete removes a swarm secret object;
- secret update mutates secret metadata under optimistic concurrency, with labels documented as the only mutable field in this API version.

The log endpoints explicitly depend on `json-file` or `journald` logging drivers. The secret update `version` parameter and service update `version` parameter are concurrency guards for persisted swarm objects.

## Risks And Edge Cases

- The chunk starts inside `ServiceUpdate`, so whole-operation conclusions for service update require the preceding lines. This range still captures the important version, rollback, registry-auth, and tag fields.
- `follow=true` changes response handling from normal HTTP body consumption to connection hijacking. Client generators that treat `101` like a JSON response will mishandle streamed logs.
- The service/task log descriptions say logs work only with `json-file` or `journald`; callers may receive errors or empty behavior with other logging drivers.
- `stdout` and `stderr` both default to `false`. Clients that omit both may not get useful log output unless daemon-side behavior chooses defaults outside this spec.
- `tail` is typed as a string because it accepts either an integer or `all`, so client validation must not force it to a numeric-only type.
- `filters` is a JSON-encoded string, not a structured query object. Incorrect escaping or incompatible `map[string][]string` encoding can silently broaden or break task/secret list queries.
- The task log endpoint lacks a `tags: ["Task"]` line in this displayed range, unlike nearby endpoints. If absent in the full file, generated documentation/client grouping may be inconsistent.
- Secret update accepts a full `SecretSpec` but only labels are mutable. Sending a spec built from partial local state risks rejection or unintended incompatibility because non-label fields must match `SecretInspect` response values.
- Secret creation can return `409` on name conflict; clients need create-or-get or retry behavior to be explicit.
- Secrets are swarm-scoped; all secret endpoints can fail with `503` when the daemon is not in a swarm, which is a deployment-state error rather than a missing-route error.
