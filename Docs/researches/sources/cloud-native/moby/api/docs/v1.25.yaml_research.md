# sources/cloud-native/moby/api/docs/v1.25.yaml

## Purpose

This file is the Swagger 2.0/OpenAPI contract for Docker Engine API version 1.25, exposed under `basePath: /v1.25` and served over HTTP or HTTPS. The header comments state that it is used to generate API documentation and the types used by Docker client/server code, so changes here affect both the public API reference and generated Go-facing data contracts. The spec documents Docker Engine 1.13-era behavior, including version negotiation guidance, open-schema compatibility expectations, registry authentication via `X-Registry-Auth`, and Redoc menu grouping through tags.

The file is organized as reusable schema `definitions` followed by `paths`. It covers the main Engine resources: containers, images/builds, system information/events, exec sessions, volumes, networks, plugins, swarm nodes, swarm cluster operations, services, tasks, and secrets.

## Important APIs, Types, and Schemas

Core schema definitions model the daemon's persistent and runtime objects:

- Container configuration: `Config`, `HostConfig`, `Resources`, `RestartPolicy`, `Mount`, `MountPoint`, `DeviceMapping`, `ThrottleDevice`, `Port`, `NetworkConfig`, and `EndpointSettings`.
- Image data: `Image`, `ImageSummary`, `ImageHistoryResponseItem`, `GraphDriver`, `BuildInfo`, `CreateImageInfo`, `PushImageInfo`, and `ImageDeleteResponse`.
- Registry and errors: `AuthConfig`, `ErrorResponse`, `ErrorDetail`, `ProgressDetail`, and `IdResponse`.
- Storage and networking: `Volume`, `Network`, `IPAM`, and `NetworkContainer`.
- Plugins: `Plugin`, `PluginMount`, `PluginDevice`, `PluginEnv`, and `PluginInterfaceType`.
- Swarm mode: `NodeSpec`, `Node`, `SwarmSpec`, `ClusterInfo`, `TaskSpec`, `TaskState`, `Task`, `ServiceSpec`, `EndpointPortConfig`, `EndpointSpec`, `Service`, `ServiceUpdateResponse`, `SecretSpec`, and `Secret`.

`HostConfig` uses `allOf` to compose the generic `Resources` schema with host-dependent container settings. `ContainerCreate` similarly composes portable `Config` with `HostConfig` and `NetworkingConfig`. Swarm update APIs use explicit `version` query parameters tied to object `Version.Index` fields, making optimistic concurrency part of the public contract for nodes, swarm settings, and services.

The operation surface is broad. Container operations include list/create/inspect/top/logs/changes/export/stats/resize/start/stop/restart/kill/update/rename/pause/unpause/attach/websocket attach/wait/delete/archive/prune. Image operations include list/build/create/pull/import/inspect/history/push/tag/delete/search/prune/commit/export/load. System operations include auth, info, version, ping, events, and disk usage. Additional resource groups expose exec, volume, network, plugin, node, swarm, service, task, and secret operations.

## Control Flow and Request Patterns

The spec encodes several multi-step workflows rather than single high-level commands:

- Running a container is split across `ContainerCreate`, optional `ContainerAttach` or `ContainerAttachWebsocket`, `ContainerStart`, `ContainerWait`, and optional cleanup through `ContainerDelete`.
- Exec is explicitly two-phase: `ContainerExec` creates an exec instance and returns an ID, then `ExecStart` attaches or detaches execution; `ExecResize` and `ExecInspect` manage the resulting session.
- Image build and registry operations are connection-sensitive streams. `ImageBuild`, `ImageCreate`, and `ImagePush` describe cancellation when the client connection closes, tying daemon work lifecycle to HTTP connection state.
- Container archive APIs model filesystem transfer as `HEAD` metadata via `X-Docker-Container-Path-Stat`, `GET` tar export, and `PUT` tar extraction with overwrite and read-only-volume error cases.
- Swarm operations follow cluster lifecycle flow: `SwarmInit`, `SwarmJoin`, `SwarmInspect`, `SwarmUpdate`, token/key rotation, `SwarmUnlockkey`, `SwarmUnlock`, and `SwarmLeave`.
- Service lifecycle is `ServiceCreate`, `ServiceInspect`, `ServiceUpdate`, `ServiceLogs`, and `ServiceDelete`, with task listing/inspection as the scheduling-result view.

Streaming and hijacking are first-class parts of the contract. `ContainerAttach` documents raw HTTP connection hijacking and the Docker multiplexed stream frame format: an 8-byte header containing stream type and big-endian payload size followed by payload bytes. TTY mode changes this behavior to an un-multiplexed raw PTY stream. `ContainerLogs`, `ServiceLogs`, `ContainerStats`, `SystemEvents`, `ExecStart`, and attach endpoints all require client code and tests to handle long-lived responses, binary content, upgrade status `101`, and regular `200` fallback behavior.

## State and Persistence Behavior

Most write APIs mutate daemon-managed state:

- Containers are created, started, stopped, restarted, killed, paused, unpaused, renamed, updated, deleted, archived into, and pruned. `HostConfig` exposes durable host-level behavior such as restart policy, logging driver, network mode, mounts, devices, cgroup settings, security options, namespace settings, and resource controls.
- Images are built, pulled/imported, tagged, pushed, removed, pruned, committed from containers, exported, and loaded. Image metadata includes layer roots, graph driver data, repository tags/digests, size accounting, and build history.
- Volumes and networks are persistent named resources with inspect/list/create/delete/prune flows. Volumes include driver options, labels, scope, usage data, and in-use conflict handling. Networks include IPAM, containers, labels, options, and pre-defined network restrictions.
- Plugins have install/create/enable/disable/configure/push/delete operations and contain rootfs, interface, Linux capability, mount, device, environment, and user settings. Pulling requires privilege acceptance in the request body.
- Swarm, nodes, services, tasks, and secrets are cluster-scoped state. Swarm specs include Raft snapshot/heartbeat/election settings, CA and external CA configuration, manager autolock, task defaults, join tokens, unlock keys, and object versions. Secrets carry base64-url-safe data in `SecretSpec`, but inspect examples omit data, reflecting secret redaction expectations.

The API consistently uses JSON-encoded query `filters` as `map[string][]string` for list and prune endpoints. Clients must preserve open-schema behavior: the introduction says servers may add response properties and ignore extra query/body properties, so generated clients should tolerate unknown fields.

## Dependencies and Integration Points

This YAML depends on Swagger 2.0 conventions, Docker-specific vendor extensions such as `x-go-name` and `x-nullable`, Redoc rendering behavior, and Docker's generated API tooling. References are internal `$ref` links under `#/definitions/...`; breakage in a definition name can cascade into generated client/server types and rendered documentation.

Runtime integration points implied by the contract include:

- Docker daemon HTTP routing and versioned URL prefixing under `/v1.25`.
- Registry authentication headers for build, pull, push, plugin pull, service create, and service update.
- Storage drivers and graph drivers for image/container metadata and tar export/import.
- Logging drivers for container and service logs, with explicit support limited to `json-file` and `journald` on those endpoints.
- Linux cgroups, namespace, mount propagation, OOM, blkio, CPU, memory, pid, and ulimit controls; plus Windows-specific CPU, isolation, console size, and disk quota options.
- SwarmKit-style cluster objects, Raft configuration, dispatcher heartbeat, CA signing, join tokens, unlock keys, service reconciliation, and task state transitions.
- Network and volume plugin drivers, including plugin privilege acceptance and plugin rootfs tar import.

## Risks and Edge Cases

Several risks are visible in the spec itself:

- Some schema descriptions are marked `TODO` or have inconsistencies, such as `NetworkConfig` and archive header descriptions. These weaken generated documentation and can hide contract ambiguity.
- There are likely schema drift issues: `Secret.Spec` references `ServiceSpec` instead of `SecretSpec`, `ServiceUpdate` returns `ImageDeleteResponse` even though `ServiceUpdateResponse` is defined, and `NetworkPrune` names its deleted-network field `VolumesDeleted`.
- Multiple fields have loose or surprising types. Examples include JSON-encoded query strings, binary bodies represented as strings, `buildargs` typed as integer despite being described as a JSON map, and `ProgressDetail.message` typed as integer.
- The API exposes powerful host controls: privileged containers, host namespaces, device mounts, cgroup tuning, bind mounts, sysctls, plugin privileges, swarm join tokens, manager unlock keys, and registry credentials. Client/server tests must treat these as security-sensitive paths.
- Streaming endpoints require different behavior for TTY and non-TTY modes, 101 upgrade versus 200 hijack fallback, binary frame parsing, cancellation on disconnect, and unbounded event/log/stat streams.
- Versioned update APIs can fail if clients omit or stale the `version` query parameter. Tests should verify conflict avoidance behavior for node, swarm, and service updates.
- Open-schema compatibility means strict JSON decoders or generated clients that reject unknown fields would violate the documented contract.

## Test Signals

Good validation for this file should include both spec-level and generated-behavior tests:

- Swagger validation succeeds, all `$ref` targets resolve, operationIds remain unique, and path/tag groupings render correctly.
- Generated client/server models preserve `x-nullable`, required fields, `allOf` composition, enum values, path/query/header/body parameter placement, binary content types, and response status codes.
- Container lifecycle tests cover create/start/inspect/logs/stats/attach/wait/delete plus error statuses for missing containers, already-started/stopped cases, paused exec, and archive read/write errors.
- Stream protocol tests cover attach frame parsing, TTY raw mode, WebSocket attach, log follow, service logs, events, stats with `stream=false`, and client disconnect cancellation during build/pull/push.
- Registry auth tests cover `X-Registry-Auth` and `X-Registry-Config` base64 JSON for image and service/plugin operations.
- Persistence tests cover image build/load/save/delete/prune, volume create/delete/prune conflict behavior, network create/connect/disconnect/delete/prune, plugin enable/disable/set/delete, and system data-usage accounting.
- Swarm tests cover init/join/leave/update with required version parameters, token/key rotation, locked-manager unlock, node update/delete, service create/update/delete/logs, task list/inspect filters, and secret create/inspect/delete behavior.
- Compatibility tests should feed unknown response fields and extra request fields to generated clients/handlers to ensure the documented open-schema model is honored.
