# sources/cloud-native/moby/api/docs/v1.26.yaml

## Purpose
Swagger 2.0/OpenAPI contract for Docker Engine API v1.26, the Docker Engine 1.13.1-era HTTP API exposed under `/v1.26`. The file is both human documentation for ReDoc and a machine-readable contract used to generate client/server-facing API types, so its schemas, `operationId` names, status codes, examples, and vendor extensions are part of the compatibility surface.

## Important APIs, Types, And Operations
Top-level API groups are `Container`, `Image`, `Network`, `Volume`, `Exec`, `Plugin`, `System`, `Swarm`, `Node`, `Service`, `Task`, and `Secret`. Container operations cover listing, create/inspect, process listing, logs, filesystem diffs/export/archive, stats, resize, lifecycle transitions, update, rename, pause/unpause, attach over hijacked HTTP or websocket, wait, delete, prune, and exec creation. Image operations cover list, build, pull/import, inspect/history, push, tag, delete, search, prune, commit, save/load, and multi-image export. System endpoints include auth validation, info, version, ping, events, and data-usage reporting. Swarm-mode endpoints cover node, swarm, service, task, and secret list/inspect/create/update/delete flows.

Core definitions include container/configuration objects (`Config`, `HostConfig`, `Resources`, `RestartPolicy`, `Mount`, `MountPoint`, `EndpointSettings`, `ContainerSummary`), image objects (`Image`, `ImageSummary`, `ImageHistoryResponseItem`, `GraphDriver`, `ImageDeleteResponse`), registry/auth and progress objects (`AuthConfig`, `BuildInfo`, `CreateImageInfo`, `PushImageInfo`, `ErrorResponse`, `IdResponse`), storage/network objects (`Volume`, `Network`, `IPAM`, `NetworkContainer`), plugin objects (`Plugin`, `PluginMount`, `PluginDevice`, `PluginEnv`, `PluginInterfaceType`), and swarm objects (`NodeSpec`, `Node`, `SwarmSpec`, `ClusterInfo`, `TaskSpec`, `TaskState`, `Task`, `ServiceSpec`, `EndpointSpec`, `Service`, `SecretSpec`, `Secret`). `x-go-name`, `x-nullable`, required lists, `allOf`, enums, integer formats, and examples guide generated Go/API models as much as the prose does.

## Control Flow
The API is resource-oriented but many operations are multi-step client workflows. Running a container requires create, optional attach, start, wait/logs/stats, and eventual stop/delete. Exec follows create (`POST /containers/{id}/exec`), start (`POST /exec/{id}/start`), optional resize, then inspect. Image build streams build context to the daemon, validates the Dockerfile, executes instructions sequentially, and cancels if the client drops the connection; pull, push, import, save, and load are also stream-oriented. Service and swarm updates require the current object `version` query parameter to avoid conflicting writes.

Streaming and connection-upgrade behavior is a major contract detail. Logs with `follow`, container attach, exec start, service logs, stats, and events can be long-lived streams. Attach specifies Docker's raw stream multiplexing: without TTY, frames have an 8-byte header with stream id and big-endian payload size; with TTY, bytes are raw PTY data. Archive endpoints use tar streams plus `X-Docker-Container-Path-Stat` for base64 JSON metadata. Many list endpoints accept JSON-encoded filter maps in query strings, so clients must serialize filter state exactly as the daemon expects.

## State And Persistence
The endpoints expose and mutate daemon-managed state: containers, local images and layers, tags/digests, volumes, networks/endpoints, plugins, swarm cluster objects, node membership, services, tasks, and secrets. Persistent host paths surface through inspect responses such as `DockerRootDir`, container `LogPath`, `ResolvConfPath`, graph-driver data, volume `Mountpoint`, mount sources, image rootfs layers, and data-usage sizes. Prune and delete endpoints reclaim persisted container/image/volume/network state, while `force`, `noprune`, `v`, and prune filters change deletion scope.

Swarm state is version-indexed and includes Raft, dispatcher heartbeat, CA settings, manager autolock/encryption-at-rest, join tokens, unlock keys, service update status, task state, and secret specs. Secrets carry base64-url-safe data on create, but inspect examples omit payload content. Registry authentication is client-supplied through `X-Registry-Auth` or `X-Registry-Config`; identity tokens from `/auth` can replace username/password for registry-facing calls.

## Dependencies And Integration Points
This spec integrates with ReDoc, Swagger/OpenAPI tooling, Moby API generation, Docker CLI/client behavior, Docker registry authentication, Dockerfile builds, logging drivers, graph/storage drivers, cgroups, namespaces, mount propagation, network/IPAM plugins, volume drivers, plugin packaging/privilege acceptance, and swarmkit-style cluster objects. It uses standard HTTP status codes plus Docker-specific conventions such as `101` upgraded streams, `204` empty success, `304` already-started/stopped container states, and JSON `{"message": ...}` errors.

The document explicitly relies on an open schema model: newer daemons may add response properties and ignore unknown query/body fields. Clients generated from this version therefore need tolerant decoders. It also captures platform-specific behavior, including Windows-only resource/isolation fields, Unix-only `top` behavior, Linux cgroups freezer pause semantics, platform-specific mount defaults, and logging endpoints limited to `json-file` and `journald`.

## Risks And Edge Cases
Several schema issues are visible in the contract itself. Some examples include fields not declared in the nearby schema, such as plugin `Tag`/`Active`, container inspect fields like `KernelMemory`, and network/task attachment details. `Secret.Spec` references `ServiceSpec` instead of `SecretSpec`, and `ServiceUpdate` declares an `ImageDeleteResponse` response schema despite a `ServiceUpdateResponse` definition. `ProgressDetail.message` is typed as integer, `IPAM.Options` is modeled as an array of maps while examples use an object, and some descriptions contain stale TODOs or mismatched wording. Generators and validation tests should treat these as compatibility landmines rather than harmless documentation typos.

Operational risks include privileged container creation, host bind mounts, device mappings, user namespace/cgroup settings, plugin privileges, registry credentials in headers, build args explicitly not suitable for secrets, archive extraction into container filesystems, force deletion/removal, swarm token rotation, manager unlock keys, and secrets update constraints. Streaming clients must handle connection hijacking, proxy upgrade behavior, TTY versus non-TTY framing, dropped connections canceling builds/pulls/pushes, and indefinite event/stats/log streams. Versioned update flows can fail or overwrite intent if clients do not fetch and submit the correct object version.

## Test Signals
Useful validation signals include parsing the YAML as Swagger 2.0, resolving every `$ref`, checking generated types for expected `x-go-name` and nullable behavior, and diffing operation IDs/status codes against server routes for API v1.26. Contract tests should exercise list filter encoding, open-schema response tolerance, standard error bodies, auth header base64 handling, registry build/pull/push flows, image tar save/load compatibility, and prune/delete `force`/scope options.

Behavioral tests should cover container create-start-wait-delete, attach/logs/exec stream framing with and without TTY, stats/events stream termination, archive HEAD/GET/PUT and read-only filesystem errors, resource update warnings, logging-driver limitations, network create/connect/disconnect/prune, volume lifecycle and in-use conflicts, plugin pull privilege acceptance/enable/disable/remove, swarm init/join/leave/update with version conflicts and token rotation, service create/update/logs, task filtering, and secret create/inspect/update/delete constraints.
