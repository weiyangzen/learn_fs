# sources/cloud-native/buildkit/api/services/control/control_vtproto.pb.go

## Purpose

This file is generated by `protoc-gen-go-vtproto` for BuildKit's `moby.buildkit.v1` Control API protobuf messages. It adds vtprotobuf fast paths to the message structs defined in `control.pb.go`: deep cloning, equality comparison, size calculation, marshaling, and unmarshaling. The generated code is performance-oriented support code for the gRPC control surface declared in `control.proto`, not business logic.

The generated methods serve all message types in the Control service: cache and disk usage requests, solve requests and responses, status streaming payloads, session byte envelopes, worker list and info messages, build history records, OCI-like descriptors, result info, and exporter definitions.

## Important APIs, Types, and Functions

The file adds a consistent method family to each supported protobuf type:

- `CloneVT() *T` and `CloneMessageVT() proto.Message`: deep-copy messages, slices, maps, byte slices, timestamps, nested BuildKit protobuf messages, and `unknownFields`.
- `EqualVT(*T) bool` and `EqualMessageVT(proto.Message) bool`: compare typed messages including nested vtprotobuf messages and retained unknown fields.
- `MarshalVT() ([]byte, error)`, `MarshalToVT([]byte) (int, error)`, and `MarshalToSizedBufferVT([]byte) (int, error)`: encode messages using precomputed sizes and reverse buffer writes.
- `SizeVT() int`: compute encoded protobuf size, including unknown fields.
- `UnmarshalVT([]byte) error`: decode wire format into existing message values, preserving unknown fields and checking malformed input.

The generated coverage includes `PruneRequest`, `DiskUsageRequest`, `DiskUsageResponse`, `UsageRecord`, `SolveRequest`, `CacheOptions`, `CacheOptionsEntry`, `SolveResponse`, `StatusRequest`, `StatusResponse`, `Vertex`, `VertexStatus`, `VertexLog`, `VertexWarning`, `BytesMessage`, `ListWorkersRequest`, `ListWorkersResponse`, `InfoRequest`, `InfoResponse`, `BuildHistoryRequest`, `BuildHistoryEvent`, `BuildHistoryRecord`, `UpdateBuildHistoryRequest`, `UpdateBuildHistoryResponse`, `Descriptor`, `BuildResultInfo`, and `Exporter`.

The most integration-heavy messages are `SolveRequest`, `StatusResponse`, and `BuildHistoryRecord`. `SolveRequest` carries solver definitions, frontend metadata, cache options, entitlements, source policy, exporters, compatibility version, and proxy-network settings. `StatusResponse` batches streamed build progress as vertices, statuses, logs, and warnings. `BuildHistoryRecord` serializes long-lived build metadata, descriptors, result maps, counters, pinned state, errors, and timestamps.

## Control Flow

The clone path is direct field-by-field copying. Scalar fields are assigned, maps are rebuilt key by key, repeated slices are allocated to matching length, byte slices are copied, and nested messages call their own `CloneVT()` where available. `BuildHistoryRecord.Error`, a `google.rpc.Status`, uses an interface check for `CloneVT()` and falls back to `proto.Clone`.

The marshal path follows vtprotobuf's reverse-buffer pattern. Each `MarshalVT()` calls `SizeVT()`, allocates exactly that many bytes, then calls `MarshalToSizedBufferVT()`. Each `MarshalToSizedBufferVT()` starts from the end of the buffer, writes non-zero/non-empty fields in descending field order, prefixes length-delimited values with varints, and appends `unknownFields` at the end of the reverse-write sequence so they remain in the output.

The size path mirrors marshaling. It skips proto3 zero values, counts varint tag and length overhead with `protohelpers.SizeOfVarint`, delegates nested size calculations to `SizeVT()`, and includes `len(m.unknownFields)`.

The unmarshal path loops over protobuf wire records until the input is consumed. It decodes the tag varint, validates field number and wire type, decodes field payloads, initializes nested message pointers and maps as needed, appends repeated fields, and routes unknown fields through `protohelpers.Skip` into `m.unknownFields`. Malformed inputs return `protohelpers.ErrIntOverflow`, `protohelpers.ErrInvalidLength`, `io.ErrUnexpectedEOF`, or field-specific `fmt.Errorf` wire-type errors.

## State and Persistence Behavior

This file does not own durable storage or mutable service state. Its state behavior is confined to in-memory protobuf message mutation during cloning and unmarshaling, plus preservation of `unknownFields` for forward-compatible wire round trips.

`UnmarshalVT` mutates the receiver in place. Repeated string/message fields generally append to existing slices. Some singular `bytes` fields such as `BytesMessage.Data`, `VertexLog.Msg`, and `VertexWarning.Short` reuse existing backing storage via `append(m.Field[:0], ...)`, while repeated byte slices such as `VertexWarning.Detail` allocate a new byte slice per element. Nested message fields are allocated only when the incoming field is present and the current pointer is nil.

Map fields are initialized lazily and then assigned by decoded keys. Duplicate protobuf map entries take the last decoded value for the same key, matching normal protobuf map semantics. Because maps are serialized by ranging over Go maps, map entry wire order is not deterministic in this generated code.

Build history persistence is represented at the data-contract level through `BuildHistoryRecord`, `BuildHistoryEvent`, and `UpdateBuildHistoryRequest`, but the file only serializes those structures. Actual build history storage, filtering, updates, deletion, pinning, and finalization live in Control service implementations outside this generated file.

## Risks and Edge Cases

This is generated code, so manual edits would be fragile and should be avoided. Schema changes should happen in `control.proto` followed by regeneration.

Several equality methods intentionally treat nil nested messages as equal to empty messages in repeated fields by substituting zero-value structs before comparing. That can differ from pointer-sensitive application expectations.

`UnmarshalVT` appends repeated fields and unknown fields to the existing receiver. Reusing a message without resetting it can accumulate stale repeated values or unknown wire data. Singular byte fields are overwritten with reusable backing storage, which is efficient but means callers should not rely on retained old slice contents after unmarshaling into the same object.

Map marshaling order is non-deterministic because Go map iteration order is non-deterministic. This is acceptable for normal protobuf semantics but is a risk for byte-for-byte comparisons, content hashing of raw marshaled bytes, or golden files that expect deterministic map ordering.

The file contains multiple fallback paths for `google.rpc.Status` because not every external protobuf type is guaranteed to provide vtprotobuf methods. Those fallbacks use `proto.Clone`, `proto.Equal`, `proto.Marshal`, and `proto.Size`, so performance can vary for `BuildHistoryRecord.Error` compared with BuildKit-owned nested messages.

Malformed or adversarial wire input is bounded by explicit overflow, length, and EOF checks. The code still allocates based on encoded lengths for strings, bytes, maps, and nested messages, so callers must rely on higher-level gRPC/protobuf message size limits for resource control.

## Test Signals

These benchmarks are a performance signal for status-stream payloads, which are likely high-volume during builds.

Useful regression signals for this file are generated-code compilation, protobuf round-trip tests comparing `proto.Marshal`/`proto.Unmarshal` against `MarshalVT`/`UnmarshalVT`, equality and clone tests for maps/slices/bytes/nested timestamps, unknown-field preservation tests, and fuzzing of `UnmarshalVT` for malformed wire data. Since the source is generated, the most important practical test is that regeneration from `control.proto` remains reproducible and all packages depending on the Control API still compile.
