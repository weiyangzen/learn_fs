# sources/cloud-native/buildkit/api/types/worker.proto

Purpose: protobuf schema for BuildKit worker records. It is the authoritative contract that generates `worker.pb.go` and `worker_vtproto.pb.go`.

Important APIs/types/functions: `WorkerRecord` includes `ID`, `Labels`, repeated `pb.Platform`, repeated `GCPolicy`, optional `BuildkitVersion`, and repeated `CDIDevice`. `GCPolicy` models pruning constraints with `all`, `keepDuration`, `filters`, `reservedSpace`, `maxUsedSpace`, and `minFreeSpace`. `BuildkitVersion` records package, version, revision, and Dockerfile frontend version. `CDIDevice` records CDI device name, automatic allow behavior, annotations, and on-demand status.

Control flow: schema-only file; runtime behavior is generated by protoc. `import "github.com/moby/buildkit/solver/pb/ops.proto"` supplies platform messages.

State and persistence behavior: field numbers are the persistence contract. `reservedSpace` uses tag 3 because it was renamed from `freeBytes`, retaining wire compatibility with older clients.

Dependencies and integration points: package `moby.buildkit.v1.types` with Go package `github.com/moby/buildkit/api/types;moby_buildkit_v1_types`. Worker listing/control APIs and UI/status clients depend on this schema.

Risks: changing field numbers or reusing removed fields would break wire compatibility. Map fields affect deterministic serialization and vtproto generated equality/clone code. CDI additions need compatibility with worker capability reporting.

Test signals: validation is indirect through generated-code compilation and API compatibility tests. Schema changes should regenerate both standard protobuf and vtproto outputs.
