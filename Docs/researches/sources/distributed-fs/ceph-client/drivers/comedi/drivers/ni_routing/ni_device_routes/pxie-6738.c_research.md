# sources/distributed-fs/ceph-client/drivers/comedi/drivers/ni_routing/ni_device_routes/pxie-6738.c

## Purpose
This generated C table describes the set of signal routes that the Comedi NI routing layer should consider valid for the `pxie-6738` board. It exports `struct ni_device_routes ni_pxie_6738_device_routes`, whose `.device` string is `pxie-6738` and whose `.routes` field is an inline array of `struct ni_route_set` entries. The file answers "can this board expose a source-to-destination route"; the companion family route-value files answer "which register value encodes that route."

## Important APIs, Types, And Data
The only exported symbol is `ni_pxie_6738_device_routes`. Each route set contains a `.dest` NI global signal name and a sentinel-terminated `(int[]){ ... 0 }` list of `.src` signal names. The table covers 60 destination route sets: PFI 0-7, backplane `TRIGGER_LINE(0..7)`, counter source/gate/aux/A/B/Z/arm/sample-clock groups for counters 0-3, AO/DI/DO sample/start/pause/timebase routes, and `NI_WatchdogExpirationTrigger`. Source lists are mostly 41-49 entries for general routing destinations, 20-21 entries for sample-clock timebase destinations, and 8 entries for watchdog expiration.

## Control Flow
There is no executable control flow in this file beyond static initialization. Runtime lookup happens in `ni_routes.c`: `ni_find_valid_routes()` searches `ni_device_routes_list` by board name, `ni_count_valid_routes()` and `ni_get_valid_routes()` iterate each `routes[i]` until `.dest == 0`, and each `.src[j]` until source `0`. A route is only reported if this device table allows it and the selected family route-value table has a non-zero register encoding, including special indirect RTSI handling.

## State And Persistence
The data is compile-time static kernel data. It is not mutated or persisted to disk at runtime. The inline arrays must remain alive for the lifetime of the module, which is satisfied by static storage in the compiled object. Termination sentinels are part of the persistent in-memory contract.

## Dependencies And Integration Points
The file includes `../ni_device_routes.h` and `all.h`, depending on `struct ni_device_routes`, `struct ni_route_set`, and NI signal constants from `ni_routes.h`/Comedi UAPI. It is intended to be generated by `ni_routing/tools/convert_csv_to_c.py` from `csv/device_routes/pxie-6738.csv`. A notable integration risk is that the central `ni_device_routes.c` list currently inspected in this tree does not include `&ni_pxie_6738_device_routes`; unless another generated header/list revision adds it, `ni_assign_device_routes()` cannot discover this table by name.

## Risks
The table is large and repetitive, so omissions or off-by-one source sets are hard to review manually. Because it is board-specific, over-permissive routes can expose invalid user-visible `INSN_DEVICE_CONFIG_GET_ROUTES` results, while under-permissive routes can hide usable hardware paths. Sentinel loss would make lookup walk past array bounds. Source constants must stay inside the `NI_NAMES_BASE..NI_NAMES_BASE + NI_NUM_NAMES` range expected by conversion and route validation tooling.

## Test Signals
Useful tests are generator round trips from CSV to C, inclusion of the symbol in `ni_device_routes/all.h` and `ni_device_routes.c`, and `ni_routes_test` coverage that exercises assignment and valid-route enumeration. A PXIe-6738-specific assertion should check `ni_assign_device_routes(..., "pxie-6738", ...)` succeeds and that representative PFI, trigger-line, AO/DI/DO, and watchdog routes are counted only when matching route values exist.
