# sources/distributed-fs/ceph-client/drivers/comedi/drivers/ni_routing/ni_route_values/ni_660x.c

## Purpose
This generated-plus-annotated family table maps NI 660x signal route pairs to hardware register encodings. It describes what value should be written for supported 660x counter/timing routes after a device route table has declared a route valid.

## Important APIs, Types, And Data
The file exports `const struct family_route_values ni_660x_route_values` with `.family = "ni_660x"`. Its `register_values` matrix contains entries for high-numbered PFI lines, eight counter source/gate/aux groups, trigger lines, internal outputs, timebases, and logic-low routes. In the inspected source there are 544 destination rows and 496 marked source encodings by simple marker count: 336 `I(...)` entries and 160 `U(...)` entries, with no `V(...)` entries. `I()` compiles as valid in the kernel but remains "implemented, needs testing" in conversion tooling; `U()` is retained only for external conversion.

## Control Flow
There is no executable logic. Runtime code indexes the matrix with `B(src)` and `B(dest)`, checks for non-zero entries, and writes `UNMARK(value)` when programming a route. Several entries carry comments such as alternate register values, showing the table encodes maintenance uncertainty as comments plus `I/U` markers.

## State And Persistence
The table is immutable compiled data. No runtime mutation or persistence occurs. The maintenance state of route confidence is persisted in source markers and comments rather than in runtime structures.

## Dependencies And Integration Points
It includes `../ni_route_values.h` and `all.h`. `ni_660x.c` driver code assigns this family through `ni_assign_device_routes("ni_660x", ...)`, stores pointers in its private routing table, and uses generic route helper functions for source lookup and route programming.

## Risks
Most entries are `I()` rather than `V()`, so the table should be treated as implemented but not exhaustively hardware-validated. `U()` source values document possible hardware encodings that current kernel code does not implement; they disappear in normal builds, so runtime route counts will not match raw source-table size. Ambiguous comments such as `or 1` indicate hardware documentation uncertainty.

## Test Signals
Tests should cover 660x assignment, valid-route enumeration, and representative route programming for counter source, gate, aux, and PFI paths. Conversion tests should verify `U()` entries survive C-to-Python-to-CSV round trips even though they compile to zero in the kernel.
