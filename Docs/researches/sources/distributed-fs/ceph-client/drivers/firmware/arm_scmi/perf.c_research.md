# sources/distributed-fs/ceph-client/drivers/firmware/arm_scmi/perf.c

Purpose: implements the SCMI Performance protocol provider. It discovers performance domains and OPPs, exposes performance and DVFS operations to SCMI clients, supports optional fast channels for performance level and limit get/set, converts SCMI events into performance reports, and registers itself as `SCMI_PROTOCOL_PERF`.

Important APIs/types/functions: protocol commands include domain attributes, describe levels, limits set/get, level set/get, notifications, fast-channel description, and extended names. `struct perf_dom_info` stores per-domain capabilities, rate limit, sustained frequency/performance, multiplier, exported `scmi_perf_domain_info`, OPP array, optional fast-channel info, xarrays by level/index, and a hash by indicative frequency. `struct scmi_perf_info` stores global domain count, power scale, stats address/size, notification command availability, and domain array. Exported protocol ops include domain count/info, limit and level set/get, DVFS OPP add, frequency set/get, estimated power, fast-switch queries, rate limits, and power scale.

Control flow: `scmi_perf_protocol_init()` allocates global state, reads protocol attributes, allocates the domain table, then for each domain reads domain attributes, initializes xarrays/hash tables, iterates `PERF_DESCRIBE_LEVELS` through the common SCMI iterator, sorts OPPs, and initializes fast channels if supported. Domain attributes determine set-limit/set-level support, notification support, fast-channel support, level-indexing mode, rate limits, sustained data, power scale, and names. OPP processing inserts each level into `opps_by_lvl`; v4 level-indexing mode also indexes by `level_index` and frequency.

Runtime operations: limits and level operations validate the domain, check capability bits, translate between performance levels and level indexes when needed, and then use a fast-channel MMIO path when available or a normal SCMI xfer otherwise. DVFS frequency operations convert between Linux frequency and SCMI level using the domain multiplier or indicative frequency table. OPP population calls `dev_pm_opp_add_dynamic()` and marks OPPs above sustained frequency as turbo. Fast switch is possible only when the level set fast-channel address exists.

State and persistence behavior: state is in-memory and scoped to the protocol instance devres group. OPPs are stored in fixed-size per-domain arrays up to `MAX_OPPS` and indexed by xarray/hash for lookup. `scmi_perf_xa_destroy()` destroys xarrays on protocol teardown. Fast-channel addresses are devm-ioremapped by core helpers and persist for the protocol instance lifetime. No disk or firmware state is persisted by the driver beyond issuing SCMI set commands.

Dependencies and integration points: depends on Linux OPP, xarray, hashtable, sort, I/O accessors, tracepoints, SCMI common iterator and fast-channel helpers from `driver.c`, and notification definitions from `notify.h`. It integrates with cpufreq/devfreq style clients through `struct scmi_perf_proto_ops` and with the notification core through two events: limits changed and performance level changed.

Risks and test signals: firmware can report duplicate or inconsistent OPP data; duplicate xarray inserts are logged and can truncate usable OPPs. Level-indexing mode requires all translations to find matching xarray/hash entries or operations return `-EIO`/`-ENODEV`. Frequency math depends on sustained values and multiplier rounding. Tests should cover v3 and v4 describe-level layouts, zero and rounded sustained ratios, OPP overflow/duplicate handling, limit validation, fast-channel get/set and doorbells, fallback messaging paths, OPP registration cleanup on failure, notification support and report conversion, and xarray destruction on deinit.
