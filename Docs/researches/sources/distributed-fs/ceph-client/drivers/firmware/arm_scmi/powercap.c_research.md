# sources/distributed-fs/ceph-client/drivers/firmware/arm_scmi/powercap.c

Purpose: implements the SCMI Powercap protocol provider. It discovers powercap domains, validates cap and PAI ranges, exposes cap, enable, PAI, measurement, threshold, and info operations, supports optional fast channels, handles asynchronous cap-set completion, supports cap and measurement notifications, and registers itself as `SCMI_PROTOCOL_POWERCAP`.

Important APIs/types/functions: commands include domain attributes, cap get/set, PAI get/set, domain name get, measurements get, cap notify, measurements notify, and fast-channel description. `struct powercap_info` stores domain count, notification command availability, per-domain runtime `scmi_powercap_state`, and public `scmi_powercap_info` array. Per-domain info includes capabilities, power units, PAI/cap ranges and steps, sustainable power, accuracy, parent id, fast-channel pointer, and names. `powercap_proto_ops` exposes domain count/info, cap get/set, cap enable get/set, PAI get/set, measurements get, and measurement threshold get/set.

Control flow: `scmi_powercap_protocol_init()` reads protocol attributes, allocates domain info and state arrays, then requires every reported domain to pass `scmi_powercap_domain_attributes_get()`. Domain attributes parse notification, async, configuration, monitoring, PAI, unit, fast-channel, range, accuracy, and parent flags; range consistency is validated by `scmi_powercap_validate()`, parent ids are checked for bounds and self-parenting, and extended names replace short names when supported. Fast channels are initialized per supported domain for cap and PAI get/set. For protocol v2 and newer, init reads the current cap to seed `last_pcap` and enabled state.

Runtime operations: cap get and PAI get use fast-channel MMIO when available or normal SCMI xfers otherwise. Cap set validates configurability and range, writes fast channel or sends `POWERCAP_CAP_SET`, and uses `do_xfer_with_response()` when the domain supports async cap set and delayed response is not ignored. Protocol v2 enable/disable is modeled by setting a non-zero last cap or sending cap zero; `cap_enable_get()` refreshes the local enabled flag from platform state. PAI set validates configurability and range. Measurements require monitoring support. Measurement threshold state is stored locally and reapplied if measurement notifications are already enabled.

Notification flow: two events are registered: cap changed and measurements changed. `scmi_powercap_notify_supported()` gates events by domain capabilities. `scmi_powercap_set_notify_enabled()` maps event ids to `POWERCAP_CAP_NOTIFY` or `POWERCAP_MEASUREMENTS_NOTIFY`; measurement notification enable requires non-zero thresholds already stored for the domain. Event payload conversion fills timestamp, agent id, domain id, power cap/PAI or measured power, and returns domain id as source.

State and persistence behavior: domain capabilities and runtime state are in-memory and devm-managed. `last_pcap`, `enabled`, `meas_notif_enabled`, and packed low/high thresholds are maintained by the Linux driver to support enable semantics and measurement notification reconfiguration. Hardware/firmware cap, PAI, and monitoring state live in SCMI firmware and are changed only by SCMI commands or fast-channel writes.

Dependencies and integration points: depends on SCMI xfer/helper operations, fast-channel helpers, I/O accessors, tracepoints, and notification core definitions. It integrates with Linux powercap-style clients through `struct scmi_powercap_proto_ops` and with notifier consumers through powercap protocol events.

Risks and test signals: `scmi_powercap_cap_set()` indexes `states[domain_id]` before an explicit domain bounds check, relying on callers to pass valid ids. Step values are validated for zero/nonzero consistency but requested cap/PAI values are range-checked without step-alignment checks. Measurement notification enable fails if thresholds were not configured first. Tests should cover invalid ranges and parent ids during init, cap zero enable/disable behavior, async delayed response domain mismatch, fast-channel versus xfer paths, protocol v1 versus v2 enable semantics, threshold update while notification is enabled, notification report conversion, unsupported monitoring/configuration paths, and out-of-range domain calls from clients.
