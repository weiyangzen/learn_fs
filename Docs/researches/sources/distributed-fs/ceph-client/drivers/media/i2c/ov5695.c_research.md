# sources/distributed-fs/ceph-client/drivers/media/i2c/ov5695.c

Purpose: implements the OmniVision OV5695 raw Bayer V4L2 I2C sensor driver for a 24 MHz external clock, reset GPIO, three supplies (`avdd`, `dovdd`, `dvdd`), two-lane CSI-2, and SBGGR10 output. It provides five fixed modes: 2592x1944, 1920x1080, 1296x972, 1280x720, and 640x480, with frame-rate metadata from 30 to 120 fps and a single 420 MHz link-frequency control.

Important APIs, types, and functions: `struct ov5695` contains the I2C client, clock, reset GPIO, supplies, subdev, media pad, controls, mutex, and current mode. Mode and register data are represented by `struct ov5695_mode` and `struct regval`; global and per-mode arrays are terminated by `REG_NULL`. Low-level access is `ov5695_write_reg()`, `ov5695_write_array()`, and `ov5695_read_reg()`. Format selection uses `ov5695_find_best_fit()` and `ov5695_set_fmt()`. Streaming uses `__ov5695_start_stream()`, `__ov5695_stop_stream()`, and `ov5695_s_stream()`. Power sequencing is split into `__ov5695_power_on()`, `__ov5695_power_off()`, and runtime PM wrappers. Controls are initialized by `ov5695_initialize_controls()` and applied in `ov5695_set_ctrl()`.

Control flow: probe allocates state, sets the default max-resolution mode, obtains a legacy XVCLK at 24 MHz, warns rather than fails on clock-rate mismatch, requires reset GPIO, gets regulators, initializes mutex/subdev/controls, powers the device, checks the 24-bit sensor ID, initializes media entity pads, registers the async sensor subdev, marks runtime PM active, enables PM, and idles the device. Stream-on resumes PM, writes global registers, writes the current mode table, replays controls, and writes mode-select streaming. Stream-off writes standby and releases PM. Active format setting chooses the nearest mode by absolute width/height distance and updates hblank/vblank control ranges; it does not immediately program registers.

State and persistence behavior: persistent software state is the current mode plus V4L2 control cache. Register contents are replayed on every stream-on from global and mode tables plus controls, so power loss does not need hardware retention. VBLANK updates exposure maximum. Digital gain is split across low and high registers, but the implementation writes the low register and then overwrites `ret` with the high-register write result, which can hide low-register failures. There is no filesystem or NVM persistence.

Dependencies and integration points: depends on I2C, V4L2 subdev/control/media APIs, runtime PM, GPIO descriptors, ordered regulator enables/disables, clock helpers, OF matching for `ovti,ov5695`, and media pipeline async registration. It uses `devm_v4l2_sensor_clk_get_legacy()` to support older clock bindings. Link frequency and pixel rate are exposed as read-only controls, but endpoint validation is minimal compared with newer drivers in the same directory.

Risks: `ov5695_check_sensor_id()` returns `ret` when the ID mismatches; if the I2C read succeeded but the ID was wrong, `ret` is 0 and the probe may incorrectly continue after logging an unexpected ID. `#define V4L2_CID_DIGITAL_GAIN V4L2_CID_GAIN` aliases digital gain to the generic gain ID if the symbol is absent, which can affect userspace semantics. Active format changes are not blocked while streaming. The 1296x972 mode table includes global reset/start-stream-like entries and even a `0x0100, 0x01` write before the stream-on path, unlike the other mode tables. There is no firmware endpoint lane/link-frequency validation. Ordered regulator operations are manual, so partial failure paths and disable ordering are important. The clock-rate mismatch is only a warning despite hard-coded timings.

Test signals: verify wrong-chip-ID behavior specifically for successful reads with bad IDs, probe with missing reset GPIO and regulator failures, stream all five modes, inspect whether the 1296x972 mode table prematurely starts streaming, run format negotiation nearest-fit cases, validate exposure/vblank and digital-gain high/low register writes with injected I2C failures, confirm runtime PM power cycling, test pattern selection, and capture SBGGR10 frames with expected dimensions and frame timing.
