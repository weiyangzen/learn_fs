# sources/distributed-fs/ceph-client/drivers/media/i2c/ov5648.c

Purpose: implements a V4L2 sub-device driver for the OmniVision OV5648 raw Bayer image sensor on an I2C/SCCB control bus with MIPI CSI-2 output. It supports a 24 MHz external clock, optional external AVDD plus mandatory DVDD/DOVDD supplies, optional reset and powerdown GPIOs, and a single source media pad. The driver exposes six fixed sensor modes from 2592x1944 down to 640x480 and two media bus codes, `MEDIA_BUS_FMT_SBGGR8_1X8` and `MEDIA_BUS_FMT_SBGGR10_1X10`.

Important APIs, types, and functions: the core state is split across `struct ov5648_sensor`, `struct ov5648_state`, `struct ov5648_ctrls`, and `struct ov5648_mode`. `ov5648_read()`, `ov5648_write()`, `ov5648_write_sequence()`, and `ov5648_update_bits()` are the low-level I2C helpers for 16-bit register addresses and 8-bit values. Sensor bring-up flows through `ov5648_sensor_power()`, `ov5648_sensor_init()`, `ov5648_sw_reset()`, `ov5648_chip_id_check()`, `ov5648_mipi_configure()`, `ov5648_isp_configure()`, and `ov5648_black_level_configure()`. Mode programming is computed rather than table-driven: `ov5648_mode_configure()` writes crop, output size, offsets, HTS/VTS, binning/subsample increments, and PLL settings via `ov5648_mode_pll1_configure()` and `ov5648_mode_pll2_configure()`. V4L2 integration is provided by `ov5648_s_stream()`, `ov5648_get_fmt()`, `ov5648_set_fmt()`, frame interval/size enumeration callbacks, runtime PM callbacks, and `module_i2c_driver()`.

Control flow: probe parses the first fwnode graph endpoint as CSI-2 D-PHY, allocates endpoint data, obtains GPIOs/regulators/clock, validates the 24 MHz XVCLK rate, initializes the subdev/media entity, initializes controls, initializes default state to the first mode and 8-bit Bayer code, enables runtime PM in the suspended state, and registers the sensor subdev asynchronously. Runtime resume powers rails and clock, performs sensor reset and identity check, applies global pad/MIPI/ISP/BLC setup, configures the current mode, restores V4L2 controls, and restarts streaming if the logical state says streaming was active. Stream-on calls `pm_runtime_resume_and_get()`, clears software standby, and marks `state.streaming`; stream-off writes standby and releases runtime PM. Format setting rejects changes while streaming, selects a supported mbus code and nearest mode, updates TRY state or active state, and can immediately program hardware if runtime PM says the device is already active.

State and persistence behavior: persistent software state is the selected `mode`, `mbus_code`, `streaming` flag, parsed endpoint, and V4L2 controls. Register contents are treated as volatile across power loss; resume replays initialization, mode programming, and control setup. Link frequency and pixel rate controls are read-only but are recalculated when format changes using PLL configuration, data-lane count, and bits per sample. Exposure, gain, and white-balance controls use V4L2 auto clusters; exposure and gain are volatile while auto algorithms may update the sensor. There is no filesystem persistence.

Dependencies and integration points: depends on Linux I2C, clocks, GPIO descriptors, regulators, runtime PM, media controller, V4L2 subdev/control/fwnode APIs, and OF graph matching for `ovti,ov5648`. CSI-2 lane count and endpoint link frequencies are taken from firmware. It integrates with receiver bridge drivers through async subdev registration and source-pad media links.

Risks: `ov5648_read()` and `ov5648_write()` treat any nonnegative short I2C transfer as success; robust code normally checks exact byte counts. The regulator/GPIO power sequence is explicitly noted as untested. Active format changes may write hardware before stream-on if the device is runtime-active, so control and PM ordering bugs can surface outside the streaming path. Link-frequency mismatches are logged in `ov5648_state_mipi_configure()` but do not abort when the internal menu or endpoint frequencies are missing the computed value. Frame interval TRY-state support is marked FIXME. The driver has many hand-coded register bitfield helpers, making PLL, crop, binning, and Bayer-order regressions likely if mode definitions are changed without hardware validation.

Test signals: useful checks are probe with correct and incorrect chip IDs, endpoint lane/link-frequency validation, runtime suspend/resume while streaming and idle, `v4l2-ctl --list-subdev-mbus-codes`, frame-size and frame-interval enumeration, stream-on/off at every mode and both 8-bit/10-bit formats, test pattern enablement, manual/auto exposure and gain transitions, H/V flip, and media link validation with a CSI-2 receiver. Hardware capture should verify frame dimensions, Bayer order, pixel rate metadata, and no stale register state after runtime PM cycling.
