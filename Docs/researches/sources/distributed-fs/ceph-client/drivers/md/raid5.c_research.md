# sources/distributed-fs/ceph-client/drivers/md/raid5.c

## Purpose
`raid5.c` implements the Linux MD RAID4, RAID5, and RAID6 personalities. It maps logical bios onto member-device stripes, maintains the stripe-head cache, computes and checks parity or RAID6 P/Q syndromes, handles degraded reads and writes, coordinates resync/recovery/replacement/reshape, and integrates optional consistency mechanisms such as the MD bitmap, RAID5 journal/write-back cache, and partial parity log (PPL).

The file is the central state machine for parity RAID in MD. User and filesystem bios enter through `raid5_make_request()`, are attached to `struct stripe_head` objects, and later progress through `handle_stripe()` into async data-copy, parity, syndrome, and block-device I/O operations. The same machinery is reused for normal reads/writes, aligned read fast paths, discard, sync/check/repair, drive replacement, and online reshape.

## Important APIs, Types, and Functions
The primary runtime object is `struct r5conf`, defined in `raid5.h`, which holds array geometry, stripe cache state, disk slots, worker groups, per-CPU scratch buffers, bitmap sequencing, reshape progress, log/cache state, wait queues, and sysfs-tunable policy. Individual cached stripes are `struct stripe_head`; each stripe has per-device `struct r5dev` entries with data pages, original pages, bios waiting to read/write, in-flight bios, device-sector mappings, and flags such as `R5_UPTODATE`, `R5_LOCKED`, `R5_Wantread`, `R5_Wantwrite`, `R5_InJournal`, and `R5_OVERWRITE`.

Important request-facing APIs are `raid5_make_request()`, `make_stripe_request()`, `raid5_get_active_stripe()`, `add_stripe_bio()`, `add_all_stripe_bios()`, `chunk_aligned_read()`, `make_discard_request()`, and `raid5_bitmap_sector()`. These split bios into stripe-sized work, account writes, handle reshape positioning, enforce overlap exclusion, and update bitmap sequencing.

The main execution path is `handle_stripe()`. It calls `analyse_stripe()` to summarize per-stripe state, then may call `handle_stripe_fill()`, `handle_stripe_dirtying()`, `schedule_reconstruction()`, `handle_parity_checks5()`, `handle_parity_checks6()`, `handle_stripe_clean_event()`, `handle_stripe_expansion()`, `raid_run_ops()`, and `ops_run_io()`. This is where read satisfaction, RMW versus reconstruct-write selection, degraded recovery, parity repair, journal write-out, replacement writes, and endio completion are orchestrated.

The async operation helpers include `async_copy_data()`, `ops_run_biofill()`, `ops_run_compute5()`, `ops_run_compute6_1()`, `ops_run_compute6_2()`, `ops_run_prexor5()`, `ops_run_prexor6()`, `ops_run_biodrain()`, `ops_run_reconstruct5()`, `ops_run_reconstruct6()`, `ops_run_check_p()`, `ops_run_check_pq()`, and their completion callbacks. They use async_tx, XOR, RAID6 syndrome generation, and recovery primitives to avoid doing large parity operations synchronously in the stripe state machine.

Geometry helpers are `raid5_compute_sector()`, `raid5_compute_blocknr()`, `stripe_set_idx()`, `raid6_d0()`, `raid6_next_disk()`, and `raid6_idx_to_slot()`. They implement RAID4 fixed parity, RAID5 rotating parity layouts, RAID6 rotating and DDF-style layouts, and old/new geometry selection during reshape.

Lifecycle and MD personality functions include `setup_conf()`, `raid5_run()`, `raid5_start()`, `raid5_free()`, `raid5_status()`, `raid5_error()`, `raid5_spare_active()`, `raid5_add_disk()`, `raid5_remove_disk()`, `raid5_resize()`, `raid5_sync_request()`, `raid5_start_reshape()`, `raid5_finish_reshape()`, `raid5_quiesce()`, takeover helpers, `raid5_change_consistency_policy()`, and the `raid4_personality`, `raid5_personality`, and `raid6_personality` registrations.

## Control Flow
Startup enters `raid5_run()`. It validates geometry, reshape safety, journal/bitmap incompatibilities, dirty degraded start rules, and consistency-policy combinations. It then calls `setup_conf()` when no existing configuration is present. `setup_conf()` allocates `r5conf`, disk slots, pending-data entries, worker groups, hash tables, inactive stripe lists, bio-split pools, per-CPU scratch buffers, stripe heads, a shrinker, and the MD kernel thread. `raid5_run()` installs sysfs attributes, sets queue limits, creates the stripe-request context mempool, initializes journal or PPL support with `log_init()`, and publishes the MD thread.

Normal I/O enters `raid5_make_request()`. Flush bios are first offered to the log layer and then to generic MD flush handling if needed. Reads on a clean, non-reshaping array may take the `chunk_aligned_read()` fast path, which remaps a chunk-contained bio directly to an in-sync member device and retries through the stripe path on error. Discard bios are accepted only through `make_discard_request()`, which converts full-stripe discards into stripe writes with `R5_Discard` semantics.

For ordinary stripe I/O, `raid5_make_request()` allocates a `stripe_request_ctx`, marks all stripe sectors covered by the bio, optionally waits around reshape boundaries, and repeatedly calls `make_stripe_request()`. Each stripe request determines whether the logical sector is ahead of, inside, or behind reshape. Ahead-of-reshape I/O uses previous geometry, behind uses current geometry, and inside-reshape I/O waits until reshape advances. The bio is attached to all covered data chunks in the stripe, `STRIPE_HANDLE` is set, preread state may be activated for sync writes, and the stripe is released through the block-plug path.

Stripe processing is performed either by the MD thread `raid5d()` or workqueue workers from `raid5_wq`, depending on `group_thread_cnt`. Both paths drain completed stripe releases, flush bitmap batches, activate delayed preread stripes, retry failed aligned reads, choose priority stripes with `__get_priority_stripe()`, process batches with `handle_active_stripes()`, flush deferred bios/log traffic, and issue pending async_tx operations.

`handle_stripe()` is a lock-bit state machine. It prevents concurrent handling with `STRIPE_ACTIVE`, skips non-head batched stripes, breaks full-stripe write batches on error, promotes sync requests, analyzes all device flags, blocks around bad-block metadata updates, schedules biofill for satisfied reads, handles over-degraded or log-failed cases, completes previous reconstruct writes, returns safe written bios, fetches needed blocks, performs RAID5-cache write-out, chooses new write handling, checks/repairs parity during sync, writes replacement devices, repairs read errors by rewrite/readback, and handles reshape expansion. It ends by applying bad-block updates, launching async operations, submitting member-device bios, decrementing preread counters, and clearing `STRIPE_ACTIVE`.

Writes use either read-modify-write or reconstruct-write. `handle_stripe_dirtying()` estimates how many reads each method needs, forces reconstruct-write when RMW is disabled or parity cannot be trusted, and delays prereads through `STRIPE_DELAYED` until enough preread slots are available. `schedule_reconstruction()` then marks data/parity blocks to drain and reconstruct. The async path copies user bio data into stripe pages, optionally pre-xors old data, recomputes parity or P/Q, and finally `ops_run_io()` writes data/parity pages to the member devices and replacements.

Resync/check/repair enters through `raid5_sync_request()`. It skips clean bitmap regions where possible, gets a stripe, sets `STRIPE_SYNC_REQUESTED`, and lets `handle_stripe()` read all needed blocks, verify parity, repair mismatches unless this is check-only, write replacement devices, and call `md_done_sync()`. Reshape is routed to `reshape_request()`, which marks destination stripes `STRIPE_EXPANDING`, marks old-layout source stripes `STRIPE_EXPAND_SOURCE`, advances `reshape_progress`, checkpoints metadata when needed, and lets `handle_stripe_expansion()` copy source data into destination stripes before parity reconstruction and final writes.

## State and Persistence Behavior
Most state in this file is volatile stripe-cache state, but it carefully coordinates with persistent MD metadata, bitmaps, journals, PPL, bad-block logs, and reshape checkpoints. The stripe cache is indexed by stripe sector in `stripe_hashtbl` and partitioned by hash locks. Stripes move among inactive lists, handle lists, low-priority cache lists, hold/delayed lists, bitmap-delay lists, release lists, and RAID5-cache full/partial lists. Reference counts and `STRIPE_ON_RELEASE_LIST`/`STRIPE_ON_UNPLUG_LIST` prevent release races between endio, worker, and plug paths.

Bitmap persistence is batch sequenced. New writes set the in-memory bitmap and record `sh->bm_seq = conf->seq_flush + 1`; stripes with unwritten bitmap batches are parked on `bitmap_list` with `STRIPE_BIT_DELAY`. `raid5d()` advances `seq_flush`, calls `bitmap_ops->unplug()`, sets `seq_write`, and reactivates delayed stripes. This ensures stripe writes are not issued before the dirty bitmap bit covering them is durable.

Journal and write-back cache state is delegated to `raid5-log.h` helpers but is deeply integrated. The stripe state tracks `R5_InJournal`, `STRIPE_R5C_CACHING`, cached full/partial stripe lists, log failures, journal flush requests, and log write-out. On quiesce or sync request, cached stripes may be forced to write out. In write-back mode, reads from degraded stripes with journaled data are deferred until the stripe is flushed, avoiding complex read-side RMW involving `orig_page`.

PPL changes stripe allocation and write rules. When PPL is active, each stripe has a `ppl_page`, partial writes can request `STRIPE_OP_PARTIAL_PARITY`, and overlapping writes are constrained to consecutive data chunks so one PPL entry can describe the data range. Consistency policy changes can enable PPL for RAID5 or return to resync policy, with stripe resizing around the changed per-stripe data.

Device and failure state is persisted through MD superblock flags, bad-block logs, recovery offsets, and reshape metadata. Read errors can set bad blocks, trigger rewrite repair, and increment corrected-error counters. Write errors set `WriteErrorSeen`, `R5_WriteError`, `WantReplacement`, and `MD_RECOVERY_NEEDED`. Reshape stores progress in `mddev->reshape_position`, `conf->reshape_progress`, `conf->reshape_safe`, `curr_resync_completed`, and superblock change flags; it also updates `recovery_offset` for partially reconstructed drives.

Quiesce uses `conf->quiesce` values to stop I/O and allow sync/reshape coordination. A quiesce request flushes RAID5-cache data, prevents new active stripes, waits for `active_stripes` and `active_aligned_reads` to drain, then wakes reshape waiters. Resuming clears the flag and wakes wait queues. Memory barriers are used where aligned-read and reshape-generation state can race with these transitions.

## Dependencies and Integration Points
This file depends on MD core structures and helpers from `md.h`, RAID geometry and stripe definitions from `raid5.h`, RAID0 takeover structures from `raid0.h`, bitmap operations from `md-bitmap.h`, and journal/PPL/cache helpers from `raid5-log.h`. It uses block-layer bios, queue limits, request flags, flush/discard semantics, blk plugs, tracepoints, sysfs, kthreads, workqueues, percpu CPU hotplug state, shrinkers, mempools, and slab caches.

Parity and data movement depend on async_tx and RAID6 math: `async_memcpy()`, `async_xor_offs()`, `async_xor_val_offs()`, `async_gen_syndrome()`, `async_syndrome_val()`, `async_raid6_datap_recov()`, and `async_raid6_2data_recov()`. Per-CPU `raid5_percpu` scratch buffers provide arrays of page pointers, DMA/address conversion space, offsets, and RAID6 spare pages.

The MD personality table exposes this implementation to the MD core for RAID4, RAID5, and RAID6. The three personalities share almost all callbacks: request routing, run/start/free/status, error handling, hot add/remove, spare activation, sync, resize, reshape, quiesce, consistency-policy changes, suspend preparation, and bitmap-sector mapping. Takeover callbacks support selected RAID0, RAID1, RAID4, RAID5, and RAID6 conversions.

Sysfs integration exposes `stripe_cache_size`, `stripe_cache_active`, `preread_bypass_threshold`, `group_thread_cnt`, `skip_copy`, `rmw_level`, `stripe_size` on non-default page-size builds, RAID5-cache journal mode, and PPL write hint. Queue-limit integration advertises RAID partial-stripe cost, chunk and optimal I/O sizes, discard constraints, stable-writes behavior for skip-copy, and maximum request sectors based on stripe bitmap tracking.

## Risks and Edge Cases
The highest-risk area is concurrency around stripe lifecycle. Hash locks, `device_lock`, stripe locks, batch locks, llist release queues, blk-plug release queues, preread counters, and wait queues must stay ordered. The code contains explicit deadlock avoidance, such as dropping `ctx->batch_last` before quiesce or stripe-cache waits, preventing batched non-head stripes from being handled, and using temp inactive lists to avoid lock inversions.

Write ordering is safety critical. Bitmap batches must be durable before writes reach member disks; journal or PPL must record enough information before partial writes; and quiesce must drain both stripe-cache work and aligned reads. Any regression in `STRIPE_BIT_DELAY`, `seq_flush`/`seq_write`, `log_stripe()`, or `ops_run_io()` ordering can expose parity inconsistency after a crash.

Degraded and dirty-start behavior is deliberately conservative. `raid5_run()` refuses dirty degraded starts unless policy allows them or PPL is present, rejects journal plus bitmap, rejects journal reshape, and disables PPL when a journal device is also configured. `handle_stripe()` fails I/O when failures exceed RAID tolerance or when the log has failed and no journaled data remains to flush.

Reshape has several race boundaries. Requests can observe old or new geometry while `conf->generation`, `reshape_progress`, and `reshape_safe` change. The code uses seqcounts and rechecks stripe position after acquiring stripe references. In-place reshape may require userspace-managed read-only startup/backups, and concurrent replacement with reshape is rejected. I/O inside the active reshape window can wait indefinitely unless `reshape_interrupted()` is handled correctly.

Discard is only enabled when the module parameter `devices_handle_discard_safely` confirms member devices return zeroes for discarded regions. The file documents a parity corruption/data-loss scenario if discard does not zero data. Discards are skipped during reshape, require whole-stripe coverage, block on overlapping reads/writes/sync, and unhash stripes afterward because lower layers may modify bio fields and stripe data is not valid.

Memory pressure affects correctness and progress. Stripe cache growth/shrink, resize during reshape, per-CPU scratch allocation, PPL pages, and RAID5-cache extra pages all have fallback or delay behavior. `handle_stripe_dirtying()` can delay stripes when it cannot allocate an extra `orig_page` for write-back RMW. The shrinker drops inactive stripes only down to `min_nr_stripes`; reshape checks that enough stripes exist before starting.

Batching improves full-stripe write throughput but is constrained. It is disabled with journal or PPL, limited to fresh full-stripe normal writes in adjacent stripes that do not cross chunks, and must break cleanly on errors, expansion/sync flags, or completion. Batch state corruption would affect reference counts, overlap wakeups, and bio completion.

## Test Signals
Useful request-path signals include clean RAID5/RAID6 reads and writes, partial writes selecting RMW versus reconstruct-write under each `rmw_level`, full-stripe write batching and batch error handling, chunk-aligned read fast path success and retry fallback, write bios with `REQ_SYNC`, `REQ_FUA`, and `REQ_PREFLUSH`, and overlap waits for concurrent bios to the same stripe block.

Consistency tests should cover bitmap-enabled arrays where writes are delayed until bitmap unplug, journal write-through/write-back behavior, journal failure flushing, PPL partial writes and policy changes, conversion between `ppl` and `resync`, and rejection of unsupported journal plus bitmap or journal plus reshape combinations.

Failure and recovery signals include single-disk degraded RAID5 reads/writes, dual-disk degraded RAID6 reads/writes, read-error correction and rewrite/readback, write-error bad-block handling, replacement-device writes, `WantReplacement` triggering spare replacement, dirty degraded start rejection, and `MD_BROKEN` when failures exceed `max_degraded`.

Sync/check/repair tests should inspect `resync_mismatches`, check-only mismatch reporting without repair, repair recomputing and writing P or P/Q, lazy recovery forcing reconstruct-write, bitmap clean-region skipping, `md_done_sync()` completion, and handling of sync interruption.

Reshape tests should cover forward and backward reshape, disk count increases and decreases, chunk-size/layout changes, in-place reshape read-only requirements, I/O ahead/behind/inside the reshape window, metadata checkpoint updates to `reshape_position`, completion through `end_reshape()` and `raid5_finish_reshape()`, and rejection of concurrent replacement.

Operational signals include sysfs tuning of stripe cache size, preread bypass threshold, group thread count, skip-copy stable-writes queue limits, and `rmw_level`; CPU hotplug allocation/freeing of per-CPU scratch buffers; shrinker dropping inactive stripes; discard disabled unless `devices_handle_discard_safely` and member limits allow safe full-stripe discard; and module init/exit registering and unregistering all three MD personalities.
