# sources/distributed-fs/ceph-client/drivers/clk/qcom/gcc-qcm2290.c

Purpose: global clock controller driver for the Qualcomm QCM2290 GCC block, matched by `qcom,gcc-qcm2290`. It exposes the SoC's shared PLLs, root clock generators, branch gates, resets, dynamic-frequency-switching RCGs, and GDSC power domains to the Linux common clock, reset, and genpd frameworks.

Important APIs, types, and functions: the file is mostly static data consumed by common Qualcomm clock helpers. It defines Alpha PLLs `gpll0`, `gpll1`, `gpll3`-`gpll11`, postdivs such as `gpll0_out_aux2`, `gpll3_out_main`, `gpll6_out_main`, `gpll8_out_main`, and `gpll9_out_main`, VCO/config tables for GPLL10, GPLL11, GPLL8, and GPLL9, parent maps/data for TCXO, sleep, and PLL-derived parents, many `clk_rcg2` roots with `freq_tbl` rate tables, a display divider `gcc_disp_gpll0_clk_src`, USB mock-UTMI postdivider, and branch clocks for camera, display, GPU, PDM, QUPv3, SDCC, USB3, video/Venus, and system interconnect paths. `gcc_qcm2290_clocks[]` maps dt-binding IDs to the corresponding `clk_regmap` objects, `gcc_qcm2290_resets[]` maps BCR and ARES offsets, `gcc_qcm2290_gdscs[]` registers CAMSS, USB30, VCODEC, Venus, and votable MMU TBU power domains, and `gcc_qcm2290_desc` binds all of this to a `regmap_config`.

Control flow: `gcc_qcm2290_init()` registers a platform driver at `subsys_initcall` time. Probe maps MMIO through `qcom_cc_map()`, registers dynamic frequency switching for the six QUPv3 serial RCGs with `qcom_cc_register_rcg_dfs()`, configures GPLL10, GPLL11, GPLL8, and GPLL9 with `clk_alpha_pll_configure()`, then calls `qcom_cc_really_probe()` to publish clocks, resets, and GDSCs. Runtime clock operations are delegated to common ops such as `clk_alpha_pll_ops`, `clk_alpha_pll_postdiv_ro_ops`, `clk_rcg2_shared_ops`, `clk_rcg2_floor_ops`, `clk_branch2_ops`, and divider ops.

State and persistence behavior: persistent state is hardware register state in the GCC MMIO region up to `0xc7000`; the driver itself stores no mutable software policy beyond framework registrations. PLL configuration programs hardware during probe. Branch clocks encode halt semantics with `BRANCH_HALT`, `BRANCH_HALT_DELAY`, `BRANCH_HALT_VOTED`, `BRANCH_VOTED`, and `BRANCH_HALT_SKIP`; several branches are marked critical, including camera/display XO or AHB paths, GPU config AHB, and system NOC CPU AHB. GDSCs persist power-domain state in GDSCR registers, with several votable HLOS1 MMU TBU domains and VCODEC using `HW_CTRL_TRIGGER`.

Dependencies and integration points: dependencies include Linux platform/module/regmap/common-clock APIs, `dt-bindings/clock/qcom,gcc-qcm2290.h`, Qualcomm alpha PLL, branch, RCG, divider, reset, GDSC, and common CC helpers. Consumers integrate by referencing the dt-binding clock, reset, and power-domain IDs. Important external parents are firmware-named `bi_tcxo` and `sleep_clk`; the controller supplies clocks to CAMSS/TFE/OPE, display, GPU, QUPv3 serial engines, eMMC/SD, USB3 PHY and master paths, Venus/VCODEC, PDM, and interconnect throttle/QMIP blocks.

Risks: correctness depends on exact register offsets, parent-map hardware selector values, and dt-binding indices matching the SoC manual. Shared and voted clocks can be hard to debug because enable bits live in vote registers such as `0x79004` and `0x7900c`, not always in the local branch register. Raw critical-clock choices can mask missing consumer votes, while under-marking critical AHB/XO clocks can hang media, GPU, or interconnect access. PLLs with dynamic update or non-default BRAMMO/EVO register layouts are sensitive to VCO/config mistakes. DFS registration is limited to QUPv3 serial RCGs, so serial-rate changes are a specific regression target.

Test signals: boot logs should show successful `gcc-qcm2290` probe with no deferred external parent failures. `/sys/kernel/debug/clk/clk_summary` should expose the GPLLs, QUPv3 sources, SDCC, USB, camera, display, GPU, and video branches with expected parent/rate choices. Functional signals include serial ports through all QUPv3 instances, SDCC1/SDCC2 rate switching including floor ops, USB3 link bring-up with skipped pipe halt checks, camera and Venus power-domain on/off through GDSCs, reset assertions through BCR IDs, and suspend/resume without critical clock loss. Clock-framework tests should exercise `qcom_cc_register_rcg_dfs()` paths for the six QUP RCGs.
