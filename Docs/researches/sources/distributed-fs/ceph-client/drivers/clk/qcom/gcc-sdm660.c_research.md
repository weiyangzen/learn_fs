# sources/distributed-fs/ceph-client/drivers/clk/qcom/gcc-sdm660.c

## Purpose
`gcc-sdm660.c` is the Qualcomm Global Clock Controller provider for Snapdragon 630/660-class SoCs. It describes the GCC register block as Linux common clock framework objects, exposes clock IDs from `dt-bindings/clock/qcom,gcc-sdm660.h`, and provides reset and GDSC power-domain control for the major on-chip peripheral islands. The modeled clock tree covers the XO and sleep inputs, GPLL0/GPLL1/GPLL4 and their early/divided paths, BLSP1/BLSP2 I2C/SPI/UART roots, general-purpose clocks, HMSS/RBCPR roots, QSPI, PDM, SDCC/eMMC/ICE, UFS, USB2/USB3, GPU/MMSS/MSS fabric clocks, and voted LPASS/Turing SMMU clocks.

## Important APIs, Types, And Functions
The file is almost entirely declarative data consumed by the qcom clock-controller helpers. Important object types are `struct clk_fixed_factor` for `xo` and early GPLL dividers, `struct clk_alpha_pll` for early PLL instances, `struct clk_alpha_pll_postdiv` for consumer-facing GPLL outputs, `struct clk_rcg2` plus `struct freq_tbl` for rate-programmable roots, `struct clk_branch` for gateable leaves, `struct gdsc` for power domains, `struct qcom_reset_map` for reset-controller lines, and `struct qcom_cc_desc` for final provider registration.

Parent maps encode the hardware parent selector values for XO, sleep, GPLL0, GPLL1, GPLL4, and divided early PLL paths. The main export arrays are `gcc_sdm660_hws[]`, `gcc_sdm660_clocks[]`, `gcc_sdm660_gdscs[]`, and `gcc_sdm660_resets[]`; they are gathered into `gcc_sdm660_desc`. `gcc_sdm660_probe()` is the only custom runtime function. It maps the GCC MMIO block with `qcom_cc_map()`, sets the HMSS AHB sleep-enable bit via `regmap_update_bits()`, and registers clocks, resets, and GDSCs with `qcom_cc_really_probe()`.

## Control Flow
Driver registration happens through `core_initcall_sync(gcc_sdm660_init)`, so the GCC provider is available early for platform devices. Device-tree matching accepts both `qcom,gcc-sdm630` and `qcom,gcc-sdm660`. At probe, qcom CC code creates the regmap using the descriptor's `regmap_config` (`32` bit registers, stride `4`, max register `0x94000`, fast I/O). The one SoC-specific probe action is setting bit 21 at register `0x52008`, allowing `hmss_ahb_clk` to be turned off by hardware during selected low-power modes. After that, all behavior is handed to the shared qcom CC registration path.

Runtime clock operations are table-driven. RCG2 frequency tables provide legal rates and parent/divider/MND settings for serial, storage, USB, UFS, HMSS, and general-purpose roots. Branch clocks refer to those roots with `CLK_SET_RATE_PARENT` where a leaf should propagate rate requests upward. Halt checks vary by hardware block: ordinary clocks use `BRANCH_HALT`, voted branches use `BRANCH_VOTED` or `BRANCH_HALT_VOTED`, slow/pipe-style clocks sometimes use delayed or skipped halt checks, and a small set carries `CLK_IS_CRITICAL` or `CLK_IGNORE_UNUSED` for boot-sensitive paths.

## State And Persistence
There is no filesystem or nonvolatile persistence. Static C descriptors define the expected hardware topology; live state is held in GCC registers and in the common clock framework's registered clock tree. Probe-time writes to `0x52008` persist only for the current boot. PLL enable state, parent selection, divider values, M/N/D values, branch gates, reset assertions, and GDSC power state are all hardware-backed. GDSCs for UFS, USB3, PCIe, and voted LPASS/Turing ADSP domains use `PWRSTS_OFF_ON`, so consumers can power those domains through Linux power-domain APIs. Reset state is exposed through reset-controller consumers and is not cached as durable state by this file.

## Dependencies And Integration Points
The driver depends on Linux platform-driver, OF match, regmap, CCF, reset-controller, and qcom-specific helpers in `common.h`, `clk-regmap.h`, `clk-alpha-pll.h`, `clk-rcg.h`, `clk-branch.h`, `reset.h`, and `gdsc.h`. External parent clocks are supplied by firmware/device tree under names such as `xo` and `sleep_clk`; internal parents are the in-file GPLL hardware clocks. Consumers integrate by referencing the SDM660 binding IDs for BLSP serial controllers, SDCC/eMMC and ICE, QSPI, PDM, USB2/USB3 controllers and PHYs, UFS controller/PHY, GPU/MMSS/MSS fabrics, HMSS RBCPR, LPASS/Turing SMMU votes, PCIe power domain, and modem restart reset.

## Risks
Parent-map correctness is the main maintenance risk. Hardware selector values are sparse and not identical across maps, especially for GPLL0 early divider, GPLL1/GPLL4, and sleep-clock alternatives. A plausible parent-data change can silently program the wrong source. Clock-critical flags should be changed conservatively: `gcc_gpu_cfg_ahb_clk` and MMSS/GPU related GPLL branches include critical or ignore-unused behavior that can affect boot or display/GPU handoff. UFS and USB symbol/pipe clocks use skipped or delayed halt checks; replacing those with strict halt polling can cause false timeouts. Reset offsets are close to live controller blocks, and the reset table includes storage, USB PHY, USB controller, and MSS restart lines, so offset or binding-ID mistakes have broad hardware impact.

## Test Signals
Expected boot signals are a successful `gcc-sdm660` platform probe, no `qcom_cc_really_probe()` errors, and clock/reset/power-domain providers visible to device-tree consumers. `clk_summary` should show XO, GPLL0/GPLL1/GPLL4 early and postdiv outputs, BLSP1/BLSP2 QUP and UART roots, HMSS GPLL/RBCPR roots, SDCC1/SDCC2 and ICE clocks, UFS AXI/Unipro/AUX/symbol clocks, USB20/USB30 master/mock/sleep/pipe clocks, and voted LPASS/Turing SMMU clocks. Hardware validation should cover serial console and I2C/SPI, eMMC/SD including ICE where present, UFS attach, USB2 and USB3 enumeration, QSPI, GPU/display/MMSS clients, modem restart handling, low-power entry exercising the HMSS AHB sleep bit, and reset assert/deassert tests for representative storage, USB, PHY, and MSS lines.
