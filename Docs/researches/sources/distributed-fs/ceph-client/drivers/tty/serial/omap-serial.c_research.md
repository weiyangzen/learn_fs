# sources/distributed-fs/ceph-client/drivers/tty/serial/omap-serial.c

Purpose: OMAP high-speed UART driver. It provides a serial-core `uart_driver` for up to ten TI OMAP UART instances, separate from 8250 because OMAP needs platform-specific register programming, wakeup handling, runtime PM, errata handling, hardware/software flow control, and RS-485 direction control.

Important APIs/types/functions: `struct uart_omap_port` wraps `struct uart_port` with OMAP register shadows (`ier`, `lcr`, `mcr`, `fcr`, `efr`, `dll`, `dlh`, `mdr1`, `scr`, `wer`), PM state, feature/errata flags, wake IRQ, RS-485 GPIO state, and latency QoS work. `serial_omap_pops` is the serial-core callback table. `serial_omap_probe()` maps MMIO, resolves OF or platform IDs, enables runtime PM, derives revision features via `omap_serial_fill_features_erratas()`, configures RS-485, and registers the port. `serial_omap_set_termios()` computes 13x/16x baud mode, divisor registers, FIFO trigger registers, hardware CTS/RTS, XON/XOFF, and read/ignore masks. `serial_omap_irq()` decodes `UART_IIR` interrupt causes and dispatches to RX, line-status, modem-status, and TX helpers. PM restore is handled by `serial_omap_restore_context()` and runtime suspend/resume callbacks.

Control flow: module init registers `serial_omap_reg` and the platform driver. Probe allocates the port, maps resources, initializes PM/QoS, reads hardware revision, stores the port in `ui[]`, and calls `uart_add_one_port()`. Open flows through `serial_omap_startup()`, which requests the main IRQ, optionally installs a dedicated wake IRQ, powers the device with runtime PM, clears FIFOs/status, sets modem control, enables RX/line interrupts, and programs wake-enable bits. Data receive path is IRQ -> `serial_omap_rdi()`/`serial_omap_rlsi()` -> `uart_insert_char()` -> `tty_flip_buffer_push()`. TX path is `start_tx()` enabling THRI, then IRQ -> `transmit_chars()` -> `serial_omap_put_char()`. Close disables interrupts, clears break/FIFOs, drops runtime PM, frees IRQs, and clears wake IRQ.

State and persistence: most hardware state is mirrored in `uart_omap_port` so termios, runtime resume, and context-loss recovery can reprogram the controller. `context_loss_cnt` detects lost register context. `port_activity` is updated on interrupts. `pm_qos_request` is updated from baud-derived latency. RS-485 state uses `rts_gpiod` plus `rs485_tx_filter_count` to suppress self-received bytes when RX-during-TX is disabled. Hardware wakeup and WER state persist while the device is powered but are rewritten on startup/resume.

Dependencies and integration points: Linux serial core, TTY flip buffers, OF compatibles `ti,omap2-uart`, `ti,omap3-uart`, and `ti,omap4-uart`, optional legacy `omap_uart_port_info`, runtime PM, wake IRQ helpers, GPIO descriptors for RS-485 RTS, CPU latency QoS, and OMAP feature callbacks for wake/context-loss. Console integration includes normal console, earlycon, and polling hooks when configured.

Risks: register programming is order-sensitive across OMAP config modes, especially EFR/TCR/TLR/MCR access and MDR1 errata i202. Runtime PM restore relies on platform context-loss reporting when available and otherwise restores conservatively. RS-485 direction timing uses blocking `mdelay()` under serial operations. Missing `clock-frequency` falls back to 48 MHz, which can silently produce wrong baud rates. The RX path handles only one received byte per RDI interrupt iteration, bounded by the outer 256 loop.

Test signals: probe success for DT and legacy platform data, alias line bounds, wake IRQ present/absent, register restore after runtime suspend with changed context count, termios coverage for 13x/16x baud selection and hardware/software flow control, RS-485 RTS polarity and TX-complete direction changes, console write while interrupts are disabled, RX line-status errors and sysrq/break handling, and i202 MDR1 timeout warning behavior.
