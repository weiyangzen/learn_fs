# sources/distributed-fs/ceph-client/drivers/infiniband/hw/bnxt_re/qplib_sp.h

Purpose: public slow-path data-model header for bnxt_re qplib. It defines the driver-facing structures used to hold firmware-reported device attributes, protection domains, GIDs, address handles, memory regions/windows, fast-registration page lists, RoCE statistics, extended packet statistics, congestion-control parameters, and the prototypes implemented by `qplib_sp.c`.

Important APIs, types, and functions: `struct bnxt_qplib_dev_attr` stores firmware version, maximum SGID/QP/CQ/MR/MW/PD/AH/SRQ/PKEY/inline-data/DPI values, WQE/SGE limits, L2 doorbell size, TQM allocation requests, atomic support, capability flags, and rate-limit range. `struct bnxt_qplib_pd` holds a firmware PD ID. `struct bnxt_qplib_gid` is a 16-byte address and `struct bnxt_qplib_gid_info` pairs it with a VLAN ID. `struct bnxt_qplib_ah` contains destination GID/MAC, PD, firmware AH ID, SGID indexes, traffic class, flow label, hop limit, service level, VLAN ID, and network type. `struct bnxt_qplib_mrw` describes MR/MW type, access flags, lkey/rkey, VA, size, page count, firmware flags, handle, and backing HWQ. `struct bnxt_qplib_frpl` wraps a fast-registration page-list HWQ. `struct bnxt_qplib_roce_stats` and `struct bnxt_qplib_ext_stat` enumerate base error/traffic counters and extended TX/RX packet/byte/CNP/ECN counters. `struct bnxt_qplib_cc_param_ext` and `struct bnxt_qplib_cc_param` model base and Gen1 congestion-control knobs. Prototypes expose SGID, device-attribute, resource, AH, MRW, FRPL, stats, CC, context-read, version, and mirror-flow APIs. Constants define reserved QP WQEs, supported GID count, maximum outstanding RDMA atomics, CQ WQE cap, access flags, reserved lkey, variable-WQE limits, static SGE count, and receive queue WQE maximum.

Control flow: this header establishes the object contracts passed between upper RDMA verbs code and the qplib slow-path implementation. Upper layers populate PD/GID/AH/MRW/CC structs, call the declared qplib API, and expect IDs, keys, maximums, and counters to be filled or updated. `qplib_sp.c` owns firmware command execution for these declarations, while `ib_verbs.c`, `main.c`, `debugfs.c`, and resource/context code consume the resulting state. The header also advertises prototypes such as `bnxt_qplib_update_sgid()` and `bnxt_qplib_alloc_fast_reg_mr()` that are declared here but not implemented in the paired `qplib_sp.c` as read in this work item, so build coverage must account for whether another file supplies them or whether the declarations are stale.

State and persistence: structures defined here are runtime state containers. Device attributes persist in memory after `QUERY_FUNC` until the device is removed or requeried. AH/MRW/FRPL objects hold firmware IDs or DMA-backed HWQs that persist until corresponding destroy/free/deregister calls. Stats structs are snapshots supplied by query calls. CC structs are request/response carriers; changes sent through `bnxt_qplib_modify_cc()` persist in firmware until changed again or reset. No filesystem persistence is introduced by this header.

Dependencies and integration points: includes the RDMA bnxt_re ABI header and relies on types from `qplib_res.h` being visible to users for `struct bnxt_qplib_hwq`, `struct bnxt_qplib_res`, `struct bnxt_qplib_ctx`, and RCFW types. It is included by the slow-path C file and by upper bnxt_re modules that bridge Linux RDMA core objects into qplib commands. Values here are tightly coupled to firmware command fields in `roce_hsi.h`, qplib resource queue definitions, IIO-style no relation; this is RDMA kernel driver code. The access flags map upper-layer MR permissions into firmware command masks.

Risks: the header is a shared ABI within the driver, so structure field changes can break multiple modules or firmware command packing. Some fields have implicit units or split integer/fractional representation (`rate_limit_*`, CC thresholds, stats counters, `max_inline_data`) and need careful documentation at call sites. `bnxt_qplib_roce_stats` contains comments that mostly restate 64-bit width and do not clarify reset/delta behavior. `bnxt_qplib_dev_attr.max_mrw` is present but the implementation populates `max_mr` and `max_mw`, so users should verify whether `max_mrw` is obsolete. Declared-but-unimplemented prototypes are a maintenance hazard if no other translation unit defines them. `struct bnxt_qplib_ah` carries both firmware SGID index and host SGID index, making mismatches possible when software and hardware GID tables diverge.

Test signals: full bnxt_re module builds with `W=1` and modpost should catch stale prototypes and missing definitions; compile matrix should include static and variable WQE modes; run verbs tests for PD/AH/MR/MW/FRMR object lifecycle using these structs; validate reported device attributes against firmware on legacy, P5, P7, PF, and VF devices; exercise CC debugfs/sysfs paths for each field width; check stats readers for overflow/delta behavior; and run sparse for endian, struct padding, and access-flag type mismatches after any header change.
