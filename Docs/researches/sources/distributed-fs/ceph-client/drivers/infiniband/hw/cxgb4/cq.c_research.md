# sources/distributed-fs/ceph-client/drivers/infiniband/hw/cxgb4/cq.c

Purpose: completion queue implementation for `iw_cxgb4`. It creates and destroys hardware CQs, maps user CQs, arms CQs, polls Chelsio CQEs into RDMA core `ib_wc` completions, synthesizes software flush completions, handles out-of-order send/read completions, and supports SRQ completion reaping.

Important APIs, types, and functions: exported functions are `c4iw_create_cq()`, `c4iw_destroy_cq()`, `c4iw_poll_cq()`, `c4iw_arm_cq()`, `c4iw_cq_rem_ref()`, `c4iw_flush_rq()`, `c4iw_flush_sq()`, `c4iw_flush_hw_cq()`, `c4iw_count_rcqes()`, and `c4iw_flush_srqidx()`. Firmware resource setup is performed by `create_cq()` and `destroy_cq()` with `FW_RI_RES_WR` operations. Polling internals include `poll_cq()`, `c4iw_poll_cq_one()`, `__c4iw_poll_cq_one()`, `cqe_completes_wr()`, `create_read_req_cqe()`, `advance_oldest_read()`, `flush_completed_wrs()`, `reap_srq_cqe()`, and `post_pending_srq_wrs()`.

Control flow: CQ creation validates entry count/vector/flags, allocates a wait object and destroy skb, rounds queue size for status page and hardware requirements, allocates CQID plus coherent queue memory, sends a firmware CQ create WR, records GTS/BAR2 addresses, inserts the CQ into the device xarray, and for user CQs returns mmap keys for CQ memory and GTS/BAR2 page. Polling locks the CQ, repeatedly calls `c4iw_poll_cq_one()`, skips nonready CQEs via `-EAGAIN`, and returns either completions or an error. `poll_cq()` chooses hardware versus software CQE, skips unrelated QP/TERMINATE/drain cases, rewrites read-response completions into read-request completions, handles out-of-order SQ completions through per-SQ shadow entries, advances SQ/RQ/SRQ indices, consumes CQEs, and marks WQs in error on CQE status or MSN mismatches. `__c4iw_poll_cq_one()` translates Chelsio opcodes/status values to `ib_wc` opcode/status/flags and invalidates local MR state for invalidate and failed fast-register completions.

State and persistence: CQ state is runtime-only in `struct c4iw_cq` and embedded `struct t4_cq`: CQID, queue memory, software CQ ring, generation bits, GTS register, BAR2 mapping, vector, locks, refcount, completion for teardown, and wait object. User mmap state is persisted only in `struct c4iw_ucontext` `mmaps` list until consumed or context destruction. Queue indices and shadow SQ/SRQ state are persisted in memory across polls and flushes; hardware queue state lives in adapter memory until firmware reset.

Dependencies and integration points: depends on RDMA core CQ APIs, uverbs driver data, cxgb4 firmware RI resource WRs, Chelsio `t4_*` queue helpers/macros, xarrays in `struct c4iw_dev`, mmap helpers from `iw_cxgb4.h`, QP/SRQ internals, memory invalidation in `mem.c`, WR logging in `device.c`, and event dispatch in `ev.c`.

Risks: polling is a subtle state machine; read-response rewriting assumes `oldest_read` is valid when a READ_RESP arrives. Out-of-order SQ completions and unsignaled WR reaping can corrupt accounting if SQ indices or CQE WRIDs are wrong. `c4iw_flush_hw_cq()` locks QPs conditionally and has a skip path that must always unlock the correct QP; changes here need lock-path review. User CQ creation has compatibility handling for older 32-byte CQE uverbs input, so response-size drift can break old providers. SRQ out-of-order reaping relies on absolute SRQ indices and pending WR lists.

Test signals: create and destroy kernel and user CQs with minimum, maximum, and invalid entry counts; test vectors outside `nciq`; verify mmap key creation; poll send, recv, RDMA read/write, immediate, invalidate, local invalidate, and fast-register completions; inject CQE status values and verify `ib_wc` mapping; exercise unsignaled WR completion reaping, out-of-order read completions, software flush of SQ/RQ, SRQ in-order and out-of-order completion, CQ arm with missed-event reporting, and concurrent destroy while events hold CQ refs.
