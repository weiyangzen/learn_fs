# sources/distributed-fs/ceph-client/drivers/infiniband/hw/cxgb4/device.c

Purpose: module and cxgb4 ULD glue for the Chelsio RDMA driver. It owns module parameters, debugfs diagnostics, low-level RDMA device allocation/open/close, resource-pool initialization, BAR/on-chip-memory mappings, cxgb4 receive/state/control callbacks, doorbell flow-control and recovery, WR wait-object allocation, and module load/unload registration.

Important APIs, types, and functions: module lifecycle is `c4iw_init_module()`/`c4iw_exit_module()`. ULD callbacks are described by `c4iw_uld_info` and implemented by `c4iw_uld_add()`, `c4iw_uld_rx_handler()`, `c4iw_uld_state_change()`, and `c4iw_uld_control()`. Device allocation/open/close flows through `c4iw_alloc()`, `c4iw_rdev_open()`, `c4iw_rdev_close()`, `c4iw_remove()`, `c4iw_dealloc()`, and `rdma_supported()`. Debugfs support includes `setup_debugfs()`, `qp_open()`, `stag_open()`, `stats_open()`, `ep_open()`, `wr_log_show()`, and `c4iw_log_wr_stats()`. Doorbell handling uses `stop_queues()`, `resume_queues()`, `recover_queues()`, and `recover_lost_dbs()`.

Control flow: module init initializes CM workqueue state, creates root debugfs, creates a registration workqueue, and registers as `CXGB4_ULD_RDMA`. The cxgb4 lower layer calls `c4iw_uld_add()` to allocate a `uld_ctx`, then state `CXGB4_STATE_UP` triggers `c4iw_alloc()` and async `c4iw_register_device()`. Allocation validates RDMA-capable virtual resources, maps BAR2 or T4 on-chip queue memory, opens the RDMA resource device, initializes xarrays/locks/waitqueues, creates per-device debugfs, and starts with adapter IRD availability. Receive callbacks convert ingress descriptors or packet gather-lists to skbs, dispatch CPLs through `c4iw_handlers[]`, or route async notification queue IDs to `c4iw_ev_handler()`. State `DOWN`, fatal, recovery, and detach paths unregister and deallocate the RDMA device.

State and persistence: all state is in memory and adapter resources. Global state includes `uld_ctx_list`, `dev_mutex`, `reg_workq`, debugfs root, and module parameters for T5 doorbell policies and WR logging. `struct c4iw_rdev` holds resource allocators, pool pointers, lldi snapshot, flags, BAR mappings, status page, statistics, queue limits, WR log, free workqueue, and pool krefs/completions. `struct c4iw_dev` owns the IB device, xarrays for CQs/QPs/MRs/TIDs, doorbell state/list, debugfs root, available IRD, and waitqueue used during teardown.

Dependencies and integration points: depends on cxgb4 ULD registration and lldi metadata, PCI BAR resources, gen pools/resource code in other driver files, RDMA device registration, CPL handlers in `cm.c`, async events in `ev.c`, queue primitives from `t4.h`, Linux debugfs/seq_file/vmalloc, xarrays, workqueues, and IB event dispatch.

Risks: `c4iw_init_module()` returns `-ENOMEM` if `reg_workq` creation fails after `c4iw_cm_init()` and debugfs creation, but does not unwind those resources in that failure path. `c4iw_alloc()` error paths after BAR/ioremap can deallocate the IB device without unmapping already mapped BAR regions on some failures. Debugfs snapshot generation counts xarray entries without holding locks, then allocates fixed-size buffers and later iterates under locks; it is intentionally racy. Doorbell recovery allocates a QP pointer list with `GFP_ATOMIC` proportional to active QPs and returns silently on allocation failure. `c4iw_dealloc()` waits for `hwtids` to empty and warns on other xarrays, so leaked endpoint refs can hang removal.

Test signals: module init failure injection, cxgb4 state transitions, device allocation on unsupported VR layouts and unsupported host page sizes, BAR2/on-chip mapping failures, resource-pool create rollback, receive-path CPL dispatch with multiple gather-list modes, doorbell full/empty/drop recovery under active QPs, debugfs reads and clears, WR log wraparound, and removal with outstanding CQs/QPs/MRs/endpoints.
