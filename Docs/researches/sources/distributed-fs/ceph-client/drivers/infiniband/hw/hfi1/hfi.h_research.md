# sources/distributed-fs/ceph-client/drivers/infiniband/hw/hfi1/hfi.h

Purpose: central HFI1 kernel header defining the driver's core data model, constants, inline helpers, and cross-file prototypes. It describes receive contexts, packets, physical port state, shared ASIC state, per-device state, user file private data, link/receive-control flags, packet header helpers, partition checks, MTU helpers, device flags, and PCI/module integration points.

Important APIs and types: key types are `struct hfi1_ib_stats`, `struct ctxt_eager_bufs`, `struct exp_tid_set`, `struct tid_queue`, `struct hfi1_ctxtdata`, `struct hfi1_packet`, `struct hfi1_pportdata`, `struct hfi1_asic_data`, `struct hfi1_devdata`, and `struct hfi1_filedata`. Important helpers include `rcvhdrq_size()`, 16B header accessors/builders, `hfi1_get_rc_ohdr()`, `incr_cntr64()`, context accessors and sequence helpers, `generate_jkey()`, `active_egress_rate()`, `egress_cycles()`, `sc_to_vlt()`, ingress/receive PKEY checks, `dd_from_*()`/`ppd_from_*()` conversions, ECN detection, GUID/PKEY accessors, receive-tail helpers, send/SDMA integrity-mask builders, multicast/LID conversion helpers, GRH construction, and `flush_wc()`. It also declares exported driver functions such as `hfi1_init()`, context allocation/free, interrupt handlers, device create/remove, PCIe helpers, platform config helpers, user page pinning, and link/port operations.

Control flow role: this header is not a runtime flow by itself; it is the contract that lets `init.c`, `file_ops.c`, `firmware.c`, interrupt handling, verbs, SDMA, PIO, MAD, netdev, and platform code share state safely. Receive packet paths use `struct hfi1_packet` and inline header/PKEY/ECN helpers. User paths use `struct hfi1_filedata`, `uctxt_offset()`, receive-tail helpers, context flags, and mmap-visible event/status state. Probe/teardown paths allocate and initialize `struct hfi1_devdata`, `struct hfi1_pportdata`, and `struct hfi1_ctxtdata` according to the layouts defined here.

State and persistence: `struct hfi1_devdata` is the lifetime owner for PCI mappings, cdevs, send/receive contexts, SDMA engines, workqueues, locks, firmware/platform state, counters, IRQ state, status/event pages, user refcount, ASPM state, RSM/IPoIB state, and physical ports. `struct hfi1_pportdata` owns per-port link state, GUIDs, PKEYs, QSFP data, work items, congestion control state, VL arbitration, counters, link-down reasons, and status pointer. `struct hfi1_ctxtdata` owns per-receive-context DMA queues, eager buffers, send context, interrupt handlers, TID queues, wait/event flags, subcontext shared memory, J_KEY, and packet sequencing. Most state is volatile kernel/hardware state, but some mappings are shared read-only or event-bit pages to user processes until device removal.

Dependencies and integration points: includes Linux PCI/DMA/cdev/interrupt/mutex/kref/I2C/xarray/rhashtable facilities, RDMA core and `rdma_vt`, HFI1 chip/register/common/verbs/PIO/MAD/QSFP/platform/affinity/MSI-X headers. It is included by most HFI1 source files and forms the compile-time integration layer with the RDMA core, PCI driver, sysfs/debugfs, cdev user ABI, and hardware register helpers.

Risks: because this file defines shared layout and inline policy, small changes have wide blast radius. `struct hfi1_devdata` begins with `struct hfi1_ibdev` and `struct hfi1_ipoib_rdma_netdev` similarly relies on first-member layout elsewhere; reordering can break container conversions. Bit masks for capabilities, receive control, link states, PKEY membership, and packet headers must match hardware and ABI. Inline PKEY/ECN/LID helpers run in hot paths and must stay cheap and correct. `hfi1_packet_present()` differs by DMA tail mode, so receive-tail memory ordering and volatile access matter. User-visible structures and event/status pages depend on stable semantics.

Test signals: full HFI1 build coverage after any structure/prototype change, sparse/lockdep for RCU and seqlock helpers, receive packet tests covering 9B/16B header parsing and PKEY checks, user ABI mmap/status/event tests, link state and MTU tests, send/SDMA integrity programming on A0 vs non-A0 hardware, and probe/remove tests that exercise allocation/free of every major state object.
