# sources/distributed-fs/ceph-client/drivers/infiniband/hw/hfi1/firmware.c

Purpose: manages HFI1 firmware acquisition, authentication, download, SBus/SerDes programming, 8051 access, platform configuration parsing, GUID reads, and shared ASIC resource locking. It is the low-level bridge between Linux firmware blobs, on-chip security/RSA hardware, 8051 firmware, SBus microcode, PCIe/fabric SerDes firmware, and platform tuning tables.

Important APIs and functions: public entry points include `hfi1_firmware_init()`, `load_firmware()`, `dispose_firmware()`, `read_8051_data()`, `wait_fm_ready()`, `sbus_request()`, `sbus_request_slow()`, `fabric_serdes_reset()`, `load_pcie_firmware()`, `acquire_hw_mutex()`, `release_hw_mutex()`, `acquire_chip_resource()`, `release_chip_resource()`, `check_chip_resource()`, `init_chip_resources()`, `finish_chip_resources()`, `set_sbus_fast_mode()`, `clear_sbus_fast_mode()`, `parse_platform_config()`, `get_platform_config_field()`, and `read_guid()`. Important internal helpers are `obtain_one_firmware()`, `__obtain_firmware()`, `retry_firmware()`, `verify_css_header()`, `load_security_variables()`, `run_rsa()`, `load_8051_firmware()`, `load_fabric_serdes_firmware()`, `load_sbus_firmware()`, and `load_pcie_serdes_firmware()`.

Control flow: `hfi1_firmware_init()` selects which firmware classes apply to ASIC, FPGA, RTL, or simulator devices, assigns default names, and calls `obtain_firmware()`. Firmware acquisition is module-global and protected by `fw_mutex`; the first device requests all enabled blobs, validates CSS headers and augmented RSA material, and leaves state in `FW_TRY`, `FW_FINAL`, or `FW_ERR`. `load_firmware()` downloads fabric SerDes firmware under the SBus chip resource, then downloads and starts 8051 firmware, retrying with alternate debug names when `retry_firmware()` decides the previous authorization/load failed. Firmware download loads RSA security variables, streams firmware into 8051 RAM or SBus receiver registers, runs the RSA engine, releases resets, and waits for firmware readiness. PCIe firmware loading similarly sequences SBus master firmware before PCIe SerDes firmware. Platform config parsing validates magic, size, per-table inverted headers, table type, CRC, metadata version, and then caches table and metadata pointers for later field extraction.

State and persistence: module-level state includes `fw_state`, `fw_err`, firmware names, load-enable flags, and four `struct firmware_details` objects; these persist across devices until module unload or error. Hardware state persists in CSRs: 8051 RAM/reset state, RSA modulus/r2/mu/header/signature registers, SBus fast mode, SerDes broadcast groups, ASIC scratch resource bits, firmware version/status registers, and local GUID register contents. `dd->pcfg_cache` persists parsed platform config pointers for the device. `dd->dc8051_ver` and `dd->base_guid` cache firmware version and GUID. Resource ownership is recorded in ASIC scratch bits and serialized with both `dd->asic_data->asic_resource_mutex` and the hardware mutex CSR.

Dependencies and integration points: uses the Linux firmware loader, mutexes, delays, CRC32, PCI device parent for firmware requests, CSR accessors from chip/common code, platform config definitions, QSFP/SerDes constants, and HFI1 logging/trace helpers. It is called from PCI probe/chip init and by link-management paths that need fabric SerDes reset, platform tuning, I2C/QSFP resource ownership, or PCIe firmware transition.

Risks: firmware authentication is strict: non-augmented firmware is rejected because the driver cannot generate `r2`/`mu`; bad CSS sizes or CRCs abort loading. `fw_state == FW_TRY` means one device may be deciding between normal and alternate blobs while others wait up to 40 seconds. SBus operations require correct fast-mode and chip-resource pairing; missing `release_chip_resource()` can block the other HFI or OS. `acquire_hw_mutex()` forcibly clears a stuck mutex on first timeout, which is pragmatic but risky if another agent is genuinely active. Platform config parsing stores pointers into `dd->platform_config.data`, so that backing memory must outlive cache use. Field extraction assumes metadata alignment/length conventions and can truncate if table metadata changes.

Test signals: successful firmware request and CSS validation logs, RSA success/failure bits, 8051 ready state and host interface version write, SBus/fabric/PCIe firmware version dumps, SerDes reset during link transitions, chip resource acquire/release under dual-HFI stress, platform config CRC/magic/version rejection tests, integrated scratch-config field reads, GUID read, and probe behavior on simulator/FPGA/ASIC variants with missing firmware.
