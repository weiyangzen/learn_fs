# sources/distributed-fs/ceph-client/drivers/scsi/qla2xxx/qla_mbx.c

Purpose: implements the synchronous and IOCB-backed mailbox command interface for the QLogic/Marvell `qla2xxx` Fibre Channel HBA driver. This file is the adapter firmware control plane: it loads and starts firmware, initializes firmware-visible control blocks and multi-queues, performs discovery and login/logout operations, reads and writes firmware/flash/register/SFP state, drives diagnostics and trace collection, handles NPIV report-id events, and exposes many typed wrappers around mailbox opcodes.

Important APIs/types/functions: `qla2x00_mailbox_command()` is the central serialized mailbox executor. It consumes `mbx_cmd_t`, writes selected `mcp->mb[]` registers according to `out_mb`, waits by interrupt completion or polling, copies selected `in_mb` registers back, and schedules ISP abort/recovery on timeouts. `mb_to_str()` names a small set of IOCB-backed mailbox commands, while `is_rom_cmd()` allows ROM/firmware-loader mailbox opcodes during ISP abort state. Firmware bring-up APIs include `qla2x00_load_ram()`, `qla2x00_execute_fw()`, `qla28xx_load_flash_firmware()`, `qla2x00_get_fw_version()`, `qla2x00_get_fw_options()`, `qla2x00_set_fw_options()`, `qla2x00_verify_checksum()`, `qla2x00_init_firmware()`, `qla2x00_get_firmware_state()`, and `qla2x00_stop_firmware()`. Discovery and fabric APIs include `qla2x00_get_adapter_id()`, `qla2x00_get_retry_cnt()`, `qla2x00_get_port_database()`, `qla24xx_get_port_database()`, `__qla24xx_parse_gpdb()`, `qla24xx_gpdb_wait()`, `qla2x00_get_port_name()`, `qla2x00_get_id_list()`, `qla24xx_gidlist_wait()`, `qla2x00_send_sns()`, `qla24xx_login_fabric()`, `qla2x00_login_fabric()`, `qla2x00_login_local_device()`, `qla24xx_fabric_logout()`, `qla2x00_fabric_logout()`, and `qla2x00_port_logout()`. Error-handling APIs include `qla2x00_abort_command()`, `qla24xx_abort_command()`, `qla2x00_abort_target()`, `qla24xx_abort_target()`, `qla2x00_lun_reset()`, `qla24xx_lun_reset()`, `__qla24xx_issue_tmf()`, `qla2x00_lip_reset()`, `qla2x00_full_login_lip()`, `qla2x00_system_error()`, and `qla_no_op_mb()`. Diagnostics and management APIs include trace controls, serdes access, RAM dump/read/write, SFP read/write, link and ISP stats, DCBX/XGMAC stats, loopback/echo tests, DPORT diagnostics, minidump template retrieval, secure flash update, LED/beacon controls, remote register access, MPI passthrough validation, and raw `qla_mailbox_passthru()`. NPIV integration is handled by `qla24xx_report_id_acquisition()`, `qla24xx_modify_vp_config()`, and `qla2x00_send_change_request()`. `qla24xx_send_mb_cmd()` is the alternate asynchronous-SRB/IOCB path used for non-critical commands that can run in parallel with regular mailbox serialization.

Control flow: the standard flow is: a wrapper fills `mbx_cmd_t` fields, sets `out_mb`, `in_mb`, timeout, flags, optional DMA size, then calls `qla2x00_mailbox_command()`. The executor first rejects permanent PCI failures, failed devices, disconnected/unloading state, EEH busy state, hung 82xx firmware, and non-ROM commands during active ISP abort/retry. It obtains `ha->mbx_cmd_comp` to serialize mailbox access, records `ha->mcp`, then under `ha->hardware_lock` marks `ha->flags.mbox_busy`, writes mailbox registers through chip-specific register layouts, clears interrupt state, triggers the host interrupt, and waits. Normal initialized operation waits on `ha->mbx_intr_comp` with `MBX_INTR_WAIT`; abort or early initialization paths poll via `qla2x00_poll()`. On interrupt completion it clears mailbox state, checks `ha->mailbox_out[0]` for `MBS_COMMAND_COMPLETE`, copies requested return registers, and releases the serializer completion. On timeout it logs register snapshots, may capture a firmware dump, increments `vha->hw_err_cnt`, and either schedules DPC ISP abort or directly invokes `ha->isp_ops->abort_isp()` when already in the DPC thread. Wrappers then interpret firmware-specific mailbox status fields, update host/adapter/fcport state, and often translate firmware errors into `QLA_*` driver return codes.

Firmware and adapter initialization flow: loader paths transfer RISC code to DMA-visible firmware memory, execute firmware with feature bits for NVMe, extended login, exchange offload, BPM/LR distance, PPC semaphore behavior, and supported link speeds, then query firmware version and attributes. `qla2x00_get_fw_version()` persists capability discovery into `ha` and `vha`: firmware versions, attributes, MPI/PHY/serdes/PEP versions, shared/DDR RAM ranges, secure firmware support, SCM support, NVMe/NVMe2 enablement, EDIF enablement, first-burst behavior, and special-feature control-block flags. `qla2x00_init_firmware()` passes the initialization control block DMA address, optional extended init control block, and optional special-feature init block to firmware. Resource count queries update firmware XCB/IOCB counts, NPIV limits, and FCF limits.

Fabric/discovery control flow: adapter-id and report-id paths establish topology and port IDs, update host/vport maps, handle FA-WWN, FCoE VLAN/FCF/MAC fields, BB credit reporting, SCM EDC/RDF status, and n2n direct-connect cases. Port database paths allocate or map DMA buffers, issue GPDB, verify login state, reject stale loop IDs or WWPN mismatches, copy WWNs and port IDs, classify FCP versus NVMe initiator/target/discovery role, record class-of-service and confirmed-completion support, then free/unmap DMA memory. Login and logout are split by firmware generation: older adapters use direct mailbox fabric/local login commands, while FWI2-capable adapters build login/logout IOCBs and submit them through `qla2x00_issue_iocb_timeout()`. Task management on 24xx+ similarly builds IOCBs and follows successful target/LUN reset with marker IOCBs to synchronize queue state.

State and persistence behavior: most state is runtime adapter, vhost, and fcport state in `struct qla_hw_data`, `scsi_qla_host_t`, `fc_port_t`, `req_que`, and firmware-visible DMA objects. Mailbox serialization state is persisted in memory through `ha->mbx_cmd_comp`, `ha->mbx_intr_comp`, `ha->mcp`, `ha->mailbox_out`, `ha->mbx_cmd_flags`, `ha->flags.mbox_busy`, `ha->flags.mbox_int`, `num_pend_mbx_stage1`, `num_pend_mbx_stage2`, `ha->chip_reset`, and `ha->flags.purge_mbox`. Discovery calls mutate `vha->d_id`, host maps, `ha->current_topology`, fcport WWNs, port IDs, login state, scan state, flags, retry counters, and session deletion/relogin flags. Firmware capability queries mutate persistent-in-driver feature flags and cached version/speed/capability fields. Some mailbox wrappers alter persistent device or flash state: flash access control, sector erase/write enable, secure flash update, firmware load-from-flash, driver version registration, port config writes, LED/beacon controls, data-rate settings, and trigger/diagnostic template retrieval interact with firmware/NVRAM or device-local flash outside normal volatile driver memory.

Dependencies and integration points: includes local `qla_def.h` and `qla_target.h`, and depends heavily on prototypes/macros from the wider qla2xxx driver. It integrates with PCI error handling (`pci_channel_offline`, PCI config reads, EEH state), Linux completions, atomic counters, spinlocks, DMA pools/coherent mappings, SCSI command structures, Fibre Channel transport state, DPC recovery, firmware dump/minidump collection, target-mode session deletion (`qlt_schedule_sess_for_deletion`, `qlt_modify_vp_config`), NVMe abort helpers, n2n discovery work, and queue-pair/request/response queue management. The exported functions are called from initialization, probe/resume, discovery, error handling, sysfs/ioctl diagnostics, debug/trace paths, NPIV code in `qla_mid.c`, and target/NVMe support modules.

Risks and edge cases: `qla2x00_mailbox_command()` has a broad blast radius; missed completion, stale `ha->mcp`, wrong `out_mb`/`in_mb` masks, or incorrect chip-family register selection can wedge firmware recovery. Timeout handling is delicate because it may dump firmware, set ISP abort bits, complete the serializer early for direct DPC abort, and wait for EEH reset to avoid DMA unmap races. Several wrappers copy output values even when the mailbox command failed, so callers must distinguish returned values from valid data. Raw passthrough and flash/remote-register operations are powerful and must remain properly gated by existing callers. DMA buffer size fields and endian conversions vary by command; bad sizes can corrupt firmware-visible memory or parse stale data. GPDB/login paths are race-prone because a port can disappear or change WWPN while firmware returns a database entry. Report-id acquisition handles n2n, fabric, loop, and vport states in interrupt/response context and defers some work to DPC; incorrect locking or premature configuration can race with session deletion. Some checks are chip-generation-specific, so adding new hardware without revisiting `IS_QLA*` guards risks disabled features or illegal mailbox commands.

Test signals: build coverage should catch prototypes, mailbox masks, and structure field drift across all qla2xxx modules. Runtime validation should cover firmware load/execute/init on supported generations, interrupt and polling mailbox completions, mailbox timeout recovery, EEH/permanent PCI failure paths, DPC-triggered ISP abort, firmware dump suppression for intentional system-error commands, NPIV enabled and disabled adapters, fabric/loop/n2n topology report-id events, GPDB parsing for FCP and NVMe targets, login/logout success and firmware error statuses, task-management marker issuance, multi-queue initialization/delete, SFP absent and present reads, trace enable/disable, DPORT diagnostics, minidump template retrieval, secure flash update error reporting, raw mailbox passthrough, and hot remove/unload while mailbox commands are pending. Hardware or simulator tests should monitor `hw_err_cnt`, `ISP_ABORT_NEEDED`, `ABORT_ISP_ACTIVE`, `mbx_cmd_comp` release, firmware dump generation, DMA mapping/unmapping balance, and fcport/vport state transitions.
