# sources/distributed-fs/ceph-client/drivers/scsi/esas2r/atioctl.h

Purpose: defines the user/kernel IOCTL ABI and management payload layouts for the ATTO ExpressSAS RAID driver. It covers legacy Express ioctl commands, CSMI SAS management structures, ATTO HBA tunnel commands, VDA management commands, SMP discovery/command payloads, status codes, and the top-level `struct atto_express_ioctl` carrier.

Important APIs/types/functions: the common header is `struct atto_express_ioctl_header` with the `"Express"` signature, return code, channel, retry count, and command range `EXPRESS_IOCTL_MIN` through `EXPRESS_IOCTL_MAX`. Firmware/configuration payloads include `atto_firmware_rw_request`, `atto_param_rw_request`, channel list/info structures, and return codes such as `IOCTL_SUCCESS`, `IOCTL_INVALID_PARAM`, and `IOCTL_GENERAL_ERROR`. CSMI support is represented by `CSMI_CC_*` control codes, `CSMI_STS_*` status codes, class-independent controller/driver/firmware structures, RAID information structures, HBA PHY/passthrough/address/task-management structures, PHY-control structures, `union atto_ioctl_csmi`, and `struct atto_csmi`. ATTO-specific HBA tunnel support is represented by `struct atto_ioctl` and payloads for adapter info/address, memory read/write, trace, SCSI pass-through, device address/info, and adapter control. VDA and SMP payloads are represented by `struct atto_ioctl_vda_*`, `struct atto_ioctl_vda`, `struct atto_ioctl_smp`, and the final union in `struct atto_express_ioctl`.

Control flow: the header has no executable control flow, but it defines the dispatch contract used by `esas2r_ioctl.c`. User space submits an Express ioctl command number with a signed header and one union payload. The driver validates command range/signature/channel, copies the fixed top-level object from user memory, dispatches by command number to firmware, params, channels, SMP, CSMI, HBA, VDA, module-info, or adapter-id handling, and copies the updated top-level object back. Nested `function`, `control_code`, version, status, and length fields further dispatch HBA/VDA/CSMI/SMP operations.

State and persistence behavior: these structures are ABI data carriers, not owned persistent state. They may cause runtime changes when handled by implementation code, including firmware downloads/uploads, parameter reads/writes/defaults, memory access, trace state changes, SCSI/SMP passthrough, VDA configuration/management, adapter resets, and task management. Several fields are flexible or variable-length (`contents[]`, `version_info[]`, `data[1]`, `byte[1]`, large firmware image buffers), so persistence and bounds are controlled by the ioctl handlers rather than this header.

Dependencies and integration points: includes `atvda.h` for VDA configuration and management payload types such as `atto_vda_cfg_init`, `atto_vda_devinfo`, and related information structures. It is included by `esas2r.h`; `esas2r_ioctl.c` uses the command codes and layouts for ioctl dispatch, `esas2r_main.c` exposes sysfs/local buffered HBA ioctl access, discovery code uses `struct atto_ioctl`, and VDA code uses `struct atto_ioctl_vda`. The ABI is tied to user-space ATTO management tools and CSMI-compatible applications.

Risks and test signals: this is a high-risk UAPI-style header even though it lives in the driver tree. Risks include packed/alignment mismatches, 32-bit versus 64-bit pointer-size differences in `struct atto_module_info`, fixed top-level copy sizes that do not cover variable-length payloads, huge embedded firmware image size in `atto_firmware_rw_request`, unchecked `data_length`/`cmd_rsp_len`/`req_length` fields in handlers, and ABI breakage if fields are reordered or resized. Test signals include ioctl fuzzing around length/version/function/status fields, compat-user testing where applicable, CSMI command coverage for supported and unsupported controls, HBA tunnel memory/trace/SCSI pass-through bounds tests, VDA variable payload length tests, SMP direct/non-direct discovery commands, invalid signature/channel/command handling, and structure size checks against user-space tooling expectations.
