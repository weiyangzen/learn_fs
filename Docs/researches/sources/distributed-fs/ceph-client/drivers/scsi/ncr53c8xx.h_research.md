# sources/distributed-fs/ceph-client/drivers/scsi/ncr53c8xx.h

Purpose: declares the public and internal contract used by the NCR/Symbios 53C8xx low-level driver and its bus-specific frontends. It combines Kconfig-derived setup defaults, endian-safe MMIO helpers, chip feature bits, user setup structures, the complete NCR register map, SCRIPTS opcode-building macros, script-visible table formats, attach-time device descriptors, command-private DMA state, and exported function prototypes.

Important APIs/types/macros: configuration defaults include `SCSI_NCR_MAX_TAGS`, `SCSI_NCR_SETUP_DEFAULT_TAGS`, `SCSI_NCR_SETUP_DEFAULT_SYNC`, `SCSI_NCR_SETUP_DISCONNECTION`, parity defaults, `SCSI_NCR_CAN_QUEUE`, `SCSI_NCR_CMD_PER_LUN`, `SCSI_NCR_SG_TABLESIZE`, and reset settle timing. Register access macros include `INB/INW/INL`, `OUTB/OUTW/OUTL`, `OUTON*`, `OUTOFF*`, `OUTL_DSP()`, and `OUTONB_STD()`. Chip description is `struct ncr_chip` with `FE_*` feature bits. User/setup state is `struct ncr_driver_setup` with `SCSI_NCR_DRIVER_SETUP` and `SCSI_NCR_DRIVER_SAFE_SETUP`. Hardware layout is `struct ncr_reg`. Script vocabulary includes `ncrcmd`, phase constants, `SCR_MOVE_*`, `SCR_SEL_*`, `SCR_WAIT_*`, `SCR_COPY*`, register-operation builders, load/store builders, jump/call/return/int encodings, condition macros, and `ncr_build_sge()`. Frontend descriptors are `struct ncr_slot` and `struct ncr_device`. Command-private state is `struct ncr_cmd_priv`. External functions are `ncr_attach()`, `ncr53c8xx_release()`, `ncr53c8xx_intr()`, `ncr53c8xx_init()`, and `ncr53c8xx_exit()`.

Control flow enabled by this header: bus frontends construct a `struct ncr_device` with MMIO base addresses, optional mapped virtual addresses, IRQ, chip feature description, host ID, and differential mode, then pass it with a `scsi_host_template` to `ncr_attach()`. The C file uses the setup defaults to initialize global driver options, uses feature bits to choose register settings and SCRIPTS features, uses MMIO macros for all chip access, uses SCRIPTS builders to define and relocate the chip-side program, and uses `struct ncr_cmd_priv` through `scsi_cmd_priv()` to track whether a command has an active DMA mapping. During unload, frontends call `ncr53c8xx_release()` after unregistering/request cleanup, and module-level setup calls `ncr53c8xx_init()`/`exit()` around SPI transport registration.

State and persistence behavior: this header does not store runtime state by itself, but it defines the shapes of state persisted for the lifetime of the loaded driver. `struct ncr_driver_setup` is initialized from compile-time defaults and optionally overridden by module or boot options in the C file. `struct ncr_chip` describes immutable chip capabilities supplied by probe code. `struct ncr_slot` and `struct ncr_device` are attach-time handoff records. `struct ncr_cmd_priv` is per-SCSI-command transient state used to ensure mapped scatter/gather data is unmapped exactly once. Register values, SCRIPTS tables, queue state, CCBs, TCBs, and LCBs are defined in the C file but depend on the opcodes, register offsets, endianness conversion macros, and constants declared here.

Dependencies and integration points: depends on `<scsi/scsi_host.h>` for `struct Scsi_Host` and the SCSI host template integration. It assumes Linux byte-order definitions and MMIO primitives are available before macro use through the including C file. It encodes NCR/Symbios register definitions originally carried from FreeBSD `ncrreg.h` and therefore must remain aligned with hardware manuals and the C file's `offsetof(struct ncr_reg, ...)` relocation logic. It also integrates with SPI transport by exposing `struct ncr_device` fields and prototypes consumed by wrapper drivers such as 53C720/Zalon style frontends.

Risks: many macros are low-level hardware contracts rather than type-safe functions. Incorrect `struct ncr_reg` offsets, endian lane macros, or SCRIPTS opcode encodings can cause direct hardware misprogramming. `SCSI_NCR_DRIVER_SETUP` and `SCSI_NCR_DRIVER_SAFE_SETUP` are positional initializers for `struct ncr_driver_setup`; field reordering requires updating both. `struct scr_tblsel` changes layout under `SCSI_NCR_BIG_ENDIAN`, so CCB construction and script selection depend on matching CPU/chip addressing mode. Feature bits such as `FE_PFEN`, `FE_RAM`, `FE_DFS`, `FE_EHP`, `FE_MUX`, and `FE_EA` directly gate code paths in the C file; a wrong chip descriptor can enable unsafe hardware behavior. `OUTL_DSP()` and `OUTONB_STD()` include memory barriers because the chip consumes driver-owned DMA structures asynchronously; bypassing those wrappers is a race risk.

Test signals: compile checks are important because many interfaces are macro-expanded `offsetof()` expressions. Useful validation includes building on little-endian and supported big-endian architectures, checking that `sizeof(struct ncr_reg)` and key register offsets match hardware expectations, probing a frontend that fills `struct ncr_device`, verifying `cmd_size >= sizeof(struct ncr_cmd_priv)` at attach, running SCSI scan and SPI transport sysfs operations, exercising sync/wide/tag negotiation to validate SCRIPTS table structures, and performing reset/release paths to confirm register access and command-private mapping state remain consistent.
