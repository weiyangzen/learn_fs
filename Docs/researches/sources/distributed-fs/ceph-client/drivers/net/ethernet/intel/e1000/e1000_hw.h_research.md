# sources/distributed-fs/ceph-client/drivers/net/ethernet/intel/e1000/e1000_hw.h

Purpose: defines the hardware contract for the legacy Intel PRO/1000 `e1000` driver. The header is the shared MAC/PHY/EEPROM register map, descriptor ABI, bit mask catalog, hardware state structure, statistics layout, and exported hardware helper API used by `e1000_hw.c`, `e1000_main.c`, `e1000_ethtool.c`, and `e1000.h`. It covers 82542 through 82547-era devices plus the CE4100 GbE variant, with compatibility definitions for older 82542 register offsets.

Important APIs and types: `e1000_mac_type`, `e1000_media_type`, `e1000_phy_type`, EEPROM/bus/flow-control enums, and PHY status enums classify hardware capabilities and runtime link state. `struct e1000_hw` is the central mutable hardware state: MMIO/flash/CE4100 MDIO mappings, PCI IDs, MAC/PHY/EEPROM types, bus data, flow-control policy, autonegotiation state, MAC addresses, LED state, adaptive IFS fields, manageability flags, PHY tuning flags, and feature/workaround booleans. `struct e1000_hw_stats`, `struct e1000_phy_info`, `struct e1000_phy_stats`, and `struct e1000_eeprom_info` define persisted driver-side snapshots of hardware counters, link diagnostics, and NVM geometry. Descriptor ABIs include `struct e1000_rx_desc`, `union e1000_rx_desc_extended`, `union e1000_rx_desc_packet_split`, `struct e1000_tx_desc`, `struct e1000_context_desc`, and `struct e1000_data_desc`; these layouts are consumed directly by DMA ring setup and packet clean/transmit paths.

Exported function prototypes form the hardware-service API implemented in `e1000_hw.c`: initialization (`e1000_reset_hw`, `e1000_init_hw`, `e1000_set_mac_type`, `e1000_set_media_type`), link setup and status (`e1000_setup_link`, `e1000_phy_setup_autoneg`, `e1000_check_for_link`, `e1000_get_speed_and_duplex`, `e1000_force_mac_fc`), PHY access/reset/info (`e1000_read_phy_reg`, `e1000_write_phy_reg`, `e1000_phy_hw_reset`, `e1000_phy_reset`, `e1000_phy_get_info`, `e1000_validate_mdi_setting`), EEPROM access/checksum/MAC-address load (`e1000_init_eeprom_params`, `e1000_read_eeprom`, `e1000_validate_eeprom_checksum`, `e1000_update_eeprom_checksum`, `e1000_write_eeprom`, `e1000_read_mac_addr`), receive filtering (`e1000_hash_mc_addr`, `e1000_rar_set`, `e1000_write_vfta`), LED control, adaptive interframe spacing, PCI/PCI-X tuning, and port-I/O register access. Error codes are small integer hardware-layer results such as `E1000_ERR_EEPROM`, `E1000_ERR_PHY`, `E1000_ERR_CONFIG`, and `E1000_ERR_RESET`.

Control flow role: this header has no executable flow of its own, but it shapes the driver lifecycle. Probe allocates `struct e1000_adapter`, embeds `struct e1000_hw`, maps BAR0 into `hw->hw_addr`, fills PCI identity fields, calls `e1000_set_mac_type`, `e1000_set_media_type`, `e1000_get_bus_info`, initializes EEPROM parameters, resets hardware, validates EEPROM checksum, and loads the permanent MAC address. Hardware initialization then uses the register constants to clear VLAN/multicast tables, initialize receive-address registers, configure link and flow control, program descriptor writeback policy, and clear read-to-clear counters. Runtime paths in `e1000_main.c` program RX/TX rings using the descriptor structs and ring register offsets, process interrupts using `ICR/IMS/IMC` masks, update multicast/VLAN filters through `RA/MTA/VFTA`, and use `TBI_ACCEPT` during receive cleanup to accept a narrow class of carrier-extension frames while adjusting statistics.

State and persistence behavior: persistent device configuration lives in EEPROM/flash and is represented by EEPROM word offsets, opcodes, checksum rules, and fields such as initial control words, LED settings, flow-control defaults, PHY class, SERDES amplitude, APM/WoL bits, and node address words. `e1000_read_eeprom` and `e1000_write_eeprom` serialize access through the hardware implementation, and the checksum contract requires the first 64 words to sum to `EEPROM_SUM` (`0xBABA`). `struct e1000_hw` stores runtime state across resets and link transitions, including original flow-control settings, autonegotiation advertisement, master/slave configuration, TBI compatibility, PHY DSP/FFE state, adaptive IFS counters, and management-cookie data. MAC and PHY statistics are hardware counters, many read-clear, then accumulated into `struct e1000_hw_stats` by the main driver.

Dependencies and integration points: includes `e1000_osdep.h`, which supplies Linux MMIO/PIO/flash access macros (`er32`, `ew32`, `E1000_WRITE_REG_ARRAY`, `E1000_READ_REG_ARRAY`, `E1000_WRITE_FLUSH`) and chooses normal versus 82542 register offsets from `hw->mac_type`. `e1000.h` includes this header and embeds its hardware/stat/PHY structs in `struct e1000_adapter`; it also casts ring memory to this header's descriptor structs through `E1000_RX_DESC`, `E1000_TX_DESC`, and `E1000_CONTEXT_DESC`. `e1000_hw.c` is the primary implementation of the declared API and consumes nearly every register/PHY/EEPROM bit definition. `e1000_main.c` integrates the definitions with PCI probe/remove, netdev operations, DMA rings, NAPI, watchdog/reset work, VLAN and multicast filtering, interrupt handling, and WoL. `e1000_ethtool.c` uses the same hardware state and descriptor layouts for diagnostics, register access, EEPROM operations, and loopback tests.

Register and hardware-surface coverage: the header enumerates PCI device IDs, BAR decode size, frame-size constants, interrupt masks, receive/transmit descriptor bits, offload context bits, multicast/VLAN/receive address table sizes, wakeup filter structures, host/management interface command structures, CE4100 auxiliary and MDIO register mappings, MAC register offsets, 82542 compatibility offsets, statistics registers, PCI-X/PCIe tuning registers, EEPROM/flash commands, PHY registers, PHY IDs, and PHY-specific bitfields for Marvell M88, Intel IGP, IFE, Realtek 8211/8201, and CE4100-related hardware. The breadth means this file is both a public driver ABI and a large hardware datasheet transcription.

Risks: descriptor structs and bit masks are DMA-visible ABI; changing packing, endianness types, status/error masks, or command bits can corrupt packets or break offloads. Register offsets are selected indirectly by `mac_type`, so misclassification in `e1000_set_mac_type` can send MMIO writes to wrong addresses, especially for 82542 compatibility and CE4100 MDIO/flash paths. EEPROM write/checksum constants touch persistent adapter configuration and can brick or misconfigure hardware if bounds, page-size, opcode, or checksum behavior is wrong. Many counters are read-clear, so polling order affects statistics. `TBI_ACCEPT` is a subtle workaround depending on frame length, VLAN status, carrier-extension byte, and frame error bits; loosening it can pass bad frames, while tightening it can drop valid TBI compatibility traffic. Management/ASF/AMT host-interface and semaphore masks overlap normal driver access and can race firmware if ownership bits are mishandled.

Test signals: build the `e1000` driver with all local include paths to catch prototype, enum, and macro regressions. Probe tests should cover representative PCI IDs for 82542, 82543/82544, 82540/82545/82546, 82541/82547, quad-port variants, VMware 82545EM behavior, and CE4100. Runtime tests should verify reset and `e1000_init_hw`, EEPROM checksum validation/read/write paths, MAC address loading, link setup for copper/fiber/SERDES, autonegotiation and forced speed/duplex, flow-control negotiation, VLAN and multicast filtering, interrupt masks, TX/RX descriptor ownership and checksum/TSO offloads, jumbo frame limits, WoL filters, ethtool diagnostics, statistics accumulation from read-clear counters, and TBI receive workaround behavior.
