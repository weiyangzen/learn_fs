# sources/distributed-fs/ceph-client/drivers/net/ethernet/marvell/octeontx2/af/rvu_npc.c

Purpose: implements the core RVU Admin Function NPC setup and MCAM resource manager for Marvell OcteonTX2/CN10K/CN20K networking. It initializes the parser/KPU and match-key extraction profiles, configures NPC interface miss behavior, installs AF-owned default steering rules, exposes mailbox handlers for raw MCAM entry/counter operations, and maintains software ownership state for MCAM entries and counters.

Important APIs and functions: initialization is centered on `rvu_npc_init()`, `rvu_npc_hw_init()`, `npc_parser_profile_init()`, `npc_load_kpu_profile()`, `npc_load_mkex_profile()`, `rvu_npc_setup_interfaces()`, `npc_mcam_rsrcs_init()`, and `npc_flow_steering_init()`. KPU/MKEX programming helpers include `npc_config_kpuaction()`, `npc_config_kpucam()`, `npc_program_kpu_profile()`, `npc_program_mkex_profile()`, and `npc_fwdb_prfl_img_map()`. Default rule helpers include `rvu_npc_install_ucast_entry()`, `rvu_npc_install_promisc_entry()`, `rvu_npc_install_bcast_match_entry()`, `rvu_npc_install_allmulti_entry()`, `rvu_npc_enable_default_entries()`, `rvu_npc_disable_default_entries()`, and `rvu_npc_update_flowkey_alg_idx()`. Raw mailbox handlers cover MCAM allocation, free, read, write, enable, disable, shift, counter allocation/free/unmap/clear/stats, allocate-and-write, key extraction config readback, parse mode/pkind updates, base steering rule readback, entry stats, and unicast rule clearing.

Control flow: `rvu_npc_init()` gets the NPC block, reads hardware constants, disables every MCAM bank entry before traffic is allowed, allocates PKIND state, programs the selected KPU parser profile, configures protocol checker defaults, sets interface miss actions, programs hash secret keys and MKEX, initializes MCAM software state, scans the active key extraction profile through `npc_flow_steering_init()`, and finally delegates CN20K-specific initialization when needed. Normal MCAM entry programming validates ownership, disables the entry, clears stale CAM words, expands `struct mcam_entry` keywords into CAM0/CAM1 hardware words, writes action and VLAN tag action registers, and reenables the entry if requested. Allocation flow chooses entries from high, middle, or low priority regions using forward and reverse bitmaps; CN20K instead delegates physical/virtual index management to `npc_cn20k_*` helpers and then mirrors allocation into common maps.

State and persistence: persistent software state is stored in `rvu->hw->mcam`: entry and reverse bitmaps, free counts, entry-to-owner, entry-to-counter, counter-to-owner, counter refcount, entry-to-target-pffunc, key size/bank geometry, reserved default-rule offsets, per-interface key fields/features, and the `mcam_rules` list managed by flow steering. Hardware state persists in NPC AF registers for PKIND, KPU CAM/action tables, MKEX KEX/LDATA/LFLAGS, MCAM CAM/action/tag/stat words, miss actions, parser protocol checker config, and match counters. Loaded firmware profile state is held in `rvu->kpu_fwdata`, `rvu->kpu_prfl_addr`, and `rvu->kpu`. `rvu_npc_freemem()` frees bitmaps/maps and unmaps or frees loaded profile memory.

Dependencies and integration: depends on RVU block discovery and resource helpers, mailbox ABI types from `mbox.h`, NIX LF and multicast helpers, CGX pkind programming, KPU/MKEX profile definitions from `npc_profile.h`, exact/hash support from `rvu_npc_hash.h`, CN20K NPC/register helpers, and core RVU PF/VF state. It is the low-level substrate used by `rvu_npc_fs.c` for higher-level flow install/delete and by exact-match code for drop-rule reservation.

Risks: MCAM entry geometry is hardware-specific, and mistakes in bank/key-size conversion can write the wrong entry. Entry updates must disable and clear before rewriting to avoid stale suppressed writes. The software maps are protected by `mcam->lock`; callers that bypass the established mailbox paths can race ownership or counter refcounts. Default PF/VF rule fixups are subtle because PF-installed VF rules may temporarily remain disabled until the VF NIXLF is initialized, and default RSS action changes must be propagated to dependent rules. Firmware KPU/MKEX loading accepts profiles from filesystem or firmware database, so size/signature/version checks are critical. CN20K paths use virtual indexes and per-entry counters, so common code must translate through `npc_cn20k_vidx2idx()` consistently.

Test signals: boot/probe should log selected KPU and MKEX profiles and initialize NPC without fallback warnings. Exercise PF/VF NIX attach/detach, default unicast/broadcast/promisc/allmulti install and enable/disable, RSS algorithm updates, MCAM allocate/free/read/write/shift, counter allocate/free/map/unmap/stats, parse mode and pkind updates, firmware profile fallback, and CN20K virtual-index allocation. Hardware traffic tests should verify default drops on RX miss, TX default forwarding on TX miss, correct broadcast/multicast replication, VF rule enablement after initialization, and counter increments for matched rules.
