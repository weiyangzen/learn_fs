# Research: sources/distributed-fs/ceph-client/drivers/net/ethernet/microchip/vcap/vcap_ag_api.h

## Purpose
`vcap_ag_api.h` is the common autogenerated enum contract for the Microchip VCAP API. It assigns stable enum IDs for VCAP types, keyfield sets, key fields, actionfield sets, and action fields across Sparx5 and LAN966x models. The generated model `.c` files use these IDs as array indexes, and driver code uses them when constructing or validating rules.

## Important APIs, Types, and Functions
- `enum vcap_type` defines ES0, ES2, IS0, IS1, IS2, and `VCAP_TYPE_MAX`.
- `enum vcap_keyfield_set` defines keysets such as IS0 normal tuple modes, IS2/ES2 ARP/IP/MAC modes, ES0 ISDX, and LAN966x-specific keysets.
- `enum vcap_key_field` defines all supported key fields, including VLAN tag fields, ingress/egress ports, L2/L3/L4 packet fields, lookup metadata, range checker bits, and protocol-specific fields.
- `enum vcap_actionfield_set` defines actionset families including Sparx5 classification/full/reduced, base type, ES0, and LAN966x variants.
- `enum vcap_action_field` defines action fields for classification, forwarding, CPU copy, policing, mirroring, VLAN rewrite, ES0 tag rewrite, counters, and pipeline controls.
- Extensive comments document field widths, target chips/stages, and semantic descriptions.

## Control Flow
There is no runtime control flow. The enums are consumed by generated field layout tables, VCAP API rule construction helpers, tc offload code, debugfs name lookups, and Sparx5-specific key selection code.

## State and Persistence Behavior
The header owns no runtime state. Its enum values are persistent ABI-like identifiers inside the driver source tree: generated arrays index by these values, and rule-building code stores them in in-memory rule structures before encoding into hardware.

## Dependencies and Integration Points
This file is included indirectly through `vcap_api.h` and directly or indirectly by Microchip VCAP model and client code. It is shared between Sparx5 and LAN966x support, so it integrates multiple hardware model origins into one enum namespace. Sparx5 implementation files use the keyset and field enums for default fields, keyset validation, selector programming, and debug output.

## Risks and Edge Cases
- Because generated C tables use enum values as sparse indexes, reordering or deleting enum members without regenerating all models breaks field mapping.
- The enum namespace contains chip-specific fields; availability must be checked against a model's field map, not assumed from enum existence.
- Comments include different widths for the same enum on different chips/stages, so callers must use `struct vcap_field` from the selected model for actual encoding width.
- The header generation metadata is newer/different than the Sparx5-specific header in this subset, so model updates should keep common and platform generated artifacts consistent.

## Test Signals
- Compile every Microchip VCAP consumer after regeneration to catch missing enum names.
- VCAP model tests should verify field lookup rejects enum values absent from a selected keyset/actionset.
- tc offload tests should cover representative fields from VLAN, L2, IPv4, IPv6, L4, policing, CPU copy, and ES0 rewrite actions.
- Regeneration diff review should treat enum ordinal changes as high risk.
