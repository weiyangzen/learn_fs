# Research: sources/distributed-fs/ceph-client/drivers/net/ethernet/microchip/sparx5/sparx5_vcap_ag_api.c

## Purpose
`sparx5_vcap_ag_api.c` is an autogenerated Sparx5 VCAP model consumed by the common Microchip VCAP API. It describes the hardware field layout for Sparx5 VCAP stages IS0, IS2, ES0, and ES2: which keysets and actionsets exist, the bit offset and width of each key/action field, typegroup encodings, readable names, and the top-level `struct vcap_info` and `struct vcap_statistics` objects exported to the Sparx5 driver.

## Important APIs, Types, and Functions
- Exports `const struct vcap_info sparx5_vcaps[]`, indexed by `enum vcap_type`.
- Exports `const struct vcap_statistics sparx5_vcap_stats`.
- Defines keyfield arrays such as `is0_normal_7tuple_keyfield`, `is2_mac_etype_keyfield`, `es0_isdx_keyfield`, and ES2 IPv4/IPv6/ARP variants.
- Defines actionfield arrays for IS0 classification/full/reduced, IS2 base type, ES0 rewrite actions, and ES2 base type.
- Defines `struct vcap_set` tables that map enum keysets/actionsets to type IDs and stream widths.
- Defines key/action field map arrays and map-size arrays used by the generic VCAP encoder.
- Defines typegroup arrays and string name arrays used by validation and debug output.

## Control Flow
There is no executable control flow beyond static initialization. At probe time `sparx5_vcap_init()` selects this model through `ctrl->vcaps = consts->vcaps` and `ctrl->stats = consts->vcap_stats`. Later VCAP core paths use the exported arrays to encode rules into cache streams, decode rules from hardware, validate field availability, and print names.

## State and Persistence Behavior
All data is immutable static metadata. It does not own runtime state or persistence. The layout controls how rules are persisted in hardware TCAM/action/counter memories by other code; a wrong offset, width, or typegroup would corrupt hardware programming even though this file itself only holds constants.

## Dependencies and Integration Points
The file depends on `vcap_api.h` for `struct vcap_field`, `struct vcap_set`, `struct vcap_info`, `struct vcap_typegroup`, and `struct vcap_statistics`, and on `sparx5_vcap_ag_api.h` for enum names. It integrates with `sparx5_vcap_impl.c`, the shared Microchip VCAP API (`vcap_api.c`, `vcap_tc.c`), debugfs naming, and tc-flower rule offload users that ask the VCAP API to build Sparx5 rules.

## Risks and Edge Cases
- This file is generated; manual edits risk drifting from hardware XML/register descriptions.
- Type IDs, stream widths, and typegroups must match hardware packing exactly or rules may match unintended traffic.
- ES2 includes an `IP_7TUPLE` keyset with type ID `-1`, so consumers must rely on stream width/typegroups rather than assuming every keyset has a positive type ID.
- Field names cover both Sparx5 and shared enum space; absent map entries are meaningful and must not be interpreted as supported fields.
- The generated timestamp and commit ID differ from the common header generation metadata, so regeneration should be done as a matched model update.

## Test Signals
- Build coverage for `CONFIG_VCAP` and Sparx5 should catch missing enum/table symbols.
- VCAP KUnit/model tests should verify encode/decode sizes, field lookup, typegroup insertion, and name lookups.
- Hardware or mocked tc-flower offload tests should exercise IS0, IS2, ES0, and ES2 rules with counters.
- Regeneration review should compare table deltas against the authoritative Microchip VCAP model, not hand-written expectations.
