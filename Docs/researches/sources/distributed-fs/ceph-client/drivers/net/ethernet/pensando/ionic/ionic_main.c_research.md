# sources/distributed-fs/ceph-client/drivers/net/ethernet/pensando/ionic/ionic_main.c

Purpose: This file provides the module entry/exit path and the shared device/admin command control plane for the Ionic driver. It translates firmware statuses, formats command names for diagnostics, posts and waits for admin queue commands, polls devcmd MMIO completion, performs device/port identify/init/reset, and registers the bus driver and debugfs root.

Important APIs/functions: `ionic_error_to_errno()` maps `enum ionic_status_code` to Linux errno values and is exported in namespace `NET_IONIC`. `ionic_adminq_post_wait()` and `ionic_adminq_post_wait_nomsg()` post admin queue contexts and wait for completion. `ionic_adminq_post()`, `ionic_adminq_wait()`, `ionic_adminq_service()`, `ionic_notifyq_service()`, and `ionic_adminq_poke_doorbell()` implement the async adminq ring mechanics. Device command helpers include `ionic_dev_cmd_wait()`, `ionic_dev_cmd_wait_nomsg()`, `ionic_setup()`, `ionic_identify()`, `ionic_init()`, `ionic_reset()`, `ionic_port_identify()`, `ionic_port_init()`, and `ionic_port_reset()`.

Control flow: Admin queue posting takes `lif->adminq_lock`, verifies the admin QCQ exists, checks ring space and firmware heartbeat, stores the caller context in descriptor metadata, copies the command, and rings the queue doorbell. Completion service checks the CQ color and queue non-emptiness, copies the completion back into each matching context through `comp_index`, completes the wait object, and clears the context pointer. Wait loops use bounded time slices up to `DEVCMD_TIMEOUT`, periodically check heartbeat/FW-reset state, return `-ENXIO` if reset interrupts the command, and flush pending admin descriptors on timeout.

Device command flow: Devcmd waits poll BAR0 `done` while firmware is running and the max timeout has not expired. `IONIC_RC_EAGAIN` retries by clearing done, sleeping, and ringing the devcmd doorbell again if enough time remains. On firmware-down interruption or timeout, the command registers are cleaned. Identify writes the Linux driver identity to devcmd side-data, requests device identity version 2, copies device identity back, logs firmware version, and then identifies classic LIF capabilities. Port init allocates coherent `port_info`, sends port init, raises the port admin state, and unwinds DMA memory on failure.

State and persistence behavior: This file mutates durable device-level state in `struct ionic`: firmware/device identity, `idev->port_info`, `port_info_pa`, devcmd register contents, and the admin queue ring state inside the active LIF. It does not own netdev queue resources. Admin command contexts are caller-owned stack or heap objects that persist only until completion. `ionic_adminq_flush()` clears queued descriptors and contexts after timeout to avoid later completions touching stale wait contexts.

Dependencies: It depends on Linux module, dynamic debug, netdevice, UTS release identity, wait completion, jiffies, and MMIO helpers through Ionic internals. Internal dependencies include `ionic_bus_register_driver()`, `ionic_bus_unregister_driver()`, `ionic_debugfs_create/destroy()`, `ionic_dev_cmd_*()` helpers, heartbeat/FW status helpers, and the LIF identify API.

Integration points: The bus-specific PCI code calls setup/identify/init/reset and LIF/port routines during probe and removal. `ionic_lif.c`, `ionic_phc.c`, firmware update code, RX filter code, and RDMA integration use the exported adminq post/wait machinery. Notifyq service integrates firmware link/reset notifications with LIF deferred work. Module init/exit bracket driver lifetime by creating debugfs and registering/unregistering the Ionic bus driver.

Risks: Adminq timeout handling must prevent use-after-free of caller contexts; flush clears ctx pointers but pending firmware completions can still appear later. Returning success from `__ionic_adminq_post_wait()` when firmware is not running means callers must handle reset state separately. Device command retry on `EAGAIN` is time-budget dependent and could mask slow firmware. Port init sends port state up after init but only reports the first error, so a failed state change may be less visible. Locking order between devcmd mutex, adminq lock, heartbeat, and reset work is critical.

Test signals: Validate probe identify/init/reset paths, firmware version logging, devcmd timeout and `EAGAIN` retry behavior, adminq command success/failure/timeout, notifyq link and reset events, module load/unload, debugfs creation cleanup on bus registration failure, and port info DMA allocation/free. Fault injection for firmware down during adminq/devcmd waits is especially important.
