# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath9k/ar9002_phy.h

Purpose: Defines AR9002 PHY/baseband register addresses, bit masks, shifts, and calibration constants used by `ar9002_phy.c` and related ath9k hardware code. It is the register contract for channel programming, CCA/noise-floor handling, spectral scan, radar/PHY error features, antenna diversity, spur mitigation, calibration, TX power control, gain tables, Bluetooth coexistence switch control, and PHY mode selection.

Important APIs, types, and constants: The file contains no functions or types beyond preprocessor constants. Register groups include base PHY control (`AR_PHY_TEST`, `AR_PHY_TURBO`, `AR_PHY_ACTIVE`), RF/ADC timing (`AR_PHY_RF_CTL*`, `AR_PHY_ADC_CTL`, `AR_PHY_SETTLING`, `AR_PHY_RXGAIN`, `AR_PHY_DESIRED_SZ`), signal detection and CCA (`AR_PHY_FIND_SIG*`, `AR_PHY_AGC_CTL1`, `AR_PHY_CCA`, extension and per-chain CCA registers), PLL/synth (`AR_PHY_SYNTH_CONTROL`, `AR_PHY_PLL_CTL*`), spectral scan (`AR_PHY_SPECTRAL_SCAN` fields and Kiwi variants), radar registers (`AR_PHY_RADAR_0/1` fields), spur-mitigation masks (`AR_PHY_TIMING_CTRL4_*`, `AR_PHY_TIMING11_*`, `AR_PHY_SPUR_REG_*`, pilot/channel masks), antenna diversity (`AR_PHY_MULTICHAIN_GAIN_CTL`, `AR_PHY_9285_ANT_DIV_*`, BT coexistence constants), calibration measurements (`AR_PHY_CALMODE*`, `AR_PHY_CAL_MEAS_*`), PHY mode (`AR_PHY_MODE_*`), CCK controls, TX power-control registers, and per-chip CCA nominal/min/max values for 5416/9280/9285/9271/9287.

Control flow and use model: Control flow is macro-driven in callers. `ar9002_phy.c` uses these constants to mask fields with `REG_RMW_FIELD()`, construct values with `SM()`, extract values with `MS()`, and set/clear bits. Channel-change code uses synth, CCK, and PHY mode fields. Spur mitigation uses timing, spur, pilot, and channel-mask constants. Noise-floor code reads CCA masks and sign-extends field values. Antenna and BT coexistence code reads/writes multi-chain gain and switch registers. Spectral scan config uses the AR9280 and Kiwi count/short-repeat bit definitions. TX power, calibration, and gain constants are shared with reset/calibration and initval logic elsewhere in ath9k.

State and persistence behavior: The header owns no runtime state. Its constants describe volatile MMIO/PHY register state that is programmed during attach, reset, channel changes, calibration, spectral operations, antenna changes, and test modes. The CCA limit constants become runtime policy when `ar9002_hw_set_nf_limits()` copies them into `struct ath_hw`. Because macros are compiled into multiple call sites, any change affects all future register accesses after rebuild but does not migrate or persist runtime hardware state.

Dependencies and integration points: The file is included by `ar9002_phy.c` and depends only on ordinary C preprocessing, but semantically depends on ath9k register access helpers and bitfield conventions. It integrates with AR9002 init tables in `ar9002_initvals.h`, hardware attach in `ar9002_hw.c`, shared channel/reset/calibration in `hw.c`, spectral debug/common code, tx99 support, EEPROM/calibration paths, and optional Bluetooth coexistence. Several addresses are chain-indexed with macros such as `AR_PHY_TIMING_CTRL4(_i)` and `AR_PHY_CAL_MEAS_*(_i)`, so callers must supply valid chain indices matching hardware chain masks.

Risks and edge cases: Register definitions are a hardware ABI. Wrong masks or shifts can corrupt unrelated fields, especially for CCA/noise-floor extraction, spectral count programming, spur delta/frequency programming, antenna diversity, and TX power-control fields. Several fields differ between AR9280-style and later Kiwi-style hardware, such as spectral scan count and short-repeat bits; callers must choose the right macro for the SREV. Some constants overlap addresses for different meanings (`AR_PHY_SLEEP_CTR_LIMIT` and `AR_PHY_SYNTH_CONTROL`, `AR_PHY_M_SLEEP` and `AR_PHY_CALMODE`), so context matters. Signed CCA values require correct field width before sign extension. Magic constants for Bluetooth antenna diversity and switch-com programming are board-sensitive.

Test signals: Compile tests should cover all users of the macros under normal, spectral, BT coexistence, and tx99 configurations. Runtime signals include correct channel synthesis, stable reset/calibration, expected NF readings and CCA bounds per chip family, working spectral scan on AR9280 and Kiwi-family parts, correct spur suppression when EEPROM spurs exist, antenna diversity get/set behavior, BT coexistence switching, and TX power/gain calibration. Register-dump comparison against known-good AR9002 programming is the most direct validation for mask/shift regressions.
