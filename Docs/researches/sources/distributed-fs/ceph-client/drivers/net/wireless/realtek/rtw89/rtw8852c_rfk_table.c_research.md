# sources/distributed-fs/ceph-client/drivers/net/wireless/realtek/rtw89/rtw8852c_rfk_table.c

## Purpose
Defines the RTL8852C RF calibration table payloads consumed by the rtw89 RFK parser. The file has no callable functions of its own; it is a catalog of `static const struct rtw89_reg5_def` register scripts plus exported `const struct rtw89_rfk_tbl ..._tbl` descriptors generated by `RTW89_DECLARE_RFK_TBL()`. These scripts cover DACK/DRCK, IQK setup and restore, DPK helper setup, RX SRAM debug access, and a large TSSI initialization/tracking/enable-disable surface for RF paths A and B across 2.4/5/6 GHz bands.

## Important APIs, Types, and Functions
The important data type is `struct rtw89_reg5_def`, whose `flag`, `path`, `addr`, `mask`, and `data` fields are interpreted by `rtw89_rfk_parser()` in `phy.c`. The table descriptors are `struct rtw89_rfk_tbl` objects named after each local array with a `_tbl` suffix. The file uses three parser op macros: `RTW89_DECL_RFK_WM()` for masked BB/MAC register writes, `RTW89_DECL_RFK_WRF()` for RF path register writes, and `RTW89_DECL_RFK_DELAY()` for microsecond delays.

The DACK/DRCK tables include `rtw8852c_dack_reload_defs_tbl`, per-path DACK reset tables, `rtw8852c_dack_defs_s0_tbl`, `rtw8852c_dack_defs_s1_tbl`, and `rtw8852c_drck_defs_tbl`. IQK and DPK-facing tables include `rtw8852c_iqk_rxk_cfg_defs_tbl`, per-path `rtw8852c_iqk_afebb_restore_defs_*_tbl`, `rtw8852c_read_rxsram_pre_defs_tbl`, `rtw8852c_read_rxsram_post_defs_tbl`, MDPD order tables 0 through 3, and DPK KIP power/clock on/off tables. TSSI tables include common and band/path-specific system setup, TX power control BB setup, HE TB setup, DCK setup, BB gain split, slope calibration origins, alignment defaults for 2G/5G/6G, slope run/track programming, TXAGC offset moving average setup, and per-path TSSI enable/disable scripts.

## Control Flow
Runtime control flow is driven by callers in `rtw8852c_rfk.c`. `rtw89_rfk_parser()` walks a selected `rtw89_rfk_tbl` in order and dispatches each row by `flag`: masked writes call `rtw89_phy_write32_mask()`, RF writes call `rtw89_write_rf()`, and delay entries call `udelay()`. Ordering inside each array is therefore behavioral, not decorative.

DACK flow uses `rtw8852c_drck_defs_tbl` after DRCK polling, uses `rtw8852c_dack_defs_s0_tbl` and `rtw8852c_dack_defs_s1_tbl` before triggering path-specific DACK, uses reset tables selected by RF path, and uses reload definitions before restoring backed-up DACK coefficients. IQK RXK setup applies `rtw8852c_iqk_rxk_cfg_defs_tbl` after RX clock/path mode setup; IQK AFE/BB restore selects path A or B restore tables after calibration. DPK uses RX SRAM pre/post tables only around debug dumping, MDPD order tables via `_dpk_set_mdpd_para()`, and KIP power/clock tables in `_dpk_kip_pwr_clk_onoff()`.

TSSI flow is the heaviest consumer. `_tssi_set_sys()` always applies common system registers, then selects 2G or 5G tables per path; 6G uses the non-2G branch for this specific system step. Subsequent helpers select path and band tables for TX power control, HE TB, TSSI DCK, BB gain split, slope calibration, 2G/5G/6G alignment defaults, slope programming, slope trigger, tracking, TXAGC offset moving average, and final enable/disable.

## State and Persistence Behavior
This file itself is read-only data. State changes occur only when another module parses a table, at which point hardware registers and RF path registers are modified. Several scripts are part of larger persistent calibration state machines in `rtwdev`: DACK reload writes backed-up coefficients stored in `rtwdev->dack`; DPK table choices affect selected backup coefficient slots and KIP/MDPD state; TSSI enable tables are paired with caller-side updates to `rtwdev->is_tssi_mode[]` and `rtwdev->tssi.base_thermal[]`.

Because the arrays are `static const`, their lifetime is the module lifetime and they are safe to reference through exported descriptors. Persistence across channel changes, suspend/resume, or firmware state is not managed here; callers decide when to replay tables.

## Dependencies and Integration Points
The file includes `rtw8852c_rfk_table.h`, which includes `phy.h` for `struct rtw89_rfk_tbl` and the RFK macros. It depends on bit/mask helpers such as `BIT()` and `MASKDWORD`, RF path constants such as `RF_PATH_A` and `RF_PATH_B`, and the generic parser implementation in `phy.c`.

The direct integration point is `rtw8852c_rfk.c`, which references every exported `_tbl` symbol. Higher-level integration is with the rtw89 PHY/RF calibration framework, Bluetooth coexistence notifications around RFK operations, channel/band selection from `struct rtw89_chan`, thermal/TSSI tracking from firmware or EFUSE-derived data, and hardware register definitions in the RTL8852C register headers.

## Risks
The tables are hardware-sequencing sensitive. Reordering entries, changing masks, using the wrong path offset, or replacing a masked write with a full-width write can silently break calibration or leave the RF/BB in an invalid mode. Many path A/path B tables are nearly mirrored with address windows around `0x58xx` versus `0x78xx` or `0x56xx` versus `0x76xx`; copy/paste errors are plausible and hard to catch by compile tests. Band-specific TSSI alignment and slope tables contain literal calibration defaults whose correctness depends on RTL8852C silicon revision expectations.

The parser performs no bounds or semantic validation beyond table size. A bad `flag` would index the handler table, and a correct flag with a bad address/mask still compiles. Delay values are microsecond busy waits, so expanding them affects calibration latency. The tables also assume callers select a valid sequence; for example enable and disable scripts must remain paired with the surrounding TSSI state updates.

## Test Signals
Useful signals are successful `rtw89` build/link coverage for all exported table names, probe on RTL8852C hardware, RFK debug logs for DACK/DRCK/IQK/DPK/TSSI without timeout messages, channel switches across 2.4/5/6 GHz, bandwidth switches through 20/40/80/160 MHz, DBCC path-specific TSSI enable/disable, stable TX power and EVM after TSSI tracking, DPK reload success on returning to a calibrated channel, RX SRAM debug output when enabled, suspend/resume or restart replay of calibration, and absence of RFK warnings such as DACK, IQK, DPK sync, or loop-limit failures.
