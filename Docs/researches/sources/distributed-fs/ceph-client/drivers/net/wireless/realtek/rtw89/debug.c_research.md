# sources/distributed-fs/ceph-client/drivers/net/wireless/realtek/rtw89/debug.c

Purpose: Implements the Realtek rtw89 driver's debug messaging and debugfs control surface. With `CONFIG_RTW89_DEBUGFS`, it exposes register/RF access, transmit-power table inspection, MAC memory and debug-port dumps, raw H2C injection, early-H2C staging, firmware crash/SER simulation, coexistence toggles, firmware-log toggles, PHY/station/CAM state dumps, DM disable controls, MLO mode controls, beacon tracking, and firmware-provided MAC diagnostics. With `CONFIG_RTW89_DEBUGMSG`, it owns the exported `rtw89_debug_mask` module parameter and the gated `rtw89_debug()` printer.

Important APIs, types, and functions: The public entry points are `rtw89_debugfs_init()`, `rtw89_debugfs_deinit()`, and `rtw89_debug()`. The debugfs framework is built around `struct rtw89_debugfs_priv_opt`, `struct rtw89_debugfs_priv`, `struct rtw89_debugfs`, and `struct rtw89_debugfs_iter_data`. Generic dispatch is handled by `rtw89_debugfs_file_read()`, `rtw89_debugfs_file_write()`, and helper callbacks that optionally enter `wiphy_locked_debugfs_read()` or `wiphy_locked_debugfs_write()`. Major debugfs callbacks include `rtw89_debug_priv_read_reg_*`, `rtw89_debug_priv_write_reg_set()`, `rtw89_debug_priv_read_rf_*`, `rtw89_debug_priv_write_rf_set()`, `rtw89_debug_priv_rf_reg_dump_get()`, `rtw89_debug_priv_txpwr_table_get()`, `rtw89_debug_priv_mac_reg_dump_*`, `rtw89_debug_priv_mac_mem_dump_*`, `rtw89_debug_priv_mac_dbg_port_dump_*`, `rtw89_debug_priv_send_h2c_set()`, `rtw89_debug_priv_early_h2c_*`, `rtw89_debug_priv_fw_crash_*`, `rtw89_debug_priv_ser_counters_get()`, `rtw89_debug_priv_btc_info_get()`, `rtw89_debug_priv_btc_manual_set()`, `rtw89_debug_priv_fw_log_manual_set()`, `rtw89_debug_priv_phy_info_get()`, `rtw89_debug_priv_stations_get()`, `rtw89_debug_priv_disable_dm_*`, `rtw89_debug_priv_mlo_mode_*`, `rtw89_debug_priv_diag_mac_get()`, and `rtw89_debug_priv_beacon_info_get()`. Static tx-power description types `struct txpwr_ent`, `struct txpwr_map`, and `struct dbgfs_txpwr_table` encode AX/BE by-rate, limit, and RU-limit register layouts.

Control flow: `rtw89_debugfs_init()` clones `rtw89_debugfs_templ`, creates the device's `rtw89` debugfs directory below the wiphy debugfs directory, then registers two groups of files through macros that bind file names to callback state. Reads allocate a per-file reusable buffer via `devm_kzalloc()`, call the relevant `cb_read`, store the number of bytes in `rused`, and serve data through `simple_read_from_buffer()` on subsequent offsets. Writes copy user data into a NUL-terminated kernel buffer, then dispatch to `cb_write`. Selection-style entries, such as `read_reg`, `read_rf`, `mac_reg_dump`, `mac_mem_dump`, and `mac_dbg_port_dump`, store parameters in the debugfs private union during write and consume them during read.

Hardware diagnostic flows are mostly direct. Register/RF callbacks parse hex or decimal arguments and call the low-level `rtw89_read*`, `rtw89_write*`, `rtw89_read_rf()`, and `rtw89_write_rf()` helpers. TX power reporting leaves power-save mode, reads regulatory/SAR/TAS/antenna-gain context, walks chip-generation-specific tx-power register maps, decodes signed 7-bit power entries according to `txpwr_factor_mac`, and formats table rows. MAC register and memory dumps choose fixed page ranges or indirect memory windows; selected RTL8852C TX FIFO memory reads temporarily set `B_AX_TCR_FORCE_READ_TXDFIFO`. MAC debug-port dumps first configure a selected port's mux registers, validate availability against HCI type, chip family, and MAC enable state, then iterate the selector range and read the configured status register after a short delay.

Firmware and runtime controls have side effects. `send_h2c` converts hex text into binary and sends raw H2C through `rtw89_fw_h2c_raw()`. `early_h2c` stores converted blobs on `rtwdev->early_h2c_list` under the wiphy lock, with a `00 00` sentinel clearing all early H2Cs. `fw_crash` accepts crash type 1, 2, or 3 and triggers firmware CPU exception, L1 reset simulation, or L0 reset simulation through chip-generation-specific helpers; L0 simulation may deliberately avoid setting `RTW89_FLAG_CRASH_SIMULATING`. SER counters read both software counters and AX/BE hardware registers after leaving power-save mode. BTC and firmware-log entries update coexistence manual state or send firmware-log H2Cs. PHY and station dumps walk mac80211 stations/interfaces atomically, dereference link state under RCU where needed, and format rate, RSSI, EVM, SNR, CAM, BA CAM, and packet-offload state. MLO controls disable MLO DM, then apply MLSR switching to MLD VIFs. `diag_mac` leaves low-power state and interprets firmware diagnostic rule elements, filtering by HCI and active band before reading normal or PCI config registers.

State and persistence behavior: Debugfs file state persists in the per-device `rtwdev->debugfs` clone until deinit; selection parameters and enabled dump-package bits are stored in `struct rtw89_debugfs_priv`. Read buffers are allocated lazily and reused, while `rused` preserves the previous read length for nonzero file offsets. Many callbacks mutate persistent driver or hardware state: raw register writes, RF writes, debug mux selection, TX FIFO force-read bits, firmware H2C queues, crash simulation flags, BTC manual control, firmware-log enablement, `hal->disabled_dm_bitmap`, and MLO mode. `rtw89_debug_mask` is a module parameter, exported for other rtw89 objects, and gates debug and hex-dump output. `rtw89_debugfs_deinit()` only frees the cloned metadata; debugfs removal is presumably handled by the enclosing wiphy/debugfs teardown.

Dependencies and integration points: Includes rtw89 core subsystems (`coex.h`, `fw.h`, `mac.h`, `pci.h`, `phy.h`, `ps.h`, `reg.h`, `sar.h`, `util.h`) plus Linux debugfs, wiphy locking, RCU, mac80211 station/interface iteration, hex parsing, and vmalloc allocation. Register names and bit masks come from `reg.h`; chip-generation dispatch depends on `rtwdev->chip`, `chip->mac_def`, and feature bits in `rtwdev->fw`. The file integrates with firmware H2C paths, SER recovery simulation, BTC coexistence, SAR/TAS/regulatory reporting, CAM allocation state, MLO/mlsr switching, packet offload lists, beacon tracking, and firmware element parsing.

Risks: This is an intentionally privileged debug surface with direct register, RF, memory, H2C, firmware crash, DM, and MLO controls; misuse can destabilize hardware or firmware. Several diagnostic paths alter mux or force-read registers and do not always restore previous values, which is acceptable for debug dumping but risky if used during active traffic. `rtw89_debugfs_file_read()` keeps a lazily allocated buffer without explicit per-open isolation, so repeated reads of the same debugfs node share device-level state. Large dumps rely on fixed buffer sizes and `rtw89_might_trailing_ellipsis()` rather than full dynamic sizing. Error paths in hardware dump code can exit after partial side effects. The MAC debug-port selector table is hard-coded for specific AX register layouts and has many chip/HCI validity branches. Raw H2C and crash simulation paths depend on firmware readiness and feature bits, but still provide a powerful failure-injection interface.

Test signals: Build coverage should include all combinations of `CONFIG_RTW89_DEBUGFS` and `CONFIG_RTW89_DEBUGMSG`, plus AX and BE chip-generation objects that reference exported debug symbols. Runtime smoke tests can read every read-only node, perform harmless select/read operations for `read_reg`, `read_rf`, `mac_reg_dump`, `mac_mem_dump`, and `mac_dbg_port_dump`, and verify locked callbacks do not trigger lockdep warnings. Hardware validation should cover PCIe vs USB/SDIO validity filtering, DBCC/CMAC1 cases, RTL8852C-specific register branches, BE crash triggers, firmware diagnostic rules, MLO debug controls, and buffer truncation indicators on large dumps. Negative tests should feed malformed arguments, unsupported crash types, non-hex H2C data, unsupported MAC pages, and unavailable debug ports.
