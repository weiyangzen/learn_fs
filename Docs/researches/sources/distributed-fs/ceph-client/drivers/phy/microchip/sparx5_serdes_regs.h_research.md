# sources/distributed-fs/ceph-client/drivers/phy/microchip/sparx5_serdes_regs.h

Purpose: This autogenerated header is the register contract for the Microchip Sparx5 SerDes driver. It does not implement runtime logic; it defines target IDs, target-size classes, register address macros, and bitfield helpers used by `sparx5_serdes.c` to program 6G, 10G, and 25G lane and CMU blocks. The register address macros wrap the project-local `__REG(...)` tuple format and depend on the external `tsize` table to compute per-target strides.

Important APIs/types/functions: The exported pieces are `enum sparx5_serdes_target`, `enum sparx5_serdes_tsize_enum`, `extern const unsigned int *tsize`, `TSIZE(o)`, `__REG(...)`, and hundreds of `*_SET(x)` / `*_GET(x)` macros built on `FIELD_PREP` and `FIELD_GET`. Important register families include `SD10G_LANE_*`, `SD25G_LANE_*`, `SD6G_LANE_*`, `SD_CMU_*`, `SD_CMU_CFG_*`, `SD_LANE_*`, and `SD_LANE_25G_*`. Fields cover transmit emphasis/taps, RX CTLE/DFE/CDR, polarity, reset, PLL lock/loss, PCS-to-PMA mode, data width, rate selection, quiet mode, and status/debug observation.

Control flow: Consumers choose a lane/CMU target macro with an instance index, pass the resulting tuple to the Sparx5 register accessor layer, and combine field helpers to prepare or decode values. No loops, callbacks, or side effects exist in this file. Its "flow" is compile-time expansion into target, group offset, register offset, width, and replication metadata.

State and persistence: The header stores no state. Persistence is hardware register state created by writes from the driver using these definitions. The only cross-file state dependency is the `tsize` array defined by `sparx5_serdes.c`; an incorrect size table would corrupt addressing across all generated macros.

Dependencies and integration points: Depends on Linux `bitfield.h`, `types.h`, and `bug.h`. It integrates only with the Microchip Sparx5 PHY implementation and the kernel register helper conventions used there. Because the file is generated by `cml-utils`, manual edits risk diverging from vendor register descriptions.

Risks: The main risks are silent register-address or bit-mask drift, accidental misuse of similarly named 10G/25G/6G fields, and no compile-time semantic validation that a field belongs to the target being programmed. Many macros expose reserved or hardware-test controls, so consumer code must sequence reset, PLL, lane power, and training bits carefully.

Test signals: Build coverage catches syntax, missing `tsize`, and bitfield macro issues. Runtime test signals are successful SerDes bring-up, link training across supported Ethernet/PCIe modes, PLL lock/loss status bits such as `*_LOL`, reset-done status bits such as `*_PMA_RST_DONE`, and absence of link instability after changing rate, width, polarity, or equalization settings.
