# sources/distributed-fs/ceph-client/drivers/crypto/talitos.c

Purpose: implements the Freescale Integrated Security Engine, also known as SEC/Talitos, as a Linux Crypto API provider. It drives SEC1 and SEC2-style descriptor hardware for AEAD `authenc(...)`, AES/DES/3DES skciphers, message digests/HMACs, and an optional hardware RNG, using device-tree capability masks to register only algorithms the underlying block advertises.

Important APIs and control flow: low-level helpers convert DMA addresses into `struct talitos_ptr`, map/unmap single buffers and scatterlists, allocate extended descriptors, and submit descriptors through `talitos_submit()`. Submission is per-channel: a caller-selected channel owns a software FIFO, `head_lock` protects enqueue, `submit_count` prevents overrunning the hardware fetch FIFO, the descriptor is DMA-mapped, and its physical address is written to `TALITOS_FF/TALITOS_FF_LO`. Interrupt handlers are generated for SEC1/SEC2 topologies, acknowledge ISR bits, mask done interrupts, and schedule tasklets; tasklets call `flush_channel()` to walk completed FIFO entries, unmap descriptors, invoke request callbacks, and release FIFO slots. `talitos_error()` decodes channel status, logs execution-unit status through `report_eu_error()`, either continues SEC2 channels or resets channels/device, and completes affected requests with errors. The hwrng path uses RNGU reset/status/FIFO registers through `talitos_rng_init()`, `talitos_rng_data_present()`, and `talitos_rng_data_read()`.

Crypto request paths build descriptor pointer slots for each operation. `aead_setkey()` parses `crypto_authenc_keys`, maps concatenated auth/encryption keys, and AEAD encrypt/decrypt allocate `talitos_edesc` objects then call `ipsec_esp()`. That function populates HMAC key/data, cipher IV/key/input/output, optional ICV storage, SEC2 link tables or SEC1 bounce buffers, and chooses hardware or software ICV verification callbacks. Skcipher operations validate block alignment, allocate descriptors, set encrypt or inbound header bits, and submit through `common_nonsnoop()`, which maps IV, key, input, output, and IV-out slots. Hash/HMAC operations use `struct talitos_ahash_req_ctx` to preserve MDEU context, buffer partial blocks, handle SHA224 software initialization when hardware lacks SHA224 constants, split oversized SEC1 requests via `sec1_ahash_process_remaining`, and submit one or two chained descriptors through `common_nonsnoop_hash()`.

State and persistence behavior: persistent device state lives in `struct talitos_private`: MMIO bases for global and execution-unit registers, IRQs, channel FIFOs, feature flags, tasklets, registered algorithm list, and RNG registration state. Per-transform state is `struct talitos_ctx`, including selected SEC channel, descriptor-header template, DMA-mapped key material, key lengths, and IV scratch. Per-request state is encoded in `struct talitos_edesc` plus hash request contexts; DMA mappings are created per request and undone in completion callbacks. Hardware state includes channel fetch FIFOs, descriptor done writeback, MDEU hash contexts, RNG FIFO state, and key/IV/output buffers described by DMA pointers. Module removal unregisters algorithms, RNG, IRQs, and tasklets but relies on devm allocation for most private memory.

Dependencies and integration points: depends on Linux Crypto API internal AEAD/skcipher/hash interfaces, `crypto_engine`-independent async callbacks, DMA mapping, scatterwalk/scatterlist helpers, OF platform probing, IRQ mapping, tasklets, PowerPC-style big-endian MMIO helpers, `hwrng`, and descriptor/register definitions from `talitos.h`. Device tree must provide `fsl,num-channels`, `fsl,channel-fifo-len`, `fsl,exec-units-mask`, and `fsl,descriptor-types-mask`; compatibles select feature quirks such as SEC1 format, SEC2.1 hardware auth check, SHA224 hardware init, HMAC acceptance, and SEC3 source link-table extent semantics. Crypto users integrate via `/proc/crypto` names such as `cbc(aes)`, `ctr(aes)`, `authenc(hmac(sha256),cbc(aes))`, `sha256`, and `hmac(sha512)`.

Risks and test signals: risks include subtle SEC1/SEC2 descriptor-format divergence, DMA mapping error paths not consistently checking mapping failures, request FIFO accounting depending on negative `submit_count` initialization, global-channel round-robin assuming power-of-two channel count, software ICV fallback paths needing exact scatter offsets, SEC1 bounce-buffer/chained-descriptor handling for large or partial hash updates, possible request leakage or stale key DMA if transform teardown races active requests, and algorithm registration silently skipping templates when capability masks or feature flags are wrong. There is a likely bug-risk pattern in `current_desc_hdr()`: it dereferences `fifo[iter].desc` while searching without checking for an empty slot. Test signals include probe success with valid DT properties, IRQ topology coverage for one/two interrupt lines, `tcrypt`/crypto self-tests for registered AEAD/skcipher/hash/HMAC algorithms, SEC1 and SEC2 large scatterlist coverage, negative tests for bad ICV returning `-EBADMSG`, RNG registration/readback when RNGU is advertised, device/channel reset recovery after injected descriptor errors, no DMA-API warnings, and removal without tasklet or IRQ use-after-free.
