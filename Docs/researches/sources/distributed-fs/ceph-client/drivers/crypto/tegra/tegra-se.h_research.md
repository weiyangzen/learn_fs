# sources/distributed-fs/ceph-client/drivers/crypto/tegra/tegra-se.h

Purpose: defines the shared NVIDIA Tegra Security Engine register map, bitfield helpers, algorithm IDs, device/register descriptors, runtime context structures, key APIs, host1x submission API, reserved keyslot helpers, and host1x opcode encoders.

Important APIs and types: register constants cover SE ownership, stream ID, SHA registers, AES0/AES1 registers, config/mode fields, key destination/address/data/manifest registers, AAD/message length, result registers, last-block fields, operation bits, KAC manifest fields, address-high encodings, and composite config templates for AES/GCM/CMAC/CBC-MAC/SHA operations. `enum se_aes_alg` and `enum se_hash_alg` define internal algorithm IDs. `struct tegra_se_alg` wraps crypto-engine algorithm unions. `struct tegra_se_regs` abstracts AES versus hash register offsets. `struct tegra_se_hw` carries compatible-specific register tables, host1x class, KAC version, and algorithm init/deinit callbacks. `struct tegra_se` is the per-device runtime object. `se_algname_to_algid()` maps Linux Crypto API names to internal IDs. Inline helpers select reserved keyslots 14/15, test reserved status, and encode host1x opcodes.

State and persistence behavior: the header owns no mutable state but fixes every cross-file ABI in the Tegra SE driver. Runtime state in `struct tegra_se` persists across crypto requests and includes shared command buffers, crypto engine, host1x resources, MMIO base, stream ID, owner ID, and manifest callback. Register macros define how command buffers program persistent hardware state such as keyslots, result registers, counters, and stream routing.

Dependencies and integration points: depends on Linux bitfield, IOMMU, host1x, crypto AEAD/engine/hash/SHA/skcipher headers, and constants such as `SZ_4M`. It is consumed by all Tegra SE source files and exposes the symbols implemented in `tegra-se-aes.c`, `tegra-se-hash.c`, `tegra-se-key.c`, and `tegra-se-main.c`.

Risks and test signals: risks include duplicate `SE_CRYPTO_CFG_XTS_DECRYPT` definitions, algorithm-name mapping drift versus registered `cra_name` strings, host1x opcode encoders lacking range checks, address-size fields assuming requested lengths fit 24 bits, register table omissions such as unused `out_addr`, and all callers relying on native-endian command words. Test signals include compile coverage for all users, crypto algorithm init mapping every registered name, command traces matching hardware docs, static checks for duplicate macros, XTS/GCM/CCM/CMAC register programming tests, and operation with IOVA addresses needing high address bits.
