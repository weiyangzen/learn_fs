# sources/distributed-fs/ceph-client/drivers/greybus/core.c

## Purpose

`core.c` is the Greybus bus core. It defines the `greybus` Linux bus, performs bundle-to-driver matching, emits Greybus uevents, wraps Greybus driver registration, and initializes the global Greybus subsystems used by host-device and operation layers. It is the root integration point that lets Greybus bundles appear as devices and bind to protocol drivers.

## Important APIs, Types, and Functions

- `greybus_disabled()` exposes the boot/module `nogreybus` switch to Greybus users.
- `greybus_bus_type` supplies `.match`, `.uevent`, `.probe`, `.remove`, and `.shutdown` callbacks for the Greybus bus.
- `greybus_register_driver()` and `greybus_deregister_driver()` adapt `struct greybus_driver` into `struct device_driver`.
- `greybus_match_one_id()` and `greybus_match_id()` implement vendor/product/class matching against `struct greybus_bundle_id`.
- `greybus_probe()` activates a bundle through the interface control connection, sets runtime PM state, and invokes the protocol driver's `probe()`.
- `greybus_remove()` resumes the bundle, disables RX or forces non-offloaded connections down, calls `disconnect()`, deactivates the bundle, and unwinds runtime PM.
- `gb_init()` and `gb_exit()` register the bus, debugfs root, host-device ID state, and operation caches/workqueue.

## Control Flow

Module initialization first honors `nogreybus`, creates the debugfs root, registers the bus, initializes host-device support, and initializes the operation subsystem. A host controller later creates `gb_host_device`, `gb_svc`, `gb_module`, `gb_interface`, `gb_control`, and `gb_bundle` devices on this bus. Matching only succeeds for bundle devices and is based on the Greybus driver's static ID table.

During probe, the core finds the matching ID, runtime-resumes the parent interface, asks the control protocol to activate the bundle, enables runtime PM on the bundle device, and calls the protocol driver. Remove performs the inverse ordering and tries to stop incoming traffic before invoking the driver's disconnect hook.

## State and Persistence Behavior

Persistent state is minimal: the `nogreybus` parameter and global registered bus/subsystem state. Bundle runtime PM state is manipulated during probe/remove, but actual interface, module, connection, and operation state lives in other files. The core assumes bundle drivers destroy all connections during failed probe and disconnect, and warns if connection lists remain non-empty.

## Dependencies and Integration Points

This file depends on the public Greybus headers, device model, runtime PM, debugfs initialization from `debugfs.c`, host-device setup from `hd.c`, operation setup from `operation.c`, control operations, bundle lifecycle, and tracepoint definition generated by including `greybus_trace.h` with `CREATE_TRACE_POINTS`.

## Risks and Edge Cases

- `greybus_remove()` logs runtime-resume failure but continues removal, so disconnect paths must tolerate partially resumed devices.
- Failed driver probes rely on drivers having cleaned connections; only `WARN_ON()` enforces this.
- Dynamic IDs are explicitly not implemented.
- Bundle deactivation is skipped if the interface is already marked disconnected, shifting cleanup responsibility to interface/SVC teardown.
- Ordering in `gb_init()` and `gb_exit()` is strict; operation and host-device cleanup must remain inverse to initialization.

## Test Signals

Useful signals include bus registration/unregistration, driver bind/unbind for matching and non-matching bundles, uevent variables for host/module/interface/control/bundle/SVC devices, runtime PM transitions around probe/remove, failure injection in bundle activation and protocol driver probe, and lockdep or tracepoint validation during hot unplug.
