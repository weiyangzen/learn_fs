# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/smu/smu_8_0_enum.h

Purpose: generated AMD SMU 8.0 enumeration header. It defines numeric value domains used by generated register fields for SMU/GFX8-era debug selection, surface layout, address tiling, color/depth/buffer/image formats, cache policies, performance-monitor modes, array types, and memory-power controls. It also defines a few SRBM clock-gating address-range constants. The file does not perform conversions or program hardware; it names the legal encoded values that other register headers and driver code can place into fields.

Important APIs and types: the interface is a collection of `typedef enum` declarations plus four `#define` address-range constants under `SMU_8_0_ENUM_H`. Debug selection is represented by `DebugBlockId` and compressed selector variants `DebugBlockId_BY2`, `DebugBlockId_BY4`, `DebugBlockId_BY8`, and `DebugBlockId_BY16`, covering graphics, memory, DMA, video, command processor, shader, texture, color/depth, cache, LDS, and reserved block IDs. Surface and addressing enums include `SurfaceEndian`, `ArrayMode`, `PipeTiling`, `BankTiling`, `GroupInterleave`, `RowTiling`, `BankSwapBytes`, `SampleSplitBytes`, `NumPipes`, `PipeInterleaveSize`, `BankInterleaveSize`, `NumShaderEngines`, `ShaderEngineTileSize`, `NumGPUs`, `MultiGPUTileSize`, `RowSize`, `NumLowerPipes`, `TileType`, `NonDispTilingOrder`, `MicroTileMode`, `TileSplit`, `SampleSplit`, `PipeConfig`, `NumBanks`, `BankWidth`, `BankHeight`, `BankWidthHeight`, and `MacroTileAspect`. Format and render enums include `ColorTransform`, `CompareRef`, `ReadSize`, `DepthFormat`, `ZFormat`, `StencilFormat`, `CmaskMode`, `QuadExportFormat`, `QuadExportFormatOld`, `ColorFormat`, `SurfaceFormat`, `BUF_DATA_FORMAT`, `IMG_DATA_FORMAT`, `BUF_NUM_FORMAT`, and `IMG_NUM_FORMAT`. Cache, memory, and monitoring enums include `GATCL1RequestType`, `TCC_CACHE_POLICIES`, `MTYPE`, `PERFMON_COUNTER_MODE`, `PERFMON_SPM_MODE`, `SurfaceTiling`, `SurfaceArray`, `ColorArray`, `DepthArray`, `ENUM_NUM_SIMD_PER_CU`, `MEM_PWR_FORCE_CTRL`, `MEM_PWR_FORCE_CTRL2`, `MEM_PWR_DIS_CTRL`, `MEM_PWR_SEL_CTRL`, and `MEM_PWR_SEL_CTRL2`.

Control flow: there is no executable control flow. The values are consumed as field encodings when other code builds register values, packet fields, debug selectors, performance-counter setup, or surface/addressing descriptors. The debug-block enums model selection granularity: the base `DebugBlockId` has many individual block and instance IDs, while the `_BY2`, `_BY4`, `_BY8`, and `_BY16` variants provide coarser selector spaces that step through related hardware blocks. The surface and format enums describe how memory layout and pixel/data interpretation choices are encoded before hardware uses them for rendering, sampling, compression, depth/stencil, buffer/image access, or performance instrumentation.

State and persistence behavior: the enum declarations are compile-time types and do not store state. The encoded values may become persistent hardware state only after a caller writes them into registers, command streams, descriptors, or firmware tables. Once written, persistence is owned by the destination register, ring packet, or memory object, not by this header. Reserved values are part of the ABI and should remain explicit so generated layouts preserve numeric compatibility, but they do not indicate safe software-owned states.

Dependencies and integration points: this header is part of the generated `include/asic_reg/smu` family and complements address headers such as `smu_8_0_d.h` and field-mask headers such as `smu_8_0_sh_mask.h`. In this source tree, the directly used SMU8 runtime include is `smu_8_0_d.h`; this enum header is not directly included by the narrow SMU8 PowerPlay files found during reference search, but its enum names and value domains match generated ASIC headers used throughout AMDGPU generations. Integration is therefore mostly through generated register-field definitions and code that needs the same numeric encodings for GFX8/SMU8-compatible register programming. The `CG_SRBM_START_ADDR`, `CG_SRBM_END_ADDR`, `CG_SRBM_DEC0_START_ADDR`, and `CG_SRBM_DEC0_END_ADDR` macros provide clock-gating/SRBM address-window constants rather than enum types.

Risks: enum values are hardware-visible encodings, not arbitrary software labels. Renumbering, deduplicating, or deleting reserved entries can silently corrupt field programming while still compiling. Many type names, such as `SurfaceFormat`, `BUF_DATA_FORMAT`, and `IMG_DATA_FORMAT`, are reused in other generated AMD ASIC headers; including multiple generation headers in one translation unit can create type-name collisions. The `_BY*` debug-block enums are not simple bit shifts of every base enum entry; they are separate generated selector tables and must not be derived mechanically without checking the values. Format enums include legacy and reserved encodings, compressed texture formats, FMASK formats, and 32-as-N reinterpretation modes, so using the wrong domain, for example `BUF_DATA_FORMAT` where `IMG_DATA_FORMAT` is expected, can produce valid numeric values with incorrect hardware meaning.

Test signals: validation is mostly compile-time and hardware-behavior based. Build targets that include generated SMU/GFX8 register headers should catch type redefinition or missing-value problems. Runtime tests should cover surface creation and rendering with linear, 1D/2D/3D tiled, PRT, thin/thick, depth, and display tiling modes; color/depth/stencil formats; buffer and image data/number formats including compressed and FMASK variants; performance-monitor counter and SPM modes; cache-policy and memory-type programming; debug-block selection paths; and memory power control states. Golden register traces or known-good generated header comparisons are strong signals because there is little functional code to unit test inside this header itself.
