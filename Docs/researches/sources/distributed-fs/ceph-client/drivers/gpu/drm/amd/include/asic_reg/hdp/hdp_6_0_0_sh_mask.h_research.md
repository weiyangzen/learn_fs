# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/hdp/hdp_6_0_0_sh_mask.h

Purpose: generated AMDGPU HDP 6.0.0 bitfield catalog. It maps HDP register fields to shifts and masks for host aperture attributes, flag handling, write-combine controls, HDP clock/power management, MEMIO transactions, XDP D2H flush and BAR updates, P2P mailbox/BAR state, XDP status, and MMHUB response/error reporting.

Important APIs, types, and functions: this header exports preprocessor constants only. There are no C functions, structs, or mutable objects. Its main API is the generated naming contract `HDP_REGISTER__FIELD__SHIFT` and `HDP_REGISTER__FIELD_MASK`, consumed by `REG_SET_FIELD()` and `REG_GET_FIELD()`. Important field groups include `HDP_NONSURFACE_*` base/swap/VMID bits; surface/non-surface flag and clear bits; `HDP_HOST_PATH_CNTL` write-combine timer/enables and all-surfaces disable; `HDP_MISC_CNTL` idle, outstanding write count, early write ack, NACK/FED, simultaneous access, read watermark, and write-burst controls; `HDP_MEM_POWER_CTRL` atomic/RC SRAM power mode enables, hysteresis, and delays; `HDP_CLK_CNTL` register-clock count and soft override bits; `HDP_MEMIO_CNTL`, `HDP_MEMIO_STATUS`, and data/address fields; `HDP_XDP_D2H_FLUSH` and `HDP_XDP_D2H_BAR_UPDATE` fields; P2P mailbox address and BAR valid/flush/address fields; host/MC request attribute fields; XDP flush/busy/sticky/check fields; and `HDP_XDP_MMHUB_ERROR` response/NACK/FED bits.

Control flow: the header has no executable flow. Runtime behavior appears when `hdp_v6_0.c` reads HDP registers and uses these macros to update fields. In `hdp_v6_0_update_clock_gating()`, `REG_SET_FIELD()` uses `HDP_CLK_CNTL__RC_MEM_CLK_SOFT_OVERRIDE_*` and `HDP_MEM_POWER_CTRL__ATOMIC_*`/`RC_*` fields to force clocks, disable power modes, enable one selected LS/DS/SD mode, set memory power control enables, and release the clock override. `hdp_v6_0_get_clockgating_state()` reads `regHDP_MEM_POWER_CTRL` and tests the `ATOMIC_MEM_POWER_LS_EN`, `ATOMIC_MEM_POWER_DS_EN`, and `ATOMIC_MEM_POWER_SD_EN` masks. XDP/MEMIO/P2P fields define possible runtime decode/programming paths for generic HDP and diagnostics code.

State and persistence behavior: the file stores no runtime state. It describes state held by HDP hardware: non-surface aperture address and VMID, sticky read/write flags, host-path write-combine configuration, power-gating controls, clock overrides, MEMIO transaction progress and errors, flush commands/counters, P2P BAR address validity, and MMHUB response status. Some fields are control bits, some are status bits, and some are clear-on-write style fields; the header does not encode access permissions or ordering requirements, so consumers must know register semantics.

Dependencies: paired with `hdp_6_0_0_offset.h` for register addresses and base indexes. Depends on AMDGPU's generated field-name convention and helper macros in the SOC15/register-access layer. It is directly tied to `hdp_v6_0.c` and to the HDP function table selected through IP discovery. Because `hdp_v6_0.c` manually handles an HDP 6.1.0 `regHDP_CLK_CNTL` offset variant while still using the same `HDP_CLK_CNTL` field layout, this mask header also implicitly supports that compatible field layout.

Integration points: directly included by `sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/hdp_v6_0.c`. That file uses the `HDP_MEM_POWER_CTRL` and `HDP_CLK_CNTL` field definitions to implement clock-gating update and reporting. The same mask names can be used by `WREG32_FIELD15`, `REG_SET_FIELD`, and `REG_GET_FIELD` callers wherever HDP 6.0.0 registers are accessed. The XDP field groups align with `sdma_v6_0.c` and `sdma_v7_0.c` inclusion of the offset header for HDP flush coordination, even though those files do not directly include this mask file.

Risks and edge cases: the HDP 6.0.0 layout is close to but not identical with HDP 5.2.1 and 7.0.0. This file lacks 5.2.1/7.0.0 fields such as `HDP_MMHUB_TLVL`, `HDP_MMHUB_UNITID`, `EARLY_WRACK_MISSING_PROTECT`, `SYSHUB_CHANNEL_PRIORITY`, GPU IOV violation logs, and HDP 7.0.0 MMHUB error-clear fields. Incorrectly reusing those fields in HDP 6 code will fail to compile or, worse, if open-coded, touch undefined bits. `HDP_MEM_POWER_CTRL` and `HDP_CLK_CNTL` masks are high-risk because a bad field can leave clocks forced on/off or enable multiple SRAM power modes. Error/status fields such as `HDP_XDP_STICKY` and `HDP_XDP_MMHUB_ERROR` should be accessed with correct clear semantics rather than blind full-register writes.

Test signals: compile coverage of `hdp_v6_0.c` validates the active `REG_SET_FIELD()` and mask-test references. Static validation should confirm every mask is contiguous at its shift and matches the generated hardware register source. Runtime signals include correct HDP clock-gating flag reporting, stable suspend/resume or power-management transitions with HDP LS/DS/SD enabled, successful HDP flush visibility for SDMA and CPU/GPU synchronization paths, and expected status/error decoding when MEMIO, XDP busy/sticky, or MMHUB response errors are injected on HDP 6.0.0 hardware.
