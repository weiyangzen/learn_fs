# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/smu/smu_8_0_d.h

Purpose: generated AMD SMU 8.0 register address header. It gives the Carrizo/SMU8 power-management and thermal driver code symbolic names for SMU, MP0/MP1, thermal controller, temperature monitor, power-management, core-power, SPMI, DRAM request, IOC, interrupt, and CAC-related register offsets. The file is pure hardware ABI data: it does not implement policy, access helpers, or runtime behavior.

Important APIs and data: the exported interface is a set of `#define` constants under the `SMU_8_0_D_H` include guard. `mm*` names are direct MMIO register indices consumed by AMDGPU/PowerPlay register helpers. `ix*` names are indexed or indirect register addresses, typically used through SMC/SMN/indirect access paths. Major groups include `ixTHM_*` thermal-controller registers; `ixTMON0_*` and `ixTMON1_*` local/remote temperature-monitor data, presence, configuration, coefficient, and debug registers; `ixTHM_FUSE*` thermal fuse registers; `mmMP0PUB_IND_*` and `mmMP_SMUIF*_MP0PUB_IND_*` indirect index/data aliases; `mmSMU_MP1_SRBM2P_MSG_*`, `RESP_*`, and `ARG_*` mailbox registers; MP crossbar, SRBM, CRBBM, DRAM request/return, IOC, and interrupt-control registers; PWRHW indirect aliases; CPU, NB, UNBPM, core power, and SPMI per-core register families; SMU power-management controls for SCLK, LCLK, ULV, ACPI, PCIE power-gating, VDDGFX idle, and deep sleep; and graphics CAC leakage/accumulator constants.

Control flow: this header has no executable control flow. Runtime flow appears in consumers. `pm/powerplay/smumgr/smu8_smumgr.c` includes this file and uses `mmSMU_MP1_SRBM2P_ARG_0`, `mmSMU_MP1_SRBM2P_RESP_0`, and `mmSMU_MP1_SRBM2P_MSG_0` for the MP1 SMC mailbox sequence: wait until the response register is nonzero, write the argument, clear the response, write the message, then wait for a nonzero response. The same file writes `mmMP0PUB_IND_INDEX_0` and `mmMP0PUB_IND_DATA_0` for MP1 SRAM indirect access during firmware upload and SMU memory operations. `pm/powerplay/hwmgr/smu8_hwmgr.c` reads `ixTHM_TCON_CUR_TMP` through `cgs_read_ind_register(..., CGS_IND_REG__SMC, ...)` to calculate the current thermal sensor value. The header therefore sits at the boundary between higher-level power-management state machines and the actual SMU/thermal hardware address map.

State and persistence behavior: the macros are compile-time constants and hold no state. The registers they name are hardware-backed state. Mailbox registers hold transient SMC command, argument, and response values shared between the host driver and MP1 firmware. Thermal registers expose live temperature, interrupt, trip, PROCHOT, and thermal-controller state. Temperature monitor coefficient and fuse registers describe calibration and fuse-derived state. Power-management registers reflect or control clocks, voltage, P-states, deep sleep, idle behavior, PCIE power-gating, ACPI signaling, and northbridge or core power state. DRAM/IOC registers coordinate indirect memory transactions. Core and SPMI registers are per-core power controller state. Values persist only according to hardware reset and firmware behavior; the header provides no caching, locking, validation, or persistence layer.

Dependencies and integration points: this file is paired with `smu_8_0_sh_mask.h`, which provides field masks for many of these registers. It is included directly by `pm/powerplay/smumgr/smu8_smumgr.c` and `pm/powerplay/hwmgr/smu8_hwmgr.c`; `amdgpu/vi.c` also carries a generated-register comment for SMU 8.0 constants. Consumers depend on `cgs_read_register`, `cgs_write_register`, `cgs_read_ind_register`, `cgs_write_ind_register`, `PHM_WAIT_FIELD_UNEQUAL`, `PHM_GET_FIELD`, and related PowerPlay/AMDGPU register helpers to choose the correct access path. The `mm*` versus `ix*` distinction is important: using an indirect address with a direct MMIO helper, or the reverse, can target the wrong hardware aperture.

Risks: these constants are a hardware ABI. A wrong value can misroute SMC mailbox messages, break firmware upload, hang waits on response registers, read an invalid temperature, write an unrelated power-management register, or corrupt low-level power state. The repeated index/data aliases for MP0PUB and PWRHW interfaces are easy to misuse because many names intentionally map to nearby or identical offsets. The two CPU/core/SPMI register families have similar names with `_0` and `_1` suffixes; copy/paste errors could program the wrong core. Thermal values also require companion mask semantics, especially range selection and fixed-point scaling from `THM_TCON_CUR_TMP`, so address constants alone are not enough to interpret sensor data safely.

Test signals: useful validation includes compile coverage of SMU8 PowerPlay files; successful Carrizo/SMU8 boot and firmware upload; SMC command paths completing without `PHM_WAIT_FIELD_UNEQUAL` timeouts; correct behavior of `smu8_send_msg_to_smc_with_parameter()` and argument readback; thermal sensor reads matching plausible temperatures across range-selection modes; suspend/resume and GPU reset without stale mailbox or indirect-index state; power-management tests that exercise SCLK/LCLK deep sleep, VDDGFX idle, PCIE power-gating, ACPI interrupts, and NB/core power state; and absence of register access faults in SMC indirect reads/writes.
