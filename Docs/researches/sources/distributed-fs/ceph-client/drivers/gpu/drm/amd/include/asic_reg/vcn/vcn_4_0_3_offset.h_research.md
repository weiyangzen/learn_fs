# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/vcn/vcn_4_0_3_offset.h

Purpose: this generated AMDGPU header is the VCN 4.0.3 register-offset map. It does not implement runtime logic; it defines the symbolic MMIO register indices that the VCN and JPEG drivers use to program AMD media hardware. Each normal register macro is paired with a `..._BASE_IDX` macro, and the pair is consumed by SOC15 register helpers to combine the register index with the selected IP block base and hardware instance. The file covers UVD/VCN decode, VCPU firmware windows, LMI memory apertures, RBC/JRBC rings, JPEG decode rings, MMSCH scheduler/mailbox registers, dynamic power-gating, clock-gating, virtualization, RAS/EDC status, and indirect context/LMI indexes.

Important APIs/types/functions: there are no C functions, structs, enums, or callable APIs in this file. Its public interface is the macro namespace. Important groups include `regUVD_TOP_CTRL`, `regUVD_CGC_GATE`, `regUVD_CGC_CTRL`, `regUVD_SUVD_CGC_GATE`, and `regUVD_SUVD_CGC_CTRL` for top-level and sub-block clock gating; `regUVD_GPCOM_VCPU_DATA0`, `regUVD_GPCOM_VCPU_DATA1`, and `regUVD_GPCOM_VCPU_CMD` for host/firmware command exchange; `regUVD_RB_BASE_LO`/`HI`, `regUVD_RB_SIZE`, `regUVD_RB_RPTR`, `regUVD_RB_WPTR`, plus the `2` through `4` variants for decode rings; `regUVD_VCPU_CACHE_OFFSET*`, `regUVD_VCPU_CACHE_SIZE*`, and `regUVD_LMI_VCPU_CACHE*_64BIT_BAR_*` for firmware code/data aperture setup; `regUVD_LMI_*_64BIT_BAR_*`, `regUVD_LMI_*_VMID`, `regUVD_LMI_CTRL`, and `regUVD_LMI_STATUS` for memory-interface programming; `regMMSCH_*` for the multimedia scheduler ucode, SRAM, context, mailbox, and GPU IOV state; `regUVD_JPEG_*`, `regJPEG_*`, `regUVD_JRBC*_UVD_JRBC_*`, and `regUVD_JMI*_UVD_*` for JPEG decode and its per-pipe ring/memory interfaces; and `regVCN_RAS_*`, `regVCN_*ERR*`, `regUVD_RAS_*`, and `regUVD_SECURITY_REG_VIO_REPORT` for RAS, poison, EDC, and security status. The `ixUVD_*` macros at the end are indirect register indexes rather than SOC15 direct register offsets.

Control flow: the header executes no control flow beyond the include guard `_vcn_4_0_3_OFFSET_HEADER`. Runtime control flow is in its consumers. `amdgpu/vcn_v4_0_3.c` includes this file and passes its macros to `SOC15_REG_ENTRY_STR`, `SOC15_REG_OFFSET`, `RREG32_SOC15`, `WREG32_SOC15`, `RREG32_SOC15_OFFSET`, and `WREG32_SOC15_OFFSET` while bringing up firmware, programming VCPU cache windows, enabling/disabling clock gates, configuring DPG, setting decode ring base/size/pointers, polling `regUVD_STATUS`, issuing soft resets, initializing MMSCH, and querying RAS poison/error status. `amdgpu/jpeg_v4_0_3.c` includes the same file for JPEG register tables, per-pipe JRBC offsets, MMSCH initialization, JPEG power/clock gating, ring read/write pointers, packet emission target registers, job-done polling, and clean/stall handling. A changed macro silently redirects those callers to a different MMIO register.

State and persistence: the file has no mutable software state and persists nothing. The constants identify hardware state that persists in the device until reset or later driver writes. Stateful targets include ring GPU addresses, ring sizes, read/write pointers, interrupt enable/status/ack registers, power and clock gate state, firmware cache/non-cache mappings, VMIDs, LMI 64-bit BARs, scratch registers, MMSCH context and mailbox state, JRBC/JMI per-pipe state, and RAS/error latches. Because many registers program GPU physical addresses or memory aperture boundaries, incorrect offsets can leave the hardware executing from the wrong firmware window, reading the wrong ring, writing completion data to the wrong memory, failing to acknowledge interrupts, or retaining bad RAS/error state until reset.

Dependencies and integration: the only direct dependency is the C preprocessor, but the values are meaningful only with AMDGPU's SOC15 base-address infrastructure and the matching bitfield header `vcn/vcn_4_0_3_sh_mask.h`. The direct generation-specific users are `drivers/gpu/drm/amd/amdgpu/vcn_v4_0_3.c` and `drivers/gpu/drm/amd/amdgpu/jpeg_v4_0_3.c`. The same symbolic names are intentionally shared across related VCN headers so driver code can stay mostly generation-stable while include selection supplies ASIC-specific offsets. This header contains 2215 `#define` entries, including 1086 `_BASE_IDX` entries; 750 of those base-index macros are `1`, while 336 are `0`. The `BASE_IDX` split matters because the first VCN/JPEG blocks use one SOC15 base entry, while additional JRBC/JMI pipe ranges and indirect indexes use another base/indexing convention.

The source block inventory is: `aid_uvd0_uvddec` at `0x1fb00`; `aid_uvd0_ecpudec` at `0x1fe00`; `aid_uvd0_uvd_mpcdec` at `0x1ff30`; `aid_uvd0_uvd_rbcdec` at `0x1ff90`; `aid_uvd0_lmi_adpdec` at `0x20090`; JPEG decode/SCLK blocks at `0x20f00` and `0x21000`; JRBC0 and JMI0 at `0x21100` and `0x21180`; JPEG common decode/SCLK at `0x21400` and `0x21480`; power-gating at `0x1f800`; MMSCH at `0x20d00`; scheduler LMI at `0x21c00`; VCN EDC at `0x21d20`; JRBC1 through JRBC7 at `0x1e000` through `0x1e600`; JMI1 through JMI7 at `0x1e080` through `0x1e680`; and indirect `uvdctxind`/`lmi_adp_indirect` blocks with base address `0x0`. The repeated JRBC/JMI blocks are structurally similar but intentionally have distinct offsets so multi-pipe JPEG code can apply `jpeg_v4_0_3_core_reg_offset()` and target each pipe.

Risks: this is generated hardware data, so the primary risk is silent offset or base-index drift. Offsets are register indices, not complete byte MMIO addresses; direct arithmetic or use outside SOC15-style helpers can address the wrong register. The repeated low/high 64-bit BAR pairs are easy to update incompletely, and an incorrect high/low pair can point the media engine at unrelated GPU memory. The repeated JRBC/JMI pipe blocks are also risky because their names differ only by pipe number while their `_BASE_IDX` values differ from the first-instance blocks. Mismatches between this offset header and `vcn_4_0_3_sh_mask.h` can make callers set valid bit masks in invalid registers. The most sensitive regions are ring base/pointer registers, interrupt route/status/ack registers, reset and power-gating controls, MMSCH mailbox/context registers, memory aperture/VMID registers, and RAS/security/EDC status registers.

Test signals: compile coverage catches missing or renamed macros in VCN 4.0.3 and JPEG 4.0.3 code, but it does not prove the numeric offsets. Runtime validation should cover VCN firmware load, MMSCH initialization and mailbox response, decode ring start/stop, JPEG decode across all active JRBC pipes, ring read/write pointer movement, interrupt enable/ack delivery, dynamic power-gating suspend/resume, clock-gating transitions, SR-IOV/GPU IOV paths, and RAS/poison query/reset handling. Practical failure signals include timeouts waiting for `regMMSCH_VF_MAILBOX_RESP`, stuck `regUVD_STATUS` or `regUVD_JRBC*_UVD_JRBC_STATUS` polls, unchanged `regUVD_RB_WPTR`/`RPTR` or JRBC pointers, missed JPEG/VCN interrupts, failed media playback or decode conformance tests, GPU page faults from bad BAR/VMID programming, and GPU reset during VCN/JPEG bring-up or suspend/resume.
