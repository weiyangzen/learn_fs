# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/vcn/vcn_5_3_0_offset.h

Purpose: provides the generated register-offset map for AMD VCN 5.3.0 hardware. The header is a preprocessor-only contract: it defines symbolic register indices for UVD/VCN/JPEG blocks and paired `..._BASE_IDX` macros used by the AMDGPU SOC15/SOC24 register-access helpers to form real MMIO addresses. It lets the driver program media decode, JPEG decode, local memory interface windows, ring buffers, power/clock gating, interrupts, virtualization mailboxes, UMSCH/MES scheduler state, and memory-check/error paths without hard-coding numeric offsets at every call site.

Important APIs/types/functions: there are no C functions, structs, enums, or executable APIs in this file. Its public interface is the macro namespace guarded by `_vcn_5_3_0_OFFSET_HEADER`. The file contains 1,675 `#define` entries: 42 `ixUVD...` indirect-register offsets, 816 `_BASE_IDX` definitions, and 1,632 `reg...` SOC register symbols. Important families include indirect context and LMI adapter offsets such as `ixUVD_CGC_MEM_CTRL`, `ixUVD_SW_SCRATCH_00` through `ixUVD_SW_SCRATCH_15`, `ixUVD_LMI_CRC*`, and `ixUVD_MEMCHECK*`; power and DPG registers such as `regUVD_IPX_DLDO_CONFIG`, `regUVD_IPX_DLDO_STATUS`, `regUVD_JPEG_POWER_STATUS`, `regUVD_DPG_LMA_CTL`, and `regUVD_DPG_PAUSE`; firmware, status, reset, and interrupt registers such as `regUVD_GPCOM_SYS_CMD`, `regUVD_VCPU_INT_STATUS`, `regUVD_SYS_INT_ACK`, `regUVD_STATUS`, `regUVD_CNTL`, `regUVD_SOFT_RESET`, and `regUVD_GPCOM_VCPU_CMD`; VCPU cache/non-cache windows such as `regUVD_VCPU_CACHE_OFFSET*`, `regUVD_VCPU_CACHE_SIZE*`, and `regUVD_LMI_VCPU_CACHE*_64BIT_BAR_*`; ring and memory aperture registers such as `regUVD_RB_BASE_LO`, `regUVD_RB_WPTR`, `regUVD_LMI_RBC_RB_VMID`, and `regUVD_LMI_RBC_IB_64BIT_BAR_HIGH`; JPEG/JRBC symbols such as `regUVD_JPEG_CNTL`, `regUVD_JPEG_PITCH`, `regUVD_JRBC0_UVD_JRBC_RB_WPTR`, `regUVD_JRBC0_UVD_JRBC_STATUS`, `regUVD_LMI_JRBC_RB_64BIT_BAR_LOW`, `regJPEG_SYS_INT_EN`, and `regJPEG_CGC_GATE`; doorbell and scheduler symbols such as `regVCN_JPEG_DB_CTRL`, `regVCN_UMSCH_MAILBOX0`, `regVCN_UMSCH_RB_WPTR`, `regVCN_UMSCH_SYS_INT_STATUS`, and `regVCN_MES_CNTL`; and MES control/status/aperture aliases such as `regVCN_MES_MTVEC_LO`, `regVCN_MES_MSTATUS_LO`, `regVCN_MES_INTERRUPT_DATA_31`, and `regVCN_MES_DC_APERTURE15_CNTL`.

Control flow: no runtime control flow executes in this header. Compile-time control is limited to the include guard. At runtime these constants are substituted into callers that perform hardware bring-up, power transitions, ring programming, interrupt handling, and polling. The direct in-tree consumer found for this exact header is `drivers/gpu/drm/amd/amdgpu/jpeg_v5_3_0.c`, which includes it with `vcn_5_3_0_sh_mask.h` and uses the offsets in SOC15 helpers. That consumer writes `regUVD_IPX_DLDO_CONFIG_ONO1` and polls `regUVD_IPX_DLDO_STATUS` for JPEG power gating; reads/writes `regUVD_JPEG_POWER_STATUS`; programs `regJPEG_CGC_CTRL`, `regJPEG_CGC_GATE`, `regJPEG_DEC_GFX10_ADDR_CONFIG`, and `regJPEG_SYS_INT_EN`; configures the JPEG doorbell with `regVCN_JPEG_DB_CTRL`; initializes the JRBC ring through `regUVD_LMI_JRBC_RB_VMID`, `regUVD_LMI_JRBC_RB_64BIT_BAR_LOW/HIGH`, `regUVD_JRBC0_UVD_JRBC_RB_RPTR`, `regUVD_JRBC0_UVD_JRBC_RB_WPTR`, `regUVD_JRBC0_UVD_JRBC_RB_CNTL`, and `regUVD_JRBC0_UVD_JRBC_RB_SIZE`; and checks idle/progress through `regUVD_JRBC0_UVD_JRBC_STATUS`. Any wrong offset changes the effective MMIO target inside those flows rather than failing locally in this header.

State and persistence: the file owns no mutable state and persists nothing. It names hardware-visible registers whose contents live in the device until overwritten, power-gated, or reset. The state described by these names includes scratch registers, firmware command and acknowledgement mailboxes, interrupt enable/status/ack latches, clock-gating configuration, power-gating status, ring base addresses and read/write pointers, 64-bit GPU-memory BAR pairs, VMID selectors, VCPU instruction/data/cache windows, local memory interface arbitration/latency/performance counters, JPEG output-buffer state, JRBC indirect-buffer and preemption-fence state, UMSCH ring/mailbox state, MES machine registers and interrupt data, and SLMI/MMSCH non-cache apertures. Because many entries are low/high halves or parallel pointer/control groups, partial or mismatched edits can leave persistent hardware state pointing at the wrong GPU address or waiting on the wrong completion bit.

Dependencies and integration: this header depends only on the C preprocessor but is meaningful only inside AMDGPU's generated ASIC register-map convention. The numeric values are register indices, not standalone byte addresses; callers combine them with IP block identifiers such as `VCN` or `JPEG`, instance numbers, and the paired `_BASE_IDX` entries through helpers such as `SOC15_REG_OFFSET`, `RREG32_SOC15`, `WREG32_SOC15`, `WREG32_P`, `SOC15_WAIT_ON_RREG`, and DPG/SRAM programming helpers. It is expected to stay synchronized with `vcn_5_3_0_sh_mask.h`, which supplies the bit masks and shifts used with these offsets, and with JPEG/VCN driver code for the same ASIC generation. Address blocks represented here are `uvdctxind` and `lmi_adp_indirect` at base `0x0`, `uvd_uvd_pg_dec` at `0x1f800`, `uvd_uvddec` and `uvd_vcn_cdefe_cdefe_broadcast_dec0` at `0x1fc00`, `uvd_ecpudec` at `0x1ff00`, `uvd_lmi_adpdec` at `0x20290`, JRBC decoder blocks at `0x20b00`, `0x20c00`, `0x21100`, and `0x21200`, JPEG decode/SCLK/JMI/common blocks from `0x20f00` through `0x21480`, `uvd_vcn_umsch_dec` at `0x21500`, `uvd_vcn_cprs64dec` at `0x21640`, `uvd_vcn_hypdec` at `0x21a00`, and `uvd_slmi_adpdec` at `0x21c00`. Several symbols intentionally alias the same offset, such as multiple SUVD clock-gating names over `0x0104` through `0x0106` and MES names like `regVCN_MES_INTR_ROUTINE_START`/`regVCN_MES_MTVEC_LO`; these aliases preserve hardware documentation and cross-driver naming compatibility.

Risks: this is generated hardware data, so the main risks are silent offset drift from the ASIC source, mismatched base indices, accidental deletion of aliases that a call site expects, and divergence from the paired shift/mask header. Treating these register indices as absolute byte addresses would target the wrong MMIO space. The most sensitive groups are power-gating and DLDO status registers, JRBC/JPEG ring base and pointer registers, low/high 64-bit BAR pairs, VMID selectors, interrupt enable/status/ack registers, memory-check controls, and MES/UMSCH scheduler apertures. A wrong value can manifest as a media engine hang, missed interrupt, GPU page fault, failed firmware handshake, bad doorbell routing, broken SR-IOV mailbox behavior, or reset recovery failure. Because the file mixes `regUVD...`, `regVCN...`, `regJPEG...`, `regUMSCH...`, and sub-block aliases, prefix-based manual refactors are especially risky.

Test signals: compile coverage should catch missing or renamed macros in `jpeg_v5_3_0.c` and any same-generation VCN/JPEG consumers. Runtime validation should include JPEG firmware resume, JPEG power-gating and dynamic-power-gating transitions, clock-gating enable/disable, doorbell setup, JRBC ring initialization, read/write pointer movement after decode submission, JPEG output pitch/address programming, interrupt delivery and acknowledgement, idle polling through `regUVD_JRBC0_UVD_JRBC_STATUS`, suspend/resume, reset-mask/per-queue reset paths, and SR-IOV behavior where applicable. Hardware failure signatures to watch are timeouts in `SOC15_WAIT_ON_RREG` for `regUVD_IPX_DLDO_STATUS` or JRBC status, unchanged ring read pointers after work submission, missed `regJPEG_SYS_INT_STATUS`/ack events, page faults after programming LMI BAR or VMID registers, stuck `regVCN_UMSCH_MES_BUSY` or mailbox responses if scheduler paths use this map, and GPU resets during JPEG decode or media conformance workloads.
