# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/vcn/vcn_2_6_0_offset.h

Purpose: provides the generated register-offset map for AMD VCN 2.6.0 hardware. The file contains only preprocessor constants: each hardware register is exposed as a `reg...` macro with a hexadecimal register offset, paired with a `..._BASE_IDX` macro that selects the SOC15 base-address table entry used by AMDGPU register helpers. It is the address contract that VCN, UVD, MMSCH, JPEG decode/encode, local-memory-interface, ring-buffer, power-gating, interrupt, RAS, and virtualization code depends on when programming this ASIC generation.

Important APIs/types/functions: there are no C functions, structs, enums, or runtime APIs in this header. The important interface is the macro namespace. Examples include VCPU firmware window registers such as `regUVD_VCPU_CACHE_OFFSET0`, JPEG decode control and ring registers such as `regUVD_JPEG_CNTL` and `regUVD_JPEG_RB_WPTR`, LMI 64-bit BAR and VMID registers such as `regUVD_LMI_RBC_RB_64BIT_BAR_LOW`, MMSCH scheduler registers such as `regMMSCH_UCODE_ADDR` and `regMMSCH_VF_MAILBOX_HOST`, JRBC/JRBC_ENC command ring registers such as `regUVD_JRBC_RB_REF_DATA` and `regUVD_JRBC_ENC_RB_WPTR`, UVD decode ring registers such as `regUVD_RB_BASE_LO` through `regUVD_RB_WPTR4`, and error/status registers such as `regVCN_RAS_CNTL`, `regUVD_RAS_VCPU_VCODEC_STATUS`, and `regUVD_RAS_JPEG0_STATUS`. Consumers normally pass these names to `SOC15_REG_OFFSET`, `RREG32_SOC15`, `WREG32_SOC15`, `WREG32_P`, or DPG-mode helpers; those helpers combine the macro offset and `_BASE_IDX` with the device's per-IP base table and instance number.

Control flow: none is executed in this file. Build-time control is limited to the include guard `_vcn_2_6_0_OFFSET_HEADER`. Runtime control flow appears in the callers: driver bring-up writes cache windows, ring bases, read/write pointers, soft reset bits, clock-gating controls, interrupt enables, and RAS controls through these offsets; ring submission code reads or writes the JRBC/UVD/JPEG pointer and status registers; power management code polls status and power-gating registers. A wrong offset changes the target MMIO register for all of that downstream control flow.

State and persistence: the header itself has no mutable state and persists nothing. Its constants identify hardware state that is persistent at the device/MMIO level until reset or later driver writes. Notable stateful regions include firmware cache/non-cache aperture programming, LMI BAR/VMID address mappings, JPEG and UVD ring read/write pointers, MMSCH mailbox/context SRAM registers, interrupt status/acknowledge registers, power-gating status and scratch registers, and RAS status/control registers. Because many registers point at GPU memory addresses, incorrect constants can persist bad ring or buffer mappings in hardware until reset and may cause GPU hangs, decode failures, or memory faults.

Dependencies and integration: the file depends only on the C preprocessor. It is part of the AMDGPU ASIC register include set under `include/asic_reg/vcn`, and is paired conceptually with same-generation shift/mask headers that describe bit fields. Its base-index values are meaningful only with AMDGPU's SOC15 base-address infrastructure. Direct users are usually generation-specific VCN/JPEG driver files selected through ASIC include plumbing; similar macro names appear across VCN 2.x, 3.x, 4.x, and 5.x headers so common driver code can keep stable symbolic register names while include selection supplies generation-specific offsets. The block inventory is: `uvd0_ecpudec` at `0x1fd00` with 56 defines, `uvd0_jpegnpdec` at `0x1e200` with 72, `uvd0_lmi_adpdec` at `0x20870` with 278, `uvd0_mmsch_dec` at `0x1e000` with 180, `uvd0_uvd_jmi_dec` at `0x1e500` with 184, JPEG common decode and SCLK blocks at `0x1e700` and `0x1e780`, JPEG encode blocks at `0x1e300` and `0x1e380`, JRBC decode/encode command blocks at `0x1e400` and `0x1e480`, MPC at `0x20310`, power-gating at `0x1f800`, RBC at `0x20370`, and the main UVD decode block at `0x1fa00`.

Risks: this is generated hardware data, so the main risks are silent address drift, base-index mistakes, and name mismatches with shift/mask headers or call sites. Offsets are small register-index values, not byte addresses; callers must use the SOC15 helpers rather than treating the constants as full MMIO addresses. Registers with repeated low/high BAR pairs are easy to update incompletely. The file uses both `regUVD...` and `regJPEG...` prefixes, reflecting hardware block naming rather than strict subsystem ownership; manual edits can break code that expects cross-generation symbol compatibility. RAS, interrupt, reset, and ring pointer registers are especially sensitive because mistakes can mask errors, wedge scheduling, or route interrupts incorrectly.

Test signals: compile coverage is the first signal because missing or renamed macros fail AMDGPU builds for VCN 2.6 users. Hardware or emulation validation should cover VCN firmware load, decode ring start/stop, JPEG decode and encode ring submission, interrupt delivery/acknowledgement, dynamic power-gating resume, SR-IOV/MMSCH mailbox paths, and RAS poison/error handling. Practical regression symptoms include failed `RREG32_SOC15`/`WREG32_SOC15` programming sequences, stuck `regUVD_STATUS` or JRBC/RBC status polls, unchanged ring write/read pointers, missed JPEG/UVD interrupts, or GPU reset during media playback and decode conformance tests.
