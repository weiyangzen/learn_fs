# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/lsdma/lsdma_6_0_0_sh_mask.h

Purpose: this generated AMDGPU ASIC register header defines LSDMA 6.0.0 register field shifts and bit masks for the same `lsdma0_lsdma0dec` block described by the 6.0.0 offset header. It is the bit-field half of the register ABI: offset macros choose a register, while these `LSDMA_*__FIELD__SHIFT` and `LSDMA_*__FIELD_MASK` macros describe how to read, write, and decode individual fields inside that register. The file is used by AMDGPU register helper macros such as `REG_SET_FIELD()` and direct mask comparisons.

Important APIs, types, and functions: there are no C functions or types. The API is the macro namespace guarded by `_lsdma_6_0_0_SH_MASK_HEADER`. Major field groups cover microcode address/data/checksum fields, error injection target selection, public register type bits, ring/IB fetch offsets, command processor and status fields, PIO status/error bits, power-gating and PGFSM controls, version and ID fields, ECC/EDC counters, UTCL1 retry/watermark/status/invalidation/XNACK/page fields, relaxed-ordering policy bits, exception bits, PIO command/control fields, interrupt enable bits, clock/control/chicken bits, graphics address configuration, and duplicated queue0/queue1 fields for RB control/base/read and write pointers, writeback addresses, IB control/base/size, skip counts, context state, doorbells, watermarks, preemption, AQL, quantum, and mid-command snapshots.

The most visible runtime fields are `LSDMA_PIO_STATUS__PIO_IDLE_MASK` and `LSDMA_PIO_STATUS__PIO_FIFO_EMPTY_MASK`, which `lsdma_v6_0.c` uses to wait for completion; `LSDMA_PIO_COMMAND__BYTE_COUNT`, `SRC_LOCATION`, `DST_LOCATION`, `SRC_ADDR_INC`, `DST_ADDR_INC`, `OVERLAP_DISABLE`, and `CONSTANT_FILL`, which compose PIO copy/fill commands; and `LSDMA_MEM_POWER_CTRL__MEM_POWER_CTRL_EN`, which toggles LSDMA memory power control. Queue fields provide lower-level support for ring-buffer operation even though the visible v6 PIO helper uses only a small subset.

Control flow: the header itself has no executable flow, but it defines the predicates and encodings used by driver control flow. A typical read/modify/write sequence reads a register through `RREG32_SOC15()`, clears the target field with the `*_MASK`, shifts the new value by `*_SHIFT`, and writes the result through `WREG32_SOC15()`. Polling flow compares a register value masked by status bits against an expected masked value; for PIO completion the expected state is both `PIO_IDLE` and `PIO_FIFO_EMPTY`. Error paths are also mask-driven: status and exception bits distinguish VM holes, zero byte counts, DRAM/SRAM ECC, NACK generated errors, NACK protection errors, XNACKs, outstanding MMHUB/UTCL2 requests, and queue exceptions.

State and persistence behavior: this file stores no software state, but it documents how persistent hardware register state is interpreted. Stateful hardware areas include command queues and doorbell capture, read/write pointer writeback, indirect-buffer progress, current context/preemption status, mid-command data snapshots, performance counters, ECC/EDC counters, UTCL1 invalidation/XNACK information, PIO command status, interrupt enable state, memory power control, and power-gating FSM state. Some fields are latched status or error indicators; others are writable controls. The header does not encode access permissions or clear-on-read/clear-on-write behavior, so consumers must rely on hardware documentation and driver sequencing.

Dependencies and integration points: this mask header is designed to be included with `lsdma_6_0_0_offset.h`. The direct driver integration is `amdgpu/lsdma_v6_0.c`, where `REG_SET_FIELD()` names `LSDMA_PIO_COMMAND` and `LSDMA_MEM_POWER_CTRL` fields and `amdgpu_lsdma_wait_for()` uses PIO status masks. It depends on AMDGPU's common register macro convention: for a register token such as `LSDMA_PIO_COMMAND` and field token `BYTE_COUNT`, helper macros expect names of the form `LSDMA_PIO_COMMAND__BYTE_COUNT_MASK` and `LSDMA_PIO_COMMAND__BYTE_COUNT__SHIFT`. The macro names also align with generated headers for adjacent LSDMA versions, enabling version-specific driver files to share source structure while including different generated definitions.

Risks and edge cases: bit-field mistakes can be as dangerous as wrong offsets. `BYTE_COUNT` is a 26-bit field (`0x03ffffff`), so callers that pass larger sizes can truncate at the field-set layer unless higher code bounds requests. Several fields are multi-bit status values rather than booleans, including command processing, exception, XNACK state, vectors, merge states, active queue IDs, performance modes, and queue sizes; treating them as single-bit flags would misdecode hardware. Reserved fields are present with masks and should not be casually written. PF, VF, and generic PIO status layouts are identical here, but code should still choose the correct register for the privilege context. Queue0 and queue1 have parallel field names with only the queue number changed, which increases the risk of configuring one queue while polling the other. The header does not provide range checks for VMID, address alignment, RB/IB sizes, AQL packet sizes, or watermarks.

Test signals: compile tests should verify all `REG_SET_FIELD()` and mask references in `lsdma_v6_0.c` resolve. Unit-style macro tests can set and extract representative fields such as `BYTE_COUNT`, `CONSTANT_FILL`, `PIO_IDLE`, `PIO_FIFO_EMPTY`, and `MEM_POWER_CTRL_EN` to catch generator or helper regressions. Hardware tests should cover normal PIO copy/fill completion, zero-count or invalid-address error reporting, ECC/NACK status visibility where fault injection is available, and power-gating transitions. Register conformance tests should compare selected masks and shifts against the LSDMA 6.0.0 hardware specification, especially fields shared with the 7.0.0 driver where source code shape is similar but register offsets differ.
