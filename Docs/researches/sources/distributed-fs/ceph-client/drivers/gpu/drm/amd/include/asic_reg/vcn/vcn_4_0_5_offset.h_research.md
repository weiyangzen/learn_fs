# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/vcn/vcn_4_0_5_offset.h

Purpose: provides the generated register-offset map for AMD VCN 4.0.5 hardware. The header contains preprocessor constants only: every hardware register is represented by a `reg...` macro holding a hexadecimal register index and a paired `..._BASE_IDX` macro selecting the SOC15 base-address table entry. In this file every base index is `1`. The constants are the address contract used by AMDGPU VCN, UVD, JPEG, local memory interface, ring-buffer, power-gating, virtualization, UMSCH/MES scheduler, and interrupt paths when programming this ASIC generation.

Important APIs/types/functions: there are no C functions, structs, enums, or callable APIs in this header. Its public interface is the macro namespace. Important families include clock/reset/status controls such as `regUVD_CGC_GATE`, `regUVD_CGC_CTRL`, `regUVD_STATUS`, `regUVD_CNTL`, `regUVD_SOFT_RESET`, and `regUVD_MMSCH_SOFT_RESET`; firmware command/mailbox registers such as `regUVD_GPCOM_VCPU_DATA0`, `regUVD_GPCOM_SYS_CMD`, `regUVD_GPCOM_VCPU_CMD`, `regUVD_IOV_MAILBOX`, and `regUVD_IOV_MAILBOX_RESP`; decode ring registers such as `regUVD_RB_BASE_LO` through `regUVD_RB_BASE_HI4`, `regUVD_RB_RPTR`, `regUVD_RB_WPTR`, and `regVCN_RB_ENABLE`; RBC/JRBC command-stream registers such as `regUVD_RBC_RB_CNTL`, `regUVD_RBC_WPTR_STATUS`, `regUVD_JRBC_RB_WPTR`, and `regUVD_JRBC_STATUS`; JPEG decode/control registers such as `regUVD_JPEG_CNTL`, `regUVD_JPEG_RB_WPTR`, `regUVD_JPEG_INT_STAT`, `regUVD_JPEG_OUTBUF_WPTR`, and `regJPEG_DEC_ADDR_MODE`; LMI BAR/VMID registers such as `regUVD_LMI_VCPU_CACHE_64BIT_BAR_LOW`, `regUVD_LMI_RBC_RB_VMID`, `regUVD_LMI_JPEG_READ_64BIT_BAR_LOW`, and `regUVD_LMI_MMSCH_NC_VMID`; power-gating and scratch registers such as `regUVD_PGFSM_CONFIG`, `regUVD_PGFSM_STATUS`, `regUVD_POWER_STATUS`, `regUVD_DPG_LMA_CTL`, and `regUVD_SCRATCH1`; UMSCH/MES scheduler registers such as `regVCN_UMSCH_MAILBOX0`, `regVCN_UMSCH_RB_BASE_LO`, `regVCN_UMSCH_SYS_INT_STATUS`, `regVCN_MES_CNTL`, `regVCN_MES_INTERRUPT`, and `regVCN_MES_DC_APERTURE15_CNTL`; and JPEG RAS controls `regUVD_JMI_DJPEG_RAS_CNTL` and `regUVD_JMI_EJPEG_RAS_CNTL`. Callers normally feed these names into SOC15 register helpers such as `SOC15_REG_OFFSET`, `RREG32_SOC15`, `WREG32_SOC15`, `WREG32_P`, or VCN dynamic-power-gating helper variants, which combine the register index, base index, and IP instance.

Control flow: no runtime control flow executes here. Build-time control is limited to the include guard `_vcn_4_0_5_OFFSET_HEADER`. Runtime control flow is in AMDGPU call sites that include this generated map: VCN bring-up programs firmware cache windows, non-cache apertures, LMI BARs, VMIDs, ring bases, and ring sizes; decode/JPEG submission paths advance write pointers and poll read pointers or status registers; interrupt handlers use the `*_INT_STATUS` and `*_INT_ACK` offsets; reset and power-management paths write soft-reset, clock-gating, and PGFSM/DPG registers; virtualization paths use IOV function IDs and mailboxes; UMSCH/MES paths initialize scheduler firmware, its command ring, aperture tables, and interrupt state. Because the macros are substituted directly into those flows, an offset error silently redirects MMIO traffic to the wrong register.

State and persistence: the file itself owns no mutable state and persists nothing. It names device-visible MMIO state that survives until hardware reset or later driver writes. Stateful regions include VCPU firmware cache and non-cache windows (`regUVD_VCPU_CACHE_OFFSET*`, `regUVD_VCPU_CACHE_SIZE*`, LMI VCPU cache BARs), command rings and buffers (`regUVD_RB_*`, `regUVD_OUT_RB_*`, `regUVD_AUDIO_RB_*`, `regUVD_RBC_*`, `regUVD_JRBC_*`, `regVCN_UMSCH_RB_*`), GPU-memory address mappings and VMIDs across decode/JPEG/MMSCH clients, interrupt enable/status/ack latches, scratch registers used during firmware and power-management handshakes, power-gating state, performance counters, and MES local/data/instruction apertures. Incorrect values can leave hardware programmed with stale or invalid GPU addresses until reset, causing hangs, memory faults, missed interrupts, failed media decode, or scheduler firmware failure.

Dependencies and integration: the header depends only on the C preprocessor and the AMDGPU include-selection convention for ASIC register maps. It is source-tree aligned under `drivers/gpu/drm/amd/include/asic_reg/vcn` and is expected to be paired with the same-generation shift/mask header that describes bit fields for these offsets. The `_BASE_IDX` values are meaningful only through the AMD SOC15 base-address infrastructure; the hex constants are register indices, not standalone byte MMIO addresses. The address block inventory is: `uvd_uvddec` at `0x1fb00` with 326 register/base-index defines, `uvd_ecpudec` at `0x1fe00` with 56, `uvd_uvd_mpcdec` at `0x1ff30` with 40, `uvd_uvd_rbcdec` at `0x1ff90` with 44, `uvd_lmi_adpdec` at `0x20090` with 240, `uvd_jpegnpdec` at `0x20f00` with 66, `uvd_uvd_jrbc_dec` at `0x21100` with 38, `uvd_uvd_jmi_dec` at `0x21200` with 184, `uvd_uvd_jpeg_common_dec` at `0x21400` with 22, `uvd_uvd_jpeg_common_sclk_dec` at `0x21480` with 28, `uvd_uvd_pg_dec` at `0x1f800` with 208, `uvd_vcn_umsch_dec` at `0x21500` with 82, `uvd_vcn_cprs64dec` at `0x21600` with 306, `uvd_vcn_hypdec` at `0x21a00` with 26, and `uvd_slmi_adpdec` at `0x21c00` with 42. The duplicated aliases in the MES region, such as `regVCN_MES_INTR_ROUTINE_START` sharing an offset with `regVCN_MES_MTVEC_LO`, preserve multiple naming conventions for the same hardware location.

Risks: this is generated hardware data, so the highest risks are silent offset drift from the ASIC source, stale aliases, base-index mistakes, and mismatches with shift/mask headers or cross-generation call sites. Treating register indices as absolute byte addresses would program the wrong MMIO locations. Low/high 64-bit BAR pairs, VMID registers, and ring pointer groups must stay coherent; partial edits can create address truncation or mismatched ownership between command rings and memory apertures. Interrupt, reset, RAS, and power-gating offsets are especially sensitive because mistakes can hide hardware errors, wedge media scheduling, or prevent recovery. The mixed `regUVD...`, `regVCN...`, `regUMSCH...`, and `regJPEG...` prefixes reflect block naming rather than strict subsystem ownership, so manual renames can break common driver code that relies on stable symbols across VCN generations.

Test signals: compile coverage is the first signal because missing or renamed macros fail AMDGPU builds for VCN 4.0.5 users. Hardware validation should cover VCN firmware load, UVD decode ring initialization, multi-ring `RB1` through `RB4` enablement and pointer movement, JPEG decode submission and output-buffer progress, JRBC/RBC indirect-buffer submission, UMSCH/MES scheduler boot and mailbox exchange, dynamic power-gating suspend/resume, SR-IOV active-function and mailbox handling, interrupt delivery and acknowledgement, LMI VMID/BAR programming, JPEG RAS controls, and reset recovery. Practical regression symptoms include stuck `regUVD_STATUS`, `regUVD_RBC_BUF_STATUS`, `regUVD_JRBC_STATUS`, or `regVCN_UMSCH_MES_BUSY` polls; unchanged ring read/write pointers after submission; missed `regUVD_SYS_INT_STATUS`, `regJPEG_SYS_INT_STATUS`, or `regVCN_UMSCH_SYS_INT_STATUS` events; failed firmware mailbox responses; page faults after LMI BAR programming; and GPU resets during media playback or decode conformance workloads.
