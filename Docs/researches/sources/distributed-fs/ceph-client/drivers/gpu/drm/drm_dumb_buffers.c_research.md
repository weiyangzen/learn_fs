# sources/distributed-fs/ceph-client/drivers/gpu/drm/drm_dumb_buffers.c

Purpose: provides the DRM/KMS common dumb-buffer ioctl helpers used for simple scanout-capable framebuffer allocation, mmap offset creation, and destruction. It standardizes a minimal userspace path for early boot graphics and generic DRM clients while still delegating actual backing-object allocation to driver callbacks.

Important APIs/types/functions: `drm_mode_align_dumb()` validates and rounds pitch/size after a driver/helper has determined an initial pitch. `drm_mode_size_dumb()` is exported for drivers to calculate pitch and total allocation size from width, height, color mode, and hardware alignment. `drm_mode_create_dumb()` validates ioctl arguments, clears output fields, and calls `dev->driver->dumb_create`. `drm_mode_create_dumb_ioctl()` wraps create and clears outputs on failure. `drm_mode_mmap_dumb()` calls `dev->driver->dumb_map_offset` or falls back to `drm_gem_dumb_map_offset()`. `drm_mode_mmap_dumb_ioctl()` clears `offset` on failure. `drm_mode_destroy_dumb()` checks dumb-buffer support and deletes the GEM handle through `drm_gem_handle_delete()`. `drm_mode_destroy_dumb_ioctl()` exposes destroy to ioctl dispatch. Key data types are `struct drm_mode_create_dumb`, `struct drm_mode_map_dumb`, `struct drm_mode_destroy_dumb`, `struct drm_device`, `struct drm_file`, `struct drm_driver`, and `struct drm_format_info`.

Control flow: size calculation first maps the requested `bpp` color-mode constant to a driver-supported fourcc through `drm_driver_color_mode_format()`. If a valid format exists, it obtains format metadata and minimum pitch for plane 0; otherwise it accepts legacy/deprecated bpp values and computes `width * ceil(bpp/8)`, warning once for unknown modes. The helper rejects zero or overflowing pitch, stores a 32-bit pitch, rounds pitch to hardware alignment, defaults size alignment to `PAGE_SIZE`, rejects non-page-aligned custom size alignment, checks `height * pitch` overflow, aligns size, and rejects zero size. Create rejects drivers without `dumb_create`, zero dimensions, arithmetic overflow in the legacy 32-bit stride/size precheck, and page-align wraparound; then it clears `handle`, `pitch`, and `size` before invoking the driver callback. Mmap rejects drivers without dumb-buffer support and delegates offset allocation to the driver or GEM default. Destroy rejects unsupported devices and deletes the handle from the caller's file handle table.

State and persistence: this file owns no persistent global state. Persistent effects are produced by delegated callbacks: successful create returns a GEM or driver-specific handle in the caller's `drm_file`, mmap offset allocation records an mmap token in the device/GEM address space, and destroy removes the handle reference. The ioctl wrappers deliberately scrub output fields on failure so userspace does not observe stale kernel stack or caller-provided garbage. Size/pitch fields in the argument structure are transient outputs and must be trusted only after a zero return.

Dependencies and integration: integrated with DRM ioctl dispatch through declarations in `drm_crtc_internal.h` and UAPI structs in `drm_mode.h`. It depends on driver callbacks in `struct drm_driver`, DRM format helpers (`drm_driver_color_mode_format()`, `drm_format_info()`, `drm_format_info_min_pitch()`), overflow/alignment helpers, GEM handle and dumb-map helpers, page-size constraints required by mmap, and DRM logging. Drivers such as shmem, DMA, VRAM, simple display, and hardware-specific KMS drivers commonly call `drm_mode_size_dumb()` from their `.dumb_create` implementations, then allocate the actual object through their memory manager.

Risks: dumb buffers are intentionally simple scanout buffers, not a portable acceleration allocation API; using them for GPU rendering can select memory with unsuitable tiling, caching, or placement. Format handling preserves compatibility with legacy userspace that passes arbitrary `bpp`, so unknown values may over-allocate rather than fail after a one-time warning. Alignment handling currently rejects non-page-aligned size alignment, which may matter for hardware with unusual constraints. The create path's precheck uses legacy cpp/stride arithmetic before the driver callback, so drivers still need their own validation for format-specific or multi-plane requirements. Destroy assumes GEM handles via `drm_gem_handle_delete()` even though the overview notes non-GEM drivers need a destroy operation; this tree's current implementation therefore fits GEM-backed dumb handles. Failure paths must keep output clearing behavior intact to avoid userspace confusion or information exposure.

Test signals: exercise `DRM_IOCTL_MODE_CREATE_DUMB`, `DRM_IOCTL_MODE_MAP_DUMB`, mmap, framebuffer creation, page flip/scanout, and `DRM_IOCTL_MODE_DESTROY_DUMB` on drivers with GEM default mapping and drivers with custom `dumb_map_offset`. Fuzz zero dimensions, huge dimensions, large/unknown `bpp`, overflow boundaries near `U32_MAX`, hardware pitch alignment, custom size alignment, and page-align wraparound. Verify failure returns clear `handle`/`pitch`/`size` or `offset`, valid creates return page-aligned nonzero size and usable pitch, repeated destroy/invalid handle paths fail cleanly, and generic DRM clients/fbdev emulation can allocate and tear down dumb buffers without leaks.
