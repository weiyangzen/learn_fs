# sources/distributed-fs/ceph-client/drivers/mtd/nand/raw/cs553x_nand.c

Purpose: this module supports NAND controllers embedded in AMD CS5535/CS5536 companion chips for Geode platforms. It discovers enabled flash chip-select windows from Geode MSRs, maps MMIO NAND windows, exposes each active chip-select as a raw NAND controller, and uses the small hardware Hamming ECC engine.

Important APIs, types, and functions: `struct cs553x_nand_controller` contains a `nand_controller`, one `nand_chip`, and the mapped MMIO window. `cs553x_exec_op()` implements the raw NAND operation interface by dispatching instructions to `cs553x_exec_instr()`. Data helpers use `memcpy_fromio()` and `memcpy_toio()` against the 0x800-byte data aperture. `cs_enable_hwecc()` and `cs_calculate_ecc()` wire the hardware ECC registers into the NAND ECC core, with correction delegated to `rawnand_sw_hamming_correct`. Module lifecycle is through `cs553x_init()`, `cs553x_init_one()`, and `cs553x_cleanup()`.

Control flow: module init first verifies the boot CPU is a Geode GX/LX, checks the DIVIL capability MSR for CS5535/CS5536, ensures flash pins are not routed to IDE, then walks four `MSR_DIVIL_LBAR_FLSH*` BAR descriptors. Each enabled NAND MMIO BAR is initialized by `cs553x_init_one()`, which allocates the controller, initializes NAND controller ops, maps the physical address, sets flash BBT use, assigns an MTD name of `cs553x_nand_csN`, and calls `nand_scan()`. After all scans, init registers each discovered MTD device. Operation execution writes CLE/ALE bytes through control and IO registers, copies data through the data aperture, and polls status for controller idle or flash ready.

State and persistence: controller state is held in a static four-entry `controllers[]` array for module cleanup. Hardware configuration comes from MSRs programmed by firmware or platform setup; the driver does not persist or alter timing MSRs. Per-chip state is limited to the mapped MMIO window, MTD name, BBT option, and ECC callbacks. Cleanup unregisters MTDs, calls `nand_cleanup()`, frees names, unmaps MMIO, and releases controller allocations.

Dependencies and integration points: the module is x86/Geode-specific and depends on `<asm/msr.h>`, CPU vendor/model data, CS553x DIVIL MSR layout, raw NAND `exec_op`, MTD registration, and generic Hamming correction. PIO mode is explicitly not implemented; only memory-mapped NAND BARs are accepted.

Risks: `cs553x_exec_op()` returns `true` for `check_only`, which is numerically success but unusual compared with common zero-return convention and may deserve caution if the core interprets positive values differently. Cleanup dereferences `controllers[i]` before checking whether it is NULL, so unloading after only some chip-selects initialized can crash. MTD registration errors are ignored in `cs553x_init()`, which can leave scanned chips in a partially registered state. The driver trusts firmware MSR BAR setup and timing; no resource reservation is used beyond `ioremap()`. Data copies larger than 0x800 bytes loop through the same aperture, which assumes the controller auto-advances internal address correctly.

Test signals: test on real Geode hardware should show correct CPU/MSR gating, no probe when flash pins are IDE-routed, discovery of each enabled NAND MMIO BAR, successful `nand_scan()` and MTD registration under `cs553x_nand_cs[0-3]`, command/address/data operations through `exec_op`, ready polling timeout behavior, hardware ECC generation and Hamming correction, and safe module unload with sparse chip-select population.
