# sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci-xenon-phy.c

Purpose: this file contains the Marvell Xenon SDHC PHY support used by `sdhci-xenon.c`. It abstracts eMMC PHY 5.0 and 5.1 register layouts, parses board-specific PHY parameters, controls Armada 3700 SoC pad voltage when present, initializes the PHY after clock/timing changes, enables the DLL for high-speed modes, configures HS200/SDR104 tuning step, and sets HS400 data/enhanced strobe behavior.

Important APIs, types, and functions: `struct xenon_emmc_phy_regs` maps version-specific timing, function-control, pad-control, DLL, and logic-timing registers. `struct xenon_emmc_phy_params` stores parsed slow-mode, ZNR/ZPR impedance, tuning-success count, tuning-step divider, and optional SoC pad control. Public entry points are `xenon_phy_adj()`, `xenon_phy_parse_params()`, and `xenon_soc_pad_ctrl()`. Core helpers include `xenon_alloc_emmc_phy()`, `xenon_emmc_phy_parse_params()`, `get_dt_pad_ctrl_data()`, `xenon_emmc_phy_init()`, `xenon_emmc_phy_enable_dll()`, `xenon_emmc_phy_config_tuning()`, `xenon_emmc_phy_strobe_delay_adj()`, `xenon_emmc_phy_slow_mode()`, `xenon_emmc_phy_set()`, and `xenon_hs_delay_adj()`.

Control flow: `xenon_phy_parse_params()` selects a DT-provided `marvell,xenon-phy-type` or defaults to eMMC 5.1, allocates PHY parameter storage, selects the matching register table, reads `marvell,xenon-phy-slow-mode`, `marvell,xenon-phy-znr`, `marvell,xenon-phy-zpr`, `marvell,xenon-phy-nr-success-tun`, and `marvell,xenon-phy-tun-step-divider`, and optionally maps the second DT resource for Armada 3700 pad control. Later, `xenon_set_ios()` in the platform driver calls `xenon_phy_adj()` after generic SDHCI IOS changes. If clock, bus width, or timing changed, `xenon_phy_adj()` calls `xenon_emmc_phy_set()`, updates cached state, and for non-legacy high-speed clocks calls `xenon_hs_delay_adj()`.

State and persistence: PHY state is cached in `struct xenon_priv` (`phy_type`, `phy_params`, `emmc_phy_regs`, previous bus width/timing/clock, and initialization card type). Hardware state includes pad receiver enables, pull-up/down selections, slow mode, SDIO mode, ZNR/ZPR values, function-control DDR/async bits, card clock enable, logic timing, DLL enable/phase/update bits, strobe bits, and SoC pad voltage. `xenon_runtime_suspend()` clears cached clock in the platform driver so resume forces PHY reconfiguration rather than assuming stale state.

Dependencies and integration points: the file depends on `sdhci-pltfm.h`, `sdhci-xenon.h`, OF address mapping, devm allocation/ioremap, SDHCI clock-control state, MMC timings and card type, and Xenon vendor registers. `xenon_soc_pad_ctrl()` is called before generic voltage switching. PHY tuning setup feeds the generic SDHCI tuning engine by programming Xenon tuning-step and consecutive-success fields.

Risks: timing correctness is board-sensitive. Default ZNR/ZPR and 90-degree DLL phase may not suit every layout, and the DDR path explicitly warns that it does not scan fixed delay lines. `tun_step_divider` is parsed as an 8-bit value but not guarded against zero before division in tuning setup. The PHY init wait is derived from register fields and clock rate, then capped at 100 loops; very slow or unusual hardware may still time out. Function-control writes require the SD card clock disabled and then reenabled, so ordering with generic clock changes matters. Armada 3700 pad control assumes a valid second resource and known `marvell,pad-type`.

Test signals: validate PHY 5.0 and 5.1 register selection, DT parsing including default values, SoC pad switching for SD and fixed-1.8V modes, internal clock stability polling, PHY initialization completion across clock rates, slow-mode behavior for legacy/SDIO/low-speed modes, ZNR/ZPR programming, DLL lock within 32 ms for HS200/SDR104/HS400, tuning step calculation and clamping, HS400 data/enhanced strobe bits and QSP pull-down, and forced PHY reprogramming after runtime resume.
