# sources/distributed-fs/ceph-client/drivers/pci/hotplug/ibmphp_ebda.c

Purpose: Parses IBM BIOS Extended BIOS Data Area hot-swap metadata for the legacy IBM PCI Hot Plug driver. It maps EBDA, finds Hot Swap and RIO data blocks, reconstructs hotplug controllers, slots, bus metadata, and POST-assigned PCI resource records, then registers the discovered slots with the PCI hotplug core.

Important APIs and functions: Public entry points include `ibmphp_access_ebda()`, `ibmphp_get_total_controllers()`, `ibmphp_get_slot_from_physical_num()`, `ibmphp_find_same_bus_num()`, `ibmphp_get_bus_index()`, `ibmphp_free_bus_info_queue()`, `ibmphp_free_ebda_hpc_queue()`, `ibmphp_free_ebda_pci_rsrc_queue()`, and `ibmphp_register_pci()`. Major internal helpers include `ebda_rio_table()`, `ebda_rsrc_controller()`, `ebda_rsrc_rsrc()`, RIO grouping helpers such as `combine_wpg_for_chassis()`, `combine_wpg_for_expansion()`, `find_chassis_num()`, `find_rxe_num()`, and slot naming helper `create_file_name()`.

Control flow: `ibmphp_access_ebda()` reads the EBDA segment pointer at BIOS data area `0x40:0x0e`, maps the EBDA block, walks chained data blocks from offset `0x180`, validates hot-swap block signature `0x4853` and RIO signature `0x4752`, then records controller and resource table offsets. If a RIO v3 table exists, `ebda_rio_table()` builds raw chassis and expansion-box lists. `ebda_rsrc_controller()` walks every EBDA controller descriptor, allocates a `struct controller` plus per-controller EBDA slot/bus arrays, builds `bus_info_head`, fills concrete `struct slot` instances, reads initial hardware slot state through `ibmphp_hpc_readslot()`, initializes device numbers with `ibmphp_init_devno()`, and registers each slot with `pci_hp_register()`. `ebda_rsrc_rsrc()` turns EBDA IO/MEM/PFM records into `struct ebda_pci_rsrc` nodes for later resource initialization.

State and persistence: The file owns global lists `ibmphp_ebda_pci_rsrc_head` and `ibmphp_slot_head`, plus private lists for controllers, bus information, RIO details, and optimized RIO grouping. Parsed EBDA contents persist as kernel heap objects until module cleanup frees the queues. Controller PCI devices are attached later by `ibmphp_probe()` when `ibmphp_register_pci()` registers a PCI driver for controller type 1.

Dependencies and integration points: Depends on `ibmphp.h` data structures and helpers, Linux PCI and list APIs, `ioremap()`/`readb()`/`readw()`/`readl()`, hotplug core `pci_hp_register()`, hardware access from `ibmphp_hpc.c`, resource consumption by `ibmphp_res.c`, and slot/device initialization from the broader IBM PHP driver. It also registers a small PCI driver for IBM HPC PCI controllers so config-space register access can find the backing `pci_dev`.

Risks: EBDA parsing is firmware-trust-heavy and uses many computed offsets with limited bounds checks beyond the top-level next-block guard. `create_file_name()` returns a static buffer, so callers must copy the name immediately as this file does. Error paths in `ebda_rsrc_controller()` can leak objects already linked to global lists or registered hotplug slots because cleanup is local to the current controller/slot. `ibmphp_free_bus_info_queue()` does not `list_del()` freed entries, which is acceptable only during teardown when the list is not reused. Slot naming and RIO grouping depend on legacy platform assumptions about chassis and RXE slot numbering.

Test signals: Boot or module load on supported IBM hardware should log EBDA size, hot swap table format 4, controller/resource counts, registered slot names, and PCI controller binding. Negative tests include missing EBDA, wrong block format, unsupported controller type, PCI hotplug slot registration failure, and cleanup after partial allocation failure. Runtime validation comes from populated `/sys/bus/pci/slots/*`, correct physical slot names, and successful `ibmphp_rsrc_init()` consumption of `ibmphp_ebda_pci_rsrc_head`.
