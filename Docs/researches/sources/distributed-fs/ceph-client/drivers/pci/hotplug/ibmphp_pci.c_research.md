# sources/distributed-fs/ceph-client/drivers/pci/hotplug/ibmphp_pci.c

Purpose: Performs legacy PCI configuration for cards inserted into IBM hotplug slots and removes those configurations on hot-removal. It probes functions behind a slot, rejects unsupported VGA and nested bridge cases, allocates BAR/window resources through the IBM PHP resource manager, programs PCI config space, and maintains per-slot `struct pci_func` chains for cleanup.

Important APIs and functions: Public APIs are `ibmphp_configure_card()` and `ibmphp_unconfigure_card()`. Key internal functions are `assign_alt_irq()`, `configure_device()`, `configure_bridge()`, `scan_behind_bridge()`, `unconfigure_boot_device()`, `unconfigure_boot_bridge()`, `unconfigure_boot_card()`, `add_new_bus()`, and `find_sec_number()`.

Control flow: `ibmphp_configure_card()` scans functions 0..7 at the slot device number, reads vendor/header/class data, rejects VGA and unsupported bridge types, configures ordinary devices via `configure_device()`, and configures PCI-to-PCI bridges via `configure_bridge()` before recursively configuring discovered downstream devices. `configure_device()` sizes BARs by writing all ones, allocates IO/MEM/PFMEM nodes with `ibmphp_check_resource()` and `ibmphp_add_resource()`, writes BAR starts, assigns interrupt line/cache/latency/command registers, and handles 64-bit BARs by zeroing the high dword. `configure_bridge()` allocates bridge BARs, chooses a secondary bus from EBDA slot topology, scans downstream devices for total window needs, allocates bridge windows, creates a new resource bus, writes bridge windows, and enables the bridge. Unconfiguration reads existing BAR/window state, finds matching resource nodes, removes resources/buses, and frees `pci_func` chains.

State and persistence: The file mutates PCI config space, `struct pci_func` linked lists hanging off a slot, `func->io[]`, `func->mem[]`, `func->pfmem[]`, `func->devices[]`, and global resource state managed by `ibmphp_res.c`. Programmed BARs, interrupt lines, bridge windows, and command bits persist in hardware until unconfigured, power-cycled, or overwritten.

Dependencies and integration points: Relies on `ibmphp_pci_bus`, PCI config accessors, EBDA slot/bus topology from `ibmphp_find_same_bus_num()`, resource APIs from `ibmphp_res.c`, and driver-specific constants/macros from `ibmphp.h`. Higher-level slot enable/disable code calls into this file after powering slots on or before powering them off.

Risks: This code reimplements PCI enumeration and resource assignment instead of using modern generic PCI core flows, so it is sensitive to BAR sizing side effects, multifunction header handling, and bridge-window alignment. `configure_bridge()` uses `PCI_DEVFN(func->function, func->device)` in one place, which is suspicious because other paths use `PCI_DEVFN(device, function)`. Nested bridges and VGA are deliberately unsupported. 64-bit memory resources are effectively truncated by zeroing upper dwords. Partial failure cleanup is narrow and may not undo all resources for multifunction or recursively configured devices.

Test signals: Hot-adding ordinary single-function, multifunction, and one-level PCI-to-PCI bridge cards should program BARs and command registers and populate resource lists. Removal should free matching resources and bus nodes. Negative signals include unsupported VGA, nested bridge rejection, insufficient IO/MEM/PFMEM windows, invalid secondary-bus allocation, BAR sizing failures, and reinsertion after previous bridge removal.
