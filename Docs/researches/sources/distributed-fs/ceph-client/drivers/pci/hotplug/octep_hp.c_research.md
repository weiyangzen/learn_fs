# sources/distributed-fs/ceph-client/drivers/pci/hotplug/octep_hp.c

Purpose: Registers the Marvell/OCTEON PCI hotplug driver for a Cavium hotplug controller function. It treats the remaining functions on the same PCI bus/device group as hotplug slots, logically removes them during probe, and re-enables or disables them in response to MSI-X command interrupts or sysfs hotplug operations.

Important APIs and types: Main types are `enum octep_hp_intr_type`, `struct octep_hp_cmd`, `struct octep_hp_slot`, `struct octep_hp_intr_info`, and `struct octep_hp_controller`. Key functions include `octep_hp_controller_setup()`, `octep_hp_pci_probe()`, `octep_hp_register_slot()`, `octep_hp_deregister_slot()`, `octep_hp_enable_pdev()`, `octep_hp_disable_pdev()`, interrupt helpers `octep_hp_request_irq()`, `octep_hp_intr_handler()`, `octep_hp_work_handler()`, and hotplug-slot ops `octep_hp_enable_slot()`/`octep_hp_disable_slot()`.

Control flow: Probe allocates a managed controller, enables and maps BAR 0, initializes locks/lists/work, allocates MSI-X vectors up to the enable/disable hotplug vector indexes, requests IRQs, then iterates sibling devices on the bus. Each sibling becomes a `hotplug_slot` named `octep_hp_N`, is registered through `pci_hp_register()`, linked to `slot_list`, and immediately disabled with `pci_stop_and_remove_bus_device_locked()`. Hardware interrupts read and clear a 64-bit slot mask from a type-specific MMIO register, queue an `octep_hp_cmd` under a spinlock, and schedule work. Workqueue context processes all queued commands and toggles matching slots.

State and persistence: `struct octep_hp_controller` persists mapped MMIO base, controller PCI device, interrupt metadata, registered slot list, command queue, and locks. Each slot persists its slot number, original devfn, optional active `hp_pdev`, and hotplug core object. Disabled devices are removed from the PCI bus and rescanned on enable; registered slots persist until devm cleanup deregisters them and re-enables devices.

Dependencies and integration points: Depends on PCI managed resource APIs, MSI-X, MMIO `readq()`/`writeq()`, generic PCI scanning/resource assignment/removal helpers, workqueues, hotplug core registration, and devm cleanup actions. It binds `PCI_VENDOR_ID_CAVIUM` device `0xa0e3`.

Risks: `octep_hp_enable_pdev()` assumes `pci_scan_single_device()` succeeds and then dereferences `hp_slot->hp_pdev` in `pci_bus_add_device()` and logging, so failed scan can crash. Probe registers all other devices on the bus, not just same-slot functions, which depends on the platform topology promised in the comments. Slot command masks use `BIT(slot_number)` with a `u64` interrupt value but `BIT()` is word-sized on some architectures; `BIT_ULL()` would better match the data width. IRQ cleanup flushes work after freeing vectors, but queued commands are only freed by the work handler.

Test signals: Binding to `177d:a0e3`, BAR mapping, MSI-X allocation/request, creation of `octep_hp_*` slots, initial logical removal of slot functions, interrupt-driven enable/disable masks, sysfs `power` toggles, and cleanup re-enabling devices are core signals. Fault tests should cover failed scan on enable, no sibling devices, malformed interrupt vector, command allocation failure in IRQ context, and repeated enable/disable idempotence.
