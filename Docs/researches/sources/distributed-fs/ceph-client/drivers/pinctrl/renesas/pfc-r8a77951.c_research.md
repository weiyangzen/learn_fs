# sources/distributed-fs/ceph-client/drivers/pinctrl/renesas/pfc-r8a77951.c

## Purpose

This file is the Renesas SH PFC pin-control description for the R-Car H3/R8A77951 PFC block and the closely related RZ/G2H/R8A774E1 build target. It does not implement a standalone platform driver. Instead, it exports `struct sh_pfc_soc_info` tables that the shared Renesas `sh-pfc` core uses to register pins, named pin groups, pinctrl functions, mux registers, drive-strength controls, bias controls, and I/O-voltage controls.

Most of the source is declarative hardware metadata. The common tables cover GPIO banks 0 through 7, non-GPIO pins such as QSPI/RPC/AVB/debug/display clock pins, and peripheral routes for audio clocks, AVB, CAN/CAN-FD, DU, HSCIF/SCIF, I2C, external IRQs, MSIOF, PWM, QSPI, SATA DEVSLP, SDHI, SSI, TMU/TPU, USB, and VIN. When `CONFIG_PINCTRL_PFC_R8A77951` is enabled, additional automotive-only DRIF and MLB groups/functions are exposed; `CONFIG_PINCTRL_PFC_R8A774E1` exposes only the common surface.

## Important APIs, Types, and Data

- `CFG_FLAGS`, `CPU_ALL_GP()`, and `CPU_ALL_NOGP()` define the complete pin universe. Most pins advertise drive-strength and pull-up/down configuration. GPIO bank 3 pins 0-11 and bank 4 pins 0-17 also advertise `SH_PFC_PIN_CFG_IO_VOLTAGE_18_33`, matching the POCCTRL mapping later in the file.
- The first large anonymous enum builds all internal pinmux IDs: GPIO data IDs, `FN_*` function IDs, GPSR/IPSR/MOD_SEL selector IDs, and public `*_MARK` IDs. The enum is generated from `GP_ALL()`, `PINMUX_GPSR`, `PINMUX_IPSR`, `PINMUX_MOD_SELS`, `PINMUX_STATIC`, and `PINMUX_PHYS`.
- `pinmux_data[]` maps public marks to selector fields. It uses `PINMUX_SINGLE()` for fixed single-function GPIO pins, `PINMUX_IPSR_GPSR()` for alternatives directly selected by GPSR/IPSR fields, `PINMUX_IPSR_MSEL()` for alternatives that require a MOD_SEL value, and `PINMUX_IPSR_PHYS*()` for physical I2C SCL/SDA pin aliases selected through `I2C_SEL_*`.
- `PINMUX_STATIC` covers non-muxable but configurable pins, including QSPI0/1, RPC, fixed AVB MII pins, display clock inputs, JTAG/debug pins, and `EXTALR`. These marks are added to `pinmux_data[]` with no associated mux function so the core can still apply drive/bias settings without trying to switch their mux.
- `pinmux_pins[]` is the complete `struct sh_pfc_pin` table generated from GPIO-backed pins plus non-GPIO pins.
- Hundreds of `<group>_pins[]` and `<group>_mux[]` arrays define the concrete pin lists and required mux marks for named groups. Common examples include AVB MDIO/MII/AVTP, CAN and CAN-FD data pairs, DU RGB666/RGB888 and sync/control pins, serial alternatives for HSCIF/SCIF/MSIOF, I2C buses 0/1/2/3/5/6, SDHI bus-width groups, SSI audio pins, USB PWEN/OVC groups, VIN4/VIN5 capture widths, QSPI 2-bit/4-bit data groups, and SATA DEVSLP alternatives.
- `pinmux_groups` aggregates 328 common `struct sh_pfc_pin_group` entries plus 31 R8A77951-only automotive entries under `CONFIG_PINCTRL_PFC_R8A77951`. The automotive block includes DRIF0-DRIF3 control/data groups and `mlb_3pin`.
- `<function>_groups[]` arrays define the group names exported under each logical pinctrl function. `pinmux_functions` wraps 55 common functions and, for R8A77951, 5 automotive functions: `drif0`, `drif1`, `drif2`, `drif3`, and `mlb_3pin`.
- `pinmux_config_regs[]` describes GPSR0-7, IPSR0-18, and MOD_SEL0-2 at PFC MMIO addresses starting at `0xe6060100`, `0xe6060200`, and `0xe6060500`. Fixed-width `PINMUX_CFG_REG()` entries cover regular fields; `PINMUX_CFG_REG_VAR()` records model reserved holes and nonuniform field widths.
- `pinmux_drive_regs[]` maps pins to drive-strength fields in DRVCTRL0-24 at `0xe6060300` through `0xe6060360`. Entries use 2-bit or 3-bit widths depending on the pad group; `PIN_DU_DOTCLKIN2` in DRVCTRL12 is gated by `CONFIG_PINCTRL_PFC_R8A77951`.
- `pinmux_ioctrl_regs[]` names POCCTRL at `0xe6060380` and TDSELCTRL at `0xe60603c0`. Only POCCTRL is wired into an operation in this file.
- `r8a77951_pin_to_pocctrl()` translates voltage-switchable pins to POCCTRL bits: GP3.0-GP3.11 map to bits 0-11, and GP4.0-GP4.17 map to bits 12-29. Unsupported pins return `-EINVAL`.
- `pinmux_bias_regs[]` maps pins to PUEN0-6 and paired PUD0-6 registers at `0xe6060400`/`0xe6060440` and following offsets. `SH_PFC_PIN_NONE` entries represent unused register bits.
- `r8a77951_pfc_ops` supplies the SoC operations consumed by the core: `.pin_to_pocctrl = r8a77951_pin_to_pocctrl`, `.get_bias = rcar_pinmux_get_bias`, and `.set_bias = rcar_pinmux_set_bias`.
- `r8a774e1_pinmux_info` and `r8a77951_pinmux_info` are the exported SoC descriptors. Both use the same pins, register tables, ops, and `pinmux_data`; the R8A77951 descriptor adds the automotive group/function counts.

## Control Flow

Runtime behavior is data-driven. The generic Renesas PFC platform code selects the appropriate exported `sh_pfc_soc_info` object for the matched SoC, maps the PFC MMIO region, unlocks writes through PMMR at `0xe6060000`, and registers the pins, groups, and functions with the Linux pinctrl subsystem.

When a consumer selects a function/group, the core resolves the group name to its `<group>_pins[]` and `<group>_mux[]` arrays. Each mux mark is looked up through `pinmux_data[]`, then the core writes the relevant GPSR/IPSR/MOD_SEL fields described in `pinmux_config_regs[]`. For groups that need a module-select value, `PINMUX_IPSR_MSEL()` entries ensure the related MOD_SEL field is programmed with the correct `SEL_*` token.

Bias requests go through `rcar_pinmux_get_bias()` and `rcar_pinmux_set_bias()`, using `pinmux_bias_regs[]` to find the PUEN/PUD bit for the target pin. Drive-strength requests use `pinmux_drive_regs[]`. I/O-voltage requests call `r8a77951_pin_to_pocctrl()` to verify the pin is one of the advertised voltage-switchable GP3/GP4 pads and to compute the POCCTRL bit.

There is no revision-specific init callback in this file. `TDSELCTRL` is listed as an I/O-control register, and `linux/sys_soc.h` is included, but this source does not call `soc_device_match()` or write TDSEL during setup.

## State and Persistence Behavior

The file's software data is static and read-only after compilation. It performs no dynamic allocation, holds no locks, and has no filesystem persistence. Mutable state is external:

- GPSR/IPSR/MOD_SEL hardware fields persist the selected GPIO or peripheral mux route until changed by another pinctrl operation or by reset.
- DRVCTRL fields persist configured pad drive strength in the PFC hardware.
- PUEN/PUD fields persist pull enable and pull direction state for supported pins.
- POCCTRL persists 1.8 V/3.3 V signaling selection for GP3.0-GP3.11 and GP4.0-GP4.17.
- Pinctrl ownership, suspend/resume save/restore, MMIO locking, and write sequencing are handled by the shared `sh-pfc` infrastructure, not by this file.

## Dependencies and Integration Points

The source includes `linux/errno.h`, `linux/kernel.h`, `linux/sys_soc.h`, and local `sh_pfc.h`. The core dependencies are the Renesas PFC macros and types provided by `sh_pfc.h`: `struct sh_pfc_soc_info`, `struct sh_pfc_soc_operations`, `struct sh_pfc_pin`, `struct sh_pfc_pin_group`, `struct sh_pfc_function`, `struct pinmux_cfg_reg`, `struct pinmux_drive_reg`, `struct pinmux_bias_reg`, `struct pinmux_ioctrl_reg`, `RCAR_GP_PIN()`, `PORT_GP_CFG_*`, `PIN_NOGP_CFG`, `PINMUX_*`, `SH_PFC_PIN_GROUP`, `BUS_DATA_PIN_GROUP`, `SH_PFC_FUNCTION`, `PINMUX_CFG_REG*`, `PINMUX_DRIVE_REG`, and `PINMUX_BIAS_REG`.

External integration points are:

- The Renesas `sh-pfc` core, which consumes the exported SoC descriptor and all table pointers.
- Linux pinctrl and GPIO consumers, which request the function and group names exposed by `pinmux_functions[]`.
- Device-tree board files, which must choose valid group/function pairs such as `sdhi*_data4`, `qspi*_data4`, `avb_mii`, `scif*_data_*`, `msiof*_clk_*`, `vin4_data*_a/b`, or R8A77951-only `drif*` groups.
- Kconfig, which controls whether `r8a774e1_pinmux_info`, `r8a77951_pinmux_info`, and the automotive-only group/function arrays are compiled.
- Electrical board design, because the POCCTRL, drive-strength, and pull-bias tables only describe what software can request; safe values depend on the board's attached devices and pad voltage rails.

## Risks and Maintenance Notes

- Table correctness is the main risk. A wrong enum ordering, GPSR/IPSR field, MOD_SEL value, register address, mux mark, or group string can compile successfully while routing a real peripheral to the wrong pad.
- Pin and mux arrays must stay index-aligned. The helper macros catch many size mismatches, but they cannot prove that a given physical pin is the right hardware pad for the named signal.
- `pinmux_groups.common[328]`, `pinmux_groups.automotive[31]`, `pinmux_functions.common[55]`, and `pinmux_functions.automotive[5]` are fixed-size aggregate members. Adding or removing entries requires updating the declared sizes or the build will fail.
- The common versus automotive split is ABI-visible. Accidentally exposing DRIF/MLB groups through `r8a774e1_pinmux_info` would change the RZ/G2H public pinctrl surface; accidentally omitting them from `r8a77951_pinmux_info` would break R-Car H3 automotive users.
- Shared pins appear in many mutually exclusive alternatives, especially serial, I2C, VIN, audio, and timer routes. Pinctrl can prevent simultaneous ownership conflicts, but it cannot validate that a board selected the intended alternate route.
- The I2C physical pin handling is subtle. Some groups use `PINMUX_IPSR_PHYS()`/`PINMUX_IPSR_PHYS_MSEL()` and `I2C_SEL_*` values to represent SCL/SDA physical aliases; a mismatch can make an apparently valid I2C group program the wrong selector.
- Voltage-control support must match both `CPU_ALL_GP()` flags and `r8a77951_pin_to_pocctrl()`. Advertising voltage switching without a valid POCCTRL bit, or mapping a bit for an unadvertised pin, would cause inconsistent pinconf behavior.
- `pinmux_bias_regs[]` contains explicit `SH_PFC_PIN_NONE` holes. Bias support should be inferred from the table, not from nearby pins or register contiguity.
- `TDSELCTRL` is present in the I/O-control register table but unused by operations in this file. Future TDSEL-related changes need a deliberate operation hook or core support rather than assuming the register is programmed today.

## Test Signals

- Build with `CONFIG_PINCTRL_PFC_R8A77951=y` to verify all common and automotive groups/functions, including DRIF/MLB and the gated `PIN_DU_DOTCLKIN2` drive entry, compile and match declared counts.
- Build with `CONFIG_PINCTRL_PFC_R8A774E1=y` to verify the common-only descriptor compiles without referencing automotive-only arrays.
- Boot or probe logs should show successful registration of `r8a77951_pfc` or `r8a774e1_pfc` with no unresolved pin group/function names.
- Pinctrl debugfs should list the expected common functions and, on R8A77951 builds, the additional `drif0`-`drif3` and `mlb_3pin` functions.
- Device-tree smoke tests should request representative routes from each large family: AVB, CAN/CAN-FD, SDHI0-3 including bus-width groups, QSPI0/1 data2/data4, SCIF/HSCIF/MSIOF alternatives, I2C physical alternatives, SSI/audio clock pins, USB PWEN/OVC, DU RGB/sync, VIN4/VIN5 widths, and automotive DRIF groups where available.
- Register-level validation should confirm selected groups produce the expected GPSR/IPSR/MOD_SEL writes and do not touch reserved fields in variable-width register definitions.
- Pinconf tests should exercise drive strength and pull-up/pull-down on known covered pins, plus negative tests for unsupported pins and `SH_PFC_PIN_NONE` holes.
- Voltage tests should request 1.8 V/3.3 V switching for GP3.0-GP3.11 and GP4.0-GP4.17 and verify unsupported pins return `-EINVAL`.
