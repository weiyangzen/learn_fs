# sources/distributed-fs/ceph-client/drivers/pinctrl/renesas/pfc-r8a77965.c

Research item: `subset-b-005099`

## Purpose

This file is the Renesas R-Car M3-N / R8A77965 pin function controller (PFC) SoC description used by the shared `drivers/pinctrl/renesas/sh-pfc` core. It is almost entirely declarative: it describes the pins, GPIO-capable ports, non-GPIO pins, mux marks, pin groups, pin functions, register bit layouts, drive-strength controls, pull-up/down controls, and IO-voltage controls for this SoC family. The shared PFC core consumes the exported `struct sh_pfc_soc_info` instances and performs the actual pinctrl, pinmux, GPIO, and pin configuration operations.

The same register map is also reused for the RZ/G2N-compatible `r8a774b1_pfc` build path, but that variant exposes only the common group/function set. When `CONFIG_PINCTRL_PFC_R8A77965` is enabled, the R8A77965 descriptor additionally exposes automotive groups and functions for DRIF and MLB.

## Important APIs, Types, and Data

- `CFG_FLAGS` combines `SH_PFC_PIN_CFG_DRIVE_STRENGTH` and `SH_PFC_PIN_CFG_PULL_UP_DOWN`; most pins declared in this file advertise both configuration capabilities.
- `CPU_ALL_GP(fn, sfx)` expands all GPIO-backed pin descriptors by GPIO bank. GP3 pins 0-11 and all GP4 pins additionally advertise `SH_PFC_PIN_CFG_IO_VOLTAGE_18_33`, making them eligible for 1.8 V / 3.3 V switching through POCCTRL.
- `CPU_ALL_NOGP(fn)` declares fixed/non-GPIO pins such as QSPI, RPC, AVB, DU dot clock inputs, JTAG-like pins, MLB_REF, PRESETOUT#, and EXTALR.
- `GPSR*`, `IP*`, and `MOD_SEL*` macros encode the hardware mux tables. GPSR entries select GPIO versus peripheral function for a port bit; IPSR entries encode the peripheral function value for a 4-bit selector field; MOD_SEL entries encode extra module select bits needed when one peripheral signal has multiple possible pin routes.
- The central enum builds three ID ranges: data IDs, function IDs (`FN_*`), and mark IDs (`*_MARK`). These IDs are later used by `pinmux_data`, pin group mux arrays, and register tables.
- `pinmux_data[]` maps generated marks to GPSR/IPSR/MOD_SEL programming requirements using macros such as `PINMUX_IPSR_GPSR`, `PINMUX_IPSR_MSEL`, `PINMUX_IPSR_PHYS`, and `PINMUX_IPSR_PHYS_MSEL`. Static non-muxable pins are represented with `PINMUX_DATA(mark, 0)` so the core can configure them without trying to mux them.
- `pinmux_pins[]` exposes all GPIO and non-GPIO pins to the core via `PINMUX_GPIO_GP_ALL()` and `PINMUX_NOGP_ALL()`.
- `pinmux_groups` is split into `common[326]` and, for R8A77965 builds, `automotive[31]`. Each group pairs a `<name>_pins[]` array with a `<name>_mux[]` array through `SH_PFC_PIN_GROUP`, `BUS_DATA_PIN_GROUP`, or subset/alias helpers.
- `pinmux_functions` is similarly split into `common[53]` and optional `automotive[5]`. Function arrays collect group names exposed to device tree clients through the Linux pinctrl API.
- `pinmux_config_regs[]` describes the mux programming registers: GPSR0-GPSR7 at `0xe6060100` through `0xe606011c`, IPSR0-IPSR18 at `0xe6060200` through `0xe6060248`, and MOD_SEL0-MOD_SEL2 at `0xe6060500` through `0xe6060508`.
- `pinmux_drive_regs[]` describes DRVCTRL0-DRVCTRL24 at `0xe6060300` through `0xe6060360`, mapping each configurable pin to a bit offset and field width.
- `pinmux_bias_regs[]` describes PUEN0-PUEN6 at `0xe6060400` through `0xe6060418` and matching PUD0-PUD6 at `0xe6060440` through `0xe6060458`, mapping pins to pull-enable and pull-direction bits.
- `pinmux_ioctrl_regs[]` exposes POCCTRL at `0xe6060380` and TDSELCTRL at `0xe60603c0`.
- `r8a77965_pin_to_pocctrl()` is the only local function with logic. It maps GP3_0-GP3_11 to POCCTRL bits 0-11 and GP4_0-GP4_17 to bits 12-29; other pins return `-EINVAL`.
- `r8a77965_pfc_ops` wires `pin_to_pocctrl`, `rcar_pinmux_get_bias`, and `rcar_pinmux_set_bias` into the SoC descriptor.
- `r8a774b1_pinmux_info` and `r8a77965_pinmux_info` are the exported `struct sh_pfc_soc_info` descriptors. Both set `unlock_reg = 0xe6060000` for PMMR, point at the common tables, and expose table sizes with `ARRAY_SIZE`.

## Functional Coverage

The common group/function inventory covers the major R-Car peripheral pin users:

- Audio clock outputs and SSI audio pins.
- EtherAVB link, MDIO/MDC, MII, AVTP match/capture, and PPS pins.
- CAN, CAN clock, and CAN FD routes.
- DU RGB output, sync, CDE, DISP, ODD/EXODDF, and dot clock outputs.
- HSCIF0-HSCIF4 and SCIF0-SCIF5 serial routes, including alternate data/clock/control pins.
- I2C0, I2C1, I2C2, I2C3, I2C5, and I2C6 routes, with some physical I2C alternatives represented through `PINMUX_PHYS`.
- INTC external IRQ0-IRQ5.
- MSIOF0-MSIOF3 serial interfaces with many route alternatives.
- PWM0-PWM6, QSPI0/QSPI1, SATA DEVSLP, SDHI0-SDHI3, TMU clocks, TPU outputs, USB0/USB1/USB30 power/over-current pins, VIN4, and VIN5.

The R8A77965-only automotive section adds DRIF0-DRIF3 receiver interface groups and the MLB 3-pin group. These are guarded by `CONFIG_PINCTRL_PFC_R8A77965`; the R8A774B1 descriptor does not include them.

## Control Flow

There is no probe function or direct registration logic in this file. Control flow is data-driven:

1. The platform-specific PFC driver selects one of the exported `sh_pfc_soc_info` descriptors according to the matched SoC/configuration.
2. The shared `sh-pfc` core uses `pins`, `groups`, `functions`, `pinmux_data`, and the function ID range to build Linux pinctrl and pinmux views.
3. When a client selects a pin function/group, the core resolves the requested group to mux marks, then consults `pinmux_data[]` and `pinmux_config_regs[]` to determine which GPSR, IPSR, and MOD_SEL bits must be programmed.
4. Register writes are protected by the PMMR unlock register at `0xe6060000`, as indicated by `.unlock_reg`.
5. Pin configuration requests, such as drive strength or bias, flow through the shared core into `pinmux_drive_regs[]` and `pinmux_bias_regs[]`.
6. IO voltage requests use the SoC operation `.pin_to_pocctrl`, implemented by `r8a77965_pin_to_pocctrl()`, to translate eligible pins to POCCTRL bit positions.

Because the file is declarative, most behavioral regressions come from bad table entries rather than branches. The main runtime branch is the POCCTRL pin-range check. Build-time branches decide whether automotive groups/functions and which SoC info export are compiled.

## State and Persistence Behavior

The file itself owns no dynamic state, no heap allocations, no locks, and no persistence layer. Its static const tables become read-only kernel data after build/load. Persistent effects are hardware register writes performed by the shared PFC core:

- GPSR/IPSR/MOD_SEL registers persist in the PFC hardware until reset or later reconfiguration.
- DRVCTRL registers persist drive-strength choices.
- PUEN/PUD registers persist pull enable and pull direction state.
- POCCTRL persists IO-voltage selection for supported SDHI-related banks.

The tables include sentinel entries in register arrays, so the core can iterate until a terminating zero/sentinel entry. Incorrect or missing sentinels would affect register table traversal.

## Dependencies and Integration Points

This file depends on Linux kernel headers `<linux/errno.h>` and `<linux/kernel.h>`, and heavily on `sh_pfc.h` for all PFC-specific macros and type definitions. Important external definitions include:

- `struct sh_pfc_pin`, `struct sh_pfc_pin_group`, `struct sh_pfc_function`, `struct pinmux_cfg_reg`, `struct pinmux_drive_reg`, `struct pinmux_bias_reg`, `struct pinmux_ioctrl_reg`, `struct sh_pfc_soc_operations`, and `struct sh_pfc_soc_info`.
- Table-generation macros such as `PORT_GP_CFG_*`, `PIN_NOGP_CFG`, `GP_ALL`, `NOGP_ALL`, `PINMUX_GPIO_GP_ALL`, `PINMUX_NOGP_ALL`, `PINMUX_DATA_GP_ALL`, `PINMUX_SINGLE`, `PINMUX_IPSR_*`, `PINMUX_CFG_REG*`, `PINMUX_DRIVE_REG`, `PINMUX_BIAS_REG`, `SH_PFC_PIN_GROUP`, `SH_PFC_FUNCTION`, and `RCAR_GP_PIN`.
- Shared helpers `rcar_pinmux_get_bias` and `rcar_pinmux_set_bias`.

The external integration surface is the Linux pinctrl subsystem. Board device trees request functions/groups by the string names generated in `pinmux_functions` and `pinmux_groups`, such as `sdhi0_data4`, `avb_mii`, `scif4_data_c`, or `vin4_data24_a`. The names in the function group arrays are therefore ABI-like within the kernel/device-tree ecosystem; renaming or removing them can break existing board descriptions. The `avb_mdc` group is kept as a deprecated alias for `avb_mdio`, showing explicit backward compatibility.

## Risk Areas

- Table consistency is the primary risk. For every group, the pins array and mux array must have matching order and length. A mismatch can program the wrong mux mark for a physical pin.
- Alternate-route entries must pair the correct IPSR function value with the correct MOD_SEL selector. Errors in `PINMUX_IPSR_MSEL` or `PINMUX_IPSR_PHYS_MSEL` can make one route work while silently breaking another route for the same peripheral.
- Conditional automotive content changes array sizes and pointer semantics. `r8a77965_pinmux_info` points at `pinmux_groups.common` and adds `ARRAY_SIZE(pinmux_groups.automotive)` to the count, relying on the `common` and `automotive` arrays being adjacent inside the enclosing struct. The same applies to functions. Changing the struct layout or adding fields would break this contiguous-table assumption.
- POCCTRL mapping is range-based and depends on `RCAR_GP_PIN()` encoding. If the encoding changes, or if a new voltage-capable bank is added without updating `r8a77965_pin_to_pocctrl()`, IO voltage control may target the wrong bit or reject valid pins.
- Drive and bias registers mix GPIO-backed pins and non-GPIO `PIN_*` constants. Incorrect constants can expose unsupported configuration or miss supported configuration for fixed pins.
- Several physical I2C alternatives are represented with `PINMUX_PHYS` and `PINMUX_PHYS_MSEL`, which means they are deliberately not simple GPSR-only routes. These entries are easy to regress if treated like ordinary mux alternatives.
- Static pins are non-muxable but still configurable. Removing them from `PINMUX_STATIC` or `pinmux_data[]` would prevent bias/drive configuration even though no mux register should be programmed.
- Some pins are shared among many functions, especially audio/SSI/MSIOF/SCIF/DRIF and SDHI/NAND-like alternatives. A table change can have broad board-level effects beyond the function being edited.

## Test Signals

Useful verification signals are mostly build-time, device-tree binding, and hardware/runtime pinctrl behavior:

- Build with `CONFIG_PINCTRL_PFC_R8A774B1=y` and `CONFIG_PINCTRL_PFC_R8A77965=y` to cover both exported descriptors and the conditional automotive groups.
- Enable compile warnings that catch unused or missing table symbols; most group/mux omissions surface as undefined mark/group references or unused arrays.
- Boot on supported boards and inspect pinctrl debugfs output for expected pin, group, and function names, including common names and R8A77965-only DRIF/MLB names.
- Exercise representative device-tree pinctrl states for SDHI, AVB, SCIF/HSCIF, I2C, MSIOF, USB, VIN, DU, QSPI, and SSI to confirm GPSR/IPSR/MOD_SEL programming.
- Test pull-up/down configuration on pins present in PUEN/PUD tables and confirm unsupported pins fail cleanly.
- Test drive-strength configuration on pins listed in DRVCTRL tables, especially AVB, SDHI, serial, and fixed QSPI/RPC pins.
- Test IO voltage switching only on GP3_0-GP3_11 and GP4_0-GP4_17; attempts on other pins should return an error path through `-EINVAL`.
- Regression-check existing device trees that use deprecated `avb_mdc`; the alias should continue resolving to the `avb_mdio` group.

## Bottom Line

`pfc-r8a77965.c` is the authoritative static pinmux and pin configuration map for R8A77965-family PFC hardware. Its correctness depends on exact alignment among pin IDs, mux marks, group arrays, function string lists, and register bitfields. The shared Renesas PFC core provides the runtime mechanics; this file supplies the SoC-specific truth table that determines which hardware bits are written for every pinctrl request.
