# sources/distributed-fs/ceph-client/drivers/pinctrl/renesas/pfc-r8a7779.c

## Purpose

This file is the Renesas R-Car H1 / `r8a7779` SoC pin function controller description for the shared Renesas `sh_pfc` pinctrl/GPIO framework. It contains no probe routine and almost no executable control flow of its own; instead it exports one descriptor, `r8a7779_pinmux_info`, that tells the common driver which pins exist, which alternate functions can be selected, which register fields control those choices, and which pins support configurable pull-up bias.

The hardware modeled here is the PFC block at the `0xfffc0000` register range. The file maps GPIO banks GP0-GP6, non-GPIO external/debug pins, multiplexed peripheral signals, module-select fields, and pull-up registers. Downstream board code or device tree pinctrl states use the named functions and groups from this descriptor to request pin modes such as DU display output, Ethernet RMII, serial ports, HSPI, I2C, SDHI/MMC, USB, VIN capture, interrupt inputs, PWM, and local bus chip selects.

## Important APIs, Types, and Data

- `CPU_ALL_GP(fn, sfx)` and `CPU_ALL_NOGP(fn)` define the SoC pin universe. GPIO-capable pins are mostly generated with `PORT_GP_*` macros and many are flagged with `SH_PFC_PIN_CFG_PULL_UP`; non-GPIO pins cover external data/debug/reset pins such as `D0-D15`, JTAG pins, `ASEBRK#/ACK`, and `PRESETOUT#`.
- The large anonymous `enum` establishes the integer IDs consumed by the `sh_pfc` macros. It is split into `PINMUX_DATA_*`, `PINMUX_FUNCTION_*`, and `PINMUX_MARK_*` ranges. Function IDs include raw register field symbols (`FN_IP...`, `FN_SEL...`) and peripheral signal symbols (`FN_SD0_CLK`, `FN_ETH_TXD0`, etc.); mark IDs are the user-facing mux targets used by group descriptors.
- `pinmux_data[]` binds function marks to register field alternatives. It uses `PINMUX_DATA_GP_ALL()` for GPIO data/function pairs, `PINMUX_SINGLE()` for simple single-function pins, `PINMUX_IPSR_GPSR()` for GPSR plus IPSR-controlled functions, and `PINMUX_IPSR_MSEL()` where a mux choice also depends on `MOD_SEL`/`MOD_SEL2`.
- `pinmux_pins[]` describes all pins as `struct sh_pfc_pin` entries, generated from `PINMUX_GPIO_GP_ALL()` and `PINMUX_NOGP_ALL()`.
- Per-peripheral `<group>_pins[]` and `<group>_mux[]` arrays define concrete pin groups. Each pin list uses `RCAR_GP_PIN(bank, pin)` and has a same-length mux mark list. These arrays are consumed by `SH_PFC_PIN_GROUP()` or `BUS_DATA_PIN_GROUP()`.
- `pinmux_groups[]` is the full `struct sh_pfc_pin_group` catalog. It includes display groups for `du0`/`du1`, `ether_rmii`, HSCIF/SCIF alternatives, HSPI, I2C, interrupt lines, LBSC chip selects, MMC/SDHI data-width groups, PWM, USB PENC/OVC, and VIN0-VIN3 groups.
- `<function>_groups[]` string arrays collect related groups into pinctrl functions. `pinmux_functions[]` exposes 40 `struct sh_pfc_function` entries: `du0`, `du1`, `ether`, `hscif0`, `hscif1`, `hspi0`, `hspi1`, `hspi2`, `i2c1`, `i2c2`, `i2c3`, `intc`, `lbsc`, `mmc0`, `mmc1`, `pwm0` through `pwm6`, `scif0` through `scif5`, `scif_clk`, `sdhi0` through `sdhi3`, `usb0` through `usb2`, and `vin0` through `vin3`.
- `pinmux_config_regs[]` is the register programming map. It declares GPSR0-GPSR6 at `0xfffc0004` through `0xfffc001c`, IPSR0-IPSR12 at `0xfffc0020` through `0xfffc0050`, and `MOD_SEL`/`MOD_SEL2` at `0xfffc0090`/`0xfffc0094`. Variable-width registers use `PINMUX_CFG_REG_VAR()` with bitfield width groups, including negative widths for reserved spans.
- `pinmux_bias_regs[]` maps pull-up registers PUPR0-PUPR6 at `0xfffc0100` through `0xfffc0118` to pin IDs. Unsupported/reserved pull-up bits are represented as `SH_PFC_PIN_NONE`.
- `r8a7779_pfc_ops` wires the SoC to shared bias handlers `rcar_pinmux_get_bias` and `rcar_pinmux_set_bias`.
- `r8a7779_pinmux_info` is the exported `const struct sh_pfc_soc_info`. It names the SoC as `r8a7779_pfc`, points at every table above, sets `.unlock_reg = 0xfffc0000` for PMMR-protected writes, and provides the pinmux data size.

## Control Flow

Control flow is descriptor-driven:

1. Platform registration for the R-Car H1 PFC selects `r8a7779_pinmux_info` from this compilation unit.
2. The common `sh_pfc` code enumerates `pinmux_pins`, `pinmux_groups`, and `pinmux_functions` to register pinctrl, pinmux, GPIO, and pin configuration capabilities.
3. A consumer requests a function/group pair, such as `sdhi0` plus `sdhi0_data4`.
4. The common code resolves the group to its mux marks, finds those marks in `pinmux_data[]`, and computes the GPSR/IPSR/MOD_SEL field writes described by `pinmux_config_regs[]`.
5. If the register is protected, writes are performed through the PMMR unlock register at `0xfffc0000`.
6. Bias get/set requests call the shared R-Car helpers through `r8a7779_pfc_ops`; those helpers use `pinmux_bias_regs[]` to locate the relevant PUPR bit for a pin.

There are no local loops, conditionals, interrupt handlers, workqueues, allocation paths, or error paths in this file. All validation and register I/O behavior lives in the shared Renesas PFC implementation and depends on the correctness of these static tables.

## State and Persistence

The only durable state affected by this file is hardware register state:

- GPSR registers select whether each GPIO-capable pin is GPIO or peripheral-function mode.
- IPSR registers select one alternate signal among a field's candidates.
- `MOD_SEL` and `MOD_SEL2` hold secondary selector state for functions with multiple routes, such as SCIF, SSI, SD2, interrupt inputs, CAN clock/CAN0, HSCIF, PWMFSW, ADI, GPS, SIM, HSPI, and I2C alternatives.
- PUPR registers enable or disable pull-ups for supported pins.

The C data itself is immutable (`static const` or exported `const`). It does not persist software state across suspend/resume; any restoration policy is handled by the common pinctrl/PFC layer and platform power-management code. Incorrect static mappings can still persist in hardware until another pinctrl state reprograms the same fields.

## Dependencies and Integration Points

- Includes `<linux/kernel.h>` for kernel helper macros such as `ARRAY_SIZE`.
- Includes `"sh_pfc.h"`, which defines the descriptor types and macros used throughout: `struct sh_pfc_soc_info`, `struct sh_pfc_pin`, `struct sh_pfc_pin_group`, `struct sh_pfc_function`, `struct pinmux_cfg_reg`, `struct pinmux_bias_reg`, `RCAR_GP_PIN`, `PINMUX_*`, `SH_PFC_*`, `PORT_GP_*`, and the R-Car bias helper declarations.
- Integrates with Linux pinctrl via the shared Renesas `sh_pfc` driver. This file supplies SoC-specific data; the shared driver supplies parsing, conflict checks, GPIO range registration, register reads/writes, PMMR unlock handling, and pinconf operations.
- Integrates with peripheral drivers indirectly. Device tree or board pinctrl states name the functions and groups exposed here, while the peripheral drivers rely on pinctrl core to apply those states before I/O.
- The named groups form ABI-like strings for board descriptions. Renaming groups or functions can break existing platform data or device tree bindings for this SoC.

## Hardware Coverage Notes

The group catalog covers several high-risk mux families:

- Display: DU0/DU1 RGB666/RGB888, clock input/output, sync, ODDF, DISP, and CDE variants.
- Storage: SDHI0-SDHI3 and MMC0/MMC1 with bus-width helper groups.
- Serial: SCIF0-SCIF5, HSCIF0-HSCIF1, and shared SCIF clock routes, many with `_b`, `_c`, `_d`, or `_e` alternatives controlled by module select bits.
- Video input: VIN0-VIN3 data/clock/sync groups.
- Board I/O: USB PENC/OVC, Ethernet RMII/link/magic, LBSC chip selects, I2C1-I2C3 alternatives, PWM0-PWM6, interrupt input alternatives, and HSPI0-HSPI2 alternatives.

## Risks

- Table alignment is the main correctness risk. Each `<group>_pins[]` array must match its `<group>_mux[]` array in length and signal order; a mismatch silently programs wrong signals onto valid pins.
- Register bitfield definitions are dense and hand-maintained. A wrong width in `PINMUX_CFG_REG_VAR()`, an omitted reserved slot, or a misplaced `0` placeholder shifts subsequent alternatives and can corrupt unrelated pin selections.
- `PINMUX_IPSR_MSEL()` entries must agree with the `MOD_SEL`/`MOD_SEL2` field encodings. A wrong selector couples otherwise correct IPSR settings to the wrong physical route.
- Many pins are shared across unrelated peripherals, for example serial, I2C, display, HSPI, SDHI, and interrupt alternatives. Conflicts are expected at the board-design level, so regressions often appear as one peripheral stealing another peripheral's pins.
- Pull-up support is not universal. `CPU_ALL_GP()` marks many pins as pull-up capable, but actual bias control depends on the PUPR table. Missing or wrong `SH_PFC_PIN_NONE` entries can make pinconf report support incorrectly or change the wrong pull-up bit.
- PMMR-protected writes depend on `.unlock_reg = 0xfffc0000`. If this base or register table is wrong, configuration writes may be ignored or affect the wrong hardware register.
- The file exposes stable function/group names. Even refactors that preserve register values can break board files if names change.

## Test Signals

- Build coverage: compile the Renesas pinctrl driver configuration that includes this SoC and treat warnings about array sizes, enum references, missing symbols, or const initializers as regressions.
- Static descriptor checks: verify every group has matching pin and mux array lengths, every group name referenced by a `<function>_groups[]` array exists in `pinmux_groups[]`, and every mark used by a mux array is represented in `pinmux_data[]`.
- Register-map review: compare GPSR/IPSR/MOD_SEL/PUPR addresses and bitfield widths against the R8A7779 hardware manual, especially reserved fields and multi-route selectors.
- Runtime pinctrl smoke tests on R8A7779 hardware or an equivalent board should request representative groups from each mux family: `ether_rmii`, `sdhi*_data4`, `mmc*_data8`, `scif*_data` variants, `i2c*_b/c/d`, `usb*_ovc`, `vin*_data8`, and DU RGB groups.
- Bias tests should call pinconf get/set for pins listed in PUPR0-PUPR6 and verify unsupported pins fail cleanly or report no bias support.
- Debugfs inspection through pinctrl should show the expected function/group names and current mux ownership after board pinctrl states are applied.
