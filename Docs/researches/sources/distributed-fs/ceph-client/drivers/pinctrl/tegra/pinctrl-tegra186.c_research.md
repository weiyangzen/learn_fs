# sources/distributed-fs/ceph-client/drivers/pinctrl/tegra/pinctrl-tegra186.c

Purpose: Provides static SoC description tables for the NVIDIA Tegra186 pinmux driver. It does not implement pinctrl algorithms itself; instead it declares Tegra186 pin IDs, pin descriptors, one-pin pin groups, supported mux function names, register/bit layout metadata, and platform-driver match data consumed by the shared Tegra pinctrl core.

Important APIs, types, and functions: The file builds `struct pinctrl_pin_desc` arrays for the main controller (`tegra186_pins`) and always-on controller (`tegra186_aon_pins`). It defines many one-element `*_pins[]` arrays used by `struct tegra_pingroup` entries. `enum tegra_mux_dt` and `tegra186_functions[]` define the exported function namespace, including PCIe, EQOS, SDMMC, QSPI, UFS, display, I2C, UART, CAN, audio, USB, and reserved functions. Macro families `PIN_PINGROUP_ENTRY_*`, `DRV_PINGROUP_ENTRY_*`, `PINGROUP`, and `DRV_PINGROUP` populate `struct tegra_pingroup` fields such as mux alternatives, mux/pull/tristate register offsets, input/open-drain/Schmitt/drive-type bits, low-power bits, pre-emphasis, and drive-strength/slew fields. `tegra186_pinctrl_probe()` fetches `of_device_get_match_data()` and calls `tegra_pinctrl_probe()`. `tegra186_pinctrl_of_match[]`, `tegra186_pinctrl_driver`, and `arch_initcall(tegra186_pinctrl_init)` bind the data to `"nvidia,tegra186-pinmux"` and `"nvidia,tegra186-pinmux-aon"`.

Control flow: At `arch_initcall` time the platform driver is registered. Device-tree matching chooses either `tegra186_pinctrl` or `tegra186_pinctrl_aon` as match data. Probe passes that static `struct tegra_pinctrl_soc_data` to the shared core, which then exposes pinctrl/pinmux/pinconf operations using the arrays in this file. Runtime mux, pull, tristate, input, open-drain, drive, Schmitt, and special-function-selection operations are therefore table-driven: the shared core looks up a group/function/configuration and writes the register bank, offset, bit, and width encoded here.

State and persistence behavior: This source stores no mutable driver state. All data is `static const` and persists for the lifetime of the kernel image. Mutable state lives in the shared `struct tegra_pmx` allocated by `tegra_pinctrl_probe()` and in the hardware registers that pinctrl clients program. Hardware pin state persists until firmware, bootloader, kernel pinctrl states, suspend/resume restore paths, or another client changes the pinmux registers. The main and AON instances are separate hardware blocks selected by compatible string, so their groups and register offsets must not be mixed.

Dependencies and integration points: Depends on Linux platform-driver, OF match, and pinctrl/pinmux headers, plus the local `pinctrl-tegra.h` shared data contract. It integrates with device tree through `nvidia,tegra186-pinmux` and `nvidia,tegra186-pinmux-aon` nodes, and with board/device pin configuration through normal pinctrl states. It also indirectly integrates with Tegra GPIO and peripheral drivers because correct mux/function/group names are required for SDMMC, EQOS Ethernet, PCIe reset/clock-request, QSPI, UFS, display, camera, audio, CAN, I2C, UART, USB VBUS, and power-management pins.

Risks: The file is highly table-sensitive: a wrong enum value, pin descriptor string, group pin array, mux function order, register offset, bank, bit number, or field width silently sends the shared core to the wrong hardware control. A notable source-data risk is that the `PINCTRL_PIN()` descriptor for `TEGRA_PIN_GPIO_CAM5_PN4` uses the string `"GPIO_CAM6_PN5"` rather than a CAM5 name, creating duplicate visible pin naming with `TEGRA_PIN_GPIO_CAM6_PN5`. Some groups intentionally have no drive entry or empty SDMMC4 pin arrays while still having pingroup register definitions; these require compatibility with the shared core's handling of zero-pin or no-drive groups. AON/main separation is another risk because register offsets overlap conceptually but target different MMIO resources. Electrical risks include misprogramming high-voltage, open-drain, pull, drive-strength, slew, pre-emphasis, and low-power bits for high-speed buses such as SDMMC, EQOS, QSPI, and UFS.

Test signals: Build coverage should include this file and `pinctrl-tegra.c` with OF matching for both compatible strings. Runtime signals include successful registration of main and AON pinctrl devices, pinctrl debugfs showing expected pin names/groups/functions, device-tree pin states selecting common functions (`sdmmc1`, `sdmmc3`, `eqos`, `qspi`, `ufs0`, `uart*`, `i2c*`, `can*`) without lookup failures, and hardware validation that pins toggle or communicate on the intended peripherals. Regression checks should include duplicate/mistyped pin names, AON GPIO/power pin configuration, suspend/resume preservation through the shared Tegra pinctrl PM path, and pinconf reads/writes for pull, tristate, input, open-drain, Schmitt, drive type, drive strength, and slew where supported.
