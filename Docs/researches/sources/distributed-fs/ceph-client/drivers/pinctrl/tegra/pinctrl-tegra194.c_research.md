# sources/distributed-fs/ceph-client/drivers/pinctrl/tegra/pinctrl-tegra194.c

Purpose: Provides static pinctrl/pinmux data for NVIDIA Tegra194. Like the Tegra186 file, it is a SoC data provider for the shared Tegra pinctrl core, but it reflects Tegra194-specific pin inventory, mux functions, register layout, high-speed-mode support, and per-group I/O rail names.

Important APIs, types, and functions: `tegra194_pins` and `tegra194_aon_pins` describe the main and AON pin sets. Single-pin `*_pins[]` arrays feed the pingroup table. `enum tegra_mux_dt` and `tegra194_functions[]` define the function IDs/names; compared with Tegra186 this includes Tegra194-specific function coverage such as `slvs`, `igpu`, `dgpu`, `pe3`, `pe4`, `pe5`, `qspi0`, `qspi1`, and `mipi`. The `PIN_PINGROUP_ENTRY_Y()` macro includes an `io_rail` argument in addition to mux, pull, tristate, input, GPIO/SFIO, open-drain, Schmitt, drive type, pre-emphasis, I/O reset, and reserved-input bits. `DRV_PINGROUP_ENTRY_Y()` encodes drive-strength and slew-rate fields. The `tegra194_pinctrl` and `tegra194_pinctrl_aon` `struct tegra_pinctrl_soc_data` objects set `hsm_in_mux`, `schmitt_in_mux`, `drvtype_in_mux`, and `sfsel_in_mux` to true. Probe and registration are handled by `tegra194_pinctrl_probe()`, `tegra194_pinctrl_of_match[]`, `tegra194_pinctrl_driver`, and `arch_initcall(tegra194_pinctrl_init)`.

Control flow: The platform driver registers during architecture initialization. OF match data selects the main or AON `struct tegra_pinctrl_soc_data`, and probe delegates to `tegra_pinctrl_probe()`. After that, all pinctrl operations are data-driven by `tegra194_groups` or `tegra194_aon_groups`: group lookup maps a consumer's device-tree pin state to a mux function and optional pinconf fields, and the common Tegra core programs the encoded bank/offset/bit fields. Main controller groups cover audio, QSPI0/1, EQOS, SOC GPIO, UART, DAP/I2S, SDMMC, PCIe, SATA, display, camera I2C, DirectDC, SPI, UFS, USB, GPU/CV power request, and high-speed storage/flash pins. AON groups cover CAN, SPI2, touch clock, UART3, I2C2/I2C5/I2C8, safe-state/power-management, reset/shutdown/PMU interrupt, and 32 kHz clock pins.

State and persistence behavior: The file has only immutable tables. Runtime state and synchronization are owned by the shared Tegra pinctrl core and the platform device. Programmed pin state persists in MMIO registers until another pinctrl state, firmware handoff, suspend/resume path, or driver action changes it. Tegra194 groups also carry I/O rail labels such as `vddio_audio`, `vddio_cam`, `vddio_pex_ctl`, `vddio_qspi`, `vddio_sdmmc*_hv`, `vddio_ao`, and `vddio_sys`; those labels are persistent metadata used by the core and bindings to reason about the electrical domain for a group.

Dependencies and integration points: Depends on Linux OF/platform/pinctrl headers and the shared local `pinctrl-tegra.h` definitions. Device-tree integration is through `"nvidia,tegra194-pinmux"` and `"nvidia,tegra194-pinmux-aon"`. Peripheral integration is broad: storage controllers depend on SDMMC and QSPI muxing, networking depends on EQOS groups and `vddio_eqos`, PCIe/SATA depend on reset/CLKREQ/WAKE groups, display and camera depend on DP/HDMI/DirectDC/camera groups, and AON/power-management code depends on reset, PMU, safe-state, power I2C, 32 kHz, and CAN pins.

Risks: Tegra194 adds I/O rail metadata and more high-speed/voltage-sensitive groups, increasing the cost of table mistakes. Incorrect `io_rail` values can associate a group with the wrong electrical domain. Wrong mux alternatives or field bits can break boot-critical devices such as storage, power I2C, PCIe reset, or PMU interrupt lines. Many drive entries are intentionally `DRV_PINGROUP_ENTRY_N(no_entry)` for high-speed or special groups, so callers and tests must distinguish unsupported drive configuration from a regression. Main and AON tables reuse similar function names while addressing different MMIO blocks. Because `hsm_in_mux` is true for Tegra194, high-speed mode programming uses mux register fields; offsets and bit positions are especially important.

Test signals: Build and boot with both pinmux compatible strings. Confirm pinctrl debugfs exposes expected main and AON pins, groups, functions, and where available I/O rail metadata. Exercise representative pin states for QSPI0/1, SDMMC1/3/4, EQOS, PCIe lane controls including PE5, UFS0, USB VBUS, UARTs, I2C, SPI, audio DAPs, CAN, and power-management pins. Validate pinconf operations for pull, tristate, input, open-drain, Schmitt, high-speed mode, drive type, special-function select, drive strength, and slew only on groups that advertise the relevant bits. Hardware-level test signals include storage enumeration, EQOS link, PCIe link training, AON wake/power behavior, CAN bus operation, and suspend/resume with pin state preserved or restored.
