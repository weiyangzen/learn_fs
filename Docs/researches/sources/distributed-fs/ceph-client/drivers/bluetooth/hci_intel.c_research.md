# sources/distributed-fs/ceph-client/drivers/bluetooth/hci_intel.c

Purpose: This file implements the Intel Bluetooth HCI UART protocol for ACPI-described Intel controllers. It combines H4 framing with Intel bootloader handling, firmware and DDC download, baud-rate switching, reset GPIO power control, host-wake IRQ runtime PM, and Intel low-power-management packets.

Important APIs, types, and functions: `struct intel_device` represents the platform side: ACPI platform device, reset GPIO, optional host-wake IRQ, current `hci_uart`, and a lock. `struct intel_data` is per-HCI-UART protocol state: partial RX skb, TX queue, busy work, flags, and parent `hci_uart`. Flag bits model bootloader, downloading, firmware loaded/failed, booting, LPM enabled, TX active, suspended, and LPM transaction states. Main callbacks are `intel_open`, `intel_close`, `intel_flush`, `intel_setup`, `intel_set_baudrate`, `intel_recv`, `intel_enqueue`, and `intel_dequeue`. Platform hooks are `intel_probe`, `intel_remove`, PM callbacks, and IRQ handler `intel_irq`.

Control flow: Platform probe maps ACPI GPIOs, acquires reset and host-wake resources, marks wake capability, and adds the device to a global list. Protocol open requires flow control, allocates `intel_data`, powers the matched platform device with reset GPIO, and starts boot wait state. Setup waits for booting, reads Intel version, validates platform and supported variants, detects whether operational firmware is already running, otherwise reads boot params, selects an `.sfi` firmware name, downloads fragments using `btintel_download_firmware`, waits for firmware-complete vendor events, optionally restores init speed before reset, sends Intel reset, waits for operational boot event, enables LPM if platform wake is active, loads optional `.ddc` config, sends HCI reset, and finally switches to operational speed. RX uses `h4_recv_buf` with a custom LPM packet descriptor and an event callback that consumes bootloader vendor events before passing normal events up.

State and persistence behavior: Runtime state is encoded in `intel->flags`, TX/RX queues, reset GPIO level, IRQ registration, PM autosuspend, and the current baud rate. Firmware and DDC files are read from `/lib/firmware` but not modified. Controller firmware, BDADDR quirks, and LPM state persist only while the controller remains powered. The global `intel_device_list` links ACPI platform resources to tty-backed HCI UART instances by shared parent device.

Dependencies and integration points: This driver depends on HCI UART, H4 receive parsing, `btintel` helpers, ACPI platform devices, GPIO descriptors, threaded IRQs, runtime PM, tty baud/flow-control APIs, wait-on-bit synchronization, firmware loading, and HCI core callbacks. It registers protocol `HCI_UART_INTEL` and platform driver `hci_intel` for ACPI IDs `INT33E1` and `INT33E3`.

Risks and edge cases: Firmware sequencing is strict and asynchronous events clear wait bits; missed or malformed vendor events cause timeouts. `intel_set_baudrate` must read Intel version before issuing speed change because the controller rejects the command otherwise. The reset command during bootloader mode lacks a command-complete event, so `intel_dequeue` injects one to preserve HCI command flow control. LPM suspend refuses while TX is active and depends on LPM ACK packets plus host-wake IRQs. Global list matching by tty parent can fail on unusual device hierarchies. PM callbacks protect `hu` with `hu_lock`, but removal and IRQ wake paths remain concurrency-sensitive.

Test signals: Useful signals include ACPI GPIO mapping, reset power on/off, host-wake IRQ resume, booting timeout, Intel version variant validation, firmware-name selection for variants 0x0b/0x0c/0x12, boot-param limited-CCE rejection, firmware-complete success/failure event handling, Intel reset boot event handling, DDC load fallback, speed conversion table coverage, unsupported speed rejection, injected command complete for reset, LPM TX active notifications, suspend/resume ACK transactions, and RX parsing of LPM packet lengths.
