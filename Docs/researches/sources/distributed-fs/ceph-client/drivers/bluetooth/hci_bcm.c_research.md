# sources/distributed-fs/ceph-client/drivers/bluetooth/hci_bcm.c

Purpose: This file implements the Broadcom/Cypress/Infineon Bluetooth HCI UART protocol driver. It provides an H4-compatible transport with Broadcom vendor setup, platform and serdev probing, GPIO/clock/regulator power sequencing, ACPI and device-tree resource discovery, host-wake runtime PM, sleep-mode programming, diagnostic packet support, and Broadcom firmware/address handling through `btbcm`.

Important APIs, types, and functions: Core private state is split between `struct bcm_data` for live HCI UART queues and receive reassembly, and `struct bcm_device` for physical resources such as GPIOs, clocks, regulators, IRQ, baud rates, Apple ACPI methods, and PM state. Device quirks use `struct bcm_device_data`. The `bcm_proto` `hci_uart_proto` supplies `bcm_open`, `bcm_close`, `bcm_flush`, `bcm_setup`, `bcm_set_baudrate`, `bcm_recv`, `bcm_enqueue`, and `bcm_dequeue`. Platform and serdev entry points are `bcm_probe`, `bcm_remove`, `bcm_serdev_probe`, and `bcm_serdev_remove`; module integration is through `bcm_init` and `bcm_deinit`.

Control flow: Open requires UART flow-control support, allocates `bcm_data`, resolves the matching `bcm_device` from serdev drvdata or the global platform-device list, sets initial and operational speeds, optionally manipulates RTS for autobaud or board quirks, and powers the controller through `bcm_gpio_set_power`. Setup delegates firmware and patchram work to `btbcm_initialize`, switches host and controller baud rates when firmware loading completed, optionally writes PCM interface parameters, calls `btbcm_finalize`, enables BDADDR property fallback for invalid default addresses, requests the host-wake IRQ, and programs Broadcom sleep parameters. TX prepends the H4 packet type and queues to `txq`; RX uses `h4_recv_buf` with standard ACL/SCO/event/ISO plus Broadcom diagnostic/null/type49/type52 packets. Dequeue wraps runtime-PM get/put around queue removal.

State and persistence behavior: Persistent storage is not written by this file. Runtime state lives in GPIO values, regulator and clock enable state, `res_enabled`, `init_speed` and `oper_speed`, `irq_acquired`, runtime PM state, `is_suspended`, queued skbs, and the current partial RX skb. Firmware and BDADDR programming are controller state changes performed through vendor HCI commands. The global `bcm_device_list` bridges ACPI platform devices to tty line-discipline instances; serdev instances keep the device as drvdata and always pass `bcm_device_exists`.

Dependencies and integration points: The driver depends on the HCI UART core, `h4_recv_buf`, Broadcom helpers in `btbcm`, serdev, tty modem control, GPIO descriptors, regulators, clocks, ACPI resource parsing, Apple-specific ACPI methods, OF properties, DMI quirks for broken IRQ descriptions, runtime PM, and HCI core callbacks `set_diag` and `set_bdaddr`. Match tables cover many ACPI `BCM2E*` IDs and OF compatibles for Broadcom, Cypress, and Infineon controllers.

Risks and edge cases: The most sensitive paths are power sequencing rollback, baud-rate ordering, and concurrency with platform-device removal. `bcm_device_lock` protects the global list and PM operations, but tty-backed devices still depend on parent-device matching. Some ACPI tables describe wrong IRQ polarity or wrong GPIO order, so the driver carries DMI and module-parameter overrides. Autobaud devices require deliberate RTS/flow-control behavior and may cap init speed. The `no_uart_clock_set` and `max_speed` quirks avoid commands or speeds unsupported by specific chips. Runtime suspend disables flow control and toggles wake GPIOs, so incorrect host-wake IRQ configuration can break low-power recovery.

Test signals: Useful validation includes platform and serdev probe paths, ACPI GPIO order variants, Apple ACPI power methods, DMI broken IRQ systems, regulator/clock failure unwind, autobaud and early baud-rate quirk handling, `btbcm_initialize` and `btbcm_finalize` error paths, Broadcom diagnostic packet injection via `set_diag`, RX parsing of vendor diagnostic packet types, runtime autosuspend on RX/TX, host-wake IRQ resume, and system suspend/resume with wake-capable devices.
