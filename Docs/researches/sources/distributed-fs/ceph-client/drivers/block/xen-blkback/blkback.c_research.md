# sources/distributed-fs/ceph-client/drivers/block/xen-blkback/blkback.c

Purpose: This file is the Xen block backend I/O engine. It services requests from Xen blkfront guests through shared rings and grant references, translates guest block protocol operations into Linux bios or block helper calls against a backend `struct block_device`, manages persistent grant mappings and a grant-page cache, returns blkif responses, handles queue threads and interrupts, reports resize events through Xenstore, and initializes/finalizes the backend interface and Xenbus driver.

Important APIs, types, and functions: The exported or cross-file entry points are `xen_blkif_be_int()`, `xen_blkif_schedule()`, `xen_blkbk_free_caches()`, `xen_blkbk_unmap_purged_grants()`, module init `xen_blkif_init()`, and module exit `xen_blkif_fini()`. Major internal subsystems are persistent grant management (`add_persistent_gnt()`, `get_persistent_gnt()`, `put_persistent_gnt()`, `free_persistent_gnts()`, `purge_persistent_gnt()`), request pool management (`alloc_req()`, `free_req()`), VBD validation/resizing (`xen_vbd_translate()`, `xen_vbd_resize()`), request-ring processing (`do_block_io_op()`, `__do_block_io_op()`), grant mapping (`xen_blkbk_map()`, `xen_blkbk_unmap()`, `xen_blkbk_map_seg()`, `xen_blkbk_parse_indirect()`), dispatch (`dispatch_rw_block_io()`, `dispatch_discard_io()`, `dispatch_other_io()`), bio completion (`end_block_io_op()`, `__end_block_io_op()`), draining (`xen_blk_drain_io()`), and response publishing (`make_response()`).

Control flow: The Xen event-channel interrupt calls `xen_blkif_be_int()`, which marks the ring as having waiting requests and wakes the per-ring backend thread. `xen_blkif_schedule()` is that thread: it is freezable, watches for backend size changes, waits for ring work and free pending request slots, calls `do_block_io_op()`, sends late EOI when appropriate, periodically purges persistent grants, shrinks the free grant-page cache, and optionally prints statistics. `__do_block_io_op()` snapshots `req_prod`, validates producer/consumer overflow, allocates a `pending_req`, copies a protocol-specific request into native `struct blkif_request`, advances `req_cons` before responding, and dispatches read/write/flush/barrier/indirect/discard/unsupported operations.

Request dispatch behavior: `dispatch_rw_block_io()` normalizes indirect operations, validates segment counts and segment sector ranges, fills `pending_req`, accumulates sector counts, maps indirect descriptor frames if needed, validates VBD read-only/range access through `xen_vbd_translate()`, checks logical-block alignment, optionally drains in-flight I/O for barriers, maps guest grants, allocates one or more bios as `bio_add_page()` capacity requires, submits them under a blk plug, and updates stats. Flush requests produce a zero-segment PREFLUSH bio. `dispatch_discard_io()` validates write access and issues either `blkdev_issue_discard()` or `blkdev_issue_secure_erase()`. Unsupported operations immediately return `BLKIF_RSP_EOPNOTSUPP`.

Grant mapping and persistence behavior: Guest data pages are represented by `struct grant_page` entries in each `pending_req`. `xen_blkbk_map()` first tries to reuse inactive persistent grants from an rb-tree keyed by grant ref when negotiated. Otherwise it obtains backend pages from `gnttab_page_cache`, maps grant refs with `gnttab_map_refs()`, and optionally promotes new mappings into `struct persistent_gnt` while under `max_pgrants`. Non-persistent mappings are unmapped after I/O completion. Persistent grants are marked active/inactive with `last_used` timestamps and retained across requests until LRU/timeout purge or backend teardown. Purge removes inactive grants from the rb-tree, queues them on `persistent_purge_list`, and a work item unmaps them outside the scheduler loop.

Completion and response behavior: Each submitted bio points back to the `pending_req`; `end_block_io_op()` calls `__end_block_io_op()` and drops the bio. Errors set the whole blkif request status, with unsupported flush/barrier also updating Xenstore-advertised feature state through `xen_blkbk_flush_diskcache()` or `xen_blkbk_barrier()`. When the pending bio count reaches zero, `xen_blkbk_unmap_and_respond()` prepares async grant unmaps, and `xen_blkbk_unmap_and_respond_callback()` returns pages to the cache, calls `make_response()`, releases the pending request slot, completes drain waiters if in-flight drops to zero, and drops the blkif reference. `make_response()` writes the protocol-appropriate response ring entry under `blk_ring_lock`, advances `rsp_prod_pvt`, pushes responses, and notifies the frontend IRQ if needed.

State and persistence behavior: Runtime state is mostly per-ring: event irq, shared ring pointers, pending request free list, in-flight count, request wait flags, per-ring kthread, persistent grant rb-tree, free page cache, purge work, shutdown wait queue, and statistics counters. Per-device state in `struct xen_blkif` includes domid, VBD metadata, protocol, rings, reference count, drain state, and buffer-cache squeeze timing. Persistent external effects include Xenstore updates for resize and feature fallback, backend module parameters (`max_buffer_pages`, `max_persistent_grants`, `persistent_grant_unused_seconds`, `max_queues`, `max_ring_page_order`, `log_stats`), and I/O submitted to the underlying block device. No filesystem data is stored by the driver except through the actual block writes it services.

Dependencies and integration points: The file depends on Xen event channels, Xen grant table mapping/unmapping and page cache helpers, Xenbus helpers declared in `common.h`, blkif ring macros and protocol structures, Linux kthreads/freezer/wait queues/workqueues, block-device helpers (`bio_alloc`, `bio_add_page`, `submit_bio`, `blkdev_issue_discard`, `blkdev_issue_secure_erase`), backend file-to-bdev access, and module initialization. It pairs with `xenbus.c` for interface allocation, backend discovery, ring setup, feature negotiation, and VBD opening.

Risks and edge cases: Safety hinges on validating untrusted frontend ring indices, operation codes, segment counts, indirect descriptor bounds, sector ranges, and logical-block alignment before touching grants or submitting bios. Grant lifetime is complex: persistent grants can be reused, purged asynchronously, or returned from interrupt-context completion, so active flags and in-use counters must stay consistent. `BUG_ON()` is used for grant unmap failures and several impossible states, making hypervisor/grant-table errors fatal. The request loop can run without a finite frontend bound, so it uses `cond_resched()` and stops when pending slots are exhausted. Barrier/drain handling depends on in-flight accounting and can delay queue progress. Incorrect read-only mapping flags or VBD translation would expose host data or allow writes outside the backend device.

Test signals: Valuable tests include frontend ring overflow/bogus producer handling, native/x86_32/x86_64 protocol request translation, reads and writes split over multiple bios, zero-segment flush, write barrier drain, discard and secure erase fallback, read-only and out-of-range access rejection, misaligned sector rejection, indirect descriptor mapping and invalid descriptor rejection, persistent grant reuse/purge/timeout/max overflow, grant map/unmap failures, backend resize Xenstore update, queue starvation when no `pending_req` is free, suspend/freezer behavior for the scheduler thread, late EOI behavior, module parameter bounds, and clean teardown with all grants and page cache entries freed.
