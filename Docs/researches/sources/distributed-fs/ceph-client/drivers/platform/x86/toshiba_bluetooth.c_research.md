# sources/distributed-fs/ceph-client/drivers/platform/x86/toshiba_bluetooth.c

Purpose: Provides Toshiba ACPI Bluetooth power/rfkill support for ACPI device `TOS6205`. It verifies that the Bluetooth device is physically present, exposes an rfkill device, controls attach/detach and power through ACPI methods, and keeps rfkill hardware state synchronized with Toshiba's Bluetooth killswitch status.

Important APIs and types: `struct toshiba_bluetooth_dev` stores the ACPI companion, rfkill handle, and cached killswitch/plugged/powered bits. Firmware methods are `_STA` for presence, `BTST` for status, `AUSB`/`DUSB` for USB attach/detach, and `BTPO`/`BTPF` for power on/off. Core functions include `toshiba_bluetooth_present`, `toshiba_bluetooth_status`, `toshiba_bluetooth_enable`, `toshiba_bluetooth_disable`, `toshiba_bluetooth_sync_status`, `bt_rfkill_set_block`, `bt_rfkill_poll`, `toshiba_bt_rfkill_notify`, and `toshiba_bt_rfkill_probe/remove`.

Control flow: Probe gets the ACPI companion, calls `_STA` to reject fake firmware devices, allocates state, reads `BTST`, allocates and registers rfkill device "Toshiba Bluetooth", sets initial hardware-block state based on the killswitch bit, and installs an ACPI notify handler. rfkill set-block first refreshes status and ignores software requests when the hardware killswitch is off; otherwise it calls disable or enable ACPI sequences. Poll and notify refresh `BTST` and update hardware-block state. Resume refreshes status and rfkill state. Remove unregisters the notify handler, unregisters/destroys rfkill, frees state, and disables Bluetooth through firmware.

State and persistence: Cached booleans mirror the latest `BTST` bitfield: bit `0x01` killswitch, `0x40` plugged, and `0x80` powered. Actual Bluetooth USB attachment and power state live in firmware/hardware. Removing the driver explicitly powers off and detaches the device. rfkill maintains user-visible block state while the driver synchronizes hardware-block state on notifications and polls.

Dependencies and integration points: Depends on ACPI platform matching, rfkill core, platform-device PM, and Toshiba firmware methods. User-visible integration is the `RFKILL_TYPE_BLUETOOTH` rfkill device named "Toshiba Bluetooth". It complements the broader `toshiba_acpi.c` WWAN support rather than sharing state.

Risks: Some firmware exposes fake `TOS6205` devices, so `_STA` checking is mandatory. The hardware switch only reliably notifies on one transition, which is why polling is implemented; removing that would leave stale rfkill state. Enable and disable are two-step sequences, so partial failure can leave USB attached but unpowered or powered but detached. Remove always disables Bluetooth, which may surprise users expecting hardware state to persist across module unload.

Test signals: Probe on real and fake `TOS6205` firmware; rfkill device appears only when `_STA` reports present; rfkill block/unblock calls execute `BTPF/DUSB` and `AUSB/BTPO`; hardware switch transitions update `rfkill_set_hw_state` via notify and polling; resume refreshes state; module unload removes rfkill and powers/detaches the device without use-after-free in notify paths.
