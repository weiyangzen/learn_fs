# sources/distributed-fs/ceph-client/drivers/accel/habanalabs/include/gaudi/asic_reg/sif_rtr_ctrl_3_regs.h

## Purpose
`sif_rtr_ctrl_3_regs.h` is the autogenerated register-address map for SIF router controller instance 3. It exposes 438 `mmSIF_RTR_CTRL_3_*` offsets from `0x336108` through `0x336CBC`. The header names the instance-3 registers for security/privilege windows, scrambler enables, E2E HBM/PCI tuning and counters, nonlinear SRAM/HBM routing, RGL controls, and rate-limit state.

## Important APIs, types, and functions
- Public macros use the `mmSIF_RTR_CTRL_3_` prefix.
- Security and privilege macros define AW/AR hit, base-low/high, and mask-low/high registers for 16 indexed ranges.
- Driver initialization macros include SRAM/HBM scrambler enables and E2E HBM/PCI size/enables.
- Monitoring/tuning macros include AW/AR counters for HBM channels and PCI, counter wrap/set controls, RGL token/latency/bank/watchdog registers, and HBM/PCI/SRAM rate-limit controls.
- Nonlinear routing macros define enable, SRAM/HBM offsets, bank selection, HBM selection, and PC selection.

## Control flow
The header has no direct control flow. It is consumed by Gaudi initialization and security paths. `gaudi_init_scrambler_sram()` and `gaudi_init_scrambler_hbm()` write SIF3 scrambler enable registers when driver-owned. `gaudi_init_e2e()` programs SIF3 HBM/PCI read/write sizes and then enables E2E. `gaudi_security.c` uses the SIF3 range symbols in table-driven range programming for secure and privileged access control.

## State and persistence
No software state is defined here. SIF3 hardware registers retain access-control, routing, E2E, rate-limit, scrambler, and counter state until reset or reconfiguration. Some status and hit bits may be sticky or latched depending on hardware semantics not represented by the header.

## Dependencies and integration points
The file integrates with `gaudi.c`, `gaudi_security.c`, shared IF router mask definitions, and generated block definitions. `gaudi_blocks.h` lists `mmSIF_RTR_CTRL_3_BASE` as `0x7FFC336000ull`. Its address layout is one member of the SIF router symmetry used by driver constants and table-driven programming.

## Risks and edge cases
- Instance-specific addresses differ by base offset only; generator or manual include mistakes can target sibling routers.
- Access-window programming is security-sensitive and split over many similarly named registers.
- E2E tuning values are instance-specific, so tests should not assume all SIF routers use identical programmed sizes.
- Nonlinear routing fields can cause valid traffic to land in wrong SRAM/HBM banks if misprogrammed.
- The header provides no metadata for reset values, sticky bits, or write side effects.

## Test signals
Positive signals include successful SIF3 traffic, expected scrambler/E2E initialization, no SIF3-specific range hit errors, and reasonable AW/AR counters under load. Negative signals include protected-range violations on valid traffic, SIF3-only throughput or data errors, unexpected counter saturation/wrap, or reset paths that fail after programming SIF3-related ranges.
