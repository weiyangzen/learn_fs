# sources/distributed-fs/ceph-client/sound/pci/nm256/nm256.c

## Purpose

`nm256.c` is the ALSA PCI driver for NeoMagic 256AV, 256ZX, and 256XL+ audio functions. It binds matching PCI audio devices, maps the chipset control BAR and a slice of shared video RAM used as the audio ring/coefficient buffer, exposes one playback and one capture PCM device, and creates an AC97 mixer facade. The implementation is strongly hardware-specific: most operations are MMIO register writes, interrupt acknowledgment, and AC97 register caching designed around older laptop quirks.

The module is built as `snd-nm256` through the adjacent `Makefile` under `CONFIG_SND_NM256`. It includes `nm256_coef.c` directly for fixed playback/record coefficient tables and their per-rate sizes.

## Important APIs, Types, And Data

- Module parameters: `index`, `id`, `playback_bufsize`, `capture_bufsize`, `force_ac97`, `buffer_top`, `use_cache`, `vaio_hack`, `reset_workaround`, `reset_workaround_2`, and legacy `enable`. These influence ALSA card identity, ring-buffer sizing, AC97 detection/reset behavior, coefficient-buffer layout, and a Sony VAIO video-RAM conflict workaround.
- `struct nm256_stream`: per-direction runtime state. It tracks the ALSA substream, running/suspended flags, MMIO buffer offsets and mapped pointers, DMA/period sizing, sample-format shift, and the next watermark period.
- `struct nm256`: card-level state. It owns the ALSA card, PCI device, mapped control port, mapped buffer window, buffer offset accounting, coefficient cache pointers, mixer status configuration, IRQ state/refcount, playback/capture streams, AC97 instance/cache, PCM handle, and register spinlock.
- PCI binding: `snd_nm256_ids` matches `PCI_DEVICE_ID_NEOMAGIC_NM256AV_AUDIO`, `PCI_DEVICE_ID_NEOMAGIC_NM256ZX_AUDIO`, and `PCI_DEVICE_ID_NEOMAGIC_NM256XL_PLUS_AUDIO`.
- Register helpers: `snd_nm256_readb/readw/readl` and `snd_nm256_writeb/writew/writel` wrap MMIO access to `chip->cport`. `snd_nm256_write_buffer` copies coefficient data into the mapped video-RAM buffer window.
- PCM ops: playback and capture implement `.open`, `.close`, `.hw_params`, `.prepare`, `.trigger`, `.pointer`, `.mmap`; non-i386 also supplies explicit I/O-memory `.copy` and playback `.fill_silence`.
- AC97 ops: `snd_nm256_ac97_reset`, `snd_nm256_ac97_write`, and `snd_nm256_ac97_read` are registered through `snd_ac97_bus`; reads are served from `chip->ac97_regs` to avoid direct mixer reads that may crash some devices.
- PM ops: `nm256_suspend` and `nm256_resume` are exposed through `DEFINE_SIMPLE_DEV_PM_OPS`.

## Control Flow

Probe starts in `snd_nm256_probe`. It applies `nm256_quirks`, creates a devm-managed ALSA card, selects the card driver string from the PCI device ID, clamps playback/capture buffer sizes to 4-128 KiB, optionally adjusts `buffer_top` for `vaio_hack`, and calls `snd_nm256_create`.

`snd_nm256_create` enables the PCI device, initializes locks and stream buffer sizes, records BAR 0 as the audio buffer/video-RAM aperture and BAR 1 as the control port, requests regions, and maps the 4 KiB control port. For NM256AV it checks AC97 presence unless `force_ac97` is set, chooses the 16-bit AV interrupt handler, and assumes 2.5 MiB video RAM. For ZX/XL+ it probes a register to choose 4 MiB or 6 MiB, installs the 32-bit interrupt handler, and uses ZX mixer-ready bits. It then computes the required tail-of-video-RAM allocation for playback buffer, capture buffer, and coefficient storage. The top of that allocation is either module-provided `buffer_top` or the BIOS signature-derived pointer found by `snd_nm256_peek_for_sig`; the chosen window is mapped and split into playback, capture, and coefficient areas. Finally it initializes chip registers with `snd_nm256_init_chip`.

After creation, probe copies reset workaround flags into the chip, creates the PCM device with `snd_nm256_pcm`, creates the AC97 mixer with `snd_nm256_mixer`, fills ALSA card names, registers the card, installs `snd_nm256_free` as the private cleanup hook, and stores driver data on the PCI device.

PCM open lazily acquires the shared IRQ via `snd_nm256_acquire_irq`, sets the runtime hardware template and buffer pointers through `snd_nm256_setup_stream`, and adds a constraint list limiting rates to eight exact values. `hw_params` records the selected DMA byte count. `prepare` derives DMA size, period size, period count, resets `cur_period`, stops local running state, and programs sample format/rate and coefficients under `reg_lock`.

Starting a stream is done through trigger callbacks. Playback programs start/end/current/watermark registers, enables freerun playback, and unmutes both channels. Capture programs the equivalent record registers and enables freerun capture. Stop mutes/disables playback or disables capture. Pointers read the hardware current-pointer register, subtract the stream buffer offset, wrap by DMA size, and convert to frames.

Interrupt handling differs by chip generation only in status width and bit definitions. `snd_nm256_interrupt` reads the 16-bit AV interrupt register; `snd_nm256_interrupt_zx` reads the 32-bit ZX version. Both acknowledge playback and capture interrupts, call `snd_pcm_period_elapsed` outside the spinlock through update helpers, then advance the hardware watermark. Misc interrupts toggle register `0x400` bit 1. Unknown status bits are acknowledged defensively. If the shared IRQ fires repeatedly with zero status, `snd_nm256_intr_check` counts bogus interrupts and eventually stops active engines.

## Coefficients And Format Handling

The fixed rates are 8000, 11025, 16000, 22050, 24000, 32000, 44100, and 48000 Hz. `snd_nm256_fixed_rate` maps the ALSA runtime rate to an index enforced by `constraints_rates`. `snd_nm256_set_format` derives register bits for rate, 16-bit samples, and stereo channels, updates `s->shift` for byte-to-sample-size adjustments, loads the matching coefficient set, and writes the playback or capture rate register.

`nm256_coef.c` provides `NM_TOTAL_COEFF_COUNT`, `coefficients`, and `coefficient_sizes[16]`; indices 0-7 are playback and 8-15 are capture. Without `use_cache`, each prepare copies one coefficient block into the stream-specific coefficient buffer and programs start/end registers. With `use_cache`, the whole coefficient table is copied once into `all_coeff_buf`; subsequent loads program offsets into that cached table. `coeffs_current` is cleared on suspend so resume/prepare can repopulate the coefficient cache.

## State And Persistence Behavior

The driver has no durable filesystem persistence. State is in kernel memory and hardware registers:

- Stream state persists across PCM callbacks in `chip->streams[]`, including buffer offsets, period accounting, `running`, and `suspended`.
- IRQ ownership is refcounted by `chip->irq_acks`; the IRQ is requested on first PCM open and released after the last close.
- AC97 mixer values persist in `chip->ac97_regs`; reads return cached values only for the known initial-value register set.
- The audio ring buffers and coefficient storage live in a remapped tail segment of video RAM. The selected tail address may come from an NM BIOS signature, from `buffer_top`, or from static per-chip assumptions.
- Suspend moves the ALSA card to D3hot, suspends AC97, and invalidates cached coefficients. Resume resets hardware, resumes AC97, restores format/coefficients for substreams marked suspended, and returns to D0.

## Dependencies And Integration Points

- Linux PCI core: probe through `struct pci_driver`, `pcim_enable_device`, `pcim_request_all_regions`, BAR discovery, and driver data storage.
- Linux MMIO APIs: `devm_ioremap`, `ioremap`, `iounmap`, `read*`, `write*`, `memcpy_toio`, `memset_io`, and iterator-to/from-I/O helpers.
- ALSA core: card allocation/registration, PCM creation, PCM runtime constraints, PCM mmap over I/O memory, period elapsed notifications, power state transitions, and AC97 bus/mixer registration.
- Kernel interrupt and locking APIs: shared `request_irq`/`free_irq`, `spinlock_t reg_lock`, `mutex irq_mutex`, scoped `guard()` lock helpers, and IRQ-safe locking in prepare/resume format restoration.
- Hardware-specific AC97 integration: the mixer is treated as mostly write-only, with reset workarounds for known laptops and a quirk denylist for hardware that should use another driver family.

## Risks And Edge Cases

- The driver relies on MMIO offsets and video-RAM layout assumptions; an incorrect `buffer_end`, invalid BIOS signature pointer, or conflicting video use can corrupt display memory or audio buffers. `vaio_hack` and `buffer_top` exist because this historically conflicted with X servers on some machines.
- AC97 direct reads are avoided because some NM256 systems can crash on mixer reads. Any change that expands readable registers or bypasses the cache is high risk.
- Reset sequences can lock up known laptops. `reset_workaround` and `reset_workaround_2` intentionally skip parts of the magic reset sequence for specific Dell/Sony systems.
- `snd_nm256_load_coefficient` refuses to load coefficients while the engine enable bit is set. Prepare/format changes must not race with active hardware.
- Period updates intentionally drop `reg_lock` around `snd_pcm_period_elapsed`; watermark advancement must remain consistent with `cur_period` and hardware interrupt timing.
- Non-i386 needs explicit copy/silence paths for I/O memory; i386 relies on the mapped I/O pointer being directly usable by ALSA mmap paths.
- Shared IRQ noise is handled by a heuristic bogus-interrupt counter; false positives can stop active playback/capture, while insufficient filtering may leave interrupt storms.
- The AC97 cache only covers registers listed in `nm256_ac97_init_val`; writes to other registers are ignored and reads return zero.

## Test Signals

- PCI probe should identify AV/ZX/XL+ devices, create one ALSA card, one PCM with playback and capture streams, and an AC97 mixer without leaking mappings or IRQs.
- Module-parameter coverage should include minimum/maximum buffer size clamping, `buffer_top`, `use_cache`, `force_ac97`, `vaio_hack`, and both reset workarounds.
- PCM smoke tests should open playback/capture independently and together, verify IRQ refcount acquisition/release, prepare each supported rate/format/channel combination, start/stop/resume/suspend triggers, and observe advancing pointers plus period elapsed callbacks.
- Mixer tests should verify cached AC97 reads reflect successful writes for known registers and that unknown registers do not cause direct hardware reads.
- Suspend/resume tests should confirm AC97 resume, coefficient cache invalidation/reload, format restoration for suspended substreams, and card power-state transitions.
- Hardware-specific regression signals include absence of lockups on quirked Dell/Sony machines, no bogus AC97 absence rejection when `force_ac97=1`, and no video-RAM/audio-buffer overlap when BIOS signatures or `buffer_top` are used.
