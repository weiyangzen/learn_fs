# sources/distributed-fs/ceph-client/net/sched/cls_bpf.c

Purpose: implements the `bpf` TC classifier, allowing classic socket-filter bytecode or eBPF `BPF_PROG_TYPE_SCHED_CLS` programs to classify packets and optionally return direct TC action verdicts. It also supports TC hardware offload callbacks for BPF classifier programs.

Important APIs/types/functions: `struct cls_bpf_head` owns the program list and handle IDR. `struct cls_bpf_prog` stores the `bpf_prog`, old classic-BPF ops copy, optional eBPF name, handle, class result, action extensions, direct-action flag (`exts_integrated`), generic flags (`skip_sw`, `skip_hw`, in-hardware reporting), hardware count, and deferred work. Core functions are `cls_bpf_classify`, `cls_bpf_change`, `cls_bpf_delete`, `cls_bpf_destroy`, `cls_bpf_get`, `cls_bpf_dump`, `cls_bpf_walk`, `cls_bpf_reoffload`, `cls_bpf_prog_from_ops`, `cls_bpf_prog_from_efd`, `cls_bpf_offload`, `cls_bpf_offload_cmd`, and `cls_bpf_offload_update_stats`. Netlink policy covers classid, classic BPF ops, eBPF fd/name, direct-action flags, and generic skip flags.

Control flow: `cls_bpf_change` parses options, allocates a handle, validates actions, enforces exactly one of classic-BPF bytecode or eBPF fd, validates direct-action and skip flags, builds the program with `bpf_prog_create` or `bpf_prog_get_type_dev`, binds an optional classid, attempts hardware offload, marks `NOT_IN_HW` if needed, updates software-use accounting, and inserts or RCU-replaces the program. `cls_bpf_classify` walks programs in list order. For skip-sw programs it avoids running the BPF program; for ingress packets it temporarily pushes the MAC header before running so BPF sees expected data pointers. In direct-action mode, the BPF return is sanitized by `cls_bpf_exec_opcode` and used as a TC action verdict, while the classid comes from `qdisc_skb_cb(skb)->tc_classid` combined with the major class. In non-direct-action mode, return `0` means no match, return `-1` means use the configured `prog->res`, and any other nonzero value becomes the classid before actions execute.

State and persistence behavior: program state is runtime-only under `tp->root`. Classic programs own a copied `sock_filter` array and a `bpf_prog` destroyed with `bpf_prog_destroy`; eBPF programs hold a fd-acquired ref released by `bpf_prog_put` and may own a duplicated name. Handles live in an IDR. Program replacement uses `list_replace_rcu`; old programs are freed through `cls_bpf_delete_prog_work` after extension net refs and RCU work. Offload state is tracked by `gen_flags` and `in_hw_count`, with stats refreshed before dump.

Dependencies/integration points: integrates with BPF core (`bpf_prog_run_data_pointers`, `bpf_prog_get_type_dev`, `BPF_PROG_TYPE_SCHED_CLS`), TC core action extension helpers, class binding, qdisc ingress helpers, hardware offload callbacks using `TC_SETUP_CLSBPF`, and `tcf_block_netif_keep_dst` when a BPF program needs destination metadata. Module registration exposes kind `bpf`.

Risks: direct-action and non-direct-action modes have different return semantics; confusing them can silently turn BPF return values into classids or TC verdicts. `skip_sw` requires successful hardware presence, and offload failure attempts rollback by calling the opposite offload command; rollback gaps would leave driver state inconsistent. Ingress MAC push/pull must remain balanced around BPF execution. Replacement deliberately unbinds the old class result and queues old program destruction; premature free would race classification. Dumping classic bytecode copies the saved user instructions, while eBPF dumps id/tag/name only, so tooling must handle both representations.

Test signals: load classic-BPF and eBPF classifiers; verify invalid combinations of fd and ops are rejected. Test direct-action returns for `OK`, `SHOT`, `STOLEN`, `TRAP`, `REDIRECT`, `UNSPEC`, and unsupported return values. Test non-direct-action return `0`, `-1`, and explicit classid values. Exercise `skip_sw`, `skip_hw`, hardware offload add/replace/destroy/reoffload, stats update on dump, ingress execution, class binding, replacement by handle, and deletion cleanup under traffic.
