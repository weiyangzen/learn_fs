# sources/distributed-fs/ceph-client/net/bluetooth/hci_sock.c

## Purpose
`hci_sock.c` implements the Linux Bluetooth HCI socket layer. It exposes `PF_BLUETOOTH` raw HCI sockets for user-space tools, user-channel sockets for exclusive controller ownership, monitor sockets for packet/control tracing, logging sockets for user log injection into monitor streams, and management/control channels for BlueZ management commands. It is the boundary between user space and HCI core device queues, management handlers, monitor consumers, and controller device events.

## Important APIs, Types, and Functions
The main per-socket private type is `struct hci_pinfo`, accessed through `hci_pi(sk)`. It stores the Bluetooth socket base, bound `struct hci_dev *hdev`, an HCI packet filter, control-message mask, HCI channel, flags, monitor cookie, opener command name, and per-socket MTU. Exported helpers include `hci_sock_set_flag()`, `hci_sock_clear_flag()`, `hci_sock_test_flag()`, `hci_sock_get_channel()`, and `hci_sock_get_cookie()`.

Global state includes `hci_sk_list` for all HCI sockets, `mgmt_chan_list` plus `mgmt_chan_list_lock` for dynamically registered management channels, `sock_cookie_ida` for monitor-control socket cookies, and `monitor_promisc` for quickly suppressing monitor work when no monitor socket is active. The security filter is `struct hci_sec_filter hci_sec_filter`, which restricts packet types, events, and command opcodes for callers lacking `CAP_NET_RAW`.

Socket operations are implemented by `hci_sock_ops`: `hci_sock_release()`, `hci_sock_bind()`, `hci_sock_getname()`, `hci_sock_sendmsg()`, `hci_sock_recvmsg()`, `hci_sock_ioctl()`, optional `hci_sock_compat_ioctl()`, `hci_sock_setsockopt()`, and `hci_sock_getsockopt()`. Registration is through `hci_sock_init()` and cleanup through `hci_sock_cleanup()`, using `proto_register()`, `bt_sock_register(BTPROTO_HCI, ...)`, and procfs integration.

Transmit and fanout helpers include `hci_send_to_sock()` for raw/user socket receive fanout, `hci_send_to_channel()` and `__hci_send_to_channel()` for flag-filtered channel fanout, `hci_send_to_monitor()` for monitor packet wrapping, `hci_send_monitor_ctrl_event()` for control-channel monitor events, and `hci_sock_dev_event()` for controller lifecycle notifications.

Monitor helpers build replay and control records: `create_monitor_event()`, `create_monitor_ctrl_open()`, `create_monitor_ctrl_close()`, `create_monitor_ctrl_command()`, `send_monitor_note()`, `send_monitor_replay()`, and `send_monitor_control_replay()`. Management channel APIs are `hci_mgmt_chan_register()` and `hci_mgmt_chan_unregister()`, with command dispatch in `hci_mgmt_cmd()`.

## Control Flow
Socket creation starts in `hci_sock_create()`, which requires `SOCK_RAW`, assigns `hci_sock_ops`, allocates a Bluetooth socket with `hci_sk_proto`, installs `hci_sock_destruct()`, and links it into `hci_sk_list`. Binding determines the channel semantics. Raw sockets may bind to a specific HCI device or `HCI_DEV_NONE`, gain a monitor cookie, may become trusted with `CAP_NET_ADMIN`, and increment device promiscuous count when bound to a device. User-channel sockets require `CAP_NET_ADMIN`, a real device, no conflicting initialization/setup/config/running state, set `HCI_USER_CHANNEL`, remove the index from management, open the device, mark the socket trusted, and take exclusive device ownership. Monitor sockets require `CAP_NET_RAW`, are trusted, receive version notes plus replay of existing controller and control-socket state, and increment `monitor_promisc`. Logging sockets require `CAP_NET_ADMIN`. Management/control sockets validate a registered management channel, set trust according to `CAP_NET_ADMIN`, and for the control channel enable default management event flags.

Release reverses binding effects. Monitor sockets decrement `monitor_promisc`. Raw, user, and control sockets emit monitor control-close events and free cookies. The socket is unlinked. User-channel release closes the controller directly, clears `HCI_USER_CHANNEL`, and re-adds the management index if the device is still registered. Device promiscuous references and `hci_dev` references are dropped before orphaning and putting the socket.

Receive fanout from the kernel to sockets uses `hci_send_to_sock()` for raw and user channels bound to the same device. Raw sockets receive command, event, ACL, SCO, and ISO packets after `is_filtered_packet()` applies the per-socket HCI filter. User sockets receive only incoming event, ACL, SCO, ISO, and driver packets. The function clones once with headroom for the type byte and then clones per recipient. Channel fanout through `hci_send_to_channel()` clones packets for sockets bound to the requested channel and carrying a required flag, usually `HCI_SOCK_TRUSTED`.

Monitor packet flow wraps HCI traffic in `struct hci_mon_hdr`, maps HCI packet types and direction into monitor opcodes, copies peer credentials into skb control data, timestamps control records, and sends only to trusted monitor sockets. When a monitor socket binds, replay functions synthesize current controller index/open/setup/up state and currently open control/raw/user sockets so monitors get a coherent starting view.

`hci_sock_sendmsg()` validates flags and MTU, copies user data into an skb, then dispatches by channel. Management channels call `hci_mgmt_cmd()`. Logging validates the monitor-log frame format and forwards it to monitor sockets. Monitor sockets cannot send. Raw/user channels require a bound, registered, up device. User-channel packets are type-checked and queued directly to `hdev->raw_q`/`tx_work`. Raw command packets are checked against the security filter unless the caller has `CAP_NET_RAW`; vendor commands go to `raw_q`, while ordinary commands are marked `HCI_REQ_START`, queued to `hdev->cmd_q`, and schedule `cmd_work`. Raw ACL/SCO/ISO data requires `CAP_NET_RAW` and goes to `raw_q`.

`hci_mgmt_cmd()` parses the management header, validates payload length, emits a monitor control-command record for the default control channel, checks opcode existence, checks trusted versus untrusted handler flags, resolves and validates optional `hdev`, enforces unconfigured and user-channel restrictions, validates fixed or variable command length, runs optional channel device initialization, then invokes the registered management handler.

Ioctl flow is split between global raw HCI ioctls and bound-device ioctls. `hci_sock_ioctl()` first validates recognized commands, requires the socket channel to be raw, lazily creates a monitor cookie/open event for unbound raw ioctl activity, then handles global device list/info/open/close/reset/stat/scan/auth/encrypt/link options and inquiry. Remaining bound ioctls go through `hci_sock_bound_ioctl()`, which rejects dead/unregistered devices, user-channel busy devices, and unconfigured devices, then handles connection/auth info and reject-list add/delete.

## State and Persistence Behavior
The socket layer keeps runtime-only state. Socket state lives in `struct hci_pinfo`: channel, bound device reference, filter, control-message options, flags, MTU, monitor cookie, and opener command name. Cookies are allocated from an IDA and freed on release; they are stable only for socket lifetime. `monitor_promisc` gates monitor packet generation and is incremented/decremented by monitor bind/release.

Device-related runtime state includes `hdev->promisc` reference counts for raw/user bindings, `HCI_USER_CHANNEL`, management index visible/removed state, reject-list entries modified by `HCIBLOCKADDR`/`HCIUNBLOCKADDR`, and queued skbs in `hdev->cmd_q` or `hdev->raw_q`. No durable storage is written here. Persistent policy, keys, or settings are handled by management/HCI core layers outside this file.

Socket receive queues carry cloned skbs with optional SCM credentials stored in `bt_cb(skb)->creds`. Raw sockets can request ancillary data for direction and timestamps through legacy `SOL_HCI` options. User, monitor, and management-like channels use normal socket receive timestamping.

## Dependencies and Integration Points
The file depends on Bluetooth core headers, HCI core device lists and command queues, HCI monitor format definitions, management APIs, socket helpers from the Bluetooth core, Linux capabilities, IDA allocation, user-copy helpers, unaligned access, compat ioctl support, UTS version data, skb allocation/cloning, procfs, and workqueues.

It integrates with HCI core TX by queueing skbs to `hdev->cmd_q` or `hdev->raw_q` and scheduling `cmd_work` or `tx_work`. It integrates with management through `hci_mgmt_chan_register()`, `hci_mgmt_cmd()`, default management event flags, index-added/index-removed notifications during user-channel ownership, and management helper calls for ioctl information. It integrates with monitor tooling by producing HCI monitor packet streams, system notes, controller lifecycle events, control open/close/command events, and user logging records. It integrates with device lifecycle through `hci_sock_dev_event()`, which notifies sockets and wakes sockets bound to unregistered devices with `EPIPE`.

## Risks and Edge Cases
The user-space boundary makes validation and privilege checks the dominant risks. Raw command sending relies on `hci_sec_filter` for unprivileged callers and `CAP_NET_RAW` for unrestricted commands and data packets. Binding channels use `CAP_NET_ADMIN` or `CAP_NET_RAW` depending on channel. `hci_sock_gen_cookie()` marks sockets trusted only after checking opener credentials with `sk_capable()` for ioctl-triggered lazy opens, which avoids trusting a socket just because a privileged process later inherited or used it.

State transitions are delicate for sockets that first issue an ioctl unbound and later bind to raw, user, or control channels. The code emits monitor close then open records to model that transition cleanly. Rebinding away from an unregistered device is allowed so applications can recover from `HCI_DEV_UNREG` without closing the socket.

User-channel ownership can disrupt normal management visibility. The bind path removes the management index, opens the device under exclusive access, and release must close the device directly, clear the user-channel flag, and re-add the index. Failures after partially setting device state need careful cleanup to avoid leaving a controller hidden or busy.

Packet and monitor fanout run under socket-list read locks and allocate with `GFP_ATOMIC`; allocation failure drops individual copies without failing the source path. Monitor control events are nested with channel fanout while holding `hci_sk_list.lock`, so future changes must avoid lock inversions with socket locks or management locks.

Input-length risks include `hci_sock_sendmsg()` minimum length and MTU checks, management header length equality, logging-frame NUL termination and ident bounds, legacy filter option copying with old `hci_ufilter` layout, and getsockopt/setsockopt user-copy lengths. Socket receive handles truncation with `MSG_TRUNC`, but callers depend on type bytes and monitor headers being preserved exactly.

## Test Signals
Socket tests should cover create rejection for non-raw socket types, binding each channel with and without the required capability, binding to nonexistent or unregistering devices, raw rebind after unregistration, user-channel exclusive access conflicts, monitor replay contents, monitor open/close transition records, and correct `monitor_promisc` accounting.

Send-path tests should cover raw command security filter allow/deny behavior, vendor command raw queueing, ordinary command queueing with `HCI_REQ_START`, ACL/SCO/ISO permission checks, user-channel packet type filtering, logging frame validation, management command length/trust/index validation, MTU enforcement, and unsupported flags. Receive-path tests should cover raw HCI filtering by type/event/opcode, type-byte prepending, direction and timestamp cmsgs, SCM credential propagation, monitor packet headers, and `MSG_TRUNC` behavior.

Lifecycle and error tests should assert that user-channel release closes and restores management visibility, device-unregister events wake bound sockets with `EPIPE`, reject-list ioctls mutate `hdev->reject_list` under device lock, cookie IDs are freed on release, `BT_SNDMTU` and `BT_RCVMTU` are rejected on HCI traffic channels but accepted for management-like channels, and cleanup unregisters procfs, Bluetooth protocol family, and proto objects in reverse initialization order.
