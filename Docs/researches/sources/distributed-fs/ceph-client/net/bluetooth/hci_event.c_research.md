# sources/distributed-fs/ceph-client/net/bluetooth/hci_event.c

## Purpose
`hci_event.c` is the Linux Bluetooth HCI event dispatcher. It receives controller event packets, validates their lengths, routes them through command-complete, command-status, classic BR/EDR event, LE meta-event, vendor-event, and ISO event handlers, and keeps the kernel's `struct hci_dev` and `struct hci_conn` state synchronized with controller reality. The file bridges raw HCI event bytes to higher layers such as management, L2CAP, SCO, ISO, SMP pairing, debugfs, sysfs, discovery, advertising, scanning, and command request completion.

## Important APIs, Types, and Functions
The externally visible entry point is `hci_event_packet(struct hci_dev *hdev, struct sk_buff *skb)`. It clones the received event into `hdev->recv_event`, handles pending request completion callbacks, pulls the HCI event header, dispatches through `hci_event_func()`, stores a wake reason if suspended, invokes request-complete callbacks, frees the skb, and increments `hdev->stat.evt_rx`.

The dispatcher is table driven. `hci_ev_table[]` maps HCI event codes to fixed or variable length handlers. `hci_le_ev_table[]` maps LE meta subevents. `hci_cc_table[]` maps command-complete opcodes to callbacks that return HCI status. `hci_cs_table[]` maps command-status opcodes to callbacks. The helper families `hci_ev_skb_pull()`, `hci_cc_skb_pull()`, and `hci_le_ev_skb_pull()` centralize bounded `skb_pull_data()` parsing and log malformed events.

Command-complete handlers update controller caches and command effects. They include setup and feature handlers such as `hci_cc_reset()`, `hci_cc_read_local_version()`, `hci_cc_read_local_commands()`, `hci_cc_read_local_features()`, `hci_cc_read_local_ext_features()`, `hci_cc_read_buffer_size()`, `hci_cc_le_read_buffer_size()`, `hci_cc_le_read_buffer_size_v2()`, `hci_cc_read_bd_addr()`, and `hci_cc_le_read_all_local_features()`. Policy, name, security, and power handlers update local state or management completion events, including `hci_cc_write_local_name()`, `hci_cc_write_auth_enable()`, `hci_cc_write_scan_enable()`, `hci_cc_write_ssp_mode()`, `hci_cc_write_sc_support()`, `hci_cc_read_enc_key_size()`, `hci_cc_read_auth_payload_timeout()`, `hci_cc_write_auth_payload_timeout()`, `hci_cc_read_rssi()`, and `hci_cc_read_tx_power()`.

LE command-complete handlers manage random addresses, advertising instances, scanning, accept lists, resolving lists, privacy mode, data length, default PHYs, periodic advertising, CIG/CIS setup, ISO paths, and LE feature storage. Representative functions are `hci_cc_le_set_random_addr()`, `hci_cc_le_set_adv_enable()`, `hci_cc_le_set_ext_adv_enable()`, `hci_cc_le_set_scan_enable()`, `hci_cc_le_set_ext_scan_enable()`, `hci_cc_le_add_to_accept_list()`, `hci_cc_le_add_to_resolv_list()`, `hci_cc_le_set_addr_resolution_enable()`, `hci_cc_le_set_cig_params()`, and `hci_cc_le_setup_iso_path()`.

Command-status handlers handle operations whose final outcome may arrive in later events. They include connection initiation and teardown (`hci_cs_create_conn()`, `hci_cs_disconnect()`, `hci_cs_le_create_conn()`, `hci_cs_le_ext_create_conn()`), authentication and encryption (`hci_cs_auth_requested()`, `hci_cs_set_conn_encrypt()`, `hci_cs_le_start_enc()`), remote feature/name reads, role switch, sniff mode transitions, SCO/eSCO setup, CIS creation, and BIG creation.

Classic event handlers cover inquiry, connection request and completion, disconnection, authentication, encryption changes, link-key exchange, role changes, packet-completion flow control, mode changes, pin code and SSP pairing, remote OOB requests, remote features, synchronous connection completion, and extended inquiry results. LE handlers cover connection complete, enhanced connection complete, advertising reports, extended advertising reports, direct advertising reports, periodic advertising sync, PAST, connection updates, remote feature completion, LTK requests, remote connection-parameter requests, PHY updates, CIS request/established, BIG create/sync/lost/info events, and all-remote-features completion.

## Control Flow
Top-level flow starts in `hci_event_packet()`. It rejects packets shorter than `struct hci_event_hdr`, stores a clone in `hdev->recv_event`, rejects event code zero, pre-completes matching request events for non-LE requested events, clones a pristine skb when a request-complete-skb callback might need unmodified bytes, strips the HCI event header, and calls `hci_event_func()`.

`hci_event_func()` indexes `hci_ev_table[event]`, checks minimum length, warns on larger-than-expected payloads, pulls the declared minimum payload, then calls either a normal handler or a request-aware handler. Command complete dispatch uses `hci_cmd_complete_evt()`: it extracts the opcode, finds a matching `hci_cc_table[]` entry, parses the command return payload, runs the opcode-specific callback, handles controller command credits through `handle_cmd_cnt_and_timer()`, calls `hci_req_cmd_complete()`, and schedules command work if credits are available. Unknown command-complete opcodes are interpreted by convention as status in byte zero so vendor commands can still report errors to synchronous command callers.

Command status dispatch uses `hci_cmd_status_evt()`: it extracts opcode and status, runs any `hci_cs_table[]` callback, updates command credits and timers, and completes the pending request immediately on failure or on successful status for commands that do not expect a later event. LE meta dispatch uses `hci_le_meta_evt()`: it can complete an LE request when the requested subevent matches `hdev->req_skb`, then validates and dispatches through `hci_le_ev_table[ev->subevent]`.

Connection flows are staged. BR/EDR connection status may allocate or clean up `hci_conn` objects, while `hci_conn_complete_evt()` assigns the handle once, transitions ACL links to `BT_CONFIG`, creates debugfs/sysfs entries, starts remote feature reads, updates scan state, and confirms SCO links immediately. LE connection complete follows similar rules in `le_conn_complete_evt()`, but additionally clears advertising state, resolves identity addresses through IRK lookup, records initiator/responder addresses for SMP, rejects blocked peers, updates pending LE auto-connect lists, starts LE feature exchange, and refreshes passive scanning before unlock.

Discovery and advertising flow is split between inquiry events and LE advertising report processing. Inquiry results update the inquiry cache and emit `mgmt_device_found()`. Inquiry complete moves discovery to name resolving or stopped. LE advertising reports are normalized by `process_adv_report()`, which validates advertising types and data lengths, trims padded data, handles directed advertising and local IRK matching, maps RPAs to identity addresses, starts pending auto-connects, merges scan responses with cached advertisements for active scanning, suppresses most passive-scan reports, and forwards mesh or monitor-relevant findings.

Security flow spans several event types. Link-key request handlers validate stored key suitability before replying. Link-key notify rejects all-zero keys and persists or flushes keys based on policy. Encryption change and key refresh events update authentication, encryption, AES-CCM, FIPS, key-size, and authenticated payload timeout state, and disconnect on unmet security requirements. SSP and OOB handlers compute authentication requirements, select user-confirm, auto-accept, passkey, or OOB replies, and notify management where user-space policy is required. LE LTK requests validate STK/LTK material, EDIV/RAND, security level, and encryption size before replying.

ISO flow updates CIG/CIS/BIS/BIG state from command responses and LE meta events. `hci_cc_le_set_cig_params()` assigns CIS handles and starts pending CIS creation. `hci_le_cis_established_evt()` computes role-dependent QoS intervals and latency from event timing fields, sets connected state, creates debugfs/sysfs nodes, and starts ISO path setup. BIG creation and BIG sync events bind BIS handles, populate broadcast QoS, establish data paths, notify failures, and terminate inconsistent BIGs.

## State and Persistence Behavior
Most state is in-memory kernel state on `struct hci_dev`, `struct hci_conn`, inquiry cache entries, advertising instances, connection-parameter objects, link keys, LTKs, OOB data, and pending work items. The file does not write durable storage directly. Persistence beyond runtime is delegated through management notifications and key-management helpers that higher layers or user space may store.

`hdev` state updated here includes feature pages, command masks, local version fields, manufacturer, local BDADDR/setup address, packet and buffer counts, scan and inquiry flags, link policy, voice setting, class of device, local name, LE features, LE/ISO MTUs and packet credits, random address/RPA expiry, advertising data and instances, LE scan type, discovery state, accept and resolving lists, privacy/address-resolution flags, PHY defaults, data-length defaults, wake reason, and hardware error code.

`hci_conn` state updated here includes handles, role, state (`BT_OPEN`, `BT_CONNECT`, `BT_CONFIG`, `BT_CONNECTED`, `BT_CLOSED`, `BT_BOUND`, `BT_CONNECT2`), reference lifetime, device addresses and address types, SMP initiator/responder addresses, remote features, LE features, encryption/authentication/security flags, key type and key size, passkey progress, RSSI/tx power/clock/auth-payload timeout, connection intervals, advertising instance association, SCO/eSCO type, ISO QoS, sync handles, CIG/CIS/BIG/BIS identifiers, transmit counters, and management-connected flags.

Concurrency is primarily protected by `hci_dev_lock()` and lockdep-annotated wake-reason storage. Command-credit state uses atomics and delayed work cancellation or scheduling. Work queues are used for command work, TX work, error resets, scan disable, advertising re-enable, RPA expiry, and ISO cleanup. RCU is used around some command counter handling and key removal paths.

## Dependencies and Integration Points
The file depends on core Bluetooth definitions from `net/bluetooth/bluetooth.h`, `hci_core.h`, and `mgmt.h`, plus `hci_debugfs.h`, `hci_codec.h`, `smp.h`, `msft.h`, and `eir.h`. It uses kernel skb parsing, unaligned access helpers, crypto constant-time comparison, atomics, delayed work, jiffies, lists, RCU freeing, sysfs/debugfs connection registration, and management event helpers.

Integration points are broad. HCI core command execution depends on command-credit handling and request completion callbacks here. Management receives device-found, connected, disconnected, pairing, key, advertising, connection-parameter, and wake-reason information. L2CAP/SCO/ISO layers receive connection, disconnection, authentication, encryption, key-change, role-switch, and ISO setup confirmations through `hci_*_cfm()` and protocol indication hooks. SMP depends on correct LE address, IRK, LTK, security-level, and encryption state. Vendor events are forwarded to `msft_vendor_evt()`. Debugfs and sysfs connection objects are created when handles become valid.

## Risks and Edge Cases
The main risk is parsing attacker-controlled or controller-controlled event data. The table-driven length checks and `skb_pull_data()` guards are central test points. Variable-length events such as inquiry results, advertising reports, command-complete CIG responses, BIG events, and packet-completion arrays are especially sensitive to malformed lengths and count fields.

Connection lifetime is high risk. The file explicitly rejects duplicate connection-complete processing because a second handle assignment could corrupt memory. It also handles connection collisions, status events that fail after an object was allocated, disconnects during suspend where a complete event may not arrive, and auto-connect list restoration after link loss.

Security-sensitive behavior includes rejecting same-BDADDR incoming BR/EDR connections, rejecting all-zero BR/EDR link keys, rejecting keys that do not meet requested security, forcing disconnect on too-small or downgraded encryption key size, expiring RPAs after LE encryption failure, and validating OOB material for Secure Connections Only mode. Regressions here can affect CVE-class pairing or impersonation defenses.

State synchronization with controller quirks is another risk. The code contains quirk branches for broken local extended features page 2, fixed buffer sizes, broken LE states, broken extended advertising report PHY bits, and broken authenticated payload timeout writes. Tests need to cover both normal and quirked controllers.

Workqueue and locking ordering matter. Handlers frequently send HCI commands while holding `hdev->lock`, schedule work, update atomics, and call management confirmations. Missed unlocks, stale pending request state, or duplicate completions can stall the command queue, leak connections, or notify user space out of order.

## Test Signals
Useful signals include packet-fuzz tests for every fixed and variable-length event table entry, especially short packets, oversized packets, zero event code, unknown command-complete opcodes, mismatched command-complete opcodes, and malformed LE advertising arrays. Command queue tests should assert command-credit recovery, request callback invocation, `HCI_CMD_PENDING` diagnostics, and work scheduling after command complete/status.

Connection tests should cover BR/EDR and LE successful setup, command-status failures, duplicate complete events, disconnect failures, suspend disconnect cleanup, blocked-address rejection, accept-list auto connection, RPA identity resolution, remote feature failures, and scan/advertising re-enable behavior. Security tests should cover zero link key rejection, unauthenticated key filtering, high security with short PIN keys, read-encryption-key-size downgrade rejection, LE LTK EDIV/RAND mismatch, STK deletion, OOB data selection, and SSP auto-accept versus management confirmation paths.

Discovery tests should assert inquiry cache updates, name resolving timeout behavior, EIR length trimming, LE active scan response merging, passive scan suppression, mesh forwarding, advertisement-monitor exceptions, extended advertising type normalization, direct advertising local IRK matching, and maximum advertising length enforcement. ISO tests should cover CIG handle assignment, CIS failure cleanup and pending retry, role-dependent QoS calculations, BIG creation with too few handles, BIG sync failure notifications, and BIG lost cleanup.
