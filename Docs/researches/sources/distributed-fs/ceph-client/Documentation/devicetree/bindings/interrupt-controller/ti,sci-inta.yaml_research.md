# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/ti,sci-inta.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Texas Instruments K3 Interrupt Aggregator`. In this tree it is an interrupt controller binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: The Interrupt Aggregator (INTA) provides a centralized machine which handles the termination of system events to that they can be coherently processed by the host(s) in the system. A maximum of 64 events can be mapped to a single interrupt. Interrupt Aggregator +-----------------------------------------+ | Intmap VINT | | +--------------+ +------------+ | m ------>| | vint | bit | | 0 |.....|63| vint0 | . | +--------------+ +------------+ | +------+ . | . . | | HOST | Globalevents ------>| . . |----->| IRQ | . | . . | | CTRL | . | . . | +------+ n ------>| +--------------+ +------------+ | | | vint | bit | | 0 |.....|63| vintx | | +--------------+ +------------+ | | | | Unmap | | +--------------+ | Unmapped events ---->| | umapidx |-------------------------> Globalevents | +--------------+ | | | +-----------------------------------------+ Configuration of these Intmap registers that maps global events to vint is done by a system controller (like the Device Memory and Security Controller on AM654 SoC). Driver should request the system controller to get the range of global events and vints assigned to the requesting host. Management of these requested resources should be handled by driver and requests system controller to map specific global event to vint, bit pair. Communication between the host processor running an OS and the system controller happens through a protocol called TI System Control Interface (TISCI protocol).

**Important APIs/types/functions:** This YAML is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/interrupt-controller/ti,sci-inta.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and any referenced dt-schema fragments. Compatible strings or compatible-pattern values are `ti,sci-inta`. Required properties are `compatible`, `reg`, `interrupt-controller`, `msi-controller`, `ti,sci`, `ti,sci-dev-id`, `ti,interrupt-ranges`. Important top-level properties are `compatible`, `reg`, `interrupt-controller`, `#interrupt-cells`, `msi-controller`, `ti,interrupt-ranges`, `ti,unmapped-event-sources`, `power-domains`. Direct and nested `$ref` dependencies are `/schemas/arm/keystone/ti,k3-sci-common.yaml#`, `/schemas/types.yaml#/definitions/uint32-matrix`, `/schemas/types.yaml#/definitions/phandle-array`. Property roles include `compatible` for driver match key and stable hardware ABI identifier; `reg` for MMIO range, bus address, or child register selector; `interrupt-controller` marks the node as an interrupt domain provider; `#interrupt-cells` for interrupt specifier cell count consumed by child/client nodes; `msi-controller` marks the node as an MSI domain provider; `ti,interrupt-ranges` for binding-specific property constrained by the schema; `ti,unmapped-event-sources` for binding-specific property constrained by the schema; `power-domains` for genpd power-domain attachment. The top-level unknown-property policy is `unevaluatedProperties: false`. Maintainers are `Lokesh Vutla <lokeshvutla@ti.com>`.

**Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. Schema composition/conditional keywords present: `allOf`. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IRQ domain code uses it to translate DT interrupt specifiers into Linux IRQs and route them to an upstream parent domain. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as `reg`, `power-domains`. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.
