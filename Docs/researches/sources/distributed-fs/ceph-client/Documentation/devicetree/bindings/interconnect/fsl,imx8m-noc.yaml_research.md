# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interconnect/fsl,imx8m-noc.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interconnect/fsl,imx8m-noc.yaml` is a Linux devicetree YAML schema for the `Generic i.MX bus frequency device` interconnect provider binding. The i.MX SoC family has multiple buses for which clock frequency (and sometimes voltage) can be adjusted. Some of those buses expose register areas mentioned in the memory maps as GPV ("Global Programmers View") but not all. Access to this area might be denied for normal (non-secure) world. The buses are based on externally licensed IPs such as ARM NIC-301 and Arteris FlexNOC but DT bindings are specific to the integration of these bus interconnect IPs into imx SOCs. It is not executable kernel code; it is the hardware-description ABI that DTS authors, dt-schema, and the relevant kernel subsystem rely on so the runtime driver can parse the node without board-specific ambiguity.

## Important APIs, Types, and Functions
The public API surface is the schema's accepted node shape. `compatible` uses `oneOf` with 3 accepted compatible forms and covers 10 compatible tokens: `fsl,imx8mm-nic`, `fsl,imx8mn-nic`, `fsl,imx8mp-nic`, `fsl,imx8mq-nic`, `fsl,imx8m-nic`, `fsl,imx8mm-noc`, `fsl,imx8mn-noc`, `fsl,imx8mp-noc`, `fsl,imx8mq-noc`, `fsl,imx8m-noc`. Top-level properties are `compatible`, `reg`, `clocks`, `operating-points-v2`, `opp-table`, `fsl,ddrc`, `#interconnect-cells`. Across nested schemas and child nodes this file mentions 7 distinct property names; nested/all required properties include `clocks`, `compatible`. Node naming is constrained by no explicit node-name constraint. Interconnect-facing properties define a provider node for the Linux interconnect framework and related devfreq/OPP consumers: addressing resources `reg`, provider cells `#interconnect-cells`, clocks/power/OPP hooks `clocks`, `operating-points-v2`, `opp-table`, and SoC/vendor topology knobs `operating-points-v2`, `#interconnect-cells`. Required properties are `compatible`, `clocks`; consumer nodes depend on these cells and phandles to vote bandwidth or performance state.

## Control Flow, State, and Persistence
Control flow is declarative JSON-schema evaluation rather than executable branching. `dt-doc-validate` and `dt_binding_check` load the YAML, expand `$ref` links, apply composition and conditional keywords, validate the DTS example blocks, and later `dtbs_check` applies the same contract to compiled board devicetrees. For interconnect providers, validation ensures that provider cells, register banks, clocks, power domains, BCM voter links, and OPP or devfreq relationships are well-formed before Linux interconnect providers register bandwidth paths consumed by other device nodes. The schema itself stores no mutable state and writes no persistent data; its persistence is the stable source-controlled hardware ABI. External references used in evaluation are `/schemas/types.yaml#/definitions/phandle`; top-level/nested conditional keywords present are `oneOf`.

## Risks
Risks are mostly ABI and validation risks rather than algorithmic failures. Tightening required properties, changing compatible ordering, renaming resources, altering cell counts, or closing extra properties can reject existing DTS users; loosening constraints can allow nodes that later fail driver probe or misdescribe hardware. This schema has 7 top-level properties and 7 distinct nested property names, with strictness profile: unknown top-level properties are rejected. Conditional branches and shared `$ref` schemas should be checked against all in-tree users before edits, because a schema-only patch can still break board builds.
