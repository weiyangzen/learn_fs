# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pps/pps-gpio.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pps/pps-gpio.yaml` defines the Linux Devicetree YAML schema for `PPS Signal via GPIO`, a PPS GPIO time-source binding. It is declarative ABI documentation and validation input, not executable driver code. Its job is to keep DTS/DTB nodes aligned with the resources, child nodes, and electrical or timing constraints expected by the matching kernel subsystem before a driver probes hardware.

## Important APIs, Types, and Functions
The API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `patternProperties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses a single `const` with 1 token: `pps-gpio`. Top-level properties are `compatible`, `gpios`, `echo-gpios`, `echo-active-ms`, `assert-falling-edge`. Top-level required properties are `compatible`, `gpios`; required properties collected from nested branches include `compatible`, `gpios`. Patterned child schemas are none. Numeric and collection constraints include `maxItems=1`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `gpios` describes board GPIO control/status wiring; `echo-gpios` describes board GPIO control/status wiring. The highest-risk ABI details are GPIO polarity, assert/clear event semantics, optional echo wiring, and latency-sensitive interrupt configuration.

## Control Flow
Control flow is dt-schema evaluation rather than imperative execution. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties` and `patternProperties`, evaluates no top-level conditionals, checks required fields and min/max constraints, validates examples, and enforces the closure policy. At runtime this YAML does not execute: the compiled DTB node is matched through a kernel OF table or subsystem-specific child-node parser, then helpers for power-supply, regulator, PWM, PTP, PPS, PowerPC platform, clocks, resets, interrupts, GPIOs, pinctrl, power domains, and MFD parents consume the validated resources.

## State and Persistence Behavior
The file stores no mutable runtime state and writes no persistent data. Its persistence is ABI stability: compatible strings, required resource names, phandle/cell counts, child-node names, electrical limit properties, fallback ordering, and example layouts become long-lived contracts in DTS and DTB artifacts. Runtime state belongs to drivers and hardware after probe, including PPS source registration, timestamp capture state, edge counters, echo-pulse state, and GPIO IRQ state.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, power sequencing, clock setup, IRQ delivery, or consumer phandle resolution. Tightening required properties can reject existing board files; loosening them can hide missing supplies, clocks, resets, interrupts, current/voltage limits, PWM cell counts, PTP/PPS GPIOs, or regulator child constraints. This schema rejects unknown top-level properties with `additionalProperties: false`. It has 5 top-level properties and 5 distinct nested property names, so broad edits should be checked against all compatibles, examples, and in-tree DTS users rather than only the filename's nominal device.

## Test Signals
Run `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/pps/pps-gpio.yaml` for targeted schema validation and `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/pps/pps-gpio.yaml` against boards using these nodes. High-value negative checks remove required `compatible`, `reg`, interrupts, clocks, resets, supplies, GPIOs, child regulator/PWM/battery nodes, or phandles; use invalid cell counts or child `reg` values; misspell vendor properties; and exercise every compatible-specific branch. Runtime integration signals are successful driver probe, correct power_supply/regulator/PWM/PTP/PPS/platform registration, clean suspend/resume or runtime-PM behavior where applicable, valid interrupt/reset/power sequencing, and no dtbs_check regressions in embedded examples or in-tree DTS users.
