# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/qcom,sc8280xp-camss.yaml

**Purpose:** Defines the Devicetree JSON-schema ABI for `Qualcomm SC8280XP Camera Subsystem (CAMSS)`. It is a Qualcomm CAMSS camera subsystem media graph binding in the Ceph client Linux source snapshot, constraining how board DTS/DTB files describe media hardware so Linux media, V4L2 mem2mem, platform, clock, reset, power-domain, IOMMU, and graph helpers can bind the correct driver resources. The source description says: The CAMSS IP is a CSI decoder and ISP present on Qualcomm platforms.

**Control flow:** Runtime control flow is supplied by dt-schema and kernel probing. `dt_binding_check` loads the core meta-schema, resolves references, validates the compatible form, applies required lists and `minItems`/`maxItems`/`const` restrictions, evaluates conditionals, and compiles the inline examples. At boot the DTB node is matched by `compatible`; the platform or media driver then reads MMIO ranges, named interrupts, clocks, resets, power domains, IOMMU streams, DMA/interconnect paths, firmware or reserved-memory phandles, and graph endpoints. There are no compatible-specific conditional branches beyond direct property validation. Media graph integration is explicit through `port@0`, `port@1`, `port@2`, `port@3`; the schema references graph/video interface rules and mentions `endpoint` 6 time(s). Endpoint validation covers remote links, lane descriptions, bus type, bus width, and synchronization/pixel-clock polarity where the hardware exposes those signals.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence itself. Its persistent effect is ABI stability for DTS files and shipped DTBs: compatible strings, child-node names, phandle relationships, address ranges, cell counts, and media graph topology are long-lived hardware descriptions. Any change to required properties, resource ordering, child object schemas, or unknown-property policy can invalidate existing board descriptions even though no kernel state is written by the YAML.

**Dependencies and integration points:** Direct schema references are `/schemas/graph.yaml#/$defs/port-base`, `/schemas/graph.yaml#/properties/ports`, `video-interfaces.yaml#`. Runtime dependencies are V4L2 async/media-controller graph links through `ports`, `port`, and `endpoint` nodes, IOMMU/SMMU stream mappings for video DMA, Linux interconnect bandwidth paths, genpd power domains, clock provider phandles and fixed clock-name ordering, Qualcomm CSIPHY/CSID/VFE sub-block naming expected by the CAMSS driver. No nested object nodes are defined beyond common schema references. Maintainers listed in the binding are `Bryan O'Donoghue <bryan.odonoghue@linaro.org>`.

**Risks:** Key risks: compatible-string or fallback-order drift can break OF matching and dtbs_check expectations; resource array ordering is ABI-sensitive for `reg-names`, `clock-names`, `interrupt-names`, `power-domain-names`, and `reset-names`; media graph mistakes in `remote-endpoint`, lane numbering, bus type, or required ports can leave cameras disconnected even when the platform device probes; wrong IOMMU stream IDs can cause video DMA faults or silent memory corruption; missing interconnect or OPP constraints can produce bandwidth or power-collapse failures under high-resolution workloads; SoC-specific power-domain count differences are easy to regress in fallback compatibles; large CAMSS bindings have many CSIPHY/CSID/VFE resources, so a single missing name can shift subsequent resources in the driver. The closure policy is `additionalProperties: False`, so unknown properties are intentionally rejected after referenced schemas are evaluated.
