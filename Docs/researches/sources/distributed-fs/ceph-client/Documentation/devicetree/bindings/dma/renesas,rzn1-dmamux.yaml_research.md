# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/dma/renesas,rzn1-dmamux.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Renesas RZ/N1 DMA mux`. In this tree it is a DMA engine, DMA router, or DMA-capable IP binding used by dmaengine providers and DMA client phandle specifiers; it constrains how board DTS files describe the hardware and how Linux drivers discover it through OF matching, phandles, and common binding references.

**Important APIs/types/functions:** This is declarative schema rather than executable code. The public ABI surface is `$id` `http://devicetree.org/schemas/dma/renesas,rzn1-dmamux.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and the referenced schemas used by dt-schema. Compatible strings are `renesas,rzn1-dmamux`. Required properties are `reg`, `dma-requests`. Important properties include `compatible`, `reg`, `#dma-cells`, `dma-masters`, `dma-requests`. Referenced schemas are `dma-router.yaml#`. Property roles include `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address; `#dma-cells` for DMA client specifier width; `dma-masters` for upstream DMA controller phandles for routers; `dma-requests` for number of peripheral DMA requests. The top-level closure rule is `additionalProperties: false`. Maintainers: Miquel Raynal <miquel.raynal@bootlin.com>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel subsystems, not by this YAML file. `dt_binding_check` loads the core meta-schema, resolves references such as `dma-router.yaml#`, applies `properties`, `required`, enum/const/items limits, and any `allOf` or conditional branches, then validates the inline examples. During boot, a matching DT node is compiled into the DTB, the kernel matches `compatible`, subsystem code reads cells and phandles, and the bound driver consumes resources such as DMA router master phandles. Conditional/schema-composition points include `allOf`, so different compatibles or child-node shapes can activate different required-property sets. It does not define nested child-node schemas.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, resource topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though no kernel state is stored here.

**Dependencies and integration points:** Integrated with dmaengine and Devicetree DMA client code. Direct schema dependencies are `dma-router.yaml#`; resource dependencies visible in the property set include DMA router master phandles. Driver integration is through `compatible`, while client/provider integration is through cell properties, phandle arrays, child schemas, and bus-standard properties declared or inherited here.

**Risks:** Main risks are schema ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, missing required clocks/resets/interrupts/power domains, stale examples, and conditional branches that accept one SoC variant while rejecting another valid one. Unknown-property policy also matters: `additionalProperties: false` can either catch misspelled DTS properties or allow legacy extension points. For bindings with child nodes or graph/connector references, parent-child address-cell and port layout mistakes can pass driver review only if dtbs_check coverage is weak.

**Test signals:** Run `make dt_binding_check DT_SCHEMA_FILES=sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/dma/renesas,rzn1-dmamux.yaml` and `make dtbs_check` against DTS users of every compatible family. Verify inline examples compile, required-property failures are reported, compatible-specific branches are exercised, inherited schemas resolve, and drivers still probe with the resources described here. The file includes 1 example block(s), which are part of the dt-schema validation signal.
