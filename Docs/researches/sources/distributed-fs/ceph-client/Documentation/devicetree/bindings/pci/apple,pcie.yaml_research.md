# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pci/apple,pcie.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pci/apple,pcie.yaml` defines the Linux Devicetree YAML schema for `Apple PCIe host controller`, a PCIe host or endpoint controller binding. The schema description says: The Apple PCIe host controller is a PCIe host controller with multiple root ports present in Apple ARM SoC platforms, including various iPhone and iPad devices and the "Apple Silicon" Macs. The controller incorporates Synopsys DesigWare PCIe logic to implements its root ports. But the ATU found on most DesignWare PCIe host bridges is absent. On systems derived from T602x, the PHY registers are in a region separate from the port registers. In that case, there is one PHY register range per port register range. It is declarative ABI documentation and validation input rather than executable kernel code; its practical role is to make DTS/DTB hardware descriptions match the resources, topology, and compatible strings expected by the relevant kernel subsystem before probe.

## Important APIs, Types, and Functions
The public API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses `oneOf` with 2 branchs and exposes 5 tokens: `apple,t8103-pcie`, `apple,t8112-pcie`, `apple,t6000-pcie`, `apple,pcie`, `apple,t6020-pcie`. Top-level properties are `compatible`, `reg`, `reg-names`, `ranges`, `interrupts`, `msi-parent`, `msi-ranges`, `iommu-map`, `iommu-map-mask`, `power-domains`. Top-level required properties are `compatible`, `reg`, `reg-names`, `bus-range`, `interrupts`, `msi-controller`, `msi-parent`, `msi-ranges`; required properties collected from nested schema branches include `bus-range`, `compatible`, `interrupts`, `msi-controller`, `msi-parent`, `msi-ranges`, `reg`, `reg-names`. Patterned child schemas are none. Numeric and collection constraints include `minItems=3`, `maxItems=10`, `minItems=2`, `maxItems=2`, `minItems=1`, `maxItems=4`, `maxItems=1`, `maxItems=5`, `maxItems=3`, `minItems=10`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `reg` describes MMIO ranges, bus child addresses, port selectors, or cell offsets; `reg-names` fixes resource ordering visible to drivers; `ranges` is a PCIe address/window or link capability contract; `interrupts` routes status, error, RX/TX, MSI, or completion IRQs; `power-domains` integrates with common clock, reset, PM, DMA/IOMMU, or reserved-memory providers. The highest-risk ABI details are compatible fallback ordering, `reg`/`reg-names`, `ranges`, bus-range, MSI and interrupt-map wiring, PHY/reset/clock ordering, PERST#/wake GPIOs, link-generation and lane-count properties, and endpoint vs root-complex mode constraints.

## Control Flow
Runtime control flow is supplied by dt-schema and kernel subsystem code, not by this YAML file. `dt_binding_check` loads the meta-schema, resolves `$ref` entries, applies `properties`, evaluates `allOf`, checks required fields, validates `minItems`/`maxItems` and enum/const constraints, validates embedded examples, and applies the closure rule. During boot, the compiled DTB node is matched by `compatible`; then platform, PCI, SDIO, SPI, MDIO, NVMEM, OPP, PCIe, netdev, wireless, accelerator, storage, clock, reset, regulator, IRQ, GPIO, IOMMU, and power-domain helpers consume the phandles and resource arrays that this schema validates. Child nodes are discovered declaratively through fixed names, pattern properties, address cells, and referenced child schemas.

## State and Persistence Behavior
The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: compatible strings, required resource names, register and interrupt ordering, phandle and cell counts, child-node names, fallback ordering, and example layouts become long-lived contracts in board DTS files and shipped DTBs. Runtime state belongs to the matching drivers and hardware after probe, including PCI host bridge registration, ECAM/config-space access, link training state, MSI domain state, DMA/IOMMU windows, endpoint BAR/function configuration, reset recovery, and runtime PM.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, link training, calibration lookup, OPP selection, NVMEM cell reads, or bus enumeration. Tightening required properties can reject existing boards; loosening them can hide missing clocks, resets, interrupts, supplies, PHY links, PCIe windows, memory regions, OPP fields, or NVMEM cells. Child-node schemas need special care because address cells, port IDs, PCI interrupt maps, wireless calibration cells, NVMEM layouts, and OPP tables must match driver-side assumptions. This schema closes composed schemas with `unevaluatedProperties: false`. It has 10 top-level properties and 10 distinct nested property names, so broad edits should be checked against all compatible variants and DTS users, not just the nominal filename.

High-value negative checks remove required properties, use invalid compatible fallbacks, corrupt `reg` or interrupt counts, misspell vendor properties, violate child-node address-cell rules, and exercise every conditional branch. Runtime integration signals are successful driver probe, correct subsystem registration, valid NVMEM/OPP/PCIe/wireless/netdev/accelerator/storage behavior as applicable, clean interrupt/reset/power sequencing, and no new dtbs_check failures in embedded examples or in-tree DTS users.
