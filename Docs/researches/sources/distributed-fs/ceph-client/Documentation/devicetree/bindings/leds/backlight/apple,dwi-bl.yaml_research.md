# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/leds/backlight/apple,dwi-bl.yaml

**Purpose:** Defines the Linux Devicetree JSON-schema contract for `Apple DWI 2-Wire Interface Backlight Controller`. In this source tree it is a LED/backlight controller binding; it constrains board DTS/DTB nodes so kernel OF matching and subsystem code can discover the hardware resources consistently. This is declarative ABI documentation, not executable Ceph client code, but it is part of the imported kernel documentation corpus that protects hardware-description compatibility. The source description says: Apple SoCs contain a 2-wire interface called DWI. On some Apple iPhones, iPads and iPod touches with a LCD display, 1-2 backlight controllers are connected via DWI. Interfacing with DWI controls all backlight controllers at the same time. As such, the backlight controllers are treated as a single controller regardless of the underlying configuration.

**Important APIs/types/functions:** The public surface is the schema itself: `$id` `http://devicetree.org/schemas/leds/backlight/apple,dwi-bl.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, composition keywords, closure rules, and `examples` consumed by `dt-schema`. Compatible strings are `apple,s5l8960x-dwi-bl`, `apple,t7000-dwi-bl`, `apple,s8000-dwi-bl`, `apple,t8010-dwi-bl`, `apple,t8015-dwi-bl`, `apple,dwi-bl`. Required properties are `compatible`, `reg`. Important top-level properties include `compatible`, `reg`, `power-domains`. Patterned or child-node surfaces include none declared. Direct schema references are `common.yaml#`. Maintainers: Nick Chan <towinchenmi@gmail.com>. Top-level property policy is `unevaluatedProperties: false`.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel drivers rather than by this YAML. `dt_binding_check` loads the core meta-schema, resolves `$ref` dependencies, applies constants/enums/cardinality/range checks, evaluates composition and conditional branches (`allOf`), and validates the embedded examples. At boot, the compiled DTB node is matched by `compatible`; the relevant LED backlight driver or common subsystem reads resource properties, phandles, child nodes, and cells before registering devices or provider relationships. Child/provider surfaces to watch here are none declared.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistence is ABI persistence: accepted DTS nodes encode hardware identity, register windows, interrupts, power/clock/reset topology, phandle cell widths, channel indexes, and child LED/IOMMU/IPMI layout for long-lived boards. Tightening `required`, changing compatible fallback order, altering cell counts, or changing closure policy can reject existing DTBs or make drivers parse resources differently.

**Dependencies and integration points:** Integrated with backlight class devices, LED current/PWM/enable controls, regulator/GPIO resources, and brightness policy. Schema dependencies include `common.yaml#`; examples may also include dt-bindings headers. Resource integration is through properties such as `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address; `power-domains` for genpd power-domain attachment. Driver integration is through `compatible`, while subsystem integration is through phandle arrays, provider cell counts, common schemas, and child-node schemas inherited or declared here.

**Risks and edge cases:** Main risks are schema ABI drift, missing or stale compatible coverage, incorrect min/max item constraints, wrong `#*-cells` values, resource names that diverge from driver expectations, conditionals that validate one SoC or chip variant while rejecting another valid one, and examples that no longer reflect real DTS users. Closure policy (`unevaluatedProperties: false`) is useful for catching misspellings but can also block legitimate extensions. For LED/backlight children, channel numbering and `reg`/`led-sources` constraints are common failure points; for IOMMU bindings, stream IDs and cell widths are especially sensitive; for IPMI bindings, host/BMC address and register-resource shape must match the driver.

**Test signals:** Run `make dt_binding_check DT_SCHEMA_FILES=sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/leds/backlight/apple,dwi-bl.yaml` and `make dtbs_check` against DTS files using every compatible listed here. The 1 embedded example block(s) should compile through `dtc` and validate against referenced schemas. Useful negative tests remove each required property, add an unknown property under the declared closure policy, exercise compatible-specific conditionals, and verify the matching Linux driver still probes with the resources, child nodes, and phandle specifiers described by this binding.
