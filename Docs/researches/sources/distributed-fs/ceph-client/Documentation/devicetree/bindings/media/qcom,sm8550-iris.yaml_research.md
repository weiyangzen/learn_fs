# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/qcom,sm8550-iris.yaml

**Purpose:** Defines the Devicetree JSON-schema ABI for `Qualcomm iris video encode and decode accelerators`. It is a Qualcomm Iris video encode/decode accelerator binding in the Ceph client Linux source snapshot, constraining how board DTS/DTB files describe media hardware so Linux media, V4L2 mem2mem, platform, clock, reset, power-domain, IOMMU, and graph helpers can bind the correct driver resources. The source description says: The iris video processing unit is a video encode and decode accelerator present on Qualcomm platforms.

**Important APIs/types/functions:** This is declarative schema, so the exported API is the binding contract rather than C functions. Public surfaces include `$id` `http://devicetree.org/schemas/media/qcom,sm8550-iris.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, examples, and dt-schema references. **Control flow:** Runtime control flow is supplied by dt-schema and kernel probing. `dt_binding_check` loads the core meta-schema, resolves references, validates the compatible form, applies required lists and `minItems`/`maxItems`/`const` restrictions, evaluates conditionals, and compiles the inline examples. At boot the DTB node is matched by `compatible`; the platform or media driver then reads MMIO ranges, named interrupts, clocks, resets, power domains, IOMMU streams, DMA/interconnect paths, firmware or reserved-memory phandles, and graph endpoints. Schema composition uses `allOf`, `else`, `if`, `oneOf`, `then`. Validation can therefore change by compatible string, for example by tightening clock/reset counts, requiring SoC-specific helper phandles, or allowing/deprecating child codec nodes. This binding has no media graph endpoint surface; integration is by platform device resources and codec-specific child nodes.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence itself. Its persistent effect is ABI stability for DTS files and shipped DTBs: compatible strings, child-node names, phandle relationships, address ranges, cell counts, and media graph topology are long-lived hardware descriptions. Any change to required properties, resource ordering, child object schemas, or unknown-property policy can invalidate existing board descriptions even though no kernel state is written by the YAML.

**Dependencies and integration points:** Direct schema references are none. Runtime dependencies are IOMMU/SMMU stream mappings for video DMA, Linux interconnect bandwidth paths, OPP and power-domain performance voting, genpd power domains, clock provider phandles and fixed clock-name ordering, reset-controller phandles, reserved-memory carveout, firmware loader naming. Nested schema surfaces include `opp-table`. These child nodes are part of the ABI, not driver-private data; their compatible values, required clocks, power domains, IOMMU entries, or codec-core markers must stay aligned with the driver. Maintainers listed in the binding are `Vikash Garodia <quic_vgarodia@quicinc.com>`, `Dikshita Agarwal <dikshita.agarwal@oss.qualcomm.com>`.

**Risks:** Key risks: compatible-string or fallback-order drift can break OF matching and dtbs_check expectations; resource array ordering is ABI-sensitive for `reg-names`, `clock-names`, `interrupt-names`, `power-domain-names`, and `reset-names`; wrong IOMMU stream IDs can cause video DMA faults or silent memory corruption; missing interconnect or OPP constraints can produce bandwidth or power-collapse failures under high-resolution workloads; SoC-specific power-domain count differences are easy to regress in fallback compatibles; codec child-node deprecation, memory carveouts, and firmware/performance votes must remain compatible with existing DTS files. The closure policy is `unevaluatedProperties: False`, so unknown properties are intentionally rejected after referenced schemas are evaluated.
