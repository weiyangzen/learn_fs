# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/microchip,csi2dc.yaml

**Purpose:** Defines the Devicetree JSON-schema ABI for `Microchip CSI2 Demux Controller (CSI2DC)`. It is a MIPI CSI-2 receiver/bridge media graph binding in the Ceph client Linux source snapshot, constraining how board DTS/DTB files describe media hardware so Linux media, V4L2 mem2mem, platform, clock, reset, power-domain, IOMMU, and graph helpers can bind the correct driver resources. The source description says: CSI2DC - Camera Serial Interface 2 Demux Controller CSI2DC is a hardware block that receives incoming data from either from an IDI interface or from a parallel bus interface. It filters IDI packets based on their data type and virtual channel identifier, then converts the byte stream to a pixel stream into a cross clock domain towards a parallel interface that can be read by a sensor controller. IDI interface is Synopsys proprietary. CSI2DC can act a simple bypass bridge if the incoming data is coming from a parallel interface. CSI2DC provides two pipes, one video pipe and one data pipe. Video pipe is connected at the output to a sensor controller and the data pipe is accessible as a DMA slave port to a DMA controller. CSI2DC supports a single 'port' node as a sink port with either Synopsys 32-bit IDI interface or a parallel interface. CSI2DC supports one 'port' node as source port with parallel interface. This is called video pipe. This port has an 'endpoint' that can be connected to a sink port of another controller (next in pipeline). CSI2DC also supports direct access to the data through AHB, via DMA channel, called data pipe. For data pipe to be available, a dma controller...

The `compatible` property uses single `const` and accepts `microchip,sama7g5-csi2dc`. Top-level required properties are `compatible`, `reg`, `clocks`, `clock-names`, `ports`; required names across nested/conditional schemas include `clock-names`, `clocks`, `compatible`, `port@0`, `port@1`, `ports`, `reg`. Top-level properties are `compatible`, `reg`, `clocks`, `clock-names`, `dmas`, `dma-names`, `ports`; all nested property names include `bus-type`, `bus-width`, `clock-names`, `clock-noncontinuous`, `clocks`, `compatible`, `dma-names`, `dmas`, `endpoint`, `port@0`, `port@1`, `ports`, `reg`, `remote-endpoint`. Resource constraints visible in the schema include `compatible` (const=microchip,sama7g5-csi2dc), `reg` (maxItems=1), `clocks` (minItems=2; maxItems=2), `clock-names` (names=pclk/scck), `dmas` (maxItems=1), `dma-names` (const=rx), `ports`. Closure is `additionalProperties: False`.

**Control flow:** Runtime control flow is supplied by dt-schema and kernel probing. `dt_binding_check` loads the core meta-schema, resolves references, validates the compatible form, applies required lists and `minItems`/`maxItems`/`const` restrictions, evaluates conditionals, and compiles the inline examples. At boot the DTB node is matched by `compatible`; the platform or media driver then reads MMIO ranges, named interrupts, clocks, resets, power domains, IOMMU streams, DMA/interconnect paths, firmware or reserved-memory phandles, and graph endpoints. There are no compatible-specific conditional branches beyond direct property validation. Media graph integration is explicit through `port@0`, `port@1`; the schema references graph/video interface rules and mentions `endpoint` 13 time(s). Endpoint validation covers remote links, lane descriptions, bus type, bus width, and synchronization/pixel-clock polarity where the hardware exposes those signals.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence itself. Its persistent effect is ABI stability for DTS files and shipped DTBs: compatible strings, child-node names, phandle relationships, address ranges, cell counts, and media graph topology are long-lived hardware descriptions. Any change to required properties, resource ordering, child object schemas, or unknown-property policy can invalidate existing board descriptions even though no kernel state is written by the YAML.

**Dependencies and integration points:** Direct schema references are `/schemas/graph.yaml#/$defs/port-base`, `/schemas/graph.yaml#/properties/ports`, `video-interfaces.yaml#`. Runtime dependencies are V4L2 async/media-controller graph links through `ports`, `port`, and `endpoint` nodes, clock provider phandles and fixed clock-name ordering, DMA slave channel provider. No nested object nodes are defined beyond common schema references. Maintainers listed in the binding are `Eugen Hristev <eugen.hristev@microchip.com>`.

**Risks:** Key risks: compatible-string or fallback-order drift can break OF matching and dtbs_check expectations; resource array ordering is ABI-sensitive for `reg-names`, `clock-names`, `interrupt-names`, `power-domain-names`, and `reset-names`; media graph mistakes in `remote-endpoint`, lane numbering, bus type, or required ports can leave cameras disconnected even when the platform device probes. The closure policy is `additionalProperties: False`, so unknown properties are intentionally rejected after referenced schemas are evaluated.
