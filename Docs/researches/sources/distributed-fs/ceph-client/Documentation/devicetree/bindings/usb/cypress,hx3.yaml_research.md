# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/usb/cypress,hx3.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/usb/cypress,hx3.yaml` defines `Cypress HX3 USB 3.0 hub controller family`, a USB hub binding. It is declarative firmware ABI documentation and dt-schema validation input; Linux does not execute this YAML at runtime, but the schema controls which DTS nodes are accepted for the corresponding hardware or bus-attached device.

## Important APIs, Types, and Functions
The exported API is the Devicetree node contract. `$id` is `http://devicetree.org/schemas/usb/cypress,hx3.yaml#` and `$schema` is `http://devicetree.org/meta-schemas/core.yaml#`. `compatible` uses `oneOf` with 3 accepted forms and exposes 8 compatible tokens: `usb4b4,6504`, `usb4b4,6506`, `usb4b4,6500`, `usb4b4,6508`, `usb4b4,6502`, `usb4b4,6503`, `usb4b4,6507`, `usb4b4,650a`. Top-level properties are `compatible`, `reg`, `reset-gpios`, `vdd-supply`, `vdd2-supply`, `peer-hub`. Top-level required properties are `compatible`, `reg`, `peer-hub`, `vdd-supply`, `vdd2-supply`; required properties discovered in nested branches are `compatible`, `peer-hub`, `reg`, `vdd-supply`, `vdd2-supply`. Patterned child schemas are none; local definitions are none. Resource/provider roles: `compatible` selects schema applicability and the kernel OF match-table entry; `reg` describes MMIO windows, bus addresses, or register resources; `reset-gpios` describes GPIO control/status wiring; `vdd-supply` connects regulator supplies; `vdd2-supply` connects regulator supplies. Across the full schema there are 6 distinct property names and collected const/enum/min/max/item signals include `enum=[usb4b4,6504, usb4b4,6506]`, `enum=[usb4b4,6500, usb4b4,6508]`, `const=usb4b4,6504`, `enum=[usb4b4,6502, usb4b4,6503, usb4b4,6507, usb4b4,650a]`, `const=usb4b4,6506`.

## Control Flow
Control flow is schema evaluation. `dt_binding_check` parses the YAML, validates the meta-schema, resolves `$ref` links, applies `properties`, `patternProperties`, required lists, item counts, const/enum checks, and composition or conditional blocks (`allOf`); it also compiles the embedded examples. `dtbs_check` applies the same rules to compiled board DTBs. During boot the kernel only consumes the DTB: OF matching selects the driver, platform/bus code maps resources, phandles are resolved, and the driver performs hardware setup.

## State and Persistence Behavior
The file has no mutable runtime state and performs no persistence. Its durable state is ABI shape: compatible strings, property names, child-node names, phandle cell counts, register and interrupt ordering, resource names, and example topology. Runtime behavior is owned by matched drivers and hardware: hub reset/configuration state, port power and connect status, over-current handling, and USB device enumeration state. Schema edits therefore persist as compatibility commitments for existing DTS files even though no code path is stored here.

## Risks
Main risks are ABI drift around hub compatible identity, reset and supply timing, downstream-port topology, peer-hub phandles, and vendor configuration properties; changing compatible ordering or removing fallback strings; broadening a schema so invalid board nodes pass; tightening a schema so existing DTBs fail; and mismatches between YAML clock/reset/regulator/PHY names and driver lookup tables. Multi-role USB and Type-C bindings are especially sensitive to graph endpoints, role-switch dependencies, connector children, and wakeup semantics. UFS bindings are sensitive to per-SoC clock arrays, ICE register resources, PHY lane counts, and reset/power sequencing. The closure profile rejects undeclared top-level properties with `additionalProperties: false`.

## Test Signals

Useful negative tests remove each required property, scramble compatible fallback order, use bad child-node names, provide too many/few clocks, resets, interrupts, PHYs, or register windows, and add undeclared properties when the schema is closed.
