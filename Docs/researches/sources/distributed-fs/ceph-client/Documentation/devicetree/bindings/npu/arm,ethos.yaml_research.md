# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/npu/arm,ethos.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/npu/arm,ethos.yaml` defines the Linux Devicetree YAML schema for `Arm Ethos U65/U85`, a neural processing unit binding. The schema description says: The Arm Ethos-U NPUs are designed for IoT inference applications. The NPUs can accelerate 8-bit and 16-bit integer quantized networks: Transformer networks (U85 only) Convolutional Neural Networks (CNN) Recurrent Neural Networks (RNN) Further documentation is available here: U65 TRM: https://developer.arm.com/documentation/102023/ U85 TRM: https://developer.arm.com/documentation/102685/ It is declarative ABI documentation and validation input rather than executable kernel code; its practical role is to make DTS/DTB hardware descriptions match the resources, topology, and compatible strings expected by the relevant kernel subsystem before probe.

## Important APIs, Types, and Functions
The public API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses `oneOf` with 2 branchs and exposes 4 tokens: `fsl,imx93-npu`, `arm,ethos-u65`, `arm,corstone1000-ethos-u85`, `arm,ethos-u85`. Top-level properties are `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `power-domains`, `sram`. Top-level required properties are `compatible`, `reg`, `interrupts`, `clocks`; required properties collected from nested schema branches include `clocks`, `compatible`, `interrupts`, `reg`. Patterned child schemas are none. Numeric and collection constraints include `maxItems=1`, `maxItems=2`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `reg` describes MMIO ranges, bus child addresses, port selectors, or cell offsets; `interrupts` routes status, error, RX/TX, MSI, or completion IRQs; `clocks` integrates with common clock, reset, PM, DMA/IOMMU, or reserved-memory providers; `clock-names` fixes resource ordering visible to drivers; `power-domains` integrates with common clock, reset, PM, DMA/IOMMU, or reserved-memory providers. The highest-risk ABI details are compute-core compatible identity, MMIO region layout, IRQ ordering, power/clock/reset dependencies, IOMMU stream IDs, SRAM or memory-region phandles, and per-core child topology.

## Control Flow
Runtime control flow is supplied by dt-schema and kernel subsystem code, not by this YAML file. `dt_binding_check` loads the meta-schema, resolves `$ref` entries, applies `properties`, evaluates no top-level conditionals, checks required fields, validates `minItems`/`maxItems` and enum/const constraints, validates embedded examples, and applies the closure rule. During boot, the compiled DTB node is matched by `compatible`; then platform, PCI, SDIO, SPI, MDIO, NVMEM, OPP, PCIe, netdev, wireless, accelerator, storage, clock, reset, regulator, IRQ, GPIO, IOMMU, and power-domain helpers consume the phandles and resource arrays that this schema validates. Child nodes are discovered declaratively through fixed names, pattern properties, address cells, and referenced child schemas.

## State and Persistence Behavior
The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: compatible strings, required resource names, register and interrupt ordering, phandle and cell counts, child-node names, fallback ordering, and example layouts become long-lived contracts in board DTS files and shipped DTBs. Runtime state belongs to the matching drivers and hardware after probe, including accelerator probe, job queue state, MMU/IOMMU mappings, firmware or microcode state, power-gated core state, and interrupt-driven command completion.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, link training, calibration lookup, OPP selection, NVMEM cell reads, or bus enumeration. Tightening required properties can reject existing boards; loosening them can hide missing clocks, resets, interrupts, supplies, PHY links, PCIe windows, memory regions, OPP fields, or NVMEM cells. Child-node schemas need special care because address cells, port IDs, PCI interrupt maps, wireless calibration cells, NVMEM layouts, and OPP tables must match driver-side assumptions. This schema rejects unknown top-level properties with `additionalProperties: false`. It has 7 top-level properties and 7 distinct nested property names, so broad edits should be checked against all compatible variants and DTS users, not just the nominal filename.

## Test Signals
Run `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/npu/arm,ethos.yaml` for targeted schema validation and `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/npu/arm,ethos.yaml` against boards using these nodes. High-value negative checks remove required properties, use invalid compatible fallbacks, corrupt `reg` or interrupt counts, misspell vendor properties, violate child-node address-cell rules, and exercise every conditional branch. Runtime integration signals are successful driver probe, correct subsystem registration, valid NVMEM/OPP/PCIe/wireless/netdev/accelerator/storage behavior as applicable, clean interrupt/reset/power sequencing, and no new dtbs_check failures in embedded examples or in-tree DTS users.
