# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interconnect/qcom,bcm-voter.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interconnect/qcom,bcm-voter.yaml` is a Linux devicetree YAML schema for the `Qualcomm BCM-Voter Interconnect` Qualcomm interconnect provider binding. The Bus Clock Manager (BCM) is a dedicated hardware accelerator that manages shared system resources by aggregating requests from multiple Resource State Coordinators (RSC). Interconnect providers are able to vote for aggregated thresholds values from consumers by communicating through their respective RSCs. It is not executable kernel code; it is the hardware-description ABI that DTS authors, dt-schema, and the relevant kernel subsystem rely on so the runtime driver can parse the node without board-specific ambiguity.

## Important APIs, Types, and Functions
The public API surface is the schema's accepted node shape. `compatible` uses `enum` list and covers 1 compatible token: `qcom,bcm-voter`. Top-level properties are `compatible`, `qcom,tcs-wait`. Across nested schemas and child nodes this file mentions 2 distinct property names; nested/all required properties include `compatible`. Node naming is constrained by no explicit node-name constraint. Interconnect-facing properties define a provider node for the Linux interconnect framework and related devfreq/OPP consumers: addressing resources none, provider cells none, clocks/power/OPP hooks none, and SoC/vendor topology knobs `qcom,tcs-wait`. Required properties are `compatible`; consumer nodes depend on these cells and phandles to vote bandwidth or performance state.

## Control Flow, State, and Persistence
Control flow is declarative JSON-schema evaluation rather than executable branching. `dt-doc-validate` and `dt_binding_check` load the YAML, expand `$ref` links, apply composition and conditional keywords, validate the DTS example blocks, and later `dtbs_check` applies the same contract to compiled board devicetrees. For interconnect providers, validation ensures that provider cells, register banks, clocks, power domains, BCM voter links, and OPP or devfreq relationships are well-formed before Linux interconnect providers register bandwidth paths consumed by other device nodes. The schema itself stores no mutable state and writes no persistent data; its persistence is the stable source-controlled hardware ABI. External references used in evaluation are `/schemas/types.yaml#/definitions/uint32`; top-level/nested conditional keywords present are none.

## Risks
Risks are mostly ABI and validation risks rather than algorithmic failures. Tightening required properties, changing compatible ordering, renaming resources, altering cell counts, or closing extra properties can reject existing DTS users; loosening constraints can allow nodes that later fail driver probe or misdescribe hardware. This schema has 2 top-level properties and 2 distinct nested property names, with strictness profile: unknown top-level properties are rejected. Conditional branches and shared `$ref` schemas should be checked against all in-tree users before edits, because a schema-only patch can still break board builds.

## Test Signals
Primary validation is `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/interconnect/qcom,bcm-voter.yaml` plus `make dtbs_check` on in-tree boards using `qcom,bcm-voter`. The 2 example blocks in this file should compile under dt-schema and remain representative of the required properties. Useful integration signals include successful interconnect provider registration, consumer bandwidth votes, devfreq/OPP transitions, clock and power-domain enablement, and no `dtbs_check` regressions for SoC DTSI files that include the provider topology.
