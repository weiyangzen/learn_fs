## Control Flow
Control flow is schema evaluation. `dt_binding_check` parses the YAML, validates the meta-schema, resolves `$ref` links, applies `properties`, `patternProperties`, required lists, item counts, const/enum checks, and composition or conditional blocks (`allOf`, `dependencies`); it also compiles the embedded examples. `dtbs_check` applies the same rules to compiled board DTBs. During boot the kernel only consumes the DTB: OF matching selects the driver, platform/bus code maps resources, phandles are resolved, and the driver performs hardware setup.

## Risks
Main risks are ABI drift around compatible strings, MMIO windows, interrupt resources, PHY phandles, clock/reset ordering, power supplies, and vendor-specific controller quirks; changing compatible ordering or removing fallback strings; broadening a schema so invalid board nodes pass; tightening a schema so existing DTBs fail; and mismatches between YAML clock/reset/regulator/PHY names and driver lookup tables. Multi-role USB and Type-C bindings are especially sensitive to graph endpoints, role-switch dependencies, connector children, and wakeup semantics. UFS bindings are sensitive to per-SoC clock arrays, ICE register resources, PHY lane counts, and reset/power sequencing. The closure profile allows additional top-level properties.
