# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mtd/ti,gpmc-nand.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Texas Instruments GPMC NAND Flash controller.`. In this tree it is a MTD flash memory controller, flash chip, ECC engine, or common flash schema binding: it constrains how DTS authors describe hardware, and it gives Linux OF/platform code a stable ABI for matching drivers, acquiring resources, and validating board descriptions with dt-schema. The source description says: GPMC NAND controller/Flash is represented as a child of the GPMC controller node.

**Important APIs/types/functions:** This is declarative schema, not executable C code. The public interface is the binding ABI exposed through `$id` `http://devicetree.org/schemas/mtd/ti,gpmc-nand.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `description`, `maintainers`, `properties`, `required`, schema composition keywords, and inline `examples`. Compatible strings or match identifiers include `ti,am64-nand`, `ti,omap2-nand`. Top-level required properties are `compatible`, `reg`, `ti,nand-ecc-opt`. Important properties include `compatible`, `reg`, `interrupts`, `#address-cells`, `#size-cells`, `ti,nand-ecc-opt`, `ti,nand-xfer-type`, `ti,elm-id`, `nand-bus-width`, `rb-gpios`. Property roles include `compatible`: driver match key and stable hardware ABI identifier; `reg`: MMIO, bus address, flash-chip select, or child register window; `interrupts`: interrupt line routing; `#address-cells`: child address cell width; `#size-cells`: child size cell width; `ti,nand-ecc-opt`: Desired ECC algorithm; `ti,nand-xfer-type`: Data transfer method between controller and chip.; `ti,elm-id`: phandle to the ELM (Error Location Module).; `nand-bus-width`: Bus width to the NAND chip; `rb-gpios`: GPIO connection to R/B signal from NAND chip. Direct or nested schema references include `/schemas/types.yaml#/definitions/string`, `/schemas/types.yaml#/definitions/phandle`, `/schemas/types.yaml#/definitions/uint32`, `/schemas/memory-controllers/ti,gpmc-child.yaml`, `mtd.yaml#`. The top-level closure policy is `unevaluatedProperties: false`. Maintainers: Tony Lindgren <tony@atomide.com>, Roger Quadros <rogerq@kernel.org>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and Linux subsystem drivers. `dt_binding_check` loads the core meta-schema, resolves references, evaluates `properties`, `required`, enum/const/items limits, and composition rules, then validates the examples. `dtbs_check` applies the same contract to compiled board DTBs. At boot, the flattened DT node is matched through `compatible` or inherited child-node context, the relevant driver parses resources such as MMIO ranges, interrupts, clocks, resets, regulators, PHYs, muxes, ECC engines, partitions, or child buses, and subsystem helpers enforce the generic parts of the contract. Schema composition/control branches in this file: allOf=1. Nested schema surface: no nested child-node schemas detected at the top level.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: accepted DTS/DTB nodes encode hardware identity, resource topology, child-node layout, and phandle cell widths for long-lived boards. Tightening `required`, changing compatible ordering, changing cell counts, or altering `additionalProperties`/`unevaluatedProperties` can break existing DTBs even though no state is stored by the YAML itself.

**Dependencies and integration points:** Integrates with MTD core, raw NAND/SPI-NOR/SPI-NAND/OneNAND/physmap drivers, ECC-engine providers, partition parsers, and nvmem/UBI consumers. Devicetree/dt-schema dependencies are the core meta-schema plus `/schemas/types.yaml#/definitions/string`, `/schemas/types.yaml#/definitions/phandle`, `/schemas/types.yaml#/definitions/uint32`, `/schemas/memory-controllers/ti,gpmc-child.yaml`, `mtd.yaml#`. Driver integration is through OF match tables and subsystem parsers; board integration is through phandles, address/size cells, interrupts, clocks, resets, regulators, power domains, child flash/partition nodes, MDIO/PHY links, mux specifiers, and examples that document expected DTS shape.

**Risks:** Main risks are ABI drift, under-specified compatibles, required resources that do not match real SoC integration, wrong `#*-cells` counts, stale examples, and conditional branches that validate one variant while rejecting another valid one. For storage bindings, partition/ECC/timing mistakes can silently corrupt flash or make media unprobeable. For network bindings, PHY mode, MDIO, reset, MAC-address, or clock mistakes can leave links down. For mux and common schemas, over-permissive closure can hide misspelled properties while over-tight closure can reject legitimate inherited properties.
