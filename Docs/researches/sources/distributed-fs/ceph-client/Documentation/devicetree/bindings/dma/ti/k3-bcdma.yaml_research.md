# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/dma/ti/k3-bcdma.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Texas Instruments K3 DMSS BCDMA`. In this tree it is a DMA engine, DMA router, or DMA-capable IP binding used by dmaengine providers and DMA client phandle specifiers; it constrains how board DTS files describe the hardware and how Linux drivers discover it through OF matching, phandles, and common binding references. The source description says: The Block Copy DMA (BCDMA) is intended to perform similar functions as the TR mode channels of K3 UDMA-P. BCDMA includes block copy channels and Split channels. Block copy channels mainly used for memory to memory transfers, but with optional triggers a block copy channel can service peripherals by accessing directly to memory mapped registers or area. **Important APIs/types/functions:** This is declarative schema rather than executable code. The public ABI surface is `$id` `http://devicetree.org/schemas/dma/ti/k3-bcdma.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and the referenced schemas used by dt-schema. Compatible strings are `ti,am62a-dmss-bcdma-csirx`, `ti,am64-dmss-bcdma`, `ti,j721s2-dmss-bcdma-csi`, `ti,j722s-dmss-bcdma-csi`. Required properties are `compatible`, `#dma-cells`, `reg`, `reg-names`, `msi-parent`, `ti,sci`, `ti,sci-dev-id`, `ti,sci-rm-range-rchan`. Important properties include `compatible`, `reg`, `reg-names`, `#dma-cells`, `msi-parent`, `power-domains`, `ti,asel`, `ti,sci-rm-range-bchan`, `ti,sci-rm-range-tchan`, `ti,sci-rm-range-rchan`. Referenced schemas are `/schemas/types.yaml#/definitions/uint32`, `/schemas/types.yaml#/definitions/uint32-array`, `/schemas/dma/dma-controller.yaml#`, `/schemas/arm/keystone/ti,k3-sci-common.yaml#`. Property roles include `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address; `#dma-cells` for DMA client specifier width; `power-domains` for power-domain attachment. The top-level closure rule is `unevaluatedProperties: false`. Maintainers: Peter Ujfalusi <peter.ujfalusi@gmail.com>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel subsystems, not by this YAML file. `dt_binding_check` loads the core meta-schema, resolves references such as `/schemas/types.yaml#/definitions/uint32`, `/schemas/types.yaml#/definitions/uint32-array`, `/schemas/dma/dma-controller.yaml#`, `/schemas/arm/keystone/ti,k3-sci-common.yaml#`, applies `properties`, `required`, enum/const/items limits, and any `allOf` or conditional branches, then validates the inline examples. During boot, a matching DT node is compiled into the DTB, the kernel matches `compatible`, subsystem code reads cells and phandles, and the bound driver consumes resources such as genpd power domains, MSI interrupt domains, TI SCI firmware resource management. Conditional/schema-composition points include `allOf`, `conditional branches`, so different compatibles or child-node shapes can activate different required-property sets. Nested or patterned child schema surfaces include `ti,asel`, `ti,sci-rm-range-bchan`, `ti,sci-rm-range-tchan`, `ti,sci-rm-range-rchan`.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, resource topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though no kernel state is stored here.

**Dependencies and integration points:** Integrated with dmaengine and Devicetree DMA client code. Direct schema dependencies are `/schemas/types.yaml#/definitions/uint32`, `/schemas/types.yaml#/definitions/uint32-array`, `/schemas/dma/dma-controller.yaml#`, `/schemas/arm/keystone/ti,k3-sci-common.yaml#`; resource dependencies visible in the property set include genpd power domains, MSI interrupt domains, TI SCI firmware resource management. Driver integration is through `compatible`, while client/provider integration is through cell properties, phandle arrays, child schemas, and bus-standard properties declared or inherited here.

**Risks:** Main risks are schema ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, missing required clocks/resets/interrupts/power domains, stale examples, and conditional branches that accept one SoC variant while rejecting another valid one. Unknown-property policy also matters: `unevaluatedProperties: false` can either catch misspelled DTS properties or allow legacy extension points. For bindings with child nodes or graph/connector references, parent-child address-cell and port layout mistakes can pass driver review only if dtbs_check coverage is weak.
