# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/thead,c900-aclint-sswi.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `ACLINT Supervisor-level Software Interrupt Device`. In this tree it is an interrupt controller binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: The SSWI device is a part of the ACLINT device. It provides supervisor-level IPI functionality for a set of HARTs on a supported platforms. It provides a register to set an IPI (SETSSIP) for each HART connected to the SSWI device. See draft specification https://github.com/riscvarchive/riscv-aclint Following variants of the SSWI ACLINT supported, using dedicated compatible string - THEAD C900 - MIPS P8700

**Important APIs/types/functions:** This YAML is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/interrupt-controller/thead,c900-aclint-sswi.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and any referenced dt-schema fragments. Compatible strings or compatible-pattern values are `sophgo,sg2044-aclint-sswi`, `thead,c900-aclint-sswi`, `mips,p8700-aclint-sswi`, `anlogic,dr1v90-aclint-sswi`, `nuclei,ux900-aclint-sswi`. Required properties are `compatible`, `reg`, `#interrupt-cells`, `interrupt-controller`, `interrupts-extended`. Important top-level properties are `compatible`, `reg`, `#interrupt-cells`, `interrupt-controller`, `interrupts-extended`, `riscv,hart-indexes`. Direct and nested `$ref` dependencies are `/schemas/types.yaml#/definitions/uint32-array`. Property roles include `compatible` for driver match key and stable hardware ABI identifier; `reg` for MMIO range, bus address, or child register selector; `#interrupt-cells` for interrupt specifier cell count consumed by child/client nodes; `interrupt-controller` marks the node as an interrupt domain provider; `interrupts-extended` for expanded interrupt phandle/specifier array; `riscv,hart-indexes` for binding-specific property constrained by the schema. **Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. Schema composition/conditional keywords present: `allOf`, `else`, `if`, `oneOf`, `then`. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IRQ domain code uses it to translate DT interrupt specifiers into Linux IRQs and route them to an upstream parent domain. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as `reg`, `interrupts-extended`. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.
