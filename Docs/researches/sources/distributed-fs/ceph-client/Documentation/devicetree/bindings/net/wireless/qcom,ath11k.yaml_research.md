# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/net/wireless/qcom,ath11k.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/net/wireless/qcom,ath11k.yaml` defines the Linux Devicetree YAML schema for `Qualcomm Technologies ath11k wireless devices`, a wireless controller binding. The schema description says: These are dt entries for Qualcomm Technologies, Inc. IEEE 802.11ax devices, for example like AHB based IPQ8074. It is declarative ABI documentation and validation input rather than executable kernel code; its practical role is to make DTS/DTB hardware descriptions match the resources, topology, and compatible strings expected by the relevant kernel subsystem before probe.

## Important APIs, Types, and Functions
The public API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses an `enum` and exposes 4 tokens: `qcom,ipq8074-wifi`, `qcom,ipq6018-wifi`, `qcom,wcn6750-wifi`, `qcom,ipq5018-wifi`. Top-level properties are `compatible`, `reg`, `interrupts`, `interrupt-names`, `qcom,rproc`, `qcom,calibration-variant`, `qcom,ath11k-calibration-variant`, `memory-region`, `iommus`, `ieee80211-freq-limit`, `wifi-firmware`, `qcom,smem-states`, `qcom,smem-state-names`. Top-level required properties are `compatible`, `reg`, `interrupts`, `qcom,rproc`; required properties collected from nested schema branches include `compatible`, `interrupt-names`, `interrupts`, `iommus`, `qcom,rproc`, `reg`. Patterned child schemas are none. Numeric and collection constraints include `maxItems=1`, `minItems=32`, `maxItems=52`, `minItems=1`, `maxItems=2`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `reg` describes MMIO ranges, bus child addresses, port selectors, or cell offsets; `interrupts` routes status, error, RX/TX, MSI, or completion IRQs; `interrupt-names` fixes resource ordering visible to drivers; `memory-region` integrates with common clock, reset, PM, DMA/IOMMU, or reserved-memory providers; `iommus` integrates with common clock, reset, PM, DMA/IOMMU, or reserved-memory providers. The highest-risk ABI details are compatible identity, bus address, interrupt or wake wiring, calibration and OTP/NVMEM references, firmware names, frequency limits, power limits, and vendor board-data properties.

## Control Flow
Runtime control flow is supplied by dt-schema and kernel subsystem code, not by this YAML file. `dt_binding_check` loads the meta-schema, resolves `$ref` entries, applies `properties`, evaluates `allOf`, checks required fields, validates `minItems`/`maxItems` and enum/const constraints, validates embedded examples, and applies the closure rule. During boot, the compiled DTB node is matched by `compatible`; then platform, PCI, SDIO, SPI, MDIO, NVMEM, OPP, PCIe, netdev, wireless, accelerator, storage, clock, reset, regulator, IRQ, GPIO, IOMMU, and power-domain helpers consume the phandles and resource arrays that this schema validates. Child nodes are discovered declaratively through fixed names, pattern properties, address cells, and referenced child schemas.

## State and Persistence Behavior
The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: compatible strings, required resource names, register and interrupt ordering, phandle and cell counts, child-node names, fallback ordering, and example layouts become long-lived contracts in board DTS files and shipped DTBs. Runtime state belongs to the matching drivers and hardware after probe, including wireless device probe, firmware boot, regulatory/channel capability selection, calibration selection, IRQ/wake state, netdev/wiphy registration, and runtime PM.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, link training, calibration lookup, OPP selection, NVMEM cell reads, or bus enumeration. Tightening required properties can reject existing boards; loosening them can hide missing clocks, resets, interrupts, supplies, PHY links, PCIe windows, memory regions, OPP fields, or NVMEM cells. Child-node schemas need special care because address cells, port IDs, PCI interrupt maps, wireless calibration cells, NVMEM layouts, and OPP tables must match driver-side assumptions. This schema rejects unknown top-level properties with `additionalProperties: false`. It has 13 top-level properties and 13 distinct nested property names, so broad edits should be checked against all compatible variants and DTS users, not just the nominal filename.

## Test Signals
Run `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/net/wireless/qcom,ath11k.yaml` for targeted schema validation and `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/net/wireless/qcom,ath11k.yaml` against boards using these nodes. High-value negative checks remove required properties, use invalid compatible fallbacks, corrupt `reg` or interrupt counts, misspell vendor properties, violate child-node address-cell rules, and exercise every conditional branch. Runtime integration signals are successful driver probe, correct subsystem registration, valid NVMEM/OPP/PCIe/wireless/netdev/accelerator/storage behavior as applicable, clean interrupt/reset/power sequencing, and no new dtbs_check failures in embedded examples or in-tree DTS users.
