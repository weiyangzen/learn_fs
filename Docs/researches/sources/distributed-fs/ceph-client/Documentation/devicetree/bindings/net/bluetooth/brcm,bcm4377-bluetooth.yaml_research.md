# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/net/bluetooth/brcm,bcm4377-bluetooth.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Broadcom BCM4377 family PCIe Bluetooth Chips`. In this tree it is a Bluetooth controller or common Bluetooth transport binding binding: it constrains how DTS authors describe hardware, and it gives Linux OF/platform code a stable ABI for matching drivers, acquiring resources, and validating board descriptions with dt-schema. The source description says: This binding describes Broadcom BCM4377 family PCIe-attached bluetooth chips usually found in Apple machines. The Wi-Fi part of the chip is described in bindings/net/wireless/brcm,bcm4329-fmac.yaml.

**Important APIs/types/functions:** This is declarative schema, not executable C code. The public interface is the binding ABI exposed through `$id` `http://devicetree.org/schemas/net/bluetooth/brcm,bcm4377-bluetooth.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `description`, `maintainers`, `properties`, `required`, schema composition keywords, and inline `examples`. Compatible strings or match identifiers include `pci14e4,5fa0`, `pci14e4,5f69`, `pci14e4,5f71`, `pci14e4,5f72`. Top-level required properties are `compatible`, `reg`, `local-bd-address`, `brcm,board-type`. Important properties include `compatible`, `reg`, `brcm,board-type`, `brcm,taurus-cal-blob`, `brcm,taurus-bf-cal-blob`, `local-bd-address`. Property roles include `compatible`: driver match key and stable hardware ABI identifier; `reg`: MMIO, bus address, flash-chip select, or child register window; `brcm,board-type`: Board type of the Bluetooth chip. This is used to decouple the overall system board from the Bluetooth module and used to construct firmware and calibration data filenames. On Apple platforms, this should be the Apple module-instance codename prefixed by "apple,", e.g. "apple,atlantisb".; `brcm,taurus-cal-blob`: A per-device calibration blob for the Bluetooth radio. This should be filled in by the bootloader from platform configuration data, if necessary, and will be uploaded to the device. This blob is used if the chip stepping of the Bluetooth module does not support beamforming.; `brcm,taurus-bf-cal-blob`: A per-device calibration blob for the Bluetooth radio. This should be filled in by the bootloader from platform configuration data, if necessary, and will be uploaded to the device. This blob is used if the chip stepping of the Bluetooth module supports beamforming.; `local-bd-address`: schema-constrained Devicetree property. Direct or nested schema references include `bluetooth-controller.yaml#`, `/schemas/types.yaml#/definitions/string`, `/schemas/types.yaml#/definitions/uint8-array`. The top-level closure policy is `additionalProperties: false`. Maintainers: Sven Peter <sven@svenpeter.dev>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and Linux subsystem drivers. `dt_binding_check` loads the core meta-schema, resolves references, evaluates `properties`, `required`, enum/const/items limits, and composition rules, then validates the examples. `dtbs_check` applies the same contract to compiled board DTBs. At boot, the flattened DT node is matched through `compatible` or inherited child-node context, the relevant driver parses resources such as MMIO ranges, interrupts, clocks, resets, regulators, PHYs, muxes, ECC engines, partitions, or child buses, and subsystem helpers enforce the generic parts of the contract. Schema composition/control branches in this file: allOf=1. Nested schema surface: no nested child-node schemas detected at the top level.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: accepted DTS/DTB nodes encode hardware identity, resource topology, child-node layout, and phandle cell widths for long-lived boards. Tightening `required`, changing compatible ordering, changing cell counts, or altering `additionalProperties`/`unevaluatedProperties` can break existing DTBs even though no state is stored by the YAML itself.

**Dependencies and integration points:** Integrates with Bluetooth HCI transport drivers, serdev/UART or PCI/platform glue, GPIO, regulator, clock, and firmware-name consumers. Devicetree/dt-schema dependencies are the core meta-schema plus `bluetooth-controller.yaml#`, `/schemas/types.yaml#/definitions/string`, `/schemas/types.yaml#/definitions/uint8-array`. Driver integration is through OF match tables and subsystem parsers; board integration is through phandles, address/size cells, interrupts, clocks, resets, regulators, power domains, child flash/partition nodes, MDIO/PHY links, mux specifiers, and examples that document expected DTS shape.

**Risks:** Main risks are ABI drift, under-specified compatibles, required resources that do not match real SoC integration, wrong `#*-cells` counts, stale examples, and conditional branches that validate one variant while rejecting another valid one. For storage bindings, partition/ECC/timing mistakes can silently corrupt flash or make media unprobeable. For network bindings, PHY mode, MDIO, reset, MAC-address, or clock mistakes can leave links down. For mux and common schemas, over-permissive closure can hide misspelled properties while over-tight closure can reject legitimate inherited properties.
