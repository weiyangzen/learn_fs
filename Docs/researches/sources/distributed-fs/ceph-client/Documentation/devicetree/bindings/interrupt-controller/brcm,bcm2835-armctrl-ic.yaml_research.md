# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/brcm,bcm2835-armctrl-ic.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/brcm,bcm2835-armctrl-ic.yaml` is a Linux devicetree YAML schema for the `BCM2835 ARMCTRL Interrupt Controller` interrupt-controller binding. The BCM2835 contains a custom top-level interrupt controller, which supports 72 interrupt sources using a 2-level register scheme. The interrupt controller, or the HW block containing it, is referred to occasionally as "armctrl" in the SoC documentation, hence naming of this binding. The BCM2836 contains the same interrupt controller with the same interrupts, but the per-CPU interrupt controller is the root, and an interrupt there indicates that the ARMCTRL has an interrupt to handle. The interrupt sources are as follows: Bank 0: 0: ARM_TIMER 1: ARM_MAILBOX 2: ARM_DOORBELL_0 3: ARM_DOORBELL_1 4: VPU0_HALTED 5: VPU1_HALTED 6: ILLEGAL_TYPE0 7: ILLEGAL_TYPE1 Bank 1: 0: TIMER0 1: TIMER1 2: TIMER2 3: TIMER3 4: CODEC0 5: CODEC1 6: CODEC2 7: VC_JPEG 8: ISP 9: VC_USB 10: VC_3D 11: TRANSPOSER 12: MULTICORESYNC0 13: MULTICORESYNC1 14: MULTICORES... It is not executable kernel code; it is the hardware-description ABI that DTS authors, dt-schema, and the relevant kernel subsystem rely on so the runtime driver can parse the node without board-specific ambiguity.

## Important APIs, Types, and Functions
The public API surface is the schema's accepted node shape. `compatible` uses `enum` list and covers 2 compatible tokens: `brcm,bcm2835-armctrl-ic`, `brcm,bcm2836-armctrl-ic`. Top-level properties are `compatible`, `reg`, `interrupt-controller`, `#interrupt-cells`, `interrupts`. Across nested schemas and child nodes this file mentions 5 distinct property names; nested/all required properties include `#interrupt-cells`, `compatible`, `interrupt-controller`, `interrupts`, `reg`. Node naming is constrained by no explicit node-name constraint. Interrupt-controller-facing properties define how child devices encode interrupt specifiers and how the kernel irqchip or MSI domain driver maps them: addressing resources `reg`, domain declarations `interrupt-controller`, `#interrupt-cells`, `interrupts`, clock/reset/power hooks none, and any GPIO or parent-domain links none. Required properties are `compatible`, `reg`, `interrupt-controller`, `#interrupt-cells`; the shape of `#interrupt-cells` and parent interrupt wiring is the main ABI exposed to DTS consumers.

## Control Flow, State, and Persistence
Control flow is declarative JSON-schema evaluation rather than executable branching. `dt-doc-validate` and `dt_binding_check` load the YAML, expand `$ref` links, apply composition and conditional keywords, validate the DTS example blocks, and later `dtbs_check` applies the same contract to compiled board devicetrees. For irqchip and MSI providers, validation ensures the interrupt domain, specifier cell count, parent interrupt lines, MSI doorbells, and child-node encoding match what the kernel interrupt-controller driver will parse during early boot or bus enumeration. The schema itself stores no mutable state and writes no persistent data; its persistence is the stable source-controlled hardware ABI. External references used in evaluation are none; top-level/nested conditional keywords present are `allOf`, `else`, `if`, `then`.

## Risks
Risks are mostly ABI and validation risks rather than algorithmic failures. Tightening required properties, changing compatible ordering, renaming resources, altering cell counts, or closing extra properties can reject existing DTS users; loosening constraints can allow nodes that later fail driver probe or misdescribe hardware. This schema has 5 top-level properties and 5 distinct nested property names, with strictness profile: unknown top-level properties are rejected. Conditional branches and shared `$ref` schemas should be checked against all in-tree users before edits, because a schema-only patch can still break board builds.

## Test Signals
Primary validation is `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/interrupt-controller/brcm,bcm2835-armctrl-ic.yaml` plus `make dtbs_check` on in-tree boards using `brcm,bcm2835-armctrl-ic`, `brcm,bcm2836-armctrl-ic`. The 2 example blocks in this file should compile under dt-schema and remain representative of the required properties. Useful integration signals include irqchip/MSI domain registration during boot, correct parent IRQ routing, valid child interrupt specifier lengths, interrupt delivery tests from devices below the domain, and no early-boot warnings about missing cells, ranges, or register resources.
