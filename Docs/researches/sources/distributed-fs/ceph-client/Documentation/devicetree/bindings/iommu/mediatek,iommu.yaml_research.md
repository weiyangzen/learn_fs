# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/iommu/mediatek,iommu.yaml

**Purpose:** Defines the Linux Devicetree JSON-schema contract for `MediaTek IOMMU Architecture Implementation`. In this source tree it is a IOMMU provider or IOMMU-adjacent binding; it constrains board DTS/DTB nodes so kernel OF matching and subsystem code can discover the hardware resources consistently. This is declarative ABI documentation, not executable Ceph client code, but it is part of the imported kernel documentation corpus that protects hardware-description compatibility. The source description says: Some MediaTek SOCs contain a Multimedia Memory Management Unit (M4U), and this M4U have two generations of HW architecture. Generation one uses flat pagetable, and only supports 4K size page mapping. Generation two uses the ARM Short-Descriptor translation table format for address translation. About the M4U Hardware Block Diagram, please check below: EMI (External Memory Interface) | m4u (Multimedia Memory Management Unit) | +--------+ | | gals0-rx gals1-rx (Global Async Local Sync rx) | | | | gals0-tx gals1-tx (Global Async Local Sync tx) | | Some SoCs may have GALS. +--------+ | SMI Common(Smart Multimedia Interface Common) | +----------------+------- | | | gals-rx There may be GALS in some larbs. | | | | | gals-tx | | SMI larb0 SMI larb1 ... SoCs have several SMI local arbiter(larb). (display) (vdec) | | | | +-----+-----+ +----+----+ | | | | | | | | |... | | | ... There are different ports in each larb. | | | | | | OVL0 RDMA0 WDMA0 MC PP VLD As above, The Multimedia HW will go through SMI and M4U while it access EMI. SMI is a bridge between m4u and the Multimedia HW. It contain smi local arbiter and smi common. It will control whether the Multimedia HW should go through the m4u for translation or bypass it and talk directly with EMI. And also SMI help control the power domain and clocks for each local arbiter. Normally we specify a local arbiter(larb) for each multimedia HW like display, video decode, and camera. And there are different ports in each larb. Take a example, There are many ports like MC, PP, VLD in the video decode local arbiter, all these ports are according to the video HW. In some SoCs, there may be a GALS(Global Async Local Sync) module between smi-common and m4u, and additional GALS module between smi-larb and smi-common. GALS can been seen as a "asynchronous fifo" which could help synchronize for the modules in different clock frequency.

**Important APIs/types/functions:** The public surface is the schema itself: `$id` `http://devicetree.org/schemas/iommu/mediatek,iommu.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, composition keywords, closure rules, and `examples` consumed by `dt-schema`. Important top-level properties include `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `mediatek,infracfg`, `mediatek,larbs`, `#iommu-cells`, `power-domains`. **Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel drivers rather than by this YAML. `dt_binding_check` loads the core meta-schema, resolves `$ref` dependencies, applies constants/enums/cardinality/range checks, evaluates composition and conditional branches (`oneOf`, `allOf`, `if`, `then`, `not`), and validates the embedded examples. At boot, the compiled DTB node is matched by `compatible`; the relevant IOMMU driver or common subsystem reads resource properties, phandles, child nodes, and cells before registering devices or provider relationships. Child/provider surfaces to watch here are none declared.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistence is ABI persistence: accepted DTS nodes encode hardware identity, register windows, interrupts, power/clock/reset topology, phandle cell widths, channel indexes, and child LED/IOMMU/IPMI layout for long-lived boards. Tightening `required`, changing compatible fallback order, altering cell counts, or changing closure policy can reject existing DTBs or make drivers parse resources differently.

**Dependencies and integration points:** Integrated with IOMMU stream IDs, DMA translation, device isolation, and `iommus`/`#iommu-cells` style phandle integration. Schema dependencies include `/schemas/types.yaml#/definitions/phandle`, `/schemas/types.yaml#/definitions/phandle-array`; examples may also include dt-bindings headers. Resource integration is through properties such as `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address; `interrupts` for interrupt routing; `clocks` for clock provider phandles; `clock-names` for named clock inputs; `power-domains` for genpd power-domain attachment; `#iommu-cells` for IOMMU client specifier cell count. Driver integration is through `compatible`, while subsystem integration is through phandle arrays, provider cell counts, common schemas, and child-node schemas inherited or declared here.

**Risks and edge cases:** Main risks are schema ABI drift, missing or stale compatible coverage, incorrect min/max item constraints, wrong `#*-cells` values, resource names that diverge from driver expectations, conditionals that validate one SoC or chip variant while rejecting another valid one, and examples that no longer reflect real DTS users. Closure policy (`additionalProperties: false`) is useful for catching misspellings but can also block legitimate extensions. For LED/backlight children, channel numbering and `reg`/`led-sources` constraints are common failure points; for IOMMU bindings, stream IDs and cell widths are especially sensitive; for IPMI bindings, host/BMC address and register-resource shape must match the driver.
