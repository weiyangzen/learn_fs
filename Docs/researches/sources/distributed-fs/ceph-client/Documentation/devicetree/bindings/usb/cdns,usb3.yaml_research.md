# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/usb/cdns,usb3.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/usb/cdns,usb3.yaml` defines `Cadence USBSS-DRD controller`, a USB3/xHCI or dual-role controller binding. It is declarative firmware ABI documentation and dt-schema validation input; Linux does not execute this YAML at runtime, but the schema controls which DTS nodes are accepted for the corresponding hardware or bus-attached device.

## Important APIs, Types, and Functions
The exported API is the Devicetree node contract. `$id` is `http://devicetree.org/schemas/usb/cdns,usb3.yaml#` and `$schema` is `http://devicetree.org/meta-schemas/core.yaml#`. `compatible` uses single `const` and exposes 1 compatible token: `cdns,usb3`. Top-level properties are `compatible`, `reg`, `reg-names`, `interrupts`, `interrupt-names`, `port`, `maximum-speed`, `phys`, `phy-names`, `cdns,on-chip-buff-size`, `cdns,phyrst-a-enable`. Top-level required properties are `compatible`, `reg`, `reg-names`, `interrupts`, `interrupt-names`; required properties discovered in nested branches are `compatible`, `interrupt-names`, `interrupts`, `reg`, `reg-names`. Patterned child schemas are none; local definitions are none. Resource/provider roles: `compatible` selects schema applicability and the kernel OF match-table entry; `reg` describes MMIO windows, bus addresses, or register resources; `reg-names` fixes semantic ordering for multiple register windows; `interrupts` maps controller, GPIO, or Type-C events into IRQ domains; `interrupt-names` maps controller, GPIO, or Type-C events into IRQ domains; `port` models USB dual-role, Type-C, or graph topology; `phys` connects USB/UFS controllers to PHY providers or exposes a PHY provider; `phy-names` connects USB/UFS controllers to PHY providers or exposes a PHY provider. Across the full schema there are 11 distinct property names and collected const/enum/min/max/item signals include `const=cdns,usb3`, `const=otg`, `const=xhci`, `const=dev`, `minItems=3`, `const=host`, `const=peripheral`, `const=wakeup`, `enum=[super-speed, high-speed, full-speed]`, `minItems=1`, `maxItems=2`, `const=cdns3,usb2-phy`, `const=cdns3,usb3-phy`.

## Control Flow
Control flow is schema evaluation. `dt_binding_check` parses the YAML, validates the meta-schema, resolves `$ref` links, applies `properties`, `patternProperties`, required lists, item counts, const/enum checks, and composition or conditional blocks (`allOf`, `dependencies`); it also compiles the embedded examples. `dtbs_check` applies the same rules to compiled board DTBs. During boot the kernel only consumes the DTB: OF matching selects the driver, platform/bus code maps resources, phandles are resolved, and the driver performs hardware setup.

## State and Persistence Behavior
The file has no mutable runtime state and performs no persistence. Its durable state is ABI shape: compatible strings, property names, child-node names, phandle cell counts, register and interrupt ordering, resource names, and example topology. Runtime behavior is owned by matched drivers and hardware: host/gadget/OTG role, endpoint/transfer rings, event interrupts, runtime PM, PHY state, wakeup behavior, and controller reset/recovery state. Schema edits therefore persist as compatibility commitments for existing DTS files even though no code path is stored here.

## Risks
Main risks are ABI drift around controller compatible strings, register and interrupt ordering, PHY arrays, `dr_mode`, role-switch wiring, clock/reset names, child-port layout, and vendor quirk properties; changing compatible ordering or removing fallback strings; broadening a schema so invalid board nodes pass; tightening a schema so existing DTBs fail; and mismatches between YAML clock/reset/regulator/PHY names and driver lookup tables. Multi-role USB and Type-C bindings are especially sensitive to graph endpoints, role-switch dependencies, connector children, and wakeup semantics. UFS bindings are sensitive to per-SoC clock arrays, ICE register resources, PHY lane counts, and reset/power sequencing. The closure profile closes composed schemas with `unevaluatedProperties: false`.

## Test Signals

Useful negative tests remove each required property, scramble compatible fallback order, use bad child-node names, provide too many/few clocks, resets, interrupts, PHYs, or register windows, and add undeclared properties when the schema is closed. Runtime signals are clean driver probe, expected PHY/role-switch/provider registration where applicable, correct device enumeration, suspend/resume without resource leaks, and no new schema warnings.
