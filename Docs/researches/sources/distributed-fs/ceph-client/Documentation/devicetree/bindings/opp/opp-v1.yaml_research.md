# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/opp/opp-v1.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/opp/opp-v1.yaml` defines the Linux Devicetree YAML schema for `Generic OPP (Operating Performance Points) v1`, a operating-points binding. The schema description says: Devices work at voltage-current-frequency combinations and some implementations have the liberty of choosing these. These combinations are called Operating Performance Points aka OPPs. This document defines bindings for these OPPs applicable across wide range of devices. For illustration purpose, this document uses CPU as a device. This binding only supports voltage-frequency pairs. It is declarative ABI documentation and validation input rather than executable kernel code; its practical role is to make DTS/DTB hardware descriptions match the resources, topology, and compatible strings expected by the relevant kernel subsystem before probe.

## Important APIs, Types, and Functions
The public API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses a composed compatible schema and exposes 0 tokens: no explicit compatible constants. Top-level properties are `clock-latency`, `voltage-tolerance`, `operating-points`. Top-level required properties are none declared at the top level; required properties collected from nested schema branches include none found. Patterned child schemas are none. Numeric and collection constraints include `maximum=10`. Important resource roles: properties are primarily direct dt-schema value constraints. The highest-risk ABI details are OPP table compatibility, `opp-hz`, voltage/current/microvolt arrays, level/performance-state values, supported-hw masks, turbo/suspend flags, named supplies, and required-opps links.

## Control Flow
Runtime control flow is supplied by dt-schema and kernel subsystem code, not by this YAML file. `dt_binding_check` loads the meta-schema, resolves `$ref` entries, applies `properties`, evaluates `dependencies`, checks required fields, validates `minItems`/`maxItems` and enum/const constraints, validates embedded examples, and applies the closure rule. During boot, the compiled DTB node is matched by `compatible`; then platform, PCI, SDIO, SPI, MDIO, NVMEM, OPP, PCIe, netdev, wireless, accelerator, storage, clock, reset, regulator, IRQ, GPIO, IOMMU, and power-domain helpers consume the phandles and resource arrays that this schema validates. Child nodes are discovered declaratively through fixed names, pattern properties, address cells, and referenced child schemas.

## State and Persistence Behavior
The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: compatible strings, required resource names, register and interrupt ordering, phandle and cell counts, child-node names, fallback ordering, and example layouts become long-lived contracts in board DTS files and shipped DTBs. Runtime state belongs to the matching drivers and hardware after probe, including registered OPP tables, enabled/disabled performance points, regulator voltage/current selection, clock-rate transitions, power-domain state votes, cooling state limits, and speed-bin filtering.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, link training, calibration lookup, OPP selection, NVMEM cell reads, or bus enumeration. Tightening required properties can reject existing boards; loosening them can hide missing clocks, resets, interrupts, supplies, PHY links, PCIe windows, memory regions, OPP fields, or NVMEM cells. Child-node schemas need special care because address cells, port IDs, PCI interrupt maps, wireless calibration cells, NVMEM layouts, and OPP tables must match driver-side assumptions. This schema allows unknown top-level properties. It has 3 top-level properties and 3 distinct nested property names, so broad edits should be checked against all compatible variants and DTS users, not just the nominal filename.
