# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/leds/register-bit-led.yaml

**Purpose:** Defines the Linux Devicetree JSON-schema contract for `Register Bit LEDs`. In this source tree it is a LED controller or common LED schema binding; it constrains board DTS/DTB nodes so kernel OF matching and subsystem code can discover the hardware resources consistently. This is declarative ABI documentation, not executable Ceph client code, but it is part of the imported kernel documentation corpus that protects hardware-description compatibility. The source description says: Register bit leds are used with syscon multifunctional devices where single bits in a certain register can turn on/off a single LED. The register bit LEDs appear as children to the syscon device, with the proper compatible string. For the syscon bindings see: Documentation/devicetree/bindings/mfd/syscon.yaml

**Important APIs/types/functions:** The public surface is the schema itself: `$id` `http://devicetree.org/schemas/leds/register-bit-led.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, composition keywords, closure rules, and `examples` consumed by `dt-schema`. Compatible strings are `register-bit-led`. Required properties are `compatible`, `mask`, `reg`. Important top-level properties include `$nodename`, `compatible`, `reg`, `mask`, `offset`. Patterned or child-node surfaces include none declared. Direct schema references are `/schemas/leds/common.yaml#`, `/schemas/types.yaml#/definitions/uint32`. Maintainers: Linus Walleij <linusw@kernel.org>. Top-level property policy is `unevaluatedProperties: false`.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel drivers rather than by this YAML. `dt_binding_check` loads the core meta-schema, resolves `$ref` dependencies, applies constants/enums/cardinality/range checks, evaluates composition and conditional branches (`allOf`), and validates the embedded examples. At boot, the compiled DTB node is matched by `compatible`; the relevant LED driver or common subsystem reads resource properties, phandles, child nodes, and cells before registering devices or provider relationships. Child/provider surfaces to watch here are none declared.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistence is ABI persistence: accepted DTS nodes encode hardware identity, register windows, interrupts, power/clock/reset topology, phandle cell widths, channel indexes, and child LED/IOMMU/IPMI layout for long-lived boards. Tightening `required`, changing compatible fallback order, altering cell counts, or changing closure policy can reject existing DTBs or make drivers parse resources differently.

**Dependencies and integration points:** Integrated with LED class devices, multicolor/flash/channel child nodes, GPIO/PWM/regulator resources, and trigger/function/color naming. Schema dependencies include `/schemas/leds/common.yaml#`, `/schemas/types.yaml#/definitions/uint32`; examples may also include dt-bindings headers. Resource integration is through properties such as `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address. Driver integration is through `compatible`, while subsystem integration is through phandle arrays, provider cell counts, common schemas, and child-node schemas inherited or declared here.

**Risks and edge cases:** Main risks are schema ABI drift, missing or stale compatible coverage, incorrect min/max item constraints, wrong `#*-cells` values, resource names that diverge from driver expectations, conditionals that validate one SoC or chip variant while rejecting another valid one, and examples that no longer reflect real DTS users. Closure policy (`unevaluatedProperties: false`) is useful for catching misspellings but can also block legitimate extensions. For LED/backlight children, channel numbering and `reg`/`led-sources` constraints are common failure points; for IOMMU bindings, stream IDs and cell widths are especially sensitive; for IPMI bindings, host/BMC address and register-resource shape must match the driver.

Useful negative tests remove each required property, add an unknown property under the declared closure policy, exercise compatible-specific conditionals, and verify the matching Linux driver still probes with the resources, child nodes, and phandle specifiers described by this binding.
