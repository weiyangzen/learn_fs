# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mfd/qcom,spmi-pmic.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mfd/qcom,spmi-pmic.yaml` is a Linux Devicetree YAML schema for `Qualcomm SPMI PMICs multi-function device`, a power-management MFD binding. Some Qualcomm PMICs used with the Snapdragon series SoCs are interfaced to the chip via the SPMI (System Power Management Interface) bus. Support for multiple independent functions are implemented by splitting the 16-bit SPMI peripheral address space into 256 smaller fixed-size regions, 256 bytes each. A function can consume one or more of these fixed-size register regions. The Qualcomm SPMI series includes the PM8941, PM8841, PMA8084, PM8998 and other PMICs. These PMICs use a "QPNP" scheme through SPMI interface. It is declarative ABI documentation and dt-schema validation input, not executable kernel code. Its job is to constrain how board DTS files describe the MFD parent and any child functions so the kernel can bind the parent driver, instantiate child devices, and hand common resources to subsystem drivers.

**Important APIs/types/functions:** The public API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, child schemas, references, examples, and compatible-specific composition. `compatible` uses ordered fallback `items` sequence and covers 75 compatible tokens: `qcom,pm2250`, `qcom,pm6125`, `qcom,pm6150`, `qcom,pm6150l`, `qcom,pm6350`, `qcom,pm660`, `qcom,pm660l`, `qcom,pm7250b`, `qcom,pm7550ba`, `qcom,pm7325`, `qcom,pm7550`, `qcom,pm8004`, `qcom,pm8005`, `qcom,pm8009`, `qcom,pm8010`, `qcom,pm8019`, `qcom,pm8028`, `qcom,pm8110`, `qcom,pm8150`, `qcom,pm8150b`, `qcom,pm8150c`, `qcom,pm8150l`, and 53 more. Top-level properties are `$nodename`, `compatible`, `reg`, `#address-cells`, `#size-cells`, `labibb`, `regulators`, `pwm`. Top-level required properties are `compatible`, `reg`; required properties discovered across nested schemas include `compatible`, `reg`. The node acts as a SPMI peripheral node. Important property roles: `compatible` selects the OF match entry and stable hardware ABI; `reg` carries the I2C/SPI/SPMI address or MMIO range; `#address-cells` defines child-node address layout; `#size-cells` defines child-node address layout; `regulators` contains regulator child nodes; `pwm` is a child-function schema entry for a subdevice. Named child-function entries are `labibb`, `pwm`, `regulators`; patterned child schemas are `(.*)?(wled|leds)@[0-9a-f]+$`, `^adc-tm@[0-9a-f]+$`, `^adc@[0-9a-f]+$`, `^audio-codec@[0-9a-f]+$`, `^battery@[0-9a-f]+$`, `^charger@[0-9a-f]+$`, `^led-controller@[0-9a-f]+$`, `^mpps@[0-9a-f]+$`, `^nvram@[0-9a-f]+$`, `^pbs@[0-9a-f]+$`, `^rtc@[0-9a-f]+$`, `^temp-alarm@[0-9a-f]+$`, and 7 more. Numeric and item constraints include `minItems=1`, `maxItems=2`.

**Control flow:** Control flow is supplied by Devicetree tooling and by the Linux MFD/subsystem core. `dt_binding_check` loads the core meta-schema, resolves `$ref` targets, applies property constraints, validates `required` sets and examples, evaluates `allOf`/`oneOf`/conditional branches, and enforces the unknown-property policy. At boot the compiled DTB node is matched through an OF compatible table; the parent MFD, syscon, PMIC, SPMI, I2C, SPI, or platform driver then reads `reg`, clocks, interrupts, resets, GPIOs, supplies, and child nodes before registering subdevices such as regulators, RTCs, GPIO/pinctrl blocks, chargers, watchdogs, LEDs, ADCs, PHYs, thermal sensors, or power/reset controllers.

**State and persistence behavior:** The YAML owns no mutable runtime state and persists no data. Its persistent effect is ABI stability: compatible tokens, child-node names, required supply/clock/IRQ/reset resources, phandle cell counts, register ranges, and fallback ordering become long-lived DTS/DTB contracts. Real state such as regulator voltage, watchdog countdown, RTC time, GPIO direction, charger status, reset line assertion, NVMEM contents, or interrupt masks is maintained by the hardware and kernel drivers that consume nodes validated by this schema.

**Risks:** Main risks are Devicetree ABI drift and parent/child contract skew. Tightening required properties can reject old board files; relaxing constraints can hide misspelled resources until probe fails. Compatible fallback ordering must match driver tables and documented hardware lineage. Child-function names and `patternProperties` must stay aligned with the subdriver bindings they reference, especially for regulators, GPIO/pinctrl, RTC, charger, LED, Type-C, watchdog, power/reset, and syscon children. Register ranges, `#address-cells`, `#size-cells`, and phandle cell counts are high-risk because they affect child resource decoding. Closure profile: top-level unknown properties are rejected by `additionalProperties: false`. This schema has 8 top-level properties and 8 distinct nested property names, so broad edits should be validated against every compatible variant and every in-tree DTS user rather than only the example node.

**Test signals:** Primary validation is `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/mfd/qcom,spmi-pmic.yaml` plus `make dtbs_check` for DTS files that instantiate each compatible. Useful negative tests remove required `reg`, IRQ, supply, clock, reset, GPIO, address-cell, or child-function properties; misspell child node names; use bad compatible fallback order; and exercise every conditional branch. Runtime signals are successful parent probe, expected child devices under sysfs/debugfs, working regulator/RTC/GPIO/pinctrl/reset/clock/charger/watchdog/LED/thermal/USB or other referenced subdrivers, and no new dtbs_check warnings for existing board examples.
