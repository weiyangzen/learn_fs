# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pci/pci-ep-bus.yaml

**Purpose:** Defines the Devicetree YAML/JSON-schema contract for `Common Properties for PCI MFD EP with Peripherals Addressable from BARs`. It is a endpoint controller or endpoint-bus binding in the PCI/PCIe devicetree binding family; it constrains how DTS/DTB nodes identify the PCI hardware, describe register windows, interrupts, clocks, resets, PHYs, address translation, DMA/IOMMU reachability, and optional child/root-port layout for Linux PCI probing. The source description says: Define a generic node representing a PCI endpoint which contains several sub- peripherals. The peripherals can be accessed through one or more BARs. This common schema is intended to be referenced from device tree bindings and does not represent a device tree binding by itself.

**Important APIs/types/functions:** This file is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/pci/pci-ep-bus.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, the `properties` block, `required` list, schema-composition keywords, inline examples, and the compatible strings consumed by kernel OF match tables. This common schema does not declare a concrete top-level `compatible`; concrete bindings include it by `$ref`. Directly declared properties are `#address-cells`, `#size-cells`, `ranges`. Required properties are none declared directly. Maintainers: A. della Porta  <andrea.porta@suse.com>.

**Control flow:** Validation flow is handled by dt-schema: the core meta-schema loads this YAML, resolves references (no explicit `$ref`; validation is local to this file plus the core meta-schema), applies direct property constraints, evaluates direct schema validation without top-level `allOf`, and then applies conditional branches. Conditional behavior: no explicit `if`/`then` branches; validation is direct plus referenced schemas. At runtime the compiled DTB has no code from this file; the kernel matches `compatible`, maps `reg` resources, programs PCI ranges, requests interrupts/MSI mappings, enables clocks/resets/regulators/PHYs/power domains, and creates host bridge/root-port or endpoint objects according to the described node.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability for board DTS files and shipped DTBs: compatible ordering, resource names, cell counts, interrupt maps, address ranges, and child-node layout become the long-lived contract that drivers and firmware rely on. For this file, the top-level and composed unknown-property policy is: additionalProperties: true.

**Dependencies:** Direct schema dependencies are no explicit `$ref`; validation is local to this file plus the core meta-schema. Resource dependencies visible in the binding include `ranges` (PCI address translation windows exposed by the host bridge) The binding also depends on the broader Devicetree PCI schemas, dt-schema tooling, and matching Linux PCI host/endpoint drivers for the compatible strings above.

**Integration points:** Integrates with Linux OF platform matching through `compatible`, PCI core setup through `device_type`, `bus-range`, `ranges`, `dma-ranges`, `#address-cells`, and `#size-cells`, interrupt infrastructure through `interrupt-map`, `interrupts`, MSI controllers or `msi-map`, and SoC resource managers through clocks, resets, PHY, regulator, power-domain, and IOMMU properties. Nested integration surface: pattern `^pci-ep-bus@[0-5]$`.

**Risks:** Main risks are ABI drift in required properties, accepting a DTS shape that the driver cannot probe, rejecting valid legacy boards, stale examples, wrong `reg-names`/`clock-names`/`reset-names` ordering, incomplete compatible coverage, and conditional branches whose `contains`/`enum` logic does not match real fallback-compatible ordering. PCI-specific risk is high around address translation and interrupts: bad `ranges`, `dma-ranges`, `iommu-map`, `msi-map`, or `interrupt-map-mask` can validate syntactically while producing unprobeable devices or broken DMA/MSI at runtime.

**Test signals:** Run `make dt_binding_check DT_SCHEMA_FILES=sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pci/pci-ep-bus.yaml` to validate this schema and its 0 inline example block(s). Run `make dtbs_check` for DTS users of each compatible string to exercise conditional branches, referenced schemas, child-node validation, closure policy, and resource-name ordering. Runtime smoke signals are successful PCI host bridge or endpoint probe, enumerated downstream devices/functions, working INTx/MSI/MSI-X, correct DMA/IOMMU mappings, and no missing-clock/reset/PHY/regulator errors in boot logs.
