# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/net/wireless/mediatek,mt76.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/net/wireless/mediatek,mt76.yaml` defines the Linux Devicetree YAML schema for `MediaTek mt76 wireless devices`, a wireless controller binding. The schema description says: This node provides properties for configuring the MediaTek mt76xx wireless device. The node is expected to be specified as a child node of the PCI controller to which the wireless chip is connected. Alternatively, it can specify the wireless part of the MT7628/MT7688 or MT7622/MT7986 SoC. It is declarative ABI documentation and validation input rather than executable kernel code; its practical role is to make DTS/DTB hardware descriptions match the resources, topology, and compatible strings expected by the relevant kernel subsystem before probe.

## Important APIs, Types, and Functions
The public API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses an `enum` and exposes 5 tokens: `mediatek,mt76`, `mediatek,mt7628-wmac`, `mediatek,mt7622-wmac`, `mediatek,mt7981-wmac`, `mediatek,mt7986-wmac`. Top-level properties are `compatible`, `reg`, `interrupts`, `power-domains`, `memory-region`, `resets`, `reset-names`, `clocks`, `clock-names`, `mediatek,infracfg`, `ieee80211-freq-limit`, `nvmem-cells`, `nvmem-cell-names`, `mediatek,eeprom-data`, `mediatek,mtd-eeprom`, `big-endian`, `mediatek,eeprom-merge-otp`, `mediatek,disable-radar-background`, `led`, `power-limits`. Top-level required properties are `compatible`, `reg`; required properties collected from nested schema branches include `compatible`, `reg`. Patterned child schemas are none. Numeric and collection constraints include `minItems=1`, `maxItems=3`, `maxItems=1`, `maxItems=2`, `minItems=2`, `minItems=4`, `maxItems=4`, `minItems=8`, `maxItems=8`, `minItems=9`, `maxItems=11`, `minItems=13`, `maxItems=13`, `maxItems=7`, `minItems=11`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `reg` describes MMIO ranges, bus child addresses, port selectors, or cell offsets; `interrupts` routes status, error, RX/TX, MSI, or completion IRQs; `power-domains` integrates with common clock, reset, PM, DMA/IOMMU, or reserved-memory providers; `memory-region` integrates with common clock, reset, PM, DMA/IOMMU, or reserved-memory providers; `resets` integrates with common clock, reset, PM, DMA/IOMMU, or reserved-memory providers; `reset-names` fixes resource ordering visible to drivers; `clocks` integrates with common clock, reset, PM, DMA/IOMMU, or reserved-memory providers; `clock-names` fixes resource ordering visible to drivers; `nvmem-cells` links calibration, MAC, serial, or speed-bin data through the NVMEM core; `nvmem-cell-names` links calibration, MAC, serial, or speed-bin data through the NVMEM core. The highest-risk ABI details are compatible identity, bus address, interrupt or wake wiring, calibration and OTP/NVMEM references, firmware names, frequency limits, power limits, and vendor board-data properties.

## Control Flow
Runtime control flow is supplied by dt-schema and kernel subsystem code, not by this YAML file. `dt_binding_check` loads the meta-schema, resolves `$ref` entries, applies `properties`, evaluates `allOf`, checks required fields, validates `minItems`/`maxItems` and enum/const constraints, validates embedded examples, and applies the closure rule. During boot, the compiled DTB node is matched by `compatible`; then platform, PCI, SDIO, SPI, MDIO, NVMEM, OPP, PCIe, netdev, wireless, accelerator, storage, clock, reset, regulator, IRQ, GPIO, IOMMU, and power-domain helpers consume the phandles and resource arrays that this schema validates. Child nodes are discovered declaratively through fixed names, pattern properties, address cells, and referenced child schemas.

## State and Persistence Behavior
The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: compatible strings, required resource names, register and interrupt ordering, phandle and cell counts, child-node names, fallback ordering, and example layouts become long-lived contracts in board DTS files and shipped DTBs. Runtime state belongs to the matching drivers and hardware after probe, including wireless device probe, firmware boot, regulatory/channel capability selection, calibration selection, IRQ/wake state, netdev/wiphy registration, and runtime PM.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, link training, calibration lookup, OPP selection, NVMEM cell reads, or bus enumeration. Tightening required properties can reject existing boards; loosening them can hide missing clocks, resets, interrupts, supplies, PHY links, PCIe windows, memory regions, OPP fields, or NVMEM cells. Child-node schemas need special care because address cells, port IDs, PCI interrupt maps, wireless calibration cells, NVMEM layouts, and OPP tables must match driver-side assumptions. This schema closes composed schemas with `unevaluatedProperties: false`. It has 20 top-level properties and 38 distinct nested property names, so broad edits should be checked against all compatible variants and DTS users, not just the nominal filename.
