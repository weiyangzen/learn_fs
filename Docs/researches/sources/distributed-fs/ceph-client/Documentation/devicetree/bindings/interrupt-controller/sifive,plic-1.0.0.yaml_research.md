# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/sifive,plic-1.0.0.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `SiFive Platform-Level Interrupt Controller (PLIC)`. In this tree it is an interrupt controller binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: SiFive SoCs and other RISC-V SoCs include an implementation of the Platform-Level Interrupt Controller (PLIC) high-level specification in the RISC-V Privileged Architecture specification. The PLIC connects all external interrupts in the system to all hart contexts in the system, via the external interrupt source in each hart. A hart context is a privilege mode in a hardware execution thread. For example, in an 4 core system with 2-way SMT, you have 8 harts and probably at least two privilege modes per hart; machine mode and supervisor mode. Each interrupt can be enabled on per-context basis. Any context can claim a pending enabled interrupt and then release it once it has been handled. Each interrupt has a configurable priority. Higher priority interrupts are serviced first. Each context can specify a priority threshold. Interrupts with priority below this threshold will not cause the PLIC to raise its interrupt line leading to the context. The PLIC supports both edge-triggered and level-triggered interrupts. For edge-triggered interrupts, the RISC-V PLIC spec allows two responses to edges seen while an interrupt handler is active; the PLIC may either queue them or ignore them. In the first case, handlers are oblivious to the trigger type, so it is not included in the interrupt specifier. In the second case, software needs to know the trigger type, so it can reorder the interrupt flow to avoid missing interrupts. This special handling is needed by at least the Renesas RZ/Five SoC (AX45MP AndesCore with a NCEPLIC100) and the T-HEAD C900 PLIC. While the RISC-V ISA doesn't specify a memory layout for the PLIC, the "sifive,plic-1.0.0" device is a concrete implementation of the PLIC that contains a specific memory layout, which is documented in chapter 8 of the SiFive U5 Coreplex Series Manual <https://static.dev.sifive.com/U54-MC-RVCoreIP.pdf>. The thead,c900-plic is different from sifive,plic-1.0.0 in opensbi, the T-HEAD PLIC implementation requires setting a delegation bit to allow access from S-mode. So add thead,c900-plic to distinguish them.

**Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. Schema composition/conditional keywords present: `allOf`, `else`, `if`, `oneOf`, `then`. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IRQ domain code uses it to translate DT interrupt specifiers into Linux IRQs and route them to an upstream parent domain. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as `reg`, `#address-cells`, `interrupts-extended`, `clocks`, `power-domains`, `resets`. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.
