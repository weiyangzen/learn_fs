# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/phy/marvell,comphy-cp110.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/phy/marvell,comphy-cp110.yaml` is a Linux Devicetree YAML schema for `Marvell MVEBU COMPHY Controller`, a multi-protocol SerDes/COMPHY binding. COMPHY controllers can be found on the following Marvell MVEBU SoCs: * Armada 7k/8k (on the CP110) * Armada 3700 It provides a number of shared PHYs used by various interfaces (network, SATA, USB, PCIe...). It is declarative firmware ABI documentation and dt-schema validation input, not executable kernel code. Its role is to make board DTS/DTB nodes describe PHY blocks, lanes, pads, ports, supplies, clocks, resets, and phandle provider contracts in the form the matching Linux PHY or controller driver expects.

**Important APIs/types/functions:** The exported API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `patternProperties`, local definitions, `required`, examples, and composition constraints. `compatible` uses `enum` list and covers 2 compatible tokens: `marvell,comphy-cp110`, `marvell,comphy-a3700`. Top-level properties are `compatible`, `reg`, `reg-names`, `#address-cells`, `#size-cells`, `clocks`, `clock-names`, `marvell,system-controller`. Top-level required properties are `compatible`, `reg`; required properties discovered across nested schemas include `#phy-cells`, `compatible`, `marvell,system-controller`, `reg`, `reg-names`. The binding acts as a parent provider with addressable child PHY/lane nodes. Provider/cell contracts are `#address-cells=const 1`, `#size-cells=const 0`, `#phy-cells=const 1`. Important property roles: `compatible` selects the OF match table entry and stable hardware ABI; `reg` carries MMIO ranges, syscon offsets, port numbers, or bus addresses; `#address-cells` enables addressable child PHY, lane, or port nodes; `#size-cells` enables addressable child PHY, lane, or port nodes; `clocks` binds reference, pipe, APB, PLL, or tracking clocks; `clock-names` binds reference, pipe, APB, PLL, or tracking clocks. Patterned child schemas are `^phy@[0-5]$`; nested topology or child names discovered from properties are no explicit nested pad/lane/port names discovered. Local reusable definitions are none. Numeric/item constraints include `minItems=1`, `maxItems=3`, `maximum=5`, `maxItems=1`, `minItems=3`; selected enum/const literals include `marvell,comphy-cp110`, `marvell,comphy-a3700`, `comphy`, `lane1_pcie_gbe`, `lane0_usb3_gbe`, `lane2_sata_usb3`, `1`, `0`, `xtal`, `mg_clk`, `mg_core_clk`, `axi_clk`.

**Control flow:** Control flow is dt-schema evaluation. `dt_binding_check` parses the YAML, validates it against the core meta-schema, resolves `$ref` dependencies, applies `properties` and `patternProperties`, evaluates `allOf`/`oneOf`/`anyOf`/conditional branches, checks `required` lists and item counts, compiles examples, and enforces the closure rule. At boot the YAML is not interpreted; firmware supplies a compiled DTB node, the kernel matches `compatible` in the relevant OF table, and the PHY/provider driver reads `reg`, clocks, resets, supplies, child lanes/ports, and `#phy-cells` to register PHYs. Consumer controllers later resolve `phys` phandles and invoke the generic PHY framework for init, power-on, mode setting, calibration, and power-off.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence. Its durable state is ABI shape: compatible strings, property names, valid enum values, provider cell counts, child-node naming, lane or port numbering, and allowed topology. Runtime state such as PLL lock, link training, lane muxing, PHY mode, impedance tuning, analog calibration, reset sequencing, and power transitions lives in the matching kernel driver and hardware registers; this schema only constrains how those resources and modes are represented in firmware.

The file includes 2 example blocks for validation.

**Risks:** Primary risks are PHY ABI drift and resource lookup mismatch. Removing or reordering compatible fallbacks can break legacy DTBs; changing `#phy-cells`, child `reg` numbering, lane names, or port names can break consumers that already reference the provider; renaming clocks, resets, supplies, GPIOs, or power domains can break driver probe even when the hardware block is unchanged. Multi-protocol SerDes and pad-controller schemas are especially sensitive because lane mux enums, protocol names, and companion USB2/USB3 or PCIe/SATA relationships must align with driver tables and board wiring. The closure profile is: top-level unknown properties are rejected by `additionalProperties: false`. Because this schema has 8 top-level properties and 10 distinct nested property names, broad edits should be checked against every compatible variant, examples, and existing DTS users.

**Test signals:** Primary validation signals are `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/phy/marvell,comphy-cp110.yaml` in a kernel tree with dt-schema installed and `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/phy/marvell,comphy-cp110.yaml` for boards using these compatibles. Useful negative checks omit required clocks/resets/supplies, use invalid `#phy-cells`, bad child-node names, wrong lane `reg` values, or unsupported enum values. Runtime integration signals are successful driver probe, registered PHY providers with expected phandle arguments, consumers resolving `phys`, clocks and regulators balanced across suspend/resume, link bring-up for the relevant USB/PCIe/SATA/UFS/MIPI/SerDes protocol, and no new schema warnings for examples or in-tree DTS files.
