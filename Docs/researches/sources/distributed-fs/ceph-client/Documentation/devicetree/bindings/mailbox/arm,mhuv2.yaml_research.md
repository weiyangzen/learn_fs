# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mailbox/arm,mhuv2.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `ARM MHUv2 Mailbox Controller`. In this tree it is a mailbox controller Devicetree binding schema; it constrains how DTS/DTB nodes describe the hardware and how Linux drivers and framework code discover resources through OF matching, phandles, common binding references, and validated child-node topology. The source description says: The Arm Message Handling Unit (MHU) Version 2 is a mailbox controller that has between 1 and 124 channel windows (each 32-bit wide) to provide unidirectional communication with remote processor(s), where the number of channel windows are implementation dependent.

**Important APIs/types/functions:** This file is declarative schema rather than executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/mailbox/arm,mhuv2.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, schema composition keywords, and inline `examples` consumed by dt-schema. Compatible strings are `arm,mhuv2-rx`, `arm,mhuv2-tx`, `arm,primecell`. Top-level required properties are `compatible`, `reg`, `#mbox-cells`, `arm,mhuv2-protocols`; conditional or nested required properties visible in composed schemas are `interrupts`. Important properties include `#mbox-cells`, `arm,mhuv2-protocols`, `clock-names`, `clocks`, `compatible`, `interrupts`, `reg`. Property roles include `#mbox-cells` (mailbox client specifier width), `clock-names` (semantic labels for clock inputs), `clocks` (clock provider phandles), `compatible` (driver match key and stable hardware ABI identifier), `interrupts` (interrupt line routing), `reg` (MMIO resource, bus address, or child register address). Direct and nested schema references are `/schemas/types.yaml#/definitions/uint32-matrix`. Local schema definitions are none. The top-level closure rule is `additionalProperties: false`. Maintainers: `Tushar Khandelwal <tushar.khandelwal@arm.com>`, `Viresh Kumar <viresh.kumar@linaro.org>`.

**Control flow:** Runtime behavior is supplied by Devicetree tooling and kernel subsystems, not by this YAML file. `dt_binding_check` loads the core meta-schema, resolves references such as `/schemas/types.yaml#/definitions/uint32-matrix`, applies `properties`, `required`, enum/const/items limits, pattern properties, local definitions, and composition keywords, then validates the inline examples. At boot, a compiled DTB node matching one of the compatible strings lets the OF core bind the relevant driver; framework code then reads resources such as mailbox channel cell counts, shared-memory regions, interrupts, doorbells, and remote endpoint semantics. Schema composition points in this file are `if`, `oneOf`, `then`. Nested or patterned child-node surfaces include none; patternProperties are none.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: board DTS files and shipped DTBs encode the compatible strings, resource ordering, cell counts, phandle topology, supplies, graph links, and child-node names validated here. Tightening required fields, changing enum ordering, altering `#*-cells`, or changing the closure policy can break existing board descriptions even though the file itself is static documentation plus validation rules.

**Dependencies and integration points:** Integrated with Linux mailbox framework, remoteproc/SCMI/firmware clients, and SoC-specific mailbox drivers. The schema depends on dt-schema core handling plus referenced schemas `/schemas/types.yaml#/definitions/uint32-matrix`. Driver integration is through `compatible`; subsystem integration is through standard properties, provider/client cell properties, OF graph `ports` and `endpoint` nodes where present, interrupts, clocks, resets, regulators, power domains, GPIOs, IOMMU mappings, DMA/mailbox phandles, and any SoC-specific properties declared in this file.

**Risks:** Main risks are schema ABI drift, missing or overly broad compatible coverage, incorrect required resources, wrong `#*-cells` or graph lane counts, examples that do not exercise conditional branches, and closure settings that either reject valid legacy DTS extensions or allow misspelled properties. For media, mailbox, LED, and CPU/platform bindings, parent/child address-cell mismatches, endpoint graph mistakes, trigger/provider phandle errors, and firmware-facing mailbox channel semantics are especially easy to miss if only the schema example is tested.
