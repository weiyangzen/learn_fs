# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/power/supply/maxim,max17040.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/power/supply/maxim,max17040.yaml` defines the Linux Devicetree YAML schema for `Maxim 17040 fuel gauge series`, a battery, fuel-gauge, or battery-monitor binding. It is declarative ABI documentation and validation input, not executable driver code. Its job is to keep DTS/DTB nodes aligned with the resources, child nodes, and electrical or timing constraints expected by the matching kernel subsystem before a driver probes hardware.

## Important APIs, Types, and Functions
The API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `patternProperties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses an `enum` with 9 tokens: `maxim,max17040`, `maxim,max17041`, `maxim,max17043`, `maxim,max17044`, `maxim,max17048`, `maxim,max17049`, `maxim,max17058`, `maxim,max17059`, `maxim,max77836-battery`. Top-level properties are `compatible`, `reg`, `maxim,alert-low-soc-level`, `maxim,double-soc`, `maxim,rcomp`, `interrupts`, `io-channels`, `io-channel-names`, `wakeup-source`. Top-level required properties are `compatible`, `reg`; required properties collected from nested branches include `compatible`, `reg`. Patterned child schemas are none. Numeric and collection constraints include `maxItems=1`, `minimum=1`, `maximum=32`, `minItems=1`, `maxItems=2`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `reg` gives MMIO, I2C, SPI, child address, or selector placement; `interrupts` routes alert, status, protection, capture, timer, or controller IRQs. The highest-risk ABI details are compatible identity, I2C/MMIO address, battery phandle, monitor resistor/calibration values, alert/IRQ wiring, charge/voltage/current limits, and vendor battery profile data.

## Control Flow
Control flow is dt-schema evaluation rather than imperative execution. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties` and `patternProperties`, evaluates `allOf`, checks required fields and min/max constraints, validates examples, and enforces the closure policy. At runtime this YAML does not execute: the compiled DTB node is matched through a kernel OF table or subsystem-specific child-node parser, then helpers for power-supply, regulator, PWM, PTP, PPS, PowerPC platform, clocks, resets, interrupts, GPIOs, pinctrl, power domains, and MFD parents consume the validated resources.

## State and Persistence Behavior
The file stores no mutable runtime state and writes no persistent data. Its persistence is ABI stability: compatible strings, required resource names, phandle/cell counts, child-node names, electrical limit properties, fallback ordering, and example layouts become long-lived contracts in DTS and DTB artifacts. Runtime state belongs to drivers and hardware after probe, including power_supply registration, state-of-charge, voltage/current/temperature measurements, battery health, charge counters, alert thresholds, suspend/resume sampling, and cached gauge registers.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, power sequencing, clock setup, IRQ delivery, or consumer phandle resolution. Tightening required properties can reject existing board files; loosening them can hide missing supplies, clocks, resets, interrupts, current/voltage limits, PWM cell counts, PTP/PPS GPIOs, or regulator child constraints. This schema closes composed schemas with `unevaluatedProperties: false`. It has 9 top-level properties and 9 distinct nested property names, so broad edits should be checked against all compatibles, examples, and in-tree DTS users rather than only the filename's nominal device.
