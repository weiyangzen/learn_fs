# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interconnect/qcom,rpmh.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interconnect/qcom,rpmh.yaml` is a Linux devicetree YAML schema for the `Qualcomm RPMh Network-On-Chip Interconnect` Qualcomm RPMh interconnect provider binding. RPMh interconnect providers support system bandwidth requirements through RPMh hardware accelerators known as Bus Clock Manager (BCM). The provider is able to communicate with the BCM through the Resource State Coordinator (RSC) associated with each execution environment. Provider nodes must point to at least one RPMh device child node pertaining to their RSC and each provider can map to multiple RPMh resources. It is not executable kernel code; it is the hardware-description ABI that DTS authors, dt-schema, and the relevant kernel subsystem rely on so the runtime driver can parse the node without board-specific ambiguity.

## Important APIs, Types, and Functions
The public API surface is the schema's accepted node shape. `compatible` uses `enum` list and covers 76 compatible tokens: `qcom,sc7180-aggre1-noc`, `qcom,sc7180-aggre2-noc`, `qcom,sc7180-camnoc-virt`, `qcom,sc7180-compute-noc`, `qcom,sc7180-config-noc`, `qcom,sc7180-dc-noc`, `qcom,sc7180-gem-noc`, `qcom,sc7180-mc-virt`, `qcom,sc7180-mmss-noc`, `qcom,sc7180-npu-noc`, `qcom,sc7180-qup-virt`, `qcom,sc7180-system-noc`, `qcom,sc8180x-aggre1-noc`, `qcom,sc8180x-aggre2-noc`, `qcom,sc8180x-camnoc-virt`, `qcom,sc8180x-compute-noc`, `qcom,sc8180x-config-noc`, `qcom,sc8180x-dc-noc`, `qcom,sc8180x-gem-noc`, `qcom,sc8180x-mc-virt`, and 56 more. Top-level properties are `reg`, `compatible`, `#interconnect-cells`. Across nested schemas and child nodes this file mentions 3 distinct property names; nested/all required properties include `compatible`, `reg`. Node naming is constrained by no explicit node-name constraint. Interconnect-facing properties define a provider node for the Linux interconnect framework and related devfreq/OPP consumers: addressing resources `reg`, provider cells `#interconnect-cells`, clocks/power/OPP hooks none, and SoC/vendor topology knobs `#interconnect-cells`. Required properties are `compatible`; consumer nodes depend on these cells and phandles to vote bandwidth or performance state.

## Control Flow, State, and Persistence
Control flow is declarative JSON-schema evaluation rather than executable branching. `dt-doc-validate` and `dt_binding_check` load the YAML, expand `$ref` links, apply composition and conditional keywords, validate the DTS example blocks, and later `dtbs_check` applies the same contract to compiled board devicetrees. For interconnect providers, validation ensures that provider cells, register banks, clocks, power domains, BCM voter links, and OPP or devfreq relationships are well-formed before Linux interconnect providers register bandwidth paths consumed by other device nodes. The schema itself stores no mutable state and writes no persistent data; its persistence is the stable source-controlled hardware ABI. External references used in evaluation are `qcom,rpmh-common.yaml#`; top-level/nested conditional keywords present are `allOf`, `if`, `then`.

## Risks
Risks are mostly ABI and validation risks rather than algorithmic failures. Tightening required properties, changing compatible ordering, renaming resources, altering cell counts, or closing extra properties can reject existing DTS users; loosening constraints can allow nodes that later fail driver probe or misdescribe hardware. This schema has 3 top-level properties and 3 distinct nested property names, with strictness profile: composition is closed with `unevaluatedProperties: false`. Conditional branches and shared `$ref` schemas should be checked against all in-tree users before edits, because a schema-only patch can still break board builds.
