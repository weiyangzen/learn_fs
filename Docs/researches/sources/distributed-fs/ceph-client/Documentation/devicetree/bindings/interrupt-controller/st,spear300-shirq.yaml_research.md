# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/st,spear300-shirq.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `SPEAr3xx Shared IRQ controller`. In this tree it is an interrupt controller binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: SPEAr3xx architecture includes shared/multiplexed irqs for certain set of devices. The multiplexor provides a single interrupt to parent interrupt controller (VIC) on behalf of a group of devices. There can be multiple groups available on SPEAr3xx variants but not exceeding 4. The number of devices in a group can differ, further they may share same set of status/mask registers spanning across different bit masks. Also in some cases the group may not have enable or other registers. This makes software little complex. A single node in the device tree is used to describe the shared interrupt multiplexer (one node for all groups). A group in the interrupt controller shares config/control registers with other groups. For example, a 32-bit interrupt enable/disable config register can accommodate up to 4 interrupt groups.

**Important APIs/types/functions:** This YAML is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/interrupt-controller/st,spear300-shirq.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and any referenced dt-schema fragments. Compatible strings or compatible-pattern values are `st,spear300-shirq`, `st,spear310-shirq`, `st,spear320-shirq`. Required properties are `compatible`, `reg`, `#interrupt-cells`, `interrupt-controller`, `interrupts`. Important top-level properties are `compatible`, `reg`, `#interrupt-cells`, `interrupt-controller`, `interrupts`. Direct and nested `$ref` dependencies are none declared. Property roles include `compatible` for driver match key and stable hardware ABI identifier; `reg` for MMIO range, bus address, or child register selector; `#interrupt-cells` for interrupt specifier cell count consumed by child/client nodes; `interrupt-controller` marks the node as an interrupt domain provider; `interrupts` for interrupt parent specifier array for wired IRQ inputs or outputs. The top-level unknown-property policy is `additionalProperties: false`. Maintainers are `Viresh Kumar <vireshk@kernel.org>`, `Shiraz Hashim <shiraz.linux.kernel@gmail.com>`.

**Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. The file has no nested conditional schema composition beyond direct property validation. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IRQ domain code uses it to translate DT interrupt specifiers into Linux IRQs and route them to an upstream parent domain. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as `reg`, `interrupts`. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.
