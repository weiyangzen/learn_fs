# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/apple,aic.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/apple,aic.yaml` is a Linux devicetree YAML schema for the `Apple Interrupt Controller` interrupt-controller binding. The Apple Interrupt Controller is a simple interrupt controller present on Apple ARM SoC platforms, including various iPhone and iPad devices and the "Apple Silicon" Macs. It provides the following features: - Level-triggered hardware IRQs wired to SoC blocks - Single mask bit per IRQ - Per-IRQ affinity setting - Automatic masking on event delivery (auto-ack) - Software triggering (ORed with hw line) - 2 per-CPU IPIs (meant as "self" and "other", but they are interchangeable if not symmetric) - Automatic prioritization (single event/ack register per CPU, lower IRQs = higher priority) - Automatic masking on ack - Default "this CPU" register view and explicit per-CPU views This device also represents the FIQ interrupt sources on platforms using AIC, which do not go through a discrete interrupt controller. It is not executable kernel code; it is the hardware-description ABI that DTS authors, dt-schema, and the relevant kernel subsystem rely on so the runtime driver can parse the node without board-specific ambiguity.

## Important APIs, Types, and Functions
The public API surface is the schema's accepted node shape. `compatible` uses ordered `items` sequence and covers 7 compatible tokens: `apple,s5l8960x-aic`, `apple,t7000-aic`, `apple,s8000-aic`, `apple,t8010-aic`, `apple,t8015-aic`, `apple,t8103-aic`, `apple,aic`. Top-level properties are `compatible`, `interrupt-controller`, `#interrupt-cells`, `reg`, `power-domains`, `affinities`. Across nested schemas and child nodes this file mentions 8 distinct property names; nested/all required properties include `#interrupt-cells`, `apple,fiq-index`, `compatible`, `cpus`, `interrupt-controller`, `reg`. Node naming is constrained by no explicit node-name constraint. Interrupt-controller-facing properties define how child devices encode interrupt specifiers and how the kernel irqchip or MSI domain driver maps them: addressing resources `reg`, domain declarations `interrupt-controller`, `#interrupt-cells`, clock/reset/power hooks `power-domains`, and any GPIO or parent-domain links none. Required properties are `compatible`, `#interrupt-cells`, `interrupt-controller`, `reg`; the shape of `#interrupt-cells` and parent interrupt wiring is the main ABI exposed to DTS consumers.

## Control Flow, State, and Persistence
Control flow is declarative JSON-schema evaluation rather than executable branching. `dt-doc-validate` and `dt_binding_check` load the YAML, expand `$ref` links, apply composition and conditional keywords, validate the DTS example blocks, and later `dtbs_check` applies the same contract to compiled board devicetrees. For irqchip and MSI providers, validation ensures the interrupt domain, specifier cell count, parent interrupt lines, MSI doorbells, and child-node encoding match what the kernel interrupt-controller driver will parse during early boot or bus enumeration. The schema itself stores no mutable state and writes no persistent data; its persistence is the stable source-controlled hardware ABI. External references used in evaluation are `/schemas/interrupt-controller.yaml#`, `/schemas/types.yaml#/definitions/uint32`; top-level/nested conditional keywords present are `allOf`.

## Risks
Risks are mostly ABI and validation risks rather than algorithmic failures. Tightening required properties, changing compatible ordering, renaming resources, altering cell counts, or closing extra properties can reject existing DTS users; loosening constraints can allow nodes that later fail driver probe or misdescribe hardware. This schema has 6 top-level properties and 8 distinct nested property names, with strictness profile: unknown top-level properties are rejected. Conditional branches and shared `$ref` schemas should be checked against all in-tree users before edits, because a schema-only patch can still break board builds.
