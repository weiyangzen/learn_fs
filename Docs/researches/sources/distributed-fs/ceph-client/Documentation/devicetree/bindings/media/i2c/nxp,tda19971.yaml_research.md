# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/i2c/nxp,tda19971.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/i2c/nxp,tda19971.yaml` is a Linux Devicetree YAML schema for `NXP TDA1997x HDMI receiver`, a video receiver or media bus bridge binding. The TDA19971/73 are HDMI video receivers. The TDA19971 Video port output pins can be used as follows: - RGB 8bit per color (24 bits total): R[11:4] B[11:4] G[11:4] - YUV444 8bit per color (24 bits total): Y[11:4] Cr[11:4] Cb[11:4] - YUV422 semi-planar 8bit per component (16 bits total): Y[11:4] CbCr[11:4] - YUV422 semi-planar 10bit per component (20 bits total): Y[11:2] CbCr[11:2] - YUV422 semi-planar 12bit per component (24 bits total): - Y[11:0] CbCr[11:0] - YUV422 BT656 8bit per component (8 bits total): YCbCr[11:4] (2-cycles) - YUV422 BT656 10bit per component (10 bits total): YCbCr[11:2] (2-cycles) - YUV422 BT656 12bit per component (12 bits total): YCbCr[11:0] (2-cycles) The TDA19973 Video port output pins can be used as follows: - RGB 12bit... It is declarative ABI documentation and validation input, not executable driver code. Its job is to constrain how board DTS files describe media hardware so V4L2, media-controller, remote-control, codec, bridge, sensor, clock, regulator, GPIO, DMA, and platform/I2C driver code can discover the expected resources.

**Important APIs/types/functions:** The public API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and any OF graph or child-node patterns. `compatible` uses `enum` list and covers 2 compatible tokens: `nxp,tda19971`, `nxp,tda19973`. Top-level required properties are `compatible`, `reg`, `interrupts`, `DOVDD-supply`, `AVDD-supply`, `DVDD-supply`; required properties found across nested schemas include `AVDD-supply`, `DOVDD-supply`, `DVDD-supply`, `compatible`, `interrupts`, `reg`. Patterned child schemas are none; graph or child-node properties discovered in nested schemas are `endpoint`, `port`. Numeric/item constraints include no explicit numeric min/max/item limits collected.

**Control flow:** Control flow is dt-schema evaluation rather than imperative logic. `dt_binding_check` loads the core meta-schema, resolves every `$ref`, applies `properties`, `required`, item/count limits, and composition branches, validates inline examples, and enforces the unknown-property policy. At runtime the YAML is not executed: the compiled DTB node is matched through the driver's OF table, and media graph parsing follows `port`/`ports` endpoints to connect sensors, bridges, serializers, deserializers, receivers, codecs, and SoC capture or processing blocks. Resource acquisition then proceeds through standard helpers for I2C/platform devices, regulators, clocks, resets, GPIOs, IRQs, DMA/IOMMU, firmware, and child remote buses when those properties are present.

**State and persistence behavior:** The schema has no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: accepted compatible strings, required supplies/clocks/resets/IRQs, endpoint lane layouts, child-node names, remote-I2C topology, and MMIO or I2C address shapes become long-lived DTB contracts. Runtime state such as video streaming, link training, sensor mode selection, codec sessions, remote serializer state, radio tuning, frame buffers, and power sequencing belongs to the matching kernel drivers and hardware.

**Risks:** Risks center on Devicetree ABI drift and media graph mismatches. Changing compatible values or fallback order can break driver binding; renaming supplies, clocks, GPIOs, interrupts, reset lines, `#*-cells`, or child nodes can break probe-time resource lookup; tightening endpoint lane counts or port numbering can reject valid boards or silently disconnect media links. Serializer/deserializer bindings add risk around remote I2C aliases, PoC supplies, GPIO forwarding, and link topology. Codec and SoC processing bindings add risk around clocks, power domains, IOMMU/DMA resources, and firmware/mailbox style dependencies. The closure profile is: top-level unknown properties are rejected by `additionalProperties: false`. This file has 13 top-level properties and 14 distinct nested property names, so schema cleanups should be checked against all compatibles and real DTS users, not only the filename's nominal device.

**Test signals:** Primary validation signals are `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/media/i2c/nxp,tda19971.yaml` and `make dtbs_check` for boards instantiating each compatible. Useful negative tests remove required regulators/clocks/resets/IRQs, use invalid endpoint `data-lanes` or port numbering, misspell vendor properties, and exercise every compatible branch. Runtime integration is indicated by successful driver probe, correct media-controller entity/link topology, valid V4L2 async subdevice binding, stable power sequencing, clean stream-on/stream-off for sensors and bridges, successful codec or image-processing queue setup for SoC blocks, and no dtbs_check regressions for existing DTS examples.
