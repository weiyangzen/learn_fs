# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/usb/generic-xhci.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/usb/generic-xhci.yaml` defines `USB xHCI Controller`, a USB3/xHCI or dual-role controller binding. It is declarative firmware ABI documentation and dt-schema validation input; Linux does not execute this YAML at runtime, but the schema controls which DTS nodes are accepted for the corresponding hardware or bus-attached device.

## Important APIs, Types, and Functions
The exported API is the Devicetree node contract. `$id` is `http://devicetree.org/schemas/usb/generic-xhci.yaml#` and `$schema` is `http://devicetree.org/meta-schemas/core.yaml#`. `compatible` uses `oneOf` with 6 accepted forms and exposes 9 compatible tokens: `generic-xhci`, `marvell,armada-375-xhci`, `marvell,armada-380-xhci`, `marvell,armada3700-xhci`, `marvell,armada-8k-xhci`, `brcm,bcm2711-xhci`, `brcm,xhci-brcm-v2`, `brcm,bcm7445-xhci`, `xhci-platform`. Top-level properties are `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `dma-coherent`, `dr_mode`, `iommus`, `power-domains`. Top-level required properties are `compatible`, `reg`, `interrupts`; required properties discovered in nested branches are `compatible`, `interrupts`, `power-domains`, `reg`. Patterned child schemas are none; local definitions are none. Resource/provider roles: `compatible` selects schema applicability and the kernel OF match-table entry; `reg` describes MMIO windows, bus addresses, or register resources; `interrupts` maps controller, GPIO, or Type-C events into IRQ domains; `clocks` integrates with the clock framework; `clock-names` integrates with the clock framework; `dma-coherent` describes DMA/IOMMU integration; `dr_mode` models USB dual-role, Type-C, or graph topology; `iommus` describes DMA/IOMMU integration; `power-domains` models generic power-domain dependencies. Across the full schema there are 9 distinct property names and collected const/enum/min/max/item signals include `const=generic-xhci`, `enum=[marvell,armada-375-xhci, marvell,armada-380-xhci]`, `enum=[marvell,armada3700-xhci, marvell,armada-8k-xhci]`, `enum=[brcm,bcm2711-xhci]`, `const=brcm,xhci-brcm-v2`, `enum=[brcm,xhci-brcm-v2, brcm,bcm7445-xhci]`, `const=xhci-platform`, `maxItems=1`, `minItems=1`, `maxItems=2`, `const=core`, `const=reg`, `enum=[host, otg]`, `const=brcm,bcm2711-xhci`.

## Control Flow
Control flow is schema evaluation. `dt_binding_check` parses the YAML, validates the meta-schema, resolves `$ref` links, applies `properties`, `patternProperties`, required lists, item counts, const/enum checks, and composition or conditional blocks (`allOf`); it also compiles the embedded examples. `dtbs_check` applies the same rules to compiled board DTBs. During boot the kernel only consumes the DTB: OF matching selects the driver, platform/bus code maps resources, phandles are resolved, and the driver performs hardware setup.

## State and Persistence Behavior
The file has no mutable runtime state and performs no persistence. Its durable state is ABI shape: compatible strings, property names, child-node names, phandle cell counts, register and interrupt ordering, resource names, and example topology. Runtime behavior is owned by matched drivers and hardware: host/gadget/OTG role, endpoint/transfer rings, event interrupts, runtime PM, PHY state, wakeup behavior, and controller reset/recovery state. Schema edits therefore persist as compatibility commitments for existing DTS files even though no code path is stored here.

## Risks
Main risks are ABI drift around controller compatible strings, register and interrupt ordering, PHY arrays, `dr_mode`, role-switch wiring, clock/reset names, child-port layout, and vendor quirk properties; changing compatible ordering or removing fallback strings; broadening a schema so invalid board nodes pass; tightening a schema so existing DTBs fail; and mismatches between YAML clock/reset/regulator/PHY names and driver lookup tables. Multi-role USB and Type-C bindings are especially sensitive to graph endpoints, role-switch dependencies, connector children, and wakeup semantics. UFS bindings are sensitive to per-SoC clock arrays, ICE register resources, PHY lane counts, and reset/power sequencing. The closure profile closes composed schemas with `unevaluatedProperties: false`.

## Test Signals
Use `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/usb/generic-xhci.yaml` for this schema and its examples, then `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/usb/generic-xhci.yaml` against boards using these compatibles. Useful negative tests remove each required property, scramble compatible fallback order, use bad child-node names, provide too many/few clocks, resets, interrupts, PHYs, or register windows, and add undeclared properties when the schema is closed. Runtime signals are clean driver probe, expected PHY/role-switch/provider registration where applicable, correct device enumeration, suspend/resume without resource leaks, and no new schema warnings. Example seed: usb@f0931000 {; compatible = "generic-xhci";; reg = <0xf0931000 0x8c8>;; interrupts = <0x0 0x4e 0x0>;; };;
