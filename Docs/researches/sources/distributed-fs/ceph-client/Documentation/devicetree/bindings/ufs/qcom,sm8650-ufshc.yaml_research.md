# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/ufs/qcom,sm8650-ufshc.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/ufs/qcom,sm8650-ufshc.yaml` defines `Qualcomm SM8650 and Other SoCs UFS Controllers`, a Qualcomm UFS host-controller binding. It is declarative firmware ABI documentation and dt-schema validation input; Linux does not execute this YAML at runtime, but the schema controls which DTS nodes are accepted for the corresponding hardware or bus-attached device.

## Important APIs, Types, and Functions
The exported API is the Devicetree node contract. `$id` is `http://devicetree.org/schemas/ufs/qcom,sm8650-ufshc.yaml#` and `$schema` is `http://devicetree.org/meta-schemas/core.yaml#`. `compatible` uses ordered fallback `items` sequence and exposes 6 compatible tokens: `qcom,eliza-ufshc`, `qcom,kaanapali-ufshc`, `qcom,sm8650-ufshc`, `qcom,sm8750-ufshc`, `qcom,ufshc`, `jedec,ufs-2.0`. Top-level properties are `compatible`, `reg`, `reg-names`, `clocks`, `clock-names`, `qcom,ice`. Top-level required properties are `compatible`, `reg`; required properties discovered in nested branches are `compatible`, `reg`. Patterned child schemas are none; local definitions are none. Resource/provider roles: `compatible` selects schema applicability and the kernel OF match-table entry; `reg` describes MMIO windows, bus addresses, or register resources; `reg-names` fixes semantic ordering for multiple register windows; `clocks` integrates with the clock framework; `clock-names` integrates with the clock framework. ## Control Flow
Control flow is schema evaluation. `dt_binding_check` parses the YAML, validates the meta-schema, resolves `$ref` links, applies `properties`, `patternProperties`, required lists, item counts, const/enum checks, and composition or conditional blocks (`select`, `allOf`); it also compiles the embedded examples. `dtbs_check` applies the same rules to compiled board DTBs. During boot the kernel only consumes the DTB: OF matching selects the driver, platform/bus code maps resources, phandles are resolved, and the driver performs hardware setup.

## State and Persistence Behavior
The file has no mutable runtime state and performs no persistence. Its durable state is ABI shape: compatible strings, property names, child-node names, phandle cell counts, register and interrupt ordering, resource names, and example topology. Runtime behavior is owned by matched drivers and hardware: UFS link bring-up, UniPro/MPHY power mode, runtime PM, clock scaling, inline crypto setup, reset sequencing, error recovery, and host controller register state. Schema edits therefore persist as compatibility commitments for existing DTS files even though no code path is stored here.

## Risks
Main risks are ABI drift around compatible fallback order, clock-name arrays, `reg`/`reg-names` ICE windows, `qcom,ice` phandles, reset lines, PHY linkage, and per-SoC conditional constraints; changing compatible ordering or removing fallback strings; broadening a schema so invalid board nodes pass; tightening a schema so existing DTBs fail; and mismatches between YAML clock/reset/regulator/PHY names and driver lookup tables. Multi-role USB and Type-C bindings are especially sensitive to graph endpoints, role-switch dependencies, connector children, and wakeup semantics. UFS bindings are sensitive to per-SoC clock arrays, ICE register resources, PHY lane counts, and reset/power sequencing. The closure profile closes composed schemas with `unevaluatedProperties: false`.
