# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/input/touchscreen/resistive-adc-touch.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/input/touchscreen/resistive-adc-touch.yaml` is a Linux devicetree YAML schema for the `Generic resistive touchscreen ADC` touchscreen controller binding. Generic ADC based resistive touchscreen controller The device must be connected to an ADC device that provides channels for position measurement and optional pressure. It is not executable kernel code; it is the hardware-description ABI that DTS authors, dt-schema, and the relevant kernel subsystem rely on so the runtime driver can parse the node without board-specific ambiguity.

## Important APIs, Types, and Functions
The public API surface is the schema's accepted node shape. `compatible` uses single `const` and covers 1 compatible token: `resistive-adc-touch`. Top-level properties are `compatible`, `io-channels`, `io-channel-names`, `touchscreen-size-x`, `touchscreen-size-y`, `touchscreen-fuzz-x`, `touchscreen-fuzz-y`, `touchscreen-inverted-x`, `touchscreen-inverted-y`, `touchscreen-swapped-x-y`, `touchscreen-min-pressure`, `touchscreen-x-plate-ohms`. Across nested schemas and child nodes this file mentions 12 distinct property names; nested/all required properties include `compatible`, `io-channel-names`, `io-channels`. Node naming is constrained by no explicit node-name constraint. Touchscreen/input-facing properties define the hardware contract consumed by Linux input drivers: bus address resources none, IRQ lines none, reset or handshake GPIOs none, power/clock/reset resources none, and calibration/input capabilities `touchscreen-size-x`, `touchscreen-size-y`, `touchscreen-fuzz-x`, `touchscreen-fuzz-y`, `touchscreen-inverted-x`, `touchscreen-inverted-y`, `touchscreen-swapped-x-y`, `touchscreen-min-pressure`, `touchscreen-x-plate-ohms`. Required properties are `compatible`, `io-channels`, `io-channel-names`, which is what makes a DTS node eligible for schema-valid probing.

## Control Flow, State, and Persistence
Control flow is declarative JSON-schema evaluation rather than executable branching. `dt-doc-validate` and `dt_binding_check` load the YAML, expand `$ref` links, apply composition and conditional keywords, validate the DTS example blocks, and later `dtbs_check` applies the same contract to compiled board devicetrees. For input devices, the validated node is then consumed by I2C, SPI, platform, GPIO, regulator, and Linux input subsystem code, which interprets coordinates, axis inversion, gesture keys, wakeup behavior, and panel geometry from the properties admitted by this schema. The schema itself stores no mutable state and writes no persistent data; its persistence is the stable source-controlled hardware ABI. External references used in evaluation are `touchscreen.yaml#`; top-level/nested conditional keywords present are `allOf`, `oneOf`.

## Risks
Risks are mostly ABI and validation risks rather than algorithmic failures. Tightening required properties, changing compatible ordering, renaming resources, altering cell counts, or closing extra properties can reject existing DTS users; loosening constraints can allow nodes that later fail driver probe or misdescribe hardware. This schema has 12 top-level properties and 12 distinct nested property names, with strictness profile: composition is closed with `unevaluatedProperties: false`. Conditional branches and shared `$ref` schemas should be checked against all in-tree users before edits, because a schema-only patch can still break board builds.
