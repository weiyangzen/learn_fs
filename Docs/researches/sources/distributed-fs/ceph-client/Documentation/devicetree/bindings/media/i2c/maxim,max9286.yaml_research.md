# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/i2c/maxim,max9286.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/i2c/maxim,max9286.yaml` is a Linux Devicetree YAML schema for `Maxim Integrated Quad GMSL Deserializer`, a automotive serializer/deserializer and camera-link bridge binding. The MAX9286 deserializer receives video data on up to 4 Gigabit Multimedia Serial Links (GMSL) and outputs them on a CSI-2 D-PHY port using up to 4 data lanes. In addition to video data, the GMSL links carry a bidirectional control channel that encapsulates I2C messages. The MAX9286 forwards all I2C traffic not addressed to itself to the other side of the links, where a GMSL serializer will output it on a local I2C bus. In the other direction all I2C traffic received over GMSL by the MAX9286 is output on the local I2C bus. It is declarative ABI documentation and validation input, not executable driver code. Its job is to constrain how board DTS files describe media hardware so V4L2, media-controller, remote-control, codec, bridge, sensor, clock, regulator, GPIO, DMA, and platform/I2C driver code can discover the expected resources.

**Important APIs/types/functions:** The public API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and any OF graph or child-node patterns. `compatible` uses single `const` and covers 1 compatible token: `maxim,max9286`. Top-level properties are `#address-cells`, `#size-cells`, `compatible`, `reg`, `poc-supply`, `enable-gpios`, `gpio-controller`, `#gpio-cells`, `maxim,bus-width`, `maxim,i2c-remote-bus-hz`, `maxim,reverse-channel-microvolt`, `maxim,gpio-poc`, `ports`, `i2c-mux`. Top-level required properties are `compatible`, `reg`, `ports`, `i2c-mux`; required properties found across nested schemas include `compatible`, `data-lanes`, `i2c-mux`, `maxim,gpio-poc`, `poc-supply`, `port`, `port@4`, `ports`, `reg`. The node acts as a I2C client node selected by parent bus address cells. Important property roles: `#address-cells` enables validated child nodes or provider specifiers; `#size-cells` enables validated child nodes or provider specifiers; `compatible` selects the OF match table entry and stable hardware ABI; `reg` carries the I2C address or MMIO register range; `poc-supply` links power rails or power-domain providers; `enable-gpios` controls hardware reset, enable, or power-down sequencing; `#gpio-cells` enables validated child nodes or provider specifiers; `ports` describes media-controller OF graph links and endpoint topology; `i2c-mux` models remote I2C access behind serializers or deserializers. Patterned child schemas are `^port[0-3]-poc-supply$`; graph or child-node properties discovered in nested schemas are `endpoint`, `port`, `port@0`, `port@1`, `port@2`, `port@3`, `port@4`, `ports`. Numeric/item constraints include no explicit numeric min/max/item limits collected.

**Control flow:** Control flow is dt-schema evaluation rather than imperative logic. `dt_binding_check` loads the core meta-schema, resolves every `$ref`, applies `properties`, `required`, item/count limits, and composition branches, validates inline examples, and enforces the unknown-property policy. At runtime the YAML is not executed: the compiled DTB node is matched through the driver's OF table, and media graph parsing follows `port`/`ports` endpoints to connect sensors, bridges, serializers, deserializers, receivers, codecs, and SoC capture or processing blocks. Resource acquisition then proceeds through standard helpers for I2C/platform devices, regulators, clocks, resets, GPIOs, IRQs, DMA/IOMMU, firmware, and child remote buses when those properties are present.

**State and persistence behavior:** The schema has no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: accepted compatible strings, required supplies/clocks/resets/IRQs, endpoint lane layouts, child-node names, remote-I2C topology, and MMIO or I2C address shapes become long-lived DTB contracts. Runtime state such as video streaming, link training, sensor mode selection, codec sessions, remote serializer state, radio tuning, frame buffers, and power sequencing belongs to the matching kernel drivers and hardware.

**Risks:** Risks center on Devicetree ABI drift and media graph mismatches. Changing compatible values or fallback order can break driver binding; renaming supplies, clocks, GPIOs, interrupts, reset lines, `#*-cells`, or child nodes can break probe-time resource lookup; tightening endpoint lane counts or port numbering can reject valid boards or silently disconnect media links. Serializer/deserializer bindings add risk around remote I2C aliases, PoC supplies, GPIO forwarding, and link topology. Codec and SoC processing bindings add risk around clocks, power domains, IOMMU/DMA resources, and firmware/mailbox style dependencies. The closure profile is: top-level unknown properties are rejected by `additionalProperties: false`. This file has 14 top-level properties and 22 distinct nested property names, so schema cleanups should be checked against all compatibles and real DTS users, not only the filename's nominal device.

**Test signals:** Primary validation signals are `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/media/i2c/maxim,max9286.yaml` and `make dtbs_check` for boards instantiating each compatible. Useful negative tests remove required regulators/clocks/resets/IRQs, use invalid endpoint `data-lanes` or port numbering, misspell vendor properties, and exercise every compatible branch. Runtime integration is indicated by successful driver probe, correct media-controller entity/link topology, valid V4L2 async subdevice binding, stable power sequencing, clean stream-on/stream-off for sensors and bridges, successful codec or image-processing queue setup for SoC blocks, and no dtbs_check regressions for existing DTS examples.
