# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/firmware/arm,scpi.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `System Control and Power Interface (SCPI) Message Protocol`. In this tree it is a firmware interface binding used to describe secure monitor, system controller, mailbox, or service-layer communication with platform firmware; it constrains how board DTS files describe the hardware and how Linux drivers discover it through OF matching, phandles, and common binding references. The source description says: Firmware implementing the SCPI described in ARM document number ARM DUI 0922B ("ARM Compute Subsystem SCP: Message Interface Protocols")[0] can be used by Linux to initiate various system control and power operations. This binding is intended to define the interface the firmware implementing the SCPI provide for OSPM in the device tree. [0] http://infocenter...

**Important APIs/types/functions:** This is declarative schema rather than executable code. The public ABI surface is `$id` `http://devicetree.org/schemas/firmware/arm,scpi.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and the referenced schemas used by dt-schema. Compatible strings are `arm,scpi`, `arm,scpi-pre-1.0`, `amlogic,meson-gxbb-scpi`. Required properties are `compatible`, `mboxes`, `shmem`. Important properties include `$nodename`, `compatible`, `mboxes`, `shmem`, `power-controller`, `sensors`, `clocks`. Referenced schemas are `/schemas/types.yaml#/definitions/uint32`, `/schemas/types.yaml#/definitions/uint32-array`. Property roles include `compatible` for driver match key and hardware ABI identifier; `mboxes` for mailbox channels; `shmem` for shared-memory regions; `clocks` for clock provider phandles. The top-level closure rule is `additionalProperties: false`. Maintainers: Sudeep Holla <sudeep.holla@arm.com>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel subsystems, not by this YAML file. `dt_binding_check` loads the core meta-schema, resolves references such as `/schemas/types.yaml#/definitions/uint32`, `/schemas/types.yaml#/definitions/uint32-array`, applies `properties`, `required`, enum/const/items limits, and any `allOf` or conditional branches, then validates the inline examples. During boot, a matching DT node is compiled into the DTB, the kernel matches `compatible`, subsystem code reads cells and phandles, and the bound driver consumes resources such as clock provider phandles, mailbox channels, shared-memory mailboxes. It has no nested conditional schema branches beyond direct property validation. Nested or patterned child schema surfaces include `power-controller`, `sensors`.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, resource topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though no kernel state is stored here.

**Dependencies and integration points:** Integrated with firmware, mailbox, shared-memory, secure-monitor, system-controller, clock, reset, power, and FPGA manager drivers. Direct schema dependencies are `/schemas/types.yaml#/definitions/uint32`, `/schemas/types.yaml#/definitions/uint32-array`; resource dependencies visible in the property set include clock provider phandles, mailbox channels, shared-memory mailboxes. Driver integration is through `compatible`, while client/provider integration is through cell properties, phandle arrays, child schemas, and bus-standard properties declared or inherited here.

**Risks:** Main risks are schema ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, missing required clocks/resets/interrupts/power domains, stale examples, and conditional branches that accept one SoC variant while rejecting another valid one. Unknown-property policy also matters: `additionalProperties: false` can either catch misspelled DTS properties or allow legacy extension points. For bindings with child nodes or graph/connector references, parent-child address-cell and port layout mistakes can pass driver review only if dtbs_check coverage is weak.

**Test signals:** Run `make dt_binding_check DT_SCHEMA_FILES=sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/firmware/arm,scpi.yaml` and `make dtbs_check` against DTS users of every compatible family. Verify inline examples compile, required-property failures are reported, compatible-specific branches are exercised, inherited schemas resolve, and drivers still probe with the resources described here.
