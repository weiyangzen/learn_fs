# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/dma/ti/k3-pktdma.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Texas Instruments K3 DMSS PKTDMA`. In this tree it is a DMA engine, DMA router, or DMA-capable IP binding used by dmaengine providers and DMA client phandle specifiers; it constrains how board DTS files describe the hardware and how Linux drivers discover it through OF matching, phandles, and common binding references. The source description says: The Packet DMA (PKTDMA) is intended to perform similar functions as the packet mode channels of K3 UDMA-P. PKTDMA only includes Split channels to service PSI-L based peripherals. The peripherals can be PSI-L native or legacy, non PSI-L native peripherals with PDMAs. **Important APIs/types/functions:** This is declarative schema rather than executable code. The public ABI surface is `$id` `http://devicetree.org/schemas/dma/ti/k3-pktdma.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and the referenced schemas used by dt-schema. Compatible strings are `ti,am64-dmss-pktdma`. Required properties are `compatible`, `#dma-cells`, `reg`, `reg-names`, `msi-parent`, `ti,sci`, `ti,sci-dev-id`, `ti,sci-rm-range-tchan`, `ti,sci-rm-range-tflow`, `ti,sci-rm-range-rchan`, `ti,sci-rm-range-rflow`. Important properties include `compatible`, `#dma-cells`, `reg`, `reg-names`, `msi-parent`, `ti,sci-rm-range-tchan`, `ti,sci-rm-range-tflow`, `ti,sci-rm-range-rchan`, `ti,sci-rm-range-rflow`. Referenced schemas are `/schemas/dma/dma-controller.yaml#`, `/schemas/arm/keystone/ti,k3-sci-common.yaml#`, `/schemas/types.yaml#/definitions/uint32-array`. Property roles include `compatible` for driver match key and hardware ABI identifier; `#dma-cells` for DMA client specifier width; `reg` for MMIO, I2C/SPI address, or child register address. The top-level closure rule is `unevaluatedProperties: false`. Maintainers: Peter Ujfalusi <peter.ujfalusi@gmail.com>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel subsystems, not by this YAML file. `dt_binding_check` loads the core meta-schema, resolves references such as `/schemas/dma/dma-controller.yaml#`, `/schemas/arm/keystone/ti,k3-sci-common.yaml#`, `/schemas/types.yaml#/definitions/uint32-array`, applies `properties`, `required`, enum/const/items limits, and any `allOf` or conditional branches, then validates the inline examples. During boot, a matching DT node is compiled into the DTB, the kernel matches `compatible`, subsystem code reads cells and phandles, and the bound driver consumes resources such as MSI interrupt domains, TI SCI firmware resource management. Conditional/schema-composition points include `allOf`, so different compatibles or child-node shapes can activate different required-property sets. Nested or patterned child schema surfaces include `ti,sci-rm-range-tchan`, `ti,sci-rm-range-tflow`, `ti,sci-rm-range-rchan`, `ti,sci-rm-range-rflow`.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, resource topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though no kernel state is stored here.

**Dependencies and integration points:** Integrated with dmaengine and Devicetree DMA client code. Direct schema dependencies are `/schemas/dma/dma-controller.yaml#`, `/schemas/arm/keystone/ti,k3-sci-common.yaml#`, `/schemas/types.yaml#/definitions/uint32-array`; resource dependencies visible in the property set include MSI interrupt domains, TI SCI firmware resource management. Driver integration is through `compatible`, while client/provider integration is through cell properties, phandle arrays, child schemas, and bus-standard properties declared or inherited here.

**Risks:** Main risks are schema ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, missing required clocks/resets/interrupts/power domains, stale examples, and conditional branches that accept one SoC variant while rejecting another valid one. Unknown-property policy also matters: `unevaluatedProperties: false` can either catch misspelled DTS properties or allow legacy extension points. For bindings with child nodes or graph/connector references, parent-child address-cell and port layout mistakes can pass driver review only if dtbs_check coverage is weak.
