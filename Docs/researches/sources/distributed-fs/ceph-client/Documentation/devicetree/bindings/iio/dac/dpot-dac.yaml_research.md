# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/iio/dac/dpot-dac.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/iio/dac/dpot-dac.yaml` is a Linux Devicetree YAML schema for `DAC emulation using a digital potentiometer`, a IIO digital-to-analog converter binding. It is assumed that the dpot is used as a voltage divider between the current dpot wiper setting and the maximum resistance of the dpot. The divided voltage is provided by a vref regulator. .------. .-----------. | | | vref |--' .---. | regulator |--. | | '-----------' | | d | | | p | | | o | wiper | | t |<---------+ | | | | '---' dac output voltage | | '------+------------+ It is declarative ABI documentation and validation input, not executable driver code. Its main job is to make board DTS nodes describe IIO hardware, IIO providers, or IIO consumers with the resources the matching kernel driver expects.

**Important APIs/types/functions:** The public API surface is the schema itself: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and the accepted child-node patterns. `compatible` uses single `const` and covers 1 compatible token: `dpot-dac`. Top-level properties are `compatible`, `vref-supply`, `io-channels`, `io-channel-names`, `#io-channel-cells`. Top-level required properties are `compatible`, `vref-supply`, `io-channels`, `io-channel-names`; required properties found across nested schemas include `compatible`, `io-channel-names`, `io-channels`, `vref-supply`. The binding acts as a IIO consumer/rescale node driven by upstream `io-channels`. Important roles: `compatible` selects the OF match table entry and stable hardware ABI; `vref-supply` links the device to regulator framework supplies; `io-channels` connects provider/consumer IIO channels; `io-channel-names` connects provider/consumer IIO channels; `#io-channel-cells` connects provider/consumer IIO channels. Patterned child schemas are none; named child-channel properties discovered in nested schemas are no explicit named channel child nodes. Numeric/item constraints include no explicit numeric min/max/item limits collected.

**Control flow:** Control flow is dt-schema evaluation. `dt_binding_check` loads the core meta-schema, resolves every `$ref`, applies the top-level and nested `properties`, evaluates `allOf`/`oneOf`/conditionals, checks required fields, validates examples, and enforces the closure policy. At boot there is no YAML execution: the compiled DTB node is matched through the driver's OF table, then IIO, regulator, clock, GPIO, IRQ, SPI/I2C/platform, DMA, and firmware helpers consume the resources named by this contract. For schemas with `channel@N` or patterned child nodes, parent address/size cells control how per-channel configuration is discovered by the driver.

**State and persistence behavior:** The file owns no mutable runtime state and persists no data. Its persistent behavior is ABI stability: accepted compatible strings, required resource names, channel indices, phandle cell counts, child-node names, and example layouts become long-lived contracts for DTS/DTB producers. Runtime state such as ADC samples, DAC output values, buffer enablement, calibration, oversampling, alarms, or data-ready interrupts belongs to the corresponding IIO driver and hardware; this schema only constrains how that stateful device is described.

**Risks:** Risks center on Devicetree ABI drift. Changing compatible values or fallback ordering can break driver matching; renaming supplies, clocks, interrupts, GPIOs, or `#io-channel-cells` breaks probe-time resource lookup; tightening required properties or child-node patterns can reject existing boards. Channel-indexed schemas need care because driver channel tables, allowed `reg` values, and analog pin functions must stay aligned. The closure profile is: top-level unknown properties are rejected by `additionalProperties: false`. Because this file contains 5 top-level properties and 5 distinct nested property names, broad cleanups should be checked against examples, all compatible variants, and in-tree DTS users rather than only the nominal device named in the filename.

**Test signals:** Primary validation signals are `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/iio/dac/dpot-dac.yaml` and `make dtbs_check` for boards instantiating each compatible. High-value negative tests remove required supplies/clocks/IRQs, use bad channel `reg` values, misspell vendor properties, and exercise every conditional compatible branch. Runtime integration is indicated by successful driver probe with regulators and clocks enabled, correct IIO channel registration, valid `io-channels` consumers, data-ready IRQ behavior where modeled, buffered capture or DAC output where relevant, and no dtbs_check regressions for existing DTS examples.
