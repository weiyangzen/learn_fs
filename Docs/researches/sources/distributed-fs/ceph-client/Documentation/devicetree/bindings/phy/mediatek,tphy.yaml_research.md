# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/phy/mediatek,tphy.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/phy/mediatek,tphy.yaml` is a Linux Devicetree YAML schema for `MediaTek T-PHY Controller`, a Linux PHY provider binding. The T-PHY controller supports physical layer functionality for a number of controllers on MediaTek SoCs, includes USB2.0, USB3.0, PCIe and SATA. It is declarative firmware ABI documentation and dt-schema validation input, not executable kernel code. Its role is to make board DTS/DTB nodes describe PHY blocks, lanes, pads, ports, supplies, clocks, resets, and phandle provider contracts in the form the matching Linux PHY or controller driver expects.

**Control flow:** Control flow is dt-schema evaluation. `dt_binding_check` parses the YAML, validates it against the core meta-schema, resolves `$ref` dependencies, applies `properties` and `patternProperties`, evaluates `allOf`/`oneOf`/`anyOf`/conditional branches, checks `required` lists and item counts, compiles examples, and enforces the closure rule. At boot the YAML is not interpreted; firmware supplies a compiled DTB node, the kernel matches `compatible` in the relevant OF table, and the PHY/provider driver reads `reg`, clocks, resets, supplies, child lanes/ports, and `#phy-cells` to register PHYs. Consumer controllers later resolve `phys` phandles and invoke the generic PHY framework for init, power-on, mode setting, calibration, and power-off.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence. Its durable state is ABI shape: compatible strings, property names, valid enum values, provider cell counts, child-node naming, lane or port numbering, and allowed topology. Runtime state such as PLL lock, link training, lane muxing, PHY mode, impedance tuning, analog calibration, reset sequencing, and power transitions lives in the matching kernel driver and hardware registers; this schema only constrains how those resources and modes are represented in firmware.

**Risks:** Primary risks are PHY ABI drift and resource lookup mismatch. Removing or reordering compatible fallbacks can break legacy DTBs; changing `#phy-cells`, child `reg` numbering, lane names, or port names can break consumers that already reference the provider; renaming clocks, resets, supplies, GPIOs, or power domains can break driver probe even when the hardware block is unchanged. Multi-protocol SerDes and pad-controller schemas are especially sensitive because lane mux enums, protocol names, and companion USB2/USB3 or PCIe/SATA relationships must align with driver tables and board wiring. The closure profile is: top-level unknown properties are rejected by `additionalProperties: false`. Because this schema has 9 top-level properties and 23 distinct nested property names, broad edits should be checked against every compatible variant, examples, and existing DTS users.

**Test signals:** Primary validation signals are `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/phy/mediatek,tphy.yaml` in a kernel tree with dt-schema installed and `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/phy/mediatek,tphy.yaml` for boards using these compatibles. Useful negative checks omit required clocks/resets/supplies, use invalid `#phy-cells`, bad child-node names, wrong lane `reg` values, or unsupported enum values. Runtime integration signals are successful driver probe, registered PHY providers with expected phandle arguments, consumers resolving `phys`, clocks and regulators balanced across suspend/resume, link bring-up for the relevant USB/PCIe/SATA/UFS/MIPI/SerDes protocol, and no new schema warnings for examples or in-tree DTS files.
