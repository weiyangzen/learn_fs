# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/ti,sci-intr.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Texas Instruments K3 Interrupt Router`. In this tree it is an interrupt controller binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: The Interrupt Router (INTR) module provides a mechanism to mux M interrupt inputs to N interrupt outputs, where all M inputs are selectable to be driven per N output. Interrupt Router +----------------------+ | Inputs Outputs | +-------+ | +------+ +-----+ | | GPIO |----------->| | irq0 | | 0 | | Host IRQ +-------+ | +------+ +-----+ | controller | . . | +-------+ +-------+ | . . |----->| IRQ | | INTA |----------->| . . | +-------+ +-------+ | . +-----+ | | +------+ | N | | | | irqM | +-----+ | | +------+ | | | +----------------------+ There is one register per output (MUXCNTL_N) that controls the selection. Configuration of these MUXCNTL_N registers is done by a system controller (like the Device Memory and Security Controller on K3 AM654 SoC). System controller will keep track of the used and unused registers within the Router. Driver should request the system controller to get the range of GIC IRQs assigned to the requesting hosts. It is the drivers responsibility to keep track of Host IRQs. Communication between the host processor running an OS and the system controller happens through a protocol called TI System Control Interface (TISCI protocol).

**Important APIs/types/functions:** This YAML is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/interrupt-controller/ti,sci-intr.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and any referenced dt-schema fragments. Compatible strings or compatible-pattern values are `ti,sci-intr`. Required properties are `compatible`, `interrupt-controller`, `#interrupt-cells`, `ti,sci`, `ti,sci-dev-id`, `ti,interrupt-ranges`. Important top-level properties are `compatible`, `ti,intr-trigger-type`, `reg`, `interrupt-controller`, `#interrupt-cells`, `ti,interrupt-ranges`. Direct and nested `$ref` dependencies are `/schemas/arm/keystone/ti,k3-sci-common.yaml#`, `/schemas/types.yaml#/definitions/uint32`, `/schemas/types.yaml#/definitions/uint32-matrix`. Property roles include `compatible` for driver match key and stable hardware ABI identifier; `ti,intr-trigger-type` for binding-specific property constrained by the schema; `reg` for MMIO range, bus address, or child register selector; `interrupt-controller` marks the node as an interrupt domain provider; `#interrupt-cells` for interrupt specifier cell count consumed by child/client nodes; `ti,interrupt-ranges` for binding-specific property constrained by the schema. The top-level unknown-property policy is `unevaluatedProperties: false`. Maintainers are `Lokesh Vutla <lokeshvutla@ti.com>`.

**Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. Schema composition/conditional keywords present: `allOf`, `else`, `if`, `then`. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IRQ domain code uses it to translate DT interrupt specifiers into Linux IRQs and route them to an upstream parent domain. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as `reg`. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.
