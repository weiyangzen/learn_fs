# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/dma/stm32/st,stm32-mdma.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `STMicroelectronics STM32 MDMA Controller`. In this tree it is a DMA engine, DMA router, or DMA-capable IP binding used by dmaengine providers and DMA client phandle specifiers; it constrains how board DTS files describe the hardware and how Linux drivers discover it through OF matching, phandles, and common binding references. The source description says: The STM32 MDMA is a general-purpose direct memory access controller capable of supporting 64 independent DMA channels with 256 HW requests. DMA clients connected to the STM32 MDMA controller must use the format described in the dma.txt file, using a five-cell specifier for each channel: a phandle to the MDMA controller plus the following five integer cells: ...

**Important APIs/types/functions:** This is declarative schema rather than executable code. The public ABI surface is `$id` `http://devicetree.org/schemas/dma/stm32/st,stm32-mdma.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and the referenced schemas used by dt-schema. Compatible strings are `st,stm32h7-mdma`. Required properties are `compatible`, `reg`, `clocks`, `interrupts`. Important properties include `#dma-cells`, `compatible`, `reg`, `clocks`, `interrupts`, `resets`, `st,ahb-addr-masks`. Referenced schemas are `/schemas/dma/dma-controller.yaml#`, `/schemas/types.yaml#/definitions/uint32-array`. Property roles include `#dma-cells` for DMA client specifier width; `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address; `clocks` for clock provider phandles; `interrupts` for interrupt line routing; `resets` for reset controller phandles. The top-level closure rule is `unevaluatedProperties: false`. Maintainers: Amelie Delaunay <amelie.delaunay@foss.st.com>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel subsystems, not by this YAML file. `dt_binding_check` loads the core meta-schema, resolves references such as `/schemas/dma/dma-controller.yaml#`, `/schemas/types.yaml#/definitions/uint32-array`, applies `properties`, `required`, enum/const/items limits, and any `allOf` or conditional branches, then validates the inline examples. During boot, a matching DT node is compiled into the DTB, the kernel matches `compatible`, subsystem code reads cells and phandles, and the bound driver consumes resources such as clock provider phandles, reset controller phandles. Conditional/schema-composition points include `allOf`, so different compatibles or child-node shapes can activate different required-property sets. Nested or patterned child schema surfaces include `st,ahb-addr-masks`.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, resource topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though no kernel state is stored here.

**Dependencies and integration points:** Integrated with dmaengine and Devicetree DMA client code. Direct schema dependencies are `/schemas/dma/dma-controller.yaml#`, `/schemas/types.yaml#/definitions/uint32-array`; resource dependencies visible in the property set include clock provider phandles, reset controller phandles. Driver integration is through `compatible`, while client/provider integration is through cell properties, phandle arrays, child schemas, and bus-standard properties declared or inherited here.

**Risks:** Main risks are schema ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, missing required clocks/resets/interrupts/power domains, stale examples, and conditional branches that accept one SoC variant while rejecting another valid one. Unknown-property policy also matters: `unevaluatedProperties: false` can either catch misspelled DTS properties or allow legacy extension points. For bindings with child nodes or graph/connector references, parent-child address-cell and port layout mistakes can pass driver review only if dtbs_check coverage is weak.

**Test signals:** Run `make dt_binding_check DT_SCHEMA_FILES=sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/dma/stm32/st,stm32-mdma.yaml` and `make dtbs_check` against DTS users of every compatible family. Verify inline examples compile, required-property failures are reported, compatible-specific branches are exercised, inherited schemas resolve, and drivers still probe with the resources described here. The file includes 1 example block(s), which are part of the dt-schema validation signal.
