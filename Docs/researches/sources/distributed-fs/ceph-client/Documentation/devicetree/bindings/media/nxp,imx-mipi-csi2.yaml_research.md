# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/nxp,imx-mipi-csi2.yaml

**Purpose:** Defines the Devicetree JSON-schema ABI for `NXP i.MX7 and i.MX8 MIPI CSI-2 receiver`. It is a MIPI CSI-2 receiver/bridge media graph binding in the Ceph client Linux source snapshot, constraining how board DTS/DTB files describe media hardware so Linux media, V4L2 mem2mem, platform, clock, reset, power-domain, IOMMU, and graph helpers can bind the correct driver resources. The source description says: The NXP i.MX7 and i.MX8 families contain SoCs that include a MIPI CSI-2 receiver IP core named CSIS. The IP core originates from Samsung, and may be compatible with some of the Exynos4 and S5P SoCs. i.MX7 SoCs use CSIS version 3.3, and i.MX8 SoCs use CSIS version 3.6.3. While the CSI-2 receiver is separate from the MIPI D-PHY IP core, the PHY is completely wrapped by the CSIS and doesn't expose a control interface of its own. This binding thus covers both IP cores.

**Important APIs/types/functions:** This is declarative schema, so the exported API is the binding contract rather than C functions. Public surfaces include `$id` `http://devicetree.org/schemas/media/nxp,imx-mipi-csi2.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, examples, and dt-schema references. The `compatible` property uses `oneOf` with 2 accepted forms and accepts `fsl,imx7-mipi-csi2`, `fsl,imx8mm-mipi-csi2`, `fsl,imx8mp-mipi-csi2`. Top-level required properties are `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `power-domains`, `ports`; required names across nested/conditional schemas include `clock-names`, `clocks`, `compatible`, `data-lanes`, `interrupts`, `phy-supply`, `ports`, `power-domains`, `reg`, `resets`. Top-level properties are `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `power-domains`, `phy-supply`, `resets`, `clock-frequency`, `fsl,num-channels`, `ports`; all nested property names include `clock-frequency`, `clock-names`, `clocks`, `compatible`, `data-lanes`, `endpoint`, `fsl,num-channels`, `interrupts`, `phy-supply`, `port@0`, `port@1`, `ports`, `power-domains`, `reg`, `resets`. Resource constraints visible in the schema include `compatible`, `reg` (maxItems=1), `interrupts` (maxItems=1), `clocks` (minItems=3), `clock-names` (minItems=3; names=pclk/wrap/phy/axi), `power-domains` (maxItems=1), `phy-supply`, `resets`, `clock-frequency` (default=166000000; deprecated=True), `fsl,num-channels` (default=1), `ports`. Closure is `additionalProperties: False`.

**Control flow:** Runtime control flow is supplied by dt-schema and kernel probing. `dt_binding_check` loads the core meta-schema, resolves references, validates the compatible form, applies required lists and `minItems`/`maxItems`/`const` restrictions, evaluates conditionals, and compiles the inline examples. At boot the DTB node is matched by `compatible`; the platform or media driver then reads MMIO ranges, named interrupts, clocks, resets, power domains, IOMMU streams, DMA/interconnect paths, firmware or reserved-memory phandles, and graph endpoints. Schema composition uses `allOf`, `else`, `if`, `oneOf`, `then`. Validation can therefore change by compatible string, for example by tightening clock/reset counts, requiring SoC-specific helper phandles, or allowing/deprecating child codec nodes. Media graph integration is explicit through `port@0`, `port@1`; the schema references graph/video interface rules and mentions `endpoint` 10 time(s). Endpoint validation covers remote links, lane descriptions, bus type, bus width, and synchronization/pixel-clock polarity where the hardware exposes those signals.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence itself. Its persistent effect is ABI stability for DTS files and shipped DTBs: compatible strings, child-node names, phandle relationships, address ranges, cell counts, and media graph topology are long-lived hardware descriptions. Any change to required properties, resource ordering, child object schemas, or unknown-property policy can invalidate existing board descriptions even though no kernel state is written by the YAML.

**Dependencies and integration points:** Direct schema references are `/schemas/graph.yaml#/$defs/port-base`, `/schemas/graph.yaml#/properties/port`, `/schemas/graph.yaml#/properties/ports`, `/schemas/types.yaml#/definitions/uint32`, `video-interfaces.yaml#`. Runtime dependencies are V4L2 async/media-controller graph links through `ports`, `port`, and `endpoint` nodes, genpd power domains, clock provider phandles and fixed clock-name ordering, reset-controller phandles. No nested object nodes are defined beyond common schema references. Maintainers listed in the binding are `Rui Miguel Silva <rmfrfs@gmail.com>`, `Laurent Pinchart <laurent.pinchart@ideasonboard.com>`.

**Risks:** Key risks: compatible-string or fallback-order drift can break OF matching and dtbs_check expectations; resource array ordering is ABI-sensitive for `reg-names`, `clock-names`, `interrupt-names`, `power-domain-names`, and `reset-names`; media graph mistakes in `remote-endpoint`, lane numbering, bus type, or required ports can leave cameras disconnected even when the platform device probes; SoC-specific power-domain count differences are easy to regress in fallback compatibles. The closure policy is `additionalProperties: False`, so unknown properties are intentionally rejected after referenced schemas are evaluated.

Run `make dtbs_check` against DTS users of `fsl,imx7-mipi-csi2`, `fsl,imx8mm-mipi-csi2`, `fsl,imx8mp-mipi-csi2` to exercise compatible-specific branches, graph endpoint requirements, resource counts, and referenced schemas.
