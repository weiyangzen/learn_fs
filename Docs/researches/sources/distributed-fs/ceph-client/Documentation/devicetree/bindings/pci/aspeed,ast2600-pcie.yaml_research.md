# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pci/aspeed,ast2600-pcie.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pci/aspeed,ast2600-pcie.yaml` defines the Linux Devicetree YAML schema for `ASPEED PCIe Root Complex Controller`, a PCIe host or endpoint controller binding. The schema description says: The ASPEED PCIe Root Complex controller provides PCI Express Root Complex functionality for ASPEED SoCs, such as the AST2600 and AST2700. This controller enables connectivity to PCIe endpoint devices, supporting memory and I/O windows, MSI and INTx interrupts, and integration with the SoC's clock, reset, and pinctrl subsystems. On AST2600, the PCIe Root Port device number is always 8. It is declarative ABI documentation and validation input rather than executable kernel code; its practical role is to make DTS/DTB hardware descriptions match the resources, topology, and compatible strings expected by the relevant kernel subsystem before probe.

## Important APIs, Types, and Functions
The public API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses an `enum` and exposes 2 tokens: `aspeed,ast2600-pcie`, `aspeed,ast2700-pcie`. Top-level properties are `compatible`, `reg`, `ranges`, `interrupts`, `resets`, `reset-names`, `aspeed,ahbc`, `aspeed,pciecfg`, `interrupt-controller`. Top-level required properties are `reg`, `interrupts`, `bus-range`, `ranges`, `resets`, `reset-names`, `msi-controller`, `interrupt-controller`, `interrupt-map-mask`, `interrupt-map`; required properties collected from nested schema branches include `aspeed,ahbc`, `aspeed,pciecfg`, `bus-range`, `clocks`, `interrupt-controller`, `interrupt-map`, `interrupt-map-mask`, `interrupts`, `msi-controller`, `phys`, `ranges`, `reg`, `reset-names`, `resets`. Patterned child schemas are `^pcie@[0-9a-f]+,0$`. Numeric and collection constraints include `maxItems=1`, `minItems=2`, `maxItems=2`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `reg` describes MMIO ranges, bus child addresses, port selectors, or cell offsets; `ranges` is a PCIe address/window or link capability contract; `interrupts` routes status, error, RX/TX, MSI, or completion IRQs; `resets` integrates with common clock, reset, PM, DMA/IOMMU, or reserved-memory providers; `reset-names` fixes resource ordering visible to drivers. The highest-risk ABI details are compatible fallback ordering, `reg`/`reg-names`, `ranges`, bus-range, MSI and interrupt-map wiring, PHY/reset/clock ordering, PERST#/wake GPIOs, link-generation and lane-count properties, and endpoint vs root-complex mode constraints.

## Control Flow
Runtime control flow is supplied by dt-schema and kernel subsystem code, not by this YAML file. `dt_binding_check` loads the meta-schema, resolves `$ref` entries, applies `properties`, evaluates `allOf`, checks required fields, validates `minItems`/`maxItems` and enum/const constraints, validates embedded examples, and applies the closure rule. During boot, the compiled DTB node is matched by `compatible`; then platform, PCI, SDIO, SPI, MDIO, NVMEM, OPP, PCIe, netdev, wireless, accelerator, storage, clock, reset, regulator, IRQ, GPIO, IOMMU, and power-domain helpers consume the phandles and resource arrays that this schema validates. Child nodes are discovered declaratively through fixed names, pattern properties, address cells, and referenced child schemas.

## State and Persistence Behavior
The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: compatible strings, required resource names, register and interrupt ordering, phandle and cell counts, child-node names, fallback ordering, and example layouts become long-lived contracts in board DTS files and shipped DTBs. Runtime state belongs to the matching drivers and hardware after probe, including PCI host bridge registration, ECAM/config-space access, link training state, MSI domain state, DMA/IOMMU windows, endpoint BAR/function configuration, reset recovery, and runtime PM.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, link training, calibration lookup, OPP selection, NVMEM cell reads, or bus enumeration. Tightening required properties can reject existing boards; loosening them can hide missing clocks, resets, interrupts, supplies, PHY links, PCIe windows, memory regions, OPP fields, or NVMEM cells. Child-node schemas need special care because address cells, port IDs, PCI interrupt maps, wireless calibration cells, NVMEM layouts, and OPP tables must match driver-side assumptions. This schema closes composed schemas with `unevaluatedProperties: false`. It has 9 top-level properties and 12 distinct nested property names, so broad edits should be checked against all compatible variants and DTS users, not just the nominal filename.
