# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/clock/mediatek,syscon.yaml

Purpose: YAML Devicetree schema for `MediaTek Clock controller syscon's`. It documents and validates nodes with compatibles `mediatek,mt2701-bdpsys`, `mediatek,mt2701-imgsys`, `mediatek,mt2701-vdecsys`, `mediatek,mt2712-bdpsys`, `mediatek,mt2712-imgsys`, `mediatek,mt2712-jpgdecsys`, `mediatek,mt2712-mcucfg`, `mediatek,mt2712-mfgcfg`, `mediatek,mt2712-vdecsys`, `mediatek,mt2712-vencsys`, `mediatek,mt6735-imgsys`, `mediatek,mt6735-mfgcfg`, `mediatek,mt6735-vdecsys`, `mediatek,mt6735-vencsys`, and 34 more. The MediaTek clock controller syscon's provide various clocks to the system.

Important APIs/types/functions: This file is a schema contract rather than runtime code. Its externally visible API is the accepted `compatible` set (`mediatek,mt2701-bdpsys`, `mediatek,mt2701-imgsys`, `mediatek,mt2701-vdecsys`, `mediatek,mt2712-bdpsys`, `mediatek,mt2712-imgsys`, `mediatek,mt2712-jpgdecsys`, `mediatek,mt2712-mcucfg`, `mediatek,mt2712-mfgcfg`, `mediatek,mt2712-vdecsys`, `mediatek,mt2712-vencsys`, `mediatek,mt6735-imgsys`, `mediatek,mt6735-mfgcfg`, `mediatek,mt6735-vdecsys`, `mediatek,mt6735-vencsys`, and 34 more), required properties (`compatible`, `#clock-cells`), and provider/consumer ABI described by `compatible`, `reg` max 1 item(s), `#clock-cells` 1, `power-domains` max 1 item(s). clock provider uses `#clock-cells = 1`; MMIO `reg` is max 1 item(s).

Control flow: There is no executable control flow. Validation flows through `dt-schema`: the YAML document is loaded against the core meta-schema, a DTS node's `compatible` selects this binding, `required` enforces mandatory fields, and if, then, else handle variant-specific shape. The examples exercise nodes such as clock-controller and provide schema smoke coverage.

State and persistence behavior: The binding persists hardware description in DTS and compiled DTB files. Clock, reset, and power-domain identifiers referenced by consumers become stable ABI between board DTS files, dt-binding headers, and Linux providers. The schema stores no runtime state; boot-time state appears when the matched driver maps `reg`, registers providers, and applies any parent clock, assigned-clock, reset, or power-domain relationships encoded in the node.

Dependencies and integration points: Depends on composition/conditional keys `if`, `then`, `else`. Integration is primarily with MediaTek clock, reset, syscon, infracfg, and topckgen drivers consume these compatibles and publish clock IDs from `dt-bindings/clock/mt*-clk.h` headers. Downstream device nodes consume the exported resources through phandles, so `#clock-cells`, `#reset-cells`, `#power-domain-cells`, `clock-names`, and header-defined IDs must remain synchronized with provider drivers and DTS users. Key control inputs modeled here are power-domain attachment.

Risks: The main risk is ABI drift: changing compatible strings, provider cell counts, required properties, or header IDs can break existing DTS files or driver probing. A wrong `reg` range can bind the driver to the wrong MMIO block, and missing parent clocks, power domains, resets, supplies, or assigned-clock data can defer probe or leave hardware ungated. Because this schema forbids unknown properties, new board-specific properties need explicit schema support.

Test signals: Run Devicetree schema checks such as `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/clock/mediatek,syscon.yaml` and DTS validation for boards using `mediatek,mt2701-bdpsys`, `mediatek,mt2701-imgsys`, `mediatek,mt2701-vdecsys`, `mediatek,mt2712-bdpsys`, `mediatek,mt2712-imgsys`, `mediatek,mt2712-jpgdecsys`, and 42 more. Good signals include clean example validation, no unresolved `$ref` or include paths, provider cell counts matching dt-binding headers, and boot logs showing the matching clock/reset driver registering expected providers without probe deferral.
