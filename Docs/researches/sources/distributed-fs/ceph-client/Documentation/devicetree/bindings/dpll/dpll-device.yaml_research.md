# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/dpll/dpll-device.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Digital Phase-Locked Loop (DPLL) Device`. In this tree it is a digital phase-locked loop binding used to describe DPLL devices, pins, references, and frequency capabilities; it constrains how board DTS files describe the hardware and how Linux drivers discover it through OF matching, phandles, and common binding references. The source description says: Digital Phase-Locked Loop (DPLL) device is used for precise clock synchronization in networking and telecom hardware. The device can have one or more channels (DPLLs) and one or more physical input and output pins. Each DPLL channel can either produce pulse-per-clock signal or drive ethernet equipment clock. **Important APIs/types/functions:** This is declarative schema rather than executable code. The public ABI surface is `$id` `http://devicetree.org/schemas/dpll/dpll-device.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and the referenced schemas used by dt-schema. Compatible strings are none declared. Required properties are none declared. Important properties include `$nodename`, `#address-cells`, `#size-cells`, `dpll-types`, `input-pins`, `output-pins`. Referenced schemas are `/schemas/types.yaml#/definitions/non-unique-string-array`, `/schemas/dpll/dpll-pin.yaml`. Property roles include `#address-cells` for child-node address cell width; `#size-cells` for child-node size cell width. The top-level closure rule is `additionalProperties: true`. Maintainers: Ivan Vecera <ivecera@redhat.com>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel subsystems, not by this YAML file. `dt_binding_check` loads the core meta-schema, resolves references such as `/schemas/types.yaml#/definitions/non-unique-string-array`, `/schemas/dpll/dpll-pin.yaml`, applies `properties`, `required`, enum/const/items limits, and any `allOf` or conditional branches, then validates the inline examples. During boot, a matching DT node is compiled into the DTB, the kernel matches `compatible`, subsystem code reads cells and phandles, and the bound driver consumes resources such as platform driver `of_match_table` binding through the compatible string. It has no nested conditional schema branches beyond direct property validation. Nested or patterned child schema surfaces include `dpll-types`, `input-pins`, `output-pins`.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, resource topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though no kernel state is stored here.

**Dependencies and integration points:** Integrated with DPLL framework consumers and board clocking descriptions. Direct schema dependencies are `/schemas/types.yaml#/definitions/non-unique-string-array`, `/schemas/dpll/dpll-pin.yaml`; resource dependencies visible in the property set include platform driver `of_match_table` binding through the compatible string. Driver integration is through `compatible`, while client/provider integration is through cell properties, phandle arrays, child schemas, and bus-standard properties declared or inherited here.

**Risks:** Main risks are schema ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, missing required clocks/resets/interrupts/power domains, stale examples, and conditional branches that accept one SoC variant while rejecting another valid one. Unknown-property policy also matters: `additionalProperties: true` can either catch misspelled DTS properties or allow legacy extension points. For bindings with child nodes or graph/connector references, parent-child address-cell and port layout mistakes can pass driver review only if dtbs_check coverage is weak.

**Test signals:** Run `make dt_binding_check DT_SCHEMA_FILES=sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/dpll/dpll-device.yaml` and `make dtbs_check` against DTS users of every compatible family. Verify inline examples compile, required-property failures are reported, compatible-specific branches are exercised, inherited schemas resolve, and drivers still probe with the resources described here. The file has no inline example block, so coverage depends on real DTS users and dtbs_check rather than schema-local examples.
