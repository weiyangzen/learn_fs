# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mfd/delta,tn48m-cpld.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mfd/delta,tn48m-cpld.yaml` is a Linux Devicetree YAML schema for `Delta Networks TN48M CPLD controller`, a multi-function device binding. Lattice CPLD onboard the TN48M switches is used for system management. It provides information about the hardware model, revision, PSU status etc. It is also being used as a GPIO expander and reset controller for the switch MAC-s and other peripherals. It is declarative ABI documentation and dt-schema validation input, not executable kernel code. Its job is to constrain how board DTS files describe the MFD parent and any child functions so the kernel can bind the parent driver, instantiate child devices, and hand common resources to subsystem drivers.

**Important APIs/types/functions:** The public API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, child schemas, references, examples, and compatible-specific composition. `compatible` uses single `const` and covers 1 compatible token: `delta,tn48m-cpld`. Top-level properties are `compatible`, `reg`, `#address-cells`, `#size-cells`. Top-level required properties are `compatible`, `reg`, `#address-cells`, `#size-cells`; required properties discovered across nested schemas include `#address-cells`, `#size-cells`, `compatible`, `reg`. The node acts as a MMIO/syscon parent node with address-translated child functions. Important property roles: `compatible` selects the OF match entry and stable hardware ABI; `reg` carries the I2C/SPI/SPMI address or MMIO range; `#address-cells` defines child-node address layout; `#size-cells` defines child-node address layout. Named child-function entries are no named child-function nodes detected; patterned child schemas are `^gpio(@[0-9a-f]+)?$`, `^reset-controller?$`. Numeric and item constraints include `maxItems=1`.

**Control flow:** Control flow is supplied by Devicetree tooling and by the Linux MFD/subsystem core. `dt_binding_check` loads the core meta-schema, resolves `$ref` targets, applies property constraints, validates `required` sets and examples, evaluates `allOf`/`oneOf`/conditional branches, and enforces the unknown-property policy. At boot the compiled DTB node is matched through an OF compatible table; the parent MFD, syscon, PMIC, SPMI, I2C, SPI, or platform driver then reads `reg`, clocks, interrupts, resets, GPIOs, supplies, and child nodes before registering subdevices such as regulators, RTCs, GPIO/pinctrl blocks, chargers, watchdogs, LEDs, ADCs, PHYs, thermal sensors, or power/reset controllers.

**State and persistence behavior:** The YAML owns no mutable runtime state and persists no data. Its persistent effect is ABI stability: compatible tokens, child-node names, required supply/clock/IRQ/reset resources, phandle cell counts, register ranges, and fallback ordering become long-lived DTS/DTB contracts. Real state such as regulator voltage, watchdog countdown, RTC time, GPIO direction, charger status, reset line assertion, NVMEM contents, or interrupt masks is maintained by the hardware and kernel drivers that consume nodes validated by this schema.

**Risks:** Main risks are Devicetree ABI drift and parent/child contract skew. Tightening required properties can reject old board files; relaxing constraints can hide misspelled resources until probe fails. Compatible fallback ordering must match driver tables and documented hardware lineage. Child-function names and `patternProperties` must stay aligned with the subdriver bindings they reference, especially for regulators, GPIO/pinctrl, RTC, charger, LED, Type-C, watchdog, power/reset, and syscon children. Register ranges, `#address-cells`, `#size-cells`, and phandle cell counts are high-risk because they affect child resource decoding. Closure profile: top-level unknown properties are rejected by `additionalProperties: false`. This schema has 4 top-level properties and 4 distinct nested property names, so broad edits should be validated against every compatible variant and every in-tree DTS user rather than only the example node.

**Test signals:** Primary validation is `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/mfd/delta,tn48m-cpld.yaml` plus `make dtbs_check` for DTS files that instantiate each compatible. Useful negative tests remove required `reg`, IRQ, supply, clock, reset, GPIO, address-cell, or child-function properties; misspell child node names; use bad compatible fallback order; and exercise every conditional branch. Runtime signals are successful parent probe, expected child devices under sysfs/debugfs, working regulator/RTC/GPIO/pinctrl/reset/clock/charger/watchdog/LED/thermal/USB or other referenced subdrivers, and no new dtbs_check warnings for existing board examples.
