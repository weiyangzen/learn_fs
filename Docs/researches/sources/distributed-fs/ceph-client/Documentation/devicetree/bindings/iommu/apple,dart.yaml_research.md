# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/iommu/apple,dart.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Apple DART IOMMU`. In this tree it is a IOMMU binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: Apple SoCs may contain an implementation of their Device Address Resolution Table which provides a mandatory layer of address translations for various masters. Each DART instance is capable of handling up to 16 different streams with individual pagetables and page-level read/write protection flags. This DART IOMMU also raises interrupts in response to various fault conditions.

**Important APIs/types/functions:** This YAML is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/iommu/apple,dart.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and any referenced dt-schema fragments. Compatible strings or compatible-pattern values are `apple,t8103-dart`, `apple,t8103-usb4-dart`, `apple,t8110-dart`, `apple,t6000-dart`, `apple,t6020-dart`. Required properties are `compatible`, `reg`, `#iommu-cells`, `interrupts`. Important top-level properties are `compatible`, `reg`, `interrupts`, `clocks`, `#iommu-cells`, `power-domains`. Direct and nested `$ref` dependencies are none declared. Property roles include `compatible` for driver match key and stable hardware ABI identifier; `reg` for MMIO range, bus address, or child register selector; `interrupts` for interrupt parent specifier array for wired IRQ inputs or outputs; `clocks` for clock provider phandles required to access the block; `#iommu-cells` for IOMMU specifier cell count consumed by DMA masters; `power-domains` for genpd power-domain attachment. The top-level unknown-property policy is `additionalProperties: false`. Maintainers are `Sven Peter <sven@svenpeter.dev>`.

**Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. Schema composition/conditional keywords present: `oneOf`. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IOMMU and DMA mapping code use it to attach masters to translation/protection domains from DT phandles. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as `reg`, `interrupts`, `clocks`, `power-domains`. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.

Verify inline examples compile, required-property failures are reported, compatible-specific branches are exercised, `$ref` targets resolve, and the corresponding driver still probes and registers its IRQ/MSI/IOMMU domain with the resources described here. The file includes 1 example block(s), which are part of the dt-schema validation signal.
