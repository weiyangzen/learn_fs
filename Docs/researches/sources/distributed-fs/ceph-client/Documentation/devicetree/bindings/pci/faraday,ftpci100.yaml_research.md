# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pci/faraday,ftpci100.yaml

**Purpose:** Defines the Devicetree YAML/JSON-schema contract for `Faraday Technology FTPCI100 PCI Host Bridge`. It is a host/root-complex controller binding in the PCI/PCIe devicetree binding family; it constrains how DTS/DTB nodes identify the PCI hardware, describe register windows, interrupts, clocks, resets, PHYs, address translation, DMA/IOMMU reachability, and optional child/root-port layout for Linux PCI probing. The source description says: This PCI bridge is found inside that Cortina Systems Gemini SoC platform and is a generic IP block from Faraday Technology. It exists in two variants: plain and dual PCI. The plain version embeds a cascading interrupt controller into the host bridge. The dual version routes the interrupts to the host chips interrupt controller. The host controller appear on the PCI bus with vendor ID 0x159b (Faraday Technology) and product ID 0x4321. I/O space considerations: The plain variant has 128MiB of non-prefetchable memory space, whereas the "dual" variant has 64MiB. Take this into account when describing the ranges. Interrupt map considerations: The "dual" variant will get INT A, B, C, D from the system interrupt controller and should point to respective interrupt in that controller in its interrupt-map. The code which is the only documentation of how the Faraday PCI (the non-dual variant) interrupts assigns the default interrupt mapping/swizzling has typically been like this, doing the swizzling on the interrupt controller side rather than in the interconnect: interrupt-map-mask = <0xf800 0 0 7>; interrupt-map = <0x4800 0 0 1 &pci_intc 0>, /* Slot 9 */ <0x4800 0 0 2 &pci_intc 1>, <0x4800 0 0 3 &pci_intc 2>, <0x4800 0 0 4 &pci_intc 3>, <0x5000 0 0 1 &pci_intc 1>, /* Slot 10 */ <0x5000 0 0 2 &pci_intc 2>, <0x5000 0 0 3 &pci_intc 3>, <0x5000 0 0 4 &pci_intc 0>, <0x5800 0 0 1 &pci_intc 2>, /* Slot 11 */ <0x5800 0 0 2 &pci_intc 3>, <0x5800 0 0 3 &pci_intc 0>, <0x5800 0 0 4 &pci_intc 1>, <0x6000 0 0 1 &pci_intc 3>, /* Slot 12 */ <0x6000 0 0 2 &pci_intc 0>, <0x6000 0 0 3 &pci_intc 1>, <0x6000 0 0 4 &pci_intc 2>;

**Important APIs/types/functions:** This file is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/pci/faraday,ftpci100.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, the `properties` block, `required` list, schema-composition keywords, inline examples, and the compatible strings consumed by kernel OF match tables. Compatible strings covered here: `cortina,gemini-pci`, `cortina,gemini-pci-dual`, `faraday,ftpci100`, `faraday,ftpci100-dual`. Directly declared properties are `compatible`, `reg`, `#address-cells`, `#interrupt-cells`, `ranges`, `dma-ranges`, `clocks`, `clock-names`, `interrupt-controller`. Required properties are `reg`, `compatible`, `#interrupt-cells`, `interrupt-map-mask`, `interrupt-map`, `dma-ranges`. Maintainers: Linus Walleij <linusw@kernel.org>.

**Control flow:** Validation flow is handled by dt-schema: the core meta-schema loads this YAML, resolves references (`/schemas/pci/pci-host-bridge.yaml#`), applies direct property constraints, evaluates top-level `allOf` composition, and then applies conditional branches. Conditional behavior: for faraday,ftpci100, adds/restricts `interrupt-controller`. At runtime the compiled DTB has no code from this file; the kernel matches `compatible`, maps `reg` resources, programs PCI ranges, requests interrupts/MSI mappings, enables clocks/resets/regulators/PHYs/power domains, and creates host bridge/root-port or endpoint objects according to the described node.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability for board DTS files and shipped DTBs: compatible ordering, resource names, cell counts, interrupt maps, address ranges, and child-node layout become the long-lived contract that drivers and firmware rely on. For this file, the top-level and composed unknown-property policy is: unevaluatedProperties: false.

**Dependencies:** Direct schema dependencies are `/schemas/pci/pci-host-bridge.yaml#`. Resource dependencies visible in the binding include `compatible` (driver OF match key and binding ABI identifier); `reg` (MMIO/config/address-space resource tuples); `#interrupt-cells` (legacy INTx interrupt specifier width); `ranges` (PCI address translation windows exposed by the host bridge); `dma-ranges` (DMA address translation windows); `clocks` (clock provider phandles); `clock-names` (stable clock input names) The binding also depends on the broader Devicetree PCI schemas, dt-schema tooling, and matching Linux PCI host/endpoint drivers for the compatible strings above.

**Integration points:** Integrates with Linux OF platform matching through `compatible`, PCI core setup through `device_type`, `bus-range`, `ranges`, `dma-ranges`, `#address-cells`, and `#size-cells`, interrupt infrastructure through `interrupt-map`, `interrupts`, MSI controllers or `msi-map`, and SoC resource managers through clocks, resets, PHY, regulator, power-domain, and IOMMU properties. Nested integration surface: child/object property `interrupt-controller`.

**Risks:** Main risks are ABI drift in required properties, accepting a DTS shape that the driver cannot probe, rejecting valid legacy boards, stale examples, wrong `reg-names`/`clock-names`/`reset-names` ordering, incomplete compatible coverage, and conditional branches whose `contains`/`enum` logic does not match real fallback-compatible ordering. PCI-specific risk is high around address translation and interrupts: bad `ranges`, `dma-ranges`, `iommu-map`, `msi-map`, or `interrupt-map-mask` can validate syntactically while producing unprobeable devices or broken DMA/MSI at runtime.
