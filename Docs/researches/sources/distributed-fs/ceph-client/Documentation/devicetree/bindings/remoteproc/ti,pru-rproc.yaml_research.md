# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/remoteproc/ti,pru-rproc.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/remoteproc/ti,pru-rproc.yaml` is a Linux devicetree YAML schema for the `TI Programmable Realtime Unit (PRU) cores` TI PRU remoteproc binding. Each Programmable Real-Time Unit and Industrial Communication Subsystem (PRU-ICSS or PRUSS) has two 32-bit load/store RISC CPU cores called Programmable Real-Time Units (PRUs), each represented by a node. Each PRU core has a dedicated Instruction RAM, Control and Debug register sets, and use the Data RAMs present within the PRU-ICSS for code execution. The K3 SoCs containing ICSSG v1.0 (eg: AM65x SR1.0) also have two Auxiliary PRU cores called RTUs with slightly different IP integration. The K3 SoCs containing the revised ICSSG v1.1 (eg: J721E, AM65x SR2.0) have an extra two auxiliary Transmit PRU cores called Tx_PRUs that augment the PRUs. Each RTU or Tx_PRU core can also be used independently like a PRU, or alongside a corresponding PRU core to... It is not executable Ceph or kernel logic; it is a hardware-description ABI used by DTS authors, dt-schema, and Linux subsystem drivers so that board descriptions match what the driver will parse at probe or early boot.

## Important APIs, Types, and Functions
The public API surface is the schema's accepted node shape. `compatible` uses `enum` list and covers 14 compatible tokens: `ti,am3356-pru`, `ti,am4376-pru`, `ti,am5728-pru`, `ti,am625-pru`, `ti,am642-pru`, `ti,am642-rtu`, `ti,am642-tx-pru`, `ti,am654-pru`, `ti,am654-rtu`, `ti,am654-tx-pru`, `ti,j721e-pru`, `ti,j721e-rtu`, `ti,j721e-tx-pru`, `ti,k2g-pru`. Top-level properties are `compatible`, `reg`, `reg-names`, `firmware-name`, `interrupts`, `interrupt-names`. Across nested schemas and child nodes this file mentions 7 distinct property names; required properties observed at all levels include `compatible`, `firmware-name`, `reg`, `reg-names`. Node naming is constrained by no explicit node-name constraint. Remoteproc-facing properties define firmware loading and processor-control resources: address ranges `reg`, `reg-names`, memory-carveout links `reg`, mailbox/interrupt/IPC hooks `firmware-name`, `interrupts`, `interrupt-names`, and clock/reset/power controls none. Required properties are `compatible`, `reg`, `reg-names`, `firmware-name`; these values are consumed by Linux remoteproc drivers before firmware boot, crash handling, and virtio/rpmsg setup.

## Control Flow, State, and Persistence
Control flow is declarative JSON-schema evaluation. `dt-doc-validate`, `dt_binding_check`, and `dtbs_check` load the YAML, expand `$ref` links, match nodes by `compatible` or referenced common-schema use, enforce required properties, evaluate composition/conditional keywords, and validate inline DTS examples. At runtime, platform bus probing hands the validated node to a remoteproc driver, which maps resources, obtains clocks/resets/power domains, reserves memory, starts firmware, and may expose rpmsg/virtio endpoints. The YAML itself stores no mutable runtime state and writes no persistent data; persistence is the source-controlled devicetree ABI and the DTB blobs built from DTS. External references used in evaluation are none; schema composition/conditional keywords present are `else`, `if`, `then`.
