# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/riscv,rpmi-system-msi.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `RISC-V RPMI system MSI service group based interrupt controller`. In this tree it is an interrupt/MSI controller binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: The RISC-V Platform Management Interface (RPMI) [1] defines a messaging protocol which is modular and extensible. The supervisor software can send/receive RPMI messages via SBI MPXY extension [2] or some dedicated supervisor-mode RPMI transport. The RPMI specification [1] defines system MSI service group which allow application processors to receive MSIs upon system events such as P2A doorbell, graceful shutdown/reboot request, CPU hotplug event, memory hotplug event, etc from the platform microcontroller. The supervisor software can access RPMI system MSI service group via SBI MPXY channel or some dedicated supervisor-mode RPMI transport. =========================================== References =========================================== [1] RISC-V Platform Management Interface (RPMI) v1.0 (or higher) https://github.com/riscv-non-isa/riscv-rpmi/releases [2] RISC-V Supervisor Binary Interface (SBI) v3.0 (or higher) https://github.com/riscv-non-isa/riscv-sbi-doc/releases

**Important APIs/types/functions:** This YAML is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/interrupt-controller/riscv,rpmi-system-msi.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and any referenced dt-schema fragments. Compatible strings or compatible-pattern values are `riscv,rpmi-system-msi`. Required properties are `compatible`, `mboxes`, `msi-parent`, `interrupt-controller`, `#interrupt-cells`. Important top-level properties are `compatible`, `mboxes`, `msi-parent`, `interrupt-controller`, `#interrupt-cells`. Direct and nested `$ref` dependencies are `/schemas/interrupt-controller.yaml#`. Property roles include `compatible` for driver match key and stable hardware ABI identifier; `mboxes` for binding-specific property constrained by the schema; `msi-parent` for links a device or nested domain to an MSI provider; `interrupt-controller` marks the node as an interrupt domain provider; `#interrupt-cells` for interrupt specifier cell count consumed by child/client nodes. The top-level unknown-property policy is `additionalProperties: false`. Maintainers are `Anup Patel <anup@brainfault.org>`.

**Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. Schema composition/conditional keywords present: `allOf`. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IRQ domain and MSI domain code use it to route wired or message-signaled interrupts from DT-described devices. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as `msi-parent`. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.
