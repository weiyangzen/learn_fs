# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/opp/allwinner,sun50i-h6-operating-points.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/opp/allwinner,sun50i-h6-operating-points.yaml` defines the Linux Devicetree YAML schema for `Allwinner H6 CPU OPP`, a operating-points binding. The schema description says: For some SoCs, the CPU frequency subset and voltage value of each OPP varies based on the silicon variant in use. Allwinner Process Voltage Scaling Tables define the voltage and frequency values based on the speedbin blown in the efuse combination. It is declarative ABI documentation and validation input rather than executable kernel code; its practical role is to make DTS/DTB hardware descriptions match the resources, topology, and compatible strings expected by the relevant kernel subsystem before probe.

## Important APIs, Types, and Functions
The public API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses an `enum` and exposes 3 tokens: `allwinner,sun50i-a100-operating-points`, `allwinner,sun50i-h6-operating-points`, `allwinner,sun50i-h616-operating-points`. Top-level properties are `compatible`, `nvmem-cells`, `opp-shared`. Top-level required properties are `compatible`, `nvmem-cells`; required properties collected from nested schema branches include `compatible`, `nvmem-cells`, `opp-hz`. Patterned child schemas are `^opp-[0-9]+$`. Numeric and collection constraints include `maxItems=1`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `nvmem-cells` links calibration, MAC, serial, or speed-bin data through the NVMEM core. The highest-risk ABI details are OPP table compatibility, `opp-hz`, voltage/current/microvolt arrays, level/performance-state values, supported-hw masks, turbo/suspend flags, named supplies, and required-opps links.

## Control Flow
Runtime control flow is supplied by dt-schema and kernel subsystem code, not by this YAML file. `dt_binding_check` loads the meta-schema, resolves `$ref` entries, applies `properties`, evaluates `allOf`, checks required fields, validates `minItems`/`maxItems` and enum/const constraints, validates embedded examples, and applies the closure rule. During boot, the compiled DTB node is matched by `compatible`; then platform, PCI, SDIO, SPI, MDIO, NVMEM, OPP, PCIe, netdev, wireless, accelerator, storage, clock, reset, regulator, IRQ, GPIO, IOMMU, and power-domain helpers consume the phandles and resource arrays that this schema validates. Child nodes are discovered declaratively through fixed names, pattern properties, address cells, and referenced child schemas.

## State and Persistence Behavior
The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: compatible strings, required resource names, register and interrupt ordering, phandle and cell counts, child-node names, fallback ordering, and example layouts become long-lived contracts in board DTS files and shipped DTBs. Runtime state belongs to the matching drivers and hardware after probe, including registered OPP tables, enabled/disabled performance points, regulator voltage/current selection, clock-rate transitions, power-domain state votes, cooling state limits, and speed-bin filtering.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, link training, calibration lookup, OPP selection, NVMEM cell reads, or bus enumeration. Tightening required properties can reject existing boards; loosening them can hide missing clocks, resets, interrupts, supplies, PHY links, PCIe windows, memory regions, OPP fields, or NVMEM cells. Child-node schemas need special care because address cells, port IDs, PCI interrupt maps, wireless calibration cells, NVMEM layouts, and OPP tables must match driver-side assumptions. This schema rejects unknown top-level properties with `additionalProperties: false`. It has 3 top-level properties and 9 distinct nested property names, so broad edits should be checked against all compatible variants and DTS users, not just the nominal filename.

## Test Signals
Run `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/opp/allwinner,sun50i-h6-operating-points.yaml` for targeted schema validation and `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/opp/allwinner,sun50i-h6-operating-points.yaml` against boards using these nodes. High-value negative checks remove required properties, use invalid compatible fallbacks, corrupt `reg` or interrupt counts, misspell vendor properties, violate child-node address-cell rules, and exercise every conditional branch. Runtime integration signals are successful driver probe, correct subsystem registration, valid NVMEM/OPP/PCIe/wireless/netdev/accelerator/storage behavior as applicable, clean interrupt/reset/power sequencing, and no new dtbs_check failures in embedded examples or in-tree DTS users.
