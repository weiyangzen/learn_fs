# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/fsl,mu-msi.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Freescale/NXP i.MX Messaging Unit (MU) work as msi controller`. In this tree it is an interrupt/MSI controller binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: The Messaging Unit module enables two processors within the SoC to communicate and coordinate by passing messages (e.g. data, status and control) through the MU interface. The MU also provides the ability for one processor (A side) to signal the other processor (B side) using interrupts. Because the MU manages the messaging between processors, the MU uses different clocks (from each side of the different peripheral buses). Therefore, the MU must synchronize the accesses from one side to the other. The MU accomplishes synchronization using two sets of matching registers (Processor A-side, Processor B-side). MU can work as msi interrupt controller to do doorbell

**Important APIs/types/functions:** This YAML is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/interrupt-controller/fsl,mu-msi.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and any referenced dt-schema fragments. Compatible strings or compatible-pattern values are `fsl,imx6sx-mu-msi`, `fsl,imx7ulp-mu-msi`, `fsl,imx8ulp-mu-msi`, `fsl,imx8ulp-mu-msi-s4`. Required properties are `compatible`, `reg`, `interrupts`, `msi-controller`, `#msi-cells`. Important top-level properties are `compatible`, `reg`, `reg-names`, `interrupts`, `clocks`, `power-domains`, `power-domain-names`, `msi-controller`, `#msi-cells`. Direct and nested `$ref` dependencies are `/schemas/interrupt-controller/msi-controller.yaml#`. Property roles include `compatible` for driver match key and stable hardware ABI identifier; `reg` for MMIO range, bus address, or child register selector; `reg-names` for semantic names for register ranges; `interrupts` for interrupt parent specifier array for wired IRQ inputs or outputs; `clocks` for clock provider phandles required to access the block; `power-domains` for genpd power-domain attachment; `power-domain-names` for binding-specific property constrained by the schema; `msi-controller` marks the node as an MSI domain provider; `#msi-cells` for MSI specifier cell count consumed by clients. The top-level unknown-property policy is `additionalProperties: false`. Maintainers are `Frank Li <Frank.Li@nxp.com>`.

**Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. Schema composition/conditional keywords present: `allOf`. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IRQ domain and MSI domain code use it to route wired or message-signaled interrupts from DT-described devices. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as `reg`, `interrupts`, `clocks`, `power-domains`. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.
