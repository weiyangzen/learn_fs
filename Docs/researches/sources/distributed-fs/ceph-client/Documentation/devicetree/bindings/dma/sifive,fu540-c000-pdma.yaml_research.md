# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/dma/sifive,fu540-c000-pdma.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `SiFive Unleashed Rev C000 Platform DMA`. In this tree it is a DMA engine, DMA router, or DMA-capable IP binding used by dmaengine providers and DMA client phandle specifiers; it constrains how board DTS files describe the hardware and how Linux drivers discover it through OF matching, phandles, and common binding references. The source description says: Platform DMA is a DMA engine of SiFive Unleashed. It supports 4 channels. Each channel has 2 interrupts. One is for DMA done and the other is for DME error. In different SoC, DMA could be attached to different IRQ line. DT file need to be changed to meet the difference. For technical doc, https://static.dev.sifive.com/FU540-C000-v1.0.pdf

**Important APIs/types/functions:** This is declarative schema rather than executable code. The public ABI surface is `$id` `http://devicetree.org/schemas/dma/sifive,fu540-c000-pdma.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and the referenced schemas used by dt-schema. Compatible strings are `microchip,pic64gx-pdma`, `microchip,mpfs-pdma`, `sifive,pdma0`, `sifive,fu540-c000-pdma`. Required properties are `compatible`, `reg`, `interrupts`. Important properties include `compatible`, `reg`, `interrupts`, `dma-channels`, `#dma-cells`. Referenced schemas are `dma-controller.yaml#`. Property roles include `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address; `interrupts` for interrupt line routing; `dma-channels` for number of DMA channels; `#dma-cells` for DMA client specifier width. The top-level closure rule is `unevaluatedProperties: false`. Maintainers: Green Wan <green.wan@sifive.com>, Palmer Debbelt <palmer@sifive.com>, Paul Walmsley <paul.walmsley@sifive.com>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel subsystems, not by this YAML file. `dt_binding_check` loads the core meta-schema, resolves references such as `dma-controller.yaml#`, applies `properties`, `required`, enum/const/items limits, and any `allOf` or conditional branches, then validates the inline examples. During boot, a matching DT node is compiled into the DTB, the kernel matches `compatible`, subsystem code reads cells and phandles, and the bound driver consumes resources such as platform driver `of_match_table` binding through the compatible string. Conditional/schema-composition points include `allOf`, so different compatibles or child-node shapes can activate different required-property sets. It does not define nested child-node schemas.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, resource topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though no kernel state is stored here.

**Dependencies and integration points:** Integrated with dmaengine and Devicetree DMA client code. Direct schema dependencies are `dma-controller.yaml#`; resource dependencies visible in the property set include platform driver `of_match_table` binding through the compatible string. Driver integration is through `compatible`, while client/provider integration is through cell properties, phandle arrays, child schemas, and bus-standard properties declared or inherited here.

**Risks:** Main risks are schema ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, missing required clocks/resets/interrupts/power domains, stale examples, and conditional branches that accept one SoC variant while rejecting another valid one. Unknown-property policy also matters: `unevaluatedProperties: false` can either catch misspelled DTS properties or allow legacy extension points. For bindings with child nodes or graph/connector references, parent-child address-cell and port layout mistakes can pass driver review only if dtbs_check coverage is weak.

Verify inline examples compile, required-property failures are reported, compatible-specific branches are exercised, inherited schemas resolve, and drivers still probe with the resources described here.
