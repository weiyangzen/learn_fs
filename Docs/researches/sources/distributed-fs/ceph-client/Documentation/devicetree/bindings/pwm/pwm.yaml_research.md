# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pwm/pwm.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pwm/pwm.yaml` defines the Linux Devicetree YAML schema for `PWM controllers (providers)`, a PWM common-schema or nexus binding. It is declarative ABI documentation and validation input, not executable driver code. Its job is to keep DTS/DTB nodes aligned with the resources, child nodes, and electrical or timing constraints expected by the matching kernel subsystem before a driver probes hardware.

## Important APIs, Types, and Functions
The API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `patternProperties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses a composed compatible schema with 0 tokens: no explicit compatible constants. Top-level properties are `$nodename`, `#pwm-cells`. Top-level required properties are `#pwm-cells`; required properties collected from nested branches include `#pwm-cells`. Patterned child schemas are none. Numeric and collection constraints include no explicit numeric or item limits collected. Important resource roles: `#pwm-cells` fixes child-node or phandle specifier shape. The highest-risk ABI details are common cell counts, consumer specifier shape, channel numbering, period/polarity ABI, and child translation rules.

## Control Flow
Control flow is dt-schema evaluation rather than imperative execution. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties` and `patternProperties`, evaluates no top-level conditionals, checks required fields and min/max constraints, validates examples, and enforces the closure policy. At runtime this YAML does not execute: the compiled DTB node is matched through a kernel OF table or subsystem-specific child-node parser, then helpers for power-supply, regulator, PWM, PTP, PPS, PowerPC platform, clocks, resets, interrupts, GPIOs, pinctrl, power domains, and MFD parents consume the validated resources.

## State and Persistence Behavior
The file stores no mutable runtime state and writes no persistent data. Its persistence is ABI stability: compatible strings, required resource names, phandle/cell counts, child-node names, electrical limit properties, fallback ordering, and example layouts become long-lived contracts in DTS and DTB artifacts. Runtime state belongs to drivers and hardware after probe, including PWM chip registration, channel request state, duty-cycle/period/polarity settings, enable state, and consumer-owned runtime policy.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, power sequencing, clock setup, IRQ delivery, or consumer phandle resolution. Tightening required properties can reject existing board files; loosening them can hide missing supplies, clocks, resets, interrupts, current/voltage limits, PWM cell counts, PTP/PPS GPIOs, or regulator child constraints. This schema allows unknown top-level properties. It has 2 top-level properties and 2 distinct nested property names, so broad edits should be checked against all compatibles, examples, and in-tree DTS users rather than only the filename's nominal device.

## Test Signals

High-value negative checks remove required `compatible`, `reg`, interrupts, clocks, resets, supplies, GPIOs, child regulator/PWM/battery nodes, or phandles; use invalid cell counts or child `reg` values; misspell vendor properties; and exercise every compatible-specific branch. Runtime integration signals are successful driver probe, correct power_supply/regulator/PWM/PTP/PPS/platform registration, clean suspend/resume or runtime-PM behavior where applicable, valid interrupt/reset/power sequencing, and no dtbs_check regressions in embedded examples or in-tree DTS users.
