# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/mstar,mst-intc.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `MStar Interrupt Controller`. In this tree it is an interrupt controller binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: MStar, SigmaStar and Mediatek TV SoCs contain multiple legacy interrupt controllers that routes interrupts to the GIC. The HW block exposes a number of interrupt controllers, each can support up to 64 interrupts.

**Important APIs/types/functions:** This YAML is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/interrupt-controller/mstar,mst-intc.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and any referenced dt-schema fragments. Compatible strings or compatible-pattern values are `mstar,mst-intc`. Required properties are `compatible`, `reg`, `mstar,irqs-map-range`. Important top-level properties are `compatible`, `interrupt-controller`, `#interrupt-cells`, `reg`, `mstar,irqs-map-range`, `mstar,intc-no-eoi`. Direct and nested `$ref` dependencies are `/schemas/types.yaml#/definitions/uint32-matrix`. Property roles include `compatible` for driver match key and stable hardware ABI identifier; `interrupt-controller` marks the node as an interrupt domain provider; `#interrupt-cells` for interrupt specifier cell count consumed by child/client nodes; `reg` for MMIO range, bus address, or child register selector; `mstar,irqs-map-range` for binding-specific property constrained by the schema; `mstar,intc-no-eoi` for binding-specific property constrained by the schema. The top-level unknown-property policy is `additionalProperties: false`. Maintainers are `Mark-PK Tsai <mark-pk.tsai@mediatek.com>`.

**Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. The file has no nested conditional schema composition beyond direct property validation. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IRQ domain code uses it to translate DT interrupt specifiers into Linux IRQs and route them to an upstream parent domain. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as `reg`. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.
