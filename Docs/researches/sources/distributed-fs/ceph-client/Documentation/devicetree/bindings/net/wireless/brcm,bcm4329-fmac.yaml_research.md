# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/net/wireless/brcm,bcm4329-fmac.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/net/wireless/brcm,bcm4329-fmac.yaml` defines the Linux Devicetree YAML schema for `Broadcom BCM4329 family fullmac wireless SDIO/PCIE devices`, a wireless controller binding. The schema description says: The Broadcom Single chip MAC part for the BCM4329 family and later Cypress chips in the same family named CYW4373 and similar. These chips also have a Bluetooth portion described in a separate binding. It is declarative ABI documentation and validation input rather than executable kernel code; its practical role is to make DTS/DTB hardware descriptions match the resources, topology, and compatible strings expected by the relevant kernel subsystem before probe.

## Important APIs, Types, and Functions
The public API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses `oneOf` with 2 branchs and exposes 30 tokens: `brcm,bcm43143-fmac`, `brcm,bcm4341b0-fmac`, `brcm,bcm4341b4-fmac`, `brcm,bcm4341b5-fmac`, `brcm,bcm4329-fmac`, `brcm,bcm4330-fmac`, `brcm,bcm4334-fmac`, `brcm,bcm43340-fmac`, `brcm,bcm4335-fmac`, `brcm,bcm43362-fmac`, `brcm,bcm4339-fmac`, `brcm,bcm43430a0-fmac`, `brcm,bcm43430a1-fmac`, `brcm,bcm43455-fmac`, `brcm,bcm43456-fmac`, `brcm,bcm4354-fmac`, `brcm,bcm4356-fmac`, `brcm,bcm4359-fmac`, `brcm,bcm4366-fmac`, `brcm,bcm43752-fmac`, `cypress,cyw4373-fmac`, `cypress,cyw43012-fmac`, `infineon,cyw43439-fmac`, `pci14e4,43dc`, and 6 more. Top-level properties are `compatible`, `reg`, `interrupts`, `interrupt-names`, `brcm,drive-strength`, `reset-gpios`, `brcm,ccode-map`, `brcm,ccode-map-trivial`, `brcm,cal-blob`, `brcm,board-type`, `apple,antenna-sku`, `clocks`, `clock-names`. Numeric and collection constraints include `maxItems=1`, `minimum=0`, `maximum=32`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `reg` describes MMIO ranges, bus child addresses, port selectors, or cell offsets; `interrupts` routes status, error, RX/TX, MSI, or completion IRQs; `interrupt-names` fixes resource ordering visible to drivers; `reset-gpios` captures board GPIO sequencing; `clocks` integrates with common clock, reset, PM, DMA/IOMMU, or reserved-memory providers; `clock-names` fixes resource ordering visible to drivers. The highest-risk ABI details are compatible identity, bus address, interrupt or wake wiring, calibration and OTP/NVMEM references, firmware names, frequency limits, power limits, and vendor board-data properties.

## Control Flow
Runtime control flow is supplied by dt-schema and kernel subsystem code, not by this YAML file. `dt_binding_check` loads the meta-schema, resolves `$ref` entries, applies `properties`, evaluates `allOf`, checks required fields, validates `minItems`/`maxItems` and enum/const constraints, validates embedded examples, and applies the closure rule. During boot, the compiled DTB node is matched by `compatible`; then platform, PCI, SDIO, SPI, MDIO, NVMEM, OPP, PCIe, netdev, wireless, accelerator, storage, clock, reset, regulator, IRQ, GPIO, IOMMU, and power-domain helpers consume the phandles and resource arrays that this schema validates. Child nodes are discovered declaratively through fixed names, pattern properties, address cells, and referenced child schemas.

## State and Persistence Behavior
The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: compatible strings, required resource names, register and interrupt ordering, phandle and cell counts, child-node names, fallback ordering, and example layouts become long-lived contracts in board DTS files and shipped DTBs. Runtime state belongs to the matching drivers and hardware after probe, including wireless device probe, firmware boot, regulatory/channel capability selection, calibration selection, IRQ/wake state, netdev/wiphy registration, and runtime PM.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, link training, calibration lookup, OPP selection, NVMEM cell reads, or bus enumeration. Tightening required properties can reject existing boards; loosening them can hide missing clocks, resets, interrupts, supplies, PHY links, PCIe windows, memory regions, OPP fields, or NVMEM cells. Child-node schemas need special care because address cells, port IDs, PCI interrupt maps, wireless calibration cells, NVMEM layouts, and OPP tables must match driver-side assumptions. This schema closes composed schemas with `unevaluatedProperties: false`. It has 13 top-level properties and 13 distinct nested property names, so broad edits should be checked against all compatible variants and DTS users, not just the nominal filename.
