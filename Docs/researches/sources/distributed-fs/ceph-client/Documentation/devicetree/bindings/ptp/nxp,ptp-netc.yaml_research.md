# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/ptp/nxp,ptp-netc.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/ptp/nxp,ptp-netc.yaml` defines the Linux Devicetree YAML schema for `NXP NETC V4 Timer PTP clock`, a PTP hardware-clock binding. The schema description says: NETC V4 Timer provides current time with nanosecond resolution, precise periodic pulse, pulse on timeout (alarm), and time capture on external pulse support. And it supports time synchronization as required for IEEE 1588 and IEEE 802.1AS-2020. It is declarative ABI documentation and validation input, not executable driver code. Its job is to keep DTS/DTB nodes aligned with the resources, child nodes, and electrical or timing constraints expected by the matching kernel subsystem before a driver probes hardware.

## Important APIs, Types, and Functions
The API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `patternProperties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses an `enum` with 1 token: `pci1131,ee02`. Top-level properties are `compatible`, `reg`, `clocks`, `clock-names`. Top-level required properties are `compatible`, `reg`; required properties collected from nested branches include `compatible`, `reg`. Patterned child schemas are none. Numeric and collection constraints include `maxItems=1`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `reg` gives MMIO, I2C, SPI, child address, or selector placement; `clocks` binds functional, bus, reference, timer, or output clocks; `clock-names` binds functional, bus, reference, timer, or output clocks. The highest-risk ABI details are compatible identity, register or I2C address, interrupt/clock resources, clock-output pins, timecounter layout, and timestamp engine placement.

## Control Flow
Control flow is dt-schema evaluation rather than imperative execution. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties` and `patternProperties`, evaluates `allOf`, checks required fields and min/max constraints, validates examples, and enforces the closure policy. At runtime this YAML does not execute: the compiled DTB node is matched through a kernel OF table or subsystem-specific child-node parser, then helpers for power-supply, regulator, PWM, PTP, PPS, PowerPC platform, clocks, resets, interrupts, GPIOs, pinctrl, power domains, and MFD parents consume the validated resources.

## State and Persistence Behavior
The file stores no mutable runtime state and writes no persistent data. Its persistence is ABI stability: compatible strings, required resource names, phandle/cell counts, child-node names, electrical limit properties, fallback ordering, and example layouts become long-lived contracts in DTS and DTB artifacts. Runtime state belongs to drivers and hardware after probe, including PHC registration, timecounter/cyclecounter state, external timestamp channels, periodic outputs, pin configuration, adjfine/adjtime state, and IRQ status.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, power sequencing, clock setup, IRQ delivery, or consumer phandle resolution. Tightening required properties can reject existing board files; loosening them can hide missing supplies, clocks, resets, interrupts, current/voltage limits, PWM cell counts, PTP/PPS GPIOs, or regulator child constraints. This schema closes composed schemas with `unevaluatedProperties: false`. It has 4 top-level properties and 4 distinct nested property names, so broad edits should be checked against all compatibles, examples, and in-tree DTS users rather than only the filename's nominal device.

Runtime integration signals are successful driver probe, correct power_supply/regulator/PWM/PTP/PPS/platform registration, clean suspend/resume or runtime-PM behavior where applicable, valid interrupt/reset/power sequencing, and no dtbs_check regressions in embedded examples or in-tree DTS users.
