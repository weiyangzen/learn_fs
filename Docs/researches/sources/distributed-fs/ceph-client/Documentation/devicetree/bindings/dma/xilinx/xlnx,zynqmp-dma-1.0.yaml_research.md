# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/dma/xilinx/xlnx,zynqmp-dma-1.0.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Xilinx ZynqMP DMA Engine`. In this tree it is a DMA engine, DMA router, or DMA-capable IP binding used by dmaengine providers and DMA client phandle specifiers; it constrains how board DTS files describe the hardware and how Linux drivers discover it through OF matching, phandles, and common binding references. The source description says: The Xilinx ZynqMP DMA engine supports memory to memory transfers, memory to device and device to memory transfers. It also has flow control and rate control support for slave/peripheral dma access.

**Important APIs/types/functions:** This is declarative schema rather than executable code. The public ABI surface is `$id` `http://devicetree.org/schemas/dma/xilinx/xlnx,zynqmp-dma-1.0.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and the referenced schemas used by dt-schema. Compatible strings are `amd,versal2-dma-1.0`, `xlnx,zynqmp-dma-1.0`. Required properties are `#dma-cells`, `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `xlnx,bus-width`. Important properties include `#dma-cells`, `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `xlnx,bus-width`, `iommus`, `power-domains`, `dma-coherent`. Referenced schemas are `../dma-controller.yaml#`, `/schemas/types.yaml#/definitions/uint32`. Property roles include `#dma-cells` for DMA client specifier width; `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address; `interrupts` for interrupt line routing; `clocks` for clock provider phandles; `clock-names` for clock input names; `iommus` for IOMMU stream mapping; `power-domains` for power-domain attachment. The top-level closure rule is `additionalProperties: false`. Maintainers: Michael Tretter <m.tretter@pengutronix.de>, Harini Katakam <harini.katakam@amd.com>, Radhey Shyam Pandey <radhey.shyam.pandey@amd.com>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel subsystems, not by this YAML file. `dt_binding_check` loads the core meta-schema, resolves references such as `../dma-controller.yaml#`, `/schemas/types.yaml#/definitions/uint32`, applies `properties`, `required`, enum/const/items limits, and any `allOf` or conditional branches, then validates the inline examples. During boot, a matching DT node is compiled into the DTB, the kernel matches `compatible`, subsystem code reads cells and phandles, and the bound driver consumes resources such as clock provider phandles, genpd power domains, IOMMU stream bindings. Conditional/schema-composition points include `allOf`, so different compatibles or child-node shapes can activate different required-property sets. Nested or patterned child schema surfaces include `xlnx,bus-width`.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, resource topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though no kernel state is stored here.

**Dependencies and integration points:** Integrated with dmaengine and Devicetree DMA client code. Direct schema dependencies are `../dma-controller.yaml#`, `/schemas/types.yaml#/definitions/uint32`; resource dependencies visible in the property set include clock provider phandles, genpd power domains, IOMMU stream bindings. Driver integration is through `compatible`, while client/provider integration is through cell properties, phandle arrays, child schemas, and bus-standard properties declared or inherited here.

**Risks:** Main risks are schema ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, missing required clocks/resets/interrupts/power domains, stale examples, and conditional branches that accept one SoC variant while rejecting another valid one. Unknown-property policy also matters: `additionalProperties: false` can either catch misspelled DTS properties or allow legacy extension points. For bindings with child nodes or graph/connector references, parent-child address-cell and port layout mistakes can pass driver review only if dtbs_check coverage is weak.
