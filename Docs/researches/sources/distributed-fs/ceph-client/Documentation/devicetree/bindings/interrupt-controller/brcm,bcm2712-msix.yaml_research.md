# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/brcm,bcm2712-msix.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/brcm,bcm2712-msix.yaml` is a Linux devicetree YAML schema for the `Broadcom bcm2712 MSI-X Interrupt Peripheral support` MSI/MSI-X interrupt-controller binding. This interrupt controller is used to provide interrupt vectors to the generic interrupt controller (GIC) on bcm2712. It will be used as external MSI-X controller for PCIe root complex. It is not executable kernel code; it is the hardware-description ABI that DTS authors, dt-schema, and the relevant kernel subsystem rely on so the runtime driver can parse the node without board-specific ambiguity.

## Important APIs, Types, and Functions
The public API surface is the schema's accepted node shape. `compatible` uses single `const` and covers 1 compatible token: `brcm,bcm2712-mip`. Top-level properties are `compatible`, `reg`, `#msi-cells`, `brcm,msi-offset`. Across nested schemas and child nodes this file mentions 4 distinct property names; nested/all required properties include `compatible`, `msi-controller`, `msi-ranges`, `reg`. Node naming is constrained by no explicit node-name constraint. Interrupt-controller-facing properties define how child devices encode interrupt specifiers and how the kernel irqchip or MSI domain driver maps them: addressing resources `reg`, domain declarations none, clock/reset/power hooks none, and any GPIO or parent-domain links none. Required properties are `compatible`, `reg`, `msi-controller`, `msi-ranges`; the shape of `#interrupt-cells` and parent interrupt wiring is the main ABI exposed to DTS consumers.

## Control Flow, State, and Persistence
Control flow is declarative JSON-schema evaluation rather than executable branching. `dt-doc-validate` and `dt_binding_check` load the YAML, expand `$ref` links, apply composition and conditional keywords, validate the DTS example blocks, and later `dtbs_check` applies the same contract to compiled board devicetrees. For irqchip and MSI providers, validation ensures the interrupt domain, specifier cell count, parent interrupt lines, MSI doorbells, and child-node encoding match what the kernel interrupt-controller driver will parse during early boot or bus enumeration. The schema itself stores no mutable state and writes no persistent data; its persistence is the stable source-controlled hardware ABI. External references used in evaluation are `/schemas/interrupt-controller/msi-controller.yaml#`, `/schemas/types.yaml#/definitions/uint32`; top-level/nested conditional keywords present are `allOf`.

## Risks
Risks are mostly ABI and validation risks rather than algorithmic failures. Tightening required properties, changing compatible ordering, renaming resources, altering cell counts, or closing extra properties can reject existing DTS users; loosening constraints can allow nodes that later fail driver probe or misdescribe hardware. This schema has 4 top-level properties and 4 distinct nested property names, with strictness profile: composition is closed with `unevaluatedProperties: false`. Conditional branches and shared `$ref` schemas should be checked against all in-tree users before edits, because a schema-only patch can still break board builds.

## Test Signals
Primary validation is `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/interrupt-controller/brcm,bcm2712-msix.yaml` plus `make dtbs_check` on in-tree boards using `brcm,bcm2712-mip`. The 1 example block in this file should compile under dt-schema and remain representative of the required properties. Useful integration signals include irqchip/MSI domain registration during boot, correct parent IRQ routing, valid child interrupt specifier lengths, interrupt delivery tests from devices below the domain, and no early-boot warnings about missing cells, ranges, or register resources.
