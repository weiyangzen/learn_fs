# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mfd/mediatek,mt6357.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mfd/mediatek,mt6357.yaml` is a Linux Devicetree YAML schema for `MediaTek MT6357 PMIC`, a power-management MFD binding. MT6357 is a power management system chip containing 5 buck converters and 29 LDOs. Supported features are audio codec, USB battery charging, fuel gauge, RTC This is a multifunction device with the following sub modules: - Regulator - RTC - Keys It is interfaced to host controller using SPI interface by a proprietary hardware called PMIC wrapper or pwrap. This MFD is a child device of pwrap. See the following for pwrap node definitions: Documentation/devicetree/bindings/soc/mediatek/mediatek,pwrap.yaml It is declarative ABI documentation and dt-schema validation input, not executable kernel code. Its job is to constrain how board DTS files describe the MFD parent and any child functions so the kernel can bind the parent driver, instantiate child devices, and hand common resources to subsystem drivers.

**Important APIs/types/functions:** The public API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, child schemas, references, examples, and compatible-specific composition. `compatible` uses single `const` and covers 1 compatible token: `mediatek,mt6357`. Top-level properties are `compatible`, `interrupts`, `interrupt-controller`, `#interrupt-cells`, `mediatek,hp-pull-down`, `mediatek,micbias0-microvolt`, `mediatek,micbias1-microvolt`, `regulators`, `rtc`, `keys`. Top-level required properties are `compatible`, `regulators`; required properties discovered across nested schemas include `compatible`, `regulators`. The node acts as a parent-managed MFD node. Important property roles: `compatible` selects the OF match entry and stable hardware ABI; `interrupts` describes IRQ routing or IRQ-controller behavior; `interrupt-controller` describes IRQ routing or IRQ-controller behavior; `#interrupt-cells` describes IRQ routing or IRQ-controller behavior; `regulators` contains regulator child nodes; `rtc` is a child-function schema entry for a subdevice; `keys` is a child-function schema entry for a subdevice. Named child-function entries are `keys`, `regulators`, `rtc`; patterned child schemas are none. Numeric and item constraints include `maxItems=1`.

**Control flow:** Control flow is supplied by Devicetree tooling and by the Linux MFD/subsystem core. `dt_binding_check` loads the core meta-schema, resolves `$ref` targets, applies property constraints, validates `required` sets and examples, evaluates `allOf`/`oneOf`/conditional branches, and enforces the unknown-property policy. At boot the compiled DTB node is matched through an OF compatible table; the parent MFD, syscon, PMIC, SPMI, I2C, SPI, or platform driver then reads `reg`, clocks, interrupts, resets, GPIOs, supplies, and child nodes before registering subdevices such as regulators, RTCs, GPIO/pinctrl blocks, chargers, watchdogs, LEDs, ADCs, PHYs, thermal sensors, or power/reset controllers.

**State and persistence behavior:** The YAML owns no mutable runtime state and persists no data. Its persistent effect is ABI stability: compatible tokens, child-node names, required supply/clock/IRQ/reset resources, phandle cell counts, register ranges, and fallback ordering become long-lived DTS/DTB contracts. Real state such as regulator voltage, watchdog countdown, RTC time, GPIO direction, charger status, reset line assertion, NVMEM contents, or interrupt masks is maintained by the hardware and kernel drivers that consume nodes validated by this schema.

**Risks:** Main risks are Devicetree ABI drift and parent/child contract skew. Tightening required properties can reject old board files; relaxing constraints can hide misspelled resources until probe fails. Compatible fallback ordering must match driver tables and documented hardware lineage. Child-function names and `patternProperties` must stay aligned with the subdriver bindings they reference, especially for regulators, GPIO/pinctrl, RTC, charger, LED, Type-C, watchdog, power/reset, and syscon children. Register ranges, `#address-cells`, `#size-cells`, and phandle cell counts are high-risk because they affect child resource decoding. Closure profile: top-level unknown properties are rejected by `additionalProperties: false`. This schema has 10 top-level properties and 11 distinct nested property names, so broad edits should be validated against every compatible variant and every in-tree DTS user rather than only the example node.

**Test signals:** Primary validation is `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/mfd/mediatek,mt6357.yaml` plus `make dtbs_check` for DTS files that instantiate each compatible. Useful negative tests remove required `reg`, IRQ, supply, clock, reset, GPIO, address-cell, or child-function properties; misspell child node names; use bad compatible fallback order; and exercise every conditional branch. Runtime signals are successful parent probe, expected child devices under sysfs/debugfs, working regulator/RTC/GPIO/pinctrl/reset/clock/charger/watchdog/LED/thermal/USB or other referenced subdrivers, and no new dtbs_check warnings for existing board examples.
