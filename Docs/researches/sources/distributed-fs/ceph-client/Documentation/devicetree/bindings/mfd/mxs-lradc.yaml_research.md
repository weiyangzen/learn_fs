# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mfd/mxs-lradc.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mfd/mxs-lradc.yaml` is a Linux Devicetree YAML schema for `Freescale MXS Low-Resolution ADC (LRADC)`, a ADC, touchscreen, or sensor MFD binding. The LRADC provides 16 physical channels of 12-bit resolution for analog-to-digital conversion and includes an integrated 4-wire/5-wire touchscreen controller. It is declarative ABI documentation and dt-schema validation input, not executable kernel code. Its job is to constrain how board DTS files describe the MFD parent and any child functions so the kernel can bind the parent driver, instantiate child devices, and hand common resources to subsystem drivers.

**Important APIs/types/functions:** The public API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, child schemas, references, examples, and compatible-specific composition. `compatible` uses ordered fallback `items` sequence and covers 2 compatible tokens: `fsl,imx23-lradc`, `fsl,imx28-lradc`. Top-level properties are `compatible`, `reg`, `clocks`, `interrupts`, `fsl,lradc-touchscreen-wires`, `fsl,ave-ctrl`, `fsl,ave-delay`, `fsl,settling`, `#io-channel-cells`. Top-level required properties are `compatible`, `reg`, `clocks`, `interrupts`; required properties discovered across nested schemas include `clocks`, `compatible`, `interrupts`, `reg`. The node acts as a bus or MMIO node selected by parent address cells. Important property roles: `compatible` selects the OF match entry and stable hardware ABI; `reg` carries the I2C/SPI/SPMI address or MMIO range; `clocks` integrates clock provider or consumer wiring; `interrupts` describes IRQ routing or IRQ-controller behavior. Named child-function entries are `clocks`; patterned child schemas are none. Numeric and item constraints include `maxItems=1`, `minItems=1`, `minItems=9`, `maxItems=13`, `minimum=1`, `maximum=32`, `minimum=2`, `maximum=2048`, `maximum=2047`.

**Control flow:** Control flow is supplied by Devicetree tooling and by the Linux MFD/subsystem core. `dt_binding_check` loads the core meta-schema, resolves `$ref` targets, applies property constraints, validates `required` sets and examples, evaluates `allOf`/`oneOf`/conditional branches, and enforces the unknown-property policy. At boot the compiled DTB node is matched through an OF compatible table; the parent MFD, syscon, PMIC, SPMI, I2C, SPI, or platform driver then reads `reg`, clocks, interrupts, resets, GPIOs, supplies, and child nodes before registering subdevices such as regulators, RTCs, GPIO/pinctrl blocks, chargers, watchdogs, LEDs, ADCs, PHYs, thermal sensors, or power/reset controllers.

**State and persistence behavior:** The YAML owns no mutable runtime state and persists no data. Its persistent effect is ABI stability: compatible tokens, child-node names, required supply/clock/IRQ/reset resources, phandle cell counts, register ranges, and fallback ordering become long-lived DTS/DTB contracts. Real state such as regulator voltage, watchdog countdown, RTC time, GPIO direction, charger status, reset line assertion, NVMEM contents, or interrupt masks is maintained by the hardware and kernel drivers that consume nodes validated by this schema.

Top-level composition and conditional keys are `if`, `then`, `else`. Integration points include OF matching through `compatible`, bus enumeration through parent addressing, `mfd-core` child creation where a parent driver is present, syscon/regmap access for shared registers, and subsystem handoff to regulator, GPIO, pinctrl, reset, clock, RTC, input, power-supply, thermal, watchdog, LED, IIO, USB/Type-C, PHY, NVMEM, network, or sound bindings referenced here. Compatible scan signals found driver-side files: `sources/distributed-fs/ceph-client/drivers/mfd/mxs-lradc.c`. In-tree DTS scan signals found board users: `sources/distributed-fs/ceph-client/arch/arm/boot/dts/nxp/mxs/imx23.dtsi`, `sources/distributed-fs/ceph-client/arch/arm/boot/dts/nxp/mxs/imx28.dtsi`. The file includes 1 example block.

**Risks:** Main risks are Devicetree ABI drift and parent/child contract skew. Tightening required properties can reject old board files; relaxing constraints can hide misspelled resources until probe fails. Compatible fallback ordering must match driver tables and documented hardware lineage. Child-function names and `patternProperties` must stay aligned with the subdriver bindings they reference, especially for regulators, GPIO/pinctrl, RTC, charger, LED, Type-C, watchdog, power/reset, and syscon children. Register ranges, `#address-cells`, `#size-cells`, and phandle cell counts are high-risk because they affect child resource decoding. Closure profile: top-level unknown properties are rejected by `additionalProperties: false`. This schema has 9 top-level properties and 9 distinct nested property names, so broad edits should be validated against every compatible variant and every in-tree DTS user rather than only the example node.

**Test signals:** Primary validation is `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/mfd/mxs-lradc.yaml` plus `make dtbs_check` for DTS files that instantiate each compatible. Useful negative tests remove required `reg`, IRQ, supply, clock, reset, GPIO, address-cell, or child-function properties; misspell child node names; use bad compatible fallback order; and exercise every conditional branch. Runtime signals are successful parent probe, expected child devices under sysfs/debugfs, working regulator/RTC/GPIO/pinctrl/reset/clock/charger/watchdog/LED/thermal/USB or other referenced subdrivers, and no new dtbs_check warnings for existing board examples.
