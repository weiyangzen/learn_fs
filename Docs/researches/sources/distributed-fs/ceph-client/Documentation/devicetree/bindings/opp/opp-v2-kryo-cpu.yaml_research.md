# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/opp/opp-v2-kryo-cpu.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/opp/opp-v2-kryo-cpu.yaml` defines the Linux Devicetree YAML schema for `Qualcomm Technologies, Inc. NVMEM OPP`, a operating-points binding. The schema description says: In certain Qualcomm Technologies, Inc. SoCs like APQ8096 and MSM8996, the CPU frequencies subset and voltage value of each OPP varies based on the silicon variant in use. Qualcomm Technologies, Inc. Process Voltage Scaling Tables defines the voltage and frequency value based on the speedbin blown in the efuse combination. The qcom-cpufreq-nvmem driver reads the efuse value from the SoC to provide the OPP framework with required information (existing HW bitmap). This is used to determine the voltage and frequency value for each OPP of operating-points-v2 table when it is parsed by the OPP framework. It is declarative ABI documentation and validation input rather than executable kernel code; its practical role is to make DTS/DTB hardware descriptions match the resources, topology, and compatible strings expected by the relevant kernel subsystem before probe.

## Important APIs, Types, and Functions
The public API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses an `enum` and exposes 2 tokens: `operating-points-v2-krait-cpu`, `operating-points-v2-kryo-cpu`. Top-level properties are `compatible`, `nvmem-cells`, `opp-shared`. Top-level required properties are `compatible`; required properties collected from nested schema branches include `compatible`, `nvmem-cells`, `opp-hz`, `opp-supported-hw`. Patterned child schemas are `^opp-?[0-9]+$`. Numeric and collection constraints include no explicit numeric or item limits collected. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `nvmem-cells` links calibration, MAC, serial, or speed-bin data through the NVMEM core. The highest-risk ABI details are OPP table compatibility, `opp-hz`, voltage/current/microvolt arrays, level/performance-state values, supported-hw masks, turbo/suspend flags, named supplies, and required-opps links.

## Control Flow
Runtime control flow is supplied by dt-schema and kernel subsystem code, not by this YAML file. `dt_binding_check` loads the meta-schema, resolves `$ref` entries, applies `properties`, evaluates `allOf`, `if`, `then`, checks required fields, validates `minItems`/`maxItems` and enum/const constraints, validates embedded examples, and applies the closure rule. During boot, the compiled DTB node is matched by `compatible`; then platform, PCI, SDIO, SPI, MDIO, NVMEM, OPP, PCIe, netdev, wireless, accelerator, storage, clock, reset, regulator, IRQ, GPIO, IOMMU, and power-domain helpers consume the phandles and resource arrays that this schema validates. Child nodes are discovered declaratively through fixed names, pattern properties, address cells, and referenced child schemas.

## State and Persistence Behavior
The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: compatible strings, required resource names, register and interrupt ordering, phandle and cell counts, child-node names, fallback ordering, and example layouts become long-lived contracts in board DTS files and shipped DTBs. Runtime state belongs to the matching drivers and hardware after probe, including registered OPP tables, enabled/disabled performance points, regulator voltage/current selection, clock-rate transitions, power-domain state votes, cooling state limits, and speed-bin filtering.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, link training, calibration lookup, OPP selection, NVMEM cell reads, or bus enumeration. Tightening required properties can reject existing boards; loosening them can hide missing clocks, resets, interrupts, supplies, PHY links, PCIe windows, memory regions, OPP fields, or NVMEM cells. Child-node schemas need special care because address cells, port IDs, PCI interrupt maps, wireless calibration cells, NVMEM layouts, and OPP tables must match driver-side assumptions. This schema rejects unknown top-level properties with `additionalProperties: false`. It has 3 top-level properties and 11 distinct nested property names, so broad edits should be checked against all compatible variants and DTS users, not just the nominal filename.
