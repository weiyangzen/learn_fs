# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/phy/calxeda-combophy.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/phy/calxeda-combophy.yaml` is a Linux Devicetree YAML schema for `Calxeda Highbank Combination PHYs for SATA`, a SATA/AHCI PHY binding. The Calxeda Combination PHYs connect the SoC to the internal fabric and to SATA connectors. The PHYs support multiple protocols (SATA, SGMII, PCIe) and can be assigned to different devices (SATA or XGMAC controller). Programming the PHYs is typically handled by those device drivers, not by a dedicated PHY driver. It is declarative firmware ABI documentation and dt-schema validation input, not executable kernel code. Its role is to make board DTS/DTB nodes describe PHY blocks, lanes, pads, ports, supplies, clocks, resets, and phandle provider contracts in the form the matching Linux PHY or controller driver expects.

**Important APIs/types/functions:** The exported API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `patternProperties`, local definitions, `required`, examples, and composition constraints. `compatible` uses single `const` and covers 1 compatible token: `calxeda,hb-combophy`. Top-level properties are `compatible`, `#phy-cells`, `reg`, `phydev`. Top-level required properties are `compatible`, `reg`, `phydev`, `#phy-cells`; required properties discovered across nested schemas include `#phy-cells`, `compatible`, `phydev`, `reg`. The binding acts as a MMIO or bus-addressed PHY provider node. Provider/cell contracts are `#phy-cells=const 1`. Important property roles: `compatible` selects the OF match table entry and stable hardware ABI; `#phy-cells` defines the phandle argument contract for PHY consumers; `reg` carries MMIO ranges, syscon offsets, port numbers, or bus addresses. Patterned child schemas are none; nested topology or child names discovered from properties are no explicit nested pad/lane/port names discovered. Local reusable definitions are none. Numeric/item constraints include `maxItems=1`, `maximum=31`; selected enum/const literals include `calxeda,hb-combophy`, `1`.

**Control flow:** Control flow is dt-schema evaluation. `dt_binding_check` parses the YAML, validates it against the core meta-schema, resolves `$ref` dependencies, applies `properties` and `patternProperties`, evaluates `allOf`/`oneOf`/`anyOf`/conditional branches, checks `required` lists and item counts, compiles examples, and enforces the closure rule. At boot the YAML is not interpreted; firmware supplies a compiled DTB node, the kernel matches `compatible` in the relevant OF table, and the PHY/provider driver reads `reg`, clocks, resets, supplies, child lanes/ports, and `#phy-cells` to register PHYs. Consumer controllers later resolve `phys` phandles and invoke the generic PHY framework for init, power-on, mode setting, calibration, and power-off.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence. Its durable state is ABI shape: compatible strings, property names, valid enum values, provider cell counts, child-node naming, lane or port numbering, and allowed topology. Runtime state such as PLL lock, link training, lane muxing, PHY mode, impedance tuning, analog calibration, reset sequencing, and power transitions lives in the matching kernel driver and hardware registers; this schema only constrains how those resources and modes are represented in firmware.

**Dependencies and integration points:** Maintainers: Andre Przywara <andre.przywara@arm.com>. Direct schema dependencies are `/schemas/types.yaml#/definitions/uint32`. Top-level composition/conditional keys are none. Integration points are Devicetree common schemas, the Linux generic PHY framework, controller bindings that consume `phys`/`phy-names`, platform/MMIO or syscon buses, regulator supplies, reset controllers, clock providers, GPIO descriptors, power domains, and SoC-specific lane mux drivers. Compatible scan signals found driver-side files: no direct in-tree driver match found by compatible scan. In-tree DTS scan signals found board users: `sources/distributed-fs/ceph-client/arch/arm/boot/dts/calxeda/ecx-common.dtsi`. The file includes 1 example block for validation.

**Risks:** Primary risks are PHY ABI drift and resource lookup mismatch. Removing or reordering compatible fallbacks can break legacy DTBs; changing `#phy-cells`, child `reg` numbering, lane names, or port names can break consumers that already reference the provider; renaming clocks, resets, supplies, GPIOs, or power domains can break driver probe even when the hardware block is unchanged. Multi-protocol SerDes and pad-controller schemas are especially sensitive because lane mux enums, protocol names, and companion USB2/USB3 or PCIe/SATA relationships must align with driver tables and board wiring. The closure profile is: top-level unknown properties are rejected by `additionalProperties: false`. Because this schema has 4 top-level properties and 4 distinct nested property names, broad edits should be checked against every compatible variant, examples, and existing DTS users.

**Test signals:** Primary validation signals are `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/phy/calxeda-combophy.yaml` in a kernel tree with dt-schema installed and `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/phy/calxeda-combophy.yaml` for boards using these compatibles. Useful negative checks omit required clocks/resets/supplies, use invalid `#phy-cells`, bad child-node names, wrong lane `reg` values, or unsupported enum values. Runtime integration signals are successful driver probe, registered PHY providers with expected phandle arguments, consumers resolving `phys`, clocks and regulators balanced across suspend/resume, link bring-up for the relevant USB/PCIe/SATA/UFS/MIPI/SerDes protocol, and no new schema warnings for examples or in-tree DTS files.
