# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/loongson,liointc.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Loongson Local I/O Interrupt Controller`. In this tree it is an interrupt controller binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: This interrupt controller is found in the Loongson-3 family of chips and Loongson-2K series chips, as the primary package interrupt controller which can route local I/O interrupt to interrupt lines of cores. Be aware of the following points. 1.The Loongson-2K0500 is a single core CPU; 2.The Loongson-2K0500/2K1000 has 64 device interrupt sources as inputs, so we need to define two nodes in dts{i} to describe the "0-31" and "32-61" interrupt sources respectively.

**Important APIs/types/functions:** This YAML is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/interrupt-controller/loongson,liointc.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and any referenced dt-schema fragments. Compatible strings or compatible-pattern values are `loongson,liointc-1.0`, `loongson,liointc-1.0a`, `loongson,liointc-2.0`. Required properties are `compatible`, `reg`, `interrupts`, `interrupt-names`, `interrupt-controller`, `#interrupt-cells`, `loongson,parent_int_map`. Important top-level properties are `compatible`, `reg`, `reg-names`, `#address-cells`, `interrupt-controller`, `interrupts`, `interrupt-names`, `#interrupt-cells`, `loongson,parent_int_map`. **Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. Schema composition/conditional keywords present: `allOf`, `else`, `if`, `then`. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IRQ domain code uses it to translate DT interrupt specifiers into Linux IRQs and route them to an upstream parent domain. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as `reg`, `#address-cells`, `interrupts`. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.
