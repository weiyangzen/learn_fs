# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/trivial-devices.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/trivial-devices.yaml` defines `Trivial I2C and SPI devices`, a Trivial Devicetree device registry. This is a list of trivial I2C and SPI devices that have simple device tree bindings, consisting only of a compatible field, an address and possibly an interrupt line. If a device needs more specific bindings, such as properties to describe some aspect of it, there needs to be a specific binding document for it just like any other devices. It is declarative firmware ABI documentation and dt-schema validation input; Linux does not execute this YAML at runtime, but the schema controls which DTS nodes are accepted for the corresponding hardware or bus-attached device.

## Control Flow
Control flow is schema evaluation. `dt_binding_check` parses the YAML, validates the meta-schema, resolves `$ref` links, applies `properties`, `patternProperties`, required lists, item counts, const/enum checks, and composition or conditional blocks (none); it also compiles the embedded examples. `dtbs_check` applies the same rules to compiled board DTBs. During boot the kernel only consumes the DTB: OF matching selects the driver, platform/bus code maps resources, phandles are resolved, and the driver performs hardware setup.

## State and Persistence Behavior
The file has no mutable runtime state and performs no persistence. Its durable state is ABI shape: compatible strings, property names, child-node names, phandle cell counts, register and interrupt ordering, resource names, and example topology. Runtime behavior is owned by matched drivers and hardware: there is no runtime state in this binding; each listed compatible delegates all behavior to the matched simple device driver and its bus core. Schema edits therefore persist as compatibility commitments for existing DTS files even though no code path is stored here.

## Risks
Main risks are ABI drift around compatible-string registry churn, duplicate vendor/model entries, devices that outgrow the trivial binding and need a dedicated schema, and board nodes relying on only generic bus properties; changing compatible ordering or removing fallback strings; broadening a schema so invalid board nodes pass; tightening a schema so existing DTBs fail; and mismatches between YAML clock/reset/regulator/PHY names and driver lookup tables. Multi-role USB and Type-C bindings are especially sensitive to graph endpoints, role-switch dependencies, connector children, and wakeup semantics. UFS bindings are sensitive to per-SoC clock arrays, ICE register resources, PHY lane counts, and reset/power sequencing. The closure profile rejects undeclared top-level properties with `additionalProperties: false`.

## Test Signals
Use `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/trivial-devices.yaml` for this schema and its examples, then `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/trivial-devices.yaml` against boards using these compatibles. Useful negative tests remove each required property, scramble compatible fallback order, use bad child-node names, provide too many/few clocks, resets, interrupts, PHYs, or register windows, and add undeclared properties when the schema is closed. Runtime signals are clean driver probe, expected PHY/role-switch/provider registration where applicable, correct device enumeration, suspend/resume without resource leaks, and no new schema warnings.
