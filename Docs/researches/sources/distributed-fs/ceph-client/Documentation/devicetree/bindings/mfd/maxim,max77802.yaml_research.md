# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mfd/maxim,max77802.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mfd/maxim,max77802.yaml` is a Linux Devicetree YAML schema for `Maxim MAX77802 Power Management IC`, a power-management MFD binding. This is a part of device tree bindings for Maxim MAX77802 Power Management Integrated Circuit (PMIC). The Maxim MAX77802 is a Power Management IC which includes voltage and current regulators (10 high efficiency Buck regulators and 32 Low-DropOut (LDO)), RTC and clock outputs. The MAX77802 provides two 32.768khz clock outputs that can be controlled (gated/ungated) over I2C. The clock IDs are defined as preprocessor macros in dt-bindings/clock/maxim,max77802.h. It is declarative ABI documentation and dt-schema validation input, not executable kernel code. Its job is to constrain how board DTS files describe the MFD parent and any child functions so the kernel can bind the parent driver, instantiate child devices, and hand common resources to subsystem drivers.

**Important APIs/types/functions:** The public API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, child schemas, references, examples, and compatible-specific composition. `compatible` uses single `const` and covers 1 compatible token: `maxim,max77802`. Top-level properties are `compatible`, `#clock-cells`, `interrupts`, `reg`, `regulators`, `inb1-supply`, `inb2-supply`, `inb3-supply`, `inb4-supply`, `inb5-supply`, `inb6-supply`, `inb7-supply`, `inb8-supply`, `inb9-supply`, `inb10-supply`, `inl1-supply`, `inl2-supply`, `inl3-supply`, `inl4-supply`, `inl5-supply`, `inl6-supply`, `inl7-supply`, `inl9-supply`, `inl10-supply`, `wakeup-source`. Top-level required properties are `compatible`, `#clock-cells`, `reg`; required properties discovered across nested schemas include `#clock-cells`, `compatible`, `reg`. The node acts as a I2C-addressed companion device or PMIC node. Important property roles: `compatible` selects the OF match entry and stable hardware ABI; `#clock-cells` integrates clock provider or consumer wiring; `interrupts` describes IRQ routing or IRQ-controller behavior; `reg` carries the I2C/SPI/SPMI address or MMIO range; `regulators` contains regulator child nodes; `inb1-supply` links supply rails to the regulator framework; `inb2-supply` links supply rails to the regulator framework; `inb3-supply` links supply rails to the regulator framework; `inb4-supply` links supply rails to the regulator framework; `inb5-supply` links supply rails to the regulator framework; `inb6-supply` links supply rails to the regulator framework; `inb7-supply` links supply rails to the regulator framework; `inb8-supply` links supply rails to the regulator framework; `inb9-supply` links supply rails to the regulator framework; and 10 more resource/property roles. Named child-function entries are `regulators`; patterned child schemas are none. Numeric and item constraints include `maxItems=1`.

**Control flow:** Control flow is supplied by Devicetree tooling and by the Linux MFD/subsystem core. `dt_binding_check` loads the core meta-schema, resolves `$ref` targets, applies property constraints, validates `required` sets and examples, evaluates `allOf`/`oneOf`/conditional branches, and enforces the unknown-property policy. At boot the compiled DTB node is matched through an OF compatible table; the parent MFD, syscon, PMIC, SPMI, I2C, SPI, or platform driver then reads `reg`, clocks, interrupts, resets, GPIOs, supplies, and child nodes before registering subdevices such as regulators, RTCs, GPIO/pinctrl blocks, chargers, watchdogs, LEDs, ADCs, PHYs, thermal sensors, or power/reset controllers.

**State and persistence behavior:** The YAML owns no mutable runtime state and persists no data. Its persistent effect is ABI stability: compatible tokens, child-node names, required supply/clock/IRQ/reset resources, phandle cell counts, register ranges, and fallback ordering become long-lived DTS/DTB contracts. Real state such as regulator voltage, watchdog countdown, RTC time, GPIO direction, charger status, reset line assertion, NVMEM contents, or interrupt masks is maintained by the hardware and kernel drivers that consume nodes validated by this schema.

**Risks:** Main risks are Devicetree ABI drift and parent/child contract skew. Tightening required properties can reject old board files; relaxing constraints can hide misspelled resources until probe fails. Compatible fallback ordering must match driver tables and documented hardware lineage. Child-function names and `patternProperties` must stay aligned with the subdriver bindings they reference, especially for regulators, GPIO/pinctrl, RTC, charger, LED, Type-C, watchdog, power/reset, and syscon children. Register ranges, `#address-cells`, `#size-cells`, and phandle cell counts are high-risk because they affect child resource decoding. Closure profile: top-level unknown properties are rejected by `additionalProperties: false`. This schema has 25 top-level properties and 25 distinct nested property names, so broad edits should be validated against every compatible variant and every in-tree DTS user rather than only the example node.

**Test signals:** Primary validation is `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/mfd/maxim,max77802.yaml` plus `make dtbs_check` for DTS files that instantiate each compatible. Useful negative tests remove required `reg`, IRQ, supply, clock, reset, GPIO, address-cell, or child-function properties; misspell child node names; use bad compatible fallback order; and exercise every conditional branch. Runtime signals are successful parent probe, expected child devices under sysfs/debugfs, working regulator/RTC/GPIO/pinctrl/reset/clock/charger/watchdog/LED/thermal/USB or other referenced subdrivers, and no new dtbs_check warnings for existing board examples.
