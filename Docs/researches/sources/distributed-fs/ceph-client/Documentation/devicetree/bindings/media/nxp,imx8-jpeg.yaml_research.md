# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/nxp,imx8-jpeg.yaml

**Purpose:** Defines the Devicetree JSON-schema ABI for `i.MX8QXP/QM JPEG decoder/encoder`. It is a JPEG codec accelerator binding in the Ceph client Linux source snapshot, constraining how board DTS/DTB files describe media hardware so Linux media, V4L2 mem2mem, platform, clock, reset, power-domain, IOMMU, and graph helpers can bind the correct driver resources. The source description says: The JPEG decoder/encoder present in iMX8QXP and iMX8QM SoCs is an ISO/IEC 10918-1 JPEG standard compliant decoder/encoder, for Baseline and Extended Sequential DCT modes.

**Important APIs/types/functions:** This is declarative schema, so the exported API is the binding contract rather than C functions. Public surfaces include `$id` `http://devicetree.org/schemas/media/nxp,imx8-jpeg.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, examples, and dt-schema references. The `compatible` property uses `oneOf` with 3 accepted forms and accepts `nxp,imx8qxp-jpgdec`, `nxp,imx8qxp-jpgenc`, `nxp,imx8qm-jpgdec`, `nxp,imx95-jpgdec`, `nxp,imx8qm-jpgenc`, `nxp,imx95-jpgenc`. Top-level required properties are `compatible`, `reg`, `clocks`, `interrupts`, `power-domains`; required names across nested/conditional schemas include `clocks`, `compatible`, `interrupts`, `power-domains`, `reg`. Top-level properties are `compatible`, `reg`, `clocks`, `interrupts`, `power-domains`, `sram`; all nested property names include `clocks`, `compatible`, `interrupts`, `power-domains`, `reg`, `sram`. Resource constraints visible in the schema include `compatible`, `reg` (maxItems=1), `clocks`, `interrupts` (minItems=1; maxItems=4), `power-domains` (minItems=1; maxItems=5), `sram`. Closure is `additionalProperties: False`.

**Control flow:** Runtime control flow is supplied by dt-schema and kernel probing. `dt_binding_check` loads the core meta-schema, resolves references, validates the compatible form, applies required lists and `minItems`/`maxItems`/`const` restrictions, evaluates conditionals, and compiles the inline examples. At boot the DTB node is matched by `compatible`; the platform or media driver then reads MMIO ranges, named interrupts, clocks, resets, power domains, IOMMU streams, DMA/interconnect paths, firmware or reserved-memory phandles, and graph endpoints. Schema composition uses `allOf`, `else`, `if`, `oneOf`, `then`. Validation can therefore change by compatible string, for example by tightening clock/reset counts, requiring SoC-specific helper phandles, or allowing/deprecating child codec nodes. This binding has no media graph endpoint surface; integration is by platform device resources and codec-specific child nodes.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence itself. Its persistent effect is ABI stability for DTS files and shipped DTBs: compatible strings, child-node names, phandle relationships, address ranges, cell counts, and media graph topology are long-lived hardware descriptions. Any change to required properties, resource ordering, child object schemas, or unknown-property policy can invalidate existing board descriptions even though no kernel state is written by the YAML.

**Dependencies and integration points:** Direct schema references are `/schemas/types.yaml#/definitions/phandle`. Runtime dependencies are genpd power domains, clock provider phandles and fixed clock-name ordering, on-chip SRAM phandle. No nested object nodes are defined beyond common schema references. Maintainers listed in the binding are `Mirela Rabulea <mirela.rabulea@nxp.com>`.

**Risks:** Key risks: compatible-string or fallback-order drift can break OF matching and dtbs_check expectations; resource array ordering is ABI-sensitive for `reg-names`, `clock-names`, `interrupt-names`, `power-domain-names`, and `reset-names`; SoC-specific power-domain count differences are easy to regress in fallback compatibles. The closure policy is `additionalProperties: False`, so unknown properties are intentionally rejected after referenced schemas are evaluated.

Useful negative tests remove required properties such as `compatible`, `reg`, `clocks`, `interrupts`, `power-domains`, alter named resource ordering, exceed item counts, and inject unknown properties to confirm the closure rule catches mistakes.
