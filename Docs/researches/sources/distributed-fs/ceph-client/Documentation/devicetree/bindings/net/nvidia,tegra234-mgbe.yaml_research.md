# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/net/nvidia,tegra234-mgbe.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/net/nvidia,tegra234-mgbe.yaml` defines the Linux Devicetree YAML schema for `Tegra234 MGBE Multi-Gigabit Ethernet Controller`, a Ethernet MAC/controller binding. It is declarative ABI documentation and validation input, not executable networking code. Its purpose is to keep DTS/DTB nodes aligned with the resources and topology expected by the matching kernel subsystem before drivers probe hardware.

## Important APIs, Types, and Functions
The API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses a single `const` with 1 token: `nvidia,tegra234-mgbe`. Top-level properties are `compatible`, `reg`, `reg-names`, `interrupts`, `interrupt-names`, `clocks`, `clock-names`, `resets`, `reset-names`, `interconnects`, `interconnect-names`, `iommus`, `power-domains`, `phy-handle`, `phy-mode`, `mdio`. Top-level required properties are `compatible`, `reg`, `interrupts`, `interrupt-names`, `clocks`, `clock-names`, `resets`, `reset-names`, `power-domains`, `phy-handle`, `phy-mode`; required properties collected from nested branches include `clock-names`, `clocks`, `compatible`, `interrupt-names`, `interrupts`, `phy-handle`, `phy-mode`, `power-domains`, `reg`, `reset-names`, `resets`. Patterned child schemas are none. Numeric and collection constraints include `maxItems=3`, `minItems=1`, `maxItems=12`, `maxItems=2`, `maxItems=1`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `reg` describes MMIO ranges, MDIO child addresses, SPI/I2C addresses, or port selectors; `interrupts` routes link/status, RX/TX, error, or management IRQs; `interrupt-names` routes link/status, RX/TX, error, or management IRQs; `clocks` binds MAC/MDIO/PHY/PTP/SerDes clock inputs; `clock-names` binds MAC/MDIO/PHY/PTP/SerDes clock inputs; `resets` defines reset-controller or GPIO reset sequencing; `reset-names` defines reset-controller or GPIO reset sequencing; `iommus` integrates the device with SoC PM, DMA, or IOMMU topology; `power-domains` integrates the device with SoC PM, DMA, or IOMMU topology; `phy-handle` connects the MAC/switch port to PHY, PCS, SFP, or fixed-link infrastructure; `phy-mode` connects the MAC/switch port to PHY, PCS, SFP, or fixed-link infrastructure; `mdio` models MDIO management bus topology. The highest-risk ABI details are compatible fallback ordering, register/interrupt ordering, clock/reset names, DMA/coherency flags, PHY or fixed-link connection modelling, and vendor resource properties.

## Control Flow
Control flow is dt-schema evaluation. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, evaluates no top-level conditionals, checks required fields and min/max constraints, validates examples, and enforces the closure policy. At runtime the YAML does not execute: a compiled DTB node is matched through the driver's OF table, then netdev, phylib/phylink, MDIO, DSA/switchdev, NFC, IEEE 802.15.4, regulator, clock, reset, GPIO, IRQ, DMA, IOMMU, and platform-bus helpers consume the validated resources. Child-node control flow is declarative too: MDIO children, switch ports, PHY packages, connector/LED nodes, and graph/fixed-link nodes are discovered by common Devicetree helpers according to the schema shape.

## State and Persistence Behavior
The file stores no mutable runtime state and writes no persistent data. Its persistence is ABI stability: compatible strings, required resource names, phandle/cell counts, child-node names, port IDs, PHY addresses, fallback ordering, and example layouts become long-lived contracts in DTS and DTB artifacts. Runtime state belongs to drivers and hardware after probe, including netdev registration, DMA rings, NAPI scheduling, runtime PM, link mode negotiation through phylink/phylib, MAC address assignment, and PTP/TSN state where supported.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource shape changes that still compile but break driver probe or link bring-up. Tightening required properties can reject existing board files; loosening them can hide missing clocks, resets, interrupts, PHY links, port nodes, or MDIO addresses. Child-node schemas need special care because port numbering, PHY package topology, MDIO mux selectors, NFC transport GPIOs, and switch CPU/user-port layout must match driver tables. This schema rejects unknown top-level properties with `additionalProperties: false`. It has 16 top-level properties and 16 distinct nested property names, so broad edits should be checked against all compatibles and DTS users, not just the filename's nominal device.

## Test Signals
Run `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/net/nvidia,tegra234-mgbe.yaml` for targeted schema validation and `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/net/nvidia,tegra234-mgbe.yaml` against boards using these nodes. High-value negative checks remove required `reg`, interrupts, clocks, resets, PHY links, MDIO children, switch ports, or GPIOs; use invalid child `reg` values; misspell vendor properties; and exercise every compatible-specific branch. Runtime integration signals are successful driver probe, correct netdev/PHY/MDIO/DSA/NFC/802.15.4 registration, clean link or controller bring-up, valid interrupt/reset/power sequencing, and no dtbs_check regressions in embedded examples or in-tree DTS users.
