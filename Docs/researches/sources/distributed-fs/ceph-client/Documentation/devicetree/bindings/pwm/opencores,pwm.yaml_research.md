# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pwm/opencores,pwm.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pwm/opencores,pwm.yaml` defines the Linux Devicetree YAML schema for `OpenCores PWM controller`, a PWM controller binding. The schema description says: The OpenCores PTC ip core contains a PWM controller. When operating in PWM mode, the PTC core generates binary signal with user-programmable low and high periods. All PTC counters and registers are 32-bit. It is declarative ABI documentation and validation input, not executable driver code. Its job is to keep DTS/DTB nodes aligned with the resources, child nodes, and electrical or timing constraints expected by the matching kernel subsystem before a driver probes hardware.

## Important APIs, Types, and Functions
The API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `patternProperties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses an ordered compatible/fallback sequence with 4 tokens: `starfive,jh7100-pwm`, `starfive,jh7110-pwm`, `starfive,jh8100-pwm`, `opencores,pwm-v1`. Top-level properties are `compatible`, `reg`, `clocks`, `resets`, `#pwm-cells`. Top-level required properties are `compatible`, `reg`, `clocks`; required properties collected from nested branches include `clocks`, `compatible`, `reg`. Patterned child schemas are none. Numeric and collection constraints include `maxItems=1`. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `reg` gives MMIO, I2C, SPI, child address, or selector placement; `clocks` binds functional, bus, reference, timer, or output clocks; `resets` defines reset-controller or GPIO reset sequencing; `#pwm-cells` fixes child-node or phandle specifier shape. The highest-risk ABI details are compatible fallback ordering, register and clock layout, `#pwm-cells`, channel counts, period counter ranges, reset/interrupt resources, and SoC-specific polarity or prescaler rules.

## Control Flow
Control flow is dt-schema evaluation rather than imperative execution. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties` and `patternProperties`, evaluates `allOf`, checks required fields and min/max constraints, validates examples, and enforces the closure policy. At runtime this YAML does not execute: the compiled DTB node is matched through a kernel OF table or subsystem-specific child-node parser, then helpers for power-supply, regulator, PWM, PTP, PPS, PowerPC platform, clocks, resets, interrupts, GPIOs, pinctrl, power domains, and MFD parents consume the validated resources.

## State and Persistence Behavior
The file stores no mutable runtime state and writes no persistent data. Its persistence is ABI stability: compatible strings, required resource names, phandle/cell counts, child-node names, electrical limit properties, fallback ordering, and example layouts become long-lived contracts in DTS and DTB artifacts. Runtime state belongs to drivers and hardware after probe, including PWM chip registration, channel allocation, configured period/duty/polarity, enabled outputs, clock/runtime-PM state, and hardware counter register state.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, power sequencing, clock setup, IRQ delivery, or consumer phandle resolution. Tightening required properties can reject existing board files; loosening them can hide missing supplies, clocks, resets, interrupts, current/voltage limits, PWM cell counts, PTP/PPS GPIOs, or regulator child constraints. This schema rejects unknown top-level properties with `additionalProperties: false`. It has 5 top-level properties and 5 distinct nested property names, so broad edits should be checked against all compatibles, examples, and in-tree DTS users rather than only the filename's nominal device.
