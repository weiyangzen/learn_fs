# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/interrupt-controller/st,stih407-irq-syscfg.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `STMicroelectronics STi System Configuration Controlled IRQs`. In this tree it is an interrupt controller binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: On STi based systems; External, CTI (Core Sight), PMU (Performance Management), and PL310 L2 Cache IRQs are controlled using System Configuration registers. This device is used to unmask them prior to use.

**Important APIs/types/functions:** This YAML is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/interrupt-controller/st,stih407-irq-syscfg.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and any referenced dt-schema fragments. Compatible strings or compatible-pattern values are `st,stih407-irq-syscfg`. Required properties are `compatible`, `st,syscfg`, `st,irq-device`, `st,fiq-device`. Important top-level properties are `compatible`, `st,syscfg`, `st,irq-device`, `st,fiq-device`, `st,invert-ext`. Direct and nested `$ref` dependencies are `/schemas/types.yaml#/definitions/phandle`, `/schemas/types.yaml#/definitions/uint32-array`, `/schemas/types.yaml#/definitions/uint32`. Property roles include `compatible` for driver match key and stable hardware ABI identifier; `st,syscfg` for binding-specific property constrained by the schema; `st,irq-device` for binding-specific property constrained by the schema; `st,fiq-device` for binding-specific property constrained by the schema; `st,invert-ext` for binding-specific property constrained by the schema. The top-level unknown-property policy is `additionalProperties: false`. Maintainers are `Patrice Chotard <patrice.chotard@foss.st.com>`.

**Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. The file has no nested conditional schema composition beyond direct property validation. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IRQ domain code uses it to translate DT interrupt specifiers into Linux IRQs and route them to an upstream parent domain. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as none declared. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.
