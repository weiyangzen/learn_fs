# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/leds/common.yaml

**Purpose:** Defines the Linux Devicetree JSON-schema contract for `Common leds properties`. In this source tree it is a LED controller or common LED schema binding; it constrains board DTS/DTB nodes so kernel OF matching and subsystem code can discover the hardware resources consistently. This is declarative ABI documentation, not executable Ceph client code, but it is part of the imported kernel documentation corpus that protects hardware-description compatibility. The source description says: LED and flash LED devices provide the same basic functionality as current regulators, but extended with LED and flash LED specific features like blinking patterns, flash timeout, flash faults and external flash strobe mode. Many LED devices expose more than one current output that can be connected to one or more discrete LED component. Since the arrangement of connections can influence the way of the LED device initialization, the LED components have to be tightly coupled with the LED device binding. They are represented by child nodes of the parent LED device binding.

**Important APIs/types/functions:** The public surface is the schema itself: `$id` `http://devicetree.org/schemas/leds/common.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, composition keywords, closure rules, and `examples` consumed by `dt-schema`. Compatible strings are none declared. Required properties are none declared. Important top-level properties include `led-sources`, `function`, `color`, `function-enumerator`, `label`, `default-state`, `linux,default-trigger`, `led-pattern`, `led-max-microamp`, `max-brightness`, `default-brightness`, `panic-indicator`, `retain-state-shutdown`, `trigger-sources`, `active-high`, `active-low`, `inactive-high-impedance`, `flash-max-microamp`, `flash-max-timeout-us`. Patterned or child-node surfaces include none declared. Direct schema references are `/schemas/types.yaml#/definitions/phandle-array`, `/schemas/types.yaml#/definitions/string`, `/schemas/types.yaml#/definitions/uint32`, `/schemas/types.yaml#/definitions/uint32-array`, `/schemas/types.yaml#/definitions/uint32-matrix`. Maintainers: Jacek Anaszewski <jacek.anaszewski@gmail.com>, Pavel Machek <pavel@ucw.cz>. Top-level property policy is `additionalProperties: true`.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel drivers rather than by this YAML. `dt_binding_check` loads the core meta-schema, resolves `$ref` dependencies, applies constants/enums/cardinality/range checks, evaluates composition and conditional branches (`oneOf`, `allOf`, `if`, `then`), and validates the embedded examples. At boot, the compiled DTB node is matched by `compatible`; the relevant LED driver or common subsystem reads resource properties, phandles, child nodes, and cells before registering devices or provider relationships. Child/provider surfaces to watch here are none declared.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistence is ABI persistence: accepted DTS nodes encode hardware identity, register windows, interrupts, power/clock/reset topology, phandle cell widths, channel indexes, and child LED/IOMMU/IPMI layout for long-lived boards. Tightening `required`, changing compatible fallback order, altering cell counts, or changing closure policy can reject existing DTBs or make drivers parse resources differently.

**Dependencies and integration points:** Integrated with LED class devices, multicolor/flash/channel child nodes, GPIO/PWM/regulator resources, and trigger/function/color naming. Schema dependencies include `/schemas/types.yaml#/definitions/phandle-array`, `/schemas/types.yaml#/definitions/string`, `/schemas/types.yaml#/definitions/uint32`, `/schemas/types.yaml#/definitions/uint32-array`, `/schemas/types.yaml#/definitions/uint32-matrix`; examples may also include dt-bindings headers. Resource integration is through properties such as `max-brightness` for maximum logical brightness; `led-sources` for hardware output/channel selection; `function` for standard LED function name; `color` for standard LED color identifier; `function-enumerator` for disambiguates same-function LEDs; `linux,default-trigger` for default LED trigger binding; `flash-max-microamp` for flash LED current limit; `flash-max-timeout-us` for flash timeout limit; `led-max-microamp` for steady LED current limit. Driver integration is through `compatible`, while subsystem integration is through phandle arrays, provider cell counts, common schemas, and child-node schemas inherited or declared here.

**Risks and edge cases:** Main risks are schema ABI drift, missing or stale compatible coverage, incorrect min/max item constraints, wrong `#*-cells` values, resource names that diverge from driver expectations, conditionals that validate one SoC or chip variant while rejecting another valid one, and examples that no longer reflect real DTS users. Closure policy (`additionalProperties: true`) is useful for catching misspellings but can also block legitimate extensions. For LED/backlight children, channel numbering and `reg`/`led-sources` constraints are common failure points; for IOMMU bindings, stream IDs and cell widths are especially sensitive; for IPMI bindings, host/BMC address and register-resource shape must match the driver.

**Test signals:** Run `make dt_binding_check DT_SCHEMA_FILES=sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/leds/common.yaml` and `make dtbs_check` against DTS files using every compatible listed here. The 3 embedded example block(s) should compile through `dtc` and validate against referenced schemas. Useful negative tests remove each required property, add an unknown property under the declared closure policy, exercise compatible-specific conditionals, and verify the matching Linux driver still probes with the resources, child nodes, and phandle specifiers described by this binding.
