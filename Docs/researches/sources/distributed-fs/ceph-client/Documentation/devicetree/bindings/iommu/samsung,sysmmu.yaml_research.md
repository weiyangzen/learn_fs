# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/iommu/samsung,sysmmu.yaml

**Purpose:** Defines the Linux Devicetree JSON-schema contract for `Samsung Exynos IOMMU H/W, System MMU (System Memory Management Unit)`. In this source tree it is a IOMMU provider or IOMMU-adjacent binding; it constrains board DTS/DTB nodes so kernel OF matching and subsystem code can discover the hardware resources consistently. This is declarative ABI documentation, not executable Ceph client code, but it is part of the imported kernel documentation corpus that protects hardware-description compatibility. The source description says: Samsung's Exynos architecture contains System MMUs that enables scattered physical memory chunks visible as a contiguous region to DMA-capable peripheral devices like MFC, FIMC, FIMD, GScaler, FIMC-IS and so forth. System MMU is an IOMMU and supports identical translation table format to ARMv7 translation tables with minimum set of page properties including access permissions, shareability and security protection. In addition, System MMU has another capabilities like L2 TLB or block-fetch buffers to minimize translation latency. System MMUs are in many to one relation with peripheral devices, i.e. single peripheral device might have multiple System MMUs (usually one for each bus master), but one System MMU can handle transactions from only one peripheral device. The relation between a System MMU and the peripheral device needs to be defined in device node of the peripheral device. MFC in all Exynos SoCs and FIMD, M2M Scalers and G2D in Exynos5420 has 2 System MMUs. * MFC has one System MMU on its left and right bus. * FIMD in Exynos5420 has one System MMU for window 0 and 4, the other system MMU for window 1, 2 and 3. * M2M Scalers and G2D in Exynos5420 has one System MMU on the read channel and the other System MMU on the write channel. For information on assigning System MMU controller to its peripheral devices, see generic IOMMU bindings.

Important top-level properties include `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `#iommu-cells`, `power-domains`. Patterned or child-node surfaces include none declared. **State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistence is ABI persistence: accepted DTS nodes encode hardware identity, register windows, interrupts, power/clock/reset topology, phandle cell widths, channel indexes, and child LED/IOMMU/IPMI layout for long-lived boards. Tightening `required`, changing compatible fallback order, altering cell counts, or changing closure policy can reject existing DTBs or make drivers parse resources differently.

**Dependencies and integration points:** Integrated with IOMMU stream IDs, DMA translation, device isolation, and `iommus`/`#iommu-cells` style phandle integration. Schema dependencies include none declared; examples may also include dt-bindings headers. Resource integration is through properties such as `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address; `interrupts` for interrupt routing; `clocks` for clock provider phandles; `clock-names` for named clock inputs; `power-domains` for genpd power-domain attachment; `#iommu-cells` for IOMMU client specifier cell count. **Risks and edge cases:** Main risks are schema ABI drift, missing or stale compatible coverage, incorrect min/max item constraints, wrong `#*-cells` values, resource names that diverge from driver expectations, conditionals that validate one SoC or chip variant while rejecting another valid one, and examples that no longer reflect real DTS users. Closure policy (`additionalProperties: false`) is useful for catching misspellings but can also block legitimate extensions. For LED/backlight children, channel numbering and `reg`/`led-sources` constraints are common failure points; for IOMMU bindings, stream IDs and cell widths are especially sensitive; for IPMI bindings, host/BMC address and register-resource shape must match the driver.
