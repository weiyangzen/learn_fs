# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pci/host-generic-pci.yaml

**Purpose:** Defines the Devicetree YAML/JSON-schema contract for `Generic PCI host controller`. It is a host/root-complex controller binding in the PCI/PCIe devicetree binding family; it constrains how DTS/DTB nodes identify the PCI hardware, describe register windows, interrupts, clocks, resets, PHYs, address translation, DMA/IOMMU reachability, and optional child/root-port layout for Linux PCI probing. The source description says: Firmware-initialised PCI host controllers and PCI emulations, such as the virtio-pci implementations found in kvmtool and other para-virtualised systems, do not require driver support for complexities such as regulator and clock management. In fact, the controller may not even require the configuration of a control interface by the operating system, instead presenting a set of fixed windows describing a subset of IO, Memory and Configuration Spaces. Configuration Space is assumed to be memory-mapped (as opposed to being accessed via an ioport) and laid out with a direct correspondence to the geography of a PCI bus address by concatenating the various components to form an offset. For CAM, this 24-bit offset is: cfg_offset(bus, device, function, register) = bus << 16 | device << 11 | function << 8 | register While ECAM extends this by 4 bits to accommodate 4k of function space: cfg_offset(bus, device, function, register) = bus << 20 | device << 15 | function << 12 | register

**Important APIs/types/functions:** This file is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/pci/host-generic-pci.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, the `properties` block, `required` list, schema-composition keywords, inline examples, and the compatible strings consumed by kernel OF match tables. Compatible strings covered here: `arm,juno-r1-pcie`, `cavium,pci-host-thunder-ecam`, `cavium,pci-host-thunder-pem`, `hisilicon,hip06-pcie-ecam`, `hisilicon,hip07-pcie-ecam`, `marvell,armada8k-pcie-ecam`, `pci-host-cam-generic`, `pci-host-ecam-generic`, `plda,xpressrich3-axi`, `snps,dw-pcie-ecam`, `socionext,synquacer-pcie-ecam`. Directly declared properties are `compatible`, `reg`, `ranges`, `dma-coherent`, `iommu-map`, `iommu-map-mask`, `msi-parent`, `ats-supported`. Required properties are `compatible`, `reg`, `ranges`. Maintainers: Will Deacon <will@kernel.org>.

**Control flow:** Validation flow is handled by dt-schema: the core meta-schema loads this YAML, resolves references (`/schemas/pci/pci-host-bridge.yaml#`), applies direct property constraints, evaluates top-level `allOf` composition, and then applies conditional branches. Conditional behavior: for arm,juno-r1-pcie, adds/restricts `dma-coherent`; for cavium,pci-host-thunder-pem, hisilicon,hip06-pcie-ecam, hisilicon,hip07-pcie-ecam, adds/restricts property cardinalities/names. At runtime the compiled DTB has no code from this file; the kernel matches `compatible`, maps `reg` resources, programs PCI ranges, requests interrupts/MSI mappings, enables clocks/resets/regulators/PHYs/power domains, and creates host bridge/root-port or endpoint objects according to the described node.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability for board DTS files and shipped DTBs: compatible ordering, resource names, cell counts, interrupt maps, address ranges, and child-node layout become the long-lived contract that drivers and firmware rely on. For this file, the top-level and composed unknown-property policy is: unevaluatedProperties: false.

**Dependencies:** Direct schema dependencies are `/schemas/pci/pci-host-bridge.yaml#`. Resource dependencies visible in the binding include `compatible` (driver OF match key and binding ABI identifier); `reg` (MMIO/config/address-space resource tuples); `ranges` (PCI address translation windows exposed by the host bridge); `dma-coherent` (coherency attribute for DMA transactions); `iommu-map` (PCI requester-ID to IOMMU stream mapping); `msi-parent` (external MSI provider reference) The binding also depends on the broader Devicetree PCI schemas, dt-schema tooling, and matching Linux PCI host/endpoint drivers for the compatible strings above.

**Integration points:** Integrates with Linux OF platform matching through `compatible`, PCI core setup through `device_type`, `bus-range`, `ranges`, `dma-ranges`, `#address-cells`, and `#size-cells`, interrupt infrastructure through `interrupt-map`, `interrupts`, MSI controllers or `msi-map`, and SoC resource managers through clocks, resets, PHY, regulator, power-domain, and IOMMU properties. Nested integration surface: no nested child schema declared directly.

**Risks:** Main risks are ABI drift in required properties, accepting a DTS shape that the driver cannot probe, rejecting valid legacy boards, stale examples, wrong `reg-names`/`clock-names`/`reset-names` ordering, incomplete compatible coverage, and conditional branches whose `contains`/`enum` logic does not match real fallback-compatible ordering. PCI-specific risk is high around address translation and interrupts: bad `ranges`, `dma-ranges`, `iommu-map`, `msi-map`, or `interrupt-map-mask` can validate syntactically while producing unprobeable devices or broken DMA/MSI at runtime.

**Test signals:** Run `make dt_binding_check DT_SCHEMA_FILES=sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/pci/host-generic-pci.yaml` to validate this schema and its 1 inline example block(s). Run `make dtbs_check` for DTS users of each compatible string to exercise conditional branches, referenced schemas, child-node validation, closure policy, and resource-name ordering. Runtime smoke signals are successful PCI host bridge or endpoint probe, enumerated downstream devices/functions, working INTx/MSI/MSI-X, correct DMA/IOMMU mappings, and no missing-clock/reset/PHY/regulator errors in boot logs.
