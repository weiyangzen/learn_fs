# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/power/supply/tps65090-charger.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/power/supply/tps65090-charger.yaml` defines the Linux Devicetree YAML schema for `TPS65090 Frontend PMU with Switchmode Charger`, a charger or external-power-supply binding. It is declarative ABI documentation and validation input, not executable driver code. Its job is to keep DTS/DTB nodes aligned with the resources, child nodes, and electrical or timing constraints expected by the matching kernel subsystem before a driver probes hardware.

## Important APIs, Types, and Functions
The API surface is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `patternProperties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses a single `const` with 1 token: `ti,tps65090-charger`. Top-level properties are `compatible`, `ti,enable-low-current-chrg`. Top-level required properties are `compatible`; required properties collected from nested branches include `compatible`. Patterned child schemas are none. Numeric and collection constraints include no explicit numeric or item limits collected. Important resource roles: `compatible` is the stable hardware ABI and OF match key; `ti,enable-low-current-chrg` constrains electrical limits or measurement calibration. The highest-risk ABI details are charger compatible identity, input/charge current limits, voltage limits, power-path wiring, IRQ and GPIO semantics, battery references, and PMIC child-node placement.

## Control Flow
Control flow is dt-schema evaluation rather than imperative execution. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties` and `patternProperties`, evaluates `allOf`, checks required fields and min/max constraints, validates examples, and enforces the closure policy. At runtime this YAML does not execute: the compiled DTB node is matched through a kernel OF table or subsystem-specific child-node parser, then helpers for power-supply, regulator, PWM, PTP, PPS, PowerPC platform, clocks, resets, interrupts, GPIOs, pinctrl, power domains, and MFD parents consume the validated resources.

## State and Persistence Behavior
The file stores no mutable runtime state and writes no persistent data. Its persistence is ABI stability: compatible strings, required resource names, phandle/cell counts, child-node names, electrical limit properties, fallback ordering, and example layouts become long-lived contracts in DTS and DTB artifacts. Runtime state belongs to drivers and hardware after probe, including charger online/health/status state, input-current limiting, charge termination, watchdogs, USB/AC detection state, IRQ status, regulator enable state, and battery charging policy.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, power sequencing, clock setup, IRQ delivery, or consumer phandle resolution. Tightening required properties can reject existing board files; loosening them can hide missing supplies, clocks, resets, interrupts, current/voltage limits, PWM cell counts, PTP/PPS GPIOs, or regulator child constraints. This schema rejects unknown top-level properties with `additionalProperties: false`. It has 2 top-level properties and 2 distinct nested property names, so broad edits should be checked against all compatibles, examples, and in-tree DTS users rather than only the filename's nominal device.
