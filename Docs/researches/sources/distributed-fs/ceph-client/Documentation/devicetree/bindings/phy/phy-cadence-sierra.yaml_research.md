# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/phy/phy-cadence-sierra.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/phy/phy-cadence-sierra.yaml` is a Linux Devicetree YAML schema for `Cadence Sierra PHY`, a Linux PHY provider binding. This binding describes the Cadence Sierra PHY. Sierra PHY supports multilink multiprotocol combinations including protocols such as PCIe, USB etc. It is declarative firmware ABI documentation and dt-schema validation input, not executable kernel code. Its role is to make board DTS/DTB nodes describe PHY blocks, lanes, pads, ports, supplies, clocks, resets, and phandle provider contracts in the form the matching Linux PHY or controller driver expects.

**Important APIs/types/functions:** The exported API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `patternProperties`, local definitions, `required`, examples, and composition constraints. `compatible` uses `enum` list and covers 2 compatible tokens: `cdns,sierra-phy-t0`, `ti,sierra-phy-t0`. Top-level properties are `compatible`, `#address-cells`, `#size-cells`, `#clock-cells`, `resets`, `reset-names`, `reg`, `reg-names`, `clocks`, `clock-names`, `cdns,autoconf`. Top-level required properties are `compatible`, `#address-cells`, `#size-cells`, `reg`, `resets`, `reset-names`; required properties discovered across nested schemas include `#address-cells`, `#phy-cells`, `#size-cells`, `compatible`, `reg`, `reset-names`, `resets`. The binding acts as a parent provider with addressable child PHY/lane nodes. Provider/cell contracts are `#address-cells=const 1`, `#size-cells=const 0`, `#clock-cells=const 1`, `#phy-cells=const 0`. Important property roles: `compatible` selects the OF match table entry and stable hardware ABI; `#address-cells` enables addressable child PHY, lane, or port nodes; `#size-cells` enables addressable child PHY, lane, or port nodes; `resets` models reset controller lines; `reset-names` models reset controller lines; `reg` carries MMIO ranges, syscon offsets, port numbers, or bus addresses; `clocks` binds reference, pipe, APB, PLL, or tracking clocks; `clock-names` binds reference, pipe, APB, PLL, or tracking clocks. Patterned child schemas are `^phy@[0-9a-f]$`; nested topology or child names discovered from properties are `cdns,num-lanes`. Local reusable definitions are none. Numeric/item constraints include `minItems=1`, `maxItems=1`, `minItems=2`, `maxItems=4`, `minimum=0`, `maximum=15`, `minimum=1`, `maximum=16`; selected enum/const literals include `cdns,sierra-phy-t0`, `ti,sierra-phy-t0`, `1`, `0`, `sierra_reset`, `sierra_apb`, `serdes`, `cmn_refclk_dig_div`, `cmn_refclk1_dig_div`, `pll0_refclk`, `pll1_refclk`, `2`, `4`, `8`, `9`.

**Control flow:** Control flow is dt-schema evaluation. `dt_binding_check` parses the YAML, validates it against the core meta-schema, resolves `$ref` dependencies, applies `properties` and `patternProperties`, evaluates `allOf`/`oneOf`/`anyOf`/conditional branches, checks `required` lists and item counts, compiles examples, and enforces the closure rule. At boot the YAML is not interpreted; firmware supplies a compiled DTB node, the kernel matches `compatible` in the relevant OF table, and the PHY/provider driver reads `reg`, clocks, resets, supplies, child lanes/ports, and `#phy-cells` to register PHYs. Consumer controllers later resolve `phys` phandles and invoke the generic PHY framework for init, power-on, mode setting, calibration, and power-off.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence. Its durable state is ABI shape: compatible strings, property names, valid enum values, provider cell counts, child-node naming, lane or port numbering, and allowed topology. Runtime state such as PLL lock, link training, lane muxing, PHY mode, impedance tuning, analog calibration, reset sequencing, and power transitions lives in the matching kernel driver and hardware registers; this schema only constrains how those resources and modes are represented in firmware.

Direct schema dependencies are `/schemas/types.yaml#/definitions/uint32`. Top-level composition/conditional keys are none. Integration points are Devicetree common schemas, the Linux generic PHY framework, controller bindings that consume `phys`/`phy-names`, platform/MMIO or syscon buses, regulator supplies, reset controllers, clock providers, GPIO descriptors, power domains, and SoC-specific lane mux drivers. Compatible scan signals found driver-side files: `sources/distributed-fs/ceph-client/drivers/phy/cadence/phy-cadence-sierra.c`. In-tree DTS scan signals found board users: `sources/distributed-fs/ceph-client/arch/arm64/boot/dts/ti/k3-j721e-main.dtsi`. The file includes 1 example block for validation.

**Risks:** Primary risks are PHY ABI drift and resource lookup mismatch. Removing or reordering compatible fallbacks can break legacy DTBs; changing `#phy-cells`, child `reg` numbering, lane names, or port names can break consumers that already reference the provider; renaming clocks, resets, supplies, GPIOs, or power domains can break driver probe even when the hardware block is unchanged. Multi-protocol SerDes and pad-controller schemas are especially sensitive because lane mux enums, protocol names, and companion USB2/USB3 or PCIe/SATA relationships must align with driver tables and board wiring. The closure profile is: top-level unknown properties are rejected by `additionalProperties: false`. Because this schema has 11 top-level properties and 15 distinct nested property names, broad edits should be checked against every compatible variant, examples, and existing DTS users.

**Test signals:** Primary validation signals are `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/phy/phy-cadence-sierra.yaml` in a kernel tree with dt-schema installed and `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/phy/phy-cadence-sierra.yaml` for boards using these compatibles. Useful negative checks omit required clocks/resets/supplies, use invalid `#phy-cells`, bad child-node names, wrong lane `reg` values, or unsupported enum values. Runtime integration signals are successful driver probe, registered PHY providers with expected phandle arguments, consumers resolving `phys`, clocks and regulators balanced across suspend/resume, link bring-up for the relevant USB/PCIe/SATA/UFS/MIPI/SerDes protocol, and no new schema warnings for examples or in-tree DTS files.
