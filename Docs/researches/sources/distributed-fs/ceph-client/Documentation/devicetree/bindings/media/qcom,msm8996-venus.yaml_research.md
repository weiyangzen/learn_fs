# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/qcom,msm8996-venus.yaml

**Purpose:** Defines the Devicetree JSON-schema ABI for `Qualcomm MSM8996 Venus video encode and decode accelerators`. It is a Qualcomm Venus video encode/decode accelerator binding in the Ceph client Linux source snapshot, constraining how board DTS/DTB files describe media hardware so Linux media, V4L2 mem2mem, platform, clock, reset, power-domain, IOMMU, and graph helpers can bind the correct driver resources. The source description says: The Venus IP is a video encode and decode accelerator present on Qualcomm platforms

**Important APIs/types/functions:** This is declarative schema, so the exported API is the binding contract rather than C functions. Public surfaces include `$id` `http://devicetree.org/schemas/media/qcom,msm8996-venus.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, examples, and dt-schema references. The `compatible` property uses `enum` list and accepts `qcom,msm8996-venus`, `qcom,msm8998-venus`. Top-level required properties are `compatible`, `iommus`, `video-decoder`, `video-encoder`; required names across nested/conditional schemas include `clock-names`, `clocks`, `compatible`, `iommus`, `power-domains`, `video-decoder`, `video-encoder`. Top-level properties are `compatible`, `power-domains`, `clocks`, `clock-names`, `interconnects`, `interconnect-names`, `iommus`, `video-decoder`, `video-encoder`; all nested property names include `clock-names`, `clocks`, `compatible`, `interconnect-names`, `interconnects`, `iommus`, `power-domains`, `video-decoder`, `video-encoder`. Resource constraints visible in the schema include `compatible`, `power-domains` (maxItems=1), `clocks` (maxItems=4), `clock-names` (names=core/iface/bus/mbus), `interconnects` (maxItems=2), `interconnect-names` (names=video-mem/cpu-cfg), `iommus` (maxItems=20), `video-decoder`, `video-encoder`. Closure is `unevaluatedProperties: False`.

**Control flow:** Runtime control flow is supplied by dt-schema and kernel probing. `dt_binding_check` loads the core meta-schema, resolves references, validates the compatible form, applies required lists and `minItems`/`maxItems`/`const` restrictions, evaluates conditionals, and compiles the inline examples. At boot the DTB node is matched by `compatible`; the platform or media driver then reads MMIO ranges, named interrupts, clocks, resets, power domains, IOMMU streams, DMA/interconnect paths, firmware or reserved-memory phandles, and graph endpoints. Schema composition uses `allOf`. Validation can therefore change by compatible string, for example by tightening clock/reset counts, requiring SoC-specific helper phandles, or allowing/deprecating child codec nodes. This binding has no media graph endpoint surface; integration is by platform device resources and codec-specific child nodes.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence itself. Its persistent effect is ABI stability for DTS files and shipped DTBs: compatible strings, child-node names, phandle relationships, address ranges, cell counts, and media graph topology are long-lived hardware descriptions. Any change to required properties, resource ordering, child object schemas, or unknown-property policy can invalidate existing board descriptions even though no kernel state is written by the YAML.

**Dependencies and integration points:** Direct schema references are `qcom,venus-common.yaml#`. Runtime dependencies are IOMMU/SMMU stream mappings for video DMA, Linux interconnect bandwidth paths, genpd power domains, clock provider phandles and fixed clock-name ordering, shared `qcom,venus-common.yaml` base binding. Nested schema surfaces include `video-decoder`, `video-encoder`. These child nodes are part of the ABI, not driver-private data; their compatible values, required clocks, power domains, IOMMU entries, or codec-core markers must stay aligned with the driver. Maintainers listed in the binding are `Stanimir Varbanov <stanimir.varbanov@linaro.org>`.

**Risks:** Key risks: compatible-string or fallback-order drift can break OF matching and dtbs_check expectations; resource array ordering is ABI-sensitive for `reg-names`, `clock-names`, `interrupt-names`, `power-domain-names`, and `reset-names`; wrong IOMMU stream IDs can cause video DMA faults or silent memory corruption; missing interconnect or OPP constraints can produce bandwidth or power-collapse failures under high-resolution workloads; SoC-specific power-domain count differences are easy to regress in fallback compatibles; codec child-node deprecation, memory carveouts, and firmware/performance votes must remain compatible with existing DTS files. The closure policy is `unevaluatedProperties: False`, so unknown properties are intentionally rejected after referenced schemas are evaluated.
