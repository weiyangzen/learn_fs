# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/nvmem/layouts/kontron,sl28-vpd.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/nvmem/layouts/kontron,sl28-vpd.yaml` defines the Linux Devicetree YAML schema for `NVMEM layout of the Kontron SMARC-sAL28 vital product data`, a NVMEM layout binding. The schema description says: The vital product data (VPD) of the sl28 boards contains a serial number and a base MAC address. The actual MAC addresses for the on-board ethernet devices are derived from this base MAC address by adding an offset. It is declarative ABI documentation and validation input rather than executable kernel code; its practical role is to make DTS/DTB hardware descriptions match the resources, topology, and compatible strings expected by the relevant kernel subsystem before probe.

## Important APIs, Types, and Functions
The public API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses a single `const` and exposes 1 token: `kontron,sl28-vpd`. Top-level properties are `compatible`, `serial-number`, `base-mac-address`. Top-level required properties are `compatible`; required properties collected from nested schema branches include `compatible`. Patterned child schemas are none. Numeric and collection constraints include no explicit numeric or item limits collected. Important resource roles: `compatible` is the stable hardware ABI and OF match key. The highest-risk ABI details are layout compatible identity, child cell naming and offsets, `#address-cells`/`#size-cells`, parser-specific TLV or environment format constraints, and consumer-visible cell names.

## Control Flow
Runtime control flow is supplied by dt-schema and kernel subsystem code, not by this YAML file. `dt_binding_check` loads the meta-schema, resolves `$ref` entries, applies `properties`, evaluates no top-level conditionals, checks required fields, validates `minItems`/`maxItems` and enum/const constraints, validates embedded examples, and applies the closure rule. During boot, the compiled DTB node is matched by `compatible`; then platform, PCI, SDIO, SPI, MDIO, NVMEM, OPP, PCIe, netdev, wireless, accelerator, storage, clock, reset, regulator, IRQ, GPIO, IOMMU, and power-domain helpers consume the phandles and resource arrays that this schema validates. Child nodes are discovered declaratively through fixed names, pattern properties, address cells, and referenced child schemas.

## State and Persistence Behavior
The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: compatible strings, required resource names, register and interrupt ordering, phandle and cell counts, child-node names, fallback ordering, and example layouts become long-lived contracts in board DTS files and shipped DTBs. Runtime state belongs to the matching drivers and hardware after probe, including parsed cell inventory, decoded manufacturing data, MAC/serial/board identity lookup, and provider-backed read caching as implemented by the NVMEM core.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, link training, calibration lookup, OPP selection, NVMEM cell reads, or bus enumeration. Tightening required properties can reject existing boards; loosening them can hide missing clocks, resets, interrupts, supplies, PHY links, PCIe windows, memory regions, OPP fields, or NVMEM cells. Child-node schemas need special care because address cells, port IDs, PCI interrupt maps, wireless calibration cells, NVMEM layouts, and OPP tables must match driver-side assumptions. This schema rejects unknown top-level properties with `additionalProperties: false`. It has 3 top-level properties and 4 distinct nested property names, so broad edits should be checked against all compatible variants and DTS users, not just the nominal filename.

## Test Signals
Run `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/nvmem/layouts/kontron,sl28-vpd.yaml` for targeted schema validation and `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/nvmem/layouts/kontron,sl28-vpd.yaml` against boards using these nodes. High-value negative checks remove required properties, use invalid compatible fallbacks, corrupt `reg` or interrupt counts, misspell vendor properties, violate child-node address-cell rules, and exercise every conditional branch. Runtime integration signals are successful driver probe, correct subsystem registration, valid NVMEM/OPP/PCIe/wireless/netdev/accelerator/storage behavior as applicable, clean interrupt/reset/power sequencing, and no new dtbs_check failures in embedded examples or in-tree DTS users.
