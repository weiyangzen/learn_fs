# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/extcon/siliconmitus,sm5502-muic.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `SM5502/SM5504 MUIC (Micro-USB Interface Controller) device`. In this tree it is a external connector binding used by extcon, USB Type-C, MUIC, and cable-detection drivers; it constrains how board DTS files describe the hardware and how Linux drivers discover it through OF matching, phandles, and common binding references. The source description says: The Silicon Mitus SM5502 is a MUIC (Micro-USB Interface Controller) device which can detect the state of external accessory when external accessory is attached or detached and button is pressed or released. It is interfaced to the host controller using an I2C interface.

**Important APIs/types/functions:** This is declarative schema rather than executable code. The public ABI surface is `$id` `http://devicetree.org/schemas/extcon/siliconmitus,sm5502-muic.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and the referenced schemas used by dt-schema. Compatible strings are `siliconmitus,sm5502-muic`, `siliconmitus,sm5504-muic`, `siliconmitus,sm5703-muic`. Required properties are `compatible`, `reg`, `interrupts`. Important properties include `compatible`, `reg`, `connector`, `interrupts`. Referenced schemas are `/schemas/connector/usb-connector.yaml#`. Property roles include `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address; `connector` for USB connector child schema integration; `interrupts` for interrupt line routing. The top-level closure rule is `additionalProperties: false`. Maintainers: Chanwoo Choi <cw00.choi@samsung.com>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel subsystems, not by this YAML file. `dt_binding_check` loads the core meta-schema, resolves references such as `/schemas/connector/usb-connector.yaml#`, applies `properties`, `required`, enum/const/items limits, and any `allOf` or conditional branches, then validates the inline examples. During boot, a matching DT node is compiled into the DTB, the kernel matches `compatible`, subsystem code reads cells and phandles, and the bound driver consumes resources such as USB connector child nodes. It has no nested conditional schema branches beyond direct property validation. Nested or patterned child schema surfaces include `connector`.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, resource topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though no kernel state is stored here.

**Dependencies and integration points:** Integrated with extcon, USB, Type-C connector, MUIC, I2C, GPIO, interrupt, and OF graph code. Direct schema dependencies are `/schemas/connector/usb-connector.yaml#`; resource dependencies visible in the property set include USB connector child nodes. Driver integration is through `compatible`, while client/provider integration is through cell properties, phandle arrays, child schemas, and bus-standard properties declared or inherited here.

**Risks:** Main risks are schema ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, missing required clocks/resets/interrupts/power domains, stale examples, and conditional branches that accept one SoC variant while rejecting another valid one. Unknown-property policy also matters: `additionalProperties: false` can either catch misspelled DTS properties or allow legacy extension points. For bindings with child nodes or graph/connector references, parent-child address-cell and port layout mistakes can pass driver review only if dtbs_check coverage is weak.
