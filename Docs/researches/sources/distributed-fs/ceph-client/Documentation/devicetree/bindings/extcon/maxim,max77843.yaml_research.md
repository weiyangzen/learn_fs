# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/extcon/maxim,max77843.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Maxim MAX77843 MicroUSB and Companion Power Management IC Extcon`. In this tree it is a external connector binding used by extcon, USB Type-C, MUIC, and cable-detection drivers; it constrains how board DTS files describe the hardware and how Linux drivers discover it through OF matching, phandles, and common binding references. The source description says: This is a part of device tree bindings for Maxim MAX77843 MicroUSB Integrated Circuit (MUIC). See also Documentation/devicetree/bindings/mfd/maxim,max77843.yaml for additional information and example.

**Important APIs/types/functions:** This is declarative schema rather than executable code. The public ABI surface is `$id` `http://devicetree.org/schemas/extcon/maxim,max77843.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and the referenced schemas used by dt-schema. Compatible strings are `maxim,max77843-muic`. Required properties are `compatible`, `connector`. Important properties include `compatible`, `connector`, `ports`. Referenced schemas are `/schemas/connector/usb-connector.yaml#`, `/schemas/graph.yaml#/properties/ports`, `/schemas/graph.yaml#/properties/port`. Property roles include `compatible` for driver match key and hardware ABI identifier; `connector` for USB connector child schema integration; `ports` for OF graph multi-port integration. The top-level closure rule is `additionalProperties: false`. Maintainers: Chanwoo Choi <cw00.choi@samsung.com>, Krzysztof Kozlowski <krzk@kernel.org>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel subsystems, not by this YAML file. `dt_binding_check` loads the core meta-schema, resolves references such as `/schemas/connector/usb-connector.yaml#`, `/schemas/graph.yaml#/properties/ports`, `/schemas/graph.yaml#/properties/port`, applies `properties`, `required`, enum/const/items limits, and any `allOf` or conditional branches, then validates the inline examples. During boot, a matching DT node is compiled into the DTB, the kernel matches `compatible`, subsystem code reads cells and phandles, and the bound driver consumes resources such as USB connector child nodes, OF graph ports. It has no nested conditional schema branches beyond direct property validation. Nested or patterned child schema surfaces include `connector`, `ports`.

**State and persistence behavior:** The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, resource topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though no kernel state is stored here.

**Dependencies and integration points:** Integrated with extcon, USB, Type-C connector, MUIC, I2C, GPIO, interrupt, and OF graph code. Direct schema dependencies are `/schemas/connector/usb-connector.yaml#`, `/schemas/graph.yaml#/properties/ports`, `/schemas/graph.yaml#/properties/port`; resource dependencies visible in the property set include USB connector child nodes, OF graph ports. Driver integration is through `compatible`, while client/provider integration is through cell properties, phandle arrays, child schemas, and bus-standard properties declared or inherited here.

**Risks:** Main risks are schema ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, missing required clocks/resets/interrupts/power domains, stale examples, and conditional branches that accept one SoC variant while rejecting another valid one. Unknown-property policy also matters: `additionalProperties: false` can either catch misspelled DTS properties or allow legacy extension points. For bindings with child nodes or graph/connector references, parent-child address-cell and port layout mistakes can pass driver review only if dtbs_check coverage is weak.
