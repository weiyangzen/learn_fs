# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/phy/nvidia,tegra194-xusb-padctl.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/phy/nvidia,tegra194-xusb-padctl.yaml` is a Linux Devicetree YAML schema for `NVIDIA Tegra194 XUSB pad controller`, a XUSB pad controller / multi-lane PHY provider binding. The Tegra XUSB pad controller manages a set of I/O lanes (with differential signals) which connect directly to pins/pads on the SoC package. Each lane is controlled by a HW block referred to as a "pad" in the Tegra hardware documentation. Each such "pad" may control either one or multiple lanes, and thus contains any logic common to all its lanes. Each lane can be separately configured and powered up. Some of the lanes are high-speed lanes, which can be used for PCIe, SATA or super-speed USB. Other lanes are for various types of low-speed, full-speed or high-speed USB (such as UTMI, ULPI and HSIC). It is declarative firmware ABI documentation and dt-schema validation input, not executable kernel code. Its role is to make board DTS/DTB nodes describe PHY blocks, lanes, pads, ports, supplies, clocks, resets, and phandle provider contracts in the form the matching Linux PHY or controller driver expects.

**Control flow:** Control flow is dt-schema evaluation. `dt_binding_check` parses the YAML, validates it against the core meta-schema, resolves `$ref` dependencies, applies `properties` and `patternProperties`, evaluates `allOf`/`oneOf`/`anyOf`/conditional branches, checks `required` lists and item counts, compiles examples, and enforces the closure rule. At boot the YAML is not interpreted; firmware supplies a compiled DTB node, the kernel matches `compatible` in the relevant OF table, and the PHY/provider driver reads `reg`, clocks, resets, supplies, child lanes/ports, and `#phy-cells` to register PHYs. Consumer controllers later resolve `phys` phandles and invoke the generic PHY framework for init, power-on, mode setting, calibration, and power-off.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence. Its durable state is ABI shape: compatible strings, property names, valid enum values, provider cell counts, child-node naming, lane or port numbering, and allowed topology. Runtime state such as PLL lock, link training, lane muxing, PHY mode, impedance tuning, analog calibration, reset sequencing, and power transitions lives in the matching kernel driver and hardware registers; this schema only constrains how those resources and modes are represented in firmware.

**Risks:** Primary risks are PHY ABI drift and resource lookup mismatch. Removing or reordering compatible fallbacks can break legacy DTBs; changing `#phy-cells`, child `reg` numbering, lane names, or port names can break consumers that already reference the provider; renaming clocks, resets, supplies, GPIOs, or power domains can break driver probe even when the hardware block is unchanged. Multi-protocol SerDes and pad-controller schemas are especially sensitive because lane mux enums, protocol names, and companion USB2/USB3 or PCIe/SATA relationships must align with driver tables and board wiring. The closure profile is: top-level unknown properties are rejected by `additionalProperties: false`. Because this schema has 10 top-level properties and 33 distinct nested property names, broad edits should be checked against every compatible variant, examples, and existing DTS users.
