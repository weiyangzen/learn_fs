# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/iommu/arm,smmu.yaml

**Purpose:** Defines the Linux Devicetree JSON-schema contract for `ARM System MMU Architecture Implementation`. In this source tree it is a IOMMU provider or IOMMU-adjacent binding; it constrains board DTS/DTB nodes so kernel OF matching and subsystem code can discover the hardware resources consistently. This is declarative ABI documentation, not executable Ceph client code, but it is part of the imported kernel documentation corpus that protects hardware-description compatibility. The source description says: ARM SoCs may contain an implementation of the ARM System Memory Management Unit Architecture, which can be used to provide 1 or 2 stages of address translation to bus masters external to the CPU. The SMMU may also raise interrupts in response to various fault conditions.

**Important APIs/types/functions:** The public surface is the schema itself: `$id` `http://devicetree.org/schemas/iommu/arm,smmu.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, composition keywords, closure rules, and `examples` consumed by `dt-schema`. Compatible strings are `qcom,msm8996-smmu-v2`, `qcom,msm8998-smmu-v2`, `qcom,sdm630-smmu-v2`, `qcom,sm6375-smmu-v2`, `qcom,smmu-v2`, `qcom,eliza-smmu-500`, `qcom,glymur-smmu-500`, `qcom,kaanapali-smmu-500`, `qcom,milos-smmu-500`, `qcom,qcm2290-smmu-500`, `qcom,qcs615-smmu-500`, `qcom,qcs8300-smmu-500`, `qcom,qdu1000-smmu-500`, `qcom,sa8255p-smmu-500`, `qcom,sa8775p-smmu-500`, `qcom,sar2130p-smmu-500`, `qcom,sc7180-smmu-500`, `qcom,sc7280-smmu-500`, and 38 more. Required properties are `compatible`, `reg`, `#global-interrupts`, `#iommu-cells`, `interrupts`. Important top-level properties include `$nodename`, `compatible`, `reg`, `#global-interrupts`, `#iommu-cells`, `interrupts`, `dma-coherent`, `calxeda,smmu-secure-config-access`, `stream-match-mask`, `clock-names`, `clocks`, `power-domains`, `nvidia,memory-controller`. Patterned or child-node surfaces include none declared. Direct schema references are `/schemas/types.yaml#/definitions/phandle`, `/schemas/types.yaml#/definitions/uint32`. Maintainers: Will Deacon <will@kernel.org>, Robin Murphy <Robin.Murphy@arm.com>. Top-level property policy is `additionalProperties: false`.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel drivers rather than by this YAML. `dt_binding_check` loads the core meta-schema, resolves `$ref` dependencies, applies constants/enums/cardinality/range checks, evaluates composition and conditional branches (`oneOf`, `allOf`, `if`, `then`, `else`, `anyOf`), and validates the embedded examples. At boot, the compiled DTB node is matched by `compatible`; the relevant IOMMU driver or common subsystem reads resource properties, phandles, child nodes, and cells before registering devices or provider relationships. Child/provider surfaces to watch here are none declared.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistence is ABI persistence: accepted DTS nodes encode hardware identity, register windows, interrupts, power/clock/reset topology, phandle cell widths, channel indexes, and child LED/IOMMU/IPMI layout for long-lived boards. Tightening `required`, changing compatible fallback order, altering cell counts, or changing closure policy can reject existing DTBs or make drivers parse resources differently.

**Dependencies and integration points:** Integrated with IOMMU stream IDs, DMA translation, device isolation, and `iommus`/`#iommu-cells` style phandle integration. Schema dependencies include `/schemas/types.yaml#/definitions/phandle`, `/schemas/types.yaml#/definitions/uint32`; examples may also include dt-bindings headers. Resource integration is through properties such as `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address; `interrupts` for interrupt routing; `clocks` for clock provider phandles; `clock-names` for named clock inputs; `power-domains` for genpd power-domain attachment; `#iommu-cells` for IOMMU client specifier cell count. Driver integration is through `compatible`, while subsystem integration is through phandle arrays, provider cell counts, common schemas, and child-node schemas inherited or declared here.

**Risks and edge cases:** Main risks are schema ABI drift, missing or stale compatible coverage, incorrect min/max item constraints, wrong `#*-cells` values, resource names that diverge from driver expectations, conditionals that validate one SoC or chip variant while rejecting another valid one, and examples that no longer reflect real DTS users. Closure policy (`additionalProperties: false`) is useful for catching misspellings but can also block legitimate extensions. For LED/backlight children, channel numbering and `reg`/`led-sources` constraints are common failure points; for IOMMU bindings, stream IDs and cell widths are especially sensitive; for IPMI bindings, host/BMC address and register-resource shape must match the driver.

**Test signals:** Run `make dt_binding_check DT_SCHEMA_FILES=sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/iommu/arm,smmu.yaml` and `make dtbs_check` against DTS files using every compatible listed here. The 2 embedded example block(s) should compile through `dtc` and validate against referenced schemas. Useful negative tests remove each required property, add an unknown property under the declared closure policy, exercise compatible-specific conditionals, and verify the matching Linux driver still probes with the resources, child nodes, and phandle specifiers described by this binding.
