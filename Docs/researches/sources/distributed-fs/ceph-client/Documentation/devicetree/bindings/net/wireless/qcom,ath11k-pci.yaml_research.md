# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/net/wireless/qcom,ath11k-pci.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/net/wireless/qcom,ath11k-pci.yaml` defines the Linux Devicetree YAML schema for `Qualcomm Technologies ath11k wireless devices (PCIe)`, a wireless controller binding. The schema description says: Qualcomm Technologies IEEE 802.11ax PCIe devices It is declarative ABI documentation and validation input rather than executable kernel code; its practical role is to make DTS/DTB hardware descriptions match the resources, topology, and compatible strings expected by the relevant kernel subsystem before probe.

## Important APIs, Types, and Functions
The public API is the schema contract: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and referenced common schemas. `compatible` uses an `enum` and exposes 2 tokens: `pci17cb,1101`, `pci17cb,1103`. Top-level properties are `compatible`, `reg`, `qcom,calibration-variant`, `qcom,ath11k-calibration-variant`, `firmware-name`, `vddrfacmn-supply`, `vddaon-supply`, `vddwlcx-supply`, `vddwlmx-supply`, `vddrfa0p8-supply`, `vddrfa1p2-supply`, `vddrfa1p7-supply`, `vddrfa1p8-supply`, `vddpcie0p9-supply`, `vddpcie1p8-supply`. ## Control Flow
Runtime control flow is supplied by dt-schema and kernel subsystem code, not by this YAML file. `dt_binding_check` loads the meta-schema, resolves `$ref` entries, applies `properties`, evaluates `allOf`, checks required fields, validates `minItems`/`maxItems` and enum/const constraints, validates embedded examples, and applies the closure rule. During boot, the compiled DTB node is matched by `compatible`; then platform, PCI, SDIO, SPI, MDIO, NVMEM, OPP, PCIe, netdev, wireless, accelerator, storage, clock, reset, regulator, IRQ, GPIO, IOMMU, and power-domain helpers consume the phandles and resource arrays that this schema validates. Child nodes are discovered declaratively through fixed names, pattern properties, address cells, and referenced child schemas.

## State and Persistence Behavior
The schema owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: compatible strings, required resource names, register and interrupt ordering, phandle and cell counts, child-node names, fallback ordering, and example layouts become long-lived contracts in board DTS files and shipped DTBs. Runtime state belongs to the matching drivers and hardware after probe, including wireless device probe, firmware boot, regulatory/channel capability selection, calibration selection, IRQ/wake state, netdev/wiphy registration, and runtime PM.

## Risks
Primary risks are Devicetree ABI drift, incomplete compatible coverage, wrong fallback ordering, and resource-shape changes that still compile but break driver probe, link training, calibration lookup, OPP selection, NVMEM cell reads, or bus enumeration. Tightening required properties can reject existing boards; loosening them can hide missing clocks, resets, interrupts, supplies, PHY links, PCIe windows, memory regions, OPP fields, or NVMEM cells. Child-node schemas need special care because address cells, port IDs, PCI interrupt maps, wireless calibration cells, NVMEM layouts, and OPP tables must match driver-side assumptions. This schema rejects unknown top-level properties with `additionalProperties: false`. It has 15 top-level properties and 15 distinct nested property names, so broad edits should be checked against all compatible variants and DTS users, not just the nominal filename.
