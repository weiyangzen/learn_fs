# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/spi/st,stm32-spi.yaml

**Purpose:** Defines the JSON-schema contract for `STMicroelectronics STM32 SPI Controller` as an SPI bus/controller Devicetree binding. It constrains DTS/DTB ABI shape for STM32 SPI controller instances, including compatible strings, register resources, clock/reset/interrupt wiring, optional DMA paths, SRAM staging support, and access-control/power-domain integration. Source description: the STM32 SPI controller communicates with external devices over SPI and supports full-duplex, half-duplex, and simplex synchronous serial communication with 4- to 32-bit data sizes.

**Important APIs/types/functions:** This file is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/spi/st,stm32-spi.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `description`, `maintainers`, `allOf`, `properties`, `required`, and referenced common bindings. Compatible strings are `st,stm32f4-spi`, `st,stm32f7-spi`, `st,stm32h7-spi`, and `st,stm32mp25-spi`. Required top-level properties are `compatible`, `reg`, `clocks`, and `interrupts`. Important properties are `reg`, `clocks`, `interrupts`, `resets`, `dmas`, `dma-names`, `sram`, `power-domains`, and `access-controllers`, plus SPI bus properties inherited from `spi-controller.yaml#` such as child nodes, chip selects, and bus mode flags. Direct `$ref` dependencies are `spi-controller.yaml#` and `/schemas/types.yaml#/definitions/phandle`. Property roles include `compatible` for OF driver matching, `reg` for the controller MMIO window, `clocks` for register and transfer timing, `interrupts` for controller IRQ delivery, `resets` for hardware initialization, `dmas`/`dma-names` for RX/TX and optional RX memory-to-memory offload, `sram` for temporary DMA/MDMA storage, and `access-controllers`/`power-domains` for platform security and power integration. Top-level closure policy is `unevaluatedProperties: false`. Maintainers are `Erwan Leray <erwan.leray@foss.st.com>` and `Fabrice Gasnier <fabrice.gasnier@foss.st.com>`. The source was read as 133 lines / 3035 bytes.

**Control flow:** Control flow is supplied by dt-schema tooling and by the Linux SPI subsystem that consumes the resulting DTB. `dt_binding_check` resolves `spi-controller.yaml#`, applies the STM32-specific property constraints, validates required resources, and evaluates the `allOf` conditionals. For `st,stm32f4-spi`, the schema forbids `st,spi-midi-ns` and `sram`, and limits DMA to RX/TX channels named `rx` and `tx`. For `st,stm32mp25-spi`, it also forbids `sram` and limits DMA to RX/TX. Other variants may expose a third `rxm2m` DMA channel and the `sram` phandle used as temporary staging storage. At boot, the SPI driver matches `compatible`, maps `reg`, enables clocks and optional reset/power/security resources, configures IRQ and DMA channels, and registers a SPI controller whose child nodes are created using inherited SPI-controller bus rules.

**State and persistence behavior:** The YAML owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: board DTS files and compiled DTBs record the STM32 SPI variant, MMIO window, interrupt, clock, reset, DMA, SRAM, and child-device layout expected by the kernel. Tightening DMA item counts, changing compatible membership, forbidding or requiring `sram`, or altering inherited SPI child-node semantics can break old board descriptions even though the schema itself has no runtime storage.

**Dependencies and integration points:** Integration is with the generic SPI controller binding, the Linux STM32 SPI driver, common clock/reset/interrupt/DMA frameworks, optional SRAM partitions described by `Documentation/devicetree/bindings/sram/sram.yaml`, power domains, and access-controller policy. Child SPI peripherals depend on inherited SPI bus semantics such as `#address-cells`, `#size-cells`, child `reg` chip-select values, `cs-gpios`, `spi-max-frequency`, and mode flags. The schema-level dependencies are the core Devicetree meta-schema, `spi-controller.yaml#`, and `/schemas/types.yaml#/definitions/phandle`.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, stale examples, wrong required-property sets, and overly broad or strict variant conditionals. STM32-specific risks include accepting an invalid three-channel DMA layout for variants that only support RX/TX, rejecting the SRAM staging phandle on variants that need RX memory-to-memory offload, mismatched `dma-names`, missing reset or power-domain data on platforms that need it, and inherited SPI chip-select polarity mistakes that validate but produce broken transfers. Because the file closes unevaluated properties, adding new platform integration properties requires deliberate schema updates.

Runtime signals include successful STM32 SPI probe, clock/reset acquisition, IRQ registration, PIO and DMA transfer tests, chip-select polarity checks, and read/write smoke tests against attached SPI peripherals.
