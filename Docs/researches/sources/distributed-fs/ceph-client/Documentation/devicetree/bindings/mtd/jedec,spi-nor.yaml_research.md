# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/mtd/jedec,spi-nor.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `SPI NOR flash ST M25Pxx (and similar) serial flash chips`. In this tree it is a MTD flash memory controller, flash chip, ECC engine, or common flash schema binding: it constrains how DTS authors describe hardware, and it gives Linux OF/platform code a stable ABI for matching drivers, acquiring resources, and validating board descriptions with dt-schema.

**Important APIs/types/functions:** This is declarative schema, not executable C code. The public interface is the binding ABI exposed through `$id` `http://devicetree.org/schemas/mtd/jedec,spi-nor.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `description`, `maintainers`, `properties`, `required`, schema composition keywords, and inline `examples`. Compatible strings or match identifiers include `jedec,spi-nor`, `issi,is25lp016d`, `micron,mt25qu02g`, `mxicy,mx25r1635f`, `mxicy,mx25u6435f`, `mxicy,mx25v8035f`, `spansion,s25sl12801`, `spansion,s25fs512s`. Top-level required properties are none at the top level. Important properties include `compatible`, `reg`, `interrupts`, `m25p,fast-read`, `broken-flash-reset`, `no-wp`, `reset-gpios`, `vcc-supply`, `spi-cpol`, `spi-cpha`. Property roles include `compatible`: driver match key and stable hardware ABI identifier; `reg`: MMIO, bus address, flash-chip select, or child register window; `interrupts`: interrupt line routing; `m25p,fast-read`: Use the "fast read" opcode to read data from the chip instead of the usual "read" opcode. This opcode is not supported by all chips and support for it can not be detected at runtime. Refer to your chips' datasheet to check if this is supported by your chip.; `broken-flash-reset`: Some flash devices utilize stateful addressing modes (e.g., for 32-bit addressing) which need to be managed carefully by a system. Because these sorts of flash don't have a standardized software reset command, and because some systems don't toggle the flash RESET# pin upon system reset (if the pin even exists at all), there are systems which cannot reboot properly if the flash is left in the "wrong" state. This boole; `no-wp`: The status register write disable (SRWD) bit in status register, combined with the WP# signal, provides hardware data protection for the device. When the SRWD bit is set to 1, and the WP# signal is either driven LOW or hard strapped to LOW, the status register nonvolatile bits become read-only and the WRITE STATUS REGISTER operation will not execute. The only way to exit this hardware-protected mode is to drive WP# H; `reset-gpios`: A GPIO line connected to the RESET (active low) signal of the device. If "broken-flash-reset" is present then having this property does not make any difference.; `vcc-supply`: Supply for the SPI NOR power.. Direct or nested schema references include `mtd.yaml#`, `/schemas/spi/spi-peripheral-props.yaml#`. The top-level closure policy is `unevaluatedProperties: false`. Maintainers: Rob Herring <robh@kernel.org>.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and Linux subsystem drivers. `dt_binding_check` loads the core meta-schema, resolves references, evaluates `properties`, `required`, enum/const/items limits, and composition rules, then validates the examples. `dtbs_check` applies the same contract to compiled board DTBs. At boot, the flattened DT node is matched through `compatible` or inherited child-node context, the relevant driver parses resources such as MMIO ranges, interrupts, clocks, resets, regulators, PHYs, muxes, ECC engines, partitions, or child buses, and subsystem helpers enforce the generic parts of the contract. Schema composition/control branches in this file: allOf=1, oneOf=1. Nested schema surface: no nested child-node schemas detected at the top level.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: accepted DTS/DTB nodes encode hardware identity, resource topology, child-node layout, and phandle cell widths for long-lived boards. Tightening `required`, changing compatible ordering, changing cell counts, or altering `additionalProperties`/`unevaluatedProperties` can break existing DTBs even though no state is stored by the YAML itself.

**Dependencies and integration points:** Integrates with MTD core, raw NAND/SPI-NOR/SPI-NAND/OneNAND/physmap drivers, ECC-engine providers, partition parsers, and nvmem/UBI consumers. Devicetree/dt-schema dependencies are the core meta-schema plus `mtd.yaml#`, `/schemas/spi/spi-peripheral-props.yaml#`. Driver integration is through OF match tables and subsystem parsers; board integration is through phandles, address/size cells, interrupts, clocks, resets, regulators, power domains, child flash/partition nodes, MDIO/PHY links, mux specifiers, and examples that document expected DTS shape.

**Risks:** Main risks are ABI drift, under-specified compatibles, required resources that do not match real SoC integration, wrong `#*-cells` counts, stale examples, and conditional branches that validate one variant while rejecting another valid one. For storage bindings, partition/ECC/timing mistakes can silently corrupt flash or make media unprobeable. For network bindings, PHY mode, MDIO, reset, MAC-address, or clock mistakes can leave links down. For mux and common schemas, over-permissive closure can hide misspelled properties while over-tight closure can reject legitimate inherited properties.
