# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/iio/dac/adi,ltc2664.yaml

**Purpose:** `sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/iio/dac/adi,ltc2664.yaml` is a Linux Devicetree YAML schema for `Analog Devices LTC2664 DAC`, a IIO digital-to-analog converter binding. Analog Devices LTC2664 4 channel, 12-/16-Bit, +-10V DAC https://www.analog.com/media/en/technical-documentation/data-sheets/2664fa.pdf It is declarative ABI documentation and validation input, not executable driver code. Its main job is to make board DTS nodes describe IIO hardware, IIO providers, or IIO consumers with the resources the matching kernel driver expects.

**Important APIs/types/functions:** The public API surface is the schema itself: `$id`, `$schema`, `title`, `maintainers`, `properties`, `required`, composition keys, examples, and the accepted child-node patterns. `compatible` uses `enum` list and covers 1 compatible token: `adi,ltc2664`. Top-level properties are `compatible`, `reg`, `spi-max-frequency`, `vcc-supply`, `v-pos-supply`, `v-neg-supply`, `iovcc-supply`, `ref-supply`, `reset-gpios`, `adi,manual-span-operation-config`, `io-channels`, `#address-cells`, `#size-cells`. Top-level required properties are `compatible`, `reg`, `spi-max-frequency`, `vcc-supply`, `iovcc-supply`, `v-pos-supply`, `v-neg-supply`; required properties found across nested schemas include `compatible`, `iovcc-supply`, `reg`, `spi-max-frequency`, `v-neg-supply`, `v-pos-supply`, `vcc-supply`. The binding acts as a SPI child device. Important roles: `compatible` selects the OF match table entry and stable hardware ABI; `reg` carries the bus chip-select/address or MMIO range; `vcc-supply` links the device to regulator framework supplies; `v-pos-supply` links the device to regulator framework supplies; `v-neg-supply` links the device to regulator framework supplies; `iovcc-supply` links the device to regulator framework supplies; `ref-supply` links the device to regulator framework supplies; `reset-gpios` controls hardware reset sequencing; `io-channels` connects provider/consumer IIO channels; `#address-cells` enables validated child channel nodes; `#size-cells` enables validated child channel nodes. Patterned child schemas are `^channel@[0-3]$`; named child-channel properties discovered in nested schemas are no explicit named channel child nodes. Numeric/item constraints include no explicit numeric min/max/item limits collected.

**Control flow:** Control flow is dt-schema evaluation. `dt_binding_check` loads the core meta-schema, resolves every `$ref`, applies the top-level and nested `properties`, evaluates `allOf`/`oneOf`/conditionals, checks required fields, validates examples, and enforces the closure policy. At boot there is no YAML execution: the compiled DTB node is matched through the driver's OF table, then IIO, regulator, clock, GPIO, IRQ, SPI/I2C/platform, DMA, and firmware helpers consume the resources named by this contract. For schemas with `channel@N` or patterned child nodes, parent address/size cells control how per-channel configuration is discovered by the driver.

**State and persistence behavior:** The file owns no mutable runtime state and persists no data. Its persistent behavior is ABI stability: accepted compatible strings, required resource names, channel indices, phandle cell counts, child-node names, and example layouts become long-lived contracts for DTS/DTB producers. Runtime state such as ADC samples, DAC output values, buffer enablement, calibration, oversampling, alarms, or data-ready interrupts belongs to the corresponding IIO driver and hardware; this schema only constrains how that stateful device is described.

**Risks:** Risks center on Devicetree ABI drift. Changing compatible values or fallback ordering can break driver matching; renaming supplies, clocks, interrupts, GPIOs, or `#io-channel-cells` breaks probe-time resource lookup; tightening required properties or child-node patterns can reject existing boards. Channel-indexed schemas need care because driver channel tables, allowed `reg` values, and analog pin functions must stay aligned. The closure profile is: composition is closed by `unevaluatedProperties: false`. Because this file contains 13 top-level properties and 15 distinct nested property names, broad cleanups should be checked against examples, all compatible variants, and in-tree DTS users rather than only the nominal device named in the filename.

**Test signals:** Primary validation signals are `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/iio/dac/adi,ltc2664.yaml` and `make dtbs_check` for boards instantiating each compatible. High-value negative tests remove required supplies/clocks/IRQs, use bad channel `reg` values, misspell vendor properties, and exercise every conditional compatible branch. Runtime integration is indicated by successful driver probe with regulators and clocks enabled, correct IIO channel registration, valid `io-channels` consumers, data-ready IRQ behavior where modeled, buffered capture or DAC output where relevant, and no dtbs_check regressions for existing DTS examples.
