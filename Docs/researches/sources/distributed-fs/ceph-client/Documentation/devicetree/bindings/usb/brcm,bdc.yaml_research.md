# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/usb/brcm,bdc.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/usb/brcm,bdc.yaml` defines `Broadcom USB Device Controller (BDC)`, a USB peripheral/support binding. It is declarative firmware ABI documentation and dt-schema validation input; Linux does not execute this YAML at runtime, but the schema controls which DTS nodes are accepted for the corresponding hardware or bus-attached device.

## Important APIs, Types, and Functions
The exported API is the Devicetree node contract. `$id` is `http://devicetree.org/schemas/usb/brcm,bdc.yaml#` and `$schema` is `http://devicetree.org/meta-schemas/core.yaml#`. `compatible` uses ordered fallback `items` sequence and exposes 2 compatible tokens: `brcm,bdc-udc-v2`, `brcm,bdc`. Top-level properties are `compatible`, `reg`, `interrupts`, `phys`, `clocks`. Top-level required properties are `compatible`, `reg`, `interrupts`; required properties discovered in nested branches are `compatible`, `interrupts`, `reg`. Patterned child schemas are none; local definitions are none. Resource/provider roles: `compatible` selects schema applicability and the kernel OF match-table entry; `reg` describes MMIO windows, bus addresses, or register resources; `interrupts` maps controller, GPIO, or Type-C events into IRQ domains; `phys` connects USB/UFS controllers to PHY providers or exposes a PHY provider; `clocks` integrates with the clock framework. Across the full schema there are 5 distinct property names and collected const/enum/min/max/item signals include `enum=[brcm,bdc-udc-v2, brcm,bdc]`, `maxItems=1`, `minItems=1`.

## Control Flow
Control flow is schema evaluation. `dt_binding_check` parses the YAML, validates the meta-schema, resolves `$ref` links, applies `properties`, `patternProperties`, required lists, item counts, const/enum checks, and composition or conditional blocks (none); it also compiles the embedded examples. `dtbs_check` applies the same rules to compiled board DTBs. During boot the kernel only consumes the DTB: OF matching selects the driver, platform/bus code maps resources, phandles are resolved, and the driver performs hardware setup.

## State and Persistence Behavior
The file has no mutable runtime state and performs no persistence. Its durable state is ABI shape: compatible strings, property names, child-node names, phandle cell counts, register and interrupt ordering, resource names, and example topology. Runtime behavior is owned by matched drivers and hardware: runtime state in the matched driver, including probe resources, role/mode state, power state, IRQ status, and hardware register contents. Schema edits therefore persist as compatibility commitments for existing DTS files even though no code path is stored here.

## Risks
Main risks are ABI drift around compatible strings, resource ordering, GPIO polarity, supply names, child-node layout, graph links, and common USB schema references; changing compatible ordering or removing fallback strings; broadening a schema so invalid board nodes pass; tightening a schema so existing DTBs fail; and mismatches between YAML clock/reset/regulator/PHY names and driver lookup tables. Multi-role USB and Type-C bindings are especially sensitive to graph endpoints, role-switch dependencies, connector children, and wakeup semantics. UFS bindings are sensitive to per-SoC clock arrays, ICE register resources, PHY lane counts, and reset/power sequencing. The closure profile rejects undeclared top-level properties with `additionalProperties: false`.

## Test Signals
Use `make dt_binding_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/usb/brcm,bdc.yaml` for this schema and its examples, then `make dtbs_check DT_SCHEMA_FILES=Documentation/devicetree/bindings/usb/brcm,bdc.yaml` against boards using these compatibles. Useful negative tests remove each required property, scramble compatible fallback order, use bad child-node names, provide too many/few clocks, resets, interrupts, PHYs, or register windows, and add undeclared properties when the schema is closed. Runtime signals are clean driver probe, expected PHY/role-switch/provider registration where applicable, correct device enumeration, suspend/resume without resource leaks, and no new schema warnings.
