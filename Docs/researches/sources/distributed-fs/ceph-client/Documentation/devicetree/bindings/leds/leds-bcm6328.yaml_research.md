# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/leds/leds-bcm6328.yaml

**Purpose:** Defines the Linux Devicetree JSON-schema contract for `LEDs connected to Broadcom BCM6328 controller`. In this source tree it is a LED controller or common LED schema binding; it constrains board DTS/DTB nodes so kernel OF matching and subsystem code can discover the hardware resources consistently. This is declarative ABI documentation, not executable Ceph client code, but it is part of the imported kernel documentation corpus that protects hardware-description compatibility. The source description says: This controller is present on BCM6318, BCM6328, BCM6362 and BCM63268. In these SoCs it's possible to control LEDs both as GPIOs or by hardware. However, on some devices there are Serial LEDs (LEDs connected to a 74x164 controller), which can either be controlled by software (exporting the 74x164 as spi-gpio. See Documentation/devicetree/bindings/gpio/fairchild,74hc595.yaml), or by hardware using this driver. Some of these Serial LEDs are hardware controlled (e.g. ethernet LEDs) and exporting the 74x164 as spi-gpio prevents those LEDs to be hardware controlled, so the only chance to keep them working is by using this driver. BCM6328 LED controller has a HWDIS register, which controls whether a LED should be controlled by a hardware signal instead of the MODE register value, with 0 meaning hardware control enabled and 1 hardware control disabled. This is usually 1:1 for hardware to LED signals, but through the activity/link registers you have some limited control over rerouting the LEDs (as explained later in brcm,link-signal-sources). Even if a LED is hardware controlled you are still able to make it blink or light it up if it isn't, but you can't turn it off if the hardware decides to light it up. For this reason, hardware controlled LEDs aren't registered as LED class devices. Each LED is represented as a sub-node of the brcm,bcm6328-leds device.

**Important APIs/types/functions:** The public surface is the schema itself: `$id` `http://devicetree.org/schemas/leds/leds-bcm6328.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, composition keywords, closure rules, and `examples` consumed by `dt-schema`. Compatible strings are `brcm,bcm6328-leds`. Required properties are `reg`, `#address-cells`, `#size-cells`. Important top-level properties include `compatible`, `reg`, `brcm,serial-leds`, `brcm,serial-mux`, `brcm,serial-clk-low`, `brcm,serial-dat-low`, `brcm,serial-shift-inv`, `#address-cells`, `#size-cells`. Patterned or child-node surfaces include `@[a-f0-9]+$`. Direct schema references are `/schemas/types.yaml#/definitions/uint32-array`, `common.yaml#`. Maintainers: Álvaro Fernández Rojas <noltari@gmail.com>. Top-level property policy is `additionalProperties: false`.

**Control flow:** Runtime control flow is supplied by Devicetree tooling and kernel drivers rather than by this YAML. `dt_binding_check` loads the core meta-schema, resolves `$ref` dependencies, applies constants/enums/cardinality/range checks, evaluates composition and conditional branches (none declared), and validates the embedded examples. At boot, the compiled DTB node is matched by `compatible`; the relevant LED driver or common subsystem reads resource properties, phandles, child nodes, and cells before registering devices or provider relationships. Child/provider surfaces to watch here are `@[a-f0-9]+$`.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistence is ABI persistence: accepted DTS nodes encode hardware identity, register windows, interrupts, power/clock/reset topology, phandle cell widths, channel indexes, and child LED/IOMMU/IPMI layout for long-lived boards. Tightening `required`, changing compatible fallback order, altering cell counts, or changing closure policy can reject existing DTBs or make drivers parse resources differently.

**Dependencies and integration points:** Integrated with LED class devices, multicolor/flash/channel child nodes, GPIO/PWM/regulator resources, and trigger/function/color naming. Schema dependencies include `/schemas/types.yaml#/definitions/uint32-array`, `common.yaml#`; examples may also include dt-bindings headers. Resource integration is through properties such as `compatible` for driver match key and hardware ABI identifier; `reg` for MMIO, I2C/SPI address, or child register address; `#address-cells` for child address cell layout; `#size-cells` for child size cell layout. Driver integration is through `compatible`, while subsystem integration is through phandle arrays, provider cell counts, common schemas, and child-node schemas inherited or declared here.

**Risks and edge cases:** Main risks are schema ABI drift, missing or stale compatible coverage, incorrect min/max item constraints, wrong `#*-cells` values, resource names that diverge from driver expectations, conditionals that validate one SoC or chip variant while rejecting another valid one, and examples that no longer reflect real DTS users. Closure policy (`additionalProperties: false`) is useful for catching misspellings but can also block legitimate extensions. For LED/backlight children, channel numbering and `reg`/`led-sources` constraints are common failure points; for IOMMU bindings, stream IDs and cell widths are especially sensitive; for IPMI bindings, host/BMC address and register-resource shape must match the driver.
