# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/iommu/apple,sart.yaml

**Purpose:** Defines the Devicetree JSON-schema contract for `Apple SART DMA address filter`. In this tree it is a IOMMU binding: it constrains how board DTS files describe the hardware block, what phandle provider/client ABI is exposed, and how Linux discovers the device through OF matching and common DT resource helpers. The source description says: Apple SART is a simple address filter for DMA transactions. Regions of physical memory must be added to the SART's allow list before any DMA can target these. Unlike a proper IOMMU no remapping can be done and special support in the consumer driver is required since not all DMA transactions of a single device are subject to SART filtering. SART1 has first been used since at least the A11 (iPhone 8 and iPhone X) and allows 36 bit of physical address space and filter entries with sizes up to 24 bit. SART2, first seen in A14 and M1, allows 36 bit of physical address space and filter entry size up to 36 bit. SART3, first seen in M1 Pro/Max, extends both the address space and filter entry size to 42 bit.

**Important APIs/types/functions:** This YAML is declarative schema, not executable code. Its public ABI surface is `$id` `http://devicetree.org/schemas/iommu/apple,sart.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, and any referenced dt-schema fragments. Compatible strings or compatible-pattern values are `apple,t6020-sart`, `apple,t8112-sart`, `apple,t6000-sart`, `apple,t8015-sart`, `apple,t8103-sart`. Required properties are `compatible`, `reg`. Important top-level properties are `compatible`, `reg`, `power-domains`. Direct and nested `$ref` dependencies are none declared. Property roles include `compatible` for driver match key and stable hardware ABI identifier; `reg` for MMIO range, bus address, or child register selector; `power-domains` for genpd power-domain attachment. The top-level unknown-property policy is `additionalProperties: false`. Maintainers are `Sven Peter <sven@svenpeter.dev>`.

**Control flow:** Runtime control flow is supplied by dt-schema tooling and the kernel subsystem that consumes the resulting DTB. `dt_binding_check` loads the core meta-schema, resolves `$ref` entries, applies `properties`, `required`, enum/const/items limits, and composition keywords, then validates the examples. At boot, a DT node satisfying this schema is matched by `compatible`; resource helpers read `reg`, clocks, resets, power domains, interrupts, MSI/IOMMU cells, and child nodes; then the relevant IRQ-domain, MSI-domain, or IOMMU driver registers provider state for clients. Schema composition/conditional keywords present: `oneOf`. It does not define nested child-node schemas.

**State and persistence behavior:** The file owns no mutable runtime state and writes no persistent data. Its persistent effect is ABI stability: DTS and DTB nodes that satisfy this contract encode hardware identity, register layout, interrupt or translation-domain topology, phandle specifier widths, and child-node layout for long-lived board files. Changing required fields, compatible ordering, cell counts, or closure policy can break existing DTBs even though the YAML itself stores no kernel state.

**Dependencies and integration points:** Linux IOMMU and DMA mapping code use it to attach masters to translation/protection domains from DT phandles. Schema-level dependencies are the core Devicetree meta-schema plus the `$ref` targets listed above. Resource integration is through properties such as `reg`, `power-domains`. Driver integration is through `compatible`; provider/client integration is through cell-count properties, phandle arrays, child schemas, and any common binding references inherited by dt-schema.

**Risks:** Main risks are Devicetree ABI drift, incomplete compatible coverage, wrong `#*-cells` counts, overly broad or overly strict conditional branches, missing required clocks/resets/interrupt parents/power domains, and stale examples. Closure policy matters because false unknown-property settings catch misspellings but can reject legitimate board extensions. For interrupt/MSI/IOMMU providers, incorrect parent-domain links or specifier widths can pass schema validation yet fail at boot with lost interrupts, bad affinity, MSI allocation failure, or DMA translation faults.
