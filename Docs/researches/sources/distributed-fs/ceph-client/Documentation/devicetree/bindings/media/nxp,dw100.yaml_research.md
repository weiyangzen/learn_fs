# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/nxp,dw100.yaml

**Purpose:** Defines the Devicetree JSON-schema ABI for `NXP i.MX8MP DW100 Dewarper core`. It is a media hardware binding in the Ceph client Linux source snapshot, constraining how board DTS/DTB files describe media hardware so Linux media, V4L2 mem2mem, platform, clock, reset, power-domain, IOMMU, and graph helpers can bind the correct driver resources. The source description says: The Dewarp Engine provides high-performance dewarp processing for the correction of the distortion that is introduced in images produced by fisheye and wide angle lenses. It is implemented with a line/tile-cache based architecture. With configurable address mapping look up tables and per tile processing, it successfully generates a corrected output image. The engine can be used to perform scaling, cropping and pixel format conversion.

**Important APIs/types/functions:** This is declarative schema, so the exported API is the binding contract rather than C functions. Public surfaces include `$id` `http://devicetree.org/schemas/media/nxp,dw100.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, examples, and dt-schema references. The `compatible` property uses `enum` list and accepts `nxp,imx8mp-dw100`. Top-level required properties are `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `power-domains`; required names across nested/conditional schemas include `clock-names`, `clocks`, `compatible`, `interrupts`, `power-domains`, `reg`. Top-level properties are `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `power-domains`; all nested property names include `clock-names`, `clocks`, `compatible`, `interrupts`, `power-domains`, `reg`. Resource constraints visible in the schema include `compatible`, `reg` (maxItems=1), `interrupts` (maxItems=1), `clocks`, `clock-names` (names=axi/ahb), `power-domains` (maxItems=1). Closure is `additionalProperties: False`.

**Control flow:** Runtime control flow is supplied by dt-schema and kernel probing. `dt_binding_check` loads the core meta-schema, resolves references, validates the compatible form, applies required lists and `minItems`/`maxItems`/`const` restrictions, evaluates conditionals, and compiles the inline examples. At boot the DTB node is matched by `compatible`; the platform or media driver then reads MMIO ranges, named interrupts, clocks, resets, power domains, IOMMU streams, DMA/interconnect paths, firmware or reserved-memory phandles, and graph endpoints. There are no compatible-specific conditional branches beyond direct property validation. This binding has no media graph endpoint surface; integration is by platform device resources and codec-specific child nodes.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence itself. Its persistent effect is ABI stability for DTS files and shipped DTBs: compatible strings, child-node names, phandle relationships, address ranges, cell counts, and media graph topology are long-lived hardware descriptions. Any change to required properties, resource ordering, child object schemas, or unknown-property policy can invalidate existing board descriptions even though no kernel state is written by the YAML.

**Dependencies and integration points:** Direct schema references are none. Runtime dependencies are genpd power domains, clock provider phandles and fixed clock-name ordering. No nested object nodes are defined beyond common schema references. Maintainers listed in the binding are `Xavier Roumegue <xavier.roumegue@oss.nxp.com>`.

**Risks:** Key risks: compatible-string or fallback-order drift can break OF matching and dtbs_check expectations; resource array ordering is ABI-sensitive for `reg-names`, `clock-names`, `interrupt-names`, `power-domain-names`, and `reset-names`; SoC-specific power-domain count differences are easy to regress in fallback compatibles. The closure policy is `additionalProperties: False`, so unknown properties are intentionally rejected after referenced schemas are evaluated.
