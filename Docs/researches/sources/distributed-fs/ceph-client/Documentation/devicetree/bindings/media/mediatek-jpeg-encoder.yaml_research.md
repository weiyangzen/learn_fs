# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/media/mediatek-jpeg-encoder.yaml

**Purpose:** Defines the Devicetree JSON-schema ABI for `MediaTek JPEG Encoder`. It is a JPEG codec accelerator binding in the Ceph client Linux source snapshot, constraining how board DTS/DTB files describe media hardware so Linux media, V4L2 mem2mem, platform, clock, reset, power-domain, IOMMU, and graph helpers can bind the correct driver resources. The source description says: MediaTek JPEG Encoder is the JPEG encode hardware present in MediaTek SoCs

**Important APIs/types/functions:** This is declarative schema, so the exported API is the binding contract rather than C functions. Public surfaces include `$id` `http://devicetree.org/schemas/media/mediatek-jpeg-encoder.yaml#`, `$schema` `http://devicetree.org/meta-schemas/core.yaml#`, `title`, `maintainers`, `properties`, `required`, examples, and dt-schema references. The `compatible` property uses ordered fallback-compatible sequence and accepts `mediatek,mt2701-jpgenc`, `mediatek,mt8183-jpgenc`, `mediatek,mt8186-jpgenc`, `mediatek,mt8188-jpgenc`, `mediatek,mtk-jpgenc`. Top-level required properties are `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `power-domains`, `iommus`; required names across nested/conditional schemas include `clock-names`, `clocks`, `compatible`, `interrupts`, `iommus`, `power-domains`, `reg`. Top-level properties are `compatible`, `reg`, `interrupts`, `clocks`, `clock-names`, `power-domains`, `iommus`; all nested property names include `clock-names`, `clocks`, `compatible`, `interrupts`, `iommus`, `power-domains`, `reg`. Resource constraints visible in the schema include `compatible`, `reg` (maxItems=1), `interrupts` (maxItems=1), `clocks` (maxItems=1), `clock-names` (names=jpgenc), `power-domains` (maxItems=1), `iommus` (minItems=2; maxItems=32). Closure is `additionalProperties: False`.

**Control flow:** Runtime control flow is supplied by dt-schema and kernel probing. `dt_binding_check` loads the core meta-schema, resolves references, validates the compatible form, applies required lists and `minItems`/`maxItems`/`const` restrictions, evaluates conditionals, and compiles the inline examples. At boot the DTB node is matched by `compatible`; the platform or media driver then reads MMIO ranges, named interrupts, clocks, resets, power domains, IOMMU streams, DMA/interconnect paths, firmware or reserved-memory phandles, and graph endpoints. There are no compatible-specific conditional branches beyond direct property validation. This binding has no media graph endpoint surface; integration is by platform device resources and codec-specific child nodes.

**State and persistence behavior:** The file stores no mutable runtime state and performs no persistence itself. Its persistent effect is ABI stability for DTS files and shipped DTBs: compatible strings, child-node names, phandle relationships, address ranges, cell counts, and media graph topology are long-lived hardware descriptions. Any change to required properties, resource ordering, child object schemas, or unknown-property policy can invalidate existing board descriptions even though no kernel state is written by the YAML.

**Dependencies and integration points:** Direct schema references are none. Runtime dependencies are IOMMU/SMMU stream mappings for video DMA, genpd power domains, clock provider phandles and fixed clock-name ordering. No nested object nodes are defined beyond common schema references. Maintainers listed in the binding are `Xia Jiang <xia.jiang@mediatek.com>`.

**Risks:** Key risks: compatible-string or fallback-order drift can break OF matching and dtbs_check expectations; resource array ordering is ABI-sensitive for `reg-names`, `clock-names`, `interrupt-names`, `power-domain-names`, and `reset-names`; wrong IOMMU stream IDs can cause video DMA faults or silent memory corruption; SoC-specific power-domain count differences are easy to regress in fallback compatibles. The closure policy is `additionalProperties: False`, so unknown properties are intentionally rejected after referenced schemas are evaluated.
