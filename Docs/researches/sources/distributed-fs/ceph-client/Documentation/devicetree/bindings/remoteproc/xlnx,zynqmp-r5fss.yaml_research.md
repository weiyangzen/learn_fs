# sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/remoteproc/xlnx,zynqmp-r5fss.yaml

## Purpose
`sources/distributed-fs/ceph-client/Documentation/devicetree/bindings/remoteproc/xlnx,zynqmp-r5fss.yaml` is a Linux devicetree YAML schema for the `Xilinx R5F processor subsystem` remote processor subsystem binding. The Xilinx platforms include a pair of Cortex-R5F processors (RPU) for real-time processing based on the Cortex-R5F processor core from ARM. The Cortex-R5F processor implements the Arm v7-R architecture and includes a floating-point unit that implements the Arm VFPv3 instruction set. It is not executable Ceph or kernel logic; it is a hardware-description ABI used by DTS authors, dt-schema, and Linux subsystem drivers so that board descriptions match what the driver will parse at probe or early boot.

## Important APIs, Types, and Functions
The public API surface is the schema's accepted node shape. `compatible` uses `enum` list and covers 3 compatible tokens: `xlnx,zynqmp-r5fss`, `xlnx,versal-r5fss`, `xlnx,versal-net-r52fss`. Top-level properties are `compatible`, `#address-cells`, `#size-cells`, `ranges`, `xlnx,cluster-mode`, `xlnx,tcm-mode`. Across nested schemas and child nodes this file mentions 13 distinct property names; required properties observed at all levels include `#address-cells`, `#size-cells`, `compatible`, `power-domains`, `ranges`, `reg`, `reg-names`, `xlnx,tcm-mode`. Node naming is constrained by no explicit node-name constraint. Remoteproc-facing properties define firmware loading and processor-control resources: address ranges `#address-cells`, `#size-cells`, `ranges`, memory-carveout links `ranges`, mailbox/interrupt/IPC hooks none, and clock/reset/power controls none. Required properties are `compatible`, `#address-cells`, `#size-cells`, `ranges`; these values are consumed by Linux remoteproc drivers before firmware boot, crash handling, and virtio/rpmsg setup.

## Control Flow, State, and Persistence
Control flow is declarative JSON-schema evaluation. `dt-doc-validate`, `dt_binding_check`, and `dtbs_check` load the YAML, expand `$ref` links, match nodes by `compatible` or referenced common-schema use, enforce required properties, evaluate composition/conditional keywords, and validate inline DTS examples. At runtime, platform bus probing hands the validated node to a remoteproc driver, which maps resources, obtains clocks/resets/power domains, reserves memory, starts firmware, and may expose rpmsg/virtio endpoints. The YAML itself stores no mutable runtime state and writes no persistent data; persistence is the source-controlled devicetree ABI and the DTB blobs built from DTS. External references used in evaluation are `/schemas/types.yaml#/definitions/phandle-array`, `/schemas/types.yaml#/definitions/uint32`; schema composition/conditional keywords present are `allOf`, `else`, `if`, `then`.

## Risks
Risks are ABI and integration risks. Changing compatible ordering, required keys, resource names, child-node patterns, cell counts, or strictness can reject existing DTS files or let invalid hardware descriptions reach runtime probe. This schema has 6 top-level properties, 13 distinct property names across nested schemas, and this strictness profile: unknown top-level properties are rejected. Conditional branches and shared `$ref` schemas should be checked against all in-tree users because schema-only edits can still break board builds or driver binding.
