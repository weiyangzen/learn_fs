# sources/distributed-fs/ceph-client/arch/x86/kvm/vmx/vmx.h

Purpose: defines the central Intel VMX private state and inline helper contract used by KVM's VMX backend. It describes per-vCPU VMX state, nested-VMX state, VMCS control shadowing, VMX control bit policy, MSR bitmap helpers, and conversion helpers between generic KVM/VT objects and VMX-specific containers.

Important APIs, types, and functions: `struct vcpu_vmx` embeds the generic `struct kvm_vcpu`, shared VT state, VMCS pointers, MSR autoload/autostore arrays, segment/rmode caches, nested VMX state, PML page state, feature-control MSR shadows, Intel PT/LBR descriptors, and virtualization exception info. `struct nested_vmx` tracks L1 VMX operation, VMCS12/shadow/eVMCS caches, vmcs02, pinned host mappings for L2 APIC/PI pages, nested posted-interrupt state, preemption timer state, nested MSR snapshots, VPID assignment, and SMM-entry nested state. `struct kvm_vmx` extends the VM object with VMX-specific TSS, identity-map, and posted-interrupt descriptor table state. Inline helpers include `to_vmx()`, `to_kvm_vmx()`, `to_vt()`, `vt_to_vcpu()`, exit-info readers, DEBUGCTL read/write masking, MSR bitmap test/set/clear helpers, control-shadow setters/getters, VMCS allocation wrappers, guest-state validity helpers, instruction-info decoders, and feature probes such as `vmx_has_waitpkg()`, `vmx_need_pf_intercept()`, `is_unrestricted_guest()`, and `vmx_can_use_ipiv()`.

Control flow and behavior: this header is not an entry-point implementation, but it shapes most VMX runtime paths. VM-exit handlers obtain cached exit reason, qualification, and interrupt info through lazy `vmcs_read*()` access that marks KVM register caches available. VM-entry/exit control changes flow through `BUILD_CONTROLS_SHADOW()`: callers update the shadow first-class state, and hardware VMCS writes happen only when the value changes. MSR interception code uses generated bitmap helpers that map low and high MSR ranges to Intel's read/write bitmap layout; out-of-range MSRs are treated as intercepted. Guest state validation uses unrestricted guest when available and otherwise delegates to strict VMX state checks. Debug-control writes preserve host-owned `DEBUGCTLMSR_FREEZE_IN_SMM` while exposing only guest-owned bits.

State and persistence: all state is in-memory kernel state tied to a VM, vCPU, per-vCPU VMCS, or pinned guest page mapping. `loaded_vmcs` switches between `vmcs01` for L1 and `vmcs02` for L2. `nested.cached_vmcs12`, `cached_shadow_vmcs12`, dirty/sync booleans, and GPA-to-HVA caches persist guest VMCS state across nested VMX instructions until flushed back to guest memory. `controls_shadow` mirrors VMCS control fields to avoid unnecessary VMREAD/VMWRITE operations and is authoritative for helper reads. PML, VPID, PI descriptor, preemption timer, and MSR autoload/autostore arrays persist for the life of the vCPU or VM and are reinitialized through VMX lifecycle code, not filesystem storage.

Dependencies and integration points: included by VMX implementation files such as `vmx.c`, `nested.c`, `main.c`, PMU, SGX, TDX, and interrupt/APIC code. It depends on KVM host APIs, VMCS definitions, low-level VMX operations from `vmx_ops.h`, x86 CPUID/MMU helpers, Intel PT/perf/LBR structures, posted interrupts, optional Hyper-V enlightened VMCS state, optional KVM Hyper-V, optional TDX declarations through related ops headers, and generic KVM register-cache conventions.

Risks and correctness concerns: layout changes to `struct vcpu_vmx` and `struct nested_vmx` can break assumptions in assembly run paths, nested-state save/restore, migration, and userspace nested-state ioctls. Control masks must track Intel capability MSRs and eVMCS support; adding a control without updating required/optional masks or eVMCS sanitation can expose unsupported VMCS fields. MSR bitmap offsets are subtle, especially the low/high read/write regions. Lazy register-cache helpers must not be used for TDX vCPUs where VMCS reads are invalid, hence the explicit warnings. Nested VMCS dirty/sync flags and pinned page maps are high-risk for stale L2 state, leaked pins, or incorrect VMCS12 propagation.

Test signals: build coverage across `CONFIG_X86_64`, `CONFIG_KVM_HYPERV`, `CONFIG_KVM_SMM`, `CONFIG_KVM_INTEL_TDX`, EPT on/off, and nested VMX on/off catches declaration and mask drift. Runtime signals include KVM selftests for VMX controls, nested VMX state save/restore, VMCS shadowing/eVMCS, MSR bitmap interception, PML dirty logging, VPID/EPT invalidation behavior, posted interrupts, SMM with nested VMX, guest DEBUGCTL behavior, and CPU hotplug or vCPU migration while VMCS state is loaded.
