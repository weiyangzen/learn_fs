# sources/distributed-fs/ceph-client/arch/x86/kvm/vmx/vmx_onhyperv.h

Purpose: provides the inline enlightened VMCS access layer for running KVM's Intel VMX backend as a nested hypervisor on Hyper-V. It lets normal VMCS accessors transparently read/write `struct hv_enlightened_vmcs` memory instead of executing VMREAD/VMWRITE, and it loads the enlightened VMCS through Hyper-V's VP assist page rather than `VMPTRLD`.

Important APIs and functions: `current_evmcs` casts the current per-CPU VMCS pointer to Hyper-V's enlightened VMCS layout. `kvm_is_using_evmcs()` reads the static key declared here and defined in `vmx_onhyperv.c`. `get_evmcs_offset()` maps an Intel VMCS field encoding to an eVMCS byte offset plus clean-field bit via `evmcs_field_offset()`, warning for unsupported fields. `evmcs_write64()`, `evmcs_write32()`, and `evmcs_write16()` store into the current eVMCS and clear the corresponding `hv_clean_fields` bit. `evmcs_read64()`, `evmcs_read32()`, and `evmcs_read16()` load from eVMCS memory and return zero for unsupported fields. `evmcs_load(u64 phys_addr)` updates Hyper-V's VP assist page to make the enlightened VMCS current and enables enlightened VM-entry. When Hyper-V support is not compiled in, all helpers become cheap stubs.

Control flow and behavior: normal VMCS access in `vmx_ops.h` first checks `kvm_is_using_evmcs()`. If true, control comes here: field encodings are translated, unsupported accesses warn and return without touching memory, supported writes update the eVMCS backing page and mark the associated clean group dirty for Hyper-V. Loading a VMCS writes `current_nested_vmcs` and `enlighten_vmentry` in the per-CPU `hv_vp_assist_page`; if the eVMCS requests nested flush hypercalls, `directhypercall` is enabled in the nested-control features.

State and persistence: state is per-CPU and per-vCPU runtime state. The active enlightened VMCS lives in memory referenced by `current_vmcs`; `hv_clean_fields` persists dirty/clean tracking between VM entries so Hyper-V can avoid reprocessing unchanged field groups. The VP assist page fields persist for the running CPU until changed by KVM, CPU hotplug teardown, or Hyper-V. There is no filesystem persistence.

Dependencies and integration points: gated by `CONFIG_HYPERV` and includes Hyper-V HVDK/MS hypervisor interfaces, Linux jump labels, VMCS12 and eVMCS field-offset definitions, and KVM bug helpers. It is integrated by `vmx_ops.h` accessors, eVMCS capability sanitation, VMX CPU enablement that validates VP assist pages, and nested VMX code that fills eVMCS fields.

Risks and correctness concerns: all field-offset mappings and clean-field bits must match Hyper-V's ABI exactly. A missing clean-field clear can cause Hyper-V to reuse stale VMCS data; an incorrect offset can corrupt unrelated eVMCS state. `evmcs_load()` depends on a valid VP assist page on every CPU where VMX is enabled, and the code treats absence as a KVM bug. Unsupported field reads returning zero can hide issues unless warning coverage is monitored.

Test signals: test with `CONFIG_HYPERV=y` and disabled builds to validate both real and stub paths. Runtime signals include nested KVM-on-Hyper-V boot, CPU hotplug while eVMCS is enabled, VP assist page validation failures, clean-field dirtying after VMCS writes, direct hypercall enablement for nested flush, and selftests that exercise unsupported VMCS field probes.
