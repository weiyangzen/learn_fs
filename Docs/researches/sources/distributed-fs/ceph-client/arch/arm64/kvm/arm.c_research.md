# sources/distributed-fs/ceph-client/arch/arm64/kvm/arm.c

## Purpose
`arm.c` is the main ARM64 KVM host integration unit. It binds the generic KVM core to ARM64 VM and vCPU lifecycle operations, user ABI ioctls, vCPU run-loop entry/exit, IRQ injection, WFI/suspend handling, hypervisor initialization, pKVM setup, and per-CPU virtualization enable/disable paths. It is the file that turns the lower-level VGIC, timer, PMU, sysreg, MMU, nested virtualization, and hyp code into a usable `/dev/kvm` architecture backend.

## Important APIs, Types, and Functions
Important file-local state includes `kvm_mode`, the early boot selected mode; `kvm_wfi_trap_policy` and `kvm_wfe_trap_policy`, controlling WFx trap behavior; `vgic_present`; `kvm_arm_initialised`; and per-CPU hyp state such as `kvm_hyp_initialized`, `kvm_arm_hyp_stack_base`, `kvm_init_params`, and `kvm_hyp_ctxt`. `struct kvm_ioctl_cap_map` maps VM ioctls to capability constants for permission/capability checks.

VM lifecycle entry points are `kvm_arch_alloc_vm`, `kvm_arch_init_vm`, `kvm_arch_create_vm_debugfs`, and `kvm_arch_destroy_vm`. They allocate the ARM64 `struct kvm`, initialize nested state, share host memory with hyp, allocate supported CPU masks, initialize stage-2 MMU state, optionally reserve pKVM host VM metadata, initialize VGIC/timers/hypercalls, and unwind in reverse order on failure. vCPU lifecycle is handled by `kvm_arch_vcpu_precreate`, `kvm_arch_vcpu_create`, `kvm_arch_vcpu_destroy`, `kvm_arch_vcpu_load`, `kvm_arch_vcpu_put`, `kvm_arch_vcpu_run_pid_change`, and `kvm_arch_vcpu_ioctl_vcpu_init`.

User ABI handling is spread across `kvm_vm_ioctl_enable_cap`, `kvm_vm_ioctl_check_extension`, `kvm_arch_vm_ioctl`, and `kvm_arch_vcpu_ioctl`. These expose and validate ARM capabilities such as MTE, SVE, PMUv3, ptrauth, EL2/NV, counter offsets, writable implementation ID registers, SEA-to-user, and supported register masks. vCPU ioctls cover `KVM_ARM_VCPU_INIT`, one-reg get/set, reg-list discovery, device attrs, vCPU events, and finalize.

The main execution API is `kvm_arch_vcpu_ioctl_run`. Its helper set includes `check_vcpu_requests`, `kvm_vcpu_exit_request`, `kvm_arm_vcpu_enter_exit`, `kvm_vcpu_wfi`, `kvm_vcpu_suspend`, and MP-state helpers. Hypervisor and module startup is rooted at `kvm_arm_init`, `init_hyp_mode`, `init_subsystems`, `cpu_prepare_hyp_mode`, `cpu_hyp_init`, `cpu_hyp_reinit`, and `kvm_arch_enable_virtualization_cpu`.

## Control Flow
Module initialization starts in `kvm_arm_init`. It rejects systems without hyp mode or with `kvm-arm.mode=none`, initializes sysreg tables, computes the IPA limit, initializes SVE and VMID allocation, then initializes hyp mappings when the kernel is not already in hyp mode. `init_hyp_mode` allocates hyp page tables, per-CPU stacks, nVHE per-CPU regions, maps hyp text/data/rodata/bss, prepares per-CPU `kvm_nvhe_init_params`, exports sanitized feature data into nVHE symbols, and performs pKVM-only initialization such as PSCI relay, host SVE state, pointer-auth keys, and memory protection. `init_subsystems` runs CPU hyp init on all CPUs, registers CPU PM notifiers, initializes VGIC hyp state, timers, perf callbacks, and hyp tracing. Only after these succeed does `kvm_init` register with the generic KVM core and set `kvm_arm_initialised`.

VM creation validates the VM type, initializes config locking and nested state, shares the `struct kvm` with hyp, prepares stage-2 MMU state, optionally reserves a pKVM VM, initializes VGIC/timer/hypercall state, and records a default max-vCPU count based on VGIC capabilities. vCPU creation initializes MP-state locking, timer/PMU/pvtime state, the vCPU MMU page cache, VGIC CPU state, and hyp sharing. First run through `kvm_arch_vcpu_run_pid_change` finalizes resources that depend on configured features: MPIDR lookup cache, VGIC resources, finalized sysregs, nested state, calculated traps, timer/PMU enablement, GICv5 PPI finalization, and pKVM hyp VM/vCPU creation.

The run loop first completes a pending MMIO return if necessary, loads the vCPU, activates its signal mask, then loops while the guest should continue. Each iteration handles pending host work, processes KVM requests, disables preemption, flushes nested/PMU/VGIC hardware state, marks the vCPU `IN_GUEST_MODE` with the required memory barrier, and either exits early for userspace/kernel work or enters hyp through `__kvm_vcpu_run`. On exit it syncs PMU, VGIC, timer, nested and FP state in a carefully ordered sequence, handles early exits before preemption is re-enabled, checks for disallowed AArch32 state, and finally dispatches architectural exit handling. Before returning to userspace it updates userspace IRQ-chip run fields and commits pending PC/exception adjustments through hyp if needed.

IRQ injection enters through `kvm_vm_ioctl_irq_line`, decodes the packed KVM ARM IRQ number, dispatches CPU IRQ/FIQ lines for userspace irqchip mode, or injects PPI/SPI lines through VGIC for in-kernel irqchips. GICv5 PPIs/SPIs are translated to GICv5 IntIDs and PPIs are restricted to the explicit userspace-exposed mask.

## State and Persistence Behavior
Most state is in generic KVM objects and ARM64 arch extensions, not persistent storage. VM state includes `kvm->arch.flags`, `vcpu_features`, `supported_cpus`, stage-2 MMU state, optional pKVM handles, hypercall state, and the RCU-protected `mpidr_data` acceleration table. vCPU state includes MP state, HCR/MDCR fields, sysregs, timer/PMU/VGIC/debug state, nested state, PID tracking, and flags such as `VCPU_INITIALIZED`. Per-CPU state tracks whether hyp has been initialized and the last vCPU that ran for a given MMU, used to invalidate stale private TLB/I-cache contexts.

Synchronization is explicit: VM config changes use `kvm->arch.config_lock`, VM/vCPU creation paths use `kvm->lock` and vCPU mutex ordering hints for lockdep, MP state uses `mp_state_lock`, slot-sensitive capability changes use `slots_lock`, and MPIDR lookup data uses RCU with `synchronize_rcu` on destruction. CPU PM notifiers reset and restore hyp state around low-power transitions. No durable on-disk state is written by this file.

## Dependencies and Integration Points
This file is tightly integrated with generic KVM (`kvm_init`, vCPU requests, dirty rings, run structures), ARM64 hyp code (`kvm_call_hyp`, nVHE symbols, VHE/nVHE mode selection), stage-2 MMU and VMID allocation, VGIC v2/v3/v5, timers, PMU, debug, FP/SVE, ptrauth, sysregs, nested virtualization, pKVM memory protection, PSCI/SMCCC, CPU PM, perf callbacks, tracepoints, irqfd/irqbypass, and user access helpers. It also consumes CPU feature infrastructure and command-line early parameters.

## Risks and Edge Cases
Correctness depends on subtle ordering in the run loop: request checks around `IN_GUEST_MODE`, interrupt disablement, VGIC/timer/PMU sync ordering, and preemption boundaries. pKVM initialization has limited recovery once protection is finalized. Capability enablement is intentionally constrained before vCPU or memslot creation; relaxing this can break ABI assumptions. MPIDR compression must fall back safely for sparse or adversarial MPIDR layouts. WFI/WFE trap policy interacts with single-task optimization, VGICv5, and direct interrupt injection. Unsupported CPU migration is detected at vCPU load and converted to `KVM_EXIT_FAIL_ENTRY`. Nested virtualization paths depend on correct HCR, VNCR/TLB, and hardware MMU switching.

## Test Signals
Useful tests include KVM selftests for ARM64 VM creation, vCPU init/finalize, one-reg ABI, capability probing, MTE/SVE/PMU/ptrauth feature combinations, irq-line injection with userspace and in-kernel irqchips, WFI wakeups, system suspend wake events, PSCI CPU on/off, dirty-ring exits, and nested virtualization. Boot-time smoke tests should cover VHE, nVHE, protected KVM, `kvm-arm.mode=` variants, CPU hotplug/PM suspend-resume, VGIC absent/present paths, and failure unwinds from hyp, VGIC, timer, and VMID initialization.
