# sources/distributed-fs/ceph-client/arch/arm/mach-omap2/omap_hwmod_2420_data.c

Purpose: Provides the OMAP2420-specific hwmod integration table. It declares chip-local IP blocks and OCP links, combines them with common OMAP2 hwmods, and exposes `omap2420_hwmod_init()` to register the OMAP2420 module graph.

Important descriptors: the file defines OMAP2420-only IVA1 and DSP classes/modules with named hardreset lines, I2C1/I2C2 modules using a 16-bit I2C class and `omap_i2c_reset`, a mailbox module using the common mailbox class, McBSP1/2 modules with pad and PRCM optional clocks, an MSDI/MMC-like module using `omap_msdi_reset`, and an HDQ/1-wire module using the common HDQ class. OCP links connect L4 CORE to I2C, mailbox, McBSP, MSDI, and HDQ; L3 to IVA, DSP, and GPMC; and L4 WKUP to watchdog and GPIO modules from common 2xxx data.

Control flow: `omap2420_hwmod_init()` calls `omap_hwmod_init()` and then passes `omap2420_hwmod_ocp_ifs` to `omap_hwmod_register_links()`. The array starts with common interconnect and module links (`l3_main__l4_core`, `mpu__l3_main`, DSS, McSPI, UARTs, timers, DSS children, crypto) and then adds 2420-specific I2C, IVA, DSP, watchdog/GPIO, McBSP, MSDI, HDQ, and GPMC links. Registration causes the core to register each master/slave hwmod once and attach each OCP slave port before the later global setup pass maps DT registers and initializes clocks.

State and persistence: this file has no executable runtime state beyond static `struct omap_hwmod`, `struct omap_hwmod_class`, `struct omap_hwmod_rst_info`, optional clock arrays, and `struct omap_hwmod_ocp_if` records. Persistent effects happen only after the core consumes the descriptors: reset lines for IVA/DSP may be asserted by setup, 16-bit I2C/MSDI register access is selected by flags, I2C1 blocks WFI while active, and HDQ uses software-supervised interface idle due to its OCP link flag.

Dependencies and integration: depends on common OMAP2 interconnect/IP block descriptors, common DSS/HDQ data, CM/PRM bit definitions for OMAP24xx, and reset helpers from I2C, MMC/MSDI, and watchdog code. It feeds platform device creation and PM runtime through the shared hwmod core rather than directly interacting with drivers.

Risks: the table mixes 2420-only modules with common OMAP2 descriptors, so any wrong link ordering or clock name affects registration and reset for multiple devices. I2C1 has a documented WFI timeout issue and relies on `HWMOD_BLOCK_WFI`; removing it can break transfers during MPU idle. MSDI and I2C use 16-bit registers, so missing `HWMOD_16BIT_REG` would produce wrong MMIO access width. HDQ marks `OMAP_FIREWALL_L4` in the OCP flags field rather than firewall union data, matching legacy usage but making the meaning easy to misread.

Test signals: OMAP2420 boot should register all links without `_register_link` warnings, preserve early UARTs when debug flags select them, and reset/idle I2C, McBSP, timers, watchdog, DSS, and crypto modules without softreset timeouts. Hardware tests should exercise I2C1 during idle/WFI, DSP/IVA hardreset assert/deassert by driver code, MSDI reset, and HDQ access through the software-supervised interface clock.
