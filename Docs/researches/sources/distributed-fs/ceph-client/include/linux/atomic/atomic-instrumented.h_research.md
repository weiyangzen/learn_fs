# sources/distributed-fs/ceph-client/include/linux/atomic/atomic-instrumented.h

## Purpose
Generated Linux atomic API layer that wraps the raw architecture atomic operations with explicit sanitizer/instrumentation hooks. Normal kernel code is expected to use these `atomic*()`, `atomic64*()`, `atomic_long*()`, `xchg*()`, and `cmpxchg*()` surfaces so KASAN/KCSAN-style tooling can observe atomic memory accesses; code that must avoid instrumentation, especially `noinstr` paths, uses the corresponding `raw_*` operations instead.

## Important APIs, Types, And Functions
The file defines inline wrappers for the main atomic families: relaxed/acquire/release reads and stores, arithmetic (`add`, `sub`, `inc`, `dec`), bitwise operations (`and`, `andnot`, `or`, `xor`), return-value and fetch-value variants, compare/exchange, conditional updates such as `add_unless`, `inc_not_zero`, `dec_and_test`, `dec_unless_positive`, and the architecture-sized `xchg`, `cmpxchg`, `cmpxchg64`, `cmpxchg128`, `try_cmpxchg`, local, and sync variants. It also covers `atomic64_t` and the `atomic_long_t` API by delegating to the raw long wrappers.

## Control Flow
Each wrapper follows a fixed generated pattern: apply a KCSAN ordering marker when the API promises full or release ordering, call an `instrument_atomic_*()` or `instrument_read_write()` helper for the memory operand, then delegate to the matching `raw_*` primitive. Full-ordering operations call `kcsan_mb()`, release operations call `kcsan_release()`, acquire and relaxed operations generally rely on the raw primitive for ordering. `try_cmpxchg*()` instruments both the target object and the caller-provided old-value pointer because both can be read and written.

## State And Persistence
The header owns no global state and persists nothing. Runtime state is the caller-owned atomic object and, for `try_cmpxchg*()`, the caller-owned expected-value storage. Its behavior is stateful only through the raw atomic primitive it calls and the sanitizer metadata emitted by the instrumentation helpers.

## Dependencies And Integration Points
It depends on `linux/build_bug.h`, `linux/compiler.h`, and `linux/instrumented.h`, plus raw atomic definitions from the lower atomic include stack. It is generated by `scripts/atomic/gen-atomic-instrumented.sh`, so the maintenance boundary is the generator and the raw atomic contract rather than this file directly. It is part of the kernel's central atomic include path and therefore affects concurrency behavior throughout the Ceph client and any included kernel code.

## Risks
The main risks are semantic drift between generated wrappers and raw primitives, incorrect instrumentation size or access mode, and misuse from `noinstr` code where instrumentation is forbidden. Ordering bugs are high-impact because the wrapper names encode memory-order guarantees. Direct edits are also risky because regeneration can overwrite them and because this file must stay mechanically aligned with the raw atomic API.

## Test Signals
Useful signals include kernel build coverage across 32-bit and 64-bit configs, atomic API selftests/LKMM-oriented tests, KCSAN/KASAN boots that exercise atomic-heavy paths, and generator diff checks showing the file matches `scripts/atomic/gen-atomic-instrumented.sh`. For Ceph-client integration, stress tests around reference counts, wait conditions, and concurrent metadata/session paths would expose wrapper misuse indirectly.
