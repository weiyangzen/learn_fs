# sources/distributed-fs/ceph-client/include/linux/atomic/atomic-long.h

## Purpose
Generated compatibility layer that exposes atomic operations on C `long` width values. It maps `atomic_long_t` to `atomic64_t` when `CONFIG_64BIT` is enabled and to `atomic_t` otherwise, giving callers one API whose storage and return width follow the target architecture.

## Important APIs, Types, And Functions
The header defines `atomic_long_t`, `ATOMIC_LONG_INIT()`, and condition-read aliases. It then provides `raw_atomic_long_*()` wrappers for reads, stores, arithmetic, bitwise operations, exchange/compare-exchange, conditional updates, and common tests such as decrement-and-test or increment-not-zero. The instrumented `atomic_long_*()` family is supplied through `atomic-instrumented.h`, which delegates back to these raw operations.

## Control Flow
Every function is an inline architecture switch. On 64-bit builds it calls the matching `raw_atomic64_*()` primitive; on 32-bit builds it calls the matching `raw_atomic_*()` primitive. There is no loop or complex branching inside the wrappers beyond `#ifdef CONFIG_64BIT`; atomicity, retry behavior, and memory barriers are entirely inherited from the selected raw primitive.

## State And Persistence
The file persists no state. It mutates caller-provided `atomic_long_t` storage and returns either the original value, updated value, boolean success, or void depending on the operation. Width is persistent in the ABI of the compiled object: 64-bit kernels get 64-bit atomic long operations, while 32-bit kernels get 32-bit operations.

## Dependencies And Integration Points
It includes `linux/compiler.h` and `asm/types.h` and relies on the raw `atomic_t` and `atomic64_t` APIs already being available in the include sequence. It is generated by `scripts/atomic/gen-atomic-long.sh`. Kernel subsystems use it when a counter or flag must match native long size, including refcount-like and pointer-adjacent accounting code.

## Risks
The key risk is assuming `atomic_long_t` is always 64-bit; on 32-bit builds it is only as wide as `atomic_t`. Another risk is adding a raw atomic operation without updating this generated layer and the instrumented layer consistently. Since this is a raw API, callers in normal instrumentable code should prefer the non-raw `atomic_long_*()` wrappers so sanitizers can see accesses.

## Test Signals
Build both `CONFIG_64BIT=y` and 32-bit configurations to catch type and format assumptions. Atomic API generation checks should show this file is reproducible. Concurrency tests that exercise counters near 32-bit overflow boundaries are useful where Ceph or VFS code stores sizes, refs, or state in atomic longs.
