# sources/distributed-fs/ceph-client/include/uapi/linux/nfsd_netlink.h

Purpose: generated UAPI netlink contract for the kernel NFS server generic-netlink family named `nfsd`, version `1`. The header is generated from `Documentation/netlink/specs/nfsd.yaml` by YNL tooling and exposes stable numeric command and attribute identifiers used by userspace administration and observability tools to query and configure nfsd state.

Important APIs/types/functions: this file defines only constants and anonymous enums, not C functions or structs. `NFSD_FAMILY_NAME` and `NFSD_FAMILY_VERSION` identify the generic-netlink family. Attribute sets include `NFSD_A_RPC_STATUS_*` for active RPC status records, `NFSD_A_SERVER_*` for server thread/time/scope/FH-key settings, `NFSD_A_VERSION_*` for NFS protocol version entries, `NFSD_A_SERVER_PROTO_VERSION` for nested protocol-version lists, `NFSD_A_SOCK_*` and `NFSD_A_SERVER_SOCK_*` for listener socket address/transport state, and `NFSD_A_POOL_MODE_*` for pool mode and pool count. `NFSD_CMD_*` enumerates operations: RPC status get, thread set/get, version set/get, listener set/get, and pool-mode set/get. Each attribute enum reserves value 0 implicitly and publishes a `*_MAX` derived from an internal `__*_MAX` sentinel for policy-table sizing.

Control flow: userspace does not call functions in this header; it builds generic-netlink messages using the family name and one `NFSD_CMD_*` command, then supplies or receives the command-specific attributes. The practical flows are request/response reads for `*_GET` commands and state-mutating requests for `THREADS_SET`, `VERSION_SET`, `LISTENER_SET`, and `POOL_MODE_SET`. RPC status responses are record-like messages carrying XID, flags, program, version, procedure, service time, IPv4/IPv6 source/destination addresses, ports, and compound operation metadata. Configuration flows depend on nested or repeated attributes for versions and sockets, as implied by the separate version, server-proto, socket, and server-socket attribute namespaces.

State and persistence behavior: the header itself holds no state. It names controls over live nfsd kernel state: thread counts, grace and lease times, server scope, file-handle key material, protocol versions, listener sockets, and pool mode. Persistence is external to this header and depends on nfsd/sysadmin tooling; netlink operations update or observe the kernel service state at runtime.

Dependencies and integration points: depends only on generated UAPI naming conventions and the Linux generic-netlink/YNL ecosystem. The kernel-side nfsd netlink implementation must keep its attribute policies, dump handlers, and command handlers in lockstep with these IDs. Userspace clients should prefer the YAML/YNL schema or this header rather than hard-coded numbers. Integration points include nfsd administrative tools, monitoring agents that inspect in-flight RPCs, service managers that set listener/thread configuration, and tests that validate UAPI compatibility.

Risks: because this is UAPI, renumbering any enum member would break existing userspace. Gaps are minimal, so additions must be appended before the relevant sentinel. Attribute type/endianness/length expectations are not visible in this header and must be read from the YAML spec or kernel policies, which creates risk for hand-written clients. Generated-file drift is also a risk: manual edits would be overwritten or become inconsistent with `nfsd.yaml`.

Test signals: compile tests should ensure the header is self-contained for userspace inclusion. Netlink/YNL tests should verify that `NFSD_FAMILY_NAME` resolves, every command accepts the documented attribute set, `*_MAX` values match kernel policies, GET dumps return parseable records, and SET commands reject missing or incorrectly typed attributes without altering nfsd state. Compatibility tests should exercise old clients after appending new attributes or commands.
