# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/ivytown/uncore-interconnect.json

## Purpose

This file is a perf PMU event catalog for Intel IvyTown x86 uncore interconnect monitoring. It is JSON data, not executable code. Its 385 event objects describe named hardware events that `tools/perf/pmu-events/jevents.py` converts into generated `pmu-events.c` tables during the perf build.

The file covers uncore traffic around the IvyTown interconnect fabric:

- `IRP`: 37 events for inbound/outbound IRP queues, cache read/write occupancy, tickles, write ordering stalls, and transactions.
- `QPI`: 200 events for QPI link clocks, link power states, flits, message classes, virtual-network credits, stalls, CRC behavior, and Tx/Rx queue occupancy.
- `R3QPI`: 127 events for ring-to-QPI bridge credits, ring lane use, ingress occupancy, NACKs, VNA/VN0/VN1 credits, and CBox/Home Agent/QPI credit exhaustion.
- `UBOX`: 21 events for uncore box clocks, event messages, filter matches, lock cycles, PHOLD cycles, RACU requests, and U2C events.

`arch/x86/mapfile.csv` maps `GenuineIntel-6-3E,v24,ivytown,core`, so these events are selected for IvyTown-family systems through the normal perf PMU event table lookup path.

## Data Shape and Important Fields

Each array item is a PMU event definition. All 385 entries include:

- `EventName`: the perf alias, such as `UNC_Q_RxL_FLITS_G1.DRS_DATA`.
- `Counter`: the allowed programmable counter indexes. This file uses `0`, `0,1`, `0,1,2`, and `0,1,2,3`.
- `PerPkg`: always `1`, marking events as package scoped.
- `Unit`: the hardware block name used by `jevents.py` to derive the Linux PMU name.

Common optional fields are:

- `EventCode`: the hardware event select value. 374 entries have it. Clocktick-style or special encoded entries can omit it, in which case `jevents.py` defaults the event code to `0`.
- `UMask`: the unit mask appended to the event encoding when nonzero. 293 entries have it.
- `BriefDescription`: short text for `perf list`. 343 entries have it.
- `PublicDescription`: longer user-facing text. 350 entries have it.

The `Unit` values integrate through `jevents.py::unit_to_pmu()`:

- `IRP` becomes `uncore_irp`.
- `QPI` becomes `uncore_qpi`.
- `R3QPI` becomes `uncore_r3qpi`.
- `UBOX` becomes `uncore_ubox`.

`jevents.py` lowercases `EventName`, normalizes descriptions with `fixdesc()`, stores `PerPkg`, and builds the event string from `EventCode` plus nonzero fields such as `UMask`. For example, an entry with `EventCode: "0x13"` and `UMask: "0x2"` becomes an event encoding like `event=0x13,umask=0x2` in the generated table.

## Event Families

The IRP section focuses on request pipeline pressure and write/read cache behavior. It includes address-match conflict merge/stall counts, cache ownership/read/write occupancy, pending write ACK occupancy, RxR AK/BL ingress fullness/inserts/occupancy, tickle effects, transaction class counts, TxR credit stalls, outbound data inserts, outbound request occupancy, and write ordering stalls.

The QPI section is the largest. It covers:

- Clock and power residency events, including `UNC_Q_CLOCKTICKS`, `UNC_Q_RxL0_POWER_CYCLES`, `UNC_Q_RxL0P_POWER_CYCLES`, `UNC_Q_TxL0_POWER_CYCLES`, `UNC_Q_TxL0P_POWER_CYCLES`, and `UNC_Q_L1_POWER_CYCLES`.
- Direct-to-core success and failure breakdowns.
- QPI message class aliases under `UNC_Q_MESSAGE.*` for DRS, HOM, NCB, NCS, NDR, and SNP traffic. These entries share event code `0x38` and carry no `UMask` or descriptions, so their correctness depends on the platform PMU encoding semantics for that selector.
- Rx link flits, inserts, occupancy, cycles-not-empty, stalls, CRC errors, and credits across VN0, VN1, and VNA.
- Tx link flits, queue inserts/occupancy, bypass events, CRC credit pressure, and TxR credit occupancy/acquisition by channel and virtual network.

The R3QPI section describes the bridge between ring resources and QPI resources. It includes empty-credit signals for CBox, Home Agent, and QPI paths, ring AD/AK/BL/IV usage by direction and lane, RxR inserts/occupancy by message class, clockwise/counter-clockwise NACKs, and VNA/VN0/VN1 credit acquisition, use, and rejection.

The UBOX section provides package-level uncore signals: UBox clockticks, event messages such as doorbells/MSI/IPI/VLW, filter match enable/disable events, lock and PHOLD cycles, RACU requests, and U2C event classes.

## Control Flow and Integration

There is no in-file control flow. Runtime behavior comes from the perf PMU event pipeline:

1. The perf build sees `tools/perf/pmu-events/Build`, where `$(PMU_EVENTS_C)` is generated by running `pmu-events/jevents.py $(JEVENTS_ARCH) $(JEVENTS_MODEL) $(OUT_DIR)`.
2. `jevents.py` scans architecture/model JSON files under `pmu-events/arch`, including this IvyTown file when the requested model is `ivytown`.
3. Each JSON object is converted to an internal event object. `EventName` becomes the alias name, `Unit` becomes the PMU name, `EventCode` initializes the `event=` selector, and `UMask` and other supported keys are appended as config terms.
4. Generated `pmu-events.c` exposes event tables used by perf's PMU lookup code.
5. User-facing commands such as `perf list` and `perf stat -e <alias>` discover these aliases through the generated tables and match them against available uncore PMUs on IvyTown systems.

Because this file is source data for generated C, changes do not affect runtime until perf regenerates and rebuilds the PMU event table.

## State and Persistence

The file is persistent static metadata. It does not store counters, runtime state, user configuration, or measured values. Its durable effects are:

- It contributes to generated build artifacts, primarily `pmu-events.c`.
- It controls the event aliases and descriptions that persist in a built perf binary.
- It marks every event as `PerPkg: "1"`, which affects how perf should treat aggregation for package-scoped uncore PMUs.

The actual hardware counter state lives in the kernel PMU drivers and hardware registers at runtime. This JSON only describes how perf should name and encode those counters.

## Dependencies

Primary dependencies are the perf PMU event tooling and the Linux perf uncore PMU naming convention:

- `tools/perf/pmu-events/jevents.py` parses this JSON and maps schema keys into generated C event records.
- `tools/perf/pmu-events/Build` wires the JSON corpus into the perf build.
- `tools/perf/pmu-events/arch/x86/mapfile.csv` selects the `ivytown` model for Intel family/model `GenuineIntel-6-3E`.
- `tools/perf/util/pmu.c`, `tools/perf/util/pmu.h`, and related PMU lookup code consume the generated tables.
- `tools/perf/builtin-list.c` and the Python perf bindings expose `EventName`, `BriefDescription`, `PublicDescription`, `ScaleUnit`, and `Unit` style metadata to users.

This file has no dependency on Ceph or distributed filesystem logic despite living under the vendored `ceph-client/tools/perf` tree.

## Risks and Edge Cases

- Missing optional fields are expected but still risky. Eleven events omit `EventCode`, 92 omit `UMask`, 42 omit `BriefDescription`, and 35 omit `PublicDescription`. `jevents.py` tolerates this, but alias usability and generated encodings depend on whether those omissions are intentional hardware semantics.
- The 32 `UNC_Q_MESSAGE.*` entries all use `EventCode: "0x38"` without `UMask`, descriptions, or filters. If these aliases require extra match-mask programming outside the standard event string, they may be hard to validate from the JSON alone.
- Some descriptions contain typos or ambiguous wording, for example `occuapancy` and grammar errors. These do not break parsing but affect `perf list` quality.
- Event names encode a large amount of semantic structure in dotted suffixes. Duplicate names are absent, but future additions should keep aliases stable because users and metrics can reference them directly.
- Counter constraints matter. QPI entries generally allow counters `0,1,2,3`; IRP entries generally allow `0,1`; UBOX includes entries constrained to counter `0`. Incorrect `Counter` values can make perf schedule events onto unsupported counters.
- Unit names are schema-sensitive. `IRP`, `QPI`, `R3QPI`, and `UBOX` are not in the explicit `unit_to_pmu()` table, so they rely on the fallback `uncore_<unit.lower()>` behavior. Renaming a unit changes the generated PMU name.

## Test Signals

Useful validation signals for this file are:

- JSON syntax validation with `jq empty sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/ivytown/uncore-interconnect.json`.
- Schema sanity checks: all entries should have `EventName`, `Counter`, `PerPkg`, and `Unit`; duplicate `EventName` values should remain absent.
- Regenerating perf PMU events through the `tools/perf/pmu-events/Build` rule should succeed without `jevents.py` parse errors.
- `tools/perf/tests/pmu-events.c` exercises generated PMU event tables and alias comparison behavior, including expected handling when `PublicDescription` is absent.
- On IvyTown hardware, `perf list` should show these aliases under the derived uncore PMUs, and `perf stat` should be able to schedule representative aliases from each unit, such as `uncore_irp/UNC_I_TRANSACTIONS.READS/`, `uncore_qpi/UNC_Q_CLOCKTICKS/`, `uncore_r3qpi/UNC_R3_CLOCKTICKS/`, and `uncore_ubox/UNC_U_CLOCKTICKS/` using the syntax accepted by that perf version.
