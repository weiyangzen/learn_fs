# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/icelakex/uncore-memory.json

## Purpose

`uncore-memory.json` defines 186 Ice Lake Xeon uncore memory-controller PMU events. It supplies symbolic aliases for integrated memory controller and free-running iMC counters so perf users can inspect DRAM, persistent memory, request queue, scheduling-buffer, throttling, refresh, page policy, and 2-level-memory tag behavior without writing raw event encodings. The file is part of the Ice Lake X model event set selected through the x86 `mapfile.csv` and consumed by the perf PMU event generator.

## Schema And API Surface

Each entry is a perf PMU event object. The stable fields are `EventName`, `EventCode`, `UMask`, `BriefDescription`, `PublicDescription`, and, for uncore routing, `Unit`. Optional hardware-selection and status fields include `Counter`, `PerPkg`, `Experimental`, and `Deprecated`. The dominant `Unit` values are `iMC` and `imc_free_running`; this distinction controls which uncore PMU instance perf binds the alias to. Representative aliases include `UNC_M_CAS_COUNT.RD`, `UNC_M_CAS_COUNT.WR`, `UNC_M_CLOCKTICKS`, `UNC_M_CLOCKTICKS_FREERUN`, `UNC_M_PMM_CMD1.RD`, `UNC_M_RPQ_INSERTS.PCH0`, `UNC_M_WPQ_OCCUPANCY_PCH1`, and `UNC_M_TAGCHK.NM_RD_HIT`.

## Control Flow And Integration

At build time, the perf make rules copy this JSON to the output `pmu-events/arch` tree and include it in `JEVENTS_DEPS`; `jevents.py` parses the array and emits C table entries for Ice Lake X. At runtime, perf matches the host CPU to the Ice Lake X table, builds aliases for the `iMC` and `imc_free_running` units, and lets `perf list` or `perf stat` resolve names such as `uncore_imc/UNC_M_CAS_COUNT.RD/` depending on the PMU naming generated by the kernel. There is no in-file control flow; behavior is determined by the generator, PMU alias resolver, and the kernel uncore PMU driver.

## State And Persistence

The file persists a static hardware contract: event code, umask, counter restrictions, per-package scope, and descriptive text. It has no mutable state. Runtime state lives in hardware counters and perf sampling sessions. `PerPkg` entries represent package-scoped counting semantics, while channel-specific suffixes such as `PCH0` and `PCH1` distinguish paths in the memory controller.

## Dependencies

The data depends on the Intel Ice Lake Xeon uncore PMU programming model and on perf's JSON schema support in `pmu-events/jevents.py`. Generated output is consumed by perf's event-listing and metric infrastructure. The file also indirectly supports metrics in other Ice Lake X JSON files that may reference memory-controller aliases by name.

## Risks

The highest risk is silent semantic drift: an incorrect `Unit`, `Counter`, `EventCode`, or `UMask` can generate a valid alias that counts the wrong hardware condition. The file mixes standard iMC programmable counters with `imc_free_running` events, so moving an event to the wrong unit would make it unavailable or misrouted. Queue occupancy and latency descriptions rely on paired events such as insert counts, non-empty cycles, and accumulated occupancy; renaming one side can break downstream formulas. Experimental or deprecated markings are also meaningful because tooling and users may filter or avoid those aliases.

## Test Signals

Useful checks are `jq` JSON parsing, successful `pmu-events/jevents.py` generation, `perf list` on an Ice Lake Xeon system showing `UNC_M_*` aliases under the expected uncore PMUs, and `perf stat` smoke tests for common counters such as CAS read/write counts and clock ticks. Formula-level sanity tests should compare derived queue occupancy or bandwidth values against known memory traffic generators.
