# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/ivytown/uncore-cache.json

## Purpose
This JSON file defines the IvyTown x86 uncore cache/home-agent PMU event topic for perf. It is static event metadata consumed by the perf PMU event generator, not executable code. The complete 3,446-line file was read, containing 349 event records: 157 `CBOX` records for cache-box/ring/TOR behavior and 192 `HA` records for home-agent, directory, memory-credit, snoop-response, and HA ring behavior. Every record is marked `PerPkg: "1"`, so the intended aggregation scope is package-level uncore counting.

## Important APIs, Types, and Functions
The important API is the perf PMU JSON schema exported to generated `struct pmu_event` rows. Records use `EventName`, `EventCode`, optional `UMask`, `Unit`, `Counter`, `PerPkg`, `BriefDescription`, and often `PublicDescription`. There are no local functions or classes. The main CBOX aliases include `UNC_C_CLOCKTICKS`, `UNC_C_LLC_LOOKUP`, `UNC_C_LLC_VICTIMS`, `UNC_C_MISC`, `UNC_C_QLRU`, `UNC_C_RING_*_USED`, `UNC_C_RING_BOUNCES`, `UNC_C_RxR_*`, `UNC_C_TOR_INSERTS`, `UNC_C_TOR_OCCUPANCY`, and `UNC_C_TxR_*`. The main HA aliases include `UNC_H_CLOCKTICKS`, `UNC_H_REQUESTS`, `UNC_H_DIRECTORY_LOOKUP`, `UNC_H_DIRECTORY_UPDATE`, `UNC_H_BT_*`, `UNC_H_TRACKER_CYCLES_NE`, `UNC_H_SNOOP_RESP`, `UNC_H_SNP_RESP_RECV_LOCAL`, `UNC_H_TAD_REQUESTS_G*`, `UNC_H_IMC_*`, `UNC_H_RPQ_*`, `UNC_H_WPQ_*`, `UNC_H_RING_*_USED`, and `UNC_H_TxR_*`.

## Control Flow, State, and Persistence
Control flow is external to this file. The perf build includes JSON files through `tools/perf/pmu-events/Build`, then `tools/perf/pmu-events/jevents.py` parses this file into generated `pmu-events.c`. In that generated table, JSON fields become `struct pmu_event` content declared in `pmu-events.h`: aliases become `name`, encoded `EventCode`/`UMask`/other format fields become the low-level `event` string, descriptions become `desc`/`long_desc`, `Unit` steers PMU matching, and `PerPkg` becomes the `perpkg` boolean. Runtime lookup is then driven by the x86 mapfile entry `GenuineIntel-6-3E,v24,ivytown,core`, so perf can expose these aliases on matching IvyTown systems.

The file has no mutable state and performs no persistence itself. Persistence is source-control storage of this JSON plus the generated perf event table in build outputs. Hardware counter state lives in the kernel uncore PMU drivers and the processor PMON registers selected by perf when a user runs commands such as `perf list` or `perf stat -e <alias>`.

## Dependencies and Integration Points
This file depends on the perf PMU event JSON contract, `jevents.py`, `pmu-events.h`, the x86 `mapfile.csv` IvyTown model mapping, and kernel support for IvyTown uncore PMUs that expose CBOX and HA units. It integrates with `perf list` discoverability, `perf stat` event alias resolution, generated event table searches such as `pmu_events_table__find_event`, and package-level uncore aggregation. It also integrates conceptually with adjacent IvyTown PMU topics for memory, interconnect, power, and QPI behavior because many HA records describe iMC queue credits, QPI ingress credits, TAD regions, directory state transitions, and ring traffic.

## Event Semantics and Control Relationships
The CBOX section models cache-box activity around LLC lookups/victims, queue occupancy, ring use, ingress retries/starvation, TOR inserts, TOR occupancy, and egress injection. Several families form paired control relationships: occupancy events such as `UNC_C_RxR_OCCUPANCY.*` and `UNC_C_TOR_OCCUPANCY.*` accumulate entries per cycle, while insert/retry events such as `UNC_C_RxR_INSERTS.*`, `UNC_C_TOR_INSERTS.*`, and `UNC_C_RxR_*_RETRY.*` count attempts or failures. The descriptions repeatedly warn that opcode/NID filters require programming `Cn_MSR_PMON_BOX_FILTER` fields, and LLC lookup events require a filter mask/state selection or they count nothing.

The HA section tracks requests once they reach the home agent. It covers backup tracker occupancy, home tracker activity, directory lookup/update states, direct-to-core behavior, HA-to-iMC reads/writes, RPQ/WPQ credit exhaustion, QPI ingress credits, snoop responses, TAD region distribution, and outbound AD/AK/BL ring egress pressure. These events are useful for deriving higher-level signals such as average queue occupancy or lifetime by combining occupancy/not-empty/insert counters, but this JSON only defines raw aliases; formulas and grouping are left to users or metrics files.

## Risks
The main risks are data correctness and alias semantics. Many event families reuse one `EventCode` with many `UMask` combinations, especially CBOX TOR inserts/occupancy, C/HA ring-use filters, HA directory states, snoop responses, and HA egress scheduler filters. A copied or mistyped mask can silently measure a different hardware condition. Some aliases are intentionally synonymous or near-duplicate, such as `IRQ_REJ` and `IRQ_REJECTED`, and several descriptions contain historical wording or typos; consumers should not infer semantics from English text alone when masks differ. Counter constraints matter: some occupancy events are limited to counter 0 or only counters 2,3, while broad clock/HA events allow counters 0-3. The special CBOX occupancy handling is particularly sensitive because `UNC_C_COUNTER0_OCCUPANCY` filters counter-0 occupancy through other counters.

## Test Signals
Useful validation starts with JSON parsing, for example `jq length` should report 349 and grouping by `Unit` should report 157 `CBOX` and 192 `HA` records. Build-time signals are successful `jevents.py` generation and compilation of generated `pmu-events.c` without schema errors. Repository tests that exercise generated PMU event tables, especially `tools/perf/tests/pmu-events.c`, are relevant smoke coverage. Runtime signals on IvyTown hardware include `perf list` showing representative aliases such as `UNC_C_TOR_INSERTS.ALL`, `UNC_C_TOR_OCCUPANCY.ALL`, `UNC_H_REQUESTS.READS`, and `UNC_H_DIRECTORY_LOOKUP.ANY`, plus `perf stat` sanity checks where broad aggregate masks exceed or equal narrower subevents under the same workload and counter constraints.
