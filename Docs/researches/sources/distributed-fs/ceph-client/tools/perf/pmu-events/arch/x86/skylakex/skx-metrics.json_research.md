# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/skylakex/skx-metrics.json

Purpose: Defines the Skylake Xeon x86 metric catalog consumed by Linux perf's PMU event pipeline. The file is a 275-entry JSON array of derived metrics, not executable code, but it becomes a user-facing perf API after `tools/perf/pmu-events/jevents.py` converts it into generated `pmu_metric` C tables. The x86 mapfile selects this directory for `GenuineIntel-6-55-[01234]` core PMUs, so these metric names and expressions back `perf list --metrics`, `perf stat -M ...`, and the Python perf metric listing APIs on SkylakeX-class systems.

Important schema and APIs: Each object centers on `MetricName` and `MetricExpr`, with `BriefDescription` always present and optional `PublicDescription`, `MetricGroup`, `ScaleUnit`, `MetricThreshold`, `MetricConstraint`, and `MetricgroupNoGroup`. `MetricGroup` is a semicolon-separated tag list used for discovery and grouped selection; major groups include `TopdownL1` through `TopdownL6`, `tma_*_group`, `Backend`, `Frontend`, `MemoryBW`, `MemoryTLB`, `Power`, `SoC`, `HPC`, `Flops`, `smi`, and `transaction`. `ScaleUnit` drives presentation and includes percent, per-instruction ratios, MB/s, GHz, ns, SMI count, and TSX cycle units. `MetricConstraint` values are limited here to `NO_GROUP_EVENTS` and `NO_GROUP_EVENTS_NMI`; `jevents.py` maps those strings onto `enum metric_event_groups` in `pmu-events.h`, and `util/metricgroup.c` uses them to decide whether events may be scheduled as a group.

Metric coverage: The file starts with direct operational metrics such as package/core C-state residency, CPI, operating frequency, CPU utilization, DTLB/ITLB miss-per-instruction ratios, LLC/NUMA locality, DDR/IO/UPI bandwidth, uncore frequency, SMI count/cycles, and TSX transaction metrics. Most of the file is Intel Top-Down Microarchitecture Analysis metadata. The top-level TMA metrics are `tma_retiring`, `tma_bad_speculation`, `tma_frontend_bound`, and `tma_backend_bound`, then the graph expands into frontend latency/bandwidth, branch resteers/mispredicts, machine clears, core bound, memory bound, L1/L2/L3/DRAM bound, DTLB/STLB page walk detail, port utilization, FP/vector usage, microcode sequencer, locks, false sharing, NUMA remote/local memory, and bottleneck summary estimates.

Expression dependencies: `MetricExpr` formulas reference architectural event aliases such as `INST_RETIRED.ANY`, `CPU_CLK_UNHALTED.*`, `UOPS_*`, `IDQ*`, `BR_*`, `MEM_LOAD_RETIRED.*`, `MEM_INST_RETIRED.*`, `CYCLE_ACTIVITY.*`, `EXE_ACTIVITY.*`, `FP_ARITH_INST_RETIRED.*`, and `DTLB_*`/`ITLB_*`. They also depend on uncore PMUs including CHA, iMC, IIO, UPI, RAPL power, cstate, and MSR aliases such as `msr@tsc@`, `msr@aperf@`, and `msr@smi@`. Perf expression runtime variables are used heavily: `duration_time`, `#SMT_on`, `#core_wide`, `#num_cores`, `#num_packages`, `#num_dies`, and `#num_cpus_online`. Many TMA entries also reference other `tma_*` metrics by name; `metricgroup__parse_groups()` resolves this recursively, records referenced metric expressions, and builds a combined event context where possible.

Control flow: At build time, `jevents.py` walks the PMU event tree, reads this JSON, normalizes JSON metric fields into generated C strings, converts constraints into enum values, and emits metric tables alongside the other SkylakeX event files. At runtime, perf locates the active metrics table through CPUID mapping, matches metric names or groups requested by the user, parses the expression dependency graph, resolves each identifier to PMU aliases or runtime variables, schedules the required event list, evaluates expressions over measured counts, applies units, and checks threshold expressions for supported outputs. The runtime path is mainly `util/metricgroup.c`, `util/expr.c`, and `util/stat-shadow.c`, with listing support in `builtin-list.c` and Python exposure through `util/python.c`.

State and persistence behavior: The JSON has no mutable state. Its persisted effects are the generated metric table compiled into perf and the stable names exposed to users and scripts. Changes to `MetricName`, `MetricGroup`, units, thresholds, or expressions are therefore compatibility-sensitive even though they are data changes. The file also encodes a durable dependency graph: high-level metrics such as `tma_bottleneck_data_cache_memory_latency` only work if all lower-level metric names and event aliases remain resolvable.

Integration points: This metric file relies on sibling SkylakeX event definitions in `cache.json`, `counter.json`, `floating-point.json`, `frontend.json`, `memory.json`, `other.json`, `pipeline.json`, `uncore-cache.json`, `uncore-interconnect.json`, `uncore-io.json`, `uncore-memory.json`, `uncore-power.json`, and `virtual-memory.json`, plus `metricgroups.json` for group descriptions. It integrates with the x86 mapfile for CPU selection, `pmu-events/README` conventions for JSON layout, `pmu-events.h` for generated metric structures, `builtin-stat.c` for `-M` execution, `builtin-list.c` for metric listing, and `tools/perf/python/ilist.py` for Python-side browsing.

Risks: The formulas are sensitive to exact event spelling, PMU naming, raw event syntax like `cha@...config1...@`, and perf expression grammar. Many expressions divide by counts that can be zero or noisy on short or idle workloads, including retired instructions, cache misses, page walks, branch counts, DSB/MITE counts, and TSX events guarded only by `has_event(...)` in some cases. Uncore, RAPL, cstate, MSR, SMT, and TSX availability varies by host, kernel configuration, permissions, and BIOS settings. Metrics using `NO_GROUP_EVENTS_NMI` may change scheduling behavior depending on the NMI watchdog, while formulas without grouping can be affected by multiplexing. Thresholds are numerous and often depend on computed metrics; a syntax or dependency error can make bottleneck highlighting misleading even when raw metric evaluation still builds.

Test signals: Build-time validation should include JSON parsing, `jevents.py` generation, and the normal perf build so expression IDs and generated structures are checked. Unit and integration coverage should include `perf test pmu-events`, `perf test parse-metric`, and smoke runs of `perf list --metrics` on an x86 build. Runtime checks on SkylakeX-like hardware should exercise `perf stat -M tma_retiring,tma_frontend_bound,tma_backend_bound,tma_memory_bound`, bandwidth metrics such as `memory_bandwidth_total` and `upi_data_receive_bw`, power/cstate metrics, `smi`, and `transaction`. Useful failure signals are missing aliases, event scheduling errors, unexpected multiplexing, NaN or infinite metric output, absent uncore PMUs, thresholds that never trigger, and differences between SkylakeX and Cascade LakeX CPUID mapping behavior.
