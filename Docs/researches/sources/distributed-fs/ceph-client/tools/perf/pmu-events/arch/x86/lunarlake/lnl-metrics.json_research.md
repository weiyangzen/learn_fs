## sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/lunarlake/lnl-metrics.json

**Purpose:** Lunar Lake metric metadata for `perf stat -M` and metric groups. The file contains 331 `pmu_metric` records covering package/core C-state residency, SMI accounting, Level 1 through deeper topdown microarchitecture analysis, frontend/backend/bad-speculation/retiring breakdowns, branch and machine-clear diagnostics, memory hierarchy and TLB bottlenecks, port utilization, arithmetic and vector mixes, FLOPs, system frequency/utilization, uncore frequency, and derived bottleneck estimates.

**Important APIs, types, and records:** Each JSON object is parsed by `jevents.py` as a `JsonEvent` with `MetricName`, `MetricExpr`, optional `MetricGroup`, `MetricThreshold`, `ScaleUnit`, `Unit`, `MetricgroupNoGroup`, `DefaultMetricgroupName`, `MetricConstraint`, `BriefDescription`, and `PublicDescription`. `MetricExpr` is parsed and simplified by `metric.ParsePerfJson()`, and `read_json_events()` may rewrite formulas in terms of other metrics through `metric.RewriteMetricsInTermsOfOthers()`. The file has 236 `cpu_core` metrics, 87 `cpu_atom` metrics, and 8 unitless/system metrics. Reused metric names across units are intentional: examples include `tma_backend_bound`, `tma_bad_speculation`, `tma_branch_mispredicts`, `tma_cisc`, `tma_core_bound`, `tma_frontend_bound`, `tma_icache_misses`, `tma_itlb_misses`, `tma_machine_clears`, and `tma_retiring`.

**Metric families:** Unitless records include C-state residency metrics such as `C10_Pkg_Residency`, `C1_Core_Residency`, `C6_Core_Residency`, SMI metrics `smi_cycles` and `smi_num`, and package/core power style percentages. Atom metrics use `cpu_atom@...@` references and an 8-slot denominator pattern such as `8 * cpu_atom@CPU_CLK_UNHALTED.CORE@` for topdown fractions. Atom records cover Topdown L1/L2/L3, instruction mix, branch mix, buffer stalls, memory execution bound, load/store bound, machine clears, FP/uop mix, and system utilization. Core metrics use hybrid Core topdown counters like `cpu_core@topdown\\-fe\\-bound@`, `cpu_core@topdown\\-be\\-bound@`, `cpu_core@topdown\\-retiring@`, and many named PMU events from sibling JSON files. Core records are much broader, including L4-L6 TMA breakdowns, bottleneck estimates prefixed `tma_bottleneck_*`, memory latency/bandwidth decomposition, port utilization, vector/shuffle/divider metrics, false sharing, streaming stores, STLB page-size splits, and uncore/system rates such as `UNCORE_FREQ`.

**Control flow and integration:** During generation, `jevents.py` reads this file after event-topic JSON files, parses every expression, and emits `struct pmu_metric` rows grouped by PMU. `MetricGroup` strings determine `perf list metricgroups` and `perf stat -M <group>` visibility; `DefaultMetricgroupName` and `MetricgroupNoGroup` control default grouping behavior; `MetricConstraint` strings such as `NO_GROUP_EVENTS`, `NO_GROUP_EVENTS_NMI`, and `NO_THRESHOLD_AND_NMI` are converted into internal event-grouping enums. At runtime, perf expands a selected metric into referenced PMU events, MSR pseudo-events (`msr@tsc@`, `msr@smi@`, `msr@aperf@`), cstate pseudo-events, duration variables, constants such as `#num_dies`, and recursively referenced metric names.

**State and persistence behavior:** Metrics are static formula metadata persisted in generated `pmu-events.c`; they hold no runtime state. Runtime metric values are derived from current counter reads, wall-clock `duration_time`, MSR/cstate snapshots, multiplexing, and PMU scheduling. Thresholds are static advisory expressions and are not parsed by `jevents.py` because threshold precedence differs from the metric-expression grammar.

**Dependencies:** Strongly depends on the complete Lunar Lake event directory, not just this subset. Atom formulas reference events such as `TOPDOWN_BE_BOUND.*`, `TOPDOWN_FE_BOUND.*`, `TOPDOWN_BAD_SPECULATION.*`, `TOPDOWN_RETIRING.ALL`, `FP_*`, `BR_*`, `LD_HEAD.*`, `MEM_BOUND_STALLS_*`, `MEM_SCHEDULER_BLOCK.*`, `MACHINE_CLEARS.*`, `UOPS_RETIRED.*`, and `CPU_CLK_UNHALTED.*`. Core formulas reference `frontend.json` entries (`DECODE.LCP`, `IDQ.*`, `IDQ_BUBBLES.*`, `FRONTEND_RETIRED.*`, `ICACHE_TAG.STALLS`), `memory.json` entries (`MACHINE_CLEARS.MEMORY_ORDERING`, `MEM_TRANS_RETIRED.*`, `OCR.*`, `OFFCORE_REQUESTS*`), and many cache, pipeline, branch, floating-point, virtual-memory, uncore, and MSR events. `metricgroups.json` supplies descriptions for group names used here.

**Risks and edge cases:** This file is name-fragile. Any event rename, missing `Unit`, missing sibling JSON record, or typo in `MetricExpr` can break parse-time generation or produce runtime "event not found" failures. Hybrid duplicate metric names require correct `Unit`; otherwise Core and Atom formulas can collapse together or be routed to the wrong PMU. Several formulas divide by event counts or derived sums that may be zero on short runs, idle systems, disabled PMUs, or unsupported counters. Some expressions intentionally use escaped event syntax, qualifiers, and raw modifiers, for example `topdown\\-be\\-bound`, `@R`, `@k`, escaped commas and equal signs, and conditional `if ... else`; mechanical escaping changes are high risk. `MetricConstraint` records are performance and correctness hints for grouping/NMI behavior, so dropping them can change schedulability or accuracy. User-visible typos in metric names, such as `adressaliasing`, may be compatibility-sensitive because users can script against metric names.

**Test signals:** First gate is JSON validity plus `jevents.py` generation because all 331 expressions are parsed. Run perf's PMU metric tests, especially `tools/perf/pmu-events/metric_test.py`, and a full `tools/perf` build that regenerates `pmu-events.c`. Integration smoke tests on Lunar Lake should include `perf list metrics`, `perf list metricgroups`, `perf stat -M TopdownL1`, representative Core metrics such as `tma_frontend_bound`, `tma_memory_bound`, `tma_fetch_latency`, and Atom metrics such as `cpu_atom` topdown and load-store-bound metrics. Runtime tests should watch for unresolved event names, excessive multiplexing via `tma_info_system_mux`, threshold behavior, and divide-by-zero or not-counted outputs on idle or short workloads.
