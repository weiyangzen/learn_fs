# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/emeraldrapids/uncore-io.json

Purpose: Defines Intel Emerald Rapids x86 uncore IO PMU event aliases for `perf`. The file is a JSON array of 375 event records used by the perf `pmu-events` generator to expose package-scoped IIO, M2PCIe, and IIO free-running counters through stable event names such as `UNC_IIO_DATA_REQ_BY_CPU.MEM_READ.PART0` and `UNC_M2P_IIO_CREDITS_USED.NCB_0`.

Important APIs/types/functions: This is data, not executable code. Its public API is the perf PMU event schema: every record has `EventName`, `EventCode`, `Counter`, `BriefDescription`, `PerPkg`, and `Unit`; most records also have `UMask`, `PublicDescription`, and IO-specific filters such as `PortMask` and `FCMask`. The units split into 214 `IIO` programmable events, 152 `M2PCIe` programmable events, and 9 `iio_free_running` counters. `PerPkg: "1"` makes these package-level aliases, while `Counter` constrains scheduling to specific uncore counters, including fixed free-running counter numbers for bandwidth parts and IIO clockticks.

Event surface: `IIO` events cover IO clockticks, PCIe completion-buffer inserts and occupancy, CPU-to-IO and IO-to-CPU data requests, transaction counts, inbound arbitration requests and wins, IOMMU lookup/cache/page-walk behavior, mask-match events, target-class request counts, outbound cache-line/TLP requests, PWT occupancy, and PCIe completion/pass-completion request classes. Many IIO request families are expanded by `PART0` through `PART7`, with `ALL_PARTS` variants when a combined port mask is provided; `MEM_READ`, `MEM_WRITE`, `PEER_READ`, `PEER_WRITE`, and `CMPD` distinguish traffic type.

`M2PCIe` events cover M2P and CMS clockticks, egress ordering blocks, IIO credit acquired/reject/used counts, local and remote peer-to-peer dedicated/shared credit taken/returned/wait behavior, P2P credit occupancy, shared/dedicated credit receipt, ingress RxC queue non-empty cycles and inserts, and egress TxC credits/full/non-empty cycles. These aliases distinguish local M2IOSF agents, remote UPI links, DRS/NCB/NCS traffic classes, and CMS port or PMM block selectors through event names and `UMask` values.

Control flow and integration: At build time, `tools/perf/pmu-events/jevents.py` parses this JSON with the rest of `arch/x86/emeraldrapids` and emits generated perf event tables. `arch/x86/mapfile.csv` maps `GenuineIntel-6-CF` to the `emeraldrapids` directory, so runtime perf lookup selects these aliases on matching CPUs. At runtime, `perf list`, parse-events, and metric code treat each record as a named alias for a unit-scoped hardware encoding. `Unit` selects the PMU namespace (`IIO`, `M2PCIe`, or `iio_free_running`), `EventCode` and `UMask` encode the event, and `PortMask`/`FCMask` provide uncore IO filter terms where supported by the corresponding kernel uncore PMU format files.

State and persistence behavior: The file has no mutable runtime state. Persistence is the source-controlled JSON plus generated C tables included in the perf build. The hardware counters themselves are sampled over a perf measurement interval and are reset or multiplexed according to normal perf event lifecycle. Occupancy and cycle-not-empty aliases are interval accumulators rather than transaction totals, so downstream metrics must combine them with clock or insert counters to compute pressure, utilization, or average residency.

Dependencies: Depends on the perf PMU JSON schema, `jevents.py`, the Emerald Rapids mapfile entry, generated `pmu-events.c`, and Linux uncore PMU drivers that expose compatible IIO, M2PCIe, and free-running IIO PMUs. Semantic correctness depends on Intel Emerald Rapids uncore documentation for IIO port/part topology, PCIe completion buffers, IOMMU/PWT behavior, M2PCIe credit rings, DRS/NCB/NCS classes, UPI remote paths, and CMS ingress/egress queues.

Risks and edge cases: The table is topology-sensitive: `PART0` through `PART7`, M2IOSF agents, UPI links, CMS ports, and IOMMU filter names must line up with the actual socket, device, and lane layout or counts can be empty or misleading. The file marks 288 records as experimental, so names or encodings may be less stable than mature perf aliases. There are 138 records without `PublicDescription`; consumers should tolerate `BriefDescription`-only entries. The table mixes byte-scaled free-running bandwidth counters, request counts, transaction counts, occupancy counts, and cycle counts, so aggregating aliases by name prefix alone can produce invalid metrics. Counter constraints are tight: many IIO records use only counters `2,3` or `0,1,2,3`, M2PCIe occupancy records can be limited to `0,1`, and free-running aliases use fixed counters, so event groups can fail to schedule or multiplex unexpectedly. Descriptions also contain small inconsistencies such as repeated part wording and a PWT note that the low-byte occupancy event undercounts above 255 unless paired with the MSB event.

Test signals: Validate JSON syntax with `jq empty` and schema coverage for required perf keys. Build perf with PMU events enabled and confirm the generated tables include representative aliases from all three units. On Emerald Rapids hardware, `perf list` should show examples such as `UNC_IIO_CLOCKTICKS`, `UNC_IIO_DATA_REQ_BY_CPU.MEM_READ.PART0`, `UNC_IIO_IOMMU0.4K_HITS`, `UNC_IIO_PWT_OCCUPANCY`, `UNC_M2P_IIO_CREDITS_USED.NCB_0`, `UNC_M2P_P2P_CRD_OCCUPANCY.ALL`, and `UNC_IIO_BANDWIDTH_IN.PART0_FREERUN`. Runtime smoke tests should drive PCIe/MMIO traffic, IOMMU translation activity, and peer-to-peer or UPI-facing IO paths, then verify that part-specific counters change only for active topology paths and that occupancy/cycle counters correlate with request or insert counters measured in the same interval.
