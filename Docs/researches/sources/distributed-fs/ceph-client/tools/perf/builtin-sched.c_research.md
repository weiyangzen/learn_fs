# sources/distributed-fs/ceph-client/tools/perf/builtin-sched.c

## Purpose

`builtin-sched.c` implements the `perf sched` builtin for scheduler tracing, replay, visualization, latency accounting, time history, and schedstat capture/reporting. It is not a scheduler implementation; it is a perf data consumer/producer that builds higher-level views from scheduler tracepoints and synthetic schedstat records.

The file provides these user-facing subcommands:

- `perf sched record`: invokes `perf record` with scheduler tracepoints selected.
- `perf sched latency`: reads recorded sched tracepoints and reports per-task scheduling latency.
- `perf sched map`: renders an ASCII CPU/task timeline of context switches.
- `perf sched replay`: reconstructs a threaded workload from recorded switch/wakeup events and replays its timing with semaphores and busy waits.
- `perf sched script`: delegates to `cmd_script()`.
- `perf sched timehist`: prints per-context-switch timing history and optional summaries, idle histories, wakeups, migrations, priorities, and callchains.
- `perf sched stats`: records, reports, diffs, or live-displays `/proc/schedstat`-derived synthetic perf records.

## Important APIs, Types, and Functions

Core state is concentrated in `struct perf_sched`. It embeds `struct perf_tool`, stores the current subcommand handler table, CPU switch state, task maps, event counters, replay control fields, latency sorting trees, map rendering options, timehist options, and schedstat session/data handles. Most subcommands reuse the same `perf_tool` but attach different `sample`, `comm`, `fork`, `lost`, and tracepoint handlers.

Replay-specific state uses `struct task_desc` and `struct sched_atom`. `task_desc` tracks a PID, comm, atom list, pthread, semaphores, and per-run CPU usage. `sched_atom` encodes a recorded run, sleep, or wakeup event and can carry a semaphore shared between a sleeping task atom and its waking task atom. `register_pid()`, `get_new_event()`, `add_sched_event_run()`, `add_sched_event_sleep()`, and `add_sched_event_wakeup()` build this replay graph from tracepoints.

Latency state uses `struct work_atom` and `struct work_atoms`. A `work_atom` tracks a single off-CPU/runqueue interval with state, sched-out time, wakeup time, sched-in time, and runtime. `work_atoms` aggregates those atoms per thread, including totals and max latency, and is stored in rb-trees sorted by PID or requested latency dimensions. `thread__get_runtime()`, `thread_atoms_search()`, `thread_atoms_insert()`, `add_sched_out_event()`, `add_sched_in_event()`, `add_runtime_event()`, `perf_sched__merge_lat()`, and `perf_sched__sort_lat()` form the latency pipeline.

Timehist state is stored in `struct thread_runtime`, per-evsel `struct evsel_runtime`, and per-CPU idle `struct idle_thread_runtime`. Important functions include `timehist_update_runtime_stats()`, `timehist_sched_change_event()`, `timehist_sched_wakeup_event()`, `timehist_migrate_task_event()`, `timehist_print_sample()`, and `timehist_print_summary()`. `evsel__save_time()` and `evsel__get_time()` maintain last sched-switch timestamps per CPU, while `get_idle_thread()` creates synthetic idle threads for PID 0 accounting.

Schedstat state uses `struct schedstat_cpu` and `struct schedstat_domain` lists backed by `perf_record_schedstat_cpu` and `perf_record_schedstat_domain` records. `perf_sched__schedstat_record()` synthesizes before/after schedstat records into a perf.data file; `perf_sched__process_schedstat()` reconstructs CPU/domain lists and computes second-pass deltas; `show_schedstat_data()` prints summary and per-CPU/domain data; `perf_sched__schedstat_report()`, `perf_sched__schedstat_diff()`, and `perf_sched__schedstat_live()` implement the report modes. Field expansion for schedstat versions 15, 16, and 17 is generated by including `<perf/schedstat-v15.h>`, `<perf/schedstat-v16.h>`, and `<perf/schedstat-v17.h>` under local macro definitions.

## Control Flow

`cmd_sched()` is the dispatch root. It initializes a `perf_sched`, calls `perf_tool__init()`, installs common event handlers, parses the subcommand, sets the relevant `trace_sched_handler`, parses subcommand-specific options, and calls the selected implementation. `thread__set_priv_destructor(free)` makes normal thread runtime data owned by thread priv storage, while some subcommands override that by storing idle-specific runtime structures on local thread objects.

Event processing for `latency`, `map`, and `replay` flows through `perf_sched__read_events()`. That function opens `input_name` as a read-mode `perf_data`, creates a `perf_session`, initializes symbols from the session environment, installs tracepoint handlers for `sched_switch`, `sched_stat_runtime`, wakeup variants, and `sched_migrate_task`, then runs `perf_session__process_events()`. If `sched_waking` exists, the older `sched_wakeup` path is ignored to avoid duplicate wakeup accounting. Each tracepoint sample goes through `perf_sched__process_tracepoint_sample()`, which invokes the handler stored in the evsel.

`latency` installs `lat_ops`. `latency_switch_event()` updates per-CPU last switch time, creates/finds outgoing and incoming threads, appends sched-out atoms, and turns runnable atoms into completed latency samples on sched-in. `latency_wakeup_event()` marks the latest atom as ready-to-run, except when full-system profiling shows the task was already runnable. `latency_runtime_event()` accumulates `sched_stat_runtime` into the latest atom. After reading all events, `perf_sched__lat()` optionally merges by comm, sorts using requested dimensions, prints per-thread latency rows, prints totals and bad-event diagnostics, and frees the rb-tree contents.

`map` installs only `map_switch_event()`. Each sched switch updates `curr_thread` and `curr_out_thread` arrays, assigns compact two-character names to tasks, applies task-name/CPU/color filters, and prints a CPU-wide visual row. `setup_map_cpus()`, `setup_color_pids()`, and `setup_color_cpus()` parse maps used by rendering, and `perf_sched__map()` frees all maps and thread references afterward.

`replay` installs wakeup, switch, and fork handlers. The read phase constructs task atom lists. `perf_sched__replay()` calibrates busy-loop and sleep overhead, reads the trace, prints atom counts, adds cross-task wakeups to keep all replay threads connected, then creates one pthread per task. `thread_func()` waits behind `start_work_mutex`, executes each atom by busy-spinning, waiting, or posting semaphores, records task-clock usage, and signals completion. `run_one_test()` repeats the synchronized replay and reports elapsed and CPU time. Repeat count zero becomes an effectively infinite loop through `UINT_MAX`.

`timehist` bypasses `perf_sched__read_events()` and configures a richer `perf_tool` in `perf_sched__timehist()`. It sets handlers for samples, mmap/comm/fork/exit/lost/attr/build-id/tracing data, parses CPU and time filters, validates callchain availability, parses priority filters, allocates idle threads, installs tracepoint handlers, and processes events. `timehist_sched_change_event()` is the key callback: it resolves the sample, updates priority, finds the relevant task or idle thread, applies filters, clamps timestamps to the requested time window, accounts run/wait/delay/pre-migration time, optionally prints the row, updates per-thread last state and per-evsel last CPU timestamp, and records the histogram time bounds. Summary printing walks the session's threads plus local idle threads.

`stats record` and `stats live` synthesize schedstat data before and after a workload or until a signal. They may enable `/proc/sys/kernel/sched_schedstats` if it was disabled and reset it on exit. `stats record` writes synthetic records into a perf.data file using `perf_data__write()` and updates the header data size, while `stats live` feeds synthetic records directly into `perf_sched__process_schedstat()` and prints the result without writing perf.data. `stats report` reads one perf.data file. `stats diff` reads two files, defaults to `perf.data.old` and `perf.data`, and compares matching CPU/domain entries.

## State and Persistence Behavior

The command reads `input_name`, defaults through perf's global input handling, and writes `output_name` only for `perf sched stats record`. `__cmd_record()` delegates to `cmd_record()` with a constructed argument vector, so ordinary `perf record` persistence rules apply for captured scheduler traces.

Several state stores are intentionally process-global: `cpu_list`, `user_requested_cpus`, `cpu_bitmap`, idle thread arrays, schedstat linked-list globals, `after_workload_flag`, and `verbose_field`. They are acceptable for a single command invocation but make reentrant use unsafe. The file also mutates global perf state such as `input_name`, `output_name`, `verbose`, `dump_trace`, `symbol_conf`, `callchain_param`, and pager settings.

In-memory lifecycle is mixed. Main perf objects are refcounted through perf helpers (`perf_session__delete()`, `thread__put()`, `perf_cpu_map__put()`, `perf_thread_map__put()`). Replay task atom arrays, semaphore allocations, and task descriptors are not exhaustively freed at the end of the process; this is command-lifetime allocation. Latency `work_atoms` are explicitly freed after printing. Timehist idle threads are freed by `free_idle_threads()`, including their last-thread references. Schedstat list cleanup frees wrapper nodes but does not free nested `cpu_data` and `domain_data` buffers, which is process-lifetime leakage in short-lived command execution.

Schedstat persistence has external side effects: `enable_sched_schedstats()` writes `1` to `/proc/sys/kernel/sched_schedstats`, and `disable_sched_schedstat()` writes `0` if the command enabled it. Signal handlers are deliberately minimal and use `pause()` as the workload boundary.

## Dependencies and Integration Points

The file integrates deeply with perf internals: sessions, evlists, evsels, machines, symbols, callchains, thread maps, CPU maps, perf data headers, synthetic events, target/workload setup, perf record, tracepoint formatting, and perf's parse-options framework. It depends on scheduler tracepoints including `sched_switch`, `sched_stat_runtime`, `sched_wakeup`, `sched_waking`, `sched_wakeup_new`, `sched_migrate_task`, and optional schedstat tracepoints.

Kernel/user integration includes `sys_perf_event_open()` for replay self task-clock counters, `getrusage()` for parent CPU time, pthreads and POSIX semaphores for replay, `prctl(PR_SET_NAME)` for replay thread names, `sysconf(_SC_NPROCESSORS_CONF)`, `/proc/sys/kernel/pid_max`, `/proc/sys/kernel/sched_schedstats`, and tracefs/procfs helpers.

`cmd_sched()` delegates `script` directly to `cmd_script()` and `record` to `cmd_record()`, keeping `perf sched` behavior aligned with generic perf tools. Timehist integrates with symbol resolution, callchain cursors, thread filters from `symbol_conf.pid_list_str`/`tid_list_str`, CPU filters from perf session CPU bitmaps, and the pager. Schedstat output uses CPU domain topology from perf data headers or live `build_cpu_domain_map()`.

## Risks and Edge Cases

Array bounds are guarded inconsistently. Many paths use fixed `MAX_CPUS` arrays and `BUG_ON(cpu >= MAX_CPUS || cpu < 0)`, which aborts rather than reports a recoverable error if malformed data contains a large CPU. `map_switch_event()` computes `cpus_nr = sched->max_cpu.cpu` in non-compact mode, which means the displayed count tracks max CPU index rather than count and can be surprising for sparse or single-CPU traces.

Replay can create one pthread and one perf event fd per recorded task. Large traces can hit file descriptor limits, memory pressure, or scheduler stress; `self_open_counters()` can raise `RLIMIT_NOFILE` only when `--force` is used and privileges allow it. Replay timing is approximate because run atoms are busy loops calibrated against local clock overhead and sleep atoms use semaphores inferred from wakeups, not true kernel scheduling behavior.

Event loss and partial CPU capture directly affect correctness. The code tracks lost events, unordered timestamps, context-switch mismatches, targetless wakeups, multitarget wakeups, and profile-CPU special cases, but output remains best-effort. Wakeup deduplication prefers `sched_waking` over `sched_wakeup`, so traces with unusual event availability need careful validation.

Timehist uses static buffers for comm and priority string formatting and global idle thread storage; this is fine in single-threaded processing but not reusable as a library. Some timehist accounting paths skip idle statistics when filters are active, and callchain display is disabled if `sched_switch` samples lack callchains.

Schedstat processing assumes event order: all first-pass CPU/domain records followed by a second pass beginning with the same initial CPU. Diff mode requires matching CPU IDs and matching domain counts/order between files. The versioned macro includes only handle schedstat versions 15, 16, and 17; newer kernel record versions would print no fields unless the headers and conditionals are updated. Error paths in schedstat allocation can leak partially allocated records.

## Test Signals

Useful behavioral checks include `perf sched record -- sleep 1` followed by `perf sched latency`, `perf sched map`, `perf sched replay -r 1`, and `perf sched timehist --summary`. For timehist, run traces with and without callchains and verify `--cpu`, `--time`, `--pid`, `--tid`, `--prio`, `--wakeups`, `--migrations`, `--idle-hist`, and `--state` filters produce plausible rows and summaries.

Schedstat tests should cover `perf sched stats` live mode with a short signaled workload, `stats record` writing a perf.data file, `stats report -i <file>`, and `stats diff old new`. Test on systems where `kernel.sched_schedstats` starts disabled and enabled to verify reset behavior. Version coverage should include records for schedstat v15, v16, and v17 if fixtures exist.

Robustness signals are the diagnostic counters printed by `print_bad_events()`: lost event ratio, unordered timestamp ratio, and context switch bug ratio. Replay tests should include traces with many tasks to exercise fd-limit handling and `--force`; map tests should include compact mode, CPU filters, task-name filters, fuzzy matching, and PID/CPU color maps.
