# sources/distributed-fs/ceph-client/rust/syn/gen/eq.rs

## Purpose

`eq.rs` is generated by `syn-internal-codegen` and supplies `Eq` and `PartialEq` implementations for syn syntax tree types. It supports the crate's `extra-traits` feature, letting downstream macro and parser code compare AST nodes in tests, caches, deduplication logic, and diagnostics without hand-writing equality for every node.

The file is intentionally data-structure-aligned rather than algorithm-heavy. Each implementation either compares all semantic child fields of a struct node, dispatches over matching enum variants, or treats punctuation/token marker variants as equal by shape. It is not intended for manual editing.

## Important APIs, Types, and Functions

The only public surface is trait implementation: `impl Eq` and `impl PartialEq` for many `crate::*` AST types. Coverage is gated by feature families:

- `#[cfg(any(feature = "derive", feature = "full"))]` covers shared derive/full nodes such as `Abi`, attributes, paths, generics, expressions that are available in derive mode, fields, types, visibility, and where predicates.
- `#[cfg(feature = "derive")]` covers derive input structures such as `Data`, `DataEnum`, `DataStruct`, `DataUnion`, and `DeriveInput`.
- `#[cfg(feature = "full")]` covers complete Rust syntax, including blocks, statements, items, trait/impl/foreign items, patterns, use trees, function signatures, receivers, and full-expression variants.

The implementations rely on the normal `==` operator for recursive child fields and on `crate::tt::TokenStreamHelper` for `proc_macro2::TokenStream` equality inside `Verbatim` variants and macro/meta token fields. Examples include `Expr::Verbatim`, `Item::Verbatim`, `Type::Verbatim`, `TypeParamBound::Verbatim`, `TraitItem::Verbatim`, `Macro`, and `MetaList`.

Special-case enum implementations compare discriminants and payloads. Operator/token marker enums such as `BinOp`, `UnOp`, `RangeLimits`, `StaticMutability`, `TraitBoundModifier`, and delimiter/mutability enums generally compare only variant shape because their payloads are syntax token markers. Uninhabited `ImplRestriction` uses an exhaustive empty `match *self {}`.

## Control Flow

There is no runtime control flow beyond trait method dispatch. For struct-like AST nodes, `eq(&self, other)` evaluates a left-to-right chain of field comparisons and short-circuits on the first mismatch. For enum-like AST nodes, `eq` matches `(self, other)` and returns true only for the same variant, recursively comparing payloads where the variant carries a meaningful AST node.

For feature-dependent enum variants, the match arms are also feature-gated. For example, `Expr` always handles derive-compatible variants such as `Binary`, `Call`, `Path`, `Struct`, `Tuple`, and `Unary`, while full-only variants such as `Array`, `Assign`, `Async`, `Await`, `Block`, `ForLoop`, `Match`, `Try`, and `While` are guarded by `#[cfg(feature = "full")]`.

Verbatim-token control flow is delegated through `TokenStreamHelper`, so equality of raw token streams is centralized in `tt` rather than implemented ad hoc in every node. This matters for AST fragments that syn preserves as uninterpreted tokens.

## State and Persistence Behavior

The file owns no mutable state, persistent storage, allocation, I/O, or synchronization. Equality is pure over two borrowed AST values. The only observable behavior is the returned boolean.

Because AST fields include spans, token markers, punctuation containers, vectors, boxed child nodes, and optional values, persistence of equality semantics depends on the corresponding `PartialEq` implementations for those field types. Span-sensitive behavior is not implemented in this file directly; token and literal equality come from their own implementations elsewhere in the crate.

## Dependencies and Integration Points

This file integrates with `syn/lib.rs`, where generated `eq`, `debug`, and `hash` modules are enabled under `extra-traits` for `derive` or `full` builds. It depends on AST definitions throughout the syn crate, token marker equality from `token.rs`, punctuated sequence equality from `punctuated.rs`, literal equality from `lit.rs`, and `crate::tt::TokenStreamHelper` for token streams.

Downstream integration is through standard Rust traits. Consumers do not call functions in this file; they enable `extra-traits` and then use `==`, `assert_eq!`, map/set membership when paired with hashing, or derived test comparisons over syn syntax nodes.

## Risks and Edge Cases

The biggest risk is generated-code drift from the AST schema. If a syntax node gains, removes, or renames a field but this generated file is not regenerated, equality can fail to compile or silently omit a meaningful field. Omitting a field is especially dangerous for tests and caches because two distinct syntax trees may compare equal.

Token-stream equality is a semantic hot spot. `Verbatim` and macro/meta token fields use `TokenStreamHelper`, so any mismatch between helper semantics and downstream expectations affects all raw-token AST comparisons. This includes formatting, grouping, punctuation spacing, and span treatment depending on the helper's implementation.

Feature gating is another sharp edge. Code compiled with only `derive` sees a different equality surface than code compiled with `full`; tests that compare full-only nodes must enable the correct features. Empty or marker-token variants intentionally compare by shape, which is correct for syntax markers but may surprise callers expecting span-sensitive equality for every token.

Manual edits are high risk because the file is generated and parallels generated `debug.rs` and `hash.rs`. Local fixes should usually be made in the generator or AST definitions, then regenerated.

## Test Signals

Useful signals are compile checks across `derive + extra-traits`, `full + extra-traits`, and combined feature sets. Focused tests should parse representative syntax and assert equality/inequality for changed fields in attributes, generics, expressions, items, patterns, paths, types, visibility, and where clauses.

Regression tests should include `Verbatim` paths such as macro tokens, raw expression/type/item tokens, and `TypeParamBound::Verbatim`, plus feature-gated full syntax like blocks, statements, items, and patterns. Generator tests should compare the generated file against current AST metadata so newly added fields and variants cannot be missed.
