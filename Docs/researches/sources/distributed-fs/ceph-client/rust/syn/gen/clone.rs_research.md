# sources/distributed-fs/ceph-client/rust/syn/gen/clone.rs

## Purpose

`sources/distributed-fs/ceph-client/rust/syn/gen/clone.rs` is a generated Syn support module that provides `Clone` implementations, and a few `Copy` marker implementations, for Syn syntax tree nodes. The file is generated by `syn-internal-codegen` and carries a warning that it is not intended for manual editing. It sits under the private `gen` module declared in `syn/lib.rs` and is compiled only when the crate feature `clone-impls` is enabled.

The module's job is mechanical but user-visible through trait availability: with `clone-impls`, downstream code can duplicate Syn AST values such as `Expr`, `Type`, `Item`, `Fields`, `Path`, `Generics`, `Visibility`, and literal nodes. The generated impls preserve the exact AST shape by cloning every field on struct-like nodes and by rebuilding the same enum variant for enum-like nodes.

## Important APIs, types, and functions

The file does not define new public types or functions. It implements standard library traits for existing `crate::...` AST types:

- `impl Clone for crate::Abi`, `AngleBracketedGenericArguments`, `Attribute`, `ConstParam`, `Constraint`, `DeriveInput`, `Field`, `Generics`, `Path`, `Type*`, and many other struct-like nodes. Each implementation constructs the same struct and calls `.clone()` on each field.
- `impl Clone for crate::Expr`, `Data`, `Fields`, `GenericArgument`, `GenericParam`, `ImplItem`, `Item`, `Lit`, `MacroDelimiter`, `Member`, `Meta`, `Pat`, `PathArguments`, `ReturnType`, `Stmt`, `TraitItem`, `Type`, `TypeParamBound`, `UseTree`, `Visibility`, and `WherePredicate`. These enum implementations pattern-match the current variant and return the corresponding variant with cloned payload.
- `impl Copy` plus `Clone` returning `*self` for small token-like or enum-like types whose payloads are copyable in this generated view, including `AttrStyle`, `BinOp`, `RangeLimits`, `TraitBoundModifier`, and `UnOp`.
- `crate::Lit` and `crate::LitBool` have clone implementations without an internal `derive` or `full` gate, reflecting that literal support exists outside the larger derive/full AST partitions.

The file starts with `#![allow(clippy::clone_on_copy, clippy::expl_impl_clone_on_copy)]` because generated code deliberately calls `.clone()` uniformly on fields and explicitly implements `Clone` for some `Copy` types. That consistency keeps code generation simple and keeps each AST type's fields represented literally.

## Control flow

Control flow is almost entirely local to each trait method:

- Struct-like `clone` methods are straight-line constructors. They create `crate::TypeName { field: self.field.clone(), ... }`.
- Enum-like `clone` methods are `match self` expressions. Each branch rebuilds the same enum variant and clones the contained value when present.
- Unit or marker variants are returned directly, for example `Visibility::Inherited`.
- Copy-backed `Clone` implementations return `*self`.

Feature gates are the main cross-cutting control mechanism. In `syn/lib.rs`, `mod clone` is included only under `#[cfg(feature = "clone-impls")]`. Inside this file, individual implementations are additionally gated by AST availability:

- `#[cfg(feature = "derive")]` covers derive-input-only nodes such as `Data`, `DataEnum`, `DataStruct`, `DataUnion`, and `DeriveInput`.
- `#[cfg(feature = "full")]` covers full-file and statement/item/pattern nodes such as `File`, `Item`, `Stmt`, `Pat`, `UseTree`, and many expression variants.
- `#[cfg(any(feature = "derive", feature = "full"))]` covers syntax shared by derive and full modes, including expressions available in derive contexts, attributes, fields, generics, paths, types, and predicates.
- Some enum arms inside `Expr::clone` are individually `#[cfg(feature = "full")]`; the non-full fallback arm is `unreachable!()` for variants that cannot be constructed when `full` is disabled.

There is no recursion written manually beyond calling `Clone` on fields. Deep traversal of an AST is delegated to the `Clone` implementations of child fields such as boxed expressions, vectors, punctuated lists, tokens, identifiers, and literal wrappers.

## State and persistence behavior

The module is stateless. It does not read external input, write files, allocate global state, cache derived data, or persist anything. Runtime allocation behavior comes only from cloning owned AST fields such as `Vec`, `Box`, `Option`, `TokenStream`, `Punctuated`, `Ident`, and nested Syn nodes. Cloning preserves syntax-tree data, tokens, spans as provided by the cloned field types, and tree topology, but it creates a distinct owned AST value wherever the underlying field type's `Clone` does so.

Because the file is generated, its effective persistent source of truth is the Syn code generator plus the AST definitions elsewhere in the crate. Manual edits would be fragile and likely overwritten by regeneration.

## Dependencies

Direct dependencies are limited to:

- Standard `Clone` and `Copy` traits from Rust prelude.
- The existing Syn AST types under `crate::...`.
- Field-level clone implementations from dependencies used by those AST types, such as `proc_macro2` token and span types, identifiers, punctuated lists, boxed nodes, options, vectors, and token marker structs.

The module's documentation annotations use `#[cfg_attr(docsrs, doc(cfg(feature = "clone-impls")))]` so docs.rs can surface the feature that enables the impls.

## Integration points

`syn/lib.rs` declares this module as private `crate::gen::clone` under:

```rust
#[cfg(feature = "clone-impls")]
#[rustfmt::skip]
mod clone;
```

The implemented traits attach directly to public or crate-visible Syn AST types, so consumers do not import this module. They simply enable the `clone-impls` feature and then call `.clone()` or use generic trait bounds requiring `Clone`.

This file complements other generated modules in the same folder:

- `debug.rs`, `eq.rs`, and `hash.rs` provide optional `Debug`, equality, and hashing support behind `extra-traits`.
- `fold.rs`, `visit.rs`, and `visit_mut.rs` provide traversal APIs behind traversal-specific features.

The clone implementations depend on the AST definitions staying synchronized with the generated field list. If an AST struct gets a new field or an enum gets a new variant, this generated file must be regenerated with matching logic.

## Risks and edge cases

- **Generated-file drift:** The largest risk is mismatch between AST definitions and generated impls. A missing field in a struct clone would fail compilation or lose data if somehow accepted; a missing enum variant would create non-exhaustive match errors.
- **Feature-gate mismatch:** The file contains nested feature gates, especially in `Expr::clone`. Incorrect gating could expose clone impls for types or variants that are unavailable in the current feature set, or could make valid feature combinations fail to compile.
- **Clone cost:** Cloning a full parsed file or large expression tree can be expensive because the implementation recursively clones every owned child. The behavior is expected for `Clone`, but callers should not treat these clones as cheap.
- **Span/token semantics:** The correctness of spans and tokens after cloning depends on the underlying token and span `Clone` semantics. This module does not normalize, refresh, or validate spans.
- **Manual edits:** The file says it is generated and not intended for manual editing. Local changes should be made in the generator or AST model, then regenerated.

## Test signals

Useful validation signals include:

- Building Syn with `--features clone-impls` across the supported feature slices: minimal literal support, `derive`, `full`, and combinations with parsing/printing as relevant.
- Compile tests that require `Clone` bounds for representative nodes such as `DeriveInput`, `Expr`, `Type`, `Item`, `File`, `Lit`, and `Visibility`.
- AST round-trip or structural tests that parse representative Rust code, clone the tree, and compare printed output or equality when `extra-traits` is also enabled.
- Feature-matrix checks ensuring `Expr` variants and full-only nodes compile only in valid feature combinations.
- Regeneration checks comparing generated output after AST definition changes, since this file should track generated source rather than hand-maintained logic.
