# sources/distributed-fs/ceph-client/rust/syn/gen/debug.rs

## Purpose

`sources/distributed-fs/ceph-client/rust/syn/gen/debug.rs` is a generated Syn support module that provides `std::fmt::Debug` implementations for Syn syntax tree nodes. It is generated by `syn-internal-codegen`, is not intended for manual editing, and is compiled through `syn/lib.rs` only when the `extra-traits` feature is enabled.

The module enables downstream users and tests to inspect AST values with `{:?}`. Its output is deliberately structured around Rust enum and struct names: struct-like syntax nodes are formatted with `debug_struct`, tuple-like enum variants with `debug_tuple`, and enum wrappers begin with strings like `Expr::`, `Type::`, `Item::`, or `Visibility::`.

## Important APIs, types, and functions

The file imports `std::fmt::{self, Debug}` and implements `Debug` for a broad set of existing `crate::...` AST nodes. It does not define public modules or exported APIs of its own.

Important implementation categories:

- Struct-like nodes implement `Debug::fmt` by creating `formatter.debug_struct("TypeName")`, calling `.field("field_name", &self.field)` for each field, then `.finish()`. Examples include `Abi`, `Arm`, `Attribute`, `Block`, `ConstParam`, `DeriveInput`, `Field`, `File`, `Generics`, `Path`, `Signature`, `WhereClause`, and many `Expr*`, `Item*`, `Pat*`, and `Type*` structs.
- Enum-like nodes write a type prefix then match each variant. Examples include `AttrStyle`, `BinOp`, `CapturedParam`, `Data`, `Expr`, `Fields`, `FnArg`, `ForeignItem`, `GenericArgument`, `GenericParam`, `ImplItem`, `Item`, `Lit`, `MacroDelimiter`, `Member`, `Meta`, `Pat`, `PathArguments`, `ReturnType`, `Stmt`, `TraitItem`, `Type`, `TypeParamBound`, `UnOp`, `UseTree`, `Visibility`, and `WherePredicate`.
- Many payload structs also define inherent helper methods named `debug(&self, formatter: &mut fmt::Formatter, name: &str) -> fmt::Result`. These are private-to-the-type inherent methods used to format the same payload with either its concrete struct name or an enum variant name. For example, `Expr::Binary` can call `ExprBinary::debug(formatter, "Binary")`, while `ExprBinary`'s direct `Debug` impl calls the same helper with `"ExprBinary"`.
- `crate::Lifetime` has an always-available helper and `Debug` impl in this file, while many larger syntax nodes are gated by `derive` or `full`.

The file starts with `#![allow(unknown_lints, non_local_definitions)]`. The latter is relevant because the generated module is nested under `gen`, but implements traits for types defined elsewhere in the crate. Those impls are legal, but lint-sensitive.

## Control flow

Every `fmt` method is deterministic and local:

- Struct formatting builds a `DebugStruct`, adds fields in source order, then finishes.
- Enum formatting writes a prefix such as `Expr::`, matches on `self`, and either writes a unit variant name or delegates to tuple/struct debug builders.
- Variant payloads are usually formatted through the generated helper methods so the same field list can be reused with different display names.
- Formatting errors are propagated with `?` after prefix writes; builder `finish()` returns the final `fmt::Result`.

Feature gates mirror the AST and trait availability:

- `syn/lib.rs` includes `mod debug` only under `#[cfg(feature = "extra-traits")]`.
- Inside the generated file, `#[cfg(feature = "derive")]`, `#[cfg(feature = "full")]`, and `#[cfg(any(feature = "derive", feature = "full"))]` determine which AST nodes and variants receive `Debug` impls.
- The `Expr` implementation has full-only branches for expression variants that exist only under `full`, and an `#[cfg(not(feature = "full"))] _ => unreachable!()` fallback for impossible variants in reduced feature sets.

There is no AST traversal beyond formatting nested fields through their own `Debug` implementations. This means output shape follows the AST graph recursively, but the recursion is driven by standard formatter calls on references.

## State and persistence behavior

The module is stateless and persistence-free. It does not mutate AST nodes, allocate durable data, cache formatting state, or interact with the filesystem or runtime environment. The only state is the borrowed `fmt::Formatter` passed into `fmt`, which receives builder calls and writes formatted output.

Debug output is derived from the current AST values at formatting time. Since it includes many token and span-bearing fields, exact output can change when upstream field-level `Debug` implementations change, when AST definitions change, or when the generator changes field ordering or helper naming.

## Dependencies

Direct dependencies are:

- `std::fmt::{self, Debug}`.
- The Syn AST types under `crate::...`.
- `Debug` implementations of every field type used by the AST, including token markers, identifiers, lifetimes, literals, punctuated lists, vectors, options, boxes, and proc-macro token streams.

Feature and documentation dependencies include:

- `extra-traits`, which enables this generated module from `syn/lib.rs`.
- `derive` and `full`, which control subsets of AST node definitions and the corresponding generated impls.
- `docsrs` `doc(cfg(...))` attributes, which annotate feature-gated impls in generated documentation.

## Integration points

`syn/lib.rs` declares this module as:

```rust
#[cfg(feature = "extra-traits")]
#[rustfmt::skip]
mod debug;
```

Consumers do not import `gen::debug`; enabling `extra-traits` makes the standard `Debug` trait available on the relevant Syn AST types. This is particularly useful in tests, diagnostics, snapshot output, and debugging procedural macro parsers.

The module is paired with generated `eq.rs` and `hash.rs` under the same `extra-traits` feature, so projects that enable it usually get richer comparison and inspection traits together. It also relies on `tt` support being included for token-tree debug behavior when `full` or `derive` is combined with `extra-traits`.

## Risks and edge cases

- **Large output:** Formatting a full syntax tree can produce very large nested debug strings. This is useful for tests but can be expensive or noisy for production diagnostics.
- **Feature-gate drift:** Incorrect internal `cfg` placement could cause implementations to refer to AST nodes or enum variants unavailable under a feature combination. `Expr`, `Pat`, `Item`, and `Type` are the most sensitive because they contain many full-only variants.
- **Generated-file drift:** If AST fields or variants change without regenerating this file, debug output can become incomplete or compilation can fail.
- **Stability assumptions:** Debug formatting is a diagnostic contract, not a stable serialization format. Consumers should avoid parsing this output as data.
- **Recursive structures:** Syn ASTs are tree-shaped through owned containers, so normal formatting should terminate. However, very deep generated code may still create deep recursive formatting calls and large allocations in the output sink.
- **Lint sensitivity:** The module suppresses `non_local_definitions`; changes to generated placement or crate lint policy may require updating generator output rather than hand-editing this file.

## Test signals

Useful validation signals include:

- Building with `--features extra-traits` in minimal, `derive`, and `full` combinations to exercise all relevant `cfg` branches.
- Tests formatting representative values for `Lit`, `Lifetime`, `DeriveInput`, `Expr`, `Type`, `Item`, `Pat`, `File`, `Visibility`, and operator enums to ensure `Debug` impls are present.
- Snapshot-style tests for selected ASTs, while treating snapshots as generator-output expectations rather than stable external format.
- Feature matrix tests with `extra-traits` plus and minus `full`, ensuring unreachable fallback paths remain impossible and no full-only variant is referenced in reduced builds.
- Regeneration checks after AST-model edits so helper methods and field lists stay synchronized with the source definitions.
