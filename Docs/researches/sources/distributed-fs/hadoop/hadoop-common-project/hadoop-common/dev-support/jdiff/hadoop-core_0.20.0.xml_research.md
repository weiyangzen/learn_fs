## Important APIs and Types

### `org.apache.hadoop`

- `HadoopVersionAnnotation` is a package annotation interface implementing `java.lang.annotation.Annotation`. It exposes `version()`, `user()`, `date()`, `url()`, and `revision()` for build provenance. This metadata is public API because downstream tooling can inspect compiled packages for version and source-revision information.

### `org.apache.hadoop.conf`

- `Configurable` is the common configuration-injection interface with `setConf(Configuration)` and `getConf()`.
- `Configuration` implements `Iterable` and `Writable`. It models Hadoop key/value configuration with layered resources, final parameters, typed accessors, variable expansion, class loading, and XML/binary serialization.
- `Configuration` constructors cover default loading, disabling default resource loading, and cloning another configuration.
- Resource APIs include static synchronized `addDefaultResource(String)` and instance `addResource(...)` overloads for classpath names, `URL`, `Path`, and `InputStream`. `reloadConfiguration()` clears resource-loaded properties/final markers so later access rereads resources while preserving values set through setters as overlays.
- Property APIs include `get`, `getRaw`, `set`, `setIfUnset`, typed getters/setters for `int`, `long`, `float`, and `boolean`, `setBooleanIfUnset`, collection/string array methods, and `getRange`.
- Class APIs include `getClassByName`, `getClasses`, two `getClass` overloads constrained by an interface/default, `setClass`, and explicit `getClassLoader`/`setClassLoader`.
- Local-resource helpers include `getLocalPath(String, String)` and `getFile(String, String)`, which choose one configured local directory by path hash and create it if necessary.
- Resource stream APIs include `getResource`, `getConfResourceAsInputStream`, and `getConfResourceAsReader`.
- Introspection and persistence APIs include `size`, `clear`, `iterator`, `writeXml(OutputStream)`, `readFields(DataInput)`, `write(DataOutput)`, `toString`, `setQuietMode`, and a debugging `main`.
- `Configuration.IntegerRanges` parses positive integer range strings like `2-3,5,7-`, provides `isIncluded(int)`, and formats back to string.
- `Configured` implements `Configurable` and is the base class for objects that simply hold a `Configuration`.

### `org.apache.hadoop.filecache`

- `DistributedCache` is a static utility for distributing job-local read-only files, archives, jars, and classpath entries to task nodes.
- `getLocalCache(...)` has three overloads that localize a URI to a base cache directory, optionally using a provided `FileStatus`, `honorSymLinkConf`, archive/file mode, a configured file timestamp, and a task working directory. Archive inputs with `.zip`, `.jar`, `.tar`, `.tgz`, or `.tar.gz` are unpacked and return the unpacked directory.
- Cache lifecycle and validation APIs include `releaseCache`, `makeRelative`, `getTimestamp`, `createAllSymlink`, `checkURIs`, and `purgeCache`.
- Configuration mutation/access APIs include `setCacheArchives`, `setCacheFiles`, `getCacheArchives`, `getCacheFiles`, localized cache path getters, timestamp setters/getters, localized archive/file setters, and add methods for cache archives/files.
- Classpath integration APIs include `addFileToClassPath`, `getFileClassPaths`, `addArchiveToClassPath`, and `getArchiveClassPaths`.
- Symlink control APIs include `createSymlink(Configuration)` and `getSymlink(Configuration)`. `checkURIs` validates fragment presence and fragment-name conflicts when symlink creation is requested.

### `org.apache.hadoop.fs` metadata and checksum types

- `BlockLocation` implements `Writable` and carries block hosts, names, topology paths, offset, and length. It provides constructors with and without topology, getters/setters, `write`, `readFields`, and `toString`.
- `ChecksumException` extends `IOException` and adds `getPos()` to report the bad checksum position.
- `FileChecksum` is an abstract `Writable` contract with `getAlgorithmName()`, `getLength()`, `getBytes()`, and value-based `equals`/`hashCode`.
- `MD5MD5CRC32FileChecksum` implements `FileChecksum` for Hadoop's MD5-of-MD5-of-CRC32 checksum. It serializes with `readFields`/`write`, supports XML output through `org.znerd.xmlenc.XMLOutputter`, parses SAX attributes via `valueOf`, exposes `LENGTH`, and formats with `toString`.
- `FileStatus` implements `Writable` and `Comparable`. It represents client-side file metadata: length, directory flag, replication, block size, modification/access times, permission, owner, group, and `Path`. Equality/hash/ordering are path-based, and protected setters normalize null permission/owner/group to defaults.
- `ContentSummary` implements `Writable` and reports length, directory count, file count, quota, consumed space, and space quota. It includes `getHeader(boolean)` and `toString(boolean)` for command output with optional quota fields.

### `org.apache.hadoop.fs.FileSystem` and wrappers

- `FileSystem` is the central abstract filesystem base class extending `Configured` and implementing `Closeable`. It is the public abstraction for local and distributed filesystems.
- Static factory/configuration APIs include `get(Configuration)`, `get(URI, Configuration)`, `getDefaultUri`, `setDefaultUri` overloads, deprecated `getNamed`, `getLocal`, `closeAll`, static permission-preserving `create(FileSystem, Path, FsPermission)`, static `mkdirs(FileSystem, Path, FsPermission)`, and static statistics accessors.
- Instance identity/path APIs include `initialize(URI, Configuration)`, `getUri()`, deprecated `getName()`, `makeQualified(Path)`, and protected `checkPath(Path)`.
- Abstract core operations include `open(Path, int)`, full-argument `create(Path, FsPermission, boolean, int, short, long, Progressable)`, `append(Path, int, Progressable)`, `rename`, both `delete` signatures with the single-argument form deprecated, `listStatus(Path)`, `setWorkingDirectory`, `getWorkingDirectory`, `mkdirs(Path, FsPermission)`, and `getFileStatus`.
- Convenience overloads cover `open(Path)`, many `create(...)` variants for overwrite, replication, progress, buffer size, block size, and permissions, `createNewFile`, append overloads, existence/type/length checks, content summary, filtered and multi-path list status, glob status with or without filter, home directory, copy/move from local, copy/move to local, local-output staging, `close`, `getUsed`, default block size/replication, file checksum, checksum verification flag, permission/owner/time setters, and delete-on-exit.

- `FileSystem.Statistics` tracks per-scheme bytes read/written with increment, getter, reset, `toString`, and `getScheme`. `FileSystem` also exposes `LOG` and `statistics` fields.
- `FilterFileSystem` wraps another `FileSystem` in protected field `fs` and forwards nearly all `FileSystem` methods to it. It is the base for transforming/decorating filesystems such as checksum and archive filesystems.
- `ChecksumFileSystem` extends `FilterFileSystem` and creates/verifies client-side checksum files for raw files. It exposes checksum-path/length helpers, checksum verification toggles, raw filesystem access, checksum-aware open/create/append/copy/list/delete/rename behavior, and `reportChecksumFailure`.
- `LocalFileSystem` extends `ChecksumFileSystem` for checksumed local disk access and provides `getRaw`, `pathToFile`, local copy overrides, and local checksum-failure quarantine behavior.
- `HarFileSystem` extends `FilterFileSystem` to read Hadoop archives. It initializes per archive URI, exposes `VERSION`, `getHarVersion`, archive URI/working-directory behavior, block location mapping to the underlying filesystem, index-based file status/listing/open, and many mutating operations documented as not implemented.
- `InMemoryFileSystem` extends `ChecksumFileSystem` for `ramfs://` files whose sizes must be known ahead of time. Its special API is `reserveSpaceWithCheckSum(Path, long)`, plus file listing/count and capacity/usage reporting.

### Streams and positional IO

- `BufferedFSInputStream` wraps an `FSInputStream` in `BufferedInputStream` and forwards seek/position/positioned-read/readFully/new-source behavior.
- `FSDataInputStream` extends `DataInputStream` and implements `Seekable` and `PositionedReadable`, wrapping an `FSInputStream` with seek, current position, positioned reads, full positioned reads, and `seekToNewSource`.
- `FSDataOutputStream` extends `DataOutputStream` and implements `Syncable`. Constructors optionally accept `FileSystem.Statistics` and starting position. It exposes `getPos`, `close`, `getWrappedStream`, and `sync`.
- `FSInputStream` is the abstract seekable/positioned `InputStream` base. It requires `seek`, `getPos`, and `seekToNewSource`, and provides positioned `read` and `readFully` helpers.
- `FSInputChecker` is an abstract `FSInputStream` that verifies checksums before returning data. Subclasses implement `readChunk(...)` and `getChunkPosition(...)`. It synchronizes read/seek/skip/getPos/available paths, can disable checksum need, converts checksum bytes to long, and uses protected `set(...)` to configure checksum behavior.
- `FSOutputSummer` is an abstract `OutputStream` that chunks outgoing bytes, computes checksums, and delegates each completed chunk to `writeChunk(byte[], int, int, byte[])`. It supports synchronized single-byte and byte-array writes, buffer flushing, checksum byte conversion, and checksum chunk buffer reset.
- `PositionedReadable` defines thread-safe positioned read operations that do not change the stream's current offset.

### Utility and shell-facing filesystem APIs

- `DF` and `DU` extend `org.apache.hadoop.util.Shell` and parse Unix `df`/`du` output for capacity/usage. `DF` exposes filesystem, capacity, used, available, percent used, mount, command parsing, `DF_INTERVAL_DEFAULT`, and a `main`. `DU` tracks disk usage with increment/decrement adjustments and optional background refresh through `start()`/`shutdown()`.
- `FileUtil` is a static filesystem/local-file helper class. It converts `FileStatus[]` to `Path[]`, recursively deletes local directories, copies between filesystems/local disk, merges directory files into one output, makes shell-safe paths, computes local `du`, unzips/untars archives, creates symlinks, runs chmod, creates local temp files near a base file, and atomically replaces files.
- `FileUtil.HardLink` supports hardlink creation and link-count retrieval across Unix, Cygwin, and Windows XP.
- `FsShell` extends `Configured` and implements `Tool` to provide command-line filesystem access. It has constructors, protected `init`, `getCurrentTrashDir`, `run`, `close`, and `main`; byte formatting helpers are deprecated in favor of `StringUtils`; fields include filesystem handle and date formatters.
- `FsUrlStreamHandlerFactory` implements `URLStreamHandlerFactory` and creates URL handlers backed by Hadoop `FileSystem` implementations for recognized schemes.
- `LocalDirAllocator` allocates local paths across configured directory sets in round-robin order, with optional size checks. It exposes write-path selection with and without known size, read-path lookup, temp-file creation, context validity checks, existence checks, and one allocator per configuration context.
- `Path` implements `Comparable` and models Hadoop path/URI names with slash separators. Constructors resolve strings and parent/child combinations, or build from URI-like components. Methods include `toUri`, `getFileSystem`, `isAbsolute`, `getName`, `getParent`, `suffix`, `toString`, equality/hash/compare, `depth`, and `makeQualified`. Constants include `SEPARATOR`, `SEPARATOR_CHAR`, and `CUR_DIR`.
- `PathFilter.accept(Path)` is the path-list inclusion predicate used by listing/globbing APIs.

## Control Flow and State Behavior

- `Configuration` control flow is layered: defaults are added globally, individual configurations add resources in order, later resources override earlier ones unless a property is marked final, set-method values overlay resource-loaded values, and `reloadConfiguration()` invalidates parsed resource state so the next access reloads it.
- `Configuration.get(...)` expands variables using properties from the same configuration first and Java system properties as fallback. `getRaw(...)` intentionally bypasses expansion.
- `Configuration.getLocalPath`/`getFile` select among configured local directories by hashing the requested relative path, then create the selected directory if missing. This creates an implicit dependency between path strings and local disk placement.
- `DistributedCache` setup flow is job configuration mutation first, timestamp capture/validation second, task-node localization on demand, optional archive extraction, optional symlink creation in the task working directory, and explicit cache release/cleanup when finished.
- `FileSystem` client flow resolves a scheme/authority from `Configuration`, obtains/caches the correct implementation, calls `initialize`, validates paths against the filesystem URI, and then delegates abstract operations to concrete filesystems. Convenience overloads normalize default buffer sizes, replication, permissions, progress callbacks, and overwrite behavior before reaching the abstract core methods.
- `deleteOnExit` stores paths for deletion when a `FileSystem` closes; `processDeleteOnExit` recursively deletes those deferred paths during close/shutdown handling.
- `globStatus` has observable null/empty semantics: null if a non-glob path does not exist, empty array if a glob pattern matches nothing, and sorted results when matches exist.
- `FilterFileSystem` control flow is pass-through delegation to the wrapped `fs`; subclasses such as `ChecksumFileSystem`, `HarFileSystem`, and `LocalFileSystem` selectively intercept operations.
- `ChecksumFileSystem` wraps raw reads/writes with checksum-file creation/verification, hides checksum files from normal status listing, and coordinates data and checksum files across rename/delete/copy.
- `FSInputChecker` and `FSOutputSummer` implement chunk-oriented checksum flow: data is consumed or produced in chunks, checksums are verified/generated per chunk, and synchronized methods guard stream position and buffers.
- `HarFileSystem` reads `_masterindex` and `_index` metadata to map logical archive paths to physical `part-*` file segments in an underlying filesystem. Mutating operations are intentionally unsupported/not implemented.
- `LocalDirAllocator` cycles through configured local directories, testing free space and writability for writes, and scans all configured directories for reads.

## Risks and Edge Cases

- API compatibility risk is high because this XML is a baseline. Removing deprecated methods such as `FileSystem.getName`, `getNamed`, single-argument `delete`, `isDirectory`, `getLength`, `getBlockSize`, `FileUtil.fullyDelete(FileSystem, Path)`, or `FsShell` byte-format helpers would still break source or binary consumers.
- `Configuration` final parameters are order-sensitive. A later resource silently failing to override a final value can surprise callers if tests do not assert final-resource precedence.
- Variable expansion can recurse through configuration and system properties. Missing properties, malformed substitutions, or cycles are likely edge cases in the implementation behind this API.
- `Configuration.getClass` and `setClass` are runtime type-sensitive. Incorrect interface constraints can become `ClassCastException`/configuration failures.
- `getLocalPath`/`getFile` and `LocalDirAllocator` create directories on demand; concurrent callers can race on directory creation or select disks that become read-only/full during later writes.
- `DistributedCache` assumes read-only cache inputs during job execution and validates modification timestamps. Mutating HDFS/http cache content mid-job can cause stale or inconsistent localized data.
- Distributed cache symlink creation depends on URI fragments. Missing or duplicate fragments cause conflicts when symlinks are enabled.
- Archive extraction through `DistributedCache`/`FileUtil` has path traversal, permissions, and cleanup risks if implementation code fails to sanitize archive entries.
- `ChecksumFileSystem` must keep data files and checksum files synchronized across rename, delete, append, copy, and local-output workflows. Partial failure can leave stale checksum files or false checksum failures.
- `FileSystem.globStatus` null-versus-empty behavior is subtle and frequently depended on by callers.
- `FileSystem.create(FileSystem, Path, FsPermission)` is documented as using two RPCs to avoid mutating umask configuration because that alternative is not thread safe. This is intentionally inefficient and has race/failure windows between create and permission-setting behavior.
- `FileStatus.equals` and `hashCode` are path-only. Metadata changes do not affect equality, which can surprise caches keyed by `FileStatus`.
- `FSInputChecker.skip` and `seek` may move past EOF without exception; the next read returns `-1`. Callers must not rely on immediate EOF errors.
- `FSInputChecker` and `FSOutputSummer` have synchronized methods around checksumming and buffer state. Incorrect subclass implementations of `readChunk`, `getChunkPosition`, or `writeChunk` can corrupt stream positioning or checksum validation.
- `HarFileSystem` is mostly read-only. Mutating methods are present because of `FileSystem` inheritance but documented as not implemented, so generic filesystem callers must handle unsupported behavior.
- `InMemoryFileSystem` requires pre-known file sizes and pre-reservation including checksum space; using ordinary `FileSystem.create` assumptions can fail unexpectedly.
- `Path` strings are URI-like but permit unescaped elements and extra normalization. Edge cases include relative paths, scheme/authority qualification, root parent handling, suffixing, and comparison order.
- `RawLocalFileSystem` is only partially visible in this chunk, so whole-class conclusions must be deferred to later chunk research.

### Core Filesystem Contracts

`RawLocalFileSystem` is visible from the middle of its class entry. The listed public operations map Hadoop paths to local files and include `pathToFile`, `getUri`, `initialize`, `open`, `append`, permission-aware and permission-less `create` overloads, `rename`, deprecated and recursive `delete`, `listStatus`, `mkdirs`, home and working directory accessors, local-file move/staging hooks, `close`, `toString`, `getFileStatus`, `setOwner`, and `setPermission`. `Trash` extends `Configured` and provides the user-facing trash facility. Constructors accept either a `Configuration` alone or a `FileSystem` plus `Configuration`. ### Remote Filesystem Implementations

`org.apache.hadoop.fs.ftp.FTPException` wraps failures in a runtime exception. `FTPFileSystem` extends `FileSystem` and exposes normal filesystem operations over FTP: `initialize`, `open`, `create`, `append`, deprecated and recursive `delete`, `getUri`, `listStatus`, `getFileStatus`, `mkdirs`, `rename`, and working/home directory accessors. Public fields include logging and default buffer/block sizes. Decompressors mirror input/dictionary handling, `needsDictionary`, `finished`, decompression, reset, and `end`. `CodecPool` is a global pool for `Compressor` and `Decompressor` instances keyed by codec. It returns pooled or new objects and accepts returned instances. This reduces allocation/native setup cost but raises lifecycle risk: callers must return objects only after streams are finished/reset and must not use them after return.

`BlockCompressorStream` and `BlockDecompressorStream` define Hadoop's block-oriented codec framing. The compressor stream writes blocks with an uncompressed length followed by one or more length-prefixed compressed chunks, bounded by buffer size minus overhead. The decompressor stream reads those framed blocks and supports `resetState`. This framing is distinct from codec-native streaming formats.

`DefaultCodec` is configurable (`setConf`, `getConf`) and supplies the default deflate/zlib codec behavior. `GzipCodec` extends it to produce gzip streams, compressor/decompressor types, and the gzip extension. Nested `GzipInputStream` and `GzipOutputStream` bridge Java gzip/deflater streams into Hadoop's compression stream API, including `available`, `close`, `read`, `write`, `skip`, `flush`, `finish`, and `resetState`.

`BZip2Codec` implements `CompressionCodec` but documents that compressor/decompressor object methods are not supported and throw `UnsupportedOperationException`; only direct stream creation is supported. That means generic code using `CodecPool` cannot assume every codec supports pooled compressor objects. The default extension is `.bz2`.

## BZip2 And Zlib Implementations

`org.apache.hadoop.io.compress.bzip2` exposes a historical pure-Java BZip2 implementation. `BZip2Constants` contains public constants and `rNums`; its documentation explicitly warns that `rNums` should not be public because malicious code can mutate it. `BZip2DummyCompressor` and `BZip2DummyDecompressor` implement the compressor/decompressor interfaces as placeholders.

`CBZip2InputStream` and `CBZip2OutputStream` perform BZip2 data transformation without the leading file magic bytes. Callers must skip `"BZ"` before constructing the input stream and must write `"BZ"` before constructing the output stream. The output stream supports block sizes 1 through 9, `chooseBlockSize`, `finish`, `close`, `flush`, and exposes several protected algorithm constants for historical subclass access. The docs call out large memory requirements, recommend prompt close, and state instances are not thread-safe.

`org.apache.hadoop.io.compress.zlib` provides both Java-wrapper and native-capable zlib contracts. `BuiltInZlibDeflater` and `BuiltInZlibInflater` adapt `java.util.zip.Deflater`/`Inflater` to Hadoop `Compressor`/`Decompressor`. `ZlibCompressor` and `ZlibDecompressor` expose synchronized stateful methods around zlib with direct buffer size configuration, byte counters, reset/end, and optional dictionaries.

## Retry APIs

`RetryPolicy` is the decision interface: `shouldRetry(Exception e, int retries)` returns whether a failed call should be retried. The boolean-only return means delay/sleep behavior is encapsulated inside the policy implementation rather than returned to the caller.

`RetryPolicies` is the static factory/constant holder. It defines `TRY_ONCE_THEN_FAIL`, `TRY_ONCE_DONT_FAIL`, and `RETRY_FOREVER`, plus factories for fixed-sleep retry by maximum count, fixed-sleep retry by maximum elapsed time, proportional sleep, exponential backoff, retry-by-exception map, and retry-by-remote-exception map. Time units are part of the factory signatures, tying retry timing to `java.util.concurrent.TimeUnit`.

`RetryProxy` creates dynamic proxies for an implementation and interface, either with one default retry policy or a map of method names to policies plus a default. It is the integration point that applies retry behavior to RPC-like or filesystem client APIs without changing the implementation class.

## Serialization APIs

The serializer package provides a pluggable framework controlled by the `io.serializations` configuration property. A `Serialization` implementation advertises `accept(Class)`, then returns a `Serializer` and `Deserializer` for matching classes. `SerializationFactory` loads configured implementations and returns the selected serializer/deserializer for a class.

`Serializer` is stateful: `open(OutputStream)`, `serialize(Object)`, and `close()`. `WritableSerialization` adapts Hadoop `Writable` objects by delegating to `Writable.write(DataOutput)` and `Writable.readFields(DataInput)`. `JavaSerialization` adapts Java `Serializable`. `DeserializerComparator` compares serialized byte slices through a supplied deserializer, and `JavaSerializationComparator` specializes that for Java serialization. The comparator APIs are useful but risky for performance because deserialization may happen during comparison unless a byte-level comparator exists.

## Control Flow And State Inferred From The API

Sequence-file control flow is append/read/seek oriented. Writers append typed or raw records, periodically sync, and expose byte lengths for later exact positioning. Readers load header metadata, key/value classes, and compression settings, then iterate records either by deserializing into reusable objects or by streaming raw key/value bytes. Sorters consume one or more sequence files, spill sorted segments to temp paths under a memory budget, merge bounded by fan-in, and optionally delete input segments during cleanup.

Writable control flow is object-reuse oriented. `readFields` mutates existing instances; factories and name registries provide late construction; comparators may compare either objects or raw byte slices; utility functions encode small signed integers compactly. These patterns are fundamental to Hadoop's performance model because object allocation and full deserialization are avoided on hot paths.

Compression control flow is stream and codec-state oriented. Codecs create streams, streams feed stateful compressors/decompressors, callers finish/close/reset, and `CodecPool` recycles codec state. Block compression adds explicit block length framing, while gzip/bzip2/zlib classes each have format-specific header, reset, and native fallback rules.

Retry proxy control flow wraps method invocation with policy decisions after exceptions. Serialization factory control flow selects a serialization implementation by configured order and class acceptance. IPC control flow creates protocol proxies, sends writable invocation requests to servers, unwraps remote exceptions, and stops proxies/clients to release threads and sockets.

## Risks And Edge Cases

Storage compatibility risk is high. Changing `WritableUtils` vint/vlong encoding, `Text` UTF-8 validation, `WritableName` aliases, `VersionedWritable` version handling, sequence-file sync/position semantics, or compression stream framing would make existing Hadoop data unreadable or incorrectly sorted.

Comparator correctness is a major risk. `WritableComparator` byte-level helpers must match `Writable` serialization exactly. Any mismatch can corrupt sort order in map output, sequence-file sort/merge, set/map file lookup, or RPC key handling. Optimized byte comparators need tests against object comparisons for signed integers, variable-length encodings, UTF-8 data, and boundary offsets.

Resource lifecycle risk appears in `SequenceFile.Reader`/`Writer`, `RawKeyValueIterator`, compression streams, codec pools, serializers/deserializers, BZip2 streams, zlib native objects, and IPC clients/proxies. Missing `close`, `finish`, `reset`, `returnCompressor`, `returnDecompressor`, `end`, or `stop` calls can leak file handles, native buffers, memory-heavy BZip2 work arrays, sockets, or threads.

Thread-safety boundaries are uneven. Some registry and zlib methods are synchronized, `SequenceFile.Reader` synchronizes core movement/value methods, but BZip2 stream docs state non-thread-safety and many mutable writable wrappers expose unsynchronized setters/getters. IPC compatibility risk includes deprecated overload migration, protocol version mismatches, UGI ticket propagation, ping interval configuration, parallel call partial failures returning nulls, and remote exception unwrapping by class name. `RemoteException.unwrapRemoteException` depends on exception classes and constructors being available locally.

Security risk is explicitly documented for `BZip2Constants.rNums`, a public mutable array that should have been private. Serialization also carries risk: Java serialization acceptance may instantiate arbitrary `Serializable` payloads, and remote exception XML/class names cross process boundaries.

## Control Flow

Record I/O flow starts from a DDL file: `Rcc.driver/main` parse command-line arguments; `Rcc.Input` parses includes, module, and records; parser productions build `JFile`, `JRecord`, `JField`, and `JType` instances; then `JFile.genCode` dispatches language-specific generation into the destination directory. The Ant wrapper follows the same core path but obtains its inputs from a single file or nested `FileSet`s and applies Ant-style failure behavior.

Serialization flow for generated records is sequential and type-directed. Primitive values are encoded according to the chosen format; records serialize fields in declaration order; vectors and maps serialize size then elements/pairs in binary format. Runtime metadata flow uses `RecordTypeInfo` and `TypeID` to describe and serialize schema/type information, while `Utils.skip` allows a reader to consume unknown or unneeded fields based on metadata.

Security authorization flow is layered. UGI discovery or config loading produces a `UserGroupInformation`; `SecurityUtil.getSubject` maps UGI to JAAS subject; ACL strings and policy providers define access rules; `ConfiguredPolicy` and `ServiceAuthorizationManager.authorize` decide whether a user can access a protocol/service. The refresh protocol allows live service ACL reload without process restart.

Utility flows are mostly helper-oriented: command-line programs should enter through `ToolRunner.run`, which consumes Hadoop generic options before invoking application-specific `Tool.run`; shell wrappers build commands, run them with optional environment/working-directory, parse output, and surface exit codes; process tree and memory plugins query platform state; sorters repeatedly call caller-supplied indexed compare/swap operations.

Bloom filter flow is hash-driven: constructors define vector size, hash count, and hash implementation; `add` maps a key to hash positions and mutates internal state; membership checks query the same positions; logical operations combine compatible filters; writable methods persist or restore filter state.

- Logical Bloom operations require compatible filter parameters; combining mismatched vector sizes/hash counts would be semantically unsafe even if the API accepts a general `Filter`.

## Control Flow and State Behavior

- Bloom-filter insertion flows through `Filter.add(Key)` for single keys and through the concrete bulk-add helpers for lists, collections, and arrays. Subclasses own the actual vector or counter mutation.
- Dynamic Bloom-filter growth is threshold-driven: insertion first searches for an active row whose recorded-key count is below the configured row cardinality, otherwise it appends a new standard Bloom-filter row and inserts there.
- Filter boolean operations mutate the receiver. The documentation for `and`, `or`, `xor`, and `not` states that the result is assigned to `this` filter.
- `HashFunction.hash(Key)` bridges filter operations to lower-level `Hash` algorithms by producing multiple vector positions for one key. The number of returned positions is driven by `nbHash`, and values must fit within the configured vector bound.
- `Key` is mutable: callers can replace bytes and weight, increment weight, deserialize new contents through `readFields`, and compare keys through `WritableComparable`.
- Retouched Bloom-filter control flow has two channels: ordinary positive-key insertion and separate false-positive recording. `selectiveClearing` then chooses which bit to clear for a specific false-positive key according to the requested remove scheme.
- Hash selection flow is configuration or constant driven: callers parse a string or read a `Configuration`, then ask `Hash.getInstance(...)` for the singleton implementation. Invalid selection is observable because the API can return `null`.

## Risks and Edge Cases

- This chunk starts mid-class. Any final per-file synthesis must merge it with the previous chunk to avoid treating `DynamicBloomFilter` as only its serialization methods.
- Bloom filters are lossy by design. `membershipTest` can return false positives, and retouched Bloom filters can additionally introduce false negatives.
- Retouched clearing is destructive because it clears bits shared by many keys. The selected `RemoveScheme` directly affects the false-positive versus false-negative tradeoff.
- `RemoveScheme` constants are untyped `short` values; invalid values passed to `selectiveClearing(Key, short)` are possible at compile time unless implementation code validates them.
- `Hash.getInstance(...)` may return `null` for invalid types, so callers that immediately dereference the result risk `NullPointerException`.
- Hash functions are not cryptographic. Using `JenkinsHash` or `MurmurHash` for adversarial input, signatures, authentication, or integrity protection would be incorrect.
- `Key` exposes mutable bytes through `getBytes()` if the implementation returns the backing array. Mutating a key after insertion into a filter or sorted/hash collection can create hard-to-debug behavior; implementation details must be checked in source.
- Serialization compatibility is sensitive: changing vector size encoding, hash type constants, key byte/weight layout, or retouched false-positive metadata would break persisted filters across versions.
- Bulk-add overloads use raw `List` and `Collection` types in this 0.20.0 API metadata. Runtime implementations must handle or fail predictably when collections contain non-`Key` values.

## Test Signals

- API compatibility tests should assert the presence, visibility, inheritance, exceptions, and deprecation state recorded here for `Filter`, `HashFunction`, `Key`, `RemoveScheme`, `RetouchedBloomFilter`, `Hash`, `JenkinsHash`, and `MurmurHash`.
- `Filter` subclass tests should cover constructor initialization, single-key add, bulk add via `List`/`Collection`/array, boolean operations mutating `this`, and `Writable` round trips.
- Dynamic Bloom-filter tests should cover row growth at the configured per-row cardinality, membership checks across multiple rows, serialization/deserialization of multiple rows, and hash-configuration preservation.
- `Key` tests should cover default construction plus `readFields`, byte/weight setters, weight increment variants, equality/hashCode/compareTo consistency, and binary serialization with empty and non-empty byte arrays.
- `HashFunction` tests should verify returned array length equals `nbHash`, each position is within bounds, repeated calls are deterministic, and `clear()` does not change results.
- Retouched Bloom-filter tests should exercise `addFalsePositive` overloads, null single-key handling, each `RemoveScheme`, invalid scheme behavior, `selectiveClearing` effects on known false positives, and the expected introduction of possible false negatives.
- Hash tests should cover string parsing for `jenkins`, `murmur`, and invalid names; configuration-based selection; `getInstance` singleton behavior; `null` on invalid type; convenience seed overloads; known vectors for Jenkins and Murmur; byte-length handling; and `JenkinsHash.main` file IO error handling.
