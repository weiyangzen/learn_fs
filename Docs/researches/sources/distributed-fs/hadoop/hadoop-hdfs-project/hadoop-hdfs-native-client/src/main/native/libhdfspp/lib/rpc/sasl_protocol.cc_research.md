# sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs-native-client/src/main/native/libhdfspp/lib/rpc/sasl_protocol.cc

## Purpose

This file implements the client-side Hadoop RPC SASL negotiation state machine for libhdfspp. It converts NameNode `RpcSaslProto` responses into libhdfspp `SaslMethod` choices, drives the configured SASL engine, sends `NEGOTIATE`, `INITIATE`, and `RESPONSE` messages over `RpcConnection`, and falls back to SIMPLE authentication only when the server advertises it.

## Important APIs, types, and functions

Important functions are `SaslProtocol::Authenticate()`, `ParseMethod()`, `BuildInitMessage()`, `extract_auths()`, `ResetEngine()`, `Negotiate()`, `Challenge()`, `SendSaslMessage()`, `AuthComplete()`, and `OnServerResponse()`. `ResetEngine()` selects `CySaslEngine` or `GSaslEngine` behind `USE_SASL` feature macros. `BuildInitMessage()` preserves the chosen protobuf `SaslAuth` entry and attaches the binary SASL token generated by `SaslEngine::Start()`.

## Control flow, state, and persistence

`Authenticate()` records the completion callback, sets `state_` to `kNegotiate`, emits a "SASL Start" event, and sends an async `NEGOTIATE` RPC while holding the SASL mutex. `OnServerResponse()` dispatches by protobuf state: `NEGOTIATE` builds a mechanism list, chooses a SASL mechanism, starts the engine, and sends `INITIATE`; `CHALLENGE` calls `SaslEngine::Step()` and sends `RESPONSE`; `SUCCESS` calls `Finish()` and completes authentication. State is in-memory only: `state_`, `auth_info_`, `sasl_engine_`, a weak owning connection, and event handlers. There is no persistence beyond the authenticated RPC connection.

## Dependencies and integration points

The implementation depends on generated `RpcHeader.pb.h`, `RpcConnection`, `RpcEngine`, `AuthInfo`, `Status`, `LibhdfsEvents`, logging, optional token data, and `XPlatform::Syscall::StringCompareIgnoreCase()`. It is integrated into RPC connection authentication through the special `SASL_METHOD_NAME` method. Test coverage is indirectly provided by RPC and SASL digest tests, while server compatibility depends on Hadoop protobuf SASL states and advertised mechanisms.

## Risks and test signals

The highest risks are callback lifetime mistakes, missing `event_handlers_` initialization before `Authenticate()`, deadlocks if methods are called without the expected locks, and incorrect fallback from Kerberos/TOKEN to SIMPLE. `BuildInitMessage()` fails hard on an empty token, so SASL engine behavior is security critical. Good signals are successful Kerberos/TOKEN negotiation, SIMPLE fallback only when advertised, no use-after-free when the connection disappears, and event pairs "SASL Start"/"SASL End" around all exits.
