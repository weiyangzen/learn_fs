# sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/datanode/fsdataset/impl/FsDatasetImpl.java

`FsDatasetImpl` is the central local-storage implementation behind the DataNode `FsDatasetSpi`. It coordinates DataNode replica state across volumes, the in-memory `ReplicaMap`, block-pool lifecycle, block creation and recovery, invalidation, directory-scanner reconciliation, cache management, RAM-disk lazy persistence, async deletion, storage reports, and MBean/metrics exposure.

Important APIs include `getStorageReports`, `getBlockReports`, `createRbw`, `createTemporary`, `append`, `recoverAppend`, `recoverClose`, `recoverRbw`, `finalizeBlock`, `invalidate`, `checkAndUpdate`, `addBlockPool`, `shutdownBlockPool`, `deleteBlockPool`, `cache`, and `uncache`. It owns `FsVolumeList`, `ReplicaMap`, `storageMap`, `FsDatasetAsyncDiskService`, `FsDatasetCache`, `RamDiskReplicaTracker`, and `RamDiskAsyncLazyPersistService`. Locking uses `DataSetLockManager` with block-pool, volume, and directory levels, plus `DataNodeLayoutSubLockStrategy` to split block operations by sublock.

Construction validates failed-volume tolerance, builds the volume list, scans each storage directory into temporary replica maps, activates volumes, starts lazy-persist support when needed, registers MBeans/metrics, and configures scanner notification throttles. Dynamic volume add prepares storage, initializes block pools, scans replicas, starts services, and activates the volume. Volume removal disables services, waits for references to drain, removes replicas from memory, invalidates old replicas outside the object lock, then removes storage and lock entries.

Replica writes are a state machine. `createTemporary` handles conflicting in-pipeline/provided replicas, selects a target volume, creates tmp files, and inserts `TEMPORARY`. `createRbw` may reserve locked memory and choose transient storage, otherwise persistent storage, then inserts `RBW`. `append`, `convertTemporaryToRbw`, `finalizeReplica`, and recovery methods move files between tmp/rbw/finalized locations, preserve last partial checksums, update generation stamps, release reserved bytes, and replace `volumeMap` entries.

Recovery paths take over or stop existing writers, validate generation-stamp ranges and lengths, truncate unacked bytes, create `RUR` state, handle copy-on-truncate with new block IDs, and finalize recovered replicas. Invalidation separates short-circuit cache invalidation, cache uncache, NameNode notification, memory removal, and async/sync disk deletion. `checkAndUpdate` reconciles directory-scanner observations with memory: it can add missing disk blocks, remove memory-only blocks, delete orphan metadata, resolve duplicates, update generation stamps, and report corrupt blocks.

Durable state is block/meta files, block-pool directories, DataStorage version/trash/rolling-upgrade state, and lazy-persist copies. Runtime state includes volume maps, storage maps, cache maps, failed-volume info, RAM-disk queues, `deletingBlock`, and lock structures. Main dependencies are `DataNode`, `DataStorage`, `FsVolumeImpl`, `BlockPoolSlice`, `DirectoryScanner`, `BlockScanner`, `FileIoProvider`, `FsDatasetCache`, async services, `ReplicaInfo` subclasses, protocol types, short-circuit registry, and metrics.

Risks are lock-order regressions, stale `volumeMap` entries after disk failure, missed reference cleanup, async deletion races, cache/lazy-persist reservation leaks, generation-stamp mistakes during recovery, and data loss during same-mount hard-link moves or copy-on-truncate. Tests should cover volume add/remove/failure tolerance, append/recover/finalize transitions, scanner reconciliation, block reports, async deletion, pmem cache reads, RAM-disk lazy persist/eviction, same-disk tiering moves, and copy-on-truncate recovery.
