## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/namenode/FSNDNCacheOp.java

Purpose: NameNode-side cache directive and cache pool operation helper. It is a package-private static dispatch layer used by `FSNamesystem` to call `CacheManager` with the right permission checker and then persist successful mutations to the edit log with retry-cache metadata.

Important APIs: directive methods are `addCacheDirective`, `modifyCacheDirective`, `removeCacheDirective`, and `listCacheDirectives`. Pool methods are `addCachePool`, `modifyCachePool`, `removeCachePool`, and `listCachePools`. `getFsPermissionChecker` returns `fsn.getPermissionChecker()` only when permissions are enabled, otherwise `null`, matching `CacheManager`'s permission-check contract.

Control flow: add directive obtains a permission checker, rejects client-supplied directive ids, calls `cacheManager.addDirective`, logs the effective directive to the edit log, and returns it. Modify/remove directive obtain a checker, apply the cache-manager mutation, and log the corresponding edit. List directive obtains a checker and returns the cache-manager batched iterator result. Cache pool add/modify/remove call the corresponding cache-manager operation and log edits; list pools uses the permission checker for filtering/authorization but does not log because it is read-only.

State and persistence behavior: the class itself has no state. Mutating methods change `CacheManager` in-memory state and immediately append edit-log records through `FSNamesystem.getEditLog()`: add/modify/remove cache directive info and add/modify/remove cache pool. The `logRetryCache` parameter is forwarded so idempotent RPC retry handling is persisted consistently. Read methods return `BatchedListEntries` without persistence changes.

Dependencies and integration points: called by `FSNamesystem` cache RPC methods around lines that handle add, modify, remove, and list cache directives and pools. It depends on `CacheManager`, `FSPermissionChecker`, `CacheDirectiveInfo`, `CacheDirectiveEntry`, `CachePoolInfo`, `CachePoolEntry`, `CacheFlag`, Hadoop batched iterators, and `AccessControlException`. Durable state written by these methods is later serialized in fsimage/edit-log paths through `CacheManager` and `FSImageSerialization`.

Risks: correct ordering matters: edit-log writes happen after successful cache-manager mutation, so failures between mutation and log append would need surrounding `FSNamesystem` locking/error handling to preserve consistency. Passing `null` permission checkers when permissions are disabled must remain accepted by `CacheManager`. Add directive's explicit id rejection protects id allocation; removing it would allow clients to collide with persisted ids. Since this class is a thin layer, behavioral checks such as quota, pool authorization, and directive validation live in `CacheManager` and must not be assumed here.

Test signals: tests should cover add/modify/remove/list directives and pools through `FSNamesystem`, permission-enabled and permission-disabled paths, client-supplied id rejection, edit-log replay and retry-cache behavior, batched listing filters/start keys, and fsimage persistence of cache manager state after operations.
