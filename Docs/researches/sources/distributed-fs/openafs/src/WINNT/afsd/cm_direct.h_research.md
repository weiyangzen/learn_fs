# sources/distributed-fs/openafs/src/WINNT/afsd/cm_direct.h

This header declares the direct-write interface for cache-bypass StoreData operations in the Windows OpenAFS cache manager. It depends on `cm_bulkIO_t` from the data-cache layer and on common cache-manager types such as `cm_scache_t`, `cm_user_t`, `cm_req_t`, and `osi_hyper_t`. The public surface is intentionally narrow: setup of direct BIODs, direct write submission, background write execution, and background cleanup.

`cm_DirectWrite` is the primary caller API. It takes a scache, file offset, length, flags, user/request context, a caller memory region, and an output byte count. `CM_DIRECT_SCP_LOCKED` tells the implementation that the caller already holds `scp->rw`, altering lock acquire/release behavior. The function queues background write work in the implementation, so the `bytesWritten` result is an accepted-byte count for the queued memory copy rather than proof that StoreData reached the file server.

`rock_BkgDirectWrite_t` is the background-daemon payload. It stores the target offset and length, a `bypass_cache` marker, and the copied memory region. `cm_BkgDirectWrite` consumes that payload by issuing the StoreData RPC, while `cm_BkgDirectWriteDone` releases store synchronization and frees allocated memory when a background request completes or is discarded. `cm_SetupDirectStoreBIOD` is also declared for collecting buffers overlapping a direct write; the implementation notes it is unused but retained to prevent code rot.

State and persistence are indirect. This header defines no persistent storage, but callers must understand that direct writes affect server-side file contents and scache status while bypassing normal dirty buffer state. Integration points are redirector/write paths, the background daemon, `cm_dcache` bulk descriptors, and StoreData synchronization in `cm_scache`. Risks include misuse of `CM_DIRECT_SCP_LOCKED`, assuming queued bytes are durable bytes, and forgetting that the background rock owns dynamically allocated memory. Test signals are compile-time consumers of `cm_DirectWrite`, background daemon execution, and cleanup behavior when requests are retried or completed.
