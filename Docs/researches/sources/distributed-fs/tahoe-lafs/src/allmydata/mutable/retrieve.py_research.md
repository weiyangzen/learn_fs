# sources/distributed-fs/tahoe-lafs/src/allmydata/mutable/retrieve.py

Purpose: Implements mutable-file download and verification. It uses a validated `ServerMap` version to select shares, fetches blocks and hash proofs through layout read proxies, validates block and share hash trees, decodes erasure-coded ciphertext, decrypts plaintext segments, streams data to a Twisted consumer, and optionally verifies all shares or retrieves private-key material for repair.

Important APIs and types: `RetrieveStatus` implements `IRetrieveStatus` and records storage index, encoding, size, status, progress, active flag, per-server fetch timings, crypto/decoder timings, and problems. `Retrieve` implements `IPushProducer` with `pauseProducing`, `resumeProducing`, and `stopProducing`. Main methods include `download`, `_start_download`, `loop`, `_setup_download`, `_setup_encoding_parameters`, `_activate_enough_servers`, `_download_current_segment`, `_process_segment`, `_validate_block`, `_get_needed_hashes`, `_decode_blocks`, `_decrypt_segment`, `_set_segment`, `_handle_bad_share`, `_mark_bad_share`, `_try_to_validate_privkey`, `_done`, and `_raise_notenoughshareserror`. `decode` is a shortcut used by mutable update logic to decode supplied block/salt data without a full streaming download.

Control flow: `download` registers as a streaming producer with the consumer, handles zero-length files immediately, and starts a loop. Setup derives k/N, version, segment/tail sizes, decoder instances, and requested start/end segments from `verinfo`, offset, and size. `_setup_download` builds a remaining sharemap for the chosen version, reuses cached `MDMFSlotReadProxy` objects from the servermap when possible, initializes per-share incomplete block hash trees, and seeds the file-level share hash tree with the known root hash. Each loop activates enough readers, asks each active reader for the current block/salt plus needed block/share hashes, validates each share, and either verifies-only or decodes/decrypts the segment. Successful plaintext is trimmed for requested offset/size and written to the consumer; failures mark shares bad, notify storage servers of corrupt data, remove readers, and allow the loop to select replacements.

State and persistence: Retrieve maintains operation state including the target `verinfo`, `_data_length`, `_need_privkey`, `_verify`, selected readers, remaining sharemap, active readers, per-share block hash trees, share hash tree, current/start/last segment, requested offset/length, pause/stopped flags, bad shares, last failure, and status timings. It does not persist file data locally; it streams to the supplied consumer. It mutates the shared servermap by marking bad shares and may populate the filenode's encoding parameters, encrypted private key, and private key after successful validation.

Dependencies and integration points: Depends on Twisted producer/consumer APIs and Deferreds, Foolscap remote failure classes, AES/RSA/hash helpers, erasure `codec.CRSDecoder`, Tahoe `hashtree`, layout `MDMFSlotReadProxy`, storage-server corruption notification, `DictOfSets`, `defer_to_thread`, and mutable exceptions (`BadShareError`, `CorruptShareError`, `UncoordinatedWriteError`, `DownloadStopped`). It is used by filenode download paths, mutable update preparation, verification/checking flows, and repair private-key recovery.

Risks: The retrieve object is documented as single-use; shared mutable fields make concurrent downloads unsafe. Reader selection favors lower share numbers and only activates replacements after failures, which may not be latency optimal. `_activate_enough_servers` fires private-key fetch Deferreds without flow-control/error aggregation. Verification mode skips plaintext use but still relies on segment processing paths; if all active readers are exhausted it stops rather than forcing decode. Corruption reporting is best-effort. Pausing uses a single deferred gate and must coordinate with stop handling to avoid writing after a consumer has stopped. Any mismatch between servermap prefix and fetched data is treated as an uncoordinated write.

Test signals: Tests should cover full and ranged downloads, zero-length files, SDMF and MDMF salt/hash validation, tail segment trimming, consumer pause/resume/stop behavior, insufficient shares, replacement of bad or disconnected readers, corrupt block hash tree, corrupt share hash chain, prefix mismatch, verify-only mode returning bad shares, private-key validation success/failure, cached reader reuse from servermap, and the `decode` shortcut used for partial updates.
