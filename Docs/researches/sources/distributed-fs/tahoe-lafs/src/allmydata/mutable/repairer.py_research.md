# sources/distributed-fs/tahoe-lafs/src/allmydata/mutable/repairer.py

Purpose: Provides high-level mutable-file repair orchestration. It refreshes a full repair-mode servermap, chooses the best recoverable version, refuses potentially data-losing repairs unless forced, downloads recoverable contents and private key material, then republishes the data so missing, stale, or bad shares are replaced.

Important APIs and types: `RepairResults` implements `IRepairResults` with `set_successful`, `get_successful`, and `to_string`. `RepairRequiresWritecapError` signals that repair cannot proceed without write authority. `MustForceRepairError` signals merge or unrecoverable-newer-version conditions that require explicit `force=True`. `Repairer.start(force=False)` launches the process; `_got_full_servermap` performs policy decisions and upload chaining; `get_results` wraps a successful upload result.

Control flow: `start` creates a fresh `ServerMap` and `ServermapUpdater` in `MODE_REPAIR`, optionally reports updater status to history, and waits for update completion. `_got_full_servermap` asks the resulting map for `best_recoverable_version`. If none exists, it returns unsuccessful `RepairResults`. If newer unrecoverable versions exist or multiple recoverable heads need merge, it raises `MustForceRepairError` unless `force=True`, because repair would discard information by reinforcing one version. It then requires a writekey, downloads the selected version with `fetch_privkey=True`, wraps the bytes in `MutableData`, calls `node.upload` with the repair servermap, and returns successful `RepairResults`.

State and persistence: The repairer itself holds the node, coerced check results, storage broker, history, and monitor. Persistent repair effects happen through `node.upload`, which uses the servermap's known shares and bad-share records to overwrite old/bogus shares and place missing shares. The repair path also intentionally fetches and populates private-key material during download so the subsequent publish can sign a new mutable version.

Dependencies and integration points: Integrates `ServermapUpdater`/`ServerMap` discovery, retrieve via `node.download_version`, publish via `node.upload`, and `MutableData` upload wrapping. It relies on `ServerMap.best_recoverable_version`, `unrecoverable_newer_versions`, `needs_merge`, and `bad_shares` semantics established by servermap/retrieve verification. Results conform to Tahoe `IRepairResults`, and input check results are coerced to `ICheckResults`.

Risks: Repair is intentionally conservative but `force=True` can lose data by skipping unrecoverable newer seqnums or choosing one recoverable concurrent head. Repair currently requires a writecap even for share redistribution because it needs write-enablers and signing keys. The `RepairResults.to_string` implementation is empty, limiting diagnostics. The original `check_results` are only used for storage-index validation; repair always performs a new MODE_REPAIR scan, so callers expecting reuse of check detail may be surprised.

Test signals: Tests should cover no recoverable version, normal repair of missing/old/bad shares, writecap absence, unrecoverable newer version with and without force, merge-needed condition with and without force, history status notification, download with private-key fetch, upload invocation with the refreshed servermap, and unsuccessful vs successful `RepairResults`.
