# sources/distributed-fs/tahoe-lafs/src/allmydata/mutable/layout.py

Purpose: Defines the packed on-storage layouts for Tahoe-LAFS mutable shares and provides read/write proxy classes that translate high-level mutable-file operations into storage-server read/write vectors. It supports both legacy SDMF shares and MDMF shares, including checkstrings, signed prefixes, offset tables, block data, block hash trees, share hash chains, signatures, verification keys, and encrypted private keys.

Important APIs and types: Top-level helpers `unpack_header`, `unpack_share`, `get_version_from_checkstring`, `unpack_sdmf_checkstring`, `unpack_mdmf_checkstring`, `pack_offsets`, `pack_share`, and `pack_prefix` encode and decode SDMF-compatible structures used by tests and by publish/servermap error handling. `SDMFSlotWriteProxy` implements `IMutableSlotWriter` by accumulating a whole SDMF share in memory and writing it once during `finish_publishing`. `MDMFSlotWriteProxy` implements the same writer interface with queued storage write vectors and an explicit offset table. `MDMFSlotReadProxy` is the shared read proxy for both SDMF and MDMF shares; it lazily fetches headers/offsets and exposes block, hash, key, signature, checkstring, prefix, encoding parameter, and version-info accessors. `LayoutInvalid` subclasses `BadShareError` for malformed layout or invalid write ordering.

Control flow: SDMF writing is simple and whole-share oriented: the caller sets block data, encrypted private key, block/share hashes, root hash, signature, and verification key; `get_signable` packs the signed prefix; `finish_publishing` asserts all pieces exist, constructs offsets, concatenates the final share, and calls `slot_testv_and_readv_and_writev` with a new-share test vector unless a caller provided an existing checkstring. MDMF writing is staged: initialization computes segment counts, block sizes, tail block size, fixed leading offsets, share-data location, and block-hash-tree location; `put_block` queues per-segment salt+block writes; `put_encprivkey`, `put_blockhashes`, `put_sharehashes`, `put_root_hash`, `put_signature`, and `put_verification_key` progressively fill offsets and enqueue writes; `finish_publishing` appends the offset table and encoding parameters, then `_write` sends the accumulated vectors with test vectors and first-write checkstring handling. Read flow starts with `_maybe_fetch_offsets_and_header`, which reads enough bytes to identify SDMF vs MDMF, parse encoding parameters, compute segment/tail sizes, and parse offsets. Later getters build precise read vectors from the cached offsets, first trying local cached data and falling back to `slot_readv`.

State and persistence: The module defines Tahoe's mutable share persistence format. SDMF offsets use fixed 32-bit and 64-bit fields after the signed prefix; MDMF uses a signable header followed by eight 64-bit offsets. Writer proxies hold transient state such as `_share_pieces`, `_offsets`, `_writevs`, `_testvs`, `_root_hash`, and `_written`; persistence happens only when storage-server slot write APIs accept the vectors. Reader proxies cache parsed header fields, offsets, version number, sequence number, root hash, salt for SDMF, encoding parameters, computed segment sizes, and optional prefetched data. Checkstrings are central concurrency state: SDMF checkstrings include version, sequence number, root hash, and salt; MDMF checkstrings include version, sequence number, and root hash.

Dependencies and integration points: The proxies are consumed by `publish.py`, `retrieve.py`, and `servermap.py`. They depend on Tahoe constants and interfaces from `allmydata.interfaces`, mutable exceptions from `allmydata.mutable.common`, `mathutil` for segment math, Twisted `Deferred`/`Failure`, and storage-server APIs `slot_testv_and_readv_and_writev` and `slot_readv`. Hash sizes and salt sizes must align with `hashutil`, `hashtree`, and the erasure codec used by publish/retrieve.

Risks: The format code is highly order-sensitive; using `MDMFSlotWriteProxy` methods out of sequence raises `LayoutInvalid` or can leave queued write vectors inconsistent. Several invariants rely on `assert`, so optimized Python would remove some validation. MDMF reserves fixed maximum sizes for private keys, signatures, verification keys, and share hash chains before it knows actual lengths; unusual key/signature sizes or share counts can challenge those assumptions. `_read` requires all requested vectors to be satisfiable from cached data before avoiding a remote read, which can underuse partial cache data. SDMF write assembly holds the full share in memory. Offset parsing converts `struct.error` into `BadShareError`, but malformed offset ordering or unexpectedly short data can still surface later through empty reads or downstream validation failures.

Test signals: Unit tests should cover SDMF and MDMF checkstring packing/unpacking, unknown version rejection, short-read `NeedMoreDataError`, malformed hash-chain/block-hash lengths, empty files, tail segments, and all read getters against cached and remote data. Writer tests should exercise new-share and existing-share test vectors, MDMF first-write checkstring update, invalid method order, segment bounds, salt/block size validation, offset table correctness, and storage-server failure responses. Integration tests should verify publish/servermap/retrieve agree on `verinfo` tuple contents for both SDMF and MDMF.
