# sources/distributed-fs/ceph/src/rgw/rgw_rest_s3.cc

## Purpose
`rgw_rest_s3.cc` is Ceph RADOS Gateway's main S3 REST dialect implementation. It maps parsed HTTP requests to S3 service, bucket, object, website, STS/IAM/pubsub, and s3control handlers; parses S3-specific query parameters, XML bodies, multipart form uploads, and headers; formats S3 XML/JSON/HTTP responses; and wires S3 authentication through local RGW users, STS session tokens, LDAP, anonymous access, and AWS Signature V2/V4 canonicalization.

The file is intentionally broad: it is the protocol adapter between generic RGW object-store operations and S3-compatible wire behavior. The backing object, bucket, user, sync-policy, lifecycle, CORS, encryption, object-lock, usage, and multipart persistence mostly lives in lower RGW/SAL layers, while this file decides which operation class runs, how inputs are interpreted, which attributes are exposed as S3 headers/XML, and which request bodies must be forwarded to the metadata master zone.

## Important APIs, types, and functions
Top-level response helpers include `list_all_buckets_start()`, `list_all_buckets_end()`, `dump_bucket()`, `rgw_get_errno_s3()`, `get_s3_expiration_header()`, `get_s3_multipart_abort_header()`, `decode_attr_bl_single_value()`, `content_encoding_without_aws_chunked()`, `create_s3_policy()`, `map_qs_metadata()`, and `parse_post_action()`.

`get_encryption_defaults()` is a central request-normalization function. It merges explicit SSE request headers with bucket default encryption from `RGW_ATTR_BUCKET_ENCRYPTION_POLICY`, rejects incompatible SSE-C plus SSE-KMS/SSE-S3 combinations, fills missing KMS algorithm/key/bucket-key fields from bucket configuration, and sets `s->err.message` for S3-style validation failures.

Object operations implemented here include `RGWGetObj_ObjStore_S3`, `RGWPutObj_ObjStore_S3`, `RGWPostObj_ObjStore_S3`, `RGWDeleteObj_ObjStore_S3`, `RGWCopyObj_ObjStore_S3`, `RGWRestoreObj_ObjStore_S3`, `RGWGetObjAttrs_ObjStore_S3`, object tagging operations, object retention/legal-hold operations, S3 Select dispatch, object layout debugging, multipart init/complete/list/abort, and multi-object delete.

Bucket/service operations include list-all-buckets, list-bucket V1/V2 and versions, bucket stat/HEAD, create/delete bucket, location, versioning, website, ACL, lifecycle, CORS, request payment, bucket/object-lock config, public access block, ownership controls, bucket encryption, bucket policy/status, metadata search config, usage, notification/pubsub integration, bucket logging integration, and replication configuration.

`ReplicationConfiguration` and nested `Rule`, `Filter`, `Destination`, `Source`, and `DeleteMarkerReplication` are local XML adapter types. They translate AWS-style bucket replication XML plus RGW zone extensions into `rgw_sync_policy_group` and `rgw_sync_bucket_pipes`, using two fixed policy group ids: `s3-bucket-replication:enabled` and `s3-bucket-replication:disabled`.

Handler classes `RGWHandler_REST_Service_S3`, `RGWHandler_REST_Bucket_S3`, and `RGWHandler_REST_Obj_S3` choose operation objects based on HTTP verb and subresources. `RGWRESTMgr_S3` performs manager-level routing, including s3control path detection, virtual-host-style bucket rewriting, S3 website routing, and POST service dispatch to STS, IAM, or pubsub action handlers.

Website classes `RGWHandler_REST_S3Website`, `RGWHandler_REST_*_S3Website`, and `RGWGetObj_ObjStore_S3Website` retarget bucket/object GET and HEAD requests through website index/error/redirect rules and emit website redirect responses.

Authentication classes and helpers in `rgw::auth::s3` include `discover_aws_flavour()`, `AWSGeneralAbstractor`, `AWSGeneralBoto2Abstractor`, `AWSBrowserUploadAbstractor`, `AWSSignerV4`, `AWSEngine`, `LDAPEngine`, `LocalEngine`, `STSEngine`, and `S3AnonymousEngine`. They parse V2/V4 credentials, build canonical requests/strings-to-sign, decide whether body-completion authentication is needed, and create local, remote, role, or anonymous auth appliers.

## Control flow
Request routing starts in `RGWRESTMgr_S3::get_resource_mgr_as_default()` and `RGWRESTMgr_S3::get_handler()`. The manager first gives s3control requests with `x-amz-account-id` and `/v20180820` to the s3control manager, rewrites virtual-host-style requests into path-style state, and diverts website-domain requests to the website manager. `RGWHandler_REST_S3::init_from_header()` parses query args, allocates a formatter, extracts URL bucket/object/version state, and builds placeholder `s->object` values. After auth, `postauth_init()` resolves tenants from URL bucket names, validates bucket/object names, parses copy-source tenants, and checks MFA if present.

Operation selection is mostly verb plus subresource. Service GET lists buckets or usage; bucket GET handles location/versioning/website/ACL/CORS/uploads/lifecycle/policy/tagging/object-lock/notification/replication/policy-status/public-access/encryption/ownership, otherwise list objects; object GET handles ACL, multipart parts, layout, tagging, attributes, retention/legal hold, otherwise object data. PUT/POST/DELETE branches similarly select bucket config writes, object upload/copy, multipart completion/init, restore, S3 Select, delete tagging, abort multipart, or multi-object delete.

GET object response flow parses optional sync, checksum, torrent, and `partNumber` parameters, then `send_response_data()` emits headers before body. It handles system-request metadata prepending, replication headers, multipart part counts, full-object or composite checksum headers under `x-amz-checksum-mode: ENABLED`, restore status, response header overrides, user metadata, object tags count, object lock headers, content type, range, ETag, expiration, version id, and appendable object metadata. Website GET wraps this path and turns `RGW_ATTR_AMZ_WEBSITE_REDIRECT_LOCATION` into a 301 redirect.

Write flows normalize metadata and encryption first, then rely on base RGW operations for storage. PUT object requires content length or chunked transfer, parses tags, object lock headers, multipart `uploadId`/`partNumber`, append position, conditional headers, canned/header ACLs, and then calls the base put implementation. POST browser upload reads multipart form fields until the `file` part, reconstructs `${filename}` keys, builds policy environment variables, validates policy/signature, extracts user metadata/tags/storage class, streams data until the multipart boundary, and drains remaining form parts. Copy object validates source condition headers and self-copy storage-class/metadata rules, then streams chunked progress until final `CopyObjectResult`.

Bucket configuration flows read bounded request bodies using `rgw_max_put_param_size`, parse XML with RGW XML decoders, validate S3-specific limits, encode persistent config into `bufferlist` or structured fields, and store `in_data` when a non-meta-master zone must forward the original request. This pattern appears in bucket tagging, replication, versioning, website, CORS, request payment, ownership controls, create bucket, and similar metadata operations.

Authentication flow discovers V2/V4 and header/query routing, then asks the configured auth strategy registry to apply S3 auth. V4 auth parses credential scope, signed headers, signature, date, and optional token; builds canonical headers, URI, query, method, canonical request hash, and string-to-sign; then chooses no completer, single-chunk completer, or streaming completer based on payload hash mode and operation type. Local auth loads the RGW user by access key, loads account/IAM policies, compares the computed signature, supports system-user impersonation via `rgwx-perm-check-uid`, and grants a local applier. STS auth decrypts the session token with `rgw_sts_key`, validates expiry and signature, then grants remote, role, or local appliers based on token account type.

## State and persistence behavior
The file mutates `req_state` heavily: `s->info.args`, `s->object_key`, `s->object`, tenant/bucket/source bucket names, `s->info.x_meta_map`, `s->info.crypt_attribute_map`, error messages, redirects, canned ACL state, MFA state, storage class, auth post-object credentials, and formatter state. Many functions only set operation fields for base classes to persist later, for example `policy`, `tags_bl`, `cors_bl`, `sync_policy_groups`, `website_conf`, `obj_retention`, `obj_legal_hold`, `cksum_algo`, and multipart ids.

Persistent cluster effects are delegated to base RGW operations and SAL objects, but this file decides the payload and metadata that are persisted: bucket encryption defaults and object SSE attributes, object tags, retention/legal hold, lifecycle and CORS blobs, bucket website config, bucket object lock config, public access block, ownership controls, request payment, replication sync policy groups, bucket index options on create, metadata-search schema, bucket/object ACL policies, multipart checksums, and appendable object state.

Multisite/meta behavior is explicit. System requests can request raw manifests, skip decryption, fetch cloud-tiered objects, prepend encoded object metadata, include RGWX mtime/pg/source-zone headers, and impersonate permission checks. Non-meta-master bucket metadata updates preserve the original input body in `in_data` so the operation can be forwarded to the metadata master. Replication configuration converts user-facing XML into sync policy pipes with enabled and disabled policy groups.

No direct durable writes happen in this translation layer beyond calling lower-level operation methods. Durable behavior emerges from encoded attributes placed on request/operation state and from base classes that consume them.

## Dependencies and integration points
This file depends on core RGW request/response helpers from `rgw_rest.h`, S3 declarations from `rgw_rest_s3.h`, website declarations from `rgw_rest_s3website.h`, s3control, pubsub, STS, IAM, bucket logging, role, and user-policy REST handlers. It uses `rgw_common`, `rgw_acl`, `rgw_policy_s3`, `rgw_cors_s3`, `rgw_tag_s3`, `rgw_bucket_sync`, `rgw_zone`, `rgw_crypt`, `rgw_cksum`, `rgw_cksum_pipe`, `rgw_s3select`, and SAL driver/object/bucket/user interfaces.

External/library dependencies include Boost string/tokenizer utilities, liboath for MFA-related support through user verification, Ceph buffer encoding/decoding, Ceph JSON/XML formatters, crypto handlers for STS token decryption, and config values from `CephContext`.

Important integration boundaries are `rgw::sal::Driver` for users, roles, zones, accounts, buckets, objects, multipart uploads, placement validation, and sync policy handlers; `rgw::auth::StrategyRegistry` for S3, post-object, STS/IAM, and anonymous auth; `RGWHTTPArgs`/`RGWEnv` for normalized HTTP inputs; and base operation classes such as `RGWGetObj_ObjStore`, `RGWPutObj_ObjStore`, `RGWCompleteMultipart_ObjStore`, and bucket metadata operations that perform storage-side work.

## Risks and edge cases
The file is a high-blast-radius protocol adapter. Small changes can affect AWS compatibility, clients, multisite replication, auth, encryption, and error-code mapping at once.

Header and query parsing is security-sensitive. `send_response_data()` explicitly rejects unauthenticated response-header overrides and control characters to avoid header injection. V4 auth has many payload-hash modes, and the list of operation types allowed to use delayed single-chunk auth must stay aligned with operations that read bodies. Query-string presigned URL handling is controlled by config and has separate V2/V4 expiry/token paths.

Encryption normalization has subtle precedence rules. Explicit SSE-C bypasses bucket defaults, explicit KMS-related fields without a REST encryption algorithm are rejected, bucket default KMS fields can synthesize request headers, and multipart part encryption reuses metadata from the multipart meta object. Incorrect ordering can break both user uploads and replicated/system requests that need encrypted bytes and attributes.

Website handling mutates `s->object` during retargeting and contains comments noting pointer-safety concerns if operation objects had captured the old object. Error-document serving manually constructs and runs a GET operation inside the error handler, so permission, formatter, and object state ordering are fragile.

S3 compatibility includes many intentionally special cases: bucket-create `-ERR_BUCKET_EXISTS` can map to success unless `rgw_bucket_eexist_override` is set; DELETE of missing objects maps to 204; delete tagging and bucket delete config return 204; `Content-Encoding: aws-chunked` is stripped from stored response headers; list-v2 and versioned list XML element names have compatibility quirks; and policy-status boolean casing follows client expectations rather than only documentation wording.

Replication config conversion can silently ignore zone names that cannot be resolved, validates duplicate priorities, and only supports owner ids stored as `rgw_user`. Destination bucket ARN parsing, tenant inheritance, old stored ARN compatibility, ACL translation owners, and enabled/disabled group mapping are all important to preserve.

The file uses raw `new` operation allocation throughout handler dispatch, relying on RGW handler ownership conventions. Many request-body paths read bounded inputs, but multipart browser upload streams through custom boundary parsing, so malformed boundaries and large form-data sequencing remain important test targets.

## Test signals
High-value tests include GET/HEAD object with range, response header overrides, anonymous override rejection, control-character rejection, `aws-chunked` content-encoding stripping, checksum mode for single-part/multipart/composite/full-object CRC cases, restore headers, replication trace/timestamp headers, object lock response headers, and system-request metadata prepending with and without tag permission.

Write-path tests should cover PUT object with content length versus chunked transfer, SSE-C/SSE-S3/SSE-KMS/default bucket encryption combinations, KMS context and bucket-key validation, object tags, retention/legal hold with disabled/enabled object-lock bucket config, conditional headers, append position errors, multipart part upload encryption/checksums, complete multipart auth completion, and copy-object self-copy metadata/storage-class validation.

Bucket metadata tests should cover create bucket XML location constraints, placement/storage class parsing, bucket index type/shards limits, object ownership header parsing, versioning and MFA delete XML, website index/redirect/error docs and routing-rule limits, lifecycle absent versus malformed attributes, CORS malformed XML and rule limits, tagging limits, request payment XML, ownership controls XML, public access block, bucket encryption get/put/delete absent mapping, and metadata-search expression parsing.

Replication tests should cover valid enabled/disabled rules, duplicate priorities, prefix/tag/and filters, delete-marker status validation, destination ARN validation, zone-name resolution, ACL translation, storage class, old stored destination ARN round trips, legacy sync-policy handler rejection, and non-meta-master forwarding of original XML.

Routing tests should cover path-style and virtual-host-style requests, s3control `/v20180820` with `x-amz-account-id`, website-domain routing, service POST dispatch to STS/IAM/pubsub by action body, object-exclusive subresource rejection at bucket scope, S3 Select POST selection, and OPTIONS CORS anonymous handling.

Auth tests should cover V2 header and query signatures including expiry and session token, V4 header and presigned signatures, disabled presigned URLs, empty payload hash mismatch, unsigned payload, streaming signed payload, unsigned chunked payload with checksum trailer, browser POST V2/V4 policy verification, local access key mismatch, system-user impersonation, STS token decryption/expiry/role/local/remote appliers, LDAP token auth, and anonymous query-route applicability.
