# sources/distributed-fs/orangefs/src/kernel/linux-2.6/namei.c

Purpose: Implements OrangeFS/PVFS2 directory inode operations for pathname creation, lookup, unlink/rmdir, symlink, mkdir, rename, and explicit unsupported hard-link/special-file behavior.

Important APIs and functions: `pvfs2_dir_inode_operations` exports directory inode operations. `pvfs2_create`, `pvfs2_symlink`, and `pvfs2_mkdir` delegate object creation to `pvfs2_create_entry` with operation types `PVFS2_VFS_OP_CREATE`, `PVFS2_VFS_OP_SYMLINK`, and `PVFS2_VFS_OP_MKDIR`. `pvfs2_lookup` performs `PVFS2_VFS_OP_LOOKUP` and attaches dentry operations. `pvfs2_unlink` removes files and directories via `pvfs2_remove_entry`. `pvfs2_rename` constructs and services `PVFS2_VFS_OP_RENAME`. `pvfs2_link` and `pvfs2_mknod` return `-EOPNOTSUPP`.

Control flow: Create-like operations call `pvfs2_create_entry`, and on returned inode success update the parent directory mtime flag, refresh inode time, mark the directory dirty, and return 0. Lookup validates name length, allocates an op, sets no-follow symlink lookup semantics, chooses the parent object reference from `PVFS2_I(dir)->refn` or a root/fallback handle, copies the target name, and calls `service_operation`. `-ENOENT` produces a negative dentry with OrangeFS dentry operations so later cached lookups can revalidate. Successful lookups call `pvfs2_iget` on the returned object reference and splice aliases into the dcache. Bad inodes are converted to the stored OrangeFS error code when possible. Rename obtains old/new parent references, copies old/new names, services the rename op, updates overwritten target ctime, releases the op, and on old kernels moves the dentry manually.

State and persistence: Namespace changes persist through client-core operations such as create/remove/rename. The kernel-side state updated here includes dcache positive/negative entries, dentry operations, inode link counts for unlink, parent directory mtime flags, dirty inode marking, and ctime for replaced dentries. Directory hard-link counts are intentionally not fully maintained for distributed clients; related code is disabled with comments.

Dependencies and integration points: Depends on Linux VFS inode/dentry operation contracts, dcache aliasing, kernel feature macros for changing operation signatures, and OrangeFS helpers from `pvfs2-kernel.h`/`pvfs2-internal.h`: `pvfs2_create_entry`, `pvfs2_remove_entry`, `op_alloc`, `service_operation`, `PVFS2_I`, `PVFS2_SB`, `PVFS_khandle_from`, `pvfs2_iget`, `pvfs2_d_splice_alias`, `pvfs2_dentry_operations`, `SetMtimeFlag`, and `pvfs2_update_inode_time`.

Risks: `pvfs2_lookup` allocates a debug buffer and uses it without checking for NULL in several paths. Rename does not perform the explicit `PVFS2_NAME_LEN - 1` length check that lookup performs before `strncpy`; long names risk truncation unless VFS validation always catches them earlier. Symlink creation uses `mode = 755`, which is decimal rather than octal `0755`, and may not represent intended permissions if the mode is consumed directly. Directory nlink maintenance is mostly disabled, so local link counts are approximate in distributed scenarios. Rename updates local ctime and may alter local dcache state even if subtle remote errors are returned through status conventions not captured by `ret`; service/downcall-status handling should be verified. Fallback parent-handle logic is unsafe with `iget4/5` and intentionally returns `-EINVAL` where inode numbers cannot be trusted.

Test signals: Exercise create/open-exclusive races, lookup hit/miss and negative-dentry revalidation, interrupted lookups, bad-inode error propagation, long names in lookup and rename, symlink target creation and mode, mkdir/rmdir/unlink parent timestamp updates, hard-link and mknod `-EOPNOTSUPP`, rename over files and directories across parents, dcache alias splicing, root/fallback parent references, and all signature variants controlled by kernel feature macros.
