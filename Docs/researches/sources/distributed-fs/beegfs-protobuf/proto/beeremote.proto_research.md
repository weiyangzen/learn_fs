# sources/distributed-fs/beegfs-protobuf/proto/beeremote.proto

**Purpose:** This proto defines the externally facing BeeRemote gRPC API for submitting, querying, updating, and completing remote storage jobs. It coordinates user requests, BeeRemote job state, worker-node work results, remote storage target configuration, stub-file lookup, and capability discovery.

**Important APIs/types/functions:** Service `BeeRemote` exposes `SubmitJob`, `UpdatePaths`, `UpdateJobs`, streaming `GetJobs`, worker-only `UpdateWork`, `GetRSTConfig`, `GetStubContents`, and `GetCapabilities`. Core messages include `JobRequest`, `Job`, `JobResult`, `UpdateJobsRequest/Response`, `GetJobsRequest/Response`, `UpdateWorkRequest/Response`, and RST/stub messages. `JobRequest` contains path, name, priority, RST ID, force/update/stub flags, generation status, and a oneof job type from `flex.SyncJob`, `flex.MockJob`, or `flex.BuilderJob`. `Job` adds ID, creation timestamp, status, external ID, and start/stop mtimes. `Job.State` and `SubmitJobResponse.ResponseStatus` document accepted, terminal, retry, and precondition states.

**Control flow:** Clients submit a `JobRequest` and receive a `JobResult` with a status indicating whether the job was created, already existed, was blocked, or had already reached a terminal/offloaded state. Jobs are updated by exact path, path prefix, job ID, and/or remote target filters. `GetJobsRequest` uses a oneof query for job ID plus path, exact path, or path prefix, with optional inclusion of deterministic work requests and latest work results. Workers return work through BeeRemote's unary `UpdateWork`, intentionally avoiding a reverse streaming result channel. `UpdatePaths` streams one update result per matching path.

**State and persistence behavior:** Comments explicitly describe BeeRemote persistence as separate key/value stores for `Job` records and `WorkResult` records, with deterministic `WorkRequest` generation to reduce stored data. Job state transitions distinguish unassigned, scheduled, running, transient error, failed, cancelled, completed, and offloaded. `start_mtime` and `stop_mtime` are optional timestamps captured around execution and must be interpreted with job state. `generation_status` allows generated requests to represent already-complete/offloaded and precondition/error outcomes before scheduling.

**Dependencies and integration points:** Imports `flex.proto` for work, worker capability, job type, and RST definitions, plus `google/protobuf/timestamp.proto`. Integrates with BeeSync/worker nodes through `flex.Work`, with remote storage target config through `flex.RemoteStorageTarget`, and with clients that need job listings or stub contents.

**Risks:** The schema documents many invariants that generated code will not enforce: worker-only `UpdateWork`, safe use of `FAILED_PRECONDITION`, allowed state transitions, terminal-state immutability, and cleanup before resubmission. `remote_storage_target` is only a numeric ID, so callers need external config consistency. Query flexibility is limited by the backing key/value indexes. Status message concatenation can grow if implementations ignore reset guidance. Force/update/stub semantics require careful implementation to avoid duplicate active work or data loss.

**Test signals:** Service tests should cover idempotent submission, duplicate/completed/offloaded outcomes, forced resubmission, generation status handling, job update filters, path-prefix streaming, work result ownership transfer, and stub lookup. Persistence tests should verify job/work-result store separation, deterministic work request reconstruction, status transitions, mtime capture, and compatibility for the `GetJobsRequest` oneof.
