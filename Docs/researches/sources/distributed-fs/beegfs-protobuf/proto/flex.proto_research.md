# sources/distributed-fs/beegfs-protobuf/proto/flex.proto

**Purpose:** This proto defines common BeeGFS Flex/BeeRemote worker-node contracts: worker lifecycle RPCs, job/work request shapes, work status reporting, remote storage target configuration, node statistics, and capability/build metadata.

**Important APIs/types/functions:** Service `WorkerNode` exposes `UpdateConfig`, `Heartbeat`, `SubmitWork`, `UpdateWork`, `BulkUpdateWork`, and `GetCapabilities`. Job/work messages include `JobLockedInfo`, `JobRequestCfg`, `WorkRequest` with segment ranges and job type oneof, `BuilderJob`, `MockJob`, `SyncJob`, and `Work` with status and repeated parts. Configuration messages include `UpdateConfigRequest/Response`, `BeeRemoteNode`, and `RemoteStorageTarget` with oneof `S3`, `POSIX`, `Azure`, or `mock`. Capability messages include `GetCapabilitiesResponse`, recursive `Feature`, and `BuildInfo`.

**Control flow:** BeeRemote configures worker nodes with BeeRemote endpoint/auth data and the full RST list. Heartbeats report readiness and optional stats. BeeRemote submits `WorkRequest` records; workers respond with `Work`, then later update status and parts. `UpdateWork` cancels a single request, while `BulkUpdateWork` currently supports unchanged bulk handling for startup/drain scenarios. Sync jobs describe what to do, work requests describe assigned segments, and work parts describe per-worker transfer progress.

**State and persistence behavior:** Work status is the central state machine: unknown, created, scheduled, running, rescheduled, transient error, failed, cancelled, and completed. Terminal worker states mean the worker should no longer retain or act on that request after returning the response. `Work.Part` stores part number, offsets, ETag, SHA-256 checksum, and completion. `JobLockedInfo` captures file state, remote state, stub URL info, external ID, and archive status used before building jobs. RST config is replaced wholesale: omitted RSTs are deleted by contract.

**Dependencies and integration points:** Imports protobuf `Timestamp`. `beeremote.proto` imports and reuses this file heavily for job types, work requests/results, RST config, and capabilities. Implementations integrate with BeeSync workers, BeeRemote management, S3-compatible object stores, POSIX paths, Azure modeled through S3-like config plus account, and build/capability reporting.

**Risks:** Generated code does not enforce worker ownership, valid state transitions, segment/part bounds, RST type support, archival restore polling durations, or secure handling of auth secrets and storage credentials. `RemoteStorageTarget.Azure` embeds S3 config, so consumers must understand provider-specific interpretation. Config update semantics delete missing RSTs, which is risky on partial config generation. Several fields use proto names that map awkwardly in some languages, such as `externalId` and `remoteStorageTarget`.

**Test signals:** Tests should exercise heartbeat readiness, config replacement including deletion of omitted RSTs, SubmitWork and UpdateWork transitions, cancellation, terminal cleanup, part checksum/ETag persistence, segment splitting, archived object restore options, RST type unmarshalling, capability recursion, and compatibility with BeeRemote job/result messages.
