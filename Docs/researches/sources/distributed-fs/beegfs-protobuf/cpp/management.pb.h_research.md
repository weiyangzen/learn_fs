- `primary_consistency_state` and `secondary_consistency_state`: `beegfs::ConsistencyState` enum fields, stored as integers and cleared to `0`.
- `storage_pool`: optional `beegfs::EntityIdSet`, required semantically only for storage targets and unset for non-storage targets.

`GetBuddyGroupsResponse` wraps the result list:

- `buddy_groups`: repeated `GetBuddyGroupsResponse_BuddyGroup` using `google::protobuf::RepeatedPtrField`. The generated API includes size, clear, indexed mutable/get, list mutable/get, and `add_buddy_groups()`.

`CreateBuddyGroupRequest` carries the inputs for buddy group creation:

- Optional `node_type`: must semantically be `META` or `STORAGE`.
- Optional `num_id`: requested numeric id, with receiver choice if omitted.
- Optional `alias`: required semantically by the proto comments, backed by `ArenaStringPtr`. The generated string API has presence, clear, templated `set_alias()`, mutable, release, and allocated-string helpers.
- Optional `primary_target` and `secondary_target`: `EntityIdSet` pointers where one identifier is sufficient according to the proto comments.

`CreateBuddyGroupResponse` returns optional `group`, the fully populated new buddy group `EntityIdSet`.

`DeleteBuddyGroupRequest` has optional `group` and optional `execute`. `execute=false` is a dry-run feasibility check, while `true` performs deletion. `DeleteBuddyGroupResponse` returns optional `group`, the fully populated deleted group.

`MirrorRootInodeRequest` and `MirrorRootInodeResponse` are zero-field messages, so no accessors appear beyond section dividers in this inline range.

`StartResyncRequest` has:

- Optional `buddy_group`: the buddy group whose secondary target should be resynced.
- Optional `timestamp`: an `int64` Unix timestamp in seconds, with `-1` meaning a full resync. The proto comments require `-1` for metadata buddy groups.
- Optional `restart`: whether to abort and restart an ongoing resync. The proto comments require `false` for metadata buddy groups.

`StartResyncResponse` is a zero-field message.

### Quota Model And Quota RPCs

`QuotaInfo` is the shared per-id, per-id-type, per-pool quota payload:

- Optional `quota_id`: system user or group id.
- `id_type`: `beegfs::QuotaIdType`, stored as an integer enum with no presence bit because it is not declared `optional`.
- Optional `pool`: `beegfs::EntityIdSet`.
- Optional `space_limit` and `inode_limit`: signed 64-bit limits where `-1` means unlimited.
- Optional `space_used` and `inode_used`: signed 64-bit usage counters.

The same `QuotaInfo` message has different semantic subsets depending on RPC. For returned data, availability controls whether limit and usage fields are set. For setting limits, `_used` fields should be ignored and the limit fields are optional.

`SetDefaultQuotaLimitsRequest` sets pool defaults:

- Optional `pool`.
- Optional `user_space_limit`, `user_inode_limit`, `group_space_limit`, and `group_inode_limit`, all signed 64-bit and using `-1` for unlimited.

`SetDefaultQuotaLimitsResponse` is zero-field.

`SetQuotaLimitsRequest` has repeated `limits`, a `RepeatedPtrField<QuotaInfo>` representing explicit per-id-and-pool quota limits. `SetQuotaLimitsResponse` is zero-field.

`GetQuotaLimitsRequest` filters explicitly set quota limits:

- Optional `user_id_min` and `user_id_max`.
- Repeated `user_id_list`.
- Optional `group_id_min` and `group_id_max`.
- Repeated `group_id_list`.
- Optional `pool`.

`GetQuotaLimitsResponse` contains optional `limits`, a single `QuotaInfo` entry. The response is intentionally single-entry because the RPC is server-streaming.

`GetQuotaUsageRequest` uses the same user/group id range and list filters plus optional `pool`, and adds optional `exceeded` to restrict results by exceeded/non-exceeded status. `GetQuotaUsageResponse` contains:

- Optional `entry`: a single streamed `QuotaInfo` usage entry.
- Optional `refresh_period_s`: quota refresh period in seconds, intended by proto comments to be set only on the first response in the stream.

### Licensing

`GetLicenseRequest` has optional `reload`, telling the receiver whether to reload and re-verify the license before responding.

`GetLicenseResponse` has optional `cert_data`, a `license::GetCertDataResult` imported from `license.pb.h`. The proto comments allow omission when no license data is available.

### Common Generated Accessor Patterns

For optional scalar fields, generated accessors follow the same pattern:

- `has_*()` checks a bit in `_impl_._has_bits_[0]`.
- `clear_*()` resets the value to its protobuf default and clears the presence bit.
- `set_*()` writes the value and sets the presence bit.
- `_internal_*()` reads the backing field; `_internal_set_*()` writes it.

For enum fields, setters accept the generated enum type but do not enforce business-level validity such as "must be META or STORAGE". The backing storage is an integer, so parsed unknown enum values and default zero values need defensive handling by higher-level code.

For message fields such as `EntityIdSet`, `QuotaInfo`, and `GetCertDataResult`, generated accessors include:

- `has_*()` with `PROTOBUF_ASSUME` that a present field has a non-null pointer.
- `clear_*()` where available, which clears the nested message and clears presence.
- `_internal_*()` returning either the stored message or that type's default instance.
- `mutable_*()` that sets presence and lazily default-constructs the nested message on the parent arena.
- `release_*()` that clears presence, detaches the pointer, and duplicates when arena ownership requires it.
- `set_allocated_*()` that deletes the old heap-owned child when appropriate and uses `GetOwnedMessage()` if parent and child arenas differ.
- `unsafe_arena_set_allocated_*()` and `unsafe_arena_release_*()` for arena-aware fast paths that rely on caller lifetime discipline.

For repeated fields, generated methods expose size, clear, indexed access, indexed mutation, whole-container mutable access, add, and whole-container const access. Repeated scalar lists use `RepeatedField<uint32_t>`; repeated message lists use `RepeatedPtrField<T>`.

## Control Flow

There is no application-level branch or RPC implementation logic in this chunk. Runtime behavior is the standard generated protobuf lifecycle:

1. Client or server code constructs a message, optionally on a `google::protobuf::Arena`.
2. Callers populate scalar fields through `set_*()`, nested messages through `mutable_*()` or `set_allocated_*()`, strings through `set_alias()` or `mutable_alias()`, and repeated fields through `add_*()` or `mutable_*()`.
3. Optional fields update `_has_bits_` so receivers can distinguish absence from an explicit protobuf default value.
4. Serialization, parsing, clearing, merging, copying, swapping, descriptor lookup, and cached-size management are implemented by generated methods declared elsewhere in the header and defined in `management.pb.cc`.
5. Service-layer code sends or receives these payloads through the `Management` gRPC methods defined in `management.proto`.

The business workflows implied by the schema are:

- Buddy group list calls produce repeated topology entries containing group identity, node type, primary/secondary targets, target consistency states, and storage pool information when applicable.
- Buddy group creation/deletion calls consume identifying information and return fully populated identifiers.
- Metadata mirroring and resync calls are command-style RPCs with mostly empty responses.
- Quota set calls mutate management-side quota state, while quota query calls stream one `QuotaInfo` entry per response.
- License retrieval can optionally force a reload before returning certificate/license data.

Actual validation, state transitions, persistence, locking, streaming loops, and error reporting live outside this header.

## State And Persistence Behavior

This chunk only manages in-memory protobuf message state. It does not read or write BeeGFS management state, quota stores, license files, or network connections by itself. Persistence occurs when callers serialize these messages or when RPC handlers apply their contents to BeeGFS management services.

State mechanics visible in this range:

- Optional scalar, string, and message fields use `HasBits<1>` presence tracking. Absence matters for many fields, including `CreateBuddyGroupRequest.num_id`, quota filter bounds, quota limits, quota usage `exceeded`, response `refresh_period_s`, and license `cert_data`.
- Non-optional enum fields in this range, such as `GetBuddyGroupsResponse_BuddyGroup.node_type`, `primary_consistency_state`, `secondary_consistency_state`, and `QuotaInfo.id_type`, clear to enum value `0` and do not have generated `has_*()` accessors.
- Repeated lists preserve insertion order in memory and on the wire.
- Nested message fields are pointer-backed and may be absent, lazily allocated, heap-owned, or arena-owned depending on parent allocation and accessor usage.
- `release_*()` intentionally detaches child messages and may duplicate arena-owned children to produce a safe heap-owned result.
- `unsafe_arena_*()` methods bypass some ownership safety and should only be used when caller and parent lifetimes are known to share the same arena assumptions.
- The generated methods use `TSanRead` and `TSanWrite` annotations around field access. These annotations aid race detection but do not make messages inherently safe for unsynchronized concurrent mutation.

Semantic state and persistence constraints are expressed only in proto comments, not enforced here. For example, `DeleteBuddyGroupRequest.execute=false` is a dry run by convention, `StartResyncRequest.timestamp=-1` means full resync, quota `-1` means unlimited, and `GetQuotaUsageResponse.refresh_period_s` should appear only on the first streamed response.

## Risks And Edge Cases

Generated code should not be hand-edited. Changes made directly to `management.pb.h` can be overwritten and can desynchronize the C++ header from `management.pb.cc`, `management.proto`, and generated outputs for other languages.

The strict protobuf runtime version check can break builds if downstream code upgrades protobuf headers without regenerating this file. That is intentional ABI protection, but it is a packaging risk.

The generated API does not enforce schema comments. Higher-level handlers must validate required-by-comment fields, complete `EntityIdSet` contents where required, one-identifier-sufficient request fields, valid node types for buddy group creation, metadata-only resync constraints, quota range pairing constraints, and first-message-only `refresh_period_s`.

Presence and default values are easy to confuse. Optional `bool execute=false`, optional `bool restart=false`, optional `bool exceeded=false`, and optional numeric values set to `0` carry different meaning from absence. Callers should use `has_*()` when semantics depend on whether a field was explicitly supplied.

Enum fields may default to `0` or carry unknown wire values. Consumers should not treat the generated enum accessors as validation for `NodeType`, `ConsistencyState`, or `QuotaIdType`.

Quota values are signed 64-bit integers with `-1` used as unlimited for limits. Handlers need to guard against other negative values, overflow in conversions to filesystem accounting types, and accidental interpretation of usage fields in set-limit requests.

Streaming responses contain one payload entry per message. Clients that expect a repeated list inside a single response will mishandle `GetQuotaLimitsResponse` and `GetQuotaUsageResponse`.

Arena ownership helpers are sharp. Mixing heap messages, arena messages, `release_*()`, `set_allocated_*()`, and `unsafe_arena_*()` incorrectly can cause lifetime bugs. Code should prefer `mutable_*()` and normal setters unless an arena ownership optimization is deliberate and tested.

License data may contain operationally sensitive certificate or entitlement material. The generated `GetLicenseResponse` API offers no redaction or access control, so logging and debugging paths must handle `cert_data` carefully.
