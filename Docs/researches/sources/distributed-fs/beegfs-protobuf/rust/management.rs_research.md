## sources/distributed-fs/beegfs-protobuf/rust/management.rs

**Purpose:** Generated Prost/Tonic Rust bindings for the `management.Management` gRPC service. It is the public wire contract for administrative operations over BeeGFS entities: aliases, nodes, targets, storage pools, buddy groups, root mirroring, resync, quotas, and license data.

**Important APIs/types/functions:** Message structs include `SetAliasRequest`, node/target CRUD requests and responses, `GetPoolsResponse::StoragePool`, `GetBuddyGroupsResponse::BuddyGroup`, `QuotaInfo`, `GetQuotaLimits*`, `GetQuotaUsage*`, and `GetLicense*`. `management_client::ManagementClient<T>` exposes async client methods for every RPC with compression and message-size configuration. `management_server::Management` is the server trait with unary methods and two server-streaming associated types, `GetQuotaLimitsStream` and `GetQuotaUsageStream`; `ManagementServer<T>` routes HTTP/2 gRPC paths to those trait methods.

**Control flow:** Requests are plain `prost::Message` structs whose optional fields encode required-by-contract-but-validated-by-server values. The client wraps requests in `tonic::Request`, waits for readiness, inserts `GrpcMethod` metadata, then calls `unary` or `server_streaming` against paths such as `/management.Management/GetNodes`. The server `Service` implementation matches the URI path, constructs a small service adapter per RPC, applies compression and size limits, and delegates to the user implementation of `Management`; unknown paths return gRPC `Unimplemented`.

**State and persistence behavior:** The file itself persists no data. Persistence semantics are the protobuf wire field numbers and optional presence bits. Many comments mark fields as "Required" even when encoded as `Option<T>` because Prost cannot enforce business validation. Streaming quota replies carry one `QuotaInfo` per message, with `refresh_period_s` only intended on the first usage response. Durable compatibility depends on stable tags, enum numeric values imported from `super::beegfs`, and service method names.

**Dependencies and integration points:** Generated by `prost-build` and depends on `prost`, `tonic`, `tonic_prost`, HTTP/body codegen types, and sibling generated modules `beegfs` and `license`. It is consumed by the BeeGFS Rust management service and clients using the gRPC API, while the classic BeeMsg management logic in `beegfs-rust/mgmtd` maintains much of the same domain state in SQLite.

**Risks:** Manual edits will be lost on regeneration and can diverge from the `.proto` schema. Business-required fields are not enforced by the generated types, so server implementations must validate identifiers, enum values, dry-run/execute flags, quotas, and pool membership. Server-streaming quota methods can create large streams; implementers need backpressure and bounded database scans. Generated client/server code is tied to the Tonic/Prost versions used at generation time.

**Test signals:** Regenerate protobuf bindings and check for clean diffs. Compile a client and server implementation against this file. Exercise every unary route, both streaming quota routes, compression and message-size builders, unknown-path behavior, optional field validation in the service layer, and round-trip encoding for nested node, target, pool, buddy group, quota, and license messages.
