# sources/distributed-fs/beegfs-protobuf/go/license/license.pb.go

Purpose: generated Go protobuf bindings for `license.proto` under the `!protoopaque` build tag. This is the hybrid/non-opaque variant for BeeGFS license certificate verification data. It exposes public struct fields while still providing generated builder, getter, setter, presence, reflection, and wire-serialization behavior.

Important APIs/types/functions: enums are `VerifyResult` and `CertType`. `VerifyResult` has `VERIFY_UNSPECIFIED`, `VERIFY_ERROR`, `VERIFY_VALID`, and `VERIFY_INVALID`. `CertType` models `CERT_TYPE_UNSPECIFIED`, CA root, CA intermediate, partner, enterprise, trial, and community certificates. Messages are `VerifyCertResult`, `VerifyFeatureResult`, `GetCertDataResult`, and `CertData`. Each enum has `Enum`, `String`, `Descriptor`, `Type`, and `Number`. Each message has generated `Reset`, `String`, `ProtoMessage`, `ProtoReflect`, `Get...`, `Set...`, optional `Has...`/`Clear...`, and a builder type.

Control flow: there is no custom verification logic here; result production happens in callers or libraries that populate these messages. Generated control flow follows protobuf runtime conventions. `Reset` zeroes messages and stores message metadata. `ProtoReflect` returns reflection metadata, lazily storing message info if needed. Getters tolerate nil receivers and return schema default values. Setters assign public fields directly. `HasData`, `HasValidFrom`, `HasValidUntil`, and `HasParentData` check pointer presence, and corresponding clear methods nil those fields. `init() -> file_license_proto_init()` builds the descriptor once, registers the `CertData.parent_data` optional/oneof wrapper metadata, and releases raw descriptor/type dependency slices after build.

State and persistence behavior: state is held entirely in caller-owned protobuf message instances and on the protobuf wire. The hybrid structs expose data fields directly: result enums, serial/message strings, nested `CertData`, timestamp pointers, DNS name slices, and recursive parent certificate data. `unknownFields` and `sizeCache` support protobuf runtime behavior. There is no file or database persistence in this generated file. The `parent_data` field is encoded as a proto3 optional/oneof-style presence field, so absence and an explicitly supplied nested certificate can be distinguished.

Dependencies: imports are `protoreflect`, `protoimpl`, `timestamppb`, and `reflect`. The only external schema dependency is `google.protobuf.Timestamp` for `CertData.valid_from` and `CertData.valid_until`.

Integration points: this package is the wire contract between BeeGFS license generation/verification code and Go consumers. `VerifyCertResult` reports certificate verification status, a string serial on success, and an error/status message for error or invalid results. `VerifyFeatureResult` reports feature validation with a message. `GetCertDataResult` returns the currently loaded certificate's simplified data, even when verification failed, plus status. `CertData` is a simplified `x509.Certificate` projection with BeeGFS-specific certificate type, integer serial, subject attributes, common-name/subject-serial strings, validity range, DNS names that encode licensed features, CA flag, and optional recursive parent/issuer data.

Risks: this is generated code, so manual edits should be avoided. The hybrid build exposes fields publicly; callers can bypass setters and create partially inconsistent messages. The file does not validate certificate chains, feature names, validity periods, DNS-name semantics, enum correctness, serial uniqueness, or parent recursion depth. Recursive `ParentData` can create large trees and, if constructed with cycles in memory, may stress generic traversal/logging code. Timestamp pointers require nil checks through `HasValidFrom` and `HasValidUntil`. Error/status messages may include verification details that should not be logged blindly in sensitive environments.

Test signals: useful tests are marshal/unmarshal round trips for all four messages, enum string/name/value checks, nil receiver getter behavior, `ParentData` presence and clearing, timestamp conversion, and compatibility tests against the opaque build variant. Higher-level license tests should verify that `VERIFY_ERROR`, `VERIFY_VALID`, and `VERIFY_INVALID` map consistently to message/serial/data population rules, especially the documented behavior that certificate data can be present even when verification failed.
