# sources/distributed-fs/beegfs-protobuf/go/license/license_protoopaque.pb.go

Purpose: generated Go protobuf bindings for `license.proto` under the `protoopaque` build tag. It represents the same BeeGFS license verification schema as `license.pb.go`, but uses the opaque API style: message fields are hidden behind generated getters, setters, presence checks, clear methods, builders, and reflection.

Important APIs/types/functions: the schema surface matches the non-opaque file: `VerifyResult`, `CertType`, `VerifyCertResult`, `VerifyFeatureResult`, `GetCertDataResult`, and `CertData`. The main API difference is structural: message fields are named `xxx_hidden_...` and should be accessed through `GetResult`, `SetResult`, `GetSerial`, `SetSerial`, `GetData`, `SetData`, `HasData`, `ClearData`, `GetParentData`, `SetParentData`, `HasParentData`, and related methods. Builder types (`VerifyCertResult_builder`, `VerifyFeatureResult_builder`, `GetCertDataResult_builder`, `CertData_builder`) provide construction without direct field access.

Control flow: there is no custom license-validation control flow. Generated methods delegate to protobuf runtime machinery. `Reset` clears the message and stores the relevant `MessageInfo`; `ProtoReflect` returns reflection metadata; getters return default values on nil receivers; setters update hidden fields; presence methods check whether nested pointer fields are nil; clear methods nil optional or nested fields. Initialization is the same descriptor build path as the hybrid file: `init()` calls `file_license_proto_init()`, which returns early if already built, registers `CertData` oneof metadata, builds a `protoreflect.FileDescriptor` with two enums and four messages, and clears raw descriptor/type dependency globals.

State and persistence behavior: all state is caller-owned in memory and encoded through protobuf serialization. Hidden fields carry verification results, certificate data, timestamps, DNS names, and recursive parent certificate data. `unknownFields` and `sizeCache` support runtime behavior. The file performs no disk persistence, no certificate loading, and no verification; it only preserves the schema state supplied by other code. `ParentData`, `ValidFrom`, and `ValidUntil` preserve pointer presence; getters alone collapse absent values to nil or defaults.

Dependencies: imports are `protoreflect`, `protoimpl`, `timestamppb`, and `reflect`. It depends on `google.protobuf.Timestamp` for certificate validity boundaries. Build selection depends on the `protoopaque` tag, making this file mutually exclusive with `license.pb.go` in normal builds.

Integration points: Go packages compiled with `-tags protoopaque` use this file for the license protobuf API. It must remain wire-compatible with `license.pb.go` and with other language bindings generated from `license.proto`. The message semantics are the same: certificate verification result/status, feature verification result/status, current certificate data retrieval, and simplified x509/BeeGFS license certificate metadata including type, serials, subject fields, validity, licensed-feature DNS names, CA status, and optional issuer data.

Risks: callers that expect exported fields from the hybrid file will fail under `protoopaque`; access should go through methods and builders for build-tag portability. The schema has no intrinsic validation of enum states, certificate validity windows, DNS-feature encoding, certificate hierarchy, or status-message consistency. Recursive `ParentData` can become expensive if populated deeply. As with the hybrid file, messages can contain sensitive or operationally revealing license details, and stringification/logging should be controlled. Manual edits are unsafe because the file is generated.

Test signals: test with `go test -tags protoopaque` for packages using `license`. Add round-trip tests comparing opaque and non-opaque builds at the wire level, especially for `CertData.parent_data`, timestamp fields, DNS name slices, and result/message conventions. API tests should exercise builders plus getters/setters/clearers rather than direct field access.
