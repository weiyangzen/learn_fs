# Research: sources/distributed-fs/beegfs-protobuf/go/beeremote/beeremote.pb.go

**Purpose:** This file is the non-opaque Go protobuf output for `beeremote.proto`. It defines the BeeRemote service data model: requests and responses for submitting jobs, querying jobs, updating jobs or worker state, retrieving remote storage target configuration, retrieving stub contents, and reporting capabilities. It also embeds the protobuf descriptor for the `BeeRemote` service; actual gRPC client/server bindings live in `beeremote_grpc.pb.go`.

**Important APIs/types/functions:** The top-level enums are `SubmitJobResponse_ResponseStatus`, `JobRequest_GenerationStatus_State`, `Job_State`, and `UpdateJobsRequest_NewState`. Core messages include `SubmitJobRequest`, `SubmitJobResponse`, `JobRequest`, `Job`, `JobResult`, `UpdatePathsRequest`, `UpdatePathsResponse`, `UpdateJobsRequest`, `UpdateJobsResponse`, `GetJobsRequest`, `GetJobsResponse`, `UpdateWorkRequest`, `UpdateWorkResponse`, `GetRSTConfigRequest`, `GetRSTConfigResponse`, `GetStubContentsRequest`, and `GetStubContentsResponse`. Nested messages include `JobRequest_GenerationStatus`, `Job_Status`, `JobResult_WorkResult`, and `GetJobsRequest_QueryIdAndPath`. Generated APIs include nil-safe getters, setters, `Has*`/`Clear*` for optional/message fields, oneof case constants and `WhichType`/`WhichQuery`, builder types for every message, enum reflection methods, and `File_beeremote_proto`.

**Control flow:** Runtime control is generated protobuf object manipulation. `init()` calls `file_beeremote_proto_init`, which registers oneof wrappers for `JobRequest.Type`, proto3 optional fields in `Job`, `UpdateJobsRequest`, and `GetStubContentsResponse`, and `GetJobsRequest.Query`, then builds the descriptor using `protoimpl.TypeBuilder`. Accessor flow is straightforward and nil-safe. `JobRequest.SetSync`, `SetMock`, and `SetBuilder` replace the `Type` oneof, and passing nil clears it; `WhichType` returns generated field-number constants for the active job type. `GetJobsRequest.SetByJobIdAndPath`, `SetByExactPath`, and `SetByPathPrefix` similarly replace the query oneof, and `WhichQuery` reports the selected query. Builder `Build` methods assign fields in order; for oneofs, if multiple builder alternatives are non-nil, later assignments in generated order overwrite earlier ones.

**State and persistence behavior:** Comments describe `Job` as the database-stored record for each path: it stores request data, job id, creation time, current status, external id, and optional start/stop BeeGFS mtimes, while `JobResult` carries `Job` plus deterministically generated `flex.WorkRequest` data and latest worker results outside the stored `Job` to reduce on-disk data. `GetJobsRequest` comments describe key/value store query constraints and secondary metadata references. Wire persistence depends on stable field numbers, enum numeric values, oneof field numbers, map encoding for `UpdateJobsRequest.RemoteTargets`, and timestamp encodings from `google.protobuf.Timestamp`. Optional pointer-backed fields include `JobRequest.Update`, `Job.StartMtime`, `Job.StopMtime`, `UpdateJobsRequest.JobId`, `GetStubContentsResponse.RstId`, and `GetStubContentsResponse.Url`; callers must use `Has*` when absence differs from default values.

**Dependencies and integration points:** The file imports `github.com/thinkparq/protobuf/go/flex` for job-specific payloads (`SyncJob`, `MockJob`, `BuilderJob`), work requests/results, remote storage targets, and capability messages. It imports protobuf reflection/runtime packages and `timestamppb` for lifecycle timestamps. The descriptor declares one `BeeRemote` service with eight methods: `SubmitJob`, `UpdatePaths`, `UpdateJobs`, `GetJobs`, `UpdateWork`, `GetRSTConfig`, `GetStubContents`, and `GetCapabilities`. `beeremote_grpc.pb.go` consumes these message types for transport. Application integration points include BeeRemote managers, worker nodes posting `UpdateWork`, clients querying or updating jobs, RST configuration consumers, and code that reads stub metadata.

**Risks:** Generated code does not enforce required-by-comment constraints such as valid path, remote storage target id, non-`UNSPECIFIED` job states, or safe state transitions; service implementations must validate them. Some semantic states have operational implications: `ERROR` can still own active worker requests, `FAILED` may preserve external ids for possible resume/cleanup, and terminal states forbid further changes. Misusing `GetUpdate()` or `GetJobId()` without `HasUpdate()`/`HasJobId()` loses absence information. `UpdateWork` is documented as worker-node-only, but access control is not generated here. `GetJobsRequest.UpdateWorkResults` can create extra locking and worker communication overhead. Builder oneof overwrite order can silently choose the last non-nil alternative if callers set more than one. Manual edits will be overwritten by regeneration.

**Test signals:** Regeneration tests should run the repository protobuf generation/check target and verify no drift from `beeremote.proto`. Serialization tests should round-trip every message, oneof case, optional field, repeated field, map field, and unknown field. State-machine tests in service code should validate allowed transitions among `UNASSIGNED`, `SCHEDULED`, `RUNNING`, `ERROR`, `FAILED`, `CANCELLED`, `COMPLETED`, and `OFFLOADED`, including forced updates and completed-job retention. Query tests should cover job-id-and-path, exact path, prefix path, inclusion flags, and `UpdateWorkResults` behavior. Integration tests should exercise `SubmitJob` with `sync`, `mock`, and `builder` job types, `UpdateWork` from worker nodes, RST config responses, stub content optional fields, and capability pass-through using the external `flex` messages.
