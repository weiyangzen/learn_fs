# sources/distributed-fs/beegfs-protobuf/go/flex/flex_protoopaque.pb.go

Purpose: generated Go protobuf bindings for `flex.proto` under the `protoopaque` build tag. The file defines the opaque API for Flex worker-node control messages used by BeeGFS/BeeRemote style distributed filesystem workflows: heartbeat, node stats, work submission and update, job configuration, remote storage target configuration, capability discovery, and the `WorkerNode` service descriptor. It is not hand-authored business logic; its purpose is to give Go callers typed construction, mutation, reflection, and wire serialization for the schema.

Important APIs/types/functions: the top-level enums are `UpdateWorkRequest_NewState`, `BulkUpdateWorkRequest_NewState`, `SyncJob_Operation`, `Work_State`, and `UpdateConfigResponse_Result`. The main RPC envelope messages are `HeartbeatRequest`, `HeartbeatResponse`, `SubmitWorkRequest`, `SubmitWorkResponse`, `UpdateWorkRequest`, `UpdateWorkResponse`, `BulkUpdateWorkRequest`, `BulkUpdateWorkResponse`, `UpdateConfigRequest`, `UpdateConfigResponse`, `GetCapabilitiesRequest`, and `GetCapabilitiesResponse`. Work modeling centers on `WorkRequest`, `Work`, `WorkRequest_Segment`, `Work_Status`, `Work_Part`, `JobRequestCfg`, `JobLockedInfo`, `SyncJob`, `MockJob`, and `BuilderJob`. Configuration modeling centers on `BeeRemoteNode`, `RemoteStorageTarget`, `RemoteStorageTarget_Policies`, `RemoteStorageTarget_S3`, `RemoteStorageTarget_Azure`, `RemoteStorageTarget_POSIX`, `RemoteStorageTarget_S3_StorageClass`, and `RemoteStorageTarget_S3_StorageClass_Archival`. Each message has generated `Reset`, `String`, `ProtoMessage`, `ProtoReflect`, getter, setter, `Has...`, `Clear...`, and builder APIs where applicable.

Control flow: this file has no application-level control loop. Runtime flow is generated protobuf behavior: enum `String`, `Descriptor`, `Type`, and `Number` methods delegate to `protoimpl`/`protoreflect`; message `Reset` zeroes the struct and stores `MessageInfo`; `ProtoReflect` lazily attaches message info; getters return zero values on nil receivers; setters mutate hidden fields; `Has...` checks pointer, oneof, or explicit-presence state; `Clear...` removes pointers, oneof alternatives, or explicit-presence bits. The only initialization path is `init() -> file_flex_proto_init()`, which guards on `File_flex_proto != nil`, registers oneof wrapper types for `JobRequestCfg`, `WorkRequest`, `SyncJob`, `RemoteStorageTarget`, and `RemoteStorageTarget_S3_StorageClass`, then builds the `protoreflect.FileDescriptor` with `protoimpl.TypeBuilder`.

State and persistence behavior: all persistent semantics are on the protobuf wire and in caller-owned message instances. The generated structs keep state in opaque `xxx_hidden_...` fields plus `unknownFields`, `sizeCache`, and sometimes `XXX_presence`. Optional scalar fields such as `JobRequestCfg.update`, `tagging`, `priority`, `storage_class`, `allow_restore`, `filter_expr`, `WorkRequest.priority`, and `SyncJob` optionals use `XXX_presence` bits so callers can distinguish "unset" from explicit zero/false/empty string. Repeated fields such as `Work.parts`, `UpdateConfigRequest.rsts`, and `RemoteStorageTarget_S3.storage_class` are represented as hidden pointers to slices in the opaque API. Map fields include metadata and capability trees. There is no disk persistence in this file.

Dependencies: imports are limited to Go protobuf runtime packages (`google.golang.org/protobuf/reflect/protoreflect`, `google.golang.org/protobuf/runtime/protoimpl`), timestamp support (`google.golang.org/protobuf/types/known/timestamppb`), and `reflect`. The schema's time-bearing fields depend on `google.protobuf.Timestamp`: `NodeStats.timestamp`, `JobLockedInfo.mtime`, `JobLockedInfo.remote_mtime`, `GetCapabilitiesResponse.start_timestamp`, and license-independent work/config timestamps.

Integration points: the raw descriptor includes one service, `WorkerNode`, with unary methods `UpdateConfig`, `Heartbeat`, `SubmitWork`, `UpdateWork`, `BulkUpdateWork`, and `GetCapabilities`. `UpdateConfigRequest` sends a `BeeRemoteNode` plus the complete set of configured `RemoteStorageTarget` entries; omitted RSTs are semantically deleted by consumers. `WorkRequest` uses a oneof for request type (`MockJob`, `SyncJob`, or `BuilderJob`), allowing one work envelope to carry mock/testing, sync, or builder work. `RemoteStorageTarget` uses a oneof for storage backend (`S3`, `POSIX`, `Azure`, or `mock`). Comments note that new RST types also need registration in the `rst.SupportedRSTTypes` map outside this generated file so config unmarshalling can map protobuf data into Go structs. Capability discovery integrates through nested `Feature` maps and `BuildInfo`.

Domain behavior encoded in types: `Work_State` documents the lifecycle from `CREATED` to `SCHEDULED`, `RUNNING`, `RESCHEDULED`, transient `ERROR`, terminal `FAILED`, `CANCELLED`, or `COMPLETED`, plus `UNKNOWN` for cases where BeeRemote cannot determine worker state. `UpdateWorkRequest` currently only supports `CANCELLED` as a meaningful state. `BulkUpdateWorkRequest` supports `UNCHANGED` and is described as primarily useful during initial node connection or node drain. `Work_Part` carries part number, byte offsets, ETag, SHA-256 checksum, and completion flag for parallel transfer integrity. S3 configuration encodes endpoint, partition, region, bucket, access key, secret key, and optional storage classes, including archival retrieval tier, retention days, polling times, and auto-restore behavior. `BeeRemoteNode` carries network address, management address, TLS certificate and TLS bypass flags, proxy flag, auth secret, and auth-disable flag.

Risks: this file is generated, so direct edits would be overwritten and should instead be made in `flex.proto` and regenerated. The opaque build tag hides fields; code that accesses exported struct fields from non-opaque generated variants will not compile with this file selected. Sensitive configuration values (`BeeRemoteNode.auth_secret`, S3 `access_key` and `secret_key`, management TLS settings, and TLS/auth disable flags) can be serialized, logged through protobuf stringification, or retained in memory if callers are careless. Presence-sensitive options require `Has...` checks; using only getters loses the distinction between unset and explicitly false/zero/empty values. Oneof builders assign alternatives sequentially, so if multiple alternatives are non-nil the last assignment wins. The schema itself does not enforce RST/job compatibility, valid time duration strings, valid endpoint formats, legal state transitions, segment bounds, part ordering, or credential safety.

Test signals: generated-code correctness is best validated by regeneration from `flex.proto`, `go test` for packages importing the `flex` package under `-tags protoopaque`, wire-compatibility tests that marshal/unmarshal representative messages, and service integration tests that exercise `WorkerNode` RPCs. Important behavioral test cases include optional presence round trips, oneof selection and clearing, RST config replacement semantics, capability map nesting, terminal work states, and sensitive byte/string fields surviving serialization without unintended nil/empty conversions. Because setters for bytes normalize nil to empty slices in some cases, tests should check nil-vs-empty expectations where callers depend on them.
