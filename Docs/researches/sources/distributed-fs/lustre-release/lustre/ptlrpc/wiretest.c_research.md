## Scope

This chunk covers the beginning of Lustre's generated `wiretest.c`, from the file header through the first part of `lustre_assert_wire_constants()`. ## Purpose

`lustre_assert_wire_constants()` verifies that the compiled kernel/user headers still match the numeric and binary layout expected by Lustre's on-the-wire protocol. It protects interoperability between clients, servers, recovery logs, persistent metadata, and user-space tools by asserting exact opcode values, feature flags, struct sizes, field offsets, array offsets, and selected magic constants.

The checks use two assertion styles:

- `LASSERTF(condition, format, value)` for runtime assertions that report the found value when the wire contract differs.
- `BUILD_BUG_ON(condition)` for compile-time invariants, often used for enum-like constants, fixed maxima, variable-array placement, and cases where a field cannot be directly checked.

The function has no loops, branches for runtime state, or side effects beyond assertion failure. Control flow is a linear list of generated checks, with compile-time conditional sections guarded by `CONFIG_LUSTRE_FS_SERVER` and `CONFIG_LUSTRE_FS_POSIX_ACL`-related includes.

The function integrates with the PTLRPC subsystem rather than defining new protocol data. Because it references many exported UAPI and internal structs, it also acts as a cross-subsystem ABI smoke test for OST, MDT/MDS, LDLM, LOV, LMV, quota, security context, LFSCK, and management service message families.

## Control Flow

The function starts with protocol scalar constants, then proceeds into increasingly complex fixed-layout structures. The generated order is meaningful for diagnosis but not for runtime behavior:

1. Assert opcode namespaces and scalar protocol constants.
2. Assert lock mode/type constants and server-only update/quota constants.
3. Assert struct sizes and field offsets using `sizeof()` and `offsetof()`.
4. Assert flexible-array payload starts by checking the offset of the first variable member against the fixed header size, for example `ladvise_hdr.lah_advise`, `lov_mds_md_*` object arrays, `lov_comp_md_v1.lcm_entries`, `lmv_*` stripe/object arrays, and `ldlm_request.lock_handle`.
5. Assert compatibility between `ptlrpc_body_v3` and `ptlrpc_body_v2` for shared fields. This is especially important for mixed-version RPC handling.
6. Enter conditional blocks for server-only types and fields when `CONFIG_LUSTRE_FS_SERVER` is enabled.

There is no dynamic input. A successful return means all compiled constants and layouts in this range matched the generated expectations for this build configuration.

## State And Persistence Behavior

This code has no persistent state of its own. Its state relevance is indirect and important: many checked structs are serialized on the network or stored in persistent metadata/log records. Examples include:

- `struct obdo`, `struct ost_body`, and `struct niobuf_remote` for object and bulk I/O protocol.
- `struct lov_mds_md_*`, `struct lov_comp_md_*`, `struct lmv_mds_md_v1`, and descriptor structs for file and directory layout metadata.
- `struct mdt_rec_*` for metadata operation records used across MDT request handling and recovery/replay paths.

Any accidental field insertion, alignment change, type-width change, or flag renumbering in these structures can corrupt inter-node communication or make old persistent state unreadable. This file catches those changes by turning layout drift into an assertion failure.

## Notable Wire Contracts In This Chunk

- `struct ptlrpc_body_v3` is asserted as 184 bytes and shares offsets/sizes for all common fields with `struct ptlrpc_body_v2`. This preserves compatibility across PTLRPC body versions.
- `struct obd_connect_data` is fixed at 192 bytes with extensive reserved padding. The padding is part of the ABI and leaves room for future negotiation data without changing the structure size.
- `struct obdo` and `struct ost_body` are both asserted at 208 bytes, tying OST RPC bodies directly to object descriptor layout.
- LOV and LMV metadata structures use fixed headers followed by flexible object/stripe entries; the checks verify the array starts exactly where consumers expect it.
- Composite layout metadata (`lov_comp_md_entry_v1` and `lov_comp_md_v1`) includes flags for stale, preferred read/write, offline, initialized, parity, compression, partial, and negative/link semantics. Bitfields for compression level and chunk log bits are explicitly noted as not directly checkable.
- MDT records in this range are all 136 bytes, with common security/credential/FID fields occupying stable offsets. This uniformity supports request decoding and replay paths that interpret reintegration records by opcode.
- LDLM request and reply layouts combine resource descriptors, lock modes, policy data, handles, and lock value blocks in fixed positions used by enqueue/convert/cancel and callback RPCs.

## Risks

- Because this file is generated, hand edits are high risk. Manual changes can make the test pass while hiding a mismatch with the actual generator inputs, or make future regeneration noisy.
- The exact numeric constants are interoperability contracts. Reusing or renumbering an opcode/flag without a migration plan can break mixed-client/server clusters.
- Struct padding is intentional. Removing fields that appear unused, changing field types for local convenience, or allowing compiler-dependent layout changes can break the wire format.
- Conditional server-only checks mean client-only and server-enabled builds validate different subsets. A change may pass in one configuration and fail in another.
- Bitfields are weak spots because the generated code cannot directly assert every bitfield member offset/size. The comments around `lov_comp_md_entry_v1` compression bitfields are an example.
- This chunk ends mid-function at the start of `struct ldlm_gl_barrier_desc` validation, so full LDLM/glimpse/barrier coverage depends on later chunks.

## Risks And Edge Cases

The main risk is silent ABI drift. Many structures in this range contain explicit padding or trailing variable-length data. Removing padding, changing a scalar type, replacing a fixed array with a pointer, or moving a flexible array would compile in ordinary code but break persisted data, RPC unmarshalling, ioctl payloads, or user-space tooling. The generated offset and size checks are meant to catch exactly that class of bug.

Server-only coverage means client-only builds will not exercise several high-risk persisted formats: nodemap, scrub, recovery, update, quota, and disk metadata records. Conversely, Linux-client and ACL feature gates mean test coverage can vary by build configuration. A compatibility change should be validated in all relevant configs rather than assuming one successful build covers the whole function.

Numeric constant drift is as risky as struct drift. Llog record types, config commands, HSM actions, LFSCK events, nodemap RBAC bits, update magic values, and disk flags are protocol values. Reusing, renumbering, or narrowing them can cause old records to be misinterpreted as new operations or make mixed-version clusters fail during recovery, configuration, or administrative operations.

The generated file can also fall out of sync with headers if developers change headers without regenerating `wiretest.c`, or regenerate using a different tool/header set. That creates noisy failures, but the noise is useful: the correct fix is to reconcile the intended ABI change with generator output, not to weaken the assertions.
