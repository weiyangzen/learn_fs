## Purpose

This section supplies known-answer vectors to the kernel crypto test manager. It is not runtime Ceph distributed-filesystem logic; it is a copy of Linux crypto self-test data used to validate algorithm implementations registered with the kernel Crypto API. The data exercises encryption, decryption, authentication, IV/counter updates, deterministic random-bit generation, and MAC generation across many algorithms and modes.

The vectors are used by test-manager code elsewhere in the crypto subsystem. For each registered algorithm name, the test manager selects the matching template array, feeds keys, IVs, plaintext, associated data, entropy, or personalization strings into the implementation under test, then compares produced output against these expected bytes.

## Important APIs, Types, And Data

The principal structures are defined near the start of `testmgr.h` and populated in this chunk:

- `struct cipher_testvec` holds symmetric-cipher cases: `key`, optional `iv`, optional expected `iv_out`, `ptext`, `ctext`, `klen`, and `len`, plus error/weak-key metadata not heavily used in this chunk.
- `struct aead_testvec` holds AEAD cases: `key`, `iv`, `ptext`, `assoc`, `ctext`, `klen`, `plen`, `alen`, `clen`, and flags such as `novrfy`. For AEADs, `ctext` stores ciphertext concatenated with the authentication tag.
- `struct drbg_testvec` holds deterministic RNG cases: entropy input, optional prediction-resistance entropy (`entpra`, `entprb`), optional additional inputs (`addtla`, `addtlb`), optional personalization string, and expected generated bytes.
- `struct hash_testvec` is used here for Camellia-CMAC test vectors through `key`, `plaintext`, `digest`, `ksize`, and `psize`.

The AES-GCM and AES-CCM tables cover generic AEAD behavior as well as IPsec-style wrappers. `aes_gcm_rfc4106_tv_template[]` uses keys that include salt bytes and AAD layouts matching RFC4106/ESP framing. `aes_gcm_rfc4543_tv_template[]` covers GMAC-style authentication behavior and includes a negative verification vector. `aes_ccm_rfc4309_tv_template[]` mirrors RFC4106-derived inputs with one-byte-shorter salt handling, and comments note that the original RFC4309 examples use nonce/AAD lengths that this implementation does not support.

`rfc7539_tv_template[]` and `rfc7539esp_tv_template[]` cover ChaCha20-Poly1305 AEAD in generic and ESP-oriented forms. The generic vector comes from RFC7539 section 2.8.2/A.5 style material and has a long message, AAD, nonce, and tag. The ESP variant follows packet/AAD layouts expected by IPsec transforms.

`aegis128_tv_template[]` contains AEGIS-128 vectors generated from the SUPERCOP reference implementation. It deliberately varies plaintext and associated-data lengths, including zero-length plaintext, zero-length AAD, small one-byte cases, 15/16/17-byte boundaries, 31/32/33/65-byte boundaries, and cases where the authentication tag dominates `clen`.

The DRBG vectors cover SP800-90A hash, HMAC, and CTR_DRBG variants. Prediction-resistant templates include two entropy reseed inputs per test request, while non-prediction-resistant templates omit `entpra` and `entprb`. The CTR variants use shorter entropy/additional/personalization lengths and expected outputs of 64 bytes; hash/HMAC SHA-based cases generally use 48-byte entropy and 128-byte expected outputs.

The legacy and block-cipher vectors cover both single-block canonical cases and mode-specific stress cases. CAST5, Camellia, and several mode templates include long generated plaintext/ciphertext sequences and expected `iv_out` values. LRW and XTS tables use doubled keys and sector/tweak IVs, including long 512-byte inputs to validate partial-block and sector-mode behavior.

## Control Flow

There is no executable control flow in this chunk. Its "flow" is declarative: each static `const` array is compiled into the kernel image or module and later iterated by crypto self-test routines. The test manager's external control flow is expected to:

1. Instantiate or find a crypto transform for the algorithm under test.
2. Apply vector key material and authentication size or IV setup when applicable.
3. Run encrypt/decrypt, digest, or DRBG generate operations using the vector fields.
4. Compare produced output and side effects such as `iv_out` against the stored expected values.
5. Treat `novrfy` AEAD vectors as expected authentication failures on decrypt rather than successful round trips.

For AEAD vectors, the expected `clen` includes tag bytes, so encryption must produce `plen + tag_len` bytes and decryption must strip/verify the tag back to `plen`. For cipher modes with `iv_out`, the harness validates that the implementation's updated IV/counter state matches the stored value after processing.

For DRBG vectors, the control sequence is instantiate with entropy and optional personalization, generate once with optional first additional input, generate again with optional second additional input, and compare the final output stream with `expected`. Prediction-resistant templates additionally require fresh entropy for each generate operation.

## Risks And Edge Cases

The highest risk is silent corruption of literal byte strings or length fields. These vectors are byte-for-byte contracts; changing one escaped byte, `klen`, `plen`, `alen`, `clen`, `len`, or `expectedlen` can make a correct implementation fail or let an incorrect implementation pass.

AEAD vectors are especially sensitive because `ctext` includes both ciphertext and tag. A length mismatch can shift tag boundaries, and `novrfy` vectors must remain negative tests rather than accidentally becoming accepted decryptions. RFC4106/RFC4309 salt and nonce conventions are also easy to misread because the key material includes salt bytes and the IV/AAD layout is transform-specific.

Mode vectors with `iv_out` are sensitive to endian and counter-update semantics. CTR, CBC, LRW, and XTS vectors test not only the output bytes but also how the implementation updates mutable IV or tweak state across full and partial blocks. The long 496/512-byte vectors are useful because they expose bugs that single-block vectors would miss.

The DRBG tables are state-machine tests. Mixing up prediction-resistant and non-prediction-resistant sequences, omitting second additional input, using the wrong personalization string length, or comparing after the wrong generate call will produce misleading results.

The chunk boundaries are a documentation hazard. The first lines belong to a prior AES-CTR/RFC3686 table started at line 19442, and the last lines are only the beginning of ARIA CBC. Any merge-stage report should reconcile this chunk with adjacent chunks before making file-level claims about those complete arrays.

High-signal configurations include AEAD, DRBG, Camellia, ARIA, SEED, CAST5, ARC4, and legacy cipher options, plus FIPS-related configurations where algorithms or vectors may be gated elsewhere.
