## Control Flow and Behavioral Contracts

The `SequenceFile.Reader` flow is cursor-based and synchronization-aware. A caller advances with `next`, optionally reads the value corresponding to the last key through `getCurrentValue`, or bypasses object creation through raw key/value reads. `seek(long)` is constrained to positions returned by `SequenceFile.Writer.getLength()`, while arbitrary offsets require `sync(long)` to move to the next sync marker. `syncSeen()` communicates whether the previous read crossed a sync marker, which is important for split readers and recovery from arbitrary offsets.

`SequenceFile.Sorter` follows an external sort/merge flow. Inputs are sorted into temporary segments under a memory budget, then merged with configurable fan-in. `sortAndIterate` returns a raw iterator for callers that want to consume the sorted records directly, while `sort` and `merge` overloads write output files. `SegmentDescriptor` mediates segment reads, sync checks, and cleanup; the preserve-input flag controls whether consumed segment files are deleted. `RawKeyValueIterator` separates key/value retrieval from cursor movement, so callers must call `next()` before reading the current buffers and must close the iterator to release streams.

`SequenceFile.Writer` and `ValueBytes` form a raw-copy path for sort/merge jobs. Writers append object key/value pairs through serializers, or append raw keys with `ValueBytes` to avoid deserialization/re-serialization. `getLength()` returns a synchronized position for future `Reader.seek()`, but the Javadoc warns that with block compression the next readable key after seeking may be earlier than the last key written when the position was sampled.

`SetFile` flow is MapFile-as-set: writers append sorted keys only, readers seek or iterate keys, and `get` returns the input key on match or null on absence. The strict increasing-key contract is central because MapFile indexing and binary search require sorted keys.

Writable serialization flow is in-place and type-driven. Implementations write fields to `DataOutput` and read fields back from `DataInput`, reusing existing object storage when possible. `WritableComparator` accelerates compare-heavy paths by comparing serialized byte ranges directly; if no raw comparator is registered, the default path deserializes two keys and invokes natural ordering. `WritableFactories` and `WritableName` support dynamic instantiation and backward-compatible class naming for persisted streams.

`Text` flow stores UTF-8 bytes directly and exposes operations in byte offsets. Search, traversal, validation, and comparison can avoid constructing Java `String` objects. Serialization uses zero-compressed length encoding, then raw bytes. Decode/encode overloads let callers choose whether malformed input is replaced or surfaced through `CharacterCodingException`. `UTF8` keeps the older wire/API behavior available but is deprecated in favor of `Text`.

`WritableUtils` variable-length integer flow uses a first byte to encode both sign and byte count. Small values fit in one byte; larger values write the high non-zero bytes first. Readers decode the first byte with `decodeVIntSize` and `isNegativeVInt`, then assemble the numeric value. These helpers are foundational to `Text`, `VIntWritable`, `VLongWritable`, and many Hadoop wire formats.

Compression flow is pull/push state-machine based. Streams call `setInput` when `needsInput` is true, then repeatedly call `compress` or `decompress` into caller buffers. A zero byte return does not necessarily mean EOF; callers must inspect `needsInput`, `needsDictionary`, or `finished`. `finish()` signals no more input for compression; `end()` releases native or Java resources. `reset()` and stream-level `resetState()` make codec objects reusable and enable positioned reads after an underlying stream seek.

Codec lookup flow starts with `CompressionCodecFactory`, which reads configured codec classes, registers default codecs, and chooses a codec by suffix from a `Path`. `CodecPool` sits between codecs and callers to reuse expensive compressor/decompressor objects. Correct lifecycle is get from pool, use through a codec stream or direct state machine, reset as needed, then return to the pool; leaking pooled instances can exhaust native resources.

BZip2 flow is special in this API version. `BZip2Codec` supports stream creation, but the compressor/decompressor object methods are not supported. The low-level CBZip2 streams expect the caller or codec wrapper to handle the two leading magic bytes. The docs emphasize memory cost, buffering needs, and non-thread-safety, so callers should close promptly and wrap single-byte-reading sources in buffering.

Zlib flow chooses between native and built-in implementations through `ZlibFactory`. The compressor/decompressor expose synchronized methods, byte counters, header modes, levels, strategies, and direct-buffer sizing. Header selection controls interoperability with raw zlib, default zlib, and gzip-framed data; decompression can also autodetect gzip/zlib headers.

TFile read flow is scanner-centric. A `TFile.Reader` exposes metadata and creates scanners, but users read key/value data only through `Scanner`. A scanner starts at the first entry in its bounded range or at end for an empty range. Cursor movement invalidates previously returned `Entry` objects. Sorted files support key-range scanners and seek/lower/upper-bound behavior; byte-range scanners round coverage to compression block boundaries and may contain zero entries. Entry value access is intentionally one-shot for several APIs because values are not cached and may be chunk streamed.

TFile write flow, visible at the end of the chunk, begins with construction over a positioned `FSDataOutputStream`, minimum compressed block size, compression name, comparator name, and configuration. The comparator contract determines sorted vs unsorted files: null or empty means unsorted; `"memcmp"` means language-independent byte comparison; `"jclass:<class>"` means a Java `RawComparator` constructed with a default constructor. `close()` releases TFile resources and is idempotent but leaves the supplied filesystem stream open.

## Risks and Compatibility Notes

This chunk begins mid-class in `SequenceFile.Reader` and ends mid-class in `TFile.Writer`. The merge lane should combine it with adjacent chunks to recover complete per-class context for those two boundary classes.

SequenceFile raw APIs are performance-sensitive and format-sensitive. Incorrect handling of sync markers, block-compression positions, raw value compression state, or serializer choice can break file splitting, sorted merges, or compatibility with existing SequenceFiles. The deprecated raw `next(DataOutputBuffer)` overload should remain available for older clients even though `nextRaw` is preferred.

Sorter and SegmentDescriptor APIs can delete input or temporary files. Misinterpreting `deleteInput`, `preserveInput`, or cleanup behavior can cause data loss. Merge fan-in and memory settings affect file descriptor pressure, temporary-file volume, and sort performance.

Writable serialization is not self-describing beyond what individual implementations write. Field order, variable-length encoding rules, writable names, and factories are binary compatibility contracts. Raw comparators must exactly match serialized key encodings; an optimized comparator that disagrees with object `compareTo` can corrupt sorted files or MapReduce ordering.

`Text.getBytes()` and similar raw buffer APIs expose backing storage. Callers must respect logical length and avoid retaining mutable buffers across mutations. UTF-8 validation, malformed replacement behavior, and byte-vs-character offsets are common edge cases. The legacy `UTF8` type remains deprecated but cannot simply be removed because older persisted data and public APIs may still reference it.

Compression lifecycle errors are a major risk. Callers must distinguish `finish`, `finished`, `close`, `reset`, `resetState`, and `end`; must return pooled codecs when appropriate; and must not assume a zero-byte compress/decompress result means EOF. Native zlib selection can change behavior and resource pressure by deployment environment.

BZip2 APIs have several traps: stream constructors omit the `"BZ"` magic handling, object-based compressor/decompressor methods are unsupported, CBZip2 streams are not thread-safe, and public constants include mutable arrays. Code using `CompressionCodec` generically must handle `UnsupportedOperationException` for BZip2 compressor/decompressor object methods.

TFile APIs are explicit about one-shot value access, entry invalidation after cursor movement, byte-range scan rounding to compression blocks, and sorted-only key-range operations. Callers that read a value twice, keep an `Entry` after `advance`, or assume byte ranges map exactly to key ranges can fail. Comparator strings are persisted and interoperability-sensitive; `"jclass:"` comparators require default constructors and are Java-specific.
