## Purpose

The Rook CRDs in this range define the API surface for object storage, RGW user credentials, multisite realm topology, object-zone pool layout, and RBD mirroring daemons. The Kubernetes API server validates custom resources against these schemas before the Rook operator reconciles them into Ceph pools, RGW daemons, users, secrets, multisite metadata, and mirror pods.

The `CephObjectStore` continuation covers RGW gateway runtime configuration, Kubernetes health probes, advertised S3 endpoints, metadata pool settings, preserve-on-delete behavior, object-store security and KMS settings, shared pool placement, multisite zone membership, status, and the scale subresource. The following object-store user and zone CRDs model RGW user/account references, user capabilities, externally reachable zone endpoints, zone data/metadata pool layout, and zone-group membership.

`CephRBDMirror` defines the desired RBD mirror daemon workload: number of mirror instances, pod labels/annotations, peer secrets, placement, priority class, resources, and status. The final `ObjectBucketClaim` and `ObjectBucket` CRDs expose the Object Bucket API used by bucket provisioners and consumers to request, bind, describe, and clean up object buckets.

## Important APIs And Schema Surfaces

`CephObjectStore.spec.gateway` fields in this chunk include Kubernetes pod scheduling fragments, RGW HTTP/HTTPS ports, priority class, pod resource requirements, service annotations/labels, TLS secret reference, and RGW config injection. `readAffinity.type` is constrained to `localize`, `balance`, or `default` and is documented as Ceph Tentacle/v20-only. `rgwCommandFlags` applies Ceph RGW config at startup and can restart pods, while `rgwConfig` and `rgwConfigFromSecret` apply runtime config without restart. `rgwConfigFromSecret` embeds `SecretKeySelector` values keyed by RGW config name.

`CephObjectStore.spec.healthCheck` exposes `readinessProbe` and `startupProbe` wrappers. Each probe can be disabled and can embed Kubernetes `exec`, `grpc`, `httpGet`, or `tcpSocket` probe settings, including thresholds, delays, periods, timeouts, termination grace period, headers, and `int-or-string` probe ports. These probe subtrees use Kubernetes list and map hints such as `x-kubernetes-list-type: atomic`.

`CephObjectStore.spec.hosting` controls S3 endpoint discovery. `advertiseEndpoint` requires `dnsName`, `port`, and `useTls`, and is returned to dependent resources such as `CephObjectStoreUser`, Object Bucket Claims, and COSI buckets/accesses. `dnsNames` lists accepted S3 hostnames and interacts with wildcard DNS and virtual-host bucket addressing.

`CephObjectStore.spec.metadataPool` and `CephObjectZone.spec.dataPool`/`metadataPool` reuse Rook pool schemas. They support replicated and erasure-coded layouts, compression settings, CRUSH root/device class, CRUSH update permission, mirroring mode and snapshot schedules, quotas, pool parameters, status checks, and RBD stats flags. The object-store and object-zone shared-pool schemas define `dataPoolName`, `metadataPoolName`, `poolPlacements`, optional non-EC data pools, storage class placements, default placement, and `preserveRadosNamespaceDataOnDelete`. Shared pool names have immutability CEL validations, and placement names use a limited pattern.

`CephObjectStore.spec.security` covers RGW-facing security configuration. It includes key rotation enablement and cron schedule, KMS connection details with token secret names, S3 server-side encryption support, RGW Beast SSL options, and TLS group strings. `spec.zone.name` links an object store to a multisite `CephObjectZone`; the CRD has a CEL validation forbidding `defaultRealm: true` when `zone.name` is set.

`CephObjectStore.status` reports `cephx.daemon` key generation/version, standard Rook conditions, secure and insecure endpoint arrays, info map, message, observed generation, phase, replica count, and workload selector. The CRD declares both a `/status` subresource and a scale subresource mapping `.spec.gateway.instances`, `.status.replicas`, and `.status.selector`.

`CephObjectStoreUser` exposes `cephobjectstoreusers.ceph.rook.io` with short names `rcou`, `objectuser`, and `cephosu`. Its spec supports `accountRef` to a same-namespace `CephObjectStoreAccount` with immutability validation, RGW admin capabilities, `clusterNamespace`, display name, provided credential keys from Secrets, operation masks, quotas, and target store. Capability values are constrained to `*`, `read`, `write`, or `read, write`; `opMask` is a set of `read`, `write`, and `delete` with a maximum of three entries. Status records info, generated or referenced Secret object references, observed generation, and phase.

`CephObjectZoneGroup` exposes `cephobjectzonegroups.ceph.rook.io` with short name `cephozg`. Its spec is intentionally small and requires `realm`, linking the zone group to a `CephObjectRealm`. Status uses the common Rook shape: conditions, observed generation, and phase.

`CephObjectZone` exposes `cephobjectzones.ceph.rook.io` with short name `cephoz`. Its spec includes externally reachable `customEndpoints`, data and metadata pool settings, default `preservePoolsOnDelete: true`, shared pools, and required `zoneGroup`. Status again records conditions, observed generation, and phase. `customEndpoints` are important for multisite replication because omitted object-store endpoints will not receive sync traffic when multisite sync is disabled for that object store endpoint.

`CephRBDMirror` exposes `cephrbdmirrors.ceph.rook.io` with short name `cephrbdm`. Its spec requires `count` with minimum `1`, supports labels/annotations, mirror peer secret names, Kubernetes placement controls, priority class, and resources. Status reports `cephx.daemon` key state, conditions, observed generation, and phase.

`ObjectBucketClaim` exposes namespaced `objectbucketclaims.objectbucket.io/v1alpha1` with short names `obc` and `obcs`. Its spec includes `storageClassName`, explicit `bucketName`, generated bucket name prefix, arbitrary `additionalConfig`, and `objectBucketName` for binding. Status is intentionally open-ended and preserved.

`ObjectBucket` exposes cluster-scoped `objectbuckets.objectbucket.io/v1alpha1` with short names `ob` and `obs`. Its spec includes `storageClassName`, endpoint details (`bucketHost`, `bucketPort`, `bucketName`, `region`, `subRegion`, and `additionalConfig`), authentication, `additionalState`, `reclaimPolicy`, and `claimRef`. Status is preserved as an open object.

## Control Flow

There is no imperative control flow in this YAML. Runtime behavior is driven by Kubernetes and Rook:

1. The CRDs are applied to the cluster, registering namespaced `ceph.rook.io/v1` object-store and mirror APIs, namespaced `objectbucket.io/v1alpha1` claims, and cluster-scoped `objectbucket.io/v1alpha1` buckets.
2. The API server validates custom resource creates and updates using these OpenAPI schemas, required fields, enums, numeric bounds, CEL validations, list/map merge hints, status subresources, printer columns, and scale subresource mappings.
3. Rook controllers watch `CephObjectStore`, `CephObjectStoreUser`, `CephObjectZoneGroup`, `CephObjectZone`, and `CephRBDMirror` resources and reconcile them into Ceph RGW services, pools, multisite topology, RGW users and secrets, and RBD mirror daemon deployments.
4. Object bucket provisioners watch `ObjectBucketClaim` requests, provision or bind buckets, create cluster-scoped `ObjectBucket` objects, populate endpoints/authentication/additional state, and update claim or bucket status.
5. Controllers update status through `/status`, preserving spec/status separation. `CephObjectStore` additionally supports Kubernetes scaling flows through its scale subresource.

## State And Persistence Behavior

The CRDs persist API definitions in Kubernetes etcd; the custom resources persist desired and observed storage state. `CephObjectStore` and `CephObjectZone` specs persist data-plane choices such as pool topology, shared pool names, placement mappings, KMS integration, endpoint advertisement, TLS settings, RGW runtime config, and deletion-preservation policy. Those fields can outlive pods and directly affect Ceph resources that are much more durable than a Kubernetes object.

Deletion semantics are explicitly modeled. `CephObjectZone.spec.preservePoolsOnDelete` defaults to `true`, and shared-pool `preserveRadosNamespaceDataOnDelete` controls whether RADOS namespace data survives zone or object-store deletion. Shared data and metadata pool names are immutable to avoid accidental data detachment or loss.

Status fields persist controller observations. Rook CRDs in this range consistently use `conditions`, `observedGeneration`, and `phase` so clients can tell whether a status reflects the latest spec generation. `CephObjectStore` and `CephRBDMirror` additionally persist CephX key version/generation state for daemon key rotation and brownfield tracking. Object bucket status and flexible config/state maps use `x-kubernetes-preserve-unknown-fields` to allow provisioner-specific data.

Kubernetes schema extensions matter for persistence and patch behavior. `x-kubernetes-preserve-unknown-fields` appears on flexible config, status, resource, and placement subtrees. `x-kubernetes-list-type: atomic` and `x-kubernetes-map-type: atomic` mean many embedded Kubernetes structures are replaced as whole values during apply/merge rather than merged item-by-item.

## Dependencies And Integration Points

The immediate dependency is Kubernetes `apiextensions.k8s.io/v1`. These CRDs depend on structural OpenAPI schema support, `/status` subresources, additional printer columns, scale subresources, CEL validation rules, and Kubernetes API conventions for object metadata and resource quantities.

The Rook Ceph operator is the main consumer of the `ceph.rook.io` APIs. Its Go API types and reconcilers must remain synchronized with this generated schema. The operator integrates the specs with Ceph RGW, RADOS pools and namespaces, Ceph multisite realms/zone groups/zones, CephX users and keys, KMS providers, Kubernetes Services, Secrets, Deployments, pod scheduling, probes, and resources.

The Object Bucket API CRDs integrate with bucket provisioners and storage classes. `ObjectBucketClaim` is namespaced for application-facing requests, while `ObjectBucket` is cluster-scoped so the provisioner can represent actual bucket instances and share endpoint/authentication/state details independent of a namespace-scoped claim.

Ceph itself is the data-plane dependency behind most fields. Pool replication and erasure coding settings influence durability and recovery behavior; RGW config, TLS, KMS, advertised endpoints, and user capabilities influence S3 access behavior; multisite endpoints and zone relationships control replication and sync.

## Risks And Edge Cases

The chunk begins mid-`CephObjectStore` schema, so the first lines are not a standalone YAML document. Research or tooling that slices this range must preserve context from the earlier object-store CRD when validating the full manifest.

Several fields are high-impact operational controls. RGW startup flags can restart gateways and can apply breaking Ceph config. Runtime RGW config and config-from-secret can store invalid keys that pass API validation but fail during reconciliation. KMS token references, TLS options, and old protocol flags can weaken or break client access if misconfigured.

Pool and placement fields can affect data durability and data retention. Replication size, erasure coding chunks, CRUSH root/device class, shared pool names, namespace preservation, and `preservePoolsOnDelete` decide where data lands and whether it is retained after custom resource deletion. The schema warns that changing pool names in placements can lead to data loss, and only some shared-pool fields have explicit immutability validation.

Endpoint fields are deceptively important. Incorrect `advertiseEndpoint`, `dnsNames`, or `customEndpoints` can cause users, Object Bucket consumers, COSI resources, or multisite peers to receive unusable S3 endpoints. Hostname lists can also cause RGW gateways to reject requests for omitted hostnames.

`CephObjectStoreUser` can grant broad RGW admin capabilities. Although enum values are constrained, the API allows `*` for many capability categories and supports externally supplied access/secret keys via Secrets. Secret selector names are structurally permissive because Kubernetes allows an empty default for backwards compatibility, so controller-side validation remains important.

The Object Bucket API schemas are intentionally loose. `additionalConfig`, `authentication`, `additionalState`, `claimRef`, and status preserve unknown fields, which supports multiple provisioners but pushes many compatibility and validation failures to provisioner logic rather than API-server validation.

`CephObjectStore` has a scale subresource tied to `.spec.gateway.instances`. Any schema drift around gateway instances, `.status.replicas`, or `.status.selector` can break `kubectl scale`, HPA-style integrations, or workload visibility.
