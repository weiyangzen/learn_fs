## Purpose

The purpose of this generated table is regression coverage for the perf x86 instruction decoder and the Intel PT instruction categorizer. The table lets the test harness feed exact byte sequences to `insn_decode()` in 64-bit mode and verify that decoded lengths match objdump/binutils output. For rows that include expected operation and branch strings, the harness also checks `intel_pt_get_insn()` classification and relative target extraction.

This chunk focuses mostly on non-branch decode coverage. Nearly all rows have `expected_rel` set to `0` and empty expected operation/branch strings, meaning the Intel PT classifier should report the default non-control-flow values. That is still useful because `intel_pt_get_insn()` must successfully consume every byte sequence even when it does not classify it as call/return/jump/syscall/etc.

The rows are designed to exercise decoder complexity rather than instruction semantics. They include many prefix combinations, operand-size changes, REX high-register references, VEX and EVEX prefixes, 32-bit address-size overrides inside 64-bit mode, SIB addressing, displacement sizes, immediate bytes, opmask registers, high vector registers, and unusual or recently added instruction encodings.

## Control Flow

There is no runtime control flow inside this file. The effective control flow is created by the including test harness:

1. `insn-x86.c` includes this fragment inside `test_data_64[]`.
2. `test__insn_x86()` calls `test_data_set(test_data_64, 1)`.
3. `test_data_set()` iterates until it reaches the sentinel row appended after the include.
4. `test_data_item()` calls `insn_decode(&insn, dat->data, MAX_INSN_SIZE, INSN_MODE_64)`.
5. The decoded `insn.length` must equal `dat->expected_length`.
6. The harness maps `expected_op_str` and `expected_branch_str` through `get_op()` and `get_branch()`.
7. `intel_pt_get_insn(dat->data, MAX_INSN_SIZE, true, &intel_pt_insn)` must succeed.
8. The resulting Intel PT `op`, `branch`, and `rel` values must match the expected row values.

The generation flow is separate. `gen-insn-x86-dat.sh` builds `insn-x86-dat-src.c` as a 64-bit object, runs `objdump -dSw`, and pipes the disassembly through `gen-insn-x86-dat.awk`. The AWK script starts collecting after the `Start here` marker and stops at `Stop here`; for every disassembly line in that range it emits a row with byte values, byte count, optional expectation fields, and the objdump text. `Expecting:` comments in the source set expected Intel PT classification fields for the next emitted row.

## Risks and Edge Cases

The main risk is generated-data drift. Editing this file directly can create rows that no longer correspond to `insn-x86-dat-src.c` or objdump output. The header and harness comments both indicate that new instructions should be added to the source file and regenerated, not hand-written here.

Assembler/binutils version skew is a real edge case. If one environment emits different encodings or disassembly spellings for new instructions, regenerated output may churn the table or change expected lengths. Conversely, older binutils may fail to generate rows for newer mnemonics, weakening coverage or breaking regeneration.

The row format is brittle because the included file has no surrounding declaration of its own. Every row must be a valid `struct test_data` initializer. Missing commas, mismatched string fields, or truncated rows will break compilation of `insn-x86.c`. The chunk boundary at line 4040 illustrates this: the full source file is valid, but the requested line slice alone ends after an initializer byte/length line and before its `asm_rep` line.

Decoder risks covered by this chunk include:

- Incorrect instruction length for long EVEX encodings, especially rows with ModRM, SIB, 32-bit displacement, and immediate bytes.
- Misinterpreting `0x67` address-size override in 64-bit mode, where objdump reports `%eax/%ecx` addressing instead of `%rax/%rcx`.
- REX and EVEX high-register handling for `%r8`-`%r13`, `%r22`, `%xmm15`, `%zmm25`-`%zmm30`, and opmask `%k1`/`%k7`.
- Confusing VEX and EVEX encodings of the same mnemonic or treating EVEX opmask/zeroing/vector-length fields as extra instruction bytes.
- Failing unusual memory forms such as vector-index gather/scatter operands, RIP-relative prefetch instructions, absolute displacement forms, and base/index/scale combinations with `%rbp` special cases.
- Mishandling MPX `bnd*`, `notrack`, SHA, keylocker/MSR-list/user-MSR, APX atomic, and AVX-NE forms that may be less common than mainstream SSE/AVX operations.

Because the test does not execute these instructions, it cannot validate CPU feature availability, exception behavior, memory access behavior, arithmetic results, or architectural side effects. It is strictly a decode/classification regression set.
