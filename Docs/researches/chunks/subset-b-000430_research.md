## Purpose

`deploy/examples/crds.yaml` is the bootstrap API surface for Rook Ceph. Applying it registers custom resources that users, Helm charts, examples, generated clients, informers, and the Rook operator all depend on. Without these CRDs, Kubernetes cannot accept `CephCluster`, `CephBlockPool`, `CephClient`, bucket notification resources, or RADOS namespace resources.

The early CRDs in this chunk cover core storage and administrative workflows:

- `CephCluster` declares the root desired state for a Rook-managed or externally connected Ceph cluster.
- `CephBlockPool` declares replicated or erasure-coded RADOS pools used by RBD, RGW, NFS, and other Ceph services.
- `CephBlockPoolRadosNamespace` declares RADOS namespaces within block pools, including CSI cluster ID and mirroring metadata.
- `CephClient` declares CephX users, capabilities, and key rotation settings.
- `CephBucketTopic` and `CephBucketNotification` declare RGW bucket notification topics/endpoints and event filters.

The schemas provide Kubernetes-side validation, status subresources, `kubectl get` printer columns, immutability rules, and partial structural typing for embedded Kubernetes objects such as probes, placement, endpoint addresses, and PVC templates.

## Important APIs And Types

All resources in this chunk are namespaced under API group `ceph.rook.io`, version `v1`, and enable the `/status` subresource. They all require top-level `metadata` and `spec`, and most status schemas preserve unknown fields for forward compatibility with operator-written status details.

`CephBlockPoolRadosNamespace` exposes short names `cephbprns` and `cephrns`. Its spec requires `blockPoolName`; optional fields include `name`, `clusterID`, and `mirroring`. The schema marks `blockPoolName`, `clusterID`, and `name` immutable with CEL validation rules. `clusterID` is constrained to 1-36 characters matching `^[a-zA-Z0-9_-]+$`. Mirroring supports modes `""`, `pool`, and `image`, a `remoteNamespace`, and snapshot schedules. Status mirrors block pool status concepts: `conditions`, `info`, `phase`, `mirroringInfo`, `mirroringStatus`, and `snapshotScheduleStatus`.

`CephBlockPool` exposes short name `cephbp`. Its spec is `NamedBlockPoolSpec`, supporting pool naming for special internal pools (`.rgw.root`, `.nfs`, `.mgr`), `failureDomain`, `crushRoot`, `deviceClass`, `application`, arbitrary `parameters`, quota settings, mirroring, status checks, replicated settings, and erasure-coded settings. Replicated pools require `replicated.size`; erasure-coded pools require `erasureCoded.codingChunks` and `erasureCoded.dataChunks`. The schema constrains erasure coding algorithm to `isa` or `jerasure`, stripe units to known values, compression mode to `none`, `passive`, `aggressive`, `force`, or `""`, and quota size strings with a storage-size regex. Status includes `phase`, `observedGeneration`, `poolID`, `info`, `conditions`, mirroring state, snapshot schedule state, and CephX peer-token key rotation status.

`CephBucketNotification` exposes short name `cephbn`. Its spec requires `topic` and may define event names and object filters. The event enum covers S3 object-created, object-removed, lifecycle expiration/transition, replication, object sync, and object restore events. Filters can be key based (`prefix`, `suffix`, `regex`), metadata based, or tag based. Status contains `phase`, `observedGeneration`, and reusable Rook conditions.

`CephBucketTopic` exposes short name `cephbt`. Its spec requires `endpoint`, `objectStoreName`, and `objectStoreNamespace`. Endpoint variants include HTTP, AMQP, and Kafka. HTTP requires `uri` and can enable CloudEvents headers or disable SSL verification. AMQP requires `uri` and `exchange`, with ack levels `none`, `broker`, or `routeable`. Kafka requires `uri`, has default `mechanism: PLAIN`, default `ackLevel: broker`, supports `useSSL`, `disableVerifySSL`, and references Kubernetes Secrets for username and password. Status records the RGW-generated `ARN`, `phase`, `observedGeneration`, and the referenced `secrets` as Kubernetes object references.

## Control Flow

There is no executable control flow in this YAML. The operational flow is Kubernetes and operator driven:

1. A user or installer applies `crds.yaml`.
2. The Kubernetes API server registers each CRD, validates structural OpenAPI schemas, and exposes namespaced REST endpoints such as `cephclusters.ceph.rook.io` and `cephblockpools.ceph.rook.io`.
3. Users, examples, Helm charts, or tests create custom resources against those endpoints.
4. The API server validates required fields, enum values, numeric bounds, regexes, immutability rules, and embedded Kubernetes object shapes before persisting accepted resources.
5. Rook controllers watch these resources through generated clientsets, listers, and informers, reconcile Ceph state, and update status through the `/status` subresource.

For `CephCluster`, the CRD is a root control-plane input. A cluster resource drives creation and updates of monitors, managers, OSDs, crash collectors, dashboard, CSI-related users/secrets, monitoring exporters, network settings, disruption budgets, placements, resources, probes, PVCs, and storage devices. This chunk stops inside storage device-set placement, so the complete storage and status contracts must be read from later chunks.

For block pools and RADOS namespaces, the operator maps the CR specs to Ceph pool, namespace, mirroring, snapshot schedule, quota, and CephX state. For object notifications, the operator maps topic and notification specs to RGW notification configuration and reports generated ARNs or failure phases. For clients, the operator creates or rotates CephX keys and manages Kubernetes Secrets unless `removeSecret` asks it to delete the Kubernetes secret while leaving the CephX keyring until CR deletion.

## State And Persistence Behavior

The CRDs define two levels of persistence. First, the CRD objects themselves persist the API definitions in Kubernetes. Second, instances of these CRDs persist desired state and operator-observed state in etcd.

Spec fields in this chunk are the durable desired state. They include Ceph pool layout, mirroring configuration, RGW notification endpoints, CephX identity and key generation, cluster image/version, host data directory, cleanup intent, network provider, monitor topology, PVC templates, placement, resource requirements, and storage device-set settings.

Status fields are durable observed state written by controllers. Repeated status patterns include `phase`, `observedGeneration`, `conditions`, `info`, mirroring status, snapshot schedule status, generated topic ARN, referenced secrets, CephX key version/generation, pool ID, Ceph health, and FSID. Because `/status` is enabled, controllers can update status independently of user-owned spec fields.

Immutability and monotonicity are important persistence semantics. `CephBlockPoolRadosNamespace.spec.blockPoolName`, `.clusterID`, and `.name` cannot change after creation. `CephClient.spec.secretName` cannot change. `CephClient.spec.security.cephx.keyGeneration` cannot be decreased. `CephCluster.spec.dataDirHostPath` cannot change. Network provider changes are constrained so users disable the old provider before enabling a new one. These rules protect state that is difficult or unsafe to remap after Ceph resources, CSI IDs, host paths, or secrets already exist.

Some fields deliberately preserve unknown keys, including pool `parameters`, client `caps`, cluster annotations/labels, health-check status details, and several status objects. This lets Rook and Ceph carry flexible maps without regenerating the CRD for every daemon-specific or Ceph-specific key.

## Risks And Edge Cases

This file must be applied before any Rook Ceph custom resources. If the CRDs are missing or stale, later `cluster.yaml`, Helm chart, test, or operator operations fail at API admission or client discovery.

Because this chunk includes generated schema, manual edits are risky. Drift from `types.go` markers, generated client assumptions, Helm `resources.yaml`, or examples can create validation differences between install methods. Regeneration with the expected controller-gen version is the safer path for schema changes.

The `CephCluster` CRD is only partially covered in this chunk. Any research or change involving storage completion, full status, version status, conditions, or later validation rules must read subsequent chunks before drawing final conclusions.

Several fields protect dangerous operations but cannot make them safe by themselves. `cleanupPolicy.confirmation: yes-really-destroy-data` gates destructive cleanup intent; storage and disk sanitization settings can still destroy data if set incorrectly. `allowUnsupported` permits unsupported Ceph versions. `continueUpgradeAfterChecksEvenIfNotHealthy` can continue upgrades despite unhealthy PG checks. `allowUninstallWithVolumes` can permit uninstall while RBD images exist.

Network settings have operational hazards. Changing host networking can trigger monitor failover, Multus requires selectors, address range auto-detection may be imprecise, and `requireMsgr2` depends on kernel support. The CEL rules catch some invalid transitions but not all environmental problems.

Security-sensitive fields include bucket topic Secret references, CephX key generation, client caps, `removeSecret`, dashboard SSL settings, endpoint `disableVerifySSL`, Kafka/AMQP credentials, and CSI `skipUserCreation`. Admission validates shape and enums, but controller reconciliation and environment checks must enforce whether referenced secrets, endpoints, and Ceph capabilities actually work.

The CRD embeds large Kubernetes object schemas for probes, affinity, PVC templates, tolerations, and topology spread constraints. These copied schemas can lag newer Kubernetes behavior or include beta/alpha fields that depend on cluster feature gates, such as `volumeAttributesClassName`, `dataSourceRef`, and cross-namespace data source fields.

Status fields often preserve unknown data. That helps compatibility, but consumers that parse status must tolerate absent, extra, or version-dependent keys instead of assuming a closed schema.
