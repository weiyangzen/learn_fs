## Purpose

`cxd_known.h` is a golden-result data file for the `BASE-CREATEX_*` torture tests. It captures how Windows XP Professional 2002 SP2 responded to combinations of SMB `NTCreateX` desired-access bits, share modes, file-vs-directory setup, and preexisting-object setup. Samba's torture runner uses these records to check whether a server under test matches that historical Windows behavior.

The first part of the chunk establishes the vocabulary for the table:

- A CreateX open result is always stored at result slot `0`.
- File follow-up probes use result slots for read, write, and execute-style read.
- Directory follow-up probes reuse the same numeric slots for enumerate, create-child, and traverse.
- Access tests use one open and compare `cxd_result`.
- Share-mode tests use two opens and compare both `cxd_result` and `cxd_result2`.

The access portion of `cxd_known[]` gives the expected status for many desired-access values under the four setup modes. It includes grouped access masks such as `0x120089`, `0x120116`, `0x12019f`, `0x1200a0`, `0x1200a9`, `0x1201b6`, and `0x1201bf`, single-bit access masks, and variants ORed with `SEC_FLAG_MAXIMUM_ALLOWED` (`0x02000000`) and `SEC_FLAG_SYSTEM_SECURITY` (`0x01000000`) where generated by the torture loop.

The share-mode portion starts the Cartesian matrix for file opens. Each row records the outcome of the first open, the operations permitted on that first handle, the outcome of a second open from a second SMB client tree, and the operations permitted on the second handle. This slice includes many `cxd_sharemode2` groups and reaches rows where `cxd_sharemode1 = 1` and `cxd_sharemode2 = 1` before the assigned chunk ends.

## Important APIs, Types, And Data

`enum { ... } cxd_results` defines the status-vector layout used by every table row:

- `CXD_CREATEX = 0` is the open status.
- `CXD_FILE_READ = 1`, `CXD_FILE_WRITE = 2`, and `CXD_FILE_EXECUTE = 3` are follow-up operations for file handles.
- `CXD_DIR_ENUMERATE = 1`, `CXD_DIR_CREATE_CHILD = 2`, and `CXD_DIR_TRAVERSE = 3` alias the same positions for directory handles.
- `CXD_MAX` is the array length for both result arrays.

`enum cxd_test` classifies how a `createx_data` row should be interpreted:

- `CXD_TEST_CREATEX_ACCESS = 0` is the one-open golden table covered by lines 56-471.
- `CXD_TEST_CREATEX_ACCESS_EXHAUSTIVE = 1` exists for generated exhaustive runs but is not stored in this table.
- `CXD_TEST_CREATEX_SHAREMODE = 2` is the two-open golden table that begins at line 475.
- `CXD_TEST_CREATEX_SHAREMODE_EXTENDED = 3` exists for generated extended share-mode runs but is not stored in this known table.

`enum cxd_flags` controls object shape and setup:

- `CXD_FLAGS_DIRECTORY = 0x1` switches the consumer from file helpers to directory helpers.
- `CXD_FLAGS_MAKE_BEFORE_CREATEX = 0x2` tells the consumer to create the object before issuing CreateX.
- `CXD_FLAGS_MASK = 0x3` and `CXD_FLAGS_COUNT = 4` define the four access-test flag permutations.

`struct createx_data` is both the table row format and the live test scratch structure used by `denytest.c`. Its inputs are `cxd_test`, `cxd_flags`, `cxd_access1`, `cxd_sharemode1`, `cxd_access2`, and `cxd_sharemode2`. Its outputs are `cxd_result[CXD_MAX]` and `cxd_result2[CXD_MAX]`.

`static const struct createx_data cxd_known[]` is the core dataset. It is a compile-time, header-defined array, included directly by `source4/torture/basic/denytest.c`. The table uses C designated initializers but stores numeric enum values (`.cxd_test = 0` or `2`, `.cxd_flags = 0`, `0x1`, `0x2`, `0x3`) rather than symbolic names. Rows with a failed CreateX usually initialize only the first status element, relying on zero/default initialization for the remaining statuses that are not compared after a failed open.

## Control Flow And Consumer Behavior

There is no executable control flow in this header; control flow is supplied by `source4/torture/basic/denytest.c`.

The main integration path is:

1. `denytest.c` includes `cxd_known.h`, making the enums, `struct createx_data`, and `cxd_known[]` visible in the same translation unit.
2. The test generator functions populate a live `struct createx_data`:
   - `torture_createx_access()` sets `cxd_test = CXD_TEST_CREATEX_ACCESS`, iterates `cxd_flags` from `0` through `CXD_FLAGS_MASK`, then tests grouped access masks and single-bit masks, including maximum-allowed and system-security variants.
   - `torture_createx_sharemodes()` sets `cxd_test = CXD_TEST_CREATEX_SHAREMODE` for non-extended runs, sets `CXD_FLAGS_DIRECTORY` only for directory variants, and iterates share-mode and access-group permutations.
3. `torture_createx_specific()` chooses file or directory helper functions from `CXD_FLAGS_DIRECTORY`, optionally creates the object when `CXD_FLAGS_MAKE_BEFORE_CREATEX` is set, opens with the first access/share tuple, and runs read/write/execute or enumerate/create-child/traverse follow-up probes when the open succeeds.
4. For share-mode tests, `torture_createx_specific()` opens the same object again through `cli2` using `cxd_access2` and `cxd_sharemode2`, then captures `cxd_result2`.
5. `cxd_find_known()` performs exact tuple matching on `cxd_test`, `cxd_flags`, both access masks, and both share modes. It skips known-table lookup for exhaustive/extended tests because those are generated rather than stored.
6. If a matching known row is found, `torture_createx_specific()` compares each captured `NTSTATUS` in `cxd_result` and, for share-mode tests, `cxd_result2`. It breaks after index `0` if the corresponding CreateX open failed.
7. If there is no known row or if comparison fails, the consumer prints a row-shaped initializer to the torture output. This is the regeneration signal for missing or changed expectations.

This chunk's table ordering matters for performance. `cxd_find_known()` keeps a static cursor and first tries the next entry before falling back to a full linear scan. The table appears ordered in the same nested-loop order used by the generator, so changing row order would not change correctness but could hurt test speed.

## State And Persistence Behavior

The header itself has no mutable state and performs no persistence. It declares compile-time constants only.

At runtime, the table drives tests that mutate a temporary SMB share path named by `CREATEX_NAME` in `denytest.c` (`"\\createx_dir"`). Depending on `cxd_flags`, the consumer may:

- Delete stale file or directory state before a run.
- Create a file or directory before issuing CreateX.
- Open a file or directory with the requested access/share tuple.
- Attempt follow-up operations against the returned handle.
- Close handles and remove temporary objects.

For normal known-table runs, the table is read-only. When the environment variable path for `CREATEX_DATA` is active in the exhaustive access path, `denytest.c` writes raw `struct createx_data` records to a data file instead of comparing against `cxd_known[]`; however, `cxd_find_known()` explicitly avoids table lookup for exhaustive and extended test kinds.

## Risks And Maintenance Notes

- The table is a golden copy of Windows XP SP2 behavior. Modern Windows, Samba, or SMB server implementations may legitimately differ in edge cases, but the torture test treats differences as compatibility signals unless the expected table is deliberately updated.
- Numeric initializers make rows compact but reduce readability. For example, `.cxd_test = 2` and `.cxd_flags = 0x1` require readers to map back to `CXD_TEST_CREATEX_SHAREMODE` and `CXD_FLAGS_DIRECTORY`.
- The same result indexes are reused for file and directory checks. This is intentional but easy to misread: slot `1` is read for files and enumerate for directories; slot `2` is write for files and create-child for directories; slot `3` is execute-read for files and traverse for directories.
- Partial result arrays are meaningful. When CreateX fails, rows often contain only `{ NT_STATUS_ACCESS_DENIED }`; the consumer stops comparison after index `0` when the open failed. Filling or comparing the remaining slots blindly would create false failures.
- `CXD_FLAGS_MAKE_BEFORE_CREATEX` changes preexisting-object state. Expected statuses for access masks can differ between creating/opening a nonexistent path and opening a path created before the test.
- SACL-related access bits are skipped when `sacl_support` is disabled. The table still contains those known results, but the runtime path may skip rows whose access masks include `SEC_FLAG_SYSTEM_SECURITY`.
- Table order has performance implications because `cxd_find_known()` optimizes for sequential access with a static index. Reordering rows can turn most lookups into full scans of a large table.
- This chunk ends in the middle of the file/non-extended share-mode matrix. Merge/reconciliation should combine this report with later chunks before drawing conclusions about all share-mode coverage, directory coverage, or the full `cxd_known[]` array.
