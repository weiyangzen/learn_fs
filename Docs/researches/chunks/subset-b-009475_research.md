## Purpose

The purpose of this generated table is to give the x86 ifuzz backend a corpus of encodable instruction forms. On package initialization, `init` calls `Register(insns)`, which installs the table into the parent `x86` package and ultimately into `iset.Arches[iset.ArchX86]`. The fuzzing engine then asks the registered instruction set for mode/type-compatible instructions and calls `Insn.Encode` to synthesize machine-code bytes.

Each literal is an encoding recipe for one instruction form. Repeated instruction names are intentional because x86 frequently has multiple encodings for the same mnemonic depending on opcode, prefix, operand size, address mode, ModRM constraints, immediate width, memory-only/register-only form, REX.W, VEX/XOP prefix fields, or CPU extension.

## Control Flow

Control flow in this chunk is minimal. During package initialization, Go executes `init`, which calls `Register(insns)`. `Register` appends pseudo instructions from `pseudo.go`, indexes every instruction by mode and type through `iset.ModeInsns.Add`, and stores the resulting `InsnSet` in the global `iset.Arches` map.

After registration, generation flow is data-driven:

1. ifuzz selects instructions from `InsnSet.GetInsns(mode, typ)`.
2. `Insn.Encode` checks `cfg.IsCompatible(insn)`.
3. The encoder emits random allowed legacy prefixes or a VEX/XOP prefix, applies fixed `Prefix`, emits `Opcode`, synthesizes ModRM/SIB/displacement fields from `Mod`, `Reg`, `Rm`, `Srm`, and `NoSibDisp`, appends generated immediates based on `Imm`/`Imm2`, and finally appends `Suffix`.
4. `InsnSet.Decode` scans registered entries in table order and uses the same metadata to estimate instruction length.

Because decode returns the first matching table entry, ordering matters for ambiguous x86 encodings. Generated entries with fixed prefixes, exact ModRM fields, and mandatory prefix bans must stay aligned with the generator's intended specificity.

## State and Persistence Behavior

This file has no durable storage and no mutable runtime state of its own beyond registration. The persistent process-wide effect is that importing `pkg/ifuzz/x86/generated` populates the global `iset.Arches` registry for x86. That state controls later fuzz generation and decoding for the process.

The instruction entries are pointer values and are not meant to be mutated after registration. The encoder treats each entry as immutable metadata while using `iset.Config` and `rand.Rand` to produce different byte streams. The only stateful behavior represented by entries is semantic metadata: `Priv` affects privilege-filtered selection, `Mode` affects architecture-mode filtering, and `Extension`/`Name` provide instruction identity for reporting and selection.

## Risks

- Generated data drift can silently reduce fuzz coverage or produce invalid instruction streams. A wrong `Mode`, `Prefix`, `Rexw`, `VexP`, `VexMap`, or immediate width changes the generated byte sequence without any local compile-time failure.
- Ambiguous encodings are order-sensitive. The decoder scans `insnset.Insns` linearly, so broad entries before specific entries can mask more precise forms.
- Prefix constraints are delicate. Missing `NoRepPrefix`, `No66Prefix`, `Mem32`, or `Mem16` can let random prefix generation turn one instruction into another or create invalid encodings.
- Privilege marking is security- and test-environment-sensitive. If a privileged instruction lacks `Priv: true`, unprivileged fuzz configurations may generate instructions that fault or disturb system state.
- Memory/register-only ModRM constraints are easy to get wrong. `Mod: -3` forbids register operands; `Mod: 3` requires them. Incorrect constraints affect both generated operands and decoder length accounting.
- VEX/XOP/AVX fields have multiple interacting sentinels. Bad `VexNoR`, `VexL`, `Rexw`, `VexP`, or `VexMap` values can generate encodings that XED rejects or that alias unrelated legacy instructions.
- This file is generated, so manual edits would be overwritten. Fixes should target the generator or source instruction list, followed by regeneration.
