## Important APIs, Types, and Macros

- `enum sparx5_target` assigns target IDs such as `TARGET_ANA_AC`, `TARGET_ANA_ACL`, `TARGET_ANA_CL`, `TARGET_ASM`, `TARGET_DEV10G`, `TARGET_DEV2G5`, `TARGET_DEV5G`, `TARGET_DSM`, `TARGET_EACL`, `TARGET_FDMA`, `TARGET_GCB`, `TARGET_HSCH`, `TARGET_HSIO_WRAP`, `TARGET_LRN`, `TARGET_PCEP`, `TARGET_PCS10G_BR`, and `TARGET_PCS25G_BR`. These IDs select the hardware aperture for a register operation.
- `extern const struct sparx5_regs *regs` is the key integration point for chip-family differences. Register macros use `regs->gaddr`, `regs->gcnt`, `regs->gsize`, `regs->rcnt`, `regs->raddr`, `regs->tsize`, `regs->fpos`, and `regs->fsize` to avoid hardcoding every layout detail when Sparx5 and LAN969x differ.
- `spx5_field_get()` and `spx5_field_prep()` are non-constant-mask variants of `FIELD_GET()` and `FIELD_PREP()`. They are required for masks whose bit widths or positions are built from the runtime `regs` descriptor.
- `__REG(...)` is a pass-through variadic macro. Each register macro expands to an argument tuple shaped as target, target instance, target count/size, group base/index/count/size, register offset/index/count, and register width. The actual address computation is performed by downstream helper macros/functions that consume this tuple.
- Every field follows a stable pattern: a mask macro using `BIT()` or `GENMASK()`, then `<FIELD>_SET(x)` and `<FIELD>_GET(x)`. Constant masks use Linux `FIELD_PREP()` / `FIELD_GET()`, while variable masks use the `spx5_` helpers.

## Control Flow and Usage

This header has no direct function control flow; it provides declarative inputs to register access code. Runtime control flow is created by callers in other Sparx5 driver files:

1. Driver code chooses the target register macro, often parameterized by a port/device target `t`, group index `g`, or replicated register index `r`.
2. The macro expands into an `__REG()` tuple with the target ID, variant-specific offsets/counts/sizes, and register width.
3. Higher-level access helpers from `sparx5_regs.h` compute the memory-mapped register address and issue reads, writes, or read-modify-writes.
4. Callers build register values with `_SET()` helpers, combine fields with bitwise OR, and decode returned values with `_GET()` helpers.

The control pattern is especially visible in table-like blocks. Analyzer port/VLAN/classification tables use group and replication indices; ASM and DEV statistics use sequential per-port counter offsets; FDMA channel registers use replicated channel indices; LRN access registers are programmed as a small command/data window for MAC table access; HSCH scheduler fields use scheduler element indices; PCEP registers program a multi-register outbound address translation region.

## State and Persistence Behavior

The macros themselves are compile-time definitions and hold no mutable state. The only C-visible state in this chunk is the global `regs` pointer, which must identify the active chip layout before any macro using variable addresses or field positions is consumed.

Persistent behavior lives in hardware registers and tables after writes:

- Analyzer/classifier/L2/L3 state controls forwarding, VLAN membership, TSN stream filters, service gates, DLB selection, ACL key selection, and learning.
- Statistics and sticky bits accumulate hardware observations until cleared by explicit reset/clear/sticky-write sequences.
- MAC, PCS, reset, PTP stamper, pause, and max-length registers configure live port behavior and must be sequenced with port bring-up/down paths.
- FDMA channel, descriptor, interrupt, and extraction/injection controls define live packet DMA behavior.
- DSM, HSCH, SDLB, and policing registers define queueing, shaping, drop, pause, and leak-bucket behavior in hardware.
- LRN access and auto-age registers drive MAC table lookup/update/scan state in the learning engine.
- PCEP outbound ATU registers persist the PCIe address translation window until reprogrammed or reset.

Chip-variant state is encoded through `regs`; several fields are marked `SPARX5 ONLY` or `LAN969X ONLY`, and many widths/positions are retrieved from `regs->fsize` or `regs->fpos`. Incorrect `regs` initialization would make otherwise valid `_SET()` / `_GET()` calls target the wrong bits or addresses.

## Risks and Edge Cases

- The file is layout-critical generated code. Wrong target IDs, offsets, group sizes, replication counts, field positions, or widths can silently corrupt unrelated hardware registers.
- Variable masks built from `regs->fsize` and `regs->fpos` depend on correct runtime chip metadata. A zero or incorrect width can make `spx5_field_get()` / `spx5_field_prep()` compute invalid shifts via `ffs(_mask) - 1`.
- Several blocks include `SPARX5 ONLY` or `LAN969X ONLY` fields in the same generated header. Callers must still gate feature use by chip family/capabilities; the macros alone do not prevent writes on unsupported hardware.
- Multi-word port masks are split into base, `CFG1`, and `CFG2` registers for some Sparx5-only source/PGID/mirror fields. Missing high words will misconfigure ports above the first mask word.
- Sticky and status fields use the same `_SET()` helpers as normal config fields. Callers must know hardware clear semantics, because writing a `1` may clear or acknowledge sticky status rather than set persistent configuration.
- Repeated register macros can hide generator anomalies. This span contains a duplicated `DEV2G5_PHAD_CTRL` block with identical macro names; this compiles only because the duplicate definitions are textually equivalent, but generator drift here would produce redefinition warnings or layout ambiguity.
- Byte counters are split across low and MSB registers in some ASM/DEV blocks. Readers must avoid torn statistics by following the driver/hardware-recommended read order or snapshot scheme.
- FDMA and LRN command/control registers represent active engines. Programming channel controls, descriptor pointers, MAC table CPU access, scan controls, or reset bits without proper ordering can race live traffic or hardware scans.
- Reset and RAM init macros can disrupt broad hardware state. `GCB_SOFT_RST`, `ASM_RAM_INIT`, `ANA_AC_RAM_INIT`, `DSM_RAM_INIT`, and `EACL_RAM_INIT` should only be used in tightly controlled init/reset paths.
- PCIe outbound ATU registers use absolute-looking offsets and split lower/upper limit/base fields. Incorrect programming could break DMA/MMIO reachability outside ordinary switch forwarding paths.
