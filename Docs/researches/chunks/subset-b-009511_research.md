## Purpose

The chunk contributes static USB device-match records used by syzkaller's virtual USB descriptor generation. Each `usbIds` map key is a Linux USB driver name, and each value is a concatenated binary string of fixed-width `UsbDeviceID` records. These records mirror kernel `struct usb_device_id` matching rules extracted by syz-usbgen, including vendor/product IDs, bcdDevice ranges, device class/subclass/protocol, interface class/subclass/protocol, and interface number.

At runtime this data lets syzkaller bias generated USB descriptors toward IDs that actual Linux drivers bind to. That improves coverage over purely random descriptors because kernel probe paths see realistic match fields for network, wireless, serial, radio/media, HID-adjacent, storage/control, and audio USB drivers.

The consumer schema is in `init_vusb.go`:

- `BytesPerUsbID = 17`: every table record must be exactly 17 bytes when decoded.

- `patchUsbDeviceID` copies matched fields into generated USB device and interface descriptors.
- `randUsbDeviceID` chooses one record from a concatenated string and decodes it with `binary.Read(..., binary.LittleEndian, &id)`.

The visible record prefixes show common match classes. Many values begin with `\x03\x00`, meaning vendor and product matching. ## Control Flow

There is no local branching or function execution in this chunk. The runtime flow is data-driven:

1. Go initializes the `usbIds` map when package `sys/linux` is loaded.
2. Later in the same file, generated `usbIdsAll` concatenates every `usbIds["driver"]` value in sorted driver order.
3. `generateUsbDeviceDescriptor` creates or mutates a syzkaller USB descriptor argument.
4. If the descriptor does not contain `ANY`, it calls `patchUsbDeviceID(g, &arg, calls, usbIdsAll, true)` to choose a random packed record from the whole generated corpus.
5. `patchUsbDeviceID` decodes the selected 17-byte record and patches descriptor fields. With `patchNonMatching=true`, it also fills fields not explicitly guarded by the match flags.
6. Specialized paths use subsets. `generateAudioDeviceDescriptor` builds a concatenated string from audio driver names, including `snd-bcd2000`, `snd-ua101`, `snd-usb-6fire`, and `snd-usb-audio` from this range, then patches only matched fields with `patchNonMatching=false`.

## Risks And Maintenance Notes

The highest-risk invariant is record width. `randUsbDeviceID` computes `len(ids) / BytesPerUsbID` and slices exactly 17 bytes. If a generated string is truncated, has an extra byte, or is concatenated across a bad boundary, the last partial record can be silently ignored or a selected record can decode incorrectly.

Match flags must stay aligned with `UsbDeviceID` field order and little-endian decoding. A generator/schema mismatch can patch vendor/product/class fields into the wrong descriptor positions and either miss the intended driver or accidentally bind another driver.

Large entries increase skew. Drivers with many records, such as `option`, `qmi_wwan`, `rt2800usb`, `rtl8xxxu`, `sierra`, and `snd-usb-audio`, have higher selection probability in `usbIdsAll` because selection is uniform by record, not by driver. That is useful for common hardware families but can reduce coverage of sparse drivers.

Targeted generators depend on exact driver-name strings. For example, `generateAudioDeviceDescriptor` names `snd-bcd2000`, `snd-ua101`, `snd-usb-6fire`, and `snd-usb-audio`; if generation changes a key spelling or omits a key, that specialized path silently loses those IDs.

Chunk boundaries are a review hazard. This range starts inside `mt76x2u` and ends inside `snd-usb-audio`, so byte-count or completeness analysis cannot treat the requested lines as a standalone valid Go fragment. Adjacent chunks are needed to validate those two boundary values.

Because the file is generated, fixes should target extraction inputs or `tools/syz-usbgen` rather than hand-editing individual string literals.
