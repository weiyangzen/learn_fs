## Container Operations In This Chunk

- `GET /containers/json` (`ContainerList`) lists containers using the compact `ContainerSummary` representation. Query parameters include `all`, `limit`, `size`, and a JSON-encoded `filters` map supporting ancestor, before/since, expose/publish, exit code, health, id/name, isolation, task flag, label, network, status, and volume filters.
- `POST /containers/create` (`ContainerCreate`) creates a container from a body composed of `ContainerConfig` plus `HostConfig` and `NetworkingConfig`. It accepts a name query parameter with a strict container-name pattern and a platform query parameter used for image lookup and warning generation when local image platform differs from the host. Responses distinguish success (`201`), bad input, missing image, conflict, and server errors.
- `GET /containers/{id}/json` (`ContainerInspect`) returns detailed container state: identity, created time, command path/args, `ContainerState`, image ID, resolver/hosts/log paths, restart count, storage driver data, host config, size fields, mount points, original config, and network settings.
- `GET /containers/{id}/top` (`ContainerTop`) lists running processes using an optional `ps_args` query string and returns `Titles` plus `Processes`.
- `GET /containers/{id}/logs` (`ContainerLogs`) streams stdout/stderr logs for `json-file` and `journald` drivers. Parameters control follow, stdout, stderr, since/until timestamps, timestamp prefixing, and tail count. It produces raw or multiplexed Docker stream media types.
- `GET /containers/{id}/changes` (`ContainerChanges`) reports filesystem changes as path/kind records where kind `0` is modified, `1` is added, and `2` is deleted.
- `GET /containers/{id}/export` (`ContainerExport`) exports the container filesystem as an octet-stream tarball.
- `GET /containers/{id}/stats` (`ContainerStats`) streams or returns one container resource-usage sample. The documentation embeds CPU and memory calculation formulas, cgroup v1/v2 differences, and compatibility handling for missing `online_cpus`.
- `POST /containers/{id}/resize` (`ContainerResize`) resizes a container TTY using required height (`h`) and width (`w`) query parameters.
- `POST /containers/{id}/start` (`ContainerStart`) starts a container and optionally overrides detach keys. It uses `204` for success and `304` for already started.
- `POST /containers/{id}/stop` (`ContainerStop`) stops a container with optional signal and timeout query parameters. It uses `204` for success and `304` for already stopped.
- `POST /containers/{id}/restart` (`ContainerRestart`) restarts a container with optional signal and timeout.
- `POST /containers/{id}/kill` (`ContainerKill`) sends a signal, defaulting to `SIGKILL`, and has a `409` response when the container is not running.
- `POST /containers/{id}/update` (`ContainerUpdate`) changes resource controls and restart policy in place using a body composed from `Resources` plus `RestartPolicy`, returning warnings on success.
- `POST /containers/{id}/rename` (`ContainerRename`) renames a container with required `name` query parameter and reports name conflicts via `409`.

## Control Flow And Behavioral Contracts

The file is declarative rather than executable code, but it encodes daemon/client control flow through request/response schemas and status codes. Container creation is represented as a composition pipeline: portable `ContainerConfig` is merged with host-only `HostConfig` and network attachment `NetworkingConfig`; the daemon then resolves image/platform constraints, creates storage/network/runtime configuration, and returns `ContainerCreateResponse` with warnings. Runtime state transitions are exposed as separate operations: create, start, stop, restart, kill, update, rename, inspect, and query logs/stats/filesystem changes.

Several definitions express API-level invariants. `ObjectVersion` documents optimistic concurrency for swarm objects: updates must carry the version read by the client, so concurrent writes do not silently overwrite each other. `RestartPolicy` specifies delayed restart behavior. `PortMap` uses container-port/protocol keys and nullable arrays to represent exposed-but-unbound ports. `NetworkSettings` keeps deprecated default-bridge fields for compatibility but points clients to the per-network `Networks` map. Image ID fields explicitly distinguish image config digests from manifest digests in `RepoDigests`.

Streaming and binary flows are represented by media types and loose schemas. Logs can be raw or multiplexed stream bytes. Stats are documented as a live stream or one-shot object, but its schema is intentionally broad (`type: object`) because daemon stats shape varies by platform and cgroup version. Export returns an octet-stream tarball. Build, create-image, and push progress definitions are shaped as JSON progress records with optional error/progress/detail/aux fields, used by endpoints outside this chunk.

## State And Persistence Behavior

The schema captures several persistent state domains. Container state includes writable-layer size, rootfs size, storage-driver metadata, log path, restart count, mount points, network sandbox data, health logs, and current runtime status. Host-level persistence appears in volume mountpoints, Docker root directory, storage-driver status, default address pools, local image cache metadata, registry mirror/insecure-registry configuration, daemon labels, configured runtimes, and component build commits.

Image definitions distinguish local mutable metadata from content-addressed image data. `ImageInspect.Metadata.LastTagTime` is daemon-local; `RepoTags` and `RepoDigests` are references; `RootFS.Layers` and `Id` are content-derived; `GraphDriverData` is driver-specific and informational. Volume definitions separate machine-local volumes from swarm cluster volumes: cluster volumes carry swarm IDs, `ObjectVersion`, CSI plugin volume IDs, capacity/context/topology, publish state per node, availability, access mode, and secrets passed to the storage plugin.

Swarm definitions model replicated cluster state, including raft snapshot/election/heartbeat settings, dispatcher heartbeat, CA rotation/signing configuration, join tokens, manager reachability, node/task/service versions, update/rollback state, service job iteration, and secret/config references. The presence of object versions and status/spec separation is important: specs are user-modifiable desired state, while status fields are manager-observed or runtime-observed state.

## Risks And Edge Cases

- The file is large and highly shared; edits to reusable definitions such as `HostConfig`, `Resources`, `EndpointSettings`, `Mount`, `ContainerConfig`, or `ErrorResponse` can silently affect many endpoints and generated types.
- Some examples and schemas are intentionally broader or older than current daemon internals for compatibility. Deprecated network fields, `VirtualSize`, registry nondistributable-artifact fields, and legacy plugin info must be preserved carefully.
- Several fields are platform-dependent or runtime-dependent. Clients must not assume Linux-only cgroup fields, Windows isolation fields, cgroup v1 memory stats, or driver-specific `GraphDriverData`/volume `Status` keys are present or stable.
- Streaming endpoints have non-ordinary HTTP behavior. `ContainerLogs` does not upgrade like attach and may omit `Content-Type`; `ContainerStats` can stream indefinitely unless `stream=false`; binary tar export and raw/multiplexed streams need client-side framing handling.
- Compatibility depends on nullable and omitted-field behavior. `x-nullable`, empty strings, `null` arrays, and omitted booleans often carry different meanings, especially for `Init`, `PidsLimit`, ports, health, swarm remote managers, and image config fields.
- Security-sensitive inputs include bind mounts, device requests, capabilities, privileged mode, sysctls, namespace joins, insecure registry config, plugin privileges, swarm CA material, secrets/config references, credential specs, and signals sent to containers.
- The stats documentation warns that cgroup v2 omits or changes key fields; clients calculating CPU and memory percentages need the documented fallback formulas and must handle missing counters.
- `ObjectVersion` optimistic concurrency is a correctness boundary for swarm updates. Clients that ignore it risk failed updates or stale desired-state writes.
