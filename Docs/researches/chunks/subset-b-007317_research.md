## Control Flow and Behavioral Contracts

The primary MapReduce task flow is input split creation, record reading, map calls, intermediate collection, partitioning, shuffle/sort/grouping, reduce calls, output writing, task commit, and job cleanup. `InputFormat` and `RecordReader` own conversion from split bytes to records. `Mapper` emits through `OutputCollector`; `Partitioner` chooses reduce partition; sort/grouping is governed by job comparators; `Reducer` iterates grouped values; `OutputFormat` creates `RecordWriter`; and `OutputCommitter` controls temporary output setup, commit, abort, and cleanup.

The old/new API bridge flow is explicit in `OutputCommitter`, `TaskAttemptContext`, `TaskID`, and `TaskAttemptID`. Public old-API classes extend new `org.apache.hadoop.mapreduce` classes, but old signatures remain part of the compatibility contract. The final new-API `OutputCommitter` methods delegate to abstract old-API methods, so subclasses implement the old hooks while the framework may call the new ones.

Progress and liveness flow is centered on `Reporter`, `TaskTracker`, and task contexts. Mappers/reducers call `reporter.progress()`, `setStatus`, and counter increments. Child tasks report `TaskStatus` periodically to `TaskTracker.statusUpdate`, can report diagnostics, next record ranges for skip mode, pings, commit-pending state, completion, shuffle errors, filesystem errors, and lost map outputs. Job clients observe aggregate state through `RunningJob` and per-task state through `TaskReport`/`TaskCompletionEvent`.

Skip-bad-record flow is retry based. After a configured number of failed attempts, tasks begin reporting current record ranges to the TaskTracker before processing records or groups. If the task crashes, the TaskTracker can identify the last reported range and skip it on later attempts. The framework narrows skipped ranges across retries until configured map/reduce skip thresholds are met or attempts are exhausted. Automatic processed-record counters can be disabled for asynchronous or buffered applications such as streaming, which must then increment counters manually.

SequenceFile reader/writer flow is split around typed objects, raw bytes, and text conversion. `SequenceFileRecordReader` reads typed `Writable` keys/values and reports byte-range progress. Binary readers/writers use `BytesWritable` but preserve the on-disk key/value class metadata configured in `JobConf`. Text readers wrap sequence-file values by converting keys and values to string form. Filtered sequence-file input wraps reader creation with key-based acceptance filters.

Task log flow crosses process and filesystem boundaries. `TaskLog.captureOutAndError` rewrites a command list so stdout/stderr land in named files, optionally after setup commands and optionally with PID-file handling. Tail length controls whether full output or only a tail is saved. `syncLogs` and `TaskLogAppender` align child JVM log output with task IDs and log-size caps. `TaskLogServlet` and `TaskTracker.MapOutputServlet` expose logs and map outputs through HTTP servlets.

JobControl flow is a state machine over dependent jobs. A `Job` begins in `WAITING`, becomes `READY` when dependencies have succeeded, moves to `RUNNING` after `submit`, and then ends in `SUCCESS` or `FAILED`. Dependency failure propagates to `DEPENDENT_FAILED`. `JobControl.run` repeatedly monitors running jobs, recomputes waiting jobs, and submits ready jobs until stopped or all jobs finish; `suspend` and `resume` affect the management thread.

Join flow is a merge over sorted child readers. `CompositeInputFormat` parses a join expression and creates child splits/readers. `CompositeRecordReader` keeps child readers ordered by current key, fills a join collector for matching keys, and invokes `combine` to decide whether to emit a tuple or derived value. Resetable iterators allow cross-product and replay semantics for multiple values under the same key. Inner, outer, override, and multifilter variants differ mainly in `combine`, `fillJoinCollector`, or `emit` behavior.

ChainMapper flow is in-task function composition. During configuration, the chain instantiates/configures each mapper using the job configuration and mapper-specific `JobConf` overrides. During `map`, output from each mapper becomes input to the next mapper until the last mapper writes to the task output collector. By-value handoff serializes/deserializes keys and values to protect downstream mappers from mutation assumptions; by-reference handoff avoids that cost when mapper contracts permit it.

## Risks and Compatibility Notes

Most classes in this chunk are deprecated old-API contracts, but deprecation does not reduce compatibility risk. Hadoop 0.20.0 users still compile and run against `org.apache.hadoop.mapred`, so method signatures, old/new bridge behavior, exception declarations, deprecation text, enum constants, and serialized `Writable` formats remain important.

Mapper/reducer contracts are mutation-sensitive. The documentation explicitly says framework key/value objects are reused, so applications must clone objects they retain. Changing reuse, grouping, comparator, combiner, partitioning, or progress semantics can break user jobs or cause subtle data corruption.

Output commit behavior is high risk because it controls atomicity and data visibility. `setupJob`, `setupTask`, `needsTaskCommit`, `commitTask`, `abortTask`, and `cleanupJob` must preserve old/new context bridging and temporary-to-final output promotion. Errors can leave partial output, delete valid output, or allow multiple attempts to commit.

Skip-bad-record behavior trades correctness for job completion. Incorrect counters, record-range reporting, or skip threshold interpretation can skip too much data, fail to isolate deterministic bad records, or make streaming/asynchronous jobs miscount progress. `Long.MAX_VALUE` and zero thresholds have special meanings that tests should preserve.

SequenceFile raw/text formats are format-compatibility surfaces. Binary output writes `BytesWritable` data while advertising configurable stored classes; mismatches can produce unreadable files. Compression type defaults to `RECORD`; changing default or configuration keys would affect persisted output. `SequenceFileAsTextRecordReader` relies on `toString()` conversions and may change output if underlying key/value `toString()` behavior changes.

Task identity string parsing and regex generation are compatibility-sensitive. Public examples show formats such as `task_..._m_000005` and `attempt_..._m_000005_0`; tools parse logs, counters, and web output around these strings. `forName`, `read`, `downgrade`, and pattern builders should preserve null wildcard behavior, zero padding, and map/reduce markers.

Task logging APIs are command-construction and file-system risk points. `captureOutAndError`, `captureDebugOut`, and `addCommand` manipulate shell commands, quoting, setup commands, PID files, stdout/stderr paths, and tail truncation. Bugs can lose logs, write to the wrong file, expose shell injection issues if callers pass untrusted strings, or make child task launch commands fail.

`TaskTracker` is a broad daemon-facing public class with synchronized RPC methods and filesystem/network side effects. Changes to commit negotiation, shuffle error handling, map-output-lost reporting, task fetch semantics, or cleanup can affect job correctness and recovery. The public `main` method and servlet endpoints also make operational behavior visible.

Join APIs are type- and ordering-sensitive. They assume sorted inputs, compatible `WritableComparable` keys, and matching tuple positions. Resetable iterators can return false despite apparent availability for nested joins; callers must respect that contract. `TupleWritable` warns against general persistence, so broadening its use can create fragile serialized data dependencies.

`ChainMapper` by-reference mode is an optimization with aliasing risk. If a mapper mutates keys/values and the next mapper assumes collector immutability, by-reference chains can corrupt downstream data. The chain also performs no key/value conversion, so declared input/output classes must match between adjacent mappers and the reducer chain.
