## Purpose

The file is a developer convenience artifact for debugging bisync integration cases from VS Code. It is generated by `bisync_debug_test.go`, whose comment says to copy only needed entries into a real VS Code `launch.json` because VS Code can crash when all generated entries are loaded at once.

Each entry gives Delve's Go extension enough information to run a single bisync test case:

- `type: "go"` selects the VS Code Go debugger.
- `request: "launch"` starts a new debug session.
- `mode: "test"` runs package tests instead of a normal binary.
- `program: "./cmd/bisync"` points at the bisync package under test.
- `args` passes `-remote`, `-remote2`, `-case`, and `-no-cleanup` to the bisync test harness.

The matrix is intended to make a failing backend/scenario/direction combination easy to reproduce interactively without manually transcribing long `go test` command lines.

## Control Flow

The JSON itself has no executable control flow. Runtime control begins when a developer selects one of these launch configurations in VS Code. VS Code invokes the Go debugger in test mode for `./cmd/bisync`, and the Go test binary receives the listed bisync harness flags.

Generation control flow is simple and deterministic:

1. `generateDebuggers()` parses the shared `fstest/test_all/config.yaml`.
2. It discovers non-empty `test_*` directories in bisync testdata.
3. It iterates over configured backends, test cases, and three variations.
4. It skips non-`RemoteRemote` variations when the backend remote is `local`, avoiding duplicate `local`/`local` configurations.
5. It writes one JSON configuration per remaining tuple.

Within this chunk, the generated ordering follows the backend order from the config file and the discovered scenario order. That ordering matters mostly for merge/reconciliation and for humans searching the large file.

## State and Persistence Behavior

The file persists a generated snapshot of launch configurations in the repository under `cmd/bisync/testdata`. It does not store bisync runtime state, listings, lockfiles, logs, or golden outputs.

The `-case` flag selects a scenario directory such as `test_resync` or `test_filters`. Those scenario directories drive the test setup and expected behavior; this launch file only routes into them.

## Risks

- The file is generated and large. Hand edits are easy to lose or make inconsistent with `bisync_debug_test.go`.
- VS Code scalability is an explicit concern; the generator warns that loading too many entries can crash VS Code.
- The chunk boundaries are mid-object. Any chunk-level parser must account for the leading tail and trailing head rather than treating this line range as standalone JSON.
- Remote names depend on local rclone configuration and service availability. Running entries for Box, Yandex, Swift, FTP, SFTP, or SugarSync can fail for environmental reasons unrelated to bisync logic.
- `-no-cleanup` intentionally preserves test artifacts. Repeated debug runs can leave remote test data behind and may affect quotas, costs, or later test isolation.
- Some generated entries may drift from current backend config. In the current tree, nearby `config.yaml` content shows the `TestSwift:` backend commented while this saved matrix still contains `TestSwift:` entries in this chunk.
- Same-backend `RemoteRemote` entries use one configured remote name for both sides. The test harness must isolate paths correctly; otherwise a debugger launch can exercise aliasing or cleanup edge cases.
- Scenario coverage is matrix-wide but not necessarily backend-supported. Individual remotes can lack modtime, checksum, empty-directory, encoding, or server-side behavior needed for specific scenarios.
