## Purpose

The purpose of this span is to provide static CP949 lead-byte pages for decoding two-byte Korean codepage sequences into Unicode `wchar_t` values. Later code in this same file indexes these `c2u_*` arrays from the second byte of a multibyte character after choosing the page by the first byte. This chunk therefore supplies most of the forward conversion data used by the module's later `char2uni()` implementation.

The data is generated from Microsoft CP949 mapping material and mixes several classes of characters: extended Hangul syllables, EUC-KR/KS X 1001 symbol pages, fullwidth ASCII variants, Hangul jamo, Greek/Cyrillic/Japanese kana blocks, box drawing and measurement symbols, Hanja, and CJK compatibility ideographs in the `F900`-style ranges. `0x0000` entries mark undefined byte positions and are part of the validation signal for invalid CP949 byte pairs.

## Control Flow

There are no executable functions in this chunk. Control flow is data-driven and occurs later when the decoder uses the first byte of a CP949 double-byte sequence to select the matching `c2u_XX` page and then uses the second byte as the array index.

The expected later decode flow is:

1. Accept a raw byte sequence from the NLS caller.
2. Treat single-byte ASCII separately.
3. For a multibyte sequence, use the lead byte to select a pointer from a page table built from these arrays.
4. Read `charset2uni[trail_byte]`.
5. Return the Unicode value when non-zero, or reject the byte pair when the entry is `0x0000`.

This chunk only supplies the page data for that flow. It does not perform bounds checks, byte classification, or error returns itself.

## Risks

- Generated table corruption is the primary risk. A single wrong value changes filename conversion semantics and can make existing directory entries appear under different Unicode names.
- `0x0000` carries semantic meaning as "undefined" rather than Unicode NUL for multibyte pages. Accidentally filling or removing zero entries can make invalid byte pairs decode as valid characters or valid byte pairs fail.
- The chunk boundary splits `c2u_F1`; any reconciliation must ensure the final table has exactly 256 entries and that the following chunk continues the same initializer rather than treating it as a separate page.
- Lead-byte page coverage must match the later `page_charset2uni` table. Missing or extra page pointers can make otherwise correct arrays unreachable or can expose undefined ranges as decodable.
- CP949 overlaps EUC-KR but is not identical to strict EUC-KR. Callers using the `euc-kr` alias may depend on the kernel's historical CP949 superset behavior; replacing these mappings with stricter EUC-KR data would be a compatibility regression.
- The tables are large and repetitive, so manual review is prone to off-by-one mistakes in second-byte positions. The comments showing byte subranges are useful validation aids but are not executable checks.
