## Purpose

`init_vusb_ids.go` stores USB device match-table records that syzkaller can inject into generated virtual USB descriptors. The values are compact binary strings rather than Go structs. Each USB ID record is 17 bytes, matching `BytesPerUsbID` in `init_vusb.go`, and is later decoded into `UsbDeviceID` with little-endian `binary.Read`.

The file is generated by `tools/syz-usbgen` from kernel logs emitted after applying the USB ID extraction patch described by `docs/linux/external_fuzzing_usb.md`. The generator emits a deterministic Go map from driver name to concatenated binary records. This lets syzkaller bias generated USB descriptors toward IDs that Linux USB drivers actually match.

## Control Flow and Consumers

This chunk has no local control flow. Its behavior comes from consumers in `sys/linux/init_vusb.go`:

- `generateUsbDeviceDescriptor` calls `patchUsbDeviceID(..., usbIdsAll, true)` to patch a generic generated USB descriptor with one random ID from the full concatenated ID pool. `usbIdsAll` is generated later in this same file from every `usbIds[...]` value.
- `generateUsbPrinterDeviceDescriptor` looks up `usbIds["usblp"]` for printer-class matching. That key is outside this chunk, but this chunk uses the same per-driver storage contract.
- `generateAudioDeviceDescriptor` builds a pool from sound-driver keys such as `snd-usb-audio`; those keys are outside this chunk, but again rely on the same map shape.
- `patchUsbDeviceID` decodes one selected 17-byte record with `randUsbDeviceID`, then patches `idVendor`, `idProduct`, `bcdDevice`, device class fields, and per-interface class/protocol/number fields in the generated descriptor according to the record's match flags.

The generator-side flow in `tools/syz-usbgen/usbgen.go` is:

1. Read a syslog file.
2. Extract `USBID: <34 hex chars> (<driver>)` matches into a driver-to-ID map.
3. Sort driver names and per-driver IDs.
4. Emit the `usbIds` map and then an all-IDs concatenation variable.

## Dependencies and Integration Points

Direct compile-time dependencies are minimal because this chunk imports nothing and references no symbols outside its own map literal. Its effective dependencies are:

- `init_vusb.go` for the `UsbDeviceID` binary layout, `BytesPerUsbID == 17`, random ID selection, and descriptor patching logic.
- `tools/syz-usbgen/usbgen.go` for the exact generation format, deterministic sorting, and 34-hex-character USB ID extraction.
- `docs/linux/external_fuzzing_usb.md` for the workflow that explains why USB IDs are extracted rather than manually maintained.
- Linux kernel USB driver match tables and extraction logs, which determine the driver names and records present here.

The map keys must remain stable because consumers and generated `usbIdsAll` refer to exact string keys. The binary value lengths must remain multiples of 17 or `randUsbDeviceID` can select misaligned records and decode invalid data.

## Risks

- Generated-data drift: editing this file by hand can conflict with the generator and with `usbIdsAll`, which is emitted later from sorted map keys.
- Binary layout coupling: the strings are tightly coupled to `UsbDeviceID` field order and little-endian decoding. Any struct layout or `BytesPerUsbID` change requires regenerating or migrating every record.
- Silent descriptor quality loss: malformed match flags or swapped bytes may still compile but cause syzkaller to generate descriptors that no longer bind to the intended Linux driver.
- Key-name sensitivity: driver lookups are plain map key strings. Renaming an entry without matching generator and consumer expectations removes it from targeted pools.
- Partial chunk boundary: line 3658 stops during the `mt76x2u` entry, so this chunk alone cannot validate the full map literal or the later all-ID concatenation.
- Large static initializer cost: the file is a large package-level map of binary strings. It is acceptable for generated syzkaller target data, but it increases source size and package initialization data.
