## Purpose

- Implement the hot execution loop behind `sqlite3_step()` for compiled SQL bytecode.
- Translate VDBE opcodes into operations on `Mem` registers, `VdbeCursor` objects, btree cursors, sorters, rowsets, database schemas, savepoints, and connection-level transaction state.
- Preserve SQLite's dynamic type semantics by applying affinity, numeric conversion, collation, NULL logic, row record serialization, and strict-table checks at opcode execution time.
- Bridge generated bytecode from the parser/planner to lower layers such as btree, pager-backed transactions, sorter, schema initialization, update/preupdate hooks, foreign-key checks, and integrity checking.
- Serve as a documentation source: comments beginning with `Opcode:` and lines beginning with `case OP_` are scanned by SQLite build scripts to generate opcode tables and opcode documentation, so formatting is part of the module contract.

## Important APIs, Types, And Functions

- `sqlite3VdbeExec(Vdbe *p)` is the central interpreter. It initializes local copies of `p->aOp`, `p->aMem`, `p->db`, counters, tracing/profile state, then executes a large `switch(pOp->opcode)` loop until it returns `SQLITE_ROW`, `SQLITE_DONE`, `SQLITE_ERROR`, `SQLITE_BUSY`, or another propagated error state through shared exit labels.
- `allocateCursor(Vdbe *p, int iCur, int nField, u8 eCurType)` allocates or reuses the `VdbeCursor` storage for cursor `iCur` inside reserved `Mem` cells. It supports btree cursors by appending a `BtCursor` allocation after `SZ_VDBECURSOR(nField)` and zeroing it with `sqlite3BtreeCursorZero()`.
- `applyNumericAffinity()`, `applyAffinity()`, `alsoAnInt()`, `computeNumericType()`, and `numericType()` implement SQLite's runtime type-affinity conversion rules. They convert string/blob-looking numeric values into integer or real representations where possible, invalidate non-canonical string representations after numeric conversion, and support comparison/arithmetic without necessarily changing `Mem.flags`.
- `sqlite3_value_numeric_type()` and `sqlite3ValueApplyAffinity()` are exported wrappers over internal `Mem` affinity logic for `sqlite3_value *` callers.
- Debug/test helpers include `memAboutToChange`, `sqlite3VdbeMemPrettyPrint()`, `memTracePrint()`, `registerTrace()`, `sqlite3PrintMem()`, `sqlite3VdbeRegisterDump()`, `checkSavepointCount()`, and coverage macro plumbing through `VdbeBranchTaken()`/`vdbeTakeBranch()`.
- Test-only globals `sqlite3_search_count`, `sqlite3_interrupt_count`, `sqlite3_sort_count`, `sqlite3_max_blobsize`, and `sqlite3_found_count` expose interpreter behavior to SQLite's Tcl/TH3 test suites.
- `vdbeColumnFromOverflow()` handles the slow `OP_Column` path when a column payload extends onto overflow pages. It may cache large table TEXT/BLOB values in a `VdbeTxtBlbCache` backed by reference-counted strings to avoid rereading the same large value.
- `vdbeIndexKeyCompare()` compares a `Mem` blob against the current btree index payload and is used by `OP_IdxDelete` to avoid deleting/reinserting identical index keys during updates.
- `sqlite3VdbeLogAbort()` formats statement-abort log messages with trigger context when `OP_Halt` raises an error.
- `out2Prerelease()` and `out2PrereleaseWithClear()` prepare output register P2 for common integer-producing opcodes while avoiding unnecessary destructor work for non-dynamic cells.
- `filterHash()` computes a simple register hash for Bloom-filter opcodes referenced by this chunk's `OP_Once` comments; the actual Bloom opcodes are outside or later in the file.

## Control Flow

`sqlite3VdbeExec()` assumes `p->eVdbeState==VDBE_RUN_STATE`, enters required btree mutexes when `p->lockMask` is non-empty, initializes progress-callback limits, resets statement-local state such as `p->rc`, `p->iCurrentTime`, and `db->busyHandler.nBusy`, then begins the dispatch loop at `p->pc`. In debug/profiling builds each opcode can be printed, timed, counted, and checked for valid input/output register use according to `sqlite3OpcodeProperty`.

The dispatch loop uses many local labels instead of structured helper calls because this path is extremely hot. `jump_to_p2`, `jump_to_p2_and_check_for_interrupt`, and `check_for_interrupt` centralize PC update, interrupt polling, and progress-callback invocation for loop backedges. Opcode handlers generally mutate `pOp` to `&aOp[target-1]`; the loop increment then advances to the target instruction.

Control-flow opcodes operate either on raw bytecode addresses or registers containing saved addresses. Coroutines store the previous PC in a register and bounce between `OP_Yield`, `OP_EndCoroutine`, and `OP_InitCoroutine`. Subroutine support uses `OP_BeginSubrtn` to seed a NULL return register, `OP_Gosub` to store the caller PC, and `OP_Return` to either fall through for inline entry or jump back through the saved address.

`OP_Halt` is the main exit opcode. It can unwind a trigger subprogram frame back to its parent, apply `OE_Ignore` jumps from triggers, format constraint errors from P4/P5 or a register, log aborts, call `sqlite3VdbeHalt()`, and map internal halt state to the public `sqlite3_step()` return code. `OP_ResultRow` sets `p->pResultRow`, stores the resume PC, invokes row tracing, and returns `SQLITE_ROW` without halting the VM.

Comparison opcodes keep `iCompare` as interpreter-local state. Scalar comparison opcodes save the last result for `OP_ElseEq`, while vector `OP_Compare` is required to be followed by `OP_Jump`, which chooses P1/P2/P3 based on the saved comparison result. Branch coverage calls mark whether jumps are taken, not taken, or NULL-driven.

Btree seek opcodes funnel through shared table/index logic. Table seeks coerce the key register toward integer rowid semantics, including special handling for real values that round above or below the actual search term. Index seeks build an `UnpackedRecord` from registers and `KeyInfo`, honor `BTREE_SEEK_EQ` hints, and may skip a following `IdxLT`/`IdxGT` when equality has already been proven. Iteration opcodes share `next_tail`, which updates cursor cache state, statement counters, and interrupt/progress polling.

## State And Persistence Behavior

- The interpreter's primary mutable state is the `Vdbe` object: program counter, memory register array, cursor array, result row pointer, change counter, frame stack, statement status counters, return code, error action, and flags such as `expired`, `usesStmtJournal`, and `minWriteFileFormat`.
- `Mem` cells carry value type flags, dynamic ownership flags, encodings, zero-blob metadata, subtype metadata, rowset storage, and debug shallow-copy provenance. Many opcodes intentionally preserve or restore `Mem.flags` after temporary affinity conversion to avoid changing SQL-visible type behavior.
- Cursor state lives in `VdbeCursor`: cursor type, `BtCursor` or sorter backing, `nullRow`, `deferredMoveto`, `movetoTarget`, `cacheStatus`, column header offsets/types, `seekResult`, `seekHit`, `seqCount`, key info, ephemeral flags, and alternate cursor mappings used by deferred table seeks.
- `OP_Column` caches record header parsing in `pC->aType`, `pC->aOffset`, `pC->nHdrParsed`, and `pC->iHdrOffset`, and invalidates that cache through `p->cacheCtr`, `pC->cacheStatus`, and `colCacheCtr` after row/index writes.
- Transaction opcodes mutate connection and btree state: `db->autoCommit`, `db->pSavepoint`, `db->nSavepoint`, `db->isTransactionSavepoint`, `db->nStatement`, deferred foreign-key counters, btree transaction state, statement journals, schema cookies, schema generation values, and schema-change flags.
- Write opcodes call `sqlite3VdbeIncrWriteCounter()` and lower-level btree APIs that persist data to the relevant database or temp btree. `OP_Insert`, `OP_Delete`, `OP_IdxInsert`, `OP_IdxDelete`, `OP_Clear`, `OP_Destroy`, and `OP_CreateBtree` are the main persistent mutation sites in this chunk.
- Ephemeral state is also important. `OP_OpenEphemeral` creates transient btrees with `BTREE_OMIT_JOURNAL | BTREE_SINGLE`; `OP_SorterOpen` creates sorter state; `OP_RowSet*` stores a rowset in a `Mem` blob; `OP_OpenPseudo` aliases a record register as a one-row cursor; `OP_ResetSorter` clears sorter/ephemeral contents.
- Hook behavior is persistent outside the current opcode. `OP_Insert` and `OP_Delete` invoke preupdate and update callbacks when configured, update `p->nChange`, and may set `db->lastRowid`.
- Schema opcodes update both on-disk btree metadata and in-memory schema objects. `OP_SetCookie` writes btree meta and adjusts `Schema.schema_cookie` or `file_format`; `OP_ParseSchema` can clear/reload schema state; `OP_Drop*` unlink in-memory schema objects after btree destruction.
- `OP_NewRowid` persists no row by itself, but it chooses rowids based on current btree contents, AUTOINCREMENT high-water registers in the root frame, and random fallback after `MAX_ROWID`.

## Risks And Edge Cases

- `vdbe.c` is performance-critical and format-sensitive. Adding helper calls or changing case/comment formatting can regress interpreter speed or break opcode generation/documentation scripts.
- Shallow-copy handling is fragile. `OP_SCopy` creates ephemeral aliases, while `OP_Copy`, `OP_Move`, `Deephemeralize()`, and `memAboutToChange()` enforce or debug lifetime rules. Mutating a source register while an `MEM_Ephem` alias is live can produce use-after-free or stale-value bugs.
- Affinity conversions intentionally differ by opcode. Some conversions are persistent (`OP_Affinity`, `OP_TypeCheck`, comparison operands under documented conditions), while others restore original flags after computing comparison values. Small changes can alter SQL type, sort, equality, or STRICT-table behavior.
- Integer/real boundary behavior is carefully encoded. Arithmetic falls back to floating point on overflow; divide/remainder by zero return NULL; rowid seeks adjust operator semantics when real-to-integer approximation is above or below the real key; `MEM_IntReal` preserves integer precision for REAL-affinity storage where possible.
- Record parsing must defend against corrupt databases without over-allocating. `OP_Column` checks header length, payload size, offset overflow, short local payload, and missing columns, but also intentionally tolerates some historical malformed record shapes such as zero header size.
- Large TEXT/BLOB reads from overflow pages have a caching optimization only for table btrees and sufficiently large values. Incorrect cache invalidation through `cacheStatus`, `colCacheCtr`, cursor movement, or writes could return stale content.
- Transaction/savepoint paths must keep btree savepoints, virtual table savepoints, connection savepoint lists, deferred constraint counters, autocommit state, and statement journals synchronized. Error or busy paths often restore the program counter and state for retry.
- Schema-cookie checks in `OP_Transaction` intentionally expire statements and may avoid schema reset if only in-memory generation changed. Virtual table reentrancy makes this behavior subtle.
- `OP_OpenEphemeral` may reuse an existing ephemeral cursor unless `noReuse` is set by `OP_OpenDup`. Duplicate cursors on materialized views depend on this no-reuse protocol to avoid clearing a table still used by another cursor.
- `OP_Insert` and `OP_Delete` have multiple flags with different operand fields (`P5` for insert flags, `P2` and `P5` split for delete flags). Confusing `OPFLAG_NCHANGE`, `OPFLAG_ISNOOP`, `OPFLAG_ISUPDATE`, `OPFLAG_AUXDELETE`, or `OPFLAG_SAVEPOSITION` can break hooks, change counts, or cursor stability.
- `OP_IdxDelete` treats missing index entries as corruption unless writable-schema mode is enabled, but also has a bypass for identical replacement keys. This path is sensitive for UPDATE statements on indexes, expression indexes, and corruption diagnostics.
- `OP_SeekScan`, `OP_SeekHit`, and `OP_IfNoHope` are optimizations whose correctness relies on falling back to normal seek behavior when uncertain. Bugs here may show up only with multi-column indexes and `IN` constraints.
- `OP_Destroy` rejects table/index drops when other reader VMs are active to avoid root-page move hazards under autovacuum. Relaxing this can leave existing cursors pointing at moved root pages.
- `OP_SqlExec` and `OP_ParseSchema` are reentrant: they call `sqlite3_exec()` while the outer VM is running. They must preserve auth/trace/analysis-limit state and `db->init.busy` correctly across errors.
- `OP_IntegrityCk` and `OP_IFindKey` are diagnostic but have correctness implications for distinguishing true corruption from expression-index floating point drift.
