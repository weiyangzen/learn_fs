# sources/user-network-fs/samba/source4/torture/basic/cxd_known.h lines 7291-8229

## Scope

This chunk covers one contiguous slice of Samba's generated/recorded `cxd_known[]` baseline table for the `source4/torture/basic/denytest.c` CreateX torture tests. The range is entirely data: 939 `struct createx_data` initializers, all with `cxd_test = 2` (`CXD_TEST_CREATEX_SHAREMODE`) and `cxd_flags = 0x1` (`CXD_FLAGS_DIRECTORY`).

The rows describe expected Windows XP SP2 behavior for SMB NT CreateX directory opens when two clients open the same directory with selected access masks and share modes. This chunk starts in the middle of the share-mode matrix at `cxd_sharemode1=5, cxd_sharemode2=2` and continues through `cxd_sharemode1=7, cxd_sharemode2=1`; later chunks continue the table.

## Purpose

The table is a regression oracle for CreateX directory share-mode compatibility. Each row encodes:

- the first open's desired access (`cxd_access1`) and share access (`cxd_sharemode1`);
- the second open's desired access (`cxd_access2`) and share access (`cxd_sharemode2`);
- the expected result vector for operations performed on the first handle (`cxd_result`);
- the expected result vector for operations performed on the second handle (`cxd_result2`).

For directory tests, the four result slots are interpreted as `CXD_CREATEX`, `CXD_DIR_ENUMERATE`, `CXD_DIR_CREATE_CHILD`, and `CXD_DIR_TRAVERSE`. In this slice every recorded status in both result arrays is `NT_STATUS_OK`, so the chunk is asserting that these directory opens, enumerations, child-creation checks, and traversal checks should all succeed for the covered combinations.

The access-mask values are the eight grouped access masks generated by `denytest.c` from the three `sec_access_bit_groups[]` elements:

- `0`: no grouped file access bits.
- `0x120089`: `SEC_RIGHTS_FILE_READ`.
- `0x120116`: `SEC_RIGHTS_FILE_WRITE`.
- `0x12019f`: read plus write.
- `0x1200a0`: `SEC_RIGHTS_FILE_EXECUTE`.
- `0x1200a9`: read plus execute.
- `0x1201b6`: write plus execute.
- `0x1201bf`: read plus write plus execute.

The share-mode values are raw NT CreateX share-access bitmasks over the three share bits documented in the code comment as `NTCREATEX_SHARE_ACCESS_{NONE,READ,WRITE,DELETE}`. Values `5`, `6`, and `7` for the first open are permissive combinations that include delete sharing in addition to read and/or write sharing; values `0` through `7` appear for the second open.

## Important APIs, Types, And Functions

The important type is `struct createx_data` from the top of `cxd_known.h`. Its input fields are `cxd_test`, `cxd_flags`, `cxd_access1`, `cxd_sharemode1`, `cxd_access2`, and `cxd_sharemode2`; its output fields are two `NTSTATUS cxd_result[CXD_MAX]` arrays. For `CXD_TEST_CREATEX_SHAREMODE`, both arrays are meaningful because the test opens the target twice, once through `cli` and once through `cli2`.

The enum values that make this slice meaningful are:

- `CXD_TEST_CREATEX_SHAREMODE = 2`, selecting the two-open share-mode test.
- `CXD_FLAGS_DIRECTORY = 0x1`, selecting directory-specific setup, open parameters, and post-open probes.
- `CXD_CREATEX = 0`, `CXD_DIR_ENUMERATE = 1`, `CXD_DIR_CREATE_CHILD = 2`, and `CXD_DIR_TRAVERSE = 3`, naming the result-vector slots for directory cases.

The consuming functions live in `source4/torture/basic/denytest.c`:

- `CXD_MATCHES()` compares a runtime `struct createx_data` against `cxd_known[]` by exact tuple match on the six input fields.
- `cxd_find_known()` finds the matching row. It has an optimization for sequential table order and deliberately returns `-1` for exhaustive/extended tests that do not have saved results.
- `createx_fill_dir()` builds an `RAW_OPEN_NTCREATEX` request for directory targets, setting `access_mask`, `share_access`, `NTCREATEX_DISP_OPEN_IF`, and `NTCREATEX_OPTIONS_DIRECTORY`.
- `createx_test_dir()` performs the directory post-open probes that populate `cxd_result[1..3]`: it creates a known child by absolute path, treats enumeration as OK, attempts child creation relative to the open directory handle, and attempts traversal to the known child through the directory handle.
- `torture_createx_specific()` executes the row's scenario, records actual statuses, looks up `cxd_known[]`, and compares each actual status to the expected table entry.
- `torture_createx_sharemodes()` generates the same row order by iterating all 8 first share modes, all 8 second share modes, and all 8 grouped access combinations for each open.
- `torture_createx_sharemodes_dir()` calls the generator with `dir=true` and `extended=false`, which is the harness path represented by this chunk.

## Control Flow

The runtime generator initializes `cxd.cxd_test` to `CXD_TEST_CREATEX_SHAREMODE` and `cxd.cxd_flags` to `CXD_FLAGS_DIRECTORY` for directory share-mode testing. It removes any previous `\\createx_dir` directory/file, then enters nested loops:

1. Iterate `cxd_sharemode1` from `0` to `7`.
2. Iterate `cxd_sharemode2` from `0` to `7`.
3. Iterate `gp1` and `gp2` from `0` to `7`.
4. Build `cxd_access1` and `cxd_access2` as combinations of read, write, and execute access groups.
5. Call `torture_createx_specific()` for each tuple.

For a row in this chunk, `torture_createx_specific()` selects the directory helpers because `CXD_FLAGS_DIRECTORY` is set. It optionally skips SACL-related tests, but this chunk contains no `SEC_FLAG_SYSTEM_SECURITY` rows. It fills the first NT CreateX request from `cxd_access1`/`cxd_sharemode1` and the second from `cxd_access2`/`cxd_sharemode2`.

The first open is issued through `smb_raw_open(cli->tree, ...)`; if that succeeds, `createx_test_dir()` populates the first result vector and the handle is closed. The second open is issued through `cli2`; if that succeeds, the same directory probes populate `cxd_result2`. With no `CREATEX_DATA` output file configured, the actual tuple is matched against `cxd_known[]`, and all four status slots in both arrays are compared to the saved expected row. Any missing row or mismatch causes the current row to be printed in table-initializer format so maintainers can inspect or update the baseline.

## State And Persistence Behavior

The header itself has no runtime state, storage, allocation, or side effects. It is a compile-time static constant table included into `denytest.c`.

The consuming test mutates only test-share state. It uses `\\createx_dir` as the target directory, creates and removes child entries named `known` and `child`, closes any opened SMB file numbers, and destroys the target path with either `smbcli_rmdir()` for directory cases or `smbcli_unlink()` for file cases. Before the share-mode matrix begins, `torture_createx_sharemodes()` removes both possible stale forms of `\\createx_dir`.

There is one persistence-related alternate path outside this header: if the `CREATEX_DATA` environment variable is used in the exhaustive access test path, `torture_createx_specific()` can write binary `struct createx_data` records to a local file descriptor. That path is not used for the normal known-table comparison represented by this chunk, and `cxd_find_known()` intentionally bypasses saved lookup for `CXD_TEST_CREATEX_SHAREMODE_EXTENDED`.

## Dependencies And Integration Points

This table depends on Samba's NT status constants, SMB raw client interfaces, and security/access-mask definitions. It is not useful by itself; it is integrated by textual inclusion into `source4/torture/basic/denytest.c`.

External protocol dependencies exercised by the rows include:

- SMB1 NT CreateX open semantics through `RAW_OPEN_NTCREATEX`.
- Directory open options (`FILE_ATTRIBUTE_DIRECTORY`, `NTCREATEX_OPTIONS_DIRECTORY`).
- Share-access compatibility between two separate SMB client states (`cli` and `cli2`).
- Directory-relative child creation and traversal using `root_fid`.
- Status-code comparison through Samba's `NTSTATUS` helpers and torture macros.

The baseline comment at the top of `cxd_known.h` says the known results were taken from Windows XP Professional 2002 SP2. This makes the table an interoperability target rather than a derivation from Samba's own implementation. A server behavior change can therefore be a real regression even when it looks internally consistent with Samba code.

## Risks And Maintenance Notes

- The chunk is generated-looking and order-sensitive. `cxd_find_known()` first tries the next table row as a performance shortcut, so preserving generator order keeps large test runs efficient. Reordering rows should still be semantically correct because of the fallback search, but it can slow the test substantially.
- The requested range starts and ends mid-matrix. Interpreting this chunk alone without adjacent chunks can make the share-mode coverage look irregular; that irregularity is a chunking artifact, not a protocol rule.
- Every row in this slice expects full success. A single typo in an access mask, share mode, or status vector would silently change the regression oracle for one tuple and could either hide a server regression or create a false failure.
- The table keys are raw numeric values rather than named access/share constants. That keeps the generated initializer compact but makes review harder; maintainers need to map `0x120089`, `0x120116`, and related masks back to the grouped read/write/execute sets in `denytest.c`.
- The results are based on Windows XP SP2. Modern Windows servers or Samba's desired compatibility target may differ for edge cases, but changing the baseline should be deliberate and supported by fresh cross-server evidence.
- Directory probes are not pure share-mode checks. A failing row may reflect open conflict, access-mask interpretation, relative create/traverse behavior, cleanup problems, or environmental issues on the share.
- The test path is shared and fixed (`\\createx_dir`). Parallel runs against the same share can interfere unless isolated at the harness level.
