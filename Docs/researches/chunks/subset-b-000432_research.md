## State And Persistence Behavior

The persistent Kubernetes state is the custom resource object stored in etcd. The schema divides user-owned desired state under `spec` from controller-owned observed state under `status`.

Several fields model persistent Ceph-side state. `CephFilesystemSubVolumeGroup.spec.filesystemName`, `spec.name`, `spec.clusterID`, and `spec.csiMetadataRadosNamespace` are immutable because changing them after creation would point the same Kubernetes object at a different CephFS/CSI identity. `CephObjectStoreAccount.spec.accountID`, `spec.name`, and `spec.store` are similarly immutable for RGW account identity. `CephNVMeOFGateway.spec.pool` persists the RADOS pool that stores gateway configuration. `CephNFS.spec.rados.pool` and `namespace` are deprecated because Rook now internally controls persistent Ganesha config placement.

Status fields persist controller observations. `observedGeneration` connects status to the latest reconciled spec generation. `phase` and `conditions` persist high-level state and transition history. CephX status (`keyCephVersion`, `keyGeneration`) persists key-management progress for daemon credentials. Filesystem mirroring and snapshot status persist monitoring snapshots of Ceph-side state, including error details and last checked/changed times.

Several schemas preserve unknown fields, especially status and parameter maps. This is intentional for compatibility with controller-written status extensions, arbitrary Ceph pool parameters, and metadata maps, but it weakens strict pruning for those sections.

## Risks And Edge Cases

This chunk begins and ends inside larger CRD definitions. Any analysis or change to `CephFilesystem` or `CephObjectStore` must reconcile neighboring chunks before drawing whole-resource conclusions.

Immutable fields are admission-critical. If CEL rules for subvolume group identity or object-store account identity are loosened, users could mutate CRs in ways that leave old Ceph resources, CSI metadata, secrets, or RGW accounts orphaned or mismatched. If they are tightened incorrectly, upgrades may reject previously valid objects.

The subvolume-group pinning rule permits exactly one of `export`, `distributed`, or `random`, or none. Since the fields are nullable, clients and generated YAML can differ between absent and explicit null; tests should cover all three valid strategies and mixed invalid combinations.

Several status and parameter maps preserve unknown fields. This helps backward/forward compatibility but allows misspelled or unexpected keys to survive. Controllers must still validate or ignore unknown Ceph parameters safely.

`CephNFS.spec.rados.pool` and `namespace` are deprecated but still accepted. Removal or behavior changes can break existing manifests even though Rook now internally fixes values to `.nfs` and the CR name.

Kerberos, SSSD, RGW additional volume mounts, and gateway extra mounts accept broad Kubernetes volume sources, including hostPath and projected sources. This is powerful but security-sensitive; admission policies outside this CRD may need to restrict host paths, service account token projection, or secret references in multi-tenant clusters.

The `CephNFS.server.image` max length is very large (`1572864`) compared with typical image fields. This may be intentional to allow config payloads in related generated types, but it is unusual for a container image string and worth checking against the Go type markers if validating API quality.

Embedded Kubernetes schemas are large and easy to drift from the Kubernetes version Rook targets. Fields such as `podCertificate`, `clusterTrustBundle`, `matchLabelKeys`, `mismatchLabelKeys`, and Dynamic Resource Allocation `claims` depend on Kubernetes feature availability. Clusters with older API servers may reject CRDs containing unsupported schema constructs or users may set fields the workload controller cannot honor.

NVMe-oF ports are individually range-validated, but the schema does not enforce uniqueness among `discoveryPort`, `gatewayPort`, `ioPort`, and `monitorPort`. Controller-side validation should catch conflicting ports if they would create unusable Services or pods.

`CephObjectStore.spec.defaultRealm` is documented as mutually incompatible with `zone`, but this chunk does not show a CEL rule enforcing that relationship. If the full CRD also lacks one, controller-side validation must enforce the invariant.

`CephObjectStore.spec.allowUsersInNamespaces` supports `*`, which is operationally convenient but broadens credential creation authority. RBAC and controller logic must ensure this does not let arbitrary namespaces create credentials for stores they should not control.

Because this file is generated by controller-gen, manual edits in `deploy/examples/crds.yaml` can mask missing kubebuilder markers in the source API types. Regeneration and diff checks are the main guard against skew.
