# sources/distributed-fs/ceph-client/crypto/testmgr.h lines 27106-33814

## Purpose
This chunk is a data-only portion of the Linux kernel crypto self-test manager header. It supplies known-answer test vectors consumed by `crypto/testmgr.c` for block-cipher, stream-cipher, AEAD, and wide-block encryption algorithms. The assigned lines begin inside `aria_cbc_tv_template[]`, then cover complete ARIA CTR/GCM tables, ChaCha20 and XChaCha stream-cipher tables, XChaCha12-derived tables, complete Adiantum-XChaCha12-AES vectors, and the beginning of the Adiantum-XChaCha20-AES table.

The vectors are static `const` templates. They do not implement cryptography themselves; they define byte-for-byte expected behavior for registered crypto algorithms.

- `struct aead_testvec`: used by ARIA GCM. Fields used here are `.key`, `.klen`, `.iv`, `.assoc`, `.alen`, `.ptext`, `.plen`, `.ctext`, and `.clen`.
- `aria_cbc_tv_template[]`: the chunk starts at the IV of a 48-byte ARIA-CBC case and continues through the end of the CBC table, covering 16/24/32-byte keys and plaintext lengths from 48 through 160 bytes in this slice.
- `aria_ctr_tv_template[]`: complete ARIA-CTR table with 16/24/32-byte keys and 16-byte IV/counter inputs, covering lengths 16 through 160 bytes.
- `aria_gcm_tv_template[]`: two ARIA-GCM AEAD vectors with 16-byte keys, 12-byte IVs, 12 bytes of associated data, 160-byte plaintexts, and 176-byte ciphertext outputs including the authentication tag.
- `chacha20_tv_template[]`: RFC7539-derived ChaCha20 vectors plus a long self-made vector, all using 32-byte keys and 16-byte IV layout as expected by the kernel implementation.

## Control Flow
There is no runtime control flow in this header section. At build time, the compiler places these static tables into the kernel image. At test time, `testmgr` selects vectors through the algorithm descriptor tables elsewhere in `testmgr.h`, allocates a transform for the registered algorithm name, calls setkey with `.key`/`.klen`, feeds `.iv`, plaintext, ciphertext, and associated data into the cipher or AEAD request path, and compares implementation output against the expected bytes here.

For symmetric ciphers, the effective flow is:
1. Encrypt `.ptext` with `.key`, `.iv`, and `.len`, then compare with `.ctext`.
2. Decrypt `.ctext` with the same key/IV and compare with `.ptext`.
3. Reuse the vectors across normal, in-place, out-of-place, and chunked request variants generated by the test manager.

For ARIA-GCM, the test flow additionally authenticates `.assoc` and treats `.clen` as ciphertext plus tag length, so failures can indicate either encryption mismatch or authentication-tag generation/verification mismatch.

## State And Persistence Behavior
The only persistent state in this slice is immutable compiled-in test data. The tables do not mutate global state, allocate memory, hold references, or persist runtime results. Runtime state is owned by the crypto API test harness and by each algorithm implementation under test.

The most important state encoded by the data is cryptographic context shape:
- ARIA coverage uses 128/192/256-bit keys and exercises CBC, CTR, and GCM mode handling.
- ChaCha/XChaCha coverage uses 256-bit keys and IV/counter encodings that check both standard ChaCha20 and extended-nonce HChaCha-derived setup.
- Adiantum coverage uses 256-bit keys and large wide-block plaintexts, stressing tweak handling and whole-sector style transformations.

## Integration Points
- Algorithm registration self-tests use these tables to accept or reject crypto providers during module load or kernel initialization.
- ARIA CBC/CTR/GCM vectors integrate with block-mode and AEAD template testing.
- ChaCha20, XChaCha20, and XChaCha12 vectors integrate with stream-cipher implementations, including extended nonce and counter-layout handling.
- Adiantum vectors integrate with filesystem/storage encryption use cases that need wide-block encryption over sector-sized buffers.

## Risks
- The chunk boundary starts mid-vector for `aria_cbc_tv_template[]`; any reconciliation must merge with the previous chunk to understand the first covered CBC test case's `.key` and `.klen`.
- The chunk boundary ends mid-vector in `adiantum_xchacha20_aes_tv_template[]`; the final 4096-byte vector is incomplete here and must be reconciled with the next chunk.
- These are byte-exact known-answer tests. A one-byte edit, missing string fragment, wrong `.len`, or mismatched `.plen`/`.clen` silently changes the expected cryptographic contract.
- IV layouts are algorithm-specific. ChaCha20 and XChaCha vectors encode counter/nonce material in the kernel's expected layout, so reformatting them to a spec's presentation layout would break tests.
- The AEAD GCM vectors include authentication tags in `.ctext`/`.clen`; treating `.clen` as only encrypted plaintext length would mis-test tag generation.
- Large inline string literals are hard to review manually and vulnerable to accidental truncation during conflict resolution or automated formatting.
