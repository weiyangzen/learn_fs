# sources/user-network-fs/samba/source4/torture/basic/cxd_known.h lines 2770-3624

## Scope

This chunk is a middle slice of the static `cxd_known[]` Windows-baseline result table used by Samba's `BASE-CREATEX_*` torture tests. The requested range contains 855 initializer rows, all for `CXD_TEST_CREATEX_SHAREMODE` (`.cxd_test = 2`) with normal file testing (`.cxd_flags = 0`). It does not define executable code, but it is executable test data: `source4/torture/basic/denytest.c` searches these rows and compares live SMB `NTCreateX` behavior against them.

The rows cover file share-mode permutations from the tail of first-open share mode `4`, through all first-open share mode `5`, and into first-open share mode `6`:

- share mode `4` is `NTCREATEX_SHARE_ACCESS_DELETE`, with second-open share modes `3` through `7` partially or completely represented in this chunk.
- share mode `5` is `NTCREATEX_SHARE_ACCESS_READ | NTCREATEX_SHARE_ACCESS_DELETE`, with second-open share modes `0` through `7` completely represented.
- share mode `6` is `NTCREATEX_SHARE_ACCESS_WRITE | NTCREATEX_SHARE_ACCESS_DELETE`, with second-open share mode `0` complete and second-open share mode `1` beginning.

The share-access bit values come from `source4/libcli/raw/smb.h`: none `0`, read `1`, write `2`, delete `4`; the table stores the OR-combinations directly.

## Purpose

The data records Windows XP Professional SP2 behavior for two sequential `NTCreateX` opens on the same file under combinations of requested file access and share access. Samba's torture runner uses the table as an oracle for ordinary `BASE-CREATEX_SHAREMODE` file tests. If a server's first open, subsequent file operations, second open, or second-handle file operations return a different `NTSTATUS`, the torture test reports a regression and prints a replacement table row.

This particular chunk emphasizes cases where delete sharing participates in the first open. Delete sharing is subtle because it allows or blocks later opens depending on the requested access mask, and the table distinguishes not only whether each open succeeds but also whether read, write, and execute-style follow-up operations on the returned handle succeed.

## Important APIs, Types, And Data Fields

The local type definitions appear earlier in the same header:

- `enum cxd_test` defines `CXD_TEST_CREATEX_SHAREMODE = 2`, the only test class present in this chunk.
- `enum cxd_flags` defines `CXD_FLAGS_DIRECTORY = 0x1` and `CXD_FLAGS_MAKE_BEFORE_CREATEX = 0x2`; every row here has flags `0`, so the tested object is a file and it is not pre-created by a special flag path.
- `struct createx_data` is both the generated-input record and expected-output record. The fields used here are `cxd_access1`, `cxd_sharemode1`, `cxd_access2`, `cxd_sharemode2`, `cxd_result[CXD_MAX]`, and `cxd_result2[CXD_MAX]`.
- `CXD_MAX` indexes four result positions: `CXD_CREATEX`, `CXD_FILE_READ`, `CXD_FILE_WRITE`, and `CXD_FILE_EXECUTE` for file tests. Directory aliases exist for the same indexes, but they are not active because `.cxd_flags = 0`.

All rows use the eight grouped access masks generated by `denytest.c` from `SEC_RIGHTS_FILE_READ`, `SEC_RIGHTS_FILE_WRITE`, and `SEC_RIGHTS_FILE_EXECUTE`:

- `0`
- `0x120089`
- `0x120116`
- `0x12019f`
- `0x1200a0`
- `0x1200a9`
- `0x1201b6`
- `0x1201bf`

Each row stores two expected status arrays. `cxd_result` applies to the first open and its follow-up operations on the first client connection. `cxd_result2` applies to the second open and follow-up operations on the second client connection.

The range contains complete 8-by-8 access-mask grids for most represented `(sharemode1, sharemode2)` pairs, plus partial grids at the chunk boundaries:

- `4:3` has 9 rows, because the previous chunk contains the beginning of this pair.
- `4:4`, `4:5`, `4:6`, `4:7` each have 64 rows.
- `5:0` through `5:7` each have 64 rows.
- `6:0` has 64 rows.
- `6:1` has 14 rows, with the remaining rows continuing in the next chunk.

There are 216 rows where the first handle's result array is all `NT_STATUS_OK`, and 214 rows where the second handle's result array is all `NT_STATUS_OK`. Most rows contain at least one `NT_STATUS_ACCESS_DENIED`, which is expected for incompatible access/share combinations or for operations not permitted by the handle's granted access. The first-open and second-open arrays are intentionally not symmetric in all rows because the first open is established before the second open is attempted, and because operation checks run against whichever handle was successfully opened.

## Control Flow And Consumption

`denytest.c` includes this header and uses `cxd_known[]` through `cxd_find_known()`. The lookup key is exact equality on `cxd_test`, `cxd_flags`, `cxd_access1`, `cxd_sharemode1`, `cxd_access2`, and `cxd_sharemode2`. The function keeps a static index optimization that first tries the next row before falling back to a full scan, so the table order is performance-significant for the normal generated traversal.

For share-mode tests, `torture_createx_sharemodes()` iterates every share mode from `0` to `7` for both opens and every grouped access combination for both opens. It sets `cxd_test` to `CXD_TEST_CREATEX_SHAREMODE`, clears or sets `CXD_FLAGS_DIRECTORY` depending on the wrapper, and calls `torture_createx_specific()` for each case. The rows in this chunk correspond to the file wrapper, not the directory wrapper.

`torture_createx_specific()` chooses file helpers because `.cxd_flags = 0`: `createx_fill_file()` builds `RAW_OPEN_NTCREATEX` requests with the row's access and share values, and `createx_test_file()` probes the returned handle with SMB read, write, and execute-read operations. It performs the first open on `cli`, performs the second open on `cli2` for share-mode tests, fills the two result arrays, and compares each populated status against `cxd_known[res].cxd_result` and `cxd_known[res].cxd_result2`.

If `CREATEX_DATA` is set, `torture_createx_specific()` writes raw `struct createx_data` records instead of comparing against the header. Otherwise, rows from this chunk are the oracle. If no row is found or a status differs, the test prints a C initializer in this same style, which is how the table can be regenerated or extended.

## State And Persistence Behavior

The header itself has no runtime mutation; `cxd_known[]` is `static const`. Persistence is source-level: the expected Windows behavior is checked into the tree as C data. The live test state is transient and isolated under `CREATEX_NAME` (`"\\createx_dir"`): the runner removes stale test paths before the permutation loop, opens and closes handles during each row, and destroys the file path at the end of `torture_createx_specific()`.

Because `data_file_fd` can redirect execution into capture mode, this table also participates in a two-mode workflow: compare mode for ordinary regression testing and generation mode for collecting new `struct createx_data` records. This chunk should therefore be treated as generated, order-sensitive baseline data rather than hand-authored logic.

## Dependencies And Integration Points

The immediate integration points are:

- `source4/torture/basic/denytest.c`, which includes `cxd_known.h`, generates matching `struct createx_data` inputs, searches the table, compares `NTSTATUS` arrays, and prints replacement rows.
- `source4/libcli/raw/smb.h`, which defines the `NTCREATEX_SHARE_ACCESS_*` bit values represented by `cxd_sharemode1` and `cxd_sharemode2`.
- Samba raw SMB client APIs used by the consumer: `smb_raw_open()`, `smb_raw_read()`, `smb_raw_write()`, `smbcli_close()`, `smbcli_unlink()`, and `smbcli_deltree()`.
- Security/access constants such as `SEC_RIGHTS_FILE_READ`, `SEC_RIGHTS_FILE_WRITE`, and `SEC_RIGHTS_FILE_EXECUTE`, which generate the access-mask set stored here.
- `NTSTATUS` constants, mainly `NT_STATUS_OK` and `NT_STATUS_ACCESS_DENIED`, used as the expected observable protocol results.

The table is source4 torture infrastructure, but it protects behavior in Samba file-server open/share-mode handling generally. Failures against these rows can point to server-side share access checks, granted access mapping, read/write/execute permission enforcement, or client-side raw SMB request construction.

## Risks And Maintenance Notes

The main risk is accidental table corruption. A one-character change to a status, access mask, share mode, or row order can silently alter the oracle for hundreds of generated test cases. Since `cxd_find_known()` optimizes for sequential lookup, reordering is not just cosmetic; it can affect test runtime and complicate comparison with generated output.

The range begins and ends mid-matrix. Changes that add or remove rows here must be coordinated with adjacent chunks for `sharemode1=4/sharemode2=3` and `sharemode1=6/sharemode2=1`; otherwise the merged per-file analysis or regenerated table may report gaps or duplicates.

The baseline is explicitly Windows XP Pro 2002 SP2 behavior. That is useful for compatibility, but it may differ from newer Windows versions or SMB2 behavior. A test failure should therefore be triaged as a compatibility signal, not automatically as proof that a newer server behavior is wrong.

The data is compact but opaque. Numeric access masks such as `0x1201bf` are generated combinations of broader file access groups, so reviewers should consult `sec_access_bit_groups[]` in `denytest.c` rather than infer permissions from the literal hex alone.

## Test Signals

The primary test signal is the `BASE-CREATEX_SHAREMODE` file torture path, which iterates into these rows and expects exact `NTSTATUS` matches. Strong signals from this chunk include:

- The first open should always be attempted and recorded at `cxd_result[CXD_CREATEX]`.
- When the first open succeeds, follow-up read, write, and execute-read checks must match the three remaining entries in `cxd_result`.
- The second open and its follow-up operations must match `cxd_result2` for the same access/share pair.
- Rows with full `NT_STATUS_OK` arrays indicate combinations where both open and all probed operations are allowed for that handle.
- Rows with `NT_STATUS_ACCESS_DENIED` after an initial `NT_STATUS_OK` indicate a handle can be opened while a specific operation on that handle is still denied by granted access.

A regression report printed by `denytest.c` in the same initializer format can be compared directly with this chunk. For this range, expected rows should continue to have `.cxd_test = 2`, `.cxd_flags = 0`, one of the eight grouped access masks for each open, and share modes within the represented boundary ranges above.
