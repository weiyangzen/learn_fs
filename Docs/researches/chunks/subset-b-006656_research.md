## Purpose

The purpose of this chunk is to publish raw Emerald Rapids CHA uncore event encodings to perf. Users and perf metrics rely on these records to name, list, schedule, and count model-specific home-agent activity without manually writing raw event selector, unit mask, and filter values.

The covered records describe what the CHA observes while servicing cache-coherency, memory, and IO traffic:

- Requests entering the CHA from local cores, remote sockets, IO devices, and internal queues.
- LLC and snoop-filter lookup outcomes, including MESIF state filters, local/remote homing filters, demand/prefetch distinctions, and hit/miss compositions.
- Lines victimized during fills, split by state and initiator.
- Snoop traffic generated by the CHA and response types returned by remote caching agents.
- Retry and reject reasons inside CHA ingress paths, including virtual-network credit shortages, address conflicts, victim conflicts, and queue-specific back pressure.
- TOR insert classifications for local IA and IO traffic, with detailed opcode, hit/miss, homing, memory target, and CXL accelerator/expander filters.

The file does not compute metrics itself. Its job is to provide the persistent event catalog that `perf list`, `perf stat -e`, perf metric formulas, and generated PMU event tables can consume for the Emerald Rapids CPU model.

## Data Shape and Important Fields

Each record is a JSON object using the common perf PMU event schema. The important fields visible in this chunk are:

- `EventName`: the symbolic perf event name, for example `UNC_CHA_LLC_LOOKUP.DATA_RD` or `UNC_CHA_TOR_INSERTS.IA_MISS_DRD_LOCAL_DDR`.
- `EventCode`: the raw PMU event selector. Heavily repeated selectors include `0x34` for `UNC_CHA_LLC_LOOKUP`, `0x35` for `UNC_CHA_TOR_INSERTS`, `0x37` for `UNC_CHA_LLC_VICTIMS`, `0x50` for `UNC_CHA_REQUESTS`, `0x51` for `UNC_CHA_SNOOPS_SENT`, `0x5c`/`0x5d` for snoop responses, and many `0x18`-through-`0x2f` values for RxC reject/retry families.
- `UMask`: the subevent mask or extended filter encoding. Many TOR entries use wide masks such as `0xc817fe01` or `0x10c8178201`, not just small byte masks, so consumers must preserve these as full event terms.
- `Counter`: mostly `0,1,2,3`. Three records in this range use only counter `0`, so tests should not assume all CHA events can schedule on all four counters.
- `Unit`: always `CHA` in this chunk.
- `PerPkg`: always `1`, indicating package-level aggregation semantics for these uncore events.
- `BriefDescription` and `PublicDescription`: user-facing descriptions. Some records have only a brief description, so generated output must tolerate missing `PublicDescription`.
- `Experimental`: present on most records in this chunk. A parsed count over objects beginning in this range showed 424 experimental objects and 78 non-experimental or unmarked objects.
- `PortMask`: present on CXL accelerator local TOR insert variants such as `IA_HIT_CXL_ACC_LOCAL`, `IA_MISS_DRD_CXL_ACC_LOCAL`, and related local CXL expander/accelerator filters. These records combine a high-bit extended `UMask` with `PortMask: "0x000"`.

There are no functions, classes, exported symbols, or local type declarations in the file. The effective "API" is the stable schema and event-name namespace consumed by perf's PMU event generator.

## Event Family Notes

Early records describe high-level CHA behavior. `UNC_CHA_BYPASS_CHA_IMC` separates full bypass, intermediate bypass, and not-taken cases for CHA-to-iMC traffic. `UNC_CHA_CORE_SNP` splits cross-snoop issuance by source and cardinality, including core, external, remote, eviction, and any-source single/multiple snoops. `UNC_CHA_DIRECT_GO` and `UNC_CHA_DIRECT_GO_OPC` expose direct GO suppression/deallocation and opcode classes such as `GO`, `GO_PULL`, `PULL`, and `FAST_GO`.

The directory and HitMe records cover multi-socket coherency shortcuts. `UNC_CHA_DIR_LOOKUP` distinguishes lookups that did or did not require snoops; `UNC_CHA_DIR_UPDATE` distinguishes HA-pipe and TOR-pipe directory updates. `UNC_CHA_HITME_LOOKUP`, `HIT`, `MISS`, and `UPDATE` distinguish read/write accesses, E/shared/writeback cases, RdInvOwn conflicts, and allocate/deallocate behavior. These are model-specific diagnostic surfaces for remote coherency behavior.

The LLC records are the largest early family before TOR inserts. `UNC_CHA_LLC_LOOKUP` entries combine request source, request type, homing, and state filters. Several descriptions emphasize a non-standard filtering equation and the need to select state bits; if the wrong mask is supplied, a named event may count nothing or count a broader class than intended. `UNC_CHA_LLC_VICTIMS` similarly slices victimized lines by MESIF state, initiator (`IA` or `IO`), and local/remote scope.

The RxC records are a repeated matrix over queue families and reject/retry causes. The chunk has families such as `UNC_CHA_RxC_IPQ0_REJECT`, `IPQ1_REJECT`, `IRQ0_REJECT`, `IRQ1_REJECT`, `ISMQ0_REJECT`, `ISMQ0_RETRY`, `OTHER0_RETRY`, `OTHER1_RETRY`, `PRQ0_REJECT`, `PRQ1_REJECT`, `REQ_Q0_RETRY`, `REQ_Q1_RETRY`, `RRQ0_REJECT`, `RRQ1_REJECT`, `WBQ0_REJECT`, and `WBQ1_REJECT`. Their subevents repeat reason names like `AD_REQ_VN0`, `AD_RSP_VN0`, `BL_RSP_VN0`, `BL_WB_VN0`, `AK_NON_UPI`, `IV_NON_UPI`, `ANY0`, `HA`, `LLC_OR_SF_WAY`, `PA_MATCH`, `SF_VICTIM`, and `VICTIM`. This regularity is useful for validation but risky if a copied description or event code lands in the wrong queue family.

The TOR insert section starts at line 3,693 and dominates the end of the chunk. It begins with aggregates such as `ALL`, `DDR`, `EVICT`, `HIT`, `IA`, and `IO`, then expands into opcode-specific IA and IO counters. The IA section covers code reads, data reads, page-table reads, RFO, ItoM, SpecItoM, writebacks, WCiL/WCiLF/WiL, LLCPrefCode/Data/RFO, CLFlush/CLFlushOpt, local/remote homing, DDR/PMM targeting, and CXL accelerator/expander memory. ## Control Flow

There is no direct runtime control flow in this JSON file. Control flow is supplied by the perf PMU event build and lookup pipeline:

1. `tools/perf/pmu-events/arch/x86/mapfile.csv` maps `GenuineIntel-6-CF` to the `emeraldrapids` model directory.
2. During the perf build, `tools/perf/pmu-events/Build` runs `tools/perf/pmu-events/jevents.py` over architecture event directories.
3. `jevents.py` loads each JSON object with `json.load(..., object_hook=JsonEvent)` and turns fields such as `EventName`, `EventCode`, `UMask`, `Counter`, `Unit`, `PerPkg`, and extra masks into generated PMU event table entries.
4. The generated `pmu-events.c` is compiled into perf.
5. At runtime, perf selects the generated Emerald Rapids event table for matching CPUs and resolves names like `UNC_CHA_TOR_INSERTS.IA_MISS_DRD` into raw uncore PMU configuration.
6. `perf list`, `perf stat`, metric parsing, and user-selected events consume those generated descriptors.

The chunk's data therefore affects runtime behavior indirectly. An edit here changes generated event descriptors after the perf event tables are regenerated and rebuilt.

## Risks

- The range ends in the middle of `UNC_CHA_TOR_INSERTS.MMCFG`. A chunk merge must not treat this chunk as containing a standalone valid JSON subarray or a complete record for that event.
- Many records are marked `Experimental`. These may have less stable documentation or validation coverage than non-experimental records, and users may see changed behavior if Intel or perf updates the encodings.
- Some records omit `UMask` or `PublicDescription`. The generator must tolerate missing optional fields, but reviewers should distinguish intentional omissions from accidental drops.
- The LLC lookup descriptions repeatedly warn about non-standard filtering and required state bits. Incorrect masks can silently produce zero counts or misleading broad counts.
- TOR insert masks are large extended encodings. Truncating them to byte-sized unit masks, treating them as signed integers, or normalizing them incorrectly would break many IA, IO, DDR, PMM, and CXL filters.
- The RxC reject/retry matrices are highly repetitive. Copy/paste mistakes in event codes, queue names, reason names, or descriptions can be hard to spot by visual review alone.
- CXL-specific TOR records combine extended `UMask` values with `PortMask`. Dropping `PortMask` or mis-associating it with non-local variants would change the targeted CXL filter.
- Counter constraints matter. Most records use counters `0,1,2,3`, but not all records in the range do, so a blanket scheduling assumption would be wrong.
- `PerPkg: "1"` is universal in this chunk. Accidentally removing or changing it could alter aggregation semantics for package-level uncore counts.
- Event-name renames would be externally visible to users and to any metrics that reference `UNC_CHA_*` names.
