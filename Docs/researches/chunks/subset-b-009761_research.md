## Important Data Shape

The object schema is uniform and generated by `bisync_debug_test.go`'s `debugFormat` template:

- `name` encodes the backend, test case, and variation in a human-readable VS Code picker label.
- `type` selects the VS Code Go debug adapter.
- `request: "launch"` runs a new test process instead of attaching.
- `mode: "test"` tells the Go extension to invoke test mode.
- `program: "./cmd/bisync"` scopes the test run to the bisync package.
- `args` are passed to the package test binary, not to the `rclone bisync` CLI command.

The three direction variants are encoded only through `-remote` and `-remote2`:

## Control Flow

There is no executable control flow inside this JSON file. The effective control flow is supplied by VS Code, the Go extension, and the bisync test harness:

1. A developer selects one launch configuration by `name`.
2. The Go debug adapter starts a Go test run for `./cmd/bisync`.
3. The test binary receives the listed flags.
4. `bisync_test.go` consumes `-remote`, `-remote2`, `-case`, and `-no-cleanup` via package-level `flag` variables.
5. The bisync test engine runs only the selected case against the selected pair of filesystem roots.

Within this chunk, the control-flow matrix is deliberately repetitive. For each complete backend block, the generated order is case-major: all three variants for `test_all_changed`, then all three for `test_backupdir`, and so on. That order mirrors the generator loops in `bisync_debug_test.go`: iterate backends, then test cases, then `LocalRemote`/`RemoteLocal`/`RemoteRemote`.

## State and Persistence Behavior

The JSON itself has no mutable state. The stateful effect comes from `-no-cleanup`, which tells the bisync test harness to retain temporary test files after the run. That is intentional for debugging because the selected launch target is meant to be run under an interactive debugger and the retained files help inspect failure state.

The remote flags choose where test fixtures and bisync metadata will be created. `local` uses local filesystem paths managed by the test harness. Named remotes such as `TestDrive:`, `TestDropbox:`, and `TestJottacloud:` rely on rclone integration-test remote configuration. `:memory:` uses rclone's in-memory backend and only persists for the process lifetime, although the launch entry still passes `-no-cleanup`.

Because every entry is a full independent debug launch, there is no persistent cursor or inter-entry dependency in this file. Persistence risks are external: leftover debug data on real remote providers, retained local temp directories, and provider-side objects that remain when tests fail or when `-no-cleanup` is used.

## Integration Points

The immediate integration point is VS Code debugger discovery: this file can be copied into or used as a source for `.vscode/launch.json` configurations. The generated entries are intentionally verbose so the debug picker exposes backend, case, and path-placement information without requiring the developer to inspect `args`.

The deeper integration point is the bisync test matrix. The `LocalRemote`, `RemoteLocal`, and `RemoteRemote` variants probe asymmetry in bisync behavior: local-to-remote, remote-to-local, and remote-to-remote setups can differ in modtime precision, checksum support, empty-directory support, case sensitivity, Unicode normalization, directory markers, object naming, and delete/copy semantics.

The compressed remotes (`TestCompressDrive:`, `TestCompressS3:`, and the tail of `TestCompressSwift:`) integrate bisync with rclone's compression wrapper layered over real backend providers. `TestGoogleCloudStorage,directory_markers:` is specifically useful for directory marker behavior, while `:memory:` is useful for fast, process-local behavior with different persistence semantics from cloud remotes.

## Risks and Edge Cases

- The chunk is not standalone JSON. It starts after an object's `name`/metadata fields and ends before a trailing object's `args`; tooling that validates only this line range as JSON will fail.
- The full launch file is huge. The generator warns that VS Code can crash if too many configurations are used at once, so this file is best treated as a catalog to copy from selectively.
- `-no-cleanup` is useful for debugging but risky against real integration remotes because failed or repeated runs can leave provider-side test data behind.
- Backend names are literal flag values. Colons, commas, and path suffixes such as `TestIA:rclone-integration-test` must not be normalized by downstream scripts.
- The `name` format is not completely uniform. Most remotes display as `Test <remote>: <case> <variant>`, while `TestIA:rclone-integration-test` appears without the extra colon separator. Parsers should prefer `args` over display names.
- The range's aggregate counts can be misleading because one leading entry contributes only `args`, and one trailing entry contributes only `name`/metadata. Merge tooling should use chunk boundaries from the manifest rather than infer completeness from local line counts.
- Real-provider launch entries are slow and may be flaky due to network, credentials, quotas, and backend consistency behavior. They should not be treated like deterministic unit-test launches.
- Direction variants using the same remote on both sides, such as `RemoteRemote`, may require the test harness to create distinct subpaths. A backend or remote configuration that maps both sides to the same physical path would invalidate the test.
