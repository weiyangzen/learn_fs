# sources/distributed-fs/ceph-client/drivers/gpu/drm/imagination/pvr_rogue_cr_defs.h lines 4821-6308

## Scope and Purpose

This chunk is the tail section of the autogenerated PowerVR Rogue control-register definition header. It contains preprocessor constants only: register offsets, full-register masks, field shifts, clear masks, field enable values, enumerated field values, and alignment metadata. There are no C functions, structs, or executable control-flow blocks in this range. The driver consumes these constants through the register access helpers in `pvr_device.h`, especially `pvr_cr_read32()`, `pvr_cr_read64()`, `pvr_cr_write32()`, `pvr_cr_write64()`, `pvr_cr_poll_reg32()`, and `pvr_cr_poll_reg64()`, which add the register offset to `pvr_dev->regs` and use Linux MMIO accessors.

The chunk covers late Rogue register regions for performance counters, OCP bus diagnostics and interrupts, security/trust configuration, checksums, secondary clock controls, DPX/ray registers, MMU fault reporting, SLC3 cache controls, context mapping, multicore control, ECC RAM initialization, and RogueXE safety-event reporting. Because the header is marked autogenerated, downstream edits should normally be made in the register-description generator inputs rather than by hand in this file.

## Important Register Families and Macros

- Performance counter blocks: `ROGUE_CR_USC_PERF_COUNTER_0`, `ROGUE_CR_TORNADO_PERF`, `ROGUE_CR_TEXAS_PERF`, `ROGUE_CR_JONES_PERF`, `ROGUE_CR_BLACKPEARL_PERF`, `ROGUE_CR_PBE_PERF`, `ROGUE_CR_SH_PERF`, and the DPX `*_PERF` blocks provide a repeated pattern of control, selector, and 32-bit counter registers. Control registers expose `CTRL_ENABLE_EN` and per-counter `CLR_N_EN` bits. Selector registers expose `BATCH_MAX`, `BATCH_MIN`, `MODE`, `GROUP_SELECT`, and `BIT_SELECT` fields. Counter registers expose a 32-bit `REG` field.
- Idle/status registers: `ROGUE_CR_JONES_IDLE` reports idle state for TDM, frame-buffer CDC/TLA paths, MMU, TLA, GARTEN, HOSTIF, SOCIF, tiling, IPP, USCS, PM, CDM, VDM, and BIF. `ROGUE_CR_SLC3_STATUS`, `ROGUE_CR_SLC3_IDLE`, and `ROGUE_CR_SLC3_FAULT_STOP_STATUS` report SLC3 read/write activity, idle sub-blocks, and fault-stop BIF state.
- OCP register block: `ROGUE_CR_OCP_REVINFO`, `ROGUE_CR_OCP_SYSCONFIG`, raw/status/enable/disable IRQ registers for three interrupt lines, `ROGUE_CR_OCP_IRQ_EVENT`, `ROGUE_CR_OCP_DEBUG_CONFIG`, and `ROGUE_CR_OCP_DEBUG_STATUS` describe OCP revision, idle/standby policy, interrupt routing, bus protocol error events, and debug connection/busy/error state for initiator and target channels.
- Security and trust registers: `ROGUE_CR_BIF_TRUST_DM_TYPE_*`, `ROGUE_CR_BIF_TRUST_DM_MASK`, `ROGUE_CR_BIF_TRUST`, and `ROGUE_CR_SYS_BUS_SECURE` define BIF trust enablement and trusted data masters, plus a system-bus secure gate. `pvr_fw_start()` uses `ROGUE_CR_SYS_BUS_SECURE` when the `sys_bus_secure_reset` feature is present to disable default protection for minimal setup and fences the write with a read.
- Checksum registers: `ROGUE_CR_FBA_FC[0-3]_CHECKSUM`, `ROGUE_CR_SHF_SHG_CHECKSUM`, `ROGUE_CR_SHF_VERTEX_BIF_CHECKSUM`, `ROGUE_CR_SHF_VARY_BIF_CHECKSUM`, `ROGUE_CR_RPM_BIF_CHECKSUM`, `ROGUE_CR_SHG_BIF_CHECKSUM`, `ROGUE_CR_SHG_FE_BE_CHECKSUM`, `DPX_CR_RQ_USC_DEBUG`, and `DPX_CR_RS_PDS_RR_CHECKSUM` expose 32-bit values used for hardware diagnostic or validation paths.
- Clock and free-list registers: `ROGUE_CR_CLK_CTRL2` and `ROGUE_CR_CLK_STATUS2` control and observe FBA, SH, VRDM, and MCU_FBTC clock state with OFF/ON/AUTO or GATED/RUNNING encodings. `ROGUE_CR_RPM_SHF_FPL` and `ROGUE_CR_RPM_SHG_FPL` describe SHF/SHG free-pool base and size, with read/write offsets and toggle bits.
- DPX/ray and fault registers: `DPX_CR_BF_PERF`, `DPX_CR_BT_PERF`, `DPX_CR_RT_PERF`, and `DPX_CR_BX_TU_PERF` mirror the performance-counter pattern. `DPX_CR_BIF_FAULT_BANK_MMU_STATUS`, `DPX_CR_BIF_FAULT_BANK_REQ_STATUS`, and `DPX_CR_BIF_MMU_STATUS` capture MMU fault bank state, request address/tag/RNW metadata, and BIF MMU busy/paused/stalled state.
- MMU mapping and fault registers: `ROGUE_CR_MMU_CBASE_MAPPING_CONTEXT` selects an 8-bit context ID; `ROGUE_CR_MMU_CBASE_MAPPING` supplies an aligned context-base address field. `ROGUE_CR_MMU_FAULT_STATUS` and `ROGUE_CR_MMU_FAULT_STATUS_META` report fault address, context, tag sideband, request ID, level, read/write direction, type, and fault bit.
- SLC3 controls: `ROGUE_CR_SLC3_CTRL_MISC` controls write combining and address decode mode with enumerations for linear, in-page hash, fixed PVR hash, scramble PVR hash, and weaved hash. `ROGUE_CR_SLC3_SCRAMBLE*` registers expose full-width scramble values.
- Context and outstanding-read registers: `ROGUE_CR_VDM_CONTEXT_STORE_MODE` defines index/instance/list modes. `ROGUE_CR_CONTEXT_MAPPING0` through `ROGUE_CR_CONTEXT_MAPPING4` map GPU engines and stack contexts to MMU context IDs. `ROGUE_CR_BIF_JONES_OUTSTANDING_READ`, `ROGUE_CR_BIF_BLACKPEARL_OUTSTANDING_READ`, and `ROGUE_CR_BIF_DUST_OUTSTANDING_READ` expose 16-bit outstanding read counters.
- Multicore registers: `ROGUE_CR_MULTICORE_GPU` advertises GPU ID and primary/compute/geometry/fragment capabilities. `ROGUE_CR_MULTICORE_SYSTEM` exposes GPU count. Fragment, geometry, and compute common control registers expose workload type, workload execute count, and GPU enable masks. Other driver files reference multicore support as a feature (`PVR_FEATURE_GPU_MULTICORE_SUPPORT`) and firmware interface structures include multicore fields, but this chunk only defines the MMIO registers.
- ECC and safety registers: `ROGUE_CR_ECC_RAM_INIT_KICK` and `ROGUE_CR_ECC_RAM_INIT_DONE` kick and observe ECC RAM initialization for MARS, RASCAL, TPU_MCU_L0, USC, and SLC_SIDEKICK. RogueXE safety registers include `ROGUE_CR_SAFETY_EVENT_ENABLE__ROGUEXE`, `ROGUE_CR_SAFETY_EVENT_STATUS__ROGUEXE`, `ROGUE_CR_SAFETY_EVENT_CLEAR__ROGUEXE`, `ROGUE_CR_FAULT_FW_STATUS`, `ROGUE_CR_FAULT_FW_CLEAR`, and `ROGUE_CR_MTS_SAFETY_EVENT_ENABLE__ROGUEXE`.

## Control Flow and Integration Points

This chunk does not implement control flow. The effective control flow appears where other driver code reads, writes, or polls the defined offsets:

- Register access is mediated by `pvr_device.h` inline helpers. A macro such as `ROGUE_CR_SAFETY_EVENT_STATUS__ROGUEXE` becomes an offset into the mapped register BAR, and masks such as `ROGUE_CR_SAFETY_EVENT_STATUS__ROGUEXE__FAULT_FW_EN` are used to test or compose register values.
- Safety-event handling in `pvr_device.c` is the clearest direct consumer of this chunk. `pvr_device_handle_safety_events()` reads `ROGUE_CR_SAFETY_EVENT_STATUS__ROGUEXE`, filters to FW fault and watchdog timeout bits, writes the same bit mask to `ROGUE_CR_SAFETY_EVENT_CLEAR__ROGUEXE`, reads `ROGUE_CR_FAULT_FW_STATUS` on FW faults, and acknowledges by writing that value to `ROGUE_CR_FAULT_FW_CLEAR`.
- Firmware startup in `pvr_fw_startstop.c` uses `ROGUE_CR_SYS_BUS_SECURE` from this chunk when hardware advertises `sys_bus_secure_reset`. It writes zero to disable the default secure-bus protection and reads the same register as a write fence before resetting/booting the firmware core.
- Other families in this chunk are integration surfaces for firmware, debug tooling, performance collection, fault diagnosis, or feature-specific code paths. The local source search did not find direct in-driver consumers for most of the performance, DPX, OCP, MMU fault, SLC3, context mapping, multicore, or ECC macros outside the autogenerated header, which means these definitions are currently latent ABI/hardware-description surface rather than heavily exercised host-driver logic.

## State and Persistence Behavior

The macros themselves persist no software state. They describe MMIO state held by the GPU hardware:

- Control registers such as performance enables, SLC3 decode mode, BIF trust, system-bus secure enablement, context mappings, multicore common controls, and ECC init kicks can change hardware behavior until reset or until firmware/driver code rewrites them.
- Status registers such as idle, fault, IRQ, checksum, outstanding-read, clock status, and ECC done reflect transient hardware state and should be read with the correct width and mask.
- Clear/ack registers such as safety event clear, fault firmware clear, and OCP IRQ enable-clear registers likely have write-one-to-clear or write-one-to-disable semantics. The local direct consumer follows that pattern by writing the observed safety/fault mask back to the clear registers.
- Alignment metadata (`*_ALIGNSHIFT`, `*_ALIGNSIZE`) on MMU/base address fields documents hardware-required granularity. Callers must shift physical/device addresses before composing register values and must preserve alignment.

## Dependencies

- Linux kernel MMIO accessors: `ioread32`, `ioread64`, `iowrite32`, `iowrite64`, `readl_poll_timeout`, and `readq_poll_timeout` are the access mechanism behind these offsets.
- Driver device state: callers need a valid `struct pvr_device` with `pvr_dev->regs` mapped to the hardware register window and feature flags checked before using variant-specific registers such as `__ROGUEXE` or security reset paths.
- Hardware/firmware contracts: field names reflect Rogue hardware units (USC, PBE, BIF, SLC3, MTS, DPX, RASCAL, MARS, JONES, BLACKPEARL, TORNADO, TEXAS, SH/SHF/SHG, RPM). Some registers are likely only valid on particular BVNCs or feature combinations.

## Risks and Edge Cases

- Width mismatches are a concrete risk. Many offsets have 64-bit `MASKFULL` values and fields above bit 31, while some are 32-bit. Using `pvr_cr_read32()` or `pvr_cr_write32()` against a 64-bit register with upper-half fields can silently drop state; using 64-bit accesses where hardware expects 32-bit accesses can also be unsafe.
- Clear masks are inverse masks for field composition, not enable values. Confusing `*_CLRMSK` with `*_EN` can clear unrelated bits or fail to set the intended bit.
- Variant suffixes matter. `__ROGUEXE` and `__SECR` macros describe feature-specific register variants. Code must check feature support before touching those offsets, as `pvr_device.c` does with `has_safety_events` and `pvr_fw_startstop.c` does with `sys_bus_secure_reset`.
- Some registers expose security, trust, MMU context, and system-bus behavior. Bad values in `ROGUE_CR_BIF_TRUST`, `ROGUE_CR_SYS_BUS_SECURE`, `ROGUE_CR_CONTEXT_MAPPING*`, or `ROGUE_CR_MMU_CBASE_MAPPING*` could break isolation, route memory through the wrong context, or prevent firmware boot.
- Performance-selector and free-list fields include packed multi-bit ranges and base-address alignment requirements. Callers should compose values with shifts/masks and avoid ad hoc literals.
- Safety-event handling deliberately filters host-handled events to FW fault and watchdog timeout, leaving other bits to firmware. Extending host handling should preserve this ownership split and avoid clearing firmware-owned events prematurely.
- The file is autogenerated. Manual edits risk being overwritten and can desynchronize from hardware XML/spec sources.
