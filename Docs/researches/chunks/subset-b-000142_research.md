## Control Flow And Protocol Behavior

Container operations define several common daemon flows. A container can be resized, started with optional detach keys, stopped or restarted with an optional signal and timeout, killed with a signal, updated in-place for resource and restart policy changes, renamed, paused through the freezer cgroup, unpaused, waited on until a selected lifecycle condition, removed with optional volume cleanup or force, and pruned in bulk when stopped. These operations expose state transitions but do not embed implementation logic; the status codes document the observable state machine, such as `304` for already started/stopped, `409` for trying to kill a non-running container or remove a running container without force, and `404` for missing containers.

The attach and exec-start flows require special client behavior. They can leave the normal request-response model and use a hijacked TCP connection or raw stream content type. For non-TTY streams, clients must demultiplex stdout and stderr using the 8-byte Docker stream header. For TTY streams, clients must treat all bytes as raw PTY traffic and cannot expect stdout/stderr separation. The websocket attach endpoint gives a parallel transport shape for similar stream selection.

Archive operations define a filesystem exchange flow around a container path. Clients can inspect archive metadata with `HEAD`, download a tar stream with `GET`, and upload a tar stream with `PUT`. The `PUT` request has meaningful safety controls: the target `path` is asserted to be a directory, `noOverwriteDirNonDir` prevents directory/file replacement mismatches, `copyUIDGID` preserves ownership mappings, and the daemon can reject writes to read-only rootfs or volumes with `403`.

Image build flow is long-running and cancellation-sensitive. The daemon reads a context stream, validates the Dockerfile before starting, processes instructions until an image ID is produced, and cancels if the client connection drops. The build endpoint is also a compatibility boundary between classic builder and BuildKit, selected by `version` and influenced by daemon `_ping` `Builder-Version`. Build outputs, target stages, platform, remote contexts, registry auth, and cache controls integrate this API with BuildKit, registries, and multi-platform workflows.

Image registry flows separate pull/import, push, tagging, delete, search, prune, inspect, save, load, and commit. `ImageCreate` uses mutually contextual parameters: `fromImage` for pull, `fromSrc` for import, `inputImage` only when `fromSrc=-`, and `repo`/`tag` mainly for import naming. `ImagePush` requires the image to already have the repository name locally and uses a separate `tag` query parameter, while its `platform` selector narrows which variant to push when a multi-platform image store exists.

System monitor flows are mostly read-only but may be long-lived. `_ping` is a lightweight health probe. `SystemEvents` streams event messages, optionally bounded by `since` and `until`, with filter scoping across object types. `SystemDataUsage` computes storage usage across images, containers, volumes, and build cache; this can be relatively expensive compared with `_ping` or `/version`.

Exec flow is two-stage. `ContainerExec` creates a daemon-side exec instance with configuration and returns an ID. `ExecStart` starts that instance and either detaches immediately or binds the client to an interactive stream. `ExecResize` mutates the TTY dimensions for an active TTY exec. `ExecInspect` reports whether the command is running, its exit code, stream settings, process config, container ID, and host PID.

Volume and network flows manage local and cluster-backed resources. Volumes are created with driver options, inspected, optionally updated when they are swarm cluster volumes, removed if not in use, and pruned. Networks are listed or created, inspected with optional troubleshooting verbosity and scope filtering, connected to containers with endpoint-level overrides, disconnected, removed, and pruned. Network connect explicitly requires a local-scoped network or attachable swarm-scoped network and says a network cannot be re-attached to a running container.

Plugin flow is multi-step and privilege-sensitive. A client can query privileges for a remote plugin, pass accepted privileges when pulling or upgrading, then enable it. Installed plugins can be inspected, disabled, force-disabled, configured, pushed, upgraded, deleted, or force-deleted. Pull and upgrade can use registry auth. Local plugin creation consumes a tar containing rootfs and manifest, which is a different path from registry pull.

Swarm flows are cluster-state dependent and use optimistic concurrency for mutable cluster objects. Init creates swarm state on a daemon, join uses a token and manager addresses, inspect reads cluster state, update mutates the spec and may rotate credentials, leave detaches the node, unlock-key retrieves the autolock key, and unlock submits it. Node, service, secret, config, and cluster-volume update endpoints require a `version` query parameter to prevent blind overwrites.

Service and task flows reflect desired-state orchestration. Creating a service records a desired `ServiceSpec`; swarmkit then schedules tasks. Updating a service requires the current version and can either submit a new spec or trigger `rollback=previous`, in which case the supplied spec is ignored. Tasks are inspected as the realized scheduler units for services and are mostly read-only in this chunk. Service and task logs expose log-driver-backed streams rather than direct container attach.

Secret and config flows are intentionally restricted. Create stores payload and metadata, list and inspect expose metadata, delete removes the object, and update only changes labels. The update documentation requires all other fields to remain unchanged from inspect output, which gives the server an explicit basis for rejecting payload or immutable-field changes.

The distribution and session flows are special integrations. Distribution inspect uses the daemon as a registry metadata client and can fail due to auth or missing remote data. Session uses HTTP upgrade to create a bidirectional h2c transport that lets the daemon call back to client-exposed services, which generic OpenAPI clients will not handle correctly without custom transport code.

## State And Persistence Behavior

Containers have mutable runtime state and persisted configuration. Start, stop, restart, kill, pause, unpause, rename, update, wait, delete, archive, attach, stats, and exec endpoints all observe or mutate that state. Resource updates are in-place and can return warnings. Delete can also remove anonymous volumes with `v=true`, making it a cross-resource mutation. Archive `PUT` mutates the container filesystem or mounted volumes and may copy UID/GID mappings.

Images and build cache are persisted content-addressed or named resources in the daemon image store and builder cache. Pull/import/load/commit/build create or modify image records, tag creates or overwrites references, delete removes tags and untagged parents when possible, prune deletes unused image records, and build prune deletes cache records. Save and load move persisted image content across a tar transport. Registry auth headers are transient request credentials but affect access to remote image/plugin content.

System information endpoints mostly read daemon state. `_ping`, `/info`, and `/version` expose daemon capabilities and state such as experimental mode and swarm status. `/events` streams persisted or live event history depending on `since` and `until`. `/system/df` computes storage usage from persisted image, container, volume, and build-cache objects.

Exec instances are daemon-side transient state tied to containers. They are created with `ContainerExec`, started with `ExecStart`, inspected with `ExecInspect`, and may expose host PIDs while running. They depend on the container being running and not paused; creation can return `409` for a paused container and start can return `409` for stopped or paused containers.

Volumes persist data through drivers. Standard volumes are created, inspected, deleted, and pruned; cluster volumes add swarm-managed state and versioned updates. Volume deletion can fail when in use, and prune deletes unused volumes in bulk. Driver options and labels are passed through to the volume subsystem, so persistence details can depend on the selected driver.

Networks persist driver configuration, IPAM configuration, labels, options, scope, and endpoint attachments. Built-in networks have protected semantics. Swarm-scoped networks are subject to attachability and operation restrictions. Because list output is intentionally smaller than inspect output, clients that need complete endpoint state must inspect individual networks.

Plugins persist installed manifests/rootfs, accepted privileges, enabled state, config settings, and registry names. Enabling or disabling a plugin affects daemon extension points such as network, volume, authorization, or logging functionality. Force disable/delete can therefore mutate daemon behavior while dependent objects still exist.

Swarm, nodes, services, tasks, secrets, configs, and cluster volumes are cluster state rather than purely local daemon state. Object versions are a persistence boundary: update operations require the caller to present the current version to avoid conflicts. Services persist desired state; tasks persist observed scheduler and container realization state. Secrets and configs persist payloads at create time but expose only label mutation through update in this API slice.

Distribution inspect does not primarily persist local daemon state; it contacts an image registry for remote descriptor and platform data. The session endpoint creates live connection state for callback services, not a durable resource, and its state lasts only for the upgraded connection lifetime.

## Risks And Edge Cases

The most important schema risk is that many `filters` parameters are typed as `string` while semantically requiring JSON-encoded `map[string][]string` data. Incorrect encoding can broaden destructive operations such as container, image, build-cache, volume, or network prune. Tests and generated clients should not treat these as arbitrary unstructured strings if safer helpers are available.

Streaming and hijacked endpoints are difficult for generic OpenAPI clients. Container attach, exec start, service logs, task logs, system events, and session can require long-lived connections, raw binary framing, HTTP upgrade handling, websocket support, or h2c. Proxies and clients that buffer or do not expose the underlying socket can break these operations even when normal JSON endpoints work.

TTY and non-TTY stream behavior is easy to confuse. Non-TTY attach/exec/log streams may be multiplexed and require frame parsing; TTY streams are raw and lose stderr separation. Tests must cover both modes because client-side parsing bugs often appear only in one mode.

Several operations are destructive or disruptive. `ContainerDelete(force=true)`, `ContainerPrune`, `ImageDelete(force=true)`, `ImagePrune`, `BuildPrune`, `VolumeDelete(force=true)`, `VolumePrune`, `NetworkDelete`, `NetworkPrune`, plugin force disable/delete, node force delete, and swarm force leave can remove data, detach workloads, or disrupt cluster behavior. Filter handling and explicit force semantics are high-risk contract areas.

Versioned updates can fail or lose intent if clients cache stale objects. `VolumeUpdate`, `NodeUpdate`, `SwarmUpdate`, `ServiceUpdate`, `SecretUpdate`, and `ConfigUpdate` require a current version. The service rollback path is especially subtle because `rollback=previous` tells the server to ignore the supplied spec.

Swarm-only endpoints share `503` behavior when the daemon is not in the required state, while init/join also use `503` when the node is already part of a swarm. Clients must distinguish not-in-swarm/already-in-swarm from `404` missing objects and from regular server `500` errors.

Container stats are version and platform sensitive. The visible chunk includes the stream and one-shot controls, and the surrounding documentation describes cgroup v1/v2 field differences. Clients computing CPU and memory percentages must account for absent `online_cpus`, absent `percpu_usage`, cgroup v2 memory field differences, and the fact that `precpu_stats` is previous-sample state.

Archive upload and download endpoints depend on filesystem semantics that the OpenAPI schema cannot fully validate. `path` may refer to files, directories, symlinks, read-only rootfs, or mounted volumes; tar entries may replace directories or files; UID/GID mapping can alter ownership. The `noOverwriteDirNonDir` and `copyUIDGID` flags should be covered by behavioral tests rather than schema tests alone.

Build and image APIs have compatibility risks across builder backends and image-store modes. `ImageBuild` supports classic builder and BuildKit, BuildKit outputs, target stages, platforms, and remote contexts. `ImagePush` platform selection is only meaningful with multi-platform image stores and must error when no matching variant exists. `ImageGet` documents OCI Image Layout plus Docker save compatibility, so consumers must tolerate both OCI content and legacy files.

Plugin APIs are privilege and lifecycle sensitive. Pulling a plugin is separate from enabling it, upgrades can require new privileges, force disable can affect dependent containers or daemon features, and delete can optionally disable first. Registry auth and accepted privilege arrays are important test inputs.

Secrets and configs intentionally restrict updates to labels. Attempts to mutate secret/config payloads or immutable fields should fail even if the body schema technically accepts a full `SecretSpec` or `ConfigSpec`. Inspect responses should avoid leaking secret data.

The `Session` endpoint is a specialized upgraded transport and its description says the server can call back to client-exposed services. It is not a normal JSON RPC call, and generated clients should likely handle it with custom code. The description contains a likely typo, `gPRC`, where `gRPC` is probably intended.
