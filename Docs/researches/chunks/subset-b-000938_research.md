## Purpose

`testmgr.h` is a data contract for the kernel crypto algorithm test manager. It does not implement cryptographic algorithms. Instead, it encodes known-answer tests, negative-test expectations, key material, public/private key encodings, expected ciphertexts, signatures, digests, public keys, shared secrets, and per-vector flags that `testmgr.c` uses to validate registered crypto implementations.

Within this chunk, the main purpose is broad early coverage for public-key and digest primitives. The vectors exercise parsing of ASN.1 RSA keys, elliptic-curve public keys, GOST parameter OIDs, Diffie-Hellman secret encodings, endianness-sensitive ECC signature storage, FIPS-conditional RSA sizes, generator-based keypair flows, keyed and unkeyed hash APIs, and long-message hashing behavior.

Although this path is under `sources/distributed-fs/ceph-client`, the file is generic Linux crypto test infrastructure rather than Ceph distributed-filesystem logic. Ceph benefits indirectly because its client-side crypto dependencies are validated by the common crypto test manager.

## Control Flow

This header itself has no runtime control flow beyond preprocessing and aggregate initialization. Its effective control flow is driven by how `testmgr.c` includes it and binds each array into `alg_test_descs[]`.

For hash templates, `alg_test_hash()` selects keyed versus unkeyed vectors, calls the shash/ahash test paths, and then applies default and randomized `testvec_config` layouts. The same `hash_testvec` fields drive setkey, digest, update/final, scatterlist alignment, chunking, and expected-error behavior.

For akcipher templates, `alg_test_akcipher()` allocates an `akcipher` transform and runs `test_akcipher_one()` for each `akcipher_testvec`. The test manager imports the encoded key, encrypts/decrypts or verifies operation-specific output as appropriate, and uses `public_key_vec` to avoid private-key-only actions on public-key vectors.

For signature templates, `alg_test_sig()` runs `test_sig_one()` over `sig_testvec` entries. The vectors provide public keys, optional parameters, OID algorithm identifiers for GOST variants, a message or digest buffer in `m`, and signature bytes in the encoding expected by the algorithm name (`ecdsa`, `x962(ecdsa)`, `p1363(ecdsa)`, `ecrdsa`, `pkcs1pad(rsa,...)`).

For KPP templates, `alg_test_kpp()` calls `do_test_kpp()` over `kpp_testvec` arrays. Deterministic entries set an explicit local secret and check generated public key plus shared secret. `genkey` entries supply an empty/minimal local secret and a peer secret/public value so the KPP implementation generates one side and the test validates output sizes and shared-secret behavior.

Preprocessor flow matters for serialized secret encodings. DH and ECDH secrets include small type/length/key-size headers with `#ifdef __LITTLE_ENDIAN` alternatives. The bytes must match the in-kernel `crypto_dh` / ECDH secret serialization format on the target architecture.

## State And Persistence Behavior

All data in this chunk is `static const` except the zeroed static declaration, so there is no mutable runtime state and no persistence to disk or external services. The vectors are compiled into the kernel/module image and live as read-only data for the lifetime of the crypto test manager.

The state encoded by the vectors is still semantically important:

- Expected lengths (`key_len`, `m_size`, `c_size`, `secret_size`, `expected_ss_size`, `psize`, `ksize`) are part of the ABI between the header and test runner. A stale length can make a valid byte string fail or let a truncated value pass.
- Error expectation fields (`setkey_error`, `digest_error`, `crypt_error`, `setauthsize_error`) let later chunks express negative tests; this chunk mainly defines the fields and uses normal success vectors.
- `fips_skip` and `CONFIG_CRYPTO_FIPS` gates control which vectors are valid in FIPS builds. The RSA vectors deliberately omit some non-FIPS material when FIPS mode/configuration is active.
- `public_key_vec`, `genkey`, and `algo` change how the same generic runner treats a vector. They are control metadata, not just documentation.

## Risks And Edge Cases

The highest risk is silent mismatch between byte strings and explicit size fields. Many vectors are long C string literal concatenations; a one-byte edit or stale `*_size` value can invalidate the test or hide a malformed vector.

Endianness is correctness-critical. ECDSA raw signatures use `be64_to_cpua()` to fill an internal fixed-width ECC buffer, while KPP secrets manually encode type and length headers differently for little-endian and big-endian builds. These paths can pass on one architecture and fail on another if edited casually.

Several vectors test parser boundaries rather than only math: DER/ASN.1 RSA keys, X9.62 ECDSA signatures, P1363 fixed-width signatures, GOST OID parameter blobs, and DH/ECDH secret serialization. Changing encodings can break parser coverage even if the mathematical values are equivalent.

FIPS conditionals are subtle. Some RSA vectors are hidden under `#ifndef CONFIG_CRYPTO_FIPS`, while vector records also have `fips_skip` fields. The two mechanisms operate at different phases: compile-time exclusion versus runtime test skipping.

Long-message digest vectors, especially the repeated 1023-byte plaintexts, are designed to exercise block-boundary and multi-update behavior. They are easy to corrupt because they are visually repetitive.

## Test Signals

Build-level signals include successful compilation of `crypto/testmgr.c` with this header under little-endian and big-endian configurations, plus FIPS and non-FIPS builds to cover conditional RSA material.

Runtime test signals come from crypto self-tests when algorithms are registered:

Useful failure symptoms include `alg: self-tests for <alg> failed` messages, mismatched digest/signature/shared-secret output, key import errors, FIPS-only failures, and architecture-specific failures on big-endian or little-endian test runs.
