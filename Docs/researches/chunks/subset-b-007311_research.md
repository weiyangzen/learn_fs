## Control Flow and Behavioral Contracts

Configuration flow is layered. Constructors establish whether default resources are loaded. Static `addDefaultResource` appends classpath resources to the global default load order. Instance `addResource` calls add overlay sources, with later properties overriding earlier ones unless the prior value is marked final. `reloadConfiguration` clears previously loaded resource-derived properties and final markers so resources will be read again on demand, while values installed with setters remain overlays. Calls to `get` return variable-expanded values, whereas `getRaw` bypasses expansion; typed getters parse string values and fall back to defaults when absent or invalid.

Class and resource lookup in `Configuration` routes through a configurable class loader. `getClassByName`, `getClass`, `getClasses`, and `setClass` define the runtime plugin pattern used throughout Hadoop: configuration properties name implementation classes, optional interface checks validate assignability, and callers instantiate or use those classes elsewhere. `writeXml`, `readFields`, and `write` are persistence boundaries for configuration state.

Distributed cache flow begins when job setup records cache file/archive URIs and timestamps in the `Configuration`. Task localization resolves each URI against the configured filesystem, verifies that the modification timestamp still matches the timestamp captured when the job started, copies the file or archive to a local base directory, unpacks archives when needed, records the localized paths, optionally creates working-directory symlinks named by URI fragments, and exposes those local paths to mappers and reducers. `releaseCache` decrements or releases use of a localized URI, while `purgeCache` clears server-side backing cache contents during reinitialization.

Filesystem resolution flow starts from `FileSystem.get(conf)` or `FileSystem.get(uri, conf)`. The URI scheme maps to a configuration property of the form `fs.<scheme>.class`, the chosen class is initialized with the full URI and configuration, and instances are cached until `close` or `closeAll`. `Path.getFileSystem(conf)` is the value-object side of the same flow. `checkPath` enforces that operations are issued against a path belonging to the target filesystem.

File creation flow in `FileSystem` is overload-heavy but converges on the abstract create method accepting `Path`, `FsPermission`, overwrite flag, buffer size, replication, block size, and optional `Progressable`. Static `FileSystem.create(fs,file,permission)` and `mkdirs(fs,dir,permission)` are documented as two-step, thread-safe permission helpers that avoid changing a shared umask. Append is optional and represented by abstract/overloaded methods that may throw when unsupported.

Read flow centers on `FSDataInputStream`, `FSInputStream`, `BufferedFSInputStream`, and `PositionedReadable`. Sequential reads update stream position, while positional reads accept an explicit file offset and are documented as thread-safe and non-mutating with respect to the current offset. `seekToNewSource` is the recovery hook for moving to another replica/source after read problems.

Checksum flow layers `ChecksumFileSystem` over a raw filesystem. It computes checksum file paths and lengths, controls verification, wraps opens and creates with checksum-aware streams, and delegates data operations such as rename/delete/list/mkdirs while accounting for checksum side files. `FSInputChecker` handles chunk reads and checksum validation; `FSOutputSummer` chunks writes and emits checksums; `ChecksumException` reports a corruption position; `LocalFileSystem.reportChecksumFailure` marks local corrupt files unusable by moving them to a bad-file area.

Copy/staging flow is split between `FileSystem` instance methods and `FileUtil` static helpers. `copyFromLocalFile`, `moveFromLocalFile`, `copyToLocalFile`, and `moveToLocalFile` handle local/remote transfer semantics and optional source deletion. `startLocalOutput` returns a direct target for local filesystems or a temporary local path for remote filesystems, and `completeLocalOutput` copies that temporary file to the final filesystem target for remote implementations. `FileUtil.copy` and `copyMerge` provide lower-level implementations across local and Hadoop filesystems.

Globbing flow in `FileSystem` expands path patterns with `*`, character classes/ranges, negated classes, escaped characters, and brace alternatives. Results are sorted by path name; no match returns `null` for non-glob nonexistent paths and an empty array for glob patterns with no matches. Optional `PathFilter` applies caller-specific filtering after pattern expansion.

HAR read flow treats a Hadoop archive as a read-mostly virtual filesystem. Initialization binds the HAR URI to an underlying filesystem and archive home. Lookups consult `_masterindex` and `_index`, using `getHarHash(Path)` to find indexed entries, then map logical archive paths to physical `part-*` files, offsets, and lengths. Reads return streams bounded to the archived file segment. Many mutating filesystem methods are explicitly "not implemented," so callers should treat HAR as archive-backed read-only storage.

Local allocation flow in `LocalDirAllocator` cycles through configured local directories per context, selecting a writable path with enough space when size is known or a writable parent when size is unknown. Read lookup scans all configured directories. Temporary files are created in the selected directory and marked for deletion on JVM exit.

## Risks and Compatibility Notes

This chunk covers public API metadata. A signature, visibility flag, exception declaration, deprecation string, field, or Javadoc change can alter JDiff compatibility results even when implementation code is unchanged.

The chunk ends mid-class and mid-method-entry for `RawLocalFileSystem`. Any merged per-file report must combine this with the next chunk to avoid treating the raw local filesystem API as complete here.

`Configuration` is a high-risk compatibility point. Resource precedence, final parameters, variable expansion, type parsing defaults, class loader behavior, XML output, and `Writable` serialization are global assumptions across Hadoop. `reloadConfiguration` is especially sensitive because it intentionally clears resource-derived state but retains setter overlays.

`DistributedCache` combines configuration mutation, HDFS/local IO, archive extraction, timestamp validation, symlink behavior, and classpath mutation. Risks include stale cache reuse when timestamps differ, URI fragment conflicts for symlinks, incomplete cleanup/release, archive traversal or extraction surprises, inconsistent ordering between URI arrays and timestamp arrays, and changing the configuration keys or comma-separated encoding used by jobs.

`FileSystem` is compatibility-critical because nearly every Hadoop storage operation routes through it. Risks include instance cache lifecycle leaks, wrong URI scheme binding, `checkPath` accepting or rejecting the wrong paths, overloads delegating with changed defaults, append being treated as mandatory instead of optional, recursive delete semantics, glob return differences (`null` versus empty array), permission/owner/time support variance, and statistics synchronization.

Checksum APIs are corruption-sensitive. Changing checksum side-file naming, bytes-per-sum, checksum length calculation, verification defaults, failure reporting, or local bad-file quarantine behavior can either hide data corruption or reject valid data. `MD5MD5CRC32FileChecksum` also needs stable binary and XML encodings.

`FileStatus`, `BlockLocation`, and `ContentSummary` are serialized metadata carriers. Comparison, equality, path handling, and read/write ordering are likely compatibility surfaces for RPCs, sorting, tests, and client behavior.

`FileUtil` methods are risky because they perform destructive local operations and may invoke OS commands. Recursive delete can leave partial state, copy/delete-source can lose data if ordering changes, archive extraction must avoid path traversal and preserve expected layout, chmod/symlink/hardlink behavior is platform-dependent, and file replacement must handle preexisting targets atomically enough for callers.

`HarFileSystem` is mostly read-only by contract in this chunk. Accidentally allowing unsupported mutations, changing URI format, changing path hashing, or altering index interpretation would break archived data access. Permissions are explicitly reported from archive index files rather than persisted original file permissions, which is a visible behavior.

`LocalDirAllocator` has documented limitations around disks becoming read-only or full during active writes. Tests and callers should not assume it protects writes after allocation. Its per-context singleton behavior and round-robin cursor are also stateful and concurrency-sensitive.

`Path` normalization and URI conversion are longstanding compatibility risks. Edge cases around relative paths, schemes, authorities, parent at root, suffix behavior, comparison ordering, `hashCode`, and qualification against filesystems can affect caches, maps, sorted listings, command-line tools, and serialized metadata.
