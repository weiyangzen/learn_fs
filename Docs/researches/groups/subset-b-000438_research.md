# sources/control-plane/rook/deploy/examples/monitoring/grafana/Ceph Cluster Dashboard.json

Purpose: defines the bundled Grafana "Ceph Cluster" dashboard for Rook/Ceph monitoring. It is a broad cluster-operations view that combines cluster health, capacity, I/O, pool utilization, OSD and PG state, alert tables, node-exporter host statistics, latency distributions, recovery activity, and daemon version counts. The dashboard is intended to be imported by Grafana alongside Prometheus metrics emitted by Ceph mgr/prometheus, Rook monitoring examples, Prometheus alert rules, and optional node-exporter scraping.

Important APIs/types/functions: this file is Grafana dashboard JSON rather than executable code. Its operational API surface is the dashboard schema and Prometheus query contract: top-level `uid` `tbO9LAiZK`, title `Ceph Cluster`, schema version `37`, tag `ceph-mixin`, datasource template variable `DS_PROMETHEUS`, interval template variable `interval`, dashboard annotations, time range `now-6h` to `now`, refresh `1m`, and 63 titled Grafana panel objects including row, stat, gauge, timeseries, table, and heatmap panels. The important metric contracts include `ceph_health_status`, `ceph_cluster_total_bytes`, `ceph_cluster_total_used_bytes`, `ceph_osd_up`, `ceph_osd_in`, `ceph_osd_numpg`, OSD operation counters and latency sums/counts, PG state gauges, pool metadata and quota metrics, `ALERTS`, node memory/CPU/disk/filesystem metrics, and daemon metadata metrics for OSD, MON, MDS, and RGW versions.

Control flow: Grafana evaluates the datasource variable first, then the optional interval variable, then panel PromQL targets over the selected time range. The first rows render instant stat/gauge panels for health, write/read throughput, capacity, object count, alert count, IOPS, monitor quorum/session count, OSD up/in/out/down counts, average PGs, and average OSD latencies. Later rows render time-series and tables: capacity combines available/used/total bytes; IOPS and throughput aggregate OSD read/write rates; pool views join pool counters to `ceph_pool_metadata` with `* on(pool_id) group_left(name)`; alert tables use `ALERTS{alertstate="firing",alertname=~"^Ceph.+"}`; sluggish and down OSD tables use latency sums and `ceph_osd_up == 0`; node panels query node-exporter metrics; PG panels fan out across active, clean, degraded, stale, undersized, incomplete, backfill, recovery, remap, repair, and related states; heatmaps/timeseries show raw and averaged OSD apply, commit, read-op, and write-op latency; version panels count daemon metadata by `ceph_version`.

State and persistence behavior: the dashboard itself is declarative and stateless after import, but Grafana persists it as a dashboard definition keyed by UID/version and stores any user edits if imported into a writable Grafana instance. Runtime state is external: Prometheus stores the metric time series, Grafana stores selected template variable values and time range in the browser/session, and alert state is read from Prometheus/Alertmanager-compatible `ALERTS` samples. There is no Kubernetes object in this file and no writeback to Ceph; all behavior is observational.

Dependencies and integration points: depends on Grafana with Prometheus datasource support and on a datasource selectable through `${DS_PROMETHEUS}`. It integrates with Ceph mgr's Prometheus exporter for Ceph metrics, Prometheus alert rule output for the `ALERTS` series, node-exporter metrics under a `job='node'` convention for CPU, and Grafana panel plugins for stat, gauge, table, timeseries, and heatmap rendering. It is shipped under Rook's `deploy/examples/monitoring/grafana` tree and is normally used with the neighboring Rook monitoring manifests and dashboard import automation.

Risks: many panels assume Ceph metric names and labels from the Ceph mgr Prometheus module; label or metric changes will silently produce empty panels. Pool panels depend on the `pool_id` to `name` join and will break if `ceph_pool_metadata` is absent. Node panels are not Rook-specific and assume node-exporter series are scraped with expected labels, including `job='node'` for CPU and root filesystem labels for free-space percentage. `ALERTS` is produced by Prometheus rule evaluation, not Ceph itself, so the alert stat/table can be empty in setups that scrape metrics but do not run matching alert rules. Several latency panels divide rate sums by rate counts; zero or missing counts can yield no series after `>= 0` filtering. The dashboard mixes legacy metadata requirements with modern schema fields, so import behavior should be checked when Grafana versions change.

Test signals: validate the JSON with `jq`, import it into a Grafana version supported by the Rook monitoring stack, and confirm the `${DS_PROMETHEUS}` variable resolves. In an integration cluster, verify non-empty series for representative queries: cluster health/capacity, OSD up/in counts, read/write IOPS and throughput, pool metadata joins, PG state counts, alert table, node-exporter CPU/memory/disk panels, OSD latency heatmaps, and daemon version counts. Regression tests should include a cluster with no firing alerts, no RGW/MDS daemons, and at least one pool to ensure panels fail empty gracefully instead of rendering query errors.

# sources/control-plane/rook/deploy/examples/monitoring/grafana/Ceph OSD Single Dashboard.json

Purpose: defines the bundled Grafana "Ceph - OSD (Single)" dashboard for inspecting one selected Ceph OSD. It narrows the cluster view to a template-selected `ceph_daemon` and shows OSD up/in status, total OSD count, PG count compared with cluster average, storage availability/usage, utilization, latency heatmaps, and average read/write/apply/commit latency.

Important APIs/types/functions: this is Grafana dashboard JSON. Its API surface is the dashboard import contract plus PromQL queries: top-level `uid` `Fj5fAfzik`, title `Ceph - OSD (Single)`, schema version `36`, tags `ceph` and `osd`, refresh `5m`, browser timezone, default time range `now-3h` to `now`, datasource template `DS_PROMETHEUS`, interval template `interval`, and query template variable `osd` populated by `label_values(ceph_osd_up, ceph_daemon)`. The dashboard has 15 titled panel objects: status/total rows and stat panels, an OSD-specific row, PG and storage timeseries, utilization gauge, latency row, four OSD latency heatmaps, read/write operation latency timeseries, and apply/commit latency timeseries.

Control flow: Grafana first resolves the Prometheus datasource, interval choices, and selected `$osd`. Status panels query `ceph_osd_up{ceph_daemon="$osd"}` and `ceph_osd_in{ceph_daemon="$osd"}` while the total count queries all `ceph_osd_up` series. The PG panel compares `ceph_osd_numpg{ceph_daemon=~"$osd"}` with the cluster average. Storage panels query `ceph_osd_stat_bytes` and `ceph_osd_stat_bytes_used`; most panels filter by `$osd`, but the available-storage and utilization expressions are hard-coded to `ceph_daemon="osd.0"`. Latency heatmaps and timeseries filter apply/commit metrics or read/write latency sum/count ratios to the selected daemon and aggregate away `instance` and sometimes `ceph_daemon`.

State and persistence behavior: the file is declarative and has no direct runtime state. Grafana persists the imported dashboard definition and browser/session selections for datasource, time range, interval, and `$osd`. Prometheus persists the OSD metric series. The dashboard performs no mutation of Ceph or Kubernetes resources.

Dependencies and integration points: depends on Grafana 9-era panel support, the Prometheus datasource plugin, and Ceph mgr Prometheus metrics for `ceph_osd_up`, `ceph_osd_in`, `ceph_osd_numpg`, `ceph_osd_stat_bytes`, `ceph_osd_stat_bytes_used`, `ceph_osd_apply_latency_ms`, `ceph_osd_commit_latency_ms`, and read/write latency sum/count metrics. It integrates with Rook's monitoring examples as an importable focused dashboard, typically linked operationally from cluster-level OSD investigations even though this JSON does not define dashboard links.

Risks: the available-storage and utilization panels contain `ceph_daemon="osd.0"` rather than the `$osd` variable, so selecting any other OSD can still show OSD 0 storage availability and utilization. Two row panels carry a concrete datasource UID `PBFA97CFB590B2093` instead of `${DS_PROMETHEUS}` even though row targets are effectively empty; this can confuse import diffs or validation in Grafana instances without that UID. The row title spells "Varience", which is cosmetic but can affect automated snapshot comparisons. The dashboard assumes `ceph_daemon` label values match strings such as `osd.0`; label changes or absent metrics will leave the variable and panels empty. Rate-based latency ratios can disappear when operation counts are zero, making idle OSDs look blank rather than explicitly zero.

Test signals: validate JSON syntax and import into Grafana, then confirm the `osd` variable populates from `label_values(ceph_osd_up, ceph_daemon)`. In a cluster with at least two OSDs, select a non-`osd.0` daemon and verify status, PGs, used storage, heatmaps, and average latencies follow the selected OSD; the hard-coded availability/utilization queries should be tested and likely corrected if the dashboard is expected to be fully variable-driven. Also test idle OSDs with no read/write counts, down/out OSDs, and import into Grafana instances where the fixed row datasource UID does not exist.

# sources/control-plane/rook/deploy/examples/monitoring/grafana/Ceph Pools Dashboard.json

Purpose: defines the bundled Grafana "Ceph - Pools" dashboard for inspecting one selected Ceph pool. It shows pool storage capacity/usage, raw stored bytes, utilization percentage, object/dirty/quota object counts, per-pool read/write IOPS, and per-pool read/write byte throughput.

Important APIs/types/functions: this is Grafana dashboard JSON. Its API surface is the dashboard import contract plus PromQL queries: top-level `uid` `-gtf0Bzik`, title `Ceph - Pools`, schema version `36`, tags `ceph` and `pools`, refresh `1m`, browser timezone, default time range `now-3h` to `now`, datasource template `DS_PROMETHEUS`, interval template `interval`, and query variable `pool` populated by `label_values(ceph_pool_metadata, name)`. The dashboard has 7 titled panel objects: pool row, pool-storage timeseries, usage gauge, pool-info row, objects timeseries, IOPS timeseries, and throughput timeseries.

Control flow: Grafana resolves `$pool` from `ceph_pool_metadata` and evaluates each panel against Prometheus. Storage panels join pool counters to metadata with `* on(pool_id) group_left(name)(ceph_pool_metadata{name=~"^$pool$"})`, then aggregate by pool name. The storage panel emits available (`ceph_pool_max_avail`), stored (`ceph_pool_stored`), total (`ceph_pool_stored + ceph_pool_max_avail`), and raw stored (`ceph_pool_stored_raw`) series. The usage gauge computes `ceph_pool_stored / (ceph_pool_stored + ceph_pool_max_avail)` after the same metadata join. Object panels show `ceph_pool_objects`, `ceph_pool_dirty`, and `ceph_pool_quota_objects`. IOPS panels use `irate(ceph_pool_rd[3m])` and `irate(ceph_pool_wr[3m])`; throughput panels use `irate(ceph_pool_rd_bytes[5m])` and `irate(ceph_pool_wr_bytes[5m])`.

State and persistence behavior: the dashboard is stateless configuration. Grafana persists the imported JSON, the selected datasource/time range/pool in user context, and any edits made after import. Prometheus persists all pool metrics. The dashboard has no side effects on Ceph pools and does not read Kubernetes resources directly.

Dependencies and integration points: depends on Grafana with Prometheus datasource support and Ceph mgr Prometheus metrics for pool metadata, capacity, object, and I/O counters. The main integration point is the `ceph_pool_metadata` label join, which translates numeric `pool_id` series into human-readable pool names and drives the `$pool` selector. It sits beside the cluster and single-OSD dashboards as part of Rook's example Grafana set.

Risks: every useful panel depends on `ceph_pool_metadata{name=~"^$pool$"}` and a successful `pool_id` join; missing metadata makes the dashboard mostly blank even if raw pool counters are scraped. Anchoring the variable as a regex protects against partial matches, but special regex characters in pool names could still affect matching because `$pool` is interpolated into a regex. Usage divides by `stored + max_avail`; unusual or missing capacity values can produce empty/invalid results. The dashboard does not expose all pool health signals, such as recovery/backfill, PG states by pool, or quota bytes; operators must cross-reference the cluster dashboard or Ceph CLI for deeper diagnosis.

Test signals: validate JSON syntax, import into Grafana, and confirm `$pool` populates from `ceph_pool_metadata`. In a test cluster with multiple pools, verify each pool selection changes storage, usage, object, IOPS, and throughput series and that legends show `{{ name }}` correctly. Include pools with zero traffic, quotas unset, and names that contain characters significant to regex matching. PromQL checks should confirm the metadata join returns one series per selected pool and does not duplicate data when multiple Prometheus targets scrape the same Ceph exporter.

# sources/control-plane/rook/deploy/examples/monitoring/keda-rgw.yaml

Purpose: provides a minimal KEDA `ScaledObject` example for autoscaling a Rook `CephObjectStore` RGW deployment based on Prometheus-observed RGW PUT-object operation rate. It demonstrates how Rook's Ceph object store custom resource can be used as a KEDA scale target when Prometheus is scraping Ceph RGW metrics.

Important APIs/types/functions: this file is Kubernetes YAML for `apiVersion: keda.sh/v1alpha1`, `kind: ScaledObject`. The object is named `rgw-scale` in namespace `rook-ceph`. `spec.scaleTargetRef` points to `apiVersion: ceph.rook.io/v1`, `kind: CephObjectStore`, `name: my-store`. Scaling bounds are `minReplicaCount: 1` and `maxReplicaCount: 5`. The only trigger is KEDA's Prometheus scaler with `serverAddress: http://rook-prometheus.rook-ceph.svc:9090`, `metricName: ceph_rgw_put_collector`, query `sum(rate(ceph_rgw_op_put_obj_ops[2m]))`, and threshold `"90"`.

Control flow: once applied to a cluster with KEDA installed, the KEDA operator watches this `ScaledObject`, resolves the referenced `CephObjectStore`, and periodically queries the configured Prometheus endpoint. The Prometheus trigger evaluates the RGW PUT-object operation rate over a two-minute window and compares the scalar result with threshold 90. KEDA then drives Kubernetes scale behavior for the referenced target, constrained by the min/max replica counts. Rook's Ceph operator remains responsible for reconciling the `CephObjectStore` and RGW deployment details.

State and persistence behavior: Kubernetes persists the `ScaledObject` in etcd, KEDA persists status/conditions on the object, and Prometheus stores the RGW operation counter samples used by the query. The YAML itself contains no secrets and no local state. Autoscaling state is distributed across KEDA's controller loop, Kubernetes scale subresource interactions, Rook's CephObjectStore reconciliation, and Prometheus scrape history.

Dependencies and integration points: requires KEDA CRDs and operator support for the Prometheus scaler, a Rook cluster with `CephObjectStore` CRD `ceph.rook.io/v1`, an object store named `my-store` in `rook-ceph`, a Prometheus service reachable at `rook-prometheus.rook-ceph.svc:9090`, and a scraped `ceph_rgw_op_put_obj_ops` counter. It integrates Rook, KEDA, Prometheus, and Ceph RGW metrics; the scale target is not a raw Kubernetes Deployment but the Rook object-store custom resource.

Risks: the example uses placeholder `my-store`, so applying it unchanged will fail or do nothing unless that CephObjectStore exists. The Prometheus service address is hard-coded to the example namespace/service name and may not match kube-prometheus-stack, OpenShift monitoring, or external Prometheus setups. The scaler assumes `ceph_rgw_op_put_obj_ops` is present and meaningful for autoscaling; GET-heavy workloads, bucket-specific hotspots, CPU saturation, or network constraints are not represented. Threshold `"90"` is an example value without workload-specific capacity calibration. Scaling a Rook CRD through KEDA depends on scale-subresource support and correct Rook reconciliation behavior; this should be validated for the Rook/KEDA versions in use.

Test signals: validate the YAML with Kubernetes server-side dry-run in a cluster with KEDA and Rook CRDs installed. Confirm `kubectl get scaledobject -n rook-ceph rgw-scale` reports ready conditions, KEDA can reach the Prometheus URL, and the query returns one scalar sample. Generate RGW PUT load and verify desired replica changes stay within 1 to 5 replicas and are reflected by the CephObjectStore/RGW deployment. Also test missing Prometheus, missing metric, nonexistent `my-store`, and low/no traffic to ensure the scaler status and fallback behavior are understandable.
