# sources/distributed-fs/ceph-client/drivers/phy/rockchip/phy-rockchip-naneng-combphy.c

Purpose: this is the Rockchip NANENG combo PHY provider for RK3528, RK3562, RK3568, RK3576, and RK3588 SoCs. One MMIO PHY block can be configured as PCIe, USB3, SATA, SGMII, or QSGMII depending on the SoC and the `#phy-cells` argument supplied by consumers. The driver is not a generic analog framework; it is a table-driven collection of GRF write-enable bitfields and PHY-register tuning sequences for each compatible.

Important APIs, types, and functions: `struct combphy_reg` describes GRF bit ranges plus enable/disable values; `struct rockchip_combphy_grfcfg` groups all SoC-specific GRF controls; `struct rockchip_combphy_cfg` binds compatible data to PHY base addresses and a configuration callback; `struct rockchip_combphy_priv` is the runtime state. Core helpers are `rockchip_combphy_param_write()` for Rockchip 16-bit write-mask GRF writes, `rockchip_combphy_updatel()` for local MMIO read/modify/write, and `rockchip_combphy_is_ready()` for the USB3 ready poll. The public PHY operations are `.init` and `.exit`; `rockchip_combphy_xlate()` records the requested `PHY_TYPE_*`.

Control flow: probe matches compatible data, maps MMIO, derives `priv->id` by comparing resource start addresses with the SoC `phy_ids[]`, parses clocks/syscon/reset/properties, asserts reset, creates one PHY, and registers an OF PHY provider. Init enables all clocks, dispatches to the SoC callback by `priv->type`, deasserts the reset, and for USB3 polls `pipe_phy_status` for ready. Exit disables clocks and asserts reset. The SoC callbacks program mode-specific muxes and analog values: PCIe gets `con*_for_pcie` plus refclk and SSC/L1SS tuning; USB3 enables CTLE/squelch/PLL tweaks and USB mux/port enable controls; SATA sets termination and SATA pipe controls; RK3568 adds SGMII/QSGMII XPCS-ready and rate/mode muxing.

State and persistence behavior: runtime state is entirely in device-managed memory plus hardware registers. `type`, `id`, `enable_ssc`, `ext_refclk`, clocks, resets, and regmaps persist for the platform device lifetime. There is no suspend/resume handler, no refcounting, and no serialization around mode selection; the design assumes one consumer chooses a stable mode through xlate before init. Hardware state is reset on probe and exit but GRF writes may persist until reset or another owner rewrites them.

Dependencies and integration points: the driver depends on the Linux PHY framework, platform bus, reset framework, clk bulk APIs, regmap/syscon, OF match data, `rockchip,pipe-grf`, `rockchip,pipe-phy-grf`, `rockchip,enable-ssc`, and `rockchip,ext-refclk`. Consumers pass standard `PHY_TYPE_*` values in their phandle. Refclk must be named with an id beginning `ref` and must currently be 24, 25, or 100 MHz depending on SoC/mode.

Risks: most behavior is hard-coded analog tuning, so regressions appear as link training failures rather than obvious software errors. `rockchip_combphy_param_write()` does not validate uninitialized `combphy_reg` fields, so adding a SoC or mode with missing table entries can silently write offset zero. `rockchip_combphy_is_ready()` ignores `regmap_read()` failures. Unsupported refclock rates abort init after clocks are already enabled but are cleaned up by the common error path. The xlate path can overwrite `priv->type` and only warns if a second consumer asks for a different type. `priv->id` can remain `-ENODEV`; only paths that switch on known IDs handle that gracefully.

Test signals: useful tests are boot/probe logs for missing `ref` clocks, GRF phandles, and reset controls; PCIe/SATA/USB3 link bring-up on each compatible and refclk combination; USB3 ready-poll warnings; PCIe L1SS/SSC behavior with internal and external reference clocks; RK3568 SGMII/QSGMII link training; and fault injection for bad refclk rates and missing syscons. Static review should verify every compatible table covers every register touched by its callback.

# sources/distributed-fs/ceph-client/drivers/phy/rockchip/phy-rockchip-pcie.c

Purpose: this legacy Rockchip PCIe PHY driver supports the RK3399 PCIe PHY through GRF syscon registers. It exposes either one legacy PHY or up to four lane PHY instances, depending on `#phy-cells`, and coordinates shared reset/PLL state across those lane instances.

Important APIs, types, and functions: `struct rockchip_pcie_data` stores GRF offsets for config, status, and lane-off registers. `struct rockchip_pcie_phy` stores the syscon regmap, four `phy_pcie_instance` children, shared mutex, reset, ref clock, and two counters: `pwr_cnt` and `init_cnt`. `rockchip_pcie_phy_of_xlate()` maps optional phandle lane indexes to PHY instances. `phy_wr_cfg()` performs the three-step write-enable pulse into the PHY config interface. PHY operations are `.init`, `.exit`, `.power_on`, and `.power_off`.

Control flow: probe gets the parent syscon regmap, match data, reset named `phy`, and enabled `refclk`; reads `#phy-cells`; creates one or four PHY objects; attaches each instance index; then registers the provider. Init is shared: under `pcie_mutex`, the first init asserts the PHY reset and increments `init_cnt`; later inits are no-ops. Power-on clears lane idle for the requesting lane, increments `pwr_cnt`, deasserts reset only for the first active lane, selects `PHY_CFG_PLL_LOCK`, waits for `PHY_PLL_LOCKED`, writes clock-test and SCC configuration for 100 MHz output, waits for PLL output state, then waits for relock. Power-off idles the lane, decrements `pwr_cnt`, and asserts reset when the last lane powers off.

State and persistence behavior: state is in the shared `rockchip_pcie_phy` object and RK3399 GRF registers. The mutex serializes lane operations and protects counters. The counters implement shared-lifetime semantics, but `rockchip_pcie_phy_exit()` currently decrements `init_cnt` and returns without extra hardware changes once initialized, making reset/power state primarily governed by power-on/off. The enabled refclk is acquired with `devm_clk_get_enabled()` and remains enabled for the device lifetime.

Dependencies and integration points: this driver depends on the PHY framework, parent syscon node, reset framework, clock framework, and RK3399 GRF bit layout. Consumers may use legacy zero-cell phandles or lane-indexed phandles. It integrates with PCIe host/controller code through generic PHY power sequencing, not through a Rockchip-specific exported API.

Risks: counter underflow is possible if consumers call power-off/exit without balanced calls; there is no explicit guard against negative `pwr_cnt` or `init_cnt`. Power-off idles a lane before confirming the shared reset assert succeeds; on assert failure it attempts to restore lane state and counter but only for the current lane. PLL polling timeouts are large but fixed and can mask board-level clock or power issues. The `#phy-cells` interpretation is unusual: a nonzero value means four PHYs, not the literal number of cells. The lane idle write uses shifted write-mask data; mistakes in bit placement would affect adjacent lanes.

Test signals: validate single-PHY legacy and four-lane DT configurations, lane-index phandle rejection for indexes >= 4, balanced multi-lane power sequencing, reset failure injection, PLL lock and output timeout logs, and PCIe link training after repeated suspend-like power cycles. Runtime traces around `pwr_cnt` are useful when multiple PCIe consumers share the PHY.

# sources/distributed-fs/ceph-client/drivers/phy/rockchip/phy-rockchip-samsung-dcphy.c

Purpose: this driver exposes Rockchip-integrated Samsung MIPI DC-PHY blocks for RK3576 and RK3588. The implemented operational mode is MIPI D-PHY transmit; C-PHY is recognized in naming and GRF mode bits but power-on/power-off currently return `-EOPNOTSUPP` for non-DPHY types.

Important APIs, types, and functions: `struct samsung_mipi_dcphy` stores clocks, regmaps, resets, selected PHY type, lane count, platform data, and computed PLL state. `struct samsung_mipi_dphy_timing` and the long timing table map lane Mbps ceilings to D-PHY timing register values. `samsung_mipi_dcphy_pll_round_rate()` searches legal PLL predivider/fbdiv/dsm/scaler values; `samsung_mipi_dcphy_pll_ssc_modulation_calc()` computes SSC parameters above 2.5 Gbps; `samsung_mipi_dcphy_configure()` accepts `phy_configure_opts_mipi_dphy`; `samsung_mipi_dphy_power_on()` programs bias, PLL, timing, lane enables, and reset release.

Control flow: probe maps MMIO into a 32-bit regmap, obtains `rockchip,grf`, `ref` and `pclk` clocks, four resets (`m_phy`, `s_phy`, `apb`, `grf`), creates one PHY, enables runtime PM, and registers an xlate provider. Xlate requires one argument and stores the requested PHY type. Init resumes runtime PM, enabling pclk then refclk. Configure clamps lanes to a maximum of four, computes PLL output for `hs_clk_rate`, records the realized rate back into the opts, and may enable SSC. Power-on resets APB, then for D-PHY asserts master reset, programs bias and PLL registers, writes clock/data lane timing for the computed lane rate, enables PLL and waits for lock, enables active lanes, deasserts master reset, and waits for skew calibration. Power-off disables lanes and PLL. Exit drops runtime PM.

State and persistence behavior: computed PLL fields and lane count persist in `samsung->pll` and `samsung->lanes` between configure and power-on. Runtime PM owns clock enable state. The selected PHY type is mutable through xlate and shared by the single PHY object. Register programming is reapplied on every power-on, so analog state is not intended to be persistent across reset/power cycles.

Dependencies and integration points: this driver uses the generic PHY API with MIPI D-PHY configure options, runtime PM, regmap MMIO, syscon GRF, clocks, and reset controls. Platform data supplies maximum lane kbps and drive-strength resistor values for RK3576 versus RK3588. Display/DSI bridge drivers are expected to call configure before power-on and use the returned adjusted HS clock rate.

Risks: C-PHY is not implemented despite the DC-PHY name, so DT consumers must request DPHY. `s_phy_rst` and `grf_apb_rst` are acquired but not actively used in the observed control paths, which may be intentional hardware setup or latent dead code. The timing table is vendor-derived and very large, so off-by-one selection errors can cause marginal high-speed signaling. `samsung_mipi_dcphy_pll_round_rate()` increments requested rate until a legal solution is found; bad constraints could make this expensive or surprising, though current limits should converge. SSC state is set when a high rate is configured but is not explicitly cleared for later lower-rate configurations.

Test signals: DSI panel bring-up across low and high lane rates, returned HS clock rate correctness, PLL lock timeout logs, runtime PM clock enable/disable balance, lane-count handling for 1-4 lanes and values above 4, RK3576 maximum-rate clamping to 2.5 Gbps, RK3588 high-rate SSC behavior, and explicit C-PHY request tests that should fail with `-EOPNOTSUPP`.

# sources/distributed-fs/ceph-client/drivers/phy/rockchip/phy-rockchip-samsung-hdptx.c

Purpose: this driver controls Samsung HDMI/eDP transmitter combo PHYs integrated in RK3576 and RK3588. It exposes a generic PHY for HDMI TMDS, HDMI FRL, and DisplayPort operation, and also registers a clock provider for the HDMI pixel/link clock derived from PHY PLL programming.

Important APIs, types, and functions: `struct rk_hdptx_phy` is the central state, holding MMIO regmap, GRF regmap, PHY id, HDMI config, clocks, four resets, clock hardware, a `restrict_rate_change` flag, atomic usage count, and DP link state. PLL tables are `rk_hdptx_frl_lcpll_cfg[]` and `rk_hdptx_tmds_ropll_cfg[]`; DP drive tables are `tx_drv_ctrl_rbr/hbr/hbr2`. Core operations include `rk_hdptx_pll_cmn_config()`, `rk_hdptx_frl_lcpll_mode_config()`, `rk_hdptx_tmds_ropll_mode_config()`, `rk_hdptx_dp_pll_init()`, `rk_hdptx_dp_aux_init()`, DP rate/lane/voltage setters, PHY validate/configure/set_mode/power callbacks, and clock `prepare`, `determine_rate`, `set_rate`, and `recalc_rate`.

Control flow: probe maps MMIO, identifies the PHY instance by resource address, gets all clocks and reset controls, obtains `rockchip,grf`, enables runtime PM, creates the PHY, registers the PHY provider, deasserts initial resets, and registers a named clock (`clk_hdmiphy_pixel0` or `clk_hdmiphy_pixel1`). HDMI configure validates TMDS or FRL parameters and records rate/bpc. HDMI power-on ensures a fallback TMDS rate from bus width when legacy bridge code has not configured the PHY, acquires the shared consumer reference, programs common PLL registers, selects HDMI mode in GRF, then writes FRL or TMDS sideband/lane sequences and waits for lock/ready. DP power-on selects DP mode, sets lane protocol/bus width, initializes ROPLL and AUX, while later DP configure calls set link rate, lanes, and per-lane voltage/pre-emphasis.

State and persistence behavior: `hdmi_cfg`, `link_rate`, `lanes`, and `restrict_rate_change` persist in memory across operations. `atomic_t usage_count` coordinates shared ownership between the PHY callbacks and the registered clock; first consumer programs/enables the hardware and final put disables or resets it. Runtime PM controls bulk clocks. Hardware state is heavily register-resident and is rewritten for mode/rate changes; `rk_hdptx_phy_clk_calc_rate_from_pll_cfg()` can reconstruct current PLL rate from registers.

Dependencies and integration points: the driver sits at the intersection of the PHY framework, common clock framework, runtime PM, regmap MMIO, Rockchip GRF syscon, reset framework, DRM bridge/display consumers, HDMI PHY configuration API, and DP PHY configuration API. It uses `of_phy_simple_xlate` for one PHY per node, plus OF clock provider registration for display clock consumers.

Risks: this is a high-blast-radius driver because HDMI and DP paths share PLL, sideband, lane, reset, and usage-count state. Atomic usage counting has underflow detection, but concurrent mode changes are not otherwise serialized by a mutex. Legacy HDMI clock-rate compatibility paths can interact with newer `phy_configure()` flows; `restrict_rate_change` is intended to constrain that but should be tested carefully. PLL tables plus dynamic ROPLL calculation must match hardware tolerances. DP voltage programming assumes `hdptx->lanes` and `hdptx->link_rate` were already configured. Poll timeouts for PLL, PHY, and sideband readiness are short and can expose board-level power/refclk problems.

Test signals: HDMI TMDS modes from 25.175 MHz through 594 MHz, dynamic non-table TMDS calculation, FRL rates including 3-lane and 4-lane cases, bpc 8/10/12/16 clock derivation, DP RBR/HBR/HBR2 training, DP lane counts 1/2/4, DP voltage/pre-emphasis matrix validation, shared clock prepare/unprepare versus PHY power-on/off sequencing, runtime PM clock balance, and GRF ready/lock timeout diagnostics.

# sources/distributed-fs/ceph-client/drivers/phy/rockchip/phy-rockchip-snps-pcie3.c

Purpose: this is the Rockchip Synopsys PCIe 3.0 PHY provider for RK3568 and RK3588. It configures lane aggregation or bifurcation, common-refclk mode, clocks, and reset sequencing before PCIe controllers use the PHY.

Important APIs, types, and functions: `struct rockchip_p3phy_priv` stores the SoC ops, MMIO pointer, selected RC/EP submode, lane mode data from DT, `phy_grf` and optional `pipe_grf`, reset, PHY object, clocks, lane array, and per-lane RX common-refclk mode. `struct rockchip_p3phy_ops` dispatches compatible-specific initialization. `rockchip_p3phy_set_mode()` records RC versus EP, `rockchip_p3phy_rk3568_init()` and `rockchip_p3phy_rk3588_init()` program SoC GRFs, and common `.init`/`.exit` manage clocks and reset.

Control flow: probe maps MMIO, gets match ops, looks up `rockchip,phy-grf`, optionally looks up RK3588 `rockchip,pipe-grf`, reads `data-lanes` with a fallback to aggregation, reads `rockchip,rx-common-refclk-mode` with a fallback to enabled on all lanes, creates a PHY, gets optional reset `phy`, gets all clocks, and registers a simple OF PHY provider. Init enables bulk clocks, asserts reset, delays, and calls the SoC init. RK3568 init deasserts PMA output clamp, detects bifurcation when any lane entry is greater than one, programs the bifurcation bit, deasserts reset, and polls `SRAM_INIT_DONE`. RK3588 init writes RX common-refclk mode per lane, deasserts clamp, builds aggregation/bifurcation mode bits from lane entries 3 and 4, writes common mode, optionally writes pipe GRF one-lane selection, deasserts reset, and polls both PHY status registers.

State and persistence behavior: DT-derived lane and refclk mode arrays persist in memory. The selected RC/EP submode is recorded but not used in hardware programming. Hardware mode persists in GRF registers until reset or rewrite. There is no runtime PM and no per-consumer refcount; the single PHY init/exit pair owns clocks and reset.

Dependencies and integration points: dependencies include the generic PHY and PCIe PHY mode constants, platform device matching, bulk clocks, reset framework, syscon regmaps, `data-lanes`, `rockchip,rx-common-refclk-mode`, and Rockchip GRF/PHP-GRF layouts. PCIe controller drivers should call `phy_set_mode_ext()` with RC/EP and then init/exit as part of link setup.

Risks: the optional reset can be NULL, but init/exit unconditionally call `reset_control_assert/deassert(priv->p30phy)`; Linux reset APIs generally tolerate NULL only for optional helpers if used consistently, so this path deserves verification. RK3568's "disable bifurcation" write uses `GRF_PCIE30PHY_WR_EN & ~RK3568_BIFURCATION_LANE_0_1`, which manipulates the write-enable mask expression rather than clearly writing a disabled value with write-enable. `data-lanes` semantics are compact and easy to misconfigure; lane values greater than one mean bifurcation on RK3568, while RK3588 treats values 3 and 4 as specific bifurcation bits. Poll timeouts are 500 microseconds with no sleep interval, making marginal refclk/power failures show up as init errors.

Test signals: RK3568 aggregation and bifurcation DTs, RK3588 aggregation, lane 0/1 and lane 2/3 bifurcation, optional pipe-grf presence/absence, RX common-refclk-mode arrays of lengths 1-4, RC and EP mode requests, missing optional reset behavior, clock enable failure cleanup, SRAM init timeout logs, and PCIe Gen3 link training after repeated init/exit cycles.

# sources/distributed-fs/ceph-client/drivers/phy/rockchip/phy-rockchip-typec.c

Purpose: this RK3399 Type-C PHY driver controls a dual-PLL PHY shared by USB3 and DisplayPort alternate mode. It exposes separate child PHYs for `usb3-port` and `dp-port`, reads extcon cable state/properties to choose USB, DP, or mixed USB3+DP operation, and programs lane assignment and orientation.

Important APIs, types, and functions: `struct rockchip_typec_phy` stores MMIO base, extcon, GRF regmap, core/ref clocks, three resets, per-port GRF config, a mutex, flip orientation, and active mode bits. `struct rockchip_usb3phy_port_cfg` maps RK3399 GRF offsets for each Type-C PHY instance. `tcphy_phy_init()` performs the common hardware bring-up; `tcphy_phy_deinit()` tears it down; `tcphy_get_mode()` translates extcon state into `MODE_UFP_USB`, `MODE_DFP_USB`, and `MODE_DFP_DP`; `rockchip_usb3_phy_power_on/off()` and `rockchip_dp_phy_power_on/off()` are the child PHY operations.

Control flow: probe matches the resource address to one of two RK3399 port configs, parses GRF/clocks/resets, asserts resets and selects external PSM in `typec_phy_pre_init()`, optionally gets extcon, creates PHYs for available `dp-port` and `usb3-port` children, and registers a simple provider. USB3 power-on locks the mutex, gets mode/orientation from extcon, falls back to USB2 if DP-only, initializes the PHY if disconnected, waits for pipe ready via GRF status, enables USB3 host routing, and records USB mode bits. DP power-on requires DP mode, reinitializes if all four lanes are needed for DP-only, selects DP in GRF, waits for DP A2, calibrates AUX, enters A0, and records DP active. Power-off paths clear mode bits and deinitialize only when no USB/DP user remains.

State and persistence behavior: `mode` is a bitmask refstate for USB and DP users, protected by `lock`; `flip` is refreshed from extcon polarity on each mode detection. Clocks and resets are active only while at least one mode bit is set. Register state is reprogrammed on each fresh init. There is no runtime PM callback despite `pm_runtime_enable()`, so active power is managed manually through clocks/resets.

Dependencies and integration points: the driver depends on extcon states/properties (`EXTCON_USB`, `EXTCON_USB_HOST`, `EXTCON_DISP_DP`, `EXTCON_PROP_USB_SS`, `EXTCON_PROP_USB_TYPEC_POLARITY`), Rockchip GRF syscon, child OF nodes named `dp-port` and `usb3-port`, reset controls `uphy`, `uphy-pipe`, `uphy-tcphy`, and clocks `tcpdcore` and `tcpdphy-ref`. It integrates with USB3 host/device and DRM DP consumers through separate PHY handles over one shared hardware block.

Risks: mode selection depends on extcon property availability; missing polarity or superspeed properties fail power-on. The comments document several undocumented AUX calibration steps, indicating board/hardware sensitivity. Mixed USB3+DP lane assignment depends on `flip`; a wrong polarity report swaps USB/DP lanes. The shared `mode` bitmask avoids full deinit while another user is active, but it does not track per-consumer counts, so duplicate power-on/off calls can clear state too early. `pm_runtime_enable()` is not paired with runtime callbacks or get/put usage. DP-only reinitialization intentionally disrupts an already active non-DP-only mode to claim all four lanes.

Test signals: extcon state matrix coverage for USB device, USB host, DP-only, DP+USB2, and USB3+DP; polarity flip and non-flip lane mapping; USB pipe ready timeout; DP A2/A0 transition timeout; AUX channel operation after calibration; repeated USB and DP power ordering in both directions; fallback to USB2 for DP-only mode when USB3 is requested; and behavior with missing extcon, missing properties, or absent child nodes.
