# sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/dev-support/jdiff/Apache_Hadoop_HDFS_2.7.2.xml

## Purpose

This XML is the JDiff public API baseline for `Apache Hadoop HDFS 2.7.2`, generated by the `IncludePublicAnnotationsJDiffDoclet` on 2016-08-24. It is not runtime code; it is a machine-readable contract used by the Hadoop build/release tooling to compare HDFS public APIs across releases. Unlike later files in this group, it contains a broad HDFS client, protocol, inotify, cache, encryption, and JMX surface: 42 packages, 29 public types, 159 methods, 23 constructors, and 6 fields.

## Important APIs, Types, And Functions

The `org.apache.hadoop.fs` entries expose block locality and volume identity wrappers: `BlockStorageLocation` extends `BlockLocation` and adds `getVolumeIds()`, `HdfsVolumeId` implements `VolumeId`, and `CacheFlag` models cache operation flags. The `org.apache.hadoop.hdfs.client` section is the densest client API: `HdfsAdmin` wraps administrative RPCs for namespace quota, storage-type quota, snapshots, cache directives, cache pools, encryption zones, inotify event streams, and storage policies; `HdfsDataInputStream` and `HdfsDataOutputStream` expose block, datanode, visible-length, read-statistics, replication, and `hsync(EnumSet<SyncFlag>)` hooks; `HdfsUtils.isHealthy(URI)` provides a health probe.

The inotify contract is represented by `DFSInotifyEventInputStream`, `Event`, `EventBatch`, and `MissingEventsException`. Polling APIs return `EventBatch` and expose transaction IDs through `getTxid()` and lag estimates through `getTxidsBehindEstimate()`. Protocol data types include `CacheDirectiveInfo`, `CacheDirectiveEntry`, `CacheDirectiveStats`, `CachePoolInfo`, `CachePoolEntry`, `CachePoolStats`, and `EncryptionZone`, with builder-style setters, validation helpers, identity methods, and stringification. Server integration surfaces include `JournalNodeMXBean`, `DataNodeMXBean`, `NameNodeMXBean`, `NameNodeStatusMXBean`, `AuditLogger`, `HdfsAuditLogger`, and `INodeAttributeProvider`.

## Control Flow And State

The XML itself has no executable control flow. Its effective flow is declarative: an `<api>` root names the release and JDiff version, `<package>` elements group public symbols, and nested `class`, `interface`, `constructor`, `method`, `field`, `param`, `exception`, and `doc` elements describe callable signatures and documentation. State is the serialized API state of HDFS 2.7.2, including method signatures, checked exceptions, deprecation status, inheritance, and public field constants such as `CachePoolInfo.DEFAULT_LIMIT` and `RELATIVE_EXPIRY_NEVER`.

## Dependencies And Integration Points

The generation command embeds the build classpath and reveals dependencies on Hadoop annotations/common/auth, SLF4J, Apache HTTP components, Zookeeper, Curator, Jetty 6, Jersey 1.x, Jackson 1.x, protobuf, Netty, HTrace 3.x, LevelDB JNI, and Hadoop crypto classes. The actual integration point is Hadoop's JDiff release process: this file is consumed with adjacent XML snapshots under `dev-support/jdiff` to detect public API additions, removals, or incompatible signature changes. It also documents external extension points that downstream users may implement, especially audit logging, inode attribute providers, MXBeans, and admin/client APIs.

## Risks And Test Signals

The file is a compatibility fixture, so risk is mostly drift: accidental edits, stale generated metadata, or mismatches with the corresponding 2.7.2 sources could produce false API-diff results. The embedded absolute classpath is build-machine-specific and should not be treated as reproducible configuration. Useful validation signals are XML well-formedness, stable `<api name="Apache Hadoop HDFS 2.7.2">`, the expected package/type counts, successful JDiff comparisons against neighboring release XMLs, and release tests that verify public annotated APIs are present or intentionally changed.

# sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/dev-support/jdiff/Apache_Hadoop_HDFS_2.8.0.xml

## Purpose

This XML is the JDiff public API baseline for `Apache Hadoop HDFS 2.8.0`, generated on 2017-03-17. It records a much smaller HDFS module public surface than the 2.7.2 snapshot because most client/protocol APIs had moved to related artifacts, leaving package declarations plus server extension interfaces and management hooks.

## Important APIs, Types, And Functions

The file declares 38 packages and 4 public types. `JournalNodeMXBean.getJournalsStatus()` exposes JMX status for JournalNode journals. `AuditLogger.initialize(Configuration)` and `AuditLogger.logAuditEvent(...)` define the NameNode audit extension point. `HdfsAuditLogger` implements `AuditLogger` and adds overloads that carry `CallerContext`, `UserGroupInformation`, and `DelegationTokenSecretManager` so audit logs can include caller context and delegation token tracking IDs. `INodeAttributeProvider` exposes `start()`, `stop()`, path-based `getAttributes(...)` overloads for `String`, `String[]`, and `byte[][]`, and `getExternalAccessControlEnforcer(...)` for replacing or wrapping the default permission enforcer.

## Control Flow And State

There is no runtime control flow in this file. The serialized flow is the JDiff schema: release metadata, package list, type entries, method signatures, parameter lists, and doc CDATA. The state captured is the public annotated API for the HDFS module at 2.8.0, including abstractness, visibility, inheritance, deprecation status, and the package-level HDFS documentation describing a distributed `FileSystem` with single-writer append semantics.

## Dependencies And Integration Points

The generation command shows integration with Hadoop annotations, Hadoop common/auth, `hadoop-hdfs-client-2.8.0`, SLF4J, HTTP components 4.5.x, Zookeeper/Curator, Jetty 6, Jersey 1.x, Jackson, protobuf, Netty, and HTrace core4. Operational integration points are the NameNode audit pipeline, inode attribute/access-control extension hooks, JournalNode JMX reporting, and the JDiff compatibility checks used by release tooling.

## Risks And Test Signals

Because this is a compatibility fixture, the main risks are malformed XML, unintentional hand edits, and incomplete API coverage after the HDFS client split. Audit APIs are particularly sensitive because `logAuditEvent` runs in a NameNode critical section and the doc explicitly requires quick return. Test signals include XML parsing, expected counts of 38 packages and 12 methods, JDiff comparisons against 2.7.2 and later 2.8.x files, and integration tests for audit logging, external access control, and JournalNode MXBean status.
