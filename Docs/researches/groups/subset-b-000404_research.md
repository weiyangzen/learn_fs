# sources/control-plane/longhorn/chart/questions.yaml

Purpose: Defines Rancher catalog questions for installing the Longhorn Helm chart. It is UI-facing metadata rather than a Kubernetes manifest: the file groups chart values into form controls for image selection, private registry credentials, default Longhorn settings, default StorageClass settings, ingress/HTTPRoute exposure, default backup resources, PSP/Windows/network-policy options, and related validation hints.

Important APIs/types/functions: The main schema is the Rancher `questions` list. Each item maps a `variable` to a Helm value key, sets a `type` such as `boolean`, `string`, `password`, `int`, `enum`, or `hostname`, and may define `default`, `label`, `description`, `group`, `required`, `min`, `max`, `options`, `show_if`, `show_subquestion_if`, and nested `subquestions`. Top-level `categories: [storage]` and `namespace: longhorn-system` classify the chart. Important value namespaces include `image.longhorn.*`, `image.csi.*`, `privateRegistry.*`, `defaultSettings.*`, `persistence.*`, `ingress.*`, `httproute.*`, `service.ui.*`, `defaultBackupStore.*`, `enablePSP`, `global.cattle.windowsCluster.enabled`, and `networkPolicies.*`.

Control flow: There is no executable flow. Rancher evaluates visibility and validation metadata, then writes selected answers into Helm values. `image.defaultImage`, `privateRegistry.createSecret`, `longhorn.default_setting`, `persistence.*.enable`, `ingress.enabled`, `httproute.enabled`, `service.ui.type`, and `longhorn.default_resource` gate subquestions. Once Helm values are produced, other chart templates consume them: image fields feed manager and CSI workloads, default settings feed the `longhorn-default-setting` ConfigMap, persistence fields feed the StorageClass, service and ingress fields feed UI exposure templates, and backup store fields should feed `default-resource.yaml`.

State and persistence behavior: This file persists no cluster state directly. Its answers become Helm release values and may indirectly create durable Longhorn cluster defaults, StorageClasses, secrets, ConfigMaps, routes, and services. Several settings are explicitly first-install or detached-volume sensitive, especially `longhorn.default_setting`, `longhorn.default_resource`, data-engine options, replica and node scheduling policies, storage network, taint toleration, node selector, and CPU/memory/resource knobs.

Dependencies and integration points: The file must remain aligned with `values.yaml`, `README.md`, and templates under `sources/control-plane/longhorn/chart/templates`. It also encodes Longhorn manager and CSI sidecar image names/tags, Rancher private-registry behavior, OpenShift PSP/SCC and route behavior, Kubernetes Ingress/Gateway API fields, Longhorn default-setting names, StorageClass parameters, and backup target defaults.

Risks: The largest risk is drift from real chart values. One concrete mismatch is present: the question variable `defaultBackupStore.backupstorePollInterval` does not match `values.yaml` and `templates/default-resource.yaml`, which use `defaultBackupStore.pollInterval`; users setting this question may not affect the rendered ConfigMap. Type drift is also likely because many Longhorn settings use JSON-like string defaults such as `{"v1":"3","v2":"3"}` while others use booleans or ints. Several warnings describe unsafe live changes, but Rancher questions cannot enforce operational preconditions like all volumes being detached. Image tag defaults and sidecar versions must be kept current with the release.

Test signals: Useful checks are `helm lint`, `helm template` with representative Rancher answer sets, schema/value-name diffing against `values.yaml`, and UI smoke tests for gated subquestions. Specific regression tests should assert that every `questions.yaml` variable path exists in `values.yaml` or is an intentional Rancher-only flag, and should cover the private-registry, default-setting, default-resource, ingress, HTTPRoute, StorageClass, OpenShift, and Windows branches.

# sources/control-plane/longhorn/chart/templates/clusterrole.yaml

Purpose: Renders cluster-scoped RBAC for Longhorn. The primary `ClusterRole` named `longhorn-role` grants the Longhorn manager broad access to Kubernetes core resources, storage APIs, snapshot APIs, Longhorn CRDs, admission webhooks, RBAC objects, leases, metrics, and discovery resources. When OpenShift support is enabled, it also renders `longhorn-ocp-privileged-role` for use of privileged and anyuid security context constraints.

Important APIs/types/functions: Kubernetes API types are `rbac.authorization.k8s.io/v1` `ClusterRole` objects. Helm helpers include `include "longhorn.labels" . | nindent 4` and the conditional `.Values.openshift.enabled`. Rule groups cover `apiextensions.k8s.io/customresourcedefinitions`, core pods/secrets/services/events/PVs/PVCs/nodes/namespaces, `apps` controllers, `batch` jobs, `policy` PDBs, `scheduling.k8s.io` priority classes, `storage.k8s.io` storage classes and CSI attachment resources, `snapshot.storage.k8s.io` snapshot resources, all listed `longhorn.io` resources and statuses, `coordination.k8s.io/leases`, `metrics.k8s.io` pods/nodes, `apiregistration.k8s.io/apiservices`, admission webhook configurations, RBAC roles/bindings and cluster roles/bindings, and `discovery.k8s.io/endpointslices`.

Control flow: Helm emits `longhorn-role` unconditionally. The Longhorn manager service account is bound to it by `clusterrolebinding.yaml`, and runtime controllers then use those permissions to install/manage CRDs, reconcile Longhorn custom resources, coordinate storage and CSI objects, inspect pods/nodes, publish events, register webhooks, and manage selected RBAC objects. If `.Values.openshift.enabled` is true, Helm appends a second ClusterRole for SCC `use` permissions; matching subjects are bound in the OpenShift branch of `clusterrolebinding.yaml`.

State and persistence behavior: The rendered ClusterRoles are persistent cluster-level RBAC resources. They do not store application state, but they authorize controllers that mutate persistent Kubernetes and Longhorn resources. RBAC changes during chart upgrade can immediately affect reconciliation, webhook lifecycle, CRD management, snapshot integration, and CSI attachment behavior.

Dependencies and integration points: Depends on `_helpers.tpl` for labels and on `values.yaml` for `openshift.enabled`. It must stay synchronized with `crds.yaml`, manager code, CSI deployment behavior, snapshot controller APIs, Kubernetes storage API versions, and OpenShift SCC requirements. The long list of `longhorn.io` resources includes volumes, engines, replicas, engine images/frontends, nodes, instance managers, share managers, backing images, backups, recurring jobs, orphans, snapshots, support bundles, system backups/restores, volume attachments, and backup backing images.

Risks: The role is intentionally broad, including wildcards on CRDs, storage resources, snapshot resources, Longhorn resources, and cluster roles/bindings. That increases blast radius if the manager service account is compromised. Missing new Longhorn CRDs or new Kubernetes resources will break reconciliation after upgrades. The OpenShift finalizer entries are conditional, so OpenShift-specific delete/finalizer flows depend on enabling the chart flag. Admission webhook create/patch/delete permissions are sensitive and should be reviewed whenever webhook names or lifecycle changes.

Test signals: `helm template` should verify both normal and OpenShift output. RBAC can be validated with `kubectl auth can-i --as system:serviceaccount:<ns>:longhorn-service-account` for manager operations and with end-to-end upgrade tests that exercise CRD creation, webhook registration, snapshot/CSI flows, and Longhorn CR status updates. Static review should compare the `longhorn.io` resource list with CRDs in `crds.yaml`.

# sources/control-plane/longhorn/chart/templates/clusterrolebinding.yaml

Purpose: Binds chart service accounts to the cluster-scoped roles required by Longhorn. It connects `longhorn-service-account` to `longhorn-role`, grants the support bundle service account `cluster-admin`, and optionally binds Longhorn service accounts to OpenShift SCC permissions.

Important APIs/types/functions: Kubernetes type is `rbac.authorization.k8s.io/v1` `ClusterRoleBinding`. Helm helpers are `include "longhorn.labels"` for labels and `include "release_namespace" .` for subject namespaces, so `namespaceOverride` is respected. Bindings are `longhorn-bind` to `ClusterRole/longhorn-role`, `longhorn-support-bundle` to `ClusterRole/cluster-admin`, and conditional `longhorn-ocp-privileged-bind` to `ClusterRole/longhorn-ocp-privileged-role`.

Control flow: Helm emits the manager binding and support-bundle binding unconditionally. The manager binding supplies the permissions defined in `clusterrole.yaml` to the service account used by `daemonset-sa.yaml`. The support-bundle binding authorizes support bundle collection with `cluster-admin`. If `.Values.openshift.enabled` is true, Helm also binds `longhorn-service-account`, `longhorn-ui-service-account`, and the namespace `default` service account to the OpenShift privileged SCC role, with an inline note that the support bundle agent uses the default service account.

State and persistence behavior: These are persistent cluster-level authorization relationships. They store no Longhorn data, but they define the effective permissions of Longhorn manager, UI, and support bundle workloads for the lifetime of the Helm release. Namespace changes through `namespaceOverride` change the subject identities, not the cluster-scoped binding names.

Dependencies and integration points: Depends on service accounts rendered by `serviceaccount.yaml` and consumed by `daemonset-sa.yaml`, `deployment` templates, UI templates, and support bundle resources. Depends on `clusterrole.yaml` for `longhorn-role` and the conditional OpenShift role. The `cluster-admin` role is a Kubernetes built-in assumption and not rendered by this chart.

Risks: The support bundle service account receives `cluster-admin`, which is a deliberate but high-privilege grant. The OpenShift branch grants SCC use to the namespace default service account, broadening privileges beyond named Longhorn accounts because the support-bundle agent uses it. ClusterRoleBinding names are static, so multiple releases in one cluster can collide unless the chart is constrained to a single release. If `namespaceOverride` diverges from the actual namespace where service accounts are created, subjects can point at the wrong identities.

Test signals: Render tests should cover default and OpenShift modes and confirm subject namespaces match `release_namespace`. Runtime checks should verify `longhorn-service-account` can perform manager operations and support bundle creation works without auth failures. Security review should flag `cluster-admin` and default-service-account SCC binding as expected exceptions rather than accidental privilege grants.

# sources/control-plane/longhorn/chart/templates/crds.yaml

Purpose: Installs the Longhorn `longhorn.io` CustomResourceDefinitions used by the manager and controllers. The header notes it is generated from `github.com/longhorn/longhorn-manager/k8s/pkg/apis` and copied into the chart, so it is not intended as a hand-authored standalone manifest. It defines the persistent Kubernetes API surface for Longhorn storage, backup, engine, node, snapshot, support, and system recovery objects.

Important APIs/types/functions: Every object is an `apiextensions.k8s.io/v1` `CustomResourceDefinition` with Helm-rendered `longhorn.labels` and `longhorn-manager: ""` labels. All CRDs are in group `longhorn.io`, scope `Namespaced`, version `v1beta2`, `served: true`, `storage: true`, and expose `status` subresources. Defined resources are `BackingImageDataSource`, `BackingImageManager`, `BackingImage`, `BackupBackingImage`, `Backup`, `BackupTarget`, `BackupVolume`, `EngineFrontend`, `EngineImage`, `Engine`, `InstanceManager`, `Node`, `Orphan`, `RecurringJob`, `Replica`, `Setting`, `ShareManager`, `Snapshot`, `SupportBundle`, `SystemBackup`, `SystemRestore`, `VolumeAttachment`, and `Volume`. Each schema includes OpenAPI `spec` and `status` fields plus `additionalPrinterColumns` for kubectl output.

Control flow: Helm applies CRDs before or with the rest of the release, making the Longhorn API types available to controllers and users. Longhorn manager then creates and reconciles namespaced CRs through Kubernetes watches and status updates. The custom resources represent desired state in `spec` and observed state in `status`: volumes and engines track attachment, frontend, replicas, backup/restore, snapshots, migration, and robustness; replicas and instance managers track per-node process state; backup resources track target, snapshot, upload, sync, progress, error, and URL fields; nodes track disks, scheduling, conditions, region/zone, and disk health; settings store configured values and applied state.

State and persistence behavior: These CRDs define durable cluster state. Kubernetes stores CR instances and status in etcd, while Longhorn controllers use them as the source of truth for storage lifecycle. `status` subresources separate controller-observed state from user spec writes. Enumerations constrain important values such as data engines `v1`/`v2`, backing image source types, backup modes, frontend types, recurring job tasks, volume access modes, data locality, replica balancing policies, snapshot integrity modes, and trim/offline rebuild flags. Some fields include immutability validation messages, for example volume backing image and encryption.

Dependencies and integration points: Depends on Kubernetes CRD v1 support and Helm label templating. It must be consistent with Longhorn manager Go API structs, generated clients/informers, RBAC in `clusterrole.yaml`, admission webhooks, UI/API clients, backup infrastructure, CSI controller behavior, snapshot integration, and upgrade/migration logic. The CRD inventory also drives RBAC resource names and informs cleanup/uninstall behavior.

Risks: Generated CRDs are large and easy to drift from controller code if the generation/copy process is skipped. Because every CRD stores `v1beta2`, schema mistakes can affect persisted production state and upgrade compatibility. CRD upgrades can be disruptive if fields, enum values, validations, or status shapes change without conversion planning. The chart labels CRDs through Helm templating, so this template cannot be applied directly with plain `kubectl apply` as the header warns. Broad schemas with nullable maps and nested status objects should be validated against server-side OpenAPI limits and Kubernetes version compatibility.

Test signals: Generation tests should diff this file against the manager API source output. `helm template` and `helm install --dry-run` should ensure all CRDs render valid YAML with labels. Cluster tests should create representative CRs for each kind and verify status subresource updates, kubectl printer columns, enum validation, and manager reconciliation. Static checks should compare the CRD resource list with `clusterrole.yaml` and generated client code.

# sources/control-plane/longhorn/chart/templates/daemonset-sa.yaml

Purpose: Renders the Longhorn manager DaemonSet plus the `longhorn-backend` Service. The DaemonSet runs one privileged `longhorn-manager` pod per eligible node, passes the manager all required component image references, mounts host paths needed for storage operations, exposes manager and webhook ports, and pre-pulls the share-manager image.

Important APIs/types/functions: Kubernetes types are `apps/v1` `DaemonSet` and `v1` `Service`. Helm helpers include `longhorn.labels`, `release_namespace`, `registry_url`, and `longhorn.timezoneEnv`. Key values include `image.longhorn.manager/engine/instanceManager/shareManager/backingImageManager/supportBundleKit`, `global.imageRegistry`, `privateRegistry.registrySecret`, `image.pullPolicy`, `longhornManager.log.format`, `preUpgradeChecker.upgradeVersionCheck`, `longhornManager.resources`, `longhornManager.priorityClass`, `longhornManager.tolerations`, `global.tolerations`, `global.nodeSelector`, `longhornManager.nodeSelector`, `global.cattle.windowsCluster.*`, `enableGoCoverDir`, `annotations`, `longhornManager.updateStrategy`, `service.manager.type`, and `service.manager.nodePort`.

Control flow: Helm builds the manager image from registry precedence `global.imageRegistry`, private/system `registry_url`, then image-specific registry, and injects the final repository/tag into the container. The manager command runs `longhorn-manager -d [ -j ] daemon` with flags for engine, instance manager, share manager, backing image manager, support bundle manager, manager image, service account, and optional upgrade version check. Kubernetes schedules the DaemonSet with optional tolerations/node selectors and update strategy. The service selects pods with `app: longhorn-manager` and exposes port 9500 as `manager`; the pod also opens ports 9502 and 9503 for admission webhook and recovery backend.

State and persistence behavior: The DaemonSet itself is desired cluster state. Manager pods mount host `/boot`, `/dev`, `/proc`, `/etc`, and `/var/lib/longhorn` into the container; `/var/lib/longhorn` uses bidirectional mount propagation, so pod operations affect host storage state. Optional `/go-cover-dir` persists coverage data on the host. Environment variables inject pod name, namespace, IP, node name, optional distro, optional coverage directory, and optional timezone. The optional `longhorn-grpc-tls` secret is mounted at `/tls-files/` and marked optional.

Dependencies and integration points: Requires `longhorn-service-account` and the RBAC from `clusterrole.yaml`/`clusterrolebinding.yaml`. It integrates with registry helper logic, private registry secrets, Longhorn default settings and image values, admission webhook clients, backend service consumers, CSI deployer behavior, support bundle generation, OpenShift/Windows scheduling values, and Kubernetes hostPath/mount-propagation support.

Risks: The manager container is privileged and mounts sensitive host paths, so node compromise risk is inherent. Incorrect image registry precedence or missing image tags prevents startup or later system-managed component creation. Optional TLS secret behavior means the workload can start without gRPC TLS material, which must match manager expectations. Service type and nodePort values can expose the backend more broadly than intended. The pre-pull share-manager sidecar sleeps forever; resource and security policy must account for it. Windows-cluster toleration/nodeSelector merging is complex and should be tested whenever scheduling defaults change.

Test signals: `helm template` should cover default, JSON log format, private registry, global image registry, imagePullSecrets as string and list, OpenShift/Windows scheduling, coverage, priorityClass, nodeSelector/tolerations, and service nodePort branches. Runtime tests should verify manager pod readiness on `/v1/healthz` over port 9502, backend service selection on port 9500, hostPath/mount propagation behavior, and successful creation of dependent Longhorn system pods with the image flags provided here.

# sources/control-plane/longhorn/chart/templates/default-resource.yaml

Purpose: Renders a ConfigMap named `longhorn-default-resource` that carries initial default backup resource settings for Longhorn. The `default-resource.yaml` data entry can include backup target URL, backup target credential secret, and backup store poll interval for first-install default resource customization.

Important APIs/types/functions: Kubernetes type is `v1` `ConfigMap`. Helm helpers are `include "release_namespace" .` for namespace and `include "longhorn.labels" .` for labels. The template uses `kindIs "invalid"` guards around `.Values.defaultBackupStore.backupTarget`, `.Values.defaultBackupStore.backupTargetCredentialSecret`, and `.Values.defaultBackupStore.pollInterval`, rendering keys `backup-target`, `backup-target-credential-secret`, and `backupstore-poll-interval` only when the value exists.

Control flow: During Helm rendering, each non-invalid backup store value is written into a YAML block string under `data.default-resource.yaml`. Longhorn manager or installation logic can then read the ConfigMap to initialize default backup resources before existing cluster resources take precedence. No Kubernetes custom resource is created directly by this template; it supplies configuration data for later Longhorn processing.

State and persistence behavior: The ConfigMap is persistent namespaced cluster state. It may influence durable Longhorn backup target configuration on first install. Because the content is a stringified YAML document, value quoting and key spelling matter. Blank or invalid values are omitted, which allows the chart to render an empty or partial `default-resource.yaml` document.

Dependencies and integration points: Depends on `values.yaml` `defaultBackupStore` fields and Rancher questions under `longhorn.default_resource`. It is conceptually paired with `default-setting.yaml`, but it is much narrower and focused on backup resources. It also integrates with any manager code that consumes the `longhorn-default-resource` ConfigMap and expects the exact dashed keys.

Risks: `questions.yaml` exposes `defaultBackupStore.backupstorePollInterval`, while this template reads `.Values.defaultBackupStore.pollInterval`; that mismatch can make the Rancher question ineffective for poll interval. Values are inserted without `quote`, so strings containing YAML-significant characters, URLs with edge cases, or secrets with special characters should be rendered and parsed carefully. The template does not conditionally omit the ConfigMap when all values are invalid, so consumers must tolerate an empty data document.

Test signals: `helm template` should verify rendering for each individual backup store field, all fields together, all fields omitted, and special-character backup target URLs/secrets. A chart metadata test should assert the Rancher question variable names match `values.yaml` and this template. Runtime tests should confirm Longhorn manager consumes `longhorn-default-resource` only at the intended lifecycle phase and applies the expected backup target, credential secret, and poll interval.
