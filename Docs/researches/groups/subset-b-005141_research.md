# sources/distributed-fs/ceph-client/drivers/platform/x86/lenovo/think-lmi.c

Purpose: Lenovo Think LMI BIOS configuration WMI driver. It binds to the Lenovo `BiosSetting` WMI GUID and exposes BIOS attributes plus authentication controls through the kernel firmware attributes class at a `thinklmi` device. User space can inspect supported BIOS settings, set new values, save pending firmware changes, manage admin/power/system/HDD/NVMe passwords, and, on supported systems, use certificate-backed authentication paths.

Important APIs, types, and functions: the file defines the Lenovo WMI GUIDs for setting enumeration, setting writes, saves, password configuration, password updates, debug commands, opcode commands, and certificate operations. `tlmi_priv` is the singleton `struct think_lmi` runtime state, protected for multi-call WMI operations by `tlmi_mutex`. `tlmi_simple_call()` is the common WMI method executor and intentionally calls the method twice to match Lenovo BIOS behavior seen from scripting interfaces. `tlmi_extract_error()` and `tlmi_errstr_to_err()` translate firmware string statuses into Linux errno values. `tlmi_setting()` queries indexed BIOS settings from the matched WMI device; `tlmi_get_bios_selections()` gets valid values for one setting; `tlmi_get_pwd_settings()` copies the password capability buffer into `struct tlmi_pwdcfg`.

Authentication sysfs: each `struct tlmi_pwd_setting` kobject exposes `is_enabled`, password length limits, `current_password`, `new_password`, `role`, `mechanism`, `encoding`, `kbdlang`, and, when relevant, HDD/NVMe `index` and `level`. `current_password_store()` only caches the current password in memory after length checks and newline stripping. `new_password_store()` requires `CAP_SYS_ADMIN`, checks `can_set_bios_password`, validates the new password length, then either uses the opcode interface (`WmiOpcodePasswordType`, optional admin password, current password, new password, final `WmiOpcodePasswordSetUpdate`) or the legacy `SetBiosPassword` string format. The opcode path has special password type strings for HDD and NVMe user/master slots.

Certificate sysfs: certificate-specific attributes are shown only when firmware advertises certificate support and only for the admin role, plus the system role on multi-certificate systems. `certificate_store()` handles three flows: empty input clears the installed certificate by signing the DMI product serial, installed certificates are updated with a signature, and fresh installs require an enabled password for the admin certificate. ThinkCenter mode uses a different set of certificate GUIDs and a different install string including password encoding and keyboard language. `cert_to_password_store()` converts certificate authentication back to password authentication using a previously staged signature. `signature_store()` and `save_signature_store()` cache signatures in memory for subsequent set/save operations. `certificate_thumbprint_show()` queries MD5, SHA1, and SHA256 thumbprints, optionally prefixed with `SVC` or `SMC` for multi-certificate systems.

BIOS attribute sysfs: each `struct tlmi_attr_setting` kobject exposes `display_name`, `current_value`, optional `possible_values`, and `type`. `current_value_show()` re-queries the WMI setting at read time, splits the `Item,Value` firmware string, and removes workstation option tails after a semicolon. `current_value_store()` strips newlines, rejects writes when setting writes are unsupported, and blocks additional bulk writes after a bulk save already made reboot necessary. It then chooses among certificate, opcode, and legacy password authentication. Certificate mode requires both the admin signature and save signature, writes through the certificate setting GUID, and either marks a bulk save as required or saves immediately. Opcode mode stages the admin password through `OpcodeIF`, writes the setting through `SetBiosSetting`, and saves immediately unless in bulk mode. Legacy mode formats the admin password, encoding, and keyboard language directly into the setting and save strings. Successful first change marks `pending_changes` and emits a `KOBJ_CHANGE` uevent from the firmware attributes class device.

Save/debug interfaces: `save_settings` exposes `single`, `bulk`, and write-only-like `save` command strings through one RW attribute. In single mode each setting write saves immediately. In bulk mode setting writes only stage changes by setting `save_required`; writing `save` performs the save and sets `reboot_required`. `pending_reboot_show()` reports `pending_changes`, which means the driver has observed a successful change and user space may need a reboot. `debug_cmd_store()` is only exposed when the firmware has the debug GUID and the module parameter `debug_support` is true; it formats an optional admin password and sends arbitrary debug commands, then marks pending changes on success.

Probe and setup control flow: `tlmi_probe()` calls `tlmi_analyze()` and then `tlmi_sysfs_init()`. `tlmi_analyze()` detects feature capabilities with `wmi_has_guid()`, including ThinkCenter-specific certificate GUIDs, then scans up to `TLMI_SETTINGS_COUNT` indexed settings using `tlmi_setting()`. For each valid non-empty item it allocates `struct tlmi_attr_setting`, stores the firmware name, converts `/` to `\` in the sysfs display name, obtains possible selections either through `GetBiosSelections` or by parsing an older `[Optional:...]` suffix, and converts comma-separated choices to semicolon-separated firmware-attributes choices. It then reads password settings, creates admin and power password objects, and, when opcode support exists, creates system, HDD, and NVMe password objects. Password state bits initialize `pwd_enabled`, HDD/NVMe first active indexes are derived with `ffs()`, and certificate-installed flags are initialized from password mode/state bits.

Sysfs object lifecycle: `tlmi_sysfs_init()` creates the `thinklmi` device in `firmware_attributes_class`, creates `attributes` and `authentication` ksets, adds a kobject for every valid BIOS setting, adds global `pending_reboot`, `save_settings`, and optional `debug_cmd` files, then adds authentication kobjects for Admin, Power-on, and opcode-only System/HDD/NVMe entries. Attribute visibility callbacks hide unsupported certificate attributes, hide HDD/NVMe-only controls from other roles, hide possible values when absent, and hide encoding/kbdlang controls when opcode support makes them unnecessary. `tlmi_release_attr()` removes global files, drops all kobjects from the ksets, unregisters the ksets, and frees cached admin signatures. `tlmi_remove()` calls that release helper and unregisters the class device.

State and persistence behavior: all driver state is global because the WMI driver is effectively singleton for the Lenovo BIOS setting GUID. Persistent firmware state lives in BIOS variables changed via WMI and only takes effect after the platform-specific save/reboot rules. Passwords and signatures written to sysfs are stored in kernel memory only and are not persisted by the driver; they are used to authenticate later WMI calls. `pending_changes`, `save_required`, `reboot_required`, `save_mode`, capability flags, and per-setting/per-auth kobjects drive the exposed state. `tlmi_mutex` serializes compound WMI command sequences so two sysfs writers do not interleave staged opcode/password/save calls.

Dependencies and integration points: depends on ACPI/WMI (`wmi_query_block()`, `wmidev_block_query()`, `wmi_evaluate_method()`, `wmi_has_guid()`), DMI product serial for certificate clear, Linux kobject/kset sysfs infrastructure, the firmware attributes class, capabilities (`CAP_SYS_ADMIN`) for sensitive writes, and kernel string/memory helpers. It integrates with the WMI bus through `tlmi_id_table` matching `LENOVO_BIOS_SETTING_GUID` and registers as a module WMI driver named `think-lmi`.

Risks and edge cases: sensitive password and signature data are cached in ordinary allocations; only one local password buffer is freed with `kfree_sensitive()`, so memory disclosure hardening is limited. The password length check in `current_password_store()` uses raw `strlen(buf)` before newline stripping, which means a sysfs newline counts against firmware limits. `strscpy(setting->password, buf, setting->maxlen)` uses the firmware max length as the destination size instead of the full buffer size, so exactly maximum-length passwords may be truncated depending on how `maxlen` is interpreted. `tlmi_simple_call()` deliberately executes successful methods twice, which is firmware-workaround behavior but raises the blast radius if a GUID is not idempotent. `tlmi_analyze()` assumes `pwd_system` exists when non-ThinkCenter certificate support initializes `pwd_system->cert_installed`; a platform advertising certificate GUIDs without opcode support would be unsafe. Several multi-step sysfs paths rely on previously cached passwords/signatures and return firmware errors only after partial staging through opcode commands. `tlmi_release_attr()` frees only admin signatures, while other password objects may also receive signatures on multi-certificate systems, creating a likely leak on unload.

Test signals: compile with WMI, ACPI, DMI, and firmware attributes enabled; load on systems with and without opcode, certificate, debug, and `GetBiosSelections` GUIDs; inspect `/sys/class/firmware-attributes/thinklmi/attributes` and `authentication` object visibility; read every `current_value` and `possible_values`; set a harmless BIOS setting in single mode and verify a save plus pending change uevent; repeat in bulk mode and ensure `save_required`, `save`, `reboot_required`, and post-save write blocking behave as intended; test password update/clear paths for admin, power-on, HDD, and NVMe roles with valid and invalid lengths/indexes/levels; test certificate install/update/clear/thumbprint/cert-to-password on ThinkPad and ThinkCenter GUID variants; unload/reload under KASAN/KMEMLEAK to catch signature and kobject cleanup problems; fuzz malformed firmware strings for missing commas, duplicate names, `Reserved`, slashes, option sections, and unexpected WMI return object types.

# sources/distributed-fs/ceph-client/drivers/platform/x86/lenovo/think-lmi.h

Purpose: private data-model header for the Lenovo Think LMI BIOS configuration driver. It defines the shared constants, enums, and structs used by `think-lmi.c` to represent firmware settings, password capabilities, authentication objects, certificate GUID sets, and the singleton driver state.

Important APIs, types, and constants: `TLMI_SETTINGS_COUNT` caps firmware setting enumeration at 256 indexed WMI records. `TLMI_SETTINGS_MAXLEN` sizes setting names and display names. `TLMI_PWD_BUFSIZE`, `TLMI_LANG_MAXLEN`, and `TLMI_INDEX_MAX` bound password, keyboard language, and HDD/NVMe index data. `struct tlmi_err_codes` maps firmware status strings to errno values. `enum encoding_option` supports ASCII and scancode password encodings. `enum level_option` distinguishes user and master HDD/NVMe password levels. `enum save_mode` models immediate single-save mode, staged bulk mode, and the `save` command token.

Password and certificate types: `struct tlmi_cert_guids` holds the platform-specific WMI GUID strings for certificate thumbprint, setting write/save, certificate-to-password, clear, update, and install operations. `struct tlmi_pwdcfg_core` mirrors the common firmware password settings buffer fields: password mode, password state bitmask, min/max length, supported encodings, and supported keyboard. `struct tlmi_pwdcfg_ext` adds ThinkStation/ThinkCenter-style HDD and NVMe user/master bitmasks. `struct tlmi_pwdcfg` combines both, and the C file copies only the bytes returned by firmware so older buffers with only the core fields still work.

Runtime object types: `struct tlmi_pwd_setting` embeds a kobject for one authentication role and stores whether the role is enabled, the staged current password, firmware password type string, user-facing role, min/max lengths, encoding, keyboard language, HDD/NVMe index, user/master level, certificate-installed state, and staged signatures for certificate operations. `struct tlmi_attr_setting` embeds a kobject for one BIOS setting and stores the WMI device, setting index, firmware name, sysfs-safe display name, and semicolon-separated possible values. `struct think_lmi` is the singleton driver state containing the WMI device, feature flags, save/reboot state, platform mode, setting/authentication arrays and ksets, cached password configuration, role pointers, and selected certificate GUID table.

Control flow role: the header has no executable flow, but its layout controls how `think-lmi.c` allocates kobjects, decides sysfs visibility, formats WMI calls, and interprets firmware capability data. The `think_lmi` feature flags are populated during WMI GUID discovery and gate all later sysfs paths. The `save_mode` enum is indexed directly by `save_mode_strings`, so enum ordering is externally visible through sysfs string matching.

State and persistence behavior: these structs hold runtime-only kernel state. BIOS settings themselves persist in firmware only after the C file sends the relevant WMI set/save methods. Password and signature buffers in `tlmi_pwd_setting` are temporary authentication material staged by sysfs writes and not persisted by this header or by the driver data model. The embedded kobjects make object lifetime dependent on kobject reference release callbacks rather than only on direct frees.

Dependencies and integration points: includes Linux types and WMI declarations for kernel integer types, `struct wmi_device`, and kobject-bearing runtime structs. The header is tightly coupled to `think-lmi.c` and the platform/x86 firmware attributes ABI; it is not a public UAPI. Firmware ABI coupling is implicit in the exact buffer layouts of `tlmi_pwdcfg_core` and `tlmi_pwdcfg_ext`.

Risks and edge cases: firmware buffer layout changes can break `struct tlmi_pwdcfg` interpretation, especially because the C file tolerates buffers larger than ThinkPad core fields but still copies into a fixed struct. Password and language fixed-size buffers require every caller to pass correct destination sizes and strip sysfs newlines. `TLMI_INDEX_MAX` bounds accepted sysfs indexes but does not prove the selected drive index exists. `enum save_mode` includes `TLMI_SAVE_SAVE` even though normal stored mode is only single or bulk, so show paths must guard against exposing the command sentinel as active state. Certificate signatures are raw pointers with per-role ownership obligations, making cleanup correctness dependent on all users freeing the right fields.

Test signals: build the driver with structure layout warnings enabled; exercise firmware password buffers that contain only core fields and buffers with extended HDD/NVMe fields; verify sysfs save-mode string matching follows enum ordering; run KASAN/KMEMLEAK through kobject create/remove failure paths; test password lengths at 0, min, max, and over max; test language strings at empty, valid short values, and values at or above `TLMI_LANG_MAXLEN`; test HDD/NVMe indexes at 0, 1, `TLMI_INDEX_MAX`, and out-of-range values.
