# sources/distributed-fs/ceph-client/kernel/workqueue.c

Purpose: this file implements the Linux generic workqueue subsystem used by the Ceph client kernel source tree and the wider kernel. It provides asynchronous execution of `work_struct`, `delayed_work`, and `rcu_work` callbacks in process context or BH softirq context, backed by per-CPU worker pools, dynamically shared unbound pools, high-priority pools, ordered workqueues, freezer-aware workqueues, memory-reclaim rescuers, CPU hotplug handling, sysfs control, debug dumps, and a stall watchdog.

Important APIs/types/functions: core internal types are `struct worker_pool`, `struct pool_workqueue`, `struct workqueue_struct`, `struct wq_node_nr_active`, `struct wq_flusher`, `struct wq_barrier`, `struct work_offq_data`, and `struct wq_pod_type`. Public/exported queueing APIs include `queue_work_on()`, `queue_work_node()`, `queue_delayed_work_on()`, `mod_delayed_work_on()`, `queue_rcu_work()`, `schedule_on_each_cpu()`, and `execute_in_process_context()`. Synchronization/lifecycle APIs include `__flush_workqueue()`, `drain_workqueue()`, `flush_work()`, `flush_delayed_work()`, `flush_rcu_work()`, `cancel_work()`, `cancel_work_sync()`, `cancel_delayed_work()`, `cancel_delayed_work_sync()`, `disable_work[_sync]()`, `enable_work()`, delayed variants, `alloc_workqueue_noprof()`, `devm_alloc_workqueue_noprof()`, `alloc_workqueue_lockdep_map()`, `destroy_workqueue()`, `apply_workqueue_attrs()`, `workqueue_set_max_active()`, `workqueue_set_min_active()`, `workqueue_congested()`, `work_busy()`, `current_work()`, `current_is_workqueue_rescuer()`, `set_worker_desc()`, and diagnostic functions such as `print_worker_info()`, `show_one_workqueue()`, `show_all_workqueues()`, and `show_freezable_workqueues()`. Scheduler-facing hooks implemented here are `wq_worker_running()`, `wq_worker_sleeping()`, `wq_worker_tick()`, and `wq_worker_last_func()`.

Core data model: each `workqueue_struct` owns one or more `pool_workqueue` objects, and each pwq connects that logical workqueue to a physical `worker_pool`. Per-CPU workqueues map CPUs to per-CPU normal or high-priority pools. Unbound workqueues map CPUs or affinity pods to dynamically hashed worker pools keyed by `workqueue_attrs` including nice value, effective cpumasks, pod cpumasks, and affinity strictness. `work_struct->data` encodes pending state, queued pwq pointer, color bits for flushing, inactive/linked bits, off-queue pool id, BH marker, and disable depth. The file's lock annotation scheme is central: pool state is guarded by `pool->lock`; the global pool/workqueue registry by `wq_pool_mutex`; worker attach/detach and worker-task CPU binding by `wq_pool_attach_mutex`; mayday lists by `wq_mayday_lock`; individual workqueue state by `wq->mutex`; and many read paths are RCU-protected.

Queueing control flow: callers first atomically set `WORK_STRUCT_PENDING_BIT`. `__queue_work()` rejects illegal enqueue attempts to destroying or draining workqueues unless the enqueue is chained from a currently executing work on the same queue. It chooses a target CPU/pwq, using local or round-robin selection for unbound work, and preserves non-reentrancy by redirecting a work item back to the pool where the same work is still executing. It increments the target pwq's in-flight count for the current flush color, obtains an active slot via `pwq_tryinc_nr_active()`, and either inserts the work into `pool->worklist` and kicks the pool or marks it inactive and appends it to `pwq->inactive_works`. Delayed work stores the target workqueue and CPU in the `delayed_work` and arms an IRQ-safe timer unless the delay is zero, in which case it queues immediately. RCU work sets pending and calls `call_rcu_hurry()` so the callback queues work after a grace period.

Worker execution control flow: `kick_pool()` wakes a regular idle worker or raises/queues the appropriate BH softirq. `worker_thread()` sets `PF_WQ_WORKER`, leaves idle state, creates more workers through `manage_workers()` if no idle worker is available, assigns work with `assign_work()`, and executes scheduled linked work through `process_scheduled_works()`. `process_one_work()` records the worker in `pool->busy_hash`, snapshots lockdep state, clears pending only after the work is fully claimed, calls the work function, checks for leaked atomic/lock/RCU state, conditionally reschedules, updates completion stats, clears CPU-intensive state, records `last_func`, removes the worker from the busy hash, and decrements active/in-flight state through `pwq_dec_nr_in_flight()`. `assign_work()` prevents same-pool concurrent execution of the same work address and function by moving colliding linked works to the worker already running it. BH workqueues reuse the same processing structure in `bh_worker()` but execute from softirq context with time/restart limits to avoid trapping softirq processing.

Concurrency and throttling behavior: per-pwq `nr_active` enforces `max_active`; unbound queues additionally share per-node `wq_node_nr_active` counters so global unbound concurrency is distributed across NUMA nodes. When active capacity is unavailable, pwqs are put on `pending_pwqs` and later activated in round-robin by `node_activate_pending_pwq()` after `pwq_dec_nr_active()`. `work_color`, `flush_color`, and `nr_in_flight[]` implement flush boundaries that are not livelocked by later queueing. `WORK_STRUCT_INACTIVE` keeps over-limit work and barrier work out of active accounting. CPU-intensive work can be declared with `WQ_CPU_INTENSIVE` or automatically detected by `wq_worker_tick()` once a concurrency-managed worker exceeds `wq_cpu_intensive_thresh_us`; such workers stop contributing to `nr_running`, and another worker is kicked to preserve forward progress.

Flush, cancel, and disable flow: `__flush_workqueue()` advances the workqueue color, arms all pwqs that have in-flight work of the flush color, sleeps on the first flusher completion, and cascades queued or overflow flushers as color slots become free. `flush_work()` inserts a stack `wq_barrier` either behind a queued target work or into the currently executing worker's scheduled list, then waits for the barrier completion. `drain_workqueue()` repeatedly flushes until all pwqs are empty while setting `__WQ_DRAINING` to block external new work. Cancel and disable paths use `try_to_grab_pending()`/`work_grab_pending()` to claim pending state from idle, timer, active queue, or inactive queue states with IRQs disabled; they remove queued work, preserve pool id/off-queue flags, update in-flight accounting, and optionally wait for running callbacks. Disable state is stored in the off-queue disable field and blocks later queueing until `enable_work()` decrements it to zero.

Worker-pool lifecycle and rescue: `create_worker()` allocates a worker id, worker struct, and kthread for regular pools or a pseudo worker for BH pools, binds it to the pool's allowed CPUs, attaches it, and puts it on the idle list. Idle workers are culled after `IDLE_WORKER_TIMEOUT` if `too_many_workers()` remains true; culling runs in process context so worker affinity can be safely reset. If worker creation stalls while pending work exists, `pool_mayday_timeout()` sends mayday requests to workqueues with `WQ_MEM_RECLAIM` rescuers. `rescuer_thread()` attaches its special worker to the needy pool, executes matching works in bounded batches, detaches, drops the mayday pwq reference, and repeats until the mayday list is empty. This path is the subsystem's forward-progress guarantee under memory pressure.

Unbound attributes, affinity, and topology: `alloc_workqueue_attrs_noprof()`, `copy_workqueue_attrs()`, `wqattrs_hash()`, and `wqattrs_equal()` describe and share unbound pools. `apply_workqueue_attrs()` prepares new pwqs for every possible CPU or ordered default pwq, commits them under `wq_pool_mutex` and `wq->mutex`, and leaves old pwqs alive until references drain. CPU pod types support default, CPU, SMT, cache, cache-shard, NUMA, and system affinity scopes. `workqueue_init_topology()` builds pod mappings after topology is available, including cache shard grouping based on `wq_cache_shard_size` and SMT sibling leaders, then remaps unbound queues to per-pod pools and recalculates per-node `max_active`.

CPU hotplug, freezer, and sysfs integration: SMP hotplug disassociates per-CPU pools in `workqueue_offline_cpu()` so workers become unbound and concurrency management is disabled while a CPU is offline, then `workqueue_online_cpu()` rebinds them and updates unbound pod mappings. BH pools are per-CPU but always disassociated and get special dead-CPU draining through `workqueue_softirq_dead()`. Freezer support sets `workqueue_freezing`, reduces freezable queues' max/min active to zero via `wq_adjust_max_active()`, checks active counts in `freeze_workqueues_busy()`, and thaws by restoring saved limits. With `CONFIG_SYSFS`, workqueues marked `WQ_SYSFS` appear under `/sys/bus/workqueue/devices/` with `per_cpu`, `max_active`, and unbound controls for `nice`, `cpumask`, `affinity_scope`, and `affinity_strict`; global unbound cpumasks are exposed through the workqueue bus attributes.

Initialization and built-in workqueues: `workqueue_init_early()` allocates global cpumasks, applies housekeeping and `workqueue.unbound_cpus` restrictions, initializes BH and CPU worker pools for all possible CPUs, prepares standard unbound/ordered attrs, and allocates system queues such as `system_wq`, `system_percpu_wq`, `system_highpri_wq`, `system_long_wq`, `system_unbound_wq`, `system_dfl_wq`, freezable and power-efficient variants, BH variants, and `system_dfl_long_wq`. `workqueue_init()` creates the pwq release kthread worker, initializes the CPU-intensive threshold, creates rescuers, creates initial BH/per-CPU/unbound workers, marks `wq_online`, and starts the watchdog. `workqueue_init_topology()` is the third phase once SMP topology is available.

State and persistence behavior: all state is in kernel memory only. Work item state persists in `work_struct->data` across queue, execution, cancellation, and off-queue states so later operations can find the last pool and disable depth. Workqueue and pool objects are RCU-freed to allow lockless or RCU-protected diagnostics and `get_work_pool()` lookups. `pool_workqueue` release is punted to `pwq_release_worker` to avoid freeing under pool locks. Module/kernel parameters such as `power_efficient`, `cache_shard_size`, `debug_force_rr_cpu`, `default_affinity_scope`, `watchdog_thresh`, `panic_on_stall`, and CPU-intensive thresholds affect runtime policy, and sysfs writes can persist only as live kernel settings, not durable filesystem state.

Dependencies and integration points: this file depends on scheduler kthread hooks, task flags, timer and IRQ-work APIs, softirq/tasklet infrastructure, RCU, lockdep/debug objects, cpumasks and CPU hotplug, NUMA topology, housekeeping/isolation masks, device/sysfs registration, memory allocation/slab caches, KASAN auxiliary stack recording, tracepoints in `trace/events/workqueue.h`, freezer support, KVM guest pause detection for watchdog false positives, and kernel parameter parsing. Ceph client code using system or private workqueues depends on these semantics for callback context, ordering, memory reclaim behavior, and teardown safety.

Risks: the highest-risk areas are memory ordering around `WORK_STRUCT_PENDING_BIT`, `set_work_pool_and_clear_pending()`, and stealing pending work; active/in-flight accounting when inactive linked barrier works are canceled; lock ordering among `pool->lock`, `wq->mutex`, `wq_pool_mutex`, `wq_pool_attach_mutex`, and `wq_node_nr_active->lock`; use-after-free avoidance for work items that may free themselves during callbacks; non-reentrancy when a work item is requeued while still running; ordered workqueue pwq replacement; CPU hotplug transitions that reset `nr_running`; BH cancellation and PREEMPT_RT callback locking; rescuer correctness under memory pressure; and watchdog false positives if progress timestamps are not updated exactly when worklist heads change. Misconfigured `WQ_MEM_RECLAIM` or illegal flush dependencies can deadlock reclaim paths.

Test signals: relevant signals include kernel workqueue selftests, lockdep with forced flush/cancel dependency paths, KASAN/KCSAN on work item lifetime and data races, CPU hotplug stress with per-CPU and unbound queues, freezer suspend/hibernate tests for `WQ_FREEZABLE`, memory pressure tests proving `WQ_MEM_RECLAIM` rescuers execute queued work, sysfs mutation tests for unbound attributes and global cpumasks, RCU work tests proving grace-period ordering, BH workqueue tests including dead-CPU draining and PREEMPT_RT cancellation paths, max_active/min_active throttling tests, ordered workqueue ordering tests across attribute changes, watchdog stall injection, and tracepoint/stat monitoring through `tools/workqueue/wq_monitor.py`.

# sources/distributed-fs/ceph-client/kernel/workqueue_internal.h

Purpose: this internal kernel header exposes the private worker representation and scheduler hook declarations shared between `kernel/workqueue.c`, scheduler code, and a small set of core kernel users such as async infrastructure. It deliberately is not a general workqueue API; public users include `<linux/workqueue.h>` instead.

Important APIs/types/functions: the central type is `struct worker`, the per-kthread or BH pseudo-worker object that executes work items from a `worker_pool`. It declares `current_wq_worker()` to safely obtain the current task's `struct worker` when `PF_WQ_WORKER` is set. It also declares scheduler callbacks `wq_worker_running()`, `wq_worker_sleeping()`, `wq_worker_tick()`, and `wq_worker_last_func()`, all implemented in `workqueue.c`.

Structure details: `struct worker` has a union list node used either as `entry` on the pool idle list or `hentry` in the pool busy hash. Execution identity fields include `current_work`, `current_func`, `current_pwq`, `current_at`, `current_start`, and `current_color`. Scheduler and diagnostic fields include `sleeping`, `last_func`, `desc`, and `task`. Pool/lifecycle fields include `pool`, `node`, `flags`, `id`, `last_active`, and `scheduled`. Rescuer-only state is represented by `rescue_wq`.

Control flow: a worker is attached to a pool, sits on the idle list while `WORKER_IDLE`, moves into the busy hash while executing a work item, and may temporarily collect linked or collision-punted work on `scheduled`. During execution, `workqueue.c` updates `current_*` fields under the pool lock before calling the work function and clears them after completion. Scheduler paths use this header's hooks to adjust concurrency accounting when a worker sleeps or resumes, detect CPU-intensive workers on ticks, and expose the last executed work function for pressure-stall accounting.

State and persistence behavior: state is runtime-only and task-associated. `current_wq_worker()` relies on the task's `PF_WQ_WORKER` flag and `kthread_data(current)` rather than durable storage. The `desc` buffer persists only for the lifetime of the worker and is used in task dumps, WARN/BUG/panic output, sysrq, and `/proc` comm formatting. Rescuer workers persist for the lifetime of their `WQ_MEM_RECLAIM` workqueue.

Dependencies and integration points: the header includes `<linux/workqueue.h>`, `<linux/kthread.h>`, and `<linux/preempt.h>`, forward-declares `struct worker_pool`, and consumes task state through `current`, `in_task()`, `PF_WQ_WORKER`, and kthread data. It is tightly coupled to the lock/state annotations documented in `workqueue.c`; the field comments use the same `L`, `K`, `S`, `A`, and `I` conventions.

Risks: because this header exposes internal layout, external misuse would couple code to fragile locking and lifetime rules. Reading `current_*` fields outside the allowed contexts can race with worker teardown or work completion. Incorrect scheduler-hook calls would corrupt `nr_running` accounting and can stall or over-parallelize workqueues. Any change to `struct worker` must remain consistent with `workqueue.c`'s idle/busy hash transitions, rescuer handling, and `/proc` worker naming.

Test signals: compile coverage should include scheduler and workqueue builds with and without `CONFIG_SMP`, `CONFIG_PREEMPT_RT`, lockdep, and watchdog options. Runtime signals include correct `/proc` kworker names/descriptions, scheduler sleep/running callbacks maintaining worker-pool concurrency, PSI use of `wq_worker_last_func()`, sysrq task dumps showing current workqueue information, and no lockdep/KCSAN reports from worker field access.

# sources/distributed-fs/ceph-client/lib/842/842.h

Purpose: this header defines the private constants and operation encoding used by the kernel software implementation of IBM 842 compression/decompression. It documents the 842 compressed stream format and supplies symbolic template/action values consumed by the compressor and decompressor implementation files.

Important APIs/types/functions: this file defines no functions or structs. It exposes special operation codes `OP_REPEAT`, `OP_ZEROS`, `OP_END`, and software-only `OP_SHORT_DATA`; bit widths `OP_BITS`, `REPEAT_BITS`, `SHORT_DATA_BITS`, `I2_BITS`, `I4_BITS`, `I8_BITS`, and `CRC_BITS`; max argument values `REPEAT_BITS_MAX` and `SHORT_DATA_BITS_MAX`; action masks `OP_ACTION`, `OP_ACTION_INDEX`, `OP_ACTION_DATA`, `OP_ACTION_NOOP`, `OP_AMOUNT`, and amount constants; shorthand template actions `D2`, `D4`, `D8`, `I2`, `I4`, `I8`, and `N0`; and `OPS_MAX` for the highest regular template row.

Format semantics: an 842 stream is a sequence of 5-bit template codes. Regular templates from 0 through `0x19` select rows in the implementation's decompression operation table, where each row contains one to four actions that together emit 8 bytes. Data actions copy literal 2-, 4-, or 8-byte arguments from the compressed bitstream. Index actions copy previously emitted 2-, 4-, or 8-byte units from logical ring windows over the output buffer; their argument widths are 8 bits for I2, 9 bits for I4, and 8 bits for I8. `N0` pads unused table slots and consumes no stream argument.

Special operation control flow: `OP_REPEAT` consumes a 6-bit count and repeats the last 8 output bytes `N + 1` times. `OP_ZEROS` emits eight zero bytes with no argument. `OP_END` terminates decompression, after which padding bits may remain to align the stream. `OP_SHORT_DATA` is a software-only extension using a 3-bit byte count followed by that many literal bytes; it allows non-8-byte-aligned input lengths for the software path but intentionally creates streams that hardware 842 decompressors reject.

State and persistence behavior: the header itself is stateless. Its constants define how compressor/decompressor code interprets transient bitstream state, output-buffer history, and optional CRC fields. The ring-window behavior is implemented by indexing into the already produced output buffer rather than maintaining separate persistent dictionaries.

Dependencies and integration points: includes are kernel-oriented: module/kernel helpers, bit operations, CRC32, unaligned access helpers, and the public `<linux/sw842.h>` API. Implementation files in `lib/842` are expected to include this header for shared constants while public callers use `sw842` interfaces. The values must match the hardware 842 format except for the explicitly software-only short-data extension.

Risks: bit-width or opcode changes would break binary compatibility with existing 842 streams and hardware decompression. The `OP_SHORT_DATA` extension is useful but hazardous if a caller expects hardware-compatible output. Index actions depend on correct ring-window math and bounds checking against the output produced so far; malformed streams can otherwise reference invalid history. End-of-stream and padding handling must not overread the compressed buffer. CRC width must remain aligned with the implementation's checksum handling.

Test signals: useful tests include software compress/decompress round trips for lengths both multiple and not multiple of 8, hardware-compatible mode tests that reject short unaligned input or avoid `OP_SHORT_DATA`, decompression tests for every regular template row and each action size, malformed index and truncated-bitstream tests, repeat/zeros/end padding tests, CRC validation tests, and cross-checks against known 842 hardware-compatible vectors.
