# sources/distributed-fs/ceph-client/drivers/gpu/drm/i915/display/intel_ddi.c

Purpose: implements the Intel i915 Display Digital Interface encoder path for HDMI, DVI, DP SST, DP MST, eDP, FDI-over-DDI, Type-C/Thunderbolt, DP 2.0 128b/132b, MSO splitter, FEC, HDCP signaling bits, link training, PLL-to-port clock selection, hardware readout, hotplug recovery, and encoder/connector initialization. It is the central modeset sequencing file that maps an `intel_encoder` plus `intel_crtc_state` into DDI buffer control, transcoder function control, PHY signal levels, sink-side DP/HDMI programming, and platform-specific clock/PHY ownership.

Important APIs/types/functions: exported entry points include `intel_ddi_init()`, `intel_ddi_get_hw_state()`, `intel_ddi_connector_get_hw_state()`, `intel_ddi_enable_clock()`, `intel_ddi_disable_clock()`, `intel_ddi_get_clock()`, `hsw_ddi_*clock*()`, `icl_ddi_combo_get_pll()`, `intel_ddi_config_transcoder_func()`, `intel_ddi_enable_transcoder_func()`, `intel_ddi_disable_transcoder_func()`, `intel_ddi_enable_transcoder_clock()`, `intel_ddi_disable_transcoder_clock()`, `intel_ddi_set_dp_msa()`, `dp_tp_ctl_reg()`, `intel_ddi_clear_act_sent()`, `intel_ddi_wait_for_act_sent()`, `intel_ddi_wait_for_fec_status()`, `intel_ddi_set_vc_payload_alloc()`, `intel_ddi_compute_min_voltage_level()`, `intel_ddi_toggle_hdcp_bits()`, `intel_ddi_sanitize_encoder_pll_mapping()`, `intel_ddi_level()`, and `intel_ddi_update_active_dpll()`. The internal encoder hooks installed by `intel_ddi_init()` are the main behavioral API: compute config, late compute, pre-PLL enable, pre-enable, enable, disable, post-disable, post-PLL disable, update-pipe, get-config, sync-state, hotplug, suspend/shutdown, and power-domain acquisition. Important private helpers include `intel_ddi_transcoder_func_reg_val_get()`, DP/HDMI pre-enable paths for HSW/TGL/MTL, `intel_ddi_buf_enable()`, `intel_ddi_buf_disable()`, `intel_ddi_read_func_ctl*()`, per-platform DDI clock hooks, Type-C DP mode programming, and PHY signal-level programming for HSW/SKL, ICL combo/MG, and TGL DKL PHYs.

Control flow: initialization starts from VBT encoder data, rejects invalid or unavailable ports, handles DSI handoff, allocates `intel_digital_port`, registers a DRM encoder, assigns platform-specific clock, readout, signal-level, HPD, power-domain, Type-C, and connector hooks, initializes DDI buffer translation selection, discovers lane reversal/DDI-A lane sharing, allocates AUX when needed, and creates DP/eDP and/or HDMI connectors. Modeset computation selects eDP transcoder for port A when present, delegates HDMI/DP timing and link computation, calculates platform minimum voltage, records BXT/GLK lane latency masks, and late-computes tiled-port synchronization. Pre-PLL enable claims Type-C links, updates active DPLL tracking, acquires AUX/main-link power, and programs FIA/DPIO lane state. Pre-enable sequences diverge by output and display generation: DP paths set link params, initialize pending `intel_dp->DP`, power the panel, map/enable port clocks, acquire DDI IO power, program MG/DKL/PORT_BUF state, configure transcoders, set PHY levels, power lanes, configure sink decompression/FEC/PCON/DSC, start and stop link training, program 128b/132b payloads, and write DP MSA; HDMI paths enable TMDS output, enable clocks/IO power, configure transcoder clock and infoframes, then final enable handles sink scrambling, buffer translations, D2D link, signal levels, workarounds, lane power, and DDI buffer enable. The enable hook enables `TRANS_DDI_FUNC_CTL`, VRR, 128b/132b payload allocation, the transcoder, FEC-live wait, vblank, DP/HDMI user-visible features, and HDCP. Disable/post-disable reverses this order: HDCP and sink features are disabled, DP panels/backlight/PSR/ALPM/decompression are quiesced, transcoders and DSC/scalers are disabled, 128b/132b VC payloads are cleared with ACT waits, DDI buffers/FEC/D2D are disabled, sink FEC readiness is cleared, clocks and IO wakerefs are released, panel power is shut down, and Type-C links are released after PLL disable.

State and persistence: persistent state is mostly held in `struct intel_digital_port`, `struct intel_encoder`, `struct intel_dp`, and `struct intel_crtc_state`. The file writes MMIO state for `DDI_BUF_CTL`, `TRANS_DDI_FUNC_CTL`, `TRANS_DDI_FUNC_CTL2`, `TRANS_CLK_SEL`, `DP_TP_CTL/STATUS`, `DDI_CLK_SEL`, platform DPLL clock-gate registers, DKL/MG/combo PHY registers, `PORT_BUF_CTL1`, MSO splitter registers, audio/HDCP bits, and DP2 frequency/payload registers. `intel_dp->DP` caches the DDI buffer control word across link-training callbacks; `intel_dp->train_set[]` drives per-lane signal levels; `intel_dp->hobl_active`, `dig_port->aux_wakeref`, `dig_port->ddi_io_wakeref`, `dig_port->lane_reversal`, `dig_port->ddi_a_4_lanes`, `dig_port->max_lanes`, Type-C link mode, and connector retry counters persist across operations. Atomic CRTC state carries lane count, port clock, output type, pipe bpp, FEC, DSC, VRR, MSO, MST master, sync slaves, HDMI scrambling, infoframe, and DPLL state. No disk persistence exists, but hardware state is read back during takeover through `get_config()` and synchronized through `sync_state()`.

Dependencies and integration: depends on the i915 display stack: DP AUX/link training/MST/PCON/DSC/tunnel/test helpers, HDMI/SCDC/infoframe/audio/HDCP helpers, DPLL managers, display power domains, DMC-aware MMIO accessors, DKL/MG/combo/CX0/SNPS/LT PHY programming, Type-C/FIA mode control, VBT BIOS parsing, PSR/ALPM/backlight/panel power, VRR, scaler/pfit, hotplug, HTI reservations, and DRM connector/encoder state. Userspace-visible integration is via atomic modesets, hotplug retries, connector privacy-screen attachment, link-status recovery, and DP/HDMI sink programming. The file also integrates with hardware takeover/readout so BIOS-enabled pipes can be represented in `intel_crtc_state` before driver modesets.

Risks: sequencing is highly platform-specific; moving clock, IO power, DP_TP, DDI buffer, FEC, D2D, or sink-side operations can cause black screens, link loss interrupts, failed FEC detection, or stuck DDI buffers. Type-C paths are fragile because Thunderbolt, DP-alt, legacy, FIA lane ownership, AUX power, and DPLL selection interact. The same `TRANS_DDI_MODE_SELECT_FDI_OR_128B132B` encoding is interpreted differently depending on DP 2.0 support. MST primary encoder paths deliberately receive NULL connector state and shared link state, so HDMI/SST assumptions can break MST. Hardware readout can misclassify MST versus 128b/132b SST if active-stream state is incomplete. Register access requires correct display power wakerefs; missing wakerefs can read stale state or fault on powered-down wells. Workarounds such as ADL-P DKL loadgen, SKL/KBL chicken bits, increased HDMI disabled time, and DDI-A lane sharing are easy to regress with broad refactors.

Test signals: build with many display generations enabled and run i915 display selftests where available. Exercise HDMI/DVI, DP SST, DP MST with multiple streams, eDP, LSPCON, Type-C legacy/DP-alt/TBT, DP 2.0 UHBR, DSC, FEC, VRR, PSR/panel replay, ALPM, MSO panels, tiled port-sync displays, HDCP, audio, privacy screen, and hotplug storms. Validate modeset enable/disable ordering with register traces, link training logs, FEC live status, ACT-handled waits, vblank on/off, DDI buffer idle/active timeouts, Type-C link reset/retry behavior, and SCDC scrambling recovery. Check suspend/resume and BIOS takeover with `get_hw_state()`/`get_config()` readout, and test error handling around missing PLLs, invalid VBT ports, failed AUX channel selection, connector init failure, and DDI clocks left ungated by firmware.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/i915/display/intel_ddi.h

Purpose: declares the i915 DDI encoder interface used by the rest of the display driver. It exposes DDI clock control, hardware readout, transcoder programming, DP transport helpers, FEC/HDCP/MSA/VC payload helpers, buffer preparation, PLL mapping sanitation, and DDI encoder initialization while keeping the implementation and platform register details in `intel_ddi.c`.

Important APIs/types/functions: the header forward-declares core display types (`intel_display`, `intel_encoder`, `intel_crtc_state`, `intel_atomic_state`, `intel_connector`, `intel_dp`, `intel_dpll`, BIOS encoder data, DRM connector state, pipes, ports, transcoders) and declares functions consumed by atomic modeset code, DP/MST code, DPLL code, and initialization paths. Key API groups are DP transport (`dp_tp_ctl_reg()`, `intel_ddi_clear_act_sent()`, `intel_ddi_wait_for_act_sent()`, `intel_ddi_set_vc_payload_alloc()`), clocks (`intel_ddi_enable_clock()`, `intel_ddi_disable_clock()`, `intel_ddi_get_clock()`, `hsw_ddi_enable_clock()`, `hsw_ddi_disable_clock()`, `hsw_ddi_is_clock_enabled()`, `icl_ddi_combo_get_pll()`, `intel_ddi_port_pll_type()`, `intel_ddi_update_active_dpll()`), transcoder programming (`hsw_ddi_get_config()`, `intel_ddi_config_transcoder_func()`, `intel_ddi_enable_transcoder_func()`, `intel_ddi_disable_transcoder_func()`, `intel_ddi_enable_transcoder_clock()`, `intel_ddi_disable_transcoder_clock()`), link and signal state (`hsw_prepare_dp_ddi_buffers()`, `intel_wait_ddi_buf_idle()`, `intel_ddi_level()`, `intel_ddi_compute_min_voltage_level()`), connector/hardware state (`intel_ddi_init()`, `intel_ddi_get_hw_state()`, `intel_ddi_connector_get_hw_state()`, `intel_ddi_sanitize_encoder_pll_mapping()`), and protocol features (`intel_ddi_set_dp_msa()`, `intel_ddi_wait_for_fec_status()`, `intel_ddi_toggle_hdcp_bits()`).

Control flow: consumers include the encoder setup path, atomic enable/disable phases, DPLL readout/update paths, DP MST payload management, HDCP code, and display sanitization. The header itself has no executable control flow, but its declarations reflect the external boundaries of `intel_ddi.c`: DDI init wires hooks, atomic paths invoke the clock/transcoder/link helpers, DP code asks for transport registers and ACT waits, and sanitization/readout code asks whether clocks and encoders remain mapped to active pipes.

State and persistence: no state is stored in the header. The declared APIs operate on persistent encoder, digital-port, CRTC-state, connector, DPLL, and display-power state defined elsewhere, and on hardware MMIO registers accessed in `intel_ddi.c`.

Dependencies and integration: includes only `i915_reg_defs.h` for `i915_reg_t` and otherwise uses forward declarations to avoid coupling users to the full display type definitions. This keeps compile-time dependencies low while allowing cross-file integration with DP, MST, HDCP, DPLL, atomic modeset, and initialization code.

Risks: because this header defines DDI's public internal contract, signature changes have broad impact across i915 display code. Many functions require specific power-domain or modeset sequencing that is not expressible in the types; callers must already hold the correct atomic state, wakeref, or encoder context. Helpers returning registers or levels depend on CRTC state matching the active port and transport mode.

Test signals: compile coverage is the primary direct signal. Functional validation comes from exercising users of these declarations: modesets, MST ACT handling, FEC status waits, HDCP bit toggles, DPLL readout, encoder sanitization, and DDI initialization across supported platforms.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/i915/display/intel_ddi_buf_trans.c

Purpose: provides the platform-, PHY-, output-, and link-rate-specific DDI buffer translation tables used to program voltage swing, pre-emphasis/de-emphasis, preshoot, cursor coefficients, scaling, and HDMI defaults. It also installs the correct `encoder->get_buf_trans` callback so `intel_ddi.c` and PHY-specific signal programming can translate a CRTC state and DP training set into the right table entry.

Important APIs/types/functions: the main exported API is `intel_ddi_buf_trans_init()`, which assigns the encoder callback. The only other exported helper is `is_hobl_buf_trans()`, used by combo PHY programming to detect the special eDP HOBL table. Static data dominates the file: Haswell/Broadwell/SKL/KBL/BXT tables for HSW-style DDI registers, ICL/EHL/JSL/TGL/RKL/ADL combo PHY tables, ICL MG PHY tables, TGL/ADLP DKL PHY tables, DG2/MTL SNPS tables, MTL C10/C20 tables, and XE3 LPD LT PHY tables. Static selector helpers include `use_edp_hobl()`, `use_edp_low_vswing()`, `intel_get_buf_trans()`, per-platform `*_get_buf_trans()` families, link-rate-specific DP/eDP helpers, HDMI/DP/eDP dispatch, UHBR detection, and the SKL port-entry clamp for DDIA/DDIE.

Control flow: `intel_ddi_buf_trans_init()` inspects display generation, platform flags, PHY type, and encoder type, then stores a function pointer in `encoder->get_buf_trans`. Later callers pass an encoder and `intel_crtc_state`; the selected callback chooses a const `intel_ddi_buf_trans` table and returns its `num_entries`. Selection primarily branches by output type (HDMI versus DP/eDP), eDP VBT policy (`low_vswing`, HOBL, and `hobl_failed`), port clock thresholds such as 270 MHz and 540 MHz, UHBR versus DP 1.4, combo versus Type-C/MG/DKL/SNPS/LT PHY, and platform variants such as SKL/KBL U/Y/H/S, JSL/EHL, TGL-UY, DG1, DG2, ADL-S, ADL-P, MTL C10/C20, and XE3 LPD. HDMI tables carry `hdmi_default_entry`; DP tables map training indices to table rows via `intel_ddi_level()` in `intel_ddi.c`.

State and persistence: all translation tables are static const data. Runtime state changes only through `encoder->get_buf_trans`; the selected table is not copied. HOBL and low-vswing decisions read persistent panel VBT state from `connector->panel.vbt.edp` and the runtime `intel_dp->hobl_failed` flag. The returned table pointer is consumed immediately by DDI/PHY programming and must match the union member expected by that platform's signal-level callback.

Dependencies and integration: integrates tightly with `intel_ddi.c` signal-level code, DP training (`intel_dp_is_uhbr()` and CRTC link parameters), VBT panel policy, encoder PHY classification (`intel_encoder_is_combo()`, C10/C20, LT PHY, Type-C), and platform detection in `intel_display`. The table entry union defined in `intel_ddi_buf_trans.h` lets HSW-style DDI, BXT DPIO, ICL combo, MG, DKL, SNPS, and LT PHY programming share one callback contract despite different register fields.

Risks: table contents are hardware tuning data, so off-by-one table sizes, wrong default HDMI entries, incorrect link-rate thresholds, or using a table with the wrong union member can produce failed link training, marginal signal integrity, HDMI failures, or panel-specific regressions. eDP HOBL/low-vswing decisions depend on VBT correctness and runtime fallback. SKL/KBL entry clamping differs for ports A/E versus other ports. New platforms must be added to both this selector and the corresponding PHY programming path; otherwise `encoder->get_buf_trans` may remain unset or return incompatible data. The final `MISSING_CASE()` only reports unknown PCI IDs and does not provide a safe generic table.

Test signals: validate DP link training across voltage/pre-emphasis combinations, HDMI at low and high TMDS rates, eDP panels with and without low-vswing/HOBL VBT flags, UHBR links, Type-C DP-alt/TBT modes, and all platform PHY families. Check that `intel_ddi_level()` never indexes past `num_entries`, HDMI defaults match expected BSpec presets, and fallback after HOBL failure selects a non-HOBL table. Regression tests should include display bring-up, suspend/resume, hotplug retraining, long cable/high-rate DP, and per-platform register traces confirming the expected union fields are programmed.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/i915/display/intel_ddi_buf_trans.h

Purpose: defines the common DDI buffer translation data model shared between the static translation tables in `intel_ddi_buf_trans.c` and the DDI/PHY programming paths in `intel_ddi.c`. It abstracts several generations of Intel display PHY tuning entries behind one union and exposes initialization and HOBL identification helpers.

Important APIs/types/functions: entry structs describe the register payloads for each hardware family: `hsw_ddi_buf_trans` (`trans1`, `trans2`, `i_boost`), `bxt_ddi_buf_trans` (`margin`, `scale`, `enable`, `deemphasis`), `icl_ddi_buf_trans` (`dw2_swing_sel`, `dw7_n_scalar`, cursor/post-cursor coefficients), `icl_mg_phy_ddi_buf_trans`, `tgl_dkl_phy_ddi_buf_trans`, `dg2_snps_phy_buf_trans`, and `xe3plpd_lt_phy_buf_trans`. `union intel_ddi_buf_trans_entry` overlays these layouts. `struct intel_ddi_buf_trans` points to an entry array and stores `num_entries` plus the `hdmi_default_entry`. Public functions are `is_hobl_buf_trans()` and `intel_ddi_buf_trans_init()`.

Control flow: no executable control flow is defined here. The intended flow is that `intel_ddi_buf_trans_init()` assigns an encoder table selector; later DDI code fetches a `struct intel_ddi_buf_trans`, chooses an entry index from HDMI defaults or DP training state, and interprets the entry through the union member matching the active PHY programming callback.

State and persistence: this header owns no state. The structures represent immutable static tables in the C file and transient pointers returned through `encoder->get_buf_trans`. The only stateful aspect is semantic: the caller must know which union member is valid for the selected platform.

Dependencies and integration: includes Linux integer types and forward declares `intel_encoder` and `intel_crtc_state`. It is included by DDI core code and by platform PHY code that needs table entries. The data shapes mirror hardware register fields documented by BSpec and consumed by HSW/SKL DDI, BXT DPIO, ICL combo/MG, TGL DKL, DG2/MTL SNPS, and XE3 LPD LT PHY implementations.

Risks: the union gives compile-time convenience but little type safety; a selector bug can make a caller read `.icl` fields from an `.snps` table. `num_entries` is an 8-bit count, so callers must still clamp indices. HDMI defaults are table-local and must be set for HDMI-capable tables. Adding a new PHY requires extending both this header and all selector/programming consumers consistently.

Test signals: compile all DDI PHY families, run modesets that exercise each union member, and verify link training and HDMI default selection on representative hardware. Static review should confirm every table's `num_entries` matches its array and every selected table matches the active `set_signal_levels` implementation.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/i915/display/intel_de.c

Purpose: implements display-engine MMIO wait helpers and legacy 8-bit register accessors for i915 display code. It centralizes polling behavior for masked register values, including sleeping versus atomic delays, firmware/unlocked reads, fast and slow timeout phases, DMC wakelock protection, and timeout result reporting.

Important APIs/types/functions: private `__intel_de_wait_for_register()` performs the polling loop against an injected read function. `intel_de_wait_for_register()` wraps it with optional fast and slow timeout phases. Public wait APIs are `intel_de_wait_us()`, `intel_de_wait_ms()`, `intel_de_wait_fw_ms()`, `intel_de_wait_fw_us_atomic()`, `intel_de_wait_for_set_us()`, `intel_de_wait_for_clear_us()`, `intel_de_wait_for_set_ms()`, and `intel_de_wait_for_clear_ms()`. Legacy byte helpers are `intel_de_read8()` and `intel_de_write8()`.

Control flow: the low-level wait records an absolute raw-ktime deadline, warns if a sleepable wait is used in atomic context through `might_sleep_if()`, forces atomic polling for very small timeouts, then loops until `(reg_value & mask) == value` or the deadline has passed. It guarantees one condition evaluation after timeout expiry, stores the last register value in `out_val` when requested, and backs off delay from 10 us up to 1000 us for sleepable waits or uses `udelay()` for atomic waits. The wrapper first tries the fast timeout if provided, then tries the slow timeout when the fast phase fails. The non-fw wait APIs take DMC wakelocks around polling; fw variants use caller-managed/unlocked accessors. Set/clear helpers are convenience wrappers with `value == mask` or `value == 0`.

State and persistence: no persistent state is owned. Functions transiently acquire DMC wakelocks for register ranges through `intel_dmc_wl_get()`/`put()`, read current MMIO state, and optionally return the final sampled value. The wait loop's delay/backoff state is local only.

Dependencies and integration: depends on Linux delay and ktime APIs, DRM warning macros, `intel_de.h` inline accessors, `intel_dmc_wl`, and uncore MMIO functions. It is used throughout display code for hardware state transitions such as DDI buffer idle/active, FEC live bits, DP idle patterns, D2D link state, and other register handshakes.

Risks: choosing the wrong atomic/sleeping variant can either sleep in atomic context or busy-wait too long. Incorrect masks/values can hide hardware failures until timeout. DMC wakelock handling must match the accessor type: normal waits protect registers internally, while fw waits assume the caller has handled locking/power context. Timeout multiplication in millisecond wrappers should be kept within sensible ranges. The 8-bit accessors are intentionally limited to old VGA registers and warn on display version >= 5 or G4X.

Test signals: exercise callers that wait for set and clear transitions, including success, timeout, and `out_value` capture. Use lockdep/atomic-context testing for `intel_de_wait_fw_us_atomic()`, verify DMC wakelock pairing, check timeout accuracy under scheduler load, and test legacy VGA byte accesses only on supported pre-G4X/pre-display-version-5 paths.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/i915/display/intel_de.h

Purpose: provides the i915 display-engine MMIO accessor layer. It wraps uncore register reads/writes with display-specific DMC wakelock handling, exposes wait helpers implemented in `intel_de.c`, and offers explicit firmware/unlocked/notrace/DSB variants for contexts that need different locking or batching semantics.

Important APIs/types/functions: `__to_uncore()` maps `intel_display` to `intel_uncore`. Normal accessors are `intel_de_read()`, `intel_de_read64_2x32()`, `intel_de_posting_read()`, `intel_de_write()`, and `intel_de_rmw()`, each acquiring and releasing DMC wakelocks around uncore access. Wait declarations cover microsecond/millisecond waits and set/clear helpers. Legacy byte declarations are `intel_de_read8()` and `intel_de_write8()`. Firmware/unlocked accessors are `intel_de_read_fw()`, `intel_de_write_fw()`, and `intel_de_rmw_fw()`, with explicit trace calls. Notrace helpers are `intel_de_read_notrace()` and `intel_de_write_notrace()`. `intel_de_write_dsb()` writes through a display state buffer when present or falls back to firmware writes.

Control flow: normal inline accessors acquire the relevant DMC wakelock for the register, perform the uncore operation, then release it. RMW reads and writes under the same DMC wakelock. FW accessors skip the normal uncore locking/wakelock path and trace register IO themselves. DSB writes either append to the DSB command stream or immediately write firmware-style MMIO, depending on whether a `struct intel_dsb *` is supplied.

State and persistence: the header owns no state but manipulates persistent hardware MMIO registers and transient DMC wakelock references. RMW helpers return the old value to allow callers to reason about prior register state. DSB writes may persist in a command buffer until the DSB is executed by surrounding code.

Dependencies and integration: includes display core, DMC wakelock, DSB, uncore, and uncore trace headers. This accessor layer is used pervasively by i915 display code, including DDI programming, power wells, transcoders, planes, PHYs, and hotplug. It isolates display code from direct uncore calls and keeps DMC wake requirements close to register access.

Risks: FW/unlocked accessors bypass serialization and are documented as dangerous on architectures where concurrent same-cacheline register access can fail; callers must provide appropriate locking or know the context is safe. Mixing DSB and immediate writes can reorder hardware programming if surrounding code is not careful. Normal accessors rely on DMC wakelock lookup for each register, so incorrect register definitions or missing wakelock coverage can affect low-power states. Notrace accessors reduce observability and should be reserved for paths that require it.

Test signals: compile and boot with register tracing, DMC firmware, and DSB paths enabled. Validate register access under display power saving, DMC DC states, modeset stress, and DDI link training. Use lockdep and register trace inspection for FW users, and compare DSB versus immediate programming behavior in paths that support both.
