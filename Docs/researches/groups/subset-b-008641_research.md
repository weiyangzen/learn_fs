# Research: sources/storage-engines/rocksdb/include/rocksdb/compression_type.h

- **Purpose:** Defines RocksDB's public compression type byte values and per-algorithm compression tuning options used by block/table writers. The enum values are part of the persistent SST format, so this header is a storage-format contract, not only an in-memory API.
- **Important APIs/types/functions:** `enum CompressionType : unsigned char` covers no compression, Snappy, zlib, bzip2, LZ4, LZ4HC, Xpress, ZSTD, the built-in boundary `kLastBuiltinCompression`, a reserved custom range `0x80..0xFE`, and `kDisableCompressionOption = 0xff`. `struct CompressionOptions` exposes `kDefaultCompressionLevel`, zlib parameters `window_bits` and `strategy`, generic `level`, dictionary controls `max_dict_bytes`, `zstd_max_train_bytes`, `max_dict_buffer_bytes`, `use_zstd_dict_trainer`, per-job `parallel_threads`, `enabled`, ratio guard `max_compressed_bytes_per_kb`, ZSTD `checksum`, `SetMinRatio()`, and defaulted equality. `CompressionManager` is forward declared for the advanced custom compression path.
- **Control flow:** This header has no runtime control flow beyond `SetMinRatio()` assigning `max_compressed_bytes_per_kb`. The meaningful flow is downstream: table builders choose a `CompressionType`, sanitize or interpret `CompressionOptions`, optionally buffer SST output for dictionary training, compress blocks, and persist the compression type byte in table metadata or block trailers.
- **State and persistence behavior:** `CompressionType` numeric values must not change because they are stored on disk. Dictionary options can cause SST-building code to buffer data in memory before finalizing dictionaries; buffered memory can be charged to block cache and may stop early on memory-limit status. `parallel_threads` changes compaction/flush resource use and can inflate SST output size due to in-flight compressed blocks.
- **Dependencies:** Includes `rocksdb/rocksdb_namespace.h` and `rocksdb/types.h`; documented behavior depends on external compression libraries zlib, LZ4/LZ4HC, and zstd, plus optional user `CompressionManager` implementations from advanced compression support.
- **Integration points:** Used by `ColumnFamilyOptions::compression`, `bottommost_compression`, `compression_per_level`, compression option string parsing in `convenience.h`, OPTIONS-file serialization, SST table building, compaction, flush, and custom compression managers.
- **Risks:** Changing enum values corrupts compatibility with existing SST files. LZ4 and LZ4HC share an on-disk format but use different level defaults, so callers can mistake type-byte identity for different decode behavior. Dictionary buffering and high ZSTD levels can create large memory/CPU spikes. Misconfigured `max_compressed_bytes_per_kb` can silently store blocks uncompressed. `enabled` has special meaning for bottommost compression options and can be misread as disabling normal compression options.
- **Test signals:** Compatibility tests should verify fixed enum byte values, string round-trips through option parsers, OPTIONS-file persistence, successful readback of SST files written with each supported compression, dictionary and no-dictionary paths, `SetMinRatio()` thresholds, checksum verification for ZSTD frames, and fallback behavior when optional compression libraries are unavailable.

# Research: sources/storage-engines/rocksdb/include/rocksdb/concurrent_task_limiter.h

- **Purpose:** Declares a small public handle for limiting the number of concurrent internal tasks shared across column families and RocksDB instances. It exposes the result of `NewConcurrentTaskLimiter()` while making clear that third-party derived classes are not supported.
- **Important APIs/types/functions:** `class ConcurrentTaskLimiter` has `GetName()`, `SetMaxOutstandingTask(int32_t limit)`, `ResetMaxOutstandingTask()`, and `GetOutstandingTask()`. `NewConcurrentTaskLimiter(const std::string& name, int32_t limit)` creates the internal implementation. Limits use `0` for "block new tasks" and negative values for "unlimited".
- **Control flow:** Callers create one limiter and pass/share it through options that accept concurrent task limiters. RocksDB internals consult the limiter before starting background work and update outstanding counts around task execution. Public methods let operators change the cap at runtime.
- **State and persistence behavior:** The limiter is an in-memory coordination object. It does not persist into SST, WAL, MANIFEST, or OPTIONS files except through whatever option owns a pointer to it. `GetOutstandingTask()` is live process state and should be treated as approximate under concurrency unless the implementation documents stronger guarantees.
- **Dependencies:** Includes `<stdint.h>`, `<string>`, and the RocksDB namespace header. Actual synchronization and scheduling are in RocksDB internals, not in this header.
- **Integration points:** Intended for options controlling background tasks such as compaction or subcompaction throttling across column families/DB instances. It also integrates with operational controls that adjust resource budgets while a DB is open.
- **Risks:** Ownership is raw-pointer based from the factory, so callers need to follow RocksDB's expected lifetime pattern and avoid deleting while DBs still reference it. Derived external implementations are unsupported, so tests or applications that subclass this interface risk breakage. Setting limit to zero can stall new work and amplify write stalls if used accidentally.
- **Test signals:** Unit and stress tests should check limit transitions (`0`, positive, negative), outstanding counts returning to zero after task completion, sharing across multiple column families/DBs, runtime cap changes under concurrency, and safe destruction only after DB/task users are gone.

# Research: sources/storage-engines/rocksdb/include/rocksdb/configurable.h

- **Purpose:** Defines `Configurable`, RocksDB's base reflection/configuration interface for objects whose options can be parsed from strings or maps, serialized, logged, compared, prepared, and validated. It is the common base behind configurable table factories, environments, caches, filters, merge operators, and nested option-bearing objects.
- **Important APIs/types/functions:** `Configurable::RegisteredOptions` records a named option object by offset plus an `OptionTypeInfo` map. Public APIs include templated `GetOptions<T>()`, `ConfigureFromMap()`, `ConfigureOption()`, `ConfigureFromString()`, `GetOptionString()`, `ToString()`, `GetOptionNames()`, virtual `GetOption()`, `AreEquivalent()`, `GetPrintableOptions()`, `PrepareOptions()`, `ValidateOptions()`, and static `GetOptionsMap()`. Protected extension points include `GetOptionsPtr()`, `ParseStringOptions()`, `ConfigureOptions()`, `ParseOption()`, `OptionsAreEqual()`, `SerializeOptions()`, `GetOptionName()`, and `RegisterOptions()`.
- **Control flow:** Derived classes typically call `RegisterOptions()` in their constructor. A configure call parses input into name/value pairs, walks registered option maps, calls `ParseOption()` for each recognized field, collects unused names, optionally invokes `PrepareOptions()`, and attempts to revert on failure. Serialization and comparison traverse the same registered option maps, subject to `ConfigOptions` depth, mutability, and sanity controls.
- **State and persistence behavior:** Registered option metadata is held in the `options_` vector as offsets relative to `this`, allowing same-type copied configurables to reuse registrations. Configuration mutates the actual option objects owned by the configurable. The serialized strings feed OPTIONS files, logs, and runtime `SetOptions()`-style APIs, but this base class does not write files itself.
- **Dependencies:** Includes atomics, strings, unordered maps/sets, vectors, `rocksdb/status.h`, and forward declarations for `Logger`, `ObjectRegistry`, `OptionTypeInfo`, `ConfigOptions`, `DBOptions`, and `ColumnFamilyOptions`. The concrete parsing/comparison behavior depends heavily on `OptionTypeInfo` definitions elsewhere.
- **Integration points:** Used by `Customizable`, `convenience.h` conversion helpers, object registries, dynamic option changes, OPTIONS-file load/save, option equivalence checks, and nested option validation/preparation during `DB::Open()`.
- **Risks:** The templated `GetOptions<T>()` uses raw pointer reinterpret casts, and the source contains a FIXME about shared pointer layout assumptions in the non-const overload. Revert on failed configuration may produce an equivalent but not identical object, especially for shared resources such as caches. Mutating options while an object is used by an open DB is undefined unless the DB's dynamic option APIs are used. Incorrect option registration offsets or maps can corrupt unrelated fields.
- **Test signals:** Tests should cover parsing from map and string, unknown/unsupported option handling, unused-option reporting, nested configurable preparation and validation, mutable-only mode, serialization round-trips, equivalence mismatch names, failure rollback, and `GetOptionNames()` omitting deprecated aliases.
<!-- END_FILE_RESEARCH: sources/storage-engines/rocksdb/include/rocksdb/configurable.h -->

# Research: sources/storage-engines/rocksdb/include/rocksdb/convenience.h

- **Purpose:** Declares public convenience helpers for converting RocksDB options between strings, maps, and typed option structs, plus utility operations for background work cancellation, file-range deletion, and SST checksum verification.
- **Important APIs/types/functions:** `struct ConfigOptions` controls parsing, serialization, comparison, registry, environment, delimiter, depth, sanity level, mutable-only mode, unknown/unsupported option behavior, and whether `PrepareOptions()` is invoked. Conversion APIs include `GetColumnFamilyOptionsFromMap/String()`, `GetDBOptionsFromMap/String()`, `GetBlockBasedTableOptionsFromMap/String()`, `GetPlainTableOptionsFromMap/String()`, `GetMemTableRepFactoryFromString()`, `GetOptionsFromString()`, `GetStringFromDBOptions()`, `GetStringFromColumnFamilyOptions()`, `GetStringFromCompressionType()`, `GetSupportedCompressions()`, `StringToMap()`, and `MapToString()`. Operational helpers include `CancelAllBackgroundWork()`, `DeleteFilesInRange()`, `DeleteFilesInRanges()` with `RangeOpt` or deprecated `RangePtr`, and `VerifySstFileChecksum()` overloads.
- **Control flow:** Callers construct `ConfigOptions`, then feed a map or semicolon-delimited string into typed conversion helpers. Helpers start from base options, parse primitive values and nested braced options, instantiate known factories where needed, and return either populated options or the base options on error. `StringToMap()` preserves nested braced values as self-contained strings; `MapToString()` naively joins already self-contained values. Operational helpers delegate to DB and table-reader internals.
- **State and persistence behavior:** Option conversion affects caller-provided option structs and serialized OPTIONS text, but does not itself open DBs. `ConfigOptions::registry` owns/locates configurable/customizable factories for parsing object-valued options. `DeleteFilesInRange(s)` can physically remove SST files wholly covered by ranges and can affect visibility for old snapshots as documented. Checksum helpers read SST files and verify whole-file/block checksums depending on overloads.
- **Dependencies:** Includes `compression_type.h`, `db.h`, `status.h`, and `table.h`, with forward declarations for `Env`, `Logger`, `ObjectRegistry`, `Options`, `DBOptions`, and `ColumnFamilyOptions`.
- **Integration points:** Public API for loading OPTIONS files, command-line tools, tests, admin tooling, `DB::SetOptions()`, table factory configuration, compression parsing, and operational maintenance workflows that delete SSTs by range or verify file integrity.
- **Risks:** Unknown options can be ignored or treated as corruption depending on `ConfigOptions` and OPTIONS-file version logic, so permissive parsing can mask typos. `MapToString()` does not escape arbitrary raw values, so hand-built maps with semicolons or unmatched braces may not round-trip. Runtime `SetOptions()` uses these map formats but does not apply the same sanitization as `DB::Open()`. `DeleteFilesInRange()` only removes files entirely within ranges, leaves L0 files, and can surprise snapshot users.
- **Test signals:** Tests should cover primitive/unit parsing, enum and vector parsing, nested table and memtable factories, object registry lookup, unknown and unsupported option modes, `StringToMap()`/`MapToString()` round-trips with braces, supported compression enumeration, delete-files range boundaries, deprecated `RangePtr` compatibility, and checksum verification failures on corrupted SSTs.

# Research: sources/storage-engines/rocksdb/include/rocksdb/customizable.h

- **Purpose:** Defines `Customizable`, a `Configurable` subclass for named pluggable RocksDB components that can be created through an `ObjectRegistry` and then configured through the same option reflection system.
- **Important APIs/types/functions:** Core virtuals are `Name()`, `GetId()`, `IsInstanceOf()`, `Inner()`, `AreEquivalent()`, `GetOption()`, and protected `NickName()`, `GenerateIndividualId()`, `GetOptionName()`, `SerializeOptions()`. Templates `CheckedCast<T>()` search this object and wrapped `Inner()` objects by `T::kClassName()`. Static helpers `GetOptionsMap()` and `ConfigureNewObject()` parse object id/name plus remaining options and configure newly created objects.
- **Control flow:** Factory code identifies a customizable type and id from option strings such as a simple name or `{id=X;...}` map, creates or reuses an object from the registry, configures remaining options, and optionally prepares it. `IsInstanceOf()` compares the requested name with `Name()` and `NickName()`. Wrapper classes expose `Inner()` so options, casts, and equivalence can pass through layered implementations.
- **State and persistence behavior:** Object identity is represented by `Name()`/`GetId()` strings in option serialization and logs. `GenerateIndividualId()` can produce process/address-specific IDs for managed object instances, which are not durable across process lifetimes. The class itself persists no storage data, but its names and options are stored in OPTIONS files and can determine which implementation is loaded during DB open.
- **Dependencies:** Includes `rocksdb/configurable.h` and `rocksdb/status.h`; relies on `ConfigOptions`, `ObjectRegistry`, and derived component factories for actual object construction.
- **Integration points:** Used by pluggable table factories, caches, environments/file systems, merge operators, compaction filters, compression managers, and wrappers such as shared or managed objects. It is the bridge between option strings, registry lookup, and runtime polymorphic components.
- **Risks:** `CheckedCast<T>()` uses static casts after name checks, so derived classes must keep `kClassName()`, `Name()`, and `IsInstanceOf()` truthful. Wrapper classes that fail to override `Inner()` hide underlying options and types. Process/address generated IDs can be reused after deletion/recreation and should not be treated as persistent identity. Misparsed ids can instantiate the wrong plugin or silently configure an existing object when the id matches.
- **Test signals:** Tests should verify simple-name and braced id parsing, nickname matching, wrapper `Inner()` traversal for `GetOption()` and `CheckedCast()`, equivalence across same/different implementations, registry creation failures, `ConfigureNewObject()` behavior with null objects and non-empty options, and serialization of nested customizables.

# Research: sources/storage-engines/rocksdb/include/rocksdb/data_structure.h

- **Purpose:** Provides small generic utility data structures used by RocksDB public APIs and internals: compact enum sets, owner-managed pointers, and interval/interval-set abstractions including a `Slice` specialization for multi-range scans and property-bearing disjoint ranges.
- **Important APIs/types/functions:** `SmallEnumSet<ENUM_TYPE, MAX_ENUMERATOR>` offers dense enum bitsets with `All()`, `Contains()`, `empty()`, iterators, `count()`, `Add()`, `Remove()`, `With()`, and `Without()`, using helper functions `detail::CountTrailingZeroBitsForSmallEnumSet()` and `BitsSetToOneForSmallEnumSet()`. `ManagedPtr<T, Owner, Fn>` is a move-only RAII wrapper that calls either a member or free cleanup function with the owner. `Interval<T, comp>` stores `[start,end]` or `[start, infinity)` ranges using `std::variant`, with a `Slice`/`Comparator` specialization. `IntervalSet<T, Compare>` keeps ordered non-intersecting intervals and merges overlaps. `IntervalSet<Slice, Comparator>` stores sorted vector-backed ranges and can reject intersections when properties/disjointness are required.
- **Control flow:** `SmallEnumSet` maps enum values to 64-bit pieces and iterates by skipping unset bits. `ManagedPtr` transfers ownership on move and frees the tracked object in destructor or move assignment replacement. Generic `IntervalSet::insertImpl()` skips empty intervals, finds overlapping ranges, erases merged intervals, and inserts a merged finite or infinite interval. The `Slice` specialization repeats the merge logic with `Comparator::Compare()` and returns `false` on empty or intersecting ranges when `fail_on_intersect` is true.
- **State and persistence behavior:** These structures are in-memory only. They can represent API state such as selected enum flags, external objects owned by DB-like owners, or scan ranges. `Slice` intervals are non-owning views, so callers must keep referenced key buffers alive as long as the interval set is used.
- **Dependencies:** Includes assertions, arrays, integer types, functionals, sets, variants, `rocksdb/comparator.h`, `rocksdb/slice.h`, and namespace definitions. The `Slice` specialization depends on caller-supplied comparators to define key ordering.
- **Integration points:** `SmallEnumSet` supports compact flag sets for enum-heavy APIs. `ManagedPtr` fits RocksDB owner/free patterns such as handles tied to DB ownership. `IntervalSet<Slice, Comparator>` is tied to `MultiScan` range handling and property pushdown where overlapping ranges may be invalid.
- **Risks:** `SmallEnumSet` relies on assertions for enum bounds; optimized builds remove these checks, so invalid enum values can address invalid pieces if callers violate contracts. `Interval<T>` uses `std::less` by default but the set's template default names `Interval<T>::CompareVariant`, so comparator compatibility is subtle. The generic interval set uses closed/overlap-style comparisons that need careful interpretation for RocksDB's common half-open key ranges. `Slice` ranges are non-owning, and the `Interval<Slice, Comparator>` specialization contains an unused `property_bag` member that may suggest unsupported persistence of properties.
- **Test signals:** Tests should cover enum sets crossing 64-bit piece boundaries, iteration order, `All()` masks, add/remove idempotence, move-only `ManagedPtr` cleanup exactly once, finite and infinite interval merging, empty interval rejection, comparator-based `Slice` ordering, `fail_on_intersect` rejection, and lifetime-sensitive use with temporary `Slice` backing strings.
<!-- END_FILE_RESEARCH: sources/storage-engines/rocksdb/include/rocksdb/data_structure.h -->

# Research: sources/storage-engines/rocksdb/include/rocksdb/db.h

- **Purpose:** Declares RocksDB's primary public database interface. `DB` is a thread-safe, persistent, versioned ordered map from keys to values, with column families, snapshots, reads/writes, LSM metadata, WAL access, compaction/flush controls, external SST ingestion, tracing, statistics, repair, and destruction APIs.
- **Important APIs/types/functions:** Top-level constants include `kDefaultColumnFamilyName`, `kPersistentStatsColumnFamilyName`, `kMajorVersion`, and `kMinorVersion`. `ColumnFamilyDescriptor` pairs a name and `ColumnFamilyOptions`; `ColumnFamilyHandle` exposes CF name/id/descriptor/comparator; `FileIngestionHandle` controls two-phase SST ingestion; `GetMergeOperandsOptions` controls merge operand enumeration; `TablePropertiesCollection` maps file names to table properties. `DB` static open APIs cover read-write, column-family open, read-only, secondary, follower, compaction-service `OpenAndCompact()`, and timestamp trim `OpenAndTrimHistory()`. Instance APIs cover `Resume()`, `Close()`, column-family create/drop/destroy, `Put()`, timestamped `Put()`, `PutEntity()`, `Delete()`, `SingleDelete()`, `DeleteRange()`, `Merge()`, `Write()`, `WriteWithCallback()`, `IngestWriteBatchWithIndex()`, `Get()`, `GetEntity()`, `GetMergeOperands()`, `MultiGet()`, `MultiGetEntity()`, `KeyMayExist()`, iterators, snapshots, properties, approximate sizes, compaction, dynamic options, background work controls, WAL flush/sync/lock, timestamps, file deletion guards, WAL iterators, live-file metadata, external file ingestion/import, checksum verification, table properties, traces, replayers, stats history, and secondary catch-up. Free functions `DestroyDB()` and `RepairDB()` perform destructive maintenance.
- **Control flow:** Typical use opens a DB with options and optional CF descriptors, receives a `unique_ptr<DB>` and CF handles, performs writes through WAL/memtable paths, reads through point lookup/iterators/snapshots, flushes memtables to SSTs, compacts SSTs in background or foreground, and closes after destroying CF handles and releasing snapshots. Secondary/follower opens replay primary metadata/WAL state for read-only access. External ingestion can either perform direct ingest or prepare files off the DB mutex and later commit handles atomically. Many overloads are thin default-CF or string/PinnableSlice adapters around pure virtual implementation hooks.
- **State and persistence behavior:** DB state persists in WAL files, MANIFEST/version metadata, OPTIONS files, SST files, blob files, IDENTITY, and optional stats history. `Close()` does not fsync WALs by itself; callers needing durability must use synced writes, `SyncWAL()`, or `FlushWAL()` as appropriate. Dynamic `SetOptions()` persists new OPTIONS files and is intentionally slow. Column-family create/drop records manifest edits, with final removal tied to handle destruction. Snapshots and iterators pin versions and can prevent obsolete SST deletion. `DisableFileDeletions()` and compaction abort/pause controls are reference-counted operational state. `GetCurrentSuperVersionNumber()` is process-lifetime state and resets after restart.
- **Dependencies:** Includes many public RocksDB headers: attribute groups, block cache trace writer, iterator, listener, metadata, multi-scan, options, snapshot, SST file writer, thread status, transaction log, types, user write callbacks, table property collectors, indexed write batches, version, and wide columns. Forward declarations connect to `Env`, `FileSystem`, events, tracing, compaction options, flush/WAL options, table properties, replayers, and stats iterators.
- **Integration points:** This is the central interface used by applications, wrappers such as `StackableDB`, tools, backup/checkpoint implementations, replication consumers reading WALs, compaction services, external SST writers/importers, monitoring systems reading properties, and tests validating DB behavior. `convenience.h` and option/configuration APIs feed into `DB::Open()` and runtime option mutation.
- **Risks:** The API surface includes many sharp contracts: failing to destroy CF handles before DB destruction, unreleased snapshots causing `Close()` aborts, using `SingleDelete()` after multiple puts or mixed deletes/merges causing undefined behavior, read-only and read-write simultaneous opens having undefined behavior, secondary DBs being incompatible with primary SST truncation, stale WAL retention breaking `GetUpdatesSince()`, and dynamic options lacking full open-path sanitization. Some APIs are experimental or unsupported by wrappers/Lite mode. Destructive calls `DestroyDB()` and `RepairDB()` can delete or lose data. Manual compaction, file deletion disabling, and WAL locking can stall writes or file cleanup if reference counts are unbalanced.
- **Test signals:** Coverage should include open-mode matrix tests, column-family lifecycle and handle destruction, write/read/delete/range-delete/merge semantics, timestamped operations, wide-column entity paths, atomic batch writes and callbacks, snapshot stability, iterator pinning, MultiGet status/value alignment, property/map/int property correctness, approximate-size flags, flush/WAL sync durability, compaction and abort controls, dynamic option persistence, external SST ingestion including two-phase abort/commit, live-file backup consistency, checksum verification, secondary catch-up, and destructive repair/destroy guarded by temporary DB fixtures.

# Research: sources/storage-engines/rocksdb/include/rocksdb/db_dump_tool.h

- **Purpose:** Declares small object-oriented wrappers for dumping a RocksDB database to a file and loading a dump file back into a database.
- **Important APIs/types/functions:** `DumpOptions` contains `db_path`, `dump_location`, and `anonymous` for suppressing DB information headers. `DbDumpTool::Run(const DumpOptions&, Options)` returns `bool`. `UndumpOptions` contains `db_path`, `dump_location`, and `compact_db`. `DbUndumpTool::Run(const UndumpOptions&, Options)` returns `bool`.

- **Dependencies:** Includes `<string>` and `rocksdb/db.h`, which brings in `Options` and the DB API.
- **Integration points:** Used by dump/undump command-line tools, tests for backup-like textual exports, and operational scripts that need a simple programmatic wrapper instead of invoking a separate process.
- **Risks:** `bool` return loses detailed `Status` diagnostics unless the implementation logs them. Incorrect options can open the wrong DB mode or comparator, making dumps unreadable or undumps invalid. Dump files can expose user data unless `anonymous` only suppresses metadata, not key/value content. Loading into an existing DB path can overwrite or merge with existing data depending on implementation semantics.
- **Test signals:** Tests should cover dump then undump round-trips, anonymous header suppression, missing path failures, comparator/options mismatches, `compact_db` effects, malformed dump input, and preservation of key ordering and values.
