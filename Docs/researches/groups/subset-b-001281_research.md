# sources/distributed-fs/ceph-client/drivers/firmware/arm_scmi/driver.c

Purpose: implements the main ARM SCMI protocol driver and platform instance lifecycle. It binds the `arm-scmi` platform device to a selected transport, registers built-in SCMI protocols, creates SCMI child devices for implemented DT protocol nodes, exposes protocol handles to SCMI client drivers, and owns the generic message transfer, response, notification, fast-channel, debugfs, raw-mode, and protocol lifetime plumbing.

Important APIs/types/functions: central state is `struct scmi_info`, which holds the instance id, transport descriptor, `struct scmi_handle`, TX/RX channel IDRs, protocol-instance IDR, implemented/active protocol lists, notification private pointer, debug state, and raw-mode handle. `struct scmi_xfers_info` manages preallocated `struct scmi_xfer` objects, token allocation bitmap, free list, and pending transfer hash. `struct scmi_protocol_instance` wraps one initialized protocol, its refcount, private data, negotiated version, and embedded `struct scmi_protocol_handle`. Exported or externally consumed entry points include `scmi_protocol_register()`, `scmi_protocol_unregister()`, `scmi_protocol_acquire()`, `scmi_protocol_release()`, `scmi_revision_area_get()`, `scmi_setup_protocol_implemented()`, raw xfer helpers, and `scmi_inflight_count()`. The handle exposes devres-managed `devm_protocol_get/acquire/put` and `is_transport_atomic`.

Control flow: module init initializes quirks, installs optional shared-memory and message operations into `scmi_trans_core_ops`, creates the debugfs root, registers built-in protocols, and registers the platform driver. `scmi_probe()` obtains the transport descriptor from platform data, parses DT overrides, initializes channels for Base and child protocols, registers bus and device-request notifiers, preallocates xfer pools, initializes debugfs/raw mode, initializes notifications, acquires the mandatory Base protocol, adds the instance to `scmi_list`, enables matching quirks, then creates SCMI devices for implemented child protocol nodes. Protocol use is lazy: `scmi_get_protocol_instance()` finds or creates an initialized `scmi_protocol_instance`, negotiates protocol version if needed, calls the protocol's `instance_init`, and registers protocol events.

Transfer flow: clients allocate messages through `xfer_get_init()`, which checks message sizes, takes a free xfer, assigns a monotonic token with `scmi_xfer_pending_set()`, and marks it in-flight. `do_xfer()` resolves the protocol TX channel, optionally enables polling, sets the protocol id from the handle, sends through transport `send_message`, waits through completion or transport polling, translates SCMI status to Linux errno, calls `mark_txdone`, and traces the transaction. `do_xfer_with_response()` adds delayed-response waiting for async commands. `scmi_rx_callback()` routes notifications to `scmi_handle_notification()` and command/delayed responses to `scmi_handle_response()`. Response handling validates message type against xfer state, supports out-of-order delayed responses by completing the missing normal response as success, copies transport payload, completes the appropriate waiter, and releases the xfer ref.

State and persistence behavior: all state is runtime memory. Xfers, channels, protocol instances, active protocol nodes, and debugfs entries are managed by devres, IDRs, xarrays, refcounts, and locks. `scmi_list` tracks active platform instances and simple `users` counts for handles. `transfer_last_id` gives monotonic transfer ids for tracing and token selection. `scmi_top_dentry` and per-instance debugfs expose current configuration and optional counters; they do not persist across unload. Removal tears down raw mode, notifications, protocol IDRs, active node refs, notifiers, channels, and the instance id.

Dependencies and integration points: depends on Linux platform, OF/DT, device links, IDR/xarray/IDA, debugfs, tracepoints, refcounting, the SCMI bus, transport descriptors and operations, protocol declarations in `protocols.h`, notification core in `notify.h`, quirks, raw mode, and optional shared-memory/message transport helpers. It registers Base, Clock, Performance, Power, Reset, Sensors, Voltage, System, Powercap, and Pinctrl protocols. It is the integration point between SCMI transports and all SCMI client drivers.

Risks and test signals: protocol lookup can return `-EPROBE_DEFER` until a protocol module is registered, and vendor protocol matching depends on vendor/subvendor/implementation version hashes and module aliases. The response path is sensitive to token reuse, delayed-response ordering, and refcount/busy-state locking; tests should exercise normal, delayed, out-of-order, timeout, unexpected, invalid, raw-mode, and polled responses. Probe and teardown tests should cover missing transport ops, invalid DT protocol ids, shared versus dedicated channels, no-RX-channel configurations, debugfs/raw-mode coexistence, notification init failure, Base protocol failure, and active users during remove. Debug counter deltas, trace events, sysfs version attributes, and `scmi_inflight_count()` are useful runtime signals.

# sources/distributed-fs/ceph-client/drivers/firmware/arm_scmi/msg.c

Purpose: provides the SCMI message-passing transport SDU packing and unpacking operations for transports built around a contiguous message buffer rather than the shared-memory helper. It translates between `struct scmi_xfer` and the on-wire little-endian SCMI message layout.

Important APIs/types/functions: `struct scmi_msg_payld` defines the transport SDU as a 32-bit SCMI message header followed by a flexible little-endian payload array. `msg_command_size()` and `msg_response_size()` report command and response SDU lengths. `msg_tx_prepare()` writes the packed header and command payload. `msg_read_header()` extracts the SCMI header. `msg_fetch_response()` stores SCMI status and response payload into the xfer. `msg_fetch_notification()` copies notification payloads. `scmi_message_operations_get()` returns the static `scmi_message_operations` table to `driver.c`.

Control flow: a transport asks the core for these operations during SCMI driver init when message transport support is enabled. Before send, `msg_tx_prepare()` writes `pack_scmi_header(&xfer->hdr)` and copies `xfer->tx.buf` when present. On receive, the transport or core reads the header with `msg_read_header()`, then either fetches a response, where payload word zero is the SCMI status, or fetches a notification, where payload begins immediately after the header.

State and persistence behavior: this file has no persistent state and allocates no memory. It only reads from and writes to caller-owned transport buffers and xfer buffers. Response length is clamped to the smaller of the expected RX size and actual available bytes after the header/status prefix.

Dependencies and integration points: depends on `common.h` for `struct scmi_xfer`, `pack_scmi_header()`, and `struct scmi_message_operations`. It is wired into `scmi_trans_core_ops.msg` by `scmi_driver_init()` when `CONFIG_ARM_SCMI_HAVE_MSG` is enabled and is then consumed by message-based transports.

Risks and test signals: callers must provide a valid SDU buffer with enough bytes for the selected operation; short responses produce zero-length payloads after status clamping but still read status from payload word zero. Tests should verify little-endian header/status conversion, command size and response size accounting, zero-length command payloads, truncated responses, max-length notification clamping, and that notifications do not interpret the first payload word as status.

# sources/distributed-fs/ceph-client/drivers/firmware/arm_scmi/notify.c

Purpose: implements the SCMI notification core for one SCMI platform instance. It lets protocol implementations register event descriptions, lets kernel clients register notifier blocks for `(protocol, event, source)` tuples, enables or disables platform event generation on demand, queues ISR-delivered notifications, and dispatches typed reports from deferred workqueue context.

Important APIs/types/functions: `struct scmi_notify_instance` stores the per-handle notification state, pending handler hash, registered protocol table, workqueue, and late-init work. `struct scmi_registered_events_desc` describes one protocol's event queue, operations, registered events, handler table, and scratch buffers. `struct scmi_registered_event` stores one event descriptor, report buffer, source refcounts, and per-source support state. `struct scmi_event_handler` stores one notifier chain, key, refcount, active/pending binding, and enabled flag. Public functions are `scmi_notification_init()`, `scmi_notification_exit()`, `scmi_register_protocol_events()`, `scmi_deregister_protocol_events()`, and `scmi_notify()`. Client-facing operations are exposed through `struct scmi_notify_ops`.

Control flow: `scmi_notification_init()` opens a devres group, allocates the instance, creates a protocol pointer table of 256 entries, creates an unbound/freezable/sysfs workqueue, initializes the pending handler hash, stores the instance in the SCMI handle, and installs notify ops. Protocols call `scmi_register_protocol_events()` from their instance init; this resolves source count, allocates a per-protocol kfifo, event descriptors, per-source refcount arrays, report buffers, checks source support if the protocol provides `is_notify_supported`, publishes the protocol descriptor, and schedules late binding of any pending handlers. Clients call `event_notifier_register` or devres variants; the core creates or finds a handler, binds it immediately if the protocol event is known, otherwise leaves it pending, registers the notifier block, and enables platform notifications for active handlers.

Notification dispatch flow: `driver.c` calls `scmi_notify()` from the RX path with a timestamp, protocol id, event id, and payload. This validates the event exists, checks payload size, verifies kfifo space, queues a small event header followed by payload into the per-protocol kfifo, and queues the protocol work item. `scmi_events_dispatcher()` drains the protocol queue sequentially, tolerating header/payload split across work runs through `in_flight`. It looks up the registered event, asks the protocol's `fill_custom_report()` to convert raw payload into the event report and source id, then calls both all-source and specific-source blocking notifier chains if present.

State and persistence behavior: state is runtime-only and scoped to the SCMI handle devres group. Registered protocol descriptors are published with memory barriers and normally persist until protocol deregistration or instance exit. Pending handlers can exist before protocol registration; late init binds or purges them. Source refcounts determine when platform notification commands are issued: the first user enables a source, further users increment, and the last unregister disables it. The workqueue is destroyed on exit and devres releases allocations.

Dependencies and integration points: depends on Linux kfifo, workqueue, mutex, hashtable, blocking notifier chains, refcounting, devres, and SCMI protocol hooks from `notify.h`. It is integrated with `driver.c` through notification instance data accessors and `scmi_notify()`. It relies on each protocol's `struct scmi_protocol_events` for event ids, payload/report sizing, source counts, support checks, enable commands, and report conversion.

Risks and test signals: the kfifo is single-consumer per protocol but receives header and payload in separate writes, so queue corruption, partial reads, and queue-full drops are important failure paths. Handler lifetime depends on balanced registration/unregistration and refcounted dispatch lookups; tests should cover unregister during queued delivery, all-source plus specific-source chains, unsupported sources, pending handler binding after lazy protocol init, purging invalid pending handlers, notification enable refcounting, duplicate registrations, malformed payload sizes, unknown event ids, queue saturation, and clean exit with pending work.

# sources/distributed-fs/ceph-client/drivers/firmware/arm_scmi/notify.h

Purpose: defines the private SCMI notification contract between protocol implementations, the notification core, and the main SCMI driver. It describes supported protocol events, protocol-specific notification callbacks, and the notification core entry points.

Important APIs/types/functions: `SCMI_PROTO_QUEUE_SZ` is the default per-protocol notification kfifo size. `struct scmi_event` defines an event id plus maximum raw payload and converted report sizes. `struct scmi_event_ops` provides protocol callbacks for source support checks, source count discovery, enable/disable commands, and custom report construction. `struct scmi_protocol_events` groups queue size, operations, event array, event count, and optional static source count. The function declarations cover notification init/exit, protocol event registration/deregistration, and ISR-side event queuing through `scmi_notify()`.

Control flow: protocol files populate static `scmi_event`, `scmi_event_ops`, and `scmi_protocol_events` tables and attach them to their `struct scmi_protocol`. During protocol instance initialization, `driver.c` passes these descriptors to `scmi_register_protocol_events()`. Client notifier registration and RX dispatch are implemented in `notify.c`, using the callback table defined here.

State and persistence behavior: this header owns no storage. It defines sizing and callback contracts for runtime state allocated by `notify.c`; those allocations are per SCMI platform instance and per initialized protocol.

Dependencies and integration points: includes Linux device, ktime, and type headers, and forward-declares `struct scmi_protocol_handle`. It is included by `driver.c`, `notify.c`, and protocol implementations such as power, performance, and powercap that publish events.

Risks and test signals: the correctness of notification handling depends on accurate `max_payld_sz`, `max_report_sz`, and source counts from each protocol. Tests should verify that each event table matches the corresponding SCMI payload/report structs and that protocols with dynamic source counts provide a reliable `get_num_sources()` callback before notifier registration is used.

# sources/distributed-fs/ceph-client/drivers/firmware/arm_scmi/perf.c

Purpose: implements the SCMI Performance protocol provider. It discovers performance domains and OPPs, exposes performance and DVFS operations to SCMI clients, supports optional fast channels for performance level and limit get/set, converts SCMI events into performance reports, and registers itself as `SCMI_PROTOCOL_PERF`.

Important APIs/types/functions: protocol commands include domain attributes, describe levels, limits set/get, level set/get, notifications, fast-channel description, and extended names. `struct perf_dom_info` stores per-domain capabilities, rate limit, sustained frequency/performance, multiplier, exported `scmi_perf_domain_info`, OPP array, optional fast-channel info, xarrays by level/index, and a hash by indicative frequency. `struct scmi_perf_info` stores global domain count, power scale, stats address/size, notification command availability, and domain array. Exported protocol ops include domain count/info, limit and level set/get, DVFS OPP add, frequency set/get, estimated power, fast-switch queries, rate limits, and power scale.

Control flow: `scmi_perf_protocol_init()` allocates global state, reads protocol attributes, allocates the domain table, then for each domain reads domain attributes, initializes xarrays/hash tables, iterates `PERF_DESCRIBE_LEVELS` through the common SCMI iterator, sorts OPPs, and initializes fast channels if supported. Domain attributes determine set-limit/set-level support, notification support, fast-channel support, level-indexing mode, rate limits, sustained data, power scale, and names. OPP processing inserts each level into `opps_by_lvl`; v4 level-indexing mode also indexes by `level_index` and frequency.

Runtime operations: limits and level operations validate the domain, check capability bits, translate between performance levels and level indexes when needed, and then use a fast-channel MMIO path when available or a normal SCMI xfer otherwise. DVFS frequency operations convert between Linux frequency and SCMI level using the domain multiplier or indicative frequency table. OPP population calls `dev_pm_opp_add_dynamic()` and marks OPPs above sustained frequency as turbo. Fast switch is possible only when the level set fast-channel address exists.

State and persistence behavior: state is in-memory and scoped to the protocol instance devres group. OPPs are stored in fixed-size per-domain arrays up to `MAX_OPPS` and indexed by xarray/hash for lookup. `scmi_perf_xa_destroy()` destroys xarrays on protocol teardown. Fast-channel addresses are devm-ioremapped by core helpers and persist for the protocol instance lifetime. No disk or firmware state is persisted by the driver beyond issuing SCMI set commands.

Dependencies and integration points: depends on Linux OPP, xarray, hashtable, sort, I/O accessors, tracepoints, SCMI common iterator and fast-channel helpers from `driver.c`, and notification definitions from `notify.h`. It integrates with cpufreq/devfreq style clients through `struct scmi_perf_proto_ops` and with the notification core through two events: limits changed and performance level changed.

Risks and test signals: firmware can report duplicate or inconsistent OPP data; duplicate xarray inserts are logged and can truncate usable OPPs. Level-indexing mode requires all translations to find matching xarray/hash entries or operations return `-EIO`/`-ENODEV`. Frequency math depends on sustained values and multiplier rounding. Tests should cover v3 and v4 describe-level layouts, zero and rounded sustained ratios, OPP overflow/duplicate handling, limit validation, fast-channel get/set and doorbells, fallback messaging paths, OPP registration cleanup on failure, notification support and report conversion, and xarray destruction on deinit.

# sources/distributed-fs/ceph-client/drivers/firmware/arm_scmi/pinctrl.c

Purpose: implements the SCMI Pinctrl protocol provider. It discovers counts of pins, groups, and functions, lazily fetches names and associations, exposes mux/config/request/free operations to SCMI pinctrl clients, and registers itself as `SCMI_PROTOCOL_PINCTRL`.

Important APIs/types/functions: command ids include attributes, list associations, settings get/configure, request/release, name get, and permissions. `struct scmi_pinctrl_info` stores counts and arrays of `scmi_group_info`, `scmi_function_info`, and `scmi_pin_info`. Groups cache name, present flag, pin list, and pin count; functions cache name, present flag, associated group list, and group count; pins cache name and present flag. The `pinctrl_proto_ops` table exposes count, name, group pins, function groups, mux set, settings get one/all, settings configure, pin request, and pin free.

Control flow: `scmi_pinctrl_protocol_init()` reads protocol attributes, rejects zero-pin firmware, allocates the pins/groups/functions arrays, and stores private state. Metadata is fetched lazily: group and function info functions call `PINCTRL_ATTRIBUTES`, allocate association arrays, then iterate `PINCTRL_LIST_ASSOCIATIONS` through the common iterator. Pin info fetches attributes only. Extended names are retrieved with `PINCTRL_NAME_GET` when the attribute flag advertises them.

Settings and request flow: `scmi_pinctrl_settings_get()` uses the iterator abstraction for either one config type or all configs, validating selector type and id before issuing `PINCTRL_SETTINGS_GET`. `scmi_pinctrl_settings_conf()` chunks configuration pairs according to the core max message size, sends repeated `PINCTRL_SETTINGS_CONFIGURE` commands, and stops on first error. `scmi_pinctrl_function_select()` configures a function on a group. `scmi_pinctrl_request_free()` wraps pin/group request and release commands and treats firmware `-EOPNOTSUPP` as success for optional request/release support.

State and persistence behavior: protocol counts and top-level arrays are devm-managed. Association arrays for lazily populated groups/functions are allocated with `kmalloc_array()` and freed explicitly in `scmi_pinctrl_protocol_deinit()`. Present flags prevent repeated metadata fetches. There is no persistent state outside current firmware pinctrl configuration changes made through SCMI commands.

Dependencies and integration points: depends on SCMI common xfer and iterator helpers, Linux bitfield helpers, and public pinctrl protocol types in `linux/scmi_protocol.h`. It does not register SCMI notification events. It is consumed by SCMI pinctrl client glue that maps generic pinctrl operations onto `scmi_pinctrl_proto_ops`.

Risks and test signals: lazy metadata population is not protected by a local mutex, so concurrent first access to the same group/function/pin could duplicate fetches or allocations depending on caller serialization. `settings_conf()` relies on max message size being large enough for at least one config pair; malformed small limits could stall progress. Tests should cover invalid selector/type combinations, zero-pin rejection, extended names, multi-part association iteration, settings get one/all, chunked settings configure, request/release optional support, deinit freeing only populated arrays, and concurrency expectations from the consuming pinctrl driver.

# sources/distributed-fs/ceph-client/drivers/firmware/arm_scmi/power.c

Purpose: implements the SCMI Power Domain protocol provider. It discovers power domains, exposes domain name and state get/set operations, supports power state change notifications, and registers itself as `SCMI_PROTOCOL_POWER`.

Important APIs/types/functions: commands include domain attributes, state set/get, state notify, and extended domain name get. `struct power_dom_info` stores per-domain synchronous/asynchronous set support, notification support, and name. `struct scmi_power_info` stores domain count, stats address/size, state notification command availability, and the domain table. `power_proto_ops` exposes `num_domains_get`, `name_get`, `state_set`, and `state_get`. Event support uses `SCMI_EVENT_POWER_STATE_CHANGED` and `struct scmi_power_state_changed_report`.

Control flow: `scmi_power_protocol_init()` allocates state, reads protocol attributes, allocates the domain table, and queries each domain. Protocol attributes supply domain count and stats area and check whether `POWER_STATE_NOTIFY` is supported. Domain attributes read capability flags and short names, then optionally replace names through the common extended-name helper for protocol v3 and newer. State set/get issue simple SCMI xfers carrying domain id and state.

Notification flow: during protocol event registration the notification core asks `scmi_power_get_num_sources()` for domain count and `scmi_power_notify_supported()` for each source. When a client registers a notifier, `scmi_power_set_notify_enabled()` issues `POWER_STATE_NOTIFY` with enable bit. RX event payloads are converted by `scmi_power_fill_custom_report()` into timestamp, agent id, domain id, and power state, with source id equal to the domain id.

State and persistence behavior: state is in-memory and devm-managed for the protocol instance lifetime. Domain names and support flags are cached after init. Firmware power domain state persists in platform firmware/hardware, but this driver only sends commands and does not persist requested state locally.

Dependencies and integration points: depends on SCMI xfer/helper operations, public SCMI power protocol types, and the notification core. It integrates with generic Linux power-domain consumers through `scmi_power_proto_ops` and with the SCMI notification core through `power_protocol_events`.

Risks and test signals: `scmi_power_name_get()` assumes callers pass a valid domain index and does not locally validate before indexing. Domain attribute query errors during init are ignored in the loop, so malformed individual domains may leave default capability/name data while protocol init succeeds. Tests should cover domain count discovery, v3 extended names, state get/set return statuses, notification enable only on supported domains, invalid event payload sizes, unsupported notification command handling, and consumers avoiding out-of-range domain ids.

# sources/distributed-fs/ceph-client/drivers/firmware/arm_scmi/powercap.c

Purpose: implements the SCMI Powercap protocol provider. It discovers powercap domains, validates cap and PAI ranges, exposes cap, enable, PAI, measurement, threshold, and info operations, supports optional fast channels, handles asynchronous cap-set completion, supports cap and measurement notifications, and registers itself as `SCMI_PROTOCOL_POWERCAP`.

Important APIs/types/functions: commands include domain attributes, cap get/set, PAI get/set, domain name get, measurements get, cap notify, measurements notify, and fast-channel description. `struct powercap_info` stores domain count, notification command availability, per-domain runtime `scmi_powercap_state`, and public `scmi_powercap_info` array. Per-domain info includes capabilities, power units, PAI/cap ranges and steps, sustainable power, accuracy, parent id, fast-channel pointer, and names. `powercap_proto_ops` exposes domain count/info, cap get/set, cap enable get/set, PAI get/set, measurements get, and measurement threshold get/set.

Control flow: `scmi_powercap_protocol_init()` reads protocol attributes, allocates domain info and state arrays, then requires every reported domain to pass `scmi_powercap_domain_attributes_get()`. Domain attributes parse notification, async, configuration, monitoring, PAI, unit, fast-channel, range, accuracy, and parent flags; range consistency is validated by `scmi_powercap_validate()`, parent ids are checked for bounds and self-parenting, and extended names replace short names when supported. Fast channels are initialized per supported domain for cap and PAI get/set. For protocol v2 and newer, init reads the current cap to seed `last_pcap` and enabled state.

Runtime operations: cap get and PAI get use fast-channel MMIO when available or normal SCMI xfers otherwise. Cap set validates configurability and range, writes fast channel or sends `POWERCAP_CAP_SET`, and uses `do_xfer_with_response()` when the domain supports async cap set and delayed response is not ignored. Protocol v2 enable/disable is modeled by setting a non-zero last cap or sending cap zero; `cap_enable_get()` refreshes the local enabled flag from platform state. PAI set validates configurability and range. Measurements require monitoring support. Measurement threshold state is stored locally and reapplied if measurement notifications are already enabled.

Notification flow: two events are registered: cap changed and measurements changed. `scmi_powercap_notify_supported()` gates events by domain capabilities. `scmi_powercap_set_notify_enabled()` maps event ids to `POWERCAP_CAP_NOTIFY` or `POWERCAP_MEASUREMENTS_NOTIFY`; measurement notification enable requires non-zero thresholds already stored for the domain. Event payload conversion fills timestamp, agent id, domain id, power cap/PAI or measured power, and returns domain id as source.

State and persistence behavior: domain capabilities and runtime state are in-memory and devm-managed. `last_pcap`, `enabled`, `meas_notif_enabled`, and packed low/high thresholds are maintained by the Linux driver to support enable semantics and measurement notification reconfiguration. Hardware/firmware cap, PAI, and monitoring state live in SCMI firmware and are changed only by SCMI commands or fast-channel writes.

Dependencies and integration points: depends on SCMI xfer/helper operations, fast-channel helpers, I/O accessors, tracepoints, and notification core definitions. It integrates with Linux powercap-style clients through `struct scmi_powercap_proto_ops` and with notifier consumers through powercap protocol events.

Risks and test signals: `scmi_powercap_cap_set()` indexes `states[domain_id]` before an explicit domain bounds check, relying on callers to pass valid ids. Step values are validated for zero/nonzero consistency but requested cap/PAI values are range-checked without step-alignment checks. Measurement notification enable fails if thresholds were not configured first. Tests should cover invalid ranges and parent ids during init, cap zero enable/disable behavior, async delayed response domain mismatch, fast-channel versus xfer paths, protocol v1 versus v2 enable semantics, threshold update while notification is enabled, notification report conversion, unsupported monitoring/configuration paths, and out-of-range domain calls from clients.
