## sources/distributed-fs/ceph-client/drivers/net/ethernet/ibm/ibmvnic.c

Purpose: implements the IBM Power virtual NIC netdev driver for VIO devices whose compatible pair is `network` / `IBM,vnic`. The driver presents an Ethernet `net_device`, negotiates capabilities with the VIOS backing device over a Command/Response Queue (CRQ), creates sub-CRQs for packet transmit and receive traffic, and uses long-term DMA buffers rather than per-packet DMA mappings. It handles boot-time initialization, passive initialization when the VIOS partner appears later, live partition mobility, backing-device failover, firmware errors, TX timeouts, MTU/ring/channel changes, ethtool statistics, and module registration.

Important APIs, types, and functions: the file binds `ibmvnic_netdev_ops` (`ndo_open`, `ndo_stop`, `ndo_start_xmit`, `ndo_set_rx_mode`, `ndo_set_mac_address`, `ndo_get_stats64`, `ndo_tx_timeout`, `ndo_change_mtu`, `ndo_features_check`) and `ibmvnic_ethtool_ops` for link, ring, channel, and stats access. `ibmvnic_probe()` allocates `alloc_etherdev_mq()`, initializes `struct ibmvnic_adapter`, registers CRQ transport, creates the failover sysfs attribute, and registers the netdev. `ibmvnic_remove()` tears down reset work, netdev registration, CRQs, sub-CRQs, pools, DMA tokens, stats, and CPU hotplug hooks. `init_crq_queue()`, `ibmvnic_send_crq()`, `ibmvnic_handle_crq()`, and `ibmvnic_tasklet()` implement the control queue. `init_sub_crqs()`, `init_sub_crq_queue()`, `init_sub_crq_irqs()`, `send_subcrq_indirect()`, and `send_subcrq_direct()` implement packet queue setup and hypervisor sends. `alloc_long_term_buff()`, `alloc_ltb_set()`, `init_rx_pools()`, `init_tx_pools()`, `replenish_rx_pool()`, `ibmvnic_xmit()`, `ibmvnic_poll()`, and `ibmvnic_complete_tx()` manage the long-term DMA data path. `ibmvnic_reset()`, `__ibmvnic_reset()`, `do_reset()`, `do_hard_reset()`, and `do_passive_init()` serialize recovery work.

Control flow: module init registers CPU hotplug states and the VIO driver. Probe reads the VIO MAC attribute, allocates the netdev and private adapter, initializes completions/locks/work items, registers the primary CRQ, sends CRQ init and version exchange, queries capabilities, requests selected capabilities, queries and controls IP offloads, then initializes stats and registers the netdev. Opening the interface logs in with the VIOS, initializes VPD, NAPI, RX/TX pools, and LTB maps, replenishes RX buffers, enables SCRQ interrupts, sets logical link up, activates TX queues, and starts netdev queues. TX copies skb data into an LTB slot, builds a TX descriptor plus optional header descriptors for checksum/LSO, flushes descriptors either direct or indirect, tracks DQL, and stops the subqueue when SCRQ usage reaches capacity. RX IRQ schedules NAPI, `ibmvnic_poll()` drains RX completion descriptors, copies packet bytes from LTB to skb, restores VLAN metadata if firmware stripped it, marks checksum status, submits via GRO, and replenishes the pool when available buffers fall below half. CRQ tasklet dispatch handles version/capability/login/offload/link/stat/VPD/map responses and transport events.

State and persistence behavior: persistent runtime state is in `struct ibmvnic_adapter` and includes negotiated capabilities, requested queue/ring/MTU tunables, fallback tunables, current protocol version, CRQ/SCRQ rings, DMA tokens, LTB map IDs, RX/TX pool reuse metadata, stats buffers, link state, reset work items, and booleans such as `tx_queues_active`, `failover_pending`, `force_reset_recovery`, `login_pending`, and `wait_for_reset`. The driver intentionally retains LTB allocations across many reset failures to avoid losing connectivity under memory pressure; buffers are freed on close/remove or when size/topology changes. CRQ state is volatile and rebuilt through hypervisor calls. VPD firmware version is read into memory and exposed through ethtool driver info, not persisted to disk. Desired ethtool changes are staged in `adapter->desired`; `wait_for_reset()` stores fallback values and restores them if the reset applying new parameters fails.

Dependencies and integration points: this code depends on Linux netdev, NAPI, ethtool, VLAN, skb, CPU hotplug, workqueue, tasklet, DMA mapping, IOMMU, IRQ mapping, and PowerPC VIO/hypervisor APIs (`plpar_hcall*`, `H_REG_CRQ`, `H_SEND_CRQ`, `H_REG_SUB_CRQ`, `H_SEND_SUB_CRQ_INDIRECT`, `H_VIOCTL`, `vio_register_driver()`). It integrates with VIOS through packed protocol structures from `ibmvnic.h`; with Kbuild through `MODULE_DEVICE_TABLE(vio, ...)`; with sysfs through write-only `failover`; with ethtool through statistics, ring/channel tuning, link settings, and firmware version; with networking core through carrier state, queue start/stop/wake, GRO, checksum/GSO feature negotiation, and XPS/IRQ affinity.

Risks and edge cases: reset serialization is the highest-risk area because transport events, open/close, failover, mobility, TX timeouts, and parameter changes can overlap; the code uses RTNL, state locks, RWI locks, completions, RCU, and `resetting` bits to constrain races. Long-term DMA buffer reuse improves recovery but requires strict map-id accounting and careful LTB size alignment; stale or mismatched LTB mapping can corrupt data path behavior. TX/RX pool free maps are ring-like and rely on correct completion accounting; bugs can leak skbs, double-free, or stall queues. Several firmware workarounds are embedded, including padding packets below min MTU, limiting indirect descriptors after `H_PARAMETER`, clearing XICS pending interrupts after mobility, and retrying login/CRQ init after partial or aborted responses. The code copies all TX/RX payloads through LTB memory rather than mapping skb fragments directly, so large packets, GSO, and fragmentation paths are performance- and bounds-sensitive. Error handling often relies on future firmware signals after `H_CLOSED` or failover-pending cases, so tests need to cover delayed recovery rather than immediate success/failure only.

Test signals: useful signals include successful probe on a VIO `IBM,vnic` device, passive-init recovery from `VNIC_DOWN`, link-up after `ibmvnic_open()`, valid negotiated MTU and queue counts, RX buffer replenishment counters, TX batched/direct packet counters, absence of DQL warnings after non-fatal reset, ethtool stats returning VIOS and per-queue counters, `ethtool -G` and `ethtool -L` triggering `VNIC_RESET_CHANGE_PARAM` with fallback on failure, sysfs failover triggering either hypervisor session failover or queued reset, live partition mobility restoring CRQ/SCRQ and indirect descriptor limits, and TX timeout queuing `VNIC_RESET_TIMEOUT` only after the watchdog interval. Build coverage should include PowerPC VIO configs with DMA/IOMMU and networking features used by the driver.

## sources/distributed-fs/ceph-client/drivers/net/ethernet/ibm/ibmvnic.h

Purpose: private protocol and state header for the IBM virtual NIC driver. It defines the on-wire CRQ/sub-CRQ descriptors exchanged with VIOS, the DMA buffer layout constants, capability and command IDs, return codes, adapter reset/state enums, queue/pool structs, statistics structs, VPD storage, tunables, and the central `struct ibmvnic_adapter` consumed by `ibmvnic.c`.

Important APIs, types, and functions: there are no functions in this header; its API is the set of constants and packed structures. Key constants include `IBMVNIC_MAX_QUEUES`, queue and descriptor sizing, TSO pool sizing, LTB sizing (`IBMVNIC_ONE_LTB_SIZE`, `IBMVNIC_LTB_SET_SIZE`), map-id limits, and reset delay. Protocol buffers include login, login response, IP offload query/control, statistics, ACL, VPD, map/unmap, physical parameters, logical link state, and multicast/MAC control. Descriptor types include TX, header, header extension, SGE, RX completion, RX buffer add, generic CRQ/SCRQ, and TX completion descriptors. `union ibmvnic_crq` and `union sub_crq` provide typed overlays for queue entries. Runtime containers include `ibmvnic_crq_queue`, `ibmvnic_sub_crq_queue`, `ibmvnic_ltb_set`, RX/TX pools and buffers, `ibmvnic_vpd`, `ibmvnic_tunables`, and `ibmvnic_adapter`.

Control flow encoded by definitions: `enum ibmvnic_commands` and `enum ibmvnic_capabilities` define the CRQ negotiation sequence used by the C file: version exchange, capability query/request, login, physical parameter query, link state, statistics, offload setup, VPD, ACL, map/unmap, and VLAN control. `enum vnic_state` constrains lifecycle transitions from probing to probed/opening/open/closing/closed/down/removing/removed. `enum ibmvnic_reset_reason` differentiates failover, mobility, fatal/non-fatal firmware errors, timeout, parameter change, and passive init, which drive reset behavior in the implementation.

State and persistence behavior: `struct ibmvnic_adapter` is the durable in-memory state root. It stores VIO/netdev pointers, CRQ/SCRQ arrays, MAC address, offload buffers and DMA tokens, VPD and firmware version, VIOS statistics token/completions, per-queue software stats, link/speed/duplex state, login buffers and tokens, negotiated capabilities, requested capabilities, LTB map bitmap, active pool/queue counts, previous pool/MTU values for reuse decisions, reset queues/work items, state locks, completions, NAPI state, booleans for reset/failover/login/TX activity, and desired/fallback tunables. Structures are packed/aligned where they are shared with firmware; pool and queue structs are cacheline-aligned for datapath access.

Dependencies and integration points: the header assumes Linux kernel types such as `struct net_device`, `struct sk_buff`, `struct napi_struct`, `struct completion`, `struct vio_dev`, `dma_addr_t`, `atomic_t`, `spinlock_t`, `mutex`, `work_struct`, `delayed_work`, `hlist_node`, bitmaps, and endian-qualified integer types. It is tightly coupled to PowerPC VIO/VIOS protocol semantics and to Linux netdev queueing, DMA, NAPI, and ethtool statistics code in `ibmvnic.c`.

Risks and edge cases: any change to packed layout, endian annotation, alignment, command IDs, descriptor flags, or capability IDs can break firmware interoperability. LTB size constants balance kernel allocation limits against the protocol's 255 map-id limit; changing them affects map pressure and allocation reliability. The header notes assumptions such as uniform RX/TX pool sizing and descriptor-version quirks; implementation changes must preserve these assumptions or update mapping/reuse logic. `struct ibmvnic_adapter` contains multiple lock domains with documented ordering between state and RWI locks; adding state without respecting that ordering risks deadlocks or reset races.

Test signals: compile-time coverage should catch missing kernel type dependencies and packed struct users, but protocol layout needs runtime VIOS tests: successful capability negotiation, login buffer parsing, TX/RX descriptor exchange, LTB map/unmap responses, offload feature setup, VPD retrieval, reset transitions for each reset reason, and queue/pool reuse after MTU or channel changes. ABI-sensitive edits should be validated with structure size/offset review against the VIOS protocol documentation or a known-good trace.

## sources/distributed-fs/ceph-client/drivers/net/ethernet/intel/Kconfig

Purpose: Kconfig menu for Intel Ethernet drivers under `drivers/net/ethernet/intel`. It provides the vendor gate `NET_VENDOR_INTEL`, includes shared Intel library menus, and declares build/configuration symbols for legacy PCI NICs, PCIe gigabit/10GbE/40GbE/E800 drivers, virtual functions, switchdev, hwmon, DCA, DCB, IPsec offload, hardware timestamping, LED trigger support, and the IDPF subdriver.

Important APIs, types, and functions: the file is declarative Kconfig, so the important surface is symbols and dependency/select relationships. Top-level `NET_VENDOR_INTEL` gates the menu. It sources `libeth/Kconfig`, `libie/Kconfig`, and `idpf/Kconfig`. Driver symbols include `E100`, `E1000`, `E1000E`, `IGB`, `IGBVF`, `IXGBE`, `IXGBEVF`, `I40E`, hidden `IAVF`, user-visible compatibility symbol `I40EVF`, `ICE`, `FM10K`, and `IGC`. Feature symbols include `E1000E_HWTS`, `IGB_HWMON`, `IGB_DCA`, `IXGBE_HWMON`, `IXGBE_DCA`, `IXGBE_DCB`, `IXGBE_IPSEC`, `IXGBEVF_IPSEC`, `I40E_DCB`, `ICE_HWMON`, `ICE_SWITCHDEV`, `ICE_HWTS`, and `IGC_LEDS`.

Control flow: menu visibility starts with `config NET_VENDOR_INTEL`; if enabled, the sourced library Kconfigs and all Intel driver prompts are visible according to their `depends on` expressions. Tristate driver selections propagate to the Makefile through `CONFIG_*` object rules. Several drivers `select` common libraries or subsystems, for example `ICE` selects `DIMLIB`, `LIBETH_XDP`, `LIBIE`, `LIBIE_ADMINQ`, `NET_DEVLINK`, `PACKING`, `PLDMFW`, and `DPLL`, while `I40E` selects `AUXILIARY_BUS`, `LIBIE`, `LIBIE_ADMINQ`, and `NET_DEVLINK`. `I40EVF` selects hidden `IAVF` to preserve the old symbol name while building the `iavf` module.

State and persistence behavior: Kconfig writes selected symbols into the kernel configuration and thereby controls what Kbuild compiles as built-in, module, or omitted. Defaults are conservative per feature: vendor gate defaults on, some optional features default on when dependencies are met, and several high-level drivers default off. No runtime state is stored here, but symbol choices persist in `.config` and affect module names, subsystem dependencies, and user-visible prompts.

Dependencies and integration points: dependencies bind Intel drivers to core kernel facilities: `PCI`, `PCI_MSI`, `HAS_IOPORT`, `PTP_1588_CLOCK_OPTIONAL`, `X86`, `PCIE_PTM`, `HWMON`, `DCA`, `DCB`, `XFRM_OFFLOAD`, `ETHTOOL_NETLINK`, `GNSS`, `NET_SWITCHDEV`, `LEDS_CLASS`, and `LEDS_TRIGGER_NETDEV`. `select` statements integrate with shared Intel libraries (`LIBETH`, `LIBETH_XDP`, `LIBIE`, `LIBIE_ADMINQ`, `LIBIE_FWLOG`) and generic subsystems (`AUXILIARY_BUS`, `CRC32`, `I2C`, `I2C_ALGOBIT`, `MDIO`, `NET_DEVLINK`, `PHYLIB`, `PLDMFW`, `XFRM_ALGO`, `NET_SHAPER`, `DIMLIB`, `PACKING`, `DPLL`).

Risks and edge cases: incorrect `select` or `depends on` rules can create invalid configs, especially when built-in drivers select features that are modules or when optional feature symbols combine built-in and module constraints. Compatibility between `I40EVF` and hidden `IAVF` is important for old configs; breaking it can silently drop VF support. Optional helpers such as hwmon, DCA, DCB, IPsec, switchdev, GNSS, PTP, and LEDs are cross-subsystem and need dependency expressions that avoid link failures. Library source order matters because driver symbols select symbols declared in sourced Kconfigs.

Test signals: run Kconfig olddefconfig/allmodconfig fragments enabling each Intel driver as built-in and module, verify no unmet direct dependency warnings, and confirm expected modules map to Makefile outputs (`e100`, `e1000`, `e1000e`, `igb`, `igbvf`, `ixgbe`, `ixgbevf`, `i40e`, `iavf`, `fm10k`, `ice`, `igc`, `idpf`). Specific regression tests should cover `I40EVF -> IAVF`, hwmon built-in/module constraints, `ICE` with `GNSS=m/y/n`, IPsec symbols requiring `XFRM_OFFLOAD`, and timestamp options requiring architecture/platform support.

## sources/distributed-fs/ceph-client/drivers/net/ethernet/intel/Makefile

Purpose: Kbuild dispatcher for Intel Ethernet drivers. It maps Intel-related `CONFIG_*` symbols from `Kconfig` to the library directories, object files, and driver subdirectories that should be built.

Important APIs, types, and functions: the file uses Kbuild `obj-$(CONFIG_...) += ...` and `obj-y += ...` assignments. `CONFIG_LIBETH` gates `libeth/`; `libie/` is always descended into through `obj-y`; driver symbols select `e100.o`, `e1000/`, `e1000e/`, `igb/`, `igc/`, `igbvf/`, `ixgbe/`, `ixgbevf/`, `i40e/`, `iavf/`, `fm10k/`, `ice/`, and `idpf/`.

Control flow: parent network Kbuild enters this directory when Intel Ethernet support is in scope. Kbuild evaluates each object line against the final `.config`; enabled built-in symbols add directories or objects to built-in traversal, module symbols add module build targets, and disabled symbols omit them. `libie/` is always traversed, while `libeth/` is conditional on `CONFIG_LIBETH`.

State and persistence behavior: there is no runtime state. Build state is derived from `.config`, and the outputs persist as built-in objects or loadable modules in the kernel build tree. The unconditional `libie/` line means its subdirectory Makefile must be safe when consumers are disabled.

Dependencies and integration points: this Makefile is paired with `drivers/net/ethernet/intel/Kconfig`; symbol names must remain synchronized. It integrates with subdirectory Makefiles for multi-object drivers and with the parent `drivers/net/ethernet/Makefile`. The `CONFIG_IAVF` object rule intentionally builds `iavf/`, matching Kconfig's hidden `IAVF` symbol selected by legacy `I40EVF`.

Risks and edge cases: symbol drift between Kconfig and Makefile will produce drivers that can be configured but not built, or directories that are built without a user-visible symbol. Unconditional library traversal can expose latent build errors if subdirectory Makefiles do not guard their objects. Ordering of common libraries before consumers is useful for clarity, though Kbuild dependency resolution handles most link ordering.

Test signals: enable each Intel driver symbol as `m` and `y` in targeted build fragments and verify the expected object or subdirectory appears in the build. Check that `CONFIG_I40EVF=m` results in `CONFIG_IAVF=m` and builds `iavf/`, that `CONFIG_LIBETH` controls `libeth/`, and that disabling all Intel drivers still allows the unconditional `libie/` traversal to complete without building unwanted driver modules.
