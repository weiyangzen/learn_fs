# sources/object-store/apache-ozone/hadoop-ozone/integration-test/src/test/java/org/apache/hadoop/fs/contract/ContractTestUtils.java

Purpose: `ContractTestUtils` is a broad, static utility class used by filesystem contract and Ozone integration tests. It centralizes byte-pattern file generation, write/read verification, cleanup, path existence assertions, listing conversion, recursive tree construction/scanning, capability assertions, vectored-read validation, and simple timing/bandwidth diagnostics. In this subset it is the shared assertion and fixture layer used by both `OzoneFileSystem` and `RootedOzoneFileSystem` tests.

Important APIs and types: The class exposes helpers around Hadoop `FileSystem`, `FileContext`, `FSDataInputStream`, `FSDataOutputStream`, `FileStatus`, `LocatedFileStatus`, `RemoteIterator`, `FileRange`, `ByteBufferPool`, `StreamCapabilities`, and `PathCapabilities`. Key APIs include `writeAndRead`, `writeDataset`, `readDataset`, `verifyFileContents`, `compareByteArrays`, `createFile`, `touch`, `appendFile`, `assertDeleted`, `assertRenameOutcome`, `assertIsFile`, `assertIsDirectory`, `assertPathExists`, `assertPathDoesNotExist`, `dataset`, `validateVectoredReadResult`, `returnBuffersToPoolPostRead`, `createAndVerifyFile`, `createSubdirs`, `treeWalk`, iterator-to-list helpers, and capability assertion helpers. Nested `TreeScanResults` stores categorized path lists, and `NanoTimer` records elapsed time and bandwidth.

Control flow: Most helpers follow an execute-and-assert pattern: create parents, write bytes, read back exactly, compare every byte, then optionally delete and verify absence. Assertion failures add context by listing parents, dumping file statuses, or logging nearby bytes around the first mismatch. Root-sensitive operations call `rejectRootOperation` before delete or rename unless explicitly allowed. Listing helpers normalize Hadoop `RemoteIterator` results into lists and include a `next()`-only path to test iterator correctness without prior `hasNext()` calls. Tree helpers recursively create deterministic directory/file layouts and recursively scan depth-first to compare actual listings with expected structures.

State and persistence behavior: The utilities do not own persistent state, but they create, mutate, and delete files and directories in the target filesystem under test. They also read filesystem configuration for buffer/modulus sizing, use generated UUID names for large-file tests, and may return pooled buffers after vectored reads. `TreeScanResults` holds in-memory snapshots of files, directories, and other statuses; equality intentionally compares counts while `assertEquivalent` checks exact path membership and duplicates. `NanoTimer` holds only start and end timestamps.

Dependencies and integration points: The file depends on AssertJ, Hadoop filesystem APIs, `RemoteIterators`, `FutureIO`, and SLF4J. Ozone tests call these helpers to avoid duplicating common touch/create/delete/list assertions. Capability helpers integrate with stream and path capability contracts such as `StreamCapabilities.UNBUFFER`; vectored-read helpers integrate with Hadoop asynchronous range-read APIs.

Risks: These helpers are assertion-heavy and can shape test semantics across many suites. Root-operation guards are important because a mistaken path can delete an entire test filesystem. `readDataset` expects the requested length to be readable and throws EOF if not. `compareByteArrays` assumes equal length and logs only a small error window. `TreeScanResults.dump` labels files and directories in a confusing order, which can affect diagnostics but not behavior. Vectored read validation depends on bounded future timeouts and returns buffers only when callers invoke the pool-return helper.

Test signals: Strong signals are exact byte equality, file length equality, successful path existence/non-existence checks, expected delete/rename return values, duplicate-free listing equivalence, expected recursive tree counts, correct vectored-read ranges, explicit presence or absence of stream/path capabilities, and bandwidth/timer logs for large-file exercises.

# sources/object-store/apache-ozone/hadoop-ozone/integration-test/src/test/java/org/apache/hadoop/fs/ozone/AbstractOzoneFileSystemTest.java

Purpose: This abstract JUnit suite exercises `OzoneFileSystem` (`o3fs`) behavior that is not fully covered by generic contract tests. It mounts a single bucket as the filesystem root and validates file, directory, listing, rename, delete, trash, replication, metrics, block-location, snapshot, link-bucket, and OM metadata behavior across configurable bucket layouts.

Important APIs and types: The suite extends `OzoneFileSystemTestBase` and uses `MiniOzoneCluster`, `OzoneClient`, `ObjectStore`, `OzoneBucket`, `OzoneVolume`, `OzoneManagerProtocol`, `OzoneFileSystem`, `OzoneFSStorageStatistics`, `Trash`, `OMMetrics`, `OMMetadataManager`, `OmKeyArgs`, `OpenKeySession`, `OzonePrefixPathImpl`, `OzoneFileStatus`, `OzoneKeyDetails`, `BucketLayout`, `ECReplicationConfig`, `RatisReplicationConfig`, `StandaloneReplicationConfig`, `LocatedFileStatus`, and `BlockLocation`. It delegates common checks to base-class helpers such as `createDoesNotAddParentDirKeys`, `fileDelete`, `verifyListStatus`, `listStatusIterator*`, `renameFile`, `renameFileToDir`, `renameToParentDir`, `setTimes`, and `fileSystemDeclaresCapability`.

Control flow: `init` configures a five-datanode `MiniOzoneCluster`, enables ACLs, trash, hsync, HBase enhancements, batch iteration size, and bucket layout, creates one volume/bucket, sets `fs.defaultFS` to `o3fs://bucket.volume/`, opens the filesystem, captures storage statistics, and creates a non-default user filesystem. `cleanup` deletes all root children after each test. Individual tests create files and directories through public `FileSystem` APIs or directly through OM/client APIs, then check `FileStatus`, metadata tables, metrics, and object-store state.

State and persistence behavior: Persistent state lives in the test Ozone cluster: volumes, buckets, keys, directory marker keys, open keys, snapshots, trash paths, and bucket replication defaults. Runtime state includes filesystem statistics snapshots, OM metrics, user identity via `UserGroupInformation`, and a cached adapter view of bucket defaults. Tests intentionally verify fake directory behavior for non-FSO layouts, explicit directory key behavior, refreshed bucket replication after adapter clock advancement, trash checkpoint purging, snapshot read isolation, and block allocations for multi-block files.

Dependencies and integration points: The suite integrates the Hadoop `FileSystem` API with Ozone Manager, object-store client APIs, OM metadata tables, native ACL behavior, trash policies, key manager prefix listing, link buckets, and datanode-backed block locations. It also checks compatibility boundaries such as rejecting `OBJECT_STORE` buckets for filesystem semantics and handling invalid checksum combine mode by returning no checksum.

Risks: Many tests are layout-dependent and use `assumeFalse(FILE_SYSTEM_OPTIMIZED...)` where legacy fake-directory semantics differ from FSO object-ID semantics. Timing-sensitive tests wait for list status, trash emptier cleanup, and refreshed bucket replication. User switching through `UserGroupInformation.setLoginUser` must restore the original user. Root cleanup must avoid trash artifacts through filters. Tests involving link-bucket loops, snapshots, and multi-block files depend on cluster services and OM metrics being stable.

Test signals: Key signals include expected `FileAlreadyExistsException` and `FileNotFoundException` paths, exact root and subdirectory listing sizes, owner/group attribution for real and proxy users, EC flags on intermediate and leaf statuses, large-directory pagination correctness, delete and rename return values for edge cases, stable modification time semantics, trash root discovery and purge, OM metric deltas, storage-statistic deltas, block-location host/name/offset/length values, `pathToKey` conversion, snapshot listing counts, and explicit failure on incompatible bucket layout.

# sources/object-store/apache-ozone/hadoop-ozone/integration-test/src/test/java/org/apache/hadoop/fs/ozone/AbstractOzoneFileSystemTestWithFSO.java

Purpose: This subclass specializes the `o3fs` test suite for `FILE_SYSTEM_OPTIMIZED` buckets. It focuses on FSO-specific semantics: object-ID directory tables, non-recursive listing, recursive file iteration, rename validation, parent and bucket modification time updates, open-key commit layout, lease recovery, logging for missing deletes, and a regression where deleted children in the double-buffer cache should not keep a parent directory from being deleted.

Important APIs and types: The class extends `AbstractOzoneFileSystemTest` with `super(true, BucketLayout.FILE_SYSTEM_OPTIMIZED)`. It uses `OMMetadataManager`, `OmBucketInfo`, `OmDirectoryInfo`, `OmKeyInfo`, `OzoneManagerDoubleBuffer`, `LeaseRecoverable`, `LocatedFileStatus`, `RemoteIterator`, `LogCapturer`, and inherited `OzoneFileSystem` accessors. Helpers `verifyDirKey`, `verifyOMFileInfoFormat`, and `renameAndAssert` inspect FSO database key formats and metadata timestamps directly.

Control flow: Tests create nested files and directories with the mounted `o3fs` URI and assert that `listStatus` returns only immediate children while `listFiles(..., true)` returns all files recursively. Rename overrides assert failures for moving a directory into its own child or into a missing/file parent. Modification-time tests capture source parent, destination parent, bucket, and file mtimes before and after rename, expecting parent/bucket changes only when affected and preserving renamed object mtimes. `testCreateFile` opens a file, verifies parent directory-table entries, closes the stream to commit the key, then waits until the open-key table is empty. `testDeleteParentAfterChildDeleted` pauses the OM double buffer, deletes child directory and file, and verifies the parent can still be deleted.

State and persistence behavior: FSO persistence is explicitly object-ID based. Directory rows are expected under `/volumeId/bucketId/parentObjectId/name`, file key rows are expected under `/volumeId/bucketId/parentObjectId/fileName`, and `OmKeyInfo.path` stores `parentID/fileName`. The suite verifies OM `numKeys` metrics for created directories, object IDs for sibling dirs, open-key cleanup after commit, TableCache/double-buffer behavior, and log output when deleting a missing path.

Dependencies and integration points: These tests connect public `FileSystem` operations to FSO-specific OM tables and the Ratis double-buffer pipeline. Lease tests integrate `LeaseRecoverable.isFileClosed` and `recoverLease` with hsync-visible open files. Listing tests exercise Ozone's FSO path resolution rather than legacy prefix-only key scanning.

Risks: The class is tightly coupled to internal OM DB key formats, object ID allocation, and double-buffer behavior. `@TestMethodOrder` plus `@Order(1)` on file creation hints at sensitivity around shared class-level cluster state. Pausing the double buffer must always be undone. Log-message assertions can be brittle if wording changes. Some comments still refer to "prefix layout", but the constructor unambiguously selects FSO.

Test signals: Strong signals include exact qualified paths in `listStatus` and `listFiles`, expected false return values for invalid renames, increasing parent/bucket mtimes where required, unchanged file mtime after rename, valid directory-table and key-table DB rows, OM `numKeys` counts, empty open-key table after commit, `isFileClosed` state transitions around hsync and lease recovery, warning logs for missing delete, and successful parent deletion while deleted children are still buffered.

# sources/object-store/apache-ozone/hadoop-ozone/integration-test/src/test/java/org/apache/hadoop/fs/ozone/AbstractRootedOzoneFileSystemTest.java

Purpose: This abstract suite validates `RootedOzoneFileSystem` (`ofs`) behavior across the full namespace rooted at `/`, where paths include `/volume/bucket/key` and may also reference special mounts such as `/tmp`. It covers volume and bucket creation/deletion, bucket-level listings, recursive adapter listings, ACL-sensitive root listing, trash across buckets, link buckets, symlink-like shell semantics, replication inheritance, content summary disk usage, snapshots and snapshot diff, linked-bucket `setTimes`, and DistCp replication behavior.

Important APIs and types: The suite uses `RootedOzoneFileSystem`, `BasicRootedOzoneClientAdapterImpl`, `OFSPath`, `MiniOzoneCluster`, `OzoneClient`, `ObjectStore`, `ClientProtocol`, `OzoneVolume`, `OzoneBucket`, `BucketArgs`, `VolumeArgs`, `OzoneAcl`, `OMMetrics`, `Trash`, `OzoneFsShell`, `DistCp`, `DistCpOptions`, `CopyMapper.Counter`, `SnapshotDiffReport`, `ContentSummary`, `QuotaUtil`, `ECReplicationConfig`, `RatisReplicationConfig`, and common Hadoop `FileSystem` types. It inherits shared filesystem behavior checks from `OzoneFileSystemTestBase`.

Control flow: `initClusterAndEnv` builds a five-datanode cluster, configures trash, hsync, ACL authorizer, bucket layout defaults, list batch size, snapshot diff page size, and `ofs://` default filesystem, then opens both admin and non-privileged OFS instances. `createVolumeAndBucket` creates a fresh test volume/bucket before each test and `cleanup` deletes it after each test. Tests often create additional random volumes/buckets, use public OFS paths to mutate them, then verify through both `FileSystem` and object-store APIs. Recursive listing tests compare adapter-level DFS results with a simulated recursive `FileSystem.listStatus` traversal.

State and persistence behavior: Persistent state includes real Ozone volumes, buckets, keys, link buckets, trash directories, snapshots, EC/Ratis key metadata, ACLs, and temporary mount buckets. Tests validate deletion ordering from key to bucket to volume, non-recursive failure on non-empty directories/volumes, root deletion failure, owner propagation for volume and bucket listings, shared and per-user `/tmp` mount creation, trash checkpoints and OM trash metrics, snapshot contents, snapshot diff pagination aggregation, and DistCp-created keys. Runtime state includes the current bucket path, cluster metrics, adapter listing continuation state, and UGI-derived user paths.

Dependencies and integration points: The suite spans the Hadoop FS surface, Ozone object-store admin APIs, OM ACL enforcement, shell commands via `ToolRunner`, snapshot APIs, MapReduce DistCp, and low-level adapter listing continuations. It also checks Ozone-specific features such as link bucket loop/target behavior, non-admin bucket creation under permissive ACLs, OFS shared temp directory policy, and storage-space accounting for EC and Ratis replication.

Risks: The suite is environment- and timing-sensitive because it starts a real cluster, waits for trash emptier behavior, and uses random names. ACL-enabled and ACL-disabled modes produce different root listing counts. Several tests are skipped for FSO or filesystem-path-enabled layouts where semantics differ. Link bucket delete semantics intentionally distinguish deleting the link from deleting target contents and rely on shell path trailing-slash behavior. DistCp tests depend on MapReduce counters and checksum skip behavior. Snapshot diff assertions assume deterministic diff ordering for created keys.

Test signals: Signals include exact home directory path, volume/bucket auto-creation via `mkdirs`, `OMException` result codes for missing volume/bucket/key or permission denied, listing sizes at bucket, volume, and root levels, recursive adapter/listStatus equivalence, continuation page counts, owner/group fields, successful and failed deletes/renames, trash root counts and OM metric deltas, link bucket source preservation, root delete returning false, replication type and factor expectations, `UNBUFFER` capability, content-summary space consumed for EC/Ratis, snapshot listing and diff sizes, linked-bucket mtime update, DistCp copy counters, and skipped-copy behavior on matching checksums.

# sources/object-store/apache-ozone/hadoop-ozone/integration-test/src/test/java/org/apache/hadoop/fs/ozone/AbstractRootedOzoneFileSystemTestWithFSO.java

Purpose: This subclass adapts the rooted `ofs` suite to `FILE_SYSTEM_OPTIMIZED` buckets. It verifies FSO-specific rename, delete, listing, and lease-recovery behavior under `/volume/bucket`, where rooted OFS path parsing must cooperate with object-ID-backed bucket internals.

Important APIs and types: The class extends `AbstractRootedOzoneFileSystemTest` with `BucketLayout.FILE_SYSTEM_OPTIMIZED`, filesystem paths enabled, and a constructor-supplied ACL mode. It uses `RootedOzoneFileSystem`, `Path`, `FileStatus`, `FSDataOutputStream`, `LeaseRecoverable`, `BucketLayout`, `ContractTestUtils`, and inherited accessors such as `getBucketPath`, `getFs`, and `getOMMetrics`.

Control flow: Override tests re-run rename edge cases using rooted paths. `testRenameDestinationParentDoesNotExist` creates `/volume/bucket/root_dir/dir1/dir2`, then verifies rename fails when the destination parent is missing and when the destination parent is a file. `testKeyRenameToBucketLevel` renames a nested key/directory to the bucket root and verifies the leaf appears at bucket level. `testRenameDir` moves a directory to a sibling `.renamed` path and confirms child directories move with it. `testRenameDirToItsOwnSubDir` validates false return and cleans up. `testDeleteVolumeAndBucket` creates a bucket tree with ten directories and six files, recursively deletes the bucket, deletes the volume, and expects only one key-delete metric increment for the bucket-level delete. `testListStatusFSO` creates and renames 1200 keys to populate TableCache beyond the listing batch size and verifies all are listed. `testLeaseRecoverable` checks open-file visibility, hsync, lease recovery, and closed-file state.

State and persistence behavior: The tests persist real FSO directory and key entries under a test bucket. The large listing test intentionally leaves renamed keys in cache before calling `listStatus`, protecting consistency between table cache and DB scans. Delete metrics assert that recursive bucket deletion is accounted at the aggregate key-delete level rather than per-child in this FSO path. Lease recovery mutates open-key/committed-key state and changes `isFileClosed` from not found, to open, to closed.

Dependencies and integration points: This subclass depends on the rooted OFS base cluster and its object-store cleanup, while specifically exercising FSO internals through public `RootedOzoneFileSystem` APIs. It integrates rename validation, bucket-root path handling, OM metrics, TableCache listing, and `LeaseRecoverable` with FSO layout.

Risks: The tests assume FSO recursive delete accounting remains a single key-delete metric increment. The 1200-key test is designed around a 1024 listing batch and may need adjustment if the batch contract changes. Cleanup is important because the tests create paths at bucket and volume levels. The lease test must close streams carefully because lease recovery can remove the open key before normal close.

Test signals: Signals include false rename results for invalid destinations, existence of renamed bucket-level and sibling paths, preservation of renamed children, successful bucket and volume deletion, expected OM key-delete metric delta, exact 1200-entry listing count with cache pressure, `FileNotFoundException` for `isFileClosed` before hsync visibility, false open-file state after hsync, true `recoverLease`, and true closed-file state afterward.
