# sources/distributed-fs/ceph-client/drivers/scsi/elx/libefc_sli/sli4.c

Purpose: implements the common, transport-independent SLI-4 operations used by the Broadcom/Emulex EFC Fibre Channel stack. It turns the hardware protocol layouts from `sli4.h` into executable mailbox commands, queue allocation/destruction, doorbell operations, completion parsing, WQE construction, firmware setup/reset, resource-id allocation, and link event callback delivery.

Important APIs/types/functions: public setup and lifecycle APIs are `sli_setup()`, `sli_init()`, `sli_reset()`, `sli_fw_reset()`, `sli_teardown()`, `sli_fw_ready()`, `sli_reset_required()`, `sli_raise_ue()`, and `sli_dump_is_ready()`. Queue APIs include `__sli_queue_init()`, `__sli_create_queue()`, `sli_queue_alloc()`, `sli_cq_alloc_set()`, `sli_fc_rq_alloc()`, `sli_fc_rq_set_alloc()`, `sli_queue_free()`, `sli_queue_arm()`, `sli_queue_eq_arm()`, and the EQ/CQ/MQ/WQ/RQ read/write helpers. WQE builders cover aborts, ELS requests/responses, FCP initiator command/read/write, FCP target receive/continue/response/send, CT generic requests, BLS responses, send-frame, transmit-sequence, and XRI requeue. Mailbox builders cover link, VFI/VPI/RPI/FCFI registration, NV parameters, topology, link/status counters, object read/write/delete, DMTF CLP, dump location, features, watchdog, SGL page posting, and header templates. Completion utilities include `sli_eq_parse()`, `sli_cq_parse()`, `sli_fc_cqe_parse()`, `sli_fc_rqe_rqid_and_index()`, length/status helpers, and `sli_fc_get_status_string()`.

Control flow: initialization begins in `sli_setup()`, which clears `struct sli4`, records OS/PCI/register handles, validates `SLI_INTF`, resolves ASIC generation/revision, allocates the bootstrap mailbox and VPD DMA buffers, initializes/reset-waits firmware through `sli_fw_init()`, queries features, and reads device configuration. `sli_get_config()` chains `READ_CONFIG`, `GET_SLI4_PARAMETERS`, controller attributes, port name, firmware revision, and NV parameters, populating queue limits, resource extents, topology, WWPN/WWNN, firmware/hardware revision strings, SGL/WQE capabilities, and timing values. `sli_init()` then requests the final feature set after dropping unsupported high-login/RX sequence features.

Control flow for queues is allocation-first, command-second, hardware-create-third. `__sli_queue_init()` allocates coherent DMA and initializes queue metadata; queue-specific command builders encode the DMA page list into a bootstrap mailbox `SLI_CONFIG` payload; `__sli_create_queue()` submits the mailbox and records the firmware-assigned queue id and doorbell address. CQ and RQ set creation use non-embedded DMA payloads and response queue-set structures. Read paths validate phase/valid bits for EQ/CQ, copy entries out, advance indices, update posted counts, and toggle phase on IF_TYPE_6 wraparound. Write paths copy WQE/MQE/RQE entries to coherent queue memory, optionally set WQ id association, ring the right doorbell, and advance indices.

Control flow for command generation is mostly stateless builders. Each `sli_cmd_*` or `sli_*_wqe()` function zeros the destination buffer, validates required DMA/parameter inputs where needed, fills little-endian fields, selects embedded versus non-embedded SLI_CONFIG payloads through `sli_config_cmd_init()`, and returns `0` or `-EIO`. Completion parsing dispatches on CQE code: WQ completions return request tags, RQ completions return RQ ids and element indices, optimized-write completions return RQ/XRI data, XRI-aborted and WQ-release events get distinct `SLI4_QENTRY_*` types, MQ completions distinguish async events from mailbox completions, and FC link ACQEs are converted into `struct sli4_link_event` for the registered callback.

State and persistence behavior: all persistent state is in memory in `struct sli4`, `struct sli4_queue`, DMA buffers, and resource bitmaps. The driver persists no data to disk. Hardware state is changed through MMIO register writes, bootstrap mailbox submissions, firmware feature requests, queue create/destroy commands, resource registration commands, and SLI port/firmware reset writes. Resource ids for VFI/VPI/RPI/XRI are modeled with extent base arrays and `use_map` bitmaps derived from `READ_CONFIG`; `sli_resource_alloc/free/reset()` mutate those maps and allocation counters. Queue state tracks DMA backing, host index, phase, posted counts, firmware queue id, doorbell address, and MQ read index or queue flags. `sli4->bmbx_non_emb_pmd` is only a pointer to the current non-embedded mailbox payload for diagnostics.

Dependencies and integration points: depends on `sli4.h` hardware layouts, `efc_common.h` logging/DMA abstractions, Linux PCI/MMIO/DMA/bitmap/time helpers, and FC protocol constants from `scsi/fc`. It is consumed by `drivers/scsi/elx/efct/efct_hw.c` for adapter bring-up, mailbox operations, link control/statistics/object commands, SGL posting, resource setup, and IO WQE dispatch; by `efct_hw_queues.c` for EQ/CQ/MQ/WQ/RQ allocation and completion handling; and by `libefc/efc_cmds.c` for domain/nport/rnode VFI/VPI/RPI registration. The callback API currently exposes link events via `SLI4_CB_LINK`.

Risks and test signals: high-risk areas are hardware ABI packing, endian conversion, DMA payload sizing, page-count limits, queue phase handling, doorbell register selection for IF_TYPE_2 versus IF_TYPE_6, bootstrap mailbox timeout/error handling, and resource bitmap lifetime across resets. Several paths return `-EIO` after allocating DMA without local cleanup if a later command-build step fails, so callers must own cleanup or leaks are possible. Some WQE fields are width-sensitive, including transfer lengths stored in 16-bit fields, XRI counts, CQ/RQ page descriptors, and object-name copies. Test signals include adapter probe on supported/unsupported SLI_INTF/ASIC IDs, firmware-not-ready and firmware-error rejection, queue create/destroy for all legal entry counts, CQ/RQ set allocation failure unwinding, EQ/CQ valid-bit wrap on both interface types, RQ id/index extraction for all CQE variants, WQE byte-pattern validation for initiator/target/ELS/BLS paths, link attention callback mapping, reset followed by resource reinitialization, and fault injection for DMA allocation/mailbox completion statuses.

# sources/distributed-fs/ceph-client/drivers/scsi/elx/libefc_sli/sli4.h

Purpose: defines the SLI-4 hardware/software contract used by `sli4.c` and the EFC driver stack. It contains register offsets, bit masks, queue/CQE/WQE/mailbox layouts, feature/resource enums, runtime state structures, inline formatting/parsing helpers, and public prototypes for common SLI-4 operations.

Important APIs/types/functions: register and doorbell definitions cover `SLI4_INTF_REG`, BMBX, port control/status/error, IF_TYPE_2 and IF_TYPE_6 EQ/CQ/MQ/RQ/WQ doorbells, and PHYDEV reset/dump control. Important data structures include `struct sli4`, `struct sli4_queue`, `struct sli4_params`, `struct sli4_queue_info`, `struct sli4_extent`, `struct sli4_sge`, `struct sli4_bde`, EQE/MCQE/ACQE/CQE variants, FC WQE formats, mailbox command/response formats, common SLI_CONFIG request/response headers, resource descriptors, and parameter blocks for BLS/ELS/CT/FCP target WQE builders. Inline helpers format doorbell writes, compute page counts, fill request headers, read SLI registers, convert queue-count masks, query max SGL/SGE, set topology, extract RQE lengths/FCFI, and set WQ id association.

Control flow: the header itself has no runtime loop, but it encodes the control flow expected by the implementation. Callers initialize `struct sli4` with PCI/register handles, use mailbox command structs to negotiate features/configuration, allocate `struct sli4_queue` objects for EQ/CQ/MQ/WQ/RQ, construct WQEs from parameter structs, parse completions into `SLI4_QENTRY_*` events, and manage hardware resource identifiers through `enum sli4_resource`. The prototypes at the end form the exported local API from the SLI layer to `efct_hw`, queue handling, and EFC command code.

State and persistence behavior: state definitions are in-memory only. `struct sli4` caches firmware/configuration identity, WWPN/WWNN, topology, timing, queue/resource capabilities, resource allocation bitmaps, negotiated features, callback pointers, the bootstrap mailbox DMA buffer, optional non-embedded mailbox payload pointer, and VPD DMA storage. `struct sli4_queue` stores coherent DMA backing, queue indices, firmware queue id, doorbell address, phase state, posted counts, processing limits, and queue flags. The header also defines hardware-visible command structures; correctness depends on matching firmware layout and little-endian fields rather than any disk persistence.

Dependencies and integration points: includes Linux PCI/delay support, Fibre Channel ELS/frame constants, and `../include/efc_common.h` for driver-common types such as `struct efc_dma` and logging. It is the central shared contract for `libefc_sli/sli4.c`, `efct/efct_hw.c`, `efct/efct_hw_queues.c`, and `libefc/efc_cmds.c`. FC constants and ELS command ids from the SCSI FC headers feed WQE builder decisions, while Linux MMIO helpers are used by inline register readers and doorbell formatting consumers.

Risks and test signals: this is ABI-sensitive code. Risks include struct layout drift, missing `__le*` conversions in users, masks that overlap or are reused with different meanings, IF_TYPE-specific doorbell mismatches, flexible-array payload sizing mistakes, resource enum/order assumptions, and queue/CQE phase semantics getting out of sync with firmware. Compile coverage with `W=1`, sparse endian checks, structure size/offset assertions where practical, and hardware or emulated mailbox tests should focus on every command layout consumed by `sli4.c`, CQE code parsing, SGL/page descriptor limits, `sli_get_max_sgl()` behavior for unsupported page-size bitmaps, and reset/resource lifetime interactions.

# sources/distributed-fs/ceph-client/drivers/scsi/esas2r/Kconfig

Purpose: declares the kernel configuration option for the ATTO ExpressSAS RAID adapter driver.

Important APIs/types/functions: defines `config SCSI_ESAS2R` as a tristate option named "ATTO Technology's ExpressSAS RAID adapter driver". It depends on `PCI` and `SCSI` and describes support for ATTO ExpressSAS R6xx SAS/SATA RAID controllers.

Control flow: no runtime control flow. At configuration time, enabling this option as built-in or module controls whether the ESAS2R object list in the local Makefile is built and linked into the kernel or module tree.

State and persistence behavior: the only persistent state is the selected kernel configuration value in the build configuration. It does not create runtime state.

Dependencies and integration points: integrates with the SCSI driver Kconfig hierarchy and the local `Makefile` through `CONFIG_SCSI_ESAS2R`. The dependency gates prevent building this PCI SCSI host driver without the PCI bus and SCSI core.

Risks and test signals: risks are limited to dependency accuracy and discoverability. Test signals include `oldconfig/menuconfig` visibility with PCI+SCSI enabled, hidden/disabled behavior when either dependency is missing, module and built-in builds, and successful inclusion of `esas2r.o` when `CONFIG_SCSI_ESAS2R=m` or `y`.

# sources/distributed-fs/ceph-client/drivers/scsi/esas2r/Makefile

Purpose: describes how the ATTO ExpressSAS RAID driver is built from its component objects when `CONFIG_SCSI_ESAS2R` is enabled.

Important APIs/types/functions: sets `obj-$(CONFIG_SCSI_ESAS2R) += esas2r.o` and composes `esas2r-objs` from `esas2r_log.o`, `esas2r_disc.o`, `esas2r_flash.o`, `esas2r_init.o`, `esas2r_int.o`, `esas2r_io.o`, `esas2r_ioctl.o`, `esas2r_targdb.o`, `esas2r_vda.o`, and `esas2r_main.o`.

Control flow: no runtime control flow. Kbuild uses the config-selected `obj-*` assignment to build either a module or built-in object, then links the listed component objects into the composite `esas2r.o`.

State and persistence behavior: build metadata only. The file creates no runtime state; it determines object inclusion and link composition during kernel builds.

Dependencies and integration points: integrates with `Kconfig` via `CONFIG_SCSI_ESAS2R` and with the ESAS2R source files that implement logging, discovery, firmware, initialization, interrupts, I/O, ioctls, target database, VDA management, and module entry points. Link ordering can matter for initialization data, exported/local symbols, and dead-code diagnostics.

Risks and test signals: risks are missing object files, stale object names after refactors, and link failures if the composite omits a translation unit that provides referenced symbols. Test signals include `make M=drivers/scsi/esas2r` or full kernel builds for `m` and `y`, modpost symbol checks, and smoke-loading the module on compatible PCI configurations.

# sources/distributed-fs/ceph-client/drivers/scsi/esas2r/atioctl.h

Purpose: defines the user/kernel IOCTL ABI and management payload layouts for the ATTO ExpressSAS RAID driver. It covers legacy Express ioctl commands, CSMI SAS management structures, ATTO HBA tunnel commands, VDA management commands, SMP discovery/command payloads, status codes, and the top-level `struct atto_express_ioctl` carrier.

Important APIs/types/functions: the common header is `struct atto_express_ioctl_header` with the `"Express"` signature, return code, channel, retry count, and command range `EXPRESS_IOCTL_MIN` through `EXPRESS_IOCTL_MAX`. Firmware/configuration payloads include `atto_firmware_rw_request`, `atto_param_rw_request`, channel list/info structures, and return codes such as `IOCTL_SUCCESS`, `IOCTL_INVALID_PARAM`, and `IOCTL_GENERAL_ERROR`. CSMI support is represented by `CSMI_CC_*` control codes, `CSMI_STS_*` status codes, class-independent controller/driver/firmware structures, RAID information structures, HBA PHY/passthrough/address/task-management structures, PHY-control structures, `union atto_ioctl_csmi`, and `struct atto_csmi`. ATTO-specific HBA tunnel support is represented by `struct atto_ioctl` and payloads for adapter info/address, memory read/write, trace, SCSI pass-through, device address/info, and adapter control. VDA and SMP payloads are represented by `struct atto_ioctl_vda_*`, `struct atto_ioctl_vda`, `struct atto_ioctl_smp`, and the final union in `struct atto_express_ioctl`.

Control flow: the header has no executable control flow, but it defines the dispatch contract used by `esas2r_ioctl.c`. User space submits an Express ioctl command number with a signed header and one union payload. The driver validates command range/signature/channel, copies the fixed top-level object from user memory, dispatches by command number to firmware, params, channels, SMP, CSMI, HBA, VDA, module-info, or adapter-id handling, and copies the updated top-level object back. Nested `function`, `control_code`, version, status, and length fields further dispatch HBA/VDA/CSMI/SMP operations.

State and persistence behavior: these structures are ABI data carriers, not owned persistent state. They may cause runtime changes when handled by implementation code, including firmware downloads/uploads, parameter reads/writes/defaults, memory access, trace state changes, SCSI/SMP passthrough, VDA configuration/management, adapter resets, and task management. Several fields are flexible or variable-length (`contents[]`, `version_info[]`, `data[1]`, `byte[1]`, large firmware image buffers), so persistence and bounds are controlled by the ioctl handlers rather than this header.

Dependencies and integration points: includes `atvda.h` for VDA configuration and management payload types such as `atto_vda_cfg_init`, `atto_vda_devinfo`, and related information structures. It is included by `esas2r.h`; `esas2r_ioctl.c` uses the command codes and layouts for ioctl dispatch, `esas2r_main.c` exposes sysfs/local buffered HBA ioctl access, discovery code uses `struct atto_ioctl`, and VDA code uses `struct atto_ioctl_vda`. The ABI is tied to user-space ATTO management tools and CSMI-compatible applications.

Risks and test signals: this is a high-risk UAPI-style header even though it lives in the driver tree. Risks include packed/alignment mismatches, 32-bit versus 64-bit pointer-size differences in `struct atto_module_info`, fixed top-level copy sizes that do not cover variable-length payloads, huge embedded firmware image size in `atto_firmware_rw_request`, unchecked `data_length`/`cmd_rsp_len`/`req_length` fields in handlers, and ABI breakage if fields are reordered or resized. Test signals include ioctl fuzzing around length/version/function/status fields, compat-user testing where applicable, CSMI command coverage for supported and unsupported controls, HBA tunnel memory/trace/SCSI pass-through bounds tests, VDA variable payload length tests, SMP direct/non-direct discovery commands, invalid signature/channel/command handling, and structure size checks against user-space tooling expectations.
