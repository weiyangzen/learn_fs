# sources/user-network-fs/samba/source3/rpc_server/spoolss/srv_iremotewinspool.c

Purpose: implements the generated DCERPC endpoint server glue for Samba's `iremotewinspool` interface. It exposes the MS-RPRN async/remote winspool interface UUID and syntax version, validates the required object UUID on calls, forwards most operations into the existing `spoolss` server after opcode remapping, and locally dispatches the few iremotewinspool operations that do not map to spoolss.

Important APIs/types/functions: `forward_opnum_to_spoolss()` is the routing gate; it keeps opnums 58, 59, 60, 61, 62, 63, 65, and 67 on the iremotewinspool implementation path and forwards all other opnums. `iremotewinspool__op_ndr_pull()`, `iremotewinspool__op_dispatch()`, `iremotewinspool__op_reply()`, and `iremotewinspool__op_ndr_push()` are the DCERPC server callbacks. `iremotewinspool_map_opcode()` translates iremotewinspool async opnums into the corresponding `spoolss` opnums before delegating to `spoolss__op_*()`. `dcesrv_iremotewinspool_interface` declares syntax UUID `76f03f96-cdfd-44fc-a22c-64950a001209` version 1.0, and `iremotewinspool_get_ep_server()` returns the endpoint server registration object.

Control flow: bind/unbind are no-op unless build-time override macros are supplied. NDR pull starts with the incoming opnum; for forwarded calls it rewrites `dce_call->pkt.u.request.opnum` to the mapped spoolss opnum when a mapping exists, then calls `spoolss__op_ndr_pull()`. For non-forwarded calls it bounds-checks against `ndr_table_iremotewinspool.num_calls`, tallocs the generated request struct, and invokes the generated NDR pull routine. Dispatch first requires the DCERPC object UUID flag and an exact match with `IREMOTEWINSPOOL_OBJECT_GUID`; mismatches fault with `DCERPC_NCA_S_UNSUPPORTED_TYPE`. Forwarded operations are sent straight to `spoolss__op_dispatch()`. Local operations populate `pipes_struct` call context, impersonate the authenticated pipe user for external RPC calls, initialize output pointers and buffers using the request's talloc context, call the `_winspool_*` worker, unimpersonate, clear pipe context, and translate `p->fault_state` into `dce_call->fault_code`.

State and persistence: this file owns no durable spooler state. It transiently mutates `dce_call->pkt.u.request.opnum` for forwarding, uses `dce_call->fault_code` and `p->fault_state` for error propagation, and temporarily assigns `p->dce_call` plus `p->mem_ctx` during local dispatch. Output storage is request-scoped talloc memory. Persistent printer, job, driver, and notification state is owned by the downstream spoolss implementation or by unimplemented local workers.

Dependencies and integration: depends on generated NDR tables for `winspool` and `spoolss`, Samba DCERPC server core, `pipes_struct` helpers, authentication impersonation helpers, and `rpc_server/spoolss/iremotewinspool_util.h` for opcode mapping. Endpoint registration iterates `ndr_table_iremotewinspool.endpoints` and optionally honors `DCESRV_INTERFACE_IREMOTEWINSPOOL_NCACN_NP_SECONDARY_ENDPOINT`. The forwarded path integrates with `srv_spoolss.c`/`srv_spoolss_nt.c`; source4 torture tests under `source4/torture/rpc/iremotewinspool*` are important consumers.

Risks: forwarding depends on keeping `forward_opnum_to_spoolss()` aligned with `iremotewinspool_util.c`; an opnum that is marked forwardable but lacks a mapping still falls through to `spoolss__op_*()` with the original opnum, which is a compatibility-sensitive behavior. The object UUID check is stricter than a generic interface dispatch and must match client binding behavior. Many local cases allocate output buffers sized directly from request fields, so malformed or very large counts rely on generated NDR validation and talloc failure handling. Because this is generated boilerplate, manual edits may be overwritten by pidl regeneration unless changes are made in the generator or IDL path.

Test signals: run Samba RPC torture for `iremotewinspool` and `iremotewinspool_driver`, especially object UUID binding, forwarded raw-call byte equivalence with spoolss, and negative cases for missing/wrong object UUID. Exercise opnums 58, 59, 60, 61, 62, 63, 65, and 67 to verify they remain local and fault as expected through the current workers. Compile tests should verify generated `ndr_table_iremotewinspool` layout and that all `_winspool_*` symbols remain linked.

# sources/user-network-fs/samba/source3/rpc_server/spoolss/srv_iremotewinspool_nt.c

Purpose: supplies the server-side worker functions for iremotewinspool operations that are not fully implemented in the forwarded spoolss path. Every handler currently marks the operation as an RPC op-range fault and returns a "not supported" protocol result, making this file an explicit unsupported-operation boundary.

Important APIs/types/functions: the file defines `_winspool_AsyncOpenPrinter()` through `_winspool_AsyncLogJobInfoForBranchOffice()` matching generated `winspool_*` request structs. Most functions return `WERROR` and use `WERR_NOT_SUPPORTED`; notification and printer-driver-package style functions return `HRESULT` and use `HRES_ERROR_NOT_SUPPORTED`. All handlers take `struct pipes_struct *p`, set `p->fault_state = DCERPC_FAULT_OP_RNG_ERROR`, and ignore request payload details beyond type matching.

Control flow: there is no branching beyond one identical path per RPC operation. `srv_iremotewinspool.c` prepares any generated out parameters first, calls the corresponding `_winspool_*` worker, then observes `p->fault_state` and converts it into a DCERPC fault. Because every worker sets `DCERPC_FAULT_OP_RNG_ERROR`, callers receive an RPC-level fault rather than only an application-level unsupported status. The implementation covers printer management, job management, forms, drivers, ports, monitors, print processors, remote notifications, driver packages, named job properties, and branch office logging.

State and persistence: no printer state, handle table, job data, notification subscription, or registry-like setting is created or mutated here. The only side effect is transient fault-state mutation on `pipes_struct`. The returned `WERR_NOT_SUPPORTED` or `HRES_ERROR_NOT_SUPPORTED` values are effectively secondary because the dispatcher treats nonzero `p->fault_state` as the authoritative fault.

Dependencies and integration: includes the generated winspool NDR headers and the common Samba includes for `pipes_struct`, `WERROR`, `HRESULT`, and DCERPC fault constants. It is integrated by symbol name with the dispatch switch in `srv_iremotewinspool.c`; generated prototypes must stay in sync with `ndr_winspool_scompat.h`. The source4 iremotewinspool torture suite is the main integration signal for unsupported behavior and for any future implementation work.

Risks: the file advertises full symbol coverage but no functional behavior, so clients expecting async MS-RPRN semantics may see hard RPC faults instead of graceful unsupported application returns. If a future handler is implemented, it must also revisit `forward_opnum_to_spoolss()` and opcode mapping so that the request actually reaches the intended worker. The mixed `WERROR`/`HRESULT` return families are easy to get wrong when adding code; mismatching a generated signature would cause build or marshalling failures. The placeholder copyright header and generated-looking structure suggest this file may be a skeleton that needs policy review before enabling features.

Test signals: unsupported-operation tests should assert both the returned protocol status family and the DCERPC fault code for local opnums. Build tests should catch signature drift against generated NDR headers. If implementing any function, add targeted RPC torture coverage for successful marshalling, access checks, handle lifetime, and parity with the equivalent spoolss operation where one exists.

# sources/user-network-fs/samba/source3/rpc_server/spoolss/srv_spoolss_handle.h

Purpose: defines the central server-side spoolss printer handle state used by Samba's spoolss RPC implementation. The header classifies handle kinds and describes the `struct printer_handle` object that tracks open printer/server/port-monitor handles, printing progress, granted access, notification state, client identity, and cached printer data.

Important APIs/types/functions: handle type constants are `SPLHND_PRINTER`, `SPLHND_SERVER`, `SPLHND_PORTMON_TCP`, and `SPLHND_PORTMON_LOCAL`. `struct printer_handle` is list-linked through `prev`/`next`; tracks document/page booleans, backend `jobid`, `printer_type`, `servername`, `sharename`, and `access_granted`; embeds a `notify` substructure with change flags, options, local machine name, local-printer id, `spoolss_NotifyOption`, client policy handle, back-channel pointer, pending change mask, in-flight `FindNextPrinterChangeNotify` flag, and messaging context; stores client machine/user strings; and caches open-printer `spoolss_DeviceMode` plus `spoolss_PrinterInfo2`.

Control flow: the header has no executable flow. In `srv_spoolss_nt.c`, instances are allocated for open handles, inserted into a global printer list, looked up by policy handle, checked for type-specific behavior, and destroyed when handles close or their talloc owner is freed. The document/page flags and job id guide StartDoc/StartPage/Write/End/Abort sequences. Notification fields are populated by change-notify registration and consumed by notification delivery and cleanup.

State and persistence: this is in-memory per-open-handle state. It persists only for the lifetime of the server process context and the policy handle, not across Samba restarts. It references longer-lived configuration and backend state such as shares, print jobs, and printer info, but the structure itself is a runtime cache/handle record. The notify back channel and messaging context link each handle to asynchronous notification machinery.

Dependencies and integration: includes generated `spoolss.h` for `spoolss_NotifyOption`, `spoolss_DeviceMode`, and `spoolss_PrinterInfo2`, and forward-declares `struct notify_back_channel`. It is included by the spoolss NT implementation and indirectly underpins forwarded iremotewinspool calls, because most iremotewinspool opnums delegate into the same spoolss handle model. The fields use Samba fixed string types (`fstring`) and talloc-owned pointers expected by the RPC server code.

Risks: `printer_handle` combines access control, backend job state, notification subscription state, and cached printer metadata, so lifetime bugs can affect multiple RPC families. Back-channel and messaging pointers require careful teardown to avoid dangling notification state. The `printer_type` constants are plain integer bit-like values, yet some code treats port monitor types with bitwise checks, so adding handle kinds needs care. Cached `devmode` and `info2` data can become stale if share configuration changes while a handle is open.

Test signals: spoolss open/close, printer/server/port-monitor type detection, access-denied paths, document lifecycle, notification registration/unregistration, and handle cleanup are the best runtime signals. Static analysis should watch for use-after-free around notify back channels and cached pointers. RPC torture involving both spoolss and iremotewinspool forwarded operations can confirm that the shared handle model behaves consistently across interfaces.
