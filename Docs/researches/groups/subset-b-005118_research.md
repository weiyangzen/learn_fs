# sources/distributed-fs/ceph-client/drivers/pinctrl/tegra/pinctrl-tegra186.c

Purpose: Provides static SoC description tables for the NVIDIA Tegra186 pinmux driver. It does not implement pinctrl algorithms itself; instead it declares Tegra186 pin IDs, pin descriptors, one-pin pin groups, supported mux function names, register/bit layout metadata, and platform-driver match data consumed by the shared Tegra pinctrl core.

Important APIs, types, and functions: The file builds `struct pinctrl_pin_desc` arrays for the main controller (`tegra186_pins`) and always-on controller (`tegra186_aon_pins`). It defines many one-element `*_pins[]` arrays used by `struct tegra_pingroup` entries. `enum tegra_mux_dt` and `tegra186_functions[]` define the exported function namespace, including PCIe, EQOS, SDMMC, QSPI, UFS, display, I2C, UART, CAN, audio, USB, and reserved functions. Macro families `PIN_PINGROUP_ENTRY_*`, `DRV_PINGROUP_ENTRY_*`, `PINGROUP`, and `DRV_PINGROUP` populate `struct tegra_pingroup` fields such as mux alternatives, mux/pull/tristate register offsets, input/open-drain/Schmitt/drive-type bits, low-power bits, pre-emphasis, and drive-strength/slew fields. `tegra186_pinctrl_probe()` fetches `of_device_get_match_data()` and calls `tegra_pinctrl_probe()`. `tegra186_pinctrl_of_match[]`, `tegra186_pinctrl_driver`, and `arch_initcall(tegra186_pinctrl_init)` bind the data to `"nvidia,tegra186-pinmux"` and `"nvidia,tegra186-pinmux-aon"`.

Control flow: At `arch_initcall` time the platform driver is registered. Device-tree matching chooses either `tegra186_pinctrl` or `tegra186_pinctrl_aon` as match data. Probe passes that static `struct tegra_pinctrl_soc_data` to the shared core, which then exposes pinctrl/pinmux/pinconf operations using the arrays in this file. Runtime mux, pull, tristate, input, open-drain, drive, Schmitt, and special-function-selection operations are therefore table-driven: the shared core looks up a group/function/configuration and writes the register bank, offset, bit, and width encoded here.

State and persistence behavior: This source stores no mutable driver state. All data is `static const` and persists for the lifetime of the kernel image. Mutable state lives in the shared `struct tegra_pmx` allocated by `tegra_pinctrl_probe()` and in the hardware registers that pinctrl clients program. Hardware pin state persists until firmware, bootloader, kernel pinctrl states, suspend/resume restore paths, or another client changes the pinmux registers. The main and AON instances are separate hardware blocks selected by compatible string, so their groups and register offsets must not be mixed.

Dependencies and integration points: Depends on Linux platform-driver, OF match, and pinctrl/pinmux headers, plus the local `pinctrl-tegra.h` shared data contract. It integrates with device tree through `nvidia,tegra186-pinmux` and `nvidia,tegra186-pinmux-aon` nodes, and with board/device pin configuration through normal pinctrl states. It also indirectly integrates with Tegra GPIO and peripheral drivers because correct mux/function/group names are required for SDMMC, EQOS Ethernet, PCIe reset/clock-request, QSPI, UFS, display, camera, audio, CAN, I2C, UART, USB VBUS, and power-management pins.

Risks: The file is highly table-sensitive: a wrong enum value, pin descriptor string, group pin array, mux function order, register offset, bank, bit number, or field width silently sends the shared core to the wrong hardware control. A notable source-data risk is that the `PINCTRL_PIN()` descriptor for `TEGRA_PIN_GPIO_CAM5_PN4` uses the string `"GPIO_CAM6_PN5"` rather than a CAM5 name, creating duplicate visible pin naming with `TEGRA_PIN_GPIO_CAM6_PN5`. Some groups intentionally have no drive entry or empty SDMMC4 pin arrays while still having pingroup register definitions; these require compatibility with the shared core's handling of zero-pin or no-drive groups. AON/main separation is another risk because register offsets overlap conceptually but target different MMIO resources. Electrical risks include misprogramming high-voltage, open-drain, pull, drive-strength, slew, pre-emphasis, and low-power bits for high-speed buses such as SDMMC, EQOS, QSPI, and UFS.

Test signals: Build coverage should include this file and `pinctrl-tegra.c` with OF matching for both compatible strings. Runtime signals include successful registration of main and AON pinctrl devices, pinctrl debugfs showing expected pin names/groups/functions, device-tree pin states selecting common functions (`sdmmc1`, `sdmmc3`, `eqos`, `qspi`, `ufs0`, `uart*`, `i2c*`, `can*`) without lookup failures, and hardware validation that pins toggle or communicate on the intended peripherals. Regression checks should include duplicate/mistyped pin names, AON GPIO/power pin configuration, suspend/resume preservation through the shared Tegra pinctrl PM path, and pinconf reads/writes for pull, tristate, input, open-drain, Schmitt, drive type, drive strength, and slew where supported.

# sources/distributed-fs/ceph-client/drivers/pinctrl/tegra/pinctrl-tegra194.c

Purpose: Provides static pinctrl/pinmux data for NVIDIA Tegra194. Like the Tegra186 file, it is a SoC data provider for the shared Tegra pinctrl core, but it reflects Tegra194-specific pin inventory, mux functions, register layout, high-speed-mode support, and per-group I/O rail names.

Important APIs, types, and functions: `tegra194_pins` and `tegra194_aon_pins` describe the main and AON pin sets. Single-pin `*_pins[]` arrays feed the pingroup table. `enum tegra_mux_dt` and `tegra194_functions[]` define the function IDs/names; compared with Tegra186 this includes Tegra194-specific function coverage such as `slvs`, `igpu`, `dgpu`, `pe3`, `pe4`, `pe5`, `qspi0`, `qspi1`, and `mipi`. The `PIN_PINGROUP_ENTRY_Y()` macro includes an `io_rail` argument in addition to mux, pull, tristate, input, GPIO/SFIO, open-drain, Schmitt, drive type, pre-emphasis, I/O reset, and reserved-input bits. `DRV_PINGROUP_ENTRY_Y()` encodes drive-strength and slew-rate fields. The `tegra194_pinctrl` and `tegra194_pinctrl_aon` `struct tegra_pinctrl_soc_data` objects set `hsm_in_mux`, `schmitt_in_mux`, `drvtype_in_mux`, and `sfsel_in_mux` to true. Probe and registration are handled by `tegra194_pinctrl_probe()`, `tegra194_pinctrl_of_match[]`, `tegra194_pinctrl_driver`, and `arch_initcall(tegra194_pinctrl_init)`.

Control flow: The platform driver registers during architecture initialization. OF match data selects the main or AON `struct tegra_pinctrl_soc_data`, and probe delegates to `tegra_pinctrl_probe()`. After that, all pinctrl operations are data-driven by `tegra194_groups` or `tegra194_aon_groups`: group lookup maps a consumer's device-tree pin state to a mux function and optional pinconf fields, and the common Tegra core programs the encoded bank/offset/bit fields. Main controller groups cover audio, QSPI0/1, EQOS, SOC GPIO, UART, DAP/I2S, SDMMC, PCIe, SATA, display, camera I2C, DirectDC, SPI, UFS, USB, GPU/CV power request, and high-speed storage/flash pins. AON groups cover CAN, SPI2, touch clock, UART3, I2C2/I2C5/I2C8, safe-state/power-management, reset/shutdown/PMU interrupt, and 32 kHz clock pins.

State and persistence behavior: The file has only immutable tables. Runtime state and synchronization are owned by the shared Tegra pinctrl core and the platform device. Programmed pin state persists in MMIO registers until another pinctrl state, firmware handoff, suspend/resume path, or driver action changes it. Tegra194 groups also carry I/O rail labels such as `vddio_audio`, `vddio_cam`, `vddio_pex_ctl`, `vddio_qspi`, `vddio_sdmmc*_hv`, `vddio_ao`, and `vddio_sys`; those labels are persistent metadata used by the core and bindings to reason about the electrical domain for a group.

Dependencies and integration points: Depends on Linux OF/platform/pinctrl headers and the shared local `pinctrl-tegra.h` definitions. Device-tree integration is through `"nvidia,tegra194-pinmux"` and `"nvidia,tegra194-pinmux-aon"`. Peripheral integration is broad: storage controllers depend on SDMMC and QSPI muxing, networking depends on EQOS groups and `vddio_eqos`, PCIe/SATA depend on reset/CLKREQ/WAKE groups, display and camera depend on DP/HDMI/DirectDC/camera groups, and AON/power-management code depends on reset, PMU, safe-state, power I2C, 32 kHz, and CAN pins.

Risks: Tegra194 adds I/O rail metadata and more high-speed/voltage-sensitive groups, increasing the cost of table mistakes. Incorrect `io_rail` values can associate a group with the wrong electrical domain. Wrong mux alternatives or field bits can break boot-critical devices such as storage, power I2C, PCIe reset, or PMU interrupt lines. Many drive entries are intentionally `DRV_PINGROUP_ENTRY_N(no_entry)` for high-speed or special groups, so callers and tests must distinguish unsupported drive configuration from a regression. Main and AON tables reuse similar function names while addressing different MMIO blocks. Because `hsm_in_mux` is true for Tegra194, high-speed mode programming uses mux register fields; offsets and bit positions are especially important.

Test signals: Build and boot with both pinmux compatible strings. Confirm pinctrl debugfs exposes expected main and AON pins, groups, functions, and where available I/O rail metadata. Exercise representative pin states for QSPI0/1, SDMMC1/3/4, EQOS, PCIe lane controls including PE5, UFS0, USB VBUS, UARTs, I2C, SPI, audio DAPs, CAN, and power-management pins. Validate pinconf operations for pull, tristate, input, open-drain, Schmitt, high-speed mode, drive type, special-function select, drive strength, and slew only on groups that advertise the relevant bits. Hardware-level test signals include storage enumeration, EQOS link, PCIe link training, AON wake/power behavior, CAN bus operation, and suspend/resume with pin state preserved or restored.

# sources/distributed-fs/ceph-client/drivers/pinctrl/tegra/pinctrl-tegra20.c

Purpose: Provides the static pinctrl data and small Tegra20-specific glue for the NVIDIA Tegra20 pinmux. Unlike the newer Tegra186/Tegra194 files, Tegra20 uses multi-pin functional groups, explicit GPIO numbering alignment, legacy mux/pull/tristate register banks, drive-group tables, and read-only clock mux registration for a few clock-output pin groups.

Important APIs, types, and functions: The file defines GPIO-backed pin IDs with `_GPIO(offset)` so the first 224 pins match the Tegra20 GPIO driver numbering, then defines non-GPIO pins with `_PIN(offset)` after `NUM_GPIOS`. `tegra20_pins[]` exposes all GPIO and non-GPIO pin descriptors, including display, GMI/NAND/IDE, SDIO, UART, SPI, ULPI, keyboard, camera/video, DDR, JTAG, clock, and power pins. Large `*_pins[]` arrays group pins by mux group (`ata`, `dap1`, `lcd`, `sdio1`, `spia`, `uad`, etc.), pull-only group (`ck32`, `ddrc`, `xm2c`, etc.), and drive group (`drive_ao1`, `drive_lcd2`, `drive_xm2d`, etc.). `enum tegra_mux` and `tegra20_functions[]` define the function namespace. `MUX_PG`, `PULL_PG`, `DRV_PG_EXT`, and `DRV_PG` build `struct tegra_pingroup` entries. `tegra20_pinctrl` sets `.ngpios = NUM_GPIOS` and `.gpio_compatible = "nvidia,tegra20-gpio"`. `tegra20_pinctrl_register_clock_muxes()` registers read-only `cdev1_mux`, `cdev2_mux`, and `csus_mux` clocks with `clk_register_mux()`. `tegra20_pinctrl_probe()` calls `tegra_pinctrl_probe()` and then registers those clock muxes. The platform driver matches `"nvidia,tegra20-pinmux"` and is registered with `arch_initcall`.

Control flow: During probe, the shared Tegra pinctrl core receives `tegra20_pinctrl` and maps the controller resources into a `struct tegra_pmx`. The Tegra20 wrapper then reads that driver data and registers clock-provider muxes for the `cdev1`, `cdev2`, and `csus` pinmux fields, using the same mux register bank (`pmx->regs[1] + 0x8`) and marking them `CLK_MUX_READ_ONLY`. Pinctrl operations are table-driven: mux groups encode four function choices, tristate register offset/bit, mux register offset/bit, and optional pull-up/down fields; pull-only groups expose only pull configuration; drive groups expose high-speed mode, Schmitt, low-power mode, drive-down/up, and slew-rising/falling fields.

State and persistence behavior: All pin definitions and group metadata are immutable. Runtime state is in the common Tegra pinctrl driver and in the clock framework objects registered by `tegra20_pinctrl_register_clock_muxes()`. Hardware pinmux, pull, tristate, and drive register values persist until changed by pinctrl state selection, clock/pin firmware setup, suspend/resume, or another driver. The clock muxes are read-only views of pinmux-selected clock parents, so they expose existing hardware selection to the clock framework without making the clock framework responsible for changing the pinmux bits.

Dependencies and integration points: Depends on Linux clock-provider APIs in addition to platform, OF, and pinctrl/pinmux headers. It integrates with the shared `pinctrl-tegra.h` core, the Tegra20 GPIO driver via exact GPIO pin numbering and `gpio_compatible`, the common clock framework via `cdev1_mux`, `cdev2_mux`, and `csus_mux`, and device-tree pinctrl states for Tegra20 boards. Peripheral dependencies include display/HDMI/CRT, GMI/NAND/IDE, SDIO, UART, SPI, I2C/DDC, ULPI USB, audio DAP/SPDIF, keyboard controller, video input/camera, DDR pad controls, power-management pins, JTAG/test pins, and system clock request.

Risks: GPIO numbering is a hard contract: moving or renumbering the first `NUM_GPIOS` pin descriptors would break GPIO/pinctrl coordination. Multi-pin groups mean a mux change can affect many pads at once, so a single wrong pin-array member or mux choice can disrupt a bus. Register offsets are expressed as deltas from `TRISTATE_REG_A`, `PIN_MUX_CTL_REG_A`, `PULLUPDOWN_REG_A`, and `PINGROUP_REG_A`; wrong base arithmetic or `-1` handling affects many groups. Some descriptor names carry historical quirks, such as `"VD_D10 PT2"` for `TEGRA_PIN_VI_D10_PT2`, which may surprise string-based diagnostics. DDR, clock, reset, power, and JTAG groups are boot-sensitive and may have limited safe runtime configurability. `clk_register_mux()` return values are ignored, so failed clock registration would not fail pinctrl probe.

Test signals: Compile with Tegra20 pinctrl and clock-provider support. Boot a Tegra20 device tree with `"nvidia,tegra20-pinmux"` and confirm pinctrl plus GPIO registration, with GPIO numbers aligned to the GPIO driver. Debugfs should show expected functions and groups, including mux, pull-only, and drive groups. Exercise board pin states for SDIO, display, UART, SPI, I2C/DDC, ULPI, audio DAP, keyboard, and GMI/NAND/IDE where available. Verify pull/tristate/mux/pinconf writes on mux groups, pull-only behavior on pull groups, drive-strength/slew/high-speed/Schmitt settings on drive groups, and absence of unsupported-feature writes where fields are `-1`. Clock tests should confirm `cdev1_mux`, `cdev2_mux`, and `csus_mux` appear as read-only clock muxes with parent selection reflecting pinmux register bits. Suspend/resume, early boot pin state, and GPIO request/mux handoff are important regression signals.
