# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/mxgpu_nv.c

Purpose: this file implements the newer AMDGPU MxGPU/SR-IOV virtual-function mailbox backend used by Navi and later SOC15/SOC21/SOC24 paths. It lets a VF request exclusive host-coordinated GPU access for init, fini, reset, and init-data exchange; receives PF notifications through mailbox interrupts; coordinates host FLR recovery; and exposes RAS virtualization requests such as poison handling, error-count retrieval, CPER dump, bad-page requests, critical-region checks, and remote RAS commands through `xgpu_nv_virt_ops`.

Important APIs and functions: exported entry points are `xgpu_nv_mailbox_set_irq_funcs()`, `xgpu_nv_mailbox_add_irq_id()`, `xgpu_nv_mailbox_get_irq()`, `xgpu_nv_mailbox_put_irq()`, and the exported `xgpu_nv_virt_ops` table. Core helpers include `xgpu_nv_mailbox_trans_msg()` for writing transmit DW0-DW3 and asserting transmit-valid, `xgpu_nv_poll_ack()` and `xgpu_nv_poll_msg()` for PF handshakes, `xgpu_nv_send_access_requests_with_param()` for serialized mailbox request/response transactions, `xgpu_nv_request_full_gpu_access()`, `xgpu_nv_release_full_gpu_access()`, `xgpu_nv_request_reset()`, `xgpu_nv_request_init_data()`, `xgpu_nv_ready_to_reset()`, and `xgpu_nv_wait_reset()`. Interrupt-facing helpers are `xgpu_nv_set_mailbox_ack_irq()`, `xgpu_nv_set_mailbox_rcv_irq()`, `xgpu_nv_mailbox_rcv_irq()`, and workqueue callbacks for FLR and bad-page data exchange. RAS-facing callbacks are `xgpu_nv_ras_poison_handler()`, `xgpu_nv_rcvd_ras_intr()`, `xgpu_nv_req_ras_err_count()`, `xgpu_nv_req_ras_cper_dump()`, `xgpu_nv_req_ras_bad_pages()`, `xgpu_nv_check_vf_critical_region()`, and `xgpu_nv_req_remote_ras_cmd()`.

Control flow: a VF transaction locks `adev->virt.access_req_mutex`, rejects new work when RAS has marked the VF unrecoverable, clears transmit-valid until stale PF ACK state drops, writes request and up to three parameters into `mmMAILBOX_MSGBUF_TRN_DW*`, asserts transmit-valid, polls for PF ACK, then clears transmit-valid. Requests that require a PF event map to expected `enum idh_event` values: init/fini/reset access wait for `IDH_READY_TO_ACCESS_GPU`, init-data waits for `IDH_REQ_GPU_INIT_DATA_READY`, and RAS subcommands wait for their corresponding ready events. Failed polling retries up to five times for most requests; init-data falls back to legacy version 0 when the PF does not support the handshake. Reset access is retried up to `NV_MAILBOX_POLL_MSG_REP_MAX`, and reset completion is a separate poll for `IDH_FLR_NOTIFICATION_CMPL`. Receive IRQ processing peeks DW0, acknowledges specific PF notifications, schedules reset-domain FLR work for FLR and unrecoverable notifications, schedules data-exchange refresh work for bad-page notifications, and intentionally ignores messages that are consumed by synchronous polling.

State and persistence: all state is volatile driver/device state. The mailbox protocol mutates hardware mailbox control and buffer registers directly. The code updates `adev->virt.req_init_data_ver`, `adev->virt.init_data_header.offset`, `adev->virt.init_data_header.size_kb`, and `adev->virt.fw_reserve.checksum_key` after successful PF responses. It also initializes `adev->virt.flr_work`, `req_bad_pages_work`, and `handle_bad_pages_work`, and toggles `adev->virt.ack_irq`/`rcv_irq` interrupt enables. RAS unrecoverable notifications set `amdgpu_ras_get_context(adev)->is_rma`, which becomes a gate that stops later access requests. There is no persistent storage beyond device/runtime state.

Dependencies and integration: the file depends on AMDGPU core device structures, register access macros, SOC15 BIF interrupt client IDs, Navi mailbox register offsets from `mxgpu_nv.h`, reset-domain scheduling, `amdgpu_device_gpu_recover()`, RAS helpers, SR-IOV runtime detection, data-exchange helpers, and PSP/firmware-reserved checksum consumers elsewhere in the driver. It is installed by ASIC glue such as `nv.c`, `soc21.c`, and `soc24.c`, which set `adev->virt.ops = &xgpu_nv_virt_ops` and register mailbox IRQ IDs 135 and 138.

Risks: mailbox sequencing is sensitive to stale ACK/valid bits; the transmit path spins until ACK clears and only logs/rate-limits if the host keeps it asserted. Poll loops use millisecond sleeps and fixed timeouts, so slow or wedged PF firmware surfaces as `-ETIME` and can elongate reset or RAS paths. `xgpu_nv_mailbox_peek_msg()` is documented as IRQ-only, but it is also used by reset-wait and RAS interrupt detection paths that rely on mailbox state being valid enough. `xgpu_nv_poll_msg()` dereferences the RAS context when handling unrecoverable state, so callers assume RAS context availability. Work handlers use `down_read_trylock()` and silently skip bad-page/data refresh work when reset-domain locking is unavailable. Interrupt receive handling does not ACK FLR notification before scheduling FLR work, so PF/VF protocol expectations must match this behavior. Error retry behavior for init-data intentionally degrades to legacy mode, which can hide PF feature mismatches.

Test signals: useful validation includes SR-IOV VF boot through init/fini access, reset access retry and `IDH_FLR_NOTIFICATION_CMPL` wait behavior, PF timeout injection for ACK and response polling, init-data v1/v2 negotiation and checksum-key propagation, IRQ registration/unregistration for SOC15 BIF IDs 135/138, FLR notification recovery with and without running jobs, bad-page notification data-exchange refresh, unrecoverable RAS notification setting RMA and blocking later requests, RAS error-count/CPER/critical-region/remote-command mailbox transactions, and lockdep coverage for access-request mutex plus reset-domain workqueue paths.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/mxgpu_nv.h

Purpose: this header defines the Navi-and-newer MxGPU mailbox contract shared by `mxgpu_nv.c` and ASIC integration code. It names mailbox timeouts, request and event IDs exchanged between VF and PF, exported virtualization operations, mailbox IRQ setup helpers, and the register offsets for transmit/receive control and message buffers.

Important APIs and types: `enum idh_request` declares VF-to-PF commands for GPU init/fini/reset access, init-data negotiation, VF error logging, ready-to-reset notification, and RAS operations including poison handling, error count, CPER dump, bad pages, critical-region check, and remote command. `enum idh_event` declares PF-to-VF events such as ready-to-access, FLR notification and completion, success/fail, query-alive, init-data-ready, RAS ready/notification events, unrecoverable error notification, and text messages. External symbols are `xgpu_nv_virt_ops`, `xgpu_nv_mailbox_set_irq_funcs()`, `xgpu_nv_mailbox_add_irq_id()`, `xgpu_nv_mailbox_get_irq()`, and `xgpu_nv_mailbox_put_irq()`. Register constants include `mmMAILBOX_CONTROL`, byte offsets for transmit and receive control, DW0-DW3 transmit and receive message-buffer registers, and `mmMAILBOX_INT_CNTL`.

Control flow: the header does not execute logic, but it encodes the protocol that `mxgpu_nv.c` implements. Callers install the IRQ source functions, add mailbox IV IDs, acquire IRQs, and use `xgpu_nv_virt_ops` to send request IDs. The mailbox implementation writes `enum idh_request` values into transmit DW0 with optional parameters in DW1-DW3, then waits for PF ACK and for one of the `enum idh_event` values in receive DW0.

State and persistence: the constants represent volatile MMIO register locations and protocol values; the header itself owns no state. The timeout constants define runtime polling limits: ACK polling, response polling, FLR completion polling, and maximum reset-request repetitions. The register definitions are direct offsets rather than persisted configuration.

Dependencies and integration: consumers require AMDGPU core declarations for `struct amdgpu_device` and `struct amdgpu_virt_ops`, plus register access helpers from included C files. The event and request numbers are a binary compatibility boundary with the PF/hypervisor mailbox implementation, so `mxgpu_nv.c`, ASIC setup files, and host firmware must agree on these numeric values.

Risks: changing any numeric request/event value or mailbox register offset can break PF/VF interoperability. The typo in the public macro prefix `NV_MAIBOX_*` is part of the local API and must be preserved unless all users are updated. The header defines `IDH_FAIL` as an event value that `mxgpu_nv.c` converts to `-EINVAL`, so adding events around that value requires care. Timeout constants are global to all users of this backend and may not fit every PF latency profile.

Test signals: compile coverage should include all ASIC files that include this header. Runtime protocol tests should verify each exported request maps to the PF event expected by `mxgpu_nv.c`, IRQ ID setup works with the declared exported functions, and mailbox register offsets read/write the intended transmit/receive buffers on supported Navi/SOC21/SOC24 VF hardware.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/mxgpu_vi.c

Purpose: this file implements the older VI-generation MxGPU/SR-IOV support for Fiji and Tonga virtual functions. It has two main responsibilities: programming VF-safe golden register sequences for supported VI ASICs, and implementing the legacy mailbox handshake used by a VF to request/release full GPU access, request reset, wait for FLR completion, and react to PF FLR notifications.

Important APIs and functions: exported entry points are `xgpu_vi_init_golden_registers()`, `xgpu_vi_mailbox_set_irq_funcs()`, `xgpu_vi_mailbox_add_irq_id()`, `xgpu_vi_mailbox_get_irq()`, `xgpu_vi_mailbox_put_irq()`, and the `xgpu_vi_virt_ops` table. Static golden-setting arrays cover Fiji MGC/CGCG initialization, Fiji A10 settings, Fiji common settings, Tonga MGC/CGCG initialization, Tonga A11 settings, and Tonga common settings. Mailbox helpers include `xgpu_vi_mailbox_send_ack()`, `xgpu_vi_mailbox_set_valid()`, `xgpu_vi_mailbox_trans_msg()`, `xgpu_vi_mailbox_rcv_msg()`, `xgpu_vi_poll_ack()`, `xgpu_vi_poll_msg()`, and `xgpu_vi_send_access_requests()`. Reset and IRQ helpers include `xgpu_vi_request_reset()`, `xgpu_vi_wait_reset_cmpl()`, `xgpu_vi_request_full_gpu_access()`, `xgpu_vi_release_full_gpu_access()`, ACK/receive IRQ set/process functions, and `xgpu_vi_mailbox_flr_work()`.

Control flow: VI initialization calls `xgpu_vi_init_golden_registers()`, switches on `adev->asic_type`, and programs the appropriate register triplets through `amdgpu_device_program_register_sequence()`. Runtime mailbox requests write the request ID into `mmMAILBOX_MSGBUF_TRN_DW0`, assert `TRN_MSG_VALID`, poll `TRN_MSG_ACK`, clear valid, and for init/fini/reset access wait for `IDH_READY_TO_ACCESS_GPU`. Receive-message polling checks `RCV_MSG_VALID` except for the documented FLR-completion workaround, compares receive DW0 with the expected event, and acknowledges to PF by setting `RCV_MSG_ACK` then waiting for `RCV_MSG_VALID` to clear. Receive IRQ processing only handles PF FLR notifications when global GPU recovery/TDR is disabled, then schedules reset-domain FLR work. FLR work builds an `amdgpu_reset_context` with `AMDGPU_HOST_FLR` and calls `amdgpu_device_gpu_recover()` when recovery is allowed.

State and persistence: state is limited to MMIO register programming and in-memory driver structures. Golden register writes configure clock gating, memory/power, graphics, SDMA, display, and VM-related registers for Fiji/Tonga VF operation. Mailbox state lives in `mmMAILBOX_CONTROL`, transmit/receive message buffers, and `mmMAILBOX_INT_CNTL`. The file initializes `adev->virt.flr_work`, sets `adev->virt.ack_irq` and `adev->virt.rcv_irq` function tables, and exposes `adev->virt.ops`; it does not persist anything across driver unload or device reset beyond hardware register side effects that are reprogrammed on init/resume.

Dependencies and integration: the code depends on many VI-era register headers (`bif_5_0`, `gfx_8_0`, `gmc_8_2`, `oss_3_0`, `dce_10_0`, `smu_7_1_3`), AMDGPU reset infrastructure, IRQ source registration, and global recovery policy. `vi.c` includes this header, calls golden-register setup for virtualized VI, installs mailbox IRQ functions, gets/adds/puts mailbox IRQs, and assigns `adev->virt.ops = &xgpu_vi_virt_ops`. IRQ IDs 135 and 138 are registered under `AMDGPU_IRQ_CLIENTID_LEGACY`.

Risks: `xgpu_vi_init_golden_registers()` uses `BUG_ON()` for unsupported chip types, so accidental calls on non-Fiji/Tonga hardware can crash the kernel. Mailbox waits are fixed-delay polling loops using `mdelay()`, which can stall CPU and are sensitive to PF latency. Error messages for receive polling say ACK even when waiting for a message, which can mislead diagnosis. The FLR-completion receive path intentionally bypasses `RCV_MSG_VALID` due to host-driver behavior, increasing dependence on receive DW0 contents. Receive IRQ handling is gated by `!amdgpu_gpu_recovery`, so behavior differs sharply based on global recovery configuration. The VI `virt_ops` table lacks newer hooks such as init-data and RAS callbacks, so generic virtualization paths must check callback availability.

Test signals: validation should cover Fiji and Tonga golden sequence programming, unsupported ASIC guard behavior, init/fini/reset access mailbox success and timeout paths, ACK clear and receive-valid clear behavior, FLR-completion wait with the valid-bit workaround, legacy IRQ ID registration and teardown, PF FLR notification scheduling when TDR is disabled, no scheduling when recovery is enabled, and suspend/resume paths that require mailbox and golden registers to be reestablished.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/mxgpu_vi.h

Purpose: this header defines the legacy VI MxGPU mailbox interface and exported entry points used by `mxgpu_vi.c` and `vi.c`. It captures the smaller pre-Navi PF/VF protocol for full-GPU access and FLR coordination and declares the VI virtualization operations table.

Important APIs and types: `VI_MAILBOX_TIMEDOUT` and `VI_MAILBOX_RESET_TIME` define polling and reset timing constants. `enum idh_request` contains the VI request IDs for GPU init access, release init access, fini access, release fini access, reset access, and VF error logging. `enum idh_event` contains mailbox receive values for clearing the message buffer, ready-to-access, FLR notification, FLR completion, and text messages. Externs include `xgpu_vi_virt_ops`, `xgpu_vi_init_golden_registers()`, `xgpu_vi_mailbox_set_irq_funcs()`, `xgpu_vi_mailbox_add_irq_id()`, `xgpu_vi_mailbox_get_irq()`, and `xgpu_vi_mailbox_put_irq()`.

Control flow: the header is declarative. VI ASIC setup code calls the golden-register initializer during virtualized device setup, installs IRQ source functions, registers mailbox IRQ IDs, then uses `xgpu_vi_virt_ops` callbacks for request/release/reset/wait-reset behavior. The corresponding C file writes these request values into mailbox DW0 and waits for the event values in receive DW0.

State and persistence: the header owns no state. Its constants parameterize runtime polling and protocol behavior in `mxgpu_vi.c`. The declared functions operate on `struct amdgpu_device` state, IRQ source tables, workqueue state, and mailbox MMIO registers, all of which are volatile runtime state.

Dependencies and integration: consumers require AMDGPU device and virtualization type declarations. Numeric values must match the PF/hypervisor protocol implemented for VI MxGPU. `vi.c` is the primary integration point, assigning the ops table and invoking the IRQ/golden-register helpers during VI ASIC initialization and teardown.

Risks: this protocol is intentionally much smaller than the NV mailbox protocol; generic callers cannot assume init-data or RAS callbacks exist. Changing enum values or timeout constants can break compatibility with older PF implementations. The header does not declare register offsets, so it relies on `mxgpu_vi.c` including the appropriate VI register headers for mailbox fields and masks.

Test signals: compile tests should verify `vi.c` and `mxgpu_vi.c` agree on the declarations. Runtime signals include successful VI SR-IOV VF init/fini/reset access, expected timeout behavior at `VI_MAILBOX_TIMEDOUT`, correct IRQ setup/teardown via the exported helpers, and absence of calls to unsupported newer virtualization callbacks.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/navi10_ih.c

Purpose: this file implements the Navi10 interrupt-handler IP block for AMDGPU. It initializes IH ring register offsets, allocates and programs interrupt rings, toggles hardware interrupt delivery, reads and advances ring pointers, handles self-interrupts for secondary rings, exposes the IP block lifecycle callbacks, and installs the `amdgpu_ih_funcs` used by the common IRQ dispatcher.

Important APIs and functions: the exported object is `navi10_ih_ip_block`. Main lifecycle callbacks are `navi10_ih_early_init()`, `navi10_ih_sw_init()`, `navi10_ih_sw_fini()`, `navi10_ih_hw_init()`, `navi10_ih_hw_fini()`, `navi10_ih_suspend()`, and `navi10_ih_resume()`, wired through `navi10_ih_ip_funcs`. Ring programming helpers include `navi10_ih_init_register_offset()`, `navi10_ih_toggle_ring_interrupts()`, `navi10_ih_toggle_interrupts()`, `navi10_ih_rb_cntl()`, `navi10_ih_doorbell_rptr()`, `navi10_ih_enable_ring()`, `navi10_ih_irq_init()`, and `navi10_ih_irq_disable()`. Runtime ring-pointer helpers are `navi10_ih_get_wptr()`, `navi10_ih_irq_rearm()`, and `navi10_ih_set_rptr()`. Self-interrupt support is handled by `force_update_wptr_for_self_int()`, `navi10_ih_self_irq()`, and `navi10_ih_set_self_irq_funcs()`. Clock-gating hooks are `navi10_ih_update_clockgating_state()`, `navi10_ih_set_clockgating_state()`, and `navi10_ih_get_clockgating_state()`.

Control flow: early init installs common IH decode/set-rptr callbacks and registers a self-IRQ source. Software init chooses bus-address versus GPU-virtual-address ring backing based on APU and firmware-load mode, initializes ring0 and the software IH ring, sets doorbell use/index, disables ring1 and ring2 by default, fills hardware register offsets, and calls common IRQ initialization. Hardware init disables all rings, lets NBIO configure IH control, optionally enables GPA addressing in IH chicken registers for direct firmware loads using bus addresses, programs each allocated ring's base, size, writeback, overflow, VMID/snoop, doorbell, and pointer registers, updates the NBIO doorbell range, enables PCI bus mastering, re-enables interrupts, turns on forced write-pointer updates for self interrupts, and marks the software ring enabled. Hardware fini disables forced write-pointer updates, disables rings, clears pointers, and waits briefly.

State and persistence: the file mutates `adev->irq.ih`, `ih1`, `ih2`, and `ih_soft` ring structures, including ring size, GPU address, bus-address mode, doorbell index, enabled flags, `rptr`, `wptr_cpu`, `rptr_cpu`, pointer masks, and register offset tables. It programs OSSSYS IH MMIO registers, NBIO doorbell ranges, doorbells, and PSP-managed IH RB control registers when SR-IOV indirect programming is required. State is recreated by sw/hw init and resume; there is no persistent storage. Overflow handling may advance `ih->rptr` to skip overwritten vectors and clears the hardware overflow bit.

Dependencies and integration: the implementation depends on AMDGPU IH core helpers, SOC15 register macros, OSSSYS 5.0 offsets and masks, NBIO functions, PCI bus mastering, firmware load type, PSP register programming for SR-IOV VFs, doorbell writes, common interrupt decoding helpers, workqueues for secondary ring processing, and AMDGPU clock-gating flags. `amdgpu_discovery.c` and SOC-specific setup add `navi10_ih_ip_block` for matching hardware, after which the common IP block framework drives these callbacks.

Risks: SR-IOV VF paths may fail if `psp_reg_program()` cannot program protected IH registers, returning `-ETIMEDOUT` from ring enable/toggle. Doorbell lost-write recovery loops up to `MAX_REARM_RETRY` and assumes register reads can confirm the hardware rptr. Overflow recovery intentionally skips to `wptr + 32`, which preserves forward progress but can drop interrupt vectors. Ring1 and ring2 are initialized with size 0 in this code path, so self-interrupt handling only matters if other setup later enables secondary rings. `navi10_ih_wait_for_idle()` is a stub that returns `-ETIMEDOUT`, and `is_idle()`/`soft_reset()` are TODO-style placeholders. Clock-gating state reporting treats a zero `mmIH_CLK_CTRL` as support indication, which is a narrow hardware-specific signal.

Test signals: useful coverage includes IP block registration and lifecycle ordering, ring initialization with PSP firmware load versus direct firmware load, APU versus dGPU bus-address selection, SR-IOV indirect IH register programming success/failure, doorbell and writeback pointer operation, interrupt enable/disable register state, ring overflow injection and rptr recovery, lost-doorbell rearm behavior on VFs, suspend/resume reprogramming, self-interrupt scheduling for ring IDs 1 and 2 if secondary rings are enabled, and clock-gating toggles under `AMD_CG_SUPPORT_IH_CG`.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/navi10_ih.h

Purpose: this header declares the Navi10 IH IP block descriptor so ASIC discovery and SOC setup code can add the interrupt-handler block to an AMDGPU device. It is the public interface for `navi10_ih.c`.

Important APIs and types: the only exported symbol is `extern const struct amdgpu_ip_block_version navi10_ih_ip_block;`. That object carries the IP block type, version numbers, and lifecycle function table implemented in `navi10_ih.c`.

Control flow: the header has no runtime logic. Consumers include it, pass `&navi10_ih_ip_block` into AMDGPU IP-block registration, and the common device initialization framework later calls the function table embedded in that descriptor.

State and persistence: there is no state in the header. The declared descriptor is a constant object in the C file; all mutable state lives in `adev->irq` rings, MMIO registers, doorbells, PSP programming state, and common IP-block framework data.

Dependencies and integration: users need the AMDGPU IP block type declarations available before including this header. The declaration is referenced by SOC/discovery code that decides whether Navi10-style IH handling applies to a given GPU. It integrates indirectly with the common interrupt handler through the descriptor's lifecycle callbacks.

Risks: because this header exposes only one descriptor, build or link failures are the primary risk if the C object is omitted from the build. Assigning this descriptor to incompatible hardware would call Navi10 register programming against the wrong OSSSYS register layout. Version changes in `struct amdgpu_ip_block_version` must remain compatible with the definition in `navi10_ih.c`.

Test signals: compile/link coverage should verify the descriptor is built and reachable from discovery/SOC code. Runtime validation is indirect: a device using this descriptor should execute Navi10 IH early/sw/hw init, receive interrupts through the common IH dispatch path, and cleanly suspend/resume/fini.
