## sources/distributed-fs/beegfs-protobuf/go/management/management_protoopaque.pb.go

**Purpose:** This is generated Go protobuf code for `management.proto` behind the `//go:build protoopaque` build tag. It exposes the opaque Go API for BeeGFS management messages in package `management`, including entity aliasing, node and target inventory, pool and buddy-group operations, quota limit and usage requests, and license lookup. It is generated by `protoc-gen-go v1.36.2` from `protoc v5.29.2`, so it should be treated as a checked-in generated artifact rather than hand-authored logic.

**Important APIs/types/functions:** The file declares 46 message types plus builders, getters, setters, presence helpers, and descriptor metadata. Top-level request/response types include `SetAliasRequest/Response`, `GetNodesRequest/Response`, delete and state-change messages for nodes and targets, `GetPools`, `CreatePool`, `AssignPool`, `DeletePool`, `GetBuddyGroups`, `CreateBuddyGroup`, `DeleteBuddyGroup`, `MirrorRootInode`, `StartResync`, `QuotaInfo`, quota set/get messages, and `GetLicenseRequest/Response`. Nested response records model `GetNodesResponse_Node` and `_Nic`, `GetTargetsResponse_Target`, `GetPoolsResponse_StoragePool`, and `GetBuddyGroupsResponse_BuddyGroup`. Every generated type implements `Reset`, `String`, `ProtoMessage`, and `ProtoReflect`; fields are accessed through `Get*`, `Set*`, `Has*`, and `Clear*` methods plus `*_builder.Build()`.

**Control flow:** There is no application control flow in this file. Runtime behavior is protobuf boilerplate: constructors/builders populate hidden fields, getters return zero values when receivers or optional values are nil, setters update hidden storage and presence bits, and clearers remove pointer fields or explicit-presence markers. `file_management_proto_init()` runs at package init, guards against duplicate initialization, marks optional fields through `OneofWrappers = []any{}`, builds a `protoimpl.TypeBuilder` with the raw descriptor, Go type table, dependency indexes, and message infos, then releases raw descriptor/type/dependency backing slices.

**State and persistence behavior:** Object state lives in private `xxx_hidden_*` fields, `protoimpl.MessageState`, `UnknownFields`, `SizeCache`, and, for optional scalar fields, `XXX_presence` bitsets and race-detection hook data. Repeated fields are stored as pointers to slices in opaque structs. Durable/wire compatibility is governed by the embedded `management.proto` descriptor and stable field numbers, not the Go struct layout. Optional fields such as delete `execute`, pool `alias`, quota ranges, quota limits, `fs_uuid`, and target capacity counters distinguish unset from explicit zero through `Has*` methods.

**Dependencies and integration points:** The generated code imports `github.com/thinkparq/protobuf/go/beegfs` for shared identifiers and enums, `github.com/thinkparq/protobuf/go/license` for `GetCertDataResult`, and `google.golang.org/protobuf` reflection/runtime packages. Its descriptor declares one `Management` service with unary RPCs for mutation and listing, plus server-streaming `GetQuotaLimits` and `GetQuotaUsage`. It must stay synchronized with `proto/management.proto`, companion generated files `management.pb.go` and `management_grpc.pb.go`, and shared proto files `beegfs.proto` and `license.proto`.

**Risks:** Manual edits will be overwritten and may diverge from the proto source. The file is only compiled under the `protoopaque` build tag; code using open-struct field access will not work with this API. Because generated getters return zero values for unset optional scalars, callers must use `Has*` when zero is meaningful. The schema carries destructive management operations with dry-run `execute` flags, so service implementations must validate identifiers, entity types, and optional presence rather than trusting default values. Quota request range semantics are documented in comments but not enforced by generated code.

**Test signals:** Regenerate protobuf outputs and check for a clean diff, especially after changes to `management.proto`, `beegfs.proto`, or `license.proto`. Compile with and without the `protoopaque` tag if both APIs are supported. Unit tests should verify optional presence round trips, builder behavior, reflection descriptor service/method lists, streamed quota response decoding, and cross-language compatibility for entity identifiers, quota entries, license responses, and nested node/target/pool/buddy-group records.

## sources/distributed-fs/beegfs-protobuf/proto/beegfs.proto

**Purpose:** This proto defines shared BeeGFS identity and state vocabulary used by other service contracts. It is package `beegfs` with Go package `github.com/thinkparq/protobuf/go/beegfs`, and centralizes entity, node, target, quota, network, and capacity enums plus reusable entity identifier messages.

**Important APIs/types/functions:** Enums include `EntityType` (`NODE`, `TARGET`, `BUDDY_GROUP`, `POOL`), `NodeType` (`CLIENT`, `META`, `STORAGE`, `MANAGEMENT`), `ReachabilityState`, `ConsistencyState`, `CapacityPool`, `NicType`, `QuotaIdType`, and `QuotaType`, all with explicit unspecified zero values. `LegacyId` carries BeeGFS numeric ID plus `NodeType`. `EntityIdSet` can carry a globally unique `uid`, globally unique `alias`, and/or legacy numeric ID. Comments define request behavior where one identifier may be enough, while response behavior should return all known identifiers.

**Control flow:** This file has no executable flow; it is a schema dependency. Consumers choose one of the identifier forms when making requests, and management-style responders expand that to a fuller `EntityIdSet` when possible. The proto3 `optional` labels on `EntityIdSet` fields preserve explicit presence for `uid`, `alias`, and `legacy_id`.

**State and persistence behavior:** Persistent compatibility depends on the numeric enum values and field numbers. `0` is reserved as invalid/unspecified across enums and identifiers. `LegacyId.num_id` treats `0` as invalid by contract, but generated code does not enforce that. Alias syntax and uniqueness rules are documented, not enforced in the schema.

**Dependencies and integration points:** This file is imported by management proto/generated Go code and likely all other BeeGFS protobuf packages needing entity references or state enums. It is the common type layer for management inventory, target states, storage pools, quota filters, and NIC reporting.

**Risks:** Reusing generic enums across contexts can allow semantically invalid combinations unless service code validates them. `LegacyId` is not globally unique without entity type context, so APIs must not treat it as a universal identifier by itself. Changing enum numbers or field numbers would break wire compatibility. Alias validation must be implemented outside generated protobuf code.

**Test signals:** Schema tests should verify round-trip presence for `EntityIdSet` optionals, unknown enum tolerance, and cross-language serialization. API tests should cover lookup by `uid`, `alias`, and `legacy_id`, invalid zero IDs, mismatched node/entity types, and response expansion to full identifier sets.

## sources/distributed-fs/beegfs-protobuf/proto/beeremote.proto

**Purpose:** This proto defines the externally facing BeeRemote gRPC API for submitting, querying, updating, and completing remote storage jobs. It coordinates user requests, BeeRemote job state, worker-node work results, remote storage target configuration, stub-file lookup, and capability discovery.

**Important APIs/types/functions:** Service `BeeRemote` exposes `SubmitJob`, `UpdatePaths`, `UpdateJobs`, streaming `GetJobs`, worker-only `UpdateWork`, `GetRSTConfig`, `GetStubContents`, and `GetCapabilities`. Core messages include `JobRequest`, `Job`, `JobResult`, `UpdateJobsRequest/Response`, `GetJobsRequest/Response`, `UpdateWorkRequest/Response`, and RST/stub messages. `JobRequest` contains path, name, priority, RST ID, force/update/stub flags, generation status, and a oneof job type from `flex.SyncJob`, `flex.MockJob`, or `flex.BuilderJob`. `Job` adds ID, creation timestamp, status, external ID, and start/stop mtimes. `Job.State` and `SubmitJobResponse.ResponseStatus` document accepted, terminal, retry, and precondition states.

**Control flow:** Clients submit a `JobRequest` and receive a `JobResult` with a status indicating whether the job was created, already existed, was blocked, or had already reached a terminal/offloaded state. Jobs are updated by exact path, path prefix, job ID, and/or remote target filters. `GetJobsRequest` uses a oneof query for job ID plus path, exact path, or path prefix, with optional inclusion of deterministic work requests and latest work results. Workers return work through BeeRemote's unary `UpdateWork`, intentionally avoiding a reverse streaming result channel. `UpdatePaths` streams one update result per matching path.

**State and persistence behavior:** Comments explicitly describe BeeRemote persistence as separate key/value stores for `Job` records and `WorkResult` records, with deterministic `WorkRequest` generation to reduce stored data. Job state transitions distinguish unassigned, scheduled, running, transient error, failed, cancelled, completed, and offloaded. `start_mtime` and `stop_mtime` are optional timestamps captured around execution and must be interpreted with job state. `generation_status` allows generated requests to represent already-complete/offloaded and precondition/error outcomes before scheduling.

**Dependencies and integration points:** Imports `flex.proto` for work, worker capability, job type, and RST definitions, plus `google/protobuf/timestamp.proto`. Integrates with BeeSync/worker nodes through `flex.Work`, with remote storage target config through `flex.RemoteStorageTarget`, and with clients that need job listings or stub contents.

**Risks:** The schema documents many invariants that generated code will not enforce: worker-only `UpdateWork`, safe use of `FAILED_PRECONDITION`, allowed state transitions, terminal-state immutability, and cleanup before resubmission. `remote_storage_target` is only a numeric ID, so callers need external config consistency. Query flexibility is limited by the backing key/value indexes. Status message concatenation can grow if implementations ignore reset guidance. Force/update/stub semantics require careful implementation to avoid duplicate active work or data loss.

**Test signals:** Service tests should cover idempotent submission, duplicate/completed/offloaded outcomes, forced resubmission, generation status handling, job update filters, path-prefix streaming, work result ownership transfer, and stub lookup. Persistence tests should verify job/work-result store separation, deterministic work request reconstruction, status transitions, mtime capture, and compatibility for the `GetJobsRequest` oneof.

## sources/distributed-fs/beegfs-protobuf/proto/beewatch.proto

**Purpose:** This proto defines BeeGFS Watch event delivery and subscriber acknowledgement messages. It provides a common `Event` envelope for versioned event payloads and a bidirectional streaming `Subscriber.ReceiveEvents` RPC.

**Important APIs/types/functions:** `Event` carries `seq_id`, `meta_id`, optional `meta_mirror`, `event_flags`, and oneof `event_data` with either `V1Event` or `V2Event`. `V1Event` models legacy BeeGFS v7 event types from `FLUSH` through `READ` and includes dropped/missed sequence counters plus path and entry ID fields. `V2Event` models BeeGFS v8 events with an explicit `INVALID = 0`, link count, path/entry fields, message user ID, timestamp, and newer event kinds such as open modes, writer closed, blocked open, stripe pattern changed, and inode locked. `Response` lets subscribers acknowledge `completed_seq` and request graceful shutdown with `shutting_down`.

**Control flow:** Producers stream `Event` messages to a subscriber; the subscriber streams `Response` messages back as it completes processing. Consumers inspect the `event_data` oneof to branch between v1 and v2 payloads. The envelope intentionally avoids minor-version markers; additive protobuf evolution is expected for minor API changes.

**State and persistence behavior:** Sequence tracking is represented by `seq_id` in the envelope and `completed_seq` in responses, while v1 also reports dropped/missed sequence counts. `meta_mirror` is optional so absence can be distinguished from mirror ID zero. Event flags are a raw bitmask whose constants live outside this proto. Persisted event records must preserve oneof case, sequence IDs, and version-specific fields.

**Dependencies and integration points:** The proto has no imports. It integrates with BeeGFS metadata/watch services and generated C++/Go/Rust protobuf outputs. The `Subscriber` service binds this schema to a stream transport used by watch subscribers.

**Risks:** `V1Event.Type` defaults to `FLUSH = 0`, so default-constructed v1 events can appear valid unless callers check envelope context. The raw flag bitmask needs shared constants from `EventContext.h`. Consumers must handle missing `event_data`, unknown enum values, and v1/v2 semantic differences. Minor version changes must remain additive to avoid breaking subscribers.

**Test signals:** Tests should round-trip v1 and v2 events, verify oneof exclusivity, preserve optional `meta_mirror` presence including explicit zero, process acknowledgement sequencing, and cover unknown future fields/enums. Streaming tests should confirm graceful shutdown signaling and backpressure/error behavior around `ReceiveEvents`.

## sources/distributed-fs/beegfs-protobuf/proto/flex.proto

**Purpose:** This proto defines common BeeGFS Flex/BeeRemote worker-node contracts: worker lifecycle RPCs, job/work request shapes, work status reporting, remote storage target configuration, node statistics, and capability/build metadata.

**Important APIs/types/functions:** Service `WorkerNode` exposes `UpdateConfig`, `Heartbeat`, `SubmitWork`, `UpdateWork`, `BulkUpdateWork`, and `GetCapabilities`. Job/work messages include `JobLockedInfo`, `JobRequestCfg`, `WorkRequest` with segment ranges and job type oneof, `BuilderJob`, `MockJob`, `SyncJob`, and `Work` with status and repeated parts. Configuration messages include `UpdateConfigRequest/Response`, `BeeRemoteNode`, and `RemoteStorageTarget` with oneof `S3`, `POSIX`, `Azure`, or `mock`. Capability messages include `GetCapabilitiesResponse`, recursive `Feature`, and `BuildInfo`.

**Control flow:** BeeRemote configures worker nodes with BeeRemote endpoint/auth data and the full RST list. Heartbeats report readiness and optional stats. BeeRemote submits `WorkRequest` records; workers respond with `Work`, then later update status and parts. `UpdateWork` cancels a single request, while `BulkUpdateWork` currently supports unchanged bulk handling for startup/drain scenarios. Sync jobs describe what to do, work requests describe assigned segments, and work parts describe per-worker transfer progress.

**State and persistence behavior:** Work status is the central state machine: unknown, created, scheduled, running, rescheduled, transient error, failed, cancelled, and completed. Terminal worker states mean the worker should no longer retain or act on that request after returning the response. `Work.Part` stores part number, offsets, ETag, SHA-256 checksum, and completion. `JobLockedInfo` captures file state, remote state, stub URL info, external ID, and archive status used before building jobs. RST config is replaced wholesale: omitted RSTs are deleted by contract.

**Dependencies and integration points:** Imports protobuf `Timestamp`. `beeremote.proto` imports and reuses this file heavily for job types, work requests/results, RST config, and capabilities. Implementations integrate with BeeSync workers, BeeRemote management, S3-compatible object stores, POSIX paths, Azure modeled through S3-like config plus account, and build/capability reporting.

**Risks:** Generated code does not enforce worker ownership, valid state transitions, segment/part bounds, RST type support, archival restore polling durations, or secure handling of auth secrets and storage credentials. `RemoteStorageTarget.Azure` embeds S3 config, so consumers must understand provider-specific interpretation. Config update semantics delete missing RSTs, which is risky on partial config generation. Several fields use proto names that map awkwardly in some languages, such as `externalId` and `remoteStorageTarget`.

**Test signals:** Tests should exercise heartbeat readiness, config replacement including deletion of omitted RSTs, SubmitWork and UpdateWork transitions, cancellation, terminal cleanup, part checksum/ETag persistence, segment splitting, archived object restore options, RST type unmarshalling, capability recursion, and compatibility with BeeRemote job/result messages.

## sources/distributed-fs/beegfs-protobuf/proto/license.proto

**Purpose:** This proto defines license and certificate result messages used to pass structured data from a Go library to consumers, including consumers crossing a C FFI boundary through serialized C strings. It models verification outcomes, certificate categories, feature checks, and simplified x509 certificate data.

**Important APIs/types/functions:** Enums are `VerifyResult` (`VERIFY_ERROR`, `VERIFY_VALID`, `VERIFY_INVALID`) and `CertType` (`CA_ROOT`, `CA_INTERMEDIATE`, `PARTNER`, `ENTERPRISE`, `TRIAL`, `COMMUNITY`). Result messages include `VerifyCertResult`, `VerifyFeatureResult`, and `GetCertDataResult`. `CertData` carries certificate type, numeric serial, subject fields, common/subject serial strings, validity timestamps, DNS names with JSON name `DNSNames`, `is_ca`, and optional recursive `parent_data`.

**Control flow:** Library code verifies a certificate or feature and serializes the corresponding result message. Consumers inspect `result` first, then either read `serial`/`data` for successful or partially available results, or read `message` for errors/invalid reasons. `GetCertDataResult` can include certificate data even when verification failed.

**State and persistence behavior:** Certificate state is a simplified x509 projection rather than full certificate bytes. Validity uses protobuf timestamps. DNS names encode licensed features such as feature names or quantity-like names. `parent_data` recursively embeds issuer information, so consumers should handle nested certificate chains. The schema preserves result distinctions between operational errors and verification invalidity.

**Dependencies and integration points:** Imports `google/protobuf/timestamp.proto`. Management generated code depends on `license.GetCertDataResult` for `GetLicenseResponse`. The comments explicitly target Go library output and language-agnostic FFI consumers.

**Risks:** This schema does not carry raw signatures, public keys, or full x509 extensions, so it is suitable for reporting, not independent cryptographic verification. Recursive `parent_data` can create large payloads if chains are long. DNS names as feature identifiers require consistent naming conventions outside the proto. Consumers must not treat `data` presence alone as proof of validity; `result` controls meaning.

**Test signals:** Tests should cover valid, invalid, and error results; serialization across C FFI boundaries; JSON mapping for `DNSNames`; timestamp round trips; parent chain nesting; and management `GetLicense` responses with reload true/false. Verification tests should assert that invalid certificates carry useful messages and that failed verification can still return available certificate data where intended.
