## sources/distributed-fs/ceph-client/drivers/mfd/cs47l90-tables.c

### Purpose
`cs47l90-tables.c` supplies the CS47L90-specific regmap metadata used by the Cirrus Logic Madera MFD core. It is a table and policy companion rather than an independently probing driver: it defines the Rev A patch sequence, the 16-bit reset/cache defaults, the readable and volatile register allowlists, ADSP memory windows, and four exported SPI/I2C regmap configurations.

### Important APIs, Types, And Functions
The exported runtime entry point is `cs47l90_patch(struct madera *madera)`, which applies `cs47l90_reva_16_patch[]` through `madera->regmap`. The file exports `cs47l90_16bit_spi_regmap`, `cs47l90_16bit_i2c_regmap`, `cs47l90_32bit_spi_regmap`, and `cs47l90_32bit_i2c_regmap`. Static data includes `cs47l90_reg_default[]`, a large `struct reg_default` table for the 16-bit register map. Static access helpers are `cs47l90_is_adsp_memory()`, `cs47l90_16bit_readable_register()`, `cs47l90_16bit_volatile_register()`, `cs47l90_32bit_readable_register()`, and `cs47l90_32bit_volatile_register()`.

### Control Flow
The patch path is linear: `cs47l90_patch()` calls `regmap_register_patch()` on the 16-bit regmap, logs `"Error in applying 16-bit patch"` with `dev_err()` on failure, and otherwise returns `0`. After the MFD/bus layer instantiates the regmaps, normal I/O flows through regmap callbacks. The 16-bit readable callback allowlists reset/revision, write sequencer controls, tone/PWM/haptics, clocking and sample-rate controls, FLL1/FLL2/FLLAO, power and mic bias, HP/mic/headphone/jack detect, five input pairs, output paths, PDM speaker, AIF1-AIF4, SPDIF and SLIMbus controls, broad mixer routing blocks, DSP1-DSP7 mixers, ASRC/ISRC/DFC paths, EQ/DRC/HPLPF/ANC/filter controls, GPIO1-GPIO38, and IRQ status/mask/raw ranges. The 16-bit volatile callback is narrower and covers reset/revision, write sequencer controls, live status registers, HP/mic/headphone detect state, input/output status, bus status, FX/ASRC/clock/DFC status, and IRQ status/raw ranges. The 32-bit callbacks allow write sequencer sequence space, OTP HPDET calibration, DSP1-DSP7 config through error-address ranges, and every ADSP memory window returned by `cs47l90_is_adsp_memory()`.

### State, Persistence, And Dependencies
The file owns no mutable C state. Persistent effects are hardware register writes from the patch and the regcache baseline seeded by `cs47l90_reg_default[]`. That default table covers clocks, sample-rate selectors, FLLs, charge pumps, LDO and mic bias, accessory/mic/headphone detection, input/output path setup, PDM speaker, AIFs, SLIMbus/SPDIF, mixer source/volume pairs, DSP routing, ASRC/ISRC/DFC routing, EQ/DRC/HPLPF coefficients, ANC/FCL/FCR coefficient blocks, DFC word controls, GPIO defaults, IRQ masks, debounce, and IRQ control. Dependencies are Linux `regmap`, `device`, and `module` APIs; Madera core state from `struct madera`; register definitions from Madera headers; `REGCACHE_MAPLE`; `ARRAY_SIZE`; and GNU C range cases in switch statements.

### Integration Points
Madera SPI and I2C bus glue consume the exported configs to instantiate big-endian 16-bit and 32-bit regmaps with 32-bit register addresses. SPI configs add `pad_bits = 16`; I2C configs omit padding. The 16-bit maps use the default table and expose registers up to `MADERA_INTERRUPT_RAW_STATUS_1`. The 32-bit maps use `reg_stride = 2`, cache type `REGCACHE_MAPLE`, no default table, and extend to `MADERA_DSP7_PMEM_ERR_ADDR___XMEM_ERR_ADDR`. Codec, IRQ, GPIO, clock, jack-detect, audio-routing, DSP firmware, and regcache sync code all depend on the correctness of these access predicates.

### Risks
The readable and volatile policies are large hand-maintained allowlists, so omitted entries can block legitimate regmap reads while missing volatile entries can produce stale IRQ, sample-rate, jack-detect, DSP, or routing status after cache use or resume. `cs47l90_patch()` has a single Rev A patch path and no revision selector, so future incompatible silicon would need new dispatch logic before reuse. The 32-bit readable and volatile callbacks intentionally treat DSP and ADSP regions as volatile, which preserves firmware/shared-memory correctness but limits caching. The patch sequence includes magic unlock-like writes and clock/FLL/output adjustments; ordering or transcription errors are likely hardware-visible and difficult to catch without silicon. Bus glue must select the SPI or I2C config that matches its framing requirements.

### Test Signals
Useful validation includes CS47L90 probe over SPI and I2C, confirmation that the patch applies once the 16-bit regmap is live, and injected `regmap_register_patch()` failures to verify error logging and return propagation. Regmap debug or targeted tests should sample readable, unreadable, volatile, and cached registers across reset/revision, clock/FLL, input/output, AIF, GPIO, IRQ, DSP config, OTP HPDET, and ADSP window boundaries. Suspend/resume tests should confirm volatile status and IRQ registers are reread from hardware while defaulted controls resync correctly. Functional smoke tests should cover playback/capture paths, AIF1-AIF4 routing, jack/mic/headphone detect, GPIOs, DSP firmware memory access, ASRC/ISRC/DFC paths, ANC/filter coefficient access, and IRQ mask/status behavior.

## sources/distributed-fs/ceph-client/drivers/mfd/cs47l92-tables.c

### Purpose
`cs47l92-tables.c` provides the CS47L92 Madera-family codec register defaults, access predicates, patch programming, ADSP memory map, and exported regmap configurations. It is chip data consumed by MFD and bus code; it does not bind a device itself.

### Important APIs, Types, And Functions
The exported function is `cs47l92_patch(struct madera *madera)`. It applies `cs47l92_reva_16_patch[]` to `madera->regmap` and `cs47l92_reva_32_patch[]` to `madera->regmap_32bit`. Exported configs are `cs47l92_16bit_spi_regmap`, `cs47l92_16bit_i2c_regmap`, `cs47l92_32bit_spi_regmap`, and `cs47l92_32bit_i2c_regmap`. `cs47l92_reg_default[]` seeds the 16-bit regcache. Static helpers are `cs47l92_is_adsp_memory()`, `cs47l92_16bit_readable_register()`, `cs47l92_16bit_volatile_register()`, `cs47l92_32bit_readable_register()`, and `cs47l92_32bit_volatile_register()`.

### Control Flow
`cs47l92_patch()` first registers the 16-bit Rev A patch and returns immediately on failure after logging a 16-bit patch error. If the 16-bit patch succeeds, it registers the 32-bit Rev A patch and similarly logs/returns any failure. Only both successful patch registrations produce a `0` return. The 16-bit readable callback covers the main control surface: reset/revision, write sequencer controls, tone/PWM/haptics, clock and sample-rate controls, CS47L92-specific FLL register ranges, mic bias/detect, HP/headphone/jack detection, four input pairs, output paths, PDM speaker, AIF1-AIF3, SPDIF/SLIMbus, PWM/output/AIF/SLIM/SPDIF/EQ/DRC/HPLP/DSP/ASRC/ISRC/DFC mixers, EQ/DRC/HPLPF processing controls, ASRC/ISRC, AUXPDM, DFC controls, GPIO1-GPIO16, and IRQ status/mask/raw ranges. The volatile callback keeps live reset/revision, write sequencer, haptics, sample-rate, async, HP/mic/headphone detect, input/output, SPDIF/SLIMbus, FX, ASRC, DFC, and IRQ status/raw registers out of stable cache assumptions. The 32-bit callbacks allow write sequencer sequence entries, OTP HPDET calibration, DSP1 config/error ranges, and four ADSP memory windows in `cs47l92_is_adsp_memory()`.

### State, Persistence, And Dependencies
This file has no private runtime state. Hardware state changes come from the 16-bit and 32-bit patches; cached state comes from `cs47l92_reg_default[]`. The default table initializes clocks, sample rates, FLL1/FLL2 values, charge pump/LDO/mic bias, accessory/headphone/mic/jack detection, input and output controls, PDM speaker and short-circuit controls, AIF1-AIF3, SLIMbus/SPDIF, mixer routing, DSP1 and ASRC/ISRC/DFC routing, EQ/DRC/HPLPF controls, AUXPDM, DFC word controls, GPIO1-GPIO16, IRQ masks, debounce, and IRQ control. Dependencies include Linux `regmap`, `device`, and `module` facilities; `struct madera`; Madera and CS47L92 register constants; `REGCACHE_MAPLE`; `ARRAY_SIZE`; and range-case switch syntax.

### Integration Points
Madera bus drivers use the exported SPI/I2C configs to create big-endian 16-bit and 32-bit maps. The 16-bit SPI config has 16 pad bits while the I2C config does not; both use `MADERA_INTERRUPT_RAW_STATUS_1` as `max_register`, the CS47L92 readable/volatile callbacks, maple cache, and the default table. The 32-bit maps use `reg_stride = 2`, extend only through `MADERA_DSP1_PMEM_ERR_ADDR___XMEM_ERR_ADDR`, and are the path for write sequencer, OTP, DSP1, and ADSP memory access. The codec, interrupt, GPIO, audio-routing, jack detection, DSP firmware, suspend/resume, and regmap-debug paths rely on this file to describe valid and live registers accurately.

### Risks
The patch function is named for Rev A data and does not branch on hardware revision, so later incompatible revisions need explicit dispatch before using different sequences. The 32-bit patch is applied only after the 16-bit patch succeeds; partial initialization failure leaves the caller responsible for aborting probe or recovery. Readable/volatile allowlists are dense and easy to drift from the register header. CS47L92 has fewer DSP/ADSP ranges than CS47L90, so copying assumptions from a larger Madera part could expose invalid addresses. The volatile treatment of DSP/ADSP memory is conservative but cache-expensive. Incorrect IRQ mask defaults or volatile status classification can cause missed interrupts, spurious cached status, or bad resume behavior.

### Test Signals
Probe tests should validate both 16-bit and 32-bit patch registration on CS47L92 and inject failures in each stage to verify logging and early returns. Regmap tests should cover boundaries for the 16-bit control space, GPIO1/GPIO16, IRQ1 status/mask/raw ranges, AIF1-AIF3, CS47L92 FLL-specific registers, DSP1 config/error ranges, OTP HPDET calibration, write sequencer entries, and each ADSP memory window. Suspend/resume should check that volatile IRQ, detect, sample-rate, output/input, bus, FX, ASRC, and DFC status reads bypass stale cache. Functional tests should exercise playback/capture, PDM speaker, jack/mic/headphone detection, AIF/SLIMbus/SPDIF routing, DSP1 firmware access, AUXPDM, DFC, ASRC/ISRC, and IRQ mask/status behavior.

## sources/distributed-fs/ceph-client/drivers/mfd/cs5535-mfd.c

### Purpose
`cs5535-mfd.c` is the core PCI MFD driver for AMD/NS CS5535 and CS5536 southbridge ISA functions. The southbridge exposes several legacy I/O BARs for SMBus, GPIO, multi-function general-purpose timers, power management, and ACPI; this driver translates the PCI BAR layout into platform child devices.

### Important APIs, Types, And Functions
The key type is `enum cs5535_mfd_bars`, which fixes BAR indices for SMB, GPIO, MFGPT, PMS, ACPI, and `NR_BARS`. Static state includes `cs5535_mfd_resources[NR_BARS]`, `cs5535_mfd_cells[]` for generic child devices, and `cs5535_olpc_mfd_cells[]` for OLPC ACPI children. Runtime entry points are `cs5535_mfd_probe()` and `cs5535_mfd_remove()`. PCI integration is through `cs5535_mfd_pci_tbl`, `cs5535_mfd_driver`, and `module_pci_driver()`.

### Control Flow
Probe enables the PCI device, copies each PCI BAR start/end into the matching static `struct resource` with `IORESOURCE_IO`, and requests the PMS BAR region. It then calls `mfd_add_devices()` to register `cs5535-smb`, `cs5535-gpio`, `cs5535-mfgpt`, and `cs5535-pms` platform children, each with one resource pointing at its BAR. On OLPC systems detected by `machine_is_olpc()`, probe also requests the ACPI BAR and adds `olpc-xo1-pm-acpi` and `olpc-xo1-sci-acpi`, both sharing the ACPI resource. Error handling unwinds in reverse order: release ACPI if needed, remove MFD children, release PMS, and disable PCI. Remove calls `mfd_remove_devices()`, releases ACPI on OLPC, releases PMS, and disables the PCI device.

### State, Persistence, And Dependencies
The driver stores BAR resources in a file-static array, so the resources persist for the lifetime of the module and are shared by the registered cells. It does not allocate per-device private data or persist configuration beyond requested PCI I/O regions and platform device registration. Dependencies include PCI core APIs, the MFD core, platform device creation inside `mfd_add_devices()`, Linux resource descriptors, `machine_is_olpc()` from `<asm/olpc.h>`, and PCI IDs for NS CS5535 ISA and AMD CS5536 ISA.

### Integration Points
The driver binds PCI devices with `PCI_VENDOR_ID_NS/PCI_DEVICE_ID_NS_CS5535_ISA` and `PCI_VENDOR_ID_AMD/PCI_DEVICE_ID_AMD_CS5536_ISA`. Child drivers bind by platform names `cs5535-smb`, `cs5535-gpio`, `cs5535-mfgpt`, `cs5535-pms`, and on OLPC, `olpc-xo1-pm-acpi` and `olpc-xo1-sci-acpi`. The BAR ordering is hardware-spec-defined and hardcoded, so the child drivers depend on this file mapping the correct I/O region to each cell.

### Risks
`cs5535_mfd_resources` is global rather than per-device, so the implementation assumes effectively one matching southbridge instance; multiple devices would overwrite shared resources. Only PMS and OLPC ACPI regions are explicitly requested by this driver; the other child resources are handed down without parent-level `pci_request_region()` calls, so resource ownership assumptions rely on child behavior and platform expectations. OLPC ACPI children share one ACPI BAR resource, which is intentional but requires non-conflicting child access. The success log always reports only `ARRAY_SIZE(cs5535_mfd_cells)`, so OLPC-specific devices are not reflected in the count.

### Test Signals
Validation should cover probe/remove on CS5535 and CS5536 hardware or emulation, with each child driver receiving the expected I/O start/end from its BAR. Error-injection tests around `pci_enable_device()`, `pci_request_region(PMS_BAR)`, `mfd_add_devices()`, ACPI BAR request, and OLPC MFD addition should verify reverse-order cleanup. OLPC-specific testing should confirm both ACPI children bind and can coexist on the shared ACPI resource. A resource audit should confirm no leaked PCI regions after failed probe or remove.

## sources/distributed-fs/ceph-client/drivers/mfd/da903x.c

### Purpose
`da903x.c` is the base I2C MFD driver for Dialog Semiconductor DA9030 and DA9034 PMICs. It centralizes low-level SMBus register access, bit update helpers, chip initialization, IRQ event masking/dispatch, notifier registration, and platform child creation from board-supplied platform data.

### Important APIs, Types, And Functions
The main private type is `struct da903x_chip`, which holds the `i2c_client`, parent `device`, chip ops, chip type field, `events_mask`, a mutex, deferred IRQ work, and a blocking notifier chain. `struct da903x_chip_ops` abstracts DA9030 vs DA9034 init, event mask/unmask, event read, and status read behavior. Exported APIs are `da903x_register_notifier()`, `da903x_unregister_notifier()`, `da903x_write()`, `da903x_writes()`, `da903x_read()`, `da903x_reads()`, `da903x_set_bits()`, `da903x_clr_bits()`, `da903x_update()`, and `da903x_query_status()`. Probe/remove entry points are `da903x_probe()` and `da903x_remove()`, registered by a `subsys_initcall()` that calls `i2c_add_driver()`.

### Control Flow
Low-level helpers wrap SMBus byte and block reads/writes and log register-address failures. Probe allocates `struct da903x_chip` with devm memory, selects ops from the I2C device ID driver data (`da9030` or `da9034`), initializes the mutex, work item, notifier chain, and client data, then calls the chip-specific `init_chip()`. DA9030 init reads chip ID and writes `DA9030_SYS_CTRL_A = 0xE8`. DA9034 init reads chip ID, writes system control, applies several fixed hardware workarounds and power settings, enables ONKEY power-down behavior, and logs detection. Probe then masks all events with `events_mask = 0xffffffff`, clears pending events by reading them, requests a falling-edge IRQ, and registers child platform devices from `da903x_platform_data`. The IRQ handler disables the IRQ and schedules work; the work item repeatedly reads events, filters masked bits, calls the blocking notifier chain for unmasked events, and re-enables the IRQ when no more events are pending. Remove unregisters all child platform devices.

### State, Persistence, And Dependencies
Runtime state is in `struct da903x_chip`: event mask state mirrors hardware IRQ mask registers, the mutex serializes read-modify-write register helpers, and the notifier chain stores event subscribers. Hardware persistence includes system-control writes, DA9034 workaround writes, event mask registers, and any exported register writes from child drivers. Platform child topology is not described in this file; it depends on `struct da903x_platform_data` containing `num_subdevs` and `subdevs`. Dependencies include Linux I2C SMBus APIs, IRQ APIs, workqueues, mutexes, blocking notifier chains, platform device helpers, devm allocation/request IRQ, and DA903x public definitions from `<linux/mfd/da903x.h>`.

### Integration Points
Child PMIC function drivers use the exported read/write/update helpers and notifier registration against the parent device. Board files or platform code provide `da903x_platform_data` listing subdevices, names, IDs, and platform data blobs; `da903x_add_subdevs()` turns those into child platform devices with the PMIC I2C device as parent. The I2C ID table binds `"da9030"` to ops index 0 and `"da9034"` to ops index 1. Event constants passed to notifier registration must match the chip-specific event bit layout: DA9030 uses three event/mask bytes, while DA9034 uses four event/mask bytes and two status bytes.

### Risks
`da903x_probe()` dereferences platform data without a NULL check in `da903x_add_subdevs()`, so this driver expects legacy board/platform data and is not self-contained for DT/ACPI-only instantiation. `da903x_register_notifier()` and `da903x_unregister_notifier()` update hardware masks without checking the return value before changing notifier registration state. Event mask updates are not protected by `chip->lock`, so concurrent notifier registration/unregistration could race on `events_mask` and hardware mask writes. `da903x_update()` compares `(reg_val & mask) != val` and writes `(reg_val & ~mask) | val`; callers must pass `val` already masked or unmasked bits may leak into the register. `da903x_query_status()` ignores read-status errors and returns a boolean based on whatever remains in `status`. IRQ work calls a blocking notifier chain from process context, which is intentional, but subscribers that sleep or reenter PMIC access can affect event drain latency.

### Test Signals
Tests should cover DA9030 and DA9034 probe paths, including chip ID reads, init register writes, full event masking, pending-event clearing, IRQ request, and child platform device creation. Fault injection on SMBus read/write, IRQ request, platform allocation/add, and chip init should verify cleanup of already-created children and devm-managed resources. Concurrency tests should exercise notifier register/unregister while IRQ work is draining events to expose mask races. Register helper tests should validate `set_bits`, `clr_bits`, and `update` under masked and already-satisfied values. Functional tests should trigger DA9030 three-byte and DA9034 four-byte event paths, verify masked events are suppressed, unmasked events reach subscribers, and status queries reflect hardware status including read-error behavior.
