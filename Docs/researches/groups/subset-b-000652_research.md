# sources/distributed-fs/ceph-client/arch/arm/mach-omap2/omap_hwmod.c

Purpose: Implements the OMAP hwmod core for legacy OMAP2/3/4-style ARM platforms. It turns static `struct omap_hwmod` and `struct omap_hwmod_ocp_if` data into a runtime registry of SoC modules, maps their MPU-visible register targets from DT, resolves clocks and clockdomains, and exposes the lifecycle operations used by `omap_device` and PM runtime paths to enable, idle, reset, and shut down IP blocks.

Important APIs, types, and functions: local `struct omap_hwmod_soc_ops` abstracts SoC-specific PRCM and reset operations, while `struct clkctrl_provider` tracks DT `ti,clkctrl` providers used to map OMAP4+ CLKCTRL offsets to common clock framework clocks. Global state is `omap_hwmod_list`, `mpu_oh`, `soc_ops`, `clkctrl_providers`, and `inited`. Public APIs are `omap_hwmod_init()`, `omap_hwmod_register_links()`, `omap_hwmod_lookup()`, `omap_hwmod_for_each()`, `omap_hwmod_for_each_by_class()`, `omap_hwmod_enable()`, `omap_hwmod_idle()`, `omap_hwmod_shutdown()`, `omap_hwmod_assert_hardreset()`, `omap_hwmod_deassert_hardreset()`, `omap_hwmod_softreset()`, `omap_hwmod_read()`, `omap_hwmod_write()`, `omap_hwmod_get_mpu_rt_va()`, `omap_hwmod_set_postsetup_state()`, `omap_hwmod_parse_module_range()`, and the dynamic `omap_hwmod_init_module()` entry used by `ti-sysc`.

Control flow: early SoC code calls `omap_hwmod_init()` to populate `soc_ops` for OMAP24xx, OMAP34xx, OMAP44xx/54xx/DRA7, or AM33xx/AM43xx/TI81xx paths and to enumerate DT clkctrl providers. Chip data files then call `omap_hwmod_register_links()`, which registers each link with `_register_link()`, registers master/slave hwmods on first sight, and appends each slave OCP port to the slave's `slave_ports` list. `omap_postcore_initcall(omap_hwmod_setup_all)` later ensures the MPU hwmod is initialized first, runs `_init()` on every registered hwmod, sets early-console UART flags when configured, and then runs `_setup()` on every initialized hwmod. `_init()` finds the `ti,hwmods` DT node under `ocp`, maps sysconfig register IO using module ranges or reg entries, initializes clockdomain/main/interface/optional clocks, applies DT flags such as `ti,no-reset-on-init`, and moves the object to `INITIALIZED`. `_setup()` optionally enables a parent hwmod, configures interface clock autoidle, enables and resets the module with `_setup_reset()`, and applies the postsetup state with `_setup_postsetup()`.

Lifecycle behavior: `_enable()` validates state, skips all-hardreset modules, adds an MPU sleep dependency, denies clockdomain idle, enables main/interface/needed optional clocks, programs modulemode, blocks CPU idle polling for flagged modules, waits for target readiness, refreshes context-loss counters, then programs SYSCONFIG active/idle bits with `_enable_sysc()`. `_idle()` reverses that path by programming idle sysconfig, removing sleep dependencies, disabling modulemode and clocks, allowing clockdomain idle, and transitioning to `IDLE`. `_shutdown()` optionally calls class `pre_shutdown`, forces sysconfig idle/autoidle, disables active clocks and modulemode, asserts all hardreset lines, and transitions to `DISABLED`. Reset flow prefers a class-specific `reset()` hook, otherwise uses OCP SYSCONFIG softreset when available, or asserts hardreset lines without deasserting them when driver control is expected. Hardreset helpers look up named reset lines and call the SoC-specific PRM/PRCM functions from `soc_ops`.

State and persistence: runtime state is in memory only: hwmod `_state`, `_int_flags`, `_sysc_cache`, `_mpu_rt_va`, resolved `struct clk *` pointers, clockdomain pointers, OCP port lists, and OMAP4 context-loss counters. Hardware-visible persistent effects include sysconfig idle/wakeup/autoidle/softreset bits, PRCM modulemode and hardreset bits, clockdomain dependencies, and clock enable state. Static chip data remains the source of truth unless `omap_hwmod_init_module()` receives `ti_sysc_module_data`; in that migration path the code checks static data against DT-generated data and, when needed, allocates replacement sysconfig/class/link state and performs setup under the hwmod spinlock.

Dependencies and integration points: this file sits between static `omap_hwmod_*_data.c` descriptors, DT `ti,hwmods`/`ti,sysc-*` nodes, the OMAP clock framework, `clockdomain`/`powerdomain`, PRM/CM register helpers, `ti-sysc`, `omap_device`, PM runtime, watchdog/I2C/HDQ/MMC/DSS reset quirks, earlycon, and low-level MMIO. OMAP4+ CLKCTRL integration can use the common clock framework via `_lookup_clkctrl_clk()` and disables direct hwmod PRCM control for those modules.

Risks: state transitions are strict but not fully defensive; incorrect static data can leave modules unmapped, unclocked, or stuck waiting for IDLEST. SYSCONFIG caching is skipped for `SYSC_NO_CACHE`, and missed cache refresh after reset/context loss can corrupt idle-mode programming. Optional clocks in reset are essential for DSS/GPIO/MMC-like modules; omitting flags can cause softreset timeouts. The `ti-sysc` migration path mutates old static objects at runtime and warns rather than fails on many mismatches, so incorrect DT data may boot with partially divergent behavior. Hardreset code intentionally leaves some processor-like IP in reset for drivers, so consumers must coordinate deassertion. Early boot ordering matters: the MPU hwmod and DSS core ordering have special handling because dependency mistakes can produce sleepdep or L3 errors.

Test signals: boot logs should be checked for `omap_hwmod` warnings about missing DT data, missing MPU register targets, clock lookup failures, sysc mismatch warnings, softreset timeouts, wait-target-ready failures, and unknown SoC type. Runtime PM tests should exercise enable/idle/shutdown transitions for UART, I2C, MMC, GPIO, timers, USB, DSS, and watchdog modules. DT migration testing should compare `ti-sysc` regbits/offsets/flags against static data and verify modules can bind, unbind, rebind, suspend, and resume. Hardware tests should include early console preservation, bootloader-left-enabled modules, context loss on OMAP4+, hardreset assert/deassert for IVA/DSP/MMU, and low-power idle paths that depend on sleep dependencies and `HWMOD_BLOCK_WFI`.

# sources/distributed-fs/ceph-client/arch/arm/mach-omap2/omap_hwmod.h

Purpose: Defines the public and internal data contract for OMAP hwmod descriptors. Static chip data files use these structs, flags, and sysconfig constants to describe IP blocks, OCP interconnects, clocks, PRCM registers, reset lines, device attributes, and runtime states consumed by `omap_hwmod.c`.

Important APIs and types: `struct omap_hwmod_rst_info` names hardreset lines and bit positions. `struct omap_hwmod_opt_clk` describes optional driver-visible clocks. `struct omap_hwmod_omap2_firewall` stores legacy L3/L4 firewall metadata for OCP links. `struct omap_hwmod_ocp_if` binds a master hwmod to a slave hwmod, optional address/firewall/clock metadata, OCP users, and interface flags. `struct omap_hwmod_class_sysconfig` describes class-level OCP SYSCONFIG/SYSSTATUS offsets, bit layout, reset delay, supported idlemodes, and feature flags. `struct omap_hwmod_omap2_prcm` and `struct omap_hwmod_omap4_prcm` hold generation-specific PRCM register metadata. `struct omap_hwmod_class` groups common sysconfig, reset, pre-shutdown, lock, and unlock hooks. `struct omap_hwmod` is the central module descriptor and contains identity, class, clocks, clockdomain, PRCM data, reset lines, OCP slave ports, sysconfig cache, runtime MMIO mapping, spinlock, state, flags, and parent linkage.

Control flow and integration: static descriptors populate mostly non-underscore fields and pass arrays of `struct omap_hwmod_ocp_if *` to `omap_hwmod_register_links()`. `omap_hwmod.c` initializes underscore fields such as `_clk`, `_mpu_rt_va`, `_mpu_port`, `_sysc_cache`, `_state`, and `_int_flags`. Public prototypes declare lookup, iteration, DT range parsing, dynamic `ti-sysc` module initialization, lifecycle operations, hardreset operations, MMIO helpers, and postsetup state control. Chip-specific init functions (`omap2420_hwmod_init()`, `omap2430_hwmod_init()`, `omap3xxx_hwmod_init()`, `dm814x_hwmod_init()`, `dm816x_hwmod_init()`) are declared here for board/SoC init code.

State and flags: idle-mode macros encode force/no/smart/smart-wakeup support for slave idle and master standby fields. `SYSC_HAS_*` and `SYSS_HAS_RESET_STATUS` describe register capabilities; `SYSC_NO_CACHE` marks modules whose sysconfig should not be cached. Module flags encode policy and quirks such as no reset on init, no idle on init, no OCP autoidle, default CLOCKACTIVITY programming, no IDLEST, optional clocks required during reset, 16-bit registers, external optional main clock, WFI blocking, forced master standby, active-only software idle, IO-chain reconfiguration, optional clocks needed for operation, permanent no-idle, and clockdomain no-auto mode. Internal flags mark missing MPU access, loaded sysconfig cache, and first-enable skip for no-idle-init modules. State macros define the lifecycle from `UNKNOWN` to `REGISTERED`, `CLKS_INITED`, `INITIALIZED`, `ENABLED`, `IDLE`, and `DISABLED`, with the default postsetup state depending on `CONFIG_PM`.

Dependencies: the header relies on Linux kernel init/list/ioport/spinlock support and forward declarations for `omap_device`, `device_node`, `ti_sysc_module_data`, and `ti_sysc_cookie`. It imports sysconfig bit layouts exported by common hwmod data files and is included by all OMAP hwmod data and core implementation files.

Risks: this header is a compact ABI between large static data tables and stateful runtime code. Bit flags are positional and not type-safe; wrong combinations can silently change reset, idle, wakeup, or clock behavior. Fields beginning with underscores must not be initialized by data files, but C does not enforce that. `u8` count fields limit descriptor cardinality. Some comments document deprecated or temporary fields (`masters/slaves`, `parent_hwmod`, postsetup state), so new uses risk extending legacy assumptions. `CONFIG_OMAP_HWMOD=n` provides only a stub for class iteration, so consumers must guard other APIs appropriately.

Test signals: build coverage should include OMAP2/3 and OMAP4+ configs, with and without `CONFIG_PM`, early UART debug variants, GPMC debug, and `CONFIG_OMAP_HWMOD`. Runtime validation is indirect: each static data file should register links without `-EINVAL`, lifecycle operations should obey valid state transitions, 16-bit modules should read/write correctly, and DT `ti-sysc` data should map to the same `sysc_regbits`, offsets, flags, and idlemodes represented by these structures.

# sources/distributed-fs/ceph-client/arch/arm/mach-omap2/omap_hwmod_2420_data.c

Purpose: Provides the OMAP2420-specific hwmod integration table. It declares chip-local IP blocks and OCP links, combines them with common OMAP2 hwmods, and exposes `omap2420_hwmod_init()` to register the OMAP2420 module graph.

Important descriptors: the file defines OMAP2420-only IVA1 and DSP classes/modules with named hardreset lines, I2C1/I2C2 modules using a 16-bit I2C class and `omap_i2c_reset`, a mailbox module using the common mailbox class, McBSP1/2 modules with pad and PRCM optional clocks, an MSDI/MMC-like module using `omap_msdi_reset`, and an HDQ/1-wire module using the common HDQ class. OCP links connect L4 CORE to I2C, mailbox, McBSP, MSDI, and HDQ; L3 to IVA, DSP, and GPMC; and L4 WKUP to watchdog and GPIO modules from common 2xxx data.

Control flow: `omap2420_hwmod_init()` calls `omap_hwmod_init()` and then passes `omap2420_hwmod_ocp_ifs` to `omap_hwmod_register_links()`. The array starts with common interconnect and module links (`l3_main__l4_core`, `mpu__l3_main`, DSS, McSPI, UARTs, timers, DSS children, crypto) and then adds 2420-specific I2C, IVA, DSP, watchdog/GPIO, McBSP, MSDI, HDQ, and GPMC links. Registration causes the core to register each master/slave hwmod once and attach each OCP slave port before the later global setup pass maps DT registers and initializes clocks.

State and persistence: this file has no executable runtime state beyond static `struct omap_hwmod`, `struct omap_hwmod_class`, `struct omap_hwmod_rst_info`, optional clock arrays, and `struct omap_hwmod_ocp_if` records. Persistent effects happen only after the core consumes the descriptors: reset lines for IVA/DSP may be asserted by setup, 16-bit I2C/MSDI register access is selected by flags, I2C1 blocks WFI while active, and HDQ uses software-supervised interface idle due to its OCP link flag.

Dependencies and integration: depends on common OMAP2 interconnect/IP block descriptors, common DSS/HDQ data, CM/PRM bit definitions for OMAP24xx, and reset helpers from I2C, MMC/MSDI, and watchdog code. It feeds platform device creation and PM runtime through the shared hwmod core rather than directly interacting with drivers.

Risks: the table mixes 2420-only modules with common OMAP2 descriptors, so any wrong link ordering or clock name affects registration and reset for multiple devices. I2C1 has a documented WFI timeout issue and relies on `HWMOD_BLOCK_WFI`; removing it can break transfers during MPU idle. MSDI and I2C use 16-bit registers, so missing `HWMOD_16BIT_REG` would produce wrong MMIO access width. HDQ marks `OMAP_FIREWALL_L4` in the OCP flags field rather than firewall union data, matching legacy usage but making the meaning easy to misread.

Test signals: OMAP2420 boot should register all links without `_register_link` warnings, preserve early UARTs when debug flags select them, and reset/idle I2C, McBSP, timers, watchdog, DSS, and crypto modules without softreset timeouts. Hardware tests should exercise I2C1 during idle/WFI, DSP/IVA hardreset assert/deassert by driver code, MSDI reset, and HDQ access through the software-supervised interface clock.

# sources/distributed-fs/ceph-client/arch/arm/mach-omap2/omap_hwmod_2430_data.c

Purpose: Provides OMAP2430-specific hwmod integration data and the `omap2430_hwmod_init()` registration entry point. It describes the OMAP2430 additions and differences relative to common OMAP2 data, especially IVA2, high-speed I2C, USB OTG, extra McBSPs, MMC/SD/SDIO, GPIO5, and McSPI3.

Important descriptors: the file defines an IVA module using the shared IVA class with logic/MMU reset lines, I2C1/I2C2 with 16-bit registers and high-speed clock names, GPIO5 with optional clocks controlled during reset, mailbox, McSPI3, USB HS OTG with rich SYSCONFIG idlemode data and erratum-driven software idle/standby flags, McBSP1-5 with shared optional clocks, MMC1/MMC2 with dbck optional clocks and HSMMC dev attributes, and HDQ1W. OCP links cover USB as both an L3 initiator and an L4 CORE target, L4 CORE access to I2C/MMC/McSPI/McBSP/GPIO5/mailbox/HDQ, L3 access to IVA and GPMC, and L4 WKUP access to watchdog/GPIO1-4.

Control flow: `omap2430_hwmod_init()` initializes the hwmod core and registers `omap2430_hwmod_ocp_ifs`. The array includes common OMAP2 interconnects, DSS, UARTs, timers, crypto, McSPI1/2, and then the 2430-specific peripherals. The core later resolves clock names such as `i2chs*_fck`, `usb_l4_ick`, `mmchs*_ick`, `mcbsp*_ick`, and PRCM IDLEST bits.

State and persistence: descriptor state is static; runtime state is produced by `omap_hwmod.c` after registration. USB HS OTG is configured with `HWMOD_NO_OCP_AUTOIDLE`, `HWMOD_SWSUP_SIDLE`, and `HWMOD_SWSUP_MSTANDBY`, so the core avoids problematic automatic idle/standby behavior. MMC modules carry optional debounce/32k-style clocks during reset. I2C modules select 16-bit MMIO access. IVA reset lines are exposed for driver-controlled hardreset behavior.

Dependencies and integration: includes OMAP24xx PRM/CM bit definitions, common OMAP2 data, HSMMC platform data, I2C reset code, watchdog integration, and the common L3 descriptor. It integrates with legacy `ti,hwmods` DT matching and platform data attributes for HSMMC voltage support.

Risks: comments note I2CHS PRCM enable registers do not follow the usual pattern, so future clock handling changes can break I2C readiness if they rely only on the generic PRCM fields. USB OTG has an erratum (`i479`) requiring OCP autoidle disable and software-supervised idle/standby; changing these flags risks deadlocks or broken idle acknowledgements. MMC optional clocks and dev attributes must match board voltage capabilities. OCP links with `OCP_USER_MPU` only for USB may affect sleep dependency behavior compared with MPU+SDMA peripherals.

Test signals: boot OMAP2430 and check for clock lookup and IDLEST wait warnings for I2C, USB, MMC, McSPI3, McBSPs, and GPIO5. Runtime tests should exercise USB OTG suspend/resume and idle transitions, MMC1 dual-voltage operation, I2C transfers across idle, IVA hardreset control, and DSS/crypto/timer modules inherited from common OMAP2 data.

# sources/distributed-fs/ceph-client/arch/arm/mach-omap2/omap_hwmod_2xxx_3xxx_ipblock_data.c

Purpose: Supplies small shared class descriptors for IP blocks common to OMAP2 and OMAP3 data files. It avoids duplicating class/sysconfig definitions for UART, VENC, L3, L4, MPU, IVA, and HDQ/1-wire.

Important descriptors: `omap2_uart_class` uses `omap2_uart_sysc`, with OMAP2-style revision/sysconfig/sysstatus offsets, SIDLE, wakeup, softreset, autoidle, and SYSSTATUS reset-done support. `omap2_venc_hwmod_class` is a simple VENC class without sysconfig data. `l3_hwmod_class`, `l4_hwmod_class`, `mpu_hwmod_class`, and `iva_hwmod_class` are simple bus/initiator classes used by both 2xxx and 3xxx module data. `omap2_hdq1w_class` uses OMAP2 type1 sysconfig and a custom `omap_hdq1w_reset` hook.

Control flow: there is no executable function in this file. Other data files reference these exported class objects while constructing `struct omap_hwmod` records; the core then consumes the class sysconfig and reset hooks during `_init()`, `_setup_reset()`, `_enable_sysc()`, and `_idle_sysc()`.

State and persistence: the file contains static descriptor state only. At runtime, classes influence how the core reads/writes SYSCONFIG, waits for softreset completion, and applies custom reset behavior. UART descriptors using this class inherit smart-idle-capable sysconfig, wakeup enable handling, and softreset support.

Dependencies and integration: depends on `omap_hwmod_common_data.c` for `omap_hwmod_sysc_type1`, `hdq1w.h` for `omap_hdq1w_reset`, and OMAP DMA headers because UART class users may integrate with DMA-capable serial blocks. The exported classes are used by OMAP2420, OMAP2430, and OMAP3 data files.

Risks: because these classes are shared across generations, any sysconfig flag change affects many UART or HDQ instances. UART wakeup/autoidle behavior depends on matching real hardware offsets; a mismatch would show up as softreset or idle failures across multiple SoCs. Simple classes without sysconfig data intentionally skip register setup; adding sysconfig blindly to bus/initiator classes could cause missing-reg mapping failures.

Test signals: build/link should confirm all exported class symbols are available to the SoC data objects. Runtime signals are UART reset/idle/wakeup behavior on OMAP2 and OMAP3, HDQ custom reset success, and absence of hwmod warnings about missing sysconfig fields for shared UART/HDQ modules.

# sources/distributed-fs/ceph-client/arch/arm/mach-omap2/omap_hwmod_2xxx_interconnect_data.c

Purpose: Defines common OMAP2xxx OCP interconnect links shared by OMAP2420 and OMAP2430. These `struct omap_hwmod_ocp_if` records express which bus master can access which slave module, which interface clock gates that path, which initiators use the path, and selected legacy firewall metadata.

Important descriptors: core bus links include L3 main to L4 CORE, MPU to L3 main, DSS to L3, and L4 CORE to L4 WKUP. Peripheral links cover L4 CORE to UART1-3, McSPI1-2, timers3-12, DSS core/dispc/rfbi/venc, RNG, SHAM, and AES. Several display links include OMAP2 L3/L4 firewall region or permission data; VENC also uses `OCPIF_SWSUP_IDLE`. Most peripheral paths list both `OCP_USER_MPU` and `OCP_USER_SDMA`, while the MPU to L3 link is MPU-only.

Control flow: no code executes in this file. OMAP2420 and OMAP2430 init arrays include these link objects and pass them to `omap_hwmod_register_links()`. The hwmod core uses each link to register master/slave hwmods, append the link to the slave's `slave_ports`, count slave ports, find the MPU runtime port, initialize interface clocks, and add/remove sleep dependencies while enabling or idling modules.

State and persistence: the descriptors are static and become runtime list nodes after registration. The `_int_flags` field is set by `_register_link()` to prevent duplicate registration if a common link appears in multiple init arrays. Interface clock names persist into `clk_get()` lookups and can affect whether accesses are possible during setup and runtime PM.

Dependencies and integration: depends on common OMAP2 L3/L4 hwmod objects, common OMAP2 IP block objects, and firewall constants from `l3_2xxx.h` and `l4_2xxx.h`. It is an integration bridge between common module descriptors and chip-specific OMAP2420/2430 arrays.

Risks: incorrect `user` bits can remove sleep dependencies and allow smart-idle while an initiator is active. Incorrect interface clock names will cause `_init_interface_clks()` warnings and may prevent register access. Duplicate link reuse relies on `_OCPIF_INT_FLAGS_REGISTERED`; if the same static object is shared across incompatible boot paths, previous registration state matters. Legacy firewall metadata is descriptive here and easy to confuse with `omap_hwmod_ocp_if.flags` because both mention firewall concepts.

Test signals: OMAP2420/2430 boot should register these common links without duplicate or invalid-link warnings, resolve interface clocks for UART/McSPI/timer/DSS/crypto modules, and expose MPU runtime ports for all accessible slaves. Runtime tests should cover SDMA and MPU users for timers, UARTs, display, and crypto, plus display idle behavior on the VENC link with software-supervised interface idle.

# sources/distributed-fs/ceph-client/arch/arm/mach-omap2/omap_hwmod_2xxx_ipblock_data.c

Purpose: Defines common OMAP2xxx IP block hwmod descriptors used by OMAP2420 and OMAP2430. It covers buses, MPU, timers, watchdog, UARTs, DSS submodules, GPIO, McSPI, GPMC, RNG, SHAM, and AES.

Important descriptors: class/sysconfig records describe OMAP2 DISPC, timers, watchdog, GPIO, mailbox, McSPI, GPMC, RNG, SHAM, and AES using type1 sysconfig fields and the appropriate reset/status/idlemode flags. The watchdog class supplies `omap2_wd_timer_disable` as pre-shutdown and `omap2_wd_timer_reset` as reset hook. Exported hwmods include `l3_main`, `l4_core`, `l4_wkup`, `mpu`, timers3-12 with `HWMOD_SET_DEFAULT_CLOCKACT`, watchdog2, UART1-3 with debug UART and software-idle-active flags, DSS core/dispc/rfbi/venc with optional clocks and reset/IDLEST quirks, GPIO1-4 with optional clocks during reset, McSPI1-2, GPMC with optional no-reset debug preservation, RNG with reset skipped to avoid an imprecise external abort, and SHAM/AES crypto blocks.

Control flow: there are no functions; chip-specific interconnect arrays reference these exported hwmods and class objects. After registration, `omap_hwmod.c` maps each module, initializes clocks, softresets where allowed, applies sysconfig idlemodes, and transitions to the postsetup state. Pre-shutdown/reset hooks are invoked by generic lifecycle paths.

State and persistence: static descriptors encode PRCM module offsets, IDLEST register IDs and bits, main clock names, optional clock roles, sysconfig offsets, and flags. These fields persist into runtime behavior by selecting MMIO width, reset strategy, default clockactivity programming, and whether reset/IDLEST/idle is skipped. RNG intentionally preserves boot state by avoiding reset because reading SYSSTATUS after softreset can abort.

Dependencies and integration: depends on OMAP24xx PRM/CM bit definitions, common hwmod classes, common DSS data, watchdog reset/disable helpers, and platform debug Kconfig macros. The exported objects are linked by `omap_hwmod_2xxx_interconnect_data.c` and the chip-specific 2420/2430 data files.

Risks: common descriptors affect both 2420 and 2430; wrong PRCM bit values or clock names can break multiple chips. Watchdog pre-shutdown/reset must remain correct to avoid unintended MPU resets. DSS requires optional clocks during reset; missing them can leave display modules wedged. GPMC reset is skipped under debug to preserve bootloader timings, so tests must account for configuration inherited from firmware. RNG reset is skipped because of an abort hazard; changing that requires hardware validation. UART debug flags prevent reset/idle for selected console UARTs; wrong debug config can break early console.

Test signals: OMAP2 boot should show successful clock lookup and reset for timers, watchdog, UARTs, GPIOs, McSPI, DSS, GPMC, and crypto without `omap_hwmod` softreset warnings. Specific hardware tests should cover watchdog shutdown, timer CLOCKACTIVITY programming, GPIO reset with optional clocks, DSS reset with all required clocks, GPMC boot timing preservation under debug, RNG probe without reset, and SHAM/AES availability where firewalls allow access.

# sources/distributed-fs/ceph-client/arch/arm/mach-omap2/omap_hwmod_3xxx_data.c

Purpose: Provides the OMAP3xxx family hwmod integration database and `omap3xxx_hwmod_init()` registration flow. It describes common OMAP3 modules plus revision/family-specific additions for OMAP3430 ES levels, OMAP36xx, and AM35xx.

Important descriptors: common bus/initiator modules include L3 main, L4 core/per/wkup/sec, MPU, IVA2 with logic/seq reset lines, and debugss. Peripheral descriptors cover timers3-11, watchdog2, UART1-4 variants, I2C1-3, DSS core/dispc/dsi/rfbi/venc, GPIO1-6, McBSP1-5 plus sidetone modules, SmartReflex MPU/IVA and CORE variants for 34xx/36xx, mailbox, McSPI1-4, MMC1-3 with pre-ES3 erratum attributes, USB host HS and TLL HS, HDQ1W, SAD2D reset lines, GPMC, MMU ISP/IVA, AM35xx Davinci MDIO/EMAC, SHAM, and SSI. Many modules include sysconfig records with precise offsets, idlemodes, reset status flags, optional clocks, clockdomain names, PRCM offsets, and erratum flags.

Control flow: `omap3xxx_hwmod_init()` calls `omap_hwmod_init()`, registers common OMAP3 links, selects the family-specific link array from `omap_rev()`, optionally registers SHAM if DT or GP-device heuristics say the secure IP is usable, registers ES-specific DSS/USB and MMC link arrays, and finally registers DSS child links last. That final ordering is intentional: the comment notes DSS core must be handled before DISPC/RFBI/DSI/VENC to avoid resetting display outputs while enabled and causing unrecoverable L3 errors. The common array wires buses, timers, UARTs, I2C, GPIOs, McBSPs, McSPI, watchdog, MMC3, and GPMC. Family arrays add IVA, SmartReflex, mailbox, HDQ, SAD2D, MMUs, SSI, UART4, USB host/TLL, MMC1/2 variants, and AM35xx MDIO/EMAC.

State and persistence: this file is static descriptor state consumed by the hwmod core. It drives runtime reset/idle policy through flags: USB host uses `HWMOD_SWSUP_SIDLE | HWMOD_SWSUP_MSTANDBY` for errata i660/i571; AM35xx EMAC sets `HWMOD_BLOCK_WFI`; watchdog uses software-supervised idle; I2C sets 16-bit register access and CLOCKACTIVITY; GPIO and DSS often enable optional clocks during reset; GPMC may skip reset under debug; MMU/IVA expose hardreset lines; SmartReflex 34xx uses `SYSC_NO_CACHE` and default clockactivity while 36xx uses wake-capable SIDLE. MMC pre-ES3 descriptors include broken multiblock-read attributes, while ES3+ descriptors use normal attributes.

Dependencies and integration: includes OMAP3 L3/L4 firewall constants, common hwmod class data, OMAP34xx PRM/CM bit definitions, I2C/watchdog reset helpers, HSMMC platform attributes, SmartReflex attributes, SoC revision helpers, and DT availability checks. It integrates with platform devices and PM runtime through the core registry, and with board security policy by checking DT status or GP/HS device type before registering SHAM.

Risks: revision selection is central. Misidentifying `omap_rev()` registers the wrong MMC descriptors, DSS links, UART4, SmartReflex class, USB modules, or AM35xx EMAC/MDIO paths. Secure IP detection is heuristic when DT is missing, so SHAM may be absent on HS parts even if hardware exists or present on boards whose firewalls block access. USB host errata require avoiding smart idle/standby; changing those flags risks deadlocks or resume stalls. AM35xx UART4 softreset depends on an optional UART1 functional clock, and EMAC blocks WFI due to interrupt wake issues. DSS registration order is a functional requirement, not just style. Some AM35xx IPSS links are modeled directly to L3/L4 despite comments saying a proper IPSS hwmod is missing.

Test signals: boot each supported revision path: 3430 ES1, 3430 ES2/ES3, 36xx, and AM35xx. Check for unknown chip warnings, registration errors, missing clockdomain/clock warnings, and DSS setup order regressions. Runtime tests should cover MMC multiblock behavior on pre-ES3 versus ES3+, USB host suspend/resume and remote wake, SmartReflex enable/idle across 34xx and 36xx sysconfig layouts, SHAM registration on GP and DT-enabled boards, AM35xx UART4 reset, EMAC wake/WFI behavior, IVA/MMU hardreset operations, and display boot when the bootloader left outputs enabled.
