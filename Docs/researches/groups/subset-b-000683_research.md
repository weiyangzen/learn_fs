## sources/distributed-fs/ceph-client/arch/arm64/kvm/arm.c

### Purpose
`arm.c` is the main ARM64 KVM host integration unit. It binds the generic KVM core to ARM64 VM and vCPU lifecycle operations, user ABI ioctls, vCPU run-loop entry/exit, IRQ injection, WFI/suspend handling, hypervisor initialization, pKVM setup, and per-CPU virtualization enable/disable paths. It is the file that turns the lower-level VGIC, timer, PMU, sysreg, MMU, nested virtualization, and hyp code into a usable `/dev/kvm` architecture backend.

### Important APIs, Types, and Functions
Important file-local state includes `kvm_mode`, the early boot selected mode; `kvm_wfi_trap_policy` and `kvm_wfe_trap_policy`, controlling WFx trap behavior; `vgic_present`; `kvm_arm_initialised`; and per-CPU hyp state such as `kvm_hyp_initialized`, `kvm_arm_hyp_stack_base`, `kvm_init_params`, and `kvm_hyp_ctxt`. `struct kvm_ioctl_cap_map` maps VM ioctls to capability constants for permission/capability checks.

VM lifecycle entry points are `kvm_arch_alloc_vm`, `kvm_arch_init_vm`, `kvm_arch_create_vm_debugfs`, and `kvm_arch_destroy_vm`. They allocate the ARM64 `struct kvm`, initialize nested state, share host memory with hyp, allocate supported CPU masks, initialize stage-2 MMU state, optionally reserve pKVM host VM metadata, initialize VGIC/timers/hypercalls, and unwind in reverse order on failure. vCPU lifecycle is handled by `kvm_arch_vcpu_precreate`, `kvm_arch_vcpu_create`, `kvm_arch_vcpu_destroy`, `kvm_arch_vcpu_load`, `kvm_arch_vcpu_put`, `kvm_arch_vcpu_run_pid_change`, and `kvm_arch_vcpu_ioctl_vcpu_init`.

User ABI handling is spread across `kvm_vm_ioctl_enable_cap`, `kvm_vm_ioctl_check_extension`, `kvm_arch_vm_ioctl`, and `kvm_arch_vcpu_ioctl`. These expose and validate ARM capabilities such as MTE, SVE, PMUv3, ptrauth, EL2/NV, counter offsets, writable implementation ID registers, SEA-to-user, and supported register masks. vCPU ioctls cover `KVM_ARM_VCPU_INIT`, one-reg get/set, reg-list discovery, device attrs, vCPU events, and finalize.

The main execution API is `kvm_arch_vcpu_ioctl_run`. Its helper set includes `check_vcpu_requests`, `kvm_vcpu_exit_request`, `kvm_arm_vcpu_enter_exit`, `kvm_vcpu_wfi`, `kvm_vcpu_suspend`, and MP-state helpers. Hypervisor and module startup is rooted at `kvm_arm_init`, `init_hyp_mode`, `init_subsystems`, `cpu_prepare_hyp_mode`, `cpu_hyp_init`, `cpu_hyp_reinit`, and `kvm_arch_enable_virtualization_cpu`.

### Control Flow
Module initialization starts in `kvm_arm_init`. It rejects systems without hyp mode or with `kvm-arm.mode=none`, initializes sysreg tables, computes the IPA limit, initializes SVE and VMID allocation, then initializes hyp mappings when the kernel is not already in hyp mode. `init_hyp_mode` allocates hyp page tables, per-CPU stacks, nVHE per-CPU regions, maps hyp text/data/rodata/bss, prepares per-CPU `kvm_nvhe_init_params`, exports sanitized feature data into nVHE symbols, and performs pKVM-only initialization such as PSCI relay, host SVE state, pointer-auth keys, and memory protection. `init_subsystems` runs CPU hyp init on all CPUs, registers CPU PM notifiers, initializes VGIC hyp state, timers, perf callbacks, and hyp tracing. Only after these succeed does `kvm_init` register with the generic KVM core and set `kvm_arm_initialised`.

VM creation validates the VM type, initializes config locking and nested state, shares the `struct kvm` with hyp, prepares stage-2 MMU state, optionally reserves a pKVM VM, initializes VGIC/timer/hypercall state, and records a default max-vCPU count based on VGIC capabilities. vCPU creation initializes MP-state locking, timer/PMU/pvtime state, the vCPU MMU page cache, VGIC CPU state, and hyp sharing. First run through `kvm_arch_vcpu_run_pid_change` finalizes resources that depend on configured features: MPIDR lookup cache, VGIC resources, finalized sysregs, nested state, calculated traps, timer/PMU enablement, GICv5 PPI finalization, and pKVM hyp VM/vCPU creation.

The run loop first completes a pending MMIO return if necessary, loads the vCPU, activates its signal mask, then loops while the guest should continue. Each iteration handles pending host work, processes KVM requests, disables preemption, flushes nested/PMU/VGIC hardware state, marks the vCPU `IN_GUEST_MODE` with the required memory barrier, and either exits early for userspace/kernel work or enters hyp through `__kvm_vcpu_run`. On exit it syncs PMU, VGIC, timer, nested and FP state in a carefully ordered sequence, handles early exits before preemption is re-enabled, checks for disallowed AArch32 state, and finally dispatches architectural exit handling. Before returning to userspace it updates userspace IRQ-chip run fields and commits pending PC/exception adjustments through hyp if needed.

IRQ injection enters through `kvm_vm_ioctl_irq_line`, decodes the packed KVM ARM IRQ number, dispatches CPU IRQ/FIQ lines for userspace irqchip mode, or injects PPI/SPI lines through VGIC for in-kernel irqchips. GICv5 PPIs/SPIs are translated to GICv5 IntIDs and PPIs are restricted to the explicit userspace-exposed mask.

### State and Persistence Behavior
Most state is in generic KVM objects and ARM64 arch extensions, not persistent storage. VM state includes `kvm->arch.flags`, `vcpu_features`, `supported_cpus`, stage-2 MMU state, optional pKVM handles, hypercall state, and the RCU-protected `mpidr_data` acceleration table. vCPU state includes MP state, HCR/MDCR fields, sysregs, timer/PMU/VGIC/debug state, nested state, PID tracking, and flags such as `VCPU_INITIALIZED`. Per-CPU state tracks whether hyp has been initialized and the last vCPU that ran for a given MMU, used to invalidate stale private TLB/I-cache contexts.

Synchronization is explicit: VM config changes use `kvm->arch.config_lock`, VM/vCPU creation paths use `kvm->lock` and vCPU mutex ordering hints for lockdep, MP state uses `mp_state_lock`, slot-sensitive capability changes use `slots_lock`, and MPIDR lookup data uses RCU with `synchronize_rcu` on destruction. CPU PM notifiers reset and restore hyp state around low-power transitions. No durable on-disk state is written by this file.

### Dependencies and Integration Points
This file is tightly integrated with generic KVM (`kvm_init`, vCPU requests, dirty rings, run structures), ARM64 hyp code (`kvm_call_hyp`, nVHE symbols, VHE/nVHE mode selection), stage-2 MMU and VMID allocation, VGIC v2/v3/v5, timers, PMU, debug, FP/SVE, ptrauth, sysregs, nested virtualization, pKVM memory protection, PSCI/SMCCC, CPU PM, perf callbacks, tracepoints, irqfd/irqbypass, and user access helpers. It also consumes CPU feature infrastructure and command-line early parameters.

### Risks and Edge Cases
Correctness depends on subtle ordering in the run loop: request checks around `IN_GUEST_MODE`, interrupt disablement, VGIC/timer/PMU sync ordering, and preemption boundaries. pKVM initialization has limited recovery once protection is finalized. Capability enablement is intentionally constrained before vCPU or memslot creation; relaxing this can break ABI assumptions. MPIDR compression must fall back safely for sparse or adversarial MPIDR layouts. WFI/WFE trap policy interacts with single-task optimization, VGICv5, and direct interrupt injection. Unsupported CPU migration is detected at vCPU load and converted to `KVM_EXIT_FAIL_ENTRY`. Nested virtualization paths depend on correct HCR, VNCR/TLB, and hardware MMU switching.

### Test Signals
Useful tests include KVM selftests for ARM64 VM creation, vCPU init/finalize, one-reg ABI, capability probing, MTE/SVE/PMU/ptrauth feature combinations, irq-line injection with userspace and in-kernel irqchips, WFI wakeups, system suspend wake events, PSCI CPU on/off, dirty-ring exits, and nested virtualization. Boot-time smoke tests should cover VHE, nVHE, protected KVM, `kvm-arm.mode=` variants, CPU hotplug/PM suspend-resume, VGIC absent/present paths, and failure unwinds from hyp, VGIC, timer, and VMID initialization.

## sources/distributed-fs/ceph-client/arch/arm64/kvm/at.c

### Purpose
`at.c` implements trapped ARM64 address-translation instruction emulation for KVM, especially for nested virtualization and guest EL2 contexts. It provides fast paths that temporarily execute hardware AT instructions under the guest translation context, slow paths that software-walk guest stage-1 page tables, PAR_EL1 synthesis, optional stage-2 composition for S12 translations, guest descriptor Access Flag updates, and helper translation APIs used by other KVM code.

### Important APIs, Types, and Functions
The core inputs and outputs are `struct s1_walk_info` and `struct s1_walk_result`, supplied by common ARM64 KVM headers. `fail_s1_walk` records architectural fault status, PTW/stage-2 markers, and failure state. `setup_s1_walk` derives a full translation walk configuration from guest sysregs and the target virtual address: regime, page size, TnSZ, start level, TTBR base, address size limits, endianness, HA/HPD, S1PIE, S1POE, stage-2-on-page-table-walk state, and disabled-MMU handling. `walk_s1` reads and validates guest descriptors, optionally translates page-table accesses through nested stage-2, applies HA Access Flag updates, and returns the final IPA/PA and descriptor metadata.

Translation entry points include `__kvm_at_s1e01`, `__kvm_at_s1e2`, `__kvm_at_s12`, and `__kvm_translate_va`. `__kvm_find_s1_desc_level` walks until a caller-specified descriptor IPA is found and reports its level. Descriptor updates use `__kvm_at_swap_desc`, which chooses LSUI, LSE CAS, or LL/SC depending on CPU capabilities. Attribute and permission synthesis is handled by `compute_par_s1`, `compute_par_s12`, `compute_s1_permissions`, `compute_s1_direct_permissions`, `compute_s1_hierarchical_permissions`, `compute_s1_indirect_permissions`, and `compute_s1_overlay_permissions`.

### Control Flow
For S1E0/S1E1 operations, `__kvm_at_s1e01` first calls `__kvm_at_s1e01_fast`. The fast path takes `kvm->mmu_lock` with interrupts disabled, saves host EL1 MMU registers when it must context-switch a nested L2 translation context, loads guest TTBR/TCR/MAIR/SCTLR/TCR2/PIR/PIRE0/POR and stage-2 state, switches HCR to the guest view, executes the matching hardware AT instruction, reads PAR_EL1 on success, restores host HCR and MMU state, and returns either a valid PAR or a failure marker. If hardware AT failed for anything other than a definitive S1 permission/access fault, `handle_at_slow` performs the software walk and writes the synthesized PAR_EL1 back to the vCPU.

The slow path computes the translation regime from the AT opcode and virtual EL2 `{E2H,TGE}` state. `setup_s1_walk` reads the applicable EL1 or EL2 control registers, selects TTBR0/TTBR1 from VA bit 55, decodes TG0/TG1, computes 52-bit PA support, checks TBI/address-size and translation-size constraints, handles disabled MMU cases, validates EPD/E0PD, derives output size from TCR IPS/PS and KVM IPA limits, aligns TTBR base addresses including LPA2 high bits, and records HA. `walk_s1` then iterates levels from the computed start level, derives the descriptor index from the VA, translates page-table descriptor accesses through nested stage-2 if required, invokes an optional filter, reads descriptors using guest endianness, validates invalid/table/block/page descriptors, records table permissions unless HPD disables hierarchy, checks output address size, updates AF when HA is enabled, and produces final output address, descriptor, level, nG, and ASID metadata.

After a successful walk, `compute_s1_permissions` calculates direct or indirect S1 permissions, applies hierarchical APTable/PXNTable/UXNTable restrictions when enabled, applies permission overlays, enforces WXN and PAN/PAN3, and lets `handle_at_slow` decide whether the requested read/write/EL0/EL1 access should become a permission fault. `compute_par_s1` converts success, disabled-MMU, or failure state to PAR_EL1. `__kvm_at_s12` first performs the S1 translation, then, when the regime and HCR require it, walks nested stage-2 for the resulting IPA, checks read/write permission, combines memory attributes/shareability, and writes a final S12 PAR.

### State and Persistence Behavior
The file is mostly stateless across calls. It temporarily mutates CPU system registers in fast paths and restores them before returning. It may persistently update guest memory by setting `PTE_AF` when hardware access flag management is architecturally enabled for the guest walk. That update is done through atomic compare-and-swap on the userspace backing page, under KVM SRCU and with writable memslot validation, and then marks the page dirty. The code also writes the emulated PAR result into the vCPU `PAR_EL1` sysreg.

### Dependencies and Integration Points
The walker depends on guest sysreg accessors, CPU feature predicates, ARM64 page-table encodings, ESR/PAR/TCR/SCTLR/HCR definitions, nested stage-2 walkers (`kvm_walk_nested_s2`), stage-2 MMU loading, KVM memslot/HVA translation, SRCU, dirty logging, privileged uaccess helpers, LSUI/LSE/LLSC atomic mechanisms, and hyp helper `__kvm_at`. It integrates with nested virtualization because AT instructions trapped from virtual EL2 need the L1-controlled translation regime and may require L2 stage-2 context lookup via `lookup_s2_mmu`.

### Risks and Edge Cases
The biggest risk is architectural drift: the software walker mirrors many ARM ARM rules for LPA2, 52-bit PA, TBI, EPD/E0PD, HPD, HA, S1PIE, S1POE, PAN3, WXN, disabled MMU, attribute composition, and stage-2 fault reporting. Any mismatch can expose incorrect PAR_EL1 results to a nested hypervisor. Fast paths are sensitive because they switch MMU context behind the host's back under interrupt-disabled locking. Descriptor AF updates can race with userspace or another vCPU; `-EAGAIN` intentionally restarts the walk. Endianness and 52-bit descriptor address extraction are easy bug points. The S12 path must distinguish S1 failures from S2 failures and avoid composing a bogus PAR when only one translation stage applies.

### Test Signals
Good coverage comes from ARM64 KVM selftests that execute AT S1E0, S1E1, S1E2, and S12 instructions from nested guests across 4K/16K/64K granules, TTBR0/TTBR1, disabled MMU, TBI on/off, EPD/E0PD, 48-bit and 52-bit PAs, LPA2, big-endian descriptors, AF set/clear, read/write/user/privileged permission failures, PAN/PAN3, WXN, HPD hierarchy, S1PIE/S1POE, nested stage-2 read/write faults, and memslot read-only/error paths. Fault tests should assert PAR_EL1 `F`, `S`, `PTW`, and `FST` fields rather than only return codes.

## sources/distributed-fs/ceph-client/arch/arm64/kvm/config.c

### Purpose
`config.c` is the ARM64 KVM feature-to-register configuration engine. It describes how guest-visible ID register features determine RES0/RES1 bits, fine-grained trap behavior, fine-grained undef behavior, and fixed bit masks for EL2/system control registers. It centralizes the mapping between architectural feature availability and the bits KVM allows, traps, forces, or hides in registers such as HCR_EL2, HCRX_EL2, SCTLR_EL1/EL2, SCTLR2, TCR2_EL2, MDCR_EL2, VTCR_EL2, and the FGT/GCIE trap registers.

### Important APIs, Types, and Functions
`struct reg_bits_to_feat_map` describes a dependency from register bits or `struct fgt_masks` to a feature. Its flags model special cases: `NEVER_FGU`, `CALL_FUNC`, `FORCE_RESx`, `MASKS_POINTER`, `AS_RES1`, `REQUIRES_E2H1`, `RES1_WHEN_E2H0`, and `RES1_WHEN_E2H1`. `struct reg_feat_map_desc` groups a register-level feature dependency with bit-level dependencies.

Macros such as `NEEDS_FEAT`, `NEEDS_FEAT_FLAG`, `NEEDS_FEAT_MASKS`, `FORCE_RES0`, `FORCE_RES1`, `DECLARE_FEAT_MAP`, and `DECLARE_FEAT_MAP_FGT` build compact declarative maps. Feature shorthand macros cover PMU, SPE, TRBE, BRBE, RAS, GIC, MTE, nested virtualization, ptrauth, S1/S2 PIE/POE, FGT, FGT2, HCX, GCIE, and many newer architecture extensions.

Public functions are `check_feature_map`, `compute_fgu`, `get_reg_fixed_bits`, and `kvm_vcpu_load_fgt`. Internal helpers include feature predicates such as `feat_nv2`, `feat_rasv1p1`, `feat_pauth`, `feat_lpa2`, and `feat_vmid16`; validation helpers `check_feat_map` and `check_reg_desc`; match helpers `idreg_feat_match`; computation helpers `compute_resx_bits`, `compute_reg_resx_bits`, `compute_fgu_bits`, and `compute_fgt`; and register-to-mask/group dispatchers.

### Control Flow
The file first defines the declarative language for feature maps, then declares feature predicates and the maps themselves. The FGT maps (`hfgrtr`, `hfgwtr`, `hfgitr`, `hdfgrtr`, `hdfgwtr`, `hafgrtr`, their FGT2 variants, and ICH GCIE variants) describe which sysreg, debug, trace, PMU, AMU, GIC CPU-interface, cache, TLBI, ptrauth, RAS, and extension-specific operations are valid only when corresponding guest-visible features exist. Non-FGT maps describe fixed/reserved behavior for HCRX_EL2, HCR_EL2, SCTLR2_EL1/EL2, TCR2_EL2, SCTLR_EL1, SCTLR_EL2, MDCR_EL2, and VTCR_EL2.

`check_feature_map` runs at initialization and validates that each map accounts for all non-architectural bits relative to the register RESx mask. It emits a KVM error if a map leaves undefined behavior for unclassified bits. Runtime computation starts with `idreg_feat_match`, which reads the guest's `kvm->arch.id_regs[]` field and compares a feature field against a minimum limit, including signed fields when needed. `compute_resx_bits` iterates a map, applies required/excluded flag filtering, evaluates forced bits, function predicates, or ID-register predicates, adjusts for E2H constraints, and accumulates RES0 or RES1 bits for unsupported features. `compute_reg_resx_bits` folds bit-level and register-level dependencies together, including static FGT mask RESx bits when the descriptor uses mask pointers.

`get_reg_fixed_bits` is the external query path for sysreg emulation: it switches on `enum vcpu_sysreg` and returns the computed RES0/RES1 mask for the requested register. `compute_fgu` computes per-VM fine-grained undef masks from unsupported feature bits grouped by FGT group. `kvm_vcpu_load_fgt` recomputes per-vCPU trap register values on load when the CPU supports FGT. It starts from architectural masks, sets/clears bits for unsupported features, folds in nested guest values when in nested context, applies RESx masks, and adds targeted overrides such as Ampere AC03 TCR_EL1 write trapping, MDSCR_EL1 trapping in hyp context, mandatory ICC_IAFFIDR/ICC_IDR trapping, and write-only trapping for guest-visible PPI enable subsets.

### State and Persistence Behavior
The declarative maps are static constant data. Runtime results are stored in VM/vCPU architecture state: `kvm->arch.fgu[]` holds fine-grained undef masks per group, and `*vcpu_fgt(vcpu, reg)` stores the computed trap register value for a loaded vCPU. `get_reg_fixed_bits` returns transient computed masks based on the current guest ID register view. There is no disk persistence. Correctness depends on feature registers being finalized before use and on recomputing FGT values at vCPU load to include nested context and CPU-specific workaround state.

### Dependencies and Integration Points
This file depends on ARM64 sysreg definitions, ID-register field metadata, KVM feature helpers (`kvm_has_feat`, `kvm_has_feat_enum`, `kvm_has_pauth`), nested context helpers, FGT mask definitions, CPU capability checks, and host sysreg reads for extension subfeatures not represented in guest ID JSON-like data, such as SMIDR, PMSIDR, and TRBIDR details. It integrates with `arm.c` via `kvm_vcpu_load_fgt` during vCPU load and via `kvm_hyp_init_symbols`, which exports FGT masks to nVHE. Sysreg emulation uses `get_reg_fixed_bits` to enforce RES0/RES1 behavior.

### Risks and Edge Cases
The main risk is incompleteness: every new architectural bit in covered registers must be mapped to a feature or forced RESx behavior, or guests can observe undefined behavior. E2H-dependent RES1/RES0 handling is subtle and must match the architecture for both host and nested virtualization contexts. Function predicates that read host registers are temporary approximations for features not fully virtualized and can become wrong once KVM exposes those features differently to guests. FGT polarity uses both mask and nmask fields, so set/clear inversion bugs can make KVM trap too much, too little, or undef accesses incorrectly. Nested context merging must preserve L1's intended traps while still enforcing host-unsupported feature restrictions.

### Test Signals
Test signals include sysreg mask selftests that vary guest ID registers and assert RES0/RES1 behavior for HCR_EL2, HCRX_EL2, SCTLR_EL1/EL2, SCTLR2, TCR2_EL2, MDCR_EL2, and VTCR_EL2; FGT tests that verify unsupported sysregs/instructions trap or undef as expected; nested virtualization tests where L1 programs FGT registers and L2 accesses affected sysregs; PMU/SPE/TRBE/debug/GIC CPU-interface feature exposure tests; and boot-time checks that `check_feature_map` is quiet for all supported kernel configurations.

## sources/distributed-fs/ceph-client/arch/arm64/kvm/debug.c

### Purpose
`debug.c` manages ARM64 KVM debug, guest debug, profiling, trace, and debug-register ownership transitions. It configures `MDCR_EL2`, records host debug capabilities, selects whether breakpoint/watchpoint registers are host-owned, guest-owned, or unused, virtualizes OS Lock effects, preserves software single-step state across KVM/user debugging, and exposes TRBE/tracing hooks used by tracing code.

### Important APIs, Types, and Functions
`cpu_has_spe` detects usable Statistical Profiling Extension support by checking ID_AA64DFR0 and PMBIDR. `kvm_init_host_debug_data` records host PMU counter count, breakpoint/watchpoint counts, and capability flags such as `HAS_SPE`, `HAS_BRBE`, `HAS_TRBE`, and `EL1_TRACING_CONFIGURED`. `kvm_debug_init_vhe` sanitizes VHE SPE state by clearing PMSCR_EL1.

`kvm_arm_setup_mdcr_el2` builds the vCPU's `mdcr_el2` trap configuration. `setup_external_mdscr` computes the external MDSCR_EL1 image used when KVM or userspace owns debug state. `kvm_vcpu_load_debug` selects debug ownership and prepares MDCR/MDSCR state before vCPU entry. `kvm_vcpu_put_debug` restores host MDCR_EL2 on VHE and repairs guest/host software-step pending state on exit. `kvm_debug_set_guest_ownership` gives ownership of debug registers to the guest after trapped access when the host is not already using them. `kvm_debug_handle_oslar` emulates writes to OSLAR_EL1 and reloads vCPU state to apply the changed ownership/trap behavior.

Trace/TRBE exported APIs are `kvm_enable_trbe`, `kvm_disable_trbe`, and `kvm_tracing_set_el1_configuration`. They are guarded by `skip_trbe_access`, which rejects preemptible callers, protected KVM, uninitialized KVM, and VHE-only cases where applicable.

### Control Flow
Host debug initialization reads `id_aa64dfr0_el1`, records PMU event counter count if PMUv3 is implemented, records BRP/WRP counts, marks SPE if implemented and not prohibited by PMBIDR, and for nVHE additionally records BRBE and TRBE/trace-filter availability. In protected mode without TRBE, EL1 tracing is forced disabled by marking `EL1_TRACING_CONFIGURED`. VHE debug initialization clears unknown reset values in PMSCR when SPE is present.

On vCPU load, KVM first asserts sysregs are not already loaded on CPU. In VHE it saves host `MDCR_EL2`. It then selects a debug owner. If userspace requested guest debugging or the guest OS Lock is enabled, KVM takes host ownership, computes an external MDSCR value, and, for userspace single-step, steals the guest single-step state machine by tracking `GUEST_SS_ACTIVE_PENDING` and `HOST_SS_ACTIVE_PENDING` around the CPSR SS bit. Otherwise it reads guest `MDSCR_EL1`: if KDE or MDE is set, debug registers are guest-owned and should be loaded eagerly; if neither is set, the state is free. Finally it calls `kvm_arm_setup_mdcr_el2`.

`kvm_arm_setup_mdcr_el2` disables preemption, initializes `vcpu->arch.mdcr_el2` with the host counter count and trap bits for PMU, SPE, trace filter, PMCR, debug ROM, and OS-related debug registers. It routes software debug exceptions to EL2 when userspace is debugging, traps debug registers with `TDA` when the guest does not own them, lets nested virtualization adjust MDCR when needed, and writes MDCR_EL2 directly on VHE. vCPU put restores host MDCR_EL2 on VHE and undoes the single-step state swap before returning to userspace.

### State and Persistence Behavior
Persistent runtime state lives in per-CPU host debug data and per-vCPU arch fields. Host data stores PMU counter count, breakpoint/watchpoint counts, debug capability flags, saved VHE `mdcr_el2`, and trace configuration. vCPU state includes `arch.mdcr_el2`, `arch.external_mdscr_el1`, `arch.debug_owner`, guest sysregs such as MDSCR/OSLSR, and software-step pending flags. No file or disk state is written. OSLAR handling updates guest OS Lock state and immediately reloads vCPU state under preemption disable so trap ownership takes effect on the current CPU.

### Dependencies and Integration Points
This file depends on ARM64 PMU/debug/trace sysreg definitions, KVM host data helpers, VHE/nVHE mode predicates, pKVM mode checks, nested virtualization MDCR setup, vCPU flag helpers, sysreg emulation accessors, and exported trace/TRBE consumers. It is called from `arm.c` during CPU hyp context initialization (`kvm_init_host_debug_data`, `kvm_debug_init_vhe`) and vCPU scheduling (`kvm_vcpu_load_debug`, `kvm_vcpu_put_debug`). The OSLAR path calls back into `kvm_arch_vcpu_put` and `kvm_arch_vcpu_load` to reapply the full scheduling state.

### Risks and Edge Cases
Debug ownership has high ABI sensitivity because userspace debugging, guest debugging, OS Lock semantics, and nested virtualization all compete for the same registers. Single-step state stealing must preserve both host-requested and guest-pending SS bits or userspace can see spurious/missing step events. `MDCR_EL2` trap bits must prevent unintended guest access to PMU, SPE, TRBE, trace, and debug resources, especially in protected or nVHE modes. The TRBE exported APIs require non-preemptible callers; misuse is warned and ignored. The OSLAR reload path is broad because it puts and reloads the whole vCPU, so callers must already be in a valid loaded-vCPU context.

### Test Signals
Relevant tests include KVM guest debug selftests for software single-step, hardware breakpoints/watchpoints, guest-owned debug register access, OS Lock enable/disable, VHE and nVHE MDCR save/restore, nested virtualization MDCR behavior, and PMU/SPE/TRBE trap exposure. Trace tests should verify `kvm_enable_trbe`, `kvm_disable_trbe`, and `kvm_tracing_set_el1_configuration` under preemption-disabled contexts and confirm protected KVM rejects TRBE manipulation. Regression checks should assert host debug state is restored after vCPU exit.
