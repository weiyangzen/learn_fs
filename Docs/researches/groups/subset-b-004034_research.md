# sources/distributed-fs/ceph-client/drivers/md/dm-vdo/recovery-journal.c

Purpose: Implements the runtime VDO recovery journal: an on-disk circular log of block-map and reference-count changes that protects dirty data until block-map pages and slab journals are durable. It owns journal entry assignment, in-memory tail block buffering, metadata writes with flush/FUA ordering, journal block reference locks, reaping of obsolete log blocks, drain/resume behavior, statistics, and post-repair reinitialization.

Important APIs, types, and functions: public entry points include `vdo_decode_recovery_journal()`, `vdo_free_recovery_journal()`, `vdo_open_recovery_journal()`, `vdo_record_recovery_journal()`, `vdo_initialize_recovery_journal_post_repair()`, `vdo_add_recovery_journal_entry()`, `vdo_acquire_recovery_journal_block_reference()`, `vdo_release_recovery_journal_block_reference()`, `vdo_release_journal_entry_lock()`, `vdo_drain_recovery_journal()`, `vdo_resume_recovery_journal()`, and statistic getters/dumpers. Core private helpers include `advance_tail()`, `prepare_to_assign_entry()`, `assign_entries()`, `write_blocks()`, `write_block()`, `complete_write()`, `reap_recovery_journal()`, `finish_reaping()`, `check_for_drain_complete()`, and lock-counter helpers around `struct lock_counter`. The implementation uses `struct recovery_journal_block` as both a list node and VIO-backed in-memory journal block.

Control flow: decode allocates the journal object, reserved in-memory tail blocks, lock-counter arrays, a flush VIO, and read-only listener, then initializes sequence/head/tail state from the superblock state. Normal operation queues `data_vio` waiters in `vdo_add_recovery_journal_entry()`, advances the append point, assigns waiters to the active tail block while disk and in-memory space are available, encodes queued entries into packed sectors, and writes blocks. Writes are batched only when no other journal writes are pending; all full blocks are queued, and the active partial block is written if it is the only way to make progress. Completion updates committed counters, releases waiters in journal order, recycles fully committed blocks, retries writes for blocks that filled during an in-flight commit, and checks drain completion.

State and persistence behavior: on disk, the journal is a circular block range rooted at `origin`; sequence numbers are monotonic and mapped to physical journal block numbers by low bits because `size` is expected to be power-of-two compatible. Each block header records metadata type, nonce, recovery count, sequence number, check byte, logical block usage, block-map data block usage, block-map head, slab-journal head, and entry count. Each write uses `REQ_PREFLUSH | REQ_FUA` so referenced data is stable before the journal entry can authorize old data overwrite. In memory, `tail`, `append_point`, `commit_point`, `last_write_acknowledged`, `block_map_head`, `slab_journal_head`, reap heads, `available_space`, `pending_write_count`, usage counters, and event counters describe progress. Reaping advances block-map and slab-journal heads only after lock counters show no live journal, logical-zone, or physical-zone references, then submits a lower-layer flush before making the space available.

Dependencies and integration points: depends on VDO completion/thread dispatch, `vio` metadata I/O, wait queues, admin state, read-only notification, packed encodings, block-map era advancement, slab depot tail commits, and kernel atomics/barriers. The block map calls into this file to journal mappings and to acquire/release journal locks for dirty block-map pages. Slab depot uses physical-zone references to keep journal blocks needed by slab journal replay. Repair calls `vdo_initialize_recovery_journal_post_repair()` after replay/rebuild. Admin load/suspend/save paths call drain/resume and record the journal into the superblock.

Risks and invariants: correctness depends on single journal-thread execution for most mutable journal state, plus explicit barriers around cross-zone lock counters. A lock-counter underflow/overflow, missed notification, or stale suspended state can prematurely reap entries needed for recovery. Sequence overflow above the slab-journal supported range forces read-only mode. Partial writes/torn sectors must remain recoverable because the active partial block may be written repeatedly. `available_space` and reserved-block calculations must prevent wrapping over a block that still appears to be a valid head. Error paths enter read-only mode, wake waiters, and recycle in-memory blocks; tests should check no waiter is stranded. The old `FIXME` notes around read-only write short-circuiting and construction state are signals for fragile lifecycle behavior.

Test signals: exercise full-block and partial-block commits, concurrent entry assignment while a block write is in flight, disk-full wait/reap wakeups, read-only transitions during pending writes and drains, suspend/save/resume state recording, lock acquisition/release from logical and physical zones, journal entry lock release ordering, slab-journal commit-threshold forcing, sequence wrap/overflow checks, and metadata I/O failure paths. Recovery tests should confirm headers record correct heads and usage counters after journal writes and after reaping.

# sources/distributed-fs/ceph-client/drivers/md/dm-vdo/recovery-journal.h

Purpose: Declares the recovery journal interface and its main in-memory data structures. The file documents the journal model: a single-threaded circular on-disk log plus a smaller set of VIO-backed in-memory tail blocks and reference counters that prevent journal blocks from being reaped before dependent block-map or slab-journal updates are durable.

Important APIs, types, and functions: `enum vdo_zone_type` names admin, journal, logical, and physical lock/dispatch domains. `struct lock_counter` stores per-block journal counters, journal decrement counters, per-zone logical/physical reference arrays, aggregate zone counts, and a completion used to notify the journal thread. `struct recovery_journal_block` represents one in-memory journal block with free/active list linkage, a write waiter, VIO, sequence and disk block number, commit state, entry counters, current packed sector pointer, and entry/commit wait queues. `struct recovery_journal` is the full journal state object containing thread/depot/block-map pointers, wait queues, admin state, sequence/head/reap positions, usage counters, I/O counters, statistics, lock counters, and flexible-array tail blocks.

Control flow contract: callers decode/open the journal with `vdo_decode_recovery_journal()` and `vdo_open_recovery_journal()`, submit asynchronous entries with `vdo_add_recovery_journal_entry()`, hold/release external references with `vdo_acquire_recovery_journal_block_reference()` and `vdo_release_recovery_journal_block_reference()`, release per-entry journal locks with `vdo_release_journal_entry_lock()`, drain/resume the journal during admin operations, record state into the superblock with `vdo_record_recovery_journal()`, and query usage/statistics. Inline helpers map a sequence number to an on-disk journal block and compute the per-lap check byte used in packed sectors.

State and persistence behavior: the header defines the durable sequence model: `head` is the minimum of block-map and slab-journal heads, `tail` is the end of the active half-open interval, and `active` is the sequence receiving entries. In-memory blocks move between `free_tail_blocks` and `active_tail_blocks`; waiters can block for an entry assignment or for commit durability. Lock counters cover the journal block itself, each journal entry until its block-map update is applied, dirty block-map pages, and slab-journal dependencies. `available_space`, `pending_decrement_count`, `pending_write_count`, and statistics provide pressure and observability signals.

Dependencies and integration points: includes VDO admin-state, flush, constants, encodings, statistics, wait-queue, numeric, and type definitions. The API is consumed by block-map, data-VIO, slab-depot, repair, superblock encoding, admin drain/save/resume paths, and statistics/debug dumping. The inline `vdo_get_recovery_journal_block_number()` depends on `vdo_compute_recovery_journal_block_number()` from numeric helpers and on the journal size property described by the comment.

Risks and invariants: structure layout and field meaning are tightly coupled to `recovery-journal.c` and `repair.c`. The single-threaded journal-zone assumption is a central invariant; fields are mostly not protected by locks. Counter arrays are `u16`, so overflow checks in the implementation are necessary. `sequence_number == 0` is treated by implementation APIs as a no-reference sentinel. Tests and audits should ensure all users respect zone type and zone id when acquiring/releasing references and that drain/resume callers use the journal thread.

Test signals: verify API users preserve entry ordering, never reuse a `data_vio` with a nonzero `recovery_sequence_number`, correctly acquire block-map and slab-journal references, record saved versus suspended starts correctly, and expose statistics without mutating state. ABI-sensitive review should compare packed encoding constants against `entries_per_block` and sector count assumptions.

# sources/distributed-fs/ceph-client/drivers/md/dm-vdo/repair.c

Purpose: Implements dirty-load recovery and read-only rebuild for VDO. It reads the whole recovery journal, locates valid journal extents, replays valid mappings into the block map, replays or rebuilds slab reference counts, recomputes usage counters, drains metadata, and reinitializes the recovery journal to a clean post-repair state.

Important APIs, types, and functions: exported APIs are `vdo_repair()` and `vdo_replay_into_slab_journals()`. `struct repair_completion` is the central state machine, embedding a VDO completion plus journal data buffers, read VIOs, journal head/tail positions, usage counters, sortable mapping entries, page completions, recovery points, slab replay progress, and rebuild traversal state. `struct numbered_block_mapping` preserves original journal order while allowing sorting by block-map page and slot. `struct recovery_point` identifies a journal entry by sequence, sector, and entry index and tracks whether the increment half has been applied to slab journals. Major helpers include `parse_journal()`, `find_recovery_journal_head_and_tail()`, `parse_journal_for_recovery()`, `parse_journal_for_rebuild()`, `extract_new_mappings()`, `compute_usages()`, `recover_block_map()`, `add_slab_journal_entries()`, `rebuild_reference_counts()`, and final drain/finish callbacks.

Control flow: `vdo_repair()` allocates a repair completion, a contiguous buffer for all journal blocks, read VIOs split by `MAX_BLOCKS_PER_VIO`, and page completions sized from cache capacity. It submits metadata reads for every journal block. When all reads finish, `finish_journal_load()` parses the journal and switches to logical-zone block-map recovery. Recovery mode finds the highest valid tail, walks from the minimum head through the first invalid/torn block or partial block, validates sectors, counts entries, extracts mappings, computes updated usage counters, sorts mappings through a min-heap, fetches each target block-map page once, applies entries in journal order per page, writes dirty pages, loads/replays slab journals, drains the block map and slab depot, then finishes. Read-only rebuild mode tolerates damaged entries by extracting what can be validated, replays block-map mappings, loads the slab depot in rebuild mode, traverses block-map tree pages and leaf pages to rebuild reference counts from current mappings, then drains metadata.

State and persistence behavior: journal parsing validates nonce, recovery count, metadata format, entry count, sequence number, physical ring position, per-sector check byte/recovery count/entry count, and entry bounds. Recovery mode treats a bad block header as the end of usable journal data and a bad sector as a torn block; mixed old/new journal formats force corrupt-journal read-only handling. Old-format journals are rejected in normal recovery with an upgrade instruction, while rebuild mode can transcribe old-format increment entries. `tail_recovery_point` marks the first position beyond usable entries, `entry_count` bounds allocation, and `highest_tail` records the newest valid block even if later holes make `tail` earlier. After completion, `finish_repair()` increments recovery counters when appropriate and calls `vdo_initialize_recovery_journal_post_repair()` with `highest_tail`, recomputed logical-block usage, and block-map data-block usage.

Dependencies and integration points: depends on recovery-journal structures and packed encodings, block-map page cache/traversal, slab depot load/drain/replay APIs, reference-count rebuild APIs, VDO admin state/load-state values, metadata VIO submission, min-heap utilities, wait queues, logger, and completion dispatch. `dm-vdo-target.c` invokes `vdo_repair()` for dirty or forced rebuild loads. `slab-depot.c` invokes `vdo_replay_into_slab_journals()` per allocator while loading the depot. The block-map page cache `rebuilding` flag suppresses block-map errors during rebuild.

Risks and invariants: repair correctness depends on not replaying stale blocks older than the superblock journal start, preserving journal order for duplicate block-map slots, and maintaining the increment-before-decrement rule when replaying slab journals. The min-heap flow sorts incrementally from the end of the entries array, which is subtle and relies on `number` as a tie-breaker. Recovery and rebuild intentionally differ in tolerance for damaged entries; changing validation can alter data-loss boundaries. The whole journal is read into memory, so journal size drives memory pressure. `free_repair_completion()` clears the block-map rebuilding flag on all cleanup paths, which is critical after errors. Usage counters are recomputed from the tail block header plus entries after the tail, so torn-tail handling directly affects accounting.

Test signals: cover clean recovery, torn sector, bad header hole, stale nonce/recovery-count blocks, mixed old/new format blocks, old-format upgrade rejection, forced read-only rebuild, invalid mapping locations, block-map page load errors, heap ordering for repeated slots, slab tailblock full/requeue behavior, reference-count rebuild from tree and leaf pages, out-of-bounds logical entries, metadata read failures, and cleanup after abort. Integration tests should verify post-repair journal start is one past `highest_tail`, block-map pages contain the last valid journal mapping for each slot, slab journal replay applies increment then decrement, and logical/refcount usage counters match rebuilt state.

# sources/distributed-fs/ceph-client/drivers/md/dm-vdo/repair.h

Purpose: Small public header for VDO repair/recovery entry points. It exposes the dirty-load repair driver and the per-allocator slab journal replay callback used while the slab depot is being loaded.

Important APIs, types, and functions: declares `vdo_repair(struct vdo_completion *parent)` and `vdo_replay_into_slab_journals(struct block_allocator *allocator, void *context)`. It includes `types.h` for forward declarations and VDO core type aliases. The header intentionally does not expose `struct repair_completion`; all repair state is private to `repair.c`.

Control flow contract: admin/load code calls `vdo_repair()` with a parent completion on the admin thread when a VDO is dirty, forced into rebuild, or rebuilding for upgrade. Slab depot load code calls `vdo_replay_into_slab_journals()` for each block allocator, passing the private repair context provided by `repair.c` during depot loading.

State and persistence behavior: no state is defined here, but both declarations participate in persistent recovery. `vdo_repair()` ultimately reads and interprets the recovery journal, updates block-map/slab metadata, and reinitializes the journal state. `vdo_replay_into_slab_journals()` replays journaled refcount effects into allocator-owned slab journals before repaired metadata is drained.

Dependencies and integration points: integrates `repair.c` with the VDO target/load path and slab depot. Callers must provide valid VDO completions, allocator completions, and the repair context established by the repair state machine.

Risks and test signals: because the context argument is opaque, misuse by slab depot callers would fail at runtime rather than compile time. Tests should verify both exported functions are invoked on their expected admin or physical-zone threads, propagate completion failures, and are not called after the repair completion has been freed.
