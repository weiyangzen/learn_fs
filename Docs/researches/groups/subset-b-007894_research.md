## sources/distributed-fs/tahoe-lafs/src/allmydata/mutable/layout.py

Purpose: Defines the packed on-storage layouts for Tahoe-LAFS mutable shares and provides read/write proxy classes that translate high-level mutable-file operations into storage-server read/write vectors. It supports both legacy SDMF shares and MDMF shares, including checkstrings, signed prefixes, offset tables, block data, block hash trees, share hash chains, signatures, verification keys, and encrypted private keys.

Important APIs and types: Top-level helpers `unpack_header`, `unpack_share`, `get_version_from_checkstring`, `unpack_sdmf_checkstring`, `unpack_mdmf_checkstring`, `pack_offsets`, `pack_share`, and `pack_prefix` encode and decode SDMF-compatible structures used by tests and by publish/servermap error handling. `SDMFSlotWriteProxy` implements `IMutableSlotWriter` by accumulating a whole SDMF share in memory and writing it once during `finish_publishing`. `MDMFSlotWriteProxy` implements the same writer interface with queued storage write vectors and an explicit offset table. `MDMFSlotReadProxy` is the shared read proxy for both SDMF and MDMF shares; it lazily fetches headers/offsets and exposes block, hash, key, signature, checkstring, prefix, encoding parameter, and version-info accessors. `LayoutInvalid` subclasses `BadShareError` for malformed layout or invalid write ordering.

Control flow: SDMF writing is simple and whole-share oriented: the caller sets block data, encrypted private key, block/share hashes, root hash, signature, and verification key; `get_signable` packs the signed prefix; `finish_publishing` asserts all pieces exist, constructs offsets, concatenates the final share, and calls `slot_testv_and_readv_and_writev` with a new-share test vector unless a caller provided an existing checkstring. MDMF writing is staged: initialization computes segment counts, block sizes, tail block size, fixed leading offsets, share-data location, and block-hash-tree location; `put_block` queues per-segment salt+block writes; `put_encprivkey`, `put_blockhashes`, `put_sharehashes`, `put_root_hash`, `put_signature`, and `put_verification_key` progressively fill offsets and enqueue writes; `finish_publishing` appends the offset table and encoding parameters, then `_write` sends the accumulated vectors with test vectors and first-write checkstring handling. Read flow starts with `_maybe_fetch_offsets_and_header`, which reads enough bytes to identify SDMF vs MDMF, parse encoding parameters, compute segment/tail sizes, and parse offsets. Later getters build precise read vectors from the cached offsets, first trying local cached data and falling back to `slot_readv`.

State and persistence: The module defines Tahoe's mutable share persistence format. SDMF offsets use fixed 32-bit and 64-bit fields after the signed prefix; MDMF uses a signable header followed by eight 64-bit offsets. Writer proxies hold transient state such as `_share_pieces`, `_offsets`, `_writevs`, `_testvs`, `_root_hash`, and `_written`; persistence happens only when storage-server slot write APIs accept the vectors. Reader proxies cache parsed header fields, offsets, version number, sequence number, root hash, salt for SDMF, encoding parameters, computed segment sizes, and optional prefetched data. Checkstrings are central concurrency state: SDMF checkstrings include version, sequence number, root hash, and salt; MDMF checkstrings include version, sequence number, and root hash.

Dependencies and integration points: The proxies are consumed by `publish.py`, `retrieve.py`, and `servermap.py`. They depend on Tahoe constants and interfaces from `allmydata.interfaces`, mutable exceptions from `allmydata.mutable.common`, `mathutil` for segment math, Twisted `Deferred`/`Failure`, and storage-server APIs `slot_testv_and_readv_and_writev` and `slot_readv`. Hash sizes and salt sizes must align with `hashutil`, `hashtree`, and the erasure codec used by publish/retrieve.

Risks: The format code is highly order-sensitive; using `MDMFSlotWriteProxy` methods out of sequence raises `LayoutInvalid` or can leave queued write vectors inconsistent. Several invariants rely on `assert`, so optimized Python would remove some validation. MDMF reserves fixed maximum sizes for private keys, signatures, verification keys, and share hash chains before it knows actual lengths; unusual key/signature sizes or share counts can challenge those assumptions. `_read` requires all requested vectors to be satisfiable from cached data before avoiding a remote read, which can underuse partial cache data. SDMF write assembly holds the full share in memory. Offset parsing converts `struct.error` into `BadShareError`, but malformed offset ordering or unexpectedly short data can still surface later through empty reads or downstream validation failures.

Test signals: Unit tests should cover SDMF and MDMF checkstring packing/unpacking, unknown version rejection, short-read `NeedMoreDataError`, malformed hash-chain/block-hash lengths, empty files, tail segments, and all read getters against cached and remote data. Writer tests should exercise new-share and existing-share test vectors, MDMF first-write checkstring update, invalid method order, segment bounds, salt/block size validation, offset table correctness, and storage-server failure responses. Integration tests should verify publish/servermap/retrieve agree on `verinfo` tuple contents for both SDMF and MDMF.

## sources/distributed-fs/tahoe-lafs/src/allmydata/mutable/publish.py

Purpose: Implements mutable-file publishing and in-place update logic. It takes an `IMutableUploadable`, encrypts and erasure-encodes the contents into mutable shares, assigns shares to storage servers based on a `ServerMap`, writes shares through layout writer proxies, detects uncoordinated writes through checkstrings, and records publish status/timings.

Important APIs and types: `PublishStatus` implements `IPublishStatus` and tracks timings, storage index, encoding, file size, status text, progress, active flag, and per-server problems. `Publish.publish(newdata)` performs initial or full-file publish. `Publish.update(data, offset, blockhashes, version)` updates existing MDMF shares in place using fetched boundary/update data. Supporting methods include `setup_encoding_parameters`, `_push`, `push_segment`, `_encode_segment`, `_push_segment`, `push_everything_else`, `push_encprivkey`, `push_blockhashes`, `push_sharehashes`, `push_toplevel_hashes_and_signature`, `finish_publishing`, `_got_write_answer`, `update_goal`, `_done`, and `_failure`. `MutableFileHandle`, `MutableData`, and `TransformingUploadable` implement `IMutableUploadable` wrappers for file-like data, bytes, and segmented partial-update merging.

Control flow: `publish` initializes write credentials, chooses a new sequence number from the servermap or `1` for first publish, loads read/write keys and RSA keys from the filenode, fetches the permuted server list, computes encoding parameters, builds the desired `(server, shnum)` goal from known and bad shares, adds homes for missing shares through `update_goal`, constructs SDMF or MDMF writer proxies, seeds existing-share checkstrings, initializes block-hash placeholders, and enters the `_push` state machine. `_push` alternates through `PUSHING_BLOCKS_STATE`, `PUSHING_EVERYTHING_ELSE_STATE`, and `DONE_STATE`, failing early if fewer than `k` share writers remain or an uncoordinated write was detected. Each segment is read, encrypted with a salt-derived readkey hash, FEC-encoded, hashed, and queued into every writer for the share. After all segments, publish writes the encrypted private key, per-share block hash trees, share hash chains, root hash, RSA signature over the signable prefix, verification key, offsets, and encoding parameters. `finish_publishing` sends each writer's storage write and `_got_write_answer` interprets test-vector results and surprise shares before updating the servermap and `placed` set.

State and persistence: Publish state is per-operation and includes the target `ServerMap`, `_new_seqnum`, `goal`, `writers`, `placed`, `bad_servers`, `bad_share_checkstrings`, `blockhashes`, `sharehash_leaves`, `sharehashes`, current segment bounds, FEC encoders, `_checkstring`, `surprised`, outstanding query count, and final `versioninfo`. Persistent changes are remote mutable slot updates via `MDMFSlotWriteProxy` or `SDMFSlotWriteProxy`; local filenode state is also updated with downloader hints after success. The concurrency guard is persistent at storage-server slots through checkstrings/test vectors, not through local locks.

Dependencies and integration points: Depends on AES and RSA helpers, Tahoe hash utilities, `hashtree`, erasure `codec`, `DictOfSets`, Twisted Deferreds, `defer_to_thread` for CPU-heavy crypto/hash work, storage broker server ordering, filenode key/secret APIs, `ServerMap`, layout writer proxies, and mutable common exceptions (`UncoordinatedWriteError`, `NotEnoughServersError`). It emits Tahoe log messages and Eliot messages from `update_goal`, and returns status objects consumed by history/status UI layers.

Risks: Publish correctness depends on an up-to-date `ServerMap`; stale or incomplete maps lead to surprise-share detection and `UncoordinatedWriteError`. `update_goal` can place multiple shares on one server when capacity is low, which is tolerated but weakens distribution. Write failures and test-vector failures are not fully distinguishable, so the code marks the server bad and treats the condition as a coordination conflict. `_failure` callbacks the deferred with a `Failure` object instead of errbacking, so callers must match existing Tahoe expectations. The state machine mutates shared operation fields across Deferred callbacks; reusing a `Publish` instance would be unsafe. Partial-update support assumes caller-supplied blockhashes and boundary segments correspond to the version being updated and has comments about unresolved tail-size behavior.

Test signals: Tests should exercise first publish, full republish, MDMF partial update, empty SDMF salt handling, segment/tail-size calculations, FEC block padding, root/signature generation, server assignment when shares are missing, bad-share replacement, grid-manager upload-permission filtering, server exhaustion, writer connection failures, failed test vectors, surprise shares with matching and mismatching checkstrings, and servermap mutation after successful writes. Uploadable tests should cover `MutableFileHandle` size/position behavior and `TransformingUploadable.read` for prefix-only, suffix-only, and boundary-spanning replacements.

## sources/distributed-fs/tahoe-lafs/src/allmydata/mutable/repairer.py

Purpose: Provides high-level mutable-file repair orchestration. It refreshes a full repair-mode servermap, chooses the best recoverable version, refuses potentially data-losing repairs unless forced, downloads recoverable contents and private key material, then republishes the data so missing, stale, or bad shares are replaced.

Important APIs and types: `RepairResults` implements `IRepairResults` with `set_successful`, `get_successful`, and `to_string`. `RepairRequiresWritecapError` signals that repair cannot proceed without write authority. `MustForceRepairError` signals merge or unrecoverable-newer-version conditions that require explicit `force=True`. `Repairer.start(force=False)` launches the process; `_got_full_servermap` performs policy decisions and upload chaining; `get_results` wraps a successful upload result.

Control flow: `start` creates a fresh `ServerMap` and `ServermapUpdater` in `MODE_REPAIR`, optionally reports updater status to history, and waits for update completion. `_got_full_servermap` asks the resulting map for `best_recoverable_version`. If none exists, it returns unsuccessful `RepairResults`. If newer unrecoverable versions exist or multiple recoverable heads need merge, it raises `MustForceRepairError` unless `force=True`, because repair would discard information by reinforcing one version. It then requires a writekey, downloads the selected version with `fetch_privkey=True`, wraps the bytes in `MutableData`, calls `node.upload` with the repair servermap, and returns successful `RepairResults`.

State and persistence: The repairer itself holds the node, coerced check results, storage broker, history, and monitor. Persistent repair effects happen through `node.upload`, which uses the servermap's known shares and bad-share records to overwrite old/bogus shares and place missing shares. The repair path also intentionally fetches and populates private-key material during download so the subsequent publish can sign a new mutable version.

Dependencies and integration points: Integrates `ServermapUpdater`/`ServerMap` discovery, retrieve via `node.download_version`, publish via `node.upload`, and `MutableData` upload wrapping. It relies on `ServerMap.best_recoverable_version`, `unrecoverable_newer_versions`, `needs_merge`, and `bad_shares` semantics established by servermap/retrieve verification. Results conform to Tahoe `IRepairResults`, and input check results are coerced to `ICheckResults`.

Risks: Repair is intentionally conservative but `force=True` can lose data by skipping unrecoverable newer seqnums or choosing one recoverable concurrent head. Repair currently requires a writecap even for share redistribution because it needs write-enablers and signing keys. The `RepairResults.to_string` implementation is empty, limiting diagnostics. The original `check_results` are only used for storage-index validation; repair always performs a new MODE_REPAIR scan, so callers expecting reuse of check detail may be surprised.

Test signals: Tests should cover no recoverable version, normal repair of missing/old/bad shares, writecap absence, unrecoverable newer version with and without force, merge-needed condition with and without force, history status notification, download with private-key fetch, upload invocation with the refreshed servermap, and unsuccessful vs successful `RepairResults`.

## sources/distributed-fs/tahoe-lafs/src/allmydata/mutable/retrieve.py

Purpose: Implements mutable-file download and verification. It uses a validated `ServerMap` version to select shares, fetches blocks and hash proofs through layout read proxies, validates block and share hash trees, decodes erasure-coded ciphertext, decrypts plaintext segments, streams data to a Twisted consumer, and optionally verifies all shares or retrieves private-key material for repair.

Important APIs and types: `RetrieveStatus` implements `IRetrieveStatus` and records storage index, encoding, size, status, progress, active flag, per-server fetch timings, crypto/decoder timings, and problems. `Retrieve` implements `IPushProducer` with `pauseProducing`, `resumeProducing`, and `stopProducing`. Main methods include `download`, `_start_download`, `loop`, `_setup_download`, `_setup_encoding_parameters`, `_activate_enough_servers`, `_download_current_segment`, `_process_segment`, `_validate_block`, `_get_needed_hashes`, `_decode_blocks`, `_decrypt_segment`, `_set_segment`, `_handle_bad_share`, `_mark_bad_share`, `_try_to_validate_privkey`, `_done`, and `_raise_notenoughshareserror`. `decode` is a shortcut used by mutable update logic to decode supplied block/salt data without a full streaming download.

Control flow: `download` registers as a streaming producer with the consumer, handles zero-length files immediately, and starts a loop. Setup derives k/N, version, segment/tail sizes, decoder instances, and requested start/end segments from `verinfo`, offset, and size. `_setup_download` builds a remaining sharemap for the chosen version, reuses cached `MDMFSlotReadProxy` objects from the servermap when possible, initializes per-share incomplete block hash trees, and seeds the file-level share hash tree with the known root hash. Each loop activates enough readers, asks each active reader for the current block/salt plus needed block/share hashes, validates each share, and either verifies-only or decodes/decrypts the segment. Successful plaintext is trimmed for requested offset/size and written to the consumer; failures mark shares bad, notify storage servers of corrupt data, remove readers, and allow the loop to select replacements.

State and persistence: Retrieve maintains operation state including the target `verinfo`, `_data_length`, `_need_privkey`, `_verify`, selected readers, remaining sharemap, active readers, per-share block hash trees, share hash tree, current/start/last segment, requested offset/length, pause/stopped flags, bad shares, last failure, and status timings. It does not persist file data locally; it streams to the supplied consumer. It mutates the shared servermap by marking bad shares and may populate the filenode's encoding parameters, encrypted private key, and private key after successful validation.

Dependencies and integration points: Depends on Twisted producer/consumer APIs and Deferreds, Foolscap remote failure classes, AES/RSA/hash helpers, erasure `codec.CRSDecoder`, Tahoe `hashtree`, layout `MDMFSlotReadProxy`, storage-server corruption notification, `DictOfSets`, `defer_to_thread`, and mutable exceptions (`BadShareError`, `CorruptShareError`, `UncoordinatedWriteError`, `DownloadStopped`). It is used by filenode download paths, mutable update preparation, verification/checking flows, and repair private-key recovery.

Risks: The retrieve object is documented as single-use; shared mutable fields make concurrent downloads unsafe. Reader selection favors lower share numbers and only activates replacements after failures, which may not be latency optimal. `_activate_enough_servers` fires private-key fetch Deferreds without flow-control/error aggregation. Verification mode skips plaintext use but still relies on segment processing paths; if all active readers are exhausted it stops rather than forcing decode. Corruption reporting is best-effort. Pausing uses a single deferred gate and must coordinate with stop handling to avoid writing after a consumer has stopped. Any mismatch between servermap prefix and fetched data is treated as an uncoordinated write.

Test signals: Tests should cover full and ranged downloads, zero-length files, SDMF and MDMF salt/hash validation, tail segment trimming, consumer pause/resume/stop behavior, insufficient shares, replacement of bad or disconnected readers, corrupt block hash tree, corrupt share hash chain, prefix mismatch, verify-only mode returning bad shares, private-key validation success/failure, cached reader reuse from servermap, and the `decode` shortcut used for partial updates.

## sources/distributed-fs/tahoe-lafs/src/allmydata/mutable/servermap.py

Purpose: Maintains and updates the map of mutable shares across storage servers. The map records which server holds which share of which mutable version, distinguishes recoverable and unrecoverable versions, tracks bad shares and server reachability, caches layout read proxies, and drives query policies for read, write, check, and repair modes.

Important APIs and types: `UpdateStatus` implements `IServermapUpdaterStatus` and records mode, storage index, status/progress, finish time, per-server timings, private-key source, and problems. `ServerMap` provides mutation and query APIs such as `mark_server_reachable`, `mark_server_unreachable`, `mark_bad_share`, `add_new_share`, `get_known_shares`, `make_sharemap`, `make_versionmap`, `shares_available`, `highest_seqnum`, `recoverable_versions`, `unrecoverable_versions`, `best_recoverable_version`, `unrecoverable_newer_versions`, `needs_merge`, `version_on_server`, and update-data getters/setters. `ServermapUpdater` is the active scanner with `update`, `_build_initial_querylist`, `_send_initial_requests`, `_do_query`, `_do_read`, `_got_results`, `_got_signature_one_share`, `_check_for_done`, `_send_more_queries`, `_done`, and error/corruption/private-key helper methods.

Control flow: A `ServermapUpdater` starts with a filenode, storage broker, monitor, existing servermap, mode, lease flag, and optional update range. `update` chooses a query strategy: check/repair query all servers; write queries enough servers to discover all existing shares plus an epsilon boundary of empty servers; read/anything starts with existing servers plus a k+epsilon sample. `_do_query` asks each storage server for an initial read vector, optionally adds a lease in parallel, and routes responses to `_got_results`. For each returned share, `_got_results` builds an `MDMFSlotReadProxy` over the prefetched bytes, fetches or validates the public key, obtains verinfo and signature, optionally fetches/validates the encrypted private key, optionally fetches blockhash and boundary segment data for update, caches the proxy, validates the signature once per version, and adds valid shares to the servermap. `_check_for_done` is the state machine that decides whether enough evidence has been gathered for the current mode or whether more servers should be queried.

State and persistence: `ServerMap` is an in-memory authority passed between map update, retrieve, publish, and repair operations. `_known_shares` maps `(server, shnum)` to `(verinfo, timestamp)`, `_bad_shares` maps bad `(server, shnum)` to old checkstrings for repair test vectors, reachability sets track query outcomes, `proxies` caches read proxies keyed by version/server/storage index/share, and `update_data` stores block hash trees plus boundary segment data for partial updates. The updater mutates these fields and finalizes `_last_update_mode`/time on completion. Persistent effects are limited to optional lease addition and best-effort corrupt-share notifications to storage servers; the share map itself is local operation state.

Dependencies and integration points: The servermap layer depends on storage broker permutation via `get_servers_for_psi`, storage-server `slot_readv` and `add_lease`, layout `MDMFSlotReadProxy`, RSA signature verification, Tahoe hash utilities, `DictOfSets`, Foolscap remote failure types, mutable mode constants, private-key decryption, and corruption exceptions. It feeds `Publish` with known/bad shares and update data, feeds `Retrieve` with version/share placement and cached readers, and feeds `Repairer` with recoverability and merge/loss policy signals.

Risks: Completion policies are heuristic outside check/repair modes; read mode may stop after k+epsilon evidence when no newer unrecoverable version is visible, while write mode searches for an epsilon empty-server boundary rather than exhaustively querying. Query state is complex (`_must_query`, outstanding queries, extra servers, empty/good/bad/server-with-shares sets), so missed state transitions can hang or finish early. A corrupt share marks the whole server bad for counting in the updater, even if other shares might be valid. `_make_verinfo_hashable` serializes offset dictionaries using current item order; equality should remain stable for dicts built consistently, but order-sensitive tuples are a subtle contract. Private-key validation is synchronous CPU/crypto work in the callback path. The map is mutable and copied shallowly for some fields, so callers must avoid concurrent mutation after an updater finishes.

Test signals: Tests should cover `ServerMap` recoverability calculations, highest sequence selection, merge detection, unrecoverable-newer-version detection, bad-share removal, copy behavior, update-data storage, and version summaries. Updater tests should cover all modes (`MODE_READ`, `MODE_WRITE`, `MODE_CHECK`, `MODE_REPAIR`, `MODE_ANYTHING`), initial query-list construction, must-query behavior, no-server short circuit, additional query scheduling, lease failure tolerance, pubkey fingerprint mismatch, bad signature/corrupt share reporting, privkey validation, cached proxy insertion, update-range data fetching, read-mode newer-unrecoverable search, write-mode boundary detection, and fatal error propagation.
