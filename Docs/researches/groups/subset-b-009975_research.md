# sources/user-network-fs/samba/source4/torture/ndr/dfs.c

Purpose: this file defines the Samba torture NDR suite for the DFS RPC interface. It is a small fixture-driven parser regression test that feeds captured wire-format DFS operation bodies into generated `ndr_dfs` pull routines and verifies selected decoded fields for `dfs_GetManagerVersion` and `dfs_EnumEx` level 300.

Important APIs, types, and functions: the exported entry point is `ndr_dfs_suite(TALLOC_CTX *ctx)`, which creates a `struct torture_suite` named `dfs`. The suite uses `torture_suite_add_ndr_pull_fn_test()` from the torture NDR harness, generated RPC types from `librpc/gen_ndr/ndr_dfs.h`, and callback validators typed as `struct dfs_GetManagerVersion *` and `struct dfs_EnumEx *`. `getmanagerversion_out_check()` asserts that `*r->out.version` is `4`. `enumex_in_check300()` validates an inbound `EnumEx` request: DFS name `w2k3dc`, level `300`, non-NULL `total` and `info` pointers, `*total == 0`, `bufsize == -1`, `info->level == 300`, and a NULL level-300 array pointer. `enumex_out_check300()` validates a response with `WERR_OK`, total count `3`, level `300`, and three decoded DFS roots with flavors `256`, `256`, and `512`.

Control flow: execution is entirely registration-time plus harness-driven parsing. Static byte arrays hold one `GetManagerVersion` output fixture, one `EnumEx` input fixture, and one `EnumEx` output fixture. `ndr_dfs_suite()` registers those arrays with NDR direction flags (`NDR_OUT` for manager version, `NDR_IN` and `NDR_OUT` for `EnumEx`). At runtime, the NDR torture helper unmarshals each byte buffer into the generated structure and calls the optional checker. The checkers are straight-line assertion code and return `true` only after all selected fields match.

State and persistence behavior: there is no persistent state, network connection, filesystem operation, or mutable global data. All data is static fixture input and stack/local decoded state created by the harness under the supplied talloc context. The only observable effects are torture assertion results.

Dependencies and integration points: this file integrates with Samba's `source4/torture/ndr` suite registry through `torture/ndr/proto.h`. It depends on the generated DFS NDR bindings matching the fixture layout, especially pointer referent handling, UTF-16 string decoding, signed integer decoding for `bufsize == -1`, union arm selection for level 300, and WERROR decoding. It indirectly protects consumers of the DFS RPC client/server stubs by detecting generated-code or IDL changes that break compatibility with captured Windows-style DFS payloads.

Risks: coverage is narrow and only checks representative fields. The `EnumEx` output fixture is sensitive to conformant/varying string handling, array counts, pointer layout, and level-specific union tags, but it does not assert every decoded scalar in the response. A generated IDL change could still pass if it preserves the asserted fields while corrupting unasserted fields. The input checker requires `info300->s == NULL`, so changes to empty-array normalization could break the test even if higher-level behavior remains compatible.

Test signals: failures indicate NDR regressions in DFS operation decoding. Strong signals include a NULL output version pointer, manager version not decoded as `4`, DFS name or level corruption in `EnumEx`, incorrect `total`/`bufsize` handling, response result not `WERR_OK`, wrong entry count, malformed UTF-16 DFS root strings, or incorrect flavor values for standalone versus domain DFS roots.

# sources/user-network-fs/samba/source4/torture/ndr/dfsblob.c

Purpose: this file defines the Samba torture NDR suite for standalone DFS referral blobs. It tests decoding of a DFS referral request and two referral response fixtures, and it also performs a targeted push-back check for referral response termination behavior.

Important APIs, types, and functions: the exported entry point is `ndr_dfsblob_suite(TALLOC_CTX *ctx)`. It uses generated DFS blob bindings from `librpc/gen_ndr/ndr_dfsblobs.h` plus public DFS blob structures from `librpc/gen_ndr/dfsblobs.h`. The fixture types under test are `dfs_GetDFSReferral_in` and `dfs_referral_resp`. `dfs_referral_out_check(struct torture_context *tctx, struct dfs_referral_resp *r)` validates that the first decoded referral's v3/r2 `special_name` is `\\msw2k3.tst`, then calls `ndr_push_struct_blob()` with `ndr_push_dfs_referral_resp` and checks that the last two bytes in the re-encoded blob are zero.

Control flow: static byte arrays represent one referral input and two referral responses. `ndr_dfsblob_suite()` registers the input fixture with `torture_suite_add_ndr_pull_test()` and no checker, registers `dfs_get_ref_out2` as a response decode-only fixture, and registers `dfs_get_ref_out` with `dfs_referral_out_check()`. The checker combines normal pull validation with a push validation: decode the fixture, inspect a high-value nested string, re-encode the decoded structure, and verify the expanded-name tail is null terminated.

State and persistence behavior: the file has no external persistence. It declares a global `DATA_BLOB blob`, which is assigned in the checker when re-pushing the decoded referral response. That global is only test scratch state; its allocation parent is the current torture context. No SMB server, DFS namespace, or filesystem is contacted.

Dependencies and integration points: this test sits in the NDR torture family and exercises generated DFS referral blob parsers and pushers. It depends on generated union selection for referral version 3, nested referral layout for the `r2` form, UTF-16 string conversion, offset handling inside packed referral buffers, and `ndr_push_struct_blob()` preserving the expected wire-compatible string terminator. It is an integration point between the IDL definitions, generated NDR code, and DFS referral marshalling used by SMB DFS client/server code.

Risks: the final two-byte terminator assertion indexes `blob.data[blob.length - 2]` and `blob.data[blob.length - 1]`, so it assumes push succeeds and produces at least two bytes; the code does not explicitly assert push status or length before indexing. The global `blob` is harmless in normal serial torture execution but is not a clean per-test local. Coverage is limited to these captured layouts and does not deeply validate every referral field in `dfs_get_ref_out2`.

Test signals: failures point to DFS referral blob compatibility regressions. The most meaningful signals are inability to pull the request/response blobs, incorrect nested `special_name` decoding, re-pushed responses lacking a UTF-16 null terminator, or generated DFS blob changes that alter offsets/string expansion enough to break round-trip validation.

# sources/user-network-fs/samba/source4/torture/ndr/dnsp.c

Purpose: this file defines NDR torture coverage for Active Directory DNS property blobs (`dnsp_DnsProperty`). It verifies selected `dnsPropertyData` union arms decoded from base64 fixtures and includes a negative regression test for a truncated/zero-length data field that previously read beyond the end of the buffer.

Important APIs, types, and functions: the exported entry point is `ndr_dnsp_suite(TALLOC_CTX *ctx)`. The suite uses generated `ndr_dnsp.h`, `torture_suite_add_ndr_pull_validate_test_b64()`, `torture_suite_add_ndr_pull_invalid_data_test()`, and base64 fixture support from `lib/util/base64.h`. `dnsp_dnsProperty_ip4_array_check()` validates `DSPROPERTY_ZONE_MASTER_SERVERS`: `wDataLength == 12`, version `1`, address count `2`, raw address integers `0x21631fac` and `0x2c631fac`, and `name == 0`. The comment records that these are logically IPv4 addresses `172.31.99.33` and `172.31.99.44`, but the current IDL models them as big-endian-related `uint32` values.

`dnsp_dnsProperty_addr_array_check()` validates `DSPROPERTY_ZONE_MASTER_SERVERS_DA`, including array header fields (`MaxCount`, `AddrCount`, `Tag`, `Family`, flags, reserved fields) and three `dnsp_dns_addr` entries. It checks two IPv4 entries on port 53 with zero IPv6/padding and one IPv6 entry with family `23`, port `53`, IPv4 `0.0.0.0`, IPv6 `fd3a:aaa3:ee87:ff09:0200:00ff:fe99:ffff`, and expected `unused` values. `dnsp_dnsProperty_deleted_by_check()` validates `DSPROPERTY_ZONE_DELETED_FROM_HOSTNAME` with hostname `w2k3-191.w2k3.base` while intentionally accepting random/uninitialized `namelength` and `name` values observed from Windows 2003.

Control flow: the file stores three positive base64 fixtures and one invalid raw byte array. `ndr_dnsp_suite()` registers the master-server IPv4 array, the DNS address array, and the deleted-from-hostname property as positive pull-validate tests with callbacks. It then registers `dnsp_dnsProperty_deleted_by_zero_wDataLength` as an invalid-data test expecting `NDR_ERR_BUFSIZE`. The checkers are straight-line structural assertions over the decoded union arm selected by `r->id`.

State and persistence behavior: there is no persistent state and no mutation outside the decoded fixture objects. The test data is static; base64 decoding is handled by the NDR torture helper. All allocations live under the suite or test talloc contexts.

Dependencies and integration points: this file protects the generated DNSP IDL and NDR code used to parse DNS-related AD attributes. It is sensitive to union arm dispatch by property ID, string conversion for UTF-16 hostname data, address-family-specific decoding, byte order for IPv4 values, and buffer-size validation in variable-length union data. The negative test directly integrates with Samba's NDR error reporting contract by requiring `NDR_ERR_BUFSIZE`.

Risks: these tests intentionally encode historical quirks. `namelength` and `name` are asserted to random-looking values because the specification says they must be ignored; a cleanup that zeroes ignored fields during parse could fail this test despite being semantically tempting. Conversely, the master-server IPv4 fixture documents a modeling issue where an IPv4 address should arguably not be plain `uint32`, so future IDL fixes need coordinated test updates. The negative fixture is important because a permissive parser could reintroduce out-of-bounds reads if it trusts `id` over `wDataLength`.

Test signals: positive-test failures indicate incorrect DNSP union selection, address array sizing, IPv4/IPv6 formatting, port/family decoding, ignored-field preservation, or UTF-16 hostname decoding. The invalid-data failure is a memory-safety signal: the parser must reject a property with `wDataLength == 0` and a retained hostname property ID rather than referencing data beyond the buffer.

# sources/user-network-fs/samba/source4/torture/ndr/drsblobs.c

Purpose: this file defines the Samba torture NDR suite for DRS-related directory service blobs: forest trust information, trust-domain password/authentication blobs, and supplemental credentials captured from several Samba and Windows releases. It is primarily compatibility regression coverage for complex, historically fragile AD replication/security blob layouts.

Important APIs, types, and functions: the exported entry point is `ndr_drsblobs_suite(TALLOC_CTX *ctx)`. It uses generated `ndr_drsblobs.h`, base64 decoding, and the NDR torture helpers for raw byte arrays and decoded `DATA_BLOB`s. `forest_trust_info_check_out()` validates a two-record `ForestTrustInfo`: version `1`, count `2`, a top-level name `f2.test`, and a domain-info record with SID `S-1-5-21-677661288-1956808876-2402106903`, DNS name `f2.test`, and NetBIOS name `F2`. `forest_trust_info_check_out2()` validates a five-record forest trust fixture, including normal top-level/domain records, disabled TLN records (`LSA_TLN_DISABLED_NEW`), and `FOREST_TRUST_SCANNER_INFO`.

`trust_domain_passwords_check_in()` validates a `trustDomainPasswords` fixture. It asserts outgoing and incoming counts, current/previous offsets, current array metadata, `TRUST_AUTH_TYPE_CLEAR`, clear password sizes, password byte equality against offsets inside the original fixture, zero previous counts, and final outgoing/incoming sizes. Supplemental credential checkers cover empty forms and real package sets: `supplementalCredentials_empty1_check()`, `supplementalCredentials_empty2_check()`, `alpha13_supplementalCredentials_check()`, `release_4_1_0rc3_supplementalCredentials_check()`, `release_4_5_0pre_GPG_supplementalCredentials_check()`, and `win2012R2_supplementalCredentials_check()`.

Control flow: `ndr_drsblobs_suite()` creates a parent suite named `drsblobs` and child suites for empty, alpha13, release 4.1.0rc3, release 4.5.0pre-GPG, and Windows 2012 R2 supplemental credential cases. It registers forest trust fixtures, trust-domain password fixtures, incoming/outgoing trust auth blobs, and supplemental credential fixtures. Most real-world supplemental credentials are stored as base64 strings, decoded with `base64_decode_data_blob_talloc()`, then registered with `torture_suite_add_ndr_pull_validate_test_blob()`. For the Windows 2012 R2 fixture, the suite explicitly forces the final byte to zero before registering it because that byte is typically uninitialized and Samba requires stable pull/push behavior.

State and persistence behavior: there is no external persistence. The only mutation is local normalization of the decoded Windows 2012 R2 supplemental credential blob's final byte. Suite-local `DATA_BLOB`s and decoded structures are allocated under talloc contexts and discarded after test execution. No directory, network, key database, or filesystem state is modified.

Dependencies and integration points: this file sits at the boundary between DRS IDL definitions and authentication/trust consumers that depend on those blobs. It tests SID decoding (`dom_sid_parse_talloc()` comparisons), forest trust record union arms, timestamp and size fields, trust-auth array offsets, supplemental credential prefixes/signatures (`SUPPLEMENTAL_CREDENTIALS_PREFIX`, `SUPPLEMENTAL_CREDENTIALS_SIGNATURE`), and package-name extraction for Kerberos, WDigest, Packages, and SambaGPG. It also exercises pull/push validation, not only loose pull parsing, for many fixtures.

Risks: the fixtures deliberately encode old Samba and Windows layouts, including uninitialized bytes and release-specific package ordering. Normalizing or sanitizing decoded structures may break these tests even when higher-level consumers ignore those fields. The trust-domain password checker uses hard-coded offsets into the original fixture for password comparison, so layout changes in the IDL must be intentional and accompanied by fixture updates. Some trust auth blob tests have no callback, so they mainly prove parser/pusher acceptance rather than semantic correctness.

Test signals: failures indicate regressions in forest trust record sizing, timestamp endianness, SID parsing, TLN-disabled flags, scanner-info union selection, trust-password offset interpretation, clear-password extraction, supplemental credential prefix/signature parsing, package counting/order, or handling of historically uninitialized trailing data. The strongest safety signal is that captured credentials from multiple eras still parse and push consistently.

# sources/user-network-fs/samba/source4/torture/ndr/drsuapi.c

Purpose: this file defines fixture-based NDR torture tests for selected DRSUAPI RPC operations. It validates that generated `drsuapi` pull routines can parse captured `DsAddEntry` request/response payloads and `DsBind` response payloads.

Important APIs, types, and functions: the exported entry point is `ndr_drsuapi_suite(TALLOC_CTX *ctx)`. It depends on generated bindings from `librpc/gen_ndr/ndr_drsuapi.h` and registers tests with `torture_suite_add_ndr_pull_fn_test()`. The active fixtures are `DsAddEntry_req1_dat`, `DsAddEntry_resp1_dat`, `DsBind_resp1_dat`, and `DsBind_resp2_dat`. There are also commented-out `DsBind_req1_dat` and `DsBind_req2_dat` fixtures, indicating captured request-side material exists but is not currently active in the suite.

Control flow: `ndr_drsuapi_suite()` creates a `drsuapi` suite, registers the `drsuapi_DsAddEntry` request fixture with `NDR_IN`, registers the `DsAddEntry` response fixture with `NDR_OUT`, registers two `drsuapi_DsBind` response fixtures with `NDR_OUT`, and returns the suite. No callback validators are provided, so the test outcome is based on successful unmarshalling according to the generated NDR routines and the torture helper's standard pull checks.

State and persistence behavior: this file is entirely static fixture data plus test registration. It does not connect to a domain controller, mutate AD state, create objects, or persist local state. The large `DsAddEntry` request fixture contains encoded distinguished names, attributes, security descriptors/SIDs, and other directory-replication fields, but they are only parsed in-memory.

Dependencies and integration points: these tests protect the generated DRSUAPI IDL for two important replication-management calls. The `DsAddEntry` fixture stresses nested directory object names, attribute arrays, security descriptors, GUIDs, SIDs, and variable-length strings. The `DsBind` response fixtures stress bind info, extension flags, GUID fields, and response-side pointer/array decoding. They integrate with the generic NDR torture harness rather than live RPC transport.

Risks: because all active registrations pass `NULL` validators, this suite detects hard parse failures and pull/push incompatibilities but does not assert specific semantic fields. A generated parser could decode to structurally valid but semantically wrong values and still pass if the NDR helper does not compare a re-pushed byte stream in a way that exposes the error. The commented request fixtures also mean request-side `DsBind` coverage is currently disabled. The large static byte arrays are hard to audit manually, so maintainers should rely on precise fixture provenance and avoid casual edits.

Test signals: failures are high-level compatibility signals for DRSUAPI NDR parsing. They suggest changes in generated IDL, pointer layout, conformant array handling, security descriptor decoding, GUID/string decoding, or extension structure layout. Lack of failures should be read narrowly: active tests prove the fixtures are accepted by the generated pull routines, not that all decoded fields are semantically verified.

# sources/user-network-fs/samba/source4/torture/ndr/epmap.c

Purpose: this file defines a small Samba torture NDR suite for the DCE/RPC endpoint mapper `epm_Map` operation. It verifies that a captured map request decodes enough of the tower/request structure to expose the expected maximum tower count and map tower length.

Important APIs, types, and functions: the exported entry point is `ndr_epmap_suite(TALLOC_CTX *ctx)`. The test depends on generated endpoint mapper bindings from `librpc/gen_ndr/ndr_epmapper.h`. `map_in_check(struct torture_context *tctx, struct epm_Map *r)` asserts `r->in.max_towers == 1`, `r->in.map_tower != NULL`, and `r->in.map_tower->tower_length == 75`. A response fixture and `map_out_check()` exist inside `#if 0`, documenting expected output-side fields such as `*num_towers == 1` and result `0x4b`, but they are not compiled or registered.

Control flow: `map_in_data` holds a captured inbound `epm_Map` payload containing object/handle space, a protocol tower, and a max-towers value. `ndr_epmap_suite()` creates an `epmap` suite and registers a single `NDR_IN` pull-function test for `epm_Map` with `map_in_check()`. The disabled output test is left as source commentary but has no runtime effect.

State and persistence behavior: there is no mutable state or persistence. The suite parses a static byte array under the torture harness and produces only assertion results.

Dependencies and integration points: this test exercises endpoint mapper IDL generated code, especially decoding of embedded tower structures and request-side pointer fields. Endpoint mapper towers are used by DCE/RPC binding discovery, so this fixture is a compact regression check for tower-length and array/pointer handling in generated NDR code.

Risks: coverage is intentionally minimal. The checker contains FIXME comments for object and entry-handle validation, so important fields are parsed but not asserted. The disabled response fixture means output-side `epm_Map` coverage is absent at runtime. Future IDL changes could preserve tower length and max-towers while breaking tower floor contents, object UUIDs, or entry handle decoding without this test catching it.

Test signals: active failures indicate inability to decode the inbound `epm_Map` request, NULL tower decoding, incorrect max-tower count, or incorrect tower length. Passing this test is a narrow signal that request-side endpoint mapper tower framing still matches the fixture.

# sources/user-network-fs/samba/source4/torture/ndr/krb5pac.c

Purpose: this file defines Samba torture NDR coverage for Kerberos PAC structures. It parses captured PAC buffers from Windows domains, validates selected UPN/DNS and PKINIT credential fields, decrypts a PKINIT PAC credential payload with a known reply key, and tests nested credential NDR/NTLM supplemental package decoding.

Important APIs, types, and functions: the exported entry point is `ndr_krb5pac_suite(TALLOC_CTX *ctx)`. The suite uses generated `ndr_krb5pac.h`, `torture_suite_add_ndr_pull_validate_test()`, `torture_suite_add_ndr_pull_test()`, and Kerberos helpers from `lib/krb5_wrap/krb5_samba.h`. `PAC_DATA_check()` and `PAC_DATA_check2()` walk decoded `PAC_DATA` buffers and validate `PAC_TYPE_UPN_DNS_INFO` for Administrator accounts in `W2K8DOM.BER.REDHAT.COM` and `W2K12DOM.BER.REDHAT.COM`. They assert `num_buffers == 5`, UPN string sizes, UPN strings, DNS domain string sizes, and DNS domain strings.

The PKINIT validator `PAC_DATA_pkinit()` is the most involved checker. It asserts PAC version `0`, six buffers, buffer types and `_ndr_size` values for logon info, credential info, logon name, UPN/DNS info, server checksum, and KDC checksum. It validates credential info version `0`, encryption type `ENCTYPE_AES256_CTS_HMAC_SHA1_96`, and encrypted-data equality against an offset in `PAC_DATA_pkinit_AS`. It builds a known AES256 reply key from hex, initializes a Kerberos context/keyblock, decrypts the credential info with `krb5_c_decrypt(..., KRB5_KU_OTHER_ENCRYPTED, ...)`, checks the plaintext length, and compares the plaintext to `PAC_DATA_pkinit_PAC_CREDENTIAL_DATA_NDR`. It then validates logon name `pkinit1`, logon time `130966349430000000`, UPN `pkinit1@w4edom-l4.base`, DNS domain `W4EDOM-L4.BASE`, and checksum types/signature lengths.

`PAC_CREDENTIAL_DATA_NDR_check()` validates a nested credential-data NDR blob containing one `NTLM` package and checks the credential bytes match `PAC_DATA_pkinit_PAC_CREDENTIAL_NTLM_SECPKG`. `PAC_CREDENTIAL_NTLM_SECPKG_check()` validates version `0`, `PAC_CREDENTIAL_NTLM_HAS_NT_HASH`, and LM/NT hash byte slices from the fixture.

Control flow: the suite registers raw and typed PAC tests for three general PAC fixtures plus PKINIT fixtures. For the first two PACs, raw validation is registered separately, while typed `PAC_DATA` uses `torture_suite_add_ndr_pull_test()` with custom callbacks because comments state validate-test cannot be used where unique pointer values inside `PAC_LOGON_INFO` do not match for extra SID cases. The third fixture uses validate tests for both `PAC_DATA_RAW` and `PAC_DATA`. PKINIT AS data is validated as raw and typed with `PAC_DATA_pkinit()`. PKINIT TGS data is validated as raw, but the following typed registration uses `PAC_DATA_pkinit_AS` again with `PAC_DATA_pkinit()`, which looks intentional or historical in code but means typed TGS-specific coverage is not actually distinct. Finally, credential-data and NTLM package fixtures are registered as their own decoded types.

State and persistence behavior: there is no filesystem, network, KDC, or account persistence. The only nontrivial runtime state is transient Kerberos crypto state allocated inside `PAC_DATA_pkinit()`: a `krb5_context`, keyblock, encrypted input wrapper, malloc-backed plaintext buffer, and talloc `DATA_BLOB`. The function frees Kerberos data/key/context after decryption. Test fixtures are static byte arrays.

Dependencies and integration points: this file is a dense integration point between generated PAC NDR code, PAC buffer offset/size handling, Kerberos crypto wrappers, checksum/enctype constants, Unicode string decoding, SID/logon info parsing, and credential package structures. It tests both `PAC_DATA_RAW` and interpreted `PAC_DATA`, plus nested credential types that consumers use after decrypting PKINIT credential info.

Risks: crypto validation depends on Kerberos library behavior and the Heimdal/MIT keyblock API conditional (`SAMBA4_USES_HEIMDAL`). The manual `malloc()` in `PAC_DATA_pkinit()` is protected by an assertion but would need careful cleanup if future assertions were inserted before the existing free calls. The typed PKINIT TGS registration appears to reuse `PAC_DATA_pkinit_AS`; if that is accidental, TGS interpreted parsing is under-covered. Several fixtures are large and callback coverage focuses on selected high-value fields, so many logon-info details are only covered by generic pull/push validation.

Test signals: failures identify PAC layout, pointer, offset, Unicode, checksum, credential, or Kerberos decryption regressions. Strong signals include wrong PAC buffer count/type/size, missing `info` pointers, incorrect UPN/DNS names, credential info encrypted bytes changing, inability to decrypt with the known reply key, plaintext mismatch against nested credential NDR, wrong logon-name time/name values, checksum type/length mismatches, or NTLM package hash extraction errors.
