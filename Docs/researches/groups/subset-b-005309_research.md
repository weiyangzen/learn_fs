## sources/distributed-fs/ceph-client/drivers/scsi/mpt3sas/mpi/mpi2_cnfg.h

**Purpose:** `mpi2_cnfg.h` is the Broadcom/LSI Fusion-MPT MPI 2.x configuration-page contract for the `mpt3sas` driver. It defines the wire layouts, page address encodings, page type IDs, page version constants, and bit masks used when the host issues `MPI2_CONFIG_REQUEST` messages to firmware and interprets `MPI2_CONFIG_REPLY` plus returned page buffers. It is not executable logic; it is the ABI vocabulary for controller manufacturing data, IOC/IO unit settings, BIOS boot settings, integrated RAID state, SAS topology, enclosure/log pages, driver persistent mappings, Ethernet management pages, and MPI 2.6 PCIe/NVMe topology pages.

**Important APIs and types:** The central headers are `MPI2_CONFIG_PAGE_HEADER`, `MPI2_CONFIG_EXTENDED_PAGE_HEADER`, and their union forms. `MPI2_CONFIG_REQUEST` carries `Action`, `ExtPageLength`, `ExtPageType`, `Header`, `PageAddress`, and a `MPI2_SGE_IO_UNION` page-buffer SGE; `MPI2_CONFIG_REPLY` returns action, page metadata, `IOCStatus`, and `IOCLogInfo`. Actions cover page-header query, current/default/NVRAM reads, current/NVRAM writes, and changeable-mask discovery. Page addressing macros encode get-next and handle/index forms for RAID volumes, physical disks, SAS expanders/devices/phys/ports/enclosures, RAID configurations, driver persistent mapping entries, Ethernet interfaces, PCIe switches/devices/links, and MPI 2.6 enclosures.

**Important page families:** Manufacturing pages 0-7 and product-specific pages expose board names, VPD, chip revision, RAID policy limits, WWIDs/device names per PHY, connector layout, enclosure names, and supported controller PCI device IDs from SAS200x through SAS39xx-class parts. IO Unit pages expose unique NVDATA versions, global flags such as write-cache and fast-path controls, GPIO, RAID accelerator DMA capabilities, power/temperature/PCIe link telemetry, sensor thresholds, credit assignment, and MPI 2.6 spin-up behavior. IOC pages expose PCI IDs, coalescing settings, integrated RAID capability limits, event masks, broadcast/notify primitive masks, and persistent target mapping limits. BIOS pages define boot preferences and requested/current boot targets by SAS WWID, enclosure slot, or device name. RAID volume, physical disk, and RAID configuration pages describe IR volume state, status flags, member disks, hot-spare pools, GUID/WWID/name, physical-disk inquiry data, errors, attributes, and configuration elements.

**Topology and telemetry types:** SAS common macros define negotiated/programmed/hardware link rates through 1.5/3/6/12/22.5 Gb/s and PHY info masks. SAS IO Unit pages describe controller PHYs, discovery status, invalid topology controls, power management, spin-up groups, port-width modulation, and fast-path statistics. SAS Expander pages describe expander handles, parent handles, route indexes, zoning/reduced-functionality status, and per-PHY attached device information. SAS Device pages define discovered end-device handles, SAS address, parent, slot/enclosure, access status, device flags, fast-path capability, SATA feature flags, and connector/enclosure level metadata. SAS PHY pages provide link counters, event data/config, threshold notifications, and initial SATA frames. SAS Port, SAS Enclosure, Log, Driver Mapping, Ethernet, Extended Manufacturing, PCIe IO Unit, PCIe Switch, PCIe Device, and PCIe Link pages cover the later protocol extensions, including NVMe access status, retimer flags, maximum transfer/capability data, PCIe error counters, and configurable PCIe link-event thresholds.

**Control flow, state, and persistence:** The header encodes a two-step config-page flow used by `mpt3sas_config.c`: callers first issue `MPI2_CONFIG_ACTION_PAGE_HEADER` to learn the page length/version, allocate or reuse a DMA page buffer, then issue a read or write action with a properly encoded `PageAddress` and SGE. Persistent state lives in controller firmware/NVRAM, not this header. The `PAGEATTR_PERSISTENT` attribute, `PAGE_WRITE_NVRAM`, NVDATA version fields, BIOS pages, IO Unit flags, IOC persistent mapping pages, and Driver Persistent Mapping page describe data that may survive resets or reboots. Many structures use flexible arrays and comments explicitly require host code to trust runtime count fields such as `NumPhys`, `NumSensors`, `NumGroups`, `NumPhyEvents`, `NumLinkEvents`, `NumberOfLayouts`, and related page lengths rather than compile-time maximums.

**Dependencies and integration points:** `mpt3sas_base.h` includes this header alongside `mpi2.h`, `mpi2_init.h`, `mpi2_ioc.h`, `mpi2_sas.h`, `mpi2_pci.h`, and `mpi2_image.h`, so the scalar typedefs (`U8`, `U16`, `U32`, `U64`), `MPI2_VERSION_UNION`, SGE unions, SCSI/SAS/PCIe device-info masks, and IOC status/function codes come from sibling MPI headers. `mpt3sas_config.c` uses the page type and ext-page type macros to format debug labels and implements the transport for reading/writing these pages. `mpt3sas_scsih.c` consumes SAS/PCIe device, expander, enclosure, and access-status pages during discovery, topology refresh, target creation, and error messages. `mpt3sas_base.c` and `mpt3sas_ctl.c` rely on the PCI device ID and config request definitions for adapter identification and user/control path config access. `mpt3sas_trigger_pages.h` extends the same extended-page-header model with driver-private persistent trigger pages.

**Risks and sharp edges:** This file is a hardware/firmware ABI, so field order, byte offsets, fixed widths, and page-version constants are high risk. The header intentionally mixes MPI2, MPI25, and MPI26 names; using a newer field on an older controller can cause firmware rejection or misinterpretation. Flexible arrays and fixed "max" arrays are dangerous unless the caller first validates `Header.PageLength` or `ExtPageLength` and the runtime count fields. PageAddress form masks must match the requested page type; an incorrect form can enumerate the wrong object or loop forever on get-next traversal. Current versus default versus NVRAM reads/writes have different persistence semantics, so writes to the wrong action can either disappear after reset or unexpectedly persist. There are some specification-derived oddities, such as overlapping/duplicated offsets in comments and obsolete aliases; consumers should rely on the struct layout and spec, not infer behavior from comments alone.

**Test signals:** Useful validation includes compile-time or static assertions for key struct sizes and offsets used in request frames; config-page header/read/write smoke tests across IO Unit, IOC, SAS Device, SAS Expander, SAS PHY, Enclosure, and PCIe Device pages; get-next enumeration for SAS and PCIe topology that terminates cleanly; negative tests for invalid page type, ext-page type, and PageAddress form; persistent mapping and BIOS/IO Unit write tests that compare current versus NVRAM/default behavior across reset where hardware allows; and fuzz-like checks that short page lengths or excessive count fields do not overrun the DMA buffer.

## sources/distributed-fs/ceph-client/drivers/scsi/mpt3sas/mpi/mpi2_image.h

**Purpose:** `mpi2_image.h` defines the firmware image, component image, extended image, flash-layout, supported-device, initialization-footer, and encrypted-hash metadata formats understood by MPI 2.x/2.6 `mpt3sas` firmware tooling paths. It is the driver-side description of binary image headers used for firmware upload/download, package version reporting, image chaining, flash-region layout, supported-device matching, and authenticated image metadata.

**Important APIs and types:** `MPI2_FW_IMAGE_HEADER` is the classic 0x100-byte firmware header with signatures, MPI/FW/NVDATA/package versions, vendor/product/protocol IDs, IOC capabilities, image size, next-image offset, checksum, boot flags, version/vendor/package strings, and reserved space. Macros define signature masks/values for MPI2 and MPI26, product ID type/product/family masks, boot flags for SPI flash variants, and fixed offsets such as image size and next-image offset. `MPI26_COMPONENT_IMAGE_HEADER` is the MPI 2.6 component header, also 0x100 bytes, with load/start/flash offsets, data/flash sizes, version/build/environment string offsets, component type signature, CRC, compression/not-flash flags, secondary flash offset, RMC/FW/NVDATA versions, hash exclusion ranges, and next-image offset. `MPI2_EXT_IMAGE_HEADER` describes chained extended image payloads by image type, checksum, image size, next-image offset, package version, and identify string.

**Image payload formats:** Flash layout data is modeled by `MPI2_FLASH_LAYOUT_DATA`, `MPI2_FLASH_LAYOUT`, and `MPI2_FLASH_REGION`, with region types for firmware, BIOS, NVDATA, firmware backup, manufacturing info, config regions, MegaRAID, common boot block/init, CBB backup, SBR/SBR backup, HIIM/HIIA, controller, IMR firmware, MR NVDATA, CPLD, PSOC, and coredump. `MPI2_SUPPORTED_DEVICES_DATA` contains a variable list of vendor/device/revision ranges accepted by an image. `MPI2_INIT_IMAGE_FOOTER` gives boot flags, image size, signatures, and reset vector for initialization images. `MPI25_ENCRYPTED_HASH_ENTRY` and `MPI25_ENCRYPTED_HASH_DATA` define variable-length encrypted hash records, with MPI25 SHA256/RSA256 values and MPI26 SHA version/size masks plus RSA key sizes through 4096.

**Control flow, state, and persistence:** The header is passive, but its fields guide firmware-image parsing. A consumer validates the signature words, reads `ImageSize`, follows `NextImageHeaderOffset` to chained images, and checks image/component type before acting on the payload. Flash-layout records describe persistent regions in controller flash; writing the wrong region can affect boot firmware, BIOS/HII, NVDATA, manufacturing data, or crash dumps. The supported-device table is a guardrail for matching a binary package to PCI IDs and revision ranges. Encrypted hash data and component CRC/hash exclusion metadata are used to verify image integrity while excluding mutable fields.

**Dependencies and integration points:** This header depends on base MPI scalar types and `MPI2_VERSION_UNION` from sibling MPI headers. `mpt3sas_base.h` includes it for core driver code. `mpt3sas_base.c` uses `Mpi2FWImageHeader_t` and `Mpi26ComponentImageHeader_t` in `_base_display_fwpkg_version()` to issue FWUpload, read the package or component image header from firmware, and display firmware package version data. Sibling `mpi2_ioc.h` defines firmware upload/download request and reply messages whose payloads use these image header layouts and references these product ID and extended image type definitions.

**Risks and sharp edges:** All structs describe on-flash/on-wire binary data, so layout drift, padding assumptions, and endian handling are critical. The header uses C flexible arrays for flash regions, layouts, supported devices, and encrypted hashes; callers must validate count fields such as `NumberOfLayouts`, `RegionsPerLayout`, `NumberOfDevices`, and `NumHash` against the containing image size. Signature constants differ between MPI2 and MPI26, and `Signature0` includes architecture-specific low-byte variants, so overly strict validation can reject valid packages while overly loose validation can accept the wrong architecture. Image chaining through `NextImageHeaderOffset` needs bounds and loop checks. Flash region writes are high impact because regions include firmware, NVDATA, manufacturing data, boot blocks, and coredumps. The string/offset fields are offsets into binary blobs, not necessarily trusted C strings.

**Test signals:** Validate struct sizes for the 0x100 firmware and component headers and 0x40 extended header. Test signature parsing for MPI2, MPI26, architecture-specific MPI26 variants, and invalid signatures. Exercise chained-image traversal with zero, valid, out-of-range, and cyclic next offsets. Parse flash-layout payloads with boundary counts and region sizes. Verify supported-device matching against PCI vendor/device/revision masks. For firmware upload paths, confirm the driver handles short uploads, bad CRC/checksum/signature values, unexpected component types, and package-version extraction without reading beyond the DMA buffer.

## sources/distributed-fs/ceph-client/drivers/scsi/mpt3sas/mpi/mpi2_init.h

**Purpose:** `mpi2_init.h` defines the MPI 2.x SCSI initiator-mode message ABI used by `mpt3sas` for normal SCSI I/O, RAID-component passthrough I/O, SCSI task management, and enclosure processor slot-status requests. It is the wire-format companion to the SCSI mid-layer request path in `mpt3sas_scsih.c`.

**Important APIs and types:** `MPI2_SCSI_IO_CDB_EEDP32` and `MPI2_SCSI_IO_CDB_UNION` model 32-byte CDB storage, EEDP protection data, or an embedded SGE. `MPI2_SCSI_IO_REQUEST` is the MPI 2.0 SCSI I/O request layout, carrying device handle, sense buffer address/length, SGL flags and offsets, data lengths, I/O flags, EEDP fields, LUN, control flags, CDB, optional vendor region, and first SGL. `MPI25_SCSI_IO_REQUEST` is the MPI 2.5/2.6 variant, replacing the 16-bit SGL flags field with `DMAFlags`, reducing `EEDPBlockSize` to 16 bits, using IEEE64 CDB SGE form, and ending with `MPI25_SGE_IO_UNION`. `MPI2_SCSI_IO_REPLY` returns SCSI status/state, IOC status/log info, transfer and sense counts, response info, task tag, SCSI status qualifier, bidirectional transfer count, and MPI 2.5+ EEDP observed/error fields.

**I/O flag and data-integrity macros:** MsgFlags choose the address space for the sense buffer. SGLFlags encode address space and SGE type for up to four SGL segments. IoFlags encode CDB length, large-CDB handling, bidirectional I/O, multicast, fast path for MPI25, port request for MPI26, and escape passthrough. `Control` encodes data direction, task/command priority, queue attribute, additional CDB length, and TLR. EEDP flags select protection operations such as check, strip, check-remove, insert, replace, and check-regen; optional bits request guard/application/reference tag checks and tag increments. MPI25 `DMAFlags` describe data/cache/interleaved/host-DIF lane combinations.

**Task management and SEP types:** `MPI2_SCSI_TASK_MANAGE_REQUEST` sends abort task, abort task set, target reset, logical unit reset, clear task set, query task, clear ACA, query task set, and query asynchronous event operations, optionally selecting SAS target reset variants or MPI26 PCIe reset semantics in `MsgFlags`. `MPI2_SCSI_TASK_MANAGE_REPLY` reports response code, IOC status/log info, termination count, and packed additional response info. `MPI2_SEP_REQUEST` and `MPI2_SEP_REPLY` read or write enclosure slot status by device handle or enclosure/slot address, with flags for identify, remove, rebuild stopped, hot spare, unconfigured, predicted fault, failed/critical array, rebuilding, faulty, device off, and no error.

**Control flow, state, and persistence:** In `scsih_qcmd()`, the driver translates a Linux `scsi_cmnd` into `Mpi25SCSIIORequest_t`: it chooses read/write/no-transfer control bits, applies simple queue and optional command priority, enables TLR where allowed, allocates an SMID, zeroes the request frame, fills function, device handle, data length, control, CDB length, system sense-buffer address, SGL offset, LUN, CDB, and SGL, then posts the SMID on normal, fast-path, or default queues depending on target flags and RAID passthrough. `_scsih_setup_eedp()` fills EEDP flags and tags from the SCSI protection operation. Completion code interprets `MPI2_SCSI_IO_REPLY` fields to produce Linux SCSI results and sense handling. Task-management helpers build `MPI2_SCSI_TASK_MANAGE_REQUEST` during abort/reset recovery and use reply response codes to decide recovery progress. The header itself stores no state; outstanding I/O state is the request frame plus driver SMID/scsi command tracking.

**Dependencies and integration points:** The header depends on MPI base types, SGE unions, LUN macros, IOC status codes, and function codes from `mpi2.h`/`mpi2_ioc.h`. `mpt3sas_base.h` includes it for all core driver modules. `mpt3sas_scsih.c` uses the SCSI I/O macros directly in `_scsih_setup_eedp()`, `scsih_qcmd()`, direct-I/O setup, fast-path posting, and task-management paths. The SCSI mid-layer supplies `scsi_cmnd`, data direction, protection operations, protection flags, CDB length, LUN, sense buffer, and scatter-gather data; the base layer supplies request frames, DMA sense-buffer addresses, SGL builders, and SMID posting functions.

**Risks and sharp edges:** MPI2 and MPI25 request layouts are similar but not identical; using the wrong typedef for a controller generation can corrupt `DMAFlags`, `SGLFlags`, or `EEDPBlockSize`. CDB length and additional-CDB-length bits must match the actual command bytes, especially for 32-byte CDBs. Data direction, bidirectional length, SGL offsets, and SGL type/address-space flags must align with DMA mapping or firmware may DMA to the wrong place. EEDP setup is subtle: wrong guard/ref/app tag bits or block size can turn valid protection I/O into check conditions or data-integrity errors. Task management request `TaskMID`, reset type, LUN, and target handle must match the outstanding command or recovery may either fail or reset more than intended. SEP slot status has write side effects on enclosure indicators and fault/remove state.

**Test signals:** Exercise normal reads, writes, no-data commands, 32-byte CDBs, fast-path targets, RAID-component passthrough, zero-length SGLs, and DMA mapping failure cleanup. Validate protection-information operations for read-strip and write-insert with guard/reference checks and observed EEDP error reporting. Confirm SCSI status/state translation for good, check condition with autosense, busy, task set full, terminated, no status, and autosense failed. Recovery tests should cover abort task, logical unit reset, target reset, and PCIe/SAS reset flag variants with expected task-management response codes. SEP tests should read and write slot status by handle and by enclosure/slot and verify that identify/remove/fault bits round-trip through firmware or a simulator.
