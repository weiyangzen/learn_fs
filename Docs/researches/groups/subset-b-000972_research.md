# sources/distributed-fs/ceph-client/drivers/accel/habanalabs/include/gaudi/asic_reg/nif_rtr_ctrl_7_regs.h

## Purpose
`nif_rtr_ctrl_7_regs.h` is an autogenerated Gaudi register-address map for NIF router controller instance 7. It exposes 438 preprocessor symbols whose values are MMIO/config offsets from `0x3F6108` through `0x3F6CBC`. The file has no executable logic; its purpose is to give the Gaudi driver stable names for the NIF-side router registers that control address range security, privilege checks, SRAM/HBM scrambling, rate limiting, request credit/e2e tuning, nonlinear address translation, and read/write counters.

## Important APIs, types, and functions
- Exported API surface is entirely `#define` symbols prefixed `mmNIF_RTR_CTRL_7_`.
- Security and privilege range families include `RANGE_SEC_*_{AW,AR}` and `RANGE_PRIV_*_{AW,AR}` hit, base-low/high, and mask-low/high registers, with 16 indexed range entries per base/mask family.
- Scrambler controls are `mmNIF_RTR_CTRL_7_SCRAM_SRAM_EN` and `mmNIF_RTR_CTRL_7_SCRAM_HBM_EN`.
- E2E control symbols cover HBM and PCI enable and sizing registers plus AW/AR counters for HBM channels and PCI.
- Nonlinear address routing symbols include `NON_LIN_EN`, `NL_SRAM_OFFSET_*`, `NL_SRAM_BANK_*`, `NL_HBM_OFFSET_*`, `NL_HBM_SEL_*`, and `NL_HBM_PC_SEL_*`.
- Rate/latency control families include `RL_HBM_*`, `RL_PCI_*`, `RL_SRAM_*`, and RGL token, bank-id, expected-latency, watchdog, and shift registers.

## Control flow
The header itself has no control flow. Control enters through driver initialization and security paths that include the aggregate Gaudi register headers. In `gaudi.c`, NIF router 7 symbols are written during SRAM and HBM scrambler setup, and E2E sizing/enabling is programmed as part of `gaudi_init_e2e()` when firmware has not already enabled those features and security firmware does not own the block. In `gaudi_security.c`, the NIF router security range symbols participate in arrays that program AW and AR protected ranges. Reads or writes use common HabanaLabs register accessors such as `WREG32()` and `RREG32()`.

## State and persistence
This file persists no software state. The persistent state is hardware-resident in the NIF RTR controller 7 registers until reset, firmware reconfiguration, or driver reinitialization. Security and privilege window programming affects future AW/AR request filtering. Scrambler and E2E bits become part of device initialization state, tracked indirectly by Gaudi capability bits such as HBM/SRAM scrambler initialization. Counter and status registers reflect hardware traffic until reset or counter set/clear operations.

## Dependencies and integration points
The file depends only on preprocessor inclusion and its include guard. It is integrated through generated register bundles included by Gaudi driver sources, while block base metadata also appears in `gaudi_blocks.h` as `mmNIF_RTR_CTRL_7_BASE` (`0x7FFC3F6000ull`). Driver consumers include `gaudi.c` for scrambler and E2E programming, `gaudi_security.c` for secure/privileged address windows, and common register access macros from the HabanaLabs driver.

## Risks and edge cases
- The symbols are autogenerated and must match the exact Gaudi RTL/register database. A wrong offset silently programs a hardware block with no compile-time type checking.
- NIF instance 7 is only one of several symmetric router controllers. Copy/paste or generator drift can make one instance use another instance's address range.
- Security range registers are indexed and directional. Mixing AW and AR arrays or low/high base/mask halves can create security holes or false access violations.
- E2E and scrambler programming is skipped under some firmware/security conditions. Tests must distinguish driver-owned programming from firmware-owned programming.
- The header supplies raw addresses only; field shifts and masks come from separate mask headers such as the shared IF router mask definitions.

## Test signals
Useful signals include successful Gaudi probe/reset with no protected-range faults, expected `gaudi_init_scrambler_*()` capability bits, successful HBM/SRAM and PCI traffic through NIF router 7, no RAZWI/protection events during normal DMA/NIC traffic, and stable E2E counter behavior after `gaudi_init_e2e()`. Negative signals include protection-bit error logs, unexpected AW/AR hit bits, failed memory traffic after enabling scrambling, or only NIF instance 7 failing while sibling router instances pass.

# sources/distributed-fs/ceph-client/drivers/accel/habanalabs/include/gaudi/asic_reg/psoc_cpu_pll_regs.h

## Purpose
`psoc_cpu_pll_regs.h` is the autogenerated register-address map for the Gaudi PSOC CPU PLL block. It exposes 47 symbols, 46 of which are `mmPSOC_CPU_PLL_*` register offsets from `0xC70100` through `0xC7051C`. The driver uses these definitions to read CPU/PSOC PLL configuration and derive timestamp/PSOC frequency data when firmware does not provide PLL information through CPUCP.

## Important APIs, types, and functions
- Frequency factor registers: `mmPSOC_CPU_PLL_NR`, `mmPSOC_CPU_PLL_NF`, `mmPSOC_CPU_PLL_OD`, and `mmPSOC_CPU_PLL_NB`.
- Divider selection and factor registers: `DIV_FACTOR_0..3`, `DIV_FACTOR_CMD_0..3`, `DIV_SEL_0..3`, `DIV_EN_0..3`, and `DIV_FACTOR_BUSY_0..3`.
- PLL control/status registers: `CFG`, `LOSE_MASK`, `LOCK_INTR`, `LOCK_BYPASS`, `DATA_CHNG`, `RST`, `SLIP_WD_CNTR`, `CLK_GATER`, and `PLL_NOT_STABLE`.
- Measurement/relaxation helpers: `CLK_RLX_0..3`, `REF_CNTR_PERIOD`, low/high reference thresholds, `FREQ_CALC_EN`, `RLX_BITMAP_CFG`, and `RLX_BITMAP_0..3`.

## Control flow
The header has no executable control flow. In Gaudi initialization, `gaudi_fetch_psoc_frequency()` first prefers firmware-provided CPU PLL data when Linux firmware and CPU queue support are available. Otherwise it falls back to direct reads from `mmPSOC_CPU_PLL_DIV_FACTOR_2`, `mmPSOC_CPU_PLL_DIV_SEL_2`, `mmPSOC_CPU_PLL_NR`, `mmPSOC_CPU_PLL_NF`, and `mmPSOC_CPU_PLL_OD`. The driver then computes either the reference clock, divided reference clock, PLL clock, or divided PLL clock and stores the resulting PSOC timestamp frequency in `hdev->asic_prop`.

## State and persistence
No software state is declared here. Hardware PLL register state persists across normal operation and may be changed by firmware, reset, or power-management flows. The driver snapshots selected PLL values into `asic_prop.psoc_timestamp_frequency`, `psoc_pci_pll_nr`, `psoc_pci_pll_nf`, `psoc_pci_pll_od`, and `psoc_pci_pll_div_factor`, making these register values indirectly persistent in driver properties after probe.

## Dependencies and integration points
The definitions integrate with `gaudi.c` frequency discovery and with firmware boot capability flags that decide whether to use CPUCP PLL info or direct MMIO reads. The computed frequency feeds timestamp and CoreSight STM configuration paths that need a PSOC clock. The block base is listed in `gaudi_blocks.h` as `mmPSOC_CPU_PLL_BASE` (`0x7FFCC70000ull`).

## Risks and edge cases
- Fallback frequency calculation trusts raw hardware values. Invalid divider selections are handled by warning and setting frequency to zero.
- Integer arithmetic can truncate derived frequencies; callers treat the result as a compact frequency value rather than a high-precision measurement.
- Firmware-owned PLL configuration may race conceptually with direct register reads if the fallback path is used before PLL values are stable.
- Output index 2 is significant in both CPUCP and direct fallback logic. Register or firmware contract drift can make timestamp frequency wrong while the driver still probes.
- The header has addresses only; semantic validation of legal PLL factors lives in the consumer code or firmware.

## Test signals
Positive signals include nonzero `psoc_timestamp_frequency`, correct device timestamp progression, valid CoreSight STM frequency programming, and absence of "invalid div select" warnings during fallback. Regression tests should cover firmware PLL-info path, fallback path, invalid divider selection, reset/reprobe, and timestamp reads that depend on this frequency data.

# sources/distributed-fs/ceph-client/drivers/accel/habanalabs/include/gaudi/asic_reg/psoc_etr_regs.h

## Purpose
`psoc_etr_regs.h` is the autogenerated register-address map for the PSOC Embedded Trace Router/Trace Buffer sink used by Gaudi CoreSight debug capture. It exposes 47 symbols, 46 of which are `mmPSOC_ETR_*` offsets from `0x2C43004` through `0x2C43FFC`. These names let `gaudi_coresight.c` configure trace buffer size, mode, AXI attributes, data buffer address, formatter state, lock/unlock, status, and device identity registers.

## Important APIs, types, and functions
- Capture buffer controls include `RSZ`, `MODE`, `BUFWM`, `DBALO`, `DBAHI`, `RWP`, `RWPHI`, `RRP`, `RRPHI`, and buffer level registers.
- Runtime control/status registers include `CTL`, `STS`, `FFSR`, `FFCR`, `PSCR`, and `AXICTL`.
- Integration-test and CoreSight management registers include `ITMISCOP0`, `ITTRFLIN`, `ITATBDATA0`, `ITATBCTR*`, `ITCTRL`, `CLAIMSET`, `CLAIMCLR`, `LAR`, `LSR`, and `AUTHSTATUS`.
- Identification symbols include `DEVID`, `DEVTYPE`, `PERIPHID0..7`, and `COMPID0..3`.

## Control flow
The header has no control flow, but its symbols are central to `gaudi_config_etr()` in `gaudi_coresight.c`. On enable, the driver unlocks the ETR through `LAR`, validates the user-provided trace buffer, writes the MSB in PSOC global config, programs `BUFWM`, `RSZ`, `MODE`, `AXICTL` when security permits, writes `DBALO/DBAHI`, sets `FFCR` and `PSCR`, and starts capture with `CTL`. On disable, it requests formatter flush/stop through `FFCR`, polls `FFCR` and `STS`, clears `CTL`, resets buffer registers, and optionally reads `RWP/RWPHI` plus the global trace MSB to return the current write pointer.

## State and persistence
No software state is stored in the header. ETR hardware state persists while debug mode is active: buffer base, size, write pointer, formatter state, AXI attributes, and capture enable. `gaudi_halt_coresight()` disables ETR when leaving debug mode. The ETR write pointer is observable state returned to userspace on disable when an output buffer is supplied.

## Dependencies and integration points
The header integrates with `gaudi_coresight.c`, CoreSight debug ioctl handling, the PSOC global config trace-address register, device memory validation, and common `WREG32()`/`RREG32()` accessors. The block base is listed in `gaudi_blocks.h` as `mmPSOC_ETR_BASE` (`0x7FFEC43000ull`). It is also mirrored by later ASIC support such as Gaudi2 CoreSight code, so symbol semantics are part of a broader HabanaLabs debug convention.

## Risks and edge cases
- ETR register sequencing is strict. Misordered `FFCR`, `STS`, and `CTL` operations can leave trace capture partially enabled or lose buffered data.
- Buffer address handling is split between ETR registers and `mmPSOC_GLOBAL_CONF_TRACE_ADDR`; both definitions must stay aligned.
- `AXICTL` programming differs under secure firmware, so default firmware attributes become part of the capture contract.
- Timeout polling depends on these exact status bit locations; wrong offsets can report success or failure against the wrong register.
- Buffer size and address validation lives in code, not this header, so raw macros can be misused by new consumers.

## Test signals
Positive signals include successful `HL_DEBUG_OP_ETR` enable/disable cycles, no CoreSight timeout logs, trace data written to SRAM/DRAM or host PMMU buffers, plausible returned write pointers, and clean ETR shutdown during debug-mode exit. Negative signals include timeout while waiting for `FFCR` or `STS`, invalid trace buffer behavior, zero or stale write pointers, and trace capture failures that are isolated to the PSOC ETR path.

# sources/distributed-fs/ceph-client/drivers/accel/habanalabs/include/gaudi/asic_reg/psoc_global_conf_masks.h

## Purpose
`psoc_global_conf_masks.h` is the autogenerated bitfield contract for Gaudi PSOC global configuration registers. It exposes 305 macros, mostly `*_SHIFT` and `*_MASK` pairs, for boot sequencing, reset control, scratchpads, semaphores, CPU boot messaging, I2C debug, trace address/user fields, interrupts, memory repair, pad configuration, ADC setup, and reset-source/status registers. It complements `psoc_global_conf_regs.h`, which provides the register offsets.

## Important APIs, types, and functions
- Boot and firmware state fields include masks for `PCI_FW_FSM`, `BOOT_SEQ_RE_START`, `BTM_FSM`, `BOOT_SEQ_FSM`, `BOOT_SEQ_TIMEOUT`, SPI image status, boot-state, boot-source, and CPU boot status.
- Reset-related fields cover watchdog, manual, PRSTN, software-all, soft-reset, unit reset, reset masks, reset source, and reset-control selector fields.
- Communication fields cover `SCRATCHPAD`, `SEMAPHORE`, `KMD_MSG_TO_CPU`, and `SPL_SOURCE`.
- Debug/trace fields include `TRACE_ADDR_MSB`, `TRACE_AWUSER`, `TRACE_ARUSER`, `ARUSER`, and `AWUSER` fields used by CoreSight and MMU context preparation.
- Interrupt/status fields cover RAZWI, ADC, timeout, combined timeout/peripheral interrupt fields, AXI errors, target id, outstanding transactions, and mask requests.
- Pad and peripheral fields cover 1.8 V/3.3 V pad config/input, I2C master/slave debug, eMMC voltage status, bootstrap pins, ADC timing, and pad selection.

## Control flow
The header has no control flow. Consumer code uses these masks when composing or extracting fields for PSOC global configuration registers. For example, Gaudi reset code writes `mmPSOC_GLOBAL_CONF_SW_ALL_RST` using `PSOC_GLOBAL_CONF_SW_ALL_RST_IND_SHIFT` and checks reset completion by masking `mmPSOC_GLOBAL_CONF_BTM_FSM` with `PSOC_GLOBAL_CONF_BTM_FSM_STATE_MASK`. CoreSight ETR code masks trace-buffer MSB values with `PSOC_GLOBAL_CONF_TRACE_ADDR_MSB_MASK`, and MMU preparation code programs trace ARUSER/AWUSER fields.

## State and persistence
The header declares no state. It defines how to encode and decode hardware state held in PSOC global config registers. Some fields are transient control pulses, such as reset commands and boot restart indicators. Others are persistent or latched status fields, such as boot status, reset source, scratchpads, semaphore values, pad configuration, and interrupt cause/mask state.

## Dependencies and integration points
This mask header must stay synchronized with `psoc_global_conf_regs.h` and with generated register definitions included by `gaudi_regs.h`. It is consumed by `gaudi.c`, `gaudi_coresight.c`, `gaudi_reg_map.h`, reset paths, firmware loader descriptors, MMU setup, and debug/trace programming. It also has conceptual overlap with Gaudi2 PSOC global config handling, where similarly named masks are used for RAZWI and debug fields.

## Risks and edge cases
- Shift/mask drift is dangerous because code can compile while reading or writing the wrong field in the right register.
- Several masks cover reset and boot sequencing. Incorrect values can prevent recovery, reset the wrong units, or leave PCIe/PSOC in an unexpected state.
- Full-width masks such as non-reset flop values and scratchpad/semaphore fields are easy to treat as unstructured storage; ownership must be coordinated with firmware.
- Directional trace ARUSER/AWUSER fields must match MMU ASID expectations, or trace writes can target the wrong address context.
- Field names in this header do not enforce read-only, write-one-to-clear, pulse, or sticky semantics.

## Test signals
Positive signals include successful boot sequence handoff, correct hard reset completion, valid CPU boot status messaging, working CoreSight ETR trace addressing, stable MMU trace ASID setup, and no unexpected RAZWI/protection interrupts. Negative signals include reset timeout while polling `BTM_FSM`, bad firmware boot status, trace buffer address truncation, wrong scratchpad-based interrupt polling behavior, or interrupt fields that cannot be cleared/masked as expected.

# sources/distributed-fs/ceph-client/drivers/accel/habanalabs/include/gaudi/asic_reg/psoc_global_conf_regs.h

## Purpose
`psoc_global_conf_regs.h` is the autogenerated register-offset map for the Gaudi PSOC global configuration block. It exposes 521 macros, 520 of which are `mmPSOC_GLOBAL_CONF_*` register offsets from `0xC4B000` through `0xC4BCD4`. This block is a central driver/firmware control surface for boot sequencing, reset control, scratchpads, semaphores, CPU messaging, trace address context, interrupts, pad configuration, ADC, memory repair, and reset controller programming.

## Important APIs, types, and functions
- Boot and firmware registers include `NON_RST_FLOPS_*`, `PCI_FW_FSM`, `BOOT_SEQ_RE_START`, `BTM_FSM`, `SW_BTM_FSM`, `SW_BOOT_SEQ_FSM`, `BOOT_SEQ_TIMEOUT`, `SPI_MEM_EN`, `SPI_IMG_STS`, `BOOT_SEQ_FSM`, `BOOT_SEQ_EXT_LD`, and `BOOT_STATE`.
- Driver/firmware communication registers include `SCRATCHPAD_0..31`, `SEMAPHORE_0..31`, `CPU_BOOT_STATUS`, `KMD_MSG_TO_CPU`, and `SPL_SOURCE`.
- Trace and MMU context registers include `TRACE_ADDR`, `ARUSER`, `AWUSER`, `TRACE_AWUSER`, and `TRACE_ARUSER`.
- Reset registers include watchdog/manual/PRSTN/software-all/soft-reset config low/high registers, `SW_ALL_RST`, `SOFT_RST`, `UNIT_RST_N*`, `PRSTN_MASK`, `WD_MASK`, `RST_SRC`, and `RST_CTRL_*`.
- Peripheral/status groups include RAZWI/protection/ADC/timeout/peripheral/AXI error interrupts, target id, eMMC voltage, bootstrap pins, memory repair, outstanding transactions, pad 1.8 V/3.3 V config/input arrays, ADC timing/config, pad defaults, pad selection, and bank mode selection.

## Control flow
The header itself does not execute code. It is used heavily by Gaudi control paths. Firmware loading descriptors store `mmPSOC_GLOBAL_CONF_KMD_MSG_TO_CPU` and `mmPSOC_GLOBAL_CONF_CPU_BOOT_STATUS`. Hard reset setup writes reset configuration registers, sets `mmPSOC_GLOBAL_CONF_BOOT_SEQ_RE_START`, writes `mmPSOC_GLOBAL_CONF_SW_ALL_RST`, waits, then checks `mmPSOC_GLOBAL_CONF_BTM_FSM`. CoreSight ETR writes `mmPSOC_GLOBAL_CONF_TRACE_ADDR` alongside PSOC ETR DBA registers. MMU setup calls `gaudi_mmu_prepare_reg()` for `TRACE_ARUSER` and `TRACE_AWUSER`. `gaudi_reg_map.h` aliases scratchpads for polling registers such as `mmHW_STATE`.

## State and persistence
Hardware state in this block persists according to PSOC reset domains. Scratchpads and semaphores are shared state between host driver and firmware. Boot and reset fields can be latched across parts of initialization and reset. Trace address and ARUSER/AWUSER settings persist while debug capture or MMU context programming is active. Pad, ADC, and memory repair registers represent board/SoC configuration state and may be firmware-owned.

## Dependencies and integration points
This header is paired with `psoc_global_conf_masks.h` for bit encodings. It is included through generated Gaudi register bundles and integrated with `gaudi.c`, `gaudi_coresight.c`, `gaudi_reg_map.h`, boot interface structures, reset handling, firmware loader/static loader setup, MMU programming, and debug flushing via `mmHW_STATE`. The block base is listed in `gaudi_blocks.h` as `mmPSOC_GLOBAL_CONF_BASE` (`0x7FFCC4B000ull`).

## Risks and edge cases
- This is a high-blast-radius register map. Incorrect offsets can break boot, reset, debug tracing, interrupt handling, or firmware messaging.
- Some registers are shared with firmware; driver writes must respect ownership and sequencing.
- Scratchpad aliases in `gaudi_reg_map.h` depend on stable scratchpad numbering. Reassigning scratchpads can break polling or interrupt-control conventions.
- Reset-control registers are split into low/high halves and multiple reset classes. Writing the wrong half or wrong class can reset unintended hardware.
- Trace address state is split between global config and ETR registers, creating a cross-header consistency requirement.
- The header does not mark volatile, read-only, write-one-to-clear, or pulse semantics.

## Test signals
Positive signals include clean firmware load, CPU boot status updates, successful hard and soft resets, stable scratchpad polling, working debug trace capture, correct MMU trace ASID programming, and expected pad/ADC behavior if exercised. Negative signals include bootloader stalls, reset timeouts, unresponsive CPUCP messaging, unexpected RAZWI or AXI errors, broken `mmHW_STATE` flush behavior, or trace writes landing outside the selected buffer/context.

# sources/distributed-fs/ceph-client/drivers/accel/habanalabs/include/gaudi/asic_reg/psoc_timestamp_regs.h

## Purpose
`psoc_timestamp_regs.h` is the autogenerated register-address map for the Gaudi PSOC timestamp counter block. It exposes 18 macros, 17 of which are `mmPSOC_TIMESTAMP_*` offsets from `0xC49000` through `0xC49FFC`. The block provides counter control, status, 64-bit counter value, frequency id, and CoreSight-style peripheral/component ID registers.

## Important APIs, types, and functions
- Counter control and status symbols: `mmPSOC_TIMESTAMP_CNTCR` and `mmPSOC_TIMESTAMP_CNTSR`.
- Counter value symbols: `mmPSOC_TIMESTAMP_CNTCVL` and `mmPSOC_TIMESTAMP_CNTCVU`, read together as a 64-bit device time.
- Frequency symbol: `mmPSOC_TIMESTAMP_CNTFID0`.
- Identification symbols: `PIDR0..7` and `CIDR0..3`.

## Control flow
The header has no direct control flow. In `gaudi.c`, timestamp initialization writes through `mmPSOC_TIMESTAMP_BASE` offsets to stop, clear/program, and restart the counter. Device time reads use `mmPSOC_TIMESTAMP_CNTCVU` and `mmPSOC_TIMESTAMP_CNTCVL`, combining the upper 32 bits and lower 32 bits into a 64-bit timestamp. PLL-derived PSOC frequency from the CPU PLL path provides the frequency context for timestamp consumers.

## State and persistence
No software state is declared here. Hardware state consists of the counter enable/control state, status, configured frequency id, and the monotonically changing counter value. Counter state is reset or reprogrammed during device initialization/reset and is otherwise read as device time.

## Dependencies and integration points
The register offsets integrate with Gaudi timekeeping helpers, timestamp initialization, and any user-visible or debug path that asks the ASIC for device time. The block base is listed in `gaudi_blocks.h` as `mmPSOC_TIMESTAMP_BASE` (`0x7FFCC49000ull`). It depends indirectly on `psoc_cpu_pll_regs.h` consumers for accurate frequency metadata.

## Risks and edge cases
- Reading upper then lower 32-bit counter registers can race rollover if the hardware does not latch reads; consumer code must tolerate or avoid non-monotonic edge cases.
- Base-relative writes in initialization use `mmPSOC_TIMESTAMP_BASE` plus offsets, while reads use named `CNTCV*` offsets. Base and offset definitions must remain consistent.
- A zero or wrong PSOC timestamp frequency makes timestamp deltas misleading even if counter reads work.
- Reset or debug paths can stop or clear the counter, so callers should not assume continuity across reset.

## Test signals
Positive signals include monotonic device time reads, expected counter rate relative to the computed PSOC timestamp frequency, successful reset/restart of the timestamp block, and stable debug timestamps. Negative signals include zero time, non-monotonic time outside reset windows, wrong elapsed-time scaling, or reads that fail only after timestamp block reinitialization.

## Purpose
`sif_rtr_ctrl_0_regs.h` is the autogenerated register-address map for SIF router controller instance 0. It exposes 438 symbols, with `mmSIF_RTR_CTRL_0_*` offsets from `0x306108` through `0x306CBC`. The register families mirror the common router-control prototype: security/privilege ranges, SRAM/HBM scrambling, rate limiting, E2E credit and counters, nonlinear SRAM/HBM routing, and RGL latency/token controls.

## Important APIs, types, and functions
- The public surface is the `mmSIF_RTR_CTRL_0_*` macro set.
- Security and privilege APIs include 16-entry AW/AR base and mask arrays and hit registers for secure and privileged windows.
- Initialization-facing controls include `SCRAM_SRAM_EN`, `SCRAM_HBM_EN`, `E2E_HBM_*`, and `E2E_PCI_*`.
- Telemetry and tuning symbols include AW/AR HBM/PCI counters, counter wrap/set controls, RGL expected-latency/token/bank registers, and rate-limit saturation/timeout/reset controls.
- Address translation symbols include nonlinear enable, SRAM/HBM offsets, SRAM bank selection, HBM selection, and HBM PC selection.

## Control flow
This header has no executable logic. During Gaudi initialization, SIF router 0 is programmed by scrambler setup and by `gaudi_init_e2e()`, which writes instance-specific E2E HBM/PCI sizes before enabling E2E. Security setup uses the SIF router 0 range macros in arrays that configure secure and privileged AW/AR windows. `gaudiP.h` also derives `SIF_RTR_CTRL_OFFSET` from SIF router block bases, so symmetric SIF layout is a driver assumption.

## State and persistence
The header owns no software state. Hardware state persists in SIF router 0 registers until reset or firmware/driver reprogramming. It includes protected range configuration, scrambler enablement, E2E sizing/enables, nonlinear routing tables, counters, and rate-limit status. Driver-level capability bits track only broader feature initialization, not each individual register.

## Dependencies and integration points
The file integrates through Gaudi generated register bundles, `gaudi.c`, `gaudi_security.c`, and `gaudiP.h`. `gaudi_blocks.h` lists `mmSIF_RTR_CTRL_0_BASE` as `0x7FFC306000ull`. The field encodings for shared router registers come from separate mask headers, while this file supplies only instance-0 addresses.

## Risks and edge cases
- SIF router instances are highly symmetric; one wrong instance prefix or base offset can program the wrong fabric path.
- Security ranges split by AW/AR and low/high base/mask halves require exact indexing.
- E2E tuning constants in `gaudi_init_e2e()` are instance-specific. Reusing another instance's values can reduce throughput or break credit behavior.
- Firmware security mode may own or skip programming, so direct register expectations vary by boot mode.
- The header cannot express register access semantics such as sticky counters or write-one-to-clear bits.

## Test signals
Positive signals include successful SIF0 HBM/PCI traffic, no secure/privileged range false positives, initialized scrambler and E2E paths, and expected traffic counters.
