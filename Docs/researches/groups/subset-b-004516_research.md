# sources/distributed-fs/ceph-client/drivers/net/ethernet/marvell/octeontx2/af/rvu_npc.c

Purpose: implements the core RVU Admin Function NPC setup and MCAM resource manager for Marvell OcteonTX2/CN10K/CN20K networking. It initializes the parser/KPU and match-key extraction profiles, configures NPC interface miss behavior, installs AF-owned default steering rules, exposes mailbox handlers for raw MCAM entry/counter operations, and maintains software ownership state for MCAM entries and counters.

Important APIs and functions: initialization is centered on `rvu_npc_init()`, `rvu_npc_hw_init()`, `npc_parser_profile_init()`, `npc_load_kpu_profile()`, `npc_load_mkex_profile()`, `rvu_npc_setup_interfaces()`, `npc_mcam_rsrcs_init()`, and `npc_flow_steering_init()`. KPU/MKEX programming helpers include `npc_config_kpuaction()`, `npc_config_kpucam()`, `npc_program_kpu_profile()`, `npc_program_mkex_profile()`, and `npc_fwdb_prfl_img_map()`. Default rule helpers include `rvu_npc_install_ucast_entry()`, `rvu_npc_install_promisc_entry()`, `rvu_npc_install_bcast_match_entry()`, `rvu_npc_install_allmulti_entry()`, `rvu_npc_enable_default_entries()`, `rvu_npc_disable_default_entries()`, and `rvu_npc_update_flowkey_alg_idx()`. Raw mailbox handlers cover MCAM allocation, free, read, write, enable, disable, shift, counter allocation/free/unmap/clear/stats, allocate-and-write, key extraction config readback, parse mode/pkind updates, base steering rule readback, entry stats, and unicast rule clearing.

Control flow: `rvu_npc_init()` gets the NPC block, reads hardware constants, disables every MCAM bank entry before traffic is allowed, allocates PKIND state, programs the selected KPU parser profile, configures protocol checker defaults, sets interface miss actions, programs hash secret keys and MKEX, initializes MCAM software state, scans the active key extraction profile through `npc_flow_steering_init()`, and finally delegates CN20K-specific initialization when needed. Normal MCAM entry programming validates ownership, disables the entry, clears stale CAM words, expands `struct mcam_entry` keywords into CAM0/CAM1 hardware words, writes action and VLAN tag action registers, and reenables the entry if requested. Allocation flow chooses entries from high, middle, or low priority regions using forward and reverse bitmaps; CN20K instead delegates physical/virtual index management to `npc_cn20k_*` helpers and then mirrors allocation into common maps.

State and persistence: persistent software state is stored in `rvu->hw->mcam`: entry and reverse bitmaps, free counts, entry-to-owner, entry-to-counter, counter-to-owner, counter refcount, entry-to-target-pffunc, key size/bank geometry, reserved default-rule offsets, per-interface key fields/features, and the `mcam_rules` list managed by flow steering. Hardware state persists in NPC AF registers for PKIND, KPU CAM/action tables, MKEX KEX/LDATA/LFLAGS, MCAM CAM/action/tag/stat words, miss actions, parser protocol checker config, and match counters. Loaded firmware profile state is held in `rvu->kpu_fwdata`, `rvu->kpu_prfl_addr`, and `rvu->kpu`. `rvu_npc_freemem()` frees bitmaps/maps and unmaps or frees loaded profile memory.

Dependencies and integration: depends on RVU block discovery and resource helpers, mailbox ABI types from `mbox.h`, NIX LF and multicast helpers, CGX pkind programming, KPU/MKEX profile definitions from `npc_profile.h`, exact/hash support from `rvu_npc_hash.h`, CN20K NPC/register helpers, and core RVU PF/VF state. It is the low-level substrate used by `rvu_npc_fs.c` for higher-level flow install/delete and by exact-match code for drop-rule reservation.

Risks: MCAM entry geometry is hardware-specific, and mistakes in bank/key-size conversion can write the wrong entry. Entry updates must disable and clear before rewriting to avoid stale suppressed writes. The software maps are protected by `mcam->lock`; callers that bypass the established mailbox paths can race ownership or counter refcounts. Default PF/VF rule fixups are subtle because PF-installed VF rules may temporarily remain disabled until the VF NIXLF is initialized, and default RSS action changes must be propagated to dependent rules. Firmware KPU/MKEX loading accepts profiles from filesystem or firmware database, so size/signature/version checks are critical. CN20K paths use virtual indexes and per-entry counters, so common code must translate through `npc_cn20k_vidx2idx()` consistently.

Test signals: boot/probe should log selected KPU and MKEX profiles and initialize NPC without fallback warnings. Exercise PF/VF NIX attach/detach, default unicast/broadcast/promisc/allmulti install and enable/disable, RSS algorithm updates, MCAM allocate/free/read/write/shift, counter allocate/free/map/unmap/stats, parse mode and pkind updates, firmware profile fallback, and CN20K virtual-index allocation. Hardware traffic tests should verify default drops on RX miss, TX default forwarding on TX miss, correct broadcast/multicast replication, VF rule enablement after initialization, and counter increments for matched rules.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/marvell/octeontx2/af/rvu_npc.h

Purpose: declares the small public interface exported by the core NPC implementation to sibling RVU AF modules. It exposes KPU/MKEX profile loading, KPU action programming, firmware database profile mapping, and MCAM bitmap bit updates.

Important APIs and types: `npc_enable_mask()` returns the KPU entry-disable mask used when enabling only programmed entries. `npc_load_kpu_profile()` selects and prepares the default or custom KPU parser profile in `rvu->kpu`. `npc_config_kpuaction()` writes one KPU or PKIND action pair to hardware. `npc_fwdb_prfl_img_map()` maps the firmware database profile image and returns its mapped address and size. `npc_mcam_set_bit()` and `npc_mcam_clear_bit()` are bitmap helpers used by MCAM resource allocation and reservation paths.

Control flow role: this header lets CN20K-specific code and other NPC companion files reuse common KPU action and MCAM bitmap primitives without exposing the full `rvu_npc.c` internals. The declared functions are called during parser profile initialization, MKEX/KPU profile selection, MCAM resource setup, and special-purpose entry reservation.

State and persistence: no state is stored in the header. The functions it declares mutate `rvu->kpu`, `rvu->kpu_fwdata`, `rvu->kpu_prfl_addr`, `rvu->hw->mcam` bitmaps/free counts, and NPC AF KPU/PKIND registers.

Dependencies and integration: depends on forward declarations from the including C files for `struct rvu`, `struct npc_kpu_profile_action`, and `struct npc_mcam`. It is consumed by `rvu_npc.c`, `rvu_npc_fs.c`, and CN20K NPC support code in this driver directory.

Risks: the bitmap helpers require `mcam->lock` to be held, as documented in their implementation; misuse can corrupt the forward and reverse allocation bitmaps or free count. `npc_config_kpuaction()` is a hardware ABI helper, so callers must pass profile data that matches the targeted KPU/PKIND entry layout and silicon generation. The firmware profile mapping helper returns an I/O mapping that must be unmapped by the caller or retained consistently in `rvu`.

Test signals: compile coverage should catch prototype drift. Runtime validation comes from successful KPU profile programming, CN20K parser initialization, MCAM allocation/free accounting, and no leaks from firmware database profile mapping/unmapping.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/marvell/octeontx2/af/rvu_npc_fs.c

Purpose: implements NPC flow steering on top of the raw MCAM manager. It scans the active key extraction profile to discover which packet fields can be matched, translates `npc_install_flow` mailbox requests into MCAM keywords/actions, maintains the ordered rule list, handles default-rule append semantics, manages optional counters, and exposes mailbox handlers for flow install/delete and field capability queries.

Important APIs and functions: `npc_flow_steering_init()` initializes `mcam->mcam_rules` and calls `npc_scan_verify_kex()`. `npc_is_feature_supported()` and `rvu_mbox_handler_npc_get_field_status()` report field support. `npc_update_entry()` writes a field value/mask into `struct mcam_entry_mdata` according to scanned keyword masks. `npc_update_flow()` handles L2/L3/L4/MPLS/IPsec/VLAN field translation and delegates IPv6 hash replacement to `npc_update_field_hash()`. `npc_populate_mcam_mdata()` abstracts normal versus CN20K entry layouts. `rvu_mbox_handler_npc_install_flow()` is the main flow-install mailbox entry point, while `rvu_mbox_handler_npc_delete_flow()`, `npc_mcam_enable_flows()`, `npc_mcam_disable_flows()`, and `npc_install_mcam_drop_rule()` manage lifetime and exact-match drop rules.

Control flow: initialization reads `NPC_AF_INTFX_KEX_CFG` parse-nibble enables and LDATA extractor registers for RX and TX. It records keyword masks for parse-result nibbles such as channel, error, layer types, LXMB, and exact-match result, then scans layer data for DMAC/SMAC, ethertype, VLAN, IPv4/IPv6, TCP/UDP/SCTP, ICMP, IPsec SPI, MPLS, and PF_FUNC. It validates that mandatory RX channel extraction exists and is not overwritten, derives `rx_features` and `tx_features`, and checks multi-layer ethertype/VLAN positions. Flow installation validates interface and supported features, optionally allocates a CN20K entry with the correct key width, resolves target pcifunc from AF/PF/VF/representor context, fills missing default DMAC, checks NIXLF state, then under `rswitch->switch_lock` constructs the MCAM entry. RX entries match channel and produce `nix_rx_action`; TX entries match PF_FUNC and produce `nix_tx_action`. The rule object is inserted in entry order, written through the raw MCAM mailbox handler, and later deleted or disabled by owner/range/entry.

State and persistence: scanned key positions persist in `mcam->rx_key_fields`, `mcam->tx_key_fields`, `mcam->rx_features`, and `mcam->tx_features`. Installed flows persist as `struct rvu_npc_mcam_rule` list nodes containing packet/mask copies, RX/TX action union, VLAN tag action, feature bits, owner, entry, counter metadata, default-rule flag, enable flag, VF VLAN marker, channel/mask, LXMB value, and CN20K hardware priority. Default unicast rules are also referenced from `rvu_pfvf->def_ucast_rule`. Hardware persistence is the MCAM entry/action/tag/counter state written by `rvu_npc.c` or CN20K handlers.

Dependencies and integration: depends on `rvu_npc.c` for raw MCAM writes, entry ownership validation, counter helpers, default entry indexing, and MCAM enable/disable; on `rvu_npc_hash.c` for hashed IPv6 field insertion; on NIX for LF lookup, multicast group index resolution, MCE updates, rate-limit aggregation, and channel numbers; on representor/switchdev state for VF MAC handling; and on CN20K helpers for extractor and MCAM entry format differences.

Risks: feature support is profile-derived, so an incompatible MKEX profile can silently make flow types unavailable or force fallback to the default profile. Overlap checks are essential because higher layers can overwrite earlier fields in the key; skipping them would install misleading filters. Default-rule append merges missing fields from the existing default unicast rule and can produce unexpected matches if feature masks are wrong. Locking alternates between `mcam->lock` and `rswitch->switch_lock`, and `npc_update_dmac_value()` temporarily drops `mcam->lock` before writing entries. CN20K allocation must free freshly allocated entries on every validation error. Counter handling differs between pre-CN20K explicit counters and CN20K per-entry counters.

Test signals: validate `npc_get_field_status` for every supported/unsupported field under default and custom MKEX profiles. Install and delete RX/TX flows for DMAC/SMAC, VLAN, IPv4/IPv6, ports, ICMP, TCP flags, IPsec, MPLS, broadcast/multicast LXMB fallback, default-rule append, counters, MCAST actions, representor targets, PF-set VF MAC, uninitialized VF behavior, and CN20K key-width allocation. Verify entry ordering, hardware counters, delete range/all paths, flow reenable after NIXLF init, flow disable on detach, and exact-match drop rule behavior.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/marvell/octeontx2/af/rvu_npc_fs.h

Purpose: defines flow-steering helper constants and declares the cross-file functions used to populate MCAM entries from parsed flow fields. It is the narrow interface between the flow-steering implementation, core NPC setup, hash support, and CN20K-specific code.

Important APIs and constants: `IPV6_WORDS` defines the four 32-bit words used when converting IPv6 addresses. `NPC_BYTESM`, `NPC_HDR_OFFSET`, `NPC_KEY_OFFSET`, and `NPC_LDATA_EN` describe fields in legacy KEX LDATA configuration words, while `NPC_KEY_OFFSET` and related masks are consumed by scanner and hash code. `npc_update_entry()` inserts a value/mask for one `enum key_fields` item into an MCAM metadata container. `npc_update_flow()` translates a full `flow_msg` packet/mask pair into MCAM keywords and stored rule packet/mask copies. `npc_populate_mcam_mdata()` points a generic metadata wrapper at either a normal `struct mcam_entry` or a `struct cn20k_mcam_entry`.

Control flow role: callers allocate or receive the correct entry object, call `npc_populate_mcam_mdata()` to bind keyword/action pointers, then call `npc_update_flow()` and lower-level action helpers before writing the entry to hardware. `npc_update_entry()` is also used by exact-match drop-rule installation and DMAC update paths when only one field needs changing.

State and persistence: no state is declared here. The APIs mutate caller-owned MCAM entry buffers and, through those buffers, the eventual hardware MCAM state. They also copy packet/mask fields into `struct rvu_npc_mcam_rule` objects passed as output.

Dependencies and integration: depends on `struct rvu`, `enum key_fields`, `struct mcam_entry_mdata`, `struct flow_msg`, `struct rvu_npc_mcam_rule`, `struct cn20k_mcam_entry`, and `struct mcam_entry` from the surrounding RVU/NPC headers. It is included by `rvu_npc_fs.c`, `rvu_npc_hash.c`, and CN20K support where generic field insertion is needed.

Risks: the bit masks in this header encode the hardware register layout for non-CN20K extractor config; using them for CN20K without the CN20K-specific masks would produce wrong byte lengths. The function contracts assume `mcam->rx_key_fields`/`tx_key_fields` were already populated by `npc_flow_steering_init()`. Calling `npc_update_entry()` before profile scanning will result in no field writes.

Test signals: compile tests should catch signature drift across common and CN20K implementations. Runtime signals are successful flow installation for both normal and CN20K entry formats, correct IPv6 field conversion, and exact-match drop rules that match the intended channel/LXMB/exact-result bits.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/marvell/octeontx2/af/rvu_npc_hash.c

Purpose: implements two related NPC hash features. The first programs and emulates field-hash extraction so IPv6 source/destination addresses can be reduced to 32-bit MCAM key fields on hardware that supports hash extract. The second implements the optional NPC exact-match table used for MAC address filtering, including hardware table programming, software entry lists, drop-on-non-hit MCAM rules, promisc transitions, and CGX MAC mailbox handlers.

Important APIs and functions: field-hash support includes `npc_config_secret_key()`, `npc_program_mkex_hash()`, `npc_update_field_hash()`, `npc_field_hash_calc()`, and `rvu_mbox_handler_npc_get_field_hash_info()`. Hash math is implemented by `rvu_npc_toeplitz_hash()`, `rvu_npc_wide_extract()`, and `rvu_npc_lshift_key()`. Exact-match setup is handled by `rvu_npc_exact_init()`, `rvu_exact_config_secret_key()`, `rvu_exact_config_search_key()`, `rvu_exact_config_table_mask()`, and `rvu_exact_config_result_ctrl()`. Runtime table management uses `rvu_npc_exact_add_table_entry()`, `rvu_npc_exact_del_table_entry_by_id()`, `rvu_npc_exact_update_table_entry()`, MEM/CAM alloc/free helpers, and CGX-facing handlers `rvu_npc_exact_mac_addr_set/add/del/reset/update()`. Promisc and feature lifetime are handled by `rvu_npc_exact_promisc_enable()`, `rvu_npc_exact_promisc_disable()`, `rvu_npc_exact_reset()`, `rvu_npc_exact_can_disable_feature()`, and `rvu_npc_exact_disable_feature()`.

Control flow: during normal NPC initialization, `npc_config_secret_key()` writes Toeplitz secret keys if hash extraction is available. `npc_program_mkex_hash()` detects IPv6 source/destination LDATA extractors configured as 4-byte fields at offsets 8 and 24, marks them hash-enabled, updates KEX LDATA config to `use_hash`, and writes HASH_CFG, HASH_MASK, and HASH_RESULT_CTRL registers. Later `npc_update_flow()` calls `npc_update_field_hash()`, which reads hash configuration, computes the same Toeplitz result in software, applies hardware mask/offset, and writes a 32-bit hash into the SIP/DIP MCAM field. Exact-match initialization reads `NPC_AF_CONST3`, checks exact-match capability and exact-result nibble enablement, allocates the `npc_exact_table`, initializes bitmaps and ordered lists, programs exact-match key/mask/result-control registers, then installs one disabled drop MCAM rule per CGX LMAC. Adding a MAC first tries a hashed multi-way MEM slot, falls back to CAM, writes the hardware entry, records a global/list node with seq_id, and enables the corresponding drop rule when the first command rule appears. Delete removes list state, disables drop rules when counts reach zero, clears hardware MEM/CAM entries, and frees the seq_id.

State and persistence: field-hash configuration is stored in NPC AF hash and secret-key registers and mirrored in `rvu->kpu.mkex_hash`. Exact-match state is held in `rvu->hw->table`: table lock, id bitmap, command rule counts, drop-rule counter indexes, promisc mode flags, MEM table ways/depth/bitmap/mask/hash mask/offset, CAM depth/bitmap, per-way ordered lists, CAM list, and global list. Each `npc_exact_table_entry` stores seq_id, MEM/CAM index, MCAM index, op type, channel, pcifunc, way, MAC, CGX/LMAC, channel type, and whether it came from a command. Hardware persistence includes exact MEM/CAM entries, exact secret/search/mask/result registers, and the MCAM drop rules installed through `rvu_npc_fs.c`.

Dependencies and integration: depends on `rvu_npc_fs.h` for field insertion and drop-rule programming, `rvu_npc.c` for MCAM enable-by-index/default indexing, CGX mailbox request types, RVU PF-to-CGX/LMAC mapping, NIX channel helpers, and debugfs-visible table lists. CN20K returns early for both MKEX hash programming and exact-match initialization, so this file primarily services pre-CN20K hardware.

Risks: the software Toeplitz implementation must match hardware bit ordering exactly or hashed IPv6 filters will miss. Hash extraction intentionally replaces full IPv6 matching with a 32-bit value under specific profiles, increasing collision risk and requiring masks to be understood by users. Exact-match update can only rewrite a MEM entry in place if the new MAC hashes to the same index; otherwise it must delete and add, which can fail if tables are full. Several exact-match paths hold `table->lock` while coordinating with MCAM enable state, so lock ordering must remain consistent. Drop-rule bookkeeping assumes CGX-only support and rejects LBK/SDP. Error paths after hardware writes and list insertion must avoid leaking table bitmap bits or seq_ids.

Test signals: validate `npc_get_field_hash_info`, IPv6 SIP/DIP filters under hash-enabled and non-hash profiles, and hardware/software hash agreement with known vectors. Exact-match tests should cover init with/without capability and exact nibble, MEM slot allocation across all ways, CAM fallback, full-table failure, MAC set/add/update/delete/reset, update that changes hash index, per-PF drop rule enable/disable as command counts cross zero, promisc enable/disable, reset by pcifunc, and debugfs table visibility. Traffic should confirm accepted programmed DMACs, dropped unknown unicast when drop rule is enabled, and no drops in promisc mode.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/marvell/octeontx2/af/rvu_npc_hash.h

Purpose: declares NPC hash-extraction and exact-match table interfaces and defines their hardware-facing configuration data. It supplies default Toeplitz keys, KEX hash register packing macros, the default IPv6 hash profile, exact-match table state structures, and the public exact-match MAC management API.

Important APIs and types: `RVU_NPC_HASH_SECRET_KEY0/1/2` define the default secret key programmed into hash and exact-match hardware. `KEX_LD_CFG_USE_HASH()` and `KEX_LD_CFG_HASH()` pack LDATA and HASH_CFG register fields; `SET_KEX_LD_HASH*()` and `GET_KEX_LD_HASH*()` macros wrap register access. `struct npc_mcam_kex_hash` stores per-interface LID/LTYPE/LD hash enable bits plus hash config, masks, and result controls. `npc_mkex_hash_default` provides default RX/TX IPv6 hash config. `struct npc_exact_table_entry` is the per-MAC software entry record, and `struct npc_exact_table` owns lock-protected bitmaps, table geometry, drop-rule metadata, promisc flags, per-way lists, CAM list, and global list. Public functions cover hash programming/calculation, exact feature detection/init/reset, exact MAC set/add/update/delete/reset, promisc toggles, feature disable checks, max-entry reporting, and drop-rule pcifunc lookup.

Control flow role: `rvu_npc.c` uses this header during NPC initialization to configure secret keys and MKEX hash state. `rvu_npc_fs.c` calls `npc_update_field_hash()` while building MCAM rules. CGX/LMAC mailbox handlers elsewhere in the AF driver call the exact-match functions when hardware exact match is enabled. Debug and management paths use max-entry and drop-rule lookup helpers.

State and persistence: the header defines the in-memory exact-match database shape and the MKEX hash profile shape; instances live under `rvu->kpu.mkex_hash` and `rvu->hw->table`. The bitmaps persist allocation state for sequence IDs, MEM table slots, and CAM table slots. Drop-rule maps persist channel/mask/pcifunc association for up to `NPC_MCAM_DROP_RULE_MAX` rules. Hardware persistence is produced by the C implementation through exact-match and hash registers.

Dependencies and integration: depends on core RVU, NPC constants, NIX interface constants, Linux list/mutex/bitmap infrastructure, Ethernet address length, and CGX mailbox request/response structures. It bridges parser/MKEX setup, flow steering, exact-match MAC management, and debugfs/reporting consumers.

Risks: the default static `npc_mkex_hash_default` is marked `__maybe_unused` but used as profile data in default KPU preparation; changing its dimensions or indices must stay synchronized with `NPC_MAX_INTF`, `NPC_MAX_LID`, `NPC_MAX_LT`, `NPC_MAX_LD`, and `NPC_MAX_HASH`. The exact-match structs mix lock-protected state with hardware table geometry; callers must respect locking implemented in the C file. `rvu_npc_exact_reset()` is declared twice, a harmless but noisy duplication that can hide prototype churn during review. Constants such as `NPC_MCAM_DROP_RULE_MAX` and `NPC_EXACT_TBL_MAX_WAYS` are hardware contract values.

Test signals: compile coverage for all prototypes, hash profile programming on hash-capable silicon, exact-match init on capable and incapable hardware, debugfs max-entry/drop-rule reporting, and CGX MAC mailbox operations that exercise every public exact-match prototype.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/marvell/octeontx2/af/rvu_reg.c

Purpose: provides a small hardware register-range validator for RVU AF code. In this file the implemented map is for NIX transmit scheduler queue register access, ensuring mailbox or debug paths only expose aligned offsets in approved scheduler-level ranges.

Important APIs and types: `struct reg_range` stores inclusive start and exclusive end offsets. `struct hw_reg_map` describes one register block selector with a register block id, range count, mask, and up to `MAX_REG_RANGES` valid ranges. `txsch_reg_map[]` defines allowed offsets for `NIX_TXSCH_LVL_SMQ`, `TL4`, `TL3`, `TL2`, and `TL1`. `rvu_check_valid_reg()` is the exported validator, taking a register map id, register block id, and register offset.

Control flow: `rvu_check_valid_reg()` first rejects offsets that are not 64-bit aligned. It then selects the map only for `TXSCHQ_HWREGMAP`; any other map id is rejected. It validates the scheduler level index, checks that the table entry's `regblk` matches the requested block, masks the register offset through the map's mask, and scans configured ranges. The function returns true only if the masked offset is greater than or equal to a range start and strictly less than that range end.

State and persistence: the only persistent state is the static read-only range table. No hardware registers are read or written here; this file is a validation gate for other code that performs register access.

Dependencies and integration: depends on Linux module/PCI includes and RVU/NIX constants from `rvu_struct.h`, `common.h`, `mbox.h`, and `rvu.h`. It integrates with mailbox/debug register access paths that need to validate transmit scheduler register offsets before servicing a request.

Risks: the table is a hardware ABI allowlist. Missing a valid range blocks legitimate diagnostics or configuration; adding too broad a range can expose unsafe registers. The mask is currently `0xFFFF` for all levels, so callers must understand that high address bits are ignored during validation. The range end is exclusive, which must match the intended register definitions. Only TX scheduler maps are supported; future register maps need explicit additions.

Test signals: unit-style tests or mailbox tests should verify rejection of unaligned offsets, unknown map ids, invalid scheduler levels, out-of-range offsets, and acceptance of each listed range boundary start with rejection at each exclusive end. Integration tests should confirm callers using this validator cannot access non-allowlisted TX scheduler registers.
