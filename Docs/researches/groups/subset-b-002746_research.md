# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/hdp/hdp_5_2_1_sh_mask.h

Purpose: generated AMDGPU HDP 5.2.1 bitfield catalog. It defines `REGISTER__FIELD__SHIFT` and `REGISTER__FIELD_MASK` constants for the HDP host data path and XDP sub-block so driver code can program HDP clock/power gating, memory-request attributes, flush/P2P BAR routing, status, IOV violation, and MMHUB error bits without hard-coded shifts.

Important APIs, types, and functions: this header exports preprocessor constants only; it has no C types, functions, storage, or executable code. The important macro families are `HDP_MMHUB_TLVL` and `HDP_MMHUB_UNITID` for transaction levels and unit IDs; `HDP_NONSURFACE_*` for non-surface aperture base, swap, VMID, and high address bits; surface/non-surface read/write flag and clear registers; `HDP_HOST_PATH_CNTL` for write-combine and stall timing; `HDP_MISC_CNTL` for early write ack, NACK/FED, simultaneous access, read watermark, channel priority, and write burst behavior; `HDP_MEM_POWER_CTRL` and `HDP_CLK_CNTL` for atomic/RC SRAM low-power and clock override fields; `HDP_MMHUB_CNTL` for RO/GCC/snoop attributes; `HDP_MEMIO_*` for indirect memory I/O transactions; and `HDP_XDP_*` fields for D2H flush commands, P2P mailbox/BAR addresses, host tap attributes, busy/sticky/check status, GPU IOV violation logs, and MMHUB response/NACK/FED error bits.

Control flow: the file itself has no control flow. Runtime flow is created by consumers such as `amdgpu/hdp_v5_2.c`, which includes this header with `hdp_5_2_1_offset.h`, reads/writes `regHDP_CLK_CNTL` and `regHDP_MEM_POWER_CTRL` through `RREG32_SOC15`/`WREG32_SOC15`, and uses `REG_SET_FIELD()` with these masks to force memory clocks on, disable HDP SRAM power modes, select exactly one LS/DS/SD mode, and then clear clock overrides. The same source reads `HDP_CLK_CNTL__*_SOFT_OVERRIDE_MASK` and `HDP_MEM_POWER_CTRL__ATOMIC_MEM_POWER_*_MASK` directly when reporting clock-gating state. Other generic HDP flush paths can combine the companion offset header with the XDP flush/status fields defined here.

State and persistence behavior: the header persists only compiled constants. The described state lives in hardware MMIO registers: sticky surface and non-surface flags, clear-on-write flag clear registers, power-gating enables, clock overrides, software semaphore contents, indirect MEMIO status/error bits, XDP flush status/counters, P2P BAR validity/address fields, IOV violation logs, and MMHUB error bits. Wrong mask or shift values become persistent driver behavior after compilation because every `REG_SET_FIELD()` and `REG_GET_FIELD()` invocation will encode or decode the wrong bits until the generated header is corrected.

Dependencies: depends on the AMDGPU register naming convention and helper macros that concatenate `REGISTER` and `FIELD` names, especially `REG_SET_FIELD`, `REG_GET_FIELD`, and SOC15 HDP register accessors. It is semantically paired with `hdp_5_2_1_offset.h`; the mask file supplies field layout while the offset file supplies `regHDP_*` addresses and `*_BASE_IDX` values. Consumers also depend on `adev->reg_offset[HDP_HWIP]`, `amdgpu_ip_version`, clock-gating flags such as `AMD_CG_SUPPORT_HDP_LS`, and the common HDP function table selected by IP discovery.

Integration points: directly included by `sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/hdp_v5_2.c`. That implementation uses the `HDP_MEM_POWER_CTRL` and `HDP_CLK_CNTL` fields to implement `hdp_v5_2_update_mem_power_gating()`, `hdp_v5_2_update_medium_grain_clock_gating()`, and `hdp_v5_2_get_clockgating_state()`. The XDP, P2P, IOV, and MMHUB error fields are exposed for lower-level register access and diagnostics in the same HDP block even when not all are used by the current C file. The header's macro names must remain aligned with generated offset names so `WREG32_FIELD15` and SOC15 access patterns can resolve both address and field metadata.

Risks and edge cases: this generated metadata is hardware-facing; an incorrect bit position can leave SRAM clock overrides asserted, enable an unintended power mode, misroute P2P BAR/mailbox traffic, or miss a sticky error. The ordering of clock/power changes matters in `hdp_v5_2.c`: clock overrides are asserted before power-mode changes and cleared afterward, so masks for `ATOMIC_MEM_CLK_SOFT_OVERRIDE` and `RC_MEM_CLK_SOFT_OVERRIDE` are high-risk. Clear/status registers such as surface flag clears, MEMIO error clears, sticky W1C fields, and IOV/MMHUB error bits should not be handled with whole-register writes unless the access semantics are understood. The HDP 5.2.1 header includes fields absent from HDP 6.0.0, such as `HDP_MMHUB_TLVL`, `HDP_MMHUB_UNITID`, `EARLY_WRACK_MISSING_PROTECT`, `SYSHUB_CHANNEL_PRIORITY`, and GPU IOV violation logs, so cross-generation copy/paste can silently target non-existent fields.

Test signals: compile coverage of `hdp_v5_2.c` is the first signal because undefined field names fail immediately. Static validation should diff every shift/mask pair against AMD's generated register database and verify mask/shift consistency for all fields used by `REG_SET_FIELD()`. Runtime signals include successful HDP LS/DS/SD transitions, clock-gating state reporting that matches programmed `cg_flags`, no hangs while toggling HDP memory power control, correct KFD HDP flush behavior, and diagnostic reads of XDP busy/sticky/error or IOV fields matching injected hardware events on HDP 5.2.1 hardware or simulator.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/hdp/hdp_6_0_0_offset.h

Purpose: generated AMDGPU HDP 6.0.0 register-offset catalog. It assigns symbolic `regHDP_*` names and matching `*_BASE_IDX` selectors to HDP registers in the `hdp_hdpdec` address block at base address `0x3c80`, covering non-surface aperture controls, flag/status registers, clock/power registers, MEMIO, direct-to-host flush controls, P2P BAR/mailbox registers, XDP status, and MMHUB error status.

Important APIs, types, and functions: this header exports constants only. There are no functions, structs, enums, or global variables. The primary API surface is the pair pattern `regHDP_REGISTER` plus `regHDP_REGISTER_BASE_IDX`. Important offsets include `regHDP_NONSURFACE_BASE`, `regHDP_NONSURFACE_INFO`, and `regHDP_NONSURFACE_BASE_HI`; flag and clear registers from `regHDP_SURFACE_WRITE_FLAGS` through `regHDP_NONSURF_FLAGS_CLR`; `regHDP_HOST_PATH_CNTL`, `regHDP_SW_SEMAPHORE`, `regHDP_OUTSTANDING_REQ`, `regHDP_MISC_CNTL`, `regHDP_MEM_POWER_CTRL`, `regHDP_MMHUB_CNTL`, `regHDP_VERSION`, and `regHDP_CLK_CNTL`; MEMIO registers at `0x00f6` through `0x00fa`; XDP D2H flush and BAR update registers at `0x0100` through `0x0123`; P2P mailbox/BAR registers at `0x0124` through `0x013b`; and XDP status/error registers through `regHDP_XDP_MMHUB_ERROR` at `0x014a`. Every listed base index is `0`.

Control flow: the header has no executable control flow. Runtime flow is indirect: `hdp_v6_0.c` includes this file and uses `RREG32_SOC15(HDP, 0, regHDP_CLK_CNTL)`, `WREG32_SOC15(HDP, 0, regHDP_CLK_CNTL, ...)`, and `regHDP_MEM_POWER_CTRL` to sequence HDP clock and SRAM power gating. That consumer has a version-specific override for HDP IP 6.1.0, where `regHDP_CLK_CNTL_V6_1` is manually defined as `0xd5`; other HDP 6.x paths use this header's `regHDP_CLK_CNTL` at `0x00d8`. Generic flush code and SDMA include paths can use this offset header to locate the XDP flush registers and counters.

State and persistence behavior: the constants do not hold state. They address persistent hardware state in the HDP MMIO register file: aperture configuration, sticky flags, software semaphore, outstanding request counts, power and clock control, indirect MEMIO transaction status/data, XDP flush arms/counters, P2P BAR mappings, frame-buffer base location, and MMHUB error latch. A bad offset or base index persists as compiled driver behavior and can redirect reads/writes to the wrong HDP register across all SOC15 register accessors.

Dependencies: depends on AMDGPU SOC15 register infrastructure. `RREG32_SOC15`, `WREG32_SOC15`, `SOC15_REG_ENTRY`, and related macros combine the register offset with the HDP hardware IP, instance, and `*_BASE_IDX` segment. It is paired with `hdp_6_0_0_sh_mask.h`, which supplies the field masks for these offsets. It also interacts with version dispatch in `amdgpu_discovery.c`, `hdp_v6_0.c`, and SDMA code that includes the header for HDP flush-related register names.

Integration points: directly included by `sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/hdp_v6_0.c`, `sdma_v6_0.c`, and `sdma_v7_0.c`. `hdp_v6_0.c` uses the clock and memory-power offsets for `hdp_v6_0_update_clock_gating()` and `hdp_v6_0_get_clockgating_state()`. The SDMA files include the offset header alongside SDMA register headers because SDMA firmware/ring paths may need HDP flush register addresses for memory visibility. The file also anchors the companion mask header: every field macro in the mask header assumes these register names and addresses refer to HDP 6.0.0 layout.

Risks and edge cases: offset drift is the dominant risk. HDP 6.0.0 places `regHDP_OUTSTANDING_REQ` at `0x00d2` and `regHDP_CLK_CNTL` at `0x00d8`, while HDP 7.0.0 moves several nearby registers; cross-generation reuse would address the wrong register. The manual 6.1.0 clock-control override in `hdp_v6_0.c` is a clue that the generated 6.0.0 offset is not universal for every HDP 6.x variant. The header has many reserved D2H slots with real offsets, so code should not infer functionality from a reserved name. All `*_BASE_IDX` values are zero; changing a base index would alter SOC15 address calculation and should be validated against the hardware register table.

Test signals: compile tests should cover every consumer include and SOC15 access using `regHDP_*` names. Static checks should diff the offset table against the vendor-generated HDP 6.0.0 register database and verify the companion mask header does not define fields for registers absent from the offset file. Runtime signals include successful HDP LS/DS/SD clock-gating transitions on HDP 6.0.0 hardware, correct handling of the HDP 6.1.0 clock-control special case, HDP flush visibility from SDMA paths, and register readback from `regHDP_VERSION`, `regHDP_XDP_BUSY_STS`, or `regHDP_XDP_MMHUB_ERROR` matching expected hardware values.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/hdp/hdp_6_0_0_sh_mask.h

Purpose: generated AMDGPU HDP 6.0.0 bitfield catalog. It maps HDP register fields to shifts and masks for host aperture attributes, flag handling, write-combine controls, HDP clock/power management, MEMIO transactions, XDP D2H flush and BAR updates, P2P mailbox/BAR state, XDP status, and MMHUB response/error reporting.

Important APIs, types, and functions: this header exports preprocessor constants only. There are no C functions, structs, or mutable objects. Its main API is the generated naming contract `HDP_REGISTER__FIELD__SHIFT` and `HDP_REGISTER__FIELD_MASK`, consumed by `REG_SET_FIELD()` and `REG_GET_FIELD()`. Important field groups include `HDP_NONSURFACE_*` base/swap/VMID bits; surface/non-surface flag and clear bits; `HDP_HOST_PATH_CNTL` write-combine timer/enables and all-surfaces disable; `HDP_MISC_CNTL` idle, outstanding write count, early write ack, NACK/FED, simultaneous access, read watermark, and write-burst controls; `HDP_MEM_POWER_CTRL` atomic/RC SRAM power mode enables, hysteresis, and delays; `HDP_CLK_CNTL` register-clock count and soft override bits; `HDP_MEMIO_CNTL`, `HDP_MEMIO_STATUS`, and data/address fields; `HDP_XDP_D2H_FLUSH` and `HDP_XDP_D2H_BAR_UPDATE` fields; P2P mailbox address and BAR valid/flush/address fields; host/MC request attribute fields; XDP flush/busy/sticky/check fields; and `HDP_XDP_MMHUB_ERROR` response/NACK/FED bits.

Control flow: the header has no executable flow. Runtime behavior appears when `hdp_v6_0.c` reads HDP registers and uses these macros to update fields. In `hdp_v6_0_update_clock_gating()`, `REG_SET_FIELD()` uses `HDP_CLK_CNTL__RC_MEM_CLK_SOFT_OVERRIDE_*` and `HDP_MEM_POWER_CTRL__ATOMIC_*`/`RC_*` fields to force clocks, disable power modes, enable one selected LS/DS/SD mode, set memory power control enables, and release the clock override. `hdp_v6_0_get_clockgating_state()` reads `regHDP_MEM_POWER_CTRL` and tests the `ATOMIC_MEM_POWER_LS_EN`, `ATOMIC_MEM_POWER_DS_EN`, and `ATOMIC_MEM_POWER_SD_EN` masks. XDP/MEMIO/P2P fields define possible runtime decode/programming paths for generic HDP and diagnostics code.

State and persistence behavior: the file stores no runtime state. It describes state held by HDP hardware: non-surface aperture address and VMID, sticky read/write flags, host-path write-combine configuration, power-gating controls, clock overrides, MEMIO transaction progress and errors, flush commands/counters, P2P BAR address validity, and MMHUB response status. Some fields are control bits, some are status bits, and some are clear-on-write style fields; the header does not encode access permissions or ordering requirements, so consumers must know register semantics.

Dependencies: paired with `hdp_6_0_0_offset.h` for register addresses and base indexes. Depends on AMDGPU's generated field-name convention and helper macros in the SOC15/register-access layer. It is directly tied to `hdp_v6_0.c` and to the HDP function table selected through IP discovery. Because `hdp_v6_0.c` manually handles an HDP 6.1.0 `regHDP_CLK_CNTL` offset variant while still using the same `HDP_CLK_CNTL` field layout, this mask header also implicitly supports that compatible field layout.

Integration points: directly included by `sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/hdp_v6_0.c`. That file uses the `HDP_MEM_POWER_CTRL` and `HDP_CLK_CNTL` field definitions to implement clock-gating update and reporting. The same mask names can be used by `WREG32_FIELD15`, `REG_SET_FIELD`, and `REG_GET_FIELD` callers wherever HDP 6.0.0 registers are accessed. The XDP field groups align with `sdma_v6_0.c` and `sdma_v7_0.c` inclusion of the offset header for HDP flush coordination, even though those files do not directly include this mask file.

Risks and edge cases: the HDP 6.0.0 layout is close to but not identical with HDP 5.2.1 and 7.0.0. This file lacks 5.2.1/7.0.0 fields such as `HDP_MMHUB_TLVL`, `HDP_MMHUB_UNITID`, `EARLY_WRACK_MISSING_PROTECT`, `SYSHUB_CHANNEL_PRIORITY`, GPU IOV violation logs, and HDP 7.0.0 MMHUB error-clear fields. Incorrectly reusing those fields in HDP 6 code will fail to compile or, worse, if open-coded, touch undefined bits. `HDP_MEM_POWER_CTRL` and `HDP_CLK_CNTL` masks are high-risk because a bad field can leave clocks forced on/off or enable multiple SRAM power modes. Error/status fields such as `HDP_XDP_STICKY` and `HDP_XDP_MMHUB_ERROR` should be accessed with correct clear semantics rather than blind full-register writes.

Test signals: compile coverage of `hdp_v6_0.c` validates the active `REG_SET_FIELD()` and mask-test references. Static validation should confirm every mask is contiguous at its shift and matches the generated hardware register source. Runtime signals include correct HDP clock-gating flag reporting, stable suspend/resume or power-management transitions with HDP LS/DS/SD enabled, successful HDP flush visibility for SDMA and CPU/GPU synchronization paths, and expected status/error decoding when MEMIO, XDP busy/sticky, or MMHUB response errors are injected on HDP 6.0.0 hardware.

State and persistence behavior: the constants are compile-time metadata only. They address hardware state in HDP 7.0.0 registers: transaction-level IDs, non-surface aperture state, sticky flags, host-path controls, outstanding request counters, SRAM power modes, clock overrides, MMHUB attribute controls, busy/error/error-clear latches, MEMIO transaction state, D2H flush state, P2P BAR mappings, frame-buffer base location, and IOV violation records. Dependencies: depends on AMDGPU SOC15 HDP register access infrastructure and the companion `hdp_7_0_0_sh_mask.h`. Reserved D2H slots are present as named offsets but should not be treated as documented control registers. Since all base indexes are zero, any future split across SOC15 segments would require coordinated generated-header and access-layer validation.

Test signals: compile coverage of `hdp_v7_0.c` verifies the active clock/power register names. Static validation should compare every offset against the HDP 7.0.0 register database and specifically check the moved control/status offsets against HDP 6.0.0 to prevent accidental reuse. Runtime signals include successful HDP LS/DS/SD transitions, correct clock-gating state reporting, readable HDP version at `regHDP_VERSION`, correct XDP busy and MMHUB error/error-clear behavior, and IOV violation log fields matching injected SR-IOV or virtualization fault scenarios.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/hdp/hdp_7_0_0_sh_mask.h

Purpose: generated AMDGPU HDP 7.0.0 bitfield catalog. It supplies shift and mask constants for HDP 7 register fields, including MMHUB transaction metadata, aperture flags, host path controls, clock/power gating, MMHUB controls and overrides, XDP busy/error/error-clear latches, MEMIO, D2H flush commands, P2P BAR/mailbox state, XDP sticky/check/frame-buffer fields, and GPU IOV violation logs.

Important APIs, types, and functions: this header exports preprocessor constants only. There are no functions, structs, or mutable variables. Important field families include `HDP_MMHUB_TLVL` and `HDP_MMHUB_UNITID`; non-surface base/swap/VMID fields; surface/non-surface flag and clear bits; `HDP_HOST_PATH_CNTL` write-combine and stall fields; `HDP_MISC_CNTL` early write ack, missing-protect, NACK/FED, simultaneous read/write, channel priority, and write burst fields; `HDP_MEM_POWER_CTRL` atomic/RC SRAM LS/DS/SD, power-control, hysteresis, and delay fields; `HDP_CLK_CNTL` soft override bits; `HDP_MMHUB_CNTL` RO/GCC/snoop bits plus override bits; `HDP_XDP_BUSY_STS` busy bits and `Z_FENCE_BIT`; `HDP_XDP_MMHUB_ERROR` and `HDP_XDP_MMHUB_ERROR_CLR` response, FED, and NACK status/clear bits; `HDP_MEMIO_*` transaction fields; `HDP_XDP_D2H_FLUSH` and BAR update fields; P2P mailbox and BAR fields; `HDP_XDP_HDP_MC_CFG` override/request fields; and IOV violation address/opcode/VF/VFID/initiator fields.

Control flow: the header itself has no executable flow. `hdp_v7_0.c` creates runtime behavior by using `REG_SET_FIELD()` with `HDP_CLK_CNTL` and `HDP_MEM_POWER_CTRL` fields. Its clock-gating path forces the RC memory clock on, clears all atomic/RC power control and LS/DS/SD enable bits, optionally enables a single supported SRAM mode, sets atomic and RC power control enable bits, and then clears the clock override. The get-state path reads `regHDP_MEM_POWER_CTRL` and tests atomic LS/DS/SD masks. Diagnostic and recovery paths can decode `HDP_XDP_BUSY_STS`, `HDP_XDP_MMHUB_ERROR`, `HDP_XDP_MMHUB_ERROR_CLR`, and GPU IOV fields when reading the companion offsets.

State and persistence behavior: the file has no state of its own. It describes fields in persistent HDP hardware state: power/clock controls, MMHUB attribute overrides, sticky busy/error/error-clear bits, MEMIO progress and errors, D2H flush controls, P2P BAR validity/address/flush values, frame-buffer base, and virtualization violation records. Several fields are status or clear-on-write style latches; this header exposes bit layout but does not communicate read-only, write-one-to-clear, or ordering semantics.

Dependencies: paired with `hdp_7_0_0_offset.h` and AMDGPU helper macros `REG_SET_FIELD`, `REG_GET_FIELD`, and SOC15 HDP accessors. It depends on the generated naming convention being exact; macro users synthesize names from register and field tokens. It is selected through HDP 7 IP integration in `amdgpu_discovery.c` and included by `hdp_v7_0.c`.

Integration points: directly included by `sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/hdp_v7_0.c`. The active consumer uses `HDP_MEM_POWER_CTRL` and `HDP_CLK_CNTL` fields to implement HDP clock-gating update and reporting. The larger field set supports lower-level register diagnostics for HDP 7-specific busy/error clear and IOV violation behavior. `HDP_MMHUB_CNTL` adds RO/GCC/snoop override fields compared with older layouts, and `HDP_XDP_HDP_MC_CFG` adds request-attribute override fields, which are integration points for memory attribute policy if future code chooses to program them.

Risks and edge cases: HDP 7.0.0 is not a drop-in mask replacement for HDP 6.0.0. It adds MMHUB TLVL/UNITID, MMHUB control override fields, `HDP_XDP_MMHUB_ERROR_CLR`, and GPU IOV logs; it also omits the late `HDP_XDP_BUSY_STS` block present in older generated layouts because busy status is now in the low control/status window. The `HDP_XDP_GPU_IOV_VIOLATION_LOG__VFID_MASK` is `0x01F00000`, wider than the HDP 5.2.1 VFID mask, so virtualization diagnostics must use the generation-specific header. Clock/power fields are high-risk because wrong masks can leave the block in an unsafe power state. Error-clear fields must be written carefully to avoid clearing unrelated latched diagnostics.

Test signals: compile coverage of `hdp_v7_0.c` validates the masks used in active clock/power paths.
