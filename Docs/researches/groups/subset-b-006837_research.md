# sources/distributed-fs/ceph-client/tools/testing/selftests/hid/tests/test_multitouch.py

Purpose: Provides the Linux HID selftest coverage for `hid-multitouch`. It builds many synthetic UHID multitouch devices from real report descriptors, loads the `hid-multitouch`/`hid_multitouch` kernel module through the shared test harness, injects touch reports, and verifies the evdev nodes, slots, key events, feature reports, quirks, timeout releases, hover behavior, palm/confidence behavior, and Precision Touchpad button behavior that the kernel exposes.

Important APIs, types, and fixtures: `KERNEL_MODULE` declares the module dependency. `BIT()` and `mt_quirks` mirror the driver's quirk flags so fixture declarations can sanity-check expected quirk names. `Data` is an attribute bag passed to hid-tools report creation. `Touch` models a finger contact with contact id, position, center/tool coordinates, tip switch, confidence, pressure, azimuth, in-range, width, and height fields. `Pen` extends `Touch` with stylus-specific fields but is not central to the current assertions. `Digitizer` extends `base.UHIDTestDevice` and owns the generic touch device behavior: descriptor selection, max-contact discovery, input-mode switching, contact-max feature report handling, and report emission. `HIDButtonType` describes clickpad, pressurepad, and discrete-button touchpads. `PTP` extends `Digitizer` with persisted click/left/right button state and appends button fields to each report. `MinWin8TSParallel`, `MinWin8TSHybrid`, and `Win8TSConfidence` generate compact Windows 8 touch-screen descriptors used as controlled fixtures. `SmartTechDigitizer` wraps a complex real descriptor and overrides report selection and evdev matching because the device exposes multiple touch-screen application collections.

Control flow: Each pytest class inherits from `base.BaseTestCase.TestUhid` through `BaseTest.TestMultitouch`, creates one UHID device in `create_device()`, then uses the inherited harness to bind it to the kernel, locate the right evdev node, send reports, and drain synchronized event frames. `Digitizer.__init__()` parses feature reports and input reports to infer `max_contacts`, current application collection, physical collection, and available input fields. `Digitizer.event()` increments `scantime`, trims the outgoing slot list to `max_contacts`, sets `Contact Count`, creates one or more HID input reports using `create_report()`, submits them through `call_input_event()`, and clears contact count after the first report in a split/hybrid sequence. `get_report()` answers feature report requests for `Contact Max`; `set_report()` watches `Inputmode` feature reports and switches the active report application between mouse, touch screen, and touch pad, including an Elan duplicate-input-mode fallback. `PTP.event()` updates sticky button state before delegating to `Digitizer.event()`, which lets split reports omit button fields without losing pressed state.

Core test flow: `test_creation()` verifies that the kernel creates the expected evdev node, the slot count matches `max_contacts`, and initial multitouch tracking IDs are released. `test_required_usages()` and `test_required_usages8()` validate HID usage placement for `Contact Max` and `Inputmode`. Single-, dual-, triple-, and maximum-contact tests assert `BTN_TOUCH`, `ABS_MT_TRACKING_ID`, and `ABS_MT_POSITION_X/Y` slot state through normal press and release sequences, with slot selection adjusted for `SLOT_IS_CONTACTID`, `SLOT_IS_CONTACTID_MINUS_ONE`, and `SLOT_IS_CONTACTNUMBER`. Additional shared tests exercise accurate contact-count truncation, Tx/Cx tool-coordinate handling, in-range hover distance, duplicate contact-id suppression, driver-generated release after a 100 ms missed release timeout, and azimuth-to-orientation conversion. PTP-specific tests check input properties for clickpads/pressurepads, reliable `BTN_LEFT`/`BTN_RIGHT` reporting across button styles, confidence/palm conversion or release behavior, and preservation of button state across hybrid multi-report contact sequences. Confidence-specific regressions check non-confident releases and sticky-finger cleanup when only one of several touches is explicitly released.

Fixture matrix and integration points: The bottom two thirds of the file is a source-tree-aligned fixture matrix of vendor/product descriptors. The Windows 7-compatible classes inherit `BaseTest.TestMultitouch`; the Windows 8-compatible classes inherit `BaseTest.TestWin8Multitouch` or `BaseTest.TestPTP`. Each fixture passes a raw HID report descriptor plus optional `BusType`, vendor id, product id, `max_contacts`, `physical`, `buttontype`, and expected quirk tuple into `Digitizer`, `PTP`, or `SmartTechDigitizer`. Covered device families include 3M, ActionStar, ASUS, Atmel, Cando, CVTouch, Cypress, Data Modul, E4, eGalax, Elo, FlatFrog, FocalTech, Hanvon, Huitoo, Ideacom, Ikaist, IRM/IRTouch, LG, Lumio, Nexio, PenMount, PixArt, PQ Labs, Quanta, Rafi, RNDPLUS, Sitronix, SmartTech, Stantum, TopSeed, TPV, TRS-Star, Unitec, Zytronic, Elan, Dell, Ilitek, ITE, N-Trig, Sharp, SiPoDev, and Synaptics. `input_info` is important because the kernel driver applies many quirks by bus/vendor/product match, so these tests validate both descriptor parsing and ID-driven driver behavior.

State and persistence behavior: Test device state is intentionally small but important. `Digitizer.scantime` monotonically increments unless a split report asks to reuse it. `Digitizer.cur_application` persists across feature `Inputmode` writes and controls which application collection emits reports. `Digitizer.max_contacts`, `physical`, `fields`, and `quirks` are computed at construction and then used by skip predicates and slot assertions. `PTP` persists click, left, and right button states across reports so the synthetic device can model touchpads whose later hybrid packets only contain contacts. The evdev side persists slot tracking IDs, positions, button values, input properties, and absolute axis metadata; assertions read that state after each synchronized event frame. Timed tests rely on the kernel driver's own delayed release timer, using `time.sleep(0.2)` to observe generated release events.

Dependencies: The file depends on the local HID selftest harness in `.base`, hid-tools report parsing/generation (`hidtools.hut.HUT`, `hidtools.util.BusType`, `base.UHIDTestDevice`), `libevdev` for event constants and evdev state inspection, `pytest` for fixtures and skip predicates, and the kernel's UHID, hid-multitouch, input, and power-management paths. It also depends on hid-tools' descriptor parser understanding the raw descriptors and usage names exactly as referenced in skip predicates and report data fields.

Risks and maintenance notes: This suite is sensitive to kernel behavior, descriptor parser behavior, and input ABI details. Several tests intentionally encode current driver behavior, such as duplicate contact-id suppression and timeout release timing, that may need updates if the kernel changes semantics. Many descriptors are huge opaque hex strings; regressions are easy to introduce when updating them because most semantic intent is only visible through later assertions and quirk tuples. Skip predicates depend on usage-name strings such as `In Range`, `Confidence`, `Azimuth`, and `X`; parser naming changes can alter coverage without obvious test edits. Timed release tests can be flaky on overloaded systems because they depend on a 100 ms kernel timer and sleep for 200 ms. The `TestPS3Controller`-style indentation issue is not present here, but there is an extra blank line before one decorator near `TestWin8TSConfidence`; it is harmless but shows the file is manually curated. Some fixtures omit `input_info`, relying on default USB `(1, 2)`, so they validate generic descriptor behavior rather than ID-specific quirks.

Test signals: Passing this file means the kernel accepted every synthetic descriptor, created the expected evdev node and slot count, honored contact max and input mode feature reports, mapped contacts into correct slots, generated stable tracking IDs, ignored duplicate contacts when expected, preserved hover and palm/confidence semantics, converted azimuth to orientation, emitted delayed releases, and reported PTP button properties/events correctly. Strong regression signals are failures in `test_creation()` for descriptor or binding changes, slot/tracking assertions for contact assignment changes, `test_mt_release_miss()` and confidence multi-release failures for timer/sticky-finger regressions, and PTP button failures for split-report state handling. Useful extension tests would add explicit assertions for pressure/width/height scaling, more stylus paths using `Pen`, and targeted tests for each quirk in `mt_quirks` that currently appears only in fixture metadata.

# sources/distributed-fs/ceph-client/tools/testing/selftests/hid/tests/test_sony.py

Purpose: Provides HID selftest coverage for Sony PlayStation controllers. It validates PS3, PS4 DualShock 4, and PS5 DualSense UHID emulation against the kernel `hid_sony` and `hid_playstation` drivers, reusing the shared gamepad tests and adding Sony-specific checks for calibrated motion sensors, battery/power-supply reporting, touchpad multitouch behavior, PS3 startup, and LED output handling.

Important APIs, types, and fixtures: `PS3_MODULE`, `PS4_MODULE`, and `PS5_MODULE` declare the kernel modules expected for the tested controller generations. `SonyBaseTest.SonyTest` inherits the generic gamepad assertions from `.test_gamepad.BaseTest.TestGamepad`. `SonyBaseTest.SonyPS4ControllerTest` adds reusable PS4/PS5 tests for accelerometer, gyroscope, battery, and touchpad behavior. Controller fixtures come from `hidtools.device.sony_gamepad`: `PS3Controller`, `PS4ControllerBluetooth`, `PS4ControllerUSB`, `PS5ControllerBluetooth`, `PS5ControllerUSB`, and `PSTouchPoint`. `application_matches` is assigned onto each controller instance so the shared harness can match application collections to evdev nodes. `CalibratedPS4Controller` and `CalibratedPS5Controller` provide deterministic accelerometer and gyroscope calibration coefficients that are mixed into the USB and Bluetooth controller classes.

Control flow: Each concrete test class constructs a hid-tools controller object in `create_device()`, attaches `application_matches`, and lets the shared UHID/gamepad harness bind it to the kernel. Sensor tests call `uhdev.event(accel=...)` or `uhdev.event(gyro=...)`, drain the `"Accelerometer"` evdev node with `next_sync_events()`, and compare the resulting `ABS_X/Y/Z` or `ABS_RX/RY/RZ` value with the requested physical value after kernel calibration. Battery tests mutate the emulated controller battery object, emit a report, and read the associated power-supply test abstraction. Touchpad tests create `PSTouchPoint` objects, emit one- and two-contact reports, and inspect the `"Touch Pad"` evdev node's multitouch slots. PS3 startup uses an autouse fixture to press the PS button before tests and drain pending udev events.

State and persistence behavior: Controller instances own mutable sensor, battery, LED, button, and touch state inside hid-tools. The battery object persists `capacity`, `cable_connected`, and `full` values across events until changed. The kernel-created power-supply class persists capacity/status and is read after reports. Motion sensor calibration data is class-level static data mixed into each calibrated controller type so test expectations do not depend on future hid-tools calibration changes. Touchpad slot state persists in evdev slots across frames, with tracking IDs expected to remain stable while touches are held and become `-1` after release. PS3 LED class state is kernel-exposed and mirrored back into the emulated hardware LED model after dispatching output reports.

Dependencies and integration points: The file depends on the local base helpers, the generic gamepad test base, hid-tools Sony controller models, `BusType`, `libevdev`, and pytest. It integrates with multiple kernel subsystems: HID report parsing, `hid_sony`, `hid_playstation`, evdev gamepad nodes, evdev accelerometer and touchpad nodes, power-supply class devices, and LED class output reports. USB and Bluetooth variants share the same behavioral tests but differ in report format, bus type, calibration feature report id, and battery discharge expectations.

Risks and maintenance notes: Sensor assertions intentionally allow tolerances because controller reports are quantized and the kernel applies inverse calibration followed by driver calibration; accelerometer tests allow plus or minus 1 and gyroscope tests allow plus or minus 64. Calibration dictionaries duplicate processed kernel calibration values; they protect tests from hid-tools changes, but they must be updated when controller fixture feature reports or kernel calibration algorithms intentionally change. Battery behavior differs by bus: discharging status is only asserted for Bluetooth, while charging/full paths are common. Touchpad tests assume two slots and specific synthetic tracking ID assignment starting at zero. A notable risk is that `test_led` appears nested inside the `start_controller` fixture due to indentation, so pytest will not collect it as an independent PS3 test unless that indentation is intentional for another mechanism; this should be reviewed if LED coverage is expected.

Test signals: Passing tests show that PS4/PS5 sensor reports round-trip through kernel calibration into expected evdev axes, battery capacity and status are reflected through power-supply state, touchpad contacts produce correct `BTN_TOUCH`, slot tracking IDs, and positions, and PS3 devices can be initialized by a PS-button press. Strong failure signals include missing `"Accelerometer"` or `"Touch Pad"` evdev nodes, values outside calibration tolerances, incorrect Bluetooth charging/discharging status, touch release leaving stale tracking IDs, or PS3 startup failing to drain events. Useful extensions would explicitly collect and validate PS3 LED behavior, assert USB and Bluetooth report differences around feature reports, and add PS5-specific touchpad or adaptive-trigger output coverage if hid-tools and the kernel expose stable hooks.
