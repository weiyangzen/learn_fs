# File Research: sources/os/plan9/9front/sys/src/cmd/audio/libvorbis/books/uncoupled/res_books_uncoupled.h

This is an autogenerated Xiph.Org Vorbis static-codebook header for uncoupled residue encoding profiles. It includes `codebook.h` and then defines only file-local `static const` data: no functions, no macros, and no include guard. The no-guard pattern is deliberate for these generated book headers: they are included into mode/template headers that need the resulting `static` objects in the same translation unit.

The file contains residue vector-quantization books and phrase/Huffman books for uncoupled Vorbis modes named around sample-rate/profile families: `8u*`, `16u*`, `44u*`, and `44un1`. Each VQ book is represented by a quantized value list (`_vq_quantlist_*`), a Huffman code length list (`_vq_lengthlist_*`), and a `static_codebook` descriptor. The descriptor fields match `static_codebook` from `codebook.h`: vector dimension, entry count, length list, map type, packed minimum/delta values, quantization bit width, sequence flag, quant list pointer, and allocation flag.

Whole-file structure:
- 219 `static_codebook` descriptors total.
- 190 residue/VQ books, all using maptype 1 implicit value mapping.
- 29 phrase/Huffman-only books, all using maptype 0 and `NULL` quant lists.
- The Huffman-only set is split into 13 `long`, 13 `short`, and 3 `single` phrase books.
- Dimensions include scalar, 2-vector, and 4-vector books; most higher-stage residue vectors are dimension 2, while early pass books often use dimension 4.
- Entry counts range across small phrase tables and lattice sizes including 25, 49, 64, 81, 100, 121, 169, 225, 289, 361, 441, and 625.

Integration path:
- `modes/residue_44u.h` includes this file directly.
- That mode file groups these `static_codebook` objects into `static_bookblock` arrays such as `_resbook_44u_0` through `_resbook_44u_9` and `_resbook_44u_n1`.
- The same mode file combines phrase books like `_huff_book__44u0__short` / `_huff_book__44u0__long` with residue bookblocks in `vorbis_residue_template` arrays.
- `modes/setup_44u.h` includes `modes/residue_44u.h`; `vorbisenc.c` includes the setup and consumes the templates when selecting encoder modes.
- Runtime initialization later turns these static descriptors into active `codebook` instances via `vorbis_book_init_encode()` / `vorbis_book_init_decode()` from `sharedbook.c`, while `codebook.c` packs/unpacks/uses the bitstream representation.

The data has no executable control flow. The important behavior is encoded in the numeric tables: zero code lengths mark unused codebook entries; nonzero lengths drive canonical codeword generation; maptype 1 plus the quant list drives lattice dequantization. Because these books are compile-time constants, corruption or accidental edits are the main risk. A single changed length or quant value can silently alter encoder output compatibility or degrade decode/encode behavior.

# File Research: sources/os/plan9/9front/sys/src/cmd/audio/libvorbis/codebook.c

This file implements Vorbis codebook bitstream serialization and runtime encode/decode operations. It depends on Ogg bitpacking (`ogg/ogg.h`), Vorbis public codec types, `codebook.h`, scaling helpers, memory helpers from `misc.h`, and portability macros from `os.h`.

Main routines:
- `vorbis_staticbook_pack()` writes a `static_codebook` to an Ogg packet buffer. It emits the Vorbis codebook sync pattern `0x564342`, dimensions, entry count, length-list encoding, map type, and quantization metadata/list for maptypes 1 and 2.
- `vorbis_staticbook_unpack()` reads the packed form back into an allocated `static_codebook`, validating sync, dimensions/entries bit budget, ordered/unordered length-list encoding, map type, quantization bit budget, and EOF conditions.
- `vorbis_book_encode()` writes a codeword from an initialized runtime `codebook`.
- `decode_packed_entry_number()` is the central decode helper. It uses a first-stage lookup table (`dec_firsttable`) where possible, then falls back to bit-reversed binary search over ordered codewords.
- `vorbis_book_decode()` returns the original entry number via `dec_index`.
- `vorbis_book_decodevs_add()`, `vorbis_book_decodev_add()`, `vorbis_book_decodev_set()`, and `vorbis_book_decodevv_add()` decode vector values and add/set them into mono, vector, or channel-interleaved output buffers.

Serialization behavior:
- Codeword lengths can be packed in ordered or unordered form. Ordered books store the initial length and run counts per length; unordered books either store all lengths directly or store a used/unused bit before each nonzero length.
- Maptype 0 has no value mapping.
- Maptype 1 stores a compact implicit lattice quant list sized by `_book_maptype1_quantvals()`.
- Maptype 2 stores an explicit `entries * dim` quant list.
- Unsupported map types return errors on pack/unpack.

Decode behavior:
- The bitstream is LSB-packed, but the optimized decode path needs MSB-first comparisons, so `bitreverse()` is used before binary-search comparison.
- The first table either maps directly to an entry or encodes a search interval using high-bit tagging.
- On decode miss or EOF, functions return `-1`; otherwise vector decode routines use `book->valuelist + entry * book->dim`.

Integration points:
- `info.c` calls `vorbis_staticbook_unpack()` while reading setup headers and `vorbis_staticbook_pack()` while writing them.
- `block.c` initializes runtime encode/decode `codebook` arrays from `static_codebook` descriptors.
- `res0.c`, `floor0.c`, and `floor1.c` call the decode/encode helpers for residue and floor data.
- `sharedbook.c` owns memory cleanup, value-list generation, codeword generation, and decode lookup table construction used by this file.

Risk and edge cases:
- The unpacker performs several explicit bounds checks against remaining packet storage before allocating and reading large lists, which is important for malformed stream handling.
- Allocation failures are not consistently checked after `malloc()` / `_ogg_malloc()` in this older C code path.
- Vector decode routines assume upper layers guard dimension granularity; the comments explicitly say most callers must ensure `n` is compatible with `book->dim`.
- `vorbis_book_decodevs_add()` allocates temporary arrays per call, so hot residue decode paths may be sensitive to allocator behavior.
- `vorbis_book_encode()` assumes the runtime codebook was initialized correctly and writes `lengthlist[a]` bits from `codelist[a]`.

Testing/review signals:
- Exercise setup-header round trips: static book pack, unpack, init decode, clear.
- Fuzz malformed setup packets around ordered length runs, unused-entry tags, maptype 1/2 quant lengths, zero dimensions, and truncated packets.
- Decode tests should cover first-table direct hits, first-table interval fallback, single-entry books, sparse books with `dec_index`, and vector add/set paths used by floor and residue backends.

# File Research: sources/os/plan9/9front/sys/src/cmd/audio/libvorbis/codebook.h

This header defines the shared static and runtime codebook data structures used by the Plan 9/9front import of libvorbis, plus prototypes for packing, unpacking, initialization, lookup, quantization, encode, decode, and cleanup helpers. It includes `ogg/ogg.h` for Ogg integer and bitpacking types.

Key types:
- `static_codebook` is the compact, declarative codebook form used in generated book headers and Vorbis setup packets. It stores vector dimension, entry count, a codeword-length list, map type, quantization parameters, quant list, and an `allocedp` ownership flag.
- `codebook` is the initialized runtime form. It stores dimensions, entry counts, a pointer back to the static descriptor, generated value/codeword lists, decode lookup structures, first-table metadata, maximum decode length, and encoder lattice helper fields.

Important fields:
- `static_codebook.lengthlist` is the canonical-code source; zero lengths mean unused entries.
- `static_codebook.maptype` selects no mapping, implicit lattice mapping, or explicit value mapping.
- `q_min`, `q_delta`, `q_quant`, and `q_sequencep` define value dequantization semantics.
- `codebook.valuelist` holds dequantized float vectors.
- `codebook.codelist`, `dec_index`, `dec_codelengths`, `dec_firsttable`, `dec_firsttablen`, and `dec_maxlength` are generated by initialization and consumed by encode/decode operations.

Declared functions fall into these groups:
- Lifecycle/init: `vorbis_staticbook_destroy()`, `vorbis_book_init_encode()`, `vorbis_book_init_decode()`, `vorbis_book_clear()`.
- Quantization/value helpers: `_book_unquantize()`, `_book_logdist()`, `_float32_unpack()`, `_float32_pack()`, `_book_maptype1_quantvals()`, `_best()`, `vorbis_book_besterror()`.
- Runtime encode helpers: `vorbis_book_codeword()`, `vorbis_book_codelen()`, `vorbis_staticbook_pack()`, `vorbis_book_encode()`.
- Runtime decode helpers: `vorbis_staticbook_unpack()`, `vorbis_book_decode()`, `vorbis_book_decodevs_add()`, `vorbis_book_decodev_set()`, `vorbis_book_decodev_add()`, `vorbis_book_decodevv_add()`.

Integration points:
- Generated headers such as `books/uncoupled/res_books_uncoupled.h` instantiate `static_codebook` objects using this layout.
- `sharedbook.c` implements initialization, dequantization, and cleanup routines declared here.
- `codebook.c` implements setup-packet pack/unpack and decode/encode routines declared here.
- Floor/residue codec backends call the decode helpers through this API after `block.c` has initialized `codec_setup_info.fullbooks`.

Risk and maintenance notes:
- The structure layout is ABI-significant inside this libvorbis source tree because generated static tables use positional initializers rather than named fields.
- Changing field order or type width would break generated book headers and setup serialization.
- Ownership is mixed: generated static books set `allocedp` to 0, while unpacked books set it to 1; cleanup must respect that distinction.
- Several helpers are internal by naming convention (`_book_*`, `_float32_*`) but are declared here for cross-file use within the library.

Testing/review signals:
- Compile-time breakage is likely if field layout and generated books diverge.
- Runtime tests should initialize generated maptype 0 and maptype 1 books, verify clear/destroy ownership behavior, and cover all public prototypes through floor/residue encode/decode paths.
