# sources/storage-engines/rocksdb/db/compaction/tiered_compaction_test.cc research

Purpose: `tiered_compaction_test.cc` is the RocksDB regression suite for tiered storage and "preclude last level" compaction behavior. It validates that data can be split between a proximal/hot level and the last/cold level based on sequence number, preserved write time, `TimedPut` timestamps, snapshots, range tombstones, and compaction style. It also verifies iterator write-time reporting from memtables, SSTs, and merge results.

Important APIs, types, and fixtures: `TieredCompactionTest` extends `DBTestBase` and installs sync-point overrides for `Compaction::SupportsPerKeyPlacement`, `CompactionJob::PrepareTimes():preclude_last_level_min_seqno`, and compaction stats collection. Its helpers read `InternalStats::CompactionStats`, per-key-placement stats, and assert `CompactionJobStats`. `SetColdTemperature()` assigns `Options::last_level_temperature = Temperature::kCold`. `SingleKeySstPartitioner` forces a file boundary after every key, while `ThreeRangesPartitioner` splits output at `Key(20)` and `Key(40)` to exercise range-sensitive placement. `PrecludeLastLevelTestBase` supplies a `MockSystemClock`, composite env, dynamic/static option mutation through `SetOptions`/`SetDBOptions` or reopen, and periodic task scheduler clock injection. Parameterized suites cover dynamic vs reopen config, universal vs leveled compaction, write protection bytes, tailing vs non-tailing iterators, and enabled vs disabled preclude behavior.

Control flow: the early `TieredCompactionTest` cases build overlapping SSTs through repeated `Put`/`Flush`, drive automatic or manual compaction, change the cold cutoff through sync-point-injected sequence numbers, and assert `FilesPerLevel()` plus SST size by `Temperature`. Universal and leveled tests both confirm that cold data lands in the last level, hot data stays in or migrates to the proximal level, and unsafe cold-to-hot migration is blocked when internal key ranges or bottommost sequence-zeroing would lose ordering information. Range deletion cases hold snapshots, add tombstones spanning hot and cold records, compact repeatedly, and verify both logical reads and `COMPACTION_RANGE_DEL_DROP_OBSOLETE` counters.

State and persistence behavior: these tests are heavily stateful. They depend on MANIFEST level metadata, SST temperature, internal sequence numbers, `seqno_to_time_mapping` table properties, snapshots preserving obsolete versions/range tombstones, and compaction statistics accumulated in `InternalStats`. Mock time controls write-time eligibility for `preclude_last_level_data_seconds` and `preserve_internal_time_seconds`. Compaction can rewrite files to L5/L6, move files directly with `MoveFilesToLevel`, split files through partitioners, or avoid output in a level when placement would overlap unsafe ranges.

Dependencies and integration points: the file integrates with `DBTestBase`, `DBImpl` test hooks, `SyncPoint`, `MockSystemClock`, compaction internals (`Compaction`, `CompactionJobStats`, `CompactionReason`, proximal output ranges), table-property collectors (`CompactForTieringCollectorFactory`), range deletion handling, `TimedPut`, `MergeOperators::CreateStringAppendOperator`, and DB iterator properties. It is a black-box/white-box hybrid: most assertions use public DB operations and metadata APIs, but critical timing and placement are forced through internal test hooks.

Risks and edge cases covered: tests defend against data being placed in cold files while a hotter range tombstone in the proximal level would hide it, range deletion endpoints changing file ranges enough to overlap existing files, concurrent last-level-only compactions colliding with proximal-level work, periodic compaction racing with preclude placement, and migration from older preserve-time settings after enabling preclude dynamically. They also cover imprecision in sequence-to-time conversion, `TimedPut` preferred sequence numbers protected by snapshots, seqno-zeroed last-level data returning write time zero, and merged values reporting the base value's write time.

Test signals: pass/fail signals are concrete file-layout strings like `0,0,0,0,0,1,1`, SST byte totals by `Temperature`, live file metadata including `num_deletions`, `num_range_deletions`, file endpoints and levels, stats counters, exact logical reads with and without snapshots, and iterator property values decoded from `rocksdb.iterator.write-time`. Disabled range-based tiering tests document unfinished or unsafe functionality and should be read as design notes rather than active guarantees.

# sources/storage-engines/rocksdb/db/comparator_db_test.cc research

Purpose: `comparator_db_test.cc` validates RocksDB DB behavior under several comparator implementations and block-based table format versions. It checks that writes, deletes, point lookups, forward/backward iteration, separator generation, and successor detection honor the configured comparator rather than assuming bytewise key order.

Important APIs and types: `KVIter` adapts an in-memory `stl_wrappers::KVMap` into the RocksDB `Iterator` interface so DB iteration can be compared against a reference model ordered by `stl_wrappers::LessOfComparator(kTestComparator)`. `DoRandomIteraratorTest()` performs random puts/deletes/flushes, then runs random `SeekToFirst`, `SeekToLast`, `Seek`, `SeekForPrev`-equivalent behavior through `Prev`, `Next`, and `Get` comparisons. Custom comparators include `DoubleComparator` (numeric double order with string tie-break), `HashComparator` (hash order with string tie-break), and `TwoStrComparator` (two length-prefixed string components). `ComparatorDBTest` owns the DB path, table factory, comparator lifetime, and parameterized block format version.

Control flow: each comparator test installs the comparator into `Options`, recreates the DB, generates deterministic key populations with `Random`, mutates the DB, flushes at configured intervals, and compares DB state against the model iterator. The test suite runs for default and latest block-based table format versions. Later tests target comparator helper methods directly: `IsSameLengthImmediateSuccessor`, `FindShortestSeparator`, and `FindShortSuccessor` for bytewise and reverse bytewise comparators, including randomized byte strings and boundary bytes.

State and persistence behavior: every test creates an isolated per-thread DB path and destroys it in the fixture destructor. Persistent state consists of memtables and flushed block-based SSTs created under the current comparator. The global `kTestComparator` is used only by test helpers and reset to bytewise on teardown. Comparator changes are applied before DB creation; this file does not test reopening an existing DB under an incompatible comparator.

Dependencies and integration points: the file uses public `DB`, `Iterator`, `Comparator`, `Options`, and `BlockBasedTableFactory` APIs, plus test utilities for random keys, fixed-format uint64 comparators, simple suffix reverse comparator, and key-value maps. It integrates comparator semantics with memtable ordering, SST table construction, point lookup, and iterator navigation.

Risks and edge cases covered: comparator bugs can manifest as missed keys, invalid reverse iteration, incorrect lower-bound seek, or inconsistent file/table ordering. Numeric and hash comparators cover non-lexicographic order; `TwoStrComparator` covers binary keys with embedded lengths; `Uint64Comparator` covers little binary keys and the need for stable binary ordering. Separator/successor tests cover equal strings, different lengths, carries across `0xff`, reverse-comparator asymmetry, and randomized strings where the shortened separator must remain inside the comparator interval.

Test signals: the main signal is exact agreement between RocksDB iterators/gets and `KVIter` over hundreds of randomized operations. Helper-method tests assert exact separator strings where deterministic and relational invariants where randomized. Failures point toward comparator contract violations, block index separator issues, memtable/SST ordering inconsistencies, or reverse iteration boundary bugs.

# sources/storage-engines/rocksdb/db/convenience.cc research

Purpose: `convenience.cc` implements public convenience functions declared under `rocksdb/convenience.h`. These functions adapt user-facing helper APIs to `DBImpl` internals for background-work cancellation, file deletion by key ranges, and standalone SST checksum verification.

Important APIs and functions: `CancelAllBackgroundWork(DB* db, bool wait)` obtains the root DB, checked-casts it to `DBImpl`, and delegates cancellation. `DeleteFilesInRange()` wraps a single optional begin/end pair into `RangePtr` and forwards to `DeleteFilesInRanges()`. The `RangePtr` overload converts pointer slices into owned/optional `RangeOpt` entries with `OptSlice::CopyFromPtr`, then calls the `RangeOpt` overload. The `RangeOpt` overload delegates to `DBImpl::DeleteFilesInRanges()`. `VerifySstFileChecksum()` has a simple overload creating default `ReadOptions`, and a fuller overload that rejects non-unknown `ReadOptions::io_activity` before calling `VerifySstFileChecksumInternal()`.

Control flow: range deletion is a layered conversion pipeline from older pointer-based range representation to the newer optional-slice representation, then into DB implementation code. Checksum verification opens an SST file through the configured filesystem, obtains its size, constructs `ImmutableOptions`, `InternalKeyComparator`, `RandomAccessFileReader`, and `TableReaderOptions`, creates a table reader from `options.table_factory`, and calls `TableReader::VerifyChecksum()` with `TableReaderCaller::kUserVerifyChecksum`.

State and persistence behavior: `CancelAllBackgroundWork` mutates live DB background scheduling state. `DeleteFilesInRanges` can delete or obsolete SST files whose key ranges fall within requested ranges, so it affects MANIFEST-visible live-file state through `DBImpl`. `VerifySstFileChecksumInternal` is read-only with respect to the target SST; it opens the file, reads metadata/data according to table-reader behavior, and may touch stats/rate limiter objects from `ImmutableOptions`.

Dependencies and integration points: this file depends on `DBImpl`, `static_cast_with_check`, filesystem abstractions (`FSRandomAccessFile`, `FileOptions`/`EnvOptions`), `RandomAccessFileReader`, `TableReader`, `TableReaderOptions`, the configured table factory, internal key comparator, compression manager, prefix extractor, and user `ReadOptions`. It is a bridge from stable public helpers to implementation-specific DB and table-reader code.

Risks and edge cases: the `DB*` must be backed by a `DBImpl` root or the checked cast will fail. Range inputs can be null to express unbounded starts/limits, so conversion correctness matters. Checksum verification assumes the supplied `Options` match the SST table format, comparator, compression manager, and filesystem used to create the file; mismatches can surface as open or checksum failures. The `io_activity` guard avoids callers attributing this operation to an unsupported activity class until plumbing exists.

Test signals: relevant validation comes from corruption/checksum tests that call DB checksum APIs, file deletion tests elsewhere, and integration tests using non-default table factories or filesystems. Expected signals are `Status::OK` for readable SSTs, corruption statuses for damaged SSTs, invalid argument for unsupported `io_activity`, and correct file-range deletion behavior through `DBImpl`.

# sources/storage-engines/rocksdb/db/convenience_impl.h research

Purpose: `convenience_impl.h` is the small private declaration header for the implementation-only checksum helper used by `convenience.cc`. It keeps the public convenience API separated from internal file-system and table-reader details.

Important API: the header declares `Status VerifySstFileChecksumInternal(const Options& options, const FileOptions& file_options, const ReadOptions& read_options, const std::string& file_path, const SequenceNumber& largest_seqno = 0);`. The default `largest_seqno` allows callers to verify ordinary SSTs while still permitting tests or specialized callers to constrain table-reader behavior with a known largest sequence number.

Control flow and state: the header itself has no control flow and no state. It exists so `convenience.cc` and any internal tests or implementation files can call the checksum implementation without exposing it in the public `rocksdb/convenience.h` surface.

Dependencies and integration points: it includes `rocksdb/db.h` for `Options`, `ReadOptions`, `Status`, and `SequenceNumber`, and `rocksdb/file_system.h` for `FileOptions`. The implementation integrates with `TableReader` creation and filesystem random-access reads in `convenience.cc`.

Risks and test signals: because this is an internal declaration, signature drift between header and implementation would be caught at compile time. The main maintenance risk is accidentally widening this internal helper into a public contract or changing defaults in ways that alter checksum verification semantics. Test signals are compile coverage and checksum/corruption tests that exercise the implementation.

# sources/storage-engines/rocksdb/db/corruption_test.cc research

Purpose: `corruption_test.cc` is RocksDB's broad corruption and recovery regression suite. It validates WAL recovery modes, SST corruption detection, manifest/descriptor repair, paranoid file checks, range-deletion metadata corruption, file checksum verification, write failure propagation, key-order guards, and crash-during-recovery consistency across regular DB and TransactionDB.

Important APIs, types, and fixtures: `ErrorFS` wraps `FileSystemWrapper` and can inject `NewWritableFile` errors. `CorruptionTest` builds an isolated DB with `kTolerateCorruptedTailRecords`, an `ErrorFS` composite env, tiny block cache, and block-based table options. Helpers include `Build()` for deterministic key/value writes, `Check()` for approximate surviving-key verification without checksum reads, `Corrupt()` for latest-file byte corruption, `CorruptTableFileAtLevel()`, `RepairDB()`, decimal `Key()`/random `Value()`, `GetSortedWalFiles()`, and WAL truncation through `CorruptFileWithTruncation()`. `CrashDuringRecoveryWithCorruptionTest` parameterizes `avoid_flush_during_recovery` and `track_and_verify_wals_in_manifest`.

Control flow: early tests corrupt WAL bytes or truncate WALs, reopen under tolerant or point-in-time modes, and assert expected data loss and open behavior. SST tests build and compact files, corrupt data/index/footer/magic/size, then compare behavior with `paranoid_checks` enabled or disabled. Other tests repair missing or corrupted descriptors, validate recovered sequence numbers, and ensure unrelated keys remain writable despite existing corrupted SSTs. Paranoid file checks use `mock::MockTableFactory` corruption modes to force bad keys, values, and reordered keys during flush or compaction. Recovery-crash tests simulate multi-column-family WAL state, inject sync/open errors through `SyncPoint`, reopen again, and verify RocksDB does not persist a MANIFEST that makes SSTs appear ahead of recoverable WAL state.

State and persistence behavior: the suite mutates actual DB directory contents: WALs are truncated, SST bytes are overwritten or extended, files are deleted, descriptors are corrupted, and `RepairDB` rebuilds metadata. Persistent state spans MANIFEST log numbers, WAL retention, column-family handles, table properties, file sizes recorded in metadata, and transaction prepare records. Several tests intentionally close and reopen DBs to force recovery code paths and validate whether corruption is caught at open time or deferred to reads/checksums.

Dependencies and integration points: the file uses `DBImpl` test hooks, `TransactionDB`, `WriteBatch`, `VersionSet`, file naming/parsing helpers, `RandomAccessFileReader`, block-based table metadata (`FindMetaBlockInFile`, `kRangeDelBlockName`), `VerifyChecksum`, `VerifyFileChecksums`, `GetFileChecksumGenCrc32cFactory`, `mock::MockTableFactory`, `SpecialEnv`, and `SyncPoint`. It also validates public convenience checksum behavior indirectly through DB-level checksum APIs.

Risks and edge cases covered: corruption may be tolerated, rejected, repaired, or deferred depending on recovery mode and paranoid flags. These tests cover corrupted WAL tails, WAL retention after point-in-time recovery, filesystem write failures, table index/footer damage, file-size mismatches, missing/deleted SSTs, corrupted range-deletion blocks, compaction input corruption with and without paranoid mode, bad key ordering from memtable or table factory, full-file checksum mismatch callbacks, and crash windows before WAL sync during recovery. TransactionDB tests add prepared transaction WAL-retention constraints.

Test signals: expected statuses are precise: `OK`, `NotFound`, `IsCorruption`, `IsIOError`, or non-OK depending on mode. Data checks assert surviving-key counts or exact values. Other signals include random-read counters for checksum readahead, error-message substrings such as `magic number`, `format_version`, and `file size mismatch`, callback hit counts for checksum mismatch, and successful second reopen after injected crash windows. The suite is intentionally white-box and sensitive to DB file layout, but it gives strong coverage of recovery invariants.

# sources/storage-engines/rocksdb/db/cuckoo_table_db_test.cc research

Purpose: `cuckoo_table_db_test.cc` validates RocksDB DB behavior when SSTs are written with the cuckoo table format. It checks flush, duplicate keys, custom comparators, compaction output splitting, duplicate-version compaction, and adaptive table factory reads across cuckoo, plain, and block-based tables.

Important APIs and fixture: `CuckooTableDBTest` owns an isolated DB path and opens with `NewCuckooTableFactory`, `NewHashLinkListRepFactory`, mmap reads, disabled concurrent memtable write, and non-dynamic level bytes. Helpers wrap `Put`, `Delete`, `Get`, `TEST_FlushMemTable`, `FilesPerLevel`, and `NumTableFilesAtLevel`. `Key(int)` generates fixed-width string keys and `Uint64Key(uint64_t)` produces binary little-endian keys for `test::Uint64Comparator`.

Control flow: `Flush` writes small key sets, flushes them to separate cuckoo SSTs, checks table properties and unique SST IDs, then verifies point reads and tombstones across three level-0 files. `FlushWithDuplicateKeys` verifies that multiple writes to the same key in one flush produce one visible entry with the latest value. `Uint64Comparator` reopens with a binary comparator and validates gets after deletes and updates. `CompactionIntoMultipleFiles` writes large values to force a big L0 file, then compacts with trivial moves disabled and checks output splits into two L1 files. `SameKeyInsertedInTwoDifferentFilesAndCompacted` confirms compaction keeps the newest value across files. `AdaptiveTable` writes with cuckoo, reopens with adaptive factories selecting plain and block-based formats for later files, then verifies reads across mixed table formats.

State and persistence behavior: persistent state is a real DB directory containing cuckoo SSTs and later mixed-format SSTs. The tests use table properties to verify entry counts and SST unique IDs, and level properties to assert compaction layout. Reopen calls preserve existing files unless `DestroyAndReopen` is used; this is essential for the adaptive table test, which deliberately accumulates files written by different factories.

Dependencies and integration points: the file integrates `DBImpl` test hooks, cuckoo table reader/factory, plain table and block-based factories through `NewAdaptiveTableFactory`, hash-link-list memtable representation, mmap reads, table metadata, and comparator test utilities. The `main()` skips the suite on big-endian platforms because cuckoo table does not support big endian.

Risks and edge cases covered: cuckoo tables need exact-match lookup correctness, stable hashing with the selected comparator, correct duplicate elimination, and compatibility with compaction. Large values stress target file sizing. Mixed table factories stress table-reader selection when old files remain in a format different from the current write factory. The suite also guards against delete markers hiding old values incorrectly and against compaction retaining obsolete duplicate versions.

Test signals: signals are exact `Get()` results, `FilesPerLevel()` strings such as `1`, `2`, `0,2`, and `0,1`, table property counts, and `VerifySstUniqueIds()`. Any failure typically indicates cuckoo table builder/reader incompatibility, comparator mismatch, compaction output sizing regression, or adaptive table factory dispatch failure.
