# sources/distributed-fs/ceph-client/drivers/clk/qcom/camcc-milos.c

Purpose: Qualcomm CAM_CC clock controller driver for the Milos platform. It describes the camera clock controller's PLLs, root clock generators, branch gates, reset lines, critical always-on CBCRs, and the CAMSS top GDSC so Device Tree camera consumers can request stable clock, reset, and power-domain resources through the common clock framework.

Important APIs/types/functions: The file is data-driven around `struct clk_alpha_pll`, `struct clk_alpha_pll_postdiv`, `struct clk_rcg2`, `struct clk_branch`, `struct gdsc`, `struct qcom_reset_map`, `struct qcom_cc_driver_data`, and `struct qcom_cc_desc`. `cam_cc_pll0` through `cam_cc_pll6` use Lucid OLE and Rivian EVO register layouts with fixed alpha PLL configurations and even/odd postdiv outputs where exposed. Parent maps connect DT clocks `bi_tcxo`, `sleep_clk`, and `iface` plus internal PLL outputs to the RCGs. Frequency tables cover BPS, CAMNOC AXI, CCI, CPHY RX, CRE, CSI PHY timers, fast/slow AHB, ICP, five MCLKs, OPE, TFE/TFE CSID, sleep, and XO sources. The final registration data is `cam_cc_milos_clocks`, `cam_cc_milos_resets`, `cam_cc_milos_gdscs`, `cam_cc_milos_plls`, `cam_cc_milos_critical_cbcrs`, `cam_cc_milos_regmap_config`, `cam_cc_milos_driver_data`, and `cam_cc_milos_desc`. `cam_cc_milos_probe()` is intentionally small and delegates to `qcom_cc_probe()`.

Control flow: module loading registers a platform driver matching `qcom,milos-camcc`. Probe calls `qcom_cc_probe(pdev, &cam_cc_milos_desc)`, which maps the MMIO range described by the DT node, initializes/configures alpha PLLs from `driver_data`, enables the listed critical CBCRs, registers all `clk_regmap` clocks, exposes reset controls, and registers the GDSC power domain. Runtime clock operations are then handled by the common Qualcomm clock drivers: RCGs select parents and divisors from the `F(...)` tables, branches program CBCR enable bits and poll halt registers, PLL postdivs adjust fixed divisors while propagating rate changes through `CLK_SET_RATE_PARENT`, and reset requests toggle the mapped BCR offsets.

State and persistence: there is no persistent software state. Static tables encode SoC register offsets, parent topology, PLL programming values, rate tables, reset offsets, and power-domain metadata. Runtime state lives in hardware registers and in CCF/GDSC registrations established during probe. The descriptor sets `.use_rpm = true`, so integration must account for RPM-managed handoff/voting behavior. `cam_cc_milos_critical_cbcrs` keeps CAM_CC_GDSC_CLK and CAM_CC_SLEEP_CLK enabled to preserve controller/power-domain infrastructure.

Dependencies and integration: depends on Linux CCF, regmap MMIO, platform bus probing, Qualcomm `clk-alpha-pll`, `clk-rcg`, `clk-branch`, `clk-regmap`, `gdsc`, `reset`, and `common` helpers, plus the DT binding IDs from `dt-bindings/clock/qcom,milos-camcc.h`. Camera stack consumers obtain clocks and resets by the binding indices in `cam_cc_milos_clocks` and `cam_cc_milos_resets`; power-domain users reference `CAM_CC_CAMSS_TOP_GDSC`.

Risks: the clock table must exactly match the DT binding enum ordering and supported hardware topology; a wrong index can silently hand a consumer the wrong clock. PLL register layout selection is mixed (`CLK_ALPHA_PLL_TYPE_LUCID_OLE` tables but Lucid EVO ops for base PLLs), so future edits need to preserve the known-compatible combination. Frequency table entries include fractional divisors and parent choices; incorrect values can overclock camera blocks or break sensor timing. Branch halt mode selection varies between normal, delay, and voted gates, and wrong polling can cause enable/disable timeouts. Critical CBCR and RPM settings affect power collapse, so removing them can break suspend or camera bring-up.

Test signals: build with the Milos CAMCC binding enabled and boot a `qcom,milos-camcc` DT node. Verify `/sys/kernel/debug/clk/clk_summary` exposes PLLs, RCGs, branch clocks, five MCLKs, TFE/OPE/BPS/ICP/CRE paths, and CAMNOC clocks at expected rates. Exercise camera sensor probe, MCLK rate changes, CSI PHY timer clocks, TFE capture paths, reset assertions for each BCR, CAMSS top GDSC on/off transitions, suspend/resume, and absence of branch halt warnings. Compare debugfs register-backed rates against the frequency tables and confirm CAM_CC_GDSC_CLK/CAM_CC_SLEEP_CLK stay enabled.

# sources/distributed-fs/ceph-client/drivers/clk/qcom/camcc-qcs615.c

Purpose: Qualcomm CAMCC driver for QCS615. It publishes camera subsystem clocks, resets, and GDSC power domains for BPS, IFE, IFE lite, IPE, JPEG, LRME, CCI, CSI PHY timers, MCLKs, CAMNOC, CPAS, and shared AHB/SOC infrastructure.

Important APIs/types/functions: The driver is built from static Qualcomm clock framework descriptors: `clk_alpha_pll` definitions for four PLLs, `clk_alpha_pll_postdiv` for `cam_cc_pll2_out_aux2`, `clk_rcg2` roots with `freq_tbl` rate tables, branch gates, five `gdsc` power domains, reset maps, a regmap config, and a `qcom_cc_desc`. PLL0/PLL1/PLL3 use Spark VCO data and default alpha PLL ops; PLL2 uses the Brammo PLL layout and exposes early/aux2 outputs. `cam_cc_qcs615_clocks` maps DT binding IDs to `clk_regmap` instances, `cam_cc_qcs615_gdscs` maps BPS/IFE/IPE/TITAN GDSCs, and `cam_cc_qcs615_resets` maps all camera BCR offsets. `cam_cc_qcs615_probe()` simply calls `qcom_cc_probe()`.

Control flow: the platform driver matches `qcom,qcs615-camcc`. Probe delegates to the common Qualcomm CC probe helper with `cam_cc_qcs615_desc`, causing MMIO mapping, PLL configuration from `cam_cc_qcs615_driver_data`, clock provider registration, reset controller registration, and GDSC provider registration. Consumers later call into CCF; RCGs choose parent source and divider from their tables, branch gates enable CBCRs and poll halt bits, reset controller operations touch BCR registers, and genpd/GDSC operations power BPS/IFE/IPE/TITAN domains. GDSC parent links make BPS, IFE0, IFE1, and IPE0 depend on `titan_top_gdsc`.

State and persistence: all state is static platform description plus volatile hardware state. PLL rate programming, branch enable state, reset assertion state, and GDSC on/off state live in CAMCC registers after probe. No state is stored outside the device. `ipe_0_gdsc` uses `RETAIN_FF_ENABLE`, so power collapse retains flip-flop state for that domain; all GDSCs use `POLL_CFG_GDSCR` so enable/disable sequencing relies on register polling.

Dependencies and integration: depends on the Linux common clock framework, regmap, platform devices, Qualcomm alpha PLL/RCG/branch/reset/GDSC helpers, and `dt-bindings/clock/qcom,qcs615-camcc.h`. It integrates with camera drivers through DT clock, reset, and power-domain references. Parent clocks come from DT only for `bi_tcxo`; internal PLL parents are described through `clk_hw` pointers.

Risks: binding index alignment is critical across `cam_cc_qcs615_clocks`, `cam_cc_qcs615_gdscs`, and `cam_cc_qcs615_resets`. Several rate tables reuse clocks across full and lite IFEs; parent or divider mistakes can produce valid-looking but wrong rates. GDSC parent ordering can break child power-up if `titan_top_gdsc` is not registered or sequenced correctly. Branch halt checks are mostly `BRANCH_HALT` with a few voted gates; incorrect halt semantics can cause intermittent camera bring-up failures. Because probe uses the generic `qcom_cc_probe()` path, any needed always-on clocks or pre-registration register tweaks must be represented in descriptor data; this file currently has no custom probe fixups.

Test signals: compile-test the driver and boot with a `qcom,qcs615-camcc` node. Check clk debugfs for expected PLL rates around 600/808/960/1080 MHz and derived RCG rates for BPS, IFE, IPE, JPEG, LRME, CCI, CSI timers, and MCLKs. Exercise all GDSCs through camera pipeline power-up/down, assert/deassert reset IDs, validate sensor MCLK frequencies, run camera capture paths for full IFE and lite IFE, and monitor dmesg for GDSC poll or branch halt timeout errors.

# sources/distributed-fs/ceph-client/drivers/clk/qcom/camcc-sa8775p.c

Purpose: Qualcomm CAMCC driver for SA8775P and the closely related QCS8300 camera clock controller. It registers camera clocks, resets, and the Titan top GDSC for a larger camera subsystem including four CCI instances, CSI PHY timers, CSID, IFEs, IPE, SFE lite blocks, CPAS bridge clocks, debug/observe clocks, sleep/XO roots, and MCLKs.

Important APIs/types/functions: The file defines Lucid EVO and Rivian EVO VCO tables, alpha PLL configs for PLL0/PLL2/PLL3/PLL4/PLL5, postdivs for even/odd outputs, parent maps for TCXO, TCXO_AO, sleep, and internal PLL outputs, `freq_tbl` instances for every RCG, branch gates for all exported clocks, `cam_cc_titan_top_gdsc`, `cam_cc_sa8775p_clocks`, `cam_cc_sa8775p_gdscs`, `cam_cc_sa8775p_resets`, `cam_cc_sa8775p_regmap_config`, and `cam_cc_sa8775p_desc`. `cam_cc_sa8775p_probe()` is the central function because it manually handles runtime PM, maps the regmap, configures PLLs, applies QCS8300-specific register/table mutations, enables a few always-on branches, and then calls `qcom_cc_really_probe()`.

Control flow: the platform driver matches both `qcom,qcs8300-camcc` and `qcom,sa8775p-camcc`. Probe enables runtime PM, resumes the device, maps CAMCC registers with `qcom_cc_map()`, configures all PLLs with the proper Lucid/Rivian helper, and then branches on `device_is_compatible(..., "qcom,qcs8300-camcc")`. For QCS8300, it rewrites selected `cmd_rcgr`, branch halt, and enable registers to the QCS8300 layout, moves the Titan GDSC register, nulls unsupported fourth-lane CCI/CSI/MCLK clocks, exposes the Titan top accumulator shift clock, and enables QCS8300-specific CAMNOC_XO/GDSC/SLEEP CBCRs. For SA8775P, it enables the corresponding SA8775P always-on CBCRs without mutating the table. It then registers clocks/GDSCs/resets with `qcom_cc_really_probe()` and releases the runtime PM reference.

State and persistence: static descriptors are mutated at probe time for the QCS8300 compatible, so the effective clock table is runtime-selected and process-global for the module instance. Hardware register state contains PLL programming, branch enables, reset lines, and GDSC state. The driver holds no persistent storage. Runtime PM is used only to keep the register block accessible during probe and registration; the final provider state is managed by CCF/GDSC consumers.

Dependencies and integration: depends on Linux runtime PM, regmap, platform devices, Qualcomm common clock helpers, GDSC/reset support, and the binding header `dt-bindings/clock/qcom,qcs8300-camcc.h`. It integrates with camera and CPAS clients through clock IDs, reset IDs, and the CAM_CC_TITAN_TOP_GDSC power domain. It also depends on Device Tree compatible selection to distinguish SA8775P and QCS8300 register layouts.

Risks: probe mutates static global clock descriptors for QCS8300, which is acceptable for a single CAMCC instance but risky if multiple compatibles were ever instantiated in one kernel lifetime. The QCS8300 path nulls unsupported clock indices; consumers using those binding IDs should receive missing clocks rather than touching invalid registers, so DT and consumer drivers must be compatible-specific. Always-on branch offsets differ between SA8775P and QCS8300; using the wrong compatible can enable the wrong CBCRs. Many branches share similar names but different offsets and halt modes, including a `BRANCH_HALT_SKIP` observe/debug clock, so offset regressions can be hard to spot without hardware testing. Runtime PM error paths must keep `pm_runtime_put()` balanced after successful resume.

Test signals: boot both `qcom,sa8775p-camcc` and `qcom,qcs8300-camcc` DTs if hardware is available. Verify qcs8300 hides CCI3/CSI3/CSIPHY3/MCLK3 resources and exposes Titan top accumulator shift, while SA8775P keeps the full table. Check clk debugfs for PLL0/2/3/4/5 and RCG rates, confirm CAMNOC_XO/GDSC/SLEEP CBCRs are enabled at the compatible-specific offsets, exercise IFE/IPE/SFE lite/CSID/CPAS/MCLK clocks, assert resets, toggle the Titan top GDSC, and run suspend/resume with camera clients to catch runtime PM or always-on clock mistakes.

# sources/distributed-fs/ceph-client/drivers/clk/qcom/camcc-sc7180.c

Purpose: Qualcomm CAM_CC driver for SC7180. It provides camera subsystem clocks and GDSC power domains for BPS, IFE0/IFE1, IFE lite, IPE, JPEG, LRME, CCI, CSI PHY timers, CAMNOC, CPAS, ICP, MCLKs, and shared AHB/SOC paths.

Important APIs/types/functions: The file defines Fabia and Agera alpha PLLs (`cam_cc_pll0` through `cam_cc_pll3`), a fixed-factor early output for PLL2, an aux postdiv for PLL2, parent maps using firmware-named `bi_tcxo`, multiple RCG rate tables, branch gates, five GDSCs, `cam_cc_sc7180_hws` for the fixed-factor hardware clock, `cam_cc_sc7180_clocks`, `cam_cc_sc7180_gdscs`, `cam_cc_sc7180_regmap_config`, and `cam_cc_sc7180_desc`. The main function is `cam_cc_sc7180_probe()`, which manually sets up runtime PM and PM clocks, configures PLLs, and calls `qcom_cc_really_probe()`. `cam_cc_pm_ops` wires runtime suspend/resume to `pm_clk_suspend` and `pm_clk_resume`.

Control flow: the driver matches `qcom,sc7180-camcc`. Probe enables runtime PM, creates PM clock tracking, adds the external `xo` and `iface` clocks, resumes the device so the register block is accessible, maps the register space through `qcom_cc_map()`, configures the four PLLs with Fabia/Agera helper functions, registers clocks and GDSCs via `qcom_cc_really_probe()`, and drops the runtime PM reference. After registration, CCF operations select RCG parents/dividers from the rate tables, branch operations enable CBCRs and poll halt state, and GDSC operations control Titan top plus child BPS/IFE/IPE domains. Runtime PM callbacks gate the PM clocks when the controller is suspended.

State and persistence: there is no persistent state. Static tables describe the hardware, while runtime hardware registers store PLL configuration, CBCR enables, and GDSC power state. `cam_cc_sc7180_hws` exports `CAM_CC_PLL2_OUT_EARLY` as a fixed-factor clock not represented as `clk_regmap`. `bps_gdsc` and `ipe_0_gdsc` have `HW_CTRL`, meaning hardware can participate in power-domain control for those blocks.

Dependencies and integration: depends on CCF, runtime PM, PM clock framework, platform bus, regmap, Qualcomm alpha PLL/RCG/branch/GDSC helpers, and `dt-bindings/clock/qcom,camcc-sc7180.h`. Device Tree must provide firmware clock names `bi_tcxo`, `xo`, and `iface` as expected by the parent and PM clock setup. Camera drivers consume the registered clocks and GDSCs through the SC7180 CAMCC binding.

Risks: PM clock acquisition is part of probe; missing `xo` or `iface` supplies fail the provider before any clocks are registered. Parent references use `.fw_name = "bi_tcxo"` instead of DT index arrays, so DT clock-names must match. There is no reset map in this descriptor, unlike newer related drivers, so consumers must not expect CAMCC reset IDs from this provider. GDSC `HW_CTRL` changes software expectations for BPS/IPE power transitions. Branch and RCG tables are dense and repetitive; mismatched rates or halt registers can manifest as camera pipeline stalls rather than compile-time errors.

Test signals: boot SC7180 with a valid `qcom,sc7180-camcc` DT node and required `xo`, `iface`, and `bi_tcxo` clock names. Confirm probe succeeds, clk debugfs shows the PLLs plus `CAM_CC_PLL2_OUT_EARLY`, MCLK0-4, IFE/BPS/IPE/JPEG/LRME/CSI/CCI clocks, and expected parent/rate selections. Exercise runtime suspend/resume of the provider, GDSC on/off for Titan/BPS/IFE/IPE domains, camera capture paths, sensor MCLK rates, and error handling by testing missing PM clocks in DT overlays or compile-time DT validation.
