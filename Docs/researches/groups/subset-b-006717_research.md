# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/sierraforest/srf-metrics.json

Purpose: defines 142 Sierra Forest perf metric formulas consumed by Linux perf's PMU events machinery for the x86 `sierraforest` architecture directory. Unlike the sibling uncore files, this file does not define raw programmable events; it defines derived metrics such as C-state residency, CPI/IPC, CPU frequency, TLB miss rates, I/O and memory bandwidth, SMI activity, UPI transmit bandwidth, and Topdown Microarchitecture Analysis (TMA) nodes.

Important APIs/types/functions: the "API" is the perf JSON metric schema. Each object is a metric record keyed primarily by `MetricName`, with `MetricExpr` as the expression evaluated by perf, optional `MetricGroup` and `MetricgroupNoGroup` for menu/group placement, optional `MetricThreshold` for highlighting suspected bottlenecks, optional `BriefDescription`/`PublicDescription`, and optional `ScaleUnit`. The expressions reference core events (`CPU_CLK_UNHALTED.*`, `INST_RETIRED.ANY`, `MEM_LOAD_UOPS_RETIRED.*`, `TOPDOWN_*`), MSR/cstate pseudo-events (`msr@tsc@`, `msr@aperf@`, `msr@smi@`, `cstate_pkg@...@`, `cstate_core@...@`), uncore events from nearby Sierra Forest JSON files (`UNC_CHA_TOR_INSERTS.*`, `UNC_M2M_IMC_*`, `UNC_UPI_*`, `UNC_IIO_*`, `UNC_P_*`), and perf runtime symbols such as `duration_time`, `#num_packages`, `#num_cores`, and `#SYSTEM_TSC_FREQ`.

Control flow: at perf build/install time, pmu-events tooling parses this JSON into generated metric tables. At runtime, `perf stat -M <metric>` or metric groups resolve `MetricName` and `MetricGroup`, schedule all referenced raw events/pseudo-events, collect counts over the measurement interval, then evaluate `MetricExpr`. Metrics are layered: for example `cpu_utilization` aliases `tma_info_system_cpu_utilization`, `tma_resource_bound` subtracts `tma_core_bound` from `tma_backend_bound`, and many TMA thresholds depend on parent TMA metrics being elevated. Topdown formulas divide slot counters by `6 * CPU_CLK_UNHALTED.CORE`, reflecting a six-wide pipeline model for this platform.

State and persistence: the file stores static metric metadata only. It has no mutable runtime state and performs no persistence itself. Runtime state is limited to perf's counter scheduling, multiplexing, aggregation, and expression evaluation. Metrics that divide by instructions, cycles, `duration_time`, or reference clocks depend on the measurement interval and perf's aggregation mode; package-level metrics also depend on topology discovery.

Dependencies and integration: this file integrates with the Linux perf pmu-events parser, x86 PMU aliases, MSR/cstate PMUs, uncore PMUs, and Sierra Forest event definition files. Several metrics depend directly on events defined in the companion uncore cache/interconnect/IIO/power files, especially CHA TOR insert/occupancy events for LLC and I/O bandwidth, PCU clockticks for C-state occupancy, UPI counters for fabric bandwidth/frequency, and memory-controller counters for memory bandwidth. `ScaleUnit` values include percent, GHz, MB/s, per-instruction, per-second, SMI count, and nanoseconds; those units drive perf's display scaling rather than changing the raw counters.

Risks: expression names must exactly match event aliases generated from the architecture event files; any rename in `uncore-cache.json`, `uncore-interconnect.json`, or other Sierra Forest PMU files can break derived metrics. Division-heavy formulas can report undefined or misleading values on zero denominators, heavily multiplexed runs, missing PMUs, or unsupported MSR/cstate devices. Topdown threshold logic is sensitive to the hard-coded six-wide slot denominator and to the assumption that all TMA component events schedule together. Bandwidth formulas encode line-size and unit assumptions, commonly multiplying event counts by 4 or 64 and dividing by `1e6 / duration_time`; mistakes here produce plausible but wrong rates. Metrics that combine per-core, per-package, and system-wide symbols need careful aggregation semantics.

Test signals: useful validation includes `jq` schema parsing, perf pmu-events generation tests, `perf list` showing the Sierra Forest metric names and groups, and `perf stat -M cpi,cpu_operating_frequency,tma_backend_bound` on supported hardware. Cross-check bandwidth metrics against raw `UNC_CHA_TOR_INSERTS.*`, IIO, UPI, and memory-controller events. For topology-sensitive metrics, compare package/core counts and C-state residency against MSR/cpuidle telemetry. For TMA, verify that parent percentages are bounded and that child metrics reconcile with the expected hierarchy under non-multiplexed collection.

# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/sierraforest/uncore-cache.json

Purpose: defines 336 Sierra Forest uncore cache/home-agent PMU events for perf. The file is centered on CHA events, with 333 `Unit: CHA` records, plus three `CHACMS` records for CMS units attached to CHA. It exposes clockticks, directory lookup/update behavior, LLC lookup/victim activity, remote snoop-filter state, OSB and request classes, interrupt queue insert/occupancy, SF evictions, and a large set of TOR insert/occupancy filters for IA, I/O, local/remote, CXL, DDR, and PMM traffic.

Important APIs/types/functions: the relevant interface is the perf event JSON schema for raw uncore events. Each record supplies `EventName`, `EventCode`, `Unit`, `Counter`, and `PerPkg`, with optional `UMask`, `PortMask`, `BriefDescription`, `PublicDescription`, and `Experimental`. Counter masks are mostly `0,1,2,3`; CHACMS and most CHA events are package-scoped through `PerPkg: "1"`. Event families include `UNC_CHA_LLC_LOOKUP.*`, `UNC_CHA_LLC_VICTIMS.*`, `UNC_CHA_REMOTE_SF.*`, `UNC_CHA_REQUESTS.*`, `UNC_CHA_TOR_INSERTS.*`, and `UNC_CHA_TOR_OCCUPANCY.*`. The file has 245 public descriptions and 148 experimental entries, signaling that many aliases are intentionally exposed but may be less stable.

Control flow: perf's pmu-events build step converts these JSON objects into alias tables. When a user requests an alias such as `UNC_CHA_TOR_INSERTS.IA_MISS_DRD_OPT_REMOTE`, perf maps the alias to the CHA uncore PMU unit, event code, umask, and eligible counters, then programs one counter per package/CHA instance as supported by the kernel PMU. Insert events count transaction occurrences; occupancy events count residency or cycles associated with matching TOR entries. Higher-level metrics in `srf-metrics.json` then consume these aliases to compute LLC misses, local/remote bandwidth, I/O read/write bandwidth, and CXL-related traffic.

State and persistence: this file is static metadata with no runtime state. Hardware state lives in the uncore CHA/CHACMS counters, and perf owns counter allocation, per-package aggregation, scaling, and multiplexing. Because CHA events are per-package and often per-agent, the observed value changes with socket topology, enabled CHA slices, and kernel exposure of the uncore PMUs. No data is persisted beyond perf output.

Dependencies and integration: it depends on the Linux perf pmu-events parser, kernel x86 uncore PMU support for Sierra Forest CHA/CHACMS units, and exact event encodings accepted by the hardware. It is tightly integrated with `srf-metrics.json`, which references aliases including `UNC_CHA_TOR_INSERTS.IO_PCIRDCUR`, `IO_MISS_*`, `IA_MISS_*`, and related local/remote variants. The CXL/DDR/PMM-specific TOR filters also complement `uncore-cxl.json` and memory/interconnect metrics by separating cache, fabric, and memory-destination behavior.

Risks: this is a large alias table, so the highest risk is semantic drift between event names, descriptions, event code/umask encodings, and hardware documentation. `UNC_CHA_LLC_LOOKUP.*` descriptions warn about non-standard filtering and the need to include required state-selection bits; incorrect masks can silently count nothing or count a broader class than the alias suggests. TOR insert and occupancy aliases have near-parallel names, making copy/paste mistakes plausible. Experimental events may not be reliable across steppings or kernel support levels. Metrics that divide insert counts into bandwidth assume 64-byte cache lines and correct local/remote/CXL classification.

Test signals: validate the JSON with `jq`, build perf's pmu-events tables, and check `perf list` for representative aliases from each family. On Sierra Forest hardware, smoke-test `UNC_CHA_CLOCKTICKS`, `UNC_CHA_TOR_INSERTS.ALL`, `UNC_CHA_TOR_OCCUPANCY.ALL`, LLC lookup aliases, and a CXL-specific alias where the platform has CXL traffic. Compare raw counts against derived `srf-metrics.json` metrics such as LLC MPI and I/O bandwidth. Counter scheduling tests should include multiple CHA events to verify counter-mask constraints and multiplexing behavior.

# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/sierraforest/uncore-cxl.json

Purpose: defines three Sierra Forest CXL-related uncore PMU aliases for perf. The file covers the B2CXL clock domain and two CXL data movement points: allocation into a CXL cache/memory receive-side memory-data packing buffer and allocation into a CXL data-path transmit command AGF for M2S data.

Important APIs/types/functions: the JSON records use the same perf uncore event schema as the other architecture files. `UNC_B2CXL_CLOCKTICKS` uses `Unit: B2CXL`, `EventCode: 0x01`, counters `0,1,2,3`, `PerPkg: "1"`, and `PortMask: "0x000"`. `UNC_CXLCM_RxC_PACK_BUF_INSERTS.MEM_DATA` uses `Unit: CXLCM`, `EventCode: 0x41`, `UMask: 0x10`, and counters `4,5,6,7`. `UNC_CXLDP_TxC_AGF_INSERTS.M2S_DATA` uses `Unit: CXLDP`, `EventCode: 0x02`, `UMask: 0x20`, and counters `0,1,2,3`. There are no public descriptions or experimental flags in this file.

Control flow: perf parses the file into PMU aliases, then maps requested aliases to the corresponding CXL uncore unit and counter set. The clockticks event can be used as a denominator or liveness signal for the B2CXL block. The insert events count specific CXL buffer/AGF allocation points and can be sampled directly or used by future derived metrics to estimate CXL memory data movement and pressure.

State and persistence: static metadata only. Runtime state is held in package-scoped CXL uncore counters and is visible only while perf is collecting. The file does not store history or configure CXL devices itself; it relies on the kernel exposing the package CXL PMU units and the hardware generating the matching allocation events.

Dependencies and integration: depends on Linux perf pmu-events support and kernel uncore PMU support for the `B2CXL`, `CXLCM`, and `CXLDP` units. It complements CXL-filtered CHA TOR aliases in `uncore-cache.json`; together, those files let perf users distinguish CXL traffic observed at CHA from CXL fabric/data-path activity. It may also feed platform-specific bandwidth or occupancy metrics if later metric JSON references these aliases.

Risks: the small file gives little semantic detail beyond brief descriptions, so users must rely on hardware documentation to interpret allocation counts and convert them to bytes or rates. Counter availability differs between `CXLCM` and `CXLDP` entries, so grouping all three events can fail or multiplex depending on PMU layout. CXL units may be absent, disabled, or unexposed on systems without relevant CXL hardware. The event names contain mixed-case path fragments (`RxC`, `TxC`, `M2S`) that must remain stable for scripts and metrics.

Test signals: validate syntax with `jq`, verify `perf list` exposes all three aliases on a Sierra Forest perf build, and run `perf stat -e UNC_B2CXL_CLOCKTICKS` as a liveness check on hardware with B2CXL support. On a CXL workload, compare `UNC_CXLCM_RxC_PACK_BUF_INSERTS.MEM_DATA` and `UNC_CXLDP_TxC_AGF_INSERTS.M2S_DATA` against CXL-specific CHA TOR hit/miss aliases from `uncore-cache.json`.

# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/sierraforest/uncore-interconnect.json

Purpose: defines 167 Sierra Forest uncore interconnect PMU aliases for perf. It covers mesh-to-memory (`B2CMI`), bridge-to-hot and bridge-to-UPI clocks (`B2HOT`, `B2UPI`), IRP/system interconnect (`IRP` via `UNC_I_*` names), mesh data fabric (`MDF`), UPI link receive/transmit traffic and power states (`UPI`), and UBOX event-message traffic (`UBOX`). The largest groups are 79 B2CMI events and 67 UPI events.

Important APIs/types/functions: each record follows perf's event JSON schema with `EventName`, `EventCode`, `Unit`, `Counter`, `PerPkg`, and often `UMask`; 10 entries include `PublicDescription`, and 123 are marked `Experimental`. B2CMI families include direct-to-core/direct-to-UPI decisions, directory hit/miss/update state transitions, IMC reads/writes, prefetch CAM insert/occupancy, tag hit/miss, and tracker occupancy. UPI families include `UNC_UPI_RxL_BASIC_HDR_MATCH.*`, `UNC_UPI_TxL_BASIC_HDR_MATCH.*`, receive/transmit flit classes, insert/occupancy slots, and low-power cycle counters. UBOX event-message aliases count doorbell, priority interrupt, IPI, MSI, and VLW messages.

Control flow: perf's pmu-events generation turns the JSON into aliases for the named uncore units. At runtime, a requested alias programs the appropriate package-scoped unit and counter. B2CMI events expose mesh-to-memory and directory decisions, UPI events expose link packet/flit mix and link power behavior, IRP events expose snoop and transaction activity, and UBOX events expose system event messages. Derived metrics in `srf-metrics.json` can use these events as raw inputs, especially for UPI bandwidth/frequency and uncore behavior diagnostics.

State and persistence: the file is declarative metadata only. Runtime counts are in hardware uncore counters and are aggregated by perf per package/link/unit according to kernel support. No state is persisted by the JSON. Occupancy-style events represent time or residency in a hardware structure during the measurement interval, while insert/header/flit events represent counted transactions.

Dependencies and integration: depends on perf's JSON parser, kernel x86 uncore drivers for the listed Sierra Forest units, and hardware encodings for event codes and masks. It integrates with `srf-metrics.json` through UPI-related metrics such as data transmit bandwidth and uncore frequency, and it complements `uncore-cache.json` because directory, snoop, and direct-routing decisions explain some CHA/TOR locality and remote-traffic behavior. UBOX MSI/message aliases can be correlated with I/O metrics, while B2CMI IMC read/write aliases can be correlated with memory bandwidth metrics.

Risks: the high experimental count means many aliases may be provisional or stepping-dependent. Several B2CMI aliases have overlapping semantic descriptions and duplicate-looking suffixed variants, for example base and `.EGRESS` forms for direct-to-UPI not-taken reasons; users need hardware guidance before combining them. UPI header-match aliases distinguish broad classes and opcode-specific forms, so summing them naively can double count. Flit, insert, and occupancy events have different units and should not be mixed without normalization. Unsupported links or power states can yield zero counts that mean either idle hardware or absent PMU support.

Test signals: validate with `jq`, build perf pmu-events tables, and verify `perf list` exposes representative aliases for B2CMI, UPI, IRP, MDF, and UBOX. Hardware smoke tests should include `UNC_B2CMI_CLOCKTICKS`, `UNC_UPI_CLOCKTICKS`, receive/transmit UPI flit aliases, B2CMI directory lookup/update aliases, and UBOX MSI/message events under an interrupt-heavy workload. Cross-check UPI data flit counts with `upi_data_transmit_bw` in `srf-metrics.json`, and compare B2CMI IMC read/write activity against memory-controller bandwidth counters.
