# sources/distributed-fs/ceph-client/drivers/media/usb/cx231xx/cx231xx-core.c

Purpose: core support for Conexant Cx23100/101/102 USB video-capture devices. It owns the global cx231xx device and extension lists, wraps USB vendor/control requests, exposes common I2C/register/GPIO helpers, selects USB alternate settings, initializes the device's I2C buses and analog blocks, and allocates/resubmits URBs for analog video or TS1 DVB transport streaming.

Important APIs/types/functions: `cx231xx_add_into_devlist()` and `cx231xx_remove_from_devlist()` maintain the global device list under `cx231xx_devlist_mutex`. `cx231xx_register_extension()`, `cx231xx_unregister_extension()`, `cx231xx_init_extension()`, and `cx231xx_close_extension()` provide the extension-module lifecycle used by DVB and other subdrivers. USB access is centralized in `cx231xx_send_usb_command()`, `cx231xx_send_vendor_cmd()`, `cx231xx_read_ctrl_reg()`, `cx231xx_write_ctrl_reg()`, and private `__usb_control_msg()`. Streaming entry points are `cx231xx_set_video_alternate()`, `cx231xx_set_alt_setting()`, `cx231xx_init_isoc()`, `cx231xx_init_bulk()`, `cx231xx_uninit_isoc()`, and `cx231xx_uninit_bulk()`. Hardware setup helpers include `cx231xx_dev_init()`, `cx231xx_dev_uninit()`, `cx231xx_gpio_set()`, `cx231xx_demod_reset()`, `cx231xx_set_mode()`, `cx231xx_ep5_bulkout()`, `cx231xx_send_gpio_cmd()`, `cx231xx_mode_register()`, the I2C master accessors, `cx231xx_reg_mask_write()`, `cx231xx_read_modify_write_i2c_dword()`, and `cx231xx_set_field()`.

Control flow: device initialization registers three real I2C masters, creates and registers the two-channel mux for I2C master 1, optionally scans physical ports, powers the device for external A/V or analog TV, resets Xceive tuners through board GPIO sequences, initializes AFE channels, places the DIF path in baseband bypass, initializes I2S and control pins, selects analog AGC routing, and zeros video/VBI/HANC/TS alternate settings. Extension modules are registered into a global list; a newly registered extension is initialized on every existing device, and a newly probed device calls each registered extension. USB register and I2C operations build vendor-request fields, then route through `__usb_control_msg()` with a heap-backed `dev->urb_buf` protected by `ctrl_urb_lock` to avoid DMA-unsafe stack buffers. For I2C reads larger than four bytes on internal buses, `cx231xx_send_vendor_cmd()` chunks control messages into first/middle/last packets by changing request `wValue` flags.

Streaming control flow: analog or DVB callers choose ISO or bulk setup. Both setup functions first tear down any old URBs, reset `struct cx231xx_dmaqueue` parser state, allocate URB pointer arrays and coherent transfer buffers, choose endpoint `0x84` for raw video or `0x81` for TS1, fill URBs, submit them, and start capture with `cx231xx_capture_start()`. ISO completion walks packet descriptors, calls the configured `isoc_copy` callback under `video_mode.slock`, clears per-packet status/length fields, and resubmits. Bulk completion calls the configured `bulk_copy` callback under the same lock and resubmits unless the endpoint is stalled or shutting down. Teardown kills/unlinks URBs, frees coherent buffers, resets a stalled endpoint, frees queue scratch state, and stops capture in the active raw or TS mode.

State and persistence: persistent driver state lives in `struct cx231xx`: `mode`, `mode_tv`, `state`, `udev`, `urb_buf`, per-interface mode descriptors, `current_pcb_config`, I2C buses, mux state, locks, board data, dimensions, and function pointers. Global persistence is limited to in-memory device/extension lists and module parameters `core_debug`, `reg_debug`, and `alt`. Hardware state is persisted only in USB interface alternate settings, endpoint halt state, GPIO/GPIE bits, power/AGC/control registers, AFE/DIF/I2S state, and capture start/stop state until the device is reset or reprogrammed. There is no on-disk persistence.

Dependencies and integration: depends on Linux USB core, I2C core, V4L2/tuner headers, board data in `cx231xx.h`, register definitions in `cx231xx-reg.h`/configuration headers, and helper functions implemented in sibling cx231xx files for AFE, DIF, I2S, GPIO, tuner callbacks, mux control, and capture start. DVB integration uses exported mode, alternate-setting, URB, demod-reset, firmware-check, and I2C-adapter helpers. Analog/VBI code uses the same URB engines with different copy callbacks. Board PCB configuration determines USB interface indices for video, audio, VBI, HANC, and TS1.

Risks: `cx231xx_dev_init()` returns immediately on later I2C/mux/setup failures without unwinding earlier registered adapters, so partial initialization can leak adapters until higher-level cleanup happens. `cx231xx_send_vendor_cmd()` mutates the caller-provided `ven_req->wValue` while chunking long requests, which is surprising if the caller reuses the structure. `cx231xx_ep5_bulkout()` copies `EP5_BUF_SIZE` bytes from the firmware pointer regardless of the supplied `size`, then compares `actlen` with `size`, so short firmware buffers would be over-read unless all callers pass at least `EP5_BUF_SIZE`. ISO setup uses `usb_fill_int_urb()` with ISO flags and packet descriptors; this may be inherited behavior but is unusual and should be compile/runtime checked. `cx231xx_read_i2c_master()` stores `value[saddr]` into a scalar when `data_len > 4`, but `saddr` can be larger than the local 64-byte buffer. `cx231xx_reg_mask_write()` treats `size` as a bit-width and only has explicit 8-bit versus "else" 32-bit behavior, so callers must pass exactly the expected sizes.

Test signals: build with cx231xx analog and DVB configs enabled; probe representative bus-powered/self-powered boards and verify three I2C adapters plus two mux adapters; enable `i2c_scan`, `core_debug`, and `reg_debug` to confirm vendor request construction; exercise analog capture over ISO and bulk paths; stream DVB TS1 over ISO and bulk and check endpoint `0x81`; disconnect during active URBs and ensure no resubmission after `DEV_DISCONNECTED`; test repeated mode switches between analog, digital, and suspend; validate alternate settings for video/VBI/HANC/audio/TS1 on high-speed and full-speed descriptors; run with USB/DMA debug to check coherent allocation and teardown balance.

# sources/distributed-fs/ceph-client/drivers/media/usb/cx231xx/cx231xx-dif.h

Purpose: static DIF band-pass-filter coefficient data for the cx231xx analog intermediate-frequency path. The file defines a small table-entry type and a large in-header `Dif_set_array[]` mapping IF frequencies to DIF BPF coefficient register writes.

Important APIs/types/functions: `struct dif_settings` contains `if_freq`, `register_address`, and `value`. `Dif_set_array[]` is a static array of register programming triples. Each supported IF frequency has entries for `DIF_BPF_COEFF01` through `DIF_BPF_COEFF36`, with paired coefficient registers packed into 32-bit values and a final `DIF_BPF_COEFF36` terminator-style register value for that frequency. The array is included into any translation unit that includes this header rather than exported as a separately compiled object.

Control flow: this header has no executable control flow. Sibling DIF implementation code is expected to select entries whose `if_freq` matches the requested analog standard/tuner IF, then write each `register_address`/`value` pair through the cx231xx register or I2C helpers. The table is ordered by increasing IF frequency from 3.0 MHz through 16.0 MHz in 100 kHz steps.

State and persistence: no runtime state is mutated here. The static table is read-only by convention but not declared `const`, so every object including the header gets a private writable copy. Hardware persistence occurs only after consumers write these values into DIF BPF registers.

Dependencies and integration: includes `cx231xx-reg.h` for `DIF_BPF_COEFF*` register addresses. It is part of analog tuner/DIF configuration used by cx231xx initialization and standard switching, especially when `cx231xx_dif_set_standard()` is asked to program IF filtering rather than use baseband bypass.

Risks: because `Dif_set_array[]` is defined in a header as `static` and not `const`, including it in multiple C files duplicates several thousand table entries in the built objects. The table has no explicit sentinel or count macro; consumers must use `ARRAY_SIZE()` in the including translation unit or otherwise know the length. Register values are hand-imported coefficient data with no validation, so a single transposed frequency/register/value silently misprograms the analog filter. Comments near some high-frequency blocks contain typo-like labels such as `113000000` while the actual `if_freq` field is `13000000`, so comments should not be parsed as data. Lack of `const` also permits accidental writes to calibration data.

Test signals: compile consumers with `-Wmissing-prototypes`/sparse-style checks to catch duplicate or unused static data; verify `cx231xx_dif_set_standard()` can locate every intended IF frequency from 3.0 MHz to 16.0 MHz; compare programmed `DIF_BPF_COEFF*` values against vendor coefficient files; tune analog standards that use common IFs such as 3.25 MHz, 4.0 MHz, and 4.5 MHz; measure analog lock/video quality after standard changes; check object size impact if the header is included by more than one C file.

# sources/distributed-fs/ceph-client/drivers/media/usb/cx231xx/cx231xx-dvb.c

Purpose: DVB extension module for cx231xx USB capture devices. It attaches board-specific demodulator/tuner frontends over cx231xx I2C adapters, registers Linux DVB adapter/demux/network/media-controller objects, starts TS1 USB streaming when demux feeds are active, and tears everything down through the cx231xx extension framework.

Important APIs/types/functions: `struct cx231xx_dvb` stores up to two frontends, feed-count lock/state, `dvb_adapter`, `dvb_demux`, `dmxdev`, hardware/memory demux frontends, `dvb_net`, and I2C module clients for demods/tuners. Static config blocks describe S5H1432, S5H1411, LGDT3305/LGDT3306A, TDA18271, MB86A20S, R820T, Si2165/Si2168/Si2157, and MN88473 attachment parameters. URB copy callbacks are `dvb_isoc_copy()` and `dvb_bulk_copy()`. Stream lifecycle is `start_streaming()`, `stop_streaming()`, `start_feed()`, and `stop_feed()`. Registration lifecycle is `dvb_init()`, `register_dvb()`, `unregister_dvb()`, `dvb_fini()`, and module init/exit functions registering `dvb_ops`.

Control flow: module init registers a `cx231xx_ops` extension. For every DVB-capable device, `dvb_init()` allocates state, installs analog tuner helper callbacks, resolves tuner/demod I2C adapters from board data, locks the device, switches to digital mode, resets the demod, then dispatches on `dev->model`. Each model branch attaches or probes a demod, optionally sets `frontend[0]->callback`, attaches or probes a tuner, and stores I2C clients for module-managed devices. Dual-frontend Hauppauge 975 setup attaches LGDT3306A and Si2168 demods, registers MFE sharing, attaches one Si2157 tuner, then copies tuner private state and ops to the second frontend. `register_dvb()` registers the adapter, media-controller hooks, frontends, software demux, dmxdev, hardware/memory demux frontends, network device, and media graph. On failure it unwinds in reverse order.

Streaming flow: a demux feed start increments `nfeeds` under `dvb->lock`; the first feed starts TS1 streaming. ISO mode selects TS1 alt setting 5, enters digital mode, marks `mode_tv`, and calls `cx231xx_init_isoc()` with `dvb_isoc_copy()`. Bulk mode selects alt 0, enters digital mode, marks `mode_tv`, and calls `cx231xx_init_bulk()` with `dvb_bulk_copy()`. Copy callbacks ignore disconnected devices, log URB or packet errors, and pass payload bytes to `dvb_dmx_swfilter()`. Feed stop decrements `nfeeds`; the last feed tears down ISO/bulk URBs and suspends the device.

State and persistence: persistent runtime state is in `dev->dvb`, frontend objects and their tuner private data, I2C clients loaded through `dvb_module_probe()`, DVB demux filter tables, feed count, adapter media graph state, and cx231xx mode/TS endpoint state. Analog helper callbacks `dev->cx231xx_set_analog_freq` and `dev->cx231xx_reset_analog_tuner` point into this file when a shared tuner can be used for analog. There is no durable persistence outside kernel/device state.

Dependencies and integration: depends on Linux DVB core (`dvbdev`, `dmxdev`, `dvb_demux`, `dvb_frontend`, `dvb_net`), V4L2 tuner support, many demod/tuner modules, cx231xx core exports for I2C adapters, mode switching, demod reset, alternate settings, and URB setup/teardown, plus board definitions for model IDs, I2C masters, addresses, and DVB capability. It integrates with media-controller support through `dvb_register_media_controller()` and `dvb_create_media_graph()`.

Risks: `start_feed()` increments `nfeeds` before `start_streaming()` and does not decrement it if streaming fails, so a failed first feed can leave feed count inconsistent and prevent later starts/stops from balancing. `stop_feed()` blindly decrements `nfeeds`, so duplicate or out-of-order stop calls could underflow and skip teardown. Many tuner attach calls are not checked after frontend attach, meaning a DVB adapter can register with a demod but missing tuner on some boards. In the Hauppauge 975 path, copying tuner ops/private data to the second frontend creates shared tuner lifetime assumptions that must match DVB core expectations. Failure paths in `dvb_init()` free `dvb` but do not detach all frontends created through `dvb_attach()` unless they were module clients, so branch-specific attach failures need leak checks. `cx231xx_dvb_bus_ctrl()` can suspend the whole device on frontend bus release while other analog/DVB users may need mode coordination.

Test signals: build with every referenced frontend/tuner as built-in and module; probe each supported board model and verify the expected demod/tuner appears in logs; run `dvbv5-scan`, tune, and capture TS packets over ISO and bulk modes; start multiple demux filters and ensure only the first starts URBs and the last stops them; force frontend/tuner attach failures to verify unwind; test dual-frontend Hauppauge 975 simultaneous and serialized use; disconnect during active DVB capture; run media graph validation when media-controller DVB is enabled; exercise analog frequency/reset helpers on shared XC5000/TDA18271 boards.

# sources/distributed-fs/ceph-client/drivers/media/usb/cx231xx/cx231xx-i2c.c

Purpose: Linux I2C adapter and mux implementation for cx231xx devices. It translates kernel `i2c_transfer()` messages into cx231xx USB vendor I2C commands, handles special Xceive XC5000 tuner transactions through GPIO bit-banged helpers, offers optional bus scanning, and exposes physical/muxed adapters to tuner, demod, IR, and analog subdrivers.

Important APIs/types/functions: module parameters `i2c_scan` and `i2c_debug` control scanning and debug output. `get_real_i2c_port()` maps bus 1 to mux port 1 or port 3 depending on `dev->port_3_switch_enabled`. `is_tuner()` detects messages targeting the board's tuner address/type. Low-level transfer helpers are `cx231xx_i2c_send_bytes()`, `cx231xx_i2c_recv_bytes()`, `cx231xx_i2c_recv_bytes_with_saddr()`, and `cx231xx_i2c_check_for_device()`. `cx231xx_i2c_xfer()` is the `master_xfer` implementation in `cx231xx_algo`. Public setup helpers are `cx231xx_do_i2c_scan()`, `cx231xx_i2c_register()`, `cx231xx_i2c_unregister()`, `cx231xx_i2c_mux_create()`, `cx231xx_i2c_mux_register()`, `cx231xx_i2c_mux_unregister()`, and exported `cx231xx_get_i2c_adap()`.

Control flow: each adapter points `algo_data` at a `struct cx231xx_i2c`. `cx231xx_i2c_xfer()` serializes all transfers with `dev->i2c_lock`, handles zero-length messages as presence probes, handles simple reads, folds a short write followed by a read to the same address into a subaddress read, and otherwise sends writes. Normal transfers populate `struct cx231xx_i2c_xfer_data` and call `dev->cx231xx_send_usb_command()`. XC5000 writes are split into firmware/register subaddress handling, 16-byte chunks with `i2c_nostop` and `i2c_reserve` flags, or GPIO I2C writes for calibration/source/standard/frequency transactions after firmware load. XC5000 reads special-case busy checks, lock-status reads, and firmware-status reads, sometimes writing the subaddress through GPIO before reading.

State and persistence: persistent state includes adapter registrations in `dev->i2c_bus[]`, each bus's `i2c_period`, `i2c_nostop`, `i2c_reserve`, `i2c_rc`, the global I2C lock, `dev->muxc`, `dev->port_3_switch_enabled`, `dev->i2c_scan_running`, and `dev->xc_fw_load_done`. Transfer helper state is temporary per message. Hardware-visible state includes the selected mux channel via `cx231xx_enable_i2c_port_3()` and any tuner state reached by USB or GPIO I2C writes.

Dependencies and integration: depends on Linux I2C and I2C mux core, V4L2/tuner definitions, cx231xx core vendor-command hooks, board data for tuner address/type and physical I2C masters, and GPIO I2C callbacks in `struct cx231xx`. `cx231xx_dev_init()` registers the three real adapters, creates the mux on bus 1, and scans I2C ports. DVB and IR code call `cx231xx_get_i2c_adap()` to attach frontend, tuner, and remote-control clients.

Risks: `cx231xx_i2c_recv_bytes()` computes `msg->buf[0] << 8 | msg->buf[1]` even when `msg->len == 1` in the XC5000 request setup, which can read beyond the one-byte buffer. `cx231xx_get_i2c_adap()` returns `dev->muxc->adapter[]` without checking mux creation or channel registration, so early callers or failed init paths can dereference null pointers. `cx231xx_i2c_mux_unregister()` assumes `dev->muxc` is valid. XC5000 transfer rewriting depends on firmware-load side effects and magic subaddresses, making regression risk high when tuner drivers change message sequences. The adapter advertises broad `I2C_FUNC_SMBUS_EMUL | I2C_FUNC_I2C` support even though transfers have cx231xx-specific chunk limits and special cases. The scan loop probes all 128 addresses and could disturb devices if enabled on fragile boards.

Test signals: register/unregister adapters repeatedly under probe/remove; verify physical adapters and mux adapters are named and visible; enable `i2c_scan=1` on known boards and compare detected addresses; tune XC5000 boards through firmware load, calibration, lock status, and analog/digital transitions; run DVB attach paths that use muxed I2C port 1 and port 3; test combined write-read messages of 1-byte and 2-byte subaddresses under KASAN/UBSAN; force mux creation failure and check cleanup; run with `i2c_debug=2` to confirm stop/nonstop behavior and chunking.

# sources/distributed-fs/ceph-client/drivers/media/usb/cx231xx/cx231xx-input.c

Purpose: IR remote-control glue for cx231xx boards that use an external I2C IR microcontroller instead of the chip's internal IR block. It binds `ir-kbd-i2c` to the board-specified I2C adapter and supplies a cx231xx-specific key polling callback.

Important APIs/types/functions: `get_key_isdbt()` is the `IR_i2c` polling callback; it reads one byte from the I2C client, treats `0xff` as no key, bit-reverses other command bytes into scancodes, reports `RC_PROTO_OTHER`, and returns whether a key was found. `cx231xx_ir_init()` allocates an rc-core scancode device, fills `IR_i2c_init_data`, sets board keymap and NEC-related masks, and creates an `ir_video` I2C client at address `0x30`. `cx231xx_ir_exit()` unregisters the I2C client and clears the stored pointer.

Control flow: initialization first checks `cx231xx_boards[dev->model].rc_map_name`; boards without a keymap return `-ENODEV` and skip IR setup. It requests the `ir-kbd-i2c` module, zeroes board info and init data, allocates an `RC_DRIVER_SCANCODE` device, fills platform data, selects the board's `ir_i2c_master`, and calls `i2c_new_client_device(cx231xx_get_i2c_adap(...), &info)`. Once bound, `ir-kbd-i2c` calls `get_key_isdbt()` to poll the hardware. Exit unregisters the client.

State and persistence: persistent state is `dev->init_data`, the allocated `rc_dev` owned through the I2C IR client, and `dev->ir_i2c_client`. The external IR controller's last key state is read over I2C; no persistent configuration is stored on disk. Keymaps come from board data.

Dependencies and integration: depends on cx231xx board definitions, exported `cx231xx_get_i2c_adap()`, Linux I2C, rc-core, `ir-kbd-i2c`, and `bitrev8()`. It integrates with boards that define both `rc_map_name` and `ir_i2c_master`.

Risks: `cx231xx_ir_init()` does not check `i2c_new_client_device()` with `IS_ERR()`/NULL and still returns 0, so IR binding failure can look successful and leave cleanup paths with an invalid or null client. If `i2c_new_client_device()` fails after `rc_allocate_device()`, ownership/freeing of `dev->init_data.rc_dev` is not explicit in this file. `cx231xx_ir_exit()` calls `i2c_unregister_device()` unconditionally, so it relies on callers only invoking exit after successful init or on the helper tolerating NULL. The callback reports `RC_PROTO_OTHER` even though init data sets `RC_PROTO_BIT_NEC`, reflecting that the microcontroller emits only command bytes; keymap compatibility must be verified per board.

Test signals: probe a board with `rc_map_name` and verify `ir-kbd-i2c` autoload and client creation at address `0x30`; press/hold/release keys and confirm `0xff` no-key behavior, `0xfe` hold behavior, bit-reversed scancodes, and keymap matches; remove/unplug after failed and successful IR init; test missing `ir-kbd-i2c` module; validate `ir_i2c_master` points to a registered cx231xx adapter or mux adapter.

# sources/distributed-fs/ceph-client/drivers/media/usb/cx231xx/cx231xx-pcb-cfg.c

Purpose: board PCB scenario resolver for cx231xx devices. It defines known self-powered and bus-powered endpoint/source layouts, reads the hardware board-configuration register, selects the matching scenario, stamps runtime USB speed/source fields, and copies the selected `struct pcb_config` into the device.

Important APIs/types/functions: module parameter `pcb_debug` enables scenario logging. `cx231xx_Scenario[]` is the core static table of `struct pcb_config` entries. Implemented scenarios cover self-powered digital-only, dual-digital, analog-only, dual, triple, compressor, plus bus-powered digital-only, analog-only, and DIF-only layouts. Each scenario supplies high-speed and full-speed `CONFIG_INFO` arrays with endpoint interface indices for interrupt, TS1, TS2, audio, video, VANC, HANC, and IR. `initialize_cx231xx()` is the only function and the external entry point declared in the header.

Control flow: `initialize_cx231xx()` reads four bytes from `BOARD_CFG_STAT` with `cx231xx_read_ctrl_reg(VRT_GET_REGISTER)`, converts them to `config_info`, and extracts USB speed from bit 0. If `BUS_POWER` is set, it masks with `BUSPOWER_MASK` and selects digital-only for `TS1_PORT | BUS_POWER`, analog-only for `AVDEC_ENABLE | BUS_POWER`, or DIF-only for `AVDEC_ENABLE | BUS_POWER | TS1_PORT`; unknown bus-powered combinations log an error and return 1. If self-powered, it masks with `SELFPOWER_MASK` and selects among digital-only, dual-digital, analog-only, dual, triple, and compressor scenarios based on TS and AV decoder bits. Selected scenarios have `speed`, TS source, and analog source fields patched from local defaults, then are copied to `dev->current_pcb_config`; `dev->current_scenario_idx` records the table index.

State and persistence: persistent runtime state is `dev->current_scenario_idx` and `dev->current_pcb_config`, which later core code uses to choose USB interface numbers for alternate settings and streaming. The source table itself is static global data and is mutated when `initialize_cx231xx()` writes scenario `speed` and source fields before copying, so those values persist in the module across devices. Hardware state is only read from `BOARD_CFG_STAT`.

Dependencies and integration: depends on `cx231xx.h`, `cx231xx-conf-reg.h`, the PCB types/macros from `cx231xx-pcb-cfg.h`, and `cx231xx_read_ctrl_reg()` from core. The selected config is consumed by `cx231xx_set_video_alternate()`, `cx231xx_set_alt_setting()`, and setup paths that need endpoint/interface layout. It also informs analog/DVB feature availability through `mode`, `ts*_source`, and `analog_source`.

Risks: `p_pcb_info` is not initialized before the switch; current branches return on unknown scenarios, but future edits must preserve that guarantee. The static scenario table is modified per device, so two devices initialized concurrently or sequentially with different speeds/source defaults can race or leave shared table state changed; copying from a local const table would be safer. Header enum values define more bus-powered scenario names than the C table implements, which can mislead callers into expecting external/combined bus-powered layouts. Unknown bus-powered configs return positive `1` instead of a negative errno, unlike self-powered unknown configs returning `-ENODEV`. Interface indices use `NOT_SUPPORTED` (`0xff`) sentinels that later code often adds 1 to after selecting a field; callers must avoid using unsupported endpoints. Some default `analog_source` local value is `0`, so selected analog scenarios may not explicitly carry `SOURCE_ANALOG`/`SOURCE_DIF` unless already encoded in the table.

Test signals: mock or run hardware with `BOARD_CFG_STAT` values for every implemented scenario and verify selected `current_scenario_idx`, speed, mode, sources, and high/full-speed interface indices; enable `pcb_debug` and compare logs; test unsupported bus/self-powered bit combinations and expected errno behavior; probe two cx231xx devices with different speed/scenario combinations under KCSAN to catch static table races; validate subsequent `usb_set_interface()` calls never use `NOT_SUPPORTED + 1`; compare endpoint layouts against USB descriptors on high-speed and full-speed operation.

# sources/distributed-fs/ceph-client/drivers/media/usb/cx231xx/cx231xx-pcb-cfg.h

Purpose: PCB configuration contract for cx231xx devices. It defines USB vendor request IDs, byte-enable masks, board-configuration bit masks, source/mode constants, endpoint-interface layout structures, scenario indices, and the `initialize_cx231xx()` prototype used to resolve hardware configuration at probe time.

Important APIs/types/functions: `enum VENDOR_REQUEST_TYPE` names cx231xx vendor requests for I2C masters, GPIO, GPIE, register access, and extended compatibility descriptors. `enum BYTE_ENABLE_MASK` supplies one- through four-byte register access masks. USB config bit definitions include `SPEED_MASK`, `TS_MASK`, `EAVP_MASK`, `ATM_MASK`, `PWR_SEL_MASK`, `BO_0_MASK`, `BO_1_MASK`, `BUSPOWER_MASK`, and `SELFPOWER_MASK`, plus enums for USB speed, external A/V presence, analog tuner mode, power type, and A/V decoder status. `MOD_*` and `SOURCE_*` constants describe feature modes and signal sources. `struct INTERFACE_INFO`, `struct CONFIG_INFO`, and `struct pcb_config` define the selected interface map and feature/source state. `enum INDEX_PCB_CONFIG` names possible PCB scenarios. `initialize_cx231xx()` initializes the runtime config.

Control flow: this header has no executable control flow, but its constants drive `cx231xx-pcb-cfg.c` scenario selection and core alternate-setting code. A caller reads hardware config through `initialize_cx231xx()`, then uses `dev->current_pcb_config.hs_config_info[]` or `fs_config_info[]` endpoint indices with `INDEX_TS1`, `INDEX_AUDIO`, `INDEX_VIDEO`, and related enum values when selecting USB interfaces.

State and persistence: no state is stored by the header itself. It defines the persistent in-memory shape copied into `struct cx231xx.current_pcb_config`: power type, speed, supported modes, TS/analog sources, per-mode config indices, config count, and high/full-speed interface maps.

Dependencies and integration: included by cx231xx core/config code and depends only on basic Linux module/init headers plus a forward declaration of `struct cx231xx`. Its vendor request and byte-enable definitions are also used by core USB control and GPIO/I2C helpers.

Risks: several names and comments contain typo-like spellings (`ENABLE_TWE_BYTE`, `USB_POWE_TYPE`, analog comments), so code search and external documentation can diverge. `TS1_TS2_PORT` and `TS1_EXT_CLOCK` share the same value with different meanings; scenario selection must know context. `INDEX_PCB_CONFIG` enumerates many bus-powered external/combined cases not represented in `cx231xx_Scenario[]`, creating a maintenance mismatch. `NOT_SUPPORTED` is `0xff` in `u8` fields; arithmetic on these fields can wrap or produce invalid USB interface numbers if not checked. `BUSPOWER_MASK` and `SELFPOWER_MASK` intentionally ignore some config bits, so new board revisions could alias an old scenario unless masks are reviewed.

Test signals: compile all cx231xx users after changing constants; unit-style checks for `sizeof(struct pcb_config)` consumers if ABI assumptions exist; scenario-selection tests for every mask combination; descriptor validation that interface indices from `struct INTERFACE_INFO` match actual USB descriptors; static analysis for uses of `NOT_SUPPORTED` fields without checks; review any new PCB enum addition against both the header and the scenario table.
