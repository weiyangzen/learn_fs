# sources/distributed-fs/ceph-client/drivers/scsi/mpt3sas/mpt3sas_base.h

Purpose: defines the shared contract for the Linux `mpt3sas`/`mpt2sas` Fusion MPT SAS host driver. It centralizes driver versioning, firmware constants, device private structures, per-adapter runtime state, DMA/request/reply queue descriptors, callback typedefs, inline reference helpers, and cross-module prototypes used by base, SCSI host, transport, config, control, debugfs, trigger, and WarpDrive support code.

Important APIs/types/functions: major constants cover driver identity, SGE depth, queue depths, NVMe PRP sizes, firmware timeouts, diagnostic buffer status, host branding/SSID tables, high-IOPS queue limits, and HBA port flags. Key private types are `struct MPT3SAS_ADAPTER`, `struct MPT3SAS_TARGET`, `struct MPT3SAS_DEVICE`, `struct _sas_device`, `struct _pcie_device`, `struct _raid_device`, `struct _sas_node`, `struct _sas_port`, `struct _sas_phy`, `struct hba_port`, `struct adapter_reply_queue`, `struct scsiio_tracker`, `struct request_tracker`, `struct chain_tracker`, and `struct _internal_cmd`. Inline APIs `sas_device_get/put()` and `pcie_device_get/put()` wrap `kref` lifetime handling. Function-pointer typedefs such as `MPT_BUILD_SG_SCMD`, `MPT_BUILD_SG`, `NVME_BUILD_PRP`, `PUT_SMID_IO_FP_HIP`, `PUT_SMID_DEFAULT`, `GET_MSIX_INDEX`, and `MPT_CALLBACK` let runtime setup swap MPI/IEEE SGL, NVMe PRP, atomic descriptor, and MSI-X selection behavior.

Control flow: this header has no large executable flow, but it defines the data lanes followed by the driver. PCI probe and base attach allocate and initialize `MPT3SAS_ADAPTER`, fill facts/static config pages, map registers, allocate request/reply/sense/chain/config DMA pools, register callbacks, and enable port discovery. SCSI I/O obtains an SMID, fills a request frame, records lookup state in `scsiio_tracker`, builds SGL/PRP data through function pointers, posts the descriptor through a `put_smid_*` callback, and later completes through reply queues and registered callbacks. Internal commands, including config, task management, control, transport, and port enable commands, serialize through `_internal_cmd` status/completion fields. Device discovery flows use config-page APIs to populate SAS/PCIe/RAID device structures and then publish them through SCSI and SAS transport layers.

State and persistence behavior: all state is in memory or firmware-visible DMA memory. `MPT3SAS_ADAPTER` is the persistent-in-driver root while the adapter exists: it stores PCI/register identity, logging flags, firmware event queues, reset flags, callback indexes, cached firmware facts and config pages, SAS/PCIe/RAID/enclosure/device lists, target ID allocators, config-page scratch DMA, request/reply/free-post queues, sense buffers, chain pools, diagnostic buffers, trigger definitions, debugfs entries, high-IOPS and io_uring poll queue state, and multipath HBA ports. Device objects keep `kref` lifetimes and list membership under adapter locks. Hardware state is persisted only in controller firmware or NVRAM when separate implementation code writes config pages; the header itself only declares the buffers and APIs that enable those operations.

Dependencies and integration points: includes MPI2/MPI26 firmware layout headers, SCSI core headers, SAS transport headers, PCI, polling, IRQ polling, and local debug/trigger headers. The declarations tie together `mpt3sas_base.c` for adapter lifecycle and queues, `mpt3sas_scsih.c` for SCSI device discovery/error handling, `mpt3sas_config.c` for firmware config pages, `mpt3sas_transport.c` for SAS transport objects, `mpt3sas_ctl.c` for ioctl/sysfs/event log/diagnostic buffers, `mpt3sas_trigger*.c` for persistent trigger support, `mpt3sas_warpdrive.c` for direct I/O, and debugfs setup. External `mpt3sas_ioc_list` and `gioc_lock` provide global adapter enumeration with list synchronization.

Risks and test signals: this header is high blast-radius because structure layout, flags, callback prototypes, queue constants, and lifetime helpers are consumed throughout the driver. Risks include stale comments versus actual fields, duplicate `MPT3SAS_COREDUMP_LOOP_DONE` definition, incorrect config page version constants in callers, mismatched endian handling across cached pages, race-prone adapter/device list manipulation, dangling `_sas_device`/`_pcie_device` references when refcounts are not paired, request/reply queue index corruption, reset paths leaving `_internal_cmd` completions unresolved, and queue-depth constants that overrun firmware credits. Test signals should include compile coverage across all driver modules, probe/remove/reset cycles, SAS/PCIe/RAID discovery and removal, MSI-X and fallback interrupt modes, io_uring poll queue pause/resume, host reset while internal/config commands are pending, diagnostic buffer registration/release, trigger-page read/update paths, direct I/O setup, and memory-leak/refcount checks on hotplug and error recovery.

# sources/distributed-fs/ceph-client/drivers/scsi/mpt3sas/mpt3sas_config.c

Purpose: implements the common firmware configuration-page access layer for `mpt3sas`. It builds MPI2 config requests, allocates DMA buffers for page payloads, serializes access through `ioc->config_cmds`, waits for firmware completion, performs reply/config sanity checks, and exposes typed helpers for manufacturing, BIOS, IOC, IO unit, SAS, PCIe, expander, enclosure, PHY, RAID, and driver persistent trigger pages.

Important APIs/types/functions: `mpt3sas_config_done()` is the callback registered for config command completions. `_config_request()` is the central send/wait/copy/retry function. `_config_alloc_config_dma_memory()` and `_config_free_config_dma_memory()` choose between the adapter scratch `ioc->config_page` and a larger coherent allocation. `_config_display_some_debug()` labels page types for config debug logging. Public getters/setters include manufacturing pages 0/1/10/11, BIOS pages 2/3/4, IO unit pages 0/1/3/8, IOC pages 1/8, SAS device page 0, PCIe device pages 0/2, PCIe IO unit page 1, SAS IO unit pages 0/1, expander pages 0/1, enclosure page 0, SAS PHY pages 0/1, RAID volume pages 0/1, RAID physical disk page 0, and helper APIs `mpt3sas_config_get_number_hba_phys()`, `mpt3sas_config_get_number_pds()`, `mpt3sas_config_get_volume_handle()`, and `mpt3sas_config_get_volume_wwid()`. Driver trigger APIs cover pages 0-4 and update master, MPI event, SCSI sense, and IOC status/loginfo trigger entries.

Control flow: each typed page accessor generally clears a local `Mpi2ConfigRequest_t`, sets `Function = MPI2_FUNCTION_CONFIG`, requests the page header with a zero-length MPI SGE, then reuses reply header fields for `PAGE_READ_CURRENT`, `PAGE_WRITE_CURRENT`, or `PAGE_WRITE_NVRAM`. `_config_request()` locks `ioc->config_cmds.mutex`, rejects concurrent use, sets VF/VP IDs to zero, copies page header metadata from the previous reply when a payload buffer is present, builds a read or write SGE, waits for the IOC to become ready, obtains an SMID from the base layer, copies the request into the firmware frame, posts it with `ioc->put_smid_default()`, and waits on `ioc->config_cmds.done`. Completion copies the reply into `config_cmds.reply`, marks complete, clears pending state, and wakes the waiter. On success, `_config_request()` validates reply page type and extended page type, optionally validates the returned page buffer, copies payload data back to the caller for read-current requests, frees temporary DMA memory, clears status to `MPT3_CMD_NOT_USED`, and returns.

State and persistence behavior: runtime state is carried by `ioc->config_cmds.status`, `smid`, `reply`, and completion object; the mutex enforces one config command per adapter. Payload DMA uses persistent adapter scratch space for small pages and transient coherent memory for larger pages, with `ioc->config_vaddr` pointing at the active buffer. Read helpers update caller-provided in-memory page structures, often cached later in `MPT3SAS_ADAPTER` by base initialization. Write helpers alter controller state; some pages are written only to current firmware state, while SAS IO unit page 1 and driver trigger pages write current state and NVRAM so settings persist across firmware resets or power cycles. `mpt3sas_config_get_volume_handle()` transiently allocates RAID configuration page memory and iterates firmware configuration numbers until it finds the volume relationship for a physical disk.

Dependencies and integration points: depends on `mpt3sas_base.h` for adapter state, config command fields, SGE builder callbacks, SMID allocation/free, IOC readiness, reply address translation, timeout diagnostics, and reset handling. It relies on MPI config page definitions and endian helpers from the included MPI headers. SCSI discovery and hotplug code call SAS/PCIe/RAID/enclosure/PHY helpers; base initialization calls manufacturing, BIOS, IOC, IO unit, and trigger-page helpers; control/sysfs paths update persistent trigger pages; WarpDrive direct-I/O setup consumes RAID page helpers. Error paths integrate with `mpt3sas_base_check_cmd_timeout()`, `mpt3sas_base_free_smid()`, `mpt3sas_base_check_for_fault_and_issue_reset()`, and `mpt3sas_base_hard_reset_handler()`.

Risks and test signals: `_config_request()` panics on firmware page-type mismatches, so malformed firmware replies are intentionally fatal. Timeout recovery is delicate because a pending config SMID may be freed locally, retried if reset marked `MPT3_CMD_RESET`, or escalate to host reset depending on recovery flags and `MPT_DRV_INTERNAL_FIRST_PE_ISSUED`. Several setters issue a current write and then an NVRAM write but do not always check the intermediate current-write return before proceeding. `mpt3sas_config_set_sas_iounit_pg1()` ignores the return from the first write. `mpt3sas_config_get_ioc_pg1()` and `mpt3sas_config_set_ioc_pg1()` use `MPI2_IOCPAGE8_PAGEVERSION` for page 1, which is worth verifying against firmware headers. Trigger update rollback flips page-0 validity if the per-trigger page update fails, but failures during rollback are not surfaced. Tests should cover header-only reads, variable-size BIOS/IOUnit/SAS IO unit pages, large config pages exceeding the 512-byte scratch buffer, all page-address forms, GET_NEXT enumeration, write-current plus write-NVRAM behavior, IOCStatus failure handling, command timeout with and without host reset, config command concurrency returning `-EAGAIN`, reset completion of pending config commands, endian correctness of copied fields, and discovery callers handling non-success IOCStatus despite `_config_request()` returning 0.
