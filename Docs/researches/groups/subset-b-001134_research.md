# sources/distributed-fs/ceph-client/drivers/clk/qcom/gcc-qcm2290.c

Purpose: global clock controller driver for the Qualcomm QCM2290 GCC block, matched by `qcom,gcc-qcm2290`. It exposes the SoC's shared PLLs, root clock generators, branch gates, resets, dynamic-frequency-switching RCGs, and GDSC power domains to the Linux common clock, reset, and genpd frameworks.

Important APIs, types, and functions: the file is mostly static data consumed by common Qualcomm clock helpers. It defines Alpha PLLs `gpll0`, `gpll1`, `gpll3`-`gpll11`, postdivs such as `gpll0_out_aux2`, `gpll3_out_main`, `gpll6_out_main`, `gpll8_out_main`, and `gpll9_out_main`, VCO/config tables for GPLL10, GPLL11, GPLL8, and GPLL9, parent maps/data for TCXO, sleep, and PLL-derived parents, many `clk_rcg2` roots with `freq_tbl` rate tables, a display divider `gcc_disp_gpll0_clk_src`, USB mock-UTMI postdivider, and branch clocks for camera, display, GPU, PDM, QUPv3, SDCC, USB3, video/Venus, and system interconnect paths. `gcc_qcm2290_clocks[]` maps dt-binding IDs to the corresponding `clk_regmap` objects, `gcc_qcm2290_resets[]` maps BCR and ARES offsets, `gcc_qcm2290_gdscs[]` registers CAMSS, USB30, VCODEC, Venus, and votable MMU TBU power domains, and `gcc_qcm2290_desc` binds all of this to a `regmap_config`.

Control flow: `gcc_qcm2290_init()` registers a platform driver at `subsys_initcall` time. Probe maps MMIO through `qcom_cc_map()`, registers dynamic frequency switching for the six QUPv3 serial RCGs with `qcom_cc_register_rcg_dfs()`, configures GPLL10, GPLL11, GPLL8, and GPLL9 with `clk_alpha_pll_configure()`, then calls `qcom_cc_really_probe()` to publish clocks, resets, and GDSCs. Runtime clock operations are delegated to common ops such as `clk_alpha_pll_ops`, `clk_alpha_pll_postdiv_ro_ops`, `clk_rcg2_shared_ops`, `clk_rcg2_floor_ops`, `clk_branch2_ops`, and divider ops.

State and persistence behavior: persistent state is hardware register state in the GCC MMIO region up to `0xc7000`; the driver itself stores no mutable software policy beyond framework registrations. PLL configuration programs hardware during probe. Branch clocks encode halt semantics with `BRANCH_HALT`, `BRANCH_HALT_DELAY`, `BRANCH_HALT_VOTED`, `BRANCH_VOTED`, and `BRANCH_HALT_SKIP`; several branches are marked critical, including camera/display XO or AHB paths, GPU config AHB, and system NOC CPU AHB. GDSCs persist power-domain state in GDSCR registers, with several votable HLOS1 MMU TBU domains and VCODEC using `HW_CTRL_TRIGGER`.

Dependencies and integration points: dependencies include Linux platform/module/regmap/common-clock APIs, `dt-bindings/clock/qcom,gcc-qcm2290.h`, Qualcomm alpha PLL, branch, RCG, divider, reset, GDSC, and common CC helpers. Consumers integrate by referencing the dt-binding clock, reset, and power-domain IDs. Important external parents are firmware-named `bi_tcxo` and `sleep_clk`; the controller supplies clocks to CAMSS/TFE/OPE, display, GPU, QUPv3 serial engines, eMMC/SD, USB3 PHY and master paths, Venus/VCODEC, PDM, and interconnect throttle/QMIP blocks.

Risks: correctness depends on exact register offsets, parent-map hardware selector values, and dt-binding indices matching the SoC manual. Shared and voted clocks can be hard to debug because enable bits live in vote registers such as `0x79004` and `0x7900c`, not always in the local branch register. Raw critical-clock choices can mask missing consumer votes, while under-marking critical AHB/XO clocks can hang media, GPU, or interconnect access. PLLs with dynamic update or non-default BRAMMO/EVO register layouts are sensitive to VCO/config mistakes. DFS registration is limited to QUPv3 serial RCGs, so serial-rate changes are a specific regression target.

Test signals: boot logs should show successful `gcc-qcm2290` probe with no deferred external parent failures. `/sys/kernel/debug/clk/clk_summary` should expose the GPLLs, QUPv3 sources, SDCC, USB, camera, display, GPU, and video branches with expected parent/rate choices. Functional signals include serial ports through all QUPv3 instances, SDCC1/SDCC2 rate switching including floor ops, USB3 link bring-up with skipped pipe halt checks, camera and Venus power-domain on/off through GDSCs, reset assertions through BCR IDs, and suspend/resume without critical clock loss. Clock-framework tests should exercise `qcom_cc_register_rcg_dfs()` paths for the six QUP RCGs.

# sources/distributed-fs/ceph-client/drivers/clk/qcom/gcc-qcs404.c

Purpose: global clock controller driver for Qualcomm QCS404, matched by `qcom,gcc-qcs404`. It describes the always-on XO wrapper, GPLLs, display, GPU, Ethernet, PCIe, USB, BLSP, SDCC, crypto, CDSP/WCSS, and miscellaneous GCC clocks, plus reset lines and MDSS/Oxili GDSC power domains.

Important APIs, types, and functions: the driver uses a fixed-factor `cxo` clock exported via `clk_hws`, Alpha PLLs for GPLL0/GPLL1/GPLL3/GPLL4, a legacy `clk_pll` GPLL6 with vote output `gpll6_out_aux`, parent maps for board XO, sleep, PCIe pipe, DSI byte/pixel PLLs, and HDMI PLL, many `clk_rcg2` roots with rate tables, `clk_byte2_ops` and `clk_pixel_ops` roots for DSI byte/pixel clocks, and branch gates for BLSP QUP/I2C/SPI/UART, Ethernet, MDSS, Oxili GPU, PCIe, USB2/USB3, PDM, SDCC, crypto, SMMU/TCU/TBU, and debug clocks. `gcc_qcs404_clocks[]`, `gcc_qcs404_resets[]`, `gcc_qcs404_hws[]`, `gcc_qcs404_gdscs[]`, and `gcc_qcs404_desc` are the exported provider tables.

Control flow: `gcc_qcs404_init()` registers the platform driver through `core_initcall`, earlier than many GCC drivers because system clocks are foundational. Probe maps registers using `qcom_cc_map()`, explicitly configures `gpll3_out_main` with the 930 MHz `gpll3_config`, then calls `qcom_cc_really_probe()`. The common Qualcomm CC layer registers the clock provider, reset controller, and GDSCs from the descriptor. There is no custom remove/suspend path beyond platform-driver unregister at module exit.

State and persistence behavior: runtime state is hardware register state in the GCC regmap up to `0x7f000` plus framework registration state. `gpll0_ao_out_main` is marked `CLK_IS_CRITICAL` and uses fixed Alpha PLL ops, and `apss_ahb_clk_src` is also critical, preserving CPU/interconnect reachability. Branches use a mix of local halt checks and voted halt checks through shared enable registers around `0x45004` and `0x4500c`. Some resets are whole-register BCRs, while several PCIe and USB resets are bit-level ARES entries in shared reset registers. MDSS and Oxili power domains use standard off/on GDSCs.

Dependencies and integration points: dependencies include common clock/regmap/platform/OF APIs, `dt-bindings/clock/qcom,gcc-qcs404.h`, Qualcomm alpha PLL and legacy PLL helpers, RCG, branch, regmap clock, reset, GDSC, and common CC helpers. External parents come from DT indices for XO, sleep, PCIe pipe, DSI PHY byte/pixel clocks, and HDMI PLL. Consumers include BLSP serial controllers, Ethernet MAC/PTP/RGMII, MDSS DSI/HDMI/display pipelines, Oxili GPU, PCIe, USB HS/SS PHY/controller paths, SDCC/eMMC ICE, crypto, CDSP/WCSS, and SMMU/interconnect blocks.

Risks: the file mixes Alpha PLLs and a legacy PLL vote path, so parent references and ops must match the hardware implementation. Display clocks depend on external DSI and HDMI PLL parents; missing or mis-indexed DT clock inputs can break pixel/byte clock registration or rate changes. PCIe uses both pipe-clock parents and many shared ARES bits, making reset ordering a common integration risk. Critical APSS/GPLL0 AO behavior is important for early boot and must not be simplified. Several branches use `BRANCH_VOTED` without direct local gating semantics, so clk-summary may not reveal all real hardware dependencies.

Test signals: a successful boot should show `gcc-qcs404` probing early and registering `cxo`, GPLLs, BLSP, Ethernet, display, PCIe, USB, SDCC, and GPU clocks. Clock summary should confirm `gpll3_out_main` is configured near 930 MHz and that AO GPLL0/APSS AHB remain enabled. Functional coverage should include BLSP UART/I2C/SPI rate changes, Ethernet PTP/RGMII rates, DSI or HDMI display modes through byte/pixel/MDP roots, PCIe link bring-up and reset sequencing, USB2/USB3 enumeration including pipe halt skip, SDCC1/2 clock floors, MDSS/Oxili GDSC power toggling, and bit-level reset assertions for PCIe/USB.

# sources/distributed-fs/ceph-client/drivers/clk/qcom/gcc-qcs615.c

Purpose: global clock controller driver for Qualcomm QCS615, matched by `qcom,qcs615-gcc`. It exposes GCC clocks, resets, fixed hardware clocks, DFS-capable QUPv3 RCGs, and GDSC power domains for storage, USB, PCIe, Ethernet, serial, GPU, media, and interconnect blocks.

Important APIs, types, and functions: the driver defines Alpha PLLs `gpll0`, `gpll3`, `gpll4`, `gpll6`, `gpll7`, and `gpll8`; fixed-factor half-rate outputs `gpll0_out_aux2_div` and `gpll3_out_aux2_div`; postdiv outputs `gpll6_out_main` and `gpll8_out_main`; parent maps for TCXO, always-on TCXO, sleep, and GPLL-derived parents; RCG rate tables for CPUSS AHB, EMAC PTP/RGMII, general-purpose clocks, PCIe auxiliary/refgen, PDM, QSPI, QUPv3 wrappers 0 and 1, SDCC, UFS, USB20 secondary, USB30 primary, and vsensor; and branch gates for aggregate NOC, AHB2PHY, CE, camera/display/video/GPU, EMAC, PCIe, PDM, PRNG, QMIP, QSPI, QUPv3, SDCC, UFS, USB, and reference-clock paths. `gcc_qcs615_hws[]` exports the two fixed-factor clocks, while `gcc_qcs615_clocks[]`, `gcc_qcs615_resets[]`, `gcc_qcs615_gdscs[]`, and `gcc_qcs615_desc` publish the provider tables.

Control flow: `gcc_qcs615_init()` registers the driver at `subsys_initcall` time. Probe maps GCC registers with `qcom_cc_map()`, disables GPLL0 active input to MM blocks and GPU with two `regmap_update_bits()` writes, force-enables selected always-needed branches via `qcom_branch_set_clk_en()` for camera AHB/XO, display AHB/XO, GPU config AHB, video AHB/XO, and CPUSS GNOC, registers DFS data for twelve QUPv3 serial RCGs across wrappers 0 and 1, and then calls `qcom_cc_really_probe()`. Unlike QCM2290 and QCS404, this probe does not explicitly configure PLLs, relying on existing hardware/boot configuration and the common clock ops for runtime control.

State and persistence behavior: persistent state lives in GCC MMIO registers up to `0xa609c`; the driver itself is static descriptor data. The forced branch enables are direct hardware state changes before provider registration and are not modeled as ordinary consumer votes. QUPv3 RCG DFS state is registered so serial clocks can switch rate safely. GDSC state covers EMAC, PCIe, UFS PHY, USB20 secondary, USB30 primary, and multiple votable HLOS1 MMU TBU domains; non-votable domains include wait values for enable, few, and clock-disable sequencing. Critical CPU/system clocks are protected with `CLK_IS_CRITICAL` on CPUSS/sys NOC AHB paths.

Dependencies and integration points: dependencies include common clock/regmap/platform/OF APIs, `dt-bindings/clock/qcom,qcs615-gcc.h`, Qualcomm alpha PLL, branch, RCG, regmap, divider, mux, reset, GDSC, and common CC helpers. External DT parents are `DT_BI_TCXO`, `DT_BI_TCXO_AO`, and `DT_SLEEP_CLK`. Consumers include EMAC, PCIe, QSPI, QUPv3 serial engines, SDCC1/2, UFS PHY/ICE/UniPro/symbol clocks, USB20 secondary and USB30 primary controllers/PHYs, camera/display/video AHB and AXI paths, GPU interconnect paths, CE/PRNG/PDM, and SMMU/MMU TBU power domains.

Risks: probe contains several raw register operations, including GPLL0 input disables and raw branch-enables, so offset drift or undocumented hardware differences can produce silent boot or media/GPU regressions. `qcom_branch_set_clk_en(regmap, 0x480040)` is notably outside the descriptor's usual local cluster naming style and should be treated as a hardware-specific always-on requirement. The two fixed-factor GPLL dividers are exported through `clk_hws`, so dt-binding IDs must align with consumers that need the divided parents. PCIe, UFS, and USB have pipe/symbol/reference clocks with skipped or delayed halt checks, which can hide PHY sequencing bugs. QUPv3 DFS spans twelve roots, increasing the chance of one wrapper/serial instance being missed in validation.

Test signals: boot should show successful `gcc-qcs615` probe with no parent-index failures and all twelve QUP DFS RCGs registered. Clock summary should expose fixed GPLL0/GPLL3 divided outputs, QUP wrapper 0/1 sources, EMAC, PCIe, UFS, USB, SDCC, and critical CPU/system clocks. Functional validation should cover both QUPv3 wrappers under multiple UART/SPI/I2C baud rates, EMAC RGMII/PTP rates, PCIe link and reset behavior, UFS link bring-up including ICE and symbol clocks, USB30 primary and USB20 secondary enumeration, SDCC1/2 high-speed rates, QSPI core rates, GDSC on/off for EMAC/PCIe/UFS/USB domains, and suspend/resume with forced camera/display/GPU/video/CPUSS clocks still sane.
