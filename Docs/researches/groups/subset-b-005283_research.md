# sources/distributed-fs/ceph-client/drivers/scsi/lpfc/lpfc_bsg.c

Purpose: implements the `lpfc` driver's Fibre Channel BSG/SGIOv4 management interface. It accepts FC transport `bsg_job` requests from user space, dispatches standard rport ELS/CT pass-through operations and Broadcom/Emulex vendor commands, manages unsolicited CT event delivery, performs diagnostic loopback and link diagnostics, issues mailbox pass-through commands including SLI_CONFIG external-buffer sessions, exposes RAS firmware logs, and returns trunk/congestion-buffer state.

Important APIs/functions: exported entry points are `lpfc_bsg_request()`, `lpfc_bsg_timeout()`, `lpfc_bsg_ct_unsol_event()`, `lpfc_bsg_ct_unsol_abort()`, and `lpfc_check_fwlog_support()`. Core request handlers include `lpfc_bsg_rport_els()`, `lpfc_bsg_send_mgmt_cmd()`, `lpfc_bsg_hst_vendor()`, `lpfc_bsg_mbox_cmd()`, `lpfc_bsg_diag_loopback_mode()`, `lpfc_bsg_diag_loopback_run()`, `lpfc_sli4_bsg_diag_mode_end()`, `lpfc_sli4_bsg_link_diag_test()`, `lpfc_bsg_get_ras_*()`, `lpfc_bsg_set_ras_config()`, `lpfc_get_trunk_info()`, and `lpfc_get_cgnbuf_info()`. Support routines allocate/copy DMA-backed BSG buffers (`lpfc_alloc_bsg_buffers()`, `lpfc_bsg_copy_data()`), own CT waiter lifetime (`lpfc_bsg_event_new/ref/unref/free()`), issue CT responses (`lpfc_issue_ct_rsp()`), and drive SLI_CONFIG non-embedded external-buffer sessions (`lpfc_bsg_handle_sli_cfg_ext()`, read/write command and ebuf helpers).

Control flow: `lpfc_bsg_request()` dispatches on `fc_bsg_request.msgcode`: host vendor commands go through `lpfc_bsg_hst_vendor()`, rport ELS through `lpfc_bsg_rport_els()`, and rport CT through `lpfc_bsg_send_mgmt_cmd()`. ELS/CT send paths allocate driver-private `bsg_job_data`, DMA command/response buffers, prepare IOCBs/WQEs, place `job->dd_data` under the CT event lock, issue on the ELS ring, then complete asynchronously in completion callbacks that copy response payloads back to the BSG scatterlist and call `bsg_job_done()`. Vendor command dispatch uses the first vendor word from `lpfc_bsg.h` and either completes inline, starts an async IOCB/mailbox, or registers a wait for unsolicited events.

State and persistence: the file maintains only runtime driver state. `job->dd_data` and `bsg_job_data.set_job` are the active ownership handoff between timeout and completion paths. CT event registration persists in `phba->ct_ev_waiters` until unregistered or freed, with queued `event_data` lists for seen/pending CT events and SLI4 context tracking in `phba->ct_ctx[]`. Diagnostic mode mutates live adapter state by blocking/unblocking SCSI hosts, changing link diagnostic/loopback state, setting or clearing `LS_LOOPBACK_MODE`, resetting the port, registering VFI/RPI resources, and using temporary self-login IDs. Mailbox pass-through uses `phba->mbox_ext_buf_ctx` as a multi-call state machine for external-buffer SLI_CONFIG commands with tag, sequence, buffer count, DMA lists, and `LPFC_BSG_MBOX_*` state. RAS commands read or alter `phba->ras_fwlog`; congestion-buffer reset reinitializes congestion statistics. None of this is persisted by the file across driver reload, although firmware/mailbox actions can change adapter-visible state.

Dependencies and integration: depends on Linux BSG, scatter-gather iterators, PCI/DMA allocation, wait queues, spinlocks, mempools, SCSI host blocking, FC transport request/reply layouts, and the lpfc SLI/ELS/mailbox/NVMe/RAS/congestion internals. It is wired into the SCSI FC transport through prototypes in `lpfc_crtn.h` and host template BSG callbacks elsewhere. It consumes command and payload ABI structures from `lpfc_bsg.h`, SLI4 bitfield helpers from hardware headers, node lookup/refcounting, ring buffer posting, mailbox issue APIs, and diagnostic debug dumping.

Important behavior details: CT unsolicited events are filtered by `FC_REG_CT_EVENT` and request ID, copied out of posted receive buffers, and delivered either by waking loopback waiters or completing a pending SET_EVENT job. SLI4 CT management responses use `phba->ct_ctx[tag]` to recover RXID/OXID/SID and invalidate the exchange once a response is issued. Diagnostic loopback first enters a quiesced mode, moves the link into loopback, self-registers an RPI, transmits a synthetic ELX loopback CT sequence to itself, waits for the unsolicited event path, compares the received length, and copies payload bytes back to user space. Mailbox access is filtered by `lpfc_bsg_check_cmd_access()`; destructive/offline-only commands require `FC_OFFLINE_MODE`, while unknown or explicitly denied commands return `-EPERM`. SLI_CONFIG external-buffer handling enforces ordered tag/sequence progression and supports both MSE and HBD non-embedded layouts, with special copy-back handling for READ_OBJECT payloads.

Risks: this is a privileged diagnostic and management entry point with a large hardware blast radius: bad validation could expose firmware, link, mailbox, or DMA misuse. The async timeout/completion race is delicate; correctness relies on clearing `job->dd_data`, `set_job`, and `LPFC_IO_CMD_OUTSTANDING` under the right locks before aborting or completing. Several payload copy paths trust firmware/user-provided lengths after local caps, so boundary tests around BSG_MBOX_SIZE, BPL counts, HBD/MSE counts, read offsets, and reply lengths are important. CT event waiter lifetime uses double `lpfc_bsg_event_unref()` patterns and list movement under `ct_ev_lock`; imbalance could cause leaks or use-after-free. Diagnostic mode can leave I/O blocked or loopback state set if an error path misses cleanup. `lpfc_bsg_get_ras_fwlog()` copies `read_size` from a single selected DMA segment and should be stressed for offsets near segment boundaries. External-buffer mailbox state is global per HBA and can be broken by out-of-order or concurrent callers; error paths reset the session but races need coverage.

Test signals: exercise all `lpfc_bsg_request()` message-code branches and vendor command IDs, including invalid IDs and undersized request/reply buffers. Cover ELS and CT success, LS_RJT, local reject timeout, invalid RPI, IOCB busy/error, and timeout aborts for queued versus already-issued IOCBs. Test CT event registration/get/send-response with multiple waiters, SLI3/HBQ/non-HBQ and SLI4 CT context paths, abort matching, payload truncation, and no-event `-ENOENT`. Test SLI3 and SLI4 diagnostic loopback entry, failure during link-down/link-up waits, self-registration failures, XRI acquisition, and cleanup after interruption. Mailbox tests should include offline-only filtering, extended in/out lengths, BIU diag, READ_EVENT_LOG, DUMP_MEMORY, UPDATE_CFG, embedded and non-embedded SLI_CONFIG, out-of-order external buffers, READ_OBJECT HBD count schemes, and mailbox timeout. RAS, trunk, forced-link-speed, and congestion-buffer commands need support-disabled, active/inactive, reset, short-buffer, and normal-read coverage.

# sources/distributed-fs/ceph-client/drivers/scsi/lpfc/lpfc_bsg.h

Purpose: defines the user/kernel ABI structures, vendor command identifiers, bitfield helpers, and SLI_CONFIG mailbox pass-through layouts consumed by `lpfc_bsg.c` for the `lpfc` BSG management interface. The header explicitly avoids raw user pointers; buffer payloads flow through the BSG request/reply scatterlists.

Important APIs/types: command IDs include CT event registration/retrieval, management response, diagnostic mode/run/end/link-test, management revision, mailbox pass-through, forced link speed, RAS FW logging operations, trunk info, and congestion-buffer info. Request/reply structs include `set_ct_event`, `get_ct_event`, `send_mgmt_resp`, `diag_mode_set`, `sli4_link_diag`, `diag_status`, `dfc_mbox_req`, RAS config/log structures, `lpfc_trunk_info`, and `get_cgnbuf_info_req`. The `bsg_bf_get/set` macro families duplicate kernel bitfield accessors in a userspace-shareable form. SLI_CONFIG layouts include MSE, HBD, embedded-0 and embedded-1 subsystem variants, and `lpfc_sli_config_mbox` with command/status fields.

Control flow: this header has no executable flow, but its command word is the first field in every vendor request and drives the `lpfc_bsg_hst_vendor()` switch. `dfc_mbox_req` controls mailbox payload offset, external input/output word counts, and multi-buffer tag/sequence. SLI_CONFIG fields determine whether `lpfc_bsg.c` treats a mailbox as embedded, non-embedded MSE, or HBD, and whether it is handled by the special external-buffer state machine.

State and persistence: all structures represent transient BSG request or reply payloads. Persistent-looking fields such as RAS log level, forced-link-speed support, trunk active/config bits, and congestion reset flags are merely ABI carriers for live driver or firmware state maintained elsewhere. Constants such as `MANAGEMENT_MAJOR_REV/MINOR_REV`, `BSG_MBOX_SIZE`, and max MSE/HBD counts constrain runtime validation.

Dependencies and integration: tightly coupled to `lpfc_bsg.c`, `lpfc_hw4.h` SLI_CONFIG definitions, FC BSG vendor messages, SLI4 FCOE/COMN subsystem opcodes, and user-space Broadcom/Emulex management tooling. The bitfield macros require standard endian helpers (`cpu_to_le32`, `le32_to_cpu`) and assume the named `_SHIFT`, `_MASK`, and `_WORD` constants adjacent to each field.

Risks: this header is an ABI boundary, so field order, sizes, command IDs, and constants are compatibility-sensitive. The bitfield helpers are macro-based and can silently produce wrong results if `_WORD` fields are not initialized or if endian variants are mismatched. Several structs use raw fixed-width integers without explicit padding/versioning; extending them must preserve old request sizes because `lpfc_bsg.c` accepts legacy mailbox request sizes. SLI_CONFIG opcodes and max-count constants must stay aligned with firmware expectations or mailbox pass-through can mis-address DMA buffers.

Test signals: build tests should verify all structs compile in kernel context and remain size-compatible with expected user-space ABI. Runtime BSG tests should use the header definitions to issue each vendor command with minimum, exact, and undersized request/reply lengths. SLI_CONFIG tests should validate bitfield extraction for EMB, MSE count, HBD count, subsystem/opcode, READ_OBJECT HBD count, trunk status bits, and little-endian setter/getter behavior.

# sources/distributed-fs/ceph-client/drivers/scsi/lpfc/lpfc_compat.h

Purpose: provides small architecture-compatibility helpers for copying between host memory and the adapter SLI memory window. The driver notes that HBA SLI memory stores little-endian longwords, so big-endian hosts must access it a word at a time while little-endian hosts can use normal I/O copy helpers.

Important APIs/functions: `lpfc_memcpy_to_slim(void __iomem *dest, void *src, unsigned int bytes)` writes host data to SLI memory. `lpfc_memcpy_from_slim(void *dest, void __iomem *src, unsigned int bytes)` reads SLI memory into host data. On big-endian builds these functions loop over `uint32_t` words using `writel()`/`readl()`, with a read flush after each write. On other builds they call `__iowrite32_copy()` and `memcpy_fromio()`.

Control flow: compile-time `#ifdef __BIG_ENDIAN` selects the implementation. Both variants convert the byte count into 32-bit word operations for writes; the big-endian read path also operates in 32-bit units. There is no runtime branching, allocation, locking, or error handling.

State and persistence: these helpers persist no state. They perform immediate MMIO or I/O-memory copies and rely on callers to pass valid SLI memory addresses, aligned buffers, and byte counts that make sense as 32-bit word counts.

Dependencies and integration: depends on `<asm/byteorder.h>` for endian detection and on Linux I/O accessors (`writel`, `readl`, `__iowrite32_copy`, `memcpy_fromio`). Integrated by lpfc low-level SLI/mailbox paths that copy to or from the adapter's SLIM region, especially on pre-SLI4 or memory-window interactions.

Risks: callers passing byte counts not divisible by four will silently ignore tail bytes in the word-loop and write-copy paths. The big-endian code casts `void *` to `uint32_t *`, so unaligned source/destination buffers would be unsafe on strict-alignment architectures. There is no bounds checking for the MMIO region. Ordering relies on `readl()` flushes in the big-endian write path and the semantics of the architecture I/O helpers elsewhere.

Test signals: compile both big-endian and little-endian configurations, including sparse checking of `__iomem` casts. Unit or hardware-in-loop tests should copy known multiword patterns to/from a mock or real SLIM region, include non-cacheable I/O memory ordering checks, and assert behavior for lengths that are exact multiples of four. Static analysis should flag any callers that pass non-word-aligned sizes.

# sources/distributed-fs/ceph-client/drivers/scsi/lpfc/lpfc_crtn.h

Purpose: central cross-module prototype header for the `lpfc` driver. It declares the functions, external templates, exported globals, and feature entry points that let the driver's discovery, mailbox, SLI, interrupt, memory, sysfs, BSG, RAS, NVMe, VMID, congestion, SR-IOV, and vport modules call each other without local redeclarations.

Important APIs/types: the header starts with mailbox/link/discovery prototypes such as `lpfc_down_link()`, `lpfc_read_topology()`, `lpfc_reg_rpi()`, `lpfc_reg_vpi()`, cleanup and discovery-state helpers, ELS/CT issue and completion helpers, and node reference/search helpers. It then declares HBA setup/teardown, interrupt handlers, polling, mailbox queue functions, SLI IOCB/WQE issue/prep/abort/cancel functions, DMA buffer allocators, memory pool setup, FC transport/sysfs templates, vport lifecycle functions, BSG entry points, RRQ helpers, debug mailbox dump helpers, SR-IOV/SLI4 queue/resource functions, RAS firmware-log APIs, NVMe/NVMe target entry points, multi-XRI pool management, VMID helpers, and SFP/RDP queries. `node_filter` is the only typedef in this file.

Control flow: the file has no implementation, but it defines integration flow between compilation units. Probe and setup code can call HBA/link/SLI setup functions; interrupt handlers call SLI event handlers; discovery code calls ELS/CT and node APIs; sysfs and BSG code call reset, mailbox, queue, RAS, and diagnostic helpers; NVMe paths call NVMe registration and LS request handlers. The BSG prototypes here connect `lpfc_bsg.c` to the rest of the driver: `lpfc_bsg_request()` and `lpfc_bsg_timeout()` are host-template callbacks, while `lpfc_bsg_ct_unsol_event()` and `lpfc_bsg_ct_unsol_abort()` are called by unsolicited CT receive/abort paths.

State and persistence: no storage is allocated here except external declarations for templates and module/global knobs. The prototypes expose mutating operations on driver state: link state, mailbox queues, IOCB rings, node lists, vport registration, memory pools, congestion/RAS buffers, NVMe local/target ports, VMID tables, and firmware/adapter resources. Persistence depends on each implementation; the header itself only records ABI between lpfc translation units.

Dependencies and integration: depends on many struct and enum declarations from other lpfc and kernel headers being visible before inclusion, including `struct lpfc_hba`, `lpfc_vport`, `lpfc_nodelist`, `lpfc_iocbq`, `LPFC_MBOXQ_t`, `struct bsg_job`, SCSI/FC transport types, NVMe-FC types, timers, queues, and mailbox context enums. It is a high-coupling internal interface: changes in function signatures ripple across many driver files. External objects such as `lpfc_template`, `lpfc_transport_functions`, and debugfs functions bind the driver to SCSI, FC transport, and debugfs registration.

Risks: because this header aggregates nearly all internal prototypes, it can hide excessive coupling and make it easy for unrelated modules to call low-level operations without a narrow ownership boundary. Signature drift or missing conditional compilation can break large portions of the driver. Several prototypes expose sharp operations such as aborting rings, resetting boards, changing PCI/SR-IOV resources, issuing mailbox/IOCB commands, and manipulating global pools; call sites must hold the correct locks and respect runtime state even though those requirements are not encoded in the declarations. Conditional declarations around optional features, such as `LPFC_MXP_STAT`, must match implementation guards.

Test signals: full-driver build coverage is the primary signal, ideally across SLI3/SLI4, NVMe enabled/disabled, NVMe target enabled/disabled, SR-IOV, debugfs, and optional statistics configurations. Link-time tests catch missing implementations or signature mismatches. Runtime smoke tests should exercise the cross-module surfaces represented here: probe/init, link up/down, mailbox wait and async paths, ELS/CT discovery, BSG callbacks, reset/offline/online, RAS setup/stop, NVMe register/unregister, VMID commands, congestion-buffer reporting, and vport create/destroy.
