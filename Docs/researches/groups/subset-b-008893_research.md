## sources/storage-engines/tikv/components/tidb_query_expr/src/impl_compare.rs

Purpose: Implements TiDB/TiKV RPN scalar comparison and extremum builtins: typed relational operators, null-safe equality, `COALESCE`, `GREATEST`, `LEAST`, and `INTERVAL` variants for numeric, string, temporal, JSON, vector, and duration-like values. The file is a central adapter between `tipb::ScalarFuncSig` mappings generated by `#[rpn_fn]` and the concrete comparison semantics supplied by `tidb_query_datatype`.

Important APIs, types, and functions: `compare<C: Comparer>` dispatches ordinary typed comparisons through `Comparer`; `compare_json`, `compare_vector_float32`, and `compare_bytes<C, F>` handle JSON/vector natural ordering and collation-aware byte ordering. `Comparer` abstracts nullable binary comparison over one `EvaluableRet` type. Implementations are `BasicComparer<T, F>` for normal `Ord` types, `UintUintComparer<F>`, `UintIntComparer<F>`, and `IntUintComparer<F>` for MySQL signed/unsigned integer edge cases. `CmpOp` turns `Ordering` into SQL boolean results and provides null behavior; implementations cover `<`, `<=`, `>`, `>=`, `!=`, `=`, and `<=>` via `CmpOpNullEq`. `coalesce`, `coalesce_bytes`, and `coalesce_json` return the first non-null argument, cloning owned representations for varlen types. `greatest_*`, `least_*`, `interval_int`, `interval_real`, and string-as-time/date variants implement MySQL scalar functions. `do_get_extremum` is the generic helper shared by most `GREATEST`/`LEAST` overloads.

Control flow: Nullable binary comparison functions first partition `(None, None)`, partial null, and non-null cases, then delegate either to native `Ord`, collation sort comparison, or explicit signed/unsigned logic. The unsigned comparers avoid interpreting wrapped `u64` values as regular signed integers: `UintIntComparer` treats unsigned values above `i64::MAX` or negative signed RHS as greater; `IntUintComparer` mirrors that for signed LHS. `coalesce*` scans varargs left to right and returns immediately on the first `Some`. `do_get_extremum` requires all arguments non-null; the first `None` returns `None`, otherwise it keeps a borrowed best candidate and returns an owned clone. `INTERVAL` treats null target as `-1`, then binary-searches the remaining sorted arguments and returns MySQL's insertion-position convention. The string-as-time/date variants parse every byte argument as UTF-8 and then as MySQL `Time`; parse or encoding errors are routed through `EvalContext::handle_invalid_time_error`.

State and persistence: The functions are stateless per call. The only mutable state is warning/error policy in `EvalContext` for invalid time/date parsing; no persistent data is written. Results are owned scalar values or writer-backed byte buffers generated by the RPN framework. `#[rpn_fn(nullable, varg)]` and `capture = [ctx]` control generated evaluator state and argument materialization.

Dependencies and integration points: Depends on `tidb_query_codegen::rpn_fn`, `tidb_query_common::Result`, `tidb_query_datatype::codec::data_type::*`, collation `Collator`, JSON/vector ordering, MySQL `Time`, and `EvalContext`. It integrates with scalar-function mapping through generated RPN metadata and with TiDB field-type flags for integer signedness through tests and mapper specialization elsewhere in the module.

Risks and edge cases: Signed/unsigned integer comparison is sensitive because unsigned constants may be carried as negative `i64` bit patterns; using `BasicComparer<Int, _>` in these paths would be wrong. `interval_*` assumes the search list is sorted according to Rust ordering and does not sort or validate it. `greatest_real`/`least_real` rely on `Real` construction/order semantics; NaN inputs can result in `None` because `Real::new(NaN)` fails in tests. String-as-time/date variants return `None` on invalid UTF-8 or invalid temporal strings depending on context SQL mode, so warning handling must stay aligned with TiDB/MySQL. `greatest_string` and `least_string` use raw byte ordering through `Ord` rather than explicit collation, so callers must route collation-sensitive comparisons elsewhere.

Test signals: Unit tests cover all comparison operators over real, duration, decimal, signed integers, and signed/unsigned integer matrices; string comparison across binary, UTF8MB4 bin/no-padding/general/unicode/0900 collations; `COALESCE`; `GREATEST`/`LEAST` for int, real, string, time/date/duration; `INTERVAL`; and string-as-time/date parsing including invalid UTF-8 and invalid temporal values. The tests exercise both ordinary null propagation and `<=>` null-safe equality.

## sources/storage-engines/tikv/components/tidb_query_expr/src/impl_compare_in.rs

Purpose: Implements SQL `IN` predicate evaluation for the RPN expression engine, with a metadata-time optimization that extracts constant RHS values into hash maps and removes them from the runtime expression tree. It supports normal scalar hashing, collation-aware string hashing, signed/unsigned integer correctness, fallback comparison for non-hashable/runtime values, and JSON comparison.

Important APIs, types, and functions: `InByHash` defines `Key`, `StoreKey`, `map`, and `map_ref` so constant and runtime keys can be normalized before hash lookup. `NormalInByHash<K>` stores values directly. `CollationAwareBytesInByHash<C>` stores `SortKey<Bytes, C>` for collation-correct string membership. `Extract` decodes constant protobuf `Expr` values into runtime scalar types; implementations handle `Int`, `Real`, `Bytes`, `Decimal`, and `Duration`, including MySQL enum handling for int/string paths. `InByCompare` marks types handled by linear equality scanning; `DateTime` uses this path because timezone context is unavailable in the metadata mapper. `CompareInMeta<T>` stores `lookup_map`, `has_null`, and integer `unsigned_flags`. Runtime functions are `compare_in_by_hash`, `compare_in_int_type_by_hash`, `compare_in_by_hash_bytes`, `compare_in_by_compare`, and `compare_in_by_compare_json`. `init_compare_in_data` is the metadata mapper and expression-tree rewriter.

Control flow: During expression build, `init_compare_in_data` walks children from right to left, excluding the left operand. Constants are decoded with `Extract`, mapped into the hash key representation, stored in `lookup_map`, and swapped toward the tail before truncation. `NULL` constants set `has_null`; scalar functions and column refs remain as runtime children. Unsigned flags are recorded and truncated in parallel with the children vector. At evaluation time, a null left operand returns SQL null. Hash paths check the metadata map first, then scan remaining runtime RHS values. If a match is found, they return `Some(1)`. If no match is found and either metadata or runtime RHS contained null, they return `None`; otherwise `Some(0)`. The int-specific hash path additionally validates that equal `i64` bit patterns are semantically equal under signed/unsigned flags before accepting a match. The compare fallback performs the same three-valued logic through linear equality only.

State and persistence: The only durable per-expression state is `CompareInMeta`, captured by the generated RPN function metadata and reused for every row/batch evaluation. It mutates the protobuf `Expr` tree during build by removing constant RHS nodes after moving them into metadata. No external persistence is involved.

Dependencies and integration points: Uses `codec::prelude::NumberDecoder`, protobuf `tipb::{Expr, ExprType, FieldType}`, field-type accessors and `FieldTypeFlag::UNSIGNED`, collation `SortKey`, MySQL decimal/duration/enum decoders, and RPN expression builder metadata hooks (`metadata_mapper = init_compare_in_data::<...>`). It integrates tightly with `map_expr_node_to_rpn_func`, `RpnExpressionBuilder`, and scalar signatures such as `InInt` and `InString`.

Risks and edge cases: The metadata mapper changes expression arity, so generated argument counts must agree with the truncated children. Hash lookup correctness depends on `Extract` decoding constants exactly the same way runtime evaluation decodes columns. Collation-aware strings allocate or borrow `SortKey` values, so `map_ref` lifetimes and comparison behavior are important. Signed/unsigned integer handling is subtle: `-1` as signed must not match `u64::MAX` unless both sides are unsigned representations, while positive equal values can match across signedness. The `lookup_map` stores one bool per key, so duplicate constants with different unsigned flags can overwrite each other; the runtime scan and positive-value exception reduce but do not eliminate the need to reason carefully about duplicate signedness combinations. `DateTime` cannot use hash metadata because timezone information is unavailable at mapping time.

Test signals: Tests verify constant extraction removes RHS constants from the expression tree, compare fallback behavior, mixed constant/dynamic `IN` lists, collation-aware string matching across binary and case-insensitive collations, signed/unsigned boundary behavior around `u64::MAX` represented as `-1`, enum decoding for both string and int `IN`, and a benchmark for a 1024-value constant `IN` list.

## sources/storage-engines/tikv/components/tidb_query_expr/src/impl_control.rs

Purpose: Implements MySQL/TiDB control-flow scalar functions in the RPN engine: `IFNULL`, searched `CASE WHEN`, and `IF`. The file provides generic fixed-width implementations plus separate bytes and JSON variants where borrowed values must be converted to owned results.

Important APIs, types, and functions: `if_null<T>`, `if_null_json`, and `if_null_bytes` return the first argument when it is non-null, otherwise the second. `case_when<T>`, `case_when_bytes`, and `case_when_json` consume raw varargs as `(condition, result)` chunks with an optional trailing else value. `if_condition<T>`, `if_condition_json`, and `if_condition_bytes` select between true/false values based on an integer condition. `case_when_validator<T>` validates child return types for raw vararg CASE expressions.

Control flow: `IFNULL` is a simple two-way branch on `lhs.is_some()`. `CASE WHEN` iterates over `args.chunks(2)`: a single final chunk is treated as ELSE; otherwise the first item is borrowed as `Option<Int>` and evaluated as false when null or zero, true for any nonzero integer. The first true condition returns its paired result immediately. If no condition matches and no ELSE exists, it returns `None`. `IF` uses the same integer truthiness rule: null or zero selects the false value. Bytes and JSON functions mirror generic flow but use `EvaluableRef`/`as_*` borrowing and produce owned `Vec<u8>` or `Json`.

State and persistence: These evaluators are stateless. They do not modify `EvalContext` or persist metadata. Validation happens at expression build time through the `extra_validator` hook for CASE functions.

Dependencies and integration points: Uses `tidb_query_codegen::rpn_fn`, `tidb_query_common::Result`, and scalar data traits from `tidb_query_datatype::codec::data_type::*`. The validators call `super::function::validate_expr_return_type`, so CASE type safety is coordinated with the broader scalar-function mapper and generated RPN argument model.

Risks and edge cases: Raw vararg access relies on validators to guarantee alternating int/result types; a missing or incorrect validator could turn `borrow_scalar_value_ref` assumptions into runtime failures. SQL truthiness is intentionally integer-only here; nonzero negative values are true and null is false for conditions. The file does not implement lazy evaluation itself: it selects from already supplied scalar references in the RPN call shape, so upstream expression planning determines whether branch expressions have already been evaluated. Bytes/JSON variants must clone/to_owned to avoid returning borrowed data beyond the evaluation call.

Test signals: Tests cover `IFNULL` null combinations, CASE first-match and ELSE behavior, null conditions, null result values, bytes CASE, and `IF` choosing true/false branches with null-as-false semantics.

## sources/storage-engines/tikv/components/tidb_query_expr/src/impl_encryption.rs

Purpose: Implements hashing, compression, decompression, legacy password hashing, uncompressed-length inspection, and random byte generation scalar functions for TiDB pushed down into TiKV's RPN engine. Despite the filename, most functions are MySQL-compatible utility/hash functions rather than reversible encryption.

Important APIs, types, and functions: `md5` and `sha1` produce lowercase hex digest bytes. `sha2` chooses SHA-224/256/384/512 based on a numeric argument, treating `0` as SHA-256 and warning/returning null for unsupported lengths. `compress` writes a MySQL-compatible zlib payload prefixed by a four-byte little-endian original length and optionally appends `.` when compressed bytes end with a space. `uncompress` reverses this format and emits warnings for corrupt data or length mismatch. `password` implements deprecated MySQL password hash behavior as `*` plus SHA1(SHA1(input)) in hex and always appends a deprecation warning. `hex_digest` wraps OpenSSL hashing. `uncompressed_length` reads the length prefix with corruption warnings for too-short nonempty inputs. `random_bytes` validates length in `[1, 1024]` and fills a byte vector with OpenSSL random bytes.

Control flow: Digest functions short-circuit null inputs and otherwise call `hex_digest`. `sha2` requires both input and hash length; unsupported hash lengths append `incorrect_parameters("sha2")` and return null. `compress` handles empty input as empty output, allocates a vector for the length header plus zlib output, encodes with `ZlibEncoder::read_to_end`, and returns null on compression failure. `uncompress` rejects too-short nonempty input, reads the expected length, decompresses from byte 4 onward, and returns bytes only when decoded length is nonzero and no greater than the stored length. `random_bytes` fails with overflow for invalid sizes and maps OpenSSL random failure into `EvaluateError::Other`.

State and persistence: Functions are per-call stateless except for warnings accumulated in `EvalContext`. `random_bytes` depends on external OpenSSL RNG state but does not persist output. Writer functions use RPN `BytesWriter`/`BytesGuard` to avoid unnecessary allocation copies when possible.

Dependencies and integration points: Depends on `openssl::hash`, `crypto::rand`, `flate2` zlib readers, `byteorder::LittleEndian`, `tidb_query_common::error::EvaluateError`, and `tidb_query_datatype::expr::{EvalContext, Error}`. It integrates with generated RPN writer and nullable function signatures and with MySQL warning semantics through `EvalContext::warnings`.

Risks and edge cases: `compress` stores input length as `u32`, so very large byte strings would truncate the advertised length even though vector capacity uses `usize`; caller limits should prevent pathological inputs. `uncompress` accepts decoded lengths smaller than the stored length but rejects larger lengths and zero decoded length, matching documented behavior but requiring compatibility vigilance. `password` is deprecated and intentionally warns; consumers must not treat it as secure password storage. `random_bytes` has a hard-coded maximum of 1024 bytes and returns errors, not null, for invalid lengths. Hash outputs are ASCII hex bytes, not binary digests.

Test signals: Tests validate MD5/SHA1/SHA2 known vectors including Unicode and invalid UTF-8 byte sequences, null handling, compression and decompression hex fixtures, uncompressed-length behavior on corrupt and short inputs, random byte length and invalid-length errors, and legacy `PASSWORD` known outputs.

## sources/storage-engines/tikv/components/tidb_query_expr/src/impl_json.rs

Purpose: Implements a broad set of MySQL/TiDB JSON scalar functions for the RPN evaluator: inspection (`JSON_DEPTH`, `JSON_TYPE`, `JSON_VALID`, `JSON_LENGTH`, `JSON_KEYS`), construction (`JSON_ARRAY`, `JSON_OBJECT`, `JSON_QUOTE`), modification (`JSON_SET`, `JSON_INSERT`, `JSON_REPLACE`, `JSON_ARRAY_APPEND`, `JSON_REMOVE`), extraction (`JSON_EXTRACT`, `JSON_UNQUOTE`), containment/membership (`JSON_CONTAINS`, `MEMBER OF`), and merge operations (`JSON_MERGE`, `JSON_MERGE_PATCH`).

Important APIs, types, and functions: `json_depth` and `json_type` call methods on `JsonRef`. `json_set`, `json_insert`, and `json_replace` share `json_modify(args, ModifyType)`. `json_array_append` appends values into extracted path targets and writes back with `ModifyType::Set`. `json_modify_validator`, `json_object_validator`, `json_with_paths_validator`, `json_with_path_validator`, `json_contains_validator`, and `member_of_validator` enforce raw-vararg type contracts. `json_array` converts SQL null arguments into JSON null. `json_object` builds a `BTreeMap<String, Json>`, rejects null keys, and validates UTF-8 keys. `json_merge` delegates to `Json::merge`; `json_merge_patch` implements RFC 7396-style merge-patch sequencing. `json_quote`, `quote`, `json_unquote`, and `unquote_string` handle JSON string quoting/unquoting. `parse_json_path_list` and `parse_json_path` convert byte path arguments to `PathExpression`.

Control flow: Most nullable raw-vararg functions first validate minimum/maximum arity through `#[rpn_fn]` and explicit `assert!`, then unpack `ScalarValueRef` by expected type. Path-based functions parse every supplied path; a null path short-circuits to `None` through `try_opt!`. Modification functions clone the base JSON, build path/value arrays, and call JSON library methods. `json_array_append` differs by returning null when the base SQL value is null, then for each path extracts the current element, merges/appends the new value, and writes it back only when the path exists. `json_valid` handles both typed JSON and bytes: JSON input is valid when present; byte input is parsed with `serde_json`; other types return 0, null input returns null. `json_contains` optionally extracts a path and rejects wildcard paths by returning null before calling `json_contains`. `json_merge_patch` scans from the right for the last non-object or null input; if that element is null it returns null, otherwise it starts merging from that point to implement MySQL/RFC behavior where later non-object values dominate earlier inputs.

State and persistence: The file is stateless beyond temporary owned JSON clones and path vectors. There is no persistent metadata. Writer-backed functions (`json_type`, `json_quote`) produce byte output through `BytesWriter`. Validators run at expression construction time and prevent runtime type ambiguity for raw varargs.

Dependencies and integration points: Uses `tidb_query_codegen::rpn_fn`, `tidb_query_datatype::codec::mysql::json::*` for `Json`, `JsonRef`, `JsonType`, `ModifyType`, `PathExpression`, parse/merge/extract/contains operations, `serde_json` for validation/unquote syntax checks, and `json_unquote` crate helper for string unescaping. It integrates with `super::function::validate_expr_return_type` and generated scalar signatures for one-arg and two-arg variants such as `JsonKeysSig`/`JsonKeys2ArgsSig`.

Risks and edge cases: Raw vararg functions depend heavily on validators matching exact call shapes; incorrect scalar signature mapping can panic on `assert!` or misborrow values. Several functions distinguish SQL null from JSON null, especially `json_array`, `json_object`, `json_merge`, `json_merge_patch`, and `json_array_append`; regressions here are easy. Path wildcard handling is function-specific: `json_contains` returns null for wildcard paths, while `json_keys` tests expect errors for wildcard paths through JSON library behavior. `json_object` uses `BTreeMap`, so duplicate keys are overwritten and output order is sorted by key, not insertion. `json_unquote` first validates fully quoted strings with `serde_json::IgnoredAny`; invalid quoted JSON strings error, while unquoted strings pass through. The file clones JSON values frequently, so large documents may have allocation costs.

Test signals: Tests cover JSON depth/type, set/insert/replace modification, arrays/objects including null keys and arity errors, merge and merge-patch examples from RFC 7396 and MySQL behavior, quote/unquote escaping and invalid quoted strings, extract/remove/length/valid, contains with and without paths including null and wildcard behavior, keys with path and wildcard errors, member-of semantics, and extensive array-append cases from TiDB/MySQL examples.

## sources/storage-engines/tikv/components/tidb_query_expr/src/impl_like.rs

Purpose: Implements the SQL `LIKE` predicate for byte-string inputs in the RPN evaluator, with pluggable collation comparison and charset decoding. It supports `%`, `_`, and caller-provided escape characters while preserving MySQL/TiDB behavior across binary and UTF8MB4 collations.

Important APIs, types, and functions: The single exported `like<C: Collator, CS: Charset>(target, pattern, escape)` function is annotated with `#[rpn_fn]` and returns `Option<i64>` as SQL boolean. It uses `CS::decode_one` to advance pattern and target by characters or bytes according to the selected charset and `C::sort_compare(..., true)` to compare one decoded target unit against one decoded pattern unit under the selected collation.

Control flow: The matcher keeps pattern and target offsets (`px`, `tx`) plus backtracking offsets after the most recent `%` (`next_px`, `next_tx`). It decodes the next pattern unit. `_` consumes one target unit if available. `%` advances the pattern, records a backtracking point, and immediately succeeds if it is the final pattern token. For ordinary characters, the code honors escape when the current pattern unit equals the escape code and another pattern unit follows, then compares the current target unit to the current pattern unit via collation. On mismatch, if a previous `%` exists, it advances `next_tx` by one decoded target unit, restores `px` to the token after `%`, and retries. Without a valid backtrack point it returns false. If both pattern and target are exhausted, it returns true.

State and persistence: The algorithm is entirely local to one call. It maintains only offsets and has no external state or metadata. The returned value is always `Some(0)` or `Some(1)` because the function is not annotated nullable; null propagation is handled by generated RPN wrappers/signature selection.

Dependencies and integration points: Depends on `tidb_query_datatype::codec::collation::{Collator, Charset}` and scalar data types. The function is selected by scalar signature `LikeSig`, with the code generator specializing `C` and `CS` from return and argument field collations/charsets. Tests show integration with `FieldTypeBuilder` collation assignment for return, target, and pattern fields.

Risks and edge cases: Correctness depends on matching the intended charset decoder to the pushed-down collation metadata. In binary charset, `_` can match one byte rather than one Unicode scalar, which is expected for binary but surprising for wide characters. Escape handling treats escape as a Unicode code point cast from `i64`; multibyte escape characters work only when decoded consistently by `CS`. The backtracking algorithm is simple and may revisit many positions for patterns with repeated `%` and late mismatches, so worst-case matching can be costly on long strings. `C::sort_compare` errors are treated as ordinary comparison non-match because only `Ok(Equal)` advances.

Test signals: Tests cover exact, prefix, suffix, infix, repeated `%`, `_`, trailing escape-like patterns, custom escape characters, pathological repeated wildcard mismatch, case-sensitive and case-insensitive collations, accent/case behavior, wide characters, emoji, binary-vs-UTF8 charset differences, and scenarios where TiDB does not push new collation metadata and binary comparison must still decode with argument charsets.
