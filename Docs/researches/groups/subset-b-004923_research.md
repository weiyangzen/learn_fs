# sources/distributed-fs/ceph-client/drivers/net/wireless/realtek/rtw89/debug.c

Purpose: Implements the Realtek rtw89 driver's debug messaging and debugfs control surface. With `CONFIG_RTW89_DEBUGFS`, it exposes register/RF access, transmit-power table inspection, MAC memory and debug-port dumps, raw H2C injection, early-H2C staging, firmware crash/SER simulation, coexistence toggles, firmware-log toggles, PHY/station/CAM state dumps, DM disable controls, MLO mode controls, beacon tracking, and firmware-provided MAC diagnostics. With `CONFIG_RTW89_DEBUGMSG`, it owns the exported `rtw89_debug_mask` module parameter and the gated `rtw89_debug()` printer.

Important APIs, types, and functions: The public entry points are `rtw89_debugfs_init()`, `rtw89_debugfs_deinit()`, and `rtw89_debug()`. The debugfs framework is built around `struct rtw89_debugfs_priv_opt`, `struct rtw89_debugfs_priv`, `struct rtw89_debugfs`, and `struct rtw89_debugfs_iter_data`. Generic dispatch is handled by `rtw89_debugfs_file_read()`, `rtw89_debugfs_file_write()`, and helper callbacks that optionally enter `wiphy_locked_debugfs_read()` or `wiphy_locked_debugfs_write()`. Major debugfs callbacks include `rtw89_debug_priv_read_reg_*`, `rtw89_debug_priv_write_reg_set()`, `rtw89_debug_priv_read_rf_*`, `rtw89_debug_priv_write_rf_set()`, `rtw89_debug_priv_rf_reg_dump_get()`, `rtw89_debug_priv_txpwr_table_get()`, `rtw89_debug_priv_mac_reg_dump_*`, `rtw89_debug_priv_mac_mem_dump_*`, `rtw89_debug_priv_mac_dbg_port_dump_*`, `rtw89_debug_priv_send_h2c_set()`, `rtw89_debug_priv_early_h2c_*`, `rtw89_debug_priv_fw_crash_*`, `rtw89_debug_priv_ser_counters_get()`, `rtw89_debug_priv_btc_info_get()`, `rtw89_debug_priv_btc_manual_set()`, `rtw89_debug_priv_fw_log_manual_set()`, `rtw89_debug_priv_phy_info_get()`, `rtw89_debug_priv_stations_get()`, `rtw89_debug_priv_disable_dm_*`, `rtw89_debug_priv_mlo_mode_*`, `rtw89_debug_priv_diag_mac_get()`, and `rtw89_debug_priv_beacon_info_get()`. Static tx-power description types `struct txpwr_ent`, `struct txpwr_map`, and `struct dbgfs_txpwr_table` encode AX/BE by-rate, limit, and RU-limit register layouts.

Control flow: `rtw89_debugfs_init()` clones `rtw89_debugfs_templ`, creates the device's `rtw89` debugfs directory below the wiphy debugfs directory, then registers two groups of files through macros that bind file names to callback state. Reads allocate a per-file reusable buffer via `devm_kzalloc()`, call the relevant `cb_read`, store the number of bytes in `rused`, and serve data through `simple_read_from_buffer()` on subsequent offsets. Writes copy user data into a NUL-terminated kernel buffer, then dispatch to `cb_write`. Selection-style entries, such as `read_reg`, `read_rf`, `mac_reg_dump`, `mac_mem_dump`, and `mac_dbg_port_dump`, store parameters in the debugfs private union during write and consume them during read.

Hardware diagnostic flows are mostly direct. Register/RF callbacks parse hex or decimal arguments and call the low-level `rtw89_read*`, `rtw89_write*`, `rtw89_read_rf()`, and `rtw89_write_rf()` helpers. TX power reporting leaves power-save mode, reads regulatory/SAR/TAS/antenna-gain context, walks chip-generation-specific tx-power register maps, decodes signed 7-bit power entries according to `txpwr_factor_mac`, and formats table rows. MAC register and memory dumps choose fixed page ranges or indirect memory windows; selected RTL8852C TX FIFO memory reads temporarily set `B_AX_TCR_FORCE_READ_TXDFIFO`. MAC debug-port dumps first configure a selected port's mux registers, validate availability against HCI type, chip family, and MAC enable state, then iterate the selector range and read the configured status register after a short delay.

Firmware and runtime controls have side effects. `send_h2c` converts hex text into binary and sends raw H2C through `rtw89_fw_h2c_raw()`. `early_h2c` stores converted blobs on `rtwdev->early_h2c_list` under the wiphy lock, with a `00 00` sentinel clearing all early H2Cs. `fw_crash` accepts crash type 1, 2, or 3 and triggers firmware CPU exception, L1 reset simulation, or L0 reset simulation through chip-generation-specific helpers; L0 simulation may deliberately avoid setting `RTW89_FLAG_CRASH_SIMULATING`. SER counters read both software counters and AX/BE hardware registers after leaving power-save mode. BTC and firmware-log entries update coexistence manual state or send firmware-log H2Cs. PHY and station dumps walk mac80211 stations/interfaces atomically, dereference link state under RCU where needed, and format rate, RSSI, EVM, SNR, CAM, BA CAM, and packet-offload state. MLO controls disable MLO DM, then apply MLSR switching to MLD VIFs. `diag_mac` leaves low-power state and interprets firmware diagnostic rule elements, filtering by HCI and active band before reading normal or PCI config registers.

State and persistence behavior: Debugfs file state persists in the per-device `rtwdev->debugfs` clone until deinit; selection parameters and enabled dump-package bits are stored in `struct rtw89_debugfs_priv`. Read buffers are allocated lazily and reused, while `rused` preserves the previous read length for nonzero file offsets. Many callbacks mutate persistent driver or hardware state: raw register writes, RF writes, debug mux selection, TX FIFO force-read bits, firmware H2C queues, crash simulation flags, BTC manual control, firmware-log enablement, `hal->disabled_dm_bitmap`, and MLO mode. `rtw89_debug_mask` is a module parameter, exported for other rtw89 objects, and gates debug and hex-dump output. `rtw89_debugfs_deinit()` only frees the cloned metadata; debugfs removal is presumably handled by the enclosing wiphy/debugfs teardown.

Dependencies and integration points: Includes rtw89 core subsystems (`coex.h`, `fw.h`, `mac.h`, `pci.h`, `phy.h`, `ps.h`, `reg.h`, `sar.h`, `util.h`) plus Linux debugfs, wiphy locking, RCU, mac80211 station/interface iteration, hex parsing, and vmalloc allocation. Register names and bit masks come from `reg.h`; chip-generation dispatch depends on `rtwdev->chip`, `chip->mac_def`, and feature bits in `rtwdev->fw`. The file integrates with firmware H2C paths, SER recovery simulation, BTC coexistence, SAR/TAS/regulatory reporting, CAM allocation state, MLO/mlsr switching, packet offload lists, beacon tracking, and firmware element parsing.

Risks: This is an intentionally privileged debug surface with direct register, RF, memory, H2C, firmware crash, DM, and MLO controls; misuse can destabilize hardware or firmware. Several diagnostic paths alter mux or force-read registers and do not always restore previous values, which is acceptable for debug dumping but risky if used during active traffic. `rtw89_debugfs_file_read()` keeps a lazily allocated buffer without explicit per-open isolation, so repeated reads of the same debugfs node share device-level state. Large dumps rely on fixed buffer sizes and `rtw89_might_trailing_ellipsis()` rather than full dynamic sizing. Error paths in hardware dump code can exit after partial side effects. The MAC debug-port selector table is hard-coded for specific AX register layouts and has many chip/HCI validity branches. Raw H2C and crash simulation paths depend on firmware readiness and feature bits, but still provide a powerful failure-injection interface.

Test signals: Build coverage should include all combinations of `CONFIG_RTW89_DEBUGFS` and `CONFIG_RTW89_DEBUGMSG`, plus AX and BE chip-generation objects that reference exported debug symbols. Runtime smoke tests can read every read-only node, perform harmless select/read operations for `read_reg`, `read_rf`, `mac_reg_dump`, `mac_mem_dump`, and `mac_dbg_port_dump`, and verify locked callbacks do not trigger lockdep warnings. Hardware validation should cover PCIe vs USB/SDIO validity filtering, DBCC/CMAC1 cases, RTL8852C-specific register branches, BE crash triggers, firmware diagnostic rules, MLO debug controls, and buffer truncation indicators on large dumps. Negative tests should feed malformed arguments, unsupported crash types, non-hex H2C data, unsupported MAC pages, and unavailable debug ports.

# sources/distributed-fs/ceph-client/drivers/net/wireless/realtek/rtw89/debug.h

Purpose: Declares the rtw89 debug categories, debugfs lifecycle hooks, and logging helpers shared across the driver. It provides compile-time fallbacks so most call sites can use `rtw89_debugfs_init()`, `rtw89_debugfs_deinit()`, `rtw89_debug()`, `rtw89_hex_dump()`, and `rtw89_debug_is_enabled()` regardless of whether debugfs or debug messages are enabled in the kernel configuration.

Important APIs, types, and functions: `enum rtw89_debug_mask` defines bit positions for TX/RX, RFK, RFK tracking, CFO, TSSI, TX power, HCI, rate adaptation, regulatory, PHY tracking, DIG, SER, firmware, BTC, beamforming, hardware scan, SAR, state, WoW, UL TB, channel, ACPI, EDCCA, power-save, and unexpected-event messages. `enum rtw89_debug_mac_reg_sel` declares the MAC/BB/IQK/RFC page selectors consumed by `debug.c`'s `mac_reg_dump` file. Under `CONFIG_RTW89_DEBUGFS`, the header declares `rtw89_debugfs_init()` and `rtw89_debugfs_deinit()`; otherwise both are empty inline stubs. It also maps `rtw89_info()`, `rtw89_info_once()`, `rtw89_warn()`, and `rtw89_err()` to device logging macros.

Control flow: For debug messages, `CONFIG_RTW89_DEBUGMSG` exposes the external `rtw89_debug_mask` and declares `rtw89_debug()`. `rtw89_hex_dump()` first checks `rtw89_debug_mask & mask`, then emits a byte dump through `print_hex_dump_bytes()`. `rtw89_debug_is_enabled()` returns the same mask test. Without `CONFIG_RTW89_DEBUGMSG`, all three are inline no-ops or `false`, allowing call sites to compile out runtime logging support while keeping source code simple.

State and persistence behavior: The only declared mutable global state is `rtw89_debug_mask`, implemented in `debug.c` as a module parameter when debug messages are enabled. Debugfs state is opaque to this header and owned by `struct rtw89_dev`. The logging macros do not persist data; they route messages to the device's kernel log stream.

Dependencies and integration points: Includes `core.h` for `struct rtw89_dev`, chip and device definitions, and kernel helpers such as `BIT()`. The mask enum is used throughout rtw89 subsystems to categorize `rtw89_debug()` and `rtw89_hex_dump()` messages. The MAC register selector enum is part of the debugfs ABI implemented by `debug.c`.

Risks: Adding or reordering enum values changes the user-visible meaning of `debug_mask` bits and can break scripts or field debugging workflows. The logging macros assume a valid `rtwdev->dev`. Because no-op stubs hide debugfs/debugmsg calls in non-debug builds, code must not rely on those calls for required side effects.

Test signals: Compile tests should cover enabled and disabled `CONFIG_RTW89_DEBUGFS` and `CONFIG_RTW89_DEBUGMSG` configurations. Runtime checks should confirm setting the `debug_mask` module parameter enables only the intended categories and that debugfs init/deinit calls are harmless in non-debugfs builds.

# sources/distributed-fs/ceph-client/drivers/net/wireless/realtek/rtw89/efuse.c

Purpose: Implements AX-generation rtw89 efuse and OTP reading. It dumps physical efuse bytes through DDV register access or DAV XTAL-SI access, converts packed physical efuse records into logical maps, parses chip efuse and phycap data through chip-specific callbacks, reads efuse version/CV bits, and extracts firmware secure-boot/MSS metadata for AX chips.

Important APIs, types, and functions: Exported or cross-file entry points are `rtw89_parse_efuse_map_ax()`, `rtw89_parse_phycap_map_ax()`, `rtw89_cnv_efuse_state_ax()`, `rtw89_read_efuse_ver()`, `rtw89_efuse_recognize_mss_info_v1()`, and `rtw89_efuse_read_fw_secure_ax()`. Important internal helpers include `rtw89_switch_efuse_bank()`, `rtw89_enable_otp_burst_mode()`, `rtw89_enable_efuse_pwr_cut_ddv()`, `rtw89_disable_efuse_pwr_cut_ddv()`, `rtw89_dump_physical_efuse_map_ddv()`, `rtw89_dump_physical_efuse_map_dav()`, `rtw89_dump_physical_efuse_map()`, `rtw89_dump_logical_efuse_map()`, `get_mss_dev_type_idx()`, and `rtw89_efuse_recognize_mss_index_v0()`. Local enums model RTL8852A Wi-Fi/BT efuse bank selection and firmware secure MSS device types.

Control flow: `rtw89_parse_efuse_map_ax()` checks the autoload-suspend bit to mark `rtwdev->efuse.valid`, allocates physical and logical maps sized from `rtwdev->chip`, dumps DDV and optional DAV physical maps, initializes the combined logical map to `0xff`, decodes physical records into logical bytes, logs the map when firmware debug is enabled, and delegates final interpretation to `rtwdev->chip->ops->read_efuse()`. `rtw89_parse_phycap_map_ax()` similarly dumps a physical region starting at `chip->phycap_addr` and passes it to `read_phycap()`. `rtw89_read_efuse_ver()` reads one byte at `EF_FV_OFSET`, extracts `EF_CV_MASK`, and treats `EF_CV_INV` as absent.

Physical access has two paths. DDV reads enable efuse power-cut circuitry for non-RTL8852A chips, optionally enable OTP burst mode for RTL8852B CAV, program `R_AX_EFUSE_CTRL` with each address, poll `B_AX_EF_RDY`, and copy the low data byte. DAV reads program XTAL SI address and mode registers, poll `XTAL_SI_RDY`, then read `XTAL_SI_READ_VAL`. The wrapper switches RTL8852A to the Wi-Fi efuse bank, chooses DDV or DAV, and retries failed dumps up to five times with warnings.

Logical parsing walks from `sec_ctrl_efuse_size` until an invalid `0xff` header or the end of the physical region. Each two-byte header encodes block index and word-enable bits; enabled two-byte words are copied into `log_map` at `(block << 3) + (word << 1)`, with bounds checks against physical and logical sizes. Secure-boot parsing reads two efuse bytes, interprets legacy v0 indexes from external PN/customer/serial fields, interprets v1 MSS device type, customer index, and key number, and sets `rtwdev->fw.sec.secure_boot` when either format is recognized.

State and persistence behavior: Successful parse calls populate persistent fields in `rtwdev->efuse`, chip-specific efuse state via `read_efuse()`, phycap state via `read_phycap()`, and `rtwdev->fw.sec` secure-boot/MSS fields. Temporary maps are heap-allocated and freed before return. DDV access mutates power/ISO/OTP-burst registers and is intended to restore them after the dump; the retry wrapper repeats the whole sequence on failure. `rtw89_cnv_efuse_state_ax()` is currently a no-op placeholder, preserving a common AX/BE interface.

Dependencies and integration points: Includes `debug.h`, `efuse.h`, `mac.h`, and `reg.h`. The implementation depends on chip metadata (`physical_efuse_size`, `logical_efuse_size`, DAV sizes, sec-control size, phycap address/size, chip ID, chip version), chip callbacks (`read_efuse`, `read_phycap`), MAC XTAL-SI helpers, register accessors, bitfield helpers, and debug logging. `rtw89_efuse_recognize_mss_info_v1()` is shared with BE secure parsing.

Risks: `rtw89_dump_physical_efuse_map_ddv()` returns immediately on poll failure without disabling efuse power-cut state, so a timeout can leave hardware state altered until later recovery. Logical parser correctness depends on efuse header encoding, size fields, and sec-control offsets matching each chip. Secure-boot parsing uses inverted efuse bit encodings and chip-specific special cases, making regressions easy when adding devices. `rtw89_hex2bin` is not here, but debug logging of full maps can expose calibration/security-sensitive efuse content when `RTW89_DBG_FW` is enabled. Bounds checks are present for logical writes, but malformed physical maps still abort the whole parse.

Test signals: Unit-style tests can feed synthetic physical efuse maps to the logical parser shape, including invalid headers, disabled words, boundary words, and oversized block indexes if refactored for testability. Hardware tests should cover RTL8852A bank switching, RTL8852B CAV OTP burst mode, DDV retry behavior, DAV XTAL-SI reads, absent DAV sizes, phycap size zero, invalid `EF_CV_INV`, and both MSS v0/v1 secure-boot encodings. Compile/build coverage should ensure all exported symbols resolve for AX chip modules.

# sources/distributed-fs/ceph-client/drivers/net/wireless/realtek/rtw89/efuse.h

Purpose: Defines shared rtw89 efuse constants, logical-block configuration, and AX/BE efuse parser entry points. It is the common contract between chip bring-up code, AX/BE efuse implementations, and chip-specific efuse interpretation callbacks.

Important APIs, types, and functions: `RTW89_EFUSE_BLOCK_ID_MASK`, `RTW89_EFUSE_BLOCK_SIZE_MASK`, and `RTW89_EFUSE_MAX_BLOCK_SIZE` define the packed block descriptor format used by BE block parsing. `EF_FV_OFSET`, `EF_FV_OFSET_BE_V1`, `EF_CV_MASK`, and `EF_CV_INV` identify efuse version/CV locations and invalid values. `struct rtw89_efuse_block_cfg` stores a packed `offset` and byte `size` for a logical efuse block. Declared functions include AX parsers (`rtw89_parse_efuse_map_ax()`, `rtw89_parse_phycap_map_ax()`, `rtw89_cnv_efuse_state_ax()`), BE parsers (`rtw89_parse_efuse_map_be()`, `rtw89_parse_phycap_map_be()`, `rtw89_cnv_efuse_state_be()`), efuse version readers (`rtw89_read_efuse_ver()`, `rtw89_efuse_read_ecv_be()`), and secure firmware helpers (`rtw89_efuse_recognize_mss_info_v1()`, `rtw89_efuse_read_fw_secure_ax()`, `rtw89_efuse_read_fw_secure_be()`).

Control flow: This header does not implement control flow directly. Consumers choose AX or BE function pointers during chip setup or probe paths, then those implementations dump physical maps, convert them to logical maps, and call chip-specific readers. The block configuration structure is consumed mainly by BE parsing to select HCI/RF/ADIE logical windows out of the packed efuse stream.

State and persistence behavior: The header defines no storage. Its constants determine how implementation files interpret persistent OTP/efuse data into `rtwdev->efuse`, `rtwdev->hal.cv`, phycap data, and `rtwdev->fw.sec`.

Dependencies and integration points: Includes `core.h` for `struct rtw89_dev`, bit macros, and efuse block enum definitions. The declarations are used by chip files that wire operations, by probe paths that parse efuse/phycap data, and by firmware secure-loading code that needs MSS/security metadata.

Risks: The misspelled `EF_FV_OFSET` name is ABI only at source level but should be preserved unless all users are updated. Incorrect block offset packing or size values in chip tables can cause BE parser misreads. Changing `EF_CV_MASK` or invalid value semantics would affect chip version detection and workaround selection.

Test signals: Build coverage should ensure both AX and BE implementation files satisfy these declarations. Runtime validation should compare parsed efuse CV, block sizes, secure-boot fields, and phycap output against known-good devices or golden efuse dumps.

# sources/distributed-fs/ceph-client/drivers/net/wireless/realtek/rtw89/efuse_be.c

Purpose: Implements BE-generation rtw89 efuse, phycap, secure-boot, and efuse CV reading. It is the BE counterpart to `efuse.c`, but uses BE register names, 4-byte-aligned DDV access, logical block descriptors, HCI-specific logical block selection, BE power-state conversion, and BE secure-boot selector decoding.

Important APIs, types, and functions: Public entry points are `rtw89_cnv_efuse_state_be()`, `rtw89_parse_efuse_map_be()`, `rtw89_parse_phycap_map_be()`, `rtw89_efuse_read_fw_secure_be()`, and exported `rtw89_efuse_read_ecv_be()`. Key helpers include `rtw89_enable_efuse_pwr_cut_ddv_be()`, `rtw89_disable_efuse_pwr_cut_ddv_be()`, `rtw89_dump_physical_efuse_map_ddv_be()`, `rtw89_dump_physical_efuse_map_dav_be()`, `rtw89_dump_physical_efuse_map_be()`, `rtw89_eeprom_parser_be()`, `rtw89_parse_logical_efuse_block_be()`, and `get_sb_cryp_sel_idx()`. Secure constants define BE external PN, serial, SB crypto selector, and security-block layout.

Control flow: `rtw89_parse_efuse_map_be()` checks BE autoload status, allocates physical DDV and optional DAV maps, dumps both physical regions, selects the HCI digital logical block based on USB versus PCIe/SDIO HCI type, parses that block, then parses the RF block. Each logical block parse allocates a block-sized `log_map`, calls `rtw89_eeprom_parser_be()`, optionally hex-dumps the result, and delegates to `chip->ops->read_efuse(rtwdev, log_map, block)`. `rtw89_parse_phycap_map_be()` dumps the physical phycap window and delegates to `read_phycap()`.

BE physical DDV reads require 4-byte-aligned address and size. The function enables BE efuse power-cut state, programs `R_BE_EFUSE_CTRL`, polls `B_BE_EF_RDY`, reads 32-bit data from `R_BE_EFUSE_CTRL_1_V1`, and stores little-endian words into the caller buffer. DAV reads still use XTAL-SI byte access. `rtw89_dump_physical_efuse_map_be()` converts efuse state to active before the dump and idle afterward, and logs physical maps when firmware debug is enabled. `rtw89_cnv_efuse_state_be()` toggles `B_BE_BT_DISN_EN` and, when leaving idle, polls `R_BE_IC_PWR_STATE` until the whole system reaches `MAC_AX_SYS_ACT`.

Logical parsing in `rtw89_eeprom_parser_be()` supports two header formats. ADIE/DAV blocks use two-byte headers with an 8-bit offset field; other blocks use three-byte headers carrying page, 13-bit offset, and word-enable bits. The parser computes the requested block's page and page offset from `struct rtw89_efuse_block_cfg`, fills the output with `0xff`, walks physical records after the secure-control area, validates block indexes, copies enabled words only when the record page and logical index overlap the requested `[offset, offset + size)` window, and handles one-byte overlap at odd boundaries.

Secure and CV flows are BE-specific. `rtw89_efuse_read_fw_secure_be()` reads four bytes from the BE security area, decodes the two-byte SB crypto selector with mirrored/complement checks in `get_sb_cryp_sel_idx()`, maps it through `sb_sel_mgn`, then reuses AX's `rtw89_efuse_recognize_mss_info_v1()` for MSS fields and sets `secure_boot` on success. `rtw89_efuse_read_ecv_be()` reads a 4-byte-aligned region containing `EF_FV_OFSET_BE_V1`, extracts `EF_CV_MASK`, rejects `EF_CV_INV`, and persists the value in `rtwdev->hal.cv`.

State and persistence behavior: Successful parsing updates `rtwdev->efuse.valid`, chip-specific efuse fields through `read_efuse()`, phycap fields through `read_phycap()`, `rtwdev->fw.sec` secure-boot/SB selector/MSS fields, and `rtwdev->hal.cv`. Temporary maps are freed on all normal exit paths. Hardware state is changed during efuse power enable/disable, OTP burst configuration, BT disable control, and power-state conversion. For RTL8922A CAV, the APHY isolation/power patch is skipped during BE DDV power toggling.

Dependencies and integration points: Includes `debug.h`, `efuse.h`, `mac.h`, and `reg.h`. It relies on BE register definitions and bit masks, MAC XTAL-SI helpers, chip efuse block tables, chip callbacks, HCI type, chip ID/CV fields, debug masks, and shared secure-MSS parsing from `efuse.c`. The HCI block choice connects efuse parsing to USB versus PCIe/SDIO device initialization.

Risks: BE DDV read paths return on poll or validation errors before calling the disable helper, which can leave efuse power/BT/power-state changes active. The top-level dump also skips the final idle conversion on early DAV/DDV errors. Strict 4-byte alignment is required for BE DDV, so callers must align version and phycap reads correctly. Logical parser overlap handling is subtle around odd offsets and block windows. Secure selector decoding intentionally rejects malformed mirror/complement patterns; new encodings require updates to `SB_SEL_MGN_MAX_SIZE` and `sb_sel_mgn`. The warning in `rtw89_parse_efuse_map_be()` reports a fixed block name for one HCI parse failure even when USB selected a different block.

Test signals: Hardware tests should cover BE DDV aligned reads, rejection of unaligned reads, DAV reads, active/idle efuse state conversion, RTL8922A CAV APHY-patch skip, USB versus PCIe/SDIO HCI block parsing, RF block parsing, phycap parsing, secure selector valid/default/invalid cases, and `EF_CV_INV` handling. Parser tests should include ADIE two-byte headers, normal three-byte headers, page filtering, odd start/end overlaps, disabled word bits, physical truncation, and oversized block indexes. Fault-injection tests should verify power-state cleanup on read-poll failures if the implementation is hardened.
