# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath9k/ar9002_initvals.h

Purpose: Provides the static register initialization data for ath9k AR9002-era hardware. The file is a catalog of `static const u32` INI arrays consumed by `ar9002_hw.c` to program MAC, baseband, analog, PCIe, receive-gain, transmit-gain, CCK FIR, and ANI-related registers for AR9280, AR9285, AR9287, and AR9271 parts.

Important APIs, types, and data: There are no functions or exported symbols. The important ABI is the table shape expected by `INIT_INI_ARRAY()` and `REG_WRITE_ARRAY()`. Mode tables use five columns, with the first column as the register address and four values for `5G_HT20`, `5G_HT40`, `2G_HT40`, and `2G_HT20`. Common tables use two columns, address plus all-modes value. Fast-clock tables use three columns. Major tables include `ar9280Modes_9280_2`, `ar9280Common_9280_2`, `ar9280Modes_fast_clock_9280_2`, AR9280 RX gain variants (`backoff_23db`, `original`, `backoff_13db`), AR9280 TX gain variants (`high_power`, `original`), `ar9280PciePhy_clkreq_always_on_L1_9280`, `ar9285Modes_9285_1_2`, `ar9285Common_9285_1_2`, AR9285 high/original/XE2 TX gain variants, `ar9287Modes_9287_1_1`, `ar9287Common_9287_1_1`, AR9287 normal/Japan 2484 CCK FIR coefficient tables, AR9287 TX and RX gain tables, `ar9271Modes_9271`, `ar9271Common_9271`, `ar9271Modes_9271_ANI_reg`, and AR9271 normal/high-power TX gain tables.

Control flow and programming model: Control flow is indirect. During attach, `ar9002_hw_init_mode_regs()` selects one mode and common table set based on hardware revision, then initializes `ah->iniModes`, `ah->iniCommon`, optional PCIe PHY, fast-clock, CCK FIR, and gain arrays. Later reset/channel code applies those arrays through common INI helpers, choosing the correct per-mode column from channel band and HT width. `ar9002_phy.c` also writes `ah->iniCckfirNormal` or `ah->iniCckfirJapan2484` for AR9287 channel 14 handling. The tables therefore form the data plane behind reset, channel-change, calibration, regulatory band, and power-mode setup.

State and persistence behavior: The arrays are immutable compiled-in driver data. Runtime state is held by `struct ath_hw` `ar5416IniArray` descriptors pointing at these arrays, not by this header itself. Values persist for the lifetime of the loaded module and are copied to hardware registers on attach/reset/channel-change events; no table changes are stored on disk or written back. Because these are raw register scripts, hardware register state can diverge after later calibration, ANI, gain, spur, or power-control code rewrites individual addresses.

Dependencies and integration points: The file depends on `u32` typedef visibility from the including C file and on the ath9k INI machinery in `hw.h`/`ar9002_hw.c`. It is tightly coupled to register definitions in `reg.h`, `ar9002_phy.h`, analog headers, EEPROM policy (`eep_ops` selects power/gain behavior elsewhere), and hardware revision macros such as `AR_SREV_9271`, `AR_SREV_9287_11_OR_LATER`, `AR_SREV_9285`, and `AR_SREV_9280_20_OR_LATER`. Integration is source-level include based; these static arrays are not visible as linker symbols outside the translation unit that includes the header.

Risks and edge cases: The main risk is silent hardware misprogramming. A wrong row address, column order, table width, or revision selection can break radio bring-up, regulatory power, RX sensitivity, spectral behavior, CCK channel 14 operation, PCIe power-save behavior, or calibration. Several tables intentionally include zeroes in unsupported bands or modes, especially AR9287/AR9271 2.4 GHz-oriented sections, so generic validation must understand that zero is sometimes deliberate. The table names encode hardware revision assumptions; reusing a table for a later SREV without comparing vendor init scripts can create hard-to-debug RF regressions. Since rows are raw constants, normal C type checking cannot catch register-field overflow, incompatible analog writes, or wrong channel-mode placement.

Test signals: Useful checks are compile coverage for all AR9002 family revision paths, attach/reset smoke tests that verify `INIT_INI_ARRAY()` selects expected table addresses and row counts, and hardware tests across AR9280, AR9285, AR9287, and AR9271. Runtime signals include successful reset, channel changes in 2 GHz and 5 GHz where supported, HT20/HT40 operation, AR9287 channel 14 CCK behavior, EEPROM-selected high/original TX gain paths, RX gain table selection, PCIe L1/CLKREQ stability, noise-floor calibration, ANI convergence, throughput, spectral scan, tx99, and absence of DMA/interrupt storms after reset. Regression tests should compare programmed registers against known-good dumps for each chip/revision/mode.

# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath9k/ar9002_mac.c

Purpose: Implements AR9002 MAC operations for ath9k. It enables receive DMA, decodes interrupt state, prepares TX/RX descriptors in the AR5416 descriptor format used by AR9002, extracts TX completion status, exposes RX descriptor setup, and attaches those callbacks to the generic ath9k hardware ops table.

Important APIs, types, and functions: `ar9002_hw_rx_enable()` writes `AR_CR_RXE(ah)` to `AR_CR`. `ar9002_hw_set_desc_link()` stores a descriptor link pointer. `ar9002_hw_get_isr()` reads and acknowledges MAC and sync interrupts, returning `ATH9K_INT_*` bits plus optional sync cause. `ar9002_set_txdesc()` fills `struct ar5416_desc` fields from `struct ath_tx_info`, including rate series, power, aggregate state, encryption type, RTS/CTS flags, retry counts, packet durations, and chain selection. `ar9002_hw_proc_txdesc()` converts hardware TX status words into `struct ath_tx_status`. `ar9002_hw_get_duration()` returns one of the four packet-duration fields from descriptor control words. `ath9k_hw_setuprxdesc()` is exported and initializes RX descriptors. `ar9002_hw_attach_mac_ops()` installs the implementation in `struct ath_hw_ops`.

Control flow: The common ath9k stack calls `ar9002_hw_attach_mac_ops()` during hardware attach. Receive setup calls `ath9k_hw_setuprxdesc()` for RX ring buffers, then `ops->rx_enable()` when the engine can run. The interrupt path calls `ops->get_isr()`, which first handles non-AR9100 async/sync interrupt gating, reads `AR_ISR`, decodes beacon miscellaneous status from `AR_ISR_S2`, optionally uses read-and-clear registers when `ATH9K_HW_CAP_RAC_SUPPORTED`, maps RX/TX/common/gentimer/TIM timer/fatal events, records TX queue bitmaps in `ah->intr_txqs`, records generic timer trigger/threshold masks, clears legacy ISR registers, handles PCI fatal/parity/RADM/local timeout sync causes, and returns whether an interrupt was present. The transmit path builds a descriptor with `ar9002_set_txdesc()`, hardware updates status fields asynchronously, and completion polling calls `ar9002_hw_proc_txdesc()` until `AR_TxDone` appears.

State and persistence behavior: Persistent state is hardware and descriptor-ring state, not file-local data. The code mutates descriptor memory shared with DMA and uses `WRITE_ONCE()`/`READ_ONCE()` around fields that hardware or other CPUs observe. It updates `ah->intr_txqs`, `ah->intr_gen_timer_trigger`, `ah->intr_gen_timer_thresh`, and the TX trigger level through `ath9k_hw_updatetxtriglevel()` on underruns. RX setup clears the RX status union with `memset()` and stores only buffer length/interrupt request control bits. Interrupt handling acknowledges hardware registers, so reads are destructive on non-RAC paths.

Dependencies and integration points: The file includes `hw.h` and Linux export support. It depends on descriptor layout macros (`AR5416DESC`, `struct ar5416_desc`, `struct ath_desc`), register access helpers (`REG_READ`, `REG_WRITE`), bitfield macros (`SM`, `MS`), SREV/capability macros, interrupt enums, TX/RX descriptor flag definitions, and common debug logging. It integrates with `recv.c` through `ath9k_hw_setuprxdesc()`, with `xmit.c`/`beacon.c` through `ath9k_hw_set_txdesc()` and TX status processing, with `hw-ops.h` dispatch wrappers, with reset/error recovery through fatal interrupt bits, and with queue scheduling through `ah->intr_txqs`.

Risks and edge cases: ISR handling is sensitive to read/clear ordering and hardware revision. Reading the wrong ISR register for RAC-capable hardware or failing to clear legacy status can cause lost interrupts or interrupt storms. `0xffffffff` status is treated as invalid hardware/unmapped MMIO. Sync fatal handling resets the host interface for RADM completion timeout. Descriptor programming must distinguish first/middle/last aggregate buffers; putting rate, duration, or aggregate length fields into the wrong segment can break A-MPDU transmission. Buffer length is masked with `AR_BufLen`, so callers must ensure DMA buffers are valid and size-limited. TX underrun handling raises trigger level and can affect throughput. AR9285 has extra descriptor control words cleared up front, so chip-specific descriptor layout assumptions matter.

Test signals: Compile and runtime coverage should include RAC and non-RAC interrupt paths, AR9100 special handling, RX/TX interrupts, beacon TIM/DTIM/CABEND/GTT/CST/TSFOOR events, generic timers, sync fatal/parity/RADM/local timeout causes, and invalid MMIO reads. TX tests should cover non-aggregate, first/middle/last aggregate descriptors, encryption key index/type, no-ack, RTS/CTS, VEOL, VMF, duration update, multi-rate retry series, per-rate TX power, underrun status, block-ack bitmap extraction, retry counts, RSSI/EVM status, and `-EINPROGRESS` before `AR_TxDone`. RX tests should confirm descriptor length masking, interrupt-request flag setup, and status clearing before reuse.

# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath9k/ar9002_phy.c

Purpose: Implements AR9002 PHY/radio operations for ath9k single-chip hardware. It programs channel synthesizer state, mitigates EEPROM-reported spurs, initializes open-loop power control, computes PLL values, reads noise floor, configures antenna diversity and Bluetooth coexistence antenna behavior, controls spectral scan, supports tx99 test transmission setup, and attaches these callbacks to ath9k ops.

Important APIs, types, and functions: `ar9002_hw_set_channel()` computes and writes `AR_PHY_SYNTH_CONTROL` for 2 GHz fractional mode and 5 GHz fractional/integer-N modes, including AR9287 CCK FIR channel 14 handling. `ar9002_hw_spur_mitigate()` scans EEPROM spur entries, converts them to baseband offsets, enables spur RSSI/filter/channel/pilot masks, programs delta phase and spur frequency fields, then calls `ar5008_hw_cmn_spur_mitigate()`. `ar9002_olc_init()` initializes open-loop TX power control state for AR9280/AR9287 variants. `ar9002_hw_compute_pll_control()` returns RTC PLL control bits for 5 GHz, fast clock, half-rate, and quarter-rate cases. `ar9002_hw_do_getnf()` reads chain noise-floor fields. `ar9002_hw_set_nf_limits()` fills nominal/min/max NF limits by SREV. `ar9002_hw_antdiv_comb_conf_get()` and `_set()` read/write AR9285 antenna-combine fields. Optional `ar9002_hw_set_bt_ant_diversity()` programs Bluetooth coexistence antenna diversity. `ar9002_hw_spectral_scan_config()`, `_trigger()`, and `_wait()` manage AR92xx spectral scan registers. `ar9002_hw_tx99_start()` and `_stop()` configure continuous TX test behavior. `ar9002_hw_attach_phy_ops()` wires all callbacks.

Control flow: During attach, `ar9002_hw_attach_phy_ops()` sets private ops for RF frequency, spur mitigation, OLC init, PLL computation, and noise-floor reads, sets public ops for antenna combine, spectral scan, tx99, and optional BT antenna diversity, then initializes NF limits. Reset/channel-change code later calls `rf_set_freq()`: channel centers are computed, synthesizer control high bits are preserved, 2 GHz uses `CHANSEL_2G()` and channel 14 CCK FIR programming, and 5 GHz selects fractional or integer mode based on EEPROM `EEP_FRAC_N_5G`, spacing, and half/quarter-rate status. Spur mitigation runs after channel selection, looking for an EEPROM spur within HT20/HT40 bounds and programming masks only when one is relevant. Spectral scan config is driven by common debugfs/common-spectral code, toggling enable, FFT, count, period, and short-repeat fields, then trigger sets ACTIVE and wait polls for completion.

State and persistence behavior: The file mutates hardware registers and selected fields in `struct ath_hw`. `ar9002_hw_set_channel()` updates `ah->curchan`. OLC init may fill `ah->originalGain[]` and reset `ah->PDADCdelta`, or program AR9287 temperature-sense TX power mode. NF limits are stored in `ah->nf_2g` and `ah->nf_5g`. Noise-floor reads fill caller-provided arrays and depend on `ah->rxchainmask` and `ah->curchan`. Antenna diversity state is represented in PHY registers and caller-owned `struct ath_hw_antcomb_conf`; BT coexistence also mutates `ah->btcoex_hw.bt_coex_mode2`. Spectral and tx99 state is register-resident and volatile across reset.

Dependencies and integration points: The file includes `hw.h` and `ar9002_phy.h`, and relies on register definitions, SREV macros, channel helpers (`IS_CHAN_*`, `ath9k_hw_get_channel_centers()`), analog register helpers, EEPROM ops, `ar5008_hw_cmn_spur_mitigate()`, common wait/logging helpers, and hardware op tables. It integrates with `hw.c` channel/reset flow through `ath9k_hw_rf_set_freq()` and `ath9k_hw_spur_mitigate_freq()`, with common spectral support through `ath9k_cmn_spectral_scan_config()`, with EEPROM-selected calibration/power setup through OLC and gain tables, with Bluetooth coexistence when enabled, and with manufacturing/test flows through tx99.

Risks and edge cases: Channel programming is high risk because synthesizer math changes by band, channel spacing, half/quarter-rate, and EEPROM fractional-N policy. Channel 2484 requires special CCK spreading/FIR treatment; missing it can break Japan channel 14. Spur mitigation depends on EEPROM spur units, HT20/HT40 frequency bounds, signed arithmetic, and denominator differences between 2 GHz and 5 GHz. Spectral count handling has AR9280-specific endless mode semantics and clamps the high bit when endless is not requested. `ar9002_hw_do_getnf()` only fills extension-channel readings in HT40 and only second-chain readings when `rxchainmask` includes chain 1, so callers must initialize arrays if they need deterministic unused entries. BT antenna diversity paths rewrite several switch and gain fields and can disrupt coexistence if called on unsupported boards. tx99 writes several magic register constants and intentionally disables normal RX behavior.

Test signals: Hardware tests should cover 2 GHz, 5 GHz, HT20, HT40, half-rate, quarter-rate, channel 2484, fractional-N EEPROM modes, fast-clock and non-fast-clock PLL paths, and spur present/absent scenarios. Calibration tests should check OLC state for AR9280 and AR9287, NF limits for AR9280/9285/9287/9271, multi-chain NF extraction, and no uninitialized NF array use. Antenna tests should verify get/set round-trips for main/alt LNA and fast-div bias, plus BT coexistence enable/disable when configured. Spectral tests should cover disabled/manual/endless/count clamping, AR9280 versus Kiwi count fields, trigger/wait timeout logging, and common-spectral integration. tx99 tests should verify queue-specific register programming and restoration/reset behavior after stop.

# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath9k/ar9002_phy.h

Purpose: Defines AR9002 PHY/baseband register addresses, bit masks, shifts, and calibration constants used by `ar9002_phy.c` and related ath9k hardware code. It is the register contract for channel programming, CCA/noise-floor handling, spectral scan, radar/PHY error features, antenna diversity, spur mitigation, calibration, TX power control, gain tables, Bluetooth coexistence switch control, and PHY mode selection.

Important APIs, types, and constants: The file contains no functions or types beyond preprocessor constants. Register groups include base PHY control (`AR_PHY_TEST`, `AR_PHY_TURBO`, `AR_PHY_ACTIVE`), RF/ADC timing (`AR_PHY_RF_CTL*`, `AR_PHY_ADC_CTL`, `AR_PHY_SETTLING`, `AR_PHY_RXGAIN`, `AR_PHY_DESIRED_SZ`), signal detection and CCA (`AR_PHY_FIND_SIG*`, `AR_PHY_AGC_CTL1`, `AR_PHY_CCA`, extension and per-chain CCA registers), PLL/synth (`AR_PHY_SYNTH_CONTROL`, `AR_PHY_PLL_CTL*`), spectral scan (`AR_PHY_SPECTRAL_SCAN` fields and Kiwi variants), radar registers (`AR_PHY_RADAR_0/1` fields), spur-mitigation masks (`AR_PHY_TIMING_CTRL4_*`, `AR_PHY_TIMING11_*`, `AR_PHY_SPUR_REG_*`, pilot/channel masks), antenna diversity (`AR_PHY_MULTICHAIN_GAIN_CTL`, `AR_PHY_9285_ANT_DIV_*`, BT coexistence constants), calibration measurements (`AR_PHY_CALMODE*`, `AR_PHY_CAL_MEAS_*`), PHY mode (`AR_PHY_MODE_*`), CCK controls, TX power-control registers, and per-chip CCA nominal/min/max values for 5416/9280/9285/9271/9287.

Control flow and use model: Control flow is macro-driven in callers. `ar9002_phy.c` uses these constants to mask fields with `REG_RMW_FIELD()`, construct values with `SM()`, extract values with `MS()`, and set/clear bits. Channel-change code uses synth, CCK, and PHY mode fields. Spur mitigation uses timing, spur, pilot, and channel-mask constants. Noise-floor code reads CCA masks and sign-extends field values. Antenna and BT coexistence code reads/writes multi-chain gain and switch registers. Spectral scan config uses the AR9280 and Kiwi count/short-repeat bit definitions. TX power, calibration, and gain constants are shared with reset/calibration and initval logic elsewhere in ath9k.

State and persistence behavior: The header owns no runtime state. Its constants describe volatile MMIO/PHY register state that is programmed during attach, reset, channel changes, calibration, spectral operations, antenna changes, and test modes. The CCA limit constants become runtime policy when `ar9002_hw_set_nf_limits()` copies them into `struct ath_hw`. Because macros are compiled into multiple call sites, any change affects all future register accesses after rebuild but does not migrate or persist runtime hardware state.

Dependencies and integration points: The file is included by `ar9002_phy.c` and depends only on ordinary C preprocessing, but semantically depends on ath9k register access helpers and bitfield conventions. It integrates with AR9002 init tables in `ar9002_initvals.h`, hardware attach in `ar9002_hw.c`, shared channel/reset/calibration in `hw.c`, spectral debug/common code, tx99 support, EEPROM/calibration paths, and optional Bluetooth coexistence. Several addresses are chain-indexed with macros such as `AR_PHY_TIMING_CTRL4(_i)` and `AR_PHY_CAL_MEAS_*(_i)`, so callers must supply valid chain indices matching hardware chain masks.

Risks and edge cases: Register definitions are a hardware ABI. Wrong masks or shifts can corrupt unrelated fields, especially for CCA/noise-floor extraction, spectral count programming, spur delta/frequency programming, antenna diversity, and TX power-control fields. Several fields differ between AR9280-style and later Kiwi-style hardware, such as spectral scan count and short-repeat bits; callers must choose the right macro for the SREV. Some constants overlap addresses for different meanings (`AR_PHY_SLEEP_CTR_LIMIT` and `AR_PHY_SYNTH_CONTROL`, `AR_PHY_M_SLEEP` and `AR_PHY_CALMODE`), so context matters. Signed CCA values require correct field width before sign extension. Magic constants for Bluetooth antenna diversity and switch-com programming are board-sensitive.

Test signals: Compile tests should cover all users of the macros under normal, spectral, BT coexistence, and tx99 configurations. Runtime signals include correct channel synthesis, stable reset/calibration, expected NF readings and CCA bounds per chip family, working spectral scan on AR9280 and Kiwi-family parts, correct spur suppression when EEPROM spurs exist, antenna diversity get/set behavior, BT coexistence switching, and TX power/gain calibration. Register-dump comparison against known-good AR9002 programming is the most direct validation for mask/shift regressions.
