## sources/distributed-fs/ceph-client/drivers/mtd/nand/raw/cadence-nand-controller.c

Purpose: this is the platform driver and raw NAND controller implementation for the Cadence high-performance NAND flash controller (`cdns,hp-nfc`). It exposes the controller through the raw NAND framework, handles multi-chip Device Tree child nodes, configures BCH ECC, drives Cadence generic commands and command-DMA descriptors, and moves page or command data through master DMA, slave DMA, or programmed I/O style access to the controller data aperture.

Important APIs, types, and functions: `struct cdns_nand_ctrl` is the controller state, carrying MMIO register bases, the data aperture, IRQ completion state, BCH capability tables, a CDMA descriptor, an internal bounce buffer, optional DMAengine channel, clock rate, board delay, selected chip, chip-select allocation bitmap, and the chip list. `struct cdns_nand_chip` wraps `struct nand_chip` with per-chip timing registers, chip-select IDs, BBM placement, sector geometry, available OOB size, and ECC strength index. `struct cadence_nand_cdma_desc` is the hardware descriptor used for erase, page read, and page write. Key routines include `cadence_nand_hw_init()`, `cadence_nand_read_bch_caps()`, `cadence_nand_setup_sdr_interface()`, `cadence_nand_setup_nvddr_interface()`, `cadence_nand_select_target()`, `cadence_nand_cdma_transfer()`, page/OOB raw and ECC read/write callbacks, `cadence_nand_exec_op()`, `cadence_nand_chip_init()`, `cadence_nand_init()`, and the DT probe/remove wrappers.

Control flow: probe obtains match data, IRQ, controller registers, the slave-DMA/data aperture resource, `nf_clk` rate, and optional `cdns,board-delay-ps` before entering `cadence_nand_init()`. Initialization allocates a coherent CDMA descriptor and a temporary 16 KiB buffer, requests the shared IRQ, waits for controller initialization complete, reads revision/features/BCH capabilities, optionally requests a DMAengine memcpy channel, maps the controller data aperture for DMA, initializes the raw NAND controller, and scans each DT child as a NAND chip. Each chip child validates its `reg` chip-select list against hardware bank count and duplicate assignment, sets default on-host ECC, calls `nand_scan()`, and registers the MTD device. Attach-time ECC selection chooses a BCH step/strength from hardware capability registers, computes sector count, available OOB bytes, bad-block marker handling, ECC strength index, and installs the Cadence page/OOB callbacks.

State and persistence: persistent software state is per-controller selected chip, current transfer type, current ECC strength index, allocated chip-select bitmap, BCH capability arrays, bounce buffer size, DMA mapping for the data aperture, and per-chip timing and OOB/ECC layout data. Runtime hardware state includes access width, ECC enable and strength, erased-page detection threshold, transfer configuration registers, skip-byte/BBM configuration, PHY timing registers, command/descriptor registers, and interrupt masks/status. There is no custom suspend/resume path in this file, so hardware state recovery depends on platform device lifetime or a future PM wrapper.

Dependencies and integration points: the driver depends on raw NAND core operation parsing, MTD registration, Device Tree child chip nodes with `reg`, DMA mapping APIs, optional DMAengine `DMA_MEMCPY`, common clock rate reporting, interrupt completions, bitfield helpers, and Cadence-specific DT properties. `cadence_nand_controller_ops` integrates through `.attach_chip`, `.exec_op`, and `.setup_interface`; page callbacks replace generic ECC read/write paths. The generic command parser covers command, address, data-in, data-out, wait-ready, and erase suboperations, while bulk page operations use command-DMA descriptors.

Risks: `cadence_nand_init()` assumes a DMA channel exists when it later dereferences `cdns_ctrl->dmac->device`; the current default match data sets `has_dma = 1`, but a non-DMA variant would need careful audit. The driver gets the clock rate but does not enable the clock, so it assumes the platform has already prepared the controller clock or uses always-on firmware setup. IRQ waiting uses a 10 second completion timeout and shared controller state, so missed or stale interrupts can cause long stalls or ambiguous errors. ECC and OOB layout depend on hardware-reported BCH metadata and manual BBM skip-byte handling; layout mistakes can overwrite bad-block markers or expose less free OOB than expected. Timing calculations use board-delay and interface-skew estimates; wrong DT delay values can produce marginal sampling. Raw page layout packing/unpacking is intricate and spans main/OOB boundaries, making regressions likely around large pages and non-default ECC geometry. The 16-bit bus force-byte path changes global access width for generic commands and must be restored reliably after `force_8bit` operations.

Test signals: successful probe should log the controller revision, enumerate every child chip, register source-tree-named MTD devices, and avoid duplicate/invalid CS errors. Functional coverage should include READID/status generic operations, BBM reads, erase through CDMA, ECC page read/write with and without OOB, raw page/OOB read/write layout round trips, 8-bit and 16-bit chips, DMA-aligned direct transfers, bounce-buffer fallback, DMAengine failure fallback, corrected and uncorrectable ECC status accounting, erased-page handling, SDR and NVDDR timing setup across supported modes, and timeout/error logs for SDMA/CDMA interrupt paths.

## sources/distributed-fs/ceph-client/drivers/mtd/nand/raw/cafe_nand.c

Purpose: this PCI driver supports the Marvell 88ALP01 OLPC "CAFE" NAND controller. It is an older raw NAND integration using legacy NAND callbacks, optional DMA into a small coherent page buffer, Reed-Solomon hardware syndrome registers, custom bad-block table descriptors, and PCI suspend resume register restoration.

Important APIs, types, and functions: `struct cafe_priv` owns the `nand_chip`, PCI device, MMIO base, Reed-Solomon control object, cached `ctl1`/`ctl2` command state, transfer counters, page address, DMA flag, DMA address, and coherent DMA buffer. The legacy NAND hooks are `cafe_nand_cmdfunc()`, `cafe_device_ready()`, `cafe_read_byte()`, `cafe_read_buf()`, `cafe_write_buf()`, and `cafe_select_chip()`. ECC-specific functions include `cafe_nand_read_page()`, `cafe_nand_write_page_lowlevel()`, `cafe_ooblayout_*()`, the CAFE BBT descriptors, and the Galois-field helpers used by `init_rs_non_canonical()`. PCI lifecycle is handled by `cafe_nand_probe()`, `cafe_nand_remove()`, and `cafe_nand_resume()`.

Control flow: probe verifies the flash-memory PCI class, enables the PCI function, maps BAR0, creates the RS decoder, installs legacy NAND callbacks, chooses flash BBT behavior unless `skipbbt` is set, derives or accepts three timing registers, resets the NAND block, requests a shared IRQ, enables the NAND clock/global IRQ routing, disables DMA for identification, and scans up to two chip selects. Attach allocates a 2112-byte coherent DMA buffer, programs its address, restores the module `usedma` setting, configures page-size/ECC bits in `ctl2`, selects a 512-byte or 2 KiB BBT layout, and installs host ECC callbacks. Page reads issue `nand_read_page_op()`, read OOB through the legacy buffer hook, inspect hardware ECC result/syndrome registers, run the RS decoder, and patch data/OOB bytes according to the controller's 12-bit symbol mapping. Page writes stage data and OOB, set the ECC autogeneration bit in `ctl2`, then complete the program operation.

State and persistence: persistent state includes module parameters (`usedma`, `skipbbt`, debug flags, `checkecc`, optional timing words), cached timing registers, coherent DMA buffer address, selected chip bit in `ctl1`, and ECC/BBT layout chosen after chip scan. Hardware state is reset and timing/DMA/global-control registers are restored during resume. There is no runtime PM; remove unregisters MTD, runs `nand_cleanup()`, releases IRQ, RS tables, MMIO, DMA memory, and the PCI device.

Dependencies and integration points: the file depends on PCI IDs for `PCI_DEVICE_ID_MARVELL_88ALP01_NAND`, raw NAND legacy hooks, MTD partition parsers (`cmdlinepart`, `RedBoot`), Linux Reed-Solomon library support, coherent DMA, IRQ handling, and CAFE-specific global/NAND register definitions. It exposes `mtd->name = "cafe_nand"` and uses flash-resident BBT descriptors tailored to its OOB layout.

Risks: this driver predates the modern `exec_op` NAND interface and relies on a large `cmdfunc()` that emulates multi-step NAND commands through controller-specific control bits. Command completion is polled up to 500 ms and IRQ handling mostly acknowledges bits, so interrupt problems may only appear as long busy waits. The 2112-byte DMA buffer matches 2 KiB page plus 64-byte OOB assumptions; unexpected page sizes are rejected, but future geometry changes would need new sizing. ECC correction manually maps RS symbols across data and OOB and can corrupt data if syndrome interpretation is wrong. `cafe_nand_remove()` frees the coherent DMA buffer after `nand_cleanup()`, while the detach hook also frees it, which is a double-free risk if both paths run with current NAND cleanup semantics. Timing defaults may become `0xffffffff` if firmware left registers unset, which is safe but very slow and hardware-dependent.

Test signals: validate PCI class filtering and BAR mapping, timing parameter handling, two chip-select scan, DMA enabled and disabled modes, read ID/status without DMA during identification, page read/write with ECC autogeneration, corrected and failed ECC accounting with `checkecc=1`, OOB-only operations, flash BBT placement for 512-byte and 2 KiB pages, suspend/resume restoring timing and DMA registers, and module removal without DMA buffer lifetime warnings.

## sources/distributed-fs/ceph-client/drivers/mtd/nand/raw/cs553x_nand.c

Purpose: this module supports NAND controllers embedded in AMD CS5535/CS5536 companion chips for Geode platforms. It discovers enabled flash chip-select windows from Geode MSRs, maps MMIO NAND windows, exposes each active chip-select as a raw NAND controller, and uses the small hardware Hamming ECC engine.

Important APIs, types, and functions: `struct cs553x_nand_controller` contains a `nand_controller`, one `nand_chip`, and the mapped MMIO window. `cs553x_exec_op()` implements the raw NAND operation interface by dispatching instructions to `cs553x_exec_instr()`. Data helpers use `memcpy_fromio()` and `memcpy_toio()` against the 0x800-byte data aperture. `cs_enable_hwecc()` and `cs_calculate_ecc()` wire the hardware ECC registers into the NAND ECC core, with correction delegated to `rawnand_sw_hamming_correct`. Module lifecycle is through `cs553x_init()`, `cs553x_init_one()`, and `cs553x_cleanup()`.

Control flow: module init first verifies the boot CPU is a Geode GX/LX, checks the DIVIL capability MSR for CS5535/CS5536, ensures flash pins are not routed to IDE, then walks four `MSR_DIVIL_LBAR_FLSH*` BAR descriptors. Each enabled NAND MMIO BAR is initialized by `cs553x_init_one()`, which allocates the controller, initializes NAND controller ops, maps the physical address, sets flash BBT use, assigns an MTD name of `cs553x_nand_csN`, and calls `nand_scan()`. After all scans, init registers each discovered MTD device. Operation execution writes CLE/ALE bytes through control and IO registers, copies data through the data aperture, and polls status for controller idle or flash ready.

State and persistence: controller state is held in a static four-entry `controllers[]` array for module cleanup. Hardware configuration comes from MSRs programmed by firmware or platform setup; the driver does not persist or alter timing MSRs. Per-chip state is limited to the mapped MMIO window, MTD name, BBT option, and ECC callbacks. Cleanup unregisters MTDs, calls `nand_cleanup()`, frees names, unmaps MMIO, and releases controller allocations.

Dependencies and integration points: the module is x86/Geode-specific and depends on `<asm/msr.h>`, CPU vendor/model data, CS553x DIVIL MSR layout, raw NAND `exec_op`, MTD registration, and generic Hamming correction. PIO mode is explicitly not implemented; only memory-mapped NAND BARs are accepted.

Risks: `cs553x_exec_op()` returns `true` for `check_only`, which is numerically success but unusual compared with common zero-return convention and may deserve caution if the core interprets positive values differently. Cleanup dereferences `controllers[i]` before checking whether it is NULL, so unloading after only some chip-selects initialized can crash. MTD registration errors are ignored in `cs553x_init()`, which can leave scanned chips in a partially registered state. The driver trusts firmware MSR BAR setup and timing; no resource reservation is used beyond `ioremap()`. Data copies larger than 0x800 bytes loop through the same aperture, which assumes the controller auto-advances internal address correctly.

Test signals: test on real Geode hardware should show correct CPU/MSR gating, no probe when flash pins are IDE-routed, discovery of each enabled NAND MMIO BAR, successful `nand_scan()` and MTD registration under `cs553x_nand_cs[0-3]`, command/address/data operations through `exec_op`, ready polling timeout behavior, hardware ECC generation and Hamming correction, and safe module unload with sparse chip-select population.

## sources/distributed-fs/ceph-client/drivers/mtd/nand/raw/davinci_nand.c

Purpose: this platform driver supports NAND attached to TI DaVinci/Keystone asynchronous EMIF hardware. It handles memory-mapped NAND command/address/data cycles, AEMIF timing programming from NAND SDR timings, 1-bit and 4-bit on-host hardware ECC engines, Device Tree/platform-data configuration, BBT/OOB layout selection, and MTD registration.

Important APIs, types, and functions: `struct davinci_nand_pdata` represents board configuration such as ALE/CLE masks, chip-select index, secondary chip-select mask, ECC mode/bits/placement, bus width, BBT options, and optional partitions. `struct davinci_nand_info` stores the NAND controller/chip, platform device, EMIF control register base, NAND data base, active chip-select address, ALE/CLE/chip-select masks, clock, and parent AEMIF handle. ECC functions include `nand_davinci_hwctl_1bit()`, `nand_davinci_calculate_1bit()`, `nand_davinci_correct_1bit()`, `nand_davinci_hwctl_4bit()`, `nand_davinci_calculate_4bit()`, and `nand_davinci_correct_4bit()`. Core NAND ops are `davinci_nand_exec_op()`, `davinci_nand_setup_interface()`, and `davinci_nand_attach_chip()`.

Control flow: probe obtains platform data or builds it from device properties, validates the core chip select, maps the NAND data resource and AEMIF control resource, enables the `aemif` clock, records parent AEMIF driver data, applies chip options/BBT descriptors, selects default ALE/CLE masks, sets the CSxNAND bit under a global spinlock, initializes the NAND controller, scans one or two chip-selects depending on `mask_chipsel`, registers partitions or a plain MTD, and logs the controller revision. `exec_op` computes `current_cs` from the operation CS and `mask_chipsel`, then emits command bytes at `mask_cle`, address bytes at `mask_ale`, bulk data through 8/16/32-bit repeated IO helpers, and wait-ready by polling `NANDFSR`. `setup_interface` converts SDR timing requirements into AEMIF read/write setup, strobe, hold, and turnaround counts and programs the parent AEMIF chip-select timings.

State and persistence: persistent global state includes `davinci_nand_lock` and `ecc4_busy`, because the 4-bit ECC engine is shared across the whole AEMIF. Per-device state includes the selected AEMIF chip-select, current read/write ECC mode, and the mapped data/control registers. Hardware state includes NANDFCR chip-select NAND mode, 1-bit or 4-bit ECC enable/start bits, ECC syndrome/load/error registers, and AEMIF timing registers. Remove unregisters the MTD and cleans the NAND chip; it attempts to release the 4-bit ECC busy flag based on ECC placement.

Dependencies and integration points: the driver integrates with raw NAND `exec_op`, MTD partitions, `ti-aemif` timing APIs, common clock APIs, platform data, generic device properties, and OF compatibles `ti,davinci-nand` and `ti,keystone-nand`. Keystone-compatible nodes set `NAND_NO_SUBPAGE_WRITE` to preserve compatibility with existing UBI layouts.

Risks: the 4-bit ECC busy flag is set when `pdata->ecc_bits == 4`, but remove clears it only when `chip->ecc.placement == NAND_ECC_PLACEMENT_INTERLEAVED`; because the 4-bit path does not necessarily set that placement, the shared ECC engine may remain marked busy after unbind. The 4-bit correction path relies on tight hardware state sequencing, jiffies-based wait loops, and type-punning of ECC bytes to `unsigned short`, which is sensitive to alignment and endian assumptions. 4-bit ECC is intentionally unavailable for 16-bit NAND and unusual page chunk counts; unsupported geometries fail attach. Device Tree parsing silently leaves many fields at zero/default if properties are absent except the required chip-select. Timing conversion uses integer nanosecond cycles and parent clock rate; bad clock data or missing parent AEMIF state breaks setup. `mask_chipsel` based multi-chip packages rely on address-line decoding rather than independent ready pins.

Test signals: cover DT and platform-data probe, required `ti,davinci-chipselect` validation, CSxNAND mode register programming, single and dual chip-select scans, 8/16/32-bit data transfer paths including `force_8bit`, wait-ready timeout behavior, 1-bit ECC correction and ECC-bit errors, 4-bit BCH syndrome correction and uncorrectable errors, OOB layout for small/large boot-medium pages, Keystone no-subpage behavior, AEMIF timing programming across SDR modes, and repeated bind/unbind to catch `ecc4_busy` lifetime issues.

## sources/distributed-fs/ceph-client/drivers/mtd/nand/raw/denali.c

Purpose: this is the shared core for Denali/Spectra raw NAND controllers used by both platform/DT and PCI wrappers. It abstracts direct versus indexed host addressing, interrupt completion, page DMA or PIO transfers, interleaved hardware ECC layout, software or hardware ECC fixup, timing programming, multi-device-per-CS adjustment, raw data/OOB transfer layout, and raw NAND operation execution.

Important APIs, types, and functions: `denali_init()`, `denali_chip_init()`, `denali_remove()`, and `denali_calc_ecc_bytes()` are exported to wrappers. `struct denali_controller` and `struct denali_chip` are defined in `denali.h` and populated by wrappers before calling this core. Internal highlights include `denali_select_target()`, `denali_setup_interface()`, `denali_page_xfer()`, `denali_dma_xfer()`, `denali_pio_xfer()`, `denali_read_page()`, `denali_write_page()`, `denali_read_raw()`, `denali_write_raw()`, `denali_hw_ecc_fixup()`, `denali_sw_ecc_fixup()`, `denali_multidev_fixup()`, `denali_exec_op()`, and IRQ helpers `denali_isr()`, `denali_wait_for_irq()`, and `denali_reset_irq()`.

Control flow: wrapper drivers map registers and host data/command space, set clock rates, capabilities, ECC capability tables, IRQ, and optional revision/OOB skip values, then call `denali_init()`. Core init reads features, derives bank count with revision-specific encoding, configures DMA availability and DMA address width, selects direct or indexed host access, sets OOB skip bytes, enables spare transfer policy/ECC/write-protect/RB pins, clears IRQs, requests the shared IRQ, and enables global interrupts. Each wrapper then allocates one or more `denali_chip` objects and calls `denali_chip_init()`, which validates bank assignments, sets NAND DMA alignment if available, configures BBT/no-subpage/on-host interleaved ECC callbacks and OOB layout, scans the chip, registers the MTD, and links it into the controller chip list.

State and persistence: controller state includes active bank, bank count, revision, capability flags, DMA availability, device count per CS, OOB skip byte count, IRQ mask/status protected by a spinlock, completion, chip list, host access callbacks, and DMA setup callback. Per-CS timing values are cached in `struct denali_chip_sel` and applied by `denali_select_target()`. Hardware state includes per-target geometry registers, ECC correction settings, DMA enable, spare/OOB marker behavior, RB pin enables, write protect, timing registers, and interrupt enables. Remove unregisters all MTDs, calls `nand_cleanup()`, unlinks chips, and disables Denali interrupts.

Dependencies and integration points: the core depends on raw NAND `exec_op` and ECC selection, MTD OOB layout APIs, DMA mapping, interrupt completions, bitfield helpers, and wrapper-provided resources/capabilities. The core supports both direct host addressing and indexed addressing depending on `FEATURES__INDEX_ADDR`, and can use either 32-bit or 64-bit Denali DMA command programming depending on `DENALI_CAP_DMA_64BIT`.

Risks: interrupt state is keyed to one `active_bank`; concurrent operations across chips would be unsafe without NAND core serialization. Old and new IP revisions reuse interrupt bits differently, so the `DENALI_CAP_HW_ECC_FIXUP` flag must match hardware. `denali_sw_ecc_fixup()` modifies the data buffer based on ECC error address registers and assumes the controller reports errors in a compatible sequence ending with `LAST_ERR`. The multi-device fixup mutates NAND memory organization, MTD sizes, shifts, ECC geometry, and OOB skip after scan data is known, so any mismatch in `DEVICES_CONNECTED` can double sizes incorrectly. Raw payload/OOB layout code splits chunks around the BBM skip region and is sensitive to ECC step/byte geometry. DMA falls back to PIO only when mapping fails, not for all runtime DMA completion errors. The 1 second IRQ timeout can convert lost hardware interrupts into `-EIO` without much recovery context.

Test signals: exercise both direct and indexed addressing, DMA and PIO paths, 32-bit and 64-bit DMA setup, page read/write with corrected ECC, uncorrectable ECC with erased-page check, raw page/OOB transfer round trips, OOB layout exposure after different skip-byte values, timing setup with valid and invalid `clk_x/clk` ratios, multi-bank and duplicate bank validation, two x8 devices connected in parallel, R/B wait handling in `exec_op`, and wrapper remove paths disabling interrupts after MTD cleanup.

## sources/distributed-fs/ceph-client/drivers/mtd/nand/raw/denali.h

Purpose: this header is the Denali NAND controller hardware contract shared by the core, Device Tree wrapper, and PCI wrapper. It defines register offsets and bitfields, per-CS and per-controller state structures, capability flags that cannot always be discovered at runtime, and the exported core API used by wrapper drivers.

Important APIs, types, and functions: the register map covers reset, spare/OOB behavior, wait counters, timing registers, geometry registers, ONFI parameter mirrors, feature bits, per-bank interrupt/status registers, ECC error reporting, DMA registers, and active channel state. `struct denali_chip_sel` caches per-bank timing register values. `struct denali_chip` wraps a `nand_chip`, list node, number of selected banks, and flexible array of selections. `struct denali_controller` carries all wrapper-provided and core-maintained state: raw NAND controller, device, chip list, clock rates, register/host MMIO bases, completion and IRQ state, DMA/OOB/multidevice flags, active bank, revision, caps, ECC caps, host read/write callbacks, and DMA setup callback. Exported prototypes are `denali_calc_ecc_bytes()`, `denali_chip_init()`, `denali_init()`, and `denali_remove()`.

Control flow: wrappers include this header, allocate/populate a `struct denali_controller`, set resource pointers and capability metadata, call `denali_init()` once, then create `struct denali_chip` instances with one or more `struct denali_chip_sel` bank entries and register them through `denali_chip_init()`. The core writes and reads the register offsets defined here for all subsequent timing, ECC, DMA, interrupt, and geometry operations.

State and persistence: this header does not execute logic, but it defines the persistent state shape used across Denali files. The most important persistent fields are `chips`, `clk_rate`, `clk_x_rate`, `reg`, `host`, IRQ status/mask, `dma_avail`, `devs_per_cs`, `oob_skip_bytes`, `active_bank`, `nbanks`, `revision`, `caps`, and `ecc_caps`. Hardware persistence is represented by the register definitions for geometry, timing, ECC, spare marker, DMA, and interrupts.

Dependencies and integration points: it depends on Linux bit macros, completions, lists, raw NAND types, spinlock type declarations, and fixed-width integer types. The capability flags `DENALI_CAP_HW_ECC_FIXUP` and `DENALI_CAP_DMA_64BIT` bridge wrapper-specific knowledge into generic core decisions.

Risks: the header encodes revision-sensitive register semantics, especially interrupt bit reuse and timing field widths, so incorrect capability/revision data in wrappers can lead the core to interpret status incorrectly. Flexible-array allocation for `denali_chip` must use `struct_size()` or equivalent with a correct `nsels`; underallocation would corrupt state. `struct denali_controller` expects wrappers to populate mandatory fields before `denali_init()`, but the type itself cannot enforce that `dev`, `irq`, `reg`, `host`, and `ecc_caps` are valid.

Test signals: build coverage should include both Denali wrappers to validate shared declarations. Runtime validation comes indirectly from correct feature decoding, interrupt handling, ECC fixup mode selection, DMA width selection, timing register programming, and multi-chip registration through the core API.

## sources/distributed-fs/ceph-client/drivers/mtd/nand/raw/denali_dt.c

Purpose: this is the Device Tree platform wrapper for the shared Denali NAND core. It binds SoC-specific compatible strings to Denali revision/capability/ECC/OOB-skip data, maps named resources, enables clocks, controls resets, initializes the core, and registers NAND chips described as child nodes.

Important APIs, types, and functions: `struct denali_dt` embeds `struct denali_controller` and owns the `nand`, `nand_x`, and `ecc` clocks plus optional `nand` and `reg` reset controls. `struct denali_dt_data` supplies wrapper-specific revision, capability flags, OOB skip bytes, and ECC capability tables. Match data covers `altr,socfpga-denali-nand`, `socionext,uniphier-denali-nand-v5a`, and `socionext,uniphier-denali-nand-v5b`. Key functions are `denali_dt_probe()`, `denali_dt_chip_init()`, and `denali_dt_remove()`.

Control flow: probe allocates wrapper state, copies match data into the embedded controller, obtains the IRQ, maps `denali_reg` and `nand_data`, enables the three clocks, gets optional shared resets, records core and bus-interface clock rates, deasserts register reset before core reset, waits for the bootstrap sequence, and calls `denali_init()`. It then walks each child node, counts `reg` bank entries, allocates a `denali_chip` with that many selections, fills each bank ID, sets the NAND flash node, and calls `denali_chip_init()`. On failure after core init, it removes Denali state and reasserts resets. Remove calls `denali_remove()` and reasserts both resets.

State and persistence: persistent wrapper state is devm-managed and stored as platform driver data. Clocks remain enabled for the bound device lifetime. Reset controls are deasserted after successful probe and asserted on remove or failure. SoC match data persists in the controller as revision, caps, OOB skip, and ECC capability pointer.

Dependencies and integration points: the wrapper depends on OF match data, named platform MMIO resources, common clock framework, reset control framework, child NAND DT nodes with `reg`, and the Denali core API. ECC capabilities differ by SoC: SocFPGA uses 512-byte steps with 8 or 15 bit strength; UniPhier variants use 1024-byte steps with SoC-specific strengths and 64-bit DMA capability.

Risks: all three clocks are mandatory; boards omitting `ecc` or `nand_x` clock names fail probe. Reset ordering is critical and encoded in probe; changing it can produce unpredictable controller behavior. `denali_dt_chip_init()` sets the flash node inside the loop, which is harmless but redundant and means no chip is initialized if `reg` count is missing. The wrapper trusts match data for revision and OOB skip bytes; incorrect compatible strings can select the wrong interrupt/ECC/DMA behavior. There is no custom suspend/resume, so clock/reset state across system sleep depends on generic platform behavior or always-on assumptions.

Test signals: validate each compatible's ECC capability selection, named resource mapping, clock enable and rate reporting, reset deassert/assert order, bootstrap delay sufficiency, child-node bank parsing, duplicate/invalid bank rejection by the core, MTD registration for multiple child chips, 64-bit DMA on UniPhier, hardware ECC fixup on all supported compatibles, and clean failure unwinding with resets reasserted.

## sources/distributed-fs/ceph-client/drivers/mtd/nand/raw/denali_pci.c

Purpose: this PCI wrapper binds Intel CE4100 and Moorestown Denali/Spectra NAND PCI functions to the shared Denali core. It enables PCI resources, maps controller and host windows, supplies fixed clock rates and PCI ECC capabilities, initializes the core, and registers one NAND chip spanning all detected Denali banks.

Important APIs, types, and functions: `denali_pci_ids` matches Intel device IDs `0x0701` and `0x0809` with wrapper-specific BAR layout handling. `NAND_ECC_CAPS_SINGLE(denali_pci_ecc_caps, denali_calc_ecc_bytes, 512, 8, 15)` supplies supported ECC choices. The lifecycle functions are `denali_pci_probe()` and `denali_pci_remove()`.

Control flow: probe allocates a `denali_controller`, enables the PCI device with managed PCI helpers, selects CSR and host memory windows according to CE4100 versus other layout, enables bus mastering, sets IRQ, ECC caps, and fixed `clk_rate = 50 MHz` / `clk_x_rate = 200 MHz`, requests all PCI regions, maps CSR and host regions, and calls `denali_init()`. It then allocates a `denali_chip` with `nsels = denali->nbanks`, requests maximum ECC strength in the chip user configuration, assigns every bank number in order, and calls `denali_chip_init()`. Remove fetches the controller from PCI drvdata and calls `denali_remove()`.

State and persistence: all wrapper allocations and mappings are devm/pcim-managed. Runtime state lives in the embedded Denali controller and the single allocated `denali_chip`. The wrapper hard-codes clock rates rather than discovering them from PCI config or firmware. PCI bus mastering remains enabled while bound.

Dependencies and integration points: the wrapper depends on PCI core managed enable/resource APIs, Intel PCI IDs, MMIO mapping, the Denali core API, and raw NAND ECC configuration. Unlike the DT wrapper, it does not use reset or clock frameworks and does not parse child topology; every hardware bank becomes a select of one NAND chip object.

Risks: CE4100 BAR handling sets `mem_len` from resource 1 while `mem_base` comes from resource 0, which is unusual and should be validated against hardware documentation. Fixed clock rates must match actual controller integration or SDR timing setup will be wrong. The wrapper registers all banks as one chip with multiple selects; platforms with different physical topology would need a different mapping. No suspend/resume support is provided. DMA capability is whatever the core detects from `FEATURES` plus wrapper caps; PCI-specific DMA constraints are limited to generic mask setup in the core.

Test signals: validate probe on both PCI IDs, BAR layout mapping for CE4100 and Moorestown, IRQ delivery through the shared Denali ISR, bank count detection, one MTD spanning all selects, maximum ECC strength choice, page read/write with DMA and PIO fallback, timing setup using the fixed 50/200 MHz rates, and remove cleanup through `denali_remove()`.
