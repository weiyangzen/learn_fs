# Research: subset-b-004822

Grouped research for Intel `iwlwifi` firmware API headers under `sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/`. These files define packed host-to-firmware command/notification ABIs rather than normal executable implementation, so the "control flow" is the sequencing and version selection used by the driver when it sends commands and parses firmware notifications.

## sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/location.h

`location.h` defines the firmware ABI for Wi-Fi location features, especially 802.11mc/11az FTM/ToF ranging, FTM responder mode, LCI/Civic location data, MCSI debug capture, responder statistics, and CSI chunk notifications. It depends on Linux 802.11 and Ethernet constants (`IEEE80211_CCMP_PN_LEN`, `ETH_ALEN`), common integer/bit helpers, and `rs.h` for antenna mask definitions used in responder flags.

The central API surface starts with `enum iwl_location_subcmd_ids`, mapping the location command group to firmware commands and notifications: range request/config/abort/extended request, responder static and dynamic configuration, LCI/Civic notification, responder stats, MCSI debug, CSI header/chunk notifications, and range response notification. The command structures are heavily versioned. Responder configuration progresses from `iwl_tof_responder_config_cmd_v6` through the current `iwl_tof_responder_config_cmd`, adding `format_bw`, NDP/LTF parameters, BSS color, band, and min/max non-triggered measurement timing. Dynamic responder configuration similarly evolves from variable LCI/Civic data in `iwl_tof_responder_dyn_config_cmd_v2` to fixed LCI/Civic buffers plus secure PASN/HGTK/cipher station data in `iwl_tof_responder_dyn_config_cmd`.

Initiator ranging is modeled as a top-level `iwl_tof_range_req_cmd*` containing up to `IWL_TOF_MAX_APS` per-AP entries. Per-AP entries evolve from basic channel/BSSID/FTM parameters in `iwl_tof_range_req_ap_entry_v2` to the current `iwl_tof_range_req_ap_entry`, which carries band, packed format/bandwidth, BSSID, burst settings, station/cipher IDs, HLTK/TK keys, calibration per bandwidth, beacon interval, PMF packet numbers, NDP negotiation parameters, and minimum measurement interval. Flags in `enum iwl_initiator_ap_flags` select ASAP, LCI/Civic, dynamic ACK, LR/FFT algorithms, MCSI reporting, trigger/non-trigger ranging, secure LTF, LMR feedback, calibration override, PMF, and negative test behavior.

There are no in-file functions; runtime flow is driver-selected ABI construction: configure global ToF state, optionally configure responder/static/dynamic state, send a range request with a unique `request_id`, optionally abort with `iwl_tof_range_abort_cmd`, then parse `TOF_RANGE_RESPONSE_NOTIF` using the notification version advertised by firmware. Response structures carry session status, per-AP measurement status, RTT/range/variance/spread, RSSI, refusal periods, timing clocks, calibration values, rate fields, confidence, and PMF PNs. State is not persisted by this header, but it defines state identifiers that higher layers must persist while a measurement is active: request IDs, per-AP station IDs, BSSID keys, PMF PN state, responder valid-field masks, and LCI/Civic/PASN credentials.

Integration points are `iwl_mvm` location/ranging code, mac80211 FTM APIs, firmware command-version dispatch, and debug/trace code that decodes MCSI/CSI/stat notifications. Risks are ABI mismatch between firmware command versions, packed bitfield mistakes in `format_bw` and NDP/LTF fields, off-by-one or length validation errors around variable CSI/data buffers, leaking or mishandling 11az keys/PNs, and confusing similarly named v8/v9 comments. Test signals include compile-time struct layout checks where available, firmware API version negotiation tests, FTM initiator/responder interoperability, abort/timeout paths, multi-AP result parsing, PMF/secure ranging replay counter tests, and malformed notification length handling.

## sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/mac-cfg.h

`mac-cfg.h` defines the newer MLD-oriented MAC configuration command group used by `iwlwifi` firmware. It includes `mac.h` and reuses shared MAC types, QoS structures, HE/EHT packet-extension structures, and access-category constants. The file covers MAC context configuration, link context configuration, station table configuration, low-latency mode, channel switch lifecycle, EMLSR/ESR notifications, TWT operations, NAN configuration, and related notifications.

`enum iwl_mac_conf_subcmd_ids` is the dispatch table for this command group. Host-to-firmware commands include `LOW_LATENCY_CMD`, `CHANNEL_SWITCH_TIME_EVENT_CMD`, `CANCEL_CHANNEL_SWITCH_CMD`, `MAC_CONFIG_CMD`, `LINK_CONFIG_CMD`, `STA_CONFIG_CMD`, `AUX_STA_CMD`, `STA_REMOVE_CMD`, `STA_DISABLE_TX_CMD`, `ROC_CMD`, `TWT_OPERATION_CMD`, and `NAN_CFG_CMD`. Firmware notifications include missed VAP/beacon, channel switch start/error, ROC/session protection, EMLSR transition failure, probe-response data, NAN cluster join, and NAN discovery-window end.

The MAC configuration ABI is split between `iwl_mac_config_cmd_v3` and current `iwl_mac_config_cmd`. Both carry context ID/color, action, MAC type, local MLD address, filter flags, generation support (`iwl_mac_wifi_gen_support_v2` or current `iwl_mac_wifi_gen_support`), and type-specific data. Current versions add NAN data (`iwl_mac_nan_data`) for NDI addresses. Link configuration is driven by `iwl_link_config_cmd`, whose `modify_mask` gates which fields are meaningful during modify operations. It binds link ID, MAC ID, PHY ID, local link address, active/listen/block state, optional bandwidth modification, basic rates, protection/QoS settings, HE/EHT/UHR parameters, beacon timing, BSS color, multi-BSSID identifiers, IBSS BSSID, NPCA parameters, priority EDCA, and reserved version space.

Station configuration is similarly versioned: `iwl_sta_cfg_cmd_v1` uses a single `link_id`; v2 adds LDPC/ICF and DPS/MIC timing fields; current `iwl_sta_cfg_cmd` uses a `link_mask` and adds DPS enable plus NAN peer mapping fields. `enum iwl_fw_sta_type` distinguishes peer, broadcast-management, multicast, NAN NMI/NDI, and driver-only AUX stations. Removal and TX-disable commands are small station-ID payloads. TWT uses `iwl_twt_operation_cmd` to encode negotiation type, wake time, interval, trigger/protection/flow fields, restricted TWT bitmaps, and AP/STA request direction. NAN uses `iwl_nan_config_cmd` with variable beacon data containing NAN attributes and vendor elements.

Control flow is a firmware-context lifecycle: add/modify/remove a MAC context, add links under it, bind/update station entries, configure timing/power-adjacent features such as TWT/NAN, and consume asynchronous notifications for beacon loss, channel switch, EMLSR, and probe response metadata. The header stores no state itself; persistence belongs to driver objects that must track context IDs/colors, link IDs, station IDs, active link masks, NAN beacon-data lengths, and EMLSR recommendations. Risks include using MAC IDs where a newer ABI expects link IDs, failing to honor `modify_mask`, sending active-link immutable fields such as PHY/local address changes, variable-length NAN beacon data bounds errors, and ABI drift across versions. Test signals include MLD association with multiple links, channel switch cancel/error handling, station add/remove/disable sequencing, NAN cluster join and DW end events, TWT negotiation behavior, and notification parsing with exact payload-size checks.

## sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/mac.h

`mac.h` is the common, older MAC-context firmware ABI used directly by legacy commands and indirectly by newer MLD APIs such as `mac-cfg.h` and `rs.h`. It defines MAC indices, station-count constants, access-category indexes, MAC types, TSF timer IDs, MAC-role-specific data unions, filtering/protection/QoS flags, HE/EHT station context payloads, missed beacon notifications, and HE monitor configuration.

Core types include `enum iwl_ac`, `enum iwl_mac_types`, and `enum iwl_tsf_id`. Role-specific state is described through `iwl_mac_data_ap`, `iwl_mac_data_ibss`, `iwl_mac_data_sta`, `iwl_mac_data_go`, `iwl_mac_data_p2p_sta`, `iwl_mac_data_p2p_dev`, and `iwl_mac_data_pibss`. These carry beacon/DTIM timing, TSF values, association state, listen interval, data-policy bits, CT window, opportunistic power save, and beacon template IDs. `iwl_mac_ctx_cmd` combines the common MAC fields with a union of these role-specific structures for `MAC_CONTEXT_CMD`.

Filtering and QoS are represented by `enum iwl_mac_filter_flags`, `enum iwl_mac_qos_flags`, and `struct iwl_ac_qos`. These encode which frame classes are passed to the host, whether decryption/FCS/probe/beacon handling is altered, whether EDCA should be updated, and per-access-category contention windows, AIFSN, FIFO mask, and TXOP. `iwl_nonqos_seq_query_cmd` exposes get/set of non-QoS sequence state by MAC ID/color. Missed beacon notifications exist in v3 MAC-ID form and v4 link-ID form.

The HE/EHT portion defines MU EDCA backoff (`iwl_he_backoff_conf`), packet extension thresholds (`iwl_he_pkt_ext_v1` and v2), station context flags (`iwl_he_sta_ctxt_flags`), HTC flags, and versioned HE station context commands. These contexts pack data from multiple 802.11 information elements: multiple-BSSID, HE capabilities, PPE thresholds, HE operation, random access parameters, MU EDCA, EHT puncturing, and multi-BSSID profile metadata. `iwl_he_monitor_cmd` configures an HE air sniffer using BSSID and AID.

There is no executable control flow in this header. Runtime flow is context assembly: driver code computes role-specific timing/filter/QoS/HE state from mac80211 configuration, fills packed little-endian ABI structs, sends add/modify/remove actions, then interprets missed-beacon and related notifications. State and persistence are external but keyed by MAC ID/color, TSF ID, station IDs, beacon timing, HE capability flags, and AC parameters. Dependencies include Linux bit helpers, endian conversion in consumers, and shared `iwlwifi` context-action enums outside this file.

Risks are layout and version mismatches, union misuse for the wrong MAC type, confusion between legacy MAC and newer link-oriented identifiers, unvalidated EDCA/PPE/capability values from IEs, and subtle power/roaming behavior changes from filter or data-policy flags. Test signals include legacy STA/AP/P2P/IBSS context setup, HE/EHT association with PPE and BSS color, missed beacon notification decoding, non-QoS sequence query behavior, monitor/sniffer setup, and cross-checks that `mac-cfg.h` users still match shared structure sizes.

## sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/nvm-reg.h

`nvm-reg.h` defines firmware ABIs for non-volatile memory access and regulatory configuration. It covers NVM section read/write, NVM capability query, MCC/LAR regulatory updates, TAS configuration, BIOS-origin configuration headers, LARI regulatory override bitmaps, PNVM completion notification, MCC-to-AP-type tables, and SAR offset mapping used by other power/PHY code.

`enum iwl_regulatory_and_nvm_subcmd_ids` maps the group to `NVM_ACCESS_COMPLETE`, `LARI_CONFIG_CHANGE`, `NVM_GET_INFO`, `TAS_CONFIG`, `SAR_OFFSET_MAPPING_TABLE_CMD`, `MCC_ALLOWED_AP_TYPE_CMD`, and `PNVM_INIT_COMPLETE_NTFY`. NVM access is represented by `iwl_nvm_access_cmd` and `iwl_nvm_access_resp`, with opcode, target (cache/OTP/EEPROM), section type, offset/length, status, and flexible data payload. `iwl_nvm_get_info_rsp_v3` and current `iwl_nvm_get_info_rsp` return general flags/version/board/MAC count, MAC SKU flags, PHY chain masks, and regulatory channel profiles.

Regulatory country handling uses `iwl_mcc_update_cmd`, response versions v3/v4/v8, and `iwl_mcc_chub_notif`. The command carries a two-letter MCC, source ID, test key, and reserved padding. Responses return status, applied MCC, capabilities, elapsed test time, geo information, source, and a variable channel-control array. `enum iwl_mcc_update_status` and `enum iwl_mcc_source` are critical for policy decisions and prioritization.

Transmit antenna selection and regulatory overrides are represented by `iwl_tas_config_cmd_common`, v3/v4/v5 TAS payloads, and `enum iwl_tas_uhb_allowed_flags`. BIOS data is normalized through `iwl_bios_config_hdr` and `bios_value_u32`, which are reused by power APIs. LARI evolves from a single `config_bitmap` in v1 through v6/v8 to current `iwl_lari_config_change_cmd`, which adds UHB, 11ax, UNII-4, channel active-state, force-disable, energy detection, 320 MHz, 11be, 11bn, UNII-9, and BIOS header fields. UATS/MCC allowed AP type commands map country rows/columns to 6 GHz and UNII-9 AP-type permissions.

Control flow is initialization and regulatory refresh: read or query NVM, signal access completion, load PNVM, apply BIOS/OEM regulatory tables, process MCC changes from host/firmware/communication hub, then update channel capability maps used by mac80211. Persistence is in firmware NVM/OTP/EEPROM and host-side cached regulatory/NVM state, not in this header. Risks include flexible-array bounds, accepting mismatched response versions, treating requested MCC as applied MCC, incorrect source-priority handling, regulatory compliance mistakes in LARI/TAS bitmaps, and stale PNVM/TAS/BIOS metadata. Test signals include NVM read/write mock responses, MCC update status matrix, invalid/low-priority/test-mode handling, country table size validation, PNVM completion parsing, LARI bitmap version coverage, and regulatory channel list comparison against expected mac80211 regdomain output.

## sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/offload.h

`offload.h` defines a small protocol-offload firmware notification ABI. The command group IDs in `enum iwl_prot_offload_subcmd_ids` cover WoWLAN wake packet notification, WoWLAN information notification, D3 end notification, and stored beacon notification. This file only defines the stored beacon payloads; the WoWLAN info/wake structures are declared elsewhere.

The stored beacon ABI is split into a common header and two versions. `iwl_stored_beacon_notif_common` records firmware/system receive timing (`system_time`, `tsf`, `beacon_timestamp`), band, channel, internal firmware rate, and `byte_count`. `iwl_stored_beacon_notif_v2` appends a fixed `MAX_STORED_BEACON_SIZE` data buffer. Current `iwl_stored_beacon_notif` adds a `sta_id` and padding before the same fixed-size beacon buffer. All structures are packed and represent notification wire format.

Control flow is firmware-to-host notification after low-power/offload operation: firmware stores a beacon, wakes or informs the host through the protocol offload group, and the driver parses either v2 or current notification based on the firmware notification version. State is transient; the actual persistent low-power/offload state is in the firmware and power-management code, while this header only encodes one notification record. Integration points are WoWLAN/D3 resume paths, beacon filtering/offload diagnostics, station association state via `sta_id`, and receive-rate decoding through other API headers.

Risks are trusting `byte_count` without capping to `MAX_STORED_BEACON_SIZE`, parsing the wrong version and misreading `sta_id` as frame data, and mishandling TSF/system timestamps during resume diagnostics. Test signals include version-specific notification parsing, `byte_count` boundary tests at 0/600/overlength, resume from D3 with stored beacon data, and ensuring the beacon payload is handed to management-frame parsers only within the validated byte count.

## sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/paging.h

`paging.h` defines the firmware paging layout command. It is intentionally small: `NUM_OF_FW_PAGING_BLOCKS` is 33, representing 32 data blocks plus one CSS block, and `struct iwl_fw_paging_cmd` carries flags, block size, block count, and an array of firmware/device-side physical addresses.

This ABI is used when the driver loads firmware that supports pageable code/data. The host allocates or maps paging blocks, fills `device_phy_addr[]` with the addresses the device should use, sets `block_size` as a power-of-two encoding, sets `block_num`, and sends the packed command to firmware. The header has no executable code and no notification path.

State and persistence live outside this file: DMA mappings, firmware image sections, and paging block lifetime are managed by firmware-loading code. The command itself is a one-time or reload-time transfer of a memory layout. Dependencies are minimal but consumers must use little-endian fields and must keep the address array aligned with firmware expectations.

Risks are DMA address truncation if a platform address does not fit the 32-bit ABI field, off-by-one errors around the CSS block, declaring more blocks than populated, mismatched block-size encoding, and lifetime bugs if paging memory is freed while firmware still references it. Test signals include firmware load on devices requiring paging, boundary checks for `NUM_OF_FW_PAGING_BLOCKS`, DMA mapping failure paths, suspend/resume or restart reload paths, and firmware error logs indicating invalid paging addresses.

## sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/phy-ctxt.h

`phy-ctxt.h` defines PHY context configuration ABI: band constants, channel width constants up to 320 MHz, control-channel position encoding, channel-info structures, RX chain bitfield masks, and versioned PHY context commands. It is consumed by MAC/link code that binds virtual interfaces and links to physical channel contexts.

`iwl_fw_channel_info_v1` encodes band, channel, width, and control position as bytes. Current `iwl_fw_channel_info` uses a 32-bit channel field plus band/width/control position/reserved bytes. The control-position comment documents legacy/VHT/EHT layout, where bit 2 marks above/below, bits 1:0 encode distance from center, and bit 3 extends distance for 320 MHz EHT. The RX chain masks define positions for driver force, valid chains, forced selection, forced MIMO selection, chain count, MIMO count, and MIMO force within a chain-info word.

`NUM_PHY_CTX` is currently fixed at 3 with a TODO that it should depend on firmware at runtime. `iwl_phy_context_cmd_tail` is a legacy tail containing TX chain, RX chain, acquisition data, and DSP flags. `iwl_phy_context_cmd_v1` contains ID/color, action, apply time, TX parameter color, channel info, and the tail. Current `iwl_phy_context_cmd` contains ID/color, action, channel info, LMAC ID, a union between older `rxchain_info` and newer SBB bandwidth/control/puncture fields, DSP flags, secondary control channel location, and padding; comments map it to command versions 3 through 7.

Runtime flow is context add/modify/remove: compute channel information from mac80211 chandef, encode width/control position and puncturing, choose LMAC, fill action and ID/color, then send to firmware before activating links that reference the PHY context. State is external: channel context objects, PHY IDs/colors, LMAC ownership, puncture mask, and RX-chain policy. Integration points include channel switching, MLD link activation, EHT 320 MHz operation, and regulatory/channel validation from NVM/regulatory code.

Risks are wrong control-channel encoding for 80/160/320 MHz, stale fixed `NUM_PHY_CTX`, version confusion in the union field, changing channel or local PHY state while active links still reference it, and undocumented chain/acquisition fields causing conservative consumers to underconfigure hardware. Test signals include channel context setup for 2.4/5/6 GHz, 20/40/80/160/320 MHz widths, punctured EHT channels, multi-LMAC operation, channel switch reconfiguration, and firmware assertions around invalid PHY context actions.

## sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/phy.h

`phy.h` defines the PHY operation command group for thermal sensing, CT kill, CTDP power budget management, temperature reporting thresholds, and also enumerates command IDs for per-chain limit offset, PPAG, and AP TX power constraints whose payloads are defined in `power.h`. It includes Linux integer and bit helpers.

`enum iwl_phy_ops_subcmd_ids` maps PHY operations to firmware subcommands and notifications: DTS measurement trigger, CTDP config, temperature threshold reporting, per-chain limit offset, per-platform antenna gain, AP TX power constraints, CT kill notification, and wide DTS measurement notification. DTS measurement has both a compact `iwl_dts_measurement_cmd`, selecting temperature and/or voltage through `enum iwl_dts_measurement_flags`, and an extended `iwl_ext_dts_measurement_cmd`, selecting automatic/request/overwrite/direct modes, sensor, average factor, bit mode, and step duration. Notifications are versioned: `iwl_dts_measurement_notif_v1` reports temp/voltage, current `iwl_dts_measurement_notif` adds threshold index, and `iwl_dts_measurement_resp` returns command response temperature.

Thermal protection and budget management are represented by `ct_kill_notif`, `enum iwl_ctdp_cmd_operation`, `iwl_ctdp_cmd`, and `temp_report_ths_cmd`. `ct_kill_notif` reports temperature plus, in newer firmware, the triggering DTS bitmap and SW/HW scheme. CTDP commands start, stop, or report a current milliwatt budget. Temperature threshold configuration accepts up to `IWL_MAX_DTS_TRIPS` thresholds.

Control flow is firmware thermal management: host requests readings or threshold reporting, firmware sends DTS/CT-kill notifications, host may adjust power budgets or enter recovery paths, and related TX power/SAR/PPAG commands from `power.h` are sent under the same PHY command group. State is maintained by thermal and power-management layers: configured threshold list, current CTDP budget, latest sensor readings, and CT-kill mode. This header is just the wire format.

Risks include using the wrong DTS command structure for a firmware version, treating the threshold index as valid for v1 notifications, unit confusion between Celsius, milliwatts, and voltage units, exceeding `IWL_MAX_DTS_TRIPS`, and delayed CT-kill response. Test signals include thermal read command/response, threshold crossing notifications, CT kill simulation or firmware debug triggers, CTDP start/stop/report paths, and command-version negotiation around extended DTS support.

## sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/power.h

`power.h` defines a broad set of firmware power, latency, TX-power, SAR, antenna-gain, beacon-filter, and 6 GHz AP power-constraint ABIs. It includes `nvm-reg.h` for BIOS configuration headers and values reused by TAS/PPAG/geo power payloads. The file is a dependency of PHY operations and regulatory power handling, not a standalone implementation.

Power-management structures include LTR flags and `iwl_ltr_config_cmd_v1/current`, legacy `iwl_powertable_cmd`, device-wide `iwl_device_power_cmd`, per-MAC `iwl_mac_power_cmd`, and `iwl_uapsd_misbehaving_ap_notif`. These cover latency tolerance, memory retention/no-sleep flags, keepalive, RX/TX idle timeouts, DTIM skipping, LPRX threshold, uAPSD snoozing, QNDP TID, per-AC UAPSD flags, heavy traffic thresholds, SMPS, BT SCO coexistence, and misbehaving AP detection.

TX power reduction is versioned through `iwl_dev_tx_power_common`, v3/v4/v5/v8 structures, `iwl_dev_tx_power_cmd_v3_v8`, v9/v10/v11 structures, and current `iwl_dev_tx_power_cmd`. Modes select link/device/chains/ACK/SAR timer/default-table behavior. Versions differ in chain-table count, sub-band count, ACK reduction support, SAR timer fields, flags, and VLP backoff. Geo power and antenna gain are represented by `iwl_geo_tx_power_profiles_cmd_v1` through v6 plus `iwl_geo_tx_power_profiles_resp`, `union iwl_geo_tx_power_profiles_cmd`, `enum iwl_ppag_flags`, and `union iwl_ppag_table_cmd`. These encode per-chain/per-band offsets, profile counts, table revision, BIOS source metadata, and PPAG gains for ETSI/China/US/Canada/UHB cases.

Beacon filtering is configured with `iwl_beacon_filter_cmd` and default/D0I3 macros. The macro `IWL_BF_CMD_CONFIG(mode)` produces endian-converted defaults for RSSI energy delta, roaming threshold, temperature filters, debug flag, escape timers, and beacon abort timers. `iwl_sar_offset_mapping_cmd` maps MCCs to SAR groups. `iwl_txpower_constraints_cmd` encodes 6 GHz LPI/SP/VLP AP type plus EIRP and PSD constraints per 20 MHz channel, with `DEFAULT_TPE_TX_POWER` representing no limit.

Control flow spans initialization and association: configure LTR/device PM, configure per-MAC PM after association, react to uAPSD misbehavior, load SAR/geo/PPAG/TAS regulatory limits from BIOS/NVM, send TX power restrictions or timers as regulatory/thermal state changes, configure beacon filtering for normal/D0I3, and apply 6 GHz constraints from AP TPE/AFC information. Persistent state is in driver power state, association parameters, BIOS/NVM regulatory tables, timers, and firmware; this header encodes the payloads.

Risks are unit mistakes (seconds, TU, usec, milliseconds, 1/8 dBm, 0.5 dB), version mismatches in TX power tables, overbroad power-save causing missed beacons or latency regressions, regulatory noncompliance from wrong SAR/PPAG/TPE values, incorrect endian handling in default macros, and stale SAR timers. Test signals include suspend/resume and D0I3 behavior, uAPSD AP misbehavior notifications, SAR/PPAG table version tests, 6 GHz AP constraint parsing, beacon filter pass/escape behavior, regulatory country transitions, and thermal-driven power changes.

## sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/rfi.h

`rfi.h` defines the radio-frequency interference mitigation table ABI. It is small but operationally important for avoiding platform self-interference, likely tied to DVFS or other platform frequency changes. It defines table sizes, a LUT entry type, a full configuration command, a firmware-installed table response, and a deactivation notification.

`iwl_rfi_lut_entry` maps one frequency to up to `IWL_RFI_LUT_ENTRY_CHANNELS_NUM` affected Wi-Fi channels and corresponding bands. `iwl_rfi_config_cmd` sends a full table of `IWL_RFI_LUT_SIZE` entries plus an `oem` flag that distinguishes default versus OEM-provided data. `enum iwl_rfi_freq_table_status` reports whether the table can be used, DVFS is not ready and the host should retry later, or the firmware disabled the feature. `iwl_rfi_freq_table_resp_cmd` returns the currently installed compact table of `IWL_RFI_LUT_INSTALLED_SIZE` entries and status. `iwl_rfi_deactivate_notif` carries a reason used for logging when firmware disables RFI mitigation.

Control flow is table provisioning and feedback: driver or platform code sends an OEM/default RFI mapping, may query or receive the installed table, handles a DVFS-not-ready status by retrying later, and logs/adjusts state if firmware deactivates the feature. State is external: platform/OEM frequency data, retry scheduling, active RFI status, and firmware's installed subset. Dependencies are only standard packed integer types and little-endian frequency/status fields.

Risks are accepting malformed table dimensions, mismatching channel and band arrays, failing to retry on `RFI_FREQ_TABLE_DVFS_NOT_READY`, silently ignoring `RFI_FREQ_TABLE_DISABLED`, and treating the installed compact table as if it had the full configured size. Test signals include default and OEM table programming, DVFS-not-ready retry behavior, firmware-disabled notification handling, table boundary validation, and channel/band mapping checks for known interference frequencies.

## sources/distributed-fs/ceph-client/drivers/net/wireless/intel/iwlwifi/fw/api/rs.h

`rs.h` defines rate-scaling and transmit-link-control firmware ABI. It includes Linux bitfield/endian helpers, integer/bit helpers, and `mac.h` for access-category constants. The file covers TLC configuration commands, TLC notifications, debug commands, legacy PLCP/rate indexes, rate_n_flags bit layouts for multiple firmware generations, link-quality retry tables, and helper declarations/converters.

TLC configuration begins with capability enums for flags (`STBC`, `LDPC`, HE DCM, EHT extra LTF, UHR ELR), channel width up to 320 MHz, chains, modulation modes (CCK/non-HT/HT/VHT/HE/EHT/UHR), HT MCS indexes, NSS, and MCS-per-bandwidth tables. Versioned `iwl_tlc_config_cmd_v3`, v4, v5, and current `iwl_tlc_config_cmd` differ in station addressing (`sta_id` versus `sta_mask` and `phy_id`), HT-rate field width, 320 MHz support, AMSDU field placement, and max-TXOP size. `iwl_tlc_update_notif` reports updated initial rate and AMSDU settings, keyed by station ID and flags. `iwl_dhc_tlc_cmd` provides debug commands such as fixed rate, aggregation duration/count limits, TPC enable/stats, RTS disable, and partial fixed rate.

Rate representation is the largest section. It defines legacy indexes and PLCP values, then two rate_n_flags layouts. Version 1 uses individual bits for HT, CCK, VHT, HE, bandwidth, SGI, antenna, STBC, DCM, beamforming, HE GI/LTF, HE type, duplicate channel, LDPC, 106-tone RU, and RTS/CTS requirements. Version 2/3 uses a modulation-type field for CCK/OFDM/HT/VHT/HE/EHT/UHR and moves NSS and width encodings, supporting 320 MHz and UHR. `iwl_v3_rate_from_v2_v3()` and `iwl_v3_rate_to_v2_v3()` convert between v2 and v3 NSS bit placement when firmware is not using v3 format. Declared helpers format/interpret rates and antennas.

`iwl_lq_cmd` is the link-quality retry table ABI. It carries station ID, reduced TPC, flags such as RTS/dynamic bandwidth/color, MIMO delimiter, single/dual stream antenna masks, per-AC initial rate indexes, aggregation thresholds, a 16-entry retry table of `rate_n_flags`, and single-stream parameters for STBC/BFER forcing. State is maintained in rate-control/TLC modules: station capabilities, firmware rate format version, current initial rate, AMSDU per-TID enablement, retry table color, aggregation limits, and debug overrides.

Risks include mixing v1/v2/v3 rate layouts, incorrect NSS conversion, using legacy PLCP indexes as HT/VHT indexes without context, wrong endian handling in converter inputs, unsupported 320 MHz/UHR bits on older firmware, and a likely suspicious macro `LQ_SS_STBC_ALLOWED_MSK` shifting by itself rather than the position name. Test signals include unit tests for rate bitfield encode/decode across v1/v2/v3, TLC config generation for legacy/HT/VHT/HE/EHT/UHR peers, notification parsing, fixed-rate debug command behavior, aggregation limit updates, and firmware interoperability with 320 MHz/UHR capability combinations.
