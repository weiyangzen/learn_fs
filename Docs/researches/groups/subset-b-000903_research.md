# sources/distributed-fs/ceph-client/arch/x86/kvm/vmx/vmx.h

Purpose: defines the central Intel VMX private state and inline helper contract used by KVM's VMX backend. It describes per-vCPU VMX state, nested-VMX state, VMCS control shadowing, VMX control bit policy, MSR bitmap helpers, and conversion helpers between generic KVM/VT objects and VMX-specific containers.

Important APIs, types, and functions: `struct vcpu_vmx` embeds the generic `struct kvm_vcpu`, shared VT state, VMCS pointers, MSR autoload/autostore arrays, segment/rmode caches, nested VMX state, PML page state, feature-control MSR shadows, Intel PT/LBR descriptors, and virtualization exception info. `struct nested_vmx` tracks L1 VMX operation, VMCS12/shadow/eVMCS caches, vmcs02, pinned host mappings for L2 APIC/PI pages, nested posted-interrupt state, preemption timer state, nested MSR snapshots, VPID assignment, and SMM-entry nested state. `struct kvm_vmx` extends the VM object with VMX-specific TSS, identity-map, and posted-interrupt descriptor table state. Inline helpers include `to_vmx()`, `to_kvm_vmx()`, `to_vt()`, `vt_to_vcpu()`, exit-info readers, DEBUGCTL read/write masking, MSR bitmap test/set/clear helpers, control-shadow setters/getters, VMCS allocation wrappers, guest-state validity helpers, instruction-info decoders, and feature probes such as `vmx_has_waitpkg()`, `vmx_need_pf_intercept()`, `is_unrestricted_guest()`, and `vmx_can_use_ipiv()`.

Control flow and behavior: this header is not an entry-point implementation, but it shapes most VMX runtime paths. VM-exit handlers obtain cached exit reason, qualification, and interrupt info through lazy `vmcs_read*()` access that marks KVM register caches available. VM-entry/exit control changes flow through `BUILD_CONTROLS_SHADOW()`: callers update the shadow first-class state, and hardware VMCS writes happen only when the value changes. MSR interception code uses generated bitmap helpers that map low and high MSR ranges to Intel's read/write bitmap layout; out-of-range MSRs are treated as intercepted. Guest state validation uses unrestricted guest when available and otherwise delegates to strict VMX state checks. Debug-control writes preserve host-owned `DEBUGCTLMSR_FREEZE_IN_SMM` while exposing only guest-owned bits.

State and persistence: all state is in-memory kernel state tied to a VM, vCPU, per-vCPU VMCS, or pinned guest page mapping. `loaded_vmcs` switches between `vmcs01` for L1 and `vmcs02` for L2. `nested.cached_vmcs12`, `cached_shadow_vmcs12`, dirty/sync booleans, and GPA-to-HVA caches persist guest VMCS state across nested VMX instructions until flushed back to guest memory. `controls_shadow` mirrors VMCS control fields to avoid unnecessary VMREAD/VMWRITE operations and is authoritative for helper reads. PML, VPID, PI descriptor, preemption timer, and MSR autoload/autostore arrays persist for the life of the vCPU or VM and are reinitialized through VMX lifecycle code, not filesystem storage.

Dependencies and integration points: included by VMX implementation files such as `vmx.c`, `nested.c`, `main.c`, PMU, SGX, TDX, and interrupt/APIC code. It depends on KVM host APIs, VMCS definitions, low-level VMX operations from `vmx_ops.h`, x86 CPUID/MMU helpers, Intel PT/perf/LBR structures, posted interrupts, optional Hyper-V enlightened VMCS state, optional KVM Hyper-V, optional TDX declarations through related ops headers, and generic KVM register-cache conventions.

Risks and correctness concerns: layout changes to `struct vcpu_vmx` and `struct nested_vmx` can break assumptions in assembly run paths, nested-state save/restore, migration, and userspace nested-state ioctls. Control masks must track Intel capability MSRs and eVMCS support; adding a control without updating required/optional masks or eVMCS sanitation can expose unsupported VMCS fields. MSR bitmap offsets are subtle, especially the low/high read/write regions. Lazy register-cache helpers must not be used for TDX vCPUs where VMCS reads are invalid, hence the explicit warnings. Nested VMCS dirty/sync flags and pinned page maps are high-risk for stale L2 state, leaked pins, or incorrect VMCS12 propagation.

Test signals: build coverage across `CONFIG_X86_64`, `CONFIG_KVM_HYPERV`, `CONFIG_KVM_SMM`, `CONFIG_KVM_INTEL_TDX`, EPT on/off, and nested VMX on/off catches declaration and mask drift. Runtime signals include KVM selftests for VMX controls, nested VMX state save/restore, VMCS shadowing/eVMCS, MSR bitmap interception, PML dirty logging, VPID/EPT invalidation behavior, posted interrupts, SMM with nested VMX, guest DEBUGCTL behavior, and CPU hotplug or vCPU migration while VMCS state is loaded.

# sources/distributed-fs/ceph-client/arch/x86/kvm/vmx/vmx_onhyperv.c

Purpose: implements the small runtime portion of KVM's VMX-on-Hyper-V enlightened VMCS support. Its main job is to advertise eVMCS usage through a static branch and sanitize VMX execution controls so KVM does not attempt to use VMCS fields that Hyper-V's eVMCSv1 does not support.

Important APIs and functions: `DEFINE_STATIC_KEY_FALSE(__kvm_is_using_evmcs)` provides the backing jump-label state consumed by `kvm_is_using_evmcs()` in the header. The local `evmcs_check_vmcs_conf(field, ctrl)` macro computes unsupported bits in a `struct vmcs_config` control field against `EVMCS1_SUPPORTED_*` masks, emits a once-only warning, and clears unsupported bits. `evmcs_sanitize_exec_ctrls(struct vmcs_config *vmcs_conf)` applies that check to primary, pin-based, secondary, tertiary, VM-entry, and VM-exit controls.

Control flow and behavior: VMX capability discovery builds a `vmcs_config`, and when KVM runs nested on Hyper-V with eVMCS enabled, `vmx_hardware_setup()` calls `evmcs_sanitize_exec_ctrls()`. Each control field is masked against the latest eVMCSv1 support definitions. If Hyper-V exposes a VMX feature in capability MSRs that KVM can see but eVMCS lacks a corresponding field, KVM warns once and disables that feature in its effective VMCS configuration.

State and persistence: the only persistent local state is the `__kvm_is_using_evmcs` static key, which changes the fast path of VMCS accessors while the module is loaded. `evmcs_sanitize_exec_ctrls()` mutates the caller's in-memory VMCS capability configuration; it does not store data independently and has no disk persistence.

Dependencies and integration points: depends on `capabilities.h` for `struct vmcs_config` and VMX control definitions, and `vmx_onhyperv.h`/`hyperv_evmcs.h` for eVMCS support masks. It integrates with VMX hardware setup in `vmx.c`, the `vmcs_read*()`/`vmcs_write*()` dispatch path in `vmx_ops.h`, and Hyper-V enlightenments exposed through `asm/mshyperv.h`.

Risks and correctness concerns: the support masks must remain synchronized with Hyper-V eVMCS field definitions. Overly permissive masks can make KVM write fields Hyper-V ignores or rejects; overly restrictive masks disable valid acceleration. The warning path intentionally treats unexpected unsupported bits as a KVM update signal, so new VMX controls require eVMCS support review.

Test signals: boot KVM-on-Hyper-V with eVMCS enabled and verify no unexpected `unsupported with eVMCS` warnings for known-good hosts. Nested virtualization selftests should cover EPT, APICv, TSC scaling, preemption timer, VM-entry/exit MSR controls, and Hyper-V nested flush paths with and without `CONFIG_HYPERV`.

# sources/distributed-fs/ceph-client/arch/x86/kvm/vmx/vmx_onhyperv.h

Purpose: provides the inline enlightened VMCS access layer for running KVM's Intel VMX backend as a nested hypervisor on Hyper-V. It lets normal VMCS accessors transparently read/write `struct hv_enlightened_vmcs` memory instead of executing VMREAD/VMWRITE, and it loads the enlightened VMCS through Hyper-V's VP assist page rather than `VMPTRLD`.

Important APIs and functions: `current_evmcs` casts the current per-CPU VMCS pointer to Hyper-V's enlightened VMCS layout. `kvm_is_using_evmcs()` reads the static key declared here and defined in `vmx_onhyperv.c`. `get_evmcs_offset()` maps an Intel VMCS field encoding to an eVMCS byte offset plus clean-field bit via `evmcs_field_offset()`, warning for unsupported fields. `evmcs_write64()`, `evmcs_write32()`, and `evmcs_write16()` store into the current eVMCS and clear the corresponding `hv_clean_fields` bit. `evmcs_read64()`, `evmcs_read32()`, and `evmcs_read16()` load from eVMCS memory and return zero for unsupported fields. `evmcs_load(u64 phys_addr)` updates Hyper-V's VP assist page to make the enlightened VMCS current and enables enlightened VM-entry. When Hyper-V support is not compiled in, all helpers become cheap stubs.

Control flow and behavior: normal VMCS access in `vmx_ops.h` first checks `kvm_is_using_evmcs()`. If true, control comes here: field encodings are translated, unsupported accesses warn and return without touching memory, supported writes update the eVMCS backing page and mark the associated clean group dirty for Hyper-V. Loading a VMCS writes `current_nested_vmcs` and `enlighten_vmentry` in the per-CPU `hv_vp_assist_page`; if the eVMCS requests nested flush hypercalls, `directhypercall` is enabled in the nested-control features.

State and persistence: state is per-CPU and per-vCPU runtime state. The active enlightened VMCS lives in memory referenced by `current_vmcs`; `hv_clean_fields` persists dirty/clean tracking between VM entries so Hyper-V can avoid reprocessing unchanged field groups. The VP assist page fields persist for the running CPU until changed by KVM, CPU hotplug teardown, or Hyper-V. There is no filesystem persistence.

Dependencies and integration points: gated by `CONFIG_HYPERV` and includes Hyper-V HVDK/MS hypervisor interfaces, Linux jump labels, VMCS12 and eVMCS field-offset definitions, and KVM bug helpers. It is integrated by `vmx_ops.h` accessors, eVMCS capability sanitation, VMX CPU enablement that validates VP assist pages, and nested VMX code that fills eVMCS fields.

Risks and correctness concerns: all field-offset mappings and clean-field bits must match Hyper-V's ABI exactly. A missing clean-field clear can cause Hyper-V to reuse stale VMCS data; an incorrect offset can corrupt unrelated eVMCS state. `evmcs_load()` depends on a valid VP assist page on every CPU where VMX is enabled, and the code treats absence as a KVM bug. Unsupported field reads returning zero can hide issues unless warning coverage is monitored.

Test signals: test with `CONFIG_HYPERV=y` and disabled builds to validate both real and stub paths. Runtime signals include nested KVM-on-Hyper-V boot, CPU hotplug while eVMCS is enabled, VP assist page validation failures, clean-field dirtying after VMCS writes, direct hypercall enablement for nested flush, and selftests that exercise unsupported VMCS field probes.

# sources/distributed-fs/ceph-client/arch/x86/kvm/vmx/vmx_ops.h

Purpose: defines the low-level VMX instruction wrappers and VMCS accessor primitives used throughout KVM's Intel backend. It centralizes compile-time VMCS field-width validation, VMREAD/VMWRITE error handling, eVMCS dispatch, VMCS load/clear, and VPID/EPT invalidation helpers.

Important APIs and functions: error hooks `vmread_error()`, `vmwrite_error()`, `vmclear_error()`, `vmptrld_error()`, `invvpid_error()`, and `invept_error()` are called from inline assembly failure paths. `vmcs_check16()`, `vmcs_check32()`, `vmcs_check64()`, and `vmcs_checkl()` reject constant field/accessor width mismatches at build time. `__vmcs_readl()` executes VMREAD with either `asm_goto_output` or a trampoline fallback. Public accessors `vmcs_read16/32/64/l()` and `vmcs_write16/32/64/l()` route to eVMCS helpers when active, otherwise execute VMREAD/VMWRITE. `vmcs_clear_bits()` and `vmcs_set_bits()` update non-64-bit VMCS fields. `vmcs_clear()` wraps VMCLEAR, `vmcs_load()` wraps VMPTRLD or eVMCS load, `__invvpid()` and `__invept()` build instruction operands, and higher-level `vpid_sync_*()` and `ept_sync_*()` choose the best invalidation extent supported by the CPU.

Control flow and behavior: most VMX implementation code calls these inline accessors rather than issuing VMX instructions directly. Reads validate field width, optionally read eVMCS memory, otherwise execute VMREAD; hardware failures call the instrumentation-safe error hooks and return zero. Writes follow the same width/eVMCS dispatch and use VMWRITE, with 32-bit builds splitting 64-bit VMCS writes into low/high fields. VMCS load chooses Hyper-V's `evmcs_load()` when the static key is active. VPID and EPT synchronization helpers avoid invalidation when VPID zero means tagging is inactive and fall back from individual/context invalidations to broader global invalidations based on CPU capability bits.

State and persistence: the file owns no storage, but its operations mutate hardware VMCS state, enlightened VMCS memory, and processor translation caches. VMCS values persist in the current VMCS/eVMCS until overwritten, cleared, or the VMCS is freed. EPT/VPID invalidations affect CPU-local or global TLB-derived caches according to the selected extent.

Dependencies and integration points: depends on x86 VMX instruction definitions from `asm/vmx.h`, exception-table and nospec infrastructure, KVM spurious-fault handling, eVMCS helpers from `vmx_onhyperv.h`, VMCS data structures from `vmcs.h`, and CPU capability helpers such as `cpu_has_vmx_invvpid_single()` and `cpu_has_vmx_invept_context()`. It is the shared access layer for `vmx.c`, `nested.c`, PMU, SGX, posted interrupt, APICv, and nested VMX paths.

Risks and correctness concerns: inline assembly constraints and failure labels are architecture-sensitive; incorrect constraints can corrupt registers or miss VM-Fail handling. Accessor-width checks only catch constant fields, so dynamic field values still rely on caller correctness. 32-bit high-half handling for 64-bit fields must remain consistent with Intel VMCS encoding. eVMCS dispatch means any new VMCS accessor must preserve clean-field and unsupported-field behavior. Invalidating too narrowly risks stale translations; invalidating too broadly hurts performance but is safe.

Test signals: compile matrix coverage with and without `CONFIG_CC_HAS_ASM_GOTO_OUTPUT`, 32-bit and 64-bit x86 builds, and Hyper-V/eVMCS builds is important. Runtime signals include KVM selftests that force VMREAD/VMWRITE paths, nested VMX VMCS access, EPT/VPID invalidation correctness, TLB shootdown behavior after MMU changes, module load on CPUs with different INVEPT/INVVPID capabilities, and fault-injection or debug coverage for VMX instruction error handlers.

# sources/distributed-fs/ceph-client/arch/x86/kvm/vmx/x86_ops.h

Purpose: declares the Intel VMX implementation entry points that populate KVM's generic `kvm_x86_ops` and `kvm_x86_init_ops` interfaces, plus optional TDX overrides. It is the contract between the common x86 KVM core and VMX-specific lifecycle, run-loop, state access, interrupt, MMU, APIC, MSR, nested, timer, and ioctl behavior.

Important APIs and functions: initialization declarations include `vmx_hardware_setup()`, `vmx_hardware_unsetup()`, `vmx_check_processor_compat()`, CPU virtualization enable/disable/emergency-disable, and exported init/runtime ops `vt_init_ops` and `vt_x86_ops`. VM/vCPU lifecycle hooks include `vmx_vm_init()`, `vmx_vm_destroy()`, `vmx_vcpu_precreate()`, `vmx_vcpu_create()`, `vmx_vcpu_free()`, `vmx_vcpu_reset()`, load/put, pre-run, run, and exit handling. State hooks cover MSRs, segments, CPL, CR0/CR4/EFER validation and writes, descriptor tables, DR7/debug registers, RFLAGS, interrupt shadow, TLB flushing, MMU root loading, hypercall patching, exception/IRQ/NMI injection, APICv operations, TSS/identity-map setup, memory type masks, exit/entry info, TSC offset/scaling, dirty logging, VMX preemption timer, and MCE setup. Under `CONFIG_KVM_SMM`, SMM entry/exit and SMI-window hooks are declared. Under `CONFIG_KVM_INTEL_TDX`, TDX VM/vCPU lifecycle, run/exit, interrupt, MSR, ioctl, TLB, MMU, and private memory helpers are declared.

Control flow and behavior: `main.c` builds `vt_x86_ops` from these VMX functions so generic KVM x86 code can call through a stable backend interface. Hardware setup probes capabilities and may adjust function pointers for features such as APICv, Hyper-V remote TLB flushes, timers, nested VMX, or TDX. The vCPU run path flows from common KVM into `vmx_vcpu_pre_run()`, `vmx_vcpu_run()`, irqoff exit handling, and `vmx_handle_exit()`. State accessors translate generic KVM requests into VMCS, MSR bitmap, APICv, EPT, VPID, and nested VMX operations.

State and persistence: this header has no storage, but it declares functions that manipulate persistent in-memory VM and vCPU state in `struct kvm_vmx`, `struct vcpu_vmx`, generic `struct kvm_vcpu`, VMCS pages, MSR autoload/autostore lists, APICv/PI descriptors, EPT roots, TSC scaling fields, and optional TDX private state. Function-pointer tables initialized from these declarations persist while the KVM module is loaded.

Dependencies and integration points: depends on generic KVM host structures, VMX private `x86.h`, x86 instruction decode/intercept structures, LAPIC, SMM, MMU, TDX, and common KVM x86 backend registration. Integrates with `vmx.c`, `main.c`, `nested.c`, `tdx.c`, `pmu_intel.c`, APIC/interrupt code, Hyper-V enlightenment paths, and KVM userspace ioctls.

Risks and correctness concerns: declarations must match the definitions and `kvm_x86_ops` expected signatures exactly; mismatches break builds or, worse, callback semantics. Because `vt_x86_ops` can be patched at hardware setup time, consumers must handle NULL feature hooks correctly. TDX and VMX share a VT ops surface but have different VMCS access rules, interrupt behavior, and private-memory constraints. Lifecycle ordering is sensitive: CPU virtualization enablement, VMCS allocation, vCPU load/put, and emergency disable paths must remain consistent with generic KVM locking and CPU hotplug.

Test signals: build coverage across SMM, TDX, Hyper-V, nested VMX, x86-64-only timer paths, and minimal configs validates the declaration surface. Runtime signals include KVM unit/selftests for vCPU creation/run/reset, MSR and segment state ioctls, CR/EFER validation, interrupt/NMI/window injection, APICv and posted interrupts, TLB flush hooks, dirty logging, nested virtualization, suspend/emergency virtualization disable, and TDX-specific VM/vCPU ioctls when enabled.
