# sources/distributed-fs/ceph-client/drivers/md/md-bitmap.c

Purpose: Implements the original MD bitmap submodule (`ID_BITMAP`) plus the `none` bitmap placeholder. It tracks dirty/resync-needed MD regions with in-memory 16-bit counters and persists one bit per chunk either in an internal metadata-adjacent bitmap or in a file-backed bitmap when `CONFIG_MD_BITMAP_FILE` is enabled. The bitmap lets MD avoid full resync after crashes, drive failures, re-adds, and clustered slot handoff.

Important APIs/types/functions: Local `struct bitmap` owns `bitmap_counts`, `bitmap_storage`, event state, flush wait queues, write-behind accounting, sysfs nodes, and clustered slot number. `struct bitmap_page` stores per-counter pages, including a low-memory "hijacked pointer" fallback. Core operations are exposed through `struct bitmap_operations bitmap_ops`: `bitmap_create()`, `bitmap_load()`, `bitmap_destroy()`, `bitmap_resize()`, `bitmap_start_write()`, `bitmap_end_write()`, `bitmap_start_sync()`, `bitmap_end_sync()`, `bitmap_cond_end_sync()`, `bitmap_close_sync()`, `bitmap_dirty_bits()`, `bitmap_unplug()`, `bitmap_daemon_work()`, `bitmap_update_sb()`, `bitmap_get_from_slot()`, and `bitmap_copy_from_slot()`. Module lifecycle is `md_bitmap_init()`/`md_bitmap_exit()`.

Control flow: Creation rejects journaled arrays, opens/caches any bitmap file, reads or creates the bitmap superblock, then calls `__bitmap_resize(..., init=true)` to allocate storage pages and counter pages. Loading creates serial pools, loads clustered slot bitmaps if needed, resets stale sync state, imports on-disk bits through `md_bitmap_init_from_disk()`, clears `BITMAP_STALE`, schedules recovery, and updates the bitmap superblock. For write I/O, `bitmap_start_write()` obtains or allocates the counter for each covered chunk, sets the persistent bit before data is submitted, handles counter overflow by waiting on `overflow_wait`, and increments the 14-bit counter. `bitmap_end_write()` updates `events_cleared` on clean arrays, marks degraded chunks `NEEDED`, decrements the counter, and marks pages pending for daemon cleanup. Resync uses `NEEDED_MASK` and `RESYNC_MASK`: `bitmap_start_sync()` reports chunks needing recovery, `bitmap_end_sync()` either clears active resync or re-marks aborted chunks needed, and `bitmap_close_sync()` sweeps any remaining active bits.

State and persistence: In-memory counters encode `NEEDED`, `RESYNC`, and pending write count in one `u16`. A counter value of 0 means the disk bit is clear, 1 means only the on-disk bit remains, 2 is the daemon-clearing threshold, and higher values include outstanding writes. `bitmap_storage` caches the bitmap superblock page, bitmap data pages, and per-page attributes (`DIRTY`, `PENDING`, `NEEDWRITE`). `bitmap_update_sb()` persists MD event counters, state flags, daemon sleep, write-behind limit, sync size, chunksize, nodes, and reserved sectors. File-backed bitmaps map file blocks via `bmap()` and bypass the filesystem on later writes; internal bitmaps write pages to active rdev metadata areas with overlap checks. `BITMAP_WRITE_ERROR` triggers `md_bitmap_file_kick()`, setting `BITMAP_STALE` and forcing conservative recovery.

Dependencies/integration: Depends on MD core (`mddev`, `md_rdev`, personality quiesce, serial pools, recovery flags, sysfs), block-device metadata I/O (`sync_page_io()`, `md_write_metadata()`, `md_super_wait()`), optional file-backed bitmap support (`buffer_head`, `bmap()`), clustered MD (`md_setup_cluster()`, `md_cluster_stop()`, slot bitmap copy), and the shared declarations in `md-bitmap.h`. The sysfs `bitmap/` group exposes location, space, time_base, backlog, chunksize, metadata, can_clear, and max_backlog_used.

Risks and test signals: Test counter overflow and wakeup behavior, low-memory page hijacking, degraded write paths preserving `NEEDED`, daemon clearing over multiple runs, superblock event mismatch forcing stale recovery, internal bitmap overlap rejection around metadata/data boundaries, file-backed bitmap block mapping failures, clustered slot offset math, resize rollback after cluster preallocation failure, and sysfs add/remove error unwinds. Pay close attention to lock transitions in `md_bitmap_checkpage()` because it deliberately drops `counts.lock` while allocating, and to `bitmap_copy_from_slot()` because it both imports remote dirty bits and optionally clears the donor bitmap.

# sources/distributed-fs/ceph-client/drivers/md/md-bitmap.h

Purpose: Defines the common MD bitmap on-disk superblock format, bitmap state flags, statistics structure, and operation vtable used by both the original bitmap (`md-bitmap.c`) and lockless bitmap (`md-llbitmap.c`) implementations.

Important APIs/types/functions: `bitmap_super_t` is the 256-byte little-endian persistent header with magic, version, MD UUID, event counters, sync size, state flags, chunksize, daemon sleep, write-behind, reserved sectors, clustered node count, and cluster name. Version constants distinguish host-endian legacy, little-endian, clustered, and lockless formats. `enum bitmap_state` defines `BITMAP_STALE`, `BITMAP_WRITE_ERROR`, lockless first-use/clean/daemon flags, and `BITMAP_HOSTENDIAN`. `struct md_bitmap_stats` normalizes stats used by cluster code and sysfs. `struct bitmap_operations` is the submodule contract for create/load/destroy/flush/write tracking/discard/sync/cluster-slot helpers/stats/sysfs groups.

Control flow: This header has no standalone runtime flow, but its inline helpers gate callers. `md_bitmap_registered()` checks whether a bitmap provider is selected. `md_bitmap_enabled()` verifies a provider and bitmap object are present, then delegates to provider `enabled()`. `md_bitmap_start_sync()` and `md_bitmap_end_sync()` fall back to 1024-sector full-resync chunks when no bitmap is active; otherwise they delegate to the selected bitmap implementation.

State and persistence: The persistent contract is `bitmap_super_t`. Comments document event-counter rules: bitmap `events` must match or be one ahead of MD metadata, and `events_cleared` records the last clean-array bit clearing point used for accepting re-added devices. `sync_size` records the device range covered by resync, with RAID-level-specific interpretation.

Dependencies/integration: Included by MD bitmap providers, clustered MD, and MD core paths that call through `mddev->bitmap_ops`. It depends on MD types (`struct mddev`, `struct md_rdev`) being available via surrounding includes and uses `sector_t`, `struct file`, and `struct attribute_group` from kernel headers.

Risks and test signals: Changes here affect all bitmap providers. Validate ABI/layout stability of the 256-byte superblock, version compatibility, endian handling, fallback sync behavior without a bitmap, and complete initialization of all `bitmap_operations` entries for each provider. Any new operation must be handled by `bitmap_none_ops`, legacy bitmap, lockless bitmap, and clustered callers.

# sources/distributed-fs/ceph-client/drivers/md/md-cluster.c

Purpose: Implements clustered MD coordination using DLM lockspaces and lock value blocks. It serializes metadata updates, distributes resync/suspend regions, coordinates new-disk/remove/re-add events, owns per-node bitmap slot recovery, and registers the `ID_CLUSTER` MD submodule.

Important APIs/types/functions: `struct md_cluster_info` holds the DLM lockspace, slot number, bitmap/resync/message/token/ack/no-new-dev lock resources, receive and recovery threads, suspend region, state flags, and wait/completion objects. `struct dlm_lock_resource` wraps DLM lock state and optional LVB storage. Message protocol is `enum msg_type` plus `struct cluster_msg`. Main exported vtable entries are `join()`, `leave()`, `slot_number()`, `metadata_update_start/finish/cancel()`, `resync_start/finish()`, `resync_info_update/get()`, `resync_start_notify()`, `area_resyncing()`, `add_new_disk()`, `new_disk_ack()`, `remove_disk()`, `load_bitmaps()`, `gather_bitmaps()`, `resize_bitmaps()`, `lock_all_bitmaps()`, `unlock_all_bitmaps()`, and `update_size()`.

Control flow: `join()` allocates cluster state, creates a DLM lockspace named from the MD UUID and cluster name, waits for DLM slot assignment, starts the receive thread, initializes communication locks, takes shared ACK/no-new-dev locks, and takes this node's bitmap lock in protected-write mode. DLM recovery callbacks set read-balancing suspension during lock recovery and schedule `recover_bitmaps()` when a node's slot fails. Message senders serialize on `MD_CLUSTER_SEND_LOCK` and the token lock, write a `cluster_msg` into the message LVB, then force peer receive by converting the ACK lock. `recv_daemon()` reads the message LVB under the message lock, dispatches `process_recvd_msg()`, and performs the ACK/message lock dance that releases the sender.

State and persistence: Cluster state is mostly in DLM locks and LVBs. Bitmap locks are named `bitmap%04d` per slot and use LVBs to publish `struct resync_info` ranges. The message lock LVB carries one `cluster_msg`. The token lock serializes cluster-wide metadata operations. The no-new-dev lock prevents metadata progress until all nodes have acknowledged a new disk. In-memory state bits distinguish join progress, receive readiness, communication ownership, new-disk waits, remote resync waits, and reconfig-mutex handoff.

Dependencies/integration: Integrates with Linux DLM (`dlm_new_lockspace()`, `dlm_lock()`, `dlm_unlock()`), MD core locking and recovery flags, MD metadata reload/update paths, MD personality quiesce/resize/size callbacks, bitmap operations for slot copy/update/resize/stats, block device capacity notification, kobject uevents for new-disk discovery, and module submodule registration.

Risks and test signals: Exercise join failure cleanup at every lock/thread allocation step, DLM lock timeouts and interruptible cancellation, sender/receiver ACK ordering, reconfig-mutex deadlock avoidance via `MD_CLUSTER_HOLDING_MUTEX_FOR_RECVD`, node failure recovery copying and clearing remote bitmaps, remote resync suspend range overlap, metadata update with no good active device, new-disk timeout and no-new-dev lock release, bitmap resize rollback, and capacity change propagation. Audit `lock_all_bitmaps()` error paths because partially initialized `other_bitmap_lockres` entries must still be released by later cleanup.

# sources/distributed-fs/ceph-client/drivers/md/md-cluster.h

Purpose: Declares the MD cluster submodule interface consumed by MD core and cluster-aware personalities. It abstracts clustered coordination behind `struct md_cluster_operations` so the rest of MD can join/leave a cluster, coordinate metadata, synchronize recovery, and coordinate bitmap slots without depending on DLM internals.

Important APIs/types/functions: `struct md_cluster_operations` embeds `struct md_submodule_head` and provides callbacks for cluster lifecycle (`join`, `leave`, `slot_number`), resync coordination (`resync_start`, `resync_finish`, `resync_info_update/get`, `resync_start_notify`, `resync_status_get`, `area_resyncing`), metadata update serialization (`metadata_update_start/finish/cancel`, `update_size`), disk membership (`add_new_disk`, `add_new_disk_cancel`, `new_disk_ack`, `remove_disk`), and bitmap-slot coordination (`load_bitmaps`, `gather_bitmaps`, `resize_bitmaps`, `lock_all_bitmaps`, `unlock_all_bitmaps`). It also declares `md_setup_cluster()`, `md_cluster_stop()`, and `md_reload_sb()`.

Control flow: No executable logic lives here. MD code calls these operations through `mddev->cluster_ops` after the cluster submodule is registered. The typical lifecycle is setup/join during bitmap read, bitmap loading across slots, metadata/resync/disk callbacks while the array is active, and leave/stop during teardown.

State and persistence: The header does not own state; all state is behind `mddev->cluster_info` in `md-cluster.c`. Its callback signatures show the persisted/shared concepts: MD event metadata, resync low/high ranges, rdev descriptors, bitmap sizes, and array size changes.

Dependencies/integration: Includes `md.h` and forward-declares MD core types. It is the contract between MD core, bitmap code, and the DLM-backed implementation in `md-cluster.c`.

Risks and test signals: Callback ordering matters. Validate callers handle missing cluster ops, propagate callback errors, and pair start/finish/cancel paths for metadata updates and add-disk operations. Any interface extension must update the concrete `cluster_ops` initializer and all call sites that assume a callback is present.

# sources/distributed-fs/ceph-client/drivers/md/md-linear.c

Purpose: Implements the deprecated MD linear personality, which concatenates member devices into one address space without redundancy. It maps incoming bios to the rdev whose cumulative end sector contains the bio sector, splitting bios that cross device boundaries.

Important APIs/types/functions: `struct dev_info` stores an rdev and its cumulative `end_sector`. `struct linear_conf` stores array size, a copy of `raid_disks`, RCU head, and the flexible array of devices. `which_dev()` binary-searches `conf->disks`. `linear_conf()` builds and validates the mapping. `linear_run()` initializes the personality. `linear_add()` hot-adds a new tail device by building a replacement config and swapping it with RCU. `linear_make_request()` remaps bios. `linear_error()` marks the whole array broken. The module registers `linear_personality` under `ID_LINEAR`.

Control flow: `linear_run()` rejects bitmaps with `md_check_no_bitmap()`, builds a configuration from rdev raid slots, sets array sectors, and registers integrity. `linear_conf()` validates every expected disk is present exactly once, optionally rounds member sectors down to `chunk_sectors`, computes cumulative end sectors, and stacks queue limits unless running under dm-raid. For I/O, `linear_make_request()` handles flushes through MD, finds the target rdev, validates bounds and device health, splits crossing bios at `end_sector`, accounts the bio, remaps `bi_bdev` and sector by subtracting the device start and adding `data_offset`, ignores unsupported discards, checks write-zeroes, and submits without accounting. `linear_add()` requires the new rdev's saved raid slot to equal the old disk count, then swaps in a new config and updates capacity.

State and persistence: Runtime mapping state is in `mddev->private` as `struct linear_conf`. Hot-add uses RCU so old mappings survive until readers drain. Persistent array layout is still from MD metadata/rdev raid slots; this file only builds the in-memory concatenation view. There is no bitmap or recovery state because linear arrays have no redundancy.

Dependencies/integration: Uses MD personality registration, MD rdev iteration, queue-limit stacking, MD flush/accounting/error helpers, block trace remap events, bio split/submission, integrity registration, RCU free, and module aliases for the linear level.

Risks and test signals: Test out-of-order or duplicate raid slots, missing devices, zero/odd `chunk_sectors` rounding, queue-limit failures, bio splits exactly at boundaries, out-of-bounds bios after hot-add, unsupported discard completion, broken rdev error handling, RCU lifetime during concurrent hot-add and I/O, and capacity notification after growth. Since failure of one disk marks the whole linear array broken, error-path tests should verify no silent remap to later devices occurs.

# sources/distributed-fs/ceph-client/drivers/md/md-llbitmap.c

Purpose: Implements the lockless MD bitmap provider (`ID_LLBITMAP`). Unlike the legacy counter bitmap, it stores one byte of state per chunk, keeps all bitmap pages cached, makes write fast paths avoid a global bitmap spinlock via per-page `percpu_ref` barriers, supports discard/unwritten states, and adds lazy/proactive recovery behavior for RAID456.

Important APIs/types/functions: `enum llbitmap_state` defines byte states: unwritten, clean, dirty, need-sync, syncing, proactive need-sync-unwritten, syncing-unwritten, clean-unwritten, and sentinel values. `enum llbitmap_action` drives the table-based state machine. `struct llbitmap_page_ctl` owns a cached page, byte-state pointer, dirty sub-block bitmap, expiry, waitqueue, and `percpu_ref active` barrier. `struct llbitmap` owns page controls, geometry, timers/work, flags, events, and behind-write counters. Key functions are `llbitmap_state_machine()`, `llbitmap_cache_pages()`, `llbitmap_read_sb()`, `llbitmap_init()`, `llbitmap_start_write()/end_write()`, `llbitmap_start_discard()/end_discard()`, `llbitmap_unplug()`, `llbitmap_flush()`, `llbitmap_start_sync()/end_sync()/close_sync()/cond_end_sync()`, `llbitmap_skip_sync_blocks()`, `llbitmap_update_sb()`, sysfs show/store handlers, and `md_llbitmap_init()/exit()`.

Control flow: Creation validates support: no journal, persistent internal metadata, no bitmap file, no external metadata, and no dm-raid. It allocates `struct llbitmap`, sets I/O granularity from the MD queue logical block size, initializes timer/work and waitqueues, installs `mddev->bitmap`, then reads the lockless bitmap superblock. First-use superblocks call `llbitmap_init()`, which chooses a chunksize that fits reserved bitmap space, caches all pages, initializes all chunk states to `BitUnwritten`, `BitClean`, or `BitCleanUnwritten` when all RAID456 devices can be zeroed, and flushes initial state. Normal load applies `BitmapActionReload` or `BitmapActionStale`, turning dirty/stale states into recovery work. Write start raises page barriers and runs `BitmapActionStartwrite`; write end releases barriers. The daemon/timer suspends expired pages by killing their percpu refs, transforms dirty to clean, then resumes the page.

State and persistence: Persistent data starts at `BITMAP_DATA_OFFSET` bytes after a standard bitmap superblock and stores one state byte per chunk. Dirty persistence is tracked per bitmap page and per `io_size` sub-block; `llbitmap_write_page()` writes only dirty sub-blocks to all non-faulty member metadata areas. `llbitmap_update_sb()` persists MD events, flags, chunksize, sync size, events_cleared, reserved sectors, and daemon sleep. `BITMAP_WRITE_ERROR` disables the provider. The pending timer starts on first dirty state and schedules daemon work after `daemon_sleep`; `barrier_idle` controls when recently touched pages can be cleaned. Resync state transitions turn need-sync into syncing, end-sync into dirty/cleanable, abort into need-sync, and can skip unwritten/clean-unwritten areas.

Dependencies/integration: Integrates with MD bitmap operations, MD recovery flags (`MD_RECOVERY_NEEDED`, `MD_RECOVERY_SYNC`, `MD_RECOVERY_LAZY_RECOVER`, `MD_RECOVERY_RECOVER`), RAID level helpers, rdev metadata I/O (`sync_page_io()`, `md_write_metadata()`, `md_super_wait()`), block zeroing (`blkdev_issue_zeroout()`), workqueues/timers/percpu refs, sysfs `llbitmap/` attributes, and MD write-behind wait semantics.

Risks and test signals: Test state-machine coverage for every state/action pair, RAID456 first-write lazy recovery, proactive sync sysfs behavior, degraded-array write and resync behavior, discard alignment using `DIV_ROUND_UP_SECTOR_T`, timer rearming when pages are dirty but not expired, daemon timeout when active refs do not drain, unplug workqueue deadlock avoidance, partial sub-block writes, write-zeroes initialization failures, resize without reallocating page cache, and `BITMAP_WRITE_ERROR` propagation. Audit `llbitmap_read_sb()` cleanup ordering because the code frees `sb_page` before `kunmap_local(sb)`, which is a suspicious lifetime ordering and should be validated on the target kernel.
