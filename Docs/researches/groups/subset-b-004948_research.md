# sources/distributed-fs/ceph-client/drivers/net/wireless/realtek/rtw89/rtw8852b_rfk_table.c

Purpose: Provides the RTL8852B RFK register programming tables used by the RTW89 PHY/RF calibration code. The file has no active functions of its own; it is a catalog of `static const struct rtw89_reg5_def` arrays that are exported as `const struct rtw89_rfk_tbl` objects through `RTW89_DECLARE_RFK_TBL()`. Runtime calibration logic in `rtw8852b_rfk.c` selects and parses these tables to initialize AFE blocks, perform DACK/DPK setup and restore, and configure TSSI power tracking for path A/path B and 2.4/5 GHz channel groups.

Important APIs and data: Every table entry is a five-field RFK command consumed by `rtw89_rfk_parser()`: `RTW89_DECL_RFK_WM()` writes a masked BB/PHY register, `RTW89_DECL_RFK_WRF()` writes an RF register on a selected path, and `RTW89_DECL_RFK_DELAY()` inserts a microsecond delay. Key exported tables include `rtw8852b_afe_init_defs_tbl`, ADDC/DADC check tables for paths A/B, staged DACK tables `rtw8852b_dack_s0_*_defs_tbl` and `rtw8852b_dack_s1_*_defs_tbl`, DPK setup/restore/KIP tables, base TSSI system tables, per-path/per-band TSSI system tables, TSSI TX power initialization tables, HE TB tables, DCK tables, DAC gain zeroing tables, TSSI slope tables, and TSSI alignment tables split by path, band, channel range, and all-vs-part programming.

Control flow: This file contributes data to parser-driven control flow. `rtw8852b_rfk.c` calls `rtw89_rfk_parser(rtwdev, &table)` or `rtw89_rfk_parser_by_cond()` from calibration helpers. The parser walks the array in source order and dispatches each entry by `flag`, so ordering in each array is the effective control flow. AFE and DPK tables generally set up shared BB/AFE registers, enable/disable calibration paths, then restore registers after calibration. DACK tables are staged per RF path: stage 1 enables and prepares analog/DACK bits, stage 2 restores selected toggles after a delay, and stage 3 disables the calibration trigger and returns mode selectors. TSSI setup first applies common system settings, then path/band tables, then TX power, DCK, DAC gain, slope, and alignment tables according to RF path and current channel.

State and persistence: The arrays are immutable `.rodata`, but parsing them mutates persistent device hardware state through BB/PHY and RF register writes. Effects persist until later calibration tables, channel changes, power transitions, firmware/driver reinitialization, or hardware reset overwrite them. The file itself stores no runtime state, locks, or cache; runtime state such as `rtwdev->is_tssi_mode`, thermal readings, DPK backup slots, and current channel selection is maintained in the consumer RFK code that decides which table to parse.

Dependencies and integration points: Includes `rtw8852b_rfk_table.h`, which includes `phy.h` for `struct rtw89_rfk_tbl`, RF path constants, and RFK declaration macros. The backing command structure is `struct rtw89_reg5_def` from `core.h`. Runtime execution depends on `rtw89_rfk_parser()` in `phy.c`, whose handlers call `rtw89_phy_write32_mask()`, `rtw89_write_rf()`, register set/clear helpers, and `udelay()`. The object is built by the RTW89 Makefile as `rtw8852b_rfk_table.o`, and table symbols are consumed by `rtw8852b_rfk.c`.

Risks: The values are hardware programming sequences with little type-level protection. A wrong register address, mask, value, RF path, delay, or table ordering can silently break calibration, transmit power tracking, EVM, thermal compensation, or regulatory power behavior. The parser does not bounds-check `flag` beyond the compile-time handler array shape, so malformed table entries would dispatch incorrectly. Per-path tables are mostly mirrored between address ranges `0x58xx/0x78xx`, `0x56xx/0x76xx`, and path A/B RF writes; copy/paste drift is a realistic maintenance risk. The 5 GHz alignment tables select by channel ranges, so missing or incorrect ranges can leave `tbl` unset or program the wrong alignment coefficients.

Test signals: Build and modpost coverage verify that every declared table symbol exists and that consumers link. Runtime signals include RFK debug traces from DACK, DPK, and TSSI paths; successful probe and PHY initialization; channel changes across 2.4 GHz and 5 GHz low/mid/high bands; path A/path B calibration; TSSI enablement and thermal tracking; DPK tracking stability; and absence of RFK timeout or degraded TX power/EVM reports. Hardware or RF lab validation is the meaningful test for numeric table changes; unit tests can only catch structure/linkage mistakes.

# sources/distributed-fs/ceph-client/drivers/net/wireless/realtek/rtw89/rtw8852b_rfk_table.h

Purpose: Declares the external RFK table symbols exported by `rtw8852b_rfk_table.c` for RTL8852B calibration code. It is the linkage contract between table definitions and `rtw8852b_rfk.c`, allowing calibration helpers to select named `struct rtw89_rfk_tbl` sequences without exposing the private `struct rtw89_reg5_def` arrays.

Important APIs and types: The header includes `phy.h` for `struct rtw89_rfk_tbl` and declares `extern const struct rtw89_rfk_tbl` objects. The declarations cover AFE initialization, ADDC/DADC enable/disable checks, DACK stage tables for RF paths A and B, DPK AFE setup/restore and KIP setup, TSSI common system configuration, per-path 2 GHz/5 GHz system tables, TX power initialization, HE TB power initialization, TSSI DCK, DAC gain tables, path/band slope tables, channel-range alignment tables, and final TSSI slope enable tables.

Control flow: The header has no executable logic, but its declarations define the names available to the RFK control flow. `rtw8852b_rfk.c` binds these symbols into ordered calibration flows by passing addresses such as `&rtw8852b_tssi_align_a_5g2_all_defs_tbl` to `rtw89_rfk_parser()`. Conditional selection is done outside the header based on RF path, current band, channel range, and whether the full or partial alignment sequence is needed.

State and persistence: No mutable state is declared. The `const` table objects refer to immutable arrays in the C file, but parsing those objects produces persistent hardware register state. The header therefore participates in hardware state transitions indirectly through symbol exposure.

Dependencies and integration points: Depends on `phy.h`, which in turn provides the RFK table type and parser prototype. Included by `rtw8852b_rfk_table.c` for definition consistency and by `rtw8852b_rfk.c` for consumption. The symbol list must stay synchronized with every `RTW89_DECLARE_RFK_TBL()` in the C file and with every direct table reference in RTL8852B RFK logic.

Risks: Missing, misspelled, or stale declarations cause compile/link failures for consumers. More subtle risk comes from declaring a table that is no longer selected or failing to declare a new table, which can leave intended hardware programming unreachable. Because all declarations share the same opaque type, the compiler cannot detect semantic mixups such as using a path B table in a path A flow or a 5 GHz alignment table for 2 GHz operation.

Test signals: Normal kernel/module build catches symbol and type mismatches. Grep or static checks comparing `extern` declarations against `RTW89_DECLARE_RFK_TBL()` definitions catch dead or missing declarations. Runtime coverage should exercise each consumer path: AFE init, DACK on both paths, DPK setup/restore, and TSSI setup across path A/path B and 2 GHz/5 GHz channel groups.
