# sources/distributed-fs/ceph-client/drivers/pci/hotplug/ibmphp_ebda.c

Purpose: Parses IBM BIOS Extended BIOS Data Area hot-swap metadata for the legacy IBM PCI Hot Plug driver. It maps EBDA, finds Hot Swap and RIO data blocks, reconstructs hotplug controllers, slots, bus metadata, and POST-assigned PCI resource records, then registers the discovered slots with the PCI hotplug core.

Important APIs and functions: Public entry points include `ibmphp_access_ebda()`, `ibmphp_get_total_controllers()`, `ibmphp_get_slot_from_physical_num()`, `ibmphp_find_same_bus_num()`, `ibmphp_get_bus_index()`, `ibmphp_free_bus_info_queue()`, `ibmphp_free_ebda_hpc_queue()`, `ibmphp_free_ebda_pci_rsrc_queue()`, and `ibmphp_register_pci()`. Major internal helpers include `ebda_rio_table()`, `ebda_rsrc_controller()`, `ebda_rsrc_rsrc()`, RIO grouping helpers such as `combine_wpg_for_chassis()`, `combine_wpg_for_expansion()`, `find_chassis_num()`, `find_rxe_num()`, and slot naming helper `create_file_name()`.

Control flow: `ibmphp_access_ebda()` reads the EBDA segment pointer at BIOS data area `0x40:0x0e`, maps the EBDA block, walks chained data blocks from offset `0x180`, validates hot-swap block signature `0x4853` and RIO signature `0x4752`, then records controller and resource table offsets. If a RIO v3 table exists, `ebda_rio_table()` builds raw chassis and expansion-box lists. `ebda_rsrc_controller()` walks every EBDA controller descriptor, allocates a `struct controller` plus per-controller EBDA slot/bus arrays, builds `bus_info_head`, fills concrete `struct slot` instances, reads initial hardware slot state through `ibmphp_hpc_readslot()`, initializes device numbers with `ibmphp_init_devno()`, and registers each slot with `pci_hp_register()`. `ebda_rsrc_rsrc()` turns EBDA IO/MEM/PFM records into `struct ebda_pci_rsrc` nodes for later resource initialization.

State and persistence: The file owns global lists `ibmphp_ebda_pci_rsrc_head` and `ibmphp_slot_head`, plus private lists for controllers, bus information, RIO details, and optimized RIO grouping. Parsed EBDA contents persist as kernel heap objects until module cleanup frees the queues. Controller PCI devices are attached later by `ibmphp_probe()` when `ibmphp_register_pci()` registers a PCI driver for controller type 1.

Dependencies and integration points: Depends on `ibmphp.h` data structures and helpers, Linux PCI and list APIs, `ioremap()`/`readb()`/`readw()`/`readl()`, hotplug core `pci_hp_register()`, hardware access from `ibmphp_hpc.c`, resource consumption by `ibmphp_res.c`, and slot/device initialization from the broader IBM PHP driver. It also registers a small PCI driver for IBM HPC PCI controllers so config-space register access can find the backing `pci_dev`.

Risks: EBDA parsing is firmware-trust-heavy and uses many computed offsets with limited bounds checks beyond the top-level next-block guard. `create_file_name()` returns a static buffer, so callers must copy the name immediately as this file does. Error paths in `ebda_rsrc_controller()` can leak objects already linked to global lists or registered hotplug slots because cleanup is local to the current controller/slot. `ibmphp_free_bus_info_queue()` does not `list_del()` freed entries, which is acceptable only during teardown when the list is not reused. Slot naming and RIO grouping depend on legacy platform assumptions about chassis and RXE slot numbering.

Test signals: Boot or module load on supported IBM hardware should log EBDA size, hot swap table format 4, controller/resource counts, registered slot names, and PCI controller binding. Negative tests include missing EBDA, wrong block format, unsupported controller type, PCI hotplug slot registration failure, and cleanup after partial allocation failure. Runtime validation comes from populated `/sys/bus/pci/slots/*`, correct physical slot names, and successful `ibmphp_rsrc_init()` consumption of `ibmphp_ebda_pci_rsrc_head`.

# sources/distributed-fs/ceph-client/drivers/pci/hotplug/ibmphp_hpc.c

Purpose: Implements low-level IBM Hot Plug Controller access and polling. It abstracts ISA, PCI config-space, and Winnipeg/I2C-style controllers, issues slot and bus commands, serializes hardware transactions, polls for slot/latch changes, and drives higher-level enable/disable updates when hardware state changes.

Important APIs and functions: Public APIs are `ibmphp_hpc_readslot()`, `ibmphp_hpc_writeslot()`, `free_hpc_access()`, `ibmphp_lock_operations()`, `ibmphp_unlock_operations()`, `ibmphp_hpc_start_poll_thread()`, and `ibmphp_hpc_stop_poll_thread()`. Internal accessors include `i2c_ctrl_read()`, `i2c_ctrl_write()`, `isa_ctrl_read()`, `isa_ctrl_write()`, `pci_ctrl_read()`, `pci_ctrl_write()`, `ctrl_read()`, `ctrl_write()`, command index mappers `hpc_writecmdtoindex()`/`hpc_readcmdtoindex()`, event processors `process_changeinstatus()`/`process_changeinlatch()`, and `hpc_wait_ctlr_notworking()`.

Control flow: Read and write operations validate command arguments, convert logical slot/bus/controller commands to controller register indexes, lock `sem_hpcaccess`, optionally map Winnipeg BAR space, wait for the controller not-working state, issue register accesses, wait for completion, update slot/controller cached status, unmap, and unlock. The polling thread cycles through latch-register polling and full slot polling under `operations_mutex`, comparing old and new slot snapshots. Status changes can call `ibmphp_do_disable_slot()` on unsafe power-good or latch transitions and then `ibmphp_update_slot_info()`.

State and persistence: The file persists two mutexes, a poll-thread pointer, an exit completion, and `to_debug` polling verbosity. Hardware state persists in controller registers and cached fields in `struct controller`/`struct slot`: slot status, extended status, bus status, controller status, and operation flags. Polling continues until module exit calls `kthread_stop()` and waits on `exit_complete`.

Dependencies and integration points: Consumes controller and slot topology built by `ibmphp_ebda.c`, bus indexes from `ibmphp_get_bus_index()`, slot count from `ibmphp_get_total_controllers()`, and slot lookup from `ibmphp_get_slot_from_physical_num()`. It calls higher-level IBM PHP operations for disable and sysfs/cache update, and uses Linux I/O port, PCI config-space, MMIO, mutex, completion, and kthread APIs.

Risks: Winnipeg I2C wait loops use constants named as seconds but sleep 10 ms per iteration in some paths, so timeout semantics are non-obvious. `ibmphp_hpc_stop_poll_thread()` locks operations after stopping the thread and then calls `free_hpc_access()` without taking `sem_hpcaccess` in that function, a fragile legacy synchronization pattern. Polling compares raw bitfields and can trigger disable on transient power-good/latch changes. The latch mask uses `0x01 << i` over physical slot numbers, so slot numbering beyond the low bits would be unsafe. I/O mappings are not checked for failure before MMIO access in read/write operations.

Test signals: Successful slot reads should update `status`, `ext_status`, and `busstatus`; writes should complete without controller timeout. Polling tests should detect attention, presence, latch, and power-good transitions and update hotplug slot info. Fault tests should cover invalid commands, missing PCI controller `ctrl_dev`, I2C timeout/status errors, unsupported controller type, and module unload with the polling thread active.

# sources/distributed-fs/ceph-client/drivers/pci/hotplug/ibmphp_pci.c

Purpose: Performs legacy PCI configuration for cards inserted into IBM hotplug slots and removes those configurations on hot-removal. It probes functions behind a slot, rejects unsupported VGA and nested bridge cases, allocates BAR/window resources through the IBM PHP resource manager, programs PCI config space, and maintains per-slot `struct pci_func` chains for cleanup.

Important APIs and functions: Public APIs are `ibmphp_configure_card()` and `ibmphp_unconfigure_card()`. Key internal functions are `assign_alt_irq()`, `configure_device()`, `configure_bridge()`, `scan_behind_bridge()`, `unconfigure_boot_device()`, `unconfigure_boot_bridge()`, `unconfigure_boot_card()`, `add_new_bus()`, and `find_sec_number()`.

Control flow: `ibmphp_configure_card()` scans functions 0..7 at the slot device number, reads vendor/header/class data, rejects VGA and unsupported bridge types, configures ordinary devices via `configure_device()`, and configures PCI-to-PCI bridges via `configure_bridge()` before recursively configuring discovered downstream devices. `configure_device()` sizes BARs by writing all ones, allocates IO/MEM/PFMEM nodes with `ibmphp_check_resource()` and `ibmphp_add_resource()`, writes BAR starts, assigns interrupt line/cache/latency/command registers, and handles 64-bit BARs by zeroing the high dword. `configure_bridge()` allocates bridge BARs, chooses a secondary bus from EBDA slot topology, scans downstream devices for total window needs, allocates bridge windows, creates a new resource bus, writes bridge windows, and enables the bridge. Unconfiguration reads existing BAR/window state, finds matching resource nodes, removes resources/buses, and frees `pci_func` chains.

State and persistence: The file mutates PCI config space, `struct pci_func` linked lists hanging off a slot, `func->io[]`, `func->mem[]`, `func->pfmem[]`, `func->devices[]`, and global resource state managed by `ibmphp_res.c`. Programmed BARs, interrupt lines, bridge windows, and command bits persist in hardware until unconfigured, power-cycled, or overwritten.

Dependencies and integration points: Relies on `ibmphp_pci_bus`, PCI config accessors, EBDA slot/bus topology from `ibmphp_find_same_bus_num()`, resource APIs from `ibmphp_res.c`, and driver-specific constants/macros from `ibmphp.h`. Higher-level slot enable/disable code calls into this file after powering slots on or before powering them off.

Risks: This code reimplements PCI enumeration and resource assignment instead of using modern generic PCI core flows, so it is sensitive to BAR sizing side effects, multifunction header handling, and bridge-window alignment. `configure_bridge()` uses `PCI_DEVFN(func->function, func->device)` in one place, which is suspicious because other paths use `PCI_DEVFN(device, function)`. Nested bridges and VGA are deliberately unsupported. 64-bit memory resources are effectively truncated by zeroing upper dwords. Partial failure cleanup is narrow and may not undo all resources for multifunction or recursively configured devices.

Test signals: Hot-adding ordinary single-function, multifunction, and one-level PCI-to-PCI bridge cards should program BARs and command registers and populate resource lists. Removal should free matching resources and bus nodes. Negative signals include unsupported VGA, nested bridge rejection, insufficient IO/MEM/PFMEM windows, invalid secondary-bus allocation, BAR sizing failures, and reinsertion after previous bridge removal.

# sources/distributed-fs/ceph-client/drivers/pci/hotplug/ibmphp_res.c

Purpose: Maintains the IBM PHP driver's private PCI resource allocator. It converts EBDA POST resource descriptors into per-bus IO, memory, and prefetchable-memory ranges, tracks resources already consumed by devices, finds aligned holes for hot-added devices and bridges, and frees resources during hot-removal.

Important APIs and functions: Public APIs are `ibmphp_rsrc_init()`, `ibmphp_add_resource()`, `ibmphp_remove_resource()`, `ibmphp_check_resource()`, `ibmphp_remove_bus()`, `ibmphp_find_resource()`, `ibmphp_free_resources()`, `ibmphp_add_pfmem_from_mem()`, `ibmphp_find_res_bus()`, and `ibmphp_print_test()`. Internal helpers include `alloc_bus_range()`, `add_bus_range()`, `update_resources()`, `fix_resources()`, `find_range()`, `remove_ranges()`, `once_over()`, `range_exists_already()`, `update_bridge_ranges()`, and `find_bus_wprev()`.

Control flow: `ibmphp_rsrc_init()` walks `ibmphp_ebda_pci_rsrc_head`. Primary-bus descriptors create sorted range lists on `gbuses`; device descriptors create allocated resource nodes and insert them into the matching bus/type list, using temporary error buses and `rangeno = -1` when device records appear before range records. After EBDA import, `update_bridge_ranges()` scans existing PCI-to-PCI bridges to add secondary-bus windows missing from EBDA and mirror those bridge windows as resources on the parent bus. `once_over()` handles EBDA prefetchable allocations that actually came from memory ranges. At runtime, `ibmphp_check_resource()` finds the smallest aligned hole in the relevant bus range list, `ibmphp_add_resource()` inserts the allocation, and removal functions unlink and free matching nodes.

State and persistence: The private `gbuses` list persists all bus nodes, range nodes, resource nodes, and `firstPFMemFromMem` fallback nodes. Range numbering is persistent within each bus and is updated when ranges are inserted. The allocator state mirrors but does not own generic PCI core resources; it is freed by `ibmphp_free_resources()`.

Dependencies and integration points: Consumes EBDA resources produced by `ibmphp_ebda.c` and services allocation/removal calls from `ibmphp_pci.c`. Uses Linux list/slab/Pci config APIs and `ibmphp.h` resource masks and constants. It also reads live PCI bridge config registers while reconstructing windows for boot-time bridges.

Risks: This allocator is complex and pointer-heavy, with separate `next` and `nextRange` chains plus range numbers that must stay synchronized. Several cleanup paths free nodes without list reinitialization because teardown is assumed. `ibmphp_check_resource()` temporarily decrements `res->len` and restores it only on many return paths; future edits could easily introduce length corruption. Address math is 32-bit in many places, while bridge prefetchable upper 32 bits are conditionally folded only on 64-bit builds. Concurrency is not local to this file; callers must hold higher-level operation locks when mutating resources.

Test signals: Initialization should produce correct bus/range/resource dumps with no lingering `rangeno = -1`. Allocation tests should cover first resource on a bus, holes before/between/after existing nodes, bridge alignment requirements, PFMEM fallback to MEM, and multiple ranges. Removal tests should cover ordinary resources, PFMEM-from-MEM coupled removal, bridge bus removal, and module cleanup after partial initialization.
<!-- END_FILE_RESEARCH: sources/distributed-fs/ceph-client/drivers/pci/hotplug/ibmphp_res.c -->

# sources/distributed-fs/ceph-client/drivers/pci/hotplug/octep_hp.c

Purpose: Registers the Marvell/OCTEON PCI hotplug driver for a Cavium hotplug controller function. It treats the remaining functions on the same PCI bus/device group as hotplug slots, logically removes them during probe, and re-enables or disables them in response to MSI-X command interrupts or sysfs hotplug operations.

Important APIs and types: Main types are `enum octep_hp_intr_type`, `struct octep_hp_cmd`, `struct octep_hp_slot`, `struct octep_hp_intr_info`, and `struct octep_hp_controller`. Key functions include `octep_hp_controller_setup()`, `octep_hp_pci_probe()`, `octep_hp_register_slot()`, `octep_hp_deregister_slot()`, `octep_hp_enable_pdev()`, `octep_hp_disable_pdev()`, interrupt helpers `octep_hp_request_irq()`, `octep_hp_intr_handler()`, `octep_hp_work_handler()`, and hotplug-slot ops `octep_hp_enable_slot()`/`octep_hp_disable_slot()`.

Control flow: Probe allocates a managed controller, enables and maps BAR 0, initializes locks/lists/work, allocates MSI-X vectors up to the enable/disable hotplug vector indexes, requests IRQs, then iterates sibling devices on the bus. Each sibling becomes a `hotplug_slot` named `octep_hp_N`, is registered through `pci_hp_register()`, linked to `slot_list`, and immediately disabled with `pci_stop_and_remove_bus_device_locked()`. Hardware interrupts read and clear a 64-bit slot mask from a type-specific MMIO register, queue an `octep_hp_cmd` under a spinlock, and schedule work. Workqueue context processes all queued commands and toggles matching slots.

State and persistence: `struct octep_hp_controller` persists mapped MMIO base, controller PCI device, interrupt metadata, registered slot list, command queue, and locks. Each slot persists its slot number, original devfn, optional active `hp_pdev`, and hotplug core object. Disabled devices are removed from the PCI bus and rescanned on enable; registered slots persist until devm cleanup deregisters them and re-enables devices.

Dependencies and integration points: Depends on PCI managed resource APIs, MSI-X, MMIO `readq()`/`writeq()`, generic PCI scanning/resource assignment/removal helpers, workqueues, hotplug core registration, and devm cleanup actions. It binds `PCI_VENDOR_ID_CAVIUM` device `0xa0e3`.

Risks: `octep_hp_enable_pdev()` assumes `pci_scan_single_device()` succeeds and then dereferences `hp_slot->hp_pdev` in `pci_bus_add_device()` and logging, so failed scan can crash. Probe registers all other devices on the bus, not just same-slot functions, which depends on the platform topology promised in the comments. Slot command masks use `BIT(slot_number)` with a `u64` interrupt value but `BIT()` is word-sized on some architectures; `BIT_ULL()` would better match the data width. IRQ cleanup flushes work after freeing vectors, but queued commands are only freed by the work handler.

Test signals: Binding to `177d:a0e3`, BAR mapping, MSI-X allocation/request, creation of `octep_hp_*` slots, initial logical removal of slot functions, interrupt-driven enable/disable masks, sysfs `power` toggles, and cleanup re-enabling devices are core signals. Fault tests should cover failed scan on enable, no sibling devices, malformed interrupt vector, command allocation failure in IRQ context, and repeated enable/disable idempotence.

# sources/distributed-fs/ceph-client/drivers/pci/hotplug/pci_hotplug_core.c

Purpose: Provides the generic PCI hotplug core interface for hotplug controller drivers. It initializes and publishes `struct hotplug_slot` objects as `struct pci_slot` sysfs entries, creates optional hotplug attributes based on driver ops, dispatches sysfs reads/writes to controller callbacks, and exposes helpers to bracket intentionally spurious link changes.

Important APIs and functions: Exported APIs include `__pci_hp_register()`, `__pci_hp_initialize()`, `pci_hp_add()`, `pci_hp_deregister()`, `pci_hp_del()`, `pci_hp_destroy()`, `pci_hp_ignore_link_change()`, `pci_hp_unignore_link_change()`, and `pci_hp_spurious_link_change()`. Internal sysfs functions include `power_read_file()`, `power_write_file()`, `attention_read_file()`, `attention_write_file()`, `latch_read_file()`, `presence_read_file()`, `test_write_file()`, feature predicates `has_*_file()`, and `fs_add_slot()`/`fs_remove_slot()`.

Control flow: Drivers call `pci_hp_register()` or the split `pci_hp_initialize()` plus `pci_hp_add()` flow. Initialization validates the slot and ops, stores owner/module name, creates or references a `pci_slot`, and links the hotplug slot to it. Add creates the module symlink and optional `power`, `attention`, `latch`, `adapter`, and `test` sysfs files, then emits a `KOBJ_ADD` uevent. Sysfs writes parse numeric values and call driver callbacks such as `enable_slot`, `disable_slot`, `set_attention_status`, and `hardware_test`. Deregistration removes sysfs files and destroys the PCI slot reference. Link-change helpers set bits in `pdev->priv_flags` and coordinate with a waitqueue so hotplug drivers can ignore changes caused by resets, D3cold, firmware updates, or FPGA reconfiguration.

State and persistence: Persistent state is mostly attached to `struct hotplug_slot` and `struct pci_slot`; this file keeps only the `debug` module parameter and `pci_hp_link_change_wq`. Sysfs files persist while a slot is published. `PCI_LINK_CHANGING` and `PCI_LINK_CHANGED` bits persist in the bridge device private flags until cleared by `pci_hp_spurious_link_change()`.

Dependencies and integration points: Used by pciehp, IBM PHP, OCTEON hotplug, CompactPCI, and other hotplug drivers through `<linux/pci_hotplug.h>`. Integrates with PCI slot core (`pci_create_slot()`/`pci_destroy_slot()`), kobject/sysfs/module infrastructure, waitqueues, and `cpci_hotplug_init()` at device init time.

Risks: Sysfs write parsing uses `simple_strtoul()` and masks to narrow integer types, so malformed trailing text is not rejected. Hotplug callbacks are invoked directly from sysfs context and must handle their own locking and runtime power. `fs_add_slot()` cleanup removes the module symlink unconditionally on some error exits even if it was never created, which is generally harmless but assumes sysfs remove tolerance. The link-change bracketing protocol depends on callers pairing ignore/unignore and hotplug drivers performing their own sanity checks afterward.

Test signals: Slot registration should create the expected sysfs files only for implemented ops and emit uevents. `power` writes should call enable/disable callbacks and reject values other than 0/1. Attention, latch, adapter, and test attributes should reflect callback availability. Link-change tests should verify wait behavior while `PCI_LINK_CHANGING` is set and one-shot true return from `pci_hp_spurious_link_change()` after unignore.

# sources/distributed-fs/ceph-client/drivers/pci/hotplug/pciehp.h

Purpose: Defines the shared private interface and controller state for the PCI Express hotplug driver. It centralizes the controller data structure, state machine constants, request flags, capability predicates, logging helpers, and function prototypes shared by `pciehp_core.c`, `pciehp_ctrl.c`, `pciehp_hpc.c`, and PCIe hotplug PCI configuration code.

Important APIs and types: The key type is `struct controller`, which owns the PCIe port service pointer, cached Device Serial Number, slot capability/control state, command-completion synchronization, pending events, notification/polling state, state machine fields, delayed attention-button work, hotplug core object, reset lock, and requester waitqueue. Important constants are `OFF_STATE`, `BLINKINGON_STATE`, `BLINKINGOFF_STATE`, `POWERON_STATE`, `POWEROFF_STATE`, `ON_STATE`, `DISABLE_SLOT`, and `RERUN_ISR`. Capability helpers include `ATTN_BUTTN()`, `POWER_CTRL()`, `MRL_SENS()`, `ATTN_LED()`, `PWR_LED()`, `NO_CMD_CMPL()`, and `PSN()`.

Control flow: The header has no executable flow beyond inline accessors `slot_name()` and `to_ctrl()`. It defines the control contract: core probe initializes `struct controller`, HPC code handles slot-control/register access and interrupts, ctrl code consumes pending events and transitions state, and config code enumerates or removes downstream PCI devices.

State and persistence: `struct controller` is the persistent state container for one PCIe hotplug slot. It caches slot registers, tracks command-completion timing, stores event bits across IRQ top/bottom halves, records whether notifications are enabled, and serializes state transitions through `state_lock` and `reset_lock`.

Dependencies and integration points: Includes Linux PCI, hotplug, mutex, rwsem, delay, and workqueue APIs plus PCIe port service definitions. The prototypes connect core lifecycle (`pcie_init()`, `pciehp_release_ctrl()`), notification (`pcie_init_notification()`), hardware operations (`pciehp_power_on_slot()`), event handling (`pciehp_handle_presence_or_link_change()`), sysfs entry points, and reset support.

Risks: State constants and request flags are shared across multiple C files, so changing values requires auditing IRQ event encoding and state-machine transitions. `DISABLE_SLOT` and `RERUN_ISR` deliberately live above the 16-bit Slot Status event width; new flags must preserve that separation. `struct controller` lock fields have documented responsibilities, and violating those lock boundaries can race sysfs, IRQ thread, PM, and reset paths.

Test signals: Compile coverage of all pciehp objects validates declarations. Runtime signals include one controller per hotplug-capable port, correct sysfs slot naming from `PSN()`, valid transitions among the six states, command completion waits waking through `queue`, requester waits waking after sysfs operations, and reset paths honoring `reset_lock`.

# sources/distributed-fs/ceph-client/drivers/pci/hotplug/pciehp_core.c

Purpose: Registers PCIe hotplug as a PCIe port service driver and bridges the generic PCI hotplug core sysfs interface to PCIe hotplug controller operations. It handles service probe/remove, slot initialization/publication, runtime and system PM interrupt handling, and presence reconciliation after probe or resume.

Important APIs and functions: Public module init entry is `pcie_hp_init()`. Key internal functions are `init_slot()`, `cleanup_slot()`, sysfs callback adapters `set_attention_status()`, `get_power_status()`, `get_latch_status()`, `get_adapter_status()`, `pciehp_check_presence()`, service callbacks `pciehp_probe()`/`pciehp_remove()`, PM helpers `pme_is_native()`, `pciehp_disable_interrupt()`, `pciehp_suspend()`, `pciehp_resume_noirq()`, `pciehp_resume()`, `pciehp_runtime_suspend()`, and `pciehp_runtime_resume()`.

Control flow: `pcie_hp_init()` registers `hpdriver_portdrv` for `PCIE_PORT_SERVICE_HP`. Probe rejects non-hotplug services or bridges without subordinate buses, allocates/initializes a controller via `pcie_init()`, initializes a hotplug slot and operations, enables notifications via `pcie_init_notification()`, publishes the slot with `pci_hp_add()`, then calls `pciehp_check_presence()` to synthesize a presence-change event if hardware and state disagree. Remove unpublishes the slot, shuts down notifications, destroys slot resources, and releases the controller. PM paths disable interrupts before suspend/runtime suspend, restore command-busy bookkeeping after config restore, clear stale hotplug events, detect device replacement across sleep, and re-enable interrupts/rescan presence on resume.

State and persistence: Exports module parameters `pciehp_poll_mode` and `pciehp_poll_time`. Per-controller state lives in `struct controller`: hotplug ops, state machine, cached command state, pending events, Device Serial Number, and notification status. Sysfs slot objects persist from successful `pci_hp_add()` until remove.

Dependencies and integration points: Uses PCIe port service registration, generic PCI hotplug core, controller/HPC functions from `pciehp_hpc.c`, state machine functions from `pciehp_ctrl.c`, runtime PM config access wrappers, PCI bus walking, and host bridge native PME policy. It integrates with the PCIe port bus, not direct PCI device driver matching.

Risks: Probe unwind must balance controller allocation, slot initialization, notification setup, and publication; future edits need to preserve that order. Resume paths deliberately synthesize events and mark old devices disconnected when DSN changes, which can surprise drivers if replacement detection is wrong. Sysfs status callbacks runtime-resume the port around config reads/writes and rely on lower layers to tolerate inaccessible hardware. Poll mode behavior depends on module parameters that retain bootarg compatibility.

Test signals: Hotplug-capable port probe should produce one `/sys/bus/pci/slots/<PSN>` entry, working `power` and status files, and immediate enable for an occupied slot. PM tests should cover system suspend/resume with unchanged, removed, and replaced devices; runtime suspend/resume; native versus non-native PME; and polling mode. Removal should leave no sysfs slot or IRQ/poll resources.

# sources/distributed-fs/ceph-client/drivers/pci/hotplug/pciehp_ctrl.c

Purpose: Implements the PCIe hotplug state machine for attention-button, sysfs, presence, and data-link events. It powers slots on/off, configures or unconfigures downstream devices, controls indicators, handles safe versus surprise removal, and coordinates synchronous sysfs requests with the IRQ thread.

Important APIs and functions: Public event handlers are `pciehp_request()`, `pciehp_queue_pushbutton_work()`, `pciehp_handle_button_press()`, `pciehp_handle_disable_request()`, `pciehp_handle_presence_or_link_change()`, `pciehp_sysfs_enable_slot()`, and `pciehp_sysfs_disable_slot()`. Internal helpers include `set_slot_off()`, `board_added()`, `remove_board()`, `__pciehp_enable_slot()`, `pciehp_enable_slot()`, `__pciehp_disable_slot()`, and `pciehp_disable_slot()`.

Control flow: IRQ/HPC code calls `pciehp_request()` to OR event/action bits into `pending_events` and wake the IRQ thread. Attention-button events toggle between stable states and five-second blinking states, scheduling or canceling `button_work`. Delayed button work translates blinking-on to a synthetic presence-change request and blinking-off to `DISABLE_SLOT`. Presence/link change handling first powers off and unconfigures an already-on slot because the device identity cannot be trusted after link/presence changes, then rechecks presence/link and powers on/configures if occupied. Sysfs enable/disable requests submit events to the IRQ thread and wait on `requester` until pending work and interrupt-thread execution complete.

State and persistence: Mutates `ctrl->state`, `ctrl->pending_events`, `ctrl->request_result`, indicator state, slot power, downstream PCI device enumeration, and hardware LBMS indications. `state_lock` serializes state transitions and delayed-work cancellation. Runtime PM references keep the port accessible while enabling/disabling slots.

Dependencies and integration points: Calls hardware helpers from `pciehp_hpc.c` for power, indicators, latch, presence, link, and power-fault status. Calls `pciehp_configure_device()` and `pciehp_unconfigure_device()` for downstream PCI enumeration/removal, generic PM runtime APIs, tracepoints, and PCI link-bandwidth reset helper. It is invoked by the IRQ thread/polling code and by hotplug core sysfs callbacks installed in `pciehp_core.c`.

Risks: Correctness depends on careful state-lock coverage around delayed work, sysfs waiters, and IRQ-thread actions. Presence/link handling intentionally removes a slot before deciding whether to re-add because same-card identity cannot be assumed; changing that would risk driver access to replaced hardware. `__pciehp_disable_slot()` returns `-EINVAL` when already powered off, which sysfs callers surface as failure even though the end state is off. If IRQ thread wakeups are lost, sysfs enable/disable can wait until `pending_events` and `ist_running` clear. Indicator updates must remain balanced on failure paths so user-visible LEDs match state.

Test signals: Exercise attention-button press, cancel within five seconds, delayed power-on/off, sysfs `power` writes, safe removal, surprise removal on DLLSC/PDC, failed link training, power fault, already-enabled/disabled cases, and PM-runtime suspended ports. Tracepoints `PCI_HOTPLUG_CARD_PRESENT`, `CARD_NOT_PRESENT`, `LINK_UP`, and `LINK_DOWN` plus final `ctrl->state` values provide strong validation.
