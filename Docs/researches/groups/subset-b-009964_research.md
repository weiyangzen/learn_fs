# sources/user-network-fs/samba/source4/torture/basic/delaywrite.c

Purpose: implements the `delaywrite` Samba torture suite for SMB1 last-write-time behavior. It exercises when servers should update file or directory write timestamps immediately, when an explicit `SET_FILE_BASIC_INFO` write time becomes sticky, how path info and handle info should agree, and how close, flush, truncation, allocation changes, two-handle access, and two-connection access affect timestamps.

Important APIs and types: the exported suite factory is `torture_delay_write(TALLOC_CTX *ctx)`. It registers `test_finfo_after_write`, `test_delayed_write_update`, `test_delayed_write_update1`, `1a`, `1b`, `1c`, `2`, `3`, `3a`, `3b`, `3c`, `4`, `5`, `5b`, `6`, `7`, `test_directory_update8`, and `test_modern_write_time1`. The tests use `struct torture_context`, `struct smbcli_state`, `union smb_fileinfo`, `union smb_setfileinfo`, `union smb_open`, `union smb_flush`, `NTSTATUS`, `NTTIME`, and talloc contexts. Important SMB client calls include `torture_setup_dir`, `smbcli_open`, `smbcli_nt_create_full` indirectly through raw open, `smbcli_write`, `smbcli_smbwrite`, `smbcli_ftruncate`, `smb_raw_fileinfo`, `smb_raw_pathinfo`, `smb_raw_setfileinfo`, `smb_raw_open`, `smb_raw_flush`, `smbcli_close`, `smbcli_unlink`, and `smbcli_deltree`.

Local helper macros define the recurring assertions and state transitions. `COMPARE_WRITE_TIME_CMP` compares write times with optional strict mode and a one-second-rounded fallback for filesystems with coarse timestamp resolution. `COMPARE_ACCESS_TIME_CMP`, `COMPARE_BOTH_TIMES_EQUAL`, `GET_INFO_FILE`, `GET_INFO_FILE2`, `GET_INFO_FILE_EX`, `GET_INFO_PATH`, `GET_INFO_PATH_EX`, `GET_INFO_BOTH`, and `GET_INFO_BOTH_EX` combine raw queries with failure handling and log comments. `SET_INFO_FILE_EX`, `SET_INFO_FILE`, and `SET_INFO_FILE_NS` issue `RAW_SFILEINFO_BASIC_INFO` updates and model explicit sticky write times, including a nanosecond offset for timestamp-resolution checks.

Control flow: every test creates or reuses `BASEDIR` (`\\delaywrite`), opens one or two SMB handles, captures initial `RAW_FILEINFO_BASIC_INFO` or `RAW_FILEINFO_ALL_INFO`, performs writes or metadata changes, then repeatedly compares the returned handle/path timestamps. Sleep calls via `smb_msleep` deliberately step around filesystem timestamp granularity and the configurable `writetimeupdatedelay` torture setting. Normal completion closes handles and removes test files and `BASEDIR`; most failure paths jump to `done` cleanup or return through `torture_assert` failure.

The early tests focus on immediate update semantics. `test_delayed_write_update` verifies a simple one-byte write changes `write_time`. `test_delayed_write_update1` verifies zero-length `SMBwrite` truncation to 1024 updates immediately, a subsequent non-zero `SMBwrite` updates within the expected delay window, and close does not change the final write time. `1a`, `1b`, and `1c` cover expansion/truncation through zero-length `SMBwrite`, `SET_END_OF_FILE_INFO`, and `SET_ALLOCATION_INFO`, including size assertions. `test_finfo_after_write` checks a two-connection pattern used to catch stale path-info cache behavior after write, with create/write/change time expectations.

The two-handle and explicit timestamp tests model Samba/Windows compatibility behavior. `test_delayed_write_update2` sets a write time with `smb_raw_setfileinfo`, verifies that writes through the same handle and flush do not disturb the explicit time, then checks how another handle and later reopen lose or bypass that stickiness. `test_delayed_write_update3`, `3a`, `3b`, `3c`, and `4` stress repeated normal writes and truncate writes, asserting immediate timestamp progression during writes and no extra timestamp update on close. `test_delayed_write_update5` and `5b` show that once an explicit write time is set, later normal writes, truncate writes, delayed updates, and close should not advance it. `test_delayed_write_update6` repeats the explicit-time behavior across two connections and keeps the second handle open across a rerun to confirm sticky state remains attached to the correct open context.

The later tests cover precision and modern semantics. `test_delayed_write_update7` sets a future write time with a non-zero millisecond component, requires `qfileinfo` and `qpathinfo` to agree before close, then reopens and checks the create/open response preserves the precise write time. `test_directory_update8` opens a directory handle, creates a file inside it, and requires the directory write time to increase while the directory handle remains open. `test_modern_write_time1` is a documented timeline over two handles: writes initially update all views, an explicit sticky time is visible from both handles and path queries, a write on the sticky handle preserves it, a write from the other handle reverts to a normal current write time, another write from the original handle does not advance it again, and close does not mutate it.

State and persistence behavior: all persistent side effects are remote SMB filesystem state under `\\delaywrite`. File contents are incidental; the suite primarily observes file size, access time, write time, change time, attributes, and handle/path consistency. Explicit write-time state is expected to behave like server-side open-handle state rather than a local variable. The code uses talloc only for test memory and open-request memory; outputs are not retained beyond each test. Cleanup removes individual files and the base directory, but early assertion exits can rely on the torture harness or subsequent setup to clean stale remote state.

Dependencies and integration points: this file sits in `source4/torture/basic` and is exposed through `torture/basic/proto.h`. It depends on Samba raw SMB1 client plumbing from `libcli/raw`, higher-level `smbcli_*` helpers, `torture/util.h`, `system/time.h`, and `system/filesys.h`. The suite registration uses `torture_suite_add_1smb_test` for single-connection cases and `torture_suite_add_2smb_test` for two-connection cases, so test execution depends on the torture framework provisioning one or two connected SMB clients. The `writetimeupdatedelay` setting scales waits and is central to runtime behavior on slow or delayed-write servers.

Risks: the suite is timing-sensitive and can be flaky on filesystems with low timestamp resolution, slow servers, or unusual write-back policies; the macros mitigate this by rounding timestamps unless `strict mode` is enabled. Several tests use loops bounded by scaled seconds and can be expensive. Some comments disagree with current assertion text in places, so maintainers should trust the active assertions over old commentary. Because the code intentionally probes Windows-compatible edge cases, changing server timestamp caching, open-handle metadata propagation, or explicit write-time semantics can break many tests at once.

Test signals: failures identify concrete protocol regressions: unchanged write time after write/truncate, write time changed by close, path info diverging from file info, sticky write time ignored, sticky write time not cleared by another handle write, timestamp precision loss after close/reopen, directory write time not updated on child creation, or delayed update happening after an explicit set. The strongest integration signal is that both handle-based and path-based metadata queries must agree across one- and two-connection paths at each documented stage.

# sources/user-network-fs/samba/source4/torture/basic/delete.c

Purpose: implements the `delete` Samba torture suite for SMB delete-on-close semantics. It verifies file and directory deletion behavior across initial `NTCREATEX_OPTIONS_DELETE_ON_CLOSE`, later `smbcli_nt_delete_on_close` calls, delete access rights, share-delete compatibility, readonly attributes, multiple open handles, connection death, rename, non-empty directories, and expected NTSTATUS values.

Important APIs and types: the exported suite factory is `torture_test_delete(TALLOC_CTX *ctx)`. It registers `deltest1` through `deltest25a`, with `deltest21`, `deltest22`, and `deltest24` as simple tests that open their own connections. Key helpers are `check_delete_on_close`, `del_clean_area`, and `CHECK_STATUS`. The file uses `struct torture_context`, `struct smbcli_state`, `union smb_search_data`, `union smb_fileinfo`, `union smb_setfileinfo`, `NTSTATUS`, security masks such as `SEC_RIGHTS_FILE_ALL`, `SEC_STD_DELETE`, `SEC_FILE_READ_DATA`, create dispositions such as `NTCREATEX_DISP_CREATE` and `NTCREATEX_DISP_OPEN`, share flags including `NTCREATEX_SHARE_ACCESS_DELETE`, and create options including `NTCREATEX_OPTIONS_DELETE_ON_CLOSE` and `NTCREATEX_OPTIONS_DIRECTORY`.

The core operations are `smbcli_nt_create_full`, `smbcli_nt_delete_on_close`, `smbcli_close`, `smbcli_open`, `smbcli_unlink`, `smbcli_deltree`, `smbcli_setatr`, `smbcli_getatr`, `smbcli_mkdir`, `smbcli_rename`, `smb_raw_setfileinfo`, `smb_raw_fileinfo`, `smb_raw_exit`, `smbcli_transport_dead`, `torture_single_search`, and `torture_open_connection`. `check_delete_on_close` is the main verifier: it searches the path, optionally queries `RAW_FILEINFO_ALL_INFO` and `RAW_FILEINFO_STANDARD_INFO` by handle, checks `delete_pending` and `nlink`, then expects `smbcli_qpathinfo` to succeed normally or fail with `NT_STATUS_DELETE_PENDING` depending on the requested state.

Control flow: most tests start with `del_clean_area(cli1, cli2)`, which sends raw exit on both sessions and removes `\\delete.dir`, `\\delete.file`, and `\\delete.new` after clearing file attributes. Each `deltest*` then constructs a specific open/delete/close scenario, checks return handles or NTSTATUS values, and confirms final path existence or deletion. The suite uses two connected SMB clients for most scenarios to distinguish same-session and cross-session behavior, while the simple tests create fresh connections to simulate transport death or single-connection directory-handle behavior.

Basic file cases cover direct deletion and access validation. `deltest1`, `2`, `3`, `4`, `7`, `8`, `10`, and `13` cover delete-on-close at open time or set after open, including share-delete requirements, multiple handles, clearing the flag, and global visibility of `delete_pending`. `deltest5` ensures `smbcli_nt_delete_on_close` cannot be applied to a legacy `OpenX` handle. `deltest6`, `9`, and `9a` verify DELETE access is required and missing access fails with `NT_STATUS_INVALID_PARAMETER` without creating or deleting the target. `deltest11` and `12` verify readonly files reject delete-on-close with `NT_STATUS_CANNOT_DELETE`.

Multi-handle propagation is the largest risk area. `deltest16`, `16a`, and `17` through `17f` encode subtle Windows-observed rules around initial delete-on-close, later opens, which close causes pending-delete state to become visible, whether subsequent opens clear or inherit the state, and whether clearing delete-on-close on one handle affects remaining handles. These tests repeatedly assert when `delete_pending` should be false while the initial delete-on-close handle is still open, when closing that handle should make other handles report pending delete, when new opens should fail with `NT_STATUS_DELETE_PENDING`, and when final close should produce `NT_STATUS_OBJECT_NAME_NOT_FOUND`.

Rename and unlink semantics are explicitly tested. `deltest15` renames an open file to `\\delete.new`, marks the renamed handle delete-on-close, verifies the old and new names have different pending-delete state, recreates `\\delete.file`, and confirms the renamed path is deleted while the recreated original remains. `deltest20b` models the CIFS client behavior of opening a file, opening another delete-on-close handle, renaming by handle with `RAW_SFILEINFO_RENAME_INFORMATION`, and expecting the renamed file to disappear after all handles close.

Directory behavior is covered separately because it differs from ordinary files. `deltest14`, `18`, `19`, `22`, and `23` cover empty directory delete-on-close, delayed pending-delete visibility with a second directory handle, and second directory opens failing with `NT_STATUS_DELETE_PENDING` once deletion is pending. `deltest20` marks an empty directory delete-pending, verifies child creation is blocked with `NT_STATUS_DELETE_PENDING`, clears the flag, creates a child, then verifies setting delete-on-close on a non-empty directory fails with `NT_STATUS_DIRECTORY_NOT_EMPTY`. It skips when running as root. `deltest20c` confirms that opening a non-empty directory with delete-on-close and closing it leaves the directory present. `deltest25` and `25a` repeat the invalid-parameter access checks for directories.

Connection and close edge cases are also represented. `deltest21` sets delete-on-close, forcibly marks the transport dead via `smbcli_transport_dead`, reopens a connection, waits briefly, and expects the file to have been removed. `deltest24` verifies that trying to unset delete-on-close before closing a handle that was created with initial delete-on-close does not prevent deletion. These cases tie delete-on-close behavior to session teardown and create-option semantics rather than only clean `smbcli_close`.

State and persistence behavior: persistent remote state is limited to `\\delete.file`, `\\delete.new`, and `\\delete.dir`. The suite intentionally manipulates server-side open-handle state, delete-pending state, link counts, attributes, and namespace entries. It uses `nlink` expectations of `0` when delete is pending and `1` otherwise in `check_delete_on_close`. Local state is just integer fnums, booleans, and status values. Cleanup is defensive because many scenarios leave paths pending or readonly.

Dependencies and integration points: this file depends on `libcli/libcli.h`, `libcli/raw/raw_proto.h`, `torture/util.h`, `torture/raw/proto.h`, and `torture/basic/proto.h`. It integrates with the Samba torture suite registry through `torture_suite_add_2smb_test` and `torture_suite_add_simple_test`. It also depends on raw search and qfileinfo behavior accurately exposing `delete_pending`, `nlink`, and path-status transitions, so it tests both SMB server semantics and client library status propagation.

Risks: delete-on-close rules are highly compatibility-sensitive and vary by object type, create disposition, and server version; several comments document Windows version differences. Tests can leave files pending delete if a failure aborts before final close, so `del_clean_area` is important. Some tests check transport error state using `CHECK_STATUS`, which reads the last transport NTSTATUS and can be affected by an unexpected intervening call. The suite also assumes the backing server can report link count and delete-pending state through the raw info levels used by `check_delete_on_close`.

Test signals: expected failures include `NT_STATUS_DELETE_PENDING`, `NT_STATUS_OBJECT_NAME_NOT_FOUND`, `NT_STATUS_INVALID_PARAMETER`, `NT_STATUS_CANNOT_DELETE`, and `NT_STATUS_DIRECTORY_NOT_EMPTY` in specific scenarios. Behavioral regressions show up as successful opens while delete is pending, missing deletion after final close or socket death, deletion despite clearing a permitted flag, path info succeeding when delete-pending should hide the path, invalid create attempts leaving objects behind, or directory delete-on-close ignoring non-empty protection.
