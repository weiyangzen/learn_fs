# sources/distributed-fs/moosefs/mfsmaster/appendres.c

## Purpose
This module tracks temporary append reservations by inode. It records a virtual length for an inode while append work is outstanding and removes the reservation once real length catches up or the reservation is explicitly cleared.

## Important APIs And Types
`appendreservation` stores `inode`, `vlength`, and a next pointer. `appendreshash[1024]` is a fixed-size separate-chaining hash table keyed by `inode % 1024`. Public functions are `appendres_getvleng`, `appendres_setvleng`, `appendres_setrleng`, `appendres_clear`, `appendres_cleanall`, and `appendres_init`.

## Control Flow
`appendres_setvleng` updates an existing entry or allocates and prepends a new reservation. `appendres_getvleng` scans the bucket and returns zero when no reservation exists. `appendres_setrleng` removes an entry when the supplied real length is greater than or equal to the reserved virtual length. `appendres_clear` removes one inode unconditionally. `appendres_cleanall` walks every bucket and frees all nodes. `appendres_init` zeroes all buckets.

## State And Persistence Behavior
All state is in-memory only and is not serialized. The table is initialized during filesystem initialization and is likely rebuilt from live append operations rather than metadata restore. Memory ownership is direct `malloc`/`free`; no allocator wrapper or failure check is used here.

## Dependencies And Integration Points
The header is consumed by `filesystem.c`; observed callers include `appendres_setvleng(inode,length)` and `appendres_init()`. This module has no locking, so it assumes the mfsmaster event loop's single-threaded metadata mutation model.

## Risks
`malloc` failure is unchecked in `appendres_setvleng`. A virtual length of zero is indistinguishable from no reservation to callers of `appendres_getvleng`. Hash collisions produce linear scans; large numbers of concurrent append reservations can degrade performance. If callers forget `appendres_clear` or never advance real length, reservations persist until `appendres_cleanall`.

## Test Signals
Useful tests cover insert/update/get, removal when `rlength >= vlength`, non-removal when `rlength < vlength`, explicit clear, `cleanall`, and collision behavior with inodes separated by 1024.

# sources/distributed-fs/moosefs/mfsmaster/bgsaver.c

## Purpose
`bgsaver.c` isolates slow disk work from the main master process. A forked background data writer receives packets over pipes, writes `metadata_download.tmp`, appends and rotates `changelog.0.mfs`, acknowledges changelog progress, and emits heartbeat packets. The parent side queues commands and integrates with the main poll/time/reload/shutdown hooks.

## Important APIs And Types
Commands include `BGSAVER_START`, `BGSAVER_WRITE`, `BGSAVER_FINISH`, `BGSAVER_CHANGELOG`, `BGSAVER_ROTATELOG`, `BGSAVER_TERMINATE`, status `BGSAVER_DONE`, changelog ack/nack, and alive. `bgsaverconn` owns data and status pipes, parse state, input/output queues, callback userdata, and mode (`FREE`, `DATA`, `KILL`). `out_packetstruct` and `in_packetstruct` represent queued packets. Public functions are `bgsaver_cancel`, `bgsaver_open`, `bgsaver_store`, `bgsaver_close`, `bgsaver_changelog`, `bgsaver_rotatelog`, and `bgsaver_init`.

## Control Flow
`bgsaver_init` creates `.bgwriter.lock`, verifies no writer is active, builds nonblocking pipes, forks, redirects child stdio to `/dev/null`, and registers parent hooks. The child `bgsaver_worker` locks `.bgwriter.lock`, polls the data pipe, reads framed packets, performs file/changelog work, and writes framed status packets. The parent creates command packets with `bgsaver_createpacket`, flushes them from `bgsaver_write`, reads status bytes in `bgsaver_read`, dispatches in `bgsaver_parse`, and kills the connection on malformed packets, pipe errors, or missing heartbeats.

## State And Persistence Behavior
Persistent files are `.bgwriter.lock`, `metadata_download.tmp`, `changelog.0.mfs`, and rotated `changelog.N.mfs` files. Metadata download writes are offset-based and CRC-checked per chunk, then `fsync`ed on finish. Changelog writes are appended, optionally rotated according to `BACK_LOGS`, and acked with timestamps. Parent process state includes pending packets, last activity timing, termination delay, and `BackLogsNumber`.

## Dependencies And Integration Points
The module uses `datapack` framing helpers, `crc`, `cfg`, `main` event registration, `mfslog`, `massert`, `sockets` nonblocking helpers, `mfsalloc`, `processname`, and `clocks`. `changelog.c` uses `bgsaver_changelog` and `bgsaver_rotatelog` in background save mode. `init.h` registers `bgsaver_init` before the changelog module.

## Risks
Only one outstanding callback pair is stored in `bgsaverconn`, so overlapping metadata write operations rely on serialized caller behavior. Some child allocations use raw `malloc` and can exit the child on failure. Changelog NACK calls `main_exit`, making write failures fatal. `bgsaver_cancel` queues `BGSAVER_FINISH`, not `BGSAVER_TERMINATE`, so its semantics depend on the current protocol state. File paths are fixed relative to the process working directory.

## Test Signals
Test through an integration run that starts the master, performs metadata download chunks with valid and invalid CRCs, rotates logs with different `BACK_LOGS`, simulates child death or pipe HUP, and verifies `main_exit` on changelog NACK. Unit-level checks can exercise packet parsing with partial reads and oversized status lengths.

# sources/distributed-fs/moosefs/mfsmaster/bio.c

## Purpose
`bio.c` provides a buffered I/O abstraction for metadata save/load paths and socket transfers. It supports file, socket, and null backends with read/write direction, buffering, file-position accounting, EOF/error tracking, and write-side CRC accumulation.

## Important APIs And Types
`struct _bio` stores buffer pointers, buffer size and positions, socket timeout, file position, CRC, direction, backend type, error/EOF state, last errno, and descriptor. Openers are `bio_null_open`, `bio_file_open`, and `bio_socket_open`. Core operations are `bio_read`, `bio_write`, `bio_seek`, `bio_skip`, `bio_sync`, `bio_shutdown`, `bio_wait`, and `bio_close`; accessors expose file position, size, CRC, EOF, error, errno, and descriptor.

## Control Flow
Writes accumulate into the buffer until flush, or bypass buffering for writes at least as large as the buffer. Reads fill the buffer and satisfy small reads from it, or copy buffered leftovers and then read large chunks directly. Direct large operations are split at `0x40000000` bytes. File seeks flush write buffers or discard read buffers before `lseek`. Socket operations delegate to MooseFS TCP helpers with timeouts.

## State And Persistence Behavior
File backends open with `O_RDONLY` or `O_WRONLY|O_CREAT|O_TRUNC` and close the descriptor in `bio_close`. Write-side CRC is XORed with `mycrc32(0, src, len)` for every `bio_write`; `bio_crc` returns and resets it for write handles. `fileposition` tracks descriptor-level movement and is adjusted for buffered read/write data when reported.

## Dependencies And Integration Points
The module depends on `massert`, `sockets`, `strerr`, and `crc`. Callers across metadata modules include `metadata.c`, `csdb.c`, `patterns.c`, `openfiles.c`, `xattr.c`, `posixacl.c`, and `posixlocks.c`; it is the common persistence I/O layer for many mfsmaster metadata sections.

## Risks
`bio_flush` does not check whether a partial internal write actually wrote the whole buffer before clearing `leng`; the internal writer sets an error, but data may already be lost from the buffer. `bio_write` computes CRC before backend success is known, so CRC can include failed writes. Null read always returns EOF-like zero, while null write records CRC. Buffer size zero would break assumptions; callers should pass nonzero sizes.

## Test Signals
Tests should cover file round trips with small and large buffers, direct large read/write paths, partial socket failures, CRC reset behavior, seek after buffered reads and writes, skip for file and socket backends, and error propagation from forced short writes.

# sources/distributed-fs/moosefs/mfsmaster/changelog.c

## Purpose
`changelog.c` is the master metadata-change logger. It increments metadata versions, formats change records, writes them to durable changelog storage, broadcasts records to metadata-log clients, and keeps bounded in-memory old-change blocks for delayed receivers and metadata sending.

## Important APIs And Types
`old_changes_entry` stores a version, length, and copied log data. `old_changes_block` stores up to 5000 entries plus aggregate size, minimum timestamp/version, and next pointer. Public operations include `changelog`, `changelog_mr`, `changelog_rotate`, `changelog_get_old_changes`, `changelog_get_minversion`, escaping helpers, init, and changelog file version/name probes.

## Control Flow
`changelog` formats a line into a static 200000-byte buffer, increments `meta_version`, writes the record through `changelog_mr`, stores/broadcasts the copied string, and updates `lastchange`. `changelog_mr` delegates to `bgsaver_changelog` in background mode or appends to `changelog.0.mfs` in async/sync foreground modes. `changelog_rotate` uses background rotation when possible, otherwise closes and renames foreground logs. `changelog_get_old_changes` locates the block covering the requested version and streams entries up to a caller limit.

## State And Persistence Behavior
Persistent state is `changelog.0.mfs` plus rotated backlog files. Foreground sync mode calls `fsync` for every record; async mode flushes stdio but does not fsync every line; background mode delegates persistence to `bgsaver`. In-memory replay retention is bounded by `CHANGELOG_PRESERVE_SECONDS`, `CHANGELOG_PRESERVE_MB`, `meta_chlog_keep_version`, and `matomlserv_get_min_version`.

## Dependencies And Integration Points
The module depends on `metadata`, `bgsaver`, `main`, `mfslog`, `matomlserv`, `cfg`, and `clocks`. Many master modules call `changelog()` for metadata mutations. `matomlserv.c` calls `changelog_get_old_changes` and `changelog_get_minversion` to serve delayed metadata log clients.

## Risks
`changelog_old_changes_free` subtracts `old_changes_head->size` from total size while freeing `old_changes_head`; this matches the block being freed but is easy to misread and should be regression-tested. Static buffers in `changelog`, `changelog_generate_gids`, and `changelog_escape_name` are not thread-safe. Foreground write failures log lost changes but do not necessarily force shutdown. File-version parsing is format-sensitive and returns zero for malformed trailing data.

## Test Signals
Test signals include generated changelog lines and version increments, foreground async/sync persistence, background delegation to bgsaver, retention pruning under time and size limits, delayed receiver replay from boundary versions, escaping of reserved bytes, and parsing first/last versions from valid and corrupt log files.

# sources/distributed-fs/moosefs/mfsmaster/chartsdata.c

## Purpose
`chartsdata.c` samples mfsmaster runtime metrics and feeds the common charts subsystem. It combines CPU, memory, filesystem operation counters, chunk operations, client traffic, chunkserver space, object counts, chunk health, server counts, and usage-difference data into the 70-slot chart schema.

## Important APIs And Types
`calcdefs`, `statdefs`, and `estatdefs` are static arrays initialized from `chartsdefs.h`. Runtime globals `rss`, `virt`, `scpu`, and `ucpu` cache resource usage. Public functions are `chartsdata_resusage` and `chartsdata_init`; internal hooks are `chartsdata_refresh`, `chartsdata_store`, and `chartsdata_term`.

## Control Flow
`chartsdata_init` initializes CPU accounting, captures initial memory usage, registers a 60-second refresh, registers hourly chart storage, registers destructor storage, and calls `charts_init` using `stats.mfs`. Each refresh initializes all slots to `CHARTS_NODATA`, fills known metrics from subsystem APIs, sets the delay chart to no data, and calls `charts_add(data, main_time()-60)`.

## State And Persistence Behavior
The charts subsystem persists samples to `stats.mfs`. On termination, this module refreshes one final sample, stores charts, and terminates chart state. Resource usage caches are process globals available through `chartsdata_resusage`.

## Dependencies And Integration Points
It depends on `charts`, `main`, `chunks`, `filesystem`, `matoclserv`, `memusage`, `cpuusage`, `matocsserv`, `csdb`, and `chartsdefs`. `init.h` registers `chartsdata_init` as the charts module. `mfsstatsdump` shares `chartsdefs.h`, so schema changes affect both producer and dump tool.

## Risks
Schema indexes in `chartsdefs.h` and producer assignments must stay aligned. CPU scaling uses `(value*6)/100`, which assumes the source accounting and one-minute interval semantics. `CHARTS_DELAY` is currently always no data despite `bgsaver` tracking changelog delay internally. Any subsystem stats function with side effects can affect chart sampling.

## Test Signals
Signals include `charts_init` success, creation/update of `stats.mfs`, non-`CHARTS_NODATA` values for active subsystems, stable `mfsstatsdump` decoding, and refresh behavior over multiple 60-second intervals.

# sources/distributed-fs/moosefs/mfsmaster/chunkdelay.c

## Purpose
`chunkdelay.c` temporarily protects chunks from deletion after representation-changing operations such as COPY-to-EC or EC-to-COPY replication. It gives chunk state time to settle before allowing destructive cleanup and schedules extra chunk work when protection expires.

## Important APIs And Types
`chunk_prot` stores a `chunkid`, timestamp, and next pointer in a 4096-bucket hash table keyed by `chunkid ^ (chunkid >> 16)`. `ProtectionDelay` is loaded from `CHUNK_PROTECTION_SECONDS`. `chunk_group` batches up to 128 expired chunk IDs for post-removal jobs. Public functions are `chunk_delay_protect`, `chunk_delay_is_protected`, and `chunk_delay_init`.

## Control Flow
`chunk_delay_protect` inserts or refreshes a timestamp for a chunk. `chunk_delay_is_protected` returns true while the protection window is active and removes expired entries lazily. `chunk_delay_remove_old` scans ten hash buckets per tick, removes expired entries, groups their IDs, and calls `chunk_do_extra_job` for each. `chunk_delay_init` clears the table, loads config, registers a 10 ms periodic scanner, and registers reload.

## State And Persistence Behavior
Protection state is volatile and process-local. There is no metadata serialization; after restart, protection windows are lost. Expiry triggers scheduling work rather than persisting a record.

## Dependencies And Integration Points
It depends on `clocks`, `chunks`, `main`, and `cfg`. Observed callers in `chunks.c` protect chunks after representation changes and initialize the module from chunk initialization. The scanner calls back into `chunk_do_extra_job`.

## Risks
Restart clears all protection delays, which can allow cleanup sooner than it would during uninterrupted runtime. Allocation in `chunk_delay_protect` and group expansion is unchecked. A very small `CHUNK_PROTECTION_SECONDS` can collapse the safety window; a very large value can defer cleanup and extra jobs for too long. The 10-bucket-per-tick scan spreads work but means full-table cleanup latency depends on timer cadence.

## Test Signals
Tests should verify protect/refresh semantics, expiry after configured delay, lazy removal in `is_protected`, scanner removal and `chunk_do_extra_job` calls, config reload, and collision behavior for multiple chunk IDs in one bucket.

The API hides a volatile in-memory hash table. Protection state is not durable across master restarts.

## Dependencies And Integration Points
It includes `<inttypes.h>` and is integrated with `chunks.c` and the main timer/reload hooks through the implementation.

## Risks
The boolean API does not expose remaining delay or insertion failure. Callers must consistently check protection before destructive actions.

## Test Signals
Compile coverage from `chunks.c` and focused behavior tests for protection and expiry validate this interface.
