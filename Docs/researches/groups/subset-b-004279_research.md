# sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci.c

Purpose: this is the generic Secure Digital Host Controller Interface core used by platform, PCI, OF, and SoC-specific SDHCI wrappers. It translates Linux MMC requests into SDHCI register programming, handles PIO/SDMA/ADMA/external DMA transfers, command and data IRQs, timers, tuning, voltage and bus-mode changes, CQE interrupt handoff, runtime/system PM, and host setup/removal.

Important APIs, types, and functions: exported entry points include `sdhci_alloc_host()`, `sdhci_setup_host()`, `__sdhci_add_host()`, `sdhci_add_host()`, `sdhci_remove_host()`, `sdhci_cleanup_host()`, `sdhci_request()`, `sdhci_request_atomic()`, `sdhci_set_ios()`, `sdhci_set_clock()`, `sdhci_set_power()`, `sdhci_start_signal_voltage_switch()`, `sdhci_execute_tuning()`, `sdhci_cqe_enable()`, `sdhci_cqe_disable()`, `sdhci_cqe_irq()`, and PM helpers. Internal hot paths include `sdhci_send_command()`, `sdhci_finish_command()`, `sdhci_finish_data()`, `sdhci_cmd_irq()`, `sdhci_data_irq()`, `sdhci_irq()`, `sdhci_thread_irq()`, and `sdhci_request_done()`. DMA support is split across `sdhci_prepare_dma()`, `sdhci_adma_table_pre()`, `sdhci_adma_table_post()`, `sdhci_request_done_dma()`, and optional external DMA helpers.

Control flow: host wrappers allocate an MMC host, fill `struct sdhci_host`, assign `sdhci_ops`, and call `sdhci_add_host()` or `sdhci_setup_host()` plus `__sdhci_add_host()`. Setup reads capabilities, applies DT capability overrides, regulators, quirks, DMA masks, ADMA buffers, OCR/capability derivation, tuning parameters, and MMC limits. Add-host initializes resets and IRQ masks, creates the completion workqueue and timeout timers, requests a threaded IRQ, registers optional LED support, calls `mmc_add_host()`, and enables card-detect IRQs. Request flow starts in `sdhci_request()` or `sdhci_request_atomic()`, checks card presence, optionally sends a manual CMD23 first, waits for inhibit bits, prepares data/DMA, programs argument, transfer mode, command, and timers, then relies on hard IRQ plus thread IRQ/completion work to finish. Command IRQs read responses and chain SBC to the real command; data IRQs process PIO buffer interrupts, SDMA boundary updates, ADMA errors, busy completion, and data-end ordering. Completion unmaps DMA, optionally resets after errors, and calls either vendor `request_done` or `mmc_request_done()`.

State and persistence: persistent in-memory state is `struct sdhci_host`: current command/data pointers, deferred command, `mrqs_done[]`, IRQ enable cache `ier`, quirks, flags, clock/power/timing, ADMA and bounce buffers, timeout values, runtime suspend and bus-power flags, CQE masks, tuning state, and regulator ownership. Hardware state lives in SDHCI registers and is reinitialized by `sdhci_init()`, reset helpers, set-ios paths, resume paths, and CQE transitions. DMA mappings are transient per request and guarded by host cookies. Timers and the completion workqueue decouple request finish from IRQ context when reset, DMA unmap, deferred commands, or always-defer policy require it.

Dependencies and integration points: the file depends on the MMC core, `sdhci.h` register/host definitions, DMA mapping and DMAEngine APIs, regulators, runtime PM, GPIO card-detect/write-protect helpers, LED class support, dynamic debug, and optional `CONFIG_MMC_SDHCI_EXTERNAL_DMA`. Vendor drivers integrate through `struct sdhci_ops` callbacks for I/O accessors, clock/power/reset, DMA enable/mask, tuning, UHS signaling, card events, ADMA descriptors, voltage switch, register dumps, and request completion. CQE users call the SDHCI CQE helpers from cqhci-backed drivers.

Risks: request state is highly concurrent across hard IRQ, IRQ thread, timers, workqueue, runtime PM, and MMC callbacks; incorrect locking or stale `mrqs_done[]` entries can double-complete or leak requests. Reset timing and inhibit-bit waits are controller-sensitive and heavily quirk-dependent. ADMA descriptor sizing, unaligned bounce fragments, 64-bit/v4-mode selection, and SDMA boundary restarts are common data-corruption risk points. Timeout handling deliberately mixes hardware and software timeouts when hardware limits are too small. Voltage switching and preset values depend on regulator truth and board capabilities. Card removal during transfer, broken card-detect lines, and CQE recovery all rely on error paths that reset state machines without losing MMC-core completion ordering.

Test signals: useful validation includes boot/probe on SDHCI v2/v3/v4 controllers, PIO, SDMA, ADMA32, ADMA64, and external-DMA transfers; single and multi-block reads/writes with CMD12/CMD23 variants; busy-response commands; card insertion/removal during active I/O; tuning for SDR50/SDR104/HS200/HS400; voltage switches across 3.3 V/1.8 V/1.2 V with and without regulators; suspend/resume and runtime PM with SDIO wake IRQs; CQE enable/disable/recovery; fault injection for CRC, timeout, ADMA, and unexpected IRQ paths; and debugfs MMC error counters/register dumps matching injected failures.

# sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci.h

Purpose: this header defines the SDHCI register map, register bit fields, ADMA descriptor formats, quirk/flag constants, `struct sdhci_host`, `struct sdhci_ops`, I/O accessor wrappers, and exported core-driver prototypes used by SDHCI bus and platform drivers.

Important APIs, types, and functions: register constants cover command, transfer, present-state, host-control, power, clock, interrupt, capabilities, ADMA, preset, and version registers through SDHCI v4.20 plus UHS-II and CQE-related bits. `struct sdhci_adma2_32_desc` and `struct sdhci_adma2_64_desc` describe hardware DMA descriptors. `enum sdhci_cookie` tracks DMA mapping ownership. `struct sdhci_host` is the central runtime object and embeds hardware-facing fields, MMC-facing state, DMA buffers, timers, workqueue, CQE state, tuning state, OCR overrides, and private driver storage. `struct sdhci_ops` is the vendor hook table. Inline `sdhci_readl/readw/readb` and `sdhci_writel/writew/writeb` route accesses through optional custom accessors when configured.

Control flow: SDHCI wrapper drivers include this header, allocate a host with private tailroom, fill hardware identity, `ioaddr`, `irq`, quirks, and `ops`, then call the core registration helpers declared here. During requests the core mutates fields declared in `struct sdhci_host` and calls vendor callbacks from `struct sdhci_ops`; wrappers may also call exported helpers directly to reuse generic clock, power, reset, tuning, CQE, and PM behavior.

State and persistence: most state is per-host and lasts from allocation until device removal. Cached register state such as `ier`, current `clock`, `pwr`, `timing`, `preset_enabled`, `v4_mode`, CQE masks, and tuning parameters mirrors hardware configuration that may need restoration after reset or resume. Pointers to `cmd`, `data_cmd`, `deferred_cmd`, and `data` represent the active request pipeline. ADMA, alignment, bounce, and external DMA fields persist as resources but are reused per request.

Dependencies and integration points: the header depends on Linux MMC host structures, scatterlists, I/O accessors, interrupt types, LED support, compiler packing/alignment annotations, and bit helpers. It is the primary integration contract between `sdhci.c` and platform drivers such as TI AM654, Fujitsu/Socionext F_SDH30, OF/ACPI wrappers, PCI wrappers, and cqhci bridges.

Risks: quirk bits encode many controller deviations and are easy to combine incorrectly; wrong flags can silently select broken DMA, wrong voltage modes, bad timeout behavior, or unsupported transfer modes. `struct sdhci_host` mixes fields protected by the spinlock with setup-time fields, so callers must follow core locking assumptions. Custom I/O accessors must preserve register-width semantics. The private tail array requires allocation through `sdhci_alloc_host()` or compatible platform helpers.

Test signals: build coverage should include configurations with and without `CONFIG_MMC_SDHCI_IO_ACCESSORS`, `CONFIG_PM`, LED class, external DMA, and CQE users. Runtime signals include correct register reads/writes through custom accessors, expected quirk-driven capability changes, and no structure-layout regressions for drivers using `sdhci_priv()`.

# sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci_am654.c

Purpose: this platform driver supports TI AM654/J721E/AM64/AM62 SDHCI 5.1 controllers. It wraps the generic SDHCI platform core with TI PHY programming, output/input tap delays, DLL setup, SoC-specific quirks, CQHCI integration, runtime PM, and device-tree property parsing.

Important APIs, types, and functions: `struct sdhci_am654_data` stores regmap, per-timing OTAP/ITAP values, clock-buffer and DLL trim settings, driver strength, strobe select, flags, quirks, DLL state, and tuning retry count. `struct sdhci_am654_driver_data` selects per-compatible `sdhci_pltfm_data`, flags, and quirks. Key routines are `sdhci_am654_set_clock()`, `sdhci_j721e_4bit_set_clock()`, `sdhci_am654_setup_dll()`, `sdhci_am654_setup_delay_chain()`, `sdhci_am654_platform_execute_tuning()`, `sdhci_am654_cqhci_irq()`, `sdhci_am654_init()`, `sdhci_am654_probe()`, runtime suspend/resume, and restore.

Control flow: probe selects driver data from OF compatible, then overrides it for AM65x SR1.0 via `soc_device_match()`. It initializes an SDHCI platform host, records TI flags/quirks, gets `clk_xin`, maps the second MMIO resource as a syscon-like regmap for PHY/CTL_CFG registers, reads TI properties, parses MMC DT properties, applies HS400 descoping for affected SoCs, overrides MMC ops for voltage switch and tuning, enables runtime PM and the clock, and calls `sdhci_am654_init()`. Init resets PHY delays, optionally calibrates IO lines, enables IOMUX, sets embedded/removable slot type, enables SDR50 tuning, calls `sdhci_setup_host()`, initializes CQHCI, reads tap-delay DT properties, applies HS400 quirk filtering, and calls `__sdhci_add_host()`.

State and persistence: parsed OTAP/ITAP arrays persist per timing mode and are used whenever the SDHCI core changes clock/timing. Tuning updates `itap_del_sel[timing]`, so a successfully discovered input tap is retained for later clock programming. Runtime suspend disables CQHCI, SDHCI runtime state, and the input clock; runtime resume reenables the clock, restores PHY/CTL_CFG settings, resumes SDHCI, and then CQHCI. `dll_enable` affects whether tuning treats the ITAP search space as circular.

Dependencies and integration points: the driver uses `sdhci-pltfm`, `sdhci-cqhci`, `cqhci`, common clock APIs, regmap MMIO, runtime PM, device properties, OF matching, and SoC revision matching. It delegates most MMC request handling to `sdhci.c` through `sdhci_ops`, while CQE interrupts are bridged through `sdhci_cqe_irq()` and `cqhci_irq()`. Device-tree bindings provide `ti,otap-del-sel-*`, optional `ti,itap-del-sel-*`, `ti,trm-icp`, `ti,driver-strength-ohm`, `ti,strobe-sel`, `ti,clkbuf-sel`, and card-detect quirks.

Risks: PHY timing is board- and mode-specific; missing mandatory legacy OTAP fails probe, while missing optional timing properties remove corresponding MMC capabilities. The tuning algorithm searches failing ITAP windows and chooses the center of the largest passing window; all-pass or all-fail results trigger retries and can still fail. Runtime resume must restore CTL_CFG and PHY state before SDHCI resumes. CQE and SDHCI IRQ handling share the same interrupt path, so masking errors can misroute completions. Some variants require suppressing SDHCI's 1.8 V enable bit or forcing card-detect test bits.

Test signals: validate each compatible string and SoC revision path, mandatory and optional DT property handling, HS400 descoping on AM62Px SR1.0/SR1.1, clock changes for legacy through HS400 modes, DLL ready polling, delay-chain fallback below 50 MHz, tuning retry and chosen ITAP logs, CQE task operation, runtime autosuspend/resume, and card-detect behavior on boards needing forced CD test mode.

# sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci_f_sdh30.c

Purpose: this platform driver supports Fujitsu/Socionext F_SDH30 SDHCI 3.0-style controllers. It supplies vendor reset, voltage-switch, minimum-clock, clock/reset resource handling, and extended-register initialization around the generic SDHCI platform core.

Important APIs, types, and functions: `struct f_sdhost_priv` stores interface/core clocks, optional reset control, vendor HS200 bit, device pointer, and the command/data delay option. `sdhci_f_sdh30_soft_voltage_switch()` programs F_SDH30 IO control and tuning registers for 1.8 V switching and optional HS200 vendor mode. `sdhci_f_sdh30_reset()` wraps generic `sdhci_reset()` with clock-before-reset, command/data delay, and forced card-present behavior for nonremovable media. Probe and remove own the platform host, clocks, reset, vendor register initialization, and `sdhci_add_host()`/`sdhci_pltfm_remove()`.

Control flow: probe allocates an SDHCI platform host with F_SDH30 private data, parses MMC properties, reads the optional command/data delay property, and for OF-backed devices enables `iface` and `core` clocks plus an optional shared reset. It initializes AHB burst/endian/bus-lock bits, toggles eMMC reset in `F_SDH30_ESD_CONTROL`, detects HS200 vendor support from SDHCI capabilities, sets a timeout quirk if the timeout clock is absent, and registers the host. Remove delegates SDHCI teardown to `sdhci_pltfm_remove()`, asserts reset, and disables clocks.

State and persistence: private state persists clock/reset handles and vendor capability choices. Hardware state in AHB, IO_CONTROL2, ESD_CONTROL, TUNING_SETTING, and TEST registers is rewritten during probe, reset, and voltage switch. The `vendor_hs200` flag is derived once from capabilities and reused during soft voltage switch.

Dependencies and integration points: the driver uses `sdhci-pltfm`, generic `sdhci_set_clock()`, `sdhci_set_bus_width()`, `sdhci_set_uhs_signaling()`, OF/ACPI matching, common clocks, reset controls, and MMC DT parsing. Compatibles are `fujitsu,mb86s70-sdhci-3.0` and `socionext,f-sdh30-e51-mmc`; ACPI ID is `SCX0002`.

Risks: the reset path writes a magic clock value if SDHCI clock control is zero, so clock/reset ordering is important. Forced card insertion for nonremovable devices can mask physical detect issues. The driver infers HS200 vendor mode from `SDHCI_CAN_DO_8BIT`, which couples bus-width capability to high-speed vendor programming. Error paths after clock enabling must unwind both clocks and reset correctly. Timeout-clock absence switches to SDCLK-derived timeout behavior, which needs accurate clock reporting.

Test signals: validate OF and ACPI probe, both clock names, optional reset deassert/assert, AHB config bits after probe, eMMC reset pulse, nonremovable card-present force, 1.8 V/HS200 voltage switch register sequence, command/data delay property behavior, and suspend/resume through `sdhci_pltfm_pmops`.

# sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci_f_sdh30.h

Purpose: this header defines the F_SDH30 vendor register offsets and bit fields used by `sdhci_f_sdh30.c` to configure AHB behavior, tuning, voltage switching, eMMC reset/HS200 mode, forced card insertion, and minimum clock.

Important APIs, types, and functions: it exposes register offsets `F_SDH30_AHB_CONFIG`, `F_SDH30_TUNING_SETTING`, `F_SDH30_IO_CONTROL2`, `F_SDH30_ESD_CONTROL`, and `F_SDH30_TEST`. Bit definitions include AHB endian/bus-lock/increment controls, command-check disable, voltage-switch control bits, eMMC reset, command/data delay, HS200 enable, forced card insert, and `F_SDH30_MIN_CLOCK`.

Control flow: the C driver includes this header and uses the definitions during probe-time vendor initialization, reset-time delay/card-detect handling, and soft voltage switching. There is no executable logic in the header.

State and persistence: the header itself stores no state. The constants identify hardware state persisted in vendor registers until reset, power loss, or explicit rewrite by the driver.

Dependencies and integration points: it assumes Linux `BIT()` is available through the including C file's headers. Its constants are tightly coupled to the F_SDH30 SDHCI wrapper and should not be used for generic SDHCI controllers.

Risks: incorrect bit definitions directly affect low-level electrical/timing behavior. Because the header has no include guard, duplicate inclusion in a broader translation unit would rely on identical macro definitions rather than guard protection, though current usage includes it once from the driver.

Test signals: compile coverage of `sdhci_f_sdh30.c`, register write traces during voltage switch and reset, and hardware tests confirming each vendor bit produces the expected controller behavior.

# sources/distributed-fs/ceph-client/drivers/mmc/host/sdricoh_cs.c

Purpose: this legacy PCMCIA/CardBus driver supports Ricoh Secure Digital readers found behind some Ricoh RL5c476 II bridges. It implements a simple MMC host using direct MMIO polling and PIO transfers rather than the SDHCI core.

Important APIs, types, and functions: `struct sdricoh_host` stores device/MMC pointers, mapped I/O base, backing PCI device, and APP_CMD state. Register helpers wrap byte/word/long MMIO with verbose debug. `sdricoh_reset()` initializes controller registers. `sdricoh_mmc_cmd()` sends commands and handles APP_CMD opcode adjustment. `sdricoh_blockio()` performs 32-bit FIFO-style PIO reads/writes. `sdricoh_request()`, `sdricoh_set_ios()`, and `sdricoh_get_ro()` implement `mmc_host_ops`. `sdricoh_init_mmc()`, `sdricoh_pcmcia_probe()`, and `sdricoh_pcmcia_detach()` bridge PCMCIA identification to PCI MMIO mapping and MMC registration.

Control flow: PCMCIA probe scans PCI devices for the Ricoh bridge ID, tries to map BAR0 of the matching PCI device, checks the controller version register, allocates an MMC host, sets static frequency/OCR/capability limits, resets the controller, and calls `mmc_add_host()`. Requests clear status, set block size/data mode for data commands, issue the command, read short or 136-bit response registers, transfer each block through a single scatterlist page mapping, finish data mode, poll for transfer completion, and call `mmc_request_done()`. Suspend is a no-op; resume resets the controller.

State and persistence: persistent state is minimal: mapped MMIO, PCI reference, MMC host, and the `app_cmd` latch that marks the command following `MMC_APP_CMD`. Hardware power/mode registers are reprogrammed by reset and set-ios. Data transfer state is synchronous within `sdricoh_request()`; there are no IRQs, DMA mappings, workqueues, or persistent request objects.

Dependencies and integration points: the driver uses the PCMCIA core for device matching, PCI APIs for CardBus bridge discovery and BAR mapping, Linux MMC host APIs, highmem page mapping, scatterlist helpers, and polling helpers. The module parameter `switchlocked` inverts the read-only interpretation for machines with reversed lock status.

Risks: the PCI scan binds indirectly through a PCMCIA function and can pick the first matching Ricoh bridge that passes version probing. The request path assumes simple scatterlist layout and maps `data->sg` page offsets per block rather than walking arbitrary SG entries. It is entirely polling-based with one-second command/data timeouts, so slow or wedged hardware blocks request context. Error checking is sparse, busy handling is marked FIXME, and frequency/voltage handling is mostly delegated to fixed controller behavior.

Test signals: test on the target Ricoh CardBus hardware with both known product strings, version register `0x4000`, read/write single and multi-block PIO, APP_CMD/ACMD command sequences, 136-bit response commands, write-protect with both `switchlocked` values, suspend/resume reset, detach cleanup with PCI ref release, and timeout behavior on card removal or unresponsive media.

# sources/distributed-fs/ceph-client/drivers/mmc/host/sh_mmcif.c

Purpose: this Renesas/SuperH MMCIF platform driver implements an asynchronous MMC/eMMC host for the on-chip MMCIF controller. It is not an SDHCI driver; it programs MMCIF-specific command, clock, interrupt, response, data, DMA, and status registers through platform-data register definitions.

Important APIs, types, and functions: `struct sh_mmcif_host` holds MMC host state, active request, platform device, clock, bus/timing, error/dying flags, MMIO base, spinlock-protected state, wait-state enum, timeout work, scatterlist iterator, power state, CCS/clock-control feature flags, thread mutex, clock-divider map, DMA channels, completion, and DMA-active flag. Key routines include DMA setup/start/release helpers, `sh_mmcif_clock_control()`, `sh_mmcif_sync_reset()`, `sh_mmcif_error_manage()`, PIO read/write helpers for single and multi-block transfers, `sh_mmcif_set_cmd()`, `sh_mmcif_start_cmd()`, `sh_mmcif_stop_cmd()`, `sh_mmcif_request()`, `sh_mmcif_set_ios()`, threaded IRQ `sh_mmcif_irqt()`, hard IRQ `sh_mmcif_intr()`, timeout work, probe/remove, and suspend.

Control flow: probe maps MMIO, allocates an MMC host, parses DT, initializes caps and limits for MMC/eMMC-only operation, gets/enables the clock, computes min/max rates, enables runtime PM, resets hardware, masks interrupts, requests one or two threaded IRQs, registers the MMC host, exposes latency QoS, then idles power/clock. `set_ios()` powers the controller up or down, controls regulators, runtime PM, clocks, reset, and DMA channel acquisition/release, and records bus width/timing. Request submission rejects non-idle state, records `host->mrq`, and starts the command. The hard IRQ acknowledges/masks interrupt bits and wakes the thread unless DMA is active; the IRQ thread advances a wait-state machine through command completion, PIO or DMA data movement, optional auto-CMD12 stop completion, and final `mmc_request_done()`.

State and persistence: `state` tracks idle/request/ios/timeout and is protected by `host->lock`; `wait_for` identifies the current bottom-half stage. `host->mrq` is the sole active request pointer. `sd_error` carries hard-IRQ error observation into the threaded handler, while `dma_active` coordinates DMA callback/error IRQ behavior. Power state persists across `set_ios()` and gates clock/runtime-PM/DMA ownership. Register state is reset by `sh_mmcif_sync_reset()` and masked during suspend/remove. Timeout work is scheduled per stage and cancelled by the IRQ thread.

Dependencies and integration points: the driver uses Linux MMC core, runtime PM, common clocks, regulators via `mmc_regulator_get_supply()`, GPIO card-detect through `mmc_gpio_get_cd`, DMAEngine, legacy SuperH DMA filter/platform data, platform resource APIs, PM QoS, and `include/linux/platform_data/sh_mmcif.h` for register offsets/accessors and platform data. OF matching supports `renesas,sh-mmcif`.

Risks: the request state machine spans hard IRQ, threaded IRQ, DMA callback, timeout work, and `set_ios()`; races are explicitly noted around remove, delayed work, and IRQ teardown. DMA is all-or-nothing for TX/RX and falls back permanently to PIO if descriptor prep fails. PIO helpers assume block sizes divisible into 32-bit register accesses. Error recovery can force command-sequence break and synchronous reset with long polling. Clock divider selection differs depending on `clkdiv_map` and platform clock behavior. The driver advertises no SD/SDIO support and is tuned for MMC/eMMC use.

Test signals: validate probe with one and two IRQ resources, DT and platform-data OCR/caps paths, runtime power cycling through `set_ios()`, clock min/max and divider programming, single/multi-block read and write using DMA and forced PIO fallback, automatic stop handling for multi-block transfers, CRC/timeout/index error paths, command busy handling, timeout work completion, suspend interrupt masking, remove while idle and while requests are blocked, and DMA channel release after fallback or power off.
