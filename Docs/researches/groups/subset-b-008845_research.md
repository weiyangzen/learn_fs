# sources/storage-engines/tikv/components/raftstore/src/store/config.rs

Purpose: This file defines the raftstore `Config` schema, default values, validation rules, metrics export, and online configuration manager for TiKV raftstore. It is the central contract for Raft timing, log GC, snapshot handling, peer liveness, split/merge behavior, batch-system pools, async IO sizing, entry-cache memory pressure, slow-store inspection, and disk hang fail-fast tuning.

Important APIs and types: `Config` is `Serialize`, `Deserialize`, `PartialEq`, and `OnlineConfig`, with kebab-case serde names and flattened `apply-` and `store-` `BatchSystemConfig` submodules. `Config::new_raft_config` builds the raft-rs `raft::Config` with peer ID, tick counts, inflight limits, message size, applied index, quorum checks, prevote, and skip-broadcast-commit. Getter helpers convert raftstore durations into `time::Duration`, expose derived GC limits, and gate entry-cache warmup. `Config::optimize_for` adjusts raft log GC limits for raft-kv-v2. `Config::tune_inspector_configs` suppresses duplicate kv disk inspection when raft and kv share a mount. `Config::validate` normalizes dependent defaults and rejects unsafe values. `write_into_metrics` and `write_change_into_metrics` publish `tikv_config_raftstore` gauges. `RaftstoreConfigManager` implements `online_config::ConfigManager` and schedules `RefreshConfigTask` work for pool, batch-size, writer, and snapshot reader resizing.

Control flow: Startup constructs defaults, optional toml deserialization overlays fields, `optimize_for` may fill raft-kv-v2 GC limits, and `validate` enforces the runtime-safe shape before raftstore starts. Validation first checks Raft timing invariants, message and entry sizes, log GC thresholds, leader lease constraints, merge ticks, disk hang timeout minimums, stale-peer timing, transfer lag, warmup duration, local read sizing, raft write wait bounds, adaptive QPS threshold, batch-system pool and batch limits, IO notify capacity, future poll size, hibernate-related peer-down duration, memory eviction ratio, snapshot generator sizing, leader lease interval defaults, raft-kv-v2 delete-range incompatibility, slow trend factors, and pending-apply minimums. Online changes flow through `RaftstoreConfigManager::dispatch`: it updates the shared `VersionTrack<Config>`, rejects illegal sync-to-async or async-to-sync `store_io_pool_size` mode switches, then sends resize tasks for affected raftstore components and updates metrics.

State and persistence behavior: `Config` itself is the deserialized and version-tracked runtime state; it does not persist raft data. Several validation steps mutate the in-memory config by filling defaults such as min and max election ticks, raft log GC count and size limits, region split check diff, batch max sizes, hibernate-safe peer down duration, and leader lease helper intervals. Metrics state is persisted only in Prometheus collectors. Online updates rely on `VersionTrack<Config>` so readers can observe a coherent config snapshot while workers receive scheduled resize tasks.

Dependencies and integration points: The file integrates with raft-rs, `batch_system`, `engine_traits::PerfLevel`, `online_config`, `tikv_util` readable config types, `SysQuota`, Prometheus, raftstore worker refresh tasks, and coprocessor split sizing. `disk_hang_timeout` is consumed by `fail_fast.rs`; store and apply batch settings are consumed by raftstore FSM pools; raft log and cache settings drive peer storage and `entry_storage.rs`; inspector intervals integrate with slow-store detection; snapshot sizing and generator pool settings feed snapshot workers.

Risks: Many defaults are derived from other subsystem constants, so changing region split size, raft-kv-v2 mode, hibernation, or CPU quota changes effective behavior after validation. Some fields are hidden, skipped, deprecated, or test-only, which creates compatibility pressure for serde and online-config generation. `raft_log_gc_count_limit()` and `raft_log_gc_size_limit()` unwrap options, so callers depend on `validate` or `optimize_for` having filled them. Online resizing of `store_io_pool_size` intentionally forbids switching between sync and async modes; bypassing `dispatch` would miss that safety guard. Disk hang timeout accepts `0s` as an explicit disable but rejects non-zero values below 30 seconds, which must stay aligned with fail-fast semantics.

Test signals: `test_config_validate` covers heartbeat/election ordering, min/max election range normalization, GC threshold and derived GC limits, leader lease constraints, merge gap versus GC count, zero merge tick rejection, disk hang timeout disable and minimum behavior, stale and abnormal leader timing, local read batch and future poll size checks, batch pool and batch-size bounds, hibernation-dependent store batch defaults, hibernation peer-down extension, message and entry size caps, region split diff derivation with buckets, raft-kv-v2 optimized GC limits, raft write wait upper bound, and inspector interval tuning.

# sources/storage-engines/tikv/components/raftstore/src/store/disk_probe.rs

Purpose: This file provides the small shared disk probe used by raftstore disk latency checks and fail-fast disk hang detection. It intentionally performs a blocking `write + sync_all` on a dedicated file so higher layers can detect either ordinary probe failures or a probe that stops making progress.

Important APIs and types: `write_sync_once(path, payload)` opens or creates the probe file with truncate-write semantics, writes the payload, syncs the file, and returns elapsed monotonic duration. `ProbeRunner` owns a probe `PathBuf`, a static payload, and shared mutex-protected `ProbeState`. `ProbeRunner::probe_once` performs the blocking IO. `try_start_probe`, `finish_probe_success`, `finish_probe_failure`, `current_probe_elapsed`, `time_since_last_success`, and `failure_count_since_last_success` expose the minimum state needed for non-overlapping probes and hang classification.

Control flow: A caller first calls `try_start_probe`; if no probe is already in flight, `ProbeState` records the start instant. The caller then invokes `probe_once`. On success, it calls `finish_probe_success`, which clears the in-flight marker, records the last success instant, and resets the failure counter. On error, it calls `finish_probe_failure`, which clears the in-flight marker and increments the failures since last success. If `sync_all` blocks indefinitely, no finish method runs, so `current_probe_elapsed` keeps growing and an independent checker can detect a hang.

State and persistence behavior: Persistent state is only the temporary probe file at the configured path. Each probe truncates and rewrites the file with the same static payload, then forces it to disk. Runtime state is in `ProbeState`: the current probe start, last successful probe time, and failure count since that success. The state is wrapped in `Arc<parking_lot::Mutex<_>>`, allowing cloned `ProbeRunner`s to be shared between a blocking probe thread and a checker thread.

Dependencies and integration points: `fail_fast.rs` uses `ProbeRunner` for raft and optional kv disk probes. `worker/disk_check.rs` uses the same helper for flush latency inspection. The module depends on standard filesystem APIs, `parking_lot::Mutex`, and TiKV's monotonic `Instant`.

Risks: The probe is deliberately blocking, so it must be run on a dedicated worker thread rather than a critical reactor or raftstore FSM thread. Callers must maintain the `try_start_probe` and finish-method protocol; missing a finish call after a non-blocking error would create a false in-flight hang. The probe file path must be on the disk being checked, otherwise it can report health for the wrong mount. The module does not delete the probe file; cleanup is the caller's responsibility.

Test signals: `test_probe_runner_probe_once` verifies that a probe writes a real file and reports non-zero elapsed time. `test_probe_runner_state` verifies non-overlap, in-flight elapsed reporting, success resetting failures, success time retention, and failure counting after a prior success.

# sources/storage-engines/tikv/components/raftstore/src/store/entry_storage.rs

Purpose: This module implements `EntryStorage`, the raft-log access subset shared by raftstore v1 and v2. It bridges persisted raft log entries in the `RaftEngine`, raft/apply metadata state, in-memory entry and term caches, async log fetching, committed-entry tracing for apply workers, entry-cache warmup for leader transfer, and cache eviction under compaction or memory pressure.

Important APIs and types: `first_index` and `last_index` derive log bounds from `RaftApplyState` and `RaftLocalState`. `CachedEntries` wraps committed entries handed to apply threads and tracks "dangle" memory that may no longer be in the main cache. `EntryCache` stores contiguous recent `Entry` values, a persisted index gate, traced apply batches, and hit/miss counters. `TermCache` stores a small ordered mapping of recent term ranges to speed term lookups. `RaftlogFetchState` and `RaftlogFetchResult` model async read lifecycle. `CacheWarmupState` tracks warmup task timeout and election-timeout staleness. `EntryStorage::new`, `entries`, `term`, `append`, `async_warm_up_entry_cache`, `on_async_warm_up_entry_cache_fetched`, `compact_entry_cache`, `evict_entry_cache`, `update_cache_persisted`, `trace_cached_entries`, and `flush_entry_cache_metrics` are the main public surface.

Control flow: `EntryStorage::new` validates raft/apply state consistency, derives `last_term` and `applied_term`, initializes caches, and stores IO histograms. `validate_states` may advance hard-state commit to the apply state's recorded commit index, but rejects missing commit entries, commit beyond last index, or a raft term older than the apply commit term. `entries` first checks the requested range against truncation and last index. It serves fully cached ranges from `EntryCache`, synchronously fetches from `RaftEngine` when async is disallowed, or schedules `ReadTask::FetchLogs` through `read_scheduler` and returns `LogTemporarilyUnavailable` when async is allowed. `async_fetch` consumes compatible fetched results, truncates to requested range and size, retries invalid results up to `MAX_ASYNC_FETCH_TRY_CNT`, and falls back to synchronous fetch for repeated mismatches or small remaining tails. `term` checks truncated and last-term shortcuts, then entry cache, term cache, and finally raft engine.

State and persistence behavior: The durable source of truth is the `RaftEngine` entries plus `RaftLocalState` and `RaftApplyState`. `append` updates only in-memory raft state and cache, while recording the new entries and truncate point in `WriteTask` for later persistence. The entry cache is constrained by `persisted`: compaction and eviction must not drop unpersisted entries because raft-rs can still need them before async writes complete. Traced `CachedEntries` prevent apply-thread batches from being freed until the full traced range is persisted and compacted. `update_cache_persisted` is called from peer persistence paths to advance this gate. `clear` resets entry and term caches without changing raft/apply state. Metrics and memory accounting are updated through `MEMTRACE_ENTRY_CACHE`, `RAFT_ENTRIES_CACHES_GAUGE`, `RAFT_ENTRY_FETCHES`, eviction bytes, task duration histograms, and warmup counters.

Dependencies and integration points: The module depends on `engine_traits::{KvEngine, RaftEngine}`, `kvproto` raft server protobuf state, raft-rs storage errors and `GetEntriesContext`, protobuf sizing, TiKV failpoints, local raft metrics, peer storage error helpers, `WriteTask`, and `ReadTask` scheduling. `PeerStorage` constructs it and forwards async fetch completions. Peer FSM code uses warmup completion and cache tracing when applying logs. Peer code updates persisted indexes after raft writes. Memory management code can call `evict_entry_cache`; log compaction calls `compact_entry_cache`.

Risks: Cache contiguity is enforced by panics on unexpected holes, so callers must append only valid raft-log sequences. Several paths assert cache and async-fetch invariants, including result low indexes and traced committed entries not overlapping uncommitted truncations. `term` unwraps a raft-engine read and panics if an expected entry is missing after range validation, treating this as data loss. Async fetch results can become invalid when low, high, size, or term expectations change; the retry and fallback logic limits stalls but must stay aligned with read worker behavior. Warmup intentionally skips compaction until election timeout to avoid invalidating prefetched ranges, which can temporarily retain more memory. Memory accounting is subtle because it includes entry data/context capacity, `VecDeque` capacity, traced batches, shrinking, and dangle entries.

Test signals: The tests cover memory size accounting across append, prepend, overlap rewrite, trace, compaction, and drop; entry lookup and out-of-range panic; term-cache normal and abnormal ordering; async fetch behavior for compacted errors, partial size-limited results, exact hits, smaller high, larger high retries, low mismatches, max retry fallback, and term changes; append truncation and direct append; mixed cache and raft-engine fetch with size and range limits; cache rewrite and persisted-index compaction; warmup task range selection and fetched-result prepend; and eviction of traced cached entries only after their persisted index permits freeing.

# sources/storage-engines/tikv/components/raftstore/src/store/fail_fast.rs

Purpose: This file implements raftstore disk hang fail-fast monitoring. It targets the "zombie" failure mode where TiKV is still alive and may hold raft leadership, but critical disk IO has stopped making progress. The monitor periodically probes raft and optional kv disks and panics the process when configured timeout rules indicate disk unavailability.

Important APIs and types: `DiskKind` distinguishes raft and kv probes and defines metric labels plus probe filenames. `DISK_PROBE_DURATION_HISTOGRAM` records probe durations by disk and outcome. `fail_fast_timeout` maps `Config::disk_hang_timeout` to an enabled timeout, treating `None` and `0s` as disabled. `run_probe` executes one non-overlapping `ProbeRunner` probe and records success or failure. `spawn_probe_thread` creates the blocking probe loop. `should_fail_fast` evaluates timeout, repeated-failure, and recent-progress veto rules. `FailFastMonitor::new` wires probes, checker worker, and progress timestamps together; `stop`, `try_join_probe_thread`, and `cleanup_probe_file` handle shutdown cleanup.

Control flow: `FailFastMonitor::new` creates a raft `ProbeRunner`, optionally a kv `ProbeRunner`, starts a dedicated `fail-fast-probe` thread, and registers an interval task on a checker `Worker`. The probe thread sleeps when fail-fast is disabled, otherwise alternates raft then kv `write + sync_all` probes once per second. The checker worker independently reads probe state once per second. For each configured disk, `should_fail_fast` first emits a stuck critical-error signal when an in-flight probe has exceeded half the timeout, then builds the base fail-fast signal from either an in-flight probe exceeding the timeout or repeated completed probe failures for a full timeout window after a prior success. A recent successful real sync-backed progress timestamp on the same disk vetoes the base signal. Without a veto, it increments the fail-fast critical-error metric, logs a critical message, and the checker panics after a best-effort async logger flush.

State and persistence behavior: Runtime state includes the stop flag, two probe runners, optional probe thread handle and exit receiver, and external atomics containing last successful raft append and kv sync times in monotonic milliseconds. Persistent state is limited to temporary probe files under the provided raft and kv directories. `stop` sets the flag, waits briefly for the probe thread to exit, joins if possible, and removes probe files. `Drop` also tries to remove probe files, but it does not join the probe thread.

Dependencies and integration points: The module consumes `Config` through `VersionTrack`, uses `disk_probe::ProbeRunner`, records Prometheus histograms, updates `tikv_util::metrics::CRITICAL_ERROR`, uses TiKV logging and panic-after-flush support, and is constructed from raftstore FSM store setup with raft and kv progress atomics. Async raft write code updates `last_raft_append_success_at_millis`; apply and write paths update `last_kv_sync_success_at_millis`, giving the monitor real IO progress signals that can veto a bad direct probe.

Risks: The dedicated probe thread can itself block indefinitely inside `sync_all`; the checker worker is therefore the critical fail-fast decision maker and must remain independent. Recent-progress vetoes reduce false positives but can delay fail-fast if unrelated sync-backed IO continues to succeed while the probe file path is unhealthy or mislocated. `stop` only joins if the probe loop sends its exit signal within two seconds, so a hung probe may survive shutdown until process exit. Fail-fast is disabled when `disk_hang_timeout` is `None` or zero, so config validation and operational guidance are important. Probe files are cleaned best-effort; removal failures are warnings unless the file is absent.

Test signals: Tests verify direct raft and kv probe writes, disabled timeout behavior for `None`, fail-fast on an in-flight probe exceeding timeout, fail-fast on repeated failures after a prior success, raft progress veto behavior for recent versus stale append timestamps, and kv sync veto behavior for recent versus stale kv timestamps. These tests exercise the core decision logic without spawning a full monitor panic path.
