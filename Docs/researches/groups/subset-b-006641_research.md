# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/cascadelakex/clx-metrics.json

Purpose: Defines 284 Cascade Lake Xeon derived perf metrics for `perf stat -M`, `perf list --metrics`, Python perf bindings, and metric validation. The file is data rather than executable code, but it is part of perf's PMU API: `tools/perf/pmu-events/jevents.py` parses each object, compiles `MetricExpr` with `metric.ParsePerfJson(...).Simplify()`, and emits compact C tables that the perf PMU and metricgroup code consume at runtime.

Important schema and APIs: Entries use `MetricName`, `MetricExpr`, `BriefDescription`, optional `PublicDescription`, `MetricGroup`, `ScaleUnit`, `MetricThreshold`, `MetricConstraint`, and `MetricgroupNoGroup`. `MetricGroup` tags place metrics in top-down analysis groups such as `TopdownL1` through `TopdownL6`, `Backend`, `Frontend`, `MemoryBW`, `Power`, `HPC`, `Flops`, `SoC`, and `smi`. `ScaleUnit` controls presentation and includes percent, GHz, MB/s, per-instruction, ns, SMI count, transaction cycles, and elision cycles. `MetricConstraint` values such as `NO_GROUP_EVENTS` and `NO_GROUP_EVENTS_NMI` are converted by jevents to grouping constraints used when perf schedules counters.

Metric coverage and dependencies: The file mixes high-level system metrics, legacy ratios, and Top-Down Microarchitecture Analysis formulas. It depends on core events like `INST_RETIRED.ANY`, `CPU_CLK_UNHALTED.*`, `IDQ.*`, `IDQ_UOPS_NOT_DELIVERED.*`, `FP_ARITH_INST_RETIRED.*`, `FRONTEND_RETIRED.*`, memory events such as `MEM_LOAD_RETIRED.*`, `MEM_LOAD_L3_MISS_RETIRED.*`, `CYCLE_ACTIVITY.*`, offcore/CHA/iMC/IIO/UPI uncore events, MSR aliases such as `msr@tsc@`, `msr@aperf@`, and `msr@smi@`, cstate aliases, power events, and perf expression variables including `duration_time`, `#num_packages`, `#num_dies`, `#has_pmem`, `#SMT_on`, and `source_count(...)`.

Control flow: During the build, jevents walks the x86 PMU event tree, reads this JSON, validates/parses metric expressions, preserves thresholds as strings, and writes generated pmu-event tables. At runtime, perf resolves a user's selected metrics to the referenced event aliases, expands grouping constraints, schedules the events, evaluates expressions over measured counts and built-in runtime variables, applies `ScaleUnit`, and uses `MetricThreshold` to annotate bottlenecks in supported output paths.

State and persistence behavior: There is no mutable runtime state in the JSON. Its persisted state is the generated perf event table plus the metric names and grouping labels exposed to users. Metric names are effectively a user-facing compatibility surface because scripts may call `perf stat -M tma_frontend_bound`, `tma_info_system_gflops`, `memory_bandwidth_read`, or similar names directly.

Integration points: This file ties directly to the sibling Cascade Lake event files because many formulas reference events defined in `frontend.json`, `floating-point.json`, memory/cache/offcore/uncore JSON files, and common architectural aliases. It also integrates with `tools/perf/tests/parse-metric.c`, `tools/perf/tests/pmu-events.c`, `tools/perf/tests/shell/lib/perf_metric_validation.py`, `tools/perf/python/ilist.py`, and `tools/perf/util/python.c` through generated `pmu-events` structures.

Risks: Metric formulas are highly sensitive to event spelling, raw event encodings, uncore PMU naming, and expression parser syntax. Several formulas divide by event counts such as retired instructions, DSB misses, cache misses, or memory inserts; idle or tiny workloads can produce zero or unstable denominators. Some system metrics depend on optional hardware state like persistent memory, SMT, RAPL, cstates, and uncore PMUs. Scheduling constraints are important because a single metric can reference many core and uncore events; dropping `NO_GROUP_EVENTS(_NMI)` where required can cause multiplexing or NMI watchdog conflicts, while overusing it can make metrics less comparable. Threshold expressions are not parsed the same way as metric expressions in jevents, so syntax errors may survive build-time parsing.

Test signals: Run `tools/perf/pmu-events/jevents.py` or the normal perf build to catch JSON and expression parse failures. Use `perf test pmu-events` and `perf test parse-metric` for generated-table coverage. Runtime smoke tests should include `perf list --metrics`, `perf stat -M tma_frontend_bound,tma_backend_bound,tma_info_system_gflops`, cstate/power metrics, and uncore bandwidth metrics on Cascade Lake-like hardware. Metric validation should watch for missing aliases, unexpected event multiplexing, divide-by-zero/NaN output, PMM-conditional paths when `#has_pmem` is false, and thresholds that fail to trigger on synthetic bottleneck workloads.

# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/cascadelakex/counter.json

Purpose: Declares the number of fixed and programmable counters available for Cascade Lake Xeon PMU units. This is capacity metadata consumed by the perf pmu-events generator and runtime tooling so perf can describe and schedule events for core and uncore units accurately.

Important schema and entries: The file contains 10 objects with `Unit`, `CountersNumFixed`, and `CountersNumGeneric`. The `core` unit reports 3 fixed counters and 4 generic counters. Uncore units report no fixed counters except `iMC` and `UBOX`, each with 1 fixed counter. Generic counter counts are `CHA=4`, `IIO=4`, `IRP=2`, `UPI=4`, `M2M=4`, `iMC=4`, `M3UPI=3`, `PCU=4`, and `UBOX=2`.

Control flow: Build-time traversal treats this as PMU metadata alongside event and metric files. Runtime perf uses the generated PMU descriptions with kernel-exposed PMUs to reason about which events can be placed together and how many counters are available for a unit, especially when metrics combine core events with CHA, iMC, IIO, UPI, PCU, UBOX, M2M, IRP, or M3UPI events.

State and persistence behavior: The file has no mutable state and no event aliases. Its persisted effect is the generated counter-capacity table. Changes affect scheduling behavior and user-visible PMU information even though no `EventName` or `MetricName` is introduced.

Dependencies and integration: The unit names must match the `Unit` values used in sibling uncore event JSON files and the PMU naming/mapping logic in `jevents.py` and perf's PMU discovery code. It also indirectly supports `clx-metrics.json` formulas that rely on uncore bandwidth, latency, and socket-level metrics because those formulas can require several events from the same unit in one run.

Risks: Incorrect counter counts cause practical scheduling bugs rather than parser failures. Overstating generic counters can make perf attempt impossible event groups; understating them can force unnecessary multiplexing or rejected metric groups. Unit spelling is a contract: if it drifts from event files or kernel PMU names, generated metadata may not attach to the intended PMU. Fixed-counter declarations for `iMC` and `UBOX` are especially easy to overlook because most uncore units list zero fixed counters.

Test signals: Validate JSON parsing and generated table output through a perf build and `perf test pmu-events`. On Cascade Lake hardware, check `perf list` for expected core and uncore PMUs, run multi-event groups near each unit's counter limit, and compare behavior for CHA/IIO/UPI/iMC/UBOX events against kernel PMU capabilities. Metric smoke tests that use uncore-heavy formulas from `clx-metrics.json` can expose bad capacity metadata through scheduling failures or unexpected multiplexing.

# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/cascadelakex/floating-point.json

Purpose: Defines Cascade Lake core floating-point arithmetic and FP assist event aliases used directly by perf users and indirectly by FLOPS, instruction-mix, and TMA metrics. The file is PMU metadata consumed by jevents and emitted into generated perf event tables.

Important event definitions: The file contains 16 events. Most use event code `0xC7` (`FP_ARITH_INST_RETIRED`) with umasks for scalar double (`0x1`), scalar single (`0x2`), combined scalar (`0x3`), 128-bit packed double (`0x4`), 128-bit packed single (`0x8`), 256-bit packed double (`0x10`), 256-bit packed single (`0x20`), 512-bit packed double (`0x40`), 512-bit packed single (`0x80`), vector aggregate (`0xfc`), and derived `4_FLOPS`/`8_FLOPS` combinations. Three BF16 events use event code `0xCF` with umasks `0x20`, `0x40`, and `0x80`. `FP_ASSIST.ANY` uses event code `0xCA`, umask `0x1e`, and `CounterMask=1` to count cycles with SSE/x87 assists.

Control flow: Jevents lowercases `EventName`, converts `EventCode`, `UMask`, `Counter`, and `CounterMask` into perf event encodings, carries descriptions into generated tables, and marks no special PMU unit, so these are core CPU events. Runtime perf resolves aliases such as `FP_ARITH_INST_RETIRED.SCALAR` or raw expressions from `clx-metrics.json` into programmable core counter events, then metric expressions weight them to compute FLOP counts, arithmetic intensity, vector width mix, and top-down FP bottleneck classifications.

State and persistence behavior: There is no mutable state. The persistent API surface is the set of event aliases and their encodings/descriptions. The `Counter` field restricts all events to generic counters 0 through 3, which must align with `counter.json`'s core counter capacity.

Dependencies and integration: `clx-metrics.json` depends heavily on these aliases for `tma_fp_scalar`, `tma_fp_vector`, `tma_fp_vector_128b`, `tma_fp_vector_256b`, `tma_fp_vector_512b`, `tma_info_core_flopc`, `tma_info_system_gflops`, and several instruction-mix metrics. The events also integrate with perf list, stat, Python metric export, and shell metric validation. Their descriptions encode hardware semantics such as DAZ/FTZ assumptions and double-counting of DPP/FMA-style operations.

Risks: The BF16 public descriptions say these events are only supported on Cooper Lake and not Cascade Lake; keeping them in the Cascade Lake directory may be intentional for shared CLX/CPX support but is a compatibility trap for tests on pure Cascade Lake hardware. Several event descriptions differ subtly from the alias names for BF16 widths, so reviewers should validate against Intel event tables before changing them. FLOP metrics depend on correct weighting and on the note that some instructions count twice; treating instruction counts as operation counts without the documented multipliers produces wrong GFLOPS. `FP_ASSIST.ANY` counts cycles, not retired instructions, so using it in ratios with instruction events needs clear units.

Test signals: Build-time JSON/jevents parsing should pass. Runtime smoke tests should run `perf stat -e FP_ARITH_INST_RETIRED.SCALAR,FP_ARITH_INST_RETIRED.512B_PACKED_SINGLE,FP_ASSIST.ANY` on FP-heavy and scalar workloads, plus `perf stat -M tma_info_system_gflops,tma_fp_vector_512b`. Validation should check that all aliases schedule on core generic counters, that BF16 aliases fail gracefully or read zero on unsupported Cascade Lake hardware, and that metric output remains sensible with DAZ/FTZ-sensitive workloads.

# sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/cascadelakex/frontend.json

Purpose: Defines Cascade Lake front-end PMU event aliases covering branch resteers, decode stalls, DSB-to-MITE switches, front-end retired latency attribution, instruction cache/tag behavior, IDQ delivery paths, microcode sequencer activity, and uop delivery shortfall. These aliases feed both direct perf event selection and `clx-metrics.json` top-down frontend metrics.

Important event definitions: The file contains 49 events. Major groups include `BACLEARS.ANY` (`0xE6/0x1`), `DECODE.LCP` (`0x87/0x1`), `DSB2MITE_SWITCHES.*` (`0xAB` with umasks `0x1` and `0x2`), `FRONTEND_RETIRED.*` (`0xC6/0x1`) using `MSRIndex=0x3F7` and different `MSRValue` selectors, `ICACHE_16B.IFDATA_STALL`, `ICACHE_64B.IFTAG_*`, `ICACHE_TAG.STALLS`, IDQ source events under event code `0x79`, and `IDQ_UOPS_NOT_DELIVERED.*` under event code `0x9C`. Some aliases use `CounterMask` to count cycles meeting a threshold, and selected aliases use `Invert` or `EdgeDetect` for event qualification.

Control flow: Jevents parses the JSON fields into generated perf encodings. For these events, `MSRIndex` and `MSRValue` are important because `FRONTEND_RETIRED.*` variants share the architectural event selector but program an auxiliary MSR to choose a precise front-end retirement classification. At runtime, perf alias resolution maps names to CPU PMU events, applies cmask/edge/invert/MSR qualifiers, and metric evaluation uses their counts to compute fetch bandwidth, fetch latency, DSB/MITE/MS utilization, icache miss latency, unknown branch rate, and top-down frontend bottleneck leaves.

State and persistence behavior: The JSON has no mutable state, but some event selections imply hardware PMU programming state beyond the event select register, especially the shared `0x3F7` MSR for `FRONTEND_RETIRED.*`. The generated event aliases persist as user-facing names and as dependencies for top-down metric formulas. All listed events target generic core counters 0 through 3.

Dependencies and integration: `clx-metrics.json` references these aliases in metrics such as `percent_uops_delivered_from_decoded_icache`, `percent_uops_delivered_from_legacy_decode_pipeline`, `tma_frontend_bound`, `tma_fetch_latency`, `tma_dsb`, `tma_mite`, `tma_dsb_switches`, `tma_lcp`, `tma_icache_misses`, `tma_itlb_misses`, `tma_info_frontend_*`, and `tma_unknown_branches`. The aliases must line up with perf's MSR lookup/programming support in jevents, kernel CPU PMU constraints, and tests that compare generated pmu-events tables.

Risks: Shared encodings with different cmask, invert, edge, or MSR values are easy to conflate. Case differs for one `FRONTEND_RETIRED.LATENCY_GE_1` event code (`0xc6`) while most use `0xC6`; parsers tolerate this, but consistency checks may flag it. Events marked as aliases, such as `ICACHE_TAG.STALLS` and `ICACHE_64B.IFTAG_STALL`, can double-count if users include both. The `FRONTEND_RETIRED.*` MSR selector state can conflict if perf incorrectly groups incompatible variants. Front-end metrics divide by slots, cycles, DSB miss counts, or branch clear counts, so very small samples can produce noisy or undefined ratios.

Test signals: Build and `perf test pmu-events` should validate encoding generation. Runtime tests should include direct events from each group, especially `FRONTEND_RETIRED.LATENCY_GE_*`, `IDQ_UOPS_NOT_DELIVERED.CORE`, `DSB2MITE_SWITCHES.PENALTY_CYCLES`, `ICACHE_TAG.STALLS`, and IDQ DSB/MITE/MS aliases. Metric smoke tests should run `perf stat -M tma_frontend_bound,tma_fetch_latency,tma_dsb,tma_mite,tma_lcp,tma_icache_misses` against workloads with large code footprints, branch-heavy behavior, and microcode-heavy instructions. Watch for MSR programming conflicts, unsupported precise/front-end-retired variants, and unexpected multiplexing when grouped with other Topdown metrics.
