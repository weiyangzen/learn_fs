# sources/cloud-native/buildkit/frontend/gateway/pb/gateway.pb.go

## Purpose

`gateway.pb.go` is generated by `protoc-gen-go` from `frontend/gateway/pb/gateway.proto`. It defines the Go protobuf message, enum, oneof, descriptor, reflection, and accessor surface for BuildKit's frontend gateway protocol in package `moby_buildkit_v1_frontend`. The file is data-contract code rather than business logic: it serializes and reflects the request/response payloads used by the `LLBBridge` gRPC service implemented in the sibling generated gRPC file.

The generated code pins protobuf runtime compatibility with `protoimpl.EnforceVersion`, exposes `File_github_com_moby_buildkit_frontend_gateway_pb_gateway_proto` as the package-level `protoreflect.FileDescriptor`, and builds that descriptor from a raw schema string during package initialization. It imports BuildKit solver definitions, worker records, source policies, API capability records, fsutil stats, protobuf timestamps, and google RPC status messages, making this file the central typed bridge between frontend clients and the BuildKit solver/control plane.

## Important APIs, Types, and Functions

The top-level enums are `AttestationKind`, `InTotoSubjectKind`, and `ChecksumRequest_ChecksumAlgo`. Each has generated `Enum`, `String`, `Descriptor`, `Type`, `Number`, and deprecated `EnumDescriptor` methods. `AttestationKind` distinguishes `InToto` from `Bundle`, `InTotoSubjectKind` distinguishes `Self` from `Raw`, and checksum algorithms cover SHA-256, SHA-384, and SHA-512.

Result and reference types define the main solve return model:

- `Result` contains a `oneof` named `Result` with legacy `RefDeprecated` and `RefsDeprecated` variants plus current `Ref` and `Refs` variants, a `Metadata` map, and an `Attestations` map keyed by string.
- `Ref` carries a reference `Id` and optional `*pb.Definition`, allowing a result ref to point back to an LLB definition.
- `RefMapDeprecated` maps names to string refs, while `RefMap` maps names to structured `*Ref`.
- `Attestations`, `Attestation`, and `InTotoSubject` model provenance and bundle metadata attached to results.

Frontend gateway operation payloads include:

- `ReturnRequest` and `ReturnResponse` for returning a final `Result` or a `google.rpc.Status` error from a frontend.
- `InputsRequest` and `InputsResponse`, where `InputsResponse.Definitions` is a map of named frontend input `*pb.Definition` values.
- `ResolveImageConfigRequest/Response`, carrying image reference, platform, resolve mode, logging name, resolver/session/store identifiers, source policies, digest, config bytes, and resolved reference.
- `ResolveSourceMetaRequest/Response`, with typed subrequests/subresponses for Git, image, and HTTP metadata resolution.
- `ResolveSourceImageRequest/Response`, `AttestationChain`, `Blob`, and `Descriptor`, supporting image config, attestations, manifest digests, blob data, descriptor metadata, and OCI-style annotations.
- `ResolveSourceGitRequest/Response`, supporting checksum, ref, commit checksum, and optional commit/tag object bytes.
- `ResolveSourceHTTPRequest/Response`, `ChecksumRequest`, and `ChecksumResponse`, supporting HTTP source metadata, last-modified timestamps, and checksum suffix handling.

Solve and filesystem payloads include:

- `SolveRequest` with `Definition`, `Frontend`, `FrontendOpt`, deprecated result-return switches, `Final`, `ExporterAttr`, `CacheImports`, `FrontendInputs`, `Evaluate`, and `SourcePolicies`.
- `CacheOptionsEntry`, matching BuildKit control cache import entries with `Type` and `Attrs`.
- `SolveResponse`, with deprecated `Ref` and current `Result`.
- `ReadFileRequest`, `FileRange`, `ReadFileResponse`, `ReadDirRequest`, `ReadDirResponse`, `StatFileRequest`, and `StatFileResponse`, used for gateway filesystem inspection against refs or container mounts.
- `EvaluateRequest/Response`, `PingRequest`, and `PongResponse`, where `PongResponse` advertises frontend API caps, LLB caps, and available workers.
- `WarnRequest/Response`, used to pass diagnostic warnings with digest, level, short/detail byte messages, URL, source info, and ranges.

Container execution payloads include:

- `NewContainerRequest/Response` and `ReleaseContainerRequest/Response`, carrying container IDs, mounts, network mode, platform, worker constraints, extra hosts, and hostname.
- `ExecMessage`, a stream message with a `ProcessID` and an `Input` oneof. Variants are `Init`, `File`, `Resize`, `Started`, `Exit`, `Done`, and `Signal`.
- `InitMessage` carries container ID, process metadata, file descriptors, TTY flag, security mode, and secret environment entries.
- `FdMessage`, `ResizeMessage`, `SignalMessage`, `StartedMessage`, `ExitMessage`, and `DoneMessage` implement the stream-level execution protocol.

Every message has generated `Reset`, `String`, `ProtoMessage`, `ProtoReflect`, deprecated `Descriptor`, and field `Get...` methods. Getter methods are nil-safe and return proto defaults such as empty string, zero, `false`, `nil`, or the first enum value.

## Control Flow

There is no handwritten control flow. Runtime behavior is generated protobuf plumbing:

1. Package initialization calls `file_github_com_moby_buildkit_frontend_gateway_pb_gateway_proto_init()`.
2. The initializer returns early if the file descriptor already exists.
3. It registers oneof wrappers for `Result` and `ExecMessage`.
4. It builds a `protoimpl.TypeBuilder` with the raw descriptor, Go type list, dependency indexes, enum metadata, and message metadata.
5. It assigns the resulting file descriptor to `File_github_com_moby_buildkit_frontend_gateway_pb_gateway_proto` and clears raw Go type/dependency slices to reduce retained state.

Per-message `ProtoReflect` methods lazily store message info in the protobuf runtime message state when needed. Getter control flow is consistently defensive: check receiver nil, inspect oneof concrete type when applicable, and return a default if the field is absent.

## State and Persistence Behavior

The file stores no application state and performs no persistence. The only package-level mutable state is protobuf runtime descriptor/cache state: raw descriptor compression via `sync.Once`, enum/message info arrays, the file descriptor, and temporary Go type/dependency slices that are nulled after initialization. Message structs can contain in-memory maps and byte slices, but serialization and persistence are left to callers and the protobuf/gRPC runtime.

Several payloads represent external state handled elsewhere: result refs, LLB definitions, image digests/configs, source metadata, cache imports, container IDs, worker records, file stats, and process I/O. This generated file does not validate or resolve any of those values.

## Dependencies and Integration Points

Key dependencies are:

- `github.com/moby/buildkit/solver/pb` for LLB definitions, platforms, source ops, source info/ranges, mounts, process metadata, network/security modes, constraints, host mappings, and secret environment data.
- `github.com/moby/buildkit/api/types` for worker records exposed by `PongResponse`.
- `github.com/moby/buildkit/sourcepolicy/pb` for source policy lists in resolution and solve requests.
- `github.com/moby/buildkit/util/apicaps/pb` for advertised API capabilities.
- `github.com/tonistiigi/fsutil/types` for directory and stat responses.
- `google.golang.org/protobuf` runtime/reflection packages for generated message behavior.
- `google.golang.org/genproto/googleapis/rpc/status` and `google.golang.org/protobuf/types/known/timestamppb` for structured errors and HTTP source timestamps.

The immediate integration partner is `gateway_grpc.pb.go`, which uses these message types as RPC inputs and outputs. Handwritten BuildKit gateway client/server code should depend on the generated types rather than constructing wire payloads manually.

## Risks and Edge Cases

The largest compatibility risk is schema evolution. Field numbers encode wire compatibility, and the schema already contains deprecated fields and removed/reserved slots (`Result` legacy refs, `SolveRequest` field 4 removed, old attestation field 11 reserved by comment, deprecated `SolveResponse.ref`). Changing numbers or reusing retired numbers would break old clients.

Generated getters can hide absent values by returning zero defaults. Callers that must distinguish unset from explicitly set zero need to inspect the field or pointer directly rather than relying on getters. Map and slice fields may be nil when absent, so callers should handle nil maps before writes.

The `Result` and `ExecMessage` oneofs require type-specific handling. A caller that assumes only current `Ref`/`Refs` variants, or only one exec stream direction for `FdMessage`, can mishandle older peers or bidirectional stream semantics.

Byte fields may carry large configs, blobs, git object bytes, diagnostics, file content, and process I/O. This file imposes no size limits; memory pressure and gRPC message limits must be enforced by callers or server configuration.

Because this file is generated, manual edits are fragile and will be overwritten by regeneration. Semantic changes should be made in `gateway.proto` and regenerated with matching tool versions.

## Test Signals

Useful test signals are primarily integration and compatibility based:

- Regenerate `gateway.pb.go` from `gateway.proto` and verify the checked-in generated output is clean.
- Compile packages importing this generated package to catch protobuf runtime or dependency drift.
- Round-trip marshal/unmarshal messages containing oneof variants, maps, nested BuildKit `pb.Definition` values, source policies, file stats, timestamps, and status errors.
- Exercise old and new solve result fields to ensure deprecated compatibility remains intact.
- Run gateway gRPC integration tests that call solve, resolve, filesystem, warning, container, and exec-stream paths using these payload types.

# sources/cloud-native/buildkit/frontend/gateway/pb/gateway.proto

## Purpose

`gateway.proto` is the authoritative protobuf schema for BuildKit's frontend gateway bridge, package `moby.buildkit.v1.frontend`. It defines the `LLBBridge` service that frontends use to ask BuildKit to resolve image/source metadata, solve LLB graphs, inspect refs or containers, exchange frontend inputs, report final results, create/release execution containers, run bidirectional process streams, and emit warnings.

The Go package option maps generated code to `github.com/moby/buildkit/frontend/gateway/pb` with Go package name `moby_buildkit_v1_frontend`. The schema imports BuildKit solver, worker, source policy, API capability, fsutil stat, timestamp, and RPC status definitions, so it is a compact but high-impact contract between gateway clients, BuildKit workers, and solver internals.

## Important APIs, Types, and RPCs

The single service, `LLBBridge`, exposes these unary RPCs:

- `ResolveImageConfig`, gated by `apicaps:CapResolveImage`, resolves image config/digest/reference for a ref, platform, mode, resolver type, session/store, and source policies.
- `ResolveSourceMeta`, gated by `apicaps:CapSourceMetaResolver`, resolves typed metadata for image, Git, and HTTP sources.
- `Solve`, gated by `apicaps:CapSolveBase`, asks the bridge to solve an LLB definition or nested frontend.
- `ReadFile`, `ReadDir`, and `StatFile`, gated by read/stat caps, inspect filesystem content behind refs.
- `Evaluate`, gated by `apicaps:CapGatewayEvaluate`, forces evaluation of a ref.
- `Ping`, `Return`, and `Inputs` provide liveness/capability discovery, final result/error reporting, and frontend input discovery.
- `NewContainer` and `ReleaseContainer` manage gateway execution containers.
- `ReadFileContainer`, `ReadDirContainer`, and `StatFileContainer`, gated by `apicaps:CapGatewayExecFilesystem`, inspect container-mounted filesystems.
- `Warn`, gated by `apicaps:CapGatewayWarnings`, emits structured source-linked warnings.

The only streaming RPC is `ExecProcess(stream ExecMessage) returns (stream ExecMessage)`, a bidirectional process-control and I/O stream.

Important message groups:

- Result messages: `Result`, `RefMapDeprecated`, `Ref`, `RefMap`, `Attestations`, `Attestation`, `AttestationKind`, `InTotoSubject`, and `InTotoSubjectKind`.
- Source resolution messages: `ResolveImageConfigRequest/Response`, `ResolveSourceMetaRequest/Response`, `ResolveSourceImageRequest/Response`, `ResolveSourceGitRequest/Response`, `ResolveSourceHTTPRequest/Response`, `AttestationChain`, `Blob`, `Descriptor`, `ChecksumRequest`, and `ChecksumResponse`.
- Solve messages: `SolveRequest`, `CacheOptionsEntry`, and `SolveResponse`.
- Filesystem messages: `ReadFileRequest`, `FileRange`, `ReadFileResponse`, `ReadDirRequest`, `ReadDirResponse`, `StatFileRequest`, and `StatFileResponse`.
- Execution messages: `NewContainerRequest/Response`, `ReleaseContainerRequest/Response`, `ExecMessage`, `InitMessage`, `ExitMessage`, `StartedMessage`, `DoneMessage`, `FdMessage`, `ResizeMessage`, and `SignalMessage`.
- Miscellaneous messages: `ReturnRequest/Response`, `InputsRequest/Response`, `EvaluateRequest/Response`, `PingRequest`, `PongResponse`, and `WarnRequest/Response`.

## Control Flow and Protocol Semantics

The schema defines protocol shape rather than implementation. Common flows implied by the messages are:

1. A frontend can call `Ping` to discover `FrontendAPICaps`, `LLBCaps`, and available `Workers`.
2. The frontend may call `Inputs` to retrieve named frontend input definitions.
3. It can call `ResolveImageConfig` or `ResolveSourceMeta` to normalize source metadata before constructing or solving LLB.
4. It calls `Solve` with an LLB `Definition`, nested `Frontend`, frontend options, cache imports, frontend input definitions, evaluation flag, and source policies.
5. The returned `SolveResponse` may expose a deprecated string ref or a structured `Result`; the result can carry refs, metadata, and attestations.
6. The frontend can inspect produced refs with `ReadFile`, `ReadDir`, `StatFile`, or trigger `Evaluate`.
7. For execution, the frontend creates a container, exchanges `ExecMessage` frames over `ExecProcess`, optionally inspects the container filesystem, then releases the container.
8. Completion is reported through `Return`, carrying either a result or a structured `google.rpc.Status` error.

The `ExecMessage` protocol is the most stateful: `InitMessage` starts a process; `FdMessage` is used in both directions for stdin/stdout/stderr bytes; `ResizeMessage` and `SignalMessage` carry terminal and signal events from client to server; `StartedMessage`, `ExitMessage`, and `DoneMessage` come from server to client. The schema explicitly notes that `FdMessage` may arrive after `ExitMessage`, and `DoneMessage` is the final message for a process.

## State and Persistence Behavior

The schema itself has no persistence, but it names durable or semi-durable concepts: refs, LLB definitions, image digests/config blobs, source checksums, cache import options, attestation chains, blob descriptors, container IDs, worker records, and diagnostic source ranges. Those values are interpreted and persisted by BuildKit subsystems outside this file.

Compatibility state is encoded in field numbering and comments. `Result` keeps deprecated non-array refs at fields 1 and 2, current structured refs at 3 and 4, metadata at 10, and attestations at 12, while field 11 is reserved by comment for an old attestation format. `SolveRequest` notes field 4 was removed in BuildKit v0.11.0, keeps result-return flags at 5 and 6, has a deprecated inline-return-related `Final` field at 10, and includes cache imports and frontend inputs behind capability comments.

## Dependencies and Integration Points

Imported schemas are central to the integration:

- `github.com/moby/buildkit/solver/pb/ops.proto` supplies `pb.Definition`, `pb.Platform`, `pb.SourceOp`, `pb.Mount`, `pb.Meta`, `pb.SecurityMode`, source ranges, network mode, worker constraints, host IPs, and secret env structures.
- `github.com/moby/buildkit/api/types/worker.proto` supplies worker records in `PongResponse`.
- `github.com/moby/buildkit/sourcepolicy/pb/policy.proto` supplies source policy controls in resolution and solve requests.
- `github.com/moby/buildkit/util/apicaps/pb/caps.proto` supplies advertised capability records.
- `github.com/tonistiigi/fsutil/types/stat.proto` supplies file stat responses.
- `google/protobuf/timestamp.proto` and `google/rpc/status.proto` supply HTTP timestamps and structured errors.

Generated siblings `gateway.pb.go` and `gateway_grpc.pb.go` are direct outputs of this schema. Handwritten BuildKit bridge implementations, frontend clients, and tests should treat this proto as the compatibility source of truth.

## Risks and Edge Cases

Wire compatibility is the main risk. Deprecated and removed fields show that older peers exist or existed; reusing field numbers, changing oneof membership, changing map value types, or renaming service methods would create interop problems.

Capability comments are not enforced by protobuf. Runtime client/server code must check API capabilities before relying on fields or methods such as source metadata, cache imports, frontend inputs, gateway evaluation, container filesystem access, and warnings.

Several messages carry unbounded bytes: image configs, exporter attrs, git object bytes, checksum suffixes, file data, warning details, process I/O, and blobs. The schema does not define limits, chunking, or validation; the gRPC layer and BuildKit implementation must enforce resource limits.

`ExecMessage` multiplexes multiple message variants and process IDs over one bidirectional stream. Implementations need a clear state machine for process start, I/O, exit, done, signals, EOF, and terminal resize events, including the documented case where file data arrives after exit.

Some field names intentionally use uppercase names in proto (`Ref`, `Definition`, `FrontendOpt`, `ContainerID`) while others use lower-case names (`digest`, `media_type`, `hostname`). Generated JSON and Go names reflect these choices, so clients relying on JSON/proto reflection should not assume uniform casing.

## Test Signals

Important validation signals include:

- Regenerate Go outputs from this proto and assert the generated files match the repository.
- Run protobuf compatibility checks when changing field numbers, oneofs, enum values, or service methods.
- Exercise all capability-gated RPCs with peers that both do and do not advertise the relevant caps.
- Test solve result compatibility across deprecated string refs, deprecated ref maps, current `Ref`, current `RefMap`, metadata, and attestations.
- Test source resolution for image, Git, and HTTP variants, including checksum algorithms and timestamps.
- Test `ExecProcess` bidirectional stream ordering, EOF, exit/error status, done finality, resize, signal handling, and multi-process `ProcessID` separation.

# sources/cloud-native/buildkit/frontend/gateway/pb/gateway_grpc.pb.go

## Purpose

`gateway_grpc.pb.go` is generated by `protoc-gen-go-grpc` from `gateway.proto`. It defines the Go gRPC client interface, server interface, default unimplemented server, registration helper, unary handlers, bidirectional stream handler, and `grpc.ServiceDesc` for the BuildKit frontend gateway `LLBBridge` service.

The file is transport glue, not BuildKit business logic. It binds the generated protobuf message types from `gateway.pb.go` to method names such as `/moby.buildkit.v1.frontend.LLBBridge/Solve` and exposes the code that gRPC uses to invoke handwritten BuildKit server implementations.

## Important APIs, Types, and Functions

The file declares full method name constants for all 17 RPCs:

- Unary: `ResolveImageConfig`, `ResolveSourceMeta`, `Solve`, `ReadFile`, `ReadDir`, `StatFile`, `Evaluate`, `Ping`, `Return`, `Inputs`, `NewContainer`, `ReleaseContainer`, `ReadFileContainer`, `ReadDirContainer`, `StatFileContainer`, and `Warn`.
- Bidirectional streaming: `ExecProcess`.

Client-side APIs:

- `LLBBridgeClient` is the public client interface. Each unary method takes `context.Context`, a typed request pointer, and optional `grpc.CallOption`s, and returns a typed response pointer plus error. `ExecProcess` takes context and call options and returns `grpc.BidiStreamingClient[ExecMessage, ExecMessage]`.
- `NewLLBBridgeClient(cc grpc.ClientConnInterface)` constructs a private `lLBBridgeClient`.
- Each unary client method prepends `grpc.StaticMethod()` to call options, allocates the output type, and calls `cc.Invoke` with the full method name.
- `ExecProcess` calls `cc.NewStream` with `LLBBridge_ServiceDesc.Streams[0]`, wraps it in `grpc.GenericClientStream[ExecMessage, ExecMessage]`, and returns it.
- `LLBBridge_ExecProcessClient` is a backwards-compatible alias for the generic bidirectional streaming client type.

Server-side APIs:

- `LLBBridgeServer` is the interface server implementations must satisfy. It mirrors the proto service and requires all unary methods plus `ExecProcess(grpc.BidiStreamingServer[ExecMessage, ExecMessage]) error`.
- `UnimplementedLLBBridgeServer` provides default methods returning `codes.Unimplemented` errors and should be embedded by value for forward compatibility.
- `UnsafeLLBBridgeServer` can be embedded to opt out of forward compatibility, at the cost of compile errors when service methods are added.
- `RegisterLLBBridgeServer(s grpc.ServiceRegistrar, srv LLBBridgeServer)` validates that embedded unimplemented servers are not nil pointers when detectable, then calls `s.RegisterService`.
- `LLBBridge_ExecProcessServer` is a backwards-compatible alias for the generic bidirectional streaming server type.

Handler and descriptor APIs:

- `_LLBBridge_<Method>_Handler` functions decode incoming unary requests, invoke the implementation directly if no interceptor is configured, or call the interceptor with a `grpc.UnaryServerInfo` and typed handler closure.
- `_LLBBridge_ExecProcess_Handler` wraps `grpc.ServerStream` in `grpc.GenericServerStream[ExecMessage, ExecMessage]` before calling the server implementation.
- `LLBBridge_ServiceDesc` contains service name, handler type, all unary method descriptors, the `ExecProcess` stream descriptor, and proto metadata path.

The generated code asserts compatibility with gRPC-Go v1.64.0 or later using `const _ = grpc.SupportPackageIsVersion9`.

## Control Flow

Unary client flow is uniform:

1. Append `grpc.StaticMethod()` to caller-provided options.
2. Allocate an output response struct.
3. Invoke `ClientConnInterface.Invoke(ctx, FullMethodName, in, out, opts...)`.
4. Return nil plus error on transport/RPC failure, otherwise return the populated output.

Streaming client flow for `ExecProcess`:

1. Append `grpc.StaticMethod()`.
2. Create a stream using the first stream descriptor in `LLBBridge_ServiceDesc`.
3. Wrap the raw client stream as `grpc.GenericClientStream[ExecMessage, ExecMessage]`.
4. Return the typed bidirectional stream to the caller.

Unary server handler flow is also uniform:

1. Allocate the request message.
2. Decode the incoming payload through the provided decoder.
3. If there is no unary interceptor, type-assert the server to `LLBBridgeServer` and call the target method.
4. If there is an interceptor, build `grpc.UnaryServerInfo`, create a closure that type-asserts the request, and call the interceptor.

Registration flow includes a defensive check: if the server exposes `testEmbeddedByValue`, `RegisterLLBBridgeServer` calls it before registration. The comment explains this catches a nil pointer embedding of `UnimplementedLLBBridgeServer` at initialization time instead of later during an RPC.

## State and Persistence Behavior

The file keeps no persistent state. The private client stores only a `grpc.ClientConnInterface`. Server state lives entirely in user-provided implementations. `LLBBridge_ServiceDesc` is immutable registration metadata, and method constants are static strings.

Runtime request/response state is transient and owned by gRPC calls and streams. Interceptors can add behavior such as logging, auth, tracing, metrics, retries, or validation, but this generated file does not implement those concerns.

## Dependencies and Integration Points

Key dependencies are:

- `context` for request scoping and cancellation.
- `google.golang.org/grpc` for client connections, call options, static method options, service registration, unary interceptors, generic streaming wrappers, and descriptors.
- `google.golang.org/grpc/codes` and `google.golang.org/grpc/status` for default unimplemented errors.
- Message types generated in `gateway.pb.go`.

This file integrates with:

- BuildKit frontend gateway client code through `NewLLBBridgeClient`.
- BuildKit bridge server implementations through `LLBBridgeServer` and `RegisterLLBBridgeServer`.
- gRPC middleware through the generated unary handler interceptor path.
- The `ExecProcess` stream state machine implemented by handwritten code using typed generic streams.

## Risks and Edge Cases

Forward compatibility depends on embedding `UnimplementedLLBBridgeServer` by value. Embedding by pointer can panic if future methods are invoked; the registration helper attempts to catch this for implementations exposing the generated test method.

All generated handlers type-assert `srv.(LLBBridgeServer)` and requests to exact pointer types. Passing the wrong server object or using a malformed manually wired descriptor would panic. Normal `RegisterLLBBridgeServer` usage avoids this.

`ExecProcess` assumes `LLBBridge_ServiceDesc.Streams[0]` is the `ExecProcess` descriptor. This is generated consistently from the proto, but manual modification would be dangerous.

The generated client prepends `grpc.StaticMethod()` to options. Callers that depend on dynamic method behavior or custom call option ordering should be aware that this option is always inserted before their options.

The file does not enforce API capability comments. A client can call any generated method; server implementations must reject unsupported features or coordinate with `Ping` capability data.

Manual edits are risky because regeneration will overwrite them. Changes should be made in `gateway.proto` and regenerated with matching `protoc-gen-go-grpc` and gRPC-Go versions.
