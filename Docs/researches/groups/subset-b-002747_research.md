# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/lsdma/lsdma_6_0_0_offset.h

Purpose: this generated AMDGPU ASIC register header defines the LSDMA 6.0.0 MMIO register offsets for the `lsdma0_lsdma0dec` address block, whose documented block base is `0x45000`. It is a pure C preprocessor contract: every `regLSDMA_*` macro is a register offset consumed by SOC15 register access helpers, and every matching `regLSDMA_*_BASE_IDX` macro selects base index `0` for this block. The file does not implement behavior itself; it lets the IP-version-specific LSDMA driver address the correct hardware registers without hard-coded literals in runtime code.

Important APIs, types, and functions: there are no C functions or types. The exported surface is the macro set guarded by `_lsdma_6_0_0_OFFSET_HEADER`. Core public register families include ucode access (`regLSDMA_UCODE_ADDR`, `regLSDMA_UCODE_DATA`, `regLSDMA_UCODE_CHECKSUM`), error injection and logging (`regLSDMA_ERROR_INJECT_CNTL`, `regLSDMA_ERROR_INJECT_SELECT`, `regLSDMA_EDC_COUNTER`, `regLSDMA_EDC_COUNTER2`, `regLSDMA_ECC_CNTL`, `regLSDMA_ERROR_LOG`, `regLSDMA_EXCEPTION_STATUS`), status and debug registers (`regLSDMA_STATUS_REG` through `regLSDMA_STATUS4_REG`, `regLSDMA_F32_COUNTER`, public dummy registers), UTCL1 translation/cache registers (`regLSDMA_UTCL1_*`), PIO registers (`regLSDMA_PIO_SRC_ADDR_LO`, `regLSDMA_PIO_SRC_ADDR_HI`, `regLSDMA_PIO_DST_ADDR_LO`, `regLSDMA_PIO_DST_ADDR_HI`, `regLSDMA_PIO_COMMAND`, `regLSDMA_PIO_CONSTFILL_DATA`, `regLSDMA_PIO_CONTROL`, `regLSDMA_PIO_STATUS`, `regLSDMA_PF_PIO_STATUS`, `regLSDMA_VF_PIO_STATUS`), interrupt/power/control registers (`regLSDMA_INT_CNTL`, `regLSDMA_MEM_POWER_CTRL`, `regLSDMA_CLK_CTRL`, `regLSDMA_CNTL`, `regLSDMA_POWER_GATING`, `regLSDMA_PGFSM_*`, `regLSDMA_ULV_CNTL`), address configuration (`regLSDMA_GB_ADDR_CONFIG`, `regLSDMA_GB_ADDR_CONFIG_READ`), and two replicated queue register banks (`regLSDMA_QUEUE0_*`, `regLSDMA_QUEUE1_*`) for ring buffer, indirect buffer, doorbell, preempt, context, watermark, AQL, and mid-command state.

Control flow: the header has no executable control flow. Runtime flow is created by consumers such as `amdgpu/lsdma_v6_0.c`, which includes this file and calls `SOC15_REG_OFFSET(LSDMA, 0, regLSDMA_PIO_STATUS)` for polling, `WREG32_SOC15()` for programming PIO source/destination/control/command registers, `RREG32_SOC15()` for read-modify-write sequences, and `REG_SET_FIELD()` with the companion mask header. The critical flow enabled by these offsets is synchronous PIO copy/fill: write address registers, write `regLSDMA_PIO_CONTROL`, compose `regLSDMA_PIO_COMMAND`, then poll `regLSDMA_PIO_STATUS` until idle and FIFO-empty bits are observed.

State and persistence behavior: this file stores no software state. Its macros identify persistent hardware state in the LSDMA engine. Registers programmed through these offsets can retain queue pointers, command state, PIO addresses, power-gating settings, status bits, ECC/error logs, and performance counter configuration until reset or overwritten by the driver or firmware. The `_BASE_IDX` macros all use `0`, so multi-instance or alternate-base behavior is delegated to the SOC15 access layer rather than encoded here.

Dependencies and integration points: the file depends only on the C preprocessor and AMDGPU naming conventions, but it is tightly coupled to `lsdma_6_0_0_sh_mask.h` for bit-field definitions and to AMDGPU SOC15 access macros for base-address calculation. The direct in-tree integration point is `sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/lsdma_v6_0.c`, which includes this header with `lsdma_6_0_0_sh_mask.h` and exports callbacks through `struct amdgpu_lsdma_funcs`. It also aligns with common LSDMA helpers in `amdgpu_lsdma.c` and with generated register naming used throughout AMDGPU.

Risks and edge cases: offset errors are high impact because they can redirect MMIO reads/writes to the wrong hardware register. Version drift is a specific risk: LSDMA 7.0.0 moves PIO, interrupt, memory power, queue status, and queue context offsets relative to this 6.0.0 map, so sharing this header with the wrong IP version would corrupt command programming or polling. Queue banks have repeating names with different offsets, making copy/paste or macro substitution mistakes easy. The PIO command path depends on `regLSDMA_PIO_STATUS` at `0x0032` for 6.0.0, while later maps place that status elsewhere. There is no compile-time validation that offsets match the hardware discovery table or firmware expectations.

Test signals: build coverage should compile `lsdma_v6_0.c` with this header and catch missing macros. Hardware or simulator tests should exercise LSDMA 6.0 PIO copy and constant-fill, verify that `regLSDMA_PIO_STATUS` reaches idle/FIFO-empty, and confirm that memory power gating toggles through `regLSDMA_MEM_POWER_CTRL`. Register-dump tests should compare programmed offsets against ASIC reference data. Negative tests should ensure the v6 driver does not include v7 offset headers, because both versions export many identical macro names with different numeric values.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/lsdma/lsdma_6_0_0_sh_mask.h

Purpose: this generated AMDGPU ASIC register header defines LSDMA 6.0.0 register field shifts and bit masks for the same `lsdma0_lsdma0dec` block described by the 6.0.0 offset header. It is the bit-field half of the register ABI: offset macros choose a register, while these `LSDMA_*__FIELD__SHIFT` and `LSDMA_*__FIELD_MASK` macros describe how to read, write, and decode individual fields inside that register. The file is used by AMDGPU register helper macros such as `REG_SET_FIELD()` and direct mask comparisons.

Important APIs, types, and functions: there are no C functions or types. The API is the macro namespace guarded by `_lsdma_6_0_0_SH_MASK_HEADER`. Major field groups cover microcode address/data/checksum fields, error injection target selection, public register type bits, ring/IB fetch offsets, command processor and status fields, PIO status/error bits, power-gating and PGFSM controls, version and ID fields, ECC/EDC counters, UTCL1 retry/watermark/status/invalidation/XNACK/page fields, relaxed-ordering policy bits, exception bits, PIO command/control fields, interrupt enable bits, clock/control/chicken bits, graphics address configuration, and duplicated queue0/queue1 fields for RB control/base/read and write pointers, writeback addresses, IB control/base/size, skip counts, context state, doorbells, watermarks, preemption, AQL, quantum, and mid-command snapshots.

The most visible runtime fields are `LSDMA_PIO_STATUS__PIO_IDLE_MASK` and `LSDMA_PIO_STATUS__PIO_FIFO_EMPTY_MASK`, which `lsdma_v6_0.c` uses to wait for completion; `LSDMA_PIO_COMMAND__BYTE_COUNT`, `SRC_LOCATION`, `DST_LOCATION`, `SRC_ADDR_INC`, `DST_ADDR_INC`, `OVERLAP_DISABLE`, and `CONSTANT_FILL`, which compose PIO copy/fill commands; and `LSDMA_MEM_POWER_CTRL__MEM_POWER_CTRL_EN`, which toggles LSDMA memory power control. Queue fields provide lower-level support for ring-buffer operation even though the visible v6 PIO helper uses only a small subset.

Control flow: the header itself has no executable flow, but it defines the predicates and encodings used by driver control flow. A typical read/modify/write sequence reads a register through `RREG32_SOC15()`, clears the target field with the `*_MASK`, shifts the new value by `*_SHIFT`, and writes the result through `WREG32_SOC15()`. Polling flow compares a register value masked by status bits against an expected masked value; for PIO completion the expected state is both `PIO_IDLE` and `PIO_FIFO_EMPTY`. Error paths are also mask-driven: status and exception bits distinguish VM holes, zero byte counts, DRAM/SRAM ECC, NACK generated errors, NACK protection errors, XNACKs, outstanding MMHUB/UTCL2 requests, and queue exceptions.

State and persistence behavior: this file stores no software state, but it documents how persistent hardware register state is interpreted. Stateful hardware areas include command queues and doorbell capture, read/write pointer writeback, indirect-buffer progress, current context/preemption status, mid-command data snapshots, performance counters, ECC/EDC counters, UTCL1 invalidation/XNACK information, PIO command status, interrupt enable state, memory power control, and power-gating FSM state. Some fields are latched status or error indicators; others are writable controls. The header does not encode access permissions or clear-on-read/clear-on-write behavior, so consumers must rely on hardware documentation and driver sequencing.

Dependencies and integration points: this mask header is designed to be included with `lsdma_6_0_0_offset.h`. The direct driver integration is `amdgpu/lsdma_v6_0.c`, where `REG_SET_FIELD()` names `LSDMA_PIO_COMMAND` and `LSDMA_MEM_POWER_CTRL` fields and `amdgpu_lsdma_wait_for()` uses PIO status masks. It depends on AMDGPU's common register macro convention: for a register token such as `LSDMA_PIO_COMMAND` and field token `BYTE_COUNT`, helper macros expect names of the form `LSDMA_PIO_COMMAND__BYTE_COUNT_MASK` and `LSDMA_PIO_COMMAND__BYTE_COUNT__SHIFT`. The macro names also align with generated headers for adjacent LSDMA versions, enabling version-specific driver files to share source structure while including different generated definitions.

Risks and edge cases: bit-field mistakes can be as dangerous as wrong offsets. `BYTE_COUNT` is a 26-bit field (`0x03ffffff`), so callers that pass larger sizes can truncate at the field-set layer unless higher code bounds requests. Several fields are multi-bit status values rather than booleans, including command processing, exception, XNACK state, vectors, merge states, active queue IDs, performance modes, and queue sizes; treating them as single-bit flags would misdecode hardware. Reserved fields are present with masks and should not be casually written. PF, VF, and generic PIO status layouts are identical here, but code should still choose the correct register for the privilege context. Queue0 and queue1 have parallel field names with only the queue number changed, which increases the risk of configuring one queue while polling the other. The header does not provide range checks for VMID, address alignment, RB/IB sizes, AQL packet sizes, or watermarks.

Test signals: compile tests should verify all `REG_SET_FIELD()` and mask references in `lsdma_v6_0.c` resolve. Unit-style macro tests can set and extract representative fields such as `BYTE_COUNT`, `CONSTANT_FILL`, `PIO_IDLE`, `PIO_FIFO_EMPTY`, and `MEM_POWER_CTRL_EN` to catch generator or helper regressions. Hardware tests should cover normal PIO copy/fill completion, zero-count or invalid-address error reporting, ECC/NACK status visibility where fault injection is available, and power-gating transitions. Register conformance tests should compare selected masks and shifts against the LSDMA 6.0.0 hardware specification, especially fields shared with the 7.0.0 driver where source code shape is similar but register offsets differ.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/include/asic_reg/lsdma/lsdma_7_0_0_offset.h

Purpose: this generated AMDGPU ASIC register header defines the LSDMA 7.0.0 MMIO register offsets for the `lsdma0_lsdma0dec` address block at documented base `0x45000`. Like the 6.0.0 offset header, it exposes only preprocessor macros: `regLSDMA_*` names carry offsets and `regLSDMA_*_BASE_IDX` names carry base index `0`. The file exists so the LSDMA 7.0 driver can use the same high-level MMIO helper calls as earlier hardware while targeting the 7.0.0 register layout.

Important APIs, types, and functions: there are no C functions or C types. The exported macro set is guarded by `_lsdma_7_0_0_OFFSET_HEADER`. It includes ucode, error injection, context boundary, ring/IB fetch, status, burst, HBM page, power gating, PGFSM, version/EDC/ECC/error, atomic, UTCL1, relaxed-ordering, physical address, public dummy, performance counter, credit, ULV, status4, CE, exception, PIO, interrupt, memory power, clock, control, and two queue-bank families. Compared with the 6.0.0 map, notable 7.0.0 differences include `regLSDMA_DCC_CNTL` at `0x002d`, removal of `regLSDMA_VF_PIO_STATUS`, movement of `regLSDMA_PIO_STATUS` and `regLSDMA_PF_PIO_STATUS` to `0x007a` and `0x007b`, movement of PIO address/command/control registers to `0x0070` through `0x0076`, movement of interrupt/power/control registers to `0x0069` through `0x006d`, omission of the 6.0.0 `regLSDMA_GB_ADDR_CONFIG*` entries, and rearrangement of many queue0/queue1 context, doorbell, AQL, preempt, and dummy offsets.

Control flow: the header itself has no runtime control flow. The control flow it enables appears in `amdgpu/lsdma_v7_0.c`: the driver writes PIO source and destination address registers, clears `regLSDMA_PIO_CONTROL`, composes `regLSDMA_PIO_COMMAND` using the companion 7.0.0 mask header, writes the command, and polls `SOC15_REG_OFFSET(LSDMA, 0, regLSDMA_PIO_STATUS)` until idle/FIFO-empty. The same offset map also enables memory power-gating read-modify-write through `regLSDMA_MEM_POWER_CTRL`. Although this flow mirrors the 6.0.0 source code, the numeric offsets differ, which is why this header must remain version-specific.

State and persistence behavior: the header has no software state. Its macros address persistent hardware state in LSDMA 7.0.0 registers: PIO command addresses and status, queue ring/IB pointers, doorbell and context/preemption state, mid-command snapshots, ECC and exception status, UTCL1 retry/invalidation/XNACK state, performance counters, power-gating state, clock/control state, and memory power-control state. All base-index macros are `0`, so the register access layer supplies the block base and instance selection. Any state written through these offsets remains in hardware until reset or later driver/firmware writes.

Dependencies and integration points: this file is paired with `lsdma_7_0_0_sh_mask.h`, which supplies field encodings for the registers named here. The direct in-tree consumer is `sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/amdgpu/lsdma_v7_0.c`; it uses this header via `SOC15_REG_OFFSET`, `WREG32_SOC15`, and `RREG32_SOC15`. The common integration path is the AMDGPU LSDMA callback table, where the v7 implementation exports copy, fill, and memory power-gating callbacks. The file also sits beside 6.0.0 and 7.1.0 generated headers; those adjacent versions are useful for comparison but are not interchangeable because macro names overlap.

Risks and edge cases: the primary risk is version mismatch. Many `regLSDMA_*` names are identical to the 6.0.0 names but point to different offsets, especially PIO status/command, memory power control, and queue context/doorbell/AQL areas. Including this header in a v6 path, or the v6 header in a v7 path, would compile cleanly yet access the wrong registers. The file contains `regLSDMA_GPU_IOV_VIOLATION_LOG_BASE_IDX` without a matching visible `regLSDMA_GPU_IOV_VIOLATION_LOG` offset macro in the read source, which may be a generated omission or a reserved/addressless base-index artifact; consumers should not assume an offset exists unless the offset macro is present. The header does not validate whether queue offsets are used with the matching queue fields from the 7.0.0 mask header. As a generated file, it also carries the usual risk that manual edits would be overwritten or desynchronized from hardware XML/register sources.

Test signals: build tests should compile `lsdma_v7_0.c` and ensure all referenced register macros resolve from this header. Hardware or simulator tests should perform v7 LSDMA PIO copy/fill, verify polling through `regLSDMA_PIO_STATUS` at the v7 offset, and validate memory power-gating writes through the v7 `regLSDMA_MEM_POWER_CTRL` offset. Register conformance checks should compare the v7 offset map to the ASIC specification and explicitly assert differences from the v6 map for PIO, interrupt/power, PF status, and queue registers. Static checks can flag accidental cross-inclusion of `lsdma_6_0_0_offset.h` in v7 code or `lsdma_7_0_0_offset.h` in v6 code.
