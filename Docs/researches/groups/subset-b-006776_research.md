# sources/distributed-fs/ceph-client/tools/power/pm-graph/sleepgraph.py

Purpose: `sleepgraph.py` is a standalone Linux suspend/resume diagnostic tool. It can run a suspend, hibernate, freeze/s2idle, or custom command test, collect dmesg and ftrace evidence, parse that evidence into kernel power-management phases and device callback timelines, and emit an interactive HTML report. It also supports reprocessing existing logs, batch/multi-run summaries, firmware timing extraction from ACPI FPDT, runtime PM inventory, ftrace callgraph capture, kprobe-based function timing, and optional Wi-Fi/process/turbostat observations.

Important APIs/types/functions: the global `SystemValues` singleton is the tool's configuration and system-interface hub. It stores command-line options, sysfs/debugfs paths, trace event names, default kprobe definitions, output paths, logging state, and helpers for root checks, ftrace setup, RTC wake alarms, output ownership, runtime suspend toggling, platform info collection, and result reporting. `Data` is the central per-test model: it owns phase definitions, device/action records, firmware and Wi-Fi timing, process execution samples, error summaries, and phase/device normalization helpers. `TestProps` parses log headers and ftrace/dmesg record formats. `FTraceLine` normalizes ftrace function-graph, nop trace event, and kprobe lines into call/return/event objects. `FTraceCallGraph` repairs and post-processes nested ftrace function graph data, then matches it to devices. `Timeline` calculates row packing and emits timeline HTML fragments. `ProcessMonitor` samples `/proc/*/stat` and writes compact execution markers into ftrace.

Control flow: in normal execution, the `__main__` parser fills `sysvals`, checks compatibility, initializes signal handling, validates system capabilities via `statusCheck()`, normalizes modes such as `mem-s2idle` to `freeze`, records platform identity, and calls `runTest()`. `runTest()` creates output files, adjusts optional runtime PM/display/sysfs knobs, initializes ftrace/kprobes through `SystemValues.initFtrace()`, calls `executeSuspend()`, cleans ftrace, parses captured evidence with `processData(live=True)`, writes HTML, restores ownership, and emits result-file state. `executeSuspend()` marks trace start/end, optionally arms RTC wake, runs either a command or writes the selected mode to `/sys/power/state`, restores altered sysfs defaults, polls Wi-Fi, captures dmesg and ftrace logs, and appends platform info.

Control flow for offline processing starts with `rerunTest()` for explicit `-dmesg`/`-ftrace`, `genHtml()` for regenerating missing HTML under a directory, or `runSummary()` for scanning HTML results. `processData()` chooses `parseTraceLog()` when ftrace trace events are available, otherwise falls back to `loadKernelLog()` plus `parseKernelLog()` with optional `appendIncompleteTraceLog()` for legacy callgraph enrichment. `parseTraceLog()` is the richest parser: it loads ordered ftrace records, opens a `Data` object on `SUSPEND START`, creates phase boundaries from `suspend_resume` events, adds device callback blocks from `device_pm_callback_start/end`, records kprobe call/return durations, builds function graphs when requested, handles s2idle loop trimming, fills missing phases, attaches source-function/process entries, and returns both test data and any failure description. HTML generation then flows through `createHTML()`, `addCSS()`, `addCallgraphs()`, and `addScriptCode()`.

State and persistence: persistent outputs are created under a timestamped `suspend-yymmdd-HHMMSS` directory unless overridden. Outputs include `<host>_<mode>_dmesg.txt`, `<host>_<mode>_ftrace.txt`, `<host>_<mode>.html`, optional gzip-compressed logs, result text files, and summary HTML files. Runtime state is heavy and privileged: the tool writes to ftrace files such as `tracing_on`, `trace`, `trace_marker`, `buffer_size_kb`, `current_tracer`, `kprobe_events`, and event enable files; it writes power state selectors under `/sys/power`; it can modify runtime PM `power/control`, ACPI debug level, PM debug messages, S0ix warning parameters, and RTC wake alarms. `SystemValues.testVal()` records original sysfs values in `cfgdef` and restores them through the `restoreall` pseudo-file. `sudoUserchown()` recursively returns generated files to `SUDO_USER` when run under sudo.

Dependencies: requires Linux power-management sysfs, ftrace/debugfs, power trace events, optional kprobes, `/proc` and `/sys` introspection, and root access for actual tests. It depends on kernel configs such as PM debug, ftrace, function graph tracer, kprobes, and trace events. Optional external commands include `turbostat`, `mcelog`, `lspci`, `lsusb`, `ethtool`, `ip`, `xset`, and `netfix`. Python dependencies are standard-library modules only. Browser-side interactivity is embedded as generated CSS and JavaScript. Firmware timing depends on ACPI FPDT and `/dev/mem` readability, with DMI fallback data from `/sys/class/dmi/id` and `/proc/cpuinfo`.

Integration points: this file is part of the kernel `tools/power/pm-graph` tooling and is intended to be run directly with sudo. It integrates with Linux PM core trace events (`suspend_resume`, wakeup source events, device PM callback start/end), ftrace function-graph tracing, kprobe event syntax, ACPI FPDT tables, runtime PM sysfs, RTC wakealarm, S0ix residency/debug files, and generated HTML summaries. Its `-summary` path also treats previously generated HTML as input, making the HTML schema an integration contract for downstream aggregation.

Risks: the script performs privileged writes to system power and tracing controls, so bugs can leave tracing, kprobe events, runtime PM settings, ACPI debug settings, RTC alarms, or display settings altered if cleanup is interrupted. Signal handling tries to emit results and then kills the process, but abrupt failures outside handled paths remain risky. Parsing is regex-heavy and tightly coupled to kernel log and trace formats; kernel wording or ftrace format changes can silently drop phases, devices, or timing data. The callgraph repair logic inserts synthetic calls/returns on misalignment, which is useful after trace loss but can hide underlying buffer overflow or corruption. `executeSuspend()` uses shell execution for user-supplied custom commands and some helper commands, so command strings are intentionally powerful and should not be treated as sanitized input. HTML generation interpolates log/device/function strings directly into markup in many places; for trusted local diagnostic data this is acceptable, but untrusted logs could inject HTML/JavaScript. There is also a likely configuration bug in `configFromFile()`: the `callloop-maxlen` option assigns to `sysvals.callloopmaxgap` instead of `sysvals.callloopmaxlen`, while command-line parsing handles `-callloop-maxlen` correctly.

Test signals: unit-level tests can feed synthetic ftrace nop/function-graph records into `FTraceLine`, `FTraceCallGraph.addLine()/postProcess()`, and `parseTraceLog()` to verify phase boundaries, device callback matching, kprobe call/return pairing, s2idle loops, missing end-marker handling, and multi-run ordering. Synthetic dmesg logs should exercise `loadKernelLog()` and `parseKernelLog()` for legacy initcall parsing. HTML tests should assert that `createHTML()` emits timelines, device detail sections, callgraphs, embedded logs, and valid summary extraction by `data_from_html()`. System smoke tests are `sleepgraph.py -status`, `-modes`, `-sysinfo`, and offline `-dmesg/-ftrace` regeneration. Live suspend tests require root and suitable hardware; they should verify cleanup of ftrace/kprobes and restoration of sysfs defaults after pass, fail, and interrupt paths.

# sources/distributed-fs/ceph-client/tools/power/x86/amd_pstate_tracer/amd_pstate_trace.py

Purpose: `amd_pstate_trace.py` is an AMD P-State trace analyzer and plotting utility. It either records AMD CPU P-State trace events for a fixed interval or consumes an existing trace file, converts `amd_cpu` trace lines into CSV data, splits that data per CPU, and generates gnuplot PNG charts for frequency, desired performance, and load.

Important APIs/types/functions: the script imports and reuses `intel_pstate_tracer` as `ipt` for shared trace buffer control, CSV splitting, gnuplot defaults, ownership fixups, and help text. Column constants such as `C_CPU`, `C_FREQ`, `C_DES_PERF`, `C_LOAD`, `C_ELAPSED`, and `C_COMM` define CSV field positions used by plotting commands. `plot_per_cpu_freq()`, `plot_per_cpu_des_perf()`, and `plot_per_cpu_load()` generate per-CPU PNG files from `cpuNNN.csv`. `plot_all_cpu_frequency()`, `plot_all_cpu_des_perf()`, and `plot_all_cpu_load()` generate aggregate charts using all `cpu???.csv` files. `store_csv()` appends parsed samples to `cpu.csv`, `cleanup_data_files()` initializes the master CSV, and `read_trace_data()` parses trace lines, computes elapsed time, duration, GHz, and load. `signal_handler()` disables and clears tracing on Ctrl-C during interval capture.

Control flow: command-line parsing accepts `-t/--trace_file` for an existing trace, `-i/--interval` for live capture, `-c/--cpu` for comma-separated CPU selection, `-n/--name` for a unique result subdirectory, and `-m/--memory` for trace buffer size. A valid run requires one trace source option and a test name. The script creates `results/<test_name>`, initializes `cpu.csv`, optionally clears trace, configures buffer size, enables `/sys/kernel/tracing/events/amd_cpu/enable`, sleeps for the requested interval, disables tracing, parses `/sys/kernel/tracing/trace`, clears/free buffers, then generates per-CPU and all-CPU plots. For file mode it resolves the trace file relative to the script directory and skips live trace setup. Finally it fixes file ownership under the output directory and returns to the original `results` parent.

State and persistence: persistent artifacts are `results/<test_name>/cpu.csv`, split `cpuNNN.csv` files from `ipt.split_csv()`, and PNG charts such as `cpu000_frequency.png`, `all_cpu_frequencies.png`, `all_cpu_des_perf.png`, and `all_cpu_load.png`. Runtime parser state includes globals `sample_num`, `last_sec_cpu`, `last_usec_cpu`, `start_time`, `current_max_cpu`, `test_name`, and `graph_data_present`. It mutates kernel tracing state in live mode by clearing trace data, changing buffer allocation, enabling/disabling the AMD CPU event file, and freeing trace buffer memory through `intel_pstate_tracer`.

Dependencies: requires Python with `Gnuplot`, `numpy`, and `decimal`; gnuplot and gnuplot-py; Linux tracing mounted at `/sys/kernel/tracing`; and the AMD CPU trace event path `/sys/kernel/tracing/events/amd_cpu/enable`. It depends on sibling `../intel_pstate_tracer/intel_pstate_tracer.py` for common helpers. The trace format is expected to contain fields named `amd_min_perf`, `amd_des_perf`, `amd_max_perf`, `freq`, `mperf`, `aperf`, and `tsc`.

Integration points: this is a user-facing tool under `tools/power/x86/amd_pstate_tracer`. It shares UI/help conventions and plotting infrastructure with Intel P-State tracing, but points the live trace source to AMD P-State events and parses AMD-specific field names. It integrates with kernel tracefs event controls, CPU selection masks, result directory ownership behavior, and gnuplot-based visualization.

Risks: the parser uses a single strict regular expression and can silently skip valid data if kernel trace text changes. `MAX_CPUS` is hard-coded to 256, so CPUs at or above that index cannot be selected and could index out of bounds if present in trace data. `load = mperf * 100 / tsc` assumes nonzero `tsc`; malformed trace data could raise division errors. Aggregate plotting shells out through `ls cpu???.csv | sed ...`; when no split files exist, command failure or empty titles can lead to poor diagnostics. Bare `except` blocks hide I/O and parsing details. The output directory must be unique, and reruns with the same `test_name` are refused. Live mode needs privileges and cleanup; the signal handler only cleans tracing when `interval` is active.

Test signals: offline tests should feed representative AMD P-State trace lines into `read_trace_data()` and assert `cpu.csv` content, elapsed/duration calculations, CPU mask filtering, `graph_data_present`, and `current_max_cpu`. Negative tests should cover missing files, malformed lines, empty traces, duplicate test names, and CPU indices outside `MAX_CPUS`. Integration smoke tests should run file mode with a small fixture and verify master/split CSVs plus per-CPU and aggregate PNG names. Live tests should verify trace event enable/disable, buffer cleanup, and Ctrl-C cleanup on systems with the AMD P-State trace event.

# sources/distributed-fs/ceph-client/tools/power/x86/intel-speed-select/Makefile

Purpose: this Makefile builds, installs, and cleans the `intel-speed-select` userspace tool from the kernel `tools/power/x86/intel-speed-select` directory. It wires the tool into the kernel tools build framework, supplies libnl compile/link flags, and creates local symlinks for required UAPI headers when building outside the kernel tree.

Important APIs/types/functions: `bindir ?= /usr/bin` controls install destination. `srctree` is inferred by walking up four directories from `CURDIR` when not provided. `NL3_CFLAGS` is populated by `pkg-config --cflags libnl-3.0`, falling back to `-I/usr/include/libnl3`. `CFLAGS` are extended with optimization/debug/warning flags, `_GNU_SOURCE`, local generated include path, and libnl include flags. `LDFLAGS` adds `-lnl-genl-3 -lnl-3`. `ALL_TARGETS` and `ALL_PROGRAMS` define the single program, `intel-speed-select`, optionally under `$(OUTPUT)`. The `prepare` target creates `$(OUTPUT)include/linux/isst_if.h` and `$(OUTPUT)include/linux/thermal.h` symlinks from kernel UAPI headers. `$(ISST_IN)` delegates object construction to `$(MAKE) $(build)=intel-speed-select`, and `$(OUTPUT)intel-speed-select` links the resulting `intel-speed-select-in.o`.

Control flow: the default `all` target builds `$(ALL_PROGRAMS)`. Before compiling the aggregate object, `prepare` ensures local generated include symlinks exist. The included `$(srctree)/tools/build/Makefile.include` supplies the kernel tools recursive build rules and variables such as `Q` and `QUIET_LINK`. `install` creates `$(DESTDIR)$(bindir)` and installs every built program there. `clean` removes the program, generated UAPI header symlink, and object/dependency files under `$(OUTPUT)` or the current directory.

State and persistence: persistent build outputs are the linked binary, intermediate object/dependency files, and generated/symlinked headers below `$(OUTPUT)include/linux`. Install persists the binary into `$(DESTDIR)$(bindir)`. The Makefile exports `srctree`, `OUTPUT`, `CC`, `LD`, and `CFLAGS` to sub-make invocations. It does not alter source files except for generated output paths.

Dependencies: depends on the kernel tools build infrastructure at `tools/build/Makefile.include`, source-local build metadata under `intel-speed-select`, a C compiler/linker, make, `pkg-config` if available, libnl development headers/libraries (`libnl-3.0`, `libnl-genl-3`), and kernel UAPI headers `include/uapi/linux/isst_if.h` and `include/uapi/linux/thermal.h`. The resulting tool's HFI netlink support also depends on libnl symbols linked here.

Integration points: this file is the top-level build contract for all C files in `tools/power/x86/intel-speed-select`, including `hfi-events.c`. It integrates kernel UAPI headers into an out-of-tree-style `$(OUTPUT)include` directory so source files can include `<linux/isst_if.h>` and `<linux/thermal.h>` without relying on system header freshness. It also participates in kernel tools installation conventions through `DESTDIR`, `bindir`, and `OUTPUT`.

Risks: the `clean` target removes only `$(OUTPUT)include/linux/isst_if.h` explicitly and not `thermal.h`, leaving a stale symlink after cleanup. If `pkg-config` is unavailable and headers are not in `/usr/include/libnl3`, compilation fails. Link flags are appended globally, so environment-provided `LDFLAGS` ordering issues could affect static or unusual toolchain builds. The symlink targets assume this Makefile remains four directories below the kernel root; moving the file or changing directory depth would break UAPI header resolution. `mkdir -p ... 2>&1 || true` suppresses directory creation errors and could mask permission issues until a later failure.

Test signals: `make -C tools/power/x86/intel-speed-select O=<tmp>` or equivalent should produce `intel-speed-select`. Build logs should show libnl include flags and link against `nl-genl-3` and `nl-3`. `make clean` should remove binaries and object/dependency files; a targeted cleanup test should check whether `include/linux/thermal.h` remains stale. Install tests should run with a temporary `DESTDIR` and verify the binary lands under `usr/bin`. Header integration tests should verify the generated symlinks point to the source tree UAPI headers.

# sources/distributed-fs/ceph-client/tools/power/x86/intel-speed-select/hfi-events.c

Purpose: `hfi-events.c` adds Intel Speed Select support for receiving Hardware Feedback Interface-related thermal generic netlink events out of band. It subscribes to the Linux thermal netlink multicast group, detects CPU capability change events, extracts CPU/performance/efficiency payloads, and triggers existing Intel Speed Select level-change processing for the affected CPU.

Important APIs/types/functions: `struct hfi_event_data` stores the libnl socket and callback set used by the module-global `drv`. `send_and_recv_msgs()` sends a generic netlink request and waits for ack/finish/error/valid callbacks. `family_handler()` scans `CTRL_ATTR_MCAST_GROUPS` for a named multicast group, and `nl_get_multicast_id()` queries `nlctrl` for the numeric group id for `THERMAL_GENL_FAMILY_NAME` and `THERMAL_GENL_EVENT_GROUP_NAME`. `struct perf_cap` temporarily holds `cpu`, `perf`, and `eff` values from a CPU capability event. `handle_event()` parses incoming thermal generic netlink messages and handles `THERMAL_GENL_EVENT_CPU_CAPABILITY_CHANGE`. `process_hfi_event()` converts `perf_cap->cpu` to `struct isst_id` via `set_isst_id()` and calls `process_level_change()`. `check_hf_suport()` uses CPUID leaf 6 bit 19 to require HFI support. `hfi_main()` initializes libnl, joins the multicast group, and runs the receive loop. `hfi_exit()` requests loop termination by setting `_hfi_exit`.

Control flow: `hfi_main()` first checks hardware support. It allocates a netlink socket, connects to generic netlink, allocates default callbacks, resolves the thermal event multicast id, joins that multicast group, installs sequence-check and valid-message callbacks, then loops on `nl_recvmsgs(sock, cb)` until `_hfi_exit` or an error. On each message, libnl invokes `handle_event()`, which parses attributes up to `THERMAL_GENL_ATTR_MAX`, checks the command id, walks the nested `THERMAL_GENL_ATTR_CPU_CAPABILITY` attribute, assigns the first three nested values to CPU, performance, and efficiency, and calls `process_hfi_event()` after each complete triple. Request/response helper flow for multicast-id lookup is separate: `nl_get_multicast_id()` builds a `CTRL_CMD_GETFAMILY` message and uses `send_and_recv_msgs()` plus `family_handler()` to discover the id.

State and persistence: runtime state is in the global `drv` socket/callback pointers and `_hfi_exit` flag. `hfi_main()` does not persist data; it reacts to events by invoking Intel Speed Select state update logic elsewhere. Netlink group membership exists only for the process lifetime. On normal loop exit after successful initialization, the function returns without freeing `sock` or `cb`, matching the comment that the netlink library lacks some deallocation/disconnect calls; on early error it frees the socket through the `free_sock` path.

Dependencies: depends on libnl generic netlink headers and libraries, Linux thermal generic netlink UAPI definitions from `<linux/thermal.h>`, CPUID support through definitions included by `isst.h`, and Intel Speed Select internal functions/types from `isst.h` such as `debug_printf()`, `BIT()`, `set_isst_id()`, and `process_level_change()`. Building this file depends on the Makefile's libnl flags and generated UAPI header symlink for `thermal.h`.

Integration points: this file is part of the `intel-speed-select` userspace tool. It integrates thermal netlink HFI events with the existing Intel Speed Select level-change handling path: CPU capability changes delivered by the kernel thermal subsystem are converted into `isst_id` and handed to `process_level_change()`. `hfi_exit()` is the external shutdown hook for whichever command path starts `hfi_main()`.

Risks: `check_hf_suport()` is misspelled but consistently used; the bigger risk is portability because CPUID leaf 6 bit 19 is x86-specific and assumes the included CPUID macro is safe on the target build. `handle_event()` assumes the nested CPU capability attributes arrive in CPU/perf/eff order and in groups of three; if the kernel attribute contract changes or attributes are missing, it can process a default or partial `perf_cap`. It does not verify `attrs[THERMAL_GENL_ATTR_CPU_CAPABILITY]` is non-null before `nla_for_each_nested()`. `send_and_recv_msgs()` sets `cb` to NULL only through allocation success assumptions; its `out:` path calls `nl_cb_put(cb)` even when `nl_cb_clone()` failed, so behavior depends on libnl tolerating NULL. Early failure paths after callback allocation jump to `free_sock` without freeing `cb`. Normal exit does not free the socket/callback. Error messages are terse and sometimes omit newlines.

Test signals: hardware-independent tests can mock or fixture generic netlink messages and assert `family_handler()` resolves the correct multicast group id and `handle_event()` calls `process_hfi_event()` after each CPU/perf/eff triple. Negative tests should cover missing multicast groups, missing CPU capability attributes, malformed nested payload lengths, and libnl allocation/send/connect failures. Hardware smoke tests on HFI-capable CPUs should confirm CPUID detection, multicast membership, receipt of `THERMAL_GENL_EVENT_CPU_CAPABILITY_CHANGE`, and corresponding `process_level_change()` calls. Build tests should verify compilation and linkage with libnl through the sibling Makefile.
