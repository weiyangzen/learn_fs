# sources/compression/xz/src/liblzma/check/crc32_small.c

Purpose: implements the size-optimized CRC32 backend used when liblzma is built with the small CRC path. It generates a single 256-entry IEEE CRC32 table at startup and exposes the public `lzma_crc32()` API.

Important APIs/types/functions: defines exported `uint32_t lzma_crc32_table[1][256]`, static `crc32_init()`, optional `lzma_crc32_init()`, and `LZMA_API(uint32_t) lzma_crc32(const uint8_t *buf, size_t size, uint32_t crc)`. The table is not static because the LZ encoder hash code can reuse it in small builds.

Control flow: initialization iterates all byte values and folds each through eight polynomial steps using reversed IEEE polynomial `0xEDB88320`. With constructor support this runs before use; otherwise `lzma_crc32()` calls `lzma_crc32_init()`, which wraps `crc32_init()` in `mythread_once()`. The CRC routine complements the incoming CRC, consumes bytes one at a time through table index `*buf ^ (crc & 0xFF)`, shifts right, and returns the complemented final value.

State and persistence: process-global table state is initialized once and then read-only in practice. There is no external persistence; thread safety depends on constructor ordering or `mythread_once`.

Dependencies/integration: includes `check.h` for the public check API and `crc_common.h` for table declarations/thread initialization. `block_header_encoder.c`, `block_header_decoder.c`, stream flags, index tests, and several container decoders depend on `lzma_crc32()`.

Risks: incorrect or skipped table initialization corrupts every CRC32 consumer, including XZ headers and lzip checks. The byte-at-a-time path is slower than fast slicing/arch implementations, so build configuration strongly affects performance. The non-static table is an internal ABI dependency for LZ hash code.

Test signals: CRC32 is exercised indirectly by stream flags, block header, index, lzip, and microlzma tests; focused regression should compare known vectors and repeated lazy initialization under threads.

# sources/compression/xz/src/liblzma/check/crc32_table_be.h

Purpose: generated big-endian CRC32 lookup table for the fast slicing-by-eight implementation. It provides precomputed constants for `lzma_crc32_table[8][256]` when `WORDS_BIGENDIAN` is selected.

Important APIs/types/functions: defines `const uint32_t lzma_crc32_table[8][256]`. There are no functions; the header is included directly by CRC implementation files so the table definition is compiled into exactly the selected translation unit.

Control flow: no runtime control flow exists in this generated artifact. The eight slices correspond to repeated applications of the reversed IEEE CRC32 polynomial, then byte-swapped for big-endian word processing. The fast CRC code indexes the slices by bytes extracted from aligned 32-bit or 64-bit loads.

State and persistence: the table is immutable static program data. It persists for the lifetime of the process and has no initialization ordering concerns.

Dependencies/integration: generated by `crc32_tablegen.c` compiled with `WORDS_BIGENDIAN`. Used by `crc32_fast.c` on big-endian builds and must stay in sync with the table generator and endian helper macros in `crc_common.h`.

Risks: any mismatch between this table and the generator polynomial/endian transform silently produces incompatible CRC32 values on big-endian systems. Because it is generated source, manual edits are high risk and should be replaced by regenerating. Multiple inclusion in the wrong build path can create duplicate definitions.

Test signals: big-endian coverage is primarily build/architecture dependent; cross-endian known-vector tests for `lzma_crc32()` and XZ header CRC validation are the key signals.

# sources/compression/xz/src/liblzma/check/crc32_table_le.h

Purpose: generated little-endian CRC32 lookup table for the fast slicing-by-eight CRC32 backend, the common path on x86 and most supported targets.

Important APIs/types/functions: defines `const uint32_t lzma_crc32_table[8][256]`. It is a data-only header included by the fast CRC32 implementation rather than a separately compiled object.

Control flow: no active control flow. The first slice is the standard reversed IEEE CRC32 byte table; the later slices precompute additional byte positions so fast code can fold four or eight bytes per iteration with table lookups and XORs.

State and persistence: immutable read-only data. Unlike `crc32_small.c`, no constructor or lazy initialization is needed, trading binary size for startup simplicity and speed.

Dependencies/integration: generated by `crc32_tablegen.c` without `WORDS_BIGENDIAN`; consumed by `crc32_fast.c`, optional i386 assembly, and indirectly any code using `lzma_crc32()`. The LZ encoder has its own generated hash table relationship to slice zero.

Risks: stale constants break all CRC32 validation in little-endian fast builds. The table is large enough to affect small-library footprint, so it must be excluded in small or arch-only builds according to `crc_common.h` feature decisions. It must not be included from more than one object.

Test signals: standard CRC32 vectors, XZ stream header/footer CRC tests, block header tests, and lzip decoder checksum tests provide useful coverage.
<!-- END_FILE_RESEARCH: sources/compression/xz/src/liblzma/check/crc32_table_le.h -->

# sources/compression/xz/src/liblzma/check/crc32_tablegen.c

Purpose: build/developer utility that generates `crc32_table_le.h`, `crc32_table_be.h`, and optionally `lz_encoder_hash_table.h` from the CRC32 polynomial.

Important APIs/types/functions: static `crc32_table[8][256]`, `init_crc32_table()`, `print_crc32_table()`, `print_lz_table()`, and `main()`. Build defines select `WORDS_BIGENDIAN` for byte-swapped output or `LZ_HASH_TABLE` for the LZ hash table.

Control flow: `main()` initializes all eight slices. For slice zero each byte is folded through eight right-shift/XOR polynomial steps; later slices start from the previous slice output and repeat the fold. Big-endian builds byte-swap all constants. The print routines emit SPDX text split across string literals, generated-file comments, and formatted hexadecimal constants.

State and persistence: transient generator state only. Persistent effects are the generated headers that are committed or included in the source tree.

Dependencies/integration: includes `tuklib_integer.h` for fixed-width integer helpers, byte swapping, and `PRIX32`. The generated tables are consumed by fast CRC and LZ hash code.

Risks: generator flags must match the target file; using little-endian output in a big-endian table or vice versa causes silent checksum failures. Output formatting is part of the checked-in artifact, so changing it creates large diffs.

Test signals: compare regenerated files to the checked-in headers and run known CRC32 vectors. The LZ hash-table mode should be verified against `src/liblzma/lz/lz_encoder_hash_table.h`.

# sources/compression/xz/src/liblzma/check/crc32_x86.S

Purpose: optional 32-bit x86 assembly implementation of the generic CRC32 fast path, optimized for i686-era processors using slicing-by-eight tables.

Important APIs/types/functions: exports hidden symbol `lzma_crc32_generic` under platform label-prefix rules and references `lzma_crc32_table`. Assembly macros handle CET `ENDBR`, symbol prefixing, alignment, function type/size metadata, PIC addressing, Mach-O indirect pointers, and GNU-stack notes.

Control flow: the function saves callee-saved registers, loads `buf`, `size`, and `crc`, resolves the table address with platform-specific PIC/non-PIC code, complements the CRC, byte-steps until the input pointer is 8-byte aligned or fewer than 16 bytes remain, then processes aligned chunks using eight table slices. Remaining bytes use the single-byte update loop before complementing and returning.

State and persistence: stateless except for reading the global CRC table. It does not initialize the table; callers/build configuration must provide the generated table.

Dependencies/integration: selected by `HAVE_CRC_X86_ASM` in fast CRC builds. `crc64_fast.c` mirrors the pattern for CRC64, while `crc_common.h` decides whether this coexists with generic C or arch-optimized dispatch.

Risks: ABI portability is the main risk: stack offsets, PIC table addressing, symbol prefixing, and platform assembler directives must match the target. It is 32-bit x86 specific and can underperform on very old i586 processors. Table layout mismatches corrupt results.

Test signals: build on ELF, Mach-O, and Windows/Cygwin 32-bit targets when supported; compare `lzma_crc32()` vectors across C and assembly backends and run header/index/lzip checksum tests.

# sources/compression/xz/src/liblzma/check/crc64_fast.c

Purpose: fast CRC64 implementation for the ECMA-182 polynomial, with generic slice-by-four code and optional architecture-optimized dispatch.

Important APIs/types/functions: includes generated `crc64_table_be.h` or `crc64_table_le.h`, defines `lzma_crc64_generic()` unless assembly supplies it, optional `crc64_arch_optimized()` via `crc_x86_clmul.h`, resolver type `crc64_func_type`, `crc64_resolve()`, constructor/lazy dispatch helpers, and exported `lzma_crc64()`.

Control flow: the generic routine complements the incoming CRC, byte-swaps on big-endian, aligns the input to four bytes, processes aligned 32-bit words through four CRC64 table slices, handles trailing bytes, reverses the big-endian swap, and complements the result. If both generic and CLMUL paths are built, a constructor or first-call dispatcher selects the optimized function when CPUID reports CLMUL/SSSE3/SSE4.1 support.

State and persistence: optional process-global function pointer `crc64_func` caches runtime dispatch. Generated tables are immutable program data.

Dependencies/integration: depends on `check.h`, `crc_common.h`, endian read helpers, generated tables, optional i386 assembly, and optional PCLMUL header. Used by check calculation for XZ Blocks when CRC64 is selected.

Risks: runtime dispatch must not call CLMUL on unsupported CPUs. Big-endian byte handling and aligned reads are correctness-sensitive. If unsupported-check policy changes, callers must still verify `lzma_check_is_supported()` before relying on CRC64.

Test signals: CRC64 known vectors, block encode/decode with CRC64 checks, CPU-dispatch tests on CLMUL and non-CLMUL hosts, and cross-endian testing.

# sources/compression/xz/src/liblzma/check/crc64_small.c

Purpose: size-optimized CRC64 implementation that computes a single 256-entry ECMA-182 lookup table at runtime and updates CRC one byte at a time.

Important APIs/types/functions: static `uint64_t crc64_table[256]`, static `crc64_init()`, and exported `LZMA_API(uint64_t) lzma_crc64(const uint8_t *buf, size_t size, uint64_t crc)`.

Control flow: initialization folds each byte through eight steps using reversed ECMA polynomial `0xC96C5795D7870F42`. With constructor support the table is prepared before calls; otherwise `lzma_crc64()` uses a function-local `mythread_once(crc64_init)`. The update path complements the input CRC, indexes the table with the low byte XOR input byte, shifts right by eight, and returns the complemented result.

State and persistence: the table is private process-global mutable state during initialization and read-only afterward. There is no persistence beyond process memory.

Dependencies/integration: includes `check.h`; uses thread-once primitives from common headers. Selected by small-build configuration instead of the larger fast CRC64 table path.

Risks: byte-at-a-time performance can be significant for large streams using CRC64, the default XZ check. Any initialization race would corrupt checks, so constructor or `mythread_once` availability matters. Unlike CRC32 small, the table is private and not shared with LZ code.

Test signals: known CRC64 vectors and XZ Block round trips using CRC64. Repeated first-call tests under concurrency are useful for no-constructor builds.
<!-- END_FILE_RESEARCH: sources/compression/xz/src/liblzma/check/crc64_small.c -->

# sources/compression/xz/src/liblzma/check/crc64_table_be.h

Purpose: generated big-endian CRC64 table for the fast slice-by-four ECMA-182 implementation.

Important APIs/types/functions: defines `const uint64_t lzma_crc64_table[4][256]` using `UINT64_C()` constants. There are no functions; this header is included as a table definition.

Control flow: none at runtime. The four slices encode successive byte-folding positions for the reversed CRC64 polynomial, then are byte-swapped for big-endian processing. `crc64_fast.c` uses these slices after endian-specific word reads and shifts.

State and persistence: immutable program data. No initialization or external persistence.

Dependencies/integration: generated by `crc64_tablegen.c` with `WORDS_BIGENDIAN`; included by `crc64_fast.c` on big-endian builds. Requires `uint64_t` and `UINT64_C` declarations from included common headers.

Risks: generated constants must match both polynomial and byte order. Big-endian CRC regressions may be missed on little-endian CI, so table drift can remain latent. Including it in multiple translation units would duplicate the table definition.

Test signals: regenerate-and-diff checks, CRC64 known vectors on big-endian or emulated big-endian builds, and XZ Block CRC64 decode validation.

# sources/compression/xz/src/liblzma/check/crc64_table_le.h

Purpose: generated little-endian CRC64 slice-by-four table for the fast CRC64 backend used by common XZ builds.

Important APIs/types/functions: defines `const uint64_t lzma_crc64_table[4][256]`. It is data-only and intentionally generated from `crc64_tablegen.c`.

Control flow: no active control flow. `crc64_fast.c` indexes the slices by bytes from the low 32 bits of the folded CRC/input word and combines them with shifted high CRC state.

State and persistence: read-only program data with process lifetime. It avoids runtime table initialization at the cost of about 8 KiB of data.

Dependencies/integration: generated by `crc64_tablegen.c` without `WORDS_BIGENDIAN`; included by `crc64_fast.c` when `WORDS_BIGENDIAN` is not defined. Used by public `lzma_crc64()` and therefore by Block integrity checks.

Risks: stale or manually altered constants break CRC64 compatibility across XZ files. The footprint may be inappropriate for small builds, which should choose `crc64_small.c` instead. The table must match the ECMA polynomial expected by the file format.

Test signals: CRC64 ECMA vectors, block encoder/decoder tests using default CRC64 check, and comparison between fast, small, assembly, and CLMUL implementations.

# sources/compression/xz/src/liblzma/check/crc64_tablegen.c

Purpose: generator utility for the CRC64 fast lookup headers, producing little-endian or big-endian `lzma_crc64_table[4][256]` definitions.

Important APIs/types/functions: static `crc64_table[4][256]`, exported-to-file-scope `init_crc64_table()`, static `print_crc64_table()`, and `main()`.

Each is folded eight times with reversed ECMA-182 polynomial `0xC96C5795D7870F42`. Big-endian generation byte-swaps every constant before printing. `main()` initializes and prints the table.

Dependencies/integration: includes `stdio.h` and `tuklib_integer.h` for `uint64_t`, byte swap helpers, and formatting macros. Its output is consumed by `crc64_fast.c`.

Risks: generator output is architecture-flag sensitive; invoking it with the wrong `WORDS_BIGENDIAN` setting produces a syntactically valid but incorrect header. Any polynomial change would require synchronized updates to small, fast, CLMUL, and assembly paths.

Test signals: regenerate headers and compare with source, run CRC64 vectors, and verify that little- and big-endian generated outputs differ only as expected by byte swapping.

# sources/compression/xz/src/liblzma/check/crc64_x86.S

Purpose: optional 32-bit x86 assembly CRC64 generic backend, adapted from the CRC32 assembly to process ECMA-182 CRC64 with slicing-by-four tables.

Important APIs/types/functions: exports hidden `lzma_crc64_generic`, references `lzma_crc64_table`, and defines platform macros for CET, symbol prefixing, alignment, PIC/non-PIC addressing, Mach-O pointers, ELF size metadata, and GNU-stack marking.

Control flow: the function preserves registers, obtains arguments and the CRC64 table address, complements the 64-bit CRC held in register pairs, aligns input, processes four-byte chunks through table slices, handles tail bytes, complements final state, and returns the 64-bit result according to i386 calling conventions.

State and persistence: stateless apart from reading immutable CRC64 table data. It has no runtime CPU dispatch or initialization logic itself.

Dependencies/integration: built when `HAVE_CRC_X86_ASM` is enabled for 32-bit x86 fast CRC64. It is selected from `crc64_fast.c` instead of the C generic function and still depends on generated `lzma_crc64_table[4][256]`.

Risks: register-pair CRC64 arithmetic, stack offsets, and platform PIC relocations are fragile. Assembly coverage is often thinner than C coverage, and any table layout or calling-convention mismatch produces bad checks or crashes. It is not a replacement for PCLMUL dispatch on modern x86.

Test signals: 32-bit x86 builds with CRC64 vectors, XZ Block round trips with CRC64 checks, and comparison against C fast/small implementations.

# sources/compression/xz/src/liblzma/check/crc_clmul_consts_gen.c

Purpose: developer utility that derives carry-less multiplication constants used by the x86 PCLMUL CRC32/CRC64 implementation.

Important APIs/types/functions: constants `p32` and `p64`, helper `calc_cldiv(uint64_t p)`, helper `calc_clrem(uint64_t p, unsigned bits)`, and `main()`.

Control flow: `calc_cldiv()` computes Barrett reduction reciprocal-style values using carry-less division over GF(2). `calc_clrem()` computes polynomial remainders for powers used in folding. `main()` prints constant groups for CRC32 and CRC64 that correspond to 512-bit folding, 128-bit folding, and Barrett reduction parameters used in `crc_x86_clmul.h`.

State and persistence: no runtime library state. Its persistent output is manually copied into CLMUL source constants.

Dependencies/integration: includes `inttypes.h` and `stdio.h`. The generated values are embedded in `crc_x86_clmul.h`; they must align with the reversed CRC32 and CRC64 polynomials used elsewhere.

Risks: this file is not part of normal runtime, so mistakes can enter through manual constant updates. Polynomial arithmetic is subtle; off-by-one degree assumptions or 64-bit truncation mistakes break only the optimized path. Printed constants must be checked against known vectors after updating.

Test signals: after regenerating constants, run CRC32/CRC64 known vectors with CLMUL forced and compare against generic implementations. Code review should also map each printed constant to the corresponding `fold512`, `fold128`, and `mu_p` initializer.

# sources/compression/xz/src/liblzma/check/crc_common.h

Purpose: shared CRC build-configuration and endian helper header, deciding which CRC32/CRC64 implementations are compiled and declaring the shared lookup tables.

Important APIs/types/functions: declares CRC tables and `lzma_crc32_init()` for small builds; defines byte extraction/shift helpers `A/B/C/D`, `S8/S32/S64`; sets feature macros such as `CRC32_GENERIC`, `CRC64_GENERIC`, `CRC32_ARCH_OPTIMIZED`, `CRC64_ARCH_OPTIMIZED`, `CRC_X86_CLMUL`, `CRC32_ARM64`, and LoongArch-related selection.

Control flow: preprocessor logic chooses implementation availability based on build macros, target architecture, endian mode, Windows constraints, and compiler support. It can select generic table code, x86 CLMUL runtime dispatch, ARM64 CRC32 acceleration, LoongArch CRC acceleration, or a combination.

State and persistence: no runtime state, but it controls whether global tables and dispatch function pointers exist in the compiled objects.

Dependencies/integration: includes `common.h`, architecture-specific headers through downstream files, and build-system feature probes. `crc32_fast.c`, `crc64_fast.c`, small CRC files, and LZ hash code rely on its declarations.

Risks: this is configuration-critical. A wrong macro combination can compile no valid implementation, duplicate definitions, or use instructions unavailable on the runtime CPU. Endian helper mistakes affect all fast CRC math. Windows and E2K special cases need careful preservation.

Test signals: matrix builds across small/fast, endian, x86 CLMUL, ARM64, LoongArch, Windows, and no-constructor configurations. Known CRC vectors should pass for every selected implementation.

# sources/compression/xz/src/liblzma/check/crc_x86_clmul.h

Purpose: header-implemented x86/E2K CLMUL CRC32 and CRC64 accelerated backend, included once with `BUILDING_CRC_CLMUL` set to either `32` or `64`.

Important APIs/types/functions: defines target attribute `crc_attr_target`, mask table `vmasks`, vector helpers `my_load128()`, `keep_high_bytes()`, `shift_left()`, `shift_right()`, `fold()`, `fold_xor()`, selected `crc32_arch_optimized()` or `crc64_arch_optimized()`, and `is_arch_extension_supported()` when generic fallback exists.

Control flow: the optimized function complements CRC, handles small inputs with scalar reads and vector shifts, handles larger inputs by folding 16-byte lanes and a four-lane 64-byte loop with PCLMUL, folds remaining bytes into one 128-bit state, then uses Barrett reduction constants to extract the final CRC32 or CRC64. CPUID checks require CLMUL, SSSE3, and SSE4.1 before runtime dispatch selects this path.

State and persistence: immutable aligned `vmasks` table plus no per-call persistent state. Dispatch state is owned by the including CRC file.

Dependencies/integration: uses `<immintrin.h>`, optional `<intrin.h>` or `<cpuid.h>`, endian unaligned read helpers, and constants generated by `crc_clmul_consts_gen.c`. Included from CRC32/CRC64 fast files.

Risks: must never be included twice and must only run on CPUs with required instruction sets. The vector tail logic intentionally reads before/around the end within safe ranges; boundary errors are security-sensitive. Constants differ between CRC32 and CRC64 and cannot be mixed.

Test signals: forced CLMUL CRC32/CRC64 vectors for sizes 0 through at least 128 with every tail length, plus runtime dispatch tests on supported and unsupported CPUs.

# sources/compression/xz/src/liblzma/check/sha256.c

Purpose: implements SHA-256 integrity check support for liblzma without depending on an external crypto library.

Important APIs/types/functions: macros for SHA-256 schedule and round functions (`blk0`, `blk2`, `Ch`, `Maj`, `S0`, `S1`, `s0`, `s1`, `R0`, `R2`), constant table `SHA256_K[64]`, static `transform()`, static `process()`, and exported internal functions `lzma_sha256_init()`, `lzma_sha256_update()`, and `lzma_sha256_finish()`.

Control flow: initialization sets the standard SHA-256 initial state and zeroes size counters. Update accumulates bytes in `check->buffer`, processes full 64-byte blocks through `transform()`, and tracks total byte count. Finish appends `0x80`, zero padding, and the big-endian bit length, processes the final block(s), and writes the digest words in big-endian order to the check buffer.

State and persistence: all hash state lives in caller-provided `lzma_check_state`: eight state words, a 64-byte buffer, and byte-count fields. No globals except constants.

Dependencies/integration: includes `check.h` and uses endian conversion helpers. Called by the generic check layer when a Block uses `LZMA_CHECK_SHA256`.

Risks: length accounting and padding boundaries are correctness-critical. The implementation is for integrity checking, not keyed authentication. Any endian conversion regression breaks interoperability.

Test signals: SHA-256 known vectors, XZ Block round trips with SHA-256 checks, and update-splitting tests where input is provided in many chunk sizes.

# sources/compression/xz/src/liblzma/common/alone_decoder.c

Purpose: streaming decoder for legacy `.lzma`/LZMA_Alone files, parsing the 13-byte Alone header and then delegating payload decoding to the LZMA1EXT decoder.
