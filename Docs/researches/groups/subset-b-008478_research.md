# sources/storage-engines/foundationdb/fdbserver/logsystem/ApplyMetadataMutation.cpp

Purpose: Applies system-key metadata mutations to the commit proxy or resolver transaction-state store and, when running on a commit proxy, emits the private log mutations needed by storage servers, TSS pairs, backup machinery, range locks, and global epoch-control paths. It is the deterministic bridge between normal committed system mutations and the in-memory metadata/cache state used by commit proxies, resolvers, storage-cache routing, log-range backup routing, and storage-server tag popping.

Important APIs/types/functions: `getStorageInfo` lazily decodes `serverTagKeyFor` and `serverListKeyFor` into a `StorageInfo` cache. The private `ApplyMetadataMutationsImpl` has overload-backed constructors for proxy metadata, resolver metadata, and direct txn-state-store application. `apply()` walks `VectorRef<MutationRef>` and dispatches to targeted `checkSet*` or `checkClear*` helpers. Public overloads of `applyMetadataMutations` adapt proxy, resolver, and direct callers. `containsMetadataMutation` is a fast classifier used to decide if a mutation batch touches metadata that needs this special handling.

Control flow: For each `SetValue` on a system key, the implementation updates the local `IKeyValueStore` unless this is an `initialCommit`, then performs side effects for matching prefixes. `keyServersPrefix` updates `keyInfo` ranges and storage tags. `serverKeysPrefix`, `serverTagPrefix`, TSS mapping/quarantine, checkpoint, and global-key paths emit privatized mutations by prefixing with `systemKeys.begin`, adding target tags to `LogPushData`, and optionally updating accumulative checksums. Configuration, version-epoch, min-required-commit-version, and recovery keys set `confChange` or trace restart-sensitive state. For `ClearRange`, the code intersects the clear with known metadata ranges, updates caches, clears txnStateStore ranges, pops removed tags through `LogSystemConsumer`, and emits clear private mutations where storage servers must be notified. Deferred vectors handle TSS server-list removal and TSS mapping installation after all in-batch ordering-sensitive mutations have been seen.

State and persistence behavior: The durable source of truth is the committed system-key mutation stream, but this file maintains the commit proxy/resolver in-memory `txnStateStore` mirror and cache structures. It mutates `KeyRangeMap<ServerCacheInfo>` for shard-to-storage routing, `KeyRangeMap<std::set<Key>>` for log-range backup destinations, `uid_applyMutationsData` for backup-agent apply-mutations workers, `storageCache`, `tag_popped`, and `tssMapping`. It writes private TLog messages to `LogPushData` so storage servers see only metadata addressed to their tags. Server tag removal can pop log tags up to `popVersion`, making tag-history retention and ordering part of persistence correctness. `initialCommit` suppresses local store writes for metadata already recovered.

Dependencies and integration points: Depends on `SystemData` key ranges/codecs, `MutationList`, `BackupAgent` apply-mutations state, `KeyBackedTypes` tuple codecs for TSS mapping, `AccumulativeChecksumUtil`, `LogProtocolMessage`, `LogPushData`, `LogSystemConsumer`, and `IKeyValueStore`. It integrates directly with commit proxy metadata context, resolver data, storage-cache update paths, range-lock feature state, TSS quarantine/mapping, backup log ranges, checkpoint requests, and version-vector TLog unicast via `setLogsChanged()`.

Risks: Determinism is critical: comments explicitly warn that every commit proxy must perform the same txnStateStore operations at the same time. Intra-batch ordering is subtle for TSS removal and mapping because server-list, server-tag, and mapping keys depend on one another. Private mutation generation must clear old checksums before adding new accumulative checksum metadata. Server tag/history clears can drop the last durable record of a tag and therefore must pop the correct log range. Range-lock mutation application assumes KRM set-range emits paired boundary mutations. Broad config-key checks intentionally mark most config changes as restart-requiring, with exclusions for operational exclusion keys.

Test signals: Useful coverage includes deterministic replay of mixed set/clear system mutations on proxy and resolver contexts; storage-server add/remove and tag reuse; TSS mapping/quarantine add and remove ordering; `keyServersPrefix` cache updates; log-range backup add/clear and metadataVersionKey sentinel behavior; checkpoint private mutations; global `lastEpochEndKey` and `killStorageKey`; range-lock pair handling; `initialCommit` suppression; accumulative checksum tagging; and `containsMetadataMutation` positives/negatives for every prefix it gates.

# sources/storage-engines/foundationdb/fdbserver/logsystem/CMakeLists.txt

Purpose: Defines the FoundationDB `fdbserver_logsystem` static library target and its link/unit-test wiring inside the fdbserver build.

Important APIs/types/functions: Uses project CMake helpers `fdb_find_sources`, `add_flow_target`, `add_fdbserver_link_test`, `add_fdbserver_unit_test`, and `configure_fdbserver_common_includes`. It then sets public and private include directories with `target_include_directories` and links `fdbserver_core` plus `fdbserver_kvstore` through `target_link_libraries`.

Control flow: CMake first discovers all sources in the directory into `FDBSERVER_LOGSYSTEM_SRCS`, builds them into a static `fdbserver_logsystem` Flow target, adds a link test against the logsystem/core/kvstore stack, adds a unit-test target named `fdbserver_logsystem_test` in the `logsystem` suite, configures common fdbserver includes, exposes the local `include` directory publicly, and links the static library's public dependencies.

State and persistence behavior: No runtime persistence is implemented here. The build file controls generated build graph state: which source files are compiled into the logsystem library, which include paths are exported to dependents, and which validation targets exist.

Dependencies and integration points: Integrates the logsystem module with the broader Flow/CMake build infrastructure and with fdbserver's core and kvstore libraries. The public include directory is the interface consumed by other fdbserver components such as master/recovery, commit proxy, TLog, and disk-queue adapter callers.

Risks: `fdb_find_sources` means new files in this directory can be picked up automatically, so accidental files may enter the static library. Link and unit tests are only as complete as the sources and test registration behind the helper macros. Publicly linking `fdbserver_core` and `fdbserver_kvstore` exposes those dependency assumptions to downstream targets.

Test signals: Build success of `fdbserver_logsystem`, `fdbserver_logsystemlinktest`, and `fdbserver_logsystem_test` is the direct signal. A clean dependency graph should compile after adding/removing logsystem files, and downstream fdbserver targets should see headers under the public `include` directory without extra include plumbing.

# sources/storage-engines/foundationdb/fdbserver/logsystem/LogSet.cpp

Purpose: Implements `LogSet` helper behavior for describing log servers/routers, identifying routers and backup workers, selecting best and quorum-compatible TLog locations for tags, maintaining locality maps, and building satellite tag placement tables.

Important APIs/types/functions: `logRouterString` and `logServerString` render configured interface IDs for tracing. `hasLogRouter` and `hasBackupWorker` test membership by UID. `populateSatelliteTagLocations` creates per-tag satellite TLog replica teams. `checkSatelliteTagLocations` validates distribution balance and traces abnormalities. `bestLocationFor` returns the preferred log index for a tag. `updateLocalitySet`, `satisfiesPolicy`, and `getPushLocations` wrap `LocalityMap`/`LocalitySet` selection logic.

Control flow: Normal primary log sets select `tag.id % logServers.size()` as the best location, add it to the push set when the tag locality matches, and then ask the locality policy for extra replicas. `allLocations` bypasses tag matching and writes to every local log server. Restricted locality sets narrow replica selection during version-vector unicast recovery. Satellite log sets use precomputed `satelliteTagLocations` and return all team members for TLog or log-router tags, then uniquify the location list. Satellite placement walks possible tag teams, repeatedly selects policy-satisfying replicas from the least-used server ordering, rotates best-server usage, and asserts each team can be built.

State and persistence behavior: `LogSet` is in-memory state derived from `TLogSet`/`CoreTLogSet` configuration and recruitment replies. It stores vectors of log servers, log routers, backup workers, localities, policy, replication/anti-quorum parameters, and `satelliteTagLocations`. Persistence occurs indirectly when `LogSystem` serializes `LogSet` back into log-system config or core state.

Dependencies and integration points: Depends on `LocalityMap`, `LocalitySet`, replication policies, `Tag` locality conventions, `TLogInterface`, `BackupInterface`, and `LogSystem` serialization/recruitment code. `LogPushData`, recovery initialization, log consumers, and commit push paths all rely on `getPushLocations` and `bestLocationFor` to choose the correct TLogs.

Risks: Placement correctness is policy-sensitive. A bad satellite `satelliteTagLocations` table can overload a subset of logs or fail anti-affinity. `satisfiesPolicy` asserts policy selection succeeds and interprets an empty result set as already satisfying the policy. `getPushLocations` must keep `locations` offsets aligned with the flattened TLog location numbering used by `LogSystem::push` and unicast recovery. Tag locality matching is central: special, satellite, transaction, log-router, and negative pseudo localities have different behavior.

Test signals: Tests should cover primary best-location modulo routing, all-location pushes, restricted locality sets, locality-policy replica expansion, satellite team generation balance, duplicate zone/multiple DC trace paths, special-locality matching, and stable flattened offsets across multi-log-set configurations.

# sources/storage-engines/foundationdb/fdbserver/logsystem/LogSystem.cpp

Purpose: Implements the tag-partitioned FoundationDB log system: message packing and push fanout, epoch recovery/locking, new TLog/log-router recruitment, old-generation retention, remote-region recovery, backup-worker tracking, config/core-state serialization, failure monitoring, and pop/recovery helpers.

Important APIs/types/functions: Free wrappers expose `LogSystem` methods to C-style/helper callers. `LogPushData` builds per-TLog binary commit payloads and tracing messages. Serialization helpers convert `LogSet`/`OldLogData` to `TLogSet`, `CoreTLogSet`, `OldTLogConf`, and `OldTLogCoreData`. Core methods include `fromLogSystemConfig`, `fromOldLogSystemConfig`, `toCoreState`, `getLogSystemConfig`, `getLogsValue`, `push`, `confirmEpochLive`, `endEpoch`, `epochEnd`, `newEpoch`, `newRemoteEpoch`, `recruitOldLogRouters`, `getDurableVersion`, `getRecoverVersionUnicast`, `trackRejoins`, `lockTLog`, `trackTLogRecoveryActor`, `popFromLog`, backup-worker setters/removers, and pseudo-locality helpers.

Control flow: Commit pushing starts in `LogPushData`, which assigns tags, computes flattened log locations through `LogSystem::getPushLocations`, serializes tagged messages with subsequences, optionally writes span-context messages for V6/V7 TLogs, and exposes per-location payloads. `LogSystem::push` sends `TLogCommitRequest`s to local log sets, waits for each set's write quorum, records latency/reset metrics, and returns the minimum successful reply version. Failure monitoring builds wait-failure futures for current TLogs, routers, backup workers, and old-generation actors and maps failures to `tlog_failed` or `backup_worker_failed`.

Control flow for recovery: `epochEnd` locks current and required old TLog sets, handles force-recovery rewriting for remote surviving logs, tracks rejoin requests, repeatedly computes durable versions from lock replies, and publishes a stopped old `LogSystem` once a recoverable minimum end is known. `getDurableVersion` applies anti-quorum, replication factor, and locality-policy math to decide if enough TLogs are locked and chooses known committed plus minimum durable versions. When version-vector TLog unicast is enabled, `getRecoverVersionUnicast` reconstructs which versions are recoverable from per-log unknown-committed-version sets and may restart recovery if locked TLog membership changes. `newEpoch` recruits primary and optional satellite TLogs, assigns recover tags, recruits old log routers when old data must be copied, initializes new TLogs, waits for recovery-finished signals, and optionally launches `newRemoteEpoch` for multi-region remote logs. `newRemoteEpoch` recruits remote TLogs and log routers, initializes them from old log-system config, and tracks remote recovery completion.

State and persistence behavior: In memory, `LogSystem` holds current `tLogs`, `oldLogData`, epoch, recruitment ID, tag counts, `recoverAt`, `knownCommittedVersion`, stopped state, locked TLog IDs, backup-worker state, pseudo-locality pop versions, outstanding pops, recovery futures, and remote recovery state. `toCoreState` writes the compact core state used by coordinators/recovery, pruning old generations only after local and remote recovery plus backup epoch constraints allow it. `getLogSystemConfig` publishes a fuller client/server view, including old TLogs until `recoveryCompleteWrittenToCoreState` is true and remote logs once written. Pop state is not durable here; it is driven through TLog `popMessages` requests and outstanding in-memory actors.

Dependencies and integration points: Integrates with `TLogInterface` RPCs (`commit`, `lock`, `confirmRunning`, `popMessages`, `recoveryFinished`, `trackRecovery`), `BackupInterface`, `RecruitFromConfigurationReply`, `RecruitRemoteFromConfigurationReply`, `DatabaseConfiguration`, replication policy utilities, Flow actors/futures, histograms, wait-failure code, remote/local locality settings, and commit-proxy span tracing. It is consumed by master recovery, commit proxies, log routers, backup/range-backup workers, and `LogSystemConsumer`.

Risks: This is high-risk correctness code. Recovery-version selection must be conservative or committed data can be lost; too conservative and recovery can repeatedly restart or stall. Version-vector unicast adds per-TLog recovery constraints and relies on locked TLog ID subset checks. Force recovery rewrites log-set state and can discard unavailable generations. Old-generation pruning must wait for storage/server recovery and backup consumers. Satellite and remote recruitment depend on tag mapping across changing tag counts. Failure detection uses quorum races and wait-failure timeouts; incorrect classification can trigger unnecessary recovery or miss a failed log. `push` assumes flattened location numbering matches `LogPushData` messages and unicast `tpcvMap` entries.

Test signals: Strong signals include simulation recovery tests across primary, satellite, and remote-region configurations; TLog loss and rejoin; log-router recruitment and replacement; backup worker old-epoch retention/removal; recovery restarts at earlier versions; version-vector unicast unknown-version reconstruction; force recovery; old-generation pruning; pseudo-locality pop minima; commit push quorum/anti-quorum behavior; connection reset metrics; and `trackTLogRecoveryActor` updating recovered versions. The source itself flags `TODO: unit tests to stress UNICAST`, which is a notable coverage gap.

# sources/storage-engines/foundationdb/fdbserver/logsystem/LogSystemConsumer.cpp

Purpose: Implements read/pop consumption of the log system for storage recovery, transaction-system recovery, log routers, and backup workers. It builds peek cursors over current and old log generations, chooses local/all/remote strategies, merges multiple tag streams, and schedules pops to TLogs and log routers.

Important APIs/types/functions: `peekAll`, `peekRemote`, two overloads of `peek`, `peekLocal`, `peekTxs`, `peekSingle`, `peekLogRouter`, `popLogRouter`, `popTxs`, `pop`, `getTxsPoppedVersion`, `getEnd`, and `getPseudoPopTag`. It instantiates cursor types such as `SetPeekCursor`, `ServerPeekCursor`, `BufferedCursor`, `ReplayMultiCursor`, `MultiCursor`, and `MergedPeekCursor`.

Control flow: `peek` dispatches remote-log tags to `peekRemote` and all other tags to `peekAll`; multi-tag peek creates one cursor per tag and buffers/merges them. `peekAll` selects local log sets matching the tag locality and current/old epoch ranges, then returns a single current `SetPeekCursor` or a `ReplayMultiCursor` stitched with epoch-end markers. `peekLocal` tries to use one matching local set and can throw `worker_removed` if a local-only path cannot safely read old generations. `peekTxs` builds transaction-system cursors for all transaction tags, preferring locality-limited merged cursors when a usable `peekLocality` and `localEnd` are supplied and falling back to `peekAll` on worker removal. `peekLogRouter` locates the generation containing the requesting log router or backup worker, chooses current or old local sets, optionally prefers satellite logs, and avoids constructing empty old-range cursors.

State and persistence behavior: The consumer is mostly stateless beyond its reference to `LogSystem`; it observes `tLogs`, `oldLogData`, `recoveredAt`, `knownLockedTLogIds`, `stopped`, tag counts, and recovery endpoints. Pop operations mutate `LogSystem::outstandingPops`, `popActors`, and `logRouterLastPops`, then asynchronously send durable `popMessages` requests to TLogs. `getTxsPoppedVersion` queries TLogs through `LogSystem::getPoppedTxs`. No local disk persistence occurs in this file.

Dependencies and integration points: Depends on `LogSystem`/`LogSet` placement, TLog peek cursor implementations, tag-locality conventions, old-generation metadata, version-vector unicast locked-TLog information, log-router/backup-worker interfaces stored in log sets, and `SERVER_KNOBS` pop delays. Storage servers and transaction logs use these cursors to replay committed messages during recovery; log routers and backup workers use the log-router paths to catch up and then pop.

Risks: Cursor composition across epochs is subtle: begin/end boundaries are exclusive/inclusive in different APIs and are adjusted by `+1` in public peek methods. Missing old generations, special locality transitions, local/remote generations, or worker removal must fail safe rather than silently skip data. Version-vector unicast requires resetting best server to `-1` unless that server is known locked/stopped. Log-router old-range peeking previously risked born-exhausted cursors when `begin >= oldEnd`, which this file explicitly avoids. Pop scheduling keeps only one actor per `(logID, tag)` outstanding; errors leave the outstanding entry filled, preventing further pops from that `LogSystem`.

Test signals: Coverage should exercise current-only and old-generation peeks; remote-log peeks through log routers; multi-tag buffering; local fallback to all peeks on `worker_removed`; transaction-system locality split at `localEnd`; stopped vs live log-router peeks; satellite preference; empty old-range skip; pop scheduling for TLogs and log routers; durable KCV passed with log-router pops; and pseudo pop-tag mapping for backup/log-router process classes.

# sources/storage-engines/foundationdb/fdbserver/logsystem/LogSystemDiskQueueAdapter.cpp

Purpose: Adapts log-system transaction replay and new pushed data to the `IDiskQueue`-style interface expected by transaction logs. It lets recovery read a byte stream from `LogSystem::peekTxs` while collecting pushed blocks and pop positions into commit messages acknowledged by the caller.

Important APIs/types/functions: `LogSystemDiskQueueAdapterImpl::readNext` is the core coroutine. Public methods implement disk queue operations: `readNext`, `getNextReadLocation`, `push`, `pop`, `commit`, `getError`, `onClosed`, `dispose`, `close`, `getCommitMessage`, and factory `openDiskQueueAdapter`.

Control flow: Recovery reads loop until at least the requested byte count is buffered or the log-system end is reached. When the cursor has no message, the adapter races cursor `getMore()`, `peekLocality` changes, and a switch timer. Timer choices rotate among unrestricted, secondary-locality, and primary-locality `peekTxs` cursors. If a cursor reports a popped version or buggify discards data, the adapter resets `recoveryLoc`, clears buffers, recreates the cursor, marks discarded data, and throws `disk_adapter_reset`. Otherwise it appends cursor messages into a recovery queue, concatenates chunks, returns at most the requested byte count, and advances `recoveryQueueLoc`.

State and persistence behavior: In-memory state includes `recoveryLoc`, `startLoc`, `recoveryQueue`, `recoveryQueueDataSize`, `recoveryQueueLoc`, `totalRecoveredBytes`, `cursor`, `localityChanged`, `peekTypeSwitches`, `hasDiscardedData`, `pushedData`, `poppedUpTo`, `nextCommit`, and pending `commitMessages`. `push` stores bytes into arena-backed blocks of `LOG_SYSTEM_PUSHED_DATA_BLOCK_SIZE` and returns the next commit location. `commit` packages pushed blocks and `popTo` into `CommitMessage`, sends it through a promise, and completes when the message's `acknowledge` future is fulfilled. The adapter does not write disk itself.

Dependencies and integration points: Depends on `IDiskQueue` types, `LogSystem::peekTxs`, `PeekTxsInfo`, Flow `race`, `delay`, `yield`, and server knobs for cursor switch timing and block sizing. TLog recovery code uses it as a disk-queue-like source/sink while the log system remains the actual persisted log.

Risks: Reset behavior is correctness-sensitive because discarded or popped data forces replay from a new location. The locality-switch race must not starve progress or read past `logSystem->getEnd()`. Returning empty data at end clears the `logSystem` reference, so later reads rely on adapter state only. `commit` asserts a pending commit-message promise exists, so callers must request commit messages before committing. `close`/`dispose` delete `this`, making ownership conventions important.

Test signals: Tests should cover reading across multiple cursor messages, partial-byte reads, end-of-log empty result, locality change switching, timer-based primary/secondary/unrestricted rotation, cursor popped reset and `disk_adapter_reset`, buggified reset in simulation, `push` block splitting, `pop` max behavior, `commit` message contents and acknowledgement, and disabled recovery returning empty reads.

# sources/storage-engines/foundationdb/fdbserver/logsystem/LogSystemFactory.cpp

Purpose: Provides small factory wrappers that decouple callers from direct `LogSystem` and `LogSystemConsumer` construction and from the concrete tag-partitioned implementation selection.

Important APIs/types/functions: `recoverAndEndLogSystemEpoch`, `makeLogSystemFromLogSystemConfig`, `makeOldLogSystemFromLogSystemConfig`, `makeLogSystemFromServerDBInfo`, and `makeLogSystemConsumerFromServerDBInfo`.

Control flow: `recoverAndEndLogSystemEpoch` forwards to `LogSystem::recoverAndEndEpoch`. The config factories return an empty reference for `LogSystemType::empty`, call `LogSystem::fromLogSystemConfig` or `LogSystem::fromOldLogSystemConfig` for `LogSystemType::tagPartitioned`, and throw `internal_error` for unknown types. Server DB info helpers extract locality and log-system config from `ServerDBInfo`, create a `LogSystem`, and optionally wrap it in a consumer.

State and persistence behavior: No state is owned or persisted here. The functions instantiate references based on already-persisted log-system config and pass through `useRecoveredAt`, `excludeRemote`, and optional actor collection parameters that affect the constructed `LogSystem`.

Dependencies and integration points: Depends on `LogSystemFactory.h`, `LogSystem.h`, `LogSystemConsumer.h`, `DBCoreState`, `ServerDBInfo`, `LogSystemConfig`, and Flow actor futures. This is the narrow integration point for components that need a log system but should not branch on log-system type themselves.

Risks: Only `empty` and `tagPartitioned` are recognized; adding another `LogSystemType` requires updating this factory or callers will hit `internal_error`. Returning null for empty configs requires callers to handle absence. The wrapper preserves `excludeRemote` and `useRecoveredAt` semantics, so incorrect caller flags can construct a log-system view with missing remote logs or different recovery end behavior.

Test signals: Build/link tests are the main direct signal. Unit tests should cover empty config returning null, tag-partitioned config returning a usable `LogSystem`, old-log construction, consumer creation from `ServerDBInfo`, and unknown type failure if a new enum value is introduced without factory support.
