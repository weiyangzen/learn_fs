# sources/distributed-fs/ceph-client/mm/shmem.c

Purpose: implements Linux shmem/tmpfs, the swap-backed in-memory filesystem used for tmpfs mounts, SysV/shared anonymous memory, memfd-style anonymous files, and `/dev/zero` shared mappings. In full `CONFIG_SHMEM` builds it adds resource accounting, quotas, swap-out/swap-in, transparent hugepage and multi-size THP support, NUMA mempolicy, userfaultfd hooks, xattrs/ACLs/casefolding, file operations, and mount option parsing. In `!CONFIG_SHMEM` builds it falls back to tiny-shmem backed by ramfs.

Important APIs/types/functions: key local types are `struct shmem_falloc` for coordinating hole punch/fallocate with faults and `struct shmem_options` for fs-context mount state. Important exported/common APIs include `shmem_mapping`, `vma_is_anon_shmem`, `vma_is_shmem`, `shmem_inode_acct_blocks`, `shmem_recalc_inode`, `shmem_charge`, `shmem_uncharge`, `shmem_add_to_page_cache`, `shmem_truncate_range`, `shmem_unuse`, `shmem_writeout`, `shmem_get_folio`, `shmem_lock`, `shmem_get_unmapped_area`, `shmem_init_fs_context`, `shmem_init`, `shmem_kernel_file_setup`, `shmem_file_setup`, `shmem_file_setup_with_mnt`, `shmem_zero_setup`, `shmem_zero_setup_desc`, `shmem_read_folio_gfp`, and `shmem_read_mapping_page_gfp`. Core operation tables are `shmem_aops`, `shmem_file_operations`, inode op tables for regular/dir/symlink/special inodes, `shmem_ops`, `shmem_vm_ops`, `shmem_anon_vm_ops`, `shmem_fs_context_ops`, and `shmem_fs_type`.

Control flow: file and anonymous mapping faults enter `shmem_fault`, optionally wait on a concurrent punch-hole `shmem_falloc`, then call `shmem_get_folio_gfp`. That central lookup path checks file size, handles userfaultfd minor/missing faults, resolves xarray swap entries through `shmem_swapin_folio`, locks cached folios, or allocates new folios through `shmem_alloc_and_add_folio`. Allocation first chooses allowable hugepage orders using mount policy, sysfs/boot THP policy, VMA hints, and page-cache conflicts, then charges memcg, inserts into the mapping xarray, charges tmpfs blocks/quota, updates inode accounting, and links the folio to LRU. Swap-out flows through `shmem_writeout`: it refuses locked/noswap/no-swap cases, splits large folios when THP swap or EOF constraints require it, allocates swap, increments swapped accounting, adds the inode to `shmem_swaplist`, replaces the file-cache folio with a swap entry, and writes the folio to swap. Swapoff calls `shmem_unuse`, scans `shmem_swaplist`, finds matching swap entries, and pulls them back with `shmem_swapin_folio`.

Control flow continued: truncation and hole punching use `shmem_undo_range` to remove page-cache folios and swap entries, handle partial large-folio boundaries by zeroing or splitting, and reconcile inode block accounting. `shmem_fallocate` supports allocation and punch-hole modes; punch-hole installs a stack `struct shmem_falloc` in `inode->i_private` so racing faults sleep rather than refilling the punched range, while allocation walks the target page indexes with `SGP_FALLOC` and rolls back newly added non-uptodate folios on failure. File reads and splice reads call `shmem_get_folio` with `SGP_READ`, copy real folios or zero-filled holes, and handle hwpoisoned subpages specially for large folios. Writes go through generic write checks plus `shmem_write_begin`/`shmem_write_end`, which enforce seals and mapping freeze, instantiate folios, zero partial new folios, mark dirty, and extend `i_size`.

State and persistence behavior: all file data lives in RAM or swap, not persistent storage. Persistent-in-memory state is split across `struct shmem_sb_info` and `struct shmem_inode_info`: superblocks hold block/inode limits, `used_blocks`, `free_ispace`, uid/gid/mode, `huge` policy, mempolicy, noswap, quota defaults, inode-number batching, and a shrinklist for unused portions of large folios; inodes hold allocated/swapped page counts, seals, flags, fallocate extent end, xattrs, mempolicy, shrinklist/swaplist links, directory offsets, and stop-eviction coordination. The mapping xarray stores either folios or encoded swap/poison entries, with large entries carrying an xarray order. Accounting must keep `info->alloced`, `info->swapped`, `mapping->nrpages`, tmpfs counters, overcommit accounting, memcg charges, and quota reservations synchronized under their respective locks.

Dependencies and integration points: this file integrates with VFS (`fs_context`, superblock/inode/file operation tables, export handles, idmapped mounts), mm (`folio`, xarray page cache, LRU, reclaim, swap cache, memcg, rmap, userfaultfd, NUMA mempolicy, THP/mTHP), security (`security_vm_enough_memory_mm`, LSM xattr initialization), quota (`shmem_quota_operations`, `dquot_*`), writeback/swap (`swap_writeout`, swapoff), sysfs/boot params for THP policy, Unicode/casefold support, simple directory-offset helpers, and ramfs for tiny-shmem fallback. It also exports setup helpers used by IPC, memfd-style users, DRM/GPU memory managers, tmpfs mounts, and shared anonymous mmap paths.

Risks: the highest-risk paths are races between truncate/hole punch, page faults, swapin/swapout, large xarray entries, and inode eviction. Large folio and multi-size THP handling must avoid data corruption when a large swap entry is split, when swapin returns a smaller folio, or when only part of a folio is inside `i_size`. Resource accounting errors can leak or double-charge tmpfs blocks, quota, memcg, swap entries, or overcommit reservations. Mount reconfiguration deliberately rejects retroactive limits and noswap/quota transitions that cannot be made safe. `inode->i_private` fallocate coordination relies on stack lifetime and `i_lock`/wake discipline. Sysfs and boot THP policy changes affect allocation behavior globally, so incorrect policy parsing or mask updates can cause unexpected allocation pressure.

Test signals: useful coverage comes from tmpfs and mm selftests, fstests exercising tmpfs truncate, fallocate, xattrs, ACLs, casefold, quota, rename, tmpfile, and remount behavior, swapoff/swap stress, THP/mTHP tmpfs tests, userfaultfd shmem tests, memfd seal tests, syzkaller-style truncate/fault/write races, and LTP SysV shared memory tests. Runtime signals include `statfs` block/inode accounting, `/proc/meminfo` shmem/swap counters, `VM_FAULT_MAJOR`, THP fallback/allocation events, `THP_SWPOUT_FALLBACK`, `MTHP_STAT_SHMEM_*`, WARNs in inode eviction, and failures from `shmem_add_to_page_cache`/`shmem_confirm_swap` race paths.

# sources/distributed-fs/ceph-client/mm/shmem_quota.c

Purpose: implements the in-memory quota format used by tmpfs/shmem when `CONFIG_TMPFS_QUOTA` is enabled. Because tmpfs has no persistent quota file, this format keeps quota IDs and their user-configured limits in memory so inactive dquots cannot be shrunk and later reloaded from disk.

Important APIs/types/functions: `struct quota_id` is the private rb-tree node containing a quota id plus block/inode hard and soft limits. `shmem_format_ops` implements `check_quota_file`, `read_file_info`, `write_file_info`, and `free_file_info` for `QFMT_SHMEM`. `shmem_quota_format` registers the format type. `shmem_quota_operations` supplies dquot operations: `shmem_acquire_dquot`, `shmem_release_dquot`, `dquot_alloc`, `dquot_destroy`, `shmem_dquot_write_info`, `shmem_mark_dquot_dirty`, and `shmem_get_next_id`.

Control flow: enabling quota causes `shmem_read_file_info` to allocate an rb-root in `mem_dqinfo->dqi_priv`, set tmpfs-specific max limits, and configure one-week block/inode grace periods. `shmem_acquire_dquot` locks the dquot and quota I/O semaphore, searches the per-type rb-tree, creates a new `quota_id` node if absent, seeds new user/group hard limits from `shmem_sb_info->qlimits`, copies stored limits into the dquot, marks all-zero limits as fake, and finally sets `DQ_ACTIVE_B` after a memory barrier. `shmem_release_dquot` skips busy dquots, finds the matching rb-tree node, removes empty/fake/default-unused entries, or copies updated dquot limits back into the node before clearing active state. `shmem_get_next_id` walks the sorted tree to support quota iteration.

State and persistence behavior: all quota state is transient per mounted superblock and quota type. The rb-tree in `dqi_priv` is the only persistent source for per-id limits while mounted; no quota file is read or written. Default hard limits are copied from mount options into newly discovered IDs. Empty dquots are pruned so the tree keeps only IDs with useful non-default limit state or usage. Synchronization uses `dquot->dq_lock`, `dqopt->dqio_sem`, and `dq_dqb_lock` for dquot fields.

Dependencies and integration points: the file depends on generic quota infrastructure (`quota_format_ops`, `quota_format_type`, `dquot_operations`, `sb_dqinfo`, `dquot_alloc`, `dquot_destroy`), tmpfs state from `linux/shmem_fs.h`, rb-tree APIs, and the init user namespace for converting `kqid` values. It is referenced from `shmem.c` when quotas are enabled on a tmpfs superblock and registered during shmem initialization.

Risks: losing an rb-tree entry loses user-provided quota limits for that id until remount, because there is no disk reload path. The pruning test must distinguish fake/default/unused dquots from meaningful configured limits. The code assumes only user and group quota types are used; an unexpected type would leave default limit locals uninitialized in `shmem_is_empty_dquot`. Lock ordering with generic dquot code matters because acquisition/release can sleep and interact with tmpfs block allocation paths.

Test signals: mount tmpfs with `usrquota`, `grpquota`, and hard-limit options; verify dquot acquisition inherits global defaults, per-id limit changes survive dquot release/reacquire within the same mount, empty/default IDs disappear from iteration, and quota enforcement blocks tmpfs writes/inode creation at the expected limits. Error-path tests should cover allocation failure in `read_file_info`/`acquire_dquot` and quota-off freeing of all rb-tree nodes.

# sources/distributed-fs/ceph-client/mm/show_mem.c

Purpose: provides generic memory reporting helpers used by sysinfo, `/proc/meminfo`-style consumers, and diagnostic `show_mem` output during OOM or manual memory dumps. It estimates available memory, fills `struct sysinfo`, and prints detailed node/zone/free-area state.

Important APIs/types/functions: exports `_totalram_pages`, `totalreserve_pages`, `totalcma_pages`, `si_mem_available`, and `si_meminfo`; under NUMA it also provides `si_meminfo_node`. Internal helpers include `show_node`, `show_mem_node_skip`, `show_migration_types`, `node_has_managed_zones`, `show_free_areas`, and `__show_mem`.

Control flow: `si_mem_available` sums low watermarks, starts from global free pages minus reserves, adds a conservative portion of active/inactive file cache, adds a conservative portion of reclaimable slab and miscellaneous kernel reclaimable pages, and clamps negative estimates to zero. `si_meminfo` and `si_meminfo_node` fill page counts directly from global or per-node vmstat counters. `__show_mem` prints a header, delegates the detailed dump to `show_free_areas`, then totals present, reserved, highmem/movable-only, CMA, hwpoisoned, and optional allocation-profiling information.

State and persistence behavior: this file owns only global accounting variables; most values are snapshots read from vmstat, zone, node, hugetlb, swap, CMA, and optional profiling state. Output is intentionally approximate and racy because it is diagnostic. `show_free_areas` briefly locks each zone only while copying buddy free-list counts and migratetype occupancy, avoiding long lock holds during printing.

Dependencies and integration points: depends on zone/node iteration, vmstat counters, cpuset nodemask filtering, highmem, hugetlb, swap reporting, block-device page accounting, CMA, memory failure counters, and optional allocation profiling codetags. It is called from OOM/reclaim diagnostics and other kernel paths needing a memory snapshot.

Risks: the available-memory heuristic can over- or under-estimate under unusual reclaimability, watermarks, memcg pressure, pinned file cache, or unreclaimable slab conditions. Diagnostic output is large and can be expensive on systems with many nodes/zones/orders. Filtering by current cpuset is intentionally imprecise. Any counter unit mismatch would directly confuse operator-facing memory diagnostics.

Test signals: compare `si_meminfo` and `si_mem_available` against `/proc/meminfo` fields under memory pressure, file-cache growth, slab growth, swap activity, CMA reservation, and NUMA cpuset filtering. OOM and SysRq memory dumps should include per-node and per-zone lines, migration type letters, hugepage info, swap-cache info, and optional profiling rows without lockdep or printk-format warnings.

# sources/distributed-fs/ceph-client/mm/shrinker.c

Purpose: implements the generic shrinker registry and scan engine used by kernel subsystems to reclaim caches under memory pressure. It supports global shrinkers, NUMA-aware shrinkers, memcg-aware shrinkers, deferred scan accounting, RCU-safe registration/removal, and debugfs integration.

Important APIs/types/functions: global state is `shrinker_list` and `shrinker_mutex`; under memcg it also maintains `shrinker_nr_max` and an IDR from shrinker IDs to shrinker objects. Public functions include `alloc_shrinker_info`, `free_shrinker_info`, `set_shrinker_bit`, `reparent_shrinker_deferred`, `shrink_slab`, `shrinker_alloc`, `shrinker_register`, and `shrinker_free`. Key internals are `shrinker_unit_alloc/free`, `expand_shrinker_info`, `xchg_nr_deferred`, `add_nr_deferred`, `do_shrink_slab`, and `shrink_slab_memcg`.

Control flow: a subsystem allocates a `struct shrinker` with `shrinker_alloc`, fills callbacks such as `count_objects` and `scan_objects`, then registers it with `shrinker_register`. During reclaim, `shrink_slab` routes non-root memcg reclaim to `shrink_slab_memcg`; root/global reclaim walks `shrinker_list` under RCU, obtains a shrinker ref with `shrinker_try_get`, drops RCU while scanning, then reacquires RCU before `shrinker_put`. `do_shrink_slab` asks the shrinker for object count, exchanges deferred work, computes a scan target from reclaim priority and `seeks`, repeatedly calls `scan_objects` in batches, records scanned/freed objects, and writes back bounded deferred work. Memcg reclaim uses bitmap bits set by `set_shrinker_bit` to scan only shrinkers that have objects in a memcg/node.

State and persistence behavior: shrinker registry state is process-lifetime kernel memory. Each shrinker may have per-node `nr_deferred` counters or, for memcg-aware shrinkers, per-memcg/per-node `shrinker_info_unit` arrays containing bitmaps and deferred counters. `expand_shrinker_info` grows every memcg's arrays when a new shrinker id exceeds the current map capacity, publishing new arrays with RCU. `shrinker_free` drops the registration ref, waits for active lookups through a completion, removes the shrinker under the mutex, detaches debugfs, removes memcg IDR state, and frees memory after an RCU grace period.

Dependencies and integration points: integrates with vmscan reclaim priority, memcg online/offline and kmem state, RCU list traversal, IDR allocation, tracepoints (`mm_shrink_slab_start/end`), VM event accounting (`SLABS_SCANNED`), debugfs hooks from `shrinker_debug.c`, and list-lru users that call `set_shrinker_bit`. Shrinker flags such as `SHRINKER_MEMCG_AWARE`, `SHRINKER_NUMA_AWARE`, and `SHRINKER_NONSLAB` determine routing and accounting.

Risks: lifetime management is subtle because shrinkers can be unregistered while reclaim is walking them and `scan_objects` may sleep. Missing `shrinker_try_get`/`shrinker_put` pairing or RCU reacquisition can use freed shrinkers or corrupt traversal. Memcg bitmap clearing relies on memory barriers paired with producers setting bits; ordering bugs can miss reclaimable objects. Deferred scan math must be capped to avoid runaway reclaim debt while preserving pressure fairness. Expansion failure must leave old memcg info valid. Reparenting deferred counters on memcg removal must not race with expansion or lose debt.

Test signals: stress global and memcg reclaim with dynamically registered shrinkers, list-lru-heavy workloads, cgroup creation/destruction, kmem on/off modes, NUMA-aware shrinkers, and concurrent shrinker unregister. Tracepoints should show bounded total_scan/deferred values, `SLABS_SCANNED` should move under pressure, debugfs entries should appear and disappear with registration, and lockdep/KCSAN should remain quiet around RCU/mutex/barrier paths.

# sources/distributed-fs/ceph-client/mm/shrinker_debug.c

Purpose: exposes registered shrinkers through debugfs so developers can inspect per-memcg/per-node reclaimable object counts and trigger manual scans for a selected shrinker.

Important APIs/types/functions: global state includes `shrinker_debugfs_ida` and `shrinker_debugfs_root`. Public hooks used by the shrinker core are `shrinker_debugfs_add`, `shrinker_debugfs_rename`, `shrinker_debugfs_detach`, and `shrinker_debugfs_remove`; initialization is `shrinker_debugfs_init`. Internal file operations are `shrinker_debugfs_count_show`, `shrinker_debugfs_scan_open`, `shrinker_debugfs_scan_write`, `shrinker_debugfs_scan_fops`, and `shrinker_debugfs_count_fops`.

Control flow: late init creates `/sys/kernel/debug/shrinker` and then walks already registered shrinkers under `shrinker_mutex` to add missing entries. `shrinker_debugfs_add` allocates a stable debugfs ID, creates a directory named `<shrinker-name>-<id>`, and installs `count` and `scan` files. Reading `count` allocates a per-node buffer, iterates memcgs when the shrinker is memcg-aware, calls the shrinker's `count_objects` callback for each node, and emits rows containing memcg id followed by node counts when total is nonzero. Writing `scan` parses `memcg_id nid nr_to_scan`, validates the target, optionally resolves and pins the memcg, builds a `shrink_control`, and invokes `scan_objects`.

State and persistence behavior: debugfs entries live only while debugfs and the shrinker exist. `shrinker->debugfs_entry`, `debugfs_id`, and `name` are updated under `shrinker_mutex`. Rename uses `kvasprintf_const`, swaps names atomically under the mutex, and frees the old name only after a successful debugfs rename. Removal is split into detach under the shrinker mutex and recursive debugfs removal plus IDA free after the core has made the shrinker unreachable.

Dependencies and integration points: depends on `debugfs`, `seq_file`, memcg iteration and lookup by ID, shrinker callbacks/flags, `shrinker_mutex`, and `shrinker_list` exported from the shrinker core. It is not on the reclaim critical path except for creation/removal/rename hooks.

Risks: manual `scan` writes can invoke arbitrary shrinker callbacks from debugfs context and may affect system state, so input validation and memcg reference handling are important. Count output can be expensive when many memcgs/nodes exist and is interruptible through `signal_pending`. The code assumes shrinker lifetime is protected by the core's registration/removal locking; debugfs files must not outlive reachable shrinker objects in a way that allows use-after-free.

Test signals: with debugfs enabled, registered shrinkers should appear under `/sys/kernel/debug/shrinker`, `count` should show rows for root or memcg-aware IDs with per-node counts, `scan` should reject malformed input, invalid nodes, invalid memcg IDs, and nonzero memcg IDs for non-memcg shrinkers, and renaming/removing shrinkers should update or delete directories without ID leaks or stale files.

# sources/distributed-fs/ceph-client/mm/shuffle.c

Purpose: implements optional randomization of buddy allocator free lists to reduce predictability of physical page allocation, especially after memory initialization and hotplug. It is controlled by a static key enabled through the `shuffle` module/kernel parameter and helpers in `shuffle.h`.

Important APIs/types/functions: defines `page_alloc_shuffle_key`, the `shuffle` parameter handler `shuffle_param_set`, `shuffle_valid_page`, `__shuffle_zone`, `__shuffle_free_memory`, and `shuffle_pick_tail`. `SHUFFLE_RETRY` bounds attempts to find a valid random swap target.

Control flow: setting the `shuffle` parameter to true enables the static branch. `__shuffle_free_memory` walks zones in a node and calls the guarded `shuffle_zone` wrapper. `__shuffle_zone` holds the zone lock, aligns to `SHUFFLE_ORDER`, walks free PFNs in the zone, validates the current page as online, in-zone, buddy, and same order, then tries up to ten random PFNs in the zone span for another valid page. If both pages are on the same migratetype list, it swaps their `lru` list positions. It periodically drops the zone lock and reschedules. `shuffle_pick_tail` consumes random bits from a cached `u64` to choose head/tail insertion behavior elsewhere in the page allocator.

State and persistence behavior: state is minimal: a static branch key, the parsed boolean parameter, and the deliberately unsynchronized cached random bits in `shuffle_pick_tail`. Shuffling mutates zone free-area list order, not page contents or allocator metadata counts. The random-bit cache is racy by design; concurrent updates are allowed and only add nondeterminism.

Dependencies and integration points: depends on buddy allocator zone state (`struct zone`, `PageBuddy`, `buddy_order`, `list_swap`, pageblock migratetype), online PFN lookup, kernel random number APIs, module parameter parsing, jump labels/static keys, and `shuffle.h` inline guards. Page allocator code can call `shuffle_free_memory`, `shuffle_zone`, `is_shuffle_order`, and `shuffle_pick_tail` only when `CONFIG_SHUFFLE_PAGE_ALLOCATOR` is enabled.

Risks: the zone lock is held while scanning potentially large PFN spans, so periodic unlock/reschedule is important for latency. Random PFNs can land in holes, offline memory, wrong zones, wrong orders, or wrong migratetypes; validation prevents list corruption but introduces bias and skipped swaps. The shuffle is explicitly not cryptographically perfect; it raises allocation unpredictability but does not guarantee uniform permutation. Any migratetype mismatch bug would place pages on the wrong free list.

Test signals: boot or enable with `shuffle=1`, verify static key-dependent paths run, confirm free-list integrity under page allocator debug checks, memory hotplug, and stress allocation/free cycles. Debug logs can show failed swap or migratetype mismatch events. Distribution tests can compare allocation PFN ordering with and without shuffle, but should not expect perfect Fisher-Yates uniformity.

# sources/distributed-fs/ceph-client/mm/shuffle.h

Purpose: provides compile-time and static-key guarded declarations/wrappers for page allocator free-list shuffling. It lets page allocator code call shuffle hooks with no-op stubs when `CONFIG_SHUFFLE_PAGE_ALLOCATOR` is disabled.

Important APIs/types/functions: defines `SHUFFLE_ORDER` as `MAX_PAGE_ORDER`. Under `CONFIG_SHUFFLE_PAGE_ALLOCATOR` it declares `page_alloc_shuffle_key`, `__shuffle_free_memory`, `__shuffle_zone`, and `shuffle_pick_tail`, and defines inline wrappers `shuffle_free_memory`, `shuffle_zone`, and `is_shuffle_order`. Without the config it provides no-op `shuffle_free_memory`, no-op `shuffle_zone`, `shuffle_pick_tail` returning false, and `is_shuffle_order` returning false.

Control flow: callers use the inline wrappers. When the config is enabled, each wrapper first checks `static_branch_unlikely(&page_alloc_shuffle_key)` and only calls the implementation when the runtime parameter has enabled shuffling. `is_shuffle_order` additionally requires the requested order to be at least `SHUFFLE_ORDER`, so only high-order free-list behavior is randomized through this hook.

State and persistence behavior: the header owns no state beyond declaring the static key. Runtime state lives in `shuffle.c`; disabled builds compile out behavior through inline stubs.

Dependencies and integration points: depends on jump labels and mm page allocator types such as `pg_data_t` and `struct zone` from included contexts. It is intended for inclusion by internal mm/page allocator code, not external modules.

Risks: incorrect guard use could make page allocator behavior depend on shuffle code even in disabled builds. `SHUFFLE_ORDER` being tied to `MAX_PAGE_ORDER` means call sites must understand which order ranges are intended for tail randomization. Static-key state must be enabled before wrappers are expected to do work.

Test signals: build both with and without `CONFIG_SHUFFLE_PAGE_ALLOCATOR`; disabled builds should have no unresolved shuffle symbols and stable allocator behavior. Enabled builds should show wrappers remain no-op until `page_alloc_shuffle_key` is enabled and `is_shuffle_order(order)` flips only for orders at or above `SHUFFLE_ORDER`.

# sources/distributed-fs/ceph-client/mm/slab.h

Purpose: internal header for Linux slab/SLUB allocator implementation. It defines the in-memory layout overlay between `struct slab` and `struct page`, cache metadata structures, boot state, kmalloc cache lookup helpers, debug/sysfs hooks, object metadata helpers, memcg slab hooks, initialization-on-alloc/free policy helpers, and internal allocator function prototypes.

Important APIs/types/functions: key structures include `struct freelist_counters`, `struct slab`, `struct kmem_cache_order_objects`, `struct kmem_cache_per_node_ptrs`, `struct kmem_cache`, `enum slab_state`, `struct slabinfo`, and `struct kmem_obj_info`. Important helpers include `slab_folio`, `page_slab`, `slab_page`, `slab_address`, `slab_nid`, `slab_pgdat`, `virt_to_slab`, `slab_order`, `slab_size`, `cache_has_sheaves`, `nearest_obj`, `__obj_to_index`, `obj_to_index`, `objs_per_slab`, `kmalloc_slab`, `is_kmalloc_cache`, `is_kmalloc_normal`, `kmem_cache_debug_flags`, `metadata_access_enable/disable`, `slab_obj_exts`, `get_slab_obj_exts`, `put_slab_obj_exts`, `slab_set_stride`, `slab_get_stride`, `slab_obj_ext`, `cache_vmstat_idx`, `large_kmalloc_order`, `large_kmalloc_size`, `slab_want_init_on_alloc`, `slab_want_init_on_free`, and `slub_debug_orig_size`.

Control flow: allocation code uses `kmalloc_slab` to map request size, bucket set, GFP flags, and caller into a kmalloc cache. Slab/page conversion helpers let allocator and diagnostics move between folio/page/slab/object views. Debug and metadata paths use `metadata_access_enable/disable` to suppress KASAN/KMSAN reports while touching allocator-private bytes. When `CONFIG_SLAB_OBJ_EXT` is enabled, callers read the encoded extension pointer from the slab, bracket access with get/put helpers, compute per-object metadata by index and stride, and rely on `alloc_slab_obj_exts` to provision extension storage. Init-on-alloc/free helpers combine static branch defaults, constructors, RCU-safe slabs, poisoning, and `__GFP_ZERO` to decide when the allocator should clear memory.

State and persistence behavior: this header describes long-lived allocator state owned by slab implementation files: global `slab_state`, `slab_mutex`, `slab_caches`, `kmem_cache`, kmalloc cache tables, and per-cache fields such as object size, alignment, free-pointer offset, sheaves, partial settings, constructors, sysfs object, hardening random value, NUMA nodes, random sequences, KASAN/usercopy/debug/stat metadata, and per-node pointers. `struct slab` reuses first-page fields and is guarded by static assertions so layout changes in `struct page` do not silently break allocator metadata.

Dependencies and integration points: depends on page/folio layout, reciprocal division, list_lru, local locks, random/hardening, kobjects/sysfs, memcg, KFENCE, KASAN/KMSAN, hardened usercopy, SLUB debug, KUnit, RCU freeing, allocation profiling, and vmstat slab counters. It provides prototypes consumed by `slab_common.c`, SLUB implementation files, sysfs/debugfs slab views, memcg hooks, usercopy checks, and kfree_rcu sheaf support.

Risks: layout overlay between `struct page` and `struct slab` is fragile; incorrect offsets or alignment can corrupt allocator state. Freelist ABA protection depends on architecture cmpxchg width and aligned `struct page`; fallback behavior must remain correct. Object index math depends on reciprocal size and tag stripping, with KFENCE special-casing. Metadata extension pointers are encoded with memcg flags and must not be dereferenced without masking and KASAN/KMSAN bracketing. Init-on-free/alloc decisions interact with constructors, poisoning, and RCU-safe caches; clearing at the wrong time can break object lifetime or hide debug signals.

Test signals: build coverage across 32-bit/64-bit, cmpxchg128/cmpxchg64, SLUB debug, KASAN/KMSAN/KFENCE, memcg, object extensions, hardened usercopy, sysfs, and tiny SLUB configurations is important. Runtime signals include slabinfo/sysfs correctness, KUnit slab tests, freelist hardening tests, KASAN/KMSAN absence around metadata access, kmalloc size-class selection checks, memcg slab charging/freeing tests, and boot-time static assertion success for page/slab layout.
