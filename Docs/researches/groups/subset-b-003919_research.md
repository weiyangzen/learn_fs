# sources/distributed-fs/ceph-client/drivers/infiniband/hw/cxgb4/cm.c

Purpose: Chelsio T4/T5/T6 iWARP connection manager. It bridges RDMA CM/IWCM operations to cxgb4 TCP offload CPLs and firmware work requests, manages active and passive connection setup, negotiates MPA v1/v2 attributes, binds endpoints to QPs, drives disconnect/abort state transitions, and defers interrupt/offload receive events to an ordered workqueue.

Important APIs, types, and functions: exported entry points are `c4iw_connect()`, `c4iw_create_listen()`, `c4iw_destroy_listen()`, `c4iw_accept_cr()`, `c4iw_reject_cr()`, `c4iw_ep_disconnect()`, `c4iw_ofld_send()`, `c4iw_cm_init()`, `c4iw_cm_term()`, and the global `c4iw_handlers[]` CPL dispatch table. Endpoint allocation and lifetime are handled by `alloc_ep()`, `c4iw_get_ep`/`c4iw_put_ep`, `_c4iw_free_ep()`, `release_ep_resources()`, and xarray mappings for `hwtids`, `atids`, and `stids`. Active-open flow is built by `c4iw_connect()`, `import_ep()`, `send_connect()`, `act_open_rpl()`, `act_establish()`, `send_flowc()`, and `send_mpa_req()`. Passive-open flow uses `c4iw_create_listen()`, `create_server4()`/`create_server6()`, `pass_accept_req()`, `accept_cr()`, `pass_establish()`, `process_mpa_request()`, `c4iw_accept_cr()`, and `send_mpa_reply()`. MPA handling lives in `process_mpa_reply()`, `process_mpa_request()`, `send_mpa_reject()`, and `connect_reply_upcall()`/`connect_request_upcall()`/`established_upcall()`. Teardown uses `peer_close()`, `peer_abort_intr()`, `peer_abort()`, `abort_rpl()`, `close_con_rpl()`, `terminate()`, `read_tcb()`/`read_tcb_rpl()`, and `complete_cached_srq_buffers()`.

Control flow: hardware and firmware CPLs enter through `c4iw_handlers[]`; most are queued by `sched()` into `rxq` and processed by `process_work()` under an ordered workqueue so endpoint freeing and upper-layer callbacks happen in sleepable context. Active connects allocate an endpoint, copy IWCM addresses/private data, reference the CM ID and QP, allocate an ATID, find an IPv4/IPv6 route, acquire an L2T entry, choose queues/window/MSS, send a CPL active-open request, handle `CPL_ACT_ESTABLISH`, send FLOWC, then transmit the MPA request. MPA reply data is accumulated across `CPL_RX_DATA` packets; once a full valid reply is available, the QP is modified to RTS with negotiated ORD/IRD and MPA attributes, and IWCM gets a connect-reply upcall. Passive listens allocate an STID/SFTID and install a server or filter; SYN/offload events allocate a child endpoint, route it, respond with pass-accept, wait for `CPL_PASS_ESTABLISH`, accumulate the MPA request, then deliver an IWCM connect-request upcall. ULP accept binds the QP, sends MPA reply, enters FPDU mode, and delivers established; reject sends MPA reject or aborts. Disconnect selects half-close versus abort from endpoint state and waits for close/abort CPLs or timer expiry.

State and persistence: all state is runtime-only. Persistent-looking data is held in endpoint structures and cxgb4 hardware TID/L2T/CLIP/server-filter tables until released. `struct c4iw_ep_common` stores CM ID, QP, device, state, mutex, kref, address pair, flags, history, preallocated skb list, and `wr_waitp`. `struct c4iw_ep` adds ATID/HWTID, TCP sequence/window parameters, route, L2T, MPA packet accumulation buffer, ORD/IRD, retry flags, timer, and SRQ abort cleanup fields. State transitions cover `IDLE`, `LISTEN`, `CONNECTING`, `MPA_REQ_WAIT`, `MPA_REQ_SENT`, `MPA_REQ_RCVD`, `MPA_REP_SENT`, `FPDU_MODE`, `ABORTING`, `CLOSING`, `MORIBUND`, and `DEAD`. Timers take an endpoint reference and enqueue timed-out endpoints to `timeout_list`; timeout processing may upcall failures and force aborts. Endpoint xarrays prevent stale TID lookups during concurrent CPL and teardown paths.

Dependencies and integration points: integrates with RDMA IWCM (`iw_cm_id`, IW events, QP transitions), cxgb4 lower-layer driver (`cxgb4_ofld_send`, TID allocation, server/filter setup, CLIP, L2T, BAR queues), Linux networking route/neighbour/VLAN/IPv6 APIs, TCP option parsing, sk_buffs, timers, workqueues, xarrays, and local driver helpers in `iw_cxgb4.h`, `qp.c`, `cq.c`, and `ev.c`. Module parameters control MPA revision, CRC/markers, read depth, TCP timestamps/SACK/window scaling, ECN, delayed ACKs, send/receive windows, peer-to-peer RTR behavior, congestion handling, and endpoint timeout.

Risks: this file has high concurrency and lifetime risk because CPLs, timers, ARP callbacks, user accept/reject calls, and QP teardown all manipulate the same endpoints. The `ep->mpa_attr.crc_enabled = (mpa->flags & MPA_CRC) | crc_enabled ? 1 : 0` expression is precedence-sensitive and effectively enables CRC whenever the global `crc_enabled` is nonzero. MPA packet `plen` is stored in a `u8` even though MPA v2 private data size includes the v2 parameter block and can exceed 255, so boundary behavior depends on earlier `MPA_MAX_PRIVATE_DATA` checks. Error paths frequently send callbacks while holding endpoint mutexes, so callback reentrancy must be audited. `pass_accept_req()` has repeated writes to `child_ep->com.local_addr`, which appears intentional for port normalization but is easy to regress. ARP failure paths synthesize fake CPLs to free endpoints in process context; missing references or skb ownership mistakes there can leak or double-free. Retry-with-MPA-v1 reuses the same endpoint and requires careful replenishment of the preallocated skb list. IPv6 CLIP get/release, ATID/HWTID xarray erase ordering, and TCB reread guard limits are important teardown edge cases.

Test signals: cover active IPv4 and IPv6 connect success, MPA v1 fallback from v2 reset, ORD/IRD negotiation including relaxed paths and insufficient-IRD TERM generation, private-data boundary and fragmented MPA headers, ARP failure on active open/accept/abort, TCAM full fallback to firmware offload connection WRs, connection-exists retry exhaustion, passive listen create/destroy with server and filter modes, peer close half-close transitions through `CLOSING`/`MORIBUND`, peer abort with SRQ cached buffer completion, timeout while MPA request/reply is in flight, fatal-device disconnect behavior, and xarray/TID cleanup under rapid connect/disconnect stress.

# sources/distributed-fs/ceph-client/drivers/infiniband/hw/cxgb4/cq.c

Purpose: completion queue implementation for `iw_cxgb4`. It creates and destroys hardware CQs, maps user CQs, arms CQs, polls Chelsio CQEs into RDMA core `ib_wc` completions, synthesizes software flush completions, handles out-of-order send/read completions, and supports SRQ completion reaping.

Important APIs, types, and functions: exported functions are `c4iw_create_cq()`, `c4iw_destroy_cq()`, `c4iw_poll_cq()`, `c4iw_arm_cq()`, `c4iw_cq_rem_ref()`, `c4iw_flush_rq()`, `c4iw_flush_sq()`, `c4iw_flush_hw_cq()`, `c4iw_count_rcqes()`, and `c4iw_flush_srqidx()`. Firmware resource setup is performed by `create_cq()` and `destroy_cq()` with `FW_RI_RES_WR` operations. Polling internals include `poll_cq()`, `c4iw_poll_cq_one()`, `__c4iw_poll_cq_one()`, `cqe_completes_wr()`, `create_read_req_cqe()`, `advance_oldest_read()`, `flush_completed_wrs()`, `reap_srq_cqe()`, and `post_pending_srq_wrs()`. Software completion helpers are `insert_recv_cqe()` and `insert_sq_cqe()`.

Control flow: CQ creation validates entry count/vector/flags, allocates a wait object and destroy skb, rounds queue size for status page and hardware requirements, allocates CQID plus coherent queue memory, sends a firmware CQ create WR, records GTS/BAR2 addresses, inserts the CQ into the device xarray, and for user CQs returns mmap keys for the CQ memory and GTS/BAR2 page. Polling locks the CQ, repeatedly calls `c4iw_poll_cq_one()`, skips nonready CQEs via `-EAGAIN`, and returns either completions or an error. `poll_cq()` chooses hardware versus software CQE, skips unrelated QP/TERMINATE/drain cases, rewrites read-response completions into read-request completions, handles out-of-order SQ completions through per-SQ shadow entries, advances SQ/RQ/SRQ indices, returns CQ credit by consuming CQEs, and marks WQs in error on CQE status or MSN mismatches. `__c4iw_poll_cq_one()` translates Chelsio opcodes/status values to `ib_wc` opcode/status/flags and invalidates local MR state for invalidate and failed fast-register completions. Destroy removes the CQ from the xarray, waits for references to drain, sends firmware reset, frees coherent memory, software queue, CQID, wait object, and saved destroy skb.

State and persistence: CQ state is runtime-only in `struct c4iw_cq` and embedded `struct t4_cq`: CQID, queue memory, software CQ ring, generation bits, GTS register, BAR2 mapping, vector, locks, refcount, completion for teardown, and wait object. User mmap state is persisted only in `struct c4iw_ucontext` `mmaps` list until the userspace mapping is consumed or context is destroyed. Queue indices and shadow SQ/SRQ state are persisted in memory across polls and flushes; hardware queue state lives in adapter memory until firmware reset.

Dependencies and integration points: depends on RDMA core CQ APIs, uverbs driver data, cxgb4 firmware RI resource WRs, Chelsio `t4_*` queue helpers/macros, xarrays in `struct c4iw_dev`, mmap helpers from `iw_cxgb4.h`, QP/SRQ internals, memory invalidation in `mem.c`, WR logging in `device.c`, and event dispatch in `ev.c`. CQ completion callbacks are invoked by `ev.c` after ingress queue notifications or async events.

Risks: polling is a subtle state machine; read-response rewriting assumes `oldest_read` is valid when a READ_RESP arrives. Out-of-order SQ completions and unsignaled WR reaping can corrupt accounting if SQ indices or CQE WRIDs are wrong. `c4iw_flush_hw_cq()` locks QPs conditionally and has a skip path that must always unlock the correct QP; changes here need lock-path review. User CQ creation has compatibility handling for older 32-byte CQE uverbs input, so response-size drift can break old providers. The CQ create error path must avoid double-freeing the preallocated destroy skb versus firmware-created resources. SRQ out-of-order reaping relies on absolute SRQ indices and pending WR lists; bad firmware CQEs can index outside expected valid receive entries if not bounded by lower helpers.

Test signals: create and destroy kernel and user CQs with minimum, maximum, and invalid entry counts; test vectors outside `nciq`; verify mmap key creation for CQ memory and GTS; poll send, recv, RDMA read/write, immediate, invalidate, local invalidate, and fast-register completions; inject CQE status values and verify `ib_wc` mapping; exercise unsignaled WR completion reaping, out-of-order read completions, software flush of SQ/RQ, SRQ in-order and out-of-order completion, CQ arm with missed-event reporting, and concurrent destroy while events hold CQ refs.

# sources/distributed-fs/ceph-client/drivers/infiniband/hw/cxgb4/device.c

Purpose: module and cxgb4 ULD glue for the Chelsio RDMA driver. It owns module parameters, debugfs diagnostics, low-level RDMA device allocation/open/close, resource-pool initialization, BAR/on-chip-memory mappings, cxgb4 receive/state/control callbacks, doorbell flow-control and recovery, WR wait-object allocation, and module load/unload registration.

Important APIs, types, and functions: module lifecycle is `c4iw_init_module()`/`c4iw_exit_module()`. ULD callbacks are described by `c4iw_uld_info` and implemented by `c4iw_uld_add()`, `c4iw_uld_rx_handler()`, `c4iw_uld_state_change()`, and `c4iw_uld_control()`. Device allocation/open/close flows through `c4iw_alloc()`, `c4iw_rdev_open()`, `c4iw_rdev_close()`, `c4iw_remove()`, `c4iw_dealloc()`, and `rdma_supported()`. Debugfs support includes `setup_debugfs()`, `qp_open()`, `stag_open()`, `stats_open()`, `ep_open()`, `wr_log_show()`, and `c4iw_log_wr_stats()`. Doorbell handling uses `stop_queues()`, `resume_queues()`, `resume_a_chunk()`, `recover_queues()`, and `recover_lost_dbs()`. Device-ucontext helpers are `c4iw_init_dev_ucontext()` and `c4iw_release_dev_ucontext()`. Wait objects are managed by `c4iw_alloc_wr_wait()` and `_c4iw_free_wr_wait()`.

Control flow: module init initializes CM workqueue state, creates root debugfs, creates a registration workqueue, and registers as `CXGB4_ULD_RDMA`. The cxgb4 lower layer first calls `c4iw_uld_add()` to allocate a small `uld_ctx`, then state `CXGB4_STATE_UP` triggers `c4iw_alloc()` and async `c4iw_register_device()`. Allocation validates RDMA-capable virtual resources, maps BAR2 or T4 on-chip queue memory, opens the RDMA resource device, initializes xarrays/locks/waitqueues, creates per-device debugfs, and starts with adapter IRD availability. Receive callbacks convert ingress descriptors or packet gather-lists to skbs, dispatch CPLs through `c4iw_handlers[]`, or route async-notification queue IDs to `c4iw_ev_handler()`. State `DOWN`, `FATAL_ERROR`, `START_RECOVERY`, and `DETACH` unregister and deallocate the RDMA device; fatal states also set `T4_FATAL_ERROR` and dispatch `IB_EVENT_DEVICE_FATAL`. Control callbacks throttle or recover doorbells on db-full/db-empty/db-drop signals.

State and persistence: all state is in memory and adapter resources. Global state includes `uld_ctx_list`, `dev_mutex`, `reg_workq`, debugfs root, and module parameters for T5 doorbell policies and WR logging. `struct c4iw_rdev` holds resource allocators, pool pointers, lldi snapshot, flags, BAR mappings, status page, statistics, queue limits, WR log, free workqueue, and pool krefs/completions. `struct c4iw_dev` owns the IB device, xarrays for CQs/QPs/MRs/TIDs, doorbell state/list, debugfs root, available IRD, and waitqueue used during teardown. Debugfs snapshots are generated at open time into vmalloc buffers and are not authoritative after open.

Dependencies and integration points: depends on cxgb4 ULD registration and lldi metadata, PCI BAR resources, gen pools/resource code in other driver files, RDMA device registration in `provider.c`, CPL handlers in `cm.c`, async events in `ev.c`, queue primitives from `t4.h`, Linux debugfs/seq_file/vmalloc, xarrays, workqueues, and IB event dispatch. It exposes module parameters used by CQ/QP/memory paths (`c4iw_wr_log`, doorbell tuning).

Risks: `c4iw_init_module()` returns `-ENOMEM` if `reg_workq` creation fails after `c4iw_cm_init()` and debugfs creation, but does not unwind those resources in that failure path. `c4iw_alloc()` error paths after BAR/ioremap can deallocate the IB device without unmapping already mapped BAR regions on some failures, which merits review. Debugfs snapshot generation counts xarray entries without holding locks, then allocates fixed-size buffers and later iterates under locks; it is intentionally racy and can truncate or miss entries. Doorbell recovery allocates a QP pointer list with `GFP_ATOMIC` proportional to active QPs and returns silently on allocation failure while state is in recovery path. Control-path statistics are partly updated under stats mutex and partly without it. `c4iw_dealloc()` waits for `hwtids` to empty and warns on other xarrays, so leaked endpoint refs can hang removal. Receive handling assumes descriptor opcode and gather-list layout match cxgb4 expectations; unexpected FL contents are logged and dropped.

Test signals: module init failure injection for workqueue/debugfs/cxgb4 registration, cxgb4 state transitions UP/DOWN/FATAL/DETACH, device allocation on unsupported VR layouts and unsupported host page sizes, BAR2/on-chip mapping failures, resource-pool create rollback, receive-path CPL dispatch with `gl == NULL`, `CXGB4_MSG_AN`, normal packet gather-list, and filter-hit RX packet synthesis, doorbell full/empty/drop recovery under active QPs, debugfs qps/stags/stats/eps/wr_log reads and clears, WR log wraparound, and removal with outstanding CQs/QPs/MRs/endpoints.

# sources/distributed-fs/ceph-client/drivers/infiniband/hw/cxgb4/ev.c

Purpose: asynchronous event and completion-notification handling for `iw_cxgb4`. It decodes error CQEs, maps hardware error status to RDMA core events, transitions affected QPs toward terminate/error handling, optionally wakes CQ completion handlers, and handles ingress queue notification queue IDs.

Important APIs, types, and functions: exported entry points are `c4iw_ev_dispatch()` for firmware CQE async events and `c4iw_ev_handler()` for CQ notification queue IDs. Internal helpers are `print_tpte()`, `dump_err_cqe()`, and `post_qp_event()`. `post_qp_event()` is the central path that logs the CQE, moves RTS QPs to `C4IW_QP_STATE_TERMINATE`, fills an `ib_event`, invokes the QP event handler, and triggers the CQ completion handler if the CQ was armed.

Control flow: `c4iw_ev_dispatch()` receives a CQE, looks up the QP by `CQE_QPID`, selects send or receive CQID based on CQE type, looks up the CQ, takes QP/CQ references under the QP xarray lock, then classifies the hardware status. Incoming RDMA write errors are treated as request errors. Access-like statuses become `IB_EVENT_QP_ACCESS_ERR`; ECC/internal statuses become `IB_EVENT_DEVICE_FATAL`; protocol/resource/MSN/overflow statuses become `IB_EVENT_QP_FATAL`; unknown statuses default to QP fatal. `c4iw_ev_handler()` is simpler: it looks up a CQ by queue ID, refs it, clears armed state, invokes the CQ comp handler under `comp_handler_lock`, then drops the ref.

State and persistence: no persistent state is owned by this file. It reads live QP/CQ xarrays, increments `c4iw_qp` and `c4iw_cq` references during callback delivery, may change QP state via `c4iw_modify_qp()`, and clears CQ armed state in the embedded `t4_cq`. Logging can read TPTE adapter state for offending STAGs.

Dependencies and integration points: depends on Chelsio CQE macros and TPTE read helpers, `c4iw_modify_qp()` from QP management, CQ ref management from `cq.c`, QP ref helpers, IB event and completion callbacks, and the receive/firmware dispatch paths in `device.c` and `cm.c`.

Risks: event handlers call driver/user-provided callbacks from interrupt-adjacent paths after taking refs but outside xarray locks; callback reentrancy into destroy paths depends on ref correctness. `post_qp_event()` checks QP state without taking the QP lock, so a concurrent state transition can race with the terminate transition. `dump_err_cqe()` reads TPTE for some ingress errors, which can fail or race with deregistration. CQ completion handler invocation assumes `ibcq.comp_handler` is valid; this is normal for registered CQs but sensitive during teardown. Bad CQID/QPID events are only logged and dropped, so missed error notification can leave higher layers waiting for normal completions.

Test signals: inject representative CQE statuses for access, fatal device, protocol fatal, unknown, and success-with-AE cases; verify QP event callback type and QP transition; verify armed CQ generates a completion callback after error; dispatch with missing QP and missing CQ; test STAG/TPTE logging on ingress write/read-response errors; run destroy-race stress where CQs/QPs are destroyed while async events are delivered.

# sources/distributed-fs/ceph-client/drivers/infiniband/hw/cxgb4/id_table.c

Purpose: small bitmap-backed ID allocator used by the cxgb4 RDMA resource layer for logical resource IDs such as TPT/STAG indices, QIDs, PDIDs, and SRQ table IDs.

Important APIs, types, and functions: `c4iw_id_table_alloc()` initializes `struct c4iw_id_table` with a start offset, number of entries, reserved entries, flags, spinlock, and bitmap. `c4iw_id_alloc()` finds the next clear bit from `last`, wraps to the first clear bit, marks it allocated, updates `last` either sequentially or pseudo-randomly, and returns logical ID `start + bit`. `c4iw_id_free()` clears an allocated bit. `c4iw_id_table_free()` frees the bitmap. Flags are `C4IW_ID_TABLE_F_RANDOM` and `C4IW_ID_TABLE_F_EMPTY`; `RANDOM_SKIP` bounds pseudo-random advancement.

Control flow: callers create a table during resource initialization, optionally pre-reserve low IDs unless the table starts empty, allocate/free IDs under the table spinlock, and destroy the table at device teardown. The random mode does not choose a fully random free bit; it randomizes the next starting hint after an allocation.

State and persistence: state is in-memory only: bitmap allocation state, logical start, maximum bit count, flags, `last` search hint, and spinlock. No hardware state is modified directly by this file; higher layers use returned IDs to program hardware tables.

Dependencies and integration points: depends on Linux bitmap helpers, random number generation, and `struct c4iw_id_table` from `iw_cxgb4.h`. It is consumed by resource initialization and allocation helpers outside this item, which in turn feed CQ/QP/MR/PD/SRQ creation.

Risks: `c4iw_id_free()` does not validate that `obj` is within range or currently allocated; caller bugs can clear arbitrary bitmap bits after unsigned subtraction. `c4iw_id_alloc()` returns `-1` in a `u32`, so callers must treat `0xffffffff` as failure or translate correctly; many local resource wrappers appear to use zero as their own failure sentinel, making boundary conventions important. Random mode only changes the next search hint and can still return predictable nearby IDs when the bitmap is sparse. Reserved-count validation is not local, so `reserved > num` would rely on bitmap helper behavior.

Test signals: allocate/free all IDs for sequential and random flags, wrap from end to beginning, reserve low IDs and verify they are skipped, empty-table flag behavior, exhaustion return handling, invalid free under KASAN/KMSAN-style tests, and concurrent allocate/free stress under IRQ-safe spinlock use.

# sources/distributed-fs/ceph-client/drivers/infiniband/hw/cxgb4/iw_cxgb4.h

Purpose: private shared header for the Chelsio `iw_cxgb4` RDMA driver. It defines the driver object model, resource tables, endpoint/QP/CQ/MR/SRQ/user-context structures, MPA and terminate wire formats, endpoint state/flag/history enums, inline helpers, mmap bookkeeping, state conversion helpers, and cross-file prototypes.

Important APIs, types, and functions: key structs are `c4iw_rdev`, `c4iw_dev`, `uld_ctx`, `c4iw_dev_ucontext`, `c4iw_ucontext`, `c4iw_pd`, `c4iw_mr`, `c4iw_mw`, `c4iw_cq`, `c4iw_qp`, `c4iw_srq`, `c4iw_ep_common`, `c4iw_ep`, and `c4iw_listen_ep`. Resource and stats types include `c4iw_id_table`, `c4iw_resource`, `c4iw_stats`, `c4iw_hw_queue`, and `wr_log_entry`. Important inlines include `cplhdr()`, `to_c4iw_dev()`, `get_chp()`, `get_qhp()`, `cur_max_read_depth()`, object container conversions, `c4iw_fatal_error()`, `c4iw_num_stags()`, WR wait helpers, `c4iw_ref_send_wait()`, mmap list helpers, QP state conversion helpers, `c4iw_ib_to_tpt_access()`, endpoint ref macros, `to_ep()`, `to_listen_ep()`, and `ocqp_supported()`. Important enums cover doorbell state, QP states and attr masks, endpoint states/flags/history, MPA/terminate layer codes, and mmap types.

Control flow: this header establishes shared contracts rather than executing a standalone flow. It lets `device.c` allocate and register `struct c4iw_dev`, `cm.c` manage `struct c4iw_ep` state and MPA negotiation, `cq.c` manage `struct c4iw_cq`, `mem.c` manage `struct c4iw_mr`, QP/SRQ/resource files manage queues and pools, and provider/uverbs paths translate RDMA core calls into these internals. `c4iw_ref_send_wait()` is a common synchronous firmware WR pattern: ref the wait object, send an skb through `c4iw_ofld_send()`, then wait up to `C4IW_WR_TO`, marking the device fatal on timeout.

State and persistence: the header defines all major runtime state layouts. Adapter-backed persistence is represented by IDs and addresses into TPT/PBL/RQT/OCQP/QP/CQ virtual resources, BAR mappings, status page, TID xarrays, and mmaps. User mappings are tracked by `c4iw_mm_entry` lists in each ucontext. Endpoint history and flags are bitfields intended for debugging and teardown decisions. Nothing here stores data beyond the loaded module/device lifetime.

Dependencies and integration points: includes Linux locking, xarray, completion, PCI, DMA, networking, waitqueue, kref, timer, I/O, workqueue, RDMA verbs/IWCM/netlink/restrack headers, cxgb4 ULD and L2T headers, Chelsio ABI, and local `t4.h`. The prototypes bind all driver subsystems: resource pools, provider registration, CM, CQ, QP, SRQ, memory registration, event dispatch, mmap, BAR2 addressing, and restrack fill helpers.

Risks: because this is the shared ABI between driver files, small layout or semantic changes can break user mmap handling, CQE size compatibility, QP state transitions, and firmware WR synchronization. `get_chp()` and `get_qhp()` return xarray entries without taking references, so callers must know whether they are under a lock or otherwise protected. `c4iw_wait_for_reply()` marks the whole device fatal on a synchronous WR timeout, a broad failure mode for transient firmware stalls. Endpoint ref macros are statement macros and do not guard against NULL. Several bitfields and comments carry typos (`remote_invaliate_disable`) or fixed widths that should be checked before adding larger values. `insert_flag_to_mmap()` classifies mappings using PCI resource ranges and on-chip memory base; BAR layout changes can silently alter mmap caching semantics.

Test signals: allmodconfig/modpost after any structure/prototype change, user ABI tests for 32-byte and 64-byte CQE creation responses, mmap tests for BAR/BAR_WC/contiguous/non-contiguous entries, firmware WR timeout injection to verify fatal-device propagation, QP state conversion matrix, endpoint refcount debug under connect/accept/reject/abort races, and compile coverage across architectures where `ocqp_supported()` changes behavior.

# sources/distributed-fs/ceph-client/drivers/infiniband/hw/cxgb4/mem.c

Purpose: memory registration and STAG/TPT/PBL management for `iw_cxgb4`. It writes adapter memory through ULP TX work requests, programs TPT entries, writes PBLs, registers user and DMA memory regions, allocates fast-registration MRs, maps scatterlists to fast-reg page lists, deregisters MRs, and invalidates local MR state after remote/local invalidate completions.

Important APIs, types, and functions: exported verbs hooks are `c4iw_get_dma_mr()`, `c4iw_reg_user_mr()`, `c4iw_alloc_mr()`, `c4iw_map_mr_sg()`, `c4iw_dereg_mr()`, and `c4iw_invalidate_mr()`. Adapter-memory writers are `_c4iw_write_mem_dma_aligned()`, `_c4iw_write_mem_inline()`, `_c4iw_write_mem_dma()`, and `write_adapter_mem()`. Registration helpers are `write_tpt_entry()`, `write_pbl()`, `dereg_mem()`, `allocate_stag()`, `finish_mem_reg()`, `register_mem()`, `alloc_pbl()`, and `c4iw_set_page()`. Module parameters `use_dsgl` and `inline_threshold` select DSGL/DMA versus inline memory writes.

Control flow: TPT writes allocate or reset a STAG index, fill `fw_ri_tpte` fields for validity, key, state, type, PD, permissions, bind enable, address type, page size, PBL address, length, and VA/FBO, then write it into adapter STAG memory. User MR registration validates unsupported DMA handles, length wrap and hardware size limits, pins pages with `ib_umem_get()`, allocates PBL space, iterates DMA blocks into page-sized chunks of big-endian PBL entries, writes those PBL chunks to adapter memory, then writes a valid TPT entry and inserts the MR into the device `mrs` xarray. DMA MR registration creates an all-memory STAG with no PBL. Fast-reg MR allocation reserves coherent memory for the memory page list, allocates PBL space and an initially invalid STAG, and inserts the MR. `c4iw_map_mr_sg()` fills the fast-reg MPL using `ib_sg_to_pages()`. Deregistration removes the MR from the xarray, frees coherent MPL memory, writes a reset TPT entry, frees PBL pool memory, releases umem and wait object, and frees the MR.

State and persistence: MR state is in `struct c4iw_mr`: RDMA core MR, optional `ib_umem`, driver device, deregistration skb, TPT attributes, coherent fast-reg MPL, DMA address, MPL lengths, and WR wait object. Hardware state persists in adapter TPT and PBL memory until deregistration resets the TPT entry and frees PBL pool space. A static atomic STAG key provides changing low-byte keys across allocations. Device stats track STAG usage in 32-byte TPT units.

Dependencies and integration points: depends on RDMA core memory APIs (`ib_umem_get`, `rdma_umem_for_each_dma_block`, `ib_sg_to_pages`), DMA mapping/coherent allocation, Chelsio firmware/TPT/ULPTX structures, resource and PBL pools, `c4iw_ref_send_wait()` and `c4iw_ofld_send()` from CM/device glue, `c4iw_ib_to_tpt_access()` from the header, xarray MR table used by CQ/event invalidation and debugfs, and QP fast-register send paths outside this work item.

Risks: `_c4iw_write_mem_dma()` does pointer arithmetic on `void *data`, which is a GNU C extension and should stay within kernel build assumptions. `_c4iw_write_mem_dma_aligned()` allocates with `GFP_KERNEL | __GFP_NOFAIL` when no skb is supplied, so memory pressure behavior can be severe. `write_tpt_entry()` frees a STAG resource whenever `reset_tpt_entry` is set, regardless of whether the adapter write succeeded, which could desynchronize software and hardware on write failure. `c4iw_alloc_mr()` error path calls `dereg_mem()` with `mhp->dereg_skb`, but this allocation path never initializes `dereg_skb`, so reset writes may allocate internally only if downstream supports NULL skb safely; this deserves focused review. Hardware size limits are explicit only for T4/T5 at 8 GiB. User registration uses a fixed `PAGE_SHIFT` instead of larger umem page sizes, potentially losing optimization. `c4iw_dereg_mr()` calls `ib_umem_release(mhp->umem)` even when `umem` is NULL; current helper behavior must remain NULL-safe.

Test signals: register and deregister DMA MR, zero-length-like and all-memory cases, user MR with invalid length/wrap/too-large T4/T5 range, multi-page PBL writes across page-sized chunks, DMA write fallback to inline when DSGL mapping fails, fast-reg MR allocation with maximum allowed SG count, scatterlist mapping overflow past `max_num_sg`, failed TPT/PBL write rollback, repeated STAG key reuse/invalidation, remote invalidate completion causing `c4iw_invalidate_mr()`, and fault injection for allocation, DMA mapping, firmware reply timeout, and xarray insertion failures.
