# sources/object-store/apache-ozone/hadoop-ozone/integration-test/src/test/java/org/apache/hadoop/ozone/client/rpc/OzoneRpcClientTests.java

Purpose: This abstract integration-test contract exercises the public Ozone RPC client API against a real `MiniOzoneCluster`. It is the broadest RPC client regression suite in this package, covering OM proxy wiring, S3 default volume behavior, volume/bucket/key lifecycle, quotas, ACL inheritance, replication configs, key read/write/rename/delete, checksums, multipart upload, object tagging, snapshots, GDPR metadata handling, stream writes, and several concurrency or failure paths.

Important APIs and types: The suite centers on shared static fixtures `MiniOzoneCluster cluster`, `OzoneClient ozClient`, `ObjectStore store`, `OzoneManager ozoneManager`, and `StorageContainerLocationProtocolClientSideTranslatorPB storageContainerLocationClient`. It drives `OzoneVolume`, `OzoneBucket`, `OzoneKey`, `OzoneKeyDetails`, `OzoneInputStream`, `OzoneOutputStream`, `OzoneDataStreamOutput`, `ClientProtocol`, `RpcClient`, `BucketArgs`, `VolumeArgs`, `OzoneQuota`, `OzoneAcl`, `OzoneObjInfo`, `OmKeyArgs`, `OmKeyInfo`, `OmMultipartInfo`, `OmMultipartCommitUploadPartInfo`, `OmMultipartUploadCompleteInfo`, `OzoneMultipartUploadPartListParts`, and replication classes such as `RatisReplicationConfig`, `StandaloneReplicationConfig`, and `ECReplicationConfig`. Helpers such as `startCluster`, `shutdownCluster`, `writeKey`, `writeFile`, `createTestKey`, `createTestKeyWithETag`, `verifyReplication`, `doMultipartUpload`, `uploadPart`, `completeMultipartUpload`, `validateOzoneAccessAcl`, and `assertBucketCount` define most of the reusable flows.

Control flow: `initialize` configures audit logging and a captured output stream; subclasses call `startCluster`, which tightens deletion-service intervals, configures the data stream packet size, builds a 14-datanode cluster, creates the RPC client, and stores OM/SCM clients. Early tests validate OM proxy addresses, default S3 volume metadata, owner setters, and volume/bucket creation options. Middle sections create objects, write and overwrite keys, inspect OM key metadata and container locations, toggle checksum verification, corrupt chunk files, and validate replica failover. Later sections run listing, rename, multipart, ACL, GDPR, S3, snapshot, stream upload, tagging, and empty key/file allocation scenarios. Several tests intentionally switch users or S3 authentication context, mutate OM metadata tables directly, suspend OM deletion services, or inject OM state-machine pauses to assert edge behavior.

State and persistence behavior: Persistent state spans OM RocksDB metadata tables for volumes, buckets, keys, deleted keys, multipart upload state, S3 secrets, object tags, key versions, ACLs, and snapshots, plus datanode container DBs and chunk files. The tests verify quota fields (`usedBytes`, `usedNamespace`, pending-delete bytes/namespace), bucket replication config, key generations and ETags, key location lengths, block commit sequence IDs, delete-table contents, versioned key-location groups, multipart part metadata, and object tags. Several tests wait for asynchronous deletion services or double-buffer flushes before asserting persistent state.

Dependencies and integration points: The file integrates the Ozone client surface with OM request handling, OM Ratis state-machine failure logging, SCM container and pipeline lookup, datanode container stores, Hadoop `FileSystem` paths for legacy bucket deletion, S3Auth and S3SecretManager, audit log output, bucket layout behavior for `OBJECT_STORE`, `LEGACY`, and `FILE_SYSTEM_OPTIMIZED`, snapshot retention and deletion services, checksum verification, network-topology-aware reads, and the client data stream path. It also depends on test utilities including `TestDataUtil`, `OzoneClientTestUtils.assertKeyContent`, `ClusterContainersUtil.corruptData`, and `GenericTestUtils.waitFor`.

Risks: Many tests are timing-sensitive because OM double-buffering, background deletion, container closure, Ratis writes, and datanode restarts must converge. Several are explicitly marked `@Flaky` or `@Unhealthy`, including parallel Ratis writes, namespace accounting, unhealthy replica reads, client leak detection, and parallel delete-bucket/create-key behavior. The suite mutates global/static state such as login user, S3 auth, OM filesystem-path config, captured output, and shared client references, so cleanup order matters. Some assertions depend on exact audit-log strings, OM exception result codes, or internal DB table layout rather than only public API behavior.

Test signals: Strong signals include exact `OMException.ResultCodes`, owner names under different users/S3 auth, quota and pending-delete counters, replication configs observed through SCM container metadata, key content and generation changes after rewrite, checksum-mismatch failures or replica failover success after corruption, multipart ETags and part ordering, ACL add/remove/set behavior and default ACL inheritance, GDPR metadata stripping from deleted keys, versioning behavior in key and deleted tables, bucket and snapshot list counts, stream-upload data equality, object-tag replacement without modification-time changes, and SCM allocation metrics for empty key versus empty file creation.

# sources/object-store/apache-ozone/hadoop-ozone/integration-test/src/test/java/org/apache/hadoop/ozone/client/rpc/TestBCSID.java

Purpose: This focused integration test verifies that a container's block commit sequence ID (BCSID) is propagated from a committed key into OM key metadata, reported by the datanode container report, and reloaded correctly after a datanode restart.

Important APIs and types: The test uses `MiniOzoneCluster`, `OzoneClient`, `ObjectStore`, `OzoneClientFactory`, `TestDataUtil.createKey`, `OmKeyArgs`, `OmKeyInfo`, `OmKeyLocationInfo`, `ReplicationConfig.fromTypeAndFactor`, `RatisReplicationConfig`, and datanode internals reached through `getDatanodeStateMachine().getContainer().getContainerSet().getContainer(...).getContainerReport().getBlockCommitSequenceId()`.

Control flow: `init` configures short container-report, command-status, heartbeat, and stale-node intervals, disables safe-mode pipeline creation, starts a one-datanode mini cluster, creates an RPC client, and creates a `bcsid` volume and bucket. `testBCSID` writes a RATIS/ONE key named `ratis`, looks the key up through OM, asserts there is exactly one latest block location, reads the same container's BCSID from the datanode container report, compares it with `OmKeyLocationInfo.getBlockCommitSequenceId()`, restarts the datanode with persistence, and checks the reported BCSID is unchanged.

State and persistence behavior: The key write commits a block to one datanode container and persists its BCSID in both container metadata and OM key-location metadata. The restart assertion verifies the datanode reload path preserves the persisted BCSID rather than resetting it or relying only on memory.

Dependencies and integration points: This test connects OM key lookup state with datanode container report state and SCM-facing report metadata. It relies on a real datanode container set, real key allocation/commit, and cluster restart support rather than mocks.

Risks: The single-datanode cluster makes the state easy to reason about but only covers RATIS/ONE. The assertions assume the created key lands in one block and that the datanode restart path completes cleanly before the report is queried. The test reaches through internal datanode structures, so refactors of container accessors can affect it even if public behavior is unchanged.

Test signals: The core signals are one block location, a datanode-reported BCSID greater than zero, equality between datanode report BCSID and OM `OmKeyLocationInfo` BCSID, and equality again after `restartHddsDatanode(0, true)`.

# sources/object-store/apache-ozone/hadoop-ozone/integration-test/src/test/java/org/apache/hadoop/ozone/client/rpc/TestBlockDataStreamOutput.java

Purpose: This integration suite validates the data-stream write path backed by `BlockDataStreamOutput`. It checks normal stream writes, recovery after container closure during a write, PutBlock and WriteChunk boundary behavior, total acknowledged data length accounting, and datanode version propagation into stream pipelines.

Important APIs and types: The file uses `MiniOzoneCluster`, `OzoneClient`, `OzoneClientFactory`, `ObjectStore`, `OzoneDataStreamOutput`, `KeyDataStreamOutput`, `BlockDataStreamOutputEntry`, `BlockDataStreamOutput`, `ByteBufferStreamOutput`, `XceiverClientManager`, `XceiverClientMetrics`, `OzoneClientConfig`, `ClientConfigForTesting`, `DatanodeRatisServerConfig`, `RatisClientConfig`, `UniformDatanodesFactory`, `DatanodeVersion`, `HddsDatanodeService`, `DatanodeDetails`, `ContainerProtos.Type`, and helpers from `TestHelper` and `ContainerTestHelper`.

Control flow: `createCluster` disables checksums, enables putBlock piggybacking, configures small chunk/flush/max/block/data-stream sizes, tightens Ratis timeouts, starts five datanodes at `SEPARATE_RATIS_PORTS_AVAILABLE`, waits for a RATIS/THREE pipeline, and creates one test volume and bucket. Parameter sources run selected tests with flush delay enabled and disabled and with data lengths around chunk and block boundaries. `testStreamWrite` writes data through `createStreamKey`, closes the stream, validates data, then repeats with `testWriteWithFailure`, which closes the active container between writes and verifies the second write succeeds on a new stream entry. Boundary tests compare Xceiver metrics before and after writes to ensure PutBlock occurs at the configured max-flush boundary and WriteChunk waits until the configured minimum packet size. The final tests inspect `BlockDataStreamOutputEntry` ack length and pipeline datanode versions.

State and persistence behavior: The suite persists streamed key data through the Ozone client and validates final object contents through `TestHelper.validateData`. Runtime state under inspection includes `KeyDataStreamOutput` stream entries, underlying `BlockDataStreamOutput`, pending and completed container operation metrics, acknowledged-byte counters, pipeline membership, and datanode version fields. Container closure during an open stream exercises stream rollover state and commit behavior.

Dependencies and integration points: It integrates the client data stream API with SCM block allocation, Ratis pipelines, Xceiver client metrics, datanode version negotiation, container closure handling, and Ozone client configuration. The cluster factory pins older datanode versions to ensure version fields are visible through both datanode internals and stream pipelines.

Risks: `testStreamWrite` is marked `@Flaky("HDDS-12027")`, reflecting timing sensitivity in stream/container closure behavior. Metric assertions can be affected by unrelated concurrent container operations if test isolation changes. Very small buffer sizes make boundary behavior deterministic but differ from production defaults. The test assumes the first stream entry is the active block stream for the inspected key.

Test signals: Key signals are byte-for-byte validation for several data lengths, successful duplicated content after writing across a forced container close, pending PutBlock count bounded by one extra pending operation, exactly two PutBlock operations for a 500-byte write with 400-byte max-flush boundary, no WriteChunk before two half-chunk writes accumulate to the minimum packet size, `getTotalAckDataLength()` equaling the written length after close, and every datanode and pipeline node exposing the configured old datanode version.
