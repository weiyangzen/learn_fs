# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath11k/rx_desc.h

Purpose: Defines the ath11k receive descriptor ABI shared by the datapath code and Qualcomm Wi-Fi hardware. The file is a packed register/TLV layout catalog for RX attention, MPDU start/end, MSDU start/end, and complete HAL RX descriptors across IPQ8074, QCN9074, and WCN6855 hardware families.

Important APIs, types, and constants: Enumerations classify RXPCU filter reasons (`enum rx_desc_rxpcu_filter`), software frame groups (`enum rx_desc_sw_frame_grp_id`), decapsulation formats (`enum rx_desc_decap_type`), decrypt status (`enum rx_desc_decrypt_status_code`), MSDU packet types, guard intervals, receive bandwidths, reception types, and RXDMA destination rings. The many `RX_*_INFO*` masks define bit positions for hardware status words, including frame validity, address-search-table status, PN/key/decrypt fields, MPDU/MSDU lengths, checksum/parser status, REO destination and flow IDs, first/last aggregate markers, VLAN handling, PHY metadata, and error flags. The packed layout structs are `struct rx_attention`, `struct rx_mpdu_start_ipq8074`, `struct rx_mpdu_start_qcn9074`, `struct rx_mpdu_start_wcn6855`, `struct rx_msdu_start_*`, `struct rx_msdu_end_*`, `struct rx_mpdu_end`, and full `struct hal_rx_desc_*` variants wrapped by `struct hal_rx_desc`.

Control flow and hardware programming model: This header has no executable code; control flow is implicit in how RX datapath code walks a hardware-filled descriptor. Hardware writes TLV tags followed by chip-specific start/end/attention blocks, optional header status, and then `msdu_payload[]`. Software decodes little-endian fields with `FIELD_GET()` masks, validates TLV ordering/descriptor completion through bits such as `RX_ATTENTION_INFO2_MSDU_DONE`, and routes packets based on REO destination, RXDMA destination, decrypt/parser/checksum status, frame group, and first/last MPDU/MSDU markers. The `hal_rx_desc_*` variants preserve hardware order and padding so code can select offsets based on `hw_params` without reinterpreting one chip's descriptor as another.

State and persistence behavior: The structures represent transient DMA-visible RX state, not durable storage. Descriptor contents persist only until the RX buffer is recycled. State encoded by hardware includes per-frame AST lookup results, sequence and QoS fields, PN/key IDs, PHY PPDU IDs, parsed L3/L4 metadata, checksums, flow IDs, REO queue addresses, and error flags. Because all structures are `__packed` with `__le16`/`__le32` fields, persistence across CPU endianness or compiler padding is explicitly not allowed; consumers must treat them as hardware ABI bytes.

Dependencies and integration points: The file depends on Linux bit macros (`BIT`, `GENMASK`), endian typedefs, Ethernet address length, and HAL datapath code that knows the active hardware revision. It integrates with receive processing in ath11k DP/HAL code, monitor mode and packet logging, REO routing, crypto/decrypt handling, checksum/offload reporting, flow-search/FSE/CCE classification, and WCN6855/QCN9074-specific code paths. The RU allocation constants at the end support HE/OFDMA receive metadata interpretation.

Risks and edge cases: The primary risk is ABI drift: any changed field order, padding byte count, mask, or chip-specific offset can corrupt packet decoding or DMA payload alignment. Several fields share names but move between `info` words on WCN6855 or QCN9074, so generic helpers must select the correct variant. Bit masks encode hardware errata and parser behavior, including fragmented buffers, PHY errors before MPDU headers, A-MSDU parser errors, FCS/decrypt/TKIP errors, and RX bitmap update failure. Length fields are limited by mask width and must be cross-checked with SKB/data-buffer sizes. The typo-like macro `RX_DESC_INFO0_RXPCU_MPDU_FITLER` and `RX_MSDU_END_INFO2_AMSDU_PARSET_ERR` are ABI symbols and should not be casually renamed if external code uses them.

Test signals: Build tests should cover all chip families that select these layouts. Runtime validation should exercise RX of management/control/data frames, multicast/broadcast, QoS/non-QoS, encrypted and unprotected frames, A-MPDU/A-MSDU first/last transitions, checksum offloads, monitor/PHY-error traffic, REO routing, and each hardware family's descriptor offsets. Fault-injection or packet-capture tests should verify FCS/decrypt/MIC/parser/length error propagation, VLAN padding/strip flags, WCN6855 first/last MSDU masks, QCN9074 cumulative checksum fields, and no descriptor overrun when header status or payload follows the packed descriptor.

# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath11k/spectral.c

Purpose: Implements ath11k spectral scan support. It configures firmware spectral scanning through WMI, allocates a direct-buffer ring for spectral FFT reports, parses firmware TLVs into the common ath spectral sample format, and exposes controls plus sample output through debugfs/relayfs.

Important APIs, types, and functions: Debugfs file operations implement `spectral_scan_ctl`, `spectral_count`, and `spectral_bins`. `ath11k_spectral_scan_config()` sets firmware parameters for disabled/background/manual modes, while `ath11k_spectral_scan_trigger()` clears and triggers sampling on a selected vdev. `ath11k_spectral_process_data()` is the direct-buffer callback registered by `ath11k_dbring_set_cfg()`, parses TLVs, and delegates FFT conversion to `ath11k_spectral_process_fft()`. `ath11k_spectral_pull_summary()` and `ath11k_spectral_pull_search()` decode little-endian TLV bitfields into host reports. Public lifecycle helpers include `ath11k_spectral_init()`, `ath11k_spectral_deinit()`, `ath11k_spectral_vif_stop()`, `ath11k_spectral_reset_buffer()`, `ath11k_spectral_get_mode()`, and `ath11k_spectral_get_dbring()`.

Control flow: Initialization first checks firmware service support (`WMI_TLV_SERVICE_FREQINFO_IN_METADATA`) and nonzero hardware FFT bin size. Per radio, it queries direct-buffer capabilities, initializes ring IDR/locks, sets up the SRNG, buffers, WMI direct-buffer config, initializes spectral defaults, and creates relayfs/debugfs files. Userspace writes `manual`, `background`, `disable`, or `trigger` to `spectral_scan_ctl`; under `conf_mutex`, the driver selects a vdev, updates `arvif->spectral_enabled`, records mode under `spectral.lock`, sends WMI disable/clear, configures scan parameters, and optionally triggers. Firmware DMA releases enter `ath11k_spectral_process_data()`, which takes `spectral.lock`, rejects disabled state, validates TLV signatures and lengths, decodes a scan summary, then decodes a scan search report into `struct fft_sample_ath11k` and writes it to the relay channel.

State and persistence behavior: Runtime state is held in `ar->spectral`: the direct-buffer ring, spinlock, relay channel, debugfs dentries, current mode, scan count, FFT size, enabled flag, and `is_primary` toggle for fragmented 160 MHz samples. `arvif->spectral_enabled` marks the vdev that owns scanning. State is volatile and reset on driver teardown, radio deinit, debugfs removal, or relay reset; no configuration is persisted outside kernel memory. The direct-buffer ring owns DMA buffers until cleanup, and relayfs buffers retain samples for userspace readers until read/reset/close.

Dependencies and integration points: The code depends on ath11k core/debug/WMI/direct-buffer APIs, `spectral_common.h` sample layout, Linux debugfs, relayfs, spinlocks, mutexes, and firmware-provided hardware spectral parameters (`fft_sz`, `fft_pad_sz`, `fft_hdr_len`, `summary_pad_sz`, `max_fft_bins`, `fragment_160mhz`). It integrates with vdev lifecycle via `ath11k_spectral_vif_stop()`, firmware DMA release through `ath11k_spectral_get_dbring()`, and debug infrastructure via `ar->debug.debugfs_pdev`. Sample consumers read the `spectral_scan` relay file in the ath common FFT format.

Risks and edge cases: TLV parsing is high-risk because malformed firmware data can otherwise overrun buffers; the code checks signature, TLV payload length, expected FFT bin length, minimum/maximum/power-of-two bin counts, and direct-buffer magic validation. Summary TLV length has a hardware bug workaround using `summary_pad_sz`, so hardware parameter mismatches can break parsing. 160 MHz fragmented sample handling relies on alternating `is_primary` and valid `freq2`; missing or reordered reports can swap primary/secondary frequency labeling. `ath11k_spectral_process_fft()` assumes a summary report was parsed before a search report; unexpected TLV order could use stale stack content if firmware violates that ordering. Debugfs writes can change `count` and `fft_size` while scanning, but changes are only applied after reconfiguration/trigger. Relay allocation failure disables the debug interface for that pdev.

Test signals: Useful tests include debugfs read/write of all modes, invalid strings, scan counts above 4095, non-power-of-two/too-small/too-large FFT bin requests, trigger while disabled, vdev removal with active spectral scan, and relay reset. Firmware or mocked direct-buffer tests should cover malformed signatures, short TLV headers, short payloads, invalid channel widths, bad bin counts, magic-value validation failure, summary padding variants, 20/40/80/160 MHz reports, fragmented 160 MHz primary/secondary alternation, and ring allocation/configuration failures. Integration tests should confirm WMI config fields match requested mode/count/FFT size and that relay samples contain correct big-endian FFT sample fields.

Test signals: Build configurations should compile with `CONFIG_ATH11K_SPECTRAL=y/m` and disabled. # sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath11k/testmode.c

Purpose: Implements nl80211 testmode support for ath11k. It exposes driver/firmware test commands, raw WMI passthrough, and factory test mode (FTM) segmented WMI command/event transport for calibration or manufacturing tools.

Important APIs, types, and functions: `ath11k_tm_policy` validates netlink attributes from the common ath testmode interface. `ath11k_tm_cmd()` is the cfg80211 testmode command entry point and dispatches `ATH_TM_CMD_GET_VERSION`, `ATH_TM_CMD_WMI`, `ATH_TM_CMD_TESTMODE_START`, and `ATH_TM_CMD_WMI_FTM`. Event handling enters through `ath11k_tm_wmi_event()`, which selects segmented or unsegmented processing based on `ATH11K_FLAG_FTM_SEGMENTED`. `ath11k_tm_process_event()` aggregates segmented FTM event payloads into `ab->testmode.eventdata`; `ath11k_tm_wmi_event_unsegmented()` forwards a raw WMI event directly to cfg80211. Command helpers include `ath11k_tm_cmd_get_version()`, `ath11k_tm_cmd_testmode_start()`, `ath11k_tm_cmd_wmi()`, and `ath11k_tm_cmd_wmi_ftm()`.

Control flow: Userspace sends cfg80211 testmode netlink data, which is parsed against `ath11k_tm_policy`. Version requests allocate a reply skb and return major/minor version attributes. Testmode start requires the radio to be `ATH11K_STATE_OFF`, allocates the FTM event aggregation buffer, moves the radio to `ATH11K_STATE_FTM`, and resets `ftm_msgref`. Raw WMI commands require data and WMI command ID, validate minimum TLV plus pdev/vdev ID space, rewrite the embedded pdev ID for pdev-set-param commands, optionally rewrite vdev IDs for vdev/unit-test commands outside FTM firmware mode, then sends through `ath11k_wmi_cmd_send()`. FTM commands set the segmented flag, require `ATH11K_STATE_FTM`, split payload into `MAX_WMI_UTF_LEN` chunks, wraps each chunk in `struct wmi_ftm_cmd` with sequence/total segment metadata, sends `WMI_PDEV_UTF_CMDID`, and increments `ftm_msgref`.

State and persistence behavior: Testmode state lives in `ab->testmode` and `ar`: `eventdata`, expected segment sequence, current data position, `ar->state == ATH11K_STATE_FTM`, `ar->ftm_msgref`, and `ATH11K_FLAG_FTM_SEGMENTED`. Data is transient and held only in kernel memory while the device is in test mode. Segmented event aggregation is protected by `ar->data_lock`; command/state transitions use `ar->conf_mutex`. The start path allocates `eventdata`, but this file does not free it; teardown/reset code elsewhere must own cleanup.

Dependencies and integration points: The code depends on `CONFIG_NL80211_TESTMODE`, cfg80211 testmode skb allocation/reply/event APIs, netlink attribute parsing, ath common testmode IDs from `../testmode_i.h`, ath11k WMI allocation/send/TLV parse helpers, firmware mode/state definitions, and `mac.c` registering `CFG80211_TESTMODE_CMD(ath11k_tm_cmd)`. WMI event dispatch in `wmi.c` calls `ath11k_tm_wmi_event()` for testmode events. It also integrates with per-vif command contexts when a raw WMI command needs a valid vdev ID.

Risks and edge cases: The WMI passthrough interface is intentionally powerful and trusts userspace-provided TLV payloads after only length and attribute checks; wrong command IDs or payloads can disturb firmware state. FTM segmented event processing increments `expected_seq` but does not explicitly compare it with `current_seq`, so missing/out-of-order segments may aggregate incorrectly if firmware misbehaves. `total_segments` is encoded in four bits, while command splitting should stay within that representable range; oversized payload policy is bounded by `ATH_TM_DATA_MAX_LEN` but must remain consistent with segment header limits. `set_bit(ATH11K_FLAG_FTM_SEGMENTED)` happens before command validation and is not cleared on failure in this file. The unsegmented event path chooses the first radio in FTM state, which is ambiguous if multiple radios could be in test mode. Allocation failures during command segmentation leave already-sent chunks in firmware.

Test signals: Build with and without `CONFIG_NL80211_TESTMODE`. Netlink tests should cover missing command/data/WMI ID attrs, oversized binary data, zero-length WMI data, short TLV buffers, unsupported commands, version reply contents, testmode start from OFF/ON/FTM states, and raw WMI vdev rewrite behavior with and without a vif. FTM tests should cover payloads exactly at, below, and above `MAX_WMI_UTF_LEN`, multi-segment `segmentinfo` encoding, `ftm_msgref` incrementing, firmware event aggregation across all segments, out-of-order/missing segments, invalid pdev IDs, absent pdev pointers, allocation failures, and forwarding through `cfg80211_testmode_event()`.

# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath11k/thermal.c

Purpose: Implements ath11k thermal integration. It registers each radio as a Linux thermal cooling device, optionally exposes a hwmon temperature input, sends WMI thermal mitigation commands for throttling, and synchronizes temperature reads with firmware events.

Important APIs, types, and functions: Cooling device callbacks are `ath11k_thermal_get_max_throttle_state()`, `ath11k_thermal_get_cur_throttle_state()`, and `ath11k_thermal_set_cur_throttle_state()`, collected in `ath11k_thermal_ops`. `ath11k_thermal_show_temp()` backs the read-only hwmon `temp1_input` attribute. `ath11k_thermal_event_temperature()` is called from WMI event handling to store a firmware-reported temperature and complete a pending read. Public lifecycle/control functions are `ath11k_thermal_register()`, `ath11k_thermal_unregister()`, and `ath11k_thermal_set_throttling()`.

Control flow: Registration skips work if the base device is already registered, then iterates radios, registers a cooling device named `ath11k_thermal`, stores it in `ar->thermal.cdev`, creates a `cooling_device` sysfs link under the wiphy device, and registers an hwmon device with `temp1_input` if hwmon is reachable. Setting a cooling state validates the requested state against `ATH11K_THERMAL_THROTTLE_MAX`, takes `conf_mutex`, sends a WMI thermal mitigation command if the radio is ON, and records the new state only on success. Reading temperature takes `conf_mutex`, requires `ATH11K_STATE_ON`, reinitializes `wmi_sync`, sends a pdev temperature WMI command, waits up to `ATH11K_THERMAL_SYNC_TIMEOUT_HZ`, then reads `ar->thermal.temperature` under `data_lock` and reports millidegree Celsius.

State and persistence behavior: Per-radio `ar->thermal` stores `cdev`, a completion used for synchronous WMI temperature reads, current throttle state protected by `conf_mutex`, and last temperature protected by `data_lock`. This is runtime-only state; cooling devices, sysfs links, and hwmon registrations are removed on unregister. Throttle state is cached in the driver but only affects firmware while the radio is ON; if the radio is OFF, `ath11k_thermal_set_throttling()` returns success without sending WMI.

Dependencies and integration points: The code depends on Linux thermal cooling device APIs, sysfs, hwmon, WMI thermal/temperature commands, ath11k state flags, and the WMI event path calling `ath11k_thermal_event_temperature()`. It integrates with userspace thermal policy through `/sys/class/thermal` cooling devices, with hwmon through `temp1_input`, and with the wiphy sysfs tree through a `cooling_device` link.

Risks and edge cases: Error unwind spans multiple radios and multiple subsystems; a failure after some registrations calls `ath11k_thermal_unregister()` for all radios, so unregister must tolerate partially initialized entries. `ath11k_thermal_register()` returns early when hwmon is not reachable, which can stop registration for later radios after registering the current cooling device. Temperature read blocks under `conf_mutex` while waiting for firmware completion, so slow firmware can delay other configuration paths. Crash flush returns `-ESHUTDOWN` after sending the temperature command. Throttling uses a single level with `priority = 0` and `dcoffpercent = throttle_state`, so policy semantics depend on firmware interpretation of duty-cycle/off-percent fields.

Test signals: Tests should cover registration/unregistration for one and multiple radios, thermal device registration failure, sysfs link failure, hwmon registration failure, non-hwmon builds, repeated unregister after partial registration, and absent `ar` entries. Runtime tests should read temperature while ON/OFF, simulate firmware completion and timeout, trigger crash-flush during a read, set throttle states 0, 1, 100, and 101, and verify WMI mitigation parameters (`pdev_id`, enable, duty cycle, low/high marks, off percent). Concurrency tests should cover temperature event arrival while a read is waiting and cooling state changes during radio stop/start.

Purpose: Declares ath11k trace events for packet logs, PPDU stats, RX descriptors, log messages, WMI commands/events, debug dumps, diagnostic TLVs, and peer power-save timestamps. It also provides empty inline trace helpers when ath11k tracing is disabled.

Important APIs, types, and events: The header sets `TRACE_SYSTEM ath11k` and `ATH11K_MSG_MAX 400`. Events include `ath11k_htt_pktlog`, `ath11k_htt_ppdu_stats`, `ath11k_htt_rxdesc`, log events from the `ath11k_log_event` class (`ath11k_log_err`, `ath11k_log_warn`, `ath11k_log_info`), `ath11k_wmi_cmd`, `ath11k_wmi_event`, `ath11k_log_dbg`, `ath11k_log_dbg_dump`, `ath11k_wmi_diag`, and `ath11k_ps_timekeeper`. Each event captures device/driver strings and event-specific fields, often including dynamic byte arrays for binary firmware/datapath payloads.

Control flow: When tracing is enabled, each `TRACE_EVENT()` expands into generated static tracepoint helpers that callers invoke around WMI send/receive, debug logging, HTT packetlog/stat handling, RX descriptor logging, diagnostics, and power-save tracking. When `CONFIG_ATH11K_TRACING` is not enabled, the header redefines `TRACE_EVENT`, `DECLARE_EVENT_CLASS`, and `DEFINE_EVENT` to generate inline no-op helpers and disabled predicates, allowing call sites to compile away tracing. The footer sets `TRACE_INCLUDE_PATH` and `TRACE_INCLUDE_FILE` and includes `<trace/define_trace.h>` outside the include guard, matching kernel tracepoint requirements.

State and persistence behavior: Trace events do not own persistent driver state. They snapshot runtime data into trace buffers when enabled: device names, driver names, WMI IDs and buffers, PPDU/pktlog/rxdesc blobs, formatted log strings, diagnostic TLVs, peer MAC addresses, timestamps, and peer power-save states. Dynamic arrays copy caller-provided buffers at trace time, so callers need only keep buffers valid for the call.

Dependencies and integration points: The header depends on Linux tracepoint macros and `core.h` for `struct ath11k` and `struct ath11k_base`. It integrates with tracefs/ftrace/perf tooling and with ath11k debug/log/WMI/HTT/DP call sites. The generated events are instantiated by `trace.c`; the include path is deliberately local instead of `include/trace/events`.

Risks and edge cases: Trace events copy arbitrary-length binary buffers into dynamic arrays, so call sites must pass accurate lengths and avoid tracing unbounded or sensitive data unless intended. `ath11k_log_dbg` formats into a fixed 400-byte dynamic array and warns on truncation, so long debug strings are clipped. Disabled tracing macro redefinitions must stay compatible with call-site expectations, especially `trace_<name>_enabled()` only being generated for `TRACE_EVENT` no-op definitions. The binary payload format is not self-describing beyond event fields, so userspace decoders must know the corresponding firmware/datapath structure versions.

Test signals: Compile with tracing enabled and disabled. Runtime tests should enable each ath11k tracefs event, trigger representative WMI commands/events, debug logs, packetlog/PPDU/RX descriptor paths, diagnostic TLVs, and peer power-save updates, then verify device/driver fields, lengths, IDs, dynamic array contents, and no truncation surprises for normal log messages. Negative tests should pass zero-length buffers where valid and confirm disabled tracing eliminates overhead-facing helper behavior without breaking call sites.
