# sources/distributed-fs/ceph-client/include/uapi/linux/nfsd_netlink.h

Purpose: generated UAPI netlink contract for the kernel NFS server generic-netlink family named `nfsd`, version `1`. The header is generated from `Documentation/netlink/specs/nfsd.yaml` by YNL tooling and exposes stable numeric command and attribute identifiers used by userspace administration and observability tools to query and configure nfsd state.

Important APIs/types/functions: this file defines only constants and anonymous enums, not C functions or structs. `NFSD_FAMILY_NAME` and `NFSD_FAMILY_VERSION` identify the generic-netlink family. Attribute sets include `NFSD_A_RPC_STATUS_*` for active RPC status records, `NFSD_A_SERVER_*` for server thread/time/scope/FH-key settings, `NFSD_A_VERSION_*` for NFS protocol version entries, `NFSD_A_SERVER_PROTO_VERSION` for nested protocol-version lists, `NFSD_A_SOCK_*` and `NFSD_A_SERVER_SOCK_*` for listener socket address/transport state, and `NFSD_A_POOL_MODE_*` for pool mode and pool count. `NFSD_CMD_*` enumerates operations: RPC status get, thread set/get, version set/get, listener set/get, and pool-mode set/get. Each attribute enum reserves value 0 implicitly and publishes a `*_MAX` derived from an internal `__*_MAX` sentinel for policy-table sizing.

Control flow: userspace does not call functions in this header; it builds generic-netlink messages using the family name and one `NFSD_CMD_*` command, then supplies or receives the command-specific attributes. The practical flows are request/response reads for `*_GET` commands and state-mutating requests for `THREADS_SET`, `VERSION_SET`, `LISTENER_SET`, and `POOL_MODE_SET`. RPC status responses are record-like messages carrying XID, flags, program, version, procedure, service time, IPv4/IPv6 source/destination addresses, ports, and compound operation metadata. Configuration flows depend on nested or repeated attributes for versions and sockets, as implied by the separate version, server-proto, socket, and server-socket attribute namespaces.

State and persistence behavior: the header itself holds no state. It names controls over live nfsd kernel state: thread counts, grace and lease times, server scope, file-handle key material, protocol versions, listener sockets, and pool mode. Persistence is external to this header and depends on nfsd/sysadmin tooling; netlink operations update or observe the kernel service state at runtime.

Dependencies and integration points: depends only on generated UAPI naming conventions and the Linux generic-netlink/YNL ecosystem. The kernel-side nfsd netlink implementation must keep its attribute policies, dump handlers, and command handlers in lockstep with these IDs. Userspace clients should prefer the YAML/YNL schema or this header rather than hard-coded numbers. Integration points include nfsd administrative tools, monitoring agents that inspect in-flight RPCs, service managers that set listener/thread configuration, and tests that validate UAPI compatibility.

Risks: because this is UAPI, renumbering any enum member would break existing userspace. Gaps are minimal, so additions must be appended before the relevant sentinel. Attribute type/endianness/length expectations are not visible in this header and must be read from the YAML spec or kernel policies, which creates risk for hand-written clients. Generated-file drift is also a risk: manual edits would be overwritten or become inconsistent with `nfsd.yaml`.

Test signals: compile tests should ensure the header is self-contained for userspace inclusion. Netlink/YNL tests should verify that `NFSD_FAMILY_NAME` resolves, every command accepts the documented attribute set, `*_MAX` values match kernel policies, GET dumps return parseable records, and SET commands reject missing or incorrectly typed attributes without altering nfsd state. Compatibility tests should exercise old clients after appending new attributes or commands.

# sources/distributed-fs/ceph-client/include/uapi/linux/nilfs2_api.h

Purpose: userspace ABI for NILFS2 filesystem management ioctls. It defines the data records used to inspect and mutate checkpoints, snapshots, segment usage, virtual-to-physical block mappings, garbage-collection descriptors, synchronization, resize, allocation range, and segment-usage updates.

Important APIs/types/functions: the key public records are `struct nilfs_cpinfo` for checkpoint metadata, `struct nilfs_suinfo` for segment usage, `struct nilfs_suinfo_update` for partial segment-usage writes, `struct nilfs_cpmode` for checkpoint/snapshot mode changes, generic userspace vector `struct nilfs_argv`, checkpoint interval `struct nilfs_period`, stats records `struct nilfs_cpstat` and `struct nilfs_sustat`, mapping records `struct nilfs_vinfo`, `struct nilfs_vdesc`, and block descriptor `struct nilfs_bdesc`. Inline helpers generated by `NILFS_CPINFO_FNS` test checkpoint flags (`snapshot`, `invalid`, `minor`); helpers generated by `NILFS_SUINFO_FNS` test `active`, `dirty`, and `error`; `nilfs_suinfo_clean()` checks for zero flags. `NILFS_SUINFO_UPDATE_FNS` creates set/clear/test helpers for `lastmod`, `nblocks`, and `flags` update masks. The ioctl API is anchored by `NILFS_IOCTL_IDENT` `'n'` and commands from `NILFS_IOCTL_CHANGE_CPMODE` through `NILFS_IOCTL_SET_SUINFO`.

Control flow: callers open a NILFS2 mount or filesystem device and issue ioctl commands with these records. Checkpoint mode changes pass `nilfs_cpmode`; checkpoint deletion passes a checkpoint number. Bulk queries use `nilfs_argv`, where `v_base` is a userspace pointer encoded as `__u64`, `v_nmembs` is the element count, `v_size` is each element size, `v_flags` carries request-specific flags, and `v_index` selects the starting checkpoint/segment/item. Cleaner flows are multi-vector: `NILFS_IOCTL_CLEAN_SEGMENTS` receives a five-element `nilfs_argv` array, tying together virtual info, vdescs, bdescs, periods, and segment numbers for garbage collection. `NILFS_IOCTL_GET_VINFO` and `GET_BDESCS` are read/write because the kernel resolves caller-provided descriptors into block mapping results. `NILFS_IOCTL_SYNC` returns a checkpoint number, while `RESIZE`, `SET_ALLOC_RANGE`, and `SET_SUINFO` push mutation parameters into the filesystem.

State and persistence behavior: the API exposes NILFS2's persistent checkpoint and log-structured segment model. Checkpoints can become snapshots or ordinary checkpoints, invalid/minor flags identify lifecycle state, and statistics report persistent counts. Segment usage records track last modification time, written-block counts, and active/dirty/error flags, which guide allocation and cleaner behavior. Virtual block and block descriptors bridge stable logical history to physical disk blocks. Ioctl mutations persist through the filesystem metadata files and on-disk checkpoint/segment structures defined separately in `nilfs2_ondisk.h`.

Dependencies and integration points: includes `<linux/types.h>` for fixed-width UAPI types and `<linux/ioctl.h>` for `_IO*` macros. It is consumed by NILFS2 utilities such as cleaners, checkpoint managers, snapshot tools, fsck-like inspectors, and tests. Kernel integration must validate `nilfs_argv` pointers and sizes, translate between these native-endian UAPI records and little-endian on-disk records, and coordinate with NILFS2 metadata files (`cpfile`, `sufile`, DAT, ifile).

Risks: `v_base` is a raw userspace pointer carried in `__u64`, so compat, bounds, alignment, and `copy_from_user`/`copy_to_user` validation are critical. Bulk ioctls can process many variable-sized records; incorrect `v_size` or `v_nmembs` handling risks short copies, overflow, or ABI confusion. Flag helpers use `1UL` while fields are fixed-width integers, so new flags must stay within field width. Cleaner ioctls are especially sensitive because bad block descriptors or segment-usage updates can cause data loss. ABI struct layout and ioctl numbers must remain stable.

Test signals: useful tests include UAPI compile tests on 32-bit and 64-bit userspace, structure-size/layout assertions, invalid `nilfs_argv` pointer and size fuzzing, checkpoint create/delete/snapshot mode round trips, segment usage query/update validation, garbage-collection ioctl dry-runs with known block maps, sync returning a monotonic checkpoint number, resize/allocation-range error cases, and regression tests for compat ioctl behavior.

# sources/distributed-fs/ceph-client/include/uapi/linux/nilfs2_ondisk.h

Purpose: UAPI description of NILFS2 on-disk layout. It defines little-endian persistent structures for inodes, super roots, superblocks, directory entries, segment summaries, block maps, DAT entries, checkpoints, and segment-usage files, plus constants for magic values, feature flags, mount options, inode numbers, block sizing, and metadata offsets.

Important APIs/types/functions: core persistent records include `struct nilfs_inode`, `struct nilfs_super_root`, `struct nilfs_super_block`, `struct nilfs_dir_entry`, `struct nilfs_finfo`, `struct nilfs_binfo_v`, `struct nilfs_binfo_dat`, `union nilfs_binfo`, `struct nilfs_segment_summary`, `struct nilfs_btree_node`, `struct nilfs_direct_node`, `struct nilfs_palloc_group_desc`, `struct nilfs_dat_entry`, `struct nilfs_snapshot_list`, `struct nilfs_checkpoint`, `struct nilfs_cpfile_header`, `struct nilfs_segment_usage`, and `struct nilfs_sufile_header`. Important macros compute metadata offsets and sizes (`NILFS_SR_*_OFFSET`, `NILFS_SR_BYTES`, `NILFS_SB_BYTES`, `NILFS_SB2_OFFSET_BYTES`, `NILFS_DIR_REC_LEN`, `NILFS_CPFILE_FIRST_CHECKPOINT_OFFSET`, `NILFS_SUFILE_FIRST_SEGMENT_USAGE_OFFSET`). Constants define special inodes (`NILFS_ROOT_INO`, `NILFS_DAT_INO`, `NILFS_CPFILE_INO`, `NILFS_SUFILE_INO`, `NILFS_IFILE_INO`, user inode start), mount/error flags, revision support, block-size limits, segment minimums, feature masks, directory file types, segment summary flags, and B-tree levels. Inline helper families set, clear, and test checkpoint flags and segment-usage flags with endian conversion; `nilfs_segment_usage_set_clean()` zeros a usage entry in little-endian form and `nilfs_segment_usage_clean()` tests cleanliness.

Control flow: this header is consumed by filesystem code and utilities that parse or construct NILFS2 media. Mount/recovery reads primary and secondary superblocks, checks `s_magic`, revision, feature masks, CRC fields, device geometry, and last segment/checkpoint pointers. Segment scanning reads `nilfs_segment_summary`, follows logical segment flags (`LOGBGN`, `LOGEND`, `SR`, `SYNDT`, `GC`), then interprets following `nilfs_finfo` and `nilfs_binfo` arrays to replay or validate log contents. The current filesystem root is discovered through a super root containing the DAT, checkpoint file, and segment usage file inodes. Checkpoint-file operations use `nilfs_cpfile_header`, `nilfs_checkpoint`, snapshot list links, and checkpoint flag helpers. Segment allocation and cleaning use `nilfs_sufile_header`, `nilfs_segment_usage`, and DAT entries to determine whether segments are clean, dirty, active, erroneous, protected, or reclaimable. Directory walking uses ext2-like record length and file-type fields.

State and persistence behavior: every multi-byte persistent field is explicitly little-endian except byte arrays and a few byte-sized fields. `nilfs_super_block` persists filesystem identity, geometry, mount/write timestamps, checkpoint and segment cursors, free-block accounting, feature negotiation, UUID, volume name, and commit thresholds. `nilfs_super_root` persists root metadata inodes outside the ifile so DAT, cpfile, and sufile are not garbage-collected like normal historical files. Checkpoints persist filesystem history and snapshot membership. DAT entries persist virtual-to-physical block validity intervals. Segment summaries persist log ordering, checksums, block counts, and whether a segment includes a super root or was written by the cleaner. Segment usage entries persist allocation/cleaning state.

Dependencies and integration points: includes `<linux/types.h>`, `<linux/magic.h>`, and `<asm/byteorder.h>`, so users must respect kernel UAPI integer and endian types. It integrates with `nilfs2_api.h` through semantic pairs: on-disk checkpoint and segment-usage structures are projected to userspace `nilfs_cpinfo` and `nilfs_suinfo`; DAT/block descriptors support cleaner ioctls; mount flags and feature masks drive VFS mount behavior. It also borrows ext2 directory-entry layout concepts and uses `__kernel_nonstring` for fixed-length volume names that need not be NUL-terminated.

Risks: on-disk ABI is extremely brittle: changing field order, size, endian handling, or computed offsets would break existing filesystems. CRC coverage depends on `s_bytes`, `NILFS_SB_BYTES`, and reserved-field exclusion, so mistakes can reject valid media or accept corrupt media. Directory record lengths and names require strict bounds checking to avoid overreads. Feature masks must cause safe read-only or mount refusal behavior for unknown features. Segment-summary and checkpoint flags drive recovery and garbage collection; incorrect interpretation can lose history or reclaim live data. The secondary superblock offset macro assumes valid device size arithmetic and needs overflow-aware callers.

Test signals: strong signals include mkfs/mount/recovery tests across block sizes from 1 KiB to 64 KiB, endian-conversion tests, structure-size and offset assertions, superblock CRC and feature-negotiation tests, primary/secondary superblock fallback, directory entry fuzzing, segment-summary replay with `LOGBGN`/`LOGEND`/`SR` combinations, checkpoint snapshot-list consistency checks, DAT validity interval tests, cleaner reclamation tests that ensure protected checkpoints remain intact, and compatibility tests against existing NILFS2 images.

# sources/distributed-fs/ceph-client/include/uapi/linux/nitro_enclaves.h

Purpose: UAPI ioctl contract for the AWS Nitro Enclaves kernel driver. It defines the commands, driver-specific errno-like values, flags, and request/response structures used by userspace enclave launch tooling to create an enclave VM slot, assign vCPUs and hugepage-backed memory, obtain image load placement, and start the enclave with a vsock CID.

Important APIs/types/functions: ioctl commands use magic `0xAE`: `NE_CREATE_VM` returns an enclave file descriptor from `/dev/nitro_enclaves`; `NE_ADD_VCPU` adds or auto-selects a vCPU through a `__u32` in/out parameter; `NE_GET_IMAGE_LOAD_INFO` exchanges `struct ne_image_load_info`; `NE_SET_USER_MEMORY_REGION` submits `struct ne_user_memory_region`; and `NE_START_ENCLAVE` exchanges `struct ne_enclave_start_info`. Driver-specific error codes occupy values 256 through 275, including CPU pool, vCPU ownership/core validity, memory alignment/hugepage/NUMA/max-region, missing resources, minimum memory, state, flag, and CID errors. Flags include `NE_EIF_IMAGE` for image type, `NE_DEFAULT_MEMORY_REGION`, and start modes `NE_ENCLAVE_PRODUCTION_MODE` and `NE_ENCLAVE_DEBUG_MODE`, with max-flag sentinels used by validation.

Control flow: the expected lifecycle is strict. First, the host configures the module CPU pool through `/sys/module/nitro_enclaves/parameters/ne_cpus`, leaving CPU 0 and siblings for the parent VM and selecting full cores from one NUMA node. Userspace opens `/dev/nitro_enclaves` and invokes `NE_CREATE_VM`, receiving an enclave fd. On that enclave fd, before start, it calls `NE_ADD_VCPU` one or more times; passing 0 requests auto-selection from the pool, otherwise the provided CPU must be available and valid. It calls `NE_GET_IMAGE_LOAD_INFO` to learn where the EIF image should be placed in enclave memory. It allocates suitably aligned hugepage-backed memory on the same NUMA node and registers regions with `NE_SET_USER_MEMORY_REGION`. Finally, `NE_START_ENCLAVE` validates resources, mode flags, full-core usage, minimum memory, and optional CID, then asks the Nitro hypervisor/PCI device to launch the enclave and returns an auto-generated CID when requested.

State and persistence behavior: the interface manages runtime kernel and hypervisor state, not persistent disk state. An enclave starts in an init state after `NE_CREATE_VM`; vCPU and memory ioctls are valid only in that state. `NE_START_ENCLAVE` transitions the enclave out of init, after which resource-setting ioctls fail with `NE_ERR_NOT_IN_INIT_STATE`. The driver tracks the creating mm and rejects certain operations from other address spaces with `EIO`. Memory regions remain pinned/associated for the enclave lifetime, and the returned enclave fd owns subsequent configuration and lifetime operations. The CPU pool is module parameter state shared across enclave creations.

Dependencies and integration points: includes `<linux/types.h>` and relies on ioctl encoding from transitive UAPI use. It integrates with the Nitro Enclaves PCI device, Linux CPU topology and NUMA accounting, hugepage allocation and `get_user_pages()`, anonymous file descriptors, `/dev/nitro_enclaves`, module parameters, and AF_VSOCK CID allocation. Userspace launchers must coordinate image loading, hugepage reservation, CPU isolation, and vsock setup with the exact sequencing documented here.

Risks: the ABI exposes host resources to a privileged launcher, so validation of CPU ownership, full-core assignment, NUMA consistency, page size, hugepage contiguity, address alignment, and CID reservation is security-sensitive. The `__u64` address and size fields require overflow and range checks. State-machine errors could allow changing resources after launch or starting an under-provisioned enclave. Error values above 255 are driver-specific and may not behave like conventional errno on all userspace paths unless documented handling is used. Debug-mode flag handling is sensitive because it changes enclave confidentiality expectations.

Test signals: tests should exercise the full happy path with configured CPU pools and hugepage memory, plus negative cases for no CPU pool, duplicate vCPU, vCPU outside pool, partial cores, cross-NUMA memory, unaligned and non-hugepage memory, too-small memory, too many regions, invalid flags, invalid/well-known/parent CIDs, operations from a different mm, repeated start, and resource ioctls after start. ABI tests should assert ioctl numbers, structure sizes, and in/out behavior for auto-selected vCPU, image memory offset, and autogenerated CID.

# sources/distributed-fs/ceph-client/include/uapi/linux/nl80211-vnd-intel.h

Purpose: Intel vendor-extension UAPI for `nl80211` wireless commands and events under Intel OUI `0x001735`. It defines command and attribute IDs used by Intel wireless drivers/userspace to coordinate CSME-owned Wi-Fi connections, host ownership handoff, and roaming-forbidden notifications.

Important APIs/types/functions: `INTEL_OUI` identifies the vendor namespace. `enum iwl_mvm_vendor_cmd` defines `IWL_MVM_VENDOR_CMD_GET_CSME_CONN_INFO` (`0x2d`), `IWL_MVM_VENDOR_CMD_HOST_GET_OWNERSHIP` (`0x30`), and `IWL_MVM_VENDOR_CMD_ROAMING_FORBIDDEN_EVENT` (`0x32`). `enum iwl_vendor_auth_akm_mode` names authentication modes: open, RSNA, RSNA-PSK, SAE, and max. `enum iwl_mvm_vendor_attr` defines sparse vendor attribute IDs for interface MAC, peer/AP MAC, SSID, station cipher, roaming-forbidden boolean, auth mode, channel number, band, colocated AP channel, and colocated AP address. `NUM_IWL_MVM_VENDOR_ATTR` and `MAX_IWL_MVM_VENDOR_ATTR` provide bounds for policy arrays.

Control flow: the documented ownership handoff begins when CSME firmware owns the device and may already be connected. The kernel asserts RFKILL with a device-not-owned reason so regular Wi-Fi operations do not race the firmware. Userspace asks for CSME connection info via `GET_CSME_CONN_INFO`, checks for a matching profile, installs a supplicant network constrained to the reported BSSID and frequency, suppresses full scans, then asks iwlmei for host ownership with `HOST_GET_OWNERSHIP`. iwlmei requests ownership from CSME; once granted, iwlwifi lifts RFKILL, loads firmware, connects quickly to the same AP, reports the connection back to CSME, and preserves connectivity. `ROAMING_FORBIDDEN_EVENT` is an event path carrying the roaming-forbidden state and VIF address.

State and persistence behavior: no persistent state is defined here. The attributes describe live firmware/driver connection state such as SSID, BSSID, channel, band, cipher, authentication mode, colocated 6 GHz AP details, interface address, and whether roaming is currently forbidden. Ownership state is a runtime relationship among CSME firmware, iwlmei, iwlwifi, rfkill, NetworkManager, and wpa_supplicant.

Dependencies and integration points: this header plugs into the generic `nl80211` vendor command framework, keyed by Intel OUI and these command IDs. Kernel integration spans Intel MVM wireless code, iwlmei CSME mediation, iwlwifi device bring-up, rfkill reporting, cfg80211/nl80211 policy validation, NetworkManager, and wpa_supplicant. Attribute semantics require userspace and kernel to agree on binary MAC address sizes, SSID length (0 to 32 octets), integer widths, and band numbering (`0` for 2.4 GHz, `1` for 5.2 GHz, `2` for 6 GHz).

Risks: sparse numeric IDs must remain stable for userspace compatibility. The ownership handoff is timing-sensitive: scans, roaming, or mismatched BSSID/frequency can break the goal of preserving the CSME TCP connection. Attribute validation is security-relevant because malformed MAC/SSID/channel/auth/cipher values cross a vendor netlink boundary. The header contains only IDs and comments, so implementers must consult the driver policy for exact nla types. Firmware capability differences and 6 GHz colocated AP handling can create compatibility edge cases.

Test signals: good coverage includes nl80211 vendor policy tests for every attribute ID and type, simulated CSME-active and CSME-idle ownership flows, RFKILL reason propagation, userspace profile matching with fixed BSSID/frequency, suppressed-scan behavior, fast reconnect preserving IP/TCP state, roaming-forbidden event delivery with VIF address, 2.4/5/6 GHz band and colocated AP attributes, and ABI checks that command and attribute numeric values do not change.
