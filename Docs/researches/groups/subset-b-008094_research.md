# sources/object-store/apache-ozone/hadoop-ozone/ozone-manager/src/main/java/org/apache/hadoop/ozone/om/OmSnapshotManager.java

Purpose: `OmSnapshotManager` is the Ozone Manager coordinator for filesystem snapshots. It owns snapshot DB checkpoint loading, snapshot reader cache lifecycle, snapshot-diff RocksDB setup, snapshot-diff APIs, snapshot feature startup safety checks, checkpoint directory cleanup, and snapshot creation limit accounting.

Important APIs/types/functions: The class implements `AutoCloseable` and exposes cache access through `getSnapshotCache`, `invalidateCache`, `invalidateCacheEntry`, `getActiveSnapshot`, `getSnapshot`, and `getActiveFsMetadataOrSnapshot`. Snapshot DB/checkpoint helpers include `createOmSnapshotCheckpoint`, `deleteSnapshotCheckpointDirectories`, `getSnapshotPath`, `extractSnapshotIDFromCheckpointDirName`, `getSnapshotPrefix`, `isSnapshotKey`, `isSnapshotFlushedToDB`, `areSnapshotChangesFlushedToDB`, and `isSnapshotPurged`. Snapshot-diff entry points are `submitSnapshotDiff`, `getSnapshotDiffResponse`, deprecated `getSnapshotDiffReport`, `cancelSnapshotDiff`, and `getSnapshotDiffList`. `snapshotLimitCheck`, `decrementInFlightSnapshotCount`, `resetInFlightSnapshotCount`, and `getInFlightSnapshotCount` enforce the configured filesystem snapshot limit.

Control flow: Construction starts by checking whether filesystem snapshots are enabled and refusing OM startup if the feature is disabled while `SnapshotInfoTable` still contains snapshots. It initializes RocksDB options and column-family metadata for the snapshot-diff DB, opens the DB under the configured diff directory, creates or finds the job/report/purged-job column families, and drops unknown intermediate column families left by failed diff jobs. It builds an `OmSnapshotLocalDataManager`, an LRU-like `SnapshotCache` backed by a Guava `CacheLoader`, and a `SnapshotDiffManager`; if snapshots are enabled it starts `SnapshotDiffCleanupService`.

State and persistence behavior: Persistent state spans the active OM RocksDB snapshot tables, checkpoint directories under the OM snapshot parent directory, per-snapshot local metadata files managed by `OmSnapshotLocalDataManager`, and a separate snapshot-diff RocksDB containing job, report, and purged-job column families. `createOmSnapshotCheckpoint` creates or reuses a RocksDB checkpoint, writes snapshot local metadata into the checkpoint, and batch-deletes bucket-scoped rows from deleted-key, deleted-dir, and snapshot-renamed tables in the active DB. Snapshot reads poll until the create transaction has flushed to disk, read local metadata to select the snapshot checkpoint version, and open an `OmMetadataManagerImpl` on that checkpoint. Cache entries hold open RocksDB handles and are invalidated or closed explicitly through the snapshot cache. `deleteSnapshotCheckpointDirectories` locks the snapshot cache entry, finds the smallest existing version with binary search, and deletes checkpoint directories in version order for crash-recoverable cleanup.

Dependencies/integration points: The class is tightly integrated with `OzoneManager`, `OmMetadataManagerImpl`, `SnapshotChainManager`, `SnapshotInfo`, `SnapshotUtils`, `SnapshotCache`, `OmSnapshotLocalDataManager`, `SnapshotDiffManager`, `SnapshotDiffCleanupService`, RocksDB managed wrappers, `RDBStore`, `TransactionInfo`, OM locks, and request/background-service code that purges keys or snapshots. `getActiveFsMetadataOrSnapshot` bridges normal metadata reads and `.snapshot/<name>/...` filesystem paths, including linked-bucket resolution before permission-sensitive snapshot reads.

Risks: Startup gating is intentionally strict; disabling snapshots with residual snapshot metadata aborts OM startup. Snapshot loading depends on transaction flush visibility and local metadata presence, so lagging followers, recent creates, or missing local metadata surface as `TIMEOUT` or `FILE_NOT_FOUND`. The snapshot cache owns live DB handles, so failing to close or invalidate entries can leak RocksDB resources. Snapshot limit accounting uses an in-flight counter with a comment noting known leader/prepare-state accounting weaknesses. Snapshot-diff DB column-family cleanup drops unknown column families at startup, which assumes all unknown families are failed intermediate diff artifacts. Several RocksDB setup failures are converted to unchecked `RuntimeException` TODO paths rather than graceful OM exceptions.

Test signals: `TestOmSnapshotManager` covers the feature-disable safety check, cache eviction and DB close behavior, snapshot path formatting, idempotent checkpoint creation, snapshot limit behavior, and checkpoint directory deletion ordering. Snapshot transaction flush helpers are covered by `TestSnapshotInfo`; snapshot local metadata and create-loader regressions are covered in `TestOmSnapshotLocalDataManager`; integration tests such as `TestOmSnapshot`, `TestOzoneFsSnapshot`, `TestOzoneManagerHASnapshot`, and snapshot background-service suites exercise snapshot reads, diff submission, cleanup, and HA behavior.

# sources/object-store/apache-ozone/hadoop-ozone/ozone-manager/src/main/java/org/apache/hadoop/ozone/om/OmSnapshotMetrics.java

Purpose: `OmSnapshotMetrics` is the metrics source used by snapshot metadata readers. It counts read-only key, filesystem, ACL, listing, and object-tagging operations against snapshots and their failures.

Important APIs/types/functions: The class is `@Metrics(context = "dfs")`, implements `OmMetadataReaderMetrics`, and exposes a singleton through `getInstance()`. It registers itself with `DefaultMetricsSystem` under the source name `OmSnapshotMetrics` using a `MemoizedSupplier`. Metric fields are `MutableCounterLong` counters annotated with `@Metric`, including per-operation counters plus aggregate `numKeyOps` and `numFSOps`.

Control flow: The private constructor prevents direct construction. The first `getInstance()` call registers the source with the default Hadoop metrics system; subsequent calls return the memoized instance. Each `inc...` method increments the operation-specific counter, and selected methods also increment aggregate counters. Key lookup, key info, list status, file status, lookup file, and object-tagging calls increment `numKeyOps`; list status, file status, and lookup file also increment `numFSOps`. Failure methods increment only failure counters.

State and persistence behavior: State is in-memory metrics-system counter state. There is no RocksDB or filesystem persistence. The singleton lifetime follows the process metrics system, so counters accumulate for the registered OM process unless the metrics system is reset by tests or process restart.

Dependencies/integration points: The class depends on Hadoop metrics2 (`MetricsSystem`, `DefaultMetricsSystem`, `MutableCounterLong`) and the `OmMetadataReaderMetrics` contract shared by active and snapshot metadata readers. Snapshot `KeyManagerImpl`, prefix manager, and metadata-reader paths can use this object to account operations performed against snapshot DBs separately from active OM metrics.

Risks: The counters rely on metrics2 injection during registration; calling increment methods on an unregistered manually constructed instance would leave fields null, but construction is private and `getInstance` registers it. Aggregate counters are hand-maintained, so new operations added to `OmMetadataReaderMetrics` need deliberate aggregate updates. Failure counters do not increment aggregate operation counters, which is a semantic choice that consumers must understand.

Test signals: There is no direct test found for this file in the searched subset. Indirect signals are metrics registration through snapshot metadata-reader construction and assertions in broader snapshot read/list/get-file-status tests that drive the corresponding reader APIs without metrics-related null pointer failures.

# sources/object-store/apache-ozone/hadoop-ozone/ozone-manager/src/main/java/org/apache/hadoop/ozone/om/OzoneAclUtils.java

Purpose: `OzoneAclUtils` centralizes ACL helper logic for OM request paths. It maps multi-tenant access IDs back to user principals and performs owner-aware ACL checks across volume, bucket, key, and prefix resources.

Important APIs/types/functions: `setOMMultiTenantManager` installs the static `OMMultiTenantManager` used by `accessIdToUserPrincipal`. `checkAllAcls` applies hierarchical ACL checks through an `OmMetadataReader`. `getParentNativeAcl` converts a child ACL operation into the required parent ACL when the native authorizer is enabled. The private `isOwner` helper compares the caller short user name to an owner name.

Control flow: `accessIdToUserPrincipal` returns the access ID unchanged when no multi-tenant manager is installed or when lookup misses; otherwise it returns the principal from `getUserNameGivenAccessId`. `checkAllAcls` switches on resource type. For volumes it checks the target volume directly with owner substitution against the volume owner. For bucket, key, and prefix resources, volume owners are checked directly against the child resource using the volume owner as `{OWNER}`; non-volume owners must first pass a parent volume ACL check and then pass the child ACL check using the bucket owner as `{OWNER}`. For native authorizer bucket checks, the parent right is computed by `getParentNativeAcl`; otherwise the parent right defaults to `READ`.

State and persistence behavior: The only mutable state is the process-static multi-tenant manager reference. The file does not persist anything. ACL decisions are delegated to the supplied `OmMetadataReader`, which reads OM metadata and authorizer state.

Dependencies/integration points: It depends on `OMMultiTenantManager`, `OmMetadataReader.checkAcls`, `OmMetadataReader.isNativeAuthorizerEnabled`, `IAccessAuthorizer.ACLType`, `OzoneObj.ResourceType`, `OzoneObj.StoreType`, Hadoop `UserGroupInformation`, and caller network identity fields. The utility is used by OM handlers that need consistent ACL behavior for active metadata and snapshot metadata readers.

Risks: The static tenant manager is global process state, so tests and multi-OM lifecycles must reset or set it carefully. Owner comparison uses `getShortUserName`, which means Kerberos realm-qualified names are reduced before comparison. The parent ACL mapping is policy-sensitive: bucket creation maps to parent `WRITE`, most bucket operations map to volume `READ`, and key/prefix create/write map to bucket `WRITE` while delete/read/list/ACL operations map to bucket `READ`. Changes to native authorizer semantics must update this function and its callers together. An unexpected resource type throws `OMException(INVALID_REQUEST)`.

Test signals: Direct test references were not found in the searched subset, but snapshot ACL integration tests and OM ACL request tests exercise this helper through `checkAcls` paths. Useful targeted tests would cover access-ID fallback, volume-owner bypass behavior, non-owner parent plus child checks, native parent ACL mappings for bucket/key/prefix operations, and invalid resource types.

# sources/object-store/apache-ozone/hadoop-ozone/ozone-manager/src/main/java/org/apache/hadoop/ozone/om/OzoneConfigUtil.java

Purpose: `OzoneConfigUtil` provides small server-side configuration helpers for OM code, currently replication-config preference resolution and capping client-provided numeric limits against server limits.

Important APIs/types/functions: `resolveReplicationConfigPreference` chooses a `ReplicationConfig` from client protobuf fields, bucket defaults, or OM defaults. `limitValue` caps a client numeric configuration value to a server maximum and enforces a minimum usable page size of two. The class is a final static utility with an SLF4J logger.

Control flow: Replication resolution first checks whether the client supplied a replication type other than `HddsProtos.ReplicationType.NONE`. If so, it builds a `ReplicationConfig` from the client type, factor, and EC config, then asks `OzoneManager.validateReplicationConfig` to reject unsupported choices. If the client supplied no type and the bucket has a `DefaultReplicationConfig`, that bucket default wins. If neither client nor bucket default is present, the method returns `ozoneManager.getDefaultReplicationConfig()`. `limitValue` starts with the client value, caps it to the server value when it exceeds the server limit, logs the cap at debug level, then raises any result less than or equal to one to two.

State and persistence behavior: There is no mutable state or persistence. The returned replication config may come from the supplied bucket object or OM default, and validation side effects are limited to `OzoneManager.validateReplicationConfig`.

Dependencies/integration points: It depends on HDDS replication model classes (`ReplicationConfig`, `DefaultReplicationConfig`, `HddsProtos`) and `OzoneManager` for validation/defaults. `limitValue` is designed for paged/list-style server APIs where client limits must not exceed server-supported limits and where page size one can cause a non-recursive `listStatus` loop involving `startKey`.

Risks: Client replication preference bypasses bucket defaults by design, so validation must be kept strong enough to prevent unsupported configs. `limitValue` applies the minimum of two after max capping, which means a server limit of zero or one still results in two; callers must only use it for APIs where that lower bound is valid. The page-size loop comment is specific to file-status/listStatus behavior and should not be generalized blindly to unrelated numeric configs.

Test signals: `TestOzoneConfigUtil` covers EC bucket defaults, server defaults, client EC preference, and RATIS bucket defaults. The searched tests do not directly cover `limitValue`; listStatus and file-status paging tests provide indirect signal for the minimum page-size behavior.

# sources/object-store/apache-ozone/hadoop-ozone/ozone-manager/src/main/java/org/apache/hadoop/ozone/om/OzoneListStatusHelper.java

Purpose: `OzoneListStatusHelper` implements FSO bucket `listStatus` assembly. It validates the requested volume/bucket/path/start key, converts filesystem paths into FSO database keys, merges directory and key table iterators in sorted order, and returns `OzoneFileStatus` entries with correct absolute key names and replication metadata.

Important APIs/types/functions: The public API is `listStatusFSO(OmKeyArgs args, String startKey, long numEntries, String clientAddress, boolean allowPartialPrefixes)`. The nested `GetFileStatusHelper` functional interface lets callers inject the existing file-status lookup path. Internal helpers are `validateStartKey`, `getStartKeyPrefixIfPresent`, `getSortedEntries`, `getStatus`, `getDbKey`, and `getId`.

Control flow: `listStatusFSO` first requires non-null `OmKeyArgs`, reads volume and bucket rows, and returns an empty list when either is missing. If `startKey` is present with a non-empty prefix key, it must be a sibling or immediate child of the requested key; otherwise the result is empty. If `startKey` is present with an empty requested key, the helper derives the listing prefix from `startKey`'s parent and rebuilds `OmKeyArgs`. It asks the injected status helper for the requested path. Missing status means the prefix is not a valid filesystem path but may be a list-keys prefix, so `getDbKey` resolves its parent path and target file name. File status returns a singleton file unless partial prefixes are allowed; directories list by constructing an FSO child prefix from volume ID, bucket ID, and directory object ID. It then derives an optional DB start-key prefix and calls `getSortedEntries`.

State and persistence behavior: The helper is stateless after construction except for references to `OMMetadataManager`, SCM block size, status helper, and OM default replication. It reads volume, bucket, directory, and key metadata tables and does not write. Returned `OzoneFileStatus` objects wrap `OmKeyInfo` values; for directories a synthetic `OmKeyInfo` is built from `OmDirectoryInfo` and its replication config is overwritten with bucket default or OM default replication. For files, the key name is mutated to the absolute listed path before wrapping.

Dependencies/integration points: It depends on FSO metadata key construction in `OMMetadataManager.getOzonePathKey`, bucket layout, `ListIterator.MinHeapIterator` and `HeapEntry` to merge directory/key tables, `OzoneFSUtils` path utilities, `OMFileRequest` helpers for absolute paths and directory-to-key conversion, `OmVolumeArgs`, `OmBucketInfo`, `OmDirectoryInfo`, `OmKeyInfo`, and `OzoneFileStatus`. The injected `GetFileStatusHelper` integrates this list implementation with the normal OM file-status API and its client-address/sort-datanodes semantics.

Risks: The method uses empty-list returns for missing volume/bucket, invalid start key, and missing parent prefix, so callers must distinguish "not found" behavior from an empty directory at higher layers if needed. File `OmKeyInfo` objects from metadata are mutated by `setKeyName`, which is acceptable only if callers do not reuse shared cached instances with the original relative key name assumption. `getDbKey` requires the parent path to resolve to a non-null status and uses `Objects.requireNonNull`, so unexpected status-helper nulls become runtime null failures. The sorted merge intentionally avoids `putIfAbsent` because null statuses are meaningful placeholders; changing that map logic can alter duplicate directory/key handling.

Test signals: Integration coverage is visible in FSO filesystem listStatus tests, including `AbstractRootedOzoneFileSystemTestWithFSO`, which notes consistency with table cache. Targeted test signals should include missing volume/bucket returning empty, sibling/immediate-child `startKey` validation, blank prefix plus start key derivation, file singleton behavior when partial prefixes are disabled, partial-prefix listing through parent DB key resolution, directory listing by object ID, sorted directory/key merge order, and page-size behavior with `startKey`.
