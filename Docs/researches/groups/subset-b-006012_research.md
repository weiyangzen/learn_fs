# sources/distributed-fs/ceph-client/kernel/bpf/btf.c

Purpose: this file is the kernel-side implementation of BPF Type Format handling for the copied Ceph client kernel tree. It parses, validates, indexes, exposes, and consumes BTF metadata for userspace-loaded BPF programs, vmlinux, modules, verifier argument modeling, map value special fields, kfunc registration, CO-RE relocation, typed pretty-printing, and struct_ops registration. It is a central bridge between raw `.BTF` bytes and the rest of the BPF verifier/runtime.

Important APIs/types/functions: the main private object is `struct btf`, which owns raw BTF data, decoded type pointers, string table pointers, resolved type IDs/sizes, IDR object ID, refcount/RCU lifetime, split-BTF base links, module/vmlinux identity, kfunc/dtor/struct-meta/struct-ops tables, and optional layout/base-id relocation state. `struct btf_verifier_env` carries parser phase, log, DFS visit state, and resolve stack. `struct btf_kind_operations` dispatches per-kind behavior through `check_meta`, `resolve`, member checks, logging, and show callbacks. Public or cross-subsystem entry points include `btf_new_fd()`, `btf_get_by_fd()`, `btf_get_fd_by_id()`, `btf_get_info_by_fd()`, `btf_put()`, `btf_type_by_id()`, `btf_name_by_offset()`, `btf_find_by_name_kind()`, `bpf_find_btf_id()`, `btf_parse_vmlinux()`, `btf_ctx_access()`, `btf_struct_access()`, `btf_prepare_func_args()`, `btf_check_type_match()`, `bpf_core_apply()`, `register_btf_kfunc_id_set()`, `register_btf_fmodret_id_set()`, `register_btf_id_dtor_kfuncs()`, `btf_type_seq_show_flags()`, `btf_type_snprintf_show()`, and `__register_bpf_struct_ops()`.

Control flow: userspace BTF loading enters through `btf_new_fd()`, which calls `btf_parse()`, allocates a kernel copy of the submitted blob, initializes verifier logging, parses the header, validates section layout, installs string/layout pointers, walks the type section, resolves all required type references, validates type tags, parses special map-value struct metadata, finalizes the log, allocates an IDR object ID, and returns an anonymous inode fd. Parsing is intentionally two-pass: `btf_check_all_metas()` first validates per-record metadata and builds `btf->types`; `btf_check_all_types()` then resolves references through a bounded DFS stack so forward references, cycles, struct/array member sizes, modifiers, pointers, vars, funcs, datasecs, and decl tags can be checked after all type IDs are known. Kernel BTF follows related but separate flows through `btf_parse_vmlinux()` and `btf_parse_module()`, using built-in or module `.BTF` sections, split-BTF base handling, sorted-name acceleration, optional module relocation against vmlinux BTF, module notifier publication, and sysfs export.

Kind-specific validation is table driven. Integers validate bit offsets, encoding, size, and member containment. Modifiers and type tags validate target type IDs and naming rules. Pointers validate byte-aligned member placement and resolve through modifiers to avoid pointer loops. Arrays validate element and index types, regular integer indices, overflow of `nelems * elem_size`, and member containment. Structs/unions validate names, member type IDs, monotonic offsets for structs, zero offsets for unions, member bounds, and bitfield rules. Enums and enum64 validate size, names, signedness flag usage, and enumerator names. Func/proto checks validate linkage, argument names, varargs, return/argument resolution, and `FUNC -> FUNC_PROTO` links. Vars/datasecs validate linkage, section names, variable placement, and section bounds. Floats validate supported sizes and minimum alignment. Decl tags validate tag values, component indexes, and legal target kinds.

State and persistence behavior: loaded BTF objects are runtime kernel objects, not persistent filesystem state. User BTF owns copied `btf->data`; vmlinux BTF points at linker-provided `__start_BTF`/`__stop_BTF`; module BTF owns copied module data and may be removed on module unload. Object IDs live in the global `btf_idr` protected by `btf_idr_lock`; after publication all frees go through `btf_put()` and RCU. Split BTF stores `base_btf`, `start_id`, and `start_str_off`, and lookups walk to base BTF when requested type or string IDs fall below those offsets. `resolved_ids` and `resolved_sizes` cache verifier resolution results for later size lookup and showing. Module BTF state is tracked in `btf_modules`, protected by `btf_module_mutex`, with live-state flags, sysfs attributes, and cache purges on coming/going transitions.

Dependencies and integration points: the file depends on UAPI BTF/BPF definitions, verifier logging, IDR, anon inodes, RCU, sysfs/kobject, module notifiers, kallsyms, net/xdp, socket/skmsg/perf/BPF LSM helpers, bpf struct_ops, kfunc ID sets, and `../tools/lib/bpf/relo_core.h` for CO-RE relocation calculation. It is tightly integrated with the BPF syscall API, verifier register/type model, map value validation, module loader, `/sys/kernel/btf`, proc fdinfo, BPF iterator conventions, tracing/LSM/struct_ops/extension program attach paths, and libbpf CO-RE relocation semantics.

Verifier and access integration: `btf_prepare_func_args()` converts function BTF into verifier argument constraints for global functions and typed subprograms, including `arg:` decl tags for `ctx`, `trusted`, `untrusted`, `nonnull`, `nullable`, and `arena`. `btf_ctx_access()` and `btf_struct_access()` walk BTF structs to translate verifier memory accesses into scalar, pointer-to-BTF-ID, untrusted memory, or nested-struct results while rejecting direct access to special allocation fields. `btf_check_type_match()` compares extension program prototypes against targets. `btf_distill_func_proto()` turns BTF prototypes into function models for calling/JIT constraints. Context helpers translate userspace-visible program contexts to kernel context types through the generated `bpf_ctx_convert` BTF object.

Map field and ownership behavior: `btf_parse_fields()` discovers special fields in structs or datasecs, including spin locks, timers, work queues, task work, refcounts, kptr/uptr fields, list/rbtree roots, and graph nodes. It validates offsets, alignment, uniqueness, allowed combinations, nested struct/array repetition, and record ordering, then stores a `struct btf_record` with cached offsets and kptr destructor/module metadata. `btf_check_and_fixup_fields()` links graph roots to value records, rejects ownership cycles, and enforces `uptr` restrictions. This code is security-sensitive because these fields influence map value lifetime, object ownership, destructor calls, and verifier access restrictions.

Kfunc, CO-RE, and struct_ops behavior: kfunc registration maps program types to hook buckets, validates every registered BTF ID as a `FUNC -> FUNC_PROTO`, validates iterator kfunc naming/prototype rules, relocates module IDs when needed, merges vmlinux sets, and supports per-hook filters plus fmodret sets. Destructor kfunc registration validates `void func(type *)` prototypes and optional CFI constraints, then keeps a sorted map from owned type IDs to destructor function BTF IDs. CO-RE support finds compatible target candidates in vmlinux first and modules second, caches candidate lists under `cand_cache_mutex`, invalidates module candidates on module load/unload, and invokes libbpf relocation calculation/patching helpers. Struct_ops registration attaches `bpf_struct_ops_desc` objects to the owning BTF when BPF JIT support is enabled.

Risks: the highest risks are verifier soundness and lifetime correctness. A missed BTF validation case can let malformed metadata confuse size, offset, pointer-trust, or function-argument reasoning. Integer overflow checks around section lengths, member offsets, array products, type counts, and copy sizes are critical. Recursive type resolution is bounded by `MAX_RESOLVE_DEPTH`, so valid but deeply nested BTF can fail, while missed cycle detection would be unsafe. Module BTF references require careful refcounting because module unload can race kfunc, CO-RE, and kptr destructor lookups. Candidate caches must be purged on module topology changes to avoid stale BTF pointers. User-facing BTF info and pretty-printing paths must copy safely and avoid leaking raw kernel pointers unless explicitly requested. IDR publication means failure paths after `btf_alloc_id()` must use `btf_put()` semantics, not direct frees.

Test signals: strong signals include BPF selftests for valid and malformed BTF blobs across every `BTF_KIND_*`, split BTF and module BTF relocation tests, fuzzing of header/section offsets and string/type sections, cycle/depth tests for pointers/modifiers/structs/arrays, enum64/float/type-tag/decl-tag validation cases, map special-field tests for kptr/uptr/timer/workqueue/list/rbtree/refcount combinations, module load/unload race tests around BTF ID lookup and CO-RE candidate cache invalidation, `BPF_OBJ_GET_INFO_BY_FD` ABI tests, verifier tests for global function arguments and `arg:` tags, kfunc registration/prototype/iterator tests, CO-RE relocation tests against vmlinux and module candidates, fd/id/refcount leak tests, and typed show tests that exercise safe copy, zero elision, arrays, bitfields, enums, and pointer formatting.

# sources/distributed-fs/ceph-client/kernel/bpf/btf_iter.c

Purpose: this source file is a kernel-tree shim that builds the shared libbpf BTF iterator implementation from `../../tools/lib/bpf/btf_iter.c` into the kernel BPF directory. The local file contains only the SPDX line and an `#include` of the tools implementation; all substantive iterator logic lives in the included file.

Important APIs/types/functions: no local functions, structs, or state are declared here. The effective APIs are those provided by the included `tools/lib/bpf/btf_iter.c`, which is expected to implement BTF type/string iteration helpers used by BTF tooling or relocation logic shared between kernel and tools code. The only direct contract in this wrapper is the relative include path and the dual-license SPDX expression `(LGPL-2.1 OR BSD-2-Clause)`.

Control flow: there is no runtime control flow in this wrapper. At compile time, the preprocessor replaces this file with the contents of the shared implementation. Any initialization, iterator stepping, termination, or error handling occurs inside the included tools source and must be reviewed there for behavioral changes.

State and persistence behavior: this wrapper has no state and persists nothing. Any iterator cursor state, temporary parsing state, or lifetime rules are owned by the included implementation and by its callers. Because this is a textual include, static symbols in the included file are compiled as if they were written in this translation unit.

Dependencies and integration points: the wrapper depends on the source tree retaining `kernel/bpf/btf_iter.c` at a relative depth where `../../tools/lib/bpf/btf_iter.c` is valid. It integrates the kernel BPF build with the shared tools/lib/bpf implementation, avoiding a forked copy. This means build flags, include search paths, and kernel/tool compatibility macros must satisfy the included code.

Risks: the main risk is source sharing drift. A change in the tools implementation can affect the kernel build even though this wrapper is unchanged. Relative include movement, license incompatibility, or assumptions in the tools file about userspace headers, allocation, errno, or endianness could break kernel compilation or behavior. Static symbol names from the included file are scoped to this translation unit, but macro environment differences can still change semantics.

Test signals: useful signals are kernel build coverage for this translation unit, tools/libbpf build coverage for the original implementation, compile tests after moving either directory, and behavioral tests that exercise the iterator APIs through their actual callers. Any change to `tools/lib/bpf/btf_iter.c` should be validated in both userspace/tooling and kernel build contexts.

# sources/distributed-fs/ceph-client/kernel/bpf/btf_relocate.c

Purpose: this source file is a kernel-tree shim that compiles the shared libbpf BTF relocation implementation from `../../tools/lib/bpf/btf_relocate.c` inside the kernel BPF directory. The local file itself contains only the SPDX declaration and a textual include; all relocation algorithms are in the included tools source.

Important APIs/types/functions: the wrapper declares no local functions or types. The effective behavior is whatever `tools/lib/bpf/btf_relocate.c` provides, most importantly the BTF relocation routines consumed by `btf.c` when parsing module split BTF with a distilled base and mapping those base IDs to vmlinux IDs. The local file's only explicit API surface is its relative include path and dual license.

Control flow: there is no local runtime flow. During compilation the included relocation source becomes this translation unit. In the surrounding BTF subsystem, the important runtime path is module parsing: `btf_parse_module()` may parse a `.BTF.base`, call `btf_relocate()`, store `base_id_map`, and then use `btf_relocate_id()` to remap BTF IDs in kfunc and destructor registration. The detailed matching and relocation decisions are delegated to the included implementation.

State and persistence behavior: this wrapper owns no state. Relocation state is transient in the included relocation code and persists only through outputs such as the relocated BTF object's adjusted metadata and `btf->base_id_map` held by `btf.c`. That map is later freed with the BTF object.

Dependencies and integration points: depends on `../../tools/lib/bpf/btf_relocate.c` being present and compatible with kernel compilation. It integrates shared libbpf relocation code with kernel module BTF loading, split-BTF support, and later ID relocation for kfunc/dtor tables. Because it is a textual include, the kernel build environment supplies the headers, macros, and symbol visibility available to the tools implementation.

Risks: relocation bugs can silently associate module BTF type IDs with incorrect vmlinux types, which can corrupt verifier reasoning, kfunc registration, CO-RE candidate matching, and destructor lookup. Since the local file is only a shim, reviewers might miss behavioral changes in the included tools file. The relative include path is fragile under tree reorganization. Shared userspace/kernel code must avoid APIs or allocation patterns that are valid in one environment but not the other.

Test signals: key signals are module BTF load tests with and without `.BTF.base`, negative tests for incompatible distilled bases, verification that `base_id_map` remaps kfunc and dtor IDs correctly, BPF selftests that load modules with split BTF and run CO-RE/kfunc programs against them, and build tests for both the kernel wrapper and the original tools implementation after relocation code changes.
