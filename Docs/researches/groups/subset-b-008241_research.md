# sources/object-store/rustfs/crates/ecstore/src/bucket/replication/replication_pool.rs

Purpose: Implements the RustFS replication worker pool and its global scheduling facade. It accepts object and delete replication work, fans it out to regular, large-object, and MRF retry workers, persists overflowed failures for restart recovery, initializes global replication stats, and bridges bucket resync lifecycle calls to `ReplicationResyncer`.

Important APIs and types: `ReplicationPool<S>` owns worker channels, active counters, `ReplicationStats`, storage, worker limits, MRF persistence channels, task handles, and an embedded `ReplicationResyncer`. `ReplicationPoolOpts` selects `ReplicationPriority::{Fast, Slow, Auto}` and maximum worker caps. `ReplicationQueueAdmission::{Skipped, Queued, Missed}` reports queue outcomes, with `merge()` making `Missed` dominate `Queued`, and `Queued` dominate `Skipped`. `ReplicationOperation` wraps either `ReplicateObjectInfo` or `DeletedObjectReplicationInfo` and implements `ReplicationWorkerOperation`, including conversion to `MrfReplicateEntry`. `ReplicationPoolTrait` exposes object-safe async operations through `DynReplicationPool` and the `GLOBAL_REPLICATION_POOL`/`GLOBAL_REPLICATION_STATS` once cells.

Control flow: `ReplicationPool::new()` derives regular/MRF worker counts from priority, applies max caps, creates bounded Tokio MPSC channels, spawns large, regular, and failed/MRF workers, then starts MRF replay and MRF persistence background tasks. Regular and large workers consume `ReplicationOperation` values and call `replicate_object()` or `replicate_delete()`; regular and MRF object workers also increment and decrement per-bucket queue stats. Object queueing hashes bucket plus object name to a stable worker channel, while large objects of at least `MIN_LARGE_OBJ_SIZE` are hashed onto the large-worker pool. Heal and existing-object operations are routed directly to MRF retry workers. Delete queueing follows the same regular-or-MRF routing but always records zero-size delete queue stats.

State and persistence behavior: Live state is held in Tokio `RwLock`/`Mutex` structures and atomic active-worker counters. Overflowed normal queue work is converted to `MrfReplicateEntry` and sent to `mrf_save_tx`; the persister flushes pending entries to `config/replication/mrf.bin` every 10 seconds or after 1000 entries. Startup MRF replay reads that file, decodes entries, re-queues object entries through `queue_replication_heal()` after fresh `get_object_info()`, re-queues delete entries through `schedule_replication_delete()`, then clears the file only after processing the entries. Resync state is loaded from `${BUCKET_META_PREFIX}/{bucket}/.replication/resync.bin`, cached in the resyncer map, and auto-resumed only for `ResyncPending` and `ResyncStarted`; failed resync targets are deliberately skipped until manually restarted.

Dependencies and integration points: The pool depends on `StorageAPI + NamespaceLocking` for object IO and locks, `ObjectIO` for config persistence, `ReplicationStats` for queue/proxy metrics, `BucketTargetSys` and `metadata_sys` for heal decision setup, `save_config`/`read_config` for metadata files, `rustfs_filemeta` replication structs and status maps, Tokio channels/tasks, and `CancellationToken` for resync startup/cancel. Public entry points `schedule_replication()`, `schedule_replication_delete()`, `queue_replication_heal()`, and `queue_replication_heal_internal()` are the integration layer used by object mutation paths, MRF replay, and healing/resync scans.

Resync integration: `start_bucket_resync()` creates or updates a target status as `ResyncPending`, persists it, registers a cancellation token keyed by bucket and ARN, then spawns `ReplicationResyncer::resync_bucket()`. `cancel_bucket_resync()` cancels the token and marks the target `ResyncCanceled`. `init_resync_internal()` launches `start_resync_routine()`, which repeatedly calls `load_resync()` until it succeeds or the supplied token is cancelled. `load_resync()` reads persisted metadata for each bucket, repopulates the in-memory map, and starts a new resync task for any target still pending or started.

Scheduling details: `schedule_replication()` converts an `ObjectInfo` and `ReplicateDecision` into `ReplicateObjectInfo`, preserving target status maps, purge status maps, replication state, actual size, tags, timestamps, and operation type. Synchronous decisions call `replicate_object()` immediately; asynchronous decisions use the global pool. `schedule_replication_delete()` queues delete work and updates stats for pending delete targets. `queue_replication_heal_internal()` builds a heal `ReplicateObjectInfo`, skips zero mod-time objects and missing configs, routes failed/pending normal objects to object heal work, routes delete markers and version-purge failures to delete heal work, and fans existing-object delete resync across selected targets using `queue_replicate_deletes_wrapper()`.

Risks: Backpressure fallback to MRF is lossy when the MRF save channel is full; warnings state that dropped entries will not be retried. The MRF persister overwrites the file with only its current in-memory pending buffer, so if the file already contains unreplayed entries while the process is running, callers must ensure startup replay has cleared or requeued them before new flushes become authoritative. `resize_failed_workers()` sends kill notifications but the spawned shared-receiver MRF workers do not read `mrf_worker_kill_tx`, so decreasing `mrf_worker_size` changes the counter but may not actually stop workers until channels close. `ReplicationPoolTrait::resize()` calls `self.resize(...)`, but no inherent `resize` method is present in this file; this may rely on another method not shown by this file or be a recursion/compile risk. MRF replay for object entries skips objects that are no longer found, while delete entries avoid source lookups; that asymmetry is intentional but important for recovery semantics. The global once cells make reconfiguration difficult after initialization. Worker task handles are stored but no shutdown/join lifecycle is implemented here.

Test signals: Unit tests cover queue-admission merge ordering, auto-resume status selection, MRF encode/decode round trips for object/delete/versioned-delete/mixed entries, routing defaults for legacy MRF entries without an `op` field, and legacy MRF binary compatibility. Additional valuable tests would exercise worker resize down behavior, queue full admission for regular and large queues, MRF persister append/overwrite semantics across multiple flushes, restart replay idempotence, global pool initialization idempotence, `schedule_replication()` synchronous versus asynchronous paths, and stale or failed resync recovery behavior.

# sources/object-store/rustfs/crates/ecstore/src/bucket/replication/replication_resyncer.rs

Purpose: Implements replication resync status serialization, resync execution, replication decision helpers, delete replication, object replication, target upload options, multipart replication, and comparison logic for deciding whether target objects need data, metadata, or no update. This file is the main execution engine behind the worker pool's `replicate_object()`, `replicate_delete()`, heal object conversion, and persisted resync metadata.

Important APIs and types: `ResyncOpts` identifies a bucket, target ARN, resync run ID, and optional cutoff time. `TargetReplicationResyncStatus` stores per-target counters, current object checkpoint, status, run ID, timestamps, and error text. `BucketReplicationResyncStatus` wraps the per-target map with version and last update data. `ReplicationResyncer` owns the in-memory bucket status map, fixed resync worker count, and cancellation tokens keyed by bucket plus ARN. `DeletedObjectReplicationInfo` describes delete-marker, version-purge, and force-delete replication work and implements `ReplicationWorkerOperation`. `ReplicationConfig` wraps an optional S3 replication config plus optional bucket targets and computes existing-object resync decisions. `MustReplicateOptions` captures metadata, tags, current status, operation type, and whether the request itself came from replication.

Persistence and wire formats: Per-bucket resync state is saved under `${BUCKET_META_PREFIX}/{bucket}/.replication/resync.bin`. The file starts with little-endian `RESYNC_META_FORMAT` and `RESYNC_META_VERSION`, followed by a custom MessagePack map with compact keys. Decode first tries the custom wire format and falls back to legacy `rmp_serde` payloads. Time fields use a sentinel `WIRE_ZERO_TIME` for `None`, and decode normalizes both that sentinel and Unix epoch back to `None`. MRF files use the same four-byte header pattern at `config/replication/mrf.bin`, then `rmp_serde::to_vec_named()`/`from_slice()` for `MrfReplicateEntry` arrays. `save_resync_status()` writes encoded state through `save_config()`.

Resync control flow: `ReplicationResyncer::mark_status()` creates missing bucket/target map entries, rejects stale updates whose `resync_id` does not match an existing non-empty state, fills run metadata, updates status timestamps, clones the bucket state, and persists it. `inc_stats()` performs the same stale-run guard and accumulates per-object replicated/failed counts in memory. `persist_to_disk()` periodically scans the map and writes buckets whose `last_update` advanced. `resync_bucket()` first checks cancellation, acquires a cluster-wide namespace lock for `.replication/{bucket}/{arn}`, loads replication config and targets, validates that exactly one target ARN matches, obtains the target client, optionally marks status started, walks the source bucket, and sends eligible objects to a fixed set of workers selected by SIP hash. Each worker turns delete markers or version-purge entries into `DeletedObjectReplicationInfo` and otherwise replicates objects as existing-object work, then verifies with `HeadObject` and sends count deltas through a broadcast channel. Completion drops worker channels, awaits the workers plus stats collector, and marks the resync completed unless earlier cancellation or runtime errors mark it canceled or failed.

Replication decision flow: `get_heal_replicate_object_info()` normalizes per-role replication status fields, chooses `check_replicate_delete()` for delete markers and version-purge status, chooses `must_replicate()` for normal objects, computes target status maps, computes an existing-object `ResyncDecision`, and returns a complete `ReplicateObjectInfo`. `ReplicationConfig::resync()` handles delete-marker existing-object decisions specially, then delegates to `resync_internal()`, which intersects replication decisions with configured remote targets and calls `resync_target()`. `resync_target()` compares reset headers, reset IDs, reset-before dates, source modification time, and target status to decide whether a target should be resynced. `must_replicate()` filters out unavailable object-store state, disabled versioning prefixes, replica writes except metadata, replication requests, missing replication config, nonmatching rules, and missing target clients before returning per-target synchronous/asynchronous decisions. `check_replicate_delete()` similarly evaluates delete replication with versioning, replica delete, target client, and error-state handling.

Delete replication flow: `replicate_delete()` handles force deletes through `replicate_force_delete_to_targets()` and normal deletes through replication config lookup, source delete-marker verification, replication-decision parsing, per-object namespace locking, parallel target deletion, local replication-state update, stats update, and event emission. It treats delete-marker creation differently from version-purge replication by using `ReplicationStatusType` for the former and `VersionPurgeStatusType` for the latter. `replicate_delete_to_target()` skips already-completed non-existing-object deletes, skips completed version purges, checks target offline state, optionally probes delete-marker presence with `HeadObject`, calls `remove_object()` with replication flags, and records target status/error/resync timestamp. `replicate_delete_marker_purge_to_targets()` performs delayed cleanup if source delete-marker purge catches a target marker that arrived late. Force-delete replication locks the object and sends force `remove_object()` calls to matching targets.

Object replication flow: `replicate_object()` loads replication config, filters target ARNs for the object's operation and tags, takes a per-object namespace lock, then spawns one task per target. Plain object operations call `ReplicateObjectInfoExt::replicate_object()`, while heal/existing/metadata-style operations call `replicate_all()`. Results are collected into `ReplicatedInfos`; if internal target status changed or a resync timestamp was written, source object metadata is updated via `put_object_metadata()`, global stats are updated, and object replication complete/failed events are sent. A secondary stats update path handles failed replications where internal metadata did not change.

Target upload behavior: `replicate_object()` and `replicate_all()` both check target offline state, source object reader availability, actual size, target bucket validity, and existing target state through `HeadObject`. AWS/RustFS version-ID format mismatches use a fallback `HeadObject` without version ID and compare ETags only via `content_matches()`. `get_replication_action()` compares ETag, version ID, actual size, delete marker, mod time, content type, content encoding, tags, object-lock headers, selected metadata prefixes, and existing-object newer-target semantics to return `All`, `Metadata`, or `None`. Full data copies build `PutObjectOptions` with user metadata, standard headers, object-lock fields, storage class, source version/etag/mtime, replica status, tags, checksum metadata, SSE-C replication headers, and internal timestamps. Multipart replication creates an upload with retry, streams each source part by range with bandwidth monitoring, completes with uploaded part ETags, and records actual object size metadata.

State and concurrency behavior: Resync status is shared in `Arc<RwLock<HashMap<...>>>`; cancellation tokens are shared in a second `RwLock` map. Resync scans use one cluster namespace lock per bucket/ARN and ten object workers. Object and delete replication use per-object namespace locks to serialize replication of the same object across workers/nodes. Target operations are parallelized with `JoinSet`; resync worker status aggregation uses a broadcast channel of capacity one. Global stats are optional through `GLOBAL_REPLICATION_STATS`. Proxy request metrics record selected `HeadObject`, `PutObject`, and `PutObjectTagging` outcomes, while expected 404/405/version-ID mismatch responses are not counted as proxy failures.

Dependencies and integration points: This file integrates with `BucketTargetSys` and `TargetClient` for target clients and S3-like operations, `metadata_sys` for replication configuration, `BucketVersioningSys` for versioning gates, `StorageAPI`/`ObjectIO`/`NamespaceLocking` for local reads/writes/locks, event notification for replication status events, bucket bandwidth monitoring for streamed replication accounting, RustFS HTTP metadata helpers for internal replication headers, `rustfs_filemeta` for decisions and statuses, AWS SDK `HeadObjectOutput`/errors, MessagePack helpers, Tokio tasks/channels, and `CancellationToken`.

Risks: The resync worker stats channel is a broadcast channel with capacity one and a single receiver; lagged messages can be lost, which can undercount resync progress if workers send faster than the collector consumes. `persist_to_disk()` uses one `update` flag across buckets inside an interval and unwraps `status.last_update` after a write, which is fragile for buckets with target updates but no bucket timestamp. `ReplicateObjectInfoExt::to_object_info()` always sets `delete_marker: true`, which looks suspicious for normal object event payloads and may distort `ObjectReplicationNotTracked` events. Several important branches are TODOs or partial, including metadata-only copy, SSE-S3/SSE-KMS support, and offline reclassification after failed target writes. A condition around `get_object_reader()` logs on `!not_found || version_not_found`, which may not match the intended "unexpected error" grouping. Delete-marker retry spawns detached cleanup work without later status reconciliation. Resync completion awaits the results collector task, but that collector receives from a broadcast channel that is only closed after all senders are dropped; this depends on sender lifetimes in the worker tasks and outer scope being correct.

Test signals: Existing tests cover multipart range calculation and invalid part sizes, custom and legacy resync MessagePack decode, resync file round trip, sentinel time handling, heal path choice for normal/delete/version-purge objects, delete replication option construction for replica versus source deletes, delete-marker versus version-purge classification, late delete-marker purge retry eligibility, retryable delete `HeadObject` errors, proxy failure filtering, version-ID mismatch detection, ETag-only content fallback, heal ROI construction, role mapping for version-purge status, cancellation-token keying, and stale resync update rejection. Missing high-value tests include full `resync_bucket()` cancellation and checkpoint recovery, lost broadcast stats behavior under load, metadata-only replication behavior once implemented, `to_object_info()` delete-marker correctness, multipart abort/error cleanup, force-delete target selection, and integration tests against AWS-style targets with incompatible version IDs.
