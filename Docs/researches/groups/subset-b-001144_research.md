# sources/distributed-fs/ceph-client/drivers/clk/qcom/gcc-sm8350.c

## Purpose
`gcc-sm8350.c` is the Qualcomm global clock controller provider for SM8350-class SoCs. It describes the GCC MMIO register block as Linux common clock framework clocks, reset-controller lines, and GDSC power domains, then exposes them under the device-tree clock IDs from `dt-bindings/clock/qcom,gcc-sm8350.h`. The modeled hardware covers the general-purpose PLL roots, QUPv3 serial engines, SDCC2/SDCC4, UFS PHY and UFS card controllers, PCIe 0/1, primary and secondary USB3 controllers, GPU/fabric votes, camera/display/video fabric clocks, PDM, branch-only reference clocks, and the related block resets and power islands.

## Important APIs, Types, And Functions
The driver is almost entirely declarative and is built from Qualcomm clock-controller helper types. It uses `struct clk_alpha_pll` for `gcc_gpll0`, `gcc_gpll4`, and `gcc_gpll9`, plus `struct clk_alpha_pll_postdiv` for `gcc_gpll0_out_even`. These use Lucid 5LPE PLL register layouts and fixed/post-divider ops. Parent selection is described with `struct parent_map` and `struct clk_parent_data` arrays for internal GPLL parents and firmware-provided parents such as `bi_tcxo`, `sleep_clk`, PCIe pipe clocks, UFS card/PHY symbol clocks, and USB3 pipe clocks.

Clock roots and leaves use `struct clk_regmap_phy_mux`, `struct clk_regmap_mux`, `struct clk_rcg2`, `struct clk_regmap_div`, and `struct clk_branch`. RCG frequency tables define the supported rates for GP clocks, PCIe AUX and PHY ref-change roots, PDM, QUPv3 serial ports, SDCC2/SDCC4, UFS card/PHY AXI, ICE, UniPro and PHY AUX roots, and USB3 master/mock-UTMI/PHY AUX roots. Branch clocks then gate the fabric, peripheral, symbol, pipe, and reference clocks with `clk_branch2_ops`, `clk_branch2_aon_ops`, or simple branch ops where only a bit needs to be forced.

Power and reset integration is through `struct gdsc` arrays and `struct qcom_reset_map`. The GDSC set includes PCIe 0/1, UFS card, UFS PHY, USB30 primary/secondary, and votable MMNOC MMU TBU domains. The reset map covers camera, display, GPU, MMSS, PCIe controller and PHY resets, QUP wrappers, QUSB2 PHYs, SDCCs, UFS card/PHY, USB3 PHY/controller blocks, USB PHY AHB2PHY, video resets, and video AXI async resets with delay. `gcc_dfs_clocks[]` marks QUPv3 RCGs for dynamic frequency scaling registration.

`gcc_sm8350_probe()` is the only custom function. It maps GCC registers with `qcom_cc_map()`, sets selected camera/display/GPU/video AHB and XO clocks on with `qcom_branch_set_clk_en()`, registers QUP DFS RCGs through `qcom_cc_register_rcg_dfs()`, sets `BIT(14)` on the UFS PHY ICE core clock register to force the memory core on, and finally calls `qcom_cc_really_probe()`. The platform driver is registered at `subsys_initcall()` and matches `qcom,gcc-sm8350`.

## Control Flow
At boot, the platform bus binds this driver to a GCC device-tree node with compatible `qcom,gcc-sm8350`. Probe maps the MMIO block according to `gcc_sm8350_regmap_config`, whose max register is `0x9c100`, then performs a small amount of mandatory hardware setup before the provider is registered. The always-on setup directly enables camera AHB/XO, display AHB/XO, GPU CFG AHB, and video AHB/XO branches so downstream multimedia and GPU blocks have their management clocks available. DFS registration happens before clock provider registration so QUPv3 serial RCGs can participate in the Qualcomm DFS scheme. The UFS PHY ICE core force bit is also programmed before consumers start using the UFS clocks.

After `qcom_cc_really_probe()` succeeds, runtime control is delegated to the common clock framework and qcom regmap ops. Consumers request rates, parents, enables, disables, resets, or power-domain transitions by numeric IDs from the SM8350 bindings. RCG ops program `cmd_rcgr` registers from the frequency tables, mux ops choose between external symbol/pipe clocks and fallback XO where applicable, branch ops vote or gate leaf clocks, reset-controller ops write the mapped reset registers, and GDSC ops control the listed power domains.

The static clock tree is organized around three main PLL roots. GPLL0 and its even divider feed most low and medium-rate peripherals, GPLL9 is used for high-rate SDCC2, and GPLL4 is included as an alternate parent in the wider parent map. External PHY or symbol parents are used for PCIe pipe, UFS RX/TX symbols, and USB3 pipe clocks. QUPv3 is the largest DFS group, with wrap0 S0-S7, wrap1 S0-S5, and wrap2 S0-S5 RCGs registered for runtime serial-port rate switching.

## State And Persistence
The file has no filesystem or firmware persistence. Its persistent state is the static descriptor data compiled into the kernel and the live GCC register state for the current boot. Probe-time writes remain in hardware until a reset or a later clock/power operation changes the same registers. PLL and post-divider descriptors represent fixed root clocks; rate changes mostly occur in RCGs and divider/mux registers. Branch clocks use several halt policies: `BRANCH_HALT` for ordinary gates, `BRANCH_HALT_VOTED` for voted or shared clocks, `BRANCH_HALT_SKIP` where external hardware controls visibility, and `BRANCH_HALT_DELAY` for pipe/symbol clocks whose parent or PHY state can delay halt reporting.

State is shared with other kernel subsystems through CCF references, reset-controller handles, and generic power domains. Hardware-controlled UFS branches are split into normal and `_hw_ctl` variants at adjacent enable bits, and USB master clocks include `__force_mem_core_on` simple branches for memory-retention behavior. These paired descriptors are important because software may enable a clock while hardware control or memory retention remains separately governed.

## Dependencies And Integration Points
The driver depends on the Linux platform bus, regmap, CCF, module infrastructure, Qualcomm clock helpers (`clk-alpha-pll.h`, `clk-branch.h`, `clk-rcg.h`, `clk-regmap.h`, `clk-regmap-divider.h`, `clk-regmap-mux.h`, `clk-regmap-phy-mux.h`), GDSC power-domain support, reset support, and the SM8350 GCC binding header. Device tree must provide firmware-named roots such as `bi_tcxo`, `sleep_clk`, PCIe pipe parents, UFS card and UFS PHY symbol clocks, and USB3 primary/secondary pipe clocks.

Consumers include QUPv3 UART/I2C/SPI controllers, SDHCI for SDCC2/SDCC4, UFS host and optional UFS card paths including inline crypto clocks, USB3 primary and secondary controllers/PHYs, PCIe controllers and PHYs, PDM audio, GPU and multimedia fabric clients, camera/display/video subsystems, and reset/power-domain users for those blocks. The driver also integrates with generic PM domain handling through GDSC descriptors and with reset-controller users through the qcom reset map.

## Risks
The main risk is register and parent-map accuracy. The file contains many near-identical QUP, UFS, USB, and PCIe descriptors whose offsets differ by wrapper or instance; a copied offset or enable bit can route an otherwise valid clock ID to the wrong register. Parent maps intentionally use sparse hardware selector values, and several external PHY/symbol muxes use XO as a fallback at selector value 2, so changing parent order can silently break pipe or symbol clocks.

UFS has high coupling between AXI, ICE core, UniPro, PHY AUX, RX/TX symbol, hardware-control, GDSC, and reset descriptors. The probe-time UFS ICE `FORCE_MEM_CORE_ON` bit is a hardware workaround-style write and should be preserved unless validated on silicon. PCIe and USB branch halt policies are also sensitive: pipe and external fabric clocks often skip polling because the clock state depends on a PHY or fabric outside GCC. Treating those as ordinary halt-polled branches can produce enable timeouts or false failures.

Always-on probe writes for camera, display, GPU, and video management clocks are not represented as normal critical clock flags in the descriptor table. Removing or reordering them may produce boot-time failures that are hard to attribute to GCC because the consumers may probe later. Reset risks are broad because the reset map includes whole-block BCRs, PHY resets, link-down resets, and delayed video AXI resets; wrong delays or wrong reset bits can affect neighboring multimedia or PCIe hardware.

## Test Signals
Useful boot signals are successful bind of `qcom,gcc-sm8350`, no `qcom_cc_map()` or `qcom_cc_register_rcg_dfs()` errors, and registered clock, reset, and power-domain providers. In debugfs, `clk_summary` should show `gcc_gpll0`, `gcc_gpll0_out_even`, `gcc_gpll4`, `gcc_gpll9`, GP roots, all QUPv3 wrap0/wrap1/wrap2 RCGs and branches, SDCC2/SDCC4 roots, UFS card/PHY roots and symbol clocks, PCIe 0/1 AUX/ref-change/pipe clocks, and USB3 primary/secondary master/mock-UTMI/pipe clocks.

Hardware validation should cover serial I/O over QUPv3 ports, SD card or eMMC operation through SDCC2/SDCC4, UFS PHY and UFS card enumeration including ICE if enabled, PCIe link training on both controllers, USB3 enumeration on primary and secondary ports, PDM audio, GPU bring-up, camera/display/video subsystem probing, and reset assert/deassert operations for representative PCIe, USB, UFS, QUP, SDCC, and video resets. Power-domain validation should confirm PCIe, UFS, USB, and MMNOC TBU GDSCs transition without clock timeout messages.

# sources/distributed-fs/ceph-client/drivers/clk/qcom/gcc-sm8450.c

## Purpose
`gcc-sm8450.c` is the Qualcomm GCC provider for SM8450 and SM8475 platforms. It registers the global clock controller's PLLs, RCG roots, muxes, dividers, branch gates, resets, and GDSC power domains for high-speed peripheral and fabric blocks. The exposed binding IDs come from `dt-bindings/clock/qcom,gcc-sm8450.h`, and the covered hardware includes GPLL0/4/9, optional SM8475 GPLL2/GPLL3, QUPv3 serial wrappers, SDCC2/SDCC4, one UFS PHY block, PCIe 0/1, USB3 primary/eUSB reference clocks, PDM, GPU/fabric votes, camera/display/video fabric clocks, and related block resets.

## Important APIs, Types, And Functions
The file uses the same qcom common clock-controller building blocks as nearby GCC drivers: `struct clk_alpha_pll`, `struct clk_alpha_pll_postdiv`, `struct clk_regmap_phy_mux`, `struct clk_regmap_mux`, `struct clk_rcg2`, `struct clk_regmap_div`, `struct clk_branch`, `struct gdsc`, `struct qcom_reset_map`, `struct clk_rcg_dfs_data`, `struct regmap_config`, and `struct qcom_cc_desc`.

The base SM8450 PLLs use Lucid EVO register layouts and ops for `gcc_gpll0`, `gcc_gpll0_out_even`, `gcc_gpll4`, and `gcc_gpll9`. The file also defines SM8475-specific init data for GPLL0/4/9 using Lucid OLE ops, plus additional Lucid OLE PLL descriptors `sm8475_gcc_gpll2` and `sm8475_gcc_gpll3`. SM8475 parent and rate tables extend UFS AXI, ICE, and UniPro roots up to 600 MHz and 806.4/850 MHz via GPLL2, and adjust SDCC2 rates to 37/148 MHz instead of the SM8450 202 MHz top entry.

Parent maps combine `bi_tcxo`, `sleep_clk`, GPLL0 main/even, GPLL4, GPLL9, SM8475 GPLL2/GPLL3, external PCIe pipe and PHY AUX clocks, UFS RX/TX symbol clocks, and USB3 pipe clocks. Frequency tables cover GP clocks, PCIe AUX/ref-change roots, PDM, QUPv3 serial engines, SDCC2/SDCC4, UFS AXI/ICE/UniPro/PHY AUX roots, and USB3 master/mock-UTMI/PHY AUX roots. Most RCGs set `.hw_clk_ctrl = true`, reflecting hardware clock-control support in this generation.

The provider arrays are `gcc_sm8450_clocks[]`, `gcc_sm8450_resets[]`, and `gcc_sm8450_gdscs[]`, all gathered by `gcc_sm8450_desc`. The clock array reserves `SM8475_GCC_GPLL2` and `SM8475_GCC_GPLL3` as `NULL` in the base descriptor and fills them only for the SM8475 compatible. `gcc_sm8450_probe()` maps registers, registers DFS data, mutates descriptors for SM8475 compatibility, sets the UFS ICE memory-core force bit, enables selected always-on management clocks, and calls `qcom_cc_really_probe()`.

## Control Flow
The driver is registered at `subsys_initcall()` and matches either `qcom,gcc-sm8450` or `qcom,sm8475-gcc`. Probe first maps the GCC register range using `qcom_cc_map()` and the `gcc_sm8450_regmap_config`, which allows registers up to `0x1f1030`. It then registers the QUPv3 DFS RCG list with `qcom_cc_register_rcg_dfs()`. This list includes wrap0 S0-S7, wrap1 S0-S6, and wrap2 S0-S6, matching the larger QUP serial surface in this generation.

If the device node is compatible with `qcom,sm8475-gcc`, probe rewrites several static descriptors before provider registration. It switches GPLL0, GPLL0 even post-divider, GPLL4, and GPLL9 from Lucid EVO to Lucid OLE register/ops init data; changes SDCC2 to the SM8475-specific rate table; changes UFS AXI, ICE core, and UniPro RCGs to the SM8475 parent map and rate tables; and inserts `sm8475_gcc_gpll2` and `sm8475_gcc_gpll3` into the descriptor clock array. This mutation happens before `qcom_cc_really_probe()`, so consumers see a single SoC-specific provider.

For both SoCs, probe sets `BIT(14)` in the UFS PHY ICE core branch register to force memory core on. It then enables camera AHB/XO, display AHB/XO, GPU CFG AHB, and video AHB/XO branches with `qcom_branch_set_clk_en()`. Once `qcom_cc_really_probe()` registers the provider, clock framework consumers drive all subsequent parent, rate, gate, reset, and GDSC operations through generic qcom regmap helpers.

## State And Persistence
The driver keeps no disk-backed state. Static descriptor data and the live GCC register contents are the only state. SM8475 support is implemented by mutating global static descriptors during probe; because there is normally one GCC instance for the SoC, that is acceptable, but it means the descriptor arrays are not immutable after compilation. Probe-time writes for DFS registration, UFS ICE force-memory behavior, and always-on management clocks persist until hardware reset or later writes.

Branch descriptors use halt policies that encode hardware ownership. Ordinary peripheral gates use `BRANCH_HALT`, shared or voted fabric clocks use `BRANCH_HALT_VOTED`, external fabric and pipe paths often use `BRANCH_HALT_SKIP`, and clocks that depend on PHY or external parent readiness use `BRANCH_HALT_DELAY`. GDSCs model PCIe 0/1 in `PWRSTS_RET_ON` and UFS/USB in `PWRSTS_OFF_ON`, so runtime PM semantics differ by domain. RCG state is stored in hardware command registers, while divider and mux state is stored in the corresponding regmap registers.

## Dependencies And Integration Points
The driver depends on Linux CCF, platform and OF matching, regmap, Qualcomm alpha PLL, branch, RCG, regmap divider/mux/PHY mux, GDSC, reset, and common CC helpers. It includes `<linux/of.h>` because SM8475 detection uses `of_device_is_compatible()`. Device tree must provide `bi_tcxo`, `sleep_clk`, PCIe pipe parents, the PCIe 1 PHY AUX parent, UFS PHY symbol parents, and the USB3 pipe parent through firmware names.

Runtime consumers include QUPv3 UART/I2C/SPI controllers, SDHCI for SDCC2 and SDCC4 including AT clocks, UFS host and inline crypto/UniPro paths, PCIe 0/1 controllers and PHYs, USB3 primary and eUSB reference users, PDM audio, camera/display/video fabric clients, GPU fabric and DVM paths, reset-controller clients, and generic PM-domain users for PCIe, UFS, and USB power domains. The SM8475 path specifically integrates additional GPLLs into the same exported binding space, so SM8475 device trees can request `SM8475_GCC_GPLL2` and `SM8475_GCC_GPLL3`.

## Risks
The SM8475 descriptor mutation is the highest-risk area. The code changes PLL register layouts, PLL init ops, parent maps, rate tables, and descriptor-array entries at probe time. Any future reordering of binding IDs, parent enums, or array sizes could leave SM8475 GPLL2/GPLL3 unavailable or make UFS roots reference parents that were not registered. The `num_parents` fields in SM8475 init data are derived from the parent-map array size and must continue to match the companion parent-data arrays.

Register offsets are generation-specific and often close to SM8350 offsets with a shifted base, which makes copy/paste errors plausible. QUPv3 wrappers have many nearly identical RCG and branch descriptors, and SM8450 has wrap1/wrap2 S6 entries that SM8350 lacks. PCIe 1 has a separate PHY AUX mux/branch in addition to pipe, ref-change, AXI, and AHB clocks; confusing those paths can break link training without obvious clock-registration failures.

UFS is especially sensitive because SM8450 and SM8475 support different parent/rate sets. The SM8475 UFS high-rate table depends on GPLL2 and includes 806.4/850 MHz options; exposing those on SM8450 or failing to expose them on SM8475 would produce invalid rate behavior. The UFS ICE force-memory bit and the hardware-control branch variants should be treated as hardware requirements. Always-on camera/display/GPU/video management clock writes are also important because consumers may rely on those clocks before normal CCF reference counts reflect use.

Reset-map risk is broad: the map covers whole-block BCRs, link-down resets, PHY resets, QUSB2/USB3 PHY resets, SDCC resets, UFS reset, and delayed video AXI async resets. The video AXI reset delay is 1000 microseconds in this file, differing from some earlier platforms, so delay changes need hardware validation.

## Test Signals
Expected boot signals include a successful bind for `qcom,gcc-sm8450` or `qcom,sm8475-gcc`, no errors from register mapping or DFS registration, and populated clock, reset, and GDSC providers. Debugfs `clk_summary` should show base GPLLs, GP roots, QUPv3 wrap0/wrap1/wrap2 roots and branches, SDCC2/SDCC4 roots and AT clocks, UFS PHY AXI/ICE/UniPro/PHY AUX/symbol clocks, PCIe 0/1 AUX/ref-change/pipe clocks, PCIe 1 PHY AUX, USB3 primary master/mock-UTMI/pipe clocks, camera/display/video/GPU fabric clocks, and eUSB/USB3 reference enables. On SM8475, `SM8475_GCC_GPLL2` and `SM8475_GCC_GPLL3` should be registered and UFS roots should accept the SM8475 high-rate table.

Hardware validation should cover QUPv3 serial ports, SDCC2 and SDCC4 card operation, UFS enumeration and performance including ICE, PCIe link training for both controllers, PCIe 1 PHY AUX behavior, USB3 enumeration, eUSB reference users where present, PDM audio, GPU bring-up, camera/display/video subsystem probing, and power-domain transitions for PCIe, UFS, and USB. Reset testing should include representative controller, PHY, QUP, SDCC, UFS, USB, and video resets while watching for qcom clock halt timeouts and collateral device loss.
