# sources/distributed-fs/ceph-client/drivers/bluetooth/hci_bcm.c

Purpose: This file implements the Broadcom/Cypress/Infineon Bluetooth HCI UART protocol driver. It provides an H4-compatible transport with Broadcom vendor setup, platform and serdev probing, GPIO/clock/regulator power sequencing, ACPI and device-tree resource discovery, host-wake runtime PM, sleep-mode programming, diagnostic packet support, and Broadcom firmware/address handling through `btbcm`.

Important APIs, types, and functions: Core private state is split between `struct bcm_data` for live HCI UART queues and receive reassembly, and `struct bcm_device` for physical resources such as GPIOs, clocks, regulators, IRQ, baud rates, Apple ACPI methods, and PM state. Device quirks use `struct bcm_device_data`. The `bcm_proto` `hci_uart_proto` supplies `bcm_open`, `bcm_close`, `bcm_flush`, `bcm_setup`, `bcm_set_baudrate`, `bcm_recv`, `bcm_enqueue`, and `bcm_dequeue`. Platform and serdev entry points are `bcm_probe`, `bcm_remove`, `bcm_serdev_probe`, and `bcm_serdev_remove`; module integration is through `bcm_init` and `bcm_deinit`.

Control flow: Open requires UART flow-control support, allocates `bcm_data`, resolves the matching `bcm_device` from serdev drvdata or the global platform-device list, sets initial and operational speeds, optionally manipulates RTS for autobaud or board quirks, and powers the controller through `bcm_gpio_set_power`. Setup delegates firmware and patchram work to `btbcm_initialize`, switches host and controller baud rates when firmware loading completed, optionally writes PCM interface parameters, calls `btbcm_finalize`, enables BDADDR property fallback for invalid default addresses, requests the host-wake IRQ, and programs Broadcom sleep parameters. TX prepends the H4 packet type and queues to `txq`; RX uses `h4_recv_buf` with standard ACL/SCO/event/ISO plus Broadcom diagnostic/null/type49/type52 packets. Dequeue wraps runtime-PM get/put around queue removal.

State and persistence behavior: Persistent storage is not written by this file. Runtime state lives in GPIO values, regulator and clock enable state, `res_enabled`, `init_speed` and `oper_speed`, `irq_acquired`, runtime PM state, `is_suspended`, queued skbs, and the current partial RX skb. Firmware and BDADDR programming are controller state changes performed through vendor HCI commands. The global `bcm_device_list` bridges ACPI platform devices to tty line-discipline instances; serdev instances keep the device as drvdata and always pass `bcm_device_exists`.

Dependencies and integration points: The driver depends on the HCI UART core, `h4_recv_buf`, Broadcom helpers in `btbcm`, serdev, tty modem control, GPIO descriptors, regulators, clocks, ACPI resource parsing, Apple-specific ACPI methods, OF properties, DMI quirks for broken IRQ descriptions, runtime PM, and HCI core callbacks `set_diag` and `set_bdaddr`. Match tables cover many ACPI `BCM2E*` IDs and OF compatibles for Broadcom, Cypress, and Infineon controllers.

Risks and edge cases: The most sensitive paths are power sequencing rollback, baud-rate ordering, and concurrency with platform-device removal. `bcm_device_lock` protects the global list and PM operations, but tty-backed devices still depend on parent-device matching. Some ACPI tables describe wrong IRQ polarity or wrong GPIO order, so the driver carries DMI and module-parameter overrides. Autobaud devices require deliberate RTS/flow-control behavior and may cap init speed. The `no_uart_clock_set` and `max_speed` quirks avoid commands or speeds unsupported by specific chips. Runtime suspend disables flow control and toggles wake GPIOs, so incorrect host-wake IRQ configuration can break low-power recovery.

Test signals: Useful validation includes platform and serdev probe paths, ACPI GPIO order variants, Apple ACPI power methods, DMI broken IRQ systems, regulator/clock failure unwind, autobaud and early baud-rate quirk handling, `btbcm_initialize` and `btbcm_finalize` error paths, Broadcom diagnostic packet injection via `set_diag`, RX parsing of vendor diagnostic packet types, runtime autosuspend on RX/TX, host-wake IRQ resume, and system suspend/resume with wake-capable devices.

# sources/distributed-fs/ceph-client/drivers/bluetooth/hci_bcm4377.c

Purpose: This file implements a PCIe Bluetooth HCI driver for Broadcom BCM4377, BCM4378, BCM4387, and BCM4388 devices, including Apple-oriented board support. Unlike the UART Broadcom driver, it boots firmware through PCI BAR registers, configures a DMA-based "Converged IPC" context, and moves HCI command, event, ACL, and SCO traffic over transfer and completion rings.

Key functions include `bcm4377_prepare_rings`, `bcm4377_init_context`, `bcm4377_boot`, `bcm4377_setup_rti`, `bcm4377_enqueue`, `bcm4377_irq`, `bcm4377_hci_open`, `bcm4377_hci_close`, `bcm4377_hci_send_frame`, `bcm4377_hci_setup`, `bcm4377_parse_otp`, and `bcm4377_probe`.

Control flow: Probe sets a constrained 32-bit DMA mask, allocates rings and context using managed coherent DMA, discovers board type from DMI or OF, optionally disables ASPM, resets and enables the PCI function, programs vendor PCI window registers, maps BAR0 and BAR2, parses OTP for stepping and vendor, allocates MSI, registers an interrupt handler, creates an HCI device, boots firmware from a board/stepping/vendor-specific `brcm/brcmbt*.bin`, transitions RTI state, and registers the HCI device. `hci_open` creates non-control completion and transfer rings using synchronous control-ring messages. `hci_setup` sends optional calibration data, loads and sends a PTB file, and checks for invalid default BDADDR. State and persistence behavior: State is volatile kernel and controller runtime state: BAR window configuration, bootstage and RTI status, DMA ring head/tail arrays, generation-tagged message IDs, per-ring enable flags, pending completions, OTP-derived stepping/vendor strings, OF calibration blobs, and HCI quirks. Firmware/PTB/calibration blobs are loaded from firmware or device tree but not modified. The driver uses message ID generations so stale completion entries from a previous open can be rejected after a ring is recreated.

Dependencies and integration points: The driver depends on PCI, MSI, coherent DMA, firmware loading, DMI, OF properties, HCI core PCI bus registration, Bluetooth management quirks, and Apple/Asahi board data conventions. It integrates with HCI through direct `hci_dev` callbacks rather than the HCI UART line discipline. Firmware naming depends on chip ID, OTP stepping, board type, and antenna vendor. Runtime PM is minimal: suspend quiesces the device and calls `hci_suspend_dev`; resume unquiesces and calls `hci_resume_dev`.

Risks and edge cases: Ring setup is highly firmware-specific; comments note that IDs, mappings, and doorbells are effectively hardcoded by firmware despite appearing configurable. DMA addresses must stay inside the special `0xfffffe00` mask. Interrupt handling trusts shared DMA ring indices and uses `dma_rmb` before reading entries; missing barriers could expose partially written completions. Error paths in `hci_open` destroy rings in reverse, but some labels appear easy to misread and need regression coverage. Firmware boot requires exact bootstage and RTI transitions within timeouts. OTP parsing rejects missing stepping/vendor, so bad board data prevents probe. PTB sending may fail benignly for some firmware but calibration data is mandatory for variants with callbacks.

Test signals: Hardware or emulator validation should cover firmware-name fallback, OTP parsing of chip and board parameters, DMI and OF board-type selection, BAR window programming, ASPM disable path, firmware boot timeout and bad bootstage handling, RTI state 1 and 2 transitions, creation/destruction of all rings, mapped ACL payloads, virtual D2H event rings, stale generation detection, message ID exhaustion, completion-ring transfer ID validation, calibration and PTB chunking, BDADDR default detection, and suspend/resume quiesce behavior.

# sources/distributed-fs/ceph-client/drivers/bluetooth/hci_bcsp.c

Purpose: This file implements the BCSP Bluetooth HCI UART protocol. BCSP is a SLIP-framed, optionally CRC-protected, sequence/acknowledgement transport with reliable and unreliable channels. It maps HCI command and ACL traffic to reliable BCSP channels, SCO to an unreliable channel, handles link-establishment messages, and optionally converts vendor HCI extension channels into HCI vendor events.

Important APIs, types, and functions: `struct bcsp_struct` tracks `unack`, `rel`, and `unrel` queues, RX reassembly state, escape state, CRC state, txack and rxack values, retransmission timer, and the next reliable TX sequence. Main protocol callbacks are `bcsp_open`, `bcsp_close`, `bcsp_enqueue`, `bcsp_dequeue`, `bcsp_recv`, and `bcsp_flush`. Helpers include `bcsp_prepare_pkt`, `bcsp_pkt_cull`, `bcsp_complete_rx_pkt`, `bcsp_handle_le_pkt`, `bcsp_unslip_one_byte`, and `bcsp_timed_event`. Module parameters `txcrc` and `hciextn` control transmitted CRC and HCI extension channel conversion.

Control flow: Enqueue classifies outgoing HCI command/ACL packets as reliable and SCO packets as unreliable, rejecting payloads larger than 12 bits. Dequeue gives priority to unreliable traffic, then sends reliable packets while the unacknowledged queue is below `BCSP_TXWINSIZE`, placing original skbs on `unack` and starting a retransmission timer. If no data can be sent but an ACK is pending, it emits an empty BCSP ACK packet. RX is a byte-wise state machine that waits for delimiters, unslips escaped bytes, reads and validates the 4-byte BCSP header checksum, collects payload and optional CRC, then dispatches complete packets. Reliable RX packets advance the expected sequence and request an ACK; all packets carry peer ACK information that culls the unack queue.

State and persistence behavior: BCSP state is entirely volatile and bound to the open HCI UART instance. It persists across incoming bytes through `rx_skb`, `rx_state`, `rx_count`, and CRC fields, and across transmit attempts through the reliable sequence, peer ACK, and retransmission timer. No filesystem or device NVM is changed. On close, the timer is shut down synchronously and all queues plus the partial RX skb are freed.

Dependencies and integration points: The file integrates with the HCI UART protocol registry via `hci_uart_register_proto`, queues TX through `hci_uart_tx_wakeup`, and delivers complete frames through `hci_recv_frame`. It depends on skbuff queues, timers, `bitrev16`, unaligned access helpers, and HCI packet definitions. It is selected through line-discipline IOCTL as `HCI_UART_BCSP`.

Risks and edge cases: Sequence and ack handling is sensitive to wraparound modulo 8 and the fixed transmit window. `bcsp_pkt_cull` logs invalid ACKs but still removes based on the computed count, so corrupt headers that pass checksum could disturb retransmission state. Out-of-order reliable packets are ACKed/cull peer acks but payloads are dropped. CRC is optional and only protects packets that request it. The RX state machine must recover from short packets, bad escape sequences, bad header checksum, and CRC mismatch without leaking skbs. HCI extension conversion rewrites unknown BCSP channels into vendor events and depends on the `hciextn` module setting.

Test signals: Good coverage includes reliable command/ACL sequencing, SCO priority as unreliable traffic, ACK-only emission, timeout retransmission with sequence rewind, modulo-8 ACK culling, link-establishment conf response and sync reset logging, SLIP escaping for `0xc0` and `0xdb`, header checksum failure, CRC success/failure, short-packet recovery, unknown channel handling with and without `hciextn`, and cleanup during close while the retransmission timer is pending.

# sources/distributed-fs/ceph-client/drivers/bluetooth/hci_h4.c

Purpose: This file implements the standard H4 Bluetooth HCI UART protocol and exports the shared `h4_recv_buf` parser used by many vendor UART transports. H4 is the simplest UART framing model: transmitted HCI frames are prefixed with a one-byte packet type, and received bytes are reassembled according to packet-type-specific fixed and variable header lengths.

Important APIs, types, and functions: `struct h4_struct` holds one partial RX skb and the TX queue. The protocol callbacks are `h4_open`, `h4_close`, `h4_flush`, `h4_enqueue`, `h4_dequeue`, and `h4_recv`, registered as `HCI_UART_H4`. The exported helper `h4_recv_buf` accepts an `hci_uart`, current partial skb, incoming buffer, and an array of `struct h4_recv_pkt` descriptors. Default descriptors handle ACL, SCO, event, and ISO packets and deliver all through `hci_recv_frame`.

Control flow: Open allocates `h4_struct` and initializes the TX queue. Enqueue prepends the HCI packet type byte to the skb and queues it. Dequeue removes the next skb. RX delegates to `h4_recv_buf`; the parser consumes optional alignment padding, recognizes a packet type, allocates a max-size skb, reads the fixed header, derives any variable payload length from the descriptor, checks tailroom, completes frames via the descriptor callback, and retains a partial skb if more bytes are needed.

State and persistence behavior: The file is stateless beyond per-open `rx_skb`, `txq`, and the `hu->padding`/`hu->alignment` fields used by the shared parser. There is no firmware loading, GPIO, clock, runtime PM, or persistent controller configuration. Close purges queued TX and frees a partial RX skb.

Dependencies and integration points: H4 depends on the HCI UART core for protocol registration and TX scheduling, on HCI core for packet definitions and `hci_recv_frame`, and on skbuff allocation/queueing. The exported `h4_recv_buf` is a central dependency for vendor transports such as Broadcom UART, Intel UART, TI LL, and Marvell UART, which extend the descriptor table with vendor packet types.

Risks and edge cases: `h4_recv_buf` is security-relevant because it handles untrusted serial bytes in interrupt or softirq-like contexts. It must reject unknown packet types, unsupported length encodings, and payload lengths larger than descriptor `maxlen`; it does so with `ERR_PTR` results and frees malformed skbs. Alignment padding is calculated after complete frames using the packet type byte plus frame length, so wrong `hu->alignment` settings can desynchronize subsequent frames. The parser ignores the `flags` bytes supplied to tty receive callbacks because the HCI UART layer passes only data to protocol receive functions.

Test signals: Validation should cover fragmented headers and payloads across multiple calls, all H4 packet types including ISO, invalid packet type `-EILSEQ`, one-byte and two-byte length fields, maxlen/tailroom overflow returning `-EMSGSIZE`, zero-length payload completion, alignment padding removal, recovery after a previous `ERR_PTR`, TX type-byte prepending, flush/close queue purging, and reuse of `h4_recv_buf` with vendor descriptor callbacks.

# sources/distributed-fs/ceph-client/drivers/bluetooth/hci_h5.c

Purpose: This file implements the Bluetooth Three-wire H5 UART protocol and serdev support for Realtek H5 controllers. H5 provides SLIP framing, reliable sequence/ack handling, optional CRC, link establishment, sleep/wakeup control packets, retransmission, and vendor setup hooks. Realtek integration adds GPIO reset/wake control, firmware download, baud-rate setup, ACPI/OF matching, runtime PM, and suspend reprobe behavior for devices that lose power.

Important APIs, types, and functions: `struct h5` stores queues, flags, RX function pointer and pending count, retransmission timer, tx sequence/ack/window, link state, sleep state, vendor hooks, serdev host object, and GPIOs. `struct h5_vnd` defines optional vendor callbacks; Realtek uses `rtl_vnd`. Core protocol callbacks are `h5_open`, `h5_close`, `h5_setup`, `h5_recv`, `h5_enqueue`, `h5_dequeue`, and `h5_flush`. Important helpers include `h5_timed_event`, `h5_link_control`, `h5_prepare_pkt`, `h5_pkt_cull`, `h5_handle_internal_rx`, `h5_complete_rx_pkt`, and the staged RX functions.

Control flow: Open initializes queues, RX state, timer, TX window, vendor power-on hook, sets `HCI_UART_INIT_PENDING`, and starts periodic sync. Until active, the timer sends sync and config requests; link-control responses move state from uninitialized to initialized to active and call `hci_uart_init_ready`. Enqueue accepts only active-state HCI data, places command/ACL on the reliable queue and SCO/ISO on the unreliable queue. Dequeue wakes a sleeping peer if needed, sends unreliable packets first, then reliable packets within the negotiated window, and finally ACK-only packets. RX is a delimiter and SLIP state machine that validates header checksum, reliable sequence ordering, active-state restrictions, optional CRC, and then dispatches HCI data or internal link-control messages.

State and persistence behavior: Protocol state is volatile: queues, `tx_seq`, `tx_ack`, `rx_ack`, `tx_win`, flags, timer state, link state, and sleep state. Serdev Realtek state also includes GPIO values, runtime PM settings, flow-control/parity/baudrate, and downloaded firmware. There is no filesystem persistence, but firmware download and HCI quirks change controller runtime behavior. Resume may schedule a `device_reprobe` for wakeup-disabled Realtek devices, effectively rebuilding the serdev/HCI instance after power loss.

Dependencies and integration points: H5 integrates with HCI UART registration, serdev, ACPI GPIO mappings, OF compatibles, runtime PM, workqueues, Realtek helpers from `btrtl`, HCI core, CRC-CCITT, and GPIO descriptors. It exports both line-discipline protocol support and a serdev driver named `hci_uart_h5`.

Risks and edge cases: Link establishment is timer-driven and can repeatedly send sync/config until the peer responds. Reset detection during active state purges queues and calls `hci_reset_dev`. The RX path clears `H5_CRC` in `h5_reset_rx`, then negotiates CRC again through config; this must match peer expectations. Reliable out-of-order packets are dropped after requesting an ACK. Sleep/wakeup state can stall TX if wake acknowledgements are lost. Realtek setup changes UART parity, baudrate, and flow control; failures in firmware download or flow-control negotiation leave the device unusable. Reprobe on resume requires module references and device references to be balanced.

Test signals: Tests should exercise sync/config negotiation, negotiated TX window and CRC, reliable retransmission timer, ACK culling, SLIP escape handling, CRC failure, header checksum failure, out-of-order reliable RX, sleep/wakeup request and response sequences, enqueue rejection before active state, ISO/SCO unreliable handling, Realtek GPIO power cycle, baud-rate command sequencing, firmware download failures, runtime PM get/put on RX/TX, and suspend/resume paths with and without wakeup-disable.

# sources/distributed-fs/ceph-client/drivers/bluetooth/hci_intel.c

Dependencies and integration points: This driver depends on HCI UART, H4 receive parsing, `btintel` helpers, ACPI platform devices, GPIO descriptors, threaded IRQs, runtime PM, tty baud/flow-control APIs, wait-on-bit synchronization, firmware loading, and HCI core callbacks. # sources/distributed-fs/ceph-client/drivers/bluetooth/hci_ldisc.c

Purpose: This file is the core tty line discipline for Bluetooth HCI UART devices. It registers the `N_HCI` line discipline, manages protocol selection through IOCTLs, owns the transmit workqueue from HCI core into tty writes, forwards tty RX bytes into the selected protocol, creates and registers `hci_dev` instances, exposes common baud-rate and flow-control helpers, and initializes all compiled HCI UART protocol modules.

Important APIs, types, and functions: The global `hup[]` protocol table is managed by `hci_uart_register_proto`, `hci_uart_unregister_proto`, and `hci_uart_get_proto`. HCI callbacks are `hci_uart_open`, `hci_uart_close`, `hci_uart_flush`, `hci_uart_send_frame`, and `hci_uart_setup`. TTY callbacks are `hci_uart_tty_open`, `hci_uart_tty_close`, `hci_uart_tty_receive`, `hci_uart_tty_wakeup`, and `hci_uart_tty_ioctl`.

Control flow: Opening the line discipline requires `CAP_NET_ADMIN`, allocates `struct hci_uart`, initializes `proto_lock`, stores it in `tty->disc_data`, sets receive room and default alignment, captures current tty speed as `oper_speed`, and flushes pending tty output. Userspace then sets flags and protocol through IOCTL. Protocol selection allocates an HCI device, attaches HCI callbacks and quirks, calls the selected protocol `open`, and registers the HCI device unless initialization is deferred. HCI sends call protocol `enqueue`, then schedule TX. TX work repeatedly asks the protocol for skbs, writes to tty, handles partial writes through `hu->tx_skb`, updates stats, and wakes waiters. TTY receive calls protocol `recv` under `proto_lock` and updates RX byte stats.

State and persistence behavior: State is per-line-discipline and volatile: selected protocol, flags, HCI device pointer, TX state bits, outstanding partial TX skb, work structs, proto lock, alignment/padding, init and operational speeds, and HCI device flags. No persistent storage is used. Closing detaches `disc_data`, closes/unregisters/frees the HCI device if registered, cancels work, closes protocol state, frees the percpu rwsem, and frees `hci_uart`.

Dependencies and integration points: The file sits between tty/serdev-adjacent protocol modules and the Bluetooth HCI core. It calls tty APIs for line discipline registration, termios baud/CRTSCTS changes, modem-control RTS manipulation, driver buffer flushing, and write callbacks. It conditionally initializes protocol modules for H4, BCSP, LL, ATH3K, H5, Intel, BCM, QCA, AG6XX, Marvell, and AML. Vendor detection in `hci_uart_setup` can install Intel or Broadcom BDADDR handlers after reading local version.

Risks and edge cases: Concurrency is central. `proto_lock` allows protocol callbacks from tty, HCI send, TX work, and close to be coordinated; `hci_uart_tx_wakeup` uses a trylock because it may run in IRQ context. Partial tty writes leave `hu->tx_skb` for the next wakeup. Close must cancel init and write work after clearing readiness to avoid use-after-free. Flow-control helper semantics are inverted for serdev (`enable` means stop controller traffic) and manually alter CRTSCTS/RTS for tty devices. IOCTL flag setting is only allowed before protocol selection. Deferred initialization via `HCI_UART_INIT_PENDING` is used by protocols such as H5 and must not register the HCI device until `hci_uart_init_ready`.

Test signals: Validation should include line-discipline open permission and missing-write-op failure, IOCTL protocol selection and busy behavior, flag validation, HCI device registration and deferred registration, protocol close cleanup, TX partial-write retry, concurrent TX wakeups, flush behavior with partial skb and protocol queue, RX forwarding under proto lock, tty wakeup scheduling, baud-rate termios changes, flow-control RTS/CRTSCTS transitions, vendor-detect local-version path, and module init/exit ordering for compiled protocols.

Purpose: This file implements the Texas Instruments LL/HCILL HCI UART protocol. Core callbacks are `ll_open`, `ll_close`, `ll_flush`, `ll_enqueue`, `ll_dequeue`, `ll_recv`, and `ll_setup`. HCILL helpers include `send_hcill_cmd`, `ll_device_want_to_wakeup`, `ll_device_want_to_sleep`, `ll_device_woke_up`, `__ll_do_awake`, and `ll_recv_frame`. Firmware helpers include `read_local_version`, `download_firmware`, `send_command_from_firmware`, and `ll_set_bdaddr`.

Control flow: Open allocates `ll_struct`, initializes queues and lock, marks the controller awake, and enables the external clock for serdev devices. Enqueue prepends the H4 type byte and either sends immediately if awake, queues on `tx_wait_q` plus sends `HCILL_WAKE_UP_IND` if asleep, or holds while waking. RX uses `h4_recv_buf` with normal HCI packets and zero-length HCILL command packet descriptors. HCILL sleep indication is ACKed and marks the controller asleep; wake indication is ACKed and moves queued packets to the active TX queue; wake ACK completes host-initiated wake. Serdev setup resets the device, waits for CTS, downloads the TI init script with retries, applies optional BDADDR quirks, and sends a vendor baud-rate command before switching host speed.

State and persistence behavior: HCILL state is volatile and protected by `hcill_lock`. Queued TX persists only until wake completion or close. Serdev setup changes controller firmware state, BDADDR, UART baud rate, flow control, enable GPIO, and clock state but writes no host-side persistent storage. NVMEM BDADDR is read once at probe and later applied or used to mark invalid address state.

Dependencies and integration points: The driver depends on the HCI UART core, `h4_recv_buf`, serdev, OF matching, GPIO descriptors, optional external clocks, NVMEM cells, TI shared transport firmware structures from `ti_wilink_st.h`, firmware loading, HCI command sync APIs, and HCI core quirks. The serdev driver `hci-ti` registers OF compatibles for TI CC2560 and WiLink ST devices.

Risks and edge cases: HCILL state transitions can be driven by both host TX and controller packets; the spinlock protects state, but `send_hcill_cmd` queues while the lock is held. Unexpected HCILL packets are logged but generally not fatal. Firmware script parsing trusts action sizes from the `.bts` file within the loaded firmware buffer and supports only send, wait, and delay actions. Setup retries firmware download by toggling BT_EN, but returns immediately on CTS failure. BDADDR handling distinguishes absent, invalid, and valid NVMEM values with `BDADDR_NONE` and `BDADDR_ANY`. External clock errors are accepted only for missing clock.

# sources/distributed-fs/ceph-client/drivers/bluetooth/hci_mrvl.c

Purpose: This file implements the Marvell Bluetooth HCI UART protocol for 88W8897 and 88W8997 style controllers. It uses H4-style packet parsing plus Marvell vendor packet types for chip-version and firmware-request handshakes, supports controller-driven firmware chunk loading, and provides serdev OF integration.

Important APIs, types, and functions: `struct mrvl_data` stores partial RX, normal TX queue, raw firmware-data queue, state flags, current firmware transmit length, and chip ID/revision. `struct mrvl_serdev` embeds `hci_uart` for serdev registration. The Marvell packet header is `struct hci_mrvl_pkt`, whose two 16-bit halves must XOR to `0xffff`. Protocol callbacks are `mrvl_open`, `mrvl_close`, `mrvl_flush`, `mrvl_setup`, `mrvl_recv`, `mrvl_enqueue`, `mrvl_dequeue`, and for 8997 `mrvl_set_baudrate`. Handshake helpers are `mrvl_recv_fw_req`, `mrvl_recv_chip_ver`, `mrvl_load_firmware`, and `mrvl_send_ack`.

Control flow: Open requires hardware flow control, allocates state, initializes queues, sets chip-version pending, and opens the serdev if present. RX ignores noise until firmware-request is pending or firmware has loaded, then uses `h4_recv_buf` with standard HCI descriptors plus firmware-request and chip-version packet descriptors. Chip version and firmware request packets validate the XOR header, ACK or NAK, update state, and wake waiters. For 8897 setup, the driver stops flow control, loads a helper firmware at initial speed, waits until the final ACK is sent, switches host baudrate to operational speed, restarts flow control, and loads the main firmware. Firmware loading is controller-driven: each firmware request supplies the next chunk size, the driver queues raw data without an H4 packet header, and a zero-length final request confirms completion. For 8997, firmware may already be loaded by Wi-Fi over SDIO; `set_baudrate` waits for CTS, marks firmware loaded, sends a vendor baud-rate command, switches serdev baudrate, and requests vendor detection.

State and persistence behavior: State is volatile: firmware/chip-version pending flags, firmware-loaded flag, `tx_len`, chip ID/revision, partial RX skb, and two TX queues. The driver reads firmware files but does not modify storage. Firmware download changes controller RAM state and UART speed. Close purges normal and raw queues, frees partial RX, closes serdev, and frees protocol state.

Dependencies and integration points: The file depends on HCI UART, `h4_recv_buf`, serdev, OF matching, firmware loading, HCI command sync APIs, wait-on-bit synchronization, flow-control helpers, and tty/serdev baud setting. OF compatibles select either the 8897 setup-driven protocol or the 8997 baud-rate-driven protocol.

Risks and edge cases: Firmware loading is paced by controller requests, so missed request packets or bad wakeups cause two-second timeouts. The loop condition allows `fw_ptr == fw_max` to wait for the controller's final zero request, but any nonzero final request is treated as failure. RX intentionally drops data before firmware load/request states to tolerate noise, which can hide unexpected controller output. Raw firmware skbs bypass normal H4 type prepending by using `rawq`; queue ordering must keep ACKs and raw chunks in the expected order. Header XOR corruption results in NAK but still depends on the controller retrying.

Test signals: Validation should include chip-version packet parsing and pending-state wakeup, corrupted header NAK, unexpected firmware request rejection, helper and main firmware load sequencing, final zero-size request handling, chunk-size adjustment near EOF, firmware request timeout and interrupt paths, raw queue dequeue without H4 prefix, normal HCI queue dequeue with prefix, serdev open/close, 8997 CTS wait, Marvell set-baudrate command, `HCI_UART_VND_DETECT` behavior after speed change, and OF match selection for both supported chips.
