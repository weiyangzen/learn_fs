# sources/distributed-fs/orangefs/src/io/bmi/bmi_wintcp/bmi-wintcp.c

Purpose: implements the Windows TCP/IP BMI method for OrangeFS/PVFS. It exposes the `bmi_method_ops` table for `bmi_tcp`, manages WinSock startup, listening sockets, outbound connections, BMI send/receive posting, completion polling, unexpected-message buffering, cancellation, address teardown, trusted-connection policy, socket buffer tuning, and event instrumentation.

Important APIs/functions: exported BMI entry points include `BMI_tcp_initialize`, `BMI_tcp_finalize`, `BMI_tcp_set_info`, `BMI_tcp_get_info`, `BMI_tcp_memalloc`, `BMI_tcp_memfree`, `BMI_tcp_unexpected_free`, `BMI_tcp_post_send`, `BMI_tcp_post_sendunexpected`, `BMI_tcp_post_recv`, `BMI_tcp_test`, `BMI_tcp_testsome`, `BMI_tcp_testunexpected`, `BMI_tcp_testcontext`, `BMI_tcp_method_addr_lookup`, `BMI_tcp_post_send_list`, `BMI_tcp_post_recv_list`, `BMI_tcp_post_sendunexpected_list`, `BMI_tcp_open_context`, `BMI_tcp_close_context`, `BMI_tcp_cancel`, `BMI_tcp_addr_rev_lookup_unexpected`, and `BMI_tcp_query_addr_range`. Internal control is centered on `tcp_server_init`, `tcp_sock_init`, `enqueue_operation`, `tcp_do_work`, `tcp_do_work_send`, `tcp_do_work_recv`, `work_on_send_op`, `work_on_recv_op`, `payload_progress`, `tcp_forget_addr`, `tcp_cleanse_addr`, `tcp_shutdown_addr`, `handle_new_connection`, and `tcp_accept_init`.

Core types/state: `struct tcp_msg_header` is the on-wire envelope: magic number, mode, tag, size, and a 24-byte encoded header. `struct tcp_op` extends a generic BMI method operation with the header, a `BMI_TCP_INPROGRESS`/`BMI_TCP_BUFFERING`/`BMI_TCP_COMPLETE` state, and one-buffer list stubs. The file uses `struct tcp_addr` from `bmi-tcp-addressing.h` for per-peer socket state. Global state includes `interface_mutex`, `interface_cond`, `sc_test_busy`, `tcp_method_params`, `op_list_array`, `completion_array[BMI_MAX_CONTEXTS]`, `tcp_socket_collection_p`, `forceful_cancel_mode`, socket buffer tunables, `check_unexpected`, and PINT event IDs. Operation-list indices separate queued sends, posted receives, inflight receives, buffered completed eager receives, and completed unexpected receives.

Control flow: initialization starts WinSock, stores method flags/id/listen address, creates the server socket when requested, allocates operation queues, builds the socket collection around the listen socket or a client-only empty set, and defines send/receive tracing events. Address lookup parses `tcp://host:port` strings into method addresses. Send posting builds an eager or rendezvous header, preserves per-peer send ordering by checking `IND_SEND`, initializes or completes the nonblocking connection with `tcp_sock_init`, tries immediate `payload_progress`, and queues any remainder with write interest in the socket collection. Receive posting first consumes a fully buffered eager message, then attaches to a buffering inflight message if possible, otherwise queues a tagged receive. Poll/test functions call `tcp_do_work`, which owns one socket-collection polling pass at a time and dispatches ready addresses to accept, send, receive, or error handlers. Receive work peeks for a full header, enforces the magic value, matches posted receives by address/tag, buffers eager payloads with no posted receive, leaves rendezvous messages waiting in buffering state, and publishes unexpected messages to the unexpected queue.

State and persistence behavior: all state is process memory; no durable state is written. BMI buffers allocated by this method are 4096-byte aligned through `PINT_mem_aligned_alloc`. Unexpected payloads are heap buffers returned to callers and later freed by `BMI_tcp_unexpected_free`. Completed normal operations are moved to `completion_array[context_id]`; unexpected receives are moved to `IND_COMPLETE_RECV_UNEXP`; eager messages that arrived before a matching post are parked in `IND_RECV_EAGER_DONE_BUFFERING`. Address failures set `tcp_addr.addr_error`; server-accepted connections also set `dont_reconnect`, while client addresses may clear `addr_error` and reconnect. `tcp_forget_addr` removes the address from polling, shuts down/closes the socket, marks all matching queued/inflight operations complete or unexpected with an error, then either deallocates the method address or asks the BMI control layer to forget it.

Dependencies and integration: depends on WinSock2, `sockio` for nonblocking socket wrappers, `socket-collection` or `socket-collection-epoll` for readiness polling, `op-list` and `id-generator` for operation tracking, BMI method support/callback APIs for address registration and forget/drop callbacks, byte-swap helpers for header encoding, PINT events and hints for tracing, gossip/PVFS error reporting, and optional server configuration helpers for trusted network/port rules. It registers new inbound addresses through `bmi_method_addr_reg_callback` and reverse lookup optionally resolves peer hostnames when the gossip mask requests access hostnames.

Risks: the implementation relies on BMI-level serialization plus `interface_mutex`, but `tcp_do_work` unlocks around socket polling and uses `sc_test_busy`/`interface_cond` to coordinate concurrent testers; races in address removal or completion publication are high risk. `BMI_tcp_close_context` cleans the context queue but leaves stale `completion_array[context_id]` rather than setting it to `NULL`. `BMI_tcp_test` increments `*outcount` without clearing it first, so callers must initialize it. `tcp_sock_init` calls `bmi_set_sock_buffers` before creating a new socket, so the first call can query/set invalid socket `-1`; the later call after `BMI_sockio_new_sock` is the effective one. The nonblocking connect path compares a BMI/PVFS error return against `-WSAEWOULDBLOCK`, which is easy to regress because wrapper functions convert error domains. `handle_new_connection` checks `ret < 0` after `bmi_method_addr_reg_callback` but does not assign that callback return to `ret`. `payload_progress` uses one static `WSABUF` vector and is only safe while module calls remain serialized. Header decode casts into the byte array as `uint32_t*`/`uint64_t*`, which can be alignment-sensitive on non-x86 ports. Buffering unmatched eager messages can grow memory without a visible cap. Cancellation after any envelope progress forcefully drops the whole address, affecting unrelated operations on the same socket.

Test signals: useful tests include WinSock startup/finalize, server listen/accept, outbound nonblocking connect including would-block completion, immediate and queued sends, list send/recv across more than `BMI_TCP_IOV_COUNT` buffers, eager and rendezvous receive matching, eager-before-post buffering, unexpected receive/free lifecycle, bad magic/header timeout, zero-read-limit connection drop, address failure/reconnect/drop-query behavior, `BMI_FORCEFUL_CANCEL_MODE`, per-context completion drains, trusted network/port allow/reject paths, hostname reverse lookup with and without the gossip mask, and socket buffer set/get hints. Runtime signals include `GOSSIP_BMI_DEBUG_TCP` logs, PVFS/gossip error messages from `payload_progress`, `tcp_sock_init`, and socket collection polling, plus PINT send/receive event start/stop pairs.

# sources/distributed-fs/orangefs/src/io/bmi/bmi_wintcp/socket-collection-epoll.c

Purpose: implements the epoll-backed socket collection backend for the TCP BMI method. It wraps an epoll file descriptor, optionally registers the server listen socket, waits for readiness, and translates epoll readiness events into BMI socket collection status bits and method addresses.

Important APIs/functions: `BMI_socket_collection_init` allocates `struct socket_collection`, creates the epoll descriptor with `epoll_create(EPOLL_CREATE_SIZE)`, stores the server socket, and registers that listen socket with `EPOLLIN|EPOLLERR|EPOLLHUP` and `data.ptr = NULL`. `BMI_socket_collection_finalize` frees the collection. `BMI_socket_collection_testglobal` initializes output arrays, limits one wait to `min(incount, BMI_EPOLL_MAX_PER_CYCLE)`, retries `epoll_wait` on `EINTR`, maps `EPOLLERR|EPOLLHUP` to `SC_ERROR_BIT`, maps readable/writable flags to `SC_READ_BIT`/`SC_WRITE_BIT`, and creates a temporary server-port method address when the listen socket event uses `data.ptr == NULL`.

Control flow: add/remove/write-interest changes are not implemented in this `.c` file; they are inline macros from `socket-collection-epoll.h` that call `epoll_ctl` immediately. `testglobal` only consumes already-registered events. A listen event is represented as a newly allocated method address whose `tcp_addr.server_port` is set, whose socket points back to the collection server socket, and whose port is set to `-1`; `bmi-wintcp.c` later recognizes this as an accept trigger and deallocates the temporary address after handling it.

State and persistence behavior: state is entirely in memory. The collection stores `epfd`, a fixed `event_array` sized by `BMI_EPOLL_MAX_PER_CYCLE`, and the listen socket. The kernel epoll set stores per-peer `bmi_method_addr_p` values through `event.data.ptr`. No sockets or method addresses are destroyed by finalization; ownership remains with the BMI TCP layer.

Dependencies and integration: depends on Linux `epoll`, `gossip`, BMI method support, `bmi-tcp-addressing.h`, and the header macros that manipulate `struct tcp_addr.write_ref_count`. It is selected when `__PVFS2_USE_EPOLL__` includes `socket-collection-epoll.h` from `bmi-wintcp.c`, even though the directory is otherwise Windows-oriented.

Risks: `BMI_socket_collection_finalize` frees the structure but does not close `epfd`, leaking the epoll descriptor. The initialization failure path after a failed server-socket `epoll_ctl` frees the collection but also does not close `epfd`. `testglobal` returns raw `-errno` rather than converting through `bmi_tcp_errno_to_pvfs`, unlike the WinSock poll backend. The code tests event bits with `POLLIN`/`POLLOUT` instead of `EPOLLIN`/`EPOLLOUT`; these are usually numerically compatible on Linux but make the backend more brittle. Allocation of a temporary server method address is guarded only by `assert`, so release builds can dereference `NULL`. Because add/remove macros ignore `epoll_ctl` return values, stale registrations or failed modifications can silently affect progress.

Test signals: cover initialization with and without a server socket, failed `epoll_create`/`epoll_ctl`, read/write/error/hangup event translation, `incount == 0`, `EINTR` retry, event batches capped at `BMI_EPOLL_MAX_PER_CYCLE`, server accept event creation, add/remove/write-interest macro behavior around `write_ref_count`, and resource-leak checks that confirm `epfd` closure if this backend is fixed.

# sources/distributed-fs/orangefs/src/io/bmi/bmi_wintcp/socket-collection-epoll.h

Purpose: declares the epoll-backed socket collection interface and embeds the fast-path add/remove/write-interest operations as macros for the TCP BMI method.

Important APIs/types/macros: `struct socket_collection` contains `epfd`, `event_array[BMI_EPOLL_MAX_PER_CYCLE]`, and `server_socket`. `SC_READ_BIT`, `SC_WRITE_BIT`, and `SC_ERROR_BIT` are the backend-neutral readiness flags returned to `bmi-wintcp.c`. `BMI_socket_collection_init`, `BMI_socket_collection_finalize`, and `BMI_socket_collection_testglobal` are implemented by the matching `.c` file. `BMI_socket_collection_add` registers a connected peer socket for `EPOLLIN|EPOLLERR|EPOLLHUP`; `BMI_socket_collection_remove` clears `write_ref_count` and deletes the socket from epoll; `BMI_socket_collection_add_write_bit` increments `write_ref_count` and modifies the socket to include `EPOLLOUT`; `BMI_socket_collection_remove_write_bit` decrements the counter and removes `EPOLLOUT` only when it reaches zero.

Control flow support: read interest is implicit and always present for registered peer sockets. Write interest is reference-counted because multiple queued sends to the same method address can require one socket to remain writable until all send operations complete or cancel. The listen socket is added by initialization, not by macros. The macro implementation stores `tcp_data->map` in `event.data.ptr`, which is the value later returned as a ready address by `BMI_socket_collection_testglobal`.

State and persistence behavior: there is no persistence. Per-address poll state is split between the kernel epoll set and `struct tcp_addr.write_ref_count`; unlike the WinSock poll backend, this header does not maintain `sc_index` or queued add/remove lists.

Dependencies and integration: includes `<sys/epoll.h>`, `bmi-method-support.h`, `bmi-tcp-addressing.h`, `quicklist.h`, and `gen-locks.h`. `quicklist`/`gen-locks` are included for interface compatibility with the non-epoll header but are not central to this backend. The macros assume `method_data` points to a valid `struct tcp_addr` with a valid socket and map pointer.

Risks: macros call `epoll_ctl` without checking return codes, so duplicate adds, missing registrations, closed sockets, and failed modifications are silent. `BMI_socket_collection_remove` calls `EPOLL_CTL_DEL` even if `tcp_data->socket` is invalid; there is no guard matching the add macro. `BMI_socket_collection_add_write_bit` asserts the socket is valid, but assertions may be compiled out. Because these are macros, each argument can be evaluated in macro context and side effects would be hazardous. The header assumes epoll semantics and is not portable to Windows despite living under `bmi_wintcp`.

Test signals: compile coverage with `__PVFS2_USE_EPOLL__`, add/remove idempotency behavior, write reference-count increment/decrement balance, failed `epoll_ctl` diagnostics if added, and integration tests that prove queued sends keep `EPOLLOUT` armed until the last send completes.

# sources/distributed-fs/orangefs/src/io/bmi/bmi_wintcp/socket-collection.c

Purpose: implements the default WinSock `WSAPoll` socket collection backend used by `bmi-wintcp.c`. It keeps a dynamic array of sockets and corresponding BMI method addresses, accepts queued add/remove requests under a mutex, polls for readiness, and returns backend-neutral readiness bits to the TCP BMI progress engine.

Important APIs/functions: `BMI_socket_collection_init` allocates the collection, initializes `queue_mutex`, allocates `pollfd_array` and `addr_array`, initializes add/remove queues, stores the server socket, and inserts the server socket as `addr_array == NULL` when present. `BMI_socket_collection_queue` removes a method address from either pending queue if already queued and adds its `tcp_addr.sc_link` to the requested queue. `BMI_socket_collection_finalize` frees arrays and the collection. `BMI_socket_collection_testglobal` drains queued removals, applies queued additions/modifications, grows arrays by `POLLFD_ARRAY_INC` when full, calls `WSAPoll`, maps `POLLERR|POLLHUP|POLLNVAL`, `POLLIN`, and `POLLOUT` into status bits, supplements missing `WSAPoll` socket errors with `getsockopt(SO_ERROR)`, and creates a temporary server-port method address for listen readiness.

Control flow: callers never modify the poll arrays directly. `socket-collection.h` macros enqueue add/remove/write-interest changes; `testglobal` applies those changes at the start of the poll pass. Removal swaps the last active array entry into the removed entry's slot and updates the shifted address's `sc_index`. Addition either updates an existing entry's `events` field or appends a new entry. Read interest is implicit for all registered sockets, while `POLLOUT` is included only when `write_ref_count > 0`. After polling, the function skips addresses still pending in `remove_queue`, then emits up to `incount` ready maps/status values.

State and persistence behavior: state is memory-only. The collection owns the `WSAPOLLFD` array, the parallel method-address array, queue heads, mutex, and listen-socket marker. Each `struct tcp_addr` stores its current `sc_index`, queue link, and `write_ref_count`. The collection explicitly does not own method addresses or sockets, so finalization does not close sockets or free addresses.

Dependencies and integration: depends on WinSock2/`WSAPoll`, `quicklist`, generic locks, BMI method support, `bmi-tcp-addressing.h`, `gossip`, and PVFS debug/error conversion helpers. The backend is used by `bmi-wintcp.c` unless `__PVFS2_USE_EPOLL__` selects the epoll backend. `alloc_tcp_method_addr` is called for listen events, and the resulting temporary map is consumed by `handle_new_connection`.

Risks: `BMI_socket_collection_init` does not check `pollfd_array` allocation before using/freeing it through later paths. Queue coalescing uses a single `sc_link` per address; callers must not enqueue the same address into unrelated lists elsewhere. Removal assumes that after swapping the last entry, `addr_array[tcp_addr_data->sc_index]` is non-NULL; if the last entry is the server socket, dereferencing it would fail, though normal removals should target peer addresses. Array growth uses `assert` instead of a recoverable `ENOMEM` path. Pipe wakeup support is commented out, so queue changes do not actively interrupt a blocking `WSAPoll`; the implementation relies on timeouts and the BMI progress model. The graceful `POLLHUP` expression uses `!(revents & POLLERR+POLLNVAL)`, where operator precedence makes the intent less clear than an explicit mask. `getsockopt(SO_ERROR)` is polled for every socket with no revents, which can add overhead at high socket counts.

Test signals: cover queue coalescing for add/remove races, write-reference updates, array growth and `sc_index` repair after removals, server socket readiness, empty collection polling, timeout behavior after queued changes, error/hangup translation including graceful close with readable data, `SO_ERROR` fallback, and cancellation paths that remove write interest while sends are queued.

# sources/distributed-fs/orangefs/src/io/bmi/bmi_wintcp/socket-collection.h

Purpose: declares the default WinSock poll socket collection interface and the macros used by the TCP BMI method to queue peer sockets for addition, removal, and write-interest changes.

Important APIs/types/macros: `struct socket_collection` contains the dynamic `WSAPOLLFD` array, parallel `bmi_method_addr_p` array, maximum/count fields, `queue_mutex`, `remove_queue`, `add_queue`, `server_socket`, and unused/commented pipe handles. The exported functions are `BMI_socket_collection_init`, `BMI_socket_collection_queue`, `BMI_socket_collection_finalize`, and `BMI_socket_collection_testglobal`. Readiness bits are `SC_READ_BIT`, `SC_WRITE_BIT`, and `SC_ERROR_BIT`. `BMI_socket_collection_add` queues an address only if `tcp_data->socket > -1`; `BMI_socket_collection_remove` queues removal; `BMI_socket_collection_add_write_bit` asserts a valid socket, increments `write_ref_count`, and queues an update; `BMI_socket_collection_remove_write_bit` decrements `write_ref_count`, asserts it remains nonnegative, and queues an update.

Control flow support: the macros only enqueue work under `queue_mutex`; the arrays are changed later inside `BMI_socket_collection_testglobal`. This delayed update model lets callers request changes while another progress pass owns the poll arrays. Read interest is implicit; the only explicit state transition is whether write interest should be included based on `write_ref_count`.

State and persistence behavior: no durable state exists. Poll membership is represented both by collection arrays and by `struct tcp_addr.sc_index`. Pending changes live in the collection's quicklist queues through each address's embedded `sc_link`. The header notes a pipe notification design, but the Windows implementation currently leaves that disabled.

Dependencies and integration: includes BMI method support, TCP addressing, quicklist, and generic locks. It is tightly coupled to `struct tcp_addr` fields `socket`, `write_ref_count`, `sc_link`, and `sc_index`. `bmi-wintcp.c` calls these macros while holding its interface mutex; the collection has its own queue mutex for poll-array update coordination.

Risks: the macro API hides side effects and assumes valid non-NULL collection/address arguments. A send cancellation or failure path must balance every `BMI_socket_collection_add_write_bit` with a remove-write call or `write_ref_count` will keep `POLLOUT` armed. Since add/remove are deferred, callers must tolerate a socket remaining in `WSAPoll` until the next `testglobal` pass. The comment says a byte is written to a pipe to break poll, but the macro does not do that in this Windows implementation; stale comments can mislead maintainers about wakeup latency.

Test signals: compile-time macro expansion in all TCP paths, add-before-connect no-op behavior, write-reference balance under multiple queued sends, removal resetting `write_ref_count`, deferred queue processing by `testglobal`, and progress behavior when a blocking poll is already in flight.

# sources/distributed-fs/orangefs/src/io/bmi/bmi_wintcp/sockio.c

Purpose: provides a small WinSock socket I/O utility layer for the TCP BMI method. It creates, binds, connects, resolves, configures, and performs nonblocking scalar/vector send and receive operations while translating selected Windows socket errors into BMI/PVFS-style errors for higher layers.

Important APIs/functions: `BMI_sockio_new_sock` creates an IPv4 TCP socket. `BMI_sockio_bind_sock` binds to `INADDR_ANY:service`; `BMI_sockio_bind_sock_specific` resolves a supplied host and binds to that address; `BMI_sockio_connect_sock` resolves and connects to a remote host/port. `BMI_sockio_init_sock` has either a `gethostbyname` implementation with `conv_h_errno` or an `inet_aton` fallback. `BMI_sockio_nbrecv`, `BMI_sockio_nbpeek`, `BMI_sockio_nbsend`, and `BMI_sockio_nbvector` implement nonblocking receive, peek, send, and WinSock vector I/O. `BMI_sockio_get_sockopt`, `BMI_sockio_set_tcpopt`, and `BMI_sockio_set_sockopt` wrap socket option access. An optional `BMI_sockio_nbsendfile` block remains under `__USE_SENDFILE__` but is effectively non-Windows legacy code.

Control flow: scalar nonblocking receive and send loop until the requested byte count completes, an interrupt restarts the call, an error occurs, or `WSAEWOULDBLOCK` returns partial progress. `BMI_sockio_nbpeek` probes with `MSG_PEEK` and returns zero when a nonblocking read would block. `BMI_sockio_nbvector` intentionally issues one `WSARecv` or `WSASend` attempt rather than looping to exhaustion, returns zero on would-block, and returns the transferred byte count on success. Bind/connect wrappers retry on `WSAEINTR`; address initialization defaults `NULL` hostnames to localhost.

State and persistence behavior: no persistent state is stored. The functions operate only on caller-owned sockets and buffers. They sometimes set global `errno` for POSIX-like semantics (`EPIPE` on zero-byte receive), but most Windows errors are left for callers via `WSAGetLastError` or converted directly in bind/connect-specific paths.

Dependencies and integration: includes WinSock2, optional netdb/inet headers, BMI types, `sockio.h`, and `gossip`. `bmi-wintcp.c` uses this layer for server socket creation, binds, connects, nonblocking header/payload movement, `TCP_NODELAY`, `SO_REUSEADDR`, and buffer tuning. Error conversions depend on `bmi_errno_to_pvfs` and BMI error constants.

Risks: error-domain handling is inconsistent: bind-specific/connect convert through `bmi_errno_to_pvfs`, while scalar I/O often returns `-1` and expects the caller to consult `WSAGetLastError`. `BMI_sockio_nbrecv` treats `recv == 0` as `EPIPE` but does not set a WinSock error, so callers that convert `WSAGetLastError` may report a stale code. `BMI_sockio_nbvector` uses `MSG_PARTIAL` as the receive flags input and loops while flags retain `MSG_PARTIAL`; that is WinSock-specific and may not mean the same thing as POSIX partial progress. `typedef unsigned int socklen_t` and casts to `(int *)` for option lengths are portability compromises. The `__USE_SENDFILE__` branch references POSIX `sendfile`/`errno` and should not be enabled in this Windows file without porting. Legacy `gethostbyname` limits IPv6 support and thread-safety.

Test signals: unit tests or socket-pair integration tests should cover bind to any/specific host, failed resolution mapping, nonblocking connect would-block behavior, scalar send/recv partial progress, peek before full BMI headers, zero-byte remote close, vector send/recv with multiple buffers, would-block returns as zero, socket option get/set, localhost default resolution, and stale-error handling after zero-byte receives.

# sources/distributed-fs/orangefs/src/io/bmi/bmi_wintcp/sockio.h

Purpose: declares the WinSock utility interface used by `bmi-wintcp.c` and provides convenience macros for socket buffer/low-water settings and Windows blocking-mode control.

Important APIs/types/macros: function prototypes cover socket creation, any-address bind, specific-address bind, connect, address initialization, nonblocking recv/send/peek, vector I/O through `LPWSABUF`, socket option get/set, TCP option set, and optional sendfile. `GET_RECVBUFSIZE`, `GET_SENDBUFSIZE`, `SET_RECVBUFSIZE`, `SET_SENDBUFSIZE`, `GET_MINSENDSIZE`, `GET_MINRECVSIZE`, `SET_MINSENDSIZE`, and `SET_MINRECVSIZE` wrap the option helpers. `SET_NONBLOCK`, `SET_NONBLOCK_AND_SIGIO`, and `CLR_NONBLOCK` use `ioctlsocket(FIONBIO)` because Windows does not use `fcntl` for socket nonblocking mode.

Control flow support: the header intentionally presents a POSIX-like API while hiding WinSock-specific types and calls. `SET_NONBLOCK_AND_SIGIO` degrades to `SET_NONBLOCK` because there is no direct Windows equivalent for `FASYNC` in this implementation. `BRAINDEADSOCKS` can compile out buffer-size setters on platforms where changing socket buffers is unsafe.

State and persistence behavior: no state is stored by the header. The macros directly mutate socket blocking mode or options on caller-owned sockets. Socket buffer tuning flows from `BMI_tcp_set_info` through `bmi_set_sock_buffers` and these macros.

Dependencies and integration: includes WinSock2, `sys/types.h`, `stdio.h`, and `bmi-types.h`. The `LPWSABUF` signature links the vector I/O API to WinSock. `bmi-wintcp.c` includes this header for all low-level socket operations and uses its macros during server setup, accepted connection setup, outbound connection setup, and tuning.

Risks: macros do not report failures; callers of `SET_NONBLOCK` and `CLR_NONBLOCK` cannot tell if `ioctlsocket` failed. The public prototypes use `int` for socket descriptors even though `BMI_sockio_new_sock` returns `SOCKET`, which can be wider or unsigned on Windows. Low-water option macros may not be supported consistently by WinSock. The comment block still references older POSIX/Linux behavior, so maintainers need to distinguish historical intent from the active Windows implementation.

Test signals: compile on supported Windows toolchains, verify socket descriptor type conversions, nonblocking and blocking transitions, buffer option macros with valid and invalid sockets, and feature-flag builds for `BRAINDEADSOCKS` and `__USE_SENDFILE__`.
