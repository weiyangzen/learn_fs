# Research: sources/distributed-fs/ceph-client/drivers/usb/gadget/udc/pch_udc.c

Purpose: implements the PCI USB device controller driver for Intel EG20T/PCH, Intel Quark X1000, and ROHM/LAPIS ML7213/ML7831 UDC hardware. It exposes the controller through the Linux USB gadget UDC framework, manages high/full-speed gadget operation, endpoint enable/disable, request queuing, DMA descriptor chains, ep0 setup/control handling, VBUS GPIO detection, PCI probe/remove/PM, and hardware interrupt dispatch.

Important APIs, types, and functions: `struct pch_udc_dev` is the device-wide state with `usb_gadget`, bound gadget driver, PCI device, endpoint array, global spinlock, stall/config/ZLP flags, DMA pools, ep0 setup data, MMIO base/BAR, current configuration tuple, and optional VBUS GPIO state. `struct pch_udc_ep` wraps `usb_ep` plus setup/data DMA descriptors, register offset, queue, endpoint number/direction, halted state, and cached endpoint status. `struct pch_udc_request` wraps `usb_request` with data descriptor chain pointers, queue linkage, DMA progress flags, and chain length. Gadget operations are `pch_udc_pcd_get_frame`, `pch_udc_pcd_wakeup`, `pch_udc_pcd_selfpowered`, `pch_udc_pcd_pullup`, `pch_udc_pcd_vbus_session`, `pch_udc_pcd_vbus_draw`, `pch_udc_start`, and `pch_udc_stop`. Endpoint operations are `pch_udc_pcd_ep_enable`, `pch_udc_pcd_ep_disable`, `pch_udc_alloc_request`, `pch_udc_free_request`, `pch_udc_pcd_queue`, `pch_udc_pcd_dequeue`, `pch_udc_pcd_set_halt`, `pch_udc_pcd_set_wedge`, and `pch_udc_pcd_fifo_flush`. Core hardware helpers cover CSR access, endpoint control/status, DMA enable bits, interrupt masks, NAK/stall/fifo handling, device init/exit, and disconnect/reconnect.

Control flow: PCI probe allocates `pch_udc_dev`, enables and maps the selected BAR, runs platform hooks for Quark or MinnowBoard GPIO lookup, initializes hardware and endpoint software state via `pch_udc_pcd_init`, enables MSI, requests the shared IRQ, initializes the spinlock and gadget ops, creates DMA pools/descriptors, sets the device disconnected, and registers the gadget UDC. `pch_udc_start` binds the gadget driver, enables ep0/device interrupts, and clears disconnect if VBUS is present or no VBUS IRQ exists. Endpoint enable validates descriptors, programs endpoint type/buffer/maxpacket and CSR endpoint mapping using the current config/interface/alt tuple, clears halt, and unmasks the endpoint interrupt. Queueing maps the request for DMA, builds a descriptor chain split on endpoint maxpacket, sets request state to `-EINPROGRESS`, immediately handles ZLPs, starts OUT DMA through `pch_udc_start_rxrequest`, or arms IN interrupts so a later IN token calls `pch_udc_start_next_txrequest`.

Control endpoint flow: reset/enum interrupts clear DMA, mask endpoint interrupts, clear endpoint CSRs/status, empty queues, report gadget reset, then `pch_udc_svc_enum_interrupt` sets the detected speed, activates ep0, enables ep0 interrupts, enables DMA, and marks ep0 OUT receive-ready. Control OUT setup interrupts copy `ep0out` setup DMA data into `dev->setup_data`, select `gadget.ep0` based on request direction, call gadget `setup` outside the spinlock via `pch_udc_gadget_setup`, then clear NAK or stall depending on the result. Hardware-generated set-configuration and set-interface interrupts synthesize USB control requests for the gadget driver, update `cfg_data`, clear stalls, set `set_cfg_not_acked`, and rely on a later ZLP path to set `CSR_DONE`.

State and persistence: there is no on-disk persistence. Runtime state is held in MMIO registers, endpoint request queues, DMA pools/descriptors, `cfg_data`, VBUS work items, and flags such as `stall`, `prot_stall`, `vbus_session`, `set_cfg_not_acked`, and `waiting_zlp_ack`. `gadget.speed` transitions from unknown to full/high/low at enumeration and back to unknown on reinit/reset/stop. Request buffers are DMA-mapped per queue operation and unmapped in `complete_req`. Endpoint descriptor chains are reused per request and extended/freed as needed. VBUS GPIO work polls for stable rise/fall before reconnect/disconnect actions.

Dependencies and integration points: depends on PCI core, MMIO accessors, DMA mapping and `dma_pool`, Linux USB gadget core, USB chapter 9 definitions, IRQ/MSI support, GPIO descriptor and lookup-table APIs, workqueues, PM ops, and board-specific PCI IDs. It registers `MODULE_DEVICE_TABLE(pci)` for Intel Quark, Intel EG20T, CircuitCo MinnowBoard, ROHM ML7213, and ROHM ML7831 devices. It integrates with gadget drivers through UDC registration and `usb_gadget_udc_reset`, with VBUS detection through optional GPIO, and with board glue through `driver_data` platform init callbacks.

Risks: DMA lifetime and pool ownership are sensitive. In remove, the ep0 OUT data descriptor allocated from `data_requests` is freed through `stp_requests`, which is a pool mismatch risk. In queue error paths after `usb_gadget_map_request`, a later `prepare_dma` failure does not visibly unmap the request before returning. `pch_udc_free_dma_chain` uses `phys_to_virt` on descriptor addresses stored in hardware descriptors, so assumptions about DMA/CPU address identity matter. `complete_req` drops `dev->lock` around gadget callbacks and mutates `ep->halted`, so request completion reentrancy must be considered. Several wait loops use fixed busy/udelay budgets and only log on timeout. VBUS work uses `mdelay` in workqueue context and calls gadget disconnect/reconnect paths outside the main IRQ path. Control-transfer acknowledgement depends on `set_cfg_not_acked` and `waiting_zlp_ack`; missed ZLP completion can leave hardware waiting for `CSR_DONE`. The `speed_fs` module parameter changes device speed at init only.

Test signals: build-test PCI gadget configurations with `CONFIG_USB_GADGET`, GPIO, MSI, and PM enabled. Runtime tests should cover probe/remove for each PCI ID path, Quark BAR selection, MinnowBoard GPIO lookup, optional/no VBUS GPIO, gadget bind/unbind, pullup and VBUS session toggles, high-speed and full-speed enumeration including `speed_fs=1`, ep0 standard/vendor/class requests, SET_CONFIGURATION and SET_INTERFACE ack paths, unsupported setup STALL, bulk/interrupt/iso endpoint enable validation, IN/OUT DMA transfers larger than one maxpacket, 64 KiB OUT transfer accounting, ZLP requests, dequeue during active DMA, set_halt/set_wedge, reset during active queues, suspend/resume interrupt masking, and remove after queued traffic has drained.

# Research: sources/distributed-fs/ceph-client/drivers/usb/gadget/udc/pxa25x_udc.c

Purpose: implements the platform USB gadget UDC driver for Intel PXA25x/PXA26x and similar IXP4xx full-speed USB device controllers. It virtualizes the fixed PXA endpoint hardware for Linux gadget drivers, handles ep0 control traffic, PIO-only data transfers, D+ pullup/VBUS decisions, suspend/resume/reset interrupts, debugfs reporting, and platform probe/remove/PM.

Important APIs, types, and functions: the companion header defines `struct pxa25x_udc`, `struct pxa25x_ep`, `struct pxa25x_request`, ep0 state, stats, endpoint constants, and debug macros. This C file defines MMIO register offsets and bit fields, static controller instance `memory`, gadget ops `pxa25x_udc_ops`, endpoint ops `pxa25x_ep_ops`, platform driver `udc_driver`, and chip revision handling. Endpoint API entry points include `pxa25x_ep_enable`, `pxa25x_ep_disable`, `pxa25x_ep_alloc_request`, `pxa25x_ep_free_request`, `pxa25x_ep_queue`, `pxa25x_ep_dequeue`, `pxa25x_ep_set_halt`, `pxa25x_ep_fifo_status`, and `pxa25x_ep_fifo_flush`. Device-level entry points include `pxa25x_udc_get_frame`, `pxa25x_udc_wakeup`, `pxa25x_udc_vbus_session`, `pxa25x_udc_pullup`, `pxa25x_udc_vbus_draw`, `pxa25x_udc_start`, and `pxa25x_udc_stop`.

Control flow: probe validates the XScale chip revision, maps registers, gets the UDC clock and platform data, requests the optional pullup GPIO, initializes the watchdog timer, disables hardware, reinitializes software endpoint lists, requests the UDC IRQ, creates optional debugfs, and registers the gadget UDC. Binding a gadget driver records `dev->driver`, enables logical pullup, and optionally registers with an OTG transceiver. Actual hardware visibility is controlled by `pullup()`, which enables the clock and UDC only when VBUS, gadget pullup, and non-suspended state all agree. `udc_enable` clears stale interrupt state, configures PXA255 `UDCCFR` when available or old PXA250 test-mode registers otherwise, unmasks reset/suspend/resume and ep0 interrupts, and asserts the board pullup. `udc_disable` masks interrupts, disconnects pullup, clears UDE, and marks speed unknown.

Endpoint and request flow: non-ep0 endpoints are statically described in `memory`; endpoint enable only validates descriptor type/address/maxpacket against fixed hardware, records `ep.desc`, resets software state, and flushes FIFO. Queued requests are PIO-only. IN transfers use `write_packet`/`write_fifo` to fill the FIFO until the request completes or the FIFO cannot accept more, then endpoint IRQs continue the transfer. OUT transfers use `read_fifo` to drain complete packets, detect short packets, record overflow, and complete requests. Isochronous requests are constrained to one packet. Completion uses `done`, temporarily marks the endpoint stopped around `usb_gadget_giveback_request`, and preserves prior status when already set.

Control endpoint flow: `handle_ep0` is the ep0 state machine for `EP0_IDLE`, `EP0_IN_DATA_PHASE`, `EP0_OUT_DATA_PHASE`, `EP0_END_XFER`, and `EP0_STALL`. It reads setup packets from `UDDR0`, handles PXA errata where RNE may be unreliable, records standard/config request flags, and forwards most requests to the gadget driver. Hardware automagic for SET_ADDRESS, SET_CONFIGURATION, and SET_INTERFACE is special-cased; configuration changes clear all non-control endpoint queues and, when `UDCCFR` exists, are acknowledged through `AREN|ACM`. Failed gadget setup results normally stall ep0 using `FST|FTF` and a watchdog that restalls if hardware clears stall bits. `ep0start` coordinates clearing setup/OUT bits and acknowledging the ep0 interrupt.

Interrupt and reset flow: `pxa25x_udc_irq` loops while it handles work. It acknowledges suspend/resume/reset bits from `UDCCR`, calls gadget suspend/resume callbacks when appropriate, resets or marks enumeration completion based on `UDA`, and services endpoint interrupt status from `USIR0/USIR1` masked by `UICR0/UICR1`. Ep0 is handled first to reduce protocol latency; other endpoint IRQs call `handle_ep`, then acknowledge the endpoint bit. `reset_gadget` and `stop_activity` stop all endpoints, nuke queued requests, delete the watchdog timer, notify gadget reset or disconnect, and reinitialize driver-visible endpoint structures.

State and persistence: state is in the singleton `memory`, hardware registers, endpoint queues, `gadget.speed`, `ep0state`, stats, flags such as `vbus`, `pullup`, `has_cfr`, `req_pending`, `req_std`, `req_config`, `suspended`, and `active`, plus platform pullup/transceiver pointers. No persistent storage exists. `CONFIG_USB_PXA25X_SMALL` reduces exported endpoint count from 16 to 3. PM suspend intentionally disconnects and disables the 48 MHz clock, then resume restores pullup policy.

Dependencies and integration points: depends on platform device resources, platform data `pxa2xx_udc_mach_info`, GPIO or board `udc_command` pullup control, optional USB PHY/OTG `otg_set_peripheral` and `usb_phy_set_power`, clocks, debugfs/seq_file, ARM/IXP register access and CPU revision checks, Linux USB gadget core, USB chapter 9 constants, and IRQ handling. The platform alias is `pxa25x-udc`.

Risks: the driver relies on many documented and observed PXA hardware quirks: SET_INTERFACE is effectively broken, hardware configuration automagic can race gadget setup, ep0 stall bits may need watchdog restalling, and some revisions lie about RNE. DMA is deliberately unused, so throughput is bounded by PIO and interrupt latency. Endpoint definitions are fixed; gadget drivers needing dynamic endpoint reconfiguration or non-default iso altsettings are poor fits. Request completion can run gadget callbacks with local IRQs disabled/restored rather than a normal spinlock discipline. The UDCCR helper call ordering should be reviewed carefully because writing mask/status registers incorrectly can acknowledge interrupts or write the wrong offset. Suspend behavior requires reliable software pullup control for hosts to see disconnect.

Test signals: build with full and `CONFIG_USB_PXA25X_SMALL` endpoint sets, PXA and IXP configurations, debugfs enabled/disabled, and PM enabled. Runtime tests should exercise platform probe chip-revision acceptance/rejection, GPIO and `udc_command` pullup paths, gadget bind/unbind, VBUS session changes, suspend/resume disconnect/reconnect, reset start/end, GET_DESCRIPTOR, SET_ADDRESS, SET_CONFIGURATION, SET_INTERFACE limitations, deferred ep0 IN/OUT requests, unsupported setup stalls and watchdog restall, bulk IN/OUT transfers across multiple packets, short packets, ZLPs, overflow on undersized OUT buffers, dequeue, halt behavior including inability to clear halt, FIFO status/flush, and disconnect/reset while queues are active.

# Research: sources/distributed-fs/ceph-client/drivers/usb/gadget/udc/pxa25x_udc.h

Purpose: private header for the PXA25x/IXP4xx full-speed UDC driver. It supplies PXA25x-specific register bit definitions not provided by common architecture headers, endpoint/request/controller data structures, ep0 state definitions, FIFO sizing constants, optional endpoint-count selection, global controller declaration, and debug/logging helpers used by `pxa25x_udc.c`.

Important APIs, types, and symbols: `struct pxa25x_ep` wraps `usb_ep` with a controller pointer, request queue, PIO IRQ count, fixed FIFO/address/attribute metadata, stopped and DMA-fixup flags, and register offsets for `UDCCS`, `UBCR`, and `UDDR`. `struct pxa25x_request` wraps `usb_request` with queue linkage. `enum ep0_state` defines `EP0_IDLE`, IN/OUT data phases, end-transfer, and stall. `struct udc_stats` tracks ep0 read/write ops and bytes plus IRQs. `struct pxa25x_udc` holds the gadget, bound gadget driver, ep0 state, stats, flags for VBUS/pullup/CFR/config/request/suspend/active state, watchdog timer, device/clock/platform data/USB PHY pointers, DMA mask, endpoint array, MMIO base, and IRQ numbers. `to_pxa25x()` maps a `usb_gadget` back to the controller.

Control flow represented by the header: the header has no independent runtime flow, but its structures shape every path in the C file. Endpoint queues are per `pxa25x_ep`; ep0 state constrains queue handling and interrupt dispatch; the controller flags decide when `pullup()` enables hardware; `start_watchdog(dev)` schedules the timer used to repair ep0 stall behavior. `PXA_UDC_NUM_ENDPOINTS` is either 3 under `CONFIG_USB_PXA25X_SMALL` or 16 otherwise, which changes both the endpoint array and interrupt-servicing range.

State and persistence: no persistence. The declared structures are the runtime state containers for the singleton controller. The header also declares `static struct pxa25x_udc *the_controller`, which is shared within the translation unit after inclusion and is used by pullup/debug helpers.

Dependencies and integration points: includes `linux/types.h` and expects `usb_ep`, `usb_gadget`, `usb_gadget_driver`, `timer_list`, `device`, `clk`, `pxa2xx_udc_mach_info`, `usb_phy`, and Linux list definitions to be visible from the C file include order. Register bit definitions such as `UFNRH_*` and `UDCCFR_*` integrate with the PXA/IXP MMIO layout defined in the C file. Debug helpers use `pr_debug`, `pr_err`, `pr_warn`, and `pr_info`.

Risks: because this is a private header included after many C-file definitions, it depends on include-order context rather than being self-sufficient. The `the_controller` definition in a header would be unsafe if included by more than one C file, though here it is private to the driver. Debug dump helpers directly read hardware registers and the global controller, so enabling DEBUG can add register access and log volume. Endpoint count changes under `CONFIG_USB_PXA25X_SMALL` alter ABI-visible gadget endpoint availability and interrupt loops.

Test signals: compile both small and normal endpoint configurations, DEBUG and non-DEBUG builds, PXA and IXP architecture selections, and W=1 style builds for include-order and unused-symbol warnings. Runtime validation should confirm debug dumps match real register state, endpoint arrays match the configured endpoint count, and watchdog scheduling works with the `timer` field.

# Research: sources/distributed-fs/ceph-client/drivers/usb/gadget/udc/pxa27x_udc.c

Purpose: implements the platform USB gadget UDC driver for Intel/Marvell PXA27x full-speed USB device controllers. It works around hardware that binds physical endpoints to a single configuration/interface/altsetting by statically defining physical endpoint combinations, matching them to logical gadget endpoints, and driving all transfers through PIO and interrupts rather than DMA.

Important APIs, types, and functions: the companion header defines `struct pxa_udc`, `struct pxa_ep`, `struct udc_usb_ep`, `struct pxa27x_request`, register macros, endpoint definition macros, and ep0 states. This C file provides debugfs files `udcstate`, `queues`, and `epstate`; endpoint matching functions `find_pxa_ep` and `update_pxa_ep_matches`; endpoint ops `pxa_ep_enable`, `pxa_ep_disable`, `pxa_ep_alloc_request`, `pxa_ep_free_request`, `pxa_ep_queue`, `pxa_ep_dequeue`, `pxa_ep_set_halt`, `pxa_ep_fifo_status`, and `pxa_ep_fifo_flush`; gadget ops `pxa_udc_get_frame`, `pxa_udc_wakeup`, `pxa_udc_pullup`, `pxa_udc_vbus_session`, `pxa_udc_vbus_draw`, `pxa27x_udc_start`, and `pxa27x_udc_stop`; and the platform driver `pxa27x-udc`.

Control flow: probe reads platform data or device-tree resources, acquires optional D+ pullup GPIO or board command callback, maps registers, obtains IRQ/clock, gets a USB PHY via OF phandle or legacy lookup, prepares the clock, initializes static endpoint data, requests a shared IRQ, registers a PHY notifier, adds the gadget UDC, creates debugfs, and enables the hardware only if pullup, driver, and VBUS state say it should run. Gadget bind records `udc->driver`, optionally registers as an OTG peripheral, and calls `udc_enable` if `should_enable_udc()` is true. Pullup and VBUS session callbacks update `pullup_on`/`vbus_sensed`, then enable or disable the controller based on `should_enable_udc()` and `should_disable_udc()`.

Endpoint flow: `udc_init_data` initializes logical USB endpoints and physical PXA endpoint queues/locks. Before enabling the UDC, `pxa_eps_setup` programs every static physical endpoint CSR with config/interface/alt/address/type/direction/maxpacket data. At endpoint enable time, the logical endpoint is matched to a current physical endpoint using `config`, `last_interface`, and `last_alternate`; the code validates descriptor type and maxpacket but cannot dynamically reconfigure physical endpoint identity. Queued requests are added under the physical endpoint lock, endpoint IRQs are enabled, and `handle_ep` writes or reads as much as possible immediately unless recursion from a gadget completion is detected. IN paths use `write_packet`/`write_fifo`; OUT paths use `read_packet`/`read_fifo`; completion goes through `req_done`, which temporarily drops locks around `usb_gadget_giveback_request`.

Control endpoint flow: ep0 uses states `WAIT_FOR_SETUP`, `SETUP_STAGE`, `IN_DATA_STAGE`, `OUT_DATA_STAGE`, `IN_STATUS_STAGE`, `OUT_STATUS_STAGE`, `STALL`, and `WAIT_ACK_SET_CONF_INTERF`. `handle_ep0` watches `UDCCSR0_SA`, `OPC`, and interrupt cause bits, avoids clearing `OPC` in cases that would flush a new setup packet, and delegates actual setup parsing to `handle_ep0_ctrl_req`. Standard requests partly handled by hardware include address, feature/status/config/interface requests; remaining descriptor/vendor/class requests are passed to the gadget driver. Hardware set-configuration and set-interface notifications are handled by `irq_udc_reconfig`, which reads active config/interface/alternate fields, synthesizes gadget setup requests, updates cached endpoint matches, and sets `UDCCR_SMAC`.

Interrupt and reset flow: `pxa_udc_irq` reads `UDCISR0/1`, handles suspend/resume/config/reset special interrupts, then services endpoint interrupts. `irq_handle_data` acknowledges ep0 and endpoint packet/FIFO interrupts and dispatches to `handle_ep0` or `handle_ep`. Reset stops activity when the controller is no longer active, marks speed full, nukes ep0, flushes ep0 status, and resets ep0 state. Suspend/resume call gadget driver callbacks when connected. PM suspend saves `UDCCSR0`, disables the UDC, drops pullup, and reports disconnect; resume restores selected control bits, reasserts pullup if needed, enables hardware, and clears OTG pad hold state through platform code.

State and persistence: no persistent storage. Runtime state lives in singleton `memory`, MMIO registers, endpoint queues/locks, endpoint stats, current config/interface/alt fields, `gadget.speed`, pullup/VBUS state, PHY notifier state, and optional PM-saved control register bits. `udc_usb_ep[i].pxa_ep` is a cache that changes when configuration changes. Static endpoint tables define which gadget combinations can work.

Dependencies and integration points: depends on platform resources, clocks, GPIO descriptors, optional `pxa2xx_udc_mach_info`, OF compatible `marvell,pxa270-udc`, USB PHY/OTG APIs and notifier events, Linux gadget UDC core, debugfs rooted at `usb_debug_root`, USB chapter 9 constants, IRQ handling, and PXA platform OTG pad helper `pxa27x_clear_otgph`. It supports legacy platform data and device tree probing.

Risks: the hardware model is not USB-spec-friendly for multiple active interfaces or dynamic alternate settings. The static endpoint table is explicitly tuned for gadget zero, file storage, ether, RNDIS/serial, and has comments that later endpoints are for completeness and may not work. Ep0 behavior relies on undocumented timing and avoids clearing `OPC` to prevent losing setup packets; changes here can break enumeration. `stop_activity` loops over logical endpoints and calls `pxa_ep_disable`, but ep0 disable returns invalid for control endpoints, so reset/remove behavior should be checked carefully. PIO-only transfer handling limits throughput and makes interrupt latency important. Lock dropping around gadget callbacks allows reentrancy, so `in_handle_ep` recursion protection is important. Pullup/VBUS enable decisions depend on correct PHY notifier and GPIO/platform data behavior.

Test signals: compile with OF, platform-data, debugfs, PM, and PHY configurations. Runtime tests should cover probe through platform data and device tree, optional/inverted pullup GPIO, PHY VBUS notifier connect/disconnect, gadget bind/unbind, pullup and VBUS session state transitions, clock enable failure handling, full-speed enumeration, ep0 GET_DESCRIPTOR and vendor/class requests, hardware SET_CONFIGURATION and SET_INTERFACE interrupts, endpoint rematching after config changes, unsupported setup STALL, multi-packet bulk IN/OUT, ZLPs, short OUT packets, iso one-packet limit, dequeue and halt semantics, reset while requests are queued, suspend/resume disconnect behavior, and debugfs queue/state output under traffic.

# Research: sources/distributed-fs/ceph-client/drivers/usb/gadget/udc/pxa27x_udc.h

Purpose: private hardware and data-model header for the PXA27x UDC gadget driver. It defines register offsets and bit fields, register access macros, endpoint definition macros, physical/logical endpoint structures, request structures, ep0 states, controller state, and logging helpers used by `pxa27x_udc.c`.

Important APIs, types, and symbols: register definitions cover global UDC registers (`UDCCR`, `UDCICR0/1`, `UDCISR0/1`, `UDCFNR`, `UDCOTGICR`, `UP2OCR`, `UP3OCR`) and per-endpoint registers (`UDCCSRn`, `UDCBCRn`, `UDCDRn`, `UDCCRn`). Bit masks define UDC enable/active/resume/OTG support, endpoint interrupt enable/status, control endpoint status, data endpoint status, endpoint configuration fields, write masks, frame/byte-count masks, and OTG/port control bits. Access macros `udc_readl`, `udc_writel`, `udc_ep_readl`, `udc_ep_writel`, `udc_ep_readb`, and `udc_ep_writeb` map structure state to raw MMIO. Endpoint macros build logical USB endpoints (`USB_EP_*`) and static physical PXA endpoints (`PXA_EP_*`) with config/interface/alt metadata.

Important structures: `struct udc_usb_ep` is the logical gadget-visible endpoint, containing `usb_ep`, a descriptor template, controller pointer, and cached matching `pxa_ep`. `struct pxa_ep` is a physical hardware endpoint with queue, spinlock, enabled/recursion flags, index/name, direction/address/config/interface/alternate/fifo/type fields, PM-saved registers, and stats. `struct pxa27x_request` wraps `usb_request`, records the logical endpoint, tracks whether it is already queued, and links into a physical endpoint queue. `struct pxa_udc` holds MMIO, IRQ, clock, gadget, driver, device, pullup mechanisms, PHY, ep0 state, stats, logical endpoint array, physical endpoint array, enable/pullup/VBUS/config/interface/alternate state, and PM save state. `to_pxa()` and `to_gadget_udc()` map gadget pointers back to the controller.

Control flow represented by the header: endpoint definition macros encode the static workaround for hardware that freezes endpoint configuration once enabled. Logical endpoints can map to different physical endpoints depending on `config`, `interface`, and `alternate`, and the C file's `find_pxa_ep` consumes exactly these fields. Ep0 state names are defined here for debug output and state-machine dispatch. Register access macros centralize address calculation from `ep->idx` and `dev->regs`.

State and persistence: no on-disk state. The header defines the complete in-memory controller state model and the static sizing constants `NR_USB_ENDPOINTS` and `NR_PXA_ENDPOINTS`. PM-only fields preserve endpoint control/status values across suspend. The `ep0_state_name` array is static debug state in the translation unit.

Dependencies and integration points: includes Linux types, spinlocks, I/O accessors, and USB OTG definitions; expects USB gadget/chapter 9 types and platform data to be visible where included. It integrates with the gadget core through embedded `usb_ep`/`usb_gadget`, with debugfs/logging through helper macros, and with PXA hardware through raw MMIO register definitions.

Risks: the static endpoint macro design is easy to extend incorrectly; config/interface/alt values must match real gadget descriptors or endpoint enable will fail at runtime. The header exposes many raw bit masks, so incorrect write-mask use can alter status bits or acknowledge interrupts. `struct udc_usb_ep` stores `struct pxa_udc *dev` in the code but the header declaration names `struct pxa_udc` only after a forward declaration typo-like mismatch with `struct pxa27x_udc`; build coverage is needed to catch type drift. `ep0_state_name` is a non-const static array in the header and would be duplicated if included by multiple C files.

Test signals: compile all configurations that include this header, especially PM and debug builds. Validate that generated endpoint CSR values from `PXA_EP_*` macros match hardware documentation, logical endpoint capabilities match descriptors, register access offsets match the PXA27x manual, and state-name indexing remains aligned with `enum ep0_state`.
