## sources/distributed-fs/ceph-client/drivers/net/can/usb/peak_usb/pcan_usb.c

Purpose: this file implements the original single-channel PEAK PCAN-USB adapter protocol on top of the shared `peak_usb` CAN-over-USB core. It translates SocketCAN classic CAN frames, controller modes, bus state notifications, timestamps, bit timing, LED identification, and the device's small command protocol into the callbacks consumed by `pcan_usb_core.c`.

Important APIs, types, and functions: `struct pcan_usb` extends `struct peak_usb_device` with a `peak_time_ref`, restart timer, and cached `can_berr_counter`. `struct pcan_usb_msg_context` tracks decoding state across packed USB records. Command helpers include `pcan_usb_send_cmd()`, `pcan_usb_wait_rsp()`, `pcan_usb_set_bus()`, `pcan_usb_set_silent()`, `pcan_usb_set_err_frame()`, `pcan_usb_set_ext_vcc()`, `pcan_usb_set_led()`, and SJA1000 register mode setup. Data paths are `pcan_usb_decode_buf()`, `pcan_usb_decode_msg()`, `pcan_usb_decode_data()`, `pcan_usb_decode_status()`, `pcan_usb_decode_error()`, and `pcan_usb_encode_msg()`. The exported `const struct peak_usb_adapter pcan_usb` binds these callbacks, endpoints, buffer sizes, timestamp conversion parameters, bit timing constants, and ethtool operations into the common driver.

Control flow: probe first validates that the interface exposes only the expected PCAN-USB command and message endpoints. Core device creation then calls `pcan_usb_init()` to set up the restart timer, read the serial number, log hardware revision, and enable additional loopback/one-shot support for newer firmware. When the netdev opens, the common core allocates URBs and calls `pcan_usb_start()`, which initializes timestamp state, resets cached bus error counters, enables bus error event reporting, optionally programs listen-only mode, and disables external VCC. Bus-on goes through `pcan_usb_write_mode()`, which sends the transceiver command and waits for hardware startup. Receive URBs contain a record count followed by internal status records or CAN data records; the decoder reconstructs 16-bit timestamps with compact 8-bit deltas, updates hardware timestamps, delivers normal frames, and synthesizes CAN error skbs on overrun, warning, passive, or bus-off transitions. Transmit builds one PCAN-USB record from a classic CAN skb, encoding standard/extended identifiers, RTR, loopback SRR, and one-shot AT flags. Restart from bus-off is asynchronous: a command URB turns the bus on, the completion schedules a timer, and the timer calls `peak_usb_restart_complete()`.

State and persistence: persistent runtime state is in the `pcan_usb` private object: hardware timestamp reference, restart timer, and the last observed TX/RX error counters. The common core stores the cached CAN channel ID, but this specific device only supports an 8-bit ID and refuses writes above `U8_MAX` or while the interface is up because flashing briefly disconnects the device. Device state is otherwise hardware-resident: bus mode, SJA1000 mode, silent mode, external VCC, LED state, error reporting, and bit timing.

Dependencies and integration points: the file depends on the shared `pcan_usb_core.h` adapter contract, Linux USB bulk messaging, SocketCAN classic CAN helpers, CAN error frame definitions, ethtool physical identification, unaligned little-endian helpers, and PEAK's SJA1000-derived firmware protocol. It integrates with `pcan_usb_core.c` through `struct peak_usb_adapter` callbacks and with userspace through SocketCAN, ethtool timestamp reporting, ethtool EEPROM access, and the core `peak_usb/can_channel_id` sysfs attribute.

Risks: the protocol has dense variable-length records, so bounds checks around timestamp, identifier, and payload fields are critical. Error state accuracy depends on bus-event records updating `pdev->bec` before status records are interpreted. Several control commands return success when the core has marked the USB device disconnected, which avoids teardown noise but can mask late-command failures. The 8-bit CAN channel ID behavior differs from other PEAK adapters. Restart relies on a fixed startup delay and a timer after asynchronous USB completion, so bus-off recovery tests should cover timing-sensitive paths.

Test signals: attach a PCAN-USB and verify probe logs hardware revision and serial number, `ip link set canX up type can bitrate ...` programs BTR0/BTR1 and reaches `ERROR-ACTIVE`, normal and RTR classic CAN frames transmit and receive with sane hardware timestamps, listen-only/one-shot/loopback modes behave according to firmware revision, induced bus warning/passive/bus-off generates SocketCAN error frames and updates berr counters, `ethtool --identify` toggles LEDs, and ethtool EEPROM operations enforce the 8-bit channel ID and refuse writes while the interface is up.

## sources/distributed-fs/ceph-client/drivers/net/can/usb/peak_usb/pcan_usb_core.c

Purpose: this is the shared USB and SocketCAN framework for the PEAK-System USB adapter family. It matches PEAK USB product IDs, creates one CAN netdev per controller/channel, owns the generic URB transmit/receive lifecycle, delegates protocol-specific encoding, decoding, timing, and control operations through `struct peak_usb_adapter`, and exposes common timestamp and CAN channel ID facilities.

Important APIs, types, and functions: the USB ID table maps product IDs to adapter descriptors such as `pcan_usb`, `pcan_usb_pro`, `pcan_usb_fd`, `pcan_usb_chip`, `pcan_usb_pro_fd`, and `pcan_usb_x6`. `peak_usb_create_dev()` allocates and registers a `struct peak_usb_device`-backed CAN netdev. `peak_usb_start()`, `peak_usb_ndo_open()`, `peak_usb_ndo_stop()`, and `peak_usb_unlink_all_urbs()` own RX/TX URB setup and teardown. `peak_usb_ndo_start_xmit()`, `peak_usb_read_bulk_callback()`, and `peak_usb_write_bulk_callback()` provide the shared data path around adapter `dev_encode_msg()` and `dev_decode_buf()` callbacks. Timestamp helpers include `peak_usb_init_time_ref()`, `peak_usb_set_ts_now()`, `peak_usb_update_ts_now()`, `peak_usb_get_ts_time()`, and `peak_usb_netif_rx_64()`. Common ethtool/sysfs helpers include `peak_usb_get_eeprom_len()`, `peak_usb_get_eeprom()`, `peak_usb_set_eeprom()`, `pcan_get_ts_info()`, and `can_channel_id_show()`.

Control flow: module init registers a `usb_driver`; USB probe selects the adapter descriptor from `driver_info`, optionally lets the adapter reject non-CAN interfaces, and creates `ctrl_count` netdevices as a sibling chain on the USB interface. Device creation initializes CAN clock and bit timing callbacks, CAN FD data bit timing when present, mode restart callback, berr-counter callback, endpoint addresses, ethtool operations, sysfs groups, echo contexts, and anchors, then registers the CAN device and runs adapter-specific initialization. Opening a netdev calls `open_candev()`, allocates and submits up to four RX URBs, preallocates ten TX URBs with buffers and contexts, runs adapter `dev_start()`, sets the bus on through `dev_set_bus()`, and starts the queue. TX picks a free echo context, asks the adapter to encode an skb into the URB buffer, anchors and submits it, and stops the queue when all TX URBs are active. RX completion checks USB status, invokes adapter decoding only after the started flag is set, and resubmits the URB. Stop clears started state, stops the net queue, kills RX/TX URBs, calls adapter stop, sets bus off, and closes CAN state. Disconnect unregisters every sibling netdev, clears connected state, frees command buffers and adapter-private shared state, and frees candevs.

State and persistence: `struct peak_usb_device` tracks connection/started flags, USB device, netdev, active TX URB count, TX echo contexts, anchors, command buffer, cached CAN channel ID, hardware revision, selected endpoints, and sibling links. `struct peak_time_ref` converts device tick domains to kernel time while handling wrap and periodically resetting the host/device base after long intervals. CAN channel ID is cached early and refreshed after ethtool reads/writes; actual persistence is device firmware/flash via adapter callbacks.

Dependencies and integration points: the file sits between Linux USB core, netdevice operations, SocketCAN `alloc_candev()`/`register_candev()`/`open_candev()`/`close_candev()`, CAN echo skb helpers, ethtool EEPROM and timestamp APIs, sysfs attributes, and all PEAK protocol-specific files. It depends on adapter descriptors exported by `pcan_usb.c`, `pcan_usb_pro.c`, and `pcan_usb_fd.c`.

Risks: adapter callbacks run under common URB and netdev assumptions; a protocol encoder must respect the preallocated buffer size and set the actual `size`, while a decoder must fully validate firmware-controlled record lengths. `peak_usb_start()` tolerates partial RX/TX URB allocation with performance warnings, which should be intentional for low-memory behavior. Sibling management is stack-like through `prev_siblings` and `next_siblings`, so error paths must restore interface data correctly. The common EEPROM helpers rely on every adapter implementing get/set channel ID and on little-endian byte slicing to make partial ethtool writes architecture-independent. Timestamp conversion is subtle around device counter wrap and long host uptime.

Test signals: device-family smoke tests should verify one netdev per channel, expected `can_channel_id` sysfs values, clean open/close cycles, URB kill/free behavior on unplug while up and down, TX queue stop/wake under full echo-context pressure, adapter decode errors causing hex dumps rather than memory misuse, bus-off restart through `CAN_MODE_START`, ethtool EEPROM partial-byte channel ID updates, and RX hardware timestamp monotonicity across device timestamp wrap.

## sources/distributed-fs/ceph-client/drivers/net/can/usb/peak_usb/pcan_usb_core.h

Purpose: this header defines the shared PEAK USB CAN adapter contract. It centralizes vendor/product IDs, driver limits, the adapter callback table, generic per-channel device state, timestamp conversion state, TX URB context state, and helper prototypes used by the PCAN-USB, PCAN-USB Pro, and PCAN-USB FD family implementations.

Important APIs, types, and functions: `struct peak_usb_adapter` is the key abstraction. It describes adapter name, product ID, control mode support, CAN clock, arbitration/data bit timing constants, channel count, ethtool operations, interface probe hook, lifecycle hooks, bus/bit timing/channel-ID operations, RX decoder, TX encoder, restart handler, berr-counter hook, endpoint addresses, timestamp scaling parameters, buffer sizes, and private allocation size. `struct peak_time_ref` stores host/device timestamp bases and adapter scaling. `struct peak_tx_urb_context` binds a TX URB to a PEAK device and CAN echo index. `struct peak_usb_device` embeds `struct can_priv` and stores adapter, controller index, state flags, USB/netdev pointers, URB anchors, command buffer, cached channel ID, revision, endpoints, and sibling links. Public helpers cover memory dumps, timestamp setup/conversion, 64-bit hardware timestamp RX, async completion, restart completion, timestamp ethtool reporting, and common ethtool EEPROM access.

Control flow: protocol-specific files declare a `const struct peak_usb_adapter` and fill this table. `pcan_usb_core.c` consumes the table during USB probe, netdev allocation, open/close, TX/RX URB callbacks, CAN bit timing changes, CAN mode restarts, and ethtool operations. Timestamp helpers use the `ts_used_bits`, `us_per_ts_shift`, and `us_per_ts_scale` fields from the active adapter descriptor.

State and persistence: the header itself stores no state, but defines the long-lived objects that hold runtime state. `PCAN_USB_STATE_CONNECTED` gates synchronous USB commands after unplug; `PCAN_USB_STATE_STARTED` gates RX decoding after netdev open. The channel ID field is a cached mirror of device-persistent configuration and is exposed through sysfs and ethtool.

Dependencies and integration points: the types assume Linux USB, netdevice, SocketCAN, ethtool, and skb timestamp APIs included by implementation files. The external adapter descriptors are the registration points that make individual protocol files visible to the common USB ID table.

Risks: callback contracts are implicit; mismatched buffer sizes, endpoint arrays, `sizeof_dev_private`, or timestamp scaling values can break multiple core paths. `PCAN_USB_MAX_CHANNEL` is two, while newer PEAK devices may have more physical channels in product naming, so adapter descriptors must accurately reflect what this core can instantiate per USB interface. The first member embedding pattern used by private structs requires `sizeof_dev_private` to be at least `sizeof(struct peak_usb_device)` and container casts to match the concrete private type.

Test signals: compile coverage should catch missing callbacks/prototypes, while runtime validation should instantiate each exported adapter descriptor, verify channel counts and endpoint arrays, confirm private struct sizing, and exercise timestamp and EEPROM helpers through at least one classic, Pro, and FD-family device.

## sources/distributed-fs/ceph-client/drivers/net/can/usb/peak_usb/pcan_usb_fd.c

Purpose: this file implements PEAK's CAN FD capable USB family: PCAN-USB FD, PCAN-Chip USB, PCAN-USB Pro FD, and PCAN-USB X6. It plugs into the shared PEAK USB core while using PEAK's uCAN/PUCAN command and message formats for CAN FD frames, data bit timing, ISO/non-ISO FD mode, hardware timestamps, error counters, overrun reporting, LED control, and firmware-provided endpoint discovery.

Important APIs, types, and functions: `struct pcan_ufd_fw_info` mirrors firmware/bootloader/device-ID/endpoint metadata. `struct pcan_usb_fd_if` is shared per USB interface and contains channel pointers, firmware info, timestamp reference, calibration ignore count, and open-channel count. `struct pcan_usb_fd_device` extends the generic PEAK device with a cached berr counter, shared interface pointer, and shared command buffer. Command helpers include `pcan_usb_fd_send_cmd()`, `pcan_usb_fd_read_fwinfo()`, `pcan_usb_fd_build_restart_cmd()`, `pcan_usb_fd_set_bus()`, `pcan_usb_fd_set_filter_std()`, `pcan_usb_fd_set_options()`, `pcan_usb_fd_set_can_led()`, `pcan_usb_fd_set_clock_domain()`, nominal/data bit timing setters, channel-ID get/set, and async restart. RX handlers include `pcan_usb_fd_decode_canmsg()`, `pcan_usb_fd_decode_status()`, `pcan_usb_fd_decode_error()`, `pcan_usb_fd_decode_overrun()`, `pcan_usb_fd_decode_ts()`, and `pcan_usb_fd_decode_buf()`. TX encoding is in `pcan_usb_fd_encode_msg()`. Four adapter descriptors at the bottom define product-specific names, channel counts, bit timing constants, endpoints, and callbacks.

Control flow: PEAK core probe calls `pcan_usb_fd_probe()` to accept only interface 0 for the FD-family path. First channel initialization allocates shared interface state and a 512-byte command buffer, reads firmware info, logs versions, derives ISO/non-ISO FD support from firmware major version, fills default command endpoints when old firmware lacks endpoint metadata, notifies the device that the driver is loaded, and later channels reuse that shared state. If firmware includes extended endpoint metadata, channel netdevs override the default data endpoints. Initialization selects a device clock-domain command matching the adapter clock and restores default LED mode. Open calls `pcan_usb_fd_start()`, which accepts all standard IDs, initializes shared time reference on first open, enables error and USB calibration messages, increments open count, resets cached berr counters, then the core sets bus on with a command list that resets error counters, toggles ISO/non-ISO FD option as needed, and enters normal or listen-only mode. RX URBs contain aligned records; decoder dispatches CAN/CAN FD frames, calibration timestamps, error-counter messages, status transitions, and USB overrun messages. TX builds one PUCAN CAN_TX record with classic or FD flags, BRS/ESI, RTR, extended ID, single-shot, channel DLC, aligned payload, and a zero-size terminator. Stop disables special messages on last close; exit turns bus and LEDs off and clears driver-loaded state.

State and persistence: shared interface state persists across sibling channel netdevs and is freed only when the last sibling is removed. Firmware info caches device IDs and endpoint numbers. `pcan_usb_fd_device::bec` stores the latest error counters received from PUCAN error records and is consumed by status-change handling and `do_get_berr_counter`. Device-persistent channel IDs are read through firmware info and written with `PCAN_UFD_CMD_DEVID_SET`. Control mode persistence is per netdev, with firmware versions before 2.x forced to non-ISO FD because they cannot switch dynamically.

Dependencies and integration points: this file depends on `pcan_usb_core.h`, `pcan_usb_pro.h` vendor request helpers, and `<linux/can/dev/peak_canfd.h>` for PUCAN commands, message layouts, and bitfield macros. It integrates with the PEAK shared core's adapter contract, SocketCAN CAN FD skb allocation, CAN FD data bit timing, CAN error state APIs, ethtool physical ID and EEPROM helpers, and hardware timestamp delivery through `peak_usb_netif_rx_64()`.

Risks: command sending has a full-speed USB workaround that slices command buffers to 64-byte packets; regressions here can affect older or low-speed negotiated devices. Firmware metadata controls endpoints and FD ISO support, so both old and extended response formats need coverage. The adapter descriptors expose only up to two channels through this core even for X6 naming, making descriptor semantics important. Status messages rely on previously received error-counter messages to choose TX/RX state direction. Decoder bounds checks must be correct for firmware-provided `size` fields. Shared open-count and command-buffer state span multiple netdevs and require open/close/unplug tests across sibling channels.

Test signals: validate all four product descriptors probe, firmware info parsing with and without extended endpoint fields, CAN and CAN FD TX/RX including BRS/ESI and RTR classic frames, nominal and data bit timing commands, listen-only/one-shot/FD non-ISO toggles, full-speed command chunking, calibration timestamp messages after the ignore window, standard filter setup, overrun/error/status frame generation, berr-counter reporting, LED identify/default/off behavior, channel-ID read/write, multi-channel open/close ordering, and unplug during active traffic.

## sources/distributed-fs/ceph-client/drivers/net/can/usb/peak_usb/pcan_usb_pro.c

Purpose: this file implements the two-channel classic CAN PEAK PCAN-USB Pro adapter protocol. It provides the device-specific command builder, firmware/bootloader/vendor-request handling, shared per-interface timestamp state, per-channel bus/bit timing/control operations, RX record decoding, TX record encoding, LED identification, and the `pcan_usb_pro` adapter descriptor consumed by the common PEAK USB core.

Important APIs, types, and functions: `struct pcan_usb_pro_interface` stores two channel device pointers, one shared `peak_time_ref`, timestamp calibration ignore count, and opened-channel count. `struct pcan_usb_pro_device` extends `struct peak_usb_device` with the shared interface pointer and cached CCBT bit timing value. `struct pcan_usb_pro_msg` abstracts record-list command buffers. `pcan_msg_init()`, `pcan_msg_init_empty()`, and `pcan_msg_add_rec()` build variable-size records. `pcan_usb_pro_send_cmd()`, `pcan_usb_pro_wait_rsp()`, and exported `pcan_usb_pro_send_req()` perform bulk and vendor control transfers. Device callbacks include timestamp enable, bitrate, bus, silent, filter, LED, channel-ID, bit timing, restart, driver-loaded notification, RX handlers, TX encoder, start/stop/init/exit/free, interface endpoint probe, and ethtool physical ID.

Control flow: the common core validates endpoints through `pcan_usb_pro_probe()` and creates two sibling netdevs. First-channel initialization allocates the shared interface object, firmware info, and bootloader info; reads FW/BL metadata through vendor requests; tells the device the driver is loaded; logs hardware revision and serial; and sets LEDs back to device-default. The second channel reuses the shared interface. Opening a channel programs listen-only mode, enables bypass filtering, and on first open initializes timestamp state and enables timestamp records. The core then sets the bus on; `pcan_usb_pro_set_bus()` re-sends the cached CCBT before enabling the bus. RX decoding reads a record count from the message header and dispatches CAN data records, status records, and timestamp calibration records. CAN data records choose the channel from the encoded length nibble, build classic CAN skbs, add EFF/RTR flags, copy payload, update stats, convert the shared 32-bit timestamp, and deliver with `netif_rx()`. Status records synthesize CAN error skbs for bus-off, warning, passive, overrun, and queue-overrun states. TX encoding selects TXMSG0/4/8 based on RTR and payload length, encodes the channel in the length nibble, adds EFF/RTR/single-shot flags, and returns the actual record-list length. Stop disables timestamp records on last close; exit turns off bus and clears driver-loaded state for channel 0.

State and persistence: the shared interface object persists until both sibling devices are freed. Shared timestamp state is valid only after enough calibration messages have been ignored for clock stabilization. `cached_ccbt` preserves the last bit timing register value so bus-on can reapply it. `dev_opened_count` gates timestamp message enable/disable across channels. Device-persistent CAN channel IDs are read and written through GETDEVID/SETDEVID records.

Dependencies and integration points: the file uses the shared PEAK core, `pcan_usb_pro.h` record definitions, Linux USB bulk/control APIs, SocketCAN classic CAN/error helpers, ethtool physical ID and common EEPROM/channel-ID helpers, and the core timestamp conversion functions. `pcan_usb_fd.c` also reuses the exported vendor-request helper and restart completion callback from this file/header family.

Risks: command/response matching only retries a small number of bulk responses and filters by data type/channel, so unsolicited records can cause control operations to fail. `pcan_msg_add_rec()` uses varargs and a static record-size table; incorrect argument ordering or record lengths can corrupt messages. Error-state handling suppresses duplicate state reports but must still account for overrun-only records. Timestamp state is shared by both channels, so first-open/last-close logic must stay balanced. Cached bit timing must be initialized before bus-on or reactivation after bus-off can use stale zero settings.

Test signals: verify two netdevs appear for one adapter, firmware and bootloader info are logged once, both channels can open independently and together, timestamp records are enabled only while at least one channel is open, bit timing CCBT is reapplied on bus-on, channel-specific CAN RX/TX and error status records route to the correct netdev, warning/passive/bus-off and overrun reports generate expected CAN error frames, single-shot/listen-only modes are encoded, ethtool identify blinks and restores LEDs, and channel-ID ethtool operations work for both channels.

## sources/distributed-fs/ceph-client/drivers/net/can/usb/peak_usb/pcan_usb_pro.h

Purpose: this header defines the PEAK PCAN-USB Pro and Pro FD vendor request constants, endpoint addresses, command record IDs, record layouts, status bits, LED modes, and shared function prototypes used by `pcan_usb_pro.c` and reused by FD-family code for common vendor control requests and restart completion.

Important APIs, types, and functions: vendor requests are identified by `PCAN_USBPRO_REQ_INFO`, `PCAN_USBPRO_REQ_FCT`, `PCAN_USBPRO_INFO_BL`, `PCAN_USBPRO_INFO_FW`, and `PCAN_USBPRO_FCT_DRVLD`. Endpoint constants describe command and CAN message pipes for Pro-style devices. Firmware and bootloader structures are `struct pcan_usb_pro_blinfo` and `struct pcan_usb_pro_fwinfo`. Command and RX/TX record structures include bit timing, bus activity, silent mode, filter, timestamp enable, device ID, LED, RX message, RX status, RX timestamp, and TX message records. `union pcan_usb_pro_rec` provides a common view for decoder dispatch. Prototypes export `pcan_usb_pro_probe()`, `pcan_usb_pro_send_req()`, and `pcan_usb_pro_restart_complete()`.

Control flow: implementation files use these constants to build bulk command record lists and parse incoming record lists. `pcan_usb_pro.c` uses all classic Pro records directly. `pcan_usb_fd.c` uses the shared endpoint defaults, vendor request helper, driver-loaded function request, firmware info request identifiers, and restart completion callback for FD-family devices.

State and persistence: the header stores no runtime state, but defines layouts for persistent or semi-persistent device state: firmware/bootloader versions, serial number halves, hardware type/revision, channel device IDs, LED mode, timestamp enable mode, bus activity, and filter state.

Dependencies and integration points: it depends on kernel integer/endian types and packed layout semantics. It is included by PEAK protocol implementations and implicitly participates in the shared adapter contract from `pcan_usb_core.h`.

Risks: packed record layout and endianness must match firmware exactly. Record IDs are used as direct indexes into record-size tables, so changes require synchronized updates in implementation files. Endpoint constants double as defaults for devices that do not return extended endpoint metadata. The Pro and FD families share some constants but not all message formats, so callers must not assume every `pcan_usb_pro_*` record applies to FD-family uCAN traffic.

Test signals: build coverage for both classic Pro and FD-family files, firmware info reads through vendor requests, driver-loaded notifications, endpoint validation, channel-ID records, LED records, and decode paths that use `union pcan_usb_pro_rec` sizes.

## sources/distributed-fs/ceph-client/drivers/net/can/usb/ucan.c

Purpose: this is the SocketCAN USB driver for Theobroma Systems UCAN protocol version 3 devices, including Mule and Seal variants. It discovers protocol/device capabilities through vendor control transfers, registers a classic CAN netdev, configures bit timing and control modes, manages bulk IN/OUT URBs, decodes received CAN and error frames, handles device TX-complete notifications, and supports bus-off restart.

Important APIs, types, and functions: protocol structures include control payload records for start, bit timing, device info, protocol version, firmware string, outbound CAN messages, inbound CAN/RX/TX-complete messages, and TX complete entries. `struct ucan_priv` embeds `can_priv` and tracks USB device/netdev, endpoint addresses and packet size, USB anchors, control buffer, parsed device info, echo skb lock, context lock, available TX URB count, and a dynamically sized context array based on firmware-reported FIFO depth. Key paths are `ucan_parse_device_info()`, `ucan_ctrl_command_out()`, `ucan_handle_error_frame()`, `ucan_rx_can_msg()`, `ucan_tx_complete_msg()`, `ucan_read_bulk_callback()`, `ucan_write_bulk_callback()`, RX URB prepare/submit helpers, `ucan_open()`, `ucan_prepare_tx_urb()`, `ucan_start_xmit()`, `ucan_close()`, `ucan_set_bittiming()`, `ucan_set_mode()`, `ucan_probe()`, and `ucan_disconnect()`.

Control flow: USB probe validates the current interface and exactly two bulk endpoints, checks endpoint packet sizes, allocates a devm control buffer, reads protocol version, rejects anything outside version 3, reads device info, validates nonzero TX FIFO depth, allocates a CAN netdev with echo slots equal to that FIFO depth, initializes locks/anchors/netdev operations, parses bit timing and supported ctrlmodes from firmware, resets the device, registers the CAN netdev, and logs the firmware string. Opening allocates the TX context array, prepares RX URBs but does not submit them yet, converts SocketCAN ctrlmode into UCAN start mode while always enabling bus error reports, starts the device over control pipe, opens CAN core state, submits all RX URBs atomically, sets `ERROR_ACTIVE`, and starts the queue. RX callbacks walk multiple 4-byte-aligned inbound messages, dispatch received CAN frames or TX-complete batches, filter error frames when berr reporting is disabled unless the bus state changed, and resubmit the URB. TX allocates a context under lock, stops the queue when FIFO contexts are exhausted, builds a coherent outbound URB with echo index in the subtype, stores the skb in echo state, submits the URB, and waits for an IN endpoint TX-complete message to release context and update stats. Close kills TX/RX anchors, sends STOP and RESET, stops the queue, releases contexts, and closes CAN core state.

State and persistence: runtime state is mostly in `ucan_priv`: parsed device capabilities, endpoint metadata, active context allocation, available FIFO slots, and CAN state. Firmware-reported capabilities define CAN clock, bit timing bounds, supported ctrlmodes, and TX FIFO depth for the lifetime of the device. There is no persistent user configuration written to the device; bit timing, start mode, restart, stop, and reset are volatile control commands.

Dependencies and integration points: the driver uses Linux USB control and bulk APIs, coherent DMA buffers, SocketCAN `alloc_candev()`, echo skb helpers, `open_candev()`/`close_candev()`, CAN error frame semantics, CAN bit timing configuration, netdevice operations, ethtool timestamp info, and USB IDs for Theobroma devices `0x2294:0x425a` and `0x2294:0x425b`.

Risks: `ucan_start_xmit()` computes `echo_index = context - up->context_array` before checking whether `context` is NULL, so low-memory or impossible allocation failures around context availability deserve scrutiny. RX and TX completion messages are firmware-controlled and require strict length and echo-index validation. The driver starts the USB device before `open_candev()` and then must stop/reset on later failures. Error filtering deliberately asks firmware for all berr reports and drops non-state-changing errors in software when berr reporting is disabled. All TX completion accounting depends on the device sending valid TX-complete messages after successful OUT URBs; USB write failure has a separate cleanup path because no completion will arrive from firmware.

Test signals: probe with supported and unsupported protocol versions, malformed endpoint descriptors, firmware-reported bit timing limits and ctrlmodes, open failure cleanup after START, all-or-nothing RX URB submission, RX of normal/RTR/error frames, berr-reporting on/off filtering, bus-off and `ip link ... restart` control command, TX queue stop/wake at FIFO depth, TX-complete success and failure flags, invalid echo indexes, unplug while URBs are active, and repeated open/close cycles.

## sources/distributed-fs/ceph-client/drivers/net/can/usb/usb_8dev.c

Purpose: this file implements the SocketCAN USB driver for the "8 devices" USB2CAN converter. It speaks a fixed 16-byte command protocol and fixed-size data frame protocol over separate command/data bulk endpoints, registers a classic CAN netdev, configures bit timing and modes, manages RX/TX URBs, decodes device status/error frames, and exposes berr counters.

Important APIs, types, and functions: `struct usb_8dev_priv` embeds `can_priv` and tracks USB/netdev pointers, active TX URB count, TX contexts, RX/TX anchors, cached berr counters, command buffer, command mutex, and RX DMA buffers. Protocol structs are `usb_8dev_tx_msg`, `usb_8dev_rx_msg`, and `usb_8dev_cmd_msg`. Control helpers include `usb_8dev_send_cmd_msg()`, `usb_8dev_wait_cmd_msg()`, `usb_8dev_send_cmd()`, `usb_8dev_cmd_open()`, `usb_8dev_cmd_close()`, and `usb_8dev_cmd_version()`. CAN paths include `usb_8dev_set_mode()`, `usb_8dev_rx_err_msg()`, `usb_8dev_rx_can_msg()`, `usb_8dev_read_bulk_callback()`, `usb_8dev_write_bulk_callback()`, `usb_8dev_start_xmit()`, `usb_8dev_get_berr_counter()`, `usb_8dev_start()`, `usb_8dev_open()`, `unlink_all_urbs()`, `usb_8dev_close()`, `usb_8dev_probe()`, and `usb_8dev_disconnect()`.

Control flow: probe checks the product string to avoid binding unrelated devices with the same vendor/product ID, allocates a CAN netdev with 20 echo slots, fills CAN clock and bit timing constants, enables loopback/listen-only/one-shot/classic DLC support, initializes anchors, TX contexts, command mutex, and devm command buffer, registers the CAN device, and reads/logs firmware and hardware version. Opening calls `open_candev()`, starts RX polling by allocating and submitting up to 20 coherent RX URBs, sends the OPEN command with manual bit timing and ctrlmode flags, marks state active, and starts the net queue. RX completion parses one or more fixed-size `usb_8dev_rx_msg` records, sends CAN records to SocketCAN, converts status/error records to CAN error skbs, and resubmits the URB. TX builds a fixed `usb_8dev_tx_msg`, finds a free echo context, anchors/submits a coherent bulk URB, stores echo skb, increments active URB count, and stops the queue when all contexts are used. Write completion frees coherent memory, releases the echo skb, updates TX stats, resets the context, and wakes the queue. Close sends the CLOSE command, marks stopped, stops the queue, kills/free RX and TX URBs, and closes CAN core state.

State and persistence: state is in the private object and device firmware. The driver caches latest TX/RX error counters from status frames for `do_get_berr_counter`. `active_tx_urbs` and `tx_contexts[].echo_index` implement in-flight TX tracking. RX coherent buffer addresses are stored for cleanup after anchored URBs are killed. Control mode and bit timing are sent on open and restart; no persistent configuration is written.

Dependencies and integration points: the file uses Linux USB bulk APIs and coherent DMA buffers, SocketCAN classic CAN and error helpers, CAN echo skb handling, netdevice operations, ethtool timestamp fallback, mutex serialization for command transfers, and USB ID `0483:1234` guarded by an iProduct string comparison.

Risks: the data protocol uses start/end marker bytes but RX parsing only iterates fixed struct sizes and does not explicitly validate markers for every data frame. `usb_8dev_write_bulk_callback()` increments TX packet stats even when `urb->status` is nonzero, which may be protocol-expected completion accounting or a possible overcount. Probe registers the CAN device before reading version; version failure unregisters through `unregister_netdev()`, while normal disconnect also calls `unlink_all_urbs()`. RX buffer cleanup frees all array entries; repeated close/unplug paths need to avoid stale pointers. Command exchange depends on a single shared command buffer and mutex, so command responses must match the expected 16-byte framing and success code.

Test signals: probe only when the product string is "USB2CAN converter", version command logs firmware/hardware, open sends manual timing with loopback/listen-only/one-shot/status-frame flags, normal and RTR classic CAN TX/RX succeeds, RX overrun/warning/passive/bus-off/protocol error frames update SocketCAN stats and berr counters, TX queue stops at 20 active URBs and wakes on completion, bus-off restart sends OPEN again, close kills all URBs and sends CLOSE, and unplug during traffic cleans anchors and candev without use-after-free.

## sources/distributed-fs/ceph-client/drivers/net/can/vcan.c

Purpose: this file implements the virtual CAN network interface type `vcan`. It provides a software-only CAN device for local testing, supports classic CAN, CAN FD, and CAN XL MTUs/capability reporting, and can optionally perform driver-level echo for testing CAN core echo behavior.

Important APIs, types, and functions: the module parameter `echo` controls whether the driver itself creates echo skbs. `vcan_tx()` is the transmit path, `vcan_rx()` reinjects locally echoed skbs, `vcan_change_mtu()` restricts MTU changes to valid CAN/CAN FD/CAN XL sizes while the device is down, `vcan_set_cap_info()` maps MTU to CAN capability flags, `vcan_setup()` initializes netdev shape and CAN multi-length private state, and `vcan_link_ops` registers the RTNL link kind.

Control flow: module init logs the virtual driver and registers `rtnl_link_ops` for `kind = "vcan"`. Creating a vcan link allocates `struct can_ml_priv` private data and calls setup. Setup assigns `ARPHRD_CAN`, default `CANXL_MTU`, no hardware header/address, zero TX queue length, `IFF_NOARP`, CAN ML private pointer, capability flags, optional `IFF_ECHO`, netdev operations, ethtool ops, and `needs_free_netdev`. TX validates CAN skb shape, updates TX stats, timestamps the skb, detects whether the CAN core marked it as loopback, and either consumes it with core echo accounting or, when `echo=1`, clones/creates an echo skb and reinjects it through `vcan_rx()`. MTU changes are rejected while up and accepted only for classic CAN, CAN FD, or valid CAN XL MTUs. Module exit unregisters the RTNL link type.

State and persistence: there is no hardware or persistent device state. Per-device state is only the CAN ML private area and netdev fields. The module-level `echo` parameter is read-only at runtime via permissions `0444` and affects all vcan devices created under the module.

Dependencies and integration points: the driver integrates with RTNL link creation (`ip link add type vcan`), netdevice TX hooks, SocketCAN skb validation and data-length helpers, CAN ML private helpers, ethtool timestamp fallback, and packet loopback conventions from the CAN core.

Risks: echo behavior changes accounting paths: with default `echo=0`, the CAN core already handled loopback and the driver only increments RX counters for looped packets; with `echo=1`, the driver performs standard echo skb creation itself. MTU changes while up are blocked to avoid capability changes under active traffic. Defaulting to CAN XL MTU means userspace should inspect capability flags if it expects classic-only behavior.

Test signals: create/delete vcan links through RTNL, send classic CAN/CAN FD/CAN XL skbs at matching MTUs, verify invalid skb drops and invalid MTUs return `-EINVAL`, verify MTU changes return `-EBUSY` while up, compare RX/TX stats with `echo=0` and `echo=1`, confirm timestamping reports through ethtool, and confirm module unload unregisters the link kind.

## sources/distributed-fs/ceph-client/drivers/net/can/vxcan.c

Purpose: this file implements the virtual CAN tunnel link type `vxcan`, modeled after veth for CAN. It creates paired CAN netdevices, optionally across network namespaces, and forwards CAN skbs transmitted on one end to the peer while supporting classic CAN, CAN FD, and CAN XL MTUs/capability reporting.

Important APIs, types, and functions: `struct vxcan_priv` stores an RCU-protected peer netdev pointer. `vxcan_xmit()` forwards skbs to the peer and resets CAN gateway hop state. `vxcan_open()`/`vxcan_close()` manage carrier state based on peer availability. `vxcan_get_iflink()` reports peer ifindex. `vxcan_change_mtu()` and `vxcan_set_cap_info()` mirror vcan MTU/capability behavior. `vxcan_setup()` initializes netdev fields and CAN ML private data. `vxcan_newlink()` creates and registers the peer and local devices from RTNL attributes. `vxcan_dellink()` unregisters both ends and clears peer pointers. `vxcan_get_link_net()` reports the peer namespace for link display semantics, and `vxcan_link_ops` wires the RTNL API.

Control flow: module init registers the `vxcan` RTNL link kind. `vxcan_newlink()` parses optional `VXCAN_INFO_PEER` nested attributes, chooses peer name and name assignment type, creates the peer in the requested peer net namespace, optionally sets peer ifindex, registers and configures the peer, then names/registers the requested device, turns carrier off on both ends, and cross-links peer pointers with RCU assignment. TX validates the CAN skb, looks up the peer under RCU, drops and counts `tx_dropped` if no peer exists, timestamps the original skb, clones it, consumes the original on clone success, forces a separate CAN skb extension with `skb_ext_add()`, resets `can_gw_hops`, assigns packet type/device/checksum fields for receive, and calls `netif_rx()`. On successful receive, source TX stats and peer RX stats are updated. Deleting either end clears both RCU peer pointers and queues both netdevices for unregister.

State and persistence: runtime state is the RCU peer pointer in each device and carrier state. There is no persistent hardware state. Netdev private memory includes aligned `vxcan_priv` followed by `can_ml_priv`, and peer namespace/name/ifindex are established at link creation.

Dependencies and integration points: the driver integrates with RTNL pair creation, nested netlink attributes from `linux/can/vxcan.h`, network namespaces, RCU pointer access, netdevice carrier and iflink APIs, SocketCAN skb validation/data-length helpers, CAN gateway skb extension state, CAN ML private helpers, and ethtool timestamp fallback.

Risks: `vxcan_xmit()` depends on clone and skb extension allocation in atomic context; allocation failures drop silently except for lack of stat increments in some clone/extension failure cases. Peer pointers must remain RCU-safe across namespace teardown and paired unregister. The TX path intentionally resets `can_gw_hops` when crossing the tunnel; tests should cover CAN gateway loop-prevention behavior. As with vcan, MTU/capability changes are blocked while running and default to CAN XL MTU.

Test signals: create vxcan pairs with and without explicit peer attributes, create peers in another network namespace, verify `iflink` and `get_link_net` behavior, bring both ends up and observe carrier on/off transitions, send classic CAN/CAN FD/CAN XL frames across the pair, confirm stats on both ends, verify CAN gateway hop counter reset, reject invalid MTUs and MTU changes while up, delete either end and confirm both peers unregister cleanly, and exercise transmit after peer removal to check drop accounting.
