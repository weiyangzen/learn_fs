## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/dev-support/jdiff/Apache_Hadoop_HDFS_3.4.0.xml

Purpose: JDiff XML snapshot for the public annotated API surface of the `hadoop-hdfs` module at Apache Hadoop HDFS 3.4.0. It is generated by the JDiff Javadoc doclet using Hadoop's public-annotation-aware doclet, and is consumed by API compatibility/report generation rather than by runtime HDFS code. The root `<api>` element identifies the API name as `Apache Hadoop HDFS 3.4.0`, uses `jdversion="1.0.9"`, points at `api.xsd`, and records the long generation classpath and sourcepath in a command-line comment. The export describes 47 packages, 9 classes, 3 interfaces, 58 methods, 13 constructors, 9 fields, and 33 documentation blocks.

Important APIs and types: the file contains package declarations for the broad HDFS module namespace but only a limited set of member-bearing public types. `org.apache.hadoop.hdfs.protocol.FSLimitException` is an abstract public quota-limit exception extending `QuotaExceededException` with protected constructors for no-arg, message, and quota/count forms plus a protected static final `serialVersionUID`. `org.apache.hadoop.hdfs.qjournal.server.JournalNodeMXBean` exposes JMX methods for journal status, host/port, cluster IDs, version, JournalNode start time, and storage information. `org.apache.hadoop.hdfs.server.aliasmap.InMemoryAliasMap` implements `InMemoryAliasMapProtocol` and `Configurable`, with configuration accessors, static `init`, `list`, `read`, `write`, block-pool lookup, `close`, protobuf conversion helpers, and bootstrap archive transfer/extraction helpers.

Important provided-storage APIs: `org.apache.hadoop.hdfs.server.common.BlockAlias` defines `getBlock()`, and `FileRegion` implements it as a `(Path, offset, length)` description of provided blocks with constructors from block ID/path offsets or from `Block` plus `ProvidedStorageLocation`. `org.apache.hadoop.hdfs.server.common.blockaliasmap.BlockAliasMap` is an abstract read/write/refresh/close contract for provided-block maps. `LevelDBFileRegionAliasMap` and `TextFileRegionAliasMap` implement it as `Configurable` classes; both expose reader/writer creation, refresh, close, and public static final SLF4J `LOG` fields, while the text implementation also exposes `blockPoolIDFromFileName(Path)` and `fileNameFromBlockPoolID(String)`.

Important NameNode APIs: `AuditLogger` defines `initialize(Configuration)` and the critical-section `logAuditEvent` method. `HdfsAuditLogger` extends that contract with overloads that add `CallerContext`, `UserGroupInformation`, and `DelegationTokenSecretManager` for token-tracking audit metadata while preserving a simpler seven-argument method. `DefaultAuditLogger` is abstract and exposes `initialize`, `logAuditMessage`, audit-event overloads, and protected audit formatting/configuration state such as `STRING_BUILDER`, caller-context limits, token tracking, and debug command set. `INodeAttributeProvider` is abstract and exposes NameNode lifecycle hooks, path/component attribute lookup overloads, and `getExternalAccessControlEnforcer` for substituting permission checks.

Control flow: there is no executable runtime control flow in this XML. The structural flow is document-order API enumeration: root metadata, package docs, package declarations, member-bearing type blocks, methods/constructors/fields, optional CDATA docs, and close tags. Consumers parse this as a static API model and compare it to other JDiff XML snapshots. The HDFS runtime flow described indirectly by the API includes JournalNode JMX polling, alias-map initialization/read/write/bootstrap transfer, block-alias map reader/writer construction, audit logger initialization and per-operation logging, and NameNode attribute/enforcer lookup.

State and persistence behavior: the XML itself is a generated, persisted compatibility artifact. Runtime state is only represented through exposed APIs: JournalNode status and storage info reflect journal directory and cluster state; `InMemoryAliasMap` and `BlockAliasMap` APIs represent persistent mappings between HDFS blocks and external/provided storage locations, including LevelDB and text-file storage; bootstrap transfer serializes alias-map state as a tar.gz archive for standby NameNodes; audit loggers hold protected configuration and thread-local formatting state; `INodeAttributeProvider` instances participate in NameNode startup/shutdown lifecycle without declaring their own persistence format here.

Dependencies and integration points: the generation command embeds dependencies on `hadoop-hdfs`, `hadoop-common`, `hadoop-hdfs-client`, Hadoop annotations, JDiff, servlet APIs, protobuf, LevelDB JNI, SLF4J, Netty, Jetty, Curator/ZooKeeper, Kerby, Jackson, Jersey, and many transitive build artifacts. The described APIs integrate with HDFS quota exceptions, QJM JournalNode JMX, provided storage alias maps, Hadoop `Configuration`, servlet responses, protobuf serialization, NameNode audit logging, security token management, `CallerContext`, `UserGroupInformation`, and pluggable NameNode authorization/attribute extension points.

Risks: because this file is generated, stale or incorrectly generated XML can produce misleading API compatibility reports. The 3.4.0 snapshot erases many generic type parameters as raw `java.util.List`, `java.util.Optional`, `ThreadLocal`, and `Set`, so compatibility comparisons can miss or overstate type-signature precision. Public visibility of implementation-oriented alias-map and audit fields/methods increases compatibility constraints. Methods that represent on-disk or serialized state, such as alias-map protobuf conversion and bootstrap archive transfer, are especially sensitive to signature drift. The command-line comment exposes build-environment paths and dependency versions, which is useful for traceability but can make diffs noisy across build hosts.

Test signals: this artifact is normally validated by XML well-formedness, schema compatibility with `api.xsd`, JDiff report generation against neighboring API snapshots, and release/build checks that ensure public annotated APIs are present. Runtime behavior is not tested by this XML directly; indirect coverage should come from HDFS alias-map tests, JournalNode JMX tests, audit logging tests, NameNode authorization extension tests, and API compatibility diffs against later files such as the 3.5.0 snapshot.

## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/dev-support/jdiff/Apache_Hadoop_HDFS_3.5.0.xml

Purpose: JDiff XML snapshot for the public annotated API surface of the `hadoop-hdfs` module at Apache Hadoop HDFS 3.5.0. The root `<api>` element identifies `Apache Hadoop HDFS 3.5.0`, uses `jdversion="1.1.1"`, references `api.xsd`, and records a much shorter generation command than the 3.4.0 artifact. The export is substantially broader than the 3.4.0 file: it describes 49 packages, 42 classes, 3 interfaces, 171 methods, 13 constructors, 9 fields, and 77 documentation blocks. Much of the increase comes from public nested enum types and package documentation now represented in the generated XML.

Important unchanged APIs: the file keeps the 3.4.0 core surface for `FSLimitException`, `JournalNodeMXBean`, `InMemoryAliasMap`, `BlockAlias`, `FileRegion`, `BlockAliasMap`, `LevelDBFileRegionAliasMap`, `TextFileRegionAliasMap`, `AuditLogger`, `DefaultAuditLogger`, `HdfsAuditLogger`, and `INodeAttributeProvider`. Several signatures are more precise than in 3.4.0: `JournalNodeMXBean.getClusterIds()` and `getStorageInfos()` return `java.util.List<java.lang.String>`, `InMemoryAliasMap.list` takes `Optional<Block>`, `read` returns `Optional<ProvidedStorageLocation>`, `BlockAliasMap` is modeled as `BlockAliasMap<T>`, and the concrete alias-map implementations bind `T` to `FileRegion`. `DefaultAuditLogger.STRING_BUILDER` and `debugCmdSet` also preserve their generic types.

Important added layout and state enums: `org.apache.hadoop.hdfs.protocol.LayoutVersion.Feature`, `org.apache.hadoop.hdfs.server.datanode.DataNodeLayoutVersion.Feature`, and `org.apache.hadoop.hdfs.server.namenode.NameNodeLayoutVersion.Feature` are now included, each implementing `LayoutVersion.LayoutFeature` and exposing `values`, `valueOf`, and `getInfo`. These document layout-version feature evolution and rolling-upgrade/downgrade compatibility expectations. `HdfsServerConstants` nested enums exposed under `org.apache.hadoop.hdfs.server.common` include `BlockUCState`, `NamenodeRole`, `NodeType`, `ReplicaState`, `RollingUpgradeStartupOption`, and `StartupOption`; `ReplicaState` includes binary `read(DataInput)` and `write(DataOutput)`, and `StartupOption` includes cluster ID, rolling upgrade, recovery, force, and interactive format accessors. `Storage.StorageState` also appears as a public enum.

Important operational enums and helpers: the balancer package exposes `ExitStatus` with `getExitCode`. Block management exposes `NodeNotChosenReason`, corrupt-replica `Reason`, `StoredReplicaState`, and cached-block-list `Type`. DataNode APIs expose file IO `OPERATION`; volume storage exposes `FsVolumeImpl.BlockDirFilter` implementing `FilenameFilter`; disk balancer exposes `DiskBalancerException.Result`; server protocol exposes `ReceivedDeletedBlockInfo.BlockStatus` with integer code conversion and `NamespaceInfo.Capability` with `getMask`; utility exposes `RwLockMode` for fine-grained locking.

Important NameNode persistence/format APIs: the NameNode package adds `AclEntryStatusFormat`, `Content`, `DirOp`, `NameNodeDirType`, `NameNodeFile`, `OperationCategory`, `Quota`, `SectionName`, `SerialNumberManager`, `TransferResult`, and `XAttrFormat`. `AclEntryStatusFormat` packs ACL entries into 32-bit integers and explicitly notes that the format is both in-memory and on-disk. `XAttrFormat` similarly packs xattrs and warns about compatibility. `NameNodeDirType` implements `Storage.StorageDirType` and distinguishes image, edits, and combined storage directories. `NameNodeFile` names fsimage-related files. `SectionName` orders protobuf fsimage section loading and has `fromString`. `SerialNumberManager` manages string-to-serial-number tables and can create or expose string tables. `Quota.isViolated(long quota, long usage)` captures quota violation semantics.

Package documentation and integration context: 3.5.0 adds CDATA docs for data transfer, SASL, protocolPB, balancer, alias map, DataNode HTTP, disk balancer and its command/connectors/datamodel/planner packages, mover, NameNode fine-grained locking, visitor, and SPS metrics. These docs identify major subsystem roles: HDFS data transfer protocol, SASL wrapping, block balancing across DataNodes or volumes, provided-storage alias mapping, disk-balancer cluster modeling and planning, tiered-storage migration, namespace visitor traversal, and external SPS metrics exposure.

Control flow: like 3.4.0, the XML has no executable runtime control flow. Its effective flow is static model traversal by JDiff consumers: package docs, type blocks, member declarations, doc CDATA, and closing tags. The APIs described imply several runtime flows: layout-version feature checks during upgrades; startup option parsing and recovery context creation; replica-state binary serialization/deserialization; NameNode fsimage section ordering; ACL/xattr bit packing; serial number table lookup; alias-map reader/writer use and bootstrap transfer; audit-event dispatch; and operational enum conversion from strings or integer wire codes.

State and persistence behavior: this generated XML persists the 3.5.0 public API contract. The represented APIs include many state-bearing or persistence-sensitive contracts: layout version features affect upgrade compatibility; `ReplicaState.read/write`, `AclEntryStatusFormat`, and `XAttrFormat` encode durable/in-memory binary forms; `SectionName` controls fsimage loading order; `NameNodeDirType` and `NameNodeFile` identify NameNode storage contents; `SerialNumberManager` controls compact identity tables; `BlockStatus.getCode/fromCode` maps protocol status to numeric codes; alias maps persist provided-block mappings through LevelDB, text, protobuf bytes, and bootstrap archives; audit loggers keep configuration and thread-local state; JournalNode JMX exposes journal storage state.

Dependencies and integration points: the source integrates with JDiff/Javadoc tooling, `api.xsd`, Hadoop public annotation filtering, and downstream API-diff report generation. The described HDFS APIs touch the HDFS protocol, QJM, NameNode, DataNode, block management, balancer, disk balancer, mover, SPS metrics, provided storage, servlet transfer, protobuf, Hadoop configuration, Java IO, JMX, security tokens, caller context, filesystem ACL/xattr types, storage policies, and wire/protobuf fsimage formats. Compared with 3.4.0, the snapshot itself also depends on a newer JDiff version and a generation setup that preserves generic signatures more accurately.

Risks: the widened generated surface may expose nested enums or implementation details as compatibility commitments even when they are primarily internal to HDFS subsystems. Any change to the public enum names, ordinal-sensitive serialization assumptions, integer codes, bit-packing formats, fsimage section ordering, or startup option parsing can have upgrade, downgrade, or wire-compatibility impact. The presence of on-disk warnings in `AclEntryStatusFormat` and `XAttrFormat` makes those especially high risk. Generic signature changes relative to 3.4.0 may show as API differences even when source compatibility is unchanged, so compatibility reports must distinguish doclet precision changes from intentional API changes. Package docs copied as license text for some packages may be noisy and less useful for semantic API review.

Test signals: expected validation includes XML well-formedness, schema compatibility, successful JDiff comparison against 3.4.0 and future snapshots, and release checks that use the generated API files. Subsystem tests should cover the behavioral contracts indirectly represented here: rolling upgrade layout-version compatibility, NameNode startup options and storage directory handling, fsimage ACL/xattr and section serialization, replica-state wire IO, alias-map persistence/bootstrap, JournalNode JMX, audit logging, balancer/disk-balancer exit/result handling, DataNode block directory filtering, and server protocol status/capability code mapping.
