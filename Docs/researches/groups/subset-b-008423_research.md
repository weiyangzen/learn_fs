# sources/storage-engines/foundationdb/contrib/sqlite/sqlite3ext.h

Purpose: This header is the loadable-extension ABI shim for the bundled SQLite copy. Extension shared libraries include it instead of `sqlite3.h` so their calls to SQLite APIs are redirected through a `sqlite3_api_routines` function table supplied by the host SQLite library at extension initialization time.

Important APIs, types, and functions: The core type is `sqlite3_api_routines`, a struct containing function pointers for the public SQLite API surface available to extensions. It covers statement binding, stepping, reset/finalize, column accessors, value/result APIs, function and collation registration, virtual table module registration, hooks, mutexes, BLOB I/O, backup, WAL, status, configuration, logging, VFS registration, memory allocation, and version/compile-option introspection. The macros below the struct remap `sqlite3_*` names to `sqlite3_api->...` fields when `SQLITE_CORE` is not defined. `SQLITE_EXTENSION_INIT1` declares the per-extension `sqlite3_api` pointer and `SQLITE_EXTENSION_INIT2(v)` initializes it from the host.

Control flow: Extension code is compiled with calls such as `sqlite3_create_function` expanded into indirect calls through `sqlite3_api`. At load time, SQLite passes a populated API table into the extension entry point; the extension calls `SQLITE_EXTENSION_INIT2` before invoking other SQLite APIs. In core SQLite builds, `SQLITE_CORE` suppresses the remapping so the main library can include the struct definition without redirecting its own calls.

State and persistence behavior: This file owns no database state and performs no I/O. Its state is a process-local global pointer per extension translation unit. Persistence effects occur only through the functions reached via the table, such as statement execution, BLOB writes, backup, WAL checkpointing, or VFS operations. ABI persistence is the main concern: comments explicitly require new entries to be appended to the end of `sqlite3_api_routines` to keep old extensions and old SQLite libraries interoperable.

Dependencies and integration points: It includes `sqlite3.h` for all public SQLite type definitions, is consumed by loadable extensions, and is also included by SQLite's extension-loader implementation to define the API table shape. It integrates with extension entry-point conventions and compile-time feature gates such as `SQLITE_CORE` and `SQLITE_OMIT_DEPRECATED`.

Risks: Reordering or inserting function pointers in the middle of `sqlite3_api_routines` is an ABI break. The header contains duplicate macro definitions for `sqlite3_prepare_v2` and `sqlite3_prepare16_v2`, which is harmless but worth preserving deliberately if this is a vendored snapshot. Extensions can crash if they call redirected APIs before `SQLITE_EXTENSION_INIT2`. Builds that define `SQLITE_CORE` accidentally for an extension would bypass the indirection and fail to link or bind against the intended host API. Deprecated entries are conditionally exposed, so extension code must match the compile options of the target SQLite.

Test signals: Useful checks are compiling a minimal loadable extension that calls `SQLITE_EXTENSION_INIT2`, registers a scalar function, and uses redirected memory/result APIs; loading it into the bundled SQLite; ABI/table-order comparison against the matching `loadext.c` or amalgamation; tests with `SQLITE_OMIT_DEPRECATED`; and smoke tests for virtual table, backup, and WAL APIs through extension code.

# sources/storage-engines/foundationdb/contrib/sqlite/sqliteInt.h

Purpose: This is the private internal interface header for FoundationDB's bundled SQLite copy. It centralizes compile-time portability setup, SQLite core typedefs, internal structs, flags, parser/query-planner state, memory and mutex declarations, varint helpers, global symbols, and a local copy of `struct Mem` for code that needs to allocate SQLite value cells outside the original SQLite implementation files.

Important APIs, types, and functions: The header defines low-level integer aliases (`i64`, `u64`, `u32`, `u16`, `u8`, etc.), pointer/integer cast macros, endianness macros, alignment helpers, `testcase`, `ALWAYS`, `NEVER`, and build defaults for threadsafety, memory status, temp-store, file format, recursive triggers, and large-file support. Major active structures include `BusyHandler`, `Db`, `Schema`, `Lookaside`, `FuncDefHash`, the public-but-internal `sqlite3` connection object, `KeyInfo`, `UnpackedRecord`, expression/query structs (`Expr`, `ExprList`, `SrcList`, `WherePlan`, `WhereLevel`, `WhereInfo`, `NameContext`, `Select`, `SelectDest`), trigger/codegen structs (`AutoincInfo`, `TriggerPrg`, `Parse`, `AuthContext`, `Trigger`, `TriggerStep`, `DbFixer`), `StrAccum`, `InitData`, `Sqlite3Config`, `Walker`, and `Mem`. Active prototypes include walker routines, corruption/misuse/cantopen breakpoint helpers, string comparison/length helpers, malloc and mutex initialization, varint encode/decode functions, `sqlite3ErrStr`, global symbol declarations, and memory-debug macros. A large amount of upstream SQLite declaration surface is present inside `#if 0` blocks, showing this fork keeps reference definitions while disabling many declarations for the trimmed integration.

Control flow: This header does not implement algorithms, but it defines the state passed through nearly every SQLite control path. A connection (`sqlite3`) owns database slots (`Db`), schema pointers, callbacks, mutexes, lookaside allocation state, active VDBEs, savepoints, virtual table transactions, limits, and error state. Parser execution builds a `Parse` object, tracks VDBE cursors/registers, schema-cookie checks, temporary register allocation, trigger context, variable bindings, authorization context, virtual table declaration state, and expression height. Name resolution traverses `NameContext`; tree rewrites and analysis use `Walker`; select planning and codegen use `Select`, `SrcList`, `WhereInfo`, and `SelectDest`; record comparison and cursor operations use `KeyInfo` and `UnpackedRecord`.

State and persistence behavior: The persistent database state is represented indirectly through `Db.pBt` b-tree handles and `Schema` metadata such as schema cookies, generation counters, table/index/trigger/foreign-key hashes, file format, encoding, flags, and cache size. The `sqlite3` object tracks transaction-visible behavior with autocommit, savepoint lists, deferred constraint count, write/active VDBE counts, last insert rowid, change counters, busy handlers, hooks, WAL callbacks, extension handles, and connection limits. Lookaside and global configuration state are process-local performance and allocator state. `Mem` carries transient SQL values but can own dynamically allocated string/blob buffers through `zMalloc` and `xDel`, so lifetime and destructor discipline are part of correctness.

Dependencies and integration points: It includes `sqliteLimit.h`, `sqlite3.h`, `hash.h`, and `btree.h`, and depends on many SQLite types supplied by those headers or by generated/amalgamated implementation files (`Vdbe`, `SubProgram`, `RowSet`, `Btree`, `sqlite3_mutex`, `sqlite3_value`, `sqlite3_module`, etc.). This is the shared contract between parser, VDBE, b-tree, schema, trigger, virtual table, memory, mutex, and utility code. The `SQLITE_OMIT_WSD` path integrates with platforms without writable static data, while global declarations expose `sqlite3Config`, `sqlite3GlobalFunctions`, opcode properties, ctype maps, and pending-byte state when not building the amalgamation.

Risks: Because this is an internal cross-module contract, layout drift is high risk: changing `sqlite3`, `Parse`, `Expr`, `Mem`, `Schema`, or planner structs can silently corrupt callers compiled against different assumptions. The disabled `#if 0` regions make this snapshot nonstandard; re-enabling or depending on declarations from those blocks can create mismatch with actual compiled implementation. `Expr` supports reduced/token-only allocation layouts, so callers must honor `EP_Reduced` and `EP_TokenOnly` before accessing trailing fields. Lookaside allocation cannot safely store shared schema objects, as noted in comments. Mutex and WSD macros can compile important synchronization or storage behavior away under feature flags. The local `Mem` copy is explicitly duplicated so external code can allocate values; it must remain ABI-compatible with the SQLite functions that manipulate it.

Test signals: High-value signals are full compile coverage of every SQLite translation unit using this header; ABI/layout checks for `Mem`, `sqlite3`, `Parse`, `Expr`, and `Schema` against the amalgamated SQLite source; parser and statement prepare tests exercising expressions, triggers, subqueries, virtual tables, savepoints, and limits; lookaside hit/miss and OOM tests; debug builds with assertions, `SQLITE_COVERAGE_TEST`, and `SQLITE_MEMDEBUG`; endian/alignment-sensitive record comparison tests; varint round-trip tests; and connection lifecycle tests covering open, error reporting, interrupt, hooks, extension handles, rollback, and close.

# sources/storage-engines/foundationdb/contrib/sqlite/sqliteLimit.h

Purpose: This header defines compile-time and default runtime limits for the bundled SQLite engine. It bounds maximum SQL/data sizes, schema shape, expression and trigger recursion, cache defaults, page sizes, database count, variable numbers, WAL autocheckpoint behavior, and related safety/performance parameters.

Important APIs, types, and functions: It provides preprocessor defaults for `SQLITE_MAX_LENGTH`, `SQLITE_MAX_COLUMN`, `SQLITE_MAX_SQL_LENGTH`, `SQLITE_MAX_EXPR_DEPTH`, `SQLITE_MAX_COMPOUND_SELECT`, `SQLITE_MAX_VDBE_OP`, `SQLITE_MAX_FUNCTION_ARG`, `SQLITE_DEFAULT_CACHE_SIZE`, `SQLITE_DEFAULT_TEMP_CACHE_SIZE`, `SQLITE_DEFAULT_WAL_AUTOCHECKPOINT`, `SQLITE_MAX_ATTACHED`, `SQLITE_MAX_VARIABLE_NUMBER`, `SQLITE_MAX_PAGE_SIZE`, `SQLITE_DEFAULT_PAGE_SIZE`, `SQLITE_MAX_DEFAULT_PAGE_SIZE`, `SQLITE_MAX_PAGE_COUNT`, `SQLITE_MAX_LIKE_PATTERN_LENGTH`, and `SQLITE_MAX_TRIGGER_DEPTH`. Values may generally be overridden by compiler definitions except for `SQLITE_MAX_PAGE_SIZE`, which is forcibly undefined and reset to `65536`.

Control flow: This file is included by `sqliteInt.h` before internal SQLite declarations are compiled. Downstream parser, VDBE, pager, b-tree, expression, trigger, and pragma code uses these constants to size arrays, validate input, set defaults, or cap runtime values exposed through APIs such as `sqlite3_limit` and pragmas.

State and persistence behavior: Most constants affect in-memory limits and input validation, but page-size and page-count values influence persistent database-file compatibility. `SQLITE_MAX_PAGE_SIZE` is locked to 65536 because a process using larger pages can create rollback/compatibility hazards for libraries compiled with smaller bounds. Default and maximum page size affect newly created databases and automatic page-size selection based on device characteristics. `SQLITE_MAX_PAGE_COUNT` is the default upper bound for `max_page_count` and can be changed at runtime.

Dependencies and integration points: It is consumed by `sqliteInt.h` and therefore by most internal SQLite code. The page-size constants integrate with pager and b-tree file-format logic. SQL length, variable, column, compound-select, function-arg, expression-depth, trigger-depth, and LIKE/GLOB pattern limits integrate with parser, code generator, expression walker, function registration/invocation, and trigger execution. Cache-size defaults feed pager/cache configuration. WAL autocheckpoint defaults integrate with WAL mode checkpoint scheduling.

Risks: Raising limits can increase memory use, parser/codegen recursion, VDBE size, and denial-of-service exposure. Lowering limits can break applications or tests that assume SQLite's normal defaults. `SQLITE_MAX_COLUMN` and `SQLITE_MAX_VARIABLE_NUMBER` affect structure field widths elsewhere, including `ynVar` selection in `sqliteInt.h`. Changing page-size bounds is compatibility-sensitive and explicitly guarded. `SQLITE_MAX_VDBE_OP` is documented as not currently enforced, so relying on it for resource control would be unsafe. The comment for compound SELECT contains an old spelling typo, but the behavior is clear.

Test signals: Run limit-boundary tests for maximum BLOB/TEXT length, SQL length, column count, compound SELECT terms, expression depth, function argument count, attached databases, host parameter numbers, LIKE/GLOB pattern length, trigger recursion depth, and page-size creation/opening. Include runtime `sqlite3_limit` and pragma tests, WAL autocheckpoint default checks, OOM/regression tests when limits are raised, and compatibility tests opening databases created with default and maximum page sizes.

# sources/storage-engines/foundationdb/contrib/stacktrace/CMakeLists.txt

Purpose: This CMake file builds the local stacktrace contribution as a static library from `stacktrace.amalgamation.cpp`, publishes the `include` directory, disables clang-tidy for this target, and wires sanitizer-specific compile definitions into the stacktrace implementation.

Important APIs, types, and functions: The build target is `stacktrace`. `add_library(stacktrace STATIC stacktrace.amalgamation.cpp)` creates the archive. `target_include_directories(stacktrace PUBLIC "${CMAKE_CURRENT_SOURCE_DIR}/include")` exposes headers such as `stacktrace/stacktrace.h` to downstream targets. Sanitizer options map `USE_ASAN` to `ADDRESS_SANITIZER`, `USE_MSAN` to `MEMORY_SANITIZER`, `USE_UBSAN` to `UNDEFINED_BEHAVIOR_SANITIZER`, and `USE_TSAN` to both `THREAD_SANITIZER` and `DYNAMIC_ANNOTATIONS_EXTERNAL_IMPL=1`.

Control flow: During CMake configure/generate, the file declares the static library and target properties. At compile time, exactly one sanitizer branch in the `if/elseif` chain contributes private definitions if the corresponding cache variable is enabled. Consumers link against `stacktrace` and inherit only the public include path, not the sanitizer defines.

State and persistence behavior: The file does not own runtime state or persistence. It controls how the stacktrace runtime is compiled. Sanitizer definitions can change code paths inside the amalgamated implementation, especially for signal-safety, unwind behavior, or annotations.

Dependencies and integration points: It depends on the source file `stacktrace.amalgamation.cpp` and the public include tree under `include`. It integrates with the repository's top-level sanitizer variables and any target linking to the static `stacktrace` library. The empty `CXX_CLANG_TIDY` target property opts the vendored/amalgamated code out of clang-tidy checks.

Risks: Sanitizer selection is mutually exclusive because of `elseif`; if multiple `USE_*SAN` variables are set, only the first in ASAN, MSAN, UBSAN, TSAN order applies. Private sanitizer definitions mean consumers do not see matching preprocessor flags unless supplied elsewhere. Disabling clang-tidy can hide modernization or warning issues in the amalgamation, though it is likely intentional for third-party code. If `stacktrace.amalgamation.cpp` is missing or the include path layout changes, the target breaks at configure/build time.

Test signals: Configure and build the target in normal, ASAN, MSAN, UBSAN, and TSAN builds; confirm `stacktrace/stacktrace.h` is reachable from a dependent target; inspect compile commands for the expected sanitizer definition; ensure clang-tidy is not run on this target; and run a small executable that links `stacktrace` and captures a stack trace in each supported build mode.

# sources/storage-engines/foundationdb/contrib/stacktrace/include/stacktrace/stacktrace.h

Purpose: This public C++ header exposes Abseil-style stack capture APIs under namespace `absl`. It provides async-signal-safe routines to collect program counters, optional frame sizes, signal-context-aware traces, and a hook for custom unwinding in specialized runtimes.

Important APIs, types, and functions: `GetStackFrames(void** result, int* sizes, int max_depth, int skip_count)` records PCs and frame sizes. `GetStackFramesWithContext(..., const void* uc, int* min_dropped_frames)` does the same with an optional signal `ucontext_t` pointer and reports a lower bound on omitted frames. `GetStackTrace(void** result, int max_depth, int skip_count)` records PCs only. `GetStackTraceWithContext` is the signal-context variant without sizes. `SetStackUnwinder` installs or clears a custom unwinder callback with the same argument shape as `GetStackFramesWithContext`, with `sizes` nullable depending on caller interest. `DefaultStackUnwinder` bypasses any custom unwinder and invokes the built-in behavior directly.

Control flow: Callers allocate result arrays, choose `max_depth`, and pass a `skip_count` that omits recent caller frames in addition to the stacktrace routine frame itself. Signal handlers use the `WithContext` variants, passing the third `sa_sigaction` argument when available. The implementation returns the number of frames stored, which may be less than available. If a custom unwinder is installed, the public capture functions call it; otherwise they use the built-in unwinder. `DefaultStackUnwinder` always chooses the built-in path.

State and persistence behavior: The header declares no persistent storage, but `SetStackUnwinder` controls process-global unwinder state in the implementation. The warning notes that other threads may still be using a custom unwinder after it is unregistered, so any state referenced by an old callback must remain valid. Stack captures are transient and write only into caller-provided buffers. `min_dropped_frames`, when non-null, receives a nonnegative lower bound that participates in the guarantee about real stack depth.

Dependencies and integration points: The API is C++ and lives in `namespace absl`, matching Abseil's debugging stacktrace interface. It is provided by the local `stacktrace` CMake target and its amalgamated implementation. It integrates with POSIX signal handling through opaque `ucontext_t` pointers, compiler/platform unwind support, sanitizer-specific build definitions, and any crash-reporting, logging, or diagnostic code that needs async-signal-safe stack capture.

Risks: Stack tracing is platform and build dependent; the header explicitly says it generally works only on configured platforms/builds. `result` must be non-null, and `sizes` must be non-null for the frame-size APIs. Custom unwinders must be async-signal-safe and must remain valid across concurrent unregister races. Passing an invalid signal context pointer can degrade or break unwinding. Frame sizes may be zero or negative when unknown, so callers must not treat them as reliable allocation sizes. Symbolization is not provided here; consumers only receive PCs.

Test signals: Unit tests should call PC-only and frame-size APIs from normal code, verify skip-count behavior with a known call chain, exercise `WithContext` with null context and from a signal handler where supported, install a custom unwinder and verify forwarding arguments and fallback after clearing it, call `DefaultStackUnwinder` while a custom unwinder is installed, test max-depth zero and small buffers, and run under sanitizer builds configured by the stacktrace CMake target.
