# sources/distributed-fs/ceph-client/drivers/dma/sh/rcar-dmac.c

Purpose: implements the Renesas R-Car Gen2/Gen3/Gen4 DMAC as a Linux DMAengine provider. It supports memory copy, slave scatter-gather, and cyclic slave transfers, exports channels through OF DMA translation, handles per-channel interrupts, and manages runtime PM for the controller.

Important APIs/types/functions: central types are `struct rcar_dmac`, `struct rcar_dmac_chan`, `struct rcar_dmac_desc`, `struct rcar_dmac_xfer_chunk`, and `struct rcar_dmac_hw_desc`. Public DMAengine hooks include `rcar_dmac_alloc_chan_resources`, `rcar_dmac_free_chan_resources`, `rcar_dmac_prep_dma_memcpy`, `rcar_dmac_prep_slave_sg`, `rcar_dmac_prep_dma_cyclic`, `rcar_dmac_device_config`, `rcar_dmac_chan_pause`, `rcar_dmac_chan_terminate_all`, `rcar_dmac_tx_status`, `rcar_dmac_issue_pending`, and `rcar_dmac_device_synchronize`. Hardware-facing helpers include `rcar_dmac_chan_start_xfer`, `rcar_dmac_fill_hwdesc`, `rcar_dmac_map_slave_addr`, `rcar_dmac_chan_halt`, `rcar_dmac_chan_reinit`, and `rcar_dmac_init`. IRQ handling is split between `rcar_dmac_isr_channel` and the threaded `rcar_dmac_isr_channel_thread`.

Control flow: probe reads OF match data for channel register layout, parses `dma-channels` and optional `dma-channel-mask`, maps global and per-channel register windows, disables channel 0 when an IOMMU group is present, initializes runtime PM, registers each channel IRQ, registers the OF DMA controller, then registers the DMAengine device. Channel resource allocation preallocates pages of software descriptors and transfer chunks and takes a runtime PM reference. Transfer preparation obtains one `rcar_dmac_desc`, builds a list of chunks from an SG list or cyclic periods, splits chunks at `DMATCR` and 4 GiB boundaries, configures CHCR fields for direction and bus width, and optionally creates a coherent hardware descriptor table when there are multiple chunks and the addresses do not cross high-address regions. `tx_submit` assigns a cookie and moves the descriptor to `pending`; `issue_pending` splices `pending` to `active` and starts the first descriptor if no transfer is running. The hard IRQ clears channel/error/transfer bits, handles address errors by clearing and reinitializing the channel, advances chunk or descriptor state, and wakes the thread when callbacks or done-list processing are needed. The IRQ thread completes cookies, invokes callbacks outside the lock, moves descriptors to `wait`, and recycles descriptors whose async_tx ack has arrived.

State and persistence: state is volatile driver and hardware state only. Each channel owns descriptor lists `free`, `pending`, `active`, `done`, `wait`, a `running` pointer, reusable chunk descriptors, descriptor pages, current slave source/destination settings, a cached resource mapping, and an allocated `mid_rid`. Hardware descriptor memory is per software descriptor and coherent DMA memory, resized page-aligned and released on channel free. The controller has a `modules` bitmap to prevent duplicate MID/RID allocations and a `channels_mask` to suppress unusable channels. No persistent on-disk state is used.

Dependencies and integration points: depends on Linux DMAengine, DMA mapping/resource mapping, OF DMA, platform IRQ/resources, runtime PM, spinlocks, and R-Car DMAC register definitions. It includes `../dmaengine.h` and registers compatibles `renesas,rcar-dmac`, `renesas,rcar-gen4-dmac`, and legacy `renesas,dmac-r8a779a0`. Slave clients request channels through one-cell OF DMA specs carrying MID/RID; `dma_slave_config` supplies FIFO addresses and bus widths. Integration with IOMMU is explicit through a 40-bit DMA mask and the channel-0 avoidance workaround.

Risks: descriptor/chunk list transitions are lock-sensitive and callbacks intentionally drop the channel lock; regressions can lose descriptors or double recycle wait-list entries. Hardware descriptor mode has address-region restrictions and an IOMMU erratum workaround that manually initializes `DMADAR`. Residue reads sample two registers with only three consistency attempts, so boundary races can produce warnings or approximate residue. `terminate_all` notes that an IRQ thread may still be running after halt. Runtime PM and channel setup interact in resource allocation/free; missed PM puts would keep the controller powered. OF channel count rejects `>= 32`, which is tied to the channel-clear mask width.

Test signals: useful signals are successful DT probe for both Gen2/Gen3 and Gen4 register layouts, `dmatest` memcpy with multi-chunk lengths, slave SG with multiple periods, cyclic audio-style callbacks, residue queries during and after descriptor-mode transfers, pause/terminate/reissue while IRQs fire, runtime suspend/resume, IOMMU-mapped transfers, and address-error IRQ recovery. Static checks should cover list manipulation, coherent descriptor allocation failures, and 64-bit DMA address boundary splitting.

# sources/distributed-fs/ceph-client/drivers/dma/sh/rz-dmac.c

Purpose: implements the Renesas RZ/G2L, RZ/V2H, and RZ/T2H DMAC as a DMAengine provider using hardware link-mode descriptors. It supports memcpy and slave SG transfers, optional ICU request-number programming for newer SoCs, pause/resume, residue reporting, and per-channel threaded IRQ completion.

Important APIs/types/functions: key types are `struct rz_dmac`, `struct rz_dmac_chan`, `struct rz_dmac_desc`, `struct rz_lmdesc`, `struct rz_dmac_info`, and `struct rz_dmac_icu`. DMAengine hooks are `rz_dmac_alloc_chan_resources`, `rz_dmac_free_chan_resources`, `rz_dmac_prep_dma_memcpy`, `rz_dmac_prep_slave_sg`, `rz_dmac_config`, `rz_dmac_terminate_all`, `rz_dmac_issue_pending`, `rz_dmac_tx_status`, `rz_dmac_device_pause`, `rz_dmac_device_resume`, and `rz_dmac_device_synchronize`. Important internal helpers are `rz_lmdesc_setup`, `rz_dmac_prepare_desc_for_memcpy`, `rz_dmac_prepare_descs_for_slave_sg`, `rz_dmac_xfer_desc`, `rz_dmac_enable_hw`, `rz_dmac_disable_hw`, and `rz_dmac_set_dma_req_no`.

Control flow: probe selects SoC data from the compatible, parses `dma-channels` and optional `renesas,icu`, maps base registers and either DMARS extension registers or ICU integration, requests the optional error IRQ and each channel IRQ, deasserts reset, creates one coherent ring of 64 link-mode descriptors per channel, registers OF DMA translation, initializes DMAengine hooks, writes default common-channel control, and registers the engine. Channel resource allocation preallocates up to 16 `rz_dmac_desc` objects into `ld_free`. Prep functions move a descriptor from `ld_free` to `ld_queue`, fill source/destination/length/SG metadata, and hand it to virt-dma. `issue_pending` marks virt-dma descriptors issued, sets `channel->desc`, converts the queued software descriptor into link-mode descriptor entries, writes request mapping through DMARS or ICU, enables hardware, and moves it to `ld_active`. The hard IRQ clears channel END or resets the channel on error; the threaded IRQ completes the active virt descriptor, returns its software object to `ld_free`, and immediately starts the next queued descriptor when present.

State and persistence: all state is in memory and hardware registers. Each channel stores its current software descriptor, fixed-size descriptor allocation count, peripheral addresses, CHCFG/CHCTRL, MID/RID, three software lists (`ld_free`, `ld_queue`, `ld_active`), and a coherent cyclic ring of `struct rz_lmdesc` with `head` and `tail` pointers. The controller owns a `modules` bitmap of allocated request IDs, reset control, base/ext register mappings, and optional ICU device reference. No persistent data is written.

Dependencies and integration points: uses DMAengine, `virt-dma`, OF DMA, Renesas ICU helpers from `irq-renesas-rzv2h.h` and `irq-renesas-rzt2h.h`, reset controls, DMA coherent memory, runtime PM, and I/O polling. OF DMA specs are one cell: low 10 bits carry MID/RID and bits 10-15 carry channel config fields used to derive CHCFG transfer mode, address mode, level, and HIEN. Generic RZ devices use DMARS registers; V2H/T2H use ICU callbacks.

Risks: `rz_dmac_xfer_desc` expects `channel->desc` to have been set before it obtains `vchan_next_desc`; that coupling is easy to break. The link descriptor ring is fixed at 64 entries, while the prep path does not visibly reject SG lists longer than the ring. Residue computation walks the descriptor ring until `CRLA` and can return zero after a full-ring guard, so ring corruption or stale headers can mask residue. `ld_free` is also checked as a completed-cookie list in residue logic, which relies on descriptor objects retaining cookies after reuse. Error IRQ handling clears hardware but does not complete or poison active virt descriptors. Probe cleanup computes the already-probed channel count with `i ? i - 1 : 0`, making off-by-one cleanup worth testing.

Test signals: validate probe on generic DMARS and ICU-backed compatibles, channel request filtering and duplicate MID/RID exclusion, memcpy and slave SG issue/completion, SG counts near and above the 64-link ring size, pause/resume polling, residue during active link-mode transfers, terminate while IRQ thread is pending, reset assert/deassert error paths, and optional error IRQ absence. Kernel static analysis should watch list transitions among `ld_free`, `ld_queue`, `ld_active` and coherent ring pointer arithmetic.

# sources/distributed-fs/ceph-client/drivers/dma/sh/shdma-base.c

Purpose: provides a reusable DMAengine base library for SH-style DMA controllers. Hardware-specific drivers embed `struct shdma_dev`, `struct shdma_chan`, and `struct shdma_desc`, supply `struct shdma_ops`, and receive common descriptor allocation, cookie handling, queueing, slave filtering, IRQ threading, cyclic support, runtime PM handoff, and DMAengine registration setup.

Important APIs/types/functions: exported APIs are `shdma_chan_filter`, `shdma_reset`, `shdma_request_irq`, `shdma_chan_probe`, `shdma_chan_remove`, `shdma_init`, and `shdma_cleanup`. Internal DMAengine hooks include `shdma_alloc_chan_resources`, `shdma_free_chan_resources`, `shdma_prep_memcpy`, `shdma_prep_slave_sg`, `shdma_prep_dma_cyclic`, `shdma_config`, `shdma_terminate_all`, `shdma_issue_pending`, and `shdma_tx_status`. Descriptor state is represented by `enum shdma_desc_status` with `DESC_IDLE`, `DESC_PREPARED`, `DESC_SUBMITTED`, `DESC_COMPLETED`, and `DESC_WAITING`.

Control flow: `shdma_init` validates required hardware callbacks, allocates the per-device channel pointer table, initializes DMAengine hook pointers, and leaves channel registration to the hardware driver. `shdma_chan_probe` initializes one channel, list heads, cookies, locks, PM state, and adds it to the DMAengine channel list. Channel allocation optionally binds a legacy or filtered slave ID, allocates a fixed descriptor array, initializes all embedded descriptors through the hardware callback, and adds them to `ld_free`. Prep code builds descriptor chains from memcpy, SG, or cyclic inputs; `shdma_add_desc` delegates hardware register fields to `ops->desc_setup`, splits transfers by `max_xfer_len`, assigns visible and hidden cookie sentinel values, and temporarily splices prepared descriptors back onto the free list as a chain. `tx_submit` assigns a cookie, moves all chunks in the prepared chain to `ld_queue`, powers the channel when the queue transitions from empty, calls `ops->setup_xfer`, and may start work immediately. `issue_pending` starts the first submitted descriptor when PM state is established. The hard IRQ delegates event detection to `ops->chan_irq`; the thread marks the first completed submitted descriptor, starts the next descriptor, and runs cleanup/callback logic.

State and persistence: `shdma_slave_used` is a module-global bitmap sized by the `slave_num` module parameter and prevents duplicate slave allocations. Each channel owns `ld_queue`, `ld_free`, a descriptor array, `slave_id`, `real_slave_id`, `hw_req`, `pm_state`, and max transfer size. Descriptor state includes cookie, chunk count, partial residue after termination, cyclic flag, and mark. Runtime PM references are taken when queues become active and put when queues drain. There is no disk persistence.

Dependencies and integration points: depends on Linux DMAengine, async_tx callbacks, runtime PM, IRQ threading, scatterlist helpers, and the public `linux/shdma-base.h` contract. Hardware drivers must implement callbacks for descriptor setup, transfer setup/start, halt, busy check, slave binding/address, IRQ interpretation, and descriptor completion. `shdmac.c` is the direct in-tree user in this subset.

Risks: descriptor chain ownership is subtle because prepared descriptors live on `ld_free` until submit, and hidden chunks use special negative cookie sentinels. Cleanup drops the lock around callbacks and loops until callbacks are drained, which can expose reentrancy or ack-order bugs. `shdma_tx_submit` powers up hardware and briefly drops the lock, so reset or free paths can race with PM state transitions. Slave allocation uses a global bitmap and comments warn the generic filter does not distinguish multiple DMAC drivers with `DMA_SLAVE`. `shdma_tx_status` reports `DMA_ERROR` for non-complete cookies not found on the queue, which makes aborted and invalid cookies indistinguishable to clients.

Test signals: exercise multi-chunk memcpy and SG chains, cyclic descriptors, callback-on-last-chunk behavior, async_tx ack recycling, terminate with partial residue callback support, PM get/put balance, IRQ hard/thread sequencing, reset from error/NMI paths, legacy `chan->private` slave binding, OF filter binding, and allocation failure after partial descriptor setup. Useful static checks include lock coverage for queue mutation and `pm_state` transitions.

# sources/distributed-fs/ceph-client/drivers/dma/sh/shdma.h

Purpose: defines the SH DMAE hardware-specific wrapper structures used by `shdmac.c` on top of the generic SHDMA base library. It binds generic `struct shdma_*` objects to SH DMAE register layout, platform data, slave configuration, and per-transfer hardware register images.

Important APIs/types/functions: exported definitions are `SH_DMAE_MAX_CHANNELS`, `SH_DMAE_TCR_MAX`, `struct sh_dmae_chan`, `struct sh_dmae_device`, `struct sh_dmae_regs`, and `struct sh_dmae_desc`. Conversion macros include `to_sh_chan`, `to_sh_desc`, `tx_to_sh_desc`, and `to_sh_dev`; only the `to_sh_dev` style is used by `shdmac.c`, while some macros appear stale against the actual `struct sh_dmae_desc` naming.

Control flow: this header has no runtime control flow. It provides the data layout consumed when `shdmac.c` embeds `struct shdma_chan` in `struct sh_dmae_chan`, embeds `struct shdma_dev` in `struct sh_dmae_device`, and embeds `struct shdma_desc` behind `struct sh_dmae_regs` in `struct sh_dmae_desc`.

State and persistence: per-channel state includes the generic SHDMA channel, selected slave config, transfer-size shift, MMIO base, IRQ name, PM error field, and resolved slave address. Per-device state includes the generic SHDMA device, channel pointer array, platform data, global device list node, channel register base, optional DMARS base, CHCR offset, and interrupt-enable bit. Per-descriptor state is a register snapshot containing SAR, DAR, and TCR plus the generic descriptor. No persistent state is represented.

Dependencies and integration points: includes `linux/sh_dma.h`, `linux/shdma-base.h`, DMAengine, interrupt, and list headers. It is tightly integrated with platform data from `struct sh_dmae_pdata` and `struct sh_dmae_slave_config`, and with the callback contract in `include/linux/shdma-base.h`.

Risks: because this is a layout header, ABI-like risks are field order/embedding assumptions between the base library and hardware driver. The macros referencing `struct sh_desc` look inconsistent with this header's `struct sh_dmae_desc`; accidental use would fail compilation. The fixed maximum of 20 channels and 24-bit TCR limit are hardware assumptions that must match platform data.

Test signals: compile coverage of all SH DMAE configurations is the primary signal. Runtime tests should indirectly validate that `sh_dmae_desc` embedding works through `sh_dmae_embedded_desc`, channel pointer arrays do not exceed `SH_DMAE_MAX_CHANNELS`, and platform data CHCR/DMARS fields map correctly to the wrapper state.

# sources/distributed-fs/ceph-client/drivers/dma/sh/shdmac.c

Purpose: implements the Renesas SuperH DMA Engine hardware driver using the generic SHDMA base library. It programs SAR/DAR/TCR/CHCR/DMAOR/DMARS registers, handles platform IRQ layouts, supports memcpy and slave DMA through the base hooks, resets on address errors and NMI, and registers a platform DMAengine device.

Important APIs/types/functions: hardware operation callbacks are collected in `sh_dmae_shdma_ops`: `sh_dmae_desc_completed`, `sh_dmae_halt`, `sh_dmae_channel_busy`, `sh_dmae_slave_addr`, `sh_dmae_desc_setup`, `sh_dmae_set_slave`, `sh_dmae_setup_xfer`, `sh_dmae_start_xfer`, `sh_dmae_embedded_desc`, `sh_dmae_chan_irq`, and `sh_dmae_get_partial`. Other key functions are `sh_dmae_rst`, `sh_dmae_ctl_stop`, `dmae_set_reg`, `dmae_start`, `dmae_init`, `dmae_set_chcr`, `dmae_set_dmars`, `dmae_find_slave`, `sh_dmae_reset`, `sh_dmae_err`, `sh_dmae_nmi_handler`, `sh_dmae_chan_probe`, `sh_dmae_probe`, and PM callbacks.

Control flow: module init registers a die notifier for NMI handling and probes the platform driver. Probe obtains platform or OF match data, maps channel and optional DMARS resources, initializes DMAengine capabilities, calls `shdma_init`, enables runtime PM, adds the device to a global RCU list for NMI scanning, resets the controller, requests an address-error IRQ when relevant, expands platform IRQ resources into per-channel IRQs, probes each channel through `shdma_chan_probe` and `shdma_request_irq`, drops the runtime PM reference, and registers the DMAengine device. During transfer setup, the base library calls `sh_dmae_setup_xfer` to set DMARS and CHCR for slave transfers or initialize MEMCPY CHCR. Starting a descriptor writes SAR/DAR/TCR and sets CHCR `DE` plus the configured interrupt bit. Channel IRQ handling checks transfer end, halts the channel, and lets the base threaded handler mark descriptors complete and queue the next descriptor. Error IRQ and NMI reset stop DMAOR, reset all base channels, then reinitialize DMAOR.

State and persistence: global state is `sh_dmae_devices` protected by `sh_dmae_lock` and read under RCU for NMI handling. Device state is platform data, channel register base, optional DMARS mapping, channel pointers, CHCR offset, and CHCR IE bit. Channel state includes register base, selected slave config, transfer shift, slave address, IRQ name, and inherited SHDMA queues. Hardware register state is restored on runtime and system resume. No persistent storage exists.

Dependencies and integration points: depends on SH DMA platform data (`linux/sh_dma.h`), the base library in `shdma-base.c`, Linux DMAengine, runtime/system PM, platform resources, raw MMIO accessors, IRQ resource flags, RCU, and die notifier/NMI infrastructure. It supports both platform-data and OF-backed slave selection. The driver registers under platform name `sh-dma-engine`.

Risks: IRQ resource parsing is complex and must match platform data channel counts; shared IRQ and error IRQ combinations are easy to misconfigure. The global NMI notifier scans all devices and resets any controller with NMIF set, which is correct for hardware but broad in blast radius. Address-error reset cannot identify a single channel and resets all channels. `sh_dmae_desc_completed` infers completion by comparing current SAR/DAR against expected end address, which can be fragile if hardware updates registers differently. Raw MMIO access and platform-data bit fields require exact SoC definitions. Probe error paths combine PM, RCU list removal, and channel cleanup.

Test signals: validate platform probe with single shared IRQ, ranges of channel IRQs, and separate error IRQ; memcpy and slave SG via `dmatest`; cyclic operation through the base library; DMARS programming for OF and non-OF slave configs; suspend/resume register restoration; runtime PM reset; address-error IRQ recovery; NMI notifier behavior; channel clear variants; and max transfer splitting at 16 MiB. Static analysis should inspect channel array bounds and RCU/list cleanup on probe failure.

# sources/distributed-fs/ceph-client/drivers/dma/sh/usb-dmac.c

Purpose: implements the Renesas USB-DMAC as a slave-only DMAengine provider using virt-dma. It is intended for fixed USB controller FIFO transfers with 32-byte bus width, per-channel IRQs, SG sequencing in software, residue reporting, and runtime PM integration.

Important APIs/types/functions: key types are `struct usb_dmac`, `struct usb_dmac_chan`, `struct usb_dmac_desc`, and `struct usb_dmac_sg`. DMAengine hooks are `usb_dmac_alloc_chan_resources`, `usb_dmac_free_chan_resources`, `usb_dmac_prep_slave_sg`, `usb_dmac_chan_terminate_all`, `usb_dmac_tx_status`, and `usb_dmac_issue_pending`. Internal helpers include `usb_dmac_chan_start_sg`, `usb_dmac_chan_start_desc`, `usb_dmac_calc_tend`, `usb_dmac_desc_get`, `usb_dmac_desc_put`, `usb_dmac_chan_halt`, `usb_dmac_soft_reset`, `usb_dmac_isr_channel`, and `usb_dmac_isr_transfer_end`.

Control flow: probe parses `dma-channels`, maps the register block, enables runtime PM, initializes DMAOR, initializes each virt-dma channel and per-channel IRQ, registers an OF DMA provider, fills DMAengine slave-only capabilities, registers the engine, then drops the PM reference. Channel resource allocation preallocates 16 descriptors each initially sized for 8 SG entries and takes a runtime PM reference. `prep_slave_sg` obtains or allocates a flexible descriptor large enough for the SG count, records direction and SG DMA addresses/lengths, and returns a virt-dma prepared descriptor. `issue_pending` marks descriptors issued and starts the first descriptor if idle. Hardware can transfer one SG entry at a time; completion IRQ advances `sg_index` and starts the next SG entry, or records final residue, completes the virt cookie, and starts the next descriptor. Termination halts hardware, clears current descriptor, returns all in-use descriptors to the free list, and frees virt-dma issued descriptors.

State and persistence: each channel owns a current descriptor pointer, IRQ number, MMIO base, descriptor allocation count, and two descriptor pools: `desc_got` for descriptors checked out by prep/issue and `desc_freed` for reusable descriptors. A completed descriptor stores `done_cookie` and final `residue` so clients can query residue after `DMA_COMPLETE`. The controller tracks channel count, engine object, and MMIO base. State is volatile only.

Dependencies and integration points: uses Linux DMAengine, `virt-dma`, OF DMA, platform resources, runtime PM, DMA mapping types, and MMIO. The OF spec is one cell selecting a channel index, and the filter requires the requested index to match the virt channel. Bus widths are fixed to `DMA_SLAVE_BUSWIDTH_32_BYTES`; directions are only MEM_TO_DEV and DEV_TO_MEM.

Risks: `usb_dmac_soft_reset` loops over channel count but checks the same `uchan` each time instead of `dmac->channels[i]`, so it may reset while another channel is busy or unnecessarily skip reset based only on the current channel. Residue calculation uses 32-bit low addresses and subtracts live SAR/DAR from the SG memory address, so high-address and wrap scenarios need scrutiny. Descriptor pools are manually managed outside normal virt-dma allocation; leaks or double moves are possible around terminate and free. There is no `device_config` hook because device FIFO addresses are implicit zero-side registers, so clients must match this hardware's fixed USB FIFO integration. The interrupt path handles NULL/FTE behavior and TE/SP bits in a hardware-specific way that can regress short-packet handling.

Test signals: run slave SG transfers for both directions, multiple SG entries, short final packets, residue during active transfer and after completion, terminate while descriptor is active, descriptor allocation growth beyond 8 SG entries, runtime suspend/resume, shutdown, and concurrent channels to expose the soft-reset channel iteration issue. Static checks should focus on list movement between `desc_got` and `desc_freed` and 32-bit address assumptions.

# sources/distributed-fs/ceph-client/drivers/dma/sprd-dma.c

Purpose: implements the Spreadtrum/Unisoc DMA controller as a DMAengine provider. It supports memcpy, slave SG, optional link-list mode supplied by clients, two-stage channel trigger configuration, pause/resume, optional controller IRQs, runtime PM clock management, and OF simple DMA channel translation.

Important APIs/types/functions: key types are `struct sprd_dma_dev`, `struct sprd_dma_chn`, `struct sprd_dma_desc`, and `struct sprd_dma_chn_hw`. DMAengine hooks include `sprd_dma_alloc_chan_resources`, `sprd_dma_free_chan_resources`, `sprd_dma_tx_status`, `sprd_dma_issue_pending`, `sprd_dma_prep_dma_memcpy`, `sprd_dma_prep_slave_sg`, `sprd_dma_slave_config`, `sprd_dma_pause`, `sprd_dma_resume`, and `sprd_dma_terminate_all`. Important internal functions are `sprd_dma_set_chn_config`, `sprd_dma_start`, `sprd_dma_stop`, `sprd_dma_fill_desc`, `sprd_dma_fill_linklist_desc`, `sprd_dma_set_2stage_config`, `sprd_dma_set_uid`, `sprd_dma_set_pending`, `sprd_dma_clear_int`, and `dma_irq_handle`.

Control flow: probe sets a 36-bit coherent DMA mask with 32-bit fallback, reads `dma-channels` or deprecated `#dma-channels`, allocates a controller object with a flexible channel array, gets mandatory `enable` and optional `ashb_eb` clocks, optionally requests the controller IRQ, maps the global register block, initializes DMAengine hooks and each virt-dma channel, enables clocks, enables runtime PM, registers the DMAengine device, and registers `of_dma_simple_xlate` with `sprd_dma_filter_fn`. Allocation takes a runtime PM reference. Memcpy prep allocates one descriptor and fills channel hardware fields with aligned width/step choices. Slave SG prep records optional `struct sprd_dma_linklist` context, decodes channel mode, trigger mode, request mode, and interrupt type from flags, builds link-list entries for multi-entry SG when supplied, and fills the initial descriptor. `issue_pending` starts the next virt descriptor when idle by programming all channel registers, UID, pending request bits, channel enable, and software request for software-triggered channels. IRQ handling scans masked global status bits, clears per-channel interrupts, runs cyclic callbacks for link-list mode, otherwise completes descriptors when the interrupt type satisfies the request mode, then starts the next descriptor.

State and persistence: controller state includes clocks, optional IRQ, global MMIO base, total channel count, and a flexible channel array. Each channel stores channel register base, current descriptor, slave config, link-list context, channel number, device UID, two-stage channel mode, trigger mode, and interrupt type. Descriptors store a complete hardware register image and transfer direction. No state persists beyond live kernel memory and hardware registers.

Dependencies and integration points: depends on DMAengine, `virt-dma`, OF DMA simple translation, Spreadtrum public header `linux/dma/sprd-dma.h` for flags/link-list contracts, clocks, runtime PM, platform resources, and MMIO. Client drivers pass a DMA request UID through OF filter data and may pass link-list memory through the prep context. The driver handles AP/AON/AGCP variants, with optional IRQ and optional ASHB clock for AGCP.

Risks: residue reporting sets `txstate` residue to a hardware address for the current descriptor rather than remaining bytes, which may be a semantic mismatch for DMAengine clients. Slave SG without link-list uses only the last SG length but first SG start address in the initial descriptor, so multi-entry SG behavior depends on client-provided link-list context. `sprd_dma_enable` does not undo the mandatory clock if enabling optional `ashb_clk` fails. The OF filter always returns true after storing `dev_id`, with no channel/request exclusivity. Cyclic detection is based solely on `linklist.phy_addr`, so any link-list transfer is treated as cyclic for IRQ callbacks. Optional no-IRQ controllers cannot complete non-cyclic cookies unless clients use polling/status semantics. Two-stage configuration mutates global group registers and needs strong tests for paired source/destination channels.

Test signals: run memcpy with different alignments and lengths above `SPRD_DMA_MEMCPY_MIN_SIZE`, slave SG single-entry and multi-entry with/without link-list context, two-stage source/destination channel combinations, all request and interrupt modes, optional IRQ absence, pause/resume timeouts, runtime PM clock enable failure, 36-bit address programming through wrap registers, terminate/free current descriptor handling, and OF request UID mapping. Static checks should focus on residue units, SG/link-list assumptions, clock error unwinding, and global two-stage register masks.

# sources/distributed-fs/ceph-client/drivers/dma/st_fdma.c

Purpose: implements the STMicroelectronics STi FDMA engine as a DMAengine provider backed by an ST SLIM remote processor firmware. It supports memcpy, slave SG, cyclic slave transfers, request-line allocation, pause/resume/terminate commands, residue reporting, IRQ completion, and OF DMA translation that boots the firmware on channel request.

Important APIs/types/functions: key functions are `st_fdma_of_xlate`, `st_fdma_dreq_get`, `st_fdma_dreq_put`, `st_fdma_xfer_desc`, `st_fdma_irq_handler`, `st_fdma_alloc_desc`, `st_fdma_alloc_chan_res`, `st_fdma_free_chan_res`, `st_fdma_prep_dma_memcpy`, `config_reqctrl`, `st_fdma_prep_dma_cyclic`, `st_fdma_prep_slave_sg`, `st_fdma_desc_residue`, `st_fdma_tx_status`, `st_fdma_issue_pending`, `st_fdma_pause`, `st_fdma_resume`, `st_fdma_terminate_all`, `st_fdma_slave_config`, and `st_fdma_probe`. Data layout and register macros are defined in `st_fdma.h`.

Control flow: probe derives the firmware name from compatible-specific driver data, reads `dma-channels`, allocates channel state, requests the shared FDMA IRQ, allocates the SLIM remoteproc wrapper, initializes virt-dma channels, reserves DREQ lines 0 and 31, fills DMAengine capabilities and hooks, registers the DMAengine device through `dmaenginem_async_device_register`, and registers an OF DMA controller. OF translation validates the DMA provider node, boots the SLIM remote processor, allocates any slave channel, stores request-line/control/type arguments, and reserves a DREQ line for paced channels. Channel resource allocation creates a DMA pool for 32-byte-aligned hardware nodes. Prep functions allocate one flexible software descriptor with one DMA-pool hardware node per SG/period, fill node control/address/length fields, and return a virt-dma descriptor. `issue_pending` starts the first issued descriptor by writing the first node pointer to channel DMEM and issuing a START command in peripheral registers. IRQ handling scans two status bits per channel, updates channel status, completes non-cyclic descriptors or invokes cyclic callbacks, starts the next descriptor if idle, and clears interrupt status.

State and persistence: state is split across Linux memory, coherent DMA-pool node memory, SLIM DMEM, and FDMA peripheral registers. The device tracks the SLIM remoteproc object, IRQ, DREQ bitmap, firmware name, and channel array. Each channel stores a DMA pool, last slave config, OF/request config, allocated DREQ line, current descriptor, and last DMA status. Software descriptors own an array of hardware node pointers and physical addresses. No disk persistence exists, but firmware boot/shutdown is tied to OF channel allocation/free.

Dependencies and integration points: depends on DMAengine, `virt-dma`, OF DMA, platform IRQs, device properties, DMA pools, and `remoteproc/st_slim_rproc.h`. It uses SLIM remote processor memory and peripheral register windows through macros in `st_fdma.h`. OF DMA args are request line, optional request-control bits masked by `FDMA_REQ_CTRL_CFG_MASK`, and optional transfer type (`FREE_RUN` or `PACED`). Compatible strings select STiH407 MPE31 firmware IDs.

Risks: `st_fdma_dreq_get` only accepts the configured request line and returns error on retry, so there is no fallback despite comments suggesting allocation. Access to `dreq_mask` is not protected by the declared `dreq_lock`; atomic bitops help individual bits but not the `fdev->dreq_mask == ~0L` check. `st_fdma_desc_residue` takes a `vdesc` argument but uses `fchan->fdesc`, so queued descriptor residue may be wrong or unsafe when no current descriptor exists. `st_fdma_prep_slave_sg` does not call `config_reqctrl`, unlike cyclic prep, so paced request-control setup depends on prior config or may be missing. Non-cyclic SG nodes form a circular `next` chain and rely on interrupt-on-last-node to stop. Remove does not explicitly unregister the DMAengine device in this file, relying on devm-style registration semantics if available. Firmware boot/shutdown balance is tied to channel allocation/free paths.

Test signals: test OF translation with one, two, and three DMA args; firmware probe deferral and boot failure; DREQ allocation conflicts; memcpy node execution; slave SG and cyclic transfers for both directions and supported bus widths; pause/resume/terminate commands; residue for active and queued cookies; IRQ error status; remoteproc shutdown on channel free; and probe/remove resource cleanup. Static analysis should check DREQ locking, `st_fdma_desc_residue` use of current descriptor, and whether `dmaenginem_async_device_register` gives intended lifecycle cleanup.

# sources/distributed-fs/ceph-client/drivers/dma/st_fdma.h

Purpose: defines the ST FDMA driver's hardware node formats, software descriptors, channel/device state, command/status registers, SLIM DMEM access macros, request-control encodings, and constants used by `st_fdma.c`.

Important APIs/types/functions: central definitions are `struct st_fdma_generic_node`, `struct st_fdma_hw_node`, `struct st_fdma_sw_node`, `struct st_fdma_driverdata`, `struct st_fdma_desc`, `enum st_fdma_type`, `struct st_fdma_cfg`, `struct st_fdma_chan`, and `struct st_fdma_dev`. Important macros include `FDMA_CMD_START`, `FDMA_CMD_PAUSE`, `FDMA_CMD_FLUSH`, `FDMA_INT_*`, `fdma_read/write`, `fchan_read/write`, `dreq_write`, `fnode_read/write`, `FDMA_NODE_CTRL_*`, and `FDMA_REQ_CTRL_*`.

Control flow: this header has no standalone runtime flow. It enables `st_fdma.c` to build linked hardware node lists, command a channel through SLIM DMEM and peripheral registers, configure paced request controls, and compute status/residue from channel/node memory.

State and persistence: `struct st_fdma_hw_node` is the hardware-consumed 32-byte-aligned descriptor with next pointer, control flags, byte count, source/destination, and generic 2D stride fields. `struct st_fdma_desc` wraps a virt-dma descriptor and a counted flexible array of software nodes. `struct st_fdma_chan` stores its DMA pool, slave config, request config, DREQ line, virt channel, current descriptor, and DMA status. `struct st_fdma_dev` stores the Linux device, compatible driver data, DMAengine device, SLIM remoteproc handle, IRQ, channels, DREQ allocation state, channel count, and firmware name. All state is in memory or device/firmware registers.

Dependencies and integration points: includes DMAengine, DMA pool, I/O, ST SLIM remoteproc, and `virt-dma`. The access macros assume `slim_rproc->peri` and `slim_rproc->mem[ST_SLIM_DMEM].cpu_addr` are valid and that channel and DREQ command blocks are laid out at fixed offsets in SLIM DMEM. Node control and request-control bit definitions form the ABI between the Linux driver, FDMA firmware, and clients.

Risks: register and DMEM accessor macros are untyped and directly compute offsets from channel IDs or DREQ lines, so invalid IDs can become out-of-bounds MMIO/DMEM accesses. `FDMA_DMA_BUSWIDTHS` in the C file uses `BIT(DMA_SLAVE_BUSWIDTH_*)` style while most DMAengine drivers use enum values as bitmasks; this should be confirmed against the local API. Flexible array structs require allocation through `kzalloc_flex` with correct node counts. Hardware node alignment is critical; changing `struct st_fdma_hw_node` layout could break firmware consumption.

Test signals: compile-time layout/alignment checks, probe with all three STiH407 compatibles, transfer prep that allocates 1 and many nodes, request-control encoding for each supported bus width, SLIM DMEM register read/write smoke tests, and negative tests for invalid DREQ/channel IDs. Firmware integration tests should confirm the node ABI fields are consumed as expected.
