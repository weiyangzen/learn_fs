# sources/distributed-fs/ceph-client/drivers/net/ethernet/emulex/benet/be_cmds.c

Purpose: implements the Emulex/Broadcom BladeEngine `benet` firmware command layer. It is the driver's control-plane bridge between Linux netdev/ethtool/probe code and adapter firmware, using mailbox WRBs before MCC queues exist and synchronous or asynchronous MCC WRBs afterward. It creates and destroys hardware queues, configures interfaces, MACs, VLANs, RSS, flow control, link state, SR-IOV resources, VXLAN offload, WOL, diagnostics, firmware logging, dump handling, and firmware download for BE2/BE3/Skyhawk/Lancer generations.

Important APIs/types/functions: command transport helpers include `embedded_payload`, `be_mcc_notify`, `be_mcc_compl_is_new`, `be_mcc_compl_process`, `be_mcc_event_process`, `be_process_mcc`, `be_mcc_notify_wait`, `be_mbox_notify_wait`, `be_wrb_cmd_hdr_prepare`, `be_cmd_notify_wait`, `wrb_from_mbox`, and `wrb_from_mccq`. Initialization and readiness APIs are `be_cmd_fw_init`, `be_cmd_fw_clean`, `be_POST_stage_get`, and `be_fw_wait_ready`. Queue and interface APIs include `be_cmd_eq_create`, `be_cmd_cq_create`, `be_cmd_mccq_create`, `be_cmd_txq_create`, `be_cmd_rxq_create`, `be_cmd_q_destroy`, `be_cmd_rxq_destroy`, `be_cmd_if_create`, and `be_cmd_if_destroy`. Network configuration APIs include `be_cmd_mac_addr_query`, `be_cmd_pmac_add`, `be_cmd_pmac_del`, `be_cmd_get_mac_from_list`, `be_cmd_set_mac_list`, `be_cmd_set_mac`, `be_cmd_vlan_config`, `be_cmd_rx_filter`, `be_cmd_rss_config`, `be_cmd_set_flow_control`, `be_cmd_get_flow_control`, `be_cmd_link_status_query`, `be_cmd_set_logical_link_config`, and `be_cmd_set_vxlan_port`. Diagnostics and management include `be_cmd_get_stats`, `lancer_cmd_get_pport_stats`, `be_cmd_get_fat_dump_len`, `be_cmd_get_fat_dump`, `lancer_initiate_dump`, `lancer_delete_dump`, `dump_present`, `be_cmd_loopback_test`, `be_cmd_ddr_dma_test`, `be_cmd_get_seeprom_data`, `be_cmd_read_port_transceiver_data`, `be_cmd_query_sfp_info`, `be_cmd_query_cable_type`, `be_cmd_get_phy_info`, `be_cmd_get_fw_log_level`, and `be_cmd_set_fw_log_level`. Firmware and resource/profile paths include `be_fw_download`, `lancer_fw_download`, `be_cmd_get_func_config`, `be_cmd_get_profile_config`, `be_cmd_set_sriov_config`, `be_cmd_config_qos`, `be_cmd_get_fn_privileges`, `be_cmd_set_fn_privileges`, `be_cmd_get_active_profile`, `be_cmd_enable_vf`, and exported `be_roce_mcc_cmd`.

Control flow: early probe uses mailbox commands guarded by `mbox_lock`: firmware init/clean, POST readiness, EQ/CQ/MCCQ creation, firmware config, function config, active profile, interrupt enable, and function reset. Once the MCC queue is created, most runtime commands allocate a WRB with `wrb_from_mccq`, fill an embedded or non-embedded payload, ring `DB_MCCQ_OFFSET`, and either wait synchronously through `be_mcc_wait_compl` or return after posting an asynchronous request. Completion processing pulls MCC CQ entries, dispatches async events by event code, processes command completions, decrements queue usage, and rearms the CQ. Async event handlers update cached link speed, link status, QoS speed, VLAN priority, PVID, OS-to-BMC filtering, QnQ VID, and SFP/port-misconfiguration state. Flashing flows parse UFI sections, check current flash CRCs, skip matching regions, stream 32 KiB chunks, and handle chip-specific fallback paths for older firmware or offset-based flashing. Lancer uses firmware objects (`/prg`, `/dbg/dump.bin`, VPD files) rather than legacy flashrom/FAT commands.

State and persistence behavior: runtime state is primarily in `struct be_adapter`: MCC queue occupancy, CQ rearm policy, cached firmware versions, function mode/caps, port/HBA/PF/VF numbers, physical link/PHY info, RSS tables and hash key, WOL capability/enabled state, privilege masks, port name, SFP state, cached statistics, error-recovery timers, and resource limits. The code updates hardware/firmware state persistently for flash images, NCSI/PHY/option ROM sections, WOL settings, function privileges, profile/SR-IOV resources, VF enablement, logical link state, HSW/VEPA/VEB configuration, QoS, VXLAN port config, firmware log level, and MAC lists. Many operations use DMA-coherent command buffers whose contents are firmware ABI data and require explicit endian conversion. Error state is persisted in adapter flags via `be_set_error`, `be_detect_error`, and UE recovery feature negotiation.

Dependencies and integration points: depends on `be.h`, `be_cmds.h`, `be_hw.h` register definitions, Linux PCI/MMIO/DMA APIs, completions, spinlocks, mutexes, netdev carrier/link helpers, firmware loading, and ethtool callers in `be_ethtool.c`. It integrates with probe/open/close queue setup, NAPI interrupt servicing through MCC completions, multicast/VLAN filter programming from netdev state, SR-IOV VF management, RoCE via exported `be_roce_mcc_cmd`, hwmon die temperature polling, ethtool flash/dump/self-test/WOL operations, and Lancer physical-device reset/dump control.

Risks: this file is high risk because it encodes firmware ABI layout, command sequencing, timeout behavior, DMA addresses, and endian conversion. Incorrect WRB tags can cause completions to write through stale pointers; wrong embedded/non-embedded selection or command size can corrupt firmware command buffers; and queue accounting mistakes can stall the MCC ring. Several paths hold `mcc_lock` while building commands and then drop it before waiting on completions, so timeout and completion ordering must remain consistent with `adapter->et_cmd_compl` and `adapter->flash_status`. Flashing code can leave adapters partially updated, and the Skyhawk fallback explicitly returns `-EAGAIN` when a reboot is required to finish. Resource descriptor parsing trusts firmware-provided descriptor lengths with only defaulting for zero length, so malformed descriptor lists can misdirect SR-IOV or QoS configuration. Privilege gating is command-specific; missing an opcode in `cmd_priv_map` can expose operations to insufficiently privileged functions. Some functions return raw MCC status while callers expect Linux errno via `be_cmd_status`.

Test signals: probe should progress through POST, mailbox init, EQ/CQ/MCCQ creation, firmware config query, and interface creation on BE2, BE3, Skyhawk, and Lancer. Runtime signals include successful RX/TX traffic, link up/down async events, `ethtool -S` stats updates, RSS indirection/hash changes, VLAN and multicast filtering, pause control, WOL programming, `ethtool -p` beacon toggling, and SR-IOV VF creation/configuration. Diagnostic tests should cover firmware dump length/read/delete/initiate, self-tests for loopback and DDR DMA, SFP EEPROM reads, firmware log-level changes, privilege-denied VF commands, MCC timeout injection, flash CRC skip behavior, signature errors, and Lancer firmware-object download/reset behavior.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/emulex/benet/be_cmds.h

Purpose: firmware command ABI header for the Emulex/Broadcom `benet` driver. It defines MCC/mailbox WRB formats, completion status encoding, async event payloads, command subsystem/opcode numbers, request and response structures for network, queue, flash, diagnostics, WOL, PHY, resource-profile, SR-IOV, and feature commands, plus the public function prototypes implemented in `be_cmds.c`.

Important APIs/types/functions: transport types include `struct be_sge`, `struct be_mcc_wrb`, `struct be_mcc_compl`, and `struct be_mcc_mailbox`, with status helpers `base_status` and `addl_status`. Command headers are `struct be_cmd_req_hdr` and `struct be_cmd_resp_hdr`. Async event structures include link state, group-5 QoS/CoS/PVID/FW-control events, QnQ debug events, and port misconfiguration events, with PHY-state helper macros. Queue creation and descriptor command types include `amap_eq_context`, `be_cmd_req_eq_create`, `amap_cq_context_be`, `amap_cq_context_v2`, `be_cmd_req_cq_create`, `amap_mcc_context_be`, `amap_mcc_context_v1`, TX/RX queue create responses, and queue destroy structures. Network configuration types include interface flags, MAC list structures, VLAN config, RX filter, link status, RSS config, flow control, HSW config, logical link config, and manage-interface filters. Management types cover statistics layouts v0/v1/v2 and Lancer pport stats, FAT/ext-FAT firmware logging, flash UFI headers/sections, flashrom commands, Lancer object read/write/delete, ACPI WOL, loopback/DDR tests, SEEPROM, PHY details, controller attributes, function privileges, resource descriptors, profile config, active profile, interrupt enable, VF enable, and UE recovery.

Control flow: this header is declarative, but it drives most control paths in `be_cmds.c`. Callers build a `be_cmd_req_hdr` with subsystem/opcode/version/domain/length, wrap it in a WRB as embedded data or an SGE-backed DMA command, submit by mailbox or MCC, then parse a `be_cmd_resp_hdr` or command-specific response. Async completions reuse `struct be_mcc_compl` storage and are cast to specific event structures based on event code and type bits. Resource configuration flows read descriptor lists, search by descriptor type and PF/VF flags, then write modified descriptors back with set-profile commands.

State and persistence behavior: most structures describe transient DMA command buffers or volatile hardware state, but several map persistent firmware state: flash sections and component optypes, NCSI/PHY/option ROM firmware images, WOL configuration, function privileges, saved/active profile resource descriptors, SR-IOV state, MAC lists, HSW/PVID/spoof-check settings, firmware log levels, and VXLAN port descriptors. Statistics structures represent cumulative firmware/hardware counters. Packed structures and pseudo-AMAP bit arrays represent firmware ABI exactly, so field order and size are part of persistent compatibility with existing firmware.

Dependencies and integration points: depends on definitions from `be.h`, `be_hw.h`, Linux Ethernet constants, ethtool RSS flags, endian types, and adapter structures. It is included by `be_cmds.c`, `be_ethtool.c`, and other driver modules that invoke command APIs. It also exposes `be_roce_mcc_cmd` indirectly through the implementation for RoCE consumers. The header bridges Linux concepts such as WOL, RSS, ethtool link modes, SR-IOV VF domains, and EEPROM/module data into firmware command structures.

Risks: layout changes are dangerous because many structures are `__packed` firmware contracts and many fields are little-endian even when represented as plain `u32`. The pseudo-AMAP structures are bit-position metadata for AMAP macros; a single inserted or removed byte changes hardware context programming. Some command response declarations use request-header-looking names for historical compatibility, so readers must not infer normal C object semantics. The stats layouts differ by chip/command version; using the wrong version corrupts counter interpretation. Flash constants and component offsets are destructive-operation metadata, so incorrect optype/offset mapping can flash the wrong partition. Interface capability masks and privilege constants must remain synchronized with firmware policy or netdev operations may silently fail or be over-permitted.

Test signals: compile coverage should catch prototype and field drift across `be_cmds.c`, `be_ethtool.c`, and main driver files. Runtime signals include valid MCC completions, async link events decoded correctly, queue IDs returned after create commands, MAC/VLAN/RSS/filter commands accepted, ethtool stats matching expected offsets for each chip generation, flash image parsing with valid cookies and signature-status handling, WOL capability reads, SFP EEPROM reads, SR-IOV profile descriptors parsed and set, and UE recovery feature negotiation on firmware that supports it. ABI-sensitive changes need hardware or firmware-emulator validation on BE2, BE3, Skyhawk, and Lancer.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/emulex/benet/be_ethtool.c

Purpose: implements the `ethtool_ops` front end for the `benet` network driver. It exposes driver/firmware identity, statistics, coalescing, link settings, ring sizing, pause control, physical port identify, firmware dump operations, WOL, offline diagnostics, firmware flashing, EEPROM/VPD/module EEPROM reads, message level, RSS hash/indirection controls, channel counts, and private flags.

Important APIs/types/functions: `struct be_ethtool_stat` plus `et_stats`, `et_rx_stats`, and `et_tx_stats` define exported counter names and offsets into driver stats. `be_get_drvinfo`, `be_get_ethtool_stats`, `be_get_stat_strings`, and `be_get_sset_count` implement identity and string/stat reporting. Coalescing uses `be_get_coalesce` and `be_set_coalesce`. Link and media reporting uses `be_get_link_ksettings`, `be_get_port_type`, `convert_to_et_setting`, and `be_pause_supported`. WOL and pause paths are `be_get_wol`, `be_set_wol`, `be_get_pauseparam`, and `be_set_pauseparam`. Diagnostics include `be_self_test`, `be_loopback_test`, `be_test_ddr_dma`, `be_set_phys_id`, `be_set_dump`, `be_get_dump_flag`, and `be_get_dump_data`. Firmware/NVM paths include `be_do_flash`, `be_get_eeprom_len`, `be_read_eeprom`, `be_get_module_info`, and `be_get_module_eeprom`. RSS/channel controls are `be_get_rxfh_fields`, `be_set_rxfh_fields`, `be_get_rxfh`, `be_set_rxfh`, `be_get_channels`, and `be_set_channels`. The exported table is `const struct ethtool_ops be_ethtool_ops`.

Control flow: ethtool invokes a table method, the method reads cached adapter state when possible, and calls `be_cmds.c` firmware commands when hardware state must be queried or changed. Link settings lazily refresh `adapter->phy.link_speed` and PHY capabilities when the cached speed is invalid, then convert BE speed/interface bits into legacy ethtool link-mode masks. Coalescing updates per-EQ AIC settings and, on Skyhawk with adaptive coalescing disabled, forces an EQD firmware update. Stats are copied by offset from global driver stats and per-queue stats, using `u64_stats_fetch_begin/retry` for 64-bit queue counters. Offline tests enable loopback modes, run firmware loopback commands, disable loopback, run DDR DMA tests except on Lancer, and poll link recovery. RSS control validates requested hash fields and Toeplitz settings, maps ethtool indirection entries to firmware RSS IDs, then calls `be_cmd_rss_config`. Channel changes validate combined/RX/TX constraints, store requested IRQ counts, and call `be_update_queues`.

State and persistence behavior: most ethtool methods are views over runtime `adapter` state: `msg_enable`, `priv_flags`, `aic_enabled`, queue counts, RSS tables/hash key/flags, link cache, flow-control cache, WOL enablement, and firmware dump length. Some operations persist settings into adapter firmware or PCI power state: WOL magic MAC and PCI wake settings, pause control, firmware log level, RSS hash configuration, channel-driven queue reconfiguration, firmware image flashing, Lancer dump creation/deletion, and beacon state toggling during physical identification. Private flag `disable-tpe-recovery` only updates driver runtime policy and logs the resulting recovery state.

Dependencies and integration points: depends on `be.h`, `be_cmds.h`, Linux ethtool APIs, PCI wake APIs, DMA allocation, netdev carrier state, queue update helpers, RSS constants, and firmware command wrappers. It integrates with user-space `ethtool`, module EEPROM/SFP readers, firmware flashing tools, dump collection workflows, SR-IOV/privilege policy through `check_privilege`, and hardware diagnostics. Several features require privileged PF-level command rights and return `-EOPNOTSUPP` for VFs or restricted functions.

Risks: ethtool is user-facing, so raw firmware statuses must be consistently mapped with `be_cmd_status`; missed mappings can expose confusing errors. EEPROM and module reads must respect offsets and lengths; the page A0/A2 split in `be_get_module_eeprom` is sensitive to pointer advancement and range calculations. RSS setters update cached indirection entries before the firmware command completes, so failed commands must leave cache in a coherent state; this file resets only `rss_flags` on one failure path. Channel changes can reconfigure queues and IRQs, creating risk if requested counts exceed firmware resource descriptors. Offline tests alter loopback state and depend on completion signaling from async MCC commands; timeout or failure paths must restore normal loopback. WOL persists PCI wake state and firmware magic MAC, so incorrect capability detection can break suspend/resume behavior. Stats arrays depend on struct offsets and assumed first fields in per-queue stats.

Test signals: `ethtool -i`, `-S`, `-c/-C`, `-k`-adjacent RSS commands, `-x/-X`, `-l/-L`, `-a/-A`, `-p`, `-s`-style link queries through netlink, `--test`, `--flash`, `--get-dump/--set-dump`, `-e`, `-m`, and `-s wol g` should exercise this surface. Verify stats string count equals data count across queue-count changes, 64-bit counters do not tear under traffic, link settings cache refreshes after async link events, pause setting denies autoneg changes, RSS rejects unsupported UDP L4 hashing on BEx, channel changes survive traffic restart, restricted VFs cannot read privileged dump/module data, and WOL persists across suspend/resume on capable devices.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/emulex/benet/be_hw.h

Purpose: hardware register and descriptor contract header for the Emulex/Broadcom `benet` Ethernet driver. It names mailbox, SLIPORT, PCI config, interrupt, doorbell, POST, WOL, UE status, and SLI interface registers, plus the host-memory descriptor formats used by event, completion, TX, and RX queues.

Important APIs/types/functions: there are no callable functions. Register definitions include `MPU_MAILBOX_DB_OFFSET` and mailbox ready/high masks, `SLIPORT_*` status/control/error offsets and masks, `PHYSDEV_CONTROL_*` reset/dump/in-progress masks, PCI config offsets for interrupt control, power management, online registers, UE status/masks, and `SLI_INTF_*` family/interface/revision fields. Doorbell definitions cover event queues (`DB_EQ_*` and R2I delay encodings), completion queues (`DB_CQ_*`), TX ULP queues (`DB_TXULP1_*`), RX queues (`DB_RQ_*`), and MCC queues (`DB_MCCQ_*`). Descriptor types include `struct be_eq_entry`, `struct be_eth_wrb`, `struct amap_eth_hdr_wrb`, `struct be_eth_hdr_wrb`, `struct amap_eth_tx_compl`, `struct be_eth_tx_compl`, `struct be_eth_rx_d`, `struct amap_eth_rx_compl_v0`, `struct amap_eth_rx_compl_v1`, and `struct be_eth_rx_compl`, plus TX completion status constants and RX packet type encodings.

Control flow: this file supplies constants used by implementation code rather than executing directly. Command setup uses the mailbox doorbell sequence documented here: write high DMA address bits, poll ready, write low DMA address bits, poll completion, then read a valid mailbox completion. Queue servicing code rings EQ/CQ/TX/RX/MCC doorbells using the masks and shifts here to post descriptors, acknowledge completions, rearm interrupts, clear interrupts, and configure interrupt delay encodings. Reset and dump paths poll or write SLIPORT and physical-device control registers. Receive and transmit paths use the descriptor and pseudo-AMAP layouts to construct TX header/fragment WRBs and parse TX/RX completion words.

State and persistence behavior: register values are volatile MMIO or PCI config state, but they control persistent-looking device behavior such as firmware reset, diagnostic dump generation, interrupt enablement, online state, UE recovery masks, and mailbox command submission. Descriptor structures represent DMA-visible runtime state shared between host and NIC: producer/consumer indices are driven by doorbells, valid bits mark entries ready for software, and completion status bits feed driver statistics and error handling. No software-owned state is stored in this header; it defines the layout that other files use to maintain adapter state.

Dependencies and integration points: consumed by `be_cmds.c`, queue setup/teardown code, interrupt/NAPI handlers, TX/RX datapath code, firmware reset/error recovery logic, and ethtool diagnostics. It depends on Linux fixed-width and endian types from surrounding includes and on AMAP bitfield helpers used against the pseudo-layout structures. The descriptors integrate directly with `struct be_queue_info` rings allocated by the driver and programmed into firmware through command structures in `be_cmds.h`.

Risks: register offsets, masks, and descriptor bit positions are hard hardware ABI. An incorrect doorbell shift can notify the wrong queue or post the wrong descriptor count; a wrong valid bit or endian assumption can drop completions or process stale entries; and an incorrect SLIPORT/PHYSDEV mask can trigger resets or dumps unexpectedly. The v0/v1 RX completion layouts differ in port, VLAN, tunneled, and header fields, so code must select the right layout for BE2/BE3 legacy versus native modes. TX completion status codes differ between BE/Skyhawk and Lancer, requiring chip-specific decoding. Doorbell ring IDs have split low/high masks for extended queue IDs, so queue-id handling must preserve both parts.

Test signals: hardware bring-up should validate mailbox command completion, POST stage polling, Lancer ready/idle polling, interrupt enable/disable, EQ/CQ rearm and delay behavior, TX doorbells under traffic, RX buffer posting, MCC command posting, and diagnostic dump generation. Datapath validation should include checksum offload, TSO, VLAN/QnQ, RSS hash reporting, tunneled packet completion, TX error decoding, RX error/drop counters, and high queue IDs that exercise extended ring-id masks. Error tests should cover UE status handling, firmware reset, no-resource SLIPORT errors, and mailbox ready timeouts.
