# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/audit_log.c

Purpose: `audit_log.c` is the DSDB ldb module that observes write-side database operations, transaction boundaries, and selected replication extended operations so Samba can emit human-readable audit lines, JSON audit records, and optional messaging-bus events. It converts adds, modifies, deletes, transaction lifecycle events, password/authentication-info changes, and replicated-update metadata into structured audit payloads. It depends on `audit_util.c` for SID/session/DN/value rendering and redaction decisions.

Important APIs, types, and functions: the module-private `struct audit_private` stores event-notification booleans, an `imessaging_context`, the current transaction GUID, and transaction start time. `has_password_changed()` and `has_authentication_information_changed()` classify messages using audit utility attribute sets. `operation_json()`, `replicated_update_json()`, `password_change_json()`, `transaction_json()`, and `commit_failure_json()` build versioned JSON wrappers. Human-readable counterparts are `operation_human_readable()`, `password_change_human_readable()`, `replicated_update_human_readable()`, `transaction_human_readable()`, and `commit_failure_human_readable()`. `audit_callback()` is the ldb asynchronous completion hook. `log_add()`, `log_modify()`, `log_delete()`, and `log_extended()` rebuild requests with this callback and add `DSDB_CONTROL_TRANSACTION_IDENTIFIER_OID`. Transaction hooks are `log_start_transaction()`, `log_prepare_commit()`, `log_end_transaction()`, and `log_del_transaction()`. `ldb_audit_log_module_init()` registers `ldb_audit_log_module_ops`.

Control flow: init allocates `audit_private`, reads `loadparm`, enables DSDB/password event notification, and optionally initializes messaging. Each write operation creates a new downstream ldb request, preserving original controls and adding the current transaction identifier. The callback forwards entries/referrals immediately and logs only when it receives `LDB_REPLY_DONE`, so audit status reflects the final ldb result. Standard operations log DSDB change payloads and, when the input message contains password or authentication attributes, emit additional password-audit events. Transaction start creates a fresh GUID and timestamp; prepare/end failures are logged at failure level; successful end logs a commit at completion level and clears the GUID; rollback logs and clears the GUID.

State and persistence: no database state is persisted by this module. Its only retained state is per-module transaction metadata and the optional messaging client. Audit artifacts leave the process through Samba debug classes, JSON audit logging, and `audit_message_send()` on `DSDB_EVENT_NAME` or `DSDB_PWD_EVENT_NAME`. Attribute values in audit records are redacted or truncated, not stored by the module.

Dependencies and integration points: this file integrates with ldb module callbacks, `lib/audit_logging`, `auth_session_info`, `imessaging`, loadparm flags `lpcfg_dsdb_event_notification()` and `lpcfg_dsdb_password_event_notification()`, password ACL validation control `DSDB_CONTROL_PASSWORD_ACL_VALIDATION_OID`, transaction identifier control `DSDB_CONTROL_TRANSACTION_IDENTIFIER_OID`, and replicated-object extended data `struct dsdb_extended_replicated_objects`. It relies on `audit_util.c` for remote address, user SID/session, request DN/name mapping, and attribute JSON generation.

Risks and edge cases: logging correctness depends on callback completion; operations that bypass these hooks or fail before a downstream request is built may not be audited. Secret redaction is delegated to attribute-name lists, so incomplete lists would leak values. Transaction GUID is module-private and reset on end/rollback; nested or missing transaction callbacks would confuse correlation. `log_operation()` appears to call `log_replicated_operation()` only when the extended OID is not `DSDB_EXTENDED_REPLICATED_OBJECTS_OID`, while `log_extended()` only wraps that OID; this inverted condition is a notable audit-coverage risk for replicated updates. Messaging send is best-effort and does not fail the ldb operation. JSON construction failures produce invalid/empty objects and a debug error rather than blocking the original DB change.

Test signals: Samba selftest registration includes `samba4.dsdb.samdb.ldb_modules.audit_log`, `samba4.dsdb.samdb.ldb_modules.audit_log.errors`, Python audit-log password-change and DSDB suites, and shared `lib.audit_logging` tests. Useful coverage should exercise successful and failed add/modify/delete, password reset versus change controls, authentication attribute changes, transaction rollback/commit failure, JSON error paths, event notification enabled/disabled, and replicated extended-operation logging.

# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/audit_util.c

Purpose: `audit_util.c` is a utility companion for DSDB audit modules. It centralizes classification of secret/password/authentication attributes, caller/session/remote-address lookup, request operation/DN extraction, modify-action naming, and JSON rendering of ldb message attributes with redaction, truncation, and base64 metadata.

Important APIs, types, and functions: public helpers include `dsdb_audit_redact_attribute()`, `dsdb_audit_is_password_attribute()`, `dsdb_audit_is_authentication_information()`, `dsdb_audit_get_remote_address()`, `dsdb_audit_get_actual_sid()`, `dsdb_audit_get_user_sid()`, `dsdb_audit_is_system_session()`, `dsdb_audit_get_unique_session_token()`, `dsdb_audit_get_actual_unique_session_token()`, `dsdb_audit_get_remote_host()`, `dsdb_audit_get_primary_dn()`, `dsdb_audit_get_message()`, `dsdb_audit_get_secondary_dn()`, `dsdb_audit_get_operation_name()`, `dsdb_audit_get_modification_action()`, and `dsdb_audit_attributes_json()`. Static `dsdb_audit_add_ldb_value()` converts one `ldb_val` into a JSON object/null value with optional `base64` and `truncated` flags.

Control flow: callers pass request/module/context objects into focused extractors. Attribute JSON generation iterates all message elements, creates one action object per element, adds add/modify action text, redacts configured sensitive attributes, and otherwise serializes each value. Repeated attribute names are merged under an attribute object with an `actions` array. Zero-length values become JSON nulls; non-printable values are base64-encoded; long values are truncated before optional base64 encoding.

State and persistence: this file has no module-private state and writes no persistent data. It reads opaque ldb context values such as `remoteAddress`, `DSDB_NETWORK_SESSION_INFO`, and `DSDB_SESSION_INFO`, and it reads ACL/session token state via `acl_user_token()`.

Dependencies and integration points: secret/password/authentication lists come from `DSDB_SECRET_ATTRIBUTES`, `DSDB_PASSWORD_ATTRIBUTES`, and `DSDB_AUTHENTICATION_ATTRIBUTES`. The code uses ldb request structs, `tsocket_address`, Samba auth/session structures, security token/SID helpers, JSON audit helpers from `lib/audit_logging`, and base64/string heuristics from ldb.

Risks and edge cases: redaction is name-based and case/list correctness is critical. `dsdb_audit_get_user_sid()` assumes `PRIMARY_USER_SID_INDEX` exists when a token is returned. Several getters return `NULL` for missing opaque values; consumers must tolerate null JSON fields and human-readable formatting of absent SIDs/DNs. Truncation happens before base64 encoding, so encoded output can exceed `MAX_LENGTH`. JSON object ownership is subtle: error paths free partially built objects and return invalid objects that callers must handle.

Test signals: selftest registration includes `samba4.dsdb.samdb.ldb_modules.audit_util`, plus audit-log tests that consume these helpers. Good test cases include redaction of every configured secret/password attribute, base64 and truncation flags, repeated attributes in modify operations, add versus modify action names, missing session/remote opaque values, rename secondary DN extraction, and operation-name mapping for all ldb request types.

# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/count_attrs.c

Purpose: `count_attrs.c` is an ldb search instrumentation module for performance analysis. It counts which attributes clients request, which attributes are returned, duplicates, missing/unwanted attributes, wildcard matches, null/empty request behavior, and request-size versus response-size pairs. The counts are stored in TDB files under the Samba private `debug` directory and are intended for analysis with `script/attr_count_read`.

Important APIs, types, and functions: `struct count_attrs_private` owns nine `tdb_wrap` stores: requested, duplicates, found, not_found, unwanted, star_match, null_req, empty_req, and req_vs_found. `struct count_attrs_context` tracks the original request, sorted requested attrs, wildcard/null state, and module. `increment_attr_count()` and `increment_req_vs_found()` implement fetch/increment/store counters. `get_sorted_attrs()` copies and sorts request attrs. `count_attrs_search()` instruments outgoing searches and builds the callback request. `count_attrs_search_callback()` classifies each returned entry. `open_private_tdb()`, `make_private_dir()`, and `count_attrs_init()` set up private storage.

Control flow: init creates `private/debug` and opens all counter databases with `TDB_CLEAR_IF_FIRST`. If setup fails, the module leaves private data NULL and subsequent searches pass through uninstrumented. For each search, requested attrs are counted first, sorted, and deduplicated for comparison. The callback forwards referrals/done normally. For entries, it either counts attributes returned for null/empty attr requests or performs a merge-style comparison between sorted requested and found attributes to classify found, not_found, unwanted, and star_match. Each entry also updates a two-integer request-versus-found count key.

State and persistence: TDB files persist the counters for the lifetime of the opened databases, but `TDB_CLEAR_IF_FIRST` means data is cleared when the first process opens the DB. Counter updates are not locked; the source explicitly accepts rare lost increments from concurrent fetch/store races. The ldb request itself is not modified except for wrapping with a callback.

Dependencies and integration points: the module uses ldb search module APIs, `tdb_wrap`, loadparm private-path resolution, filesystem `mkdir`, and Samba debug logging. It is independent of DSDB schema semantics and treats attributes as case-insensitive strings.

Risks and edge cases: the duplicate-removal loop sets `n_attrs = j`, which undercounts by one for unique lists because `j` is the last index rather than the number of retained elements; that can skew comparisons. Counter stores are best-effort and non-atomic across processes. Initialization failure silently disables counting after warnings. TDB key layout for request-versus-found uses host `ssize_t` pairs, so analysis tools must match platform width/endianness. Large searches add per-entry sorting and comparisons, so this module is diagnostic rather than free.

Test signals: likely validation is by module-level unit/integration tests or manual `attr_count_read` inspection. Useful tests include null attrs, empty attr arrays, wildcard requests, duplicate requested attrs, duplicate returned attrs, unwanted generated attrs, TDB setup failure pass-through, and concurrent search load where statistical rather than exact counts are acceptable.

# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/descriptor.c

Purpose: `descriptor.c` is the DSDB security descriptor module. It computes initial `nTSecurityDescriptor` values on object creation, enforces owner-write invariants, recalculates descriptors on security descriptor modifications and moves, filters returned descriptors according to SD flags, and schedules/executes security descriptor inheritance propagation at transaction prepare time.

Important APIs, types, and functions: transaction state is held in `struct descriptor_data` and `struct descriptor_transaction`, including an in-memory dbwrap map of registered changes and processed objects. `struct descriptor_changes` records NC root, object GUID, parent GUID, force-self/children flags, and list bookkeeping. Descriptor construction flows through `get_default_ag()`, `get_sd_unpacked()`, `get_default_group()`, `descr_handle_sd_flags()`, `get_new_descriptor_nonlinear()`, and `get_new_descriptor()`. Request hooks are `descriptor_add()`, `descriptor_modify()`, `descriptor_search()`, `descriptor_rename()`, `descriptor_extended()`, and transaction hooks. Propagation is handled by `descriptor_extended_sec_desc_propagation()`, `descriptor_sd_propagation_object()`, and `descriptor_sd_propagation_recursive()`.

Control flow: add requests ignore special DNs, detect NC heads, fetch parent SD when needed, locate the structural class, validate any supplied owner SID, compute a new descriptor from class default, parent descriptor, supplied descriptor, token, default owner/group, and inheritance rules, then forwards a modified add request plus `DSDB_CONTROL_CALCULATED_DEFAULT_SD_OID`. Modify requests pass through unless they target `nTSecurityDescriptor` or internal propagation control. They validate propagation-control shape, reject unsupported descriptor delete, optionally validate owner changes, fetch current object/parent descriptors and class, compute the replacement descriptor, and schedule child propagation if the descriptor changed. Search requests wrap only when SD flags or requested attributes require descriptor filtering. Rename wraps the downstream request and schedules force-self propagation after a successful move. Extended propagation operations register object GUID work items into transaction maps; prepare commit sorts changes parent-first and recursively recalculates affected subtrees.

State and persistence: descriptor values are persisted by rewriting `nTSecurityDescriptor` attributes in ldb operations. The module keeps transaction-local talloc memory and in-memory rb-tree maps to de-duplicate propagation registrations and processed objects; these are freed on transaction end or rollback. No separate on-disk state is kept by this module. It relies on ldb transaction boundaries so prepare-commit propagation sees a stable tree.

Dependencies and integration points: it uses Samba security descriptor/NDR APIs, SDDL parsing, schema class defaults, DSDB NC/root lookups, extended DN GUID extraction, ACL security tokens, `create_security_descriptor()`, `map_generic_rights_ds`, dbwrap rbt maps, `DSDB_CONTROL_SEC_DESC_PROPAGATION_OID`, `DSDB_EXTENDED_SEC_DESC_PROPAGATION_OID`, `LDB_CONTROL_SD_FLAGS_OID`, and helper scheduling from DSDB module utilities. It is intentionally positioned above `repl_meta_data`, and comments in that module refer to descriptor interactions.

Risks and edge cases: this is security-critical code; mistakes can grant or hide access. Owner validation depends on token privileges and default-administrator-group logic. Partial SD flag handling must preserve unspecified old descriptor parts exactly. Propagation can be expensive for large subtrees, so de-duplication and parent-first sorting are important. Internal propagation control has strict validation and uses the control `critical` bit as a local unchanged marker, which is subtle. `can_write_owner()` computes `default_owner` but then checks `security_token_is_sid(security_token, owner_sid)` again instead of comparing with `default_owner`, which deserves scrutiny. Any failure during prepare commit aborts the transaction.

Test signals: selftest registration references LDAP security descriptor Python tests and general `samba.tests.security_descriptors`. High-value coverage includes add with/without explicit SD, invalid owner SID, SD flags search filtering, modify owner/group/DACL/SACL subsets, rejected descriptor delete, rename propagation, recursive inherited ACE updates, replication-triggered extended propagation de-duplication, and rollback cleanup of transaction maps.

# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/dirsync.c

Purpose: `dirsync.c` implements Samba's LDAP DirSync control handling for DSDB searches. It validates DirSync controls, upgrades/adjusts the underlying search, filters returned attributes and entries based on USNs, replication metadata, linked-value metadata, and up-to-dateness vectors, and returns a refreshed DirSync cookie.

Important APIs, types, and functions: `struct dirsync_context` holds request/module, default attribute count, highest/from-request USN, cursor vector, extended-DN mode, incremental linked-value mode, local-only/partial flags, functional level, invocation ID, schema, and NC root. `dirsync_ldb_search()` is the search hook. `dirsync_filter_entry()` is the large per-entry filtering engine. `dirsync_create_vector()` builds the cookie up-to-dateness vector. `dirsync_search_callback()` handles entries, referrals, and final cookie/control creation. `dirsync_ldb_init()` registers `LDB_CONTROL_DIRSYNC_OID`.

Control flow: searches without DirSync pass through. DirSync requests must be critical and rooted at an NC head. If object-security mode is absent, the module checks `GUID_DRS_GET_CHANGES` against the NC root security descriptor, preserving Windows-like error behavior while not using the result for detailed attribute filtering. Requested attrs are copied and augmented with needed internal attrs such as `uSNChanged`, `replPropertyMetaData`, `instanceType`, `objectGUID`, and `parentGUID`; `*` or null attrs also request full SD flags. Extended-DN, reveal-internals, show-recycled, and show-deleted controls are added as needed. Cookies are unmarshalled to determine `fromreqUSN`, local-only behavior, and cursor suppression. The downstream search is forced to subtree scope and optionally filters `uSNChanged >= fromreqUSN + 1`.

State and persistence: the module persists no server-side state. Client progress is encoded in the returned `ldapControlDirSyncCookie`, which stores time, high-watermark USNs, current invocation ID, and optionally an up-to-dateness vector derived from `replUpToDateVector` on the NC root. Per-request `highestUSN` advances while entries are emitted.

Dependencies and integration points: DirSync depends on ldb LDAP controls, DSDB schema/attribute metadata, replication metadata NDR blobs (`replPropertyMetaDataBlob`, `replUpToDateVectorBlob`, `ldapControlDirSyncCookie`), linked-attribute extended DN components (`RMD_LOCAL_USN`, `RMD_INVOCID`, `RMD_FLAGS`, `RMD_ORIGINATING_USN`), ACL extended rights (`GUID_DRS_GET_CHANGES`), sequence numbers, invocation IDs, and ranged-results behavior that observes the control's critical bit.

Risks and edge cases: filtering is complex and security-sensitive because it decides what changed data is disclosed. Backlinks, constructed/non-replicated attrs, deleted links, referrals, NC roots, RDN attributes, and incremental linked values all have special paths. Cookie parsing failure maps to unsupported critical extension. The module ignores some advertised flags (`ANCESTORS_FIRST_ORDER`, `PUBLIC_DATA_ONLY`) and marks partial false unconditionally, so paging/size-limit behavior should be reviewed with surrounding modules. Attribute filtering relies on replicated metadata being present and parseable; missing metadata on inaccessible deleted objects is treated specially. Timing/commentary around filtered attribute sets notes a known limitation.

Test signals: selftest registers `samba4.ldap.dirsync.python(ad_dc_ntvfs)` via `dsdb/tests/python/dirsync.py`. Strong tests should cover first sync, cookie resume, cross-invocation vectors, object-security flag behavior, insufficient rights error selection, null/`*`/specific attrs, incremental linked-value add/delete ranges, deleted/recycled objects, referrals to other naming contexts, malformed cookies, and interaction with ranged results.

# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/dns_notify.c

Purpose: `dns_notify.c` is an ldb transaction module that detects changes to DNS zone objects under Samba's MicrosoftDNS containers and notifies the internal DNS server to reload zones after a successful transaction. It covers direct database changes and replicated inbound changes that create, modify, or delete `dnsZone` objects.

Important APIs, types, and functions: `struct dns_notify_private` stores a linked list of watched base DNs and a transaction-scoped `reload_zones` flag. `struct dns_notify_watched_dn` stores each watched container. `dns_notify_add()`, `dns_notify_modify()`, and `dns_notify_delete()` detect relevant changes. `dns_notify_start_trans()`, `dns_notify_end_trans()`, and `dns_notify_del_trans()` manage transaction state. `dns_notify_dnssrv_send()` creates an `imessaging` client, binds to IRPC service `dnssrv`, and sends `dcerpc_dnssrv_reload_dns_zones_r_send()`. `dns_notify_dnssrv_done()` receives completion and cleans up.

Control flow: init builds watched DNs for `CN=MicrosoftDNS,CN=System,<domain>`, `CN=MicrosoftDNS,DC=DomainDnsZones,<forest>`, and `CN=MicrosoftDNS,DC=ForestDnsZones,<forest>`. Add checks whether the new DN is below a watched container and whether the structural object class is `dnsZone`; modify/delete first search the existing object class, then set `reload_zones` if it is a zone. Relax-control and special-DN requests pass through. At transaction start/rollback the reload flag is cleared. At successful transaction end, if the flag is set, the module asynchronously sends an IRPC reload request to the DNS server.

State and persistence: watched DNs are module-private state. `reload_zones` is transient transaction state. No ldb data is changed by this module; the only side effect is an asynchronous reload notification after commit. Failed notification logs debug output but does not roll back the committed database transaction.

Dependencies and integration points: the module uses DSDB schema lookup, structural object-class resolution, DSDB module search helpers with recycled/internal/storage-format flags, ldb transaction hooks, `imessaging_client_init()`, `irpc_binding_handle_by_name()`, generated DNSSRV IRPC client stubs, loadparm, and Samba event context. It is tightly coupled to Samba AD DNS partition layout.

Risks and edge cases: notification is best-effort, so DNS may be stale if messaging setup, IRPC binding, send, or async completion fails. The code skips requests with `LDB_CONTROL_RELAX_OID`. In `dns_notify_modify()` and `dns_notify_delete()`, the watched-base comparison references `req->op.add.message->dn` even though the active operation is modify/delete; this union-field access is a serious correctness/crash risk and could prevent reloads. The module notifies once per transaction regardless of how many zones changed. Watched DNs are constructed unconditionally; absent DNS partitions are not validated at init.

Test signals: coverage is likely integration-level through DNS server/database tests rather than direct unit tests. Useful tests include add/modify/delete of `dnsZone` in all three watched containers, non-zone DNS child changes that should not reload, relaxed operations, transaction rollback, multiple changes in one transaction, missing/unreachable `dnssrv`, and the modify/delete watched-DN access path.

# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/dsdb_notification.c

Purpose: `dsdb_notification.c` implements a simplified LDAP notification control for DSDB searches. Rather than holding a fully asynchronous persistent search, it stores a USN cookie in the request control and expects the LDAP layer/client to retry periodically; each subsequent call returns objects whose `uSNChanged` is greater than the previously observed high-water mark.

Important APIs, types, and functions: `struct dsdb_notification_cookie` holds `known_usn`. `dsdb_notification_verify_tree()` constrains accepted filters to Windows-compatible broad filters, allowing present tests on common attributes such as `objectClass`, `objectGUID`, `distinguishedName`, and `name`. `dsdb_notification_filter_search()` manages cookie setup and builds the USN search. `dsdb_notification_search()` detects `LDB_CONTROL_NOTIFICATION_OID`. `dsdb_notification_init()` registers the control.

Control flow: special DN searches and searches without the notification control pass through. Notification searches must have a parse tree accepted by `dsdb_notification_verify_tree()`. On the first call, the module allocates a cookie in `control->data`, marks the control non-critical/done, records the current highest sequence number, and returns success without entries. On later calls, it builds a replacement filter `uSNChanged > previous_known_usn`, updates `known_usn` to the current highest sequence number, and forwards a downstream search with the original base, scope, attrs, and controls.

State and persistence: no server-side persistent state exists. Progress is stored in the in-memory control data object across retries within the caller's control handling. The DB state consulted is only `LDB_SEQ_HIGHEST_SEQ` and `uSNChanged`.

Dependencies and integration points: the module depends on ldb parse trees, ldb sequence numbers, `LDB_CONTROL_NOTIFICATION_OID`, `dsdb_module_werror()` with `WERR_DS_NOTIFY_FILTER_TOO_COMPLEX`, and normal ldb search callback behavior through `dsdb_next_callback`.

Risks and edge cases: this is intentionally not a true async persistent search, so correctness depends on periodic retries by the LDAP server/client layer. The generated parse-tree uses `LDB_OP_GREATER` while comments describe `>=`, so boundary semantics depend on `known_usn + 1` formatting. Complex filters are rejected or, for OR, accepted if one branch is broad enough. `talloc_move(down_req, &filter_usn)` occurs before `down_req` is assigned, which is suspicious even if harmless in practice. If the caller loses control data, the next request restarts from the current high-water mark and misses older changes.

Test signals: direct test registration was not obvious in the searched selftest snippets, so this is probably covered through LDAP notification integration. Useful tests include first-call empty result with cookie creation, second-call results after modifications, rejected complex filters with `WERR_DS_NOTIFY_FILTER_TOO_COMPLEX`, OR/AND validation behavior, special-DN pass-through, and loss/reinitialization of cookie state.

# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/encrypted_secrets.c

Purpose: `encrypted_secrets.c` encrypts configured DSDB secret attributes before they are written to disk and decrypts them on search results. It mitigates disclosure of `sam.ldb` content and memory-read exposure by wrapping secret values in NDR `EncryptedSecret` blobs using AES-128-GCM through GnuTLS.

Important APIs, types, and functions: `struct es_data` stores whether encryption is active, the key array, and GnuTLS algorithm ID. Key handling is in `get_key_directory()` and `load_keys()`. Encryption helpers include `makeEncryptedSecret()`, `makePlainText()`, `gnutls_encrypt_aead()`, `encrypt_value()`, `encrypt_element()`, and `encrypt_secret_attributes()`. Decryption helpers include `check_header()`, `gnutls_get_algorithm()`, `gnutls_decrypt_aead()`, `decrypt_value()`, `decrypt_element()`, and `decrypt_secret_attributes()`. Ldb hooks are `es_search()`, `es_callback()`, `es_add()`, `es_modify()`, `es_delete()`, `es_rename()`, and `es_init()`.

Control flow: init checks `@SAMBA_DSDB` for `SAMBA_ENCRYPTED_SECRETS_FEATURE`; if present, it loads `encrypted_secrets.key` from the same directory as `sam.ldb` and enables encryption. Add/modify hooks pass through when encryption is disabled or no secret attrs are present. Otherwise they copy the message, encrypt each secret attribute value, rebuild the downstream add/modify request, and forward it. Search wraps results with a callback; each entry has secret attributes decrypted before being sent upward. Delete and rename pass through unchanged.

State and persistence: the persistent artifact is `encrypted_secrets.key`, a 16-byte AES key stored beside the database. Secret attribute values are persisted as NDR `EncryptedSecret` structures with magic/version/algorithm header, IV, authenticated associated data over the header, and ciphertext/tag. Missing or zero-length key files disable encryption/decryption with warnings; invalid short reads fail init. Existing encrypted values require the same key to decrypt.

Dependencies and integration points: this module depends on DSDB secret attribute lists, `@SAMBA_DSDB` required feature metadata, ldb module wrapping, NDR structures from `drsblobs`, GnuTLS AEAD APIs, ldb URL opaque `ldb_url`, and Samba data-blob/talloc helpers. It should be ordered so writes are encrypted before reaching storage and reads are decrypted before higher layers inspect attributes.

Risks and edge cases: key storage beside `sam.ldb` is explicitly a mitigation rather than strong key isolation. If the feature is required but the key is missing or zero length, the module disables encryption/decryption, which can expose plaintext or make encrypted data unreadable depending on existing DB state. AEAD IV generation depends on `gnutls_rnd()`. Header/version/algorithm mismatches fail decryption rather than treating data as plaintext. Error comments note messages can be inconsistent after partial encryption/decryption failure, though rebuilt requests reduce caller mutation. Memory ownership is delicate because encrypted/decrypted elements are inserted into copied ldb messages.

# sources/user-network-fs/samba/source4/dsdb/samdb/ldb_modules/extended_dn_in.c

Purpose: `extended_dn_in.c` is an input-side ldb module that resolves extended DN syntax such as `<GUID=...>`, `<SID=...>`, and `<WKGUID=...>` into normal database DNs before search/modify/delete/rename processing. It also rewrites DN-valued search filter terms so filters against linked DN attributes use canonical extended-linearized DNs.

Important APIs, types, and functions: `struct extended_search_context` carries original request, rewritten parse tree, candidate base DN, input DN, and WKGUID prefix. `extended_base_callback()` resolves the base extended DN and builds the real downstream operation. `extended_final_callback()` forwards downstream replies. `ldb_dn_match_allowed()` enforces stricter LDAP-facing syntax for untrusted requests. Filter rewriting is handled by `struct extended_dn_filter_ctx`, `set_parse_tree_false()`, `extended_dn_filter_callback()`, and `extended_dn_fix_filter()`. `extended_dn_in_fix()` orchestrates base-DN and filter rewriting for search/modify/delete/rename hooks. Module init registers both `extended_dn_in_openldap` and `extended_dn_in`.

Control flow: each operation calls `extended_dn_in_fix()` with the operation DN. Search requests first walk the filter in test mode; if a DN-valued equality/transitive term needs resolution, the parse tree is shallow-copied and rewritten. If the operation DN has no extended component, the original or filter-rewritten request is passed down. Otherwise, the module validates extended-DN shape for untrusted requests, prioritizes GUID lookup over SID lookup, handles WKGUID by searching `wellKnownObjects`/`otherWellKnownObjects` under the specified base, and performs an internal system search with extended-DN display. The base callback rejects duplicate matches, maps no match to `NO_SUCH_OBJECT`, and then builds the original operation with the resolved DN.

State and persistence: no persistent state is kept. All resolution state is request-scoped talloc data. The module reads schema metadata and database objects to canonicalize DNs but does not modify DB contents directly.

Dependencies and integration points: it uses ldb extended DN APIs, DSDB schema attributes with `dn_format == DSDB_NORMAL_DN`, matching rule `SAMBA_LDAP_MATCH_RULE_TRANSITIVE_EVAL`, always-false matching rule `SAMBA_LDAP_MATCH_ALWAYS_FALSE`, DSDB search flags for system/extended-DN/deleted/recycled/DBCHECK behavior, all-partition searches for GUID/SID, and WKGUID attributes `wellKnownObjects` and `otherWellKnownObjects`. The OpenLDAP variant avoids certain one-way-link transformations.

Risks and edge cases: resolving by SID can be ambiguous, so GUID is prioritized; duplicate matches intentionally return `NO_SUCH_OBJECT`. Untrusted LDAP requests with multiple extended components are rejected or rewritten to always false. Treating confidential indexed DN attributes as unindexed avoids timing side channels, but changes search behavior. Filter parse-tree shallow copies and in-place value replacement require careful ownership. WKGUID parsing depends on a comma separator and `B:32:<guid>:` prefix matching. Failed internal lookups often return success without rewriting filter terms, which can make malformed DN filters behave as no-match instead of hard failure.

Test signals: useful coverage is typically LDAP behavior tests around extended DN searches and link filters. Cases should include GUID/SID/WKGUID base resolution, duplicate SID matches, untrusted invalid multi-component extended DNs, deleted/recycled controls, DBCHECK behavior, DN-valued equality filters, transitive-eval filters, confidential indexed DN attributes, OpenLDAP module variant behavior, and modify/delete/rename using extended old DNs.
