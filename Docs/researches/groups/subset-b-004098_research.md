# sources/distributed-fs/ceph-client/drivers/media/i2c/ov5648.c

Purpose: implements a V4L2 sub-device driver for the OmniVision OV5648 raw Bayer image sensor on an I2C/SCCB control bus with MIPI CSI-2 output. It supports a 24 MHz external clock, optional external AVDD plus mandatory DVDD/DOVDD supplies, optional reset and powerdown GPIOs, and a single source media pad. The driver exposes six fixed sensor modes from 2592x1944 down to 640x480 and two media bus codes, `MEDIA_BUS_FMT_SBGGR8_1X8` and `MEDIA_BUS_FMT_SBGGR10_1X10`.

Important APIs, types, and functions: the core state is split across `struct ov5648_sensor`, `struct ov5648_state`, `struct ov5648_ctrls`, and `struct ov5648_mode`. `ov5648_read()`, `ov5648_write()`, `ov5648_write_sequence()`, and `ov5648_update_bits()` are the low-level I2C helpers for 16-bit register addresses and 8-bit values. Sensor bring-up flows through `ov5648_sensor_power()`, `ov5648_sensor_init()`, `ov5648_sw_reset()`, `ov5648_chip_id_check()`, `ov5648_mipi_configure()`, `ov5648_isp_configure()`, and `ov5648_black_level_configure()`. Mode programming is computed rather than table-driven: `ov5648_mode_configure()` writes crop, output size, offsets, HTS/VTS, binning/subsample increments, and PLL settings via `ov5648_mode_pll1_configure()` and `ov5648_mode_pll2_configure()`. V4L2 integration is provided by `ov5648_s_stream()`, `ov5648_get_fmt()`, `ov5648_set_fmt()`, frame interval/size enumeration callbacks, runtime PM callbacks, and `module_i2c_driver()`.

Control flow: probe parses the first fwnode graph endpoint as CSI-2 D-PHY, allocates endpoint data, obtains GPIOs/regulators/clock, validates the 24 MHz XVCLK rate, initializes the subdev/media entity, initializes controls, initializes default state to the first mode and 8-bit Bayer code, enables runtime PM in the suspended state, and registers the sensor subdev asynchronously. Runtime resume powers rails and clock, performs sensor reset and identity check, applies global pad/MIPI/ISP/BLC setup, configures the current mode, restores V4L2 controls, and restarts streaming if the logical state says streaming was active. Stream-on calls `pm_runtime_resume_and_get()`, clears software standby, and marks `state.streaming`; stream-off writes standby and releases runtime PM. Format setting rejects changes while streaming, selects a supported mbus code and nearest mode, updates TRY state or active state, and can immediately program hardware if runtime PM says the device is already active.

State and persistence behavior: persistent software state is the selected `mode`, `mbus_code`, `streaming` flag, parsed endpoint, and V4L2 controls. Register contents are treated as volatile across power loss; resume replays initialization, mode programming, and control setup. Link frequency and pixel rate controls are read-only but are recalculated when format changes using PLL configuration, data-lane count, and bits per sample. Exposure, gain, and white-balance controls use V4L2 auto clusters; exposure and gain are volatile while auto algorithms may update the sensor. There is no filesystem persistence.

Dependencies and integration points: depends on Linux I2C, clocks, GPIO descriptors, regulators, runtime PM, media controller, V4L2 subdev/control/fwnode APIs, and OF graph matching for `ovti,ov5648`. CSI-2 lane count and endpoint link frequencies are taken from firmware. It integrates with receiver bridge drivers through async subdev registration and source-pad media links.

Risks: `ov5648_read()` and `ov5648_write()` treat any nonnegative short I2C transfer as success; robust code normally checks exact byte counts. The regulator/GPIO power sequence is explicitly noted as untested. Active format changes may write hardware before stream-on if the device is runtime-active, so control and PM ordering bugs can surface outside the streaming path. Link-frequency mismatches are logged in `ov5648_state_mipi_configure()` but do not abort when the internal menu or endpoint frequencies are missing the computed value. Frame interval TRY-state support is marked FIXME. The driver has many hand-coded register bitfield helpers, making PLL, crop, binning, and Bayer-order regressions likely if mode definitions are changed without hardware validation.

Test signals: useful checks are probe with correct and incorrect chip IDs, endpoint lane/link-frequency validation, runtime suspend/resume while streaming and idle, `v4l2-ctl --list-subdev-mbus-codes`, frame-size and frame-interval enumeration, stream-on/off at every mode and both 8-bit/10-bit formats, test pattern enablement, manual/auto exposure and gain transitions, H/V flip, and media link validation with a CSI-2 receiver. Hardware capture should verify frame dimensions, Bayer order, pixel rate metadata, and no stale register state after runtime PM cycling.

# sources/distributed-fs/ceph-client/drivers/media/i2c/ov5670.c

Purpose: implements the OmniVision OV5670 5MP raw Bayer V4L2 sensor driver. It targets a 19.2 MHz external clock, three regulators (`avdd`, `dvdd`, `dovdd`), optional powerdown and reset GPIOs, two-lane MIPI CSI-2, and a GRBG 10-bit output format. It provides six table-defined modes: 2592x1944, 2560x1440, 1296x972, 1280x720, 648x486, and 640x360, all based on one 840 Mbps-per-lane link-frequency configuration.

Important APIs, types, and functions: `struct ov5670` holds the V4L2 subdev, media pad, parsed endpoint, controls, current mode, clock, regulators, GPIOs, mutex, and one-time `identified` flag. Mode metadata lives in `struct ov5670_mode`; register sequences use `struct ov5670_reg` and `struct ov5670_reg_list`; PLL/link setup uses `struct ov5670_link_freq_config`. Register access is through `ov5670_read_reg()`, `ov5670_write_reg()`, `ov5670_write_regs()`, and `ov5670_write_reg_list()`. Control paths are `ov5670_set_ctrl()`, `ov5670_update_digital_gain()`, and `ov5670_enable_test_pattern()`. Streaming paths are `ov5670_start_streaming()`, `ov5670_stop_streaming()`, and `ov5670_set_stream()`. Firmware and media integration are handled by `ov5670_probe()`, `ov5670_init_controls()`, `ov5670_init_state()`, `ov5670_get_selection()`, `ov5670_runtime_resume()`, and `ov5670_runtime_suspend()`.

Control flow: probe validates XVCLK, initializes the I2C subdev and internal state ops, obtains regulators/GPIOs, parses a fwnode graph endpoint while defaulting CSI-2 lanes to two, optionally powers and identifies the sensor if ACPI reports D0, initializes the mutex and default max-resolution mode, creates controls, initializes media entity state, enables runtime PM, registers the async sensor subdev, and idles the device. Stream-on holds the mutex, resumes runtime PM, identifies the module if not already identified, issues software reset, writes the link-frequency PLL sequence, writes the current mode register table, configures MIPI lane control, applies all controls with `__v4l2_ctrl_handler_setup()`, and writes `OV5670_MODE_STREAMING`. Stream-off writes standby and drops runtime PM, returning success even if standby write fails.

State and persistence behavior: the selected mode is stored in `cur_mode`; TRY formats and crops live in V4L2 subdev state; current V4L2 controls are cached by the control framework and replayed at stream-on. The `identified` flag prevents repeated chip ID reads after a successful check. `VBLANK` updates the exposure range, and active format changes update `link_freq`, `pixel_rate`, `vblank`, and read-only `hblank` limits. No sensor registers are assumed persistent after power loss because stream-on replays PLL, mode, MIPI, and control state.

Dependencies and integration points: depends on I2C transfer helpers, unaligned big-endian conversion, ACPI/OF matching (`INT3479`, `ovti,ov5670`), runtime PM, V4L2 controls/events/fwnode, media entity links, clocks, GPIOs, and regulator bulk APIs. `g_skip_frames` reports two initial frames to discard. The firmware graph is important; missing endpoint returns `-EPROBE_DEFER` because some IPU3 systems rely on a bridge driver to create the endpoint.

Risks: only one mbus code is supported, so flips are not exposed and Bayer-order changes from physical orientation must be handled elsewhere. The endpoint parser is fed a preinitialized two-lane value, but the driver does not strongly validate all endpoint link frequencies against its menu beyond the parsed mode setup. Large static mode tables are hard to audit and can diverge from `supported_modes` metadata. `ov5670_stop_streaming()` masks standby-write failures. `ov5670_set_pad_format()` does not reject active format changes while streaming; correctness relies on the pipeline not changing active mode during stream. Short I2C writes are detected, but the register table programming has no rollback on partial failure.

Test signals: verify probe on ACPI and OF systems, endpoint deferral with bridge-created nodes, chip ID read caching, runtime PM power sequencing, `v4l2-compliance` subdev pad operations, all six frame-size enumerations, crop/native/bounds selections, `g_skip_frames`, stream-on/off around every mode, exposure/vblank range coupling, digital gain writing to all RGB channels, test pattern enable/disable, and data capture for GRBG10 dimensions and frame timing.

# sources/distributed-fs/ceph-client/drivers/media/i2c/ov5675.c

Purpose: implements an OV5675 raw Bayer V4L2 sub-device driver for a 19.2 MHz clock, two-lane CSI-2, 10-bit GRBG output, reset GPIO, and `avdd`/`dovdd` supplies. It supports two table-driven modes, 2592x1944 and 1296x972, both using a 900 Mbps link frequency and a computed pixel-rate model.

Important APIs, types, and functions: `struct ov5675` contains the subdev, media pad, control handler, clock, reset GPIO, regulator bulk array, key controls, current mode, mutex, and `identified` flag. `struct ov5675_mode`, `struct ov5675_reg_list`, and `struct ov5675_link_freq_config` describe supported modes and PLL tables. Register access uses `ov5675_read_reg()`, `ov5675_write_reg()`, and `ov5675_write_reg_list()` with big-endian packed transfers. Timing helpers `to_pixel_rate()` and `to_pixels_per_line()` derive V4L2 pixel-rate and hblank metadata. Controls are handled by `ov5675_set_ctrl()`, `ov5675_update_digital_gain()`, `ov5675_test_pattern()`, `ov5675_set_ctrl_hflip()`, and `ov5675_set_ctrl_vflip()`. Hardware validation is concentrated in `ov5675_get_hwcfg()`, while stream and PM paths are `ov5675_start_streaming()`, `ov5675_stop_streaming()`, `ov5675_set_stream()`, `ov5675_power_on()`, and `ov5675_power_off()`.

Control flow: probe allocates state, validates hardware configuration from fwnode graph, initializes the subdev, powers the device, optionally identifies it if ACPI says the device is in D0, initializes the mutex/default mode/controls, configures media entity and internal open callback, registers the async sensor subdev, enables runtime PM, and idles the device. Stream-on resumes runtime PM, identifies the module if needed, writes the selected PLL register list, writes the selected mode list, replays V4L2 controls, and sets mode-select to streaming. Stream-off writes standby and releases PM. Format setting chooses the nearest supported mode, updates TRY state or active `cur_mode`, and refreshes link frequency, pixel rate, vblank range/default, and hblank range/default.

State and persistence behavior: software state is `cur_mode`, cached controls, and the `identified` flag. Digital gain updates are grouped with the sensor's group-access registers: start, write manual red/green/blue gains, end, and launch. Controls are not written while runtime PM says the device is inactive; they are replayed on stream-on. The driver does not persist register settings across power cycles except through V4L2 control cache and mode metadata.

Dependencies and integration points: uses V4L2 fwnode parsing and fwnode device properties, I2C, GPIO descriptors, regulator bulk APIs, runtime PM, ACPI and OF matching (`OVTI5675`, `ovti,ov5675`), media entity link validation, and V4L2 subdev pad/video operations. `ov5675_get_hwcfg()` enforces two CSI-2 data lanes, presence of endpoint link frequencies, and exact support for every link frequency in `link_freq_menu_items`.

Risks: `ov5675_set_ctrl()` ignores return values from HFLIP/VFLIP helper calls, so flip I2C failures can be reported as success. Active format changes are not rejected while streaming. `ov5675_get_selection()` only supports ACTIVE selections, so TRY-state crop queries fail. The VBLANK write adds an unexplained `+ 10` to `height + vblank`, which is easy to regress without sensor timing knowledge. Power-on is called unconditionally during probe before runtime PM setup, then PM state is reconciled later; error paths need careful validation. The driver only supports one Bayer code and two modes, so additional sensor capabilities would require coordinated changes to mode tables, timing controls, and firmware validation.

Test signals: validate fwnode rejection for wrong lane counts and missing/unsupported link frequencies, probe power sequencing, chip ID mismatch handling, stream-on/off for both modes, format negotiation to nearest mode, `v4l2-compliance` pad ops including TRY selection limitations, exposure/vblank coupling including the `+ 10` VTS behavior, group-held digital gain updates, H/V flip error propagation tests, test pattern modes, and captured GRBG10 frame geometry after runtime suspend/resume.

# sources/distributed-fs/ceph-client/drivers/media/i2c/ov5693.c

Purpose: implements a low-level V4L2 driver for OV5693 raw Bayer sensors using the kernel CCI/regmap helper API rather than hand-written I2C byte packing. It supports a 19.2 MHz clock, two CSI-2 lanes, a 419.2 MHz link frequency, 10-bit SBGGR output, runtime PM with autosuspend, crop/format selection, horizontal and vertical binning, and a single source pad.

Important APIs, types, and functions: `struct ov5693_device` owns the regmap, lock, GPIOs, regulators, clock, active `mode` structure, subdev, pad, and nested control bundle. Register definitions use `CCI_REG8/16/24`. `ov5693_global_regs` is the sensor-wide initialization table. Controls are implemented by `ov5693_s_ctrl()`, `ov5693_g_volatile_ctrl()`, and helpers for exposure, analogue gain, digital RGB gain, flips, VTS, and test pattern. Mode programming is handled by `ov5693_mode_configure()`, while power and initialization flow through `ov5693_sensor_powerup()`, `ov5693_sensor_powerdown()`, `ov5693_sw_reset()`, `ov5693_sensor_init()`, `ov5693_sensor_resume()`, and `ov5693_sensor_suspend()`. Pad operations are richer than many adjacent drivers: `ov5693_set_selection()` changes crop, `ov5693_set_fmt()` derives output size and binning ratio from crop, and enumeration exposes full or half crop size.

Control flow: probe initializes CCI regmap, validates firmware endpoint requirements, creates the mutex, initializes the I2C subdev, obtains clock/GPIOs/regulators, sets default crop and format, initializes controls, initializes media entity pads, powers the sensor even before runtime PM is enabled, verifies chip ID, enables runtime PM with a held reference, registers the async subdev, and then enables 1 second autosuspend. Runtime resume powers rails and clock, resets the sensor, writes global registers, applies current crop/format/binning, and leaves streaming disabled. Stream-on resumes PM, replays controls, and writes the stream register. Stream-off writes stop and drops PM. Active crop/format changes update in-memory mode and control ranges; hardware is reprogrammed on the next resume/init path rather than by direct writes in `set_fmt()`.

State and persistence behavior: active state includes crop rectangle, output frame format, binning flags, odd increment values, computed VTS, and V4L2 controls. VBLANK dynamically adjusts the exposure maximum. Exposure and gain have volatile read helpers, although they are wired to `V4L2_CID_EXPOSURE_ABSOLUTE` and `V4L2_CID_AUTOGAIN` cases while the created controls are `V4L2_CID_EXPOSURE` and `V4L2_CID_ANALOGUE_GAIN`, making the volatile path suspicious. Register state is treated as volatile across PM; resume replays global and mode state. There is no durable persistence outside kernel memory.

Dependencies and integration points: depends on CCI regmap, I2C, clocks, GPIOs, regulators, ACPI/OF matching (`INT33BE`, `ovti,ov5693`), V4L2 controls and fwnode properties, media entity pads, and firmware graph endpoint data. `ov5693_check_hwcfg()` defers probe if a bridge-created endpoint is not ready, enforces two lanes, and requires the 419.2 MHz link frequency.

Risks: `ov5693_get_fmt()` returns active mode format unconditionally and ignores TRY state, unlike `set_fmt()` and crop helpers. The volatile control callback appears to check control IDs that are not created by `ov5693_init_controls()`. `ov5693_set_fmt()` and `ov5693_set_selection()` do not explicitly reject active changes while streaming; mode memory and control ranges can change while hardware still runs an older configuration. The clock-rate mismatch only warns rather than fails, even though timing constants assume 19.2 MHz. The format calculation permits only crop size or 2x binned output; unsupported dimensions are silently rounded to that model. Error handling relies on CCI's accumulated `ret` pattern, so individual register failures are not identified.

Test signals: run fwnode validation for endpoint deferral, wrong lane count, and missing link frequency; verify chip ID detection; exercise crop and format TRY/ACTIVE paths; run `v4l2-compliance` for get_fmt TRY behavior; stream after changing crop to full and half size; confirm hblank/vblank/exposure updates; test runtime autosuspend/resume while idle and streaming; validate H/V flip, RGB digital gain, analogue gain, exposure, and test pattern writes; capture SBGGR10 frames to confirm dimensions, binning, and Bayer order.

# sources/distributed-fs/ceph-client/drivers/media/i2c/ov5695.c

Purpose: implements the OmniVision OV5695 raw Bayer V4L2 I2C sensor driver for a 24 MHz external clock, reset GPIO, three supplies (`avdd`, `dovdd`, `dvdd`), two-lane CSI-2, and SBGGR10 output. It provides five fixed modes: 2592x1944, 1920x1080, 1296x972, 1280x720, and 640x480, with frame-rate metadata from 30 to 120 fps and a single 420 MHz link-frequency control.

Important APIs, types, and functions: `struct ov5695` contains the I2C client, clock, reset GPIO, supplies, subdev, media pad, controls, mutex, and current mode. Mode and register data are represented by `struct ov5695_mode` and `struct regval`; global and per-mode arrays are terminated by `REG_NULL`. Low-level access is `ov5695_write_reg()`, `ov5695_write_array()`, and `ov5695_read_reg()`. Format selection uses `ov5695_find_best_fit()` and `ov5695_set_fmt()`. Streaming uses `__ov5695_start_stream()`, `__ov5695_stop_stream()`, and `ov5695_s_stream()`. Power sequencing is split into `__ov5695_power_on()`, `__ov5695_power_off()`, and runtime PM wrappers. Controls are initialized by `ov5695_initialize_controls()` and applied in `ov5695_set_ctrl()`.

Control flow: probe allocates state, sets the default max-resolution mode, obtains a legacy XVCLK at 24 MHz, warns rather than fails on clock-rate mismatch, requires reset GPIO, gets regulators, initializes mutex/subdev/controls, powers the device, checks the 24-bit sensor ID, initializes media entity pads, registers the async sensor subdev, marks runtime PM active, enables PM, and idles the device. Stream-on resumes PM, writes global registers, writes the current mode table, replays controls, and writes mode-select streaming. Stream-off writes standby and releases PM. Active format setting chooses the nearest mode by absolute width/height distance and updates hblank/vblank control ranges; it does not immediately program registers.

State and persistence behavior: persistent software state is the current mode plus V4L2 control cache. Register contents are replayed on every stream-on from global and mode tables plus controls, so power loss does not need hardware retention. VBLANK updates exposure maximum. Digital gain is split across low and high registers, but the implementation writes the low register and then overwrites `ret` with the high-register write result, which can hide low-register failures. There is no filesystem or NVM persistence.

Dependencies and integration points: depends on I2C, V4L2 subdev/control/media APIs, runtime PM, GPIO descriptors, ordered regulator enables/disables, clock helpers, OF matching for `ovti,ov5695`, and media pipeline async registration. It uses `devm_v4l2_sensor_clk_get_legacy()` to support older clock bindings. Link frequency and pixel rate are exposed as read-only controls, but endpoint validation is minimal compared with newer drivers in the same directory.

Risks: `ov5695_check_sensor_id()` returns `ret` when the ID mismatches; if the I2C read succeeded but the ID was wrong, `ret` is 0 and the probe may incorrectly continue after logging an unexpected ID. `#define V4L2_CID_DIGITAL_GAIN V4L2_CID_GAIN` aliases digital gain to the generic gain ID if the symbol is absent, which can affect userspace semantics. Active format changes are not blocked while streaming. The 1296x972 mode table includes global reset/start-stream-like entries and even a `0x0100, 0x01` write before the stream-on path, unlike the other mode tables. There is no firmware endpoint lane/link-frequency validation. Ordered regulator operations are manual, so partial failure paths and disable ordering are important. The clock-rate mismatch is only a warning despite hard-coded timings.

Test signals: verify wrong-chip-ID behavior specifically for successful reads with bad IDs, probe with missing reset GPIO and regulator failures, stream all five modes, inspect whether the 1296x972 mode table prematurely starts streaming, run format negotiation nearest-fit cases, validate exposure/vblank and digital-gain high/low register writes with injected I2C failures, confirm runtime PM power cycling, test pattern selection, and capture SBGGR10 frames with expected dimensions and frame timing.

# sources/distributed-fs/ceph-client/drivers/media/i2c/ov6211.c

Purpose: implements an OmniVision OV6211 monochrome/global-shutter-style sensor driver using V4L2 subdev streams APIs and CCI regmap access. It supports a single 400x400 mode at 120 fps, 8-bit greyscale `MEDIA_BUS_FMT_Y8_1X8`, a 24 MHz master clock, one 480 MHz link-frequency entry, reset GPIO, three supplies (`avdd`, `dovdd`, `dvdd`), and one source media pad.

Important APIs, types, and functions: `struct ov6211` holds the device, CCI regmap, clock, reset GPIO, supplies, subdev, pad, controls, and saved `pre_isp` register value. The only mode is described by `struct ov6211_mode` and `ov6211_400x400_120fps_mode`. Controls are built by `ov6211_init_controls()` and applied by `ov6211_set_ctrl()`, with `ov6211_set_test_pattern()` preserving non-test-pattern bits from the saved pre-ISP register. Streaming uses the modern pad stream callbacks `ov6211_enable_streams()` and `ov6211_disable_streams()`, with `.s_stream = v4l2_subdev_s_stream_helper`. Firmware and power setup are handled by `ov6211_check_hwcfg()`, `ov6211_power_on()`, `ov6211_power_off()`, `ov6211_identify_sensor()`, and `ov6211_probe()`.

Control flow: probe initializes the subdev and CCI regmap, obtains and validates XVCLK when a nonzero rate is reported, checks endpoint link frequencies via `v4l2_link_freq_to_bitmap()`, obtains reset GPIO and regulators, powers the sensor to read chip ID and the current pre-ISP register, initializes controls, assigns the subdev state lock to the control handler lock, sets internal state ops, initializes pads, finalizes subdev active state, enables runtime PM, registers asynchronously, then enables autosuspend and idles the device. Stream enable resumes PM, writes software reset, writes the single mode's CCI register sequence, replays controls, and writes mode-select streaming. Stream disable writes standby and schedules autosuspend.

State and persistence behavior: V4L2 subdev state stores the current pad format, but because there is only one mode, format setting always resolves to 400x400 Y8. Controls cache vblank, exposure, analogue gain, and test-pattern values; they are skipped while runtime PM is inactive and replayed on stream enable. `pre_isp` is captured once during probe and used as the base value for test-pattern toggling, preserving unrelated bits across control changes. Register state is not expected to survive suspend; stream enable rewrites the full mode table and controls.

Dependencies and integration points: depends on CCI regmap, I2C, V4L2 stream-aware subdev helpers, media entity link validation, fwnode endpoint parsing, `v4l2_link_freq_to_bitmap()`, runtime PM with autosuspend, clocks, GPIOs, regulators, and OF matching for `ovti,ov6211`. The mode uses raw colorspace metadata even though the bus code is greyscale Y8, which matters to receiver and userspace interpretation.

Risks: pixel-rate calculation is `link_freq / bpp` and does not multiply by two edges or lane count, so metadata should be checked against the sensor/receiver timing model. `ov6211_set_ctrl()` uses `pm_runtime_get_if_active()` and then `pm_runtime_put()`; this is intentional for active-only writes but should be checked under concurrent stream transitions. The control handler lock is not explicitly initialized before being assigned to `sd.state_lock`; if the V4L2 core leaves it NULL, state locking assumptions differ from drivers with an explicit mutex. Only link frequency is validated in `ov6211_check_hwcfg()`; lane count is not explicitly checked in this file. `pre_isp` is sampled only at probe, so any later firmware or mode-table change to that register outside the test-pattern bit can be overwritten by test-pattern toggles.

Test signals: validate endpoint link-frequency rejection, optional zero-rate clock behavior, chip ID mismatch, saved `pre_isp` preservation, stream enable/disable through both pad stream callbacks and legacy s_stream helper, runtime autosuspend/resume, exposure/vblank range coupling, analogue gain writes, test pattern on/off, `v4l2-compliance` for subdev state and stream APIs, and captured 400x400 Y8 frames at expected timing.
