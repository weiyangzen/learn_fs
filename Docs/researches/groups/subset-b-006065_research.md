# sources/distributed-fs/ceph-client/kernel/trace/bpf_trace.c

Purpose: implements the kernel tracing side of BPF: helper function bodies for tracing program types, verifier/prog ops for kprobe, tracepoint, raw tracepoint, tracing, writable raw tracepoint, and perf-event programs, perf-event attachment to trace events, raw tracepoint registration, multi-kprobe and multi-uprobe BPF links, session kfunc registration, and dynptr-based probe-read/copy helpers. It is the main bridge between BPF programs and ftrace, perf, tracepoints, kprobes, uprobes, BTF, modules, and security lockdown policy.

Important APIs and types: exported helper prototypes include `bpf_probe_read_user`, `bpf_probe_read_kernel`, string variants, `bpf_probe_write_user`, `bpf_trace_printk`, `bpf_trace_vprintk`, `bpf_seq_printf`, `bpf_seq_write`, `bpf_seq_printf_btf`, perf-event read/output helpers, `bpf_get_current_task`, `bpf_task_pt_regs`, signal helpers, `bpf_d_path`, `bpf_snprintf_btf`, `bpf_get_func_ip`, attach-cookie helpers, branch-record helpers, and function-argument helpers. Verifier/program operation tables include `kprobe_verifier_ops`, `tracepoint_verifier_ops`, `raw_tracepoint_verifier_ops`, `tracing_verifier_ops`, `raw_tracepoint_writable_verifier_ops`, and `perf_event_verifier_ops`. Link state is represented by `struct bpf_kprobe_multi_link`, `struct bpf_uprobe_multi_link`, per-run contexts for kprobe/uprobe/session execution, and `struct bpf_trace_module` for module-provided raw tracepoints.

Control flow: trace-event BPF execution starts at `trace_call_bpf()`, rejects recursive per-CPU BPF execution, then runs the trace event's RCU-protected program array. Helper dispatch flows through per-program-type `*_prog_func_proto()` switches that gate helpers by attach type, capability token, lockdown mode, sleepability, and config options. Perf-event attachment serializes on `bpf_event_mutex`, copies `tp_event->prog_array`, enforces `BPF_TRACE_MAX_PROGS`, records event cookies, and frees old arrays after RCU-safe replacement. Raw tracepoint lookup scans the built-in `__bpf_raw_tp` linker range and, with modules enabled, the notifier-maintained module list; registration validates maximum context and writable access before calling tracepoint registration. Multi-kprobe attach accepts either user addresses or symbol names, optionally sorts cookies with addresses, pins target modules, configures `fprobe` entry/exit callbacks, and settles a `BPF_LINK_TYPE_KPROBE_MULTI` link. Multi-uprobe attach resolves a user path, optional target pid, offsets, ref-counter offsets, and cookies, then registers `uprobe_consumer` handlers for a `BPF_LINK_TYPE_UPROBE_MULTI` link. Runtime callbacks set `current->bpf_ctx`, run the BPF program under the proper RCU flavor and migration/preemption rules, and expose entry IP, cookie, return/session state, and per-session data through helpers or kfuncs.

State and persistence: all state is kernel-lifetime or link-lifetime runtime state, not durable storage. Persistent-looking objects are BPF links, perf events, tracepoint program arrays, module references, path/task references for uprobes, per-CPU nesting buffers for perf output and raw tracepoint pt_regs, per-CPU signal irq_work, and workqueue state used to enable the `bpf_trace_printk` event. Memory-safety behavior is stateful through RCU, tasks-trace RCU for sleepable programs, module reference counts, `bpf_prog_active` recursion counters, and cleanup paths in link release/deallocation.

Dependencies and integration points: depends on BPF core/verifier/BTF APIs, perf events, tracepoints, ftrace/fprobe, kprobes, uprobes, module notifiers, kallsyms/ftrace symbol lookup, security lockdown, LSM sleepability checks, path/namei, signal delivery, seq_file, BPF iterators, network tracing helper prototypes, and arch support for pt_regs/ftrace regs. `bpf_trace.h` supplies the trace event used by `bpf_trace_printk`.

Risks and test signals: high-risk areas are recursion and nesting limits in NMI/IRQ contexts, RCU flavor mismatches for sleepable vs non-sleepable programs, user pointer copy/zeroing semantics, lockdown/capability helper exposure, stale module references for multi-kprobes, uprobe task/path lifetime, address/cookie sorting correctness, context write restrictions, and perf-event array replacement races. Test signals include BPF selftests for trace helpers, raw tracepoints, tracepoints, perf-event output/read, `bpf_trace_printk`, BTF snprintf/seq output, kprobe_multi/uprobe_multi links with cookies and returns, session programs/kfuncs, module unload while probes are attached, lockdown-denied helpers, recursion/missed counters, and 32-bit/config-disabled fallback builds returning `-EOPNOTSUPP`.

# sources/distributed-fs/ceph-client/kernel/trace/bpf_trace.h

Purpose: declares the `bpf_trace` tracepoint system and the `bpf_trace_printk` trace event consumed by the BPF tracing helper implementation. It is intentionally small: it defines the trace event schema used to route formatted BPF trace-print messages through the kernel trace event machinery.

Important APIs and types: `TRACE_EVENT(bpf_trace_printk, TP_PROTO(const char *bpf_string), ...)` records a single dynamic string field named `bpf_string` and prints it with `TP_printk("%s", __get_str(bpf_string))`. `TRACE_SYSTEM`, `TRACE_INCLUDE_PATH`, and `TRACE_INCLUDE_FILE` connect this header to `<trace/define_trace.h>` when `CREATE_TRACE_POINTS` is defined by `bpf_trace.c`.

Control flow: when `bpf_trace.c` defines `CREATE_TRACE_POINTS` and includes this header, the tracepoint objects and trace event metadata are instantiated. At runtime, `bpf_trace_printk()` and `bpf_trace_vprintk()` format into a temporary buffer and call `trace_bpf_trace_printk(data.buf)`, which emits this event. The helper lookup path also schedules work to enable the event so users loading programs that call the helper can see output even if the event was disabled.

State and persistence: the header declares trace metadata only. Runtime event enablement state, ring-buffer records, and formatted message storage are owned by ftrace/tracefs infrastructure and by `bpf_trace.c` helper buffers; no durable state is held here.

Dependencies and integration points: depends on `<linux/tracepoint.h>` and the trace event macro system. It integrates directly with tracefs event naming as `bpf_trace/bpf_trace_printk`, and with the generated `trace_bpf_trace_printk()` callsite used in `kernel/trace/bpf_trace.c`.

Risks and test signals: risk is primarily ABI/schema drift: changing the event name, field name, or include path would break helper output visibility and tracefs consumers. Test signals are successful kernel trace event generation, `available_events` containing `bpf_trace:bpf_trace_printk`, BPF selftests or manual programs using `bpf_trace_printk`, and build coverage for trace header multi-read handling.

# sources/distributed-fs/ceph-client/kernel/trace/error_report-traces.c

Purpose: instantiates error-report tracepoints and exports the `error_report_end` tracepoint symbol to GPL modules. The file exists so the trace event declarations from `<trace/events/error_report.h>` have one C translation unit that defines their storage.

Important APIs and types: `#define CREATE_TRACE_POINTS` before including `<trace/events/error_report.h>` causes the error-report tracepoint definitions to be emitted. `EXPORT_TRACEPOINT_SYMBOL_GPL(error_report_end)` makes the end-of-report tracepoint available to GPL-only modules.

Control flow: there is no runtime function body in this file. Build-time trace macro expansion creates the tracepoint descriptors and helper callsites declared by the header. Runtime producers in other kernel code call the generated tracepoint functions, and module users can bind to the exported `error_report_end` tracepoint.

State and persistence: state is tracepoint registration/enabled state owned by the generic tracepoint subsystem. Trace records are transient ring-buffer/perf data. This file stores no persistent state and performs no initialization beyond static tracepoint definition.

Dependencies and integration points: depends on the generic trace event system and `<trace/events/error_report.h>`. Its integration surface is the exported GPL tracepoint symbol, which lets modular error-reporting consumers or tracers observe report completion without depending on private C objects.

Risks and test signals: risks are build/link regressions if the trace event header changes name or stops declaring `error_report_end`, and module ABI expectations around GPL-only export. Test signals include successful allmodconfig-style builds, `EXPORT_TRACEPOINT_SYMBOL_GPL` resolving during module link, tracefs visibility of error-report events, and a producer exercising begin/end error-report events with consumers attached.

# sources/distributed-fs/ceph-client/kernel/trace/fgraph.c

Purpose: implements function graph tracing infrastructure: allocation and management of per-task shadow return stacks, registration of `struct fgraph_ops` clients, dispatch of entry and return callbacks, direct static-call optimization for the single-client case, PID filtering, sleep-time accounting, CPU/task lifecycle support, and unwinder helpers that recover original return addresses.

Important APIs and types: exported or externally used entry points include `function_graph_enter_regs()`, `ftrace_return_to_handler()`, `ftrace_graph_get_ret_stack()`, `ftrace_graph_top_ret_addr()`, `ftrace_graph_ret_addr()`, `fgraph_reserve_data()`, `fgraph_retrieve_data()`, `fgraph_retrieve_parent_data()`, `fgraph_get_task_var()`, `fgraph_init_ops()`, `ftrace_graph_init_idle_task()`, `ftrace_graph_init_task()`, `ftrace_graph_exit_task()`, `register_ftrace_graph()`, and `unregister_ftrace_graph()`. Core state includes `fgraph_array`, `fgraph_array_bitmask`, LRU index allocation, `fgraph_stack_cachep`, global `ftrace_graph_active`, static keys/calls for direct dispatch, and task fields `ret_stack`, `curr_ret_stack`, `curr_ret_depth`, `trace_overrun`, and sleep timestamps.

Control flow: registration takes `ftrace_lock`, creates the shadow-stack slab cache, initializes CPU hotplug support and `fgraph_array`, assigns the client an index, optionally enables the direct static-call path, allocates return stacks for idle and existing tasks, registers the sched-switch probe, and starts ftrace graph subops. Function entry calls `function_graph_enter_regs()`, recursion-checks, pushes an `ftrace_ret_stack` frame, runs either the direct `entryfunc` or all active `fgraph_ops`, lets entry callbacks reserve data, and records a bitmap of clients that need return callbacks. Function return reaches `ftrace_return_to_handler()`, pops the frame, restores the original return address, updates pt_regs, dispatches `retfunc` callbacks selected by the bitmap, then moves `curr_ret_stack` and depth back. Unregistration removes the client from arrays/filter subops, switches direct/non-direct mode as client count changes, unregisters sched/PM hooks when the last client leaves, and clears graph flags.

State and persistence: state is runtime-only but long-lived while graph tracing is active. Each task has a 4 KiB shadow stack from `fgraph_stack_cachep`; idle stacks are per-CPU cached. The stack encodes frame offsets, callback bitmaps, reserved data blocks, and per-client task variables. Barriers protect interrupt/unwinder views of partially updated stacks. Hibernation pauses graph tracing because task stack state is unstable across suspend/resume. Sleep-time accounting persists in task fields only for tracing duration.

Dependencies and integration points: integrates with dynamic ftrace, `struct ftrace_ops`, arch return-to-handler glue, static calls/jump labels, scheduler tracepoints, PM notifier, CPU hotplug, task lifecycle hooks, stack unwinders, and optional function return-value tracing. `fprobe.c` is a major in-tree client through `register_ftrace_graph()`.

Risks and test signals: high-risk areas are stack offset encoding, interrupt-visible ordering around `curr_ret_stack`, overrun handling, direct-dispatch transitions when the active client count changes, client index reuse, PID filter wrapping, module/client unregister while callbacks are in flight, hibernation pause behavior, and unwinder reconstruction of tail calls. Test signals include function_graph tracer smoke tests, fprobe return-handler tests, stack unwinder tests under active graph tracing, task fork/exit and CPU hotplug coverage, sched-switch sleep-time accounting, PM hibernation pause/resume, recursion stress, and configurations with/without dynamic ftrace, static calls, ftrace regs, and return-value support.

# sources/distributed-fs/ceph-client/kernel/trace/fprobe.c

Purpose: implements fprobe, a higher-level wrapper that registers function entry and optional return probes on top of ftrace and function graph tracing. It supports registration by filter glob, symbol list, or address list; tracks probes in RCU-safe hash tables; dispatches entry and exit callbacks; stores per-entry data on fgraph's shadow stack; and handles module unload cleanup.

Important APIs and types: public APIs are `fprobe_count_ips_from_filter()`, `register_fprobe()`, `register_fprobe_ips()`, `register_fprobe_syms()`, `fprobe_is_registered()`, `unregister_fprobe_async()`, and `unregister_fprobe()`. Core state includes `fprobe_table` keyed by `struct fprobe *`, `fprobe_ip_table` keyed by ftrace IP, `fprobe_mutex`, shared `fprobe_ftrace_ops` for entry-only probes, shared `fprobe_graph_ops` for probes with exit handlers, and counters/registered flags for each backend. `struct fprobe_hlist` and `struct fprobe_hlist_node` are the registered-node storage referenced by both hash tables.

Control flow: registration resolves target IPs from kallsyms/module kallsyms, symbol arrays, or caller-provided addresses, canonicalizes each address through `ftrace_location()`, validates `entry_data_size`, allocates `hlist_array`, installs ftrace filters, registers either ftrace entry ops or fgraph ops, and inserts nodes into both the per-fprobe and per-IP lookup tables. Entry-only probes use `fprobe_ftrace_entry()`: after ftrace recursion protection it RCU-walks all nodes for the IP and calls the entry handler unless the probe is disabled or has an exit handler. Return-capable probes use `fprobe_fgraph_entry()`: it precomputes required fgraph storage, reserves it, invokes entry handlers, and records headers plus optional entry data only for probes whose entry callback allowed the exit callback. `fprobe_return()` retrieves that fgraph data, verifies the fprobe is still registered and enabled, then calls each exit handler. Unregister removes nodes, updates ftrace filters only for IPs no longer used by a same-backend probe, unregisters shared backends when counters drop to zero, and frees node storage after RCU; synchronous unregister waits for a grace period.

State and persistence: registered probes are runtime kernel state owned by caller-provided `struct fprobe` plus allocated `hlist_array`. The IP table is RCU-readable from ftrace callback context while updates are mutex-protected. Return-probe per-invocation state is transient data encoded on fgraph's shadow stack with either an arch-specific one-word header or generic packed header. Module references are taken during filter matching and released after registration; module-going notifications remove nodes that point into the unloading module.

Dependencies and integration points: depends on ftrace filters and callbacks, function graph tracing, kallsyms and module kallsyms, kprobe busy tracking for callbacks shared with kprobes, rhashtable/rhltable, RCU, module notifiers, and arch optional fprobe header encoding. It is consumed by BPF multi-kprobe links in `bpf_trace.c` and by kernel users of `<linux/fprobe.h>`.

Risks and test signals: risks include RCU lifetime mistakes during unregister/module unload, stale ftrace filters when allocation of removal IP lists fails, mismatched ftrace vs fgraph backend counters, entry-data size/header overflow, recursion behavior when sharing handlers with kprobes, missed-counter accounting, duplicate IP handling, and races where a probe is unregistered between entry and return. Test signals include `lib/tests/test_fprobe.c`, BPF kprobe_multi selftests, registration by glob/symbol/IP, overlapping probes on the same IP with mixed entry-only and return handlers, module unload with active probes, async vs sync unregister, disabled probes, entry handlers that suppress exit callbacks, and config matrices without ftrace regs/args or without modules.
