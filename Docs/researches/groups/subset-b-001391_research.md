# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/display/dc/core/dc_surface.c

Purpose: this file implements the Display Core plane-state object helpers: construction defaults, status sampling, reference-counted lifetime for plane/color helper objects, DCC/tiling disable forwarding, and shallow configuration copy for an existing plane state. Despite the historical `surface` naming, the implementation is centered on `struct dc_plane_state` and the color objects embedded in or referenced from it.

Important APIs, types, and functions: `dc_create_plane_state()` allocates a zeroed plane state, initializes `kref`, and calls `dc_plane_construct()`. `dc_plane_construct()` sets safe color defaults: identity gamma, bypass input/shaper/blend transfer functions, cleared 3D LUT state, and premultiplied alpha enabled. `dc_plane_get_pipe_mask()` maps a plane state to active HUBP instances in an arbitrary `struct dc_state`. `dc_plane_get_status()` returns `struct dc_plane_status` after optionally refreshing pending flip state and color histogram data. Retain/release APIs cover `dc_plane_state`, `dc_gamma`, `dc_transfer_func`, and `dc_3dlut`.

Control flow: status reads first validate the plane, context, and current DC state, clear pending status fields requested by `union dc_plane_status_update_flags`, exit idle power state through `dc_exit_ips_for_hw_access()`, then walk current pipes again to call `dc->hwss.update_pending_status()` and `dpp->funcs->dpp_cm_hist_read()` as requested. Object lifetime uses Linux `kref`: retain increments, release calls a type-specific free callback, and allocation uses `kvzalloc_obj()`/`kvfree()`.

State and persistence: state is in-memory only. `struct dc_plane_state::status` caches requested/current address, flip pending, right-eye, and histogram fields. `dc_plane_copy_config()` intentionally preserves the destination `kref` while copying the entire source plane configuration, so reference lifetime survives config replacement. `dc_plane_force_dcc_and_tiling_disable()` does not persist anything itself; it delegates per-pipe hardware clearing to `dc->hwss.clear_surface_dcc_and_tiling`.

Dependencies and integration points: depends on `dc.h`, private core pipe/resource types, `dc_plane_priv.h`, DPP histogram hooks, HUBP instances, and HWSS callbacks. It is called by DC commit/update paths and by firmware-offload code such as FAMS2 flip building when a pipe mask is needed.

Risks and test signals: `dc_plane_get_status()` mutates status in a `const` plane pointer context through current pipe state, so callers must treat status reads as hardware-affecting and idle-power-sensitive. `dc_plane_get_pipe_mask()` uses `plane_state->ctx->dc->res_pool->pipe_count`, so malformed or stale plane contexts can mis-scan a supplied `dc_state`. `dc_gamma_release()` takes a double pointer and unconditionally dereferences `*gamma`; callers must pass valid owned objects. Useful tests are plane create/release leak checks, flip pending clear after hardware update, histogram reset/read paths with DPP hooks, pipe-mask correctness for MPC/ODM split pipes, and preservation of refcount across `dc_plane_copy_config()`.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/display/dc/core/dc_vm_helper.c

Purpose: this file is the small Display Core VM helper layer that records VMID usage per HUBP and routes physical/virtual address space programming requests to hardware sequencer callbacks. It bridges DC state, HUBBUB/HUBP system aperture setup, and DML2 GPUVM enablement.

Important APIs, types, and functions: `vm_helper_mark_vmid_used()` updates the two-entry rolling usage history for one HUBP. `dc_setup_system_context()` calls `dc->hwss.init_sys_ctx()` with `struct dc_phy_addr_space_config`, caches the physical aperture in `dc->vm_pa_config`, marks it valid, enables `dc->dml2_options.gpuvm_enable`, and calls `dc_z10_save_init()`. `dc_setup_vm_context()` forwards `struct dc_virtual_addr_space_config` and a VMID to `dc->hwss.init_vm_ctx()`. `dc_get_vmid_use_vector()` ORs current/recent VMID bitmasks across all HUBPs. `vm_helper_init()` records the supported VMID count and clears usage.

Control flow: initialization clears `hubp_vmid_usage` for `MAX_HUBP`. System context setup is conditional on `hwss.init_sys_ctx`; if present, the callback returns the number of VMIDs and the function records the aperture for later restore/power-gating paths. Per-VM setup has no local validation and assumes `hwss.init_vm_ctx` is present. VMID usage queries scan all HUBP slots and combine both recent history entries.

State and persistence: no disk or firmware-persistent state is stored here. Persistent runtime state is `vm_helper->num_vmid`, the per-HUBP rolling VMID masks, and `dc->vm_pa_config`. `vm_helper_mark_vmid_used()` copies the usage struct by value and updates the copy, which means the intended history update is not written back to `vm_helper->hubp_vmid_usage[hubp_idx]`; if this is not optimized away by later code, VMID use tracking will remain stale.

Dependencies and integration points: depends on `vm_helper.h`, `dc.h`, HWSS system/VM context callbacks, `MAX_HUBP`, DML2 configuration, and Z10 save/restore support. It is used by DC creation/resume/commit paths that must program GPUVM apertures before HUBP fetches display surfaces.

Risks and test signals: the by-value update in `vm_helper_mark_vmid_used()` is the main correctness risk and should be covered by a unit or debug assertion that `dc_get_vmid_use_vector()` changes after marking a VMID. `dc_setup_vm_context()` lacks a null callback guard unlike system setup. Bounds for `hubp_idx` and VMID position are not checked here. Test signals include system aperture programming count from `init_sys_ctx`, `dc->vm_pa_config.valid`, DML2 GPUVM enablement, Z10 save/restore behavior, and VMID vector changes during multi-plane flips on different HUBPs.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/display/dc/dc.h

Purpose: `dc.h` is the primary public Display Core interface used by AMDGPU Display Manager and adjacent DC modules. It publishes versioning, capability structures, debug/configuration knobs, VM setup types, surface/color/link/sink objects, the central `struct dc`, and the externally callable DC lifecycle, validation, commit, link, power, DMUB, and diagnostic APIs.

Important APIs, types, and functions: top-level capability/config types include `dc_caps`, `dc_config`, `dc_debug_options`, `dc_bug_wa`, `dc_clocks`, `dc_phy_addr_space_config`, `dc_virtual_addr_space_config`, and `dc_init_data`. Color and plane contracts include transfer functions, 3D LUTs, plane color-management flags, `dc_plane_status`, `surface_update_flags`, `dc_plane_state`, `dc_plane_info`, `dc_fast_update`, and `dc_surface_update`. Link/sink contracts include `dc_link`, `dc_sink`, DP link-training/protocol helpers, HPD/AUX/I2C entry points, backlight/PSR/Replay/Panel Replay functions, USB4 DPIA bandwidth APIs, and persistent link-resource map helpers. `struct dc` ties together config/debug/caps, context, links, current state, resource pool, clock manager, HWSS, VM helper, scratch state, DML/DML2 options, and power state.

Control flow: callers create DC with `dc_create()`, initialize hardware with `dc_hardware_init()`, validate planes/streams through `dc_validate_*()`, then commit streams and surface updates through the declared commit/update interfaces. Link control flows start from detection/HPD/AUX reads, proceed through link-cap selection and training, and expose status/trace helpers to DM. Power and firmware flows use idle optimization wrappers, memory clock locks, PSR/Replay controls, DMUB notifications, IPS controls, and hardware release/resume calls.

State and persistence: this header defines both volatile state and state intended to survive driver reload logic. `dc_get_cur_link_res_map()`/`dc_restore_link_res_map()` explicitly let DM persist link resource allocation so hotplug-order-dependent resources remain stable across reboot. Plane/sink objects are reference counted. `dc->current_state`, scratch state, VM physical aperture, debug data, clock limits, DML state, and link structures are runtime state. `dc_register_software_state` is a large diagnostic snapshot schema for register-programming inputs used in underflow and QoS analysis.

Dependencies and integration points: includes DC type headers, stream/plane/link service types, HW sequencer, compressor, DMCU, DML/DML2, DMUB commands, SPL sharpness types, HDCP, GPIO, BIOS/parser-derived graphics object definitions, and OPP hardware definitions. It is the shared ABI between Display Manager, core DC, resource code, hardware sequencers, link code, DMUB service code, and diagnostics.

Risks and test signals: because this is a broad public header, field layout and semantic drift are high-risk. Large debug/config structs can silently change feature policy; bitfields and arrays must match firmware, DML, and ASIC limits. New fields in `dc_plane_state`, `dc_link`, or `struct dc` need clone/copy/lifetime audits. Test signals include successful build across DCN feature configs, ABI consumers compiling, mode validation/commit tests, HPD/AUX/link-training tests, PSR/Replay/FAMS/IPS firmware interactions, and underflow/QoS diagnostic capture returning coherent data.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/display/dc/dc_bios_types.h

Purpose: this header defines the Display Core VBIOS abstraction. It lets DC call either the default internal BIOS parser or a Display Manager supplied override through one vtable, while storing parsed firmware tables and board/display metadata in `struct dc_bios`.

Important APIs, types, and functions: `struct dc_vbios_funcs` is the callback table. Query callbacks cover connector count and IDs, source object resolution, I2C/HPD GPIO info, device tags, spread spectrum entries, embedded panel info, GPIO pin info, encoder capabilities, board layout, SOC bounding box, connector capabilities, LTTPR capability/interop, and connector speed caps. Command callbacks wrap ATOM/VBIOS operations such as CRTC source selection, encoder/transmitter control, DAC load detection, CRTC enable, pixel/DCE clock programming, spread-spectrum programming, CRTC timing programming, display PLL programming, display power gating, and LVTMA control. `struct dc_bios` stores the function table, raw BIOS image pointers/sizes, local copy, context, scratch register addresses, integrated info, firmware info, VRAM info, SOC bounding box info, and golden table.

Control flow: DC obtains or constructs a `dc_bios`, then uses `bios->funcs` for all firmware table reads and firmware-assisted hardware programming. The override design means diagnostics or platform code can provide alternate implementations without changing callers. Destruction is also virtual through `bios_parser_destroy()`.

State and persistence: firmware state is the raw BIOS image and local parsed/cache fields. `fw_info_valid` gates whether cached firmware info is usable. `integrated_info`, `vram_info`, `bb_info`, and `golden_table` retain parsed table results for later DC and resource initialization. Scratch register addresses identify BIOS scratch state used for boot/accelerated-mode coordination.

Dependencies and integration points: depends on `include/bios_parser_types.h` for ATOM parser result codes and data structures. It integrates with DC creation, link/resource enumeration, clock setup, spread-spectrum policy, panel power sequencing, golden table/SOC bounding-box initialization, and diagnostics that override VBIOS behavior.

Risks and test signals: every callback pointer is an implicit contract; missing optional callbacks need caller-side guards. Parser output must match ASIC firmware table revisions and endian/layout expectations. Override implementations can diverge from the internal parser. Test signals include connector enumeration, I2C/HPD mapping, embedded panel info, clock table programming, power-gating table calls, parser destroy coverage, and successful DC bring-up with both real and override VBIOS providers.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/display/dc/dc_ddc_types.h

Purpose: this header defines the DDC, I2C, and AUX transaction data model used by DC link detection, EDID reads, DPCD access, and dongle classification. It is a pure type contract without executable code.

Important APIs, types, and functions: `enum aux_transaction_type` distinguishes native DP AUX from I2C-over-AUX. `enum i2caux_transaction_action` encodes read/write/status actions, MOT variants, and DP read/write opcodes. `aux_request_transaction_data`, `aux_reply_transaction_data`, and `aux_payload` describe low-level AUX transfers, including address, length, data pointer, reply pointer, MOT/write flags, status-update writes, and defer delay. I2C is described by `i2c_payload`, `i2c_command_engine`, and `i2c_command`, with `DDC_I2C_COMMAND_ENGINE` defaulting to software I2C. `ddc`, `ddc_service`, `ddc_flags`, `ddc_wa`, `ddc_transaction_type`, and `display_dongle_type` hold GPIO pins, transaction mode, cached EDID buffer, link context, workaround flags, and dongle category.

Control flow: callers build one or more I2C payloads or a single AUX payload, then pass them into DDC/link helpers declared elsewhere. Reply status is returned through `aux_reply_transaction_data` or `aux_payload.reply`; EDID reads cache into `ddc_service.edid_buf` up to `DC_MAX_EDID_BUFFER_SIZE`. Transaction type records whether the service is using native I2C, I2C-over-AUX, defer-aware I2C-over-AUX, or retry-defer behavior.

State and persistence: state is runtime only. `ddc_service` persists link-local DDC state across detection operations: flags such as `EDID_QUERY_DONE_ONCE`, internal-display classification, repeated-start forcing, stress-read mode, workaround bits, dongle type, current address, and the EDID cache. No disk persistence exists.

Dependencies and integration points: depends on GPIO abstractions, `dc_context`, `dc_link`, and link/DDC implementations that perform actual AUX/I2C transactions. It is consumed by DC public APIs such as `dc_submit_i2c()`, `dc_link_aux_transfer_raw()`, link detection, EDID parsing, DPCD reads, and DP/HDMI dongle handling.

Risks and test signals: transfer payloads store raw data pointers, so lifetime and buffer length validation are caller responsibilities. AUX data size defaults to 16 bytes, but DPCD/EDID flows must segment larger operations correctly. Reply enums combine AUX and I2C-over-AUX status bits, so decode mistakes can break retry/defer behavior. Test signals include EDID block reads, DPCD native reads/writes, I2C-over-AUX defer retries, HPD disconnect replies, software I2C fallback, repeated-start devices, and dongle type detection.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/display/dc/dc_dmub_srv.c

Purpose: this file implements the DC-side service wrapper around DMCUB/DMUB firmware messaging. It owns command queue execution, idle-power wake/reallow handling, firmware capability and diagnostic queries, FAMS/FAMS2 and SubVP command construction, cursor offload/update commands, IPS residency commands, LSDMA commands, boot-time CRC setup, and firmware power-state notifications.

Important APIs, types, and functions: construction/lifetime are `dc_dmub_srv_create()` and `dc_dmub_srv_destroy()`. Core transport is `dc_dmub_srv_cmd_list_queue_execute()`, `dc_dmub_srv_wait_for_idle()`, `dc_dmub_srv_cmd_run(_list)()`, `dc_wake_and_execute_dmub_cmd(_list)()`, and `dc_wake_and_execute_gpint()`. Register-interface and framebuffer-ring command paths are split into `dc_dmub_srv_reg_cmd_list_queue_execute()` and `dc_dmub_srv_fb_cmd_list_queue_execute()`. Feature flows include FAMS DRR/manual-trigger, `dc_dmub_srv_p_state_delegate()`, `dc_dmub_setup_subvp_dmub_command()`, FAMS2 config/DRR/passthrough flips, visual-confirm color, DPIA trace, cursor info/offload, IPS idle and residency, DMUB caps, diagnostics, LSDMA copy/fill/register commands, and pre-OS DMCUB logging.

Control flow: command submission first queues commands using the DMUB inbox type, executes the queue, optionally waits for idle or reply, and records timeout diagnostics on failure. The wake helpers temporarily exit idle power optimizations if `idle_allowed` is true, execute through DM-provided `dm_execute_dmub_cmd*()` helpers, then reallow idle if policy permits. Idle entry writes shared IPS driver signals according to DC config/debug policy and sends an idle notification without waking recursively. Idle exit clears driver signals, may notify PMFW through the clock manager, waits for IPS commits/hardware power-up, resynchronizes inboxes, and notifies DMCUB that idle is false.

State and persistence: runtime state lives in `struct dc_dmub_srv`: DMUB pointer, context, idle flags/counters, cached driver IPS signals, register-helper offload state, and cursor-offload enablement. DMUB shared memory is used for IPS driver/FW state, cursor offload framebuffer, scratch memory for IPS residency output, IB memory for FAMS2 v3 configs, LSDMA ring memory, and firmware debug/pre-OS structures. No disk persistence exists.

Dependencies and integration points: depends on `dmub_srv` hardware/firmware helpers, DM execution callbacks, DC context/state/resource helpers, HWSS/clock manager, DML bandwidth outputs, SubVP/FAMS firmware command layouts, HUBP/DPP cursor register caches, link PSR/Replay settings, and logger/error recovery helpers. It is the integration point between DC mode programming and display firmware services.

Risks and test signals: command timeout handling can loop indefinitely when `debug.disable_timeout` is set. Power-state D3 is often treated as a nonfatal false return, so callers must handle skipped commands. Idle entry/exit has race-sensitive counters and shared-memory signal ordering. `dc_dmub_srv_get_pipes_for_stream()` assigns `pipes = i` instead of accumulating a bitmask, which is worth auditing against firmware expectations. FAMS/SubVP timing math has many rounding and cap dependencies. LSDMA linear copy subtracts one from count, so zero byte counts would underflow. Test signals include DMUB ring full handling, wait-with-reply copyback, D3 command rejection, idle enter/exit under concurrent callers, IPS residency reads, FAMS/SubVP firmware command payloads, cursor updates for PSR/Replay, FAMS2 flips for graphics/video planes, LSDMA command emission, and diagnostic logging on induced timeout.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/amd/display/dc/dc_dmub_srv.h

Purpose: this header publishes the DC DMUB service state and command helper API used by Display Core and Display Manager code to interact with DMCUB firmware. It separates higher-level DC behavior from the lower-level `dmub_srv` transport and firmware command definitions.

Important APIs, types, and functions: `struct dc_reg_helper_state` stores burst/offload command-gathering state for register helper paths. `struct dc_dmub_srv` stores the wrapped `dmub_srv`, DC context, DM backpointer, idle exit counter, IPS driver signals, idle/wake flags, cursor offload flag, and register offload state. Public APIs cover pending/idle waits, command run/list execution, stream mask notification, boot restore/optimized-init status, outbox/trace control, DRR and FAMS/FAMS2 commands, p-state delegation, feature caps query, visual-confirm color, INBOX0 operations, diagnostics, SubVP setup, cursor update/offload, firmware version check, DPIA tracing, hardware power checks, idle optimizations, power-state notification, link-redetect polling, wake-and-execute wrappers, GPINT, LSDMA operations, IPS residency, boot-time CRC, hardware release, and pre-OS DMCUB info logging.

Control flow: callers should prefer `dc_wake_and_execute_dmub_cmd_list()` or `dc_wake_and_execute_gpint()` when the DC lock is held, because those wrappers coordinate idle-power wake and re-entry around DMUB communication. Specialized helpers populate firmware command payloads and then use those wrappers or direct DM execution depending on whether they are already in a wake path.

State and persistence: the header-defined state is runtime only. It does, however, point to DMUB-owned shared memory and framebuffers whose contents survive across command calls while the driver is loaded. `idle_allowed`, `needs_idle_wake`, and `driver_signals` mirror low-power coordination state; `cursor_offload_enabled` records successful firmware offload initialization.

Dependencies and integration points: includes `dm_services_types.h` and `dmub/dmub_srv.h`, and forward-declares DC, state, pipe, timing, and surface update structures. The API is used by DC core, link, power, cursor, SubVP/FAMS, diagnostics, and DM integration layers.

Risks and test signals: because this header exposes many firmware-coupled structs and command helpers, DMUB command layout changes require synchronized firmware and driver updates. Bitfield parameter structs for LSDMA must match firmware packing. Callers must choose the right wait type and avoid wake-wrapper recursion in idle paths. Test signals include compile coverage for all feature configs, command payload size checks, cursor offload enable/disable, idle redetect polling, FAMS2 v2/v3 config selection, LSDMA parameter packing, and IPS residency query return semantics.
