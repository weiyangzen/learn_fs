# sources/object-store/rustfs/crates/ecstore/src/pools.rs

Purpose: This file owns RustFS ECStore pool metadata, decommission orchestration, decommission object migration, post-decommission verification, and usable-capacity reporting for erasure-coded pools. It bridges persistent pool state (`pool.bin`), runtime cancellation state, bucket/object traversal, lifecycle/object-lock/replication rules, and storage-admin capacity snapshots.

Important APIs/types/functions: Key constants are `POOL_META_NAME`, `POOL_META_FORMAT`, and `POOL_META_VERSION`, defining the on-disk pool metadata envelope. Core state types are `PoolStatus`, `PoolMeta`, `PoolDecommissionInfo`, `PoolSpaceInfo`, and `DecomBucketInfo`. `PersistedPoolMeta`, `PersistedPoolStatus`, and `PersistedPoolDecommissionInfo` are the explicit persisted schema used to retain resume queues that are skipped in the runtime `PoolDecommissionInfo` serde representation. Helper families validate pool indices and state transitions (`ensure_valid_decommission_pool_index`, `ensure_decommission_start_allowed`, `ensure_decommission_cancel_allowed`, `validate_start_decommission_request`), bind and clear cancellation tokens (`bind_decommission_cancelers`, `take_decommission_canceler`, `cancel_decommission_canceler`), update decommission counters and current object fields, and add contextual error messages around metadata save/reload/listing/migration operations.

The main `PoolMeta` methods construct metadata from configured `Sets`, load and save `pool.bin`, start/cancel/fail/complete decommission state, manage queued and completed buckets, persist periodic progress with `update_after`, validate command-line pool changes, and return resumable decommission pools. `PoolDecommissionInfo` exposes `bucket_push`, `is_bucket_decommissioned`, and `bucket_pop` to manage queue and progress state. The `ECStore` implementation exposes `status`, `decommission`, `start_decommission`, `decommission_cancel`, `is_decommission_running`, `spawn_decommission_routines`, `do_decommission_in_routine`, `decommission_failed`, and `complete_decommission`; internal async helpers perform per-bucket and per-entry migration. `SetDisks::list_objects_to_decommission` adapts raw metacache listings into a decommission callback. Capacity helpers include `get_total_usable_capacity`, `get_total_usable_capacity_free`, `fallback_total_capacity_dedup`, and `fallback_free_capacity_dedup`.

Control flow: Starting decommission begins in `ECStore::decommission` or `start_decommission`. Indices are deduplicated, single-pool deployments and empty requests are rejected, rebalance conflicts are checked, target pool indices and active state are validated, all buckets plus RustFS metadata prefixes are collected, buckets are pre-healed, metadata buckets are force-created, pool space is sampled, and `PoolMeta` is updated with fresh `PoolDecommissionInfo` plus bucket queues before being saved to every pool. `decommission` then binds per-index child cancellation tokens and spawns background routines; if spawning fails, it tries to cancel every requested decommission and returns a combined spawn/rollback error.

Background work flows through `do_decommission_in_routine` into `decommission_in_background`. Each pending bucket is skipped if already marked complete, otherwise `decommission_pool` launches one listing worker per set in the source pool. Listing workers call `SetDisks::list_objects_to_decommission`, which obtains online disks, computes majority listing quorum, calls `list_path_raw`, resolves partial metacache entries with `MetadataResolutionParams`, and invokes the callback. The callback throttles via `Workers`, then calls `decommission_entry`; the first entry error is stored and cancels the bucket token.

`decommission_entry` ignores directories, loads and sorts file versions, applies lifecycle decisions, optionally expires lifecycle-deleted versions, skips the last delete marker when no replication is configured, copies delete markers through `delete_object`, migrates remote tiered objects through `decommission_tiered_object`, migrates local objects by reading from the source set and calling `data_movement::migrate_object`, and retries local reads/migrations up to three times. Not-found, missing-version, and data-movement-overwrite errors are treated as cleanup-safe ignored outcomes in selected paths. Successful/failed counters and bytes are recorded in `PoolMeta`; source entries are deleted from the decommissioned pool only when all versions were decommissioned and none were merely expired by lifecycle. Progress is persisted at most every 30 seconds and notification metadata reloads are attempted best-effort.

When background work returns, `do_decommission_in_routine` derives terminal state from failed item counters and cancel state. Cancellation preserves canceled state. Non-cancel background errors mark the pool failed. Clean completion runs `check_after_decommission`, which re-lists every relevant bucket/prefix in every set of the source pool and counts remaining non-delete, non-lifecycle-expired versions; any remaining version fails finalization. Successful verification marks the pool complete, saves metadata, reloads notification metadata, and clears the canceler. Manual cancel/fail/complete paths also save pool metadata, reload notification metadata if available, and cancel/clear the runtime token.

State and persistence behavior: Pool metadata is stored as little-endian format/version header plus MessagePack payload in `pool.bin`, saved through `save_config` to every pool and read through `read_config` from a selected pool. `PoolMeta::decode_pool_meta_payload` first decodes the explicit persisted schema, then falls back to the older direct `PoolMeta` payload and resets `dont_save` because it is runtime-only. The persisted schema intentionally includes fields that `PoolDecommissionInfo` marks `#[serde(skip)]` in its runtime serde shape: queued buckets, completed buckets, current bucket/prefix/object. This is important for resume after restart. Progress counters, terminal flags, timestamps, and start/current/total capacity are persisted; runtime cancellation tokens live in `ECStore::decommission_cancelers` and are not persisted.

Dependencies and integration points: The file depends on bucket versioning, lifecycle evaluation and expiry, object lock default retention, replication metadata, notification system metadata reloads, config persistence, metacache raw listings, data movement, heal operations, bucket creation/listing, object IO, storage admin backend snapshots, and set/disk abstractions. It also integrates with `rustfs_filemeta` for `MetaCacheEntry`, `FileInfoVersions`, and metadata resolution; `rustfs_concurrency::Workers` for bounded migration concurrency; `tokio_util::CancellationToken`; `rmp_serde`; `byteorder`; `time`; `tracing`; and `rustfs_madmin` disk/storage structures for capacity accounting.

Risks: Decommission spans many asynchronous boundaries and mutable states, so failure classification matters. Some helper methods on `PoolMeta` silently ignore out-of-range or missing decommission state, while newer wrapper helpers return explicit contextual errors; callers must pick the stricter path when correctness matters. Runtime cancellation and persisted canceled state can diverge if the process exits mid-operation, though resumable-pool logic excludes complete and canceled pools. Lifecycle expiry during data movement means some source versions are intentionally not migrated and also not source-cleaned if `expired > 0`, which is subtle but prevents deleting entries that still require source retention semantics. `check_after_decommission` skips delete markers and data-usage cache entries, so it verifies remaining data versions rather than a completely empty source prefix. Capacity calculation deduplicates disks by endpoint/path plus pool/set/disk indexes for erasure-coded capacity and by endpoint/path for fallback; duplicated or missing disk identity fields can still skew results. Many notification reload errors are warnings only, leaving persistence authoritative but observers possibly stale until another reload.

Test signals: Inline tests cover state-transition helpers, index validation, decommission start/cancel guards, cancellation token binding/replacement/clearing, contextual error wrappers, bucket queue operations, counter updates, current-object tracking, periodic update error cases, terminal state classification, lifecycle cleanup decision helpers, delete-marker and remote-tiered `ObjectOptions`, MessagePack persistence of resume queues, legacy payload decoding, listing worker join errors, data movement multipart abort/index helpers, and Windows path conversion. Capacity behavior is partly tested in the separate `pools_test.rs` file. The test suite is mostly unit-level; high-value integration behavior that still depends on broader e2e coverage includes full decommission under real storage, lifecycle/replication/object-lock interactions, restart/resume, and concurrent cancel/fail races.

# sources/object-store/rustfs/crates/ecstore/src/pools_test.rs

Purpose: This file provides focused unit tests for pool usable-capacity accounting, especially deduplication of duplicate disk entries. It protects against inflated total/free capacity when `StorageInfo.disks` contains repeated `rustfs_madmin::Disk` records, and verifies erasure-coding data-disk filtering.

Important APIs/types/functions: The tests import `get_total_usable_capacity`, `get_total_usable_capacity_free`, `fallback_total_capacity_dedup`, and `fallback_free_capacity_dedup` from `crate::pools`. Test fixtures use `rustfs_madmin::Disk`, `rustfs_madmin::StorageInfo`, and `rustfs_madmin::BackendInfo`, setting disk identity fields (`endpoint`, `drive_path`, `pool_index`, `set_index`, `disk_index`), capacity fields (`total_space`, `available_space`, `used_space`), `state`, and backend erasure coding fields such as `standard_sc_data` and `standard_sc_parity`.

Control flow: `test_single_disk_no_duplication` builds one online 2 TB disk with 500 GB free and backend data count `1`, then asserts total/free usable capacity exactly match the disk. `test_duplicate_disk_entries_deduped` pushes the same disk record 232 times and asserts both total and free capacity are counted once. `test_four_disk_erasure_coding` creates four 1 TB disks in one set with two data disks and two parity disks, then asserts usable total capacity includes only disk indexes below the configured data-disk count. `test_fallback_dedup` creates 100 duplicate disk records without erasure-index fields and verifies fallback total/free deduplication counts one physical disk.

State and persistence behavior: The file has no persistent state and no filesystem or object-store side effects. All state is in-memory fixture data passed directly to capacity helper functions. The important modeled state is the disk identity tuple and backend erasure coding layout; assertions check the derived reported capacity.

Dependencies and integration points: These tests exercise the public capacity helpers in `pools.rs`, which are used by `ECStore::get_decommission_pool_space_info` and therefore affect `ECStore::status` and decommission progress reporting. They also indirectly document the contract with `rustfs_madmin::StorageInfo`: `standard_sc_data` determines usable disk indexes when available, while fallback logic deduplicates by endpoint and drive path when backend layout cannot drive the calculation.

Risks: The tests cover duplicate entries, a single erasure-coded set, and fallback deduplication, but they do not cover offline disk states, negative `pool_index`, multiple pools, multiple sets, inconsistent `standard_sc_data`, zero data-disk counts, or fallback behavior with distinct disks sharing endpoint/path but different indexes. The duplicate-entry scenario assumes duplicate records have identical endpoint, drive path, pool, set, and disk indexes; partial identity duplication is left to the implementation. Free-capacity erasure coding is not explicitly checked in the four-disk parity test.

Test signals: Strong signals are exact capacities: one disk reports `2_000_000_000_000` total and `500_000_000_000` free, 232 duplicate records still report the same single-disk values, four disks with `standard_sc_data = vec![2]` report `2_000_000_000_000` total usable capacity, and 100 fallback duplicate records report one disk's total/free capacity.
