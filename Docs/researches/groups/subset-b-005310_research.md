# sources/distributed-fs/ceph-client/drivers/scsi/mpt3sas/mpi/mpi2_ioc.h

Purpose: defines the MPI v2 IOC, port, event, firmware transfer, power-management, MPI v2.6 IO Unit Control, and MCTP passthrough wire messages used by the `mpt3sas` driver. It is a protocol contract rather than executable code: structures and constants here must match firmware frame layouts byte-for-byte because request frames, reply frames, and event payloads are DMA-visible or copied directly from firmware replies.

Important APIs/types/functions: the initialization path uses `Mpi2IOCInitRequest_t`, `Mpi2IOCInitReply_t`, and `Mpi2IOCInitRDPQArrayEntry` to publish request/reply queue addresses, page size, MSI-X vector count, MPI/header versions, reply queue depths, RDPQ array mode, NVMe SGL format, and coredump enablement. Discovery and capability probing use `Mpi2IOCFactsRequest_t`/`Mpi2IOCFactsReply_t`, `Mpi2PortFactsRequest_t`/`Mpi2PortFactsReply_t`, and `Mpi2PortEnableRequest_t`/`Mpi2PortEnableReply_t`; the reply capability bits gate integrated RAID, diagnostic buffers, event replay, MSI-X index support, RDPQ array capability, NVMe protocol, coredump, SR-IOV, atomic requests, and MCTP passthrough. Event handling centers on `Mpi2EventNotificationRequest_t`, `Mpi2EventNotificationReply_t`, and `Mpi2EventAckRequest_t`; payload structs cover SAS discovery/topology/device status, IR volume and physical disk changes, log entries, temperature, power performance, active cable exceptions, SAS/PCIe topology, PCIe device status/enumeration/link counters, enclosure changes, host messages, quiesce, and SAS discovery errors. Firmware service structures include `Mpi2FWDownloadRequest`, `Mpi25FWDownloadRequest`, `Mpi2FWUploadRequest_t`, `Mpi25FWUploadRequest_t`, and their transaction-context SGEs/replies. Later sections define `Mpi2PwrMgmtControlRequest_t`, `Mpi26IoUnitControlRequest_t`, and `Mpi26MctpPassthroughRequest_t`.

Control flow: there is no runtime control flow in the header, but it drives the driver state machine. `mpt3sas_base.c` sends IOCFacts, stores the `Mpi2IOCFactsReply_t` in adapter state, allocates queues from the reported limits, then sends IOCInit and PortEnable. It posts event masks through `Mpi2EventNotificationRequest_t`, dispatches `Mpi2EventNotificationReply_t` payloads by `Event`, and issues `Mpi2EventAckRequest_t` when `AckRequired` is set. `mpt3sas_ctl.c` exposes many of these message formats to user ioctls and validates special cases such as MCTP capability, firmware upload/download, diagnostic operations, toolbox commands, and reset-producing IO Unit Control operations. `mpt3sas_scsih.c` consumes SAS and IR event data to add/remove devices, update RAID volume/physical disk state, and send remove-device IO Unit Control requests.

State and persistence: this header itself stores no state. Its fields represent persistent and transient controller state: IOCFacts persist in `struct MPT3SAS_ADAPTER` for feature gating; event masks and queue addresses remain active in firmware until reset/reinitialization; firmware download/upload image types can alter flash, backup, manufacturing, SBR, CPLD, PSOC, coredump, or product-specific regions; power-management requests change controller/PHY power modes; IO Unit Control operations can clear persistent mappings or remove devices; MCTP passthrough transfers are transient.

Dependencies and integration: depends on base MPI types and SGE/version definitions from neighboring MPI headers, especially `mpi2_type.h`, `mpi2.h`, `mpi2_cnfg.h`, and image/config page definitions. Integration points include the base bring-up/reset code, interrupt/reply processing, event workqueues, SCSI host/device management, sysfs/diagnostic trigger handling, and user passthrough ioctls. Comments explicitly require runtime bounds checks before indexing flexible arrays such as IR config elements, SAS topology PHY entries, and PCIe topology port entries.

Risks: every structure is an ABI with firmware, so field order, width, alignment, endian type, and flexible-array sizing are high risk. Several names are version-scoped (`MPI25`, `MPI26`) and must not be used blindly against older HBAs. Event payloads are variable length and copied from firmware; consumers must use `EventDataLength`, `NumElements`, and `NumEntries` instead of assuming the maximum shape. Feature bits are security and safety boundaries for dangerous operations such as firmware modification, diagnostic buffer ownership, MCTP passthrough, reset, and persistent device removal. The typo-like `MPI26_MCTP_MSG_CONEXT_UNUSED` is part of the local API and could be misread during maintenance.

Test signals: build coverage should include `mpt3sas` with MPI v2.0/v2.5/v2.6 code paths enabled. Runtime signals include successful IOCFacts/IOCInit/PortEnable on supported adapters, correct queue depth and RDPQ array setup, capability printouts matching hardware, event replay and event ack behavior, SAS/PCIe topology hotplug events, RAID config-change events, firmware upload/download rejection and success paths, diagnostic buffer post/release ioctls, MCTP passthrough capability checks, and reset recovery after IO Unit Control operations.

# sources/distributed-fs/ceph-client/drivers/scsi/mpt3sas/mpi/mpi2_pci.h

Purpose: defines MPI v2.6 PCIe attached-device constants and NVMe encapsulated request/reply layouts for `mpt3sas` tri-mode adapters. It lets the driver treat PCIe/NVMe devices as firmware-addressed endpoints while carrying native NVMe command data and optional error response buffers through MPI request frames.

Important APIs/types/functions: PCIe `DeviceInfo` masks classify direct attach, PCI switch, NVMe, SCSI, and no-device states. `Mpi26NVMeEncapsulatedRequest_t` carries `DevHandle`, the encapsulated command length, error response DMA/base address, error response allocation length, direction/submission queue/address-space flags, data length, and an inline `NVMe_Command[4]` starter field that callers size with the actual command payload. `Mpi26NVMeEncapsulatedErrorReply_t` reports IOC status/log info, encapsulated command length, and error response count. Flag constants distinguish admin versus I/O submission queues, no-data/write/read/bidirectional transfer direction, system versus ioctl error response address space, and forced admin error response generation.

Control flow: the header has no executable flow. In driver flow, passthrough ioctl handling in `mpt3sas_ctl.c` validates `MPI2_FUNCTION_NVME_ENCAPSULATED`, builds or copies a `Mpi26NVMeEncapsulatedRequest_t`, maps user data and error-response buffers, sets the direction flags, and sends the request through the base layer. The reply processing path detects NVMe encapsulated replies and copies the error response count/status back to userspace. `mpt3sas_base.c` sizes request frames specially for NVMe encapsulated commands because the inline command field is variable-length beyond the fixed structure.

State and persistence: no persistent state is owned by this header. Runtime state consists of transient DMA mappings, error response buffers, and firmware request/reply frames. The target `DevHandle` and PCIe device type come from IOC/config/event state defined elsewhere.

Dependencies and integration: depends on `mpi2_type.h` basic MPI integer aliases and broader MPI function/status definitions from `mpi2.h`/`mpi2_ioc.h`. It integrates with the adapter capability check `MPI2_IOCFACTS_PROTOCOL_NVME_DEVICES`, the ioctl passthrough path, PCIe topology/status event handling from `mpi2_ioc.h`, and PCIe configuration pages from `mpi2_cnfg.h`.

Risks: the flexible command payload and error-response DMA address are easy places for length, alignment, and address-space mistakes. Direction flags must match the mapped SGE/data buffers or firmware can DMA the wrong way. The `MPI26_*` scope means these layouts are for MPI v2.6-class devices; using them against older adapters would be a protocol mismatch. User passthrough of NVMe admin commands also needs strict capability and bounds checks.

Test signals: useful signals are ioctl tests for read, write, no-data, and admin-queue commands; invalid length and unsupported-capability rejection; correct error-response count propagation; hotplug/topology tests that identify NVMe versus switches; and reset/error injection around aborted or timed-out NVMe encapsulated commands.

# sources/distributed-fs/ceph-client/drivers/scsi/mpt3sas/mpi/mpi2_raid.h

Purpose: defines MPI Integrated RAID action messages and action-specific payloads. These structures let host utilities and the driver ask firmware to create/delete/activate volumes, change cache settings, manage physical disks and hot spares, start/stop RAID functions, set rebuild/scrub rates, perform compatibility checks, and query progress indicators.

Important APIs/types/functions: `Mpi2RaidActionRequest_t` is the central command frame, combining `Action`, volume/physical disk selectors, an `Mpi2RaidActionData_t` union, and an optional action-data SGE. The action-data union covers raw words, rate changes (`Mpi2RaidActionRateData_t`), start/stop RAID functions, hot-spare selection, and device firmware update mode. Volume creation uses `Mpi2RaidVolumeCreationStruct_t` and `Mpi2RaidVolumePhysDisk_t`, with flags for default settings, background init, low-level init, and migration. Other payloads include `Mpi2RaidOnlineCapacityExpansion_t`, `Mpi2RaidCompatibilityInputStruct_t`, `Mpi2RaidVolIndicator_t`, and `Mpi2RaidCompatibilityResultStruct_t`. `Mpi2RaidActionReply_t` returns IOC status/log info plus a reply union containing progress, volume handle/state, physical disk number, compatibility result, or raw words.

Control flow: this header does not execute code. In the driver, RAID state is mostly learned through config pages and events, while action frames can be sent through the generic passthrough/control path. `mpt3sas_ctl.c` recognizes `MPI2_FUNCTION_RAID_ACTION` and `MPI2_FUNCTION_RAID_SCSI_IO_PASSTHROUGH` when validating user MPI requests. `mpt3sas_scsih.c`, `mpt3sas_config.c`, and `mpt3sas_warpdrive.c` consume adjacent RAID config-page definitions to maintain `_raid_device` state; the action definitions here are the active-command counterpart to that passive config/event state.

State and persistence: the header owns no state, but many actions mutate persistent controller RAID metadata: volume membership, hot-spare assignment, volume names, write-cache settings, physical disk hidden/offline/failed state, and rebuild/consistency-check progress. `Mpi2RaidVolIndicator_t` and operation-status events provide transient progress state including block counts, operation type, percent complete, and elapsed seconds.

Dependencies and integration: depends on MPI SGE definitions and RAID/config constants from `mpi2.h` and `mpi2_cnfg.h`, including volume type and cache setting defines referenced by comments. It integrates with IOCFacts integrated-RAID capability, IR event handling in `mpi2_ioc.h`, config-page helpers for RAID volume and physical disk pages, SCSI exposure of volumes, and management ioctls.

Risks: these messages can permanently alter arrays, so action selection and user authorization/bounds checking matter. `MPI2_RAID_VOL_CREATION_NUM_PHYSDISKS` defaults to `1` but is intended to be build-customizable; code that assumes the default cannot describe larger creation requests without an external SGE or adjusted compile-time value. The obsolete `MPI2_RAID_VOL_CREATION_USE_DEFAULT_SETTINGS` define has a misleading bit position and should not be used for new code. Reply union interpretation depends entirely on the requested action and IOC status.

Test signals: test through management tooling or mocked MPI frames for each action family, especially create/delete, hot-spare add/delete, compatibility checks, progress indicators, and firmware rejection paths. Driver-level signals include correct integrated-RAID capability gating, RAID event handling after actions, config-page refresh after state changes, and no regression in WarpDrive/fast-path RAID0 handling.

# sources/distributed-fs/ceph-client/drivers/scsi/mpt3sas/mpi/mpi2_sas.h

Purpose: defines MPI Serial Attached SCSI status values, SAS device-info flags, SMP passthrough, SATA passthrough, and pre-MPI-v2.6 SAS IO Unit Control messages. These layouts are the protocol bridge between Linux SAS transport/SCSI management operations and firmware-controlled SAS/SATA links.

Important APIs/types/functions: `MPI2_SASSTATUS_*` constants describe firmware SAS protocol outcomes. `MPI2_SAS_DEVICE_INFO_*` flags classify device type and roles such as SSP/STP/SMP target or initiator, SATA device/host, ATAPI, enclosure processor, expander, direct attach, and LSI device. `Mpi2SmpPassthroughRequest_t`/`Reply_t` carry SMP request and response buffers through an SGE, optionally using immediate mode. `Mpi2SataPassthroughRequest_t`/`Reply_t` carry ATA FIS command/status data, transfer direction, DMA/PIO/FPDMA flags, data length, and an MPI/IEEE SGE union. `Mpi2SasIoUnitControlRequest_t`/`Reply_t` cover link reset, hard reset, clear error log, force full discovery, remove device, mapping lookup, IOC parameter setting, fast-path enable/disable, NCQ enable/disable, and persistent clearing for MPI v2.5 and earlier.

Control flow: the header is declarative. Runtime consumers include `mpt3sas_transport.c`, which builds SMP passthrough frames for SAS expander access and sends IO Unit Control link resets from transport PHY reset operations; `mpt3sas_base.c`, which sizes request frames and synchronously issues SAS IO Unit Control operations; and `mpt3sas_scsih.c`, which sends remove-device IO Unit Control messages during topology cleanup. `mpt3sas_ctl.c` validates passthrough ioctl functions for SMP, SATA, and SAS IO Unit Control and treats PHY link/hard reset as reset-sensitive operations.

State and persistence: no local state is stored. Requests affect live SAS/SATA link state, firmware discovery tables, NCQ/fast-path settings, and device presence. Clear-all-persistent and remove-device operations can alter firmware persistence or cached topology state. SMP/SATA passthrough data buffers are transient DMA mappings.

Dependencies and integration: depends on MPI SGE unions from the common MPI headers. It integrates with the Linux SAS transport class, libsas-like expander access paths, SCSI error handling and target reset flow, config pages for SAS device/PHY/IO unit data, event structures from `mpi2_ioc.h`, and user passthrough ioctls.

Risks: passthrough requests expose low-level link/device operations, so malformed FIS/SMP lengths, SGE direction mismatches, or missing reset serialization can disrupt buses. The SAS IO Unit Control section is explicitly replaced by MPI v2.6 IO Unit Control in `mpi2_ioc.h`; version-aware callers must choose the right operation constants. Flexible SGE union members differ between MPI v2.0 and v2.5, which is an ABI risk when building request frames.

Test signals: transport-layer tests should exercise SMP expander access, PHY hard/link reset, SATA passthrough read/write and FPDMA cases, NCQ toggle behavior, remove-device cleanup, timeout/reset handling, and firmware responses for each `MPI2_SASSTATUS_*` class. Hotplug and topology-change events are important end-to-end signals because they verify these control messages and event/config refreshes agree.

# sources/distributed-fs/ceph-client/drivers/scsi/mpt3sas/mpi/mpi2_tool.h

Purpose: defines MPI toolbox and diagnostic-buffer message formats. These are management and service interfaces for flash/NVRAM cleanup, memory movement, diagnostic upload/CLI, ISTWI/I2C-style access, beacon control, text display, PCIe lane margining, trace/snapshot/extended diagnostic buffer posting, and diagnostic buffer release.

Important APIs/types/functions: `Mpi2ToolboxReply_t` is the common toolbox reply. Request layouts include `Mpi2ToolboxCleanRequest_t`, `Mpi2ToolboxMemMoveRequest_t`, `Mpi2ToolboxDiagDataUploadRequest_t`, `Mpi2ToolboxIstwiReadWriteRequest_t`, `Mpi2ToolboxBeaconRequest_t`, `Mpi2ToolboxDiagnosticCliRequest_t`, `Mpi25ToolboxDiagnosticCliRequest_t`, `Mpi2ToolboxTextDisplayRequest_t`, and `Mpi26ToolboxLaneMarginingRequest_t`. Tool constants select clean, memory move, diagnostic data upload, ISTWI, beacon, diagnostic CLI, text display, and backend PCIe lane margining. Diagnostic buffer interfaces use `Mpi2DiagBufferPostRequest_t`/`Reply_t` and `Mpi2DiagReleaseRequest_t`/`Reply_t`, with buffer types for trace, snapshot, and extended utilization buffers and flags for release-on-full or immediate release.

Control flow: the header has no code, but `mpt3sas_ctl.c` uses these definitions heavily for user management ioctls. It validates toolbox commands, blocks or special-cases diagnostic CLI and PCIe lane margining, validates memory-move SGEs, posts diagnostic buffers through `MPI2_FUNCTION_DIAG_BUFFER_POST`, updates `ioc->diag_buffer_status`, copies/retrieves released buffers, and releases them with `MPI2_FUNCTION_DIAG_RELEASE`. Diagnostic trigger code watches events and releases trace buffers when configured conditions match.

State and persistence: toolbox clean flags can erase persistent flash, SEEPROM, NVRAM, manufacturing pages, SBR, boot services, backup firmware, HII, controller, MegaRAID, and product-specific regions. Diagnostic buffer post/release state is maintained outside the header in adapter fields such as registered/released/driver-allocated/app-owned flags, DMA addresses, buffer sizes, and release conditions. Beacon, text display, lane margining, ISTWI, and diagnostic CLI operations are transient controller service actions.

Dependencies and integration: depends on MPI SGE unions, IOC capability bits for diagnostic trace/snapshot/extended buffers, and the control ioctl layer. It integrates with sysfs diagnostic trigger/release paths, DMA allocation/freeing, user copy APIs, firmware reset handling, and management tooling that understands Broadcom/Avago toolbox commands.

Risks: many toolbox operations are destructive or privileged. Clean flags can wipe firmware and NVRAM regions; memory move uses host-provided SGEs; diagnostic CLI and ISTWI can expose low-level controller internals; diagnostic buffers require careful ownership and release-state transitions to avoid DMA use-after-free or leaking stale diagnostic contents. `MPI2_DIAG_BUF_TYPE_COUNT` must stay aligned with arrays indexed by buffer type. MPI v2.0 versus v2.5 diagnostic CLI SGE layout differences are another ABI risk.

Test signals: ioctl tests should cover diagnostic buffer register/query/read/release paths, all supported buffer types and capability rejections, release-on-full and trigger release behavior, reset cleanup, app-owned versus driver-owned transitions, memory-move validation, toolbox clean rejection/authorization in management paths, ISTWI read/write length handling, beacon toggles, and lane-margining command framing.

# sources/distributed-fs/ceph-client/drivers/scsi/mpt3sas/mpi/mpi2_type.h

Purpose: provides the foundational MPI v2 scalar and pointer typedefs used by all neighboring Fusion-MPT MPI protocol headers. It maps MPI names onto Linux fixed-width little-endian types so on-wire structures can express firmware byte order directly.

Important APIs/types/functions: when `MPI_TYPE_H` has not already provided them, it defines `U8` as `u8`, `U16` as `__le16`, `U32` as `__le32`, and `U64` as aligned `__le64`. Pointer aliases `PU8`, `PU16`, `PU32`, and `PU64` are also provided. There are no functions or runtime APIs.

Control flow: there is no runtime behavior. The include guard and `MPI_TYPE_H` check prevent duplicate typedefs when an older/common MPI type header is already included.

State and persistence: no state is stored. The persistent effect is compile-time: every MPI request, reply, config page, event, and SGE structure using these aliases documents little-endian firmware fields.

Dependencies and integration: depends on Linux kernel type definitions already being visible through the including path. It is included directly or indirectly by the MPI header set under `drivers/scsi/mpt3sas/mpi`, including IOC, SAS, PCIe, RAID, toolbox, config, and image headers.

Risks: endian annotations matter. Treating `U16`/`U32`/`U64` as CPU-native integers without `le16_to_cpu()`, `cpu_to_le16()`, and related helpers can break on big-endian systems and obscure sparse warnings. The explicit 4-byte alignment on `U64` is part of the firmware ABI; changing it can shift fields in packed-like protocol structures. Pointer aliases are legacy style and should not encourage unchecked casts from arbitrary buffers without size validation.

Test signals: compile with sparse/endian checking, build on architectures with strict alignment and non-little-endian configurations where possible, and run structure-size/offset-sensitive driver tests that exercise IOC init, passthrough, events, config pages, and diagnostic buffer requests.
