# sources/distributed-fs/ceph-client/drivers/scsi/qedi/qedi_iscsi.c

Purpose: implements the libiscsi/scsi_transport_iscsi-facing half of the QLogic FastLinQ QEDI iSCSI offload driver. It exposes the SCSI host template, iSCSI transport callbacks, endpoint connect/poll/disconnect lifecycle, connection/session setup and teardown, generic PDU staging, SCSI task transmit and cleanup, path-resolution handoff to userspace, hardware connection offload/update calls through `qedi_ops`, and recovery escalation for link, TCP, and iSCSI firmware errors.

Important APIs/types/functions: `qedi_host_template` binds the driver to SCSI core using libiscsi queueing and error handlers, with a QEDI host reset wrapper that calls `qedi_recover_all_conns()`. Session APIs are `qedi_session_create()` and `qedi_session_destroy()`, which clamp queue depth, call `iscsi_session_setup()`, and allocate per-task DMA resources. Connection APIs are `qedi_conn_create()`, `qedi_conn_bind()`, `qedi_conn_start()`, and `qedi_conn_destroy()`. Endpoint APIs are `qedi_ep_connect()`, `qedi_ep_poll()`, `qedi_ep_disconnect()`, and `qedi_set_path()`. Data-path hooks include `qedi_task_xmit()`, `qedi_mtask_xmit()`, `qedi_iscsi_send_generic_request()`, `qedi_cleanup_task()`, and the exported `qedi_iscsi_transport`. Recovery/error helpers include `qedi_start_conn_recovery()`, `qedi_process_iscsi_error()`, `qedi_process_tcp_error()`, `qedi_mark_device_missing()`, and `qedi_mark_device_available()`.

Control flow: user/session creation starts with an endpoint returned by `qedi_ep_connect()`. That endpoint records the destination address, allocates the send queue, acquires a hardware connection handle from QED, stores the endpoint in `qedi->ep_tbl`, and sends an `ISCSI_KEVENT_PATH_REQ` to userspace so `iscsiuio` can resolve source IP, MAC, VLAN, PMTU, and local port. `qedi_set_path()` receives that path, validates the MAC/MTU, updates host IP state, allocates or preserves a local TCP source port from `lcl_port_tbl`, and queues `qedi_offload_work()`. The work item calls `qedi_iscsi_offload_conn()`, builds TCP/iSCSI offload parameters, registers the doorbell for recovery, invokes `qedi_ops->offload_conn()`, and waits for firmware to signal `EP_STATE_OFLDCONN_COMPL`. Later `qedi_conn_bind()` associates the libiscsi connection with the endpoint and connection-id table, while `qedi_conn_start()` pushes negotiated digest/R2T/burst settings into firmware through `qedi_iscsi_update_conn()` before starting libiscsi.

State and persistence behavior: runtime state is in `struct qedi_endpoint`, `struct qedi_conn`, libiscsi session/connection objects, and tables owned by `struct qedi_ctx`. Per-connection login and text/NOP/TMF buffers are coherent DMA allocations in `generic_pdu_resc`; per-task SGE and sense buffers are allocated during session setup. Endpoint state uses the `EP_STATE_*` bit-like constants from `qedi_iscsi.h` and wait queues `ofld_wait`/`tcp_ofld_wait` to bridge userspace path resolution, firmware connect completion, and disconnect completion. `qedi->cid_que.conn_cid_tbl` and `qedi->ep_tbl` map firmware/software connection IDs to QEDI objects; `qedi->lcl_port_tbl` persists allocated source ports until endpoint disconnect. No disk persistence occurs here, but negotiated connection attributes, doorbell recovery registration, and offload state are persisted in firmware until destroy/release paths run.

Dependencies and integration points: depends on SCSI core, libiscsi, scsi_transport_iscsi, net address/VLAN helpers, coherent DMA APIs, and QEDI internal headers. It calls lower-level transmit helpers declared elsewhere (`qedi_send_iscsi_login()`, `qedi_send_iscsi_nopout()`, `qedi_send_iscsi_logout()`, `qedi_send_iscsi_tmf()`, `qedi_send_iscsi_text()`, `qedi_iscsi_send_ioreq()`, `qedi_clearsq()`, `qedi_iscsi_unmap_sg_list()`) and QED hardware operations through global `qedi_ops`. It cooperates with `qedi_main.c` for PCI probe, interrupt/completion handling, task-id maps, LL2/UIO path discovery, queue allocation, link updates, and recovery work.

Risks and test signals: high-risk areas are connection lifetime races between endpoint disconnect, offload work, firmware async events, and libiscsi recovery; correct cleanup of coherent DMA buffers on partial allocation failures; table bounds for `iscsi_cid`; task-id cleanup after transmit failure; local port leaks; and waits that can sleep while firmware or userspace path resolution is stuck. `qedi_mtask_xmit()` copies `task->data_count` into a fixed login/generic PDU buffer and relies on libiscsi limits to avoid overflow. `qedi_process_iscsi_error()` has an always-zero `err_mask`, so known errors become recovery-triggering errors and unknown errors do not. Test signals should include IPv4 and IPv6 login/logout, digest negotiation, NOP/text/TMF paths, path-resolution failure with invalid MAC, MTU changes through `qedi_reset_host_mtu()`, local port reuse, offload timeout, disconnect during in-flight TMF cleanup, link-down recovery, host reset recovery for all connections, shutdown/offline behavior, and leak/race checks around session teardown.

# sources/distributed-fs/ceph-client/drivers/scsi/qedi/qedi_iscsi.h

Purpose: defines the QEDI iSCSI transport-side contract shared by `qedi_iscsi.c`, `qedi_main.c`, completion processing, and transmit/recovery helpers. It captures endpoint state values, default TCP/offload tuning constants, MTU/header sizes, per-endpoint queue metadata, per-connection generic PDU resources, per-command DMA/task state, TMF work tracking, boot target formatting state, and ITT encoding helpers.

Important APIs/types/functions: constants include `ISCSI_MAX_SESS_PER_HBA`, TCP keepalive/retransmit defaults, default MTU/MSS values, `JUMBO_MTU`, IP/TCP/VLAN header lengths, and `QEDI_SQ_WQES_MIN`. The endpoint state enum is central to connect/disconnect flow, covering idle, acquire, offload start/complete/fail/none, disconnect start/complete/timeout, TCP FIN/RST, logout, cleanup, and connect failure states. `struct qedi_endpoint` stores addresses, ports, VLAN, PMTU, MACs, IP family, wait queues, connection IDs, QED handle/doorbell, send queue and PBL DMA, and offload work. `struct generic_pdu_resc` contains coherent buffers and BD tables for login/generic PDU request/response payloads. `struct qedi_conn` wraps libiscsi connection state, active command list, cleanup counters, firmware CIDs, generic PDU resources, TMF work list, and disconnect coordination fields. `struct qedi_cmd` carries per-task header, SGE table, task context, sense DMA, task ID, cleanup/TMF state, slowpath flag, and embedded CQE work. Macros `qedi_set_itt()`, `qedi_get_itt()`, and `QEDI_OFLD_WAIT_STATE()` encode task IDs and endpoint wait predicates.

Control flow: this header has no executable flow, but its fields describe the main state transitions. `qedi_ep_connect()` creates and initializes `qedi_endpoint`, allocates SQ/PBL members, and waits for path/offload progress through the endpoint wait queues. `qedi_conn_bind()` links `qedi_conn` to `qedi_endpoint` and uses `iscsi_conn_id`/`fw_cid` fields for table and firmware lookup. `qedi_task_xmit()` fills `qedi_cmd` fields, maps data into `qedi_io_bdt`, and uses the ITT helpers to correlate firmware completions to commands. TMF cleanup and endpoint disconnect use `tmf_work_list`, `fw_cleanup_works`, `wait_queue`, and `ep_disconnect_starting` to drain cleanup work before destroying a hardware connection.

State and persistence behavior: all state is runtime-only and scoped to an adapter, endpoint, connection, or libiscsi task. DMA addresses in endpoint, command, and generic PDU structures are firmware-visible and must stay valid until matching free/cleanup paths complete. `active_cmd_count`, `cmd_cleanup_req`, `cmd_cleanup_cmpl`, and cleanup-state constants coordinate firmware cleanup with libiscsi error handling. `qedi_boot_target` is only a small in-memory formatter for matching NVM boot target information against live sessions. No NVM layout is defined here; persistent boot data comes from `qedi_nvm_iscsi_cfg.h` and is consumed in `qedi_main.c`.

Dependencies and integration points: includes socket and completion types plus local `qedi.h`, and assumes SCSI, libiscsi, ethernet, DMA, and firmware queue structures are already available through included QEDI headers. The structures are used by `qedi_iscsi.c` for transport callbacks, `qedi_main.c` for queue allocation/completion and boot target matching, and lower-level IO/TMF helpers for WQE construction and CQE processing.

Risks and test signals: structure fields cross many modules, so layout or semantic changes have broad impact. Endpoint state is represented as distinct numeric values but some values are bit-like; code compares for equality in wait predicates and switch statements, so combining flags would break flow. DMA pointer fields require strict ownership and zeroing after free. `qedi_cmd.task_id` uses `U16_MAX` as an invalid sentinel while task maps may have larger compile-time limits, so bounds discipline matters. Test signals should cover all endpoint states, ITT encode/decode consistency, task cleanup after successful and failed sends, disconnect while `fw_cleanup_works` is nonzero, and build coverage for all users of the shared structures.

# sources/distributed-fs/ceph-client/drivers/scsi/qedi/qedi_main.c

Purpose: implements the PCI/QED hardware-facing half of the QEDI iSCSI offload driver. It owns module parameters, QED operation registration, PCI probe/remove/shutdown/recovery, adapter allocation, queue and DMA memory setup, interrupt registration, per-CPU completion threads, LL2/UIO path-discovery plumbing for `iscsiuio`, NVM iSCSI boot information export, link and hardware error callbacks, task/ITT maps, and adapter recovery.

Important APIs/types/functions: module-global setup includes `qedi_ops`, `qedi_scsi_transport`, `qedi_pci_driver`, per-CPU `qedi_percpu`, and `qedi_udev_list`. QED event integration is handled by `qedi_iscsi_event_cb()`, `qedi_link_update()`, `qedi_schedule_recovery_handler()`, `qedi_schedule_hw_err_handler()`, and `qedi_cb_ops`. UIO/LL2 APIs include `qedi_alloc_uio_rings()`, `qedi_init_uio()`, `qedi_uio_open()`, `qedi_uio_close()`, `qedi_ll2_rx()`, `qedi_ll2_process_skb()`, and `qedi_ll2_recv_thread()`. Hardware resources are prepared by `qedi_set_iscsi_pf_param()`, `qedi_alloc_global_queues()`, `qedi_alloc_bdq()`, `qedi_prepare_fp()`, `qedi_setup_int()`, and `qedi_request_msix_irq()`. Completion processing flows through `qedi_msix_handler()`, `qedi_process_completions()`, `qedi_queue_cqe()`, and `qedi_percpu_io_thread()`. Task maps use `qedi_get_task_idx()`, `qedi_clear_task_idx()`, `qedi_update_itt_map()`, `qedi_get_task_tid()`, and `qedi_get_cmd_from_tid()`. Boot/NVM support uses `qedi_get_boot_info()`, `qedi_get_nvram_block()`, `qedi_setup_boot_info()`, and `qedi_show_boot_*()` helpers. Lifecycle entry points are `qedi_init()`, `qedi_cleanup()`, `qedi_probe()`, `qedi_remove()`, `qedi_shutdown()`, `__qedi_probe()`, `__qedi_remove()`, and `qedi_recovery_handler()`.

Control flow: module init obtains QED iSCSI ops, initializes debugfs if enabled, registers the QEDI iSCSI transport, creates CPU hotplug state that starts one per-CPU CQE processing thread, and registers the PCI driver. Normal PCI probe allocates an iSCSI host and `qedi_ctx`, probes the QED device for iSCSI protocol, fills device info, allocates PF queues/BDQ/NVM buffers, prepares fastpath status blocks, starts QED slowpath, configures interrupts, arms BDQ doorbells, stores MAC/name, registers callbacks, starts LL2, starts the QED iSCSI function, brings link up, adds the SCSI/iSCSI host, allocates UIO rings, initializes CID/endpoint/ITT maps, creates TMF and offload workqueues, initializes recovery work, reserves task ID 0, creates boot sysfs objects, and marks driver state to management firmware. Remove/shutdown tears those pieces down in reverse, including host removal, workqueues, debugfs, interrupts, QED stop/LL2 stop/slowpath stop/remove, DMA queue memory, CID/endpoint/port tables, UIO, ITT map, LL2 thread/skbs, boot kset, and SCSI host.

State and persistence behavior: `struct qedi_ctx` is the adapter root and persists for the lifetime of the PCI device or across recovery re-probe. It contains hardware handles, flags (`QEDI_IN_RECOVERY`, `QEDI_IN_SHUTDOWN`, `QEDI_IN_OFFLINE`, UIO state), link state, PF parameters, global CQ/BDQ/NVM DMA memory, endpoint and CID tables, local-port bitmap, ITT map, completion queues, workqueues, LL2 skb list, UIO memory, boot kset, and statistics locks. Per-CPU state persists through CPU hotplug and carries work lists plus kthreads. NVM iSCSI boot data is read from firmware image `QED_NVM_IMAGE_ISCSI_CFG` into a coherent buffer and exported via `iscsi_boot_sysfs`; this file reads and reports persistent firmware configuration but does not write it. Firmware image fields are also fed into management firmware TLV callbacks.

Dependencies and integration points: depends on PCI, SCSI core, libiscsi transport registration, CPU hotplug, kthreads, UIO, LL2 networking, debugfs, DMA coherent memory, QED common/iSCSI/LL2 operations, iscsi_boot_sysfs, and local QEDI headers. It integrates with `qedi_iscsi.c` for exported transport object, connection recovery, endpoint/table operations, SQ allocation, and MTU reset. It calls `qedi_fp_process_cqes()` and other completion/IO helpers from the rest of the driver. Userspace `iscsiuio` integration is through UIO memory regions and LL2 ARP/IP/IPv6 frame delivery; path setup returns via `qedi_set_path()` in `qedi_iscsi.c`.

Risks and test signals: probe/remove/recovery is high risk because many resources are allocated in staged order and recovery mode reuses an existing `qedi_ctx` while reinitializing hardware. Failure labels in `__qedi_probe()` must stay aligned with which resources are available. Completion handling depends on firmware producer indexes, CQ wrap, per-CPU thread availability, and valid `cid_que.conn_cid_tbl` entries; stale completions after disconnect are dropped. `qedi_get_cmd_from_tid()` dereferences `cmd` after looking it up from the ITT map and assumes it is non-NULL before checking `cmd->task_id`. UIO open is gated by `CAP_NET_ADMIN`, but ring counters are shared between kernel and userspace and need careful bounds testing. Boot sysfs CHAP secret display paths can pass NULL when CHAP flags are disabled if those attributes are still visible. Test signals should include full probe/remove under fault injection, recovery re-probe, PCI error callback, fan-fail board-disable work, CPU hotplug with queued CQEs, MSI-X allocation/free, LL2 receive/transmit through UIO, path discovery under VLAN and MTU changes, NVM boot sysfs for IPv4/IPv6/DHCP/CHAP/mutual CHAP, link-down session failure, task map exhaustion, and DMA leak checks across all error paths.

# sources/distributed-fs/ceph-client/drivers/scsi/qedi/qedi_nvm_iscsi_cfg.h

Purpose: defines the on-firmware NVM iSCSI boot configuration layout consumed by QEDI. It models the management-firmware iSCSI configuration image, including global/generic boot flags, initiator IPv4/IPv6 settings, target entries, CHAP credentials, LUN encoding, PF mapping metadata, and image version/signature constants.

Important APIs/types/functions: top-level sizing constants are `NUM_OF_ISCSI_TARGET_PER_PF` and `NUM_OF_ISCSI_PF_SUPPORTED`, matching iBFT and four-PF assumptions. Address/name unions include `nvm_iscsi_dhcp_vendor_id`, `nvm_iscsi_ipv4_addr`, `nvm_iscsi_ipv6_addr`, `nvm_iscsi_name`, `nvm_iscsi_chap_name`, `nvm_iscsi_chap_password`, and `nvm_iscsi_lun`. Structured layouts are `nvm_iscsi_initiator_ipv4`, `nvm_iscsi_initiator_ipv6`, `nvm_iscsi_generic`, `nvm_iscsi_initiator`, `nvm_iscsi_target`, `nvm_iscsi_block`, and `nvm_iscsi_cfg`. Bit definitions cover DHCP TCP/IP and iSCSI configuration, IPv6/fallback, iSNS modes, address redirect, CHAP/mutual CHAP, timeout fields, VLAN/IP version, IP priority, target enabled and boot-login status, TCP port, target IP version, block PF mapping, non-empty/mapped flags, and image signature/version.

Control flow: this header only declares binary layouts, but `qedi_main.c` uses them after `qedi_get_boot_info()` reads `QED_NVM_IMAGE_ISCSI_CFG` into `qedi->iscsi_image`. `qedi_get_nvram_block()` walks `nvm_iscsi_cfg.block[]`, extracts block flags and mapped PF ID from `block->id`, and selects the block matching the adapter absolute PF ID. Boot sysfs helpers then inspect `generic.ctrl_flags`, `initiator.generic_cont0`, initiator address/name fields, and the primary/secondary target records to format Ethernet, initiator, and target sysfs attributes. Management TLV code also reads CHAP flags and target information from this layout.

State and persistence behavior: the structs represent persistent firmware/NVM state, not kernel-owned mutable runtime state. The comments record byte offsets and intended total block size, so padding and field widths are part of the external contract. Strings and credentials are fixed-size byte arrays, not necessarily NUL-terminated beyond firmware convention; readers use precision formatting for most names/passwords. IPv4 and IPv6 addresses can be accessed as raw bytes or word arrays, and callers decide display format from `NVM_ISCSI_CFG_GEN_IPV6_ENABLED` and per-target `ip_ver`.

Dependencies and integration points: relies on `BIT()` and field extraction macros supplied by included kernel/QEDI headers at use sites. It is consumed by QEDI boot information, MFW TLV reporting, and any code that needs to understand the iSCSI NVM image returned by QED common ops. The layout aligns with firmware definitions rather than SCSI core types.

Risks and test signals: this is an ABI-like firmware layout, so changing field sizes, order, or constants can break boot configuration parsing. Some field names contain historical typos (`primay_radius_server`, `boot_taget` in callers), so consumers must match existing names. CHAP password max length is fixed at 16 bytes, and sysfs display of secrets should be reviewed for policy and NULL handling. Tests should validate selection of the correct PF block, empty/unmapped block handling, IPv4 and IPv6 address formatting, DHCP-origin behavior, VLAN extraction, TCP port extraction, disabled target handling, primary/secondary target reporting, CHAP and mutual CHAP flags, image signature/version checks if added, and big/little-endian assumptions against real firmware images.

# sources/distributed-fs/ceph-client/drivers/scsi/qedi/qedi_sysfs.c

Purpose: provides QEDI SCSI-host sysfs attributes for link state and link speed. It is intentionally small and is wired into `qedi_host_template.shost_groups` through `qedi_shost_groups`.

Important APIs/types/functions: `qedi_dev_to_hba()` converts a sysfs `struct device` to `struct Scsi_Host` with `class_to_shost()` and then to `struct qedi_ctx` with `iscsi_host_priv()`. `port_state_show()` reports `Online` when `qedi->link_state` is `QEDI_LINK_UP`, otherwise `Linkdown`. `speed_show()` calls `qedi_ops->common->get_link()` and prints `if_link.speed / 1000` as Gbit. `DEVICE_ATTR_RO(port_state)` and `DEVICE_ATTR_RO(speed)` define read-only attributes. `qedi_shost_attr_group` and exported `qedi_shost_groups[]` package the attributes for SCSI host registration.

Control flow: after the QEDI host is registered, SCSI core creates the shost attribute group. A sysfs read of `port_state` uses the cached atomic link state that `qedi_link_update()` maintains in `qedi_main.c`. A sysfs read of `speed` queries QED common ops synchronously for current link output and formats speed. There are no write paths, allocation paths, or long-lived state transitions in this file.

State and persistence behavior: no state is stored in this file. It observes `qedi->link_state`, `qedi->cdev`, and QED link output. Output is transient and reflects current runtime link state; it is not persisted.

Dependencies and integration points: includes `qedi.h`, `qedi_gbl.h`, `qedi_iscsi.h`, and `qedi_dbg.h`. The group is referenced from `qedi_host_template` in `qedi_iscsi.c`. The speed attribute depends on global `qedi_ops` and a live QED common device.

Risks and test signals: `speed_show()` assumes `qedi_ops`, `qedi_ops->common`, and `qedi->cdev` are valid while sysfs reads are possible; remove ordering through `iscsi_host_remove()` should prevent use after teardown. `sprintf()` is used instead of `sysfs_emit()`, matching older style but worth modernizing if touching this area. Test signals should read both attributes with link up/down, during remove stress, after recovery, and with firmware returning zero or unusual link speeds.

# sources/distributed-fs/ceph-client/drivers/scsi/qedi/qedi_version.h

Purpose: centralizes QEDI driver version constants used for module metadata, UIO version reporting, QED slowpath driver identity, and probe logging.

Important APIs/types/functions: `QEDI_MODULE_VERSION` is `"8.37.0.20"`. Numeric components are `QEDI_DRIVER_MAJOR_VER`, `QEDI_DRIVER_MINOR_VER`, `QEDI_DRIVER_REV_VER`, and `QEDI_DRIVER_ENG_VER`, set to `8`, `37`, `0`, and `20`.

Control flow: this header has no executable flow. `qedi_main.c` passes the numeric version fields to `qedi_ops->common->slowpath_start()`, uses the string for `uio_info.version`, logs it at probe, and publishes it via `MODULE_VERSION()`.

State and persistence behavior: no runtime state is stored. Version values are compile-time constants and therefore persist only as built module metadata and driver-identification values passed to firmware/management interfaces.

Dependencies and integration points: consumed by QEDI source files through local includes. It should stay synchronized with any package, firmware compatibility, or management tooling expectations for this driver.

Risks and test signals: the string and numeric components can drift if one is updated without the other. Test signals are mostly build and metadata checks: verify module version output, UIO version field, QED slowpath parameters, and probe log formatting after any version bump.

# sources/distributed-fs/ceph-client/drivers/scsi/qla1280.c

Purpose: implements the QLogic ISP1020/1040/1080/1240/1280/10160/12160 PCI parallel SCSI host driver. It covers PCI discovery, firmware loading from `qlogic/*.bin`, NVRAM/default configuration, request/response ring setup, SCSI command IOCB construction, mailbox commands, interrupts, completion handling, SCSI error recovery, target negotiation, adapter reset, and module parameter parsing.

Important APIs/types/functions: `qla1280_driver_template` exposes SCSI host operations: `queuecommand`, `sdev_configure`, abort/device reset/bus reset/host reset handlers, BIOS geometry, and info string. PCI support is `qla1280_pci_tbl`, `qla1280_probe_one()`, `qla1280_remove_one()`, `qla1280_pci_driver`, `qla1280_init()`, and `qla1280_exit()`. Firmware support is `qla1280_request_firmware()`, `qla1280_load_firmware_pio()`, `qla1280_load_firmware_dma()`, `qla1280_start_firmware()`, and `qla1280_load_firmware()`. Hardware configuration uses `qla1280_read_nvram()`, `qla1280_set_defaults()`, `qla1280_nvram_config()`, `qla1280_config_bus()`, `qla1280_config_target()`, and `qla1280_set_target_parameters()`. Command flow uses `qla1280_queuecommand_lck()`, 64-bit or 32-bit `qla1280_*_start_scsi()`, `qla1280_req_pkt()`, `qla1280_isp_cmd()`, `qla1280_intr_handler()`, `qla1280_isr()`, `qla1280_status_entry()`, `qla1280_error_entry()`, `qla1280_return_status()`, and `qla1280_done()`. Error handling uses `qla1280_error_action()`, `qla1280_abort_command()`, `qla1280_device_reset()`, `qla1280_bus_reset()`, and `qla1280_abort_isp()`.

Control flow: module init optionally parses boot/module options and registers the PCI driver. Probe skips AMI subsystem devices, enables PCI bus mastering, allocates a SCSI host and `scsi_qla_host`, sets DMA mask, allocates coherent request/response rings, maps MMIO, disables interrupts, requests the IRQ, initializes the adapter, adds the SCSI host, and scans targets. Adapter initialization clears flags/registers, reads NVRAM or falls back to defaults, loads firmware under host lock, pushes NVRAM-derived settings to hardware through mailbox commands, initializes rings, performs bus resets, and marks the adapter online. Queuecommand maps the SCSI command DMA, chooses a free outstanding-command handle, builds command and continuation IOCBs in the request ring, advances the ring index, and writes mailbox4 to notify firmware. Interrupts disable adapter interrupts, run `qla1280_isr()`, collect done SRBs, call `qla1280_done()`, and then re-enable interrupts. ISR handles mailbox completions/asynchronous events and response-ring entries; status/error entries clear outstanding slots and queue completions.

State and persistence behavior: persistent runtime state lives in `struct scsi_qla_host`: PCI/MMIO references, firmware version, NVRAM copy/valid flag, bus settings, request and response rings, ring indexes and counts, outstanding command array, done queue, mailbox completion/timer state, flags, and counters. Firmware blobs are cached globally in `qla1280_fw_tbl[]` under `qla1280_firmware_mutex` and released at module exit, allowing reuse during adapter recovery. NVRAM is read from hardware once during initialization into `ha->nvram`; the driver writes derived settings to current firmware/hardware state but does not persist new NVRAM values. SCSI command state is stored in `struct srb` embedded as command private data and in `cmd->host_scribble` as a handle/completed sentinel.

Dependencies and integration points: depends on Linux PCI, DMA mapping/coherent APIs, firmware loader, MMIO register access, timers/completions, SCSI core, SCSI midlayer error handling, and local `qla1280.h` register/IOCB/NVRAM definitions. Firmware files declared via `MODULE_FIRMWARE()` are `qlogic/1040.bin`, `qlogic/1280.bin`, and `qlogic/12160.bin`. The driver integrates with the SCSI device configure path to set queue depth and negotiation flags based on NVRAM and discovered device capabilities.

Risks and test signals: this is legacy hardware code with many lock drops around mailbox commands and error recovery. Risks include races between error handling and normal completions, mailbox timeout behavior, use of `host_scribble` for handles, stale `outstanding_cmds` entries, DMA mapping cleanup on queuecommand failure after partial setup, request-ring free-space accounting, response-ring handle validation, NVRAM endian/format assumptions, firmware request lifetime, and reset recovery while commands are pending. `qla1280_req_pkt()` busy-waits with polling and can be called from interrupt context. `qla1280_status_entry()` indexes `ha->outstanding_cmds[pkt->handle]` in a debug print path before full validation in one branch. Test signals should include firmware load failure and invalid firmware length, NVRAM checksum failure/default config, 32-bit and 64-bit DMA builds, command queue saturation returning `SCSI_MLQUEUE_HOST_BUSY`, large scatter-gather requiring continuation entries, mailbox timeout and completion, interrupt-driven and polled completions, CHECK CONDITION sense copy, target busy/queue full, abort/device/bus/adapter reset, dead-bus detection, remove while idle and with outstanding commands, and module exit releasing cached firmware images.
