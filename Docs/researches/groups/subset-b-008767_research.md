# sources/storage-engines/sqlite/src/btree.h

## Purpose

`btree.h` is the public interface for SQLite's B-tree storage subsystem. It exposes the opaque `Btree`, `BtCursor`, `BtShared`, and `BtreePayload` types used by higher layers, and declares the entry points used by the pager/VDBE/schema layers to open database files, manage transactions, create and destroy tables, open cursors, move through table/index b-trees, read/write payloads, maintain database-header metadata, and run integrity checks. The header is deliberately interface-heavy and implementation-light; detailed page layout, cursor state, shared-cache internals, and pointer-map details live in `btreeInt.h`.

## Important APIs, Types, and Flags

The central lifecycle APIs are `sqlite3BtreeOpen()`, `sqlite3BtreeClose()`, `sqlite3BtreeSetPageSize()`, `sqlite3BtreeGetPageSize()`, `sqlite3BtreeSetCacheSize()`, `sqlite3BtreeSetSpillSize()`, `sqlite3BtreeSetPagerFlags()`, `sqlite3BtreeMaxPageCount()`, `sqlite3BtreeLastPage()`, `sqlite3BtreeSecureDelete()`, `sqlite3BtreeSetAutoVacuum()`, and `sqlite3BtreeGetAutoVacuum()`. `sqlite3BtreeOpen()` accepts both btree-layer flags (`BTREE_OMIT_JOURNAL`, `BTREE_MEMORY`, `BTREE_SINGLE`, `BTREE_UNORDERED`) and VFS open flags, making it the bridge between SQLite connection setup and the pager/VFS stack.

Transaction APIs are `sqlite3BtreeBeginTrans()`, `sqlite3BtreeCommitPhaseOne()`, `sqlite3BtreeCommitPhaseTwo()`, `sqlite3BtreeCommit()`, `sqlite3BtreeRollback()`, `sqlite3BtreeBeginStmt()`, `sqlite3BtreeSavepoint()`, `sqlite3BtreeTxnState()`, and, when WAL is enabled, `sqlite3BtreeCheckpoint()`. The commit API is explicitly split into two phases for multi-database commit coordination and rollback-journal/WAL interactions.

Schema and metadata APIs include `sqlite3BtreeSchema()`, `sqlite3BtreeSchemaLocked()`, `sqlite3BtreeGetMeta()`, `sqlite3BtreeUpdateMeta()`, `sqlite3BtreeNewDb()`, `sqlite3BtreeSetVersion()`, and the metadata indexes `BTREE_FREE_PAGE_COUNT`, `BTREE_SCHEMA_VERSION`, `BTREE_FILE_FORMAT`, `BTREE_DEFAULT_CACHE_SIZE`, `BTREE_LARGEST_ROOT_PAGE`, `BTREE_TEXT_ENCODING`, `BTREE_USER_VERSION`, `BTREE_INCR_VACUUM`, `BTREE_APPLICATION_ID`, and virtual `BTREE_DATA_VERSION`. The comment maps these indexes to database-header offsets by `36 + idx*4`, so callers in `build.c` and other schema code can manipulate file-format, text-encoding, and schema-cookie fields through the btree abstraction.

Structural mutation APIs are `sqlite3BtreeCreateTable()`, `sqlite3BtreeDropTable()`, `sqlite3BtreeClearTable()`, `sqlite3BtreeClearTableOfCursor()`, `sqlite3BtreeTripAllCursors()`, `sqlite3BtreeIncrVacuum()`, `sqlite3BtreeTransferRow()`, and `sqlite3BtreeClearCache()`. Table creation flags distinguish rowid-table b-trees (`BTREE_INTKEY`) from index/WITHOUT ROWID b-trees (`BTREE_BLOBKEY`).

Cursor APIs form the data-access contract used by the VDBE: `sqlite3BtreeCursor()`, `sqlite3BtreeCloseCursor()`, `sqlite3BtreeTableMoveto()`, `sqlite3BtreeIndexMoveto()`, `sqlite3BtreeCursorHasMoved()`, `sqlite3BtreeCursorRestore()`, `sqlite3BtreeFirst()`, `sqlite3BtreeLast()`, `sqlite3BtreeNext()`, `sqlite3BtreePrevious()`, `sqlite3BtreeEof()`, `sqlite3BtreeIntegerKey()`, `sqlite3BtreePayload()`, `sqlite3BtreePayloadFetch()`, `sqlite3BtreePayloadSize()`, `sqlite3BtreeMaxRecordSize()`, `sqlite3BtreeInsert()`, `sqlite3BtreeDelete()`, `sqlite3BtreeCount()`, and incremental-blob helpers under `SQLITE_OMIT_INCRBLOB`. Cursor flags include write cursors (`BTREE_WRCSR`), delete-only optimization hints (`BTREE_FORDELETE`), insert/delete hints (`BTREE_SAVEPOSITION`, `BTREE_AUXDELETE`, `BTREE_APPEND`, `BTREE_PREFORMAT`), and hint flags (`BTREE_BULKLOAD`, `BTREE_SEEK_EQ`).

`BtreePayload` is the key insert payload contract. For rowid tables, `pKey` is `NULL`, `nKey` is the integer rowid, and `pData`/`nData`/`nZero` describe the table record. For indexes and WITHOUT ROWID tables, `pKey`/`nKey` contain the encoded key, and `aMem`/`nMem` may expose decomposed values. This split lets the btree layer operate on both table and index b-trees without exposing page-format internals to the VDBE.

## Control Flow and State

At runtime, higher layers open a `Btree`, configure pager/cache/page-size settings, begin a transaction, create/open cursors, move cursors to entries, read or mutate cells, and commit or roll back. `sqlite3FinishCoding()` and DDL code in `build.c` rely on the metadata constants and btree transaction opcodes generated by the VDBE; the actual btree methods implement the storage-side work. Cursor movement follows a seek/restore pattern: external callers can ask whether a cursor moved, restore a saved position, or pin/unpin it while reading payload. This is critical because writes may rebalance pages and invalidate raw page pointers.

Shared-cache builds add mutex and table-lock APIs: `sqlite3BtreeLockTable()`, `sqlite3BtreeEnter()`, `sqlite3BtreeLeave()`, `sqlite3BtreeEnterAll()`, `sqlite3BtreeLeaveAll()`, `sqlite3BtreeEnterCursor()`, `sqlite3BtreeLeaveCursor()`, `sqlite3BtreeSharable()`, and debug mutex assertions. Non-shared-cache builds macro many of these to no-ops, preserving call-site simplicity while avoiding unnecessary locking.

## Persistence Behavior

The header defines the stable interface for persistent database state: page size, reserved bytes, secure-delete behavior, auto-vacuum mode, header metadata, schema cookies, file-format version, largest root page, and text encoding. `BTREE_AUTOVACUUM_NONE`, `BTREE_AUTOVACUUM_FULL`, and `BTREE_AUTOVACUUM_INCR` are persisted through header metadata and interpreted by the implementation to decide whether pointer-map pages and truncation work are required. `BTREE_DATA_VERSION` is explicitly virtual: it is read like metadata but computed by the pager rather than stored directly in the database header.

Table/index b-tree type flags determine on-disk cell semantics. `BTREE_INTKEY` is used for SQL rowid tables and stores a 64-bit integer key with separate payload. `BTREE_BLOBKEY` is used for indexes and WITHOUT ROWID tables, where the key itself encodes the record identity and content. Insert/delete flags provide persistence hints but must not weaken correctness; for example, `BTREE_APPEND` may optimize append paths but cannot assume the caller's prediction is true.

## Dependencies and Integration Points

`btree.h` depends on core SQLite types such as `sqlite3`, `sqlite3_vfs`, `Pgno`, `Pager`, `KeyInfo`, `UnpackedRecord`, `Mem`, `sqlite3_value`, `Schema`, and `BtCursor`, most of which are declared through `sqliteInt.h` and related internal headers. It is consumed broadly by the VDBE, schema builder, pager-facing code, integrity-check code, backup API, incremental blob API, WAL checkpoint paths, and shared-cache locking logic.

The file connects directly to `build.c`: schema-building code uses `BTREE_FILE_FORMAT`, `BTREE_TEXT_ENCODING`, and `BTREE_SCHEMA_VERSION` in generated `OP_ReadCookie`/`OP_SetCookie` opcodes; table/index creation emits `OP_CreateBtree` with `BTREE_INTKEY` or `BTREE_BLOBKEY`; temporary databases are opened with `sqlite3BtreeOpen()` and configured with `sqlite3BtreeSetPageSize()`; read-only checks use `sqlite3BtreeIsReadonly()`.

## Risks and Edge Cases

The API is sensitive to transaction state and mutex discipline. Cursor operations against moved or invalidated pages must use restore and movement checks correctly or risk reading wrong data after rebalance or concurrent shared-cache changes. The `BTREE_FORDELETE` flag is only a hint for alternative storage engines; SQLite's native engine ignores it, so callers must not depend on it for semantic behavior.

Metadata index constants are part of the database file contract. Changing them would corrupt interpretation of the database header and break compatibility. `BTREE_DATA_VERSION` is a special virtual meta-value in the same API space, so implementation and callers must avoid treating every meta index as a writable header field.

Compile-time feature gates can remove WAL, shared-cache mutex calls, incremental blob support, cursor hints, mmap limit support, and test/debug APIs. New code using this interface must honor the same guards or it will break reduced builds.

## Test Signals

Good test coverage should exercise DDL paths that create rowid tables, indexes, WITHOUT ROWID tables, temp tables, and auto-vacuum databases because those paths use different btree flags and metadata. Transaction tests should cover begin/commit phase split, rollback, savepoints, statement rollback, WAL checkpointing, and backup interactions. Cursor tests should include payload fetch across overflow pages, cursor movement after inserts/deletes, `BTREE_APPEND`, `BTREE_SAVEPOSITION`, incremental blob reads/writes, and shared-cache table locks. Integrity-check tests should call through `sqlite3BtreeIntegrityCheck()` and verify corruption detection for duplicate pages, orphaned pages, malformed overflow chains, and bad root-page metadata.

# sources/storage-engines/sqlite/src/btreeInt.h

## Purpose

`btreeInt.h` is the private implementation header for SQLite's disk-backed B-tree engine. It documents the database file and page layout, defines in-memory structures derived from on-disk pages, and supplies macros/constants used by `btree.c` and closely related storage code. Compared with `btree.h`, this file is deliberately internal: it exposes `MemPage`, `BtShared`, `BtCursor`, pointer-map constants, page flags, endian helpers, and integrity-check state that must remain tightly synchronized with the implementation.

## Important Types, Structures, and Macros

The leading comment is a compact specification of the SQLite database file format: page numbering starts at 1; page 1 begins with a 100-byte database header; header offsets include page size, file-format read/write versions, reserved bytes, payload fractions, change counter, database size, freelist trunk, freelist count, schema cookie, file format, cache size, largest root page, text encoding, user version, incremental-vacuum mode, application id, version-valid-for, and SQLite version number. It also describes btree page headers, cell pointer arrays, freeblocks, fragments, variable-length integers, cells, overflow pages, and freelist trunk/leaf pages.

`MX_CELL_SIZE(pBt)` and `MX_CELL(pBt)` derive maximum cell and cell-count bounds from `BtShared.pageSize`. The page type flags `PTF_INTKEY`, `PTF_ZERODATA`, `PTF_LEAFDATA`, and `PTF_LEAF` mirror the first byte of each on-disk btree page and drive parser behavior for cells.

`MemPage` stores the decoded state of a pager page: initialization flags, key/layout flags, page number, leaf/interior state, header and cell offsets, local payload limits, free-byte counts, overflow-cell staging arrays, owning `BtShared`, raw page bytes (`aData`, `aDataEnd`, `aCellIdx`, `aDataOfst`), pager handle, and function pointers for cell-size and parse-cell routines. The first eight bytes are special because pager extra storage zeroes only that prefix when a new page is allocated.

`BtLock` records shared-cache table locks by `Btree`, root page, and read/write mode. `Btree` is the per-connection handle with connection pointer, shared `BtShared`, transaction state, sharability/lock flags, incremental-blob and backup counters, data-version cache, shared-cache linked-list fields, debug seek count, and page-1 lock. `BtShared` is the per-database shared state: pager, current db, cursor list, page-1 cache, open flags, auto-vacuum flags, transaction state, payload limits, page size/usable size, transaction count, schema pointer and destructor, mutex, content-tracking bitvec, shared-cache locks/writer state, temp cell buffer, and transfer-row preformat size.

`CellInfo` is the decoded cell contract used by cursor and payload routines: integer key or payload-size value, payload pointer, total payload size, local payload size, and cell size on the btree page. `BtCursor` stores cursor state, flags, pager flags, hints, skip/error code, owning `Btree`/`BtShared`, overflow cache, saved key, linked-list membership, current `CellInfo`, last key, root page, current stack depth, key type, current cell index, parent index stack, `KeyInfo`, current page, and parent page stack. `BTCURSOR_MAX_DEPTH` limits tree depth to 20 and acts as a corruption guard.

Cursor flags include write, valid cached key, valid overflow cache, at-last, incremental blob, multiple cursors on same btree, and pinned states. Cursor states are `CURSOR_VALID`, `CURSOR_INVALID`, `CURSOR_SKIPNEXT`, `CURSOR_REQUIRESEEK`, and `CURSOR_FAULT`, with `skipNext` changing meaning by state. This distinction is important after mutations: a cursor can temporarily retain logical position while physical page references are invalid.

Pointer-map macros and constants (`PTRMAP_PAGENO`, `PTRMAP_PTROFFSET`, `PTRMAP_ISPAGE`, `PTRMAP_ROOTPAGE`, `PTRMAP_FREEPAGE`, `PTRMAP_OVERFLOW1`, `PTRMAP_OVERFLOW2`, `PTRMAP_BTREE`) define auto-vacuum metadata used to find parent pointers when moving pages. `PENDING_BYTE_PAGE(pBt)` reserves the page containing the locking pending byte. `ISAUTOVACUUM(pBt)` collapses auto-vacuum compile-time choices into an expression. `IntegrityCk` collects global state for `PRAGMA integrity_check`, including page references, error accumulator, page counts, heap for cell coverage, and row counts.

## Control Flow and State

The btree implementation loads raw pager pages and initializes `MemPage` structures from on-disk bytes. Page flags decide whether a page has integer keys, data payloads, leaf content, and child pointers. Cursor movement maintains a stack of `MemPage` pointers and cell indexes from root to current page, so seek and next/previous operations can descend, ascend, and rebalance without recomputing from the root each time. Cell parsing produces `CellInfo`, and overflow-page state may be cached in `BtCursor.aOverflow`.

Transactions are represented at two levels: `Btree.inTrans` for the per-connection handle and `BtShared.inTransaction`/`nTransaction`/`pWriter` for shared database state. The `btreeIntegrity(p)` macro asserts that shared transaction state and handle state remain consistent. Shared-cache locking tracks table-root locks through `BtShared.pLock` and uses `BTS_PENDING` and `pWriter` to avoid writer starvation when readers block a writer.

Page free-space state is represented by both raw on-disk freeblock chains and decoded `MemPage.nFree`. Overflow cells staged in `aiOvfl`/`apOvfl` allow page-balancing code to temporarily hold cells before reinserting them into local page layout. `BtShared.pHasContent` records pages moved to the freelist during a transaction so rollback/journaling code can reason about page content.

## Persistence Behavior

This header defines persistent on-disk invariants rather than performing writes itself. The database header offsets, page header fields, cell encoding, overflow chains, freelist trunk layout, and pointer-map format are compatibility-critical. Integer fields are big-endian on disk, and helpers `get2byte`, `put2byte`, `get4byte`, `put4byte`, and `get2byteAligned` centralize access. Any implementation change must preserve file-format compatibility or gate behavior by file-format metadata.

Auto-vacuum persistence is centered on pointer-map pages. Each non-pointer-map database page has at most one parent pointer entry, allowing page moves to update parent references without scanning the entire file. This interacts with root pages, overflow chains, freelist pages, and btree child pages. The largest-root-page metadata in `btree.h` and pointer-map macros here are used together by table/index creation and drop paths in `build.c` and VDBE opcodes.

The database page format also persists payload-locality decisions. `BtShared.maxLocal`, `minLocal`, `maxLeaf`, and `minLeaf` mirror page-size and payload-fraction rules so cells can decide how many bytes remain local versus spill to overflow pages. Corruption defenses depend on `aDataEnd`, `usableSize`, `maskPage`, maximum local payload bounds, and tree-depth checks.

## Dependencies and Integration Points

`btreeInt.h` includes `sqliteInt.h` and uses pager types (`Pager`, `DbPage`), schema/connection types (`sqlite3`, `Schema`), expression accumulator types for integrity checking (`StrAccum`), bitsets (`Bitvec`), key comparison metadata (`KeyInfo`), and core integer typedefs. It is used primarily by the btree implementation, integrity-check code, auto-vacuum page-moving logic, cursor/payload code, and shared-cache locking code.

Its definitions support APIs declared in `btree.h`. `Btree`, `BtShared`, and `BtCursor` are opaque publicly but concrete here. VDBE opcodes generated from `build.c` (`OP_CreateBtree`, `OP_Destroy`, `OP_Clear`, `OP_OpenRead`, `OP_OpenWrite`, `OP_Transaction`) eventually execute against these structures. Schema-builder decisions such as `BTREE_INTKEY` versus `BTREE_BLOBKEY`, auto-vacuum root-page moves, and temp database setup rely on the internal page and pointer-map invariants defined here.

## Risks and Edge Cases

The largest risk is mismatching decoded in-memory assumptions with on-disk bytes. Page header offsets differ for page 1 and leaf/interior pages; cells have optional child pointers, optional data-size varints, integer-key special cases, local/overflow splits, and optional overflow pointers. Corruption or integer overflow in any of those calculations can become a memory safety issue, which explains fields such as `aDataEnd`, depth bounds, and aligned/get helpers.

Shared-cache and transaction fields require strict mutex discipline. Comments specify that `MemPage` is protected by `MemPage.pBt->mutex`, `Btree` fields by `sqlite3.mutex`, and `BtShared` fields mostly by `BtShared.mutex` with exceptions for global shared-list fields. Code that bypasses these rules risks stale cursors, incorrect writer exclusion, or schema-cache races.

Compile-time options reshape the structures and behavior. `SQLITE_OMIT_AUTOVACUUM`, `SQLITE_OMIT_SHARED_CACHE`, `SQLITE_THREADSAFE`, `SQLITE_OMIT_GENERATED_COLUMNS` consumers, debug builds, and byte-order/compiler macros all affect available fields or helper behavior. Any external assumptions about structure layout are unsafe.

Pointer-map behavior is especially sensitive during page moves and drops. Incorrect parent-type entries can orphan pages or corrupt overflow chains. `PENDING_BYTE_PAGE` must remain unused by normal database allocation to preserve locking behavior.

## Test Signals

Storage tests should cover page sizes from 512 through 65536, page-1 header offsets, leaf and interior btree pages, intkey tables, zerodata/index b-trees, overflow payloads, freelist trunk/leaf handling, and fragment/freeblock accounting. Corruption tests should target malformed varints, bad freeblock chains, bad overflow pointers, impossible tree depth, duplicate page references, pointer-map mismatches, root-page moves, and pending-byte-page allocation attempts.

Concurrency and shared-cache tests should verify read/write table locks, pending writer behavior, cursor fault propagation, cursor restore after mutation, pinned cursors, and incremental blob cursor interactions. Auto-vacuum tests should create/drop tables and indexes while verifying pointer-map entries, root-page movement, freelist counts, and schema rootpage updates. Integrity-check tests should assert that `IntegrityCk` catches duplicate use, orphaned pages, and malformed btree coverage.

# sources/storage-engines/sqlite/src/build.c

## Purpose

`build.c` contains parser action routines for schema-building and DDL-related SQL. It is invoked as grammar rules reduce statements such as `CREATE TABLE`, `DROP TABLE`, `CREATE INDEX`, `DROP INDEX`, `CREATE VIEW`, foreign-key declarations, column constraints, source-list construction, transactions, savepoints, reindexing, and WITH clauses. Its job is to build or destroy in-memory schema objects, generate VDBE programs that persist schema changes into `sqlite_schema`, coordinate btree creation/destruction through opcodes, enforce SQL rules and authorization checks, and keep schema cookies/caches coherent.

## Important APIs and Functional Areas

Statement finalization and nested parsing are handled by `sqlite3FinishCoding()` and `sqlite3NestedParse()`. `sqlite3FinishCoding()` appends `OP_Halt`, emits `OP_Transaction` and schema-cookie verification for each database in `cookieMask`, adds shared-cache table locks, starts autoincrement bookkeeping, codes factored constant expressions, handles `RETURNING` result emission, and makes the VDBE ready. `sqlite3NestedParse()` formats SQL and recursively invokes the parser to append schema-maintenance SQL, with builtin functions preferred.

Schema lookup and cleanup APIs include `sqlite3FindTable()`, `sqlite3LocateTable()`, `sqlite3LocateTableItem()`, `sqlite3PreferredTableName()`, `sqlite3FindIndex()`, `sqlite3FreeIndex()`, `sqlite3UnlinkAndDeleteIndex()`, `sqlite3CollapseDatabaseArray()`, `sqlite3ResetOneSchema()`, `sqlite3ResetAllSchemasOfConnection()`, `sqlite3CommitInternalChanges()`, `sqlite3DeleteTable()`, `sqlite3UnlinkAndDeleteTable()`, `sqlite3FindDbName()`, `sqlite3FindDb()`, `sqlite3TwoPartName()`, `sqlite3WritableSchema()`, and `sqlite3CheckObjectName()`. These functions manage schema hash tables, object namespaces, temp/main/attached lookup order, writable-schema exceptions, and schema reset deferral.

Column and table construction is centered on `sqlite3StartTable()`, `sqlite3AddColumn()`, `sqlite3AddNotNull()`, `sqlite3AffinityType()`, `sqlite3AddDefaultValue()`, `sqlite3AddPrimaryKey()`, `sqlite3AddCheckConstraint()`, `sqlite3AddCollateType()`, `sqlite3AddGenerated()`, `sqlite3ChangeCookie()`, `createTableStmt()`, `convertToWithoutRowidTable()`, and `sqlite3EndTable()`. These build `Table`, `Column`, `Index`, default-expression, generated-column, CHECK, and foreign-key metadata while also emitting VDBE code for table root-page allocation and `sqlite_schema` updates.

View and virtual-table support appears in `sqlite3CreateView()`, `sqlite3ViewGetColumnNames()`, `viewGetColumnNames()`, `sqliteViewResetAll()`, `sqlite3IsShadowTableOf()`, `sqlite3MarkAllShadowTablesOf()`, `sqlite3ShadowTableName()`, `sqlite3ReadOnlyShadowTables()`, and virtual-table branches inside create/drop paths. RETURNING support is modeled as a temporary trigger by `sqlite3AddReturning()` and cleaned by `sqlite3DeleteReturning()`.

Drop and destroy paths include `sqlite3RootPageMoved()`, `destroyRootPage()`, `destroyTable()`, `sqlite3ClearStatTables()`, `sqlite3CodeDropTable()`, `tableMayNotBeDropped()`, `sqlite3DropTable()`, and `sqlite3DropIndex()`. These remove schema rows, clear statistics and autoincrement rows, drop triggers, destroy btree root pages in safe order for auto-vacuum, update schema cookies, and emit internal `OP_DropTable`/`OP_DropIndex`/`OP_VDestroy` operations.

Index construction and rebuild are handled by `sqlite3RefillIndex()`, `sqlite3AllocateIndexObject()`, `sqlite3HasExplicitNulls()`, `sqlite3CreateIndex()`, `sqlite3DefaultRowEst()`, `sqlite3Reindex()`, and `sqlite3KeyInfoOfIndex()`. The code resolves indexed expressions, collations, sort order, partial-index predicates, WITHOUT ROWID primary-key tails, default planner estimates, covering-index masks, uniqueness handling, schema insertion, and sorter-based index population.

Foreign-key and constraint helpers include `sqlite3CreateForeignKey()`, `sqlite3DeferForeignKey()`, `sqlite3HaltConstraint()`, `sqlite3UniqueConstraint()`, and `sqlite3RowidConstraint()`. Parser-list utilities include `sqlite3ArrayAllocate()`, `sqlite3IdListAppend()`, `sqlite3IdListDelete()`, `sqlite3IdListIndex()`, `sqlite3SrcListEnlarge()`, `sqlite3SrcListAppend()`, `sqlite3SrcListAssignCursors()`, `sqlite3SubqueryDelete()`, `sqlite3SubqueryDetach()`, `sqlite3SrcListDelete()`, `sqlite3SrcItemAttachSubquery()`, `sqlite3SrcListAppendFromTerm()`, `sqlite3SrcListIndexedBy()`, `sqlite3SrcListAppendList()`, `sqlite3SrcListFuncArgs()`, and `sqlite3SrcListShiftJoinType()`.

Transaction and schema-verification helpers are `sqlite3BeginTransaction()`, `sqlite3EndTransaction()`, `sqlite3Savepoint()`, `sqlite3OpenTempDatabase()`, `sqlite3CodeVerifySchema()`, `sqlite3CodeVerifyNamedSchema()`, `sqlite3BeginWriteOperation()`, `sqlite3MultiWrite()`, and `sqlite3MayAbort()`. CTE helpers at the end are `sqlite3CteNew()`, `sqlite3CteDelete()`, `sqlite3WithAdd()`, `sqlite3WithDelete()`, and `sqlite3WithDeleteGeneric()`.

## Control Flow and State

For `CREATE TABLE`, parsing starts at `sqlite3StartTable()`, which resolves the target database, checks reserved names and authorizer policy, detects namespace collisions, allocates a `Table`, and, outside schema initialization, emits VDBE code to create a placeholder root page and placeholder row in `sqlite_schema`. Column-related parser reductions then call `sqlite3AddColumn()` and constraint routines to fill `Table.aCol`, defaults, affinities, generated expressions, CHECK constraints, primary-key indexes, collations, and foreign keys. `sqlite3EndTable()` finalizes strict/WITHOUT ROWID rules, resolves self-references, estimates row/index widths, writes the final `sqlite_schema` row via nested SQL, increments the schema cookie, reparses affected schema, and links the table into schema hashes during initialization.

For `CREATE INDEX`, `sqlite3CreateIndex()` first reads schema, resolves the target table and index database, rejects views/virtual/system tables, allocates or invents the index name, performs authorization, resolves index expressions and collations, appends rowid or primary-key tail columns, computes uniqueness and covering-index metadata, links the index into schema state, emits `OP_CreateBtree` and an `sqlite_schema` row, calls `sqlite3RefillIndex()` for explicit indexes on existing tables, changes the schema cookie, and schedules schema reparse. During CREATE TABLE, automatic PRIMARY KEY/UNIQUE indexes are linked without populating storage because the table is still empty.

`convertToWithoutRowidTable()` rewrites both schema objects and generated VDBE code after a `WITHOUT ROWID` clause. It marks primary-key columns NOT NULL, changes the table root btree from `BTREE_INTKEY` to `BTREE_BLOBKEY`, creates a primary-key index for former integer-primary-key tables, removes duplicate PK columns, bypasses the separate PK index root-page creation, assigns the table root page to the PK index, replaces rowid tails on unique indexes with PK columns, and extends the PK index to cover all non-virtual table columns.

Drop flow begins with lookup and authorization in `sqlite3DropTable()` or `sqlite3DropIndex()`. Table drops verify object kind, protect system/shadow/eponymous tables, clear statistics and foreign-key references, remove triggers, delete schema rows, destroy btree root pages, destroy virtual tables when needed, emit internal drop opcodes, bump the schema cookie, and reset view columns. Root pages are destroyed largest-first by `destroyTable()` so auto-vacuum page moves cannot cause a later destroy to target an already-moved root page.

Statement finalization ties these action routines together. Calls such as `sqlite3BeginWriteOperation()` set bits in the top-level parse masks instead of immediately emitting all transaction code. `sqlite3FinishCoding()` later generates transaction/schema-verification opcodes for every used database, then jumps to statement body code. This delayed prologue pattern lets nested parser actions contribute to one coherent VDBE program.

## Persistence Behavior

Persistent schema state is stored in `sqlite_schema` or `sqlite_temp_schema` through generated SQL in `sqlite3NestedParse()`. For table creation, `sqlite3StartTable()` reserves a rowid and root-page register, inserts a placeholder schema row, and `sqlite3EndTable()` updates that row with `type`, `name`, `tbl_name`, `rootpage`, and SQL text. For index creation, `sqlite3CreateIndex()` inserts an `index` row with rootpage and optional SQL text. Drop paths delete matching schema rows. Every schema mutation calls `sqlite3ChangeCookie()` so prepared statements can detect schema invalidation.

Btree storage is not directly manipulated by C calls here; instead the file emits VDBE opcodes that call the btree layer at execution time. `OP_CreateBtree` creates table/index root pages using `BTREE_INTKEY` or `BTREE_BLOBKEY`, `OP_Destroy` frees root pages and returns moved-root information for auto-vacuum, `OP_Clear` clears existing index contents for reindex, `OP_OpenWrite` opens storage cursors, and `OP_Transaction` starts read/write/exclusive transactions. Temporary database storage is opened through `sqlite3OpenTempDatabase()` using `sqlite3BtreeOpen()` with temp-file flags and configured page size.

The file also persists side tables and metadata: autoincrement creates and updates `sqlite_sequence`; `sqlite_stat1` through `sqlite_stat4` rows are deleted on drop; generated-column and CHECK validation may emit SQL that forces expression validation; views store SQL and lazily derive column metadata; WITHOUT ROWID tables persist as blob-key primary-key btrees instead of rowid btrees.

## Dependencies and Integration Points

`build.c` depends on nearly every internal SQLite subsystem: parser state (`Parse`, tokens, grammar flags), schema objects (`Table`, `Column`, `Index`, `FKey`, `Trigger`, `View`, `With`, `Cte`), hash tables, expression and select builders/resolvers, authorization, virtual tables, collations, foreign-key support, rename tracking, VDBE opcode construction, pager/btree metadata constants, auto-vacuum behavior, WAL-independent transaction setup, and memory management.

It integrates directly with `btree.h` through constants and APIs such as `BTREE_FILE_FORMAT`, `BTREE_TEXT_ENCODING`, `BTREE_SCHEMA_VERSION`, `BTREE_INTKEY`, `BTREE_BLOBKEY`, `sqlite3BtreeOpen()`, `sqlite3BtreeSetPageSize()`, `sqlite3BtreeIsReadonly()`, and shared-cache table locks. It integrates with `btreeInt.h` indirectly through root-page semantics, auto-vacuum root-page movement, pointer-map correctness, and the distinction between rowid-table and blob-key btrees.

The VDBE is the major integration boundary. Most persistent work is encoded as opcodes rather than executed immediately, so correctness depends on matching parser-time schema objects to runtime opcode behavior. This file also integrates with schema loading: when `db->init.busy` is true, the same parser actions reconstruct in-memory objects from existing `sqlite_schema` rows without re-emitting writes.

## Risks and Edge Cases

Schema mutation has many mode-dependent branches. `db->init.busy`, `IN_SPECIAL_PARSE`, `IN_DECLARE_VTAB`, `IN_RENAME_OBJECT`, temp database handling, writable-schema, defensive mode, imposter tables, virtual tables, shadow tables, STRICT tables, generated columns, WITHOUT ROWID, autoincrement, and omitted-feature builds all alter behavior. Bugs in these gates can either reject valid legacy SQL or allow unsafe schema changes.

Memory ownership is intricate. Many routines transfer ownership of expressions, select trees, source lists, CTEs, index expressions, and token-derived names, with cleanup paths that must handle OOM and parser errors. Incorrect cleanup can leak schema memory, double-free parse objects, or leave lookaside-allocated expression nodes in persistent schema structures. The generated-column error path explicitly replaces bad expressions with `NULL` to avoid lookaside-backed schema corruption.

Root-page and auto-vacuum handling is correctness-critical. Drops must destroy root pages in descending order, and `destroyRootPage()` must update `sqlite_schema` if `OP_Destroy` moves another root page. A mismatch between in-memory `tnum`, schema rootpage rows, and btree root pages can corrupt subsequent schema loads.

Index creation has subtle compatibility behavior: legacy string column names are converted to identifiers; explicit `NULLS FIRST/LAST` is rejected; DESC is honored only for file format >=4; duplicate automatic constraints may collapse into one index; WITHOUT ROWID indexes append primary-key columns instead of rowid; collating sequence lookup can disable an index and request schema retry. These behaviors need targeted tests because they are easy to disturb during refactors.

Security and policy risks include reserved `sqlite_` names, shadow-table write/drop restrictions under defensive mode, authorization checks for schema-table writes and DDL actions, and eponymous virtual tables. The `IF NOT EXISTS`/`IF EXISTS` paths deliberately emit harmless write-like opcodes so readonly classification stays compatible.

## Test Signals

DDL tests should cover `CREATE TABLE`, `CREATE TABLE AS SELECT`, `CREATE TEMP TABLE`, `CREATE VIEW`, `CREATE INDEX`, partial indexes, expression indexes, unique and primary-key constraints, generated columns, CHECK constraints, collations, STRICT tables, WITHOUT ROWID tables, autoincrement, foreign keys, `DROP TABLE`, `DROP VIEW`, `DROP INDEX`, `REINDEX`, `BEGIN` variants, savepoints, and temp database creation.

Compatibility tests should include legacy schema table names, reserved-name rejection, writable-schema exceptions, quoted identifiers, string literals in index/PK column lists, old file format DESC behavior, duplicate automatic constraints with differing conflict policies, view rowid behavior, circular views, and schema reload from `sqlite_schema`.

Storage-facing tests should verify generated VDBE opcode effects: schema cookie changes, rootpage allocation, index population with sorter uniqueness checks, statement rollback for abortable multiwrite DDL, auto-vacuum root-page relocation on drop, stat-table cleanup, sqlite_sequence creation/deletion, temp btree opening, and parse-schema invalidation. Reduced-build tests should compile with feature omissions such as `SQLITE_OMIT_VIEW`, `SQLITE_OMIT_VIRTUALTABLE`, `SQLITE_OMIT_FOREIGN_KEY`, `SQLITE_OMIT_GENERATED_COLUMNS`, `SQLITE_OMIT_AUTOVACUUM`, `SQLITE_OMIT_REINDEX`, and `SQLITE_OMIT_CTE`.
