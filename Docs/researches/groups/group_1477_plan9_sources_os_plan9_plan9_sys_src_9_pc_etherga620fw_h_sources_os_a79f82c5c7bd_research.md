# File Research: sources/os/plan9/plan9/sys/src/9/pc/etherga620fw.h

## Purpose

Generated firmware image header for the Plan 9 PC kernel GA620 Ethernet driver. The adjacent driver `etherga620.c` includes this file and loads its arrays into Alteon Tigon 2 NIC local memory during reset.

This is not normal handwritten C control logic. It is an embedded firmware blob expressed as C constants and static integer arrays.

## Contents

- Generated marker: `/* Generated by genfw.c */`.
- Firmware release constants:
  - `tigon2FwReleaseMajor = 0xc`
  - `tigon2FwReleaseMinor = 0x4`
  - `tigon2FwReleaseFix = 0xb`
- Firmware load layout:
  - start address: `0x00004000`
  - text: address `0x00004000`, length `0x11bc0`
  - rodata: address `0x00015bc0`, length `0x10d0`
  - data: address `0x00016cc0`, length `0x1c0`
  - sbss: address `0x00016e80`, length `0xcc`
  - bss: address `0x00016f50`, length `0x20c0`
- Static arrays:
  - `tigon2FwText`: 18,161 integer words in the generated array; driver copies `0x11bc0` bytes.
  - `tigon2FwRodata`: 1,077 integer words in the generated array; driver copies `0x10d0` bytes.
  - `tigon2FwData`: 113 integer words in the generated array; driver copies `0x1c0` bytes.

The arrays each contain one word more than the declared segment byte length requires, consistent with the generated array comment form `/*(MAX_*_LEN/4) + 1*/`. The driver’s copy routine is length-bounded, so the declared segment lengths govern what reaches the NIC.

## Integration

`etherga620.c` uses this header directly:

- Includes `etherga620fw.h`.
- In `ga620reset`, it writes text, rodata, and data to NIC SRAM with `ga620lmw`.
- It clears sbss and bss by calling `ga620lmw` with `nil` data.
- It later starts the NIC CPU at `tigon2FwStartAddr`.

The load helper writes 32-bit words through the device local-memory window and assumes 32-bit aligned destination and length.

## Embedded Metadata

Printable strings in the rodata image identify this as Alteon AceNIC/Tigon firmware built from old vendor source paths such as `nic/fw2/common`. Embedded metadata includes:

- `FW_VERSION: #1 Fri Apr 7 17:57:52 PDT 2000`
- `FW_COMPILE_BY: devrcs`
- `FW_COMPILE_HOST: compute`
- `FW_COMPILER: gcc version 2.7.2`
- RCS headers for firmware modules including `fwmain.c`, `timer.c`, `command.c`, `mcast.c`, `dma.c`, `trace.c`, `data.c`, `mem.c`, `send.c`, `recv.c`, `mac.c`, and `cksum.c`.

## Dependencies

This file relies on being included by a C file that already has Plan 9 kernel integer type conventions and device access helpers available. It declares only `static int` arrays and preprocessor constants, so it has internal linkage when included into `etherga620.c`.

## Filesystem Relevance

Indirect. The file belongs to the Plan 9 PC kernel source tree and supports network device initialization, not VFS or filesystem behavior. Its relevance to subset A is OS-kernel coverage rather than filesystem-specific logic.

## Risks and Maintenance Notes

- Opaque firmware blob: behavior cannot be audited from this header without disassembling or recovering the original firmware source.
- Generated file: edits should be made through the firmware generation pipeline, not by manually changing hex words.
- Architecture assumptions: integer word order and the GA620 driver’s local-memory write path are part of the firmware loading contract.
- The blob embeds very old compiler/build metadata, so provenance and licensing should be treated as important if redistributing or modernizing this driver.

# File Research: sources/os/plan9/plan9/sys/src/9/pc/etherif.h

## Purpose

Shared Plan 9 PC Ethernet interface header. It defines the per-device `Ether` structure used by `devether.c` and many PC Ethernet drivers, plus common helper declarations and ring-index macros.

## Contents

- Constants:
  - `MaxEther = 48`: maximum registered Ethernet card types.
  - `Ntypes = 8`: number of Ethernet protocol type slots in the embedded `Netif`.
- Forward declaration:
  - `typedef struct Ether Ether;`
- `struct Ether`:
  - Embeds `ISAConf` for hardware configuration.
  - Tracks controller number, PCI/TBDF identifier, and Ethernet address.
  - Provides driver callbacks:
    - `attach`
    - `detach`
    - `transmit`
    - `interrupt`
    - `ifstat`
    - `ctl`
    - `power`
    - `shutdown`
  - Holds driver-private controller pointer `ctlr`.
  - Holds output queue `oq`.
  - Embeds `Netif`, making the generic network-interface state part of every Ethernet device.
- Shared functions:
  - `etheriq(Ether*, Block*, int)`: input packet demultiplexing path.
  - `addethercard(char*, int(*)(Ether*))`: register a card reset/probe routine.
  - `ethercrc(uchar*, int)`: Ethernet CRC helper.
  - `parseether(uchar*, char*)`: parse textual Ethernet address.
- Ring macros:
  - `NEXT(x, l)` wraps an index forward modulo length.
  - `PREV(x, l)` wraps an index backward modulo length.

## Integration

This header is included by the generic Ethernet device implementation `devether.c` and by many PC Ethernet drivers such as `etherga620.c`, `ether82557.c`, `ether8169.c`, `ether2114x.c`, `ether8390.c`, and others.

The generic device layer uses `addethercard` to build the available driver table and allocates/populates `Ether` instances during probing. Individual drivers fill the callback fields during reset/probe so the generic `/net/ether*` interface can call into device-specific attach, transmit, interrupt, statistics, control, power, and shutdown paths.

## Dependencies

The header assumes surrounding Plan 9 kernel headers have already defined:

- `ISAConf`
- `uchar`
- `Eaddrlen`
- `Ureg`
- `Queue`
- `Netif`
- `Block`
- `ulong`

It has no include guard, which is common in this older Plan 9 kernel style but means it should be included once per compilation unit.

## Filesystem Relevance

Indirect. This is networking infrastructure in the Plan 9 kernel PC port. It does not implement VFS or local filesystem operations, but it is part of the OS kernel source tree covered by subset A.

## Risks and Maintenance Notes

- `Ether` is a shared ABI-like structure across all PC Ethernet drivers and `devether.c`; field changes have broad driver impact.
- Callback nullability is driver-dependent, so callers must continue to honor the existing conventions.
- `NEXT` and `PREV` evaluate their arguments directly; callers should avoid side-effect expressions.
- The embedded `Netif` means generic network state and driver state are tightly coupled.
