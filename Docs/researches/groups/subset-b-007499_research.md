## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/namenode/FSImageFormat.java

Purpose: legacy binary FSImage reader/writer facade for the NameNode namespace. The outer `FSImageFormat` class chooses between protobuf and pre-protobuf image loaders, retains the old binary format implementation for compatibility and offline tooling, and owns upgrade-time reserved-path renaming. The large format comment documents the durable binary layout: layout version, namespace identity, inode count, block generation stamps, txid, inode id state, snapshots, directory tree, under-construction files, secret-manager state, and cache-manager state.

Important APIs and types: `AbstractLoader` exposes the loaded image MD5 and txid. `LoaderDelegator` reads the first bytes of an image and dispatches to `FSImageFormatProtobuf.Loader` when it sees `FSImageUtil.MAGIC_HEADER`, otherwise to the legacy `Loader`. `newLoader(Configuration, FSNamesystem)` is the public factory used by `FSImage` and validation tools. The legacy `Loader` reads old images into an `FSNamesystem`, updates `BlockIdManager`, restores inode ids, snapshots, leases, cache state, and delegation tokens, and exposes helpers used by snapshot image code such as `loadINodeWithLocalName`, `loadINodeFileAttributes`, `loadINodeDirectoryAttributes`, and `getSnapshot`. The deprecated `Saver` writes old binary images for compatibility with external fsimage tooling.

Control flow: `LoaderDelegator.load` is one-shot and selects the implementation before delegating. The legacy `Loader.load` opens a digesting stream, validates exact layout version, reads optional layout flags, namespace id, inode count, block generation stamp fields, optional txid, optional last inode id, optional snapshot manager state, and compression metadata. It then unwraps compression and loads the namespace by either local-name optimized directory traversal, snapshot-aware local-name traversal, or old full-path traversal. After inodes are loaded it restores files under construction, delegation-token state, cache-manager state, checks EOF, records the MD5, and marks the loader complete.

Important inode flow: `loadINode` uses the encoded `numBlocks` discriminator. Non-negative values are files with contiguous `BlockInfoContiguous` blocks, optional file diffs, optional under-construction snapshot metadata, and `PermissionStatus`. `-1` is a directory with namespace/storage quotas, optional snapshot flags, and permissions. `-2` is a symlink, guarded by `FileSystem.areSymlinksEnabled()`. `-3` is an `INodeReference` loaded through `SnapshotFSImageFormat.ReferenceMap`. Loaded child files are passed through `updateBlocksMap` so the `BlockManager` can connect blocks to the file inode. Root attributes are copied onto the live `FSDirectory.rootDir` rather than replacing it.

State and persistence behavior: the file directly maps durable FSImage fields into NameNode state: generation stamp ranges, sequential block id state, transaction id, last inode id, snapshot lists and diffs, inode tree topology, block collection mappings, leases for under-construction files, delegation token keys/tokens, and cache pools/directives. The legacy saver writes layout version `-51`, layout flags, namespace id, inode count, block id manager state, checkpoint txid, last inode id, snapshot manager state, compressed inode tree, under-construction file table, secret-manager state, cache-manager state, and a forced file-channel sync. Both load and save calculate MD5 over the image stream.

Upgrade and compatibility behavior: reserved names that were legal in older layouts are renamed during upgrade. `useDefaultRenameReservedPairs`, `setRenameReservedPairs`, and `renameReservedPathsOnUpgrade` populate or apply mappings for components such as `.snapshot` and `/.reserved`; missing mappings throw `IllegalReservedPathException` with rollback/remediation guidance. Layout-feature checks gate fields such as snapshot support, stored txids, inode ids, diskspace quota, access time, compression, sequential block ids, and optimized snapshot inodes.

Dependencies and integration points: this class is called by `FSImage` for image loading and by `FsImageValidation`; it collaborates with `FSNamesystem`, `FSDirectory`, `BlockManager`, `BlockIdManager`, `LeaseManager`, `SnapshotManager`, `SnapshotFSImageFormat`, `FSImageSerialization`, `FSImageCompression`, `NameNodeLayoutVersion`, startup-progress reporting, and Hadoop MD5 utilities. The reserved-path options integrate with `NameNode` startup parsing. The deprecated saver is kept for external binary fsimage compatibility rather than the normal current save path, which uses `FSImageFormatProtobuf.Saver`.

Risks: this is high-risk recovery code because corrupted layout interpretation can silently rebuild an incorrect namespace. The legacy loader requires exact layout-version equality, so compatibility depends on callers using it only for supported old images. Reserved-path renaming can fail startup or rename user paths during upgrade if configured incorrectly. Snapshot reference handling can undercount progress and must avoid loading duplicate subtrees. Under-construction snapshot files use `/.reserved/.inodes/<id>` compatibility paths, which are explicitly marked as a format-preserving hack. The deprecated saver writes a fixed old layout and should not become the primary persistence path for modern features such as erasure-coded and striped blocks.

Test signals: relevant tests include fsimage load/save round trips, upgrade tests for reserved `.snapshot` and `.reserved` paths, snapshot fsimage tests, under-construction lease restoration tests, block map reconstruction checks, cache-manager and delegation-token persistence tests, symlink upgrade behavior, fsimage validation, and offline image viewer compatibility. `TestFSImageWithSnapshot` directly exercises the protobuf saver and `FSImageFormat.newLoader`, while storage and namespace tests exercise the loader indirectly through NameNode startup.

## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/namenode/FSImageFormatPBINode.java

Purpose: protobuf FSImage inode-section codec for NameNode namespace persistence. It translates `FsImageProto.INodeSection`, `INodeDirectorySection`, and `FilesUnderConstructionSection` protobuf records into in-memory `INode` objects on load, and serializes the live inode map, directory child links, and leases on save. It is the inode-specific worker used by `FSImageFormatProtobuf`.

Important APIs and constants: the top-level constants define ACL and xattr compact bit layouts that are shared with `AclEntryStatusFormat` and `XAttrFormat`. `Loader.loadPermission`, `loadAclEntries`, `loadXAttrs`, and `loadQuotaByStorageTypeEntries` decode compact protobuf ids through `SerialNumberManager.StringTable`. `Loader.loadINodeDirectory` constructs directories, quota features, ACL features, and xattr features. `Loader.updateBlocksMap` connects file blocks to the `BlockManager`. `Saver.buildINodeFile`, `buildINodeDirectory`, and the section serializers are the corresponding write-side API.

Loader control flow: `loadINodeSection` reads an `INodeSection` header, resets `FSDirectory`'s last inode id, configures startup progress, then repeatedly parses delimited inode records. Root inode attributes are merged into the existing root; other inodes are built, inserted into the inode map under synchronization, and batched for async name-cache and block-map updates. `loadINodeDirectorySection` parses parent-child `DirEntry` records after inode objects exist, adds normal children by inode id, and adds reference children by index into the loader context reference list. `loadFilesUnderConstructionSection` drains records for compatibility because protobuf file UC state is embedded in inode file records and leases are added during inode load.

Parallel load behavior: if `FSImageFormatProtobuf` enables parallel loading and the image has `_SUB` sections, `loadINodeSectionInParallel` and `loadINodeDirectorySectionInParallel` submit subsection readers to an executor. The first inode subsection carries the header and is processed before submitting work. Each worker reads a bounded section stream from the parent loader. A `CountDownLatch` joins all work, exceptions are collected in a synchronized list, and inode totals are checked against the expected header count. Non-thread-safe updates are guarded by synchronization or funneled through single-thread executors for block-map and name-cache mutation.

INode conversion behavior: file loading selects contiguous or striped `BlockInfo` based on protobuf block type and erasure-coding policy id. Striped files require a valid persisted erasure-coding policy and use `BlockInfoStriped`; replicated files use `BlockInfoContiguous` and replication. The loader restores permissions, modification/access times, storage policy, ACLs, xattrs, and file-under-construction data. For UC files, it adds a lease and converts the last block to `UNDER_CONSTRUCTION`. Directory loading restores namespace and storage-space quota, per-storage-type quota, ACLs, and xattrs. Symlink loading restores target, times, and permissions.

Saver control flow: `serializeINodeSection` writes the section header with last inode id and inode-map size, then serializes every inode in map iteration order, committing subsections when the parent saver's `inodesPerSubSection` threshold is reached. `serializeINodeDirectorySection` writes child-link records only for directories with children, validates that every non-reference child exists in the inode map, records reference children into `SaverContext.refList`, and counts dangling-child errors instead of immediately failing. `serializeFilesUCSection` iterates lease-manager inode ids and writes compatibility records after validating the inode exists and is still under construction.

State and persistence behavior: this file persists inode ids, local names, file blocks, block type, replication or erasure-coding policy id, preferred block size, storage policy, directory quotas, type quotas, ACL entries, xattrs, symlink targets, under-construction client metadata, directory tree topology, and inode references. It deliberately separates inode object records from directory child edges, allowing all inodes to be loaded before parent-child topology is attached. It depends on the string table for compact permission, ACL, and xattr identity storage.

Dependencies and integration points: integrates tightly with `FSImageFormatProtobuf.Loader` and `.Saver`, `FSDirectory`, `FSNamesystem`, `BlockManager`, `LeaseManager`, `SerialNumberManager`, `PBHelperClient`, `ErasureCodingPolicyManager`, `Snapshot` reference lists, `QuotaCounts`, ACL/xattr feature classes, and startup progress. Offline image viewers also reuse the public static loader helpers to decode permissions, ACLs, and xattrs from protobuf images without instantiating the full NameNode.

Risks: the parallel path is sensitive to section boundaries and synchronization; incorrect subsection headers or counts throw corruption errors, while missing executor shutdown or delayed async updates could leave maps incomplete if callers skipped `waitBlocksMapAndNameCacheUpdateFinished`. The write path logs and counts dangling child pointers, so callers must treat nonzero image errors as meaningful. String-table mismatch corrupts users, groups, ACL names, or xattr names. Striped-file loading assumes erasure-coding policies have already been loaded before inode sections. Root feature merging must preserve the existing root identity while accurately copying ACL, xattr, quota, and encryption-zone metadata.

Test signals: exercise protobuf image save/load with replicated and erasure-coded files, ACL and xattr round trips, per-storage-type quota persistence, under-construction lease restoration, snapshot/reference child ordering, parallel save/load with subsection thresholds, dangling child detection, root ACL/xattr/encryption zone restoration, and offline image viewer permission/ACL/xattr decoding. Tests should compare inode counts, block map ownership, child order, and lease-manager state after reload.

## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/namenode/FSImageFormatProtobuf.java

Purpose: top-level protobuf FSImage reader/writer. It defines the current sectioned on-disk fsimage container, dispatches each protobuf section to subsystem-specific loaders/savers, manages compression and summary offsets, supports optional parallel inode loading through subsections, and computes persisted MD5 digests.

Important APIs and types: `LoaderContext` holds the string table and loaded inode-reference list shared by inode and snapshot loaders. `SaverContext` holds the reference list used during save and a generic `DeduplicationMap` helper. `Loader` implements `FSImageFormat.AbstractLoader` and exposes loaded MD5, txid, and context. `Saver` writes a new image and exposes saved MD5, context, subsection threshold, and current section output stream for child savers. `SectionName` enumerates all recognized sections and defines load ordering by enum ordinal.

File format behavior: protobuf images start with `FSImageUtil.MAGIC_HEADER`. The actual section bytes follow from offset equal to header length. A `FileSummary` protobuf is written at the tail as a delimited message followed by a four-byte summary length. Each summary section records a name, offset, and length. Optional compression is applied per section stream and stored in the summary's codec name. `FSImageUtil.loadSummary` validates on-disk version and layout support before section loading begins.

Loader control flow: `Loader.load` starts a daemon `DigestThread` to compute the whole-file MD5 in parallel, then opens `RandomAccessFile` and `FileInputStream` and calls `loadInternal`. `loadInternal` validates magic and summary, optionally requires the image layout version to equal the software layout version for rollback cases, sorts sections by `SectionName`, removes `_SUB` sections into a side list, and optionally creates a fixed thread pool. It then visits sections in load order, wraps each bounded `LimitInputStream` for compression, and calls subsystem loaders for namespace info, string table, erasure coding, inodes, inode references, snapshots, directory links, files under construction, snapshot diffs, secret-manager state, and cache-manager state.

Section semantics: `NS_INFO` restores block generation stamps, generation stamp limit, last allocated contiguous and striped block ids, transaction id, and rolling-upgrade start time when a rollback image exists. `STRING_TABLE` constructs a `SerialNumberManager.StringTable`. `ERASURE_CODING` restores persisted erasure-coding policies before inode load. `INODE` and `INODE_DIR` delegate to `FSImageFormatPBINode.Loader`; `INODE_REFERENCE`, `SNAPSHOT`, and `SNAPSHOT_DIFF` delegate to `FSImageFormatPBSnapshot.Loader`. `SECRET_MANAGER` reads delegation keys/tokens with startup progress, and `CACHE_MANAGER` reads cache pools/directives into `CacheManager.PersistState`.

Saver control flow: `Saver.save` enables subsections when parallel mode and inode-count thresholds require it, opens the output channel, and calls `saveInternal`. `saveInternal` writes the magic header through a digesting buffered stream, initializes `FileSummary` with on-disk version and layout version, wraps the section stream for compression, writes name-system state, optionally erasure-coding policies, inode and snapshot sections, secret-manager state, cache-manager state, and finally string table. It flushes the current compression stream, writes the summary and summary length, closes the stream, and records the MD5. `commitSection`, `commitSubSection`, and `commitSectionAndSubSection` update the summary with offsets and lengths using the file channel position.

State and persistence behavior: this file owns container-level persistence for block id manager state, namespace id, rolling-upgrade marker, erasure-coding policy definitions, inode graph sections, snapshot sections, delegation tokens, cache state, compact string table, codec name, layout version, offsets, lengths, and digest. It intentionally stores string table last while loading it early by sorting sections by logical section order rather than physical write order. Subsections are optional physical partitions of logical sections, used to allow parallel load for large namespaces.

Dependencies and integration points: called by `FSImage.saveFSImage` and by `FSImageFormat.LoaderDelegator`. It integrates with `FSImageUtil`, `FSImageCompression`, `FSImageFormatPBINode`, `FSImageFormatPBSnapshot`, `FSNamesystem`, `BlockIdManager`, `CacheManager`, `DelegationTokenSecretManager`, `ErasureCodingPolicyManager`, `SerialNumberManager`, `NameNodeLayoutVersion`, `MD5FileUtils`, startup progress, compression codecs, and offline image viewer utilities that parse section summaries.

Risks: section ordering is a compatibility contract: string table and erasure-coding policy state must be available before dependent sections, and directory edges must load after inode objects. Offset accounting depends on flushing compression streams at exactly the right times; a missed flush corrupts summary lengths. Parallel subsection loading assumes each subsection is a complete delimited stream and that exactly the header count is loaded. `getAndRemoveSubSections` mutates the section list, so later logic relies on all physical subsection names ending in `_SUB`. Unknown sections throw during normal load if the section name is unrecognized; unknown enum ordering changes can affect forward/backward compatibility. The digest thread computes MD5 concurrently and any delayed exception must be rethrown after join.

Test signals: validate image magic and summary tail parsing, compressed and uncompressed round trips, save/load with every section type, layout-version rollback enforcement, parallel load/save thresholds and subsection counts, MD5 generation, section offset/length accuracy, unknown-section rejection, rolling-upgrade restore only when rollback image exists, erasure-coding policy restore before inode load, cache/delegation token persistence, and offline image viewer section parsing.

## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/namenode/FSImagePreTransactionalStorageInspector.java

Purpose: storage-directory inspector for the old pre-HDFS-1073 NameNode storage layout, before image and edits files carried transaction ids in their names. It discovers `fsimage`, `fsimage.ckpt`, `edits`, and `edits.new`, compares checkpoint timestamps, performs crash recovery for in-progress checkpoints, and supplies the image/edit-log load plan for legacy upgrades.

Important APIs and state: `inspectDirectory(StorageDirectory)` records whether a directory has a version file, whether it contains image and/or edits files, its `fstime` checkpoint timestamp, latest image and edits storage directories, whether any storage directory is out of date, and whether an unfinalized upgrade exists via `previous`. `readCheckpointTime` reads the `fstime` long from `NameNodeFile.TIME` if present and readable. `getLatestImages` returns a single `FSImageFile` with `INVALID_TXID` after consistency checks and recovery. `getEditLogStreams(NNStorage)` is a static convenience used by `FSImage` to produce legacy edit-log streams.

Control flow: each inspected directory is skipped as out of date if it has no version file. Image-capable directories are checked for `fsimage`; edits-capable directories are checked for `edits`; each directory contributes a checkpoint time into a set for later consistency checks. The inspector tracks the image directory with the highest checkpoint time and the edits directory with the highest checkpoint time. `getLatestImages` requires both sides, allows one rare image-newer-than-edits scenario with explicit error logs, otherwise rejects mismatched checkpoint times, then runs `doRecovery`.

Recovery behavior: `doRecovery` looks for `fsimage.ckpt` in the chosen image directory. If it exists and the chosen edits directory also has `edits.new`, it deletes the checkpoint image because a checkpoint upload may not have completed. If `fsimage.ckpt` exists without `edits.new`, it completes the checkpoint by renaming `fsimage.ckpt` to `fsimage`, deleting the destination first if needed for Windows rename behavior. Any checkpoint recovery sets `needToSaveAfterRecovery`.

State and persistence behavior: this class does not parse image contents. It reasons over durable storage files and timestamp metadata: `VERSION`, `fstime`, `fsimage`, `fsimage.ckpt`, `edits`, `edits.new`, and `previous`. `needToSave` becomes true when any directory lacks current metadata, checkpoint times disagree, the image checkpoint is newer than edits, or checkpoint crash recovery occurred. `getMaxSeenTxId` returns `0` because pre-transactional storage has no seen-txid file contract.

Dependencies and integration points: extends `FSImageStorageInspector` and is selected by `NNStorage` for older layouts. It uses `NNStorage.getStorageFile`, `NameNodeDirType`, `NameNodeFile`, `FileUtil.canRead`, `EditLogFileInputStream`, and `StorageDirectory`. `FSImage` uses it to load pre-transactional edit logs during upgrade. The result feeds the generic image-loading path through `FSImageFile`.

Risks: timestamp-based recovery is weaker than transaction-id-based recovery and can discard edits in the rare image-newer-than-edits case. Inconsistent image/edit checkpoint times normally abort startup, so clock or file-copy mistakes can block recovery. The rename/delete logic must be correct across platforms. `getEditsInStorageDir` asserts that `edits` exists; production safety depends on earlier discovery checks. Because legacy images return `INVALID_TXID`, later code must treat txid handling as a special upgrade case.

Test signals: tests should cover no-version formatted dirs, missing image or edits files, consistent and inconsistent checkpoint times, image-newer-than-edits special case, `fsimage.ckpt` plus `edits.new` deletion, `fsimage.ckpt` rename completion, detection of unfinalized upgrades, need-to-save decisions, and edit stream ordering for `edits` followed by `edits.new` when present.

## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/namenode/FSImageSerialization.java

Purpose: shared binary and XML serialization helpers for legacy FSImage, edit-log operations, cache manager persistence, erasure-coding policy persistence, under-construction inode compatibility, and offline image viewer support. It centralizes the exact writable encodings used by old NameNode durable formats.

Important APIs and types: the class is static-only and uses a `ThreadLocal<TLData>` containing reusable `DeprecatedUTF8`, primitive writable objects, and an `FsPermission` to reduce allocations while remaining safe for multi-threaded image saving. Inode helpers include `readINodeUnderConstruction`, `writeINodeUnderConstruction`, `writeINodeFile`, `writeINodeFileAttributes`, `writeINodeDirectory`, `writeINodeDirectoryAttributes`, `saveINode2Image`, and private symlink/reference writers. Primitive helpers include `readString`, `writeString`, `readBytes`, `writeBytes`, `readPathComponents`, `readLocalName`, compact block array methods, and writable-based primitive wrappers. Cache and erasure-coding helpers read/write binary and XML forms.

INode serialization behavior: files write local name, inode id, replication, modification/access times, preferred block size, blocks, snapshot file diffs, optional under-construction client info, and permission status. Directories write local name, inode id, placeholder file fields, `-1` type marker, namespace/storage quotas, snapshot flags, and permissions. Symlinks use the `-2` marker and write target plus permissions. References use the `-3` marker, record whether the reference is `WithName`, persist last/destination snapshot id, and delegate referred inode state to `SnapshotFSImageFormat.ReferenceMap`.

Under-construction behavior: `readINodeUnderConstruction` reads path bytes, inode id when supported, replication, modification time, preferred block size, blocks, permissions, client name, client machine, and asserts that old block-location count is zero. It converts the last block to `UNDER_CONSTRUCTION` and constructs an `INodeFile` with lazy-persist absent in pre-protobuf images. `writeINodeUnderConstruction` writes the same compatibility form and intentionally writes zero block locations.

Primitive and block-array behavior: string and byte-array encodings use `DeprecatedUTF8` or short-length local names, preserving old image/edit-log compatibility. `readPathComponents` converts a serialized full path directly to `byte[][]` components without creating a string first. `writeCompactBlockArray` delta-encodes block sizes and generation stamps with variable-length longs while writing random block ids directly; `readCompactBlockArray` rejects negative counts and reconstructs absolute values from deltas.

Cache and erasure-coding persistence: `writeCacheDirectiveInfo` and `readCacheDirectiveInfo` use a bitmask for optional path, replication, pool, and expiration fields and reject unknown flags. XML variants translate the same logical fields through `XMLUtils.Stanza` and SAX events. `writeCachePoolInfo` and `readCachePoolInfo` persist pool name plus optional owner, group, mode, limit, max relative expiry, and default replication behind a bitmask that rejects unknown bits; XML variants mirror those fields. `writeErasureCodingPolicy` and `readErasureCodingPolicy` persist codec name, data/parity units, cell size, and optional schema extra options.

Dependencies and integration points: used heavily by `FSImageFormat`, `SnapshotFSImageFormat`, `FSEditLogOp`, `CacheManager`, offline image viewer code, and legacy image tooling. It integrates with `INode` subclasses, `Block`, `BlockInfoContiguous`, `PermissionStatus`, `FsPermission`, `QuotaCounts`, `CacheDirectiveInfo`, `CachePoolInfo`, `ECSchema`, `ErasureCodingPolicy`, `XMLUtils`, Hadoop writable types, and layout feature checks through callers.

Risks: these helpers define durable binary compatibility, so field order, sentinel markers, bitmask values, and string encodings cannot change casually. `writeBytes` uses a short length, so local-name length constraints must be enforced elsewhere. Thread-local reuse is allocation-friendly but unsafe if callers keep references to mutable writable internals. Compact block arrays rely on deltas and reject only negative counts, so corrupt deltas can still produce nonsensical sizes or generation stamps unless higher-level validation catches them. XML and binary variants must stay semantically aligned for offline image viewer and edit-log XML tooling.

Test signals: tests should round-trip every inode type including references and under-construction files, validate block delta encoding, exercise cache directive/pool binary and XML optional-field combinations including unknown-flag rejection, test erasure-coding schema extra options, verify path component and local-name encodings, and run edit-log compatibility tests because many `FSEditLogOp` classes call these primitives directly.

## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/namenode/FSImageStorageInspector.java

Purpose: abstract strategy interface for scanning NameNode storage directories and producing a namespace image load plan. It hides the difference between transactional fsimage naming and legacy timestamp-based storage from callers such as `NNStorage` and `FSImage`.

Important APIs and types: subclasses implement `inspectDirectory(StorageDirectory)`, `isUpgradeFinalized()`, `getLatestImages()`, `getMaxSeenTxId()`, and `needToSave()`. The nested `FSImageFile` value object records the storage directory, checkpoint transaction id, and concrete file. Its constructor asserts that txids are nonnegative or `HdfsServerConstants.INVALID_TXID`; `getFile`, `getCheckpointTxId`, and `toString` expose the selected image.

Control flow: callers create a concrete inspector, pass it to storage-directory traversal, and then ask it for selected image files and post-load decisions. `getLatestImages` is allowed to throw when no usable image exists or when storage consistency is insufficient. `needToSave` tells startup whether a fresh namespace save is required after loading and replaying edits.

State and persistence behavior: the abstract class has no mutable state beyond the `FSImageFile` record, but it defines the persisted-state contract for subclasses: inspect local storage directories, account for finalized upgrade state, choose the image checkpoint, report the maximum seen txid floor, and indicate whether storage should be rewritten to reconcile stale or recovered directories.

Dependencies and integration points: depends on `StorageDirectory`, `HdfsServerConstants`, and `File`. Implemented by `FSImageTransactionalStorageInspector` and `FSImagePreTransactionalStorageInspector`. Used by `NNStorage.inspectStorageDirs`, `FSImage`, `BackupImage`, and storage retention code that must reason about image files without parsing image contents.

Risks: the abstraction is package-private and intentionally narrow, but incorrect subclass semantics can make the NameNode load an older image, ignore a required seen-txid floor, or skip a required save after recovery. `FSImageFile` exposes package-visible `sd` and `txId` fields, so ordering and comparisons rely on callers preserving the meaning of `INVALID_TXID` for legacy images.

Test signals: storage inspector tests should verify selected image files across multiple storage directories, no-image failures, upgrade-finalized detection through `previous` directories, need-to-save behavior, max-seen-txid reporting, and stable formatting of `FSImageFile` for diagnostics. `TestFSImageStorageInspector` and NameNode storage configuration tests are the direct signals.

## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/namenode/FSImageTransactionalStorageInspector.java

Purpose: storage inspector for transactional NameNode layouts where fsimage filenames carry checkpoint txids such as `fsimage_0000000000000000123`. It discovers valid image files, records the highest seen transaction id from storage metadata, detects unfinalized upgrades, and returns all latest-equivalent image copies.

Important APIs and state: constructors accept either the default `NameNodeFile.IMAGE` type or an `EnumSet<NameNodeFile>` for alternate image-like files used by retention and transfer code. Each target name builds a regex `<name>_(\\d+)`. `inspectDirectory` updates `needToSave`, `maxSeenTxId`, `foundImages`, and `isUpgradeFinalized`. `getLatestImages` returns all images whose txid equals the highest discovered txid. `getFoundImages` exposes an immutable copy for retention logic and tests.

Control flow: inspection first treats a missing version file as a just-formatted directory and marks `needToSave`. It then tries to read the directory's transaction id file with `NNStorage.readTransactionIdFile`; failure logs a warning and skips further inspection of that directory. It lists the `current` directory, matches candidate filenames against configured image patterns, parses the txid, and accepts only files from storage directories configured for images. Malformed txid names are logged and skipped. The finalized flag is the conjunction of all inspected directories lacking a `previous` directory.

State and persistence behavior: the class does not open or validate image contents. Its durable inputs are the storage version file, seen-txid file, `current` directory listing, fsimage-like filenames, storage directory type, and `previous` directory. `maxSeenTxId` is a lower bound that later edit-log selection must honor. `needToSave` only covers freshly formatted directories in this implementation; inconsistent or stale transactional image selection is handled by missing image errors or edit-log recovery elsewhere.

Dependencies and integration points: extends `FSImageStorageInspector`, uses `NNStorage.NameNodeFile`, `NameNodeDirType`, `StorageDirectory`, `FileUtil.listFiles`, and Guava immutable/list helpers. ## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/namenode/FSImageUtil.java

Purpose: small utility for recognizing and opening protobuf FSImage files. It defines the protobuf image magic header, validates container version/layout support from the tail summary, and wraps section streams with configured compression codecs.

Important APIs: `MAGIC_HEADER` is the UTF-8 bytes for `HDFSIMG1`; `FILE_VERSION` is the supported on-disk container version. `checkFileFormat(RandomAccessFile)` verifies minimum file length and leading magic bytes. `loadSummary(RandomAccessFile)` reads the last four bytes as summary length, reads the preceding delimited `FileSummary`, validates `ondiskVersion`, and requires the summary layout version to support `Feature.PROTOBUF_FORMAT`. `wrapInputStreamForCompression(Configuration, String, InputStream)` returns the original stream for an empty codec name or creates the configured image codec input stream.

Control flow: callers position or open a `RandomAccessFile`, call `checkFileFormat` to reject short or non-protobuf images, then call `loadSummary` to parse the summary from the file tail. Section readers pass the summary codec string to `wrapInputStreamForCompression` before parsing protobuf records.

State and persistence behavior: this class has no internal mutable state. It encodes container-level persistence constants and validates summary fields that control all protobuf section parsing. `loadSummary` uses a fixed four-byte length suffix and treats nonpositive length as an `IOException`.

Dependencies and integration points: used by `FSImageFormatProtobuf.Loader`, offline image viewer tools such as `FSImageLoader`, `PBImageTextWriter`, and `FileDistributionCalculator`, and any code that needs to inspect protobuf fsimage sections. It depends on `FsImageProto.FileSummary`, `NameNodeLayoutVersion`, `LayoutVersion.Feature.PROTOBUF_FORMAT`, `FSImageCompression`, Hadoop `CompressionCodec`, and `Configuration`.

Risks: `checkFileFormat` consumes bytes from the current file position and does not rewind, so callers must account for file position before subsequent reads. A corrupt or extreme summary length can seek before the file start or allocate a large byte array; validation only rejects nonpositive lengths and unsupported versions. Compression codec class names in the summary are trusted through `FSImageCompression.createCompression`, so missing codecs fail load. The utility validates protobuf-format feature support but does not enforce exact layout-version equality; that is caller policy.

Test signals: tests should cover short files, wrong magic, valid magic, negative or zero summary length, unsupported on-disk version, unsupported layout version, uncompressed stream pass-through, compressed stream wrapping with configured codecs, and offline viewer parsing of summary/sections.

## sources/distributed-fs/hadoop/hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/namenode/FSNDNCacheOp.java

Purpose: NameNode-side cache directive and cache pool operation helper. It is a package-private static dispatch layer used by `FSNamesystem` to call `CacheManager` with the right permission checker and then persist successful mutations to the edit log with retry-cache metadata.

Important APIs: directive methods are `addCacheDirective`, `modifyCacheDirective`, `removeCacheDirective`, and `listCacheDirectives`. Pool methods are `addCachePool`, `modifyCachePool`, `removeCachePool`, and `listCachePools`. `getFsPermissionChecker` returns `fsn.getPermissionChecker()` only when permissions are enabled, otherwise `null`, matching `CacheManager`'s permission-check contract.

Control flow: add directive obtains a permission checker, rejects client-supplied directive ids, calls `cacheManager.addDirective`, logs the effective directive to the edit log, and returns it. Modify/remove directive obtain a checker, apply the cache-manager mutation, and log the corresponding edit. List directive obtains a checker and returns the cache-manager batched iterator result. Cache pool add/modify/remove call the corresponding cache-manager operation and log edits; list pools uses the permission checker for filtering/authorization but does not log because it is read-only.

State and persistence behavior: the class itself has no state. Mutating methods change `CacheManager` in-memory state and immediately append edit-log records through `FSNamesystem.getEditLog()`: add/modify/remove cache directive info and add/modify/remove cache pool. The `logRetryCache` parameter is forwarded so idempotent RPC retry handling is persisted consistently. Read methods return `BatchedListEntries` without persistence changes.

Dependencies and integration points: called by `FSNamesystem` cache RPC methods around lines that handle add, modify, remove, and list cache directives and pools. It depends on `CacheManager`, `FSPermissionChecker`, `CacheDirectiveInfo`, `CacheDirectiveEntry`, `CachePoolInfo`, `CachePoolEntry`, `CacheFlag`, Hadoop batched iterators, and `AccessControlException`. Durable state written by these methods is later serialized in fsimage/edit-log paths through `CacheManager` and `FSImageSerialization`.

Risks: correct ordering matters: edit-log writes happen after successful cache-manager mutation, so failures between mutation and log append would need surrounding `FSNamesystem` locking/error handling to preserve consistency. Passing `null` permission checkers when permissions are disabled must remain accepted by `CacheManager`. Add directive's explicit id rejection protects id allocation; removing it would allow clients to collide with persisted ids. Since this class is a thin layer, behavioral checks such as quota, pool authorization, and directive validation live in `CacheManager` and must not be assumed here.

Test signals: tests should cover add/modify/remove/list directives and pools through `FSNamesystem`, permission-enabled and permission-disabled paths, client-supplied id rejection, edit-log replay and retry-cache behavior, batched listing filters/start keys, and fsimage persistence of cache manager state after operations.
