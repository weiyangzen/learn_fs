# Research: sources/storage-engines/rocksdb/db/version_set_test.cc

- **Purpose:** Large regression suite for `db/version_set.h` behavior. It validates version-storage metadata, manifest replay and rewrite, WAL edits persisted through `VersionEdit`, atomic-group semantics, best-effort recovery from incomplete manifests, missing SST/blob-file handling, off-peak time parsing, timestamp history lower bounds, and file-metadata cache charging.
- **Important APIs/types/functions:** Test fixtures include `GenerateLevelFilesBriefTest`, `VersionStorageInfoTestBase`, `VersionStorageInfoTest`, `VersionStorageInfoTimestampTest`, `FindLevelFileTest`, `VersionSetTestBase`, `VersionSetTest`, `VersionSetWithTimestampTest`, `VersionSetAtomicGroupTest`, `AtomicGroupBestEffortRecoveryTest`, `VersionSetTestDropOneCF`, `EmptyDefaultCfNewManifest`, `VersionSetTestEmptyDb`, `VersionSetTestMissingFiles`, `BestEffortsRecoverIncompleteVersionTest`, and `ChargeFileMetadataTestWithParam`. Helpers construct manifests (`PrepareManifest`, `CreateCurrentFile`, `CreateNewManifest`), dummy SST/blob files (`CreateDummyTableFiles`, `WriteDummyBlobFile`), and call `VersionSet::Recover`, `TryRecoverFromOneManifest`, `TryRecover`, `LogAndApply`, `Close`, `AddLiveFiles`, and `GetObsoleteFiles`.
- **Control flow:** The file starts with isolated unit tests for brief level-file generation and range overlap searching, then builds increasingly realistic `VersionSet` fixtures around a temporary DB directory and mock table factory. Manifest tests write `VersionEdit` records directly with `log::Writer`, set `CURRENT`, recover through `VersionSet`, and assert resulting column families, live files, WAL sets, blob metadata, and manifest validation counters. Atomic-group tests use marked `VersionEdit` sequences and sync points to verify buffering, replay, incomplete trailing groups, corrupt groups, incorrect group sizes, and reactive reads. Best-effort recovery tests intentionally create missing table/blob references, then assert which suffixes can be retained.
- **State and persistence behavior:** The suite creates real test directories, MANIFEST files, CURRENT files, SST files through a mock table builder, and valid blob files through `BlobLogWriter`. It checks persistence across `VersionSet` reopen, new MANIFEST creation, MANIFEST truncation/corruption, and DB close. WAL tests confirm WAL additions/deletions are persisted in MANIFEST and replayed into `WalSet` without creating unnecessary `Version` objects for pure WAL edits.
- **Dependencies and integration points:** Depends on `db/version_set.h`, `db/version_edit.h`, `db/manifest_ops.h`, blob metadata/writer classes, `MockTableFactory`, `MockSystemClock`, `SyncPoint`, `DBTestBase`, block-based table cache charging utilities, and filesystem helpers. It is an integration-level guard for manifest format, recovery behavior, table/blob liveness accounting, and DB option interactions.
- **Risks:** These tests encode subtle recovery rules: pure WAL edits must not allocate new versions, smaller WAL synced-size updates must be ignored, dropped column families must be removed from atomic flush groups, MANIFEST validation must rotate only when enabled or size checks fail, and best-effort recovery must not keep unsafe non-L0 or non-suffix missing-file states. Because the suite manually edits manifests, drift in `VersionEdit` encoding, required fields, or CF metadata can break many cases.
- **Test signals:** Uses `ASSERT_OK`, `EXPECT_NOK`, status class checks, live-file counts, WAL map contents, blob-file lists, sync-point counters, statistics ticker `MANIFEST_VALIDATION_FAILURE_COUNT`, and cache charge totals. Running the RocksDB `version_set_test` binary is the direct signal.

# Research: sources/storage-engines/rocksdb/db/version_util.cc

- **Purpose:** Implements `LoadTableHandlersHelper`, a DB-open helper that eagerly opens SST table readers and pins table-cache handles for a set of `FileMetaData` entries.
- **Important APIs/types/functions:** Exports `Status LoadTableHandlersHelper(...)`. It consumes `(FileMetaData*, level)` pairs, `TableCache`, `FileOptions`, `InternalKeyComparator`, `InternalStats`, `MutableCFOptions`, `ReadOptions`, max thread count, prefetch controls, L0 metadata pin-size limit, and an optional atomic stop flag.
- **Control flow:** The helper uses an atomic file index shared by worker threads. Each worker exits when another worker records an error, all files are consumed, the optional stop flag is set, or the table cache has reached finite capacity. For each file it calls `TableCache::FindTable` with `pin_table_handle=true`, histogram selection from `InternalStats::GetFileReadHist(level)`, filter/prefetch settings, level, temperature, and pinning limits. The caller thread participates as one worker after spawning `max_threads - 1` background `port::Thread`s.
- **State and persistence behavior:** It mutates table-cache state by opening/pinning table handles; it does not write persistent data. `ret` records the first failing `Status` using an atomic `has_error` guard.
- **Dependencies and integration points:** Depends on `TableCache`, `InternalStats`, `FileMetaData`, `port::Thread`, and `SyncPoint` hooks around `FindTable`. It is called from version-building/open paths to warm cache before the DB starts serving normal reads.
- **Risks:** Shared `ret` is written only by the thread that wins `compare_exchange_strong`, so status publication relies on all threads joining before return. The capacity guard stops early when usage reaches capacity, so callers must tolerate partial warming. `max_threads` is assumed positive; invalid values would reduce concurrency semantics.
- **Test signals:** Sync points `VersionBuilder::Rep::LoadTableHandlers::BeforeFindTable` and `AfterFindTable` allow tests to inject or observe table-open behavior. Expected outcomes are first error propagation, stop-flag cancellation, and no overrun of table-cache capacity.

# Research: sources/storage-engines/rocksdb/db/version_util.h

- **Purpose:** Declares version utility helpers and defines `OfflineManifestWriter`, a thin wrapper around `VersionSet` for reading and modifying MANIFEST state without opening a full DB.
- **Important APIs/types/functions:** Declares `LoadTableHandlersHelper`. Defines `OfflineManifestWriter` with constructor, `Recover`, `LogAndApply`, `Versions`, `IOptions`, and private `WithDbPath`. It owns `WriteController`, `WriteBufferManager`, `ImmutableDBOptions`, a small table cache, `EnvOptions`, and `VersionSet`.
- **Control flow:** The constructor sanitizes DB path state, creates a 1 MiB LRU table cache, and initializes `VersionSet` with user DB options and no tracers/error handler. `Recover` forwards to `VersionSet::Recover` with missing-file tolerance enabled. `LogAndApply` creates and locks an `InstrumentedMutex` to satisfy `VersionSet::LogAndApply`'s DB-mutex contract, applies the edit, then unlocks.
- **State and persistence behavior:** `OfflineManifestWriter` can persist new manifest edits through `VersionSet::LogAndApply`, including file removals, CF metadata, and other `VersionEdit` changes. It avoids DB flush/compaction side effects and uses `no_error_if_files_missing=true` during recovery so offline cleanup can target already-missing files.
- **Dependencies and integration points:** Includes `db/version_set.h`, RocksDB options/status/file-system headers, cache creation, write controller/buffer manager, and `FSDirectory`. It is intended for manifest operations tools or APIs that need real option parsing but not full DB lifecycle.
- **Risks:** It imitates the DB mutex locally; callers must avoid concurrent use unless they provide higher-level serialization. Because it bypasses DB open, it will not perform normal DB-side validation, background work, or live-file lifecycle management. `WithDbPath` only fills `db_paths` when empty, matching `SanitizeOptions` expectations.
- **Test signals:** Correctness is visible through successful `Recover`, persisted `LogAndApply` results, and subsequent DB/VersionSet recovery from the modified MANIFEST.

# Research: sources/storage-engines/rocksdb/db/wal_edit.cc

- **Purpose:** Implements WAL manifest edit encoding/decoding and the in-memory `WalSet` state machine used by `VersionSet` recovery and WAL durability checks.
- **Important APIs/types/functions:** Implements `WalAddition::EncodeTo`, `WalAddition::DecodeFrom`, JSON/ostream/debug output for `WalAddition`, `WalDeletion` encode/decode/output/debug, and `WalSet::{AddWal,AddWals,DeleteWalsBefore,Reset,CheckWals}`.
- **Control flow:** `WalAddition` encodes the WAL number, optional synced-size tag, and terminating tag. Decode reads the number, then tag/value pairs until `kTerminate`, rejecting unknown or truncated tags as corruption. `WalDeletion` encodes only the cutoff WAL number. `WalSet::AddWal` ignores obsolete WALs below `min_wal_number_to_keep_`, inserts new WAL metadata, treats duplicate creation without synced size as corruption, ignores out-of-order smaller/equal synced-size updates, and otherwise advances the synced size. `DeleteWalsBefore` monotonically raises the cutoff and erases lower-numbered entries.
- **State and persistence behavior:** `WalAddition` and `WalDeletion` bytes are persisted inside MANIFEST `VersionEdit` records. `WalSet` itself is in-memory and reconstructed by replay. `min_wal_number_to_keep_` is not separately persisted; replayed deletion edits recreate its effect.
- **Dependencies and integration points:** Uses `Slice`, `Status`, `PutVarint*`, `GetVarint*`, and `Env::GetFileSize`. Integrated with `VersionEdit`, `VersionSet`, MANIFEST rewrite, WAL creation/sync/deletion logging, and recovery-time WAL consistency checks.
- **Risks:** `WalAdditionTag` values are persisted format and must remain backward compatible. Older readers reject unknown tags, so adding future tags requires compatibility planning. Unsynced WALs are deliberately skipped by `CheckWals` because directory entries may not be durable; this is correct but means only synced-size metadata is enforceable.
- **Test signals:** Covered by `wal_edit_test.cc` and `version_set_test.cc`: duplicate create corruption, synced-size overwrite rules, deletion cutoff behavior, missing WAL detection, shrink-size detection, and recovery from MANIFEST.

# Research: sources/storage-engines/rocksdb/db/wal_edit.h

- **Purpose:** Declares WAL metadata/edit classes that are embedded in `VersionEdit` and replayed by `VersionSet` to remember live WAL files and their durable synced sizes.
- **Important APIs/types/functions:** Defines `WalNumber`, `WalMetadata`, persisted enum `WalAdditionTag`, `WalAddition`, `WalDeletion`, `WalAdditions`, and `WalSet`. Public operations include metadata synced-size accessors, WAL addition/deletion encode/decode/debug methods, `WalDeletion::IsEmpty/Reset`, `WalSet::AddWal`, `AddWals`, `DeleteWalsBefore`, `Reset`, `GetMinWalNumberToKeep`, `GetWals`, and `CheckWals`.
- **Control flow:** The header documents a two-stage WAL lifecycle: creation writes a `WalAddition` without synced size; sync/close writes a `WalAddition` with size; obsoletion writes a cutoff through `WalDeletion`. `WalSet` consumes these events under external synchronization.
- **State and persistence behavior:** `WalMetadata` uses `uint64_t::max()` as the sentinel for unknown synced size. `WalAdditionTag` is explicitly persisted and part of the user-visible format contract. `WalSet` stores a sorted map from log number to metadata plus a monotonically increasing in-memory minimum WAL number to keep.
- **Dependencies and integration points:** Depends on JSON event logging, RocksDB namespace/status/env declarations, STL map/vector/unordered_map, and port headers. Used by `VersionEdit` encoding, `VersionSet` WAL replay, MANIFEST rewrite, and WAL integrity checks.
- **Risks:** The class comment states modifications to `WalAddition`/`WalDeletion` may need corresponding `VersionEdit` and tests changes. `WalSet` is not thread-safe; DB mutex or equivalent serialization is required. The unknown-size sentinel must not be confused with a real file size.
- **Test signals:** Interface behavior is validated by `wal_edit_test.cc`; persistence behavior is validated by `version_set_test.cc` WAL and atomic-group cases.

# Research: sources/storage-engines/rocksdb/db/wal_manager.cc

- **Purpose:** Implements `WalManager`, the component that lists alive/archived WALs, opens transaction-log iterators, reads first sequence numbers, archives/deletes WAL files, and purges obsolete archived logs by TTL or size budget.
- **Important APIs/types/functions:** Implements `DeleteFile`, `GetSortedWalFiles`, `GetUpdatesSince`, `PurgeObsoleteWALFiles`, `ArchiveWALFile`, `GetSortedWalsOfType`, `RetainProbableWalFiles`, `ReadFirstRecord`, `GetLiveWalFile`, and `ReadFirstLine`.
- **Control flow:** `GetSortedWalFiles` lists alive logs first, optionally archived logs second, then suppresses alive duplicates that raced with archive movement. `GetUpdatesSince` rejects `seq_per_batch_`, lists WALs, trims probable files by binary search on start sequence, and constructs `TransactionLogIteratorImpl`. `PurgeObsoleteWALFiles` rate-limits itself, scans archive children, deletes files older than TTL, deletes empty files when size limit is enabled, computes how many non-empty files fit in the size budget, then deletes oldest sorted archived logs. `ReadFirstRecord` checks a mutex-protected cache, reads alive path first, falls back to archive path, and caches nonzero sequences. `ReadFirstLine` opens a sequential file, uses `log::Reader`, decodes the first write batch sequence, treats empty compressed WALs as sequence `1`, and reports corrupt first records through a reporter.
- **State and persistence behavior:** Mutates filesystem state by deleting WAL files and renaming alive WALs to archive. Maintains in-memory `read_first_record_cache_` and `purge_wal_files_last_run_`; cache entries are erased on successful deletion/purge. It reads WAL file sizes and first records but does not write WAL contents.
- **Dependencies and integration points:** Depends on filename parsing, log reader/writer format, `TransactionLogIteratorImpl`, `WriteBatchInternal`, `DeleteDBFile`, filesystem/env APIs, `IOTracer`, sync points for race tests, and DB options (`WAL_ttl_seconds`, `WAL_size_limit_MB`, `paranoid_checks`, `wal_dir`, clock).
- **Risks:** WAL movement/deletion races are explicitly handled but still require careful path construction. Size-limit deletion computes keep count from largest observed file, a conservative approximation. `ReadFirstRecord` uses sequence `0` as skip/empty and `1` for compressed-empty inclusion, so consumers must treat the value as an inclusion hint in that edge case. TTL logic uses wall-clock time and guards against unsigned underflow when clocks move backwards.
- **Test signals:** `wal_manager_test.cc` checks cache behavior, TTL and size purge, clock-backwards safety, iterator behavior over empty WALs, and `TryAgain` when new logs appear after iterator creation. Other DB tests use sync points for archive/list races.

# Research: sources/storage-engines/rocksdb/db/wal_manager.h

- **Purpose:** Declares `WalManager`, the DB-side abstraction for treating WAL files as an ordered transaction-log stream while also managing archive deletion and first-record metadata.
- **Important APIs/types/functions:** Public methods include `GetSortedWalFiles`, `GetUpdatesSince`, `PurgeObsoleteWALFiles`, `ArchiveWALFile`, `DeleteFile`, `GetLiveWalFile`, and test-only wrappers `TEST_ReadFirstRecord`/`TEST_ReadFirstLine`. Private helpers include `GetSortedWalsOfType`, `RetainProbableWalFiles`, `ReadFirstRecord`, and `ReadFirstLine`.
- **Control flow:** Callers request sorted WAL metadata or a transaction-log iterator. Internally the manager enumerates alive/archive directories, derives start sequence numbers from first records, filters likely WALs for the requested sequence, and hands ownership to the iterator. Purge operations are separate and controlled by DB options.
- **State and persistence behavior:** Holds references/copies of immutable DB options, file options, `Env`, `FileSystemPtr`, WAL directory string, archive-location flag, IO tracer, a mutex-protected first-record cache, and an atomic last-purge timestamp. It persists no metadata itself; durable state is the WAL/archive files on disk.
- **Dependencies and integration points:** Includes `db/version_set.h`, file utilities, DB options, `rocksdb/transaction_log.h`, `Env`, `Status`, atomic utilities, and `IOTracer`. Integrated with `DBImpl` WAL lifecycle, transaction-log tailing APIs, and obsolete-file cleanup.
- **Risks:** The class stores `const std::string& wal_dir_` bound to `ImmutableDBOptions`; the options object must outlive the manager. Cache coherence depends on using `WalManager` deletion paths or explicit erase in purge code. `seq_per_batch_` disables `GetUpdatesSince`.
- **Test signals:** The header exposes test wrappers for first-record parsing; production tests validate public sorted-log, live-log, archive, and iterator behaviors.

# Research: sources/storage-engines/rocksdb/db/wide/blob_column_resolver_util.h

- **Purpose:** Header-only shared helpers for resolving wide-column blob values in read and compaction paths.
- **Important APIs/types/functions:** Namespace `blob_resolver_util` provides `FindBlobColumn`, `FindInCache`, `CacheInlinedBlob`, and `IsBlobColumnIndex`. It operates on vectors of `(column_index, BlobIndex)` and `(column_index, unique_ptr<PinnableSlice>)`.
- **Control flow:** Each lookup helper performs a linear scan because the expected number of blob columns per entity is small. `FindBlobColumn` returns the matching `BlobIndex` or null, handling a null blob-columns pointer. `FindInCache` returns a cached `PinnableSlice*` or null. `CacheInlinedBlob` appends a new `PinnableSlice`, pins the inline blob value from `BlobIndex::value()`, and returns a `Slice` over the cached value. `IsBlobColumnIndex` delegates to `FindBlobColumn`.
- **State and persistence behavior:** No persistent state. The only mutation is appending to the caller-owned per-resolution cache so returned `Slice`s remain valid after the helper returns.
- **Dependencies and integration points:** Depends on `db/blob/blob_index.h`, `rocksdb/slice.h`, and `PinnableSlice`. Shared by `ReadPathBlobResolver` and `CompactionBlobResolver` to keep blob-column lookup/cache logic consistent across foreground reads and compaction.
- **Risks:** Returned pointers and slices are valid only while the caller-owned vectors and `PinnableSlice` instances remain alive and un-invalidated. Duplicate column indices would return/cache the first match for lookup but `CacheInlinedBlob` does not deduplicate, so callers should check cache before appending. Linear scan is appropriate for the documented few-column case but would scale poorly if wide entities contain many blob columns.
- **Test signals:** No direct test in this file. Expected signals come from wide-column blob read/compaction tests that compare resolved values, cache reuse, and behavior for non-blob columns.
