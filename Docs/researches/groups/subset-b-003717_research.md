# sources/distributed-fs/ceph-client/drivers/gpu/drm/radeon/clearstate_si.h

Purpose: provides the Southern Islands render clear-state data consumed by the radeon clear-state machinery. The file is a static hardware register reset table rather than executable logic: it describes default values for the `SECT_CONTEXT` register section so the driver can emit a known-good context state into GPU command streams.

Important APIs and types: the file includes `clearstate_defs.h` and instantiates seven `static const u32` arrays named `si_SECT_CONTEXT_def_1` through `si_SECT_CONTEXT_def_7`. These arrays are collected into `static const struct cs_extent_def si_SECT_CONTEXT_defs[]`, where each entry provides an array pointer, starting register address, and count. `static const struct cs_section_def si_cs_data[]` exposes the section list with `SECT_CONTEXT` and a `SECT_NONE` terminator.

Control flow: there is no runtime control flow in this header. The consuming clear-state code walks `si_cs_data`, then walks each `cs_extent_def`, writing each value at the corresponding sequential context register offset. Zero-valued `HOLE` entries preserve address spacing for registers that are skipped or reserved by the hardware layout, so the array index remains aligned with the register address range.

State and persistence: all state is immutable build-time data. The persistent effect occurs only after another radeon component emits these values to the GPU, resetting context registers such as DB depth/stencil state, PA scissor and viewport state, SPI interpolation/input state, CB color target state, VGT tessellation/streamout state, and AA/sample defaults. The static data itself has no dynamic lifetime, allocation, locking, or persistence outside the module image.

Dependencies and integration points: the table depends on `struct cs_extent_def`, `struct cs_section_def`, and section enum values from `clearstate_defs.h`. It integrates with the radeon command-submission/render-state setup code for SI-generation ASICs. The register names in comments are documentation only; correctness depends on each array length matching the extent count and the encoded base register addresses matching the SI context register map.

Risks: this file is fragile because the data is positional. A missing, extra, or reordered value shifts every following register write in an extent. `HOLE` entries are significant and must not be trimmed. Register defaults such as broad scissors (`0x40004000`), enabled masks, viewport z ranges, `PA_CL_CLIP_CNTL`, `PA_SU_SC_MODE_CNTL`, `IA_MULTI_VGT_PARAM`, and color target default blocks must match hardware expectations; incorrect values can cause hangs, rendering corruption, or invalid command streams. The header lacks include guards and is intended for controlled inclusion by one data consumer.

Test signals: useful validation is build coverage for the including clear-state unit, static checks that each extent count equals the corresponding array length, and runtime smoke tests on SI hardware that initialize rings, emit clear state, and run simple GL/DRM render operations. GPU hang tests and register-dump comparison against known-good SI defaults are the highest-signal checks.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/radeon/cypress_dpm.c

Purpose: implements Dynamic Power Management for Evergreen/Cypress-family radeon GPUs. It programs clocks, voltages, memory-controller timing, PCIe Gen2 behavior, spread spectrum, clock gating, display-gap behavior, and SMC firmware tables so the ASIC can switch among low/medium/high power levels and ACPI states.

Important APIs and types: exported entry points include `cypress_dpm_init`, `cypress_dpm_fini`, `cypress_dpm_setup_asic`, `cypress_dpm_enable`, `cypress_dpm_disable`, `cypress_dpm_set_power_state`, `cypress_dpm_display_configuration_changed`, and `cypress_dpm_vblank_too_short`. SMC table helpers include `cypress_convert_power_level_to_smc`, `cypress_populate_smc_initial_state`, `cypress_populate_smc_acpi_state`, `cypress_populate_smc_voltage_tables`, `cypress_upload_sw_state`, `cypress_upload_mc_reg_table`, `cypress_get_table_locations`, and `cypress_populate_mc_reg_table`. Clock and memory helpers include `cypress_populate_mclk_value`, `cypress_map_clkf_to_ibias`, `cypress_get_mclk_frequency_ratio`, `cypress_get_strobe_mode_settings`, `cypress_calculate_burst_time`, and `cypress_program_memory_timing_parameters`. The implementation uses `struct evergreen_power_info` from `cypress_dpm.h`, embedded `struct rv7xx_power_info`, AtomBIOS voltage/timing tables, and `RV770_SMC_*`/`SMC_Evergreen_*` firmware structures.

Control flow: initialization allocates `struct evergreen_power_info`, parses platform and power tables, sets default thresholds and feature flags, detects voltage GPIO support, and records the SMC SRAM limit. ASIC setup reads clock/voltage/memory properties, advertises PCIe Gen2 when ACPI support exists, and enables ACPI power management. Enabling DPM restores clock gating state, constructs voltage tables, derives MVDD configuration, optionally builds dynamic AC timing tables by forcing MC S0/S1 states, enables backbias/spread-spectrum/thermal features, uploads SMC firmware, reads SMC table offsets, populates the SMC state table and MC register table, starts the SMC, enables SCLK/MCLK control, starts global power management, and enables clock gating/throttling. A power-state transition restricts levels, optionally requests a PCIe link-speed increase before the switch, sets UVD clocks, halts the SMC, uploads the new software state and MC table, programs memory timing registers, resumes the SMC, asks firmware to switch state, updates UVD, and optionally requests a PCIe link-speed decrease after the switch. Disable reverses the hardware features, stops DPM/SMC, disables spread spectrum, restores MC state, and resets SMIO status.

State and persistence: persistent software state is stored in `rdev->pm.dpm.priv` as `struct evergreen_power_info`, including feature booleans, VDDC/VDDCI voltage tables, MVDD indices, MC register table data, ACPI VDDCI, SMC table offsets, and current/requested power-state snapshots. Hardware-persistent state includes many MMIO registers, SMC SRAM state tables, SMC soft registers, clock-gating configuration, PCIe capability/request state, and MC timing state. Firmware-facing structs are explicitly byte-swapped with `cpu_to_be16`/`cpu_to_be32`; endian correctness is part of the persistent hardware contract. The code also tracks whether an ACPI PCIe performance request was registered so it can be removed or updated consistently.

Dependencies and integration points: the file depends on AtomBIOS helpers for clock dividers, spread-spectrum data, memory info, AC timing, voltage tables, and power-table parsing. It builds on RV770/RV740/R600 DPM helpers for SCLK population, response times, firmware upload, SMC messaging, voltage control, UVD clock sequencing, thermal throttling, and memory timing. It uses Evergreen register definitions from `evergreen.h`/`evergreend.h`, radeon device/ASIC hooks from `radeon.h` and `radeon_asic.h`, Linux PCI/ACPI support, and low-level register macros such as `RREG32`, `WREG32`, `WREG32_P`, `RREG32_PCIE_PORT`, and `WREG32_PCIE_PORT`.

Risks: this is hardware-sequencing code with tight ordering requirements. MC S0/S1 forcing waits for vblank and sequencer responses; timeout or ordering mistakes can produce display corruption or memory-controller instability. SMC SRAM offset reads and uploads must match the firmware header layout. Voltage-table trimming drops lower entries when more than `MAX_NO_VREG_STEPS` exist, so off-by-one or unsorted AtomBIOS data can select the wrong voltage. PCIe Gen2 ACPI requests depend on platform firmware behavior and current link status. Dynamic AC timing is disabled on initialization failure, but partial hardware state may already have been touched. Many helpers return `-EINVAL` on unsupported voltage/SMC conditions; callers log and abort enable/transition paths, so regressions often appear as DPM failing to enable rather than isolated helper failures.

Test signals: build tests must cover both `CONFIG_ACPI` and non-ACPI paths. Runtime validation requires Evergreen/Cypress-class hardware across GDDR5 and non-GDDR5 memory, mobile and desktop boards, and multiple display counts. High-signal tests include DPM enable/disable loops, suspend/resume, power-profile switching, UVD workload transitions, PCIe link-speed changes, vblank-short detection under active displays, thermal throttling interrupts, and GPU hang detection while changing memory clocks. Register/SMC table dumps compared with AtomBIOS expectations are valuable for MC timing and voltage programming.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/radeon/cypress_dpm.h

Purpose: declares the Evergreen/Cypress DPM private data structures, constants, and helper prototypes shared by Cypress-family power-management implementation files. It adapts the RV770 DPM model to Evergreen SMC memory-register tables, VDDCI/MVDD handling, AC timing, and display/PCIe features.

Important APIs and types: `struct evergreen_mc_reg_entry` stores one memory-clock threshold and the MC register values for that range. `struct evergreen_mc_reg_table` stores the valid-register mask, entry count, last address slot, per-range register data, and SMC register addresses. `struct evergreen_ulv_param`, `struct evergreen_arb_registers`, and `struct at` hold ULV, arbitration, and timing parameters. `struct evergreen_power_info` embeds `struct rv7xx_power_info` as its first field and adds Evergreen-specific booleans, voltage tables, MVDD indices, MC register data, SMC offsets, and current/requested state copies. The header also declares Cypress DPM helpers for SMC conversion/upload, voltage-table construction, memory timing, display-gap setup, SCLK/MCLK control, PCIe Gen2 advertisement, and MCLK strobe/frequency calculations.

Control flow: the header itself has no runtime control flow. Its layout defines the data contract used by `cypress_dpm.c` and related radeon DPM code. The "must be first" embedded `rv7xx_power_info` supports helper code that treats Evergreen state as an RV770-compatible base with additional fields available through `evergreen_get_pi()`.

State and persistence: this header defines persistent per-device DPM state. The MC register table persists across DPM transitions and is uploaded into SMC SRAM when dynamic AC timing is active. Voltage tables persist after AtomBIOS parsing and are reused for every SMC state conversion. Feature booleans such as `memory_transition`, `pcie_performance_request`, `sclk_deep_sleep`, and `uvd_enabled` gate later hardware programming. `current_*` and `requested_*` snapshots preserve software-side power-state context.

Dependencies and integration points: it includes `rv770_dpm.h` for the base DPM model and `evergreen_smc.h` for SMC table types and constants such as `SMC_EVERGREEN_MC_REGISTER_ARRAY_SIZE`. The prototypes are consumed by other radeon ASIC-specific DPM files that share Cypress conversion logic. It integrates with AtomBIOS voltage tables, radeon power states, and RV770 SMC firmware structures.

Risks: structure layout is part of an implicit inheritance pattern; moving `rv7xx` away from the first field would break base-helper casts. Constants such as `CYPRESS_MGCGCGTSSMCTRL_DFLT`, Redwood/Cedar variants, and `CYPRESS_VRC_DFLT` encode hardware-specific defaults. The MC register arrays are bounded by SMC constants and `MAX_AC_TIMING_ENTRIES`; producers must not overrun them when parsing AtomBIOS tables. Public prototypes expose many low-level helpers, so call ordering must be enforced by implementation code rather than the type system.

Test signals: compile coverage across all radeon files including this header is the first guard. Runtime validation comes from Cypress DPM initialization, SMC uploads, dynamic AC timing, and power-state transitions that exercise the state fields. Static layout checks or targeted review should verify the embedded-base invariant and array bounds.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/radeon/dce3_1_afmt.c

Purpose: implements audio format programming for DCE3.2-era radeon display hardware. It writes HDMI/DisplayPort speaker allocation, ELD/SAD audio descriptors, audio DTO clock registers, HDMI ACR packet values, audio packet enables, infoframe controls, and AVMUTE state.

Important APIs and functions: `dce3_2_afmt_hdmi_write_speaker_allocation()` and `dce3_2_afmt_dp_write_speaker_allocation()` program endpoint speaker allocation and select HDMI versus DP connection mode. `dce3_2_afmt_write_sad_regs()` converts CEA short audio descriptors into hardware audio descriptor registers. `dce3_2_audio_set_dto()` chooses DTO0 or DTO1 based on the DIG encoder and programs phase/module/wallclock ratio. `dce3_2_hdmi_update_acr()` writes CTS/N values for 32, 44.1, and 48 kHz families. `dce3_2_set_audio_packet()` enables HDMI audio packets and audio infoframes. `dce3_2_set_mute()` toggles HDMI general-control AVMUTE.

Control flow: speaker-allocation helpers read the fixed endpoint speaker register, clear the opposite transport mode and allocation bits, set HDMI or DP mode, then write either EDID-provided allocation byte `sadb[0]` or stereo fallback value 5. SAD programming iterates a static register-to-codec-type map, scans all supplied `struct cea_sad` entries, keeps the descriptor with the highest channel count for each format, accumulates PCM stereo frequencies specially, and writes one descriptor register per supported codec type. DTO setup exits when no CRTC or DIG private data exists, derives a wallclock ratio from pixel clock, and writes the matching DTO register block. ACR and packet helpers are direct offset-based register writes for the HDMI block selected by the caller.

State and persistence: no software state is allocated or retained. The persistent state is hardware register state in the audio endpoint, DCCG DTO registers, HDMI ACR packet registers, AFMT audio packet controls, infoframe controls, and AVMUTE bit. Values remain active until modeset, audio reconfiguration, reset, or another AFMT operation overwrites them.

Dependencies and integration points: the file depends on Linux HDMI constants, DRM EDID `struct cea_sad`, radeon encoder/CRTC structures, `radeon_audio.h`, `radeon_asic.h`, and DCE3/R600 register definitions from `r600d.h`. It is called by the radeon audio and modeset paths when enabling HDMI/DP audio for digital encoders on DCE3.2 hardware.

Risks: the code assumes endpoint 0 for speaker and SAD programming, which matches this hardware generation but is not portable to later multi-pin designs. `sad_count` controls whether `sadb[0]` is read, but the parameter name for speaker allocation is separate from SAD count semantics and can be confusing. DTO programming divides `clock / 24000` and writes `clock` as module, so zero or malformed pixel clocks would be invalid. Incorrect ACR/DTO values can produce silent audio or clock drift rather than obvious display failures.

Test signals: test by connecting HDMI and DP sinks with varied EDID audio blocks, checking ALSA/ELD exposure, verifying stereo fallback with absent SADB, playing PCM and compressed formats, switching modes at pixel clocks spanning all DTO ratio branches, and confirming mute/unmute behavior. Register traces around ACR and AFMT programming are useful for regressions.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/radeon/dce6_afmt.c

Purpose: implements AFMT and audio endpoint programming for DCE6/DCE8 radeon display hardware. Compared with DCE3.2, it handles multiple audio pins through per-pin endpoint offsets and locked endpoint-index/data access.

Important APIs and functions: `dce6_endpoint_rreg()` and `dce6_endpoint_wreg()` serialize indirect endpoint register reads/writes with `rdev->end_idx_lock`; writes use DCE8 direct index semantics or pre-DCE8 `AZ_ENDPOINT_REG_WRITE_EN` encoding as appropriate. `dce6_audio_get_pin()` refreshes pin connectivity and returns the first connected pin not already used by a digital encoder. `dce6_afmt_select_pin()` binds an AFMT block to a pin ID. `dce6_afmt_write_latency_fields()` writes lipsync latency from the DRM connector and mode. Speaker and SAD helpers mirror the DCE3.2 behavior but use `dig->pin->offset`. `dce6_audio_enable()` controls pin hotplug/audio enable. `dce6_hdmi_audio_set_dto()` programs HDMI DTO0, and `dce6_dp_audio_set_dto()` programs DP DTO1 with DCE8 dentist divider adjustment.

Control flow: endpoint accesses take a spinlock, select an indexed codec register, access the data register, and release the lock, protecting the shared endpoint index/data pair from concurrent users. Pin discovery scans `rdev->audio.pin[]`, reads each pin's default configuration, marks disconnected ports, then searches DRM encoder state to avoid returning a pin already assigned to a DIG encoder. Most AFMT helpers guard against missing DIG, AFMT, or pin pointers before writing registers. HDMI and DP speaker programming clear the other transport bit and set fallback stereo allocation when no speaker-allocation data exists. SAD programming loops over the same codec map as DCE3.2. DTO programming selects HDMI DTO0 or DP DTO1 source, writes phase/module ratios, and adjusts DP clock on DCE8 using the decoded display reference divider.

State and persistence: software state lives in the existing radeon device: `rdev->audio.pin[i].connected`, DIG encoder `pin` assignments, AFMT offsets, and the shared `end_idx_lock`. Hardware-persistent state includes endpoint speaker/descriptors/lipsync/hotplug registers, `AFMT_AUDIO_SRC_CONTROL`, `DCCG_AUDIO_DTO_SOURCE`, DTO phase/module registers, and DCE8 DTO1 registers. No heap allocations occur in this file.

Dependencies and integration points: the implementation uses `dce6_afmt.h`, `radeon.h`, `radeon_audio.h`, Southern Islands/DCE6 register definitions from `sid.h`, DRM encoder lists, `struct cea_sad`, and radeon digital encoder private data. It integrates with radeon modeset/audio setup when assigning audio pins and programming HDMI or DP audio for DCE6+ ASICs, including DCE8-specific register differences.

Risks: endpoint register access is indirect and shared, so any caller bypassing the lock can corrupt indexed operations. Pin selection depends on current encoder assignments; stale `dig->pin` state can lead to two encoders using one audio pin or to no pin being selected. The function logs only when no connected pin exists, and many helpers silently return when state is incomplete, which can hide setup failures. DCE8 DP clock adjustment depends on `radeon_audio_decode_dfs_div()` returning a sane divider; bad divider handling can break DP audio clocks.

Test signals: validate with DCE6 and DCE8 hardware, multiple simultaneous digital encoders, HDMI and DP sinks, hotplug cycles, and EDIDs with varied audio descriptors and latency fields. Check that endpoint register writes are stable under concurrent modesets/audio updates, ALSA ELD matches sink capabilities, DP audio remains correct across dentist divider values, and no pin is double-assigned.

# sources/distributed-fs/ceph-client/drivers/gpu/drm/radeon/dce6_afmt.h

Purpose: declares the DCE6 AFMT/audio endpoint helper interface used by radeon display and audio code. It provides forward declarations for DRM/radeon types and prototypes for endpoint access, HDMI/DP speaker/SAD programming, latency programming, pin selection, and audio DTO setup.

Important APIs and types: the header forward-declares `struct cea_sad`, `struct drm_connector`, `struct drm_display_mode`, `struct drm_encoder`, `struct radeon_crtc`, and `struct radeon_device`. Prototypes include `dce6_endpoint_rreg`, `dce6_endpoint_wreg`, `dce6_afmt_write_sad_regs`, HDMI/DP speaker allocation writers, `dce6_afmt_write_latency_fields`, `dce6_afmt_select_pin`, `dce6_hdmi_audio_set_dto`, and `dce6_dp_audio_set_dto`.

Control flow: there is no implementation flow in the header. It defines the call surface used by modeset/audio code to program DCE6+ audio hardware in a staged sequence: choose/select a pin, program sink capability descriptors and speaker allocation, program latency fields, and set the DTO clock for HDMI or DP transport.

State and persistence: no state is stored in this header. The declared functions mutate radeon device state and hardware endpoint/AFMT/DCCG registers in `dce6_afmt.c`. The use of forward declarations keeps compile-time coupling low while preserving the ABI between radeon display code and AFMT implementation.

Dependencies and integration points: the header is private to the radeon driver and guarded by `__DCE6_AFMT_H__`. It is included by `dce6_afmt.c` and by other DCE6/DCE8 display paths that need audio programming helpers. Callers must provide valid encoder/connector/mode/CRTC/device objects whose private radeon fields are initialized.

Risks: the prototypes expose low-level register helpers and assume callers know the correct block offset and transport-specific sequencing. There is no type-level distinction between HDMI and DP clocks or between SAD count and speaker-allocation byte count. Missing declarations for non-header-local helpers such as pin acquisition or audio enable may be intentional internal linkage through other headers, but API drift should be reviewed when changing audio setup paths.

Test signals: compile coverage catches prototype drift. Runtime tests should exercise HDMI and DP audio setup through the public prototypes on DCE6/DCE8 hardware, including modesets, hotplug, EDID audio changes, and DTO programming.
