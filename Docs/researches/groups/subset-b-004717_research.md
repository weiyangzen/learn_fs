# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath10k/debugfs_sta.c

Purpose: provides the ath10k per-station debugfs surface and the helper routines that feed per-station RX/TX observability. It exposes station-scoped controls for aggregation sessions, peer log triggering, peer power-save state, RX TID counters, and extended TX statistics, and it lets RX/firmware-stat paths accumulate data into `struct ath10k_sta` fields that are later dumped through debugfs.

Important APIs/types/functions: exported helpers are `ath10k_sta_update_rx_tid_stats_ampdu`, `ath10k_sta_update_rx_tid_stats`, `ath10k_sta_update_rx_duration`, and `ath10k_sta_add_debugfs`. Debugfs file handlers include `ath10k_dbg_sta_read/write_aggr_mode`, `ath10k_dbg_sta_write_addba`, `ath10k_dbg_sta_write_addba_resp`, `ath10k_dbg_sta_write_delba`, `ath10k_dbg_sta_read/write_peer_debug_trigger`, `ath10k_dbg_sta_read_peer_ps_state`, `ath10k_dbg_sta_read_tid_stats`, and `ath10k_dbg_sta_dump_tx_stats`. The main data objects are `struct ath10k_sta`, `struct ath10k_sta_tid_stats`, `struct ath10k_htt_data_stats`, firmware peer-stat structures, and mac80211 `struct ieee80211_sta`.

Control flow: RX statistics enter from `htt_rx.c`. Normal RX updates parse the first 802.11 header, reject non-data frames, derive QoS TID when present, honor `ar->sta_tid_stats_mask`, find the station under RCU, and update per-TID counters under `ar->data_lock`. A-MPDU updates look up the peer by firmware `peer_id` and bucket each MPDU range into subframe-count counters. RX duration updates are driven from firmware statistics, choosing extended or legacy peer lists based on `stats->extended` and accumulating matching peer durations into `arsta->rx_duration`. Debugfs writes parse user input, validate TIDs against the data/mgmt TID boundary, serialize with `ar->conf_mutex`, check `ATH10K_STATE_ON` where needed, and send WMI commands for ADDBA, ADDBA response, DELBA, aggregation-mode reset, or peer debug trigger. Debugfs reads allocate or format temporary buffers, take `conf_mutex` and/or `data_lock`, and copy snapshots to userspace.

State and persistence: all state is runtime-only. Per-station state lives in mac80211 station driver-private memory (`arsta->tid_stats`, `arsta->tx_stats`, `arsta->rx_duration`, `arsta->aggr_mode`, `arsta->peer_ps_state`) and disappears when the station is removed. The global `sta_tid_stats_mask` and `enable_extd_tx_stats` controls come from ath10k debugfs and gate collection/visibility. There is no on-disk persistence; debugfs files are recreated for each station via `ath10k_sta_add_debugfs`.

Dependencies/integration: integrates with mac80211 station debugfs through `sta_add_debugfs`, with HTT RX indication paths for TID and aggregation counters, with firmware-stat collection in `debug.c` for RX duration, with `htt_rx.c` per-peer TX-stat accumulation, and with WMI commands in `wmi-ops.h` for aggregation and peer debugging. Locking depends on mac80211 RCU station lookup, `ar->data_lock` for mutable station counters, and `ar->conf_mutex` for firmware-facing configuration.

Risks: statistics are best-effort snapshots and can be disabled by `sta_tid_stats_mask`, so zero counters may mean either no traffic or no collection. `tid > IEEE80211_NUM_TIDS` allows the non-QoS bucket at `IEEE80211_NUM_TIDS` but must stay aligned with `tid_stats` array sizing. Debugfs manual aggregation commands return `count` when the device is down or the station is not in manual aggregation mode, which can hide no-op writes from scripts. The TX stats read path warns and returns zero bytes if `arsta->tx_stats` was not allocated, and the fixed temporary buffer sizes rely on current counter cardinalities. Firmware command failures are logged but many write handlers still report a successful byte count after warning.

Test signals: exercise station add/remove with `sta_add_debugfs`, read every generated file, and write invalid/valid inputs for `aggr_mode`, `addba`, `addba_resp`, `delba`, and `peer_debug_trigger`. RX tests should drive QoS, non-QoS, non-data, error, chained-drop, filter-drop, and A-MPDU range paths while checking `dump_tid_stats` buckets. Integration tests should toggle `sta_tid_stats_mask` and `enable_extd_tx_stats`, verify `tx_stats` appears only when peer/extd stats are enabled, and run station teardown while debugfs reads are active to catch locking or lifetime assumptions.

# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath10k/hif.h

Purpose: defines the ath10k Host Interface abstraction used by core, BMI, HTC, HTT, debug, and bus-specific implementations. It is the narrow call table that lets the common driver send frames, exchange bootloader messages, read/write device diagnostics, map HTC services to transport pipes, power and suspend the device, and fetch target information without knowing whether the device is PCI, AHB, SDIO, USB, or high-latency.

Important APIs/types/functions: `enum ath_dbg_mode` selects firmware log routing through diagnostic or copy-engine paths. `struct ath10k_hif_sg_item` describes one scatter-gather transfer with a target transfer ID, optional completion context, debug virtual address, DMA address, and length. `struct ath10k_hif_ops` contains the bus callbacks: `tx_sg`, `diag_read`, optional `diag_write`, `exchange_bmi_msg`, `start`, `stop`, optional `start_post`, optional `get_htt_tx_complete`, `map_service_to_pipe`, `get_default_pipe`, optional `send_complete_check`, `get_free_queue_number`, optional MMIO-like `read32/write32`, `power_up`, `power_down`, optional `suspend/resume`, optional `fetch_cal_eeprom`, optional `get_target_info`, and optional `set_target_log_mode`. The rest of the file is inline wrappers such as `ath10k_hif_tx_sg`, `ath10k_hif_power_up`, and `ath10k_hif_map_service_to_pipe`.

Control flow: higher layers never call bus implementations directly. During boot, core powers the device with `ath10k_hif_power_up`, exchanges BMI messages through `ath10k_hif_exchange_bmi_msg`, optionally gets target info/calibration, starts regular transport with `ath10k_hif_start`, and runs optional `start_post`. HTC and HTT use `ath10k_hif_map_service_to_pipe` to bind service IDs to uplink/downlink pipes, then submit HTC-framed packets with `ath10k_hif_tx_sg`. Timeout recovery paths can call `ath10k_hif_send_complete_check` on polled pipes, and diagnostics/debug paths use `diag_read/write`, `read32/write32`, and firmware log mode callbacks when implemented.

State and persistence: this header owns no storage. It standardizes access to `ar->hif.ops` and expects bus drivers to keep their own runtime state under `struct ath10k`. Optional wrappers return `-EOPNOTSUPP`, `0`, or a sentinel read value for unsupported operations. No data persists beyond the device lifetime.

Dependencies/integration: depends on `core.h`, `bmi.h`, and `debug.h` for the shared `struct ath10k`, firmware mode, target-info, and warning interfaces. It is consumed heavily by `htc.c`, `htt.c`, `htt_tx.c`, firmware loading, debug/diagnostic code, and bus implementations. The transport contract includes sleepability for BMI exchanges, DMA validity for `paddr` in non-high-latency sends, and pipe IDs that must match firmware HTC service routing.

Risks: required callbacks are not checked before dereference, so bus registration must fully populate mandatory ops. Unsupported optional `read32` returns `0xdeaddead` after logging; callers must not treat it as a valid register value. `diag_write`, suspend/resume, target-info, EEPROM fetch, and log-mode support vary by bus and firmware, so portable code must handle `-EOPNOTSUPP`. `ath10k_hif_sg_item.transfer_context == NULL` suppresses TX completion callbacks; misuse can leak ownership expectations in HTC/HTT. Pipe mapping mistakes surface later as credit starvation, missing completions, or dropped HTT/WMI traffic.

Test signals: compile all ath10k bus variants and run probe/remove on supported transports. Unit-style fake HIF tests should verify mandatory callback dispatch, optional fallback returns, and `send_complete_check` no-op behavior. Integration tests should cover firmware download, HTC ready wait with forced completion polling, service-to-pipe mapping for WMI/HTT/pktlog, suspend/resume unsupported paths, diagnostic read/write failure handling, and DMA completion behavior for scatter-gather sends with and without transfer contexts.

# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath10k/htc.c

Purpose: implements the ath10k Host-Target Control protocol. HTC frames higher-level services such as WMI, HTT data, test streams, NMI, and pktlog over HIF pipes; manages service connection handshakes; enforces target TX credit accounting; processes target trailers for credits and lookaheads; dispatches RX/TX completions to endpoint callbacks; and supports high-latency TX bundling.

Important APIs/types/functions: exported entry points are `ath10k_htc_init`, `ath10k_htc_wait_target`, `ath10k_htc_start`, `ath10k_htc_connect_service`, `ath10k_htc_send`, `ath10k_htc_send_hl`, `ath10k_htc_stop_hl`, `ath10k_htc_setup_tx_req`, `ath10k_htc_change_tx_credit_flow`, `ath10k_htc_alloc_skb`, `ath10k_htc_tx_completion_handler`, `ath10k_htc_rx_completion_handler`, `ath10k_htc_notify_tx_completion`, and `ath10k_htc_process_trailer`. Internal helpers build aligned control skbs, prepare HTC headers, consume/release endpoint credits, process credit/lookahead records, send bundled HL packets, drain bundle completion work, connect pktlog, and reset endpoint state.

Control flow: initialization resets endpoint state, initializes `tx_lock`, records `htc->ar`, and creates a pseudo connection for control endpoint 0. After HIF start, `ath10k_htc_wait_target` waits for a READY control message, polls HIF completion as a timeout workaround, validates credit count/size, records extended bundle/alternate-credit fields, and initializes bundle work. `ath10k_htc_connect_service` either sets up the pseudo control endpoint or sends a CONNECT_SERVICE request over EP0, waits for `ctl_resp`, validates the response, records endpoint callbacks and credit settings, maps the HTC service to HIF pipes, and disables credit flow for non-WMI-control services. `ath10k_htc_start` sends SETUP_COMPLETE, enables SDIO RX bundling flags when needed, and optionally connects pktlog.

TX control flow: `ath10k_htc_send` rejects wedged devices and invalid endpoints, pushes an HTC header, consumes credits, fills endpoint ID, payload length, flags, and sequence number, DMA-maps non-HL skbs, and sends one SG item through `ath10k_hif_tx_sg`. Error paths unmap, restore credits, and pull the header. HIF completions call `ath10k_htc_tx_completion_handler`, which uses `ATH10K_SKB_CB(skb)->eid` to find the endpoint and invokes `ath10k_htc_notify_tx_completion`; that restores skb data, handles a hardware-specific delayed unmap workaround, drops bundle carrier skbs, and dispatches endpoint `ep_tx_complete`.

RX control flow: HIF RX completions enter `ath10k_htc_rx_completion_handler`. It pulls the HTC header, validates endpoint connectivity and maximum length, validates/trims optional trailers, processes credit and lookahead records, drops zero-payload trailer-only frames, and hands payload skbs to endpoint `ep_rx_complete`. EP0 messages are handled by `ath10k_htc_control_rx_complete`, which copies READY and CONNECT_SERVICE responses into `control_resp_buffer` and completes `ctl_resp`, or forwards suspend-complete events to `htc_ops.target_send_suspend_complete`.

State and persistence: state is volatile in `struct ath10k_htc` and `struct ath10k_htc_ep`: endpoints, callbacks, service IDs, pipe IDs, sequence numbers, credits, credit sizes, bundle queues, completion buffer/length, `ctl_resp`, and target credit/bundle parameters. `tx_lock` protects endpoint credit and sequence state. Work items `bundle_tx_work` and `tx_complete_work` process HL bundle queues. There is no persistent storage.

Dependencies/integration: depends on HIF for pipe mapping, SG transmit, DMA completion polling, and bus type; on skbuff ownership conventions and `ATH10K_SKB_CB`; on workqueues owned by `struct ath10k`; on HTT/WMI endpoint callbacks supplied by callers; and on target firmware protocol messages defined in `htc.h`. It exports key functions for bus modules and upper ath10k layers.

Risks: malformed target trailers can perturb credit accounting or lookahead state; the trailer length checks and some warning strings are easy to misread during debugging. Credit accounting must be balanced across direct sends, bundle sends, HIF errors, and completions, or WMI/HTT can starve. `ctl_resp` is a single shared response buffer, so unsolicited EP0 messages while a request is pending are treated as fatal protocol confusion. Bundling copies skb bytes into a carrier skb and later completes original skbs from `tx_complete_head`; ownership bugs here can double-complete or leak skbs. Required endpoint callbacks are assumed after service setup, and non-HL DMA map/unmap timing includes a target-specific delay workaround on some hardware.

Test signals: test boot sequencing through READY timeout, forced HIF completion polling, invalid READY lengths, zero credit size, and extended READY bundle parsing. Service tests should cover successful/failed WMI/HTT/pktlog connections, unsupported service-to-pipe mapping, duplicate endpoint setup, and credit-flow disablement. TX/RX tests should inject HIF errors, DMA mapping failures, wedged state, invalid EIDs, unconnected endpoints, oversized frames, trailer-only frames, malformed trailer records, credit reports, lookahead bundles, and HL bundle queue drain/stop behavior.

# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath10k/htc.h

Purpose: declares the ath10k HTC wire protocol and host-side HTC data structures. It documents the HTC frame layout, endpoint/service namespace, control messages, trailer records, credit reports, bundle count encoding, endpoint callback contract, and the public HTC API implemented by `htc.c`.

Important APIs/types/functions: protocol definitions include `struct ath10k_htc_hdr`, `enum ath10k_htc_tx_flags`, `enum ath10k_htc_rx_flags`, `ath10k_htc_get_bundle_count`, HTC message IDs, connection flags/statuses, READY/READY_EXT, CONNECT_SERVICE request/response, SETUP_COMPLETE_EXT, trailer record IDs, `struct ath10k_htc_credit_report`, `struct ath10k_htc_lookahead_report`, and `struct ath10k_htc_record`. Host definitions include service groups/IDs (`ATH10K_HTC_SVC_ID_WMI_CONTROL`, `ATH10K_HTC_SVC_ID_HTT_DATA_MSG`, `ATH10K_HTC_SVC_ID_HTT_LOG_MSG`, and others), endpoint IDs EP0-EP8, callback tables `struct ath10k_htc_ops` and `struct ath10k_htc_ep_ops`, connection request/response structs, `struct ath10k_htc_ep`, and `struct ath10k_htc`.

Control flow expressed by the header: HTC TX frames are `<htc_hdr><payload>`; RX frames are `<htc_hdr><payload><trailer>`, with the header length covering payload plus trailer and `trailer_len` describing the suffix. Trailer records are ID-length-value blocks that can carry credits and lookahead data. EP0 is reserved for HTC control; services are connected to target-assigned endpoints before higher layers send traffic. Endpoint callbacks receive payload completions after HTC has stripped or restored headers. Bundle counts are encoded partly in high flag bits and, for counts above 16, in extra bits shifted by `ATH10K_HTC_BUNDLE_EXTRA_SHIFT`.

State and persistence: no runtime state is allocated by the header itself, but it defines all HTC runtime state held in `struct ath10k_htc`. Persistent behavior is limited to in-memory endpoint arrays, endpoint credit counts, target credit size, alternate data credit size, maximum bundled RX messages, control response buffer, and completion object. All fields are reset during driver initialization or device teardown; no state is persisted across probe cycles.

Dependencies/integration: includes Linux kernel list/bug/skbuff/timer/bitfield helpers and is included by `htt.h`, `htc.c`, bus code, and other ath10k modules. It must stay byte-for-byte compatible with firmware expectations, using packed/aligned structs and little-endian integer types for wire fields. It also encodes the service IDs that HIF bus implementations map to uplink/downlink transport pipes.

Risks: the header contains firmware ABI, so field reordering, alignment changes, or enum value changes can break target communication. The message ID enum name has a duplicated `ath10k` spelling (`ath10k_ath10k_htc_msg_id` and record/header equivalents), which is harmless but can confuse search and generated documentation. The endpoint count is fixed at nine entries; service connection code must validate all target-assigned EIDs. Bundle count decoding depends on flag bit layout shared with RX flags. `struct ath10k_htc_svc_conn_resp` has `buffer_len` and `actual_len` fields that are not central in the current implementation, so new code should not infer they are populated unless it verifies call sites.

Test signals: compile-time checks should cover packed struct sizes and offsets if ABI churn is suspected. Runtime tests should validate READY, CONNECT_SERVICE, SETUP_COMPLETE_EXT, trailer credit reports, lookahead records, bundle count decoding for max messages above and below 16, and unsupported service IDs. Cross-bus tests should confirm each HIF backend maps the service IDs defined here consistently and can route WMI, HTT data, and pktlog endpoints.

# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath10k/htt.c

Purpose: implements HTT protocol initialization, firmware-version negotiation, HTC service connection, firmware-specific target-to-host message type mapping, and chip-specific RX descriptor operation tables. It is the common setup bridge between HTC transport and the larger HTT TX/RX implementations in `htt_tx.c` and `htt_rx.c`.

Important APIs/types/functions: exported data tables are `qca988x_rx_desc_ops`, `qca99x0_rx_desc_ops`, and `wcn3990_rx_desc_ops`. Exported functions are `ath10k_htt_connect`, `ath10k_htt_init`, and `ath10k_htt_setup`. Static target-to-host translation arrays map firmware-specific enums (`MAIN`, `10.x`, `TLV`, `10.4`) to common `enum htt_t2h_msg_type`. Helper functions for WCN3990 convert raw RX descriptor buffers to the abstract base descriptor and return pointers/offsets for attention, fragment info, MPDU/MSDU start/end, PPDU start/end, header status, and payload. QCA99x0 helpers provide L3 pad and MSDU limit error extraction from v1 descriptors.

Control flow: `ath10k_htt_init` records `htt->ar`, sets the TX prefetch length used by low-latency firmware classification, chooses the T2H message translation table according to `ar->running_fw->fw_file.htt_op_version`, and installs TX/RX operation tables through `ath10k_htt_set_tx_ops` and `ath10k_htt_set_rx_ops`. `ath10k_htt_connect` connects the HTT data service over HTC with HTT RX/TX completion callbacks, records the assigned endpoint, enables HL bundle support when appropriate, queries whether HIF suppresses HTT TX completions, and adjusts HTC credit-flow behavior. `ath10k_htt_setup` initializes the target-version completion, sends an HTT version request, waits up to three seconds for `target_version_received`, verifies major version 2 or 3, configures fragment descriptor banks, configures RX rings, and sends aggregation limits.

State and persistence: all state is runtime-only in `struct ath10k_htt`. This file initializes firmware message mapping (`t2h_msg_types`, max), version fields/completion, prefetch length, endpoint ID, operation tables, and setup-time target configuration. The RX descriptor ops are const tables selected indirectly through hardware parameters. No persistent storage is used.

Dependencies/integration: depends on `htt.h` protocol definitions, `core.h` hardware/firmware state, `debug.h`, and `hif.h`. It integrates with HTC by connecting `ATH10K_HTC_SVC_ID_HTT_DATA_MSG` and using `ath10k_htt_htc_tx_complete`, `ath10k_htt_htc_t2h_msg_handler`, and `ath10k_htt_op_ep_tx_credits` callbacks. It depends on `htt_tx.c` for H2T version/ring/fragment/aggr messages and TX ops, and on `htt_rx.c` for target-version completion and RX ops. RX descriptor ops depend on `rx_desc.h` layout definitions and `ar->hw_params.rx_desc_ops`.

Risks: the firmware operation version controls every T2H decode path; a wrong table makes valid target messages appear as wrong common types. `ATH10K_FW_HTT_OP_VERSION_UNSET/MAX` intentionally warns and fails, so firmware metadata must be populated before HTT init. `ath10k_htt_setup` assumes the target version response is delivered by the RX handler; missing HTC routing or blocked interrupts produce setup timeouts. Major versions outside 2 and 3 are rejected even if other parts of the firmware load. RX descriptor offsets are ABI-sensitive and chip-specific; selecting the wrong ops table can corrupt RX parsing or crash firmware, especially because legacy v1 layout is intentionally retained for stability on older families.

Test signals: boot tests should cover each advertised `htt_op_version` and verify T2H message dispatch for version, RX, TX completion, peer map/unmap, stats, pktlog, fetch, and peer stats messages. Setup tests should inject version timeouts, unsupported major versions, failures from frag descriptor bank config, RX ring config, and aggregation config. Hardware or emulated RX descriptor tests should validate v1/v2 offsets, QCA99x0 L3 pad/MSDU limit extraction, WCN3990 pointer accessors, and `ath10k_htt_rx_msdu_size` calculations against selected descriptor sizes.

# sources/distributed-fs/ceph-client/drivers/net/wireless/ath/ath10k/htt.h

Purpose: defines the ath10k HTT host-target protocol ABI and host-side HTT state. It covers host-to-target commands, target-to-host indications, TX descriptors, RX ring setup, debug statistics, security and block-ack events, TX completion formats, high-latency fetch/push scheduling, RX descriptor layouts, DMA-backed rings/banks, operation tables, and public functions shared across `htt.c`, `htt_tx.c`, `htt_rx.c`, debugfs, and mac80211 integration.

Important APIs/types/functions: command-side definitions include `enum htt_h2t_msg_type`, `struct htt_cmd`, `struct htt_data_tx_desc`/`_64`, fragment descriptors, checksum/offload flags, RX ring setup structs for 32/64-bit DMA, stats requests, OOB sync, aggregation config, management TX descriptors, fragment bank config, queue-state config, TX fetch responses, and aggregation defaults. Response-side definitions include firmware-specific T2H enums and common `enum htt_t2h_msg_type`, version responses, RX indications, RX flush/peer map/unmap/security/ADDBA/DELBA events, TX completions and appended retry/timestamp/RSSI data, management TX completions, rate-control updates, RX fragment/offload/in-order indications, pktlog/test messages, channel changes, peer TX stats, and stats status records.

Host state: `struct ath10k_htt` is the central runtime object. It stores the HTC endpoint, RX indication queue, target version completion, aggregation limits, T2H translation table, RX ring state (`netbufs_ring`, in-order hash table, DMA paddr ring, alloc index shadow register, fill counters, retry timer, lock), TX pending IDR and counters, TX done FIFO, confused flag, completion queues, RX status template, DMA fragment descriptor bank, DMA TX buffer bank, optional host TX queue state shared with firmware, memory-allocation flags, TX/RX operation tables, completion suppression, and HL bundle queues. `struct ath10k_htt_tx_ops` and `struct ath10k_htt_rx_ops` abstract target-family and bus-mode differences for ring config, fragment-bank config, TX, TX buffer allocation, aggregation config, flush, paddr ring access, and RX fragment processing.

Control flow encoded by the header: HTT setup sends a version request, fragment descriptor bank config, RX ring config, and aggregation config over HTC. TX paths allocate an MSDU ID, fill a data or management TX descriptor, reference fragment/ext descriptors, and later consume target TX completion indications. RX paths keep a DMA ring of buffers, allow firmware to fill buffers and report them through RX indications, optionally use in-order physical-address indications for full RX reorder, process peer map/unmap/security events, and pass decoded frames toward mac80211. High-latency/push-pull firmware can request host queues through TX fetch indications and host queue-state shared memory.

State and persistence: all state is in kernel memory and DMA allocations for the lifetime of the device. Rings, IDR entries, FIFOs, timers, wait queues, hash tables, and shared queue-state memory are recreated on start and freed on stop/destroy. Firmware-visible DMA state includes RX paddr rings, alloc-index shadow memory, fragment descriptor banks, TX buffers, and optional `htt_q_state`. There is no on-disk persistence.

Dependencies/integration: depends on Linux DMA pools, hash tables, kfifo, interrupts, mac80211, `htc.h`, `hw.h`, and `rx_desc.h`. It is consumed by `htt.c`, `htt_tx.c`, `htt_rx.c`, `txrx`, debugfs, and mac80211 TXQ code. The protocol structs must match firmware ABI exactly with packed little-endian fields. Hardware parameters choose RX descriptor ops and TX/RX ops, while HTC provides the transport endpoint.

Risks: this header is dense firmware ABI; changes to enum values, packed struct layout, endianness, flexible-array placement, or descriptor offsets can silently break target communication. Many messages carry variable-length trailing arrays, so every parser must bound-check `num_msdus`, `num_records`, `fw_rx_desc_bytes`, `msdu_count`, `num_resp_ids`, and stats status series. Ring sizes and fill levels must stay compatible with firmware and DMA alignment; refill failure can starve RX, while stale hash/IDR entries can mis-associate buffers or completions. The RX descriptor abstraction defaults to v1 layout for compatibility, which helps older chips but makes wrong `rx_desc_ops` selection hard to diagnose. TX queue-state comments note firmware ignores some configured fields and question map sizing, so scheduler features require hardware/firmware validation.

Test signals: compile tests should cover 32-bit and 64-bit DMA builds, HL and LL modes, and all firmware operation versions. Runtime tests should cover HTT version negotiation, RX ring refill under pressure, RX in-order mode, peer map/unmap churn, security indication handling, ADDBA/DELBA, TX completion parsing with appended retries/timestamps/RSSI/PPDU duration, management TX status, TX fetch response/confirm, TX mode switch, peer TX stats, pktlog/test messages, and error paths for malformed variable-length indications. ABI-sensitive tests should assert selected descriptor sizes/offsets for QCA988x/QCA99x0/WCN3990 and verify `HTT_RX_BUF_SIZE - rx_desc_size` remains large enough for expected MSDUs.
