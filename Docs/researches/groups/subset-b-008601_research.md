# Research: sources/storage-engines/rocksdb/db/db_kv_checksum_test.cc

- **Purpose:** Regression and fault-injection coverage for key/value checksum protection across write batches, WAL handoff, memtable insertion, reads, iterators, column families, and flush. The file verifies that protected write batches and `memtable_protection_bytes_per_key` detect byte-level corruption and return `Status::Corruption` before corrupted state is accepted as durable data.
- **Important APIs/types/functions:** Defines `WriteBatchOpType` for `Put`, `Delete`, `SingleDelete`, `Merge`, `PutEntity`, and `DeleteRange`; `WriteMode` for protected-batch and write-option protection paths; `GetWriteBatch()` for constructing one-operation batches; `DbKvChecksumTestBase::GetCFHandleToUse()` for default-CF fallback on `PutEntity`; `DbKvChecksumTest::ExecuteWrite()` and `CorruptNextByteCallBack()` for parameterized corruption loops; `DbKvChecksumTestMergedBatch` and `CorruptWriteBatch()` for write-group merge coverage; `DbKVChecksumWALToWriteBatchTest`; and `DbMemtableKVChecksumTest` for read-side memtable checksum validation. It relies on `WriteBatch::VerifyChecksum()`, `WriteBatchInternal::Append()`, `WriteBatchInternal::Contents()`, `WriteOptions::protection_bytes_per_key`, `Options::memtable_protection_bytes_per_key`, `DBImpl` test hooks, and `XXH3_64bits`.
- **Control flow:** Parameterized tests iterate through operation types, corruption addends, write modes, and protection-byte sizes. WAL tests set `SyncPoint` callbacks at `DBImpl::WriteToWAL:log_entry`, skip the unprotected sequence-number prefix, reopen after each corruption-induced read-only transition, and assert WAL size and background error state do not advance. Memtable-add tests corrupt the encoded memtable entry through `MemTable::Add:Encoded` and expect the write to fail. Merged-batch tests force a two-writer write group via `WriteThread::JoinBatchGroup` sync points, corrupt either leader or follower pre-merged batch bytes, and verify both writers see corruption. Read-side tests first write valid entries, then corrupt saved memtable bytes through `Memtable::SaveValue:Found:entry` or `MemTable::Add:BeforeReturn:Encoded`, then exercise `Get`, `MultiGet`, iterators, and flush.
- **State and persistence behavior:** The tests repeatedly destroy, reopen, and create column families because checksum failures move the DB into read-only/background-error state. WAL state is observed through `TEST_wals_total_size()` and `TEST_GetBGError()`. Column-family tests write through non-default handles named `pikachu` or `ramen`. Memtable corruption tests deliberately avoid corrupting selected length bytes to prevent invalid memory access while still checking checksum detection.
- **Dependencies:** Includes `db/blob/blob_index.h`, `db/db_test_util.h`, and `rocksdb/rocksdb_namespace.h`. It depends on RocksDB's gtest harness, `SyncPoint`, `DBTestBase`, write-thread internals, merge operators, wide-column `PutEntity`, XXH3 checksum implementation, and DBImpl test-only inspection methods.
- **Integration points:** Covers the write path between public `DB::Write`, `WriteBatch`, write group leader/follower merging, WAL serialization, recovery log replay, memtable add/save, point reads, multi-get, iterator creation, and flush. It also validates that column-family-aware encodings and default-column-family fallbacks are protected consistently.
- **Risks:** The tests are tightly coupled to internal sync-point names and encoded entry layouts, including hard-coded sequence-number and value-length offsets. Corrupting too early or too broadly can produce crashes instead of corruption statuses. The merged-batch tests use busy waiting and thread coordination, so scheduler timing changes can affect reliability. One-byte checksum cases are explicitly skipped as flaky.
- **Test signals:** Success is indicated by `ASSERT_TRUE(status.IsCorruption())`, unchanged WAL sizes, corruption background errors, successful `VerifyChecksum()` in non-corruption cases, expected XXH3 handoff checksum during recovery, iterator invalidity with corruption status, and `Flush()` returning corruption after reading corrupted protected memtable data.

# Research: sources/storage-engines/rocksdb/db/db_log_iter_test.cc

- **Purpose:** Tests RocksDB transaction log iteration through `GetUpdatesSince()` across normal WAL replay, column families, archive movement, restart, corruption gaps, batched operations, and `WriteBatch::PutLogData` blobs.
- **Important APIs/types/functions:** Defines `DBTestXactLogIterator`, `OpenTransactionLogIter(SequenceNumber)`, helper `ReadRecords()` returning the last seen sequence and record count, and `ExpectRecords()`. Test cases cover `TransactionLogIterator`, `TransactionLogIteratorRace`, `TransactionLogIteratorCheckWhenArchive`, `TransactionLogIteratorStallAtLastRecord`, `TransactionLogIteratorCheckAfterRestart`, `TransactionLogIteratorCorruptedLog`, `TransactionLogIteratorBatchOperations`, and `TransactionLogIteratorBlobs`. Core APIs are `DBImpl::GetUpdatesSince`, `TransactionLogIterator::Valid/Next/GetBatch/status`, `BatchResult`, `WriteBatch::Handler`, `GetSortedWalFiles`, `FlushWAL`, `TEST_SwitchWAL`, and WAL truncation helpers.
- **Control flow:** Basic tests open a DB with log-iterator options, write records across default and non-default column families, reopen, sleep to cross WAL timestamps, and verify the iterator sees monotonically increasing sequences and expected record counts. Race tests, enabled only outside `NDEBUG`, use sync-point dependencies to interleave WAL listing with purge/archive movement and ensure no record is missed when logs are moved mid-scan. Archive tests invoke a transaction-log iterator from inside `WalManager::PurgeObsoleteFiles`. Corruption tests disable file deletion, truncate the first WAL, re-enable deletion, append a later record, and verify iteration from the beginning stops with non-OK status while iteration after the gap can find the later record.
- **State and persistence behavior:** Durable state is primarily WAL files and archived WAL metadata. The test repeatedly flushes memtables to force log switching and archival, reopens the DB to validate persisted WAL discovery, and directly truncates a WAL file to simulate a physical log gap. Sequence numbers are used as the contract for ordering and resume points.
- **Dependencies:** Includes `db/db_test_util.h`, `env/mock_env.h`, `port/stack_trace.h`, and `util/atomic.h`. It relies on `OptionsForLogIterTest()`, `ChangeCompactOptions()`, DBTestBase column-family helpers, `SyncPoint`, mock environment sleeping, and test file truncation utilities.
- **Integration points:** Exercises the public backup/replication-facing transaction log iterator API against `WalManager`, WAL archive purge logic, flush/switch-WAL behavior, `WriteBatch` decoding, and column-family-aware write batches. The blob test validates `PutLogData()` items remain in the iterator's batch stream and are delivered to a `WriteBatch::Handler` in order.
- **Risks:** The race coverage is debug-build-only because sync points are compiled out in release builds. Record counts depend on WAL retention and archive behavior from `OptionsForLogIterTest()`. The corrupted-log case must preserve enough later WAL data to test seeking past the gap, so file deletion is explicitly disabled during truncation.
- **Test signals:** Expected signals are valid iterators from requested sequence numbers, strictly increasing `BatchResult::sequence`, exact record counts, OK iterator status for normal paths, non-OK status at a truncated WAL gap, successful resume after the gap, and exact handler output for ordered put/log-data/delete batch contents.

# Research: sources/storage-engines/rocksdb/db/db_logical_block_size_cache_test.cc

- **Purpose:** Linux-only tests for `LogicalBlockSizeCache` reference counting when DB and column-family paths are registered and unregistered through RocksDB open, close, read-only open, handle destruction, and multi-DB sharing.
- **Important APIs/types/functions:** Defines `EnvWithCustomLogicalBlockSizeCache`, an `EnvWrapper` overriding `RegisterDbPaths()` to call `LogicalBlockSizeCache::RefAndCacheLogicalBlockSize()` and `UnregisterDbPaths()` to call `UnrefAndTryRemoveCachedLogicalBlockSize()`. `DBLogicalBlockSizeCacheTest` owns path strings, a cache, and a custom env. Tests cover `OpenClose`, `OpenDelete`, `CreateColumnFamily`, `CreateColumnFamilies`, `OpenWithColumnFamilies`, `DestroyColumnFamilyHandle`, `MultiDBWithDifferentPaths`, and `MultiDBWithSamePaths`.
- **Control flow:** The fixture injects deterministic logical-block-size behavior: directory block size lookups return `1024`, while the fd callback returns the fd value. Each test opens DBs with `options.env = env_.get()` and optionally sets `Options::db_paths` or `ColumnFamilyOptions::cf_paths`. It then asserts cache size, presence, and reference counts after open, column-family creation, drop, handle destruction, DB close/reset, and destroy.
- **State and persistence behavior:** Persistent DB files are created under per-thread test paths, but the main state under test is the in-memory cache keyed by DB, data, and column-family paths. A dropped column family does not immediately unregister paths because existing handles or background references can still need the cached block size. Destroying handles decrements path references, while closing/resetting the DB releases remaining DB and background references.
- **Dependencies:** Compiled only under `OS_LINUX`; includes `env/io_posix.h`, `rocksdb/db.h`, `rocksdb/env.h`, and `test_util/testharness.h`. It depends on the POSIX logical block size cache implementation, `DB::Open`, `DB::OpenForReadOnly`, `DestroyDB`, column-family APIs, and env path registration hooks.
- **Integration points:** Validates the integration between DB open/close lifecycle, column-family path registration, env-level path registration, read-only open, and logical block size lookup caching used by file IO setup. Multi-DB tests check that one shared env can safely share or separate cached path entries depending on whether DBs use common `db_paths` and `cf_paths`.
- **Risks:** Because it is Linux-gated, cross-platform builds do not exercise this behavior. The tests assume exact cache ref-count semantics; changes in background reference lifetime or handle ownership can require updates. Test-specific block-size callbacks do not validate real filesystem block size discovery.
- **Test signals:** Assertions check cache `Size()`, `Contains(path)`, and `GetRefCount(path)` after every lifecycle transition. Correct behavior means paths are cached once per unique path, ref counts increase for shared DB/CF usage, drops do not prematurely remove entries, and all entries disappear after all DB and CF references are closed or destroyed.

# Research: sources/storage-engines/rocksdb/db/db_memtable_test.cc

- **Purpose:** Tests memtable insertion, duplicate-sequence handling, concurrent merge writes, insertion hints, column-family id propagation to memtable factories, memtable integrity checks, and concurrent writes through vector memtable representation.
- **Important APIs/types/functions:** Defines `DBMemTableTest`, `MockMemTableRep`, `MockMemTableRepFactory`, and `TestPrefixExtractor`. `MockMemTableRep` wraps a real `MemTableRep` and records `InsertWithHint()` calls and hint values. `MockMemTableRepFactory` captures the last column-family id passed to `CreateMemTableRep()`. Test cases cover `DuplicateSeq`, `ConcurrentMergeWrite`, `InsertWithHint`, `ColumnFamilyId`, parameterized seek integrity checks, general skiplist integrity checks, and `VectorConcurrentInsert`.
- **Control flow:** `DuplicateSeq` constructs `MemTable` directly and validates that adding the same internal key sequence with different value types returns `TryAgain`, while incrementing sequence permits a new entry. It repeats under prefix hint insertion and concurrent memtable write post-processing. `ConcurrentMergeWrite` directly adds many merge operands from two threads into one memtable with a UInt64 add merge operator, then reads the summed result through `MemTable::Get()`. `InsertWithHint` opens a DB with a mock factory and prefix extractor, then checks that keys sharing prefixes reuse hints and keys outside the transform domain do not use hint insertion.
- **State and persistence behavior:** Some tests instantiate `MemTable` directly with `ImmutableOptions`, `MutableCFOptions`, and `WriteBufferManager`, so state remains in memory. DB-level tests reopen real RocksDB instances, flush column families, and verify persisted values where needed. Integrity tests capture raw pointers to encoded skiplist keys using sync points, mutate bytes in place, and then restore them after verification.
- **Dependencies:** Includes `db/db_test_util.h`, `db/memtable.h`, `db/range_del_aggregator.h`, `rocksdb/memtablerep.h`, and `rocksdb/slice_transform.h`. It relies on skiplist and vector memtable factories, `SliceTransform`, `SyncPoint`, DBTestBase helpers, internal key comparators, merge context, and write-buffer management.
- **Integration points:** Covers the boundary between public writes and memtable representation, direct `MemTable::Add`/`Get`, prefix-hint optimization, concurrent memtable post-processing, column-family metadata propagation into custom factories, paranoid memory checks in inline skiplist iteration, and vector representation behavior under multi-threaded write batches.
- **Risks:** Several tests mutate raw in-memory memtable bytes, so they are tightly coupled to encoded-key layout and sync-point names. Integrity-check outcomes depend on `allow_data_in_errors`, `paranoid_memory_checks`, and `memtable_verify_per_key_checksum_on_seek`; disabling these options changes expected statuses from corruption to not-found or iterator invalidity. Concurrent tests rely on deterministic final aggregation or disjoint key ranges to avoid order sensitivity.
- **Test signals:** Expected signals include `Status::TryAgain` for duplicate sequence inserts, exact memtable counters, correct UInt64 merge sum, hint reuse counts and pointer equality, captured column-family ids after flush, corruption statuses and optional hex key data in error strings, sorted iterator output over 1000 vector-rep inserts, and OK flushes after concurrent multi-CF writes.

# Research: sources/storage-engines/rocksdb/db/db_merge_operand_test.cc

- **Purpose:** Validates `DB::GetMergeOperands()` behavior, lifetime pinning, operand ordering, result-size optimizations, short-circuit callbacks, base value/deletion handling, immutable memtables, read-only DBs, and blob-file-backed values.
- **Important APIs/types/functions:** Defines a local `LimitedStringAppendMergeOp` derived from `StringAppendTESTOperator` whose `ShouldMerge()` forces partial merge when operand count reaches a limit. `DBMergeOperandTest` derives from `DBTestBase`. Tests use `GetMergeOperandsOptions::expected_max_number_of_operands`, `continue_cb`, arrays of `PinnableSlice`, `Merge`, `Put`, `Delete`, `Flush`, `CompactRange`, `MoveFilesToLevel`, `ReadOnlyReopen`, `TEST_SwitchMemtable`, and blob options.
- **Control flow:** Basic coverage writes keys with combinations of puts, deletes, merges, memtable-only operands, L0 files, different levels, immutable memtables, and read-only reopen. It calls `GetMergeOperands()` and verifies operand counts and order from oldest/base to newest operands, or a merged base string when the merge operator's `ShouldMerge()` compacts operands. Capacity tests reduce `expected_max_number_of_operands` and require `Status::Incomplete`. Short-circuit tests install a continuation callback that stops after a fixed number of operands in mutable memtable, SST, or immutable memtable scans.
- **State and persistence behavior:** The test deliberately moves operands between mutable memtable, immutable memtable, flushed SSTs, compacted levels, and blob files. Lifetime regression tests keep returned `PinnableSlice` values alive after cache eviction or after a memtable flush/SuperVersion change. `GetMergeOperandsLargeResultOptimization` expects all returned slices to be pinned and then flushes to challenge resource ownership.
- **Dependencies:** Includes DB test utilities, `rocksdb/merge_operator.h`, `rocksdb/perf_context.h`, debug utilities, block builder, `SyncPoint`, `FaultInjectionEnv`, and multiple merge-operator implementations. Blob coverage depends on `enable_blob_files` with `min_blob_size = 0`.
- **Integration points:** Exercises point lookup internals that gather merge operands from memtables, immutable memtables, table cache, blob values, and multiple LSM levels without performing a full merge unless a base value or merge operator policy requires it. It covers API behavior for writable and read-only DB handles.
- **Risks:** Operand ordering and partial-merge behavior are sensitive to merge-operator semantics and LSM layout; tests use `Flush`, `CompactRange`, and `MoveFilesToLevel` to make layout predictable. Cache and memtable lifetime bugs can manifest as use-after-free, so the tests rely on pinning semantics rather than only value equality. Blob-file paths add configuration-specific risk.
- **Test signals:** Signals are OK or `Incomplete` statuses as appropriate, exact `number_of_operands`, exact operand strings and ordering, `PinnableSlice::IsPinned()` for large results, callback invocation counts, stable values after flush/SuperVersion changes, and successful read-only `GetMergeOperands()`.

Pinning tests build many operands across files and levels, then verify reads after table cache eviction or block cache shrinking. Tailing iterator tests run writer and reader threads while flushing and compacting.
- **State and persistence behavior:** The suite creates durable SSTs through repeated flushes, manually moves files to levels, compacts bottommost levels, retains snapshots, evicts table cache entries, and varies block cache use. `TailingIteratorMemtableUnrefedBySomeoneElse` pins an old SuperVersion with a separate iterator, flushes during merge-value collection, then releases the old SuperVersion mid-seek to ensure `ForwardIterator` pins operands safely.

- **Risks:** Some tests are heavy and timing-sensitive: large write counts, background flush/compaction, cache eviction during merge, and tailing iterator polling can be resource dependent. Merge semantics are operator-specific, so replacing operator behavior changes expected values. Snapshot checker tests intentionally diverge from normal sequence visibility and depend on internal `ReadCallback` behavior.
- **Test signals:** Expected signals include exact merged values, retained unmerged internal versions after write-time merge errors, corruption status with `kMergeOperatorFailed` subcode for must-merge failures, `IsOkMergeOperandThresholdExceeded()` flags while still returning OK values, exact files-per-level layout, successful map verification under cache eviction, no tailing iterator errors, correct snapshot-filtered values across flush/compaction, and expected key-version types after max-successive-merge conversion to `Put` or `PutEntity`.

# Research: sources/storage-engines/rocksdb/db/db_open_with_config_test.cc

- **Purpose:** Opens and reopens RocksDB with a broad, production-like configuration to validate that many option families can coexist: FIFO compaction, blob files, compression choices, memtable and block protection, write-buffer sizing, level settings, wide-column writes, and persisted data reads.
- **Important APIs/types/functions:** Defines `DBOpenWithConfigTest`, helper `CompressionSupported()`, `GetPrimaryCompressionForTest()`, and `GetBottommostCompressionForTest()`. Test cases are `OpenWithComprehensiveConfig` and `ReopenWithSameConfig`. It uses `Options`, `BlockBasedTableOptions`, `CompressionOptions`, `CompactionOptionsFIFO`, `CompactionOptionsUniversal`, `Temperature`, `VerifyOutputFlags`, `WideColumns`, `PutEntity`, `Get`, `Flush`, `DestroyAndReopen`, and `Reopen`.
- **Control flow:** Compression helpers choose LZ4 when linked, otherwise ZSTD, otherwise no compression; bottommost compression prefers ZSTD if available. The comprehensive test starts from default options, sets `max_open_files = -1`, fills many mutable and immutable option fields, configures block-based table factory, opens the DB, writes wide-column entities and a plain key, flushes, reads default-column values back, and compares a subset of retrieved options to expected values. The reopen test writes data, closes, reopens with the same configuration, and verifies data persists.
- **State and persistence behavior:** The DB is destroyed/reopened for a clean start, writes keys and wide-column entities, flushes them to SST/blob-backed storage depending on options, closes and reopens, and verifies values remain readable. Options are not persisted by this file as the primary test target; instead, `db_->GetOptions()` is used to verify effective in-memory options after open.
- **Dependencies:** Includes `db/db_test_util.h`, `port/stack_trace.h`, `rocksdb/convenience.h`, and `rocksdb/table.h`. The test depends on compiled-in compression support detection and calls `RegisterCustomObjects(argc, argv)` in `main()` so custom object factories can be registered for option parsing/object lookup in the broader RocksDB test harness.
- **Integration points:** Exercises option sanitization/open validation for compression, blob, FIFO compaction, memtable checksum protection, block protection, wide-column entity writes, block-based table factory setup, and data retrieval after flush and reopen. It provides a compact smoke test that combinations accepted by configuration code still produce a functional DB.
- **Risks:** Because it sets many unrelated options at once, a failure can be caused by option incompatibility, platform compression availability, blob/wide-column behavior, or compaction configuration. It checks only a subset of configured fields after open, so it is a broad smoke test rather than exhaustive option serialization validation.
- **Test signals:** Signals include successful `DestroyAndReopen`/`Reopen`, OK `PutEntity`, `Put`, `Flush`, and `Get` calls, expected values for `key1` and `key2`, and retrieved option equality for compression, bottommost compression, FIFO compaction, blob enablement, buffer sizes, level count, auto-compaction disablement, TTL, protection byte settings, paranoid checks, background IO stats, and max-successive-merge settings.

# Research: sources/storage-engines/rocksdb/db/db_options_test.cc

- **Purpose:** Large dynamic-options regression suite for RocksDB DB and column-family options. It verifies immutable option rejection, mutable option parsing/serialization, runtime option propagation, option-file persistence, compaction and flush scheduling side effects, FIFO/TTL behavior, compression changes, direct-IO validation, and concurrent `SetOptions`/`SetDBOptions` races.
- **Important APIs/types/functions:** Defines `DBOptionsTest` with helpers `GetMutableDBOptionsMap()`, `GetMutableCFOptionsMap()`, randomized mutable option map builders, and static `assert_candidate_files_empty()`. It exercises `SetDBOptions`, `SetOptions`, `EnableAutoCompaction`, `GetDBOptions`, `GetOptions`, `LoadLatestOptions`, `SanitizeOptions`, `SanitizeCfOptions`, `DBImpl::TEST_ValidateOptions`, `OffpeakTimeOption`, `GetDBOptionsFromString`, `MockFileSystem`, `FaultInjectionTestFS`, `NewGenericRateLimiter`, block-based table option mutation, FIFO options, compression options, and direct I/O file options.
- **Control flow:** Early tests prove options such as `track_and_verify_wals_in_manifest`, `async_wal_precreate`, and `verify_sst_unique_id_in_manifest` become immutable after open. Mutable option tests randomize sanitized maps, set them, then compare `GetDBOptions()`/`GetOptions()` to expected string maps. IO tests set bytes-per-sync, WAL bytes-per-sync, writable file buffer sizes, background job counts, delayed write rates, max WAL sizes, stats tasks, and obsolete-file scan periods, using sync points or internal counters to confirm runtime behavior. Compaction tests enable auto compaction, change triggers, alter FIFO TTL/max-size/allow-compaction/temperature thresholds, and verify file counts and statistics.
- **State and persistence behavior:** The suite repeatedly opens, closes, destroys, and reopens DBs; creates multiple column families; writes and flushes data to form L0/L1 files; reads live manifest and options files; and uses mock time and fault-injection filesystems. `SetOptionsAndFileRace` compares in-memory CF options to loaded options from the latest options file after concurrent mutation. `SetOptionsNoManifestWrite` checks that selected option changes do not append to MANIFEST and are installed atomically under DB mutex. `AvoidFlushDuringShutdown` verifies that WAL-disabled writes are either flushed or lost depending on `avoid_flush_during_shutdown`.
- **Dependencies:** Includes internal DB/column-family headers, option helper utilities, mock env/time env, sync points, rate limiter, stats history, options util, fault injection FS, and many DBImpl test hooks. Several tests use environment support checks for compression and direct I/O and bypass or expect not-supported statuses accordingly.
- **Integration points:** This file ties option parsing metadata to live DB behavior: env thread pools, write controller stalls/delays, VersionSet manifest sizing and offpeak options, table cache capacity, periodic task scheduler, file writer range sync, compaction picker compression decisions, FIFO compaction picker, options-file persistence, and file-system direct-IO validation. It also covers multi-column-family option application through vector and map overloads.
- **Risks:** It is broad and uses many internal hooks, so failures can be caused by option metadata drift, sanitization changes, scheduling races, filesystem capabilities, or feature availability such as Snappy/LZ4/direct I/O. Concurrency tests are mini-stress tests that look for indefinite inconsistency rather than proving every interleaving. Some older assertions around immutable table factory sub-options are commented out, signaling known limitations in mutability enforcement.
- **Test signals:** Signals include OK/NOK statuses for mutable and immutable changes, exact option values after set/reopen/load, sync-point callback counts, range-sync counter reductions after increasing sync thresholds, background thread and write-controller state changes, table/cache capacities, file counts after compaction, FIFO statistics counters, validation error messages for malformed offpeak or FIFO temperature settings, absence of temp files after failed options persistence, unchanged manifest file number/size for no-manifest-write changes, and expected direct-IO validation or file-option flags.
