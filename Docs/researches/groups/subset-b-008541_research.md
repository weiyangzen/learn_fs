# Research: sources/storage-engines/pebble/range_keys.go

- **Purpose:** Implements Pebble iterator support for range keys, including construction of the range-key iterator stack, suffix-based range-key masking of point keys, block-property-filter acceleration for masking, and lazy activation of combined point/range iteration.
- **Important APIs/types/functions:** `Iterator.constructRangeKeyIter` wires batch, memtable, L0 sublevel, and lower-level range-key iterators into `keyspan` iterator configuration. `containsAnyRangeKeys` checks L0 sublevels before allocating range-key level iterators. `rangeKeyMasking` implements `keyspan.SpanMask` and `sstable.BoundLimitedBlockPropertyFilter` through `SpanChanged`, `SkipPoint`, `Intersects`, `SyntheticSuffixIntersects`, `KeyIsWithinLowerBound`, and `KeyIsWithinUpperBound`. `lazyCombinedIter`, `combinedIterState`, and `combinedIterState.Trigger` implement on-demand switching from point-only iteration to `keyspan.InterleavingIter`.
- **Control flow:** Iterators normally start point-only. Lower-level iterators may trigger `combinedIterState` when a file containing range keys is observed. `lazyCombinedIter.initCombinedIteration` selects a seek key, allocates `iteratorRangeKeyState`, calls `constructRangeKeyIter`, initializes `InterleavingIter`, and forwards future operations to the combined iterator. Range-key masking is updated on every covering span transition; then point keys are skipped if their suffix is hidden by the active masking suffix.
- **State and persistence behavior:** The file itself persists nothing, but reads persistent range-key metadata from manifests, memtables, batches, and sstables. It mutates iterator-local state: active mask span/suffix, stale range-key flags, stats counters, current iterator implementation, and debug logging wrappers. It respects read-state versions and memtable sequence visibility.
- **Dependencies:** Internal packages include `base`, `invariants`, `keyspan`, `manifest`, and `treesteps`; public integration includes `sstable.BoundLimitedBlockPropertyFilter`. It depends on `Iterator` fields, `IterOptions.RangeKeyMasking`, batch indexes, memtable range-key iterators, L0 sublevels, and manifest range-key level metadata.
- **Integration points:** Used by user-facing `Iterator` operations whenever range keys may be visible, particularly MVCC-style range-key masking. The block-property-filter hooks integrate with sstable block skipping, and lazy switching keeps ordinary point scans cheaper until a range-key file is encountered.
- **Risks:** Correctness is sensitive to suffix comparator semantics, inclusive/exclusive bound handling for block skipping, stable lifetime of triggered file-bound keys, and the seek-key adjustment when range keys may exist before the first surfaced point key. Masking comments and implementation must stay aligned: the implementation skips point keys whose suffix sorts after the selected active range-key suffix. Bugs can manifest as hidden visible points, leaked deleted MVCC versions, or skipped blocks outside the masking span.
- **Test signals:** Direct tests live outside this file. Repository signals include `iterator_test.go` randomized range-key masking, `data_test.go` checks for lazy combined iteration initialization, external iterator and ingest/excise tests configuring `RangeKeyMasking`, and compaction test coverage over range-key behavior.

- **Risks:** Because it is an alias/delegation layer, risk is mainly API compatibility and semantic drift if internal `keyspan` or range-deletion encoding changes. Incorrect caller assumptions about key kind or encoded value are handled by the internal decoder rather than this file.
- **Test signals:** No local tests in this file. Coverage is indirect through sstable range-deletion encoding/decoding tests, compaction/replay paths that round-trip range tombstones, and any external package tests importing `rangedel.Decode`.

# Research: sources/storage-engines/pebble/read_compaction_queue.go

- **Purpose:** Maintains a tiny bounded queue of candidate read compactions while enforcing non-overlap among queued key ranges.
- **Important APIs/types/functions:** `readCompactionMaxQueueSize` is fixed at 5. `readCompactionQueue` stores a contiguous prefix of `*readCompaction` entries and the current `size`. `combine` appends a newer queue into an older queue through `add`. `add` removes any existing overlapping ranges, compacts holes through `shiftLeft`, and either appends or evicts the oldest entry if full. `remove` pops the oldest queued compaction.
- **Control flow:** Insertion compares starts and ends with `base.Compare`, treats `right.start <= left.end` as overlap, clears overlaps, compacts nil holes, and preserves insertion order for remaining entries. A full queue drops the first entry by shifting left before writing the new candidate at the tail.
- **State and persistence behavior:** In-memory only. It affects scheduling decisions for read compactions but does not persist queue state. The bounded array avoids allocations and limits attention to recently read ranges.
- **Dependencies:** Depends on `internal/base.Compare` and the package-local `readCompaction` type with `start` and `end` byte slices.
- **Integration points:** Used by DB read-compaction machinery to accumulate small numbers of recent ranges before compaction scheduling. `combine` supports merging older/newer queue views without allowing overlapping work items to coexist.
- **Risks:** The overlap predicate uses inclusive comparison against `left.end`; if `readCompaction.end` is intended as exclusive, adjacent ranges may be coalesced as overlapping. Because old entries are discarded on overlap rather than merged, range detail can be lost. The fixed capacity favors recency and can starve older candidates under heavy read churn.
- **Test signals:** No dedicated tests in this file. Behavior is indirectly exercised by read-compaction scheduling tests and by any compaction tests that assert read-triggered compaction behavior under overlapping read ranges.

# Research: sources/storage-engines/pebble/read_state.go

- **Purpose:** Provides lock-light snapshots of the current LSM `Version` and memtable queue for readers, avoiding `DB.mu` on normal read-state loads while preserving lifetime safety.
- **Important APIs/types/functions:** `readState` contains `db`, atomic `refcnt`, `current *manifest.Version`, and `memtables flushableList`. `ref`, `unref`, and `unrefLocked` manage version and memtable reader references. `DB.loadReadState` grabs `DB.readState.RLock`, references the current state, and returns it. `DB.updateReadStateLocked` builds a fresh snapshot under `DB.mu`, references its version/memtables, installs it under `DB.readState.Lock`, optionally runs a checker, and unreferences the old snapshot.
- **Control flow:** Readers load and later unref snapshots. Writers or version/memtable transitions publish a new immutable snapshot for future readers. Last unref releases the manifest version and each memtable reader reference; the non-locked path also schedules obsolete object deletion.
- **State and persistence behavior:** State is in-memory but protects persistent objects from deletion while readers can still see them. Version references retain sstable metadata and object lifetimes; memtable reader refs retain mutable/immutable memtable storage. `updateReadStateLocked` reflects durable and in-memory state transitions into the read path.
- **Dependencies:** Depends on `sync/atomic`, `internal/manifest`, `DB.mu`, `DB.readState`, `flushableList`, version reference APIs, memtable reader ref APIs, and obsolete object deletion scheduling.
- **Integration points:** Central to iterator/get creation and any read path that needs a consistent view. It bridges write-side version/memtable changes to read-side snapshot isolation.
- **Risks:** Reference-count imbalance can leak versions/memtables or allow premature deletion. Calling `unref` while holding `DB.mu` would violate lock ordering, which is why `unrefLocked` exists. The checker callback runs after publishing the new state and fatal-exits on error, so it must remain diagnostic rather than recoverable control flow.
- **Test signals:** `read_state_test.go` provides a benchmark stressing `loadReadState`, `unref`, and update publication under parallel access with several update ratios. Functional coverage is mostly indirect through all DB read/write tests.

# Research: sources/storage-engines/pebble/record/log_writer.go

- **Purpose:** Implements Pebble's asynchronous WAL-oriented record writer, with recyclable/WAL-sync chunk emission, background flushing, sync batching, optional minimum sync intervals, metrics, and failover-oriented external sync notification.
- **Important APIs/types/functions:** `LogWriter`, `LogWriterConfig`, `PendingSync`, `PendingSyncIndex`, `ExternalSyncQueueCallback`, `LogWriterMetrics`, `SyncConcurrency`, and `NoSyncIndex` are the key exported surface. Internal machinery includes `block`, `syncQueue`, `pendingSyncsWithSyncQueue`, `pendingSyncsWithHighestSyncIndex`, `flusherCond`, `NewLogWriter`, `flushLoop`, `flushPending`, `queueBlock`, `Close`, `CloseWithLastQueuedRecord`, `WriteRecord`, `SyncRecord`, `SyncRecordGeneralized`, `emitEOFTrailer`, `emitFragmentRecyclable`, and `emitFragmentSyncOffsets`.
- **Control flow:** Writers append encoded fragments into the current 32 KiB block. Full blocks are queued to a background `flushLoop`; sync requests are enqueued separately and signal the flusher. The flusher snapshots pending blocks, current partial data, and sync waiters in an order that guarantees a requested sync includes all earlier queued data. It writes blocks/data, optionally calls `Sync`, notifies waiters or external callbacks, enforces minimum sync intervals with a timer, and records metrics. `Close` emits an EOF trailer, drains the loop, syncs final data, closes the underlying writer, and returns blocks to a pool.
- **State and persistence behavior:** Persists records to the underlying writer using recyclable or WAL-sync chunk formats. WAL-sync chunks encode the last durable synced offset, enabling readers to distinguish corruption from ambiguous tail EOF. In-memory state includes active block, free/pending block lists, pending sync queue/index, sync-blocked flag, metrics, background goroutine state, accumulated errors, and pooled block buffers.
- **Dependencies:** Depends on `record.go` constants and CRC format, `base` metrics, `crtime`, `errors`, `prometheus`, `pprof`, `sync/atomic`, and writer interfaces `io.Writer`, `io.Closer`, and `Sync() error`.
- **Integration points:** Used by Pebble WAL writing and commit pipeline paths. The external sync callback path integrates with WAL failover, while the wait-group queue path supports standalone WAL sync notifications. `record.Reader` consumes the emitted recyclable and WAL-sync chunks.
- **Risks:** Concurrency ordering is subtle: sync waiters must not be popped before their data is flushed, queue slots must not be reused before semaphores release, and min-sync blocking must not deadlock close. `WriteWALSyncOffsets` is consulted only during construction, despite the config comment about runtime ratcheting, so format changes after construction require careful higher-level handling. EOF trailer emission assumes sufficient room for the recyclable header. Errors propagate asynchronously and may lag writes until the next queue/close boundary.
- **Test signals:** `log_writer_test.go` covers sync queue concurrency, lost wakeup prevention in `flusherCond`, sync error propagation, sync-position guarantees, min-sync interval blocking and close release, metrics, pending block backlog, highest-index callbacks, generalized sync/close errors, WAL-sync offset monotonicity, and allocation/queue benchmarks.

# Research: sources/storage-engines/pebble/record/record.go

- **Purpose:** Defines Pebble's block/chunk record stream format and implements synchronous `Reader`/`Writer` support for legacy, recyclable, and WAL-sync chunk encodings.
- **Important APIs/types/functions:** Public surface includes `Reader`, `Writer`, `NewReader`, `NewWriter`, `Reader.Next`, `Reader.Offset`, `Writer.Next`, `Writer.WriteRecord`, `Writer.Flush`, `Writer.Close`, `Writer.Size`, `Writer.LastRecordOffset`, `IsInvalidRecord`, and errors `ErrNotAnIOSeeker`, `ErrNoLastRecord`, `ErrZeroedChunk`, `ErrInvalidChunk`, and `ErrUnexpectedEOF`. Internal core includes chunk/wire-format constants, `headerFormatMappings`, `Reader.nextChunk`, `Reader.readAheadForCorruption`, `Reader.seekRecord`, `singleReader.Read`, `Writer.fillHeader`, `Writer.writeBlock`, `Writer.writePending`, and `singleWriter.Write`.
- **Control flow:** The reader scans 32 KiB blocks, validates chunk headers, log numbers, lengths, and CRCs, stitches full/first/middle/last chunks into logical records, and skips to first chunks when needed. On invalid or zeroed chunks, it reads ahead for WAL-sync offsets proving that the invalid offset should have been durable; absent proof, it reports `ErrUnexpectedEOF`. The writer buffers chunks into 32 KiB blocks, fills headers when records end or blocks fill, zero-fills unusable block tails, and flushes/close-finalizes records.
- **State and persistence behavior:** This file defines durable wire formats. Legacy chunks store CRC/size/type, recyclable chunks add a log number for file reuse, and WAL-sync chunks add a synced-offset watermark for corruption disambiguation. Reader state tracks block number, buffer bounds, current record sequence, last-chunk status, accumulated error, and first invalid offset. Writer state tracks buffered ranges, block number, base offset, last record offset, current sequence, pending chunk status, and accumulated error.
- **Dependencies:** Depends on `encoding/binary`, `io`, `math`, `errors`, `base`, `bitflip`, and `crc`. `LogWriter` shares constants and header mappings.
- **Integration points:** Used for MANIFEST records, WAL records, replay/recovery readers, and general record-stream utilities. `recovery.go` relies on `record.IsInvalidRecord` and `ErrUnexpectedEOF` semantics to decide whether log tails are tolerable or corrupt.
- **Risks:** Header parsing is security/corruption sensitive. Off-by-one block-boundary errors can corrupt streams or hide records. WAL recycling depends on low 32-bit log numbers and EOF trailers. Read-ahead must avoid falsely converting ambiguous unclean tails into corruption while still detecting durable corruption when later WAL-sync offsets prove it.
- **Test signals:** `record_test.go` covers round trips through both `Writer` and `LogWriter`, boundary sizes, flush behavior, stale readers, offsets/seeking, corrupt blocks, recyclable log reuse, truncation, log-number mismatch, partial records, WAL-sync datadriven cases, and write benchmarks.

# Research: sources/storage-engines/pebble/record/rotation.go

- **Purpose:** Provides `RotationHelper`, a small state machine for deciding when a record log should rotate to a new file containing a snapshot plus subsequent edits.
- **Important APIs/types/functions:** `RotationHelper` tracks `lastSnapshotSize`, `sizeSinceLastSnapshot`, and `lastRecordSize`. `AddRecord(recordSize)` accumulates edit size and remembers the last record. `ShouldRotate(nextSnapshotSize)` returns true when edits since the last snapshot exceed either the previous snapshot size or the next/current snapshot estimate. `Rotate(snapshotSize)` records the new snapshot size and carries forward the latest record as post-snapshot edit size. `DebugInfo` exposes state for tests.
- **Control flow:** Callers add every record. When external file-size rotation pressure exists, they call `ShouldRotate` with the estimated next snapshot size. On rotation, `Rotate` resets the baseline while preserving the latest edit because that edit is applied after the newly written snapshot.
- **State and persistence behavior:** In-memory only. It influences persistent log-file rotation frequency and therefore replay cost, but it does not write records itself.
- **Dependencies:** No imports. It is deliberately unit-less: sizes may be bytes, entry counts, or another monotonic estimate correlated with snapshot and edit cost.
- **Integration points:** Used by record-log clients that write periodic snapshots and incremental edits. The policy balances write amplification from snapshots against recovery replay cost.
- **Risks:** The helper is only as good as the caller's size estimates and call ordering. Forgetting `AddRecord`, calling `Rotate` at the wrong point, or using incomparable units for record and snapshot size will produce too-frequent rotation or excessive replay tails. Strict `>` comparisons mean equality does not rotate.
- **Test signals:** `rotation_test.go` drives the helper with datadriven `add`, `should-rotate`, and `rotate` commands and checks debug state/output.

# Research: sources/storage-engines/pebble/recovery.go

- **Purpose:** Recovers Pebble database state at open time by reading directory metadata, format markers, OPTIONS, manifests, object storage state, WALs, and replaying unflushed WAL records into flushables.
- **Important APIs/types/functions:** `recoverState` and `(*recoveredState).init` discover and validate on-disk state. `recoveredState` stores directories, format marker, manifest marker/number, max file number, obsolete temp/WAL files, object provider, previous options file, recovered version, and WAL sets. `RemoveObsolete` cleans marker leftovers, temp files, and obsolete WAL segments. `checkForLegacyFormatVersion1` rejects old `CURRENT`-based stores. `recoveredVersion` and `recoverVersion` replay MANIFEST records. `DB.replayWAL` replays logical WAL records. `DB.replayIngestedFlushable` reconstructs flushable ingests and excises from WAL batches.
- **Control flow:** Recovery locks directories, lists files, finds format/version markers, opens object storage, locates and replays the current manifest, validates consistency, reads previous OPTIONS for compatibility and WAL failover identity, computes max used file number, scans WAL directories, and partitions WALs into obsolete vs replay-needed. WAL replay reads record batches, tolerates only allowed tail EOF cases, rejects corruption, applies normal batches into memtables, converts large batches to flushable batches, and converts ingest/excise entries to flushable ingests followed by WAL rotation.
- **State and persistence behavior:** `recoverState` is read-only except for opened locks/providers; `RemoveObsolete` later deletes obsolete marker/temp/WAL artifacts. `recoverVersion` reconstructs persisted LSM metadata including virtual backings, blob files, L0 organization, next file number, min unflushed WAL, and next sequence number. `replayWAL` mutates in-memory memtable/flushable queues and, in non-read-only mode, forces replayed memtables to flush for durability.

- **Integration points:** Invoked during DB open before normal operation. It integrates record-layer tail/corruption semantics with Pebble's durability model, manifest version state, WAL failover directories, object providers, ingested sstables/blob files, and obsolete-file cleanup.
- **Risks:** Recovery is high-stakes: misclassifying WAL tails can lose acknowledged writes or reject healthy stores. File-number ratcheting must avoid collisions with obsolete/ingested objects. Replay of ingests depends on referenced table/blob files still existing. Lock ordering matters because `replayWAL` may drop/reacquire `DB.mu`. Legacy format and option compatibility checks must prevent accidental overwrite or unsafe open.
- **Test signals:** Coverage is distributed across Pebble open/recovery, WAL, ingest, excise, corruption, and format-version tests. Record-layer tests supply important signals for `record.IsInvalidRecord` and `ErrUnexpectedEOF` behavior used here.

# Research: sources/storage-engines/pebble/replay/replay.go

- **Purpose:** Implements compaction workload replay: reconstructs flush/ingest/excise steps from captured manifests and sstables, applies them to a test Pebble DB, paces application, waits for compactions to quiesce, and reports benchmark-style metrics.
- **Important APIs/types/functions:** Public types include `Pacer`, `Unpaced`, `PaceByReferenceReadAmp`, `PaceByFixedReadAmp`, `Metrics`, `Plot`, and `Runner`. Key functions/methods include `computeReadAmp`, `waitForReadAmpLE`, `Metrics.Plots`, `Metrics.WriteBenchmarkString`, `Runner.Run`, `refreshMetrics`, `compactionsAppearQuiesced`, `nextCompactionOrFlushCompletes`, `Wait`, `Close`, `eventListener`, `applyWorkloadSteps`, `prepareWorkloadSteps`, `findWorkloadFiles`, `findManifestStart`, `blobFileMap.Lookup`, and `loadFlushedSSTableKeys`.
- **Control flow:** `Run` discovers workload files, finds the manifest start relative to the run DB, opens a staging dir and DB with WAL disabled, installs event listeners, and starts goroutines for preparation, application, and metrics refresh. Preparation reads manifest edits, classifies edits as flush/ingest/compaction/ingest-and-excise, applies version edits to track metadata/read amp, reconstructs flush batches by reading captured sstables, or stages ingested files. Application paces each step, commits flush batches plus `AsyncFlush`, calls `Ingest` or `IngestAndExcise`, and reports progress. Metrics refresh samples DB metrics after workload steps and compaction/flush completions until workload exhaustion and quiescence.
- **State and persistence behavior:** Replays into `RunDir`, creates a staging directory, copies workload sstables for ingest, opens captured sstables/blob files read-only, and writes a new Pebble DB without WAL. In-memory state tracks manifest offsets, workload file sets, metrics samples, write-stall counters, compaction/flush counters, channels, cancellation, and final metrics.
- **Dependencies:** Depends on Pebble public APIs, internal `base`, `manifest`, `rangedel`, `rangekey`, byte allocator, record reader, sstable/blob readers, vfs, errgroup, and benchfmt.
- **Integration points:** Used by benchmarking tooling to evaluate compaction heuristics against captured production-like workloads. It bridges manifest replay, sstable readers, Pebble batch/ingest APIs, event listeners, metrics, and benchstat-compatible output.
- **Risks:** Workload fidelity depends on correctly classifying version edits and reconstructing flushed keys in sequence-number order. Missing captured sstables/blob files abort replay. Quiescence detection is deliberately subtle and event-driven; errors in started/completed accounting can stop too early or hang. `MaxWriteBytes` uses cumulative bytes and may cut after crossing the threshold. Range tombstone/key reconstruction assumes decoded spans contain one key for range-key operations.
- **Test signals:** This file has no adjacent test in the listed set. Indirect signals come from replay tool tests, manifest/record/sstable/rangekey/rangedel tests, and benchmark output sanity. Runtime failures surface as missing workload files, decode errors, Pebble event background errors, or non-quiescing compactions.
