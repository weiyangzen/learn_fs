# sources/distributed-fs/alluxio/core/server/master/src/main/java/alluxio/master/file/DefaultFileSystemMaster.java

Purpose: `DefaultFileSystemMaster` is Alluxio's central file-system metadata master. It implements `FileSystemMaster`, exposes client/job/worker gRPC services, owns the inode namespace, mount table, UFS metadata sync, permission enforcement, async persistence orchestration, file/block metadata integration, audit logging, and master-side metrics. It is the public API surface behind operations such as status/list, create, complete, delete, rename, free, mount/unmount, ACL/attribute mutation, sync metadata, active sync, worker heartbeat, and UFS mode updates.

Important APIs/types/functions: the class extends `CoreMaster` and implements `DelegatingJournaled`, with `getServices()`, `getDelegate()`, `createJournalContext()`, `start()`, `stop()`, and `close()` wiring master lifecycle and journaling. Read/status APIs include `getFileId()`, `getFileInfo()`, `listStatus()`, `exists()`, `checkAccess()`, `checkConsistency()`, `getFileBlockInfoList()`, `getInAlluxioFiles()`, and `getInMemoryFiles()`. Mutating APIs include `createFile()`, `completeFile()`, `createDirectory()`, `delete()`, `rename()`, `free()`, `mount()`, `updateMount()`, `unmount()`, `setAcl()`, `setAttribute()`, `scheduleAsyncPersistence()`, `startSync()`, and `stopSync()`. Metadata-sync entry points are `loadMetadataIfNotExist()`, `syncMetadata(...)`, `syncMetadata(AlluxioURI, SyncMetadataContext)`, `syncMetadataAsync()`, `getSyncProgress()`, `cancelSyncMetadata()`, `activeSyncMetadata()`, `needsSync()`, and `recordActiveSyncTxid()`. Internal helpers such as `createFileInternal()`, `completeFileInternal()`, `deleteInternal()`, `renameInternal()`, `setAttributeSingleFile()`, `setAclSingleInode()`, `checkUfsMode()`, and `commitBlockInfosForFile()` perform the locked and journaled work. Inner heartbeat executors `PersistenceScheduler`, `PersistenceChecker`, and `TimeSeriesRecorder` drive background persistence and metrics.

State and persistence: durable namespace state is maintained through `InodeTree`, `InodeDirectoryIdGenerator`, `MountTable`, `MasterUfsManager`, `ActiveSyncManager`, and `JournaledJobMetaStore`, all grouped in `mJournaledGroup` under `CheckpointName.FILE_SYSTEM_MASTER`. Journal writes flow through `RpcContext`, which combines a `JournalContext`, `BlockDeletionContext`, and operation cancellation tracker; when configured, inode journal entries are merged through `FileSystemMergeJournalContext`. The class maintains volatile/process state for UFS absent-path and block-location caches, async persist request/job maps, executor pools, audit writer, sync process, scheduler, access-time updater, and time-series store. File persistence metadata includes inode `PersistenceState`, persist job IDs, temp UFS paths, UFS fingerprints, content hashes in xattrs, direct-children-loaded bits, pin/replication/TTL/ACL state, and mount options. Startup reconstructs pending persistence from journaled inode state and initializes UFS clients for restored mounts.

Control flow: public API methods follow the file's documented convention: create an `RpcContext`, optionally run UFS metadata sync, acquire the appropriate inode path lock, perform permission and mount/UFS-mode checks, then call an `*Internal` helper. Reads commonly use `LockPattern.READ`; path-creating operations use `WRITE_EDGE`; inode mutations use `WRITE_INODE`; rename locks source and destination as a pair. Status and listing support a two-pass load-metadata loop: first inspect the locked path, then call `loadMetadataIfNotExist()` and retry if the requested metadata is absent or descendants must be loaded. `listStatusInternal()` recursively streams entries, handles partial and prefix listings, checks execute permissions on directories, and updates access times.

Create/complete/delete/rename flow: `createFile()` and `createDirectory()` sync parent metadata, check parent write permission, reject unwritable mounts, optionally verify UFS writability, and delegate to `mInodeTree.createPath()`. `completeFile()` validates block metadata, computes length and UFS fingerprint for persisted files, updates inode-file completion state, commits block metadata to `BlockMaster`, and can schedule async persistence. `delete()` may skip metadata sync for Alluxio-only deletes, rejects recursive mount-point deletion unless explicitly allowed, delegates to `deleteInternal()`, and only deletes blocks after inode journal work through the block deletion context. `deleteInternal()` walks descendants, honors recursive and skip-not-persisted rules, checks per-child write permission unless bypassed, deletes UFS objects through `SafeUfsDeleter`, removes mount table entries, cancels pending persist jobs, journals inode deletion from children to parents, and reports failed UFS deletions. `rename()` syncs both sides, checks parent write permission, blocks root/cross-mount/subpath/mount-point renames, supports S3 overwrite/multipart idempotency syntax, journals inode movement before UFS rename, and rolls back the inode rename if the UFS rename fails. Persist-on-rename marks files or descendants `TO_BE_PERSISTED` and enqueues exponential timers.

Mount, ACL, attribute, and sync flow: `mount()` validates and prepares a UFS client under the mount-table write lock, loads mount-point directory metadata, and journals the mount only after validation succeeds; failure removes the provisional UFS client. `updateMount()` rejects active-sync mount points, validates a new UFS client with a new mount ID, then journals mount-table update. `unmount()` stops active sync for the mount, removes the mount-table entry, and deletes Alluxio-only metadata recursively. `setAcl()` and `setAttribute()` sync metadata, check owner/superuser/write permissions based on requested mutation, precheck recursive descendants, update inode ACL/attributes, flush recursive journal batches when needed, and best-effort or strict-propagate relevant UFS ACL/owner/mode changes. `activeSyncMetadata()` forces full or incremental `InodeSyncStream` runs; public sync APIs dispatch to `DefaultSyncProcess` task groups with progress and cancellation support.

Background persistence and worker integration: `scheduleAsyncPersistenceInternal()` marks completed files `TO_BE_PERSISTED` unless blacklisted and records an `ExponentialTimer`. `PersistenceScheduler` scans `mPersistRequests`, backs off when the job service is busy, turns expired requests back to `NOT_PERSISTED`, generates temp UFS paths, submits `PersistConfig` to the job master, and journals job ID/temp-path metadata. `PersistenceChecker` polls job status, cancels requested jobs, retries failed or status-query-failed jobs, and runs successful completion in `mPersistCheckerPool`; `handleSuccess()` validates optional file length, creates missing UFS parent directories with owner/group/mode/ACLs, renames temp files into place, journals persisted state and UFS fingerprint, propagates persisted state to ancestors, updates the absent-path cache, and cleans fast-durable-write staging files. `workerHeartbeat()` accepts persisted file IDs from legacy worker persistence, marks them persisted through `setAttribute()`, and returns an empty `PERSIST` command because persistence is now job-service driven.

Dependencies and integration points: this master sits between the RPC service handlers, `BlockMaster`, inode metastore, mount/UFS layer, `InodeSyncStream`, `DefaultSyncProcess`, active-sync manager, job service, scheduler, audit log writer, metrics registry, security/authentication helpers, ACL/mode classes, UFS fingerprinting, and journal system. It uses `DefaultPermissionChecker` for access decisions, `MountTable` and `MasterUfsManager` for path resolution and physical UFS mode, `UfsAbsentPathCache`/`UfsBlockLocationCache` for sync and block-location optimization, and `MetricsSystem` for counters/gauges/time-series recording. Tests and downstream code also use visible-for-testing accessors for inode store/tree/lock manager/sync cache/mount table/scheduler.

Risks: this is a high-blast-radius coordinator with many cross-system consistency windows. Several operations mutate UFS and journal Alluxio metadata in separate steps; crash or failover between those steps can create Alluxio/UFS divergence, noted explicitly for delete and handled partially by rename rollback and consistency checks. Recursive operations can touch many inodes, so journal batching, cancellation, descendant locking order, and permission prechecks are critical. Metadata sync can change namespace state before reads/writes and must avoid stale absent-cache decisions. Async persistence has races around file mutation versus persisted temp output, job-service backpressure, temp cleanup, object-store direct persist, and parent directory permission propagation. ACL propagation to UFS logs and continues on some failures, while owner/mode propagation aborts Alluxio changes on UFS failure. The class is annotated `@NotThreadSafe` despite being used in a concurrent master environment, relying on inode locks, concurrent maps, executor discipline, and lifecycle ordering. Auditing depends on creating audit contexts inside inode lock scope to preserve event order.

Test signals: broad coverage exists in `FileSystemMasterTest` for create/delete variants, lost files, worker heartbeat, mount/unmount and read-only mount behavior, UFS info, fingerprints, xattrs, ACL behavior, and operation-specific regressions. `FileSystemMasterSyncMetadataTest`, `FileSystemMasterSyncMetadataMetricsTest`, and related bases exercise metadata sync, metrics, executor instrumentation, UFS status cache metrics, and sync-aware overrides. `FileSystemMasterMetricsTest` verifies registered gauges. Important additional signals would include crash-window/replay tests around delete/rename/mount/updateMount, async persistence job-service backpressure and size-validation races, recursive journal flush boundaries, active-sync stop while full sync is running, direct-UFS status error mapping, and ACL UFS propagation failure semantics.

# sources/distributed-fs/alluxio/core/server/master/src/main/java/alluxio/master/file/DefaultPermissionChecker.java

Purpose: `DefaultPermissionChecker` is the default Alluxio namespace authorization implementation. It evaluates the authenticated client user's owner/group/other ACL permissions over a locked inode path, including execute checks on ancestors, direct permission checks on the target inode, parent/ancestor checks for creates, owner/superuser checks for metadata changes, and superuser checks for privileged operations.

Important APIs/types/functions: the class implements `PermissionChecker` and is constructed with an `InodeTree`. Public methods are `checkParentPermission(Mode.Bits, LockedInodePath)`, `checkPermission(Mode.Bits, LockedInodePath)`, `getPermission(LockedInodePath)`, `checkSetAttributePermission(LockedInodePath, boolean, boolean, boolean)`, and `checkSuperUser()`. Core helpers are `getGroups()`, `checkOwner()`, `checkInodeList()`, `checkInode()`, `getPermissionInternal()`, `isPrivilegedUser()`, and `toExceptionMessage()`.

State and persistence: the checker stores only `mInodeTree`, the boolean `mPermissionCheckEnabled`, and the configured supergroup name, all captured at construction from global configuration. It does not journal or mutate file-system state. It reads locked inode views, authenticated user identity from `AuthenticatedClientUser`, group membership from `CommonUtils.getGroups()`, root owner from `InodeTree`, ACL state from each `InodeView`, and mode bits for diagnostic messages.

Control flow: all permission methods return immediately when authorization is disabled. `checkParentPermission()` skips root, obtains the existing inode view list from the locked path, removes the final inode when the full path exists, then checks requested bits on the parent or last existing ancestor after requiring execute permission on earlier ancestors. `checkPermission()` checks execute on every ancestor and requested bits on the final inode. `getPermission()` returns `NONE` when disabled or when user/group lookup fails; otherwise it returns `ALL` for privileged users, `NONE` if an ancestor execute check fails, or the target inode's resolved ACL permission as mode bits. `checkSetAttributePermission()` composes the rules used by `chown`, `chgrp`, `chmod`, and other attribute updates: superuser for owner changes, owner or privileged user for group/mode changes, and write permission for other attribute mutations. `checkSuperUser()` verifies the user is root owner or belongs to the configured supergroup.

Permission semantics: `checkInodeList()` rejects empty path metadata, bypasses all checks for privileged users, requires `EXECUTE` on every inode before the target, then either checks ownership of the target or calls `checkInode()` for each requested ACL action. Null inodes are tolerated, which supports incomplete paths where only ancestors exist. `checkInode()` expands `Mode.Bits` into ACL actions and delegates to `InodeView.checkPermission(user, groups, action)`, throwing an `AccessControlException` with user, access bits, path, failing inode name, owner, group, and mode. `isPrivilegedUser()` defines privilege as either the root inode owner or membership in the configured filesystem supergroup.

Dependencies and integration points: `DefaultFileSystemMaster` constructs this checker and uses it before nearly every user-visible namespace operation. It depends on Alluxio global configuration keys for permission enablement and supergroup, authentication context, group mapping service, `LockedInodePath` and `InodeView`, `Mode.Bits`, ACL action conversion, path utilities, and Alluxio exception message types. The implementation assumes callers already hold the appropriate inode locks and provide a path whose inode view list reflects the operation's target or closest existing ancestor.

Risks: the class is annotated `@NotThreadSafe` and captures configuration once, so runtime changes to authorization enablement or supergroup are not reflected by existing instances. Group lookup failures become permission denials, which is safe but can turn identity backend outages into broad access failures. `checkParentPermission()` mutates the `inodeList` returned by `LockedInodePath.getInodeViewList()` when full path exists; this is safe only if that API returns a mutable copy rather than shared path state. Null inode tolerance is important for incomplete paths but can mask malformed path lists. Privileged-user behavior depends on root owner correctness and group mapping freshness. Error messages expose inode owner/group/mode and failing component, which is useful operationally but should be considered in multi-tenant contexts.

Test signals: `PermissionCheckerTest` builds an in-memory inode tree with fake user/group mapping and validates filesystem owner privilege, configured supergroup privilege, owner/group/other permission success and failure, no fall-through between owner/group/other mode classes, parent and ancestor checks for missing paths, invalid path behavior, and `getPermission()` results. Additional useful coverage would check permission-disabled behavior, group mapping IO failures, root path parent checks, `checkSetAttributePermission()` combinations, runtime configuration changes after construction, null inode lists, and ACL-specific extended entries beyond basic mode bits.
