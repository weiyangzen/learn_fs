# sources/storage-engines/foundationdb/contrib/sqlite/btree.h

Purpose: This header defines the internal SQLite b-tree subsystem contract used by the VDBE, pager, schema, backup, and table/index layers in FoundationDB's bundled SQLite copy. It exposes opaque `Btree`, `BtCursor`, and `BtShared` handles, database open/close and pager configuration APIs, transaction boundaries, table lifecycle operations, cursor movement and record access, metadata cookie access, vacuum/integrity helpers, and shared-cache mutex hooks. It is an interface file rather than an implementation file, but it is the central declaration boundary for persistent database storage behavior.

Important APIs and types: The primary types are `Btree` for an open database b-tree, `BtCursor` for table/index scans and mutations, and `BtShared` for shared-cache state. `sqlite3BtreeOpen`, `sqlite3BtreeClose`, `sqlite3BtreeSetCacheSize`, `sqlite3BtreeSetSafetyLevel`, `sqlite3BtreeSetPageSize`, `sqlite3BtreeMaxPageCount`, `sqlite3BtreeSecureDelete`, and auto-vacuum functions configure the database file and pager behavior. `sqlite3BtreeBeginTrans`, `sqlite3BtreeCommitPhaseOne`, `sqlite3BtreeCommitPhaseTwo`, `sqlite3BtreeCommit`, `sqlite3BtreeRollback`, `sqlite3BtreeBeginStmt`, and `sqlite3BtreeSavepoint` define transactional control. Table and schema APIs include `sqlite3BtreeCreateTable`, `sqlite3BtreeDropTable`, `sqlite3BtreeClearTable`, `sqlite3BtreeGetMeta`, `sqlite3BtreeUpdateMeta`, `sqlite3BtreeSchema`, `sqlite3BtreeLockTable`, and `sqlite3BtreeTripAllCursors`. Cursor APIs cover open/zero/close, seek, first/last/next/previous, EOF, key/data sizing and fetching, insert, delete, cached rowid, and cursor invalidation. FoundationDB-specific or non-upstream-looking additions include range-oriented deletion helpers `sqlite3BtreeDeleteRange` and `sqlite3BtreeLazyDelete`.

Control flow: Callers open a `Btree`, configure pager/page-size/safety behavior before heavy use, begin read or write transactions, create/open table cursors, seek or scan through records, apply inserts/deletes, then commit or roll back. For a durable commit the header preserves SQLite's two-phase split: phase one syncs or prepares state, and phase two completes the commit. Cursor methods assume the caller has a valid cursor allocation sized by `sqlite3BtreeCursorSize` and initialized by `sqlite3BtreeCursorZero`; shared-cache builds wrap b-tree access with `sqlite3BtreeEnter`/`Leave` or cursor enter/leave helpers.

State and persistence behavior: This API controls persistent page trees, database header metadata, free-page accounting, root-page allocation, rollback or journal/WAL backed transactions, schema cookies, auto-vacuum metadata, cache size, reserve bytes, secure delete behavior, savepoints, and integrity checking. Metadata constants map to database header offsets by `36 + idx * 4`, including free-page count, schema version, file format, default cache size, largest root page, text encoding, user version, and incremental vacuum. `SQLITE_N_BTREE_META` is locally defined as `10` with a TODO noting it exists to keep other modules compiling, which makes the metadata surface a compatibility-sensitive stub.

Dependencies and integration points: The declarations depend on SQLite core typedefs and structs such as `sqlite3`, `u32`, `u8`, `i64`, `sqlite3_int64`, `Schema`, `Pager`, `KeyInfo`, and `UnpackedRecord`. The implementation lives in `btree.c`, with copies in `sqlite3.amalgamation.c`; VDBE opcodes use these functions for table scans, writes, metadata cookies, ephemeral b-trees, and transaction opcodes. The flags must match pager-level values for `BTREE_OMIT_JOURNAL`, `BTREE_NO_READLOCK`, and `BTREE_MEMORY`. `BTREE_UNORDERED` is asserted in implementation to be valid only with `BTREE_SINGLE` and is propagated from query planning for hash-compatible unordered ephemeral structures. Shared-cache mutex macros compile to no-ops when shared cache or threadsafety is omitted.

Risks: This file is a cross-module ABI within the SQLite subtree, so signature drift between `btree.h`, `btree.c`, and the amalgamation can break compilation or, worse, silently miscompile callers. The local TODO around `SQLITE_N_BTREE_META` is risky because VDBE metadata opcodes assert against this bound. Transaction phase signatures must stay aligned; this header declares `sqlite3BtreeCommitPhaseTwo(Btree*, int)` while related implementation/amalgamation references in this tree show one-argument forms, so this area deserves build coverage. Range and lazy deletion APIs carry higher storage risk because they can delete multiple pages/records and expose stack/range parameters; incorrect cursor ordering or partial failure semantics could corrupt logical table contents. Mutex macros that collapse to constants can hide missing lock coverage in non-debug or single-threaded builds.

Test signals: Useful checks are full SQLite subtree compilation, API signature consistency against `btree.c` and `sqlite3.amalgamation.c`, transaction commit/rollback/savepoint tests, metadata cookie read/write tests, auto-vacuum and secure-delete persistence tests, cursor movement and mutation tests for integer-key and blob-key tables, integrity-check tests after create/drop/clear/range-delete/lazy-delete paths, unordered ephemeral table tests, and shared-cache/threadsafe builds that exercise the mutex declarations rather than the no-op macros.

# sources/storage-engines/foundationdb/contrib/sqlite/hash.h

Purpose: This header defines SQLite's small generic in-memory hash table used by schema and connection metadata structures in the bundled SQLite copy. It is not a persistent storage structure; it provides name-to-object lookup, insertion, deletion-by-null-insert, clearing, and linear iteration over all stored elements.

Important APIs and types: `Hash` stores the hash table state: bucket count `htsize`, entry count `count`, a global doubly linked list head `first`, and an optional bucket array `ht` whose entries track the first element and count for each hash bucket. `HashElem` stores list links, `data`, `pKey`, and `nKey`. Public functions are `sqlite3HashInit`, `sqlite3HashInsert`, `sqlite3HashFind`, and `sqlite3HashClear`. Iteration and access are provided by macros `sqliteHashFirst`, `sqliteHashNext`, and `sqliteHashData`; key and count macros are present but commented out as unused.

Control flow: Clients initialize a `Hash`, insert data by key, look up data by key and key length, remove an entry by inserting a null data pointer for that key, iterate from `sqliteHashFirst` through `sqliteHashNext`, then clear the table at schema/connection teardown. For small tables `htsize` and `ht` may remain zero and lookups fall back to a linear scan of the global element list. Once the table grows, the implementation can allocate buckets, with each bucket representing a contiguous run inside the global doubly linked list.

State and persistence behavior: All state is process-local heap memory. The structure preserves a global list ordering in addition to bucket membership, which lets schema teardown scan all entries without walking buckets. Keys are stored as `const char *` plus length, so ownership and lifetime are implementation/client-contract concerns rather than self-evident from the header. `sqlite3HashClear` releases table internals but does not describe ownership of client `data`; callers elsewhere are responsible for destroying schema objects, collations, modules, triggers, or table structures before or around hash cleanup.

Dependencies and integration points: The header is consumed by SQLite schema management, connection-level collation/module maps, table/index/trigger/foreign-key maps, and b-tree schema cleanup paths. Cross-references in this subtree show iteration over schema hashes in `btree.c` and extensive insert/find/clear usage in the amalgamation around parser, schema, trigger, virtual table, and connection teardown logic. The implementation is in the SQLite hash module embedded into `sqlite3.amalgamation.c`.

Risks: The structure is not truly opaque because macros read fields directly, so layout changes require coordinated recompilation of every user. Since key memory is exposed as a pointer/length pair, inserting stack or temporary key buffers would be unsafe unless the implementation copies keys or the caller guarantees lifetime. Iteration while mutating can invalidate `HashElem` links. The small-table linear-search optimization makes performance sensitive to growth thresholds in the implementation. Because deletion is encoded as `sqlite3HashInsert(..., NULL)`, call sites must distinguish intentional deletion from accidental null data. There is no embedded locking; callers rely on higher-level SQLite connection/schema mutex discipline.

Test signals: Good signals include insertion replacement returning prior data, deletion by null insert, lookup misses and hits with explicit key lengths, iteration over all entries after growth and after removal, clear leaving zero count and no buckets/list head, schema load/drop tests that exercise table/index/trigger hashes, collation/module registration tests, and sanitizer or leak runs around repeated schema resets.

# sources/storage-engines/foundationdb/contrib/sqlite/shell.c

Purpose: This file implements the standalone `sqlite` command-line shell for the bundled SQLite library. It handles interactive and batch input, command history, SQL statement accumulation and execution, output formatting, dot commands such as `.dump`, `.schema`, `.import`, `.backup`, and `.restore`, SQLite status reporting, optional extension loading, logging, timers, VFS selection, and process-level signal interruption.

Important APIs and types: Runtime state is carried by `struct callback_data`, which stores the open `sqlite3 *db`, output stream, display mode, separator, null rendering, column widths, destination table for insert mode, current statement, log stream, database filename, VFS name, echo/stats flags, and previous `.explain` state. Output modes are `MODE_Line`, `MODE_Column`, `MODE_List`, `MODE_Semi`, `MODE_Html`, `MODE_Insert`, `MODE_Tcl`, `MODE_Csv`, and `MODE_Explain`. Key functions include `main_init`, `main`, `open_db`, `process_sqliterc`, `process_input`, `do_meta_command`, `shell_exec`, `shell_callback`, `dump_callback`, `run_schema_dump_query`, `run_table_dump_query`, `display_stats`, `local_getline`, `one_input_line`, `set_table_name`, `appendText`, `output_quoted_string`, `output_c_string`, `output_html_string`, `output_csv`, `find_home_dir`, and the SIGINT `interrupt_handler`.

Control flow: `main` initializes callback state, configures SQLite logging and single-thread mode, installs the SIGINT handler, performs an early argument scan for database/init/VFS/heap settings, opens an existing database lazily, processes `~/.sqliterc` or `-init`, applies command-line display options on a second pass, then either executes one command or enters `process_input`. `process_input` reads lines, dispatches leading-dot meta commands only when no SQL is buffered, accumulates SQL until semicolon or recognized `go`/`/` terminators, checks completeness with `sqlite3_complete`, opens the database if needed, times execution when enabled, and passes SQL to `shell_exec`. `shell_exec` prepares one statement at a time, echoes SQL if requested, steps rows, constructs column/value/type arrays for `shell_callback`, prints stats, finalizes, and advances to leftover SQL. Dot commands are parsed in-place by `do_meta_command` and handled through a long prefix-matching dispatch chain.

State and persistence behavior: Persistent effects mostly occur through SQLite APIs invoked by SQL or dot commands. `.backup` and `.restore` use `sqlite3_backup_init`, repeated `sqlite3_backup_step(100)`, and `sqlite3_backup_finish` to copy database pages between files, with restore retrying short busy periods. `.dump` emits a transactional SQL script, toggles writable schema for virtual tables, queries `sqlite_master`, prints table contents as `INSERT` statements, and disables foreign key enforcement for replay. `.import` opens an input file, starts a transaction, splits lines by the configured separator, binds fields into an `INSERT`, and commits or rolls back on format/error conditions. Runtime state includes global `db` for interrupt handling, `seenInterrupt`, `bail_on_error`, `stdin_is_interactive`, prompts, output/log file handles, command history path, and per-session display settings.

Dependencies and integration points: The shell integrates with `sqlite3.h`, the SQLite C API, readline/editline when available, platform timing APIs (`getrusage` or `GetProcessTimes`), signal handling, home-directory discovery, stdio file I/O, optional loadable extensions, optional I/O tracing, optional VFS tracing, and SQLite test controls. The `shellstatic` SQL function is registered to safely pass shell pattern strings into `.dump`, `.schema`, `.tables`, and `.indices` queries without formatting them directly into SQL. The shell is a consumer of the SQLite library in this subtree, so it indirectly exercises pager, b-tree, parser, VDBE, backup, virtual table, status, and VFS layers.

Risks: Several command parsers mutate argument buffers in place, so quoted/backslash parsing bugs can affect subsequent dispatch. `.import` is separator-based rather than a full CSV parser and does not handle quoted separators or multiline fields. Some fixed buffers (`separator`, `nullvalue`, prompts, column arrays of size 100, `azArg[50]`) impose silent truncation or command limits. Error handling is uneven in places: backup/restore loops step fixed page chunks without progress callbacks, `.dump` has corruption fallback behavior that can emit reordered data, and dynamically built SQL requires careful quoting. `run_schema_dump_query` allocates `len + 100` but calls `sqlite3_snprintf(sizeof(zQ2), ...)`, which uses pointer size rather than allocation size and is a likely truncation bug. The `.log` branch accepts `nArg >= 1` but immediately reads `azArg[1]`, so a bare `.log` can dereference an uninitialized argument. The `.testctrl` prefix checks include suspicious comparisons such as `strncmp(..., "bitvec_test", 6) == 3`, which likely makes some options unreachable. The shell configures `SQLITE_CONFIG_SINGLETHREAD`, so embedding assumptions differ from multithreaded clients.

Test signals: High-value tests include batch and interactive-style input completion, dot-command prefix matching, `.bail` behavior, Ctrl-C interruption against a long query, every output mode including BLOB and NULL rendering, `.mode insert` identifier quoting, `.dump` and restore replay for tables/indexes/triggers/views/virtual tables, `.schema`, `.tables`, and `.indices` pattern filtering through `shellstatic`, `.import` commit and rollback on column-count mismatch, `.backup` and `.restore` page-copy behavior under busy and normal conditions, `.output` and `.log` file handling, `.stats` and `.timer` output under supported platforms, `-init` and `.sqliterc` precedence, command-line option parsing, extension loading gates, and sanitizer/fuzzer coverage for meta-command tokenization and SQL accumulation.
