# Research: sources/storage-engines/rocksdb/db/db_write_buffer_manager_test.cc

- **Purpose:** Parameterized RocksDB test coverage for `WriteBufferManager` behavior across column families, independent DB instances sharing one manager, runtime `allow_stall` changes, and WAL recovery enforcement. It exercises both cache-costed and non-cache-costed WBM construction through `testing::Bool()`.
- **Important APIs/types/functions:** Defines `DBWriteBufferManagerTest : DBTestBase, testing::WithParamInterface<bool>` with `cost_cache_`. Test cases cover `SharedBufferAcrossCFs1`, `SharedWriteBufferAcrossCFs2`, `SharedWriteBufferLimitAcrossDB`, `SharedWriteBufferLimitAcrossDB1`, `MixedSlowDownOptionsSingleDB`, `MixedSlowDownOptionsMultipleDB`, `StopSwitchingMemTablesOnceFlushing`, `RuntimeChangeableAllowStall`, `WriteBufferManagerLimitDuringWALRecoverySingleDB`, `WriteBufferManagerLimitDuringWALRecoveryMultipleDBs`, `DoubleSchedulingBugDuringWALRecovery`, and `ReadOnlyRecoveryWithEnforceWBMDoesNotAssert`.
- **Control flow:** Most tests configure small global WBM limits with large per-CF `write_buffer_size`, write enough data to exceed the shared limit, then use `SyncPoint` callbacks such as `WBMStallInterface::BlockDB`, `WriteThread::WriteStall::Wait`, and `DBImpl::BackgroundCallFlush:start` to hold flushes while asserting which DBs or writers block. Recovery tests write WAL-only data, close, reopen with different WBM limits/options, and check whether flushes bound memory during replay.
- **State and persistence behavior:** State under test is mutable memtable memory charged to `WriteBufferManager`, write-stall state, immutable memtable/flush-pending properties, shared WBM accounting across multiple `DB::Open()` instances, and WAL contents replayed during recovery. Persistent artifacts are test DB directories, WAL files, and generated SSTs; cleanup closes and destroys auxiliary DBs where created.
- **Dependencies:** Uses `db/db_test_util.h`, `db/write_thread.h`, `NewLRUCache`, `WriteBufferManager`, `InstrumentedMutex`, `InstrumentedCondVar`, `SyncPoint`, `SleepingBackgroundTask`, and DB test helpers (`CreateAndReopenWithCF`, `Put`, `Flush`, `ReadOnlyReopen`, `TotalTableFiles`). It depends on RocksDB internals exposing test sync points and test-only properties.
- **Integration points:** Validates DB write admission and memtable switching paths that consult WBM, the WBM-to-cache charging mode, `WriteOptions::no_slowdown`, background flush scheduling, and `Options::enforce_write_buffer_manager_during_recovery`. It also protects `FlushScheduler` interactions during WAL recovery and read-only recovery.
- **Risks:** The tests depend on exact memory thresholds and allocator/accounting behavior; changes to arena charging or mutable limit calculations can require updating expected counts. SyncPoint dependencies are race-sensitive and can hang if internal sync-point names or ordering drift. Multi-DB tests share one WBM, so cleanup failures can leak state into later assertions.
- **Test signals:** Assertions check OK/Incomplete statuses, block counts, writer-set sizes, WBM `ShouldFlush()`, mutable memtable memory before/after recovery, L0 table counts, DB properties, and absence of debug assertions in duplicate scheduling regressions.

# Research: sources/storage-engines/rocksdb/db/db_write_test.cc

- **Purpose:** Broad write-path regression suite for RocksDB `DBImpl::WriteImpl`, write-thread batching, WAL flushing/syncing/locking, error propagation, WAL recycling/recovery, and `IngestWriteBatchWithIndex`.
- **Important APIs/types/functions:** Defines parameterized `DBWriteTest : DBTestBase, testing::WithParamInterface<int>` and unparameterized `DBWriteTestUnparameterized`. Key tests include `SyncAndDisableWAL`, `WriteStallRemoveNoSlowdownWrite`, `WriteThreadHangOnWriteStall`, `WriteThreadWaitNanosCounter`, `IOErrorOnWALWritePropagateToWriteThreadFollower`, `PipelinedWriteRace`, `ManualWalFlushInEffect`, `UnflushedPutRaceWithTrackedWalSync`, `InactiveWalFullySyncedBeforeUntracked`, `IOErrorOnWALWriteTriggersReadOnlyMode`, `IOErrorOnSwitchMemtable`, `LockWALInEffect`, `LockWALConcurrentRecursive`, `ConcurrentlyDisabledWAL`, WAL recycle tests, and `IngestWriteBatchWithIndex`. Helper `CorruptLogFile()` rewrites a WAL record header byte range to simulate recovery corruption.
- **Control flow:** The file instantiates write-mode variants (`kDefault`, `kConcurrentWALWrites`, `kPipelinedWrite`). It creates deterministic write-stall and write-group interleavings with `SyncPoint`, spawns `port::Thread`/`std::thread` writers, injects filesystem failures through fault-injection env/fs wrappers, and reopens DBs to validate durable WAL behavior. WAL-lock tests hold recursive locks while parallel Put, Flush, and external-file ingestion block until the final unlock.
- **State and persistence behavior:** Exercises WAL buffers, synced WAL size tracking in MANIFEST, alive/recycled WAL metadata, read-only/background-error state after WAL failures, sequence numbers frozen by `LockWAL`, write-thread linked-list state, and persisted key/value state after crash-style `DropUnsyncedFileData()` or corrupted WAL recovery. It also validates that disabled-WAL writes do not inflate `WAL_FILE_BYTES`.
- **Dependencies:** Uses DB test utilities, `WriteBatchInternal`, `WriteThread`, `FaultInjectionTestEnv`, `FaultInjectionTestFS`, log reader/writer classes, `SstFileWriter`, `WriteBatchWithIndex`, merge operators, perf context, and RocksDB public APIs such as `FlushWAL`, `SyncWAL`, `LockWAL`, `UnlockWAL`, `Resume`, `IngestExternalFile`, and `IngestWriteBatchWithIndex`.
- **Integration points:** Directly targets `DBImplWrite`, `WriteThread` group formation/completion, WAL tracking and manual flush semantics, background error handling after write path I/O failures, external SST ingestion blocking on WAL locks, and write-batch-with-index ingestion constraints.
- **Risks:** Many scenarios are concurrency regressions with busy waits and sync points, so internal ordering changes can make tests flaky or stale. Fault-injection expectations vary with `manual_wal_flush`; tests deliberately branch on option behavior. WAL corruption tests assume current log record layout and point-in-time recovery semantics.
- **Test signals:** Signals include InvalidArgument for sync+disableWAL, OK/Incomplete/NOK results under stalls, perf counter `write_thread_wait_nanos`, leader/follower counts, persisted key visibility after reopen, `WALBufferIsEmpty()`, current log numbers, read-only mode after failure, recursive WAL lock completion flags, WAL byte statistics, and expected corruption during reopen.

# Research: sources/storage-engines/rocksdb/db/dbformat.cc

- **Purpose:** Implementation for RocksDB internal-key encoding helpers, timestamp key transformations, debug formatting, internal-key comparator overloads, lookup-key construction, and `IterKey` buffer growth.
- **Important APIs/types/functions:** Defines constants `kValueTypeForSeek = kTypeValuePreferredSeqno`, `kValueTypeForSeekForPrev = kTypeDeletion`, and `kDisableUserTimestamp`. Implements `GetEntryType`, `AppendInternalKey`, `AppendInternalKeyWithDifferentTimestamp`, `AppendUserKeyWithDifferentTimestamp`, `AppendInternalKeyFooter`, min/max timestamp append/pad/strip/replace helpers, `ParsedInternalKey::DebugString`, `InternalKey::DebugString`, `InternalKeyComparator::Compare` overloads, `LookupKey::LookupKey`, `IterKey::EnlargeBuffer`, and `IterKey::EnlargeSecondaryBufferIfNeeded`.
- **Control flow:** Encoding functions append user-key bytes and then little-endian fixed64 footers produced by `PackSequenceAndType`. Timestamp helpers split the user key at its suffix and insert supplied, min, or max timestamp bytes before adding or preserving the footer. Comparator overloads first compare extracted user keys through `UserComparatorWrapper`; equal user keys are ordered by descending packed sequence/type footer. `LookupKey` builds a memtable lookup record as varint32 length, user key, optional timestamp, and seek footer.
- **State and persistence behavior:** The file does not persist state itself, but it defines byte layouts embedded in memtables, SST data blocks, metadata blocks, WAL lookup records, and debug logs. `IterKey` methods allocate and release heap buffers for large keys, while inline buffers avoid allocations for short keys.
- **Dependencies:** Depends on `db/dbformat.h`, `db/lookup_key.h`, perf context declarations, `port/port.h`, fixed-width coding helpers, and string escaping utilities. It relies on public comparators for user-key ordering and timestamp stringification.
- **Integration points:** Used by table builders/readers, memtable lookups, iterators, write batch parsing, range tombstone serialization, and any component that sorts or displays internal keys. The choice of `kValueTypeForSeek` determines seek sentinel ordering for the whole storage engine.
- **Risks:** Internal-key byte layout is on-disk compatible state; changing type values, footer packing, timestamp placement, or comparator ordering can corrupt ordering/recovery. The min/max timestamp helpers rely on size assertions and may misbehave in release builds if callers pass malformed keys. Debug formatting must avoid leaking redacted keys unless `log_err_key` is intended.
- **Test signals:** Covered by `dbformat_test.cc` encode/decode, short separator/successor, timestamp pad/strip/replace, range tombstone end-key ordering, `IterKey` operations, and version macro tests.

# Research: sources/storage-engines/rocksdb/db/dbformat.h

- **Purpose:** Central declaration and inline implementation file for RocksDB internal key format: value type enumeration, sequence/type packing, parsed and encoded key abstractions, internal comparators, iterator key storage, write-batch record readers, range tombstones, and predecessor WAL metadata.
- **Important APIs/types/functions:** Declares on-disk `ValueType` values, `kMaxSequenceNumber`, `kDisableGlobalSequenceNumber`, `kNumInternalBytes`, `ParsedInternalKey`, `InternalKeyComparator`, `InternalKey`, `IterKey`, `InternalKeySliceTransform`, `RangeTombstone`, `ParsedInternalKeyComparator`, and `PredecessorWALInfo`. Inline functions include `IsValueType`, `IsExtendedValueType`, `PackSequenceAndType`, `UnPackSequenceAndType`, `ParseInternalKey`, `ExtractUserKey`, timestamp extraction/strip helpers, `ExtractInternalKeyFooter`, `ExtractValueType`, `UpdateInternalKey`, `GetInternalKeySeqno`, comparator overloads, and `PredecessorWALInfo::EncodeTo/DecodeFrom`.
- **Control flow:** `ParseInternalKey` validates minimum length, decodes the last eight bytes as packed sequence/type, exposes the leading bytes as `user_key`, and returns corruption for non-extended value types. `InternalKey` owns an encoded string and delegates encoding/decoding to append/parse helpers. `IterKey` tracks whether its current slice is user or internal key, supports pinned external memory or copied inline/heap buffers, reconstructs delta-encoded keys with optional min timestamp insertion, and swaps ownership while preserving pointer provenance.
- **State and persistence behavior:** Value type enum values are explicitly on-disk and must not be renumbered. Internal keys are stored as `<user key | 8-byte packed sequence/type>`, optionally with user-defined timestamps in the user-key suffix. `RangeTombstone` serializes deletion ranges as internal keys plus end-key values and uses max sequence/type sentinels for exclusive end-key ordering. `PredecessorWALInfo` persists three fixed64 fields: log number, size bytes, and last recorded sequence.
- **Dependencies:** Includes RocksDB public comparator/slice/slice-transform/types APIs, coding helpers, and user comparator wrapper. Forward integration exists with write batch record parsing, table index builders, memtable/block iterators, range deletion handling, WAL metadata, and timestamp-aware comparators.
- **Integration points:** This header is foundational across DB format, table, memtable, compaction, iterator, and WAL code. `InternalKeyComparator` enforces global storage ordering, `InternalKeySliceTransform` adapts user prefix extractors to internal keys, and `IterKey` is used in block/data iteration where allocation and pointer lifetime are performance-sensitive.
- **Risks:** On-disk enum changes, footer packing changes, or comparator changes are compatibility-breaking. Many helpers use `assert` for size/type preconditions; release builds rely on upstream validation. `IterKey::Swap` and timestamp reconstruction are pointer/ownership sensitive and can create use-after-free or corruption if modified without exhaustive inline/heap/pinned coverage. `kTypeMaxValid` is allowed in limited contexts, so validation changes must account for range tombstone iterator sentinels.
- **Test signals:** `dbformat_test.cc` exercises internal key parse/encode, comparator-sensitive short separator/successor, `IterKey` inline/heap/pinned/secondary swap, timestamp padding/stripping, update-in-place, range tombstone end-key ordering, and version macro invariants.

# Research: sources/storage-engines/rocksdb/db/error_handler.cc

- **Purpose:** Implements RocksDB background error classification, severity escalation, automatic recovery from no-space and retryable I/O errors, recovery shutdown coordination, quarantine handling for ambiguous MANIFEST edits, and error-handler statistics.
- **Important APIs/types/functions:** Defines severity maps `ErrorSeverityMap`, `DefaultErrorSeverityMap`, and `DefaultReasonMap`. Implements `ErrorHandler::CancelErrorRecoveryForShutDown`, `HandleKnownErrors`, `SetBGError`, `AddFilesToQuarantine`, `ClearFilesToQuarantine`, `OverrideNoSpaceError`, `RecoverFromNoSpace`, `ClearBGError`, `RecoverFromBGError`, `StartRecoverFromRetryableBGIOError`, `RecoverFromRetryableBGIOError`, `CheckAndSetRecoveryAndBGError`, `EndAutoRecovery`, and `RecordStats`.
- **Control flow:** `SetBGError` converts incoming status to `IOStatus`, records counters, handles data-loss and manual-WAL fatal cases, routes retryable/file-scope I/O errors to auto-resume logic, and falls back to `HandleKnownErrors`. `HandleKnownErrors` classifies by reason/code/subcode/paranoid checks, applies no-space overrides, notifies listeners, records the most severe background error, sets recovery context, invokes SstFileManager no-space recovery, and stops DB work for hard errors. Auto-resume starts a recovery thread that loops `ResumeImpl()` with timed waits until success, fatal/shutdown, nonretryable failure, or retry-count exhaustion.
- **State and persistence behavior:** Maintains `bg_error_`, `recovery_error_`, `recovery_in_prog_`, `soft_error_no_bg_work_`, `allow_db_shutdown_`, `end_recovery_`, `is_db_stopped_`, `recover_context_`, `recovery_thread_`, and unsorted `files_to_quarantine_`. It does not write persistent files directly, but controls whether DB writes/background work stop and whether quarantined SST file numbers may be deleted during MANIFEST recovery.
- **Dependencies:** Depends on `DBImpl::ResumeImpl`, DB options/listeners/statistics, `SstFileManagerImpl::StartErrorRecovery/CancelErrorRecovery`, event helper notifications, logging, `InstrumentedMutex`/condvar, `port::Thread`, `IOStatus` metadata such as scope/retryable/data-loss, and background error reason enums.
- **Integration points:** Central path for compaction/flush/write callback/MANIFEST/memtable/async-open errors. It gates write availability, background work scheduling, DB close readiness, SstFileManager no-space recovery, listener callbacks (`OnBackgroundError`, `OnErrorRecoveryEnd`), statistics tickers/histograms, and recovery flush reasons.
- **Risks:** Severity maps are policy-critical; missing reason/code/subcode combinations fall through to broader defaults. Incorrect auto-recovery decisions can either leave a recoverable DB stopped or resume unsafely after WAL/data-loss errors. Recovery thread coordination releases and reacquires DB mutex; shutdown, listener callbacks, and close readiness require careful ordering. Quarantine must be cleared only after successful recovery to avoid deleting files needed for MANIFEST consistency.
- **Test signals:** Directly and indirectly tested by DB write/background-error suites through fatal/read-only transitions, `Resume()`, auto-resume counters, listener notifications, recovery success/failure, no-space handling, retryable I/O behavior, and file-quarantine deletion blocking.

# Research: sources/storage-engines/rocksdb/db/error_handler.h

- **Purpose:** Declares the `ErrorHandler` class and `DBRecoverContext`, which encapsulate RocksDB background-error state, severity policy entry points, recovery lifecycle, DB-stop queries, and quarantined file tracking.
- **Important APIs/types/functions:** `DBRecoverContext` stores `FlushReason flush_reason` and `bool flush_after_recovery`, defaulting to `kErrorRecovery` and false. `ErrorHandler` exposes constructor, `EnableAutoRecovery`, `GetErrorSeverity`, `SetBGError`, `GetBGError`, `GetRecoveryError`, `ClearBGError`, `IsDBStopped`, `IsBGWorkStopped`, `IsSoftErrorNoBGWork`, `IsRecoveryInProgress`, `ReadyForShutdown`, `RecoverFromBGError`, `CancelErrorRecoveryForShutDown`, `EndAutoRecovery`, `AddFilesToQuarantine`, `GetFilesToQuarantine`, and `ClearFilesToQuarantine`.
- **Control flow:** Public methods are called under DB mutex for error setting, recovery, shutdown, and quarantine access. `IsBGWorkStopped` stops background work when an active error is hard-or-worse, auto recovery is disabled, or a soft error requires exclusive recovery work. `ReadyForShutdown` only returns true when recovery is not in progress and listener notification has not temporarily blocked DB close.
- **State and persistence behavior:** Holds references to `DBImpl`, immutable DB options, DB mutex/condition variable, background and recovery status objects, recovery thread, flags for auto recovery/recovery progress/no-bg-work/shutdown, atomic stopped state, statistics pointer, and file numbers quarantined during uncertain MANIFEST recovery. State is in-memory but directly affects durable recovery, flush behavior, and obsolete file deletion safety.
- **Dependencies:** Includes instrumented synchronization, DB options, `IOStatus`, listener/status APIs, and `autovector`. Forward-declares `DBImpl`; private methods integrate with SstFileManager, DB resume, listener notifications, logging, and statistics in the `.cc` implementation.
- **Integration points:** Owned by `DBImpl` to mediate background errors from flush, compaction, writes, MANIFEST writes, memtable operations, and async file opens. It is consulted by write/background scheduling paths to determine stopped state and by close/destructor logic to avoid shutdown while recovery callbacks are active.
- **Risks:** Most public methods assume DB mutex discipline; using them without the lock can race recovery state, quarantine vectors, or close readiness. Severity escalation is monotonic except explicit recovery clearing, so callers must pass accurate reasons/status metadata. The class owns a recovery thread and must join it during shutdown to avoid use-after-free of DBImpl or mutex state.
- **Test signals:** Behavior is observed by tests that inject I/O errors, call `Resume`, check read-only/stopped modes, wait for auto recovery, verify listener callbacks, and ensure quarantined or obsolete files are not deleted prematurely.
