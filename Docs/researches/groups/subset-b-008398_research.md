# sources/storage-engines/foundationdb/contrib/observability_splunk_dashboard/ratekeeper.xml

Purpose: defines a Splunk SimpleXML dark-theme dashboard, "FoundationDB - RateKeeper (Dev)", for diagnosing transaction throttling, Ratekeeper limit decisions, storage/TLog/proxy pressure, transaction trace latency, process resource usage, and inter-role network symptoms.

Important APIs/types/functions: this is declarative Splunk XML rather than program code. Its operational API is the token set in the `<fieldset>` and panel-local inputs: `Index`, `LogGroup`, `TimeSpan`, `UpdateRateTypeToken`, `ChartBinSizeToken`, `ChartByMachineToken`, role filters for process metrics, and source/destination role filters for network panels. The important SPL constructs are `timechart`, `stats`, `eventstats`, `join`, `append`, `rex`, `makemv`, `mvindex`, `bin`, `replace`, and `eval`.

Control flow: Splunk evaluates each panel search independently over the selected index/log group/time range. The top panels aggregate storage and proxy bandwidth, then the dashboard moves through Ratekeeper inputs/outputs (`RkUpdate` or `RkUpdateBatch`), zero-TPS causes, candidate limit metrics, storage/TLog/proxy runtime backpressure, transaction debug latencies, process CPU/memory/disk/network charts, and finally connection timeout/ping latency by selected roles. Panel-local dropdowns alter grouping by injecting fragments such as `by Machine`, `By Machine`, `Step`, or `MachineStep` into SPL.

State and persistence: no application state is persisted by the file. Splunk UI token values and selected time windows are transient dashboard state. All durable information comes from indexed FoundationDB trace events. The dashboard assumes trace fields such as `TrackLatestType`, `Time`, `Machine`, `Role`, rate counters encoded as space-delimited strings, and transaction debug IDs are already extracted.

Dependencies and integration: integrates with FoundationDB trace logging in Splunk, using event types including `StorageMetrics`, `TLogMetrics`, `ProxyMetrics`, `GrvProxyMetrics`, `RkUpdate*`, `ProcessMetrics`, `Role`, `TransactionDebug`, `GetValueDebug`, `CommitDebug`, `TransactionAttachID`, `ConnectionTimedOut`, `ConnectionTimeout`, and `PingLatency`. It spans both pre-7.0 and 7.0+ proxy naming by including master, GRV, and commit proxy role/event forms.

Risks: user-supplied tokens are interpolated directly into SPL, so malformed values can break searches or broaden scope. Some token values are case/wording sensitive (`by Machine`, `By Machine`, `Machine`, `MachineStep`) and can silently change grouping. Several searches depend on costly `join` and broad wildcard location matches, which can be slow on large trace windows. Space-delimited rate fields are parsed by fixed `mvindex` positions, so trace-format changes can corrupt derived rates. Chart 26 computes `_time=T1` even though that query defines `TBegin`/`TEnd`, so its binned commit stats may have a broken time base. Chart titles say severity thresholds in human terms elsewhere in this dashboard family; any edits should keep titles and SPL thresholds synchronized.

Test signals: validation should include Splunk SimpleXML parsing, token default rendering, and sample searches for each event family over a known FDB trace index. Useful smoke tests are: Ratekeeper charts produce rows for `RkUpdate` and `RkUpdateBatch`; storage/TLog queue and free-space charts handle both grouped and ungrouped modes; transaction trace panels return GRV/read/commit latency for known IDs; network panels work after selecting source and destination roles; and searches do not time out on representative production time ranges.

# sources/storage-engines/foundationdb/contrib/observability_splunk_dashboard/recovery.xml

Purpose: defines the "FoundationDB - Long Recovery (Dev)" Splunk dashboard for finding long master recoveries and drilling into recovery causes, recruited roles, TLog state, storage tag popping, timeout distributions, proxy selection, and high-severity events during a selected recovery window.

Important APIs/types/functions: this file is SimpleXML with tables, charts, an event panel, global and panel-local inputs, and one drilldown token. Core tokens include `IndexForOverview`, `LogGroupForOverview`, `time_token_for_recoveryhistorytable`, `Index`, `LogGroup`, `ReoveryTime`, role multiselects (`RolesToken`, timeout source/destination role tokens, `BadEventRoleToken`), `row.TLogID`, `SearchMachineToken`, and time bin tokens. Its SPL uses `stats list(*)`, `eventstats`, `join`, `dedup`, `mvexpand`, `mvcombine`, `set diff`, `replace *:tls`, and date formatting with `strftime`.

Control flow: Table 1 summarizes long recovery candidates from `MasterRecoveryState`, master role transitions, and termination events. Table 2 scopes all following panels to a user-selected recovery time span and groups recovery attempts by master ID and machine. Tables 3-8 explain trigger and recruitment context. Tables 9-15 are TLog-focused and depend on Table 11's cell drilldown setting `row.TLogID`; they show recovery counts, role contacts, detailed TLog events, popped/ready tags, and tag set differences. Tables/charts 16-20 then inspect current storage servers, timeout distributions by source/destination, proxy 0, latest role state for a machine, and severity event distributions.

State and persistence: the dashboard itself is stateless except for Splunk tokens. The only explicit control-flow state is the drilldown token `row.TLogID` populated from Table 11. Persistent data is FoundationDB trace/event data in Splunk; the dashboard derives recovery durations, latest role state, data center mappings, and tag sets at query time.

Dependencies and integration: depends on FoundationDB event schemas for `MasterRecoveryState`, `Role`, `MasterTerminated`, `RecoveryInternal`, `ProxyReplies`, `CommitProxyReplies`, `ResolverReplies`, `MasterRecruitedInitialStorageServers`, `WaitFailureClient`, `MasterRecoveredConfig`, `ProcessMetrics`, TLog lifecycle/rejoin/tag events, `StorageMetrics`, connection timeout events, and severity fields. It integrates with both old and new transaction-role names (`MasterProxyServer` plus `CommitProxyServer`/`GrvProxyServer`).

Risks: several labels contain typos or stale wording (`ReoveryTime`, titles saying severity `>=20` while SPL uses `Severity>10`), which can mislead operators. Table 11's initial SPL has mixed `OR`/`AND` precedence without explicit parentheses around the whole event family, so filters such as `TrackLatestType` and `SeeLogEventDetailTableToken` may not apply to all alternatives as intended. `row.TLogID`-dependent panels return empty or confusing output until the user clicks Table 11. The `set diff` panel warns that abbreviated results containing `...` make Table 15 wrong, indicating cardinality/output limits can affect correctness. Numerous `join` commands and wide `stats list(*)` aggregations can be expensive or lossy on large windows. Assumptions such as "each machine has at most one SS" are embedded in table titles and queries.

Test signals: validate SimpleXML loading in Splunk and run with a known long-recovery trace. Smoke tests should cover Table 1 candidate discovery, Table 2 recovery attempt grouping, Table 11 drilldown populating Tables 9-15, timeout charts after selecting source/destination role filters, storage tag diff behavior on high-cardinality tag sets, and severity tables matching their documented threshold. Query plan/runtime checks are important because multiple panels use nested joins over broad time windows.

# sources/storage-engines/foundationdb/contrib/observability_splunk_dashboard/transaction_latency.xml

Purpose: defines a Splunk dashboard for tracing long latency in ClusterController-issued FoundationDB transactions across GRV, get-value, and commit phases for FDB 6.3 and 7.0+.

Important APIs/types/functions: exposed dashboard tokens are `Index`, `LogGroup`, optional `transactionID`, `time_token`, and drilldown-set tokens `BeginTime`, `EndTime`, `ReadID`, `GrvID`, and `CommitID`. The SPL API centers on attach-ID events (`TransactionAttachID`, `GetValueAttachID`, `CommitAttachID`), debug events (`TransactionDebug`, `GetValueDebug`, `CommitDebug`), `join`, `return`, `stats list`, `eventstats min(Time)`, calculated `Delta`/duration fields, and ordered `case()` maps for known debug locations.

Control flow: the first table finds complete transactions by requiring all three attach IDs, joins each phase to its completion event, computes phase durations and a scoped time range, and sorts by total duration. Its cell drilldown sets the phase IDs and begin/end time tokens. Subsequent panels use those tokens to show ordered GRV events, a 6.3-specific raw committed-version substep, get-value events, full commit events, resolver substeps, and TLog commit substeps grouped by machine and sorted by duration.

State and persistence: the dashboard persists no data. User input and drilldown selections drive all downstream state. The underlying persistent source is trace data indexed in Splunk, and the dashboard assumes timestamps are comparable numeric `Time` fields, IDs are preserved across attach events, and debug locations have stable names.

Dependencies and integration: integrates tightly with FoundationDB transaction tracing instrumentation and version-specific naming. It recognizes native API, proxy, master, resolver, storage server, and TLog location strings. The main table intentionally does not cover getrange operations or operations without commit, so it is scoped to a narrower transaction shape than general client tracing.

Risks: downstream tables are empty until a transaction row is selected. Completeness filtering (`Count=3`) excludes partial, read-only, getrange, or failed flows, which is useful for latency decomposition but can hide important incidents. The ordering logic is hard-coded to exact `Location` strings; trace schema changes or role renames can misorder or drop steps. Some commit ordering strings use `TLogServer.tLogCommit.*` while related dashboards/searches often use `TLog.tLogCommit.*`; version mismatch can leave TLog panels empty. Nested `join` and `return $To` subsearches can hit Splunk subsearch limits for broad `transactionID=*` windows.

Test signals: test with a known complete CC transaction that has GRV, read, and commit attach IDs. Confirm the first table sets all drilldown tokens, the GRV panel shows ordered proxy/master steps for both 6.3 and 7.0+ traces, the get-value panel sorts by the intended location order, commit panels show resolver and TLog duration rows, and narrowing `transactionID` to a single hex ID avoids broad subsearch behavior.

# sources/storage-engines/foundationdb/contrib/pkg_tester/test_fdb_pkgs.py

Purpose: implements pytest-based package validation for FoundationDB Linux packages by installing built `.deb` and `.rpm` artifacts into disposable Docker images and running functional, packaging, backup/restore, client-build, ownership, and executable-stack checks.

Important APIs/types/functions: `run(args)` streams subprocess output and asserts success. `Image` wraps a Docker image ID with `dispose()`. `Container` wraps Docker container lifecycle (`docker run`, `exec`, `cp`, `commit`, `rm -f`) and supports optional systemd-style init arguments. `ubuntu_image_with_fdb_helper(versioned)` and `centos_image_with_fdb_helper(versioned)` locate packages under `$BUILDDIR/packages`, install prerequisites and FDB packages, then commit reusable images. Pytest fixtures expose unversioned/versioned Ubuntu and CentOS images and parametrized `linux_container` values. Tests include `test_db_available`, `test_client_app`, `test_write`, `test_execstack_permissions_libfdb_c`, `test_etc_owner`, and `test_backup_restore`.

Control flow: session fixtures build base images once per package type/platform, yielding `None` if no matching artifacts exist. Each test invocation receives a fresh container derived from the committed image; Ubuntu containers manually start `/etc/init.d/foundationdb`, while CentOS uses `initd=True`. Test bodies execute commands inside containers, compare selected command output to syrupy-style snapshots, and dispose containers/images in `finally` blocks.

State and persistence: the test creates Docker containers and intermediate committed images, writes temporary files inside containers, and uses `/tmp/fdb_backup` for backup/restore. Cleanup removes containers and committed images, but package installation state persists in the committed image for the duration of the test session. It requires external state in `$BUILDDIR/packages` and a working Docker daemon.

Dependencies and integration: depends on pytest, snapshot fixture support, Docker, Ubuntu and `centos:7` images, package manager network access, FoundationDB package artifacts, `fdbcli`, `fdbbackup`, `fdbrestore`, `execstack`, `ldconfig`, `gcc`, `pkg-config`, `cmake`, and the installed FoundationDB C client package config/CMake config. It integrates with FoundationDB build outputs rather than source code directly.

Risks: `run()` reads line-by-line while the process is alive and asserts after the loop; unusual buffering or large output could delay visibility. Docker image/container cleanup is best-effort after successful object creation but failed Docker commands before assignment can leave external resources. Versioned fixture checks in `linux_container` test `ubuntu_image_with_fdb is None` and `centos_image_with_fdb is None` instead of their versioned counterparts, which can skip or mis-handle versioned-only package sets. CentOS 7 and package-manager network dependencies are aging and can make tests flaky. The tests run privileged-ish system services in containers and mount `/sys/fs/cgroup:ro`, so host Docker configuration matters. Snapshot assertions are sensitive to CLI text changes.

Test signals: the file is itself a test suite. Passing signals include all four parametrized container modes either run or skip only when their package type is absent, `fdbcli get/set` succeeds, the sample C client compiles with both pkg-config and CMake, `execstack` output matches the expected non-executable stack snapshot, `/etc/foundationdb` ownership matches the package contract, and backup/restore round-trips key `x`.

# sources/storage-engines/foundationdb/contrib/prx.py

Purpose: provides a command-line helper for FoundationDB maintainers to cherry-pick all commits from a GitHub pull request into the current branch while tracking progress across conflicts.

Important APIs/types/functions: `_silent_subprocess()` runs external commands and returns stripped UTF-8 output. Module constants capture `CURRENT_BRANCH`, `CURRENT_HEAD`, and `GIT_ROOT` at import time. `MergeOperation` owns progress persistence in `.git/__cherrypick_merge.status`, defines the `MergeProgress` dataclass, JSON encoder/object hook, progress read/write/delete helpers, merge-commit detection, merge commit expansion, and single-commit cherry-picking. PR helpers query GitHub CLI JSON (`_get_pull_request_info`), checkout PRs (`_prepare_pull_request`), tag completed PRs (`_tag`), create progress (`_start_merge`), report/abort/continue/drop current cherry-pick state, parse CLI args, and dispatch in `_main()`.

Control flow: `prx.py merge PR [--dry-run]` rejects an existing progress file, fetches PR commit metadata via `gh pr view`, decides whether to use the merge commit's first-parent range or the PR branch commits, writes a progress JSON file, and either reports/drops it for dry run or iteratively cherry-picks commits. On each successful cherry-pick `_continue_merge()` increments `cherry_picked` and rewrites progress. `continue` assumes the current conflicted commit was manually resolved and advances before resuming. `abort` resets the worktree to the saved `merge_on` commit and deletes progress. `status` prints completed and pending commit lists.

State and persistence: persistent state is the JSON progress file in `.git`, plus git history, tags named `cherry-pick-pr-<pr>`, and any in-progress cherry-pick state. The script also mutates the working tree and current branch through `gh pr checkout`, `git checkout`, `git cherry-pick`, `git reset --hard`, and `git tag`.

Dependencies and integration: depends on `git`, GitHub CLI `gh`, network access to `https://github.com/apple/foundationdb`, JSON output shape for `commits`, `mergeCommit`, `headRepository`, and `headRepositoryOwner`, and a clean enough git worktree for cherry-picks/reset. It is FoundationDB-specific through `FDB_BASE_REPOSITORY`.

Risks: import-time git commands fail immediately outside a git repo. `_silent_subprocess()` catches all exceptions and may print `None` rather than captured failing output. `_fetch_upstream` is defined but not used. `_abort_merge()` uses `git reset --hard`, which discards local changes after the saved head. `MergeOperation.cherry_pick_commit()` silently skips merge commits, which can omit intended changes if a PR commit list contains merges. Progress parsing coerces `merge_id` with `str(dct.get("merge_id"))`, turning JSON null into the string `"None"`. `_is_already_committed()` relies on `git branch <branch> --contains <commit>` output length and may be brittle with unexpected branch output. The `continue` command calls `_drop_current_cherrypick()` first, so using it before committing a manual conflict resolution can incorrectly mark a commit as resolved; it only blocks when `.git/CHERRY_PICK_HEAD` still exists.

Test signals: practical validation should use a disposable git clone and mock or sandbox `gh` responses. Tests should cover merge-commit PRs, fast-forward PRs, dry-run cleanup, progress JSON round-trip, conflict/resume behavior, skipped merge commits, tag replacement, status output, and abort behavior. Because the script mutates git state, integration tests need isolated repositories and should assert the progress file and tag state after each action.

# sources/storage-engines/foundationdb/contrib/rapidjson/rapidjson/allocators.h

Purpose: defines RapidJSON's allocator concept plus two concrete allocator implementations used by the parser and DOM: a CRT-backed allocator and a monotonic memory-pool allocator.

Important APIs/types/functions: the documented `Allocator` concept requires `kNeedFree`, `Malloc(size_t)`, `Realloc(void*, size_t, size_t)`, and static `Free(void*)`. `CrtAllocator` wraps `std::malloc`, `std::realloc`, and `std::free`, normalizing zero-size allocation to `NULL`. `MemoryPoolAllocator<BaseAllocator>` exposes constructors for default chunks or a user-supplied first buffer, destructor, `Clear()`, `Capacity()`, `Size()`, `Malloc()`, `Realloc()`, no-op `Free()`, and private `AddChunk()`. Its internal `ChunkHeader` stores capacity, used size, and next pointer.

Control flow: `MemoryPoolAllocator::Malloc()` aligns requested size, lazily allocates a chunk when no head exists or the head lacks capacity, returns memory after the aligned header, and advances the current chunk size. `Realloc()` handles null/new-zero cases, refuses to shrink, expands in place only when the original allocation is the most recent block and capacity permits, otherwise allocates a new block and copies the old bytes without freeing the original. `Clear()` walks allocated chunks and frees all non-user chunks, then resets the user buffer size if present.

State and persistence: allocator state is in-memory only: a singly linked list of chunks, the configured chunk capacity, optional user buffer pointer, and optional owned base allocator. Memory allocated from the pool persists until `Clear()` or destruction; individual `Free()` calls intentionally do nothing when using the pool.

Dependencies and integration: includes `rapidjson.h` for namespace/macros, alignment, assertions, and allocation helpers. It is the default allocator for `GenericValue`/`GenericDocument` in `document.h`, and interacts with parser stack/data structures that rely on amortized append allocation and stable pointers.

Risks: `MemoryPoolAllocator` is monotonic and can retain memory longer than callers expect; `Realloc()` can duplicate live data and leave old blocks stranded until pool reset. The default constructor leaves `baseAllocator_` null until the first `AddChunk()`, but `Clear()` calls `baseAllocator_->Free()` for non-user chunks, so correct operation assumes chunks were only created after `AddChunk()` initialized the base allocator. It is not thread-safe. User-supplied buffers must exceed `sizeof(ChunkHeader)` and remain alive for the allocator lifetime. The closing include-guard comment says `RAPIDJSON_ENCODINGS_H_`, which is stale but not functional.

Test signals: RapidJSON allocator tests should cover zero-size CRT behavior, pool allocation alignment, user-buffer first allocation and non-freeing destruction, chunk growth beyond default capacity, in-place and copying `Realloc()`, `Clear()` capacity/size behavior, and DOM parse/build workloads using both `MemoryPoolAllocator` and `CrtAllocator`.

# sources/storage-engines/foundationdb/contrib/rapidjson/rapidjson/document.h

Purpose: implements RapidJSON's DOM layer: JSON value storage/manipulation (`GenericValue`/`Value`), document parsing as a SAX handler (`GenericDocument`/`Document`), object member iterators, string-reference helpers, typed getter/setter helpers, and array/object facade classes.

Important APIs/types/functions: key types are `GenericMember`, `GenericMemberIterator`, `GenericStringRef`/`StringRef`, `internal::TypeHelper`, `GenericValue<Encoding, Allocator>`, `GenericDocument<Encoding, Allocator, StackAllocator>`, `GenericArray`, `GenericObject`, and typedefs `Value`/`Document`. `GenericValue` provides constructors for null/bool/integer/double/string/object/array, move-style assignment, `CopyFrom`, `Swap`, type predicates, object APIs (`FindMember`, `AddMember`, `RemoveMember`, `EraseMember`), array APIs (`Reserve`, `PushBack`, `PopBack`, `Erase`), numeric/string getters and setters, and `Accept(handler)`. `GenericDocument` adds parse entry points (`ParseStream`, `ParseInsitu`, `Parse` overloads), parse error accessors, allocator/stack access, and SAX handler callbacks.

Control flow: DOM parsing builds values through SAX callbacks on `GenericDocument`. Primitive callbacks placement-new a `ValueType` onto an internal stack. `StartObject`/`StartArray` push empty container sentinels. `Key` delegates to `String`. `EndObject(memberCount)` pops `memberCount` members from the stack and copies them into allocator-owned object storage with `SetObjectRaw`; `EndArray(elementCount)` does the same for elements. On successful parse, exactly one root value is popped and moved into the document. `GenericValue::Accept()` performs the reverse traversal, emitting SAX events recursively to a handler.

State and persistence: values store a compact tagged union `Data` containing flags, string metadata or inline short-string bytes, numeric payload, object member pointer/size/capacity, or array element pointer/size/capacity. Ownership is flag-dependent: constant strings borrow external storage, copy strings own allocator memory or inline short-string storage, arrays/objects own allocator-allocated contiguous buffers. `GenericDocument` owns or borrows a DOM allocator, owns a parse stack, and stores the last `ParseResult`. No disk persistence exists.

Dependencies and integration: includes `reader.h`, `internal/meta.h`, `internal/strfunc.h`, `memorystream.h`, `encodedstream.h`, `<new>`, and `<limits>`. It integrates RapidJSON's SAX reader with DOM storage, allocator implementations from `allocators.h`, stream wrappers, encoding types, parse flags, writer/handler concepts via `Accept()`, and optional C++11/std::string/range-for feature macros.

Risks: many APIs assert rather than return errors for precondition violations such as wrong type, missing object member via `operator[]`, out-of-range array index, or invalid UTF character width. Assignment and `AddMember`/`PushBack` transfer ownership by raw assignment and nulling the source, so using moved-from values incorrectly can surprise callers. Constant string APIs require caller-guaranteed lifetime; misuse produces dangling pointers. Object lookup is linear and equality over objects is O(n^2). `RemoveMember` is constant time but reorders members; `EraseMember` preserves order at linear cost. `memmove`/`memcpy` are used on value/member storage, relying on RapidJSON's controlled move semantics. With `MemoryPoolAllocator::kNeedFree=false`, destructors skip recursive frees, which is intentional but means memory is recovered only with allocator lifetime. `GenericDocument` inherits from `GenericValue` without a virtual destructor, so deleting through a base pointer is unsafe as documented.

Test signals: coverage should include parsing from streams, in-situ buffers, read-only strings with explicit length and alternate encodings; parse error code/offset propagation; deep copy across allocators; short-string and copied-string paths; constant-string lifetime-sensitive paths; object add/find/remove/erase ordering; array reserve/push/pop/erase; numeric flag predicates and lossless conversion checks; `Accept()` round-trips through a writer or clone document; move/swap behavior; and builds with/without optional iterator, std::string, C++11, and pointer-optimization macros.

# sources/storage-engines/foundationdb/contrib/rapidjson/rapidjson/encodedstream.h

Purpose: provides RapidJSON stream adapters that read or write byte streams using a specified UTF encoding, plus auto-detecting UTF input and dynamically selected UTF output wrappers.

Important APIs/types/functions: `EncodedInputStream<Encoding, InputByteStream>` wraps a byte input stream and exposes `Peek()`, `Take()`, and `Tell()` in `Encoding::Ch` units after consuming an optional BOM. A UTF-8 `MemoryStream` specialization skips a UTF-8 BOM and forwards directly. `EncodedOutputStream<Encoding, OutputByteStream>` writes optional BOMs and encoded characters. `AutoUTFInputStream<CharType, InputByteStream>` detects encoding from BOM or RFC 4627 null-byte patterns, exposes `GetType()`, `HasBOM()`, `Peek()`, `Take()`, and `Tell()`. `AutoUTFOutputStream<CharType, OutputByteStream>` selects an output encoding at runtime and writes optional BOMs.

Control flow: static wrappers bind encoding behavior at compile time and delegate character reads/writes to `Encoding::Take`, `TakeBOM`, `Put`, and `PutBOM`. `AutoUTFInputStream` peeks four bytes, consumes BOM bytes when present, otherwise infers UTF-8/16/32 and endian-ness from the first four-byte null pattern, asserts the caller's character type is wide enough for UTF-16/32, selects a function pointer from a table, and keeps a one-character lookahead. `AutoUTFOutputStream` validates the requested `UTFType`, chooses the `Put` function pointer table entry, optionally writes a BOM, and forwards `Put()`/`Flush()`.

State and persistence: stream state is transient: references/pointers to the wrapped byte stream, current decoded character for input streams, selected `UTFType`, function pointer dispatch, and `hasBOM_`. No data is persisted outside bytes consumed from or written to the wrapped stream.

Dependencies and integration: includes `stream.h` and `memorystream.h`, and relies on encoding classes from RapidJSON (`UTF8`, `UTF16LE`, `UTF16BE`, `UTF32LE`, `UTF32BE`), `UTFType`, stream concepts (`Peek`, `Take`, `Tell`, `Peek4`, `Put`, `Flush`), and assertion/static-assert macros. `document.h` uses `EncodedInputStream<SourceEncoding, MemoryStream>` for explicit-length string parsing with encoding conversion.

Risks: write methods on input wrappers and read methods on output wrappers are intentionally unimplemented and assert; calling them in generic code can fail at runtime. Auto-detection needs `Peek4()` support and falls back to the caller-provided default type when insufficient bytes or an unknown null pattern is seen. Character-width suitability is checked only by assertions, so release builds may not protect against too-small `CharType` for UTF-16/32. The UTF-8 `MemoryStream` specialization skips BOM bytes permissively one byte at a time if each expected byte matches, which is fast but not a full validation path. The closing include-guard comment says `RAPIDJSON_FILESTREAM_H_`, which is stale.

Test signals: test static UTF-8/16/32 input and output with and without BOM, auto-detection for each BOM and RFC 4627 null pattern, default fallback when `Peek4()` returns null, `HasBOM()` correctness, `Tell()` advancement after BOM consumption, output BOM emission control, and integration parsing explicit-length buffers through `GenericDocument::Parse<SourceEncoding>(str, length)`.
