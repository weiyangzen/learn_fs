# sources/distributed-fs/ceph-client/drivers/crypto/talitos.c

Purpose: implements the Freescale Integrated Security Engine, also known as SEC/Talitos, as a Linux Crypto API provider. It drives SEC1 and SEC2-style descriptor hardware for AEAD `authenc(...)`, AES/DES/3DES skciphers, message digests/HMACs, and an optional hardware RNG, using device-tree capability masks to register only algorithms the underlying block advertises.

Important APIs and control flow: low-level helpers convert DMA addresses into `struct talitos_ptr`, map/unmap single buffers and scatterlists, allocate extended descriptors, and submit descriptors through `talitos_submit()`. Submission is per-channel: a caller-selected channel owns a software FIFO, `head_lock` protects enqueue, `submit_count` prevents overrunning the hardware fetch FIFO, the descriptor is DMA-mapped, and its physical address is written to `TALITOS_FF/TALITOS_FF_LO`. Interrupt handlers are generated for SEC1/SEC2 topologies, acknowledge ISR bits, mask done interrupts, and schedule tasklets; tasklets call `flush_channel()` to walk completed FIFO entries, unmap descriptors, invoke request callbacks, and release FIFO slots. `talitos_error()` decodes channel status, logs execution-unit status through `report_eu_error()`, either continues SEC2 channels or resets channels/device, and completes affected requests with errors. The hwrng path uses RNGU reset/status/FIFO registers through `talitos_rng_init()`, `talitos_rng_data_present()`, and `talitos_rng_data_read()`.

Crypto request paths build descriptor pointer slots for each operation. `aead_setkey()` parses `crypto_authenc_keys`, maps concatenated auth/encryption keys, and AEAD encrypt/decrypt allocate `talitos_edesc` objects then call `ipsec_esp()`. That function populates HMAC key/data, cipher IV/key/input/output, optional ICV storage, SEC2 link tables or SEC1 bounce buffers, and chooses hardware or software ICV verification callbacks. Skcipher operations validate block alignment, allocate descriptors, set encrypt or inbound header bits, and submit through `common_nonsnoop()`, which maps IV, key, input, output, and IV-out slots. Hash/HMAC operations use `struct talitos_ahash_req_ctx` to preserve MDEU context, buffer partial blocks, handle SHA224 software initialization when hardware lacks SHA224 constants, split oversized SEC1 requests via `sec1_ahash_process_remaining`, and submit one or two chained descriptors through `common_nonsnoop_hash()`.

State and persistence behavior: persistent device state lives in `struct talitos_private`: MMIO bases for global and execution-unit registers, IRQs, channel FIFOs, feature flags, tasklets, registered algorithm list, and RNG registration state. Per-transform state is `struct talitos_ctx`, including selected SEC channel, descriptor-header template, DMA-mapped key material, key lengths, and IV scratch. Per-request state is encoded in `struct talitos_edesc` plus hash request contexts; DMA mappings are created per request and undone in completion callbacks. Hardware state includes channel fetch FIFOs, descriptor done writeback, MDEU hash contexts, RNG FIFO state, and key/IV/output buffers described by DMA pointers. Module removal unregisters algorithms, RNG, IRQs, and tasklets but relies on devm allocation for most private memory.

Dependencies and integration points: depends on Linux Crypto API internal AEAD/skcipher/hash interfaces, `crypto_engine`-independent async callbacks, DMA mapping, scatterwalk/scatterlist helpers, OF platform probing, IRQ mapping, tasklets, PowerPC-style big-endian MMIO helpers, `hwrng`, and descriptor/register definitions from `talitos.h`. Device tree must provide `fsl,num-channels`, `fsl,channel-fifo-len`, `fsl,exec-units-mask`, and `fsl,descriptor-types-mask`; compatibles select feature quirks such as SEC1 format, SEC2.1 hardware auth check, SHA224 hardware init, HMAC acceptance, and SEC3 source link-table extent semantics. Crypto users integrate via `/proc/crypto` names such as `cbc(aes)`, `ctr(aes)`, `authenc(hmac(sha256),cbc(aes))`, `sha256`, and `hmac(sha512)`.

Risks and test signals: risks include subtle SEC1/SEC2 descriptor-format divergence, DMA mapping error paths not consistently checking mapping failures, request FIFO accounting depending on negative `submit_count` initialization, global-channel round-robin assuming power-of-two channel count, software ICV fallback paths needing exact scatter offsets, SEC1 bounce-buffer/chained-descriptor handling for large or partial hash updates, possible request leakage or stale key DMA if transform teardown races active requests, and algorithm registration silently skipping templates when capability masks or feature flags are wrong. There is a likely bug-risk pattern in `current_desc_hdr()`: it dereferences `fifo[iter].desc` while searching without checking for an empty slot. Test signals include probe success with valid DT properties, IRQ topology coverage for one/two interrupt lines, `tcrypt`/crypto self-tests for registered AEAD/skcipher/hash/HMAC algorithms, SEC1 and SEC2 large scatterlist coverage, negative tests for bad ICV returning `-EBADMSG`, RNG registration/readback when RNGU is advertised, device/channel reset recovery after injected descriptor errors, no DMA-API warnings, and removal without tasklet or IRQ use-after-free.

# sources/distributed-fs/ceph-client/drivers/crypto/talitos.h

Purpose: defines the Talitos/SEC descriptor ABI, software request/channel/private data structures, feature bits, register offsets, and descriptor-header constants consumed by `talitos.c`.

Important APIs and types: `struct talitos_ptr` models a hardware descriptor pointer in SEC2 format with length, jump/extent byte, extended address byte, and low pointer, or SEC1 format with `len1`. `struct talitos_desc` contains the high/low header words, seven pointer slots, and a SEC1 `next_desc`. `struct talitos_edesc` extends a hardware descriptor with source/destination scatter counts, IV DMA address, link-table DMA metadata, and a flexible link-table or SEC1 bounce-buffer area. `struct talitos_request` stores the in-flight descriptor DMA address and callback. `struct talitos_channel` holds each channel's MMIO base, software FIFO, head/tail locks, FIFO indices, and atomic submit counter. `struct talitos_private` is the whole device state: global and execution-unit register bases, IRQs, locks, geometry/capability fields, channels, tasklets, algorithm list, and hwrng data. `has_ftr_sec1()` resolves SEC1 behavior from build options and runtime feature bits.

Control flow encoded by constants: global register definitions cover master reset/remap, interrupt mask/status/clear, channel base/stride, channel config/status/fetch FIFO/current descriptor/descriptor-buffer registers, and execution-unit bases for SEC1.0, SEC1.2, and SEC2. Descriptor bits select primary and secondary execution units, modes for AES/DEU/MDEU, HMAC/pad/init/continue/auth-check behavior, direction, done notification, descriptor type, and link-table jump/return markers. Macros such as `DESC_TYPE()`, `PRIMARY_EU()`, and `SECONDARY_EU()` let probe-time code compare algorithm templates against DT capability masks.

State and persistence behavior: the header itself owns no mutable state but fixes the binary layout of DMA descriptors and the in-memory driver state used by interrupt handlers, tasklets, Crypto API callbacks, and hwrng code. Endianness annotations and `cpu_to_be32()` constants are part of the hardware contract; changing them would alter on-wire descriptor values. Feature flags persist in `talitos_private.features` and gate runtime paths for SEC1, hardware auth check, SHA224 hardware init, HMAC support, and source link-table extent rules.

Dependencies and integration points: depends on Linux types such as `__be32`, `dma_addr_t`, `scatterlist`, `tasklet_struct`, `hwrng`, atomics, spinlocks, and flexible-array helpers. It is tightly integrated with Freescale/NXP SEC hardware documentation and with the Crypto API templates in `talitos.c`.

Risks and test signals: risks include layout drift breaking DMA descriptors, SEC1/SEC2 union misuse, big-endian constant mistakes, feature-bit mismatches versus compatible strings, and register-offset assumptions that vary by SEC revision. Test signals are successful compilation for `CONFIG_CRYPTO_DEV_TALITOS1`, `CONFIG_CRYPTO_DEV_TALITOS2`, and combined builds; correct descriptor sizes; hardware completion writeback to `DESC_HDR_DONE`; capability filtering matching DT masks; and no sparse/endian warnings in descriptor construction.

Test signals include clean module linkage, presence of all four objects in `tegra-se.o`, and successful registration on both `nvidia,tegra234-se-aes` and `nvidia,tegra234-se-hash` compatibles.

# sources/distributed-fs/ceph-client/drivers/crypto/tegra/tegra-se-aes.c

Purpose: implements NVIDIA Tegra Security Engine AES-family algorithms: skcipher `cbc(aes)`, `ecb(aes)`, `ctr(aes)`, `xts(aes)`, AEAD `gcm(aes)` and `ccm(aes)`, and ahash-style `cmac(aes)`.

Important APIs and control flow: skcipher state is held in `struct tegra_aes_ctx` and per-request `struct tegra_aes_reqctx`. `tegra_aes_setkey()` and `tegra_xts_setkey()` validate AES/XTS keys, try to insert them into SE keyslots, and cache key bytes for later reserved-slot insertion if normal allocation fails. `tegra_aes_crypt()` validates request length, marks encrypt/decrypt, and queues to the shared crypto engine. `tegra_aes_do_one_req()` copies the request scatterlist to a coherent buffer, pads non-XTS hardware input to block size, prepares config and crypto config, ensures keyslot IDs, emits a host1x command stream with `tegra_aes_prep_cmd()`, waits for host1x completion, updates CBC/CTR IVs, copies output back, invalidates reserved keyslots, and finalizes the skcipher request.

AEAD control flow decomposes authenticated modes into several SE jobs. GCM initializes IV words from the 96-bit GCM nonce, optionally runs `tegra_gcm_do_gmac()` over AAD, runs `tegra_gcm_do_crypt()` over payload, runs `tegra_gcm_do_final()` to generate a 128-bit tag, and verifies tags in software on decrypt with `crypto_memneq()`. CCM validates the RFC3610/NIST IV format, zeroes the counter field, formats B0/AAD/plaintext blocks in `tegra_ccm_format_blocks()`, computes CBC-MAC with `tegra_ccm_compute_auth()`, then encrypts/decrypts payload and tag through CTR in `tegra_ccm_do_ctr()`, with decrypt doing CTR before MAC verification. CMAC uses `struct tegra_cmac_reqctx` to stage update/final tasks, preserve intermediate result registers across updates, reserve the last block for finalization, and uses a shash fallback for zero-length digest edge cases.

State and persistence behavior: transform state stores keyslot IDs, cached key bytes, key length, algorithm ID, IV size, auth size, and fallback shash for CMAC. Request state stores coherent input/output buffers, scatterlist pointers, lengths, operation config words, IV/counter words, temporary auth data, residue buffers, and saved CMAC result registers. Hardware state is in SE keyslots, result registers, linear counter registers, and host1x command execution; normal keyslots persist across transform lifetime until `cra_exit`, while reserved keyslots 14/15 are overwritten after each fallback use. The code copies all request data through DMA-coherent bounce buffers rather than mapping caller scatterlists directly.

Dependencies and integration points: depends on `tegra-se.h` register/opcode/key APIs, the shared `tegra_se_host1x_submit()`, crypto engine registration/finalization, Linux AES/GCM/XTS helpers, scatterwalk copy helpers, coherent DMA allocation, result-register MMIO reads/writes, and keyslot management from `tegra-se-key.c`. `tegra_init_aes()` sets the KAC manifest callback, registers skcipher, AEAD, and CMAC algorithms, and unwinds partial registration on failure; `tegra_deinit_aes()` unregisters them.

Risks and test signals: risks include several error-path issues: `tegra_aes_setkey()`, `tegra_xts_setkey()`, and `tegra_aead_setkey()` return success even when key insertion fails, relying on cached-key reserved-slot fallback later; `tegra_ccm_do_one_req()` appears to pass `outbuf` to the inbuf free call and `inbuf` to the outbuf free call, which is a serious DMA-free mismatch; GCM allocates zero-sized buffers when both AAD/payload are absent; CMAC export/import copies DMA pointers and transient buffer addresses, making imported state unsafe across lifetimes; command-buffer sharing relies on crypto-engine serialization; and bounce-buffer allocation caps/size checks are limited despite `SE_MAX_MEM_ALLOC`. Test signals include crypto self-tests for AES modes, XTS key validation, GCM/CCM tag verification failures returning `-EBADMSG`, empty CMAC using fallback correctly, DMA-API debug for CCM frees, repeated setkey/exit invalidating slots, IV copyback for CBC/CTR, large scatterlist requests, and host1x timeout/error paths finalizing requests exactly once.

# sources/distributed-fs/ceph-client/drivers/crypto/tegra/tegra-se-hash.c

Purpose: implements NVIDIA Tegra Security Engine hash and HMAC algorithms for SHA1, SHA224, SHA256, SHA384, SHA512, SHA3-224, SHA3-256, SHA3-384, SHA3-512, and HMAC-SHA224/256/384/512.

Important APIs and control flow: `struct tegra_sha_ctx` stores the SE device, algorithm ID, fallback state, keyslot ID, and fallback ahash transform. `struct tegra_sha_reqctx` stores scatter source, coherent data/residue/digest/intermediate-result buffers, algorithm/config fields, total length, block size, task bits, keyslot ID, saved result registers, and embedded fallback request. `tegra_sha_get_config()` maps algorithm IDs to SHA/HMAC config words. Public hash operations set task bits and queue to the crypto engine unless `ctx->fallback` is active, in which case they delegate to the fallback ahash. `tegra_sha_do_one_req()` processes queued init/update/final phases: init allocates digest, residue, and intermediate-result DMA buffers; update keeps a final block as residue, copies processable bytes into a coherent buffer, emits a host1x command via `tegra_sha_prep_cmd()`, and stores intermediate output; final processes residue, submits the last command, copies the digest to the caller, and frees buffers.

Command preparation programs message length and message-left registers, adds one extra byte to non-final update lengths so hardware does not treat them as final, writes either hash-init or previously saved HASH_RESULT registers, programs source and destination DMA addresses, optionally selects an HMAC keyslot, starts the operation, and appends a syncpoint increment. `tegra_se_insert_hash_result()` handles result-register byte-order quirks, including SHA384/SHA512 word-pair swapping and big-endian conversion for SHA1/SHA2 intermediate values. HMAC setkey uses SE keyslots only for AES-sized key lengths accepted by `aes_check_keylen()`; other key lengths switch the transform to a software fallback.

State and persistence behavior: per-transform fallback mode persists after `tegra_hmac_setkey()` until another successful hardware key submission clears it. Hardware HMAC keys persist in SE keyslots until `tegra_sha_cra_exit()` invalidates them. Per-request hardware state is stored in coherent buffers and in saved `HASH_RESULT` snapshots; these are allocated at init and freed on final, making init/update/final sequencing important. Export/import for hardware mode copies the whole request context, including DMA buffer pointers, which is fragile if used outside a live request lifetime.

Dependencies and integration points: depends on `tegra-se.h` register definitions, host1x command submission, crypto engine ahash registration, Linux SHA/SHA3 constants, scatterwalk copy helpers, coherent DMA, fallback ahash allocation with `CRYPTO_ALG_NEED_FALLBACK`, and keyslot insertion from `tegra-se-key.c`. `tegra_init_hash()` installs the hash KAC manifest callback and registers every `tegra_hash_algs` entry; `tegra_deinit_hash()` unregisters them. Runtime selection is used by the `nvidia,tegra234-se-hash` compatible in `tegra-se-main.c`.

Risks and test signals: risks include HMAC hardware support being limited to AES key lengths rather than normal HMAC arbitrary key lengths, fallback state being transform-global and therefore sensitive to setkey ordering, export/import copying DMA addresses, zero-length hash behavior depending on final path with `datbuf.size == 0`, unbounded coherent allocation proportional to update size, no direct scatterlist DMA mapping, and correctness dependence on SHA result-register byte ordering. Test signals include KATs for all SHA/SHA3 algorithms, HMAC tests with 16/24/32-byte keys using hardware and non-AES-sized keys using fallback, incremental update/final tests with block-boundary residues, export/import tests, host1x timeout handling, DMA-API checks, and digest byte order for SHA384/SHA512.

# sources/distributed-fs/ceph-client/drivers/crypto/tegra/tegra-se-key.c

Purpose: manages NVIDIA Tegra SE keyslots and key insertion command streams shared by AES, AEAD, CMAC, and HMAC code.

Important APIs and control flow: global keyslot state is a `u16` bitmap protected by `kslt_lock`; keyslot 0 and reserved slots 14/15 are pre-marked unavailable for normal allocation. `tegra_keyslot_alloc()` finds the first zero bit with `ffz()`, marks it in use, and returns 0 on exhaustion. `tegra_keyslot_free()` clears a bit. `tegra_key_prep_ins_cmd()` emits a host1x command stream that stalls/dummies the SE op register, writes a key manifest, selects a destination slot, writes each 32-bit key word through key address/data registers, configures insert mode, starts the operation, and appends a syncpoint increment. `tegra_key_insert()` serializes command-buffer use under `kslt_lock` and submits the keybuf through `tegra_se_host1x_submit()`.

State and persistence behavior: `tegra_se_keyslots` persists module-wide across all SE instances, not per device. Normal allocated keyslots remain occupied until transform exit calls `tegra_key_invalidate()`, which overwrites the slot with zeros and frees the bit. Reserved keyslots are overwritten by `tegra_key_invalidate_reserved()` but are never freed for normal allocation. `tegra_key_submit()` reuses an existing valid slot if the caller's `keyid` is already allocated; otherwise it allocates a slot before insertion. If insertion fails after allocation, the allocated bit is not freed in this file.

Dependencies and integration points: depends on host1x opcode helpers and register offsets in `tegra-se.h`, AES key-size constants for zeroing with `AES_MAX_KEY_SIZE`, and the device-specific `se->manifest()` callback installed by AES or hash initialization. AES uses normal and reserved submit helpers, while hash/HMAC uses normal key submission and key invalidation.

Risks and test signals: risks include global keyslot accounting across multiple SE devices, allocation leaks when insertion fails, `tegra_keyslot_free()` accepting reserved or invalid slots without validation, key casting to `u32 *` assuming alignment and native word order, no keylen multiple-of-4 guard in this file, serialized key insertion reusing a shared keybuf, and returning 0 as both exhaustion sentinel and reserved slot number. Test signals include repeated setkey/exit cycles leaving the bitmap at reserved-only state, failure injection for host1x key insertion, concurrent transforms across AES/hash devices, reserved-slot fallback overwrite behavior, invalid key length rejection by callers, and KAC manifest values for ENC/XTS/GCM/CMAC/HMAC purposes.

# sources/distributed-fs/ceph-client/drivers/crypto/tegra/tegra-se-main.c

Purpose: provides the platform, host1x, DMA command-buffer, and hardware-descriptor glue for the NVIDIA Tegra Security Engine crypto driver.

Important APIs and control flow: command buffers are wrapped as `host1x_bo` objects by `tegra_se_cmdbuf_ops`. `tegra_se_host1x_bo_alloc()` allocates a DMA buffer from the parent device, initializes refcounted BO state, and returns it for command or key streams. Pin/unpin convert the coherent buffer to an sg table, DMA-map it for host1x, and expose the physical address to the job. `tegra_se_host1x_submit()` allocates a serialized host1x job, attaches a gather from the command BO, pins/submits it, waits indefinitely for the syncpoint end value, and releases the job.

Probe flow allocates `struct tegra_se`, maps MMIO, sets a 39-bit coherent DMA mask, enables the device clock, reads the IOMMU stream ID, programs `SE_STREAM_ID`, creates and starts a `crypto_engine`, and registers a host1x client. Host1x client initialization requests a channel and syncpoint, allocates 4 KiB command and key buffers, then calls the hardware-specific `init_alg()` callback. Compatible data selects either Tegra234 AES registers/class `0x3b` and `tegra_init_aes()`, or Tegra234 hash registers/class `0x3d` and `tegra_init_hash()`. Module init registers a host1x driver first and the platform driver second; module exit unregisters both.

State and persistence behavior: persistent per-device state includes host1x client/channel/syncpoint, shared command/key buffers, crypto engine, clock, stream ID, MMIO base, owner ID, and hardware data. Command buffers are reused across queued crypto requests and key insertions; correctness depends on crypto-engine serialization and keyslot mutex serialization. Host1x completion is synchronous from each crypto-engine worker. Removal exits the crypto engine and unregisters the host1x client; client deinit unregisters algorithms and releases buffers/channel/syncpoint.

Dependencies and integration points: depends on platform DT compatibles `nvidia,tegra234-se-aes` and `nvidia,tegra234-se-hash`, host1x client/job/syncpoint APIs, Tegra IOMMU stream ID lookup, Linux clocks, coherent DMA, crypto engine, and register definitions from `tegra-se.h`. AES/hash/key files call `tegra_se_host1x_submit()` to execute generated command streams.

Risks and test signals: risks include `tegra_se_host1x_bo_alloc()` leaking the wrapper if DMA allocation fails, `tegra_se_host1x_submit()` returning on syncpoint wait timeout without unpinning or putting the job, command/key buffer size fixed at 4 KiB with no explicit command length bound, `map->chunks = err` after successful `dma_map_sgtable()` leaving zero chunks, removal ordering where crypto engine exit occurs before host1x client unregister, and host1x client registration ignoring a return value. Test signals include platform probe for both compatibles, stream ID programmed correctly, host1x job pin/submit/wait success, timeout/error injection without leaked jobs, algorithm registration during client init, request serialization under load, module unload after active requests, and DMA mask/IOMMU operation above 32-bit addresses.

# sources/distributed-fs/ceph-client/drivers/crypto/tegra/tegra-se.h

Purpose: defines the shared NVIDIA Tegra Security Engine register map, bitfield helpers, algorithm IDs, device/register descriptors, runtime context structures, key APIs, host1x submission API, reserved keyslot helpers, and host1x opcode encoders.

Important APIs and types: register constants cover SE ownership, stream ID, SHA registers, AES0/AES1 registers, config/mode fields, key destination/address/data/manifest registers, AAD/message length, result registers, last-block fields, operation bits, KAC manifest fields, address-high encodings, and composite config templates for AES/GCM/CMAC/CBC-MAC/SHA operations. `enum se_aes_alg` and `enum se_hash_alg` define internal algorithm IDs. `struct tegra_se_alg` wraps crypto-engine algorithm unions. `struct tegra_se_regs` abstracts AES versus hash register offsets. `struct tegra_se_hw` carries compatible-specific register tables, host1x class, KAC version, and algorithm init/deinit callbacks. `struct tegra_se` is the per-device runtime object. `se_algname_to_algid()` maps Linux Crypto API names to internal IDs. Inline helpers select reserved keyslots 14/15, test reserved status, and encode host1x opcodes.

State and persistence behavior: the header owns no mutable state but fixes every cross-file ABI in the Tegra SE driver. Runtime state in `struct tegra_se` persists across crypto requests and includes shared command buffers, crypto engine, host1x resources, MMIO base, stream ID, owner ID, and manifest callback. Register macros define how command buffers program persistent hardware state such as keyslots, result registers, counters, and stream routing.

Dependencies and integration points: depends on Linux bitfield, IOMMU, host1x, crypto AEAD/engine/hash/SHA/skcipher headers, and constants such as `SZ_4M`. It is consumed by all Tegra SE source files and exposes the symbols implemented in `tegra-se-aes.c`, `tegra-se-hash.c`, `tegra-se-key.c`, and `tegra-se-main.c`.

Risks and test signals: risks include duplicate `SE_CRYPTO_CFG_XTS_DECRYPT` definitions, algorithm-name mapping drift versus registered `cra_name` strings, host1x opcode encoders lacking range checks, address-size fields assuming requested lengths fit 24 bits, register table omissions such as unused `out_addr`, and all callers relying on native-endian command words. Test signals include compile coverage for all users, crypto algorithm init mapping every registered name, command traces matching hardware docs, static checks for duplicate macros, XTS/GCM/CCM/CMAC register programming tests, and operation with IOVA addresses needing high address bits.

# sources/distributed-fs/ceph-client/drivers/crypto/ti/Makefile

Purpose: declares the build composition for the TI DTHE V2 crypto driver.

Important APIs and control flow: when `CONFIG_CRYPTO_DEV_TI_DTHEV2` is enabled, the build produces `dthev2.o` from `dthev2-common.o` and `dthev2-aes.o`.

State and persistence behavior: no runtime state exists here; it controls link-time aggregation of common DTHE V2 support and AES-mode implementation code.

Dependencies and integration points: depends on the Kconfig symbol in the same directory and on the implementation objects exporting a complete module entry/registration path between common and AES files.

Risks and test signals: risks include unresolved symbols if common/AES object ownership is split incorrectly, future hash/RNG support requiring Makefile updates, and stale object names if implementation files are renamed. Test signals include clean module or built-in linkage for `CONFIG_CRYPTO_DEV_TI_DTHEV2=y/m` and modpost showing a single `dthev2` module from both objects.
