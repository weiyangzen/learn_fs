# sources/distributed-fs/beegfs-protobuf/go/flex/flex_protoopaque.pb.go

Purpose: generated Go protobuf bindings for `flex.proto` under the `protoopaque` build tag. The file defines the opaque API for Flex worker-node control messages used by BeeGFS/BeeRemote style distributed filesystem workflows: heartbeat, node stats, work submission and update, job configuration, remote storage target configuration, capability discovery, and the `WorkerNode` service descriptor. It is not hand-authored business logic; its purpose is to give Go callers typed construction, mutation, reflection, and wire serialization for the schema.

Important APIs/types/functions: the top-level enums are `UpdateWorkRequest_NewState`, `BulkUpdateWorkRequest_NewState`, `SyncJob_Operation`, `Work_State`, and `UpdateConfigResponse_Result`. The main RPC envelope messages are `HeartbeatRequest`, `HeartbeatResponse`, `SubmitWorkRequest`, `SubmitWorkResponse`, `UpdateWorkRequest`, `UpdateWorkResponse`, `BulkUpdateWorkRequest`, `BulkUpdateWorkResponse`, `UpdateConfigRequest`, `UpdateConfigResponse`, `GetCapabilitiesRequest`, and `GetCapabilitiesResponse`. Work modeling centers on `WorkRequest`, `Work`, `WorkRequest_Segment`, `Work_Status`, `Work_Part`, `JobRequestCfg`, `JobLockedInfo`, `SyncJob`, `MockJob`, and `BuilderJob`. Configuration modeling centers on `BeeRemoteNode`, `RemoteStorageTarget`, `RemoteStorageTarget_Policies`, `RemoteStorageTarget_S3`, `RemoteStorageTarget_Azure`, `RemoteStorageTarget_POSIX`, `RemoteStorageTarget_S3_StorageClass`, and `RemoteStorageTarget_S3_StorageClass_Archival`. Each message has generated `Reset`, `String`, `ProtoMessage`, `ProtoReflect`, getter, setter, `Has...`, `Clear...`, and builder APIs where applicable.

Control flow: this file has no application-level control loop. Runtime flow is generated protobuf behavior: enum `String`, `Descriptor`, `Type`, and `Number` methods delegate to `protoimpl`/`protoreflect`; message `Reset` zeroes the struct and stores `MessageInfo`; `ProtoReflect` lazily attaches message info; getters return zero values on nil receivers; setters mutate hidden fields; `Has...` checks pointer, oneof, or explicit-presence state; `Clear...` removes pointers, oneof alternatives, or explicit-presence bits. The only initialization path is `init() -> file_flex_proto_init()`, which guards on `File_flex_proto != nil`, registers oneof wrapper types for `JobRequestCfg`, `WorkRequest`, `SyncJob`, `RemoteStorageTarget`, and `RemoteStorageTarget_S3_StorageClass`, then builds the `protoreflect.FileDescriptor` with `protoimpl.TypeBuilder`.

State and persistence behavior: all persistent semantics are on the protobuf wire and in caller-owned message instances. The generated structs keep state in opaque `xxx_hidden_...` fields plus `unknownFields`, `sizeCache`, and sometimes `XXX_presence`. Optional scalar fields such as `JobRequestCfg.update`, `tagging`, `priority`, `storage_class`, `allow_restore`, `filter_expr`, `WorkRequest.priority`, and `SyncJob` optionals use `XXX_presence` bits so callers can distinguish "unset" from explicit zero/false/empty string. Repeated fields such as `Work.parts`, `UpdateConfigRequest.rsts`, and `RemoteStorageTarget_S3.storage_class` are represented as hidden pointers to slices in the opaque API. Map fields include metadata and capability trees. There is no disk persistence in this file.

Dependencies: imports are limited to Go protobuf runtime packages (`google.golang.org/protobuf/reflect/protoreflect`, `google.golang.org/protobuf/runtime/protoimpl`), timestamp support (`google.golang.org/protobuf/types/known/timestamppb`), and `reflect`. The schema's time-bearing fields depend on `google.protobuf.Timestamp`: `NodeStats.timestamp`, `JobLockedInfo.mtime`, `JobLockedInfo.remote_mtime`, `GetCapabilitiesResponse.start_timestamp`, and license-independent work/config timestamps.

Integration points: the raw descriptor includes one service, `WorkerNode`, with unary methods `UpdateConfig`, `Heartbeat`, `SubmitWork`, `UpdateWork`, `BulkUpdateWork`, and `GetCapabilities`. `UpdateConfigRequest` sends a `BeeRemoteNode` plus the complete set of configured `RemoteStorageTarget` entries; omitted RSTs are semantically deleted by consumers. `WorkRequest` uses a oneof for request type (`MockJob`, `SyncJob`, or `BuilderJob`), allowing one work envelope to carry mock/testing, sync, or builder work. `RemoteStorageTarget` uses a oneof for storage backend (`S3`, `POSIX`, `Azure`, or `mock`). Comments note that new RST types also need registration in the `rst.SupportedRSTTypes` map outside this generated file so config unmarshalling can map protobuf data into Go structs. Capability discovery integrates through nested `Feature` maps and `BuildInfo`.

Domain behavior encoded in types: `Work_State` documents the lifecycle from `CREATED` to `SCHEDULED`, `RUNNING`, `RESCHEDULED`, transient `ERROR`, terminal `FAILED`, `CANCELLED`, or `COMPLETED`, plus `UNKNOWN` for cases where BeeRemote cannot determine worker state. `UpdateWorkRequest` currently only supports `CANCELLED` as a meaningful state. `BulkUpdateWorkRequest` supports `UNCHANGED` and is described as primarily useful during initial node connection or node drain. `Work_Part` carries part number, byte offsets, ETag, SHA-256 checksum, and completion flag for parallel transfer integrity. S3 configuration encodes endpoint, partition, region, bucket, access key, secret key, and optional storage classes, including archival retrieval tier, retention days, polling times, and auto-restore behavior. `BeeRemoteNode` carries network address, management address, TLS certificate and TLS bypass flags, proxy flag, auth secret, and auth-disable flag.

Risks: this file is generated, so direct edits would be overwritten and should instead be made in `flex.proto` and regenerated. The opaque build tag hides fields; code that accesses exported struct fields from non-opaque generated variants will not compile with this file selected. Sensitive configuration values (`BeeRemoteNode.auth_secret`, S3 `access_key` and `secret_key`, management TLS settings, and TLS/auth disable flags) can be serialized, logged through protobuf stringification, or retained in memory if callers are careless. Presence-sensitive options require `Has...` checks; using only getters loses the distinction between unset and explicitly false/zero/empty values. Oneof builders assign alternatives sequentially, so if multiple alternatives are non-nil the last assignment wins. The schema itself does not enforce RST/job compatibility, valid time duration strings, valid endpoint formats, legal state transitions, segment bounds, part ordering, or credential safety.

Test signals: generated-code correctness is best validated by regeneration from `flex.proto`, `go test` for packages importing the `flex` package under `-tags protoopaque`, wire-compatibility tests that marshal/unmarshal representative messages, and service integration tests that exercise `WorkerNode` RPCs. Important behavioral test cases include optional presence round trips, oneof selection and clearing, RST config replacement semantics, capability map nesting, terminal work states, and sensitive byte/string fields surviving serialization without unintended nil/empty conversions. Because setters for bytes normalize nil to empty slices in some cases, tests should check nil-vs-empty expectations where callers depend on them.

# sources/distributed-fs/beegfs-protobuf/go/license/license.pb.go

Purpose: generated Go protobuf bindings for `license.proto` under the `!protoopaque` build tag. This is the hybrid/non-opaque variant for BeeGFS license certificate verification data. It exposes public struct fields while still providing generated builder, getter, setter, presence, reflection, and wire-serialization behavior.

Important APIs/types/functions: enums are `VerifyResult` and `CertType`. `VerifyResult` has `VERIFY_UNSPECIFIED`, `VERIFY_ERROR`, `VERIFY_VALID`, and `VERIFY_INVALID`. `CertType` models `CERT_TYPE_UNSPECIFIED`, CA root, CA intermediate, partner, enterprise, trial, and community certificates. Messages are `VerifyCertResult`, `VerifyFeatureResult`, `GetCertDataResult`, and `CertData`. Each enum has `Enum`, `String`, `Descriptor`, `Type`, and `Number`. Each message has generated `Reset`, `String`, `ProtoMessage`, `ProtoReflect`, `Get...`, `Set...`, optional `Has...`/`Clear...`, and a builder type.

Control flow: there is no custom verification logic here; result production happens in callers or libraries that populate these messages. Generated control flow follows protobuf runtime conventions. `Reset` zeroes messages and stores message metadata. `ProtoReflect` returns reflection metadata, lazily storing message info if needed. Getters tolerate nil receivers and return schema default values. Setters assign public fields directly. `HasData`, `HasValidFrom`, `HasValidUntil`, and `HasParentData` check pointer presence, and corresponding clear methods nil those fields. `init() -> file_license_proto_init()` builds the descriptor once, registers the `CertData.parent_data` optional/oneof wrapper metadata, and releases raw descriptor/type dependency slices after build.

State and persistence behavior: state is held entirely in caller-owned protobuf message instances and on the protobuf wire. The hybrid structs expose data fields directly: result enums, serial/message strings, nested `CertData`, timestamp pointers, DNS name slices, and recursive parent certificate data. `unknownFields` and `sizeCache` support protobuf runtime behavior. There is no file or database persistence in this generated file. The `parent_data` field is encoded as a proto3 optional/oneof-style presence field, so absence and an explicitly supplied nested certificate can be distinguished.

Dependencies: imports are `protoreflect`, `protoimpl`, `timestamppb`, and `reflect`. The only external schema dependency is `google.protobuf.Timestamp` for `CertData.valid_from` and `CertData.valid_until`.

Integration points: this package is the wire contract between BeeGFS license generation/verification code and Go consumers. `VerifyCertResult` reports certificate verification status, a string serial on success, and an error/status message for error or invalid results. `VerifyFeatureResult` reports feature validation with a message. `GetCertDataResult` returns the currently loaded certificate's simplified data, even when verification failed, plus status. `CertData` is a simplified `x509.Certificate` projection with BeeGFS-specific certificate type, integer serial, subject attributes, common-name/subject-serial strings, validity range, DNS names that encode licensed features, CA flag, and optional recursive parent/issuer data.

Risks: this is generated code, so manual edits should be avoided. The hybrid build exposes fields publicly; callers can bypass setters and create partially inconsistent messages. The file does not validate certificate chains, feature names, validity periods, DNS-name semantics, enum correctness, serial uniqueness, or parent recursion depth. Recursive `ParentData` can create large trees and, if constructed with cycles in memory, may stress generic traversal/logging code. Timestamp pointers require nil checks through `HasValidFrom` and `HasValidUntil`. Error/status messages may include verification details that should not be logged blindly in sensitive environments.

Test signals: useful tests are marshal/unmarshal round trips for all four messages, enum string/name/value checks, nil receiver getter behavior, `ParentData` presence and clearing, timestamp conversion, and compatibility tests against the opaque build variant. Higher-level license tests should verify that `VERIFY_ERROR`, `VERIFY_VALID`, and `VERIFY_INVALID` map consistently to message/serial/data population rules, especially the documented behavior that certificate data can be present even when verification failed.

# sources/distributed-fs/beegfs-protobuf/go/license/license_protoopaque.pb.go

Purpose: generated Go protobuf bindings for `license.proto` under the `protoopaque` build tag. It represents the same BeeGFS license verification schema as `license.pb.go`, but uses the opaque API style: message fields are hidden behind generated getters, setters, presence checks, clear methods, builders, and reflection.

Important APIs/types/functions: the schema surface matches the non-opaque file: `VerifyResult`, `CertType`, `VerifyCertResult`, `VerifyFeatureResult`, `GetCertDataResult`, and `CertData`. The main API difference is structural: message fields are named `xxx_hidden_...` and should be accessed through `GetResult`, `SetResult`, `GetSerial`, `SetSerial`, `GetData`, `SetData`, `HasData`, `ClearData`, `GetParentData`, `SetParentData`, `HasParentData`, and related methods. Builder types (`VerifyCertResult_builder`, `VerifyFeatureResult_builder`, `GetCertDataResult_builder`, `CertData_builder`) provide construction without direct field access.

Control flow: there is no custom license-validation control flow. Generated methods delegate to protobuf runtime machinery. `Reset` clears the message and stores the relevant `MessageInfo`; `ProtoReflect` returns reflection metadata; getters return default values on nil receivers; setters update hidden fields; presence methods check whether nested pointer fields are nil; clear methods nil optional or nested fields. Initialization is the same descriptor build path as the hybrid file: `init()` calls `file_license_proto_init()`, which returns early if already built, registers `CertData` oneof metadata, builds a `protoreflect.FileDescriptor` with two enums and four messages, and clears raw descriptor/type dependency globals.

State and persistence behavior: all state is caller-owned in memory and encoded through protobuf serialization. Hidden fields carry verification results, certificate data, timestamps, DNS names, and recursive parent certificate data. `unknownFields` and `sizeCache` support runtime behavior. The file performs no disk persistence, no certificate loading, and no verification; it only preserves the schema state supplied by other code. `ParentData`, `ValidFrom`, and `ValidUntil` preserve pointer presence; getters alone collapse absent values to nil or defaults.

Dependencies: imports are `protoreflect`, `protoimpl`, `timestamppb`, and `reflect`. It depends on `google.protobuf.Timestamp` for certificate validity boundaries. Build selection depends on the `protoopaque` tag, making this file mutually exclusive with `license.pb.go` in normal builds.

Integration points: Go packages compiled with `-tags protoopaque` use this file for the license protobuf API. It must remain wire-compatible with `license.pb.go` and with other language bindings generated from `license.proto`. The message semantics are the same: certificate verification result/status, feature verification result/status, current certificate data retrieval, and simplified x509/BeeGFS license certificate metadata including type, serials, subject fields, validity, licensed-feature DNS names, CA status, and optional issuer data.

Risks: callers that expect exported fields from the hybrid file will fail under `protoopaque`; access should go through methods and builders for build-tag portability. The schema has no intrinsic validation of enum states, certificate validity windows, DNS-feature encoding, certificate hierarchy, or status-message consistency. Recursive `ParentData` can become expensive if populated deeply. As with the hybrid file, messages can contain sensitive or operationally revealing license details, and stringification/logging should be controlled. Manual edits are unsafe because the file is generated.

Test signals: test with `go test -tags protoopaque` for packages using `license`. Add round-trip tests comparing opaque and non-opaque builds at the wire level, especially for `CertData.parent_data`, timestamp fields, DNS name slices, and result/message conventions. API tests should exercise builders plus getters/setters/clearers rather than direct field access.
