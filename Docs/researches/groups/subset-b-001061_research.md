# sources/distributed-fs/ceph-client/drivers/block/ublk_drv.c

Purpose: This file implements the Linux userspace block device driver (`ublk`). It exposes a control misc device (`/dev/ublk-control`), per-device character devices (`/dev/ublkcN`), and blk-mq disks (`ublkbN`) whose I/O is serviced by userspace daemons through `io_uring` passthrough commands. The driver handles device creation, parameter negotiation, block queue setup, daemon fetch/commit protocol, copy/user-copy/zero-copy data movement, shared-memory zero copy, zoned block operations, integrity metadata, user recovery, quiesce/stop/delete flows, and unprivileged-device permission policy.

Important APIs, types, and functions: Core state is held in `struct ublk_device`, `struct ublk_queue`, `struct ublk_io`, `struct ublk_uring_cmd_pdu`, `struct ublk_batch_fetch_cmd`, and `struct ublk_buf_range`. Public kernel integration points are `ub_fops`, `ublk_mq_ops`, `ublk_batch_mq_ops`, `ublk_ch_fops`, `ublk_ch_batch_io_fops`, and `ublk_ctl_fops`. Control commands are dispatched by `ublk_ctrl_uring_cmd()` into helpers such as `ublk_ctrl_add_dev()`, `ublk_ctrl_start_dev()`, `ublk_ctrl_del_dev()`, `ublk_ctrl_set_params()`, `ublk_ctrl_get_params()`, `ublk_ctrl_start_recovery()`, `ublk_ctrl_end_recovery()`, `ublk_ctrl_quiesce_dev()`, `ublk_ctrl_set_size()`, `ublk_ctrl_reg_buf()`, and `ublk_ctrl_unreg_buf()`. I/O commands are handled by `ublk_ch_uring_cmd_local()` or `ublk_ch_batch_io_uring_cmd()`, with request dispatch through `ublk_queue_rq()`, `ublk_queue_rqs()`, `ublk_batch_queue_rq()`, `ublk_batch_queue_rqs()`, `ublk_dispatch_req()`, `ublk_batch_dispatch()`, and completion through `__ublk_complete_rq()`.

Control flow: Device creation starts at `UBLK_CMD_ADD_DEV`: userspace passes `struct ublksrv_ctrl_dev_info`, the driver validates queue count/depth and feature combinations, allocates an idr id, blk-mq tag set, per-queue command buffers, per-queue `ublk_io` slots, optional batch event FIFOs, and finally adds a per-device character node. Userspace then sets parameters through `UBLK_CMD_SET_PARAMS`, mmaps the per-queue command buffers, and submits one fetch command for each queue/tag. `UBLK_IO_FETCH_REQ` stores the `io_uring_cmd`, daemon task, and buffer metadata into `struct ublk_io`; once all queue slots are ready `ublk_mark_io_ready()` completes `ub->completion`. `UBLK_CMD_START_DEV` waits for that completion, validates the daemon pid, creates a blk-mq disk with negotiated queue limits, applies capacity/zoned attributes, adds the disk, and optionally schedules an async partition scan.

I/O path: blk-mq calls `ublk_queue_rq()` or the batch variant. `ublk_prep_req()` checks fail/quiesce/cancel state, translates the block request into a userspace descriptor in the mmaped `ublksrv_io_desc` array via `ublk_setup_iod()`, and starts the request. Non-batch mode schedules task work on the stored daemon command; `ublk_dispatch_req()` either asks userspace for a write buffer (`UBLK_IO_RES_NEED_GET_DATA`), maps/copies write data into the daemon buffer, performs automatic io_uring bvec registration, or completes the fetch command so userspace sees a new request. Userspace replies with `UBLK_IO_COMMIT_AND_FETCH_REQ`, which records the result, updates the buffer address or zone append LBA, optionally unregisters auto-registered buffers, completes the previous request, and arms the same slot for a later request. Batch mode decouples request tags into a per-queue kfifo; multishot fetch commands pull tag arrays into selected buffers, while batch prep/commit commands walk user-provided element arrays to arm or complete many slots at once.

Data movement and zero-copy behavior: In the default mapped-buffer mode, `ublk_map_io()` copies write request pages into a daemon-provided userspace buffer, while `ublk_unmap_io()` copies read data back from that buffer on completion. `UBLK_F_USER_COPY` exposes `read_iter` and `write_iter` on the character device so the daemon can copy request data directly at encoded offsets; integrity metadata uses the same path with `UBLKSRV_IO_INTEGRITY_FLAG`. `UBLK_F_SUPPORT_ZERO_COPY` lets the daemon register request bvecs into io_uring buffers using `UBLK_IO_REGISTER_IO_BUF`/`UBLK_IO_UNREGISTER_IO_BUF`. `UBLK_F_AUTO_BUF_REG` performs that registration during dispatch and tracks whether the request needs userspace fallback. `UBLK_F_SHMEM_ZC` lets userspace register long-term pinned shared-memory buffers in `ublk_ctrl_reg_buf()`; registered PFN ranges are stored in a maple tree, and `ublk_try_buf_match()` marks matching request pages with a compact `ublk_shmem_zc_addr()` descriptor so no per-I/O page copy is needed.

State and persistence behavior: Persistent user-visible state is the created char device, block disk, sysfs/module parameter state, device number allocation, negotiated disk capacity and queue limits, and any pinned shared-memory registrations held for the device lifetime. Most internal state is volatile kernel state: per-slot command ownership flags (`ACTIVE`, `OWNED_BY_SRV`, `NEED_GET_DATA`, `AUTO_BUF_REG`, `CANCELED`), request references, daemon task pointers, device state (`LIVE`, `QUIESCED`, `FAIL_IO`, `DEAD`), queue cancel/fail/force-abort flags, and batch fetch state (`fcmd_head`, `active_fcmd`, `evts_fifo`). User recovery intentionally preserves the disk while daemon state is reset: daemon exit transitions the device to stopped, quiesced, or fail-I/O depending on recovery flags, then a later daemon can run start/end recovery after all fetch slots are reestablished.

Dependencies and integration points: The file is tightly integrated with blk-mq (`blk_mq_alloc_tag_set`, `blk_mq_alloc_disk`, queue freeze/quiesce, request batching, timeouts), gendisk lifecycle, `io_uring_cmd` passthrough and io_uring provided-buffer registration, kernel task work, block integrity, zoned block APIs (`blk_revalidate_disk_zones`, `disk_report_zone`, `REQ_OP_ZONE_*`), user memory pinning (`pin_user_pages_fast`), maple trees, idr/ida allocation, misc/char device registration, Linux permission checks, and UAPI definitions in `uapi/linux/ublk_cmd.h`. It also includes capability/owner checks for unprivileged devices and a module parameter (`ublks_max`) limiting unprivileged device creation.

Risks and edge cases: The driver is concurrency-sensitive because request completion, io_uring cancel, daemon file release, disk deletion, queue quiesce, recovery, and buffer unregister callbacks all touch the same per-slot state. Reference accounting for user-copy, zero-copy, and auto-buffer registration is subtle: `io->ref` and `task_registered_buffers` must sum to expected values across daemon death and completion, or requests can hang or complete after data structures are freed. Batch mode has extra races around `active_fcmd`, multishot CQE buffer selection, event kfifo reinsertion after partial dispatch failure, and cancellation of active versus queued fetch commands. Shared-memory zero copy pins long-term user pages and relies on queue freeze plus maple-tree locking to avoid PFN-range lookups racing with unregister. Unprivileged devices deliberately disable recovery and zero-copy/user-copy features, kill the daemon on timeout, and permanently suppress some partition scans to avoid deadlocks and privilege traps. Zoned and integrity support depend on precise feature negotiation and correct reuse of the command address field.

Test signals: Useful validation includes creating privileged and unprivileged devices, invalid feature-combination rejection, parameter validation for basic/discard/zoned/integrity/segment/dma limits, mmap size and owner checks, normal read/write/flush/discard/write-zeroes paths, `NEED_GET_DATA` write flow, user-copy read/write and integrity offsets, zero-copy buffer registration/unregistration from daemon and non-daemon tasks, auto-buffer fallback and unregister behavior, shared-memory registration/unregistration plus PFN match/mismatch cases, batch fetch/prep/commit/cancel flows, daemon crash with each recovery mode, quiesce timeout behavior, stop/try-stop/delete while disk is open, zoned report and zone append LBA handling, and request timeout behavior for unprivileged daemons.

# sources/distributed-fs/ceph-client/drivers/block/virtio_blk.c

Purpose: This file implements the virtio block frontend driver. It binds to `VIRTIO_ID_BLOCK`, negotiates virtio block features, creates a blk-mq disk named with the legacy `vd*` scheme, maps Linux block requests into virtqueue scatter-gather commands, handles completion interrupts and polling, exposes serial/cache sysfs attributes, processes capacity changes, supports discard/write-zeroes/secure-erase/flush and host-managed zoned devices, and tears down or restores virtqueues across device removal, suspend, and virtio reset.

Important APIs, types, and functions: Core state is `struct virtio_blk`, `struct virtio_blk_vq`, and per-request `struct virtblk_req`. Request setup and submission are handled by `virtblk_setup_cmd()`, `virtblk_map_data()`, `virtblk_add_req()`, `virtblk_prep_rq()`, `virtio_queue_rq()`, `virtio_queue_rqs()`, and `virtio_commit_rqs()`. Completion paths are `virtblk_done()`, `virtblk_request_done()`, `virtblk_poll()`, and `virtblk_complete_batch()`. Configuration and lifecycle helpers include `virtblk_read_limits()`, `virtblk_update_capacity()`, `virtblk_config_changed_work()`, `init_vq()`, `virtblk_probe()`, `virtblk_remove()`, `virtblk_freeze_priv()`, and `virtblk_restore_priv()`. Sysfs/block operations are supplied through `virtblk_fops`, `serial_show()`, `cache_type_show()`, and `cache_type_store()`.

Control flow: On probe, the driver allocates an ida index, `struct virtio_blk`, virtqueues, a blk-mq tag set, and queue limits read from virtio configuration. Queue depth defaults to the virtqueue capacity, adjusted when indirect descriptors are unavailable, unless overridden by the `queue_depth` module parameter. The disk is named with `virtblk_name_format("vd", index, ...)`, marked read-only when the host advertises `VIRTIO_BLK_F_RO`, capacity is read, `virtio_device_ready()` enables virtqueue use, optional zoned revalidation runs, and `device_add_disk()` publishes the disk with sysfs attributes. Request submission translates `REQ_OP_*` operations into virtio type codes and sector fields, builds discard/write-zeroes/secure-erase range payloads when needed, maps block segments to an sg table, adds out header, data sg, and in status header to the selected virtqueue, and kicks the queue when the block layer marks the request as the last in a dispatch batch.

I/O and completion behavior: For reads, writes, flushes, discards, write zeroes, secure erase, zone management, zone append, zone report, and get-id commands, the request private data carries an out header, variable in header, sg table, and inline scatterlist storage. The status byte is always treated as the last byte of the in-header, allowing zone append to return a written sector plus status. `virtblk_done()` disables callbacks under the virtqueue lock, drains used descriptors with `virtqueue_get_buf()`, schedules blk-mq completion unless fake timeout is active, and restarts stopped queues. Poll queues have no interrupt callback and are drained by `virtblk_poll()`, which can batch successful completions through `io_comp_batch`. Cleanup frees mapped sg tables and special range payload allocations.

Zoned and limits behavior: With `CONFIG_BLK_DEV_ZONED`, `virtblk_read_zoned_limits()` accepts only host-managed zoned devices, rejects zero/non-power-of-two zone sizes and invalid append/write-granularity limits, sets `BLK_FEAT_ZONED`, zone limits, chunk sectors, and disables discard limits for zoned devices. `virtblk_report_zones()` allocates a bounded vmalloc report buffer, issues internal `REQ_OP_DRV_IN` zone report requests, parses virtio zone type/state descriptors into `struct blk_zone`, and feeds `disk_report_zone()`. `virtblk_setup_cmd()` translates Linux zone open/close/finish/append/reset/reset-all operations into virtio command types and records the append completion sector.

State and persistence behavior: Persistent visible state includes the allocated block major, disk minor range, disk capacity, read-only flag, queue limits, cache mode, serial sysfs value, and negotiated virtio feature set. Runtime state includes virtqueue pointers, per-queue locks, queue mapping counts for default/poll queues, the work item for capacity changes, and `vblk->vdev` guarded by `vdev_mutex` for paths that can run after removal. Capacity changes are processed asynchronously by `virtblk_config_changed_work()` and update the block layer with `set_capacity_and_notify()`. Cache mode sysfs writes modify virtio config WCE and commit updated queue write-cache features.

Dependencies and integration points: The driver depends on virtio core (`register_virtio_driver`, feature negotiation, config reads/writes, virtqueue allocation/reset/notify), blk-mq, gendisk/block queue limits, scatterlist allocation, sysfs device attributes, workqueues, ida minor allocation, zoned block APIs, and block-layer helpers for discard/write-zeroes/secure-erase ranges. It advertises legacy and modern feature tables; legacy excludes zoned support while modern includes `VIRTIO_BLK_F_ZONED`.

Risks and edge cases: Virtqueue locking must serialize add, kick, interrupt completion, and polling. Queue-stop/restart behavior is sensitive to `-ENOSPC` versus `-ENOMEM`: only virtqueue space exhaustion stops the hardware queue. Range payloads for discard/write-zeroes/secure-erase are dynamically allocated under atomic context and must be freed on every failure/completion path. Host-provided config values can be invalid; secure erase rejects zero alignment/sector/segment values, MQ rejects zero queue count, and zoned devices reject unsupported models or geometry. Removal/reset must flush config work, freeze/quiesce queues, reset the virtio device, delete virtqueues, and set `vblk->vdev = NULL` before freeing resources so late geometry or zone report paths return `-ENXIO` rather than dereferencing stale virtio state.

Test signals: Useful tests include single-queue and multi-queue probe, `num_request_queues` and `poll_queues` mapping, read/write/flush/discard/write-zeroes/secure-erase request translation, queue full and allocation-failure paths, interrupt and polling completions, fake timeout behavior, serial get-id success and unsupported `-EIO`, cache sysfs visibility and WCE updates, capacity-change work, host read-only devices, invalid virtio config values, zoned probe/report/append/reset flows, suspend/resume and reset_prepare/reset_done, and removal under concurrent config changes.

# sources/distributed-fs/ceph-client/drivers/block/xen-blkback/Makefile

Purpose: This Makefile wires the Xen block backend driver into Kbuild. When `CONFIG_XEN_BLKDEV_BACKEND` is enabled, it builds the `xen-blkback` module/object from the backend request engine and Xenbus integration sources.

Important APIs, types, and functions: There are no C APIs or runtime types in this file. The important build declarations are `obj-$(CONFIG_XEN_BLKDEV_BACKEND) := xen-blkback.o` and `xen-blkback-y := blkback.o xenbus.o`. These Kbuild variables define the module name and its constituent objects.

Control flow: Kbuild evaluates the `obj-*` assignment based on kernel configuration. If Xen block backend support is selected, `blkback.o` and `xenbus.o` are linked into `xen-blkback.o`; otherwise this directory contributes no object for the backend.

State and persistence behavior: The file has no runtime state, persistence, or generated output by itself. Its only persistent effect is the build graph encoded in the repository: changing it changes which objects are compiled into the kernel/module.

Dependencies and integration points: The Makefile depends on the kernel Kbuild system and the `CONFIG_XEN_BLKDEV_BACKEND` Kconfig symbol. It integrates `blkback.c` (request processing, grant mapping, bio submission) with `xenbus.c` (device discovery/configuration and ring setup), matching declarations shared in `common.h`.

Risks and edge cases: Build omissions are the main risk. Removing `xenbus.o` would leave no Xenbus frontend/backend negotiation; removing `blkback.o` would leave declarations without the actual I/O engine. Renaming the module target changes module identity and aliases expected by Xen tooling.

Test signals: Build with `CONFIG_XEN_BLKDEV_BACKEND=y` and `=m` should compile/link `xen-blkback.o` from both objects. Build with the symbol disabled should skip the object. Module metadata and alias checks should confirm the resulting object includes the `xen-backend:vbd` alias from `blkback.c`.

# sources/distributed-fs/ceph-client/drivers/block/xen-blkback/blkback.c

Purpose: This file is the Xen block backend I/O engine. It services requests from Xen blkfront guests through shared rings and grant references, translates guest block protocol operations into Linux bios or block helper calls against a backend `struct block_device`, manages persistent grant mappings and a grant-page cache, returns blkif responses, handles queue threads and interrupts, reports resize events through Xenstore, and initializes/finalizes the backend interface and Xenbus driver.

Important APIs, types, and functions: The exported or cross-file entry points are `xen_blkif_be_int()`, `xen_blkif_schedule()`, `xen_blkbk_free_caches()`, `xen_blkbk_unmap_purged_grants()`, module init `xen_blkif_init()`, and module exit `xen_blkif_fini()`. Major internal subsystems are persistent grant management (`add_persistent_gnt()`, `get_persistent_gnt()`, `put_persistent_gnt()`, `free_persistent_gnts()`, `purge_persistent_gnt()`), request pool management (`alloc_req()`, `free_req()`), VBD validation/resizing (`xen_vbd_translate()`, `xen_vbd_resize()`), request-ring processing (`do_block_io_op()`, `__do_block_io_op()`), grant mapping (`xen_blkbk_map()`, `xen_blkbk_unmap()`, `xen_blkbk_map_seg()`, `xen_blkbk_parse_indirect()`), dispatch (`dispatch_rw_block_io()`, `dispatch_discard_io()`, `dispatch_other_io()`), bio completion (`end_block_io_op()`, `__end_block_io_op()`), draining (`xen_blk_drain_io()`), and response publishing (`make_response()`).

Control flow: The Xen event-channel interrupt calls `xen_blkif_be_int()`, which marks the ring as having waiting requests and wakes the per-ring backend thread. `xen_blkif_schedule()` is that thread: it is freezable, watches for backend size changes, waits for ring work and free pending request slots, calls `do_block_io_op()`, sends late EOI when appropriate, periodically purges persistent grants, shrinks the free grant-page cache, and optionally prints statistics. `__do_block_io_op()` snapshots `req_prod`, validates producer/consumer overflow, allocates a `pending_req`, copies a protocol-specific request into native `struct blkif_request`, advances `req_cons` before responding, and dispatches read/write/flush/barrier/indirect/discard/unsupported operations.

Request dispatch behavior: `dispatch_rw_block_io()` normalizes indirect operations, validates segment counts and segment sector ranges, fills `pending_req`, accumulates sector counts, maps indirect descriptor frames if needed, validates VBD read-only/range access through `xen_vbd_translate()`, checks logical-block alignment, optionally drains in-flight I/O for barriers, maps guest grants, allocates one or more bios as `bio_add_page()` capacity requires, submits them under a blk plug, and updates stats. Flush requests produce a zero-segment PREFLUSH bio. `dispatch_discard_io()` validates write access and issues either `blkdev_issue_discard()` or `blkdev_issue_secure_erase()`. Unsupported operations immediately return `BLKIF_RSP_EOPNOTSUPP`.

Grant mapping and persistence behavior: Guest data pages are represented by `struct grant_page` entries in each `pending_req`. `xen_blkbk_map()` first tries to reuse inactive persistent grants from an rb-tree keyed by grant ref when negotiated. Otherwise it obtains backend pages from `gnttab_page_cache`, maps grant refs with `gnttab_map_refs()`, and optionally promotes new mappings into `struct persistent_gnt` while under `max_pgrants`. Non-persistent mappings are unmapped after I/O completion. Persistent grants are marked active/inactive with `last_used` timestamps and retained across requests until LRU/timeout purge or backend teardown. Purge removes inactive grants from the rb-tree, queues them on `persistent_purge_list`, and a work item unmaps them outside the scheduler loop.

Completion and response behavior: Each submitted bio points back to the `pending_req`; `end_block_io_op()` calls `__end_block_io_op()` and drops the bio. Errors set the whole blkif request status, with unsupported flush/barrier also updating Xenstore-advertised feature state through `xen_blkbk_flush_diskcache()` or `xen_blkbk_barrier()`. When the pending bio count reaches zero, `xen_blkbk_unmap_and_respond()` prepares async grant unmaps, and `xen_blkbk_unmap_and_respond_callback()` returns pages to the cache, calls `make_response()`, releases the pending request slot, completes drain waiters if in-flight drops to zero, and drops the blkif reference. `make_response()` writes the protocol-appropriate response ring entry under `blk_ring_lock`, advances `rsp_prod_pvt`, pushes responses, and notifies the frontend IRQ if needed.

State and persistence behavior: Runtime state is mostly per-ring: event irq, shared ring pointers, pending request free list, in-flight count, request wait flags, per-ring kthread, persistent grant rb-tree, free page cache, purge work, shutdown wait queue, and statistics counters. Per-device state in `struct xen_blkif` includes domid, VBD metadata, protocol, rings, reference count, drain state, and buffer-cache squeeze timing. Persistent external effects include Xenstore updates for resize and feature fallback, backend module parameters (`max_buffer_pages`, `max_persistent_grants`, `persistent_grant_unused_seconds`, `max_queues`, `max_ring_page_order`, `log_stats`), and I/O submitted to the underlying block device. No filesystem data is stored by the driver except through the actual block writes it services.

Dependencies and integration points: The file depends on Xen event channels, Xen grant table mapping/unmapping and page cache helpers, Xenbus helpers declared in `common.h`, blkif ring macros and protocol structures, Linux kthreads/freezer/wait queues/workqueues, block-device helpers (`bio_alloc`, `bio_add_page`, `submit_bio`, `blkdev_issue_discard`, `blkdev_issue_secure_erase`), backend file-to-bdev access, and module initialization. It pairs with `xenbus.c` for interface allocation, backend discovery, ring setup, feature negotiation, and VBD opening.

Risks and edge cases: Safety hinges on validating untrusted frontend ring indices, operation codes, segment counts, indirect descriptor bounds, sector ranges, and logical-block alignment before touching grants or submitting bios. Grant lifetime is complex: persistent grants can be reused, purged asynchronously, or returned from interrupt-context completion, so active flags and in-use counters must stay consistent. `BUG_ON()` is used for grant unmap failures and several impossible states, making hypervisor/grant-table errors fatal. The request loop can run without a finite frontend bound, so it uses `cond_resched()` and stops when pending slots are exhausted. Barrier/drain handling depends on in-flight accounting and can delay queue progress. Incorrect read-only mapping flags or VBD translation would expose host data or allow writes outside the backend device.

Test signals: Valuable tests include frontend ring overflow/bogus producer handling, native/x86_32/x86_64 protocol request translation, reads and writes split over multiple bios, zero-segment flush, write barrier drain, discard and secure erase fallback, read-only and out-of-range access rejection, misaligned sector rejection, indirect descriptor mapping and invalid descriptor rejection, persistent grant reuse/purge/timeout/max overflow, grant map/unmap failures, backend resize Xenstore update, queue starvation when no `pending_req` is free, suspend/freezer behavior for the scheduler thread, late EOI behavior, module parameter bounds, and clean teardown with all grants and page cache entries freed.

# sources/distributed-fs/ceph-client/drivers/block/xen-blkback/common.h

Purpose: This header defines the shared data structures, protocol adapters, constants, and cross-file declarations for the Xen block backend. It bridges Xen blkif wire formats, backend ring state, virtual block device metadata, persistent grant tracking, pending request bookkeeping, and the functions implemented by `blkback.c` and `xenbus.c`.

Important APIs, types, and functions: Protocol definitions include `struct blkif_common_request`, x86_32 and x86_64 packed request variants for rw/discard/other/indirect operations, `DEFINE_RING_TYPES()` instantiations, `union blkif_back_rings`, and `enum blkif_protocol`. Backend state types include `struct xen_vbd`, `struct persistent_gnt`, `struct xen_blkif_ring`, `struct xen_blkif`, `struct seg_buf`, `struct grant_page`, `struct pending_req`, and `struct phys_req`. Cross-file declarations include `xen_blkif_interface_init()`, `xen_blkif_interface_fini()`, `xen_blkif_xenbus_init()`, `xen_blkif_xenbus_fini()`, `xen_blkif_be_int()`, `xen_blkif_schedule()`, `xen_blkbk_free_caches()`, `xen_blkbk_flush_diskcache()`, `xen_blkbk_barrier()`, `xen_blkbk_xenbus()`, and `xen_blkbk_unmap_purged_grants()`.

Control flow: `xenbus.c` uses the declarations and structures here to create/configure a `struct xen_blkif`, open a backend VBD, allocate rings, negotiate protocol/features, and start one backend thread per `struct xen_blkif_ring`. `blkback.c` then consumes the ring union according to `blk_protocol`, turns requests into `pending_req` objects using the segment/grant arrays defined here, submits bios, and uses the declared Xenbus helpers to update feature state and retrieve the Xenbus device for resize notifications.

State and persistence behavior: `struct xen_vbd` stores user-visible backend device state: guest handle, read-only bit, type, physical device id, opened backend file, cached size, flush/discard/persistent-grant feature flags, and persistent-grant overflow status. `struct xen_blkif_ring` stores per-queue runtime state: irq, shared ring, ring lock, request wait queues, in-flight count, backend kthread, pending request pool, persistent grant rb-tree, grant page cache, purge/free work, stats, and shutdown wait queue. `struct xen_blkif` stores per-device state: domid, handle, protocol, VBD, backend pointer, refcount, drain completion, ring count/order, and all rings. `struct pending_req` stores all state needed to complete one frontend request after bios finish, including grant pages, indirect pages, segment geometry, bios, unmap operations, and async unmap callback data.

Dependencies and integration points: The header depends on Linux block, vmalloc, wait queue, rbtree, interrupt, module, and I/O headers; Xen grant table, Xen page, Xenbus, ring, blkif, and protocol headers; and architecture hypervisor setup headers. It defines constants derived from Xen page size, Linux page size, blkif segment limits, and indirect descriptor geometry. The `xen_blkif_get()`/`xen_blkif_put()` macros integrate reference release with scheduled work so final cleanup occurs asynchronously.

Risks and edge cases: The packed x86 protocol structures must match the ABI used by 32-bit and 64-bit frontends, including padding and alignment; mistakes would corrupt request decoding. Indirect segment constants must stay consistent with Xen blkif maximums and the advertised `feature-max-indirect-segments`. `XEN_PAGES_PER_SEGMENT` assumes Linux `PAGE_SIZE` is at least Xen page size and affects segment geometry on non-4K-page kernels. Fixed-size arrays in `pending_req` are sized by `MAX_INDIRECT_SEGMENTS` and `MAX_INDIRECT_PAGES`, so all request validation in `blkback.c` must enforce those bounds before filling arrays. Refcount macros schedule async free work, so code must not assume final destruction is synchronous.

Test signals: Compile coverage across native, x86_32, and x86_64 protocol support is important. Runtime tests should negotiate each protocol, submit normal and indirect requests at maximum segment counts, exercise different Linux page sizes where supported, validate persistent-grant feature negotiation and overflow state, verify refcount release schedules cleanup once, and confirm `xenbus.c` and `blkback.c` agree on ring, VBD, and pending request layouts.
