# sources/distributed-fs/ceph-client/mm/mmap.c

Purpose: implements the main Linux virtual memory mapping lifecycle for this source tree: `brk`, `mmap`, `munmap`, deprecated `remap_file_pages`, VMA lookup, unmapped-area selection, stack expansion, process address-space teardown, special mappings, mmap sysctls, and `dup_mmap()` during fork. It is the central coordinator between syscall inputs, `mm_struct` accounting, maple-tree VMA storage, filesystem-backed mappings, anonymous/shmem/hugetlb mappings, userfaultfd notifications, memory policy, KSM, khugepaged, and security hooks.

Important APIs/types/functions: exports or defines `vma_set_page_prot`, `mlock_future_ok`, `do_mmap`, `ksys_mmap_pgoff`, `mmap_pgoff`, optional `old_mmap`, `vm_unmapped_area`, `generic_get_unmapped_area`, `generic_get_unmapped_area_topdown`, `mm_get_unmapped_area_vmflags`, `__get_unmapped_area`, `mm_get_unmapped_area`, `find_vma_intersection`, `find_vma`, `find_vma_prev`, `expand_stack_locked`, `find_extend_vma_locked`, `expand_stack`, `do_munmap`, `vm_munmap`, `munmap`, `remap_file_pages`, `vm_brk_flags`, `exit_mmap`, `may_expand_vm`, `vm_stat_account`, `_install_special_mapping`, `mmap_init`, `mmap_read_lock_maybe_expand`, and `dup_mmap`. Key data types are `mm_struct`, `vm_area_struct`, `vma_iterator`, `vm_unmapped_area_info`, `vm_special_mapping`, `mmu_gather`, `unmap_desc`, `file`, `inode`, and VMA flag sets.

Control flow: `brk` write-locks `mmap_lock`, validates the data-segment limit, page-aligns requested and old break values, then either shrinks through `do_vmi_align_munmap()` or grows through `do_brk_flags()` after stack-gap and mlock checks. `do_mmap` normalizes hints, lengths, protection, execute-only pkeys, MAP_FIXED_NOREPLACE, file access rules, noexec paths, memfd seals, overcommit flags, anonymous shared/droppable behavior, hugetlb handling, and finally delegates installation to `mmap_region`. `ksys_mmap_pgoff` resolves file descriptors or anonymous hugetlb pseudo-files before calling `vm_mmap_pgoff`. Unmapped-area helpers choose bottom-up or top-down placement, honor arch/file `get_unmapped_area`, THP alignment, security minimum address checks, and stack guard gaps. `munmap` wrappers delegate to maple-tree-aware unmap helpers and finish userfaultfd completion outside the write-side changes. `exit_mmap` releases MMU notifiers, unmaps all VMAs under a gather, frees page tables, clears the maple tree, tears down VMA objects, and unaccounts committed memory. `dup_mmap` duplicates the maple tree, then replaces entries with copied VMAs, policies, userfaultfd contexts, anon-vma/file interval links, and copied page tables, with a cleanup path for partial fork failure.

State and persistence: all durable state is in kernel memory: `mm->brk`, VMA maple tree entries, VMA flags/protections, `mm` counters (`total_vm`, `data_vm`, `exec_vm`, `stack_vm`, `locked_vm`, high watermarks), file mapping interval trees, userfaultfd event lists, rmap/anon-vma links, and sysctl/module parameters such as `max_map_count`, ASLR mmap randomization bits, `legacy_va_layout`, `stack_guard_gap`, and reserve kbytes. The file writes no on-disk data itself, but it makes persistent process-visible address-space changes and invokes filesystem mapping hooks. `vma_set_page_prot` uses `WRITE_ONCE` because some protection removal paths read it without the mmap lock.

Dependencies and integration points: depends on the security subsystem (`security_mmap_addr`, `security_mmap_file`, `security_vm_enough_memory_mm`), architecture hooks (`arch_get_unmapped_area*`, `arch_mmap_check`, cache/TLB context operations), hugetlb, shmem, memfd seals, pkeys, KSM, khugepaged, uprobes, perf mmap events, memory hotplug notifiers, overcommit accounting, maple tree/VMA iterator helpers, userfaultfd, MMU notifiers, and filesystem `file_operations` such as `mmap`, `get_unmapped_area`, `FOP_MMAP_SYNC`, and `FOP_UNSIGNED_OFFSET`.

Risks: address/length overflow, pgoff overflow, stale or incorrect VMA iterator state after merges/splits, accounting imbalances on partial fork or unmap failure, missing userfaultfd completion, mmap-lock ordering, improper handling of sealed VMAs through MAP_FIXED replacement, and file-backed mapping permission bugs are high-impact. `dup_mmap` is especially sensitive because it must preserve file interval-tree ordering, VMA policies, and page-table state while recovering cleanly from OOM. Stack expansion and unmapped-area selection must preserve guard gaps and arch security constraints.

Test signals: syscall tests for `brk`, `mmap`, `munmap`, `MAP_FIXED_NOREPLACE`, `MAP_SYNC`, `MAP_LOCKED`, anonymous/file/hugetlb/shmem mappings, noexec mounts, memfd seals, overcommit and rlimit boundaries, stack growth faults, fork/exec/exit stress, userfaultfd mmap/remap/unmap events, KSM/khugepaged fork behavior, and mm selftests around maple-tree VMA merging/splitting would exercise the core paths. Runtime signals include tracepoints `trace_vm_unmapped_area` and `trace_exit_mmap`, perf mmap events, warnings around map count and data rlimits, and lockdep coverage of mmap/rmap locks.

# sources/distributed-fs/ceph-client/mm/mmap_lock.c

Purpose: implements mmap-lock tracepoint glue, per-VMA read-lock coordination, lockless VMA lookup under RCU, next-VMA iteration with fallback to `mmap_lock`, and careful fault-time locking for architectures that use `lock_mm_and_find_vma`. It is the synchronization companion to the VMA mutation paths in `mmap.c`, `mprotect.c`, `mremap.c`, and fault handlers.

Important APIs/types/functions: trace wrappers `__mmap_lock_do_trace_start_locking`, `__mmap_lock_do_trace_acquire_returned`, and `__mmap_lock_do_trace_released`; per-VMA write-side helpers `__vma_start_write` and `__vma_exclude_readers_for_detach`; read-side helpers `vma_start_read`, `lock_vma_under_rcu`, `lock_next_vma`, and `lock_next_vma_under_mmap_lock`; fault helpers `get_mmap_lock_carefully`, `upgrade_mmap_lock_carefully`, and `lock_mm_and_find_vma`. Key types and state are `vm_area_struct`, `mm_struct`, `vma_exclude_readers_state`, `vma_iterator`, VMA `vm_refcnt`, `vm_lock_seq`, `mm_lock_seq`, `rcuwait`, and tracepoints from `trace/events/mmap_lock.h`.

Control flow: with tracing enabled, public wrappers simply emit mmap-lock tracepoints from a separate translation unit to avoid include dependency cycles. With `CONFIG_PER_VMA_LOCK`, write-side mutation calls `__vma_start_write`, which marks the VMA as excluding readers via a high refcount flag, waits for per-VMA readers to leave, updates `vm_lock_seq` to the current mm write sequence, and releases the exclusive marker. RCU lookup uses the maple tree, attempts to increment a bounded VMA refcount, validates `vm_mm` and lock sequence, and either returns a stable per-VMA read lock or aborts/falls back. `lock_next_vma` combines speculative mmap-lock sequence checking with RCU iteration and falls back to taking `mmap_read_lock` when gaps or races cannot be verified. `lock_mm_and_find_vma` handles page-fault contexts carefully: it avoids deadlocking on kernel faults not covered by exception tables, optionally upgrades to a write lock, expands grow-down stacks, and returns with the read side held after downgrading.

State and persistence: state is volatile synchronization state in `mm_struct` and `vm_area_struct`: per-VMA refcounts, lock sequence numbers, writer wait queues, and trace events. No persistent data is written. Detach handling can mark a VMA as detached by driving its refcount to zero, preventing new readers while unlinked VMAs are freed or repurposed.

Dependencies and integration points: integrates with RCU, maple-tree iteration, rwsem-backed `mmap_lock`, lockdep annotations, memory cgroup VMA lock event counters, exception tables, page-fault register state, stack expansion from `mmap.c`, and optional no-MMU fallback lookup. Consumers include page fault paths, userfaultfd fast paths, VMA walkers, and mutation paths that call `vma_start_write`.

Risks: false locked/unlocked decisions must be one-sided; a false unlocked result would let readers race VMA mutation, so the sequence/refcount checks are deliberately conservative. Refcount overflow, VMA reuse under RCU, detached VMA races, lock upgrade failure in kernel fault context, and iterator gaps during lockless next-VMA traversal are subtle. Incorrect ordering between writer sequence updates and reader acquire barriers can expose partially modified VMA fields.

Test signals: lockdep under page faults, RCU stall testing, per-VMA lock selftests, mmap/mprotect/munmap racing with faults, stack-growth faults from user and exception-table-covered kernel contexts, and tracing checks for mmap lock start/acquire/release events. VMA lock event counters (`VMA_LOCK_MISS`, `VMA_LOCK_ABORT`) are useful runtime signals for fallback and race behavior.

# sources/distributed-fs/ceph-client/mm/mmu_gather.c

Purpose: provides the generic `mmu_gather` implementation used to batch page freeing, rmap removal, page-table freeing, and TLB invalidation during unmap, exit, mprotect/userfaultfd write-protect, and other page-table teardown paths. It amortizes expensive TLB shootdowns while preserving architecture and software page-table-walker safety.

Important APIs/types/functions: `tlb_gather_mmu`, `tlb_gather_mmu_fullmm`, `tlb_gather_mmu_vma`, `tlb_finish_mmu`, `tlb_flush_mmu`, `tlb_flush_rmaps`, `__tlb_remove_folio_pages`, `__tlb_remove_page_size`, `tlb_remove_table`, `tlb_remove_table_sync_one`, and `tlb_remove_table_sync_rcu`. Key types are `mmu_gather`, `mmu_gather_batch`, `mmu_table_batch`, encoded page pointers, `mm_struct`, `vm_area_struct`, `folio`, and page-table descriptor/table pointers.

Control flow: `__tlb_gather_mmu` initializes an on-stack gather, local page batch, table batch, page-size/range metadata, and increments `mm` pending TLB flush state. Page removal encodes pages plus flags such as delayed rmap and multi-page counts into the active batch; when the batch fills, `tlb_next_batch` either advances to an existing batch, allocates another page of batch storage, or forces a flush. `tlb_flush_mmu` performs the architecture TLB flush and then frees batched tables/pages. `tlb_finish_mmu` detects nested batched PTE modifications and forces fullmm/range reset when needed, flushes, frees secondary batches, and decrements pending flush state. Table freeing either batches tables, defers through RCU callbacks, synchronizes via IPI/RCU for lockless walkers, or falls back to immediate single-table freeing when allocation fails.

State and persistence: all state is transient in `mmu_gather` and its allocated batch pages. The visible lasting effects are freed physical pages/page tables, updated rmap state, and cleared pending TLB flush counters in the target `mm`. It does not persist data to disk. RCU callbacks may delay actual freeing beyond the caller's critical section.

Dependencies and integration points: integrates with architecture `asm/tlb.h` hooks, page allocator, swap cache freeing, rmap (`folio_remove_rmap_ptes`), hugetlb page sizes, RCU, SMP IPI synchronization, page poisoning/init-on-free policies, PT reclaim, nested TLB flush detection, and MM unmap paths such as `exit_mmap`, `mprotect`, `munmap`, and userfaultfd operations.

Risks: freeing page tables before all hardware/software walkers are excluded can produce use-after-free; missing a required TLB flush can leave stale translations; delayed rmap batching must not span unsupported batch chains; multi-page encoded entries must stay paired when chunking free batches; and nested gather users can require broader flushes than the original range. Allocation failure in table batching must still make forward progress without weakening synchronization.

Test signals: unmap/exit/mremap/mprotect stress under SMP, lockless GUP and page-table-walker tests, page poisoning/init-on-free configurations, hugetlb and THP unmap workloads, nested page-table modifications from concurrent userfaultfd or mprotect, and architecture TLB selftests. Runtime warnings in `tlb_finish_mmu`, page-size assertions, and KASAN/KCSAN reports are strong signals.

# sources/distributed-fs/ceph-client/mm/mmu_notifier.c

Purpose: implements the MMU notifier framework that lets secondary MMU users, such as KVM, device drivers, and interval-notifier users, track invalidations, aging, and address-space release for an `mm_struct`. It coordinates hlist-based notifier callbacks and interval-tree-based subscriptions with SRCU, spinlocks, invalidate sequence numbers, and deferred interval-tree updates.

Important APIs/types/functions: `mmu_interval_read_begin`, `__mmu_notifier_release`, `__mmu_notifier_clear_flush_young`, `__mmu_notifier_clear_young`, `__mmu_notifier_test_young`, `__mmu_notifier_invalidate_range_start`, `__mmu_notifier_invalidate_range_end`, `__mmu_notifier_arch_invalidate_secondary_tlbs`, `__mmu_notifier_register`, `mmu_notifier_register`, `mmu_notifier_get_locked`, `mmu_notifier_unregister`, `mmu_notifier_put`, `mmu_interval_notifier_insert`, `mmu_interval_notifier_insert_locked`, `mmu_interval_notifier_remove`, and `mmu_notifier_synchronize`. Core types are `mmu_notifier_subscriptions`, `mmu_notifier`, `mmu_notifier_ops`, `mmu_notifier_range`, `mmu_interval_notifier`, interval-tree nodes, SRCU `srcu`, and the lockdep invalidate map.

Control flow: registration allocates `mmu_notifier_subscriptions` if needed, takes all MM locks, installs the subscription container with release semantics, and either adds an hlist notifier or enables interval-tree mode. Invalidation start first walks intersecting interval notifiers, sets/increments invalidate sequence state, invokes `invalidate_start`/`invalidate`, queues finish callbacks, and then invokes hlist `invalidate_range_start` callbacks under SRCU. Non-blocking failures return `-EAGAIN` after required cleanup. Invalidation end finalizes interval invalidation, applies deferred interval-tree insert/remove operations, wakes waiters, and calls hlist end callbacks. Release handles both interval and hlist subscribers before `exit_mmap` frees pages. `mmu_interval_read_begin` provides a collision-retry snapshot so users can build shadow mappings and later detect invalidation via their own lock. Unregister/put paths use SRCU grace periods and `mm_count` pins to prevent callback/free races.

State and persistence: subscription state lives in `mm->notifier_subscriptions`, including an hlist, interval tree, active invalidation count, invalidate sequence, waitqueue, deferred add/remove list, and per-subscription reference counts. It is in-memory only, but it protects externally visible secondary mappings from using stale CPU page-table translations. `mmgrab`/`mmdrop` maintain lifetime across callbacks and asynchronous frees.

Dependencies and integration points: depends on SRCU, RCU hlist traversal, interval trees, spinlocks, wait queues, `mm_take_all_locks`, `mmap_lock`, lockdep, scheduler non-blocking annotations, and range events from unmap/protection/migration paths. Integrates with `exit_mmap`, `mprotect`, `mremap`, page aging, architecture secondary TLB invalidation, KVM/device driver SPTE teardown, and module unload via `mmu_notifier_synchronize`.

Risks: invalidation start/end pairing is critical; non-blocking failures must not call end for interval notifiers that reported `-EAGAIN` but must call hlist end for callbacks that may have succeeded. Interval-tree changes during active invalidation must be deferred or sequence-marked to avoid missed collisions. SRCU and mm lifetime ordering must prevent release/unregister/free races. Sequence wrap is mitigated by odd/even state but still relies on readers using the documented retry protocol.

Test signals: KVM and device-driver notifier tests, mmu interval notifier selftests, userfaultfd/migrate/unmap stress with registered notifiers, non-blocking invalidation paths, module unload after `mmu_notifier_put`, and `exit_mmap` with concurrent unregister. Lockdep coverage of invalidate start/end and SRCU/KCSAN race testing are important.

# sources/distributed-fs/ceph-client/mm/mmzone.c

Purpose: provides small but central memory-zone helpers: online node iteration, zone iteration, zonelist filtering by highest zone and optional NUMA nodemask, LRU vector initialization, and optional NUMA balancing cpupid exchange stored in folio flags.

Important APIs/types/functions: `first_online_pgdat`, `next_online_pgdat`, `next_zone`, `__next_zones_zonelist`, `lruvec_init`, and conditional `folio_xchg_last_cpupid`. Key types are `pglist_data`/`pg_data_t`, `zone`, `zoneref`, `nodemask_t`, `lruvec`, `lru_list`, and `folio`.

Control flow: node iteration returns `NODE_DATA(first_online_node)` or advances via `next_online_node`. `next_zone` increments within the current node's `node_zones` array, then moves to the first zone of the next online node. `__next_zones_zonelist` advances through zonerefs until the zone index is at or below the requested highest zone and, when supplied, the zone's node is in the nodemask. `lruvec_init` zeroes the structure, initializes the LRU lock, zswap state, LRU list heads, poisons the unevictable list head by deleting it, and initializes multi-gen LRU state. `folio_xchg_last_cpupid` atomically replaces the cpupid bitfield in folio flags with a cmpxchg loop.

State and persistence: initializes and mutates in-memory memory-management state only. `lruvec_init` prepares locks/list heads and LRU generation state for later reclaim operations. `folio_xchg_last_cpupid` persists a NUMA-balancing hint in folio flags until the next update.

Dependencies and integration points: depends on NUMA node masks and node data macros, zonelist encoding helpers, zswap LRU-vector state, multi-gen LRU initialization, folio flag layout, and optional NUMA balancing configuration. Allocation paths and reclaim code consume these helpers when scanning zonelists or managing per-node/memcg LRUs.

Risks: incorrect zonelist advancement can select zones above the caller's allowed class or outside a NUMA policy. The unevictable LRU list is intentionally poisoned, so callers must honor its special handling. Cpupid bit manipulation must preserve unrelated folio flags and be atomic under concurrent NUMA hinting.

Test signals: NUMA allocation policy tests, memory hotplug/node onlining tests, reclaim/LRU initialization tests, zswap and multi-gen LRU boot coverage, and NUMA balancing workloads that verify cpupid exchange does not corrupt folio flags.

# sources/distributed-fs/ceph-client/mm/mprotect.c

Purpose: implements `mprotect`, `pkey_mprotect`, protection-key allocation/free syscalls, and the lower-level page-table/VMA protection update machinery used by mprotect-like operations, NUMA balancing, and userfaultfd write protection. It updates VMA flags, page protections, commit accounting, MMU notifier ranges, and TLB gather state while preserving COW, soft-dirty, uffd-wp, THP, hugetlb, and PFN permission semantics.

Important APIs/types/functions: `can_change_pte_writable`, `change_protection`, `mprotect_fixup`, `mprotect`, `pkey_mprotect`, `pkey_alloc`, and `pkey_free`. Major internal helpers include `change_pte_range`, `change_pmd_range`, `change_pud_range`, `change_p4d_range`, `change_protection_range`, `change_present_ptes`, `change_softleaf_pte`, `mprotect_folio_pte_batch`, `prot_none_walk_ops`, and `do_mprotect_pkey`. Key types are `mmu_gather`, `vm_area_struct`, `vma_iterator`, page-table entries at all levels, `folio`, `page`, `mm_walk`, `pgprot_t`, `vma_flags_t`, and protection-key state.

Control flow: syscall entry normalizes tagged/page-aligned input, growth flags, read-implies-exec, lengths, pkey validity, and architecture protection validation before taking `mmap_write_lock`. It walks contiguous VMAs in the requested range, checks permissions (`VM_MAY*`), W^X denial, architecture flag validity, LSM `security_file_mprotect`, and optional `vm_ops->mprotect`. `mprotect_fixup` rejects sealed VMAs, performs PFN modify checks for PROT_NONE transitions, charges private writable mappings when needed, modifies/splits/merges VMA flags, starts VMA write protection, recalculates `vm_page_prot`, and calls `change_protection`. Page-table walkers descend through pgd/p4d/pud/pmd/pte levels, split huge mappings when required for uffd markers, populate page tables for uffd-wp markers, notify secondary MMUs for pud-level changes, batch compatible folio PTEs, handle migration/device-private/marker soft entries, and flush through the supplied `mmu_gather`.

State and persistence: persistent process state includes VMA access flags, pkeys, `vm_page_prot`, soft-dirty/uffd-wp PTE bits and markers, dirty/write PTE state, memory accounting (`VM_ACCOUNT`, `total_vm` category counters), and pkey allocation bits in `mm_struct`. No disk data is written. TLB flush state is transient but required for correctness after PTE permission changes.

Dependencies and integration points: integrates with pagewalk, hugetlb, THP splitting, swap/migration entries, mmu notifiers, perf mmap events, mempolicy, pkeys, LSM hooks, architecture cache/TLB/protection validators, KSM, userfaultfd, PFNMAP/MIXEDMAP permission checks, and `mmu_gather` from `mmu_gather.c`. VMA sealing from `mseal.c` directly blocks changes here.

Risks: PTE writability optimization must not bypass COW, writenotify, soft-dirty, or uffd-wp requirements. Huge-page splitting and uffd marker population can return `-ENOMEM` mid-walk. Commit-accounting transitions for private writable mappings must unwind on VMA modification failure. MMU notifier boundaries must cover changes visible to secondary MMUs. Sealed VMAs must return `-EPERM`. Protection-key syscalls must not expose unallocated pkeys.

Test signals: `mprotect`/`pkey_mprotect` syscall tests, protection-key selftests, W^X policy tests, userfaultfd write-protect tests, soft-dirty tests, NUMA balancing PROT_NONE scanning, THP/hugetlb mprotect tests, PFNMAP/MIXEDMAP device mappings, locked private mapping population, and mmu notifier/KVM invalidation stress. Runtime signals include TLB flush warnings, lockdep, and perf mmap events after VMA changes.

# sources/distributed-fs/ceph-client/mm/mremap.c

Purpose: implements the `mremap` syscall and shared page-table movement machinery for resizing, moving, duplicating some shared mappings, fixed-address remaps, `MREMAP_DONTUNMAP`, hugetlb-aware moves, multi-VMA move-only operations, and userfaultfd remap notifications. It coordinates VMA copying, VMA splitting/merging, accounting, rmap locks, MMU notifiers, TLB/cache flushing, page-table relocation, and cleanup/recovery on partial failure.

Important APIs/types/functions: public `mremap` syscall and `move_page_tables`; central data structures `enum mremap_type`, `struct vma_remap_struct`, and `pagetable_move_control`. Important helpers include `move_ptes`, `move_normal_pmd`, `move_normal_pud`, `move_huge_pud`, `move_pgt_entry`, `try_realign_addr`, `vrm_set_delta`, `vrm_remap_type`, `vrm_overlaps`, `vrm_set_new_addr`, `vrm_calc_charge`, `prep_move_vma`, `unmap_source_vma`, `copy_vma_and_data`, `dontunmap_complete`, `move_vma`, `shrink_vma`, `mremap_to`, `expand_vma_in_place`, `expand_vma`, `mremap_at`, `notify_uffd`, `check_prep_vma`, `check_mremap_params`, `remap_move`, and `do_mremap`.

Control flow: syscall entry strips tags only from the old address, initializes userfaultfd state lists, and calls `do_mremap`. Parameter validation checks flags, alignment, new length, fixed/dontunmap implications, MAYMOVE requirements, target overlap, and address range. Under `mmap_write_lock`, the code checks map-count headroom, then either performs a batched move-only range or prepares a single VMA. Preparation rejects sealed VMAs, aligns hugetlb lengths, classifies shrink/expand/no-resize, validates range containment, mlock/rlimit/overcommit expansion, pgoff overflow, and `VM_DONTEXPAND`/`VM_PFNMAP`. Shrinks unmap the trailing range. Expands prefer in-place `vma_merge_extend`; otherwise MAYMOVE picks a new area and calls `move_vma`. Fixed moves first unmap the destination, then copy the source VMA to the destination, move page tables, invoke `vm_ops->mremap`, and unmap the source unless `MREMAP_DONTUNMAP` keeps it. On page-table move failure, it moves entries back from new to old and unmaps the new VMA.

State and persistence: lasting state includes source/destination VMA topology, page-table entries at new addresses, removed or retained source mappings, `VM_LOCKED` clearing for DONTUNMAP remnants, anon-vma links, hugetlb reservation fixups, commit and VM statistics, soft-dirty markings on moved PTEs, uffd-wp cleanup when remap events are disabled, and userfaultfd remap/unmap events. Transient state includes `vma_remap_struct`, `pagetable_move_control`, rmap locks, mmu notifier range, and rollback information.

Dependencies and integration points: depends on mmap/VMA helpers (`copy_vma`, `do_vmi_munmap`, `vma_merge_extend`, maple iterators), hugetlb page-table movement, THP PMD/PUD movement, anon/file rmap locks, KSM unmerge, security memory accounting, userfaultfd, MMU notifiers, filesystem `vm_ops->may_split` and `vm_ops->mremap`, `get_unmapped_area`, page-table allocation, architecture `move_pmd`/`move_pud` support, and cache/TLB flush helpers.

Risks: this is high-risk MM code. Page-table movement must not lose PTEs, miss TLB flushes, or race rmap walkers. Fixed moves can invalidate the source VMA when destination overlaps the same broader VMA after unmap. Accounting must distinguish move, copy-like DONTUNMAP, shrink, and rollback. Multi-VMA moves are constrained because userfaultfd and custom `get_unmapped_area` can make fixed layout assumptions invalid. Hugetlb expansion is intentionally disallowed due to reservation limitations. Sealed VMAs must block all remap forms.

Test signals: `mremap` selftests for shrink, expand, MAYMOVE, FIXED, DONTUNMAP, overlap rejection, old_len zero shared mappings, multi-VMA move-only ranges with holes, mlocked expansion population, hugetlb/THP moves, KSM pages, userfaultfd remap event behavior, uffd-wp without remap events, file-backed VMAs with `may_split`/`mremap`, map-count limit failures, and fault/rmap stress during moves. KASAN/KCSAN, lockdep, MMU notifier/KVM stress, and soft-dirty tests are important.

# sources/distributed-fs/ceph-client/mm/mseal.c

Purpose: implements the `mseal` syscall, which marks a fully mapped virtual address range as sealed so later metadata-changing operations such as `munmap`, `mremap`, MAP_FIXED replacement, `mprotect`, pkey changes, and selected destructive advice can be denied by other MM paths.

Important APIs/types/functions: `do_mseal`, syscall `mseal`, `range_contains_unmapped`, and `mseal_apply`. Key types are `mm_struct`, `vm_area_struct`, `vma_iterator`, and `vma_flags_t`; the important state bit is `VMA_SEALED_BIT`.

Control flow: `do_mseal` rejects nonzero flags, strips address tags, requires a page-aligned start, page-aligns length, rejects length wrap and range overflow, and treats zero-length ranges as success. It then takes `mmap_write_lock_killable`, scans the range with `range_contains_unmapped` to ensure the start, middle, and end contain no holes, and on success makes a second pass with `mseal_apply`. The apply pass splits/merges VMAs as needed through `vma_modify_flags`, starts VMA write synchronization, and sets `VMA_SEALED_BIT`; already sealed VMAs are skipped as a no-op.

State and persistence: sealing is persistent in the process address space as a VMA flag until the VMA is destroyed with the process. There is no unseal operation. No disk data is written. The range must be completely mapped at seal time because unmapped holes could later be filled with unsealed mappings and mislead callers about the protected extent.

Dependencies and integration points: uses mmap write locking, VMA iterators, VMA flag modification helpers, and `internal.h`. Other files enforce the seal: `mprotect_fixup` returns `-EPERM`, `mremap` rejects sealed VMAs, and unmap/MAP_FIXED/madvise paths are expected to consult VMA sealing before destructive metadata changes.

Risks: the two-pass scan/apply logic relies on the write lock to keep topology stable. Range-hole detection must catch leading, internal, and trailing gaps. VMA splitting/merging can still fail with OOM or map-count pressure. Any MM path that modifies sealed metadata but forgets to check `vma_is_sealed` would undermine the syscall guarantee.

Test signals: `mseal` syscall tests for alignment, flags, zero length, overflow, unmapped leading/internal/trailing holes, repeated sealing, partial-VMA sealing that forces splits, and denial of `mprotect`, `pkey_mprotect`, `mremap`, `munmap`, and MAP_FIXED replacement after sealing. Stress tests should include map-count/OOM split failures and concurrent faults while sealing under the write lock.

# sources/distributed-fs/ceph-client/mm/msync.c

Purpose: implements the `msync` syscall for synchronizing shared file-backed mappings over a virtual address range. Modern `MS_ASYNC` is intentionally a no-op for I/O initiation; `MS_SYNC` delegates to filesystem `fsync` over mapped file ranges, and `MS_INVALIDATE` rejects locked mappings.

Important APIs/types/functions: syscall `msync`, `find_vma`, `vfs_fsync_range`, `get_file`, `fput`, and mmap read locking helpers. Key types are `mm_struct`, `vm_area_struct`, `file`, and file offsets (`loff_t`).

Control flow: the syscall strips address tags, validates flags, page alignment, mutually exclusive `MS_ASYNC`/`MS_SYNC`, page-aligns length, detects overflow, and returns success for empty ranges. It takes `mmap_read_lock`, finds the first VMA, and loops until the end address. Gaps are ignored for work purposes but recorded as a final `-ENOMEM`; with pure `MS_ASYNC`, a gap returns immediately because no further work is needed. `MS_INVALIDATE` fails with `-EBUSY` on locked VMAs. For each shared file-backed VMA under `MS_SYNC`, it computes file offsets from VMA start and `vm_pgoff`, takes a file reference, drops `mmap_lock`, calls `vfs_fsync_range(file, fstart, fend, 1)`, releases the file, and reacquires the read lock if more VMAs remain.

State and persistence: it does not change VMA topology. Persistent effects are filesystem-specific writeback/synchronization side effects from `vfs_fsync_range`. It may return a remembered `-ENOMEM` for holes even if all mapped parts synced successfully. File references protect the file while the mmap lock is dropped.

Dependencies and integration points: integrates with VMA lookup in `mmap.c`, VFS `fsync` implementations, shared mapping semantics, locked-VMA state, and tagged address handling. Filesystem clients with mmap support, including distributed filesystems in this source tree, observe this through their `fsync` operation rather than through direct code in `msync.c`.

Risks: dropping and reacquiring `mmap_lock` around filesystem sync means VMA topology can change; the loop restarts lookup at the next virtual address. Offset computation must avoid syncing the wrong file range. `MS_ASYNC` behavior may surprise legacy expectations but is explicitly documented in the code. Locked mappings with invalidation must fail consistently.

Test signals: `msync` tests for invalid flags, unaligned addresses, length overflow, empty range, holes returning `-ENOMEM`, `MS_ASYNC` no-op behavior, `MS_SYNC` on private vs shared and anonymous vs file-backed mappings, `MS_INVALIDATE` against mlocked VMAs, and filesystem error propagation from `vfs_fsync_range`.
