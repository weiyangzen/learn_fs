# sources/distributed-fs/ceph-client/drivers/net/ethernet/pensando/ionic/ionic_if.h

Purpose: This header is the firmware and hardware ABI for the Ionic network device. It defines the command opcodes, status codes, queue descriptor formats, identity/configuration blocks, notification events, statistics layouts, and BAR register structures shared by the Ethernet driver, RDMA support, firmware update path, and low-level device helpers.

Important APIs/types: `enum ionic_cmd_opcode` is the central command namespace for device, port, LIF, queue, VF, CMB, QoS, RDMA, and firmware commands. `enum ionic_status_code` is translated by `ionic_error_to_errno()` in `ionic_main.c`. `struct ionic_admin_cmd` and `struct ionic_admin_comp` are the generic admin queue wire format, with `color_match()` checking CQ ownership. Identity/configuration contracts include `union ionic_drv_identity`, `union ionic_dev_identity`, `union ionic_lif_identity`, `union ionic_lif_config`, `union ionic_port_identity`, `union ionic_q_identity`, `union ionic_discover_cmb_identity`, and the deprecated aggregate `struct ionic_identity`. Queue formats include `struct ionic_q_init_cmd`, `struct ionic_q_init_comp`, Tx/Rx descriptors, SG descriptors, and completions. `encode_txq_desc_cmd()` and `decode_txq_desc_cmd()` pack and unpack Tx descriptor opcode, flags, SG count, and 52-bit DMA address fields. `union ionic_dev_cmd`, `union ionic_dev_cmd_comp`, `union ionic_adminq_cmd`, and `union ionic_adminq_comp` provide typed views over fixed-size MMIO/admin ring command slots. Hardware register maps include `union ionic_dev_info_regs`, `union ionic_dev_cmd_regs`, `union ionic_dev_regs`, `struct ionic_hwstamp_regs`, `struct ionic_doorbell`, and `struct ionic_intr_status`.

Control flow: The file itself has no runtime control flow beyond inline bit packing and `color_match()`. Its declarations drive the runtime flows in `ionic_main.c` and `ionic_lif.c`: driver identify writes `union ionic_drv_identity` into devcmd side data, firmware returns `union ionic_dev_identity`, LIF init passes a DMA address for `struct ionic_lif_info`, queue init supplies ring bases and features, and admin completions return typed command results. Notify queue events use `union ionic_notifyq_comp` so `ionic_notifyq_service()` can switch on event code and enqueue link or reset work.

State and persistence behavior: Most structures describe firmware-owned or DMA-shared state rather than persistent kernel state. `struct ionic_lif_info` and `struct ionic_port_info` are coherent DMA memory populated by firmware and later read by the driver for link status, configuration, and statistics. Identity unions are snapshots captured during probe or reset recovery. Descriptor rings and completions are persistent while queues are initialized and are interpreted with color bits and ring indices. Firmware status, heartbeat, serial, firmware version, and current timestamp are exposed via BAR0 device info registers.

Dependencies: The header assumes Linux bit macros, endian types, DMA-address conventions, and IO register access performed by callers. It is included by Ionic device, queue, LIF, Tx/Rx, ethtool, PHC, firmware, and RDMA support. It is the bridge between Linux netdev/PTP concepts and the device firmware contract.

Integration points: Netdev offload negotiation maps `enum ionic_eth_hw_features` to `NETIF_F_*` flags. Hardware timestamping uses `enum ionic_txstamp_mode`, `enum ionic_pkt_class`, `struct ionic_lif_setphc_cmd`, and `struct ionic_hwstamp_regs`. SR-IOV netdev ops use `struct ionic_vf_setattr_cmd` and related VF enums. RSS uses `IONIC_RSS_HASH_KEY_SIZE`, `enum ionic_rss_hash_types`, and the RSS payload in `struct ionic_lif_setattr_cmd`. RDMA consumes LIF/RDMA identity, RDMA reset/create queue commands, and doorbell/CMB layout.

Risks: ABI drift is the primary risk: structure sizes, packing, endian annotations, bit assignments, queue feature versions, and BAR offsets must remain synchronized with firmware. Descriptor bitfield mistakes can corrupt DMA addresses or offload flags. The 52-bit address mask and packed unions require care on new hardware. Feature bits are shared across netdev, timestamping, CMB, and RDMA paths, so adding a bit without updating all consumers can silently disable or misconfigure capabilities.

Test signals: Compile-time coverage should catch missing enum/field consumers, but ABI correctness needs probe tests against supported firmware, queue bring-up, Tx/Rx traffic with checksum/TSO/VLAN/RSS, link event handling, SR-IOV VF configuration, CMB discovery, firmware update commands, and PTP hardware timestamp tests. Dynamic debug dumps in admin/dev command paths help verify exact command bytes and completions.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/pensando/ionic/ionic_lif.c

Purpose: This is the main Logical Interface implementation for the Ionic Ethernet driver. It owns netdev allocation and registration, LIF initialization, admin/notify/Tx/Rx queue lifecycle, interrupt/NAPI setup, link-state handling, netdev operations, feature negotiation, RSS, RX filters, SR-IOV VF controls, XDP setup, hardware timestamp queue plumbing, queue reconfiguration, and firmware reset recovery.

Important APIs/functions: Public entry points include `ionic_lif_alloc()`, `ionic_lif_init()`, `ionic_lif_register()`, `ionic_lif_unregister()`, `ionic_lif_deinit()`, `ionic_lif_free()`, `ionic_lif_identify()`, `ionic_lif_size()`, `ionic_restart_lif()`, `ionic_qcqs_free()`, `ionic_txrx_free()`, `ionic_stop_queues_reconfig()`, `ionic_reconfigure_queues()`, `ionic_lif_rss_config()`, `ionic_lif_rx_mode()`, `ionic_lif_deferred_enqueue()`, `ionic_link_status_check_request()`, and hardware timestamp helpers exported to `ionic_phc.c`. Internal key paths include `ionic_qcq_alloc()`, `ionic_qcq_enable()`, `ionic_qcq_disable()`, `ionic_lif_txq_init()`, `ionic_lif_rxq_init()`, `ionic_txrx_alloc()`, `ionic_txrx_init()`, `ionic_txrx_enable()`, `ionic_start_queues()`, `ionic_stop_queues()`, `ionic_open()`, `ionic_stop()`, `ionic_lif_handle_fw_down()`, and `ionic_lif_handle_fw_up()`. `ionic_netdev_ops` binds the implementation to Linux netdev callbacks.

Control flow: Probe sizing starts with `ionic_lif_size()`, which reads firmware queue/interrupt capacity, reserves timestamp queues when supported, and allocates IRQ vectors while falling back to fewer notify, event, or Tx/Rx queues. `ionic_lif_alloc()` allocates the netdev, LIF identity, DMA LIF info block, affinity masks, admin/notify QCQs, Tx/Rx QCQ arrays, RSS table, PHC state, locks, work items, and debugfs nodes. `ionic_lif_init()` issues a LIF devcmd, maps the kernel doorbell page, initializes adminq and notifyq, negotiates netdev features, initializes RX filters, programs the station MAC, and marks `IONIC_LIF_F_INITED`. `ionic_lif_register()` registers PHC, netdevice notifier, and netdev, then requests an initial link check.

Queue flow: `ionic_open()` allocates Tx/Rx QCQs, initializes firmware queues, sets real netdev queue counts, starts queues only if carrier is already up, and recreates timestamp queues if needed. Tx/Rx queue allocation builds DMA rings, CQ rings, SG rings, optional CMB rings, page pools for RX, NAPI structs, debugfs mappings, IRQs, and coalescing defaults. Queue initialization sends `IONIC_CMD_Q_INIT`, stores firmware hardware queue IDs/types, sets doorbell values, and adds NAPI callbacks. Enabling fills RX rings, sends `IONIC_Q_ENABLE`, enables NAPI, unmasks interrupts, and wakes netdev Tx queues. Stop/deinit/free reverse these stages by disabling netdev Tx, masking interrupts, synchronizing IRQs, disabling NAPI, quiescing the LIF, unregistering XDP RXQ info, emptying rings, freeing page pools, DMA memory, CMB mappings, IRQs, and QCQ shells.

Event and deferred control flow: Adminq NAPI services notifyq events, admin completions, and special timestamp queues, then returns interrupt credits and optionally pokes doorbells for the workaround path. Notifyq link events enqueue or perform `ionic_link_status_check()`, which starts queues and carrier on link up or stops queues and carrier on link down. Notifyq reset events enqueue `IONIC_DW_TYPE_LIF_RESET`; the worker runs either firmware-down teardown or firmware-up restart. Deferred RX mode work syncs kernel UC/MC lists and firmware filters outside atomic netdev callbacks.

State and persistence behavior: `struct ionic_lif` is the durable per-netdev state: state bits, locks, QCQ pointers, firmware identity, coherent LIF info, RSS key/table, RX filter database, queue dimensions, coalescing settings, PHC pointer, XDP program, and doorbell state. `IONIC_LIF_F_INITED`, `IONIC_LIF_F_UP`, `IONIC_LIF_F_FW_RESET`, `IONIC_LIF_F_FW_STOPPING`, `IONIC_LIF_F_BROKEN`, split-interrupt and CMB flags gate lifecycle transitions. Coherent `lif->info` persists firmware status/statistics across queue lifetimes until LIF free. RSS key/indirection and VF attributes are replayed after firmware reset. XDP program pointers are installed with `READ_ONCE`/`WRITE_ONCE` and released with `bpf_prog_put()`.

Dependencies: The implementation depends on Linux netdevice, NAPI, IRQ affinity, PCI/MSI, DMA coherent allocation, page pool, XDP RXQ info, DIM interrupt moderation, rtnetlink-safe netdev callbacks, workqueues, timers, and debugfs. Internal dependencies include `ionic_dev.h` devcmd helpers, `ionic_txrx.h` datapath functions, `ionic_rx_filter.h`, `ionic_ethtool.h`, `ionic_bus.h`, `ionic_aux.h`, CMB helpers, heartbeat/watchdog logic, and the ABI in `ionic_if.h`.

Integration points: Netdev callbacks expose open/stop/xmit/BPF/XDP xmit/stats/rx mode/features/MAC/MTU/VLAN/VF/hwtstamp operations. Firmware integration uses devcmds for LIF/adminq init and adminq commands for queue control, features, filters, RSS, MTU, MAC, and timestamp mode. PTP integration uses special hardware timestamp Tx/Rx queues and filter steering. RDMA/auxbus integration unregisters during firmware down and re-registers after restart. Debugfs exposes LIF and QCQ state, and ethtool consumes queue/coalescing/RSS facilities.

Risks: Queue lifecycle ordering is delicate: IRQ/NAPI enablement, adminq availability, DMA ring ownership, and firmware queue state must stay synchronized on normal open/stop, reconfiguration, timeout recovery, and firmware reset. `ionic_reconfigure_queues()` swaps live queue resources and can leak or miswire interrupts if unwind paths diverge. CMB reconfiguration frees before reallocating because device memory is scarce, raising restore risk. Link and reset work crosses atomic/worker contexts and must respect state bits. XDP is incompatible with split interrupts and constrained by MTU/frags. Firmware command failures during stop/restart can leave queues disabled or the LIF marked broken. VF replay intentionally ignores many return values, so failed replay may only show indirectly.

Test signals: Exercise probe/remove, `ip link set up/down`, carrier transitions, surprise firmware reset/down/up, Tx timeout recovery, queue count/descriptor/coalescing reconfiguration, split-interrupt toggling, CMB rings, RSS changes, VLAN filter add/delete, promiscuous/allmulti/filter overflow, MAC changes on PF/VF, SR-IOV VF set/get stats/config, XDP attach/detach with MTU limits and redirects, hardware timestamp queue creation, and kdump minimal queue sizing. Runtime signals include netdev carrier messages, debugfs QCQ entries, adminq errors, DIM coalescing changes, IRQ affinity masks, and `rtnl_link_stats64` counters.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/pensando/ionic/ionic_lif.h

Purpose: This header declares the core LIF state model, QCQ container, per-queue software statistics, PHC state, queue reconfiguration parameters, inline helpers, and cross-file LIF APIs used by the Ionic Ethernet driver, PTP hardware timestamping, datapath, ethtool, RX filter, and RDMA/auxiliary integration code.

Important APIs/types: `struct ionic_qcq` wraps queue, completion queue, interrupt info, NAPI, DIM, debugfs, DMA/CMB ring backing, SG backing, and optional doorbell work. `struct ionic_lif` is the central per-netdev object containing netdev pointer, state bitmap, locks, admin/notify/Tx/Rx QCQs, timestamp queues, deferred work, doorbell page, queue counts/descriptors, feature masks, RX filter state, RSS table/key, coalescing config, PHC, debugfs, and XDP program. `struct ionic_phc` holds cyclecounter/timecounter, PTP clock info, timestamp config, and synchronization for hardware clock operations. `struct ionic_queue_params` captures mutable queue settings used by ethtool/XDP/timestamp reconfiguration. Inline helpers include `ionic_init_queue_params()`, `ionic_set_queue_params()`, `ionic_coal_usec_to_hw()`, and `ionic_txq_hwstamp_enabled()`. Public prototypes expose LIF lifecycle, link checks, address filters, queue reconfiguration, RSS, RX mode, PHC/hwtstamp, and timestamp queue operations.

Control flow: The header does not execute major logic but codifies state transitions used in `ionic_lif.c`. Queue parameters are snapshotted before reconfiguration, mutated, and then either applied or restored. Conditional PTP stubs compile hwtstamp operations to `-EOPNOTSUPP` or no-ops when `CONFIG_PTP_1588_CLOCK` is disabled, allowing netdev ops to remain present without requiring PHC support.

State and persistence behavior: `enum ionic_lif_state_flags` defines the lifecycle and recovery flags persisted in `lif->state`: initialized, queues up, link check requested, filter sync needed, firmware reset/stopping, split interrupts, broken state, DIM enablement, and CMB Tx/Rx rings. Per-queue stats persist separately from firmware stats and include Tx offload, DMA-map, timestamp, and XDP counters. `struct ionic_phc` persists the requested hwtstamp configuration so it can be replayed after firmware reset and queue recreation.

Dependencies: The header depends on Linux PTP/timecounter APIs, net timestamp config, DIM, PCI, BPF forward declarations through included driver headers, `ionic_rx_filter.h`, and the queue/API types in `ionic_api.h`. It assumes `struct ionic`, `struct ionic_queue`, `struct ionic_cq`, and `struct ionic_intr_info` definitions from included Ionic internals.

Integration points: `q_to_qcq()`, `napi_to_qcq()`, and related macros link datapath queue callbacks back to the LIF container. `ionic_get_stats64()` is wired into netdev ops. PHC prototypes are consumed by `ionic_phc.c` and netdev hwtstamp ops. `ionic_reconfigure_queues()` is used by ethtool queue settings, XDP attach/detach, CMB changes, and hardware timestamp RX-all mode. RX mode and RSS APIs are used by netdev callbacks and ethtool.

Risks: Because `struct ionic_lif` is shared across many files, field lifetime assumptions must remain stable. State bits are concurrency gates; adding or reusing bits without auditing worker, NAPI, firmware reset, and netdev paths can produce races. Conditional PTP stubs can hide timestamp feature paths in builds without `CONFIG_PTP_1588_CLOCK`, so callers must still handle `-EOPNOTSUPP`. Queue parameter helpers change state bits directly and need to stay aligned with allocation/reconfiguration unwind logic.

Test signals: Build with and without `CONFIG_PTP_1588_CLOCK`, with XDP and SR-IOV enabled. Exercise queue reconfiguration, PHC hwtstamp set/get, RX/TX stats accumulation, DIM coalescing updates, and firmware reset replay to validate state held in these structures. Static analysis should check lock coverage around `queue_lock`, `config_lock`, `adminq_lock`, PHC locks, and deferred work list use.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/pensando/ionic/ionic_main.c

Purpose: This file provides the module entry/exit path and the shared device/admin command control plane for the Ionic driver. It translates firmware statuses, formats command names for diagnostics, posts and waits for admin queue commands, polls devcmd MMIO completion, performs device/port identify/init/reset, and registers the bus driver and debugfs root.

Important APIs/functions: `ionic_error_to_errno()` maps `enum ionic_status_code` to Linux errno values and is exported in namespace `NET_IONIC`. `ionic_adminq_post_wait()` and `ionic_adminq_post_wait_nomsg()` post admin queue contexts and wait for completion. `ionic_adminq_post()`, `ionic_adminq_wait()`, `ionic_adminq_service()`, `ionic_notifyq_service()`, and `ionic_adminq_poke_doorbell()` implement the async adminq ring mechanics. Device command helpers include `ionic_dev_cmd_wait()`, `ionic_dev_cmd_wait_nomsg()`, `ionic_setup()`, `ionic_identify()`, `ionic_init()`, `ionic_reset()`, `ionic_port_identify()`, `ionic_port_init()`, and `ionic_port_reset()`.

Control flow: Admin queue posting takes `lif->adminq_lock`, verifies the admin QCQ exists, checks ring space and firmware heartbeat, stores the caller context in descriptor metadata, copies the command, and rings the queue doorbell. Completion service checks the CQ color and queue non-emptiness, copies the completion back into each matching context through `comp_index`, completes the wait object, and clears the context pointer. Wait loops use bounded time slices up to `DEVCMD_TIMEOUT`, periodically check heartbeat/FW-reset state, return `-ENXIO` if reset interrupts the command, and flush pending admin descriptors on timeout.

Device command flow: Devcmd waits poll BAR0 `done` while firmware is running and the max timeout has not expired. `IONIC_RC_EAGAIN` retries by clearing done, sleeping, and ringing the devcmd doorbell again if enough time remains. On firmware-down interruption or timeout, the command registers are cleaned. Identify writes the Linux driver identity to devcmd side-data, requests device identity version 2, copies device identity back, logs firmware version, and then identifies classic LIF capabilities. Port init allocates coherent `port_info`, sends port init, raises the port admin state, and unwinds DMA memory on failure.

State and persistence behavior: This file mutates durable device-level state in `struct ionic`: firmware/device identity, `idev->port_info`, `port_info_pa`, devcmd register contents, and the admin queue ring state inside the active LIF. It does not own netdev queue resources. Admin command contexts are caller-owned stack or heap objects that persist only until completion. `ionic_adminq_flush()` clears queued descriptors and contexts after timeout to avoid later completions touching stale wait contexts.

Dependencies: It depends on Linux module, dynamic debug, netdevice, UTS release identity, wait completion, jiffies, and MMIO helpers through Ionic internals. Internal dependencies include `ionic_bus_register_driver()`, `ionic_bus_unregister_driver()`, `ionic_debugfs_create/destroy()`, `ionic_dev_cmd_*()` helpers, heartbeat/FW status helpers, and the LIF identify API.

Integration points: The bus-specific PCI code calls setup/identify/init/reset and LIF/port routines during probe and removal. `ionic_lif.c`, `ionic_phc.c`, firmware update code, RX filter code, and RDMA integration use the exported adminq post/wait machinery. Notifyq service integrates firmware link/reset notifications with LIF deferred work. Module init/exit bracket driver lifetime by creating debugfs and registering/unregistering the Ionic bus driver.

Risks: Adminq timeout handling must prevent use-after-free of caller contexts; flush clears ctx pointers but pending firmware completions can still appear later. Returning success from `__ionic_adminq_post_wait()` when firmware is not running means callers must handle reset state separately. Device command retry on `EAGAIN` is time-budget dependent and could mask slow firmware. Port init sends port state up after init but only reports the first error, so a failed state change may be less visible. Locking order between devcmd mutex, adminq lock, heartbeat, and reset work is critical.

Test signals: Validate probe identify/init/reset paths, firmware version logging, devcmd timeout and `EAGAIN` retry behavior, adminq command success/failure/timeout, notifyq link and reset events, module load/unload, debugfs creation cleanup on bus registration failure, and port info DMA allocation/free. Fault injection for firmware down during adminq/devcmd waits is especially important.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/pensando/ionic/ionic_phc.c

Purpose: This file implements Ionic PTP Hardware Clock and Linux hardware timestamp configuration support. It maps Linux hwtstamp requests to Ionic firmware capabilities, creates dedicated timestamp queues and RX steering filters, registers a PHC, reads hardware timestamp registers, maintains cyclecounter/timecounter state, and sends PHC synchronization commands to firmware.

Important APIs/functions: Netdev hwtstamp entry points are `ionic_hwstamp_set()` and `ionic_hwstamp_get()`. Reset/open replay helpers are `ionic_lif_hwstamp_replay()` and `ionic_lif_hwstamp_recreate_queues()`. PHC lifecycle functions are `ionic_lif_alloc_phc()`, `ionic_lif_register_phc()`, `ionic_lif_unregister_phc()`, and `ionic_lif_free_phc()`. PTP clock callbacks include `ionic_phc_adjfine()`, `ionic_phc_adjtime()`, `ionic_phc_settime64()`, `ionic_phc_gettimex64()`, and `ionic_phc_aux_work()`. `ionic_lif_phc_ktime()` converts raw hardware ticks from Tx/Rx completions to `ktime_t`.

Control flow: `ionic_hwstamp_set()` takes `lif->queue_lock`, then `ionic_lif_hwstamp_set_ts_config()` serializes timestamp configuration with `phc->config_lock`. TX modes are mapped from `HWTSTAMP_TX_*` to `IONIC_TXSTAMP_*` and checked against firmware capability bits. RX filters are mapped from `HWTSTAMP_FILTER_*` to Ionic packet-class masks; unsupported specific filters fall back to `HWTSTAMP_FILTER_ALL` and RX-all queue feature reconfiguration. Enabling TX or specific RX timestamping creates special hardware timestamp queues through LIF helpers, sets firmware TX timestamp mode, installs RX steering filters, and stores the requested config for later get/replay. On partial failure it reverts changed RX filter and TX mode but leaves special queues allocated.

PHC flow: `ionic_lif_alloc_phc()` validates hardware timestamp registers and feature bits, allocates `struct ionic_phc`, initializes a `cyclecounter` from firmware mask/mult/shift, optionally scales multiplier/shift for finer adjustment headroom, initializes the `timecounter` to current real time, computes an auxiliary worker delay near one quarter of wrap period, and copies `ionic_ptp_info`. Registration calls `ptp_clock_register()` and schedules auxiliary work. PTP adjustments reject firmware reset state, update the local timecounter under `phc->lock`, post `IONIC_CMD_LIF_SETPHC` through adminq, drop the lock, and then wait for completion. `gettimex64` reads hardware tick registers with system timestamp bracketing and converts to nanoseconds.

State and persistence behavior: `phc->ts_config`, `ts_config_tx_mode`, and `ts_config_rx_filt` persist the user's requested timestamping mode for `SIOCGHWTSTAMP`, firmware reset replay, and queue recreation after stop/open. `phc->cc` and `phc->tc` are protected by a spinlock and represent the current PHC conversion state. Firmware receives synchronized tick/nsec/frac/mult/shift via `LIF_SETPHC` commands. During firmware reset, PHC operations return `-EBUSY` or keep polling without updating basis, so external PTP daemons must restore time afterward.

Dependencies: This file depends on Linux PTP clock APIs, `kernel_hwtstamp_config`, netdev hwtstamp ops, system timestamp helpers, timecounter/cyclecounter math, and Ionic admin queue and LIF queue helpers. It consumes ABI fields `hwstamp_tx_modes`, `hwstamp_rx_filters`, `hwstamp_mask`, `hwstamp_mult`, `hwstamp_shift`, `IONIC_ETH_HW_TIMESTAMP`, packet-class bits, and `struct ionic_hwstamp_regs`.

Integration points: Netdev ops in `ionic_lif.c` call hwtstamp set/get. LIF register/unregister/free call PHC lifecycle routines. LIF firmware-up recovery calls `ionic_lif_hwstamp_replay()`, and netdev open calls `ionic_lif_hwstamp_recreate_queues()`. Tx/Rx completion paths can call `ionic_lif_phc_ktime()` to translate hardware ticks. Firmware integration is through `IONIC_CMD_LIF_SETPHC`, timestamp TX mode setattr, RX filter steering, and RX queue feature reconfiguration.

Risks: Timestamp configuration spans queue allocation, firmware attributes, RX filters, and queue reconfiguration; partial failure can leave allocated but unused timestamp queues by design. RX filter fallback to all timestamp packets may increase traffic to timestamp queues. Hardware tick read assumes high cannot change twice during the reread window. Multiplier/shift scaling must avoid overflow and preserve wrap-period assumptions. PHC state is not maintained across firmware upgrade/reset, so callers must tolerate `-EBUSY` and resynchronize. Lock ordering among `queue_lock`, `config_lock`, `phc->lock`, and adminq waits is important.

Test signals: Build with PTP enabled and disabled. Run `hwstamp_ctl`/`ethtool -T` style checks for supported TX/RX modes, invalid mode rejection, `SIOCGHWTSTAMP`, PHC registration under `/dev/ptp*`, `phc2sys`/`ptp4l` adjustment paths, firmware reset replay, open/stop queue recreation, specific PTP and RX-all filtering, Tx/Rx hardware timestamp counters, and fault injection for adminq failures during TX mode or RX filter changes.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/pensando/ionic/ionic_regs.h

Purpose: This header provides the low-level MMIO helper contract for Ionic interrupt-control registers and queue doorbells. It defines the interrupt register layout, legal mask/credit bit encodings, coalescing maximums, doorbell bit packing macros, and inline write/read helpers used by queue and NAPI code.

Important APIs/types: `struct ionic_intr` maps one interrupt-control register block with `coal_init`, `mask`, `credits`, `mask_assert`, and current `coal`. `enum ionic_intr_mask_vals` defines mask and unmask values. `enum ionic_intr_credits_bits` defines the credit count mask, signed count mask, unmask bit, reset-coalesce bit, and combined rearm value. Inline functions are `ionic_intr_coal_init()`, `ionic_intr_mask()`, `ionic_intr_credits()`, `ionic_intr_clean()`, `ionic_intr_mask_assert()`, and `ionic_dbell_ring()`. Doorbell macros `IONIC_DBELL_QID()` and `IONIC_DBELL_RING()` compose queue ID and ring selector fields, with `IONIC_DBELL_INDEX_MASK` reserved for producer index bits supplied by callers.

Control flow: These helpers are small MMIO operations. Queue setup initializes coalescing and masks interrupts. Queue enable cleans credits, enables NAPI, installs affinity hints, and unmasks with `ionic_intr_mask()`. NAPI completion returns processed credits plus unmask/reset flags with `ionic_intr_credits()`. Queue disable masks interrupts and synchronizes IRQs. Doorbell ring writes a 64-bit value to the queue-type slot in a mapped doorbell page.

State and persistence behavior: Interrupt mask, coalescing, and credit state live in device MMIO registers and persist until explicitly changed or device reset. `ionic_intr_clean()` preserves the signed outstanding credit count while resetting coalescing. `ionic_intr_credits()` guards against credit values larger than the hardware count field and falls back to the current signed count before writing flags.

Dependencies: The header depends on Linux `io.h` accessors and the device BAR mappings established by bus/device code. It is consumed by `ionic_lif.c`, queue code, adminq service, and datapath NAPI handlers.

Integration points: Interrupt helpers integrate with MSI-X allocation, NAPI poll completion, DIM coalescing updates, queue enable/disable, and firmware queue initialization through interrupt indices. Doorbell helpers integrate with queue producer updates for admin, notify, Tx, Rx, and RDMA-style queues via the mapped per-LIF doorbell page.

Risks: Incorrect credit accounting can leave interrupts masked, over-credit hardware, or produce interrupt storms. Coalescing values are device units, so callers must convert from microseconds correctly. Doorbell writes rely on qtype indexing into the mapped page; wrong qtype or QID composition can ring the wrong queue. MMIO ordering assumptions are delegated to `iowrite32()`/`writeq()` and caller-side queue posting barriers.
