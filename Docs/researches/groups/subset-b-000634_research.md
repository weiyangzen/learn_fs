# sources/distributed-fs/ceph-client/arch/arm/boot/dts/nxp/imx/imx35-pinfunc.h

Purpose: `sources/distributed-fs/ceph-client/arch/arm/boot/dts/nxp/imx/imx35-pinfunc.h` is the Linux Devicetree pin-function catalog for NXP/Freescale i.MX35 pads. It is included by `imx35.dtsi` and exposes named preprocessor macros that board DTS files place in `fsl,pins` arrays. Each macro gives the pinctrl driver the SoC-specific mux register offset, pad-control register offset, optional input-select register offset, mux mode, and daisy-chain input value for one pad/function pairing.

Important APIs/types/functions: this file defines no C functions, structs, enums, or runtime APIs. Its external interface is a set of `#define MX35_PAD_<pad>__<function>` macros. The header guard is `__DTS_IMX35_PINFUNC_H`, and the shared tuple contract is documented as `<mux_reg conf_reg input_reg mux_mode input_val>`. I counted 952 pin-function macros over 283 unique pad names and about 40 first-level function prefixes. High-volume function families include `IPU` display/camera routes, `EMI` external-memory routes, `ARM11P` event/debug bus routes, `GPIO1`/`GPIO2`/`GPIO3`, `USB_TOP`, `KPP`, `SDMA`, `ATA`, `CSPI`, `AUDMUX`, `UART`, `FEC`, `ESDHC`, `CCM`, `SPDIF`, and `ESAI`. Pad-name clusters are especially heavy around ATA, FEC, SD1/SD2, CSI/display (`D3`, `LD*`), CSPI, I2C, and UART signal groups.

Control flow: there is no executable control flow in the header. The effective flow is build-time and boot-time data flow: a DTS includes `imx35.dtsi`, which includes this header; board pinctrl nodes list one or more `MX35_PAD_*` macros followed by a board-specific pad-control value; `dtc` expands each macro into numeric cells; at runtime the Freescale i.MX pinctrl driver consumes the cells and writes the mux, config, and input-select registers. Macros with an `input_reg` of `0x000` do not require a daisy-select write, while nonzero `input_reg` plus `input_val` selects one routed input source for peripherals with shared inputs.

State and persistence behavior: the file stores no mutable runtime state. It is persistent hardware-description data that becomes part of compiled DTBs and overlays. Runtime pin state is created when the kernel applies pinctrl states from the DTB, and the important persistent values are the register offsets and mux/daisy literals in each macro. The final pad electrical configuration is not fully encoded here; board DTS entries append a pad-control word such as `0x80000000` or `0x1c5`, so this header supplies the SoC mux identity while each board supplies drive, pull, hysteresis, and similar policy.

Dependencies and integration points: the file depends only on the C preprocessor used by DTS compilation and on the i.MX pinctrl binding's cell ordering. Local integration points include `imx35.dtsi`, `imx35-eukrea-cpuimx35.dtsi`, `imx35-eukrea-mbimxsd35-baseboard.dts`, and `imx35-pdk.dts`, which use these macros for FEC Ethernet, I2C, SD/MMC, UART, audio, GPIO, and card-detect/power pins. The data must stay synchronized with the i.MX35 IOMUXC register map and with the Linux driver that interprets the five-cell tuple plus the appended config cell.

Risks: every macro is ABI-like device-tree data, so a typo in a register offset, mux mode, or daisy value can compile cleanly while routing a board signal to the wrong peripheral. The highest-risk entries are nonzero input-select macros, reused input registers with different `input_val` values, and pads that can route to unrelated high-impact functions such as FEC, SD/MMC, USB, display, debug/event bus, watchdog/reset, or boot/control signals. Because many board files use old, literal pad-control values, changing macro names or tuple order can break DTS compilation or silently change hardware behavior.

Test signals: useful static checks are `make dtbs_check` or at least `make ARCH=arm dtbs` for i.MX35 boards, plus targeted `dtc` builds of `imx35-pdk.dtb` and Eukrea i.MX35 DTBs. A simple tuple-shape check should verify that every `MX35_PAD_` macro expands to exactly five numeric cells. Runtime validation requires board boot logs from pinctrl, successful Ethernet/SD/UART/I2C probing, and peripheral-specific smoke tests for pins using nonzero daisy-select registers.

# sources/distributed-fs/ceph-client/arch/arm/boot/dts/nxp/imx/imx50-pinfunc.h

Purpose: `sources/distributed-fs/ceph-client/arch/arm/boot/dts/nxp/imx/imx50-pinfunc.h` is the Linux Devicetree pin-function catalog for the i.MX50 SoC. It provides symbolic `MX50_PAD_<pad>__<function>` macros used by i.MX50 board DTS pinctrl states. The macros translate readable pad/function names into the numeric mux register, config register, input-select register, mux mode, and input daisy value consumed by the i.MX pinctrl driver.

Important APIs/types/functions: this is a declarative preprocessor header, not an implementation file. It has the guard `__DTS_IMX50_PINFUNC_H` and repeats the standard pin-function tuple comment `<mux_reg conf_reg input_reg mux_mode input_val>`. I counted 905 macros over 171 unique pads and about 54 first-level function prefixes. The catalog is dense because many pads expose many alternates. Major function families include `EIM`, `ELCDIF`, `EPDC`/`EPCD`, `SDMA`, `USBPHY1`, `USBPHY2`, `KPP`, GPIO banks 1 through 6, `AUDMUX`, `SRC`, `ESDHC1` through `ESDHC4`, `FEC`, `TPIU`, `CCM`, `CSPI`, `ECSPI`, `SSP`, `UART`, `I2C`, `PWM`, and debug/observe routes. Pad clusters are dominated by EPDC/e-paper display controller pins, display pins, EIM pins, SD2/SD3, key matrix, SSI, ECSPI, UART, and I2C pads.

Control flow: the file contributes no branches or runtime calls. The data path is DTS preprocessing into `fsl,pins`: `imx50.dtsi` includes this header, board nodes choose macros such as FEC-over-display pins, eSDHC pins, e-paper controller pins, GPIOs, or UART/I2C pins, and the compiled DTB gives the pinctrl driver numeric cells. During pinctrl state application, the driver programs mux and pad-control registers and, when `input_reg` is nonzero, programs the daisy-select value that chooses which pad feeds a peripheral input.

State and persistence behavior: all state is static hardware description persisted in source and compiled DTB form. The header defines SoC routing capabilities, while board DTS files append pad-control values to encode electrical state. The runtime kernel does not modify this header; it recreates pin state at boot, resume, or overlay application from the DTB. Macros exposing boot/source configuration, reset, USB PHY, trace, and EPDC routes are particularly state-sensitive because they can affect early boot straps, display bring-up, debug visibility, or external bus behavior.

Dependencies and integration points: integration is through `imx50.dtsi` and board files such as `imx50-evk.dts` and `imx50-kobo-aura.dts`. The EVK uses these macros for CSPI, FEC, and UART routing; the Kobo Aura board uses extensive EPDC, GPIO, I2C, SD/MMC, ECSPI, PWM, and UART pin groups. The header must remain aligned with the i.MX50 IOMUXC reference manual, the common Freescale/NXP pinctrl cell binding, and the `pinctrl-imx` driver family.

Risks: risk is concentrated in alternate-function density and daisy-select literals. A wrong `input_val` on shared UART, FEC, SDMA, EIM/NAND, or USB over-current/power inputs can leave drivers probing correctly but receiving no signal. The EPDC-heavy pad set means display and e-reader boards can regress through apparently unrelated changes to GPIO or EIM alternates. Macro renames are also risky because DTS sources refer to these names directly; tuple order or field-count errors fail or miscompile pinctrl data.

Test signals: run `make ARCH=arm dtbs` for i.MX50 DTBs, with focus on `imx50-evk.dtb` and `imx50-kobo-aura.dtb`, and run `dtbs_check` where schemas are available. Static tests should ensure each `MX50_PAD_` macro has exactly five tuple cells and that nonzero input-select registers are intentional. Hardware smoke tests should cover EPDC/display, SD card detection and data transfer, FEC networking, I2C devices, UART consoles, SPI chip-select GPIOs, and USB power/over-current pins on boards that use those routes.

# sources/distributed-fs/ceph-client/arch/arm/boot/dts/nxp/imx/imx51-pinfunc.h

Purpose: `sources/distributed-fs/ceph-client/arch/arm/boot/dts/nxp/imx/imx51-pinfunc.h` is the i.MX51 Devicetree pin-function definition header. It maps symbolic pad/function combinations to the numeric cells required by i.MX pinctrl nodes. Board DTS files use these macros in `fsl,pins` properties to request UART, SD/MMC, Ethernet, display, NAND, EIM, GPIO, audio, USB, keypad, camera, and other pinmux functions.

Important APIs/types/functions: the file exposes preprocessor macro constants only. It uses guard `__DTS_IMX51_PINFUNC_H` and documents the tuple format `<mux_reg conf_reg input_reg mux_mode input_val>`. I counted 754 macros over 245 unique pads and about 55 first-level function prefixes. Large function families include `EIM`, GPIO banks, `DISP1`, `DISP2`, `FEC`, `NANDF`, `USBH1`/`USBH2`/`USBH3`/`USBOTG`, `PATA`, `CSI1`, `CSI2`, `BOOT`, `KEY`, `CSPI`, `UART`, `AUD`, `SD1` through `SD4`, `I2C`, `DI`, and watchdog/clock/reset related routes. Pad-name clusters are led by EIM, NAND, display, USB host, GPIO, key matrix, camera, SD/MMC, CSPI, and audio pads.

Control flow: there is no in-file execution. The control path is indirect: `imx51.dtsi` includes this header, board-level pinctrl groups select macros, the DTS compiler expands each selected macro to five cells plus the appended pad-control cell, and the pinctrl driver writes the mux/config/daisy registers when a device's pinctrl state is selected. Macros with nonzero input-select offsets, such as UART, I2C, FEC, camera, and audio inputs, create an extra register-programming dependency beyond the pad mux mode itself.

State and persistence behavior: this header is static source data that persists into DTBs. It does not own live kernel state, but it defines how live pin state is reconstructed for every i.MX51 board at boot and during pinctrl state changes. Some entries have `conf_reg` set to `0x000` for pads or modes without a normal pad-control register in this map, so consumers must preserve the tuple values exactly rather than infer missing fields. Board files provide the electrical configuration word separately, so the stable contract is the SoC routing tuple, not board drive-strength policy.

Dependencies and integration points: the header integrates through `imx51.dtsi` and board DTS files such as `imx51-zii-scu3-esb.dts` and `imx51-ts4800.dts`. Those boards use the macros for ECSPI, SD1/SD4, FEC over display/EIM/NAND pads, I2C, GPIO, UART, and USB host control. The file depends on the common i.MX pinctrl binding and the i.MX51 IOMUXC register layout. It also interacts with subsystem drivers indirectly because a bad pin tuple can surface as failures in MMC, FEC Ethernet, SPI, I2C, display, audio, camera, or USB rather than as a pinctrl-specific error.

Risks: the main risk is silent hardware misrouting from wrong mux modes or input daisy values. i.MX51 has many remapped high-speed and board-critical functions across EIM, NAND, display, and USB pads; a single bad macro can break Ethernet RMII/RGMII-style signal groups, SD data widths, display bus pins, or console UARTs. The header also contains many similarly named functions (`UART*_TXD`, `UART*_RXD`, `*_CTS`, `*_RTS`, `DISP*`, `DI*`, `NANDF_*`), so copy/paste and off-by-one daisy values are plausible maintenance hazards.

Test signals: run `make ARCH=arm dtbs` for i.MX51 board DTBs and target known consumers such as ZII SCU3 ESB and TS-4800. Static validation should check that every `MX51_PAD_` macro has exactly five numeric tuple cells and that macro names remain unique. Functional signals are serial console operation, SD/MMC enumeration including 4-bit and 8-bit groups, FEC link and traffic, SPI/I2C device probing, display output, and USB host power/over-current behavior on boards using the relevant pin groups.

# sources/distributed-fs/ceph-client/arch/arm/boot/dts/nxp/imx/imx53-pinfunc.h

Purpose: `sources/distributed-fs/ceph-client/arch/arm/boot/dts/nxp/imx/imx53-pinfunc.h` is the i.MX53 pin-function macro catalog for Linux Devicetree. It provides the symbolic constants used in i.MX53 board pinctrl groups, mapping each pad/function selection to mux, pad-control, input-select, mux-mode, and daisy-select numeric cells for the common i.MX pinctrl driver.

Important APIs/types/functions: this file defines macros only; there are no functions, classes, structs, or runtime types. It uses guard `__DTS_IMX53_PINFUNC_H` and the tuple contract `<mux_reg conf_reg input_reg mux_mode input_val>`. I counted 1,175 macros over 201 unique pads and about 64 first-level function prefixes, making it the densest of this four-file group. Large function families include `IPU`, `EMI`, `SDMA`, `USBOH3`, `AUDMUX`, GPIO banks 1 through 7, `USBPHY1`, `USBPHY2`, `PATA`, `KPP`, `CSPI`, `CCM`, `SRC`, `ESAI1`, `ECSPI1`, `ECSPI2`, `FEC`, `TPIU`, `GPU3d`, `CAN`, `I2C`, `UART`, `SPDIF`, and security/debug routes. Pad-name clusters are led by EIM, PATA, DISP0, CSI0, GPIO, key matrix, FEC, NAND, SD1/SD2, DI0, and LVDS pads.

Control flow: the header itself is linear preprocessor data. Runtime flow starts when `imx53.dtsi` includes this file and board DTS files place `MX53_PAD_*` macros in `fsl,pins`. The compiler emits numeric cells; the pinctrl driver programs IOMUXC mux and config registers and applies select-input values for routed peripheral inputs. Because i.MX53 has many multiplexed display, camera, Ethernet, PATA, and EIM pins, a single board pinctrl state often combines macros from several physical pad clusters to build one peripheral bus.

State and persistence behavior: the file has no mutable state, persistence layer, or runtime allocation. It is persistent board-support data compiled into DTBs. The values here determine the mux identity and input routing, while board DTS pad-control cells determine electrical properties. On boot or pinctrl state changes, kernel state is recreated from those compiled cells. Some macros target early/control functions such as boot source, reset, PLL bypass, JTAG/security, and clock outputs, so their static values can affect debug, reset, and low-level board behavior as well as ordinary peripheral I/O.

Dependencies and integration points: the main include integration is `imx53.dtsi`. Board-level users include `imx53-sk-imx53.dts` and other i.MX53 boards that configure AUDMUX, CAN, clock output, ECSPI, SD/MMC, FEC, I2C, GPIO, NAND, PWM, UART, display, and camera groups. The macros depend on the i.MX53 IOMUXC register map and the common `pinctrl-imx` tuple interpretation. They also integrate indirectly with display/IPU, V4L2 camera, FEC networking, MMC, SPI, I2C, audio, USB, CAN, and GPIO consumers because those drivers depend on correct pinctrl states.

Risks: i.MX53's high alternate-function density makes copy/paste mistakes, wrong daisy values, and accidental mux-mode swaps the primary risk. Display and camera routes span many sequential data pins where one bad macro can cause subtle color, sync, or capture failures. FEC, SD/MMC, I2C, UART, CAN, and NAND signals require coherent multi-pin groups, so partial edits can leave a peripheral half-routed. Security/debug/reset/boot-related alternates should be treated carefully because a board may boot but lose recovery, JTAG, reset, or clock behavior.

Test signals: run `make ARCH=arm dtbs` for i.MX53 boards and `dtbs_check` as available. Static validation should verify each `MX53_PAD_` macro has five tuple cells and that macro names are unique. Hardware validation should include serial console, FEC link and traffic, SD/MMC transfers, I2C scans, SPI transactions, NAND access where present, display output, camera capture where routed, CAN traffic, USB host/device signals, and suspend/resume pinctrl behavior for boards using alternate low-power states.
