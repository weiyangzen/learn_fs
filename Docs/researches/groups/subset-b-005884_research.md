## sources/distributed-fs/ceph-client/include/linux/mfd/wm8350/supply.h

Purpose: this header is the public MFD-side contract for the WM8350 PMIC power-supply and charger child driver. It names the charger/readback registers, charger bitfields, logical charger and supply IRQ numbers, policy encoding helpers, and the runtime structures shared between the WM8350 core and `drivers/power/supply/wm8350_power.c`.

Important APIs, types, and constants: `WM8350_BATTERY_CHARGER_CONTROL_[1-3]` identify charger configuration/status registers; `WM8350_CHG_*` masks and values encode enable, end-of-charge current, trickle/fast state, USB throttling, current/voltage selections, status values, and timing. `WM8350_IRQ_CHG_*`, `WM8350_IRQ_USB_LIMIT`, and `WM8350_IRQ_EXT_*_FB` are indexes into the WM8350 core IRQ table. `WM8350_CHG_FAST_LIMIT_mA(x)`, `WM8350_CHG_EOC_mA(x)`, fixed voltage macros, and trickle-current/threshold macros translate board policy into register fields. `struct wm8350_charger_policy` carries board-selected charging limits and timeouts. `struct wm8350_power` stores the child platform device, three `power_supply` objects, a policy pointer, and a revision-G timing coefficient.

Control flow: the header contains no executable code, but it shapes the power driver flow. Probe obtains `wm8350->power`, reads the board policy, calls charger configuration, registers battery/USB/AC supplies, and registers the IRQs defined here. Charger configuration preserves the enable bit in control register 1, writes end-of-charge/trickle/USB-throttle policy, chooses USB or wall fast-current limits based on detected supplies, and writes charge timeout with revision-specific scaling. The IRQ handler switches on `irq - wm8350->irq_base` using the IRQ indexes from this header, reconfigures charging on fast-ready or supply-feedback events, sets `WM8350_CHG_FAST` when fast charging may start, and notifies the affected power-supply objects.

State and persistence: policy values are not persisted by this header; they are supplied by board/machine code and held through `wm8350_power.policy`. Hardware state persists in WM8350 charger registers across driver reads/writes, with protected writes requiring core unlock/lock sequencing in the consumer. `rev_g_coeff` affects timeout encoding and must match the chip revision. The `power_supply` pointers represent registered kernel objects and are notification targets when supply or charger state changes.

Dependencies and integration points: includes `linux/mutex.h` and `linux/power_supply.h`; depends on the parent `struct wm8350` from `wm8350/core.h` and IRQ registration in `drivers/mfd/wm8350-irq.c`; integrates with AUXADC/comparator definitions for voltage readings and supply detection. The power driver maps these fields to the power_supply class, sysfs charger-state reporting, and WM8350 register helpers.

Risks: policy macros do minimal validation. `WM8350_CHG_FAST_LIMIT_mA(x)` masks to four bits after division by 50, and `WM8350_CHG_EOC_mA(x)` masks after subtracting 10, so out-of-range policy inputs can silently wrap into valid-looking register fields. Missing policy prevents charger configuration. Incorrect IRQ numbering would break charger/supply event routing because handlers subtract the parent IRQ base. Revision coefficient or supply-detection mistakes can program an incorrect timeout or current limit. Register constants overlap protected PMIC state, so consumers must preserve unrelated bits and obey core locking.

Test signals: build coverage should include `CONFIG_WM8350_POWER`. Runtime signals include successful registration of battery/USB/AC supplies, correct `POWER_SUPPLY_PROP_STATUS` transitions for `WM8350_CHG_STS_OFF/TRICKLE/FAST`, charger_state sysfs text matching control register 2, IRQ notifications for hot/cold/fail/timeout/start/end/fast-ready and external supply feedback, rejected USB fast-current policies above 500 mA, and register traces showing expected writes to controls 1 and 2 for USB versus wall charging.

## sources/distributed-fs/ceph-client/include/linux/mfd/wm8350/wdt.h

Purpose: this header defines the WM8350 watchdog register masks, timeout IRQ number, and minimal child state structure used by the WM8350 watchdog platform driver. It is the MFD contract between the PMIC core register map and `drivers/watchdog/wm8350_wdt.c`.

Important APIs, types, and constants: `WM8350_WDOG_HIB_MODE`, `WM8350_WDOG_DEBUG`, `WM8350_WDOG_MODE_MASK`, and `WM8350_WDOG_TO_MASK` are fields in `WM8350_SYSTEM_CONTROL_2`. `WM8350_IRQ_SYS_WDOG_TO` names the watchdog-timeout interrupt index in the parent IRQ controller. `struct wm8350_wdt` currently stores only the watchdog child `platform_device`.

Control flow: the header has no functions, but the watchdog driver uses these masks when handling watchdog core operations. Probe retrieves the parent `struct wm8350`, sets the global `watchdog_device` parent and driver data, programs the default 4 second timeout, and registers with the watchdog framework. `set_timeout()` validates a table of supported 1, 2, and 4 second values, unlocks PMIC protected registers, clears `WM8350_WDOG_TO_MASK`, writes the selected timeout value, relocks, and updates `wdt_dev->timeout`. `start()` clears `WM8350_WDOG_MODE_MASK` and writes mode value `0x20`; `stop()` clears the same mode bits; `ping()` refreshes by rewriting `WM8350_SYSTEM_CONTROL_2`.

State and persistence: watchdog mode and timeout persist in the WM8350 system-control register until changed or reset. The Linux watchdog object is static in the driver and uses a module `nowayout` parameter; this header's `struct wm8350_wdt` is embedded in the parent core state and is used for platform-device ownership rather than per-open state. The timeout IRQ is represented in the MFD IRQ map even though the watchdog driver primarily uses the watchdog core callbacks.

Dependencies and integration points: includes `linux/platform_device.h`; relies on `wm8350/core.h` for system-control register access, protected-register lock/unlock, parent data, and the embedded `struct wm8350_wdt`. It integrates with the Linux watchdog framework, platform bus, WM8350 MFD child creation, and the WM8350 IRQ table.

Risks: only three timeout values are supported; unsupported values return `-EINVAL`. Protected-register lock/unlock must balance under the watchdog mutex or watchdog mode can be left partially configured. `start()` writes a literal mode field (`0x20`) rather than a named mode macro, so changes to field semantics would be easy to miss. The static watchdog device means the implementation assumes a single WM8350 instance. If the timeout IRQ number is changed inconsistently with the MFD IRQ map, timeout event reporting can break.

Test signals: build with `CONFIG_WM8350_WATCHDOG`; probe should register a watchdog named `WM8350 Watchdog` under platform device `wm8350-wdt`. Exercise `set_timeout` for 1, 2, 4, and invalid values, verify `WDOG_TO` bits in `WM8350_SYSTEM_CONTROL_2`, start/stop mode-bit transitions, keepalive rewriting of the register, `nowayout` behavior, and absence of lock imbalance or register-write failures.

## sources/distributed-fs/ceph-client/include/linux/mfd/wm8400-audio.h

Purpose: this large generated-style header is the WM8400 audio-codec register field map. It gives the WM8400 ASoC codec driver symbolic names for power, digital audio interface, clocking, DAC/ADC, GPIO-adjacent audio status, input/output mixers, anti-pop, microphone-bias, and FLL fields. It also declares the cache-reset hook exported by the MFD core.

Important APIs, types, and constants: the file defines register-field masks, shifts, widths, and enumerated values for audio registers from power management through FLL control. High-use groups include `WM8400_CODEC_ENA`, `WM8400_SYSCLK_ENA`, input/output enables, `WM8400_AIF_WL_*`, `WM8400_AIF_FMT_*`, clock dividers, DAC/ADC volume/filter bits, line-input volume/mute/zero-cross bits, speaker/Class-D fields, mixer route switches and volumes, `WM8400_SOFTST`/anti-pop bits, `WM8400_MICBIAS` fields, and `WM8400_FLL_*` masks. The only function declaration is `wm8400_reset_codec_reg_cache(struct wm8400 *wm8400)`.

Control flow: the header is declarative. In `sound/soc/codecs/wm8400.c`, these constants parameterize ALSA controls, TLV controls, DAPM widgets/routes, mixer route conflict checks, audio-interface format setup, clock and FLL programming, bias-level transitions, and reset handling. The codec driver calls `wm8400_reset_codec_reg_cache()` after a component reset so the shared regmap cache in the MFD core returns to defaults before normal audio paths are restored.

State and persistence: no C state is allocated here. Hardware audio state persists in WM8400 registers and is cached by the parent regmap (`REGCACHE_MAPLE` in `wm8400-core.c`). The generated masks must remain synchronized with both the silicon datasheet and the MFD register addresses in `wm8400-private.h`; otherwise ALSA controls will update the wrong bits. The cache-reset function intentionally mutates regmap cache state, not just software-local codec state.

Dependencies and integration points: includes itself by path, which is unusual but harmless due to include guards after the first definition; forward-declares `struct wm8400`; integrates with the WM8400 MFD core, ASoC codec driver, regmap cache, ALSA controls, DAPM graph, and machine-driver clock/format setup. It depends on address macros from `wm8400-private.h` when consumers combine register names with the field masks from this file.

Risks: generated field maps are brittle: a wrong mask/shift produces silent audio-control corruption. Some macros encode values rather than masks, so callers must use them with the correct register and mask. The self-include is confusing for static analysis and maintainers. Because this header exposes low-level register fields directly, there is little type checking for invalid combinations such as unsupported audio word length, route conflicts, FLL parameters, or power sequencing. Cache reset is a shared-core operation; calling it at the wrong time can discard dirty but intentional cached writes.

Test signals: compile the WM8400 codec and MFD core together; instantiate `wm8400-codec`; enumerate mixer and volume controls that reference these macros; exercise DAPM route changes, audio interface formats (`right-justified`, `left-justified`, `I2S`, `DSP`), word lengths, clock divider setup, FLL setup, bias transitions, anti-pop sequencing, and codec reset. Register traces should show only the intended bitfields changing, and audio loopback/playback/capture should survive cache reset and suspend/resume.

## sources/distributed-fs/ceph-client/include/linux/mfd/wm8400-private.h

Purpose: this private header defines the WM8400 core state structure, register count, register addresses, and non-audio/PMIC-side field map used by the MFD core, regulator driver, and codec support. It is private to in-kernel WM8400 drivers rather than a board-facing API.

Important APIs, types, and constants: `WM8400_REGISTER_COUNT` defines the regmap maximum register span. `struct wm8400` contains the parent `device`, shared `regmap`, and an array of six regulator `platform_device` objects. Register-address macros cover identity, audio, GPIO, LDO/DCDC regulator, interface, power-management, interrupt, shutdown, and line-comparator registers. Field macros cover chip revision, GPIO/GPI debounce/IRQ/pull/function/status fields, regulator enable/voltage/ramp/current-limit fields, interface and PM bits, interrupt status/mask/levels, shutdown reasons, and line-comparator thresholds.

Control flow: the MFD core uses `WM8400_RESET_ID`, `WM8400_ID`, `WM8400_CHIP_REV_MASK`, `WM8400_REGISTER_COUNT`, and volatile interrupt/shutdown register constants during probe and regmap setup. The regulator driver uses `struct wm8400.regulators[]`, regulator IDs from `wm8400.h`, LDO/DCDC register constants, and voltage/ramp masks to create software-controlled regulator platform devices and operate them through regmap. The codec driver combines register addresses from this header with audio field macros from `wm8400-audio.h`.

State and persistence: persistent driver state is the devres-managed `struct wm8400` allocated by the I2C MFD probe. The `regmap` caches 8-bit register, 16-bit value hardware state; interrupt status, interrupt levels, and shutdown reason are volatile. The regulator platform-device array persists inside `struct wm8400` so `wm8400_register_regulator()` can register each regulator at most once and keep platform-device storage alive for the platform bus.

Dependencies and integration points: includes `wm8400.h`, mutex/platform-device/regmap headers, and connects the MFD core, regulator driver, ASoC codec driver, I2C probe path, MFD child registration, and Linux regulator framework. It is also tied to `wm8400-core.c` cache configuration and the public `wm8400_register_regulator()` API.

Risks: this header is the single source of truth for many numeric hardware fields; off-by-one register count or address errors can make regmap reject valid registers or permit invalid ones. Private state includes platform-device objects directly, so duplicate regulator registration is guarded by checking `.name` but still relies on caller discipline. Volatile-register classification is implemented in the core, not encoded here, so adding new status registers requires core updates. The header mixes audio, regulator, GPIO, interrupt, and shutdown definitions, increasing the chance that unrelated changes have cross-driver effects.

Test signals: build `CONFIG_MFD_WM8400`, `CONFIG_REGULATOR_WM8400`, and the WM8400 codec. Probe should reject non-`0x6172` reset IDs, log revision from `WM8400_ID`, register the codec child, and allow board `platform_init()` to register regulator children. Regulator tests should verify LDO/DCDC voltage selection, enable/disable, suspend-mode programming, duplicate registration rejection, and correct regmap accesses to `LDO*_CONTROL` and `DCDC*_CONTROL_*`. Cache tests should confirm volatile interrupt/shutdown registers are not treated as stable cached state.

## sources/distributed-fs/ceph-client/include/linux/mfd/wm8400.h

Purpose: this is the small public WM8400 MFD client interface for board/platform code. It exposes regulator IDs, optional platform initialization data, and the helper used by board code to request software control of an on-chip regulator.

Important APIs, types, and constants: `WM8400_LDO1` through `WM8400_DCDC2` number the six WM8400 regulators. `struct wm8400_platform_data` contains a `platform_init(struct device *dev)` callback invoked by the MFD core after codec child registration and chip identification. `wm8400_register_regulator(struct device *dev, int reg, struct regulator_init_data *initdata)` registers one regulator platform child with board-supplied constraints and consumer data.

Control flow: the MFD I2C probe validates the device and then calls `pdata->platform_init(wm8400->dev)` if provided. Board platform initialization can call `wm8400_register_regulator()` for selected regulator IDs. The regulator helper resolves the parent `struct wm8400`, rejects an already named regulator device, fills the persistent `wm8400->regulators[reg]` platform-device slot with name `wm8400-regulator`, ID, parent, and init data, then registers it with the platform bus. The `wm8400-regulator` driver then binds and operates the selected LDO/DCDC through the shared regmap.

State and persistence: this header itself has no state. Platform data is usually static board data and must remain valid while probe runs. Each registered regulator persists as a platform device stored in `struct wm8400.regulators[]`; the regulator init data becomes platform data for that child. The MFD core only warns if no platform initialization is supplied, so systems without board data may still get the codec child but no explicit regulator setup.

Dependencies and integration points: includes `linux/regulator/machine.h`; depends on `struct device` declarations from included kernel headers; integrates with `drivers/mfd/wm8400-core.c`, `drivers/regulator/wm8400-regulator.c`, the platform bus, and regulator framework constraints/consumer supply model.

Risks: `wm8400_register_regulator()` relies on callers passing a valid regulator ID in the 0 to 5 range; the declaration does not express bounds. Duplicate registration returns `-EBUSY`. Missing `platform_init()` can leave board regulators unregistered and consumers unsatisfied. Board-supplied `regulator_init_data` must match the hardware rail and consumer graph; wrong constraints can over/under-voltage devices. Since this is a legacy platform-data style API, DT-only systems need alternate board integration.

Test signals: probe logs should show chip revision and either platform-init success or the no-platform-init warning. Board tests should call `wm8400_register_regulator()` for all required rails, observe `wm8400-regulator` platform children with IDs matching the macros, verify duplicate calls fail, and verify regulator constraints/consumer supplies are honored through enable/disable and voltage changes.

## sources/distributed-fs/ceph-client/include/linux/mfd/wm8994/core.h

Purpose: this header defines the central WM8994-family MFD object, chip type enum, shared child-driver constants, inline regmap I/O helpers, and IRQ helper API for WM8994, WM8958, and WM1811 devices.

Important APIs, types, and constants: `enum wm8994_type` identifies WM8994, WM8958, and WM1811. `WM8994_NUM_GPIO_REGS`, `WM8994_NUM_LDO_REGS`, and `WM8994_NUM_IRQ_REGS` size child resources. `WM8994_IRQ_*` constants enumerate core codec events and `WM8994_IRQ_GPIO(x)` maps 1-based GPIO numbers after `WM8994_IRQ_TEMP_WARN`. `struct wm8994` holds copied platform data, type/revision/customer ID, device/regmap pointers, LDO-drive policy, GPIO/IRQ bases, parent IRQ and regmap IRQ data, optional edge-IRQ domain, suspend flag, DBVDD regulator pointer, and bulk supply array. Inline helpers wrap `regmap_read`, `regmap_write`, `regmap_bulk_read`, raw bulk write, update-bits, threaded IRQ request/free, and declarations for `wm8994_irq_init()`/`wm8994_irq_exit()`.

Control flow: the I2C MFD core allocates and fills `struct wm8994`, creates a base regmap, copies/overlays platform data, registers LDO children, enables supplies, reads hardware ID/revision, reinitializes the regmap cache for the actual chip, applies patches, programs platform GPIO/pull defaults, initializes IRQs, registers codec/GPIO children, and uses the fields in this structure for suspend/resume. Child drivers receive the parent pointer via `dev_get_drvdata()` or platform data, then use the inline helpers for all register and IRQ operations.

State and persistence: `struct wm8994` is the persistent per-device software state. Hardware register state is represented through regmap and regcache, with `suspended` indicating cache-only/powered-down state. Platform data is copied into the structure so child drivers do not depend solely on external storage. IRQ state is kept in `irq_data` and optionally an `irq_domain` for GPIO-backed edge-trigger emulation. Bulk supplies are allocated after chip type selection and must remain until device teardown.

Dependencies and integration points: includes mutex, interrupt, regmap, and `wm8994/pdata.h`; forward-declares regulator and IRQ-domain types. Integrates with Linux MFD, I2C, regmap, regmap-irq, gpiolib, regulator, runtime PM, ASoC codec, and platform-data/OF translation. The IRQ helper translates logical WM8994 IRQ numbers to virtual IRQs using `regmap_irq_get_virq()`.

Risks: `wm8994_reg_read()` returns either a non-negative register value or a negative errno, so callers must check `< 0` before treating values as unsigned. `wm8994_bulk_write()` uses `regmap_raw_write()` with `count * sizeof(u16)`, making endianness and register format dependent on regmap configuration. `wm8994_request_irq()` hard-codes `IRQF_TRIGGER_RISING` for requested child IRQs and returns `-EINVAL` if IRQ init did not populate `irq_data`. The `WM8994_IRQ_GPIO(x)` macro assumes callers pass chip GPIO numbers 1 through 11; using zero maps onto `TEMP_WARN`. Shared state fields require careful suspend/resume and child teardown ordering.

Test signals: successful MFD probe should populate type/revision/customer ID and register child devices. Unit or runtime checks should cover reg_read error handling, update-bits masking, bulk read/write length correctness, IRQ request/free after `wm8994_irq_init()`, GPIO IRQ mapping for 1 through 11, runtime suspend/resume cache transitions, supply enable/disable balance, and child drivers refusing IRQ setup when no parent IRQ is available.

## sources/distributed-fs/ceph-client/include/linux/mfd/wm8994/gpio.h

Purpose: this header defines the WM8994-family GPIO configuration vocabulary. It gives the GPIO driver and board/DT defaults symbolic function selectors and bitfields for each of the eleven GPIO control registers.

Important APIs, types, and constants: `WM8994_GPIO_MAX` is 11. `WM8994_GP_FN_*` values select pin-specific behavior, plain GPIO, IRQ, temperature, microphone-bias detect/short signals, FLL/SRC lock signals, DRC activity, write-sequencer status, FIFO error, OPCLK, thermal warning, DCS done, and FLL outputs. `WM8994_GPN_DIR`, pull-up/down, polarity, open-drain/push-pull, debounce, level, and function masks define the common layout for `WM8994_GPIO_1 + offset` registers.

Control flow: the header has no functions. `drivers/gpio/gpio-wm8994.c` uses the masks to implement gpiolib callbacks: request rejects unavailable pins on WM8958, direction-in sets `GPN_DIR`, get reads `GPN_LVL`, direction-out updates direction and level, set updates level, set_config toggles open-drain/push-pull through `GPN_OP_CFG`, and to_irq maps GPIO offsets through the parent regmap IRQ data. The MFD core applies `pdata->gpio_defaults[i]` values to `WM8994_GPIO_1 + i` during initialization when the values are non-zero; DT `wlf,gpio-cfg` zero entries are converted to `WM8994_CONFIGURE_GPIO`.

State and persistence: GPIO state is stored in hardware GPIO registers and cached by regmap. Platform defaults persist in `struct wm8994_pdata.gpio_defaults[]`; gpiolib line state is managed by the GPIO child driver. Alternate-function selections persist until overwritten by board defaults, gpiolib operations, reset, or suspend/resume cache synchronization.

Dependencies and integration points: consumed by the WM8994 GPIO platform driver, MFD core GPIO-default programming, debugfs GPIO reporting, ASoC/event routing for function signals, and regmap IRQ support. It relies on register-address definitions from `wm8994/registers.h` in consumers and on `struct wm8994` helpers from `core.h`.

Risks: the chip GPIOs are documented as 1-based for IRQ macro purposes, while gpiolib offsets are 0-based for register indexing; mixing those conventions can misroute IRQs. Some WM8958 GPIO offsets are invalid and must be rejected by the driver. A `gpio_defaults` value of zero normally means "do not configure" unless DT converted it to `WM8994_CONFIGURE_GPIO`, so board-data semantics differ from DT semantics. Incorrect alternate-function selection can steal pins from IRQ, clock, mic-detect, or audio status functions. Pull and output configuration mistakes can increase leakage or conflict electrically with board wiring.

Test signals: build `gpio-wm8994`; probe should expose 11 GPIOs where supported and resources for `WM8994_IRQ_GPIO(1..11)`. Test direction/get/set operations by observing `GPN_DIR` and `GPN_LVL`, pinconf open-drain/push-pull behavior, `to_irq()` virtual IRQ mapping, WM8958 invalid-pin rejection, DT `wlf,gpio-cfg` defaults, and debugfs function names for alternate functions.

## sources/distributed-fs/ceph-client/include/linux/mfd/wm8994/pdata.h

Purpose: this header defines board/platform configuration for WM8994-family MFD and codec drivers. It covers GPIO defaults, LDO regulator constraints, IRQ bases/flags, codec tuning tables, microphone/jack detection timing and thresholds, line-output topology, pull policies, microphone-bias setup, and audio-interface clocking limits.

Important APIs, types, and constants: sizing constants include `WM8994_NUM_LDO`, `WM8994_NUM_GPIO`, `WM8994_NUM_AIF`, DRC/EQ/MBC/VSS/enhanced-EQ register counts, and `WM8994_CONFIGURE_GPIO`. Data types include `wm8994_ldo_pdata`, `wm8994_drc_cfg`, `wm8994_retune_mobile_cfg`, `wm8958_mbc_cfg`, `wm8958_vss_hpf_cfg`, `wm8958_vss_cfg`, `wm8958_enh_eq_cfg`, `wm8958_micd_rate`, and the aggregate `wm8994_pdata`. The aggregate includes GPIO and IRQ bases, GPIO default register values, LDO init data, DSP tuning table arrays and counts, mic-detect rates, mic-bias delays, lineout differential/feedback flags, mic/jack detect delays and IRQ, mic-bias levels/configuration, jack thresholds, external-capacitor mode, LDO enable drive policy, pull policy for SPKMODE and CS/ADDR, max clocked channels per AIF, and optional IRQ GPIO.

Control flow: the MFD core copies platform data into `struct wm8994`, overlays selected OF properties, registers LDO children, uses `irq_base`/`gpio_base`, writes non-zero GPIO defaults, records `ldo_ena_always_driven`, applies pull policy, and passes the data to child drivers. The LDO regulator driver reads `pdata->ldo[id].init_data` unless defaults/OF are used. The codec driver builds ALSA enumerated controls from DRC/ReTune tables, writes selected tuning register arrays at runtime, applies lineout topology and mic-bias delays through WM hubs helpers, clamps AIF clocking to `max_channels_clocked[]`, and uses mic/jack detect timing, rates, thresholds, external-capacitor, and optional micdet IRQ settings in accessory detection.

State and persistence: platform data is copied into `struct wm8994.pdata`, so scalar values persist for device lifetime. Pointer members still refer to caller-owned tuning arrays, names, and rate tables; those must remain valid. Runtime selections such as active DRC or ReTune configuration are held in codec-private state, while the static arrays here define valid choices. Regulator init data is consumed by regulator registration and affects persistent regulator constraints.

Dependencies and integration points: depends on regulator machine constraints and fixed-width `u16` register arrays from kernel types. It integrates with MFD core, regulator framework, gpiolib, regmap IRQ, ASoC codec controls, WM hubs analogue handling, accessory detection, DT property parsing for selected fields, and board files using legacy platform data.

Risks: count/pointer mismatches for DRC/EQ/MBC/VSS/enhanced-EQ/micd arrays can cause invalid reads in the codec driver. Register arrays are written directly to hardware, so bad WISCE-generated or hand-authored values can break audio processing. Pointer lifetime is not owned by the core copy. `WM8994_CONFIGURE_GPIO` is a sentinel outside the 16-bit GPIO register field and must be interpreted correctly by consumers. Delay and threshold values are board-specific and can cause jack/mic detection flakiness or power regressions. LDO policy flags affect leakage and suspend behavior; setting `ldo_ena_always_driven` incorrectly can leave pins floating or waste power. Several fields are legacy platform-data only while OF parsing covers only a subset, so DT and non-DT systems can diverge.

Test signals: verify platform-data and DT probe paths produce expected `wm8994->pdata` values; LDO children use supplied or default constraints; GPIO defaults are written; IRQ base and optional edge `irq_gpio` paths deliver interrupts; codec enumerates DRC/ReTune controls with the configured names; selecting each tuning profile writes the expected number of registers; mic/jack detection honors delays/rates/external-cap mode; lineout single-ended/differential and feedback flags alter analogue routing; and `max_channels_clocked[]` clamps AIF channel clocks with a visible diagnostic.
