## sources/distributed-fs/ceph-client/drivers/gpu/drm/display/drm_dp_mst_topology.c

### Purpose
`drm_dp_mst_topology.c` is the DRM DisplayPort Multi-Stream Transport helper implementation. It manages MST branch and port discovery, sideband request/reply encoding, HPD IRQ sideband processing, I2C and DPCD proxying to remote MST devices, VCPI/time-slot payload allocation, DSC helper AUX selection, MST atomic private state, and topology lifetime. It is the central helper used by DP drivers that expose MST connectors while keeping the physical root connector and remote branch topology synchronized with kernel atomic modesetting state.

### Important APIs, Types, And Functions
The file exports the driver-facing MST manager and payload API: `drm_dp_mst_topology_mgr_init()`, `drm_dp_mst_topology_mgr_destroy()`, `drm_dp_mst_topology_mgr_set_mst()`, `drm_dp_mst_topology_queue_probe()`, `drm_dp_mst_topology_mgr_suspend()`, `drm_dp_mst_topology_mgr_resume()`, `drm_dp_mst_hpd_irq_handle_event()`, `drm_dp_mst_hpd_irq_send_new_request()`, `drm_dp_mst_detect_port()`, `drm_dp_mst_edid_read()`, `drm_dp_mst_get_edid()`, and connector AUX registration helpers. Payload and atomic helpers include `drm_dp_atomic_find_time_slots()`, `drm_dp_atomic_release_time_slots()`, `drm_dp_mst_atomic_setup_commit()`, `drm_dp_mst_atomic_wait_for_dependencies()`, `drm_dp_mst_root_conn_atomic_check()`, `drm_dp_mst_update_slots()`, `drm_dp_mst_atomic_check_mgr()`, `drm_dp_mst_atomic_check()`, `drm_atomic_get_mst_topology_state()`, `drm_atomic_get_old_mst_topology_state()`, and `drm_atomic_get_new_mst_topology_state()`.

Core internal structures come from the public MST helper header and are manipulated here: `struct drm_dp_mst_topology_mgr`, `struct drm_dp_mst_branch`, `struct drm_dp_mst_port`, `struct drm_dp_mst_topology_state`, `struct drm_dp_mst_atomic_payload`, sideband message TX/RX bodies, and pending UP requests. The implementation adds `struct drm_dp_pending_up_req` for queued upstream notifications.

The sideband layer is built from CRC helpers (`drm_dp_msg_header_crc4()`, `drm_dp_msg_data_crc4()`), header encode/decode (`drm_dp_encode_sideband_msg_hdr()`, `drm_dp_decode_sideband_msg_hdr()`), request encode/decode/dump functions exported for selftests, reply parsers, request parsers, and builders for link address, DPCD read/write, enum path resources, allocate payload, clear payload ID table, power up/down PHY, and query stream encryption status. The TX queue is driven by `drm_dp_queue_down_tx()`, `process_single_down_tx_qlock()`, `process_single_tx_qlock()`, `drm_dp_mst_wait_tx_reply()`, and `drm_dp_mst_kick_tx()`.

Topology mutation is handled by `drm_dp_mst_link_probe_work()`, `drm_dp_send_link_address()`, `drm_dp_mst_handle_link_address_port()`, `drm_dp_mst_handle_conn_stat()`, `drm_dp_port_set_pdt()`, branch/port lookup helpers, and delayed destruction workers. Remote access is exposed through fake AUX/I2C adapters using `drm_dp_mst_dpcd_read()`, `drm_dp_mst_dpcd_write()`, `drm_dp_mst_i2c_xfer()`, `drm_dp_mst_i2c_read()`, and `drm_dp_mst_i2c_write()`.

### Control Flow
Manager initialization sets up locks, TX and destroy lists, work items, wait queues, the ordered delayed-destroy workqueue, the root private atomic object, and immutable hardware limits. Enabling MST through `drm_dp_mst_topology_mgr_set_mst(true)` reads DPCD capabilities, creates the primary branch at LCT 1, enables MST and UP requests in `DP_MSTM_CTRL`, clears the root payload table, and queues link probing. Disabling MST clears the primary pointer, disables `DP_MSTM_CTRL`, marks RX state for reset, and drops the primary topology reference so destruction cascades asynchronously.

Topology probing runs under `probe_lock`. The first probe sends `CLEAR_PAYLOAD_ID_TABLE` to work around hubs that report zero available PBN after reset, then recursively sends `LINK_ADDRESS` to branches whose `link_address_sent` flag is false. Link-address replies update or create ports, register I2C-over-sideband buses for end devices, create child branches for MST branching ports, call the driver `add_connector` callback for output ports, register dynamic connectors, enumerate path resources to learn `full_pbn` and FEC capability, recurse into child branches, and prune stale ports not present in the latest reply.

HPD IRQ handling is split between immediate parsing and queued topology mutation. `drm_dp_mst_hpd_irq_handle_event()` consumes ESI bits, updates sink count, reads downstream replies when `DP_DOWN_REP_MSG_RDY` is set, and reads upstream requests when `DP_UP_REQ_MSG_RDY` is set. Down replies are matched against the first TX queue entry by destination branch and request type, parsed into the waiting TX message, removed from the queue, and signaled on `tx_waitq`. Upstream CSN/RSN messages are ACKed immediately, stored in `up_req_list`, and processed by `drm_dp_mst_up_req_work()` under `probe_lock`; CSN may update a port, trigger reprobing, and emit a hotplug event. RSN is parsed and logged but has a TODO for state handling.

Sideband down requests are chunked to the 48-byte sideband frame limit and further limited by `max_dpcd_transaction_bytes` and the 16-byte AUX transaction maximum. `drm_dp_mst_wait_tx_reply()` waits up to 4 seconds, optionally polling HPD IRQ every 50 ms when the driver provides `poll_hpd_irq`, removes timed-out messages from the queue, dumps debug state when enabled, and kicks the next queued TX. `drm_dp_mst_hpd_irq_send_new_request()` is called after the driver ACKs IRQ bits so the helper can send another down request without interleaving transactions.

Payload programming is a two-part commit protocol. `drm_dp_add_payload_part1()` assigns the next local VC start slot, updates manager slot counters, writes the payload entry to the root DFP DPCD, and marks the payload as locally/DFP allocated. The driver then performs ACT and hardware programming. `drm_dp_add_payload_part2()` sends the remote `ALLOCATE_PAYLOAD` sideband request and marks the payload remote. Removal runs in reverse: `drm_dp_remove_payload_part1()` sends remote and DFP removal when the port is still downstream of the primary branch, and `drm_dp_remove_payload_part2()` compacts subsequent VC start slots, updates manager counters, drops the payload's malloc reference when deleted, and clears allocation status.

Atomic check flow starts when drivers call `drm_dp_atomic_find_time_slots()` for active MST streams and `drm_dp_atomic_release_time_slots()` for disconnected or modeset streams. These helpers add or update `struct drm_dp_mst_atomic_payload` entries in the MST private object. `drm_dp_mst_atomic_check_mgr()` checks recursive branch PBN limits from root to leaves and validates total time slots, payload count, and VCPI assignment. Commit setup records dependent CRTC commits in the MST state, and `drm_dp_mst_atomic_wait_for_dependencies()` serializes nonblocking commits that share only the MST topology and copies final runtime allocation fields into the new state.

DSC helper flow uses topology and DPCD inspection to select the correct AUX for DSC capability and enable writes. `drm_dp_mst_dsc_aux_for_port()` checks FEC support on every non-virtual upstream link, recognizes virtual DPCD cases, handles DP-to-DP and DP-to-HDMI/logical ports, applies a Synaptics quirk path, and falls back to endpoint DSC/FEC capability checks.

### State, Persistence, And Dependencies
Persistent topology state is held in `mgr->mst_primary` and the branch/port graph protected by `mgr->lock`. Each branch and port has two lifetimes: a topology kref for membership in the live graph, and a malloc kref for memory that may need to outlive disconnect while drivers or payloads still hold references. Ports also hold connector pointers, fake remote AUX/I2C adapters, cached EDID for logical ports, DPCD revision, PDT/MCS/DDPS/LDPS status, SDP stream counts, path PBN limits, FEC capability, and optional passthrough AUX for DSC.

Persistent atomic state is stored in the manager's DRM private object. `struct drm_dp_mst_topology_state` carries payload list, `payload_mask`, total/start slots, PBN divider, pending CRTC mask, and commit dependencies. Payloads keep malloc references to their ports so stale but still-allocated streams can be torn down after topology removal. Runtime commit fields such as VC start slot and allocation status are copied forward only after previous dependent commits complete.

Sideband RX state persists across multi-part messages in `mgr->down_rep_recv` and `mgr->up_req_recv`, and `reset_rx_state` forces both to be cleared when MST is disabled. TX state persists in `mgr->tx_msg_downq`, with `qlock` protecting queue membership and state transitions. Workqueue state spans `work`, `tx_work`, `up_req_work`, `delayed_destroy_work`, and the dedicated ordered delayed-destroy workqueue.

The implementation depends on DRM atomic/private object helpers, DRM connector and EDID helpers, DP DPCD/AUX helpers, I2C core, workqueues, wait queues, krefs, optional stack depot ref-history debugging, DP MST constants, and driver callbacks in `struct drm_dp_mst_topology_cbs`. Hardware persistence is mostly in the sink/branch DPCD: `DP_MSTM_CTRL`, sideband message registers, payload table entries, GUID registers, DSC/FEC capability registers, and branch OUI/debug registers.

### Integration Points
Drivers integrate by initializing one topology manager per physical DP connector, implementing the MST callback table, calling MST capability detection and `set_mst()` on plug/unplug, routing HPD IRQ ESI handling through this file, calling atomic find/release/check helpers during modeset validation, and using add/remove payload part helpers during commit. Dynamic MST connectors are created through the driver's `add_connector` callback and later exposed with `drm_connector_dynamic_register()`.

Remote devices integrate through the fake AUX/I2C path. EDID reads, DDC transactions, DPCD reads, DSC capability reads, and remote AUX devnodes all route through sideband messages to the correct branch and port. Debugfs integration uses `drm_dp_mst_dump_topology()` to dump graph, atomic payload state, DPCD fields, branch OUI, and root payload table. HDCP integrates through `drm_dp_send_query_stream_enc_status()`, which sends a root-targeted query using the payload VCPI.

### Risks
The largest correctness risk is lifetime and locking. Topology refs, malloc refs, connector refs, delayed destruction, atomic payload references, and queued TX messages all interact with hot-unplug. Missing a reference can create use-after-free; holding the wrong lock across connector destruction can deadlock. The implementation explicitly avoids destroying connectors in kref release paths and uses delayed work, but callers must follow the documented rules.

Sideband parsing is length-sensitive and some parsers check only after reading adjacent bytes. Corrupt branch replies, unexpected request types, bad CRCs, mismatched request replies, and out-of-order fragments are mostly rejected or logged, but MST hardware frequently deviates from spec. Timeouts are treated as I/O failures and can remove queued messages; the payload path even notes a remaining race where the last connected branch can disappear between selection and sideband payload removal.

Atomic state must be used exactly as documented. Calling find and release for the same port in one check phase is rejected; failing to call MST atomic check can overcommit slots or PBN; failing to call commit setup/wait helpers can allow nonblocking commits to race on shared topology state. `payload_mask` and VCPI allocation assume `max_payloads` and bit operations stay within supported ranges.

Several hardware workarounds and spec ambiguities are embedded: clearing payload ID tables for hubs reporting zero PBN, polling HPD IRQ for devices that drop short pulses, assigning GUIDs when hubs report null GUIDs, interpreting query stream encryption status despite observed HDCP bit inconsistencies, and Synaptics DSC quirk handling. These paths need regression coverage when changing message sequencing or DPCD access.

### Test Signals
High-value signals include MST enable/disable on a root hub, link-address probing of nested branches, hotplug and unplug CSN handling, suspend/resume reprobing with GUID preservation or rewrite, stale port pruning after resume, payload add/remove with ACT status polling, remote payload removal after downstream disconnect, nonblocking atomic commit serialization, branch/port refcount debug output under `CONFIG_DRM_DEBUG_DP_MST_TOPOLOGY_REFS`, EDID reads through remote I2C, remote DPCD reads/writes, DSC AUX selection across endpoint, virtual DPCD, DP-to-DP, DP-to-HDMI, and quirked Synaptics paths, and timeout behavior with missing HPD IRQs. Useful failure signals are `-ENOSPC` from slot/PBN checks, `-EINVAL` for invalid stale topology operations, `-EIO` for sideband/AUX failures, NAK debug reasons, and hotplug events emitted after topology changes.

## sources/distributed-fs/ceph-client/drivers/gpu/drm/display/drm_dp_mst_topology_internal.h

### Purpose
`drm_dp_mst_topology_internal.h` is a narrow internal declaration header for DP MST helper selftests. It exposes only the sideband request encode/decode/dump helpers implemented in `drm_dp_mst_topology.c`, without publishing the full internal topology implementation as public driver API.

### Important APIs, Types, And Functions
The header forward-declares `struct drm_dp_sideband_msg_req_body`, `struct drm_dp_sideband_msg_tx`, and `struct drm_printer`. It declares `drm_dp_encode_sideband_req()`, which serializes a typed sideband request body into a raw TX message; `drm_dp_decode_sideband_req()`, which decodes a raw TX message back into a request body for debug/test use and may allocate nested byte buffers; and `drm_dp_dump_sideband_msg_req_body()`, which prints a decoded request body through a DRM printer with indentation.

### Control Flow
The header has no executable control flow. Its declarations let test code call the request codec helpers directly. The real control flow is in the implementation: encode switches on `req_type`, decode mirrors that switch and allocates copies for variable-length DPCD/I2C payloads, and dump formats the decoded union members by sideband request type.

### State, Persistence, And Dependencies
No state is stored in this header. It depends on the public or compilation-unit-visible definitions of the sideband request and TX structures from the MST helper stack, plus `struct drm_printer` from DRM print infrastructure. The include guard `_DRM_DP_MST_HELPER_INTERNAL_H_` prevents multiple inclusion.

### Integration Points
This is included by `drm_dp_mst_topology.c` and by DP MST selftest code that needs to validate sideband serialization without depending on static functions. The functions themselves are exported with `EXPORT_SYMBOL_FOR_TESTS_ONLY`, so the intended consumers are test modules rather than production display drivers.

### Risks
The main risk is accidental API creep. Adding declarations here makes internal helpers reachable by tests and potentially by other in-tree code, so it should remain limited to stable test seams. Decode callers must also know that variable-length fields in decoded DPCD/I2C requests can own allocated memory and must be freed according to request type, as done by the topology debug dump path.

### Test Signals
Build coverage should confirm this header remains sufficient for MST selftests without pulling in unrelated internals. Runtime selftest signals include encode/decode round trips for link address, path resource, payload allocation, remote DPCD, remote I2C, PHY power, and stream encryption requests; correct dump output for each request type; and no leaks from decoded variable-length request payloads.

## sources/distributed-fs/ceph-client/drivers/gpu/drm/display/drm_dp_tunnel.c

### Purpose
`drm_dp_tunnel.c` implements the DRM helper for DisplayPort tunnels, especially USB4/Thunderbolt DP tunneling bandwidth allocation. It discovers tunnel capability from DP tunneling DPCD registers, groups related tunnels by driver/group ID, tracks tunnel lifetime, enables or disables bandwidth allocation mode, requests tunnel bandwidth, updates software state from hardware notifications, and exposes atomic helpers for checking stream bandwidth against per-tunnel DPRX limits and shared tunnel-group bandwidth.

### Important APIs, Types, And Functions
The exported manager and object API is `drm_dp_tunnel_mgr_create()`, `drm_dp_tunnel_mgr_destroy()`, `drm_dp_tunnel_detect()`, `drm_dp_tunnel_destroy()`, `drm_dp_tunnel_get()`, `drm_dp_tunnel_put()`, `drm_dp_tunnel_name()`, and `drm_dp_tunnel_set_io_error()`. Runtime bandwidth/state API includes `drm_dp_tunnel_enable_bw_alloc()`, `drm_dp_tunnel_disable_bw_alloc()`, `drm_dp_tunnel_bw_alloc_is_enabled()`, `drm_dp_tunnel_alloc_bw()`, `drm_dp_tunnel_get_allocated_bw()`, `drm_dp_tunnel_update_state()`, `drm_dp_tunnel_handle_irq()`, `drm_dp_tunnel_max_dprx_rate()`, `drm_dp_tunnel_max_dprx_lane_count()`, and `drm_dp_tunnel_available_bw()`.

Atomic integration is provided by `drm_dp_tunnel_atomic_get_state()`, `drm_dp_tunnel_atomic_get_old_state()`, `drm_dp_tunnel_atomic_get_new_state()`, `drm_dp_tunnel_atomic_set_stream_bw()`, `drm_dp_tunnel_atomic_get_required_bw()`, `drm_dp_tunnel_atomic_get_group_streams_in_state()`, and `drm_dp_tunnel_atomic_check_stream_bws()`.

Internal types are `struct drm_dp_tunnel_mgr`, which owns the DRM device, group array, bandwidth request wait queue, and optional ref tracker; `struct drm_dp_tunnel_group`, which is a DRM private object containing related tunnels and total available bandwidth; `struct drm_dp_tunnel`, which stores AUX, name, kref, group pointer, granularity, estimated and allocated bandwidth, maximum DPRX link caps, adapter ID, and error/destroyed flags; `struct drm_dp_tunnel_group_state`, the atomic private state for a group; and `struct drm_dp_tunnel_state`, which records per-stream bandwidth requirements for one tunnel.

### Control Flow
Detection starts with `drm_dp_tunnel_detect()`, which reads only the relevant tunneling DPCD ranges using a bitmap of register addresses and contiguous AUX transfers. If `DP_TUNNELING_SUPPORT` is absent it returns `-ENODEV`. Otherwise it validates register consistency, creates a tunnel object, derives the driver/group ID and adapter ID, initializes bandwidth granularity, allocated bandwidth, bandwidth allocation support/enabled flags, name, kref, group membership, and optional debug reference tracking.

Tunnel grouping is allocated from a fixed-size manager array. `lookup_or_alloc_group()` reuses an active group with the same nonzero group ID or selects an inactive slot. Group ID zero is treated specially and should not have multiple tunnels. Empty groups are freed back to inactive state when their tunnel list becomes empty. Each group owns a DRM private object so atomic state can validate all streams sharing the same bandwidth pool together.

Enabling bandwidth allocation first checks the tunnel is not destroyed and has no I/O error, verifies support and nonzero group ID, writes `DP_DPTX_BW_ALLOCATION_MODE_CONTROL` to enable display-driver bandwidth allocation mode and unmask allocation IRQs, then rereads and validates tunneling registers while allowing the allocated bandwidth to have changed. It initializes DPRX caps and group available bandwidth on first enable. Disabling resets software `allocated_bw` to `-1` and clears the control bits.

Bandwidth requests go through `drm_dp_tunnel_alloc_bw()` and `allocate_tunnel_bw()`. The requested kB/s value is rounded up to the tunnel granularity and written to `DP_REQUEST_BW`. The helper clears prior request status, waits up to 3 seconds on the manager wait queue, and uses `drm_dp_tunnel_handle_irq()` or polling wakeups to observe `DP_BW_REQUEST_SUCCEEDED` or `DP_BW_REQUEST_FAILED`. If status-change bits arrive while waiting, it rereads and validates tunnel registers, updates group available bandwidth, and continues. Success stores the rounded allocation in software; I/O failures mark the tunnel as errored.

State updates are notification-driven but include a lost-notification guard. `drm_dp_tunnel_update_state()` checks and clears capability/estimated-bandwidth status bits; when bandwidth allocation is enabled it also rereads `DP_ESTIMATED_BW` to catch missed changes. It then rereads all info registers, validates immutable fields, updates maximum DPRX caps, recomputes group available bandwidth, and returns 1 only when meaningful state changed.

Atomic stream bandwidth flow stores required bandwidth per stream ID in `struct drm_dp_tunnel_state`. Setting a nonzero stream bandwidth creates or updates the tunnel state and resizes a compact bandwidth array keyed by the stream mask. Setting zero removes that stream and frees the whole tunnel state when no streams remain. Atomic check iterates every new tunnel group state, sums each tunnel's stream requirements, verifies each tunnel against `get_max_dprx_bw()`, rounds each tunnel requirement to granularity capped by max DPRX bandwidth, sums group bandwidth, and verifies the sum against `group->available_bw`. On failure it returns `-ENOSPC` and reports either the failing tunnel stream mask or the whole group stream mask.

### State, Persistence, And Dependencies
The manager persists for the lifetime chosen by the driver and owns all tunnel groups. Tunnel objects persist through krefs and optional `CONFIG_DRM_DISPLAY_DP_TUNNEL_STATE_DEBUG` reference tracking; `destroyed` prevents double destroy, and `has_io_error` prevents further management after AUX failures. Tunnel hardware-derived state includes bandwidth granularity, estimated bandwidth, allocated bandwidth, max DPRX link rate/lane count, support/enabled flags, and adapter/group identity.

Group state persists both outside and inside atomic commits. Outside atomic state, `group->available_bw` is the estimated group total including allocated bandwidth of all active tunnels plus free bandwidth reported by the connection manager. The value starts at `-1` until bandwidth allocation mode is enabled and state is updated. Inside atomic state, `struct drm_dp_tunnel_group_state` owns a list of tunnel stream states and is duplicated/destroyed through `tunnel_group_funcs`.

The implementation depends on DP tunneling DPCD definitions from `drm_dp.h`, AUX helpers from `drm_dp_helper.h`, public tunnel types from `drm_dp_tunnel.h`, DRM atomic private object helpers, Linux krefs, wait queues, export/ref tracker support, and DP link-rate conversion helpers. Hardware state is persisted in DP tunneling DPCD registers such as OUI/device ID, USB4 driver ID, group ID, bandwidth granularity, estimated/allocated bandwidth, max link caps, mode control, request bandwidth, and tunneling status.

### Integration Points
Display drivers use a tunnel manager to detect tunnels on DP AUX links, enable allocation mode when supported, allocate bandwidth before driving streams, release bandwidth by allocating zero, and destroy tunnel objects on disconnect. Drivers route DP tunnel IRQ handling through `drm_dp_tunnel_handle_irq()`, then call `drm_dp_tunnel_update_state()` when it reports capability or estimated-bandwidth changes. Link-training and mode validation can query `drm_dp_tunnel_max_dprx_rate()`, `drm_dp_tunnel_max_dprx_lane_count()`, and `drm_dp_tunnel_available_bw()`.

Atomic integration lets drivers associate stream IDs and required bandwidths with tunnels during atomic check, query all stream IDs in a group, and run `drm_dp_tunnel_atomic_check_stream_bws()` as a global bandwidth gate. The group private object ensures streams in the same USB4/Thunderbolt bandwidth pool are checked together even if they belong to separate DP tunnels.

### Risks
Register validation is strict by design. Changes in bandwidth allocation support, driver/group ID, granularity, or unexpected allocated bandwidth changes cause `-EINVAL`; this protects software state but may reject quirky hardware. The file explicitly skips checking reported bandwidth-allocation-enabled state during update because some devices always report zero, so software and hardware may diverge if writes are lost without an AUX error.

Bandwidth units are kB/s internally but debug output often converts to Mb/s, and DPCD request values are granularity units. Bugs in rounding or `MAX_DP_REQUEST_BW` boundaries would over-request or under-request tunnel bandwidth. Initial allocated bandwidth of zero is treated as undetermined (`-1`) until the first explicit request, which callers must handle.

Concurrency and lifetime risks center on krefs, group private states, and IRQ waiters. A tunnel marked with I/O error stops management but remains allocated until references drop. `drm_dp_tunnel_mgr_destroy()` warns if groups still contain tunnels, so drivers must destroy tunnels first. Atomic stream state uses compact arrays keyed by masks; stream ID bounds and mask resizing need care, especially because the warning check compares against the bit width of the mask type.

Group available bandwidth is inferred from one tunnel's estimated bandwidth plus software-known allocations from other enabled tunnels. `update_group_available_bw()` probes peer tunnels and marks them errored if the AUX probe fails, but disconnected or stale peers can still influence calculations until state is updated. Lost IRQs are partly handled by explicit `DP_ESTIMATED_BW` reads, but bandwidth request completion still depends on status bits becoming visible before the 3-second timeout.

### Test Signals
High-value signals include detection of links with no tunneling support, valid BWA-capable tunnels with nonzero group IDs, rejection of invalid group IDs or granularity, group slot exhaustion, enable/disable bandwidth allocation mode, initial `available_bw` transition from `-1`, allocation success and failure status handling, 3-second timeout behavior, I/O-error latching after AUX failures, lost estimated-bandwidth notification recovery, multi-tunnel group bandwidth recomputation, tunnel destroy and manager destroy ordering, atomic stream set/clear resizing, duplicate stream ID debug warnings, per-tunnel DPRX bandwidth failures, group bandwidth failures with correct failed stream masks, and correct handling of zero bandwidth release requests.
