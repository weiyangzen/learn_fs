## sources/distributed-fs/hadoop/hadoop-common-project/hadoop-common/src/main/java/org/apache/hadoop/fs/LeaseRecoverable.java

`LeaseRecoverable` is a small filesystem capability interface for filesystems that can recover writer leases and report whether a file is closed. Its public API is `recoverLease(Path)` and `isFileClosed(Path)`, both throwing `IOException` and optionally `UnsupportedOperationException` when unsupported. It has no internal state or persistence; implementations are expected to bind the methods to filesystem-specific metadata services, such as HDFS lease recovery. Dependencies are only `Path` and Java IO. Integration is capability-oriented: callers can probe or cast filesystem implementations before invoking recovery. Risks center on ambiguous return semantics, because `recoverLease()` returns true when no recovery is needed as well as when a closed state is reached. Tests should cover unsupported filesystems, closed files, active leases, retry/idempotency behavior, and propagation of server-side IO failures.

## sources/distributed-fs/hadoop/hadoop-common-project/hadoop-common/src/main/java/org/apache/hadoop/fs/LocalDirAllocator.java

`LocalDirAllocator` chooses configured local directories for temporary and local-work files. It maintains one static `AllocatorPerContext` per configuration key, with each context holding an atomic snapshot of parsed directories, `DF` capacity probes, a local filesystem, and an atomic last-directory index. Public APIs allocate write paths with known or unknown size, find existing read paths, iterate all matching read paths, create JVM-delete-on-exit temp files, test existence, and remove deprecated contexts. Control flow refreshes the context whenever the raw config string changes, creates or filters unusable directories through `DiskValidator`, then selects paths by weighted random choice for unknown sizes or round-robin/random-increment scanning for known sizes. State is JVM-local and configuration-driven; no persistent metadata is written besides created directories/temp files. Dependencies include `Configuration`, `FileSystem.getLocal`, `DF`, `DiskValidatorFactory`, `DiskChecker.DiskErrorException`, `StringUtils`, and hostname reporting for errors. Integration points include MapReduce/HDFS local scratch allocation and callers expecting local path search under multiple roots. Risks include races with disk capacity changing after allocation, static context sharing across users/tests, `ifExists()` using stale context without `confChanged()`, path normalization by stripping leading slash, and roulette selection corner cases when availability totals change after validation failures. Test signals should include config reloads, unwritable/missing dirs, no-space errors, known-size versus unknown-size selection, path iteration, temp-file cleanup flags, and concurrent access to the atomic context.

## sources/distributed-fs/hadoop/hadoop-common-project/hadoop-common/src/main/java/org/apache/hadoop/fs/LocalFileSystem.java

`LocalFileSystem` is the checksummed `file:///` filesystem wrapper built on `ChecksumFileSystem` with `RawLocalFileSystem` as the default raw implementation. It initializes the raw filesystem once, honors alternate schemes via `swapScheme`, and enables checksum verification from `LOCAL_FS_VERIFY_CHECKSUM`. Important APIs expose `getScheme()`, `getRaw()`, `pathToFile()`, local copy operations, checksum failure handling, and symlink delegation. The most involved control path is `reportChecksumFailure()`: it canonicalizes the bad data file, finds the highest writable parent on the same mount, creates `bad_files`, closes data/checksum streams, and renames both files with a random suffix. State is mostly delegated to the raw filesystem and checksum sidecar files; the random suffix is process-local. Dependencies include `ChecksumFileSystem`, `RawLocalFileSystem`, `DF`, `FileUtil`, and common configuration keys. Risks include best-effort rename failures being logged but ignored, mount-prefix assumptions when finding `bad_files`, and the static `Random` suffix not guaranteeing collision freedom. Tests should exercise checksum verification toggles, bad-file quarantine behavior, symlink delegation, raw path conversion, and copy semantics.

## sources/distributed-fs/hadoop/hadoop-common-project/hadoop-common/src/main/java/org/apache/hadoop/fs/LocalFileSystemPathHandle.java

`LocalFileSystemPathHandle` is the concrete `PathHandle` for local files. It stores a string path and an optional modification time, serializes them through `FSProtos.LocalFileSystemPathHandleProto`, and verifies a resolved `FileStatus` by checking presence and, when bound, modification time equality. State is immutable after construction, with `mtime` represented as nullable `Long` internally from an `Optional<Long>`. It integrates with `RawLocalFileSystem.open(PathHandle, ...)` and `createPathHandle()`, which chooses whether content changes are allowed. Dependencies include protobuf `ByteString`, `ByteBuffer`, `FileStatus`, and `InvalidPathHandleException`. Risks include path strings being location-based rather than inode-based, so moves are unsupported; modification time granularity can miss rapid content changes; `bytes()` sets `path` without null validation. Tests should cover serialization round trips, stale mtime rejection, unbound handles that allow content changes, null byte buffers, equality/hash behavior, and opening through the raw local filesystem.

## sources/distributed-fs/hadoop/hadoop-common-project/hadoop-common/src/main/java/org/apache/hadoop/fs/MultipartUploader.java

`MultipartUploader` is an unstable public async interface for multipart uploads across filesystems and nodes. It extends `Closeable` and `IOStatisticsSource`, with futures for `startUpload(Path)`, `putPart(...)`, `complete(...)`, `abort(...)`, and best-effort `abortUploadsUnderPath(Path)`. Implementations must close part input streams after reading and may upload parts out of order or in parallel. The interface has no state itself; persistent state lives in backend upload sessions and opaque `UploadHandle`, `PartHandle`, and final `PathHandle` values. Dependencies include `CompletableFuture`, `InputStream`, `Map`, and Hadoop path/handle/statistics types. Integration is with object stores and commit protocols that need durable multipart identifiers. Risks include unclear lifecycle ownership when futures fail, eventual-consistency gaps in abort-under-path, validation of part numbers and non-empty handle maps being left to implementations, and resource leaks if streams are not closed. Tests should cover parallel parts, out-of-order completion, abort idempotency, failed future cleanup, statistics exposure, and unsupported bulk abort returning `-1`.
<!-- END_FILE_RESEARCH: sources/distributed-fs/hadoop/hadoop-common-project/hadoop-common/src/main/java/org/apache/hadoop/fs/MultipartUploader.java -->

## sources/distributed-fs/hadoop/hadoop-common-project/hadoop-common/src/main/java/org/apache/hadoop/fs/Options.java

`Options` groups reusable option types for filesystem operations. `CreateOpts` provides typed varargs for block size, buffer size, replication, bytes per checksum, checksum options, progress callbacks, permissions, and parent creation, with validation and exact-class duplicate detection through `getOpt()`/`setOpt()`. `Rename` encodes NONE/OVERWRITE/TO_TRASH as byte values. `ChecksumOpt` merges default, user checksum type, and legacy bytes-per-checksum settings. `HandleOpt` models path-handle validity constraints (`changed`, `moved`) and provides resolver helpers. Later nested contracts define checksum combine modes and standard open/create option keys for builder APIs, including read policies and conditional overwrite semantics. State is per immutable option instance and static constant sets. Dependencies include `FsPermission`, `Progressable`, `DataChecksum`, Java streams/functions, and path-handle/file-status APIs. Integration spans `FileSystem`, `FileContext`, builders, object-store commit protocols, and handle creation. Risks include exact-class matching in `CreateOpts` versus assignable matching in `HandleOpt`, `Rename.valueOf(byte)` relying on enum order, and many string option contracts requiring consistent recognition by implementations. Tests should cover duplicate detection, checksum precedence, byte-code mapping, handle option presets, standard option set immutability, and unsupported must/optional create options in concrete filesystems.

`PathIOException` is the POSIX-like base `IOException` for path-related failures. Integration is broad across Hadoop FS exceptions and NativeIO tests. Risks include `getPath()` reparsing invalid original strings, mutable message state surprising log aggregation, null path formatting, and cause messages being appended manually in addition to exception chaining. Tests should cover formatting combinations, fully-qualified path inclusion, target path parsing, subclass defaults, and serialization compatibility.

`TrashPolicyDefault` implements Hadoop's standard trash layout. Initialization reads deletion interval, checkpoint interval, and whether to clean unexpected trash-root entries; negative deletion intervals are clamped to disabled. `moveToTrash()` normalizes relative paths, verifies existence, rejects items already under trash or containing the trash root, computes `trashRoot/Current/<original path>`, creates parent directories with owner-only permissions, handles parent collisions by suffixing a timestamp, and renames with `Rename.TO_TRASH`, retrying around checkpoint races. Checkpoint APIs rename `Current` to timestamped directories, suffixing after collisions, and delete expired checkpoints by parsing current and old timestamp formats. `Emptier` sleeps to interval boundaries, scans all trash roots, deletes old checkpoints, creates new ones, and closes the filesystem on exit. State includes intervals, clean flag, static date formats synchronized during parse/format, and filesystem trash roots/checkpoint directories. Dependencies include common trash config keys, `Options.Rename`, `FsPermission`, `Time`, `FileStatus`, and `FileSystem` trash-root APIs. Integration includes shell rm/trash commands, NameNode emptier services, encryption-zone-aware trash roots, and ViewFS via `Trash`. Risks include rename atomicity depending on filesystem, timestamp collisions beyond 1000 attempts, cleanup of unexpected entries being destructive when enabled, clock skew affecting expiration, race windows between mkdir/existence/rename, static `DateFormat` requiring synchronization, and path string prefix checks for already-in-trash. Tests should cover disabled/negative intervals, move collision handling, already-in-trash and contains-trash rejection, checkpoint creation/deletion including old formats, immediate expunge, emptier interval adjustment, unexpected-entry cleanup flag, and multiple trash roots.
