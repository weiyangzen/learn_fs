# sources/storage-engines/sqlite/src/resolve.c

## Purpose
`resolve.c` is SQLite's name-resolution pass for parser trees. It walks expressions and SELECT trees after expansion, converts symbolic identifiers into concrete column, trigger, register, aggregate, or window-function expression nodes, validates context-specific restrictions, and records metadata used by later planning and code generation. Its output is not persisted on disk, but it is persistence-critical for schema objects because CHECK constraints, generated columns, partial indexes, expression indexes, triggers, views, RETURNING clauses, and UPSERT expressions are accepted or rejected here before they are stored or compiled.

## Important APIs, Types, And Functions
The public entry points are `sqlite3ResolveExprNames()`, `sqlite3ResolveExprListNames()`, `sqlite3ResolveSelectNames()`, `sqlite3ResolveOrderGroupBy()`, `sqlite3ResolveSelfReference()`, `sqlite3CreateColumnExpr()`, `sqlite3MatchEName()`, and `sqlite3ExprColUsed()`. They operate on `Parse`, `NameContext`, `Walker`, `Expr`, `ExprList`, `Select`, `SrcList`/`SrcItem`, `Table`, `Schema`, `FuncDef`, `Window`, and `Upsert`.

The core resolver is `lookupName()`, which handles `Z`, `Y.Z`, and `X.Y.Z` references; source aliases; nested FROM subqueries; generated `ENAME_TAB`/`ENAME_ROWID` names; visible rowid aliases; trigger `new`/`old`; UPSERT `excluded`; RETURNING base-register references; FULL JOIN `USING` coalescing; authorization callbacks; and `SrcItem.colUsed`/`rowidUsed` tracking. `resolveExprStep()` is the expression-walker callback that dispatches identifier lookup, function resolution, aggregate/window classification, subquery correlation marking, vector-size checks, parameter bans, truth-value rewrites, and the WHERE-only NOT NULL strength reduction. `resolveSelectStep()` resolves whole SELECT statements, including subqueries in FROM, result expressions, HAVING, WHERE, table-valued-function arguments, ORDER BY, GROUP BY, compound SELECT term counts, ON-clause validity, and compound ORDER BY matching.

Important helpers include `resolveAlias()` and `incrAggFunctionDepth()` for copying result-set expressions into alias references while preserving aggregate depth; `resolveAsName()`, `resolveOrderByTermToExprList()`, `resolveCompoundOrderBy()`, and `resolveOrderGroupBy()` for ORDER/GROUP term mapping; `notValidImpl()`/`sqlite3ResolveNotValid()` for rejecting illegal constructs in partial indexes, index expressions, CHECK constraints, and generated columns; `exprProbability()` for `likelihood()`/`likely()`/`unlikely()` selectivity hints; `resolveSetExprSubtypeArg()` for subtype-sensitive functions; and `windowRemoveExprFromSelect()` for de-duplicating window objects when ORDER/GROUP terms become aliases.

## Control Flow
Expression resolution begins with `sqlite3ResolveExprNames()` or `sqlite3ResolveExprListNames()`. Both set up a `Walker` with `resolveExprStep()` and, unless disabled with `NC_NoSelect`, `resolveSelectStep()`. They temporarily clear aggregate/window flags in the active `NameContext`, walk the tree, then propagate `EP_Agg` and `EP_Win` to the resolved expressions.

For identifiers, `resolveExprStep()` normalizes `TK_ID` and dotted `TK_DOT` forms and calls `lookupName()`. `lookupName()` searches from the innermost `NameContext` outward, first scanning FROM sources and nested FROM result names, then trigger/UPSERT/RETURNING pseudo-sources, then rowid aliases, then SQLite's legacy result-set alias extension. A single match rewrites the expression to `TK_COLUMN`, `TK_TRIGGER`, `TK_REGISTER`, `TK_FUNCTION` for FULL JOIN coalesce, `TK_NULL` on error, or leaves a double-quoted token as `TK_STRING` when the compatibility mode permits. It increments `NameContext.nRef` on all contexts between the top and the match, which is later used to mark correlated subqueries.

For functions, `resolveExprStep()` looks up the `FuncDef`, validates arity, authorization, internal/direct/unsafe flags, deterministic restrictions, subtype requirements, and aggregate/window legality. Aggregate functions become `TK_AGG_FUNCTION`, accumulate an `op2` depth relative to the `NameContext` that owns their source references, and set `NC_HasAgg`, `NC_MinMaxAgg`, or `NC_OrderAgg` on the owning context. Window functions are updated through `sqlite3WindowUpdate()`, their partition/order/filter expressions are walked, and their `Window` objects are linked into the SELECT.

SELECT resolution in `resolveSelectStep()` marks a SELECT as resolved, resolves LIMIT/OFFSET without table names, recursively resolves FROM subqueries while tracking correlation, resolves the result list with aggregate/window permissions, decides whether the SELECT is aggregate, enables result aliases for HAVING/WHERE/ORDER/GROUP resolution, resolves table-valued-function arguments, handles converted compound ORDER BY relocation, checks GROUP BY aggregate misuse, enforces compound result-column counts, validates ON-clause placement, and finally resolves the right-most compound ORDER BY with `resolveCompoundOrderBy()`.

## State And Persistence Behavior
The resolver mutates AST nodes in place. It sets `Expr.op`, `Expr.iTable`, `Expr.iColumn`, `Expr.y.pTab`, `Expr.op2`, `Expr.affExpr`, expression flags such as `EP_Agg`, `EP_Win`, `EP_CanBeNull`, `EP_ConstFunc`, `EP_SubtArg`, `EP_Unlikely`, `EP_FromDDL`, and list metadata such as `ExprList_item.u.x.iOrderByCol`, `fg.bUsed`, and `fg.done`. It also updates `NameContext.ncFlags`, `nRef`, `nNcErr`, `nNestedSelect`, `SrcItem.colUsed`, `SrcItem.fg.rowidUsed`, trigger `oldmask`/`newmask`, `Select.selFlags`, `SrcItem.fg.isCorrelated`, `Parse.checkSchema`, `Parse.bHasExists`, and parser error offsets.

For schema-affecting expressions, `sqlite3ResolveSelfReference()` builds a fake one-table `SrcList` with cursor `-1`, sets `NC_IsDDL` plus the requested context flag, and resolves expressions before they become schema content. This is where subqueries, parameters, non-deterministic functions, and dotted column references are blocked for contexts that cannot safely persist them. Double-quoted-string compatibility is gated by connection DQS flags and schema-initialization state, with legacy schemas always accepted.

## Dependencies And Integration Points
The file depends on the parser and AST definitions in `sqliteInt.h`, expression allocation/comparison/deletion in `expr.c`, SELECT expansion/preparation and ON-clause checking in `select.c`, function lookup/flags in `func.c`, authorization in `auth.c`, window support in `window.c`, rename-token remapping in ALTER TABLE paths, schema/table metadata, trigger and UPSERT state, generated-column and partial-index flags, VDBE normalize support for double-quoted strings, and planner metadata such as `colUsed` for covering-index decisions.

Downstream consumers include SELECT code generation, WHERE planning, aggregate analysis, window rewriting, trigger code generation, RETURNING handling, UPSERT code, ALTER TABLE validation, schema loading, expression-index and partial-index creation, generated-column evaluation, and the authorizer. Error text produced here is part of SQLite's observable SQL behavior and is heavily exercised by TCL tests.

## Risks And Edge Cases
High-risk behavior concentrates around ambiguity rules and context flags. `lookupName()` must distinguish real columns from rowid aliases, nested FROM synthetic names, schema-table aliases, trigger pseudo-tables, UPSERT `excluded`, RETURNING registers, and result aliases while preserving SQLite's legacy compatibility behavior. FULL JOIN `USING` can turn ambiguous matches into `coalesce()` expressions, so ownership, nullability, and authorization must remain consistent. Aggregate and window depth (`op2`) is fragile across subqueries and alias substitution. Incorrect `nRef` updates can misclassify correlated subqueries. Incorrect `colUsed` bits can lead to invalid covering-index decisions, especially for generated columns and wide tables.

Context validation is also delicate: deterministic, direct-only, unsafe, internal, parameter, subquery, and dotted-reference restrictions differ across CHECK constraints, partial indexes, expression indexes, generated columns, DDL schema loading, VACUUM INTO, ALTER TABLE rename, and normal DML. The double-quoted string fallback intentionally accepts legacy SQL but can mask misspelled identifiers. Error-offset recording and `db->suppressErr` in compound ORDER BY matching can change external diagnostics.

## Test Signals
Relevant SQLite tests include `select1.test`, `select4.test`, `selectA.test`, and `tkt2822.test` for ORDER BY/GROUP BY alias and range behavior; `joinH.test` and `rowid.test` for ambiguous columns and rowid resolution; `index7.test`, `indexexpr*.test`, `vtabK.test`, and generated-column tests for context restrictions; `window*.test` and `aggnested.test` for aggregate/window misuse; `upsert*.test` for `excluded` resolution; `returning*.test`, `trigger*.test`, and `wherelimit.test` for trigger/RETURNING name contexts; `altertab*.test` and `alterdropcol*.test` for rename and schema revalidation; and `subquery.test` for correlation and aggregate misuse. Useful assertions are exact error strings such as "no such column", "ambiguous column name", "misuse of aggregate/window function", "ORDER BY term out of range", "row value misused", and "prohibited in generated columns/partial index WHERE clauses".

# sources/storage-engines/sqlite/src/rowset.c

## Purpose
`rowset.c` implements SQLite's internal `RowSet`, a memory-only collection of 64-bit rowids optimized for VDBE operations that need to accumulate rowids, test duplicate rowids by batch, or later read rowids in ascending order. It is used by bytecode such as `OP_RowSetAdd`, `OP_RowSetRead`, and `OP_RowSetTest`, especially for rowid-table DELETE/UPDATE staging and OR-clause rowid-union logic. The object is deliberately not a general set: after sorted extraction starts no more inserts are allowed, and membership testing and sorted extraction are mutually exclusive use modes.

## Important APIs, Types, And Functions
The public API declared in `sqliteInt.h` is `sqlite3RowSetInit(sqlite3*)`, `sqlite3RowSetClear(void*)`, `sqlite3RowSetDelete(void*)`, `sqlite3RowSetInsert(RowSet*, i64)`, `sqlite3RowSetNext(RowSet*, i64*)`, and `sqlite3RowSetTest(RowSet*, int iBatch, i64)`. `RowSet` stores chunk ownership, the database handle, an unsorted or sorted insertion list (`pEntry`/`pLast`), a fresh-entry pool (`pFresh`/`nFresh`), a forest of test trees (`pForest`), flags, and the current test batch. `RowSetEntry` is reused as list node, binary-tree node, and forest-list node. `RowSetChunk` batches entry allocation.

Private helpers are `rowSetEntryAlloc()` for amortized chunk allocation; `rowSetEntryMerge()` for merging two sorted lists while removing duplicates; `rowSetEntrySort()` for bottom-up merge sorting through bucketed runs; `rowSetTreeToList()` and `rowSetListToTree()` for converting between sorted lists and balanced-ish search trees; and `rowSetNDeepTree()` for building fixed-depth tree fragments from a sorted list.

## Control Flow
`sqlite3RowSetInit()` allocates the `RowSet` and uses any spare bytes in the allocation as the first fresh-entry pool. `sqlite3RowSetInsert()` appends a new entry to the `pRight` insertion list, clearing `ROWSET_SORTED` if the new rowid is not greater than the previous rowid. No duplicate elimination happens on insert.

`sqlite3RowSetNext()` implements sorted extraction. On its first call it sorts `pEntry` if needed, sets `ROWSET_NEXT`, and then returns the head rowid on each call. Because `rowSetEntrySort()` merges equal values by retaining only one copy, duplicates are removed before extraction. When the list becomes empty, it calls `sqlite3RowSetClear()` immediately so large RowSets release chunks before statement finalization.

`sqlite3RowSetTest()` implements duplicate testing with batch visibility. When `iBatch` differs from the stored batch, current list entries are sorted if needed and folded into `pForest`. Each forest node stores a binary search tree in `pLeft` and the next forest node in `pRight`; if an existing forest slot is occupied, its tree is flattened, merged with the new sorted list, and carried forward until an empty slot is found, much like binary addition. After this conversion, the new insertion list is cleared and the current batch is updated. The test then searches every tree in the forest and returns true if `iRowid` was inserted in a prior batch. Inserts made after a test with the same batch number are intentionally invisible until the batch changes.

## State And Persistence Behavior
RowSet state is transient per database connection and per VDBE `Mem` value. Memory allocations use `sqlite3DbMallocRawNN()` and therefore report OOM through `db->mallocFailed`; no partial error code is returned by insert/test helpers. Chunks are retained for the object's lifetime unless `sqlite3RowSetClear()` is called, and `sqlite3RowSetDelete()` clears chunks before freeing the RowSet itself. `sqlite3RowSetClear()` resets logical state to an empty, sorted RowSet but does not rebuild the original inline fresh pool, so later inserts allocate a normal chunk if the object is reused after clearing.

The key state invariants are `ROWSET_SORTED` reflects only the current `pEntry` list, `ROWSET_NEXT` forbids further inserts and membership tests, `pForest==0` is required for sorted extraction, and `sqlite3RowSetTest()` cannot be mixed with `sqlite3RowSetNext()`. Duplicates are tolerated on input and eliminated by merge operations. The batch number controls visibility, not ownership: all entries remain memory-resident until clear/delete.

## Dependencies And Integration Points
`rowset.c` depends only on `sqliteInt.h` facilities: SQLite integer types, assertions, `ROUND8`, memory allocation/free wrappers, and connection OOM state. The object is exposed through `Mem` values in `vdbemem.c`, where `sqlite3VdbeMemSetRowSet()` stores a `RowSet*` with `xDel=sqlite3RowSetDelete`. VDBE opcodes in `vdbe.c` call the API for `OP_RowSetAdd`, `OP_RowSetRead`, and `OP_RowSetTest`. Code generators in `delete.c`, `update.c`, and `wherecode.c` emit those opcodes for rowid staging and OR-optimization duplicate suppression; `whereexpr.c` documents the OR-clause rowid union use case.

## Risks And Edge Cases
The most important risk is violating the intended mode split: `sqlite3RowSetNext()` after tests or inserts after `Next()` are guarded mainly by assertions, so opcode generation must preserve the protocol in release builds. Batch semantics are subtle: same-batch tests ignore same-batch inserts, which is required by `OP_RowSetTest` control flow but easy to misuse outside the VDBE pattern. Recursive list/tree conversion could become deep for very large sets, although the tree-building strategy aims to keep search trees balanced. Allocation failure leaves inserts silently skipped except for `db->mallocFailed`; callers must notice connection OOM state. Since `RowSetEntry.pRight` has different meanings in insertion lists, sorted lists, tree right links, and forest links, maintenance mistakes can corrupt the structure.

Duplicate removal happens only during sort/merge, so memory use can grow with duplicate inserts until a test or read phase. `sqlite3RowSetClear()` deliberately releases chunks but sets `nFresh` to zero, which changes subsequent allocation behavior if a cleared RowSet is reused. The merge-sort bucket array has a fixed size of 40 buckets, relying on practical allocation limits to keep the number of entries within range.

## Test Signals
Direct unit tests for `rowset.c` are scarce; behavior is exercised through VDBE and SQL features that emit RowSet opcodes. Good signals are DELETE/UPDATE statements on rowid tables that collect rowids before mutation, OR-clause queries using rowid-union plans, and EXPLAIN output containing `RowSetAdd`, `RowSetRead`, or `RowSetTest`. Relevant source integration points are `delete.c`, `update.c`, `wherecode.c`, `vdbe.c`, and `vdbemem.c`. Regression tests should include duplicate rowids, unsorted inserts, sorted inserts that preserve `ROWSET_SORTED`, empty reads, very large rowsets, OOM/fault injection, and RowSetTest batches where rowids inserted after a same-batch test remain invisible until the batch changes.
