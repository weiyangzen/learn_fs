## sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci-tegra.c

Purpose: this is the NVIDIA Tegra SDHCI platform driver. It adapts the generic SDHCI core to Tegra SDMMC controller generations from Tegra20 through Tegra234, covering SoC-specific capability quirks, tap/trim programming, pad voltage control, pad drive-strength autocalibration, CQHCI/eMMC command queue support, timeout-clock handling, IOMMU stream ID programming, runtime PM, and system suspend/resume.

Important APIs, types, and functions: `struct sdhci_tegra_soc_data` selects the `sdhci_pltfm_data`, DMA mask, NV quirk bitmap, and tap-delay calibration bounds for each compatible. `struct sdhci_tegra` is the live private state: power GPIO, optional `tmclk`, pinctrl states, reset control, autocal offsets, default tap/trim/DQS trim, CQE enablement, current clock rate, tuned tap delay, and stream ID. Register hooks include `tegra_sdhci_readw()`, `tegra_sdhci_writew()`, `tegra210_sdhci_writew()`, and `tegra_sdhci_writel()`. Timing and signal paths center on `tegra_sdhci_set_clock()`, `tegra_sdhci_set_uhs_signaling()`, `tegra_sdhci_execute_tuning()`, `tegra_sdhci_execute_hw_tuning()`, `tegra_sdhci_post_tuning()`, `tegra_sdhci_tap_correction()`, `tegra_sdhci_hs400_enhanced_strobe()`, `tegra_sdhci_hs400_dll_cal()`, and `tegra_sdhci_set_timeout()`. Platform lifecycle is `sdhci_tegra_probe()`, `sdhci_tegra_add_host()`, `sdhci_tegra_remove()`, runtime PM callbacks, and system sleep callbacks.

Control flow: probe selects match data, initializes the SDHCI platform host, sets static capabilities such as alternate Android GPT and busy-response support, optionally installs Tegra pad-control voltage switching and periodic autocalibration hooks, installs HS400 enhanced-strobe handling, parses MMC DT properties and Tegra-specific `supports-cqe`, default tap/trim, DQS trim, and pad autocal offset properties, obtains optional power GPIO and timeout clock, gets the core clock and reset control, initializes OPP support, runtime-resumes the device, pulses the SDHCI reset line, then registers either plain SDHCI or SDHCI plus CQHCI. After successful registration, Tegra234-style stream IDs are written into `SDHCI_TEGRA_CIF2AXI_CTRL_0`.

State and persistence: software state is mostly cached hardware configuration used to recover after full resets or clock changes: default tap/trim, tuned tap, DQS trim, DDR signaling flag, pad calibration requirement, last calibration timestamp, pinctrl availability, CQE flag, and current clock rate. Full SDHCI reset reapplies vendor capability overrides, default tap/trim, SDR/DDR mode advertisements, VREF, and pad-calibration-needed state. Runtime suspend disables the core clock; runtime resume reenables it. System suspend suspends CQHCI when active, suspends SDHCI, force-suspends runtime PM, and arms GPIO card-detect wake; resume reverses wake, runtime PM, stream ID programming, SDHCI resume, and CQHCI resume.

Dependencies and integration points: the file integrates with the MMC and SDHCI platform cores, `sdhci-cqhci`/`cqhci`, common clock and OPP frameworks, GPIO descriptors, pinctrl, regulators, reset controls, runtime PM, DMA masks, Tegra IOMMU stream ID helpers, and OF compatibles `nvidia,tegra20-sdhci` through `nvidia,tegra234-sdhci`. `mmc_of_parse()` supplies card-detect, bus-width, regulator, and timing policy. CQHCI is exposed only when `supports-cqe` is present and host setup succeeds.

Risks: the driver is quirk dense, so wrong compatible data can advertise unsupported UHS modes, DMA widths, timeout behavior, or CQE behavior. Pad voltage switching depends on both regulator capabilities and complete pinctrl states; missing states disable safe dual-voltage operation. Pad autocalibration runs periodically and around timing changes, and timeout fallback writes fixed drive strengths or selects drive-strength pinctrl states, so board DT values are timing-critical. Tuning correction uses tap-delay bounds, tuning status windows, and current clock rate arithmetic; bad bounds or clock rates can select marginal taps. CQHCI paths work around Tegra block-size write restrictions and DCMD R1B timing, making CQE resume/unhalt ordering fragile. The write hook suppresses timeout/CRC signal bits and relies on software timers for real errors.

Test signals: useful validation is successful probe per compatible, correct advertised capabilities and DMA mask, no `tmclk` or reset-control probe failures, voltage switching with the expected pinctrl state, recurring pad autocalibration without "Pad autocal timed out", SDR104/HS200 tuning and post-tuning tap selection, HS400 DQS trim and DLL calibration, enhanced strobe toggling, long busy operations using erase-timeout-limit behavior, CQHCI enable/disable/resume and DCMD status traffic, stream ID programming on Tegra234, card-detect wake from suspend, and stable runtime autosuspend/resume.

## sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci-uhs2.c

Purpose: this file is a reusable UHS-II extension layer for SDHCI hosts. It is not a standalone platform driver; instead, `sdhci_uhs2_add_host()` wraps generic SDHCI registration, detects SDHCI v4 UHS-II capability, installs UHS-II MMC host operations when enabled, and supplies UHS-II-specific reset, power, timeout, PHY initialization, command packet, transfer, completion, and interrupt handling.

Important APIs, types, and functions: exported entry points are `sdhci_uhs2_dump_regs()`, `sdhci_uhs2_reset()`, `sdhci_uhs2_set_power()`, `sdhci_uhs2_set_timeout()`, `sdhci_uhs2_clear_set_irqs()`, `sdhci_uhs2_irq()`, `sdhci_uhs2_add_host()`, and `sdhci_uhs2_remove_host()`. `sdhci_uhs2_host_ops_init()` replaces `mmc_host_ops.uhs2_control` and `.request`. Low-level helpers handle UHS-II timers, power sequencing, interface detect, capability parsing, settings programming, dormant checks, clock enable/disable, command packet construction, response extraction, DMA/data setup, request completion, and threaded IRQ continuation.

Control flow: registration calls `sdhci_setup_host()`, interprets `SDHCI_SUPPORT_UHS2` and `SDHCI_CAN_VDD2_180`, optionally sets `MMC_CAP2_SD_UHS2`, and only keeps UHS-II support if SDHCI v4 mode is active. During card initialization the MMC core calls `uhs2_control`; `UHS2_PHY_INIT` performs optional host pre-detect work, polls `SDHCI_PRESENT_STATE` for interface detect and lane sync, reads UHS-II caps through `SDHCI_UHS2_CAPS_PTR`, resets the SD UHS-II block, reenables SDHCI interrupts, and enables UHS-II error interrupts. `UHS2_SET_CONFIG` writes selected lane, LSS, FCU, retry, and data-gap settings through `SDHCI_UHS2_SETTINGS_PTR`.

State and persistence: the layer reuses `struct sdhci_host` state (`host->cmd`, `host->data`, `host->ier`, `host->mrqs_done`, timers, deferred command, DMA flags) and fills `mmc->uhs2_caps` from hardware. UHS-II power state is cached in `host->pwr`. A full UHS-II reset clears `host->clock`; SD-only resets clear UHS-II block state, so the code restores SDHCI interrupt enables and UHS-II error enables afterward. Request completion records errors in `cmd->error` or `data->error`, unmaps DMA when needed, and resets UHS-II command/data state machines after command or data failures.

Dependencies and integration points: the file depends on generic `sdhci.h`, the register definitions in `sdhci-uhs2.h`, MMC UHS-II command structures (`cmd->uhs2_cmd`), regulator helpers for `vmmc` and `vqmmc2`, SDHCI v4 capability bits, generic SDHCI request/data/DMA/completion helpers, and MMC core UHS-II operations such as `enum sd_uhs2_operation`. Platform drivers must call `sdhci_uhs2_add_host()` and usually route their IRQ hook through `sdhci_uhs2_irq()`.

Risks: UHS-II behavior is active only when `mmc_card_uhs2()` is true, so mixed UHS-I/UHS-II paths must stay consistent. Timer programming depends on `host->timeout_clk`; bad or zero clock data can produce wrong command-response and deadlock timeouts. Power sequencing currently assumes 1.8 V VDD2 support and delays with fixed 5 ms waits. Command packet writes rely on `cmd->uhs2_cmd` payload layout already being in transmission byte order. Error IRQ classification maps many packet errors to `-EILSEQ`, with special cases for timeout, deadlock, and ADMA errors. The request path strips stop/SBC fields because UHS-II handles transfer semantics differently; generic MMC callers must have prepared compatible requests.

Test signals: test SDHCI v4 registration with and without `SDHCI_SUPPORT_UHS2`, regulator-backed and fixed VDD2 power on/off, interface-detect and lane-sync timeout handling, capability parsing into `mmc->uhs2_caps`, settings writes for speed A/B and half/full duplex, native abort and dormant commands, single and multi-block data paths with DMA, command/data error IRQ injection, deferred-command retry after inhibit release, card insert/remove threaded IRQ handling, and full remove/reset on live UHS-II cards.

## sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci-uhs2.h

Purpose: this header defines the SDHCI Category B/C UHS-II register map, bit fields, error masks, capability/settings offsets, and exported helper prototypes consumed by `sdhci-uhs2.c` and platform SDHCI drivers that opt into UHS-II support.

Important APIs, types, and functions: the register constants cover UHS-II block size/count, command packet area, transfer mode, command register, response buffer, message selection, device interrupt status/select/code, UHS-II software reset, timer control, UHS-II interrupt status/enable/signal registers, settings pointer, capabilities pointer, embedded-control pointer, and vendor pointer. Composite masks such as `SDHCI_UHS2_INT_ERROR_MASK`, `SDHCI_UHS2_INT_CMD_ERR_MASK`, and `SDHCI_UHS2_INT_DATA_ERR_MASK` define how the implementation separates command and data errors. Public prototypes expose register dumping, reset, power, timeout, host add/remove, IRQ-mask update, and IRQ filtering.

Control flow: the header itself has no runtime control flow, but it encodes the contract used by the C file. `SDHCI_UHS2_CMD_PACKET` and `SDHCI_UHS2_CMD_PACK_MAX_LEN` describe how command packets are staged before writing `SDHCI_UHS2_CMD`. Transfer mode bits drive DMA, block-count mode, byte mode, write direction, busy wait, and half-duplex operation. Software reset bits distinguish full UHS-II reset from SD block reset. Capability and settings offsets are relative to hardware-provided pointers, so drivers read `SDHCI_UHS2_CAPS_PTR` and `SDHCI_UHS2_SETTINGS_PTR` before accessing the corresponding tables.

State and persistence: the constants describe persistent hardware register state, not software-owned storage. Settings fields program negotiated lane counts, speed range, synchronization/direct LSS values, retry counts, FCU count, and data gap. Capability fields expose DAP, GAP, lane modes, 64-bit addressing, boot support, device type/count, topology, PHY revision/range, link revision, host type, block length, and transport data-gap support.

Dependencies and integration points: the header includes `<linux/bits.h>` for `BIT()` and `GENMASK()`, forward-declares `struct sdhci_host`, `struct mmc_command`, and `struct mmc_request`, and relies on surrounding SDHCI/MMC headers for common register and type definitions. It is included by `sdhci-uhs2.c`; platform drivers include it when they need exported UHS-II helpers or register definitions.

Risks: the file is a register ABI, so incorrect offsets or masks would silently corrupt UHS-II command, response, interrupt, or capability handling. Several settings are pointer-relative, which means callers must validate hardware pointers before using them. Error masks intentionally omit `SDHCI_UHS2_INT_VENDOR_ERR` from the aggregate error mask, so vendor-specific errors require platform-specific handling if needed. The `SDHCI_UHS2_MAKE_BLKSZ()` helper exists but the current implementation writes block size/count directly, so future users should confirm DMA boundary semantics.

Test signals: validate compile coverage for all exported prototypes, register dump output matching hardware manuals, capability/settings pointer bounds, interrupt mask behavior for command versus data errors, full and SD resets, and command packet length programming up to the 20-byte maximum.

## sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci-xenon-phy.c

Purpose: this file contains the Marvell Xenon SDHC PHY support used by `sdhci-xenon.c`. It abstracts eMMC PHY 5.0 and 5.1 register layouts, parses board-specific PHY parameters, controls Armada 3700 SoC pad voltage when present, initializes the PHY after clock/timing changes, enables the DLL for high-speed modes, configures HS200/SDR104 tuning step, and sets HS400 data/enhanced strobe behavior.

Important APIs, types, and functions: `struct xenon_emmc_phy_regs` maps version-specific timing, function-control, pad-control, DLL, and logic-timing registers. `struct xenon_emmc_phy_params` stores parsed slow-mode, ZNR/ZPR impedance, tuning-success count, tuning-step divider, and optional SoC pad control. Public entry points are `xenon_phy_adj()`, `xenon_phy_parse_params()`, and `xenon_soc_pad_ctrl()`. Core helpers include `xenon_alloc_emmc_phy()`, `xenon_emmc_phy_parse_params()`, `get_dt_pad_ctrl_data()`, `xenon_emmc_phy_init()`, `xenon_emmc_phy_enable_dll()`, `xenon_emmc_phy_config_tuning()`, `xenon_emmc_phy_strobe_delay_adj()`, `xenon_emmc_phy_slow_mode()`, `xenon_emmc_phy_set()`, and `xenon_hs_delay_adj()`.

Control flow: `xenon_phy_parse_params()` selects a DT-provided `marvell,xenon-phy-type` or defaults to eMMC 5.1, allocates PHY parameter storage, selects the matching register table, reads `marvell,xenon-phy-slow-mode`, `marvell,xenon-phy-znr`, `marvell,xenon-phy-zpr`, `marvell,xenon-phy-nr-success-tun`, and `marvell,xenon-phy-tun-step-divider`, and optionally maps the second DT resource for Armada 3700 pad control. Later, `xenon_set_ios()` in the platform driver calls `xenon_phy_adj()` after generic SDHCI IOS changes. If clock, bus width, or timing changed, `xenon_phy_adj()` calls `xenon_emmc_phy_set()`, updates cached state, and for non-legacy high-speed clocks calls `xenon_hs_delay_adj()`.

State and persistence: PHY state is cached in `struct xenon_priv` (`phy_type`, `phy_params`, `emmc_phy_regs`, previous bus width/timing/clock, and initialization card type). Hardware state includes pad receiver enables, pull-up/down selections, slow mode, SDIO mode, ZNR/ZPR values, function-control DDR/async bits, card clock enable, logic timing, DLL enable/phase/update bits, strobe bits, and SoC pad voltage. `xenon_runtime_suspend()` clears cached clock in the platform driver so resume forces PHY reconfiguration rather than assuming stale state.

Dependencies and integration points: the file depends on `sdhci-pltfm.h`, `sdhci-xenon.h`, OF address mapping, devm allocation/ioremap, SDHCI clock-control state, MMC timings and card type, and Xenon vendor registers. `xenon_soc_pad_ctrl()` is called before generic voltage switching. PHY tuning setup feeds the generic SDHCI tuning engine by programming Xenon tuning-step and consecutive-success fields.

Risks: timing correctness is board-sensitive. Default ZNR/ZPR and 90-degree DLL phase may not suit every layout, and the DDR path explicitly warns that it does not scan fixed delay lines. `tun_step_divider` is parsed as an 8-bit value but not guarded against zero before division in tuning setup. The PHY init wait is derived from register fields and clock rate, then capped at 100 loops; very slow or unusual hardware may still time out. Function-control writes require the SD card clock disabled and then reenabled, so ordering with generic clock changes matters. Armada 3700 pad control assumes a valid second resource and known `marvell,pad-type`.

Test signals: validate PHY 5.0 and 5.1 register selection, DT parsing including default values, SoC pad switching for SD and fixed-1.8V modes, internal clock stability polling, PHY initialization completion across clock rates, slow-mode behavior for legacy/SDIO/low-speed modes, ZNR/ZPR programming, DLL lock within 32 ms for HS200/SDR104/HS400, tuning step calculation and clamping, HS400 data/enhanced strobe bits and QSP pull-down, and forced PHY reprogramming after runtime resume.

## sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci-xenon.c

Purpose: this is the platform SDHCI driver for Marvell Xenon SDHC controllers used on Armada AP806/AP807/CP110/3700 and AC5 variants. It wraps generic SDHCI with Xenon slot enablement, clock gating policy, tuning policy, voltage-switch pad control, SDIO interrupt indication, eMMC/SD/SDIO PHY integration, variant-specific quirks, runtime PM, and OF/ACPI matching.

Important APIs, types, and functions: `sdhci_xenon_ops` supplies custom `.voltage_switch`, `.set_power`, `.reset`, `.set_uhs_signaling`, and `.get_max_clock` while using generic SDHCI clock and bus-width helpers. MMC host ops are replaced by `xenon_set_ios()`, `xenon_start_signal_voltage_switch()`, `xenon_init_card()`, `xenon_execute_tuning()`, and `xenon_enable_sdio_irq()`. Platform setup flows through `xenon_probe()`, `xenon_probe_params()`, `xenon_sdhc_prepare()`, `xenon_remove()`, `xenon_runtime_suspend()`, and `xenon_runtime_resume()`. Helper functions program `XENON_SYS_OP_CTRL`, `XENON_SYS_EXT_OP_CTRL`, retuning registers, slot enable bits, SDCLK-off-while-idle, ACG, and command-conflict masking.

Control flow: probe initializes an SDHCI platform host with Xenon quirks, records hardware variant from OF/ACPI match data, replaces MMC ops, enables core and optional AXI clocks on DT systems, parses MMC properties, applies SDHCI properties, disables ACG early, parses Xenon-specific properties and PHY parameters, prepares the SDHC slot, enables runtime PM autosuspend, and registers the host. Parameter parsing validates `marvell,xenon-sdhc-id` against hardware slot count, parses `marvell,xenon-tun-count`, disables HS200 on AP806, and on AC5 with more than 2 GB RAM disables ADMA/64-bit DMA so generic SDHCI bounce buffering is used; after registration it may restore a 34-bit DMA mask for AC5 DDR addressing.

State and persistence: `struct xenon_priv` from the shared header stores slot ID, tuning count, initial card type, cached IOS state for PHY decisions, AXI clock, PHY type/params/register table, restore-needed flag, and hardware variant. Full SDHCI reset clears vendor state, so `xenon_reset_exit()` reapplies retune setup, disables ACG initially, disables SDCLK-off-while-idle, and masks command-conflict errors. Runtime suspend suspends the SDHCI host, requests retuning unless tuning mode 3 is active, disables the core clock, and clears cached PHY clock. System suspend force-suspends runtime PM and marks restore needed; runtime resume reenables the clock and re-prepares the slot if needed before resuming SDHCI.

Dependencies and integration points: the driver depends on generic SDHCI platform helpers, `sdhci-xenon.h`, the companion PHY file through `xenon_phy_parse_params()`, `xenon_phy_adj()`, and `xenon_soc_pad_ctrl()`, common clock APIs, runtime PM, DMA mask APIs, sysinfo memory sizing, OF properties, and optional ACPI IDs `MRVL0002` through `MRVL0004`. It uses MMC DT parsing for regulators and card properties, then custom voltage switching to keep the internal clock enabled while SoC pad control and generic voltage switching occur.

Risks: the driver deliberately forces tuning mode 1 and disables retuning interrupts, so tuning regressions may show up only under high-speed transfer testing. Preset values are disabled for HS, HS200, and HS400 to avoid invalid preset reads, and this dynamic quirk manipulation must remain aligned with generic SDHCI behavior. SDCLK-off-while-idle is enabled after clocks rise above 400 kHz; early enablement could interfere with initialization. AC5 DMA behavior depends on total memory size and crossbar limits, with a non-obvious post-registration DMA mask adjustment. Fixed-vqmmc platforms skip generic signal-voltage switching, relying on SoC pad control.

Test signals: validate probe over OF and ACPI variants, core/AXI clock enable and autosuspend, slot ID validation, SDHC enable/disable and parallel transfer bits, command-conflict masking after reset and resume, AP806 HS200 suppression, AC5 bounce-buffer/DMA mask behavior above 2 GB RAM, voltage switching with fixed and regulator-backed vqmmc, PHY adjustment on IOS changes, tuning mode 1 execution, SDIO async IRQ indication bits, runtime/system suspend-resume with retune needed, and host removal cleanup.

## sources/distributed-fs/ceph-client/drivers/mmc/host/sdhci-xenon.h

Purpose: this shared header defines Marvell Xenon SDHC vendor register offsets, bit fields, variant IDs, private driver state, and the PHY helper interface used between `sdhci-xenon.c` and `sdhci-xenon-phy.c`.

Important APIs, types, and functions: register definitions cover system configuration, system operation control, extended operation control, tuning status/control, eMMC strobe control, retuning request control, extended present state, and current DLL delay. Constants define default and lowest SDCLK frequencies, retuning counts, and Xenon-specific Host Control 2 values for HS200 and HS400. `enum xenon_variant` names `XENON_A3700`, `XENON_AP806`, `XENON_AP807`, `XENON_CP110`, and `XENON_AC5`. `struct xenon_priv` is the shared per-host state. Function prototypes export `xenon_phy_adj()`, `xenon_phy_parse_params()`, and `xenon_soc_pad_ctrl()` from the PHY companion.

Control flow: the header itself does not execute logic, but it defines the data contract for the Xenon driver pair. The platform file allocates `struct xenon_priv` as SDHCI platform private data, fills variant, slot ID, tuning count, clocks, and restore state, then delegates PHY parsing and adjustment to the PHY file. The PHY file reads and updates `phy_type`, `phy_params`, `emmc_phy_regs`, cached IOS fields, and initial card type from this structure.

State and persistence: persistent state in `struct xenon_priv` includes retuning period, SDHC slot index, initialization-time card type, cached bus width/timing/clock for avoiding redundant PHY programming, AXI clock handle, selected PHY type, board-specific PHY parameters, register table pointer, restore-needed flag for system sleep, and hardware variant. Comments explicitly limit `init_card_type` to initialization/PHY-timing use rather than normal transfer-time card access.

Dependencies and integration points: the header assumes SDHCI/MMC types are visible to C files including it and shares constants with both the platform and PHY implementations. It is the boundary that prevents the PHY file from needing to know platform probe details while still letting it use Xenon-private state.

Risks: because register offsets and bit fields are centralized here, incorrect definitions affect reset recovery, slot enablement, SDIO IRQ indication, retuning, HS400 strobe, and DLL lock detection. `struct xenon_priv` contains a `void *phy_params`, so type safety is enforced only by the platform/PHY pairing. Cached IOS state must be cleared on runtime suspend; otherwise the PHY layer can skip needed reconfiguration after clocks are stopped.

Test signals: compile both Xenon C files together, validate all supported compatibles map to the expected `enum xenon_variant`, verify private state initialization before PHY calls, confirm reset/resume reuses the register constants correctly, and exercise IOS changes that update cached bus width/timing/clock.
