## sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/lunarlake/frontend.json

**Purpose:** Lunar Lake frontend PMU event metadata for Linux `perf`. The file supplies 68 static event aliases that describe branch-address clears, decode and microcode-sequencer stalls, frontend-retired attribution, instruction-cache and instruction-delivery queue behavior, and Atom-side microcode decode events. It is part of the Lunar Lake x86 model directory selected by `arch/x86/mapfile.csv` entry `GenuineIntel-6-BD,v1.21,lunarlake,core`.

**Important APIs, types, and records:** This is data consumed by `tools/perf/pmu-events/jevents.py`, not executable code. Each object is parsed into `JsonEvent`; key fields are `EventName`, `EventCode`, `UMask`, `Counter`, `Unit`, `SampleAfterValue`, optional `PublicDescription`, and optional event modifiers such as `MSRIndex`, `MSRValue`, `CounterMask`, `EdgeDetect`, `Invert`, and `Deprecated`. `Unit` is especially important on Lunar Lake because `jevents.py` maps `cpu_core` and `cpu_atom` to distinct Linux hybrid PMUs. The file has 43 `cpu_core` records and 25 `cpu_atom` records. Duplicate user-facing names intentionally exist where Core and Atom encodings differ: `BACLEARS.ANY` is `cpu_atom` event `0xe6/0x1` but `cpu_core` event `0x60/0x1`, and `FRONTEND_RETIRED.ITLB_MISS` is present on both units with different semantics and selectors.

**Event families:** The Atom side defines `BACLEARS.*`, `DECODE_RESTRICTION.PREDECODE_WRONG`, `FRONTEND_RETIRED.*` slots such as `BRANCH_DETECT`, `BRANCH_RESTEER`, `CISC`, `DECODE`, `ICACHE`, `ITLB_MISS`, `OTHER`, `PREDECODE`, `FRONTEND_RETIRED_SOURCE.*`, `ICACHE.*`, and `MS_DECODED.*`. The Core side defines unknown-branch `BACLEARS.ANY`, `DECODE.LCP`, `DECODE.MS_BUSY`, `DSB2MITE_SWITCHES.PENALTY_CYCLES`, `FRONTEND_RETIRED.*` PEBS-distribution style events configured through `MSRIndex` `0x3F7`, `ICACHE_DATA.*`, `ICACHE_TAG.*`, `IDQ.*`, and `IDQ_BUBBLES.*`. Core `FRONTEND_RETIRED.LATENCY_GE_*` entries use `MSRValue` thresholds such as `0x600206`, `0x601006`, `0x608006`, `0x610006`, and `0x620006`.

**Control flow and integration:** During the perf build, `jevents.py` walks JSON files in the Lunar Lake directory, loads this file with `json.load(..., object_hook=JsonEvent)`, canonicalizes event encodings, and emits compact C PMU tables in generated `pmu-events.c`. `JsonEvent.lookup_msr()` converts `MSRIndex` `0x3F7` into a `frontend=` event field, and `unit_to_pmu()` preserves hybrid routing as `cpu_core` or `cpu_atom`. At runtime, `perf list` and `perf stat -e cpu_core/<event>/` or `cpu_atom/<event>/` resolve these aliases from the generated table. `lnl-metrics.json` depends heavily on this file: Core formulas reference `DECODE.LCP`, `IDQ.*`, `IDQ_BUBBLES.*`, `FRONTEND_RETIRED.*`, `ICACHE_TAG.STALLS`, and Atom formulas reference `BACLEARS.ANY`, `TOPDOWN_FE_BOUND.*`, and Atom frontend-retired slots from the broader Lunar Lake event set.

**State and persistence behavior:** The file is static source metadata. It does not persist runtime state; runtime counts, sampling periods, frontend MSR programming, and counter allocation exist only in a perf session. Build outputs persist only as generated event tables. `SampleAfterValue` values influence default sampling periods and therefore runtime overhead and sample density.

**Dependencies:** Depends on Linux perf's PMU JSON schema, `jevents.py` parsing, `metric.py` expression validation for cross-file metric references, x86 hybrid PMU device names, and Lunar Lake hardware encodings. Several Core events depend on frontend MSR `0x3F7` selector support; `CounterMask`/`EdgeDetect`/`Invert` entries depend on perf preserving cmask, edge, and inv bits. Integration also depends on sibling Lunar Lake files such as `pipeline.json`, `cache.json`, `virtual-memory.json`, and `lnl-metrics.json`.

**Risks and edge cases:** Hybrid duplicate names are expected but fragile: removing or incorrectly changing `Unit` can make `jevents.py` assert on duplicates or route an event to the wrong PMU. `EventCode` and `UMask` changes can silently corrupt topdown-derived diagnostics. `MSRIndex`/`MSRValue` mistakes on Core `FRONTEND_RETIRED.*` entries will program the wrong frontend distribution selector. Some entries have derived-cycle behavior through `CounterMask`, `EdgeDetect`, and `Invert`; those fields are easy to lose in mechanical JSON edits and directly affect metrics such as IDQ bubbles and stall periods. Descriptions include domain-specific terms such as DSB, MITE, BACLEAR, BTCLEAR, and LCP; documentation updates should preserve their meaning because `perf list` exposes them to users.

**Test signals:** Validate with `jq empty` on this file and a full `tools/perf` PMU events generation build. High-value parser tests include `tools/perf/pmu-events/metric_test.py` and any build target that regenerates `pmu-events.c`, because `JsonEvent` asserts duplicate event names within a PMU table. Runtime smoke signals on Lunar Lake are `perf list frontend`, `perf list cpu_core`, `perf list cpu_atom`, and targeted collection of representative aliases such as `cpu_core/DECODE.LCP/`, `cpu_core/IDQ.MITE_UOPS/`, `cpu_core/FRONTEND_RETIRED.LATENCY_GE_16/`, `cpu_atom/BACLEARS.ANY/`, and `cpu_atom/FRONTEND_RETIRED.ICACHE/`.

## sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/lunarlake/lnl-metrics.json

**Purpose:** Lunar Lake metric metadata for `perf stat -M` and metric groups. The file contains 331 `pmu_metric` records covering package/core C-state residency, SMI accounting, Level 1 through deeper topdown microarchitecture analysis, frontend/backend/bad-speculation/retiring breakdowns, branch and machine-clear diagnostics, memory hierarchy and TLB bottlenecks, port utilization, arithmetic and vector mixes, FLOPs, system frequency/utilization, uncore frequency, and derived bottleneck estimates.

**Important APIs, types, and records:** Each JSON object is parsed by `jevents.py` as a `JsonEvent` with `MetricName`, `MetricExpr`, optional `MetricGroup`, `MetricThreshold`, `ScaleUnit`, `Unit`, `MetricgroupNoGroup`, `DefaultMetricgroupName`, `MetricConstraint`, `BriefDescription`, and `PublicDescription`. `MetricExpr` is parsed and simplified by `metric.ParsePerfJson()`, and `read_json_events()` may rewrite formulas in terms of other metrics through `metric.RewriteMetricsInTermsOfOthers()`. The file has 236 `cpu_core` metrics, 87 `cpu_atom` metrics, and 8 unitless/system metrics. Reused metric names across units are intentional: examples include `tma_backend_bound`, `tma_bad_speculation`, `tma_branch_mispredicts`, `tma_cisc`, `tma_core_bound`, `tma_frontend_bound`, `tma_icache_misses`, `tma_itlb_misses`, `tma_machine_clears`, and `tma_retiring`.

**Metric families:** Unitless records include C-state residency metrics such as `C10_Pkg_Residency`, `C1_Core_Residency`, `C6_Core_Residency`, SMI metrics `smi_cycles` and `smi_num`, and package/core power style percentages. Atom metrics use `cpu_atom@...@` references and an 8-slot denominator pattern such as `8 * cpu_atom@CPU_CLK_UNHALTED.CORE@` for topdown fractions. Atom records cover Topdown L1/L2/L3, instruction mix, branch mix, buffer stalls, memory execution bound, load/store bound, machine clears, FP/uop mix, and system utilization. Core metrics use hybrid Core topdown counters like `cpu_core@topdown\\-fe\\-bound@`, `cpu_core@topdown\\-be\\-bound@`, `cpu_core@topdown\\-retiring@`, and many named PMU events from sibling JSON files. Core records are much broader, including L4-L6 TMA breakdowns, bottleneck estimates prefixed `tma_bottleneck_*`, memory latency/bandwidth decomposition, port utilization, vector/shuffle/divider metrics, false sharing, streaming stores, STLB page-size splits, and uncore/system rates such as `UNCORE_FREQ`.

**Control flow and integration:** During generation, `jevents.py` reads this file after event-topic JSON files, parses every expression, and emits `struct pmu_metric` rows grouped by PMU. `MetricGroup` strings determine `perf list metricgroups` and `perf stat -M <group>` visibility; `DefaultMetricgroupName` and `MetricgroupNoGroup` control default grouping behavior; `MetricConstraint` strings such as `NO_GROUP_EVENTS`, `NO_GROUP_EVENTS_NMI`, and `NO_THRESHOLD_AND_NMI` are converted into internal event-grouping enums. At runtime, perf expands a selected metric into referenced PMU events, MSR pseudo-events (`msr@tsc@`, `msr@smi@`, `msr@aperf@`), cstate pseudo-events, duration variables, constants such as `#num_dies`, and recursively referenced metric names.

**State and persistence behavior:** Metrics are static formula metadata persisted in generated `pmu-events.c`; they hold no runtime state. Runtime metric values are derived from current counter reads, wall-clock `duration_time`, MSR/cstate snapshots, multiplexing, and PMU scheduling. Thresholds are static advisory expressions and are not parsed by `jevents.py` because threshold precedence differs from the metric-expression grammar.

**Dependencies:** Strongly depends on the complete Lunar Lake event directory, not just this subset. Atom formulas reference events such as `TOPDOWN_BE_BOUND.*`, `TOPDOWN_FE_BOUND.*`, `TOPDOWN_BAD_SPECULATION.*`, `TOPDOWN_RETIRING.ALL`, `FP_*`, `BR_*`, `LD_HEAD.*`, `MEM_BOUND_STALLS_*`, `MEM_SCHEDULER_BLOCK.*`, `MACHINE_CLEARS.*`, `UOPS_RETIRED.*`, and `CPU_CLK_UNHALTED.*`. Core formulas reference `frontend.json` entries (`DECODE.LCP`, `IDQ.*`, `IDQ_BUBBLES.*`, `FRONTEND_RETIRED.*`, `ICACHE_TAG.STALLS`), `memory.json` entries (`MACHINE_CLEARS.MEMORY_ORDERING`, `MEM_TRANS_RETIRED.*`, `OCR.*`, `OFFCORE_REQUESTS*`), and many cache, pipeline, branch, floating-point, virtual-memory, uncore, and MSR events. `metricgroups.json` supplies descriptions for group names used here.

**Risks and edge cases:** This file is name-fragile. Any event rename, missing `Unit`, missing sibling JSON record, or typo in `MetricExpr` can break parse-time generation or produce runtime "event not found" failures. Hybrid duplicate metric names require correct `Unit`; otherwise Core and Atom formulas can collapse together or be routed to the wrong PMU. Several formulas divide by event counts or derived sums that may be zero on short runs, idle systems, disabled PMUs, or unsupported counters. Some expressions intentionally use escaped event syntax, qualifiers, and raw modifiers, for example `topdown\\-be\\-bound`, `@R`, `@k`, escaped commas and equal signs, and conditional `if ... else`; mechanical escaping changes are high risk. `MetricConstraint` records are performance and correctness hints for grouping/NMI behavior, so dropping them can change schedulability or accuracy. User-visible typos in metric names, such as `adressaliasing`, may be compatibility-sensitive because users can script against metric names.

**Test signals:** First gate is JSON validity plus `jevents.py` generation because all 331 expressions are parsed. Run perf's PMU metric tests, especially `tools/perf/pmu-events/metric_test.py`, and a full `tools/perf` build that regenerates `pmu-events.c`. Integration smoke tests on Lunar Lake should include `perf list metrics`, `perf list metricgroups`, `perf stat -M TopdownL1`, representative Core metrics such as `tma_frontend_bound`, `tma_memory_bound`, `tma_fetch_latency`, and Atom metrics such as `cpu_atom` topdown and load-store-bound metrics. Runtime tests should watch for unresolved event names, excessive multiplexing via `tma_info_system_mux`, threshold behavior, and divide-by-zero or not-counted outputs on idle or short workloads.

## sources/distributed-fs/ceph-client/tools/perf/pmu-events/arch/x86/lunarlake/memory.json

**Purpose:** Lunar Lake memory PMU event metadata for `perf`. The file supplies 42 aliases for Atom load-head stalls, memory-ordering machine clears, Core sampled load/store latency, misaligned page-split references, offcore response demand code/data/RFO accesses, and Core offcore request/outstanding L3-miss demand-data events.

**Important APIs, types, and records:** This is parsed by `jevents.py` into event rows. Required fields are `EventName`, `EventCode`, `UMask`, `Counter`, `Unit`, `SampleAfterValue`, and descriptions; optional fields include `MSRIndex`, `MSRValue`, `Data_LA`, and `CounterMask`. The file has 24 `cpu_atom` records and 18 `cpu_core` records. Cross-unit duplicate names are intentional for `MACHINE_CLEARS.MEMORY_ORDERING`, `OCR.DEMAND_DATA_RD.DRAM`, `OCR.DEMAND_DATA_RD.L3_MISS`, and `OCR.DEMAND_RFO.L3_MISS`, with different Core and Atom event codes or offcore selector values.

**Event families:** Atom `LD_HEAD.*` records share event code `0x05` and classify oldest-load stalls as L1 miss, WCB full, page walk, store-address block, store-data block, other pipeline blocks, and retirement-visible variants using masks such as `0x81`, `0xa0`, `0x84`, `0xc0`, and `0xff`. Memory ordering records include Atom and Core `MACHINE_CLEARS.MEMORY_ORDERING` plus Atom `MACHINE_CLEARS.MEMORY_ORDERING_FAST`. Core `MEM_TRANS_RETIRED.LOAD_LATENCY_GT_*` records use event `0xcd`, `MSRIndex` `0x3F6`, and `MSRValue` thresholds from `0x4` through `0x800`; all have `Data_LA` set for address-capable precise sampling. `MEM_TRANS_RETIRED.STORE_SAMPLE` also has `Data_LA`. Atom OCR records use event `0xB7` with `MSRIndex` `0x1a6,0x1a7`; Core OCR records use event `0x2A,0x2B`. Core offcore request records include `OFFCORE_REQUESTS.L3_MISS_DEMAND_DATA_RD` and `OFFCORE_REQUESTS_OUTSTANDING.*`.

**Control flow and integration:** `jevents.py` converts `MSRIndex` `0x3F6` to `ldlat=` for sampled load-latency thresholds and `0x1A6/0x1A7` to `offcore_rsp=` for OCR selectors. It uses only the first event code from comma-separated `EventCode` strings when canonicalizing the generated event field, while preserving PMU/unit routing. `Data_LA` causes an additional description note that the event supports address collection when precise. Runtime users reach these aliases through `perf list memory` and `perf record/stat -e cpu_core/<event>/` or `cpu_atom/<event>/`. `lnl-metrics.json` uses these records for Atom load/store-bound formulas, Core memory-bound breakdowns, memory latency/bandwidth estimates, machine-clear attribution, and L3-miss/offcore diagnostics.

**State and persistence behavior:** The file persists only hardware alias metadata and default sampling periods. Runtime state is transient counter state, PEBS/sample data, load-latency threshold programming, and offcore response MSR programming. OCR and load-latency events are especially stateful at runtime because they require selector MSRs, but those selectors are derived from static `MSRValue` fields each time perf schedules the event.

**Dependencies:** Depends on Lunar Lake hardware memory-event encodings, hybrid PMU names, `jevents.py` MSR mappings, and sibling metric/event files. `LD_HEAD.*` events are consumed by Atom memory execution metrics. Core sampled latency records depend on PEBS/data-address support and perf's `ldlat=` handling. OCR aliases depend on offcore response MSRs `0x1a6/0x1a7` and on perf preserving selector values for Core and Atom separately.

**Risks and edge cases:** Offcore and load-latency selectors are high risk: a wrong `MSRValue` can silently measure a different response class or latency threshold. Comma-separated `EventCode` and `MSRIndex` values require parser compatibility; `jevents.py` explicitly takes the first event code and maps the first MSR index, so future schema changes need care. `Data_LA` records are sampling-oriented and may not behave like ordinary counting events. Hybrid duplicate OCR names must keep `Unit` correct to avoid duplicate-table assertions or wrong-PMU collection. `SampleAfterValue` values vary widely, from very low store/load-latency sampling periods to million-cycle stall counters; changing them affects overhead and sample representativeness.

**Test signals:** Validate JSON syntax, then run PMU event generation and metric parser tests. Runtime smoke tests on Lunar Lake should include `perf list memory`, `perf stat -e cpu_atom/LD_HEAD.L1_MISS_AT_RET/`, `perf stat -e cpu_core/MACHINE_CLEARS.MEMORY_ORDERING/`, and offcore aliases such as `cpu_core/OCR.DEMAND_DATA_RD.L3_MISS/` where supported. Sampling tests should exercise `cpu_core/MEM_TRANS_RETIRED.LOAD_LATENCY_GT_128/` with precise address capture and confirm that `ldlat=` programming and `Data_LA` behavior are accepted by the kernel.
