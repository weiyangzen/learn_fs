# sources/distributed-fs/hadoop/hadoop-common-project/hadoop-common/src/main/java/org/apache/hadoop/fs/FileSystem.java

Purpose: `FileSystem` is Hadoop's stable public abstract base class for URI-addressed filesystems. It defines the legacy `FileSystem` API used by HDFS, local filesystems, object stores, checksumming wrappers, filters, and third-party implementations. The class owns filesystem instance discovery/caching, default URI handling, path validation/qualification, common operation overloads, capability probing, global statistics registration, builder APIs, and default unsupported implementations for optional features.

Important APIs and types: the required subclass contract centers on `getUri`, `open(Path,int)`, `create(Path,FsPermission,boolean,int,short,long,Progressable)`, `append(Path,int,Progressable)`, `rename(Path,Path)`, `delete(Path,boolean)`, `listStatus(Path)`, `setWorkingDirectory`, `getWorkingDirectory`, `mkdirs(Path,FsPermission)`, and `getFileStatus(Path)`. Static construction APIs include `get(Configuration)`, `get(URI,Configuration)`, `newInstance(...)`, `getLocal`, `newInstanceLocal`, `closeAll`, and `closeAllForUGI`. Common convenience APIs layer defaults for create/open/append overloads, path handles, server defaults, block locations, listing/filtering/globbing, recursive file iteration, local copy helpers, delete-on-exit, content summaries, quota usage, permissions, checksums, symlinks, ACLs, xattrs, snapshots, storage policies, trash roots, multipart upload, and bulk delete.

Control flow: URI resolution first normalizes deprecated names (`local`, unqualified HDFS names), applies the configured default filesystem when scheme or authority is absent, optionally bypasses the cache with `fs.$scheme.impl.disable.cache`, and otherwise delegates to `Cache.get`. Cache misses are serialized by a semaphore sized by `fs.creation.parallel.count`; a filesystem class is found from `fs.$scheme.impl` or `ServiceLoader<FileSystem>`, instantiated by reflection, initialized, inserted into the cache, and optionally registered for automatic shutdown. Most overloads collapse into a small set of abstract core calls; for example create overloads resolve buffer size, replication, block size, umask, flags, and checksum options before calling the abstract create method, while list APIs build iterators from `listStatus` or `listStatusBatch`.

State and persistence behavior: process-global state includes `CACHE`, `statisticsTable`, service-loaded scheme bindings, the symlink-enabled flag, and the daemon statistics cleaner thread. Instance state includes its cache key, per-class/per-scheme `Statistics`, the `deleteOnExit` path set, and the `resolveSymlinks` configuration flag. No file metadata is persisted by this base class; persistence is delegated to implementations. `close()` processes delete-on-exit entries and removes the instance from the cache. The cache's shutdown hook closes automatically closable filesystems at JVM shutdown, and `MultipleIOException` aggregates close failures.

Dependencies and integration points: this class ties together Hadoop `Configuration`, `Path`, `FileStatus`, `FSDataInputStream`, `FSDataOutputStream`, `FsPermission`, `UserGroupInformation`, delegation tokens, `SecurityUtil`, `Credentials`, `GlobalStorageStatistics`, tracing, `ShutdownHookManager`, `FileUtil`, `Globber`, `FSLinkResolver`, builder implementations, and capability constants. It is the compatibility point for `FilterFileSystem`, `ChecksumFileSystem`, `LocalFileSystem`, `DistributedFileSystem`, `FileContext` transition methods, and external ecosystem shims. Implementers must keep new APIs consistent with wrappers and capability probes.

Statistics behavior: nested `Statistics` stores write-heavy counters in per-thread `StatisticsData` instances referenced through weak references. Reads aggregate `rootData` plus all live thread-local data under the statistics lock. A daemon cleaner folds counters from garbage-collected threads into `rootData`. `reset()` avoids mutating other threads' thread-local data by adding the negative aggregate to `rootData`. `getStatistics(scheme, class)` registers a `FileSystemStorageStatistics` provider in `GlobalStorageStatistics`, while `clearStatistics()` resets through the global statistics registry.

Optional feature defaults: many advanced features deliberately throw `UnsupportedOperationException` unless overridden, including path-handle open/create, concat, truncate, msync, symlink operations, snapshots, ACLs, xattrs, storage policies, quotas, corrupt-block listing, multipart upload, and non-recursive create. Other defaults are no-ops or coarse fallbacks, such as `setPermission`, `setOwner`, `setTimes`, checksum toggles, `setReplication` returning true, default status returning unbounded capacity, block locations returning localhost, and bulk delete returning `DefaultBulkDeleteOperation`.

Risks: `createNewFile` is explicitly non-atomic because it checks existence before creating. Default recursive `getContentSummary` and `listFiles` can be expensive and racy on large mutable trees. `exists`, `isFile`, and `isDirectory` add extra metadata calls and can create time-of-check/time-of-use hazards. `checkPath` depends on canonical URI/authority comparison and default URI authority inference, so custom filesystems must override carefully if their authority semantics differ. The cache must avoid leaking duplicate filesystem instances under concurrent creation; the semaphore and duplicate close path are central to that. Global service loading is one-time and logs but skips broken service entries, which can hide classpath issues until scheme lookup fails. Symlinks are globally disabled by default, so per-instance `resolveSymlinks` is not enough to enable traversal.

Test signals: important coverage should exercise default URI fallback, cache hit/miss behavior, cache bypass, duplicate concurrent creation cleanup, UGI-specific cache keys, automatic close and delete-on-exit, service-loader and `fs.$scheme.impl` resolution, path qualification and wrong-FS rejection, create/append builder flag routing, open-file mandatory option rejection, statistics aggregation/reset and thread cleanup, default unsupported optional APIs, list/glob iterator behavior, `hasPathCapability` for bulk delete and symlinks, and delegation token issuer propagation to child filesystems.

# sources/distributed-fs/hadoop/hadoop-common-project/hadoop-common/src/main/java/org/apache/hadoop/fs/FileSystemLinkResolver.java

Purpose: `FileSystemLinkResolver<T>` is a private evolving helper for implementing `FileSystem` operations that may encounter symbolic links and need to retry after resolving the first unresolved path component. It specializes the more generic symlink resolver pattern for operations that start on a `FileSystem` and may continue on another filesystem if the resolved target crosses URI boundaries.

Important APIs and types: subclasses implement `doCall(Path)` for the first operation attempt on the original filesystem and `next(FileSystem, Path)` for retrying the equivalent operation against a resolved target on a different filesystem. The public `resolve(FileSystem, Path)` method drives the retry loop and returns the generic operation result.

Control flow: `resolve` begins with the supplied filesystem and path, assumes callers already validated the path with `FileSystem.checkPath`, and invokes `doCall`. If the call succeeds, the result is returned. If `doCall` throws `UnresolvedLinkException`, the resolver first checks the instance-level `resolveSymlinks` flag and then the global `FileSystem.areSymlinksEnabled()` flag. It enforces `FsConstants.MAX_PATH_LINKS` to detect likely cycles, resolves the first unresolved component through `filesys.resolveLink(p)`, qualifies the target with `FSLinkResolver.qualifySymlinkTarget(fs.getUri(), p, target)`, obtains the filesystem for the resolved path with `FileSystem.getFSofPath`, and either delegates immediately to `next` for a new filesystem or loops again on the same filesystem.

State and persistence behavior: the class has no persistent fields. Runtime state is local to `resolve`: the current path, current filesystem, link-follow count, and last operation result. It does not alter filesystem metadata; it only performs resolution and delegates operations to filesystem implementations.

Dependencies and integration points: it depends on `FileSystem.resolveLink`, `FileSystem.getFSofPath`, global symlink enablement, `CommonConfigurationKeys.FS_CLIENT_RESOLVE_REMOTE_SYMLINKS_KEY` diagnostics, `FSLinkResolver.qualifySymlinkTarget`, and `FsConstants.MAX_PATH_LINKS`. It is meant to be instantiated anonymously by `FileSystem` methods that need consistent symlink retry behavior while keeping the operation-specific call in `doCall`/`next`.

Risks: resolution-disabled failures wrap the original `UnresolvedLinkException` in an `IOException`, so callers must not rely on the original exception type after policy checks. Cross-filesystem resolution exits through `next` immediately; same-filesystem resolution can repeat until success or the maximum link count is exceeded. The method uses `filesys.resolveLink(p)` even after `fs` has changed for qualification, so implementations must ensure the first unresolved component remains meaningful to the original resolver path until a cross-filesystem handoff occurs. Cycle detection is count-based rather than graph-based.

Test signals: coverage should include successful no-link calls, same-filesystem link resolution with repeated unresolved components, cross-filesystem handoff to `next`, disabled per-client symlink resolution, globally disabled symlink resolution, and cyclic or too-deep link chains that exceed `MAX_PATH_LINKS`.

# sources/distributed-fs/hadoop/hadoop-common-project/hadoop-common/src/main/java/org/apache/hadoop/fs/FileSystemStorageStatistics.java

Purpose: `FileSystemStorageStatistics` adapts a `FileSystem.Statistics` instance into the newer `StorageStatistics` interface. It exposes the counters maintained by `FileSystem.Statistics.StatisticsData` as named long statistics for global storage-statistics consumers.

Important APIs and types: the class extends `StorageStatistics`, stores a non-null `FileSystem.Statistics`, and exposes `getScheme()`, `getLongStatistics()`, `getLong(String)`, `isTracked(String)`, and `reset()`. Its tracked keys are `bytesRead`, `bytesWritten`, `readOps`, `largeReadOps`, `writeOps`, `bytesReadLocalHost`, `bytesReadDistanceOfOneOrTwo`, `bytesReadDistanceOfThreeOrFour`, `bytesReadDistanceOfFiveOrLarger`, `bytesReadErasureCoded`, and `remoteReadTimeMS`.

Control flow: `getLongStatistics()` captures an aggregate `StatisticsData` snapshot from `stats.getData()` and returns a `LongStatisticIterator` over the fixed key array. Each iterator step calls `fetch(data, key)` and wraps the value in `LongStatistic`. `getLong(key)` fetches the current aggregate data and dispatches by string key. `readOps` deliberately reports `data.getReadOps() + data.getLargeReadOps()`, while `largeReadOps` remains independently visible. Unknown keys return null. `isTracked` scans the fixed key list.

State and persistence behavior: persistent object state is just the referenced `FileSystem.Statistics`; all exposed values are derived from that statistics object. The iterator keeps a snapshot `StatisticsData`, so later increments are not reflected in an already-created iterator. `reset()` delegates to `stats.reset()`, which affects the underlying shared per-filesystem statistics counters rather than only this adapter.

Dependencies and integration points: the adapter is constructed from `FileSystem.getStatistics(scheme, cls)` when registering a `StorageStatisticsProvider` with `GlobalStorageStatistics`. It depends on `StorageStatistics.LongStatistic`, `FileSystem.Statistics.StatisticsData`, and Hadoop `Preconditions`. Consumers using `GlobalStorageStatistics` see these keys for legacy `FileSystem` implementations that report through `FileSystem.Statistics`.

Risks: `fetch` validates only that the key is non-null; unknown strings silently return null, so callers must use `isTracked` or handle missing values. `LongStatisticIterator.next()` calls `val.longValue()` and therefore depends on every key in `KEYS` being handled by `fetch`; adding a key without updating the switch would introduce a null dereference. The `readOps` aggregate includes large reads, which is correct for this API but can surprise callers that sum `readOps` and `largeReadOps`.

Test signals: useful tests should assert constructor rejection of null statistics or null data, exact key tracking, iterator order and exhaustion behavior, unknown-key null return, `readOps` including large reads, distance-bucket and erasure-coded counters, remote read time, scheme propagation, and that `reset()` zeroes the underlying statistics visible through both this adapter and the original `FileSystem.Statistics`.
