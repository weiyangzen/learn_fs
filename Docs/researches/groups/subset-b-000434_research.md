# sources/control-plane/rook/deploy/examples/create-external-cluster-resources-tests.py

Purpose: this is the unit-test companion for Rook's `create-external-cluster-resources.py` helper. It imports the hyphenated production script through `importlib.import_module`, creates `RadosJSON` instances with representative command-line arguments, replaces the real Ceph `rados.Rados` connection with `DummyRados.Rados()`, and exercises output generation, auth-cap construction, CephFS pool discovery, endpoint validation, monitoring endpoint selection, upgrade mode, skip-monitoring behavior, and v2 monitor port selection.

Important APIs/types/functions: the only test class is `TestRadosJSON(unittest.TestCase)`. `setUp` constructs a default `RadosJSON` with `--rbd-data-pool-name`, `--rgw-endpoint`, and JSON output, then injects `DummyRados`. `tearDown` delegates to `RadosJSON.shutdown`. Individual tests call production methods directly: `main`, `create_cephCSIKeyring_user`, `create_checkerKey`, `get_cephfs_data_pool_details`, `_invalid_endpoint`, `get_active_and_standby_mgrs`, and `get_ceph_external_mon_data`. The tests also mutate `self.rjObj._arg_parser` and `self.rjObj.cluster.cmd_output_map` directly to simulate CLI and Ceph response variants.

Control flow: the default fixture validates both JSON and bash output paths and confirms an unsupported output format raises `ExecutionFailureException`. CephFS tests alter the fake `fs ls` JSON to cover multiple filesystems, selected filesystem names, missing filesystem names, multiple data pools, missing data pools, and empty data-pool arrays. Monitoring tests build `RadosJSON` without RGW arguments, set or clear `monitoring_endpoint` and `monitoring_endpoint_port`, call `get_active_and_standby_mgrs`, and compare returned IP/port values against expected defaults or `DummyRados` hostname conversion. RGW endpoint validation checks `_invalid_endpoint` accepts a normal `IPv4:port` endpoint and rejects an out-of-range port. Upgrade testing constructs a separate object with `--upgrade --run-as-user=client.csi-cephfs-provisioner` and drives `main`.

State and persistence behavior: the tests do not persist to disk and do not create Kubernetes resources. State is intentionally in-memory and highly mutable: the fake cluster has `return_val`, `err_message`, `cmd_output_map`, and `dummy_host_ip_map`; the parsed arguments object is mutated between assertions; and some tests replace `self.rjObj` with a new object without first shutting down the previous dummy instance. Output state is inspected through `self.rjObj.out_map`, especially `MONITORING_ENDPOINT` and `MONITORING_ENDPOINT_PORT` after skip or failure paths.

Dependencies and integration points: this file depends on the production script's `DummyRados` fixture data and on `test-data/ceph-status-out` loaded by `DummyRados`. It uses Python `unittest`, `json`, `os`, `sys.path` manipulation, and `importlib`. It is tightly coupled to the exact sorted JSON command strings used as keys in `DummyRados.cmd_output_map`, such as `{"format": "json", "prefix": "fs ls"}` and `{"format": "json", "prefix": "status"}`. The direct import of the production script means the test environment still needs import-time handling for `rados` and `rbd`; if those modules are unavailable and not otherwise provided, the production script exits before `DummyRados` can be substituted.

Risks: assertions are weak in several places because many tests only print output and rely on absence of exceptions. Direct mutation of private `_arg_parser` fields bypasses parser validation and can hide bugs in CLI parsing or config-file precedence. The tests do not verify the exact JSON or bash payload shape emitted by `main`, so resource schema regressions can pass. Test cases reuse a mutable fixture, and exception paths can leave modified command maps or parser fields for the rest of a test method. Monitoring host conversion through `DummyRados` uses random IP generation for unseen hostnames, so tests avoid exact assertions except where the dummy map already contains a hostname. The production script's import-time dependency on Ceph Python modules is a fragility for ordinary Python unit-test runners.

Test signals: existing coverage is strongest for direct `ExecutionFailureException` paths around Ceph command errors, invalid endpoint ports, missing CephFS names/pools, missing prometheus service, invalid monitoring ports, and v2 monitor port extraction. Missing signals include exact output-resource comparison, config-file precedence, RGW admin-ops success/failure behavior, topology pools, RBD namespace validation, cephx key rotation generation selection, `--output` file writing, TLS certificate handling, and subprocess failure details for `radosgw-admin` and `ceph fs subvolumegroup`.

# sources/control-plane/rook/deploy/examples/create-external-cluster-resources.py

Purpose: this Python command-line helper connects to an existing external Ceph cluster and emits the Kubernetes resources or shell exports needed for a Rook consumer cluster. It discovers monitor, manager, CephFS, RBD, RGW, topology, namespace, and dashboard details; creates or upgrades Ceph auth users for the external health checker and CSI drivers; optionally validates RGW endpoints and multisite settings; and serializes the result as JSON resource descriptors or bash `export` lines.

Important APIs/types/functions: `ExecutionFailureException` is the script's operational failure type. `DummyRados` is an in-file fake `rados` implementation for unit tests, with canned monitor command outputs keyed by sorted JSON command strings. `S3Auth` implements an AWS S3-style request signer for RGW admin-ops validation. `RadosJSON` is the main class. Its major surfaces are `gen_arg_parser`, `parse_config_file`, `_common_cmd_json_gen`, `get_ceph_external_mon_data`, `get_active_and_standby_mgrs`, `get_*_caps_and_entity`, `create_cephCSIKeyring_user`, `create_checkerKey`, `get_cephfs_data_pool_details`, `create_rgw_admin_ops_user`, `validate_rgw_endpoint`, `validate_rbd_metadata_ec_pool_name`, `validate_rados_namespace`, topology validation helpers, `_gen_output_map`, `gen_json_out`, `gen_shell_out`, `get_cephx_latest_key_generation`, `upgrade_users_permissions`, `upgrade_user_permissions`, and `main`.

Control flow: import time requires `requests`, `rados`, and `rbd`; missing Ceph bindings print an error and exit. Construction parses CLI args, optionally overlays a config file, chooses default `client.healthchecker` and RGW pool prefix outside upgrade mode, creates a `rados.Rados` object from optional conf/keyring, reads config when needed, and connects. `main` normalizes the legacy cluster-name flag, lowercases the Kubernetes cluster name, computes the cephx key generation from `auth ls`, applies rotate or revert semantics, then chooses upgrade, JSON, or bash generation. JSON and shell generation both call `_gen_output_map`, which validates RBD and namespace inputs, discovers CephFS defaults, creates required users, gathers monitoring endpoints unless skipped, validates topology inputs, optionally creates and validates RGW admin-ops credentials, and stores all derived values in `out_map`. `gen_json_out` converts `out_map` into a list of ConfigMap, Secret, CephCluster, StorageClass, and CephBlockPoolRadosNamespace descriptors; `gen_shell_out` writes non-empty exported variables. The script-level `__main__` wrapper catches expected errors, prints diagnostics, re-raises execution failures, and always shuts the cluster down.

State and persistence behavior: runtime state is held in `RadosJSON._arg_parser`, `run_as_user`, `cluster`, `_excluded_keys`, and `out_map`. `_gen_output_map` is idempotent after first population because it returns immediately when `out_map` is non-empty. Persistent effects happen in the external Ceph cluster rather than the repository: `auth get-or-create`, `auth caps`, `rbd pool_init`, `radosgw-admin user create/info/caps add`, and `ceph fs subvolumegroup create/pin` can all mutate cluster state. File persistence is limited to `--output`, which writes the generated JSON or shell text to a local file. Config-file parsing mutates parsed arguments in place, with command-line arguments taking precedence over `[Configurations]` values.

Dependencies and integration points: the script integrates with Ceph monitor commands through `rados.Rados.mon_command`, RBD pool and namespace APIs through `rbd.RBD`, external CLI tools `radosgw-admin` and `ceph`, HTTP(S) RGW and manager endpoints through `requests`, and Kubernetes/Rook consumers through the generated resource descriptors. It assumes Ceph command outputs have fields such as `quorum_leader_name`, `monmap.mons[].public_addr`, `mgrmap.services.prometheus`, `mgrmap.standbys`, `auth_dump`, `fs ls` metadata/data pool fields, and RGW admin info `storage_backends[0].cluster_id`. It also integrates with Rook's external cluster flow by emitting well-known object names like `rook-ceph-mon-endpoints`, `rook-ceph-operator-creds`, `rook-csi-rbd-node`, `ceph-rbd`, `cephfs`, and `ceph-rgw`.

Auth and resource generation details: CSI user caps are generated by user type and optional restriction. Restricted RBD users require `--rbd-data-pool-name` and `--k8s-cluster-name`, can use `--alias-rbd-data-pool-name` when pool names contain `.` or `_`, and optionally include a RADOS namespace in both entity name and OSD caps. Restricted CephFS users require a Kubernetes cluster name and can scope OSD caps to a selected filesystem metadata tag. The health checker gets monitor quorum/version, manager config, MDS, and RGW pool permissions based on `--rgw-pool-prefix`. Generation suffixes are appended for cephx rotation. Existing users are reused by `check_user_exist`, while upgrade mode reads existing caps, merges new cap fragments in stable order, and applies `auth caps`.

Validation and discovery behavior: endpoint parsing accepts IPv4, IPv6-in-brackets, and FQDN forms with valid TCP port ranges. Manager monitoring discovery reads `ceph status`, extracts the prometheus URL, adds standby managers, converts hostnames to IPs, and verifies reachability unless using `DummyRados`; `--skip-monitoring-endpoint` avoids this requirement. CephFS discovery silently returns when multiple filesystems exist and no selector is provided, but raises when explicit filesystem or data-pool inputs are inconsistent. RBD metadata EC validation requires the data pool to be erasure-coded and the metadata pool to be replicated. RGW validation can create an admin-ops user, add `info=read` when supported, probe HTTP/HTTPS, compare RGW cluster ID to Ceph FSID, and validate non-default RGW pools. Topology support requires all topology flags together and matching pool/value lengths.

Risks: import-time `sys.exit(1)` on missing `rados` or `rbd` makes the module hard to import in lightweight tooling and tests. Many booleans in argparse are declared without `action="store_true"` or a converter, so config-file or CLI string values such as `"false"` can still behave truthy. `parse_config_file` checks `str(sys.argv)` instead of the explicit `arg_list`, which can be wrong for tests or embedded callers. The code catches broad exceptions in hostname conversion and canonical-header handling, potentially hiding root causes. Several external mutations happen before later validation steps, so a failure can leave partially created users, subvolume groups, or caps. RGW multisite validation overwrites `err` repeatedly and does not immediately stop after each failure. `_gen_output_map` caches the first result and will not reflect later argument mutations. Endpoint validation uses network probes and admin-ops calls, creating environmental flakiness. Upgrade cap merging splits on commas, which is fragile for cap syntaxes where commas are semantic separators inside a single permission string.

Test signals: good tests should cover parser/config precedence, import behavior with and without Ceph bindings, dry-run command text, all user cap/entity combinations, cephx rotate/revert generation selection, `auth get-or-create` reuse versus creation, upgrade cap merge ordering, CephFS zero/one/many filesystem cases, RBD EC metadata validation, RADOS namespace case and existence checks, monitoring endpoint discovery and skip mode, IPv4/IPv6/FQDN endpoint parsing, RGW TLS and admin-ops validation, topology missing/mismatched flags, generated JSON resource shape for each optional feature, bash output exclusion of `K8S_CLUSTER_NAME`, and `--output` file writing. The existing companion unit tests exercise several direct method failure paths with `DummyRados`, but they do not yet assert most emitted resource payloads.

# sources/control-plane/rook/deploy/examples/csi-ceph-conf-override.yaml

Purpose: this Kubernetes ConfigMap provides a Ceph configuration override for Rook CSI sidecars. It defines `csi-ceph-conf-override` in the `rook-ceph` namespace and supplies a `ceph.conf` fragment under `data` so deployed CSI components can consume non-default Ceph client settings.

Important APIs/types/functions: the resource is a core Kubernetes `v1` `ConfigMap`. The significant keys are `metadata.name: csi-ceph-conf-override`, `metadata.namespace: rook-ceph` with a `# namespace:operator` substitution hint used by Rook example manifests, and `data.ceph.conf`, a literal block containing a `[global]` Ceph config section. The Ceph settings are `auth_cluster_required = cephx`, `auth_service_required = cephx`, `auth_client_required = cephx`, and `rbd_validate_pool = false`.

Control flow: this file has no executable control flow. Operationally, it is applied to Kubernetes before or alongside Rook CSI deployment. The operator or deployment manifests mount or reference the ConfigMap so CSI pods see the override as part of their Ceph configuration. The namespace comment indicates the example can be rewritten to the operator namespace by manifest tooling or documentation conventions.

State and persistence behavior: persistence is Kubernetes API state. Once applied, the ConfigMap stores a static `ceph.conf` fragment. Changes require updating the ConfigMap and ensuring any consuming pods reload or restart if they do not dynamically reread the mounted file. It does not contain secrets, but it changes client behavior for all consumers wired to the override.

Dependencies and integration points: this file integrates with Rook's CSI configuration path, Ceph client configuration syntax, Kubernetes ConfigMap storage, and Rook example deployment namespace replacement. The three `auth_*_required = cephx` settings align the CSI clients with CephX authentication. `rbd_validate_pool = false` affects RBD client behavior by disabling pool validation, which can be useful when the CSI driver needs to operate before a pool is visible in the expected way or when external-cluster metadata differs from local defaults.

Risks: disabling RBD pool validation can mask an incorrectly named or missing pool until a later operation fails. A namespace mismatch prevents CSI pods from finding the ConfigMap. Because the whole `ceph.conf` fragment is embedded as a literal string, indentation mistakes or accidental key changes can silently alter client behavior. Authentication settings must remain consistent with the external Ceph cluster; if the cluster does not use CephX in the expected way, CSI startup or volume operations can fail.

Test signals: validate this manifest with Kubernetes YAML tooling, confirm it applies in the intended namespace, confirm the CSI deployment references or mounts `csi-ceph-conf-override`, inspect a running CSI pod to ensure the resulting `ceph.conf` includes these settings, and run RBD-backed volume provisioning against a pool that would otherwise exercise `rbd_validate_pool` behavior. Regression checks should include namespace substitution and ConfigMap update/restart behavior.
