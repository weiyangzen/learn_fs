## sources/user-network-fs/nfs-ganesha/src/FSAL/FSAL_GPFS/include/gpfs.h

Purpose: This is the imported IBM GPFS user-library public ABI header used by the GPFS FSAL. It is explicitly marked as taken directly from GPFS source and should not be modified beyond license notices, so its role is compatibility: it gives Ganesha source code the exact types, constants, function declarations, errno extensions, and 32/64-bit inode mappings expected by libgpfs and GPFS kernel services.

Important APIs and types: The file starts with platform abstraction for `GPFS_API` and `gpfs_file_t`, then defines GPFS scalar types, timestamp types, stat-lite masks, ACL formats, Windows attribute flags, share/lease constants, GPFS inode/stat types, directory entry formats, inode attribute formats, fssnap/iscan/ifile/restore opaque handle types, quota structures, clone operations, lightweight event structures, QoS calls, encryption helpers, and trace functions. High-importance function families include ACL calls (`gpfs_getacl`, `gpfs_putacl`), exact and lite stat calls (`gpfs_fstat`, `gpfs_stat_x`, `gpfs_statlite`), backup/restore-by-inode flows (`gpfs_get_fssnaphandle_*`, `gpfs_open_inodescan*`, `gpfs_next_inode*`, `gpfs_iopen*`, `gpfs_iread`, `gpfs_iwrite`, `gpfs_iclose`), quota and fileset calls (`gpfs_quotactl`, `gpfs_getfilesetid`), clone management (`gpfs_clone_snap`, `gpfs_clone_copy`, `gpfs_declone`, `gpfs_clone_split`, `gpfs_clone_unsnap`), lightweight events (`gpfs_lwe_*`), and trace bridging (`gpfs_init_trace`, `gpfs_query_trace`, `gpfs_add_trace`, `gpfs_fini_trace`).

Control flow and state: This header has no executable control flow, but it encodes many stateful protocols. ACL buffers are variable-length and caller-owned. Fssnap handles are volatile objects that must be freed with `gpfs_free_fssnaphandle`; scan handles are consumed by seek/next/stat calls and must be closed with `gpfs_close_inodescan`; inode file handles are opened by inode and closed with `gpfs_iclose`; restore sessions move through enable, start, write/attribute restore, sync, and end states. Lightweight event sessions maintain kernel-side queues, access-right tokens, event responses, and token invalidation after release. The `GPFS_64BIT_INODES` block remaps public names to 64-bit variants and changes default structure versions.

Persistence behavior: The declared calls directly expose persistent GPFS metadata and data operations: ACL updates, file times, Windows attributes, share/lease state, file truncation, extended attributes, storage-pool placement, quota accounting, snapshot/incremental restore identifiers, inode content reads/writes, clone parent/child state, encryption key wrapping, and trace output. Many APIs distinguish volatile handles from non-volatile snapshot IDs; backup/restore logic must persist fssnap IDs rather than in-memory handles.

Dependencies and integration points: Consumers must compile in an environment where GPFS headers, system stat/statfs structures, errno values, and open flags are compatible. The header is a boundary with libgpfs and GPFS kernel services rather than local Ganesha code. GPFS FSAL files use it alongside `gpfs_nfs.h` to translate NFS-Ganesha behavior to GPFS-specific handles, attributes, pNFS, tracing, and callback semantics.

Risks: ABI drift is the dominant risk; local edits or mismatched GPFS library versions can corrupt variable-length structs, wrong ioctl payloads, or 32/64-bit inode selection. The backup/restore APIs require superuser privilege and careful lifecycle management. Many calls return `-1` with errno, including GPFS-specific errno ranges, so wrappers must preserve errno semantics. Variable-length ACL, xattr, and scan buffers require exact size handling. Several comments document behavior that is version-dependent or experimental, including directory preallocation, clone support, QoS, encryption, and LWE. Test signals should include compile checks against target GPFS headers/libraries, runtime smoke tests for stat/handle/open paths, ACL/xattr round trips, 64-bit inode builds, and failure injection for privilege, stale handle, ENOSPC, ENOSYS, and buffer-too-small cases.

## sources/user-network-fs/nfs-ganesha/src/FSAL/FSAL_GPFS/include/gpfs_nfs.h

Purpose: This header defines the GPFS/Ganesha NFS interface contract carried through `gpfs_ganesha(int op, void *oarg)`. It is the GPFS-specific command and argument ABI for open-by-handle, pNFS layout/device operations, data-server reads/writes, xstat, xattrs, locking, callbacks, tracing, quota, and filesystem-location requests.

Important APIs and types: The central API is `gpfs_ganesha`, parameterized by `OPENHANDLE_*` operation codes. The command range starts at `OPENHANDLE_GET_VERSION` and covers name-to-handle, open-by-handle, file layout, device info/list, layout get/return/commit, inode update, xstat get/set/access, lock get/set, thread update, DS read/write, verifier, fsync, share reservation, close, link/rename/readlink/unlink/create/stat by handle/name, fd read/write, allocate/reopen/fadvise/seek, statfs, xattrs, mknode, tracing, quota, and FS locations. Key payloads include `struct gpfs_file_handle`, `struct name_handle_arg`, `struct open_arg`, `struct glock`, pNFS structs such as `nfsd4_pnfs_deviceid`, `nfsd4_layout_seg`, `pnfs_filelayout_layout`, `deviceinfo_arg`, `layoutget_arg`, `layoutcommit_arg`, `dsread_arg`, `dswrite_arg`, plus xstat/xattr/quota/fs-location argument structs.

Control flow and state: Callers populate one operation-specific struct, pass it to `gpfs_ganesha`, and interpret in/out fields after return. Several payloads carry file descriptors rooted at a mount directory, GPFS file handles, client IP strings, lock owners, state reclaim flags, or verifier buffers. pNFS state flows through device IDs, layout segments, layout body XDR streams, commit ranges, return cookies, and callback reasons. Callback state is represented by `callback_arg`, where GPFS reports invalidation/update/lock/delegation/layout/device reasons and flags such as `UP_SIZE`, `UP_TIMES`, and `XATTR_*` tell Ganesha which cached state changed.

Persistence behavior: The file itself persists nothing, but its payloads operate on persistent GPFS namespace objects by file handle or fd. It exposes metadata updates through xstat and create/stat structures, persistent link/rename/unlink/mknode operations, pNFS layout commitments that may update size/mtime, xattr mutation, quota controls, and fs-location discovery. It also carries ephemeral process state such as open fds, lock owner pointers, share reservations, write verifiers, and callbacks that must be interpreted while the relevant Ganesha state exists.

Dependencies and integration points: It depends on NFS and POSIX types supplied by surrounding includes, including `struct flock`, `struct stat`, `struct statfs`, `pnfs_deviceid`, and `fsal_stats` from Ganesha. GPFS FSAL implementation files use these opcodes to call into GPFS kernel/user infrastructure. The operation numbering and statistics constants (`GPFS_STAT_MAX_OPS`, `GPFS_TOTAL_OPS`) must stay synchronized with GPFS-side dispatch.

Risks: This is a fragile binary interface: field ordering, integer widths, handle lengths, and opcode values must match the GPFS implementation. The stats-range comments already note missing opcodes and a special placeholder, so adding operations without updating ranges can break telemetry or bounds checks. Many structs include raw pointers passed across the interface, making lifetime and address-space expectations critical. Client IP propagation and credential payloads are security-sensitive. Test signals should include version negotiation, each opcode family smoke test, pNFS layout get/commit/return validation, lock reclaim/grace behavior, callback invalidation handling, and xstat/xattr buffer length edge cases.

## sources/user-network-fs/nfs-ganesha/src/FSAL/FSAL_GPFS/main.c

Purpose: This file is the GPFS FSAL module entry point. It declares the singleton `GPFS` module object, default filesystem capability metadata, module-level configuration, GPFS trace logging integration, and the load/unload hooks that register GPFS with NFS-Ganesha.

Important APIs and functions: `struct gpfs_fsal_module GPFS` embeds `struct fsal_module` and initializes `fs_info` with high limits, link/symlink/lock/xattr/ACL support, pNFS MDS and DS support, trace support, grace flag, supported attributes, and cache-expiry behavior. `gpfs_params` exposes configuration for link/symlink support, timestamp setting, umask, cross-device export authorization, delegations, pNFS MDS/DS, FSAL trace, and FSAL grace. `log_to_gpfs` packages Ganesha log component text into `struct trace_arg` and invokes `gpfs_ganesha(OPENHANDLE_TRACE_ME, &targ)`. `init_config` prepares stats, loads the GPFS config block into `fs_info`, creates a GPFS log facility, and enables or disables that facility according to `fsal_trace`. `gpfs_init` registers the module and installs module operations, while `gpfs_unload` releases the log facility and unregisters the FSAL.

Control flow and state: On shared-object load, `gpfs_init` registers `myname = "GPFS"` with `FSAL_ID_GPFS`, assigns operation pointers for DS ops, export creation, configuration, device info, device-address sizing, optional DBus stats extraction, and stats reset, then initializes base and pNFS-enhanced object operation tables. During configuration, Ganesha calls `init_config`; parse errors abort initialization with `ERR_FSAL_INVAL`, while successful parse configures logging and returns no error. On unload, logging is released before module unregistration.

Persistence behavior: This file persists no user data. It mutates process-global module state: the singleton `GPFS.module`, its `fs_info`, log facility registry state, and operation vectors. The configured capability flags influence later exports and client-visible NFS behavior, including whether pNFS and trace integration are advertised.

Dependencies and integration points: The file integrates `fsal.h`, `fsal_internal.h`, `FSAL/fsal_init.h`, `gpfs_methods.h`, `gsh_config.h`, and the GPFS NFS trace opcode contract from `gpfs_nfs.h` through `trace_arg` and `OPENHANDLE_TRACE_ME`. It depends on FSAL core registration, config parsing, logging facility management, stats setup, GPFS export creation, GPFS handle ops, and pNFS helper hooks.

Risks: The config block is `CONFIG_UNIQUE`, so multiple GPFS FSAL global blocks are intentionally disallowed. Trace logging only sends `compstr` with `strlen(compstr)`, not the full log message; if GPFS trace users expect message text, this is surprising. `log_to_gpfs` silently ignores nonpositive levels. Failure to create/enable/disable the log facility aborts config. Capability defaults advertise broad GPFS and pNFS support, so incorrect build/runtime GPFS support can produce client-visible failures later. Test signals include module load/unload tests, config parsing tests for each GPFS parameter, logger enable/disable behavior, `gpfs_ganesha(OPENHANDLE_TRACE_ME)` error propagation, pNFS capability toggles, and stats hook availability with and without DBus.

## sources/user-network-fs/nfs-ganesha/src/FSAL/FSAL_KVSFS/CMakeLists.txt

Purpose: This CMake file builds the KVSFS FSAL plugin module. It wires KVSFS source files into a shared module named `fsalkvsfs`, links it to the KVS namespace library and hiredis, assigns module version metadata, and installs it into the configured FSAL destination.

Important build definitions: If `KVSFS_PREFIX` is set, it appends include and library flags using `${KVSNS_PREFIX}/include` and `${KVSNS_PREFIX}/lib`. `fsalkvsfs_LIB_SRCS` includes `kvsfs_fsal_internal.c`, `kvsfs_main.c`, `kvsfs_export.c`, `kvsfs_handle.c`, `kvsfs_file.c`, `kvsfs_xattrs.c`, `kvsfs_mds.c`, and `kvsfs_ds.c`. `add_library(fsalkvsfs MODULE ...)` creates the dynamically loaded FSAL module. `target_link_libraries` links `kvsns`, `hiredis`, and `${SYSTEM_LIBRARIES}`. `set_target_properties` sets version `4.2.0` and soversion `4`. `install(TARGETS fsalkvsfs COMPONENT fsal DESTINATION ${FSAL_DESTINATION})` installs the plugin.

Control flow and state: The file has straightforward configure-time control: optional prefix flags, source aggregation, target creation, sanitizer hook, link libraries, properties, and install rule. Runtime FSAL behavior is defined in the C sources.

Persistence behavior: Build state consists of compiler/linker flags, produced module artifacts, and installation into the FSAL plugin destination. No source-level runtime persistence is encoded here.

Dependencies and integration points: It integrates with the repository's global CMake macros, especially `add_sanitizers`, `SYSTEM_LIBRARIES`, and `FSAL_DESTINATION`. Appending `-L` to `CMAKE_C_FLAGS` is also nonstandard because library search paths are link flags, not compile flags. Test signals include configuring with and without prefix variables, verifying `fsalkvsfs` links to the intended libraries, ensuring sanitizer builds actually instrument `fsalkvsfs`, and installing/loading the module in a Ganesha test instance.

## sources/user-network-fs/nfs-ganesha/src/FSAL/FSAL_KVSFS/kvsfs_ds.c

Purpose: This file implements KVSFS pNFS data-server operations. It allows NFSv4.1 DS filehandles to be created from wire handles and services direct data-server read, write, commit, permission, and release operations using the KVSNS API.

Important functions: `kvsfs_release` frees the private `struct kvsfs_ds`. `kvsfs_ds_read` opens the KVSNS file read-only using `op_ctx` credentials, performs `kvsns_read` at the requested offset and length, closes the KVSNS open handle, fills supplied length and EOF, and returns NFSv4 status. `kvsfs_ds_write` opens write-only, writes the buffer through `kvsns_write`, closes, zeroes the write verifier, and reports the requested stability as the achieved stability. `kvsfs_ds_commit` is a no-op that zeroes the verifier and returns `NFS4_OK`. `make_ds_handle` validates a wire handle length, allocates `struct kvsfs_ds`, copies `struct kvsfs_file_handle`, and leaves `connected = false`. `pds_permissions` delegates request authorization to `nfs4_export_check_access`. `kvsfs_pnfs_ds_ops_init` copies default DS ops then installs KVSFS methods.

Control flow and state: The DS handle is a lightweight wrapper around a serialized KVSFS inode handle. Read/write operations do not use cached mdcache object handles; each operation opens and closes a KVSNS file handle using the caller's current UID/GID. Error paths translate negative KVSNS errno-style returns with `posix2nfs4_error`. The `connected` flag is initialized but not otherwise used in this file, matching the comment that lazy connection may be needed for FILE_SYNC4-style behavior.

Persistence behavior: Persistent file content is read and written through KVSNS. Commit does not flush or persist anything beyond what KVSNS writes already do, and write verifiers are all zero. DS handle allocation itself is ephemeral and freed by release.

Dependencies and integration points: The file depends on FSAL pNFS DS interfaces, `pnfs_utils.h`, NFS export/credential helpers, `op_ctx`, KVSFS private handle types from `kvsfs_fsal_internal.h`, KVSNS calls (`kvsns_open`, `kvsns_read`, `kvsns_write`, `kvsns_close`), and POSIX-to-NFS error translation.

Risks: Stateid validation is not performed locally; the stateid parameters are unused. EOF is set only when `amount_read == 0`, so short reads before EOF may not indicate EOF. Stability and commit semantics are weak: `kvsfs_ds_write` returns whatever stability was requested without explicit fsync, and `kvsfs_ds_commit` is a no-op. Close errors override successful read/write, while close errors after a failed read/write are ignored. Test signals should include DS handle length validation, read/write with caller credential changes, negative KVSNS error mapping, short read/EOF behavior, FILE_SYNC4/commit durability expectations, and export access checks.

## sources/user-network-fs/nfs-ganesha/src/FSAL/FSAL_KVSFS/kvsfs_export.c

Purpose: This file implements KVSFS FSAL export creation, export operation initialization, filehandle digest validation, state allocation/freeing, supported-attribute filtering, pNFS export configuration, and optional DS/MDS enablement during export setup.

Important functions and data: `kvsfs_export_release` detaches the export and frees ops/private export storage. `get_dynamic_info` currently returns success without filling dynamic filesystem info. `kvsfs_wire_to_host` validates non-null handle buffers and exact `struct kvsfs_file_handle` size. `kvsfs_supported_attrs` returns FSAL-supported attributes minus `ATTR_ACL`. `kvsfs_free_state` destroys the embedded `fsal_fd` and frees the state. `kvsfs_alloc_state` allocates `struct kvsfs_state_fd`, initializes generic state, and initializes a KVSFS fd for stateful opens. `get_fsal_obj_hdl` maps an FSAL fd back to its containing KVSFS object handle. `kvsfs_export_ops_init` installs release, lookup, handle creation, dynamic info, supported attrs, state allocation, and fd-to-object callbacks. The config blocks define `kvsns_config` and PNFS settings including stripe unit, enable flag, DS count, and up to four DS addresses/ports. `kvsfs_create_export` parses config, starts KVSNS, attaches the export, sets `op_ctx->fsal_export`, computes pNFS DS/MDS enablement, creates/registers a pNFS DS if needed, and enables MDS export ops if needed.

Control flow and state: Export creation allocates the private export first, initializes ops, parses config into the object, starts the global KVSNS API with the configured file, and attaches the export to the FSAL. pNFS DS insertion uses the current export ID as the DS server ID and links the DS back to `op_ctx->ctx_export`. Error paths detach an attached export and free the allocation, but KVSNS shutdown is not visible here. Runtime state allocation is per open/share state and anchored to `op_ctx->fsal_export`.

Persistence behavior: The file starts the KVSNS API using a persistent config path, but it does not itself persist namespace data. Export objects and state objects are in-memory. pNFS DS registration mutates process-global pNFS DS tables.

Dependencies and integration points: It depends on Ganesha FSAL core, config parsing, pNFS utilities, `kvsfs_methods.h`, KVSNS startup, export lists, `op_ctx`, `pnfs_ds_insert`, and module ops that create FSAL pNFS DS instances. The supported-attribute function intentionally disables ACLs despite the broader FSAL framework having ACL concepts.

Risks: `get_dynamic_info` returns success without filling `infop`, which can mislead callers expecting dynamic space or filesystem state. On KVSNS startup success followed by later export creation failure, this file frees the export but does not show corresponding KVSNS stop/cleanup. `fsal_error` remains initialized to `ERR_FSAL_INVAL`, so some errors lose specificity. `op_ctx->fsal_export` mutation during creation can be sensitive in concurrent config paths. pNFS server ID is special-cased to the export ID, so duplicate IDs cause insertion failure. Test signals include config parse defaults, invalid KVSNS config handling, pNFS enable/disable matrix, duplicate DS server ID, handle size mismatch, state allocation/free leak checks, and dynamic-info caller behavior.

## sources/user-network-fs/nfs-ganesha/src/FSAL/FSAL_KVSFS/kvsfs_file.c

Purpose: This file implements KVSFS regular-file open, reopen, close, read, write, and commit operations for the FSAL object operation vector. It adapts Ganesha's state/share/FD machinery to KVSNS file handles and direct KVSNS read/write calls.

Important functions: `kvsfs_open_by_handle` selects either a state fd or the object's global fd, starts exclusive fd work, optionally checks share conflicts under `obj_lock`, skips no-op reopens, calls `kvsfs_reopen_func`, manages fd LRU insertion/bumping, optionally refreshes attributes after create/truncate, updates share counters, and completes fd work. `kvsfs_open_by_name` performs lookup because KVSFS lacks open-by-name, rejects non-regular objects, then opens by handle. `kvsfs_reopen_func` converts FSAL open flags to POSIX flags, opens the KVSNS inode with caller credentials, closes any previous KVSNS fd, stores the new fd, and records NFS open flags. `kvsfs_close_func` closes and clears a KVSNS fd. `kvsfs_open2` handles no-create, guarded/exclusive/unchecked create, verifier setup, mode/umask calculation, KVSNS create via `kvsfs_create2`, object handle allocation, post-create setattr/getattr, final open, and cleanup/unlink on failures. `kvsfs_status2`, `kvsfs_reopen2`, `kvsfs_commit2`, and `kvsfs_close2` expose status/reopen/no-op commit/state close to FSAL. `kvsfs_read2` and `kvsfs_write2` acquire usable fds through `fsal_start_io`, iterate over iovecs with `kvsns_read`/`kvsns_write`, complete I/O, update stateless share counters, and invoke async callbacks.

Control flow and state: The file heavily relies on FSAL fd state. Stateful opens use `struct kvsfs_state_fd`; stateless I/O may use a temporary fd. The only path taking both fd work mutex and object lock is documented in `kvsfs_open_by_handle` to avoid ABBA deadlock. Share counters are updated only after successful open/reopen and during state close or stateless I/O cleanup. Create flow distinguishes whether this process definitely created the file through `O_EXCL`; only then are extra attributes set and cleanup unlink attempted on later failure.

Persistence behavior: Persistent namespace and file content changes occur through `kvsfs_create2`, `kvsns_open`, `kvsns_close`, `kvsns_getattr`, `kvsns_setattr` through object ops, `kvsns_unlink` cleanup, `kvsns_read`, and `kvsns_write`. `kvsfs_commit2` does not force durability and returns success. File truncation is represented through FSAL open flags passed to KVSNS open. The file does not cache data itself, only KVSNS open handles and FSAL open flags.

Dependencies and integration points: It depends on `op_ctx` credentials and export, FSAL common fd/share helpers (`fsal_start_fd_work_no_reclaim`, `fsal_start_io`, fd LRU, share conflict/counter helpers), POSIX conversion helpers, KVSFS handle allocation and create functions, KVSNS file APIs, object ops for lookup/setattr/getattrs/release, and async completion callbacks.

Risks: `old_openflags` is only assigned inside the `state != NULL` branch but is used in no-op and LRU logic for stateless/global opens, which is a potential uninitialized-read bug unless hidden by compiler/control assumptions. `kvsfs_close_func` casts `struct fsal_fd *` directly to `struct kvsfs_fd *`; because `fsal_fd` is the first member of `struct kvsfs_fd`, this works only while layout stays that way. Read/write callbacks may report success even if `fsal_complete_io` fails because `status2` is logged but not propagated. EOF is true only when total bytes read is zero. Commit is a no-op. In `kvsfs_open2`, the `fileerr` label releases `hdl` and unlinks if `created` even after a successful open path, because control falls through to `fileerr` rather than returning immediately after `kvsfs_open_by_handle`; this should be reviewed as it appears capable of releasing/unlinking a successfully opened created file. Test signals should target open/create modes, share conflicts, stateless vs stateful opens, truncate attribute refresh, successful exclusive create lifetime, cleanup-on-error behavior, read/write iovec partial failures, `fsal_complete_io` failure injection, and commit durability expectations.

## sources/user-network-fs/nfs-ganesha/src/FSAL/FSAL_KVSFS/kvsfs_fsal_internal.c

Purpose: This small translation unit owns the definition of KVSFS module-global filesystem information declared in the internal header. It exists to provide one storage location for `global_fs_info`.

Important APIs and types: The only exported object defined here is `struct fsal_staticfsinfo_t global_fs_info;`. The `FSAL_INTERNAL_C` macro is defined before including `kvsfs_fsal_internal.h` so the header suppresses its `extern` declarations guarded by `#ifndef FSAL_INTERNAL_C`.

Control flow and state: There is no executable control flow. State consists of the mutable global `global_fs_info`, with comments saying access is thread-safe because it is read-only except during initialization.

Persistence behavior: No persistent storage is touched. The object is process-global runtime state that should be initialized once and then treated as read-only by KVSFS code.

Dependencies and integration points: It includes `config.h`, `fsal.h`, `kvsfs_fsal_internal.h`, `abstract_mem.h`, and `pthread.h`. Other KVSFS files include the internal header and reference `global_fs_info` as an external symbol. The broader module initialization path likely copies or derives FSAL static capabilities from this object.

Risks: Because `global_fs_info` is writable C global storage, the claimed thread safety depends on discipline outside this file. If initialization and access overlap, there is no lock here. Test signals are mostly link/build checks ensuring exactly one definition exists, plus module initialization tests verifying the global is fully populated before exports or object ops read it.

## sources/user-network-fs/nfs-ganesha/src/FSAL/FSAL_KVSFS/kvsfs_fsal_internal.h

Purpose: This is the private KVSFS FSAL header shared by KVSFS implementation files. It declares operation-vector initializers, the KVSFS wire filehandle, the pNFS DS private handle, default KVSNS config path, supported attribute mask, handle sizing helper, global FS info, and pNFS helper prototypes.

Important APIs and types: `kvsfs_export_ops_init` and `kvsfs_handle_ops_init` are the main operation table initializers. `typedef struct kvsfs_file_handle` wraps `kvsns_ino_t kvsfs_handle`, making the wire handle effectively a KVSNS inode identifier. `struct kvsfs_ds` embeds public `struct fsal_ds_handle`, a wire handle, a `struct kvsfs_filesystem *`, and a `connected` flag. `KVSNS_DEFAULT_CONFIG` points to `/etc/kvsns.d/kvsns.ini`. `KVSFS_SUPPORTED_ATTRIBUTES` includes type, size, fsid, fileid, mode, link count, owner, group, atime, rawdev, ctime, mtime, space used, and change. `kvsfs_sizeof_handle` returns the fixed wire handle size. The non-`FSAL_INTERNAL_C` section declares `global_fs_info`, pNFS MDS helpers (`kvsfs_getdeviceinfo`, `kvsfs_fs_da_addr_size`, `export_ops_pnfs`, `handle_ops_pnfs`) and DS ops initializer `kvsfs_pnfs_ds_ops_init`.

Control flow and state: The only inline control is fixed-size handle sizing. The header defines the object shapes used for DS lifetime and wire-handle validation. The `FSAL_INTERNAL_C` guard separates the defining translation unit from external consumers.

Persistence behavior: The header does not persist data, but it defines the serialized handle contract. A KVSFS NFS filehandle contains a KVSNS inode value, so any persistence or stability guarantee depends on KVSNS inode stability across server restarts and namespace mutations. The default config path controls how exports locate the backing KVSNS service if not overridden.

Dependencies and integration points: It depends on Ganesha `fsal.h` and `<kvsns/kvsns.h>`. All KVSFS C files rely on these definitions to convert between Ganesha FSAL handles and KVSNS objects. pNFS-related prototypes connect export and object operation vectors with KVSFS MDS and DS files.

Risks: The handle format has no version, length field, fsid, checksum, or generation number in this header; `kvsfs_wire_to_host` only checks size. Stale inode reuse in KVSNS could therefore be a serious correctness/security concern unless prevented elsewhere. `struct kvsfs_ds` references `struct kvsfs_filesystem *`, but this subset does not show where it is defined or used. Test signals should include handle encode/decode stability, stale handle behavior after delete/recreate, default config override, supported attribute claims versus actual object ops, and pNFS helper linkage.
