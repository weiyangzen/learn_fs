# sources/distributed-fs/ceph-client/drivers/net/ethernet/chelsio/cxgb4/t4fw_api.h

Purpose: this header is the packed firmware ABI for Chelsio T4/T5/T6 adapters. It defines firmware return codes, work request opcodes and layouts, mailbox command opcodes and layouts, firmware parameter mnemonics, PF/VF resource discovery structures, VI/MAC/RSS/queue/port/statistics commands, firmware image headers, devlog records, and newer offload work requests. It is not executable code; its value is that all PF, VF, RDMA, crypto, iSCSI, FCoE, and Ethernet datapath code can construct and decode firmware messages with one shared layout.

Important APIs, types, and macros: `enum fw_retval` mirrors errno-style firmware completion values. `enum fw_wr_opcodes`, `struct fw_wr_hdr`, `struct fw_eth_tx_pkt_wr`, `struct fw_eth_tx_pkt_vm_wr`, `struct fw_ofld_connection_wr`, `struct fw_flowc_wr`, `struct fw_ofld_tx_data_wr`, `struct fw_crypto_lookaside_wr`, and `struct fw_tlstx_data_wr` describe egress work requests placed on SGE queues. `enum fw_cmd_opcodes` and `struct fw_cmd_hdr` provide the generic command header used by mailbox commands such as `fw_ldst_cmd`, `fw_reset_cmd`, `fw_hello_cmd`, `fw_caps_config_cmd`, `fw_params_cmd`, `fw_pfvf_cmd`, `fw_iq_cmd`, `fw_eq_eth_cmd`, `fw_eq_ctrl_cmd`, `fw_vi_cmd`, `fw_vi_mac_cmd`, `fw_vi_rxmode_cmd`, `fw_vi_enable_cmd`, `fw_vi_stats_cmd`, `fw_port_cmd`, `fw_port_stats_cmd`, `fw_rss_ind_tbl_cmd`, `fw_rss_glb_config_cmd`, `fw_rss_vi_config_cmd`, `fw_sched_cmd`, `fw_clip_cmd`, `fw_debug_cmd`, and `fw_hma_cmd`.

The core programming model is field packing. Every command has `*_S`, `*_M`, `*_V()`, and often `*_G()` macros for shift, mask, value construction, and extraction. Call sites must combine these macros with `cpu_to_be32()`, `be32_to_cpu()`, `cpu_to_be64()`, and related endian helpers because the structures use `__be16`, `__be32`, and `__be64` for firmware-visible fields. `FW_CMD_OP_V()`, `FW_CMD_REQUEST_F`, `FW_CMD_READ_F`, `FW_CMD_WRITE_F`, `FW_CMD_EXEC_F`, `FW_CMD_RETVAL_G()`, and `FW_LEN16()` are the command-level helpers used across mailbox transactions. `FW_WR_OP_V()`, `FW_WR_LEN16_V()`, `FW_WR_FLOWID_V()`, and the egress queue flags are the comparable helpers for queue work requests.

The header is especially relevant to the VF driver in the sibling `cxgb4vf` directory. `FW_PARAMS_MNEM_*`, `FW_PARAMS_PARAM_PFVF_*`, and `struct fw_pfvf_cmd` define the VF resource report consumed during VF initialization. `struct fw_iq_cmd`, `struct fw_eq_eth_cmd`, and `struct fw_eq_ctrl_cmd` define ingress and egress queue allocation/free/modify commands used by `sge.c`. `struct fw_vi_cmd`, `struct fw_vi_mac_cmd`, `struct fw_vi_rxmode_cmd`, `struct fw_vi_enable_cmd`, and `struct fw_vi_stats_cmd` define virtual-interface allocation, MAC filter programming, receive mode, enable/disable, and statistics operations used by `t4vf_hw.c` and `cxgb4vf_main.c`. `struct fw_rss_ind_tbl_cmd`, `struct fw_rss_glb_config_cmd`, and `struct fw_rss_vi_config_cmd` define RSS setup, including the basic-virtual mode required by the VF driver.

Control flow: there is no runtime flow in this file, but the protocol flow it encodes is central. A driver builds a packed structure, sets command opcode and flags, sends it through a mailbox or SGE work request, then decodes firmware status and response fields using the matching `*_G()` macros. For VF bring-up, the expected sequence is reset/hello-like firmware contact in lower layers, parameter discovery through `FW_PARAMS_CMD` and `FW_PFVF_CMD`, queue allocation through IQ/EQ commands, VI allocation through `FW_VI_CMD`, RSS programming through RSS commands, and link/port information through `FW_PORT_CMD`.

State and persistence: the header itself stores no state. It defines externally persistent hardware/firmware state: queue contexts, virtual interfaces, MAC filters, RSS tables, port link configuration, firmware device logs, hardware capability bitmaps, and firmware image version fields. Some commands are state creating or destroying (`ALLOC`, `FREE`, `ENABLE`, `RESET`, `INITIALIZE` flags); others are state observation (`READ`, statistics commands, devlog command). Because these are ABI structures, changing layout, size, alignment, or constants has persistent compatibility impact with adapter firmware.

Dependencies and integration points: the file depends on Linux fixed-width and endian integer types supplied by its includers, Ethernet constants such as `ETH_ALEN`, and helper conventions from Chelsio common headers. It integrates with Chelsio PF Ethernet (`cxgb4`), VF Ethernet (`cxgb4vf`), RDMA (`iw_cxgb4`), crypto (`chcr`), and offload consumers that share the same firmware. It also couples to firmware versioning and image parsing through `struct fw_hdr`, `FW_HDR_FW_VER_*` macros, and devlog structures.

Risks: this is an ABI header, so off-by-one field widths, wrong shift constants, endian mistakes at call sites, or structure padding assumptions can corrupt firmware commands. The layout mixes legacy and newer commands, so stale call sites may use 16-bit port capabilities when 32-bit capabilities are needed. Several macros expose raw values without range checking; callers must validate queue counts, VI IDs, RSS sizes, and capability masks before packing. Firmware feature probing is also critical: newer commands such as `FILTER2`, encapsulated `CPL_FW4_MSG`, HMA, TLS, and crypto lookaside must only be used when firmware advertises support.

Test signals: compile coverage across `cxgb4`, `cxgb4vf`, RDMA, crypto, and storage offload users catches type and layout drift. Runtime signals include successful mailbox command completion, correct `FW_CMD_RETVAL_G()` decoding, VI allocation and MAC filter setup, queue allocation and teardown, RSS table programming, ethtool statistics matching firmware counters, and firmware devlog readability. Good negative tests include forcing old firmware feature sets, mailbox errors such as `FW_EINVAL` or `FW_ENOSPC`, queue allocation failures, and mismatched capability masks.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/chelsio/cxgb4/t4fw_version.h

Purpose: this small header records the driver-side firmware version policy for Chelsio T4, T5, and T6 adapters. It defines the expected firmware version tuple for each chip generation and the minimum acceptable firmware version tuple used by firmware compatibility checks elsewhere in the Chelsio driver stack.

Important macros: `T4FW_VERSION_MAJOR`, `T4FW_VERSION_MINOR`, `T4FW_VERSION_MICRO`, and `T4FW_VERSION_BUILD` define the packaged or expected T4 firmware version as `1.23.3.0` in hex-coded components. `T4FW_MIN_VERSION_MAJOR`, `T4FW_MIN_VERSION_MINOR`, and `T4FW_MIN_VERSION_MICRO` set T4's minimum acceptable firmware to `1.4.0`. Equivalent T5 and T6 expected versions are also `1.23.3.0`, while their minimum version macros are `0.0.0`, meaning this header does not impose a stricter minimum for those generations in this tree.

Control flow: the file has no runtime control flow. It is included by Chelsio code that formats firmware versions, compares adapter firmware against expected or minimum tuples, and decides whether to warn, reject, or continue with firmware-dependent behavior. Combined with `t4fw_api.h`'s `struct fw_hdr` and `FW_HDR_FW_VER_*` macros, it allows code to compare firmware image headers and live adapter firmware revisions.

State and persistence: this header stores compile-time policy only. The values become persistent in built kernel modules and affect adapter initialization behavior until the module or kernel is replaced. Runtime firmware revision state lives in adapter parameter structures populated from firmware queries, not in this header.

Dependencies and integration points: the file has only include guards and constants, but it is coupled to the Chelsio firmware ABI and firmware files distributed with the kernel or vendor packages. PF and VF paths can surface these values through probe logs, ethtool driver information, or compatibility checks.

Risks: stale constants can cause misleading warnings or failed compatibility checks against real adapter firmware. A too-low minimum version may let code use firmware commands not implemented by older firmware, while a too-high minimum can reject otherwise usable devices. Because the constants are per chip generation, copying a T4 policy to T5/T6 without validating feature availability would be risky.

Test signals: build inclusion should be warning-free. Runtime validation is visible in adapter probe logs, firmware compatibility warnings, and `ethtool -i` output that reports live firmware and TP microcode versions. Compatibility tests should cover T4 minimum-version rejection, current-version acceptance, and T5/T6 behavior when firmware reports older but functional versions.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/chelsio/cxgb4vf/Makefile

Purpose: this Makefile wires the Chelsio T4/T5/T6 SR-IOV Virtual Function Ethernet driver into the kernel build. When `CONFIG_CHELSIO_T4VF` is enabled, it builds one module or built-in object named `cxgb4vf` from the VF driver's main, hardware, and SGE implementation files.

Important build variables: `obj-$(CONFIG_CHELSIO_T4VF) += cxgb4vf.o` ties the aggregate driver object to Kconfig. `cxgb4vf-objs := cxgb4vf_main.o t4vf_hw.o sge.o` defines the linked components: PCI/netdev/debugfs/ethtool logic in `cxgb4vf_main.o`, firmware and hardware mailbox helpers in `t4vf_hw.o`, and queue/datapath logic in `sge.o`.

Control flow and integration: there is no runtime flow in the Makefile. Build flow is symbol driven: enabling the Kconfig symbol compiles the three objects and links them into a single driver. The resulting driver registers a PCI driver whose device IDs are included from the PF driver's PCI ID table and whose module metadata is defined in `cxgb4vf_main.c`.

State and persistence: persistent state is build output and module metadata generated from the selected configuration. There is no runtime state in this file. The aggregate object boundary matters because symbols can remain file-local where appropriate while still linking into one driver module.

Dependencies and integration points: this file depends on the surrounding kernel build system and the `CONFIG_CHELSIO_T4VF` Kconfig symbol. The objects it links depend on shared Chelsio headers from `../cxgb4/`, Linux PCI, netdevice, ethtool, debugfs, DMA mapping, and firmware mailbox infrastructure.

Risks: omitting one object breaks link-time symbol resolution or removes major functionality. For example, dropping `sge.o` would leave transmit/receive queue functions unresolved, while dropping `t4vf_hw.o` would remove firmware command helpers needed by probe and configuration. A mismatch between Kconfig and Makefile names would silently prevent the driver from building in expected configurations.

Test signals: `make M=drivers/net/ethernet/chelsio/cxgb4vf`, `allmodconfig`, and `CONFIG_CHELSIO_T4VF=m/y` builds should produce a single `cxgb4vf` module or built-in object. `modinfo cxgb4vf` should show metadata and PCI aliases from `cxgb4vf_main.c` and the included Chelsio PCI ID table.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/chelsio/cxgb4vf/adapter.h

Purpose: this header defines the VF driver's central in-memory model and the OS callback surface required by the shared Chelsio VF common code. It describes adapter-wide resources, per-virtual-interface port state, SGE ingress/egress rings, queue reverse maps, interrupt layout, debug/mailbox state, and register access helpers.

Important types: `struct port_info` represents one VF-visible virtual interface, including `adapter`, VLAN ID, VIID, MAC filter index, RSS slice size, physical `port_id`, queue-set allocation, module and port type, MDIO address, and `struct link_config`. The driver currently caps itself at `MAX_NPORTS == 1`, but the structures preserve PF-style multi-port naming.

`struct sge_fl`, `struct sge_rspq`, `struct sge_eth_rxq`, `struct sge_txq`, and `struct sge_eth_txq` hold the queue state used by `sge.c` and `cxgb4vf_main.c`. Free lists track available buffers, producer/consumer indices, allocation failures, descriptor memory, DMA addresses, BAR2 doorbell mapping, and queue IDs. Response queues track NAPI, descriptor position, generation bit, interrupt coalescing parameters, queue IDs, netdev association, and a `rspq_handler_t`. Ethernet RX queues combine a response queue, free list, and per-queue receive statistics. TX queues track ring occupancy, producer/consumer indices, queue stop/restart counters, hardware and software descriptors, DMA mapping, status page, and BAR2 metadata.

`struct sge` groups all queue resources: Ethernet TX/RX queue arrays, firmware event queue, optional forwarded interrupt queue for MSI mode, timers for starving free-list refill and TX cleanup, active queue counts, SGE timer/counter settings, decoded SGE placement parameters, and reverse maps from absolute queue IDs to software queues. `EQ_IDX()`, `IQ_IDX()`, `EQ_MAP()`, and `IQ_MAP()` are important helpers for converting firmware absolute queue IDs into compact driver arrays.

`struct adapter` is the top-level VF object attached to `struct pci_dev`. It stores MMIO mappings (`regs`, `bar2`), PCI device pointers, registered/open netdev bitmaps, adapter flags, firmware-discovered `adapter_params`, MSI-X vector labels, SGE state, port netdev pointers, message level, debugfs root, stats and mailbox locks, mailbox command log, mailbox wait list, and hash-MAC fallback list.

Control flow: the header has only inline helpers and declarations, but it constrains runtime flow throughout the driver. Probe allocates and initializes `struct adapter`, creates `struct net_device` instances whose private data are `struct port_info`, fills `adapter->params` through `t4vf_hw.c`, configures queue counts, and later `setup_sge_queues()` populates the SGE queue arrays. Interrupt handlers and firmware event handlers use the reverse maps to locate queues from firmware-provided queue IDs. Netdev callbacks use `netdev2pinfo()`, `netdev2adap()`, and `adap2pinfo()` to move between Linux and Chelsio state.

State and persistence: all fields are runtime state. Hardware state persists in adapter firmware and SGE contexts, while this header stores the driver's mirrored view: queue indices, DMA ring addresses, NAPI state, MAC hash list, and flags such as `CXGB4VF_FULL_INIT_DONE`, `CXGB4VF_USING_MSI`, `CXGB4VF_USING_MSIX`, `CXGB4VF_QUEUES_BOUND`, `CXGB4VF_ROOT_NO_RELAXED_ORDERING`, and `CXGB4VF_FW_OK`. The `FULL_INIT_DONE` flag is a configuration boundary: ring sizes and queue layout are intended to be changed only before initial queue allocation.

Dependencies and integration points: this header includes Linux networking, PCI, interrupt, spinlock, skbuff, and Ethernet headers plus `../cxgb4/t4_hw.h`. It declares OS callbacks `t4vf_os_link_changed()` and `t4vf_os_portmod_changed()` that common hardware code calls when firmware reports link or module changes. It declares SGE functions implemented in `sge.c` and used by the main driver, including queue allocation, resource cleanup, transmit, receive handling, interrupt selection, SGE initialization, start, and stop.

Risks: queue ID reverse maps assume firmware allocates compact relative queue IDs under a consistent absolute base; if base calculation is wrong, egress updates can wake the wrong queue or read outside map bounds. Many fields are updated in interrupt, NAPI, timer, and netdev contexts, so locking and ordering are important. The fallback `readq`/`writeq` definitions perform two 32-bit accesses and are only safe for registers where that ordering is acceptable. The single-port cap simplifies logic but can hide provisioning mismatches if firmware grants more VIs than the driver uses.

Test signals: successful probe should populate `adapter`, `port_info`, and SGE defaults before netdev registration. Opening a VF should allocate queues and fill reverse maps, and debugfs `sge_qinfo` should show coherent queue IDs, sizes, indices, and netdev names. Interrupt-mode tests should cover MSI-X and MSI forwarded-interrupt paths. Stress tests should watch free-list starvation counters, TX queue stop/restart counters, NAPI disable on close, and cleanup with no DMA leaks.

# sources/distributed-fs/ceph-client/drivers/net/ethernet/chelsio/cxgb4vf/cxgb4vf_main.c

Purpose: this is the main Linux PCI/netdevice driver for Chelsio T4/T5/T6 SR-IOV Virtual Functions. It owns module parameters, PCI probe/remove/shutdown, adapter initialization, netdev operations, ethtool operations, debugfs files, interrupt mode selection, queue-set sizing, firmware-event handling, and high-level open/close control. Hardware mailbox details and datapath ring operations are delegated to `t4vf_hw.c` and `sge.c`.

Important entry points: `cxgb4vf_module_init()` validates the `msi` module parameter, creates the top-level debugfs directory, and registers `cxgb4vf_driver`. `cxgb4vf_pci_probe()` enables the PCI device, claims regions, sets 64-bit DMA, maps BAR0 and optionally BAR2, prepares the adapter, initializes firmware-facing state with `adap_init0()`, allocates netdevs and VIs, selects MSI-X or MSI, configures queues, registers netdevs, and creates per-device debugfs files. `cxgb4vf_pci_remove()` and `cxgb4vf_pci_shutdown()` unregister netdevs, stop SGE activity, disable interrupts, free queues and VIs, unmap BARs, free mailbox and MAC-hash state, and release PCI resources.

Runtime netdev operations are collected in `cxgb4vf_netdev_ops`. `cxgb4vf_open()` refuses to run without `CXGB4VF_FW_OK`, calls `adapter_up()` for the first open interface, refreshes port information, starts the link/VI path through `link_start()`, records the VF VLAN ACL, and starts TX queues. `cxgb4vf_stop()` stops TX queues, drops carrier, disables the VI with `t4vf_enable_pi()`, clears the open bitmap, and calls `adapter_down()` for the last close. `t4vf_eth_xmit()` and `t4vf_ethrx_handler()` are supplied by `sge.c`.

Initialization control flow: `adap_init0()` performs a firmware reset to compensate for unreliable or absent PCIe FLR behavior, retrieves device/VPD/SGE/RSS/VF-resource parameters, requires RSS global mode `FW_RSS_GLB_CONFIG_CMD_MODE_BASICVIRTUAL`, initializes SGE software parameters, optionally tells newer firmware it can handle encapsulated `CPL_FW4_MSG`, decodes interrupt timer and packet-counter arrays, validates VF port and VI provisioning, calls `size_nports_qsets()`, and sets `CXGB4VF_FW_OK`. Probe then creates netdevs for the allowed port mask, allocates a VI with `t4vf_alloc_vi()`, initializes per-port state with `t4vf_port_init()`, optionally applies an assigned MAC ACL, enables interrupts, calls `cfg_queues()`, and registers the netdevs.

Adapter-up control flow: the first open calls `adapter_up()`. If full initialization has not happened, it calls `setup_sge_queues()` to allocate the optional MSI forwarded interrupt queue, firmware event queue, per-queue RX response/free-list queues, and TX queues, then builds absolute-to-relative queue reverse maps. It calls `setup_rss()` to map each VI RSS table slice to the active RX queue absolute IDs and, in basic-virtual mode without tunnel-all lookup, writes a default ingress queue. It names MSI-X vectors and sets `CXGB4VF_FULL_INIT_DONE`. Each open then requests IRQs, enables NAPI and response-queue interrupt arming via `enable_rx()`, and starts SGE timers through `t4vf_sge_start()`.

Firmware event and interrupt behavior: `fwevtq_handler()` handles firmware event queue CPLs. `CPL_FW6_MSG` with command replies is passed to `t4vf_handle_fw_rpl()`. `CPL_FW4_MSG` can encapsulate `CPL_SGE_EGR_UPDATE`, which is decoded and falls through to the egress-update path. `CPL_SGE_EGR_UPDATE` validates the absolute egress queue ID, maps it to an Ethernet TX queue, increments restart statistics, and wakes the netdev TX queue. Unexpected CPLs, out-of-range queue IDs, null maps, and mismatched queue IDs are logged. MSI-X uses one vector for firmware events and one per Ethernet RX queue; MSI uses a forwarded interrupt queue armed separately.

MAC, RX mode, VLAN, and MTU behavior: `link_start()` programs receive mode with VLAN extraction enabled, installs the primary MAC filter through `cxgb4vf_change_mac()`, and enables the VI. MAC filter allocation first tries exact TCAM through `t4vf_change_mac()` or `t4vf_alloc_mac_filt()`; if firmware reports no exact entries, the driver maintains `adapter->mac_hlist`, computes a 64-bit hash vector in `cxgb4vf_set_addr_hash()`, and programs hash filtering through `t4vf_set_addr_hash()`. `set_rxmode()` synchronizes unicast and multicast lists and sets promiscuous/all-multicast/broadcast/VLAN extraction flags. `cxgb4vf_change_mtu()` sends the new MTU to firmware before updating `dev->mtu`. `cxgb4vf_fix_features()` keeps VLAN TX and RX acceleration coupled because firmware exposes a combined setting, and `cxgb4vf_set_features()` updates firmware receive mode when VLAN RX state changes.

Ethtool and diagnostics: link settings translate firmware port/module/capability values into ethtool link modes through `from_fw_port_mod_type()` and `fw_caps_to_lmm()`. FEC support is exposed through `cxgb4vf_get_fecparam()`. Driver info reports live firmware and TP microcode versions from `adapter->params.dev`. Ring sizing, coalescing, pause parameters, LED identify, standard stats, private statistics, and register dumps are supported. Ring sizes can be changed only before `CXGB4VF_FULL_INIT_DONE`; coalescing can update live queue context through `t4vf_set_params()` if the response queue already exists. Register dumps avoid reading the mailbox-control register because that can trigger ownership arbitration.

Debugfs behavior: per-adapter debugfs exposes `mboxlog`, `sge_qinfo`, `sge_qstats`, `resources`, and `interfaces`. `mboxlog` dumps the circular mailbox command log without locking, knowingly allowing partially updated entries. Queue info and stats group Ethernet queue sets four per display entry and also show firmware event and MSI interrupt queues. Resource output reflects the firmware-provisioned VF limits (`nvi`, `neq`, `nethctrl`, `niqflint`, `niq`, `tc`, `pmask`, `nexactf`, `r_caps`, `wx_caps`).

State and persistence: major runtime state lives in `struct adapter`, `struct port_info`, and `struct sge`. Persistent hardware state includes allocated VIs, MAC filters or hash vector, queue contexts, RSS table entries, enabled/disabled VI state, and firmware reset side effects. Driver state is bounded by bitmaps (`registered_device_map`, `open_device_map`), flags (`FW_OK`, interrupt mode, full init), debugfs dentries, NAPI state, IRQ registrations, DMA ring allocations, and mailbox logs. Queue parameters and ring sizes persist only until the driver is unloaded or queues are freed, but after full initialization they cannot be changed through ethtool ringparam.

Dependencies and integration points: this file depends on Linux PCI, DMA mapping, netdevice, ethtool, MDIO, debugfs, seq_file, NAPI, MSI/MSI-X, and Chelsio common headers. It calls hardware and firmware helpers from `t4vf_common.h`/`t4vf_hw.c` for reset, parameter discovery, VI allocation, port init/update, MAC filters, RSS, stats, RX mode, identify, mailbox reply handling, and VF ACL queries. It calls SGE helpers from `sge.c` for queue allocation, queue cleanup, transmit, receive, interrupt selection, and timers.

Risks: firmware initialization failures are logged but probe may continue in debug mode, so netdev paths must keep checking `CXGB4VF_FW_OK`. The module-global `msi` variable is modified to `MSI_MSI` on MSI-X fallback, which can affect later devices in the same module instance. Queue reverse-map assumptions are security and stability sensitive because firmware event queue messages drive TX queue wakeups. Hash MAC fallback must keep `mac_hlist` synchronized or multicast/unicast filtering can become stale. Debugfs mailbox log reads are intentionally unlocked. Register dumps avoid one mailbox register but still read many VF-visible registers, so hardware access errors can surface there. Error unwinding must free VIs, netdevs, BAR mappings, interrupts, debugfs nodes, SGE resources, mailbox log memory, and hash list entries in the right order.

Test signals: build with `CONFIG_CHELSIO_T4VF=m/y`, load with `msi=2` and `msi=1`, and probe on T4 and T5/T6 hardware or VF-capable emulation. Probe logs should show firmware resource discovery, interrupt mode, and registered netdevs. Functional tests should cover open/close cycles, link changes, assigned MAC ACL handling, exact MAC exhaustion with hash fallback, multicast list sync, MTU changes, VLAN feature toggles, RSS distribution across queue sets, ethtool stats/register/ring/coalesce output, debugfs file reads, suspend/shutdown/remove, and forced failures in firmware commands, IRQ allocation, netdev registration, and queue allocation. Runtime counters to watch include TX queue stops/restarts, RX checksum/VLAN/GRO counters, free-list allocation failures, and firmware mailbox log entries.
