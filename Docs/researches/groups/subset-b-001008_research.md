# sources/distributed-fs/ceph-client/drivers/accel/rocket/rocket_registers.h Research

## Purpose
`rocket_registers.h` is an autogenerated hardware register ABI header for the Rocket accelerator driver. It was generated from Mesa `registers.xml` by `gen_header.py` and exposes MMIO register offsets, bit masks, shifts, and static inline value packers for programming accelerator blocks. The file contains no runtime logic, allocation, or persistence; its value is the exactness of the register map consumed by driver code that writes and reads the device.

## APIs, Types, And Register Families
The exported API is preprocessor symbols plus `static inline uint32_t FIELD(uint32_t val)` helpers. Each helper left-shifts a caller-supplied field value and masks it into the register bit range. Important register families are:

- `REG_PC_*` at `0x00000000`: version, operation enable, base address, interrupt mask/clear/status/raw status, task control, DMA base, and task status.
- `REG_CNA_*` at `0x00001000`: convolution/neural-array status, pointer, operation enable, convolution modes, tensor sizes, weight sizes, CBUF banking, conversion parameters, padding, DMA settings, data decompression amounts, and clock gates.
- `REG_CORE_*` at `0x00003000`: core status, pointer, operation enable, MAC gating, miscellaneous config, output size, and clipping/truncation.
- `REG_DPU_*` at `0x00004000`: data-processing output configuration, bias/batchnorm/elementwise controls, output conversion, LUT programming, and surface addressing.
- `REG_DPU_RDMA_RDMA_*` at `0x00005000`: DPU read DMA status, dimensions, base addresses, source feature modes, DMA config, surface notch, padding, and weights.
- `REG_PPU_*` at `0x00006000` and `REG_PPU_RDMA_RDMA_*` at `0x00007000`: pooling/post-processing dimensions, modes, kernel/padding config, destination format, read DMA source strides, and data format.
- `REG_DDMA_*` and `REG_SDMA_*` at `0x00008000` and `0x00009000`: data/system DMA outstanding limits, read/write weights, ID errors, FIFO clear, arbitration, QoS, AXI read/write config, write strobes, and idle status.
- `REG_GLOBAL_OPERATION_ENABLE` at `0x0000f008`: global enable bits for CNA, core, DPU, DPU RDMA, PPU, and PPU RDMA.

## Control Flow
There is no executable control flow beyond inline field packing. Driver control flow will typically compose a 32-bit register value with one or more helpers, write it to an offset with the kernel MMIO accessor used by the Rocket driver, poll status registers such as `*_S_STATUS` or `*_CFG_STATUS`, and clear or mask interrupts using the PC interrupt registers.

## State And Persistence
The header itself has no state. It defines hardware state addresses. The persistent contract is source compatibility: register names, offsets, masks, and shifts must match the accelerator RTL and firmware expectations. Regeneration from a changed XML source can silently alter the kernel driver's hardware behavior.

## Dependencies And Integration Points
The helpers require `uint32_t` to be visible before inclusion; this is normally supplied by the including kernel source. Integration is with the Rocket accelerator driver, Linux MMIO helpers, interrupt handling, command submission, DMA setup, and any firmware or userspace ABI that assumes the same register layout.

## Risks
The helpers mask overflow rather than validating field ranges, so callers can accidentally truncate too-large values. Many reserved fields have helpers, which can make it easy to write nonzero reserved bits if callers use them incorrectly. Because the file is generated, manual edits are high risk and likely to be lost. Register-map drift between Mesa XML, kernel driver, and hardware would cause difficult-to-debug accelerator failures.

## Test Signals
Useful signals include compile coverage of all driver translation units that include the header, sparse or clang warnings for missing `uint32_t`, MMIO trace comparison against known-good programming sequences, interrupt-mask/status tests, register readback tests where hardware supports it, and accelerator smoke tests that exercise CNA, DPU, PPU, RDMA, and DMA paths.

# sources/distributed-fs/ceph-client/drivers/accessibility/Kconfig Research

## Purpose
This Kconfig file creates the top-level `ACCESSIBILITY` menu and gates accessibility-specific kernel options. It documents the subsystem scope: devices and software adapters for disabled users, including braille devices, speech synthesis, and keyboard remapping.

## Important Options
`menuconfig ACCESSIBILITY` is a boolean visibility gate. Selecting it does not build code by itself; it exposes subordinate options. `config A11Y_BRAILLE_CONSOLE` enables console output on a braille device and depends on `VT` and `SERIAL_CORE_CONSOLE`. The file also includes `drivers/accessibility/speakup/Kconfig`, making Speakup configuration available only when `ACCESSIBILITY` is enabled.

## Control Flow
Kconfig control flow is declarative. If `ACCESSIBILITY=n`, all enclosed options are skipped and disabled. If `ACCESSIBILITY=y`, the braille console option and Speakup submenu are evaluated. `A11Y_BRAILLE_CONSOLE` can only be selected when virtual terminal and serial console support are available.

## State And Persistence
The persisted state is the generated kernel `.config`: `CONFIG_ACCESSIBILITY`, `CONFIG_A11Y_BRAILLE_CONSOLE`, and any `CONFIG_SPEAKUP*` values. No runtime state is created by this file.

## Dependencies And Integration Points
This integrates with the kernel Kconfig system, the drivers build tree, VT console support, serial console support, and the Speakup Kconfig file. The braille help text also documents a runtime boot integration point: `console=brl,ttyS0` with serial-console-style options.

## Risks
Because `ACCESSIBILITY` is only a menu gate, users may incorrectly expect it to build functionality by itself. The braille option is tightly tied to serial-console support and currently documents only VisioBraille support. Moving the `source` line outside the `if ACCESSIBILITY` block would alter visibility and dependency behavior for Speakup.

## Test Signals
Test with `make menuconfig` or `scripts/kconfig/conf` to confirm visibility, with `CONFIG_ACCESSIBILITY=n` to ensure no child options survive, and with `VT` or `SERIAL_CORE_CONSOLE` disabled to confirm the braille console dependency is enforced.

# sources/distributed-fs/ceph-client/drivers/accessibility/braille/braille_console.c Research

## Purpose
`braille_console.c` provides minimal kernel support for a serial VisioBraille display. When registered through `console=brl,...`, it can mirror recent console output to a 40-cell braille device and let the user switch into a virtual-console browsing mode with keyboard navigation.

## Important APIs And Functions
The external registration API is `braille_register_console()` and `braille_unregister_console()`, called by console setup code. `braille_write()` encodes a 40-cell buffer into the VisioBraille wire format with escaping and checksum, avoids duplicate writes with `lastwrite`, and dispatches through `braille_co->write`. `keyboard_notifier_call()` handles Insert, arrows, Home, PageUp, PageDown, and lock-state feedback beeps. `vt_notifier_call()` tracks `VT_WRITE` and `VT_UPDATE` events. `vc_refresh()`, `vc_follow_cursor()`, and `vc_maybe_cursor_moved()` maintain and render a 40-column slice of the active virtual console.

## Control Flow
Registration optionally calls the underlying serial console setup, marks the console enabled, stores it in `braille_co`, then registers keyboard and VT notifiers. Console output arrives via VT notifications and updates `console_buf`. Pressing Insert switches from recent-message mode to VC browsing. In browsing mode, navigation keys adjust `vc_x` and `vc_y`, refresh the visible slice, and consume handled keys with `NOTIFY_STOP`. Unregistration removes notifiers and clears the console pointer.

## State And Persistence
State is process-global within the driver: `sound`, `console_buf`, `console_cursor`, `vc_x`, `vc_y`, last cursor coordinates, `console_show`, `console_newline`, `lastVC`, and `braille_co`. It is volatile and reset on boot/module lifetime. There is no persistent storage.

## Dependencies And Integration Points
The file depends on console, VT, keyboard notifier, console map translation, selection/vt internals, input key codes, module parameters, and `kd_mksound()`. It integrates with serial console setup and virtual-terminal screen buffers.

## Risks
The implementation is device-specific and assumes 40 cells. Global state and notifier callbacks require careful lifetime handling around unregister. The code reads screen glyphs by offset and depends on VT internals. `braille_write()` silently maps non-byte glyphs to `?`, so Unicode output loses information. Navigation boundary logic depends on `vc_cols >= WIDTH`; narrow consoles would need review.

## Test Signals
Boot with `console=brl,ttyS0` and verify serial setup, duplicate suppression, message display, Insert mode switching, arrow navigation, cursor following, VT switching flushes, lock-key beep feedback with `sound=1`, and clean unregister without notifier callbacks after removal.

# sources/distributed-fs/ceph-client/drivers/accessibility/speakup/Makefile Research

## Purpose
The Speakup Makefile maps Kconfig symbols to synthesizer driver objects, assembles the core `speakup.o` composite object, and defines host-tool generation steps for keymap headers.

## Important Build Rules
Each `CONFIG_SPEAKUP_SYNTH_*` option adds a matching `speakup_*.o`. `obj-$(CONFIG_SPEAKUP) += speakup.o` builds the core. `speakup-y` includes `buffers.o`, `devsynth.o`, `i18n.o`, `fakekey.o`, `main.o`, `keyhelp.o`, `kobjects.o`, `selection.o`, `spk_ttyio.o`, `synth.o`, `thread.o`, and `varhandlers.o`; `serialio.o` is added with `CONFIG_SPEAKUP_SERIALIO`.

Generated files are central: `makemapdata` emits `mapdata.h`, `genmap` consumes `speakupmap.map` plus `mapdata.h` to emit `speakupmap.h`, and `main.o` depends on `speakupmap.h`. `clean-files` removes the generated headers.

## Control Flow
Kbuild first builds host programs as needed, runs `makemapdata` with `TOPDIR` and `SPKDIR`, builds `genmap.o` after `mapdata.h`, runs `genmap`, and only then builds `main.o` with the generated keymap header.

## State And Persistence
Generated state exists under the object directory as `mapdata.h` and `speakupmap.h`; it is build-local and cleaned by kbuild. Runtime state is in the linked Speakup objects.

## Dependencies And Integration Points
The file depends on kbuild host program support, `makemapdata.c`, `genmap.c`, `speakupmap.map`, headers consumed by `makemapdata`, and all Speakup implementation objects. It integrates Kconfig selections with actual driver link composition.

## Risks
Generated-header ordering is fragile: `main.o` requires `speakupmap.h`, and `genmap.o` requires `mapdata.h`. Missing dependencies can create parallel-build races. Renaming synthesizer symbols or objects without synchronized changes breaks driver builds.

## Test Signals
Use parallel builds such as `make -jN drivers/accessibility/speakup/` to catch dependency races. Test `CONFIG_SPEAKUP=y/m`, individual synthesizer modules, clean rebuilds, and `make clean` behavior for generated headers.

# sources/distributed-fs/ceph-client/drivers/accessibility/speakup/buffers.c Research

## Purpose
`buffers.c` implements Speakup's fixed-size speech synthesis ring buffer and TTY throttling hooks. It queues `u16` characters for the active synthesizer and helps prevent console writers from outrunning speech output.

## Important APIs
Exported functions are `speakup_start_ttys()`, `synth_buffer_empty()`, `synth_buffer_getc()`, `synth_buffer_peek()`, `synth_buffer_skip_nonlatin1()`, and `synth_buffer_clear()`. `synth_buffer_add()` is the write-side queue function used inside Speakup. Internal helpers include `speakup_stop_ttys()` and `synth_buffer_free()`.

## Control Flow
`synth_buffer_add()` first drops data if `synth->alive` is false, avoiding TTY stoppage that cannot be recovered by a dead synth thread. When free space falls below 100 entries it starts the synth and stops TTYs; when only one slot is free it drops the new character. Otherwise it writes to `buff_in`, wraps at `buffer_end`, and clears `spk_paused`. Readers call `synth_buffer_getc()` or `peek()` and wrap `buff_out` similarly. `synth_buffer_skip_nonlatin1()` advances past non-Latin-1 values for synthesizers that cannot emit them.

## State And Persistence
The state is a static `u16 synth_buffer[8192]` plus `buff_in`, `buff_out`, and `buffer_end`. It is volatile and module-lifetime only. TTY stopped state lives in VT/TTY structures and is affected by stop/start calls.

## Dependencies And Integration Points
This file depends on `speakup_console`, `vc_cons`, `synth`, `synth_start()`, `spk_paused`, and kernel TTY helpers. It integrates with the Speakup synth thread and console ingestion path.

## Risks
The ring buffer has no internal locking; callers must use the Speakup locking discipline. If the synth dies after TTYs are stopped, recovery depends on later `speakup_start_ttys()` from a live context. Buffer pressure drops characters when full. `speakup_start_ttys()` has a subtle guard around `speakup_console[i]->tty_stopped` that should be reviewed with console state semantics.

## Test Signals
Stress high-volume console output, synth death/restart, buffer wraparound, full-buffer dropping, non-Latin-1 skipping, and TTY stop/start recovery. Lockdep and KCSAN are useful around concurrent producer and synth-thread consumption.

# sources/distributed-fs/ceph-client/drivers/accessibility/speakup/devsynth.c Research

## Purpose
`devsynth.c` exposes Speakup speech injection devices to userspace through misc devices `/dev/synth` and `/dev/synthu`. The former accepts byte-oriented Latin-1 text and writes directly to the active synth; the latter accepts UTF-8, decodes it to `u16`, queues it in the synth buffer, and starts speech output.

## Important APIs
Public lifecycle functions are `speakup_register_devsynth()` and `speakup_unregister_devsynth()`. File operations include `speakup_file_open()`, `speakup_file_release()`, `speakup_file_read()`, `speakup_file_write()`, and `speakup_file_writeu()`. The misc devices use dynamic minors and names `synth` and `synthu`.

## Control Flow
Open fails with `-ENODEV` if no synth exists and uses `xchg(&dev_opened, 1)` to enforce a single open across both devices. Latin-1 writes copy userspace data in 256-byte chunks, take `speakup_info.spinlock`, and call `synth_write()`. UTF-8 writes copy chunks, use `synth_utf8_get()` to decode complete sequences, skip invalid data, defer incomplete tails by reducing `bytes`, then under the same spinlock call `synth_buffer_add()` for each decoded value and `synth_start()`. Reads return EOF.

## State And Persistence
Static flags track misc registration and one-open status: `synth_registered`, `synthu_registered`, and `dev_opened`. No user data persists after write completion. UTF-8 partial sequence progress is maintained only within a write call through `want` and `count`.

## Dependencies And Integration Points
This file depends on miscdevice registration, user copy helpers, Speakup globals, the synth write path, UTF-8 decoding, synth buffer, and the Speakup spinlock.

## Risks
One `dev_opened` flag serializes both devices, so opening `/dev/synth` blocks `/dev/synthu`. `dev_opened` is reset with a plain store on release after atomic open; this is simple but worth concurrency review. Invalid UTF-8 is silently skipped. Large writes can return partial completion for incomplete UTF-8 tails. Holding the Speakup spinlock around synth operations requires those operations to be IRQ-safe and non-sleeping.

## Test Signals
Test misc registration and deregistration, single-open `-EBUSY`, no-synth `-ENODEV`, Latin-1 writes, UTF-8 valid/invalid/incomplete writes, partial returns, and module unload with devices registered.

# sources/distributed-fs/ceph-client/drivers/accessibility/speakup/fakekey.c Research

## Purpose
`fakekey.c` creates a virtual input keyboard used by Speakup to inject a synthetic Down Arrow key press into the input subsystem and to identify that synthetic key path.

## Important APIs
`speakup_add_virtual_keyboard()` allocates and registers an `input_dev` named `Speakup`. `speakup_remove_virtual_keyboard()` unregisters it. `speakup_fake_down_arrow()` emits press and release events for `KEY_DOWN` followed by `input_sync()`. `speakup_fake_key_pressed()` reports whether the current CPU is inside such synthetic reporting.

## Control Flow
Initialization allocates an input device, fills identity fields, sets `EV_KEY` and `KEY_DOWN`, then registers it. On registration failure, it frees the device and clears the global pointer. Injection disables local interrupts, disables preemption to keep CPU-local state stable, sets the per-CPU `reporting_keystroke` flag, reports key down/up/sync, clears the flag, then restores preemption and interrupts.

## State And Persistence
State consists of global `virt_keyboard` and per-CPU `reporting_keystroke`. It persists only while Speakup is loaded or initialized.

## Dependencies And Integration Points
The file depends on the Linux input subsystem, per-CPU variables, preemption and IRQ controls, and Speakup callers that need to distinguish synthetic input via `speakup_fake_key_pressed()`.

## Risks
`speakup_fake_down_arrow()` assumes `virt_keyboard` is non-NULL and registered; callers must only inject after successful setup. Disabling local IRQs and preemption keeps state coherent but makes the section sensitive to any future sleeping call. Only `KEY_DOWN` is advertised, so expanding fake-key support requires updating key bits.

## Test Signals
Test add/remove lifecycle, failure handling for input registration, injected event sequence with evtest or input tracing, current-CPU flag behavior during callback handling, and no injection after removal.

# sources/distributed-fs/ceph-client/drivers/accessibility/speakup/genmap.c Research

## Purpose
`genmap.c` is a host build tool that converts `speakupmap.map` into the generated `speakupmap.h` keymap data consumed by Speakup. It parses key/modifier/function names from `mapdata.h`, validates mapping syntax, builds per-key state tables, and emits a compact numeric initializer.

## Important APIs And Data
The program's only public interface is its command-line usage: `genmap filename`. Internal state includes `key_data[MAXKEYVAL][16]`, `shift_table[17]`, `max_states`, `flags`, and `map_ver`. It consumes generated symbols such as `init_key_data`, `key_table`, `struct st_key`, `find_key()`, `add_key()`, `open_input()`, `oops()`, and `infile` from `mapdata.h` and `utils.h`.

## Control Flow
`main()` clears tables, initializes shift state zero, imports known names through `add_key()`, opens the map file, then parses each line. Modifiers must appear before the input key, `=` separates the Speakup function, and duplicate key/state assignments are rejected. After parsing, it locates `spk_key` and `spk_lock`, mirrors those functions into key-up states by adding the Speakup state bit, counts used keys, and prints version, key count, state count, shift states, flags, each used key row, and a trailing version marker.

## State And Persistence
All state is process-local during the build. Persistent output is the generated header captured by kbuild.

## Dependencies And Integration Points
This tool is built and run by the Speakup Makefile. It depends on libc, `libgen.h`, `ctype.h`, `mapdata.h`, `utils.h`, and the Speakup map file. It integrates with `main.o` through the generated `speakupmap.h`.

## Risks
The parser uses `strtok()` and assumes non-empty parsed lines; blank lines may leave `cp` NULL before `*cp`. It enforces at most 16 shift states and byte-sized function values. Output is raw C initializer text, so any format change must match Speakup consumers. The arbitrary `map_ver` is used as a consistency sentinel.

## Test Signals
Test with the canonical `speakupmap.map`, malformed lines, unknown names, duplicate combinations, too many shift states, blank/comment lines, and compare generated output against expected fixtures in a clean parallel build.

# sources/distributed-fs/ceph-client/drivers/accessibility/speakup/i18n.c Research

## Purpose
`i18n.c` implements Speakup's message catalog. It stores default English strings, lets users override messages, validates formatted-message overrides, groups message ranges for sysfs-style operations, initializes defaults, and frees user strings at unload.

## Important APIs
`spk_msg_get()` returns the active string for an enum index. `spk_msg_set()` replaces one message with a `kmemdup_nul()` copy after bounds checks and format validation for formatted messages. `spk_find_msg_group()` locates named groups such as `ctl_keys`, `colors`, `formatted`, `function_names`, `key_names`, `announcements`, and `states`. `spk_reset_msg_group()`, `spk_initialize_msgs()`, and `spk_free_user_msgs()` manage active/default pointers.

## Control Flow
Initialization copies `speakup_default_msgs` into `speakup_msgs`. Reads index directly into the active pointer table. Setting a message allocates first, validates format specifier compatibility if the target is in the formatted range, then under `speakup_info.spinlock` frees the old user string if needed and installs the new pointer. Reset and free paths walk ranges under the same spinlock and restore default pointers.

## State And Persistence
State is two arrays indexed by `enum msg_index_t`: immutable default pointers and mutable active pointers. User overrides are dynamically allocated and persist until reset, replacement, or module unload. No disk persistence exists in this file.

## Dependencies And Integration Points
The file depends on `i18n.h` enum ordering, kernel allocation and string helpers, `speakup_info.spinlock`, and callers in key help, kobjects, and speech output. Format validation is tied to default formatted strings and supported conversions `%c`, `%d`, `%s`, `%x`, and `%ld`.

## Risks

# sources/distributed-fs/ceph-client/drivers/accessibility/speakup/i18n.h Research

## Purpose
`i18n.h` declares Speakup's message-index ABI and message-catalog APIs. It is the authoritative ordering for all message groups used by the implementation and callers.

## Important Types And APIs
`enum msg_index_t` defines ranges for announcements, formatted messages, control keys, colors, key states, key names, and function names. It includes range sentinels such as `MSG_ANNOUNCEMENTS_START`, `MSG_FORMATTED_START`, `MSG_KEYNAMES_START`, and `MSG_FUNCNAMES_END`. `struct msg_group_t` names a contiguous range. Declared APIs are `spk_msg_get()`, `spk_msg_set()`, `spk_find_msg_group()`, `spk_reset_msg_group()`, `spk_initialize_msgs()`, and `spk_free_user_msgs()`.

## Control Flow
The header has no runtime control flow. Its enum values drive array indexing, range validation, help text lookup, group reset loops, and user-visible message selection.

## State And Persistence
No state is stored here. The enum values are a persistent in-kernel contract between implementation files and any sysfs/kobject interfaces that expose or consume message indices and groups.

## Dependencies And Integration Points
This header integrates tightly with `i18n.c`, `keyhelp.c`, Speakup command enums in other headers, cursor tracking, edge navigation, and kobject message management. Comments explicitly require cursor messages to match `enum cursor_track` and edge messages to match `enum edge`.

## Risks
Reordering enum members can break array lookups and spoken command descriptions. Adding a formatted message requires adding a default string and ensuring the validator in `i18n.c` accepts the needed conversion specifiers. Adding a function name requires synchronizing `keyhelp.c`'s `funcvals[]` mapping.

## Test Signals
Build tests catch missing defaults only indirectly. Stronger checks include verifying every enum value that should be user-visible has a non-NULL default, validating group boundaries, exercising help output for function names, and testing message overrides by group.

# sources/distributed-fs/ceph-client/drivers/accessibility/speakup/keyhelp.c Research

## Purpose
`keyhelp.c` implements Speakup's interactive help mode. It maps Speakup command functions to their assigned keys, speaks key names and command descriptions, and supports browsing help by initial letter or cursor keys.

## Important APIs And Data
The external entry point is `spk_handle_help(struct vc_data *vc, u_char type, u_char ch, u_short key)`. Internal tables include `funcvals[]`, which maps function-name message order to Speakup command constants, `key_offsets[MAXFUNCS]`, `key_data[MAXKEYS]`, `letter_offsets[26]`, `masks[]`, `state_tbl`, `cur_item`, and `nstates`.

## Control Flow
On first use, `help_init()` derives first-letter offsets from localized function names and locates the generated key state table in `spk_our_keys`. Entering help through the Speakup help command sets `spk_special_handler`, speaks help instructions, and calls `build_key_data()`. `build_key_data()` counts command assignments across key states, allocates offsets into the static `key_data` array, and stores key/state pairs. In help mode, Space exits, letters jump to command groups, cursor up/down moves through functions, and other recognized keys or commands speak either the key name or command description.

## State And Persistence
State is static and volatile: cached letter offsets, built key offsets/data, current item, state table pointer, and state count. It is rebuilt on help entry to reflect remapped keys. `spk_special_handler` in broader Speakup state persists while help mode is active.

## Dependencies And Integration Points
The file depends on keyboard type constants, generated `spk_our_keys`, Speakup command constants, i18n messages from `spk_msg_get()`, and speech output through `synth_printf()`.

## Risks
`funcvals[]` must remain ordered with `MSG_FUNCNAMES_START` entries; drift gives wrong descriptions. `MAXFUNCS` and `MAXKEYS` are fixed limits, and `build_key_data()` stops filling if offsets exceed `MAXKEYS`, potentially losing help mappings. Localized function names affect first-letter navigation and can collide or produce non-ASCII initials that do not fit the `a` to `z` flow.

## Test Signals
Exercise entering/exiting help, letter jumps, up/down navigation, key lookup for assigned and unassigned commands, remapping followed by help rebuild, localized message sets, and boundary cases where generated keymaps approach static table limits.
