# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/vuid_state.h

`vuid_state.h` declares the client-facing interface for the virtual user input device state package. The package tracks the state of events generated by one or more physical devices that produce `Firm_event` input events, with the conceptual VUID event namespace described by `vuid_event.h`.

The public state handle is intentionally opaque: `Vuid_state` is a `caddr_t`, with `VUID_STATE_NULL` as the null sentinel. The API consists of `vuid_set_value()` to update state from a `Firm_event`, `vuid_get_value()` to query a value by VUID event ID, `vuid_destroy_state()` to free a state object, and `vuid_copy_state()` to duplicate state. Comments on mutating/copying/destruction functions warn callers not to invoke them in critical sections or at interrupt level, implying allocation or blocking behavior in the implementation.

This header is the stable consumer contract, while `vuid_store.h` defines the private storage structures used behind the opaque handle.

# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/vuid_store.h

`vuid_store.h` is the private implementation header for VUID state storage. It backs the opaque state type exposed by `vuid_state.h` and is tuned for compact storage of mostly-boolean input state with a small number of integer-valued input codes.

The comments describe the typical state layout: a VKEY segment containing location absolute/delta values, plus an ASCII/meta segment of boolean values. The package knows how to keep absolute and delta location values related, so mouse or locator movement can update complementary state. The storage design optimizes for high-volume mouse tracking and grouped checks of modifier/shift-button state.

`Vuid_value` is a linked-list node for one non-boolean VUID value, storing a segment-relative offset and integer value. `Vuid_seg` is a linked-list node for a VUID segment. It stores the segment base address, a bit array for boolean state, a parallel bit array indicating which offsets are integer-backed, and a linked list of `Vuid_value` nodes for those integer values. Segment and value lists are deliberately unsorted unless profiling shows a need.

The bit manipulation macros operate on segment-relative offsets and use a most-significant-bit-first convention within each byte. They set, clear, and test the boolean-state array and the integer-presence array. `vuid_cstate_to_state()` casts the opaque client state to the private `Vuid_seg *` representation.

Key dependencies are the VUID segment sizing constants such as `VUID_SEG_SIZE`, supplied by the VUID event namespace headers. The main correctness risk is that callers must keep offsets within segment bounds; the macros perform no bounds checking.

# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/vuid_wheel.h

`vuid_wheel.h` defines VUID mouse-wheel ioctl and data structures. It includes `sys/vuid_event.h` for the `VUIOC` ioctl base.

The header caps the supported wheel count at `VUID_WHEEL_MAX_COUNT` and defines ioctls to get wheel count, get wheel information, get wheel state, and set wheel state. `wheel_info` carries a version field, wheel ID, and format. Supported formats are unknown, horizontal, and vertical. `wheel_state` carries a version field, wheel ID, and state flags. The only defined state flag is `VUID_WHEEL_STATE_ENABLED`.

Wheel event values encode deltas in the low byte. `VUID_WHEEL_DELTAMASK` masks that byte, and `VUID_WHEEL_GETDELTA()` casts it to `signed char`, preserving negative wheel movement encoded in 8-bit two's-complement form.

This file is an ABI shim between VUID-aware input drivers and consumers that query wheel topology and enablement.

# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/vxlan.h

`vxlan.h` provides the common VXLAN wire-header definitions. It includes fixed-width integer types and exposes constants for the 8-byte VXLAN header, the 3-byte VXLAN network identifier, the VNI-present flag, and the shift used to position/extract the VNI field.

`vxlan_hdr_t` is packed to match the network header layout exactly. It contains a 32-bit flags word and a 32-bit VNI/reserved word. `VXLAN_F_VDI` is the standard VXLAN valid-network-ID flag bit, and `VXLAN_ID_SHIFT` accounts for the reserved low byte in the VNI field.

The file is intentionally small and shared by VXLAN implementation code that needs stable packet-format definitions.

# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/wait.h

`wait.h` defines process-wait option flags, wait-status decoding macros, and userland wait-family prototypes. It is gated by feature-test macros to expose POSIX/XPG/extension interfaces with the correct namespace.

Always-visible wait options include `WUNTRACED` and `WNOHANG`. Under broader X/Open or extension exposure, the header adds `WEXITED`, `WTRAPPED`, `WSTOPPED`, `WCONTINUED`, `WNOWAIT`, and `WOPTMASK`. Status helper constants and macros expose low/high-byte decoding, stopped/continued/core-dump tests, and signal/exit status extraction.

The standard wait status macros use the traditional encoded integer layout: low byte zero means exited, low byte nonzero with no high-byte data means signaled, low byte `0177` with high-byte data means stopped, and `0177777` represents continued state.

Outside `_KERNEL`, the header declares `wait()`, `waitpid()`, and, when permitted by feature tests, `waitid()`, legacy `wait3()`, and extension `wait4()`. It includes `resource.h`, `siginfo.h`, and `procset.h` only when those declarations are needed.
<!-- END FILE RESEARCH: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/wait.h -->

# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/waitq.h

`waitq.h` declares a kernel-only wait queue abstraction for scheduler threads. The exported `waitq_t` stores a dispatcher lock, first queued thread pointer, queued-thread count, and a blocked flag. The lock protects all fields.

The API initializes and finalizes queues, enqueues a `kthread_t`, wakes a specific queued thread, changes priority for a queued thread, wakes the first queued thread, tests emptiness, and blocks or unblocks future enqueues. `waitq_enqueue()` returns success/failure because enqueue attempts fail when the queue is blocked.

This header depends on kernel thread and dispatcher-lock types. It is a compact synchronization primitive for code that needs explicit control over waiters rather than a plain condition variable.
<!-- END FILE RESEARCH: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/waitq.h -->

# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/watchpoint.h

`watchpoint.h` defines the VM-side data structures and kernel helper APIs for process watchpoints. The user-facing watchpoint interface is in `proc(5)` and `sys/procfs.h`; this header describes how the kernel represents watched ranges and the pages whose protections are modified to detect access.

`watched_area_t` represents one watched virtual-address interval. It is stored in an AVL tree sorted by user virtual address and records start address, end address, and watch type flags. `watched_page_t` represents one affected page, also AVL-linked and additionally linked into the process protection list. It stores the page address, modified and original protections, reference counts for user/kernel `pr_mappage()` mappings by access class, flags, and counts of read/write/execute watched areas intersecting the page.

Page flags distinguish pages whose watch protections are temporarily restored (`WP_NOWATCH`) from pages that need a `SEGOP_SETPROT()` update (`WP_SETPROT`).

Kernel helpers include copy and word-access variants that ignore watchpoints, region-scoped disable/enable functions for copyops, thread-wide watchpoint enable/disable, global setup, predicates for watch pages and watchpoints, single-step watch handling, AVL comparators, and `watch_copyops`. `pr_find_watched_area()` supports lookup/insertion-position discovery in a process watch-area tree.

Correctness depends on carefully bracketing temporary disables and restoring protections after kernel copies; otherwise kernel-internal accesses could spuriously trigger user watchpoints or leave watched pages unprotected.
<!-- END FILE RESEARCH: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/watchpoint.h -->

# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/xti_inet.h

`xti_inet.h` defines Internet-specific XTI option levels, option names, option structures, and IP TOS helper constants. The file explicitly marks itself private and says applications should include the public `<xti_inet.h>` wrapper instead.

The header preserves legacy non-`T_` constants unless `_XPG5` is defined. These include `INET_TCP`, `TCP_NODELAY`, `TCP_MAXSEG`, `TCP_KEEPALIVE`, `INET_UDP`, `UDP_CHECKSUM`, `INET_IP`, and selected `IP_*` option numbers. Comments explain that some constants are exposed only for XTI specification test assertions or compatibility, and their semantics may follow established `<netinet/in.h>` behavior rather than strict XTI semantics.

The preferred modern constants use the `T_` prefix: `T_INET_TCP`, `T_TCP_NODELAY`, `T_TCP_MAXSEG`, `T_TCP_KEEPALIVE`, `T_INET_UDP`, `T_UDP_CHECKSUM`, `T_INET_IP`, and `T_IP_*` options. `struct t_kpalive` is the XTI TCP keepalive option payload, with on/off and timeout fields using `t_scalar_t`.

For IP type-of-service, the header defines precedence levels from routine through network control and service bits for low delay, high throughput, high reliability, and low cost. `SET_TOS()` combines precedence and service bits into the encoded TOS byte.

This file is primarily ABI compatibility glue between XTI and the Internet protocol option namespaces.
<!-- END FILE RESEARCH: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/xti_inet.h -->

# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/xti_osi.h

`xti_osi.h` defines ISO/OSI-specific XTI option and management constants. Most content is hidden when `_XPG5` is defined, reflecting that these compatibility definitions are for older XTI exposure.

The header defines ISO transport classes `T_CLASS0` through `T_CLASS4`, priority values, protection levels, and the obsolete default TPDU length constant `T_LTPDUDFLT`. Comments state that some options are exposed because XTI specification tests require them, even when the system may not implement the corresponding protocol behavior.

Quality-of-service helper structures model rates and request values: `struct rate` has target and minimum acceptable values; `struct reqvalue` carries called/calling rates; `struct thrpt` combines maximum and average throughput; and `struct transdel` combines maximum and average transit delay.

`ISO_TP` is the protocol level for ISO transport. Connection-oriented option constants cover throughput, transit delay, error/failure probabilities, establishment/release delays, resilience, protection, priority, and expedited data. Connectionless aliases map selected options onto the same values. Management options include TPDU length, acknowledgement/reassignment timers, extended format, flow control, checksum, network expedited data, receipt confirmation, preferred class, and alternate classes.

This header is a standards-compatibility namespace rather than an implementation driver.
<!-- END FILE RESEARCH: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/xti_osi.h -->

# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/zcons.h

`zcons.h` defines constants for the zone console driver. It names the global-zone manager side minor node as `globalconsole` and the non-global-zone subsidiary side minor node as `zoneconsole`. The subsidiary name is chosen so global-zone tools see a meaningful device name, while links inside the zone present it as `console`.

`ZC_IOC` is the base for zone-console ioctls. `ZC_HOLDSUBSID` and `ZC_RELEASESUBSID` instruct the manager side to hold or release a reference to the subsidiary vnode. The comments explain why zoneadmd uses these around console device-node lifetime: holding the subsidiary preserves the STREAMS anchor and `ptem` module even if `ttymon` inside the zone pops STREAMS modules, maintaining terminal semantics while the zone is running.

This file is tightly coupled to the `uts/common/io/zcons.c` implementation and zoneadmd console setup/teardown sequencing.
<!-- END FILE RESEARCH: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/zcons.h -->

# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/zmod.h

`zmod.h` declares the public kernel interface for zmod, an in-kernel RFC 1950-compatible compression/decompression library. The implementation lives under `usr/src/uts/common/zmod/`.

The header mirrors common zlib status and configuration constants: success, stream end, dictionary needed, errno-style failure, stream/data/memory/buffer/version errors, and compression levels from no compression through best speed, best compression, and default compression.

The exported routines are `z_uncompress()`, `z_compress()`, `z_compress_level()`, and `z_strerror()`. The compress/uncompress functions take destination pointer and destination-size pointer plus source pointer and source size, matching the common zlib pattern where the destination size is both input capacity and output length.

This is a small ABI header used by kernel consumers that need compressed data handling without depending on userland zlib.
<!-- END FILE RESEARCH: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/zmod.h -->

# File Research: sources/os/illumos/illumos-gate/usr/src/uts/common/sys/zone.h

`zone.h` is the central private zone contract for illumos. It exposes user/kernel shared constants for zone IDs, zone syscall subcommands, attributes, status/event strings, subprocess exit codes, zone creation arguments, and network attribute payloads. Under `_KERNEL`, it also defines the full `zone_t` structure, zone reference tracking, zone-specific data, visibility macros, and zone management APIs.

The shared namespace defines zone ID limits and special IDs: `GLOBAL_ZONEID` is 0, user-created zones start at 1, `MAX_ZONEID` is 9999, and `ALL_ZONES` is the special token for operations spanning every zone. Zone syscall subcodes cover create, destroy, get/set attributes, enter, list, shutdown, lookup, boot, and datalink add/delete/check/list operations. Zone attributes cover root, name, status, privilege set, unique ID, pool ID, init PID/name/restart policy, boot arguments, brand, physical memory cap, scheduling class, flags, hostid, allowed filesystems, network data, and security flags. Brand-specific attributes begin at `ZONE_ATTR_BRAND_ATTRS`.

The event constants define the sysevent channel/class/subclass for zone status changes and the status strings used in those events. Callback attribute names include zone name, old/new state, timestamp, and zone ID. Subprocess exit values distinguish success, usage failure, incomplete-but-no-recovery-needed failure, and fatal failure requiring recovery, matching zoneadm/zoneadmd orchestration needs.

`zone_def` and its 32-bit variant describe zone creation input: name, root, privilege set, resource-control buffer, extended error output, ZFS dataset buffer, label matching, DOI, sensitivity label, and creation flags. Extended errors include unknown, chrooted creation attempt, existing mounts under the zone path, and duplicate label. `zone_status_t` enumerates the lifecycle from uninitialized through initialized, ready, booting, running, shutting down, empty, down, dying, and dead. A comment warns that mdb's `zone_status_names` must be kept in sync. `zone_cmd_arg_t` and `zone_cmd_rval_t` define the door protocol used to communicate with zoneadmd for commands such as ready, boot, reboot, halt, mount, unmount, and shutdown.

Name and path constants constrain zone names to 64 bytes because they are embedded in AF_UNIX socket paths. `GLOBAL_ZONENAME`, `ZONENAME_REGEXP`, `ZONES_TMPDIR`, and `ZONE_DOOR_PATH` define the public naming and zoneadmd door path conventions. Zone flags distinguish logged reference counts, uniquely hashed Trusted Extensions labels, scratch zones, and exclusive-IP zones. `ZCF_NET_EXCL` is the corresponding create flag. `zone_net_data_t` carries network attribute records for zone network address or default-router data, including datalink ID and variable payload.

The kernel-only section defines reference tracking and accounting support. `zone_ref_subsys_t` assigns subsystem buckets for tracked holds from NFS, NFSv4, SMBFS, MNTFS, LOFI, VFS, and IPC. Each tracked `zone_ref_t` links into a zone's reference list for debugger visibility. `zone_dataset_t` records ZFS datasets exported to a zone. Kstat structures cover generic zone resource values, memory-cap paging statistics, CPU microstate/load/fork-failure/init/boot statistics, and other per-zone counters.

`zone_t` is the in-kernel zone object. Immutable identity fields include name, nodename/domain strings, hostid behavior, root vnode/path, zone ID, unique generation ID, brand, root path length, and selected creation flags. `zone_lock` protects reference counts, credential holds, subsystem reference counts, the reference list, task count, flags, zone-specific data list, and `zone_pfexecd`. Other fields have dedicated lock domains: `zone_linkage` is protected by `zonehash_lock`; status and zone kernel-thread list by `zone_status_lock`; LWP counts by `zone_nlwps_lock`; memory reservation/caps by `zone_mem_lock`; LOFI caps by `zone_rctl_lock`; mounted filesystems by `vfs_list_lock`; pool binding by `pool_lock`; processor set binding by `cpu_lock`; datalink list by `zone_lock`; mntfs private data by `zone_mntfs_db_lock`; memory-cap stats by `zone_mcap_lock`; misc stats by `zone_misc_lock`; and mount/create/destroy synchronization by `zone_mount_lock` plus `zone_mount_cv`.

The `zone_t` fields span process/task/LWP accounting, System V IPC and shared memory usage, zone-wide rctls, locked-memory and swap limits, LOFI limits, zone-specific data, zsched and init process state, boot errors and arguments, physical memory caps, privilege set, mounted VFS list, zone kcred, pool/processor-set binding, boot time, visible CPU counts, exported datasets, Trusted Extensions label and MLP state, init restart policy, scheduling class, swap/locked-memory/process kstats, datalink list, netstack pointer, CPU caps, audit context, mntfs state, pfexec daemon registration, allowed filesystem list, memory-cap paging stats, default security flags, microstate aggregation, fork-failure counters, load average state, FSS usage counters, DTrace private counters, and mount-in-progress state.

The exported kernel API covers initialization, the `zone()` syscall implementation, zone holds/releases, tracked reference holds/releases, credential/task holds, lookup by ID/label/name/path, current zone ID retrieval, datalink walking and checks, load-average updates, zone-specific data key creation/deletion/get/set, zone-scoped kernel thread creation and exit, status waits with timeout/signal variants, status retrieval, hostid and kcred lookup, pool and pset get/set, visible CPU counts, dataset visibility checks, zone-aware `kadmin()`, global shutdown, mount-progress bracketing, and zone walking. Global state includes `zone0`, `global_zone`, `maxzones`, and rctl handles for LWPs, processes, locked memory, swap, and LOFI.

Zone-specific data (`ZSD`) lets subsystems register per-zone keys with create, shutdown, and destroy callbacks. `struct zsd_entry` is nominally private to `zone.c` but exposed for mdb. Its flags track needed, in-progress, and completed phases for create/shutdown/destroy. Comments explain this avoids holding locks while invoking callbacks, preventing deadlocks.

The visibility macros implement zone isolation rules: `INGLOBALZONE()` tests whether a process is in the global zone; `HASZONEACCESS()` allows access to same-zone objects or global-zone observers; `ZONE_PATH_VISIBLE()` checks whether a resolved global path lies under a zone root; `ZONE_PATH_TRANSLATE()` maps a visible global path into the zone's path view; and `ZONE_SPECIALPID()` treats PIDs 0 and 1 as visible in all zones. `ZONE_ROOTVP()` and `VN_IS_CURZONEROOT()` are vnode helpers, with comments warning that active ZSD initialization can make `curzone` assumptions unsafe.

This header is a high-blast-radius kernel interface. Changes to enum ordering, `zone_t` field semantics, lock ownership, or ZSD callback state require coordinated updates in zone.c, mdb, resource controls, networking, VFS, process accounting, and zoneadmd-facing userland.
